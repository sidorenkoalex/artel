# QUESTIONS: артефактная ветка новой задачи заводится от origin/main, а не от пина

## Вопросы

1. **Требование 2 ТЗ («Для внешнего target (клон целевого) — родитель
   по тому же правилу для origin целевого») не соответствует
   проверенной архитектуре: какого кода это требование касается?**

   Проверено по коду и ADR:
   - `artifact_branch.commit_files` (строки ~109–127) вызывает
     `write_commit(config.ROOT, ...)` — БЕЗ параметра target/repo,
     жёстко на корень пульта. Родитель первого коммита берётся из
     `gitcmd.branch_head_sha(config.MAIN_BRANCH)` — это `main` ПУЛЬТА,
     не какого-либо целевого проекта.
   - `catalog._new_external_artifact_branch` (строка 168, вызывается
     из `cmd_new` БЕЗ передачи `target`, строка 154) — вызывает тот же
     `commit_files` для ЛЮБОГО target одинаково.
   - Модуль-докстринг `artifact_branch.py` (строки 1–8): «С A7 —
     ЛЮБОЙ target, включая артель... новые задачи артели заводят эту
     ветку тем же кодом, что и любой другой target» — то есть
     артефактная ветка живёт ИСКЛЮЧИТЕЛЬНО в репозитории пульта
     (`config.ROOT`), независимо от target.
   - `snapshot._target_workspace` — «клон целевого» с его собственным
     `origin` существует, но используется ТОЛЬКО при публикации
     снапшота ЗАКРЫТИЯ (`done`/`killed`, без родителя — `write_commit`
     без `parent`), не при заведении задачи и не для родителя первого
     коммита артефактной ветки.
   - ADR-0003 §3д говорит, что для внешних target'ов первичка
     (`tasks/<id>/`) должна жить в `.artel/projects/<target>/`
     (локальный репо БЕЗ remote) — это противоречит наблюдаемому коду
     T094, где она везде живёт в ветке пульта; правка ADR от 27.08
     («для внешних target'ов 3д действует без изменений») этому
     наблюдаемому коду тоже не соответствует буквально.

   Родителя-«целевого-origin» для артефактной ветки в коде просто нет
   — варианты:

   A) Требование 2 — избыточное уточнение: поскольку артефактная
      ветка ЛЮБОГО target (включая внешний) физически коммитится в
      `config.ROOT`, правило требования 1 (fetch `origin/main` пульта)
      уже покрывает и внешний target — отдельного кода не требуется,
      SPEC фиксирует это явно как факт, а не как новый критерий.
   B) Требование 2 предполагает НОВУЮ возможность: обобщить
      `commit_files`/`write_commit`, чтобы параметр repo/target можно
      было передать и для него тоже применялся тот же fetch-правило
      origin/main — даже притом что сегодня ни один вызывающий код
      не пользуется этим путём (код без потребителя, тесты — только
      под сам этот путь).
   C) Требование 2 описывает более крупную архитектурную правку —
      перенос первички внешних target'ов в `.artel/projects/<target>/`
      по ADR-0003 §3д — выходит далеко за рамки «рамка: $15» и
      формулировки инцидента (только про пин `config.MAIN_BRANCH`).

   Дефолт при молчании: **A** — SPEC формулирует требование 2 как
   констатацию (родитель для любого target выбирается тем же кодом
   `commit_files`, работающим только с `config.ROOT`), без отдельного
   AC и без нового кода сверх требования 1; вариант B/C не
   реализуются.

## Контекст

Прочитан `TZ.md` целиком; сверены `orchestrator/artifact_branch.py`,
`orchestrator/gitcmd.py`, `orchestrator/catalog.py` (`cmd_new`,
`_new_external_artifact_branch`), `orchestrator/snapshot.py`,
`docs/adr/0003-target-projects.md` (§3д, ревизия 27.08), прецеденты
fetch `origin/main` без сдвига HEAD в `orchestrator/pin.py` и
`orchestrator/fsm_merge_gate.py` (строка 39) — оба уже делают то, что
просит требование 1, так что для НЕГО архитектурной неясности нет.

Также найдена и прочитана параллельная задача
`01M1TQ0X14Y5B3C87WC0Q31PK2` («отказ push артефактной ветки в журнал
и на повтор; doctor сверяет локальный ref с origin и CI артефактной
ветки») — та самая «задача журнала push» из раздела «Порядок» этого
ТЗ. Она пока в `spec_writing` (SPEC.md там — черновик шаблона, ещё не
заполнен), проверки «артефактная ветка синхронна» в текущем коде
`orchestrator/doctor.py` нет вовсе. Требование 3 текущего ТЗ уже само
предусматривает оба исхода («если она уже есть... иначе — отдельная
проверка») — блокирующего вопроса по нему не завожу, SPEC понесёт
эту развилку как есть с уточнением на момент запуска разработчика
(сверка по `status` задачи 01M1TQ0X14Y5B3C87WC0Q31PK2).
