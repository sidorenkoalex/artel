# SPEC: артефактная ветка новой задачи заводится от origin/main, а не от пина

## Контекст

Инцидент 06.09: `artifact_branch.commit_files` при первом коммите
артефактной ветки берёт родителя из `gitcmd.branch_head_sha(config.MAIN_BRANCH)`
(`orchestrator/artifact_branch.py:118-119`) — головы ЛОКАЛЬНОГО `main`
пульта, то есть пина главной копии (ADR-0013: HEAD главной копии по
построению отстаёт от `origin/main`). Каталог `tasks/` в новой
артефактной ветке наследуется целиком от этого родителя. 06.09
черновики ревьювера, уже удалённые с `origin/main` коммитом f29d97f2,
оказались в артефактных ветках двух задач, заведённых после удаления
(01M1TNMBY8, 01M1TNN4TM): ветки взяли `tasks/` от пина 603efe92, где
файлы ещё были. CI обеих веток красный по guard с первого пуша. Тот же
механизм разнесёт по каждой новой задаче любой мусор или устаревший
артефакт, попавший в пин, пока пин не обновлён.

## Требования

1. Родитель первого коммита артефактной ветки — голова `origin/main`
   (после `git fetch origin main`, без изменения HEAD главной копии:
   пин не двигается). Если `origin` недоступен (нет сети, нет `origin`,
   песочницы) — как сегодня, локальный `main`, с записью в журнал
   задачи («артефактная ветка от локального main: <причина>»).
2. Родитель для внешнего target (клон целевого) выбирается тем же
   кодом требования 1: артефактная ветка любого target, включая
   внешний, физически коммитится в репозиторий пульта
   (`config.ROOT`, `artifact_branch.commit_files` →
   `write_commit(config.ROOT, …)`), отдельного правила или кода для
   «origin целевого» не требуется. Поведение с `parent` при повторных
   коммитах (`branch_head_sha(branch)`, когда ветка уже существует) —
   без изменений.
3. `doctor`: в проверке «артефактная ветка синхронна» (если к моменту
   разработки она уже реализована задачей журнала push
   01M1TQ0X14Y5B3C87WC0Q31PK2 — расширить её; иначе — отдельная новая
   проверка в `orchestrator/doctor.py`) — `warn`, если родитель первого
   коммита артефактной ветки живой задачи не является предком
   `origin/main` (ветка заведена от устаревшего пина с расхождением).
   Какой из двух вариантов применим, определяется по `status` задачи
   01M1TQ0X14Y5B3C87WC0Q31PK2 на момент старта разработки этой задачи.
4. Тесты:
   а) в песочнице с локальным `origin`, ушедшим вперёд от `main`,
      первый коммит артефактной ветки имеет родителем голову
      `origin/main`, и `tasks/` в ветке — состояние `origin`, не пина;
   б) без `origin` — родитель локальный `main`, и в журнал задачи
      записана причина;
   в) HEAD главной копии после `new` не изменился (мутация: `git pull`
      вместо `fetch` обязана быть поймана тестом);
   г) существующие `tests/test_artifact_branch*.py`,
      `tests/test_catalog*.py` остаются зелёными без правки ассертов.

## Критерии приёмки

AC-1. Родитель первого коммита артефактной ветки — голова
`origin/main` после `git fetch origin main`; HEAD главной копии
(локальный `main` пульта) после `new` не изменился ни в одной
операции (проверяется тестом требования 4в, ловящим случайную замену
`fetch` на `pull`).

AC-2. Если `origin` недоступен (нет сети, нет `origin`, песочница) —
родитель первого коммита остаётся локальный `main` (текущее
поведение), и в журнал задачи (`store.journal`) добавлена запись с
причиной вида «артефактная ветка от локального main: <причина>».

AC-3. Для внешнего target отдельного кода или правила не вводится:
родитель первого коммита артефактной ветки выбирается тем же кодом,
что и в AC-1/AC-2, — SPEC фиксирует это как констатацию существующей
архитектуры (артефактная ветка любого target коммитится в
`config.ROOT`), а не как новый критерий с отдельным тестом.

AC-4. Поведение параметра `parent` при повторных коммитах в уже
существующую артефактную ветку (`branch_head_sha(branch)` возвращает
непустое значение) не меняется.

AC-5. `doctor` предупреждает (`warn`), если родитель первого коммита
артефактной ветки живой задачи не является предком `origin/main` —
либо расширением проверки «артефактная ветка синхронна» задачи
01M1TQ0X14Y5B3C87WC0Q31PK2 (если она к моменту разработки уже
реализована), либо отдельной новой проверкой в `orchestrator/doctor.py`
(если нет) — выбор варианта фиксируется разработчиком по факту
`status` задачи 01M1TQ0X14Y5B3C87WC0Q31PK2 на момент начала работы.

AC-6. Тест в песочнице с локальным `origin`, ушедшим вперёд от
`main`: первый коммит новой артефактной ветки имеет родителем голову
`origin/main`, и содержимое `tasks/` в ветке соответствует состоянию
`origin`, а не пина главной копии.

AC-7. Тест без `origin` (или с недоступной сетью): родитель —
локальный `main`, и запись в журнал задачи содержит причину.

AC-8. Существующие `tests/test_artifact_branch*.py`,
`tests/test_catalog*.py` проходят зелёными без правки ассертов.

## Не входит

- Обновление пина главной копии.
- Пересоздание уже заведённых артефактных веток (в т.ч. 01M1TNMBY8,
  01M1TNN4TM из инцидента).
- Уборка `tasks/` в существующих артефактных ветках.
- Новый код или обобщение `commit_files`/`write_commit` под параметр
  «origin целевого target» — ответ Оператора (ANSWER-1, вопрос 1,
  вариант A) снимает это как избыточное: артефактная ветка любого
  target физически коммитится в `config.ROOT`, правило требования 1
  уже покрывает все target одним кодом.
- Перенос первички внешних target'ов в `.artel/projects/<target>/` по
  ADR-0003 §3д — вне рамки и формулировки инцидента.
- Правка ADR-0003 или иных документов вне зоны задачи.
