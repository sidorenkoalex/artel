# SPEC: стоп-кран волны: класс отказа у нескольких задач подряд останавливает циклы всем

## Контекст

Классификация отказа попытки уже есть (`orchestrator/failure_classification.py`:
классы 1а/1б/«системный кандидат»/«обрыв потока»/session_limit,
`TRANSIENT_SYSTEM_CLASSES`), но бэкофф и эскалация решают судьбу только
ОДНОЙ задачи (T082) — три инцидента (31.08: ~40 мин Connection refused
жгли по три попытки на T075–T078; 04.09: обрыв сессии; 05.09: восемь
таймаутов шагов подряд) показали, что при системном отказе каждая
задача переживает его самостоятельно и возвращает её в работу
Оператор вручную по одной. Нужен межзадачный «стоп-кран»: если один
класс отказа бьёт по нескольким РАЗНЫМ задачам подряд за короткое
окно — это системная проблема, а не проблема одной задачи, и новые
агентные шаги по всем задачам того же target'а должны штатно
остановиться до решения Оператора, тем же приёмом, что уже несёт
`pause` (T070).

## Требования

1. Новые константы `orchestrator/config.py`: `WAVE_BREAKER_WINDOW_SEC`
   (по умолчанию 900 — 15 минут) и `WAVE_BREAKER_TASKS` (по умолчанию
   3); счётчик и порог читают их оттуда, не хардкодят.
2. Функция подсчёта по журналу шагов (`steps`) числа РАЗНЫХ задач
   target self с отказом ОДНОГО класса в пределах
   `WAVE_BREAKER_WINDOW_SEC`: классы — `TRANSIENT_SYSTEM_CLASSES` (1а,
   1б, системный кандидат) плюс отдельный класс «таймаут шага» (запись
   журнала `"agent run TIMEOUT"`, `orchestrator/runner.py`). Считаются
   задачи, не события — несколько отказов одной и той же задачи одного
   класса дают 1, не N.
3. При достижении `WAVE_BREAKER_TASKS` в пределах окна — алерт
   `kind=incident`, сообщение «стоп-кран волны: класс <класс> у N задач
   за M минут». Дедуп — на ОТКРЫТЫЙ алерт этого же класса (ключ дедупа
   — target+kind+source+класс, не буквальный текст сообщения: N/M в
   сообщении меняются от повторного срабатывания к срабатыванию, точное
   совпадение текста для такого алерта не годится, тем же классом
   проблемы, что уже решён для `report.token_rate_divergence`,
   `orchestrator/alerts.py`).
4. Инциденты сторожа зависших прогонов тестов
   (`doctor.check_hung_test_runs`, источник `doctor.hung_test_runs`) —
   иной класс, в счётчик стоп-крана не входят.
5. Пока по target self открыт алерт стоп-крана — `run`/`auto` любой
   задачи ЭТОГО target перед стартом НОВОГО агентного шага видят
   открытый алерт и отказывают начать шаг тем же приёмом, что штатная
   пауза (`orchestrator/pause.py`, `pause.is_paused`/`REFUSAL_ACTION`):
   уже идущий шаг не прерывается; `approve`/`reject`/`budget`/`status`
   не блокируются. Причина отказа — в stdout вызова и в журнале
   отказавшей задачи.
6. `alert-ack <id>` открытого алерта стоп-крана снимает блокировку
   немедленно (решение Оператора после `doctor live-smoke`, как для
   эскалаций). Повторное срабатывание того же класса ПОСЛЕ ack заводит
   НОВЫЙ алерт — не гасится прежним ack. Автоматического снятия нет.
7. `doctor` показывает открытый алерт стоп-крана первым пунктом вывода
   — раньше остальных проверок.
8. `status` несёт пометку у КАЖДОЙ задачи target self, пока алерт
   стоп-крана открыт (блокирует весь target, не только 3 задачи,
   вызвавшие срабатывание).
9. Стоп-кран действует только для target self (догфуд,
   `config.DEFAULT_TARGET`); задачи любого другого target не
   учитываются счётчиком и не блокируются им.

## Критерии приёмки

AC-1. `orchestrator/config.py` несёт `WAVE_BREAKER_WINDOW_SEC=900` и
`WAVE_BREAKER_TASKS=3`; функция подсчёта и порог срабатывания читают
именно эти константы (правка констант меняет поведение без правки
остального кода).

AC-2. Три РАЗНЫЕ задачи target self отказали классом 1б (сетевой отказ
до API) в пределах `WAVE_BREAKER_WINDOW_SEC` — заводится алерт
`kind=incident` с текстом, называющим класс, число задач и окно.

AC-3. Две РАЗНЫЕ задачи с тем же классом за то же окно — алерт НЕ
заводится.

AC-4. Отказы РАЗНЫХ классов (по одной задаче на 1а, на 1б, на
«таймаут шага») не суммируются в общий счётчик ни одного отдельного
класса.

AC-5. Несколько отказов ОДНОЙ И ТОЙ ЖЕ задачи одного класса в пределах
окна считаются как одна задача, не как несколько событий.

AC-6. Таймаут шага (журнальная запись «agent run TIMEOUT») учитывается
отдельным классом наравне с классами `TRANSIENT_SYSTEM_CLASSES`.

AC-7. Инцидент сторожа зависших прогонов тестов
(`doctor.check_hung_test_runs`) не увеличивает счётчик ни одного
класса стоп-крана.

AC-8. Пока алерт стоп-крана данного класса уже открыт, повторное
достижение порога тем же классом не заводит второй такой же алерт
(дедуп по target+kind+source+класс).

AC-9. Отказы задачи внешнего target (не self) не учитываются счётчиком
стоп-крана self.

AC-10. Пока по target self открыт алерт стоп-крана, `run`/`auto` любой
задачи этого target отказывают начать НОВЫЙ агентный шаг с названной
причиной (текст упоминает стоп-кран); шаг, уже идущий на момент
срабатывания, не прерывается; причина отказа появляется и в stdout
вызова, и в журнале отказавшей задачи.

AC-11. `approve`, `reject`, `budget`, `status` работают на задачах
target self как обычно независимо от открытого алерта стоп-крана.

AC-12. `alert-ack <id>` открытого алерта стоп-крана снимает блокировку
— следующий `run`/`auto` того же target стартует агентный шаг штатно;
новое срабатывание того же класса ПОСЛЕ ack заводит новый алерт, а не
повторно гасится прежним ack.

AC-13. `doctor` печатает открытый алерт стоп-крана первым пунктом
вывода, до остальных проверок.

AC-14. `status` несёт пометку у каждой задачи target self, пока алерт
стоп-крана открыт.

AC-15. Существующие тесты бэкоффа/эскалации класса «транзиентное
системное» (SPEC T082) и `pause`/`pause --now` (T070/T074) остаются
зелёными без единого ослабления.

AC-16. Задача внешнего target не блокируется открытым алертом
стоп-крана self и не помечается им в `status`.

## Оценка объёма и деление

Сработавшие сигналы: зона задачи — 5 файлов кода
(`orchestrator/alerts.py`, `orchestrator/auto.py`, `orchestrator/runner.py`,
`orchestrator/doctor.py`, `orchestrator/catalog.py`; `orchestrator/config.py`
и `tests/` — общие зоны, не в счёт), число критериев приёмки — 16
(≥ 10). Оба порога `SPLIT_SIGNAL_ZONE_FILES`/`SPLIT_SIGNAL_AC_COUNT`
превышены. ТЗ Оператора уже называет естественную границу деления
(«счётчик+алерт / пауза в run-auto») — использую её буквально.

Замечание по зоне: ТЗ перечисляет `orchestrator/alerts.py`,
`orchestrator/auto.py`, `orchestrator/runner.py`, `orchestrator/doctor.py`,
`orchestrator/config.py`, `tests/` — без `orchestrator/catalog.py`.
Требование 8 (пометка в `status`) физически реализуется в
`orchestrator/catalog.py::cmd_status` (карта кодовой базы — единственное
место, печатающее строки `status`), поэтому файл добавлен в `zones`
как адрес уже названного ТЗ требования, а не новое требование сверх
ТЗ.

**Часть 1 — счётчик и алерт стоп-крана.** Зона:
`orchestrator/alerts.py`, `orchestrator/runner.py` (2 файла + общие).
AC-1..AC-9 (9 критериев). Требования 1–4, 9 (в части подсчёта). Даёт
константы, функцию подсчёта РАЗНЫХ задач по классу за окно, алерт
`kind=incident` с верным ключом дедупа, вызываемый из двух точек
`runner.py`, где уже журналируется классифицированный отказ
(`failure_classification._record_failure_classification`) и таймаут
шага (`"agent run TIMEOUT"`). Самостоятельно мержима: результат —
новый видимый Оператору алерт-индикатор без единого изменения
поведения `run`/`auto` — система ведёт себя как раньше, просто
сигнализирует раньше человека. Часть первая в порядке — без неё
части 2 нечего проверять на старте шага.

**Часть 2 — пауза run/auto и видимость.** Зона: `orchestrator/runner.py`,
`orchestrator/auto.py`, `orchestrator/doctor.py`, `orchestrator/catalog.py`
(4 файла + общие). AC-10..AC-16 (7 критериев). Требования 5–9 (в части
блокировки/видимости). Опирается на алерт части 1 (читает его как
готовый факт, не заводит сама). Даёт собственно блокировку старта
нового шага, снятие по `alert-ack`, первую строку `doctor`, пометку
`status`. Самостоятельно мержима поверх части 1: без неё система лишь
видит проблему (часть 1), с ней — ещё и штатно останавливается.

Решение по нарезке (нарезка на 2 части либо обоснованный монолит) —
за Оператором на гейте SPEC.

## Не входит

- Автоматический перезапуск/резюме после снятия блокировки — только
  ручное действие Оператора (`alert-ack`), как и для эскалаций.
- Изменение бэкоффа/числа попыток ОДНОЙ задачи (T082) — механика
  ретраев не трогается.
- Прерывание уже идущих шагов — стоп-кран останавливает только СТАРТ
  нового шага.
- Внешние target: стоп-кран действует только для target self
  (`config.DEFAULT_TARGET`, догфуд). Распространение счётчика/паузы на
  внешние target — отдельная задача поверх многотаргетной архитектуры;
  в этой задаче параметризация по target не делается ни в каком виде.
