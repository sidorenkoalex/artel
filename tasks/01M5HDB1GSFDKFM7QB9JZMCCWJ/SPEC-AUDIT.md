# SPEC-AUDIT: suite-run отказывает новому полному прогону из шага developer

## ТЗ и SPEC

Каждому пункту ТЗ соответствует пункт SPEC:

Раздел «Не входит» совпадает с ТЗ, список «только чтение» перенесён туда же (SPEC.md:146–147). Файлов ANSWER-n в каталоге документов нет, раздела «Решения Оператора на гейте SPEC» в брифе нет.

Требований сверх ТЗ в SPEC нет.

Одна потеря в критериях (подробно — в разделе о проверяемости, отклонение О1). ТЗ п. 7 и SPEC тр. 8 (SPEC.md:83–84) требуют нового теста отказа developer «под той же подменой БД только на чтение». Ни один AC этого не требует:

## Зоны

Зоны `orchestrator/suite_run.py, orchestrator/role_prompt.py, tests/` покрывают всё, что меняют требования. `docs/codebase-map.md` регенерируется: он в `config.COMMON_ZONES` (`orchestrator/config.py:814`). Защищённые пути не меняются: `skills/coding-standards.md` в «Не входит», и текст в нём уже верен (:107–110). Песочница ролей не расширяется.

Ограничение «из `tests/` меняются только новый файл и `readonly_db`» записано только в «Не входит» (SPEC.md:146). AC его не проверяет — кроме части «прочие изменения файла readonly_db отсутствуют» в AC-8. Правку утверждений других файлов `tests/` отсекает гейт неослабления тестов. Отклонением это не считаю.

## Пути обхода гейтов

- Смена `ROLES` (модульная константа) не убирает ни одного утверждения: `scripts/guard.py:1999` `weakened_helpers` и `changed_classes` (:2010) по ней не сработают. Гейт неослабления тестов эту миграцию, по-видимому, механически не увидит. Рамку держат только AC-8, мандат ANSWER и ревью. Отклонением SPEC это не считаю — наблюдение для Оператора.
- О1 позволяет буквальное исполнение: тест отказа developer пишется только на обычной БД. Тогда реализация, которая под БД только на чтение (как у роли на Codex) падает или идёт другим путём — например, разрешает id через `_db()` и ловит исключение `store.db`, — не поймана ни одним AC. Именно этот сценарий стенд `readonly_db` и держал для developer.
- Сравнение маркера: AC-6 перечисляет пустой маркер и HOME без маркера. Реализация через `runner.in_role_environment` будет поймана.

## Вердикт

**concerns.** SPEC верен по фактам и по содержанию соответствует ТЗ. Найденные отклонения Оператор может закрыть на гейте:

- **О1 (существенное).** Тест отказа developer «под той же подменой БД только на чтение» (SPEC.md:83–84, ТЗ п. 7, условие ADR-0024 п. 4 «не без новых проверок раннего отказа») не перенесён ни в один AC. AC-1 (SPEC.md:103) подмену не называет, AC-9 (SPEC.md:119) покрывает только AC-1–AC-7, а ADR-0024 п. 5 требует переносить свойства матрицы в AC. Исправление: в AC-1 добавить «в том числе под подменой `store.db` на соединение только на чтение (как `readonly_db`)».
- **О2 (уточнение).** В AC-3 (SPEC.md:107) «без новых записей» перечисляет лог, `run.json`, замок и фон. Будет ли в этом случае у developer вызван `deliver_journal` (сейчас он идёт раньше `_running`, `suite_run.py:779` против :802), не сказано. ТЗ п. 3 говорит общее «без новых записей». Обе реализации допустимы — нужно одно слово Оператора, либо оставить как есть.
- **О3 (мелкое).** Фраза AC-1 «задача, заданная префиксом id, разрешается в полный id чтением БД `mode=ro`» не называет наблюдаемый признак — например, полный id в тексте отказа или URI `mode=ro` у подменённого `sqlite3.connect`. Без него мутация «префикс не разрешён» может пройти.
- **О4 (мелкое).** Позитивная часть AC-5 (SPEC.md:111) «называет запуск упавших тестов CI или гейта по именам» не задаёт проверяемой формы. Ловится только негативная часть (нет `suite-run <id>` без флагов).
- **Наблюдение.** Миграцию `ROLES` механический гейт неослабления не видит (`scripts/guard.py:1999`). Рамка мандата держится на AC-8 и ревью.
