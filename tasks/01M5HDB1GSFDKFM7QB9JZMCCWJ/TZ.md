# suite-run отказывает новому полному прогону из шага developer

## Факты

Строка копилки `docs/backlog.md` «Анализ долгой канарейки 20261012T192225Z» (13.10): developer-4 и developer-5 канарейки запустили полный suite-run, суммарно около 49 минут ожидания; строка бэклога «Полный suite-run из шага developer: машинное соблюдение контракта» закрыта 22.10 как её дубль, формулировка оттуда: «Отказ только нового full developer до журнала/БД/lock/PID; сохранить --failed, статус и ожидание существующего запуска, другие роли и полные гейты». Повтор 22.10: developer задачи 01M5H24PZXZTBM03SF6V576S5P (шаг developer-1) вызвал `artel.py suite-run 01M5H24PZXZTBM03SF6V576S5P` без флагов (прогон №1, режим `full`, начат 09:46, оборван по пределу 1500 с), приёмка задачи 01M5GXZK2WTZ89AXQ7QY2RJD9R около 25 минут ждала общий замок полного прогона.

**Граница задачи одной фразой:** под маркером `ARTEL_ROLE=developer` команда `suite-run <id>` без `--failed` и без `--wait`, когда прогона этой задачи ещё нет, отказывает раньше любых записей; всё остальное поведение команды и все прочие вызывающие — прежние.

- Запрет записан только текстом, `skills/coding-standards.md:107` — «В шаге разработчика полный набор `tests/` не запускай: его выполняют CI и гейт приёмки». Миссия developer говорит обратное: `orchestrator/role_prompt.py:413` — `suite_run_note` (вызывается только в ветке developer сборки миссии) начинается словами «Полный набор тестов — только командой пульта … suite-run <id>» (`orchestrator/role_prompt.py:420`) и прямо предлагает полный прогон.
- Порядок команды `orchestrator/suite_run.py:771` — `cmd_suite_run`: разбор аргументов; `orchestrator/suite_run.py:774` — `_db` (сначала соединение пульта на запись, при отказе — только чтение `mode=ro`); `orchestrator/suite_run.py:779` — `deliver_journal` (досыл отложенного журнала, пишет в БД); `orchestrator/suite_run.py:780` — ветка `--wait`; `orchestrator/suite_run.py:792` — проверка `failed` (флаг `--failed`); `orchestrator/suite_run.py:802` — `_running` (ответ «прогон этой задачи уже идёт — второй не запускаю»); `orchestrator/suite_run.py:812` — `_acquire_lock` (замок); `orchestrator/suite_run.py:819` — `_new_log` (лог); `orchestrator/suite_run.py:829` — `Popen` (фоновый процесс); `orchestrator/suite_run.py:838` — `_write_json` (запись `run.json`). Признак роли из окружения фонового процесса снимается (строка 826), поэтому сторож `conftest.py` прогон не останавливает. Роль команда не проверяет нигде. Режима «прогон перечисленных файлов» у `suite-run` нет: разбор аргументов принимает ровно один позиционный аргумент — номер задачи.
- `--failed` повторяет перечень упавших прошлого прогона `suite-run` этой задачи: `_read_failed` (`orchestrator/suite_run.py:224`) читает `failed.json` каталога задачи; гейты пульта этот перечень не пишут. Без прошлого прогона отказ `--failed` советует «сначала полный прогон: … suite-run <id>».
- Маркер роли: сборка окружения шага `role_env` в `orchestrator/runner.py` ставит `ARTEL_ROLE` = имя роли шага для обоих провайдеров; тем же маркером пользуются сторож полного набора в `conftest.py` и отказ команд роли `orchestrator/artel.py:2120` — `_refuse_if_role_restricted`; `suite-run` входит в белый список `orchestrator/artel.py:2073` — `_ROLE_ALLOWED_COMMANDS`. Распознавание шага роли `in_role_environment` в `orchestrator/runner.py` считает ролью и процесс без маркера, но с HOME дома роли — имени роли оно не знает. Оба механизма по их же описанию «отсекают ошибочный вызов, но не граница» (`docs/stack.md`, «Паритет безопасности роли»).
- Убитая задача 01M4XVM49PP5WHSXT5S8JW85WN (та же тема, 14–16.10, $40,90 из $45): ADR-0024 (`docs/adr/0024-developer-full-suite-contract.md`, «принят, не исполнен») п. 3 потребовал подтверждать роль «по process/lease», а маркер `ARTEL_ROLE` удостоверением не считать; это развернулось в доверенный канал ADR-0025 (сокет-брокер вне песочницы, kernel peer PID, исключение в политике сети Codex, правка провайдеров и проверки изоляции doctor), эскалации AC-17 о живом стенде Codex/Claude × macOS/Linux и подготовку виртуальной машины; 16.10 Оператор отложил ADR-0025 (механизм песочницы — Docker, ADR-0023, «Поправка 16.10.2026») и ликвидировал задачу. ## Требуется

1. **Отказ.** `suite-run <id>` без `--failed` и без `--wait` в процессе, где `ARTEL_ROLE` равен `developer`, завершается ненулевым кодом с отказом, если прогона этой задачи сейчас нет. Решение принимается до открытия БД на запись и любой иной записи в БД, до досыла журнала `deliver_journal`, до создания каталога задачи в хозяйстве `suite-run`, лога, `run.json`, замка и фонового процесса; задача разрешается в полный id только чтением БД (`mode=ro`; поправка ADR-0024 п. 2). Проверка: файл БД (байты), каталог отложенного журнала, каталог `suite-run` и файл замка до и после вызова совпадают; подмены запуска фонового процесса (`Popen`), открытия БД на запись (store.db) и `suite_lock.deliver_journal` не вызваны ни разу.
2. **Текст отказа** называет команду и роль и содержит подсказку: полный набор прогонит CI и автопроверка приёмки; свои файлы — `python3 -m pytest tests/<файлы> …` в переднем плане (форма из `skills/coding-standards.md:107`), планка — `plank-run <id> [файл]`, повтор упавших — `suite-run <id> --failed`. Команда `suite-run <id> <файлы>` в тексте не называется: такого режима нет.
3. **Прогон этой задачи уже идёт** (условие `_running`): developer без флагов получает прежний ответ «уже идёт … второй не запускаю» с номером, pid и логом и код 0, без новых записей.
4. **Сохраняется для developer:** `--wait <минуты>` (в том числе `--wait 0` — чтение состояния и отчёта) и `--failed` — как сейчас, с досылом журнала и прежними отказами. Отказ `--failed` «прошлого прогона нет» при маркере `developer` не советует полный прогон, а называет запуск упавших тестов CI или гейта по именам; у остальных вызывающих текст прежний. Под маркером `developer` ни одна из четырёх подсказок полного прогона — `--wait` «прогона нет», `--wait` «оборван», `--failed` «упавших нет», сам отказ developer (п. 1) — не называет `suite-run <id>` без флагов; у прочих вызывающих тексты прежние.
5. **Сохраняется для всех прочих:** процесс без `ARTEL_ROLE` (Оператор), маркер любой другой роли, процесс с HOME роли без маркера, пустой `ARTEL_ROLE` — полный `suite-run` запускается как сейчас (замок, лог, фон, снятие маркера в фоне, досыл журнала). Гейты, CI, канарейка, прогон полного набора пульта `run_full_suite`, замок `suite_lock`, пределы и таймауты не меняются.
6. **Миссия developer** (`suite_run_note`) больше не предлагает полный прогон: говорит, что полный набор гоняют CI и гейт приёмки, и называет `python3 <пульт>/orchestrator/artel.py suite-run <id> --failed` и `… --wait <минуты>`; в миссии сказано, что `--failed` работает только после прогона Оператора или ревьювера (перечень упавших пишет только `suite-run`); `MissionTest::test_ac25_developer_mission_names_suite_run_with_pult_path` остаётся зелёным без правки. Миссия ревьювера внешнего проекта (`suite-run` в перечне команд) не меняется.
7. **Миграция `readonly_db`** — строго в рамке мандата Оператора (решение 2); исполнение — только ANSWER на spec_gate: развилка «developer под БД только на чтение запускает полный прогон» заменяется новым тестом отказа developer под той же подменой БД только на чтение; матрица неослабления в PLAN — строка на каждый из пяти методов: свойство, чем держится после.
8. **Новые тесты** — отдельный файл `tests/`: отказ (п. 1–2) с проверкой отсутствия побочных эффектов; уже идущий прогон (п. 3); `--wait 0` и `--failed` developer под подменой БД только на чтение (п. 4), причём `--failed` берёт общий замок, а при замке гейта отказ называет задачу гейта; настоящий `sleep` и ожидание фоновых процессов в тестах не используются; Оператор, другая роль (случайная из ролей конвейера, кроме developer), HOME роли без маркера, пустой маркер (п. 5); миссия (п. 6). Тяжёлый запуск подменяется (запуск фонового процесса или прогон полного набора пульта, как в существующих стендах suite-run); настоящий полный `tests/` в тестах и в шагах задачи не запускается; зёрна случайного выбора печатаются. Каждый тест несёт «Ловит мутацию: …»: отказ после `deliver_journal` или после замка; отказ любой роли; отказ `--failed`/`--wait`; отказ при уже идущем прогоне; маркер не проверен.
