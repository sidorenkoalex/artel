# SPEC: suite-run отказывает новому полному прогону из шага developer

## Контекст

Запрет полного `tests/` в шаге разработчика записан только текстом
(`skills/coding-standards.md:107`), а миссия developer
(`orchestrator/role_prompt.py:413`, `suite_run_note`) прямо предлагает полный
прогон `suite-run <id>`. Канарейка 12.10 (developer-4, developer-5, ~49 минут
ожидания) и задача 01M5H24PZXZTBM03SF6V576S5P 22.10 (полный прогон из
developer-1, оборван по пределу 1500 с; приёмка 01M5GXZK2WTZ89AXQ7QY2RJD9R
~25 минут ждала общий замок) показали цену. `cmd_suite_run`
(`orchestrator/suite_run.py:771`) роль не проверяет нигде. Действующее
основание — ADR-0024 с поправкой 22.10.2026 (коммит 3aacbd39): признак
developer — непустой маркер `ARTEL_ROLE`, равный `developer`; уровень защиты —
отсечение ошибочного вызова, не граница против намеренного обхода; id задачи
разрешается чтением БД `mode=ro`.

Граница задачи одной фразой: под маркером `ARTEL_ROLE=developer` команда
`suite-run <id>` без `--failed` и без `--wait`, когда прогона этой задачи ещё
нет, отказывает раньше любых записей; всё остальное поведение команды и все
прочие вызывающие — прежние.

## Требования

1. **Отказ.** `suite-run <id>` без `--failed` и без `--wait` в процессе, где
   `ARTEL_ROLE` равен `developer`, завершается ненулевым кодом с отказом, если
   прогона этой задачи сейчас нет. Решение принимается до открытия БД на
   запись и любой иной записи в БД, до досыла журнала
   `suite_lock.deliver_journal`, до создания каталога задачи в хозяйстве
   `suite-run`, лога, `run.json`, замка и фонового процесса; задача
   разрешается в полный id только чтением БД (`mode=ro`; поправка ADR-0024
   п. 2).
2. **Текст отказа** называет команду и роль и содержит подсказку: полный
   набор прогонит CI и автопроверка приёмки; свои файлы —
   `python3 -m pytest tests/<файлы> …` в переднем плане (форма
   `skills/coding-standards.md:107`), планка — `plank-run <id> [файл]`,
   повтор упавших — `suite-run <id> --failed`. Команда
   `suite-run <id> <файлы>` в тексте не называется: такого режима нет.
3. **Прогон этой задачи уже идёт** (условие `_running`): developer без флагов
   получает прежний ответ «уже идёт … второй не запускаю» с номером, pid и
   логом и код 0, без новых записей.
4. **Сохраняется для developer:** `--wait <минуты>` (в том числе `--wait 0` —
   чтение состояния и отчёта) и `--failed` — как сейчас, с досылом журнала и
   прежними отказами.
5. **Подсказки под маркером developer.** Отказ `--failed` «прошлого прогона
   нет» при маркере `developer` не советует полный прогон, а называет запуск
   упавших тестов CI или гейта по именам. Под маркером `developer` ни одна из
   четырёх подсказок полного прогона — `--wait` «прогона нет», `--wait`
   «оборван», `--failed` «упавших нет», сам отказ developer (требование 1) —
   не называет `suite-run <id>` без флагов. У прочих вызывающих все эти
   тексты прежние.
6. **Сохраняется для всех прочих:** процесс без `ARTEL_ROLE` (Оператор),
   маркер любой другой роли, процесс с HOME роли без маркера, пустой
   `ARTEL_ROLE` — полный `suite-run` запускается как сейчас (замок, лог, фон,
   снятие маркера в окружении фона, досыл журнала).
7. **Миссия developer** (`suite_run_note`) больше не предлагает полный
   прогон: говорит, что полный набор гоняют CI и гейт приёмки, и называет
   `python3 <пульт>/orchestrator/artel.py suite-run <id> --failed` и
   `… --wait <минуты>`; в миссии сказано, что `--failed` работает только
   после прогона Оператора или ревьювера (перечень упавших пишет только
   `suite-run`). `MissionTest::test_ac25_developer_mission_names_suite_run_with_pult_path`
   (`tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py:1413`) остаётся
   зелёным без правки. Миссия ревьювера внешнего проекта (`suite-run` в
   перечне команд) не меняется.
8. **Миграция `readonly_db`** — строго в рамке мандата Оператора (решение 2
   ТЗ; исполнение — только строкой ANSWER на spec_gate): в
   `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_suite_run_readonly_db.py` из выбора
   роли стенда (`ROLES`, строка 60) исключается `developer`; пять адресных
   носителей ADR-0024 п. 4 (`ReadonlyDbOutcomeTest::test_ac4_…`,
   `JournalRedeliveryTest::test_ac5_…`, `SharedLockTest::test_ac6_…`,
   `LimitUnchangedTest::test_ac8_…`, `LogPlacementTest::test_ac9_…`) по
   именам и утверждениям не меняются. Развилка «developer под БД только на
   чтение запускает полный прогон» заменяется новым тестом отказа developer
   под той же подменой БД только на чтение. В PLAN — матрица неослабления:
   строка на каждый из пяти методов — свойство и чем оно держится после.
9. **Новые тесты** — отдельный файл `tests/` (долгоживущий приёмочный тест
   задачи `tests/test_<id>_*.py` этим файлом и считается, ADR-0020; второй
   файл с теми же свойствами не требуется). Покрывает: отказ (требования 1–2)
   с проверкой отсутствия побочных эффектов; уже идущий прогон (требование 3);
   `--wait 0` и `--failed` developer под подменой БД только на чтение
   (требование 4), причём `--failed` берёт общий замок, а при замке гейта
   отказ называет задачу гейта; подсказки (требование 5); Оператор, другая
   роль (случайная из ролей конвейера, кроме developer), HOME роли без
   маркера, пустой маркер (требование 6); миссия (требование 7). Тяжёлый
   запуск подменяется (запуск фонового процесса или прогон полного набора
   пульта, как в существующих стендах suite-run); настоящий `sleep` и
   ожидание фоновых процессов не используются; настоящий полный `tests/` в
   тестах и в шагах задачи не запускается; зёрна случайного выбора
   печатаются; каждый тест несёт строку «Ловит мутацию: …».

## Критерии приёмки

AC-1. Под `ARTEL_ROLE=developer` вызов `suite-run <id>` без `--failed` и без `--wait` при отсутствии идущего прогона этой задачи завершается ненулевым кодом с отказом; байты файла БД, каталог отложенного журнала, каталог `suite-run` и файл замка до и после вызова совпадают; подмены запуска фонового процесса (`Popen`), открытия БД на запись (store.db) и `suite_lock.deliver_journal` не вызваны ни разу; задача, заданная префиксом id, разрешается в полный id чтением БД `mode=ro`.

AC-2. Текст отказа AC-1 называет команду `suite-run` и роль developer и содержит: что полный набор прогонит CI и автопроверка приёмки; `python3 -m pytest tests/<файлы>` в переднем плане; `plank-run <id> [файл]`; `suite-run <id> --failed`; текст не содержит формы `suite-run <id> <файлы>`.

AC-3. Под `ARTEL_ROLE=developer`, когда прогон этой задачи уже идёт (условие `_running`), вызов `suite-run <id>` без флагов печатает прежний ответ «уже идёт … второй не запускаю» с номером прогона, pid и логом, завершается кодом 0 и не создаёт новых записей (лог, `run.json`, замок, фоновый процесс).

AC-4. Под `ARTEL_ROLE=developer` и подменой БД только на чтение `suite-run <id> --wait 0` читает состояние и отчёт как сейчас, а `suite-run <id> --failed` при наличии перечня упавших прошлого прогона берёт общий замок полного прогона и запускает повтор упавших; при замке, который держит гейт другой задачи, отказ `--failed` называет задачу гейта. Досыл журнала и прежние отказы `--wait`/`--failed` у developer сохраняются.

AC-5. Под `ARTEL_ROLE=developer` отказ `--failed` «прошлого прогона нет» называет запуск упавших тестов CI или гейта по именам и не советует полный прогон; ни одна из подсказок — `--wait` «прогона нет», `--wait` «оборван», `--failed` «упавших нет», отказ AC-1 — не содержит `suite-run <id>` без флагов. Для процесса без маркера эти же тексты совпадают с прежними.

AC-6. Процесс без `ARTEL_ROLE`, процесс с маркером другой роли конвейера (случайной, кроме developer), процесс с HOME роли без маркера и процесс с пустым `ARTEL_ROLE` по `suite-run <id>` без флагов запускают полный прогон как сейчас: берут замок, создают лог и `run.json`, запускают фоновый процесс без `ARTEL_ROLE` в его окружении, досылают журнал.

AC-7. Миссия developer (`suite_run_note`) не предлагает полный прогон `suite-run <id>` без флагов, говорит, что полный набор гоняют CI и гейт приёмки, называет `python3 <пульт>/orchestrator/artel.py suite-run <id> --failed` и `python3 <пульт>/orchestrator/artel.py suite-run <id> --wait <минуты…>` и говорит, что `--failed` работает только после прогона Оператора или ревьювера; `MissionTest::test_ac25_developer_mission_names_suite_run_with_pult_path` зелёный без правки; миссия ревьювера внешнего проекта не меняется.

AC-8. В `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_suite_run_readonly_db.py` выбор роли стенда (`ROLES`) не содержит `developer`; пять методов `test_ac4_readonly_db_run_reaches_same_outcome_and_report`, `test_ac5_pult_process_delivers_journal_record`, `test_ac6_role_suite_run_and_gate_share_one_lock_file`, `test_ac8_readonly_db_run_keeps_profile_limit_and_timeout_outcome`, `test_ac9_suite_run_logs_live_under_suite_run_dir` сохраняют имена, классы, виды и число утверждений; прочие изменения этого файла отсутствуют; PLAN несёт матрицу неослабления — строку на каждый из пяти методов со свойством и тем, чем оно держится после.

AC-9. Новые тесты задачи лежат отдельным файлом `tests/`, покрывают AC-1–AC-7, не вызывают настоящий `time.sleep` и не ждут фоновых процессов, не запускают настоящий полный `tests/`, печатают зёрна случайного выбора, и каждый тестовый метод несёт строку «Ловит мутацию: …» (среди мутаций: отказ после `deliver_journal` или после замка; отказ любой роли; отказ `--failed`/`--wait`; отказ при уже идущем прогоне; маркер не проверен).

## Оценка объёма и деление

Сработавший сигнал: `budget_usd` ≥ $30 (потолок задачи по ТЗ — $30;
калибровка для 9 критериев и 3–4 файлов зоны даёт ~40, ставка снижена до
потолка Оператора). Зона — 2 модуля и 2 файла `tests/`, критериев 9.

**Обоснование монолита.** Отказ developer в `cmd_suite_run` и миграция
`ROLES` в `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_suite_run_readonly_db.py`
неразделимы: отказ без миграции делает пять методов `readonly_db` красными
примерно в трети прогонов (случайная роль стенда), миграция без отказа
снимает покрытие developer, ничем его не заменив (ADR-0024 п. 4 запрещает
простое исключение developer без новых проверок раннего отказа). Правка миссии
(`role_prompt.py`) мала и описывает то же новое поведение; отдельная часть с
ней мержилась бы в промежуточном состоянии «миссия запрещает, команда
разрешает» или наоборот. Решение — за Оператором на гейте SPEC.

## Не входит

- Раздел SPEC «Заменяемые тесты»: мандат на ослабление пяти методов даётся только строкой ANSWER на spec_gate (решение Оператора 2 ТЗ).
- Удостоверение роли по процессу или lease, сокет-брокер, правка политики песочницы и провайдеров (ADR-0025, отложен).
- Запрет самостоятельного `python3 -m pytest` в обход сторожа `conftest.py`.
- Новый режим `suite-run <id> <файлы>`.
- Наполнение перечня упавших `--failed` из гейтов или CI.
- Правка `skills/coding-standards.md` (текст уже верен).
- Отказ полного прогона другим ролям.
- Изменение гейтов, CI, канарейки, `acceptance.run_full_suite`, замка `suite_lock`, пределов и таймаутов.
- Правка `orchestrator/artel.py` (меняет идущая задача 01M5H24PZXZTBM03SF6V576S5P), `orchestrator/runner.py`, `orchestrator/suite_lock.py`, `orchestrator/acceptance.py`, провайдеров, `orchestrator/doctor/isolation.py`, `conftest.py`, ADR-0024/0025, `docs/backlog.md`, `docs/stack.md` и прочих файлов `tests/`, кроме нового файла задачи и файла `readonly_db` в рамке мандата.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность защищённых путей, непревышение бюджета — их держит пульт.
