# PLAN: amend-tests для долгоживущих файлов в tests/ и исключение их из диффа ревью и меры гейта ёмкости

## Подход

Три узла, все в зонах SPEC; `orchestrator/advance_gates/`, `scripts/guard.py`,
`orchestrator/acceptance.py`, `orchestrator/artifact_branch.py` только
вызываются.

**Перечень лока — один источник.** И `amend`, и `review` читают перечень
лока существующим `advance_gates.acceptance.long_lived_manifest(task_id, t,
target)` (дерево коммита `tests_locked_sha`). Пустой словарь (нет лока, нет
файла, пустой перечень, внешний target) — «задача без долгоживущих файлов»,
всё идёт прежним путём (требование 7).

**`amend-tests` из worktree (`amend._cmd_amend_tests`).** Область правки
долгоживущих путей включается только при непустом перечне лока:
- изменения `git status` делятся на три группы — каталог планки,
  долгоживущие пути задачи (`guard.is_long_lived_test_path`), прочее; прочее
  — прежний отказ «за пределами», с путём; перечень лока не прочитан при
  наличии правки долгоживущего пути — отказ;
- файл перечня в worktree отличается от ветки документов — отказ с именем
  `long_lived.sha256.txt` (проверка действует всегда: перечень пишет только
  пульт);
- итоговое состояние — долгоживущие файлы с диска worktree
  (`ls-files --cached --others --exclude-standard -- tests`, только
  существующие); проверки до записи в порядке: трассируемость AC (планка +
  тексты долгоживущих, `guard.acceptance_traceability_errors(tdir, extra)`),
  строка группы планки (прежняя), для `tests/` — строка «Группа:
  долгоживущий», признаки и «Ловит мутацию»
  (`guard.long_lived_errors_from_files`), правило удаления (ниже), сухой сбор
  (`acceptance.collect(..., extra=…)`) и прогон (`acceptance.run(tdir,
  cwd=worktree, extra=…)`) — красный прогон допускается, только если каждый
  файл прогона (планка и долгоживущие) несёт маркер «Красен до реализации»/
  «Зелёный с рождения» (прежнее правило, распространённое на новую группу);
- запись строго (а) → (б) → (в): коммит в worktree кодовой ветки ровно
  изменённых долгоживущих путей (`add -A -- пути`, `commit -- пути`,
  идентичность пульта как у чекпоинта); коммит в ветку документов снимка
  планки с перечнем, пересчитанным `blob_sha256` по новой голове кодовой
  ветки; сдвиг `tests_locked_sha`. Сбой (б) после (а) — ненулевой код,
  сообщение с `amend-tests <id> --from-branch --reason …`, без
  `AMEND_ACTION`.

**Правило удаления (требование 4).** Для пути перечня лока, которого нет в
итоговом состоянии: текст файла — с головы кодовой ветки, а если его там уже
нет — с родителя коммита, удалившего его (`git log --diff-filter=D`).
Имена методов сравниваются без класса (`guard.qualified_test_methods`,
последний сегмент): перенос метода в `acceptance_tests/` меняет класс.
Потерянные методы — отказ с файлом, методами и ссылкой на ADR-0020 п.8.

**`--from-branch` (требование 2).** Помимо прежнего расхождения
`acceptance_tests/` лока и головы ветки документов — расхождение перечня лока
с суммами долгоживущих файлов головы кодовой ветки. Проверки те же, что в
worktree-режиме, по содержимому головы кодовой ветки; сухой сбор и прогон —
только при расхождении долгоживущих (планка материализуется из ветки
документов в worktree, долгоживущие пути worktree обязаны совпадать с
головой — иначе отказ). При непустом перечне лока перечень головы ветки
документов, не совпадающий с пересчитанным, заменяется коммитом
пересчитанного — в лок попадает только он.

**Счётчик ADR-0012.** `AMEND_ACTION` журналируется один раз в конце
успешного вызова, после (в); отказы и сбой между записями журналируют
«amend-tests отклонён»/«amend-tests прерван» — не `AMEND_ACTION`.

**`review.snapshot_exclude`.** К прежнему кортежу добавляется
`:(exclude,literal)<путь>` на каждый путь перечня лока. Строка задачи
читается прямо из БД, только если файл БД есть (`get_task` роняет процесс
на отсутствующей задаче, а существующий тест зовёт узел без песочницы БД);
любой сбой — прежний кортеж. Фильтр исключений `_shown_diff` распознаёт и
длинную форму магии (ловушка SPEC). Пакет ревью: компонент на каждый путь
перечня (текст `git show <кодовая ветка>:<путь>`, `artifact_part` с
`run_id`) после ANSWER-n.md и до стат-списка; заметка об исключении — только
при непустом перечне. Задача без перечня — текст пакета байт в байт прежний.

## Шаги

1. `orchestrator/review.py`: `_locked_long_lived_paths`, расширение
   `snapshot_exclude`, фильтр `_shown_diff`, компонент и заметка пакета.
2. `orchestrator/amend.py`: worktree-режим (группы изменений, проверки,
   три записи, сообщение восстановления), `--from-branch` с расхождением
   долгоживущих путей, правило удаления.
3. `docs/stack.md`: абзац о судьбе приёмочных тестов (требование 8).
4. `tests/test_amend_long_lived.py`: сторожа свойств, не покрытых
   планкой (литеральная форма исключения, отказ при непрочитанном перечне в
   worktree-режиме, `--from-branch` без расхождения при непустом перечне,
   перенос с другим классом). Карта кодовой базы — регенерация тем же
   коммитом.
5. Прогон планки задачи и затронутых модулей `tests/` по одному.

## Влияние на систему

- Сверка сумм, лок каталога, гейт ёмкости — не меняются (только вызываются).
  Мера гейта ёмкости уменьшается ровно на байты зафиксированных перечнем
  файлов, которые ревьювер получает отдельным компонентом; файл с префиксом
  задачи вне перечня остаётся в мере и в диффе.
- Окно и порог ADR-0012 не меняются; `AMEND_ACTION` по-прежнему одно событие
  на успешный вызов.
- Сбой чтения перечня: в пакете/гейте — долгоживущие файлы остаются в
  диффе (не пропадают из поля зрения); в `amend-tests` — отказ (fail-closed).
- Откат — revert коммита ветки задачи; данных БД задача не меняет.

## Риски

- Прогон/сухой сбор в `amend-tests` идёт из worktree: при непустом перечне
  прогон планки меняет `cwd` с `config.ROOT` на worktree — это тот же
  `cwd`, что у прогона на `in_dev -> verifying`; задач без перечня это не
  касается.
- Сторонние незакоммиченные правки долгоживущих путей в worktree в режиме
  `--from-branch` дают отказ, а не молча прогоняются вместо головы ветки.
