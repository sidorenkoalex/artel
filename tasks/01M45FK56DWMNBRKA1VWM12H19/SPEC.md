# SPEC: Этап 3 ADR-0021, часть 2 из 3: защищённые пути проекта, зоны, приложения к PLAN и карта на repo_context

## Контекст
ADR-0021 (пункты 8, 12, 13) переводит проверки пункта 8 на `repo_context`
и удаляет развилки по `config.DEFAULT_TARGET`. Это вторая часть этапа 3.
Сегодня гейт зон (`orchestrator/advance_gates/zones.py`, ~189) и гейт
применимости приложений PLAN (`orchestrator/advance_gates/plan_appendix.py`,
~150) у внешнего проекта не исполняются. На гейте мержа сверка защищённых
путей в диффе, применение приложений PLAN и карта кодовой базы включаются
признаком `repo_context.is_artel` (`orchestrator/fsm_merge_gate.py` ~89,
~904, ~980). Все места сверки защищённых путей берут перечень пульта
`config.PROTECTED_PATHS` для любого проекта. Поле `no_paths` записи
`targets.yaml` проверяется только на форму, код его не читает. У записи
`artel` в этом поле 9 путей, а в `config.PROTECTED_PATHS` — 18. Номера
строк даны по пину 6eb98eff и сдвинутся после мержа части 1
(01M45FJVGQT1K0P8HDEXZX6HS7).

## Требования

1. **Перечень защищённых путей проекта** — одна функция, общая для всех
   мест сверки. Где она живёт, решает разработчик.
   - Для внешнего проекта функция возвращает записи поля `no_paths` его
     записи `targets.yaml`.
   - Для артели функция возвращает `config.PROTECTED_PATHS`, прочитанный в
     момент вызова. Содержимое поля `no_paths` записи `artel` на результат
     не влияет.
   - **Обоснование выбора источника для артели.** ADR-0021 п.8 называет
     этот перечень. `docs/invariants.md` называет `config.PROTECTED_PATHS`
     единым источником защищённых путей (шапка и строка «Защищённые
     пути»), так что выбор `no_paths` потребовал бы менять формулировку
     инварианта, а таблица ADR-0021 п.12 таких правок не предусматривает.
     Задание CI читает перечень из текста конфигурации пульта
     (`scripts/ci_protected_paths.py`, только чтение по ТЗ). Контекст
     артели разрешается без чтения `targets.yaml`
     (`repo_context.resolve`), поэтому защита путей пульта не зависит от
     того, читается ли `targets.yaml`. При этом выборе формулировка
     документа инвариантов не меняется, и эскалация по ТЗ п.1 не
     нужна. Поле `no_paths` записи `artel` становится зеркалом
     `config.PROTECTED_PATHS`, его совпадение держит сторож (требование 4).
   - Формула сверки во всех местах одна:
     `config.is_protected_path(path, <перечень проекта задачи>)`.

2. **Места сверки из «Фактов» ТЗ берут перечень проекта задачи:**
   - гейт зон (`orchestrator/advance_gates/zones.py` ~37-41);
   - гейт мержа: защищённые пути в диффе (`orchestrator/fsm_merge_gate.py`
     ~50-51, ~89);
   - подсветка черновика MR (`orchestrator/github_adapter.py` ~74-89);
   - допуск путей приложений PLAN (`scripts/guard.py` ~316-318 и
     `guard.plan_appendices` в вызовах пульта);
   - зоны ТЗ и SPEC (`scripts/guard.py::protected_zones` ~2975-2982 в
     вызове из `orchestrator/catalog.py::_tz_path_check` ~213 и из гейта
     SPEC).

   Функции `scripts/guard.py` принимают перечень явно. Без явного перечня
   (в том числе при самостоятельном запуске
   `python3 scripts/guard.py <файл>`) действует перечень артели
   `config.PROTECTED_PATHS`. Вызовы пульта передают перечень проекта
   задачи.

3. **Проверки пункта 8 этой части исполняются для любого проекта с
   разрешённым контекстом** — в клоне и рабочей копии задачи из
   `repo_context`. Развилки из «Фактов» удаляются:
   - `zones.py` ~189;
   - `plan_appendix.py` ~150;
   - `is_artel` на гейте мержа: ~89 (защищённые пути в диффе), ~904
     (приложения PLAN), ~980 — только для шага карты.

   Поведение для артели не ослабляется ни в одном месте. «Профиль» ниже —
   профиль тестов проекта из части 1. Таблица проверок:

   | Проверка | Источник репозитория | Из записи проекта / профиля | Неразрешённый контекст | Проект без профиля |
   |---|---|---|---|---|
   | Гейт зон (`in_dev -> review`) | рабочая копия задачи (`workspace.task_repo`), база — `gitcmd.diff_base` | перечень защищённых путей проекта (требование 1); общие зоны вне конфликта проекта (требование 5); профиль не нужен | отказ перехода с причиной, называющей проект и «контекст не разрешён» (fail-closed, ADR-0002) | исполняется полностью — от профиля не зависит |

   | Приложения PLAN: допуск путей и применимость на выходе `in_dev` | рабочая копия задачи | перечень защищённых путей проекта | отказ перехода с причиной, называющей проект | исполняется полностью |

   Для артели контекст разрешается всегда (`repo_context.resolve` не
   читает `targets.yaml`), поэтому столбец «неразрешённый контекст» её не
   касается.

4. **`targets.yaml` приводится к действительности приложением к PLAN**
   (защищённый путь).
   - Поле `no_paths` записи `artel` — ровно 18 записей
     `config.PROTECTED_PATHS`.
   - Комментарий записи больше не называет поле декларацией. Он говорит,
     что для внешнего проекта поле — перечень защищённых путей проекта,
     а у `artel` — зеркало `config.PROTECTED_PATHS` под сторожем.
   - Прочие поля записи `artel` (в том числе профиль тестов части 1) этой
     частью не меняются.
   - Тест-сторож в `tests/` сверяет множество записей поля `no_paths`
     записи `artel` реального `targets.yaml` с `config.PROTECTED_PATHS` и
     называет каждую расходящуюся запись с указанием стороны, где её нет.
   - Сторож зелёный на дереве с наложенным приложением: CI ветки
     накладывает приложения PLAN перед тестами
     (`scripts/plan_appendix_ci.py`). На дереве ветки без приложения он
     красный по построению (см. «Не входит», ожидаемая краснота).

5. **Общие зоны вне конфликта на гейте зон** — свои у каждого проекта.
   - Для артели — `config.COMMON_ZONES`, как сегодня.
   - Для внешнего проекта — пустой перечень. Пути `COMMON_ZONES` — пути
     репозитория артели (`orchestrator/config.py`, `tests/`, …), и в
     чужом репозитории они ничего не значат. Файл внешнего проекта
     проходит гейт зон, только если он покрыт `zones`/`zones_extension`
     задачи.

6. **Классы приложений, требующие полного прогона, на гейте мержа.**
   - Для артели классы прежние: `tests/`, `.github/`, `**/conftest.py`,
     `pyproject.toml`, `pytest.ini`, `setup.cfg`, `tox.ini`.
   - Для внешнего проекта полный прогон требует каждое применённое
     приложение. Пульт не знает, какие файлы чужого репозитория влияют на
     сбор и прогон его тестов, поэтому выбрано строгое правило.
   - Внешний проект с профилем: прогон идёт командой профиля в
     scratch-дереве мержа. Красный исход — тот же отказ мержа, что
     сегодня у артели.
   - Внешний проект без профиля: приложения применяются без полного
     прогона. В журнал задачи пишется запись о том, что полный прогон
     приложений не выполнен, потому что у проекта нет профиля тестов.
     Молча не пропускается ничего.

7. **Карта кодовой базы на гейте мержа** исполняется для проекта, в
   дереве мержа которого есть генератор `scripts/codebase_map.py`.
   - Есть генератор: регенерация и коммит карты идут как сегодня у
     артели. Провал не останавливает мерж и заводит прежний инцидент.
   - Нет генератора: шаг карты не выполняется, коммита карты нет,
     инцидента нет. В журнал задачи пишется запись о том, что карта не
     строится, потому что в дереве мержа нет генератора. Мерж
     продолжается.
   - Шаги `guard --all` и RETRO в той же ветке кода (~980) остаются под
     признаком артели (см. «Не входит»).

8. **Тесты.** Свойства требований 1–7 закрепляются тестами в `tests/` с
   заявками «Ловит мутацию»; долгоживущие приёмочные тесты автора тестов
   (`tests/test_01m45fk56dwmnbrka1vwm12h19_*.py`) засчитываются и
   повторно не пишутся. Существующие тесты не ослабляются.
   - Смену ожиданий существующих тестов разработчик выносит эскалацией с
     точным списком: файл, тест, прежнее и новое ожидание. Это тесты из

     `tests/test_protected_paths_gate.py:123`), и любые другие, найденные
     при работе.
   - Смена проводится по мандату Оператора разделом SPEC «Меняемое
     поведение» механикой задачи «Смена поведения в существующих тестах»,
     с перечнем в PLAN.
   - Дополнение записей `targets.yaml` в фикстурах (например, полем
     `no_paths`) — не смена ожидания. Оно перечисляется в PLAN отдельно.

## Критерии приёмки

AC-1. Для задачи внешнего проекта функция перечня защищённых путей
возвращает записи `no_paths` записи проекта в `targets.yaml`. Путь под
записью `no_paths` признаётся защищённым. Путь под записью
`config.PROTECTED_PATHS`, которой нет в `no_paths` проекта (например,
`skills/x.md` при `no_paths: [infra/]`), защищённым не признаётся.

AC-2. Для задачи артели функция перечня защищённых путей возвращает
`config.PROTECTED_PATHS`, прочитанный в момент вызова. Если подменить
`config.PROTECTED_PATHS`, результат меняется. Если у записи `artel` в
`targets.yaml` поле `no_paths` расходится с `config.PROTECTED_PATHS`,
результат от этого не меняется.

AC-3. Гейт зон на `in_dev -> review` исполняется для задачи внешнего
проекта с заявленными зонами:
- файл вне `zones`/`zones_extension` — отказ перехода «вне зон»;
- файл под записью `no_paths` проекта — отказ с текстом о защищённом
  пути;
- файл под записью `config.PROTECTED_PATHS`, отсутствующей в `no_paths`
  проекта и покрытый зонами задачи, переход не держит.

AC-4. На гейте зон пути `config.COMMON_ZONES` (например,
`orchestrator/config.py`, `tests/test_x.py`) не покрывают файлы задачи
внешнего проекта: такой файл вне заявленных зон — отказ перехода. Для
задачи артели те же пути по-прежнему покрыты общими зонами.

AC-5. На гейте мержа дифф ветки задачи внешнего проекта сверяется по её
перечню:
- путь под записью `no_paths` — задача уходит в `escalated` с тем же
  именованным текстом о защищённом пути, что у артели;
- дифф, задевающий только путь из `config.PROTECTED_PATHS`, которого нет
  в `no_paths`, эскалации не вызывает.

AC-6. Подсветка защищённых путей в черновике MR задачи внешнего проекта
перечисляет пути диффа под записями `no_paths` проекта. Пути под
записями `config.PROTECTED_PATHS`, которых нет в `no_paths`, в ней
отсутствуют.

AC-7. Допуск путей приложений PLAN работает по перечню проекта задачи.
- Приложение к пути из `no_paths` внешнего проекта допускается.
- Приложение к пути вне его перечня (в том числе к пути, защищённому
  только у артели) — именованная ошибка «путь вне защищённых».
- `python3 scripts/guard.py <PLAN.md>` без перечня проекта сверяет пути
  по `config.PROTECTED_PATHS`.

AC-8. Гейт применимости приложений PLAN на выходе `in_dev` исполняется
для задачи внешнего проекта в её рабочей копии. Приложение, которое не
применяется к рабочей копии, отказывает переходу. Применимое приложение
переход не держит.

AC-9. На гейте мержа приложения PLAN задачи внешнего проекта
применяются в scratch-дереве мержа её клона и коммитятся в мерж.
- С профилем тестов любое применённое приложение запускает полный прогон
  командой профиля; красный прогон — отказ мержа.
- Без профиля полный прогон не идёт, а журнал задачи несёт запись, что
  полный прогон приложений не выполнен из-за отсутствия профиля.
- Для артели полный прогон по-прежнему требуют приложения к `tests/`,
  `.github/`, `**/conftest.py`, `pyproject.toml`, `pytest.ini`,
  `setup.cfg`, `tox.ini` и не требуют приложения к остальным защищённым
  путям.

AC-10. Защищённые зоны ТЗ (`new`) и SPEC (гейт SPEC) для задачи внешнего
проекта определяются по `no_paths` её записи. Зона под записью
`no_paths` даёт отказ «защищённый путь только приложением». Зона под
записью `config.PROTECTED_PATHS`, которой нет в `no_paths`, такого отказа
не даёт. Для артели — прежний перечень.

AC-11. Если в дереве мержа нет `scripts/codebase_map.py`, гейт мержа не
коммитит карту и не заводит инцидент карты. Журнал задачи несёт запись,
что карта не строится из-за отсутствия генератора, и мерж доходит до
`done`. Если генератор в дереве мержа есть, карта регенерируется и
коммитится как сегодня, независимо от проекта.

AC-12. Для задачи внешнего проекта, чей контекст не разрешается
(неизвестное имя проекта или нечитаемая запись `targets.yaml`), гейт зон
и гейт применимости приложений PLAN отказывают переходу. Причина
называет проект и неразрешённый контекст. Гейт ёмкости диффа переход по-прежнему
не держит.

AC-13. Тест-сторож сверяет `no_paths` записи `artel` реального
`targets.yaml` с `config.PROTECTED_PATHS`. На дереве с наложенным
приложением PLAN он зелёный. Если записи расходятся (в `targets.yaml`
есть лишняя запись или не хватает записи из `config.PROTECTED_PATHS`),
он красный, и в его выводе названа каждая расходящаяся запись.

AC-14. Приложение PLAN к `targets.yaml` применяется к `main` (`git apply
--check`). После наложения:
- поле `no_paths` записи `artel` по множеству записей равно
  `config.PROTECTED_PATHS` (18 записей);
- комментарий записи не называет поле декларацией;
- остальные поля записи не изменены;
- `orchestrator/targets.py::check` проходит без ошибок.

## Оценка объёма и деление
Сработавшие сигналы:
- в зоне больше 5 файлов: `orchestrator/advance_gates/zones.py`,
  `orchestrator/advance_gates/plan_appendix.py`,
  `orchestrator/fsm_merge_gate.py`, `orchestrator/github_adapter.py`,
  `orchestrator/catalog.py`, `scripts/guard.py` и место функции перечня
  проекта;
- критериев приёмки больше 10 (14);
- `budget_usd` не ниже $30;
- зона задевает механизм, на который опирается запись «Защищённые пути»
  `docs/invariants.md`.

Деление этапа 3 на три части уже сделал Оператор (решение 05.10, ТЗ).
Ниже — материал Оператору для решения о монолите этой части.

**Обоснование монолита.** Нерасщепимая смена механики — удаление развилок
проверок вместе с перечнем защищённых путей проекта. Развилки на гейте
зон, гейте применимости приложений и гейте мержа сегодня существуют
именно потому, что перечень пульта к внешнему проекту неприменим (их
докстринги: «`config.PROTECTED_PATHS` — файлы пульта»). Возможные разрезы
дают нерабочее промежуточное состояние:
- **Развилки сняты, перечня проекта нет.** Внешний проект проверялся бы
  по файлам пульта: ложные отказы и пропуск его собственных защищённых
  путей.
- **Перечень проекта есть, развилки на месте.** Для внешнего проекта это
  мёртвый код, сверх которого «сторож совпадения» артели ничего не
  проверяет.

Резать по зонам нельзя: зона части — один каталог `orchestrator/` плюс
`scripts/guard.py` и `tests/`. Любые две подчасти делили бы
`orchestrator/` и шли бы друг за другом замком зон без выигрыша в
параллельности, тем же доводом, что сам Оператор привёл для частей 1 и 2.
Приложение к `targets.yaml` и его сторож неотделимы друг от друга:
сторож без приложения красен.

**Бюджет.** По калибровке класс задачи — больше 15 критериев или от 8
файлов зоны, то есть ~85. Миссия шага разрешает только снижение от
дефолта $50, поэтому выставлено $50, на $5 выше рамки ТЗ ($45). Для
сравнения: этап 2 при рамке $60 потратил $155. Потолок группы 3 по
решению Оператора — $100; поднять его можно командой `budget`.

## Не входит
- **Часть 1 этапа 3** (01M45FJVGQT1K0P8HDEXZX6HS7): профиль тестов
  проекта (имя, форма, разбор поля, запись профиля артели), работа
  проекта без профиля и перевод проверок тестов. Сюда входят
  неослабление, заявка мутации, долгоживущие файлы, строки группы,
  перечень сумм, раздел изменённых утверждений пакета ревью, шаг
  неослабления на гейте мержа (`fsm_merge_gate.py` ~123) и прогон планки
  в рабочей копии задачи. Эта часть только пользуется профилем:
  командой полного прогона в требовании 6.
- **Часть 3 этапа 3:** прочие 28 развилок по проекту пульта по умолчанию,
  в том числе развилки `orchestrator/zone_lock.py`, `checkpoint.py` и
  `github_adapter.py::_gh_repo_kwargs`, и места сверки вне перечня
  «Фактов» ТЗ. Кроме того: сведение дубля разрешения контекста, сторож
  против прямых сравнений, сквозной тест внешнего потока в песочнице и
  описание перевода в карте кодовой базы.
- **Шаги `guard --all` и RETRO на гейте мержа** (~980) остаются под
  признаком артели. Они не входят в перечень проверок ТЗ п.2, а коммит
  RETRO в `main` — предмет этапа 4.
- **Этап 4:** отмена наложения снимка документов и коммита RETRO на
  `main`, уборка каталога задач из `main` артели, пересмотр ADR-0020 п.2.
- Разделение журналов и базы по проектам (триггер №29). Подключение
  реального внешнего проекта.
- **Правка файлов только для чтения по ТЗ:** `docs/invariants.md`,
  `tests/test_invariants.py`, `docs/adr/`, `docs/roadmap.md`,
  `docs/backlog.md`, `docs/operator-session.md`, `templates/`, `skills/`,
  `CLAUDE.md`, `models.yaml`, `roles.yaml`, `.github/workflows/ci.yml`,
  `conftest.py`, `scripts/ci_protected_paths.py`,
  `scripts/codebase_map.py`. Правка `scripts/plan_appendix_ci.py` и
  `.github/` (упомянуты как класс полного прогона и как механизм CI
  ветки) — тоже не входит. Выбор источника в требовании 1 формулировку
  инварианта не меняет. Найдёт разработчик, что менять её всё же нужно, —
  эскалация с вопросом Оператору.
- `targets.yaml` в кодовой ветке не меняется, только приложением к PLAN
  (требование 4).
- Раздел «Меняемое поведение» заранее не заполняется: мандат на смену
  ожиданий существующих тестов Оператор выдаёт по эскалации роли (ТЗ).
- **Ожидаемая краснота сторожа AC-13 на дереве ветки без приложения.**
  Полный набор `tests/` на `acceptance` (автогейт и `approve`) гоняется
  в рабочей копии задачи без наложенных приложений

  красный по построению. CI ветки накладывает приложения и даёт зелёный

  приёмки, это не дефект кода задачи.
- Зелёный полный набор `tests/`, зелёный CI ветки, неизменность
  защищённых путей в кодовой ветке и непревышение бюджета держит пульт.
