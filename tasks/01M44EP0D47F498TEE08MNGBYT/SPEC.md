# SPEC: Порядок мержей по зависимостям задач: поле merge_after

## Контекст
Пульт мержит задачи в порядке прихода на гейт мержа: очередь
`orchestrator/merge_queue.py` — FIFO по времени входа, о смысловом порядке
задач она не знает. Порядок «эта задача — только после той» живёт лишь
текстом (строка «Порядок:» ТЗ и подразделов «## Деление»), и пульт его не
исполняет. Прецедент 13.09: инвариант из приложения 01M2CN465W попал в
main раньше мержа фикса — набор был красен до мержа, остальные мержи волны
стояли. Задача вводит машиночитаемое поле зависимостей `merge_after`:
оно проверяется на гейте SPEC, хранится в БД, переписывается только по
трём каналам с журналом и удерживает `approve` на `merge_gate`, пока
зависимости не в `done`.

## Требования
1. **Поле SPEC.** SPEC несёт необязательное поле frontmatter `merge_after`
   — список id задач через запятую либо пусто. Если поля нет или оно
   пусто, зависимостей нет. Элементом может быть полный id или его
   префикс. `scripts/guard.py` проверяет только форму, без доступа к БД:
   каждый элемент — строка в формате id задачи пульта, элементы не
   повторяются, ни один не совпадает с id самой задачи (поле `task:`
   frontmatter). Нарушение — ошибка guard, которая называет элемент и
   причину. Проверка формы действует для SPEC любой `schema_version`, если
   поле присутствует. Новая версия схемы не вводится:
   `SUPPORTED_SCHEMA_VERSION` остаётся 5. Существующие SPEC, где поля нет,
   остаются валидными без правок.
2. **Гейт SPEC.** `approve` на `spec_gate` проверяет каждый элемент
   `merge_after` по БД и отказывает с именем элемента и причиной, если:
   (а) задачи нет; (б) префикс неоднозначен (разрешение — тот же узел,
   что `store.resolve_task_id`); (в) задача в состоянии `killed`;
   (г) задача принадлежит другому target, чем проверяемая задача;
   (д) после разрешения префиксов зависимость указывает на саму задачу
   или замыкает цикл в графе `merge_after` всех задач БД с учётом нового
   значения. Отказ работает тем же мягким путём, что отказ сверки путей с
   зонами (`fsm.py::_approve_spec_gate`): задача остаётся на `spec_gate`,
   `merge_after` в БД не пишется, журнал задачи называет причину. Если
   проверки прошли, значение пишется в новую колонку таблицы `tasks` в том
   же `approve`, что и `zones`, полными id в порядке SPEC. Если поля нет,
   колонка пуста. На переходе `spec_writing -> spec_gate` проверки по БД
   не выполняются, там действует только проверка формы через guard
   (требование 1). Колонка добавляется и в DDL, и миграцией
   `add_column` (`orchestrator/schema.py`).
3. **Каналы переписывания.** После гейта SPEC значение `merge_after` в БД
   меняется только по трём каналам. Каждое изменение пишет в журнал задачи
   строку «было → стало» с указанием канала. Новое значение каждого канала
   проходит проверки требований 1 и 2 (форма, существование, однозначность,
   не `killed`, тот же target, отсутствие самоссылки и цикла).
   - **PLAN.** Канал работает на переходе `in_dev -> verifying` по образцу
     `fsm_advance._apply_plan_budget`. Если в frontmatter PLAN.md есть поле
     `merge_after` и его значение после разрешения полными id отличается от
     значения в БД, значение применяется при двух условиях: раздел PLAN.md
     «Влияние на систему» содержит строку `merge_after` (это обоснование
     смены), и новое значение прошло проверки. Пустое поле снимает все
     зависимости. Если поля в PLAN нет, значение в БД не меняется и журнал
     молчит. Если значение не проходит проверку или нет обоснования, в
     журнал пишется «merge_after из PLAN отклонён» с причиной и прежним
     значением, а переход идёт как раньше: отказ значения не останавливает
     переход, как у бюджета из PLAN. Канал не ограничен одним разом, он
     срабатывает на каждом таком переходе.
   - **Мандат Оператора в ANSWER-n.md.** Вводится третий вид строки
     мандата с маркером `Зависимости мержа:`, он добавляется в
     `mandate.MANDATE_MARKERS`. После маркера идёт список id через
     запятую (полных или префиксов) либо одно слово `нет`, которое снимает
     все зависимости. Строка задаёт новое значение целиком. Её проверяет
     узел `mandate.refusals` при записи ответа (`answer`) до коммита
     ANSWER, по правилам требований 1 и 2. Если проверка не прошла,
     `answer` отказывает: ANSWER не коммитится, БД не меняется. Если
     прошла, `answer` пишет новое значение в БД (полными id) с записью
     журнала «было → стало». Строка мандата принимается в тех же
     состояниях, что мандаты зон и тестов (`escalated`, `in_dev`,
     `review`), и дополнительно в `merge_gate`: иначе отказ из-за убитой
     зависимости (требование 4) не мог бы назвать рабочий канал. В
     `in_dev`/`review`/`merge_gate` действует тот же рубеж окружения роли
     (`runner.in_role_environment`), что у мандата зон. В `merge_gate`
     ANSWER без этой строки отказывается, как раньше.
   - **Эскалация роли.** Роль предлагает новое значение в своей эскалации
     (`QUESTIONS.md` или раздел «## Эскалация» артефакта) готовой строкой
     мандата `Зависимости мержа: …`. Значение вступает в силу, только когда
     Оператор переносит эту строку в ANSWER-n.md, то есть через канал
     мандата выше. Отдельного кода, который читает предложение из
     эскалации, нет.
4. **Гейт мержа.** `approve` на `merge_gate` проверяет `merge_after` до
   взятия мьютекса merge-окна (`merge_lock.acquire`) и до входа в
   `merge_queue`.
   - Если хоть одна зависимость не в `done` и ни одна не в `killed`, гейт
     отказывает. Печать и журнал задачи называют каждую незавершённую
     зависимость с её текущим состоянием и подсказку повтора
     `approve <id>`. Мьютекс не берётся, строка `merge_queue` не
     пишется, задача остаётся на `merge_gate`, merge не выполняется.
   - Если хоть одна зависимость в `killed`, гейт отказывает отдельным
     именованным отказом. Он называет убитую задачу и канал снятия
     зависимости: `answer` со строкой `Зависимости мержа: …`
     (требование 3). Мьютекс и очередь при этом не трогаются, задача
     остаётся на `merge_gate`.
   - Если поля нет или все зависимости в `done`, гейт и очередь работают
     как раньше, а `merge_queue` остаётся только взаимным исключением
     окна.
5. **`status` и `show`.** `catalog.cmd_status` дописывает в конец строки
   задачи добавку `[ждёт мержа: <id> (<состояние>), …]`. Её строят тем же
   способом, что `_zone_wait_suffix`: заново из БД на каждый вызов. Добавка
   печатается только в состояниях `acceptance` и `merge_gate` и только
   пока есть зависимости не в `done`. В добавку входят только такие
   зависимости. `show <id>` печатает строку `зависимости мержа: <id>
   (<состояние>), …` со всеми зависимостями задачи, включая
   завершённые, если поле непустое, в любом состоянии задачи. Если поле
   пустое, строки нет.
6. **Карта кодовой базы.** `docs/codebase-map.md` описывает поле
   `merge_after`, место проверки (гейт SPEC и каналы) и место отказа (гейт
   мержа). Карта автогенерируемая, поэтому описание попадает в неё через
   docstring модулей при регенерации `scripts/codebase_map.py`, а не
   ручной правкой.
7. **Приложение к PLAN.** Правка защищённых путей делается приложением к
   PLAN.md (unified-диф, `git apply --check` на чистом дереве) и включает:
   - в `templates/SPEC.md` — закомментированное поле `merge_after` с
     пояснением по образцу `zones`/`budget_usd`;
   - в `templates/PLAN.md` — закомментированное поле `merge_after` с
     правилом: смену обосновывает раздел «Влияние на систему», и в нём
     упоминается `merge_after`;
   - в `skills/spec-authoring.md` — правило аналитику: `merge_after`
     заполняется из ТЗ («Порядок: после …»), изобретать зависимости без
     основания нельзя;
   - в `skills/escalation-rules.md` — как роль предлагает смену
     `merge_after` готовой строкой `Зависимости мержа: …` в эскалации.

## Критерии приёмки

AC-1. `python3 scripts/guard.py` на SPEC с `merge_after:
01M44EP0D47F498TEE08MNGBYT`, где этот id совпадает с полем `task:`, даёт
ошибку, которая называет поле и элемент. SPEC с повтором элемента
(`merge_after: 01M446X1, 01M446X1`) даёт ошибку о повторе. SPEC с
элементом не в формате id задачи (например, `merge_after: foo bar`) даёт
ошибку формы. SPEC с корректным списком из двух разных id и SPEC без поля
`merge_after` (`schema_version` 1–5) проходят без ошибок по этому полю.
`guard.SUPPORTED_SCHEMA_VERSION` равен 5.

AC-2. `approve` на `spec_gate` задачи, у которой SPEC несёт в
`merge_after` id отсутствующей задачи, оставляет её на `spec_gate`,
колонка `merge_after` в БД остаётся пустой, журнал задачи называет этот
id и причину «нет такой задачи». Так же ведёт себя префикс, подходящий
к двум задачам: причина — неоднозначность.

AC-3. `approve` на `spec_gate` отказывает тем же способом (задача на
`spec_gate`, колонка не записана, журнал называет id и причину) в трёх
случаях: зависимость в состоянии `killed`; зависимость с другим target;
префикс в `merge_after`, который разрешается в id самой задачи.

AC-4. `approve` на `spec_gate` задачи A с `merge_after: B` отказывает с
причиной «цикл», если в БД у задачи B уже записано `merge_after = A`
(также при цикле через третью задачу C). Задача A остаётся на `spec_gate`.

AC-5. `approve` на `spec_gate` с корректным `merge_after`, заданным
префиксами, переводит задачу дальше и пишет в колонку `merge_after` БД
полные id тем же `approve`, что и `zones`. SPEC без поля даёт пустую
колонку, и переход идёт как раньше.

AC-6. `approve` на `merge_gate` задачи, у которой зависимость в состоянии
не `done` и не `killed` (например, `acceptance`), отказывает. Печать и
журнал называют id зависимости, её состояние и подсказку
`approve <id>`. Задача остаётся на `merge_gate`, мьютекс merge-окна не
занят (строки `merge_lock` нет), в `merge_queue` нет строки задачи,
merge не выполнялся.

AC-7. `approve` на `merge_gate` задачи, у которой зависимость в `killed`,
отказывает сообщением, отличным от отказа AC-6. Сообщение называет убитую
зависимость и канал снятия: `answer` со строкой `Зависимости мержа:`.
Мьютекс и очередь не заняты, задача на `merge_gate`, ожидания в цикле
нет: команда возвращается.

AC-8. Если все зависимости задачи в `done` или поля `merge_after` у
задачи нет, `approve` на `merge_gate` проходит прежним путём: берёт
мьютекс merge-окна, при занятом окне встаёт в `merge_queue`, выполняет
merge.

AC-9. На переходе `in_dev -> verifying` PLAN.md с `merge_after`, отличным
от значения в БД, и с упоминанием `merge_after` в разделе «Влияние на
систему» меняет значение в БД (полными id). Журнал задачи получает
строку с прежним и новым значением. Пустое `merge_after:` в PLAN снимает
зависимости тем же способом. PLAN без поля значение в БД не меняет.

AC-10. На переходе `in_dev -> verifying` значение в БД остаётся прежним,
журнал получает запись об отклонении с причиной, а задача всё равно
переходит в `verifying`, если PLAN.md несёт `merge_after`, который не
проходит проверку (несуществующая, убитая или собственная зависимость,
цикл) или не обоснован в разделе «Влияние на систему».

AC-11. `answer` с ANSWER-n.md, где есть строка `Зависимости мержа: <id>`,
для задачи в `escalated` пишет новое значение в БД полными id и строку
журнала «было → стало». Строка `Зависимости мержа: нет` очищает значение.
В состоянии `merge_gate` такой `answer` принимается, вызванный вне
окружения роли.

AC-12. `answer` с ANSWER-n.md, чья строка `Зависимости мержа:` называет
несуществующую, убитую, собственную или замыкающую цикл зависимость,
отказывает до коммита: ANSWER-n.md не появляется в ссылке документов
задачи, значение в БД не меняется. Отказывает и `answer` в `merge_gate`,
если файл без этой строки или процесс вызван в окружении роли.

AC-13. `status` печатает в конце строки задачи в `acceptance` или
`merge_gate` добавку `[ждёт мержа: <id> (<состояние>)]` по каждой
зависимости не в `done`. Добавки нет, если все зависимости в `done`, если
поля нет и если задача в другом состоянии (например, `in_dev`). После
перевода зависимости в `done` в БД следующий вызов `status` печатает
строку без добавки, без других действий.

AC-14. `show <id>` задачи с непустым `merge_after` печатает строку
`зависимости мержа:` со всеми зависимостями и их состояниями, включая
`done`. У задачи без зависимостей такой строки нет.

AC-15. После `python3 scripts/codebase_map.py` текст
`docs/codebase-map.md` содержит `merge_after` в строке «Назначение»
хотя бы одного раздела модуля `orchestrator/`. Закоммиченная карта
совпадает с выводом генератора.

## Оценка объёма и деление
Сработавшие сигналы: число критериев приёмки 15 (порог 10). Число файлов
зоны не меньше 5: каталоги `orchestrator/` и `tests/` (по коду правки
ожидаются в `schema.py`, `fsm.py`, `fsm_merge_gate.py`, `fsm_advance.py`,
`answer.py`, `advance_gates/mandate.py`, `catalog.py` и `scripts/guard.py`).

**Обоснование монолита** (материал для решения Оператора):
- Поле без отказа на гейте мержа — мёртвые данные: БД его хранит, но
  ничто его не исполняет.
- Отказ на гейте мержа без проверки на гейте SPEC пропускает в БД
  несуществующие, убитые и циклические зависимости. Задача с циклом
  навсегда остаётся на `merge_gate`.
- Отказ из-за убитой зависимости без канала мандата в `answer` (с
  приёмом в `merge_gate`) оставляет задачу на `merge_gate` без штатного
  выхода, кроме `kill`.

Поэтому поле, гейт SPEC, мандат `answer` и отказ гейта мержа — одна
атомарная смена механики. Отдельно отделимы только канал PLAN
(требование 3, AC-9–AC-10) и добавки `status`/`show` (AC-13–AC-14). Это
небольшие части: на отдельный цикл с планкой не ниже $25 каждая
подзадача стоила бы дороже, чем экономит.

Бюджет: `budget_usd: 40` равен рамке Оператора из ТЗ. Калибровка
`config.BUDGET_CALIBRATION_TABLE` для 15 критериев и 8+ файлов кода даёт
ориентир выше, около $45–85. Это риск недобора бюджета на второй
итерации ревью. Поднять потолок вправе только Оператор командой `budget`.

## Не входит
Приложением: templates/SPEC.md, templates/PLAN.md, skills/spec-authoring.md, skills/escalation-rules.md.
Только чтение: scripts/codebase_map.py.

- Зависимость старта developer — предусловие `run` по `merge_after`, как
  у лока зон.
- Автоматический разбор строки «Порядок:» ТЗ командой `new` и подразделов
  «## Деление» (`fsm._spawn_division_subtasks` поле не заполняет).
- Ожидание зависимости циклом внутри `approve` вместо отказа.
- Перестановка FIFO `merge_queue` или учёт в ней смыслового порядка.
- Проверка циклов в `doctor`.
- Проверка `merge_after` по БД на переходе `spec_writing -> spec_gate`:
  там действует только проверка формы guard.
- Чтение предложения новой зависимости из эскалации роли кодом: такое
  предложение вступает в силу только через мандат в ANSWER.
- Новая `schema_version` артефактов.
- Правка путей только для чтения: `docs/adr/`, `docs/roadmap.md`,
  `docs/backlog.md`, `docs/operator-session.md`, `CLAUDE.md`,
  `models.yaml`, `roles.yaml`, `.github/workflows/ci.yml`, `conftest.py`,
  `tests/test_invariants.py`, `docs/invariants.md`.
- Требование ТЗ п.7 о тестах с заявкой «Ловит мутацию» покрывают
  приёмочные тесты автора тестов по AC-1–AC-15 в `tests/`. Отдельных
  повторов этих свойств SPEC не требует. Неослабление существующих
  тестов и полный зелёный `tests/` проверяет пульт.
- Новое состояние FSM: отказы гейтов оставляют задачу в прежнем
  состоянии, маршрут не меняется. Поэтому числа шагов в
  `tests/test_invariants.py` не затрагиваются.
