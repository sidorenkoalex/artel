# PLAN: автогейт приёмки — критерий «существующие tests/ зелёные» исполняется по CI

## Подход

Новая пометка критерия `ci` (наравне с `manual`/`skip`/`escalate`)
проходит через три точки, которые уже разбирают/потребляют пометки
`AC-n`, без создания параллельных путей:

1. `scripts/guard.py` — единственное ядро разбора пометок
   (`AC_MARKER`/`scan_ac_content`) и единственное ядро трассируемости
   (`traceability_errors_from_content`), которое уже переиспользуют и
   дисковый путь (`acceptance_traceability_errors`), и ветко-корректный
   (`orchestrator/fsm.py::_tests_writing_ac_state`, SPEC T031) —
   правится только здесь, оба потребителя получают новое поведение
   бесплатно.
   - `AC_MARKER`: альтернатива `(manual|skip|escalate)` расширяется
     литералом `ci`.
   - Новая функция `ci_marker_wording_ok(criterion_text)` — эвристика
     по ключевым словам требования 3/AC-2 («существующ», `tests/`,
     «зелён», «не ослаб»), case-insensitive substring match,
     fail-closed (ни одного слова — не ok).
   - Новый regex `AC_ITEM_FULL` — тот же якорь `^AC-(\d+)\.`, что и
     существующий `AC_ITEM`, но захватывает полный текст критерия (до
     следующего `AC-n.` или конца раздела) — нужен, чтобы сверить
     формулировку критерия с пометкой `ci` этого же номера.
   - `traceability_errors_from_content`: в ветке `for n, (kind, reason)
     in markers.items()` добавляется `elif kind == "ci" and not
     ci_marker_wording_ok(...)`, называющая номер критерия и
     подсказывающая `manual` — тот же приём и то же место, что уже
     обрабатывает `skip`/`escalate` без причины.

2. `orchestrator/fsm_autogate.py::_autogate_conditions` — условие «а»
   получает третью ветвь (после существующих `manual_ns`/`skip_ns`):
   критерии с пометкой `ci` не смешиваются с manual/skip-списками
   (AC-3), а проверяются через `orchestrator/ci.py::verifying_status`
   —ту же функцию, что уже опрашивает `orchestrator/fsm_advance.py::
   verifying` для головы КОДОВОЙ ветки задачи (`t["branch"]`), поэтому
   «sha головы обязан совпасть со sha, для которого CI зелёный»
   (требование 2) выполняется автоматически конструкцией
   `verifying_status` (она сама берёт sha из `head_sha(branch)` и
   спрашивает CI именно этого sha) — без отдельной сверки sha в новом
   коде. Не-зелёный исход (`none`/`running`/`red`) — ранний возврат с
   причиной, называющей критерий и note; зелёный — запись в `ok` и
   продолжение существующей цепочки условий б/в/г/д без изменений.

3. `orchestrator/acceptance.py::summary` — новый необязательный
   параметр `branch: str | None = None` (тот же приём именования, что
   `materialize_from_branch(task_id, branch, code_dir)`), сводка
   получает третью категорию (`ci`) рядом с `manual`/`skip`: число в
   заголовочной строке и, если пометки `ci` есть и `branch` назван,
   строка на критерий с результатом `ci.verifying_status(branch)`.
   Единственный вызывающий (`orchestrator/fsm_advance.py::review`,
   строка с `card = acceptance.summary(acc_tdir)`) передаёт
   `branch=t["branch"]` — тот же `t["branch"]`, который уже читает
   `_autogate_conditions` и `verifying()`.

`skills/test-authoring.md` — приложение к этому PLAN отдельным
unified-диффом (защищённый путь, правит только Оператор, требование
5/AC-7); дифф проверен `git apply --check` на чистом дереве перед
сдачей.

## Влияние на систему

Затронуты структурные инварианты guard (AC-разметка/трассируемость) и
механика автогейта приёмки (ADR-0007) — оба уже несут собственные
юнит-тесты (`tests/test_guard_*`, `tests/test_fsm_autogate.py`), которые
эта задача прогоняет без ослабления (AC-8, п.5 плана). Новая ветвь
условия «а» — строго ДОБАВЛЕНИЕ (пометка `ci`, которой не существовало
до этой задачи), существующие пути (без пометки `ci` вовсе, только
`manual`/`skip`) проходят прежним кодом байт-в-байт: ни один
существующий тест на `manual_ns`/`skip_ns` не меняет поведения. Новый
параметр `acceptance.summary(tdir, branch=None)` — с дефолтом `None`,
обратная совместимость гарантирована сигнатурой (единственный
вызывающий явно передаёт `branch`). Откат — правка ограничена 4 файлами
зоны, ревертится одним `git revert` без внешних побочных эффектов (ни
миграций схемы БД, ни изменений `gates.yaml`/`roles.yaml`).

## Риски

- Эвристика `ci_marker_wording_ok` — по ключевым словам, не по смыслу:
  критерий с пометкой `ci`, который случайно содержит слово «зелён» не
  в контексте тестов, прошёл бы без отказа. Fail-closed работает только
  в одну сторону (нет слова → отказ); ложноположительный пропуск —
  риск, который SPEC явно принимает (требование 3: «эвристика по тексту
  критерия», не семантический анализ).
- `ci.verifying_status` — тот же вызов `gh`, что и `verifying()`;
  двойной опрос CI за один вход в `acceptance` (один — из
  `_maybe_autogate_acceptance` через `_autogate_conditions`, если есть
  пометка `ci`) не новая нагрузка относительно уже существующего
  вызова `verifying()` при входе в `verifying`, но у ролей задачи с
  несколькими критериями `ci` в одной планке — один вызов на всю
  планку (список `ci_ns` собирается один раз), не по одному на
  критерий.

### Вопросы

1. (блокирует) Гейт `_review_rework_gate_refuses`
   (`orchestrator/fsm_advance.py:738-787`) сравнивает время последнего
   коммита, тронувшего `tasks/<id>/REVIEW.md` на артефактной ветке
   (`review_ts`), со временем последнего НЕ-«подтяжка main» коммита
   кодовой ветки (`code_ts`): отказ, если `code_ts <= review_ts`. На
   этой задаче `review_ts` = 2026-09-06T02:18:26+03:00 — это автокоммит
   «артефакты шага developer», КОТОРЫЙ САМ РАЗМЕТИЛ реестр замечаний
   REVIEW.md (`fixed`/`fixed`/`rejected`/`fixed` для R1-F1..R1-F4, как и
   требует coding-standards.md) уже ПОСЛЕ того, как код фикса был
   закоммичен (`5d841e89`, 2026-09-06T02:17:53+03:00) — оба события одного
   и того же шага developer, автокоммит артефактов пишется строго после
   кода. Итог: `code_ts` (02:17:53) < `review_ts` (02:18:26) — гейт
   отказывает с формулировкой «нет шага developer после итерации 1»,
   хотя фикс есть, реестр размечен, все существующие тесты + guard +
   приёмка зелёные (см. «Контекст»). Три подряд отказа `advance` с этой
   же формулировкой (история отказов) — тот же коммит `5d841e89`
   каждый раз, дальше расти `code_ts` неоткуда без ЕЩЁ ОДНОГО коммита
   кода. Как разблокировать переход `in_dev -> review`?
   - (a) Разработчик делает в этом шаге ещё один коммит в кодовую ветку
     (реальных изменений в зоне SPEC уже не осталось — весь диф зоны
     реализован и подтверждён тестами), чтобы `code_ts` стал позже
     `review_ts`, — точечный обход именно этой задачи, без правки
     гейта. Дефолт при молчании — НЕ делаю сам: коммит без
     содержательного изменения — то, от чего явно предостерегает
     coding-standards.md («не изобретай»), а какой именно коммит
     легитимен — решение вне роли developer.
   - (b) Правка `_review_rework_gate_refuses` — брать время ПЕРВОГО
     коммита с `status: changes_requested` текущей итерации (коммит
     ревьювера), а не «последний коммit, тронувший REVIEW.md» (который
     смешивает автора-ревьювера и автора-разработчика) — правильный
     фикс класса дефекта, но `orchestrator/fsm_advance.py` вне зон этой
     SPEC (зона: `orchestrator/fsm_autogate.py`, `orchestrator/ci.py`,
     `scripts/guard.py`, `orchestrator/acceptance.py`, `tests/`; ранее
     ANSWER-1.md уже расширял зону на ОДНУ конкретную строку этого же
     файла под AC-6, не на этот гейт) — нужен отдельный мандат или
     отдельная задача.
   - (c) Оператор проводит переход `in_dev -> review` в обход гейта
     вручную (минуя `advance`).
   - Дефолт на случай молчания по всему пункту: не предпринимаю (a) —
     жду решения Оператора по (a)/(b)/(c), артефакт остаётся в
     `escalate`.
