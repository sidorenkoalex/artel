## Требуется

1. **Поля профиля.** `Profile` получает `test_support: tuple = ()`, `layers: tuple = ()` и `paths: tuple = ()` (вне сравнения, как прочие поля компонента; строка записи `paths` — кортеж из одного элемента, как в `_regexes`); `_with_component_fields` их переносит. Действующие слои — новая `project_profile.layers_of(profile)`: явное поле `layers`; без поля — `("python-ast",)` у команды pytest (`acceptance.is_pytest_command` отложенным импортом, как в `plank_rule`) и `()` у прочих. Проверка записи `check` в `orchestrator/targets.py` (в `_check_component_rules`, признак pytest — `_is_pytest_command`) после прежней проверки вида значения отказывает элементу `layers`, отличному от `python-ast` («<место>: поле 'layers' — '<элемент>': допустим только python-ast»), и `python-ast` у компонента с командой не pytest («<место>: поле 'layers' — python-ast у команды не pytest»). Строгий режим — профиль в границе без `python-ast` в действующих слоях; при `python-ast` слой python-ast снимает строгий режим только для файлов .py внутри `test_support`, прочие файлы под масками `test_support` (данные, снимки) — в строгом режиме.
2. **Прежние версии на коде ветки.** В `_judge` после сравнения: набор C — пути каждой записи `diff_name_status(база, голова)`, кроме `A` (у `R` — прежний путь), подходящие под маски `tests` или `test_support` компонента, плюс файлы всех заменяемых тестов компонента (`approved_replacements`, компонент идентификатора — компонент профиля). У компонента без `tests` тестовые файлы C — пути файлов всех записей полного отчёта базы, включая записи ошибок уровня файла (строгая альтернатива); пути `test_support` и файлы замен входят в C по-прежнему. C пуст — шаг не исполняется (ни выписки, ни прогона, ни строки записи). Иначе третья выписка — прямо в `scratch/<ключ>` вызовом `worktree add --detach` (уборка — тем же `finally` в `_gate`), в `trees` под ключом, отличным от «база» и «голова ветки»; пути C восстанавливаются `git checkout <база> -- <пути>` (удалённый — восстановлен; новый путь переименования остаётся); прогон — полный набор компонента (`components_full_suite`, `fresh=True`), если в C есть путь `test_support`, иначе только файлы `tests` из C (`_report_run` с пределом компонента). Судятся идентификаторы базы из `PASS_TO_PASS`, чей файл попал в прогон. Исход прежней версии — по правилу перепрогона: зелёный — `in_pass_to_pass`, всё прочее (красный, пропуск, `todo`, нет записи) — красный. Красный — два перепрогона файла на третьей выписке и на базе тем же `_rerun` (выписка прежних версий — на месте стороны ветки) и классификация по правилу `_redness`; трижды красный — находка «прежняя версия красная на коде ветки», вперемешку — «прежняя версия нестабильна на коде ветки», история перепрогонов третьей выписки ведётся отдельно от истории базы и ветки, красная база — строка «нестабилен и на базе», как сейчас. Строка находки — прежней формы «<вид>: <идентификатор> — <исходы>», исходы начинаются с «прежняя версия: » и несут «; база: ». Находка этого требования по идентификатору, у которого уже есть находка прежнего вида, не добавляется (одна находка на идентификатор, старшая). Сбой выписки или прогона — отказ подготовки (`_Prepare`), не пропуск.
3. **Заменяемые тесты на деле.** Для каждого идентификатора `approved_replacements` компонента: нет в отчёте базы — находка «заменяемый тест не найден в отчёте базы»; на базе не из `PASS_TO_PASS`, а также красный хотя бы в одном перепрогоне базы — находка «заменяемый тест не зелёный на базе» (исходы обеих — с «база: »; для красного в перепрогоне — с исходами перепрогонов); строки «заменён по SPEC» в этом случае нет; прежняя версия зелёная хотя бы в одном прогоне третьей выписки — находка «замена не нужна: прежняя версия зелёная на коде ветки» (исходы — с «прежняя версия: »); трижды красная при зелёной базе — строка записи «заменён по SPEC: <идентификатор> → AC-<n>». Находки этого требования добавляются и при находке прежнего вида по тому же идентификатору. Утверждённая замена снимает только находки «исчез» и «прежняя версия красная на коде ветки» своего идентификатора: элемент покрытия — `замена:<идентификатор>→AC-<n>`, источник в строке записи — «замена SPEC → AC-<n>»; сначала проверяется мандат Оператора (`_covering_pair`), затем замена. «Сломан правкой», «нестабилен», пропуск, `todo`, `fails` и находки этого требования она не снимает. Не заявленный тест, красный на третьей выписке, снимает только мандат Оператора.
4. **Строгий режим.** У профиля в строгом режиме каждый существующий файл (запись `diff_name_status`, кроме `A`; у `R` — прежний путь) `tests` или `test_support` — находка вида «строгий режим — правка существующего файла», строка `строгий режим — правка существующего файла: <путь> — статус <статус>` (идентификатор находки — путь), в том числе файл заменяемого теста. Её снимает только мандат Оператора прежним маркером «Ослабление тестов разрешено:» с элементом, равным пути файла (новая функция покрытия пути: элемент прежнего маркера, равный пути; она также принимает путь в мандате на путь — см. ниже; мандат по идентификатору и префикс `путь::имя` её не снимают); утверждённая замена её не снимает. В строгом режиме утверждённая замена снимает только находки «исчез» и «прежняя версия красная на коде ветки» своего теста. Критерий: правка соседнего теста в файле заменяемого теста без мандата на путь файла — находка, отказ гейта.

   **Мандат на путь вне `weakening_scope`.** В `orchestrator/advance_gates/mandate.py` (`_weakening_scope_refusal`) у профиля в границе `in_outcome_bounds` элемент прежнего маркера годен, если путь в `weakening_scope`, под масками `tests`/`test_support` компонента или в файлах компонента по `paths` (без `paths` — любой путь репозитория). Критерий: мандат на путь файла кода с находкой «исключение в коде», выданный командой `answer`, принят и снимает находку.
5. **Исключения в коде.** Строки, добавленные диффом `git diff -M -U0 база голова` (номер строки — по файлу головы; переименование без правки строк находки не даёт; двоичные файлы пропускаются) в файлы компонента вне масок `tests` и `test_support` (компонент файла — по полю `paths`; у единственного компонента без `paths` — любой файл репозитория), содержащие подстроку из `outcome_integrity.CODE_EXCEPTION_TOKENS = ("v8 ignore", "istanbul ignore", "c8 ignore", "eslint-disable", "import.meta.env.MODE", "process.env.VITEST", "NODE_ENV")`, — находка вида «исключение в коде», строка `исключение в коде: <путь> — строка <n>: <подстрока>` (идентификатор — путь; по находке на строку и подстроку); снимает её только мандат с элементом, равным пути (та же функция покрытия пути, что в требовании 4). Действует у всех профилей в границе. Удалённые строки и файлы под масками `tests`/`test_support` не проверяются.
6. **Находки и доказательство.** Новые виды входят в `_KINDS`, `_RANK` (после прежних, номерами 4–10 в порядке перечисления видов в требованиях 2–5) и разбор `_finding_id` (идентификатор — тест или путь; граница идентификатора — первые « — » с исходами своего вида). Действие отказа — прежнее правило (`BROKEN_REFUSAL_ACTION`, только если все непокрытые находки — «сломан правкой», иначе `OUTCOME_REFUSAL_ACTION`); новых действий журнала нет. Подсказка `_mandate_hint` для новых видов называет мандат на путь. В отпечаток доказательства входят элементы `замена:<идентификатор>→AC-<n>` всех утверждённых замен компонента по последней записи, не только покрывших находки; `_proven` пересчитывает покрытие по виду находки (тест — `_covering_pair`, затем замена по текущей последней записи утверждения; путь — функция покрытия пути) — новое утверждение SPEC отменяет доказательство. Строка счёта записи пройденного гейта прежняя; прогоны третьей выписки — отдельной строкой «прежние версии: файлов <n>; прогонов <m>» только при непустом C. Порядок строк записи пройденного гейта: счёт, доказательство, «прежние версии: …», «нестабилен и на базе», «заменён по SPEC», покрытые находки. Оба рубежа — одним ядром.
7. **Автогейт по правилу планки.** `_plank_rule_refusal` отказывает только при отказе построения правила; при правиле не по умолчанию `_autogate_conditions` читает пометки планки по правилу (`_plank_sources(…, rule=rule)`, `scan_ac_content(…, rule=rule)`). Правило по умолчанию — прежние условия и тексты побайтно. Отказ снимается при правиле не по умолчанию только если профиль задачи в границе гейта исходов; иначе — прежний текст отказа.
8. Тесты детерминированы, без сети и без Node (учебный проект в git: компонент `junit-xml` с pytest и компонент `pult-vitest` с подменённым раннером, пишущим отчёт пульта): прежняя версия изменённого теста зелёная — нет находки; красная — находка; перемешанная — «нестабильна»; находка прежнего вида по тому же идентификатору — одна строка; правка только файла `test_support` — полный прогон прежних версий; удалённый и переименованный файл, запись `T`; компонент без `tests` — C только из `test_support`; C пуст — третьей выписки нет; замена — каждая из трёх находок требования 3 и снятие «исчез»; замена не снимает пропуск; строгий режим — находка на правку файла, снятие только мандатом на путь (мандат по идентификатору и префикс `путь::имя` — не снимают), файл заменяемого теста без мандата — находка (замена снимает лишь «исчез» и «прежняя версия красная»), правка соседнего теста в файле замены без мандата — находка; явный и выведенный `layers`, оба отказа проверки записи; каждая подстрока исключения в добавленной строке и её отсутствие в удалённой строке и в файле `tests`; компонент без `paths`; доказательство на мерже — та же четвёрка проходит без прогона, смена утверждённой замены требует прогона, мандат на путь в отпечатке; маркер владельца — до третьей выписки; автогейт — правило с меткой доходит до условий пометок, отказ построения правила — прежний текст.
