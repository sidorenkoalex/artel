## Пути обхода гейтов

1. **Сбой `git diff` — тихий пропуск (fail-open).** `diff_name_status`
   возвращает `None` при отказе git (`orchestrator/gitcmd.py:483-484`);
   SPEC (SPEC.md:86-87) объявляет отказом подготовки только «сбой
   выписки или прогона». Буквальное исполнение `diff_name_status(...) or
   []` даёт пустой C (нет прежних версий), ноль находок строгого режима;
   то же для `git diff -M -U0` исключений в коде (SPEC.md:130) — ноль
   находок «исключение в коде». Гейт пройден без проверки. SPEC должен
   назвать сбой обоих диффов `_Prepare`.
2. **Граница автогейта без признака канарейки.** SPEC.md:176-178 и AC-27
   (SPEC.md:302-307): отказ снимается, «если профиль задачи в границе
   гейта исходов». Ядро гейта исходов канареечную задачу пропускает
   (`outcome_integrity.py:539-540`, `:616-617`), а в `fsm_autogate.py`
   признака канарейки нет вовсе. Исполнитель, буквально проверяющий
   `in_outcome_bounds(profile)`, снимет отказ автогейта у канареечной
   задачи, где гейт исходов не исполнялся, — тот самый случай, ради
   которого стоял запрет 19.10. SPEC должен назвать предикат (граница
   ядра `_bounds(t["is_canary"], target)` не `None`) и критерий на
   канарейку.
3. (ТЗ-определённое, к сведению) Новый файл `A` под маской `test_support`
   не попадает ни в строгий режим (только не-`A`), ни в исключения в коде
   (маски `tests`/`test_support` исключены) — `process.env.VITEST` в новом
   `setup`-файле поддержки не виден. Это прямо задано ТЗ п. 4–5, не
   отклонение SPEC; отмечено для Оператора.
