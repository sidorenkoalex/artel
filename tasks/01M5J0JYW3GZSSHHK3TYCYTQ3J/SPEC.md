# SPEC: G3б-2 — гейт неослабления по исходам: прежние версии тестов на коде ветки, строгий режим, исключения в коде, сверка заменяемых тестов; автогейт по правилу планки

## Контекст
Вторая часть G3б волны G по ADR-0026 («Решение» п. 6 — прежние версии
изменённых или удалённых файлов `tests`/`test_support` против кода ветки,
строгий режим, исключения в коде; п. 7 — прежняя версия заменяемого теста
на коде ветки обязана быть красной, не заявленный покрасневший тест —
находка). Сейчас гейт исходов (`orchestrator/advance_gates/outcome_integrity.py`,
ядро `_judge`:481) сравнивает только полный набор базы и головы: тест,
который правка теста «подогнала» под сломанный код, не виден; утверждённые
G3б-1 замены (`mandate.approved_replacements`, `mandate.py:623`) гейт не
читает; поля компонента `test_support` и `layers` (`targets.py:98`, `:101`)
принимает схема, но не читает гейт; автогейт приёмки при правиле планки не
по умолчанию отказывает всегда (`fsm_autogate.py:236`, решение Оператора
19.10 «до G3б»). Решения Оператора 21.10: в строгом режиме утверждённая
замена правку файла не покрывает; `layers` без поля — `python-ast` у
команды pytest, строгий режим у прочих.

**Граница задачи:** новое поведение — только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`)
истинно; у артели и у записи `test_profile` гейты, записи журнала, пакет
ревьювера и автогейт прежние побайтно (новые поля профиля — со значениями
по умолчанию, у артели гейт исходов не создаётся вовсе).

## Требования

1. **Поля профиля.** `Profile` (`orchestrator/project_profile.py:66`)
   получает `test_support: tuple = ()`, `layers: tuple = ()` и
   `paths: tuple = ()` — вне сравнения, как прочие поля компонента; строка
   записи `paths` — кортеж из одного элемента (как в `_regexes`);
   `_with_component_fields` их переносит. Действующие слои — новая
   `project_profile.layers_of(profile)`: явное поле `layers`; без поля —
   `("python-ast",)` у команды pytest (`acceptance.is_pytest_command`
   отложенным импортом, как в `plank_rule`) и `()` у прочих. `check` в
   `orchestrator/targets.py` (в `_check_component_rules`, признак pytest —
   `_is_pytest_command`) после прежней проверки вида значения отказывает
   элементу `layers`, отличному от `python-ast`, текстом
   «<место>: поле 'layers' — '<элемент>': допустим только python-ast», и
   `python-ast` у компонента с командой не pytest — текстом
   «<место>: поле 'layers' — python-ast у команды не pytest». Строгий
   режим — профиль в границе без `python-ast` в действующих слоях; при
   `python-ast` слой снимает строгий режим только для файлов `.py` внутри
   `test_support`, прочие файлы под масками `test_support` (данные,
   снимки) — в строгом режиме.

2. **Прежние версии на коде ветки.** В `_judge` после сравнения строится
   набор C: пути каждой записи `diff_name_status(база, голова)`, кроме `A`
   (у `R` — прежний путь), подходящие под маски `tests` или `test_support`
   компонента, плюс файлы всех заменяемых тестов компонента
   (`approved_replacements`; компонент идентификатора — компонент
   профиля). У компонента без `tests` тестовые файлы C — пути файлов всех
   записей полного отчёта базы, включая записи ошибок уровня файла; пути
   `test_support` и файлы замен входят в C по-прежнему. C пуст — шаг не
   исполняется (ни выписки, ни прогона, ни строки записи). Иначе третья
   выписка головы — прямо в `scratch/<ключ>` вызовом
   `worktree add --detach` (уборка — тем же `finally` в `_gate`), в
   `trees` под ключом, отличным от «база» и «голова ветки»; пути C
   восстанавливаются `git checkout <база> -- <пути>` (удалённый —
   восстановлен; новый путь переименования остаётся). Прогон — полный
   набор компонента (`components_full_suite`, `fresh=True`), если в C есть
   путь `test_support`, иначе только файлы `tests` из C (`_report_run` с
   пределом компонента). Судятся идентификаторы базы из `PASS_TO_PASS`,
   чей файл попал в прогон. Исход прежней версии — по правилу
   перепрогона: зелёный — `in_pass_to_pass`, всё прочее (красный,
   пропуск, `todo`, нет записи) — красный. Красный — два перепрогона
   файла на третьей выписке и на базе тем же `_rerun` (третья выписка —
   на месте стороны ветки) и классификация по правилу `_redness`:
   трижды красный — находка «прежняя версия красная на коде ветки»,
   вперемешку — «прежняя версия нестабильна на коде ветки»; история
   перепрогонов третьей выписки ведётся отдельно от истории базы и ветки;
   красная база — строка «нестабилен и на базе», как сейчас. Строка
   находки — прежней формы «<вид>: <идентификатор> — <исходы>», исходы
   начинаются с «прежняя версия: » и несут «; база: ». Находка этого
   требования по идентификатору, у которого уже есть находка прежнего
   вида, не добавляется (одна находка на идентификатор, старшая). Сбой
   выписки или прогона — отказ подготовки (`_Prepare`), не пропуск.

3. **Заменяемые тесты на деле.** Для каждого идентификатора
   `approved_replacements` компонента: нет в отчёте базы — находка
   «заменяемый тест не найден в отчёте базы»; на базе не из
   `PASS_TO_PASS`, а также красный хотя бы в одном перепрогоне базы —
   находка «заменяемый тест не зелёный на базе» (исходы обеих — с
   «база: »; для красного в перепрогоне — с исходами перепрогонов),
   строки «заменён по SPEC» в этом случае нет; прежняя версия зелёная
   хотя бы в одном прогоне третьей выписки — находка «замена не нужна:
   прежняя версия зелёная на коде ветки» (исходы — с «прежняя версия: »);
   трижды красная при зелёной базе — строка записи «заменён по SPEC:
   <идентификатор> → AC-<n>». Находки этого требования добавляются и при
   находке прежнего вида по тому же идентификатору. Утверждённая замена
   снимает только находки «исчез» и «прежняя версия красная на коде
   ветки» своего идентификатора: элемент покрытия —
   `замена:<идентификатор>→AC-<n>`, источник в строке записи —
   «замена SPEC → AC-<n>»; сначала проверяется мандат Оператора
   (`_covering_pair`), затем замена. «Сломан правкой», «нестабилен»,
   пропуск, `todo`, `fails` и находки этого требования замена не снимает.
   Не заявленный тест, красный на третьей выписке, снимает только мандат
   Оператора.

4. **Строгий режим.** У профиля в строгом режиме каждый существующий файл
   (запись `diff_name_status`, кроме `A`; у `R` — прежний путь) `tests`
   или `test_support` — находка вида «строгий режим — правка
   существующего файла», строка `строгий режим — правка существующего
   файла: <путь> — статус <статус>` (идентификатор находки — путь), в том
   числе файл заменяемого теста. Её снимает только мандат Оператора
   прежним маркером «Ослабление тестов разрешено:» с элементом, равным
   пути файла (новая функция покрытия пути: элемент прежнего маркера,
   равный пути); мандат по идентификатору и префикс `путь::имя` её не
   снимают; утверждённая замена её не снимает. В строгом режиме
   утверждённая замена снимает только находки «исчез» и «прежняя версия
   красная на коде ветки» своего теста.

5. **Мандат на путь вне `weakening_scope`.** В
   `orchestrator/advance_gates/mandate.py` (`_weakening_scope_refusal`) у
   профиля в границе `in_outcome_bounds` элемент прежнего маркера годен,
   если путь в `weakening_scope`, под масками `tests`/`test_support`
   компонента или в файлах компонента по `paths` (без `paths` — любой
   путь репозитория). Вне границы — прежнее правило и прежние тексты.

6. **Исключения в коде.** Строки, добавленные диффом
   `git diff -M -U0 база голова` (номер строки — по файлу головы;
   переименование без правки строк находки не даёт; двоичные файлы
   пропускаются) в файлы компонента вне масок `tests` и `test_support`
   (компонент файла — по полю `paths`; у единственного компонента без
   `paths` — любой файл репозитория), содержащие подстроку из
   `outcome_integrity.CODE_EXCEPTION_TOKENS = ("v8 ignore",
   "istanbul ignore", "c8 ignore", "eslint-disable",
   "import.meta.env.MODE", "process.env.VITEST", "NODE_ENV")`, — находка
   вида «исключение в коде», строка `исключение в коде: <путь> — строка
   <n>: <подстрока>` (идентификатор — путь; по находке на строку и
   подстроку); снимает её только мандат с элементом, равным пути (та же
   функция покрытия пути, что в требовании 4). Действует у всех профилей
   в границе. Удалённые строки и файлы под масками `tests`/`test_support`
   не проверяются.

7. **Находки и доказательство.** Новые виды (требования 2–4, 6) входят в
   `_KINDS`, `_RANK` (после прежних, номерами 4–10 в порядке
   перечисления: «прежняя версия красная на коде ветки», «прежняя версия
   нестабильна на коде ветки», «заменяемый тест не найден в отчёте
   базы», «заменяемый тест не зелёный на базе», «замена не нужна:
   прежняя версия зелёная на коде ветки», «строгий режим — правка
   существующего файла», «исключение в коде») и разбор `_finding_id`
   (идентификатор — тест или путь; граница идентификатора — первые « — »
   с исходами своего вида). Действие отказа — прежнее правило
   (`BROKEN_REFUSAL_ACTION`, только если все непокрытые находки —
   «сломан правкой», иначе `OUTCOME_REFUSAL_ACTION`); новых действий
   журнала нет. Подсказка `_mandate_hint` для новых видов называет мандат
   на путь. В отпечаток доказательства входят элементы
   `замена:<идентификатор>→AC-<n>` всех утверждённых замен компонента по
   последней записи, не только покрывших находки; `_proven` пересчитывает
   покрытие по виду находки (тест — `_covering_pair`, затем замена по
   текущей последней записи утверждения; путь — функция покрытия пути) —
   новое утверждение SPEC отменяет доказательство. Строка счёта записи
   пройденного гейта прежняя; прогоны третьей выписки — отдельной строкой
   «прежние версии: файлов <n>; прогонов <m>» только при непустом C.
   Порядок строк записи пройденного гейта: счёт, доказательство,
   «прежние версии: …», «нестабилен и на базе», «заменён по SPEC»,
   покрытые находки. Оба рубежа (`in_dev -> verifying` и окно мержа
   `merge_gate_escalates`) — одним ядром `_gate`; на мерже доказательство
   (`_proven`) проверяется до третьей выписки.

8. **Автогейт по правилу планки.** `_plank_rule_refusal`
   (`orchestrator/fsm_autogate.py:236`) отказывает только при отказе
   построения правила; при правиле не по умолчанию `_autogate_conditions`
   читает пометки планки по правилу (`_plank_sources(…, rule=rule)`,
   `scan_ac_content(…, rule=rule)`). Правило по умолчанию — прежние
   условия и тексты побайтно. Отказ при правиле не по умолчанию снимается
   только если профиль задачи в границе гейта исходов; иначе — прежний
   текст отказа.

9. **Тесты** детерминированы, без сети и без Node: учебный проект в git —
   компонент `junit-xml` с pytest и компонент `pult-vitest` с подменённым
   раннером, пишущим отчёт пульта. Существующие тесты `tests/` не
   правятся (опись — «Материалы»).

## Критерии приёмки

AC-1. У профиля компонента поля `test_support`, `layers`, `paths`
перенесены из записи `components:` (строка `paths` — кортеж из одного
элемента); у артели и `test_profile` — `()`. `layers_of` возвращает явное
поле `layers`; без поля — `("python-ast",)` у команды pytest и `()` у
команды не pytest.

AC-2. `targets.check` отказывает записи с элементом `layers`, отличным от
`python-ast`, текстом «<место>: поле 'layers' — '<элемент>': допустим
только python-ast» и записи с `python-ast` у компонента с командой не
pytest текстом «<место>: поле 'layers' — python-ast у команды не pytest»;
`python-ast` у команды pytest проходит.

AC-3. Изменённый существующий тестовый файл, прежняя версия которого
зелёная на коде ветки, находки требования 2 не даёт: гейт пройден, запись
пройденного гейта несёт строку «прежние версии: файлов <n>; прогонов <m>».

AC-4. Прежняя версия изменённого теста трижды красная на коде ветки при
зелёной базе — отказ `OUTCOME_REFUSAL_ACTION` со строкой
«прежняя версия красная на коде ветки: <идентификатор> — прежняя версия:
…; база: …».

AC-5. Прежняя версия красная и зелёная вперемешку на третьей выписке —
находка «прежняя версия нестабильна на коде ветки»; красная в перепрогоне
базы — не находка, а строка «нестабилен и на базе: <идентификатор>».

AC-6. Тест, у которого уже есть находка прежнего вида (например «стал
пропуском»), и прежняя версия которого красная на коде ветки, даёт в
детали отказа ровно одну строку со своим идентификатором — старшей
находки.

AC-7. Изменён только файл под маской `test_support` — на третьей выписке
гоняется полный набор компонента; изменены только файлы `tests` — только
эти файлы.

AC-8. Удалённый тестовый файл на третьей выписке восстановлен и его тесты
базы судятся; у переименованного — восстановлен прежний путь, новый путь
остаётся; запись со статусом `T` входит в C.

AC-9. У компонента без `tests` в C входят пути файлов всех записей
полного отчёта базы (включая записи ошибок уровня файла) и изменённые
пути `test_support`.

AC-10. C пуст — третьей выписки нет (ни `worktree add` третьей выписки,
ни прогона), строки «прежние версии: …» в записи нет.

AC-11. Сбой третьей выписки или её прогона — отказ
`PREPARE_REFUSAL_ACTION`, переход не совершён; выписка убрана.

AC-12. Маркер владельца `GATE_OWNER_MARKER` лежит в `scratch` до
`worktree add` третьей выписки; после гейта каталога третьей выписки нет.

AC-13. Утверждённый заменяемый тест, которого нет в отчёте базы, — находка
«заменяемый тест не найден в отчёте базы», отказ.

AC-14. Утверждённый заменяемый тест не из `PASS_TO_PASS` базы либо
красный хотя бы в одном перепрогоне базы — находка «заменяемый тест не
зелёный на базе», отказ; строки «заменён по SPEC» нет.

AC-15. Прежняя версия утверждённого заменяемого теста зелёная хотя бы в
одном прогоне третьей выписки — находка «замена не нужна: прежняя версия
зелёная на коде ветки», отказ.

AC-16. Прежняя версия утверждённого заменяемого теста трижды красная при
зелёной базе, тест исчез на ветке — гейт пройден (профиль с
`python-ast`): запись несёт «заменён по SPEC: <идентификатор> → AC-<n>» и
строки находок «исчез» и «прежняя версия красная на коде ветки» с
«— покрыто мандатом замена SPEC → AC-<n>».

AC-17. Утверждённая замена не снимает «стал пропуском» своего теста —
отказ; не заявленный тест, красный на третьей выписке, снимает только
мандат Оператора.

AC-18. Строгий режим: правка существующего файла `tests` — находка
«строгий режим — правка существующего файла: <путь> — статус <статус>»,
отказ; мандат «Ослабление тестов разрешено:» с элементом, равным пути,
её снимает; мандат по идентификатору и префикс `путь::имя` — не снимают.

AC-19. Строгий режим: файл утверждённого заменяемого теста без мандата на
путь файла — находка строгого режима, отказ (замена снимает лишь «исчез»
и «прежняя версия красная на коде ветки»); правка соседнего теста в файле
замены без мандата на путь файла — находка, отказ гейта.

AC-20. Профиль с `python-ast`: правка файла `.py` внутри `test_support`
находки строгого режима не даёт; правка файла не `.py` под маской
`test_support` — даёт.

AC-21. У профиля в границе мандат «Ослабление тестов разрешено:» на путь
файла кода компонента (вне `weakening_scope`), выданный командой `answer`,
принят и снимает находку «исключение в коде» этого файла; у профиля вне
границы — прежний отказ элементу.

AC-22. Каждая подстрока `CODE_EXCEPTION_TOKENS` в строке, добавленной в
файл кода компонента, — находка «исключение в коде: <путь> — строка <n>:
<подстрока>» с номером строки по файлу головы; подстрока в удалённой
строке, в файле под маской `tests` и переименование без правки строк
находки не дают.

AC-23. У единственного компонента без `paths` проверка исключений в коде
охватывает любой файл репозитория вне масок `tests`/`test_support`; у
компонента с `paths` — только файлы, подходящие под `paths`.

AC-24. Отказ только из находок «сломан правкой» — `BROKEN_REFUSAL_ACTION`;
при любой находке нового вида — `OUTCOME_REFUSAL_ACTION`; подсказка отказа
с находкой нового вида называет мандат на путь.

AC-25. Порядок строк записи пройденного гейта: счёт (прежней формы),
доказательство, «прежние версии: …», «нестабилен и на базе», «заменён по
SPEC», покрытые находки.

AC-26. На мерже запись пройденного гейта с той же четвёркой «голова;
база; ключ; мандат», где покрыты находки новых видов (путь и замена),
избавляет от прогона: ни выписки прежних версий, ни полного набора;
смена утверждённой замены (новая запись утверждения) после записи —
гейт исполняется прогоном; элемент мандата на путь входит в отпечаток.

AC-27. Автогейт: при правиле планки не по умолчанию у профиля в границе
гейта исходов отказа «до гейта неослабления по исходам (G3б) не
исполняется» нет, планка с меткой доходит до условий пометок, читаемых по
правилу (пометка manual в файле планки по правилу даёт отказ «критерии
manual — AC-<n>»); отказ построения правила — прежний текст
«автогейт: <причина>»; правило не по умолчанию у профиля вне границы —
прежний текст отказа.

AC-28. У артели и у записи `test_profile` гейт исходов не создаётся (ни
прогона, ни записи журнала), а итог автогейта — условия и текст — побайтно
равен эталону, снятому с кода пина.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны 5 (не считая общей `tests/`) —
порог 5; критериев приёмки 28 — порог 10; `budget_usd` 75 — порог $30.

**Обоснование монолита** (материал для решения Оператора; решение 21.10
уже разделило G3б на три задачи, это вторая):
- требования 2–4 и 6 — новые виды находок одного ядра `_judge`; все они
  проходят через общий разбор `_finding_id`, ранг `_RANK`, отпечаток и
  `_proven` (требование 7). Часть без требования 7 оставила бы покрытые
  находки нового вида неразбираемыми на мерже (`_proven` никогда не
  совпадёт — задача на мерже всегда гоняет прогон), часть без новых
  видов — требование 7 беспредметно;
- требование 1 (`layers_of`, поля профиля) потребляют только требования
  2 (`test_support`), 4 (строгий режим) и 6 (`paths`); отдельно не имеет
  потребителя;
- требование 5 (мандат на путь) — единственный способ снять находки
  строгого режима и исключений в коде; без него эти находки неснимаемы
  ничем, кроме возврата правки, — промежуточное состояние запирает
  законные правки;
- требование 8 (снятие запрета автогейта) по решению 19.10 допустимо
  только после полного гейта исходов (строгий режим и прежние версии);
  отдельной частью раньше — ослабление, позже — подзадача с полом $25 на
  правку в одну функцию.
Возможная нарезка для Оператора, если монолит не принят: (1)
`project_profile.py`+`targets.py`+`mandate.py` (поля, `layers_of`,
мандат на путь), (2) `outcome_integrity.py` (требования 2–4, 6, 7), (3)
`fsm_autogate.py` (требование 8), строго в этом порядке.
