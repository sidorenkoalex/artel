# SPEC: G3б-2 — гейт неослабления по исходам: прежние версии тестов на коде ветки, строгий режим, исключения в коде, сверка заменяемых тестов; автогейт по правилу планки

## Контекст
Это вторая часть G3б волны G по ADR-0026: «Решение», п. 6 — прежние версии
изменённых или удалённых файлов `tests`/`test_support` гоняются против кода
ветки, строгий режим, исключения в коде; п. 7 — прежняя версия заменяемого
теста на коде ветки обязана быть красной, а не заявленный покрасневший тест —
находка. Сейчас гейт исходов (`orchestrator/advance_gates/outcome_integrity.py`,
ядро `_judge`:481) сравнивает только полный набор базы и головы, и несколько
вещей он не видит:
- тест, который правка «подогнала» под сломанный код;
- замены, утверждённые G3б-1 (`mandate.approved_replacements`, `mandate.py:623`):
  гейт их не читает;
- поля компонента `test_support` и `layers` (`targets.py:98`, `:101`): схема их
  принимает, гейт не читает.

Кроме того, автогейт приёмки при правиле планки не по умолчанию отказывает
всегда (`fsm_autogate.py:236`, решение Оператора 19.10 «до G3б»).

Решения Оператора 21.10: в строгом режиме утверждённая замена правку файла
не покрывает; `layers` без поля — `python-ast` у команды pytest, строгий режим
у прочих. Ответ Оператора ANSWER-1 (22.10):
- у компонента без поля `tests` роль масок `tests` играет перечень файлов
  полного отчёта базы;
- сбой любого из двух диффов — отказ подготовки;
- граница снятия отказа автогейта — граница ядра `_bounds`, канарейка
  исключена.

Решения Оператора на гейте SPEC (22.10, круг 2, только ужесточающие) и
ответ ANSWER-2 (22.10):
- на третьей выписке удаляются все файлы `A`, не являющиеся файлами кода:
  под масками `tests`/`test_support`, а у компонента без `tests` — все
  файлы `A` под `weakening_scope`, есть у них записи в отчёте головы или
  нет;
- освобождение файла `A` от поиска подстрок исключений сужено: у
  компонента без `tests` тестовым считается только файл `A` под
  `weakening_scope` с записями в полном отчёте головы.

**Граница задачи:** новое поведение — только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`)
истинно. У артели и у записи `test_profile` гейты, записи журнала, пакет
ревьювера и автогейт остаются прежними побайтно: новые поля профиля
получают значения по умолчанию, у артели гейт исходов не создаётся вовсе.

## Требования

1. **Поля профиля.** `Profile` (`orchestrator/project_profile.py:66`)
   получает поля `test_support: tuple = ()`, `layers: tuple = ()` и
   `paths: tuple = ()`. Они вне сравнения, как прочие поля компонента;
   строка записи `paths` становится кортежем из одного элемента (как в
   `_regexes`); `_with_component_fields` их переносит.

   Действующие слои возвращает новая `project_profile.layers_of(profile)`:
   явное поле `layers`, а без поля — `("python-ast",)` у команды pytest
   (`acceptance.is_pytest_command` отложенным импортом, как в `plank_rule`)
   и `()` у прочих.

   `check` в `orchestrator/targets.py` (в `_check_component_rules`, признак
   pytest — `_is_pytest_command`) после прежней проверки вида значения
   отказывает:
   - элементу `layers`, отличному от `python-ast`, — текстом
     «<место>: поле 'layers' — '<элемент>': допустим только python-ast»;
   - `python-ast` у компонента с командой не pytest — текстом
     «<место>: поле 'layers' — python-ast у команды не pytest».

   Строгий режим — у профиля в границе без `python-ast` в действующих
   слоях: в нём все тестовые файлы компонента (требование 2) и все файлы
   под масками `test_support`. У профиля с `python-ast` в строгом режиме
   остаются только файлы не `.py` под масками `test_support` (данные,
   снимки); тестовые файлы компонента, файлы `.py` под масками
   `test_support` и файлы `.py` внутри `weakening_scope` профиля — вне
   строгого режима (ADR-0026, «Решение» п. 6; AC-17(б), AC-21).

2. **Тестовые файлы компонента.** Тестовый файл компонента — путь под
   масками `tests` компонента. У компонента без поля `tests` маски заменяет
   перечень путей файлов всех записей полного отчёта базы, включая записи
   ошибок уровня файла (ANSWER-1, вопрос 1). Это определение действует в
   требованиях 3, 5 и 7 (набор C, строгий режим, исключения в коде) везде,
   где сказано «маски `tests`».

   Только для поиска подстрок исключений (требование 7) у компонента без
   поля `tests` тестовым файлом, а не файлом кода, считается ещё файл ветки
   со статусом `A`, который подходит под маски `weakening_scope` профиля
   задачи (у артели — `tests/**/*.py`) и есть среди файлов записей полного
   отчёта головы (решение Оператора на гейте SPEC, круг 2, п. 2). Файлами
   кода, в которых подстроки ищутся, остаются:
   - файл `A` под `weakening_scope` без записей в отчёте головы (новый
     модуль кода, вспомогательный модуль);
   - существующий файл под `weakening_scope`, которого нет в отчёте базы.

   Удаление файлов `A` на третьей выписке этим определением не
   ограничивается — его правило в требовании 3 (ANSWER-2).

3. **Прежние версии на коде ветки.** В `_judge` после сравнения строится
   набор C. В него входят:
   - пути каждой записи `diff_name_status(база, голова)`, кроме `A` (у `R`
     берётся прежний путь), которые являются тестовыми файлами компонента
     (требование 2) или подходят под маски `test_support`;
   - файлы всех заменяемых тестов компонента (`approved_replacements`;
     компонент идентификатора — компонент профиля).

   Значит, у компонента без `tests` в C попадают только изменённые на ветке
   файлы, которые есть в отчёте базы; неизменённые файлы отчёта базы и
   новые файлы ветки в C не входят.

   Если C пуст, шаг не исполняется: нет ни выписки, ни прогона, ни строки
   записи.

   Иначе:
   - **Выписка.** Делается третья выписка головы — прямо в
     `scratch/<ключ>` вызовом `worktree add --detach`. Уборка — тем же
     `finally` в `_gate`. В `trees` она лежит под ключом, отличным от
     «база» и «голова ветки». Пути C восстанавливаются командой
     `git checkout <база> -- <пути>`: удалённый файл восстанавливается,
     новый путь переименования остаётся. На третьей выписке удаляются все
     файлы ветки со статусом `A`, которые не являются файлами кода: тесты и
     файлы поддержки — ровно как на базе, код — как в голове. Удаляются:
     - файлы `A` под масками `tests` и `test_support` компонента;
     - у компонента без поля `tests` — все файлы `A` под масками
       `weakening_scope` профиля, есть у них записи в отчёте головы или нет
       (`conftest.py`, вспомогательные модули — включительно; ANSWER-2).
       Ложная находка на новый модуль кода под `weakening_scope` снимается
       мандатом Оператора — принятая цена ужесточения (ANSWER-2).
   - **Прогон.** Если в C есть путь `test_support`, гоняется полный набор
     компонента (`components_full_suite`, `fresh=True`). Иначе гоняются
     только тестовые файлы из C (`_report_run` с пределом компонента).
   - **Что судится.** Идентификаторы базы из `PASS_TO_PASS`, чей файл
     попал в прогон. Исход прежней версии считается по правилу
     перепрогона: зелёный — `in_pass_to_pass`, всё прочее (красный,
     пропуск, `todo`, нет записи) — красный.
   - **Красный исход.** Файл перепрогоняется дважды на третьей выписке и
     на базе тем же `_rerun` (третья выписка — на месте стороны ветки) и
     классифицируется по правилу `_redness`. Трижды красный — находка
     «прежняя версия красная на коде ветки»; вперемешку — «прежняя версия
     нестабильна на коде ветки». История перепрогонов третьей выписки
     ведётся отдельно от истории базы и ветки. Красная база даёт строку
     «нестабилен и на базе», как сейчас.
   - **Строка находки** — прежней формы «<вид>: <идентификатор> —
     <исходы>»; исходы начинаются с «прежняя версия: » и несут «; база: ».
   - **Одна находка на идентификатор.** Если у идентификатора уже есть
     находка прежнего вида, находка этого требования не добавляется.

   Сбой выписки или прогона — отказ подготовки (`_Prepare`), а не пропуск.

4. **Заменяемые тесты на деле.** Для каждого идентификатора
   `approved_replacements` компонента:
   - нет в отчёте базы — находка «заменяемый тест не найден в отчёте базы»;
   - на базе не из `PASS_TO_PASS` или красный хотя бы в одном перепрогоне
     базы — находка «заменяемый тест не зелёный на базе». Исходы обеих
     находок — с «база: », у красного в перепрогоне — с исходами
     перепрогонов. Строки «заменён по SPEC» в этом случае нет;
   - прежняя версия зелёная хотя бы в одном прогоне третьей выписки —
     находка «замена не нужна: прежняя версия зелёная на коде ветки»
     (исходы — с «прежняя версия: »);
   - прежняя версия трижды красная при зелёной базе — строка записи
     «заменён по SPEC: <идентификатор> → AC-<n>».

   Находки этого требования добавляются, даже если у того же
   идентификатора есть находка прежнего вида.

   Утверждённая замена снимает со своего идентификатора только находки
   «исчез» и «прежняя версия красная на коде ветки». Элемент покрытия —
   `замена:<идентификатор>→AC-<n>`, источник в строке записи — «замена
   SPEC → AC-<n>». Сначала проверяется мандат Оператора (`_covering_pair`),
   затем замена. «Сломан правкой», «нестабилен», пропуск, `todo`, `fails` и
   находки этого требования замена не снимает. Не заявленный тест,
   красный на третьей выписке, снимает только мандат Оператора.

5. **Строгий режим.** У профиля в строгом режиме каждый существующий файл
   из `diff_name_status` (кроме `A`; у `R` — прежний путь), который
   является тестовым файлом компонента или лежит под масками
   `test_support`, даёт находку вида «строгий режим — правка существующего
   файла». Это касается и файла заменяемого теста. Строка находки:
   `строгий режим — правка существующего файла: <путь> — статус <статус>`;
   идентификатор находки — путь.

   Снимает её только мандат Оператора прежним маркером «Ослабление тестов
   разрешено:» с элементом, равным пути файла. Для этого вводится новая
   функция покрытия пути: элемент прежнего маркера, равный пути. Мандат по
   идентификатору и префикс `путь::имя` находку не снимают, утверждённая
   замена — тоже. В строгом режиме утверждённая замена снимает только
   находки «исчез» и «прежняя версия красная на коде ветки» своего теста.

6. **Мандат на путь вне `weakening_scope`.** В
   `orchestrator/advance_gates/mandate.py` (`_weakening_scope_refusal`) у
   профиля в границе `in_outcome_bounds` элемент прежнего маркера годен в
   любом из случаев:
   - путь в `weakening_scope`;
   - путь под масками `tests`/`test_support` компонента;
   - путь среди файлов компонента по `paths` (без `paths` — любой путь
     репозитория).

   Вне границы действуют прежнее правило и прежние тексты.

7. **Исключения в коде.** Проверяются строки, добавленные диффом
   `git diff -M -U0 база голова`:
   - номер строки — по файлу головы;
   - переименование без правки строк находки не даёт;
   - двоичные файлы пропускаются.

   Проверяются файлы компонента вне тестовых файлов компонента и вне масок
   `test_support`. Компонент файла определяется по полю `paths`; у
   единственного компонента без `paths` — любой файл репозитория.

   Строка, содержащая подстроку из `outcome_integrity.CODE_EXCEPTION_TOKENS
   = ("v8 ignore", "istanbul ignore", "c8 ignore", "eslint-disable",
   "import.meta.env.MODE", "process.env.VITEST", "NODE_ENV")`, даёт находку
   вида «исключение в коде»: строка `исключение в коде: <путь> — строка
   <n>: <подстрока>`, идентификатор — путь, по находке на строку и
   подстроку. Снимает её только мандат с элементом, равным пути (та же
   функция покрытия пути, что в требовании 5).

   Проверка действует у всех профилей в границе. Удалённые строки,
   тестовые файлы компонента (у компонента без `tests` — в том числе файлы
   `A` под масками `weakening_scope` с записями в отчёте головы,
   требование 2) и файлы под масками `test_support` не проверяются.

8. **Сбой диффа — отказ подготовки.** Если `diff_name_status(база,
   голова)` вернул `None` или `git diff -M -U0 база голова` не отработал,
   это отказ подготовки (`_Prepare`, действие `PREPARE_REFUSAL_ACTION`), а
   не пустой C и не ноль находок строгого режима или исключений в коде
   (ANSWER-1, вопрос 2).

9. **Находки и доказательство.** Новые виды (требования 3–5, 7) входят в
   `_KINDS`, `_RANK` и разбор `_finding_id`. В `_RANK` они идут после
   прежних, номерами 4–10 в таком порядке:
   1. «прежняя версия красная на коде ветки»;
   2. «прежняя версия нестабильна на коде ветки»;
   3. «заменяемый тест не найден в отчёте базы»;
   4. «заменяемый тест не зелёный на базе»;
   5. «замена не нужна: прежняя версия зелёная на коде ветки»;
   6. «строгий режим — правка существующего файла»;
   7. «исключение в коде».

   В `_finding_id` идентификатор — тест или путь; граница идентификатора —
   первые « — » с исходами своего вида.

   Действие отказа — по прежнему правилу: `BROKEN_REFUSAL_ACTION`, только
   если все непокрытые находки — «сломан правкой», иначе
   `OUTCOME_REFUSAL_ACTION`. Новых действий журнала нет. Подсказка
   `_mandate_hint` для новых видов называет мандат на путь.

   В отпечаток доказательства входят элементы
   `замена:<идентификатор>→AC-<n>` всех утверждённых замен компонента по
   последней записи, а не только покрывших находки. `_proven` пересчитывает
   покрытие по виду находки: у теста — `_covering_pair`, затем замена по
   текущей последней записи утверждения; у пути — функция покрытия пути.
   Доказательство отменяет смена состава или содержимого утверждённых
   замен компонента (отпечаток по элементам «замена:…»); повторное
   утверждение SPEC с тем же составом замен доказательство не отменяет.

   Строка счёта записи пройденного гейта остаётся прежней. Прогоны третьей
   выписки идут отдельной строкой «прежние версии: файлов <n>; прогонов
   <m>», и только при непустом C. Порядок строк записи пройденного гейта:
   1. счёт;
   2. доказательство;
   3. «прежние версии: …»;
   4. «нестабилен и на базе»;
   5. «заменён по SPEC»;
   6. покрытые находки.

   Оба рубежа (`in_dev -> verifying` и окно мержа `merge_gate_escalates`)
   идут через одно ядро `_gate`. На мерже доказательство (`_proven`)
   проверяется до третьей выписки.

10. **Автогейт по правилу планки.** `_plank_rule_refusal`
    (`orchestrator/fsm_autogate.py:236`) отказывает только при отказе
    построения правила. При правиле не по умолчанию `_autogate_conditions`
    читает пометки планки по правилу (`_plank_sources(…, rule=rule)`,
    `scan_ac_content(…, rule=rule)`). При правиле по умолчанию условия и
    тексты прежние побайтно.

    При правиле не по умолчанию отказ снимается только для задачи в
    границе гейта исходов — той же, что у ядра: `_bounds(t["is_canary"],
    t["target"])` (`outcome_integrity.py:536`) не `None`, то есть профиль в
    `in_outcome_bounds` и задача не канарейка. Иначе, в том числе у
    канарейки, остаётся прежний текст отказа (ANSWER-1, вопрос 3).

11. **Тесты** детерминированы, без сети и без Node. Учебный проект в
    git — компонент `junit-xml` с pytest и компонент `pult-vitest` с
    подменённым раннером, пишущим отчёт пульта. Существующие тесты `tests/`
    не правятся (опись — в «Материалах»).

## Критерии приёмки

AC-1. У профиля компонента поля `test_support`, `layers`, `paths`
перенесены из записи `components:` (строка `paths` — кортеж из одного
элемента); у артели и `test_profile` они равны `()`. `layers_of` возвращает
явное поле `layers`, а без поля — `("python-ast",)` у команды pytest и `()`
у команды не pytest.

AC-2. `targets.check` отказывает записи с элементом `layers`, отличным от
`python-ast`, текстом «<место>: поле 'layers' — '<элемент>': допустим
только python-ast». Записи с `python-ast` у компонента с командой не pytest
он отказывает текстом «<место>: поле 'layers' — python-ast у команды не
pytest». `python-ast` у команды pytest проходит.

AC-3. Изменённый существующий тестовый файл, прежняя версия которого
зелёная на коде ветки, находки требования 3 не даёт: гейт пройден, запись
пройденного гейта несёт строку «прежние версии: файлов <n>; прогонов <m>».

AC-4. Прежняя версия изменённого теста трижды красная на коде ветки при
зелёной базе — отказ `OUTCOME_REFUSAL_ACTION` со строкой «прежняя версия
красная на коде ветки: <идентификатор> — прежняя версия: …; база: …».

AC-5. Прежняя версия, красная и зелёная вперемешку на третьей выписке, даёт
находку «прежняя версия нестабильна на коде ветки». Красная в перепрогоне
базы — не находка, а строка «нестабилен и на базе: <идентификатор>».

AC-6. Не заменяемый тест с находкой прежнего вида (например «стал пропуском»), прежняя
версия которого красная на коде ветки, даёт в детали отказа ровно одну
строку со своим идентификатором — строку старшей находки.

AC-7. Если изменён только файл под маской `test_support`, на третьей
выписке гоняется полный набор компонента. Если изменены только файлы
`tests`, гоняются только эти файлы.

AC-8. Удалённый тестовый файл на третьей выписке восстановлен, и его тесты
базы судятся. У переименованного файла восстановлен прежний путь, новый
путь остаётся. Запись со статусом `T` входит в C.

AC-9. У компонента без поля `tests` в C попадают только изменённые на ветке
файлы (запись `diff_name_status`, кроме `A`; у `R` — прежний путь), которые
есть в отчёте базы, включая файл записи ошибки уровня файла:
- (а) ветка правит только код — третьей выписки нет;
- (б) ветка правит один существующий тестовый файл базы — на третьей
  выписке гоняется только он, а неизменённые файлы отчёта базы не
  гоняются;
- (в) ветка добавляет новый тестовый файл (`A`) — третьей выписки нет;
- (г) ветка правит файл, у которого в отчёте базы только запись ошибки
  уровня файла, — файл входит в C.

AC-10. Если C пуст, третьей выписки нет: ни `worktree add` третьей выписки,
ни прогона. Строки «прежние версии: …» в записи нет.

AC-11. Сбой третьей выписки или её прогона даёт отказ
`PREPARE_REFUSAL_ACTION`: переход не совершён, выписка убрана.

AC-12. Подменённый сбой `diff_name_status(база, голова)` (возврат `None`)
даёт отказ `PREPARE_REFUSAL_ACTION`, переход не совершён. Так же
подменённый сбой `git diff -M -U0 база голова` даёт отказ
`PREPARE_REFUSAL_ACTION`, а не ноль находок «исключение в коде».

AC-13. В момент вызова `worktree add` третьей выписки маркер владельца
`GATE_OWNER_MARKER` лежит в том же `scratch`, а путь третьей выписки —
внутри этого `scratch`. После гейта каталога третьей выписки нет.

AC-14. Утверждённый заменяемый тест, которого нет в отчёте базы, даёт
находку «заменяемый тест не найден в отчёте базы» и отказ.

AC-15. Утверждённый заменяемый тест не из `PASS_TO_PASS` базы либо красный
хотя бы в одном перепрогоне базы даёт находку «заменяемый тест не зелёный
на базе» и отказ; строки «заменён по SPEC» нет.

AC-16. Если прежняя версия утверждённого заменяемого теста зелёная хотя бы
в одном прогоне третьей выписки, это находка «замена не нужна: прежняя
версия зелёная на коде ветки» и отказ.

AC-17. Прежняя версия утверждённого заменяемого теста трижды красная при
зелёной базе, профиль с `python-ast`:
- (а) тест исчез на ветке — гейт пройден. Запись несёт «заменён по SPEC:
  <идентификатор> → AC-<n>» и строку находки «исчез» с «покрыто мандатом
  замена SPEC → AC-<n>». Строки «прежняя версия красная на коде ветки» по
  этому идентификатору нет: одна находка на идентификатор;
- (б) тест есть на ветке и зелёный (файл изменён) — гейт пройден. Запись
  несёт «заменён по SPEC: <идентификатор> → AC-<n>» и строку находки
  «прежняя версия красная на коде ветки» с «покрыто мандатом замена SPEC →
  AC-<n>».

AC-18. Утверждённая замена не снимает «стал пропуском» своего теста — это
отказ. Не заявленный тест, красный на третьей выписке, снимает только
мандат Оператора.

AC-19. Строгий режим: правка существующего файла `tests` даёт находку
«строгий режим — правка существующего файла: <путь> — статус <статус>» и
отказ. Мандат «Ослабление тестов разрешено:» с элементом, равным пути, её
снимает; мандат по идентификатору и префикс `путь::имя` — не снимают.
Удалённый файл `tests` (статус `D`) даёт ту же находку со статусом `D`;
переименованный (статус `R…`) — находку с прежним путём файла.

AC-20. Строгий режим: файл утверждённого заменяемого теста без мандата на
путь файла даёт находку строгого режима и отказ — замена снимает лишь
«исчез» и «прежняя версия красная на коде ветки». Правка соседнего теста в
файле замены без мандата на путь файла — тоже находка и отказ гейта.

AC-21. Профиль с `python-ast`: правка файла `.py` внутри `test_support`
находки строгого режима не даёт, правка существующего файла `tests` — тоже
не даёт, а правка файла не `.py` под маской `test_support` — даёт.

AC-22. У профиля в границе мандат «Ослабление тестов разрешено:» на путь
файла кода компонента (вне `weakening_scope`), выданный командой `answer`,
принят и снимает находку «исключение в коде» этого файла. У профиля вне
границы элементу — прежний отказ.

AC-23. Каждая подстрока `CODE_EXCEPTION_TOKENS` в строке, добавленной в
файл кода компонента, даёт находку «исключение в коде: <путь> — строка
<n>: <подстрока>» с номером строки по файлу головы. Подстрока в удалённой
строке, в файле под маской `tests`, в файле под маской `test_support`, в
двоичном файле и переименование без правки строк находки не дают.

AC-24. У единственного компонента без `paths` проверка исключений в коде
охватывает любой файл репозитория вне масок `tests`/`test_support`, у
компонента с `paths` — только файлы, подходящие под `paths`.

AC-25. Отказ только из находок «сломан правкой» — `BROKEN_REFUSAL_ACTION`;
при любой находке нового вида — `OUTCOME_REFUSAL_ACTION`. Подсказка отказа
с находкой нового вида называет мандат на путь.

AC-26. Порядок строк записи пройденного гейта: счёт (прежней формы),
доказательство, «прежние версии: …», «нестабилен и на базе», «заменён по
SPEC», покрытые находки.

AC-27. На мерже запись пройденного гейта с той же четвёркой «голова; база;
ключ; мандат», где покрыты находки новых видов (путь и замена), избавляет
от прогона: нет ни выписки прежних версий, ни полного набора. Если после
записи сменился состав или содержимое утверждённых замен компонента, гейт
исполняется прогоном; повторное утверждение SPEC с тем же составом замен
прогона не вызывает. Элемент мандата на путь входит в отпечаток.

AC-28. Автогейт: при правиле планки не по умолчанию у задачи в границе
гейта исходов (не канарейка) отказа «до гейта неослабления по исходам
(G3б) не исполняется» нет, и планка с меткой доходит до условий пометок,
читаемых по правилу: пометка manual в файле планки по правилу даёт отказ
«критерии manual — AC-<n>». Отказ построения правила — прежний текст
«автогейт: <причина>». Правило не по умолчанию у профиля вне границы —
прежний текст отказа.

AC-29. Автогейт: у канареечной задачи (`is_canary`) с профилем в
`in_outcome_bounds` и правилом планки не по умолчанию остаётся прежний
отказ «до гейта неослабления по исходам (G3б) не исполняется».

AC-30. У артели и у записи `test_profile` гейт исходов не создаётся: нет ни
прогона, ни записи журнала. Итог автогейта — условия и текст — побайтно
равен эталону, снятому с кода пина.

AC-31. Исключения в коде у компонента без поля `tests`:
- (а) новый модуль кода (статус `A`) под `weakening_scope`, покрывающим
  код, без записей в отчёте головы, с подстрокой исключения — находка
  «исключение в коде» и отказ;
- (б) существующий файл под `weakening_scope`, которого нет в отчёте базы,
  с добавленной строкой с подстрокой исключения — находка «исключение в
  коде» и отказ;
- (в) новый файл тестов (статус `A`) под `weakening_scope` с записями в
  отчёте головы — долгоживущий `tests/test_<id>_x.py` со строкой
  `monkeypatch.setenv("NODE_ENV", …)` — находки «исключение в коде» не
  даёт. Тот же текст в новом файле кода вне `weakening_scope` даёт находку
  «исключение в коде» и отказ.

AC-32. Ветка добавляет `conftest.py`, подменяющий сломанную функцию кода,
и правит существующий тест, проверяющий эту функцию. На третьей выписке
добавленного файла нет: прежняя версия изменённого теста красная, находка
«прежняя версия красная на коде ветки» и отказ. Так в каждом из случаев:
- (а) `conftest.py` под маской `test_support`;
- (б) `conftest.py` под масками `tests` компонента с полем `tests`;
- (в) `conftest.py` под `weakening_scope` компонента без поля `tests` (без
  `test_support`) — записей в отчёте головы у него нет.

AC-33. Исход прежней версии на третьей выписке «пропуск» и «нет записи»
(ошибка сборки файла) при зелёной базе считается красным: трижды такой
исход даёт находку «прежняя версия красная на коде ветки» и отказ.

AC-34. Находки требования 4 добавляются и при находке прежнего вида по
тому же идентификатору: утверждённый заменяемый тест исчез на ветке, а его
прежняя версия зелёная на третьей выписке — отказ, деталь несёт строку
«замена не нужна: прежняя версия зелёная на коде ветки» по этому
идентификатору (находку «исчез» замена при этом снимает).

## Оценка объёма и деление

Сработавшие сигналы:
- файлов зоны 5 (не считая общей `tests/`) — порог 5;
- критериев приёмки 34 — порог 10;
- `budget_usd` 75 — порог $30;
- зона задевает гейт неослабления.

**Обоснование монолита** — материал для решения Оператора. Решение 21.10
уже разделило G3б на три задачи, эта — вторая. Почему её не резать
дальше:
- **Требования 3–5, 7, 8 нельзя отделить от требования 9.** Это новые виды
  находок одного ядра `_judge`, и все они проходят через общий разбор
  `_finding_id`, ранг `_RANK`, отпечаток и `_proven` (требование 9). Часть
  без требования 9 оставила бы покрытые находки нового вида неразбираемыми
  на мерже: `_proven` никогда не совпадёт, и задача на мерже всегда гоняет
  прогон. Часть без новых видов делает требование 9 беспредметным.
- **Требования 1–2 самостоятельного потребителя не имеют.** Поля профиля,
  `layers_of` и тестовые файлы компонента потребляют только требования 3
  (`test_support`), 5 (строгий режим) и 7 (`paths`).
- **Требование 6 нельзя отложить.** Мандат на путь — единственный способ
  снять находки строгого режима и исключений в коде. Без него эти находки
  снимаются только возвратом правки, и промежуточное состояние запирает
  законные правки.
- **Требование 10 привязано к полному гейту.** Снятие запрета автогейта по
  решению 19.10 допустимо только после полного гейта исходов. Отдельной
  частью раньше — это ослабление, а позже — подзадача с полом $25 на
  правку одной функции.

Возможная нарезка для Оператора, если монолит не принят, — строго в этом
порядке:
1. `project_profile.py` + `targets.py` + `mandate.py` — поля, `layers_of`,
   мандат на путь;
2. `outcome_integrity.py` — требования 2–5, 7–9;
3. `fsm_autogate.py` — требование 10.

## Не входит

- Предупреждение `doctor` о файлах поддержки вне шаблона `test_support`
  (бэклог, решение Оператора 21.10).
- Задача на несколько компонентов, выбор компонентов задачи и гейта по
  диффу, несколько компонентов в одном гейте, снятие отказа записи из
  нескольких компонентов (G3б-3).
- Раздел SPEC «Заменяемые тесты», утверждение на гейте SPEC, сверка на
  гейте планки и `amend-tests` для файлов с меткой (G3б-1, смержена).
- Разбор синтаксиса JS в гейте неослабления (только текстовый поиск
  подстрок) и ветвление по окружению сверх перечня подстрок.
- Записи по тестам в кэше итога (бэклог).
- Поля записи компонента (`tests`, `test_support`, `layers`, `paths`) в
  ключе доказательства — решение Оператора 22.10 (Е-2 аудита, п. 8):
  строка бэклога, не эта задача.
- Прогон прежних версий неизменённых файлов отчёта базы у компонента без
  `tests` — буквальное «все файлы отчёта базы» Оператор отклонил (ANSWER-1,
  вопрос 1, вариант B).
- Изменение подписей вызывающих и одноимённых функций в модулях «только
  чтение» ТЗ — все они только читаются: `scripts/guard.py`,
  `orchestrator/acceptance.py`, `orchestrator/fsm.py`,
  `orchestrator/fsm_advance.py`, `orchestrator/fsm_merge_gate.py`,
  `orchestrator/review.py`, `orchestrator/advance_gates/two_sided.py`,
  `orchestrator/advance_gates/acceptance.py` (`in_outcome_bounds`),
  `orchestrator/advance_gates/tests_writing.py`,
  `orchestrator/reporters/outcome.py`, `orchestrator/gitcmd.py`,
  `orchestrator/workspace.py`, `orchestrator/store.py`,
  `orchestrator/liveness.py`, `orchestrator/repo_context.py`,
  `orchestrator/advance_gates/refusal_classes.py`,
  `orchestrator/checkpoint.py`, `orchestrator/dry_run.py`,
  `orchestrator/preflight.py`, `orchestrator/models.py`,
  `docs/adr/0026-project-components-and-outcome-gates.md` и др. Сигнатура
  `_bounds` не меняется: `fsm_autogate.py` её только зовёт. В изменяемых
  модулях меняется только следующее:
  - `orchestrator/advance_gates/mandate.py` — только
    `_weakening_scope_refusal`;
  - `orchestrator/project_profile.py` — только поля `Profile`,

  - `orchestrator/targets.py` — только проверка `layers` в

  - `orchestrator/fsm_autogate.py` — только `_plank_rule_refusal` и чтение

- Требование ТЗ «существующие тесты `tests/` без правок и зелёные»
