# SPEC: ADR-0021, этап 1 (б) — документы вне рабочей копии кода, доступ ролей, упразднение репозитория фиксации

## Контекст
После части (а) (01M3Z2DMQRD0BD7AARFVTCVVG8) документы задачи живут в
одной ссылке `refs/artifacts/<id>`, но на диск по-прежнему выкладываются
внутрь рабочей копии кода: `runner.role_cwd` →
`artifact_branch.materialize_task_dir` пишет весь `tasks/<id>/` в
`.artel/worktrees/<id>`, `acceptance.materialize_from_branch()` пишет
`acceptance_tests/` туда же. Ссылка внешнего проекта живёт в `config.ROOT`
и уходит в `origin` пульта, хотя ADR-0021 п.3 требует репозиторий самого
проекта. Репозиторий фиксации области проекта (ADR-0003 п.15) остаётся в
коде (`fixation._fix_external`, `_read_external`,
`projects.init_artifact_repo`), хотя фиксация документов уже читает голову
ссылки. Часть (б) выносит документы из рабочей копии кода, открывает их
ролям на запись и упраздняет репозиторий фиксации. Задача делится на две
подзадачи по решению Оператора (ANSWER-1, вопрос 2): см. «Деление».

## Требования
1. **Каталог документов.** Каталог документов задачи —
   `.artel/projects/<проект>/tasks/<id>/` для любого проекта, включая
   артель до этапа 2. Пульт выкладывает туда документы из
   `refs/artifacts/<id>` перед шагом роли. Правки роли в этом каталоге
   пульт забирает автокоммитом шага.
2. **Доступ роли.** Каталог роли — рабочая копия кода задачи. Каталог
   документов открыт роли на запись дополнительно: claude —
   `--add-dir <каталог документов>`; codex — `codex exec --add-dir
   <каталог документов>`. Поддержка проверена: claude 2.1.283 (`claude
   --help`: `--add-dir <directories...>`), codex-cli 0.157.1 (`codex exec
   --help`: `--add-dir <DIR>  Additional directories that should be
   writable alongside the primary workspace`, проверка Оператора 03.10,
   ANSWER-1). Закреплённый минимум codex (`min_cli_version: 0.155.1`,
   `models.yaml`) не проверен: developer в PLAN сверяет флаг со справкой
   версии 0.155.1 или с журналом изменений вендора. При расхождении
   developer эскалирует, а не обходит.
3. **`acceptance_tests/` только на время прогона.** `acceptance_tests/`
   выкладывается в рабочую копию кода только на время прогона и убирается
   после него — при зелёном исходе, красном исходе и сбое прогона.
   Прочие документы задачи в рабочей копии кода не лежат никогда.
4. **Защита — гейты, не права доступа.** Документы и закреплённые тесты
   от роли защищают гейты пульта: сверка с зафиксированным коммитом
   ссылки, перечень сумм, отметка автокоммита (ADR-0021 п.7).
   Существующие гейты не ослабляются.
5. **Упразднение репозитория фиксации.** Репозиторий фиксации области
   проекта упраздняется вместе с потребителями: `fixation._fix_external`,
   `_read_external`, родственные функции, `projects.init_artifact_repo`.
   Зафиксированное состояние документов — коммит ссылки.
6. **Ссылка внешнего проекта.** Ссылка документов внешнего проекта живёт в
   репозитории самого проекта и отправляется в его `origin` (ADR-0021
   п.3). Ссылка артели — в git главной копии пульта, как сейчас. Сверка с
   `origin` на гейте мержа и в `kill`, досылка и проверки `doctor` части
   (а) работают с репозиторием задачи, а не всегда с пультом.
7. **`docs/stack.md`.** Таблица паритета безопасности роли и описание
   провайдеров отражают каталог документов на запись у обоих провайдеров.
8. **Инварианты — приложением к PLAN.** 21 (часть: каталог роли плюс
   каталог документов задачи на запись) и 25 (часть: репозиторий фиксации
   упразднён, снять «грязную копию»). Приложение проверено
   `git apply --check`.
9. **Тесты в `tests/`** — постоянные сторожа с заявками «Ловит мутацию» на
   поведение требований 1–3 и 5–6 (см. критерии). Существующие тесты не
   ослабляются. Меняются только в объёме, прямо требуемом ADR-0021, и
   перечисляются в PLAN.

## Критерии приёмки
AC-1. Перед шагом роли содержимое `.artel/projects/<проект>/tasks/<id>/`
совпадает с деревом `tasks/<id>/` головы `refs/artifacts/<id>`, в том
числе для задачи артели.

AC-2. Вне прогона приёмочных тестов в рабочей копии кода задачи
(`.artel/worktrees/<id>`) нет каталога `tasks/<id>/` и ни одного файла
документов задачи — ни перед шагом роли, ни после него.

AC-3. Правка или новый файл роли в каталоге документов задачи после шага
попадает автокоммитом шага новым коммитом в `refs/artifacts/<id>`, потомком
прежней головы.

AC-4. Команда шага claude содержит `--add-dir <каталог документов задачи>`.
Команда шага codex содержит `exec --add-dir <каталог документов задачи>`,
а глобальные флаги остаются до подкоманды `exec`. Каталог роли (cwd) у
обоих провайдеров — рабочая копия кода задачи.

AC-5. Во время прогона приёмочных тестов `acceptance_tests/` лежит в
рабочей копии кода. После прогона его там нет — при зелёном исходе, при
красном исходе и при сбое прогона (исключении внутри прогона).

AC-6. Гейты лока `acceptance_tests/`, перечня сумм долгоживущих тестов и
сверки фиксации отказывают на правке роли в каталоге документов так же,
как отказывали на правке внутри рабочей копии кода.

AC-7. Заведение внешнего проекта и задачи внешнего проекта не создают
репозиторий фиксации области проекта. Переходы FSM не пишут в него и не
читают из него. Зафиксированное состояние документов на переходе — коммит
`refs/artifacts/<id>`.

AC-8. Для задачи внешнего проекта `refs/artifacts/<id>` создаётся в
репозитории проекта и после коммита отправляется в `origin` проекта; в
git пульта и в `origin` пульта такой ссылки нет. Для задачи артели
ссылка, как и раньше, живёт в git главной копии пульта и уходит в
`origin` пульта.

AC-9. Сверка ссылки с `origin` на гейте мержа и в `kill`, досылка на
`set_state` и проверки `doctor` части (а) для задачи внешнего проекта
читают репозиторий проекта и его `origin`. Расхождение там даёт тот же
именованный отказ или строку `doctor`, что для задачи артели.

AC-10. `docs/stack.md`: таблица паритета безопасности роли и описание
обоих провайдеров называют каталог документов задачи, открытый на запись
(`--add-dir` у claude и у `codex exec`).

AC-11. Приложение к PLAN с правками инвариантов 21 (часть) и 25 (часть,
без «грязной копии») проходит `git apply --check`, и
`tests/test_invariants.py` с этим приложением зелёный.

## Оценка объёма и деление
Сработавшие сигналы:
- число затрагиваемых модулей/файлов зоны ≥ 5: около 17 модулей
  `orchestrator/` (`runner`, `artifact_branch`, `acceptance`,
  `fsm_advance`, `advance_gates/acceptance`, `advance_gates/tests_writing`,
  `amend`, `pull`, `checkpoint`, `fixation`, `projects`, `snapshot`,
  `cleanup`, `fsm_merge_gate`, `providers/claude`, `providers/codex`,
  `doctor/*`), тесты и `docs/stack.md`;
- число критериев приёмки ≥ 10 (11);
- `budget_usd` ≥ $30;
- зона задевает механизмы, на которые опираются записи
  `docs/invariants.md` (21, 25).

Решение — нарезка на две части (ANSWER-1, вопрос 2, вариант A). Часть (а)
с сопоставимым охватом подошла к потолку гейта ёмкости (262144 байт), и
шаг developer дважды упёрся в таймаут; монолит части (б) не уложится.

- **(б1) — документы вне кода и доступ ролей** (требования 1–4 и 7,
  инвариант 21, AC-1…AC-6, AC-10, AC-11 в части инварианта 21). Первая:
  на её выкладку опирается (б2).
- **(б2) — упразднение репозитория фиксации и ссылка внешнего проекта**
  (требования 5–6, инвариант 25, AC-7…AC-9, AC-11 в части инварианта 25).
  После (б1).

Почему мерж (б1) не переносит живую (б2) на новое устройство (ADR-0021
п.13): выкладка документов собирается заново на каждом шаге из головы
ссылки, поэтому живая задача на следующем шаге просто получает документы
по новому адресу; хранилище документов (ссылка) не меняется. Почему (б2)
безопасна для живых задач: фиксация уже читает голову ссылки (часть (а)),
а внешних задач в базе 0. Обоснование принято Оператором (ANSWER-1).
Каждая часть мержима с зелёной планкой: (б1) не трогает репозиторий
фиксации и место ссылки, (б2) не трогает выкладку и команды провайдеров.

- Часть (в) этапа 1: команда `docs` и пакетный fetch, отмена CI на
  `artifact/**`, перевод `--artifact-branch` в `scripts/guard.py` на гейт,
  уборка веток `artifact/**`.
- Этап 2 ADR-0021 (клон и рабочие копии задач в области проекта,
  `config.ROOT` перестаёт меняться), этапы 3–4.
- Изоляция файловой системы ролей (строка бэклога).
- Перенос исторических снимков и живых задач.
- Подъём `min_cli_version` codex — отдельное решение Оператора
  (ANSWER-1, вопрос 1); `models.yaml` только для чтения.
- Правка `docs/adr/`, `docs/roadmap.md`, `docs/backlog.md`,
  `docs/operator-session.md`, `templates/`, `targets.yaml`, `models.yaml`,
  `roles.yaml`, `CLAUDE.md`, `.github/workflows/ci.yml`, `scripts/guard.py`,
  `scripts/ci_push_class.py` — по ТЗ только чтение.
- Прямая правка `docs/invariants.md`, `tests/test_invariants.py` и
  `skills/` — только приложением к PLAN (`skills/` — лишь абзацы о
  расположении документов задачи на диске, если они есть).
- Ожидаемая краснота: тесты, утверждающие выкладку `tasks/<id>/` в
  рабочую копию кода и репозиторий фиксации, меняются в объёме,
  требуемом ADR-0021; гейт неослабления тестов пропускает их только с
  мандатом Оператора `Ослабление тестов разрешено: …` в ANSWER-n.md, PLAN
  подзадачи перечисляет такие тесты.
- Полный зелёный `tests/`, зелёный CI ветки, неизменность защищённых путей
  и непревышение бюджета — их держит пульт.
