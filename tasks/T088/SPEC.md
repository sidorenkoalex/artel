# SPEC: Авто-ack алертов: непокрытые источники doctor

## Контекст
Механика авто-закрытия алертов при исчезновении условия (T035, T054)
покрывает `doctor.orphans.dir`, `doctor.orphans.branch`,
`doctor.orphans.worktree`, `doctor.backup_age`, `doctor.leases`,
`doctor.merge_lock` — каждый зовёт `_auto_ack_gone` после своей
проверки. Сверка кода `orchestrator/doctor.py` (все вызовы
`alerts.raise_alert` с `kind="incident"`) подтверждает ровно пять
непокрытых источников того же класса, буквально совпадающих со
списком ТЗ: `doctor.live_smoke` (`live_smoke`, строка 370),
`doctor.recovery.sha`/`doctor.recovery.dirty`/`doctor.recovery.fsck`
(`recovery_check`, строки 435/443/452) и `doctor.task_counter`
(`check_task_counters`, строка 773) — ни одного дополнительного
непокрытого incident-источника в `doctor.py` сверка не находит. Их
алерты после исчезновения условия остаются открытыми до ручного ack
Оператора — то же «окно ручной разгребли», которое T035/T054 уже
закрыли для остальных источников.

## Требования
1. `live_smoke` после своей проверки закрывает авто-ack'ом алерт
   `doctor.live_smoke`, если очередной прогон (`live_smoke`/
   `_live_smoke_run`) вернул `status="ok"`.
2. `recovery_check` после проверки sha для конкретного target закрывает
   авто-ack'ом алерт `doctor.recovery.sha` ИМЕННО этого target, если
   при текущем прогоне sha головы совпадает с зафиксированным (либо у
   target больше нет задачи с зафиксированным sha).
3. `recovery_check` после проверки чистоты для конкретного target
   закрывает авто-ack'ом алерт `doctor.recovery.dirty` этого target,
   если рабочая копия артефактного репо этого target при текущем
   прогоне больше не грязная (`is_clean` не возвращает `False`).
4. `recovery_check` после `git fsck` для конкретного target закрывает
   авто-ack'ом алерт `doctor.recovery.fsck` этого target, если fsck
   при текущем прогоне завершается без ошибки.
5. `check_task_counters` после своей проверки закрывает авто-ack'ом
   алерт `doctor.task_counter` конкретного target, если счётчик номеров
   этого target при текущем прогоне снова ≥ наблюдаемого max.
6. Для источников `doctor.recovery.sha`, `doctor.recovery.dirty`,
   `doctor.recovery.fsck`, `doctor.task_counter` (проверки, идущие по
   нескольким target одновременно) авто-ack алерта одного target не
   зависит от состояния другого target — закрывается только алерт
   target'а, чьё условие фактически исчезло.
7. Пока условие, представленное открытым алертом одного из пяти
   источников, остаётся в силе, авто-ack для него не происходит (тот
   же принцип, что требование 7 T035 и требование 3 T054).
8. Автоматический ack для этих пяти источников проставляет
   `ack_by=doctor` и `ack_resolution` тем же форматом, что и
   существующий механизм (`alerts.auto_ack`), без изменений самой
   функции.
9. Заведение алертов (`raise_alert`), дедупликация среди открытых
   алертов и ручной ack (в т.ч. `cmd_alert_ack`) для этих пяти
   источников при живом условии поведение не меняют.
10. Изменения ограничены `orchestrator/doctor.py` (и тестами при
    необходимости) и картой кодовой базы; условия, при которых
    `live_smoke`/`recovery_check`/`check_task_counters` заводят алерт
    (`raise_alert`), не меняются сверх добавления вызова авто-ack.

## Критерии приёмки

AC-1. Алерт `doctor.live_smoke` закрывается авто-ack'ом, когда
очередной прогон `live_smoke` возвращает `status="ok"`; пока прогон
продолжает проваливаться — авто-ack не проставляется.

AC-2. Алерт `doctor.recovery.sha` конкретного target закрывается
авто-ack'ом, когда sha головы этого target при повторном прогоне
`recovery_check` снова совпадает с зафиксированным (или зафиксированной
задачи для target больше нет); пока расхождение сохраняется — не
закрывается.

AC-3. Алерт `doctor.recovery.dirty` конкретного target закрывается
авто-ack'ом, когда рабочая копия артефактного репо этого target при
повторном прогоне снова чистая; пока она остаётся грязной — не
закрывается.

AC-4. Алерт `doctor.recovery.fsck` конкретного target закрывается
авто-ack'ом, когда `git fsck` этого target при повторном прогоне снова
завершается без ошибки; пока fsck продолжает проваливаться — не
закрывается.

AC-5. Алерт `doctor.task_counter` конкретного target закрывается
авто-ack'ом, когда счётчик номеров этого target при повторном прогоне
`check_task_counters` снова ≥ наблюдаемого max; пока счётчик отстаёт —
не закрывается.

AC-6. Открытый алерт одного target для источников `doctor.recovery.sha`
/ `doctor.recovery.dirty` / `doctor.recovery.fsck` / `doctor.task_counter`
не получает авто-ack по состоянию другого target — только по фактически
исчезнувшему условию своего.

AC-7. Ручной ack (`alerts.ack` / `cmd_alert_ack`) и дедупликация
открытых алертов (`raise_alert`) для этих пяти источников при живом
условии работают как до этой задачи — без изменений.

AC-8. Существующий набор тестов проходит зелёным без ослаблений,
удаления или смягчения проверок.

## Не входит
- Изменение `raise_alert`, дедупликации алертов или ручного ack —
  принцип целостности, трогать нельзя (как в T035/T054).
- Новые виды алертов и новые проверки doctor сверх добавления авто-ack
  к пяти перечисленным источникам.
- Изменение условий, при которых `live_smoke`/`recovery_check`/
  `check_task_counters` заводят алерт (`raise_alert`), сверх добавления
  вызова авто-ack.
- Информационные алерты порогов программы (`kind=threshold`, ADR-0010,
  T085) и алерты `kind=trigger` — прямая граница ТЗ, ack-обязательств у
  них нет.
- Источники incident, не относящиеся к `doctor.py` (например
  `spend.unknown_cost`, алерты `brief.py`/`github_adapter.py`/`fsm.py`)
  — вне рамки «источников doctor», заявленной ТЗ; сверка кода
  подтверждает, что внутри `doctor.py` иных непокрытых источников того
  же класса, кроме перечисленных в требованиях 1–5, нет.
