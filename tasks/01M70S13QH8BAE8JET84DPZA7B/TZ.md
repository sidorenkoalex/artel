# ТЗ: Раннер compose: шаблон файла окружения — только с защищённого пути, копия удаляется после прогона

# Раннер compose: шаблон файла окружения — только с защищённого пути, копия удаляется после прогона

## Факты

1. Раннер `compose` перед подъёмом стенда копирует шаблон окружения `compose_env_template` из дерева прогона — рабочей копии задачи или дерева мержа — в `compose_env_file` (`orchestrator/acceptance.py:1273-1303`, `_compose_prepare`; копия — `:1299`). Дерево задачи пишет роль: правка шаблона в ветке задачи (например, `PYTEST_ADDOPTS`, `PYTHONPATH`) меняет окружение прогона гейта.
2. Защищённые пути внешнего проекта — `repo_context.protected_paths(ctx)` (`orchestrator/repo_context.py:111-127`): поле `no_paths` записи и пути обвязки; формула сверки — `config.is_protected_path(путь, перечень)` (`orchestrator/config.py:836`). Правку защищённого пути гейт зон и гейт диффа на мерже отвергают. Правила «шаблон окружения обязан быть защищённым путём» нет. У записи проекта на `compose` шаблон лежит под маской вида `<каталог>/**`, которую формула сейчас не раскрывает (строка копилки `e895cc3e6`); маски начинает понимать задача эпика о масках `no_paths`. `doctor` наличие шаблона проверяет в `compose_record_checks` (`orchestrator/doctor/project_checks.py:748-796`; без `docker` — сразу отказ «Docker не найден», `:763`), защищённость — нигде.
3. Копия шаблона (`compose_env_file`) после прогона не удаляется. Копия делается до блока `try` прогона (вызов `_compose_prepare` — `acceptance.py:1375`, `try` прогона — `:1431`); `finally` (`:1464-1475`) убирает стенд, отчёт и каталог перекрытия, но не файл окружения; отказы между копией и `try` (сокет Docker, ошибка или таймаут `config`, не JSON в ответе, отказ по собранной конфигурации, нет сервиса) уходят без уборки.
4. Поле `compose_env_template` входит в ключ итога (`_COMPOSE_KEY_FIELDS`, `:842-843`).
5. ADR-0032 (черновик, п. 8, этап 8) заменяет шаблон окружения образцом проекта в точке ветвления и переопределениями машины; эта задача — защита до его исполнения.

## Требуется

1. Перед копией шаблона `_compose_prepare` проверяет, что `compose_env_template` — защищённый путь проекта: контекст — `repo_context.resolve(profile.project)` (поле `project` профиля заполняет `with_tools`, `orchestrator/project_profile.py:449-453`), проверка — `config.is_protected_path(template_rel, repo_context.protected_paths(ctx))`. Контекст не разрешился или имя проекта пустое — отказ запуска (закрыто по умолчанию). Шаблон не защищён — отказ запуска: текст называет поле, путь и способ исправить («внести путь в `no_paths` записи проекта»); `docker` не вызывается — тот же путь возврата, что у прочих отказов `_compose_prepare`.
2. `doctor`: в строке `project-compose-<имя>` (`compose_record_checks`) проверка защищённости шаблона идёт до поиска `docker` и даёт отказ при том же условии (имя проекта, компонент, путь) — и на машине без Docker.
3. На любом исходе после копии — зелёный и красный прогон, отказ подъёма служб, таймаут, любой отказ между копией и подъёмом стенда — файл `compose_env_file`, записанный копией этого прогона, удаляется. Отслеживаемый git файл до копии уже отвергнут (`:1278-1286`).
4. Прочие отказы, их порядок и тексты — без изменений.

## Критерии приёмки

Тесты — в новом долгоживущем файле задачи, по образцу песочницы `stand` файла ядра (`tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`): подменённый `docker`, настоящая запись проекта в песочнице.

- AC-1: шаблон вне `no_paths` — отказ запуска с именем поля и пути; в журнале вызовов подменённого `docker` нет ни одного вызова; файла окружения в дереве нет.
- AC-2: шаблон под `no_paths` (каталог-префикс и точный путь — отдельными случаями) — прогон идёт как раньше; запись проекта, которая не разрешается, — отказ запуска.
- AC-3: после зелёного прогона, после отказа подъёма служб (код `up` не 0), после таймаута `run`, после ненулевого кода `config` и после отказа по собранной конфигурации — файла `compose_env_file` в дереве нет (каждый исход случаем; ловит удаление только внутри `try`).
- AC-4: `doctor` проекта песочницы с шаблоном вне `no_paths` при отсутствии `docker` в `PATH` — строка `project-compose-<имя>` с отказом, называющим проект и путь; с шаблоном под `no_paths` — отказа о шаблоне нет.

Каждый тест — со строкой «Ловит мутацию: …».

Безопасность тестов: настоящий Docker не вызывается; настоящие записи проектов `.artel/targets.yaml` главной копии не читаются.

Существующие тесты: записи песочниц compose в них стоят с `no_paths: []` и после требований 1–2 краснеют. Правка разрешена только в записях песочниц — в `no_paths` добавляется путь шаблона окружения записи — в файлах `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`, `tests/test_01m6qrmyw4jh23mvwf3rdd7vgw_compose_tree_bounds.py`, `tests/test_01m6paj61dp2r2cmm71pj8w0kf_compose_record_line.py`, `tests/test_01m6paj61dp2r2cmm71pj8w0kf_role_env_compose.py`, `tests/test_doctor_compose_stands.py`, `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py`, по мандату Оператора (решение эпика); утверждения, методы и параметризация этих тестов не меняются. Другой красный тест — эскалация с именем теста.

Зоны: `orchestrator/acceptance.py`, `orchestrator/doctor/project_checks.py`, `tests/` (долгоживущие файлы задачи и шесть файлов записей песочниц выше).

Только чтение: `orchestrator/repo_context.py`, `orchestrator/config.py`, `orchestrator/project_profile.py`, `tests/sandbox.py`.

Не входит:
- образец окружения из точки ветвления и переопределения машины (ADR-0032 п. 8);
- защита `compose_file` (его собранная конфигурация проверяется правилами перекрытия);
- правка записей подключённых проектов: до мержа Оператор сверяет, что шаблон каждой записи на `compose` защищён (после задачи о масках `no_paths` — маской, иначе точным путём командой `target-set`);
- `.artel/targets.yaml` главной копии: настоящие записи, тесты его не читают и задача его не правит.

Приоритет 1.
