# SPEC: G2б-1 — долгоживущие файлы компонента по шаблону `long_lived`, строка группы и «Ловит мутацию:» у файлов с меткой `AC-<n>: `

## Контекст
Пятая задача волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`, «Решение» пп. 1, 5; «Решения Оператора», вопрос 1; «Порядок исполнения» — строка G2б), первая половина G2б. Опирается на G2а-1 (01M59KMPG2ZMK10V556VZVQD65: `project_profile.plank_rule`, `guard.PlankRule.is_labelled`, `guard.first_comment`) и G2а-2 (01M59Z0FW1699SJQ2FA5Y76CZ3: выкладка `plank_layout`).

Сегодня поле компонента `long_lived` (шаблон пути, `orchestrator/targets.py:90`) описано, но не исполняется: у единственного компонента — отказ «long_lived исполняется после G2б» (`orchestrator/targets.py:411-415`), форма шаблона проверяется лишь на `<id>` (`orchestrator/targets.py:493`, `_template_path_error`). Профиль несёт только пару `long_lived_dir`/`long_lived_name` (`orchestrator/project_profile.py:66`), правило имени `guard.is_long_lived_test_path` (`scripts/guard.py:3820`) не знает `<dir>`, подсказки зашивают хвост «<имя>.py»/«*.py», а строка группы, статика и трассируемость долгоживущих файлов разбираются только как Python — долгоживущий `.jsx` проходит гейты групп и статики без единой проверки.

**Граница задачи:** поведение меняется только у компонента записи `components:` с полем `long_lived` и у файлов, которые правило планки проекта признаёт файлами с меткой `AC-<n>: `; артель, записи `test_profile` (sled сегодня) и компоненты с парой `long_lived_dir`/`long_lived_name` — прежние пути, тексты и исходы побайтно.

## Требования

1. **Запись (`orchestrator/targets.py`).** Отказ «long_lived исполняется после G2б» (`_check_component_rules`) снят. Порядок проверок компонента: форма шаблона → «шаблон или пара» → наличие.
   - Форма проверяется только у вида `path_template` (поле `long_lived`); у `plank_layout` правила прежние. Каждое нарушение — `TargetsError` с текстом, называющим компонент и поле `long_lived`:
     - `<id>` и `<name>` — ровно по одному разу и только в последнем сегменте шаблона;
     - `<dir>` — не больше одного раза и только целым сегментом;
     - часть пути до первого заполнителя (корень) непуста;
     - у компонента, чьё правило планки — метка `AC-<n>: `, последний сегмент шаблона (после замены `<id>` образцом идентификатора задачи, `<name>` — строкой `a`) подходит под маски поля `tests` этого компонента; признак «правило — метка» в `targets.py` — `tests` непуст и команда не pytest, тем же правилом, что `acceptance.is_pytest_command`, но без импорта `orchestrator/acceptance.py` (цикл импорта).
   - Форма проверяется у компонента любой записи, включая запись из нескольких компонентов.
   - `long_lived` вместе с `long_lived_dir` или `long_lived_name` — прежний отказ «поле 'long_lived' вместе с '<поле>' — либо шаблон, либо пара полей».
   - У единственного компонента без шаблона и без обоих полей пары — отказ с текстом «нет ни шаблона long_lived, ни пары long_lived_dir/long_lived_name» вместо прежнего «нет поля 'long_lived_dir' — обязательно у единственного компонента записи». Компонент с одним полем пары из двух — прежний отказ «нет поля '<поле>' — обязательно у единственного компонента записи».
   - Тест G1а `tests/test_01m58fnwbv25ff26e7az9q9912_components.py::…::test_ac2_structure_and_entry_level_refusals` (подслучай «long_lived вместе с long_lived_dir», строка 374, шаблон `tests/test_<id>.py` без `<name>`) сверен и приведён к новому правилу: входной шаблон подслучая — годной формы, чтобы подслучай по-прежнему проверял отказ «либо шаблон, либо пара полей», а не отказ формы. Утверждения метода не меняются.
2. **Пара при чтении записи.** После проверки формы `targets.py` дополняет поля компонента с `long_lived` парой: `long_lived_dir` — корень шаблона (часть до сегмента с первым заполнителем, без завершающей `/`), `long_lived_name` — остаток (может начинаться с `<dir>/`). Пример: `frontend/src/<dir>/<name>.<id>.test.jsx` → `frontend/src` и `<dir>/<name>.<id>.test.jsx`; `backend/tests/test_<id>_<name>.py` → `backend/tests` и `test_<id>_<name>.py` (та же пара, что у sled сегодня). `repo_context.profile_of`, `Profile.from_values`, `project_profile._with_component_fields`, `project_profile.component_profiles` получают пару без правки; все места, читающие `long_lived_dir` как корень для git и диска (включая цель полного набора и выкладку `pytest-own` в `orchestrator/acceptance.py`), работают без правки.
3. **Правило имени (`scripts/guard.py`).** `is_long_lived_test_path` понимает `<dir>`: ноль или больше сегментов, каждый — `[A-Za-z0-9_-][A-Za-z0-9_.-]*` (сегмент, начинающийся с точки, в том числе каталог выкладки `.artel-plank`, не подходит); `<id>` — идентификатор задачи в нижнем регистре; `<name>` — прежнее `[a-z0-9_]+`. Одна функция `guard` строит пример пути для подсказок: `<id>` — идентификатор в нижнем регистре, `<name>` — переданная подстановка (`<имя>` либо `*`), `<dir>` → `<каталог>`; `Profile.long_lived_example` зовёт её. Долгоживущие файлы по шаблону с `<dir>` признаются своими в любом подкаталоге корня (решение Оператора 19.10 о паритете).
4. **Подсказки.** Каждый текст, называющий путь долгоживущего файла как префикс плюс «<имя>.py» или «*.py», берёт пример пути из требования 3: отказ `guard.long_lived_plank_errors`, подсказка обязательного артефакта test_author в `orchestrator/runner.py` (`{prefix}<имя>.py`), пункты 2а (`_long_lived_author_note`) и 5 (`_plank_run_point`) задания test_author, фраза задания developer (`_long_lived_developer_note`, с подстановкой `*`). Где в тексте есть `<имя>`, рядом — пояснение и для `<каталог>` (каталог модуля). У шаблона без `<dir>`, оканчивающегося на `<name>.py` (артель, sled), тексты побайтно прежние.
5. **Строка группы у файла с меткой `AC-<n>: `.** У файла, который правило планки проекта (`project_profile.plank_rule`, `PlankRule.is_labelled`) признаёт файлом с меткой по имени файла, строка группы читается из первого комментария (`guard.first_comment`): значения, правила и тексты отказов — прежние (`plank_file_group`), место в тексте — «в первом комментарии файла» вместо «в докстринге модуля»; в блоке `/* … */` перед «Группа:» допускается ведущая « * ». Применяется к тестовым файлам планки по правилу (гейт групп выхода из `tests_writing`, `preflight`) и к долгоживущим файлам (гейт долгоживущих, `preflight`). Файлы Python — прежний разбор (синтаксически битый `.py` у артели и sled — прежний исход, отказ даёт сухой сбор). Долгоживущий файл не с расширением `.py`, не признанный файлом с меткой, — отказ гейта долгоживущих «<файл>: не файл с меткой AC-<n>: и не Python — группа и статика не проверяемы».
6. **Статика долгоживущего файла с меткой.** Признаки — по тексту файла: любое вхождение литерала «имя каталога tasks с косой чертой после него» (как у Python-файлов) и идентификатора задачи без учёта регистра, включая комментарии; тексты признаков прежние, строка — номер строки файла. У каждого вызова теста, который распознаёт `plank_test_names` (за головой «(» или «.each(»), в комментарии непосредственно над вызовом — строка «Ловит мутацию: <непустой текст>», иначе отказ «<файл>:<строка>: тест «<имя>» долгоживущего файла без «Ловит мутацию: …» в комментарии над вызовом». «Комментарий над вызовом» — подряд идущие строки `//` либо один блок `/* … */`, кончающийся на строке прямо над головой вызова; пустая строка его обрывает. Признаки импорта, закрытых имён и git у файла с меткой не проверяются; правило импортов `long_lived_imports` — только Python. Файл планки с меткой и строкой «Группа: долгоживущий» — прежний отказ `long_lived_plank_errors` с примером пути из требования 3 и та же статика (как у Python в `_tests_writing_test_groups_gate`).
7. **Трассируемость долгоживущих по правилу.** Долгоживущие источники передаются парами (путь, текст) с правилом планки проекта: `fsm._tests_writing_ac_state` (оба пути), `fsm_advance.tests_writing`, `guard.acceptance_traceability_errors` (правило — и для `extra_sources`), `preflight` (`_traceability`). `it('AC-<n>: …')` долгоживущего файла с меткой покрывает AC-n; файл Python — прежний разбор.
8. **`amend-tests` для файлов с меткой — отказ до G3б.** Если в правке или на голове ветки есть файл планки или долгоживущий файл с меткой `AC-<n>: `, команда отказывает текстом «amend-tests для файлов планки с меткой AC-<n>: — до G3б не исполняется; правка планки — reject на гейте» до любых записей; файлы Python — прежний путь. В `orchestrator/amend.py` меняется только этот отказ.
9. **Гейт зон и сверка сумм** — через `Profile.is_long_lived` без правки `orchestrator/advance_gates/zones.py`, `orchestrator/checkpoint.py`, `orchestrator/advance_gates/acceptance.py`, `orchestrator/plank_run.py`: файл developer `frontend/src/<каталог>/<имя>.<id>.test.jsx` признаётся своим долгоживущим, перечень `long_lived.sha256.txt` пишется на выходе из `tests_writing` и сверяется на переходах и гейте мержа. Новая функция `guard`, вызванная в телах перехода, вызывается и в `orchestrator/preflight.py`; сторож предпроверки `tests/test_01m4p4zp37wv81410ytzhkqc8d_preflight.py::…::test_ac9_transition_guard_calls_equal_preflight_and_not_checked` не правится.
10. **Прежнее поведение у артели, записей `test_profile` и компонентов с парой полей.** Тексты и исходы ниже не меняются и закрепляются тестами до правки:
    - отказы `targets._check_component_rules` о паре полей: «поле 'long_lived' вместе с '<поле>' — либо шаблон, либо пара полей»; «нет поля '<поле>' — обязательно у единственного компонента записи» у компонента с одним полем пары (кроме заменяемого текста требования 1 для компонента без обоих полей);
    - `tests_writing.LONG_LIVED_ACTION` («переход отклонён: долгоживущие файлы tests/») с подсказкой `_long_lived_refusal` («test_author только добавляет файлы <пример> со строкой «Группа: долгоживущий»; верни прочее к базе ветки и повтори artel.py advance <id>»);
    - отказы `tests_writing._diff_entry_error`: переименование/копия, правка файла базы, удаление файла базы, изменение иного статуса, «путь вне <каталог>/ — кодовая ветка несёт только файлы <каталог>/», «файл без префикса задачи — имя <пример>»;
    - «<путь>: нет строки «Группа: долгоживущий» — в <каталог>/ кодовой ветки только долгоживущие файлы»;
    - отказ `guard.long_lived_plank_errors` («<файл>: «Группа: долгоживущий» в каталоге приёмочных тестов — перенеси файл в <префикс><имя>.py кодовой ветки»);
    - отказы `guard.plank_file_group` для Python: «нет строки группы в докстринге модуля — допиши «Группа: долгоживущий» или «Группа: разовый»», «неизвестное значение строки группы «<значение>» — допустимы только «долгоживущий» и «разовый»», «строк группы две с разными значениями — оставь одну»;
    - подсказка `runner.py` об обязательном артефакте test_author («acceptance_tests/ (файл в tasks/<id>/acceptance_tests/ либо долгоживущий файл <префикс><имя>.py)»);
    - пункт 2а задания test_author (`role_prompt._long_lived_author_note`), пункт 5 (`role_prompt._plank_run_point`, обе ветки — артель и внешний проект) и фраза задания developer (`role_prompt._long_lived_developer_note`, «Долгоживущие файлы задачи в <каталог>/ (<префикс>*.py) …»).
11. **Тесты** детерминированы, без сети и без Node: учебный проект с двумя компонентами (`junit-xml` на pytest с шаблоном `backend/tests/test_<id>_<name>.py` и `pult-vitest` с шаблоном `frontend/src/<dir>/<name>.<id>.test.jsx`) — форма записи, разбор шаблона, принадлежность путей, подсказки; места через `project_profile.decide` (чекпоинт test_author, гейт долгоживущих, перечень и его сверка, гейт зон, трассируемость, `preflight`, отказ `amend-tests` требования 8, `plank-run` долгоживущего файла) — на записи `components:` из одного компонента каждого вида.

Решения по умолчанию Оператора (ТЗ): `<dir>` допускает ноль сегментов (модуль в корне шаблона); признак «файл с меткой» у долгоживущего файла — по имени файла правилом планки проекта; файл `.py` — по правилам Python; отказ построения правила планки (компонент `pult-vitest` без `tests`) — прежние исходы G2а-1; автогейт и сводка приёмки читают долгоживущие файлы как сегодня.

## Критерии приёмки

AC-1. Запись `components:` с единственным компонентом `pult-vitest` и `long_lived: frontend/src/<dir>/<name>.<id>.test.jsx` (маски `tests` покрывают `*.test.jsx`) проходит `targets.check`/`targets.load`, а профиль компонента несёт пару `long_lived_dir` = `frontend/src`, `long_lived_name` = `<dir>/<name>.<id>.test.jsx`; компонент `junit-xml` с `long_lived: backend/tests/test_<id>_<name>.py` даёт пару `backend/tests` / `test_<id>_<name>.py`.

AC-2. Шаблон `long_lived` с `<name>` или `<id>` вне последнего сегмента, с повтором `<id>`/`<name>`, с `<dir>` внутри сегмента или дважды, с пустым корнем — отказ `TargetsError` с текстом, называющим компонент и поле `long_lived`; так же у компонента записи из нескольких компонентов.

AC-3. У компонента с правилом-меткой (`tests` непуст, команда не pytest) шаблон `long_lived`, чей последний сегмент не подходит под маски `tests` (например `.ts` при масках только `*.test.jsx`), — отказ записи; `long_lived` вместе с `long_lived_dir` — прежний отказ «либо шаблон, либо пара полей»; единственный компонент без шаблона и без пары — отказ с текстом «нет ни шаблона long_lived, ни пары long_lived_dir/long_lived_name»; прежнего текста «long_lived исполняется после G2б» нет ни в одном отказе.

AC-4. `guard.is_long_lived_test_path` для шаблона `frontend/src/<dir>/<name>.<id>.test.jsx` признаёт своими `frontend/src/components/button.<id>.test.jsx` и `frontend/src/button.<id>.test.jsx` (ноль сегментов `<dir>`), не признаёт `frontend/src/.artel-plank/<id>/button.<id>.test.jsx` и файл с идентификатором другой задачи; функция примера пути даёт `frontend/src/<каталог>/<имя>.<id>.test.jsx` при подстановке `<имя>` и `frontend/src/<каталог>/*.<id>.test.jsx` при `*`, а `Profile.long_lived_example` возвращает её результат.

AC-5. У компонента `pult-vitest` файл `frontend/src/components/button.<id>.test.jsx`, добавленный test_author, коммитится чекпоинтом шага, попадает в перечень `long_lived.sha256.txt` на выходе из `tests_writing`, сверяется на переходах и признаётся гейтом зон своим долгоживущим.

AC-6. `it('AC-1: …')` в долгоживущем файле с меткой покрывает критерий AC-1 в трассируемости выхода из `tests_writing` (`fsm._tests_writing_ac_state`, `fsm_advance.tests_writing`), в `guard.acceptance_traceability_errors` для `extra_sources` и в `preflight`.

AC-7. Долгоживущий `.jsx` с меткой без «// Группа: долгоживущий» в первом комментарии (или с иным значением строки группы) — отказ выхода из `tests_writing` и `preflight` с именем файла и текстом «в первом комментарии файла»; строка группы в блоке `/* … */` с ведущей « * » перед «Группа:» распознаётся.

AC-8. Долгоживущий `.jsx` с меткой, содержащий литерал «имя каталога tasks с косой чертой после него» (как у Python-файлов) или идентификатор задачи в любом регистре (включая комментарий), — отказ выхода из `tests_writing` и `preflight` с именем файла, номером строки и прежним текстом признака; вызов теста без строки «Ловит мутацию: <текст>» в комментарии непосредственно над вызовом (в том числе при пустой строке между комментарием и вызовом) — отказ «<файл>:<строка>: тест «<имя>» долгоживущего файла без «Ловит мутацию: …» в комментарии над вызовом»; тот же файл с комментарием «Ловит мутацию: …» над каждым вызовом и без признаков — проходит.

AC-9. Тестовый файл планки `.test.jsx` с меткой без строки группы в первом комментарии — отказ гейта групп выхода из `tests_writing` и `preflight` с текстом «в первом комментарии файла»; файл планки с меткой и строкой «Группа: долгоживущий» — отказ `long_lived_plank_errors` с примером пути из AC-4.

AC-10. Долгоживущий файл не `.py`, не признанный правилом планки файлом с меткой (например `.ts` при метке только для `*.test.jsx`), — отказ гейта долгоживущих «<файл>: не файл с меткой AC-<n>: и не Python — группа и статика не проверяемы».

AC-12. `plank-run` по пути долгоживущего файла `frontend/src/components/button.<id>.test.jsx` у компонента `pult-vitest` признаёт его долгоживущим файлом задачи (без запуска Node).

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (10 модулей + `tests/`); число критериев приёмки ≥ 10 (14); `budget_usd` ≥ $30 (стоит $60 — «Рамка: $60» ТЗ Оператора; калибровка по таблице дала бы верхний уровень ≥8 файлов зоны, $60 — ниже него).

**Обоснование монолита** (материал Оператору для решения на гейте SPEC):
- ТЗ уже является половиной строки G2б, нарезанной Оператором по ADR-0026 (G2б-1/G2б-2); остаток ТЗ связан одним переключателем — снятием отказа «long_lived исполняется после G2б» (требование 1).
- Без требований 5–7 снятие отказа открывает дыру, которую ТЗ называет фактом: долгоживущий `.jsx` проходит гейты групп и статики без единой проверки — промежуточное состояние ослабляет рубеж выхода из `tests_writing` (ADR-0002).
- Требования 3–7 без требований 1–2 недостижимы через `decide` (запись с `long_lived` по-прежнему отказывает) — сквозные критерии AC-5, AC-6, AC-12 в такой части непроверяемы, планка части не имела бы сквозного пути.
- Требование 9 (сторож предпроверки) связывает правки тел перехода (`fsm.py`, `fsm_advance.py`, `advance_gates/tests_writing.py`) с `preflight.py` в одном мерже: разнесение их по частям красит сторож на промежуточной части.
- Подсказки (требование 4) возможно было бы выделить отдельно, но они опираются на функцию примера пути требования 3 и без требования 1 недостижимы для шаблона с `<dir>`; отдельная часть дала бы лишь бессодержательную правку артели (тексты прежние побайтно).
