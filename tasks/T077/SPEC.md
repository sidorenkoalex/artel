# SPEC: Guard называет точную причину отказа

## Контекст
Текст отказа `scripts/guard.py` — исполнимая инструкция: роль обязана
мочь починить нарушение по одному тексту, не читая код guard. Фактура
T069 (29.08) показала, что это не так: сообщение о маркере красноты не
говорило, что объяснение обязано быть НА ТОЙ ЖЕ СТРОКЕ после
двоеточия — роль дважды заявила «сделано» с переносом строки
($1.23 холостого прогона). Тот же класс — неполное сообщение,
непонятное без чтения кода guard — повторился в T071 (заголовок
секции H3 вместо H2) и в T073. Задача — ревизия всех сообщений отказа
guard.py одним заходом по двум правилам: сообщение называет
нарушенное требование целиком (включая неочевидные детали формы) и
говорит, что сделать, а не только что не так.

## Требования
1. Для каждого правила guard, проверяющего структуру артефакта
   (`RULES`-секции и статусы, `schema_version`, обязательные
   frontmatter-поля, поле `task`, AC-разметка критериев приёмки,
   трассируемость AC↔тест, маркер красноты, секция «Проверено
   исполнением»), существующее сообщение отказа проверяется по
   фактуре «мог бы агент починить нарушение по одному этому тексту, не
   читая scripts/guard.py» и переписывается, если не проходит.
2. Переписанное сообщение называет нарушенное требование целиком,
   включая неочевидные детали формы правила (не просто «что-то не
   так»).
3. Переписанное сообщение говорит, что сделать для исправления, а не
   только что нарушено — по образцу сообщений секции «Проверено
   исполнением» (`scripts/guard.py::review_evidence_errors`, T072).
4. Существующие тесты, проверяющие текст сообщений guard.py
   (`tests/test_guard_schema.py` и другие), обновляются синхронно с
   переписанными сообщениями — не удаляются.
5. Для каждого переписанного сообщения добавляется или обновляется
   тест, проверяющий его точный текст — по образцу тестов секции
   «Проверено исполнением» из T072 (`tests/test_guard_schema.py::
   ReviewEvidenceSectionTest`, включая различение «пусто» и
   «отсутствует», как в `test_missing_and_empty_messages_differ`).

## Критерии приёмки
AC-1. Сообщение об отсутствии или пустом объяснении маркера красноты
называет требование «непустое объяснение на той же строке после
двоеточия» (`«Красен до реализации:»`/`«Зелёный с рождения:»`).

AC-2. Сообщение об отсутствующей обязательной секции, вызванное тем,
что заголовок присутствует на неверном уровне (не H2), называет
требуемый уровень заголовка (`## <имя секции>`, не H3 и не другой
уровень).

AC-3. Для каждого сообщения отказа, порождаемого правилом guard из
списка требования 1, текст называет нарушенное требование целиком,
включая неочевидные детали формы правила, а не только факт нарушения.

AC-4. Для каждого сообщения из AC-3 текст говорит, что нужно сделать
для исправления, а не только что не так.

AC-5. Существующие тесты текста сообщений guard.py обновлены синхронно
с переписанными сообщениями и не удалены.

AC-6. Полный тестовый набор проекта зелёный после изменений.

## Не входит
- Изменение самих правил guard (какие структуры принимаются или
  отклоняются) — только тексты сообщений об их нарушении.
- Логика FSM/оркестратора — вне объёма (`orchestrator/fsm.py` зовёт
  guard, но не меняется).
- Низкоуровневые сообщения об ошибках доступа к файлу (`не прочитан:
  {exc}` в `check()`/`acceptance_traceability_errors()`, `файл не
  найден` в `main()`) — это не нарушение правила guard, а сбой чтения
  файла; правила 1–4 к ним не применяются.
