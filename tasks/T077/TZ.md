# ТЗ: guard называет точную причину отказа — ревизия сообщений

## Контекст

Роадмап, P3-строка «Guard называет точную причину отказа». Фактура
T069 (29.08): сообщение «нет маркера „Красен до реализации:" или
„Зелёный с рождения:" в докстринге модуля» не говорит, что T064
требует непустое объяснение НА ТОЙ ЖЕ СТРОКЕ после двоеточия —
у роли маркер был, но с переносом строки, и она дважды заключила
«всё сделано» ($1.23 холостого прогона). Класс повторился трижды
за два дня (T069, T071 — заголовки секций H3 vs H2, T073).
Принцип: текст отказа guard — исполнимая инструкция; роль обязана
мочь починить нарушение, не читая код guard.

## Что нужно

Ревизия ВСЕХ пользовательских сообщений отказа scripts/guard.py
одним заходом, по двум правилам:

1. Сообщение называет нарушенное требование целиком, включая
   неочевидные детали формы: для маркера красноты — «непустое
   объяснение на той же строке после двоеточия»; для обязательных
   секций — «секция `## <имя>` уровнем H2 (`## `), не H3»; и так
   далее по каждому правилу guard.
2. Сообщение говорит, ЧТО сделать, а не только что не так
   (образец уже есть: сообщения evidence-контракта T072 «добавь
   секцию с перечислением…»).

Прогон по каждому правилу guard: перечислить существующие сообщения,
для каждого проверить исполнимость по фактуре «мог бы агент починить
по одному тексту», переписать не проходящие. Тесты на текст ключевых
сообщений — по образцу RejectionMessageNamesWhatIsMissingTest (T072).

## Границы

- Сами правила guard не меняются и не ослабляются — только тексты
  сообщений об их нарушении.
- Логика FSM/оркестратора — вне объёма.

## Критерии приёмки (ориентир для SPEC)

- Сообщение о маркере красноты называет требование same-line;
  сообщение об отсутствующей секции называет требуемый уровень
  заголовка.
- Для каждого правила guard сообщение содержит и причину, и действие.
- Полный тестовый набор зелёный; существующие тесты сообщений
  обновлены синхронно, не удалены.
