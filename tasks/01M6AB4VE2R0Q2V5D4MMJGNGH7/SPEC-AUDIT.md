  и AC-9 при этом требуют отдельный итог «MR не найден». Не задано,

  разработчик отличать его разбором текста `reason`.
- **Б-4.** Требование 6 и AC-17: «надзор `auto` … раз в N минут». Но

- **Б-5.** Возврат из эскалации (`answer`+`approve`) идёт через

## Пути обхода гейтов

- **Е-1.** Через `sha` MR по (а), когда MR открыт. Таблица (строка 4)
  требует только «(а) есть». Запасной `sha` MR («метод без коммита
  слияния») не привязан к статусу «влит». Голова открытого MR может
  оказаться предком `origin/<base>`: кто-то отправил ветку в `base`
  напрямую. Тогда итог — «влит этим MR», и `--confirm` закроет задачу
  как `merged_upstream` при открытом MR. ТЗ («иначе `sha` MR при методе
  без коммита слияния») подразумевает уже влитый MR. Привязки к статусу
  SPEC не задаёт.
- **Е-2.** Через «принятую голову» (Е2). Если путь `_approve_escalated`
  записывает голову сервера при снятии любой эскалации из
  `awaiting_human`, а не только эскалации по чужому коммиту, то любой
  `answer`+`approve` молча узаконит чужой коммит на сервере. SPEC
  ограничивает это словами «снимающих эскалацию по чужому коммиту», но
  признак класса эскалации не задан (Б-5), и AC-14 проверяет только
  положительный случай.
- Закрытие из надзора поймано тестом наблюдаемого состояния (AC-17,
  AC-20, Е1). Путь «вызвать функцию закрытия в обход CLI» тоже пойман.

## Вердикт

concerns. Ни одно расхождение SPEC не ломает: Оператор может решить их
на гейте, где нужно — строкой ANSWER-n.

1. **А-1.** Мандата на правку `HINT` нет в ANSWER-n. Гейт читает мандат
   только из ANSWER-n (`advance_gates/test_integrity.py:1061-1085`), а не

2. **Б-3.** «MR не найден» стоит ниже «отказа `forge`», хотя ответ 404 и
   есть отказ `forge` (`gitlab_adapter.py:204`, `:498`; SPEC, таблица
   требования 3, строки 1–2). Признак «не найден» не определён.
3. **Б-2.** `git cherry` не называет коммит базы. «Найденный в базе
   коммит» для sha закрытия по (б) не определён (SPEC, требование 4;
   AC-6).
4. **Е-1.** (а) через `sha` MR не привязан к статусу «влит», и
   `--confirm` может закрыть задачу при открытом MR (SPEC, требование 3,
   строка 4 таблицы).
5. **В-1.** AC-3 не ловит пересчёт точки ответвления: от чужих коммитов
   в базе `merge-base` не меняется, нужен сценарий после вливания.
6. **Б-4.** «Надзор `auto` раз в N минут» противоречит выходу `auto <id>`
   в `awaiting_human` (`auto.py:72-73`, `:546`). Не задано, жить ли
   циклу задачи в этом состоянии.
7. **Б-5 / Е-2.** Место и условие записи «принятой головы» в
   `fsm._approve_escalated` (`fsm.py:1705-1770`) не заданы, нет
   отрицательного AC «иная эскалация голову не принимает».
8. **Б-1.** `_docs_ref_unsynced` (`fsm_merge_gate.py:1351`; путь `done` —
   `:1512`, не `:1596`) печатает подсказку `approve`, которая в
   `awaiting_human` не работает. Нужно сказать, какой текст отказа
   выдаёт `--confirm`.
9. **В-2.** На `--confirm` не определено, убирается ли локальная ветка
   (`fsm_merge_gate.py:1376-1378`, `doctor/orphans.py:188-190`).
