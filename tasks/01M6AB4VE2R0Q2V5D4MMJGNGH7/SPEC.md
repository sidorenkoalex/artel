# SPEC: Б2.2 — команда `mr-sync`: сверка MR и нахождения правки в `base`, закрытие `done` по подтверждению Оператора

## Контекст
ADR-0029 (принят 26.10.2026), п. 2, 3, 10. После Б2.1б (01M5XZ9Z68XE2EKPDHYCAK25KF)
гейт мержа проекта с `merge_gate: target-human` открывает MR через `forge`
и переводит задачу в `awaiting_human` (`fsm_merge_gate._approve_for_project_people`,
`fsm_merge_gate.py:1576`); дальше задачу не двигает ничто: `approve`/`reject`/
`answer`/`amend-tests` в `awaiting_human` отказывают подсказкой
`fsm.AWAITING_HUMAN_HINT` «состояние ждёт людей проекта — mr-sync (шаг Б2.2)»
(`fsm.py:43`; подсказка состояния в `status` — `config.py:941-943`). Люди
проекта могут влить MR, закрыть его, перенести правку в другую ветку или влить
её сжатием вместе с чужой правкой — пульт обязан проверять фактическое
нахождение правки в `base`, а не только статус MR (решение Оператора
26.10.2026 в ADR-0029).

Сегодня `forge.MergeRequest` (`forge.py:67`) несёт только `iid, url, title,
state, draft, assignee, reason`; GitLab заполняет его в
`gitlab_adapter._merge_request` (`gitlab_adapter.py:497`), `mr_status` —
`gitlab_adapter.py:545`. `closed_as` знает только `divided` (`schema.py:244`).
Путь `done` гейта мержа — `fsm_merge_gate.py:1549-1552`:
`_finalize_done_state` (`:1337`, `state -> done` и снятие lease) →
`cleanup._commit_closing` (`cleanup.py:736`) → `snapshot.commit_closing`
(`snapshot.py:96`) → `retro.build_done` (`retro.py:551`, строка «Итог: done,
sha …») → `_cleanup_merged_task` (`:1367`, рабочая копия, локальная ветка и
ветка на сервере). Перед этим путь `done` сверяет ссылку документов задачи с
`origin` (`_docs_ref_unsynced`, `fsm_merge_gate.py:1596`). Подтверждённая
Оператором голова кода — `fsm_merge_gate._confirmed_code_head`
(`fsm_merge_gate.py:1649`). Зоны освобождаются по терминальному состоянию
(`zone_lock.py:111-116`), зависимости `merge_after` — по `done`. Последняя
своя отправка ветки — `gitcmd.last_sent_sha` (`gitcmd.py:233`). Поля доставки
читаются `targets.delivery_policy` (`targets.py:559`). `target-human` до Б2.3
неподдержан: в тестах — подменой `targets.SUPPORTED_MERGE_GATES`/
`SUPPORTED_FORGES`.

## Требования

1. **Поля `forge.MergeRequest`**: добавлены `target_branch`, `source_branch`,
   `sha` (голова MR), `merge_commit_sha`, `squash_commit_sha`, все `None` по
   умолчанию. `gitlab_adapter._merge_request` заполняет их из одноимённых
   полей ответа MR GitLab; поля нет в ответе — `None`. Прочие вызовы `forge`
   и белый список API (`ALLOWED_PAIRS`) не меняются.

2. **Подтверждённая голова и точка ответвления.**
   - Подтверждённая голова — `fsm_merge_gate._confirmed_code_head` задачи.
   - Точка ответвления — `git merge-base <подтверждённая голова>
     origin/<base>`, вычисленная на `approve` гейта мержа и записанная в БД
     задачи и в журнал при переходе в `awaiting_human`. Сверки требований 3–5
     берут записанное значение и не вычисляют его заново.
   - Дифф задачи — `git diff <точка ответвления>..<подтверждённая голова>`
     (две точки); `gitcmd.diff_base` для сверки не используется.

3. **Команда `mr-sync [<id>…]`** — новый модуль `orchestrator/mr_sync.py`,
   регистрация и справка в `orchestrator/artel.py`.
   - Без id — все задачи проектов с `merge_gate: target-human` в
     `awaiting_human`; задачи прочих проектов и прочих состояний не
     сверяются. С id — только названные; задача не найдена, не в
     `awaiting_human` или её проект не `target-human` — отказ с причиной по
     этой задаче.
   - Только чтение: `fetch` базовой ветки в клон пульта и
     `forge.mr_status`; команда ничего не отправляет, MR и ветку не меняет.
   - По каждой задаче печатает и пишет в журнал задачи:
     - статус MR: открыт / влит / закрыт без вливания / не найден /
       переведён на другую целевую ветку (`target_branch` MR не равен
       `base` записи проекта);
     - признаки нахождения правки в `origin/<base>` от подтверждённой головы:
       - (а) коммит вливания — `merge_commit_sha`, иначе
         `squash_commit_sha`, иначе `sha` MR (метод без коммита слияния) —
         предок головы `origin/<base>`;
       - (б) все коммиты задачи найдены в базе по содержимому
         (`git cherry origin/<base> <подтверждённая голова> <точка
         ответвления>`, без merge-коммитов);
       - (в) обратное наложение диффа задачи (требование 2) на
         `origin/<base>` проходит (`git apply --check -R --binary
         --whitespace=nowarn`), а прямое — нет; доказательство печатается
         по файлам;
     - итог — ровно один, первый подошедший сверху вниз по таблице:

       | Порядок | Условие | Итог |
       |---|---|---|
       | 1 | любой отказ `forge` или git | «неизвестно» с причиной (не зелёный, закрытия не допускает) |
       | 2 | MR не найден | «MR не найден» |
       | 3 | `target_branch` MR ≠ `base` | «MR переведён на другую ветку» |
       | 4 | (а) есть | «влит этим MR»; при провале (в) — с пометкой «после вливания файлы менялись» |
       | 5 | (а) нет, все коммиты по (б) — при любом статусе MR, в том числе «влит» | «в базе, влит иначе» (по (б)) |
       | 6 | (а) нет, (б) не полностью, (в) проходит — при любом статусе MR | «в базе, влит иначе» (только по (в)) |
       | 7 | часть коммитов найдена по (б), (в) не проходит | «в базе частично» |
       | 8 | ни одного признака — при любом статусе MR, в том числе «влит» | «нет в базе» |

   - Последний итог и время сверки сохраняются у задачи (БД,
     `schema.py`/`store.py`).

4. **Закрытие `mr-sync <id> --confirm`** — только для одной задачи (больше
   одного id или без id — отказ) и только при итоге «влит этим MR» или «в
   базе, влит иначе». Итог «в базе, влит иначе» только по признаку (в)
   (строка 6 таблицы) требует `--confirm --by-content`; без `--by-content` —
   отказ.
   - Итог пересчитывается в момент `--confirm` той же сверкой требования 3,
     а не берётся из прошлого запуска.
   - Перед переходом `--confirm` выполняет ту же сверку ссылки документов
     задачи с `origin`, что путь `done` гейта мержа (`_docs_ref_unsynced`,
     `fsm_merge_gate.py:1596`); несовпадение — отказ тем же исходом, задача
     остаётся в `awaiting_human`.
   - Успех: переход `awaiting_human → done`; `closed_as` =
     `merged_upstream` (итог по (а)) или `merged_upstream_other` (по (б)/(в));
     константы рядом с `schema.CLOSED_AS_DIVIDED`.
   - Коммит закрытия с RETRO в `refs/artifacts/<id>` — тем же путём, что
     `done` гейта мержа (`cleanup._commit_closing` → `snapshot.commit_closing`),
     с sha из доказательства: по (а) — коммит вливания; по (б) — найденный в
     базе коммит; по (в) — голова `origin/<base>` с пометкой «по содержимому»
     в RETRO.
   - Рабочая копия задачи убирается; ветка задачи на сервере и MR не
     трогаются (ни отправки в ветку, ни её удаления, ни вызовов `forge`,
     меняющих MR); lease снимается, как в `_finalize_done_state`; зоны
     освобождаются; задачи, зависящие от этой по `merge_after`, продолжают.
   - Прочие итоги — отказ `--confirm` с итогом и подсказкой (`kill`, новая
     задача, ожидание); задача остаётся в `awaiting_human`.

5. **Инциденты** (ADR-0029 п. 3):
   - MR задачи (ссылка `mr_iid` в БД) влит или закрыт до перехода в
     `awaiting_human` — проверка на `approve` гейта мержа
     (`fsm_merge_gate.py`) — эскалация задачи, MR не снимается с черновика и
     не назначается.
   - Чужой коммит: проверка действует только при открытом MR. MR открыт и
     голова ветки задачи на сервере не равна последней своей отправке
     (`gitcmd.last_sent_sha`) — эскалация без перезаписи ветки; проверяют
     `mr-sync` (в том числе без `--confirm`) и `approve` на `merge_gate`.
   - MR влит, либо ветка задачи удалена на сервере — не инцидент (вливание с
     перебазированием штатно переписывает ветку): сверка идёт по признакам
     (а)/(б)/(в) требования 3.
   - После `answer` + `approve`, снимающих эскалацию по чужому коммиту,
     голова ветки на сервере на момент этого `approve` записывается в журнал
     задачи как принятая; дальнейшие проверки чужого коммита сравнивают
     голову на сервере с последней принятой, а не с `last_sent_sha`.
   - Эскалация из `awaiting_human` возвращается в `awaiting_human` (механика
     Б2.1а).

6. **Опрос по расписанию — поле `policy.mr_sync_interval_min`** записи
   проекта (`targets.py`: только это поле и его проверка). Целое > 0; по
   умолчанию поля нет — опрос выключен, только ручной `mr-sync`; `0`,
   отрицательное, не целое — отказ загрузки с именем поля. При заданном
   значении надзор `auto` и надзор эпика (`orchestrator/auto.py`) раз в N
   минут вызывают `mr-sync` без `--confirm` для задач проекта в
   `awaiting_human` и пишут итог в журнал; при смене итога задачи
   относительно прошлой сверки — уведомление `watch` (`orchestrator/watch.py`).
   `--confirm` надзор не вызывает никогда.

7. **Показ**: `status` (`catalog.py`) и доска (`board.py`) у задачи в
   `awaiting_human` показывают последний итог `mr-sync` и время сверки.
   Подсказка состояния из Б2.1а — без «(шаг Б2.2)»: `fsm.AWAITING_HUMAN_HINT`
   (`fsm.py:43`) и подсказка `awaiting_human` в `config.py:941-943` (в
   `config.py` меняется только это место).

8. **Инварианты** — приложением PLAN к `tests/test_invariants.py`
   (защищённый путь):
   - `mr-sync` входит в обход команд (`commands()`,
     `tests/test_invariants.py:400`); песочница обхода несёт проект с
     `merge_gate: target-human` и задачей в `awaiting_human`, так что
     `mr-sync` в обходе сверяет непустой набор задач, а не отказывает
     пустым;
   - тест свойства строки 18 (`docs/invariants.md:48`): `mr-sync --confirm`
     — команда Оператора, `auto` и надзор эпика её не вызывают; тест
     наблюдает отсутствие закрытия — задача в `awaiting_human`, коммита
     закрытия в `refs/artifacts/<id>` нет, `closed_as` пуст, — а не
     аргументы вызова.

## Критерии приёмки
Поддержка `target-human` — подменой `targets.SUPPORTED_MERGE_GATES`/
`SUPPORTED_FORGES` в тесте; песочницы — вымышленные проекты с локальным
`origin`.

AC-1. Подменённый ответ GitLab на `GET /projects/:id/merge_requests/:n` с
`target_branch`, `source_branch`, `sha`, `merge_commit_sha`,
`squash_commit_sha` → одноимённые поля `forge.MergeRequest` из
`gitlab_adapter.mr_status` заполнены этими значениями; ответ без них — поля
`None`.

AC-2. `mr-sync` без id сверяет все задачи проектов с `target-human` в
`awaiting_human` и не сверяет задачи проекта с `operator` и задачи в других
состояниях; `mr-sync <id>` по задаче не в `awaiting_human` или проекта не
`target-human` — отказ с причиной.

AC-3. Переход в `awaiting_human` записывает в БД задачи и в журнал точку
ответвления — `git merge-base` подтверждённой головы
(`_confirmed_code_head`) и `origin/<base>` на момент `approve`; после того как
`origin/<base>` сдвинулся чужими коммитами, `mr-sync` берёт записанную точку
(журнал сверки называет её), и признак (в) считается по диффу
`<точка>..<подтверждённая голова>`.

AC-4. Итог «влит этим MR»: коммит вливания — предок `origin/<base>` →
признак (а) в выводе и журнале; `mr-sync <id> --confirm` переводит задачу в
`done`, `closed_as=merged_upstream`, коммит закрытия в `refs/artifacts/<id>`
несёт RETRO с sha коммита вливания, рабочая копия задачи убрана; шпион не
видит ни отправки в ветку задачи, ни удаления ветки на сервере, ни вызовов
`forge`, меняющих MR.

AC-5. Пометка «после вливания файлы менялись»: (а) есть, правка задачи затем
изменена в `base` (обратное наложение не проходит) → итог «влит этим MR» с
пометкой в выводе. Контрольный случай: (а) есть, правка в `base` не менялась
(обратное наложение проходит) → итог «влит этим MR» без пометки.

AC-6. MR закрыт, коммиты задачи перенесены в другую ветку и влиты в `base` →
признак (б), итог «в базе, влит иначе»; `--confirm` → `done`,
`closed_as=merged_upstream_other`, sha закрытия — найденный в базе коммит.

AC-7. MR закрыт, правка влита сжатием вместе с другой правкой → только
признак (в) с доказательством по файлам; `--confirm` без `--by-content` —
отказ, задача в `awaiting_human`; `--confirm --by-content` — `done`,
`closed_as=merged_upstream_other`, sha в RETRO — голова `origin/<base>`,
пометка «по содержимому».

AC-8. Итоги «в базе частично», «нет в базе», «MR не найден», «MR переведён на
другую ветку» (`target_branch` ≠ `base`) и отказ `forge` (итог «неизвестно» с
причиной) печатаются каждый своим текстом; `--confirm` при каждом из них
отказывает с итогом и подсказкой, задача в `awaiting_human`.

AC-9. Порядок итогов по таблице требования 3: MR не найден при правке в базе
по (б) → «MR не найден»; `target_branch` ≠ `base` при наличии (а) → «MR
переведён на другую ветку»; MR в статусе «влит», (а) нет, коммиты найдены по
(б) → «в базе, влит иначе»; MR в статусе «влит» без единого признака → «нет в
базе».

AC-10. Итог пересчитывается на `--confirm`: прошлый запуск `mr-sync` дал «влит
этим MR», затем ответ `forge` или `origin/<base>` изменён так, что итог —
«нет в базе», → `--confirm` отказывает, задача в `awaiting_human`.
`mr-sync --confirm` с двумя id или без id — отказ, ни одна задача не
закрыта.

AC-11. `--confirm` при итоге «влит этим MR», когда ссылка документов задачи
не совпадает с `origin` (та же сверка, что `_docs_ref_unsynced` пути `done`
гейта мержа), — отказ, задача в `awaiting_human`, коммита закрытия нет.

AC-12. После успешного `--confirm` зона задачи свободна (задача той же зоны
не ждёт её), а задача с `merge_after` на закрытую больше ею не держится.

AC-13. Инцидент «MR влит до `awaiting_human`»: у задачи на `merge_gate` есть
`mr_iid`, подменённый `forge.mr_status` отвечает «влит» (или «закрыт») →
`approve` эскалирует задачу, `undraft_mr`/`assign_mr` не званы, задача не в
`awaiting_human`.

AC-14. Инцидент «чужой коммит» при открытом MR: голова ветки на сервере не
равна `gitcmd.last_sent_sha` → `mr-sync` и `approve` на `merge_gate`
эскалируют задачу, шпион не видит отправки ветки; после `answer` + `approve`
задача снова в `awaiting_human`, журнал несёт голову сервера на момент этого
`approve` как принятую, и следующий `mr-sync` при той же голове не
эскалирует.

AC-15. Не инцидент: MR влит (ветка на сервере переписана вливанием с
перебазированием) либо ветка задачи удалена на сервере → `mr-sync` не
эскалирует, итог — по признакам (а)/(б)/(в), задача в `awaiting_human`.

AC-16. `mr-sync` без `--confirm` (без инцидента) ничего не меняет в БД, кроме
записей журнала и последнего итога со временем сверки: снимок строки задачи
до и после отличается только этими полями.

AC-17. `policy.mr_sync_interval_min`: без поля надзор `auto` и надзор эпика
`mr-sync` не вызывают; с полем — сверяют задачи проекта в `awaiting_human` и
не чаще раза в N минут (подменённые часы); ни при каком итоге, включая «влит
этим MR», надзор задачу не закрывает — задача в `awaiting_human`, коммита
закрытия в `refs/artifacts/<id>` нет, `closed_as` пуст; значения `0`,
отрицательное, не целое — отказ загрузки записи с именем поля.

AC-18. Опрос надзора сменил итог задачи (например «нет в базе» → «влит этим
MR») → `watch` показывает уведомление о смене; повторная сверка с тем же
итогом нового уведомления не даёт.

AC-19. `status` и доска у задачи в `awaiting_human` после `mr-sync`
показывают последний итог и время сверки; подсказка `awaiting_human` в
`status` и отказ `approve`/`reject`/`answer`/`amend-tests` не содержат
«(шаг Б2.2)» и называют `mr-sync`.

AC-20. PLAN несёт приложение к `tests/test_invariants.py`, которое
применяется к `base` (`git apply --check`), добавляет `mr-sync` в обход
команд с песочницей, где есть проект `target-human` с задачей в
`awaiting_human` (`mr-sync` в обходе сверяет её, а не отказывает пустым), и
тест «`auto` и надзор эпика не закрывают задачу `mr-sync --confirm`»,
наблюдающий состояние, коммит закрытия и `closed_as`.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (17 модулей `orchestrator/`);
критериев приёмки ≥ 10 (20); `budget_usd` ≥ $30 ($50 — рамка ТЗ); зона
задевает механизмы записей `docs/invariants.md` (переходы FSM, гейт мержа,
строка 18 — `auto` не проходит гейты, `tests/test_invariants.py`).

Материал для решения Оператора — **обоснование монолита**: ТЗ уже шаг Б2.2
плана ADR-0029 с рамкой $50. Сердце задачи — одна сверка (требования 2–3),
которой пользуются и ручной `mr-sync`, и `--confirm` (пересчёт в момент
подтверждения, AC-10), и опрос надзора, и проверка чужого коммита; закрытие
без сверки не мержимо (нечем решать), сверка без закрытия оставляет
`awaiting_human` тупиком, как сейчас. Возможный разрез по зонам, если
Оператор его предпочтёт: (1) поля `forge.MergeRequest`, запись точки
ответвления, `mr_sync.py` только на чтение, хранение и показ итога,
подсказка без «(шаг Б2.2)» (AC-1–AC-3, AC-5, AC-8, AC-9 без `--confirm`,
AC-16, AC-19) — первой, без зависимостей; (2) `--confirm` и путь `done`
(`fsm.py`, `cleanup.py`, `snapshot.py`, `retro.py`, `schema.py`), инциденты
на `approve` (`fsm_merge_gate.py`), опрос (`targets.py`, `auto.py`,
`watch.py`) и приложение к инвариантам (AC-4, AC-6, AC-7, AC-10–AC-15,
AC-17, AC-18, AC-20) — после части 1. Калибровка для >15 критериев — ~$85;
потолок держит рамка ТЗ $50.
