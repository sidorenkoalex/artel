# ТЗ: GitLab Б2.2: команда mr-sync — сверка MR и нахождения правки в base, закрытие done по подтверждению Оператора

# GitLab, шаг Б2.2: команда `mr-sync` — сверка MR и фактического нахождения правки в `base`, закрытие `done` по подтверждению Оператора

## Факты

ADR-0029 (принят 26.10.2026), п. 2 (инциденты), п. 3 (`mr-sync`), п. 10 (инвариант 18), «Пересматривает» (ADR-0003 п. 7, ADR-0028). Влиты: адаптер хостинга (А1.1, А1.2), ветка и отправка (Б1.1, Б1.2), состояние `awaiting_human` и MR на гейте мержа (Б2.1а, Б2.1б). Аналитик сверяет номера строк по коду после мержа Б2.1б.

1. Адаптер: `forge.mr_status(target, mr) -> forge.MergeRequest` (`orchestrator/forge.py`), реализация GitLab — `gitlab_adapter.mr_status` / `_merge_request` (`orchestrator/gitlab_adapter.py`). `forge.MergeRequest` сейчас несёт `iid, url, title, state, draft, assignee, reason` — нет `target_branch`, `merge_commit_sha`, `squash_commit_sha`, `sha` (голова MR), `source_branch`. Вызов `GET /projects/:id/merge_requests/:n` уже в `ALLOWED_PAIRS`; эти поля GitLab отдаёт в том же ответе.
2. Задача хранит `mr_iid`, `mr_url` (`schema.py`/`store.py`, Б2.1а); подтверждённая Оператором голова — sha `approve` на `merge_gate` (журнал задачи); последняя своя отправка ветки — журнал отправок `gitcmd` (Б1.1).
3. `closed_as` сейчас только `divided` у `killed` (`schema.CLOSED_AS_DIVIDED`); коммит закрытия с RETRO в `refs/artifacts/<id>` пишется путём `done` гейта мержа (`fsm_merge_gate.py`, после push).
4. В `awaiting_human` `approve`/`reject`/`answer` отказывают с подсказкой «mr-sync (шаг Б2.2)» (Б2.1а).
5. Инвариант 18 — `tests/test_invariants.py` (обход команд Оператора, которые `auto` не вызывает).

## Требуется

1. **Поля `forge.MergeRequest`**: `target_branch`, `source_branch`, `sha`, `merge_commit_sha`, `squash_commit_sha` (все `None` по умолчанию); GitLab заполняет их из ответа MR. Прочие вызовы и белый список API не меняются.
2. **Команда `mr-sync [<id>…]`** (без id — все задачи проектов с `target-human` в `awaiting_human`; с id — названные, иначе отказ с причиной). Только чтение: `fetch` базовой ветки в клон пульта и `forge.mr_status`; ничего не отправляет, MR и ветку не меняет. По каждой задаче печатает и пишет в журнал:
   - статус MR: открыт / влит / закрыт без вливания / не найден / переведён на другую целевую ветку (`target_branch != base`);
   - признаки нахождения правки в `origin/<base>` от подтверждённой головы:
     - (а) коммит вливания (`merge_commit_sha`, иначе `squash_commit_sha`, иначе `sha` MR при методе без коммита слияния) — предок головы `origin/<base>`;
     - (б) все коммиты задачи найдены в базе по содержимому (`git cherry origin/<base> <голова> <точка ответвления>`, без merge-коммитов);
     - (в) обратное наложение диффа задачи от точки ответвления на `origin/<base>` проходит (`git apply --check -R --binary --whitespace=nowarn`), а прямое — нет; доказательство печатается по файлам;
   - итог: «влит этим MR» (а); при (а) и провале (в) — пометка «после вливания файлы менялись»; «в базе, влит иначе» (MR закрыт или открыт, правка по (б) или (в)); «в базе частично»; «нет в базе»; «MR не найден»; «MR переведён на другую ветку». Любой отказ `forge` или git — итог «неизвестно» с причиной, не зелёный.
3. **Закрытие `mr-sync <id> --confirm`** — только для одной задачи и только при итоге «влит этим MR» или «в базе, влит иначе»; итог «в базе, влит иначе» лишь по признаку (в) требует `--confirm --by-content`. Итог пересчитывается в момент `--confirm`, а не берётся из прошлого запуска. Переход `awaiting_human → done`, `closed_as` = `merged_upstream` (а) или `merged_upstream_other` (б/в); коммит закрытия с RETRO в `refs/artifacts/<id>` — тем же путём, что `done` гейта мержа, с sha из доказательства (коммит вливания или найденный коммит; по (в) — голова `origin/<base>` с пометкой «по содержимому»). Рабочая копия задачи убирается; ветка на сервере и MR не трогаются; зоны освобождаются; зависимые по `merge_after` продолжают. Прочие итоги — отказ `--confirm` с итогом и подсказкой (`kill`, новая задача, ожидание).
4. **Инциденты** (ADR-0029 п. 3): MR влит или закрыт до перехода в `awaiting_human` (проверка на `approve` гейта мержа) — эскалация; голова ветки на сервере не совпадает с последней своей отправкой (чужой коммит) — эскалация без перезаписи; проверяют `mr-sync` и `approve` на `merge_gate`. Эскалация из `awaiting_human` возвращается в него же (Б2.1а).
5. **Опрос по расписанию — поле `policy.mr_sync_interval_min`** (целое > 0; по умолчанию поля нет — опрос выключен, только ручной `mr-sync`; иное значение — отказ загрузки с именем поля). При заданном значении надзор `auto` и надзор эпика раз в N минут вызывают `mr-sync` только на чтение для задач проекта в `awaiting_human`, пишут итог в журнал; при смене итога задачи — уведомление `watch`. `--confirm` надзор не вызывает никогда.
6. **Показ**: `status` и доска — последний итог `mr-sync` и время сверки у задачи в `awaiting_human`; подсказка состояния из Б2.1а — без «(шаг Б2.2)».
7. **Инварианты** (приложением PLAN к `tests/test_invariants.py`): `mr-sync` в обходе команд; строка 18 — `mr-sync --confirm` команда Оператора, `auto` её не вызывает.

Критерии приёмки (поддержка `target-human` — подменой `targets.SUPPORTED_MERGE_GATES`/`SUPPORTED_FORGES` в тесте; песочницы — вымышленные проекты с локальным `origin`):
- поля MR: подменённый ответ GitLab с `target_branch`, `merge_commit_sha`, `squash_commit_sha`, `sha` → поля `forge.MergeRequest` заполнены; без них — `None`;
- итог «влит этим MR»: коммит вливания — предок `origin/<base>` → (а), `--confirm` переводит в `done`, `closed_as=merged_upstream`, коммит закрытия с sha вливания, рабочая копия убрана, шпион отправок не видит отправки в ветку задачи, удаления ветки, вызовов изменения MR;
- пометка «после вливания файлы менялись»: (а) есть, правка задачи затем изменена в base → пометка в выводе;
- MR закрыт, коммиты задачи перенесены в другую ветку и влиты → (б), «в базе, влит иначе», `--confirm` → `merged_upstream_other`;
- MR закрыт, правка влита сжатием вместе с другой правкой → только (в): `--confirm` без `--by-content` — отказ; с `--by-content` — `done`, sha = голова base, пометка «по содержимому»;
- «в базе частично», «нет в базе», «MR не найден», «MR переведён на другую ветку», отказ `forge` → `--confirm` отказывает, состояние `awaiting_human`;
- инциденты: MR влит до `awaiting_human` → эскалация на `approve`; чужой коммит в голове ветки → эскалация, шпион не видит отправки; после `answer` + `approve` задача снова в `awaiting_human`;
- `mr-sync` без `--confirm` ничего не меняет в БД, кроме записи журнала и последнего итога (снимок задачи до и после);
- `policy.mr_sync_interval_min`: без поля надзор `mr-sync` не вызывает; с полем — вызывает только на чтение и не чаще N минут (подменённые часы); шпион не видит `--confirm` от надзора ни при каком итоге; `0`, отрицательное, не целое — отказ загрузки;
- проекты с `operator` и артель: поведение и существующие тесты прежние.
