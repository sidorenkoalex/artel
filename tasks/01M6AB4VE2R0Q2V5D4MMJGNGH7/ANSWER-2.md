# ANSWER-2: ответ Оператора

## Ответы

Ответ сессии при Операторе (права волны G) на эскалацию разработчика Б2.2, 01.11.2026.

1. **Вопрос 1 — вариант (а)**, по мандату Оператора 26.10 на тесты, которые меняет ADR-0029 (п. 3 «Инциденты» требует чтения статуса MR на `approve`). В `test_ac15_gate_with_link_talks_to_mr_only_by_undraft_and_assign`: разрешённое множество — `{"undraft_mr", "assign_mr", "mr_status"}`; подделка `mr_status` отвечает открытым невлитым MR; добавить `len(stand.fake.named("mr_status")) <= 1`; из строки документации теста убрать `mr_status` из «ловимых мутаций». Остальные проверки теста (состояние `awaiting_human`, запрет иных вызовов MR через `MR_CALLS`) не менять.

Ослабление тестов разрешено: tests/test_01m5xz9z68xe2ekpdhycak25kf_mr_delivery.py::test_ac15_gate_with_link_talks_to_mr_only_by_undraft_and_assign

2. **Вопрос 2 — вариант (б), не дефолт:** отказ `forge.mr_status` на `approve` гейта мержа задачи с `mr_iid` — отказ `approve` с причиной, задача остаётся на гейте (проверка инцидента не пропускается при сбое). Нужен тест: подделка `mr_status` с отказом → `approve` отказывает, состояние `merge_gate`, шпион не видит `undraft_mr`/`assign_mr`.
3. **Вопрос 3 — вариант (б):** уведомлять `watch` и о первом итоге сверки задачи (иначе вливание MR до первой сверки остаётся без уведомления); дальше — только при смене итога.

Независимая проверка: проверяющий сессии при Операторе 01.11 — «не ослабляет»: `MR_CALLS` по-прежнему ловит любой иной вызов MR (повторный `open_mr`, правка, закрытие, слияние); `mr_status` — только чтение (`GET` в `ALLOWED_PAIRS`); условия — правка строки документации и предел одного чтения.
