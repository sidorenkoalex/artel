# QUESTIONS: Несколько проектов: мьютекс и очередь мержа по проекту

## Вопросы

Сверка по требованию 2 ТЗ. Мерж ведёт scratch-worktree в клоне своего проекта (`fsm_merge_gate._perform_carpentry_merge`). Рабочее дерево `config.ROOT` он не трогает: пин двигает только `pin-update`, вне цикла (fsm_merge_gate.py:6-15). Коммит закрытия уходит в `refs/artifacts/<id>` репозитория задачи. `merge_after` проверяется до мьютекса (merge_after.py:410). Окно тишины уже разделено по проекту. Отдельного общего исключения для этого всего не нужно. Общее у мержей разных проектов — только БД пульта. Но «одна строка мьютекса на пульт» зашита в трёх местах вне зон ТЗ (вопросы 1–3). ТЗ велит такие находки эскалировать до SPEC.

1. **Где разделить строку мьютекса по проекту? Сегодня одну строку на пульт держит `store.py`, а он по ТЗ только для чтения.** `store.set_merge_lock` (store.py:1249) начинает с `DELETE FROM merge_locks` без WHERE. Взятие окна задачей sled сотрёт строку живого держателя артели, и две задачи одного проекта смогут попасть в окно вместе. `store.merge_lock_row` (store.py:1235) отдаёт первую строку таблицы без порядка. Таблица `merge_locks` (schema.py:148) без ключа, несколько строк в ней допустимы и без смены схемы.
   - A) Добавить `orchestrator/store.py` в зоны. Добавить туда функции чтения, записи и снятия строки мьютекса по проекту. Прежние функции сохранить для читателей вне зон (`notes.py`, `doctor/leases.py`).
     - ломается: ничего. Прежние сигнатуры store остаются, у артели с одним проектом в таблице одна строка, как сейчас.
     - ослабляется: ничего. Взаимное исключение внутри проекта держит та же атомарная запись под `BEGIN IMMEDIATE` (merge_lock.py:66).
     - цена: +1 файл зоны (~30–50 строк), сигнал объёма «5 и более файлов зоны» вместе с вопросами 2–3.
     - чьё решение: Оператор (зоны ТЗ).
   - B) `store.py` не трогать. `merge_lock.py` пишет SQL к `merge_locks` сам, в обход `store.set_merge_lock`/`merge_lock_row`.
     - ломается: `store.set_merge_lock` остаётся живой ловушкой. Любой его будущий вызов сотрёт строки держателей всех проектов, а его докстринг (store.py:1242) будет описывать неверный инвариант.
     - ослабляется: правило «один адрес запросов к таблице» (store.py — слой БД пульта). Исключение будет держаться только в merge_lock.py.
     - цена: зона прежняя (3 файла + tests/), дублирование SQL.
     - чьё решение: Оператор.
   - C) Добавить колонку `target` в `merge_locks`/`merge_queue`: `orchestrator/schema.py` и `orchestrator/store.py` в зоны, миграция через `add_column`.
     - ломается: ничего, если миграция догоняет старые БД (schema.py:336-346, тот же приём).
     - ослабляется: ничего.
     - цена: +2 файла зоны, миграция и её тесты. Без колонки проект и так виден соединением с `tasks.target` по `task_id`.
     - чьё решение: Оператор.
   - дефолт: A — самая узкая правка без ловушки в слое БД. Колонка (C) не нужна: проект строки виден по её `task_id`.

2. **Окно тишины `notes.py` читает одну строку мьютекса, а `notes.py` по ТЗ только для чтения. Расширять ли зоны?** `notes._silence_window_reason` (notes.py:281) берёт `store.merge_lock_row` — одну произвольную строку. Если в таблице две строки (держатель sled и держатель артели) и первой придёт строка sled, функция её пропустит (notes.py:291-294) и держателя артели не увидит. Пока задача артели в `merge_gate`, окно держит второй триггер — состояние (config.py:509). Но после `_finalize_done_state` (fsm_merge_gate.py:1357) под мьютексом ещё идут `_commit_closing`, уборка, `_await_main_ci` (ждёт CI новой головы main артели) и `_rebuild_core_reference`. На этом отрезке окно держит только строка держателя. Тогда `note` запушит в main артели, пока мерж артели ждёт CI своей головы.
   - A) Добавить `orchestrator/notes.py` в зоны: окно тишины смотрит все строки мьютекса, а не одну. Требование: «держатель артели открывает окно при любом числе строк мьютекса».
     - ломается: ничего. С одной строкой поведение прежнее (тесты `tests/test_notes.py`, `tests/test_01m563947r26nzw2tjekm36qrd_note_window_project.py`).
     - ослабляется: ничего.
     - цена: +1 файл зоны, ~10 строк и тест.
     - чьё решение: Оператор (зоны ТЗ).
   - B) `notes.py` не трогать. Принять, что после `done` окно тишины может не увидеть держателя артели, пока держит и внешний проект.
     - ломается: на отрезке `done → _await_main_ci → справочник` возможен push заметки в main артели во время мержа артели.
     - ослабляется: окно тишины по держателю мьютекса (notes.py:281-294, SPEC 01M563947R26NZW2TJEKM36QRD) при двух и более держателях.
     - цена: 0 сейчас, отдельная задача потом.
     - чьё решение: Оператор (ослабление свойства).
   - C) `notes.py` не трогать, а прежнее `store.merge_lock_row` (если store в зонах, вопрос 1-A) возвращает строку держателя артели первой.
     - ломается: ничего видимого. Но окно тишины будет держаться на неявном порядке выдачи функции в другом модуле.
     - ослабляется: ничего, пока порядок не тронут.
     - цена: +0 файлов сверх вопроса 1-A, хрупкая связь.
     - чьё решение: Оператор.
   - дефолт: A — без него разделение мьютекса тихо ослабляет уже смерженное окно тишины, а ТЗ окно тишины в задачу не включает только как «уже сделанное».
