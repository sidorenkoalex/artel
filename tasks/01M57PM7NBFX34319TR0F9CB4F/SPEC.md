# SPEC: Несколько проектов: мьютекс и очередь мержа по проекту

## Контекст
Мьютекс мержа (`orchestrator/merge_lock.py`: `acquire`, `touch_heartbeat`,
`release`) и очередь мержа (`orchestrator/merge_queue.py`: `_head_task_id`,
`queue_wait_minutes`, `wait_for_window`) сейчас одни на все проекты пульта.
Поэтому мерж задачи внешнего проекта (sled) ждёт мержа задачи артели, и
наоборот. Гейт мержа внешнего проекта ждёт CI своей ветки до 3600 с и всё
это время держит мьютекс, задерживая мержи артели. Мержи разных проектов идут
в разные репозитории и разные клоны.

Сверка по требованию 2 ТЗ (батч QUESTIONS, ответ ANSWER-1). Мерж ведёт
scratch-worktree в клоне своего проекта, рабочее дерево главной копии артели
он не трогает. Пин двигает только `pin-update` вне цикла мержа. Коммит
закрытия уходит в `refs/artifacts/<id>` репозитория задачи. `merge_after`
проверяется до мьютекса. Окно тишины уже разделено по проекту (SPEC
01M563947R26NZW2TJEKM36QRD). Общего исключения между проектами из этого
ничего не требует, общий ресурс — только БД пульта. Вывод «одна строка
мьютекса на пульт» зашит в трёх местах:
- `store.set_merge_lock` (`orchestrator/store.py:1249`) стирает всю таблицу
  `merge_locks` (`DELETE` без `WHERE`);
- `store.merge_lock_row` (`orchestrator/store.py:1235`) отдаёт первую строку
  таблицы без порядка;
- `merge_lock.touch_heartbeat` (`orchestrator/merge_lock.py:95`) продлевает
  «единственную» строку.

Строку мьютекса читают также окно тишины `notes._silence_window_reason`
(`orchestrator/notes.py:281`) и `doctor check_merge_lock`. Оператор
расширил зоны на `store.py` и `notes.py` (ANSWER-1, ответы 1-A и 2-A), а
doctor вынес за рамки задачи (ответ 3-B).

## Требования

1. Мьютекс мержа разделён по проекту задачи (`target` задачи из БД пульта).
   Задача проекта P берёт мьютекс, если у P нет живого держателя другого
   процесса. Держатель другого проекта не даёт ей отказа, не перехватывается
   и не перезаписывается.
2. Внутри одного проекта правила мьютекса прежние. Второй процесс получает
   отказ с прежним текстом, если у проекта есть живой держатель. Мёртвый
   держатель того же проекта перехватывается с прежней записью журнала
   «мьютекс merge перехвачен». `release` снимает только строку своего
   процесса (session_id и pid).
3. Продление heartbeat держателя во время ожидания CI
   (`merge_lock.touch_heartbeat`, вызовы в `orchestrator/fsm_merge_gate.py`)
   продлевает строку держателя своего проекта. Строку держателя другого
   проекта оно не меняет.
4. Очередь мержа разделена по проекту. Голова очереди для задачи проекта P —
   первая по времени входа (FIFO) запись проекта P. Записи других проектов
   не задерживают её вход в мерж. `wait_for_window` ждёт освобождения
   мьютекса только своего проекта. Потолок ожидания и текст отказа по
   потолку прежние.
5. Мёртвые записи очереди проекта убираются по прежнему правилу (протухший
   heartbeat, `merge_lock._holder_is_dead`) и не держат голову очереди
   своего проекта.
6. Тексты ожидания называют держателя того же проекта, что и ждущая задача.
   Это отказ `acquire` «merge-окно занято …», запись журнала входа в очередь
   «ждёт merge-окна: держит …» и добавка `status` «[ждёт merge-окна: занято
   <id> (pid <pid>), N мин]» (`merge_queue.wait_suffix`). Минуты очереди в
   `status` считаются по записи самой задачи. У артели с одним проектом
   тексты и исходы прежние, это зафиксировано тестами до правки.
7. `orchestrator/store.py` получает функции чтения, записи и снятия строки
   мьютекса мержа по проекту. `store.set_merge_lock` больше не стирает строки
   других проектов. Прежние функции (`merge_lock_row`, `set_merge_lock`,
   `release_merge_lock`, `merge_queue_rows`) и их сигнатуры сохраняются для
   читателей вне зон (`orchestrator/doctor/leases.py`).
8. Окно тишины `notes._silence_window_reason` смотрит все строки мьютекса,
   а не одну. Живой держатель-задача артели открывает окно при любом числе
   строк мьютекса и любом их порядке в таблице. Прочие правила окна (SPEC
   01M563947R26NZW2TJEKM36QRD) прежние.
9. Тесты задачи детерминированы и работают без сети. Две задачи разных
   проектов (артель и учебный внешний) входят в мерж одновременно, и ни одна
   не ждёт другую. Две задачи одного проекта сохраняют прежнее взаимное
   исключение и порядок.

## Критерии приёмки

AC-1. Задача внешнего проекта держит живой мьютекс. `merge_lock.acquire`
задачи артели другим процессом возвращает `None` (мьютекс взят). После этого
в `merge_locks` есть строки обоих держателей, строка держателя внешнего
проекта не изменилась. Симметрично при обратном порядке проектов.

AC-2. Живой держатель другого проекта есть, своих записей очереди и
держателя у проекта задачи нет. Тогда `merge_queue.wait_for_window` задачи
возвращается на первой итерации опроса без ожидания, мьютекс её проекта
взят этим процессом.

AC-3. Задача проекта держит живой мьютекс. `acquire` второй задачи того же
проекта другим процессом возвращает отказ с прежним текстом «[<id>]
merge-окно занято сессией <sid> (pid <pid>, задача <id держателя>),
heartbeat N сек назад — дождись освобождения и повтори approve», строка
держателя не меняется.

AC-4. Мёртвый держатель (протухший heartbeat) проекта P перехватывается
`acquire` задачи проекта P, в журнал пишется «мьютекс merge перехвачен».
Мёртвый держатель другого проекта при `acquire` задачи проекта P остаётся
в таблице без изменений.

AC-5. `merge_lock.release` процесса снимает только его строку. Строка
держателя другого проекта и строка другого процесса того же session_id
остаются.

AC-6. Держат два проекта. `merge_lock.touch_heartbeat`, вызванный
держателем проекта A, обновляет `heartbeat_ts` строки A, а `heartbeat_ts`
строки держателя проекта B остаётся прежним.

AC-7. Очередь мержа проекта P при записях нескольких проектов. Голова
очереди для задачи P — её самая ранняя запись проекта P, даже если раньше
неё в таблице стоит запись другого проекта. Две задачи одного проекта
входят в мерж в порядке входа в очередь (FIFO).

AC-8. Мёртвая запись очереди проекта P убирается и не держит голову
очереди проекта P.

AC-9. Держат два проекта. Текст отказа `acquire`, запись журнала входа в
очередь и добавка `status` от `wait_suffix` называют держателя проекта
ждущей задачи, а не держателя другого проекта. При одном проекте (артель)
все три текста совпадают с прежними побайтно.

AC-10. В `merge_locks` строки держателей двух проектов. Вызов
`store.set_merge_lock` для задачи одного проекта не удаляет строку
держателя другого проекта. Прежние `store.merge_lock_row`,
`store.set_merge_lock`, `store.release_merge_lock` вызываются с прежними
сигнатурами.

AC-11. В `merge_locks` строки живого держателя внешнего проекта и живого
держателя-задачи артели, в любом порядке вставки. `notes._silence_window_reason`
возвращает причину «держатель merge-окна жив (сессия <sid>, задача <id>)»
для держателя артели (окно открыто).

## Оценка объёма и деление
Сработавшие сигналы: 5 файлов кода в зоне (`merge_lock.py`,
`merge_queue.py`, `fsm_merge_gate.py`, `store.py`, `notes.py`) плюс
`tests/`; 11 критериев приёмки (≥ 10); `budget_usd` $45 (≥ $30, бюджет
поднят Оператором в ANSWER-1, ответ 4).

Обоснование монолита (ANSWER-1, ответ 4: «монолит с обоснованием»):
- Разделение мьютекса по проекту в `merge_lock.py`/`merge_queue.py` не
  работает без правки `store.set_merge_lock`. Пока тот стирает всю
  таблицу, взятие окна вторым проектом сотрёт строку живого держателя
  первого, и две задачи одного проекта смогут попасть в окно вместе. Это
  нарушение взаимного исключения внутри проекта.
- Правка `store.py` без `merge_lock.py` бессмысленна: `acquire` по-прежнему
  читает одну строку на пульт.
- Разделение мьютекса без правки `notes.py` тихо ослабляет уже смерженное
  окно тишины. На отрезке после `done` (`_commit_closing`, уборка,
  `_await_main_ci`, справочник ядра — `orchestrator/fsm_merge_gate.py:1357`
  и далее) окно держит только строка держателя. При двух строках
  `merge_lock_row` может отдать строку внешнего проекта, и `note` запушит в
  main артели во время мержа артели.
- Отдельно мержимой части с зелёной планкой и без промежуточного
  ослабления нет, поэтому задача делается одной.
