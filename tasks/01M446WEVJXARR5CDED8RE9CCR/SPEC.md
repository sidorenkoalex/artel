# SPEC: auto — единые правила «отказ, который чинит роль → повтор шага роли»; run продвигает состояние

## Контекст
Сейчас `auto` решает «повторить роль или остановиться» после отказа
перехода по двум разрозненным перечням в `orchestrator/auto.py`
(`ROLE_NOT_FINISHED_REFUSAL_ACTIONS`, `_IN_DEV_ROLE_FIXABLE_REFUSAL_ACTIONS`)
и по состоянию: в `in_dev` любой другой отказ — `Refused` без шага роли,
со второго такого же — остановка; в `review`/`tests_writing`/`spec_writing`
любой журналируемый отказ запускает роль, каким бы он ни был; отказ guard'а
артефакта — немедленная остановка в любом состоянии. Один текст действия
гейта местами смешивает причину, которую чинит роль, и сбой git
(`_mutation_claim_gate` в `orchestrator/advance_gates/review.py`). 04.10.2026
задача 01M443HPZBMJGCHVGV4JQN88RS встала на отказе гейта заявки мутации,
который мог починить сам developer, и Оператор вручную делал `run`,
`advance`, `auto`; `run` после успешного шага состояние не двигает
(`orchestrator/runner.py`, «дальше: artel.py advance <id>»).

Задача вводит один перечень классов отказов рядом с гейтами, единую реакцию
`auto` по классу во всех четырёх агентских состояниях (`spec_writing`,
`tests_writing`, `in_dev`, `review`) и один `advance` после успешного
`run`. Зона `docs/operator-session.md` открыта для описания новой реакции
`run`/`auto` Оператору; отдельным критерием это не требуется.

## Требования
1. Классы отказов. Каждый отказ перехода из `spec_writing`, `tests_writing`,
   `in_dev`, `review` относится ровно к одному из двух классов: «чинит роль»
   (недостаток артефакта или кода роли текущего состояния) или «чинит
   Оператор» (решение, мандат, бюджет, сбой окружения, git, push). Класс
   задаёт ОДИН перечень в коде в `orchestrator/advance_gates/`; `auto`
   читает класс отказа только из него. Содержимое перечня — таблица
   «Перечень отказов» ниже. Отказ, которого в перечне нет (в том числе
   будущий), `auto` считает «чинит Оператор».
2. «Чинит роль». На такой отказ предварительного `advance` `auto` запускает
   шаг роли текущего состояния; действие и подробность отказа из журнала
   попадают в бриф этого шага (блок истории отказов). Исключение — два
   отказа подкласса «роль ещё не закончила» (таблица, пометка «РНЗ»): шаг
   роли запускается, но в бриф они, как и сейчас, не попадают — роли нечего
   в них читать, и существующие тесты этого фильтра не ослабляются. Тот же
   отказ (то же действие), повторившийся после завершённого шага той же
   роли в этом же визите состояния, — остановка `auto` с причиной, где
   названо действие отказа (правило `_role_step_between_repeated_refusals`,
   распространённое на весь класс и все четыре состояния).
3. «Чинит Оператор». На такой отказ `auto` останавливается с первого же
   отказа, без шага роли; причина остановки называет действие отказа.
4. Отказ guard'а артефакта текущей роли («переход отклонён guard'ом») —
   класс «чинит роль»: один шаг роли с текстом отказа guard'а в брифе,
   повтор после этого шага — остановка (требование 2), а не немедленная
   остановка, как сейчас.
5. Несмешение классов в одном действии. Где один текст действия сегодня
   несёт причины разных классов, причина класса «чинит Оператор» получает
   отдельное действие журнала (новый текст с префиксом «переход отклонён:»),
   прежнее действие остаётся за причиной класса «чинит роль»:
   1) гейт заявки мутации: отсутствие заявки «Ловит мутацию» — прежнее
      действие «переход отклонён: гейт заявки мутации»; сбой git (база
      сравнения, список файлов диффа, чтение файла теста) — отдельное
      действие;
   2) прогон приёмки на выходе `in_dev`: красная планка — прежнее действие
      «переход отклонён: приёмочные тесты»; «рабочая копия задачи не
      заведена» и «рабочая копия задачи не выписана на ветку» — отдельное
      действие;
   3) долгоживущие файлы на выходе `tests_writing`: нарушение правила
      «test_author только добавляет файлы» — прежнее действие «переход
      отклонён: долгоживущие файлы tests/»; сбой git (дифф кодовой ветки
      не прочитан, файл не прочитан на голове, сумма не посчитана, перечень
      не записан в ветку документов) — отдельное действие;
   4) «переход отклонён: дерево не на ветке задачи» остаётся только за
      случаем «артефакт РОЛИ ТЕКУЩЕГО СОСТОЯНИЯ не прочитан с ветки»
      (`SPEC.md`/`QUESTIONS.md` в `spec_writing`, `REVIEW.md` в `review`,
      `PLAN.md` в `in_dev`); git не ответил на перечисление ветки
      (`QUESTIONS.md` в `spec_writing`, `acceptance_tests/` в
      `tests_writing`), на подсчёт `ANSWER-*.md` перед эскалацией, а также
      не прочитан с ветки чужой для состояния документ (`SPEC.md` в
      `tests_writing`, в подтяжке main и при поиске планки на выходе
      `in_dev`) — отдельное действие класса «чинит Оператор».
   Остальные гейты четырёх состояний проверены на то же смешение
   (столбец «Смешение» таблицы): других случаев нет — у гейта зон, гейта
   ёмкости, гейта неослабления тестов, лока приёмочных тестов и перечня
   долгоживущих тестов обе ветви одного действия одного класса. Сами
   условия гейтов (что отказывает и когда) не меняются.
6. `artel.py run <id>`: после успешного шага роли (rc=0), если задача
   по-прежнему в агентском состоянии, команда один раз выполняет
   `advance` и печатает его исход (переход, отказ или «нечего
   продвигать»). Отказ этого `advance` не запускает новый шаг роли. Шаг не
   успешен (rc≠0, отказ стартовать) или задача уже вне агентского
   состояния (например, эскалирована внутри шага) — `advance` не
   выполняется. Флаг отключения не вводится: `advance` после шага — тот
   же следующий шаг, который `run` сейчас велит сделать руками, и
   отдельный режим «без продвижения» ТЗ не требует. Шаг роли, который
   запускает сам цикл `auto` или канарейка, дополнительного `advance` от
   `run` не получает — продвижение там остаётся за циклом.
7. Ограничители сохраняются: `config.AUTO_MAX_STEPS`,
   `config.AUTO_STALL_STEPS_LIMIT` (считает и шаги роли на отказах класса
   «чинит роль»), остановка на второй подряд эскалации по конфликту
   подтяжки main.

## Критерии приёмки
AC-1. Предварительный `advance` в своём состоянии журналирует отказ класса
«чинит роль» (любое действие таблицы с классом Р, кроме РНЗ): `auto`
запускает шаг роли этого состояния, не останавливаясь, и бриф этого шага
содержит действие и подробность отказа из журнала.

AC-2. Тот же отказ класса «чинит роль» повторился после завершённого шага
той же роли в том же визите состояния: `auto` останавливается без второго
шага роли, причина остановки содержит действие отказа.

AC-3. Отказ класса «чинит Оператор» (любое действие таблицы с классом О) в
любом из состояний `spec_writing`, `tests_writing`, `in_dev`, `review`:
`auto` останавливается на первом же таком отказе, шаг роли не запускается,
причина остановки содержит действие отказа.

AC-4. Отказ с действием «переход отклонён: …», которого нет в перечне
классов: `auto` реагирует как на класс «чинит Оператор» (AC-3).

AC-5. Гейт заявки мутации: тест в `tests/` без заявки «Ловит мутацию» —
действие «переход отклонён: гейт заявки мутации», `auto` запускает шаг
developer с текстом этого отказа в брифе; сбой git того же гейта (база
сравнения, список файлов, чтение файла теста) — другое действие журнала, и
`auto` останавливается без шага developer.

AC-6. Прогон приёмки на выходе `in_dev`: красная планка — действие
«переход отклонён: приёмочные тесты» класса «чинит роль»; рабочая копия
задачи не заведена или не выписана на ветку — другое действие класса
«чинит Оператор».

AC-7. Выход `tests_writing`: изменение/удаление/переименование файла в
`tests/` вопреки правилу долгоживущих файлов — действие «переход отклонён:
долгоживущие файлы tests/» класса «чинит роль»; сбой git той же проверки —
другое действие класса «чинит Оператор».

AC-8. Действие «переход отклонён: дерево не на ветке задачи» журналируется
только когда артефакт роли текущего состояния не прочитан с ветки; git не
ответил на перечисление ветки или на подсчёт `ANSWER-*.md`, либо не
прочитан с ветки документ другой роли — другое действие класса «чинит
Оператор».

AC-9. Отказ guard'а артефакта текущей роли («переход отклонён guard'ом»)
на предварительном `advance`: `auto` запускает один шаг роли с текстом
отказа guard'а в брифе вместо немедленной остановки; тот же отказ после
этого шага — остановка (AC-2).

AC-10. `artel.py run <id>` после шага роли с rc=0 в агентском состоянии
выполняет `advance` ровно один раз: при готовом артефакте состояние
задачи продвигается, исход `advance` напечатан в выводе `run`.

AC-11. `artel.py run <id>`: `advance` после успешного шага отклонил
переход — исход напечатан, новый шаг роли не запускается; шаг завершился с
rc≠0 — `advance` не выполняется, состояние не меняется.

AC-12. Шаг роли, запущенный циклом `auto`, сам `advance` не выполняет:
продвижение после шага делает только цикл, число попыток `advance` на одну
итерацию цикла не растёт.

AC-13. Ограничители сохраняются для нового класса: шаги роли на отказах
класса «чинит роль» с разными действиями, `config.AUTO_STALL_STEPS_LIMIT`
раз подряд без перехода, — остановка «цикл не сходится»; общий счёт шагов
по-прежнему ограничен `config.AUTO_MAX_STEPS`.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` ≥ $30 (рамка Оператора $35); число
критериев приёмки ≥ 10 (13).

Материал для решения Оператора — **монолит** (решение утверждает Оператор
на гейте SPEC):
- требования 1–5 и 7 — одна атомарная смена механики: перечень классов,
  реакция `auto` по классу и разделение действий гейтов не разрезаются.
  Перечень без новой реакции `auto` — мёртвые данные; новая реакция без
  разделённых действий сразу ошибается в классе на смешанных гейтах
  (сбой git гейта заявки мутации тратил бы шаг developer, а AC-3 запускал
  бы немедленную остановку на отказах, которые чинит роль);
- требование 6 (`run` продвигает состояние) от классов не зависит и
  технически отделимо в самостоятельно мержимую подзадачу. Против деления
  — цена: планка бюджета подзадачи не ниже $25, две подзадачи —
  от $50 при рамке ТЗ $35, а часть с `run` — малая правка CLI с тремя
  критериями (AC-10–AC-12).
