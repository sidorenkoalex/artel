# PLAN: Стабилизация двух тестов, краснящих CI под нагрузкой (full_suite_limit_runs, test_liveness)

## Подход

Замеры ниже — машина Оператора (macOS, 14 ядер), нагрузка — 14 процессов
`python -c 'while 1: pass'` (по числу ядер, сценарий AC-1/AC-4).

### Причина 1: full_suite_limit_runs — старт пробника позже предела (требование 1)

Предел (`limit[0]`) отсчитывается от `subprocess.Popen`/`run` pytest в
`orchestrator/acceptance.py::_run_full_suite_now` (~1303–1341): `-n 1 -p
xdist` — старт главного pytest, старт рабочего процесса xdist, сбор
пробника — всё внутри предела, до `note("start")` (`PROBE_TEST`, строка 60).
Замер времени «запуск pytest `-n 1 -p xdist` → запись старта пробника» тем
же argv (`-p no:cacheprovider -p timeout -o timeout=… -n 1 -p xdist`):

| Условие | Старт пробника, с |
|---|---|
| без нагрузки, 5 раз | 0,33–0,37 |
| нагрузка 14 процессов (1× ядра), 8 раз | 1,21; 1,40; 2,22; 2,38; 2,93; 5,06; 5,78; 5,83 |
| нагрузка 28 процессов (2× ядра), 6 раз | 8,96; 9,49; 10,47; 10,60; 11,44; 12,18 |

Под нагрузкой 1× старт доходит до ~5,8 с — больше нижней части диапазонов
main (ac3_cut N 3–6, ac4 C 3–6, ac5 N 4–7): прогон убит до `note("start")`,
`events("start")` пуст — ровно «[] is not true» из CI. Платформа здесь
роли не играет (старт интерпретатора и xdist — одинаковый путь на Linux
и macOS; раннер CI ubuntu под полным набором xdist — та же нагрузка ядер).

Чувствительность `test_ac6_*` (оба) и `test_ac7_*` (требование 2): их
утверждения проверяют только текст таймаута в выводе `approve` и журнале
(`timeout_lines`, «прогон не уложился в N с», «прогон полного набора
tests/ превысил Nс») — старт пробника не утверждается. Текст таймаута
пишет `_full_suite_timeout_note` при `TimeoutExpired` независимо от того,
успел ли пробник стартовать: поздний старт их не краснит, `hold` 100 ≫ N
не даёт прогону закончиться самому. Нечувствительны — не меняются (это
же держит требование 7: их подъём добавил бы к файлу ещё ~+20–25 с).

### Причина 2: test_liveness — подсчёт в момент распада группы (требование 1)

`_spawn_group_with_child` (tests/test_liveness.py:51–69): лидер делает
`print(c.pid)` в `stdout=PIPE`. stdout в канал у CPython блочно
буферизован — строка уходит из буфера только при выходе лидера, т.е.
после его `time.sleep(5.0)`. Значит `leader.stdout.readline()` возвращается
не сразу, а через ~5 с — в момент выхода лидера. Замер на ветке без
нагрузки: `readline` вернулся через 5,03 с. Потомок спит те же 5 с, но
отсчёт его сна начат на время старта его интерпретатора позже — он
переживает лидера на миллисекунды. Подсчёт `_group_member_count` после
`readline` идёт в этой гонке: без нагрузки обычно успевает (2), под
нагрузкой потомок уже вышел, остаётся лидер (зомби до `wait`, всё ещё
числящийся в группе/сессии) — 1. `ps` здесь не причина: `timeout=5` не
истекает (подсчёт штатный, не нижняя оценка запасного пути — запасной
путь при пустом PATH теста тоже дал бы 1, но выход по таймауту ps не
наблюдался: на ветке подсчёт под нагрузкой — 0,4–0,7 с на весь метод).

Замер гонки на помощнике main (`sleep_sec=5`, тот же скрипт лидера,
подсчёт `liveness._group_member_count` сразу после `readline`, затем
поллинг смерти потомка): кортеж — (`readline`, с; длительность `ps`, с;
запас жизни потомка после `readline`, с; подсчёт).

| Условие | Замеры |
|---|---|
| без нагрузки, 3 | (5,10; 0,31; 0,31; **1**), (5,19; 0,10; 0,18; 2), (5,52; 0,11; 0,29; 2) |
| нагрузка 14 процессов, 8 | (6,09; 0,26; 0,51; 2), (5,74; 0,10; 0,47; 2), (6,90; 0,41; 0,64; 2), (6,02; 0,32; 0,65; 2), (6,50; 0,33; 1,05; 2), (6,05; 0,21; 0,21; **1**), (6,90; 0,36; 0,51; 2), (7,62; 0,17; 1,08; 2) |

`readline` возвращается не раньше ~5 с (выход лидера), запас потомка —
0,2–1,1 с, а `ps` занимает 0,1–0,4 с: когда `ps` не короче запаса,
подсчёт — 1 (2 из 11 замеров). Это и есть «1 != 2» из CI; `timeout=5` у
`ps` ни разу не близок к срабатыванию — код пульта не причина.

Платформы:
- macOS (BSD `ps`): `ps -g <pgid>` выбирает процессы по лидеру группы
  процессов (man ps: «processes with the specified process group
  leaders»); лидер с `start_new_session=True` — лидер группы, потомок
  наследует pgid → 2, пока оба живы.
- Linux (procps `ps`, раннер CI ubuntu): `ps -g <число>` выбирает
  процессы по СЕССИИ, а не по группе (procps: `-g` — «session or effective
  group name»). В тесте это совпадает: лидер запущен с
  `start_new_session=True` (tests/test_liveness.py:64), его sid = pgid =
  pid лидера, потомок наследует и сессию, и группу → тоже 2, пока оба
  живы. Гонка «потомок вышел раньше подсчёта» одна и та же на обеих
  платформах.

Правка (не зависит от платформы): потомок и лидер живут до явного снятия
уборкой теста (`sleep_sec=600`, уборка `terminate_process_group` + `wait`
уже стоит в методе), а `PYTHONUNBUFFERED=1` в окружении на время
`_spawn_group_with_child` — чтобы pid потомка пришёл по каналу сразу, а
не при выходе лидера (иначе `readline` ждал бы 600 с). Это условие запуска
в самом методе, помощник не меняется (Д-1: меняется только передаваемый
`sleep_sec`). Подсчёт идёт, пока группа гарантированно из двух процессов;
утверждение `assertEqual(count, 2)` не тронуто. `orchestrator/liveness.py`
не меняется (требование 6 условно: причина не в коде пульта).

### Пределы full_suite_limit_runs (требование 2, 7)

Нижняя граница поднята до 11 с: ×1,9 к максимуму старта под нагрузкой 1×
ядра (5,83 с). Диапазон 11–13 выбран узким намеренно: худшее сочетание
зёрен main (3, 3, 4) против ветки (13, 13, 13) даёт +29 с к файлу —
требование 7 держится на всём диапазоне зерна, а не в среднем
(13–16 давал бы до +38 с).

| Метод | main | ветка | N < C < hold | C ≠ 900 |
|---|---|---|---|---|
| ac3_cut | C 40–50, N 3–6, hold 100 | C 40–50, N 11–13, hold 100 | 11–13 < 40–50 < 100 | да |
| `test_ac4_*` | C 3–6, hold 60–80 | C 11–13, hold 60–80 | 11–13 < 60–80 | да |
| `test_ac5_*` | N 4–7, COPY_LIMIT 60, hold 100 | N 11–13, COPY_LIMIT 60, hold 100 | 11–13 < 60 (COPY_LIMIT) < 100; обрыв на 11–13 с + старт — внутри окна `--wait 1` (60 с) | 60 ≠ 900 |

`hold` не менялся: он уже кратно больше C (ac4) и C (ac3_cut) — соразмерен.
Подмена `config.FULL_SUITE_WORKERS` (строки 208, 525), `PROBE_TEST`
(49–65) и место `note("start")` — без изменений; утверждения не тронуты,
меняются только литералы `randint(...)` и диапазоны в докстрингах.

Бюджет SPEC ($25) не переоценивается.
