# SPEC: Стабилизация двух тестов, краснящих CI под нагрузкой (full_suite_limit_runs, test_liveness)

## Контекст
Два теста стабильно зелёные по отдельности (локально 3 из 3 за ~5 с), но
краснят CI в полном наборе (~5000 тестов, xdist) на раннере GitHub
(ubuntu) — 11.10.2026 четыре случая (CI ветки 01M4MQAGRWMWR0GFDM9086P3TD,
прогон 38123982463; CI main 513ec5da, прогон 38168246062, обе попытки; CI
ветки 01M4M67SGNEYMN9F1C7XVX24XE, 38139177114; CI main c47f3c9a,
38139914132), 10.10 — `test_ac3` того же файла на CI мержа
01M4KAYMW2YRFB7G0442WFVSHA.

Обозначения ниже: C — предел `config.FULL_SUITE_TIMEOUT_SEC`, подменённый
тестом (в main модуля — 900); N — предел подполя
`full_suite_timeout_sec` профиля тестов; `hold` — время держания
теста-пробника (`PROBE_TEST`, строки 49–65 файла).

- `tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py::ConfigLimitCutsGateRunTest::test_ac4_gate_run_without_subfield_is_cut_at_patched_config`
  (~381–405): C = `randint(3, 6)`, `hold` = `randint(60, 80)`;
  `self.assertTrue(self.events("start"))` падает «[] is not true» —
  прогон обрезан по пределу раньше, чем пробник записал старт (старт
  python и сбор pytest под нагрузкой дольше C). Тот же приём (предел
  обрезки 3–7 с) по коду main у:
  - `ProfileLimitCutsGateRunTest::test_ac3_gate_run_is_cut_at_profile_limit_not_config`
    (далее ac3_cut; ~341–351: C 40–50, N 3–6, `hold` 100);
  - `TimeoutSourceTextTest::test_ac6_profile_limit_timeout_names_limit_and_profile_source`
    (~422–441: C 40–50, N 3–6, `hold` 100) и
    `TimeoutSourceTextTest::test_ac6_config_limit_timeout_names_limit_and_config_source`
    (~454–472: C 3–6, `hold` 100);
  - `TimeoutTextStartsTest::test_ac7_timeout_texts_keep_their_starts_with_effective_limit`
    (~491–507: C 40–50, N 3–6, `hold` 100);
  - `SuiteRunProfileLimitTest::test_ac5_suite_run_cuts_at_profile_limit_and_reports_it`
    (~606–622: N 4–7, предел копии пульта `COPY_LIMIT` = 60, `hold` 100,
    отчёт — `suite-run --wait 1`).
  `test_ac3_profile_limit_above_config_lets_gate_run_finish` берёт C 2–3 с
  с иным ожиданием (пробник должен закончиться сам).
- `tests/test_liveness.py::GroupMemberCountPathTest::test_counts_members_exactly_when_ps_is_not_on_path`
  (~165–183): «1 != 2». `_spawn_group_with_child(sleep_sec=5.0)` (~51–69)
  — лидер и потомок спят 5 с; под нагрузкой подсчёт может прийти после
  выхода потомка либо `ps` не уложиться в `timeout=5`
  (`orchestrator/liveness.py::_group_member_count` ~94–111, запасной путь
  даёт нижнюю оценку 1). На CI (ubuntu) `ps -g` — procps, на машине
  Оператора — BSD `ps` macOS.

В предел C/N методов файла full_suite_limit_runs укладывается не только
старт пробника, но и весь путь до него: тест подменяет
`config.FULL_SUITE_WORKERS` на `"1"` (строки ~208, ~525), поэтому прогон
идёт с `-n 1 -p xdist` — запуск главного процесса pytest, запуск рабочего
процесса xdist и сбор теста-пробника в нём происходят внутри того же
предела. Нижняя граница предела (требование 2) рассчитывается с учётом
этого старта воркера под нагрузкой.

## Требования
1. Причина каждого падения установлена по коду и замером под нагрузкой
   (прогон файла параллельно с нагрузочным процессом) и записана в PLAN —
   не догадкой. Вывод о причине учитывает Linux (раннер CI — ubuntu,
   `ps -g` из procps) наравне с macOS: в PLAN — рассуждение для обеих
   платформ.
2. Методы `tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py`,
   где прогон обрезается по пределу из config/профиля, — ac3_cut,
   `test_ac4_gate_run_without_subfield_is_cut_at_patched_config` и
   `test_ac5_suite_run_cuts_at_profile_limit_and_reports_it` обязательно
   (правка `test_ac5_*` не условна), а также те из `test_ac6_*` (оба) и
   `test_ac7_*`, чувствительность которых установлена требованием 1, —
   стабилизируются ТОЛЬКО подъёмом нижней границы пределов (C, N) до
   уровня, где старт пробника (вместе со стартом воркера xdist `-n 1`,
   см. «Контекст») гарантирован, и соразмерным `hold` (решение Оператора
   на гейте SPEC 11.10.2026, возврат 20:21:45Z). При этом в каждом
   изменённом методе:
   - N < C < `hold` (в методах без N — C < `hold`);
   - C ≠ 900 (значение `config.FULL_SUITE_TIMEOUT_SEC` модуля в main) — в
     том числе на всём диапазоне от зерна;
   - для `test_ac5_*`: N < 60 (`COPY_LIMIT`), и обрыв по N приходится на
     окно ожидания `suite-run --wait 1`.
3. Запрещено как средство стабилизации методов требования 2: повтор
   `approve` или сценария в цикле; маркеры перезапуска (flaky, reruns и
   подобные); `skip`/`skipIf` под нагрузкой; запись события `start` кем-либо,
   кроме теста-пробника (`PROBE_TEST`, строки 49–65 файла).
4. Данные и условия `tests/test_liveness.py::GroupMemberCountPathTest::test_counts_members_exactly_when_ps_is_not_on_path`
   изменены так, что подсчёт делается, пока группа гарантированно из
   двух процессов (например, потомок живёт до явного завершения тестом,
   а не 5 с); утверждение «ровно 2» сохраняется.
5. Утверждения (`assert*`) существующих методов не удаляются и не
   ослабляются; вид утверждения не меняется. Смена литерала в
   утверждении допустима только перечнем раздела «Меняемое поведение»
   с дословными литералами — в этом SPEC такой смены нет (раздел
   отсутствует); понадобится — эскалация Оператору.
6. Если причина падения `test_liveness` — в коде пульта (например,
   `timeout=5` у `ps` в `orchestrator/liveness.py::_group_member_count`
   неоправданно мал), правка вносится в `orchestrator/liveness.py` с
   тестом; таймаут `ps`, если меняется, — не больше 15 с; свойство «сбой `ps` не выдаётся за пустую группу» (живая
   группа при сбое `ps` даёт не 0) не ослабляется. Правка (в тестах и в
   коде пульта) не зависит от платформы: одно и то же поведение на Linux
   (procps) и macOS.
7. Время: каждый изменённый метод под нагрузкой укладывается в 120 с;
   суммарное время прогона каждого изменённого тестового файла растёт не
   больше чем на 30 с по сравнению с main (время файла мерится без
   нагрузки).
8. `tests/sandbox.py` не меняется.
9. Если замер требования 1 показывает, что для гарантии старта нужно
   превысить +30 с на файл (требование 7) или иное ограничение этого SPEC
   (N < C < `hold`, N < 60 в `test_ac5_*`, 120 с на метод, таймаут `ps`
   не больше 15 с), — эскалация Оператору с замером, а не выход за рамку.

## Критерии приёмки
AC-1. При прогоне файла `tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py`
параллельно с нагрузочным процессом (N процессов
`python -c 'while 1: pass'` по числу ядер) не менее 5 раз подряд каждый
изменённый метод зелёный со своими утверждениями:
- ac3_cut и `test_ac4_*` — пробник стартовал (`events("start")` не пуст),
  вывод `approve` содержит «прогон не уложился в N с» (ac3_cut) / «… в C с»
  (`test_ac4_*`), `approve` вернулся раньше C (ac3_cut) / раньше `hold`
  (`test_ac4_*`);
- `test_ac5_*` — пробник стартовал, в отчёте `suite-run --wait 1` есть
  строка «не уложился» с N и ни одна такая строка не несёт 60;
- `test_ac6_profile_*` — строки таймаута в выводе `approve` и в журнале
  задачи есть, называют N и «профиль тестов проекта <имя артели>», без
  «config»;
- `test_ac6_config_*` — строки таймаута в выводе и журнале есть, называют
  C и «config», без «профиль тестов проекта»;
- `test_ac7_*` — вывод и журнал содержат «прогон не уложился в N с» и
  исход, начинающийся с «прогон полного набора tests/ превысил Nс».

AC-2. До правки тот же сценарий нагрузки (AC-1/AC-4) на main хотя бы раз
красный для ac3_cut или `test_ac4_*` и для
`test_counts_members_exactly_when_ps_is_not_on_path`; если воспроизвести
красноту не удалось — причина показана замером в PLAN (времена старта
пробника / подсчёта под нагрузкой против предела).

AC-3. Мутации, которые ловили изменённые методы до правки, ловятся и
после — каждая краснит свой метод:
- ac3_cut — гейт мержа берёт `config.FULL_SUITE_TIMEOUT_SEC`, а не
  подполе профиля (отказ называет C, а не N);
- `test_ac4_*` — предел без подполя взят при импорте (умолчание параметра
  `timeout=config.FULL_SUITE_TIMEOUT_SEC` или константа модуля);
- `test_ac5_*` — фоновый прогон `suite-run` берёт
  `config.FULL_SUITE_TIMEOUT_SEC` либо отчёт о таймауте печатает значение
  config, а не N;
- `test_ac6_profile_*` — источник в текст не дописан либо всегда
  «config»;
- `test_ac6_config_*` — источник дописывается только при заданном
  подполе либо назван профилем проекта при его отсутствии;
- `test_ac7_*` — источник вставлен в начало текста таймаута вместо
  дописывания либо в начале текста осталось значение config.
Требование распространяется только на методы, которые правка меняет.

AC-4. `tests/test_liveness.py::GroupMemberCountPathTest::test_counts_members_exactly_when_ps_is_not_on_path`
зелёный при прогоне файла параллельно с тем же нагрузочным процессом не
менее 5 раз подряд, с утверждением, что подсчёт равен ровно 2; мутация
«`ps` ищется только по PATH вызывающего» (без запасных `/bin`,
`/usr/bin`) по-прежнему его краснит.

AC-5. При правке `orchestrator/liveness.py` подсчёт для живой группы при
сбое `ps` (не запустился, не ответил в срок, ненулевой код) не равен 0;
таймаут `ps`, если изменён, не больше 15 с.

AC-6. В каждом изменённом методе файла full_suite_limit_runs на всём
диапазоне значений от зерна: N < C < `hold` (без N — C < `hold`), C ≠ 900;
в `test_ac5_*` N < 60. Стабилизация не использует повтор `approve`/сценария
в цикле, маркеры перезапуска, `skip`/`skipIf` и запись события `start` не
тестом-пробником.

AC-7. Каждый изменённый метод под нагрузкой AC-1/AC-4 проходит быстрее
120 с; время прогона каждого изменённого тестового файла на ветке,
измеренное без нагрузки, больше времени его прогона на main (тоже без
нагрузки) не более чем на 30 с.

AC-8. `tests/sandbox.py` на ветке совпадает с main.
