# ТЗ: Стабилизация двух тестов, краснящих CI под нагрузкой (full_suite_limit_runs, test_liveness)

Источник: копилка 10.10 и 11.10 (приоритет 1: «Третий за день красный CI
от … test_ac4 …»), решение Оператора 11.10.2026 — заводить вне очереди.

Случаи (11.10): CI ветки 01M4MQAGRWMWR0GFDM9086P3TD (прогон 38123982463),
CI main 513ec5da (прогон 38168246062, обе попытки), CI ветки
01M4M67SGNEYMN9F1C7XVX24XE (38139177114), CI main c47f3c9a

(локально 3 из 3 за ~5 с); падают только в полном наборе (~5000
тестов, xdist) на раннере GitHub.

Факты (origin/main b98e967d):
- `tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py`:
  `ConfigLimitCutsGateRunTest::test_ac4_gate_run_without_subfield_is_cut_at_patched_config`
  (~380–403): предел C = `randint(3, 6)` с, пробник держит
  `randint(60, 80)` с; утверждение `self.assertTrue(self.events("start"))`
  падает «[] is not true» — прогон обрезан по пределу раньше, чем
  пробник успел записать событие старта (запуск python и сбор pytest под
  нагрузкой дольше C). Тот же приём у test_ac3 (~341–344: предел профиля
  `randint(3, 6)`) — падал 10.10. Остальные методы файла используют
  пределы 40–50 с или 2–3 с с иными ожиданиями — проверить, какие из них
  чувствительны к тому же.
- `tests/test_liveness.py::GroupMemberCountPathTest::test_counts_members_exactly_when_ps_is_not_on_path`
  (~165–183): «1 != 2». `_spawn_group_with_child(sleep_sec=5.0)` (~51–69):
  потомок и лидер спят 5 с; под нагрузкой подсчёт может прийти после
  выхода потомка (группа из одного лидера) либо `ps` не уложиться в
  `timeout=5` (`orchestrator/liveness.py::_group_member_count` ~94–111,
  запасной путь даёт нижнюю оценку 1). Причину установить по коду и
  замером, не догадкой.

Требуется:
1. Установить причину каждого падения (по коду и, где можно, замером
   под нагрузкой — например, прогон файла параллельно с нагрузочным
   процессом) и записать её в PLAN.
2. Изменить ДАННЫЕ и УСЛОВИЯ тестов так, чтобы они не зависели от
   скорости старта процессов под нагрузкой, сохранив проверяемое
   свойство и ловимую мутацию каждого метода:
   - test_ac4 (и test_ac3, и иные методы файла с тем же приёмом):
     прогон обрезается по пределу из config/профиля, а не идёт до конца
     пробника. Допустимо: поднять нижнюю границу предела (например, до
     уровня, где старт пробника гарантирован, с соразмерным `hold`) либо
     отсчитывать проверку старта иначе — без ослабления утверждения
     «пробник стартовал» и «отказ называет предел C».
   - test_liveness: подсчёт делается, пока группа гарантированно из двух
     процессов (например, потомок живёт до явного завершения тестом, а
     не 5 с); утверждение «ровно 2» сохраняется.
3. Утверждения (`assert*`) существующих методов не удаляются и не
   ослабляются; если меняется значение в утверждении — разделом SPEC
   «Меняемое поведение» с дословными литералами; смена вида утверждения —
   только вопросом Оператору с матрицей.
4. Если причина в коде пульта (например, `timeout=5` у `ps` неоправданно
   мал), — правка кода в зоне `orchestrator/liveness.py` с тестом, без
   ослабления свойства «сбой ps не выдаётся за пустую группу».
5. Время прогона каждого изменённого файла не растёт больше чем на
   30 с по сравнению с текущим.

Критерии приёмки (направление; планку пишет test_author):
- Изменённые методы зелёные при прогоне файла параллельно с
  нагрузочным процессом (например, N процессов `python -c 'while 1: pass'`
  по числу ядер) не менее 5 раз подряд; до правки тот же сценарий хотя
  бы раз красный (или причина показана замером).
- Мутации, которые ловили методы до правки (обрезка по пределу взята при
  импорте; ps ищется только по PATH), ловятся и после.
