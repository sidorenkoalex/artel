# PLAN: Протокол рестарта после таймаута шага — WIP-чекпоинт оркестратора

## Подход

Сегодня таймаут шага (`orchestrator/runner.py::run_agent_once`, ветка
`timed_out`) оставляет WIP агента незакоммиченным; следующий `run`
встречает грязную копию в `fixation.check_integrity` и уводит задачу в
`escalated` — рестарт решался только руками Оператора (прецеденты T022,
T037: ручной коммит-чекпоинт). Задача — автоматизировать ровно это
действие, не трогая саму сверку целостности (требование 5).

Ключевые решения:

1. **Новая функция `runner.commit_timeout_checkpoint(conn, task_id,
   role) -> str`**, вызывается из `run_agent_once` внутри `if
   timed_out:`, до журнала «agent run TIMEOUT» — чтобы рестарт, начатый
   сразу по этой записи, уже видел зафиксированное чистое состояние.
   Первым делом сверяет `store.task_target(conn, task_id) ==
   config.DEFAULT_TARGET` — иначе тихий no-op (см. «Риски»: `gitcmd.git`
   всегда бьёт по `config.ROOT`, для внешнего target это не тот
   репозиторий, где работала роль). Дальше делает `git add -A` + `git
   diff --cached --quiet` (есть ли что коммитить) + `git commit` —
   только через `gitcmd` (требование 7). Коммитит, только если `git
   diff --cached --quiet` вернул 1 (есть застейдженный дифф) — так AC-4
   (чистое дерево → пустой коммит не заводится) выполняется без
   отдельной проверки чистоты до `add`. Отказ git на любом из трёх
   шагов (`add`/`diff`/`commit`) — тихий отказ, без коммита и без
   журнала: та же деградация, что уже выбрана в `fixation._fix_external`
   для «git не ответил».
2. **Сообщение коммита** — буквально из SPEC: `f"{task_id}:
   WIP-чекпоинт после таймаута шага {role}"` (требование 2, дословно
   проверяется AC-1 приёмочного теста).
3. **Идентичность коммита** — служебная, `fixation.FIXATION_AUTHOR_
   NAME`/`FIXATION_AUTHOR_EMAIL` (уже существующие константы, которые
   `fixation._fix_external` использует для коммита фиксации внешнего
   target по тому же доводу: это действие оркестратора, не роли и не
   Оператора). Импорт `fixation` в `runner.py` уже есть, новых
   зависимостей не добавляется.
4. **Журнал факта чекпоинта** — `store.journal(conn, task_id,
   "orchestrator", "WIP-чекпоинт после таймаута шага", detail)`, где
   `detail` несёт сообщение коммита и sha (требование 3, AC-1: actor
   `orchestrator`, пометка таймаута в тексте).
5. **Повторная фиксация sha — центральный момент плана.** Коммит
   чекпоинта легитимно сдвигает HEAD ветки задачи мимо `store.
   set_state` (единственной прежде точки, где `tasks.fixed_sha`
   обновлялся). Без повторной фиксации следующий `run` сравнил бы живой
   sha (уже сдвинутый чекпоинтом) с `fixed_sha`, зафиксированным ДО
   таймаута, — получил бы «sha разошёлся» и всё равно ушёл в
   `escalated`, то есть AC-2 не выполнялся бы, хотя дерево уже чистое
   (проверено локальным прогоном приёмочных тестов на первой версии
   реализации без этого шага — `test_ac2_restart_after_checkpoint_
   does_not_escalate` падал именно на «инцидент целостности», не на
   «грязная копия»). Решение: приватная `store._record_fixation`
   переименована в публичную `store.record_fixation` (единственная
   правка сигнатур в этой задаче — сама логика функции не менялась,
   только видимость и обновлённый докстринг про второго вызывающего);
   `set_state` продолжает звать её как раньше. `runner.
   commit_timeout_checkpoint` зовёт `store.record_fixation(conn,
   task_id)` после успешного коммита — `fixation.check_integrity`
   и `fixation.fix()` при этом не меняются вовсе (требование 5): они
   как и раньше читают текущее состояние, просто оно уже сдвинуто и
   свежо зафиксировано.
6. **rc != 0 (не таймаут) не трогается** — `commit_timeout_checkpoint`
   вызывается ТОЛЬКО из ветки `if timed_out:`; ветка `if rc != 0:` кода
   не меняется (требование 4, AC-3).

## Шаги

1. `orchestrator/runner.py`: функция `commit_timeout_checkpoint` +
   вызов из `run_agent_once` внутри `if timed_out:`.
2. `orchestrator/store.py`: `_record_fixation` → `record_fixation`
   (публичная), докстринг дополнен про вызов из
   `runner.commit_timeout_checkpoint`; правка двух комментариев
   (`orchestrator/runner.py`, `orchestrator/review.py`), называвших
   функцию по старому приватному имени.
3. `docs/codebase-map.md`: регенерация (`scripts/codebase_map.py`) —
   новые публичные функции `runner.commit_timeout_checkpoint`,
   `store.record_fixation`.
4. `docs/invariants.md`: строка 30 реестра — протокол рестарта после
   таймаута, со ссылкой на приёмочные тесты T041 и собственные юнит-тесты.
5. Юнит-тесты `tests/test_timeout_checkpoint.py`: чистое дерево (нет
   коммита, нет журнала), грязное дерево (коммит + сообщение + sha в
   журнале), повторная фиксация (`check_integrity` после чекпоинта —
   `None`, `fixed_sha` равен новому HEAD), отказ на каждом из трёх шагов
   (`git add`/`git diff --cached`/`git commit` — тихий отказ, ни
   коммита, ни журнала на каждом), target не догфуд (no-op — тихий
   отказ уже на входе, до `git add`).
6. Прогон локальных приёмочных тестов T041 (AC-1..AC-4) и полного
   набора `tests/`.

## Влияние на систему

- **`fixation.check_integrity`/`fixation.fix`/`fixation.read` не
  менялись** — ни строчки; сверка целостности работает как и раньше,
  просто видит уже сдвинутое и зафиксированное состояние (принцип
  целостности, требование 5 SPEC).
- **`store._record_fixation` → `store.record_fixation`**: единственное
  изменение видимости существующей функции в этой задаче. Поведение
  байт-в-байт то же (тело не менялось), вызов из `set_state` не
  изменился по сигнатуре и порядку. Внешних вызывающих у приватного
  имени не было (проверено `grep -rn "_record_fixation"` по `orchestrator/`
  и `tests/` до правки — единственный вызов внутри `store.py` и два
  упоминания в комментариях, оба обновлены на новое имя). Риск
  регрессии — минимальный: переименование без изменения тела и точки
  вызова.
- **Ветка `rc != 0` (провал по коду возврата) не затронута** —
  чекпоинт не вызывается там ни при каких условиях (AC-3 приёмочного
  теста это проверяет explicit).
- **Бюджет/учёт стоимости не затронуты** — чекпоинт вызывается уже
  после `close_pump`/`charge_missing_result`/`budget.
  check_program_spend` (по месту в коде — внутри `if timed_out:`,
  которое идёт следом за ними), их результат не читает и не меняет.
- **Откат**: оба изменения — чистое добавление функции
  (`commit_timeout_checkpoint`) и переименование (`record_fixation`)
  без изменения тела. Откат — удаление вызова в `run_agent_once` и
  функции целиком; переименование обратимо тем же способом (вернуть
  `_` и точку вызова в `set_state`).
- Не входит и не тронуто (SPEC, «Не входит»): поведение при `rc != 0`,
  логика эскалации по факту самого таймаута, коммит куда-либо, кроме
  ветки задачи.

## Риски

- Если в момент таймаута рабочее дерево ветки задачи по какой-то
  причине не соответствует ветке задачи (роль ещё не сделала `git
  checkout -b` — легитимный ранний момент до первого коммита роли),
  `commit_timeout_checkpoint` закоммитит то, что реально стоит
  выписанным в HEAD на этот момент — то же вырожденное поведение,
  что уже принято в `fixation._fix_dogfood` (сверка по текущему
  чекауту, не по имени ветки, кроме явного `on_foreign_branch`). Не
  расширял чекпоинт логикой чтения «чужой ветки» — в продовом флоу
  роль создаёт свою ветку первым действием миссии до всякого
  таймаута, а добавление такой логики без своего критерия приёмки
  было бы расширением зоны задачи.

- **Только догфуд** (REVIEW.md T041, итерация 1, замечание major):
  `commit_timeout_checkpoint` теперь явно проверяет `target ==
  config.DEFAULT_TARGET` и не коммитит ничего для внешнего target —
  тем же приёмом, что уже применяет `fsm._dirty_refuses` («Только
  догфуд», ADR-0003 3д). Раньше функция безусловно била по
  `config.ROOT` через `gitcmd.git`, что для внешнего target было бы
  вдвойне неверно: (а) ROOT — дерево пульта, не тот репозиторий, где
  реально работала роль (workspace target'а, `role_cwd`), и чекпоинт
  либо подхватил бы чужое незакоммиченное состояние ROOT под
  сообщением этой задачи, либо ничего не нашёл бы там, оставив
  настоящий WIP workspace'а нетронутым; (б) даже коммит в сам
  workspace не решил бы AC-1/AC-2 для внешнего target — `check_
  integrity` для него сверяется не с workspace, а с артефактным
  репозиторием `.artel/projects/<target>/` (`fixation.read`/
  `_read_external`), а свой workspace ADR-0003 §4 вообще не коммитит
  никогда. Полноценный чекпоинт для внешнего target требует решения
  на уровне многотаргетной архитектуры фиксации (что физически
  коммитить и куда), это отдельная задача, не точечная правка этой
  функции. Пока `targets.yaml` объявляет только `artel`
  (`config.DEFAULT_TARGET`, ADR-0003 3д — «особый случай до A7»), эта
  ветка не задета вживую; юнит-тест `test_non_dogfood_target_skips_
  checkpoint` фиксирует no-op явно, не полагаясь на то, что второго
  target пока не существует.
