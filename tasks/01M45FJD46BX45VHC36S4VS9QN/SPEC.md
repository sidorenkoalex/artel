# SPEC: Смена поведения в существующих тестах без эскалации; ослабление — по-прежнему мандатом

## Контекст
Сегодня правка утверждения существующего тестового метода, даже прямо
вызванная требованием SPEC, проходит через эскалацию разработчика и ответ
Оператора мандатом. Так было в двух случаях 05.10: в задаче
01M446WEVJXARR5CDED8RE9CCR (шесть методов, `calls == 2` → `calls == 1`)
и в задаче 01M44EP4Q927DJXVX9YMMZ0B7V (семь методов, текст рецепта отказа).
В обоих случаях менялось только ожидаемое значение, а ответа Оператора
ждали 30–40 минут. Эскалацию вызывает не гейт: изменённые утверждения
узел `orchestrator/advance_gates/test_integrity.py` сегодня только
наблюдает (SPEC 01M3Y753QNG6TS5C7MTJS1MEV6). Эскалацию требуют правило
навыка разработчика и пункт чек-листа ревью.

Решение Оператора 05.10: смена ожидания проходит без эскалации, если она
объявлена в SPEC и подтверждена машинной проверкой. Ослабление
по-прежнему проходит только мандатом «Ослабление тестов разрешено: …».
Значит, изменённые утверждения из наблюдения становятся находкой гейта
неослабления. Исключение — смена ожидания, объявленная в SPEC и
доказанная двусторонним прогоном. Новое правило меняет поведение,
которое закрепляют инвариант 38 и существующие тесты наблюдения. Их
правка — смена ожидания самой задачи, и на пине пульта она идёт прежним
путём: эскалацией с мандатом (раздел «Меняемое поведение» ниже).

Чтение ТЗ в одном месте. Пункт 5 ТЗ называет ослаблением «расширение
допуска (`delta`, `places` больше прежнего либо появились)». У `places`
больше знаков — это сужение допуска. SPEC следует определяющим словам
«расширение допуска»: ослабление — `delta` больше прежнего, `places`
меньше прежнего (требование 9).

## Требования

1. **Раздел SPEC «## Меняемое поведение».** Раздел необязательный.
   Пункт раздела — строка списка вида
   `` - `tests/<путь>.py::<Класс>::<метод>`: `<было>` → `<стало>` (требование <N>) ``.
   - Пар «было → стало» в одной строке может быть несколько, через `; `:
     `` `2` → `1`; `"a"` → `"b"` ``.
   - Имя метода квалифицированное: в том виде, в каком его отдаёт
     `guard.qualified_test_methods`, и хотя бы с одним классом
     (`Класс::метод`; вложенные классы — через `::`).
   - `<N>` — номер пункта раздела «Требования» того же SPEC.
   - Строки раздела, которые не начинаются с `- `, — свободный текст. Если
     раздел пуст или несёт только шаблонную заглушку, это то же самое, что
     раздела нет.
2. **Форма раздела проверяется в `scripts/guard.py`.** Проверка работает
   и в CLI (`python3 scripts/guard.py <SPEC.md>`), и на переходе
   `spec_writing -> spec_gate`. Нарушением считаются:
   - путь не под `tests/` или не `*.py`;
   - имя без класса;
   - пустое «было» или «стало» (обе стороны — непустой текст в обратных
     кавычках);
   - нет ссылки «(требование N)» либо пункта N нет в разделе «Требования»;
   - один и тот же метод назван дважды.

   Нарушение называет строку раздела. SPEC без раздела проверяется как
   сегодня.
3. **Approve гейта SPEC сверяет раздел с базой.** Проверка идёт в
   `orchestrator/fsm.py::_approve_spec_gate` для задачи target артели, не
   канареечной. Каждый названный метод обязан существовать в голове
   `main` репозитория задачи под этим квалифицированным именем (по
   `guard.qualified_test_methods`).
   - Нет файла или метода — мягкий отказ «approve отклонён» с именем
     метода, тем же способом, что нынешние отказы гейта SPEC. Задача
     остаётся на `spec_gate`.
   - Молчание git при чтении `main` — тот же мягкий отказ с названной
     причиной.
   - После успешной сверки пишется запись журнала задачи «объявлена смена
     поведения тестов». Она перечисляет каждую строку раздела: метод,
     пары «было → стало», номер требования. Эта запись и есть решение
     Оператора о смене поведения.
   - SPEC без раздела — ни сверки, ни записи. Для канареечной задачи и
     внешнего target раздел проверяется только по форме (требование 2) и
     на рубежах не действует.
4. **Объявленное берётся из approve, а не из текущего текста SPEC.** Узел
   `test_integrity` читает объявленные методы и пары «было → стало» из
   последней записи «объявлена смена поведения тестов» (требование 3).
   Правка раздела после approve на рубежах не действует до нового approve.
5. **Различение смены ожидания и ослабления живёт в `scripts/guard.py`**,
   публичной функцией рядом с `changed_test_assertions`, а не копией в
   пульте. Правило для метода, сохранившего имя, строится на нормальных
   формах `guard.test_assertions`:
   - R — утверждения base, которых в head меньше (то, что сегодня отдаёт
     `changed_test_assertions`). A — утверждения head, которых в base
     меньше (мультимножества нормальных форм).
   - R пусто — смены нет: добавленные и переставленные утверждения
     находкой не являются, как сегодня.
   - **Смена ожидания**: каждое утверждение из R сопоставляется отдельному
     утверждению из A с равной *маскированной* формой. Маскированная
     форма — нормальная форма, в которой каждая константа-литерал
     (`ast.Constant`) заменена одной меткой. При нескольких кандидатах
     с одной маскированной формой сопоставление идёт по порядку появления
     в методе. «Фактическая смена значений» — пары (константа base,
     константа head), различающиеся на одной позиции сопоставленных
     утверждений.
   - **Ослабление или иная смена** — всё, что правило смены ожидания не
     признало. Сюда входят: утверждений меньше; другой вид (`assertEqual`
     → `assertIn`/`assertTrue`/`assertIsNotNone`); литерал на позиции base
     заменён вызовом, атрибутом или именем; любой иной сдвиг маскированной
     формы. Удаление метода, удаление файла и пропуск остаются находками
     `_file_findings`, как сегодня.
6. **Сверка с объявленным.** Для метода из объявленного перечня
   (требование 4) с признанной сменой ожидания множество фактических пар
   обязано совпасть с множеством объявленных пар. Обе стороны объявленной
   пары читаются `ast.literal_eval` и сравниваются по типу и значению;
   сторона, которая не читается как литерал, ни с чем не совпадает.
   - Несовпадение — находка «смена не совпала с объявленным». Она
     называет фактические пары.
   - Объявленный метод без изменённых утверждений — не находка. Журнал
     требования 8 называет его «объявлен в SPEC, утверждения не изменены».
7. **Исходы рубежей.** Оба рубежа: переход `in_dev -> verifying` и гейт
   мержа.
   - а) Смена ожидания в объявленном методе, совпавшая с объявленным,
     проходит с записью журнала, если выполнены требования 9–12
     (строгость, двусторонний прогон, его признание на мерже, храповик).
   - б) Иначе — находка узла отказа. Это ослабление в любом методе, любая
     смена утверждений метода вне объявленного перечня и несовпадение с
     объявленным. Находка проходит тем же путём, что находки
     `_file_findings` сегодня: отказ перехода `in_dev -> verifying`
     именованным действием «переход отклонён: гейт неослабления тестов»
     и эскалация на гейте мержа.
   - Строка находки называет файл, квалифицированное имя метода и
     причину. Причина — одна из трёх: смена вне раздела «Меняемое
     поведение»; ослабление: <признак>; смена не совпала с объявленным.
   - Покрытие мандатом — тем же `Finding.mandate_elements` (путь,
     `путь::Класс`, `путь::Класс::метод`, оба пути пары переименования).
     Покрытая находка уходит в журнал «ослабление тестов разрешено
     мандатом Оператора», как сегодня. Мандат по-прежнему снимает любую
     находку, в том числе находки требований 9–12.
   - Канареечная задача и внешний target — без изменений: гейт не
     проверяется, новых записей нет.
8. **Журнал рубежей.**
   - Записи наблюдения сохраняются в прежней форме на обоих рубежах.
     Это «изменены утверждения тестов (наблюдение)» с отметкой «покрыто
     мандатом ANSWER-n» и «наблюдение не выполнено: …».
   - К ним добавляется запись «утверждения тестов: исход рубежа». Её
     пишет каждый проход, где есть изменённый или объявленный метод.
     Запись называет каждый такой метод (`путь::Класс::метод`) и исход по
     нему. Возможные исходы: смена ожидания по SPEC (требование N) — с
     итогом двустороннего прогона, когда он есть; покрыто мандатом
     ANSWER-n; находка: <причина>; объявлен в SPEC, утверждения не
     изменены.
9. **Строгость нового ожидания не ниже старого.** Каждая фактическая пара
   смены ожидания (требование 5) оценивается по позиции константы.
   Ослабление — находка требования 7б с названным признаком.
   - Допуск. У `assertAlmostEqual` и `pytest.approx` ослабление — это
     `delta`, `rel` или `abs` больше прежнего либо `places` меньше
     прежнего. У `assertNotAlmostEqual` — наоборот. Появление допуска,
     которого не было, — это сдвиг маскированной формы, то есть уже
     находка требования 5.
   - Регулярное выражение: второй аргумент `assertRegex`,
     `assertRaisesRegex`, `assertWarnsRegex`, а также `match=` у
     `pytest.raises` и `pytest.warns`. Ослабление — убыло вхождений
     якорей `^`, `$`, `\A`, `\Z` либо прибыло вхождений `.*` или `.+`.
     Любая смена регулярного выражения `assertNotRegex` — признак, который
     правило не оценивает.
   - Вхождение: первый аргумент `assertIn`, левая часть `in` в `assert`
     и в `assertTrue`. Ослабление — новая строка пуста либо является
     собственной подстрокой старой. Для `assertNotIn` и `not in` —
     старая строка является собственной подстрокой новой.
   - Порядок: `assertGreater`, `assertGreaterEqual`, `assertLess`,
     `assertLessEqual`, а также `>`, `>=`, `<`, `<=` в `assert` и в
     `assertTrue`/`assertFalse`. Ослабление — числовая граница сдвинута в
     разрешающую сторону. Нечисловая граница — признак, который правило
     не оценивает.
   - Равенство (смена значения строгость не меняет): аргументы
     `assertEqual`, `assertNotEqual`, `assertIs`, `assertIsNot`,
     `assert*Equal` коллекций и строк, `assertCountEqual`; `==`, `!=`,
     `is`, `is not` в `assert` и в `assertTrue`/`assertFalse`; аргументы
     `assert_called_with`, `assert_called_once_with`, `assert_any_call`,
     `assert_has_calls`.
   - Литерал, заменённый вызовом, атрибутом или именем, — находка
     требования 5 с признаком «литерал заменён вычисленным значением».
   - Константа на любой другой позиции — находка с признаком «правило не
     умеет оценить строгость», не пропуск.
10. **Двусторонний прогон на переходе `in_dev -> verifying`.**
    - **Место.** Прогон идёт в составе рубежа неослабления
      (`_test_integrity_gate_refuses`), после сравнения, и только если
      сравнение не дало непокрытых находок. Каждый тест-кандидат
      прогоняется дважды, поэтому сначала идут дешёвые отказы. Перечень
      методов даёт само сравнение. Порядок существующих отказов перехода
      не меняется: гейт заявки мутации → рубеж неослабления → гейт
      отработки замечаний ревью → проверка головы на origin → прогон
      приёмки. Нет записи «объявлена смена поведения тестов» или нет
      методов исхода 7а — прогон не выполняет ни одного вызова git и
      pytest и ничего не пишет в журнал.
    - **Что прогоняется.** Каждый метод исхода 7а, не покрытый мандатом.
      Новая версия файла теста (из head) прогоняется на дереве базы
      сравнения (`gitcmd.diff_base`) и обязана упасть: тест различает
      поведение. Старая версия файла (из base) прогоняется на дереве
      головы ветки и тоже обязана упасть: поведение действительно
      сменилось. Если любая из сторон зелёная — отказ с именем метода и
      стороной.
    - **Что считается доказательством.** Падение засчитывается, только
      если pytest отчитал узел метода как проваленный в фазе выполнения
      (call) с исключением класса `AssertionError` (включая подклассы,
      `self.fail`, `mock.assert_*`) либо `pytest.fail.Exception`
      («DID NOT RAISE»/«DID NOT WARN»). Класс и фаза берутся из отчёта
      pytest об узле, а не из кода возврата процесса. Не доказательство,
      а отказ с названной причиной: ошибка сборки или импорта, ошибка
      фазы setup (`setUp`, фикстуры), иное исключение в фазе call
      (`NameError`, `AttributeError`, `TypeError`, …), пропуск, узел не
      найден.
    - **Где и чем.** Во временных деревьях вне рабочей копии задачи
      (образец `fsm_merge_gate._scratch_worktree`):
      `git worktree add --detach` в клоне проекта задачи
      (`workspace.task_repo`) во временный каталог. Два дерева на весь
      рубеж: база и голова. Команда и окружение — те же, что
      `acceptance._pytest_command`/`_pytest_env`, с узлом
      `tests/<файл>.py::<Класс>::<метод>`. Таймаут на каждый прогон
      pytest — именованная константа `orchestrator/config.py`.
    - **Уборка.** Деревья дерегистрируются (`git worktree remove
      --force`), а их каталоги удаляются при любом исходе: успех, отказ,
      таймаут, исключение.
    - **Сбои.** Таймаут и молчание git (нет базы, не создалось дерево) —
      отказ (fail-closed), не пропуск.
    - **Исход.** Отказ — тем же именованным действием рубежа
      неослабления. Пройденный прогон пишет запись журнала «двусторонний
      прогон пройден» с sha головы ветки, sha базы и перечнем методов.
11. **Гейт мержа двусторонний прогон не повторяет.** Метод исхода 7а
    проходит гейт мержа, только если есть запись «двусторонний прогон
    пройден» с sha, равным текущей голове ветки, и запись называет этот
    метод. Иначе это находка «двусторонний прогон для текущей головы не
    записан», то есть эскалация до мандата. Голова, сдвинувшаяся после
    перехода, заново доказывает смену поведения на переходе либо получает
    мандат.
12. **Храповик.** Общее число тестовых методов
    (`guard.qualified_test_methods`) и утверждений (`guard.test_assertions`)
    по `tests/**/*.py` в голове ветки не меньше, чем в базе сравнения.
    - Разница считается по файлам диффа `tests/` того же прохода:
      неизменённые файлы вносят в обе стороны одно и то же. Новых
      запросов git храповик не делает. Неразбираемая сторона файла даёт
      ноль.
    - Находка храповика называет числа «было → стало» (методы,
      утверждения) и файлы, где число убыло. Она добавляется, только если
      иных непокрытых находок в проходе нет: иначе отказ уже стоит и
      адресно называет причину убыли.
    - Мандат покрывает убыль, если каждый файл с убылью покрыт элементом
      мандата. Покрывает путь файла (любой путь пары переименования) либо
      элементы `путь::Класс`/`путь::Класс::метод`, покрывающие каждый
      метод этого файла, который исчез или потерял утверждения. Покрытая
      убыль уходит в журнал «ослабление тестов разрешено мандатом
      Оператора».
13. **Ревью-пакет.** `orchestrator/review.py::_changed_assertions_part`
    сохраняет заголовок «Изменённые утверждения тестов» и прежнюю строку
    наблюдения по каждому методу (`<путь>: утверждения изменены в
    <Класс>::<метод>: <текст>`).
    - К строке добавляются исход рубежа (требование 8) и, для
      объявленного метода, строка «было → стало (требование N)» из записи
      approve. Для метода исхода 7а — ещё итог двустороннего прогона для
      текущей головы: пройден / не записан.
    - Текст «переход и мерж от них не зависят» заменяется таким:
      «смена утверждений вне раздела «Меняемое поведение» SPEC и
      ослабление отказывают переходу `in_dev -> verifying` и эскалируют
      гейт мержа до мандата Оператора».
    - Канареечная задача и внешний target — без раздела, как сегодня.
14. **Карта кодовой базы.** `docs/codebase-map.md` регенерирована
    (`scripts/codebase_map.py`). Карта берёт строку «Назначение» из первой
    строки модульного докстринга. Строки «Назначение» модулей, несущих
    механику, вместе называют: раздел SPEC «Меняемое поведение», смену
    ожидания и ослабление, двусторонний прогон, сверку с объявленным,
    строгость, храповик. Это узел `orchestrator/advance_gates/test_integrity.py`
    и модули, заведённые задачей.
15. **Приложения к PLAN для защищённых путей.** Каждое приложение
    проверено `git apply --check` на чистом дереве, это подтверждено в
    PLAN.
    - `templates/SPEC.md` — необязательный раздел «## Меняемое поведение»
      с образцом строки требования 1 и пояснением, когда он нужен.
    - `skills/spec-authoring.md` — правило аналитику: каждый существующий
      тестовый метод, чьё ожидание меняется по требованиям, перечисляется
      в разделе с конкретными значениями. Ослабление разделом не
      оформляется, только вопросом Оператору.
    - `skills/coding-standards.md` — правило разработчику: смена ожидания
      в методе из раздела SPEC идёт без эскалации. Любая иная правка
      утверждений, удаление, пропуск и расширение допуска — по-прежнему
      эскалация до сдачи шага.
    - `skills/review-checklist.md` — Фаза B: сверка каждого изменённого
      ожидания с требованием SPEC и строкой «было → стало». Пункт
      «утверждения существующих тестов сверены с base» правится под это.
    - `docs/invariants.md` — строка инварианта 38 под новое поведение:
      смена утверждений вне раздела SPEC и ослабление — отказ;
      двусторонний прогон; храповик.
    - `tests/test_invariants.py` — сторож новой строки внутри того же
      приложения (CI ветки идёт без приложений). Смена утверждения метода
      вне объявленного перечня отказывает переходу, а мандат снимает
      отказ.
16. **Существующие тесты.**
    - Методы раздела «Меняемое поведение» ниже — это смена ожидания самой
      задачи. Новой механики на пине пульта ещё нет, поэтому их правка
      идёт прежним путём: эскалацией разработчика с мандатом Оператора.
      Число и вид их утверждений не уменьшаются, кроме смен «было →
      стало», названных в разделе.
    - Фикстура `tests/test_test_integrity_gate.py::EarlyReturnFindingTest::test_early_return_present_in_base_is_not_a_finding`
      меняет в голове утверждение `self.assertTrue(READY)` на
      `self.assertTrue(bool(READY))`, а по новому правилу это находка.
      Фикстура правится так, чтобы правка головы не была сменой
      утверждения. Утверждения самого метода не меняются.
    - Остальные существующие тесты не ослабляются.
17. **Тесты сценариев.** Сценарии критериев приёмки держат приёмочные
    тесты задачи с заявкой «Ловит мутацию» (долгоживущая группа в
    `tests/`, ADR-0020). Отдельного повтора тех же свойств в `tests/`
    SPEC не заказывает.

## Критерии приёмки

AC-1. `python3 scripts/guard.py` на SPEC с годным разделом «Меняемое поведение» (одна и две пары «было → стало», имя `путь::Класс::метод`, ссылка на существующий пункт «Требования») завершается без нарушений. На SPEC без раздела вывод тот же, что до задачи.

AC-2. `python3 scripts/guard.py` на SPEC с негодной строкой раздела завершается ненулевым кодом, а нарушение называет строку. Случаи нарушения: путь не под `tests/`, имя без класса, пустое «было», пустое «стало», нет «(требование N)», номер N отсутствует в «Требования», метод повторён. Тот же SPEC отклоняется на `advance` из `spec_writing`.

AC-3. `approve` на `spec_gate` при разделе с методом, которого нет в `main` репозитория задачи (нет метода либо нет файла), даёт мягкий отказ «approve отклонён» с именем метода. Задача остаётся в `spec_gate`. Молчание git при чтении `main` даёт тот же мягкий отказ с причиной.

AC-4. Успешный `approve` на `spec_gate` при годном разделе пишет одну запись журнала «объявлена смена поведения тестов», которая называет каждый метод, его пары «было → стало» и номер требования. `approve` SPEC без раздела такой записи не пишет и проходит как до задачи.

AC-5. Функция различения в `scripts/guard.py` для метода, сохранившего имя, даёт следующие исходы:
- смена только литерала при том же числе и виде утверждений — «смена ожидания» с фактической парой;
- `assertEqual` → `assertIn`, `assertEqual` → `assertTrue`, `assertEqual` → `assertIsNotNone`, удалённое утверждение, литерал → вызов — «ослабление/иная смена»;
- только добавленное или только переставленное утверждение — «смены нет».

AC-6. Переход `in_dev -> verifying` проходит, когда в методе из объявленного перечня сменён литерал, пара совпадает с объявленной, и выполнены условия строгости, двустороннего прогона и храповика. Запись «утверждения тестов: исход рубежа» называет метод с исходом «смена ожидания по SPEC (требование N)».

AC-7. Та же смена литерала в методе вне объявленного перечня отказывает переходу действием «переход отклонён: гейт неослабления тестов». Detail называет файл, `Класс::метод` и причину «смена вне раздела «Меняемое поведение»». Гейт мержа на том же диффе переводит задачу в `escalated`.

AC-8. `assertEqual` → `assertIn`, `assertEqual` → `assertTrue` и удаление утверждения отказывают переходу даже в методе из объявленного перечня; гейт мержа эскалирует.

AC-9. Мандат «Ослабление тестов разрешено: …» снимает находки AC-7 и AC-8, если его элемент — путь файла, `путь::Класс` или `путь::Класс::метод`. Переход проходит, а журнал «ослабление тестов разрешено мандатом Оператора» называет находку. Мандат на другой метод того же файла находку не снимает.

AC-10. Смена литерала в объявленном методе, фактическая пара которой не совпадает с объявленной «было → стало», отказывает переходу. Detail называет фактическую пару.

AC-11. Если раздел SPEC правится после `approve` на `spec_gate`, исход рубежа не меняется: он определяется перечнем записи «объявлена смена поведения тестов».

AC-12. Для канареечной задачи и задачи внешнего target на диффе AC-7 переход проходит как до задачи. Записей «утверждения тестов: исход рубежа» и «двусторонний прогон пройден» нет.

AC-13. На диффе с изменёнными утверждениями оба рубежа пишут прежнюю запись «изменены утверждения тестов (наблюдение)» в прежней форме. Запись «утверждения тестов: исход рубежа» называет каждый изменённый метод и исход по нему.

AC-14. Раздел ревью-пакета «Изменённые утверждения тестов» по каждому методу несёт прежнюю строку наблюдения, исход рубежа и, для объявленного метода, строку «было → стало (требование N)». Текста «переход и мерж от них не зависят» в пакете нет, есть текст замены из требования 13.

AC-15. В объявленном методе с совпавшей парой отказывают переходу:
- `delta` больше прежнего;
- `places` меньше прежнего у `assertAlmostEqual`;
- `rel`/`abs` у `pytest.approx` больше прежнего.

Detail называет признак ослабления допуска.

AC-16. В объявленном методе с совпавшей парой отказывают переходу, и detail называет признак:
- регулярное выражение `assertRegex`/`assertRaisesRegex` потеряло якорь `^`, `$`, `\A` или `\Z`;
- в регулярное выражение добавлено `.*` или `.+`.

AC-17. Если в объявленном методе ожидаемый литерал заменён вызовом либо атрибутом импортированного модуля, переход отклоняется с признаком «литерал заменён вычисленным значением».

AC-18. В объявленном методе с совпавшей парой отказывают переходу: строка `assertIn` заменена своей собственной подстрокой; граница `assertGreater` сдвинута вниз. Отказывает и смена константы на позиции, которую правило не оценивает (аргумент вызова внутри `assertTrue(...)`), с признаком «правило не умеет оценить строгость».

AC-19. Двусторонний прогон: если новая версия метода зелёная на дереве базы, переход отклоняется с именем метода и стороной «новая версия на базе».

AC-20. Двусторонний прогон: если старая версия метода зелёная на дереве головы ветки, переход отклоняется с именем метода и стороной «старая версия на ветке».

AC-21. Двусторонний прогон: если новая версия на базе падает ошибкой импорта, ошибкой `setUp` или иным исключением фазы call (не `AssertionError`), переход отклоняется с причиной «не доказательство» и названным видом ошибки.

AC-22. Двусторонний прогон: таймаут прогона pytest отклоняет переход с причиной «таймаут». Сбой git при заведении временного дерева тоже отклоняет переход и называет причину.

AC-23. Временные деревья убраны при каждом исходе прогона: пройден, отказ AC-19…AC-22, исключение. Это значит, что после рубежа `git worktree list` клона проекта задачи не несёт деревьев рубежа, а их временные каталоги не существуют.

AC-24. Двусторонний прогон, где обе стороны падают на утверждении, пропускает переход и пишет запись «двусторонний прогон пройден» с sha головы ветки и именем метода. Прогон не выполняется (ни git-деревьев, ни pytest, ни записи) в двух случаях: у задачи нет записи «объявлена смена поведения тестов»; сравнение дало непокрытую находку.

AC-25. Гейт мержа не запускает pytest. Метод исхода 7а проходит гейт мержа без эскалации, если есть запись «двусторонний прогон пройден» для текущей головы ветки. Если голова ветки отличается от записанной, задача уходит в `escalated` с находкой, которая называет метод.

AC-26. Храповик: если убыль числа методов либо утверждений по `tests/` — единственная находка прохода и мандата нет, переход отклоняется. Detail называет числа «было → стало» и файл с убылью. Мандат на этот файл снимает находку, и переход проходит.

AC-27. Раздел ревью-пакета для метода исхода 7а называет итог двустороннего прогона для текущей головы: «пройден» при записи AC-24, иначе «не записан».

AC-28. `docs/codebase-map.md` совпадает с выводом `python3 scripts/codebase_map.py` на голове ветки. Строки «Назначение» модулей механики (требование 14) называют: «Меняемое поведение», «смена ожидания», «ослабление», «двусторонний прогон», «сверка с объявленным», «строгость», «храповик».

AC-29. Приложения PLAN к `templates/SPEC.md`, `skills/spec-authoring.md`, `skills/coding-standards.md`, `skills/review-checklist.md`, `docs/invariants.md`, `tests/test_invariants.py` несут содержание требования 15, а `git apply --check` каждого на чистом дереве проходит. Сторож инварианта 38 в приложении к `tests/test_invariants.py` отказывает переходу на смене утверждения вне объявленного перечня и пропускает её с мандатом.

## Оценка объёма и деление

Сработали сигналы:
- 29 критериев приёмки (порог `SPLIT_SIGNAL_AC_COUNT` = 10);
- зона задевает механизм, на который опирается запись `docs/invariants.md`
  (инвариант 38).

Механику несут файлы `orchestrator/advance_gates/test_integrity.py`,
`orchestrator/fsm.py`, `orchestrator/review.py`, `scripts/guard.py`,
модуль двустороннего прогона и `orchestrator/config.py`; к ним добавляются
тесты, карта и шесть приложений. По калибровке (больше 15 критериев) это
класс ~$85 либо деление.

**Обоснование монолита** (решение Оператора 05.10: задача остаётся одной,
без деления).
- Потолок задачи задан Оператором выше калибровочного уровня: объём
  одной задачи покрыт бюджетом без нарезки.
- Деление перевело бы эту задачу-родителя в `killed`. Тогда сломалась бы
  зависимость мержа задачи 01M45FJVGQT1K0P8HDEXZX6HS7 (этап 3 ADR-0021,
  часть 1): её `merge_after` называет эту задачу, а убитая задача в main
  не попадёт никогда.
