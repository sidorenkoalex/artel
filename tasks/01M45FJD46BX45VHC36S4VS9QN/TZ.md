# ТЗ: Смена поведения в существующих тестах без эскалации, ослабление — по-прежнему мандатом

Источник: бэклог, строка «Смена поведения в существующих тестах без
эскалации, ослабление — по-прежнему мандатом» (приоритет 1, $70; рядом с
этапом 3 ADR-0021). Сегодня любая правка утверждения существующего
тестового метода, даже прямо вызванная требованием SPEC, проходит через
эскалацию разработчика и ответ Оператора мандатом. Прецеденты 05.10:
задача 01M446WEVJXARR5CDED8RE9CCR (шесть методов `test_auto_cycle`,
ожидание `calls == 2` → `calls == 1`, эскалация 04.10 22:17) и задача
01M44EP4Q927DJXVX9YMMZ0B7V (семь методов, текст рецепта отказа, эскалация
05.10 02:06) — в обоих случаях только смена ожидаемого значения, простой
по 30–40 минут на ответ Оператора. Решение Оператора 05.10: смена
ожидания, объявленная в SPEC и подтверждённая машинной проверкой,
проходит без эскалации; ослабление — по-прежнему только мандатом.
Деление на две задачи (пункты 1, 2, 4, 7 и пункты 3, 5, 6 бэклога) — на
усмотрение аналитика по сигналам объёма.

Требуется:
1. SPEC получает необязательный раздел «Меняемое поведение»: перечень
   существующих тестовых методов `tests/`, чьи ожидания меняются по
   требованиям задачи, каждый в виде `tests/<файл>.py::<Класс>::<метод>`
   с конкретными значениями «было → стало» и ссылкой на требование
   SPEC. Точный формат строки задаёт SPEC; `scripts/guard.py` проверяет
   форму раздела (имя метода в квалифицированном виде, непустые «было»
   и «стало», ссылка на требование) на переходе `spec_writing ->
   spec_gate`. Approve гейта SPEC дополнительно проверяет, что каждый
   названный метод существует в базе (main) под этим именем, и пишет
   журнал задачи с перечнем объявленных смен — это и есть решение
   Оператора о смене поведения. Отказ — мягкий, тем же способом, что
   нынешние отказы гейта SPEC. SPEC без раздела ведёт себя как сегодня.
2. Узел `test_integrity` по нормальной форме `guard.test_assertions`
   различает в методе, сохранившем имя, СМЕНУ ОЖИДАНИЯ (то же число и
   тот же вид утверждений; меняются только ожидаемые значения — SPEC
   задаёт точное правило, например равенство нормальных форм при
   замене литералов-констант меткой) и ОСЛАБЛЕНИЕ (утверждений меньше;
   вид шире — `assertEqual` → `assertIn`/`assertTrue`/`assertIsNotNone`;
   удаление; пропуск; любой иной сдвиг, который правило смены ожидания
   не признало). Правило живёт в `scripts/guard.py` рядом с
   `changed_test_assertions`, а не копией в пульте. Исход:
   а) смена ожидания в методе из раздела «Меняемое поведение» —
      проходит с записью журнала, только если выполнены пп. 3–6;
   б) ослабление (в любом методе) и любая смена утверждений метода вне
      раздела — находка узла отказа: отказ перехода `in_dev ->
      verifying` и эскалация на гейте мержа до мандата «Ослабление
      тестов разрешено: …», тем же покрытием `Finding.mandate_elements`,
      что сегодня. Мандат по-прежнему снимает любую находку.
   Канареечная задача и внешний target — без изменений (гейт не
   проверяется). Нынешние записи наблюдения либо остаются, либо
   заменяются записями нового рубежа — решает SPEC, но журнал обязан
   называть каждый изменённый метод и исход по нему.
3. Двусторонний прогон каждого метода из п. 2а на рубеже `in_dev ->
   verifying` (место в маршруте — рядом с гейтом неослабления; SPEC
   обосновывает порядок относительно соседних гейтов, не ломая порядок
   существующих отказов): новая версия теста на коде базы сравнения
   обязана упасть (тест различает поведение), старая версия теста на
   коде ветки обязана упасть (поведение действительно сменилось).
   Зелёный любой из двух — отказ с именем метода и стороной. Падение
   засчитывается, только если упал сам метод на утверждении; ошибка
   сборки, импорта или подготовки (`setUp`) — не доказательство, а
   отказ с названной причиной (SPEC задаёт, как это различается по
   выводу pytest). Прогон — во временных деревьях вне рабочей копии
   задачи (образец `_scratch_worktree`), той же командой и окружением,
   что `acceptance._pytest_command`/`_pytest_env`, с таймаутом; деревья
   и каталоги убираются при любом исходе, включая таймаут и исключение.
   Таймаут и молчание git — отказ (fail-closed), не пропуск. На гейте
   мержа двусторонний прогон не повторяется; SPEC решает, как рубеж
   мержа узнаёт, что прогон на переходе пройден для той же головы
   ветки (например журнал с sha), либо обосновывает другое.
4. Сверка с объявленным: фактическая смена значений в утверждениях
   метода совпадает с «было → стало» раздела SPEC (SPEC задаёт правило
   сопоставления значения со строкой SPEC). Любая иная правка
   утверждений в методе — находка п. 2б (отказ до мандата).
5. Строгость нового ожидания не ниже старого; ослаблением (находка п.
   2б) считаются: расширение допуска (`delta`, `places` больше прежнего
   либо появились), расширение регулярного выражения (потеря якорей `^`/
   `$`/`\A`/`\Z`, замена конкретного текста на `.*`/`.+`), замена
   литерала значением, вычисленным проверяемым кодом (ожидаемый аргумент
   был константой, стал вызовом или атрибутом импортированного модуля).
   Точный перечень признаков и их проверку задаёт SPEC; признак, который
   правило не умеет оценить, — находка, не пропуск.
6. Храповик: общее число тестовых методов (`guard.qualified_test_methods`)
   и утверждений (`guard.test_assertions`) по `tests/**/*.py` в голове
   ветки не меньше, чем в базе сравнения; убыль без мандата — находка
   п. 2б с названными числами «было → стало». SPEC решает, как мандат
   покрывает убыль (элемент мандата на файл либо метод, которые дали
   убыль).
7. Ревьювер сверяет каждое изменённое ожидание с требованием SPEC:
   раздел ревью-пакета (`review._changed_assertions_part`) называет по
   каждому методу исход рубежа (смена ожидания по разделу SPEC с итогом
   двустороннего прогона, покрыто мандатом, находка) и строку «было →
   стало» из SPEC; текст «переход и мерж от них не зависят» заменяется
   соответствующим новому поведению.
8. `docs/codebase-map.md` описывает раздел SPEC «Меняемое поведение»,
   различение смены ожидания и ослабления, двусторонний прогон, сверку
   с объявленным, правило строгости и храповик.
9. Тесты в `tests/` с заявками «Ловит мутацию» на пп. 1–7, в том числе:
   форма раздела SPEC — годная и негодная строка; approve гейта SPEC
   отказывает на методе, которого нет в базе; смена литерала в методе
   из раздела при пройденном прогоне — переход проходит с записью
   журнала; та же смена в методе вне раздела — отказ; `assertEqual` →
   `assertIn`/`assertTrue` и удаление утверждения — отказ даже в методе
   из раздела; мандат снимает такую находку; двусторонний прогон: новая
   версия зелёная на базе — отказ, старая версия зелёная на ветке —
   отказ, падение на ошибке импорта — отказ, таймаут — отказ, временные
   деревья убраны при каждом исходе; смена значения, не совпавшая с
   «было → стало», — отказ; расширение `delta`/`places`, потеря якоря
   регулярного выражения, литерал → вызов проверяемого кода — отказ;
   убыль числа методов или утверждений без мандата — отказ, с мандатом —
