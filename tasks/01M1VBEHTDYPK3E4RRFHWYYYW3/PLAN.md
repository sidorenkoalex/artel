# PLAN: команда `note` — строка в копилку/бэклог изолированным коммитом от origin/main

## Подход
Новый модуль `orchestrator/notes.py` несёт всю механику: он не трогает
рабочую копию `config.ROOT` вовсе (AC-5) — правка `docs/backlog.md`
происходит в отдельном постоянном git-репозитории `config.ROOT/.artel/
notes-work` (заводится `git init` лениво при первом обращении, живёт
рядом с `.artel/state.db`/`.artel/venv`, вне поля зрения git пульта —
`.artel/` целиком в `.gitignore`), у которого remote `origin` каждый
раз синхронизируется с `origin` главной копии (`gitcmd.git("remote",
"get-url", "origin")` в `config.ROOT`) — так `break_origin_remote`/
`restore_origin_remote` песочницы (правка `origin` ГЛАВНОЙ копии)
доходят до нашей копии автоматически, без своего механизма слежения.

Каждая попытка записи (вставка либо `--append`) — цикл до 3 итераций:
fetch `origin/<MAIN_BRANCH>` в `notes-work`, `checkout -B <MAIN_BRANCH>
FETCH_HEAD` (отбрасывает результат прошлой неудачной попытки, тело
цикла ничего не знает о предыдущих итерациях), пересчитать правку
ЗАНОВО от свежего содержимого (валидация числа колонок/уникальности
ключа — здесь же, `sys.exit` до первой попытки push, если решение
неоднозначно или колонки не сходятся), закоммитить, запушить. Успех —
sha в журнал (`store.journal`, `task_id=None`, `actor="operator"`).
Отказ push после 3 попыток или сетевой отказ fetch (не расходует
попытки push — это другой класс отказа) — коммит не потерян: параметры
операции (не сырой git-объект — воспроизводимы детерминированно из
текущего содержимого раздела) сериализуются JSON-файлом в
`config.ROOT/.artel/notes-pending/<ts>-<uuid8>.json`. `notes.pending_
notes()` читает эти файлы — единственная точка, которую опрашивает
`doctor.check_pending_notes()` и приёмочные тесты, не заглядывая внутрь
конкретного хранилища (SPEC разрешает `.artel/notes-pending/` ИЛИ ветку
`notes-pending` — выбран первый вариант, он проще для повторного
воспроизведения правки на свежем fetch).

Любой вызов `cmd_note` (включая `--flush`) сначала оппортунистически
пытается допушить всё из `pending_notes()` (требование 7/AC-8), затем —
если это не чистый `--flush` — выполняет запрошенную вставку/`--append`
тем же циклом. Опережающий flush обёрнут в `try/except SystemExit` на
каждый файл отдельно: устаревшая удержанная заметка, переставшая
проходить свою же валидацию (структура раздела изменилась), не должна
рушить ТЕКУЩИЙ вызов — файл остаётся висеть, доктор продолжит
предупреждать, а новая заметка всё равно уйдёт.

Разбор разделов и колонок — без захардкоженных чисел (требование 2):
заголовок раздела ищется точным совпадением строки (`## Копилка` и т.д.,
`SECTION_HEADINGS`), число колонок и позиция вставки (сразу после
строки-разделителя) читаются из фактической таблицы файла построчным
разбором. `--append` ищет ключ-подстроку ПО ВСЕМ трём разделам сразу
(флага раздела у `--append` нет ни в ТЗ, ни в тестах) и требует ровно
одного совпадения среди строк данных (не шапки/разделителя).

`orchestrator/doctor.py` получает `check_pending_notes()` (без `conn`,
как `check_root_pin`/`check_canary_pool_drift`) — `warn` при непустом
`notes.pending_notes()`, регистрируется в `all_checks`. `docs/operator-
session.md` получает правку абзаца «Копилка и бэклог пополняются»:
называет `note` исполняющей правило (упоминаний scratch-worktree в
файле и так не было — самостоятельно проверено, `assertNotIn` пройдёт
без правки этой части).

Решение Оператора 06.09 на гейте SPEC приняло монолит (разрез отменён,
мотив снят мержем 01M1TT9BPB) — эта задача закрывает SPEC целиком,
включая часть, ранее размеченную как «часть 2» (doctor + документ).

## Влияние на систему
Новый модуль не переиспользует `gitcmd.git()` для операций над
`config.ROOT` в смысле мутации — только `remote get-url` (чтение) и
чтение головы через `gitcmd.head_sha`/`in_repo` над ОТДЕЛЬНЫМ
репозиторием (`notes-work`), поэтому пин HEAD главной копии (ADR-0013)
не затрагивается ни при одном исходе (AC-5, AC-10 — HEAD `config.ROOT`
не входит в зону этой команды вовсе).

`.artel/notes-work` и `.artel/notes-pending/` — новые подкаталоги
`.artel/`, уже целиком в `.gitignore`; не пересекаются с существующими
путями (`state.db`, `venv`, `projects`, `worktrees`, `logs`) ни по
имени, ни по семантике. Путь читается функцией через `config.ROOT`
динамически на каждый вызов (не кэшируется модульной константой при
импорте) — тот же приём, что и у остальных модулей, которым нужна
корректная работа под патчем `config.ROOT` в песочнице (сознательно НЕ
добавлял `NOTES_PENDING_DIR`/`NOTES_WORK_DIR` в `config.py` как
предвычисленные константы: `tests/sandbox.ALL_CONFIG_ATTRS` патчит
только перечисленный список атрибутов по имени, новая константа,
вычисленная в `config.py` один раz при импорте, не подхватила бы патч
`config.ROOT` и НЕ ТУДА писала бы в песочнице — пришлось бы ещё и
трогать `tests/sandbox.py`, расширяя список патчей ради одной новой
задачи; функция, читающая `config.ROOT` при каждом вызове, не несёт
этой ловушки и не требует правки общего тестового инфраструктурного
файла).

`store.journal` с `task_id=None` — уже поддерживаемый код (`task_target`
деградирует до `config.DEFAULT_TARGET` на `NULL`), формат записи
проверен приёмочным тестом AC-10 напрямую через `steps WHERE task_id IS
NULL`.

Существующие тесты `tests/test_doctor.py` не меняют поведения других
проверок — новая добавляется в конец `all_checks`, не меняет порядок
существующих вызовов.

Откат: модуль `notes.py`, запись в диспетчере `artel.py` и проверка
doctor — независимые, обратимые правки (revert коммита); правка
`docs/operator-session.md` — текстовая, обратимая тем же путём.

## Риски
- `--append` ищет совпадение по всем трём разделам сразу (SPEC не даёт
  `--append` позиционного раздела) — если в будущем понадобится сузить
  поиск одним разделом, это отдельное расширение сигнатуры, не входит
  в эту задачу («Не входит» SPEC про `--task` — по аналогии, раздел для
  `--append` тоже не специфицирован сверх приёма ключа).
- Постоянный (не одноразовый) рабочий репозиторий `notes-work`
  переживает между вызовами `note` в проде (не только внутри одного
  тестового процесса) — это сознательный выбор простоты и скорости
  (не полное `clone` истории на каждый вызов), а не случайное
  побочное состояние: каждый цикл начинается с `fetch`+`checkout -B`,
  так что устаревшее содержимое `notes-work` никогда не влияет на
  результат.
