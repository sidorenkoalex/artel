# QUESTIONS: Аудит SPEC — шаг spec_auditor между сдачей SPEC и spec_gate (ADR-0022)

## Вопросы

Сверка ТЗ с кодом (ветка задачи, база de280309) показала: требования 1, 2,
6, 7 нельзя выполнить в границах «Зоны» / «Только чтение» ТЗ — нужные места
лежат в файлах только для чтения или вне зон. Вопросы 1–3 блокируют SPEC
целиком, 4–5 определяют отдельные требования.

1. **Агентское состояние аудита и `tests/test_invariants.py` (только
   чтение).** Роль шага резолвит `runner.step_role`
   (`orchestrator/runner.py:130`, только чтение) через `config.STATE_ROLE`;
   иного пути запустить агента новой роли, кроме нового ключа
   `STATE_ROLE` (например, состояние `spec_audit`), без правки `runner.py`
   нет (особый случай `analyst` в `runner.py:131–149` привязан к
   `spec_writing`). Новый ключ краснит
   `tests/test_invariants.py::FsmStatesCoverTheCodeTest::test_every_working_state_is_swept`
   (`tests/test_invariants.py:431`: `STATE_ROLE ⊆ FSM_STATES`, кортеж
   `FSM_STATES` — `tests/test_invariants.py:75`), пока в `FSM_STATES` не
   добавлено новое состояние. Дополнение кортежа — усиление (свипы
   инвариантов охватывают ещё одно состояние), не ослабление, но файл в ТЗ
   — «только чтение».
   — варианты:
   A) снять «только чтение» с `tests/test_invariants.py` в части `FSM_STATES`
      (добавить новое состояние в кортеж) — что ломается: ничего; что
      ослабляется: ничего, свипы шире; цена: строка теста; решение —
      Оператора (файл инвариантов);
   B) снять «только чтение» с `orchestrator/runner.py` (резолв роли аудита в
      `step_role` по образцу `analyst`, без ключа `STATE_ROLE`) — что
      ломается: ничего в тестах; что ослабляется: новое агентское состояние
      выпадает из свипов `test_invariants.py` (`AgentRunsOnlyFromRunTest`,
      `MergeOnlyFromMergeGateTest` и др. идут по `FSM_STATES`) — инварианты
      для него не проверяются; цена: правка `runner.py`; решение —
      Оператора;
   C) оставить оба файла только для чтения — требование 1 невыполнимо,
      задача не может быть сдана.
   — дефолт: A — единственный вариант без ослабления; `runner.py` остаётся
   только для чтения.

2. **Распространяется ли аудит на SPEC без аналитика (прежний флоу: нет
   `TZ.md`, SPEC пишет Оператор).** ТЗ п.1: «каждая задача после сдачи SPEC
   аналитиком … без исключений по размеру задачи и проекту»; ADR-0022 п.3:
   «у каждой задачи, без исключений». Прежний флоу (`runner.py:98–104`,
   `roles.yaml:12–15`) аналитика не имеет. От ответа зависит
   `tests/test_invariants.py::FreshVerdictGuardsAcceptanceTest::test_every_return_to_dev_requires_a_new_verdict`
   (`tests/test_invariants.py:830–834`: SPEC ready без `TZ.md` → `advance`
   → `spec_gate`) и около 30 файлов `tests/`, где задача без `TZ.md`
   ожидает `spec_writing → spec_gate` одним `advance` (только
   `tests/test_analyst_role.py` из них несёт `TZ.md`).
   — варианты:
   A) аудит только для задач с `TZ.md` (флоу аналитика) — что ломается:
      ничего из существующих тестов; что ослабляется: SPEC Оператора идёт
      на гейт без независимой проверки (как сегодня); цена: нет; решение —
      Оператора (ADR-0022 п.3 читается шире);
   B) аудит для любой задачи — что ломается: ожидание `spec_gate` после
      `advance` в ~30 файлах `tests/`, включая `test_invariants.py` (только
      чтение — нужен ответ на вопрос 1 и снятие запрета на этот метод);
      каждый метод — строкой «Меняемое поведение» (инвариант 38); что
      ослабляется: ничего, но объём правки тестов вырастает в разы и
      прямо давит на рамку $85; цена: +1 итерация разработчика по оценке;
      решение — Оператора.
   — дефолт: A — формулировка ТЗ «после сдачи SPEC аналитиком» и
   отсутствие аналитика в прежнем флоу; расширение на флоу Оператора —
   отдельной задачей, если нужно.

3. **Файлы вне зон, без которых требования не выполнимы.** Ни в «Зоны», ни
   в «Только чтение» ТЗ не названы:
   - `orchestrator/role_prompt.py` — миссия роли собирается по имени роли
     (`role_prompt.py:33`, `:56`); без правки аудитор получит пустую миссию
     (требование 2, бриф аудитора);
   - `orchestrator/artel.py` — разбор флага `approve` (`--no-answer`:
     `artel.py:1647–1661`, `:1820`) и регистрация команд CLI; требование 6
     (явный флаг на `approve` при `fail`) и требование 7 (команда
     повторного аудита) без него не выполнимы;
   - `orchestrator/models.py` — см. вопрос 4 (только при варианте A там).
   — варианты: A) добавить в зоны `orchestrator/role_prompt.py` и
   `orchestrator/artel.py` (и `orchestrator/models.py` при 4A) — что
   ломается: ничего; что ослабляется: ничего; цена: +2–3 файла зоны, уже
   внутри класса бюджета ~$85; решение — Оператора (зоны ТЗ); B) не
   добавлять — требования 2 (миссия), 6, 7 выпадают из SPEC.
   — дефолт: A.

4. **«Модель по умолчанию — та же, что у аналитика» внутри набора
   моделей.** Наборы `model_sets.yaml` (только чтение) задают модель по
   ролям: в `codex-all` (`model_sets.yaml:17–21`) `analyst:
   gpt-5.6-terra`; записи `spec_auditor` в наборе нет, и резолв по ярусу
   `strong` (`models.resolve_role`, `orchestrator/models.py:599–624`) даст
   аудитору модель яруса, а не модель аналитика набора. Пары «роль —
   модель» (`model_sets.yaml` `pairs:`) для `spec_auditor` тоже нет.
   — варианты:
   A) роль `spec_auditor` без своей записи в наборе наследует модель и
      провайдера аналитика этого набора (правка `orchestrator/models.py`,
      вопрос 3) — что ломается: ничего; что ослабляется: допуск пар —
      аудитор идёт на модели, допущенной для `analyst`, не для
      `spec_auditor`; цена: правка резолвера; решение — Оператора;
   B) «та же модель» — только по ярусу (`model_tier: strong` в
      `roles.yaml`); в наборе с иной моделью аналитика аудитор идёт на
      модели яруса, пока Оператор `doc-commit`ом не добавит
      `spec_auditor` в набор — что ломается: ничего; что ослабляется:
      ничего; цена: нет; решение — Оператора (правка наборов).
   — дефолт: B — без кода вне зон и без обхода допуска пар; ADR-0022 п.6
   прямо отдаёт смену модели аудитора наборам моделей.

5. **Деление задачи.** Сработают сигналы объёма: файлов зоны ≥ 5 (≥ 8 с
   вопросом 3), критериев приёмки ≥ 10, `budget_usd` ≥ $30. ADR-0022 п.2
   плана: «деление решается на гейте SPEC». Чтобы SPEC сразу нёс нужную
   форму:
   — варианты:
   A) монолит в рамке $85 — обоснование: шаг аудита без возврата по `fail`
      и без вердикта на гейте не самостоятелен; что ослабляется: ничего;
      цена: одна крупная задача, риск третьей итерации ревью сверх рамки;
   B) нарезка на 2 части: 1) механика — состояние, роль, бриф, guard
      `SPEC-AUDIT.md`, глубина по сигналам, возврат по `fail`, вердикт на
      `show`/`status`, флаг `approve`, команда повторного аудита,
      приложения `roles.yaml`/`templates/SPEC-AUDIT.md`/`skills/spec-audit.md`;
      2) матрица последствий в QUESTIONS (`templates/QUESTIONS.md`,
      `skills/spec-authoring.md`, требование 9) — независимая часть только
      на защищённых путях; цена: +~$25 на вторую задачу, но меньше риск
      рамки первой;
   решение — Оператора.
   — дефолт: B — требование 9 не связано с машиной состояний и мержимо
   отдельно; SPEC оформит его разделом «## Деление».
