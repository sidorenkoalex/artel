# SPEC: GitLab В1.2: гейт неослабления по исходам из отчётов задания CI

## Контекст
Часть 2 из 2 задачи 01M5XX9PW3K206Q3EKQCT649QF (GitLab В1): её требования
5, 6, 7 и критерии AC-14…AC-24; разделы «Контекст», «Матрица неослабления»
и «Не входит» SPEC родителя действуют и здесь (ответы Оператора ANSWER-1,
ANSWER-2, ANSWER-3 родителя). ADR-0026 п. 6, ADR-0029 п. 9, инвариант 41
(«неизвестный итог не зелёный»).

Сейчас гейт неослабления по исходам (`advance_gates/outcome_integrity.py`)
берёт исходы базы и головы только из локальных прогонов выписок
(`_checkouts` `:769`, `_full_runs`/`_full_run` `:388`/`:395`, `_rerun`
`:407`, `_prior_checkout` `:672`). Задача переводит гейт для компонента
`full_suite: ci` (поле профиля из части 1, 01M5XZSKK8GZTECA2KWAFHE029) на
отчёты задания `ci_job` — только в точке входа гейта мержа
`merge_gate_escalates` (`:1153`, вызов через `_outcome_integrity_merge_gate`,
`fsm_merge_gate.py:1380-1390`), в том числе у проектов с `target-human`. На
`in_dev → verifying` (`_outcome_integrity_gate_refuses`, `:1143`, вызов
`fsm_advance.py:843`) голова ещё не сжата и не отправлена на origin
(`fsm_advance.py:855-856`, `:868`), конвейера у неё нет, — там гейт судит по
локальным выпискам, как сейчас (ANSWER-3, вопрос 1).

`forge.TestReport` — `<classname>::<name>` → статус GitLab, без атрибута
`file`; отсюда правило перевода отчёта в `CaseResult`
(`reporters/outcome.py:43`) с идентификатором `project_profile.test_id`
(`project_profile.py:623`). У проекта с вливанием MR перебазированием
дерево коммита слияния в базе совпадает с деревом второго родителя —
перебазированной головы влитого MR, у которой конвейер с отчётом есть, —
отсюда поиск отчёта базы у родителя с тем же деревом.

Поля компонента `full_suite`/`ci_job` гейт читает из `project_profile`
части 1 (01M5XZSKK8GZTECA2KWAFHE029); код этой задачи начинается после
влития части 1 в main — порядок `start_after` поставлен Оператором.

## Требования
Для компонента с `full_suite: ci`; сигнатуры `_outcome_integrity_gate_refuses`
и `merge_gate_escalates` не меняются.

1. **Источник исходов на гейте мержа.** На гейте мержа
   (`merge_gate_escalates`) исходы головы и базы берутся из отчётов задания
   `ci_job` (`forge.job_test_report`), а не из локальных прогонов выписок:
   выписок базы и головы (`_checkouts`), перепрогона красных (`_rerun`) и
   третьей выписки (`_prior_checkout`) нет. На переходе `in_dev → verifying`
   гейт компонента `ci` судит по локальным выпискам базы и головы, как
   сейчас, и отчётов задания CI не читает.

2. **Годность отчёта стороны** (голова и база). Отчёт задания `ci_job` годен,
   только если задание завершено со статусом `success`, либо со статусом
   `failed` без права падать (`allow_failure` ложно) — тогда исходы берутся
   из отчёта; и отчёт разобран (`TestReport.outcomes` не `None`). Задание
   идёт, не начато, отменено (`canceled`), ручное (`manual`), пропущено, в
   ином статусе (в том числе `failed` с правом падать) или его отчёт не
   разобран — отчёт стороны не годен.

3. **Отчёт головы** — из конвейера ровно sha головы; отчёт родителя головы,
   даже с тем же деревом, не подставляется. Нет годного отчёта
   головы — сбой подготовки: запись `MERGE_PREPARE_ACTION` с именованной
   причиной, задача остаётся на `merge_gate`, отправки нет; не пропуск
   гейта и не эскалация.

4. **Отчёт базы** — из конвейера коммита точки ответвления (та же точка,
   что `_diff_base` `:785` / `_merge_base_of` `:793`). Нет у него задания
   `ci_job` с годным отчётом — из конвейера родителя точки ответвления
   (`git rev-list --parents -n1 <точка>`), дерево которого совпадает с
   деревом точки ответвления (`git rev-parse <c>^{tree}`). Поиск — только
   чтением (git, чтение `forge`), без поиска MR через хостинг, без записи в
   хостинг и в репозиторий.
   - Найден у родителя — запись журнала «отчёт базы: задание <job id>
     коммита <sha> (дерево совпадает с <точка>)», где <job id> — наибольший
     `id` попыток `ci_job` из `forge.pipeline_status(<sha>).jobs`; гейт
     сравнивает исходы по этому отчёту.
   - Не найден ни у точки ответвления, ни у родителя того же дерева — сбой
     подготовки с причиной «нет отчёта базы» (запись `MERGE_PREPARE_ACTION`,
     задача остаётся на `merge_gate`, отправки нет), не пропуск гейта и не
     эскалация.

5. **Находки сравнения.** Тест, зелёный в отчёте базы (`PASS_TO_PASS`) и
   красный (`failed`/`error`) в отчёте головы, — находка BROKEN с прежним
   действием отказа гейта мержа (`MERGE_REFUSAL_ACTION`, `escalated`). Тест,
   зелёный в базе и отсутствующий в голове, — находка `compare` (`:185`),
   как у локальных исходов.

6. **Утверждённая замена теста** (`_replacement_findings`, `:739`): нет
   записи в отчёте базы — REPLACED_MISSING, запись не зелёная —
   REPLACED_NOT_GREEN, как раньше; иначе — отказ гейта
   (`MERGE_REFUSAL_ACTION`) с причиной «замена теста не проверяема в режиме
   ci», не сбой подготовки.

7. **Доказательство, G3б-2 и запись прохода.** На мерже в режиме `ci`
   доказательство `_proven` (`:897`) не используется: отчёты базы и головы
   читаются и сравниваются заново при каждом прогоне гейта. Находки G3б-2 —
   строгого режима (`_strict_findings`) и «исключение в коде»
   (`_code_exception_findings`) — в режиме `ci` на гейте мержа остаются:
   дифф базы и головы читается git без выписок. Запись `PASSED_ACTION` в
   режиме `ci` несёт ключ компонента: имя компонента, дерево головы
   (`git rev-parse <sha>^{tree}`) и `id` заданий `ci_job` головы и базы,
   отчёты которых сравнивались, — без сумм файлов блокировки. Строка
   доказательства этой записи разбирается прежним разбором `PROOF_LINE`
   (`outcome_integrity.py:88-89`, ключ — без пробельных символов), а ключи
   разных компонентов с одним деревом головы различимы (в ключе — имя
   компонента).

8. **Перевод отчёта `forge` в `CaseResult`.** Каждая запись
   `<classname>::<name>` → статус переводится в `CaseResult` с
   идентификатором схемы `project_profile.test_id`
   (`<компонент>:<путь от корня репозитория>::<полное имя>`):
   - ключ делится на `classname` и `name` по первому `::`;
   - `classname` содержит `/` — это путь файла теста от рабочего каталога
     компонента (`workdir`), полное имя — `name`;
   - иначе `classname` — точечный путь: путь файла — самый длинный префикс
     его частей, для которого `<части через '/'>.py` есть файлом в дереве
     коммита отчёта под рабочим каталогом компонента (чтение дерева git, без
     выписки); остаток `classname` за модулем — класс, точки в нём
     заменяются на `::`; полное имя — `<класс>::<name>`, без класса — `name`;
   - путь от `workdir` приводится к пути от корня репозитория так же, как у
     локального разбора JUnit (`_root_path`, `reporters/outcome.py:80`);
   - статус: `success` → `passed`, `failed` → `failed`, `skipped` →
     `skipped`, `error` → `error`;
   - неоднозначный перевод — файл модуля не найден в дереве, статус вне
     перечня, два ключа отчёта дают один идентификатор — даёт для этого
     теста исход «неизвестно»: гейт не считает такой тест зелёным и не
     засчитывает его совпадением с тестом другой стороны;
   - «неизвестно» в отчёте головы при годном отчёте базы, в котором тест
     зелёный, — находка вида BROKEN («сломан правкой»), тот же вид, что у
     красного теста в отчёте головы; мандат Оператора снимает её так же,
     как находку BROKEN (ANSWER-3 родителя);
   - неоднозначная запись в отчёте базы, по которому гейт сравнивает
     (требование 4), — сбой подготовки: запись `MERGE_PREPARE_ACTION` с
     причиной «отчёт базы неоднозначен: <id>», где <id> — идентификатор
     неоднозначной записи (ключ `<classname>::<name>` отчёта, если
     идентификатор не построен); задача остаётся на `merge_gate`, отправки
     нет; тест не выпадает молча из `PASS_TO_PASS`.

9. **Компонент `local` и артель.** Для компонента `local` (явно или по
   умолчанию) и для артели поведение гейта по исходам, записи журнала и
   существующие тесты — прежние.

## Критерии приёмки

AC-1. Гейт по исходам в режиме `ci` на гейте мержа (`merge_gate_escalates`)
на подменённом `forge`: тест, зелёный в отчёте базы и красный (`failed`,
отдельно — `error`) в отчёте головы, — запись `MERGE_REFUSAL_ACTION` с
находкой BROKEN и состояние `escalated`, в том числе когда задание
`ci_job` головы завершено статусом `failed` без права падать с разобранным
отчётом (такой отчёт годен); тест, зелёный в отчёте базы и
отсутствующий в отчёте головы, — запись `MERGE_REFUSAL_ACTION` и
`escalated`; при этом шпион не видит ни выписки базы и головы, ни
перепрогона красных, ни третьей выписки, ни локального прогона.

AC-2. Гейт по исходам в режиме `ci` на гейте мержа: у коммита точки
ответвления нет задания `ci_job` с отчётом, а у его родителя с тем же
деревом отчёт есть — гейт сравнивает исходы по отчёту родителя, в журнале —
запись «отчёт базы: задание <job id> коммита <sha> (дерево совпадает с
<точка>)».

AC-3. Гейт по исходам в режиме `ci` на гейте мержа: годного отчёта нет ни у
точки ответвления, ни у родителя того же дерева — каждый случай отдельно: у
базы нет задания `ci_job`; задание базы идёт (`running`); не начато
(`pending`/`created`); отменено (`canceled`); ручное (`manual`); пропущено
(`skipped`); `failed` с правом падать; отчёт базы не разобран (`None`);
родитель с годным отчётом есть, но его дерево другое — запись
`MERGE_PREPARE_ACTION` с причиной «нет отчёта базы», задача остаётся в
`merge_gate` (не `escalated`), отправки нет. Задание базы `failed` без права
падать с разобранным отчётом — отчёт годен: гейт сравнивает исходы по нему.

AC-4. Гейт по исходам в режиме `ci` на гейте мержа: у головы нет годного
отчёта — каждый случай отдельно: задания `ci_job` нет; задание идёт
(`running`); не начато (`pending`/`created`); отменено (`canceled`); ручное
(`manual`); пропущено (`skipped`); `failed` с правом падать; отчёт головы
`None`; у головы годного отчёта нет, а у родителя головы с тем же деревом
годный отчёт есть (отчёт головы берётся только ровно по sha головы) — гейт
не пропущен: запись `MERGE_PREPARE_ACTION` с именованной
причиной, задача остаётся в `merge_gate` (не `escalated`), отправки нет.

AC-5. Гейт по исходам в режиме `ci` на гейте мержа с утверждённой заменой
теста: заменяемого теста нет в отчёте базы — находка REPLACED_MISSING; тест
в отчёте базы не зелёный — REPLACED_NOT_GREEN; тест в отчёте базы зелёный —
запись `MERGE_REFUSAL_ACTION` с причиной «замена теста не проверяема в
режиме ci», без записи `MERGE_PREPARE_ACTION` и без локального прогона.

AC-6. Гейт по исходам в режиме `ci` на мерже (`merge_gate_escalates`): при
наличии в журнале записи о пройденном гейте с той же головой и базой гейт
заново читает отчёты базы и головы через `forge` (шпион видит оба чтения) и
сравнивает их; локальной выписки нет.

AC-7. Перевод отчёта `forge` в `CaseResult` по правилу требования 8:
`classname` с `/` → путь из `classname`; точечный `classname`, модуль
которого есть файлом `.py` в дереве коммита, → путь модуля и класс с `::`;
для отчёта JUnit без атрибута `file`, с найденным модулем и без повтора
имени идентификатор совпадает с тем, что даёт локальный разбор
(`reporters/outcome.py` `parse_junit`) того же теста компонента; статусы
`success`/`failed`/`skipped`/`error` → `passed`/`failed`/`skipped`/`error`.
Для компонента с непустым `workdir`: модуль точечного `classname` ищется в
дереве под `workdir`, а путь идентификатора — от корня репозитория
(с префиксом `workdir`), как у локального разбора.

AC-8. Неоднозначный перевод — модуль не найден в дереве, статус вне
перечня, два ключа отчёта с одним идентификатором — даёт для этого теста
«неизвестно»: тест, зелёный в отчёте базы и неоднозначный в отчёте головы,
даёт на гейте мержа отказ (`MERGE_REFUSAL_ACTION`) с находкой вида BROKEN,
а не совпадение; мандат Оператора на эту находку как на BROKEN снимает её.

AC-9. Гейт по исходам на переходе `in_dev → verifying`
(`_outcome_integrity_gate_refuses`) для компонента `full_suite: ci` судит,
как сейчас, по локальным выпискам базы и головы: шпион видит выписки и
локальный прогон, чтений `forge.job_result`/`forge.job_test_report`/
`forge.pipeline_status` нет; тест, зелёный на базе и красный на голове
локально, даёт прежний отказ.

AC-10. Гейт по исходам в режиме `ci` на гейте мержа при годных отчётах базы
и головы без расхождений исходов: дифф базы и головы правит существующий
файл тестов компонента без слоя `python-ast` — находка строгого режима
(`_strict_findings`); добавленная строка файла кода компонента несёт маркер
исключения — находка «исключение в коде» (`_code_exception_findings`); в
обоих случаях — отказ гейта мержа, как у локальных исходов, и шпион не
видит выписок.

AC-11. Гейт по исходам в режиме `ci` на гейте мержа, пройденный: запись
`PASSED_ACTION` несёт ключ компонента по дереву головы (`git rev-parse
<sha>^{tree}`) и `id` заданий `ci_job` головы и базы; ключ снимается без
выписки головы и без чтения сумм файлов блокировки.

AC-12. Гейт по исходам в режиме `ci` на гейте мержа: в отчёте базы, по
которому гейт сравнивает, есть неоднозначная запись — каждый случай
отдельно: модуль точечного `classname` не найден в дереве; статус вне
перечня; два ключа отчёта дают один идентификатор — запись
`MERGE_PREPARE_ACTION` с причиной «отчёт базы неоднозначен: <id>», задача
остаётся в `merge_gate` (не `escalated`), отправки нет.

AC-13. Гейт по исходам в режиме `ci` на гейте мержа, пройденный для двух
компонентов `full_suite: ci` с одним деревом головы: строка доказательства
каждой записи `PASSED_ACTION` разбирается `PROOF_LINE`
(`outcome_integrity.proof_fields` не `None`), ключи двух компонентов
различаются и каждый несёт имя своего компонента, дерево головы и `id`
заданий `ci_job` головы и базы.

## Оценка объёма и деление

Сработавшие сигналы: критериев приёмки 13 (порог `SPLIT_SIGNAL_AC_COUNT` =
10); `budget_usd` = 40 (порог `SPLIT_SIGNAL_BUDGET_USD`); зона задевает
механизм инварианта 41 (`docs/invariants.md`, итог «неизвестно» не
зелёный). Файлов зоны — 2 без `tests/` (ниже порога).

Решение — **монолит** (материал для решения Оператора). Задача уже часть 2
деления родителя 01M5XX9PW3K206Q3EKQCT649QF, принятого Оператором на гейте
SPEC 27.10 с рамкой $40. Перевод отчёта в `CaseResult`
(`reporters/outcome.py`, требование 8) без потребителя в гейте ничего не
меняет и проверяется только через него (AC-8 — на гейте мержа), а гейт
режима `ci` (`outcome_integrity.py`, требования 1–7) без перевода не
получает исходов; разрезанная по зонам пара даёт либо мёртвый код, либо
гейт, не способный прочитать отчёт.
