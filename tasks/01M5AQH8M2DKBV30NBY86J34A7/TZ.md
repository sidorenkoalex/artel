Требуется:

1. **Исход прогона наружу.** Функция run модуля acceptance получает необязательный параметр `records` (список, как `file_times`): у профиля с отчётом в него кладутся состояние прогона (`refusal`, `timed_out`, `state` объекта `ReportRun`) и записи `CaseResult`; прежние вызовы, их аргументы и исходы не меняются. Прогон на базе — с `--continue-on-collection-errors` только у команды pytest (`is_pytest_command`) и только в этом гейте. Отчётчик и разборщики отчётов не меняются; общий вердикт `verdict` гейтом не используется.
2. **Гейт честного `FAIL_TO_PASS`** — новый гейт выхода из `tests_writing` после сухого сбора и до перечня сумм, внутри той же уборки планки. Выключенные случаи: профиль вне границы — гейт не создаётся; правило планки не построено — отказ гейта текстом отказа построения; нет ни одного критерия, покрытого тестом (`fsm._tests_writing_ac_state`), — прогона нет, запись журнала «честный FAIL_TO_PASS: критериев с тестом нет»; кодовой ветки ещё нет (`code_diff` — `None`) — прогон одной планки в той же рабочей копии, что сухой сбор. Прогон — планка и свои долгоживущие файлы в рабочей копии кодовой ветки (код базы). «Неизвестно» — только отказ подготовки, таймаут, отчёта нет или он не разобран — отказ с причиной.
3. **Провал проверки.** Для каждого покрытого критерия — записи из файлов планки и своих долгоживущих файлов, у которых последний сегмент полного имени (разделитель « > » у Vitest, «::» у JUnit) несёт метку критерия (`AC-<n>: ` в начале — у файла с меткой; `test_ac<n>_` — у pytest). Записей нет — «AC-n: теста нет в отчёте». Каждая запись — провал проверки: у `pult-vitest` исход `failed` (имя ошибки из `failure_errors`); у `junit-xml` — `failed`, а вид падения начинается с «assert » или с имени из `failure_errors`; пустой `failure_errors` у `junit-xml` и у `pult-vitest` — отказ «список «провал проверки» не задан у компонента <имя>» до прогона (решение Оператора 19.10, п. 6). Иначе — находка с идентификатором и видом: прошёл, пропуск или `todo` (с `mode`), имя ошибки, таймаут, падение хука, `fails`, повтор.
4. **Повтор имени, ошибка уровня файла, порядок.** Идентификатор с `#<n>` в файлах планки или своих долгоживущих — находка «повтор имени теста в файле: <идентификатор>» (ADR п. 3). Ошибка уровня файла на базе — находка «<файл>: ошибка уровня файла — тесты файла не исполнены» (строже ADR п. 5 до G3а): у JUnit — запись `error` с видом падения «collection failure», файл в тексте находки — по имени записи (`parse_junit` не хранит classname, разборщик не меняется); у Vitest — тестовый файл планки (метод is_test правила) без записей в отчёте. Порядок: пустой `failure_errors` (проверяется до прогона, и у `junit-xml`, и у `pult-vitest`) → подготовка → повторы `#<n>` → по критериям → ошибки уровня файла; все находки — одним отказом, действие журнала «переход отклонён: честный FAIL_TO_PASS».
5. **«Зелёный с рождения».** Перечень — раздел SPEC «## Зелёный с рождения» со строками `AC-<n>` (критерии, не файлы); утверждение — обычное одобрение SPEC на гейте SPEC (решение Оператора 19.10, п. 7, в толковании ассистента). SPEC читается с ветки документов на выходе из `tests_writing`. Маркер «Зелёный с рождения:» (докстринг модуля у Python, первый комментарий — `guard.first_comment` — у файла с меткой) допустим у файла планки, все тесты `AC-<n>` которого — из перечисленных критериев: эти тесты обязаны быть в отчёте и пройти; иначе маркер — находка гейта. У долгоживущих файлов тесты `AC-<n>` всегда по п. 3.
6. **Ветка.** В гейте приёмки (`_acceptance_run_body`) у профиля в границе, после зелёного прогона и до `_seed_repeats_escalate`: для каждого критерия, покрытого тестом по зафиксированной планке и долгоживущим файлам перечня (тем же разбором по правилу, что на выходе из `tests_writing`), в записях прогона ветки есть хотя бы одна запись с меткой критерия, и все такие — `passed` без повторов. Иначе отказ, действие журнала «переход отклонён: приёмочные тесты — тест критерия не в отчёте», деталь «AC-n — теста нет в отчёте прогона ветки».
7. **Запреты и «одна метка на тест»** — новая функция `guard` по тексту файлов с меткой (тестовые файлы планки и свои долгоживущие файлы), без комментариев и строковых литералов: `.fails`, `.skipIf`, `.runIf`, `.only`, `vi.setConfig`; в аргументах первого уровня вызова `it`/`test`/`describe` (с цепочками) — объект с ключом `retry` или `timeout` либо числовой литерал; в одном литерале имени метка `AC-<n>: ` встречается больше одного раза; литерал `describe` с меткой `AC-<n>: ` в начале. Отказ — «<файл>:<строка>: <что найдено> — запрещено в тексте планки». Вызов — в `_tests_writing_test_groups_gate` (файлы планки), в `_tests_writing_long_lived_gate` (долгоживущие файлы) и в `preflight` (сторож).
8. **Переносы 1, 2, 5 и текст автогейта.** (1) Чекпоинт пишет запись о взятом умолчании правила один раз на визит `tests_writing` (нет такой записи после последней «state -> tests_writing»), вне визита `tests_writing` не пишет; гейт посторонних, выбирая последнюю запись визита, пропускает записи `PLANK_RULE_DEFAULT_ACTION`; `journal_plank_default` и документы перед мержем — прежние. (2) Разбор скобок `.each(…)` пропускает комментарии `//` до конца строки и `/* … */`: таблица с `// don't` распознаётся. (5) Каталог планки плоский по правилу G2а-1 (вложенный путь — посторонний), выкладка остаётся плоской — закрепить тестом: вложенный файл отброшен чекпоинтом и не выложен. Автогейт: запрет для правила не по умолчанию сохраняется до G3б (решение Оператора 19.10, п. 9); текст `_plank_rule_refusal` целиком — «автогейт: прогон планки компонента <имена> по правилу — до гейта неослабления по исходам (G3б) не исполняется; приёмку решает Оператор»; отказ построения правила — прежний текст.
9. **У артели, записей `test_profile` и компонентов без `report` гейты, прогоны и тексты — прежние.** Аналитик перечисляет в SPEC тексты, закрепляемые тестами до правки: состав и порядок гейтов выхода из `tests_writing`, отказ «переход отклонён: приёмочные тесты» с хвостом, исходы `_acceptance_run_body`, причины автогейта (кроме заменяемого текста п. 8), отказы гейта посторонних, отказы гейта групп и гейта долгоживущих.
10. Тесты детерминированы, без сети и без Node: учебный проект с двумя компонентами (`junit-xml` на pytest и `pult-vitest` с подменённым раннером, пишущим заранее заданный отчёт) — каждая находка п. 2–7 и их порядок; сквозной выход из `tests_writing` и гейт приёмки — на записи `components:` из одного компонента каждого вида; выключенный случай — у артели и у записи `test_profile` с раннером pytest-own и `report: junit-xml` гейт не создан и прогона нет. Переносы 3 и 4 — тестами: `retro` зовёт `scan_acceptance_tests` без правила и получает прежний счёт; `plank-run` долгоживущего файла при правиле с отказом построения — код 0, раннер запущен, текста отказа нет. Переносы из приёмки G2б-1 — тестами в новом файле задачи: (6) `amend-tests` в режиме рабочей копии, планка только из `.md`, критерий покрыт долгоживущим файлом с меткой, правится этот файл — отказ, лок не сдвигается; (8) каждый отказ формы шаблона `long_lived` сверяется по своей причине, а не только по имени компонента.

Критерии приёмки:
- у `pult-vitest` планка, чьи тесты `AC-<n>` на базе падают с `AssertionError`, выходит из `tests_writing`; тест, прошедший на базе, упавший с `TypeError`, по таймауту, в хуке, пропущенный, `todo`, с `fails` или отсутствующий — отказ с идентификатором;
- файл планки без записей в отчёте базы (импорт несуществующего модуля) — отказ; на ветке отсутствие теста `AC-<n>` в отчёте — отказ гейта приёмки; «Зелёный с рождения» у файла вне перечня SPEC — отказ;
- `it.only`, `test.fails`, `{ retry: 2 }`, `vi.setConfig`, два `AC-<n>: ` в имени, повтор имени теста в файле — отказ с файлом и строкой;
- у компонента `junit-xml` на pytest тест `test_ac1_…`, падающий на `assert`, проходит гейт; ошибка сбора и пустой `failure_errors` — отказ;
- у артели и записи `test_profile` перечисленные в SPEC тексты и исходы прежние; сторож предпроверки зелёный без правки.

Решения по умолчанию (аналитику не спрашивать): прогон на базе — в рабочей копии кодовой ветки на выходе из `tests_writing` (её код равен базе — это держит гейт долгоживущих), отдельной выписки базы нет; запреты ищутся текстом без разбора синтаксиса JS; у файлов pytest запреты не проверяются (`xfail` и `skip` ловит п. 3 как пропуск).
