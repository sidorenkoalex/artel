## Зоны
- **Г1.** Новые действия журнала «переход отклонён: честный FAIL_TO_PASS» и
  «переход отклонён: приёмочные тесты — тест критерия не в отчёте» не входят в
  перечень классов `REFUSAL_CLASSES`
  (`orchestrator/advance_gates/refusal_classes.py:66-111`). Неизвестное
  действие получает класс «чинит Оператор»
  (`orchestrator/advance_gates/refusal_classes.py:114-117`), а на таком классе
  `auto` останавливается с первого отказа (`orchestrator/auto.py:863-864`).
  Тогда находку честного `FAIL_TO_PASS`, которую должен чинить test_author, и
  отказ ветки, который должен чинить developer, цикл не вернёт роли. SPEC не
  называет класс этих действий. `refusal_classes.py` нет ни в зонах, ни в
  «только чтение», а сверку литералов держит `tests/test_refusal_classes.py`.
  Если класс должен быть «чинит роль», нужна зона, иначе разработчик
  эскалирует посреди работы. Кроме того, требование 4 сводит под одно
  действие отказ «список «провал проверки» не задан у компонента» (его чинит
  Оператор в `targets.yaml`) и находки роли. Класс у одного действия может
  быть только один.
- Прочие зоны покрывают требования. `orchestrator/fsm.py`,
  `orchestrator/plank_run.py`, `orchestrator/retro.py`,
  `orchestrator/fsm_merge_gate.py` и `orchestrator/reporters/` нужны только на
  чтение: SPEC зовёт `fsm._tests_writing_ac_state` и
  `fsm._read_foreign_branch_text_or_refuse`, а переносы 3 и 4 —
  только тесты. Защищённые пути (`skills/`, `templates/`, `gates.yaml`,
  `roles.yaml`, `.github/`) не затронуты. Песочница ролей не расширяется.

## Пути обхода гейтов
- **Е1 (главный).** Требование 5: перечень «## Зелёный с рождения» читается
  «с ветки документов на выходе из `tests_writing`», то есть с головы ссылки.
  Голова двигается автокоммитом каждого шага роли. test_author может прямо в
  каталоге документов дописать в SPEC.md раздел «## Зелёный с рождения» со
  строками своих критериев. Чекпоинт закоммитит правку: в
  `_commit_external_step_artifacts` (`orchestrator/checkpoint.py:1416-1508`)
  нет запрета менять чужой артефакт. Конфликт-гвард ловит только правку
  Оператора, сделанную во время шага (`orchestrator/checkpoint.py:1090-1106`).
  Фиксация сверяет голову ссылки, а не содержимое SPEC
  (`orchestrator/fixation.py:131-154`). После этого тесты, проходящие на базе,
  выйдут из `tests_writing` под маркером «Зелёный с рождения:». Буквальное
  исполнение требования 5 открывает обход сути гейта: вместо «утверждение —
  одобрение SPEC на гейте SPEC» (ТЗ п. 5) перечень утверждает сам test_author.
  Нужно читать перечень из SPEC той версии, что одобрена на гейте SPEC, либо
  отказывать, если SPEC.md с одобрения изменился.
- **Е2.** Запреты требования 7 ищутся по тексту без строковых литералов и
  только у `it`/`test`/`describe`. Обходы:
  - `suite(…)` — синоним `describe` в Vitest — с `{ retry: … }`/`{ timeout: … }`;
  - `it['only']`, `vi['setConfig']` — имя метода в строке;
  - параметры через переменную: `it('AC-1: x', opts, fn)`, тайм-аут
    константой вместо числа.

  Часть обходов закрывает исполнение: `retry_count` даёт находку «повтор» на
  базе и красит ветку (`orchestrator/reporters/outcome.py:239-242`);
  `--allowOnly=false` и `--retry=0` стоят в базовой команде
  (`orchestrator/project_profile.py:359-361`); пропуск на ветке ловит
  требование 6. Не закрыты увеличенный тайм-аут через `suite` или переменную и
  `vi['setConfig']`. ТЗ задаёт поиск «текстом без разбора синтаксиса», так что
  это принятое ограничение. Решение Оператора — принять или добавить `suite`
  в перечень.
- **Е3.** «Код базы» — это рабочая копия кодовой ветки. Гейт долгоживущих
  сверяет только закоммиченный дифф
  (`orchestrator/advance_gates/tests_writing.py:464-466`), чистоту рабочего
  дерева перед прогоном на базе не проверяет никто. Чекпоинт test_author
  откатывает правки вне мандата, но при сбое git он рабочее дерево не трогает
  (`orchestrator/checkpoint.py:376-378`), а файлы из `.gitignore` не
  откатывает вовсе. Тогда незакоммиченная правка кода может уронить на
  `assert` тест, который на настоящей базе проходит, и гейт пропустит его.
  Вероятность низкая; это следствие решения ТЗ «отдельной выписки базы нет».
  Достаточно было бы, например, проверить `git status` перед прогоном.

## Вердикт
**concerns** — SPEC близок к ТЗ, факты о коде в основном верны. Есть
отклонения, которые Оператор может снять на гейте, правкой SPEC или решением.
Два из них лучше решить до одобрения: иначе разработчик упрётся в эскалацию
(Г1), или гейт станет обходимым (Е1).

1. **Е1** — перечень «Зелёный с рождения» с головы ссылки документов правится
   самим test_author; читать его из одобренной на гейте SPEC версии
   (`orchestrator/checkpoint.py:1416-1508`, `orchestrator/checkpoint.py:1090-1106`,
   `orchestrator/fixation.py:131-154`; SPEC требование 5, AC-14).
2. **Г1** — класс новых действий журнала не задан, по умолчанию «чинит
   Оператор», и `auto` встанет на первой находке. `refusal_classes.py` вне
   зон. Одно действие требования 4 смешивает отказ Оператора (пустой
   `failure_errors`) и находки роли
   (`orchestrator/advance_gates/refusal_classes.py:66-117`,
   `orchestrator/auto.py:863-864`; SPEC требования 2, 4, 6).
3. **Б2** — отказы плана и выкладки `run` и ранний выход «планки нет» обходят
   `ReportRun`: `records` останется пустым, и гейт рискует выдать «теста нет»
   вместо отказа подготовки (`orchestrator/acceptance.py:1526-1545`; SPEC
   требование 1, AC-19).
4. **Б1** — «правило планки не построено» в новом гейте на переходе
   недостижимо: раньше отказывает `_tests_writing_ac_state`
   (`orchestrator/fsm.py:646-651`, `orchestrator/fsm_advance.py:543`; SPEC
   требование 2, AC-12).
5. **В1** — «аргументы первого уровня» не определены; нет отрицательного
   критерия на литерал или объект в теле колбэка и в таблице `.each` (SPEC
   требование 7, AC-16, AC-17).
6. **А2** — проект с двумя компонентами не проходит `decide`
   (`orchestrator/repo_context.py:161-163`,
   `orchestrator/project_profile.py:194-198`, 276-278). SPEC не уточняет, что
   его находки проверяются прямым вызовом гейта, и по какому компоненту гейт
   берёт `failure_errors` (SPEC требование 10).
7. **AC-15** — проверка «с повтором» после зелёного прогона недостижима,
   повтор уже красит прогон (`orchestrator/reporters/outcome.py:239-242`);
   критерий проверяем только прямым вызовом.
8. **А1** — оговорка ТЗ п. 5 «в толковании ассистента» потеряна; толкование
   п. 7 стоит подтвердить Оператору (SPEC требование 5).
9. **Е2, Е3** — остаточные обходы: текстовые запреты (`suite`, доступ по
   строке, параметры через переменную) и незакоммиченное рабочее дерево на
   прогоне базы. Низкая вероятность, решение Оператора — принять или усилить.
10. **Б3** — SPEC не говорит, как сопоставить записи отчёта с файлами планки
    по путям выкладки (`orchestrator/acceptance.py:1433-1444`). Деталь
    исполнения, отмечена как риск.
