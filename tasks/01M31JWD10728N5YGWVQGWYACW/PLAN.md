# PLAN: Возврат из эскалации ревьювера — маркер «ответ должен дойти до роли»

## Подход

Содержательная правка — одна: `orchestrator/fsm_advance.py::_review_escalate`
после своего `store.set_state(..., "escalated", ...)` зовёт
`_mark_artifact_escalation(conn, task_id, detail)` тем же вызовом и с тем
же `detail`, что уже зовут `spec_writing` (строки 112, 136) и
`tests_writing` (строка 322). Текст эскалации («эскалация от ревьювера»)
выносится в локальную переменную `detail` — иначе `set_state` и маркер
разошлись бы при любой будущей правке формулировки, а планка AC-1 сверяет
именно равенство `detail` двух записей.

Почему этого достаточно. Читатель маркера уже готов: `auto.py:321`
включает `fsm.ARTIFACT_ESCALATION_ROLE_STEP_MARKER` в
`_ROLE_STEP_REQUIRED_MARKERS`, а `_role_step_since_state_entry`
(`auto.py:384-395`) при взведённом `role_step_required` делает анкером
запись `state -> in_dev`, которую иначе пропустила бы как
`_ESCALATED_RETURN_DETAILS`. Требование 2 закрывается без единой строки в
`auto.py`/`fsm.py` — они в «Не входит» SPEC ровно поэтому.

Границы правки (требования 3-4). Вызов ставится ВНУТРЬ `_review_escalate`,
а не в `fsm_advance.review` и не в общий узел перехода в `escalated`:
эскалация по бюджету из `review` (`budget.enforce_budget`) и остальные
эскалации без собственного основания переделки идут мимо этой функции и
остаются без маркера. `escalated_from` не трогается — точка возврата
остаётся `in_dev` (требование 3, AC-7).

Тестовый слой. `tests/test_artifact_escalation_marker.py` несёт тест
`MarkerWrittenByTheEscalationPointsTest::
test_review_escalation_does_not_journal_the_marker` (строки 341-356),
закрепляющий прежнее ошибочное решение SPEC 01M2XFSJ1Z7BS6HR69SAT1D81Y.
Решение Оператора (ANSWER-1, вопрос 1, вариант A): тест ПЕРЕПИСЫВАЕТСЯ под
новое ожидание, имя метода — ровно
`test_review_escalation_journals_the_marker`. Половина прежней проверки,
правкой не отменяемая («маркер не вынесен в общий узел эскалации»),
сохраняется отдельным НОВЫМ тестом
`test_budget_escalation_from_review_journals_no_marker` в том же классе —
эскалация по бюджету из `review` маркера не пишет. Перечень «не исчезли»
планки AC-8 новых имён не запрещает (сверка на включение), и именно такой
новый тест ANSWER-1 прямо разрешает.

Потолок SPEC (25 $) не переоценивается: число файлов и шагов плана
совпадает с оценкой SPEC (правится один модуль кода и один модуль тестов),
поле `budget_usd` во frontmatter не раскомментировано.

## Шаги

1. `orchestrator/fsm_advance.py::_review_escalate` — локальная переменная
   `detail = "эскалация от ревьювера"`, её передача в `store.set_state` и
   вызов `_mark_artifact_escalation(conn, task_id, detail)` сразу после
   перехода. Докстринг функции называет причину (инциденты 20.09/21.09) и
   границу: маркер ставит именно эта точка, не любой переход в `escalated`
   из `review`.
2. `tests/test_artifact_escalation_marker.py` — переписать
   `test_review_escalation_does_not_journal_the_marker` в
   `test_review_escalation_journals_the_marker` (ожидание обратное:
   маркер ЕСТЬ отдельной записью сразу за `state -> escalated`, `actor`
   = `fsm`, `detail` равен detail эскалации); добавить
   `test_budget_escalation_from_review_journals_no_marker` — сохранённую
   половину прежней проверки. Шапка модуля упоминает третью точку
   эскалации и эту задачу.
3. Прогон: планка задачи
   (`tasks/01M31JWD10728N5YGWVQGWYACW/acceptance_tests/`) и четыре модуля
   AC-8 (`tests/test_artifact_escalation_marker.py`,
   `tests/test_auto_escalated_return_rework_gate.py`,
   `tests/test_fsm_review_rework_gate.py`,
   `tests/test_fsm_review_rework_sha_gate.py`), плюс соседи затронутого
   кода: `tests/test_auto_cycle.py`, `tests/test_review_freshness.py`,
   `tests/test_invariants.py` (последний — ожидаемо зелёный, см. SPEC
   «Материалы»; краснота там = эскалация, не правка). Регенерация карты
   кодовой базы `python3 scripts/codebase_map.py` тем же коммитом.

Один шаг MR: части «только код» и «только тесты» по отдельности не
мержатся (обоснование монолита — SPEC «Оценка объёма и деление»).

## Влияние на систему

- **Что затрагивается за пределами правки.** Новая запись журнала на
  каждой эскалации ревьювера — её читает `auto._role_step_since_state_entry`
  и (безразлично) `catalog.cmd_log`/`report`. Поведение меняется ровно в
  одном месте: после возврата из такой эскалации цикл `auto` требует
  завершённого шага developer до предварительного advance. Это и есть
  требование 2.
- **Инварианты и гейты рядом.** Ни один не ослабляется: правка ДОБАВЛЯЕТ
  анкер рубежа переделки там, где его не было, — рубеж становится строже,
  не мягче. `auto._ESCALATED_RETURN_DETAILS` и пропуск записей возврата
  без маркера остаются нетронутыми (требование 4, AC-5). Гейты
  `_review_escalation_sha_gate`/`_review_rework_gate` работают с теми же
  данными: маркер — отдельная запись журнала, `code_sha` и
  `reviewed_iter` он не трогает.
- **Существующие тесты.** Один тест переписывается под новое ожидание по
  явному решению Оператора (ANSWER-1, вопрос 1) — не удаляется и не
  ослабляется: его вторая половина («маркер не в общем узле эскалации»)
  переезжает в отдельный новый тест. Остальные три модуля AC-8 не
  правятся вовсе; `tests/test_invariants.py` (защищённый путь) не
  правится — по SPEC «Материалы» его сценарий идёт через `fsm.cmd_advance`
  напрямую, мимо рубежа `auto`.
- **Откат.** Revert одного merge-коммита ветки задачи: правка — один
  вызов в одной функции плюс тестовый модуль, внешних состояний
  (БД-схема, файлы, ветки) не заводится.

## Риски

- Задача, эскалированная ревьювером ДО мержа этой правки и возвращённая
  ПОСЛЕ, маркера в журнале не имеет — её возврат по-прежнему пройдёт мимо
  роли. Класс известен и не чинится задним числом: обход тот же, что
  применялся 20.09/21.09 (`stop` + `reject` из `verifying`).
- Дополнительный обязательный шаг developer после каждой эскалации
  ревьювера стоит денег даже там, где правок коду не нужно. Требование 3
  SPEC это признаёт осознанно: подтверждающий шаг дешёвый, а альтернатива
  (ответ не доходит до роли) дороже.
