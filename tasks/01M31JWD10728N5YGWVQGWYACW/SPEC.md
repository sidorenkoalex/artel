# SPEC: Возврат из эскалации ревьювера: маркер «ответ должен дойти до роли»

## Контекст

Возврат из эскалации ревьювера уводит задачу мимо роли: после `answer` +
`approve` предварительный advance переводит задачу `in_dev -> verifying`
«по готовым артефактам», и ответ Оператора до developer не доходит. Два
случая за три дня, одна механика: 20.09 (01M2XJKKPH) — переход через 16 с
после возврата; 21.09 (01M31DRD81) — `state -> in_dev | эскалация
разрешена, продолжаем` в 08:52:09, «шаг developer не нужен: переход
выполнен по готовым артефактам | in_dev -> verifying» в 08:52:22, код тот
же (64399a0d), ANSWER-1 до роли не дошёл. Оба раза выручал обход: `stop` +
`reject` из `verifying` с причиной — запись возврата становилась анкером
гейта переделки.

Причина: маркер «ответ Оператора должен дойти до роли»
(`fsm.ARTIFACT_ESCALATION_ROLE_STEP_MARKER`) пишет
`orchestrator/fsm_advance.py::_mark_artifact_escalation` только для
эскалаций по артефакту роли в `spec_writing` и `tests_writing` (SPEC
01M2XFSJ1Z7BS6HR69SAT1D81Y). Эскалация ревьювера `_review_escalate` пишет
только `state -> escalated | эскалация от ревьювера`, маркера НЕ пишет —
и запись возврата пропускается как `_ESCALATED_RETURN_DETAILS`, а шаг
developer, отработанный до эскалации, засчитывается. SPEC
01M2XFSJ1Z7BS6HR69SAT1D81Y счёл случай review невоспроизводимым —
воспроизводится стабильно.

## Требования

1. Эскалация ревьювера (`REVIEW.md status: escalate`,
   `orchestrator/fsm_advance.py::_review_escalate`) пишет маркер «ответ
   Оператора должен дойти до роли» тем же вызовом
   `_mark_artifact_escalation`, что эскалации `spec_writing`/
   `tests_writing`, — сразу после `state -> escalated`.
2. После `answer` + `approve` возврат в `in_dev` становится анкером гейта
   переделки, и предварительный advance не переводит задачу дальше до
   завершённого шага developer, бриф которого несёт ANSWER.
3. Вариант возврата — в `in_dev` с обязательным шагом developer (как
   задача возвращается сегодня, только теперь с анкером). Альтернатива
   из копилки — возврат в `review` с обязательным шагом reviewer — не
   выбирается: ответ Оператора на вопрос ревьювера почти всегда меняет
   трактовку требования, а значит код; developer, которому правок не
   нужно, подтверждает PLAN и выходит дешёвым шагом. Довода против
   аналитик не нашёл — довод ТЗ подтверждается кодом: бриф developer уже
   несёт ANSWER-n.md последней эскалации, бриф reviewer собирается
   ревью-пакетом иначе.
4. Возвраты из эскалации БЕЗ основания переделки (бюджет, лимит сессии,
   провал агента) ведут себя как сегодня: запись возврата анкером не
   становится, шаг роли, отработанный до эскалации, засчитывается.
5. Тесты в `tests/`: сценарий 21.09 воспроизводится журналом задачи в
   песочнице; эскалация по бюджету из `review` и эскалации
   `spec_writing`/`tests_writing` сохраняют прежнее поведение.

## Критерии приёмки

AC-1. Эскалация ревьювера по `REVIEW.md status: escalate` пишет в журнал
задачи маркер «ответ Оператора должен дойти до роли» отдельной записью
сразу после записи `state -> escalated` — тем же вызовом
`_mark_artifact_escalation`, что эскалации `spec_writing`/
`tests_writing`.

AC-2. Сценарий «эскалация ревьювера → `answer` → `approve` → `auto`»
запускает шаг developer, а не переводит задачу `in_dev -> verifying` по
готовым артефактам.

AC-3. Бриф developer этого шага несёт ANSWER последней эскалации.

AC-4. Сценарий 21.09 (задача 01M31DRD81) воспроизводится журналом задачи
в песочнице: до правки последовательность записей даёт переход
`in_dev -> verifying` без шага developer, после правки — шаг developer.

AC-5. Эскалация по бюджету из состояния `review`: после возврата запись
анкером не становится, шаг роли, отработанный до эскалации,
засчитывается — поведение прежнее.

AC-6. Эскалации `spec_writing` и `tests_writing` — поведение прежнее:
маркер пишется там же и так же, как до правки.

AC-7. Точка возврата эскалации ревьювера — `in_dev` (эскалация
по-прежнему не выставляет `escalated_from`), не `review`.

AC-8. Существующие `tests/test_artifact_escalation_marker.py`,
`tests/test_auto_escalated_return_rework_gate.py`,
`tests/test_fsm_review_rework_gate.py`,
`tests/test_fsm_review_rework_sha_gate.py` остаются зелёными.
