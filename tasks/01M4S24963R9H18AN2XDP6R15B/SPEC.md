# SPEC: Справочник ядра — генератор, настройка проекта, кэш (К-3а)

## Контекст
Замер 12.10.2026: developer до первой правки читает `orchestrator/store.py`
(40% шагов), `scripts/guard.py` (39%), `orchestrator/config.py` (34%),
`tests/sandbox.py` (33%), `orchestrator/fsm.py` (33%), `orchestrator/runner.py`
(23%), `orchestrator/gitcmd.py`; чаще всего ищут `def journal`,
`def set_state`, `PROTECTED_PATHS`, `COMMON_ZONES`, `STATE_ROLE`,
`DEFAULT_TARGET`. Карта кодовой базы (`scripts/codebase_map.py`) даёт только
имена публичных функций — без сигнатур, docstring, классов и констант.
Задача — часть «а» из двух (решение Оператора 12–13.10.2026): генератор
короткого справочника «как пользоваться» (порядка 5–10 тыс. токенов) по
коммиту проекта через `ast`, его настройка в записи проекта `targets.yaml` и
пересоздаваемый кэш в `.artel/projects/<проект>/knowledge/derived/`
(ADR-0003 п.3а, п.3б). Включение в бриф, предел размера, шаг после мержа и
настройка артели — ТЗ К-3б; новый код этой задачей ни из одной команды
пульта не вызывается, поведение пульта байт в байт прежнее.

## Требования

1. **Генератор `scripts/core_reference.py`.** Функция
   `build(sources, setting, sha, *, min_uses, generator_sha256)` по набору
   исходных текстов (путь → текст), настройке проекта (требование 3) и sha
   источника строит текст справочника. Разбор — только `ast`: код проекта не
   импортируется и не исполняется (ни `import`/`importlib`, ни
   `exec`/`eval`/`compile` с исполнением). Генератор импортирует только
   стандартную библиотеку, не модули пульта, и не читает `config`: порог
   использования, `generator_sha256` и sha источника приходят параметрами.
   Выход детерминирован: тот же вход — байт в байт тот же текст.
   Командная строка: `python3 scripts/core_reference.py <корень дерева>
   <модуль>... [--constants-module <модуль> --constants <ИМЯ>...]
   [--min-uses N] [--sha <метка>]` (умолчания: `3` и «рабочее дерево»)
   печатает справочник по файлам диска в stdout и ничего не пишет на диск.
   Набор файлов в этом режиме — обычные файлы (не символьные ссылки) `.py`,
   отслеживаемые git в корне (`git ls-files`); нет git — все `.py`, кроме
   каталогов с ведущей точкой, `__pycache__`, `node_modules`, `venv`. Режим
   предназначен для деревьев Оператора, не для чужих.
2. **Содержимое справочника** — по каждому модулю настройки в её порядке,
   одна строка на запись. «Файлы коммита» — `.py`, отслеживаемые git в этом
   коммите; одно правило для подсчёта использования и поиска примеров:
   а) путь и первая строка docstring модуля;
   б) публичные (без ведущего `_`) функции верхнего уровня, включая
      `async def`, используемые не менее чем в `config.CORE_REFERENCE_MIN_USES`
      = 3 других файлах коммита (обращение `<модуль>.<имя>` или
      `from … <модуль> import <имя>`; `<модуль>` — имя файла без `.py`):
      имя, сигнатура как в коде (параметры, значения по умолчанию,
      аннотации, возвращаемый тип) и первая строка docstring, обрезанная до
      100 символов с «…» (нет docstring — ничего). Декораторы сигнатуру не
      меняют; при двух определениях одного имени верхнего уровня берётся
      последнее;
   в) публичные классы верхнего уровня по тому же правилу использования:
      имя, базовые классы, имена публичных методов одной строкой (без
      сигнатур и docstring);
   г) пример вызова к записи п. б — только вызов, целиком умещающийся в
      одну строку и не длиннее 80 символов; из подходящих по длине — первый
      по порядку «путь файла (посимвольная сортировка строк), затем номер
      строки»: вызов `<модуль>.<имя>(` в любом файле коммита, иначе
      `<имя>(` в файле, импортирующем имя из модуля, иначе `<имя>(` в самом
      модуле; подходящего нет — примера нет;
   д) константы — только перечнем имён из настройки и только из модуля
      констант настройки: имя, значение одной строкой (пробелы схлопнуты,
      длиннее 400 символов — обрезка с «…») и пояснение — комментарий в той
      же строке, иначе первое предложение сплошного блока комментариев
      непосредственно над присваиванием (до первого `.`, `:` или `;`, за
      которым пробел; не более 160 символов), иначе «без пояснения». Имя
      перечня не найдено — строка «нет в коммите».
   Модуль настройки отсутствует в коммите или не разбирается — в его
   разделе строка с причиной, остальные модули строятся. Любой файл коммита,
   не разобранный `ast` (`SyntaxError`, `ValueError`, `RecursionError`,
   `MemoryError`, не декодируется как UTF-8), сборку не роняет: в подсчёт
   использования не входит и считается в шапке.
   Шапка: `built_at_sha`, `generator_sha256` (требование 5), настройка
   (модули, модуль и имена констант, `CORE_REFERENCE_MIN_USES`), число
   неразобранных и пропущенных файлов, sha256 тела; строка для роли:
   справочник описывает код коммита `built_at_sha`, правки задачи после него
   не отражены, полный текст модуля — в рабочем каталоге.
   Тексты из кода (docstring, значения и комментарии констант, примеры
   вызовов) очищаются: символы категории Cc заменяются пробелом; строки
   делятся только по `\n`.
3. **Настройка** — необязательное поле `core_reference` записи проекта в
   `targets.yaml`: `modules` (непустой список строк; каждая оканчивается на
   `.py`, относительная, без ведущего `/`, без пустых сегментов, `.`, `..` и
   обратных слэшей, без повторов), `constants_module` (необязательный, один
   из `modules`), `constants` (непустые идентификаторы Python без повторов;
   обязателен при `constants_module` и запрещён без него). `targets.check`
   проверяет поле тем же приёмом, что `test_profile`: отказ называет проект,
   поле и подполе; неизвестное подполе — отказ. Поле проекта читает новая
   `targets.core_reference(name)`: файл разбирается один раз, проверяется
   только запись `name` (сломанная чужая запись справочник этого проекта не
   отключает). Механизм не знает имён модулей артели: всё берётся из
   настройки.
4. **Чтение исходников коммита — пакетно**: один `git ls-tree -r -l -z <sha>`
   и один `git cat-file --batch` (не `gitcmd.show` на файл), `git -C <клон
   проекта>` (`repo_context.clone_path`), окружение `gitcmd.pult_env()`;
   `orchestrator/gitcmd.py` не меняется. Без checkout и без рабочего дерева.
   `<sha>` — 40 шестнадцатеричных знаков (голова ветки узнаётся
   `rev-parse`). В набор берутся только записи типа blob с режимом 100644
   или 100755 и именем на `.py`: символьные ссылки (120000) и подмодули
   (160000) пропускаются и считаются в шапке. Пределы — константы `config`:
   `CORE_REFERENCE_MAX_FILES` = 2000, `CORE_REFERENCE_MAX_SOURCE_BYTES` =
   32 МиБ, `CORE_REFERENCE_MAX_BLOB_BYTES` = 1 МиБ,
   `CORE_REFERENCE_MAX_LISTING_BYTES` = 64 МиБ (вывод `ls-tree` читается
   потоком, превышение — как сверх пределов). Число файлов, объём и размер
   blob проверяются по размерам из `ls-tree -l` ДО запуска `cat-file`; на
   вход `cat-file` идут только sha blob'ов в пределах; ответ разбирается по
   длине из строки `<sha> blob <размер>`, строка `missing` — файл пропущен и
   посчитан в шапке. Крупный blob пропускается и считается; сверх пределов
   числа файлов, объёма или вывода, по общему сроку — справочник не
   строится, исход требования 7. Срок `config.CORE_REFERENCE_GIT_TIMEOUT_SEC`
   = 60 — общий на всю сборку (оба вызова git и разбор): второму вызову
   передаётся остаток срока; `TimeoutExpired` и `OSError` — сбой источника.
   Также `config.CORE_REFERENCE_MIN_USES` = 3 (требование 2).
5. **Кэш** — `.artel/projects/<проект>/knowledge/derived/core-reference.md`
   через `repo_context.projects_root()` в момент вызова; при `NO_AREA` —
   `off` (требование 6). Обоснование (PLAN повторяет его одной строкой):
   карта лежит в `docs/codebase-map.md` git артели и коммитится после мержа —
   для внешнего проекта такой путь означал бы запись пульта в чужой
   репозиторий; `knowledge/` — дом производных знаний по ADR-0003 п.3а, вне
   git, не трогает диффы мержа, гейт ёмкости и сторож неизменности главной
   копии; `derived/` отделяет пересоздаваемое от курируемых файлов К-4а;
   файл можно удалить — следующая сборка восстановит. Модуль кэша —
   `orchestrator/reference_cache.py`. Запись атомарна (временный файл в том
   же каталоге и замена); файл читается один раз целиком, шапка и тело
   разбираются из одного прочтения. Кэш годен, только если совпадают
   `built_at_sha`, настройка из шапки, sha256 тела и `generator_sha256` —
   sha256 байт файла загруженного модуля генератора
   (`core_reference.__file__`), считанный при импорте модуля пультом (не
   `config.ROOT / …`). Не совпало — сборка заново и перезапись. Кэш, не
   являющийся обычным файлом или крупнее четырёх
   `CORE_REFERENCE_MAX_BLOB_BYTES`, считается испорченным (пересборка).
6. **Интерфейс для К-3б**: `reference_cache.get_reference(conn, task_id, *,
   reason, sha=None)` → значение с полями `text` (содержимое файла кэша
   целиком — шапка и тело, как записано; или пусто), `note` (пометка для
   брифа или пусто), `state` — `off` (у проекта нет поля), `fresh` (собран
   сейчас), `cached` (кэш годен), `unverified` (источник не узнать, отдан
   кэш), `absent` (справочника нет). `sha=None` — голова ветки задачи в
   клоне проекта (коммит, не рабочее дерево); иначе — переданный коммит.
   `reason` — `brief` или `merge`. Каждая сборка — запись журнала задачи
   «справочник ядра: построен» (sha, байты, число записей, длительность,
   повод). Голову ветки не узнать (нет клона или ветки, git не ответил):
   есть кэш — `unverified` с пометкой «не сверен: <причина>,
   built_at_sha=…»; кэша нет — `absent` с пометкой. До чтения
   `targets.yaml`: область проектов `NO_AREA` — `off` без алерта, пометки и
   журнала (кэш не читается и не пишется, git не зовётся). Читаемый
   `targets.yaml` без записи проекта — тоже `off`. Нечитаемый файл, запись
   без разбора поля, неверное поле — `absent` с пометкой и алертом
   (требование 7). `off` не даёт побочных эффектов (git, журнал, алерт).
   Функция не бросает исключений и не завершает процесс.
7. **Сбои** (модуль или имя константы не найдены, модуль не разобран,
   источник недоступен или сверх пределов требования 4, кэш не записан,

## Критерии приёмки

AC-1. Генератор не исполняет код проекта: модуль, чей верхний уровень
оставляет след на диске или падает при исполнении, разобран — справочник
собран, следа нет. Импорты самого `scripts/core_reference.py` (проверка `ast`)
— только стандартная библиотека, ни одного модуля пульта. Два вызова `build`
на одном входе дают байт в байт одинаковый текст.

AC-2. Командная строка `python3 scripts/core_reference.py <корень> <модуль>...
[--constants-module … --constants …] [--min-uses N] [--sha …]` печатает
справочник в stdout и не пишет на диск ни одного файла; умолчание
`--min-uses` равно `config.CORE_REFERENCE_MIN_USES` (= 3). В git-дереве в
разбор попадают только обычные `.py` из `git ls-files` (файл вне индекса и
символьная ссылка — нет); без git — `.py` вне каталогов с ведущей точкой,
`__pycache__`, `node_modules`, `venv`.

AC-3. Использование считается числом других файлов коммита (обращение
`<модуль>.<имя>` или `from … <модуль> import <имя>`), не числом обращений;
собственный файл модуля в подсчёт не входит; имя, используемое ровно в 3
файлах, в справочник входит, в 2 — нет; приватное (с ведущим `_`) имя не
входит. Порог берётся из параметра `min_uses`.

AC-4. Запись функции несёт путь модуля и первую строку его docstring, имя,
сигнатуру как в коде (параметры, значения по умолчанию, аннотации,
возвращаемый тип) и первую строку docstring, обрезанную до 100 символов с
«…»; `async def` не теряется; декоратор сигнатуру не меняет; при двух
определениях одного имени верхнего уровня берётся последнее.

AC-5. Запись публичного класса верхнего уровня (по тому же правилу
использования) несёт имя, базовые классы и имена публичных методов одной
строкой — без сигнатур и docstring методов.

AC-6. Пример вызова к функции — однострочный вызов не длиннее 80 символов,
первый по порядку «путь файла посимвольно, затем номер строки», с
приоритетом: `<модуль>.<имя>(` в любом файле коммита → `<имя>(` в файле,
импортирующем имя из модуля → `<имя>(` в самом модуле; подходящего нет —
примера нет.

AC-7. Константы выводятся только из перечня настройки и только из модуля
констант: значение одной строкой со схлопнутыми пробелами, длиннее 400
символов — обрезка с «…»; пояснение — комментарий в той же строке (главнее
блока над ней), иначе первое предложение сплошного блока комментариев над
присваиванием до первого `.`/`:`/`;` с пробелом за ним, не длиннее 160
символов, иначе «без пояснения»; имя перечня, которого нет, — строка «нет в
коммите». Константа вне перечня в справочник не попадает.

AC-8. Отсутствующий или неразбираемый модуль настройки даёт в своём разделе
строку с причиной, остальные разделы строятся. Файл коммита с
`SyntaxError`/`ValueError`/`RecursionError`/`MemoryError`/не-UTF-8 сборку не
роняет, в подсчёт использования не входит и посчитан в шапке. Шапка несёт
`built_at_sha`, `generator_sha256`, настройку (модули, модуль и имена
констант, `CORE_REFERENCE_MIN_USES`), число неразобранных и пропущенных
файлов, sha256 тела и строку для роли о коммите `built_at_sha`. Символ
категории Cc из кода в справочник не доходит (заменён пробелом).

AC-9. `targets.check` и `targets.core_reference(name)` отказывают каждому
неверному случаю поля `core_reference` из требования 3 (пустой/не список
`modules`, путь не на `.py`, абсолютный, с пустым сегментом, `.`, `..`,
обратным слэшем, повтор; `constants_module` вне `modules`; `constants`
пустой, не идентификатор, с повтором, без `constants_module`;
`constants_module` без `constants`; неизвестное подполе) с отказом,
называющим проект, поле и подполе. Сломанная чужая запись `targets.yaml` не
отключает справочник проекта через `targets.core_reference`. Перечень
модулей и констант берётся из настройки, не зашит в код.

AC-10. Исходники коммита читаются ровно двумя запусками git на сборку
(`ls-tree -r -l -z` и `cat-file --batch`) независимо от числа файлов, из
объектов коммита, а не рабочего дерева (незакоммиченная правка в текст не
попадает). Символьная ссылка, подмодуль и ответ `missing` в разбор не
попадают и посчитаны в шапке; крупный blob (> `CORE_REFERENCE_MAX_BLOB_BYTES`)
пропущен и посчитан. Превышение `CORE_REFERENCE_MAX_FILES` или
`CORE_REFERENCE_MAX_SOURCE_BYTES` по размерам `ls-tree` останавливает сборку
до запуска `cat-file`; вывод `ls-tree` сверх `CORE_REFERENCE_MAX_LISTING_BYTES`
останавливает сборку; общий срок `CORE_REFERENCE_GIT_TIMEOUT_SEC`, исчерпанный
к второму вызову, останавливает сборку. Значения констант `config` — как в
требовании 4.

AC-11. Кэш пишется в `<область проектов>/<проект>/knowledge/derived/core-reference.md`
и больше никуда; сбой замены при записи оставляет прежний файл целым.
Кэш перестраивается при новом sha, другой настройке, испорченном теле
(несовпадение sha256, не обычный файл, крупнее четырёх
`CORE_REFERENCE_MAX_BLOB_BYTES`) или другом `generator_sha256`; при полном
совпадении не перестраивается — вторая выдача на том же sha даёт `cached` и
не пишет запись журнала «справочник ядра: построен». `generator_sha256` —
sha256 байт файла загруженного модуля генератора, не путь от `config.ROOT`
(в песочнице с подменённым корнем вычисляется без ошибки).

AC-12. `get_reference(conn, task_id, *, reason, sha=None)` возвращает `text`,
`note`, `state` по требованию 6: проект без поля и читаемый `targets.yaml`
без записи — `off`; при `NO_AREA` — `off` без сборки, записи файла, алерта,
журнала, запуска git и чтения `targets.yaml`; `off` ни в одном случае не
даёт побочных эффектов; при недоступной голове ветки и наличии кэша —
`unverified` с пометкой «не сверен: <причина>, built_at_sha=…», без кэша —
`absent` с пометкой; переданный `sha` используется вместо головы ветки;
каждая сборка пишет в журнал задачи «справочник ядра: построен» с sha,
байтами, числом записей, длительностью и поводом. На сбое git, записи или
разбора функция не бросает исключение.

AC-13. Каждый сбой требования 7 (модуль/имя константы не найдены, модуль не
разобран, источник недоступен или сверх пределов, кэш не записан,

AC-14. Тест-сторож: генератор по файлам рабочего дерева репозитория с
настройкой артели из ТЗ К-3б, заданной в самом тесте, выдаёт `journal`,
`set_state`, `PROTECTED_PATHS`, `COMMON_ZONES`, `STATE_ROLE`,
`DEFAULT_TARGET`.

## Меняемое поведение
Нет: ожидания существующих тестовых методов `tests/` не меняются. Песочница
подменяет `config.TARGETS` записью без поля `core_reference`, поэтому
новое необязательное поле существующих проверок `targets` не задевает.

## Оценка объёма и деление
Сработавший сигнал: число критериев приёмки 14 ≥ `SPLIT_SIGNAL_AC_COUNT`
(10); ТЗ также называет сигнал «зоны» (6 путей в поле `zones`). Критерии
сгруппированы по пунктам ТЗ — не более 15, класс калибровки «до 15
критериев и до 7 файлов» ($45, совпадает с рамкой ТЗ).

Материал для решения Оператора — обоснование монолита (из ТЗ): генератор
(`scripts/core_reference.py`), его настройка (`targets.core_reference`,
`targets.check`) и кэш с единым интерфейсом `get_reference`
(`orchestrator/reference_cache.py`) не делятся без промежуточного кода без
потребителя: генератор без настройки и кэша ни из чего не вызывается,
настройка без генератора ничего не настраивает, кэш без обоих не имеет
содержимого. Интерфейс К-3б опирается на все три части сразу. Решение
принимает Оператор на гейте SPEC.
