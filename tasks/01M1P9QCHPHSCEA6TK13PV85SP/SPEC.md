# SPEC: Механика зон, часть 3: сверка диффа с зонами при переходе в ревью

## Контекст
Родитель — 01M1NKVPD2A79PQ6K0JVV1B2Q1 «Механика зон» (SPEC на гейте
04.09: решение о делении на три части; эта задача — часть 3, из
требования 4 ТЗ родителя). Сегодня переход `in_dev → review`
пропускает дифф ветки задачи без сверки с заявленными зонами —
единственная страховка от выхода задачи за свои границы в коде —
содержательное ревью постфактум. Нужен формальный отказ перехода,
когда дифф трогает файлы вне заявленных зон, дополняющий, а не
заменяющий это ревью.

Задача зависит от части 1 («Зоны: машиночитаемое поле и общий
список») — читает поле `zones` задачи и общий список зон из
`orchestrator/config.py`, которые часть 1 заводит в БД/конфиге; не
пересекается по коду с частью 2 («Зоны: занятость на старте кода»).
Код этой задачи стартует после мержа части 1 в main; до её мержа эта
задача остаётся на стадии SPEC.

## Требования
1. Переход `in_dev → review` отклоняется, если дифф ветки задачи к
   main трогает файлы вне заявленных в `zones` задачи путей и вне
   общего списка зон (`orchestrator/config.py`). Отказ называет
   конкретные файлы вне зон.
2. Исключение: PLAN несёт раздел расширения зон с обоснованием,
   подкреплённым мандатом Оператора (ANSWER с явным согласием на
   расширение) — расширение записывается в БД задачи, переход
   проходит.
3. Реализация — отказ на существующем переходе `in_dev → review` по
   образцу действующих отказов `advance` (лок планки, свежесть), не
   новое состояние FSM; отказ доносится до следующего запуска роли
   developer по действующей механике доставки отказа (T078).
4. Существующий набор `tests/` остаётся зелёным без ослабления.

## Критерии приёмки
AC-1. Переход `in_dev → review` отклоняется, если дифф ветки задачи к
main трогает файлы вне путей, заявленных в `zones` задачи, и вне
общего списка зон в `orchestrator/config.py`.

AC-2. Отказ перехода по AC-1 называет конкретные файлы диффа, лежащие
вне зон, а не общую формулировку.

AC-3. Исключение из AC-1: если PLAN задачи несёт раздел расширения зон
с обоснованием, подкреплённым ANSWER Оператора с явным согласием на
расширение, — расширение записывается в БД задачи, и переход
`in_dev → review` проходит.

AC-4. Отказ по AC-1 реализован как дополнительное условие на
существующем переходе `in_dev → review` (по образцу `budget_block`/
отказов свежести ветки), без введения нового состояния FSM.

AC-5. Отказ по AC-1 доносится до следующего запуска роли developer по
действующей механике доставки отказа `advance` (T078), а не теряется
между запусками.

AC-6. Пересечение диффа с путями из общего списка зон
(`orchestrator/config.py`) не считается нарушением по AC-1.

AC-7. Существующий набор тестов (`tests/`) остаётся зелёным; ни один
существующий тест, гейт, лимит или guard-проверка не ослаблены и не
отключены этой задачей.

## Не входит
- Занятость зоны на старте кода роли developer (часть 2,
  01M1NKVPD2A79PQ6K0JVV1B2Q1) — эта задача не блокирует старт `in_dev`,
  только переход `in_dev → review`.
- Содержательное ревью — ревьювер по-прежнему сверяет дифф по
  чек-листу как прежде; механика зон формальная, дополняет, не
  заменяет ревью.
- Поле `zones:` во frontmatter SPEC, его сохранение в БД при `approve`
  и общий список зон в `orchestrator/config.py` — заводит часть 1
  (01M1NKVPD2A79PQ6K0JVV1B2Q1), эта задача только читает эти данные.
- Очередь и переупорядочивание задач на занятой зоне — механика части
  2, к переходу `in_dev → review` отношения не имеет.
