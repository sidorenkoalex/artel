# PLAN: сверка диффа с зонами при переходе in_dev → review

## Подход

Часть 1 (01M1NKVPD2A79PQ6K0JVV1B2Q1) уже смержена в main на момент
старта этой задачи (`COMMON_ZONES`/колонка `tasks.zones` существуют) —
первым шагом подтянут main в ветку задачи (коммит «подтяжка main»,
карта перегенерирована), дальше код пишется против реального
`orchestrator/config.COMMON_ZONES`, без `create=True`.

Отказ AC-1 реализован как дополнительное предусловие на существующем
переходе `in_dev -> review` (`orchestrator/fsm_advance.py::in_dev`), по
образцу соседнего гейта ёмкости diff (`_capacity_gate_refuses`) в том
же файле: своя маленькая функция `_zones_gate_refuses`, вызываемая
после свежести ветки и гейта ёмкости, перед `store.set_state(...,
"review", ...)`. Отказ журналируется через `store.journal(...,
"переход отклонён: гейт зон", ...)` — тот же префикс `REFUSAL_ACTION_
PREFIX`, что и остальные отказы `advance`, поэтому `store.
refusal_history`/`brief.advance_refusal_history` (T078) подхватывают
его без отдельной проводки (AC-5). Задача остаётся в `in_dev`
(`return True` из гейта → `in_dev()` возвращает `False`, не меняя
`state`) — нового состояния FSM нет (AC-4).

Список файлов диффа — `gitcmd.diff_names(config.MAIN_BRANCH,
t["branch"])`: тот же примитив, что уже используется рядом
(`in_dev` — лок `acceptance_tests/`), только без ограничения путём.
Внешний (не self) target гейт не проверяет — тот же довод, что уже несёт
`_capacity_gate_refuses` рядом (`git diff` в `config.ROOT` не видит код
внешнего target).

Зона файла — «путь равен зоне или начинается с неё» (`_touches_zone`),
буквально та же формула, что `fsm_merge_gate._touches_protected_path`
для `PROTECTED_PATHS` — не новое правило префикса, переиспользование
существующего. Зона задачи = `tasks.zones` ∪ `tasks.zones_extension`
(ANSWER-1, п.4) ∪ `config.COMMON_ZONES` (AC-6).

Исключение AC-3 — три параметра зафиксированы ANSWER-1.md Оператора
этой задачи (канал ADR-0012), реализация читает их буквально:
1. Раздел `## Расширение зон` PLAN.md, строка `Пути: <...>` —
   `guard.section_body(plan_text, "Расширение зон")` (уже читаемая
   функция guard, переиспользуется, не копируется) + разбор строки
   `Пути:` по префиксу.
2. Мандат — строка `Расширение зон разрешено: <...>` в ЛЮБОМ
   `ANSWER-n.md` ветки задачи; перебор файлов — тот же приём, что
   `fsm._answer_file_count` (`gitcmd.ls_tree_files` + фильтр по имени
   `ANSWER-*.md`), чтение каждого — `gitcmd.show`.
3. Каждый путь раздела PLAN обязан входить хотя бы в один такой
   маркер — иначе исключение не открывается, и гейт отказывает по
   AC-1/AC-2 (называя фактически непокрытые файлы). Совпадение
   успешно — `tasks.zones_extension` пополняется (объединение с уже
   накопленным, не перезапись), переход проходит.

Новая колонка `tasks.zones_extension TEXT` — миграция `add_column`,
тем же приёмом, что и `zones` части 1 (и в `SCHEMA` для свежей БД, и в
`migrate()` для существующей).

## Шаги

1. `orchestrator/store.py`: колонка `zones_extension` (SCHEMA + migrate).
2. `orchestrator/fsm_advance.py`: `_zones_gate_refuses` и разбор
   раздела «Расширение зон»/мандата ANSWER, подключение в `in_dev`.
3. Юнит-тесты новых функций (`tests/test_zones_gate.py`), прогон
   приёмочных тестов задачи и полного `tests/`.

## Влияние на систему

Новое предусловие только на переходе `in_dev -> review`, только для
`target == config.DEFAULT_TARGET` (внешний target — вне зоны, как и
гейт ёмкости рядом). Не меняет ни одного существующего состояния FSM,
не трогает `review`/`verifying`/`tests_writing`/`spec_writing`. Новая
колонка БД `zones_extension` — идемпотентная миграция, NULL для всех
существующих строк (нейтральна: пустая зона расширения не сужает
существующее поведение). Существующие гейты этого перехода (лок
`acceptance_tests/`, свежесть ветки, гейт ёмкости) не тронуты по
порядку и семантике — новый гейт добавлен последним перед `set_state`.
Откат — удаление вызова `_zones_gate_refuses` из `in_dev` и самой
функции; колонка `zones_extension` остаётся неиспользуемой, но
безвредной (тот же путь отката, что и у соседних add_column-колонок).

## Риски

- Задача без ЗАЯВЛЕННОЙ зоны вовсе (`zones` и `zones_extension` оба
  пусты — SPEC старой версии до `guard.requires_zones`, либо тестовая
  фикстура, заведённая мимо гейта SPEC) — гейт НЕ звонится (уточнение
  по факту прогона полного `tests/`, AC-7: буквальное «вне заявленных
  путей» при пустом списке отказало бы такой задаче на каждом файле вне
  `COMMON_ZONES` — четыре существующих теста (`tests/
  test_acceptance_tests_flow.py::LockTest`, `tests/test_amend.py::
  AmendThenReviewGateTest`) заводят задачу в обход гейта SPEC, зону не
  декларируют, и это регрессия AC-7, не требование AC-1). Решение:
  гейт активен, только если задача ХОТЬ ЧТО-ТО заявила в `zones`/
  `zones_extension` — опт-ин механики, не ретроактивный запрет для
  того, что в ней не участвует.
