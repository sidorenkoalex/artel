## Пути обхода гейтов
1. **Исход верный, текст не тот.** Исполнитель возвращает правильный `kind`
   (RED/RUNNING/NONE) с новым текстом, например «итог по Actions: красный —
   test». AC-1..AC-6 проходят. Но `auto` не остановится на красном
   (`auto.py:485`, `verifying_is_red`), и задача снова ждёт потолок 5400 с —
   тот самый симптом 18.10. `ci-rerun` красного не находит (`ci_rerun.py:89-90`).
   Гейт мержа читает «идёт»/«неизвестен» без маркеров как red
   (`status_kind`, `fsm_merge_gate.py:363`) и запускает ре-ран
   незавершённого или неизвестного CI.
2. **Фильтр по триггеру.** Ни один AC не проверяет триггер. Две буквальные
   реализации проходят все AC и расходятся: «все запуски коммита» (красный
   `push`-запуск красит ветку, зелёный `push` без `pull_request` даёт
   зелёный) и «только `pull_request`». Для вершины main проекта (требование 1
   включает её через `failed_check_names`, `ci.py:611`, `ci_rerun.py:291`)
   фильтр `pull_request` обычно оставляет пустой набор: `_inherited_from_main`
   молча возвращает "", а `ci-rerun` получает «статус main неизвестен».
3. **Чужие ветки.** Запросы Actions по `head_sha` возвращают и прогоны
   других веток на том же коммите. Без требования отбора по `head_branch`
   (как `_branch_checks` на пути check-runs) красный прогон main на том же
   sha красит задачу.
4. **Переход по коду, не по тексту.** Переход по «403» без текста проходит
   AC-7, в котором 403 rate limit не назван, хотя требования 1 и 4 это
   запрещают.
5. **Doctor.** Функция проверки есть и покрыта тестом прямого вызова, но
   не зарегистрирована в `project_entry_checks`, и `doctor` её не печатает;
   AC-9/AC-10 этого не ловят.
