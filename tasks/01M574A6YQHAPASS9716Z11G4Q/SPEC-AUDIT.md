## Пути обхода гейтов
1. **Ложный красный на неизвестном.** Требование 2 (последний пункт)
   задаёт для `verifying_status` только «статус неизвестен, не зелёный».
   Ни исход-константа, ни ложность `verifying_is_red` для него не названы:
   требование 5 перечисляет только «проверки идут» и «проверок нет». Можно
   отдать `VERIFYING_RED`/`NONE` с текстом «CI коммита X не зелёный: ответ
   Actions неполон». Тогда `auto` останавливается с алертом красного CI
   (`auto.py:485`), `watch` шлёт событие (`watch.py:219`), а `ci-rerun`
   находит «красный» sha (`ci_rerun.py:89-90`). AC-6 при этом зелёный.
2. **Порядок «идёт» и «красный».** Требование 2: красный выигрывает у
   идущего. На пути check-runs порядок обратный: идущий выигрывает
   (`ci.py:785-796`). Реализация, повторившая порядок check-runs, проходит
   AC-2 (все завершены) и AC-3 (красных нет), но нарушает требование 2.
3. **Красный запуск без имён.** Возьмём запуск `failure`/`startup_failure`
   без заданий с не-GREEN заключением. Буквально по требованию 3
   `failed_check_names` вернёт `set()`. Для вершины main это читается
   «на main ничего не упало», и `ci-rerun` идёт в повтор вместо отказа
   (`ci_rerun.py:291-305`). Это тот же класс лжи, от которого охраняет
   `ci.py:884-888`.
4. **doctor и 403 rate limit.** Требование 8 говорит «check-runs 403,
   Actions доступны — `warn`» без оговорки текста. 403 «API rate limit
   exceeded» по буквальному прочтению даёт `warn` «CI читается по Actions
   runs». Но по требованию 4 CI в этом случае на Actions не переходит, и
   строка doctor ложна.
5. **`_inherited_from_main` на пути Actions.** Требование 1 называет вход
   «через `_inherited_from_main`». При этом ни требование 2, ни один AC не
   требуют, чтобы красный исход Actions считал унаследованную красноту и
   `PULL_MAIN_HINT` (`ci.py:791-795`). Реализация без этого проходит все
   AC.

## Вердикт
**concerns** — отклонения 1–6 первого визита закрыты. Новые отклонения
устранимы уточнением на гейте, переписывать SPEC целиком не нужно:

1. Исход `verifying_status` «статус неизвестен» на пути Actions
   (SPEC, требование 2, последний пункт; требование 5) не закреплён ни
   константой исхода, ни требованием `verifying_is_red(note)` ложно
   (`orchestrator/ci.py:835`). AC-6 проверяет только «не зелёный».
   Следствие — ложный стоп `auto` с алертом (`orchestrator/auto.py:485`).
   Предложение: потребовать для этого исхода `verifying_is_red(note)`
   ложно (и, например, `VERIFYING_NONE`/`RUNNING` по образцу
   `ci.py:754-758`) и дописать это в AC-6.
2. Правило требования 2 «красный выигрывает у идущего» не проверяется ни
   одним AC. Оно противоположно порядку пути check-runs
   (`orchestrator/ci.py:785-796`). Предложение: сценарий в AC-2 или AC-3
   «один запуск красный, другой идёт» с ожидаемым исходом.
3. Требование 3: у красного запуска без красных заданий (нет заданий,
   `startup_failure`) имя не определено. Буквально выходит `set()`, и для
   вершины main это ложное «ничего не упало» (`orchestrator/ci.py:884-888`,
   `orchestrator/ci_rerun.py:291-305`). Предложение: имя запуска (workflow)
   как имя упавшего, либо `(None, причина)`.
4. Требование 8 и AC-11: 403 с иным текстом (rate limit) на check-runs в
   doctor не отделён от 403 «Resource not accessible». `warn` о чтении по
   Actions для него ложен (требование 4). AC-11 не проверяет и
   401/неразобранный → `fail`, а AC-12 — отказ `gh_env` → `skip`
   (`orchestrator/doctor/misc_checks.py:80`).
5. Требование 1 называет вход `_inherited_from_main`
   (`orchestrator/ci.py:611`), но не требует считать его на красном исходе
   Actions, и ни один AC это не проверяет. Предложение: либо требование
   плюс сценарий в AC-2, либо снять упоминание из требования 1.
6. Мелочь: охрана `is_artel` у `fsm_merge_gate.py` стоит на `:582`, не на
   `:583`, как пишет SPEC (на `:626` ссылка верна).
