не проверяется.

проекта (требование 4 ТЗ) — все вызовы в зоне (`orchestrator/ci.py`):

## Требования

1. Когда чтение check-runs коммита ветки задачи или вершины main внешнего
   проекта отказано правами — HTTP 403 с текстом «Resource not accessible by
   personal access token» или «Resource not accessible by integration», —
   статус CI этого коммита определяется по запускам GitHub Actions этого
   коммита (`/actions/runs?head_sha=<sha>` и задания запусков, право
   Actions: read) того же репозитория проекта. Требование действует на всех
   входах пути задачи внешнего проекта из «Контекста»: `verifying_status`,
   `branch_status`, `failed_check_names` (в том числе для вершины main в
   `ci-rerun`). HTTP 403 с иным
   текстом (например, превышение лимита запросов) под это требование не
   подпадает — это требование 4.
2. Вердикт ветки задачи по Actions (`verifying_status`, `branch_status`;
   инвариант 19 — неизвестное или неполное не читается как зелёное):
   - в вердикт идут только запуски ветки задачи: запуск, чей `head_branch`
     непуст и отличен от ветки задачи, исключается — то же правило, что
     `_other_branch`/`_branch_checks` (`ci.py:549-570`) держат на пути
     check-runs; запуск без `head_branch` остаётся в вердикте;
   - «запуск триггера ветки» — запуск с событием `pull_request` (см.
     «Контекст»); запуски других событий ветки задачи тоже остаются в
     вердикте;
   - зелёный — только когда есть хотя бы один завершённый запуск триггера
     ветки и все запуски вердикта (триггера ветки и других событий)
     завершены с заключением из `GREEN` (`ci.py:27`);
   - есть незавершённый запуск вердикта и нет красного — «проверки идут»;
   - любой завершённый не-зелёный запуск вердикта (любого события) —
     красный, с именами упавших заданий этого запуска, в том числе когда
     рядом идёт другой запуск вердикта (красный выигрывает у идущего:
     красное известно сразу, инвариант 19 это не нарушает); у красного
     запуска без красных заданий (заданий нет, `startup_failure` и т. п.)
     именем упавшего считается имя запуска (workflow);
   - запусков вердикта нет вовсе, либо нет ни одного запуска триггера ветки
     при завершённых зелёных запусках других событий, — прежнее поведение
     для коммита без проверок: у `verifying_status` — исход
     `_no_checks_by_branch` (`ci.py:805-822`) по тому же ответу
     `gh run list`, у `branch_status` — не зелёный, «статус неизвестен»;
   - ответ Actions (запуски или задания) не получен, не разобран или неполон
     (получено меньше, чем обещает `total_count` ответа) — статус неизвестен,
     не зелёный. У `verifying_status` этот исход выражается существующими
     константами по образцу `ci.py:754-758` (`VERIFYING_NONE` или
     `VERIFYING_RUNNING` — что ближе по смыслу, выбор обосновывается в
     PLAN), не красный: `verifying_is_red(note)` для него ложно.
3. `failed_check_names` по Actions — имена заданий завершённых запусков
   коммита с заключением не из `GREEN`, по всем событиям и без отбора по
   ветке (как на пути check-runs, `ci.py:899-901`); у красного запуска без
   красных заданий в множество идёт имя запуска (workflow) — пустое
   множество при красном запуске недопустимо; у коммита нет ни одного
   запуска, либо ответ Actions не получен, не разобран или неполон —
   `(None, причина)`, не пустое множество.
4. Прочие ответы чтения check-runs внешнего проекта (сеть, 401, 404, 5xx,
   403 с иным текстом, неразобранный ответ) — исход и тексты как до правки,
   запросов к Actions по `head_sha` ради вердикта не делается.
5. Тексты статуса на пути Actions читаются существующими разборщиками так
   же, как тексты пути check-runs:
   - красный `verifying_status` — `verifying_is_red(note)` истинно,
     `red_status_sha(note)` возвращает первые 8 знаков sha коммита;
   - «проверки идут», «проверок нет» и «статус неизвестен»
     `verifying_status` — `verifying_is_red(note)` ложно;
   - `branch_status`: идущий — `status_kind(note) == "running"`; статус
     неизвестен (нет запусков, ответ Actions не получен/не разобран/неполон)
     — `"unknown"`; красный — `"red"`;
   - первая строка `note` — строка вердикта (на ней стоят разборщики;
     `verifying_head_not_in_origin` читает начало `note`).
6. Причина перехода на Actions видна в выводе статуса одной строкой:
   «check-runs недоступны токену проекта (403) — итог по Actions runs» — в
   `note` каждого исхода `verifying_status` и `branch_status`, полученного по
   Actions.
7. Артель (свой репозиторий, токен Оператора) — путь и тексты статуса CI
   прежние; это фиксируется тестами до правки, и они остаются зелёными
   после неё.
8. `doctor`: новая проверка `project-ci-token-<проект>` для каждой записи
   внешнего проекта, в выводе `doctor` рядом с прочими строками проекта
   (`project_entry_checks`, `doctor/cli.py:101`) — читает ли токен проекта
   проверки коммита вершины базовой ветки (check-runs) и запуски Actions.
   Авторизация — та же, что у прочих вызовов `gh` проекта в doctor
   (`gh_env`, `doctor/misc_checks.py:80`). Исходы:
   - оба доступны — `ok`;
   - check-runs 403, Actions доступны — `warn` с текстом «CI читается по
     Actions runs; для check-runs токену нужно право Checks: read»;
   - check-runs отказывает иначе (401, 404, 5xx, неразобранный ответ) при
     доступных Actions — `fail` с причиной: для таких ответов поведение CI
     не меняется (требование 4), и статус CI проекта пульт не узнает;
   - check-runs 403 с иным текстом, чем «Resource not accessible …»
     (превышение лимита запросов и пр.), — `skip` с причиной (временный
     отказ, права не определены), не `warn` о чтении по Actions;
   - Actions недоступны — `fail` (пульт CI проекта не увидит);
   - сеть недоступна (вызов `gh` не дал HTTP-ответа: обрыв, таймаут) —
     `skip` с причиной, не `fail`;
   - нет `gh` CLI либо слот токена не читается (`gh_env` вернул отказ) —
     `skip` с причиной;
   - в процессе роли — `skip` с `ROLE_SKIP` без сети и связки ключей, как у
     `project-token-<проект>` (`project_checks.py:49`);
   - запись артели — `skip` с `NOT_APPLICABLE`, как у прочих строк проекта
     (`project_checks.py:36-37`).
   Значение токена в вывод не попадает.
9. Тесты детерминированы, без сети и реального GitHub: подмена `gh`/ответов
   API на учебном внешнем проекте (403 на check-runs; Actions: идёт /
   зелёный / красный / пусто), сценарии doctor.

## Критерии приёмки

AC-1. Учебный внешний проект, check-runs коммита ветки отвечают 403
«Resource not accessible by personal access token», все Actions-запуски
коммита ветки задачи (среди них запуск события `pull_request`) завершены
успешно: `verifying_status` даёт `VERIFYING_GREEN`, `branch_status` —
`True`, задача выходит из `verifying`.

AC-2. Тот же проект, один Actions-запуск ветки задачи завершён красным
(`failure`), остальные зелёные: `verifying_status` даёт `VERIFYING_RED`,
его `note` называет имя упавшего задания, `verifying_is_red(note)`
истинно, `red_status_sha(note)` — первые 8 знаков sha головы;
`branch_status` — `False` с `status_kind(note) == "red"`;
`failed_check_names` для этого коммита возвращает множество с этим именем.
То же — когда красный запуск события `push`, а запуск `pull_request`
зелёный. То же — когда один запуск ветки задачи завершён красным, а другой
ещё идёт: исход красный (не «проверки идут»), `note` называет имя
упавшего задания.

AC-3. Тот же проект, Actions-запуск ветки задачи ещё идёт, красных нет:
`verifying_status` даёт `VERIFYING_RUNNING`, `verifying_is_red(note)`
ложно; `branch_status` — `False` с `status_kind(note) == "running"`.
Красный запуск ветки задачи без красных заданий (заданий нет вовсе либо
заключение запуска `startup_failure`): `verifying_status` даёт
`VERIFYING_RED`, его `note` называет имя запуска (workflow);
`failed_check_names` для этого коммита возвращает множество с именем
запуска, не пустое множество.

AC-4. Тот же проект, у коммита нет ни одного Actions-запуска:
`gh run list` по ветке отвечает пустым списком — `verifying_status` даёт
`VERIFYING_NONE` с «проверок нет вовсе»; `gh run list` по ветке показывает
запуск — `VERIFYING_RUNNING` с «проверки идут» (оба — исходы
`_no_checks_by_branch` до правки на тех же ответах `gh run list`);
`branch_status` в обоих случаях — `False` с `status_kind(note) ==
"unknown"`. Тот же исход, когда у коммита есть только завершённые зелёные
запуски события `push` и нет запуска `pull_request`.

AC-5. Тот же проект, на коммите есть зелёный завершённый запуск
`pull_request` ветки задачи и красный запуск с `head_branch` другой ветки
(например, базовой): `verifying_status` даёт `VERIFYING_GREEN`,
`branch_status` — `True`; если же единственный запуск коммита — запуск
другой ветки, исход тот же, что в AC-4.

AC-6. При 403 на check-runs ни пустой, ни неполный (запусков или заданий
меньше `total_count`), ни неразобранный, ни не полученный ответ Actions не
даёт зелёного исхода ни у `verifying_status`, ни у `branch_status`
(`status_kind(note) == "unknown"` для неполного, неразобранного и не
полученного ответа), а `failed_check_names` возвращает `None` с причиной,
не пустое множество — и для головы ветки, и для вершины main. Исход
`verifying_status` «статус неизвестен» на пути Actions (неполный,
неразобранный, не полученный ответ) — одна из существующих констант
`VERIFYING_NONE`/`VERIFYING_RUNNING`, не красный: `verifying_is_red(note)`
ложно, и цикл `auto` на `verifying` с таким исходом не останавливается
алертом `AUTO_STOP_VERIFYING_RED` (`auto.py:485-489`), а продолжает опрос.

AC-7. Вершина main внешнего проекта при 403 на check-runs: её
Actions-запуски (события `push`) завершены, одно задание красное —
`failed_check_names(<sha вершины main>)` возвращает множество с его
именем; все зелёные — пустое множество.

AC-8. На исходах AC-1..AC-6 `note` `verifying_status` и `branch_status`
содержит строку «check-runs недоступны токену проекта (403) — итог по
Actions runs», и она не первая строка `note`; 403 с текстом «Resource not
accessible by integration» даёт тот же переход на Actions, что «by personal
access token».

AC-9. Внешний проект, чтение check-runs отказывает сетью, 401, 404, 5xx,
403 с текстом «API rate limit exceeded» или неразобранным ответом: исход и
текст `verifying_status`, `branch_status` и `failed_check_names` совпадают
с поведением до правки, запросов `actions/runs?head_sha=` ради вердикта не
делается.

AC-10. Артель на тех же подменах ответов (включая 403 на check-runs): исход
и текст `verifying_status`, `branch_status`, `failed_check_names` прежние —
тесты, зафиксированные до правки, зелёные и после неё.

AC-11. doctor для внешнего проекта: в выводе `doctor` есть строка
`project-ci-token-<проект>`; check-runs и Actions доступны — `ok`;
check-runs 403, Actions доступны — `warn` с текстом «CI читается по
Actions runs; для check-runs токену нужно право Checks: read»; check-runs
отвечает 401, 404, 5xx или неразобранным ответом, Actions доступны —
`fail`; check-runs 403 с текстом «API rate limit exceeded» — `skip` с
причиной, не `warn`; Actions недоступны — `fail`.

AC-12. doctor для внешнего проекта при обрыве сети — `skip` с причиной, не
`fail`; без `gh` CLI — `skip` с причиной; `gh_env` вернул отказ (слот
токена не читается) — `skip` с причиной; в процессе роли — `skip` с
`ROLE_SKIP` без вызова `gh`; для записи артели — `skip` с `NOT_APPLICABLE`;
ни в одном из сценариев AC-11/AC-12 значение токена проекта не встречается
в выводе doctor.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` ≥ $30 (рамка ТЗ $35); число критериев
приёмки = 12; зона задевает механизм инварианта 19 `docs/invariants.md`
(неизвестный статус CI не зелёный). Класс по калибровке (до 15 критериев,
4 файла зоны) — ~$45; `budget_usd` оставлен рамкой ТЗ $35, поднять — решение
Оператора.

Обоснование монолита (материал для решения Оператора):
- Естественный шов есть — часть CI (`orchestrator/ci.py`, AC-1..AC-10) и
  часть doctor (`orchestrator/doctor/*`, AC-11..AC-12), обе с `tests/`.
  Часть CI мержима отдельно; часть doctor отдельно впереди CI — нет: её
  `warn` утверждает «CI читается по Actions runs», что до части CI ложь.
- Довод за монолит — цена: Оператор дал одну рамку $35 на всё; деление
  добавляет второй проход analyst/аудит SPEC/test_author (~$10 сверх), а
  часть doctor мала (одна проверка в `project_checks.py` и её имя в
  строках проекта). Атомарности механики здесь нет — это решение по цене,
  не по неразрезаемости.
- Если Оператор предпочтёт деление: часть 1 — CI (`orchestrator/ci.py`,
  `tests/`), первая; часть 2 — doctor (`orchestrator/doctor/project_checks.py`,
  `orchestrator/doctor/cli.py`, `tests/`), после части 1.

## Не входит

- Красный main внешнего проекта на гейте мержа (и `main_line_status` для
  внешнего проекта вообще — его вызыватели только артель).

  требует, идущий запуск ждёт потолок ожидания `verifying`.

  исполнен» (`_event_divergence`, `_unexecuted_full_suite`) на пути Actions —
  ТЗ их не требует.
- Смена токена sled — это делает Оператор.
- Задача sled 01M55SKHZ293CCAK0N7T4H7ZMR.
- Правка `find_run_id` (`ci.py:1279`) и `accepted_full_suite`
  (`ci.py:961`) — см. сверку в «Контексте».
- Правка вне зон: `orchestrator/fsm*.py`, `orchestrator/ci_rerun.py`,
  `orchestrator/doctor/main_ci.py`, `orchestrator/targets.py`,
  `targets.yaml`, `docs/backlog.md` — только чтение; потребность в такой
