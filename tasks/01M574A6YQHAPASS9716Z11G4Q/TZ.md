# CI внешнего проекта при токене без права Checks: итог по Actions runs и проверка прав токена в doctor

## Факты

Живой случай 18.10, задача sled 01M55SKHZ293CCAK0N7T4H7ZMR, пин 03fa6903 (после 01M55V7WB9 «CI ветки внешнего проекта»). Из `verifying` задача ушла в `escalated`:

> потолок ожидания CI в verifying исчерпан (5400с) — последний статус: статус check-runs коммита 9495860f неизвестен (gh не ответил: gh: Resource not accessible by personal access token (HTTP 403)), но `gh run list` по ветке task/01m55skhz293ccak0n7t4h7zmr-… показывает запуск — проверки идут

- Токен проекта sled (слот `sled-github-token`, `targets.yaml`) — персональный токен. Эндпоинт `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` (`orchestrator/ci.py:224` `check_runs_page`, `:250` `check_runs`) отвечает ему 403, а `gh run list` (Actions) — работает.
- В итоге статус CI ветки внешнего проекта никогда не становится известным: `_no_checks_by_branch` (`ci.py:805-816`) по `gh run list` читает «проверки идут», цикл ждёт до потолка 5400 с и эскалирует. Завершён ли запуск и с каким итогом — пульт не узнаёт.
- `doctor` (`orchestrator/doctor/project_checks.py:220` `check_project_token`) отвечает `project-token-sled: ok` (токен есть в слоте и отличен от токена Оператора), право на чтение проверок коммита не проверяет.
- Вызовы `check_runs`: `ci.py:748, 892, 920, 969, 1213, 1326` — сверить, какие из них на пути задачи внешнего проекта (verifying, гейт мержа, `failed_check_names`, `ci-rerun`, CI main после мержа).

## Требуется

1. Когда чтение check-runs коммита ветки (или main) внешнего проекта отказано правами (HTTP 403 «Resource not accessible by personal access token» / «by integration»), статус CI коммита определяется по запускам GitHub Actions этого коммита (`/actions/runs?head_sha=<sha>` и задания запусков, право Actions: read) того же репозитория проекта.
   - Инвариант 19 сохраняется: неизвестное или неполное не читается как зелёное. Зелёный — только когда все запуски с триггером, которым CI проекта проверяет ветку (у sled — `pull_request`, см. doctor `project-ci-pull-request-sled`), завершены успешно; идущие — «проверки идут»; любой красный — красный с именами упавших заданий (для `failed_check_names` и сводок); нет запусков — прежнее поведение «проверок нет».
   - Причина перехода на Actions видна в выводе статуса (одна строка: «check-runs недоступны токену проекта (403) — итог по Actions runs»).
2. Другие ответы (сеть, 401, 404, 5xx, неразобранный ответ) — сегодняшнее поведение без изменения. Артель (свой репозиторий, токен Оператора) — путь и тексты прежние; зафиксировать тестами до правки.
3. `doctor`: новая проверка для каждого внешнего проекта — токен проекта читает проверки коммита базовой ветки (check-runs) и запуски Actions. Исходы: оба доступны — ok; check-runs 403, Actions доступны — warn с текстом «CI читается по Actions runs; для check-runs токену нужно право Checks: read»; Actions недоступны — fail (пульт CI проекта не увидит). Сеть недоступна — skip с причиной, не fail. Токен в вывод не попадает.
4. Аналитик сверяет все вызовы `check_runs` и `_no_checks_by_branch` на пути задачи внешнего проекта; найденное в зонах — в требования, вне зон — эскалация до SPEC.
5. Тесты детерминированы, без сети и реального GitHub: подмена `gh`/ответов API на учебном внешнем проекте (403 на check-runs; Actions: идёт / зелёный / красный / пусто), сценарии doctor.

Критерии приёмки:
- учебный внешний проект с 403 на check-runs: зелёные завершённые Actions-запуски — CI ветки зелёный, задача выходит из verifying; красный запуск — красный с именем задания; идущий — «проверки идут»; без запусков — прежнее «проверок нет»;
- 403 не превращается в зелёный ни при пустом, ни при неполном ответе Actions;
- у артели вывод и решения CI прежние (тесты до правки зелёные и после);
- doctor на трёх сценариях токена даёт ok / warn / fail, на обрыве сети — skip; токен не печатается.

Зоны: `orchestrator/ci.py`, `orchestrator/doctor/project_checks.py`, `orchestrator/doctor/cli.py`, `tests/`.

Только чтение: `orchestrator/fsm*.py`, `orchestrator/ci_rerun.py`, `orchestrator/doctor/main_ci.py`, `orchestrator/targets.py`, `targets.yaml`, `docs/backlog.md`. Правка вне зон — эскалация до SPEC.

Не входит: мерж через PR; красный main внешнего проекта на гейте мержа; смена токена sled (это делает Оператор); задача sled 01M55SKHZ293CCAK0N7T4H7ZMR.
