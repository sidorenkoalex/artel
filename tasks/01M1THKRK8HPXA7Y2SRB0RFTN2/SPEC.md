# SPEC: стоп-кран волны, часть 2 — пауза run/auto по открытому алерту и видимость

## Контекст

Часть 1 (задача 01M1THKPNZ11DBZAQDMJ33EMJR) заводит алерт
`kind=incident` «стоп-кран волны», когда один класс отказа бьёт по
нескольким разным задачам target self подряд за короткое окно, но сама
не меняет поведение `run`/`auto` — система только сигнализирует.
Задача читает этот алерт как готовый факт (не заводит его сама) и
подключает штатную остановку: пока алерт открыт, новые агентные шаги
по target self не стартуют, а Оператор видит это в `doctor` и
`status`, тем же приёмом, что уже несёт `pause` (T070/T074). Деление
на части — по решению Оператора 06.09 на гейте SPEC родительской
задачи 01M1SHK1JGQFD73B735WK5YTNY; нормативный текст требований и
критериев приёмки — SPEC родителя, требования 5–9 (в части блокировки
и видимости) и AC-10..AC-16, перенесённые в эту SPEC буквально (номера
AC перенумерованы сквозно с 1 по конвенции analyst, текст не менялся).
Старт задачи — после мержа части 1.

## Требования

1. Пока по target self открыт алерт стоп-крана — `run`/`auto` любой
   задачи этого target перед стартом НОВОГО агентного шага видят
   открытый алерт и отказывают начать шаг тем же приёмом, что штатная
   пауза (`orchestrator/pause.py`, `pause.is_paused`/`REFUSAL_ACTION`):
   уже идущий шаг не прерывается; `approve`/`reject`/`budget`/`status`
   не блокируются. Причина отказа — в stdout вызова и в журнале
   отказавшей задачи.
2. `alert-ack <id>` открытого алерта стоп-крана снимает блокировку
   немедленно. Повторное срабатывание того же класса ПОСЛЕ ack
   заводит НОВЫЙ алерт — не гасится прежним ack. Автоматического
   снятия нет.
3. `doctor` показывает открытый алерт стоп-крана первым пунктом
   вывода — раньше остальных проверок.
4. `status` несёт пометку у КАЖДОЙ задачи target self, пока алерт
   стоп-крана открыт (блокирует весь target, не только задачи,
   вызвавшие срабатывание).
5. Стоп-кран блокирует старт нового шага только для target self
   (`config.DEFAULT_TARGET`, догфуд) — задачи любого другого target
   не блокируются и не помечаются.

## Критерии приёмки

AC-1. Пока по target self открыт алерт стоп-крана, `run`/`auto` любой
задачи этого target отказывают начать НОВЫЙ агентный шаг с названной
причиной (текст упоминает стоп-кран); шаг, уже идущий на момент
срабатывания, не прерывается; причина отказа появляется и в stdout
вызова, и в журнале отказавшей задачи.

AC-2. `approve`, `reject`, `budget`, `status` работают на задачах
target self как обычно независимо от открытого алерта стоп-крана.

AC-3. `alert-ack <id>` открытого алерта стоп-крана снимает блокировку
— следующий `run`/`auto` того же target стартует агентный шаг штатно;
новое срабатывание того же класса ПОСЛЕ ack заводит новый алерт, а не
повторно гасится прежним ack.

AC-4. `doctor` печатает открытый алерт стоп-крана первым пунктом
вывода, до остальных проверок.

AC-5. `status` несёт пометку у каждой задачи target self, пока алерт
стоп-крана открыт.

AC-6. Существующие тесты бэкоффа/эскалации класса «транзиентное
системное» (SPEC T082) и `pause`/`pause --now` (T070/T074) остаются
зелёными без единого ослабления.

AC-7. Задача внешнего target не блокируется открытым алертом
стоп-крана self и не помечается им в `status`.

## Оценка объёма и деление

Сработавший сигнал: «число затрагиваемых модулей/файлов» — guard
считает уникальные пути `orchestrator/*.py`/`scripts/*.py` по ВСЕМУ
тексту SPEC, не только по полю `zones:`. Текст называет 5 путей:
4 из `zones:` (`runner.py`, `auto.py`, `doctor.py`, `catalog.py`) плюс
`orchestrator/pause.py` — файл, который требование 1 называет как
ГОТОВЫЙ приём для повторного использования (`is_paused`/
`REFUSAL_ACTION`), а не как файл, который эта задача правит. Реальная
зона (файлы кода, которые меняются) — 4 файла, ниже порога
`SPLIT_SIGNAL_ZONE_FILES=5`; `pause.py` в `zones:` намеренно не
включён.

Монолит принят: это уже вторая часть деления, которое Оператор
утвердил на гейте SPEC родительской задачи 01M1SHK1JGQFD73B735WK5YTNY
06.09 (часть 1 — счётчик и алерт, часть 2 — эта задача, блокировка и
видимость). Четыре требования части 2 (блокировка старта шага, снятие
по `alert-ack`, первая строка `doctor`, пометка `status`) — грани ОДНОЙ
и той же проверки «открыт ли алерт стоп-крана self»: блокировка без
видимости в `doctor`/`status` оставляет Оператора без объяснения, почему
шаги отказывают; видимость без блокировки не выполняет саму цель
требования (штатная остановка). Ни одна грань не мержима отдельно без
того, чтобы оставить механизм недостроенным — дальше делить нечего.

## Не входит

- Автоматический перезапуск/резюме после снятия блокировки — только
  ручное действие Оператора (`alert-ack`).
- Прерывание уже идущих шагов — стоп-кран останавливает только СТАРТ
  нового шага.
- Внешние target: задачи любого target, кроме self
  (`config.DEFAULT_TARGET`), не блокируются и не помечаются; в этой
  задаче параметризация по target не делается ни в каком виде.
