# PLAN: стоп-кран волны, часть 2 — пауза run/auto по открытому алерту и видимость

## Подход

Читаем открытый алерт стоп-крана (`kind=incident`, `alerts.WAVE_BREAKER_SOURCE`,
`target=config.DEFAULT_TARGET`), заведённый частью 1
(`alerts.check_wave_breaker_failure`/`check_wave_breaker_timeout`), тем же
приёмом, что уже несёт штатная пауза (`orchestrator/pause.py::is_paused`/
`REFUSAL_ACTION`): готовый факт в БД, ни новой таблицы, ни нового состояния
FSM. Один общий геттер `runner.wave_breaker_alerts_open(conn)` — список
открытых алертов этого класса — переиспользуется в трёх точках требования
(отказ старта шага, первая строка `doctor`, пометка `status`), чтобы
критерий «алерт открыт» не разъезжался между командами.

Важное расхождение с текстом SPEC (раздел «Оценка объёма и деление»,
zones): `orchestrator/doctor.py` на момент старта этой задачи (после
подтяжки main, где домержена независимая задача 01M1TT9BPBRYMDXXEWVZSRG51V)
— уже не монолитный файл, а пакет `orchestrator/doctor/` (facade
`__init__.py` + `cli.py` с `cmd_doctor`). Правка легла в `orchestrator/
doctor/cli.py` (там же живёт `cmd_doctor`) по внутренней дисциплине самого
пакета (докстринг `orchestrator/doctor/__init__.py`): коллаборанты читаются
через фасад (`doctor.runner...`), не импортируются в подмодуле напрямую.
Смысл требования 3 (SPEC) от этого не меняется — `doctor.py` в тексте SPEC
обозначает функциональность команды `doctor`, а не конкретный путь файла.

`config.py` не входит в `zones:` SPEC, но несёт новую константу
`AUTO_STOP_WAVE_BREAKER` (подсказка `auto` при отказе паузы стоп-крана) —
тем же способом, что уже хранит `AUTO_STOP_PAUSE`/`AUTO_STOP_ZONE_WAIT`
для абсолютно того же класса отказа («`run` отказался стартовать по
причине, не относящейся к этой задаче»). Без этой константы `auto`
свалился бы на общий, ничего не объясняющий текст «run отказался
стартовать» — тот же провал, что уже был закрыт для паузы/зоны.

Требование 2, вторая половина («повторное срабатывание после ack заводит
НОВЫЙ алерт») закрыто уже частью 1 без единой правки: `alerts.
_raise_wave_breaker_alert` дедуплицирует только среди `open_alerts`
(`ack_ts IS NULL`) — подтверждённый алерт немедленно выпадает из выборки,
следующее срабатывание того же класса заводит новую строку. Эта часть
только читает то же самое условие.

## Шаги

1. `orchestrator/runner.py`: `WAVE_BREAKER_REFUSAL_ACTION` (текст action
   журнала, отсечка для `auto`, по образцу `pause.REFUSAL_ACTION`) +
   `wave_breaker_alerts_open(conn)` (список открытых алертов self) + отказ
   старта НОВОГО агентного шага в `_cmd_run`, только для `target ==
   config.DEFAULT_TARGET`, строго после проверки паузы и до workspace/
   pre-flight/spawn (уже идущий шаг не трогает).
2. `orchestrator/config.py`: `AUTO_STOP_WAVE_BREAKER` — подсказка `auto`
   по образцу `AUTO_STOP_PAUSE`/`AUTO_STOP_ZONE_WAIT`.
3. `orchestrator/auto.py`: `_run_wave_breaker_refusal` (тот же приём
   отсечки «отказал ИМЕННО этот вызов», что и `_run_paused_refusal`/
   `_run_zone_wait_refusal`) + разбор в `_role_run_step`, `alert=False`
   (причина уже видна первой строкой `doctor`/пометкой `status` — алерт
   `attention` здесь дублировал бы уже открытый `incident`).
4. `orchestrator/doctor/cli.py`: `cmd_doctor` печатает открытые алерты
   стоп-крана первым пунктом вывода, до `restore`/остальных проверок,
   через `doctor.runner.wave_breaker_alerts_open`.
5. `orchestrator/catalog.py`: `_wave_breaker_suffix` (по образцу
   `_lease_holder_suffix`/`_zone_wait_suffix`) + вызов в `cmd_status` —
   пометка у каждой строки задачи target self, пока хоть один алерт
   открыт; один запрос на весь вывод, не по строке на задачу.
6. Юнит-тесты новых функций (`tests/test_runner_wave_breaker.py`,
   `tests/test_auto_wave_breaker_refusal.py`,
   `tests/test_catalog_wave_breaker_status.py`,
   `tests/test_doctor_wave_breaker.py`) + прогон затронутых существующих
   планок (`test_pause.py`, `test_pause_now.py`, `test_auto_cycle.py`,
   `test_catalog_status_log.py`, `test_doctor.py`, `test_multitarget.py`).

## Влияние на систему

Новая точка отказа в `_cmd_run` встаёт СТРОГО после проверки паузы и до
`target`/workspace/pre-flight/git-сверки/spawn — уже идущий шаг (эта же
функция, стартовавшая раньше открытия алерта) не прерывается (AC-1),
`approve`/`reject`/`budget`/`status`/`advance` эту точку не проходят вовсе
(AC-2) — они не зовут `_cmd_run`. Существующие тесты паузы (T070/T074) и
бэкоффа/эскалации транзиентного системного (T082) не меняются: новая
проверка добавлена отдельным блоком после паузы, ничего в их коде не
трогает, прогнаны без правок (см. «Шаги» п.6) — принцип целостности не
нарушен.

`auto.py`: `alert=False` для стоп-крана (по аналогии с паузой/зоной) —
сознательный выбор не дублировать `kind=attention` поверх уже открытого
`kind=incident`; Оператор видит причину без второго алерта.

`config.py` затронут (не в `zones:` SPEC) — риск: пока задача открыта,
конкурентная правка `config.py` другой задачей не защищена зоной; риск
принят из-за малости правки (одна новая константа-кортеж, без изменения
существующих) и отсутствия альтернативного места для подсказки `auto`
(весь класс `AUTO_STOP_*` живёт там же).

`orchestrator/doctor.py` в `zones:` SPEC — по факту `orchestrator/
doctor/` (пакет, смержен после SPEC этой задачи независимой задачей
01M1TT9BPBRYMDXXEWVZSRG51V). Правка легла в `orchestrator/doctor/cli.py`
по внутренней дисциплине пакета (фасад-доступ `doctor.runner...`) — не
эскалация: расхождение чисто в пути файла, само требование 3 выполнено
буквально (первая строка вывода `doctor`, до остальных проверок).

Откат: все пять правок независимы и обратимы по отдельности (`git
revert` соответствующего коммита) — ни одна не меняет схему БД, формат
существующих алертов или чужой код.

- Несколько открытых алертов стоп-крана одновременно (разные классы

  возвращает список, а не одну строку; `doctor`/`status`/отказ `run`
  перечисляют/учитывают их все, не только первый.
