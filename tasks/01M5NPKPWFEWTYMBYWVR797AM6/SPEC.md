# SPEC: команда пульта `mutation-run` — прогон патчей мутаций против названных тестовых файлов во временной копии и таблица «мутация → исход»

## Контекст
Доказательство неослабления при консолидации тестов артели — множество
убиваемых мутаций (строка бэклога «Периодическая консолидация тестов
артели», решение Оператора 23.10.2026; ADR-0027 п. 8). Внутри шага роли
прогон мутаций не исполним: сторож роли в корневом `conftest.py`
(`pytest_configure`) роняет рабочие процессы xdist под `ARTEL_ROLE`
(«node down», «no tests ran»). Шагу доступны только рабочая копия и
каталог документов. Около 70 мутаций последовательно не укладываются в
`AGENT_TIMEOUT_SEC` = 2700 с (`orchestrator/config.py:132`). Команды
пульта для такого прогона нет. Задача добавляет её по образцу `suite-run`
(`orchestrator/suite_run.py`): фоновый прогон, окружение без признака
роли, временная копия клона, замок `suite_lock`, лог и таблица исходов
в каталоге хозяйства `suite-run`.

## Требования

1. Команда `artel.py mutation-run <id> --ref <base|head|worktree> --tests <путь>[,<путь>…] [--patches <a>-<b>] [--wait <минуты>]`.
   - Патчи — файлы `mutation-<nnn>.diff` каталога документов задачи на
     диске (`artifact_branch.docs_dir(id, target)`). Если этого каталога
     на диске нет, патчи берутся из `refs/artifacts/<id>`
     (`artifact_branch.ls_tree`, `show`).
   - Набор патчей пуст — отказ без запуска с текстом «патчей мутаций нет».
   - `--patches` задаёт диапазон номеров; по умолчанию прогоняются все
     патчи. Отказ без запуска получают: запись не вида `<a>-<b>` с целыми
     `a`, `b`; обратный диапазон (`a` больше `b`); диапазон, выходящий за
     номера набора (`a` меньше наименьшего или `b` больше наибольшего
     номера патча).
   - `--ref base` — база ветки задачи (`gitcmd.diff_base`).
   - `--ref head` — закоммиченная голова кодовой ветки задачи.
   - `--ref worktree` — HEAD рабочей копии задачи плюс её незакоммиченные
     файлы (приём `appendix_tree._carry_uncommitted`). Рабочая копия при
     этом только читается.
   - `--tests` — явные пути файлов под `tests/`. Каждый путь
     нормализуется относительно корня репозитория. Разрешён только
     существующий файл `test_*.py` под `tests/`. Отказ без запуска
     получают: пустой список; каталог в любой записи списка (`tests`,
     `tests/`, `./tests`, `tests/.`, подкаталог `tests/`); путь вне
     `tests/`; несуществующий файл; файл под `tests/` с именем не вида
     `test_*.py`. Полный набор этой командой не гоняется.
   - Проверка `--tests` идёт до создания временной копии, по дереву
     выбранной ревизии: для `--ref base` и `--ref head` — `git ls-tree`
     этой ревизии; для `--ref worktree` — рабочая копия задачи вместе с её
     незакоммиченными файлами. После создания копии повторная сверка не
     делается.
2. Команда поддерживает только раннер пульта: профиль тестов проекта
   отсутствует (`profile is None`, запись артели `pult-pytest`). Для
   проекта с иным профилем команда отказывает без запуска с текстом
   «профиль проекта не поддержан командой mutation-run».
3. Прогон идёт фоном, как у `suite-run`: `--wait` — не больше 9 минут,
   отчёт — повторным вызовом команды. Окружение фонового прогона не
   содержит `config.ARTEL_ROLE_ENV`: признак роли команда снимает только
   у своего фонового процесса, как `suite-run`
   (`orchestrator/suite_run.py:921–922`); сторож корневого `conftest.py`
   не меняется.
4. Временная копия создаётся через `suite_run._base_copy` (префикс
   `artel-suite-base-` и маркер владельца `liveness.SUITE_OWNER_MARKER`
   прежние). Она убирается на любом исходе, в том числе при исключении.
   После подготовки копии (для `--ref worktree` — вместе с перенесёнными
   незакоммиченными файлами) в копии делается локальный коммит-основа.
5. Перед патчами выполняется контрольный прогон названных тестов без
   патча. Контроль красный, если в отчёте есть любая запись `failed` или
   `error`, любая запись уровня файла, код возврата ненулевой или итог
   контроля — «итог неизвестен». Красный контроль — отказ всей команды с
   текстом «тесты красные без мутаций»; ни один патч не прогоняется.
   Контрольный прогон, оборванный по пределу (требование 7), красным не
   считается: это отказ всей команды с текстом «контрольный прогон оборван
   по пределу N с», где N — предел в секундах, а не «тесты красные без
   мутаций»; ни один патч не прогоняется.
6. Патчи прогоняются по очереди. Для каждого патча:
   - Патч «трогает тесты», если среди его путей есть путь под `tests/`,
     путь из `--tests`, файл `conftest.py` в любом каталоге,
     `pyproject.toml`, `pytest.ini`, `.pytest.ini`, `pytest.toml`,
     `setup.cfg` или `tox.ini`. Переименование и копирование (`copy
     from`/`copy to`) проверяются по обоим путям — исходному и новому.
     Такой патч не применяется; его исход — «патч трогает тесты».
   - Иначе патч применяется `git apply`. При отказе исход — «патч не
     применяется».
   - Применённый патч прогоняется через `acceptance.run_full_suite` с
     `--continue-on-collection-errors` и junit-xml вне копии.
   - После каждого патча копия сбрасывается к коммиту-основе:
     `git reset --hard <основа> && git clean -ffdx`. Если затем
     `git status --porcelain` не пуст (в копии остался посторонний файл),
     вся команда отказывает; причина отказа называет непустой
     `git status --porcelain` после сброса.
7. Предел профиля (`project_profile.full_suite_limit(target)`) действует
   на всю команду, включая контрольный прогон. Каждый прогон получает
   остаток предела от старта команды. Когда предел истёк, текущая мутация
   получает исход «оборвана по пределу», каждая оставшаяся — «не прогнана
   (предел)»; строки всех этих мутаций пишутся в таблицу.
8. Исход прогнанной мутации определяется по коду возврата и разбору
   junit-xml (`reporters/outcome.parse_junit`):
   - «убита» — есть хотя бы одна запись `failed` не уровня файла; к
     исходу прилагается список таких узлов;
   - «ошибка сбора, импорта или setup» — таких записей `failed` нет, но
     есть `error` или запись уровня файла (в том числе запись уровня файла
     с `failed`). Этот исход не считается доказательством;
   - «не убита» — код возврата 0 и все записи `passed`/`skipped`;
   - «итог неизвестен» — отчёта нет, он не разобран или пуст при
     ненулевом коде возврата; либо код возврата ненулевой, а записей
     `failed` и `error` нет. Такой исход никогда не засчитывается как «не
     убита» (инвариант 41);
   - «оборвана по пределу», «не прогнана (предел)» — требование 7;
   - «патч не применяется», «патч трогает тесты» — требование 6.
9. Таблица исходов — файл `<id>-mutation-run-<n>.mutations.tsv` рядом с
   логом `<id>-mutation-run-<n>.log` в `suite_lock.directory()/<id>/`.
   - Шапка таблицы несёт источник патчей, sha ревизии прогона и sha256
     каждого патча. Источник — «каталог на диске» либо «ссылка» с sha
     ссылки `refs/artifacts/<id>`, из которой взяты патчи.
   - Строка таблицы — номер патча, исход и узлы через запятую.
   - Строка пишется сразу после каждой мутации.
10. У команды свои файлы состояния — `mutation-run.json` и
    `mutation-result.json`. Файл `run.json` прогона `suite-run` она не
    использует. Документы задачи (каталог документов и
    `refs/artifacts/<id>`), её ветка и рабочая копия командой не меняются.
    - Под ролью на Codex (БД пульта доступна только на чтение) команда
      ведёт себя как `suite-run` в той же обстановке
      (`orchestrator/suite_run.py:169–179`,
      `orchestrator/suite_lock.py:194–196`): состояние пишется в каталог
      хозяйства `suite-run`, в БД команда не пишет.
11. Команда берёт замок `suite_lock`; держатель описывается как `suite-run`
    задачи, это принимается. Номер прогона в замке несёт префикс `m`
    (например `"m3"`), чтобы `suite_lock.adopt()` не спутал его с прогоном
    `suite-run` той же задачи. Замок занят — команда не ждёт, а отказывает
    сразу, без запуска, называя держателя, как `suite-run`
    (`orchestrator/suite_run.py:907–911`). Предел профиля не поднимается: набор патчей,
    не укладывающийся в предел, делится на части аргументом `--patches`.
12. Команда разрешена роли (`_ROLE_ALLOWED_COMMANDS`,
    `orchestrator/artel.py:2181`). Она регистрируется в словаре `table`
    функции `artel.main` и строкой блока «Команды:» докстринга
    `orchestrator/artel.py`. Таблица — свидетельство, не гейт: никакой
    гейт пульта её не читает.
13. Тесты команды лежат в новом файле `tests/`, написанном в стиле pytest
    (ADR-0027):
    - имена функций — `test_ac<n>_…`;
    - у каждой функции есть строка «Ловит мутацию:»;
    - нет ожидания по часам: фоновая часть вызывается в процессе теста
      напрямую, либо ожидание идёт помощниками `tests/sandbox.py`;
    - значение `config.FULL_SUITE_WORKERS` в коде не меняется
      (`orchestrator/config.py:230`); в тестах оно подменяется на 2.

## Критерии приёмки

AC-1. В проекте песочницы с модулем и тестом прогоняются два патча: первый ломает функцию модуля, второй меняет только комментарий. В таблице у первого стоит исход «убита» с именем упавшего узла, у второго — «не убита».

AC-2. Патч, вносящий синтаксическую ошибку в модуль, получает исход «ошибка сбора, импорта или setup», а не «убита» и не «не убита». Запись `failed` уровня файла даёт тот же исход, а не «убита».

AC-3. Патч, который не применяется `git apply`, получает исход «патч не применяется». Исход «патч трогает тесты» получает и не применяется каждый из патчей: трогающий файл под `tests/`; трогающий `conftest.py` в подкаталоге вне `tests/`; трогающий `pyproject.toml`; трогающий `pytest.ini`, `.pytest.ini`, `pytest.toml`, `setup.cfg` или `tox.ini`; переименовывающий файл модуля в путь под `tests/`; переименовывающий файл под `tests/` в путь вне `tests/`; копирующий (`copy from`/`copy to`) файл модуля в путь под `tests/`; копирующий файл под `tests/` в путь вне `tests/`.

AC-4. Контрольный прогон без патча красный — команда отказывает целиком с текстом «тесты красные без мутаций», и ни один патч не прогоняется. Отказ наступает в каждом случае: в контроле есть упавший тест; в контроле есть только ошибка сбора файла (запись уровня файла); контроль кончился ненулевым кодом возврата без записей `failed` и `error`. Контрольный прогон, оборванный по пределу, даёт отказ всей команды с текстом «контрольный прогон оборван по пределу N с» (N — предел в секундах), а не «тесты красные без мутаций», и ни один патч не прогоняется.

AC-5. Каждый из вызовов отказывает без запуска — контрольный прогон и прогон патчей не стартуют, замок не берётся, временная копия не создаётся: `--tests tests`; `--tests tests/`; `--tests ./tests`; `--tests tests/.`; `--tests` с подкаталогом `tests/`; список, в котором одна запись — файл `tests/test_*.py`, а другая — `tests/`; пустой список `--tests`; путь вне `tests/`; несуществующий файл `tests/test_*.py`; файл под `tests/` с именем не вида `test_*.py`; `--ref base` с файлом `tests/test_*.py`, который есть на диске рабочей копии задачи, но не в дереве базы; пустой набор патчей — с текстом «патчей мутаций нет»; `--patches x`; `--patches 5-2`; `--patches` с диапазоном за номерами набора.

AC-6. После прогона временная копия `artel-suite-base-…` убрана. Она убрана и после исключения посреди прогона. Когда после сброса в копии остаётся посторонний файл (сброс подменён), вся команда отказывает с причиной, называющей непустой `git status --porcelain`, и копия убрана и в этом случае. После команды не изменились: у рабочей копии задачи — `git status --porcelain` и HEAD; у главной копии — `git status --porcelain`, HEAD, ветки `refs/heads/*`, ссылки `refs/artifacts/*` и `git worktree list`; у задачи — sha ссылки `refs/artifacts/<id>` и содержимое каталога документов.

AC-7. Тест запускает команду настоящим подпроцессом CLI с `ARTEL_ROLE=developer` в окружении и с `--wait`; в проекте песочницы лежит свой `conftest.py`-сторож, роняющий процессы под `ARTEL_ROLE`. Прогон с xdist (`config.FULL_SUITE_WORKERS` подменён на 2) проходит, и исходы мутаций получены. Если фоновый прогон не снимает признак роли, тест красный.

AC-8. Прогоняются три патча; прогон второго подменён исходом «предел». Таблица содержит строку первой мутации с её исходом, строку второй с исходом «оборвана по пределу» и строку третьей с исходом «не прогнана (предел)». Предел, переданный каждому прогону команды, не больше остатка предела профиля от старта команды.

AC-9. С `--ref worktree` прогон видит незакоммиченный тестовый файл рабочей копии задачи: тест, названный в `--tests`, существует только незакоммиченным. Он прогоняется в контроле и при каждом из трёх патчей, ломающих функцию модуля: у всех трёх, в том числе у второго и третьего, исход «убита» с узлом этого теста.

AC-10. `--patches 2-2` прогоняет только второй патч: в таблице одна строка, с номером 2.

AC-11. Шапка таблицы `<id>-mutation-run-<n>.mutations.tsv` несёт sha256 каждого прогнанного патча, источник патчей и sha ревизии прогона. Таблица лежит рядом с логом `<id>-mutation-run-<n>.log` в `suite_lock.directory()/<id>/`. Каталог документов задачи на диске есть — источник в шапке «каталог на диске». Каталога документов на диске нет — патчи берутся из `refs/artifacts/<id>`, прогон идёт, источник в шапке «ссылка» с sha этой ссылки.

AC-12. Исход мутации «итог неизвестен», не «не убита», в каждом случае: отчёт junit-xml отсутствует; отчёт не разобран; отчёт пуст при ненулевом коде возврата; код возврата ненулевой, а в отчёте только записи `passed`/`skipped`.

AC-13. Номер прогона `mutation-run`, записанный в замке `suite_lock`, несёт префикс `m`. Команда пишет свои файлы состояния `mutation-run.json`/`mutation-result.json` и не создаёт и не меняет `run.json` прогона `suite-run` той же задачи. Когда БД пульта открывается только на чтение, команда пишет состояние в каталог хозяйства `suite-run` и ничего не пишет в БД. Когда замок `suite_lock` занят другим прогоном, команда сразу отказывает с описанием держателя: контрольный прогон не стартует, временная копия не создаётся.

AC-14. `mutation-run` значится в словаре `table` функции `artel.main`, в строке блока «Команды:» докстринга `orchestrator/artel.py` и в `_ROLE_ALLOWED_COMMANDS`.

AC-15. Для проекта с профилем тестов, отличным от раннера пульта, команда отказывает с текстом «профиль проекта не поддержан командой mutation-run»; контрольный прогон не стартует, замок не берётся.

| Фоновый прогон без признака роли | Сторож роли роняет pytest под `ARTEL_ROLE` — `conftest.py:80` (`pytest_configure`) | Остаётся: сторож не меняется; признак снимается только у фонового процесса команды, как у `suite-run` (`orchestrator/suite_run.py:921–922`) | AC-7; неизменность `conftest.py` — «Не входит» | Остаётся |

## Оценка объёма и деление
Сработавшие сигналы:
- число критериев приёмки ≥ 10 — их 15;
- зона, возможно, задевает механизм, на который опирается запись
  `docs/invariants.md`: запись 41 — «итог неизвестен» не равен «не убита»;
  команда потребляет этот механизм, сам механизм не меняется.

Предлагаемое решение — монолит. Что нельзя разрезать:
- Весь код задачи — один новый модуль `orchestrator/mutation_run.py`
  плюс строки регистрации в `orchestrator/artel.py`. Регистрация без
  модуля указывает на несуществующую команду, а модуль без регистрации
  недостижим из CLI и из роли.
- Тесты по ТЗ лежат новым файлом `tests/` и проверяют поведение этого же
  модуля. Тесты без модуля красные, модуль без тестов не проходит
  приёмку.
- Части фонового прогона связаны по данным: разбор аргументов, копия на
  ref, контроль, цикл патчей с откатом, таблица и замок пишут общие файлы
  состояния и таблицу. Ни один из этих кусков сам по себе не даёт
  работающей команды.

Решение принимает Оператор на гейте SPEC.
