# PLAN: Стоп-кран auto по повторному отказу advance

## Подход

Инцидент T035: `cmd_advance` уже журналирует каждый свой отказ (кроме
guard'а структуры артефакта) записью `actor="fsm"`, `action` вида
«переход отклонён[: причина]» — этот текст ничем не отличается между
вызовами, если причина отказа не изменилась. `cmd_auto` (`orchestrator/auto.py`)
сегодня смотрит только на смену `state`, а не на журнал, поэтому не видит
разницы между «агент ещё работает» и «advance отказывает по одной и той же
внешней причине раз за разом».

Решение — целиком внутри `cmd_auto`, без изменений `fsm.py` (SPEC,
«Не входит»): после каждого `run`+`advance` без смены состояния цикл
смотрит в журнал, что именно записал `fsm.cmd_advance` ЗА ЭТОТ вызов
(watermark по числу строк журнала задачи до вызова, а не по всей истории —
иначе отказ прошлого шага засчитался бы за отказ текущего). Если это
запись с `action`, начинающимся на «переход отклонён», её текст сравнивается
с текстом такой же записи предыдущего шага (`prev_refusal`, переменная
цикла, `None` в начале и после любого шага, где сравнение не подошло).
Совпал текст на двух подряд шагах без смены состояния — стоп, тем же по
характеру способом, что и существующие остановки `auto_stop`: журнал,
причина (переиспользуется журнальный текст `fsm`) и подсказка «почини
причину и повтори `artel.py advance <id>`».

Guard структуры артефакта (SPEC T034, требование 2) не участвует в этой
проверке: `fsm.cmd_advance` в этом случае возвращает `True`, и существующая
ветка `cmd_auto` останавливается раньше, до вычисления watermark'а нового
правила, — правила не пересекаются по построению (SPEC, требование 3).

Шаг, на котором `advance` не журналировал отказ («переход отклонён» не
записан — SPEC.md/PLAN ещё не ready), обнуляет `prev_refusal`: он не
часть серии (требование 4), и, что важно, не даёт двум ОДИНАКОВЫМ, но
НЕ подряд идущим отказам склеиться через него в ложную остановку.

## Шаги

1. `orchestrator/auto.py`: добавить константу `REFUSAL_ACTION_PREFIX`,
   приватную функцию поиска записи журнала «переход отклонён…»,
   добавленной конкретным вызовом `cmd_advance` (watermark по числу строк
   журнала до вызова), и логику подсчёта серии из двух подряд одинаковых
   отказов в `cmd_auto` с остановкой через существующий `auto_stop`.
   Юнит-тесты в `tests/test_auto_cycle.py` на все критерии приёмки
   (одинаковый текст дважды подряд — стоп; агент ещё работает — не стоп;
   разный текст — не стоп; серия рвётся шагом без журналируемого отказа).

## Влияние на систему

Изменение — только внутри `cmd_auto`, добавляет дополнительное условие
остановки цикла; ничего не ослабляет — наоборот, сужает окно, в котором
цикл может сжечь бюджет на повторе одного и того же детерминированного
отказа (сам инцидент T035). `config.AUTO_MAX_STEPS` — верхняя защита —
не изменяется и продолжает работать как и раньше для серий, которые
новое правило не ловит (разный текст отказа, отказ без журнала). Ручные
гейты (`spec_gate`, `acceptance`, `merge_gate`) новое правило не
затрагивает — из них `advance` не вызывается циклом вовсе (условие
`while role is not None`), это область другого требования (T034,
требование 3). Существующие тесты `tests/test_auto_cycle.py` и локальные
приёмочные тесты `tasks/T038/acceptance_tests/` — код чинится под них,
их правка не входит в задачу (SPEC, «Не входит»; acceptance_tests
залочены tasks/T023).

Откат — правка одного файла (`orchestrator/auto.py`), без миграций схемы
и без изменения формата журнала: `git revert` коммита задачи.
