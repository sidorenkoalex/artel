# SPEC: эскалация «конфликт подтяжки main» называет конфликтные файлы

## Контекст

`_pull_main_or_escalate` (`orchestrator/fsm.py`) при неудачном `git
merge` пишет в `detail` эскалации только `merge.stderr` (обрезанный до
500 символов). Git же печатает список конфликтующих файлов
(«CONFLICT (content): Merge conflict in <файл>») и «Automatic merge
failed» в **stdout**, а не в stderr — эскалация приходит с пустой
причиной («конфликт подтяжки main в ветку …: »). Оператор 05.09 трижды
воспроизводил слияние руками, чтобы узнать список файлов; все три
конфликта были аддитивными (`docs/backlog.md`).

## Требования

1. При конфликте подтяжки, который не разрешается автоматически
   (`_auto_resolve_map_conflict` не сработала или неприменима), `detail`
   эскалации несёт: список конфликтных файлов (`git diff --name-only
   --diff-filter=U`, вызванный до `merge --abort`), первые строки
   stdout `git merge` (ограничение — 500 символов, тем же приёмом, что
   уже применяется к stderr) и stderr, если он не пуст (тоже до 500
   символов). Формат: одна строка «конфликтные файлы: a, b, c», затем
   хвост вывода.
2. Тот же список и хвост вывода видны в выводе `run`/`auto` без
   отдельного обращения к `artel.py log` — существующий канал
   (`store.set_state` печатает `detail` в скобках после `-> {state}`,
   `orchestrator/store.py:655`) достаточен: требование выполняется тем
   же изменением, что и требование 1, не отдельным кодом вывода.
3. Автоматическое разрешение карты (`_auto_resolve_map_conflict`, T067)
   и остальное поведение подтяжки (успешный merge, «ветка не отстала»,
   красная приёмка после подтяжки) не меняются. `git merge --abort`
   по-прежнему выполняется до записи эскалации при неразрешённом
   конфликте.

## Критерии приёмки

AC-1. Конфликт merge, где единственный конфликтующий файл — НЕ
`docs/codebase-map.md` (авторазрешение не применяется), приводит к
`detail` эскалации, содержащему строку «конфликтные файлы: <имя файла>»
и строку с `CONFLICT` из stdout `git merge` (обрезано до 500 символов,
как stderr сейчас).

AC-2. Конфликт merge, где конфликтующих файлов два — `docs/codebase-
map.md` и ещё один файл: `_auto_resolve_map_conflict` не вызывается
(или вызывается и не завершает merge — список конфликтов не равен
ровно `[MAP_REL]`), `git merge --abort` выполняется, `detail` несёт
оба имени файлов через `, ` в строке «конфликтные файлы: …».

AC-3. `git merge` вернул ненулевой код с пустыми `stdout` и `stderr`
(и/или `git diff --name-only --diff-filter=U` тоже пуст) — `detail` не
содержит пустых хвостов (лишних пустых строк, `; ` без текста после
и т.п.); формат деградирует так же, как прежний вырожденный случай
«git не ответил осмысленно».

AC-4. Существующие тесты подтяжки — `tests/test_branch_freshness_gate.py`
(сценарии свежести/конфликта T051/T052/T053) и `tests/test_fsm_map_
conflict_autoresolve.py` (T067, авторазрешение карты) — остаются
зелёными без ослабления их утверждений.

AC-5. Единственный конфликтующий файл — ровно `docs/codebase-map.md`:
поведение `_auto_resolve_map_conflict` (checkout --theirs + регенерация
+ commit) не меняется — при успехе merge завершается без эскалации, при
неудаче любого шага — `merge --abort` и эскалация по правилам AC-1/
AC-2/AC-3 (список конфликтов на момент неудачи).

## Не входит

- Автоматическое разрешение аддитивных конфликтов (не карты) —
  наблюдение копилки `docs/backlog.md`, отдельное решение Оператора.
- Изменение формата/канала вывода `run`/`auto` сверх уже
  существующего (`store.set_state` печатает `detail`) — требование 2
  закрывается содержимым `detail`, не новым кодом печати.
- Любые изменения `_auto_resolve_map_conflict` самой по себе (условие
  и механика разрешения карты, T067) — только чтение списка конфликтов
  вокруг неё не должно менять её поведение.
