# PLAN: CR-2 — тихая финализация соединения БД из чужого потока

## Подход
`_AutoClosingConnection.__del__` (orchestrator/store.py:74-90) сегодня —
голый `self.close()`. Когда объект уничтожается в потоке, отличном от
создавшего соединение, `close()` бросает `sqlite3.ProgrammingError`;
поскольку это происходит внутри `__del__`, интерпретатор не даёт
исключению распространиться — вместо этого печатает в stderr
«Exception ignored in: ... Traceback ...». Это штатное (не баговое)
поведение sqlite3 — соединение и так безопасно освобождается GC, просто
`close()` из чужого потока невозможен по ограничению самой библиотеки.

Решение — узкий `try/except sqlite3.ProgrammingError: pass` вокруг
`self.close()` внутри `__del__`. Никакая другая логика не меняется:
класс, `db()`, `enable_wal`, `migrate` — не трогаются. Путь «закрытие из
своего потока» не проходит через `except`, потому что там
`ProgrammingError` не возникает вовсе — поведение T090
(`test_no_resourcewarning_when_connection_is_used_inline_and_discarded`)
не меняется физически, а не только по результату теста.

Единственная архитектурно значимая деталь — то, что перехват должен
быть именно по классу `sqlite3.ProgrammingError`, не по более широкому
`sqlite3.Error` или `Exception`: иначе перехват скрыл бы реальные ошибки
`close()` (диск, повреждение БД). ADR не требуется — точечная правка
обработки исключения в приватном методе, не архитектурное решение.

## Шаги

1. Обернуть `self.close()` в `_AutoClosingConnection.__del__`
   (orchestrator/store.py) в `try/except sqlite3.ProgrammingError: pass`.
   Добавить юнит-тест в `tests/test_store_db_connection_close.py`,
   покрывающий кросс-поточную финализацию (в дополнение к приёмочным
   AC-1..AC-4, которые уже фиксируют требование с mock и с реальными
   потоками).

## Покрытие требований

| Требование SPEC | Шаг |

| 1 (перехват ProgrammingError в __del__, не течёт наружу) | 1 |
| 2 (перехват узкий — только ProgrammingError) | 1 |

## Влияние на систему
Правка ограничена телом `__del__` одного класса в `orchestrator/store.py`
— единственного модуля, пишущего SQL (ADR-0003 3ж). `db()` вызывается
сотнями мест кодовой базы инлайн; поведение `close()` для «своего
потока» и семантика `db()` (WAL, `row_factory`, схема) не меняются —
проверено существующим `tests/test_store_db_connection_close.py`
(четыре теста, включая T090) и приёмочными AC-1..AC-4. Перехват сужен
до одного конкретного класса исключения — не ослабляет ни один
существующий тест, гейт или инвариант; расширения `except` не вносится.
Откат — удалить `try/except`, вернуть `self.close()`.

## Риски
Нет рисков за пределами описанного: изменение локально, тесты SPEC
полностью его специфицируют (mock-уровень AC-1, реальные потоки AC-2,
неизменность T090 AC-3, полный прогон AC-4).
