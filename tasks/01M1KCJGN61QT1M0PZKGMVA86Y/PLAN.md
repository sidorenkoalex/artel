# PLAN: CR-2 — тихая финализация соединения БД из чужого потока

## Подход
`_AutoClosingConnection.__del__` (orchestrator/store.py) сегодня вызывает
`self.close()` без обработки исключений. Когда сборщик мусора добивает
объект в потоке, отличном от создавшего соединение, `sqlite3` запрещает
закрытие и поднимает `sqlite3.ProgrammingError`; поскольку вызов идёт из
`__del__`, интерпретатор гасит распространение сам, но предварительно
печатает в stderr блок «Exception ignored in: … ProgrammingError: SQLite
objects created in a thread can only be used in that same thread.» — это
штатный, безопасный случай (объект всё равно освобождается), но шум
маскирует настоящие предупреждения при прогоне тестов.

Решение — узкий `try/except sqlite3.ProgrammingError: pass` вокруг
`self.close()` внутри `__del__`. Никакой другой логики не меняется:
закрытие из своего потока (`ResourceWarning`-путь T090) не задевается,
потому что там `ProgrammingError` не возникает вовсе — перехватывать
нечего. Альтернатива (проверять `threading.current_thread()` до вызова
`close()`) отклонена: `sqlite3` уже делает эту проверку и сообщает её
результат типом исключения — дублировать её логику отдельным условием
избыточно и рискует разойтись с реальным критерием sqlite3 при будущих
изменениях CPython/sqlite3.

Архитектурно решение не значимо (13 строк в одном классе) — отдельный
ADR не нужен.

## Шаги

1. `orchestrator/store.py`: обернуть `self.close()` в `__del__`
   `_AutoClosingConnection` узким `try/except sqlite3.ProgrammingError:
   pass`; короткий комментарий-«почему» над `__del__` (штатность
   кросс-поточной финализации, причина узости перехвата).
2. `tests/test_store_db_connection_close.py`: юнит-тест
   `test_del_swallows_programmingerror_from_foreign_thread_close` —
   `close()` подменяется моком, бросающим `sqlite3.ProgrammingError`
   (сигнатура сообщения sqlite3 при межпоточном закрытии), `__del__()`
   вызывается из отдельного потока напрямую; тест проверяет отсутствие
   исключения. Существующий тест
   `test_no_resourcewarning_when_connection_is_used_inline_and_discarded`
   (T090) не тронут — тем же путём и байт-в-байт (AC-3 проверяет это
   явно через `inspect.getsource`).

Оба шага уже реализованы в рабочем дереве на момент постановки этого
плана (диф см. `git diff` по обоим файлам) — план фиксирует их задним
числом и служит чек-листом покрытия требований/критериев ниже.

## Влияние на систему
Правка ограничена телом `__del__` одного класса
(`_AutoClosingConnection`, orchestrator/store.py:74-100) — единственная
точка создания соединений в кодовой базе (`store.db()`), от неё зависят
все модули, читающие/пишущие `state.db` (список — секция «Импортируется»
`orchestrator/store.py` в docs/codebase-map.md). Перехват сужен до
конкретного класса исключения и до конкретной точки вызова (`close()`
внутри `__del__`), поэтому он не маскирует:
- ошибки `close()` иной природы (IntegrityError и т.п. — не
  перекрываются `sqlite3.ProgrammingError`, пробрасываются как раньше;
- закрытие из своего потока — там `ProgrammingError` не возникает,
  ветка перехвата не задействуется, `ResourceWarning`-инвариант T090
  (tests/test_store_db_connection_close.py) не меняется;
- любой другой код в `__del__` — тела `try` нет ничего, кроме
  `self.close()`.

Существующие тесты/инварианты не ослаблены: T090
(`test_no_resourcewarning_when_connection_is_used_inline_and_discarded`)
проходит без изменения исходного кода (AC-3 проверяет это байт-в-байт),
`test_row_factory_and_wal_unchanged` и
`test_explicit_close_then_gc_does_not_raise` не затронуты. Откат —
удалить `try/except`, вернуть `self.close()` (однострочный revert).

## Риски
Перехват `sqlite3.ProgrammingError` теоретически мог бы скрыть ошибку
`close()` того же типа исключения, но иной причины (не межпоточность).
На практике `sqlite3.Connection.close()` поднимает `ProgrammingError`
только в двух случаях: закрытая-повторно операция после `close()` (сам
`close()` идемпотентен и не бросает при повторном вызове) и
межпоточный запрет — второй случай и есть предмет CR-2. Риск принят как
несущественный: он совпадает с риском, уже принятым для CR-3 прошлой
ревизии (та же природа мотивации).
