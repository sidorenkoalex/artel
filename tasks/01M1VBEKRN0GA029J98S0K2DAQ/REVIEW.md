## Замечания

- major — `orchestrator/watch.py:149-160,224` — `_emit_alerts` фильтрует новые алерты по `set(selection)` — ТЕКУЩЕЙ (пересчитанной в этой же итерации) динамической выборке, а не по объединению `selection ∪ known_step_id`, которое использует остальной цикл (`watch.py:209`, обоснованное в PLAN.md пункт 3 «Ключевые решения» именно тем, что задача, выпавшая из `--all`/`--mine` (стала терминальной либо сменила владельца), обязана продолжать наблюдаться, иначе её последний переход пропадёт). Как только задача выходит из динамической выборки, курсор `known_alert_id` в `_emit_alerts` необратимо проходит мимо всех последующих алертов с `target`, равным её id — они не печатаются никогда, хотя SPEC AC-3 не оговаривает такого исключения («kind не фильтруется» — про выход задачи из выборки речи тоже нет), а PLAN.md прямо признаёт тот же риск для `steps`/`STATE` и чинит его объединением. Воспроизведено вручную (песочница `tests.sandbox.TmpRootTest`, `watch --all --events alerts --interval 0.3`): задача переведена в `done` и в тот же момент заведён алерт с `target` этой задачи — `STATE=done` печатается, алерт — нет ни в этой итерации, ни в последующих. Тот же класс дыры — для `--mine` при смене владельца (перехват lease) задачи в процессе работы `watch`. Предложение: в `_emit_alerts` фильтровать по объединению `selection ∪ known_step_id` (или отдельному множеству id всех когда-либо виденных задач), тем же приёмом, что уже применён для `steps`/`STATE` на `watch.py:209`.
