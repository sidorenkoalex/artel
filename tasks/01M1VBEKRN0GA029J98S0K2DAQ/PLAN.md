# PLAN: команда `watch` — дозор событий журнала для сессии Оператора

## Подход

Один новый модуль `orchestrator/watch.py` с единственной публичной
функцией `cmd_watch(argv: list[str]) -> None` (сигнатура зафиксирована
приёмочными тестами `tasks/01M1VBEKRN0GA029J98S0K2DAQ/acceptance_tests/
test_watch.py`): сам разбирает сырой `argv` без argparse — тем же
приёмом ручного разбора, что и остальные команды `artel.py`
(`_tz_arg`/`_k_arg`/`_reason_arg`). Один вход в `artel.py` (таблица
диспетчера `main()`). Монолит — по решению Оператора 06.09 из SPEC
«Оценка объёма»: резать нечего.

Ключевые решения:

1. **Селекторы валидируются до единого обращения к БД** (AC-1):
   `_parse_args` — чистая функция над `argv`, не импортирует `store` и
   не вызывает `store.db()`; счётчик присутствующих флагов `--tasks`/
   `--mine`/`--all` проверяется первым действием.
2. **База отсчёта — «первый взгляд» на задачу**, не момент запуска
   команды буквально: при первом появлении id задачи в объединении
   «текущая выборка ∪ уже известные id» её текущий последний `steps.id`
   и текущее `tasks.state` запоминаются БЕЗ печати — это и даёт
   «поток только новых записей» (AC-2) единым кодом для задачи из
   стартовой выборки и для задачи, обнаруженной опросом позже (AC-11) —
   разницы в коде между ними нет, только момент первого взгляда.
3. **Отслеживание состояния (`STATE=`) идёт по ОБЪЕДИНЕНИЮ выборки и
   уже известных задач**, не по одной текущей выборке: `--all`
   динамически перестаёт включать задачу, как только она становится
   терминальной (`state NOT IN ('done','killed')` — то же условие, что
   и у самого селектора), и без объединения последний переход такой
   задачи в `done`/`killed` остался бы ненапечатанным — AC-7 требует
   печати смены состояния независимо от `--events`, не «пока задача
   ещё в выборке». Не покрыто отдельным AC, но напрямую следует из
   буквального требования 4 SPEC («смена... печатается... в любой
   момент»); без объединения тест на этот случай не писали, но
   поведение осталось бы тихо неверным для `--all`.
4. **`--until` замораживает выборку**: при заданном `--until`
   динамический пересчёт `--mine`/`--all` (AC-5) не идёт — выборка,
   вычисленная один раз до входа в цикл (и уже проверенная на «ровно
   одна задача», AC-6), остаётся той же самой задачей всю жизнь
   команды. `--until` по определению следит за ОДНОЙ конкретной
   задачей; допустить, чтобы список из одного элемента внезапно стал
   пустым или расширился из-за перевычисления `--all` на следующей
   итерации, значило бы потерять саму цель наблюдения без единого
   печатного сигнала об этом. AC-5 (тест DynamicAllSelectionTest)
   `--until` не использует — противоречия с приёмочными тестами нет.
5. **`store.py` получает два новых read-only метода**, а не остаётся
   совсем без изменений, как предполагала оценка объёма SPEC («`store.
   py` — только чтение через существующие функции»): у существующих
   функций алертов (`open_alerts`) нет способа получить «новые записи
   с id больше X» без фильтра по `ack_ts IS NULL` — то есть подтверждённый
   (`ack`) во время работы `watch` алерт молча выпал бы из потока, хотя
   AC-3 такого исключения не описывает («`kind` не фильтруется» — про
   подтверждение не сказано ни слова). Единственный модуль, которому
   позволено писать SQL (ADR-0003 3ж) — `store.py`; добавляю туда
   `max_alert_id`/`alerts_since` тем же стилем, что уже несут соседние
   функции секции «Алерты» (`alerts_older_than`, `get_alert`) — без
   этого пришлось бы либо писать SQL в `watch.py` (нарушение ADR-0003
   3ж), либо молча терять подтверждённые алерты (расхождение с AC-3).
   Это разошлось с прогнозом SPEC «Оценка объёма» — фиксирую здесь,
   не оспариваю задним числом сам прогноз.

## Шаги

1. `orchestrator/store.py`: `max_alert_id(conn) -> int` (базовый снимок
   — id последнего существующего алерта на момент старта `watch`,
   0 — таблица пуста) и `alerts_since(conn, min_id) -> list` (алерты с
   `id > min_id`, по возрастанию `id`) — тем же местом и стилем, что
   секция «Алерты».
2. `orchestrator/watch.py` (новый): `cmd_watch(argv)` + приватные
   помощники разбора argv, выбора задач (`--tasks`/`--mine`/`--all`),
   классификации событий (`--events`), печати строки формата `log` с
   идентификатором задачи, цикла опроса (`--interval`) и условия выхода
   (`--until` либо истощение нетерминальных задач выборки).
3. `orchestrator/artel.py`: импорт `watch`, запись `"watch": lambda:
   watch.cmd_watch(rest)` в таблицу диспетчера `main()`, строка в
   `Команды:` и абзац с описанием + строка в списке «Модули пакета»
   верхнего докстринга (по образцу уже описанных там команд).
4. `docs/operator-session.md`, «Возобновление сессии», п.4 «Поставить
   дозор»: переписан на `artel.py watch --mine` как актуальный способ;
   прежние сценарии сессии (`watch_tasks.py`/`watch_spec_gate.py`) как
   актуальный способ не упоминаются (AC-9).
5. Юнит-тесты: приёмочные тесты `tasks/01M1VBEKRN0GA029J98S0K2DAQ/
   acceptance_tests/test_watch.py` (уже написаны test_author, залочены
   T023 — код чинится под них) покрывают AC-1..AC-13; AC-9 закрывается
   правкой doc-файла в шаге 4; AC-14 — существующий набор `tests/`
   остаётся зелёным без правки ассертов (проверяется прогоном
   затронутых модулей — `tests/test_store_journal.py`,
   `tests/test_session.py`, `tests/test_new_argv_parsing.py` — и самим
   CI на пуш ветки, не полным `tests/` из шага этой роли).

## Влияние на систему

- `orchestrator/store.py` — единственная незапланированная в «Оценке
  объёма» правка кода вне `watch.py`/`artel.py`: два новых read-only
  метода (`max_alert_id`, `alerts_since`), никакая существующая
  функция/таблица/SQL-запрос не меняется — регресс для остальных
  вызывающих мест исключён по построению (чисто аддитивная правка).
  Обоснование расхождения с прогнозом — в «Подходе», пункт 5.
- `watch` не проходит через `lease.py`/`fsm.py`/`runner.py` — открывает
  собственное соединение `store.db()` и только читает: `store.
  task_steps`/`store.all_tasks`/`store.get_task`-эквивалент (через
  `all_tasks`)/`store.alerts_since`/`store.max_alert_id`. Ни одна из
  них не пишет — принцип целостности не затронут (AC-8/AC-13 это же
  проверяют тестом на счётчики строк `steps`/`leases`/`alerts` до и
  после прогона).
  Ни `advisory lease`, ни лимитер `MAX_PARALLEL_TASKS`, ни зонный
  замок эту команду не проходят — она не мутирующая, тем же классом,
  что `status`/`log`/`doctor` (см. докстринг `artel.py`, инвариант о
  `release`).
- `docs/operator-session.md` — правка одного пункта одного раздела;
  остальные разделы файла не тронуты (сверено AC-9 приёмочного теста:
  секция вырезается по заголовкам `## `, посторонние правки тест не
  ловит, но и не требует).
- Откат: `orchestrator/watch.py` — новый файл, откатывается удалением;
  правка `store.py` — аддитивная, откатывается удалением двух функций;
  правка `artel.py` — снятие записи из таблицы диспетчера и импорта;
  правка `docs/operator-session.md` — точечная, `git revert` одним
  файлом без побочных эффектов на другие пункты.
- Гейт занятости зоны (`zone_lock`, SPEC 01M1P9QAG65GVF69YJEV0V18D9):
  `orchestrator/store.py` — общая зона по SPEC («конфликт текстовый»);
  два новых метода в конце секции «Алерты» — минимальная поверхность
  конфликта с параллельными задачами, трогающими тот же файл.

## Риски

- `--mine`/`--all` с пустой выборкой на старте (ни одной подходящей
  задачи прямо сейчас) немедленно завершает `watch` кодом 0 —
  буквальное прочтение AC-6 («пока есть хотя бы одна нетерминальная
  задача в выборке»: пустая выборка не содержит ни одной, условие
  ложно с самого начала). Для операторского сценария «`watch --mine`
  фоновым процессом ещё до того, как session взяла первый lease» это
  означает мгновенный выход, а не ожидание появления первой своей
  задачи — не предмет AC, но стоит держать в уме при запуске в
  `docs/operator-session.md`.
- `_owner_session_id` (выборка `--mine`) читает `task_steps` целиком на
  КАЖДУЮ задачу БД на каждой итерации опроса — O(число задач × размер
  журнала каждой) при пересчёте каждые `--interval` секунд. При
  типичном размере БД пульта (десятки задач, интервал по умолчанию
  30с) не проблема; при кратном росте числа одновременных задач могло
  бы стать поводом для отдельной оптимизации — вне объёма этой задачи.
