# SPEC: команда `watch` — дозор событий журнала для сессии Оператора

## Контекст
Сегодня дозор сессии Оператора — python-сценарии вне репозитория
(`watch_tasks.py`, `watch_spec_gate.py`): опрос `steps` раз в 30 секунд
по списку задач, вшитому при запуске (новую задачу подхватывает только
перезапуск), печать строк в формате, не совпадающем с `log`, разный
набор у каждой сессии. `docs/operator-session.md` («Возобновление
сессии», п. 4) требует «поставить дозор» отдельным ручным шагом —
нужна штатная команда пульта, читающая БД тем же способом, что и
остальной CLI, без побочных эффектов на состояние задачи.

## Требования

1. `artel.py watch [--tasks <id>[,<id>...]] [--mine] [--all]
   [--events <класс>[,<класс>...]] [--interval SEC] [--until <state>]`
   печатает на stdout поток новых записей журнала `steps` (и связанных
   записей таблицы `alerts` для класса `alerts`) выбранных задач,
   начиная с момента запуска команды, строками формата `log` (ts, task,
   actor, action, detail), без буферизации — `flush` на каждой строке.
2. Классы событий `--events` — именованные фильтры над `action`
   (и, для `alerts`, над таблицей `alerts`); по умолчанию
   `transitions,refusals,gates,steps`.
3. `--mine`/`--all` определяют выборку задач динамически: список
   пересчитывается заново каждый `--interval`, новая задача подхватывается
   без перезапуска команды.
4. Выход по `--until <state>` (для выборки из одной задачи) либо по
   истощению нетерминальных задач в выборке; код возврата 0. Смена
   `tasks.state` отслеживаемой задачи печатается отдельной строкой
   `STATE=<state>`.
5. `watch` не пишет в `steps`/`alerts`, не берёт lease, не меняет
   `tasks.state` — только чтение через собственное соединение
   `store.db()`, каждая итерация — свежий запрос (не переиспользует
   снимок предыдущей итерации).
6. `docs/operator-session.md`, п. 4 «Поставить дозор» — переписан:
   дозор — `artel.py watch --mine` фоновым процессом, прежние сценарии
   сессии не упоминаются как актуальный способ.

## Критерии приёмки

AC-1. `artel.py watch` принимает флаги `--tasks <id>[,<id>...]`,
`--mine`, `--all` (селекторы выборки задач — ровно один из трёх
обязателен; ни один не задан или задано более одного — ошибка
использования, код возврата ≠ 0, без обращения к БД), `--events
<класс>[,<класс>...]`, `--interval SEC` (по умолчанию 30) и `--until
<state>`.

AC-2. Пока команда запущена, она печатает на stdout, без буферизации
(`flush` сразу после каждой строки), новые записи `steps` выбранных
задач, появившиеся с момента запуска `watch` — строкой вида
`ts  task  actor  action` с добавлением `  | detail`, если `detail` не
пусто (та же схема полей, что несёт `log`, плюс идентификатор задачи,
так как поток объединяет несколько задач).

AC-3. Классы `--events` (по умолчанию `transitions,refusals,gates,steps`;
явный `--events` заменяет набор классов целиком, не дополняет дефолт):
- `transitions` — записи, чей `action` начинается с `state -> `;
- `refusals` — записи, чей `action` начинается с `переход отклонён`
  (`store.REFUSAL_ACTION_PREFIX`);
- `gates` — записи вида `state -> spec_gate`, `state -> acceptance`,
  `state -> merge_gate`, `state -> escalated` (те же 4 состояния, что
  несёт флаг «ЖДЁТ ОПЕРАТОРА» в `catalog.cmd_status`) — подмножество
  `transitions`;
- `steps` — записи, чей `action` начинается с `agent run` (started,
  finished, retry, SKIPPED, TIMEOUT, FAILED);
- `budget` — записи, чей `action` начинается с `бюджет`;
- `alerts` — записи таблицы `alerts`, появившиеся с момента запуска
  `watch`, чей `target` совпадает с id одной из выбранных задач (`kind`
  не фильтруется; запись, чей `target` не равен id ни одной выбранной
  задачи — не по формату id задачи, а по имени target-проекта или
  `NULL` — в поток не попадает).
Одна и та же запись журнала печатается один раз, даже если подпадает
под несколько выбранных классов одновременно (например, `state ->
spec_gate` — и `transitions`, и `gates`).

AC-4. `--mine` выбирает задачи, у которых `session_id` последней по
времени (по возрастанию `id` записей `steps`) записи с `actor="lease"`
(`lease взят`/`lease перехвачен`) совпадает с `session_id` вызывающей
сессии (`session.resolve_session_id`); если для задачи такой записи
нет ни одной — сравнивается `session_id` записи `created`.

AC-5. `--all` выбирает все задачи, чьё `state` не входит в `{done,
killed}`; для `--mine`/`--all` выборка задач пересчитывается заново
каждые `--interval` секунд (не фиксируется на момент запуска команды) —
задача, заведённая после старта `watch`, появляется в потоке без
перезапуска команды.

AC-6. `--until <state>`: на момент начала опроса выборка обязана
состоять ровно из одной задачи (иначе — ошибка использования до начала
опроса, код возврата ≠ 0); `watch` завершается кодом 0, как только
`state` этой задачи становится равен `<state>`. Без `--until`: `watch`
работает, пока среди выбранных задач есть хотя бы одна не в `{done,
killed}`, и завершается кодом 0, когда все выбранные задачи оказались в
`{done, killed}`.

AC-7. При каждой замеченной смене `tasks.state` отслеживаемой задачи (в
любой момент, независимо от выбранных `--events`) `watch` дополнительно
печатает отдельной строкой `STATE=<state>`.

AC-8. `watch` не создаёт записей в `steps`, не создаёт и не изменяет
записи в `alerts`, не берёт и не продлевает lease, не меняет
`tasks.state` — только читает через собственное соединение `store.db()`;
каждая итерация опроса открывает/использует новое чтение (не переиспользует
результат предыдущей итерации), чтобы не воспроизводить дефект
устаревшего снимка WAL.

AC-9. `docs/operator-session.md`, раздел «Возобновление сессии», пункт
4 «Поставить дозор» переписан: дозор — фоновый процесс `artel.py watch
--mine`; сценарии сессии (`watch_tasks.py`/`watch_spec_gate.py`) как
актуальный способ не упоминаются.

## Не входит

- Уведомления вне терминала (push, мессенджеры, звук).
- Команда `report` и любые изменения в ней.
- Историческая выдача (записи `steps`/`alerts`, существовавшие до
  момента запуска `watch`) — поток только новых записей.
- Изменение самих сценариев `watch_tasks.py`/`watch_spec_gate.py` (они
  живут вне репозитория пульта) — только замена рекомендации в
  `docs/operator-session.md`.
