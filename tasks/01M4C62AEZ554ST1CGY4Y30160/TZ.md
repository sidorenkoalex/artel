# ТЗ: Независимый дозор: позиция в журнале, системное уведомление, запуск без привязки к чату

# ТЗ: Независимый дозор — позиция в журнале, системное уведомление, запуск без привязки к чату

Приоритет: первый (решение Оператора 07.10.2026).

Источник: решение Оператора 07.10.2026. Подписка Claude заканчивается,
поэтому сессия при Операторе временно переходит в Codex. Управление
задачами и дозор выносятся из чата ассистента: дозор — отдельный процесс
системы, Codex и Claude Code — сменные интерфейсы для команд и анализа.
Заменяет задачу 01M4BPFHC8X851YAKD0PG3J8RW (ликвидирована 07.10 на гейте
SPEC): её Stop-хук Codex не мог доставить событие, пришедшее между ходами
чата. Копилка 30.09 (`docs/backlog.md`): «Дозор задач в чате Codex не
доставил уведомления об эскалациях автоматически», «Нет штатной связки
watch с продолжением завершённого хода Codex», «Анализ зависимости от
хуков: … guard-artel-bg.py».

Решение Оператора о смене контракта запуска (07.10.2026): отсоединённый
`run`/`auto` связывается с наблюдением системы, а не с чатом
ассистента. Клиент и ID чата становятся необязательными метаданными
для аудита. Гейт свежести наблюдения перед запуском сохраняется.

Факты (пин d76f804a, сверка 07.10):
- Наблюдение — таблицы `observations`, `observation_tasks`,
  `observed_runs` (`orchestrator/schema.py` ~44–59); в `observations`
  поля `client TEXT NOT NULL`, `chat TEXT NOT NULL`. Функции —
  `orchestrator/store.py` ~37–130 (`register_observation`,
  `touch_observation`, `matching_observation` сверяет задачу, проект,
  сессию пульта, клиента и чат).
- Отсоединённый запуск: `orchestrator/artel.py::_cycle_args` (~724)
  отказывает без `--client codex|claude --chat <ID>`;
  `_launch_detached` (~756) ищет наблюдение по клиенту и чату и
  отказывает, если связь старше `config.OBSERVATION_STALE_SECONDS` (90 с).
  `observe register` (`_cmd_observe` ~863) требует `--client` и `--chat`.
  Подсказки запуска — `orchestrator/cycle_hint.py`.
- `orchestrator/watch.py::cmd_watch` (~508) печатает события «начиная с
  момента запуска»: позиция чтения (`known_step_id` по задаче,
  `known_alert_id`) живёт только в памяти процесса, и каждый новый
  `watch` начинает с текущего конца журнала. События, пришедшие, пока
  наблюдателя не было, теряются. Связь отмечается `touch_observation`
  первым действием каждого опроса. Пустой набор задач завершает
  наблюдателя (`_should_stop`).
- Журнал `steps` и таблица `alerts` имеют возрастающий `id` —
  годится как позиция чтения.
- Поведение «без `--client`/`--chat` — отказ» закреплено долгоживущими
  тестами: `tests/test_detached_cycle.py`,
  `tests/test_01m3sx69e8p64d77j1xthmhe40_observation.py`,
  `tests/test_cycle_hint.py`,
  `tests/test_01m3xtfjcc5tg63fhw907gqm4d_launch_hint.py`,
  `tests/test_01m42nbcadgsgtcbzb8nkbvdvh_observe_extra_args.py`;
  сопоставление по клиенту и чату — `test_ac8_launch_requires_matching_client_and_chat`
  там же и `tests/test_observation_edges.py` (два чата на одну задачу:
  неявный выбор — отказ, явный — только названное наблюдение).
  Завершение наблюдателя на пустом наборе описано в
  `docs/operator-session.md`, «Когда наблюдатель завершается сам»;
  разбор выборки `watch` — `tests/test_watch.py`.
- В окружении роли `watch --observation` и все подкоманды `observe`,
  кроме `show`, запрещены (`artel.py::_ROLE_ALLOWED_COMMANDS` ~1587).
- PID процесса наблюдателя в БД не хранится: `observe show` говорит
  только о свежести связи.
  Смена этого поведения — объявленная (инвариант 38: раздел SPEC
  «Меняемое поведение», пары «было → стало» на гейте SPEC).
- В главной копии стоит игнорируемый git `.codex/hooks.json` с
  PreToolUse-хуком `guard-artel-bg`: требует поле `run_in_background`
  протокола Claude Code, которого у Codex нет. `hook-migrate
  inspect|apply|restore --client codex|claude` (`artel.py` ~950–1060)
  умеет снимать такие подключения.
- `docs/operator-session.md` ~419–611 описывает порядок фоновых
  запусков только для Claude Code (наблюдатель — инструмент Monitor,
  чат — `CLAUDE_CODE_SESSION_ID`); ~437 — пункт о том, что сессии на
  Codex не ведутся (тогда пульт под Codex ещё дорабатывался).
- ADR-0004 (панель) — направление совпадает, но панель в задачу не
  входит.

Требуется:
1. У наблюдения в БД две позиции в журнале: «оповещено» (докуда
   дозор напечатал события и отправил уведомления) и «разобрано»
   (докуда ассистент или Оператор подтвердил обработку). `watch
   --observation <ID>` начинает с позиции «оповещено», а не с конца:
   после перезапуска наблюдателя события, пришедшие без него,
   печатаются. Позиция «оповещено» продвигается только после выдачи
   события. Без `--observation` поведение `watch` прежнее.
2. Подтверждение обработки: команда пульта отмечает события наблюдения
   до заданной позиции как обработанные (например, ассистент или
   Оператор после разбора гейта); команда просмотра выдаёт
   необработанные события наблюдения и завершается — для ассистента
   любого клиента, пришедшего в сессию; работает независимо от того,
   жив ли процесс дозора. Позиция «разобрано» двигается только вперёд:
   подтверждение уже разобранного ничего не меняет и сообщает, когда и
   кем (метаданные клиента, если переданы) оно подтверждено; два
   одновременных подтверждения не откатывают позицию. Форму команд
   выбирает SPEC.
3. Системное уведомление macOS на события, требующие Оператора: переход
   в `spec_gate`, `acceptance`, `merge_gate`, `escalated`, отказ
   перехода, остановка цикла. Включается флагом наблюдателя или
   настройкой наблюдения; не требует сторонних пакетов. Текст события
   (название задачи, подробности журнала — недоверенные данные)
   передаётся в вызов уведомления аргументом, а не подстановкой в текст
   сценария `osascript`, — без возможности исполнить его как код. Вне
   macOS уведомление отключено с одной строкой в выводе. Сбой
   уведомления не останавливает наблюдателя и пишется в его вывод.
4. Наблюдатель — независимый процесс: работает в терминале Оператора
   или под службой вне чата ассистента, отмечает связь, переживает
   окончание ответа ассистента. Пустой набор задач его не завершает,
   пока наблюдение активно (или SPEC обосновывает иное поведение и
   описывает, как Оператор держит наблюдателя между задачами);
   `observe stop` по-прежнему его завершает. Наблюдатель записывает в
   наблюдение свой PID и хост; `observe show` и `doctor` сообщают, жив
   ли процесс дозора на этой машине.
5. Контракт запуска: `run`/`auto` без `--attach` и `observe register`
   работают без `--client` и `--chat`. Запуск связан с наблюдением
   (ID наблюдения флагом необязателен): запуск разрешён, если хотя бы
   одно активное наблюдение сессии пульта с этой задачей свежо, и
   записывается в свежее наблюдение (при нескольких свежих — по
   правилу SPEC; явный ID — только в названное). Смотреть статус и
   события можно из любого числа чатов одновременно — запуск к чату
   не привязан; `--client` и `--chat`, если
   переданы, сохраняются как метаданные и в сопоставлении не участвуют.
   Гейт свежести (90 с) сохраняется. Миграция схемы для существующих
   наблюдений; прежний вызов с `--client`/`--chat` продолжает работать.
6. Снятие мешающего хука: `doctor` сообщает о подключённом
   `guard-artel-bg`, требующем `run_in_background`, и называет команду
   `hook-migrate`, которая его снимает. Сам файл `.codex/` роль не
   правит.
7. `docs/operator-session.md`: единый порядок фоновых запусков для
   любого клиента (Codex, Claude Code, терминал) — наблюдатель в
   терминале Оператора, запуск, приход ассистента к накопленным
   событиям, подтверждение; таблица отказов; пункт ~437 заменён.
   `docs/stack.md` — абзац о независимом дозоре.
8. Дозор ничего не утверждает, не запускает и не меняет состояние
   задач; пишет только связь, PID, позиции и подтверждение наблюдения.
   В окружении роли команда подтверждения запрещена, команда
   просмотра — по решению SPEC (только чтение).

Меняемое поведение (объявляется в SPEC парами «было → стало»): отказ
`run`/`auto`/`observe register` без `--client`/`--chat` и сопоставление
наблюдения по клиенту и чату; отказ запуска при двух наблюдениях с
одной задачей без явного выбора (`tests/test_observation_edges.py`,
`test_two_chats_cannot_be_chosen_implicitly_for_one_task`) — становится
запуском по любому свежему наблюдению; завершение `watch --observation` на
пустом наборе задач (если SPEC его меняет). Остальные утверждения
названных тестов не ослабляются.

Критерии приёмки (направление; планку пишет test_author):
- Наблюдатель остановлен, задача записала события, наблюдатель
  запущен снова — события напечатаны, повторный запуск их не дублирует.
- Подтверждённые события командой просмотра не выдаются,
  неподтверждённые — выдаются, в том числе при остановленном дозоре;
  повторное и запоздалое подтверждение не сдвигает позицию назад.
- Название задачи с кавычками и управляющими символами доходит до
  вызова уведомления дословно, отдельным аргументом.
- `observe show` различает «дозор жив» и «PID записан, процесса нет».
- Уведомление вызывается на событиях из перечня требования 3 и не
  вызывается на прочих; сбой вызова уведомления не роняет наблюдателя
  (проверка с подменой вызова, без настоящего уведомления).
- `auto` без `--client`/`--chat` при свежем наблюдении запускается,
  при устаревшем — отказ; вызов с `--client`/`--chat` работает как
  прежде; существующие наблюдения после миграции читаются.
- Наблюдатель и команды просмотра и подтверждения не меняют
  `tasks.state` и не берут lease.
- AC-manual: наблюдатель запущен в терминале Оператора, задача
  запущена из чата Codex, чат закрыт; задача дошла до гейта — пришло
  системное уведомление; новый чат (любого клиента) командой просмотра
  получил событие гейта. Исполняет Оператор до approve приёмки.
