# SPEC: Прогоны в контейнере по запросу роли — plank-run и suite-run для проекта с раннером compose

## Контекст
Прогон с раннером `compose` в процессе роли отказывает до любого вызова
`docker` (`COMPOSE_ROLE_REFUSAL`, `orchestrator/acceptance.py:817`;
проверка `runner.in_role_environment()` в `_compose_report_run`).
`suite-run` запускает отвязанный процесс, снимая только `ARTEL_ROLE`, дом
роли остаётся — и Compose отказывает и там. Опыт 06.11: на первой задаче
проекта с раннером `compose` все три роли получили код 4 «раннер compose в
шаге роли не исполняется», тесты сданы неисполненными. ADR-0023, пятая
поправка 07.11.2026 (`docs/adr/0023-role-step-sandbox.md:1404`), допускает
прогоны по запросу роли до песочницы ОС: роль записывает запрос, исполняет
его процесс пульта, ведущий шаг роли (`runner.run_agent_once`), тем же
узлом, что гейты.

## Требования

1. **Запрос.** `plank-run <id> [<файл>]` и `suite-run <id> [--failed]`,
   вызванные в процессе роли (признак `runner.in_role_environment()`) для
   задачи проекта с раннером `compose`, не вызывают `docker`: команда
   записывает запрос в хозяйство пульта задачи и печатает «запрос принят,
   итог — `<команда> --wait <минуты>`». Запрос несёт ровно: вид (планка с
   указанным файлом или без; полный набор; повтор упавших), id задачи,
   время.
2. Итог запроса читается командой `<команда> --wait <минуты>` той же
   команды, что записала запрос (`plank-run <id> --wait <минуты>` и
   `suite-run <id> --wait <минуты>`), в прежнем формате отчёта этой команды.
3. Правила `suite-run` для разработчика (новый полный прогон — отказ) —
   прежние и в режиме запроса.
4. У проектов без раннера `compose` и вне шага роли поведение `plank-run` и
   `suite-run` — прежнее побайтно.
5. **Исполнитель.** Процесс пульта, ведущий шаг роли этой задачи
   (`runner.run_agent_once`), пока шаг идёт, берёт запросы задачи по одному
   и исполняет их прежними узлами (`acceptance.run_plank` для планки; путь
   полного набора `suite-run` для полного набора и повтора упавших) в своём
   окружении, вне окружения роли, на рабочей копии задачи с незакоммиченными
   правками. Итог пишется туда, откуда его читает `--wait`, в прежнем формате
   отчёта команды.
6. Полный набор (и повтор упавших) исполнитель ведёт под общим замком полных
   прогонов (`suite_lock`); занятый замок — итог «прогон не начат: замок занят
   <держатель>».
7. **Что исполнитель не принимает:** запрос другой задачи; запрос без шага
   роли этой задачи в полёте; файл планки вне долгоживущих файлов задачи и её
   `acceptance_tests`; любые поля запроса сверх вида, файла и id. Отказ —
   итогом запроса с причиной; `docker` при этом не вызывается.
8. **Пределы.** Одновременно исполняется не больше одного запроса задачи,
   следующие ждут в очереди; в очереди не больше 3 запросов — запрос сверх
   этого отказывается при записи (в процессе роли, сообщением команды).
   Предел времени прогона — прежний для вида прогона.
9. Шаг роли, завершившийся раньше итога прогона: прогон снимается тем же
   путём, что прерванный прогон гейта (включая снятие стенда Compose), итог
   «прерван: шаг роли завершён».
10. **Журнал.** По каждому исполненному или отказанному исполнителем запросу
    — запись журнала задачи «прогон по запросу роли: <вид>, итог <…>»; если
    пишет процесс без права записи в БД — через отложенную запись
    `suite_lock.defer_journal`.
11. Прямой прогон `compose` в процессе роли (не через запрос) по-прежнему
    отказывает `COMPOSE_ROLE_REFUSAL`; текст и место отказа не меняются.

## Критерии приёмки

AC-1. Given вымышленный проект с раннером `compose` (подменённый `docker` в
PATH) и процесс с признаком роли, When `plank-run <id>`, Then подменённый
`docker` не вызван в процессе роли, запрос записан в хозяйство пульта задачи,
вывод команды называет `--wait`.

AC-2. Given запрос, записанный по AC-1, When исполнитель (процесс пульта без
признака роли) берёт его, Then подменённый `docker` вызван исполнителем, и
итог читается `plank-run <id> --wait <минуты>` в прежнем формате отчёта
`plank-run`.

AC-3. Given процесс с признаком роли и проект с раннером `compose`, When
`suite-run <id> --failed` (или `suite-run <id>` ролью, которой полный прогон
разрешён), Then `docker` в процессе роли не вызван, запрос записан, вывод
называет `--wait`; итог исполнителя читается `suite-run <id> --wait <минуты>`
в прежнем формате отчёта `suite-run`.

AC-4. Given запрос с чужим id задачи, Then исполнитель отказывает итогом с
причиной, `docker` не вызван.

AC-5. Given запрос планки с файлом вне долгоживущих файлов задачи и её
`acceptance_tests`, Then исполнитель отказывает итогом с причиной, `docker`
не вызван.

AC-6. Given запрос с полем сверх вида, файла и id, Then исполнитель
отказывает итогом с причиной, `docker` не вызван.

AC-7. Given запрос задачи без шага роли этой задачи в полёте, Then запрос не
исполняется — отказ итогом с причиной, `docker` не вызван.

AC-8. Given занятый замок полных прогонов, When исполнитель берёт запрос
полного набора, Then итог «прогон не начат: замок занят <держатель>»,
`docker` не вызван.

AC-9. Given шаг роли завершён до итога прогона, Then прогон снят, итог
«прерван: шаг роли завершён», стенд Compose снят (подменённый `docker` получил
команду снятия стенда).

AC-10. Given три запроса задачи в очереди (один исполняется или все ждут), When
четвёртый запрос подряд, Then отказ при записи, запрос не записан.

AC-11. Given исполнитель с двумя запросами задачи, Then второй начинает
исполняться только после итога первого (одновременно не больше одного).

AC-12. Given исполнитель исполнил запрос или отказал ему, Then в журнале
задачи запись «прогон по запросу роли: <вид>, итог <…>».

AC-13. Given роль разработчика и `suite-run <id>` без флагов в проекте с
раннером `compose`, Then прежний отказ разработчику, запрос не записан.

AC-14. Given проект без раннера `compose` (в процессе роли) или вызов вне
шага роли (в проекте с `compose`), When `plank-run <id>` / `suite-run <id>`,
Then вывод и действие команд — прежние побайтно, запрос не записан.

AC-15. Given прямой прогон `compose` в процессе роли (узел
`_compose_report_run` не через исполнителя), Then прежний отказ
`COMPOSE_ROLE_REFUSAL`, `docker` не вызван.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (`plank_run.py`, `suite_run.py`,
`runner.py`, `acceptance.py`, `suite_lock.py`, плюс карта и `tests/`); число
критериев приёмки ≥ 10 (15); `budget_usd` ≥ $30.

**Обоснование монолита (материал для решения Оператора).** Запрос
(`plank_run.py`/`suite_run.py`) и исполнитель (`runner.py`) — одна атомарная
смена механики: запрос без исполнителя переводит роль из честного отказа
«раннер compose в шаге роли не исполняется» в ответ «запрос принят», за
которым итог не придёт никогда (`--wait` истекает) — хуже прежнего состояния.
Исполнитель без запроса не имеет входа и мёртв. Узкие правки `acceptance.py`
(вызов узлов из исполнителя) и `suite_lock.py` (отложенная запись журнала)
обслуживают исполнитель и отдельно смысла не имеют. Разрезать по зонам без
промежуточного нерабочего состояния нельзя.

## Не входит

- Доступ роли к Docker в любом виде.
- Произвольные команды или образы в контейнере по запросу роли.
- Песочница ОС шага роли (B3).
- Линтер проекта в шаге роли (отдельная строка копилки).
- Правка настоящего локального слоя `.artel/targets.yaml` в тестах и при
  разработке; чтение `.artel/targets.yaml` в тестах.
- Изменение отказа `COMPOSE_ROLE_REFUSAL` (текст, место, условие) — в
  `acceptance.py` только вызов узлов из исполнителя.
- Правка `orchestrator/artel.py`, `orchestrator/config.py`,
  `orchestrator/stack.py`, `tests/sandbox.py`,
  `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`,
  `docs/adr/0023-role-step-sandbox.md` — только чтение.
- `docs/codebase-map.md` — только регенерацией `scripts/codebase_map.py`.
- «Существующие тесты — зелёные без правки» — её держит пульт (полный
  зелёный набор `tests/`); покраснение существующего теста — эскалация с
  именем теста, без его правки.
