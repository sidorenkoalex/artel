# SPEC: Прогоны в контейнере по запросу роли — plank-run и suite-run для проекта с раннером compose

## Контекст
Прогон с раннером `compose` в процессе роли отказывает до любого вызова
`docker` (`COMPOSE_ROLE_REFUSAL`, `orchestrator/acceptance.py:817`;
проверка `runner.in_role_environment()` в `_compose_report_run`).
`suite-run` запускает отвязанный процесс, снимая только `ARTEL_ROLE`, дом
роли остаётся — и Compose отказывает и там. Опыт 06.11: на первой задаче
проекта с раннером `compose` все три роли получили код 4 «раннер compose в
шаге роли не исполняется», тесты сданы неисполненными. ADR-0023, пятая
поправка 07.11.2026 (`docs/adr/0023-role-step-sandbox.md:1404`), допускает
прогоны по запросу роли до песочницы ОС: роль записывает запрос, исполняет
его процесс пульта, ведущий шаг роли (`runner.run_agent_once`), тем же
узлом, что гейты. Решения по неясным местам ТЗ — ANSWER-1 (07.11.2026).

## Требования

1. **Запрос.** `plank-run <id> [<файл>]` и `suite-run <id> [--failed]`,
   вызванные в процессе роли (признак `runner.in_role_environment()`:
   маркер `ARTEL_ROLE` или `HOME`, равный дому роли) для задачи, профиль
   прогона которой — с раннером `compose`, не вызывают `docker`: команда
   записывает запрос в каталог `suite-run` задачи под
   `suite_lock.directory()` и печатает «запрос принят, итог — `<команда>
   --wait <минуты>`». Режим запроса включается по профилю прогона задачи
   (раннер компонента задачи, `project_profile.py:509`), а не по проекту в
   целом: задача компонента с раннером `pytest-own` в проекте, где у другого
   компонента раннер `compose`, сохраняет прежний `plank-run` (и прежний
   `suite-run`).
2. **Поля запроса** — ровно четыре: вид (планка с указанным файлом или
   без; полный набор; повтор упавших), файл (для планки), id задачи, время.
   Время записывает команда только для сведения: исполнитель решений по
   нему не принимает.
   **Форма.** Очередь запросов задачи — каталог
   `suite_lock.directory()/<id задачи>/requests/`, один запрос — один файл
   `<номер запроса>.json`. Запрос — объект JSON ровно с ключами `kind`,
   `file`, `task_id`, `time`; значения `kind`: `plank` (планка), `full`
   (полный набор), `failed` (повтор упавших); `file` — путь файла планки
   строкой либо `null` (планка целиком, `full`, `failed`); `time` — время
   записи строкой. Итог запроса — файл `<номер запроса>.result.json` в том
   же каталоге (вид, итог, строка «принят шагом …» либо причина отказа);
   `--wait` читает его.
3. При записи запроса команда заводит новый номер прогона и состояние
   «запрос принят, ждёт исполнителя». В процессе роли без живого lease
   шага этой задачи команда запрос не пишет и отказывает (защита от ошибки,
   не рубеж).
4. **Чтение итога.** Итог запроса читается той же командой:
   `plank-run <id> --wait <минуты>` и `suite-run <id> --wait <минуты>`, в
   прежнем формате отчёта этой команды. Предел минут у обеих —
   `config.SUITE_RUN_MAX_WAIT_MIN`. `--wait` ждёт итог именно номера
   последнего запроса своего вида (требование 17): итог прошлого прогона за
   новый не выдаётся. Запрос,
   не взятый исполнителем к истечению ожидания, — вывод «запрос в очереди
   (позиция N), прогон не начат» и подсказка повторного `--wait`; прогон
   начат, но не закончен — «прогон не прерван, повтори `--wait`».
5. **Диспетчер `plank-run`** (`orchestrator/artel.py`) передаёт
   `cmd_plank_run` все аргументы команды. Во всех проектах (с раннером
   `compose` и без, в шаге роли и вне его) меняются только две вещи:
   неизвестный третий аргумент — отказ, называющий этот аргумент (сейчас
   он молча отбрасывается, `artel.py:2797-2798`); `--wait <минуты>`
   разбирается как чтение итога (требование 4), а не как имя файла планки
   (сейчас — отказ «файла --wait нет в планке», `plank_run.py:233-237`).
   Формы `plank-run <id>` и `plank-run <id> <файл>` вне режима запроса —
   прежние побайтно (разбор, вывод, действие). Строка справки (`artel.py:207`) называет
   `plank-run <id> [<файл> | --wait <минуты>]`. Основание белого списка
   команд роли для `plank-run` и `suite-run` (`artel.py:2562-2589`)
   дополняется, не заменяется: «пишет запрос в каталог `suite-run`,
   состояния задачи и lease не меняет»; для проектов без `compose`
   `plank-run` по-прежнему пишет временную выкладку `tasks/<id>/`.
   `_ROLE_ALLOWED_COMMANDS`, `_ROLE_REFUSED_FLAGS`,
   `_ROLE_ALLOWED_SUBCOMMANDS`, `_role_allowed_command` и строки
   диспетчера других команд не меняются.
6. Правила `suite-run` для разработчика (новый полный прогон — отказ) —
   прежние и в режиме запроса.
7. У задач, профиль прогона которых не с раннером `compose` (в том числе у
   задачи компонента `pytest-own` в проекте, где у другого компонента раннер
   `compose`, — требование 1), и вне шага роли поведение `plank-run` и
   `suite-run` — прежнее побайтно, кроме двух изменений разбора
   `plank-run` из требования 5 (отказ на неизвестный третий аргумент,
   разбор `--wait`).
8. **Исполнитель.** Процесс пульта, ведущий шаг роли этой задачи
   (`runner.run_agent_once`), пока шаг идёт, берёт запросы задачи по одному
   и исполняет их прежними узлами в своём окружении, вне окружения роли, на
   рабочей копии задачи с незакоммиченными правками: планку — путём
   `cmd_plank_run` целиком (источник планки, проверки до выкладки, выкладка,
   прогон `acceptance.run_plank`, строки итога), полный набор и повтор
   упавших — путём полного набора `suite-run`. Итог пишется туда, откуда его
   читает `--wait`, в прежнем формате отчёта команды.
   **Дочерний прогон.** Каждый запрос исполнитель ведёт в собственном
   дочернем процессе (дочерний прогон): либо новый интерпретатор пульта,
   чей `config.ROOT` — корень того же пульта, что у исполнителя (в тесте —
   копия пульта в песочнице теста, её `config.ROOT` равен корню
   песочницы), либо `multiprocessing` в режиме `spawn` с явной передачей
   путей пульта (в тесте — путей песочницы). `fork` не используется: в
   процессе исполнителя уже идёт поток перекачки вывода агента
   (`runner.py:1993`). Тело полного набора и повтора упавших
   (`suite_run.background`) исполняется в этом же дочернем прогоне —
   без отвязанного фона в чужой сессии (`suite_run.py:926-937`
   `start_new_session=True` в этом пути не используется).
9. Полный набор (и повтор упавших) исполнитель ведёт под общим замком полных
   прогонов (`suite_lock`); занятый замок — итог «прогон не начат: замок занят
   <держатель>», без ожидания замка.
10. **Привязка к шагу.** В начале своего шага исполнитель отказывает всем
    запросам, уже лежащим в очереди задачи (по собственному перечню файлов
    очереди, не по полю времени), итогом «запрос без шага роли этой задачи в
    полёте». Принимая запрос, исполнитель сам записывает в итог «принят шагом
    <session_id lease>/<номер попытки>, <время исполнителя>». В конце шага
    исполнитель отказывает всем оставшимся в очереди запросам итогом «не
    исполнен: шаг роли завершён».
11. **Что исполнитель не принимает:** запрос другой задачи; вид вне трёх
    допустимых (требование 2); файл планки вне долгоживущих файлов задачи и
    её `acceptance_tests`; любые поля запроса сверх четырёх (требование 2);
    вид, запрещённый роли своего шага (разработчику — полный набор,
    требование 6), — в том числе когда файл запроса подложен в каталог
    `suite-run` в обход команды (каталог открыт роли на запись,
    `suite_lock.py:40-44`; сейчас запрет держит только команда,
    `suite_run.py:862-865`); любой запрос, если профиль прогона задачи
    (компонента задачи — раннер задаётся у компонента,
    `project_profile.py:509`) не с раннером `compose`: проверка идёт у
    разрешённого профиля прогона задачи, а не у проекта в целом, — иначе код
    роли проекта без контейнера исполнялся бы на хосте в окружении пульта.
    Отказ — итогом запроса с причиной; текст отказа называет её (чужой id,
    файл, лишний ключ, вид, роль, раннер); `docker` и pytest при этом не
    вызываются.
12. **Пределы.** Одновременно исполняется не больше одного запроса задачи,
    следующие ждут в очереди; в очереди не больше 3 запросов — запрос сверх
    этого отказывается при записи (в процессе роли, сообщением команды).
    Предел времени прогона — прежний для вида прогона.
13. **Конец шага до итога.** Шаг роли, завершившийся раньше итога прогона
    любого вида (планка, полный набор, повтор упавших): прогон снят, стенд
    Compose снят — подменённый `docker` получил `down` проекта Compose,
    поднятого дочерним прогоном исполнителя; замок полных прогонов
    (`suite_lock`), если прогон его держал, освобождён; итог «прерван: шаг
    роли завершён». Снятие в дочернем прогоне идёт прежним
    `_compose_teardown` (`acceptance.py:1306-1327`) из `finally`
    `_compose_report_run`. Исполнитель ждёт выхода дочернего прогона дольше,
    чем длится снятие стенда в самом дочернем прогоне: предел ожидания
    исполнителя — `config.COMPOSE_TEARDOWN_TIMEOUT_SEC` плюс запас; дочерний
    прогон не вышел к пределу — снятие группы процессов дочернего прогона.
    Затем в обоих случаях (дочерний прогон вышел сам или снят) исполнитель
    ищет оставшийся проект Compose вызовом `docker ps -a --filter
    label=com.docker.compose.project --format {{json .}}` (образец —
    `orchestrator/doctor/orphans.py:339-343`) и, если найден, делает явный
    `docker compose --project-name <имя> down --remove-orphans` (без `-v`).
    Отбор проекта — префикс `artel-<id задачи строчными>-` и метка
    `artel.run-pid`, равная pid своего дочернего прогона. Прогон снят и итог
    записан до учёта шага (`_account_step`, `runner.py:1762`). Этот pid
    исполнитель берёт из объекта запущенного им процесса (требование 8), не
    из `run.json`. Имя проекта и pid из запроса и из любых файлов каталога
    `suite-run` (их пишет роль) не берутся. Дочерний прогон запускается в
    своей группе процессов в той же сессии (`process_group=0`); снимается
    только эта группа — не группа процесса пульта. Сигнал конца шага
    исполнитель посылает своему дочернему прогону, и тот до него доходит
    (дочерний прогон — не в отвязанной чужой сессии). После снятия
    записаны итог «прерван: шаг роли завершён» и запись журнала
    (требование 14), процесс пульта доводит шаг роли до конца сам.
14. **Журнал.** По каждому исполненному или отказанному исполнителем запросу
    — запись журнала задачи «прогон по запросу роли: <вид>, итог <…>». Пишет
    её только исполнитель, напрямую через `store.journal`; перечень
    `suite_lock.deferrable` не расширяется.
15. **Итог запроса — сведения роли**, не свидетельство для гейтов и ревью:
    гейты пульта (планка, полный набор, исходы) свой итог получают
    собственным прогоном, файл итога запроса на него не влияет.
16. Прямой прогон `compose` в процессе роли (не через исполнителя) по-прежнему
    отказывает `COMPOSE_ROLE_REFUSAL`; текст, место и условие отказа не
    меняются.
17. **Своё состояние запросов планки.** Итог запроса планки не пишется в
    `failed.json` и не отдаётся `suite-run --wait`; итог полного набора и
    повтора упавших не отдаётся `plank-run --wait`. Каждое `--wait` ждёт
    последний запрос своего вида.

## Критерии приёмки

AC-1. Given вымышленный проект с раннером `compose` (подменённый `docker` в
PATH), процесс с признаком роли и живой lease шага задачи, When
`plank-run <id>`, Then подменённый `docker` не вызван в процессе роли, запрос
записан в каталог `suite-run` задачи под `suite_lock.directory()` — объект
JSON ровно с ключами `kind`, `file`, `task_id`, `time` (требование 2,
«Форма»), вывод команды называет `--wait`.

AC-2. Given запрос, записанный по AC-1, When исполнитель (процесс пульта без
признака роли) берёт его, Then подменённый `docker` вызван исполнителем, и
итог читается `plank-run <id> --wait <минуты>` в прежнем формате отчёта
`plank-run`, с строкой «принят шагом <session_id lease>/<номер попытки>, …».

AC-3. Given процесс с признаком роли, живой lease шага и проект с раннером
`compose`, When `suite-run <id> --failed` (или `suite-run <id>` ролью, которой
полный прогон разрешён), Then `docker` в процессе роли не вызван, запрос
записан, вывод называет `--wait`; итог исполнителя читается
`suite-run <id> --wait <минуты>` в прежнем формате отчёта `suite-run`.
Форма теста (и в красной фазе, где до кода `suite-run` в процессе роли
запускает отвязанный фон, `suite_run.py:926-930`): `cmd_suite_run` идёт
только в копии пульта во временной песочнице — процессом с
`start_new_session` и снятием группы процессов (образец
`tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py:313-339`); pid
отвязанного фона, ушедшего в свою сессию, тест добирает по файлу вызовов
заглушек (pid и ppid каждого вызова), не по `run.json`, и снимает сам
(образец добора и снятия —
`tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py:409-423`,
`stop_everything` по `calls_file`) — либо с
подменой `suite_run.subprocess.Popen` (образец `tests/test_suite_run.py:250`).
Вызов `cmd_suite_run` при настоящем `config.ROOT` запрещён: отвязанный фон —
новый интерпретатор с настоящими `config.ROOT`, `DB`, `LOGS`
(`config.py:11-14`, `suite_run.py:78-79`) и взял бы настоящий замок полных
прогонов машины (`suite_lock.py:172-181`).

AC-4. Given принятый, но не взятый исполнителем запрос и итог прошлого
прогона задачи в каталоге `suite-run`, When `suite-run <id> --wait 0` (и
`plank-run <id> --wait 0`), Then вывод «запрос в очереди (позиция N), прогон
не начат» с подсказкой повторного `--wait`; итог прошлого прогона не выдан.
Given запрос, взятый исполнителем, и прогон по нему идёт, When
`suite-run <id> --wait 0` (и `plank-run <id> --wait 0`), Then вывод «прогон
не прерван, повтори `--wait`» (требование 4); итог прошлого прогона не
выдан.

AC-5. Given `plank-run <id> --wait <минуты>` с числом минут больше
`config.SUITE_RUN_MAX_WAIT_MIN`, Then отказ, текст которого называет предел
(`SUITE_RUN_MAX_WAIT_MIN` и допустимый диапазон минут); Given
`plank-run <id> <файл> <лишний аргумент>`, Then отказ, текст которого
называет этот лишний аргумент. Тест сверяет текст отказа, а не только код
выхода (на базе `--wait 99` отказывает иным текстом «файла --wait нет в
планке», `plank_run.py:233-237`, лишний аргумент молча отбрасывается).

AC-6. Given процесс с признаком роли и проект с раннером `compose`, When
`plank-run <id> --wait <минуты>` и `suite-run <id> --wait <минуты>`, Then
проверка команд роли их пропускает; набор `_ROLE_ALLOWED_COMMANDS` —
прежний.

AC-7. Given процесс с признаком роли, проект с раннером `compose` и у задачи
нет живого lease шага, When `plank-run <id>`, Then отказ, запрос не записан,
`docker` не вызван. Форма теста: `plank-run` идёт подпроцессом только через
`artel.py` копии пульта во временной песочнице, где `config.ROOT` — корень
песочницы, а задача заведена в БД копии; при настоящем `config.ROOT`
`store.db()` мигрировал бы настоящую БД (`plank_run.py:165`), а отказ
зеленел бы потому, что вымышленный id в настоящей БД не найден.

AC-8. Given запрос с чужим id задачи, Then исполнитель отказывает итогом,
текст которого называет причину (чужой id), `docker` не вызван; Given тот же
файл, где исправлен только `task_id` на id задачи шага, Then запрос исполнен
(подменённый `docker` вызван).

AC-9. Given запрос планки с файлом вне долгоживущих файлов задачи и её
`acceptance_tests`, Then исполнитель отказывает итогом, текст которого
называет причину (файл), `docker` не вызван; Given тот же файл, где исправлен
только `file` на файл `acceptance_tests` задачи, Then запрос исполнен
(подменённый `docker` вызван).

AC-10. Given запрос с ключом сверх `kind`, `file`, `task_id`, `time`, Then
исполнитель отказывает итогом, текст которого называет причину (лишний
ключ), `docker` не вызван; Given тот же файл без лишнего ключа, Then запрос
исполнен (подменённый `docker` вызван). Given запрос с `kind` вне `plank`,
`full`, `failed`, Then отказ итогом, текст которого называет причину (вид),
`docker` не вызван; Given тот же файл с `kind`, исправленным на `plank`, Then
запрос исполнен (подменённый `docker` вызван).

AC-11. Given запрос, лежавший в очереди задачи до начала шага исполнителя (в

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (`plank_run.py`, `suite_run.py`,
`runner.py`, `acceptance.py`, `artel.py`, плюс карта и `tests/`); число
критериев приёмки ≥ 10 (26); `budget_usd` ≥ $30; ТЗ ссылается на ADR-0023
(пятая поправка).

**Обоснование монолита (материал для решения Оператора).** Запрос
(`plank_run.py`/`suite_run.py`, диспетчер `artel.py`) и исполнитель
(`runner.py`) — одна атомарная смена механики: запрос без исполнителя
переводит роль из честного отказа «раннер compose в шаге роли не
исполняется» в ответ «запрос принят», за которым итог не придёт никогда
(«запрос в очереди» на каждый `--wait`) — хуже прежнего состояния.
Исполнитель без запроса не имеет входа и мёртв. Правка `acceptance.py`
(вызов узлов из исполнителя) и диспетчера `artel.py` обслуживают эту же
механику и отдельно смысла не имеют. Разрезать по зонам без промежуточного
нерабочего состояния нельзя. Бюджет — рамка ТЗ $70 (больше 15 критериев,
калибровка дала бы ~85; ниже — по рамке Оператора).
