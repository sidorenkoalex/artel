# ANSWER-1: ответ Оператора

## Ответы

Основание: решение Оператора 07.11.2026 — задачу ведёт сессия Оператора с правами волны G («все заведённые задачи веди с правами волны G»); ответы — по дефолтам батча вопросов аналитика.

## Мандат

Расширение зон разрешено: orchestrator/artel.py

Пояснение: в `orchestrator/artel.py` разрешено только: диспетчер передаёт `cmd_plank_run` весь `rest`; строка справки `plank-run` называет `--wait <минуты>`; основание белого списка команд роли для `plank-run` и `suite-run` переписывается под новое поведение («пишет запрос в каталог `suite-run`, состояния задачи и lease не меняет»). Основание белого списка дополняется, а не заменяется (для проектов без `compose` команда по-прежнему пишет временную выкладку в `tasks/<id>/`); неизвестный третий аргумент `plank-run` — отказ. Не меняются: `_ROLE_ALLOWED_COMMANDS`, `_ROLE_REFUSED_FLAGS`, `_ROLE_ALLOWED_SUBCOMMANDS`, `_role_allowed_command` и строки диспетчера других команд.

## Ответы

1. A — `plank-run <id> [<файл> | --wait <минуты>]`; предел минут — `SUITE_RUN_MAX_WAIT_MIN`; не уложился в одно ожидание — «прогон не прерван, повтори `--wait`».
2. A, запасной путь — B: исполнитель ведёт прогон в дочернем процессе, в конце шага посылает сигнал, `finally` в `_compose_report_run` снимает стенд прежним `_compose_teardown`; не уложился в `COMPOSE_UP_DOWN_SEC` — снять группу процессов и явный `docker compose --project-name <имя проекта Compose задачи> down --remove-orphans`. Имя проекта Compose для явного `down` исполнитель вычисляет сам (`acceptance.compose_project_name`), из запроса его не берёт. В SPEC — одно требование: «прогон снят, подменённый `docker` получил `down` проекта Compose задачи».
3. A в уточнённой форме — привязку к шагу держит исполнитель, а не поле запроса: в начале своего шага исполнитель отказывает всем запросам, уже лежащим в очереди задачи (по собственному перечню файлов, не по полю времени), итогом «запрос без шага роли этой задачи в полёте»; при приёме запроса сам записывает в итог «принят шагом <session_id lease>/<номер попытки>, <время исполнителя>»; в конце шага отказывает всем оставшимся итогом «не исполнен: шаг роли завершён». Отказ при записи без живого lease шага в команде роли — защита от ошибки, не рубеж.
4. Поля запроса: вид, файл, id задачи и время; время записывает команда только для сведения — исполнитель решений по нему не принимает (условие матрицы пятой поправки ADR-0023: от роли принимаются только вид прогона и файлы задачи); поле сверх четырёх — отказ итогом.
5. A — при записи новый номер прогона и состояние «запрос принят, ждёт исполнителя»; `--wait` ждёт итог этого номера, по истечении — «запрос в очереди (позиция N), прогон не начат» и подсказка повторного `--wait`; итог прошлого прогона за новый не выдаётся.
6. A — журнал пишет только исполнитель через `store.journal`; перечень `suite_lock.deferrable` не расширяется; `orchestrator/suite_lock.py` из зон задачи уходит.
7. A — запрос и итог в каталоге `suite-run` задачи под `suite_lock.directory()`; итог запроса — сведения роли, не свидетельство для гейтов и ревью (оговорка Е2 аудита подтверждена).
