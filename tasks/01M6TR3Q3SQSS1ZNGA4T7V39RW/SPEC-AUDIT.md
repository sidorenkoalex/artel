  ложно по коду.** `compose_project_name(task_id, run_id)`

  снимает. Из id задачи имя не вычислить. Остаются пути, которых SPEC не
  выбирает: (а) поиск проектов по префиксу `artel-<id>-`

  `doctor` (`orphans.py`, `_stands_survey`); (б) передача `run_id` в
  `_compose_report_run` снаружи — правка `acceptance.py` сверх «только вызов
  узлов» (ТЗ «Зоны»); (в) канал от дочернего процесса к исполнителю — если
  через файл в `suite_lock.directory()`, его пишет и роль, а это ровно то
  «имя из запроса», которое ANSWER-1 запрещает (роль подложит имя чужого
  стенда, исполнитель снимет его `down`). Решение ANSWER-1 о содержании
  в силе, но факт под ним надо заменить выбором (а)/(б)/(в) с условием.
- **Б2. «Снятие идёт прежним `_compose_teardown` из `finally`» после сигнала
  исполнителя — верно только для сигнала, превращаемого в исключение.**
  Опыт (временный процесс Python, `timeout 20`): SIGTERM без обработчика —
  rc -15, `finally` не исполнен; SIGINT — rc -2, `finally` исполнен.
  `liveness.terminate_process_group` (им снимается группа шага,
  `runner.py:2005`) шлёт SIGTERM. Если исполнитель пошлёт его же, процесс
  умрёт сразу, «не уложилось в предел» не наступит, явного `down` не будет
  — стенд останется. AC-14 такую реализацию поймает (нет `down`), так что
  это не дыра критерия, а неточность требования: сигнал/обработчик надо
  назвать.
- **Б3. Предел снятия.** Треб. 13: «не уложилось в
  `config.COMPOSE_UP_DOWN_SEC`» (300 с). Узел снятия ограничен другим
  пределом — `config.COMPOSE_TEARDOWN_TIMEOUT_SEC = 120`
  (`config.py:238`, `acceptance.py:1312`). Ошибкой не является (300 > 120),
  но конец шага задерживается до 5 минут без нужды; и явный `down` SPEC
  (`down --remove-orphans`) — без `-v`, тогда как `_compose_teardown`
  снимает `down -v --remove-orphans` (`acceptance.py:1313`): после
  запасного пути тома стенда остаются. Замечание.
- **Б4. Общее состояние планки и полного набора не задано.** Треб. 3-4:
  запрос «заводит новый номер прогона и состояние», `--wait` ждёт «номера
  последнего запроса». Хозяйство `suite-run` задачи — один `run.json`,
  `result.json`, `failed.json` (`suite_run.py:127-139`), нумерация — общая
  (`_new_log`, `:148-166`). SPEC не говорит, делят ли запросы планки эти
  файлы и номер с полным набором: при общем `result.json` `suite-run --wait`
  после запроса планки выдаст отчёт планки (или наоборот), а итог планки,
  записанный в `failed.json`, подменит перечень для `suite-run --failed`.
  «Последний запрос» для `plank-run --wait` при более позднем запросе
  `suite-run` (и наоборот) не определён. Тесты AC-2/AC-3/AC-4 гоняют виды
  порознь и этого не поймают.
- **Б5. Codex и БД в команде роли.** Треб. 3 требует в процессе роли
  прочесть lease; `cmd_plank_run` начинается с `store.db()`

  роли Codex БД на запись не открыта (`suite_run.py:169-179` поэтому

## Пути обхода гейтов

- **Е1.** Через Б1(в): если исполнитель узнаёт имя проекта Compose из файла
  в `suite_lock.directory()`, роль подменяет его и получает `docker compose
  --project-name <чужой стенд> down` процессом пульта — снятие стенда
  другой задачи или гейта. Закрывается выбором (а) или (б) из Б1.
- **Е2.** Через Б4: при общем `failed.json` роль запросом планки с
  выбранным файлом подменяет перечень упавших, и `suite-run --failed`
  ревьювера/Оператора повторит не те тесты. Гейты на `failed.json` не
  опираются — замечание, не обход гейта.
- Прочие пути аудита 1 (подложенный журнал, итог запроса как свидетельство,
  флаг исполнителя в `_compose_report_run`) закрыты треб. 14-16, AC-17,
  AC-18, AC-21.
