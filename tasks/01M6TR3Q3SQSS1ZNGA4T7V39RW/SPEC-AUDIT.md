Красная фаза: `cmd_suite_run` — в копии пульта или с подменой `Popen`
(AC-3, «Материалы», решение №2.2); исполнитель — в копии пульта
(решение №2.3); на базе процесс-«агент» ждёт итог с пределом времени —
зависания нет; рекурсии и неограниченного порождения процессов нет;
настоящий `docker` не зовётся (подмена в PATH). Отвязанный фон базы в
красной фазе (`suite-run --failed` в роли) живёт в копии пульта, под домом
роли отказывает compose и сам выходит — ограничен.

Отклонения:

**В1. Формат файла запроса не задан, а критерии требуют писать и править
его в обход команды.** SPEC задаёт только состав полей (треб. 2) и
каталог (треб. 1). Имя и место файла очереди внутри каталога задачи,
сериализация, имена ключей и значения поля «вид» не названы. Без них:
AC-1 («с полями вид, файл, id задачи, время») не проверить, не выбрав
ключи; AC-8 (чужой id), AC-10 (лишнее поле, вид вне трёх), AC-11 (время
из будущего), AC-25 (подложенный полный набор) требуют от автора тестов
создать или исправить файл, который исполнитель признает своим. Тест,
написанный до кода, навяжет разработчику придуманный формат — класс
`тест-навязывает-устройство` (skills/escalation-rules.md), круг
эскалации на `in_dev`. Нужно в SPEC: путь файла очереди (например
`suite_lock.directory()/<id>/requests/<n>.json`), JSON с ключами и
значения вида (например `plank`/`full`/`failed`).

**В2. Запрос имени проекта у `docker` (AC-22) — форма вызова не задана.**
Подменённый `docker` должен ответить на поиск проекта по префиксу и метке
`artel.run-pid` (треб. 13), а каким вызовом его ищут (`docker ps -a
--filter label=…`, `docker compose ls`, `inspect`), SPEC не говорит.
Автор теста выберет вызов — разработчик обязан совпасть. В пульте уже
есть образец: `doctor` ищет стенды через `docker ps -a --filter
label=com.docker.compose.project --format {{json .}}`
(`orchestrator/doctor/orphans.py:339-343`). Нужно в SPEC: назвать этот
образец формой поиска (или иную форму явно).

**В3 (мелкое). Действие журнала не названо.** «Запись журнала «прогон по
запросу роли: <вид>, итог <…>»» (треб. 14, AC-17) не разделяет действие и
текст записи; вторая часть AC-17 (подложенный в очередь отложенных
записей файл «с действием «прогон по запросу роли»») проверяет перечень
`deferrable` только при совпадении имени действия с кодом. Часть на базе
уже зелёная, ловит лишь расширение перечня этим действием — достаточно
назвать действие строкой («прогон по запросу роли») в треб. 14.

## Пути обхода гейтов

**Е1. Исполнитель не отказывает запросу задачи, чей проект не с раннером
`compose`.** Треб. 8 запускает исполнителя на каждом шаге роли, треб. 11
перечисляет отказы (чужая задача, вид, файл, лишнее поле, вид, запрещённый
роли), но не «профиль задачи — не `compose`». Каталог `suite-run` открыт
роли на запись (`suite_lock.py:40-44`), и роль проекта с раннером пульта
(pytest на хосте) может подложить файл запроса планки. Исполнитель
исполнит `cmd_plank_run` в окружении процесса пульта: код теста роли
пойдёт на хосте без дома роли, обёртки git роли и предела процессов шага,
на незакоммиченной рабочей копии и по требованию роли. Основание пятой
поправки ADR-0023 (`docs/adr/0023-role-step-sandbox.md:1421-1426`) —
«тот же узел гейтов с проверкой собранной конфигурации и перекрытием», то
есть прогон в контейнере; для проекта без `compose` это основание не
действует. Нужно: в треб. 11 — отказ запросу задачи, профиль которой не с
раннером `compose`; критерий — подложенный запрос в такой задаче, отказ
итогом, pytest не запущен.

**Е2 (существующий обход, к сведению).** Разработчику запрещён новый
полный прогон (треб. 6, AC-25), но `--failed` разрешён, а перечень
упавших `failed.json` лежит в том же открытом роли каталоге
(`suite_run.py:137-139`, `:229`, `:648-662`): подложенный перечень `["tests"]` +
`suite-run <id> --failed` дают полный набор. Обход существует и без этой
задачи (запрет — «отсечение ошибочного вызова, не граница»,
`suite_run.py:247-251`); AC-25 его не закрывает. Решение — за Оператором:
принять как прежний остаточный риск или потребовать, чтобы исполнитель
сверял перечень повтора с итогом прошлого исполненного им прогона.

**Е3 (не отклонение).** Предел очереди 3 держит только команда (треб. 12);
подложенные файлы его обходят, но исполняются по одному в пределе шага и
под общим замком — нагрузка не больше, чем у роли, повторяющей запросы
после каждого итога.

Итог запроса как свидетельство для гейтов закрыт треб. 15 и AC-18; имя
проекта и pid из файлов роли для `down` закрыты треб. 13 и AC-22.

## Вердикт

**concerns** — SPEC вести можно; отклонения решает Оператор на гейте:

1. В1 — формат файла запроса (путь, сериализация, ключи, значения вида)
   не задан; AC-1, AC-8, AC-10, AC-11, AC-25 требуют писать/править файл
   в обход команды — тест навяжет устройство
   (SPEC.md, треб. 1-2; AC-1, AC-8, AC-10, AC-11, AC-25).
2. Е1 — нет отказа исполнителя запросу задачи без раннера `compose`:
   подложенный файл запускает планку роли на хосте в окружении пульта
   (SPEC.md, треб. 8, 11; `suite_lock.py:40-44`;
   `docs/adr/0023-role-step-sandbox.md:1421-1426`).
3. Г1 — «без `start_new_session`» вместе с «снятием группы процессов
   прогона» без названной своей группы (`process_group=0`) ведут к
   `killpg` группы пульта (SPEC.md, треб. 8, 13; AC-14).
4. Д1 — ограничение существующих тестов на ожидание агента названо только
   для `FakeProc`; `mock.Mock` с `wait.side_effect=[TimeoutExpired, -9]`
   (`tests/test_agent_failure.py:321-325`, `tests/test_step_cost.py:911-919`)
   ломается от опроса `proc.wait` (SPEC.md, «Не входит»; `runner.py:1997`).
5. В2 — форма поиска проекта у `docker` для AC-22 не задана; образец —
   `orchestrator/doctor/orphans.py:339-343` (SPEC.md, треб. 13, AC-22).
6. В3 (мелкое) — действие журнала «прогон по запросу роли» не отделено
   от текста; вторая часть AC-17 зависит от совпадения имени (SPEC.md,
   треб. 14, AC-17).
7. Е2 (к сведению) — подложенный `failed.json` + `--failed` даёт
   разработчику полный набор; AC-25 этот прежний обход не закрывает
   (`suite_run.py:137-139`, `:229`, `:648-662`).

Факты SPEC о коде и утверждение записки о SIGINT/SIGTERM подтверждены
кодом и опытом; потерь требований ТЗ, ANSWER-1 и решений гейта нет.
