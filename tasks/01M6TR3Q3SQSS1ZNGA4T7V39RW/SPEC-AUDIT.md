# SPEC-AUDIT: Прогоны в контейнере по запросу роли — plank-run и suite-run для проекта с раннером compose

  (`start_new_session=True`); `config.SUITE_RUN_MAX_WAIT_MIN = 9` —
  `orchestrator/config.py:270`; `_state_dir` = `suite_lock.directory()` —

- `suite_lock.defer_journal` — `orchestrator/suite_lock.py:229`.

Не подтвердилось или неполно:

- **Б1. `plank-run <id> --wait <минуты>` недостижим через диспетчер.**
  `orchestrator/artel.py:2797-2798`: `plank_run.cmd_plank_run(rest[0],
  rest[1] if len(rest) > 1 else None)` — третий аргумент (минуты) в команду
  не передаётся, `--wait` приходит как `file_arg`. `artel.py` по SPEC («Не
  входит») — только чтение. Треб. 2 и AC-2 для `plank-run` выполнимы только
  чтением `sys.argv` в обход диспетчера (`artel.py:2707-2711`). Справка
  `artel.py:207` («plank-run <id> [<файл>]») и обоснование белого списка
  `artel.py:2566-2569` («plank-run … состояния пульта не меняет») тоже
  устаревают, а править их нельзя. SPEC это место не называет.
- **Б2. «Тем же путём, что прерванный прогон гейта (включая снятие стенда
  Compose)» (треб. 9) — такого пути в коде нет.** Стенд снимается только в
  `finally` самого `_compose_report_run` (`acceptance.py:1464-1473`), то есть
  при исключении или таймауте внутри процесса прогона. Прерванный извне
  прогон гейта (снятие группы процессов, `pause-now`) стенд не снимает —
  его как «забытый стенд» находит `doctor` и снимает `doctor --fix`
  (`orchestrator/doctor/orphans.py:382-410`). Опыт (временный каталог,
  `timeout 20`): процесс Python без обработчика, получивший SIGTERM, выходит
  с rc -15 и `finally` не исполняет. Значит, если исполнитель снимет
  фоновый процесс прогона так же, как `liveness.terminate_process_group`
  снимает группу шага (`runner.py:2005`), стенд останется. Механизм снятия
  (обработчик сигнала, прерывание в потоке, явный `down` по имени проекта)
  SPEC не задаёт, а ссылается на путь, которого нет.
- **Б3. «Прежний узел» планки — не только `acceptance.run_plank`** (треб. 5).
  Источник планки (черновик каталога документов в `tests_writing`,
  ссылка — в прочих состояниях: `plank_run.py:176-193`), выкладка
  `acceptance.plank_in_code_copy` (`:275-277`), проверки до выкладки
  (`:194-256`) и строки отчёта «итог pytest/vitest» (`:290-309`) живут в
  `cmd_plank_run`, а не в `run_plank`. Исполнитель, вызвавший только
  `run_plank`, прогонит пустой путь и не даст «прежнего формата отчёта
  `plank-run`». Не ошибка, но формулировка SPEC неточна.
- **Б4. Песочница Codex.** На запись роли Codex из хозяйства пульта открыт
  только `suite_lock.directory()` (`orchestrator/providers/codex.py:416-440`;
  модуль вне зон). Запрос, положенный в другое место, роль Codex записать не
  сможет. SPEC место не закрепляет (А2).
- **Б5. Журнал через `defer_journal` (треб. 10).** `defer_journal` откладывает
  только действия закрытого перечня `suite_lock.deferrable`
  (`suite_lock.py:212-222, 234-235`); нового действия «прогон по запросу
  роли» там нет, вызов вернёт `False`. По треб. 10 запись делает исполнитель
  — процесс пульта с правом записи в БД, так что отложенная запись ему не
  нужна. Но SPEC оставляет её как вариант, и прямой путь к ней — расширить
  перечень `deferrable` (см. Д3, Е1).

Тест, запущенный до кода: для всех AC роль-процесс сейчас идёт прежним путём
(`plank-run` отказывает кодом с `COMPOSE_ROLE_REFUSAL`, `suite-run` запускает
отвязанный фон), исполнителя нет — красные фазы падают на отсутствии
запроса или исполнителя, без рекурсии git. Опасность одна — AC-3 (ниже).

- **В1. Запросы, оставшиеся в очереди к концу шага, не определены.** Треб. 9
  говорит только об исполняемом прогоне. Ждущие в очереди запросы шага N
  возьмёт исполнитель шага N+1 (возможно, другой роли): «запрос без шага роли
  этой задачи в полёте» (треб. 7) по букве выполнен — шаг N+1 в полёте.
  Ни один AC этого не ловит.
- **В2. `suite-run --wait` до взятия запроса.** `_wait` читает `run.json` и
  `result.json` (`suite_run.py:824-857`). Пока запрос в очереди и `run.json`
  исполнитель не переписал, `--wait` ответит итогом прошлого прогона задачи
  (если `result.run == run.run`) как итогом нового запроса, либо «нет ни
  одного прогона»/«оборван», если в `run.json` лежит pid завершённого фона.
  SPEC не задаёт, что показывает `--wait` для принятого, но ещё не взятого
  запроса, и AC-3 этого не проверяет (в чистой песочнице прошлого итога нет).

## Пути обхода гейтов

- **Е1.** Разработчик выполняет треб. 10 буквально через `defer_journal`,
  добавив действие в `deferrable`. Роль Codex пишет каталог очереди
  (`suite_lock.py:194-204`) и подкладывает зелёную запись журнала о прогоне,
  которого не было. Журналу верит Оператор. Нужен запрет: запись журнала
  пишет только исполнитель напрямую, перечень `deferrable` не расширяется.
- **Е2.** Итог запроса лежит в каталоге, открытом роли на запись
  (`suite_lock.directory()`). Роль может записать `result.json` сама, и
  `--wait` выдаст этот итог (так и сейчас у `suite-run`). Пока итог
  запроса не идёт в гейты, это не обход. Но SPEC не говорит, что итог
  запроса — не свидетельство для гейтов и ревью. Замечание, не блокер.
- **Е3.** «Запрос без шага роли в полёте»: без признака из В1 исполнитель
  шага N+1 исполнит запросы шага N.
- **Е4.** Флаг исполнителя, отключающий проверку роли в
  `_compose_report_run`, формально допустим («в `acceptance.py` только вызов
  узлов»). Его закрывает треб. 11 и AC-15 — при условии, что AC-15
  проверяет и `HOME` дома роли без маркера (как
  `test_01m6paj61d4pyap79adrpa6mwv_compose_run.py:1511-1512`). SPEC этот
  вариант признака не называет — стоит перенести.
