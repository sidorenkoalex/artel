# SPEC: G1б — итог тестов компонента из отчёта: JUnit, отчётчик пульта для Vitest, окружение и установка пультом

## Контекст
Это вторая задача волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`: «Решение» пп. 4, 8, 10, 12; строка G1б в «Порядке исполнения»). Схема компонентов уже в main:
- G1а (01M58FNWBV25FF26E7AZ9Q9912) — `project_profile.components`, `select_components`, `test_id`/`parse_test_id`;
- G1а-2 (01M58PG72PG64GS790XM2EWS61) — `Profile.tools`, `with_tools`, проверки `doctor`, ключ кэша.

Как сейчас:
- итог любого прогона пульт читает из кода возврата и текста pytest: `orchestrator/acceptance.py:374` `run_summary_line`, `:1516` `_full_suite_outcome`, `:1950` `failed_entries`, `orchestrator/suite_run.py:349` `parse`;
- `suite-run` отказывает не-pytest команде (`suite_run.py:262` `_is_pytest`);
- полный прогон гейта мержа гоняет один профиль (`fsm_merge_gate.py:818-850`) и идёт только после применённых приложений PLAN (`_full_suite_or_refuse` из `_apply_plan_appendices`, `fsm_merge_gate.py:1038-1068`);
- поле `install` профиля не исполняется (`targets.py:61-63`);
- сторож зависших тестов узнаёт только `pytest`/`unittest` (`doctor/hung_test_watchdog.py:20`);
- JUnit Vitest не различает провал проверки и ошибку.

Задача переводит компоненты с отчётом на итог только из отчёта. Пульт получает свой отчётчик Vitest, установку зависимостей и исполнение `checks_local`. Вводится инвариант 41. Поведение артели не меняется. Решения Оператора по батчу вопросов — `tasks/01M590GJAF0EDV4NBC4C99MFVH/ANSWER-1.md` (пп. 1–8). Решения Оператора по SPEC-AUDIT на гейте SPEC (возврат 19.10.2026, пп. 1–9) внесены в требования 2, 3, 7, 12, 13 и AC-2, AC-4, AC-5, AC-9, AC-10, AC-15, AC-17, AC-19.

Запись с несколькими компонентами остаётся под отказом `MULTI_COMPONENT_PENDING` на входах гейтов (ANSWER-1, п. 1). Отказ стоит:
- на входе гейта мержа — `fsm_merge_gate.py:1253-1265` → `project_profile.decide`, `project_profile.py:158-162`;
- в `acceptance._task_own_profile` — `acceptance.py:2459-2460`;
- в `suite-run` — `suite_run.py:279-281`;
- в строке предела `doctor`.

Механика по компонентам (прогон каждого затронутого компонента, `checks_local`, предел) делается и проверяется в узлах полного прогона. Сквозной путь появится после G3а/G3б.

## Требования

1. **Итог `junit-xml` из отчёта.** Для компонента с `report: junit-xml` пульт добавляет к команде компонента `report_args`. Подстановка `{path}` в них — файл отчёта вне рабочей копии. Команда запускается в `workdir` компонента, с чистым окружением компонента, своей группой процессов и таймаутом. Итог читается **только из отчёта**. По каждому тесту итог несёт:
   - идентификатор компонента (ADR-0026 п. 3, `project_profile.test_id`);
   - исход: `passed`, `failed`, `error` или `skipped`;
   - вид падения;
   - причину пропуска;
   - время.

   Текст вывода раннера на исход не влияет.
2. **Умолчание `report_args` для `junit-xml`.** У `report: junit-xml` без `report_args` пульт подставляет `[--junitxml, {path}]` — только у записей с итогом из отчёта (требование 4): у записи `test_profile` с `runner: pytest-own` и `report` (у такой записи `report_args` быть не может, `targets.py:44-60`) и у компонента записи `components:` с `report`. У артели (`runner: pult-pytest`) и у записи `test_profile` без `report` команда прежняя, умолчание не подставляется. Умолчание живёт в `orchestrator/project_profile.py`. Явные `report_args` компонента имеют приоритет над умолчанием (ANSWER-1, п. 3; решение Оператора на гейте SPEC, п. 3).
3. **Исход «неизвестно».** Исход «неизвестно» не зелёный. Он наступает:
   - при коде возврата без разборчивого отчёта (отчёта нет или он не разобран);
   - при отчёте без тестов и ненулевом коде.

   Форма исхода (ANSWER-1, п. 5):
   - значение исхода — константа `acceptance.FULL_SUITE_NOT_STARTED`;
   - деталь начинается с `итог неизвестен: <причина>`;
   - в узлах `acceptance` и в выводе он называется «неизвестно»;
   - прогон у исхода «неизвестно» был: лог прогона пишется, и деталь называет путь лога (в отличие от «прогон не начат», который возвращается без лога, `acceptance.py:2363-2366`).

   Исход отличается от «красный прогон» и «таймаут прогона». От «прогон не начат» его отличает деталь. `approve --accept-red` отказывает исходу «неизвестно» существующей веткой `fsm.py:1304-1313`, без правки `orchestrator/fsm.py`. Подсказка гейта мержа для этого исхода (`fsm_merge_gate.py:996-1005`, сейчас «повтори, когда машина освободится») называет исход «неизвестно» и его причину (решение Оператора на гейте SPEC, п. 8).
4. **Различитель «итог из отчёта»** (ANSWER-1, п. 4).
   - На прежнем разборе (код возврата и текст pytest) остаются запись `test_profile` с `runner: pult-pytest` (артель) и запись `test_profile` без `report`.
   - Итог из отчёта получают запись `test_profile` с `report` и `runner: pytest-own` (sled backend) и любой компонент записи `components:` с `report`. `runner` компонента при этом не читается.
5. **Отчётчик пульта для `pult-vitest`.** Для компонента с `report: pult-vitest` пульт даёт свой отчётчик: файл в репозитории пульта, в новом каталоге `orchestrator/reporters/`. Отчётчик пишет JSON по каждому тесту:
   - идентификатор;
   - состояние;
   - имя ошибки;
   - признак таймаута;
   - падение хука (какого);
   - `mode` (`run`/`skip`/`todo`/`only`);
   - признак `fails`;
   - число повторов.
6. **Классификация исходов `pult-vitest`.**
   - Падение с именем ошибки из `failure_errors` компонента — провал проверки.
   - Падение с иным именем ошибки (в том числе `TypeError`), таймаут и падение хука — ошибка.
   - `skip`, `todo`, `only` и `fails` различимы в итоге.
   - Число повторов теста видно в итоге.
   - Тест с числом повторов больше 0 не зелёный: прогон красный с причиной «повтор» (вторая половина инварианта 41).
7. **Команда и окружение Vitest задаёт пульт** (ТЗ п. 2; ANSWER-1, п. 6; решения Оператора на гейте SPEC, пп. 1, 2, 4).
   - Прогон `pult-vitest` идёт в тех же условиях, что `junit-xml` (требование 1): в `workdir` компонента, с чистым окружением компонента, своей группой процессов и таймаутом.
   - В окружении стоит `CI=true`.
   - `command` компонента `pult-vitest` обязан совпасть с базовым argv `node_modules/.bin/vitest run --config vitest.config.js --allowOnly=false --update=false --retry=0` — без `--expect.requireAssertions`. Этот флаг добавляет пульт сам, если версия Vitest его принимает. Версию пульт берёт из `tools` компонента или из вывода `--version`.
   - Кэш Vite/Vitest лежит вне `node_modules` и вне рабочей копии — в каталоге пульта проекта. Механизм — флаг командной строки, который добавляет пульт (кандидаты `--cacheDir` / `--cache.dir`; какой — подтверждает проба этапа 2). Пока флаг кэша не подтверждён для версии Vitest компонента, подготовка прогона отказывает с текстом.
   - Отказы подготовки прогона (прогон не зелёный, текст называет причину): расхождение `command` с базовым argv (в том числе `--expect.requireAssertions` внутри `command`); версия Vitest не принимает `--expect.requireAssertions` (текст называет флаг); флаг кэша не подтверждён для версии Vitest; в `report_args` компонента нет `{pult_reporter}` или `{path}`.
   - `report_args` компонента подставляют `{path}` и `{pult_reporter}`. `{pult_reporter}` — путь файла отчётчика в `orchestrator/reporters/`, подключаемый `--reporter=<путь>`.
   - Подмножество тестов (планка, `suite-run --failed`) передаётся подстановкой `{tests}` в `select` компонента. Без `select` прогон подмножества отказывает с текстом, а полный прогон идёт.
8. **Места прогона.** Итог по отчёту действует во всех местах прогона по профилю проекта:
   - прогон планки `acceptance.run` на каждом из его входов: рубеж `in_dev → verifying` (`advance_gates/acceptance.py:405`, `:408`), подтяжка main (`pull.py:668`, `:671`), `amend-tests` (`amend.py:554`, `:728`);
   - повтор красных `acceptance.run_repeat` (`advance_gates/acceptance.py:169`);
   - `acceptance.run_plank` (`plank-run`);
   - сухой сбор `acceptance.collect` и `advance_gates/tests_writing.py`;
   - `suite-run`;
   - двусторонний прогон (вызов, `advance_gates/two_sided.py`);
   - полный прогон гейта мержа.
9. **`suite-run` и не-pytest команды.** `suite-run` не отказывает компоненту с отчётом по признаку «не pytest» (`_is_pytest`) и не добавляет флаги xdist к не-pytest команде. Для записи `test_profile` без `report` с не-pytest командой отказ прежний.
10. **Полный прогон гейта мержа** (ANSWER-1, п. 2).
    - Существующий прогон гейта мержа (после применённых приложений PLAN, `fsm_merge_gate.py:1038-1068`) идёт **по каждому затронутому компоненту**.
    - Компоненты выбирает `project_profile.select_components` по диффу ветки вместе с путями приложений.
    - Итог прогона зелёный, только если зелёны все прогнанные компоненты.
    - Предел полного набора (`full_suite_limit`) берётся по компоненту — его `full_suite_timeout_sec`.
    - Новый безусловный прогон не вводится: без приложений, или когда все приложения уже в main, полного прогона на гейте мержа по-прежнему нет.
11. **Запись с несколькими компонентами** (ANSWER-1, п. 1). Отказ `MULTI_COMPONENT_PENDING` остаётся на всех входах, перечисленных в «Контексте»: вход гейта мержа, `acceptance._task_own_profile`, `suite-run`, строка предела `full-suite-timeout-<проект>` в `doctor`. Прогон каждого затронутого компонента, `checks_local` и предел по компоненту делаются в узлах полного прогона (`acceptance.full_suite`/`run_full_suite`, шаг полного прогона гейта мержа). Эти узлы работают с записью из двух компонентов, когда их зовут напрямую, без прохода через `approve`.
12. **Установку зависимостей исполняет пульт** (решение Оператора на гейте SPEC, п. 6).
    - Пульт исполняет команду `install` компонента один раз на версию файла блокировки компонента. Для npm это `npm ci --ignore-scripts`, файл блокировки — `package-lock.json`.
    - Файл блокировки берётся из рабочей копии ветки задачи — того дерева, что проверяется, а не из main. Установка ключуется суммой его содержимого.
    - Правило одно для любого `install` (`npm ci`, `uv sync` и др.): файл блокировки — в `workdir` компонента. `install` без файла блокировки в `workdir` — отказ прогона с текстом формы «install без файла блокировки не исполняется», не зелёный.
    - Каталог зависимостей (`node_modules`) и кэш принадлежат пульту. К рабочей копии задачи они подключаются только для чтения: символьная ссылка на каталог пульта с правами только чтения или эквивалент.
    - Прогоны гейтов используют тот же каталог.
    - Перед прогоном гейт сам сверяет, что `node_modules` рабочей копии подключён к каталогу пульта, и не доверяет каталогу дерева. Подменённое подключение — отказ прогона, не зелёный.
    - Сбой установки — отказ прогона с текстом, не зелёный.
13. **`checks_local`** (ANSWER-1, п. 7; решение Оператора на гейте SPEC, п. 5). Пульт исполняет `checks_local` компонента внутри узла полного набора приёмки `acceptance.acceptance_suite` (`acceptance.py:2393`) — он общий для `approve` (`fsm.py:1294-1296`) и автогейта (`fsm_autogate.py:326-328`); `orchestrator/fsm_autogate.py` не трогается. Так же — на каждом гейте мержа затронутого компонента. Это не зависит от того, откуда взят итог полного набора (свежий прогон, кэш `acceptance.py:2327-2343`, CI `acceptance.py:2422-2429`) и шёл ли прогон вообще. Ненулевой код проверки — красный итог с выводом проверки.

19. **Инвариант 41.** Новый инвариант 41 «неизвестный или неразобранный местный итог тестов не зелёный; повторы внутри прогона компонентов с отчётом пульта запрещены» — это строка `docs/invariants.md` и проверка в `tests/test_invariants.py`. Обе правки едут приложением к PLAN: пути защищённые, применяет пульт по приложению, коммит — по правилам приложений. Проверка инварианта поведенческая. На учебной записи она утверждает, что итог «неизвестно» не зелёный и что тест с повтором больше 0 не зелёный. Наличия строки для неё недостаточно. Сторож свойства лежит внутри того же приложения.
20. **Проверки детерминированы**, без сети и без настоящего Node. Учебный проект содержит компоненты `junit-xml` (pytest) и `pult-vitest` (подменённый раннер, пишущий заранее заданный JSON отчётчика). Сценарии:
    - зелёный;
    - провал проверки;
    - ошибка;
    - таймаут;
    - падение хука;
    - `skip`/`todo`/`only`/`fails`;
    - повтор;
    - отчёта нет;
    - отчёт не разобран;
    - сбой установки.

## Критерии приёмки

AC-1. Компонент `junit-xml`:
- зелёный отчёт — зелёный итог;
- отчёт с проваленным тестом — красный итог по провалу;
- отчёта нет — исход «неизвестно», не зелёный.

В каждом случае исход определяется отчётом, а не текстом вывода раннера: тот же вывод с другим отчётом даёт другой исход (требования 1, 3).

AC-2. Компонент `junit-xml`:
- ненулевой код возврата при отчёте без тестов — исход «неизвестно», не зелёный;
- неразборчивый отчёт — исход «неизвестно», не зелёный;
- по каждому тесту итог несёт идентификатор вида `<компонент>:<путь>::<имя>`, где `<путь>` — от корня репозитория: у компонента с непустым `workdir` (например `workdir: frontend`) путь содержит его (`frontend/src/x.test.jsx`), а не путь от `workdir` (`src/x.test.jsx`); исход из `passed`/`failed`/`error`/`skipped`, вид падения, причину пропуска и время (требования 1, 3).

AC-3. Команда компонента `junit-xml` получает `report_args`, где `{path}` указывает на файл вне рабочей копии. Команда запускается в `workdir` компонента с окружением компонента и не наследует прочее окружение пульта (требование 1).

AC-4. Умолчание `report_args`:
- запись `test_profile` с `report: junit-xml` и `runner: pytest-own` без `report_args` запускается с аргументами `--junitxml <путь вне рабочей копии>`, и её итог читается из отчёта;
- компонент с явными `report_args` запускается с ними, а не с умолчанием;
- argv полного прогона и прогона планки у записи артели (`runner: pult-pytest`, `report: junit-xml`) и у записи `test_profile` без `report` совпадает с argv main: умолчание `[--junitxml, {path}]` к нему не добавляется (требования 2, 17, 18).

AC-5. Исход «неизвестно»:
- значение исхода — `acceptance.FULL_SUITE_NOT_STARTED`;
- деталь начинается с `итог неизвестен: `;
- вывод узла `acceptance` называет исход «неизвестно»;
- лог прогона записан, и деталь исхода называет его путь;
- `approve --accept-red` гейта приёмки на этом исходе отказывает, задача не продвигается;
- подсказка гейта мержа на исходе «неизвестно» называет исход «неизвестно» и его причину, а не «повтори, когда машина освободится» (требование 3).

AC-6. Различитель:
- запись `test_profile` с `runner: pult-pytest` и `report: junit-xml` (как у артели) получает итог по коду возврата и тексту pytest, а не из отчёта;
- запись `test_profile` без `report` — тоже по коду возврата и тексту pytest;
- запись `test_profile` с `report: junit-xml` и `runner: pytest-own` получает итог из отчёта;
- компонент записи `components:` с `report: pult-vitest` без поля `runner` получает итог из отчёта (требование 4).

AC-7. Компонент `pult-vitest`:
- падение `TypeError` — ошибка;
- падение `AssertionError` (имя из `failure_errors`) — провал проверки;
- таймаут — ошибка с признаком таймаута;
- падение хука — ошибка с названием хука (требования 5, 6).

AC-8. Компонент `pult-vitest`:
- тест `it.fails` и тест `todo` различимы в итоге: между собой, с зелёным и с пропущенным;
- `skip` и `only` различимы;
- число повторов теста видно в итоге;
- тест с числом повторов больше 0 при зелёном состоянии даёт красный итог с причиной «повтор» (требования 5, 6).

AC-9. Прогон `pult-vitest` на подменённом раннере:
- запускается в `workdir` компонента, с окружением компонента без прочего окружения пульта, в своей группе процессов и с таймаутом: раннер, превысивший таймаут, снимается вместе с группой, итог не зелёный;
- окружение содержит `CI=true`;
- argv начинается с базового `node_modules/.bin/vitest run --config vitest.config.js --allowOnly=false --update=false --retry=0` и содержит `--reporter=<путь файла orchestrator/reporters/>` (через `{pult_reporter}` в `report_args`);
- `--expect.requireAssertions` добавлен пультом, когда версия Vitest компонента его принимает; если не принимает — подготовка отказывает с текстом, называющим флаг, и итог не зелёный;
- флаг кэша передан пультом, и его путь лежит вне рабочей копии и вне `node_modules`;
- для версии Vitest без подтверждённого флага кэша подготовка отказывает с текстом, итог не зелёный (требование 7).

AC-10. Компонент `pult-vitest`, отказы подготовки (каждый с текстом, итог не зелёный):
- `command` не совпадает с базовым argv требования 7 (например `[npx, vitest, run]`, argv с чужим `--config`/`--retry` или с `--expect.requireAssertions` внутри `command`);
- в `report_args` нет `{pult_reporter}`;
- в `report_args` нет `{path}`.

Передача подмножества:
- подмножество тестов передаётся подстановкой `{tests}` в `select`;
- без `select` прогон подмножества отказывает с текстом, а полный прогон идёт (требование 7).

AC-11. Для компонента `junit-xml` с исходом «неизвестно» ни одно место прогона не даёт зелёного итога. Места:
- рубеж `in_dev → verifying` (`acceptance.run` из `advance_gates/acceptance.py`);
- подтяжка main (`pull.py`);
- `amend-tests` (оба входа `amend.py`);
- повтор красных `run_repeat`;
- `plank-run` (`run_plank`);
- сухой сбор (`collect`, `advance_gates/tests_writing.py`);
- `suite-run`;
- двусторонний прогон (требования 3, 8).

AC-12. `suite-run`:
- для компонента с отчётом и не-pytest командой не отказывает по признаку «не запуск pytest» и не добавляет к команде флаги xdist (`-n`);
- для записи `test_profile` без `report` с не-pytest командой отказ прежний (требования 9, 17).

AC-13. Узел полного прогона гейта мержа (после приложений) на учебной записи из двух компонентов, оба затронуты:
- гоняет оба компонента;
- итог зелёный, только если зелёны оба, и красный, если красен любой;
- предел каждого прогона — `full_suite_timeout_sec` своего компонента;
- компонент, затронутый только путём приложения PLAN, тоже прогоняется;
- без приложений полного прогона на гейте мержа нет, как на main (требование 10).

AC-14. Запись с несколькими компонентами по-прежнему отказывается с `MULTI_COMPONENT_PENDING` на входе гейта мержа, в `acceptance._task_own_profile`, в `suite-run` и в строке предела `full-suite-timeout-<проект>` у `doctor`. Узлы полного прогона, вызванные напрямую с такой записью, гоняют каждый затронутый компонент (требования 10, 11).

AC-15. Установка `install`:
- исполняется пультом один раз на версию файла блокировки: второй прогон при той же сумме содержимого `package-lock.json` установку не повторяет, смена содержимого — повторяет;
- файл блокировки читается из рабочей копии ветки задачи: правка `package-lock.json` в ветке (при неизменном main) ведёт к новой установке;
- `install` без файла блокировки в `workdir` компонента не исполняется — отказ прогона с текстом «install без файла блокировки не исполняется», не зелёный; то же правило — у не-npm `install` (например `uv sync` без `uv.lock`);
- сбой установки — отказ прогона с текстом, не зелёный (требование 12).

AC-16. Каталог зависимостей:
- `node_modules` в рабочей копии — подключение каталога пульта только для чтения, запись в него из рабочей копии отказывает;
- прогон гейта использует тот же каталог;
- подмена подключения (`node_modules` рабочей копии заменён собственным каталогом или ссылкой не на каталог пульта) — отказ прогона, не зелёный (требование 12).

AC-17. `checks_local` компонента:
- исполняются в узле `acceptance.acceptance_suite` — его вызов с `actor="operator"` (путь `approve`) и с `actor="fsm"` (путь автогейта) одинаково гоняет `checks_local` — и на гейте мержа, в том числе когда итог полного набора взят из кэша или из CI;
- ненулевой код проверки — красный итог, вывод проверки виден в тексте итога (требование 13).

AC-18. Ключ базы итога у компонента с отчётом:
- меняется при смене `tools`, содержимого файла блокировки, команды или `report_args`;
- различен у двух компонентов одного дерева;
- одинаков у входа гейта мержа и у входа `suite-run`;
- профиль `suite-run` несёт `tools` компонента;
- у записи артели ключ равен значению main (требования 14, 15).

AC-19. Сторож зависших тестов:
- признаёт зависшим процесс с командой компонента проекта по `command` записи (например `node_modules/.bin/vitest run`), а не только `pytest`/`unittest`;
- процесс с командой, не совпадающей с `command` ни одной записи (и не `pytest`/`unittest`), зависшим не признаёт, как бы долго он ни шёл (требование 16).

AC-20. У артели исходы и тексты требования 17 прежние. На прежних входах (вывод pytest, код возврата) с значениями main совпадают:
- константы;
- строки журнала;
- выжимка;
- разбор итоговой строки;
- строки `suite-run`;
- тексты отказов.

Требования 17, 18.

AC-21. Инвариант 41 стоит строкой в `docs/invariants.md` в приложении PLAN, проверка инварианта — в `tests/test_invariants.py` того же приложения. Проверка поведенческая: на учебной записи она падает при мутациях «исход "неизвестно" считается зелёным» и «тест с повтором больше 0 считается зелёным». `git apply --check` приложения на чистом дереве проходит (требование 19).

## Оценка объёма и деление

Сработали сигналы:
- число файлов зоны ≥ 5 (17 элементов зоны);
- число критериев приёмки ≥ 10 (21);
- `budget_usd` ≥ $30 ($60 — рамка ТЗ).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
- Узел всех требований — `orchestrator/acceptance.py`: прогон планки, сбор, полный набор, ключ итога, разбор исхода. Зона не режется поперёк: любая часть деления держала бы её же.
- Инвариант 41 «неизвестный итог не зелёный» осмыслен, только когда итог по отчёту действует во всех местах прогона разом. Часть, переводящая на отчёт одни места (планку) без других (полный набор гейта мержа, `suite-run`), оставила бы компонент sled backend с двумя источниками исхода, расходящимися между гейтами. Это промежуточное состояние с ослабленным свойством.
- Полный прогон по каждому затронутому компоненту (требование 10) без итога из отчёта (требования 1–7) гонял бы `pult-vitest` без разбора — исход не определён.
- Если Оператор предпочтёт деление, естественный шов — отдельная вторая часть «установка пультом + `checks_local`» (требования 12, 13). Первая часть мержима отдельно: без второй прогон `pult-vitest` в рабочей копии роли не имеет `node_modules` и отказывает (не зелёный, fail-closed). Цена деления — ещё один цикл analyst/test_author/review (~$15–20) сверх рамки $60.
- ADR-0026 («Порядок исполнения») оценивает G1б одной задачей в $50–65.
