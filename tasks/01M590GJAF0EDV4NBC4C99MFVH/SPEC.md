# SPEC: G1б — итог тестов компонента из отчёта: JUnit, отчётчик пульта для Vitest, окружение и установка пультом

## Контекст
Вторая задача волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`, «Решение» пп. 4, 8, 10, 12; строка G1б «Порядка исполнения»). Схема компонентов уже в main: G1а (01M58FNWBV25FF26E7AZ9Q9912 — `project_profile.components`, `select_components`, `test_id`/`parse_test_id`) и G1а-2 (01M58PG72PG64GS790XM2EWS61 — `Profile.tools`, `with_tools`, проверки `doctor`, ключ кэша). Сегодня итог любого прогона пульт читает из кода возврата и текста pytest (`orchestrator/acceptance.py:374` `run_summary_line`, `:1512` `_full_suite_outcome`, `:1946` `failed_entries`; `orchestrator/suite_run.py:349` `parse`), `suite-run` отказывает не-pytest команде (`suite_run.py:262` `_is_pytest`), гейт мержа гонит один профиль (`fsm_merge_gate.py:818-850`), поле `install` профиля не исполняется (`targets.py:61-63`), сторож зависших тестов узнаёт только `pytest`/`unittest` (`doctor/hung_test_watchdog.py:20`), а JUnit Vitest не различает провал проверки и ошибку. Задача переводит компоненты с отчётом на итог только из отчёта, даёт пульту свой отчётчик Vitest, установку зависимостей и `checks_local`, и вводит инвариант 41 — при неизменном поведении артели.

Различитель «итог из отчёта» в этом SPEC: компонент (или профиль `test_profile`) с заданным `report` (`junit-xml` или `pult-vitest`) и раннером, отличным от `pult-pytest`. У артели в `targets.yaml` стоит `report: junit-xml` при `runner` по умолчанию `pult-pytest` (`targets.py:69`) — по ТЗ (требование 7) она остаётся на прежнем разборе; запись sled backend (`runner: pytest-own`, `report: junit-xml`) переходит на итог из отчёта.

## Требования

1. Для компонента с `report: junit-xml` пульт добавляет к команде компонента `report_args` с подстановкой `{path}` — файл отчёта вне рабочей копии; запускает команду компонента в его `workdir` с чистым окружением компонента, своей группой процессов и таймаутом; итог читает **только из отчёта**: по каждому тесту — идентификатор компонента (ADR-0026 п. 3, `project_profile.test_id`), исход (`passed` / `failed` / `error` / `skipped`), вид падения, причина пропуска, время. Текст вывода раннера на исход не влияет.
2. Код возврата без разборчивого отчёта (отчёта нет, отчёт не разобран) или отчёт без тестов при ненулевом коде — исход «неизвестно», не зелёный. Исход «неизвестно» различим от «красный прогон», «таймаут прогона» и «прогон не начат» во всех местах, где показывается исход.
3. Для компонента с `report: pult-vitest` — отчётчик пульта: файл в репозитории пульта в новом каталоге `orchestrator/reporters/`, подключаемый `--reporter=<путь>`. Отчётчик пишет JSON по каждому тесту: идентификатор, состояние, имя ошибки, признак таймаута, падение хука (какого), `mode` (`run`/`skip`/`todo`/`only`), признак `fails`, число повторов.
4. У `pult-vitest` «провал проверки» — падение с именем ошибки из `failure_errors` компонента; падение с иным именем ошибки (в том числе `TypeError`), таймаут и падение хука — ошибка. `skip`, `todo`, `only` и `fails` различимы в итоге; число повторов теста видно в итоге.
5. Окружение и команду Vitest задаёт пульт: `CI=true` в окружении; запуск `node_modules/.bin/vitest run --config vitest.config.js --allowOnly=false --update=false --retry=0` и `--expect.requireAssertions`, если флаг принимается версией Vitest; не принимается — отказ подготовки прогона с текстом, называющим флаг (прогон не зелёный). Кэш Vite — вне рабочей копии.
6. Итог по отчёту действует во всех местах прогона по профилю проекта: прогон планки (`acceptance.run_plank`), сухой сбор (`acceptance.collect`, `advance_gates/tests_writing.py`), `plank-run`, `amend-tests`, `suite-run`, двусторонний прогон (вызов, `advance_gates/two_sided.py`), полный прогон на гейте мержа. `suite-run` не отказывает компоненту с отчётом по признаку «не pytest» (`_is_pytest`) и не добавляет флаги xdist к команде не-pytest.
7. Полный прогон гейта мержа идёт **по каждому затронутому компоненту** (выбор `project_profile.select_components` по диффу ветки); итог гейта зелёный, только если зелёны все прогнанные компоненты. Предел полного набора (`full_suite_limit`) — по компоненту (`full_suite_timeout_sec` компонента).
8. Установку зависимостей исполняет пульт: команда `install` компонента исполняется пультом один раз на версию файла блокировки компонента (для npm — `npm ci --ignore-scripts`, файл блокировки `package-lock.json`). Каталог зависимостей (`node_modules`) и кэш принадлежат пульту и подключаются к рабочей копии задачи только для чтения (символьная ссылка на каталог пульта с правами только чтения или эквивалент); прогоны гейтов используют тот же каталог. Сбой установки — отказ прогона с текстом, не зелёный.
9. `checks_local` компонента исполняются пультом на гейтах приёмки и мержа вместе с полным прогоном; ненулевой код проверки — красный итог с выводом проверки.
10. Профиль `suite-run` (`suite_run._profile_command`, `orchestrator/suite_run.py:271`) получает `tools` тем же помощником `project_profile`, что `decide` и `acceptance._task_own_profile` (`project_profile.with_tools`); ключ базы итога полного набора включает `tools` компонента — одинаково у гейта мержа и у `suite-run`.
11. Сторож зависших тестов (`doctor/hung_test_watchdog.py`) узнаёт команды компонентов проекта (по `command` записи), а не только `pytest`/`unittest`.

    - исходы `acceptance.FULL_SUITE_GREEN` = `'зелёный прогон'`, `FULL_SUITE_RED` = `'красный прогон'`, `FULL_SUITE_TIMEOUT` = `'таймаут прогона'`, `FULL_SUITE_NO_TESTS` = `'tests/ нет в worktree'`, `FULL_SUITE_NOT_STARTED` = `'прогон не начат'`, `FULL_SUITE_NO_TESTS_NOTE` = `'tests/ нет в worktree — полный набор не проверен'` (`acceptance.py:1401-1420`);

    - `suite-run`: строки отчёта `[<id>] suite-run №<n> (полный набор|повтор упавших): <исход>`, `прошло: N, упало: M, пропущено: K`, `полный лог: <путь>` (`suite_run.py:426-463`), разбор `suite_run.parse` и тексты отказа `_profile_command` (`suite_run.py:279-293`, включая отказ «— не запуск pytest: флаги параллели pytest (-n) к ней неприменимы» для записи без `report`);

Тексты сводок для него: исходы и головы строк журнала — те же константы и формы, что в требовании 12 (`зелёный прогон`, `красный прогон`, `таймаут прогона`, `прогон не начат`, `полный набор tests/ зелёный|красный: …`), плюс новый исход «неизвестно» (требование 2); выжимка и перечень упавших, числа `прошло/упало/пропущено` в `suite-run` — из отчёта (идентификаторы упавших тестов и вид падения), а не из итоговой строки pytest.

## Критерии приёмки

AC-1. Компонент `junit-xml`: зелёный отчёт — зелёный итог; отчёт с проваленным тестом — красный итог по провалу; отчёта нет — исход «неизвестно», не зелёный; исход в каждом случае определяется отчётом, независимо от текста вывода раннера (тот же вывод с другим отчётом даёт другой исход) (требования 1, 2).
AC-2. Компонент `junit-xml`: ненулевой код возврата при отчёте без тестов и неразборчивый отчёт — исход «неизвестно», не зелёный; по каждому тесту итог несёт идентификатор вида `<компонент>:<путь>::<имя>`, исход из `passed`/`failed`/`error`/`skipped`, вид падения, причину пропуска и время (требования 1, 2).
AC-3. Команда компонента `junit-xml` получает `report_args` с `{path}`, указывающим на файл вне рабочей копии, и запускается в `workdir` компонента с окружением компонента, без наследования прочего окружения пульта (требование 1).
AC-4. Компонент `pult-vitest`: падение `TypeError` — ошибка, падение `AssertionError` (имя из `failure_errors`) — провал проверки; таймаут и падение хука — ошибка с признаком таймаута / названием хука (требования 3, 4).
AC-5. Компонент `pult-vitest`: тест `it.fails` и тест `todo` различимы в итоге (между собой и с зелёным/пропущенным), `skip` и `only` различимы; число повторов теста видно в итоге (требования 3, 4).
AC-6. Прогон `pult-vitest`: окружение содержит `CI=true`, argv — `node_modules/.bin/vitest run --config vitest.config.js --allowOnly=false --update=false --retry=0`, `--reporter=<путь файла orchestrator/reporters/>` и `--expect.requireAssertions`; при версии, не принимающей `--expect.requireAssertions`, — отказ подготовки с текстом, называющим флаг, итог не зелёный; кэш Vite указывает вне рабочей копии (требование 5).
AC-7. Итог по отчёту действует в прогоне планки, сухом сборе, `plank-run`, `amend-tests`, `suite-run` и двустороннем прогоне: для компонента `junit-xml` с отчётом «неизвестно» ни одно из этих мест не даёт зелёного итога (требования 2, 6).
AC-8. `suite-run` для компонента с отчётом с не-pytest командой не отказывает по признаку «не запуск pytest» и не добавляет к команде флаги xdist (`-n`); для записи `test_profile` без `report` с не-pytest командой отказ прежний (требования 6, 12).
AC-9. Полный прогон гейта мержа проекта с двумя компонентами, оба затронуты диффом, гоняет оба компонента; итог зелёный, только если зелёны оба, и красный, если красен любой; предел каждого прогона — `full_suite_timeout_sec` своего компонента (требование 7).
AC-10. Установка `install` компонента исполняется пультом один раз на версию файла блокировки: второй прогон при той же версии `package-lock.json` установку не повторяет, смена версии — повторяет; сбой установки — отказ прогона с текстом, не зелёный (требование 8).
AC-11. Рабочая копия роли не может изменить каталог зависимостей: `node_modules` в рабочей копии — подключение каталога пульта только для чтения, запись в него из рабочей копии отказывает; прогон гейта использует тот же каталог (требование 8).
AC-12. `checks_local` компонента исполняются на гейте приёмки и на гейте мержа вместе с полным прогоном; ненулевой код проверки — красный итог, вывод проверки виден в тексте итога (требование 9).
AC-13. Ключ базы итога полного набора для компонента с объявленными `tools` одинаков у входа гейта мержа и у входа `suite-run` и меняется при смене `tools`; профиль `suite-run` несёт `tools` компонента (требование 10).
AC-14. Сторож зависших тестов признаёт зависшим процесс с командой компонента проекта (по `command` записи, например `node_modules/.bin/vitest run` или `uv run --frozen pytest`), а не только `pytest`/`unittest` (требование 11).
AC-15. У артели исходы и тексты требования 12 прежние: на прежних входах (вывод pytest, код возврата) константы, строки журнала, выжимка, разбор итоговой строки, строки `suite-run` и тексты отказов совпадают со значениями main (требования 12, 13).
AC-16. Инвариант 41 стоит строкой в `docs/invariants.md` в приложении PLAN, проверка инварианта — в `tests/test_invariants.py` того же приложения; `git apply --check` приложения на чистом дереве проходит (требование 14).

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (17 элементов зоны); число критериев приёмки ≥ 10 (16); `budget_usd` ≥ $30 ($60 — рамка ТЗ).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
- Узел всех требований — `orchestrator/acceptance.py` (прогон планки, сбор, полный набор, ключ итога, разбор исхода): зона не режется поперёк, любая часть деления держала бы её же.
- Инвариант 41 «неизвестный итог не зелёный» осмыслен только когда итог по отчёту действует во всех местах прогона разом: часть, переводящая на отчёт одни места (планку) без других (полный набор гейта мержа, `suite-run`), оставила бы компонент sled backend с двумя источниками исхода, расходящимися между гейтами, — промежуточное состояние с ослабленным свойством.
- Полный прогон по каждому затронутому компоненту (требование 7) без итога из отчёта (требования 1–4) гонял бы `pult-vitest` без разбора — исход не определён.
- Естественный шов, если Оператор предпочтёт деление: «установка пультом + `checks_local`» (требования 8, 9) отдельной второй частью — без неё прогон `pult-vitest` в рабочей копии роли не имеет `node_modules` и отказывает (не зелёный, fail-closed), то есть первая часть мержима отдельно; цена деления — ещё один цикл analyst/test_author/review (~$15–20) сверх рамки $60.
- ADR-0026 («Порядок исполнения») оценивает G1б одной задачей в $50–65.

- Бриф и сводки роли (G5): итоговая строка в `agent_log.py`, `runner.py`, `watch.py`, `report.py`.
- Перевод записи sled (этап 2 плана): `targets.yaml` и `orchestrator/targets.py` — только чтение.
- Контейнерная среда.
- Прямая правка защищённых `docs/invariants.md` и `tests/test_invariants.py` в ветке: только приложением к PLAN (требование 14), применяет пульт.
- Правка вне зон ТЗ (в том числе `orchestrator/fsm_autogate.py`, `orchestrator/repo_context.py`, `scripts/guard.py`, `orchestrator/advance_gates/test_integrity.py`, `orchestrator/advance_gates/mandate.py`) — эскалация.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность защищённых путей вне приложения и непревышение бюджета — их держит пульт.
