## Пути обхода гейтов
- **Е9. `checks_local` гейта мержа можно вшить в ветку полного прогона после приложений.** Требование 13 (SPEC:108) велит гнать проверки на каждом гейте мержа, «шёл ли прогон вообще». Требование 10 (SPEC:98) сохраняет гейт мержа без полного прогона, когда приложений нет. Естественная точка встраивания — шаг полного прогона `_full_suite_or_refuse` (`fsm_merge_gate.py:1038-1068`), а он без приложений не вызывается. AC-17 этот случай не называет, так что у задачи без приложений (обычный случай) `checks_local` на мерже не исполнятся, и тест этого не заметит.
- **Е10. Какой файл считается файлом блокировки, задано только для npm и `uv`.** Правило «файл блокировки — в `workdir`; без него `install` не исполняется» (SPEC:103) не говорит:
  - как пульт узнаёт имя файла блокировки у произвольной команды `install`. Поля для него в схеме нет (`targets.py:84-104`). SPEC называет `package-lock.json` (npm) и пример `uv.lock` (AC-15). Таблица «команда → файл» остаётся на усмотрение исполнителя. Для неизвестной команды исполнитель может, например, взять манифест `package.json` или сумму пустого множества, а не отказать;
  - что значит пустой `install: []` у артели (`targets.yaml:51`) и у sled backend (`targets.yaml:93`): «установки нет» или «`install` без файла блокировки — отказ». У артели второе прочтение ловит AC-20. У sled backend — ничто.

  Риск — fail-open (установка по манифесту без закрытого lock-файла) у неизвестной команды и лишний отказ у пустого `install`.
- Замечание, не отклонение. Где хранится знание «версия Vitest принимает `--expect.requireAssertions`» и «флаг кэша подтверждён для версии» (SPEC:79-81), SPEC не задаёт. Решение п. 2 оставляет подтверждение пробе этапа 2. Отказ при неподтверждённом флаге fail-closed, AC-9 обе ветки проверяет. Обхода не видно: неверный флаг у настоящего Vitest даёт ошибку запуска без отчёта, то есть «неизвестно».
