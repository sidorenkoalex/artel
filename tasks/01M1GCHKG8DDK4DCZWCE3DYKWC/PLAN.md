# PLAN: Наблюдаемость сессий — идентичность в журнале, lease-события, рекон обрывов

## Подход

Идентификатор сессии (требование 1, AC-1) выносится из `lease.py` в
новый лист графа импортов `orchestrator/session.py` (только `os`, по
образцу `liveness.py`) — `lease.resolve_session_id` становится тем же
самым объектом функции (`from .session import resolve_session_id`), не
второй копией. Это снимает цикл `store -> lease -> store`: `store.py`
импортирует `session` напрямую (без цикла, `session.py` ничего из
пакета не читает).

Хранение identity в журнале (требование 2, AC-2) — новая колонка
`steps.session_id` (миграция `add_column`, тем же приёмом, что и
остальные догоняющие колонки в `store.migrate()`), не часть `detail`:
колонка не задевает формат `detail`, на который завязаны существующие
regex-парсеры алертов (`_LEASE_ALERT_RE` и соседи в `doctor.py`).

Центральное решение: `store.journal()` получает keyword-only параметр
`session_id: str | None = None` и, если он не передан явно, сама
резолвит identity ТЕКУЩЕГО процесса через `session.resolve_session_id`.
Explicit-параметр — только там, где вызывающий код уже держит identity,
отличную от «сейчас резолвящейся из окружения этого же процесса» (только
`lease.acquire()`: приёмочные тесты дают ей identity литеральной строкой
в обход `ARTEL_SESSION_ID`). Все остальные ~70 существующих мест
`store.journal(...)` по всей кодовой базе (`pause.py`, `release.py`,
`fsm.py`, `runner.py`, `budget.py`, ...) не правятся вовсе — они уже
исполняются внутри ОДНОГО процесса CLI-вызова, чей `ARTEL_SESSION_ID`/ppid
не меняется по ходу вызова, поэтому дефолтный резолв внутри `journal()`
даёт ТУ ЖЕ identity, что дала бы явная прокидка. Это не магия в ущерб
трассируемости, а единственная точка, где SPEC и просит логику держать
(«единая функция», требование 1) — при этом AC-1/AC-2/AC-6 (release,
pause/resume, pause --now) проходят без единой правки этих модулей,
поскольку их существующие вызовы `store.journal(...)` уже не передают
`session_id` и подхватывают дефолт. Правки по существу остаются только
там, где либо (а) нужно ДОБАВИТЬ новую запись журнала, которой раньше не
было (свежий захват lease, снятие при kill/done), либо (б) вызывающий
код обязан явно передать чужую/иную identity (`lease.acquire`).

Жизненный цикл lease (требование 3, AC-4..AC-6): `lease.acquire()`
журналирует ОБЕ ветки (`row is None` — новая запись «lease взят»;
перехват — существующая запись «lease перехвачен», дополненная разбором
причины: pid держателя проверяемо мёртв на ЭТОМ host -> «pid мёртв»,
иначе (чужой host или живой pid) -> прежний текст «heartbeat протух»,
триггер перехвата не меняется). Снятие «любым путём» — новая функция
`lease.release_any(conn, task_id, actor, action)`: читает текущую строку
`leases`, снимает её (`store.release_lease` по её же `session_id`, тот
же приём, что уже использует `release.cmd_release` для защиты от узкой
гонки чтение/снятие) и журналирует СНИМАЮЩУЮ (текущую, из дефолта
`journal()`) identity, а не прежнего держателя. Используется в двух
НОВЫХ точках, где lease раньше не трогался вовсе: `cleanup._cmd_kill`
(AC-6, путь `kill`) и `fsm_merge_gate._cmd_approve_merge_gate` сразу
после перехода в `done` (AC-6, путь `done`). Путь `pause --now`
(`orchestrator/pause.py::cmd_pause_now`) уже безусловно снимает lease
(`store.release_lease` напрямую) и уже журналирует это отдельной
записью — только её существующий вызов `store.journal(...)` без
`session_id` подхватывает дефолт, без изменения кода.

Рекон осиротевшего шага (требование 4, AC-7/AC-8) — в
`doctor.check_leases`: для каждого lease, подтверждённо мёртвого
(AC-9 ниже), берётся журнал задачи, и если в нём есть «agent run
started» без терминальной пары ГДЕ УГОДНО дальше (перебор по порядку с
отслеживанием «висящего старта», не сравнение с последней записью —
докстринг AC-7 в приёмочном тесте прямо предупреждает про эту ловушку)
— дописывается «шаг оборван смертью сессии `<id>`». Идемпотентность
(AC-8) — по построению: сам текст этого события содержит маркер
(«оборван»), который следующий проход того же перебора засчитывает как
терминальную пару для того же «agent run started», так что повторный
прогон второй раз этот же шаг сиротой уже не увидит. `catalog.cmd_status`
рекон не делает — SPEC явно допускает любой из `run`/`auto`/`status`/
`doctor`, а `doctor.check_leases` уже владеет и мёртвым pid, и строкой
`leases` в одном месте.

Анти-race `doctor.check_leases` (AC-9) — второй снимок
`liveness._pid_alive` после короткого `time.sleep` (0.05 с, тот же
порядок, что уже использует `pause.TERMINATE_POLL_SEC`) ПЕРЕД тем, как
считать lease мёртвым: FAIL остаётся только если оба снимка согласны.
FAIL-строка (AC-10) обогащается ролью/номером шага/временем его старта/
последним событием журнала ТОЛЬКО в `Check.detail` — сообщение,
уходящее в `alerts.raise_alert` (и разбираемое `_LEASE_ALERT_RE`),
остаётся byte-в-byte прежним, иначе авто-ack (SPEC T054) перестал бы
узнавать собственные алерты. Снимок журнала для «последнего события»
берётся ДО записи рекона тем же проходом — иначе рекон сам стал бы
«последним событием» и подменял бы то, что реально видел Оператор перед
прогоном.

Итерация 2 (REVIEW.md, R1-F1): номер и время старта шага в FAIL-строке
(AC-10) были условны на «есть неразрешённый `agent run started`»,
что оставляло FAIL-строку без этих полей в сценарии «сессия умерла
МЕЖДУ шагами» (последний запуск агента уже штатно закрыт терминальным
событием — не сирота для рекона, но AC-10 требует поля безусловно).
Исправлено выбором первого из двух вариантов ревьювера: `_lease_fail_
detail` больше не принимает `orphan` параметром, а сама находит
ПОСЛЕДНЮЮ запись «agent run started» в журнале задачи через новую
`_last_start_step(steps)` — независимо от того, закрыта ли она
терминальной парой. Для рекона (AC-7/AC-8) по-прежнему используется
отдельная `_orphaned_start_step` (нужна именно НЕзакрытая запись,
другая семантика) — две функции не объединялись, чтобы не смешивать
«что реконить» и «что показать Оператору».

`status` (требование 6, AC-11) — `catalog.cmd_status` дописывает
держателя lease (identity + жив/мёртв по тому же `liveness._pid_alive`,
для чужого host — «жив» по умолчанию: pid недоступен для опровержения,
тот же принцип, что уже применяет `doctor.check_merge_lock`) СТРОГО в
конец существующей строки — префикс (id/state/ревью/бюджет/title) не
трогается ни в порядке, ни в составе.

`log` (AC-3) — `catalog.cmd_log` дописывает `[session_id]` в конец
строки, только если колонка непустая (легаси-записи БД без миграции —
`None`) — форматированная строка, не дамп структуры.

## Шаги

1. `orchestrator/session.py` (новый модуль) + `orchestrator/lease.py`
   делегирует `resolve_session_id` туда; `orchestrator/store.py` —
   колонка `steps.session_id` (SCHEMA + migrate), `journal()` с
   дефолтным резолвом. Юнит-тесты: `session.resolve_session_id`
   (перенесённые проверки из `tests/test_lease.py`, поведение то же),
   `store.journal` — дефолт резолвит, явный параметр побеждает дефолт.

2. `lease.py::acquire()` — журнал свежего захвата (AC-4), разбор причины
   перехвата pid-мёртв/heartbeat-протух (AC-5), явный `session_id` в
   обоих вызовах `store.journal`. `lease.release_any()` — новая функция
   (AC-6, снятие «любым путём» + identity снимающей стороны). Юнит-тесты
   в `tests/test_lease.py`: фиксация свежего захвата в журнале, обе
   причины перехвата, `release_any` на существующем/отсутствующем lease.

3. Пути снятия lease «любым путём» (AC-6): `cleanup._cmd_kill` зовёт
   `lease.release_any` безусловно после перехода в `killed`;
   `fsm_merge_gate._cmd_approve_merge_gate` — сразу после перехода в
   `done`. `pause.cmd_pause_now` не правится (уже безусловно снимает и
   журналирует — дефолтный резолв `journal()` из шага 1 закрывает его
   без кода). Юнит-тесты на оба новых пути в `tests/test_kill_cleanup.py`
   / существующем файле гейта merge.

4. `catalog.cmd_log`/`cmd_status` — видимость (AC-3, AC-11). Юнит-тесты
   в `tests/test_workspace.py`-соседних/новом файле каталога: строка
   `log` с session_id остаётся одной читаемой строкой; `status` кажет
   держателя жив/мёртв, существующий префикс не сдвинут.

5. `doctor.check_leases` — анти-race (AC-9), обогащённый FAIL (AC-10),
   рекон осиротевшего шага (AC-7/AC-8). Юнит-тесты в
   `tests/test_doctor.py`: flaky-первый-снимок не роняет FAIL,
   FAIL-строка несёт все пять полей, рекон дописывает ровно одну
   терминальную запись за N последовательных прогонов.

6. Прогон `pytest` целиком + приёмочные тесты задачи + `scripts/guard.py`
   + регенерация `docs/codebase-map.md` (правятся `orchestrator/*.py`).

## Влияние на систему

`store.journal()` — самый широко используемый примитив пакета (~70
вызывающих мест). Новый параметр — keyword-only с дефолтом `None`,
позиционная сигнатура для всех существующих вызовов не меняется —
обратной несовместимости нет. Дефолтный резолв добавляет один вызов
`os.environ.get`/`os.getppid()` на каждую запись журнала — без
подпроцессов и I/O, стоимость незаметна.

Новая колонка `steps.session_id` — аддитивная миграция (`add_column`,
существующий приём), читатели по имени колонки (`r["session_id"]`)
безопасны и для старых строк (`NULL`). Полнотекстовые/структурные
сверки существующих тестов на `steps` не переставляют и не удаляют
колонки — grep по кодовой базе (`git grep 'dict(row)\|dict(r)'` в
tests/) не нашёл мест, сравнивающих запись `steps` как готовый словарь
целиком.

`doctor.check_leases` получает `time.sleep(0.05)` на каждый кандидат в
«мёртвые» (AC-9) — не на каждый lease, только на уже подозрительные;
для типичного прогона (0-2 мёртвых lease в тестовой БД) прибавка к
времени тестов — миллисекунды.

Формат `detail` записи `«lease перехвачен»` меняется текстуально (новая
причина «pid мёртв» рядом со старой «heartbeat протух») — это НЕ
формат, который парсит `_LEASE_ALERT_RE`/`_lease_alert_live` (тот
разбирает отдельное сообщение алерта `doctor.leases`, не эту запись
журнала lease.py) — авто-ack не задет. `tests/test_lease.py` проверяет
только `"lease" in action`, не текст `detail` дословно — существующее
покрытие не ломается.

Инварианты/лимиты/CAS-переходы, которые SPEC явно запрещает трогать
(триггер протухания lease, лимитер по живым lease, `store.set_state`),
не меняются — задача добавляет только журналирование и чтение поверх
существующих решений `lease.acquire`/`set_state`, ни один из вызовов
самого решения (сравнение возраста heartbeat, CAS `expected_state`) не
правится.

Откат — точечный: пять затронутых файлов плюс новый `session.py`, без
изменений схемы, ломающих обратную совместимость (колонка аддитивная).

## Риски

- Дефолтный резолв `session_id` внутри `store.journal()` — неявный для
  читателя, который смотрит только на конкретный вызывающий модуль
  (например, `pause.py`) и не находит там ни одного упоминания
  identity. Смягчено докстрингом `journal()`, явно объясняющим дефолт
  и указывающим, что это и есть единая точка требования 1 SPEC.
- `time.sleep` внутри `check_leases` — единственный источник
  недетерминизма шага 5; интервал (0.05 с) выбран по аналогии с уже
  существующим `pause.TERMINATE_POLL_SEC`, а не произвольно.

Итерация 4 (REVIEW.md, R4-F1): вне артефактного канала на ветку попал
коммит `19a4031`, ослабляющий якорь id в залоченном приёмочном тесте
`test_ac11_status_shows_holder.py` (`^T\d{3}` -> `^\S+`) без ссылки на
ADR или запись в артефактах задачи — ревьювер разобрал два варианта
закрытия: задокументировать решение или отменить коммит. Выбран второй:
фикстурные id теста заводятся литералами `"T001"`/`"T002"`/`"T003"`
через прямой `store.insert_task`, минуя `idgen`/`cmd_new`, так что
продовый переход на ULID (T094) на этот конкретный тест не влияет —
ослабление якоря было немотивированным по существу, а не только
формально неавторизованным. Правка `19a4031` отменена точечно (только
строка `EXISTING_COLUMNS_RE`), файл возвращён к состоянию, одобренному
итерацией 3.
