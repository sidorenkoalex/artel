## Замечания

- major — `orchestrator/doctor.py:740-757` (`_lease_fail_detail`) — FAIL-строка `doctor` по мёртвому lease называет «шаг N (старт ts)» ТОЛЬКО когда в журнале есть неразрешённый «agent run started» (`if orphan is not None:` на строке 752) — сама формулировка докстринга это признаёт: «номер и время старта оборванного шага **(если есть)**» (строка 744). AC-10 требует называть держателя, роль, номер шага, время старта шага и последнее событие как одинаково обязательные пункты, без оговорки «если применимо». Воспроизведено вручную: держатель lease мёртв, но последнее событие журнала задачи уже терминальное («agent run finished», без незакрытого старта) — `check_leases` вернул `fail | T001: lease сессии sess-no-orphan мёртв (pid ... на ...), роль developer, последнее событие: agent run finished (2026-01-02 03:05:00Z)`, без единого упоминания шага или времени его старта. Это ровно тот сценарий, который делает наблюдаемость неполной для Оператора: сессия могла умереть МЕЖДУ шагами (не обязательно во время активного `agent run`) — а именно постфактум-нечитаемость журнала и есть повод всей задачи (SPEC, «Контекст»). Приёмочный тест AC-10 (`test_ac9_ac10_doctor_lease_check.py::FailLineFieldsTest`) этот путь не покрывает — фикстура всегда оставляет незакрытый «agent run started». Предложение: либо называть номер/время ПОСЛЕДНЕГО шага задачи независимо от того, закрыт ли он терминальным событием (степень «оборванности» тогда только для рекона AC-7/AC-8, не для состава FAIL-строки), либо явно сузить и обосновать в PLAN.md, почему поле опционально, и уточнить в этом же месте, что для не-«оборванных» случаев Оператор всё равно обязан звать `log` — то есть в этом случае AC-10 не выполняется полностью тем текстом, что заявлен.
