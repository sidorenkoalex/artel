# SPEC: Наблюдаемость сессий — идентичность в журнале, lease-события, рекон обрывов

## Контекст

Инцидент 02.09.2026: перехват задачи T101 другой сессией прошёл штатно
— advisory lease (T044), CAS (T050) и лимитер по живым lease
(инвариант 32) отработали корректно, — но по журналу задачи
ассистентская сессия постфактум не смогла восстановить картину
произошедшего: ошибочно диагностировала «конвейер стоит, lease мёртв»
и едва не рекомендовала снять lease живой задачи. Причина — журнал
`steps` фиксирует ЧТО произошло, но не КЕМ (какой сессией), и молчит о
жизненном цикле lease (взят/перехвачен/снят). Смежная находка
исследования watchdog T084
(`docs/research/2026-08-31-t084-watchdog-liveness.md`, «Дыра 1»):
смерть держащего lease процесса без ручного вызова `doctor` не
оставляет в журнале терминальной записи — «agent run started» повисает
без пары. `doctor.check_leases` (`orchestrator/doctor.py:685`) сегодня
ставит вердикт «мёртв» по одному снимку `os.kill(pid, 0)`, что ловит
race между pid'ами соседних шагов одной и той же сессии (шаг A
завершился и процесс исчез, шаг B ещё не стартовал) как ложный «мёртв».

## Требования

1. Единый идентификатор сессии оркестратора: существующая механика
   `session_id` lease (`ppid-N`, `orchestrator/lease.py::resolve_session_id`)
   выносится в общую функцию, доступную всем командам, не только
   мутирующим через lease. Формат — решение разработчика (допустимо
   оставить `ppid-N`, допустимо усилить), но идентификатор, попадающий
   в таблицу `leases` и в журнал `steps`, обязан быть одним и тем же
   для одного вызова.
2. Каждая запись журнала `steps` несёт идентификатор сессии, её
   записавшей. Способ хранения (отдельная колонка через миграцию либо
   структурированная часть `detail`) — решение разработчика с
   обоснованием в PLAN.md; человекочитаемость вывода `log`
   (`catalog.cmd_log`) не ухудшается.
3. Жизненный цикл lease становится событиями журнала задачи:
   - захват свободного lease — кем;
   - перехват lease мёртвого держателя — кто перенял, у кого, причина
     (pid мёртв / heartbeat протух);
   - снятие lease любым путём (обычный `release`, `kill`, успешное
     закрытие задачи, `pause --now`) — кем.
   Молчаливых изменений владения lease не остаётся ни на одном из
   перечисленных путей.
4. Рекон осиротевшего шага: команда (`run`, `auto`, `status` или
   `doctor` — выбор пути реализации остаётся за разработчиком),
   обнаружив в журнале запись «agent run started» без терминальной
   пары при мёртвом держателе lease, дописывает терминальное событие
   «шаг оборван смертью сессии `<id>`» идемпотентно — ровно одно такое
   событие на один оборванный шаг, повторные обнаружения того же
   обрыва новую запись не создают. Полноценный фоновый watchdog-процесс
   в объём задачи не входит (T084 остаётся исследованием, не
   реализацией).
5. `doctor`, проверка lease (`check_leases`): вердикт «мёртв» ставится
   только после повторной сверки живости через короткий интервал —
   анти-race между pid'ами соседних шагов одной сессии. FAIL-строка
   называет держателя (`session_id`), роль, номер шага, время старта
   шага и последнее журнальное событие задачи.
6. `status`: для задач с активным lease выводится держатель (сессия,
   жив/мёртв). Формат вывода — решение разработчика; существующие
   колонки вывода `status` не удаляются и не переставляются.
7. Существующее тестовое покрытие (invariants, lease, doctor, pause,
   cleanup, catalog) остаётся зелёным без ослабления.

## Критерии приёмки

AC-1. Есть единая функция получения `session_id`, доступная всем
командам оркестратора (не только тем, что уже проходят через
`lease.py`), и она — единственный источник идентификатора сессии для
lease и для журнала одного и того же вызова.

AC-2. Каждая новая запись таблицы `steps` (журнал задачи) несёт
идентификатор сессии, её записавшей.

AC-3. Вывод `log` (`catalog.cmd_log`) остаётся читаемым: наличие
`session_id` в записи не превращает строку вывода в нечитаемый дамп
структуры.

AC-4. Захват свободного (ранее не существовавшего) lease журналируется
отдельной записью, называющей взявшую сессию.

AC-5. Перехват lease мёртвого держателя журналируется записью,
называющей перенявшую сессию, прежнего держателя и причину перехвата
(pid мёртв или heartbeat протух).

AC-6. Снятие lease каждым из путей — обычный `release`, `kill`,
успешное закрытие задачи (`done`), `pause --now` — журналируется
записью, называющей снявшую сессию; тесты покрывают каждый путь
отдельно.

AC-7. Обнаружив в журнале запись «agent run started» без терминальной
пары при мёртвом держателе lease, рекон дописывает терминальное
событие «шаг оборван смертью сессии `<id>`».

AC-8. Повторное обнаружение того же самого оборванного шага не создаёт
вторую терминальную запись — на один оборванный шаг ровно одно
событие обрыва (идемпотентность).

AC-9. `doctor`, проверка lease: если первый снимок живости pid —
«мёртв», а повторный снимок после короткого интервала — «жив», FAIL по
этому lease не выставляется (анти-race между pid'ами соседних шагов
одной сессии).

AC-10. FAIL-строка `doctor` по мёртвому lease называет держателя
(`session_id`), роль, номер шага, время старта шага и последнее
журнальное событие задачи.

AC-11. `status` для задачи с активным lease показывает держателя
(идентификатор сессии) и его живость (жив/мёртв); существующие
колонки вывода `status` присутствуют и не переставлены.

AC-12. Полный прогон существующего набора тестов (`pytest`) зелёный —
без ослабления или удаления существующих проверок.

## Не входит

- Полноценный фоновый watchdog-процесс и пороги прогресса шага/цикла
  (T084 остаётся исследованием, не реализуется в этой задаче).
- Аутентификация операторов и разделение прав (Д1, ADR-0001).
- Изменение механики advisory lease, лимитера по живым lease и
  CAS-переходов состояния (`store.set_state`) — задача добавляет
  только наблюдаемость поверх существующего поведения, не меняет его.
- Замена формата `session_id` на что-то отличное от текущего принципа
  «идентичность разрешается один раз, используется everywhere»:
  остаться на `ppid-N` — допустимый исход, задача не требует нового
  формата.
