# ТЗ: Наблюдаемость сессий — идентичность в журнале, lease-события, рекон обрывов

Источник: инцидент 02.09.2026 (перехват T101 другой сессией).
Перехват прошёл штатно — advisory lease (T044), CAS (T050) и лимитер
по живым lease (инвариант 32) отработали, — но постфактум картина
оказалась нечитаемой: ассистентская сессия ошибочно диагностировала
«конвейер стоит, lease мёртв» и почти рекомендовала release живой
задачи. Смежный фундамент: исследование watchdog T084
(docs/research/2026-08-31-t084-watchdog-liveness.md) — «смерть сессии
не оставляет терминальной записи в журнале».

Суть: журнал фиксирует ЧТО произошло, но не КЕМ (какой сессией) и
молчит о жизненном цикле lease; doctor выносит вердикт «lease мёртв»
по одному снимку, ловя race между pid'ами соседних шагов одной
сессии. Требуется идентичность сессии и события lease в журнале,
терминальная запись для оборванных шагов и анти-race в doctor.

Требуется:
1. Единый идентификатор сессии оркестратора: существующая механика
   session_id lease (`ppid-N`, orchestrator/lease.py) выносится в
   общую функцию, доступную всем командам; формат — решение
   исполнителя (допустимо оставить `ppid-N`, допустимо усилить),
   но идентификатор в lease и в журнале обязан быть одним и тем же.
2. Каждое журнальное событие несёт идентификатор сессии, записавшей
   его. Способ (отдельная колонка через миграцию либо
   структурированная часть detail) — решение исполнителя в SPEC
   с обоснованием; читаемость `log` не ухудшается.
3. Жизненный цикл lease — события журнала задачи: захват (кем);
   перехват lease мёртвого держателя (кто перенял, у кого, причина —
   pid мёртв/протух); снятие (release/kill/done/pause --now, кем).
   Молчаливых изменений владения lease не остаётся.
4. Рекон осиротевшего шага: команда, обнаружившая в журнале
   «agent run started» без терминальной пары при мёртвом держателе
   lease, дописывает терминальное событие «шаг оборван смертью
   сессии <id>» (идемпотентно — ровно одно такое событие на
   оборванный шаг). Где именно живёт рекон (run/auto/status/doctor)
   — решение исполнителя; полноценный фоновый watchdog в задачу
   не входит (T084 остаётся исследованием).
5. doctor, проверка lease: вердикт «мёртв» ставится только после
   повторной сверки живости через короткий интервал (анти-race
   между pid'ами соседних шагов одной сессии); FAIL-строка называет
   держателя, роль и номер шага, время старта и последнее журнальное
   событие задачи.
6. `status`: для задач с активным lease — держатель (сессия,
   жив/мёртв). Формат вывода — решение исполнителя, существующие
   колонки не ломаются.
7. Тесты: session_id в событии; каждое lease-событие (захват,
   перехват, снятие каждым путём); идемпотентность рекона; анти-race
   doctor (первый снимок мёртв — повторный жив → не FAIL);
   отображение держателя в status; существующие тесты зелёные.

Зоны: orchestrator/lease.py, liveness.py, store.py (журнал/миграция),
runner.py, doctor.py, catalog.py (status/log), cleanup.py, release.py,
pause.py, tests/. ВНИМАНИЕ: store.py, doctor.py, catalog.py,
cleanup.py — зона T094 (M1): задачу НЕ запускать до мержа M1;
после мержа конфликт зон невозможен, оговорка снимается.

Не входит: фоновый watchdog-процесс и пороги прогресса (T084);
аутентификация операторов и разделение прав (Д1, ADR-0001);
изменение механики advisory lease, лимитера и CAS-переходов —
только наблюдаемость поверх.
