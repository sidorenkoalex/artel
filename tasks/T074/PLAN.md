# PLAN: pause --now — жёсткая приостановка + чекпоинт аварийного шага

## Подход

Два независимых, но соседних расширения существующей механики — оба
аддитивные, ничего в T070/T041/T059/T040 не меняют по умолчанию:

1. **`orchestrator.pause.cmd_pause_now(task_id)`** — новая функция рядом
   с `cmd_pause`/`cmd_resume` (интерфейс зафиксирован приёмочными тестами
   `tasks/T074/acceptance_tests/_sandbox.py`, «Допущения интерфейса»).
   Алгоритм:
   - `runner.step_role(t)` (отложенный импорт `runner` внутри функции —
     `runner.py` на уровне модуля импортирует `pause`, обратный импорт на
     уровне модуля был бы циклом; приём, которым уже пользуется
     `runner._cmd_run` для `doctor`) — роль текущего состояния. `None` —
     агентного шага в принципе нет (требование 6/AC-15) → печать и
     делегирование в `cmd_pause`.
   - `store.lease_row` — данные держателя (требование 2/AC-6). Нет
     строки → печать и делегирование в `cmd_pause` (AC-7, ветка 1).
   - `hostname != socket.gethostname()` → честный отказ «вне объёма»
     (AC-8) без делегирования в `cmd_pause` — SPEC называет это именно
     отказом прерывания, не деградацией всей команды; пометка паузы всё
     равно нужна отдельным шагом (требование 1 безусловно), поэтому даже
     здесь в конце вызывается `cmd_pause`.
   - `liveness._pid_alive(row["pid"])` ложно → печать и делегирование в
     `cmd_pause` (AC-7, ветка 2).
   - Иначе — полная последовательность прерывания (AC-1..AC-5, AC-10,
     AC-11): журнал «обнаружен бегущий шаг» → `os.kill` (SIGTERM, затем
     SIGKILL после короткого таймаута опроса `liveness._pid_alive`) →
     журнал «процесс агента прерван» → учёт частичной стоимости из
     ДИСКОВОГО лога шага (`agent_log.last_agent_log` +
     `spend.partial_tokens_from_log` + существующий
     `spend.charge_missing_result`, механика T040 — процесс, читающий
     лог, не тот, что его писал, поэтому используется файл, не память) →
     чекпоинт (`runner.commit_pause_now_checkpoint`, механика
     T041/T059) → `store.release_lease` по `session_id` из уже
     прочитанной строки (тот же приём, что `release.cmd_release`) →
     `cmd_pause(task_id)` (требование 1 — «обычная пометка паузы»,
     AC-2).
   - `cmd_pause_now` НЕ ждёт (`waitpid`) прерванный процесс — он не его
     потомок (требование 2 — «в другом процессе той же машины»),
     соответствует допущению `_sandbox.py`.

2. **Расширение чекпоинта аварийного завершения (требование 3, AC-9)** —
   в `orchestrator/runner.py::run_agent_once`: новая функция
   `commit_abnormal_checkpoint(conn, task_id, role, cause)`, общая
   git-обвязка `_commit_worktree_change` (та же, что уже используют
   `commit_timeout_checkpoint`/`commit_step_artifacts`, SPEC T059) под
   отдельным сообщением коммита и действием журнала, узнаваемым как
   чекпоинт (слово «чекпоинт» в обоих). Вызывается в двух точках, где
   раньше чекпоинта не было вовсе:
   - ветка `rc != 0` — до записи «agent run FAILED» (сама запись и
     возврат `"failed"` не меняются — не трогает существующий класс
     учёта провала роли/ретрая, требование 3 не про эскалацию);
   - ветка успешного `rc == 0`, но `pump.error is not None` (обрыв
     stdout-пайпа без таймаута) — ВМЕСТО безусловного
     `commit_step_artifacts` (иначе WIP закоммитился бы обычным
     «автокоммитом артефактов», неотличимым от штатного успеха — ровно
     ложноположительный сценарий, разобранный в докстринге
     `test_ac9_checkpoint_on_abnormal_step_end.py`).
   `commit_timeout_checkpoint` не трогается вовсе (таймаут остаётся
   отдельной веткой со своим сообщением, как в T041).

   Побочный эффект: `tasks/T041/acceptance_tests/
   test_checkpoint_after_timeout.py::test_ac3_return_code_failure_does_not_checkpoint`
   кодировал ПРЕЖНЕЕ правило («rc != 0 не коммитит») — SPEC T074,
   требование 3, явно заменяет его противоположным и сам называет это
   не противоречием, а плановой заменой («старый тест кодировал правило
   ДО этой задачи»). Тест переписан на новое поведение (переименован в
   `test_ac3_return_code_failure_now_checkpoints_per_t074`, ссылка на
   T074 в докстринге) — это не ослабление теста (принцип целостности
   не задет: тест как строгую проверку не снят, а приведён в
   соответствие с правилом, которое сама SPEC T074 предписывает как
   замену прежнего). Ни один другой тест на старое поведение не
   ссылается (проверено grep по репозиторию).

3. **Учёт частичной стоимости из файла** — `spend.partial_tokens_from_log`
   (новая функция в `orchestrator/spend.py`, рядом с
   `stream_usage_tokens`): читает лог-файл целиком, прогоняет каждую
   строку через уже существующий `stream_usage_tokens`, суммирует. Тот
   же разбор, что `OutputPump.catch_cost` делает по потоку — здесь
   постфактум по уже записанным на диск строкам (единственный вариант
   для `pause --now`, работающей в чужом процессе). `charge_missing_result`
   не меняется — используется как есть (её текстовые пометки «частичн»/
   «неизвестна» уже удовлетворяют журнальные требования AC-10).

## Влияние на систему

- `orchestrator/pause.py` растёт новой публичной функцией; `cmd_pause`/
  `cmd_resume`/`is_paused`/`REFUSAL_ACTION` не меняются — наблюдаемое
  поведение обычного `pause`/`resume` (T070) не задето (SPEC «Не
  входит»).
- `orchestrator/runner.py::run_agent_once` получает два новых вызова
  чекпоинта в ветках, которые раньше не коммитили ничего; сама логика
  ретрая, эскалации после `AGENT_ATTEMPTS`, учёта стоимости (T040) не
  меняется — только дописывается git-коммит перед уже существующими
  журнальными записями. Затронутые существующие тесты (`test_agent_failure.py`,
  `test_step_cost.py`, `test_analyst_role.py` и другие пользователи
  `fake_git`) не ломаются: `fake_git` отвечает `rc=0` на `git diff
  --cached --quiet`, что для `_commit_worktree_change` означает «нечего
  коммитить» — новые вызовы остаются тихим no-op на этих песочницах
  (проверено чтением `tests/sandbox.py::fake_git` и прогоном полного
  набора).
- Единственная запись существующего тестового набора, которая меняет
  СМЫСЛ (не ослабляется, а приводится в соответствие с новым явным
  требованием SPEC): `tasks/T041/acceptance_tests/
  test_checkpoint_after_timeout.py::test_ac3_...` — см. «Подход», п.2,
  и `tasks/T074/acceptance_tests/_sandbox.py`, «Допущения интерфейса».
  `fixation.check_integrity`, лимиты, гейты FSM, инварианты
  `docs/invariants.md` — не трогаются.
- `pause --now` не берёт lease задачи и не проходит лимитер
  параллельных задач (тот же довод, что уже есть в докстринге
  `orchestrator/pause.py` для `cmd_pause`/`cmd_resume` и в
  `orchestrator/release.py` для `cmd_release`): она не мутирует шаг
  своей же сессией, а действует НАД чужим держателем.
- Откат: обе новые функции (`commit_abnormal_checkpoint`,
  `commit_pause_now_checkpoint`) и `cmd_pause_now` — самостоятельные
  точки входа, не переиспользуемые старым кодом; откат — удаление трёх
  функций, двух вызовов в `run_agent_once` и возврат
  `test_ac3_...` к прежней форме.

## Риски

- Сигнал по pid из lease адресует процесс-держатель CLI-сессии
  (`run`/`auto`), а не напрямую дочерний `claude`-процесс (лизу пишет
  `os.getpid()` вызывающей сессии, `orchestrator/lease.py`, не
  меняется этой задачей). В реальной эксплуатации `SIGTERM`
  родительской CLI-сессии не гарантированно каскадно завершает её
  потомка — риск осиротевшего `claude`-процесса. Приёмочные тесты
  T074 (`_sandbox.py`, «Допущения интерфейса») сознательно проверяют
  только сам факт прерывания адресованного pid, не каскад по дереву
  процессов — тот же объём, что зафиксировал test_author. Если это
  окажется недостаточным на практике — отдельная задача (например,
  process group на старте агента), не входит в объём T074.
- Короткий опрос-эскалация SIGTERM→SIGKILL (константа в `pause.py`)
  чуть удлиняет `cmd_pause_now` на живых процессах без обработчика
  сигнала (доли секунды в тестах, т.к. процесс умирает сразу же).
