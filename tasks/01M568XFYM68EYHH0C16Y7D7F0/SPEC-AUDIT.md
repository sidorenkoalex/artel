# SPEC-AUDIT: kill задачи внешнего проекта — уборка ветки и PR в его репозитории

## ТЗ и SPEC
Требования ТЗ 1–4, критерии приёмки, зоны, перечень «только чтение», «Не
входит» и рамка $25 в SPEC отражены. ANSWER-n.md у задачи нет, решений
Оператора на гейте SPEC в брифе нет. Требований сверх ТЗ в SPEC нет:
требование 3 SPEC («ни локально, ни в `origin`») уточняет фразу ТЗ «не
удаляются» и ей не противоречит.

Расхождения:
- ТЗ п.1 «после сегодняшней уборки» в SPEC стало «помимо нынешней
  уборки» (SPEC, требования 1–2). Порядок «сначала нынешняя уборка, потом
  уборка в репозитории проекта» и порядок двух новых операций между собой
  в SPEC не заданы — подробнее в отклонении 3.
- Ссылки ТЗ `cleanup.py:178, 212` к коду устарели: сейчас

  оговорено, и AC-7 («тексты `kill`…») можно прочитать как требование

## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да, с оговоркой | Удаление ветки в `origin` не сделано или сделано не на тот ref. Оговорка: AC-1 не требует, чтобы ветка была в `origin` ДО `kill`. Тест, где ветку в bare-репозиторий не запушили, проходит на коде без новой уборки — отклонение 4. Обход `gitcmd` сырым `subprocess` AC-1 не поймает (bare-репозиторию авторизация не нужна), это ловит только случай «нет токена» в AC-5. |
| AC-2 | да | Нет вызова `gh pr close`; `--repo` не тот или не `url` записи (тогда нет `GH_TOKEN`); нет комментария или он с другим текстом. |
| AC-3 | да, с оговоркой | `push --mirror`/`--prune` или удаление `refs/artifacts/<id>`. Оговорка та же, что у AC-1: AC-3 не требует, чтобы ссылка была в `origin` до `kill` (отклонение 4). |
| AC-4 | да, с пробелом | Исключение наружу или отсутствие записи «оставлено» при сбое `gh`. Не поймает мутацию «после сбоя `gh` удаление ветки в `origin` пропущено»: AC-4 не требует, чтобы вторая операция шла независимо от первой (отклонение 3). |

## Зоны
Зоны `orchestrator/cleanup.py, tests/` покрывают требования. Закрытие PR
и удаление ветки можно сделать в `cleanup.py` готовыми `ci.gh(repo=url)`
и `gitcmd.in_repo(clone, "push", "origin", "--delete", …)`, правки
`ci.py`/`gitcmd.py` не нужны. Карта `docs/codebase-map.md` входит в
`config.COMMON_ZONES` (`orchestrator/config.py:803`). Защищённых путей
(`config.PROTECTED_PATHS`, `orchestrator/config.py:758-764`) задача не
трогает. Тест AC-6 нельзя класть в `tests/test_invariants.py`: это
защищённый путь, и SPEC его не называет. Песочница ролей не
расширяется.

Защита от зависания git-пуша (отклонение 2) тоже возможна внутри зоны
без правки `gitcmd.py`: параметры `-c http.lowSpeedLimit=… -c
http.lowSpeedTime=…` перед `push` разбирает `_hosting_project`
(`gitcmd.py:94-98`), токен при этом сохраняется. Но SPEC такого способа
не называет.

## Пути обхода гейтов
- **Ветки или ссылки в `origin` не было до `kill`.** AC-1 и AC-3 можно
  проверить на учебном проекте, где ветка задачи и `refs/artifacts/<id>`
  в bare-`origin` не опубликованы. Тогда «ветки нет» и «ссылка есть»
  выполняются без всякой уборки или ничего не доказывают (отклонение 4).
- **Остановка на первом сбое.** Новая уборка может прекратиться после
  сбоя `gh` (ранний `return`), и ветка в `origin` останется. AC-4
  проходит, потому что запись «оставлено» есть и `kill` не упал
  (отклонение 3).
- **Сырой git мимо `gitcmd`.** Удалить ветку можно прямым
  `subprocess.run(["git", "push", ...])`: с bare-репозиторием AC-1
  проходит. Если AC-5 закрыт только сценарием «пуш отказал», случай
  «нет токена» не проверен, и требование «токеном проекта» (SPEC,
  требование 2) остаётся непроверенным.
- **База `main` в учебном проекте.** AC-7 проходит на коде без правки
  `:211` (отклонение 5).

## Вердикт
**concerns.** SPEC можно вести дальше. Ниже — отклонения, которые
Оператор может снять на гейте.

1. **Деление и повторный `kill` терминальной задачи молча получают
   уборку в репозитории проекта.** SPEC («Обоснование монолита») кладёт
   новую уборку внутрь `cleanup_killed_task`. Эту функцию зовёт и
   деление на гейте SPEC (`orchestrator/fsm.py:979`): `approve` деления
   внешней задачи станет ходить в `gh pr close` и `git push --delete`, а
   в журнале появятся записи «оставлено» про PR, которого не было.
   Повторный `kill` задачи в `done` (`orchestrator/cleanup.py:428`, затем
   `:457`) удалит ветку уже влитой задачи в `origin` проекта и попробует
   закрыть смерженный PR. SPEC не говорит, входят ли эти пути в
   требование. Нужен ответ: только `kill` нетерминальной (или `killed`)
   задачи — или все вызыватели.
2. **«git не ответил» не защищён таймаутом.** Требование 4 SPEC
   перечисляет «`gh` или `git` не ответили», но `gitcmd.git` запускает
   git без таймаута (`orchestrator/gitcmd.py:186`), а `gitcmd.py` — только
   для чтения. Молчащий хостинг повесит `kill`. Ни один AC зависание не
   проверяет (AC-5 — только отказ). Нужно решение: защищать ли `kill` от
   зависания пуша (средствами зоны, например `-c http.lowSpeedTime`) и
   проверять ли это.
3. **Порядок и независимость двух операций не заданы.** SPEC (требования
   1–2, 4) не говорит, что удаление ветки выполняется и после сбоя
   закрытия PR, и наоборот, и в каком порядке они идут. На GitHub
   удаление head-ветки закрывает PR само, после чего `gh pr close` с
   комментарием «задача ликвидирована в пульте: <id>» откажет, и
   комментарий не появится. Поэтому PR надо закрывать до удаления ветки.
   AC-4 не ловит раннего выхода после сбоя `gh`.
4. **Нет предусловий AC-1 и AC-3.** Ни один из них не требует, чтобы
   ветка задачи и `refs/artifacts/<id>` были в `origin` до `kill`
   (SPEC, AC-1, AC-3). Без этого тесты проходят пустыми.
5. **AC-7 не требует базы, отличной от `main`.** Учебный проект с
   базой `main` делает AC-7 непроверяющим на `orchestrator/cleanup.py:211`.
6. **Охват AC-7 неоднозначен.** «Тексты `kill`» можно прочитать как
   включающие `orchestrator/cleanup.py:81-82` (`drop_task_dir`). Этот
   текст говорит о главной копии артели (`config.ROOT`), и
   `config.MAIN_BRANCH` там верен. Нужно уточнить: правке подлежит
   только `:211`.
7. **AC-5 связывает два сценария через «или».** Тест может закрыть
   критерий одним сценарием. Требование «через механизм токена
   `gitcmd`» (SPEC, требование 2) проверяется только сценарием «нет
   токена» (пустой слот, `orchestrator/gitcmd.py:134-138`). Нужно
   требовать оба сценария.
8. **Не задано поведение без PR.** Не сказано, звать ли `gh pr close`,
   когда `draft_mr_created = 0`, и когда проект не `forge: github`
   (`orchestrator/github_adapter.py:126-129` заводит PR только там). Если
   разработчик молча пропустит вызов по флагу, это разойдётся с ТЗ п.2
   («нет PR — запись „оставлено“»). Если позовёт `gh` для проекта не на
   GitHub, в журнале будет заведомый сбой.
