# SPEC-AUDIT: kill задачи внешнего проекта — уборка ветки и PR в его репозитории

## ТЗ и SPEC
Это второй визит аудита. Требования ТЗ 1–4, его критерии приёмки, зоны,
список «только чтение», раздел «Не входит» и рамка $25 в SPEC есть.
ANSWER-n.md у задачи нет. Решение Оператора на гейте SPEC №1 перенесено
полностью:
- (1) уборка в репозитории проекта — только на пути `kill`, который
  переводит задачу в `killed` из нетерминального состояния; это отдельная
  функция, `cleanup_killed_task` её не зовёт (SPEC, требование 1). Деление
  и повторный `kill` задачи в `done`/`killed` эту уборку не запускают
  (AC-9 а, б).
- (2) предел ожидания: для `gh` — `ci.gh` с `GH_TIMEOUT_SEC` (требование
  2), для git — `-c http.lowSpeedLimit/-c http.lowSpeedTime` без правки
  `gitcmd.py` (требование 3); проверяется AC-6 с причиной «не ответил».

Отклонения 1–8 первого аудита закрыты:
- порядок и независимость операций — требование 4 и AC-2/AC-3;
- предусловие публикации в `origin` — AC-1;
- база, отличная от `main`, — AC-8;
- охват текста только строкой `:211` — требование 8;
- сценарии «отказ пуша» и «пустой слот» разделены — AC-4 и AC-5;
- поведение без PR и вне GitHub — требование 2 и AC-9 в.

Требования, которого нет ни в ТЗ, ни в решении Оператора, в SPEC нет.
Требование 2 SPEC («независимо от признака `draft_mr_created`», «для
проекта не на GitHub `gh` не вызывается») уточняет ТЗ п.2 («нет PR —
запись „оставлено“») и ему не противоречит.

Расхождение одно. ТЗ п.1 говорит «после сегодняшней уборки», SPEC
(требование 1) — «после нынешней уборки». Ни там, ни там не сказано, что
делать, когда нынешняя уборка сама себя пропускает. Подробности —
отклонение 1.

## Факты против кода
- `cleanup_killed_task` — `orchestrator/cleanup.py:185-220`; `_cmd_kill` —
  `:394-457`. Признак перехода в `killed` — `won` (`:419-428`). Уборка
  зовётся безусловно на `:457`. Подтверждено.
- Текст «перейди на {config.MAIN_BRANCH} и повтори kill» —
  `orchestrator/cleanup.py:210-211`. Подтверждено. `drop_task_dir`
  (`:81-82`) работает с главной копией артели. Подтверждено.
- Второй вызыватель — `orchestrator/fsm.py:979`
  (`_cleanup_divided_parent`). Подтверждено. Ещё `cmd_kill` зовут
  `orchestrator/artel.py:1973` (CLI) и `orchestrator/canary.py:1390, 1410,
  1604, 1683`. Канареечные задачи идут через тот же `_cmd_kill`. Для
  артели (AC-7) они не меняются. Отдельной оговорки о канарейке во
  внешнем проекте SPEC не делает. Это не отклонение: PR канарейке не
  заводится (`orchestrator/github_adapter.py:126`), а запись «оставлено»
  допустима по требованию 6.
- `ensure_draft_mr` — `orchestrator/github_adapter.py:114`. PR заводится
  только для GitHub-проекта (`:129`) и пропускается по `draft_mr_created`
  или `is_canary` (`:126`). Подтверждено.
- `ci.gh(..., repo=…)` — `orchestrator/ci.py:39-80`. Предел —
  `config.GH_TIMEOUT_SEC`, читается в момент вызова (`:62`), поэтому тест
  может его уменьшить. `GH_TOKEN` берётся из слота записи через
  `gitcmd.project_by_url` (`:65-71`). При пустом слоте `gh` не
  запускается (`:68-69`). Подтверждено. Таймаут даёт текст «gh молчал
  дольше N с» (`:76-78`), а не «не ответил»; см. отклонение 2.
- `gitcmd.git` — `orchestrator/gitcmd.py:162-188`, без таймаута (`:185`).
  `_hosting_project` пропускает пары `-C`/`-c` перед подкомандой
  (`:97-100`). Значит, `in_repo(clone, "-c", "http.lowSpeedLimit=…", …,
  "push", "origin", "--delete", …)` сохраняет и распознание проекта по
  пути клона, и токен. Подтверждено, правка `gitcmd.py` не нужна.
- Не оговорено в SPEC, но важно для тестов. В процессе роли
  `hosting_token` отказывает всем хостинговым операциям внешнего проекта
  (`orchestrator/gitcmd.py:129-132`). Тесты AC-1/AC-2, которые прогоняет
  роль, должны это нейтрализовать: подменить `runner.in_role_environment`
  или окружение. Это деталь тестов, а не отклонение SPEC.
- `-c http.lowSpeed*` работает только на HTTP(S)-транспорте. Для `origin`
  в виде пути к bare-репозиторию или SSH-адреса предела нет. AC-6
  поэтому требует подставного HTTP-хостинга на `127.0.0.1`. Требование 9
  это разрешает («или локальным подставным хостингом»). Guard не считает
  `localhost`/`127.0.0.1` сетевым адресом (`scripts/guard.py:2855`).

## Зоны
Зоны `orchestrator/cleanup.py, tests/` покрывают требования. Нужное
вызывается из `cleanup.py` через `ci.gh(repo=url)`, `gitcmd.in_repo(...)`
и `targets.target(...)["forge"/"base"/"url"]`. Карта `docs/codebase-map.md`
входит в общие зоны. Защищённых путей (`config.PROTECTED_PATHS`) задача не
трогает. Тесты нельзя класть в `tests/test_invariants.py`. Песочница
ролей не расширяется. Правка `fsm.py` не нужна: новая функция зовётся из
`_cmd_kill`, и путь деления не меняется сам собой.

## Пути обхода гейтов
- **Уборка только при успешной локальной уборке.** Новую функцию можно
  поставить в ветку `else` (`orchestrator/cleanup.py:212-216`) или звать
  только при отсутствии пропуска. Все AC проходят: в AC-8 ветка checked
  out, но наличие уборки в репозитории проекта там не проверяется. А
  повторный `kill` по AC-9 б уборку уже не делает, так что PR и ветка в
  `origin` остаются навсегда (отклонение 1).
- **«не ответил» на любой сбой.** Если причина каждого сбоя — «не
  ответил: <stderr>», AC-6 проходит без различения таймаута и отказа.
  AC-3/AC-4 этого не запрещают (отклонение 2). Вред небольшой: причина
  в журнале вводит в заблуждение.

## Вердикт
**concerns.** SPEC можно вести дальше. Серьёзных отклонений нет: замечания
первого аудита и решение Оператора на гейте учтены. Ниже — уточнения,
которые Оператор может снять на гейте.

1. **Пропуск локальной уборки и уборка в репозитории проекта.**
   Требование 1 («после нынешней уборки») не говорит, выполняется ли
   уборка в репозитории проекта, когда `cleanup_killed_task` пропускает
   уборку. Таких случаев два: ветка задачи checked out в клоне
   (`orchestrator/cleanup.py:203-211`) и база не найдена
   (`orchestrator/cleanup.py:199-202`). Текст на `:211` предлагает
   «повтори kill», но повторный `kill` уже `killed`-задачи уборку в
   репозитории проекта по требованию 1 и AC-9 б не делает. Предлагаемое
   уточнение: уборка в репозитории проекта выполняется на пути `won`
   независимо от исхода локальной уборки. Ей нужно только имя ветки,
   локальная ветка для `push origin --delete` не требуется. В AC-8
   стоит добавить проверку, что `gh pr close` позван и ветки в `origin`
   нет.
2. **Слова «не ответил».** `ci.gh` при таймауте отдаёт «gh молчал дольше
   N с» (`orchestrator/ci.py:76-78`). git при срабатывании
   `http.lowSpeedTime` пишет своё сообщение («Operation too slow» и
   подобные). Требование 6 и AC-6 требуют слов «не ответил», но не
   говорят, как отличить таймаут от отказа, и AC-3/AC-4 не запрещают
   «не ответил» при обычном отказе. Это мелочь: точность причины в
   журнале.
3. **Стабильность AC-6.** «Не дольше суммы пределов» при уменьшенных
   пределах (секунды) на загруженной машине чувствительно к накладным
   расходам git и `gh`. Разумно разрешить тесту запас сверху (например,
   сумма пределов плюс фиксированный допуск). Иначе тест будет мигать
   на полном прогоне.
