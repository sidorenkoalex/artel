# SPEC: kill задачи внешнего проекта — уборка ветки и PR в его репозитории

## Контекст
`kill` (`orchestrator/cleanup.py:185`, `cleanup_killed_task`) убирает только
рабочую копию, каталог задачи и локальную ветку в клоне проекта. Ветка
`task/<id>-…` в `origin` внешнего проекта и черновой PR, заведённый
`github_adapter.ensure_draft_mr`, остаются — в чужом репозитории их видят
люди проекта (пример: sledproject/sled#17 у задачи
01M55SKHZ293CCAK0N7T4H7ZMR). Удаления веток в `origin` и закрытия PR в пульте
нет. Текст «перейди на … и повтори kill» называет `config.MAIN_BRANCH`
(`orchestrator/cleanup.py:211`), а не базу проекта. Решение Оператора 18.10:
документы задачи (`refs/artifacts/<id>`, в том числе RETRO) публикуются в
репозиторий проекта как сейчас, переключатель не нужен.

Решения Оператора по аудиту SPEC 18.10 (возврат со `spec_gate`): уборка в
репозитории проекта выполняется только при `kill`, переводящем задачу в
`killed` из нетерминального состояния; деление на гейте SPEC
(`orchestrator/fsm.py:979`, `_cleanup_divided_parent` →
`cleanup_killed_task`) и повторный `kill` задачи в `done`/`killed` её не
выполняют. Пуш удаления и `gh` идут с пределом ожидания средствами зоны.

## Требования
1. `kill` задачи внешнего проекта, переводящий её в `killed` из
   нетерминального состояния, после нынешней уборки выполняет уборку в
   репозитории проекта: закрывает черновой PR задачи и удаляет ветку задачи
   в `origin` проекта. Уборка в репозитории проекта — отдельная функция,
   которую зовёт только этот путь `kill`; `cleanup_killed_task` её не зовёт.
2. Закрытие PR — `gh pr close` ветки задачи через `ci.gh(..., repo=<url
   проекта>)` (токен слота проекта, предел ожидания `GH_TIMEOUT_SEC` из
   `ci.gh`) с комментарием «задача ликвидирована в пульте: <id>».
   Выполняется для проекта с `forge: github` независимо от признака
   `draft_mr_created`; для проекта не на GitHub `gh` не вызывается (PR там
   пульт не заводит, `orchestrator/github_adapter.py:126-129`).
3. Удаление ветки — git-пуш удаления в `origin` проекта через `gitcmd`
   (`gitcmd.in_repo`/`gitcmd.git`, механизм токена хостинга проекта), с
   пределом ожидания, переданным без правки `orchestrator/gitcmd.py`
   (параметры `-c http.lowSpeedLimit=… -c http.lowSpeedTime=…` вызова
   либо иной предел, если `gitcmd` позволяет передать его без своей
   правки).
4. Порядок: сначала закрытие PR, затем удаление ветки (удаление head-ветки
   на GitHub закрывает PR само, и комментарий потом не добавить). Операции
   независимы: сбой закрытия PR не отменяет попытку удаления ветки.
5. `refs/artifacts/<id>` при `kill` внешней задачи не удаляются — ни
   локально, ни в `origin` проекта.
6. Любой сбой уборки в репозитории проекта (нет PR, `gh` или `git` не
   ответили в пределах предела или вернули ошибку, пустой слот токена)
   даёт запись «оставлено: <что> — <причина>» в журнал уборки; `kill` не
   отменяется, не падает исключением, задача в `killed`. Молчащий хостинг
   даёт причину со словами «не ответил».
7. У артели поведение `kill` не меняется: PR и ветки артели — как сейчас,
   прежние вызовы. Это фиксируется тестами до правки кода.
8. Текст `kill` «перейди на … и повтори kill» (`orchestrator/cleanup.py:211`)
   для задачи внешнего проекта называет базу проекта, а не
   `config.MAIN_BRANCH`. Текст `drop_task_dir`
   (`orchestrator/cleanup.py:81-82`) относится к главной копии артели и не
   меняется.
9. Тесты детерминированы и без сети: учебный внешний проект с
   bare-репозиторием (или локальным подставным хостингом) в роли `origin` и
   подставным `gh`.

## Критерии приёмки
AC-1. Учебный внешний проект: ветка задачи `task/<id>-…` и `refs/artifacts/<id>` опубликованы в bare-`origin` ДО `kill` (тест это проверяет); после `kill` задачи из нетерминального состояния ветки задачи в `origin` нет, а `refs/artifacts/<id>` есть и в клоне, и в `origin`.
AC-2. При `kill` задачи внешнего проекта с `forge: github` подставной `gh` получает `pr close` для ветки задачи с `--repo <url записи проекта>`, комментарием «задача ликвидирована в пульте: <id>» и токеном слота проекта (`GH_TOKEN`) в окружении; вызов `gh pr close` происходит раньше пуша удаления ветки.
AC-3. Подставной `gh` отвечает ошибкой (ненулевой код, «нет PR») при `kill` внешней задачи: в журнале уборки запись «оставлено: <PR> — <причина>», ветка задачи в `origin` всё равно удалена, задача в `killed`, `kill` завершается без исключения.
AC-4. Пуш удаления ветки отказывает (например, `origin` отклоняет удаление) при `kill` внешней задачи: в журнале уборки запись «оставлено: <ветка> — <причина>», задача в `killed`, `kill` завершается без исключения.
AC-5. Слот токена проекта (`token_slot` записи) пуст при `kill` внешней задачи: ни `gh`, ни git-пуш к хостингу не запускаются (отказ механизма токена), в журнале уборки записи «оставлено» по PR и по ветке, задача в `killed`, `kill` завершается без исключения.
AC-6. Молчащий подставной хостинг (подставной `gh`, не отвечающий дольше предела `ci.gh`; `origin`, принимающий соединение и не отвечающий на пуш удаления) не задерживает `kill` дольше суммы пределов ожидания этих двух операций (тест вправе уменьшить пределы); в журнале уборки записи «оставлено: … — … не ответил…», задача в `killed`.
AC-7. `kill` задачи артели не вызывает `gh pr close` и не пушит удаление веток в `origin` — набор вызовов `gh`/`git` к хостингу тот же, что до правки (тест зафиксирован до правки кода).
AC-8. Учебный внешний проект с базой, отличной от `main` (например, `trunk`): при ветке задачи, checked out в клоне, текст отказа уборки называет «перейди на <база проекта> и повтори kill», а не `main`.
AC-9. Ни `gh pr close`, ни пуш удаления ветки не выполняются: (а) при `approve` деления на гейте SPEC задачи внешнего проекта (`_cleanup_divided_parent`); (б) при повторном `kill` задачи внешнего проекта в `done` и в `killed`; (в) при `kill` задачи внешнего проекта не на GitHub — `gh` не вызывается (удаление ветки в `origin` при этом выполняется).

## Оценка объёма и деление
Сработавшие сигналы: «число затрагиваемых модулей/файлов» (guard считает
пути, упомянутые в тексте SPEC, — большинство из них только для чтения:
`orchestrator/ci.py`, `orchestrator/github_adapter.py`, `orchestrator/gitcmd.py`,
`orchestrator/workspace.py`, `orchestrator/repo_context.py`,
`orchestrator/fsm.py`, `docs/backlog.md`) и «прогноз диффа не дан».

Прогноз диффа: 20 КиБ

**Обоснование монолита.** Зона записи — один модуль кода
(`orchestrator/cleanup.py`) и тесты к нему. Резать нечего: закрытие PR,
удаление ветки в `origin` и запись «оставлено» при сбое — одна новая
функция уборки в репозитории проекта, вызываемая из `_cmd_kill` на пути
перехода в `killed`; текст с базой проекта — правка той же функции
`cleanup_killed_task`. Отдельная часть «тесты артели до правки» без кода не
мержима как самостоятельная ценность, а часть «код» без них нарушает
требование 7. Решение утверждает Оператор на гейте SPEC.
