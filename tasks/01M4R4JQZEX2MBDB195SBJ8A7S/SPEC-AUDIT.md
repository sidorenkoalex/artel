# SPEC-AUDIT: Мандат на правку существующего теста на гейте SPEC, без эскалации разработчика

## ТЗ и SPEC
- Требования 1–5 ТЗ перенесены в SPEC почти дословно (SPEC.md:27-58).
  ANSWER-n у задачи нет. Требований сверх ТЗ нет: добавка «При отказе
  ANSWER не создаётся» (SPEC.md:32) только уточняет ТЗ.
- ТЗ п.5 «Существующие тесты не ослабляются» перенесено в «Не входит»
  (SPEC.md:120) с пояснением, что это свойство держит пульт (рубеж
  неослабления и полный прогон). Требование не потеряно, а передано
  механизму, который уже существует. Не отклонение.
- ТЗ п.3 говорит, что мандат засчитывается «на переходе `in_dev ->
  verifying` и на гейте мержа». Требование 3 SPEC это повторяет

  `in_dev -> verifying`. Перечень тестов в ТЗ п.5 тоже называет только
  in_dev, поэтому это не потеря ТЗ, но гейт мержа критерием не покрыт.
  Риск низкий: оба места зовут общий `_evaluate` →
  `_answer_mandate` (`orchestrator/advance_gates/test_integrity.py:1088`,
  `:1570`). См. отклонение 3.

## Факты против кода
Всё, что SPEC утверждает о коде, подтвердилось:
- `_cmd_answer`: `orchestrator/answer.py:286-395`. Общий отказ «answer
  доступна только для задачи в состоянии escalated» на `spec_gate`:

  `answer.py:149`; `_commit_answer` с `store.record_fixation`:
  `answer.py:258`, `:273`.
- `_answer_mandate` читает все ANSWER-n и пропускает файлы, чей

  `test_integrity.py:867-892`, `zones.py:92-115`.

  технически проходит проверку формы.

  требованием SPEC.

  `spec_gate`. Существующие тесты отказа используют `spec_writing`

## Пути обхода гейтов
1. Исполнитель может сделать ветку `spec_gate` «прошёл матрицу →
   коммит», вызвав `_matrix_problems` напрямую, без `mandate.refusals`.
   Тогда строка «Ослабление тестов разрешено: orchestrator/answer.py»
   или элемент с пробелом пройдёт: матрица названность элемента проверит,
   а его форму — нет. ANSWER с негодным элементом молча не засчитается
   гейтом (прецедент 26.09, `answer.py:107-111`). Ни один AC этого не
   ловит (отклонение 1).
2. Исполнитель может проверять запрет строк зон/зависимостей ПОСЛЕ
   `_read_checked_answer_file`. Тогда «Зависимости мержа: <негодный id>»
   отказывается сообщением `merge_after.value_refusals`, а не названным
   в AC-3. Поведение безопасно (ANSWER не создан), но тест AC-3 с таким
   файлом краснеет при любой из двух разумных реализаций. Это зона для
   эскалации «тест-навязывает-устройство» (отклонение 2).
3. Оператор может положить в файл с мандатом тестов произвольный
   свободный текст. Он дойдёт до брифов последующих ролей мимо reject и
   SPEC. ТЗ п.2 это прямо разрешает, обходом исполнителем это не
   является. Наблюдение, не отклонение.
4. Есть сигнал аудита «б) мандат в ANSWER» (`spec_audit.py:118-123`).
   Мандат, данный на `spec_gate` после вердикта аудита, текущий аудит не
   увидит, а следующий визит после reject увидит. ТЗ п.4 сознательно
   ставит мандат после аудита, а независимую проверку матрицы требует
   строка «Независимая проверка:». Не отклонение.

## Вердикт
concerns. Все отклонения Оператор может закрыть на гейте, правкой SPEC
или решением:

1. Нет критерия на проверку формы элементов мандата на `spec_gate`.
   Требование 2 (SPEC.md:33-36) называет `_read_checked_answer_file`,
   то есть `mandate.refusals` (`orchestrator/answer.py:113-118`,
   `orchestrator/advance_gates/mandate.py:147-171`). Но AC-4
   (SPEC.md:78-81) проверяет только матрицу и «Независимая проверка:».
   Мутацию «ветка `spec_gate` зовёт только `_matrix_problems`» не
   поймает ни один AC. Предлагаю дополнить AC-4: строка «Ослабление
   тестов разрешено: <элемент вне tests/**/*.py или с пробелом>» →
   отказ тем же сообщением, что в `in_dev`, ANSWER не создан.
2. Порядок отказов в AC-3 (SPEC.md:72-76) не задан. Файл со строкой
   зон/зависимостей, не прошедший заодно проверку формы или матрицы
   (`answer.py:113-119`, `mandate.py:222-225`), отказывает другим
   сообщением, если `spec_gate`-проверка стоит после
   `_read_checked_answer_file`. Нужно либо указать, что запрет строк
   зон и зависимостей на `spec_gate` срабатывает раньше проверок формы,
   либо оговорить, что тестовый файл AC-3 в остальном проходит
   проверки формы.
3. Гейт мержа из требования 3 (SPEC.md:40-43, ТЗ п.3) не покрыт AC-6
   (SPEC.md:87-91). Код рубежа общий (`test_integrity.py:1088`, `:1570`)
   и задачей не меняется, поэтому риск низкий. Оператор решает: оставить
   так или расширить AC-6 до гейта мержа.

путь» проверяем только прямым вызовом `answer.cmd_answer`. Через CLI
