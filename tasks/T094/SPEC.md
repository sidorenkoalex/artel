# SPEC: M1: артефактный контур — Б₃ + ULID

## Контекст
Многооператорная эпоха (docs/multi-operator.md, решения Оператора
31.08–01.09, роадмап §3 «Многооператорный контур») требует топологии
«Б₃»: код задачи живёт в смертной ветке целевого (`task/*`), артефакты
`tasks/<id>/` при жизни задачи — в вечной артефактной ветке ПУЛЬТА
(её заводит `cmd_new`), а при закрытии (done/killed) снапшот
артефактов + RETRO уходит в несмерживаемый `refs/artifacts/<id>`
ЦЕЛЕВОГО — жизнь там, где механика (пульт), вечность там, где
принадлежность (целевой). Сейчас все механики читают `tasks/<id>/`
из кодовой ветки целевого по единственному sha (инварианты 25–28);
аудит v6 (BL-1, Q-1, Q-2) показал, что наивное разнесение «код →
ветка, tasks/ → реф» ломает фиксацию sha, лок `acceptance_tests`,
все ветко-чтения, guard в CI и coldstart. Аудит v7 (V7-3, V7-6,
V7-Q1, V7-Q2) добавил и закрыл решениями Оператора 01.09: судьбу
нумерозависимого кода при переходе на ULID, исход отказа push
снапшота, адрес снапшота partial-целевых, порядок M1→A7. Эта задача
реализует M1 целиком по прочтению этих решений (роадмап.md §3, блок
«M1 «артефактный контур»»).

Мандат на правку ADR-0005 (пп. 1, 2, 4, 5) предоставлен этим ТЗ тем
же заходом — правка не требует отдельного MR Оператора, подтверждается
им на переходе `spec_gate` этой задачи.

## Требования
1. PLAN первым разделом несёт реестр всех мест системы, читающих
   `tasks/<id>/` из кодовой ветки задачи (не менее: хэш-фиксация
   гейтов, лок `acceptance_tests`, ветко-корректные чтения статусов
   и брифов, guard в CI, coldstart), с планом перенаправления каждого
   пункта на артефактную ветку пульта (лечение BL-1).
2. Идентификатор новой задачи — ULID; формат id знает единственная
   функция-генератор, остальной код и тесты обращаются с id как
   с непрозрачной строкой (без парсинга `T%03d`, сортировок по числу,
   предположений о длине). Старые идентификаторы формата `Tnnn`
   продолжают работать без миграции.
3. CLI-команды, принимающие id задачи, разрешают уникальный префикс
   id в полный идентификатор и честно отказывают при неоднозначном
   совпадении нескольких задач.
4. CI содержит греп-линт, отклоняющий новые парсинги формата
   идентификатора задачи вне функции-генератора.
5. Retention логов (`docs/retention.md`, `prune`) отбирает задачи по
   дате закрытия из журнала, а не по числовому номеру; для задач
   с историческим `Tnnn`-идентификатором применяется тот же датовый
   критерий.
6. Контур счётчика номеров задач (`task_counters`, пересев при
   холодном старте, doctor-сверка, ADR-0005 п.5) замораживается как
   legacy: генератором становится ULID, doctor-сверка деградирует
   в информационный статус «счётчик не движется» без блокировки;
   полное удаление контура — за пределами этой задачи.
7. `cmd_new` создаёт артефактную ветку задачи в репозитории пульта
   и делает push в origin best-effort: отказ сети не блокирует
   заведение задачи.
8. Роли коммитят содержимое `tasks/<id>/` в артефактную ветку пульта,
   а не в кодовую ветку целевого; кодовая ветка `task/*` целевого
   свободна от артефактов задачи.
9. Фиксация на переходах гейтов несёт два sha — головы кодовой ветки
   целевого и головы артефактной ветки пульта.
10. Все точки чтения из реестра (требование 1) при живой задаче
    читают `tasks/<id>/` из артефактной ветки пульта; инварианты
    25–28 остаются в силе.
11. На каждом переходе FSM оркестратор дописывает в артефактную ветку
    файл-паспорт живой задачи строкой статуса (состояние, момент
    перехода, оператор/актор) — «только для глаз», не входит
    в автоматические решения.
12. При переходе задачи в состояние `done` или `killed` (канареечный
    прогон исключён) оркестратор публикует в `refs/artifacts/<id>`
    ЦЕЛЕВОГО репозитория снапшот — артефакты задачи + RETRO с полями
    `operator`/`model`/`artel_sha` — строго до удаления кодовой
    и артефактной веток; это правило единое для целевых уровня
    `full` и `partial` (снапшот всегда в refs целевого, не
    в `.artel/projects/<target>/`).
13. Отказ push снапшота не блокирует переход `done`/`killed`: переход
    состояния совершается, но кодовая и артефактная ветки не
    удаляются, пока снапшот не подтверждён в origin целевого;
    недоставленный снапшот дожимается повторной попыткой при
    следующей команде задачи и прогоном `doctor`.
14. Локальный кэш ретро-корпуса в `.artel/` — расходный: полностью
    пересобирается fetch'ем `refs/artifacts/*` целевых, не является
    единственным хранилищем.
15. ADR-0005 правится пп. 1, 2, 4, 5 под топологию Б₃: сужение
    «чужое не публикуем» (п.1) до видимой поверхности (ветки/MR/main);
    следствие для догфуда (п.2) — артефактная ветка пульта + снапшот
    в refs целевого, не переезд в `tasks/` main; вечный адрес
    артефактов (п.4) — контент-адресация через `refs/artifacts/<id>`
    целевого вместо `<merge-sha>:tasks/<id>/`; холодный старт (п.5) —
    судьба счётчика номеров по требованию 6. Пп. 6 и 7 не трогаются
    (уже аннотированы решениями Оператора 01.09).
16. До исполнения A7 задачи целевого `self` (само-таргет пульта)
    продолжают текущий однобраншевый флоу: артефактная ветка,
    паспорт живой задачи и снапшот при закрытии к ним не применяются
    (догфуд-оговорка переходного периода).

## Критерии приёмки
AC-1. PLAN.md задачи, реализующей это SPEC, первым разделом содержит
реестр точек чтения артефактов из кодовой ветки, покрывающий как
минимум хэш-фиксацию гейтов, лок `acceptance_tests`, ветко-корректные
чтения, guard в CI и coldstart, с планом перенаправления каждого
пункта на артефактную ветку пульта.

AC-2. Функция-генератор идентификатора задачи возвращает валидный
ULID; вне тела этой функции в кодовой базе отсутствуют новые операции
парсинга/сортировки/предположений о длине формата id.

AC-3. CLI-команда, принимающая id задачи, разрешает уникальный
префикс id в полный идентификатор и отказывает с явным сообщением
о неоднозначности, если префиксу соответствует более одной задачи.

AC-4. CI-джоб отклоняет добавление нового парсинга формата
идентификатора задачи (например, регэксп на `T%03d` или аналог) вне
функции-генератора.

AC-5. Задачи с историческим идентификатором `Tnnn` проходят команды
CLI и переходы FSM без регресса после введения ULID-генератора.

AC-6. Retention логов отбирает задачи к сохранению/удалению по дате
закрытия из журнала; задачи с идентификатором `Tnnn` участвуют в этом
же датовом отборе, не в отборе «последние N по номеру».

AC-7. doctor-сверка счётчика номеров задач при отсутствии новых
пронумерованных (`Tnnn`) задач сообщает информационный статус
«счётчик не движется», не блокируя и не алертуя пульт.

AC-8. `cmd_new` создаёт артефактную ветку задачи в репозитории пульта
и делает попытку её push в origin; отказ push не прерывает заведение
задачи и не превращает его в ошибку команды.

AC-9. После завершения шага роли артефакты `tasks/<id>/` закоммичены
в артефактную ветку пульта; кодовая ветка `task/*` целевого не несёт
изменений `tasks/<id>/`.

AC-10. Запись фиксации гейта содержит оба sha — головы кодовой ветки
целевого и головы артефактной ветки пульта — на момент перехода.

AC-11. Каждая точка чтения из реестра (AC-1) у живой задачи читает
`tasks/<id>/` из артефактной ветки пульта, а не из кодовой ветки
целевого; существующие тесты инвариантов 25–28 остаются зелёными.

AC-12. На каждом переходе FSM в артефактную ветку добавляется строка
паспорта живой задачи с состоянием, моментом перехода и
оператором/актором перехода.

AC-13. При переходе задачи в `done` или `killed` (не канареечный
прогон) оркестратор публикует в `refs/artifacts/<id>` целевого
снапшот, включающий артефакты задачи и RETRO с полями `operator`,
`model`, `artel_sha`, до удаления кодовой и артефактной веток задачи.

AC-14. Снапшот при закрытии публикуется в `refs/artifacts/<id>`
целевого одинаково для целевых уровня `full` и `partial` — снапшот
не пишется в `.artel/projects/<target>/`.

AC-15. При недоступности push снапшота в origin целевого переход
`done`/`killed` всё равно совершается и не удаляет кодовую
и артефактную ветки; повторная попытка push снапшота выполняется при
следующей команде этой задачи и при прогоне `doctor`.

AC-16. Полное удаление локального кэша ретро-корпуса в `.artel/` не
теряет данных — кэш пересобирается fetch'ем `refs/artifacts/*`
целевых.

AC-17. `docs/adr/0005-data-preservation-and-memory.md` несёт правки
пп. 1, 2, 4 и 5, отражающие топологию Б₃ (артефактная ветка пульта
при жизни задачи, снапшот в `refs/artifacts/<id>` целевого при
закрытии вместо merge-адресации, сужение «чужое не публикуем» до
видимой поверхности, судьбу счётчика номеров); пп. 6 и 7 не изменены.

AC-18. До исполнения A7 задачи с целевым `self` не заводят
артефактную ветку, паспорт живой задачи и снапшот при закрытии —
проходят прежним однобраншевым флоу без регресса существующих тестов
self-таргета.

## Не входит
- Sync-транспорт M2 целиком: `pull --ff-only` на входе команд, автопуш
  шагов и гейтов, fetch refs для кэша как машинная фоновая обвязка,
  клейм мерж-окна между операторами, граница эфемерности политики
  гейтов по возрасту origin.
- A7 (артель как внешний target: stage0/stage1, защищённые пути
  с подсветкой в MR, тест «merge не меняет запущенную версию»).
- Уборочный коммит исторических `tasks/` и `docs/retro/` из дерева
  main — операторский, после M1+A7.
- Д1 (дебрендизация).
- Полное удаление контура счётчика номеров задач (`task_counters`
  и связанный код) — отдельная мелочь после M1 (роадмап §3, M1).
- Опция пошаговых метаданных RETRO (кроме `operator`/`model`/
  `artel_sha`) — не включается в снапшот этой задачей.
- Правка roadmap.md (в т.ч. чек-лист подключения B2 «право записи
  refs/artifacts») — мандат этого ТЗ ограничен ADR-0005 пп. 1/2/4/5.
- Правило «`refs/artifacts/*` удаляет только Оператор» как код-гейт —
  это политика (docs/multi-operator.md), не механизм, который эта
  задача обязана реализовывать в коде.
- Двухоператорный эксперимент, `docs/onboarding-operator.md`, метрики
  коллизий имён/конфликтов — предмет отдельной задачи после M2.
- Разводка self-таргета (артель) на двухбраншевый догфуд-флоу — по
  умолчанию ТЗ включается только в A7.
