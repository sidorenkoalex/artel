## Требуется

1. **Поля записи** (`targets.py`, раздел `policy`, проверка при загрузке): `policy.max_awaiting` (целое > 0, по умолчанию 3), `policy.awaiting_holds_zones` (bool, по умолчанию `true`). Предикат «мерж делают люди проекта» — функция `targets.py` (по образцу `push_whitelisted`); вне `targets.py` значение `merge_gate` с литералами не сравнивается.
2. **Состояние `awaiting_human`** — в `fsm.STATES` (после `merge_gate`), не окончательное, без гейта Оператора; `waiting_on` в модели доски — `human` (новое значение). Учитывается во всех местах из Факта 2 по ADR-0029 п. 2: блокировка зон — по `awaiting_holds_zones`; `auto` останавливается без алерта; надзор эпика не держит место за задачей в `awaiting_human` и не считает её ждущей Оператора; `report`/`watch`/`status`/доска показывают состояние и ссылку на MR; зависимые по `merge_after` ждут `done`; эскалация из `awaiting_human` возвращает в него же; рабочая копия хранится до `done`/`kill`; в `MAX_PARALLEL_TASKS` не считается.
3. **`approve` на `merge_gate` для записи с `target-human`** (ADR-0029 п. 1): исполняются без изменений сверка sha, ссылка документов, `no_paths`, неослабление по тексту и по исходам, лок планки, зелёный CI головы, подтяжка при сдвиге base (тем же методом `freshness`; после неё — новый CI и гейт по исходам, возврат на гейт). Подтверждённый sha обязан совпасть с головой, которая уходит в MR, иначе отказ. Не исполняются: слияние в scratch, приложения PLAN, `checks_local` по дереву мержа, карта и `guard --all`, отправка base, ожидание CI base, справочник ядра, удаление ветки и рабочей копии. Задача с приложениями PLAN — отказ «приложения не применяются в проекте с target-human — правку вносят люди проекта». Затем пульт через `forge` открывает MR ветки задачи в `base` с исполнителем `policy.mr_assignee` (при `draft_mr: true` — снимает черновик с уже открытого и назначает исполнителя), пишет ссылку на MR в БД и журнал и переводит задачу в `awaiting_human`. Любой отказ `forge` — задача остаётся на гейте с именованной причиной; MR не открыт дважды (сверка открытых MR ветки).
4. **Предел `max_awaiting`**: сверх предела задач проекта в `awaiting_human` `approve` на `merge_gate` отказывает с причиной, задача остаётся на гейте; `status` показывает «очередь: предел awaiting_human».
5. **Черновой MR через `forge`** (п. 7): для записи с `target-human` и `draft_mr: true` — черновой MR при первой отправке ветки (вход в `verifying`) через `forge.open_mr(draft=True)`, а не через `gh`; для `draft_mr: false` — MR один, на гейте мержа; в описании MR — подсветка изменённых защищённых путей. Поведение GitHub-проектов с `operator` не меняется.
6. **`max_in_flight`** (п. 12): задача проекта не отправляет ветку на входе в `verifying`, если незакрытых задач проекта с веткой на сервере (от `verifying` до `awaiting_human`) уже `max_in_flight`; задача ждёт в `in_dev` с именованной причиной в журнале и `status`.
7. **В `awaiting_human`**: `approve`, `reject`, `answer` отказывают с подсказкой «состояние ждёт людей проекта — mr-sync (шаг Б2.2)»; пульт ничего не отправляет в ветку задачи и не меняет MR.
8. **`kill` задачи с `target-human`**, ветка которой отправлена: ветку на сервере не удаляет, MR не закрывает (при любом хостинге), убирает только рабочую копию и пишет ссылку на MR в журнал.
9. **Инварианты** (приложением PLAN к `tests/test_invariants.py`): `FSM_STATES` с `awaiting_human`; новый тест «для проекта с `target-human` пульт не выполняет слияние, не отправляет `base` и ничего не отправляет в ветку задачи в `awaiting_human`» (по образцу `MergeOnlyFromMergeGateTest`); новый тест «MR открывается или снимается с черновика только для подтверждённой головы с зелёным CI».

Критерии приёмки (поддержка `target-human` в тестах включается подменой `targets.SUPPORTED_MERGE_GATES`/`SUPPORTED_FORGES` внутри теста; значения в коде не меняются — это Б2.3):
- `approve` на `merge_gate` записи `target-human` на подменённом `forge`: MR открыт с исполнителем, задача в `awaiting_human`, ссылка в журнале; шпионы не видят слияния, отправки base, удаления ветки и рабочей копии, ожидания CI base;
- sha `approve` не совпал с головой — отказ, MR не открыт; задача с приложениями PLAN — отказ с причиной; отказ `forge` — задача на гейте, повторный `approve` не открывает второй MR;
- предел `max_awaiting`: (предел+1)-я задача — отказ, задача на гейте;
- `draft_mr: true` — черновой MR на входе в `verifying`, на гейте снят черновик; `draft_mr: false` — MR только на гейте;
- `max_in_flight`: сверх предела ветка не отправлена, задача в `in_dev` с причиной;
- `awaiting_human`: `approve`/`reject`/`answer` — отказ с подсказкой; `auto` остановлен без алерта; зоны держатся при `awaiting_holds_zones: true` и освобождаются при `false`; задача по `merge_after` ждёт `done`; доска — `waiting_on: human`;
- `kill` в `awaiting_human`: ветка на сервере и MR не тронуты (шпион отправок не видит `--delete`), рабочая копия убрана, ссылка на MR в журнале;
- проекты с `operator` (артель, GitHub): существующие тесты `approve`, `kill`, `cleanup`, доски, `report`, `auto` зелёные без правки, кроме перечисленных в «Существующие тесты».
