# SPEC: R3 — `fsm.py`: подтяжка в модуль `pull.py` с явными исходами, approve как таблица переходов

## Контекст
Ревизия кодовой базы (замер 06.09, после мержа «причины конфликта
подтяжки» 01M1REVMB5) фиксирует в `orchestrator/fsm.py` две крупные
функции: `_pull_main_or_escalate` (218 строк — свежесть ветки против
origin, merge, авторазрешение конфликта карты, детализация конфликта,
WIP-чекпоинт не-картовых правок, откат/сохранение слияния, эскалация) и
`_cmd_approve` (125 строк цепочки `if state == ...`). Роадмап §3, фаза
R, пункт R3 требует разобрать обе на более мелкие явные единицы без
изменения поведения — по тому же правилу, что уже применено к R2
(`fsm_advance.py`) и R7 (`fsm_merge_gate.py`, смержена).

## Требования
1. Новый модуль `orchestrator/pull.py` вводит перечисление/датакласс
   исходов подтяжки главной ветки: `Fresh`, `Pulled(sha)`,
   `Conflict(files, note)`, `Refused(reason)`. Каждая ветка сегодняшней
   `_pull_main_or_escalate` (сверка свежести против origin, `git
   merge`, авторазрешение конфликта `docs/codebase-map.md`,
   детализация неразрешённого конфликта, WIP-чекпоинт не-картовых
   правок перед merge, материализация и прогон приёмочной планки из
   артефактной ветки) — отдельная короткая функция в `pull.py`.
2. `orchestrator/fsm._pull_main_or_escalate` остаётся точкой входа с
   прежней сигнатурой (`conn, task_id, t, state) -> str`) и прежним
   контрактом возврата (`"escalated"` / `"refused"` / `"fresh"` /
   `"pulled"`) для всех трёх вызывающих точек (`in_dev -> review`,
   `acceptance -> merge_gate`, `merge_gate -> done`): внутри —
   обращение к `pull.py` и перевод его исхода в прежние записи журнала
   (`store.journal`) и эскалации (`store.set_state(..., "escalated",
   ...)`).
3. `orchestrator/fsm._cmd_approve` заменяет цепочку `if state == ...`
   на таблицу «состояние → обработчик» (словарь): ключи — состояния
   `spec_gate`, `acceptance`, `merge_gate`, `escalated`, обработчики —
   существующие функции переходов; ветка «иначе» (состояние вне
   таблицы) сохраняет прежний текст отказа.
4. Поведение не меняется (правило фазы R): тексты записей журнала и
   эскалаций подтяжки, а также тексты отказов `_cmd_approve` (в т.ч. «в
   состоянии X нечего подтверждать», отказ approve из `escalated` без
   свежего `ANSWER-*.md`) — байт-в-байт как до правки. Существующие
   тесты (в частности `tests/test_branch_freshness_gate.py`,
   `tests/test_fsm_map_conflict_autoresolve.py`,
   `tests/test_fsm_merge_conflict_note.py`) проходят без правки
   утверждений (`assert`); подмены `mock.patch.object(fsm, "...")` в
   существующих тестах на переносимых именах продолжают работать —
   `fsm.py` реэкспортирует нужные имена из `pull.py`.
5. Новые юнит-тесты покрывают `pull.py` по каждому из четырёх исходов
   через лёгкую песочницу с поддельным git (по образцу
   `tests/test_fsm_map_conflict_autoresolve.py`) и таблицу `_cmd_approve`
   — каждое состояние из требования 3 ведёт к ожидаемому обработчику.
6. Смоук-сверка: три сценария подтяжки (свежая ветка; конфликт merge
   только по `docs/codebase-map.md`, авторазрешаемый; конфликт merge по
   двум файлам, неразрешаемый) записаны фикстурой ДО правки кода;
   после рефакторинга журнал и вывод в stdout по тем же трём сценариям
   совпадают с зафиксированной фикстурой байт-в-байт.

## Критерии приёмки
AC-1. `orchestrator/pull.py` существует и определяет тип(ы) исходов
подтяжки с четырьмя вариантами: `Fresh`, `Pulled(sha)`,
`Conflict(files, note)`, `Refused(reason)`; логика сегодняшней
`_pull_main_or_escalate` (сверка свежести, merge, авторазрешение
конфликта карты, детализация конфликта, WIP-чекпоинт, материализация и
прогон приёмочной планки) разложена в `pull.py` отдельными короткими
функциями, а не одной функцией на 200+ строк.

AC-2. `orchestrator.fsm._pull_main_or_escalate` сохраняет сигнатуру
`(conn, task_id, t, state) -> str` и прежний контракт возврата
(`"escalated"` / `"refused"` / `"fresh"` / `"pulled"`) для всех трёх
точек вызова (`in_dev -> review`, `acceptance -> merge_gate`,
`merge_gate -> done`), делегируя вычисление исхода `pull.py`.

AC-3. Тексты записей журнала (`store.journal`) и эскалаций
(`store.set_state(..., "escalated", ...)`) во всех сценариях подтяжки
(свежая ветка; авторазрешённый конфликт карты; неразрешённый конфликт;
именованный отказ «планка не найдена в источнике»; инцидент отказа
«would be overwritten by merge»; красные приёмочные тесты после
подтяжки) остаются байт-в-байт такими же, как до рефакторинга.

AC-4. `orchestrator.fsm._cmd_approve` использует словарь «состояние →
обработчик» вместо цепочки `if state == ...`; обработчики для
`spec_gate`, `acceptance`, `merge_gate`, `escalated` — существующие
функции переходов; поведение и печатаемые/журналируемые тексты (в т.ч.
«в состоянии X нечего подтверждать» и отказ approve без свежего
`ANSWER-*.md` из `escalated`) остаются байт-в-байт прежними.

AC-5. Существующие тесты, подменяющие имена через
`mock.patch.object(fsm, "...")` на именах, перенесённых в `pull.py`,
проходят без изменений — `fsm.py` реэкспортирует эти имена.

AC-6. Весь существующий набор тестов (включая
`tests/test_branch_freshness_gate.py`,
`tests/test_fsm_map_conflict_autoresolve.py`,
`tests/test_fsm_merge_conflict_note.py`) проходит без правки
утверждений (`assert`).

AC-7. Новые юнит-тесты на `pull.py` в лёгкой песочнице с поддельным git
(по образцу `tests/test_fsm_map_conflict_autoresolve.py`) покрывают все
четыре исхода: `Fresh`, `Pulled`, `Conflict`, `Refused`.

AC-8. Новый юнит-тест на таблицу `_cmd_approve` проверяет, что каждое
состояние из требования 3 (`spec_gate`, `acceptance`, `merge_gate`,
`escalated`) ведёт к ожидаемому обработчику, а состояние вне таблицы —
к прежнему тексту отказа.

AC-9. Смоук по трём сценариям подтяжки (свежая ветка; конфликт merge
только по `docs/codebase-map.md`; конфликт merge по двум файлам),
записанным фикстурой до правки кода, после рефакторинга даёт журнал и
вывод в stdout, совпадающие с фикстурой байт-в-байт.

## Оценка объёма и деление
Сработавший сигнал: бюджет (`budget_usd` 35 ≥ `config.
SPLIT_SIGNAL_BUDGET_USD` 30). Число критериев (9) и число зон (2
модуля + `tests/`) — ниже своих порогов.

Монолит принят по прецеденту роадмапа: §3 фазы R разбивает ревизию
кодовой базы на самостоятельные пункты R1–R8 заранее, каждый — по
одной крупной функции/паре функций одного файла с фиксированным
бюджетом (R2 и R6/R7 — тоже ~$35), и явно оговаривает «каждая задача
самостоятельна, фазу можно прервать после любой» — то есть дальнейшее
дробление ВНУТРИ пункта роадмапом не предполагалось. Требование 1-2
(модуль `pull.py`) и требование 3 (таблица `approve`) — два
одинаково небольших механических рефакторинга ~100-150 строк каждый
внутри одного и того же файла `fsm.py`, под одним и тем же инвариантом
фазы R «поведение байт-в-байт»; они не пересекаются по коду
(`_pull_main_or_escalate` и `_cmd_approve` — разные функции) и могли
бы мержиться отдельно, но общая фикстура байт-в-байт (смоук
требования 6) и общий набор существующих тестов подтяжки/approve,
который обе части обязаны не сломать, делают совместную проверку
дешевле раздельной: разбиение на 2 подзадачи добавило бы отдельный
цикл analyst/reviewer/developer/test_author (роадмапная оценка ~$35
уже закладывает это как одну задачу) без выигрыша в мержимости — ни
одна из двух частей не оставляет систему в нерабочем промежуточном
состоянии, но и не производит самостоятельной ценности отдельно от
цели R3 «уменьшить fsm.py».
