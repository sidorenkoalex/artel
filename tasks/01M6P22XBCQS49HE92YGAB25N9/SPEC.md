# SPEC: Раннер тестов внешнего проекта в контейнере Docker Compose

## Контекст
Доверенный внешний проект, тесты которого требуют служб (СУБД, брокер,
кэш) и запускаются в контейнере сервиса Compose-файла проекта, под
раннером `pytest-own` не исполним: голый pytest на машине не видит
служб, команда `docker compose … run` в профиле пишет отчёт по пути
машины, которого нет в контейнере, свой `HOME` отрезает Docker от его
конфигурации, подъёмом и снятием служб никто не занимается. Поправка
Оператора 05.11.2026 к ADR-0023 (коммит 77e9ca9ca, пп. 1-4) разрешает
для такого проекта вид раннера `compose` с перекрытием пульта (сети
внутренние, порты сняты) и доступ шага роли к Docker только при этом
профиле. Задача вводит этот раннер во все места прогона профиля с
отчётом (`orchestrator/acceptance.py::_report_run` и его потребители),
в окружение шага роли и в `doctor`.

Опыт 05.11 вне пульта (ТЗ, факт 6): подъём служб — 6 с, полный набор
`-n 8` — 176 с, JUnit-отчёт под смонтированным каталогом читается с
машины, `classname` — от рабочего каталога контейнера (= `workdir`
записи) без перевода, `down -v --remove-orphans` — 1 с без остатков.

## Требования

1. **Вид раннера `runner: compose`** входит в `PROFILE_RUNNERS`
   (`orchestrator/targets.py`). Поля записи: Compose-файл (путь в
   дереве), сервис тестов, файл окружения Compose и шаблон, из которого
   он копируется (пути в дереве), соответствие «каталог дерева → каталог
   в контейнере» (ровно одна пара), команда pytest в контейнере (по
   умолчанию `pytest`). `compose` проходит те же проверки и ветки, что
   `pytest-own`: `project_profile.reported`, `acceptance._own`,
   `test_integrity._own_profile`, `PROFILE_OWN_RUNNER_ONLY`,
   `machine.path`; допустим и в `test_profile`, и в `components:`.
   Проверка при загрузке: пути полей — внутри дерева, без `..`;
   `report: junit-xml` обязателен; поля `install`, `tools`,
   `checks_local` вместе с `compose` — отказ загрузки с именем поля.
2. **Перекрытие пульта** (ADR-0023, поправка 05.11, п. 2): пульт
   собирает конфигурацию проекта (`docker compose -f <файл> --env-file
   <файл> config`), в собранной конфигурации снимает `ports` у каждого
   сервиса и ставит `internal: true` каждой сети, включая неявную
   `default`, и запускает стенд одним получившимся файлом во временном
   каталоге прогона (`-f <файл пульта>`, `--project-directory` — каталог
   Compose-файла проекта). Сервис с `network_mode`, сеть с
   `external: true` или монтирование сокета Docker — отказ запуска с
   именем сервиса или сети; без перекрытия стенд не поднимается.
3. **Отчёт и пути**: отчёт — в `<каталог>/.artel-report/<прогон>.xml`
   под смонтированным каталогом дерева; pytest получает путь в
   контейнере по соответствию, пульт читает файл с машины; каталог
   отчётов убирается после прогона; `.artel-report` и файл окружения
   внесены в `info/exclude` дерева (как в `acceptance._link_deps`).
   Рабочий каталог контейнера — образ `workdir` по соответствию
   (`run -w`). Путь машины в аргументах места прогона, не лежащий под
   смонтированным каталогом, — отказ запуска с именем пути.
4. **Изоляция и жизненный цикл**: имя проекта Compose —
   `artel-<id задачи строчными>-<прогон>` (только `[a-z0-9-]`); перед
   прогоном — `up -d --wait` служб, от которых зависит сервис; прогон —
   `run --rm`; после — всегда `down -v --remove-orphans` (у сервиса без
   `image:` — с `--rmi local`), в том числе по таймауту, отказу,
   исключению и снятию группы процессов; провал `up` — отказ прогона с
   выводом Compose, не красный исход тестов.
5. **Окружение Docker**: вызов `docker compose` получает конфигурацию
   Docker пульта явно (`DOCKER_CONFIG`, контекст или `DOCKER_HOST`) без
   остального `HOME`; подстановка `${…}` Compose не получает переменных
   пульта, кроме `DOCKER_*`; окружение pytest в контейнере — из
   Compose-файла и файла окружения проекта.
6. **Шаг роли** (ADR-0023, поправка 05.11, п. 3): для задачи проекта с
   профилем `compose` `runner.role_env` дописывает каталог программы
   `docker` в `PATH` и `DOCKER_CONFIG` (контекст) пульта явно и только
   при этом профиле; `stack.ROLE_ENV_ALLOWLIST` не меняется; у прочих
   профилей и у артели окружение роли побайтно прежнее. Перечень
   разрешённых команд роли не меняется.
7. **Ключ итога**: смена Compose-файла, сервиса, перекрытия или
   соответствия каталогов меняет ключ сохранённого итога полного набора
   (`acceptance._report_suite_result_key`).
8. **Время**: предел прогона учитывает подъём и снятие служб (слагаемое
   записи или умолчание в `orchestrator/config.py`); таймаут снимает и
   стенд (требование 4).
9. **`doctor`**: строка «забытые стенды пульта» — контейнеры и сети
   Compose с именем проекта `artel-*` без живого прогона: `warn` с
   именами, `--fix` снимает (`orchestrator/doctor/orphans.py`); строка
   проверки записи `compose` — Compose-файл и сервис есть в клоне,
   `docker compose version` отвечает и не ниже 2.0 (`fail` с версией).
10. **Документация**: `docs/codebase-map.md` регенерирована.
11. **Форма тестов** (ТЗ, «Критерии приёмки», «Безопасность тестов»):
    обязательные тесты — без настоящего Docker: вызов `docker compose`
    подменён исполнителем, который записывает argv и окружение и пишет
    отчёт в смонтированный каталог дерева; допустим один необязательный
    тест с настоящим Docker, пропускаемый при его отсутствии с
    именованной причиной, — только вымышленный Compose-файл с образом из
    локального кэша, без сети, с `down -v` в `finally`. Проекты —
    вымышленные во временной песочнице; никогда — настоящий клон и
    настоящий локальный слой; в текстах тестов — ни имён, ни адресов
    реальных проектов.

## Критерии приёмки

AC-1. Запись с `runner: compose` и полными полями загружается и в `test_profile`, и в `components:`.

AC-2. Запись `compose` без `report: junit-xml`, с путём поля вне дерева, с путём, содержащим `..`, с полем `install`, `tools` или `checks_local` — отказ загрузки, текст которого называет поле.

AC-3. Прогон планки профиля `compose`: argv — `docker compose --project-name artel-<id>-<…> --project-directory <каталог Compose-файла> -f <собранный файл пульта> run --rm -w <образ workdir> <сервис> pytest <цели> --junitxml <путь в контейнере> …`; путь отчёта в контейнере соответствует файлу под смонтированным каталогом; итог — по отчёту, прочитанному с машины; в собранном файле у каждой сети, включая `default`, — `internal: true`, ни у одного сервиса нет `ports`.

AC-4. Compose-файл с `network_mode` у сервиса, сетью `external: true` или монтированием сокета Docker — отказ запуска, текст которого называет сервис или сеть; стенд не поднимается.

AC-5. Путь машины вне смонтированного каталога в аргументах места прогона — отказ запуска с именем пути.

AC-6. `down -v --remove-orphans` с тем же именем проекта вызывается при зелёном исходе, красном исходе, таймауте и исключении; провал `up` — отказ прогона с текстом вывода Compose, исход тестов не засчитан.

AC-7. Два одновременных прогона (база и голова гейта неослабления) получают разные имена проекта Compose; имя проекта — из id задачи строчными, только `[a-z0-9-]`.

AC-8. Двусторонний прогон (`two_sided`) и гейт исходов (`outcome_integrity`) для профиля `compose` идут веткой отчёта (`_report_run`): в argv нет `-p <плагин пульта>`, в окружении нет `PYTHONPATH` пульта.

AC-9. Окружение вызова `docker compose` несёт `DOCKER_CONFIG` пульта и не несёт `HOME` пульта и прочих его переменных, кроме `DOCKER_*`.

AC-10. После прогона `compose` каталог `.artel-report` под смонтированным каталогом убран; `.artel-report` и файл окружения Compose внесены в `info/exclude` дерева прогона.

AC-11. Предел времени прогона `compose` больше предела того же места без стенда на слагаемое подъёма и снятия служб (значение записи, без него — умолчание `orchestrator/config.py`); по таймауту стенд снимается (`down -v --remove-orphans`).

AC-12. Смена Compose-файла, сервиса, перекрытия или соответствия каталогов меняет ключ итога полного набора (`_report_suite_result_key`).

AC-13. Профили `pytest-own` и `pult-pytest`: argv и окружение прогонов побайтно прежние.

AC-14. Окружение шага роли (`runner.role_env`): у задачи проекта с профилем `compose` — каталог программы `docker` в `PATH` и `DOCKER_CONFIG` пульта; у `pytest-own`, `pult-pytest` и артели — побайтно прежнее; `stack.ROLE_ENV_ALLOWLIST` не изменён.

AC-15. `doctor`: контейнеры и сети с именем проекта Compose `artel-*` без живого прогона — строка `warn` с их именами (ответ `docker ps` подменён); `doctor --fix` их снимает.

AC-16. `doctor`: запись `compose`, у которой Compose-файла или сервиса нет в клоне, — `fail`; `docker compose version` не отвечает или ниже 2.0 — `fail` с версией.
