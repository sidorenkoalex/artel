# ANSWER-1: ответ Оператора

## Ответы

Основание: решения сессии при Операторе 05.11.2026 по QUESTIONS.md аналитика: вопросы 1, 2, 4, 5 — в пределах её прав (Оператор: «Да, разбирай»); вопрос 3 — решение Оператора («по вопросу 3: Г»), вариант Г предложен сессией после опыта 05.11. Рамка — ADR-0023, поправка 05.11 (77e9ca9c).

## Вопрос 1 — PATH вызова `docker compose`: вариант A с уточнением

Правило `PATH` вызова `docker` — новое, не `_own_path`: каталоги `machine.path` записи (если поле задано), затем каталог найденной программы `docker` (без разрешения ссылки), затем `_OWN_SYSTEM_PATH_DIRS` (`orchestrator/acceptance.py:156`). `PATH` вызывающего служит только для поиска `docker` и в окружение вызова не входит. Окружение вызова — ровно `PATH` по этому правилу, `DOCKER_CONFIG` и `DOCKER_HOST` (вне процесса роли — `DOCKER_CONFIG` пульта, заданный или `<дом Оператора>/.docker`, `DOCKER_HOST` — только если задан в окружении пульта, иначе контекст из конфигурации; в процессе роли — оба из окружения роли, вопрос 3), `LANG`/`LC_ALL` пульта (если заданы) и `TMPDIR`; `HOME` и прочие переменные пульта не передаются. Это отступление от буквы критерия ТЗ («не несёт прочих переменных») на `PATH`, `LANG`, `LC_ALL`, `TMPDIR`; тест окружения проверяет точный состав переменных и точный состав каталогов `PATH`.

Опыт 05.11: помощник `docker-credential-desktop` (значение `credsStore` конфигурации Docker пульта) работает без `HOME`, но только если в `PATH` есть `docker-credential-osxkeychain`; оба лежат в каталоге программы `docker` (`/usr/local/bin` на этой машине), поэтому вне шага роли скачивание и сборка с учётными данными пульта работают.

## Вопрос 2 — `command` и `env` записи `compose`: вариант A с уточнением

`command` записи `compose` — команда pytest в контейнере; при `compose` необязателен, без него — `["pytest"]`; у прочих раннеров обязательность прежняя. `env` при `compose` — отказ загрузки с именем поля, проверяемый по полю `env` раздела `description` (профиля или компонента) до сведения разделов: после сведения `machine.path` уже лежит в `env["PATH"]` (`orchestrator/targets.py:775-793`). `machine.path` при `compose` допустим и задаёт только `PATH` вызова `docker` (вопрос 1), в контейнер не идёт. В критерии загрузки — позитивный случай `compose` с `machine.path` и негативный с `env`. Отступление от буквы ТЗ, требование 1: `workdir` и `machine.path` проходят, `env` — нет.

## Вопрос 3 — Docker в шаге роли: вариант Г (решение Оператора)

Варианты A, B и C отклонены. По опыту 05.11 помощник `credsStore` без `docker-credential-osxkeychain` не работает, а с ним роль получила бы доступ к связке ключей macOS — шире ADR-0023, поправка 05.11, п. 4. Без помощника Docker отказывает даже на публичных образах (вариант C).

Вариант Г: пульт на каждый шаг роли задачи с профилем `compose` собирает каталог задачи под `.artel/` (свой на задачу: `<…>/<id задачи>/` под `.artel/` — не внутри рабочей копии задачи, не в доме роли и не в `.artel/projects/<имя>/tasks/`; сборка с атомарной заменой; путь — константой рядом с `runner.role_env`, `orchestrator/config.py` не трогается):
- `bin/` — ровно одна ссылка на найденную программу `docker`; помощников учётных данных и прочих программ нет;
- `config/config.json` — копия конфигурации Docker пульта без `credsStore`, `credHelpers`, `auths` и `currentContext`;
- `config/cli-plugins/` — ровно одна ссылка `docker-compose` на дополнение Compose, найденное пультом (`<DOCKER_CONFIG пульта>/cli-plugins/docker-compose`, затем системные каталоги дополнений Docker); других дополнений нет. Без неё `docker compose` с этим `DOCKER_CONFIG` отказывает «unknown command» (опыт проверяющего 05.11); сборка без `buildx` идёт встроенным способом с предупреждением Compose;
- адрес службы Docker — `DOCKER_HOST`, найденный пультом по текущему контексту Docker пульта.

`runner.role_env` для такой задачи дописывает в `PATH` роли каталог `bin/` и выставляет `DOCKER_CONFIG` на `config/` и `DOCKER_HOST`; `stack.ROLE_ENV_ALLOWLIST` не меняется. Вызовы `docker compose`, которые пульт делает из процесса роли (`plank-run`, `suite-run`), берут `DOCKER_CONFIG` и `DOCKER_HOST` окружения роли, а не конфигурацию пульта. Процесс роли распознаётся `runner.in_role_environment()` (`orchestrator/runner.py:1366-1383`: признак `ARTEL_ROLE` или дом роли; фоновый `suite-run` снимает `ARTEL_ROLE`, дом роли остаётся). В процессе роли без `DOCKER_CONFIG` или `DOCKER_HOST` в окружении — отказ запуска с именем переменной, без отката на конфигурацию Docker пульта. Опыт 05.11 вне пульта: `env -i` с `PATH` из каталога с одной ссылкой `docker` и системных каталогов, `DOCKER_CONFIG` на такую копию и `DOCKER_HOST` по текущему контексту — `docker version` и `docker manifest inspect` публичного образа без входа в реестр проходят. Следствие, принятое Оператором: из шага роли публичные образы скачиваются без входа в реестр; образы закрытых реестров и сборка на их основе из шага роли не работают — их заранее поднимают гейты пульта вне роли (там конфигурация пульта, вопрос 1) или Оператор. Забытые каталоги задач `compose` без живой задачи — строка `doctor` «забытые стенды пульта» (`warn`, `--fix` снимает). Критерии: у профиля `compose` в `PATH` роли — каталог `bin/` с ровно одной ссылкой `docker`; в `config/config.json` нет ключей `credsStore`, `credHelpers`, `auths`; в `config/cli-plugins/` ровно одна ссылка `docker-compose`, `docker compose version` в окружении шага роли отвечает (необязательный тест с настоящим Docker); процесс роли с удалённым `DOCKER_CONFIG` — отказ, конфигурация пульта не читается; каталог задачи `compose` без живой задачи — `warn` строки `doctor` с путём, `--fix` удаляет, каталог живой задачи не трогается; у прочих профилей и у артели окружение роли побайтно прежнее.

Отступление от буквы ТЗ, требований 5 и 6, и критериев AC-9 и AC-14 SPEC: в процессе роли вместо каталога программы `docker` — каталог `bin/`, вместо конфигурации Docker пульта — копия без учётных данных, вместо контекста — `DOCKER_HOST`. Вне процесса роли требование 5 — по букве. Относительно ADR-0023, поправка 05.11, п. 3 — сужение, не расширение.

## Вопрос 4 — фиксированные имена в Compose-файле: вариант A с уточнением

`container_name` у любого сервиса собранной конфигурации — отказ запуска с именем сервиса, без условий. Явный `name:` сети или тома — отказ с именем сети или тома, если он не равен `<имя проекта Compose прогона>` и не начинается с `<имя проекта Compose прогона>_`. Четвёртая причина отказа сверх трёх ТЗ (требование 2); Compose-файл проекта пульт не правит. Сборка конфигурации — с тем же `--project-name`, что `up`/`run`/`down`. Критерий: отказ на `container_name`, на `name:` сети, на `name:` тома и на имя вида `<имя проекта>2_db` (начинается с имени проекта без `_`).
