# QUESTIONS: Раннер тестов внешнего проекта в контейнере Docker Compose

## Вопросы

Аудит SPEC вернул первый вариант SPEC (SPEC-AUDIT.md, вердикт fail, 14
отклонений). Одиннадцать отклонений правятся в SPEC без решения Оператора:
имена полей записи, канал поиска `docker`, отметка живого стенда, дерево
сборки конфигурации, правило сокета, проверка по собранной конфигурации,
`role_env` при непрочитанном профиле, `skip` строк doctor без проекта
`compose`. Их правку следующий шаг аналитика внесёт вместе с ответом на
этот батч. Ниже только то, что упирается в букву ТЗ или в ADR-0023.
Утверждения о поведении Docker CLI и Compose проверены по документации,
опытом не проверены: программы `docker` в шаге роли нет (ТЗ, факт 4).

1. **PATH вызова `docker compose` и смысл `machine.path` у `compose` (аудит, Б4 и часть Б5).** ТЗ, требование 5 и критерий «окружение вызова `docker compose` … не несёт `HOME` пульта и прочих его переменных» запрещают вызову любые переменные пульта, кроме `DOCKER_*`, в том числе `PATH`. Но `~/.docker/config.json` пульта несёт `credsStore: desktop` (опытом в аудите), и Docker CLI ищет помощника `docker-credential-desktop` по `PATH`. Без `PATH` перестаёт работать скачивание и сборка с образами не из кэша. ТЗ, требование 1 допускает `machine.path` при `compose` («проходит те же проверки … `machine.path`»), но не говорит, чей это `PATH`.
   - A) `PATH` вызова `docker` собирает пульт так же, как у `pytest-own` (`acceptance._own_path`, `orchestrator/acceptance.py:156-186`): `machine.path` записи, каталог найденной программы `docker` и системные каталоги `_OWN_SYSTEM_PATH_DIRS` (`acceptance.py:153`). Программу `docker` пульт ищет по `PATH` вызывающего. Критерий ТЗ читается как «из переменных пульта — только `PATH` в этой сборке и `DOCKER_*`».
     - ломается: буква критерия ТЗ «не несёт прочих переменных» — `PATH` в окружении вызова будет; тест AC-9 проверяет состав `PATH`, а не его отсутствие.
     - ослабляется: ничего из сегодняшнего: у `pytest-own` то же правило `PATH` (`acceptance.py:156`); `HOME` пульта по-прежнему не передаётся.
     - цена: ничего сверх задачи; одна строка требования 5 и один критерий.
     - чьё решение: Оператор (отступление от буквы критерия ТЗ).
   - B) Буквально по ТЗ: вызов `docker` без `PATH`, `machine.path` при `compose` — отказ загрузки.
     - ломается: `up`/`run` с образом не из кэша и сборка с закрытым реестром на машине с `credsStore` — отказ Docker «executable file not found in $PATH»; противоречит ТЗ, требование 1 (`machine.path` допустим при `compose`).
     - ослабляется: ничего.
     - цена: ничего в задаче; ручная сборка образов на машине до прогона.
     - чьё решение: Оператор.
   - C) `PATH` вызова — только `machine.path` записи (без него — только каталог `docker` и системные каталоги); `PATH` вызывающего не используется даже для поиска `docker`, путь к `docker` задаёт константа `orchestrator/config.py`.
     - ломается: на машине, где `docker` лежит не по константе, раннер не находит его без правки `config.py`; подмена `docker` в тестах — через константу, а не через `PATH`.
     - ослабляется: ничего.
     - цена: ещё одна константа и строка doctor, если её проверять; объём тот же.
     - чьё решение: Оператор.
   - дефолт: A — единственный вариант, при котором работают и `credsStore`, и `machine.path` по ТЗ, требование 1; правило `PATH` уже принято для `pytest-own`.

2. **Смысл полей `command` и `env` у записи `compose` (аудит, Б5).** `command` — обязательное подполе профиля (`orchestrator/targets.py:57`, нет в `PROFILE_OPTIONAL` `:76`). ТЗ, требование 1 вводит отдельно «команду pytest в контейнере (по умолчанию `pytest`)». `env` по ТЗ при `compose` допустим (`PROFILE_OWN_RUNNER_ONLY`, `targets.py:85`), но требование 5 говорит: «окружение pytest в контейнере — из Compose-файла и файла окружения проекта», подстановка `${…}` — без переменных пульта, кроме `DOCKER_*`. Чьё окружение задаёт `env` — не сказано.
   - A) `command` записи `compose` и есть команда pytest в контейнере; при `compose` он необязателен, без него — `["pytest"]`. `env` при `compose` — отказ загрузки с именем поля: окружение pytest задают только файлы проекта.
     - ломается: буква ТЗ, требование 1 «`compose` проходит `PROFILE_OWN_RUNNER_ONLY`» — `workdir` проходит, `env` нет.
     - ослабляется: обязательность `command` в `test_profile` (`targets.py:57`) — только для `compose`; у прочих раннеров прежняя.
     - цена: ничего сверх задачи.
     - чьё решение: Оператор.
   - B) `command` — как в A. `env` при `compose` допустим и уходит в окружение вызова `docker compose`: им пользуется подстановка `${…}` Compose; в контейнер переменные попадают, только если их назвал Compose-файл.
     - ломается: ничего из ТЗ: переменные `env` — записи, не пульта; запись получает второй канал задать окружение тестов, кроме файла окружения.
     - ослабляется: ничего.
     - цена: один критерий («`env` записи виден подстановке, переменные пульта — нет»).
     - чьё решение: Оператор.
   - C) Отдельное новое поле команды в контейнере (имя задаёт SPEC), `command` у `compose` — отказ загрузки; `env` — как в A.
     - ломается: обязательный `command` у `compose` запрещён — у проверки загрузки появляется исключение «обязательное поле, кроме `compose`», запись `test_profile` и `components:` расходится по форме с прочими раннерами.
     - ослабляется: обязательность `command` (`targets.py:57`) — для `compose`.
     - цена: ещё одно поле в проверках `targets.py` и в ключе итога.
     - чьё решение: Оператор.
   - дефолт: A — без нового поля и без второго канала окружения; буквальный смысл требования 5 («окружение pytest — из файлов проекта»).

3. **Что значит «каталог программы `docker`» в `PATH` шага роли (аудит, Г3).** ADR-0023, поправка 05.11, п. 3 добавляет в окружение роли «каталог программы `docker`». На этой машине `docker` — ссылка `/usr/local/bin/docker`, рядом лежат `docker-credential-osxkeychain`, `docker-credential-desktop`, `kubectl`, `hub-tool` и другие программы; в каталоге настоящего файла (`/Applications/Docker.app/Contents/Resources/bin`) — те же помощники учётных данных (проверено аудитом). Курируемый дом роли запрещает `security find-generic-password` (`docs/reference/role-home/claude/settings.json:13`); помощник связки ключей в `PATH` роли — второй путь к ней. П. 4 ADR принимает полную власть над Docker, посторонние программы каталога он не называет.
   - A) Буквально: каталог, где найдена программа `docker` (у этой машины — `/usr/local/bin`).
     - ломается: ничего в работе раннера.
     - ослабляется: `PATH` роли «только каталоги объявленных инструментов» (`orchestrator/runner.py:1339-1340`) — роль задачи `compose` видит все программы `/usr/local/bin`, в том числе помощник связки ключей; запрет `settings.json:13` обходим.
     - цена: ничего.
     - чьё решение: Оператор (шире ADR-0023 п. 4).
   - B) Отдельный каталог пульта (под `.artel/`), который пульт собирает на шаг: ссылка на `docker` и ссылка на помощника, названного `credsStore` конфигурации Docker пульта (у этой машины — `docker-credential-desktop`), больше ничего.
     - ломается: ничего в работе раннера: команды пульта находят `docker`, Docker CLI находит своего помощника.
     - ослабляется: роль получает помощника `credsStore` — выдаёт учётные данные реестров Docker (не всю связку ключей); это часть «полной власти над Docker» п. 4.
     - цена: каталог и его пересборка на каждом шаге задачи `compose`, ещё один критерий.
     - чьё решение: Оператор.
   - C) Как B, но только ссылка на `docker`, без помощника.
     - ломается: из шага роли (`plank-run`, `suite-run`) не работает скачивание и сборка образа при `credsStore`: Docker CLI не находит помощника. Гейты пульта вне шага роли работают.
     - ослабляется: ничего сверх п. 4.
     - цена: как B; образы до шага роли поднимает Оператор или гейт.
     - чьё решение: Оператор.
   - дефолт: B — в `PATH` роли ровно то, без чего Docker пульта работает; посторонних программ каталога нет.

4. **Фиксированные имена в Compose-файле проекта (аудит, Б2, Е2).** ТЗ, требование 4 ставит изоляцию прогонов на имя проекта Compose `artel-<id>-<прогон>`. Сборку конфигурации SPEC поправит сам: `config` получит то же `--project-name`, тогда имена неявных сетей и томов станут `<имя проекта>_<имя>` (по документации Compose, опытом не проверено). Но Compose-файл проекта может задать имя явно: `container_name` у сервиса, `name:` у сети или тома. Тогда два прогона (планка роли и гейт, две задачи одного проекта) делят контейнер, сеть или том БД, а `down -v` одного снимает том другого. ТЗ называет три причины отказа запуска (`network_mode`, `external: true`, сокет); этой среди них нет.
   - A) Отказ запуска с именем сервиса, сети или тома, если в собранной конфигурации есть `container_name` или `name:` сети/тома, не начинающийся с имени проекта прогона.
     - ломается: проект с `container_name` или явным `name:` не запускается под `compose`, пока его Compose-файл не поправят.
     - ослабляется: ничего.
     - цена: один критерий и три случая отказа в тесте.
     - чьё решение: Оператор (четвёртая причина отказа сверх ТЗ).
   - B) Перекрытие пульта снимает `container_name` и заменяет явный `name:` сети/тома на `<имя проекта>_<ключ>`.
     - ломается: код проекта, который обращается к контейнеру по `container_name`, а не по имени сервиса, на стенде не находит его (красный тест, а не отказ запуска).
     - ослабляется: ничего.
     - цена: как A.
     - чьё решение: Оператор (перекрытие шире ADR-0023 п. 2: там только сети и порты).
   - C) Ничего не делать: изоляция только по имени проекта, как в ТЗ.
     - ломается: у проекта с явными именами — общие контейнер, сеть или том между одновременными прогонами; двусторонний прогон и гейт исходов судят по БД соседнего прогона.
     - ослабляется: изоляция стенда «под своим именем проекта» (ADR-0023, поправка 05.11, п. 1) — только для таких проектов.
     - цена: ничего.
     - чьё решение: Оператор.
   - дефолт: A — отказ не трогает Compose-файл проекта и укладывается в форму трёх отказов ТЗ, требование 2.

5. **Нижний порог версии `docker compose` в doctor (аудит, Б3).** ТЗ, требование 9: «не ниже 2.0». Команда подъёма стенда по ТЗ, требование 4 — `up -d --wait`; флаг `--wait` появился в Compose v2.1.1 (по журналу изменений Compose, опытом не проверено). На 2.0.x doctor скажет `ok`, а `up` откажет.
   - A) Порог 2.1.1.
     - ломается: ничего; doctor честно отказывает версии, на которой стенд не поднимется.
     - ослабляется: ничего.
     - цена: ничего.
     - чьё решение: Оператор (число из ТЗ).
   - B) Порог 2.0, как в ТЗ.
     - ломается: на 2.0.x — `ok` в doctor и отказ прогона «провал `up`» на каждом месте.
     - ослабляется: ничего.
     - цена: ничего.
     - чьё решение: Оператор.
   - дефолт: A — порог по версии, которая исполняет команду требования 4.
