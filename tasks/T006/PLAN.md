# PLAN: Код возврата агента как провал шага

## Подход

`cmd_run` сейчас берёт `rc` у процесса агента и пишет его в журнал
одинаково при любом значении (orchestrator/artel.py:501-503): и rc=0,
и rc=1 после 401 дают «agent run finished» плюс подсказку `advance`.
Никакого решения по rc не принимается — его и добавляем.

Ключевые решения:

- **Один запуск агента выносится в `run_agent_once`, цикл попыток
  остаётся в `cmd_run`.** Ретрай — это повтор всего запуска целиком
  (новый лог, новая запись в журнале), поэтому граница функции проходит
  ровно по «запустили процесс — дождались — оценили rc». `cmd_run` после
  этого читается как политика: сколько попыток, какая пауза, что делать
  после исчерпания.
- **Исход попытки — строка, а не rc.** `run_agent_once` возвращает
  `("ok" | "failed" | "timeout" | "skipped", пояснение)`. rc наружу не
  нужен: решение по нему принято внутри, а различать нужно четыре
  ситуации, из которых ретраится только одна. Возвращать rc и разбирать
  его повторно в `cmd_run` значило бы принимать одно решение дважды.
- **Ретраятся только провалы по rc.** Таймаут шага (30 мин) не
  ретраится: SPEC требует реакции на код возврата, а три подряд
  таймаута — это полтора часа до возврата управления Оператору, то есть
  ухудшение против нынешнего поведения. Отсутствие CLI (`FileNotFoundError`)
  не ретраится по той же причине, по которой оно и сегодня не ошибка
  шага: повторный запуск ничего не изменит, промпт уже напечатан для
  ручного прогона. Обе ветки, как и раньше, возвращают управление
  Оператору без подсказки `advance`.
- **Пауза между попытками — экспоненциальный бэкофф от
  `RETRY_BACKOFF_SEC`** (5 с, затем 10 с), как в docs/design.md §6
  «транзиентные — ретраи с экспоненциальным бэкоффом». Десятки секунд —
  верх диапазона, разрешённого SPEC; больше на шаге в 30 минут смысла
  не имеет, а Оператора в терминале держит зря.
- **Счётчик попыток пишется в журнал каждой записью прогона**
  («попытка N/3» в `agent run started`, `FAILED`, `finished`, `TIMEOUT`),
  а не отдельной строкой в конце: журнал читают как ленту `log <id>`, и
  номер попытки нужен рядом с событием, а не в сводке.
- **Хвост лога берётся из файла прогона** (`log_tail`), а не копится в
  памяти: лог уже пишется по ходу шага (T005), причина падения — в его
  последних строках (401, трейсбек CLI). Ограничение по строкам и по
  символам одновременно: одна строка трейсбека может быть длиной в
  экран, а `detail` в журнале читается глазами.
- **Каждая попытка получает свой файл лога** — это уже свойство
  `new_agent_log` (инкремент N), менять ничего не нужно: разбор провала
  требует логов всех трёх попыток, а не только последней.
- **Эскалация — через `set_state(..., "escalated", "fsm", причина)`.**
  Отдельного счётчика в БД ретраи не заводят: они живут внутри одного
  вызова `cmd_run`, между вызовами их состояние никому не нужно.
  `review_iters` при этом не трогается — требование SPEC «ретраи не
  считаются итерациями ревью» выполняется тем, что счётчик итераций
  двигает только `cmd_advance` по вердикту REVIEW.md.
- **Точка возврата из `escalated` — только для эскалации по провалу
  агента** (итерация 2, по замечанию ревью). `cmd_approve` возвращал
  эскалированную задачу в `in_dev` откуда бы она ни ушла, и упавшее
  ревью уезжало в разработку: следующий `run` поднимал разработчика на
  ветке, где всё сделано. `cmd_run` перед эскалацией пишет состояние
  своего шага в новую колонку `escalated_from`, `cmd_approve` возвращает
  туда и колонку гасит. Эскалации по вердикту ревьювера и по исчерпанным
  лимитам её не пишут и ведут себя как раньше — у каждой из них своя
  правильная точка возврата (после трёх кругов ревью работать снова
  разработчику, а не ревьюверу), и решать это разом — задача не про код
  возврата агента.

Архитектурно значимого решения нет — ADR не требуется.

## Шаги

1. `orchestrator/artel.py`: константы `AGENT_RETRIES`, `AGENT_ATTEMPTS`,
   `RETRY_BACKOFF_SEC`, `LOG_TAIL_LINES`, `LOG_TAIL_CHARS`; функция
   `log_tail(path)` (последние строки лога прогона); вынос одного
   запуска в `run_agent_once` с записью `agent run FAILED` (rc, номер
   попытки, хвост лога) при rc != 0 и подсказкой `advance` только при
   rc=0; цикл попыток с бэкоффом в `cmd_run` и перевод задачи в
   `escalated` после исчерпания ретраев.
2. `tests/test_agent_failure.py`: юнит-тесты на `log_tail` и на `cmd_run`
   с подменённым процессом агента — успех, провал с успехом со второй
   попытки, эскалация после трёх провалов, неизменность `review_iters`,
   отсутствие подсказки `advance` при провале, отсутствие ретраев у
   таймаута и у ненайденного CLI. Правка `tests/test_agent_log.py:403` —
   тест сверял `detail` записи TIMEOUT дословно, а в ней теперь есть
   номер попытки (требование 2).

3. По замечаниям ревью (итерация 1): колонка `escalated_from` (+ миграция
   старой БД) и возврат `approve` в упавший шаг вместо `in_dev` — major;
   «(без ретрая)» в записи `agent run TIMEOUT`, хвост лога только в
   журнале (в консоли — rc, попытка, путь), тест хвоста различает
   попытки — minor. Тесты: возврат в `in_dev` и в `review`, неизменность
   возврата у прочих эскалаций, миграция старой БД, отсутствие дубля
   хвоста в консоли.

Оба шага — один MR: тесты проверяют поведение, которого без шага 1 нет.

## Покрытие требований

| Требование | Шаг |
|---|---|
| 1 (rc != 0 → `agent run FAILED` с rc и хвостом лога) | 1 |
| 2 (до 2 ретраев с бэкоффом, счётчик попыток в журнале) | 1 |
| 3 (после ретраев — `escalated` с причиной, виден в `status`) | 1, 3 |
| 4 (rc=0 — как раньше; `advance` печатается только при успехе) | 1 |
| 5 (юнит-тесты: успех, ретрай с успехом, эскалация) | 2, 3 |

## Риски

- Ретраим всё подряд, включая содержательные ошибки (сломанный промпт,
  падение агента на первой же секунде) — три бесполезных прогона вместо
  одного. Так решил SPEC («Не входит»: различение транзиентных и
  содержательных по тексту лога); цена ограничена бэкоффом в секунды и
  тем, что каждая попытка пишет отдельный лог.
- Провал агента посреди шага может оставить незакоммиченные правки в
  рабочем дереве, и следующая попытка стартует не с чистого места
  (docs/design.md §6 «шаг перезапускается с чистого контейнера» — в
  Фазе 0 контейнеров нет). Задача этого не меняет; уборка рабочего
  дерева между попытками — отдельное решение уровня оркестратора.
- rc != 0 у `claude` может означать и отказ агента от работы по
  содержательной причине, а не системный сбой. Тогда задача уедет в
  `escalated` — то есть к Оператору, что и есть верное поведение при
  неотличимых ошибках: молча предлагать `advance`, как сегодня, хуже.
- Точку возврата из `escalated` теперь пишет только `cmd_run`, поэтому
  правило «куда возвращает `approve`» стало зависеть от источника
  эскалации. Пока источников с точкой возврата один, это читается по
  коду; когда её захотят и вердикту ревьювера, и лимитам — правило надо
  будет собрать в одном месте, а не дописывать третью ветку.
- Хвост лога попадает в журнал и в вывод `status`/`log` как есть. Это
  вывод агента, то есть данные: если в нём окажется секрет, он окажется
  и в БД `.artel/state.db`. `.artel/` вне git, но чистка журнала от
  секретов — отдельная задача, здесь она не решается.
