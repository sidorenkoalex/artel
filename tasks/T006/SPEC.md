# SPEC: Код возврата агента как провал шага

## Контекст
При прогоне T003 агент упал с 401 (истёкший OAuth CLI), rc=1 — но
`cmd_run` записал в журнал «agent run finished, rc=1» и предложил
`advance`, как будто шаг успешен. Системные ошибки (авторизация, сеть,
падение CLI) неотличимы от нормального завершения. По дизайну
(docs/design.md §6 «Устойчивость») транзиентные ошибки ретраятся
с бэкоффом и не считаются итерацией, системные — эскалируются.

## Требования
1. rc != 0 у процесса агента трактуется как провал шага: в журнал
   пишется `agent run FAILED` с rc и хвостом лога (последние строки
   из .artel/logs/<файл> — там причина, например 401).
2. Провал шага ретраится автоматически с бэкоффом: до 2 повторных
   запусков (пауза между ними — секунды/десятки секунд), счётчик
   попыток пишется в журнал. Ретраи не считаются итерациями ревью.
3. После исчерпания ретраев задача переводится в escalated с внятной
   причиной (rc, хвост лога) — Оператор видит её в status как
   «ЖДЁТ ОПЕРАТОРА».
4. Успешный запуск (rc=0) ведёт себя как сейчас; подсказка
   «дальше: advance» печатается только при успехе.
5. Покрыто юнит-тестами в tests/ (без реального claude CLI — через
   подмену запускаемой команды или функции): успех, провал с ретраями
   и успехом со второй попытки, эскалация после исчерпания ретраев.

## Критерии приёмки
1. Запуск `run` с заведомо падающей командой агента (в тесте) даёт:
   2 ретрая, запись FAILED с rc в журнале, состояние escalated.
2. Успешный со второй попытки запуск не эскалирует и не ломает FSM.
3. При rc=0 поведение и вывод не изменились.
4. `python3 -m unittest discover -s tests` зелёный, guard и CI зелёные.

## Не входит
- Различение транзиентных и содержательных ошибок по содержимому лога
  (эвристики по тексту 401/timeout — не сейчас, ретраем всё).
- Парсинг стоимости из вывода агента.
- Очистка каталога задачи при kill (отдельная задача).
