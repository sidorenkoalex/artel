# PLAN: Полный прогон тестов из шага роли — команда `suite-run`

## Подход

Новый модуль `orchestrator/suite_run.py` — команда `suite-run <id> [--wait
<минуты> | --failed]`, запись в таблице диспетчера `orchestrator/artel.py`
и в белом списке `_ROLE_ALLOWED_COMMANDS`.

- **Запуск** (`cmd_suite_run`): профиль тестов проекта читается
  `repo_context.profile_of`; нет профиля, профиль не прочитан или его
  команда не запуск pytest (`_is_pytest`: исполняемый `pytest`/`py.test`
  либо `-m pytest`) — отказ ненулевым кодом без прогона. Затем: идёт
  прогон этой задачи (`run.json`: pid жив, отчёта этого номера нет) —
  печать его номера и лога, второй не заводится; замок машины держит
  живой процесс — отказ с id задачи и pid держателя. Иначе — лог
  `agent_log.new_agent_log(<id>, "suiterun")` (номер прогона = номер
  лога), отвязанный процесс `python -c ... suite_run.background(...)`
  (`start_new_session`, stdin/stdout не наследуются, cwd = `config.ROOT`,
  окружение без `ARTEL_ROLE`) и немедленный возврат с номером, pid и
  путём к логу.
- **Замок** берёт сама команда, атомарно (`O_EXCL` на
  `.artel/logs/suite-run/lock.json`; замок мёртвого pid снимается; пустой
  только что созданный файл считается занятым), до заведения лога и
  запуска: занятый — немедленный отказ с id задачи и pid держателя. После
  запуска замок переписан на pid фонового процесса (`_hand_lock`), сбой
  запуска снимает замок (итерация 2, R1-F2).
- **Фоновый процесс** (`background`): принимает переданный замок своей
  задачи и номера прогона (`_adopt_lock`; без него берёт сам), гонит ветку через
  `acceptance.run_full_suite(workspace.path, command=<профиль>,
  targets=("tests",) | <перечень упавших>, extra=("-vv",), log=<лог>)`,
  пишет перечень упавших задачи (`failed.json`), считает базу, дописывает
  полные перечни упавших в конец лога, пишет отчёт (`result.json`).
  Исключение пульта — тоже отчёт с путём к логу; замок снимается в
  `finally`.
- **Узел прогона** `acceptance.run_full_suite` получает необязательные
  параметры `command`, `targets`, `extra`, `log`. Без них (все гейты)
  команда и исход прежние байт-в-байт (тест `GateArgvTest`). С `log`
  вывод идёт прямо в файл (`PYTHONUNBUFFERED=1`, ход прогона читается
  по ходу), pytest — в своей группе процессов, на пределе
  `config.FULL_SUITE_TIMEOUT_SEC` убивается вся группа вместе с рабочими
  xdist; исход таймаута — тем же префиксом `_full_suite_timeout_note()`.
- **Итог базы**: `acceptance.full_suite` после прогона гейта сохраняет
  перечень упавших (`.artel/logs/fullsuite-results/<sha>.json`) только
  для завершённого прогона (зелёный/красный с итоговой строкой pytest) и
  только для чистого дерева (`clean_tree_sha`: HEAD и пустой `git status`
  вне `tasks/`); сбой git — без сохранения, исход гейта не меняется.
  `suite-run` берёт sha базы `gitcmd.diff_base(ветка, repo=клон)`;
  сохранённого итога нет — прогон базы тем же фоновым процессом после
  ветки во временной рабочей копии клона (`git worktree add --detach` в
  системном временном каталоге; `worktree remove --force` + `rmtree` +
  `prune` в `finally`). Завершённый прогон базы сохраняется тем же
  `save_failures`, незавершённый — «база не посчитана». `--failed` базу
  не гонит.
- **Разбор и отчёт**: упавшие с сообщением — только из блока «short test
  summary info» (`acceptance.short_summary_block`: от последнего заголовка
  блока до следующего разделителя `=== … ===`), строки хода — только до
  первой секции отчёта pytest (`FAILURES` и далее): захваченный лог и
  stdout упавших тестов (`ERROR    m:файл:строка …`, `FAILED …`) не
  становятся «упавшими» (итерация 2, R1-F1). `-vv` даёт строку на каждый выполненный тест (ход
  прогона для «ещё идёт» и числа успевшей части при обрыве) и сообщение
  упавшего в «short test summary info» без обрезки по ширине терминала.
  Признак группы — первая строка сообщения pytest («ValueError: …»),
  обрезка до `SUITE_RUN_MAX_LINE_CHARS`, не больше `SUITE_RUN_MAX_GROUPS`
  групп и хвост «и ещё N групп, M тестов», до трёх примеров на группу.
  «Падают и на базе» — числом, перечень — в конце лога.
- **Ожидание** `--wait <минуты>` (0…`SUITE_RUN_MAX_WAIT_MIN`, иначе отказ
  без ожидания): отчёт последнего прогона, «ещё идёт» с ходом (секунды и
  число выполненных тестов по логам ветки и базы) и кодом 1, «оборван»,
  если процесса нет и отчёта он не оставил; без прогонов — отказ с
  подсказкой `suite-run <id>`.
- Миссия разработчика (`role_prompt.suite_run_note`) называет
  `python3 <config.ROOT>/orchestrator/artel.py suite-run <id>`, формы
  `--wait` и `--failed`.

Бюджет SPEC ($85) не пересматривается.

## Влияние на систему

- Гейты приёмки и мержа: команда прогона и исход прежние (параметры
  `run_full_suite` по умолчанию дают прежний argv — `GateArgvTest`);
  добавлено только сохранение перечня упавших после завершённого прогона,
  без исключений наружу (сбой git/записи — без сохранения). Предел
  `FULL_SUITE_TIMEOUT_SEC` не тронут.
- Сторож `conftest.py` не меняется: фоновый прогон идёт без `ARTEL_ROLE`,
  это прогон пульта.
- Белый список роли расширен одной командой, которая пишет только в
  `.artel/logs/` (лог, `suite-run/<id>/`, `suite-run/lock.json`,
  `fullsuite-results/`); БД, lease, журнал шагов не трогаются (AC-23).
  Временная рабочая копия базы — в системном временном каталоге,
  снимается с учёта клона на любом исходе.
- Существующие тесты не менялись.
- Откат — revert коммитов задачи; файлы `.artel/logs/suite-run/` и
  `.artel/logs/fullsuite-results/` после отката никем не читаются.

## Риски

- Нагрузка: прогон `-n FULL_SUITE_WORKERS` параллельно гейту пульта
  удваивает нагрузку машины; замок держит не больше одного прогона
  `suite-run`, но гейты он не ждёт (SPEC этого не требует).
- Итог базы сохраняется по sha коммита: у внешнего проекта гейт гонит
  набор командой пульта, `suite-run` — командой профиля; итог гейта всё
  равно ложится по sha дерева, как требует требование 7.
- Повторное использование pid после смерти фонового процесса может
  ложно показать прогон «идущим» до следующей проверки — окно мало,
  `--wait` тогда завершится «ещё идёт», а не ложным отчётом.

## Предложения системе

- `docs/codebase-map.md` в брифе роли отстал от кода: в проекции нет
  `orchestrator/project_profile.py`, хотя `acceptance.py` уже ссылается на
  него (`built_at_sha` карты брифа старше подтяжки main) — класс «бриф
  собран по карте до подтяжки main в шаге».
- `orchestrator/acceptance.py::failed_test_lines` (выжимка журнала гейтов,
  код до этой задачи) — тот же класс, что R1-F1: `FAILED`/`ERROR` с
  начала строки ищутся по всему выводу, и захваченный лог упавшего теста
  попадает в выжимку как «упавший». Перевести на `short_summary_block` —
  смена выжимки журнала гейтов, вне зоны этой задачи; отдельная задача.
- `skills/coding-standards.md` предписывает проверять сторожей временной
  мутацией, но команды для этого нет: правка кода руками и её откат — тот
  же класс обхода, что был у планки до `plank-run`.
