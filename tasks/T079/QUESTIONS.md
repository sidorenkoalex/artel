# QUESTIONS: B1b: GitHub-адаптер, Draft-MR и состояние verifying

## Вопросы

1. **Механика самого merge: локальный `git merge` (как сейчас) или через
   GitHub-адаптер (API)?** ТЗ п.1 называет `merge` одной из операций
   GitHub-адаптера — наравне с веткой задачи, Draft-MR и чтением статусов
   CI. Сегодня merge на гейте `merge_gate` — целиком локальный git:
   `orchestrator/fsm.py::_cmd_approve_merge_gate` делает `git checkout
   main` → `git pull --ff-only` → `git merge --no-ff` → генерация
   карты/RETRO → `git push`, с конфликт-логикой T052 (`git merge
   --abort`, различение содержательного конфликта / конфликта в
   защищённых путях / инфраструктурного отказа) и мьютексом окна мержа
   T053. ADR-0003 §6 описывает интерфейс фордж-адаптера с операцией
   `merge` и формулирует «Merge в целевой — только оркестратор через
   адаптер»; аудит 23.08 (v4-decisions, L460) фиксирует «A7 + B1b меняют
   способ merge (адаптер вместо локального git merge)». Два способа
   понять объём этой задачи существенно расходятся в размере и в том,
   трогает ли она защищённую конфликт-механику T052/T053 (принцип
   целостности, ADR-0002 — такое трогать без явного решения Оператора
   нельзя):
   — варианты:
   A) **Заменить** — `approve` из `merge_gate` мержит через
      GitHub-адаптер (API, например `gh pr merge`) вместо локального
      `git merge --no-ff`; конфликт-логика T052 (три исхода: конфликт /
      конфликт в защищённых путях / инфраструктурный отказ) и мьютекс
      T053 переосмысляются под API-семантику (`mergeable`/`conflict`
      вместо кода возврата `git merge`) — это отдельная, более крупная
      переделка существующих тестов T052/T053.
   B) **Не заменять** — локальный `git merge --no-ff` + push остаётся
      ровно как сейчас (T052/T053 не трогаются); адаптерная операция
      `merge` в этой задаче реализуется как побочный эффект локального
      мержа — Draft-MR переводится в ready на входе в `merge_gate`
      (п.2 ниже) и закрывается/подтверждается смерженным после того,
      как локальный push уже доставил коммит в `main` (через API-вызов
      close/merge-mark или через штатное автоопределение GitHub по
      коммиту в истории `main`).
   — дефолт при молчании: **B** — бюджет ТЗ ($25+15) и формулировки
     ТЗ (п.5 упоминает только «связку возврата» T052, не переделку
     самой конфликт-механики) не читаются как мандат на переписывание
     T052/T053; A требует отдельного решения Оператора по ADR-0002.

2. **Поведение `verifying` при красном/упавшем CI: авто-возврат в
   `in_dev`, только ручной `reject`, или вообще без возврата (кроме
   исчерпания потолка ожидания из п.4 ТЗ)?** ТЗ п.5 явно ссылается на
   незакрытый остаток T052: SPEC T052 (раздел «Не входит») оставил
   «verifying/await-ci как отдельное состояние (B1b) — связка остаётся
   за B1b», не задав самого поведения. Symmetричный прецедент в
   `merge_gate` — красный CI НЕ выталкивает автоматически (инвариант
   19, SPEC T052 требование 3/AC-5): `approve` просто отказывает, и
   решение (ждать/перезапускать CI/`reject` с причиной) остаётся за
   Оператором. Нужно решить, действует ли та же симметрия для
   `verifying`, где Оператора в моменте может не быть (ожидание CI —
   потенциально автоматическая фаза без синхронного участия
   Оператора):
   — варианты:
   A) **Авто-возврат** — если проверки CI по ветке приходят красными
      (не «идут», а завершились неуспехом), задача автоматически
      переходит `verifying -> in_dev` с диагностикой (какая проверка
      упала) в журнале — тем же приёмом, что автовозврат по конфликту
      мержа в T052.
   B) **Только ручной `reject`** — `verifying` сам не возвращает,
      только ждёт (с потолком из п.4 ТЗ); Оператор (или будущий
      автоматический наблюдатель) видит красный CI и делает `reject
      <id> "<причина>"`, расширяя область действия команды с
      `merge_gate` (T052) также на `verifying`.
   C) **Не возвращает вовсе** — `verifying` только ждёт до потолка
      ожидания; и «красный CI», и «нет проверок вовсе» после потолка —
      это эскалация (`escalated`), а не возврат в `in_dev`.
   — дефолт при молчании: **B** — прямая симметрия с уже принятым для
     `merge_gate` инвариантом 19 («красный CI не выталкивает
     автоматически», SPEC T052 требование 3) и минимальное расширение
     существующей команды `reject`, а не новая автоматика.

## Контекст

Прочитан TZ.md, роадмап §3 (фаза B, B1a/B1b/A7), ADR-0003 (§§4–13,
особенно §6 «Forge-адаптер» и §7 «Исполнитель гейта мержа»),
docs/design.md (диаграмма FSM и список запланированных расширений),
tasks/T052/SPEC.md (раздел «Не входит»: явный остаток передан в B1b),
tasks/T053/SPEC.md (та же формулировка остатка), orchestrator/fsm.py
(`_cmd_approve_merge_gate`, `_handle_merge_conflict` — текущая
локальная merge-механика T052/T053), orchestrator/ci.py (существующее
чтение check-runs — уже покрывает часть требования 1 ТЗ про «чтение
статусов CI»), docs/roadmap.md (строка P3 «CI-события GitHub
теряются», $15, источник п.4 ТЗ), docs/audits/roadmap-audit-2026-08-23-
v4-decisions.md (L460 — «A7 + B1b меняют способ merge»).

Установлено без вопроса (не требует эскалации, использовано при
будущем SPEC): точка вставки состояния `verifying` в цепочку FSM —
между `review` и `acceptance`, не между `acceptance` и `merge_gate`
(docs/design.md, список «запланированные расширения маршрута»:
«`verifying` между review и acceptance»; ADR-0003 §10 называет
`verifying` носителем verify-профиля, применяемого до приёмки).

ADR-0002) без решения Оператора. Без ответа на вопрос 2 нельзя
написать AC для поведения `verifying` при красном CI — п.5 ТЗ прямо
требует «учесть остаток T052», но не задаёт, что именно происходит
при провале CI внутри `verifying`.
