# SPEC: B1b: GitHub-адаптер, Draft-MR и состояние verifying

## Контекст

Роадмап §3, фаза B, строка B1b ($25+15): внешний GitHub-контур поверх
изоляции обвязки целевого из B1a (T069), первый прогон — на самой
артели (target `artel`, targets.yaml, forge: github, merge_gate:
operator). Сегодня конвейер целиком локален: merge — только
`git merge --no-ff` + push (T052/T053), у задачи нет видимого людям
MR, а зелёный CI проверяется ровно один раз — на входе в `merge_gate`;
приёмка (`acceptance`) стартует сразу по вердикту ревью, не дожидаясь
CI головного коммита. Ответ Оператора на батч вопросов (ANSWER-1)
зафиксировал два решения: механика самого merge не меняется (остаётся
локальный `git merge --no-ff` + push, T052/T053 не трогаются;
GitHub-адаптер получает только Draft-MR-флоу и её как побочный
эффект отмечает смерженной), а состояние `verifying` не возвращает
задачу автоматически — только ручной `reject` (симметрия инварианта
19) и потолок ожидания, актуальный для строки роадмапа P3
(«CI-события GitHub теряются», T040).

## Требования

1. GitHub-адаптер целевого `artel` (forge: github, targets.yaml)
   заводит Draft MR ветки задачи при первом входе задачи в `in_dev`
   (заголовок MR либо содержит id/название задачи — конкретный текст
   не специфицируется). Повторные входы задачи в `in_dev` (после
   замечаний ревью или после `reject` из `verifying`) не заводят
   второй Draft MR для той же задачи — MR один на весь жизненный цикл
   задачи.
2. При входе задачи в `merge_gate` (переход `acceptance -> merge_gate`)
   Draft MR, заведённый требованием 1, снимается с Draft (undraft) —
   становится обычным MR. Сам исполнитель гейта мержа остаётся
   `operator` (targets.yaml); режим `target-human`/состояние
   `awaiting_human` (ADR-0003 п.7) этой задачей не активируется.
3. Операция «merge» адаптера в этой задаче не мержит через API:
   слияние по-прежнему выполняет локальный `git merge --no-ff` + push
   внутри существующего `approve` из `merge_gate` (`fsm.py::
   _cmd_approve_merge_gate`), без изменений его механики, включая три
   исхода провала (SPEC T052) и мьютекс merge-окна (SPEC T053).
   Adapter-операция «merge» реализуется как отметка/закрытие Draft MR
   из требования 2 смерженным ПОСЛЕ того, как push уже доставил
   коммит в `main`, — явным вызовом API или расчётом на автоопределение
   GitHub по коммиту в истории `main` (выбор конкретного способа — за
   реализацией).
4. Новое состояние FSM `verifying` вставляется между `review` и
   `acceptance` (docs/design.md, список запланированных расширений;
   ADR-0003 п.10): исход, который раньше переводил задачу из `review`
   сразу в `acceptance` (свежий вердикт REVIEW.md `approved` + зелёные
   `acceptance_tests`), теперь переводит её в `verifying`. Само
   состояние `acceptance` и всё, что после него (включая автогейт по
   политике `gates.yaml`, ADR-0007), не меняется — меняется только
   момент входа в него.
5. `advance` из `verifying` проверяет статус CI головного коммита
   ветки задачи и различает четыре случая (роадмап, строка P3;
   TZ п.4):
   - зелёный (все check-runs завершены, конклюжны в допустимом
     множестве) — переход `verifying -> acceptance`;
   - «проверок нет вовсе» — check-runs коммита пусты И `gh run list`
     по ветке тоже не показывает запусков — задача остаётся
     в `verifying`, диагностика и подсказка Оператору — в журнал;
   - «проверки идут» — check-runs показывают незавершённые ИЛИ
     check-runs пусты, но `gh run list` по ветке показывает запуск
     для этой ветки/коммита (задержка события — прецедент T040) —
     задача остаётся в `verifying`;
   - «CI красный» — check-runs завершены, есть незелёный конклюжн —
     задача остаётся в `verifying` (не возвращается автоматически).
   Во всех не-зелёных случаях система не создаёт коммитов в ветке
   задачи с единственной целью сдвинуть её голову и «разбудить» CI
   (роадмап P3: пустой коммит ломает approve-по-sha).
6. Ожидание в `verifying` имеет потолок — именованную константу.
   По его исчерпании без зелёного статуса CI (любой из трёх
   не-зелёных случаев требования 5, включая «проверок нет вовсе»)
   `advance` переводит задачу `verifying -> escalated` с диагностикой
   последнего известного статуса CI в журнале. Это единственный
   автоматический выход из `verifying`, кроме зелёного CI.
7. Красный CI сам по себе не выталкивает задачу из `verifying` —
   симметрия инварианта 19 и требования 3 SPEC T052, распространённая
   на новое состояние (остаток T052, зафиксированный в его SPEC как
   «связка с verifying/await-ci — B1b»). Выход из `verifying` при
   красном CI — либо ручной `reject`, либо истечение потолка ожидания
   (требование 6).
8. `artel.py reject <id> "<причина>"` расширяется на `verifying`:
   один переход `verifying -> in_dev` с причиной в журнале, тем же
   приёмом, каким T052 расширила `reject` на `merge_gate` — без
   увеличения `review_iters`/`accept_rejects`.
9. Механизм периодического вызова `advance` в `verifying` (кто и как
   часто опрашивает статус CI, пока задача ждёт — Оператор вручную,
   `auto`, внешний cron/`loop`-скил) этой задачей не специфицируется:
   специфицировано только поведение самого `advance` при вызове
   в `verifying` (требования 5–7). Разовый вызов `advance` — полный
   контракт; частота его повторения — эксплуатационная деталь.

## Критерии приёмки

AC-1. Draft MR ветки задачи в target `artel` заводится через
GitHub-адаптер при первом входе задачи в `in_dev`; повторные входы
задачи в `in_dev` (после замечаний ревью или после `reject` из
`verifying`) не создают второй Draft MR для той же задачи.

AC-2. При входе задачи в `merge_gate` (переход `acceptance ->
merge_gate`) Draft MR, заведённый по AC-1, снимается с Draft
(undraft).

AC-3. Если реализация явно закрывает/помечает MR смерженным через
адаптер, такой вызов происходит только после успешного `git push`
в `main` внутри `approve` из `merge_gate` — никогда до него и никогда
при отказном исходе `approve` (содержательный конфликт, конфликт
в защищённых путях, инфраструктурный отказ, красный CI — все три
исхода определены SPEC T052).

AC-4. Переход `review -> verifying`: REVIEW.md со свежим вердиктом
`approved` (`artifacts.fresh_verdict_iteration`) и зелёные
`acceptance_tests` переводят задачу в `verifying`; прямого перехода
`review -> acceptance` для этого исхода больше нет.

AC-5. `advance` из `verifying` при зелёном CI головного коммита ветки
задачи (все check-runs завершены, конклюжны в множестве `ci.GREEN`)
переводит задачу `verifying -> acceptance`, включая попытку автогейта
`acceptance` по политике `gates.yaml` — так же, как это происходило
при входе в `acceptance` до этой задачи.

AC-6. `advance` из `verifying`, когда check-runs головного коммита
пусты и `gh run list` по ветке тоже не показывает запусков, оставляет
задачу в `verifying`; в журнал попадает запись «проверок нет»
с подсказкой Оператору; переход ни в `acceptance`, ни в `escalated`
не выполняется (пока не исчерпан потолок ожидания из AC-9).

AC-7. `advance` из `verifying`, когда check-runs головного коммита
пусты, но `gh run list` по ветке показывает запуск для этой
ветки/коммита, трактует статус как «проверки идут» (не как «проверок
нет»); диагностика в журнале называет источник (`gh run list`);
задача остаётся в `verifying`.

AC-8. `advance` из `verifying`, когда check-runs головного коммита
завершены и хотя бы одна проверка не входит в `ci.GREEN`, оставляет
задачу в `verifying` (не в `in_dev`, не в `escalated`); список
незелёных проверок — в журнале.

AC-9. По истечении потолка ожидания (именованная константа) без
зелёного CI в любом из случаев AC-6—AC-8 `advance` переводит задачу
`verifying -> escalated` с диагностикой последнего известного статуса
CI в журнале.

AC-10. `artel.py reject <id> "<причина>"` из `verifying` выполняет
переход `verifying -> in_dev`, причина записывается в журнал;
`review_iters` и `accept_rejects` этим переходом не изменяются.

AC-11. `reject` из состояний, отличных от `merge_gate`, `acceptance`
и `verifying`, ведёт себя так же, как до этой задачи — без изменений
в поведении, доступных состояниях и лимитах.

AC-12. Ни при каком исходе `advance` из `verifying` (AC-5—AC-9)
оркестратор не создаёт коммит в ветке задачи с единственной целью
сдвинуть её голову («разбудить» CI).

AC-13. Существующее поведение SPEC T052 (три исхода провала merge из
`merge_gate`: содержательный конфликт, конфликт в защищённых путях,
инфраструктурный отказ/красный CI) и SPEC T053 (мьютекс merge-окна)
не меняется этой задачей; соответствующие тесты остаются зелёными.

AC-14. Реализация ограничена `orchestrator/` (новые/изменённые
модули), `tests/` и `docs/codebase-map.md`; ни один путь из no_paths
target `artel` (`gates.yaml`, `roles.yaml`, `targets.yaml`, `.github/`,
`templates/`, `skills/`, `docs/invariants.md`, `tests/test_invariants.py`,
`CLAUDE.md`) не меняется.

## Не входит

- Merge через GitHub API (вариант A вопроса 1 QUESTIONS.md) —
  отдельная задача с отдельным решением Оператора по ADR-0002;
  локальная конфликт-механика T052 и мьютекс T053 не переосмысляются.
- Режим `merge_gate: target-human`, состояние `awaiting_human`,
  поллинг merge-события форджа для этого режима, наблюдение внешних
  дискуссий MR и триаж комментариев (ADR-0003 §9) — фаза C.
- gitlab-адаптер — реализуется только `forge: github`.
- Полная система per-target verify-профилей (`verify: [ci,
  agent:...]`, агент-верификатор после кода, ADR-0003 п.10) сверх
  ядра ожидания CI — C2 и далее; для `artel` пустой профиль
  покрывается ядром `verifying` этой задачи.
- Активация роли `verifier` (roles.yaml, сейчас `executor: none`) —
  вне объёма; `verifying` в этой задаче не запускает агента.
- Автоматический возврат `verifying -> in_dev` по красному CI без
  `reject` или истечения потолка ожидания — запрещён требованием 7
  (симметрия инварианта 19).
- Поведение Draft MR при `kill` задачи и при возврате `review ->
  in_dev`/`verifying -> in_dev` (обновление, комментарий, переоткрытие)
  — ТЗ не описывает, эта задача не реализует.
- Операции форж-адаптера `comment`/`reply`/`list_discussions`/
  `mr_events`/`approve_label` (ADR-0003 §6) — нужны только триажу
  ADR-0003 §9 (target-human), вне объёма этой задачи.
- Механизм периодического вызова `advance` в `verifying` (сон/интервал
  внутри `auto`, отдельный демон, cron/`loop`-скил) — требование 9;
  специфицировано только поведение отдельного вызова.
- Песочница B3, креды роли в контейнере (B-спайк) — границы ТЗ.
- N=2 (межтаргетный параллелизм), merge queue — B4, отдельная задача.
- Изменение схемы БД сверх того, что нужно для потолка ожидания
  и, при необходимости, отметки заведённого Draft MR — не требование
  этой задачи, а допустимая опция при реализации.
- Файлы вне `orchestrator/`, `tests/` и `docs/codebase-map.md`, в
  частности пути no_paths, перечисленные в AC-14.
