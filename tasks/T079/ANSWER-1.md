# Ответ Оператора на QUESTIONS T079 (решение 31.08.2026)

## Вопрос 1 — механика merge: вариант B (не заменять)

Локальный `git merge --no-ff` + push остаётся ровно как сейчас;
конфликт-механика T052 и мьютекс T053 НЕ трогаются. Адаптерная
операция merge в этой задаче — побочный эффект локального мержа:
Draft-MR переводится в ready на входе в merge_gate и
помечается/закрывается смерженным после того, как push доставил
коммит в main (API-вызов либо штатное автоопределение GitHub по
коммиту в истории main — выбрать при реализации, что проще
и наблюдаемее).

Вариант A (merge через API) — осознанно отложен: отдельная задача
с отдельным решением по ADR-0002, актуальна к эпохе чужих целевых,
где локального push в main целевого нет. В SPEC этой задачи
зафиксировать в «Не входит».

## Вопрос 2 — verifying при красном CI: вариант B (только ручной reject)

`verifying` сам задачу не возвращает: ждёт с потолком ожидания
(п.4 ТЗ). Красный CI виден Оператору; решение — за ним: команда
`reject <id> "<причина>"` расширяется с merge_gate также на
verifying. Симметрия с инвариантом 19 («красный CI не выталкивает
автоматически», SPEC T052 требование 3) сохраняется. Исчерпание
потолка ожидания (в т.ч. случай «проверок нет вовсе») — эскалация,
не автоворот.

## Подтверждение попутного

Точка вставки verifying между review и acceptance (установлено
analyst по design.md и ADR-0003 §10) — верно, так и делать.
