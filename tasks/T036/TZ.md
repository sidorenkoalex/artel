# ТЗ: Merge-последовательность merge_gate через gitcmd.git

Merge-последовательность merge_gate через обёртку gitcmd.git (ревизия CR-2026-08-26-4).

Проблема: единственная git-последовательность системы мимо эталонной обёртки gitcmd.git — самое опасное место, мерж в main: orchestrator/fsm.py:440-445, четыре голых subprocess.run(["git", ...]) (checkout main, pull --ff-only, merge --no-ff, push). Мимо единого шва тестируемости и обработки отказов, который для git-вызовов уже существует (gitcmd.git).

Что сделать: перевести эти четыре вызова на gitcmd.git, сохранив поведение в точности.

Это задача класса «рефакторинг» (правила T015): поведение не меняется — тот же порядок команд, те же тексты записей журнала (в т.ч. «merge FAILED» с хвостом stderr до 500 символов) и те же тексты отказов sys.exit; наблюдаемые поверхности — CLI-вывод approve, журнал steps, состояние задачи. Зелёность существующих тестов = неизменность поведения. Тесты: сценарии и ассерты не меняются; допустимы только пути патчей (mock gitcmd.git вместо fsm.subprocess.run) — ревьювер сверяет по диффу. Никаких попутных улучшений (не трогать соседние ветки cmd_approve, не менять сообщения, не добавлять ретраи).

Критерии приёмки (ориентир): (1) в fsm.py не остаётся прямых subprocess.run(["git", ...]); (2) отказ любой из четырёх команд по-прежнему пишет «merge FAILED» в журнал и завершает CLI с тем же текстом; (3) успешный путь по-прежнему переводит задачу в done с той же записью журнала; (4) все существующие тесты зелёные, правки в тестах — только пути патчей.
