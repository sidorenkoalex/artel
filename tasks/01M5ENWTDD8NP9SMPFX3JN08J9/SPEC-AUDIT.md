## Пути обхода гейтов
- Сводка Vitest — наблюдение для дозора и отчёта, не гейт: блок, который роль
  сама выведет (`echo`), даст запись «прогон vitest». У pytest та же поверхность
  уже есть; гейт этим не обходится, отклонения нет.
- Требование 7, вторая часть («сверка изменённых утверждений — по строкам
  гейта исходов пакета ревьювера», SPEC.md:94-95), не называет раздел пакета
  ревьювера, а AC-10 проверяет только применимость приложения. Дописку можно
  написать так, что ревьювер у компонента `pult-vitest` получит лишь «каталог
  долгоживущих тестов компонента» вместо `tests/`, а сверки утверждений не
  будет. Пункт для Оператора на гейте PLAN (содержание приложения — его
  решение), отдельного отклонения SPEC нет.
- Требование 1 опирается на `labelled_components`, а требования 3/6 — на
  `report == pult-vitest`. Меченый `junit-xml` с командой не pytest получает
  задание Vitest-формы, но «итог pytest» в plank-run. Так прямо задано в ТЗ
  («Граница задачи»), это не обход.

## Вердикт
**concerns** — SPEC можно вести дальше. Ниже отклонения, по которым решает
Оператор на гейте SPEC:

1. **Проба формы блока Vitest на sled выпала из обязательств** —
   SPEC.md, раздел «Не входит» («Проба настоящей формы блока Vitest на sled —
   этап 2 плана, не тест ветки») против ТЗ п. 5 («подтверждается пробой на sled
   (этап 2 плана)»). Ни одно требование SPEC не обязывает PLAN нести этап
   пробы. Вывести пробу из «Не входит» в требование («PLAN, этап 2 — проба на
   sled; расхождение формы — эскалация») либо снять её решением Оператора.
2. **Текст пункта 2 при пустом `plank_layout` не определён** — SPEC.md:48-50
   («На прогоне файлы лежат в `<plank_layout с id задачи>`…») и AC-2
   (SPEC.md:113). Признак требования 1 срабатывает у меченого компонента без
   `plank_layout` и без `report` (orchestrator/project_profile.py:496-503).
   Такой компонент уже заводит существующий тест, который остаётся без правок
   (tests/test_01m5aa5ts90rdj2afxb882wtpd_template_hints.py:54-61, :193-217).
   Здесь выкладки по `plank_layout` нет (orchestrator/acceptance.py:1328-1333,
   :1400-1406), и фраза о каталоге выкладки окажется пустой или ложной.
   Варианты: опустить фразу о выкладке; заменить её указанием, что выкладка не
   определена; отказать в признаке. Сейчас выбор остаётся разработчику.
3. **Эталон текста и формат секунд заданы не до конца** — SPEC.md:45,
   :49 (`<последние сегменты масок tests>` и `<plank_layout с id задачи>` без
   правила подстановки: разделитель масок, кавычки, `<id>` в верхнем или
   нижнем регистре) и SPEC.md:67-68, AC-3 (SPEC.md:117-121): для `ms` сказано
   «две цифры после точки», для `s` формат детали не задан (`1.5s` → `1.5s` или
   `1.50s`). Test_author должен сочинить эталон сам, и планка может закрепить
   форму, которой SPEC не требует (`тест-навязывает-устройство`).
4. **Нет поведения при `decide(target).profile is None`** — SPEC.md:70-71,
   :80, AC-5 (SPEC.md:129-133). Буквальная формула
   `decide(target).profile.report` падает `AttributeError` у проекта без
   профиля: `decide` возвращает `skip`/`refusal` без профиля
   (orchestrator/project_profile.py:184-209). Падение случится в
   `_spawn_and_wait` (orchestrator/runner.py:1708), то есть на запуске каждого
   шага такого проекта, и в `plank-run` (orchestrator/plank_run.py:287-291).
   Нужно явно сказать, что без профиля — прежнее поведение, и добавить случай
   в AC-5/AC-9.
5. **Неполный перечень сигналов деления** — раздел «Оценка объёма и деление»
   называет два сигнала. `guard.split_signal_names` (scripts/guard.py:4687-4727)
   на этом SPEC даёт ещё «затронут инвариантный механизм» (зона `tests/`, а
   также журнал шагов из инварианта 11, docs/invariants.md:41, который
   опирается на `agent_log`/`runner`) и «прогноз диффа не дан». Обоснование
   монолита этих двух сигналов не касается. Guard SPEC проходит
   (`GUARD: ок`), так что решение по объёму — за Оператором с полным
   перечнем.
