# PLAN: G5б — задание test_author по правилу планки, сводки Vitest, итоговая строка plank-run, скилы приложением

## Подход
Новое поведение включается двумя признаками, каждый — из уже существующего
источника, без правки модулей «только чтение»:

- **Задание test_author** (`orchestrator/role_prompt.py`): признак —
  `profile.component in project_profile.plank_rule(target).labelled_components()`,
  где `profile = project_profile.decide(target).profile` (тот же источник,
  что у guard). Профиль `None` или компонент без метки — прежний текст
  побайтно (пункт 2 «unittest…», пометки `#`). С признаком — пункт 2 по
  требованию 1 (последние сегменты `profile.tests` в порядке записи, фраза
  о `plank_layout` только при непустом поле, `<id>` → id задачи как есть),
  строка запретов, пометки `//` в пунктах 3–4 с хвостом «— с начала строки
  в файле планки компонента». Пункты 2а и 5 собираются прежними функциями
  (`_long_lived_author_note`, `_plank_run_point`).
- **Сводки и итог plank-run**: признак — `decide(target).profile.report ==
  REPORT_VITEST` с проверкой `profile is None` (`runner._reports_vitest`,
  то же условие в `plank_run.cmd_plank_run`).

Разбор блока Vitest — новая `agent_log.vitest_summaries(text)` рядом с
`pytest_summaries`: ANSI снимается тем же `_ANSI_ESCAPE_RE`, строки
обрезаются; блок = строка `Test Files  <сч> (<n>)`, сразу за ней
`Tests  <сч> (<n>)`, и в следующих четырёх строках `Duration  <число>(ms|s)`
с допустимым хвостом. Деталь — «<сч Tests> (<n>) in <секунды:.2f>s»
(`ms` переводятся в секунды). Разбор pytest не тронут (требование 5).

Насос `OutputPump` получает параметр `on_vitest_summary` (умолчание `None`)
и зовёт его тем же приёмом, что `on_pytest_summary`, со своим перехватом
сбоя записи. `runner._spawn_and_wait` передаёт параметр (запись
`VITEST_RUN_ACTION` в журнал своим соединением, как у pytest) только
задаче `pult-vitest`; у прочих kwarg не передаётся вовсе. Дозор сравнивает
действие с парой `_TEST_RUN_ACTIONS` во всех трёх местах (класс и два
бюджета), отчёт `_test_author_steps` считает секунды обоих действий
(деталь Vitest несёт « in X.XXs», `_PYTEST_SECONDS_RE` её читает).

`plank-run` у `pult-vitest` пишет «итог vitest: <последний блок либо
«итоговой строки нет»>» и «код выхода vitest»; у прочих — прежние строки
(`acceptance.run_summary_line`).

Скилы — приложениями ниже (защищённые пути); `git apply --check` обоих
приложений на чистом дереве ветки пройден (см. «Шаги», 4).

Бюджет SPEC ($30) не пересматривается.

## Влияние на систему
- Журнал шагов (инвариант 11): добавлено только новое действие
  «прогон vitest», и пишется оно только у задачи с `report: pult-vitest`;
  записи «прогон pytest», их деталь и разбор не менялись — у артели (в
  том числе у этой задачи) насос создаётся с тем же набором аргументов,
  что прежде.
- Задание test_author у артели, `test_profile`, pytest-компонентов и
  неопределённого профиля — прежний текст побайтно (AC-1/AC-5 долгоживущих
  тестов зелёные). `_labelled_profile` зовёт `decide` и `plank_rule` —
  оба без побочных эффектов; `plank_rule` у артели возвращается до чтения
  записи.
- Дозор: класс `pytest` расширен второй записью пары; бюджет строк общий —
  поток строк дозора у артели не меняется (записей «прогон vitest» у неё
  нет).
- `plank-run`: у прочих задач строки прежние; `decide` здесь уже звался.
- Гейты, guard, лимиты и тесты не ослабляются; существующие тесты не
  правлены, удалённых или переименованных методов нет.
- Откат — revert коммита задачи; приложения к скилам применяет только
  мерж.

## Риски
- Настоящая форма блока Vitest на sled не проверена (по SPEC — этап 2);
  если реальный вывод расставит пробелы иначе, чем двойной пробел после
  «Test Files»/«Tests»/«Duration», сводки не будет (поведение — как
  сейчас, без ложных записей).
- Несколько блоков Vitest в выводе `plank-run` — берётся последний, как у
  pytest (`run_summary_line`).

```diff
+## Компонент с меткой `AC-<n>: ` (Vitest)
+Разделы выше о unittest (метод `test_ac<n>_…`, `test_*.py`, `_*.py`,
+пометки `# AC-n: …`, `tests/`, `tests/sandbox.py`) относятся к
+Python-компоненту и к артели. Если компонент проекта задачи получает от
+правила планки метку `AC-<n>: ` (`project_profile.plank_rule`,
+`guard.PlankRule.labelled_components`; так у `report: pult-vitest` и у
+компонента с масками `tests` и командой не pytest), — задание роли
+называет это явно, и для планки действует этот раздел (ADR-0026,
+«Решение» пп. 4, 5, 11):
+- **Метка.** Тест — вызов `it`/`test`, имя которого начинается с
+  `AC-<n>: ` (например, `it("AC-3: отказ без токена", …)`): одна метка
+  на тест, `describe` меткой не начинается. Имя файла планки — по
+  последнему сегменту масок `tests` компонента (их называет задание),
+  файлы — прямо в `tasks/<id>/acceptance_tests/`, без подкаталогов;
+  общий код — помощники `_<имя>.<расширение>`.
+- **Запреты.** В тексте планки запрещены `.fails`, `.skipIf`, `.runIf`,
+  `.only`, `vi.setConfig`, ключи `retry`/`timeout` и числовой литерал в
+  аргументах `it`/`test`/`describe`/`suite` (`guard.plank_ban_errors`):
+  такой тест прошёл бы, ничего не проверив, или ослабил бы прогон.
+- **Каталог планки и импорты.** У компонента с `plank_layout` пульт на
+  прогоне выкладывает планку в этот каталог рабочей копии (`<id>` —
+  идентификатор задачи как есть; точный путь называет задание): импорты
+  кода проекта пиши относительно него, а не относительно
+  `acceptance_tests/`.
+- **Пометки.** Критерий без теста помечается `// AC-n: manual — …`,
+  `// AC-n: skip — …` или `// AC-n: escalate — …` с начала строки в
+  файле планки компонента; пометка `#` у такого компонента не читается.
+- **Долгоживущий файл** пишется в каталог долгоживущих тестов
+  компонента по его шаблону `long_lived` (`<id>` — id задачи в нижнем
+  регистре, `<name>` — имя, `<dir>` — каталог модуля; конкретный путь
+  называет пункт 2а задания) и проверяется тем же правилом метки и
+  запретов.
+- **Прогон** — только командой пульта `artel.py plank-run <id> [файл]`:
+  она прогонит планку и долгоживущие файлы раннером компонента и
+  напечатает «итог vitest: …; код выхода vitest: …» по итоговому блоку
+  Vitest.
```
