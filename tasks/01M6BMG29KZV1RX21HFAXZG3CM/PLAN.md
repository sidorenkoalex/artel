# PLAN: GitLab: гейт неослабления по исходам для full_suite ci — на verifying по отчёту CI отправленной головы

## Подход
Гейт для компонента `full_suite: ci` переезжает с `in_dev` на `verifying`.
Ядро прежнее — `_judge_ci`, база — `_diff_base`. Новое ядро не пишется,
гейт мержа не меняется.

- `in_dev`: `_outcome_integrity_gate` пропускает одиночный компонент
  `ci`. Пропуск не молчаливый: пишется запись
  «пропуск проверки: гейт неослабления по исходам» со строкой
  `DEFERRED_LINE`. В `_components_gate` на рубеже `in_dev` компоненты `ci`
  уходят из числа судимых в строки `DEFERRED_LINE`. Компоненты `local` и
  локальная часть `both` судятся, как прежде.
- `verifying`: новая точка входа `outcome_integrity.verifying_gate`.
  Её вызывает `fsm_advance.verifying` после зелёного CI и сверки перечня,
  до перехода в `review`. Судятся только компоненты `ci`/`both` в
  границе: `_gate(..., ci=True)` → `_gate_ci(verifying=True)`.
  Голова — `gitcmd.branch_head_sha` кодовой ветки. Это та же локальная
  ветка, голову которой `ci.verifying_status` только что признал зелёной:
  после сжатия, после перебазирования и после `pull-main`. Мандат
  читается с `artifact_source.resolve`.
- Ожидание и эскалация: `_ci_report` теперь возвращает третий элемент —
  признак «проходящая негодность». Проходящие случаи: задания нет, статус
  из перечня незавершённых, статус или отчёт не прочитан, перезапуск во
  время чтения. Для головы `_judge_ci` бросает `_Pending`, подкласс
  `_Prepare`. Гейт мержа ловит его как `_Prepare` — его поведение
  прежнее. На `verifying` такой отказ получает действие `PENDING_ACTION`:
  пишется запись без префикса «переход отклонён» (бриф и `auto` её не
  читают), дальше действует прежний потолок `VERIFYING_CEILING_SEC` с
  этой причиной. Любой иной сбой подготовки — эскалация сразу, с причиной
  дословно.
- Находки. Класс «чинит Оператор» (`OUTCOME_REFUSAL_ACTION`) — запись
  отказа тем же действием и текстом, затем `escalated`. Класс «сломан
  правкой» — сначала `state -> in_dev` с деталью `RETURN_DETAIL`, затем
  запись отказа: её видит `store.refusal_history` и бриф developer. Два
  исключения ведут в `escalated`: повтор (тот же набор id, что у
  предыдущего отказа гейта исходов задачи, и после него был шаг
  developer) и предел (возврат с `RETURN_DETAIL` у задачи уже был).
  Повтор проверяется первым, как требует правило «если подходят оба».
  Счёт ведётся по журналу всей задачи, новой колонки нет.

## Влияние на систему
- Защита не ослабляется. `review` из `verifying` для `ci`/`both`
  достижим только через проход гейта. Неполные данные дают ожидание или
  эскалацию, пропуска нет. Гейт мержа перепроверяет подтверждённую
  голову, как прежде. Ослабление `test_ac9` идёт по мандату ANSWER-1;
  метод сохранил имя, его утверждения переписаны под новое свойство.
- Стоп-кран `auto` не правился. Находки «чинит Оператор», повтор и
  предел ведут в `escalated`, а `escalated` останавливает цикл.
- Классы отказов (`refusal_classes.py`) и инвариант 3 только читаются.
- Откат — revert merge-коммита задачи.

## Риски
- Ожидание отчёта головы пишет запись `PENDING_ACTION` на каждом опросе
  `verifying`. Журнал растёт так же, как от записей статуса CI.
- Ветка-источник документов читается на каждом опросе `ci`
  (`artifact_source.resolve`). Это дешёвое чтение git.

## Предложения системе
- Признак «проходящая негодность отчёта» сейчас живёт третьим элементом
  кортежа `_ci_report`. Если таких различий станет больше, стоит завести
  тип исхода чтения отчёта (outcome_integrity.py).
