# SPEC-AUDIT: GitLab: гейт неослабления по исходам для full_suite ci — на verifying по отчёту CI отправленной головы

## ТЗ и SPEC
Требования ТЗ 1–6 и критерии приёмки ТЗ в SPEC есть: ТЗ п.1 → треб. 1/AC-1;
п.2 → треб. 2–8/AC-2…AC-9; п.3 → треб. 9/AC-10; п.4 → треб. 11; п.5 →
треб. 12/AC-13; п.6 → «Не входит». Решения ANSWER-1 перенесены: ответ 1
(мандат, условия (а)/(б), файл в зонах) → треб. 10, 13, AC-11, AC-12, зоны,
матрица; ответ 2 → треб. 6/AC-7; ответ 3 → треб. 3. Требований сверх ТЗ и
ANSWER нет.

Расхождения:
1. **ТЗ п.2, первый подпункт: «разработчик получает те же сведения»** —
   в SPEC (треб. 3, AC-3) это сведено к «тот же текст и то же действие
   журнала». По коду этого мало. Бриф разработчика берёт отказы только
   текущего визита состояния: `brief.advance_refusal_history`
   (`orchestrator/brief.py:1413`) → `store.refusal_history`
   (`orchestrator/store.py:1185-1195`). Нижняя граница выборки — последняя
   запись `state -> in_dev`. Если отказ записан на `verifying` до
   `set_state(..., "in_dev")`, а это естественный порядок «записать отказ,
   потом вернуть», граница его отрезает: разработчик после возврата
   находок не увидит. AC-3 проверяет только журнал и такую реализацию
   пропускает. Нужно требование и критерий: бриф шага developer после
   возврата с `verifying` несёт находки.
2. **ТЗ п.2: «Голова — sha, отправленный на входе в `verifying`»** —
   SPEC (треб. 2, AC-8) повторяет это дословно. Но на `verifying` голова
   может смениться без выхода из состояния. `pull-main` подтягивает main,
   отправляет новую голову и оставляет задачу ждать её CI
   (`orchestrator/pull_main.py:1-9`). Опрос `verifying` судит CI текущей
   головы ветки (`ci.verifying_status` → `head_sha(branch)`,
   `orchestrator/ci.py:1028`). Если реализация запомнит sha «на входе»,
   то после `pull-main` гейт сравнит отчёт старого sha, а в `review` уйдёт
   новая голова, гейтом не проверенная (см. «Пути обхода», п.1).
   Формулировка должна быть: «текущая отправленная голова ветки — та, чей
   CI признан зелёным в этом опросе (после сжатия, а не коммит роли)».

Уточнения, которых нет в SPEC:
3. **AC-2 «конвейер головы, конвейер базы»** — общее ядро (треб. 2,
   «то же ядро») пишет в запись прохода номера *заданий* `ci_job`
   (`голова {head_report.job_id}, база {base_report.job_id}`), а не
   конвейеров (`outcome_integrity.py:1222-1227`). В `_CiReport` номера
   конвейера нет вовсе (`:1036-1041`). AC-2 буквально требует того, чего
   ядро не даёт, а треб. 2 запрещает уходить от ядра. Нужно выбрать одно
   из двух: «задание `ci_job` головы и базы (номер попытки)» либо явное
   добавление номера конвейера в запись.
4. **Граница треб. 4 («ждать») и треб. 6 («эскалировать сразу»)** —
   `_judge_ci` сворачивает любую негодность отчёта головы в один
   `_Prepare("нет отчёта головы: …")` (`outcome_integrity.py:1159-1161`).
   Туда попадают задания нет (`:1054`), перезапуск (`:1063`), статус не
   прочитан (`:1066`), любой статус вне `success`/`failed` (`:1068`:
   `running`, `pending`, `created`, `canceled`, `manual`, `skipped`),
   `allow_failure` (`:1070`) и неразобранный отчёт (`:1072`). Треб. 4 и
   AC-5 называют только «нет / `running` / не разобран». По тексту треб. 6
   «всё, кроме исходов треб. 4» `pending`/`created` (тоже «не готов») и
   сбой чтения статуса хостинга эскалируют сразу. Похоже, это не
   намерение ТЗ («ещё не готов — ожидание»). Перечень статусов-ожиданий
   надо задать явно.

## Пути обхода гейтов
1. **Устаревшая голова после `pull-main`** (п.2). Реализация запоминает
   sha на входе в `verifying`. Оператор делает `pull-main` — новая голова
   с подтянутым main отправлена, CI зелёный. Гейт сверяет отчёт старого
   sha (годный, без расхождений), и задача уходит в `review` с головой, по
   которой гейт исходов на `verifying` не судил. Гейт мержа потом поймает
   это (`_gate_ci`), но ревьювер получит «гейт исходов не исполнялся» для
   головы (`review_lines`, `outcome_integrity.py:1465-1482`), а AC-11 по
   смыслу нарушен.
2. **Находки до разработчика не доходят** (п.1). Буквальное «тот же
   текст, то же действие журнала» с записью до `state -> in_dev`
   формально выполняет AC-3. При этом бриф разработчика по построению
   `store.refusal_history` находок не несёт: шаг developer идёт вслепую, а
   повторная сдача ведёт к тому же отказу на `verifying`, ценой полного
   цикла CI на каждой попытке.
3. **Записи из нескольких компонентов.** SPEC не говорит о пути
   `project_profile.is_multi` (`outcome_integrity.py:1256-1265`,
   `_components_gate` `:1280-1333`): там компоненты диффа судятся каждый
   своим `_gate`. Реализация может снять `ci` с `in_dev` и поставить гейт
   на `verifying` только в ветке одного профиля (`:1266-1270`). Тогда у
   записи с компонентами разной `full_suite` (`local` + `ci`) компонент
   `ci` останется с локальными выписками на `in_dev` (против треб. 1) или
   уйдёт в `review` без гейта на `verifying` (против треб. 10). AC-1…AC-11
   не требуют сценария с несколькими компонентами. Нужна строка
   требования: «компонент `ci`/`both` записи `components:` — так же, по
   компоненту; компоненты `local` той же записи — на `in_dev` как сейчас».
4. **Немедленная эскалация вместо ожидания** (п.4) — не обход, а
   неоправданная остановка: `pending`/`created` или сбой HTTP чтения
   статуса по букве треб. 6 эскалируют задачу сразу.

Ручной `advance` из `in_dev` после возврата с `verifying` (PLAN уже
`ready`) повторно отправит ту же голову. Цикл `auto` это держит: гейт
переделки `_rework_gate_blocks` по записи `state -> in_dev`
(`orchestrator/auto.py:391-469`, `:751-771`). Ручной путь ведёт себя так
же, как существующий `reject` с `verifying`, — это не новое отклонение.

   головы» (`outcome_integrity.py:1054-1072`, `:1159-1161`); `pending`/`created`
   и сбой чтения статуса по букве SPEC эскалируют сразу.
5. Треб. 7 / AC-9: сторона перезапуска не названа. На стороне базы ядро
   даёт «нет отчёта базы», а не «перезапущено»
   (`outcome_integrity.py:1090-1108`). Указать задание головы.
6. Зоны: `tests/` сужен против ТЗ («долгоживущие файлы задачи»). Файл

(`outcome_integrity.py:1256-1265`, `:1280-1333`) в SPEC не упомянуты, и
ни один критерий их не проверяет.
