  `unsupported_reason`; `orchestrator/github_adapter.py:60`
  `_is_github_target`; `orchestrator/gitcmd.py:121` `hosting_token`.
- `repo_context.resolve` (`orchestrator/repo_context.py:85-101`) разрешает
  запись с `forge: gitlab`: `_project_context` в ci (`ci.py:135-157`)
  дойдёт до контекста. Значит, ветка `forge: gitlab` в ci по `repo`

Не подтвердилось или опущено:
- **Ф-1. `policy.ci_required_jobs` в записи проекта не бывает.** SPEC
  (треб.5; AC-5, AC-19) исходит из того, что поле можно прочитать из
  записи. Но раздел `policy` локального слоя принимает только перечень
  `targets.py:330-334`. Неизвестное поле — `TargetsError` («неизвестное
  поле», `targets.py:441-443`). `_flatten` переносит в плоскую запись
  только поля `targets.py:585-588`, и `ci_required_jobs` среди них нет.
  Поэтому в записи, полученной через `targets.target`, поле
  отсутствует всегда, а правило «`manual` из обязательных → `running`»
  в боевой записи не срабатывает никогда. `targets.py` вне зон SPEC, и
  в «Не входит» шаг, который добавит поле в схему, не назван.
- **Ф-2. «Запись без `token_slot`» (AC-3) через загрузчик
  недостижима.** `token_slot` — обязательное поле (`targets.py:38`,
  проверка :624-626; раздел `machine` :335). А `gitcmd.hosting_token` на
  записи без слота отдаёт `(None, None)` — «прежняя авторизация»
  (`gitcmd.py:124-137`), а не отказ. SPEC не говорит, что GitLab-ветка
  должна считать `(None, None)` отказом (у GitHub это штатный путь без
  токена). Правило выводится из треб.3 («токен не получен … именованная
  причина»), но место ловушки не названо. Тип параметра `target` в
  функциях `forge` (имя записи или сама запись) SPEC тоже не задаёт. От
  этого зависит, как тест AC-3/AC-5/AC-19 подаёт запись без
  `token_slot` или с `ci_required_jobs`.
- Справочно, не отклонение: GitHub-итог `forge.pipeline_status`
  (треб.2, из ТЗ) расходится с цветом `ci.verifying_status` на тех же
  данных. `ci` проверяет «идёт» раньше «красного» (`ci.py:1034-1045`), а
  `action_required` считает красным (`GREEN` :27, `failed` :1023). В
  `forge` порядок обратный, и `action_required` → `unknown`. Сейчас ci
  для GitHub через `forge` не ходит, так что поведение не меняется. Но
  будущий потребитель `forge.pipeline_status` для GitHub получит другой
  цвет, чем гейт ci.

## Пути обхода гейтов
- **О-1 (Д-1).** Реестр в `forge.py` объявлен, а `ci.py` ветвится
  сравнением с константой (`targets.FORGES[...]`) или по признаку URL.
  Сторож А0 ловит только литералы, AC на треб.1 нет — смысл требования
  «выбор поиском по ключу» обходится буквально зелёным.
- **О-2 (AC-17).** Если сторож AC-17 ищет только узлы `urllib.…`/
  `http.client.…`, то импорт имени (`from urllib.request import urlopen`)
  на уровне модуля и вызов `urlopen` из функции, отличной от транспорта,
  проходят. SPEC стоит уточнить: сторож учитывает импорты и их псевдонимы
  (`Import`/`ImportFrom`) — импорт `urllib`/`http.client` разрешён только
  внутри транспорта либо имя из такого импорта вызывается только там.
- **О-3 (Д-2).** AC-5/AC-19 проходят на словаре-записи с
  `ci_required_jobs`, поданном в обход `targets.target`. Боевая запись
  поле не принимает (`targets.py:441`), поэтому обязательное ручное
  задание считается необязательным, а конвейер с непрогнанным
  обязательным `manual` — `green`. Пока GitLab закрыт
  (`SUPPORTED_FORGES`), это недостижимо. Но Б2 откроет поддержку, и дыра
  перейдёт к инварианту 19, если шаг, вводящий поле, не назван.
- **О-4 (Д-3).** Требование 5 не задаёт старшинство правил при
  сочетаниях: задание `failed` + задание `canceled`; конвейер `running`
  + задание `failed` без права падать; конвейер `manual` + `created` без
  более раннего `manual`; два конвейера `red` и `unknown`. Для гейта мержа
  это безопасно (все случаи не `green`). Но от выбора между `red`,
  `running` и `unknown` зависят `status_kind`/`verifying_is_red` и
  поток ci (ре-ран, «красный» против «неизвестен»). AC-5 проверяет лишь
  «не green», так что любой выбор разработчика проходит.

## Вердикт
`concerns`: SPEC исполним, правила зелёного CI GitLab и отображение в ci
покрыты проверяемыми критериями. Решения Оператора на гейте ждут
отклонения:

1. **Д-2 / Ф-1 / О-3** — `policy.ci_required_jobs` не принимается
   загрузчиком записи (`orchestrator/targets.py:330-334`, :441-443,
   :585-588), а `targets.py` вне зон SPEC (frontmatter `zones`). Варианты:
   а) добавить `orchestrator/targets.py` в зоны и требование «поле
   `policy.ci_required_jobs` — список строк, принимается и переносится в
   запись»; б) записать в «Не входит» шаг, который вводит поле (Б1/Б2),
   и условие: не открывать `SUPPORTED_FORGES` для gitlab без него.
2. **Д-1 / О-1** — у треб.1 (реестр, выбор по ключу) нет критерия
   приёмки. Сторож А0 (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:453-471`)
   не ловит ветвление в `ci.py` сравнением с константой или по URL.
   Предложение: AC-ast «в `ci.py` нет обращения к полю `forge` записи,
   кроме передачи в `forge`; в `forge.py` выбор — индексом словаря».
3. **Д-3 / О-4** — нет старшинства итогов при сочетаниях статусов
   (SPEC треб.5). AC-5 вторым случаем проверяет только «не green».
4. **Ф-2** — не сказано, что `(None, None)` из `gitcmd.hosting_token`
   (`orchestrator/gitcmd.py:124-137`) для GitLab — отказ «токен не
   получен». Не задан тип параметра `target` функций `forge`. При том
   что `token_slot` — обязательное поле записи (`orchestrator/targets.py:624-626`),
   AC-3 «запись без `token_slot`» проверяем только записью в обход
   загрузчика.
5. **AC-17 / О-2** — сторож транспорта стоит уточнить: ловить импорт
   имён из `urllib`/`http.client` и вызов по псевдониму вне транспорта.
