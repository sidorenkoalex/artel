    (`os.getpgrp()` в исполнителе), отвечает на `config`/`ps`/`network
    ls`/`version`/`context inspect`/`compose down` заданным текстом (в том
    числе зависанием и ненулевым кодом) и пишет отчёт в смонтированный
    каталог дерева. Метки в ответе подменённого `docker ps`/`docker
    network ls` — ровно формат Docker: одна строка `ключ=значение` через
    запятую (решение гейта части 2, №1.7). Ответ подменённого `docker
    compose version --short` — ровно форма Docker: `2.39.4-desktop.1`
    (решение гейта части 2, №2.2).
    Отдельная группа процессов вызова утверждается только по группе,
    записанной подменённым `docker`: она не равна `os.getpgrp()` теста
    (решения гейта части 2, №5.1, №6.1); `os.getpgid` после `os.killpg`
    не применяется. Зависший вызов подменённого `docker` порождает
    дочерний процесс, записывает его pid и затем зависает (`exec sleep
    <n>`); снятие группы по пределу тест утверждает тем, что сразу
    после возврата вызова строки или починки `os.kill(<записанный pid
    дочернего процесса>, 0)` поднимает `ProcessLookupError` — без
    ожидания и без повторов в тесте (решения гейта части 2, №5.2, №6.1,
    №7.1; `orchestrator/test_lint.py:75-94` запрещает в тестах
    `time.sleep` с ненулевой паузой и циклы до срока). Исчерпание проб
    ожидания группы тест получает подменой: константа числа проб
    подменена малым числом, а ответ пробы — «группа есть» на каждую
    пробу (подменённый `os.killpg` с сигналом 0 поднимает
    `PermissionError` либо подменена `liveness._group_exists`); тест
    утверждает исход по пределу без исключения (решение гейта части 2,
    №8.1). В `finally` тест снимает только записанные pid
    зависшего вызова и его дочернего процесса, а не pid уже завершившихся
    вызовов (решение гейта части 2, №5.1). Тест вправе подменить
    `doctor.project_checks.DOCKER_CALL_TIMEOUT_SEC` и
    `config.COMPOSE_TEARDOWN_TIMEOUT_SEC` — атрибут именно модуля
    `orchestrator/config.py` — на 1 с (решения гейта 2.6; гейта части 2,
    №6.2). Тесты всех случаев, кроме случая процесса роли, снимают из
    своего окружения `ARTEL_ROLE` и дом роли (`HOME` не равен дому роли);
    отдельный случай с выставленным `ARTEL_ROLE` проверяет `skip` обеих
    строк без вызова подменённого `docker` (решение гейта части 2, №6.3).
    Окружение каждого вызова подменённого
    `docker` тест сверяет так: в `os.environ` теста выставлены `HOME`

## Критерии приёмки

AC-1. У задачи с профилем `compose` (в `test_profile`; в одном из компонентов) окружение `runner.role_env` побайтно равно окружению той же вымышленной записи с профилем `pytest-own` (временный дублёр записи проекта в песочнице, настоящие файлы не меняются); у `pytest-own`, `pult-pytest`, артели, вызова без проекта и при непрочитанной записи проекта окружение `role_env` побайтно прежнее, исключения нет; `stack.ROLE_ENV_ALLOWLIST` не изменён.

AC-2. `doctor`, строка «забытые стенды пульта» — функция строки и функция её починки вызываются через фасад `doctor`, в песочнице с подменённым `config.ROOT`; ответ `docker ps`/`docker network ls` подменён, метки в нём — строка `ключ=значение` через запятую: контейнеры и сети проекта формы `artel-<id строчными, 26 знаков>-<8 hex>` с тройкой меток `artel.run-*`, мёртвой по pid и времени (мёртвый pid; живой pid со временем `artel.run-started` раньше старта этого процесса), — `warn` с именами, починка зовёт `down --remove-orphans` с их именем проекта, в argv `down` нет ни `-v`, ни `-f`, рабочий каталог вызова — пустой временный каталог; стенд живого прогона (живой pid и время `artel.run-started` не раньше старта процесса) — и с именем этого хоста, и с чужим именем хоста в `artel.run-host` — в `warn` не попадает, `down` для него не зовётся; проект `artel-foo` и проект правильной формы без единой метки живого прогона в `warn` не попадают, починка `down` для них не зовёт; чужой контейнер Compose с меткой `com.docker.compose.project.config_files=/a.yml,/b.yml` в ответе `docker ps` — строка не падает, в `warn` его нет, `down` для него не зовётся; стенд правильной формы с каждым из трёх видов порчи меток (нет одной метки; `artel.run-pid` не число; `artel.run-started` не в формате `store.now()`) — `warn` «метки стенда не разобраны» с именем проекта Compose, починка `down` для него не зовёт, строка не падает. Адрес демона не `unix://` (подменённый `docker context inspect` отвечает `tcp://…` при не заданном `DOCKER_HOST`; `DOCKER_HOST=tcp://…` в окружении пульта) — `skip` «демон Docker не локальный», `down` не вызван. Строка не входит в список `check_orphans`, исходы `check_orphans` прежние; строка есть в `doctor.all_checks(conn)` песочницы, а `cmd_doctor(fix=True)` с подменёнными по имени прочими починками (как `tests/test_doctor_closed_ref_fix.py:177-183`) и подменённой по имени `doctor._fix_canary_live` вызывает её починку, подменённая `_fix_canary_live` вызвана, ни одна настоящая починка, включая `_fix_canary_live`, не исполнена. В окружении с выставленным `ARTEL_ROLE` — `skip` «в шаге роли Docker не вызывается», подменённый `docker` не вызван ни строкой, ни починкой; прочие случаи идут без `ARTEL_ROLE` и с `HOME`, не равным дому роли. Без проекта `compose` — `skip`, `docker` не вызван ни строкой, ни починкой; проект `compose` есть, а `docker` в `PATH` нет — `warn` «программа docker не найдена»; сломанный слой проектов (вымышленный слой в песочнице) — `warn` «слой проектов не прочитан», прочие строки `doctor` печатаются, починка ничего не снимает; починка при `conn=None` при проекте `compose` — ни одного вызова `docker`; подменённый `docker ps`, `docker network ls` или `docker context inspect` зависает (порождает дочерний процесс, записывает его pid, затем `exec sleep <n>`; предел `DOCKER_CALL_TIMEOUT_SEC` подменён на 1) или возвращает ненулевой код — `warn` «Docker не отвечает», строка завершается за предел, сразу после возврата строки `os.kill(<pid дочернего процесса зависшего вызова>, 0)` поднимает `ProcessLookupError`. Подменённый `compose down` зависает так же, с дочерним процессом (подменён атрибут `config.COMPOSE_TEARDOWN_TIMEOUT_SEC` модуля `orchestrator/config.py` на 1, и он действует на `down`) — починка завершается за предел, сразу после её возврата `os.kill(<pid дочернего процесса зависшего `down`>, 0)` поднимает `ProcessLookupError`. Исчерпание проб ожидания группы после `os.killpg` (константа числа проб подменена малым числом, каждая проба отвечает «группа есть» — `PermissionError`) — у зависшего `ps` строка даёт `warn` «Docker не отвечает», у зависшего `down` починка возвращается; исключения нет, `doctor` не падает. У каждого вызова подменённого `docker` строки и её починки (`context inspect`, `ps`, `network ls`, `compose down`) записанная им группа процессов не равна `os.getpgrp()` теста, в окружении нет `HOME` пульта и переменной-метки, выставленной тестом в `os.environ`; `PATH` вызова — ровно каталог подменённого `docker` и `_OWN_SYSTEM_PATH_DIRS`; `os.getpgid` после снятия по пределу не применяется; в `finally` тест снимает только pid зависших вызовов и их дочерних процессов.

AC-3. `doctor`, строка записи `compose`: строка есть в `doctor.all_checks(conn)` для вымышленного проекта `compose` в песочнице; нет `compose_file` или `compose_env_template` в клоне — `fail`; `config --services` вызван с `--env-file` на шаблон окружения из клона; сервиса нет в ответе `config --services` — `fail` с именем сервиса; подменённый `config --services` возвращает ненулевой код — `fail` с текстом Compose; ответ подменённого `docker compose version --short` `2.39.4-desktop.1` — `ok`, `v2.39.4` — `ok`, `v2.0.3` — `fail` с найденной версией, `2.1.0` — `fail` с найденной версией, `2.1.1` — `ok`; `docker compose version` не отвечает — `fail`; `docker` в `PATH` нет — `fail` «программа docker не найдена»; проект с двумя компонентами `compose`, у одного из которых нет Compose-файла в клоне, — одна строка, `fail` с именем этого компонента; подменённый `docker` зависает (порождает дочерний процесс, записывает его pid, затем `exec sleep <n>`; предел `DOCKER_CALL_TIMEOUT_SEC` подменён на 1) или возвращает ненулевой код — `fail` с текстом вызова, строка завершается за предел, сразу после возврата строки `os.kill(<pid дочернего процесса зависшего вызова>, 0)` поднимает `ProcessLookupError`; исчерпание проб ожидания группы после `os.killpg` (константа числа проб подменена малым числом, каждая проба отвечает «группа есть» — `PermissionError`) — `fail` с текстом вызова, исключения нет; в окружении с выставленным `ARTEL_ROLE` — `skip` «в шаге роли Docker не вызывается», подменённый `docker` не вызван, прочие случаи идут без `ARTEL_ROLE` и с `HOME`, не равным дому роли. У каждого вызова подменённого `docker` строки (`config --services`, `compose version`) записанная им группа процессов не равна `os.getpgrp()` теста, в окружении нет `HOME` пульта и переменной-метки, выставленной тестом в `os.environ`; `PATH` вызова содержит каталоги `machine.path` вымышленной записи по правилу части 1 (требование 6); `os.getpgid` после снятия по пределу не применяется; в `finally` тест снимает только pid зависших вызовов и их дочерних процессов.
