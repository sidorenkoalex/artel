17. **Форма тестов** (ТЗ родителя, «Критерии приёмки», «Безопасность
    тестов»; решения гейта 2, 3).
    Обязательные тесты — без настоящего Docker: программа `docker`
    подменена исполнителем в каталоге `PATH` теста, который записывает
    argv, окружение и свой pid, отвечает на `config`/`ps`/`network ls`/
    `version`/`context inspect` заданным текстом (в том числе зависанием
    и ненулевым кодом) и пишет отчёт в смонтированный каталог дерева.
    Метки в ответе подменённого `docker ps`/`docker network ls` — ровно
    формат Docker: одна строка `ключ=значение` через запятую (решение
    гейта части 2, №1.7). Ответ подменённого `docker compose version
    --short` — ровно форма Docker: `2.39.4-desktop.1` (решение гейта
    части 2, №2.2).
    Зависание подменённого `docker` — `exec sleep <n>` в исполнителе (без
    дочернего процесса-внука). Снятие процессов в `finally` (решение
    гейта части 2, №1.3): тест снимает записанный pid подменённого `docker`,
    а группу процессов — только если её номер не равен `os.getpgrp()`;
    вызовы `docker` пульта идут с `start_new_session=True`, так что группа
    `docker` не совпадает с группой pytest. Тест вправе подменить
    `runner.DOCKER_CALL_TIMEOUT_SEC` на 1 с (решение гейта 2.6) и кортеж
    системных каталогов дополнений Compose (требование 12) — на каталоги
    песочницы. Окружение каждого вызова подменённого `docker` тест
    сверяет так: в `os.environ` теста выставлены `HOME` пульта и
    переменная-метка теста, в записанном окружении вызова нет ни того,
    ни другого (решение гейта 3.1).
    Тесты строки «забытые стенды» вызывают саму функцию строки и саму
    функцию её починки через фасад `doctor`, а не `cmd_doctor(fix=True)`;
    тест, идущий через `cmd_doctor`, подменяет по имени все прочие
    починки, как `tests/test_doctor_closed_ref_fix.py:177-183`; ни одна
    настоящая починка пульта в тестах задачи не исполняется.
    Необязательный тест с настоящим Docker в этой части — `docker compose
    version` в окружении шага роли (прогон вымышленного Compose-файла и
    отказы по сокету Docker, требование 5, — часть 1); он утверждает, что
    `docker compose version` в окружении шага роли (окружение `role_env`
    задачи с профилем `compose`) отвечает версией не ниже 2.1.1, и
    пропускается с именованной причиной, если Docker не отвечает,
    дополнение Compose не найдено ни в `DOCKER_CONFIG` песочницы, ни в
    системных каталогах дополнений, или выставлена переменная окружения
    `CI` (решение гейта части 2, №1.10). Причина «Docker не отвечает»
    проверяется пробой Docker в окружении пульта (вне роли), а не в
    окружении шага роли: реализация без ветки `compose` в `role_env` даёт
    красный тест, а не пропуск (решение гейта части 2, №2.6). Сеть и
    скачивание образов исключены.
    Проекты — вымышленные во временной песочнице; `config.ROOT` (а с ним
    `runner.compose_role_dir()`) и `DOCKER_CONFIG` — каталоги песочницы;
    никогда — настоящий клон, настоящий локальный слой, настоящий
    `~/.docker`; в текстах тестов — ни имён, ни адресов реальных проектов.

## Критерии приёмки

AC-1. `runner.role_env` для задачи с профилем `compose` (в `test_profile` или в одном из компонентов) и провайдера `claude`: последний элемент `PATH` — `<compose_role_dir()>/<id строчными>/bin` под подменённым `config.ROOT` песочницы, `<compose_role_dir()>/<id строчными>` — ссылка на каталог версии `<id строчными>.v<…>`, в `bin/` ровно одна запись — ссылка `docker` на найденную программу; `DOCKER_CONFIG` — `<…>/<id строчными>/config`, содержимое `config.json` равно `{}` при вымышленной конфигурации пульта с `credsStore`, `auths` и `cliPluginsExtraDirs`; в `config/cli-plugins/` ровно одна запись — ссылка `docker-compose`; `DOCKER_HOST` — значение пульта `unix://…`; без него и при пустом `DOCKER_HOST` пульта — ответ подменённого `docker context inspect`. `DOCKER_HOST=tcp://…` пульта — отказ старта, `docker context inspect` не нужен, агент не запущен. Подменённый `docker context inspect`: зависание (`exec sleep <n>`; тест снимает записанный pid, группу — только если её номер не равен `os.getpgrp()`) — отказ старта за предел `runner.DOCKER_CALL_TIMEOUT_SEC` (по умолчанию 10, тест вправе подменить на 1), ненулевой код — отказ, пустой или не `unix://` адрес — отказ; отказ — экземпляр `OSError`, в нём текст вызова, пустого `DOCKER_HOST` в окружении роли нет. Окружение вызова подменённого `docker context inspect` — ровно переменные требования 6: нет `HOME` пульта и переменной-метки, выставленной тестом в `os.environ`. Провайдер `codex` — отказ (`OSError`) с текстом «раннер compose в песочнице Codex не поддержан», каталог задачи не собран. При каждом из этих отказов `role_env` исход `run_agent_once` — `skipped` с текстом отказа, в журнале задачи — запись «agent run SKIPPED» с текстом отказа, агент не запущен.

AC-2. Повторная сборка каталога задачи: `<compose_role_dir()>/<id строчными>` — ссылка на новый каталог версии, прежний каталог версии удалён, временной ссылки `<id строчными>.tmp-<pid>` не осталось, посторонние записи, подложенные в `bin/` и `cli-plugins/` после прошлой сборки, отсутствуют. При подменённом кортеже системных каталогов дополнений: дополнение есть только в системном каталоге песочницы — `cli-plugins/docker-compose` — ссылка на него; дополнения нет ни в `DOCKER_CONFIG` пульта, ни в каталогах кортежа — `role_env` поднимает `OSError` с именем; без найденного `docker` — `OSError` с именем.

AC-3. У `pytest-own`, `pult-pytest`, артели, вызова без проекта и при непрочитанной записи проекта окружение `role_env` побайтно прежнее, исключения нет, каталог задачи не создаётся; `stack.ROLE_ENV_ALLOWLIST` не изменён.

AC-4. `doctor`, строка «забытые стенды пульта» — функция строки и функция её починки вызываются через фасад `doctor`, в песочнице с подменённым `config.ROOT`; ответ `docker ps`/`docker network ls` подменён, метки в нём — строка `ключ=значение` через запятую: контейнеры и сети проекта формы `artel-<id строчными, 26 знаков>-<8 hex>` с тройкой меток `artel.run-*`, мёртвой по `lease.process_alive`, — `warn` с именами, починка зовёт `down --remove-orphans` с их именем проекта, без `-v`; стенд живого прогона, проект `artel-foo` и проект правильной формы без единой метки живого прогона в `warn` не попадают, починка `down` для них не зовёт; стенд правильной формы с каждым из трёх видов порчи меток (нет одной метки; `artel.run-pid` не число; `artel.run-started` не в формате `store.now()`) — `warn` «метки стенда не разобраны» с именем проекта Compose, починка `down` для него не зовёт, строка не падает. Записи `compose_role_dir()`: ссылка живой задачи и каталог версии, на который она указывает, на месте и после починки, ссылка разрешается; каталог версии живой задачи, на который ссылка не указывает, — `warn` с путём, починка удаляет его; временная ссылка `<id строчными>.tmp-<pid>` с мёртвым pid — `warn`, починка удаляет её; все записи задачи в `done`/`killed` или без строки в БД (ссылка, каталог версии, временная ссылка) — `warn` с путём, починка удаляет их; обход и починка видят только каталог песочницы. Без проекта `compose` — `skip`, `docker` не вызван, записи `compose_role_dir()` не удалены и починкой; сломанный слой проектов (вымышленный слой в песочнице) — `warn` «слой проектов не прочитан», прочие строки `doctor` печатаются, починка ничего не снимает и не удаляет; починка при `conn=None` — ни одного вызова `docker`, ни одной удалённой записи (каталог задачи песочницы при проекте `compose` на месте); подменённый `docker ps` зависает (`exec sleep <n>`, предел `runner.DOCKER_CALL_TIMEOUT_SEC` подменён на 1; тест снимает записанный pid, группу — только если её номер не равен `os.getpgrp()`) или возвращает ненулевой код — `warn` «Docker не отвечает», строка завершается за предел. У каждого вызова подменённого `docker` строки и её починки (`ps`, `network ls`, `compose down`) в окружении нет `HOME` пульта и переменной-метки, выставленной тестом в `os.environ`; `PATH` вызова — ровно каталог подменённого `docker` и `_OWN_SYSTEM_PATH_DIRS`.

AC-5. `doctor`, строка записи `compose`: нет `compose_file` или `compose_env_template` в клоне — `fail`; `config --services` вызван с `--env-file` на шаблон окружения из клона; сервиса нет в ответе `config --services` — `fail` с именем сервиса; подменённый `config --services` возвращает ненулевой код — `fail` с текстом Compose; ответ подменённого `docker compose version --short` `2.39.4-desktop.1` — `ok`, `v2.0.3` — `fail` с найденной версией, `2.1.1` — `ok`; `docker compose version` не отвечает — `fail`; проект с двумя компонентами `compose`, у одного из которых нет Compose-файла в клоне, — одна строка, `fail` с именем этого компонента; подменённый `docker` зависает (`exec sleep <n>`, предел `runner.DOCKER_CALL_TIMEOUT_SEC` подменён на 1; тест снимает записанный pid, группу — только если её номер не равен `os.getpgrp()`) или возвращает ненулевой код — `fail` с текстом вызова, строка завершается за предел. У каждого вызова подменённого `docker` строки (`config --services`, `compose version`) в окружении нет `HOME` пульта и переменной-метки, выставленной тестом в `os.environ`.

AC-6. Необязательный тест с настоящим Docker этой части утверждает: `docker compose version` в окружении шага роли (окружение `role_env` задачи с профилем `compose`, песочница `DOCKER_CONFIG` со ссылкой на дополнение) отвечает версией не ниже 2.1.1. Тест пропускается с именованной причиной при каждом из условий: Docker не отвечает пробе в окружении пульта (вне роли); дополнение Compose не найдено ни в `DOCKER_CONFIG` песочницы, ни в системных каталогах дополнений; выставлена переменная `CI`. Проба Docker для причины пропуска идёт в окружении пульта, утверждение `docker compose version` — в окружении роли: `role_env` без ветки `compose` при отвечающем Docker даёт красный тест, а не пропуск.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны — 5 вне общих зон (`runner.py`,
`doctor/project_checks.py`, `doctor/orphans.py`, `doctor/cli.py`,
`doctor/__init__.py`; порог 5); `budget_usd` $30 ≥ $30; зона задевает
песочницу роли (`runner.role_env`).

Предложение — **обоснование монолита**: задача сама — вторая часть
нарезки родителя 01M6P22XBCQS49HE92YGAB25N9, утверждённой Оператором на
гейте SPEC родителя, с рамкой $30 из ТЗ. Дальнейший разрез возможен только
на «окружение роли» (требования 12, 13) и «`doctor`» (требования 14, 15),
но обе половины опираются на одну публичную константу
`runner.DOCKER_CALL_TIMEOUT_SEC` и функцию `runner.compose_role_dir()` с
её именами записей (строка «забытые стенды» разбирает их), а зона `doctor`
без каталога задачи даёт строку, проверяющую несуществующие каталоги.
Каждая половина — менее $25 планки, деление удорожит работу на шаги
analyst/аудита без выигрыша в мержимости. Решение — за Оператором на
гейте SPEC.
