## Пути обхода гейтов
- П1 (Д1). Требование 14 говорит о «каталоге задачи `<compose_role_dir()>/<id>`
  (ссылка)». Каталоги версий и временная ссылка требования 12 лежат в
  том же `compose_role_dir()`, но их имена и судьба SPEC не задаёт.
  Буквальная реализация может обходить все записи каталога. Тогда каталог
  версии с именем не формы id — это «задача не существует» → `warn`, а
  `--fix` удалит версию живой задачи: ссылка повиснет, `DOCKER_CONFIG`
  роли пропадёт посреди шага. AC-4 «каталог живой задачи на месте»
  удовлетворяется уцелевшей ссылкой. Обратная сторона: осиротевшая
  версия (сбой между сборкой и подменой) не убирается никогда.
- П2 (Д2, Д3). Подменённый `docker` тестов отвечает тем текстом, который
  выберет автор тестов. Версия `2.0.1` против настоящего `Docker Compose
  version v2.39.4-desktop.1` и выдуманный текст отказа `config` против
  текста Compose дают зелёные тесты и неверную строку `doctor` на машине.
  Тот же класс, что формат `Labels`, который решение 7 закрыло.
- П3 (Д4). Строку записи можно реализовать только для `test_profile`:
  AC-5 компоненты не проверяет, а проект с `compose` в компоненте (это
  «задача с профилем `compose`» по требованию 12) получит роль с Docker
  без строки проверки.

## Вердикт
**concerns** — SPEC можно вести дальше, отклонения решаемы Оператором на
гейте:

- Д1 — требования 12/14: имена каталогов версий и временной ссылки в
  `compose_role_dir()` не заданы. Обход строки «забытые стенды» может
  принять версию живой задачи за каталог несуществующей задачи и удалить
  её `--fix`; осиротевшие версии не убираются. AC-4 этого не ловит
  (требуется: каталог версии живой задачи цел, ссылка разрешается). См. П1.
- Д2 — требование 15 / AC-5: форма вывода `docker compose version`
  (префикс `v`, суффикс `-desktop.N`, `--short` или полная строка) не
  закреплена. Подменённый `docker` может отвечать иначе, чем настоящий.
  Опытом не проверено: в окружении шага нет `docker`.
- Д3 — требование 15 / AC-5: признак «отказ `config` из-за файла, которого
  нет в клоне» (по какому тексту Compose) не задан. Текст подменённого
  ответа и распознавание реализации могут разойтись с настоящим Compose.
- Д4 — требование 15 / AC-5: не сказано, проверяется ли запись `compose`
  у компонентов (строка на компонент или на проект). Задача с `compose`
  только в компоненте по требованию 12 — «задача с профилем `compose`».
- Д5 — требование 14: поведение при неполной или испорченной тройке
  `artel.run-*` (нет одной метки, pid не число, время не в формате
  `store.now()`) не задано; `lease.process_alive` поднимет `ValueError`
  (`orchestrator/lease.py:414`), строка зовётся без перехвата
  (`doctor/cli.py:226` — ряд `check_orphans`).
- Д6 — AC-6: не сказано, в каком окружении проверяется причина пропуска
  «Docker не отвечает». Проверка в окружении роли превращает реализацию
  без ветки `compose` в пропуск, а не в красный тест.
- Д7 — требование 12 / AC-1: проверка «адрес `unix://`» читается только
  для вывода `context inspect`. Поведение при `DOCKER_HOST` пульта вида
  `tcp://` и при пустом `DOCKER_HOST` пульта («задан»?) не задано. Часть 1
  (требование 5) откажет такому адресу при прогоне, так что дыры нет, но
  окружение роли получит удалённый демон.
