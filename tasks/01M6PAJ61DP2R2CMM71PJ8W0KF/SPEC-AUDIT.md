Не подтвердилось или не проверено:
- **Ф1. «Сборка — во временный каталог рядом с атомарной заменой
  прежнего» (требование 12) на POSIX так не делается.** Проверено опытом
  во временном каталоге (macOS, Python): `os.replace(a, b)` при непустом
  `b` даёт `[Errno 66] Directory not empty`. Атомарного обмена каталогов в
  stdlib нет: `RENAME_EXCHANGE`/`renamex_np` недоступны, нужна подмена через
  ссылку. Разработчик буквально выполнить требование не может и сделает
  `rmtree` + `rename`, то есть неатомарно. AC-2 атомарность не проверяет.
- **Ф2. Формат `Labels` в `docker ps`/`docker network ls --format
  '{{json .}}'` в SPEC не закреплён («формат Docker»).** По документации
  Docker CLI поле `Labels` в таком выводе — одна строка `k=v,k2=v2`, не
  объект. Опытом не проверено: в окружении шага `docker` нет (`which
  docker` → not found). Если формат не закреплён, автор тестов может
  отдать в подменённом `docker` JSON-объект, а разработчик — разбирать
  объект. Тогда тесты зелёные, а настоящий `doctor` строку не разбирает.
- **Ф3. Поиск дополнения Compose (требование 12).** «Системные каталоги
  дополнений Docker» не перечислены и не названы подменяемым именем.
  Новые версии Docker Desktop кладут дополнение в
  `/Applications/Docker.app/Contents/Resources/cli-plugins` и объявляют
  этот каталог ключом `cliPluginsExtraDirs` в `~/.docker/config.json`, а
  ссылку в `~/.docker/cli-plugins` не ставят. По знанию инструмента,
  опытом не проверено (Docker здесь нет). Значит, на такой машине
  требование даст `OSError` и шаг роли не стартует. См. также В2.
- **Ф4. Проверка `config --services` (требование 15) идёт с `--env-file
  <compose_env_template>` в клоне, где `compose_env_file` нет.** Часть 1
  перед `config` копирует шаблон в `compose_env_file` (SPEC части 1,
  требование 4), то есть Compose-файл проекта может ссылаться на
  `compose_env_file` через `env_file:`. Compose v2 при отсутствии файла
  `env_file:` (без `required: false`) завершает `config` ошибкой. Строка
  `doctor` тогда даст `fail` на исправной записи. По знанию инструмента,
  опытом не проверено.
- Ф5. Остаются «опытом не проверено» SPEC: формат `docker context inspect
  --format '{{.Endpoints.docker.Host}}'` и `docker compose --project-name
  <имя> down -v --remove-orphans` без `-f`. Проверить опытом не удалось —
  в окружении шага нет `docker`. По знанию инструмента оба верны (Compose
  v2 находит ресурсы проекта по меткам), но это не опыт.

Нет причины пропуска «дополнение Compose не найдено в песочнице `DOCKER_CONFIG`». При `DOCKER_CONFIG` песочницы (требование 17: «никогда — настоящий `~/.docker`») дополнение Docker Desktop в песочнице не найдётся, и тест станет красным вместо пропуска (В3) |

Что сделает тест, запущенный до кода (красная фаза):
- AC-1…AC-3 зовут `role_env`. Без кода `compose`-ветки нет, подменённый
  `docker` не вызывается — красный без порождения процессов. Безопасно.
- AC-4/AC-5 до кода падают на `AttributeError` фасада — безопасно.
- **В1 (опасная форма снятия процесса).** Требование 17 и AC-1/AC-4/AC-5:
  «тест снимает группу процессов в `finally`». Реализация не обязана
  запускать `docker` в новой сессии (`start_new_session` SPEC не требует).
  Тогда группа подменённого `docker` = группа самого pytest, и
  `os.killpg(os.getpgid(pid), …)` в `finally` снимет сам процесс теста
  вместе с раннером полного прогона и его рабочими процессами `-n`. Это
  возможно в зелёной фазе и при любой мутации, убирающей
  `start_new_session`. Безопасную форму критерий не задаёт: снимать
  записанный pid (при `exec sleep` это тот же процесс), а группу — только
  если она ≠ `os.getpgrp()`.

## Пути обхода гейтов
- П1. Фильтр «метка `com.docker.compose.project` начинается с `artel-`, а
  меток `artel.run-*` нет» шире, чем стенды пульта. Под него попадёт любой
  чужой Compose-проект Оператора с именем `artel-…` (например, стенд
  разработки самой артели), и `--fix` выполнит ему `down -v`, удалив
  тома. Требование выполнено буквально, а смысл «трогаем только своё»
  обойдён. Имя проекта части 1 строго `artel-<id задачи строчными>-<8 hex>`
  (SPEC части 1, требование 3), так что фильтр можно сузить до этой формы.
- П2. Отказ «раннер compose в песочнице Codex не поддержан» можно поднять
  не-`OSError`-исключением. AC-1 будет выполнен, но настоящий `run`
  упадёт трассировкой мимо журнала «agent run SKIPPED»
  (`runner.py:1821-1827`), и отказ не станет «именованным отказом старта
  шага» (Д2).
- П3. «Атомарная замена» (Ф1) неисполнима и критерием не проверяется.
  Буквальная реализация (`rmtree` + `rename`) оставляет окно без каталога —
  при одном lease на задачу безвредно, но формулировка вводит в
  заблуждение.

гейте:

- Д1 — помощники части 1 (поиск `docker`, окружение требования 6, префикс
  имени, имена меток) в рабочей копии отсутствуют:
  `grep docker orchestrator/acceptance.py` пуст, в `targets.PROFILE_RUNNERS`
  нет `compose` (`orchestrator/targets.py:83`). Часть 1 — на аудите SPEC,
  её публичные имена не закреплены (SPEC части 1, требование 3, называет
  их только описанием). `merge_after` упорядочивает только мерж, а
  `start_after` шаги не держит: шаг роли задачи уже был
  (`orchestrator/merge_after.py:654-660`). SPEC не говорит, как авторам
  тестов и разработчику обращаться к помощникам до мержа части 1 (имена
  или подтяжка main до `tests_writing`).
- Д2 — тип «именованного отказа» (`context inspect`, Codex; требования
  12, 13) не задан, а `run_agent_once` ловит только `OSError`
  (`orchestrator/runner.py:1819-1827`). Нужно: `OSError` (или подкласс),
  либо критерий на исход `run_agent_once`.
- Д3 (В1) — «тест снимает группу процессов в `finally`» (требование 17;
  AC-1, AC-4, AC-5) без безопасной формы: при `docker` в группе pytest
  тест снимет сам себя и раннер прогона. Нужна форма «снять записанный
  pid; группу — только если ≠ `os.getpgrp()`» либо требование
  `start_new_session` к вызовам `docker`.
- Д4 (П1) — фильтр `artel-` без проверки формы имени части 1
  (требование 14): `down -v` чужих проектов `artel-*` с удалением томов.
- Д5 (Ф3, В2) — системные каталоги дополнения Compose не перечислены и не
  подменяемы. AC-2 («без дополнения — `OSError`») недетерминирован на
  машине с системным дополнением. На Docker Desktop с `cliPluginsExtraDirs`
  дополнение не найдётся, и шаг роли не стартует (опытом не проверено).
- Д6 — поведение строки «забытые стенды» при непрочитанном слое проектов
  (`TargetsError`) не задано. Строка регистрируется вне ветки годного
  `targets.load()` (`orchestrator/doctor/cli.py:221-226`), и падение
  уронит весь `doctor`.
- Д7 (Ф2) — формат `Labels` вывода `{{json .}}` не закреплён (строка
  `k=v,…` по документации Docker). Подменённый `docker` тестов может
  разойтись с настоящим.
- Д8 (Ф4) — `config --services` в клоне без `compose_env_file`: ложный
  `fail` при `env_file:` в Compose-файле (опытом не проверено).
- Д9 (Ф1) — «атомарная замена» каталога неисполнима через `os.replace`
  (опыт: `Errno 66 Directory not empty`).
- Д10 (В3) — AC-6: нет положительного утверждения; условие «образа нет»
  неприменимо; нет причины пропуска «дополнение не найдено» при
  `DOCKER_CONFIG` песочницы.
- Д11 (Ф5) — утверждения о Docker CLI («опытом не проверено») проверить
  опытом не удалось: в окружении шага нет `docker`.
