# Ручной мерж для GitHub, часть 2: открытие пары `github` + `target-human`, проверки записи и строки `doctor`

Решение Оператора 01.11 (см. часть 1, задача 01M6M1799YCY5HXMHHD71SHJET); решения Оператора 04.11 по этой части («ок по рекомендациям») — требования 3, 7–9. Эта задача открывает пару после того, как часть 1 дала `_GitHub` функции MR. Номера строк — по origin/main 92bdb87b7; часть 1 смержена 05.11 (main 904cb6ed) — аналитик сверяет номера по коду.

## Факты

1. Поддержанные значения и пары: `SUPPORTED_FORGES = ("github", "gitlab")`, `SUPPORTED_MERGE_GATES = ("operator", "target-human")`, `SUPPORTED_PAIRS = {("github", "operator"), ("gitlab", "target-human")}`; комментарий над ними объясняет, почему `github` + `target-human` закрыта (`orchestrator/targets.py:25-33`).
2. Отказ неподдержанной пары — `targets.unsupported_reason`: текст «гейт мержа <г> не поддержан для хостинга <х> (поддержаны: <перечень `sorted(SUPPORTED_PAIRS)`>)» (`orchestrator/targets.py:292-313`). Его ставят `new` (`orchestrator/catalog.py:856`), `run`/`auto` (`orchestrator/runner.py:294-298`), `approve`; строка `doctor` `project-support-<проект>` — `fail` с причиной, иначе `ok` (`orchestrator/doctor/cli.py:36-47`).
3. Проверки записи доставки через MR — `_check_delivery` (`orchestrator/targets.py:622-726`): `branch_template`, `ref_pattern`, `squash_before_mr`, `freshness`, `commit_template`, `commit_author`, `co_author`, `push_options`, `push_options_forbidden`, `ci_required_jobs`, `mr_assignee`, `draft_mr`, `max_in_flight`, `max_awaiting`, `awaiting_holds_zones`, `mr_sync_interval_min`; значение `forge` в них не участвует. Полный набор из CI (`full_suite: ci|both`) запись принимает только у хостинга, реализация которого читает отчёт задания (`orchestrator/targets.py:1137-1160`); у `_GitHub` функции `job_test_report` нет (часть 1, требование 7) — такая запись GitHub отказывает при загрузке.
4. Строки `doctor` записи: `project_entry_checks` выбирает путь GitHub или GitLab по `forge.ci_by_pipeline`, без литерала (`orchestrator/doctor/project_checks.py:37-69`); для записи с `target-human` добавляет `project-ci-file-no-paths-<проект>` (только при компоненте с `full_suite` ci/both) и `project-submodules-<проект>` (`orchestrator/doctor/project_checks.py:70-75`).
5. `project-ci-file-no-paths` проверяет только файл GitLab `CI_FILE = ".gitlab-ci.yml"` (`orchestrator/doctor/project_checks.py:668`, `orchestrator/doctor/project_checks.py:740-750`); `project-ci-reruns-<проект>-<к>` строится для `target-human` при `full_suite` ci/both и разбирает тот же файл (`orchestrator/doctor/project_checks.py:450-452`, `orchestrator/doctor/project_checks.py:1266-1303`). Для GitHub обе строки достижимы только при `full_suite` ci/both, которое запись GitHub не примет (факт 3).
6. Не зависят от хостинга: `project-submodules` (`orchestrator/doctor/project_checks.py:1361-1372`), сверка хука `pre-push` и файла политики проекта `target-human` (`orchestrator/doctor/git_hooks.py:262-266`, `orchestrator/doctor/git_hooks.py:329-334`; каталог хуков — `orchestrator/gitcmd.py:279-288`); сам хук сравнивает ссылки по шаблону ветки и не знает хостинга (`scripts/git-hooks/target-human/pre-push`); точка отправки проверяет белый список по `merge_gate`, не по `forge` (`orchestrator/gitcmd.py:1199-1207`, `orchestrator/gitcmd.py:1241-1246`).
7. Строка срока токена строится только у реализации с `token_expiry` (`orchestrator/doctor/misc_checks.py:160-174`, вызов — `orchestrator/doctor/cli.py:206`); у GitHub её нет, и тест закрепляет отсутствие строки (`tests/test_01m5wcxbr9k8cn586w1ap3zn6q_gitlab_doctor_probe.py:544-566`).
8. `kill` задачи проекта с `target-human` после отправки ветки не трогает сервер — ни ветку, ни PR (`orchestrator/cleanup.py:296-302`, `orchestrator/cleanup.py:319-333`); закрытие PR `gh pr close` идёт только иначе (`orchestrator/cleanup.py:311-312`).
9. Сторож литералов `forge`/`merge_gate` вне `orchestrator/targets.py` — `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:425-488`.
10. Повтор CI пультом: на красном CI гейт зовёт `fsm_merge_gate._ci_confirm_red_or_flake` (`orchestrator/fsm_merge_gate.py:297-320`) → `ci.trigger_rerun` (`orchestrator/ci.py:1793-1837`); для хостинга с конвейерами (GitLab, `forge.ci_by_pipeline`) повтор отказан («ре-ран CI не запущен: … не поддержано»), для GitHub — настоящие `gh run rerun [--failed]` и `gh run watch` в репозитории проекта. Тот же `trigger_rerun` зовёт команда Оператора `ci-rerun` (`orchestrator/ci_rerun.py:231`, `:308`). ADR-0029, «Не входит», исключает запуск заданий конвейера проекта пультом.
11. `policy.ci_required_jobs` читает только `gitlab_adapter._required` (`orchestrator/gitlab_adapter.py:417-418`); `_GitHub.pipeline_status` поле не видит, пропущенная проверка `skipped` считается зелёной (`orchestrator/ci.py:27`) — запись GitHub с этим полем загрузится, а гарантия пропадёт.
12. `kill`: для записи с `target-human` после отправки ветки сервер не трогается (`cleanup._server_left_to_project_people`, `orchestrator/cleanup.py:319-333`); ДО отправки уборка идёт обычным путём и для `forge: github` зовёт `_close_project_pr` → `gh pr close` (`orchestrator/cleanup.py:311-312`, `:245`) — у GitLab закрытия PR в этом пути нет.
13. Строка `project-ci-file-no-paths` строится в `project_entry_checks` только при компоненте с `full_suite` ci/both (`orchestrator/doctor/project_checks.py:70-73`), а такую запись GitHub не примет (факт 3) — для GitHub строка не появится ни разу. `config.is_protected_path` (`orchestrator/config.py:818`) понимает записи `**/<имя>`, `**/<каталог>/` и префиксы; маски вида `*` не понимает (нынешняя проверка GitLab принимает `*` через `project_profile.mask_matches`, а гейт её не применяет — расхождение, строка копилки).

## Требуется

1. **Открыть пару**: `SUPPORTED_PAIRS` — `{("github", "operator"), ("github", "target-human"), ("gitlab", "target-human")}`; комментарий `orchestrator/targets.py:25-30` — по новому составу. Неподдержанной остаётся `gitlab` + `operator`; текст её причины меняется только перечнем пар (`unsupported_reason` не правится).
2. **Те же проверки записи**: запись `github` + `target-human` проходит ровно через `_check_delivery` и правило `full_suite` (факт 3) — без новых исключений для GitHub; отличия, если аналитик их найдёт при сверке кода, — эскалация с перечнем, не правка.
3. **`project-ci-file-no-paths` для GitHub** (решение Оператора 04.11, п. 4): для записи с `target-human` хостинга без конвейеров (`not forge.ci_by_pipeline`, без литерала — факт 9) строка строится ВСЕГДА, без условия `full_suite`; для GitLab — прежнее условие (факт 13). Проверяемый путь — по реализации хостинга: GitLab — файл `.gitlab-ci.yml`, как сейчас; GitHub — каталог `.github/workflows/`: `ok`, если `config.is_protected_path(".github/workflows/<любой файл>", no_paths записи)` истинно — любой записью, для которой формула истинна (например, `.github/workflows/`, `.github/`, `**/workflows/`); иначе `fail` с именем каталога. Маски вида `*` для GitHub не принимаются (формула гейта их не применяет).
4. **Явные исходы прочих строк для GitHub** `target-human` — закрепить тестами без правки кода, если поведение уже такое: `project-support` — `ok`; `project-submodules` и строки хука `pre-push` — есть; `project-ci-reruns` — нет (полный набор из CI запись GitHub не примет); `token-expiry` — нет (факт 7). Если сверка покажет иное — эскалация.
5. **Полный цикл в песочнице**: задача вымышленного проекта `github` + `target-human` от входа в `verifying` (черновой PR открыт `ensure_forge_draft_mr`) → `approve` на `merge_gate` → `awaiting_human` (черновик снят, исполнитель назначен) → вливание в локальном `origin` → `mr-sync` «влит этим MR» → `mr-sync --confirm` → `done`; `kill` такой задачи после отправки — ветка и PR не тронуты, `gh pr close` не вызван.
6. **Документация**: `docs/codebase-map.md` — описания затронутых тестов и строк `doctor`.
7. **Без повтора CI в проекте людей** (решение Оператора 04.11, п. 1): `ci.trigger_rerun` для клона проекта с `targets.merged_by_project_people` не зовёт `gh` и возвращает «ре-ран CI не запущен: …» с причиной (как отказ GitLab), до любого вызова `gh`; исход гейта на красном CI — прежний путь неудачного повтора (`orchestrator/fsm_merge_gate.py:320-338`): запись `flake-rate` «повтор не запущен: …», выход «merge отклонён: <статус> … задача осталась на гейте merge», задача на `merge_gate`; команда Оператора `ci-rerun` для такого проекта отказывает тем же текстом. Для артели и записей `operator` (в том числе GitHub) поведение прежнее.
8. **`ci_required_jobs` только у хостинга, который его читает** (п. 2): запись проекта людей (`targets.merged_by_project_people`), у которой задано `policy.ci_required_jobs`, а реализация хостинга в реестре `forge` поле не читает (признак реализации, по образцу `_check_full_suite_source`, `orchestrator/targets.py:1137-1160`; не литерал), отказывает при загрузке с именем поля и хостинга. GitLab и записи `operator` (в том числе `github` + `operator`, `tests/test_01m5wdb7f14sq30qvwjy2xybg2_record_fields.py:55-68`, `:233`) — без изменений.
9. **`kill` не закрывает PR проекта людей** (п. 3): для записи с `targets.merged_by_project_people` уборка `gh pr close` не зовёт ни до, ни после отправки ветки; до отправки удаляется только ветка origin задачи, если она есть; для записи, у которой прежде закрывался бы PR (хостинг без конвейеров), журнал уборки называет «PR не тронут: MR вливают люди проекта»; для GitLab `target-human` запись журнала прежняя. Для `github` + `operator` закрытие PR прежнее.

Критерии приёмки:
- `unsupported_reason` для `github` + `target-human` — `None`; `new`, `run`, `auto`, `approve` такой записи не отказывают причиной поддержки; `project-support` — `ok`;
- `gitlab` + `operator` — по-прежнему отказ `new`, `run`, `auto`, `approve`, `fail` строки `project-support`; текст причины — с перечнем «github + operator, github + target-human, gitlab + target-human»;
