# SPEC: Единый коммит результата роли через пульт для всех провайдеров

## Контекст
Разработчик на Codex (песочница `workspace-write`) меняет код в worktree
задачи, но `git add` получает отказ: индекс git worktree лежит вне
рабочего каталога шага (`.git/worktrees/<имя>/index` главной копии).
Миссия developer (`orchestrator/role_prompt.py`, пункт 4 «закоммить код в
ветку») и скил `coding-standards.md` («ход разработчика заканчивается
коммитом кода», коммит пультом — «дефект шага») требуют коммита от роли,
поэтому роль ставит PLAN `status: escalate`. Затем пульт успешно
коммитит код (`checkpoint.commit_success_checkpoint`, SPEC
01M283NC4JJXK7QS68Y9ET8TBK), но задача всё равно уходит в `escalated` по
PLAN. Так было в 01M3SX69E8P64D77J1XTHMHE40 и 01M3V4ZPB6HFDJ36MTDAQG5VNT.
У Claude другой режим разрешений, поэтому там дефект не проявляется. Есть
и другой пробел: отказ git внутри `_commit_worktree_change` сейчас
проходит молча, и следующий `advance` объясняет грязную копию текстом
«роль обязана коммитить» (`fsm._dirty_refuses`).

Цель задачи: штатный коммит кода по итогам шага одинаково для обоих
провайдеров делает пульт. Он делает это существующим механизмом
(`checkpoint.py`, аварийный автокоммит 01M283NC4JJXK7QS68Y9ET8TBK и
зонный фильтр 01M290PVYG2VJK6442H5BAX9MA), без второго механизма. Роль
сдаёт код, проверки и свой артефакт.

## Требования
1. Контракт роли. Миссии ролей не требуют от роли выполнять `git add`/
   `git commit` для кода. Миссия developer прямо сообщает, что код,
   оставленный в worktree, по итогам шага коммитит пульт.
2. Штатное завершение шага developer (rc=0, обязательный артефакт на
   месте, поток не оборван). Незакоммиченные изменения worktree вне
   `tasks/<id>/` в пределах мандата и зон пульт коммитит существующим
   механизмом `checkpoint.py` до записи «agent run finished» и до любого
   перехода состояния. Коммит делается служебной идентичностью
   (`fixation.FIXATION_AUTHOR_*`), за ним следует перефиксация sha
   (`store.record_fixation`). Поведение не зависит от провайдера роли
   (`claude`/`codex`).
3. Успешный штатный коммит пульта — норма, не дефект роли. Исход шага
   остаётся «ok». Алерт не заводится, запись провала или отказа в
   журнал не пишется. Запись журнала об этом коммите называет sha и
   закоммиченные пути и не квалифицирует его как дефект или нарушение
   роли.
4. Реальная ошибка коммита пульта (ненулевой код возврата git на любой
   операции коммита, кроме случая «нечего коммитить») не проходит молча.
   Журнал получает запись с именем операции git и текстом ошибки git.
   Изменения остаются в worktree, не откатываются и не теряются. Задача
   не переходит из текущего состояния, пока коммит не состоится. Текст
   отказа последующего `advance` по грязной копии называет незакоммиченный
   результат шага. Он не утверждает, что коммитить обязана роль.
5. Пульт не присваивает чужие изменения. Пути вне зон задачи
   (`checkpoint._zone_paths`) не попадают в коммит пульта, остаются в
   worktree и журналируются одной записью `STRAY_WORKTREE_FILES_ACTION`.
   `tasks/<id>/` в кодовую ветку не коммитится: он уходит в артефактную
   ветку, как сейчас.
6. Повторное завершение и уже существующие коммиты. Если коммитить
   нечего (роль закоммитила всё сама либо завершение повторено без новых
   изменений), пульт не создаёт ни пустого, ни дублирующего коммита.
   Собственные коммиты роли в ветке задачи пульт не переписывает, не
   амендит и не сквошит. Если роль закоммитила часть изменений, пульт
   коммитит только оставшийся незакоммиченный остаток. Существующие
   коммиты роли проходят те же гейты выхода из `in_dev` (зоны, защищённые
   пути, лок тестов), что и коммит пульта.
7. Содержательная эскалация роли сохраняется. PLAN со `status: escalate`
   уводит задачу в `escalated` при `advance` и тогда, когда пульт успешно
   закоммитил код этого шага. Автоматически эскалация не снимается.
8. test_author — мандат не расширяется. Пульт коммитит в кодовую ветку
   только собственные долгоживущие файлы задачи
   (`tests/test_<префикс задачи>_*.py`, пока задача в `tests_writing`),
   прочие изменения вне `tasks/<id>/` откатываются с записью в журнал. Это
   прежнее поведение `_test_author_checkpoint`. Отказ git при коммите этих
   файлов подчиняется требованию 4: запись
   `TEST_AUTHOR_NOT_COMMITTED_ACTION` несёт операцию git и текст его
   ошибки, файлы остаются в worktree. Роли analyst и reviewer мандата
   кода не получают.
9. Внешний target (`target` ≠ `config.DEFAULT_TARGET`). Поведение
   прежнее: workspace внешнего target пульт не коммитит (ADR-0003 §4;
   `commit_success_checkpoint`/`_wip_checkpoint` возвращают пусто). Ни
   коммита в workspace, ни коммита в `config.ROOT`, ни новых прав ролям
   эта задача не вводит. Артефакты по-прежнему переносятся
   `_commit_external_step_artifacts`.
10. Песочница не расширяется. Команда шага Codex сохраняет
    `--sandbox workspace-write` без новых доступных на запись корней.
    Набор разрешённых инструментов и режим разрешений шага Claude не
    расширяются.
11. Сохраняются без изменения поведения: зонные проверки, защита main,
    лок приёмочных и долгоживущих тестов, ограничения ролей, разделение
    кодовой и артефактной веток, lease, аварийные WIP-чекпоинты (таймаут,
    rc≠0, обрыв потока, `pause --now`) и фиксация SHA.
12. Документация. `docs/stack.md` описывает правило: штатный коммит кода
    результата шага делает пульт для обоих провайдеров, роль коммитить не
    обязана. `docs/operator-session.md` описывает, что Оператор видит в
    журнале при отказе git на коммите пульта и как это разобрать.
13. Приложение для Оператора к PLAN.md (защищённые пути роль не правит).
    Это unified-диф к `skills/coding-standards.md` (раздел «Завершение
    хода»: убрать требование заканчивать ход коммитом и квалификацию
    коммита пультом как дефекта) и к `skills/conventions-core.md` (строки
    о том, что роль коммитит код, и о регенерации карты «тем же
    коммитом»). Диф проверен `git apply --check`. `templates/` правок не
    требует: ни один шаблон не требует от роли коммита кода.

## Критерии приёмки
AC-1. Текст миссии developer, который собирает `role_prompt.mission_brief_package`, не содержит требования закоммитить код и сообщает, что незакоммиченный код worktree по итогам шага коммитит пульт. Ни одна из миссий analyst/test_author/developer/reviewer не требует от роли выполнить `git add` или `git commit`.

AC-2. Шаг developer задачи target `artel` завершается штатно (rc=0, PLAN.md на месте), в worktree остаются незакоммиченные изменения в пределах зон. Тогда голова ветки задачи содержит эти изменения одним новым коммитом служебной идентичности пульта, исход шага — «ok». Коммит появляется в журнале раньше записи «agent run finished», и задача на этот момент ещё не сменила состояние.

AC-3. Регрессия Codex с недоступным git index. Шаг developer с провайдером `codex` оставил изменения кода незакоммиченными (роль не смогла записать индекс) и PLAN.md `status: ready`. Пульт коммитит изменения, и следующий `advance` из `in_dev` не отказывает по грязной копии и не уводит задачу в `escalated`.

AC-4. Регрессия Claude. Тот же сценарий, что в AC-3, с провайдером `claude` даёт тот же результат: изменения закоммичены пультом, исход шага «ok», `advance` не отказывает по грязной копии.

AC-5. Успешный штатный коммит пульта не заводит алерт и не пишет в журнал запись провала или отказа шага. Запись о коммите называет sha и закоммиченные пути и не содержит слов «дефект» или «нарушение».

AC-6. Отказ git пульта. Операция коммита пульта (`add`, `reset` или `commit`) возвращает ненулевой код, и это не случай «нечего коммитить». Тогда журнал несёт запись с именем этой операции git и текстом ошибки git, а изменения остаются в worktree незакоммиченными и не откаченными. Последующий `advance` не переводит задачу из `in_dev`, и текст его отказа не утверждает, что коммитить обязана роль.

AC-7. Посторонние файлы. Шаг developer оставил незакоммиченными изменения в зоне задачи и файл вне её зон. Тогда коммит пульта содержит только изменения в зоне, посторонний файл остаётся в worktree незакоммиченным, а журнал несёт одну запись `STRAY_WORKTREE_FILES_ACTION` с его путём. Файлы `tasks/<id>/` в кодовый коммит не попадают.

AC-8. Повтор завершения. Повторный вызов штатного завершения шага developer без новых изменений в worktree не меняет голову ветки задачи и не пишет в журнал второй записи о коммите пульта.

AC-9. Существующие коммиты роли. Роль закоммитила часть изменений сама, остальное оставила в worktree. Тогда после завершения шага собственный коммит роли остаётся в истории ветки неизменным (тот же sha, предок головы), а пульт добавляет ровно один коммит с оставшимися изменениями. Если роль закоммитила всё, пульт не добавляет коммита.

AC-10. Содержательная эскалация. Шаг developer оставил PLAN.md `status: escalate` и незакоммиченный код, пульт успешно закоммитил код. Тогда `advance` переводит задачу в `escalated`.

AC-11. test_author. В `tests_writing` шаг test_author оставил свой новый файл `tests/test_<префикс задачи>_<имя>.py` и правку чужого файла `tests/`. Тогда пульт коммитит только свой файл, правка чужого файла откачена с записью в журнал. При отказе git на коммите своего файла запись `TEST_AUTHOR_NOT_COMMITTED_ACTION` содержит имя операции git и текст его ошибки, а файл остаётся в worktree.

AC-12. Внешний target. Для задачи с target ≠ `artel` штатное завершение шага developer не создаёт коммитов ни в workspace target'а, ни в репозитории пульта и не пишет в журнал записей о коммите пульта или его отказе.

AC-13. Песочница. Команда шага провайдера `codex` содержит `--sandbox workspace-write` и не содержит дополнительных доступных на запись корней. Команда шага `claude` несёт тот же набор разрешённых инструментов и тот же режим разрешений, что до задачи.

AC-14. `docs/stack.md` содержит правило: штатный коммит кода результата шага делает пульт одинаково для `claude` и `codex`. `docs/operator-session.md` содержит описание записи журнала при отказе git на коммите пульта и порядок разбора.

AC-15. PLAN.md несёт приложение-диф к `skills/coding-standards.md` и `skills/conventions-core.md`. Оно убирает требование, чтобы роль заканчивала ход коммитом кода, и квалификацию коммита пультом как дефекта шага. Диф применяется `git apply --check` на чистом дереве ветки.

## Оценка объёма и деление
Сработавшие сигналы:
- в зоне 7 путей (порог 5);
- 15 критериев приёмки (порог 10);
- зона `orchestrator/checkpoint.py` задевает механизм фиксации SHA и
  WIP-чекпоинтов, на который опираются записи `docs/invariants.md`.

Решение — обоснование монолита (утверждает Оператор на гейте SPEC):
- Механика — одна. Изменения кода сосредоточены в одной обвязке
  (`checkpoint._commit_worktree_change` и её вызов в
  `runner._finish_ok`) плюс текст отказа `fsm._dirty_refuses`. Остальные
  пути зоны — текст миссии (`role_prompt.py`) и два документа.
- Регрессия, ради которой задача заведена (AC-3: Codex с недоступным
  индексом), закрывается только сменой контракта и механики вместе.
  Часть «только механика» оставляет миссию с требованием коммита, и
  Codex продолжит эскалировать PLAN. Часть «только контракт» снимает
  требование коммита, пока отказ git пульта остаётся молчаливым: роль
  больше не коммитит, а сбой коммита пульта не останавливает задачу с
  причиной. Это худшее промежуточное состояние, чем сегодняшнее.
- Деление удвоило бы постоянную часть цены (analyst, test_author и
  ревью на каждую часть) при объёме, который укладывается в класс ~$45.

## Не входит
- Исправление авторизации канарейки.
- Миграция хуков.
- Автоматические approve, merge и deploy.
- Снятие содержательных эскалаций роли (PLAN/REVIEW `status: escalate`,
  `QUESTIONS.md`, пометки `AC-n: escalate`).
- Второй механизм коммита рядом с `checkpoint.py`: аварийный автокоммит
  (01M283NC4JJXK7QS68Y9ET8TBK) и зонный фильтр
  (01M290PVYG2VJK6442H5BAX9MA) переиспользуются.
- Расширение песочницы или прав любой роли, в том числе права коммитить
  для analyst и reviewer, и мандата test_author.
- Коммит кода пультом для внешнего target (workspace ADR-0003 §4) —
  поведение сохраняется, см. требование 9.
- Прямая правка `skills/` и `templates/`: только приложение к PLAN.md для
  Оператора (требование 13).
- `orchestrator/brief.py` и несуществующий `orchestrator/agent_prompt.py`
  из зон ТЗ. Миссии ролей собирает `orchestrator/role_prompt.py`, бриф
  developer подтягивает скилы как есть, правка `brief.py` не нужна.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность
  защищённых путей и непревышение бюджета — их держит пульт.
