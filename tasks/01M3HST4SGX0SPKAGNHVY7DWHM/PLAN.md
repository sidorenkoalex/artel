# PLAN: Команды note и doc-commit: единый формат строки, применение заготовки документа, тесты перед коммитом конфигурации

## Подход

Вся правка кода — в двух файлах зоны (`orchestrator/notes.py`,
`orchestrator/artel.py`), плюс `docs/operator-session.md` и `tests/`.
Три содержательных блока ложатся на уже существующий путь записи
(«fetch origin → построить правку → сверить → commit → push», `_run` /
`_fetch_and_build` / `_commit_and_push`), не заводя второго:

1. **Формат строки** (требования 1–8) — внутри чистых функций
   `_apply_insert` / `_apply_append` / `_apply_set_priority`. Обрамление
   снимается ТЕМ ЖЕ `_row_cells` (:154), которым сегодня читается шапка
   раздела: один разбор строки на весь модуль вместо двух (сегодняшний
   собственный `text.split("|")` в `_apply_insert` :181 — и есть причина
   трёх отказов 27.09). Колонки, форма которых нормализуется, находятся
   по ЗАГОЛОВКУ шапки («П», «Дата»), не по номеру: колонка «Дата» есть у
   «Копилки» и отсутствует у «Бэклога»/«Очереди Оператора» (замер
   «Материалов» SPEC подтверждён на вершине — см. «Влияние на систему»).
2. **`note --apply`** (требования 9–12) — новый вид записи
   (`APPLY_KIND = "apply"`) в том же JSON-формате `_hold_pending`, что
   `note` и `doc-commit`: окно тишины, удержание, общий `--flush` и
   изолированный рабочий репозиторий достаются бесплатно, ветвление —
   ровно в двух точках (`_fetch_and_build`, `_commit_and_push`), тем же
   приёмом, которым в модуль вошёл `doc-commit`. Сверка базы — та же
   функция сравнения blob-sha, что у `_build_doc_commit` (:373).
3. **Гейт полного набора** (требования 13–16) — одна функция
   `_suite_gate_refusal`, вызываемая из `_commit_and_push` СРАЗУ ПОСЛЕ
   записи правки в дерево рабочего репозитория и ДО `git commit`: это и
   есть «дерево с УЖЕ применённой правкой» требования 13, и это же место
   даёт правильное поведение на обоих путях — при открытом окне тишины
   запись удерживается, вовсе не запуская прогон (она ещё не
   отправляется), а прогон случается на `--flush`, когда отправка
   действительно идёт. Прогон — существующий единственный вход
   `acceptance.run_full_suite(root)`; он же отдаёт «не зелено» на
   «набор не запустился вовсе» (`tests/` в дереве нет), чем требование
   14 закрывается без отдельной ветки.

Бюджет SPEC ($45) не переоценивается: зона — два файла кода, шагов пять,
расхождения с оценкой SPEC нет.

**Оговорка по требованию 18** (подробно — «Риски», п. 1): приложение
даёт Оператору не замороженный снимок `docs/backlog.md` целиком (244 КиБ
на вершине b21f01e6), а детерминированный генератор заготовки от
АКТУАЛЬНОГО origin/main плюс замер того, что он изменит. Причина не в
объёме: снимок, сделанный сегодня, к моменту применения потеряет все
строки, дописанные в бэклог за это время, и требование 12 честно
перечислит их как удалённые — уже после того, как они будут удалены.

## Шаги

1. **Формат строки `note`** (`orchestrator/notes.py`): разбор
   вставляемого текста через `_row_cells`; сверка числа ячеек — после
   снятия обрамления; нормализация приоритета (`_normalized_priority`,
   цифра 1–4, допускается ведущая «П»/«п») с именованным отказом,
   несущим пример формы; нормализация даты (`_normalized_date`, год
   снимается, прочее не трогается); дописка состояния с разделителем
   `— <ДД.ММ>: ` и без ведущего разделителя у пустой ячейки; флаг
   `--state` как второе имя `--append`. Немой вариант поиска шапки
   раздела (`_table_header_cells`) — общий с шагом 2, выделяется здесь,
   `_find_table_header` остаётся его говорящей обёрткой.
2. **`note --apply <файл> --message "<основание>"`** (тот же файл):
   вид записи `apply`; `_build_apply` — сверка базы (blob-sha
   `FETCH_HEAD:docs/backlog.md` против `HEAD:docs/backlog.md` пина),
   отказ «заготовка совпадает с origin» (иначе `git commit` не найдёт
   изменений и запись повиснет в `notes-pending/` без внятной причины),
   сверка формы заготовки (`_apply_shape_refusal`: три раздела, у
   каждого таблица, число колонок шапки как в origin); перечень
   удалённых строк (`_dropped_rows`, усечение до 80 знаков тем же
   приёмом, что сообщение коммита `note --drop`) → запись журнала
   пульта; сообщение коммита несёт `--message` целиком.
3. **Гейт полного набора `tests/` перед коммитом конфигурации** (тот же
   файл): `_suite_gate_refusal` на путях `DOC_COMMIT_CONFIG_PATHS` и
   только на них; `doc-commit … --accept-red "<основание>"` —
   осознанный обход с обязательным основанием и записью журнала
   (путь + основание), по идиоме `artel._accept_red_arg` /
   `approve --accept-red`.
4. **Документация** (`docs/operator-session.md`, докстринг
   `orchestrator/artel.py`): обе формы строки `note`, нормализованные
   формы приоритета и даты, разделитель дописки состояния,
   `note --apply`; в справке CLI — `note --apply` и `--accept-red` у
   `doc-commit`.
5. **Тесты** (`tests/`): три новых файла регрессов
   (`test_notes_row_format.py`, `test_notes_apply.py`,
   `test_doc_commit_suite_gate.py`); адаптация значений-фикстур
   приоритета в `tests/test_notes.py` и `tests/test_doc_commit.py`
   (подробно — «Влияние на систему») и посев зелёного `tests/` в
   `DocCommitSandbox`. Прогон планки задачи и затронутых модулей.
6. **Замечания ревью итерации 1** (тот же файл кода плюс
   `docs/operator-session.md` и регрессы): чистота общего рабочего
   репозитория `.artel/notes-work` (`_restore_tree` перед выходом гейта,
   принудительный checkout с проверкой кода возврата, сверка «уже
   совпадает» по blob-sha вместо файла дерева — R1-F1); своя сверка базы
   `--apply` вместо пиновой (`_foreign_base_refusal` плюс `base_blob`
   записи — R1-F2); попутный флаш не заводит прогон набора и отказ при
   флаше больше не молчит (`_flush_pending(explicit)` — R1-F3); запись
   журнала об обходе только на пути конфигурации (R1-F4); сверка примера
   формы приоритета в регрессах (R1-F5). Разметка каждой записи реестра
   REVIEW.md — там же, с описанием сделанного.

## Влияние на систему

**Что затрагивается за пределами правки.** `orchestrator/notes.py` зовут
`orchestrator/artel.py` (диспетчер), `orchestrator/doctor/misc_checks.py`
(`pending_notes()` — формат записи не меняется, новые поля `accept_red` и
`base_blob` необязательные: проверка считает записи, а не разбирает их
поля) и документация. Новых вызовов git три, все через `orchestrator/
gitcmd.py` без его правки: `clean -f -- <путь>` и `checkout -f`
(приведение дерева рабочего репозитория), `log --format` (свой ли коммит
тронул документ), `hash-object --stdin` через существующую
`gitcmd.carpentry` (blob-sha содержимого, единственная точка `subprocess`
плотницкой записи — её же подменяет песочница тестов). Публичные имена модуля
(`cmd_note`, `cmd_doc_commit`, `pending_notes`,
`DOC_COMMIT_CONFIG_PATHS`, `BACKLOG_REL`, `DOC_COMMIT_KIND`,
`DOC_COMMIT_BASE_REFUSAL`, `DOC_COMMIT_FOREIGN_REFUSAL`) сохраняются —
на них опираются `tests/test_doc_commit.py` и стенд залоченной планки.
Новый импорт `orchestrator/acceptance.py` в `notes.py` цикла не даёт:
`acceptance` тянет `agent_log`/`ci`/`config`/`gitcmd`/`stack` и
`scripts/guard.py`, ни один из них `notes` не импортирует (проверено
по блоку «Импортирует» карты кодовой базы).

**Инварианты, гейты, лимиты рядом — и почему не ослабляются.**

- Гейт неослабления тестов (`advance_gates/test_integrity.py`) видит
  удаление/переименование файлов `tests/`, исчезнувшие тестовые методы и
  появившиеся маркеры пропуска. Ни одного из трёх в правке нет: файлы и
  методы на месте, скипов не добавляется, новые тесты только
  добавляются.
- `doc-commit` не ослабляется ни в одной существующей сверке: список
  допустимых путей, сверка базы с пином, разбор `--from`, рубеж
  окружения роли, окно тишины и удержание остаются прежними; гейт
  набора — ДОБАВЛЕННАЯ сверка, единственный её обход
  (`--accept-red`) требует основания и пишет журнал.
- Сверка числа колонок у `note` (требование 2) сохраняется и после
  снятия обрамления становится СТРОЖЕ, не слабее: сегодня «| 1 | 2 | 3 |»
  проходит как пять ячеек с двумя пустыми, после правки — отказ.
- Диапазон приоритета 1–4 сохраняется: новая форма («П2») добавляется к
  приёму, границы не расширяются (охраняется тестом планки AC-4 и
  существующими `ApplySetPriorityTest`).
- Нового промежуточного состояния FSM, правок `gates.yaml`/`roles.yaml`/
  `templates/`/`skills/`/`.github/`, `docs/invariants.md` и
  `tests/test_invariants.py` задача не делает.

**Адаптация значений-фикстур в двух существующих тестовых файлах —
честно и явно.** `tests/test_notes.py` и `tests/test_doc_commit.py`
вставляют строки с ячейкой приоритета **«9»** (13 мест: `test_notes.py`
:59, :63–64 и десять вызовов `cmd_note` в стендах окна тишины;
`test_doc_commit.py` :509, :550, :575). Требования 3–4 SPEC и критерий
AC-4 залоченной планки предписывают отказ любому приоритету вне 1–4 —
значит «9» становится отказом, и девять существующих тестов покраснели
бы не по своему предмету (место вставки строки, окно тишины, общий флаш
двух видов записей), а по значению фикстуры, к их предмету отношения не
имеющему. Правка — замена значения ячейки приоритета «9» → «4» (и
соответствующей ожидаемой строки в `test_notes.py` :63–64). Ни один
ассерт, сценарий, тест или файл при этом не удаляется, не
переименовывается и не скипается — машинный рубеж неослабления
(`test_integrity.findings`) такую правку находкой не считает, и по
существу она ослаблением не является: проверяемое поведение остаётся то
же. Требование 8/19 SPEC («`tests/test_notes.py` остаётся зелёным и не
ослабляется») иначе неисполнимо вместе с требованиями 3–4 — это
единственный способ выполнить оба.

Второе такое же место: `test_doc_commit.py::
test_config_path_gets_config_prefix_docs_path_gets_docs_prefix` коммитит
`roles.yaml`, а стенд `DocCommitSandbox` дерева `tests/` не несёт — по
требованию 14 это «набор не запустился» и, значит, отказ. Вместо правки
самого вызова в `DocCommitSandbox.setUp` сеется тривиально ЗЕЛЁНЫЙ
`tests/test_ok.py`: вызов и все ассерты теста остаются байт-в-байт, а
зелёный путь гейта заодно получает постоянный регресс.

**Откат.** Revert одного merge-коммита ветки: правка целиком аддитивна
(новые функции, новые флаги, новые тестовые файлы), состояния в БД не
заводит, схему не мигрирует, файлов на диске не переносит. Записи
журнала прошлых вызовов после откатов остаются в `steps` — они
read-only и ничему не мешают.

## Риски

1. **Требование 18 в буквальной форме («полное содержимое файла»
   приложением) опасно, и приложение даёт другую форму.**
   `docs/backlog.md` на вершине `origin/main` (b21f01e6) — 244 584
   байта / 258 строк. Замороженный снимок такого файла, применённый
   `note --apply` через день, БЕЗВОЗВРАТНО снимет все строки, дописанные
   за этот день (а бэклог по конвенции CLAUDE.md пополняется в момент
   обнаружения аномалии, то есть ежедневно): сверка базы требования 10
   этого не поймает — она сравнивает origin с пином главной копии, а не
   с версией, от которой готовилась заготовка, — и требование 12 честно
   перечислит потерянные строки уже ПОСЛЕ потери. Поэтому приложение
   ниже даёт детерминированный генератор заготовки от АКТУАЛЬНОГО
   содержимого плюс замер того, что он изменит (43 ячейки приоритета,
   7 ячеек даты на вершине b21f01e6). Если Оператор предпочитает
   замороженный снимок целиком — скажи, добавлю его отдельным файлом
   `tasks/<id>/backlog-draft.txt` (не `.md`: белый список
   `guard.TASK_ROOT_ALLOWED_MD` `.md`-имён в корне каталога задачи
   закрыт, файл другого расширения легален).
2. **Прогон полного набора удлиняет `doc-commit` конфигурации на
   минуты.** Правка `roles.yaml` перестаёт быть мгновенной. Это и есть
   цена, которую SPEC покупает: прецедент 27.09 (a6da0abe → красный
   main → откат d910c523 → встали ветки волны) стоил дороже. Гейт
   стоит в `_commit_and_push`, то есть на КАЖДОЙ попытке повтора
   non-fast-forward (до `MAX_PUSH_ATTEMPTS = 3`): в вырожденном случае
   гонки push — три прогона. Выносить его выше нельзя, не потеряв
   привязку к «дереву с уже применённой правкой»; отказ выходит
   `sys.exit` с первой попытки, так что три КРАСНЫХ прогона подряд
   невозможны. Итерация 2: отказ гейта — единственный выход из команды
   ПОСЛЕ записи файла в общее рабочее дерево, поэтому он снимает
   записанное (`_restore_tree`), а дерево перед каждой сборкой
   приводится к `FETCH_HEAD` принудительно и с проверкой кода возврата;
   попутный флаш удержанную правку конфигурации не отправляет, чтобы
   прогон не сел на произвольную `note` (R1-F1, R1-F3).
3. **Дописка состояния с датой меняет вид уже существующих ячеек при
   следующей дописке.** Прежний слипшийся текст ячейки сохраняется
   целиком (требование 7) и новая дописка отделяется от него — то есть
   документ чинится постепенно, а не разово; разовая чистка — за
   заготовкой Оператора, вне этой задачи.
4. **Две строки «Копилки» текущего документа несут `|` внутри текста**
   (строки 138 и 180: 8 и 23 ячейки против шапки из 5). Генератор
   заготовки их НЕ трогает (нормализация применяется только к строкам,
   чьё число ячеек совпадает с шапкой) — иначе он переклеил бы чужой
   текст. Для `note --apply` это безопасно: сверка требования 11
   касается только шапок разделов, не строк данных.
5. **Признак «свой коммит» в сверке базы `--apply` — сообщение коммита,
   не только адрес автора** (итерация 2, R1-F2). Адрес, который ставит
   `-c user.email=NOTE_AUTHOR_EMAIL`, перебивает `GIT_AUTHOR_EMAIL`
   окружения пульта (проверено прогоном: коммит уносит адрес окружения, а
   не константу), поэтому одного адреса не хватило бы. Сообщение строит
   сам пульт (`_commit_message`, префикс `NOTE_COMMIT_SUBJECT_PREFIX`), и
   константа взята из того же места, чтобы два места не разошлись.
   Остаточный риск: посторонний коммит с сообщением, начинающимся тем же
   префиксом, сверка сочтёт своим. Сверка — страховка Оператора от
   затирания чужой правки заготовкой, а не рубеж безопасности; второй её
   контур («документ уехал после чтения заготовки», `base_blob` записи) от
   сообщения не зависит вовсе.

## Предложения системе

- `skills/coding-standards.md` требует «существующие тесты зелёные и не
  ослаблены», но не разделяет два разных действия: ослабление проверки и
  адаптацию ЗНАЧЕНИЯ фикстуры под новое правило валидации. Класс
  повторится у любой задачи, вводящей валидацию поля, которое старые
  фикстуры заполняли произвольно (здесь — приоритет «9» в 13 местах
  двух файлов). Одна строка в скиле («правка значения фикстуры под новое
  правило — не ослабление; удаление ассерта, теста, файла или добавление
  скипа — ослабление») сняла бы вопрос до его возникновения.
- SPEC этой задачи требует (требование 18) приложением «полное
  содержимое файла» размером 244 КиБ, не назвав ни его объём, ни
  риск устаревания снимка. Стадии SPEC стоило бы мерить объём файла,
  который она предписывает положить в артефакт: потолок части
  контекстного пакета (`context_package`, 65536 байт) меньше этого
  требования в четыре раза.
- Удержанную запись `.artel/notes-pending/`, которая больше не нужна
  (правку увезли другой командой, заготовка устарела), снять командой
  пульта нечем: `--flush` её только пробует отправить, а `doctor` о ней
  сообщает. Остаётся удаление файла руками — обход команды пульта по
  классу CLAUDE.md. Просится `note --drop-pending <файл|все>` с записью
  журнала; пока команды нет, обход назван в
  `docs/operator-session.md` явно (итерация 2, R1-F3).
- Идентичность коммитов `note`/`doc-commit` (`NOTE_AUTHOR_NAME`/
  `NOTE_AUTHOR_EMAIL`, «коммитит и там, где `user.email` не настроен»)
  фактически не действует: `-c user.email=…` перебивается
  `GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_EMAIL` окружения, и коммиты пульта
  уносят адрес Оператора (или роли — в окружении шага обе переменные
  выставлены). Тот же класс у `fixation.FIXATION_AUTHOR_*`, откуда приём
  скопирован. Лечится `-c`-парой на `GIT_*`-переменные в окружении
  дочернего процесса (`gitcmd.pult_env`) — отдельной задачей: зона
  `gitcmd.py` в эту не входит.

## Приложение: заготовка `docs/backlog.md` для `note --apply`

Требование 18 — разовая нормализация существующих строк документа;
применяет Оператор сам, задача `docs/backlog.md` не коммитит. Ниже —
генератор заготовки и команда применения. Генератор читает АКТУАЛЬНОЕ
содержимое `origin/main` (не снимок этого PLAN — см. «Риски», п. 1),
нормализует ровно те же две формы теми же правилами, что и код задачи
(цифра приоритета, дата без года), и пишет заготовку в файл.
Диффов защищённых путей приложение не несёт: `docs/backlog.md`
защищённым путём не является и коммитится командой `note`, а не
коммитом Оператора на мерже.

Порядок (из корня пульта, после мержа этой задачи):

```
# 1. Свежее содержимое документа из origin/main — в файл-источник.
git fetch -q origin main
git show FETCH_HEAD:docs/backlog.md > /tmp/backlog-origin.md

# 2. Заготовка: нормализация приоритета и даты по шапкам разделов.
python3 - /tmp/backlog-origin.md /tmp/backlog-draft.md <<'EOF'
import re, sys
from pathlib import Path
src, dst = Path(sys.argv[1]), Path(sys.argv[2])
lines = src.read_text(encoding="utf-8").split("\n")
headings = ["## Копилка", "## Бэклог", "## Очередь Оператора"]
prio = re.compile(r"^[Пп]?([1-4])$")
year = re.compile(r"^(\d\d?)\.(\d\d?)\.\d\d+$")
def cells(line):
    s = line.strip()
    inner = s[1:-1] if s.startswith("|") and s.endswith("|") else s
    return [c.strip() for c in inner.split("|")]
changed = 0
for heading in headings:
    i = lines.index(heading) + 1
    while not lines[i].strip().startswith("|"):
        i += 1
    header = cells(lines[i])
    k = i + 2
    while k < len(lines) and not lines[k].startswith("## "):
        line = lines[k]
        row = cells(line)
        if line.strip().startswith("|") and len(row) == len(header):
            for n, head in enumerate(header):
                if head == "П":
                    m = prio.match("".join(row[n].split()))
                    if m is not None:
                        row[n] = m.group(1)
                elif head == "Дата":
                    m = year.match(row[n])
                    if m is not None:
                        row[n] = m.group(1) + "." + m.group(2)
            new = "| " + " | ".join(row) + " |"
            if new != line:
                lines[k] = new
                changed += 1
        k += 1
dst.write_text("\n".join(lines), encoding="utf-8")
print("строк изменено:", changed)
EOF

# 3. Глазами: что именно поменялось (ожидается только приоритет и дата).
diff -u /tmp/backlog-origin.md /tmp/backlog-draft.md

# 4. Применение одним коммитом пульта в origin/main.
python3 orchestrator/artel.py note --apply /tmp/backlog-draft.md \
  --message "разовая нормализация приоритета и даты (01M3HST4SGX0SPKAGNHVY7DWHM, требование 18)"
```

Генератор шага 2 прогнан на вершине `b21f01e6` перед сдачей PLAN (тот же
приём, которым скил требует сверять приложение-диф перед сдачей — здесь
приложение не диф, а генератор, поэтому сверка не `git apply --check`, а
прогон самого генератора): отработал без ошибки, замер ниже
воспроизводится числом в число.

Замер на вершине `b21f01e6` (что изменит шаг 2): 43 ячейки приоритета
формы «П<цифра>» → «<цифра>», 7 ячеек даты «ДД.ММ.ГГГГ» → «ДД.ММ»,
итого 50 строк из 202 (файл — 244 584 байта). Две строки «Копилки» (138 и 180 файла на той
вершине) несут `|` внутри текста и под нормализацию НЕ попадают — их
число ячеек не совпадает с шапкой, и переклеивать их автоматически
нельзя (см. «Риски», п. 4). Удалённых строк в заготовке нет, поэтому
запись журнала требования 12 назовёт «удалено строк: 0».

Перенос исполненных строк и слияние дублей («разнос» из «Контекста»
SPEC) в эту заготовку сознательно не входит: это содержательное решение
Оператора о каждой строке, а не механическое преобразование формы, и
механика `note --apply` готова принять любую заготовку, которую Оператор
соберёт поверх шага 2.
