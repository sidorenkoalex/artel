- Опыт во временном каталоге (`tempfile.mkdtemp`, timeout 20 с): `zipfile.extractall` положил `../evil.xml` и `/abs.xml` внутрь каталога распаковки как `evil.xml`/`abs.xml`, без отказа. `infolist()` при этом отдаёт исходные имена, так что проверка до распаковки выполнима. Утверждение SPEC верно.

Расходится или не задано:
1. **Перезапуск задания пультом — штатный путь, и артефакт к попытке не привязан.** `ci.trigger_rerun` (`orchestrator/ci.py:1819-1848`) выполняет `gh run rerun <run_id> --failed`, то есть задание полного набора перезапускается в том же `run_id`. SPEC (SPEC.md «Материалы», «У перезапуска задания тот же `run_id`…») из этого выводит только отказ при двух артефактах. Как ведёт себя `actions/runs/<run_id>/artifacts` при перезапуске, SPEC не утверждает и не проверяет; опытом без сети это не проверить. Возможны два исхода:
   - (а) артефакт прежней попытки остаётся в списке — тогда после любого `ci-rerun` отчёт этого коммита навсегда «неизвестно»: источник `full_suite: ci` перестаёт работать ровно в сценарии, который пульт сам запускает;
   - (б) новая попытка упала до выгрузки — тогда единственный артефакт принадлежит прежней попытке и приписывается новой. Тр. 3 («артефакт прогона этой попытки», SPEC.md:52-53) ничем это не отличает: в объекте артефакта нет номера попытки, есть только `created_at`, а сверка по времени попытки не требуется.

   Итог (б) смягчает `ci.py:1412-1415` (статус `failed` при зелёном отчёте — «неизвестно»). Но при `success` новой попытки без выгрузки и красном отчёте прежней итог — ложный красный `JOB_RED` (`ci.py:1409-1411`).
2. **Путь для записи артели не задан.** `forge.github_call` отказывает артели без запуска `gh` (`orchestrator/forge.py:202-205`). `_GitHub.pipeline_status` для артели зовёт `ci.check_runs` без `repo` (`forge.py:232-233`). Тр. 5 говорит «с репозиторием записи» (SPEC.md:72), но не говорит, что у артели вход тот же, что у `pipeline_status`. Реализация через `github_call` пройдёт все AC (они на вымышленной внешней записи), а артель на этапе 4б получит «неизвестно» на каждой приёмке — ровно тот исход, который ТЗ «Факты» 3 называет проблемой.
3. **Таблица тр. 2 (SPEC.md:43-50) неполна.** В ней нет состояния `requested` (у check run в API GitHub это одно из состояний незавершённого прогона) и нет строки «иное значение». Перевод неназванного значения остаётся на усмотрение разработчика, и AC-4 его не проверяет.
4. Не проверено, без сети: отдаёт ли `commits/<sha>/check-runs` с умолчанием `filter=latest` незавершённую новую попытку, а не только завершённые. На этом стоит ветка «последняя попытка не завершена — ожидание» (тр. 1). Подмена в тестах это поведение примет на веру. Отклонением не считаю, отмечаю для гейта.

## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да | попытка выбирается по наименьшему номеру или пропущенный check run не исключается (статус `skipped`, отчёт пустой или чужой); незавершённая большая попытка игнорируется (возвращается статус меньшей); вызов идёт в транспорт GitLab; ключ без `classname::` |
| AC-2 | да | при отсутствии задания возвращается пустой статус или чужое задание; причина без имени задания |
| AC-3 | да, частично | снята проверка `expired`, числа артефактов, числа `*.xml`, числа компонентов, предела после распаковки — получается непустой отчёт вместо `None`; временный каталог не удаляется. Проверку путей ловит только «причина называет случай»: `zipfile` сам снимает `..` (опыт), и «файлов вне каталога нет» останется верным и без проверки. | AC-5 | да | умолчание не `junit`; поле без проверки типа (список или число принимаются) |
| AC-6 | да | строки нет; `ok` при отсутствующем артефакте; зелёный коммит ищется не по ветке `base`. | AC-9 | да | реестр подставляется в `targets` при импорте `ci` — процесс без `ci` загружает запись. Выполнимость: подменить реестр, не импортируя `ci` до загрузки, можно заглушкой модуля в `sys.modules` или хуком импорта; SPEC оставляет выбор автору тестов (SPEC.md «Материалы») |

Предел времени скачивания (тр. 5, `CI_REPORT_DOWNLOAD_TIMEOUT_SEC`; ТЗ тр. 3 «с пределом времени») ни одним AC не проверяется. Мутация «вызов без `timeout`» проходит все критерии. Безопасная форма теста есть: подменная программа `gh` спит дольше подменённой константы (порядка 1 с).

Красная фаза. До кода `job_result`/`job_test_report` отвечают «не реализовано» без запуска `gh`, `doctor` строки не выводит, поле не известно. Тесты краснеют на утверждениях; рекурсии, порождения процессов и меняющих команд нет. AC-9 запускает подпроцесс с `timeout` (образец — `hosting_registry.py:105-107`). AC-6 безопасен, только если тест зовёт `component_checks` или подменяет программу `gh` целиком. `doctor.all_checks` с одной подменой `ci.gh` дошёл бы до проверок, которые зовут `gh` другими путями. SPEC называет «без сети», форму не задаёт — некритично.

## Пути обхода гейтов
1. **Чужой артефакт в том же прогоне** (см. «Факты» п. 1). Буквальная реализация тр. 3 берёт единственный артефакт с именем у `run_id` попытки, не сверяя его с попыткой. Все AC проходят, но после `ci-rerun` пульта отчёт прежней попытки читается как отчёт новой. Ложный красный возможен; ложный зелёный перекрыт `ci.py:1412-1415` только при статусе не `success`.
2. **Артель вне проверки.** Реализация через `forge.github_call` (`forge.py:202-205` отказывает артели) или через `ctx.remote` без ветки `is_artel` проходит все AC на вымышленной записи. При этом не работает для единственного названного в ТЗ потребителя.
3. **Предел размера по метаданным.** Проверка `size_in_bytes` из списка артефактов до скачивания выполняет AC-3 «архив больше предела», а фактические байты `gh api …/zip` читаются целиком без предела. Требование «предел размера скачиваемого архива» (ТЗ тр. 3) этим обходится. AC-3 не требует случая, где метаданные занижены.
4. **Предел времени** не проверяется (см. «Проверяемость»): вызов без `timeout` проходит все AC.

## Вердикт
`concerns`. SPEC вести можно: ядро требований верно, факты о коде подтвердились, мандаты и матрица полны. Решить отклонения Оператор может на гейте: уточнением SPEC или записками разработчику.

Отклонения:
1. Привязка артефакта к попытке при перезапуске в том же `run_id` не задана (SPEC.md:52-53, «Материалы»; `orchestrator/ci.py:1819-1848`). Поведение API артефактов при перезапуске не проверено. Варианты: сверка `created_at` артефакта с `started_at`/`completed_at` попытки; признать «неизвестно» после перезапуска приемлемым и записать это в SPEC; проверка Оператором на настоящем репозитории.
2. Путь чтения для записи артели не задан и не проверен (SPEC.md:72; `orchestrator/forge.py:202-205`, `:232-233`). Нужно требование «вход тот же, что у `_GitHub.pipeline_status`, в том числе для артели» и вариант AC на записи с `is_artel`.
3. Предел размера архива не обязан действовать на фактические байты (SPEC.md:77-80, AC-3 SPEC.md:150-151). Нужен случай AC-3 с заниженным `size_in_bytes`.
4. Предел времени скачивания не покрыт ни одним AC (SPEC.md:80).
5. Таблица тр. 2 без `requested` и без строки «иное значение» (SPEC.md:43-50).
6. Мелкое: в AC-3 мутацию «нет проверки путей» ловит только «причина называет случай», а не отсутствие файлов вне каталога (`zipfile` снимает `..`, опыт). Автору тестов стоит знать, что утверждение о файлах здесь ничего не доказывает.
