# QUESTIONS: Итог и отчёт тестов задания CI у адаптера GitHub: job_result и job_test_report

## Вопросы

ТЗ в остальном достаточно для SPEC. Остановило одно прямое противоречие: требования 1–2 ТЗ («реализовать `job_result`/`job_test_report` для GitHub») и строка ТЗ «существующие тесты — зелёные без правки; если краснеет — эскалация с именем теста, без правки» на main несовместимы. Два существующих теста прямо требуют для `forge: github` ответа «не реализовано для github» без вызова `gh` именно по этим двум функциям:

- `tests/test_01m6m1799ycy5hxmhhd71shjet_github_mr_units.py::test_ac16_other_functions_not_implemented_without_gh[job_result]` и `[job_test_report]` (строки 935–958: `assert NOT_IMPLEMENTED in res.reason`, `assert lab.gh.calls == []`);
- `tests/test_01m5wcxbm7wcmrwcbwnchmar3t_gitlab_forge.py::test_ac13_github_other_functions_refuse[job_result]` и `[job_test_report]` (словарь `GH_CALLS`, строки 370–372; утверждение — строки 1196–1197: «не реализовано для github», `lab.gh_calls == []`).

Любая реализация из требований 1–2 делает эти четыре варианта красными. Убрать варианты из параметризации — удаление утверждений, не смена значения: разделом «Меняемое поведение» это не оформляется, нужен мандат Оператора. Тест `tests/test_01m5xzskk8gzteca2kwafhe029_component_fields.py::test_ac3_forge_without_job_test_report_refused` подменяет реестр сам и от реализации не краснеет (строки 179–186).

1. **Как поступить с четырьмя вариантами существующих тестов, которые требуют «не реализовано для github» для `job_result`/`job_test_report`?**
   - A) Мандат «Ослабление тестов разрешено»: из параметризации `test_ac16_other_functions_not_implemented_without_gh` (`github_mr_units.py:935-937`) и словаря `GH_CALLS` (`gitlab_forge.py:370-372`) убираются ключи `job_result` и `job_test_report`; прочие пять функций остаются под тем же утверждением. Свойство «GitHub-реализация этих двух функций читает check runs/артефакт, а не GitLab и не пусто» переходит к новым долгоживущим тестам этой задачи (AC ТЗ 1–2).
     - ломается: четыре варианта двух тестов исчезают из прогона; строка ТЗ «существующие тесты — зелёные без правки» читается как «кроме этих четырёх вариантов».
     - ослабляется: сторож «реестр не отдаёт github-у функцию GitLab, `gh` не зван» для двух функций (`gitlab_forge.py:1196-1197`, `github_mr_units.py:956-958`); его замещает новый тест, который требует вызова `gh api`, а не транспорта GitLab, и проверяет исходы по check runs.
     - цена: ~0; две правки списков в `tests/`, зона задачи `tests/` уже названа.
     - чьё решение: Оператор (мандат на ослабление тестов, ADR-0002).
   - B) Задачу не начинать до отдельной правки этих тестов Оператором (отдельный MR / `amend`), затем вернуть ТЗ аналитику без изменений.
     - ломается: ничего в коде; задача ждёт.
     - ослабляется: то же, что в A, но решение принимается вне задачи.
     - цена: время одного дополнительного цикла Оператора; ~$2 на повторный шаг аналитика.
     - чьё решение: Оператор.
   - C) Реализовать функции под другими именами или условием (например, только при наличии `ci_report_artifact`), чтобы старые тесты остались зелёными.
     - ломается: противоречит требованиям 1–2 и факту 3 ТЗ: `targets._check_full_suite_source` (`orchestrator/targets.py:1318-1322`) пускает `full_suite: ci` только по наличию `job_test_report` в реестре, и запись GitHub так и не загрузится.
     - ослабляется: ничего, но цель задачи не достигается.
     - цена: работа впустую.
     - чьё решение: Оператор.
   - дефолт: A. Это прямое следствие требований 1–2 ТЗ, и правка ограничена удалением двух ключей из двух списков; SPEC перечислит четыре варианта в «Не входит»/«Материалах» вместе с мандатом.

2. **Сверка «одна попытка» в `ci.job_full_suite` для GitHub: заполнять ли `Job.id` в `_GitHub.pipeline_status`?** Сейчас `_GitHub.pipeline_status` строит `Job(name, status)` без `id` (`orchestrator/forge.py:238-240`), а `ci.job_full_suite` сверяет номер последней попытки до и после чтения отчёта по `Job.id` (`orchestrator/ci.py:1352-1360`, `:1383-1386`). У GitHub оба номера — `None`, сверка проходит всегда: перезапуск задания между `job_result` и `job_test_report` не ловится, а `JobSuite.job_id` в тексте итога — `None`.
   - A) Не трогать `pipeline_status`: требование 5 ТЗ и граница «изменение приёмки» сохраняются буквально. Ограничение записать в «Не входит» SPEC.
     - ломается: ничего.
     - ослабляется: для GitHub не действует свойство «статус и отчёт — одной попытки» (`ci.py:1370-1374`, ANSWER-1 п. 3 SPEC 01M5XZSKK8GZTECA2KWAFHE029): `job_result`/`job_test_report` сами выбирают последнюю попытку, но независимо друг от друга.
     - цена: ~0.
     - чьё решение: Оператор.
   - B) `_GitHub.pipeline_status` заполняет `Job.id` номером check run (зона `orchestrator/forge.py` уже названа), чтобы сверка в `ci.job_full_suite` работала; `job_result`/`job_test_report` берут ту же попытку.
     - ломается: меняется состав `PipelineStatus.jobs` у GitHub. Существующие тесты, сравнивающие `jobs` целиком, могут покраснеть; отдельно не проверено.
     - ослабляется: ничего; свойство «одна попытка» распространяется на GitHub.
     - цена: +1 критерий, ~+$5–10 (тест на перезапуск между чтениями).
     - чьё решение: Оператор.
   - дефолт: A. ТЗ этого не требует, а B меняет поведение `pipeline_status` всех проектов GitHub; при молчании ограничение будет явно записано в «Не входит».
