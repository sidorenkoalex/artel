## Требования

1. **Разбиение циклов подслучаев.** В каждом разбиваемом методе (перечень —
   «Контекст») цикл подслучаев заменяется отдельными методами — по одному
   подслучаю (или одной доле перечня) на метод. Параметризованные
   подклассы не применяются (решение Оператора, круг 2, п. 3): новые методы
   стоят в том же классе либо в выделенном классе, который несёт только
   разбиваемые методы и не собирает повторно прочие тестовые методы
   исходного класса (наследованием или иначе).
2. **Перенос дословно.** Тела, утверждения, зёрна, тексты подслучаев и строки
   «Ловит мутацию» переносятся дословно. Исходное имя метода сохраняется за
   первым подслучаем или первой долей, остальные получают новые имена.
   Каждый новый метод несёт докстринг с «Сценарий» и «Ловит мутацию:» своего
   подслучая; для долей — исходный текст целиком.
   **Помощники с утверждениями — на первом уровне** (решение Оператора на
   гейте SPEC, круг 2, п. 1). Вызовы помощников с утверждениями
   (`refusal`, `no_gate_refusal`, `operator_mandate`, `enter_audit`,
   `assert_depth`, `assert_prepare`, `check_places`, `check_home`,
   `scenario`, `wrapper_records`) стоят прямо в теле каждого тестового
   метода — со старым и с новыми именами — а не в другом помощнике. В общий
   вспомогательный метод (имя не начинается с `test`) выносится только
   подготовка подслучая без утверждений. Вспомогательные методы добавляются
   в тестовые классы, не в классы подготовки (`OutcomeGateSandbox` и т. п.).
   **Метод со старым именем** несёт в своём теле вызовы помощников всех
   ветвей подслучаев исходного метода; ветвление по метке подслучая стоит в
   самом методе, исполняется только его доля. Каждый метод — со старым и с
   новыми именами — исполняет только свою долю.
   Для каждого разбиваемого метода из перечня «Контекст» учёт
   `guard.test_assertions` по старому имени на ветке не меньше прежнего:
   мультимножество утверждений метода на main ⊆ мультимножество
   утверждений одноимённого метода на ветке.
   У `test_ac9` за старым именем остаётся первый подслучай по
   детерминированному порядку — сортировке по метке — среди всех его
   подслучаев: «ADR в ТЗ»; доли категорий и остальные пять фиксированных
   подслучаев («бюджет 44», «бюджет 45», «защищённый путь», «мандат в
   ANSWER», «приложение PLAN») — новые методы.
3. **Перечни подслучаев** (`places` у `PultUnchangedTest`, `PLACES` у
   `pytest_own_places`, категории путей-признаков из `config` у `test_ac9`)
   делятся на фиксированное число долей `перечень[i::K]` по
   детерминированному порядку (сортировка по метке); перемешивание — внутри
   доли. Число долей K не больше длины перечня, и каждая доля утверждает
   свою непустоту (`assertTrue(доля)`) — решение Оператора, круг 2, п. 2.
   Перечень остаётся единственным источником: разбиение не заменяет
   его вписанной копией, и новый элемент перечня по-прежнему попадает под
   проверку без правки теста. Сценарием в PLAN: объединение долей равно
   полному перечню, доли не пересекаются.
   `PLACES` (`pytest_own_places.py:62–65`) и его порядок не меняются —
   литерал побайтно прежний; доли строятся из него (сортируется копия, не
   сама константа), так что `FULL_PLACES` и `TWO_SIDED` остаются прежними.
   В каждой доле `test_ac3_home_fresh_and_removed_after_completion` и
   `test_ac3_home_removed_after_timeout_and_exception` — не меньше двух
   прогонов, чтобы проверка «HOME не общий у нескольких прогонов» (`Ловит
   мутацию`, строки 510–513) сохранялась в каждой доле.
4. **Время.** Самый длинный тест каждого из четырёх файлов при отдельном
   прогоне файла — не более 10 с. Замеры «до» и «после» — в одном PLAN на
   одной машине, каждый отдельным прогоном файла на свободной машине:
   средняя загрузка за минуту в начале прогона ниже 4, её значение
   записано в PLAN рядом с замером. Под нагрузкой задача защищает тем, что
   самый длинный тест короче таймаута 120 с (`pyproject.toml`) с запасом.
5. **Вспомогательный метод `tests_dir`** переименовывается (имя не
   начинается с `test`) во всех местах вызова; число тестов набора
   уменьшается ровно на число классов, где он собирался.
6. **Неизменное.** Классы подготовки `OutcomeGateSandbox` и все прочие имена
   (классы, функции, константы), которые импортируют другие файлы `tests/`
   (`tests/test_01m5ddtvzea40zb9bheh4ydee7_merge_outcome_gate.py` импортирует
   из файла outcome_gate `ENTRY_HEAD`, `PLAN_READY`, `PLANK_PY`, `SEP`,
   `OutcomeGateSandbox`, `flow`, `js_source`, `py_source`, `py_tests`,
   `spec_text`, `ulid`), не меняются — ни имена, ни поведение, ни значения;
   `tests/sandbox.py`, `conftest.py`, `pyproject.toml` не меняются.
7. **Доказательство неослабления в PLAN.md:**
   - таблица «старый тест → новые тесты» для каждого разбитого метода;
   - сверка деревьев функцией `guard.test_assertions` по обеим сторонам,
     мультимножествами: утверждения старого метода ⊆ утверждения метода со
     старым именем на ветке (требование 2) и ⊆ объединение утверждений его
     новых методов;
   - мутации из строк «Ловит мутацию» разбиваемых тестов — по одной на
     разбиваемый метод: каждая применяется к коду пульта в worktree задачи;
     до правки красный хотя бы один старый тест, после правки краснеет новый
     метод того же подслучая; в конце `git status --porcelain orchestrator/`
     пуст; итог — в таблице;
   - число тестов до и после с пересчётом (минус `tests_dir`, плюс методы
     разбиения; повторно собранных копий прочих методов нет — требование 1);
   - время самого длинного теста каждого файла до и после (`--durations`).
8. Новых тестов в `tests/` сверх получившихся разбиением задача не добавляет.

## Критерии приёмки

AC-1. Ни один разбиваемый метод из перечня «Контекст» не содержит цикла подслучаев: каждый подслучай (место, признак) проверяется отдельным тестовым методом, для перечней из требования 3 — отдельной долей; параметризованных подклассов нет, новые методы стоят в том же классе либо в выделенном классе, который несёт только разбиваемые методы и не собирает повторно прочие тестовые методы исходного класса; исходное имя каждого разбиваемого метода существует и исполняет только первый подслучай или первую долю (у `test_ac9_each_signal_alone_switches_to_full_review` — подслучай «ADR в ТЗ»); каждый из 6 фиксированных подслучаев `test_ac9` («ADR в ТЗ», «бюджет 44», «бюджет 45», «защищённый путь», «мандат в ANSWER», «приложение PLAN») исполняется ровно одним методом.

AC-2. Тела, утверждения, зёрна, тексты подслучаев и строки «Ловит мутацию» перенесены дословно; вызовы помощников с утверждениями (`refusal`, `no_gate_refusal`, `operator_mandate`, `enter_audit`, `assert_depth`, `assert_prepare`, `check_places`, `check_home`, `scenario`, `wrapper_records`) стоят прямо в теле каждого тестового метода, не в другом помощнике; в общий вспомогательный метод тестового класса (не класса подготовки), имя которого не начинается с `test`, вынесена только подготовка подслучая без утверждений; каждый новый метод несёт докстринг с «Сценарий» и «Ловит мутацию:» своего подслучая (для долей — исходный текст целиком).

AC-3. Перечни `places`, `PLACES` и категории путей-признаков из `config` делятся на фиксированное число долей `перечень[i::K]` после сортировки по метке, перемешивание — внутри доли; число долей K не больше длины перечня, и каждая доля утверждает свою непустоту (`assertTrue(доля)`); вписанной копии перечня в тесте нет, и элемент, добавленный в исходный перечень, попадает в одну из долей без правки теста; в каждой доле обоих методов `test_ac3_*` файла `pytest_own_places` не меньше двух прогонов; PLAN.md несёт сценарий, показывающий, что объединение долей равно полному перечню и доли не пересекаются.

AC-4. При отдельном прогоне каждого из четырёх файлов зоны на свободной машине (средняя загрузка за минуту в начале прогона ниже 4) самый длинный тест длится не более 10 с; PLAN.md несёт замеры `--durations` «до» и «после» по каждому файлу — каждый отдельным прогоном файла на одной машине, со значением загрузки в начале прогона.

AC-5. Метод `tests_dir` в `tests/test_01m52eehsrd93wmphwb5vjyrkd_profile_callers.py` переименован в имя, не начинающееся с `test`, во всех местах вызова; pytest больше не собирает его как тест ни в одном из 13 классов.

AC-6. `OutcomeGateSandbox` и имена, импортируемые из файлов зоны другими файлами `tests/` (перечень — требование 6), не изменились ни именем, ни поведением, ни значением; литерал `PLACES` (`tests/test_01m52eefna1wh31962hvnt0yz9_pytest_own_places.py:62–65`) побайтно прежний, `FULL_PLACES` и `TWO_SIDED` прежние; `tests/sandbox.py`, `conftest.py`, `pyproject.toml` и файлы `tests/` вне зоны не изменены.

AC-7. Для каждого разбиваемого метода из перечня «Контекст» мультимножество его утверждений по `guard.test_assertions` на main ⊆ мультимножество утверждений одноимённого метода на ветке (метод со старым именем несёт в своём теле вызовы помощников с утверждениями всех ветвей подслучаев, ветвление по метке подслучая — в самом методе); PLAN.md несёт таблицу «старый тест → новые тесты» для каждого разбитого метода и сверку `guard.test_assertions` по обеим сторонам мультимножествами, показывающую оба включения: утверждения старого метода ⊆ утверждения метода со старым именем на ветке и ⊆ объединение утверждений его новых методов.

AC-8. PLAN.md несёт таблицу мутаций — по одной на разбиваемый метод, из его строк «Ловит мутацию»: мутация кода пульта в worktree задачи красит хотя бы один старый тест до правки и новый метод того же подслучая после правки; после мутаций `git status --porcelain orchestrator/` пуст.

AC-9. PLAN.md несёт число тестов набора до и после с пересчётом: разница равна числу добавленных разбиением методов минус число классов, где собирался `tests_dir`; повторно собранных копий прочих тестовых методов (через наследование или выделенный класс) в наборе нет.
