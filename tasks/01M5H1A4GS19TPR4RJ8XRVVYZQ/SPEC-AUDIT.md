## Пути обхода гейтов
- **О-6 (Ф-3).** Чтобы уложиться в AC-4, исполнитель может разбить и
  методы вне перечня (ac20, ac6_red_kinds) — расширение объёма без
  решения Оператора, без таблицы и сверки треб. 7 по ним (треб. 7 требует
  доказательств только для «разбиваемых методов из перечня»): разбиение
  вне перечня ушло бы мимо доказательства неослабления. Либо оставляет
  AC-4 красным в PLAN — тогда критерий не проверяет ничего.
- **О-5. Второе включение AC-7 / треб. 7 не определено.** «Утверждения
  старого метода ⊆ объединение утверждений его новых методов» — у
  мультимножеств «объединение» обычно максимум кратностей (`Counter |`),
  а не сумма (`Counter +`). На main у test_ac8 тело `refusal` учтено
  дважды (вызовы 1455 и 1458 — одна нормальная форма), у test_ac9 —
  `enter_audit` и тело `assert_depth` дважды (778/779, 783/784); каждый
  новый метод зовёт их по разу. При максимуме включение невыполнимо при
  любом верном разбиении, при сумме — выполнимо; исполнитель вправе
  выбрать ту трактовку, под которую сходится его таблица, и сверка в PLAN
  перестаёт что-либо доказывать. Неясно и то, входит ли метод со старым
  именем в «его новые методы»: если входит, включение пусто (он несёт
  весь прежний учёт по первому включению). Предложение: «⊆ сумма
  (`Counter +`) утверждений методов с новыми именами и исполняемой доли
  метода со старым именем».
- **О-1 (Ф-2).** Вынос правил подслучая (`checkout` с `self.git`) в общий
  помощник подготовки — буквально по треб. 2 — снимает утверждение `git`
  с учёта старого имени: ложный путь, закончится находкой гейта.
- Обход через мёртвые ветви метода со старым именем — принят Оператором
  (решения №1 п. 1, №2 п. 1), не поднимается.
