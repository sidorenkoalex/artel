# ТЗ: Чистый прогон канарейки учитывает эскалацию аудитора SPEC по той же ловушке

Источник: решение Оператора 13.10.2026; строка копилки 13.10 «Критерий
чистого прогона канарейки … не учитывает аудитора SPEC (ADR-0022)»
(коммит 60271ad3, П2); прогон канарейки 20261013T185506Z набора
`c-codex-all`, задача клона 01M4V9WRZ7N7F88P5YX1E522PT, шаблон
`canary-status-sort`.

Факты (main 60271ad3):
- `orchestrator/models.py::unclean_reason` признаёт прогон чистым при
  эскалациях только если `expected_escalation_met(row)` и
  `row["escalations"] <= 1`: «выполненная ожидаемая покрывает ровно одну
  эскалацию» (решение Оператора 02.10.2026, SPEC
  01M3YCHVVEK14SK8GT4R0H7M2C, требование 8). Правило принято до роли
  `spec_auditor` (ADR-0022, 11.10.2026).
- В строку `canary_runs` (`orchestrator/store.py::insert_canary_run`)
  пишется только общее число эскалаций —
  `len(metrics["escalations"])` из
  `orchestrator/canary.py::_escalation_notes` (переходы
  `state -> escalated` журнала задачи клона). Какая роль эскалировала,
  в строке не хранится.
- Журнал задачи клона роль различает: в прогоне 20261013T185506Z первый
  переход `state -> escalated` из `spec_writing` с деталью «analyst:
  батч вопросов по ТЗ …», второй — из `spec_audit` с деталью «эскалация
  от аудитора SPEC». Обе эскалации — по одной намеренной ловушке шаблона
  (`canary-expect-escalation: yes`: требования 1 и 3 ТЗ шаблона
  несовместимы). Синтетический ANSWER канарейки («Оператора нет, выбери
  наименее рискованное прочтение») противоречие не снимает, и аудитор
  верно не пропускает SPEC на одном из толкований.
- Следствие: на любом шаблоне с ожидаемой эскалацией прогон, в котором
  ловушку видят и аналитик, и аудитор, не чистый по числу эскалаций. Это
  касается допуска любой пары через `admit` (ADR-0019 п.5) и наказывает
  верную работу аудитора. Шаблоны с ловушкой в пуле: `canary-status-sort`
  (средний), `canary-budget-percent-ambiguous` (трудный).

Требуется:
1. Строка `canary_runs` хранит, какие роли эскалировали в прогоне
   (форма — выбор SPEC: число эскалаций по ролям либо перечень ролей по
   порядку). Роль эскалации определяется по состоянию, из которого задача
   ушла в `escalated` (`spec_writing` — analyst, `spec_audit` —
   spec_auditor, и так далее для прочих ролей), а не разбором текста
   детали. Эскалация, роль которой не установлена, считается отдельной
   неизвестной ролью. Старые строки без этих данных разбираются как
   сейчас — по общему числу.
2. Критерий чистоты (`unclean_reason`) на шаблоне с ожидаемой
   эскалацией (`expected_escalation_met(row)` истинно) допускает не
   больше одной эскалации от analyst и не больше одной от spec_auditor;
   хотя бы одна из них обязана быть, как сейчас. Эскалация любой другой
   роли или неизвестной роли, вторая эскалация той же роли — прогон не
   чистый, причина называет роль и число.
3. На шаблоне без ожидаемой эскалации ничего не меняется: любая
   эскалация, включая эскалацию аудитора, делает прогон не чистым.
4. Строки `canary_runs` без данных о ролях (записанные до задачи)
   сохраняют нынешнее правило: ожидаемая покрывает ровно одну эскалацию.
   Задним числом прогоны не перекрашиваются.
5. Сводка `admit` (`pair_admission`) в строке не чистого прогона
   называет причину по новому правилу; прочие числа допуска ADR-0019 п.5
   не меняются.
6. Тесты: прогон с ловушкой — analyst + spec_auditor по одной — чистый;
   analyst + developer — не чистый; две эскалации analyst — не чистый;
   одна эскалация spec_auditor без ловушки — не чистый; строка без
   данных о ролях с двумя эскалациями — не чистая, как раньше; роль
   определяется по состоянию до `escalated`.

Матрица неослабления:
- Шаблоны без ловушки — критерий не меняется (требование 3).
- Шаблон с ловушкой — допуск расширяется ровно на одну эскалацию одной
  роли (spec_auditor); test_author, developer, reviewer и повторные
  эскалации ловятся как раньше (требование 2).
- Старые строки не перекрашиваются (требование 4).
- Числа допуска (три чистых, два шаблона, средний класс) и прочие
  условия чистоты (ревью, повтор developer, отказ автогейта) не трогаются.

Зоны: orchestrator/models.py, orchestrator/canary.py,
orchestrator/store.py, tests/.

Не входит: особое условие допуска для самой пары spec_auditor
(«аудитор обязан поймать ловушку», аналог `ADMIT_TZ_AMBIGUITY_ROLE`) —
после канарейки-ловушки с дефектным SPEC по ADR-0022 п.4–5; правка
текста ADR-0019 п.5 (формулировка «эскалации (кроме ожидаемой)» новому
правилу не противоречит; если SPEC сочтёт иначе — эскалация, не правка
ADR); правка шаблонов пула канарейки; синтетический ANSWER канарейки.
