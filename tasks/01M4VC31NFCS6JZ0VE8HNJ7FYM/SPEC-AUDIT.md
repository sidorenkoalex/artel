# SPEC-AUDIT: Чистый прогон канарейки учитывает эскалацию аудитора SPEC по той же ловушке

## ТЗ и SPEC
Требования ТЗ 1–6 отражены в SPEC 1–6 в обе стороны:
- ТЗ п.1 (роли в строке, форма на выбор SPEC, роль по состоянию, не по
  детали, неизвестная роль отдельно, старые строки по числу) → SPEC
  треб. 1 (перечень по порядку, колонка `escalation_roles`, литерал
  `unknown`, `NULL` у старых строк) и треб. 4.

  не чистый с ролью и числом) → SPEC треб. 2 (подстрока
  `эскалаций роли <роль>: <число>`). «Хотя бы одна из них» в ТЗ и «хотя бы
  одна эскалация» в SPEC эквивалентны: при `expected_escalation_met`
  (`actual_escalation == 1`) эскалация есть всегда, а любая не из
  analyst/spec_auditor делает прогон не чистым.
- ТЗ п.3, п.4, п.5, п.6 → SPEC треб. 3, 4, 5, 6 и AC-8, AC-9, AC-10.
- Решение Оператора на гейте SPEC №1 исполнено: Т-1 — AC-1…AC-3 несут
  записи `agent run started`/`agent run finished` между `state -> X` и
  `state -> escalated`; Т-2 — треб. 4 и AC-9 явно приравнивают отсутствие
  ключа к `NULL`; Ф-1 — «Материалы» называют `:2232` в
  `_run_task_in_ephemeral_clone`.
- Сверх ТЗ в SPEC — только уточнения механики: строки `drive_failed` и
  оборванного прогона пишутся с `NULL` (согласно ТЗ п.4 по смыслу);
  вычисление из `steps` пультом без смены `_DRIVE_METRIC_FIELDS` —
  следствие совместимости клона старого кода, не новое требование.
- «Не входит» SPEC совпадает с «Не входит» ТЗ.

## Пути обхода гейтов
Е-1 (концерн, решение за Оператором). Правило «роль = состояние до
`escalated`» (ТЗ п.1, SPEC треб. 1) приписывает роли состояния и
эскалации ПУЛЬТА, которые идут тем же переходом `state -> escalated` из
текущего состояния:
- `orchestrator/budget.py:288-302` `enforce_budget` — «бюджет исчерпан»,
  `expected_state=state` после шага любой роли, в том числе
  `spec_writing`/`spec_audit`;
- `orchestrator/fixation.py:248` — эскалация по инциденту фиксации.

Канарейка бюджетную эскалацию переживает: однократно поднимает потолок и
ведёт задачу дальше (`canary.py:1742-1747`), вердикт строки остаётся
`green`, если потолок второй раз не исчерпан (`_run_verdict`,
`canary.py:2000`). Следствие на шаблоне с ловушкой:
- analyst эскалирует ловушку, затем бюджет исчерпан после шага
  `spec_audit` → `escalation_roles = analyst,spec_auditor` → по новому
  правилу ЧИСТЫЙ; на main тот же прогон не чистый
  (`escalations 2`, `models.py:1149-1151`);
- бюджет исчерпан после шага analyst, ловушку ловит только аудитор →
  `analyst,spec_auditor` → чистый, на main — не чистый.

Это расширение допуска сверх матрицы ТЗ («ровно на одну эскалацию одной
роли (spec_auditor)» — подразумевается эскалация самой роли, не пульта),
и SPEC его не называет. Выполнить SPEC буквально — значит открыть этот
путь. ТЗ запрещает разбор текста детали, поэтому аналитик закрыть его
сам не мог. Варианты для Оператора: (а) принять как есть (редкий случай:
бюджет до гейта SPEC — `DEFAULT_BUDGET_USD`); (б) считать бюджетную
эскалацию ролью `unknown` по признаку журнала, а не детали — запись
подъёма потолка канарейкой `_CEILING_RAISE_ACTION` (`canary.py:238`,
`_ceiling_already_raised` `:1620`) следует за такой эскалацией; (в) отдельная
задача. Замечу, что смежная дыра есть и на main: одна бюджетная
эскалация в `spec_writing` уже засчитывается «ожидаемой»
(`actual_escalation` — любая эскалация) — она задачей не вводится.

Других путей обхода не найдено: критерий читает только колонку, которую
пишет пульт из журнала клона (`steps` результата), а не поле, которое
код клона мог бы подставить; старые строки по-прежнему по старому
правилу.

   `orchestrator/canary.py:1742-1747`; правило — SPEC треб. 1 (роль по

   место вычисления ролей в пульте SPEC треб. 1 не фиксирует — риск

   `tests/test_canary_codex_clone_auth.py:597-614`).
