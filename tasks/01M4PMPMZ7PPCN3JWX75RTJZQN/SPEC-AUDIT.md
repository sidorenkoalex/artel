## Пути обхода гейтов
- Подделать признак merge-коммита веткой PR нельзя: HEAD строит GitHub,
  файл события пишет раннер, первый родитель — цель. Правка самого скрипта
  веткой вынесена в «Не входит».
- **Отклонение C.** Исполнитель может, следуя критериям буквально,
  трактовать ошибку `merge-base --is-ancestor` как «условие выполнено»
  (например, `returncode != 1` вместо `== 0`) — ни один AC этого не поймает.
  При `BASE_SHA`, которого нет в чекауте (base.sha пропал после
  force-push в main), база станет `HEAD^1`, перечень и дифф прочитаются, и
  джоб даст 0 там, где прежняя проверка давала 2. Это ослабление fail-closed.
  Требование 4 его запрещает, но тестом оно не закреплено. Вероятность
  мутации невысокая, класс тот же, что Оператор уже закрывал по перечню.
- **Отклонение D.** Исполнитель реализует «сбой диффа от `HEAD^1` → откат на
  `BASE_SHA`». Тест AC-9 в описанной форме (отказ на любом `diff`) всё равно
  получит код 2, и заявка «Ловит мутацию» окажется ложной. В CI откат на
  более широкий дифф с прежним перечнем пропустил бы путь, защищённый только
  в `HEAD^1`.
- Попутно: обёртка, перехватывающая подкоманду `diff`, закрепляет за кодом
  именно `git diff`. Реализация через `git diff-tree` или `git log
  --name-only` тест AC-9 не провалит, а обойдёт: обёртка не сработает, и
  код будет 0/1 вместо 2. Это устройство кода, которого SPEC в требованиях
  не требует. Сейчас код использует `git diff` (:138), так что на практике
  это не мешает. Отдельным отклонением не считаю, но при решении по D стоит
  иметь в виду.
- При `BASE_SHA == HEAD^1` git считает коммит предком самого себя: условие
  выполнено, меняется только строка источника. На вердикт не влияет.

## Вердикт
`concerns`. Оба отклонения прошлого аудита закрыты. A — снятие сценария
«нечитаемый первый родитель» и трактовка ошибки git в SPEC.md, требование 4,
третий пункт и последний абзац, и AC-6. B — сбой диффа добавлен в AC-9. В
новой редакции два отклонения, оба решаются на гейте:

1. **C. Ветка «ошибка git при проверке предка → откат» не проверяется ни
   одним критерием, а SPEC утверждает обратное** (SPEC.md, AC-6, последнее
   предложение: «покрыт AC-5»). Условие AC-5 «`BASE_SHA` не предок
   `HEAD^1`» на валидных объектах — код git 1, не ошибка. Мутация «ошибка
   (128) → условие выполнено» проходит, а при несуществующем `BASE_SHA` она
   даёт код 0 вместо прежнего 2 (`scripts/ci_protected_paths.py:128-131`,
   проверено: `git merge-base --is-ancestor 1111…1111 HEAD` → 128).
   Варианты решения: дополнить AC-5 или AC-9 случаем «merge-коммит PR и файл
   события корректны, `BASE_SHA` — несуществующий sha → откат, код 2 с
   причиной» либо принять как есть.
2. **D. Заявка «Ловит мутацию» в AC-9 (сбой диффа) не выполнима по коду
   возврата** (SPEC.md, AC-9: «обёрткой `git` в `PATH` теста, отказывающей на
   подкоманде `diff`»). При отказе на любом `diff` мутант с откатом падает на
   диффе `BASE_SHA...HEAD` и тоже возвращает 2
   (`scripts/ci_protected_paths.py:152-156`). Варианты: обёртка отказывает
   только на диффе от `HEAD^1` (sha известен тесту), а дифф от `BASE_SHA`
   пропускает — тогда мутант даст 0/1; либо явно задать признак отката в
   выводе при коде 2 и проверять его отсутствие; либо принять как есть.

Наблюдения без отклонения: текста решений Оператора от 12.10.2026 в
артефактах нет (нет ANSWER-n.md), сверено только по содержанию. Остаётся
неточность «текущая вершина» в «Контексте». Обёртка `git diff` в AC-9
