## Пути обхода гейтов
- Подделать признак merge-коммита из ветки PR нельзя. HEAD на
  `pull_request` — merge-коммит GitHub, файл события пишет раннер, первый
  родитель — цель PR. Ни одно из трёх условий ветка не контролирует.
  Правка самого скрипта веткой вынесена в «Не входит», как и сегодня.
- PR, где main и ветка одинаково изменили защищённый путь: в
  `HEAD^1...HEAD` изменения нет. Но чистый эффект PR на этот путь
  относительно цели тоже нулевой, так что это не обход.
- Путь, снятый Оператором с защиты в main после `base.sha`, при новой базе
  перестаёт краснить PR. Это решение доверенной стороны, и матрица ТЗ его
  принимает.
- Бывший путь обхода прошлого аудита (откат на `BASE_SHA` при нечитаемом
  перечне `HEAD^1` даёт код 0) теперь закрыт требованием 4 и AC-9.
- Остаётся одна лазейка, которую никакой AC не проверяет (отклонение B).
  Исполнитель может буквально выполнить AC-9 (перечень → код 2) и при
  сбое диффа от доказанного `HEAD^1` откатиться на `BASE_SHA`. Вердикт
  тогда будет по более широкому диффу и прежнему перечню, а путь,
  защищённый только в `HEAD^1`, пройдёт. Тот же класс, что закрыло решение
  Оператора по перечню. Вероятность низкая: дифф между читаемыми
  коммитами почти не падает.
- Мелочь для исполнителя: при `BASE_SHA == HEAD^1` (новых коммитов в main
  нет) «предок» в смысле git включает равенство, и условие выполнено. SPEC
  этого не оговаривает. Вердикт от трактовки не зависит, меняется только
  строка источника в выводе.
