# SPEC: База сравнения джоба защищённых путей — первый родитель merge-коммита PR

## Контекст
Джоб `protected-paths` (`.github/workflows/ci.yml:290-318`) передаёт
`BASE_SHA` = `github.event.pull_request.base.sha` в
`scripts/ci_protected_paths.py`, а тот берёт перечень `PROTECTED_PATHS` из
`orchestrator/config.py` базы (`base_protected_paths`,
`scripts/ci_protected_paths.py:123`) и дифф `git diff --name-only
<base>...HEAD` (`changed_files`, `:135`). `base.sha` события фиксируется при
открытии/обновлении PR и устаревает: коммит Оператора в main по защищённому
пути после этого (11.10.2026: 9002a77d, `docs/adr/0022-handoff-audit.md`)
попадает в дифф как изменение PR, и джоб красный у всех открытых PR (прогон
38124848279, PR #259). `ci-rerun` несёт тот же payload события и не лечит.
На событии `pull_request` `actions/checkout` выгружает merge-коммит PR
(`refs/pull/N/merge`): первый родитель — текущая вершина целевой ветки,
второй — голова ветки PR. Задача — брать базу от первого родителя, когда
HEAD доказанно такой merge-коммит, и сохранить прежнее поведение с базой
`BASE_SHA` (её дифф строже — шире) во всех остальных случаях.

## Требования
1. HEAD считается merge-коммитом PR, только если одновременно: у HEAD ровно
   два родителя; переменная окружения `BASE_SHA` не пуста и является предком
   `HEAD^1`; второй родитель `HEAD^2` равен `pull_request.head.sha` из файла
   события, путь к которому несёт переменная окружения `GITHUB_EVENT_PATH`.
   Тогда база сравнения — `HEAD^1`: и перечень защищённых путей, и дифф
   берутся от неё. Если хотя бы одно условие не выполнено — прежнее
   поведение с базой `BASE_SHA`, и вывод называет, какое условие не
   выполнено.
2. Пустой `BASE_SHA` — по-прежнему красный джоб с кодом возврата 2 при любой
   форме HEAD.
3. Выбор базы реализуется в `scripts/ci_protected_paths.py`;
   `.github/workflows/ci.yml` не меняется. Вывод джоба называет
   использованную базу (sha) и её источник: «первый родитель merge-коммита
   PR» либо «BASE_SHA события».
4. Отказ закрытый (fail-closed, ADR-0002) сохраняется — не зелёный по
   умолчанию:
   - все три условия требования 1 выполнены (база — доказанный `HEAD^1`),
     а перечень защищённых путей или дифф от `HEAD^1` не читаются —
     красный джоб с кодом 2 и названной причиной; откат на `BASE_SHA` в
     этом случае недопустим: перечень по `BASE_SHA` не строже перечня по
     `HEAD^1` (путь, внесённый в перечень только в `HEAD^1`, прошёл бы с
     кодом 0);
   - откат на `BASE_SHA` допустим только когда не выполнено одно из
     условий требования 1: у HEAD не два родителя; `BASE_SHA` не предок
     `HEAD^1`; файла события нет или он не читается (в том числе не задан
     `GITHUB_EVENT_PATH`, файл не JSON, нет `pull_request.head.sha`);
     `HEAD^2` не равен `pull_request.head.sha`;
   - перечень или дифф от `BASE_SHA` не читаются — код 2 с названной
     причиной, как в прежней проверке.
   Решение Оператора 12.10.2026 по аудиту SPEC (отклонение 2).
5. Сохраняются свойства: «ветка, которая создаёт файл и тем же изменением
   вносит его в перечень, свой PR не красит» (SPEC
   01M31DRD81092HB69J0MAKZMGH) и «PR, меняющий защищённый путь базы, —
   красный».
6. Тесты в `tests/` — на временном git-репозитории; скрипт запускается с
   явным окружением без переменных `GITHUB_*` раннера, файл события —
   временный. Тесты несут заявки «Ловит мутацию» на: возврат к `BASE_SHA`
   при merge-коммите PR; взятие второго родителя вместо первого; удаление
   сверки второго родителя с головой PR. Существующие тесты скрипта
   (`tests/test_ci_protected_paths.py`,
   `tests/test_protected_test_settings.py::CiScriptRunsAsScriptTest`) не
   ослабляются. Долгоживущие приёмочные тесты автора тестов
   (`tests/test_01m4pmpmz7ppcn3jwx75rtjzqn_*.py`, ADR-0020) этому
   требованию удовлетворяют; свойства, которые они уже держат, разработчик
   отдельными тестами в `tests/` не повторяет.

## Критерии приёмки

AC-1. Случай 11.10: временный репозиторий, где после `BASE_SHA` в целевую
ветку закоммичено изменение защищённого пути, ветка PR этот путь не трогает,
HEAD — merge-коммит PR (два родителя, `BASE_SHA` — предок `HEAD^1`, `HEAD^2`
равен `pull_request.head.sha` временного файла события из
`GITHUB_EVENT_PATH`): скрипт завершается кодом 0.

AC-2. При merge-коммите PR из AC-1 перечень защищённых путей берётся из
`orchestrator/config.py` коммита `HEAD^1`, а дифф — `HEAD^1...HEAD`: путь,
внесённый в перечень только в `HEAD^1` (после `BASE_SHA`) и изменённый
веткой PR, даёт код 1.

AC-3. PR, меняющий защищённый путь, — код 1 при обеих формах HEAD: при
merge-коммите PR и при HEAD, не являющемся merge-коммитом PR (например, с
одним родителем).

AC-4. HEAD — слияние main в ветку задачи (два родителя, но `HEAD^2` не
равен `pull_request.head.sha` из файла события), защищённый путь изменён в
более раннем коммите ветки: код 1, база — `BASE_SHA`, вывод называет
невыполненное условие (второй родитель не голова PR).

AC-5. Каждое невыполненное условие требования 1 по отдельности — у HEAD не
ровно два родителя; `BASE_SHA` не предок `HEAD^1`; `HEAD^2` не равен
`pull_request.head.sha` — ведёт к базе `BASE_SHA`, и вывод называет именно
это условие.

AC-6. Нечитаемый или неполный файл события (файла нет, не JSON, нет
`pull_request.head.sha`, `GITHUB_EVENT_PATH` не задан) — откат
на базу `BASE_SHA` с названной в выводе причиной; вердикт тот же, что у
прежней проверки: защищённый путь в диффе от `BASE_SHA` — код 1, без
защищённых путей в этом диффе — код 0.

AC-7. Пустой `BASE_SHA` — код 2 при любой форме HEAD, в том числе при HEAD
с двумя родителями и корректным файлом события;
`tests/test_protected_test_settings.py::CiScriptRunsAsScriptTest` зелёный без
правки.

AC-8. Вывод скрипта называет использованную базу (sha) и её источник
строкой «первый родитель merge-коммита PR» либо «BASE_SHA события» — и при
коде 0, и при коде 1.

AC-9. Все три условия требования 1 выполнены, а перечень от `HEAD^1` не
прочитан (в `HEAD^1` нет `orchestrator/config.py` либо значение
`PROTECTED_PATHS` в нём не разбирается) — код 2, и вывод называет причину;
в том числе когда перечень и дифф от `BASE_SHA` читаются и защищённых путей
в диффе от `BASE_SHA` нет, то есть откат на `BASE_SHA` дал бы код 0. Перечень
от `BASE_SHA` при откате (условие требования 1 не выполнено) не прочитан —
код 2 с названной причиной.

AC-10. Ветка, которая создаёт файл и тем же изменением вносит его в
`PROTECTED_PATHS`, свой PR не красит: код 0 при merge-коммите PR и при
прежней базе `BASE_SHA`.

## Оценка объёма и деление
Сработавшие сигналы: число критериев приёмки ≥ 10 (10); `budget_usd` ≥ $30
(40); зона задевает механизм, на который опирается запись в
`docs/invariants.md` (строка 16 и строка «Защищённые пути» — задание CI
`protected-paths`).

Материал для решения Оператора — обоснование монолита: правка сосредоточена
в одной функции выбора базы одного файла `scripts/ci_protected_paths.py`
(~170 строк), тесты к ней — в `tests/`, карта — производная. Разрезать
«выбор базы» и «откат на `BASE_SHA`/названную причину» нельзя: часть,
берущая `HEAD^1` без полного набора условий и отката, ослабляет проверку
(принимает, например, слияние main в ветку задачи за merge-коммит PR) и
нарушает требование 4 до мержа второй части; часть только с выводом без
выбора базы не меняет поведения и самостоятельной ценности не несёт.
Бюджет: `budget_usd: 40` расходится с рамкой ТЗ «$15» — ставка по
калибровке (до 10 критериев, до 4 файлов зоны — ~40; планка не ниже $25);
решение Оператора 12.10.2026 по аудиту SPEC: 40 принимается.

Критериев 10, потому что каждое условие требования 1 и каждый откат
проверяются отдельно — объём кода от этого не растёт.

  `templates/`, `CLAUDE.md`, `roles.yaml`, `.artel/` — только чтение по ТЗ;
  неизменность защищённых из них держит пульт.
- Тот же приём с `pull_request.base.sha` у джобов `id-format-greplint` и
  `canary-guid-leak` (`ci.yml` ~60, ~98, ~121) — правка `ci.yml` только
  Оператором, отдельная строка бэклога.
- Защита самого скрипта `scripts/ci_protected_paths.py` от правки веткой
  PR.
- Раздел «Меняемое поведение» не нужен: существующие методы
  `tests/test_ci_protected_paths.py` текст вывода `main()` не проверяют, а
  `CiScriptRunsAsScriptTest` проверяет лишь код 2 и вхождение `BASE_SHA` в
  вывод — оба ожидания сохраняются (требование 2).
- Полный зелёный набор `tests/` и зелёный CI ветки — её держит пульт.
