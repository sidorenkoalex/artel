# PLAN: Лог агента в файл по ходу шага

## Подход

`cmd_run` сейчас зовёт `subprocess.run` без пайпов: вывод агента идёт
прямо в терминал Оператора и нигде не сохраняется (orchestrator/artel.py:352).
Чтобы получить и файл, и консоль, нужен пайп + собственная перекачка строк
(«tee»): `subprocess.Popen(stdout=PIPE, stderr=STDOUT, bufsize=1)` и цикл
`for line in proc.stdout`, который пишет строку и в `sys.stdout`, и в
лог-файл, открытый с построчной буферизацией (`buffering=1`).

Ключевые решения:

- **Режим вывода агента — `--output-format stream-json --verbose`.**
  Построчная перекачка сама по себе критерий приёмки 1 не даёт: источник
  должен отдавать строки по ходу. Замерено на реальном CLI (обе пробы —
  один и тот же промпт с двумя `sleep 15` в Bash, время прихода строки
  от старта процесса):

  | Режим | Строки | Первая строка | Процесс завершён |
  |---|---|---|---|
  | `text` (было) | 1 | +43.81 с | +44.33 с |
  | `stream-json` | 27 | +1.13 с (события далее на +3, +7, +11, +23, +26, +29, +41 с) | +46.21 с |

  То есть в прежнем режиме `tail -f` весь шаг показывает пустой файл —
  ровно тот случай («кажется зависло»), ради которого задача и заведена.
  Сквозная проверка критерия приёмки 1 (боевые `new_agent_log`/`OutputPump`/
  `stream_to_log` и боевые флаги, безобидный промпт, файл опрашивался как
  `tail -f`): строки легли в лог на +7.05, +7.55, +23.20 и +37.32 с при
  живом процессе, завершился он на +39.84 с. В файле — читаемый текст
  («I'll run both commands.», «· Bash python3 -c …»), а не сырой JSON.
  `--verbose` обязателен: без него CLI выходит с rc=1 и сообщением
  «When using --print, --output-format=stream-json requires --verbose».
  `--include-partial-messages` не берём: событий раз в несколько секунд
  достаточно, чтобы отличить работу от зависания, а посимвольная сборка
  чанков усложнила бы рендер без выигрыша по SPEC.
- **Сырой JSON Оператору не показываем — рендерим строки событий**
  (`render_agent_line`). Требование 2 (вывод читаем в консоли) и
  требование 1 (строки по ходу) иначе конфликтуют. Из потока событий
  берём два вида: текст ассистента (что агент сказал) и `tool_use`
  (что он делает — имя инструмента + команда/путь). Служебные события
  (хуки, `rate_limit_event`, сводки задач, `init`) отбрасываем: они не
  помогают отличить работу от зависания, а лог замусоривают.
  Ошибочный `result` (`is_error`) печатаем — иначе провал шага молчит.
  Не-JSON строки (stderr агента, трейсбеки CLI) проходят как есть, так
  что ничего не проглатывается молча. Стоимость/токены из `result` не
  парсим — SPEC «Не входит».
- **stderr сливаем в stdout** (`stderr=subprocess.STDOUT`), а не читаем
  вторым потоком: SPEC требует обе струи в одном файле, а порядок строк
  при слиянии на уровне ОС сохраняется без синхронизации в Python.
- **Перекачка — в потоке-демоне с join по таймауту.**
  `for line in proc.stdout` блокируется, пока агент молчит, поэтому
  таймаут шага нельзя мерить внутри цикла: поток качает строки, основной
  делает `proc.wait(timeout=AGENT_TIMEOUT_SEC)` и убивает процесс по
  таймауту. EOF на пайпе приходит, только когда write-конец закрыт всеми,
  кто его унаследовал, — переживший агента фоновый процесс держал бы
  `run` вечно. Поэтому `daemon=True` + `pump.join(PUMP_JOIN_TIMEOUT_SEC)`:
  управление возвращается Оператору в любом случае, а незавершённая
  перекачка отмечается в журнале как неполный лог.
  `proc.stdout` закрываем только после успешного join — закрывать пайп,
  пока в нём висит читающий поток, значит поменять один вечный блок на
  другой (`close()` ждёт лок буфера).
- **Сбой лога не должен быть тихим.** Поток запоминает своё исключение
  (`OutputPump.error`), `cmd_run` после join пишет в журнал
  `agent log FAILED` — иначе недоступный на запись `.artel/logs`
  выглядел бы как успешный шаг. Если лог не открылся, пайп всё равно
  дочитывается в консоль: перестать читать — значит подвесить агента на
  записи в переполненный пайп.
- **Номер прогона N — из имён существующих файлов**, а не из БД: лог
  живёт в `.artel/logs/`, состояние прогонов уже есть на диске, лишняя
  колонка в схеме не нужна. Файл создаётся (`touch`) сразу при выборе
  имени — чтобы `tail -f` можно было запустить, не дожидаясь первой
  строки агента.
- Путь логов — модульная константа `LOGS` рядом с `DB`/`TASKS`, чтобы
  тесты подменяли её так же, как подменяют остальные пути (mock.patch.object).

Архитектурно значимого решения нет — ADR не требуется.

## Риски

- Рендер завязан на формат событий `stream-json` конкретной версии
  `claude`. Ломается он мягко: незнакомое событие отбрасывается,
  не-JSON строка проходит как есть, лог не пустеет полностью, но может
  обеднеть. Проверка — прогон `run` после обновления CLI.
- Строка без `\n` в конце не появится в логе, пока не придёт перевод
  строки, — итератор строк отдаёт хвост только при закрытии пайпа. Для
  наблюдаемости шага этого достаточно: `stream-json` пишет по событию
  на строку.
- Ошибка записи в лог посреди шага (кончился диск) обрывает перекачку:
  пайп перестаёт читаться, агент упирается в переполненный пайп и
  снимается по таймауту шага. Управление к Оператору вернётся, в
  журнале будет `agent log FAILED`; удерживать шаг живым при мёртвом
  логе — отдельная задача.
- Перекачка в отдельном потоке пишет в `sys.stdout` параллельно с
  основным потоком. В `cmd_run` основной поток в это время только ждёт
  процесс и ничего не печатает, а поток join-ится до печати итога, так
  что перемешивания строк нет.
- Незакрытый `.artel/logs/` растёт без ротации. Вне зоны задачи (SPEC
  «Не входит» про это молчит) — при необходимости отдельная задача.
