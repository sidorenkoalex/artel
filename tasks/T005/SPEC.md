# SPEC: Лог агента в файл по ходу шага

## Контекст
Сейчас `cmd_run` запускает `claude -p` без перехвата вывода: stdout
агента виден только после завершения шага (буферизуется), Оператор
не может отличить работающего агента от зависшего — при прогоне T003
это выглядело как «кажется зависло». Дизайн (docs/design.md §7 «молчащий
агент», §14 «live-стрим: MVP = лог шага в файле») требует наблюдаемости
шага по ходу.

## Требования
1. Вывод агента (stdout и stderr) при `run` пишется в файл
   `.artel/logs/<task_id>-<role>-<N>.log` в реальном времени (построчно,
   без ожидания конца шага); N — порядковый номер запуска этой роли
   по задаче, чтобы прогоны не перезатирались.
2. Вывод по-прежнему виден и в консоли `run` (как сейчас), поведение
   команды для Оператора не меняется.
3. Путь к лог-файлу печатается в начале шага и пишется в журнал шагов
   (steps.detail) при старте.
4. Каталог `.artel/logs/` не попадает в git (уже под .artel/ в
   .gitignore — не ломать).
5. Покрыто юнит-тестами в tests/: имя файла с инкрементом N; запись
   идёт построчно (без полного буферирования до конца процесса) —
   допустима проверка через фейковый процесс/поток.

## Критерии приёмки
1. Во время работы агента `tail -f .artel/logs/<последний>.log`
   показывает появляющиеся строки до завершения шага.
2. Повторный `run` той же роли по той же задаче создаёт новый файл
   с N+1, старый не перезатёрт.
3. В `log <id>` видна запись о старте шага с путём к лог-файлу.
4. `python3 -m unittest discover -s tests` зелёный, guard и CI зелёные.

## Не входит
- Парсинг стоимости/токенов из вывода агента (отдельная задача).
- Обработка rc != 0 как провала шага (отдельная задача).
- Стриминг куда-либо кроме файла и консоли.
