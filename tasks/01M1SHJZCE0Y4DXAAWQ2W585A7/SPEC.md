# SPEC: подзадачи деления заводит пульт из раздела «Деление» SPEC при approve

## Контекст

Скил `skills/spec-authoring.md` («Нарезка на 2–4 подзадачи») сегодня
велит аналитику «заведи подзадачи командой `cmd_new`», но инвариант
«пульт только из главной копии» (T056) запрещает команды пульта из
worktree роли — analyst не может исполнить собственный скил. Третий
подряд случай класса «скил отстаёт от механики» (копилка 05.09,
docs/backlog.md, приоритет 2). Решение Оператора 05.09: у роли
появляется штатный канал заявки на подзадачу через артефакт (раздел
SPEC), заводит подзадачи сам пульт при `approve` на `spec_gate`.

## Требования

1. Формат заявки на деление — новая секция `## Деление` в
   `templates/SPEC.md`, состоящая из 2–4 подразделов `### <название
   подзадачи>` (по одному на подзадачу). Каждый подраздел несёт:
   заголовок-название (строка), список полей `Зоны:` и `Порядок:` (для
   первой части — «первая, без зависимостей»; для остальных —
   «после части N»), необязательное поле `Рамка:` (бюджет $), и текст
   ТЗ подзадачи — свободный текст после полей, до следующего `###`
   или конца секции. `scripts/guard.py` проверяет формат: число
   подразделов в диапазоне 2–4, наличие обязательных полей (название,
   зоны, порядок, непустой текст ТЗ) у каждого, и что каждая зона
   подраздела входит либо в зоны родителя (frontmatter `zones:`),
   либо в общие зоны (`orchestrator/config.py::COMMON_ZONES`) — не
   режет зону родителя поперёк.
2. При `approve` на `spec_gate` SPEC, несущего заполненную секцию
   `## Деление`, пульт заводит подзадачи той же механикой, что
   `catalog.cmd_new` (сама функция либо её внутренняя реализация,
   решает разработчик на этапе PLAN): название и рабочая копия ТЗ —
   из подраздела; `TZ.md` подзадачи — текст ТЗ подраздела с
   добавленной первой строкой «Родительская задача: <id родителя> —
   <название родителя>»; поля `Зоны:`/`Рамка:` подраздела остаются
   текстом внутри `TZ.md` (аналитик подзадачи прочитает их и оформит
   `zones:`/`budget_usd` своего SPEC как обычно — эта задача не учит
   `cmd_new` новым параметрам зон/бюджета). Родительская задача при
   этом переходит в состояние `killed` — в коде сегодня нет
   отдельного состояния «поделена» (`orchestrator/config.py:483`,
   таблица `AUTO_STOP` перечисляет все состояния FSM: `killed` —
   единственное терминальное непродолжаемое состояние с подходящим
   смыслом) — с записью в журнал родителя «поделена на: <id1>, <id2>,
   ...» (перечень id всех заведённых подзадач одной строкой).
3. Идентификаторы заведённых подзадач печатаются Оператору сразу по
   завершении `approve`. Повторный `approve` того же родителя не
   заводит дублей: обеспечивается тем, что после первого успешного
   `approve` состояние родителя больше не `spec_gate` (`killed`) — код
   `_cmd_approve` обрабатывает ветку деления только при входе в
   состоянии `spec_gate` (`orchestrator/fsm.py`), а для `killed`
   срабатывает существующая ветка `else: печатает «нечего
   подтверждать»` — задача этой SPEC зафиксировать это свойство тестом
   (AC-12), не вводить отдельную проверку по тексту журнала.
4. Приложением к PLAN (пути меняет только Оператор — `skills/`,
   `templates/` — `conventions-core`, «Никогда: ... правка ...
   templates/ / skills/»): три unified-диффа, каждый провален через
   `git apply --check` на чистом дереве до сдачи, что подтверждается
   в PLAN.md:
   - `templates/SPEC.md` — секция `## Деление` (формат по требованию 1)
     рядом с существующей `## Оценка объёма и деление`;
   - `skills/spec-authoring.md` — в «Нарезка на 2–4 подзадачи» фраза
     «Заведи подзадачи командой `cmd_new`» заменяется описанием
     раздела `## Деление` (аналитик оформляет заявку в SPEC, не зовёт
     команду пульта сам);
   - `docs/operator-gates.md`, гейт SPEC, п.6 — Оператор видит заявку
     на деление в секции `## Деление` SPEC и утверждает её тем же
     `approve` на `spec_gate` (без отдельной команды).
5. Тесты (`tests/`, юнит-слой): SPEC с корректной секцией `## Деление`
   (2 подраздела) — `approve` на `spec_gate` заводит 2 подзадачи с
   `TZ.md` и первой строкой-ссылкой на родителя, журнал родителя несёт
   запись «поделена на: ...» с обоими id; повторный `approve` того же
   родителя не заводит новых задач и не дублирует запись журнала;
   секция `## Деление` без обязательного поля одного из подразделов —
   `scripts/guard.py` отказывает и называет поле; зона подраздела вне
   зон родителя и вне общих зон — `scripts/guard.py` отказывает.
   Существующие тесты `cmd_new` (`tests/test_catalog_new_race.py` и
   др.) и гейта SPEC (`tests/test_advance_guard.py`,
   `tests/test_zones_approve.py`, `tests/test_guard_split_signals.py`)
   остаются зелёными без ослабления.

## Критерии приёмки

AC-1. `templates/SPEC.md` несёт новую секцию `## Деление`: 2–4
подраздела `### <название>`, у каждого — поля `Зоны:` и `Порядок:`
(первая часть — «первая, без зависимостей»; остальные — «после части
N»), необязательное поле `Рамка: $N`, и текст ТЗ подзадачи (свободный
текст после полей до следующего `###` или конца секции).

AC-2. `scripts/guard.py` отказывает SPEC, если число подразделов
секции `## Деление` меньше 2 или больше 4 — сообщение называет
фактическое число.

AC-3. `scripts/guard.py` отказывает SPEC, если у подраздела секции
`## Деление` отсутствует обязательное поле (название, `Зоны:`,
`Порядок:` либо пуст текст ТЗ) — сообщение называет отсутствующее
поле и подраздел.

AC-4. `scripts/guard.py` отказывает SPEC, если хотя бы одна зона
подраздела секции `## Деление` не входит ни в зоны родителя
(frontmatter `zones:`), ни в общие зоны
(`orchestrator/config.py::COMMON_ZONES`) — сообщение называет
непокрытую зону и подраздел.

AC-5. `approve` на `spec_gate` SPEC, несущего заполненную (без ошибок
guard) секцию `## Деление`, заводит по одной подзадаче на каждый
подраздел той же механикой, что `catalog.cmd_new`: название — из
заголовка подраздела; `TZ.md` подзадачи — текст ТЗ подраздела с первой
строкой «Родительская задача: <id родителя> — <название родителя>».

AC-6. Родительская задача при успешном заведении подзадач (AC-5)
переходит в состояние `killed` с записью в журнал «поделена на:
<id1>, <id2>, ...» — перечень id всех заведённых на этом `approve`
подзадач.

AC-7. Идентификаторы заведённых подзадач печатаются на экран по
завершении `approve` из AC-5.

AC-8. Повторный `approve` родителя, уже находящегося в `killed`
(после AC-6), не заводит новых подзадач и не изменяет журнал — ветка
обработки состояния в `orchestrator/fsm.py::_cmd_approve` не
срабатывает вне состояния `spec_gate`.

AC-9. SPEC без секции `## Деление` (обычный случай, без заявки на
деление) не меняет поведение существующего `approve` на `spec_gate`
— переход в `tests_writing`/`in_dev` по прежним правилам (skip_tests/
AC-разметка), без создания подзадач.

AC-10. `templates/SPEC.md`, `skills/spec-authoring.md`,
`docs/operator-gates.md` (гейт SPEC, п.6) — три unified-диффа
приложены к PLAN.md, каждый проверен `git apply --check` на чистом
дереве, подтверждение — строкой в PLAN.md (требование 4).

AC-11. Тест: SPEC с корректной секцией `## Деление` (2 подраздела) —
`approve` на `spec_gate` заводит 2 подзадачи, у каждой `TZ.md` несёт
первую строку-ссылку на родителя; журнал родителя содержит запись
«поделена на: ...» с обоими id.

AC-12. Тест: повторный `approve` того же (уже `killed`) родителя не
создаёт новых задач и не добавляет вторую запись «поделена на:...» в
журнал.

AC-13. Тест: секция `## Деление` с подразделом без обязательного поля
— `scripts/guard.py` отказывает и называет отсутствующее поле.

AC-14. Тест: секция `## Деление` с зоной подраздела вне зон родителя и
вне общих зон — `scripts/guard.py` отказывает и называет зону.

AC-15. Существующие тесты `cmd_new` (`tests/test_catalog_new_race.py`
и др.) и гейта SPEC (`tests/test_advance_guard.py`,
`tests/test_zones_approve.py`, `tests/test_guard_split_signals.py`)
остаются зелёными без ослабления.

## Оценка объёма и деление

Сработавшие сигналы: число критериев приёмки (15 ≥ 10, порог
`config.SPLIT_SIGNAL_AC_COUNT`); бюджет (`budget_usd` 35 ≥ 30, порог
`config.SPLIT_SIGNAL_BUDGET_USD`); затронут инвариантный механизм
(`scripts/guard.py` упомянут в `docs/invariants.md:84`).

Монолит (материал для решения Оператора на гейте, не решение):
задача одной механикой связывает три компонента, которые не мержимы
по отдельности с зелёной планкой —
- формат секции `## Деление` (`templates/SPEC.md` + guard-проверка,
  требование 1) сам по себе бесполезен без потребителя;
- потребитель — переход `approve`/`spec_gate` (`orchestrator/fsm.py`,
  требования 2-3), который не существует и не тестируется без уже
  проверенного guard'ом формата (AC-5..AC-9 читают ту же секцию, что
  проверяют AC-1..AC-4);
- документация роли (`skills/spec-authoring.md`,
  `docs/operator-gates.md`, требование 4) описывает механику,
  которой без двух предыдущих частей ещё нет — смерженная раньше
  них, она учит аналитика писать секцию, которую пульт ещё не умеет
  читать.

Резать по границам зон (единственный легитимный способ нарезки,
`skills/spec-authoring.md`) означало бы смержить формат без
потребителя, потребителя без формата, либо документацию без обоих —
каждое промежуточное состояние либо мёртвый код, либо ссылка на
несуществующую механику. `budget_usd: 35` — рамка, заданная ТЗ
Оператора напрямую (не эвристика калибровки), ниже дефолта
оркестратора ($50): решение об уровне бюджета для монолитной задачи
такого размера — за Оператором на этом гейте.

## Не входит

- Механика родительства в БД: связка «подзадача → родитель» остаётся
  текстом (первая строка `TZ.md` подзадачи), как и сегодня — нет
  колонки/таблицы, отдельного поля в `store`.
- Автоматический порядок запуска подзадач: поле `Порядок:` — только
  информация в `TZ.md` подзадачи для её будущего SPEC/PLAN, пульт не
  планирует и не блокирует старт подзадач по нему.
- Деление на этапе PLAN: секция `## Деление` — только SPEC/`spec_gate`,
  решение о делении на PLAN этой задачей не рассматривается.
