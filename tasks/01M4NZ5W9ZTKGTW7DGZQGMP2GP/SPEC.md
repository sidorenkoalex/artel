# SPEC: Наблюдение неослабления — двусторонний прогон каждого изменённого метода и замер расхода test_author (шаг 0)

## Контекст
Шаг 0 порядка работ по тестам конвейера (очередь Оператора 11.10, решение
Оператора 11.10.2026). Оператору нужны данные для решения об уровнях
строгости гейта неослабления (шаг 4): где текстовый вердикт гейта и
двусторонний прогон расходятся и падает ли новая версия теста на
изменённом утверждении или на предусловии. Сейчас двусторонний прогон
(`orchestrator/advance_gates/two_sided.py`) вызывается из
`_test_integrity_gate` (`orchestrator/advance_gates/test_integrity.py`
~1292–1366) только для методов, объявленных в «Меняемом поведении», его
плагин не пишет строку упавшего утверждения, а время прогона не
журналируется. Расход шагов test_author в отчёте не сведён. Задача
добавляет только наблюдение (запись в журнал) и отчёт — поведение гейта
не меняется (приём «сначала наблюдение, потом отказ», прецедент 01M3Y753).
Решения по неясным местам — ANSWER-1 (Оператор, 11.10.2026); мандат на
ослабление не выдан.

## Требования
1. Плагин двустороннего прогона (`_PLUGIN_SOURCE`) записывает для
   упавшего узла путь и номер строки места утверждения и текст этой
   строки; `Outcome` отдаёт их наружу. Место утверждения — последний кадр
   трассировки, чей файл совпадает с файлом узла (так `self.assert*`
   указывает на строку теста, а не на `unittest/case.py`). Если такого
   кадра нет (утверждение в помощнике другого файла) — последний кадр
   трассировки вне библиотек, и признак «в изменённых строках» для него —
   «неприменимо» (ANSWER-1, п.5). Вердикт двустороннего прогона
   (`refusals`, `results`) и его использование гейтом не меняются.
2. Наблюдение: на переходе `in_dev → verifying`, после текстового
   вердикта (`_evaluate`/`_journal_pass`) и до ветвления по нему, для
   КАЖДОГО изменённого метода из `ev.cmp.changes` с
   `base_source != head_source` (не только объявленного в «Меняемом
   поведении») выполняется двусторонний прогон и пишется запись в журнал
   действием «двусторонний прогон (наблюдение)», содержащая: адрес
   метода; текстовый вердикт (`ev.outcomes`); вид изменения (`kind`,
   `signs`); исход каждой стороны (утверждение / зелёный / иная
   причина); путь и строку упавшего утверждения; признак, входит ли эта
   строка в изменённые строки метода; длительность. Методы с
   `base_source == head_source` не прогоняются.
3. Признак «строка в изменённых строках метода» считается по каждой
   стороне отдельно (ANSWER-1, п.6): строка упавшего утверждения стороны
   «новая версия на базе» сверяется с изменёнными строками head-версии
   метода, строка стороны «старая версия на ветке» — с изменёнными
   строками base-версии метода (по диффу base/head метода).
4. Наблюдение не влияет на вердикт и переход: исключение, таймаут, сбой
   git при наблюдении дают запись в журнал с причиной, а переход идёт
   так же, как без наблюдения. Повторный `advance` на том же sha головы
   не гоняет наблюдение заново (основание — запись в журнале).
5. Наблюдение никогда не пишет действие «двусторонний прогон пройден»
   (`TWO_SIDED_PASSED_ACTION`) и не меняет «доказанность» метода ни для
   гейта мержа (`_proven_addresses`), ни для ревью-пакета
   (`review_lines`) (ANSWER-1, п.1г).
6. Включение наблюдения — флаг-атрибут `orchestrator/config.py`, по
   умолчанию включено. Предел времени на всё наблюдение одного перехода —
   константа `orchestrator/config.py`, по умолчанию 600 с. Таймаут каждой
   стороны прогона наблюдения — меньшее из
   `TWO_SIDED_PYTEST_TIMEOUT_SEC` и остатка предела; метод, на котором
   остаток исчерпан, и все следующие записываются с исходом «не прогнан:
   предел». Таймаут объявленного двустороннего прогона гейта не меняется
   (ANSWER-1, п.4). Для задачи канарейки наблюдение выключено.
7. Окружение тестов (ANSWER-1, п.1а): `tests/sandbox.py` выставляет флаг
   наблюдения выключенным рядом с подменой `config.ROLES` /
   `config.MODELS_LOCAL` (~436–439) с комментарием о причине; больше
   ничего в `tests/sandbox.py` не меняется. Боевое значение «включено»
   закреплено отдельным тестом по исходнику `orchestrator/config.py`, а
   не по значению атрибута после подмены.
8. Под выключенным флагом окружения тестов без правок остаются зелёными
   `TwoSidedTest::test_ac24_no_declaration_runs_nothing` и
   `TwoSidedTest::test_ac24_uncovered_finding_runs_nothing`
   (`tests/test_01m45fjd46bx45vhc36s4vs9qn_declared_change.py`
   ~1646–1691) и `tests/test_fsm_advance_gate_smoke.py` (ANSWER-1, п.1б).
   Существующие тесты гейта неослабления и двустороннего прогона не
   правятся.
9. Новые тесты на ВКЛЮЧЁННОМ флаге (в том числе на сценариях обоих
   `test_ac24_*`) доказывают неизменность вердикта (ANSWER-1, п.1в):
   непокрытая находка — тот же отказ, тот же текст отказа, состояние
   `in_dev`, запись наблюдения есть; объявленная смена — тот же вердикт и
   та же запись «двусторонний прогон пройден», что без наблюдения;
   находка, покрытая мандатом, — прежний вердикт; без записи объявления
   — переход проходит; сбой или таймаут наблюдения — прежний вердикт,
   отказа нет.
10. Замер расхода test_author без новой телеметрии: команда `report`
    (отдельным разделом существующего отчёта) по шагам test_author за
    окно `OPERATOR_WINDOW_DAYS` (14 дней, `orchestrator/report.py:53`;
    ANSWER-1, п.3) выводит: стоимость, токены, число вызовов инструментов
    по видам (из лога шага), число прогонов pytest и их суммарное время
    (из журнала), число созданных файлов и их строк — отдельно `tests/` и
    `acceptance_tests/`. Файлы считаются по различным путям строк
    `· Write <путь>` лога шага; строки — с диска по этому пути, если файл
    на месте, иначе «н/д» (ANSWER-1, п.2). Раздел только читает
    имеющиеся данные; `report` не вызывает git.
11. Сводка наблюдения: тот же отчёт выводит по записям требования 2
    таблицу «текстовый вердикт × исход двустороннего прогона × строка в
    изменённых».

## Критерии приёмки
AC-1. Для узла, упавшего на `self.assert*` (стиль `unittest` тестов
пульта) и на голом `assert`, `Outcome` двустороннего прогона несёт путь
файла теста, номер строки и текст строки утверждения; номер строки
совпадает с номером строки утверждения в файле теста (не строка
`unittest/case.py`). Для утверждения в помощнике другого файла пишется
последний кадр вне библиотек, а признак «в изменённых строках» —
«неприменимо». `refusals` и `results` двустороннего прогона на тех же
входах прежние.

AC-2. Изменённый, но не объявленный в «Меняемом поведении» метод на
переходе `in_dev → verifying` при включённом флаге получает запись
журнала «двусторонний прогон (наблюдение)» с адресом метода, текстовым
вердиктом, `kind` и `signs`, исходом каждой стороны, путём и строкой
упавшего утверждения, признаком «в изменённых строках» и длительностью.

AC-3. Метод из `ev.cmp.changes` с `base_source == head_source`
двусторонним прогоном наблюдения не прогоняется.

AC-4. Признак «строка в изменённых строках метода» считается по каждой
стороне отдельно и проверяется на фикстуре, где правка метода сдвигает
номера строк между base и head: признак истинен, когда упавшее
утверждение изменено между base и head метода, и ложен, когда упавшее
утверждение не изменено.

AC-5. Сбой наблюдения — исключение, таймаут, сбой git (в том числе
подменённый pytest, который падает или зависает) — даёт запись в журнал
с причиной; исход перехода `in_dev → verifying` совпадает с исходом без
наблюдения, отказа из-за наблюдения нет.

AC-6. Повторный `advance` на том же sha головы ветки, для которого запись
наблюдения уже есть в журнале, наблюдение не повторяет (новых прогонов
и новых записей наблюдения нет).

AC-7. При включённом флаге вердикт гейта неизменен: в сценарии
`test_ac24_uncovered_finding_runs_nothing` — тот же отказ, тот же текст
отказа, состояние `in_dev`, запись наблюдения есть; в сценарии
`test_ac24_no_declaration_runs_nothing` (нет записи объявления) —
переход проходит; при объявленной смене — тот же вердикт и та же запись
«двусторонний прогон пройден», что без наблюдения; при находке,
покрытой мандатом, — прежний вердикт.

AC-8. Наблюдение ни в одном сценарии (включая непокрытую находку и
необъявленный метод с зелёными сторонами) не пишет действие
`TWO_SIDED_PASSED_ACTION`; множество `_proven_addresses` для гейта мержа
и строки `review_lines` ревью-пакета совпадают с полученными без
наблюдения.

AC-9. Флаг наблюдения в исходнике `orchestrator/config.py` имеет значение
«включено», предел времени — 600 с (проверка по исходнику, не по
атрибуту после подмены `tests/sandbox.py`). При выключенном флаге
наблюдение не выполняется (ни прогонов, ни записей). Для задачи
канарейки наблюдение не выполняется.

AC-10. Таймаут стороны прогона наблюдения — меньшее из
`TWO_SIDED_PYTEST_TIMEOUT_SEC` и остатка предела; при исчерпанном
пределе метод, на котором он исчерпан, и все следующие записываются с
исходом «не прогнан: предел»; таймаут объявленного двустороннего прогона
гейта остаётся `TWO_SIDED_PYTEST_TIMEOUT_SEC`.

AC-11. Ветка задачи меняет в `tests/sandbox.py` только выставление
флага наблюдения выключенным рядом с подменой `config.ROLES` /
`config.MODELS_LOCAL`, с комментарием о причине; файлы
`tests/test_01m45fjd46bx45vhc36s4vs9qn_declared_change.py` и
`tests/test_fsm_advance_gate_smoke.py` веткой не изменены.

AC-12. Отчёт `report` выводит для шагов test_author за окно
`OPERATOR_WINDOW_DAYS`: стоимость, токены, число вызовов инструментов по
видам, число прогонов pytest и их суммарное время, число созданных файлов
и их строк отдельно для `tests/` и `acceptance_tests/`; файл, который
упомянут строкой `· Write <путь>` лога шага, но отсутствует на диске,
даёт «н/д» в числе строк. Построение отчёта не вызывает git.

AC-13. Отчёт `report` выводит сводку записей наблюдения — таблицу
«текстовый вердикт × исход двустороннего прогона × строка в изменённых»
с числами по записям журнала.

Сработавшие сигналы: число затрагиваемых файлов зоны (6 записей, из них
3 — общие зоны `orchestrator/config.py`, `docs/codebase-map.md`,
`tests/`; собственных модулей три: `two_sided.py`, `test_integrity.py`,
`report.py`); число критериев приёмки ≥ 10 (13 — рост от условий
ANSWER-1 к неизменности вердикта); `budget_usd` ≥ $30; зона задевает
механизм инварианта 38 (`docs/invariants.md`, гейт неослабления).

Решение — монолит (утверждает Оператор). Материал для решения:
- Инвариантный механизм задачей не меняется: вердикт и отказы гейта
  неослабления прежние (требования 4, 5, 9; AC-5, AC-7, AC-8),
  добавляются только запись в журнал и отчёт — сигнал по инварианту 38
  здесь о соседстве кода, не о смене поведения.
- Технически возможная нарезка — «плагин + наблюдение» (`two_sided.py`,
  `test_integrity.py`, `config.py`, `tests/`) первой и «отчёт»
  (`report.py`, `tests/`) после неё; каждая часть мержима сама. Но
  сводка требования 11 читает формат записи требования 2, и разнесённые
  по двум задачам формат и его читатель сверяются только на втором
  мерже; а две задачи по планке не ниже $25 каждая выходят за рамку
  ТЗ ($35). Атомарности смены механики, запрещающей нарезку, нет —
  довод за монолит в объёме (три собственных модуля) и рамке Оператора.
- Бюджет: рамка ТЗ $35; калибровка для 13 критериев при трёх собственных
  модулях даёт ~45 — выше рамки не поднимаю, решение о рамке за
  Оператором на гейте SPEC.

## Не входит
- Изменение вердикта и отказов гейта неослабления (шаг 4, через ADR).
- Двусторонний прогон (и наблюдение) на гейте мержа.
- Телеметрия времени отдельных вызовов инструментов; новая телеметрия
  для замера test_author вообще — только чтение имеющихся лога шага,
  журнала и файлов на диске.
- Вызов git из `report` (ANSWER-1, п.2) и новый аргумент командной
  строки `report` (`orchestrator/artel.py` вне зон задачи): период —
  существующее окно `OPERATOR_WINDOW_DAYS`.
- Правка существующих тестов гейта неослабления и двустороннего прогона
  (`tests/test_test_integrity_gate.py`,
  `tests/test_guard_assertion_changes.py`,

  `tests/test_fsm_advance_gate_smoke.py` и прочих) и любые правки
