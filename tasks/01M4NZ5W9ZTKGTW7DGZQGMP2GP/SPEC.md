# SPEC: Наблюдение неослабления — двусторонний прогон каждого изменённого метода и замер расхода test_author (шаг 0)

## Контекст
Шаг 0 порядка работ по тестам конвейера (очередь Оператора 11.10, решение
Оператора 11.10.2026). Оператору нужны данные для решения об уровнях
строгости гейта неослабления (шаг 4): где текстовый вердикт гейта и
двусторонний прогон расходятся и падает ли новая версия теста на
изменённом утверждении или на предусловии. Сейчас двусторонний прогон
(`orchestrator/advance_gates/two_sided.py`) вызывается из
`_test_integrity_gate` (`orchestrator/advance_gates/test_integrity.py`
~1324–1365) только для методов, объявленных в «Меняемом поведении», его
плагин не пишет строку упавшего утверждения, а время прогона не
журналируется. Расход шагов test_author в отчёте не сведён. Задача
добавляет только наблюдение (запись в журнал) и отчёт — поведение гейта
не меняется (приём «сначала наблюдение, потом отказ», прецедент 01M3Y753).

## Требования
1. Плагин двустороннего прогона (`_PLUGIN_SOURCE`) записывает для
   упавшего узла путь и номер строки последнего кадра теста (место
   утверждения) и текст этой строки; `Outcome` отдаёт их наружу. Вердикт
   двустороннего прогона (`refusals`, `results`) и его использование
   гейтом не меняются.
2. Наблюдение: на переходе `in_dev → verifying`, после текстового
   вердикта (`_evaluate`/`_journal_pass`) и до ветвления по нему, для
   КАЖДОГО изменённого метода из `ev.cmp.changes` с
   `base_source != head_source` (не только объявленного в «Меняемом
   поведении») выполняется двусторонний прогон и пишется запись в журнал
   действием «двусторонний прогон (наблюдение)», содержащая: адрес
   метода; текстовый вердикт (`ev.outcomes`); вид изменения (`kind`,
   `signs`); исход каждой стороны (утверждение / зелёный / иная
   причина); путь и строку упавшего утверждения; признак, входит ли эта
   строка в изменённые строки метода (по диффу base/head метода);
   длительность. Методы с `base_source == head_source` не прогоняются.
3. Наблюдение не влияет на вердикт и переход: исключение, таймаут, сбой
   git при наблюдении дают запись в журнал с причиной, а переход идёт
   так же, как без наблюдения. Повторный `advance` на том же sha головы
   не гоняет наблюдение заново (основание — запись в журнале).
4. Включение наблюдения — флаг в `orchestrator/config.py`, по умолчанию
   включено. Предел времени на всё наблюдение одного перехода — константа
   `orchestrator/config.py`, по умолчанию 600 с; при исчерпании предела
   оставшиеся методы записываются с исходом «не прогнан: предел». Для
   задачи канарейки наблюдение выключено.
5. Замер расхода test_author без новой телеметрии: команда `report`
   (отдельным разделом существующего отчёта) по задачам выводит для шагов
   test_author: стоимость, токены, число вызовов инструментов по видам
   (из лога шага), число прогонов pytest и их суммарное время (из
   журнала), число созданных файлов `tests/` и их строк. Раздел только
   читает уже имеющиеся данные.
6. Сводка наблюдения: тот же отчёт выводит по записям требования 2
   таблицу «текстовый вердикт × исход двустороннего прогона × строка в
   изменённых».

## Критерии приёмки
AC-1. Для упавшего узла двустороннего прогона `Outcome` несёт путь файла
теста, номер строки и текст строки упавшего утверждения; номер строки
совпадает с номером строки `assert` в файле теста. `refusals` и
`results` двустороннего прогона на тех же входах прежние.

AC-2. Изменённый, но не объявленный в «Меняемом поведении» метод на
переходе `in_dev → verifying` получает запись журнала «двусторонний
прогон (наблюдение)» с адресом метода, текстовым вердиктом, `kind` и
`signs`, исходом каждой стороны, путём и строкой упавшего утверждения и
длительностью; вердикт гейта прежний — отказ по находке остаётся тем же
отказом, пропуск — пропуском.

AC-3. Метод из `ev.cmp.changes` с `base_source == head_source`
двусторонним прогоном наблюдения не прогоняется.

AC-4. Признак «строка в изменённых строках метода» в записи наблюдения
истинен, когда упавшее утверждение изменено между base и head метода, и
ложен, когда упавшее утверждение не изменено.

AC-5. Сбой наблюдения — исключение, таймаут, сбой git (в том числе
подменённый pytest, который падает или зависает) — даёт запись в журнал
с причиной; исход перехода `in_dev → verifying` (переход либо тот же
отказ гейта) совпадает с исходом без наблюдения.

AC-6. Повторный `advance` на том же sha головы ветки, для которого запись
наблюдения уже есть в журнале, наблюдение не повторяет (новых прогонов
и новых записей наблюдения нет).

AC-7. Флаг `config` по умолчанию включён, предел времени по умолчанию —
600 с. При выключенном флаге наблюдение не выполняется. При исчерпанном
пределе оставшиеся методы записываются с исходом «не прогнан: предел».
Для задачи канарейки наблюдение не выполняется.

AC-8. Отчёт `report` выводит для шагов test_author: стоимость, токены,
число вызовов инструментов по видам, число прогонов pytest и их
суммарное время, число созданных файлов `tests/` и их строк.

AC-9. Отчёт `report` выводит сводку записей наблюдения — таблицу
«текстовый вердикт × исход двустороннего прогона × строка в изменённых»
с числами по записям журнала.

## Оценка объёма и деление
Прогноз диффа: 40 КиБ (плагин и `Outcome` ~1–2 КиБ, наблюдение в
`test_integrity.py` ~8 КиБ, раздел отчёта ~8 КиБ, константы `config`
<1 КиБ, тесты ~20 КиБ) — ниже половины потолка гейта ёмкости.

Сработавшие сигналы (по отказу guard): число затрагиваемых файлов зоны
(6 записей, из них 3 — общие зоны `orchestrator/config.py`,
`docs/codebase-map.md`, `tests/`; собственных модулей три:
`two_sided.py`, `test_integrity.py`, `report.py`); зона задевает механизм
инварианта 38 (`docs/invariants.md`, гейт неослабления).

Решение — монолит (утверждает Оператор). Материал для решения:
- Инвариантный механизм задачей не меняется: вердикт и отказы гейта
  неослабления прежние (требования 1, 3; AC-1, AC-2, AC-5), добавляются
  только запись в журнал и отчёт — сигнал по инварианту 38 здесь о
  соседстве кода, не о смене поведения.
- Технически возможная нарезка — «плагин + наблюдение» (`two_sided.py`,
  `test_integrity.py`, `config.py`, `tests/`) первой и «отчёт»
  (`report.py`, `tests/`) после неё; каждая часть мержима сама. Но
  сводка требования 6 читает формат записи требования 2, и разнесённые
  по двум задачам формат и его читатель сверяются только на втором
  мерже; а две задачи по планке не ниже $25 каждая выходят за рамку
  ТЗ ($35). Атомарности смены механики, запрещающей нарезку, нет —
  довод за монолит в объёме (три собственных модуля, 9 критериев) и
  рамке Оператора.
