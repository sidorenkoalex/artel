# SPEC: `answer` для задачи в `in_dev` (мандат на расширение зон), `zones-extend`, `amend-tests --from-branch`

## Контекст

Аудит обходных сценариев Оператора 06.09 нашёл два класса ручной
работы, которых быть не должно: четыре раза за день ANSWER Оператора
с мандатом на расширение зон клался в артефактную ветку руками
(scratch-worktree, `git update-ref`, push) — существующий канал
`answer` принимает файл только для задачи в `escalated`
(`orchestrator/answer.py:82`), а мандат на расширение зон
(`fsm_advance._answer_zones_mandate`) нужен, пока задача ещё в
`in_dev`/`review`. Один раз лок планки приёмки сдвинут прямой правкой
БД: разработчик поправил залоченный тест под решение Оператора,
автокоммит унёс правку в артефактную ветку, а `amend-tests` сравнивает
только с незакоммиченным рабочим деревом (`amend._worktree_changed_paths`)
и не видит уже закоммиченную автокоммитом правку — «нет изменений,
нечего фиксировать».

Эта задача закрывает оба класса штатными командами вместо ручных
обходов.

## Требования

1. `answer <id> <файл>` принимает задачу в состояниях `in_dev` и
   `review`, если файл несёт маркер «Расширение зон разрешено:», —
   тем же кодом коммита ANSWER-n в артефактную ветку, что и для
   `escalated`, без смены состояния задачи. Без маркера в этих
   состояниях — прежний отказ (`answer` доступна только для
   `escalated`).

2. Команда `zones-extend <id> <путь>[, <путь>]` пишет ANSWER-n с
   маркером мандата и, если PLAN.md ветки задачи уже несёт раздел
   «Расширение зон» с теми же путями, сразу применяет мандат к
   `tasks.zones_extension`.

3. `amend-tests <id> --reason … --from-branch` источником правки берёт
   расхождение `acceptance_tests/` между `tests_locked_sha` и головой
   артефактной ветки (не рабочим деревом); без флага поведение команды
   не меняется.

4. Существующее поведение `answer`, `amend-tests` и гейта зон вне
   описанных выше случаев не меняется.

5. `docs/operator-session.md` и `docs/operator-gates.md` документируют
   три новых пути вместо ручного коммита в артефактную ветку.

## Критерии приёмки

AC-1. `answer <id> <файл>` принимает задачу в состояниях `in_dev` и
`review`, если файл несёт маркер «Расширение зон разрешено:», —
коммитит ANSWER-n в артефактную ветку тем же кодом, что и для
`escalated`, без смены состояния задачи, и журналирует запись «ANSWER
создан (мандат на расширение зон: <пути>)». Без маркера в этих
состояниях — прежний отказ («`answer` доступна только для состояния
escalated»).

AC-2. Guard-проверка секции «## Ответы» ANSWER-n применяется одинаково
независимо от состояния задачи, в котором файл создан (`in_dev`,
`review` или `escalated`).

AC-3. Команда `zones-extend <id> <путь>[, <путь>]` создаёт ANSWER-n с
маркером «Расширение зон разрешено: <пути>» и текстом «мандат
Оператора: <пути>». Если PLAN.md ветки задачи уже несёт раздел
«Расширение зон» с теми же путями — команда сразу обновляет
`tasks.zones_extension` (после чего гейт зон `in_dev -> review`
пропускает файлы этих путей). Если раздела с такими путями в PLAN.md
нет — `zones_extension` не трогается, а журнал несёт запись «раздел
PLAN отсутствует — разработчик добавит на следующем шаге».

AC-4. `amend-tests <id> --reason … --from-branch` источником правки
берёт расхождение `acceptance_tests/` между `tests_locked_sha` и
головой артефактной ветки (не рабочим деревом). При расхождении —
журналирует список изменившихся файлов и сдвигает `tests_locked_sha`
на голову артефактной ветки с записью «правка планки», как обычный
`amend-tests`. Без расхождения — отказ «нет расхождения». Без флага
`--from-branch` поведение команды не меняется.

AC-5. Существующие `tests/test_answer*.py`, `tests/test_amend*.py` и
`tests/test_zones_gate.py` остаются зелёными без правки ассертов.

AC-6. `docs/operator-session.md` и `docs/operator-gates.md` обновлены
(unified-диф приложением к PLAN.md): описывают `answer` в `in_dev`/
`review`, `zones-extend` и `amend-tests --from-branch` как замену
ручному коммиту в артефактную ветку.

AC-7. Тест на мутацию: `answer` для задачи в `in_dev`/`review` с файлом БЕЗ
маркера «Расширение зон разрешено:» отказывает прежним сообщением; снятие
этой проверки (приём любого файла в `in_dev`) красит тест.

AC-8. Тест: `zones-extend` при наличии в PLAN.md ветки раздела «Расширение
зон» с теми же путями обновляет `tasks.zones_extension`, и гейт зон
пропускает дифф по этим путям; без раздела — запись журнала «раздел PLAN
отсутствует», `zones_extension` не меняется.

AC-9. Тест: `amend-tests --from-branch` при расхождении `acceptance_tests/`
между `tests_locked_sha` и головой артефактной ветки сдвигает лок на голову
с записью «правка планки» и перечнем файлов; без расхождения — отказ «нет
расхождения»; без флага — прежнее поведение по worktree (мутация: сдвиг
лока без расхождения — красный).

## Не входит

  состояний и сценариев, не перечисленных в критериях приёмки выше.
