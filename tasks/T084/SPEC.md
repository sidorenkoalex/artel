# SPEC: Исследование — watchdog живости конвейера

## Контекст
Роадмап P3, строка «Исследование: watchdog живости конвейера» ($15).
Сейчас нет механизма, который бы явно детектировал молчаливую смерть
или зависание агентного шага и auto-цикла: задача числится в
агентном состоянии, а живого процесса нет; либо шаг работает дольше
разумного порога без прогресса. Актуальность выросла: MAX_PARALLEL_TASKS
поднят до 10 (31.08, docs/roadmap.md) — при десятке одновременных
задач молчаливая смерть одного `auto` вероятнее, а заметить её
глазами Оператора труднее. Рядом уже существует несколько частично
пересекающихся механизмов (таймаут шага, health-check, alerts,
lease/liveness, стоп-кран топтания) — прежде чем строить что-то
новое, нужна карта того, что уже есть, и того, чего не хватает.
Выход этой задачи — предложение, не реализация.

## Требования

1. Собрать карту существующих механизмов, каждый — со ссылкой на
   код/задачу (файл:строка или T-номер) и выводом, что именно он
   детектит и НЕ детектит применительно к двум сценариям ТЗ:
   (a) задача числится в агентном состоянии, а живого процесса нет;
   (b) шаг работает дольше разумного порога без прогресса. Обязательные
   к рассмотрению механизмы: таймаут шага в runner (T022/T041);
   health-check C0 (планируемый, фаза C, ещё не реализован);
   alerts A3 и авто-закрытие T035; отказ №12 реестра v5 (возраст
   состояния, docs/audits/roadmap-audit-2026-08-24-v5-chief-engineer.md
   §1.5); lease/liveness (T044, T057, T062) и doctor-проверки leases;
   стоп-кран T038 и роадмап-строка «Стоп-кран: потолок топтания без
   отказа».
2. По карте из требования 1 — явно назвать дыры: конкретные сценарии
   молчаливой смерти/зависания шага или auto-цикла, которые НИ ОДИН
   из перечисленных механизмов не покрывает целиком.
3. Оценить кандидатов на закрытие найденных дыр — минимум три:
   heartbeat шага в журнал; возраст состояния в doctor; сторожевой
   прогон watchdog по расписанию (список не предрешает выбор —
   разработчик вправе оценить дополнительных кандидатов сверх этого
   списка). Для каждого кандидата — какие дыры из требования 2 он
   закрывает, что рядом можно переиспользовать, риски и стоимость.
4. Дать явную рекомендацию: что строить, в каком модуле/роли/фазе
   этому предстоит жить, что НЕ строить и почему — с оценками в
   стиле роадмапа (объём в $, по аналогии со строками docs/roadmap.md).
5. Код самого watchdog-механизма (любого из кандидатов) в объёме этой
   задачи не пишется — только предложение.
6. Предложение фиксируется отдельным постоянным файлом документа (не
   только содержанием PLAN.md) — путь и точное оформление на
   усмотрение разработчика при условии, что файл закоммичен в ветку
   задачи, переживёт закрытие T084 (не только в каталоге `tasks/T084/`,
   который система не подвергает ретеншну, но которому недостаёт
   заметности предложения из роадмапа) и несёт явную ссылку на T084
   и дату написания.

## Критерии приёмки

AC-1. Документ-предложение существует отдельным файлом, закоммичен в
ветку задачи, содержит все четыре раздела: карта существующих
механизмов (требование 1), явный список дыр (требование 2), оценка
кандидатов (требование 3), рекомендация (требование 4).

AC-2. Карта покрывает все шесть механизмов, перечисленных в
требовании 1 — по каждому указана ссылка на код/задачу и явный вывод
«детектит / не детектит» для обоих сценариев ТЗ (агентное состояние
без живого процесса; шаг дольше порога без прогресса).

AC-3. Оценены минимум три кандидата из требования 3 (heartbeat в
журнал, возраст состояния в doctor, сторожевой прогон по расписанию);
для каждого — вывод, какие дыры из AC-2 он закрывает, и оценка
стоимости/сложности.

AC-4. Рекомендация явно называет: что строить, в каком
модуле/роли/фазе этому предстоит жить, что НЕ строить — с
обоснованием по каждому пункту.

AC-5. Diff задачи не содержит кода нового детект-механизма
(heartbeat/возраст состояния в doctor/scheduled watchdog) — только
документ-предложение и, при необходимости, обновление строки T084 в
docs/roadmap.md.

## Не входит

- Реализация любого из кандидатов (heartbeat, возраст состояния в
  doctor, сторожевой прогон по расписанию) — только оценка.
- Окончательное решение, какой кандидат внедрять — рекомендация, не
  факт внедрения; запуск follow-up задачи (если он последует) —
  решение Оператора отдельным ТЗ.
- Реализация или изменение health-check C0 (фаза C ещё не начата) —
  в карте C0 упоминается только как планируемый механизм.
- Правки protected-paths (roles.yaml, gates.yaml, templates/, skills/,
  .github/) — документ-предложение живёт вне этих путей.
