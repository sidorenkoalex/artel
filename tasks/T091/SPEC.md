# SPEC: Рефакторинг: декомпозиция диспетчеров fsm/runner

## Контекст
Роадмап P3 «Декомпозиция длинных диспетчеров» (ревизия CR-2026-08-26-7);
решение Оператора 01.09 — «следующий содержательный заход в fsm/runner»
состоялся (T079/T082/T085–T087 нарастили обе зоны). Класс задачи —
«рефакторинг»: действует блок правил «Правила для ТЗ-черновиков класса
„рефакторинг" (из T015)» из skills/code-revision.md целиком. Поведение
не меняется — только внутренняя структура модулей.

## Требования
1. Декомпозиция ориентирована на `orchestrator/fsm.py` и
   `orchestrator/runner.py` — диспетчеры из заголовка задачи. Зоны-
   ориентиры, названные ТЗ (не предписание, декомпозицию предлагает
   исполнитель в PLAN): в `fsm.py` — `cmd_advance` (ветвление if/elif
   по состояниям, кандидат «обработчик на состояние»), `cmd_approve`
   (выросшие ветки merge_gate с ожиданием CI T087, эскалаций, гейтов),
   размер модуля целиком; в `runner.py` — `cmd_run` и `run_agent_once`
   (классификация ошибок T082 добавила веса). `orchestrator/doctor.py`
   (эвристика code-revision.md — модуль выше ~500 строк) и
   `orchestrator/auto.py` (цикл с verifying-опросом T086) — те же
   зоны-ориентиры ТЗ того же рода; включение их в объём этой задачи —
   на усмотрение разработчика в PLAN, SPEC этого не требует и не
   запрещает.
2. Поведение не меняется ни для одной из затронутых команд.
   Наблюдаемые поверхности, обязанные остаться идентичными: CLI-вывод
   всех команд, тексты и порядок событий журнала шагов, схема БД,
   имена файлов/веток/алертов, коды возврата. Зелёность полного
   существующего набора `tests/` — определение неизменности поведения.
3. Тесты (`tests/`) не меняются по сценариям и ассертам; допустимые
   правки — только строки импортов и адреса `mock.patch` (пути
   модулей) — точность сверяет ревьюер по diff.
4. Рефакторинг не несёт попутных улучшений, переименований поведения
   или новых механизмов; дедупликация кода допустима только для
   идентичных фрагментов.
5. PLAN обязан нести таблицу переносов (символ → откуда → куда) и
   явный план отката: revert одного merge возвращает систему к
   состоянию до рефакторинга.
6. До и после рефакторинга снимается смоук на живых данных пульта
   (`status`, `log`, `doctor` read-only); сравнение выводов
   фиксируется в артефактах задачи (PLAN.md или TEST_REPORT.md).

## Критерии приёмки

AC-1. `python3 -m unittest discover -s tests` зелёный на итоговом
коммите ветки задачи (тот же состав тестов, что до рефакторинга,
без семантических правок).

AC-2. Diff каталога `tests/` содержит только правки строк импортов и
адресов `mock.patch` — сценарии и ассерты не изменены (проверяется
ревьюером по diff на review_gate).

AC-3. CLI-вывод, тексты и порядок событий журнала шагов, схема БД,
имена файлов/веток/алертов и коды возврата всех команд, затронутых
рефакторингом, идентичны выводу до рефакторинга — подтверждается
смоуком (`status`, `log`, `doctor` read-only на живых данных пульта),
явное сравнение «до/после» зафиксировано в PLAN.md или TEST_REPORT.md.

AC-4. PLAN.md содержит таблицу переносов (колонки: символ → откуда →
куда) для каждого перенесённого элемента и явный план отката
(revert одного merge возвращает всё).

AC-5. Diff задачи не содержит правок вне `orchestrator/` (включая
регенерацию `docs/codebase-map.md` тем же коммитом, если правились
`*.py` в orchestrator/), `tests/` (только импорты/патчи по AC-2) и
артефактов задачи `tasks/T091/`; protected-paths (`no_paths` из
`targets.yaml`: `gates.yaml`, `roles.yaml`, `targets.yaml`,
`CLAUDE.md`, `.github/`, `templates/`, `skills/`,
`docs/invariants.md`, `tests/test_invariants.py`) не тронуты.

AC-6. guard и CI зелёные на итоговом коммите ветки задачи.

## Не входит
- Изменение поведения любых команд (CLI-вывод, журнал, схема БД,
  имена файлов/веток/алертов, коды возврата) — только структура кода.
- Правки `tests/` сверх импортов и адресов `mock.patch`.
- Правки protected-paths (`no_paths` из `targets.yaml`).
- Новые механизмы — задача только переносит существующий код.
