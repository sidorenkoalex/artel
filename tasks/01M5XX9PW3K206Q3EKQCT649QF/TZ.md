# GitLab, шаг В1: источник полного набора компонента — `full_suite: local | ci | both`, исходы тестов из отчёта задания CI

## Требуется

1. **Поля компонента** (`targets.py`, проверка при загрузке; без полей — поведение прежнее):
   - `full_suite`: `local` (по умолчанию) | `ci` | `both`;
   - `ci_job`: имя задания CI; обязательно при `ci` и `both`, запрещено при `local`;
   - `ci`/`both` допустимы только для записи, у которой хостинг поддерживает чтение отчёта задания (реализация `forge` имеет `job_test_report`); иначе — отказ загрузки с именем поля. Сравнение с литералом хостинга не используется (сторож А0).
   Поля доходят до профиля компонента (`project_profile.Profile`).
2. **Итог полного набора из CI** (приёмка, `acceptance._acceptance_suite_run`): для компонента с `ci` — итог берётся из задания `ci_job` в конвейере ровно этого sha (`forge.job_result` + `forge.job_test_report`). Зелёный — только если задание есть, не с правом падать, `success`, отчёт разобран и в нём нет `failed`/`error`. Нет задания, пропущено, ручное, идёт, отчёт не разобран или пуст — итог «неизвестно» (инвариант 41), не зелёный, с именованной причиной. `both` — нужны оба: локальный прогон и итог CI. Локально в режиме `ci` гоняются только тесты задачи (долгоживущие файлы и планка). Запись журнала называет источник: «полный набор: итог задания CI <ci_job>, конвейер <id>, sha <sha>, тестов <n>».
3. **Гейт неослабления по исходам в режиме `ci`** (`outcome_integrity.py`): исходы головы и базы — из отчётов задания `ci_job`, а не из локальных выписок.
   - Отчёт головы — конвейер ровно sha головы.
   - Отчёт базы — конвейер коммита точки ответвления (`_diff_base`/`_merge_base_of`); если у него нет задания `ci_job` с отчётом — конвейер любого коммита, дерево которого совпадает с деревом точки ответвления (сверка `git rev-parse <c>^{tree}`; кандидаты — родители коммита точки ответвления и головы влитых в неё MR, найденные только чтением). Найден — запись журнала «отчёт базы: конвейер <id> коммита <sha> (дерево совпадает с <точка>)». Не найден — отказ гейта с причиной «нет отчёта базы», не пропуск.
   - Перевод отчёта `forge` в `CaseResult` с идентификатором той же схемы, что у локальных исходов компонента; правило перевода `<classname>::<name>` → `<компонент>:<путь>::<имя>` задаёт SPEC; неоднозначный перевод — «неизвестно» для этого теста, а не совпадение.
   - Перепрогон красных и третья выписка в режиме `ci` не выполняются локально: красный в отчёте головы — красный.
4. **Компонент `local`** (по умолчанию) и артель — поведение, записи журнала и существующие тесты прежние.

Критерии приёмки:
- проверка записи: `ci` без `ci_job`, `ci_job` при `local`, `ci` у хостинга без отчётов — отказ загрузки с именем поля;
- приёмка в режиме `ci` на подменённом `forge`: `success` + разобранный отчёт без падений → зелёный; отчёт с `failed` → красный; задания нет / `manual` / `running` / отчёт `None` → «неизвестно», не зелёный; запись журнала с конвейером, sha и числом тестов;
- `both`: зелёный только при зелёных обоих источниках;
- гейт по исходам в режиме `ci`: тест, зелёный в отчёте базы и красный/пропавший в отчёте головы, — отказ (как у локальных исходов); база без задания, но с коммитом того же дерева, у которого отчёт есть, — гейт работает по нему (запись журнала); нет ни того, ни другого — отказ «нет отчёта базы»;
- локально в режиме `ci` запускаются только тесты задачи (шпион прогона не видит полного набора);
- для артели и компонента `local` существующие тесты приёмки, полного набора и гейта по исходам зелёные без правки.
