# SPEC-AUDIT: GitLab В1 — источник полного набора `full_suite: local | ci | both`, исходы из отчёта задания CI

## ТЗ и SPEC

Из ТЗ в SPEC перенесено: поля компонента (тр. 1), итог CI на приёмке (тр. 2),
режим `both` (тр. 3), автогейт (тр. 4), гейт по исходам с поиском отчёта базы

записях журнала (SPEC.md:30-34, :66-70, :97-100). Потерь требований ТЗ нет.

Расхождения:
1. **В SPEC есть правило, которого нет в ТЗ, и оно противоречит коду.**
   SPEC.md:76-77: в `both` «иначе — старший из двух итогов (красный старше
   «неизвестно»)». В ТЗ (`TZ.md`, тр. 2: «`both` — нужны оба») порядка нет. В коде
   действует обратный порядок: `components_full_suite` ставит «неизвестно» и
   «не начат» раньше красного (acceptance.py:3343-3345, :3358-3359), потому что
   `approve --accept-red` принимает любой незелёный итог, кроме
   `FULL_SUITE_NOT_STARTED` (fsm.py:1573-1588; «неизвестно» в такой форме —
   acceptance.py:384-387). С правилом SPEC пара «локальный красный + CI
   неизвестно» даёт красный итог, и `--accept-red` закрывает приёмку, хотя
   итог CI не установлен. Это обход инварианта 41 (см. «Пути обхода», п. 1).
2. В ТЗ кандидаты базы — «родители коммита точки ответвления и головы влитых в
   неё MR, найденные только чтением». SPEC.md:94-96 переносит это дословно, но
   не говорит, как найти «головы влитых MR»: в `forge` нет чтения MR по
   коммиту (forge.py:203-252: `mr_status` — по iid, `branch_pipeline` — по
   имени ветки), а `forge.py` по ТЗ только для чтения. На деле достижимы только
   родители по git (у коммита слияния второй родитель и есть перебазированная
   голова MR). Нужно явно сузить кандидатов до родителей либо назвать
   источник.
3. В ТЗ два указания расходятся: «Аналитик сверяет по коду все места выбора
   источника полного набора и вносит их файлы в зоны SPEC поимённо» и
   «`fsm_merge_gate.py` — только чтение». SPEC.md:382-387 нашёл место
   `fsm_merge_gate.py:1085-1093` (локальный полный набор на гейте мержа после
   приложений) и вывел его за рамки задачи, не задав вопроса Оператору. Значит,
   у компонента `ci` гейт мержа по-прежнему гоняет полный набор локально
   (если у задачи есть приложения), и требование «локально в режиме `ci` —
   только тесты задачи» (SPEC.md:71-73) на мерже не выполняется. Решить это
   может только Оператор.

## Пути обхода гейтов

1. **`both` + `--accept-red`** (SPEC.md:76-77): локальный набор красный, CI
   «неизвестно» (задание `manual` или не запускалось) → итог «красный» →
   `approve --accept-red "<основание>"` проводит приёмку, хотя итог CI не
   установлен. Буквальное исполнение SPEC ломает инвариант 41.
2. **Форма «неизвестно» в режиме `ci`** не задана (SPEC.md:62-65): исполнитель
   вправе вернуть `FullSuiteRun(False, FULL_SUITE_RED, …)` с причиной —
   AC-5…AC-7 зелёные, а `--accept-red` принимает задание `ci_job`, которое не
   запускалось.
3. **Дерево приёмки ≠ дерево sha CI** (SPEC.md:52-53 «ровно sha, который
   принимается»): приёмка идёт на голове с наложенными приложениями PLAN
   (fsm.py:1553-1565, fsm_autogate.py:419-422), а отчёт CI — на голове без них.
   Для артели это различие отправляет итог в локальный прогон
   (acceptance.py:3431-3432); для `ci` SPEC правила не даёт, и зелёный CI
   головы примет дерево, которого CI не видел. То же со свежестью
   относительно main (:3433-3436) и с `approve --fresh-suite` (`fresh=True`,
   :3420).
4. **Нет отчёта головы → пропуск гейта**: требование SPEC.md:103-104 не
   покрыто ни одним AC (см. таблицу критериев).
5. **Компонент `ci` без `report`**: `in_outcome_bounds` ложно → гейт исходов
   пропускается молча, и режим `ci` гейта не задействуется вовсе. SPEC не
   требует `report` при `ci` и не называет такой пропуск.
6. **Набор задания CI задаёт ветка**: голова читает отчёт конвейера, который
   собран по конфигурации CI самой ветки. На приёмке проверяется только «нет
   `failed`/`error` и отчёт не пуст» (SPEC.md:56-59), поэтому задание, сужённое
   до малого набора, даёт зелёный. От этого защищают гейт исходов (пропавшие
   тесты → GONE) и гейт зон/защищённых путей проекта — но только если
   компонент в границе (п. 5). SPEC стоит явно сослаться на эту защиту или
   сверять число тестов с базой.
