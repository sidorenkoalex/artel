**Отклонение К1 (расхождение ТЗ и решения П1 по следствию; вопрос
Оператору, не ошибка аналитика).** Критерий ТЗ: «отчёт с `failed` →
красный» (TZ.md, «Критерии приёмки», п. 2). Решение П1 делает «неизвестно»
итог задания в любом завершённом не-`success` статусе, «независимо от
содержимого отчёта» (SPEC, требование 2; AC-8 «… и при отчёте с
`failed`»). Но GitLab ставит заданию pytest с упавшими тестами статус
`failed`. Значит, настоящая краснота набора у компонента `ci` на приёмке
всегда будет «неизвестно». Красный итог (`FULL_SUITE_RED`, AC-7)
достижим, только когда задание `success` при упавших тестах в отчёте
(`|| true` и т. п.). Отсюда: `approve --accept-red` на компонент `ci` с
реальной краснотой не работает никогда. Защита fail-closed, ослабления
нет, но приёмка красного `ci`-компонента Оператором закрыта. Дефолт —
оставить как есть (решение П1 буквально); иначе — уточнить П1: `failed`
без права падать с отчётом, где есть `failed`/`error`, — красный.

## Пути обхода гейтов

1. **Обрезанный отчёт базы в статусе `failed` (остаток П2, принят
   Оператором).** Задание базы оборвано таймаутом раннера: статус
   `failed` без права падать, отчёт частичный. По П2 такой отчёт годен.
   Тест из необрезанной части базы, удалённый веткой, находки GONE
   (`compare` `:196-200`) не даст. Новая краснота головы всё равно
   остановится на `_ci_ready_or_wait` (`fsm_merge_gate.py:1522`), поэтому
   остаток узкий — только пропажа тестов. Оператор решил явно («failed
   без права падать — исходы из отчёта»), отклонением не поднимаю.
2. **«Красный» вместо «неизвестно» на приёмке.** После П1 закрыт: AC-8
   требует `is_unknown` для `failed`/`canceled` при любом отчёте. Обратная
   сторона — К1.
3. **Тихий отказ от G3б-2.** После П3 закрыт: AC-23.
4. **Набор задания сужен конфигурацией CI ветки.** Закрыт:
   - пропавший тест — GONE (AC-14);
   - `allow_failure` — «неизвестно» на приёмке и негодный отчёт на мерже
     (AC-8, AC-16, AC-17);
   - отчёт не выгружен — `None`.
5. **Неоднозначный перевод в базе у компонента без масок `tests`
   (замечание).** `_Files.is_test` без `tests` берёт пути из отчёта базы
   (`outcome_integrity.py:504-510`). Тест базы с неоднозначным переводом
   (модуль не найден) пути не даёт. Правка такого файла может не попасть
   в находки строгого режима. Случай редкий (у правильно найденного
   модуля путь есть), но SPEC его не называет; достаточно оговорки
   разработчику: путь неоднозначной записи всё равно учитывать в
   `base_paths`.
