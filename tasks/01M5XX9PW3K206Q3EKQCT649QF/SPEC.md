# SPEC: GitLab В1 — источник полного набора `full_suite: local | ci | both`, исходы тестов из отчёта задания CI

## Контекст
ADR-0029 п. 9 и инвариант 41 («неизвестный итог не зелёный»). Сейчас полный
набор компонента на приёмке гоняется локально; итог CI принимается только
у артели (`ci.accepted_full_suite`, `ci.py:1269`, отказ другим проектам
`:1275-1276`), отчёт тестов CI не читается. Гейт неослабления по исходам
(`advance_gates/outcome_integrity.py`) берёт исходы базы и головы только из
локальных прогонов выписок. Адаптер хостинга уже влит (А1.1, А1.2):
`forge.job_result`, `forge.job_test_report`, `forge.pipeline_status`,
`forge.branch_pipeline`. Задача даёт компоненту выбор источника полного
набора — локально, из задания CI или оба — и переводит гейт по исходам в
режиме `ci` на отчёты задания CI. У проекта на GitLab с вливанием MR
перебазированием конвейеры базовой ветки могут не содержать тестовых
заданий; дерево коммита слияния совпадает с деревом перебазированной
головы влитого MR (его второго родителя), у которой отчёт есть, — отсюда
поиск отчёта базы по совпадению дерева.

Ответ Оператора ANSWER-1 (27.10.2026, вопрос 1, вариант B): интерфейс
`forge` номер конвейера не отдаёт, `forge.py`/`gitlab_adapter.py` остаются
только для чтения; в записях журнала вместо номера конвейера — номер
задания: `id` последней попытки `ci_job` из `forge.pipeline_status(sha).jobs`
(выбор «наибольший `id`» среди заданий с именем `ci_job`).

Ответ Оператора ANSWER-2 (27.10.2026, батч после аудита SPEC 1 из 2; на
все семь вопросов — вариант A): локальный полный набор на мерже после
приложений PLAN остаётся (вопрос 1); в режиме `ci` — те же три условия
принятия итога CI, что у артели, невыполненное — «неизвестно» (вопрос 2);
кандидаты отчёта базы — только родители точки ответвления по git
(вопрос 3); красный тест в отчёте головы — находка BROKEN (вопрос 4);
утверждённая замена теста у компонента `ci` — отказ гейта с причиной
(вопрос 5); доказательство `_proven` в режиме `ci` не используется
(вопрос 6); компонент `ci`/`both` без `report` не загружается (вопрос 7).

Форма «неизвестно» полного набора в пульте — `FullSuiteRun` с исходом
`FULL_SUITE_NOT_STARTED` и деталью, начинающейся `UNKNOWN_PREFIX`
(`acceptance.py:353-356`, `acceptance.is_unknown` `:384`); только её
`approve --accept-red` не принимает (`fsm.py:1573-1582`).

## Требования

1. **Поля компонента.** Запись компонента в `targets.yaml` принимает поля
   `full_suite` и `ci_job` (`targets.COMPONENT_FIELDS`, проверка при
   загрузке):
   - `full_suite`: `local` | `ci` | `both`; без поля — `local`;
   - `ci_job`: имя задания CI; обязательно при `ci` и `both`, запрещено при
     `local` (в том числе при `local` по умолчанию);
   - `ci`/`both` допустимы только у записи, у которой реализация хостинга
     в реестре `forge` имеет `job_test_report`; иначе — отказ загрузки.
     Проверка не сравнивает значение хостинга с литералом (сторож А0);
   - компонент с `full_suite: ci` или `both` обязан иметь поле `report`;
     без него — отказ загрузки (ANSWER-2, вопрос 7: иначе компонент
     выпадает из границы гейта исходов `in_outcome_bounds`,
     `advance_gates/acceptance.py:213-218`).
   Каждый отказ загрузки называет имя поля. Компонент без полей
   `full_suite`/`ci_job` загружается и ведёт себя как раньше. Значения полей
   доходят до профиля компонента `project_profile.Profile`.

2. **Итог полного набора из CI на приёмке** (`acceptance._acceptance_suite_run`).
   Для компонента с `full_suite: ci` итог полного набора берётся из задания
   `ci_job` в конвейере ровно sha головы ветки
   (`forge.job_result` + `forge.job_test_report`):
   - условия принятия итога CI — те же три, что у артели
     (`acceptance.py:3421-3440`; ANSWER-2, вопрос 2): дерево гейта (голова
     с наложенными приложениями PLAN) совпадает с деревом головного
     коммита; голова свежа относительно `origin/<базовая ветка проекта>`;
     условие выполнено — читается задание CI. Невыполненное условие (дерево
     другое, не прочитано, ветка не свежа, голова не прочитана) даёт итог
     «неизвестно» с именованной причиной, а не локальный полный прогон;
   - `--fresh-suite` (`fresh=True`) в режиме `ci` заново читает итог задания
     CI через `forge` и локального полного набора не запускает;
   - зелёный — только если задание есть, у него нет права падать
     (`allow_failure` ложно у задания `ci_job` в
     `forge.pipeline_status(sha).jobs`), статус `success`, отчёт разобран
     (`TestReport.outcomes` не `None`), не пуст и в нём нет исходов
     `failed`/`error`;
   - отчёт с исходом `failed` или `error` при прочих условиях зелёного —
     красный (`FULL_SUITE_RED`);
   - задания нет, задание пропущено, ручное (`manual`), идёт (`running`,
     `pending` и прочие незавершённые), с правом падать, отчёт `None` или
     пуст — итог «неизвестно» (инвариант 41) в форме `acceptance.is_unknown`
     (`FULL_SUITE_NOT_STARTED`, деталь с `UNKNOWN_PREFIX`) с именованной
     причиной в журнале;
   - запись журнала называет источник: «полный набор: итог задания CI
     <ci_job>, задание <job id>, sha <sha>, тестов <n>», где <job id> — `id`
     последней попытки `ci_job` (наибольший `id`) из
     `forge.pipeline_status(sha).jobs`, <n> — число тестов отчёта
     (ANSWER-1).
   Локально в режиме `ci` полный набор компонента на приёмке не гоняется:
   локально запускаются только тесты задачи — долгоживущие файлы задачи и
   планка.

3. **Режим `both`.** Нужны оба источника: локальный полный прогон
   компонента (как в `local`) и итог задания CI по правилам требования 2.
   Итог полного набора зелёный, только если зелёны оба. Иначе решает
   старший из незелёных итогов в порядке `components_full_suite`
   (`acceptance.py:3358-3359`): «неизвестно» старше красного — пара
   «локальный красный + CI неизвестно» даёт «неизвестно» в форме
   `acceptance.is_unknown`, которую `approve --accept-red` не принимает.

4. **Автогейт приёмки** (`fsm_autogate.py`, распознавание итога CI по
   записи журнала, `:426`) распознаёт зелёную запись требования 2 как итог
   CI полного набора — так же, как распознаёт итог CI артели сейчас.

5. **Гейт неослабления по исходам в режиме `ci`**
   (`advance_gates/outcome_integrity.py`, обе точки входа:
   `_outcome_integrity_gate_refuses` и `merge_gate_escalates`; сигнатуры не
   меняются). Для компонента с `full_suite: ci` исходы головы и базы
   берутся из отчётов задания `ci_job` (`forge.job_test_report`), а не из
   локальных прогонов выписок:
   - отчёт головы — конвейер ровно sha головы; нет разобранного отчёта
     головы (задания нет, отчёт `None`) — гейт не пропущен: отказ с
     именованной причиной (инвариант 41);
   - отчёт базы — конвейер коммита точки ответвления (та же точка, что
     `_diff_base`/`_merge_base_of`). Если у него нет задания `ci_job` с
     разобранным отчётом — конвейер родителя коммита точки ответвления
     (`git rev-list --parents -n1 <точка>`), дерево которого совпадает с
     деревом точки ответвления (сверка `git rev-parse <c>^{tree}`). Поиск —
     только чтением (git, чтение `forge`), без поиска MR через хостинг,
     без записи в хостинг и в репозиторий (ANSWER-2, вопрос 3);
   - отчёт базы найден у родителя — запись журнала «отчёт базы: задание
     <job id> коммита <sha> (дерево совпадает с <точка>)», где <job id> —
     `id` последней попытки `ci_job` из `forge.pipeline_status(<sha>).jobs`
     (ANSWER-1); гейт сравнивает исходы по этому отчёту;
   - нет отчёта ни у точки ответвления, ни у родителя того же дерева —
     отказ гейта с причиной «нет отчёта базы», не пропуск гейта;
   - перепрогон красных (`_rerun`) и третья выписка (`_prior_checkout`)
     в режиме `ci` локально не выполняются, выписки базы и головы
     (`_checkouts`) — тоже;
   - тест, зелёный в отчёте базы (`PASS_TO_PASS`) и красный (`failed`/
     `error`) в отчёте головы, — находка BROKEN («сломан правкой») с
     прежним действием отказа (ANSWER-2, вопрос 4); тест, зелёный в базе и
     отсутствующий в голове, — находка `compare` (пропал), как у локальных
     исходов;
   - утверждённая замена теста (`_replacement_findings`): нет записи в
     отчёте базы — REPLACED_MISSING, запись не зелёная — REPLACED_NOT_GREEN,
     как раньше; иначе — отказ гейта с причиной «замена теста не
     проверяема в режиме ci» (ANSWER-2, вопрос 5), не сбой подготовки;
   - на мерже доказательство `_proven` в режиме `ci` не используется: гейт
     каждый раз заново читает отчёты базы и головы и сравнивает их
     (ANSWER-2, вопрос 6).

6. **Перевод отчёта `forge` в `CaseResult`.** Каждая запись
   `<classname>::<name>` → статус отчёта задания переводится в `CaseResult`
   с идентификатором схемы `project_profile.test_id`
   (`<компонент>:<путь от корня репозитория>::<полное имя>`) — той же, что у
   локальных исходов компонента. Правило:
   - ключ делится на `classname` и `name` по первому `::`;
   - `classname` содержит `/` — это путь файла теста от рабочего каталога
     компонента (`workdir`), полное имя — `name`;
   - иначе `classname` — точечный путь: путь файла — самый длинный префикс
     его частей, для которого `<части через '/'>.py` есть файлом в дереве
     коммита отчёта под рабочим каталогом компонента (чтение дерева git,
     без выписки); остаток `classname` за модулем — класс, точки в нём
     заменяются на `::`; полное имя — `<класс>::<name>`, без класса —
     `name`;
   - путь от `workdir` приводится к пути от корня репозитория так же, как у
     локального разбора JUnit (`reporters/outcome.py`, `_root_path`);
   - статус: `success` → `passed`, `failed` → `failed`, `skipped` →
     `skipped`, `error` → `error`;
   - неоднозначный перевод — файл модуля не найден в дереве, статус вне
     перечня выше, два ключа отчёта дают один идентификатор — даёт исход
     «неизвестно» для этого теста: гейт не считает такой тест зелёным и не
     засчитывает его совпадением с тестом другой стороны.

7. **Компонент `local` и артель.** Для компонента `local` (явно или по
   умолчанию) и для артели поведение приёмки, полного набора и гейта по
   исходам, записи журнала и существующие тесты — прежние.

## Критерии приёмки

AC-1. Загрузка `targets.yaml` с компонентом `full_suite: ci` без `ci_job`
отказывает, и текст отказа называет поле `ci_job`.

AC-2. Загрузка `targets.yaml` с компонентом, у которого `ci_job` задан при
`full_suite: local` (и при отсутствии поля `full_suite`), отказывает, и
текст отказа называет поле `ci_job`.

AC-3. Загрузка `targets.yaml` с компонентом `full_suite: ci` (и `both`) у
записи, реализация хостинга которой в реестре `forge` не имеет
`job_test_report` (подменённый реестр), отказывает, и текст отказа
называет поле `full_suite`.

AC-4. Загрузка `targets.yaml` с компонентом `full_suite: ci` (и `both`) и
`ci_job`, но без поля `report`, отказывает, и текст отказа называет поле
`report`.

AC-5. Компонент с `full_suite: ci`, `ci_job` и `report` у записи с
реализацией хостинга, имеющей `job_test_report`, загружается;
`project_profile.Profile` компонента несёт значения `full_suite` и
`ci_job`; компонент без полей получает в профиле `full_suite` = `local`.

AC-6. Приёмка компонента `full_suite: ci` на подменённом `forge`: у sha
головы две попытки задания `ci_job` с разными `id`, последняя (наибольший
`id`) без права падать, `job_result` — `success`, отчёт разобран, не пуст и
без `failed`/`error` → итог полного набора зелёный; в журнале — запись
«полный набор: итог задания CI <ci_job>, задание <job id>, sha <sha>, тестов
<n>» с наибольшим `id`, sha головы и числом тестов отчёта.

AC-7. Приёмка компонента `full_suite: ci` на подменённом `forge`: `success`
и отчёт с исходом `failed` (и отдельно — с `error`) → итог полного набора
красный.

AC-8. Приёмка компонента `full_suite: ci` на подменённом `forge`: каждый из
случаев — задания `ci_job` нет; задание `manual`; задание `running`; задание
пропущено; отчёт `None`; отчёт пуст; задание с правом падать — даёт итог,
для которого `acceptance.is_unknown` истинно, с именованной причиной в
журнале; `approve --accept-red "<основание>"` такой итог не принимает
(приёмка отклонена); автогейт приёмки такой итог не принимает.

AC-9. Приёмка компонента `full_suite: ci`: дерево гейта (голова с
наложенным приложением PLAN) отличается от дерева головного коммита — итог
«неизвестно» (`acceptance.is_unknown`) с причиной о расхождении дерева;
голова не свежа относительно `origin/<базовая ветка>` — итог «неизвестно» с
причиной о свежести; в обоих случаях шпион не видит локального полного
прогона компонента.

AC-10. Приёмка компонента `full_suite: ci` с `fresh=True` (`approve
--fresh-suite`): итог задания CI прочитан через `forge` заново, шпион не
видит локального полного прогона компонента.

AC-11. Приёмка компонента `full_suite: both`: итог полного набора зелёный
только при зелёном локальном прогоне и зелёном итоге задания CI; зелёный
CI при красном локальном и красный CI при зелёном локальном — итог не
зелёный; «неизвестно» CI при зелёном локальном и «неизвестно» CI при
красном локальном — итог «неизвестно» (`acceptance.is_unknown`), который
`approve --accept-red` не принимает.

AC-12. Приёмка компонента `full_suite: ci`: шпион локального прогона видит
запуск только тестов задачи (долгоживущие файлы задачи и планка) и не видит
запуска полного набора компонента.

AC-13. Автогейт приёмки (`fsm_autogate.py`) распознаёт зелёную запись
журнала требования 2 как итог CI полного набора: текст его записи о
приёмке тот же, что для итога CI артели, а не текст локального прогона.

AC-14. Гейт по исходам в режиме `ci` на подменённом `forge` (обе точки
входа): тест, зелёный в отчёте базы и красный (`failed`, отдельно —
`error`) в отчёте головы, — отказ с находкой BROKEN; тест, зелёный в отчёте
базы и отсутствующий в отчёте головы, — отказ; при этом шпион не видит ни
выписки базы и головы, ни перепрогона красных, ни третьей выписки, ни
локального прогона.

AC-15. Гейт по исходам в режиме `ci`: у коммита точки ответвления нет
задания `ci_job` с отчётом, а у его родителя с тем же деревом отчёт есть —
гейт сравнивает исходы по отчёту родителя, в журнале — запись «отчёт
базы: задание <job id> коммита <sha> (дерево совпадает с <точка>)».

AC-16. Гейт по исходам в режиме `ci`: отчёта нет ни у точки ответвления,
ни у родителя того же дерева (в том числе родитель с отчётом есть, но его
дерево другое) — отказ гейта с причиной «нет отчёта базы».

AC-17. Гейт по исходам в режиме `ci` (обе точки входа): у головы нет
задания `ci_job` (и отдельно — отчёт головы `None`) — гейт не пропущен:
отказ с именованной причиной, не `None`.

AC-18. Гейт по исходам в режиме `ci` с утверждённой заменой теста:
заменяемого теста нет в отчёте базы — находка REPLACED_MISSING; тест в
отчёте базы не зелёный — REPLACED_NOT_GREEN; тест в отчёте базы зелёный —
отказ гейта с причиной «замена теста не проверяема в режиме ci», без сбоя
подготовки и без локального прогона.

AC-19. Гейт по исходам в режиме `ci` на мерже (`merge_gate_escalates`):
при наличии в журнале записи о пройденном гейте с той же головой и базой
гейт заново читает отчёты базы и головы через `forge` (шпион видит оба
чтения) и сравнивает их; локальной выписки нет.

AC-20. Перевод отчёта `forge` в `CaseResult` по правилу требования 6:
`classname` с `/` → путь из `classname`; точечный `classname`, модуль
которого есть файлом `.py` в дереве коммита, → путь модуля и класс с `::`;
для отчёта JUnit без атрибута `file`, с найденным модулем и без повтора
имени идентификатор совпадает с тем, что даёт локальный разбор
(`reporters/outcome.py` `parse_junit`) того же теста компонента; статусы
`success`/`failed`/`skipped`/`error` → `passed`/`failed`/`skipped`/`error`.

AC-21. Неоднозначный перевод — модуль не найден в дереве, статус вне
перечня, два ключа отчёта с одним идентификатором — даёт для этого теста
«неизвестно»: тест, зелёный в отчёте базы и неоднозначный в отчёте головы,
даёт отказ гейта, а не совпадение.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны 7 без общих зон (порог
`SPLIT_SIGNAL_ZONE_FILES` = 5); критериев приёмки 21 (порог
`SPLIT_SIGNAL_AC_COUNT` = 10); `budget_usd` = 70 (порог
`SPLIT_SIGNAL_BUDGET_USD`); зона задевает механизм инварианта 41
(`docs/invariants.md`, итог «неизвестно» не зелёный).

Решение — **нарезка на две части** по границе зон:

1. «Источник полного набора на приёмке» — поля компонента, итог из CI в
   режимах `ci`/`both`, распознавание записи автогейтом (требования 1–4, 7;
   AC-1…AC-13). Зоны: `targets.py`, `project_profile.py`, `acceptance.py`,
   `fsm_autogate.py`, `ci.py`. Самостоятельно мержима: поля без режима `ci`
   в записях не меняют поведения, а с режимом `ci` приёмка уже работает
   целиком. Гейт по исходам до части 2 остаётся на локальных выписках —
   это прежнее, рабочее поведение, не промежуточное нерабочее.
2. «Гейт по исходам из отчётов CI» — перевод отчёта в `CaseResult` и гейт
   неослабления в режиме `ci` (требования 5–7; AC-14…AC-21). Зоны:
   `advance_gates/outcome_integrity.py`, `reporters/outcome.py`. Опирается
   на поля `full_suite`/`ci_job` профиля из части 1 — без неё режим `ci`
   гейту не виден, поэтому идёт после части 1.

Рамки частей делят рамку Оператора $70: часть 1 — $40, часть 2 — $30.
