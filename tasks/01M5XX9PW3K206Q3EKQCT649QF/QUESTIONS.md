# QUESTIONS: GitLab В1 — источник полного набора `full_suite: local | ci | both`, исходы из отчёта задания CI

## Вопросы

Батч после возврата аудита SPEC 1 из 2 (SPEC-AUDIT.md). Здесь только
пункты, где нужно решение Оператора: пункты аудита 3, 7, 2, 4, 9, 10, 11.
Остальные пункты (1, 5, 6, 8, 12 и матрицу неослабления) аналитик закроет
в SPEC сам после ответа. Порядок «неизвестно» раньше красного в `both`
возьмётся из `components_full_suite` (acceptance.py:3358-3359). Форма

(fsm.py:1573-1584). Добавятся AC на эту форму и на «нет отчёта головы».
Вопросы отсортированы по блокирующести.

1. **Гейт мержа после приложений PLAN у компонента `full_suite: ci` (аудит п. 3).** В ТЗ два указания расходятся. Первое: «сверить все места выбора источника полного набора и внести их файлы в зоны». Второе: «`fsm_merge_gate.py` — только чтение». На мерже задачи с приложением PLAN полный набор после наложения гоняется локально (fsm_merge_gate.py:1084-1093, `acceptance.components_full_suite`). CI это дерево не видел: приложения накладываются только на мерже.
   - A) Оставить локальный полный набор на мерже после приложений как есть. Это единственное исключение из правила «локально в режиме `ci` только тесты задачи». В SPEC оно будет названо в «Не входит» решением Оператора.
     - ломается: ничего в коде. Если полный набор компонента `ci` локально не запускается (нужны сервисы CI), задача с приложением PLAN не пройдёт мерж: прогон будет красным или с таймаутом.
     - ослабляется: ничего. Проверка дерева после приложений полным набором остаётся (fsm_merge_gate.py:1084-1093).
     - цена: 0; объём SPEC не меняется.
     - чьё решение: Оператор.
   - B) В режиме `ci` отдавать на этом месте «неизвестно» с причиной «дерево после приложений не прогнано в CI». Правка — в `acceptance.components_full_suite` (в зоне), `fsm_merge_gate.py` не трогается.
     - ломается: задача с приложением PLAN у компонента `ci` не мержится без решения Оператора. Функцию также зовёт `outcome_integrity._full_run` (outcome_integrity.py:397) — там нужно отдельное различение.
     - ослабляется: ничего (строже прежнего).
     - цена: +1 требование и +1 AC, ~$3–5.
     - чьё решение: Оператор.
   - C) В режиме `ci` после приложений принимать итог CI головы без приложений.
     - ломается: дерево с приложениями уходит в main, не проверенное ни одним полным прогоном.
     - ослабляется: проверка дерева после приложений (fsm_merge_gate.py:1084-1093) снята для компонента `ci`.
     - цена: нужна правка `fsm_merge_gate.py` (вне зон по ТЗ) или обход через acceptance.py; мандат на ослабление.
     - чьё решение: Оператор.
   - дефолт: A — ничего не ослабляет и не трогает файл только для чтения. Исключение явно названо.

2. **Условия принятия итога CI на приёмке в режиме `ci` (аудит п. 7).** У артели итог CI принимается при трёх условиях: дерево гейта (голова плюс приложения PLAN, fsm.py:1553) совпадает с деревом головы, ветка свежа относительно origin/main и нет `--fresh-suite` (acceptance.py:3421-3440). Иначе полный набор гоняется локально. Для режима `ci` ТЗ это не задаёт, а локальный полный набор в режиме `ci` не гоняется.
   - A) Те же три условия. Если условие не выполнено (дерево другое или ветка не свежа) — итог «неизвестно» с именованной причиной, не локальный прогон. `--fresh-suite` в режиме `ci` заново читает итог задания CI и локального полного набора не запускает.
     - ломается: задача с приложением PLAN у компонента `ci` не проходит приёмку (дерево гейта ≠ дерево головы). Несвежую ветку нужно сначала подтянуть (`pull-main`).
     - ослабляется: ничего. Равенство дерева и свежесть, как у артели (acceptance.py:3434-3439), держатся и для `ci`.
     - цена: +2 AC (дерево, свежесть), ~$3.
     - чьё решение: Оператор.
   - B) Те же три условия, но при невыполненном условии и при `--fresh-suite` — откат на локальный полный набор компонента, как у артели (acceptance.py:3449-3457).
     - ломается: правило «локально в режиме `ci` только тесты задачи» (ТЗ, тр. 2) нарушается в этих случаях. Компонент, который нельзя прогнать локально, получит красный итог или таймаут, и тогда `--accept-red` его примет.
     - ослабляется: ничего в проверке дерева. Слабеет граница «в режиме `ci` только CI».
     - цена: +2 AC, ~$3.
     - чьё решение: Оператор.
   - C) Не сверять дерево гейта с деревом головы: приложения проверит локальный прогон на мерже (вопрос 1, A). Свежесть требуется.
     - ломается: на приёмке принимается дерево, которого CI не видел.
     - ослабляется: равенство дерева приёмки и дерева итога CI (acceptance.py:3434-3435) для `ci` снято. Остаётся только проверка на мерже.
     - цена: +1 AC; мандат на ослабление.
     - чьё решение: Оператор.
   - дефолт: A — по инварианту 41: итог, неприменимый к дереву приёмки, не зелёный и не принимается `--accept-red`.

3. **Кандидаты отчёта базы: «головы влитых в точку ответвления MR» (аудит п. 2).** Найти их нечем. В `forge` нет чтения MR по коммиту: `mr_status` ищет по iid, `branch_pipeline` — по имени ветки (forge.py:203-252). `forge.py`/`gitlab_adapter.py` только для чтения (ТЗ, ANSWER-1). У коммита слияния при rebase-вливании голова MR — второй родитель, её видно из git.
   - A) Сузить кандидатов до родителей коммита точки ответвления по git (`git rev-list --parents -n1`). Отдельного поиска MR нет. Голова влитого MR — родитель коммита слияния.
     - ломается: при вливании без коммита слияния (fast-forward, squash) голова MR не родитель. Отчёт базы тогда не найдётся, и будет отказ «нет отчёта базы».
     - ослабляется: ничего. Меньше кандидатов — чаще отказ, без пропуска гейта.
     - цена: 0.
     - чьё решение: Оператор (сужение формулировки ТЗ).
   - B) Искать головы MR через хостинг — нужна новая функция чтения в `forge`/`gitlab_adapter`.
     - ломается: ничего, но зоны расширяются на файлы, которые по ТЗ только для чтения.
     - ослабляется: ничего.
     - цена: +2 файла зоны, +1–2 AC, ~$6–10; пересечение с А-серией.
     - чьё решение: Оператор.
   - дефолт: A — вливание перебазированием с коммитом слияния (ТЗ, факт 6) им покрыто, а файлы только для чтения не трогаются.

4. **Вид находки на красный тест в отчёте головы без перепрогона (аудит п. 4).** `compare` (outcome_integrity.py:185-217) красноту `PASS_TO_PASS` не судит. Это делают перепрогоны `_rerun`/`_redness` (:407-447): BROKEN, UNSTABLE или FLAKY_ON_BASE. ТЗ перепрогоны в режиме `ci` запрещает: «красный в отчёте головы — красный». От вида находки зависит, каким мандатом её можно покрыть (`_cover` по виду).
   - A) Сразу BROKEN («сломан правкой»), действие `BROKEN_REFUSAL_ACTION`.
     - ломается: нестабильный тест, разово красный в CI головы, даёт отказ «сломан правкой». Снимается повторным конвейером или мандатом.
     - ослабляется: различение BROKEN/UNSTABLE/FLAKY_ON_BASE (outcome_integrity.py:430-447) в режиме `ci` недоступно по ТЗ. Отказ остаётся.
     - цена: 0.
     - чьё решение: Оператор.
   - B) Новый вид находки, например «красный в отчёте CI», отдельно от BROKEN.
     - ломается: мандаты, написанные под BROKEN, его не покрывают — нужен свой элемент мандата.
     - ослабляется: ничего.
     - цена: +1 вид находки в `outcome_integrity.py`, +1 AC, ~$2–3.
     - чьё решение: Оператор.
   - дефолт: A — прямое чтение ТЗ «красный — красный»: существующий вид отказа без нового словаря.

5. **Утверждённые замены тестов в режиме `ci` (аудит п. 9).** ТЗ запрещает третью выписку в режиме `ci`. Поэтому проверки прежних версий (PRIOR_RED/PRIOR_UNSTABLE, outcome_integrity.py:959-976) в этом режиме выключены — это решение ТЗ, в матрице оно будет записано. Но `_replacement_findings` (:739-766) без истории третьей выписки бросает `_Prepare` (:753-756). Значит, сейчас любая утверждённая замена у компонента `ci` — сбой подготовки гейта.
   - A) Отказ гейта с именованной причиной «замена теста не проверяема в режиме `ci`» (REPLACED_MISSING/REPLACED_NOT_GREEN по отчёту базы проверяются как раньше).
     - ломается: задача с утверждённой заменой у компонента `ci` не проходит гейт без решения Оператора.
     - ослабляется: ничего.
     - цена: +1 AC, ~$2.
     - чьё решение: Оператор.
   - B) Проверять только REPLACED_MISSING и REPLACED_NOT_GREEN по отчёту базы. Проверку REPLACED_NEEDLESS (прежняя версия красная на коде ветки) пропустить, и замена засчитывается строкой «заменён по SPEC».
     - ломается: ничего не отказывает.
     - ослабляется: доказательство, что прежняя версия заменяемого теста красная на коде ветки (outcome_integrity.py:757-763), у компонента `ci` снято.
     - цена: +1 AC; мандат на ослабление.
     - чьё решение: Оператор.
   - C) Для заменяемых тестов делать локальную третью выписку и перепрогон, как сейчас (исключение из ТЗ, тр. 3).
     - ломается: компонент, который нельзя прогнать локально, получает сбой подготовки.
     - ослабляется: ничего.
     - цена: +1 AC, ~$3; расходится с ТЗ.
     - чьё решение: Оператор.
   - дефолт: A — ничего не ослабляет, без локального прогона.

6. **Доказательство на мерже (`_proven`) в режиме `ci` (аудит п. 10).** Ключ компонента `_component_key` (outcome_integrity.py:813-826) снимается по выписке головы ради сумм файлов блокировки.      - ослабляется: ничего.
     - цена: +1 AC (шпион: локальной выписки нет, отчёты прочитаны на мерже), ~$2.
