# QUESTIONS: GitLab В1 — источник полного набора full_suite (local|ci|both), исходы из отчёта задания CI

## Вопросы

ТЗ хватает на всё, кроме одного места. Остальное (правило перевода
`<classname>::<name>` → `<компонент>:<путь>::<имя>`, кандидаты базы,
деление объёма) аналитик решит в SPEC сам, вопросов по этому нет.

1. **Откуда взять номер конвейера для записей журнала «полный набор: итог задания CI <ci_job>, конвейер <id>, sha <sha>, тестов <n>» (требование 2) и «отчёт базы: конвейер <id> коммита <sha> …» (требование 3)?** Интерфейс `forge`, который ТЗ объявляет только для чтения, номер конвейера не отдаёт. `forge.JobResult` (`orchestrator/forge.py:54-57`) — только `status`/`reason`. `forge.TestReport` (`forge.py:60-63`) — только `outcomes`/`reason`. `forge.Job` (`forge.py:33-39`) несёт `id` задания, а не конвейера. `BranchPipeline` (`forge.py:111-116`) — без номера. Внутри адаптера номер есть (`gitlab_adapter._last_attempt`, `gitlab_adapter.py:449-457`, первый элемент пары), но наружу не выходит. В зонах задачи нет способа получить «конвейер <id>» без правки файлов, закрытых на запись.
   - A) Добавить в зоны `orchestrator/forge.py` и `orchestrator/gitlab_adapter.py`, только для одного изменения: необязательное поле `pipeline: int | None = None` последним в `JobResult` и `TestReport`, адаптер GitLab заполняет его из `_last_attempt`. Записи журнала — ровно в формате ТЗ.
     - ломается: ничего у вызывающих — поле последнее и со значением по умолчанию. Задача трогает два файла, которые ТЗ объявило только для чтения; возможна пересечка с параллельными задачами Б-серии, если они правят `forge.py`.
     - ослабляется: ничего; «сторож А0» (реестр `forge.IMPLEMENTATIONS`, `forge.py:153`) не задет — новых сравнений с литералом хостинга нет.
     - цена: +2 файла зоны (всего 10), +1–2 критерия, ~+$5; сигнал деления по числу файлов срабатывает сильнее.
     - чьё решение: Оператор (расширение зон, закрытых в ТЗ на запись).
   - B) Оставить `forge.py`/`gitlab_adapter.py` только для чтения. В журнал вместо номера конвейера писать номер задания — `id` последней попытки `ci_job` из `forge.pipeline_status(sha).jobs` (тот же выбор «наибольший id», что у `_last_attempt`): «полный набор: итог задания CI <ci_job>, задание <job id>, sha <sha>, тестов <n>» и «отчёт базы: задание <job id> коммита <sha> (дерево совпадает с <точка>)».
     - ломается: текст двух записей журнала отличается от формулировки ТЗ (слово «конвейер» → «задание», другой номер); по номеру задания конвейер в GitLab находится одним переходом.
     - ослабляется: ничего — запись по-прежнему однозначно называет источник итога; инвариант 41 (`reporters/outcome.py:250`) не задет.
     - цена: ноль сверх текущего объёма; лишний вызов `pipeline_status` на sha.
     - чьё решение: Оператор (меняется формат записи, заданный в ТЗ).
   - C) Писать «конвейер ?» (номер неизвестен), формат ТЗ сохраняется буквально; номер появится, когда интерфейс `forge` его отдаст (отдельной задачей).
     - ломается: запись журнала не указывает, какой именно конвейер дал итог; AC «запись журнала с конвейером» выполняется только формально.
     - ослабляется: прослеживаемость источника итога (сейчас её держит запись `acceptance.py:3442` «прогон <run_id>» у артели).
     - цена: ноль.
     - чьё решение: Оператор.
   - дефолт: B — не трогает файлы, которые ТЗ закрыло на запись, и сохраняет однозначность источника. Отличается только слово и номер в записи журнала.
