# QUESTIONS: GitLab В1 — источник полного набора, исходы из отчёта задания CI (батч после аудита SPEC 2 из 2)

## Вопросы

Контекст батча: аудит SPEC 2 из 2 вернул SPEC (SPEC-AUDIT.md, п. 1–4).
Пункт 1 неисполним без решения Оператора: на переходе `in_dev → verifying`
гейт исходов (`fsm_advance.py:843`) стоит ДО сжатия ветки
(`fsm_advance.py:855-856`, `squash_before_mr`) и до пуша головы на origin
(`_origin_push_gate`, `fsm_advance.py:868`). В момент гейта у sha головы
конвейера нет, а при `squash_before_mr` на origin уходит другой sha — у
проверяемого sha конвейера не будет никогда. Требование 5 SPEC в нынешнем
виде (отчёт головы — конвейер ровно sha головы, нет отчёта — отказ) даёт
на `in_dev` вечный отказ для компонента `full_suite: ci`. `fsm_advance.py`
по ТЗ только для чтения (держит Б2.1), перенести гейт за пуш задача не
вправе. Пункты 3–4 аудита (AC-12, неточность про `approve`) аналитик
правит в SPEC сам после ответа; п. 3 вынесен вопросом 3 только потому,
что меняет формулировку критерия из ТЗ.

1. **Что делает гейт исходов на `in_dev → verifying` для компонента `full_suite: ci`, раз отчёта CI головы в этой точке нет?**
   - A) На `in_dev` гейт компонента `ci` судит по локальным выпискам базы и головы, как сейчас (`_checkouts`, `_rerun`, `_prior_checkout`); отчёты задания CI — только на гейте мержа (`merge_gate_escalates`). Второе названное исключение из правила «локально в режиме `ci` только тесты задачи» (рядом с ANSWER-2, вопрос 1) — в «Не входит» решением Оператора.
     - ломается: ТЗ требование 3 («исходы головы и базы — из отчётов задания `ci_job`, а не из локальных выписок») выполняется только на мерже; на `in_dev` в режиме `ci` локально гоняются два полных прогона набора (и перепрогон красных) — для проекта, выбравшего `ci` из-за тяжёлого набора, это прежняя цена прогона.
     - ослабляется: ничего — гейт на `in_dev` остаётся прежним (`outcome_integrity.py:925-981` `_judge`), на мерже добавляется сверка по отчётам CI; для `target-human` (мержа пультом нет, Б2.1) гейт по-прежнему работает на `in_dev` локально.
     - цена: меньше объёма части 2 (точка `in_dev` не меняется для `ci`); AC-14/AC-17/AC-18/AC-21 сводятся к точке мержа; бюджет части 2 ($30) держится.
     - чьё решение: Оператор (отступление от ТЗ требование 3 на одной точке входа).
   - B) На `in_dev` гейт компонента `ci` пишет в журнал «гейт исходов для головы … не исполнялся» (`NOT_RUN_LINE`, `outcome_integrity.py:84`) и пропускает; судит только мерж по отчётам CI.
     - ломается: на `in_dev` для `ci` нет ни локальных прогонов, ни сверки исходов — находка «сломан правкой» видна только на мерже, после ревью и приёмки (поздний и дорогой возврат).
     - ослабляется: гейт неослабления по исходам на `in_dev` (`fsm_advance.py:843` → `outcome_integrity.py:1143`) для `ci` выключен; для проектов с `target-human`, где мержа пультом нет (Б2.1), гейт исходов в режиме `ci` не работает вовсе — инвариант ADR-0026 п. 6 для них не держится ничем.
     - цена: дешевле всего в коде; цена — риск пропустить ослабление тестов у `target-human`.
     - чьё решение: Оператор (выключение гейта на точке входа).
   - C) Перенести гейт исходов на `in_dev` за сжатие и пуш головы (и ждать/читать конвейер пушнутого sha) — правка `fsm_advance.py`, отдельной задачей после Б2.1; в этой задаче часть 2 делается только для точки мержа, точка `in_dev` для `ci` — как в A до той задачи.
     - ломается: порядок рубежей `in_dev` (сейчас «все рубежи до сжатия», SPEC 01M5WDB7JY0VJGHVKCABA2QC5T, требование 7); ожидание конвейера на переходе — новый режим `advance`; `tests/test_fsm_advance_gate_smoke.py` сверяет журнал и порядок отказов байт-в-байт.
     - ослабляется: ничего в этой задаче (как A); в будущей — зависит от её SPEC.
     - цена: новая задача после Б2.1 (класс ~$40), эта задача — как A.
     - чьё решение: Оператор (новая задача, правка зоны Б2.1).
   - дефолт: A — гейт нигде не ослабевает и `fsm_advance.py` не трогается; B выключает гейт для `target-human` целиком, C — отдельная работа в зоне Б2.1.

2. **Гейт мержа в режиме `ci`: нет отчёта головы (задания `ci_job` нет, отчёт `None`) или «нет отчёта базы» — это эскалация или сбой подготовки?** (SPEC AC-16/AC-17; формулировка «не `None`» к `merge_gate_escalates` неприменима — она возвращает `bool`, `outcome_integrity.py:1153-1202`.)
   - A) Оба случая — сбой подготовки: запись `MERGE_PREPARE_ACTION` с именованной причиной и `sys.exit` (`outcome_integrity.py:1188-1193`); задача остаётся на `merge_gate`, push нет, повтор — `approve` после того, как CI дошёл.
     - ломается: ничего из существующего; отсутствие отчёта не становится находкой, которую снимает мандат (мандат его и не снял бы).
     - ослабляется: ничего — мерж не проходит (fail-closed), гейт не пропущен.
     - цена: в коде — тот же путь, что `_Prepare` (`outcome_integrity.py:1130-1140`); Оператор повторяет `approve`, пока отчёт не появится.
     - чьё решение: Оператор.
   - B) Оба случая — эскалация: запись `MERGE_REFUSAL_ACTION`, `escalated` (`outcome_integrity.py:1194-1196`).
     - ломается: эскалация советует снять находку мандатом (`outcome_integrity.py:1197-1201`), а отсутствие отчёта мандатом не снимается — совет ложный; после ответа задача снова идёт на гейт мержа.
     - ослабляется: ничего — мерж не проходит.
     - цена: ход Оператора `answer` на каждый «конвейер ещё идёт».
     - чьё решение: Оператор.
   - C) Нет отчёта головы — сбой подготовки (конвейер мог ещё не дойти, повтор `approve`); «нет отчёта базы» — эскалация (структурная причина, нужен Оператор).
     - ломается: как A для головы, как B для базы (ложный совет о мандате на базе).
     - ослабляется: ничего — мерж не проходит в обоих случаях.
     - цена: две ветки исхода, два критерия вместо одного.
     - чьё решение: Оператор.
   - дефолт: A — оба исхода fail-closed, задача стоит на `merge_gate` без смены состояния, и нет ложного совета о мандате. На `in_dev` (если по вопросу 1 там судят отчёты) — обычный отказ гейта `GateRefusal` с той же причиной.

3. **AC-12: свести критерий к «полный набор компонента локально не запускается» или оставить «шпион видит запуск только тестов задачи»?** Долгоживущие файлы и планка задачи гоняются на `in_dev → verifying` (`_acceptance_run_refuses`, `fsm_advance.py:874`), а не внутри `acceptance.acceptance_suite`; нынешний текст читается как требование запускать их внутри приёмки.
   - A) AC-12: «приёмка компонента `full_suite: ci` не запускает локально полный набор компонента (шпион его не видит)»; требование 2 — «локально полный набор компонента не гоняется; тесты задачи идут, как сейчас, на `in_dev → verifying`».
     - ломается: ничего — место прогона тестов задачи прежнее.
     - ослабляется: ничего — прогон планки и долгоживущих файлов держит `fsm_advance.py:874`, он не меняется.
     - цена: правка текста SPEC.
     - чьё решение: роль (формулировка), Оператор подтверждает отход от буквы ТЗ («запускаются только тесты задачи»).
   - B) Оставить как в ТЗ: шпион внутри приёмки видит запуск планки и долгоживущих файлов.
     - ломается: в `acceptance_suite` появляется второй прогон тестов задачи (уже прогнанных на `in_dev`) — лишнее время приёмки и новая точка отказа.
     - ослабляется: ничего.
     - цена: доп. объём части 1 и время каждого `approve`.
     - чьё решение: Оператор.
   - дефолт: A — проверяемое свойство ТЗ («шпион прогона не видит полного набора») сохраняется без дублирования прогона тестов задачи.
