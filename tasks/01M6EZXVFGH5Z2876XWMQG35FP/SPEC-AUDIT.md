Не подтвердилось / не сказано:
- **Б-1. «Иных правок `forge.py`/`gitlab_adapter.py` нет» (SPEC:55-57)
  буквально невыполнимо.** Код ответа живёт в `Reply.status`
  (`gitlab_adapter.py:79-84`, `:262-263`), но `protections` и
  `pipeline_status` читают через `_read_all`, который возвращает
  `(None, reason)` и код теряет (`gitlab_adapter.py:282-291`, `:586-588`,
  `:412-414`); `_pipeline_findings` для заданий — тоже (`:382-385`). Чтобы
  заполнить поле, нужно менять сигнатуру `_read_all`/`_pipeline_findings`
  — это «иная правка». SPEC должен сказать, что изменение пути, несущего
  код от `request` до результата, входит в «заполнение поля».
- **Б-2. Выбор проверки `project-ci-token` «наличием функции»
  не работает:** `_GitHub` тоже имеет `pipeline_status`
  (`forge.py:132-159`), поэтому `hasattr(impl, "pipeline_status")` не
  различит хостинги — годится только `ci_by_pipeline`. SPEC:32-35
  перечисляет оба способа без указания, какой для какой строки.
- **Б-3. Требование 10 не имеет точки исполнения в разрешённых зонах.**
  В интерфейсе `forge` нет функции «доступен ли адрес по токену»
  (`forge.py:210-261`), добавить её запрещает требование 4 (SPEC:55-57);
  значит, проба — `git ls-remote` с токеном слота через `gitcmd`, сетевой
  вызов, но SPEC не называет механизм. Строки 5.1/5.2/5.5 в процессе роли
  дают `ROLE_SKIP` (`project_checks.py:46-55`); про новые строки 8–10 —
  ни слова.
- **Б-4.** Фасад `doctor` не импортирует `catalog`
  (`orchestrator/doctor/__init__.py`, карта: импортов `catalog.py` нет), а
  `project_checks.py` читает коллаборантов только через фасад
  (`project_checks.py:6-7`); `orchestrator/doctor/__init__.py` вне зон.
  Обход есть (`entry.get("branch_template")` +
  `targets.DEFAULT_BRANCH_TEMPLATE`, как `catalog.py:629-630`), но SPEC:174
  отсылает именно к `catalog.branch_template`.

## Пути обхода гейтов
- **Е-1. Литерал хостинга мимо сторожа.** `forge.hosting(name) == "gitlab"`,
  `IMPLEMENTATIONS.get(...) is doctor.forge.gitlab_adapter`,
  `type(...).__name__ == …` — сторож ac9 их не видит (`field_like`,
  `tests/…unsupported_project.py:425-442`); SPEC запрещает первое
  словами, но AC-12 не требует теста, который это поймал бы.
- **Е-2. Различение «по полю», заполненному разбором текста.** Адаптер
  может выставить поле, разобрав собственный `reason` («(403)»), — AC-9 на
  подменённом `forge` этого не увидит. SPEC должен сказать: поле — из
  `Reply.status`/исключения транспорта, тест — на уровне транспорта
  адаптера для заполнения поля.
- **Е-3. Строка повторов по букве.** Проверка только литерала `retry:` в
  блоке задания `ci_job` пропускает `default: retry:`, `extends:`/якоря,
  `--reruns` в `variables`/`PYTEST_ADDOPTS`, `-p rerunfailures` (ср.
  `targets.RERUN_FLAGS`/`RERUN_PLUGINS`, `targets.py:1109-1111`) — смысл
  инварианта 41 обходится. SPEC не задаёт охват.
- **Е-4. Правила `workflow` по букве.** «Ветка не попадает под конвейер»
  без семантики оценки `if` (`=~`, `==`, `$CI_PIPELINE_SOURCE`,
  `when: never`, отсутствие `workflow:` вообще) — можно считать «попадает»
  любую ветку при любом правиле с `$CI_COMMIT_BRANCH`, и строка никогда не
  предупредит. AC-3 при этом проходит на одном подобранном файле.
- **Е-5. Строка подмодулей без пробы.** Без механизма (Б-3) строку можно
  сделать по одному разбору `.gitmodules` (хост совпал → `ok`), не проверив
  доступ по слоту, — AC-6 без «зелёного» случая и без заданной точки
  подмены это не отличит.

## Вердикт
**fail** — SPEC в таком виде не даёт автору тестов однозначной планки без
навязывания устройства, а три новых строки проходят постоянным исходом.
Отклонения:

1. В-1 / Е-2 — поле кода ответа без имени, значений и отображения кодов
   (SPEC.md:51-57, AC-9 SPEC.md:127-133; `orchestrator/forge.py:42-49,
   99-119`; `orchestrator/gitlab_adapter.py:197-211`).
2. Б-1 — «иных правок нет» противоречит необходимой правке `_read_all`/
   `_pipeline_findings` (SPEC.md:55-57; `orchestrator/gitlab_adapter.py:282-308,
   376-395, 580-590`).
3. В-2 — имена и место новых строк требований 8–10 не заданы
   (SPEC.md:74-83, 108-116).
4. В-3 — AC-3…AC-6 без парного случая: постоянный `warn`/`fail` проходит
   (SPEC.md:103-116).
5. Б-3 / Е-5 — механизм пробы доступа подмодуля не задан, в интерфейсе
