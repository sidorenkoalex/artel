# ТЗ: бюджет задачи по ADR-0014: дефолт, потолок ролей, обязательный budget_usd в SPEC, переоценка на PLAN

# ТЗ: дефолт, потолок ролей и статическая оценка бюджета задачи (ADR-0014)

Источник: ADR-0014 (`docs/adr/0014-budget-default-and-role-cap.md`,
принят Оператором 05.09), бэклог 05.09 приоритет 2. Нормативный текст —
сам ADR; ниже — что именно сделать, чтобы его исполнить. При расхождении
ТЗ и ADR прав ADR; неясность — эскалация, не догадка.

Сегодня. `config.DEFAULT_BUDGET_USD = 50` — и дефолт задачи
(`catalog.cmd_new`), и граница для `budget_usd` из SPEC
(`budget.spec_budget`: выше константы — отвергается с предупреждением,
`apply_spec_budget` вызывается из `fsm_advance` на переходе
`spec_writing -> spec_gate`). Поле `budget_usd` в SPEC необязательное
(`templates/SPEC.md`, закомментировано; `scripts/guard.py` не требует).
PLAN.md читается в `fsm_advance` при переходе `in_dev -> review`
(frontmatter через `yamlmini.frontmatter`), бюджет из PLAN не читается.
Инвариант 10 (`docs/invariants.md`, `tests/test_invariants.py::
ExhaustedBudgetIsNotBypassableTest`) — «поднять потолок может только
Оператор командой budget».

Требуется (нумерация — по пунктам решения ADR-0014):

1. `orchestrator/config.py`: `DEFAULT_BUDGET_USD` остаётся 50 —
   потолок задачи до применения SPEC; новая константа
   `ROLE_BUDGET_CAP = 100.0` с комментарием-ссылкой на ADR-0014.
2. SPEC: `budget_usd` обязателен — `scripts/guard.py` отказывает SPEC
   без поля или с не-числом (для `schema_version` текущей и выше;
   исторические SPEC в `tasks/` не перепроверяются — прежний приём
   guard для новых сигналов). `budget.spec_budget`/`apply_spec_budget`:
   значение применяется на гейте SPEC как потолок в обе стороны, если
   `0 < value <= ROLE_BUDGET_CAP`; значение выше потолка ролей — отказ
   guard (не тихое усечение) с подсказкой: делить задачу (оценка объёма,
   01M1KS8K9R…) либо эскалировать вопрос бюджета Оператору. Потолок с
   `budget_source = operator` значением из SPEC не перебивается (как
   сегодня). Справка `orchestrator/artel.py` (абзац про бюджет из SPEC)
   и комментарий в `templates/SPEC.md` — по новой семантике.
3. PLAN: во frontmatter `templates/PLAN.md` — необязательное поле
   `budget_usd` с комментарием (переоценка по числу файлов и шагов,
   только при расхождении с оценкой SPEC, с обоснованием в разделе
   «Подход»). `fsm_advance` при ПЕРВОЙ сдаче PLAN (`status: ready`,
   итерация ревью 1, ни одного применения `plan` в истории задачи)
   применяет значение один раз и только вверх, не выше `ROLE_BUDGET_CAP`,
   с `budget_source = plan` и записью в журнал (старый и новый потолок,
   источник). PLAN без поля потолок не меняет; значение ниже текущего
   потолка — не применяется (журнальная запись «не применён: ниже
   потолка»); значение выше потолка ролей — отказ guard с той же
   подсказкой, что в п.2; после возврата из ревью или приёмки повторная
   сдача PLAN потолок не трогает; потолок с `budget_source = operator`
   значением из PLAN не перебивается.
4. Исчерпание, эскалация, команда `budget`, стоп-лосс программы — без
   изменений; ни один существующий тест на них не ослабляется.
5. Инвариант 10 в `docs/invariants.md` переформулирован по ADR-0014
   п.6; `tests/test_invariants.py` дополняется: SPEC и PLAN со значением
   выше `ROLE_BUDGET_CAP` потолок не поднимают (отказ guard), PLAN
   применяется не более одного раза и не после возврата, потолок
   Оператора не перебивается ни SPEC, ни PLAN.
6. Сигнал «подозрение на большой объём» в guard (порог `budget_usd`
   ≥ $30 и прочие, tasks/01M1KS8K9R…) согласовать с новой калибровкой
   ADR-0014 п.7 так, чтобы сигнал не срабатывал на типовой задаче
   ($35–45) и по-прежнему срабатывал на классе «>10 AC или ≥5 файлов
   (~$70)»; пороги — константы `config` с комментарием; поведение
   деления не ослаблять (класс «лимит» — покрыт ADR-0014).
7. Приложением к PLAN (защищённые пути, применяет Оператор): правки
   `skills/spec-authoring.md` (калибровка по ADR-0014 п.7: до 5 AC и до
   3 файлов ~$35, 6–10 AC ~$45, >10 AC или ≥5 файлов ~$70 либо деление;
   планка — не ниже $25; поле обязательно) и скила разработчика
   (правило переоценки на PLAN).
8. Тесты в `tests/`: guard отказывает SPEC без поля; SPEC $80 на гейте
   даёт потолок $80 (`budget_source = spec`); SPEC $120 — отказ guard;
   PLAN $90 при потолке $45 — потолок $90 (`plan`), повторная сдача PLAN
   с $100 после возврата — потолок не меняется; PLAN $30 при потолке
   $45 — не применён; Оператор поставил $60 — SPEC/PLAN не перебивают;
   существующие `tests/test_spec_budget.py`, `tests/test_step_cost.py`,
   `tests/test_invariants.py` зелёные без ослабления ассертов.

Зоны: orchestrator/budget.py, orchestrator/config.py,
orchestrator/fsm_advance.py, orchestrator/catalog.py, scripts/guard.py,
templates/SPEC.md, templates/PLAN.md, docs/invariants.md, tests/.

«>10 AC или ≥5 файлов ~$70» аналитику оценить честно; деление по
оценке объёма допустимо: например, (а) SPEC-часть с guard и потолком
ролей, (б) PLAN-часть с переоценкой).
