# SPEC: бюджет задачи по ADR-0014 — дефолт, потолок ролей, обязательный budget_usd в SPEC, однократная переоценка на PLAN

## Контекст

`config.DEFAULT_BUDGET_USD = 50` играет сегодня две роли сразу: дефолт
задачи без оценки (`catalog.cmd_new`) и единственная верхняя граница
для `budget_usd` из SPEC (`budget.spec_budget`: значение выше константы
отвергается предупреждением, `apply_spec_budget` вызывается из
`fsm_advance.spec_writing` на переходе `spec_writing -> spec_gate`).
Поле `budget_usd` в SPEC необязательное (`templates/SPEC.md`,
закомментировано; `scripts/guard.py` его не требует). PLAN.md читается
в `fsm_advance.in_dev` при переходе `in_dev -> review`, но бюджет из
него не читается вовсе. Инвариант 10 (`docs/invariants.md`,
`tests/test_invariants.py::ExhaustedBudgetIsNotBypassableTest`) —
«поднять потолок может только Оператор командой `budget`».

Замер 05.09 по 51 завершённой задаче (ADR-0014, «Контекст»): потолок из
SPEC применился только у 2 задач из 50 (у остальных 48 потолок выставил
Оператор командой `budget` — 88 раз за 04–05.09 по 46 задачам), 30
эскалаций «бюджет исчерпан» за 04–05.09 по 23 задачам, 20 задач из 51 —
расход выше $50. Оператор принял ADR-0014 (`docs/adr/0014-budget-
default-and-role-cap.md`, 05.09): дефолт остаётся $50, но появляется
отдельный потолок ролей $100, `budget_usd` в SPEC становится
обязательным и применяется потолком в обе стороны в его пределах,
разработчик получает право на одну переоценку на PLAN. При расхождении
этого SPEC и ADR-0014 нормативен ADR.

## Требования

1. `orchestrator/config.py`: `DEFAULT_BUDGET_USD` остаётся 50. Новая
   константа `ROLE_BUDGET_CAP = 100.0` с комментарием-ссылкой на
   ADR-0014 — верхняя граница потолка, который вправе выставить роли
   (SPEC, затем один раз PLAN) без участия Оператора.
2. `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION` поднимается до
   следующего значения (5) — тем же приёмом version-gating, что уже
   несут `requires_ac_markup`/`requires_registry`/
   `requires_split_assessment`/`requires_zones`, и по тому же доводу,
   что несёт запись `docs/invariants.md` о правилах guard: новое
   правило не должно задним числом ловить уже открытые задачи текущей
   версии 4. Новая проверка отказывает SPEC (`type: spec`) с
   `schema_version >= 5` без поля `budget_usd` или со значением, не
   разбираемым как число тем же разбором, что и сегодня
   (`budget.spec_budget`/`spend.cli_number`); SPEC версии ниже 5 (весь
   сегодняшний беклог, включая уже открытые задачи версии 4) этим
   правилом не проверяется.
3. `scripts/guard.py`, независимо от `schema_version` (проверка
   значения уже существующего необязательного поля, не факта его
   присутствия): SPEC ИЛИ PLAN с `budget_usd`, разобранным как число
   выше `ROLE_BUDGET_CAP`, — отказ guard (не тихое усечение) с
   подсказкой поделить задачу (оценка объёма, 01M1KS8K9RXWHX2PW3ZKB0P903)
   либо эскалировать вопрос бюджета Оператору.
4. `budget.spec_budget`/`budget.apply_spec_budget`: на переходе
   `spec_writing -> spec_gate` значение из SPEC применяется потолком
   задачи в обе стороны (и выше, и ниже сегодняшнего дефолта) при
   условии `0 < value <= ROLE_BUDGET_CAP` (сравнение с `ROLE_BUDGET_CAP`
   заменяет сегодняшнее сравнение с `DEFAULT_BUDGET_USD`). Потолок с
   `budget_source = operator` значением из SPEC не перебивается — как
   сегодня.
5. Справка `orchestrator/artel.py` (абзац о применении `budget_usd` из
   SPEC) переписывается под новую семантику: потолок применяется в обе
   стороны в пределах потолка ролей, а не только понижается от дефолта.
6. `templates/PLAN.md`: необязательное поле frontmatter `budget_usd` с
   комментарием (переоценка по числу файлов и шагов, только при
   расхождении с оценкой SPEC, с обоснованием в разделе «Подход»).
   `fsm_advance.in_dev`, при ПЕРВОЙ сдаче PLAN (`status: ready`, задача
   ещё не получала ни одного вердикта ревьювера — `review_iters == 0`,
   и потолок ещё не был выставлен переоценкой PLAN ранее), применяет
   значение поля потолком задачи один раз и только ВВЕРХ (значение
   ниже текущего потолка — не применяется, с журнальной записью «не
   применён: ниже потолка»), не выше `ROLE_BUDGET_CAP`, с
   `budget_source = plan` и журнальной записью (старый потолок, новый
   потолок, источник). PLAN без поля потолок не меняет. После возврата
   из ревью (`changes_requested`) или из приёмки повторная сдача PLAN
   потолок не трогает, даже если поле снова заполнено. Значение выше
   `ROLE_BUDGET_CAP` — отказ guard той же проверкой и той же подсказкой,
   что в требовании 3 (новый код в `fsm_advance.py` для этого не
   заводится). Потолок с `budget_source = operator` значением из PLAN
   не перебивается — симметрично требованию 4.
7. Исчерпание потолка, эскалация «бюджет исчерпан», команда `budget`,
   стоп-лосс программы (`PROGRAM_STOP_LOSS_USD`, ADR-0010) — без
   изменений; ни один существующий тест на них не ослабляется.
8. `docs/invariants.md`, инвариант 10, переформулируется по ADR-0014
   п.6: «поднять потолок выше `ROLE_BUDGET_CAP` может только Оператор
   командой `budget`; в пределах потолка ролей потолок задаёт SPEC на

   test_invariants.py` дополняется: SPEC и PLAN со значением выше

   применяется не более одного раза и не после возврата из ревью или
   приёмки; потолок Оператора не перебивается ни SPEC, ни PLAN.
9. `config.SPLIT_SIGNAL_BUDGET_USD` (сегодня $30, порог сигнала
   «подозрение на большой объём» в `scripts/guard.py`) пересчитывается
   по калибровке ADR-0014 п.7 так, чтобы типовая задача по новой
   калибровке ($35–45) сигнал не поднимала, а класс «>10 критериев
   приёмки или ≥5 файлов зоны» (~$70) — по-прежнему поднимал: новое
   значение строго больше $45 и не больше $70. Именованная константа
   `config` с комментарием-обоснованием; меняет только Оператор
   (ADR-0002, класс «лимит»).
10. Приложением к PLAN.md (защищённые пути, применяет Оператор,
    `git apply --check` на чистом дереве перед сдачей):
    - unified-диф `templates/SPEC.md` (комментарий поля `budget_usd` по
      новой семантике требования 4) и `templates/PLAN.md` (поле
      `budget_usd` требования 6), плюс синхронный подъём
      `schema_version: 4 -> 5` во всех четырёх шаблонах, которые сегодня
      разделяют это число (`SPEC.md`, `PLAN.md`, `REVIEW.md`,
      `TEST_REPORT.md`) — тем же приёмом, каким версия 4 поднималась во

    - unified-диф скила разработчика: правило однократной переоценки
      `budget_usd` на PLAN (число файлов и шагов, только при

## Критерии приёмки

AC-1. `orchestrator/config.py` несёт `ROLE_BUDGET_CAP = 100.0` с
комментарием-ссылкой на ADR-0014; `DEFAULT_BUDGET_USD` остаётся 50.

AC-2. `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION` поднят до 5.
Новая проверка отказывает SPEC (`type: spec`) с `schema_version >= 5`
без поля `budget_usd` или со значением, которое не разбирается как
число; SPEC с `schema_version < 5` (весь сегодняшний беклог, включая
уже открытые задачи версии 4) этой проверкой не затрагивается.

AC-3. `scripts/guard.py` отказывает SPEC или PLAN, чей `budget_usd`
разбирается как число выше `ROLE_BUDGET_CAP`, независимо от
`schema_version`, с подсказкой поделить задачу (01M1KS8K9RXWHX2PW3ZKB0P903)
либо эскалировать вопрос бюджета Оператору.

AC-4. `budget.spec_budget`/`budget.apply_spec_budget`: на переходе
`spec_writing -> spec_gate` значение SPEC применяется потолком задачи
и выше, и ниже сегодняшнего дефолта, при `0 < value <= ROLE_BUDGET_CAP`;
потолок с `budget_source = operator` значением из SPEC не перебивается.

AC-5. Абзац о бюджете из SPEC в справке `orchestrator/artel.py`
переписан под новую семантику (обе стороны, потолок ролей, не только
понижение от дефолта).

AC-6. `fsm_advance.in_dev`, при первой сдаче PLAN (`status: ready`,
`review_iters == 0`, потолок ещё не выставлялся переоценкой PLAN),
применяет `budget_usd` из PLAN потолком задачи один раз и только вверх,
не выше `ROLE_BUDGET_CAP`, с `budget_source = plan` и журнальной
записью (старый потолок, новый потолок, источник).

AC-7. PLAN без поля `budget_usd` потолок не меняет; значение ниже
текущего потолка не применяется, с журнальной записью «не применён:
ниже потолка».

AC-8. Повторная сдача PLAN после возврата из ревью
(`changes_requested`) или из приёмки потолок не меняет, даже если поле
снова заполнено значением выше текущего потолка.

AC-9. Потолок с `budget_source = operator` значением из PLAN не
перебивается — симметрично AC-4.

AC-10. Исчерпание потолка, эскалация «бюджет исчерпан», команда
`budget`, стоп-лосс программы (`PROGRAM_STOP_LOSS_USD`) — поведение и
существующие тесты не изменены и не ослаблены.

AC-11. `docs/invariants.md`, инвариант 10, переформулирован: «поднять
потолок выше `ROLE_BUDGET_CAP` может только Оператор командой `budget`;
в пределах потолка ролей потолок задаёт SPEC на гейте SPEC и один раз
PLAN при первой сдаче».

AC-12. `tests/test_invariants.py` дополнен: SPEC и PLAN со значением
выше `ROLE_BUDGET_CAP` потолок не поднимают (отказ guard); переоценка
PLAN применяется не более одного раза и не после возврата из ревью или
приёмки; потолок Оператора не перебивается ни SPEC, ни PLAN.

AC-13. `config.SPLIT_SIGNAL_BUDGET_USD` пересчитан значением строго
больше $45 и не больше $70 (именованная константа с комментарием) —
SPEC с `budget_usd: 45` сигнал «подозрение на большой объём» не
поднимает, SPEC с `budget_usd: 70` — поднимает.

AC-14. Тесты в `tests/`: guard отказывает SPEC (`schema_version >= 5`)
без `budget_usd`; SPEC `budget_usd: 80` на гейте SPEC даёт потолок $80
(`budget_source = spec`); SPEC `budget_usd: 120` — отказ guard; PLAN
`budget_usd: 90` при текущем потолке $45 на первой сдаче — потолок $90
(`budget_source = plan`); повторная сдача PLAN с `budget_usd: 100`
после возврата из ревью — потолок не меняется; PLAN `budget_usd: 30`
при потолке $45 — не применяется; потолок $60, выставленный командой
`budget`, не перебивается ни SPEC, ни PLAN. Существующие
`tests/test_spec_budget.py`, `tests/test_step_cost.py`, `tests/
test_invariants.py` остаются зелёными без ослабления ассертов —
включая пересмотр тестов, зафиксировавших старую семантику «выше
дефолта — отказ», на новую «выше `ROLE_BUDGET_CAP` — отказ».

AC-15. Приложением к PLAN.md (защищённые пути, применяет Оператор,
каждый диф проверен `git apply --check` на чистом дереве перед сдачей):
unified-диф `templates/SPEC.md`/`templates/PLAN.md` (новая семантика
поля `budget_usd`) с синхронным подъёмом `schema_version: 4 -> 5` во
всех четырёх шаблонах, разделяющих это число (`SPEC.md`, `PLAN.md`,
`REVIEW.md`, `TEST_REPORT.md`); unified-диф `skills/spec-authoring.md`
(калибровка ADR-0014 п.7: до 5 AC и 3 файлов ~$35, 6–10 AC ~$45,
>10 AC или ≥5 файлов ~$70 либо деление, планка не ниже $25, поле
обязательно); unified-диф скила разработчика (правило однократной
переоценки на PLAN).

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (6:
`orchestrator/budget.py`, `orchestrator/config.py`,
`orchestrator/fsm_advance.py`, `orchestrator/catalog.py`,
`orchestrator/artel.py`, `scripts/guard.py` — порог 5); число критериев
приёмки (15 — порог 10); бюджет (`budget_usd: 50` — порог $30);
затронут инвариантный механизм (`scripts/guard.py` — упомянут
`docs/invariants.md`, запись о версия-гейтинге новых правил guard,
строка 84).

Честная оценка по калибровке ADR-0014 п.7 (15 критериев, 6 файлов
зоны) — класс «>10 критериев или ≥5 файлов» (~$70). Значение выше
сегодняшнего `DEFAULT_BUDGET_USD` ($50) сегодняшняя система молча
отклонит (эта же задача поднимает потолок ролей — до её мержа
действует старый предел), поэтому монолитная рамка технически не
может нести честную оценку без риска упереться в бюджет по ходу
работы. Нарезка на 2 части, по границам зависимости, устраняет и
это несоответствие:

**Часть 1 — «Потолок ролей и обязательный budget_usd в SPEC»**
(требования 1–5, 9, соответствующая половина 7–8, часть 10 —
`templates/SPEC.md`+синхронный подъём версии четырёх шаблонов,
`skills/spec-authoring.md`; AC-1..AC-5, AC-10 (SPEC-сторона), AC-11
(первое предложение — SPEC-часть формулировки), AC-13, AC-14
(SPEC-сценарии), AC-15 (диф SPEC.md/PLAN.md/REVIEW.md/TEST_REPORT.md +
skills/spec-authoring.md)):
зоны `orchestrator/config.py`, `scripts/guard.py`, `orchestrator/
budget.py`, `orchestrator/artel.py`, `tests/`. Идёт первой: вводит
`ROLE_BUDGET_CAP` и общую (для SPEC и PLAN) guard-проверку потолка
ролей, на которую опирается часть 2. Самостоятельно мержима с зелёной
планкой: после мержа система уже требует и применяет `budget_usd` из
SPEC в обе стороны в пределах $100 — poведение PLAN не меняется вовсе
(остаётся как сегодня), рабочее состояние без полуготовых кусков.

**Часть 2 — «Однократная переоценка бюджета на PLAN»** (требования 6,
соответствующая половина 7–8, часть 10 — `templates/PLAN.md`
(содержательно — само поле уже поднято версией в части 1), скил
разработчика; AC-6..AC-9, AC-11 (второе предложение — PLAN-часть
формулировки), AC-12, AC-14 (PLAN-сценарии), AC-15 (диф скила
разработчика)): зоны `orchestrator/fsm_advance.py`, `docs/
invariants.md`, `tests/`. Идёт второй — использует `ROLE_BUDGET_CAP` и
guard-проверку потолка ролей части 1 (значение PLAN выше потолка ролей
эта часть не проверяет заново, полагается на общую проверку части 1).
Самостоятельно мержима: расширяет уже рабочее поведение части 1 разовой
переоценкой на PLAN, не оставляет систему в промежуточном состоянии.

Решение (нарезка либо монолит) утверждает Оператор на гейте SPEC
(`docs/operator-gates.md`).

  05.09, ADR-0014, «Контекст»).

  `templates/SPEC.md`, `templates/PLAN.md`, `templates/REVIEW.md`,
  `templates/TEST_REPORT.md` — только unified-диф приложением к PLAN.md,
  применяет Оператор.

  `docs/research/` — отдельно, делает Оператор (ADR-0014, «Раскатка»).
- Внешние target — задача только `config.DEFAULT_TARGET`.
