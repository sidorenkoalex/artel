# ТЗ: `answer` для задачи в `in_dev` (мандат на расширение зон) и `amend-tests --from-branch`

Источник: аудит обходных сценариев Оператора 06.09. Четыре раза за день
ANSWER Оператора клался в артефактную ветку руками (scratch-worktree на
локальном ref, файл с шапкой и секцией «## Ответы», коммит с сообщением
как у `cmd_answer`, `git update-ref`, push): канал мандата на расширение
зон (`fsm_advance._answer_zones_mandate`, маркер «Расширение зон
разрешено:») рассчитан на задачу в `in_dev` с разделом «Расширение зон»
в PLAN, а `cmd_answer` принимает только `escalated`
(`answer.py:82`). Один раз лок планки сдвинут прямой правкой БД:
разработчик поправил залоченный тест под решение Оператора, автокоммит
унёс правку в артефактную ветку, а `amend-tests` видит только
незакоммиченный worktree (`amend._worktree_changed_paths`) — «нет
изменений, нечего фиксировать». Строки копилки 06.09 (обе).

Требуется:
1. `answer <id> <файл>` принимает задачу в `in_dev` (и `review`), если
   файл несёт маркер мандата «Расширение зон разрешено:» — коммит
   ANSWER-n в артефактную ветку тем же кодом, что для `escalated`, без
   смены состояния; журнал «ANSWER создан (мандат на расширение зон:
   <пути>)». Без маркера в `in_dev` — прежний отказ. Guard-проверка
   секции «## Ответы» — та же.
2. Команда `zones-extend <id> <путь>[, <путь>]`: пишет ANSWER-n с
   маркером и текстом «мандат Оператора: <пути>» и, если PLAN.md ветки
   уже несёт раздел «Расширение зон» с теми же путями, сразу
   обновляет `tasks.zones_extension` (иначе журнал: «раздел PLAN
   отсутствует — разработчик добавит на следующем шаге»). Сокращает путь
   с трёх операций до одной.
3. `amend-tests <id> --reason … --from-branch`: источник правки —
   расхождение `acceptance_tests/` между `tests_locked_sha` и головой
   артефактной ветки (не worktree); команда журналирует диф (список
   файлов), сдвигает `tests_locked_sha` на голову с записью «правка
   планки», как обычный `amend-tests`; без флага поведение прежнее.
   Правка, унесённая автокоммитом шага роли, тем самым легализуется
   Оператором явно, не правкой БД.
4. Тесты: (а) `answer` в `in_dev` с маркером — коммит в артефактную
   ветку и запись журнала; без маркера — отказ (мутация: приём любого
   файла в `in_dev` — красный); (б) `zones-extend` создаёт ANSWER и
   при наличии раздела PLAN обновляет `zones_extension`, гейт зон после
   этого пропускает файл; (в) `amend-tests --from-branch` сдвигает лок
   при расхождении и отказывает «нет расхождения» без него;
   (г) существующие `tests/test_answer*.py`, `tests/test_amend*.py`,
   `tests/test_zones_gate.py` зелёные без правки ассертов.
5. `docs/operator-session.md` и `docs/operator-gates.md` (приложением
   к PLAN): ручной коммит в артефактную ветку больше не нужен —
   `answer`/`zones-extend`/`amend-tests --from-branch`.

Зоны: orchestrator/answer.py, orchestrator/amend.py,
orchestrator/artel.py, orchestrator/fsm_advance.py,
docs/operator-session.md, docs/operator-gates.md, tests/.
Порядок: после мержа «CI до ревью» (01M1TQ0TRC, зона `fsm_advance.py`).

Не входит: правка зон SPEC в БД после approve (зоны читаются из
`tasks.zones` — отдельный кандидат: `zones` перечитываются из SPEC при
операторской правке на гейте).
