# SPEC: Бриф разработчика: вход роли одним документом

## Контекст

Сейчас роль developer получает только текстовую миссию с инструкцией
самой прочитать `tasks/<id>/SPEC.md` (`orchestrator/runner.py`,
миссия developer) — карту кодовой базы и проектные конвенции она не
получает вовсе, и добирает контекст повторными чтениями репозитория
(трение). Роадмап (§2, «Бриф разработчика — $25») требует, чтобы
оркестратор собирал вход роли одним документом: SPEC + срез
`docs/codebase-map.md` + конвенции. Карта уже существует и
поддерживается автогеном (T027, `scripts/codebase_map.py`,
CI-джоба `codebase-map` в `.github/workflows/ci.yml`) — эта задача
переиспользует её механизм сверки `built_at_sha` для проверки
свежести карты по принципу ADR-0003 §3б («кэш с меткой источника,
сверка при потреблении, никогда молчаливое доверие»). Аналогичный по
идее, но не идентичный по содержанию прецедент уже есть для роли
reviewer (`review.review_package` в `orchestrator/review.py`).

## Требования

1. Перед стартом шага роли developer оркестратор собирает единый
   документ входа роли (бриф) из трёх компонентов: содержимое
   `tasks/<id>/SPEC.md`, содержимое `docs/codebase-map.md`,
   содержимое корневого файла конвенций проекта (`CLAUDE.md`).
2. Компоненты брифа передаются агенту непосредственно в тексте
   промпта — не инструкцией «прочитай файл X сам».
3. Скилы роли (`skills/*.md`, подключаемые через `roles.yaml`)
   в бриф не дублируются — остаются существующим отдельным блоком
   промпта.
4. Компонент «карта» — содержимое `docs/codebase-map.md` целиком, без
   урезания по зоне задачи (при фактическом размере файла на момент
   этого SPEC — 687 строк, ~30 КБ — полное включение дешевле, чем
   вычисление и поддержка среза по зоне).
5. Перед сборкой компонента «карта» оркестратор лениво (в момент
   сборки брифа, не заранее) сверяет свежесть карты: диапазон от
   `built_at_sha` карты (frontmatter `docs/codebase-map.md`) до
   текущего HEAD базовой ветки по путям `orchestrator/*.py`,
   `scripts/*.py`, `tests/*.py` — тем же способом, которым уже
   пользуется CI-джоба `codebase-map` (ADR-0003 §3б).
6. Если сверка находит расхождение (карта стухла), оркестратор
   регенерирует карту (`scripts/codebase_map.py`) до сборки брифа
   и использует регенерированную версию.
7. Если регенерация не удалась, молчаливая сборка брифа со стухшей
   картой запрещена: оркестратор фиксирует алерт и добавляет в бриф
   явную текстовую пометку о неактуальности карты (использованный
   `built_at_sha`, список путей расхождения).
8. Оркестратор считает хэш содержимого каждого из трёх компонентов
   брифа (SPEC, карта, конвенции) и пишет их в журнал БД шага сборки
   брифа — воспроизводимость шага опирается на эту запись.
9. Роль analyst дополнительно получает компонент «карта» тем же
   механизмом (сборка + ленивая сверка свежести + регенерация/пометка
   + хэш в журнал), добавленным к её текущему входу (`TZ.md`) —
   остальной вход и скилы analyst не меняются.

## Критерии приёмки

AC-1. Промпт, передаваемый роли developer при старте шага, содержит
текст `tasks/<id>/SPEC.md` этой задачи целиком.

AC-2. Промпт роли developer содержит текст `docs/codebase-map.md`
целиком.

AC-3. Промпт роли developer содержит текст корневого файла конвенций
проекта (`CLAUDE.md`) как компонент, отдельный от блока скилов роли.

AC-4. Промпт роли developer не содержит повторно текста файлов
`skills/*.md` сверх уже существующего блока «--- СКИЛЫ РОЛИ ---».

AC-5. Если диапазон от `built_at_sha` карты до текущего HEAD базовой
ветки содержит изменения по путям `orchestrator/*.py`, `scripts/*.py`
или `tests/*.py`, оркестратор перед сборкой брифа запускает
`scripts/codebase_map.py` и использует регенерированную карту.

AC-6. Если такого диапазона изменений нет, карта не регенерируется
и пометка о неактуальности в бриф не добавляется.

AC-7. Если регенерация карты завершилась ошибкой, в журнал алертов
записывается запись об этом, и текст брифа содержит явную пометку
о неактуальности карты с указанием использованного `built_at_sha`
и путей расхождения.

AC-8. В журнал БД для шага сборки брифа роли developer записаны хэши
содержимого всех трёх компонентов (SPEC, карта, конвенции),
использованных в конкретном прогоне.

AC-9. Промпт, передаваемый роли analyst при старте шага, дополнительно
к существующему входу (`TZ.md`) содержит текст `docs/codebase-map.md`
целиком, собранный той же сверкой свежести и с записью хэша в журнал
БД, что и для developer.

## Не входит

- Роли reviewer и test_author: бриф в этой задаче не подключается.
  reviewer уже пользуется отдельным механизмом (`review_package`),
  test_author в ТЗ и роадмаповой формулировке задачи не упомянут.
- Компонент «конвенции» для роли analyst: не добавляется в этой
  задаче — ТЗ и роадмап (A5) называют для analyst только «срез
  карты», не конвенции.
- Публикация брифа или его компонентов во внешние targets (ветка
  `artel` целевого): публикация артефактов в принципе отложена
  (ADR-0003 п.3), задачи фазы A ещё не вывели конвейер на внешние
  targets.
- Изменение генератора карты (`scripts/codebase_map.py`) и переход
  на гибридную схему «скелет скриптом + семантические аннотации
  агентом» (ADR-0003 §3б): карта остаётся чисто-скелетной, как после
  T027.
- Срез карты по «зоне задачи» (фильтрация содержимого по файлам или
  директориям вместо файла целиком): не реализуется в этой задаче
  (обоснование — требование 4); пересмотр — отдельной задачей, если
  фактический размер карты заметно вырастет.
- Инструмент диагностического перепрогона шага по хэшам из журнала
  (упомянут в ТЗ как будущий потребитель записи, «P3»): эта задача
  только пишет хэши компонентов в журнал, сам перепрогон не
  реализуется.
- Правки путей из `no_paths` целевого artel (`gates.yaml`,
  `roles.yaml`, `targets.yaml`, `.github/`, `templates/`, `skills/`,
  `docs/invariants.md`, `tests/test_invariants.py`): вне мандата
  разработчика (принцип целостности, ADR-0002).
