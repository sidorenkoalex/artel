## Замечания

- **blocker** — `orchestrator/brief.py:50-54,72-74` (`_regenerate_map`,
  `fresh_map_text`) — регенерация карты пишет `docs/codebase-map.md`
  **на диск, в `config.ROOT`**, без коммита (`scripts/codebase_map.py:183-185`
  — `output_path.write_text(...)` относительно `cwd=config.ROOT`, тот же
  генератор что у CI). Для догфуд-таргета (`config.DEFAULT_TARGET`) —
  единственного таргета, реально используемого сейчас (SPEC T028, «Не
  входит»: «задачи фазы A ещё не вывели конвейер на внешние targets») —
  `runner.role_cwd` (`orchestrator/runner.py:318-319`) отдаёт агенту
  роли **тот же самый `config.ROOT`** как рабочий каталог. Сборка
  брифа (и, значит, возможная регенерация) вызывается
  (`orchestrator/runner.py:169,136`) ДО запуска агента
  (`run_agent_once`, `orchestrator/runner.py:202`) — то есть
  незакоммиченная правка `docs/codebase-map.md` оказывается в РОВНО
  том рабочем дереве, от которого агент создаёт ветку задачи и в
  которое, по своей миссии, обязан «закоммить всё в ветку»
  (`orchestrator/runner.py:166-167` — миссия developer, дословно
  «закоммить всё в ветку»). `fixation.check_integrity`/`_fix_dogfood`
  (`orchestrator/fixation.py:56-59`) сверяет чистоту только
  `tasks/<id>/`, не всего ROOT — эта грязь никак не детектируется.
  Сценарий поломки: задача A трогает `orchestrator/*.py`; на задаче B
  (следующий шаг developer/analyst, любой) сверка находит расхождение
  (требование 5, работает штатно), карта перегенерируется на диске
  пульта, но не коммитится; агент B создаёт ветку `task/B` от `main`
  (уносит незакоммиченную правку с собой) и по инструкции коммитит
  «всё» — в коммит задачи B без её ведома и без упоминания в
  PLAN/SPEC задачи B попадает изменение `docs/codebase-map.md`,
  никак не относящееся к её объёму (принцип целостности: «Изменения
  вне зоны задачи — дефект»). PLAN T028 «Влияние на систему» утверждает
  обратное — «пишет только в журнал шага (store.journal) и в alerts»
  — это неточно: дисковая запись файла в реальном рабочем дереве
  пульта не упомянута и не проанализирована, тестов на этот сценарий
  нет (юнит-тесты `tests/test_brief.py::FreshMapTextTest` гоняют
  регенерацию в tmp-каталоге без git вовсе). Предложение: коммитить
  регенерированную карту отдельным, раскрытым шагом до старта агента
  (или явно её `git checkout --`/`stash` после чтения в память), либо
  писать регенерацию во временную копию и не трогать рабочее дерево
  ROOT напрямую.

- **major** — `orchestrator/brief.py:38-47` (`_stale_paths`) — при
  ошибке самой git-команды (`res.returncode != 0`) функция возвращает
  `[]`, то есть трактует «git не ответил» ТОЖДЕСТВЕННО «расхождений
  нет» — карта отдаётся как свежая, без алерта и без пометки. Это
  расходится с принципом, который цитирует сам докстринг модуля
  (`orchestrator/brief.py:9-11`, ADR-0003 §3б «никогда молчаливое
  доверие»): защита требования 7 сделана только для отказа
  РЕГЕНЕРАЦИИ, но не для отказа самой СВЕРКИ свежести, хотя обе —
  «git не ответил» по духу ADR. Не гипотетически: сегодня `git diff
  --name-only "" HEAD -- ...` (пустой `built_at_sha`) и `git diff
  --name-only <sha-без-истории> HEAD -- ...` (история `main`
  переписана после записи `built_at_sha`, например force-push/rebase —
  операция, которую сам `CLAUDE.md` не запрещает, а требует
  подтверждения) оба падают с `fatal: bad revision` (rc=128),
  проверено локально: `git diff --name-only "" HEAD -- orchestrator/*.py`
  → `fatal: bad revision ''`. Ровно эта ветка (rc≠0 → `[]`) уже
  непреднамеренно эксплуатируется фикстурами этой же задачи —
  `tests/test_doctor.py::TmpRootTest.setUp` (ROOT — не git-репозиторий
  вовсе), `tests/test_git_fixation.py::ExternalIntegrityIncidentBlocksRunTest.setUp`
  (аналогично), `tests/test_git_fixation.py::RealPultGitTest.setUp`
  (git-репозиторий есть, но `built_at_sha: 000...0` — несуществующий
  коммит), `tests/test_multitarget_invariants.py::TmpRootTest.setUp`
  (аналогично первому) — во всех четырёх реальный `gitcmd.git` падает
  на диффе и код молча трактует это как «карта свежа»; ни один тест
  не проверяет и не документирует это поведение как решение, а не как
  случайную удачу подмены. Предложение: при `returncode != 0`
  различать «неизвестно» и «расхождений нет» (как уже делает
  `gitcmd.diff_paths`, возвращающий `None`), и на «неизвестно» — тот же
  путь алерта/пометки, что и для провала регенерации, а не молчаливое
  доверие.

- **minor** — `tasks/T028/PLAN.md`, раздел «Риски» — утверждение
  «`git diff --name-only "" HEAD -- <пути>` эквивалентен `git diff
  --name-only HEAD -- <пути>` (сравнение с самим собой, пустой дифф)»
  фактически неверно: команда падает с `fatal: bad revision ''`
  (rc=128), а не возвращает пустой дифф по rc=0. Итоговое поведение
  (карта не регенерируется, пометка не добавляется) в коде
  действительно совпадает с тем, что описывает PLAN — но по другой
  причине (ветка `returncode != 0` в `_stale_paths`, см. замечание
  major выше), не потому что дифф пуст. Стоит поправить формулировку
  риска, чтобы она не вводила в заблуждение при будущей отладке этого
  же класса сценариев.

## Вердикт

changes_requested — один blocker (побочная незакоммиченная запись в
рабочее дерево пульта при регенерации карты, вне объявленного PLAN
влияния на систему) и один major (сверка свежести карты молча
доверяет карте при отказе самой git-команды, а не только при отказе
регенерации). Правки:
1. Исключить незакоммиченную мутацию `config.ROOT` при регенерации
   карты в брифе (или явно раскрыть и обработать её как коммит/откат).
2. `_stale_paths` — не сворачивать «git не ответил» в «расхождений
   нет»; довести до того же алерта/пометки, что и провал регенерации.
3. (minor, по желанию) поправить формулировку риска в PLAN.
