# ТЗ: Долгоживущие приёмочные тесты пишутся в tests/ ветки задачи и фиксируются перечнем сумм (ADR-0020, задача 2)

# ТЗ: Долгоживущие приёмочные тесты — test_author добавляет файлы в tests/ ветки задачи, пульт фиксирует их перечнем контрольных сумм

Источник: ADR-0020 (решение Оператора 28.09.2026), пункты 3–7, 11, 12 —
вторая из трёх задач внедрения. Зависит от задачи 1 «Приёмочные тесты
двух групп — пометка группы в файле и проверки долгоживущих файлов на
выходе из tests_writing» (строка группы, статические проверки, заявка
мутации): заводится после её мержа. Предпосылка — задача
01M3MVXZXF25KYY2P213E0M39X (защищённые пути для настроек сбора тестов).
Задача 3 (`amend-tests` для файлов в `tests/`, дифф ревью) зависит от
этой. Ревью схемы 28.09: сверка лока приёмочных тестов на гейте мержа
отсутствует и сейчас.

Факты (origin/main 171ab4c6, после мержа задачи 1 01M3N0BWYQ9KHVN41Z4G72706R):
- В кодовую ветку коммитит только developer: `orchestrator/checkpoint.py`
  (`_commit_worktree_change`); изменения test_author, analyst и reviewer
  вне `tasks/<id>/` откатываются `_discard_out_of_mandate_changes` с
  записью в журнал (правило введено после инцидента hotfix
  01M1KT0792125J9ZNJNZJ86E9Q). test_author работает в worktree кодовой
  ветки задачи.
- Задание test_author (`orchestrator/role_prompt.py`) велит писать тесты
  только в `tasks/<id>/acceptance_tests/` и не трогать код репозитория.
- Лок: на выходе из `tests_writing` (`orchestrator/fsm_advance.py::
  tests_writing`) в `tasks.tests_locked_sha` пишется голова ветки
  документов, затем `fsm._maybe_ensure_draft_mr` (`orchestrator/fsm.py`)
  пушит кодовую ветку. Сверку лока делает
  `orchestrator/advance_gates/acceptance.py::_acceptance_lock_refuses`
  (дифф каталога `tasks/<id>/acceptance_tests` между локом и головой
  ветки документов, сбой git — отказ) только на `in_dev -> verifying`.
  Гейт мержа `orchestrator/fsm_merge_gate.py::_cmd_approve_merge_gate`
  лок не сверяет вовсе; подтяжка `main` — `_sync_main_or_wait`.
- Разрешённые имена каталога приёмочных тестов включают `*.txt` и `*.md`
  (`scripts/guard.py::ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`): файл
  перечня внутри каталога попадает под нынешний лок без новой колонки
  БД.
- Прогон приёмочных тестов: `orchestrator/acceptance.py::run` после
  `materialize_from_branch`; на `in_dev -> verifying` его зовёт
  `advance_gates/acceptance.py::_acceptance_run_refuses`. Автогейт
  приёмки (`orchestrator/fsm_autogate.py`) приёмочные тесты заново не
  гоняет, но гоняет весь `tests/` рабочего каталога задачи
  (`acceptance.full_suite`).
- Трассируемость критериев: `fsm._tests_writing_ac_state` через
  `guard.scan_ac_content(sources)` — ядро уже принимает список
  исходников.
- `tests/` входит в общие зоны (`config.COMMON_ZONES`): одинаковые пути
  двух параллельных задач гейт зон конфликтом не считает. Первые восемь
  знаков id задачи — метка времени; у задач, заведённых в одну секунду,
  они совпадают.
- Гейт неослабления тестов (`advance_gates/test_integrity.py`) видит
  долгоживущий файл до мержа как новый и его ослабление не ловит.
- CI (`.github/workflows/ci.yml`) гоняет `pytest tests` на каждый пуш
  `task/**`: ветка будет красной с момента пуша долгоживущих файлов до
  кода разработчика. Пульт читает CI только головы ветки.

Требуется:
1. test_author задачи target `artel` вправе добавлять новые файлы
   `tests/test_<префикс>_<имя>.py` в кодовую ветку своей задачи:
   `checkpoint.py` коммитит в кодовую ветку только файлы, которых нет в
   базе ветки и имя которых несёт префикс задачи; любое другое изменение
   вне `tasks/<id>/` (правка, переименование, удаление существующего
   файла, файл без префикса, путь вне `tests/`) откатывается, как
   сейчас, с записью в журнал. Свои же добавленные файлы test_author
   вправе менять и удалять до выхода из `tests_writing` (в том числе при
   возврате в `tests_writing` полным циклом пересмотра по ADR-0012).
2. Префикс однозначно выводится из id задачи и не совпадает у двух
   разных задач; форму выбирает и обосновывает SPEC (с учётом факта о
   первых восьми знаках id). Путь, уже существующий в `origin/main`, —
   отказ.
3. Гейт на выходе из `tests_writing`: дифф кодовой ветки против её базы
   (`gitcmd.diff_base`, `gitcmd.diff_name_status`) содержит только
   добавленные файлы `tests/` с префиксом задачи, каждый со строкой
   группы «долгоживущий»; к каждому применяются проверки задачи 1
   (статические признаки, «Ловит мутацию», сухой сбор — из `tests/`).
   Файл со строкой «долгоживущий» в каталоге приёмочных тестов — отказ
   с подсказкой перенести его в `tests/`. Отказ называет пути.
4. Трассируемость: критерий покрыт методом `test_ac<n>_…` в каталоге
   приёмочных тестов или в долгоживущем файле `tests/` кодовой ветки;
   SPEC решает, сохраняются ли имена `test_ac<n>_…` в `tests/`.
5. Перечень: на выходе из `tests_writing`, до записи
   `tests_locked_sha`, пульт пишет в ветку документов перечень «путь →
   SHA-256 содержимого на голове кодовой ветки» всех долгоживущих файлов
   задачи; место (файл внутри каталога приёмочных тестов либо иное под
   тем же локом) и формат выбирает SPEC. Перечень без записей допустим.
   Правка перечня после лока ловится нынешней сверкой лока.
6. Сверка: на каждом переходе после `tests_writing` (SPEC перечисляет
   переходы и ставит один общий узел) и на гейте мержа после
   `_sync_main_or_wait` содержимое каждого пути перечня на голове
   кодовой ветки совпадает с суммой; отсутствующий или изменённый файл —
   отказ перехода с путём и подсказкой «код чинится под тест; правка
   теста — `amend-tests` по решению Оператора»; сбой git — отказ. На том
   же рубеже мержа сверяется и нынешний лок каталога приёмочных тестов
   (`_acceptance_lock_refuses`).
7. Прогон: на `in_dev -> verifying` долгоживущие файлы перечня
   исполняются в том же прогоне, что приёмочные тесты
   (`acceptance.run`); итог называет число тестов обеих групп. SPEC
   подтверждает, что полный прогон `tests/` автогейта приёмки включает
   долгоживущие файлы ветки, и не заводит второго прогона.
8. Задание ролей (`role_prompt.py`): test_author узнаёт, куда писать
   долгоживущие файлы, как назвать и что существующие файлы `tests/`
   трогать нельзя; developer — что долгоживущие файлы задачи
   зафиксированы так же, как приёмочные тесты.
9. Область: target `artel`, включая канареечные задачи; внешний target и
   задача без приёмочных тестов (`skip_tests`) — без перечня и без
   сверки, поведение прежнее. Ликвидация задачи (`kill`) отдельных
   действий не требует.
10. Правила ролей (приложениями):
    - `skills/test-authoring.md`: долгоживущие файлы пишутся в `tests/`
      кодовой ветки с префиксом задачи; временная оговорка задачи 1
      («до мержа задачи 2 — в каталоге приёмочных тестов») снимается;
    - `skills/coding-standards.md`: разработчик дописывает тесты только
      на свойства, не покрытые долгоживущими файлами; правило «двойник в
      `tests/`» задачи 1 для разработчика снимается; долгоживущие файлы
      не правит — расхождение с ними эскалирует;
    - `skills/review-checklist.md`: повтор долгоживущего теста
      разработчиком — замечание; временное правило «Долгоживущие
      свойства — в `tests/`» не снимается (ADR-0020, пункт 10);
    - `docs/invariants.md`, инвариант 27: лок распространяется на
      перечень долгоживущих файлов, сверка — на переходах и на мерже.
11. Тесты (`tests/`, песочница `tests/sandbox.py`): добавленный
    test_author файл с префиксом коммитится в кодовую ветку; правка
    существующего файла `tests/`, файл без префикса, путь вне `tests/`
    — откатываются (заявка мутации «откат вне мандата снят»); гейт
    «только добавление» отказывает на M/D/R; перечень записан до лока и
    несёт верные суммы; изменённый после лока долгоживущий файл — отказ
    на `in_dev -> verifying` и на гейте мержа; удалённый — отказ; сбой
    git — отказ; изменённый после лока файл каталога приёмочных тестов —
    отказ на гейте мержа; прогон приёмки включает долгоживущие файлы;
    внешний target — без перечня. Полный набор `tests/` зелёный; ни один
    существующий тест и гейт не ослаблен.
