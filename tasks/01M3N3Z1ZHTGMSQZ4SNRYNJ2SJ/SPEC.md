# SPEC: Долгоживущие приёмочные тесты пишутся в tests/ ветки задачи и фиксируются перечнем сумм (ADR-0020, задача 2)

## Контекст
Это вторая из трёх задач внедрения ADR-0020 (пункты 3–7, 11, 12). Она
опирается на смерженную задачу 1 01M3N0BWYQ9KHVN41Z4G72706R: строка
группы `Группа: долгоживущий` / `Группа: разовый` в docstring модуля,
статические признаки, заявка «Ловит мутацию», сухой сбор. Сейчас
долгоживущие файлы по временной оговорке задачи 1 лежат в
`tasks/<id>/acceptance_tests/` и после мержа не исполняются. Коммиты в
кодовую ветку разрешены только developer: изменения test_author вне
`tasks/<id>/` откатывает `orchestrator/checkpoint.py::
_discard_out_of_mandate_changes`. Эта задача разрешает test_author только
ДОБАВЛЯТЬ файлы с префиксом задачи в `tests/` кодовой ветки. Пульт
фиксирует эти файлы перечнем SHA-256 под нынешним локом и сверяет
перечень на переходах после `tests_writing` и на гейте мержа. На гейте
мержа сейчас не сверяется и лок каталога приёмочных тестов: эта задача
закрывает и этот пробел.

## Решения, которые ТЗ оставило SPEC

**Р1. Префикс (ТЗ, требование 2).** Префикс равен полному id задачи в
нижнем регистре, 26 знаков, например `01m3n3z1zhtgmsqz4snrynj2sj`. Имя
файла: `tests/test_<id в нижнем регистре>_<имя>.py`, где `<имя>`
непустое и состоит из `[a-z0-9_]`. Почему не короче. Id — это ULID
(`orchestrator/idgen.py`): первые 10 знаков — метка времени в
миллисекундах, а 8 знаков совпадают у задач, заведённых в одну секунду.
Любой собственный префикс id захватывает случайную часть лишь частично
и оставляет ненулевую вероятность совпадения. Уникальность гарантирует
только полный id. Нижний регистр совпадает с формой имени ветки
`task/<id>-<slug>`. Такое имя — допустимый идентификатор модуля Python.

**Р2. Перечень (ТЗ, требование 5).** Файл
`tasks/<id>/acceptance_tests/long_lived.sha256.txt` лежит внутри каталога
приёмочных тестов. Имя подходит под `ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`
(`.+\.txt`), поэтому перечень покрыт нынешним локом `tests_locked_sha`
без новой колонки БД. Формат:
- кодировка UTF-8;
- по строке на долгоживущий файл: `<64 знака SHA-256 строчными><два
  пробела><путь от корня репозитория>\n`;
- строки отсортированы по пути;
- комментариев нет;
- пустой файл означает перечень без записей.

Формат совместим с `sha256sum -c`: Оператор может проверить перечень
вручную из корня рабочей копии кодовой ветки. Сумма берётся от байтов
файла в дереве коммита головы кодовой ветки, а не рабочего каталога.

**Р3. Имена методов (ТЗ, требование 4).** Имена `test_ac<n>_…` в
долгоживущих файлах `tests/` сохраняются. Трассируемость задачи считает
только долгоживущие файлы своей задачи, то есть файлы с её префиксом.
Поэтому одноимённые методы уже смерженных задач в `tests/` покрытие
чужой задачи не дают.

**Р4. Переходы сверки перечня (ТЗ, требование 6).** Узел сверки один, он
вызывается на следующих рубежах:
- `in_dev -> verifying`;
- `verifying -> review`;
- `review -> acceptance`;
- `acceptance -> merge_gate` командой `approve` (`orchestrator/fsm.py`);
- гейт мержа `_cmd_approve_merge_gate` после `_sync_main_or_wait`.

Сверки нет на следующих путях:
- `tests_writing -> in_dev`: там перечень только что записан с той же
  головы;
- возврат `review -> in_dev`: в `in_dev` расхождение и исправляется, а
  отказ возврата запер бы задачу в `review`;
- переходы в `escalated` и `killed`;
- путь автогейта `acceptance -> merge_gate` (`orchestrator/fsm_autogate.py`):
  по ТЗ модуль только для чтения, этот путь покрывает сверка на гейте
  мержа.

## Требования

1. **Коммит test_author в `tests/`.** Правило действует для задач target
   `artel`, включая канареечные, без `skip_tests`. На чекпоинте шага
   test_author `orchestrator/checkpoint.py` коммитит в кодовую ветку
   файлы `tests/test_<префикс Р1>_<имя>.py`, которых нет в базе ветки
   (`gitcmd.diff_base`). Правку и удаление таких своих файлов пульт
   коммитит тоже, пока задача не вышла из `tests_writing`, в том числе
   при возврате в `tests_writing` полным циклом пересмотра по ADR-0012.
   Любое другое изменение вне `tasks/<id>/` откатывается, как сейчас, с
   записью в журнал: правка, переименование или удаление файла из базы,
   файл без префикса задачи, путь вне `tests/`.
2. **Гейт «только добавление» на выходе из `tests_writing`.** Дифф
   кодовой ветки против её базы (`gitcmd.diff_base`,
   `gitcmd.diff_name_status`) содержит только добавленные (`A`) файлы
   `tests/` с префиксом задачи. Отказ, если выполнено хотя бы одно:
   - в диффе есть `M`, `D` или `R`;
   - в диффе есть файл без префикса;
   - в диффе есть путь вне `tests/`;
   - путь уже существует в `origin/main`;
   - у добавленного файла нет строки `Группа: долгоживущий`.

   Отказ называет пути.
3. **Проверки задачи 1 для файлов `tests/`.** К каждому добавленному
   долгоживущему файлу `tests/` применяются проверки задачи 1:
   статические признаки, «Ловит мутацию» и сухой сбор из `tests/`.
4. **Долгоживущий файл в каталоге приёмочных тестов.** Для target
   `artel` файл со строкой `Группа: долгоживущий` в
   `tasks/<id>/acceptance_tests/` даёт отказ на выходе из
   `tests_writing`. Отказ называет путь и подсказывает перенести файл в
   `tests/` по правилу имени Р1.
5. **Трассируемость.** Критерий `AC-n` покрыт, если метод
   `test_ac<n>_…` есть в каталоге приёмочных тестов или в долгоживущем
   файле `tests/` кодовой ветки этой задачи (Р3).
6. **Перечень.** На выходе из `tests_writing`, до записи
   `tests_locked_sha`, пульт пишет в ветку документов перечень по Р2
   для всех долгоживущих файлов задачи с суммами по голове кодовой
   ветки. Перечень без записей допустим. Правку перечня после лока
   ловит нынешняя сверка лока (`_acceptance_lock_refuses`).
7. **Сверка перечня.** Один общий узел работает на рубежах Р4. На каждом
   из них содержимое каждого пути перечня на голове кодовой ветки должно
   совпадать с суммой. Если файл отсутствует или изменён, переход
   получает отказ. Отказ называет путь и несёт подсказку «код чинится
   под тест; правка теста — `amend-tests` по решению Оператора». Сбой
   git тоже даёт отказ.
8. **Лок каталога на гейте мержа.** На гейте мержа после
   `_sync_main_or_wait` сверяется и нынешний лок каталога приёмочных
   тестов (`_acceptance_lock_refuses`). Расхождение или сбой git дают
   отказ.
9. **Прогон.** На `in_dev -> verifying` долгоживущие файлы перечня
   исполняются в одном прогоне с приёмочными тестами (`acceptance.run`).
   Итог называет число тестов обеих групп. Полный прогон `tests/`
   автогейта приёмки (`acceptance.full_suite` из рабочего каталога
   задачи) включает долгоживущие файлы ветки, потому что они лежат в её
   `tests/`. Второго прогона задача не заводит.
10. **Задание ролей (`orchestrator/role_prompt.py`).**
    - test_author узнаёт три вещи: долгоживущие файлы пишутся в `tests/`
      кодовой ветки; имя — `tests/test_<префикс>_<имя>.py` с конкретным
      префиксом своей задачи; существующие файлы `tests/` трогать нельзя.
    - developer узнаёт, что долгоживущие файлы задачи зафиксированы так
      же, как приёмочные тесты.
11. **Область.** Правила действуют для target `artel`, включая
    канареечные задачи. Для внешнего target и для задачи со
    `skip_tests` нет ни перечня, ни сверки, поведение прежнее. Ликвидация
    задачи (`kill`) отдельных действий не требует.
12. **Приложения к PLAN.** Пульт применяет их на мерже, для каждого
    `git apply --check` проходит на чистом дереве.
    - `skills/test-authoring.md`: долгоживущие файлы пишутся в `tests/`
      кодовой ветки с префиксом задачи. Временная оговорка задачи 1 «до
      мержа задачи 2 — в каталоге приёмочных тестов» снимается.
    - `skills/coding-standards.md`: разработчик дописывает тесты только
      на свойства, не покрытые долгоживущими файлами. Правило «двойник в
      `tests/`» задачи 1 для разработчика снимается. Долгоживущие файлы
      разработчик не правит, расхождение с ними эскалирует.
    - `skills/review-checklist.md`: если разработчик повторяет
      долгоживущий тест, это замечание. Временное правило «Долгоживущие
      свойства — в `tests/`» не снимается (ADR-0020, пункт 10).
    - `docs/invariants.md`, инвариант 27: лок распространяется на
      перечень долгоживущих файлов, сверка идёт на переходах Р4 и на
      мерже.

## Критерии приёмки

AC-1. У задачи target `artel` test_author добавил файл
`tests/test_<префикс>_<имя>.py`, которого нет в базе ветки. После
чекпоинта шага файл закоммичен в кодовую ветку задачи.

AC-2. test_author правит существующий в базе файл `tests/`, или
добавляет файл `tests/` без префикса задачи, или меняет путь вне
`tests/` и вне `tasks/<id>/`. Каждое такое изменение откатывается на
чекпоинте с записью в журнал, в кодовую ветку оно не попадает.

AC-3. test_author правит или удаляет свой ранее закоммиченный файл с
префиксом задачи, пока задача не вышла из `tests_writing`. Правка или
удаление коммитятся, отката нет.

AC-4. Префикс равен полному id задачи в нижнем регистре (Р1). У двух
задач, id которых совпадают в первых восьми и в первых десяти знаках,
префиксы различаются.

AC-5. На выходе из `tests_writing` дифф кодовой ветки против базы
содержит `M`, `D` или `R`, файл без префикса или путь вне `tests/`. Во
всех этих случаях переход получает отказ, и отказ называет пути.

AC-6. Добавленный файл с префиксом, путь которого уже существует в
`origin/main`, даёт отказ на выходе из `tests_writing`, и отказ называет
путь.

AC-7. Добавленный в `tests/` файл с префиксом без строки `Группа:
долгоживущий` даёт отказ на выходе из `tests_writing`, и отказ называет
путь.

AC-8. К долгоживущему файлу `tests/` на выходе из `tests_writing`
применяются проверки задачи 1: нарушение статического признака,
отсутствие «Ловит мутацию» у метода или несобираемость из `tests/` дают
отказ.

AC-9. Файл со строкой `Группа: долгоживущий` в
`tasks/<id>/acceptance_tests/` задачи target `artel` даёт отказ на
выходе из `tests_writing`. Отказ называет путь и подсказывает перенести
файл в `tests/`.

AC-10. Критерий, покрытый только методом `test_ac<n>_…` в долгоживущем
файле `tests/` кодовой ветки этой задачи, считается покрытым.
Одноимённый метод в файле `tests/` без префикса этой задачи покрытия не
даёт.

AC-11. На выходе из `tests_writing` перечень
`tasks/<id>/acceptance_tests/long_lived.sha256.txt` записан в ветку
документов раньше `tests_locked_sha`, то есть присутствует в дереве
коммита лока. В перечне по строке на каждый долгоживущий файл задачи в
формате Р2, и сумма каждой строки равна SHA-256 содержимого файла на
голове кодовой ветки.

AC-12. У задачи без долгоживущих файлов перечень записан пустым, и выход
из `tests_writing` проходит.

AC-13. Если перечень правится в ветке документов после лока, переход
`in_dev -> verifying` получает отказ нынешней сверки лока.

AC-14. Долгоживущий файл изменён в кодовой ветке после лока. Переход
`in_dev -> verifying` получает отказ, и гейт мержа тоже. Отказ называет
путь и несёт подсказку «код чинится под тест; правка теста —
`amend-tests` по решению Оператора».

AC-15. Если долгоживущий файл перечня удалён из кодовой ветки после
лока, переход получает отказ, и отказ называет путь.

AC-16. Сверка перечня выполняется одним общим узлом на каждом рубеже Р4:
- `in_dev -> verifying`;
- `verifying -> review`;
- `review -> acceptance`;
- `acceptance -> merge_gate` командой `approve`;
- гейт мержа после `_sync_main_or_wait`.

Расхождение на любом из них — отказ.

AC-17. Сбой git при сверке перечня (чтение головы кодовой ветки или
содержимого файла) даёт отказ перехода, а не пропуск.

AC-18. Если файл каталога приёмочных тестов изменён в ветке документов
после лока, гейт мержа отказывает после `_sync_main_or_wait`. Сбой git
в этой сверке тоже даёт отказ.

AC-19. На `in_dev -> verifying` долгоживущие файлы перечня исполняются в
том же прогоне `acceptance.run`, что и приёмочные тесты. Итог называет
число тестов разовой и долгоживущей групп.

AC-20. У задачи внешнего target и у задачи со `skip_tests` перечень не
пишется и сверка перечня не выполняется. Их переходы ведут себя как до
задачи.

AC-21. Задание test_author в `orchestrator/role_prompt.py` называет три
вещи: каталог `tests/` кодовой ветки как место долгоживущих файлов, имя
`tests/test_<префикс>_<имя>.py` с префиксом своей задачи и запрет
трогать существующие файлы `tests/`. Задание developer сообщает, что
долгоживущие файлы задачи зафиксированы так же, как приёмочные тесты.

AC-22. PLAN.md несёт четыре приложения по требованию 12:
`skills/test-authoring.md`, `skills/coding-standards.md`,
`skills/review-checklist.md` и `docs/invariants.md` (инвариант 27). Для
каждого в PLAN.md подтверждён прогон `git apply --check` на чистом
дереве.

AC-23. Полный набор `tests/` зелёный. Ни один существующий тест и гейт
не ослаблен.

## Оценка объёма и деление

Сработавшие сигналы:
- файлов зоны 9 (≥ 5), плюс `tests/`;
- критериев приёмки 23 (≥ 10);
- `budget_usd` 35 (≥ $30);
- зона задевает механизм инварианта 27 `docs/invariants.md` (лок
  каталога приёмочных тестов).

**Обоснование монолита.** Эта задача уже выделена Оператором как вторая
часть трёхчастного внедрения ADR-0020. Внутри неё атомарно меняется
место и защита долгоживущих файлов.
- Если отдельно смержить часть «test_author коммитит в `tests/` + гейт
  только добавления», долгоживущие файлы окажутся в кодовой ветке без
  перечня и сверки. Разработчик сможет их править, а это слабее
  нынешнего положения: сейчас файлы лежат под локом каталога. Такое
  промежуточное состояние ослабляет инвариант 27.
- Если отдельно смержить часть «перечень + сверка», ей нечего фиксировать:
  файлов в `tests/` нет, пока их не разрешил коммит test_author.
- Задания ролей и отказ за долгоживущий файл в каталоге приёмочных
  тестов (требование 4) имеют смысл только вместе с обеими частями.

Решение о монолите утверждает Оператор на гейте SPEC.

Бюджет: `budget_usd` равен рамке ТЗ ($35). Калибровка
`config.BUDGET_CALIBRATION_TABLE` для класса «больше 15 критериев или
8 и более файлов зоны» ориентирует на ~85. Рамка Оператора ниже
калибровки, и риск подъёма потолка по ходу задачи реален. Ставку не
поднимаю: ТЗ задаёт рамку, поднять потолок вправе Оператор командой
`budget`.

Новых состояний FSM и промежуточных шагов в существующих маршрутах
задача не добавляет: рубежи сверки ставятся на существующие переходы.
Поэтому ожидаемой красноты `tests/test_invariants.py` нет.

  `tests/`».
- Распространение схемы на внешние target.

- Правка джобов CI (`.github/`), в том числе красного CI ветки с момента

- Сверка перечня на пути автогейта в `orchestrator/fsm_autogate.py`: по

- Правки модулей только для чтения по ТЗ: `orchestrator/gitcmd.py`,
