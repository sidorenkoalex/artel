## Замечания ревью 3 — закрытие

- **major (`UnicodeDecodeError` на пути diff) — закрыт, проверено вживую.**
  `git_diff_part`:450–460 ловит исключение и отдаёт причину третьим значением.
  Воспроизвёл тот же сценарий, на котором ловил дефект в прошлый раз: временный
  репозиторий в песочнице (рабочее дерево не тронуто), ветка добавляет
  `latin.txt` со строкой `caf\xe9 na\xefve r\xe9sum\xe9 stra\xdfe` в latin-1,
  NUL нет. До правки здесь был трейсбек; теперь:

  ```
  [] -> ИСКЛЮЧЕНИЕ UnicodeDecodeError ...       # сырой git по-прежнему падает
  ['--stat'] -> rc 0 ' latin.txt | 1 +\n ...'   # стат-список декодируется
  diff часть: ('(не собран: не прочитан: ...)', 0, 'не прочитан: ...')
  note: символов 1317, байт 1557, строк diff 0, diff не собран: не прочитан: ...
  стат-список latin.txt в пакете: True
  ```

  То есть `run` доходит до журнала, причина в `log <id>` названа, и — важное —
  стат-список выживает: `git diff --stat` отдаёт ASCII и декодируется. Это ровно
  то, что PLAN обещает в шаге 4.

- **minor (docstring `test_worktree_fallback_is_journaled`) — закрыт.**
  tests/test_review_package.py:620–626 теперь описывает фактическую песочницу
  («`setUp` копирует `templates/` в песочницу под подменённый `ROOT`») вместо
  прежнего «подмены `ROOT` тест не требует». Противоречия с фикстурой нет.

- **minor (счёт тестов) — закрыт.** PLAN: «195 против 155 на main, из них 40
  новых, минус ноль». Пересчитал независимо: main 155, ветка 195, новых 40 —
  сходится, и сходится с фактическим прогоном (`Ran 195 tests`).

## Замечания

- **minor — tests/test_review_package.py:105 (`FakeGit.__call__`) — `raises_on`
  сравнивает `args[0]`, поэтому фейк не умеет развести `git diff --stat` и
  `git diff`: в тестах они падают только вместе, а в жизни падает только второй.
  Реальная форма сбоя набором не покрыта, и гарантия «стат-список остаётся
  полным» ничем не защищена.** `raises_on = "diff"` (:472, :685) роняет оба
  вызова `git_diff_part`, хотя вживую (см. воспроизведение выше) `--stat`
  декодируется и отдаёт полный список файлов — единственное, по чему ревьювер
  судит об объёме изменения, когда содержимого diff нет вовсе.

  Сценарий поломки. Следующий, кто тронет `review_package`:500–501, увидит по
  тестам, что при сбое diff стат-список тоже недоступен, и сделает
  напрашивающееся: не тратить второй вызов git / показать одну общую причину.
  Проверил мутацией на копии дерева (рабочее дерево не тронуто, база падений
  копии — 18 ошибок в тестах уборки, которым нужен настоящий репозиторий):

  | Мутация | Исход |
  |---|---|
  | стат-список не собирается, когда diff не собрался (порядок вызовов меняется) | падает `test_stat_and_diff_are_taken_against_main` — **поймана**, но по порядку вызовов, а не по потере списка |
  | порядок вызовов сохранён, стат-список затирается причиной сбоя diff (`if diff_failed: stat = f"(не собран: {diff_failed})"`) | **выживает**: 40/40 в `tests.test_review_package`, полный набор — те же 18 ошибок базы, ни одного нового падения |

  Последствие второй мутации на живом сценарии: ревьювер получает пакет, где нет
  ни diff, ни списка файлов, — то есть судит о чужом MR вообще вслепую, ровно тот
  исход, который PLAN называет худшим («выпрошенный вслепую аппрув»). Набор этого
  не заметит.
  Предложение: ключевать `raises_on` по полной команде, а не по `args[0]`
  (например, бросать, когда `raises_on` — подстрока `" ".join(args)`, либо
  сравнивать с кортежем флагов), и добавить тест «diff не декодируется, а
  стат-список в пакете полный» — он же прямо выражает обещание шага 4 PLAN.

- **minor — orchestrator/artel.py:419–426 (`artifact_text`) — если `git show`
  упал на декодировании, а файл есть в рабочем дереве, пакет говорит «в ветке
  нет», хотя файл в ветке есть, и причину сбоя молча выбрасывает.** При успешном
  откате `in_branch` (:422) никуда не уходит: возвращается только
  `WORKTREE_NOTE`:396. Проверил прямым прогоном в песочнице — `git show` бросает
  `UnicodeDecodeError`, PLAN.md лежит в дереве:

  ```
  текст:   '# PLAN из ДЕРЕВА (другая ветка!)'
  пометка: ' (в ветке нет, показан файл из рабочего дерева)'
  причина сбоя декодирования названа? False
  ```

  Сценарий: артефакт закоммичен, но с байтами не в UTF-8. Ревьювер видит версию
  из дерева (а дерево оркестратор штатно держит на main — то есть возможно чужое
  содержимое), в журнал уходит `не из ветки, а из рабочего дерева: …`, и Оператор
  идёт разбираться, почему разработчик не закоммитил артефакт, вместо того чтобы
  чинить кодировку. Это то же «молчание выдаётся за пустоту», против которого
  написан весь остальной раздел, — просто на редкой ветке.
  Досягаемость честно оцениваю как низкую: артефакты и шаблон пишет сам
  оркестратор, всегда в UTF-8, — поэтому minor, а не major, и поэтому же это не
  повод держать MR. Предложение: при успешном откате дописывать причину к
  пометке (`WORKTREE_NOTE` + `не прочитан: …`), чтобы диагноз не подменялся.
