# ТЗ: Вердикт CI на verifying и на гейте мержа — по прогонам ветки задачи

Источник: копилка 30.09 (приоритет 1, «Задача застревает на verifying на
навсегда красном коммите main…»), черновик
docs/drafts/2026-10-05/tz-k2-verifying-red.md (часть «вердикт»; команда
подтяжки main — отдельная задача `pull-main`, заводится параллельно).
Решение Оператора 12.10.2026 — заводить.

Факты (origin/main 3a1be8b0):
- `orchestrator/ci.py::verifying_status` (~524-595): голова ветки →
  `check_runs(sha)` — ВСЕ проверки коммита любого события и любой ветки;
  `failed` — любая не-зелёная; правило `_unexecuted_full_suite` (~455):
  пропущенное задание полного набора требует исполненного близнеца в push
  или pull_request. Индекс прогонов коммита — `_commit_workflow_runs`
  (~357; запрос `actions/runs?head_sha=…&per_page=10`,
  `CI_RUNS_PER_PAGE = 10`), `_run_of` (~394), `_run_event` (~404); сегодня
  индекс строится только для подписи. `_event_divergence` (~421) — только
  текст. `branch_status` (~672) — то же для ожидания CI гейта мержа.
- Прогон pull_request несёт `headBranch` = ветка задачи (проверено на
  прогоне 38124848279) — фильтр по ветке реализуем для обоих событий.
- Исход статуса дальше читается по подстрокам текста: `verifying_is_red`
  («не зелёный:»), `status_kind` («ещё идёт», «неизвестен»),
  `_RED_NOTE_SHA_RE`, `stuck_check_ids` («check-run id»);
  `orchestrator/ci_rerun.py:89` ищет красный исход в журнале тем же
  `verifying_is_red`.
- Сравнение упавших проверок головы ветки и вершины main уже есть —
  `ci.failed_check_names(sha)` (~637; используется в ci_rerun.py
  ~267-279).
- Прочие потребители `verifying_status`, чьё поведение изменится без
  правки их файлов: `orchestrator/fsm_autogate.py:287`,
  `orchestrator/acceptance.py:1868`, `orchestrator/ci_rerun.py:123/158`.

Требуется:
1. Вердикт `verifying_status` и `branch_status` строится по проверкам
   прогонов ветки задачи. Набор обязательных проверок не меняется: все
   check-run'ы, которые сегодня входят в вердикт, и правило
   `_unexecuted_full_suite`, — но только из прогонов ветки задачи. Нового
   требования присутствия обоих событий не вводится.
2. Исключается из вердикта ТОЛЬКО проверка, у которой прогон найден и его
   головная ветка — другая ветка. Проверка без найденного прогона (индекс
   не получен, прогона нет на странице, у проверки нет связи с прогоном)
   остаётся в вердикте, как сегодня. Исключённые проверки называются в
   тексте статуса.
3. Ни одной проверки ветки задачи после исключения — исход «проверок нет
   / идут» (как сегодня для коммита без проверок), не зелёный.
4. Если упавшая проверка ветки красна с тем же именем и на вершине main
   (через `ci.failed_check_names`), красный статус говорит об этом
   отдельной фразой («красный унаследован от main <sha>») и подсказывает
   команду `pull-main <id>` (команда из параллельной задачи pull-main). Вердикт остаётся красным.
5. Новые фразы (об исключённых прогонах других веток и «унаследован от
   main») не содержат подстрок, по которым разбирают статус (`не
   зелёный:`, `ещё идёт`, `неизвестен`, `check-run id`) — тот же запрет,
   что в докстринге `_event_divergence`.
6. Тесты в `tests/` с заявками «Ловит мутацию»: вердикт по всем проверкам
   коммита вместо прогонов ветки (красный прогон main на том же коммите
   красит задачу); отбрасывание проверки без найденного прогона (красная
   проверка ветки без прогона в индексе → задача красная); пусто после
   фильтра → зелёный; зелёный статус с красным прогоном другой ветки —
   `verifying_is_red` ложь, `status_kind` не меняется. Существующие тесты
   не ослабляются.
7. Раздел SPEC «Меняемое поведение» называет текст статуса и потребителей
   из «Фактов» (fsm_autogate.py, acceptance.py, ci_rerun.py).

Матрица неослабления (независимая проверка 12.10): из вердикта
исключаются только проверки, доказанно принадлежащие прогонам ДРУГИХ
веток; всё неопределённое остаётся; пустой набор не зелёный; набор
обязательных проверок и правило полного набора те же; «унаследован от
main» — только поясняющая фраза при красном вердикте.
