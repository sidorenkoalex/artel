# SPEC: Вердикт CI на verifying и гейте мержа — по прогонам ветки задачи

## Контекст
`orchestrator/ci.py::verifying_status` (~524) и `branch_status` (~672)
судят голову ветки задачи по ВСЕМ check-run'ам коммита — любого события и
любой ветки (`failed` на ~563/~698 — любая не-зелёная проверка). Красный
прогон `main` на том же коммите красит задачу, и она застревает на
`verifying` (копилка 30.09, приоритет 1). Индекс прогонов коммита
(`_commit_workflow_runs` ~357, `_run_of` ~394) сегодня строится только для
подписи проверок. Прогон и push, и pull_request несёт головную ветку
задачи (`headBranch`, проверено на прогоне 38124848279) — значит, вердикт
можно строить по прогонам ветки задачи. Подтяжка main в ветку — отдельная
задача `pull-main` (01M4PMR5EVFK4KQDPWB1KEGM7V).

## Требования
1. Вердикт `verifying_status` и `branch_status` строится по проверкам
   прогонов ветки задачи. Набор обязательных проверок не меняется: все
   check-run'ы, которые сегодня входят в вердикт, и правило
   `_unexecuted_full_suite`, — но только из прогонов ветки задачи. Нового
   требования присутствия обоих событий (push и pull_request) не вводится.
2. Из вердикта исключается ТОЛЬКО проверка, у которой прогон найден и его
   головная ветка — другая ветка. Проверка без найденного прогона (индекс
   не получен, прогона нет на странице, у проверки нет связи с прогоном)
   остаётся в вердикте, как сегодня. Исключённые проверки называются в
   тексте статуса.
3. Ни одной проверки ветки задачи после исключения — исход «проверок нет /
   идут» (как сегодня для коммита без проверок), не зелёный.
4. Если упавшая проверка ветки красна с тем же именем и на вершине main
   (через `ci.failed_check_names`), красный текст статуса говорит об этом
   отдельной фразой «красный унаследован от main <sha>». Фраза стоит в
   красном тексте обоих читателей — `verifying_status` и `branch_status`
   (ANSWER-1, п.2). Подсказка команды `pull-main <id>` стоит только в
   красном тексте `verifying_status`: гейт мержа подтягивает main сам
   (`orchestrator/fsm_merge_gate.py` ~671). Вердикт остаётся красным. На
   красном исходе гейта мержа `branch_status` зовётся дважды (ANSWER-1,
   п.2) — это учитывается, а не ломает исход.
5. Новые фразы (об исключённых проверках прогонов других веток и
   «унаследован от main») не содержат подстрок, по которым разбирают
   статус: `не зелёный:`, `ещё идёт`, `неизвестен`, `check-run id` — тот же
   запрет, что в докстринге `_event_divergence` (~428).
6. Тесты в `tests/` с заявками «Ловит мутацию»: вердикт по всем проверкам
   коммита вместо прогонов ветки (красный прогон main на том же коммите
   красит задачу); отбрасывание проверки без найденного прогона (красная
   проверка ветки без прогона в индексе → задача красная); пусто после
   фильтра → зелёный; зелёный статус с красным прогоном другой ветки —
   `verifying_is_red` ложь, `status_kind` не меняется. Существующие тесты
   не ослабляются (кроме разрешённого мандатом в требовании 8).
7. Раздел «Меняемое поведение» называет текст статуса и потребителей
   `verifying_status` из ТЗ: `orchestrator/fsm_autogate.py:287`,
   `orchestrator/acceptance.py:1868`, `orchestrator/ci_rerun.py:89/123/158`.
8. Метод `tests/test_ci_status.py::RunEventLabelTest::test_green_outcome_does_not_ask_workflow_runs`
   (мандат ослабления ANSWER-1, п.3): утверждение
   `assertFalse([c for c in calls if "actions/runs" in c], calls)`
   (строка ~1070) заменяется двумя утверждениями «ровно один запрос
   `actions/runs` в каждом вызове статуса»: число вызовов `gh` запоминается
   после `verifying_status`, запросы `actions/runs` считаются отдельно до
   этой границы и после неё (`branch_status`) — `assertEqual(..., 1, calls)`
   для каждой части. Утверждения о зелёном исходе обоих читателей
   (строки ~1067-1069) не меняются. Докстринг метода несёт заявку «Ловит
   мутацию»: прогоны коммита запрашиваются повторно в одном вызове статуса,
   либо читатель статуса не строит индекс прогонов и не отсекает проверки
   других веток (ноль запросов в его вызове). Метод
   `RunEventLabelTest::test_unlinked_check_runs_do_not_ask_workflow_runs`
   не меняется и остаётся зелёным.
9. В долгоживущем тесте `tests/test_01m46d5zzqy7gbew5tbvq0p3zv_ci_event.py`
   (помощник `FakeGitHub.add_run`, строка ~173) литерал данных фикстуры
   `"head_branch": "main"` меняется на `"task/x"` — ветку, которую тест
   спрашивает (ANSWER-1, п.1). Утверждения и остальные строки файла не
   меняются: разница по файлу — ровно одна строка.

## Критерии приёмки
AC-1. Коммит головы ветки несёт зелёные проверки прогона ветки задачи и
красную проверку прогона, найденного в индексе, с головной веткой `main`:
`verifying_status` даёт `VERIFYING_GREEN`, `branch_status` — `True`, текст
статуса называет исключённую проверку. Зелёные проверки только прогона
push ветки задачи (без pull_request) дают зелёный вердикт — присутствия
обоих событий не требуется.

AC-2. Красная проверка ветки, прогон которой не найден (индекс не получен;
прогона нет на странице индекса; у проверки нет `check_suite.id` и ссылки
на прогон), остаётся в вердикте: `verifying_status` — `VERIFYING_RED`,
`branch_status` — `False`.

AC-3. Все проверки коммита принадлежат прогонам других веток: исход
`verifying_status` — `VERIFYING_NONE` или `VERIFYING_RUNNING` (как для
коммита без проверок), не `VERIFYING_GREEN`; `branch_status` — `False`.

AC-4. Пропущенное (`skipped`) задание полного набора в прогоне ветки задачи,
чей исполненный зелёный близнец есть только в прогоне другой ветки, не
даёт зелёного вердикта: `verifying_status` — не `VERIFYING_GREEN`,
`branch_status` — `False` (правило `_unexecuted_full_suite` — только по
прогонам ветки задачи).

AC-5. Зелёный статус при красной проверке прогона другой ветки:
`ci.verifying_is_red(note)` — ложь; `ci.status_kind(note)` равен
`status_kind` того же текста без фразы об исключённых проверках.

AC-6. Упавшая проверка ветки, имя которой есть в `ci.failed_check_names`
вершины main: красный текст `verifying_status` (`VERIFYING_RED`) и
`branch_status` (`False`) несёт фразу «красный унаследован от main <sha>»;
текст `verifying_status` несёт подсказку `pull-main <id>`, текст
`branch_status` её не несёт. Упавшая проверка, которой нет среди упавших на
вершине main, фразы не даёт; вердикт в обоих случаях красный.

AC-7. Фраза об исключённых проверках и фраза «унаследован от main» (с
подсказкой) не содержат подстрок `не зелёный:`, `ещё идёт`, `неизвестен`,
`check-run id`.

AC-8. `tests/test_ci_status.py::RunEventLabelTest::test_green_outcome_does_not_ask_workflow_runs`
утверждает ровно один запрос `actions/runs` в вызове `verifying_status` и
ровно один — в вызове `branch_status` (`assertEqual(..., 1, calls)` для
каждой части); утверждения о зелёном исходе обоих читателей прежние; метод
и `test_unlinked_check_runs_do_not_ask_workflow_runs` зелёные.

AC-9. Разница `tests/test_01m46d5zzqy7gbew5tbvq0p3zv_ci_event.py` с main —
ровно одна строка: `"head_branch": "main"` → `"head_branch": "task/x"` в
`FakeGitHub.add_run`; все методы файла зелёные.

## Меняемое поведение
Текст статуса `verifying_status` и `branch_status` (требования 2, 4):
появляются фраза об исключённых проверках прогонов других веток и, на
красном исходе, фраза «красный унаследован от main <sha>» (подсказка
`pull-main <id>` — только у `verifying_status`). Исход меняется для
коммита, чьи красные/идущие проверки принадлежат только прогонам других
веток: был красный/идущий, станет зелёный (если проверки ветки зелёные)
либо «проверок нет / идут» (если проверок ветки нет).

Потребители `verifying_status`, чьё поведение изменится без правки их
файлов (файлы — только чтение): `orchestrator/fsm_autogate.py:287`,
`orchestrator/acceptance.py:1868`, `orchestrator/ci_rerun.py:123/158`;
`orchestrator/ci_rerun.py:89` ищет красный исход в журнале через
`verifying_is_red` — подстрока `не зелёный:` остаётся только в красном
исходе (требование 5). Потребитель `branch_status` — ожидание CI гейта
мержа (`orchestrator/fsm_merge_gate.py`, только чтение).

Смена ожидания `tests/test_ci_status.py::RunEventLabelTest::test_green_outcome_does_not_ask_workflow_runs`
меняет вид утверждения (`assertFalse` → `assertEqual`) и поэтому пунктом
этого раздела не оформлена: она идёт мандатом ослабления ANSWER-1, п.3
(требование 8). Правка фикстуры требования 9 — литерал данных, не
утверждения, пунктом раздела тоже не оформлена (ANSWER-1, п.1).
