## Пути обхода гейтов
1. Поле ветки прогона (SPEC.md:22). Разработчик, буквально взявший
   `headBranch` из SPEC, читает несуществующее в REST поле — фильтр
   мёртв, а новые тесты, написанные им же на заглушках с ключом
   `headBranch`, зелёные. Гейт не ослабляется (ничего не исключается),
   но задача формально сдана без результата. Обратный вариант — пустой
   `head_branch` считать «другой веткой» — ловит существующий
   tests/test_ci_status.py:1042-1053.
2. Пустой после фильтра исход `branch_status` (SPEC.md:37-38, AC-3).
   Текст вида «у коммита X нет проверок ветки задачи» без «неизвестен»
   формально выполняет AC-3 (`False`), но `status_kind` вернёт "red" —
   гейт мержа уйдёт в ре-ран и `sys.exit` «merge отклонён»
   (fsm_merge_gate.py:344, 273-305) вместо ожидания, плюс запись
   «подтверждённый красный» в flake-rate. Не обход в сторону зелёного,
   но порча метрики и поведения гейта.
3. «Унаследован от main» (AC-6). Неизвестная вершина main / её статус —
   поведение не задано; без требования «нет данных — фразы нет, исход
   прежний» реализация может молча опустить сверку (AC-6 всё равно
   пройдёт на заглушке). Вердикт остаётся красным — гейт не обходится.
4. Замечено вне зоны (не отклонение SPEC): `ci-rerun` сверяет
   `failed_check_names(head)` по ВСЕМ проверкам коммита
   (ci_rerun.py:267, 286-291) — после задачи может отказать «дефект
   main» по проверке прогона другой ветки, которой нет в вердикте
   `verifying`. Отказ консервативный; файл — только чтение.
