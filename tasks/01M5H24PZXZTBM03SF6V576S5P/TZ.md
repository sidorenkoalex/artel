# Механика канарейки, часть Б-1б: параллельный прогон --parallel

## Факты

Решения Оператора 19.10–21.10: строка бэклога «Частота канарейки и неподвижный main на время её прогона — механикой пульта» (коммит 49ce342c); часть А (реестр живого прогона, окно тишины, отказ мержа и обходов окна во время канарейки) смержена коммитом 25bd2f22; часть Б-2 (реестр живой канарейки) смержена коммитом 26469784. Один прогон `--k 2` идёт около часа, и всё это время пульт по механике части А отказывает `approve` на `merge_gate` и удерживает `note`. Цель — короче окно канарейки: задачи прогона идут одновременно отдельными процессами. Решение Оператора 21.10 по итогам второй независимой проверки ТЗ Б-1: Б-1 делится на две задачи; эта (Б-1б) заводится после мержа Б-1а (01M5FZ9G7M, смержена коммитом 82666a80). Решения Оператора 21.10 по этой задаче: `--parallel` отказывает для набора, где хоть одна роль на провайдере Codex; не более двух одновременных дочерних процессов; дочерний без строки прогона — красная строка от родителя, ненулевой код родителя при ненулевом дочернем, вывод задачи целиком по её завершении; срок ожидания родителя 60 с принят. В задачу включён перенос 1 из гейта SPEC части А (01M5C6QA6S, 20.10).

## Требуется

1. **Флаг `--parallel`.** `canary --k <N> [--sha] [--set] [--template] [--detach] --parallel` ведёт задачи прогона отдельными дочерними процессами подкоманды `canary run-task` (Б-1а), по одному на шаблон. Повторный флаг — отказ «canary: повторный --parallel» в _cmd_canary до ветки --detach. С `--detach` флаг доезжает до отвязанного процесса, файл результата — один. Справка `artel.py` называет флаг: --parallel — в ту же строку справки, что canary --k … --template … (её ищет tests/test_canary_template_flag.py::UsageNamesTemplateFlagTest); соседство --detach с пояснением о штатном запуске прежнее (CanaryHelpTest). Без флага _cmd_canary зовёт cmd_canary прежним набором именованных аргументов; новый параметр передаётся только при --parallel, по образцу on_run_stamp (только при --result-file). Тесты tests/test_new_argv_parsing.py с assert_called_once_with зелёные без правок. Без флага — прежний путь побайтно (единственная развилка — в `cmd_canary`, прежняя ветка не переписана). Критерий «побайтно прежний» — п. 9: существующие тесты последовательного пути зелёные без правок и новый тест сравнивает вывод прогона без флага с литералом, снятым на коде до правок этой задачи.
2. **Отказ для набора с ролями Codex.** `--parallel` при непустом `codex_roles` плана набора — отказ до обращения к origin, до замка профиля и до первого клона: «canary: --parallel недоступен для набора <имя>: роли <роли> на провайдере codex — профиль Codex канарейки один на машину; веди прогон без --parallel». Общий профиль Codex родитель и дочерние не трогают; без `--parallel` восстановление профиля прежнее. Критерий: тест п. 9.
3. **Не более двух одновременных процессов; очередь не останавливается.** Число одновременно живых дочерних процессов ограничено константой модуля `orchestrator/canary.py`, равной 2 (обоснование — замок полного прогона тестов не работает между клонами). При `--k` больше 2 остальные шаблоны ждут в очереди в порядке прогона; следующий запускается, когда завершился один из идущих. Ненулевой код выхода дочернего и исключение при его запуске или ожидании очередь не останавливают: следующий шаблон запускается так же, как после кода 0. Очередь прекращается только сигналом родителю (п. 5). Критерий: тест п. 9.
4. **Родитель прогона.** Как сейчас и ровно один раз: выбор шаблонов, план набора, проверяемый sha (единственное обращение к origin), `run_stamp`, запись реестра с меткой прежним `_live_run_record` (метка несёт pid родителя), вызов приёмника `on_run_stamp`, первая строка вывода (с флагом — дополнена « параллельно: не более 2 процессов»). Перед запуском родитель проверяет, что имена шаблонов попарно различны (иначе — отказ до первого клона); проверка попарной различности — до _resolve_target_sha и до записи реестра; тест повтора имени проходит через прежний отказ _named_pool_templates. Дочерние процессы — подкоманда `canary run-task` с пятью аргументами (`--stamp` — `run_stamp` родителя, `--template` — путь шаблона, `--sha` — проверяемый sha родителя как есть, то есть полный 40-символьный sha из `_resolve_target_sha`, а не значение флага `--sha` команды и не пометка происхождения, `--set` — plan.name, то же значение, что поле set_name записи родителя, `--summary` — поле summary плана, пустая строка при пустом); argv дочернего собирает одна функция `orchestrator/canary.py` (имя — в отчёте разработчика), через неё тесты подменяют дочерний. Дочерний запускается интерпретатором пульта с `-u`, как `_detach_canary`, под откладыванием сигналов по образцу `_SignalDeferral`, каждый в своей группе процессов, рабочий каталог — корень пульта. Дочерний — прямой потомок процесса родителя, без промежуточной оболочки: проверка метки Б-1а сравнивает pid в метке с `os.getppid()` дочернего.

   **Сверка формы sha в дочернем — единственная правка подкоманды Б-1а.** `canary run-task` с `--sha`, не совпадающим целиком с формой полного sha (`[0-9a-f]{40}`, как `SHA_FORM`), — отказ «canary run-task: --sha <значение> — не полный 40-символьный sha» с ненулевым кодом до записи дочернего в реестр: своей записи и её временного файла нет, строки `canary_runs` нет, `_run_one_task` и клон не вызваны, метка не тронута. Место сверки — разбор `_cmd_canary_run_task` после проверки `run_stamp` либо начало `cmd_canary_run_task` до `_set_plan`; остальной порядок подкоманды Б-1а прежний. Родителю такой дочерний даёт красную строку по п. 6 («процесс задачи завершился с кодом 1 без строки прогона»). Критерий: тест п. 9. Журнал дочернего — файл `<run_stamp>-<шаблон>.log` (шаблон — имя файла без `.md`) в подкаталоге canary каталога журналов пульта (атрибут LOGS модуля config, вне клона, переживает прогон); файл открывает родитель до запуска и передаёт дочернему как стандартный вывод и вывод ошибок. Дочернему родитель не передаёт `--result-file` и приёмник. Критерий: тест п. 9 сверяет argv подменённого дочернего (флаг `-u`, пять аргументов), путь журнала и одну первую строку.
5. **Остановка дочерних; реестр.** Родитель снимает свою запись и метку только после завершения всех запущенных дочерних. На любом выходе (штатно, исключение, сигнал, `KeyboardInterrupt`) родитель не запускает шаблоны из очереди и останавливает ещё живых дочерних: SIGTERM группам всех живых дочерних сразу, затем общее ожидание без SIGKILL не дольше константы модуля `orchestrator/canary.py`, равной 60 с (два срока `GROUP_TERMINATE_GRACE_SEC` на снятие группы ведения внутри дочернего плюс запас на уборку клона и origin-заглушки; тест сверяет, что константа больше двух `GROUP_TERMINATE_GRACE_SEC`); группам дочерних, не завершившихся за этот срок, — SIGKILL; затем ожидание завершения всех дочерних. Остановка дочерних (SIGTERM, ожидание, SIGKILL, ожидание, красные строки п. 6) идёт под откладыванием SIGTERM, SIGHUP и SIGINT по образцу `_SignalDeferral`. Повторный сигнал её не прерывает, запись и метка родителя снимаются после неё. Сигнал, пришедший во время остановки, после неё заново не поднимается и код выхода не меняет: код выхода родителя — 128 + номер первого сигнала, полученного родителем; если родитель выходил не по сигналу, а сигнал пришёл во время остановки, — 128 + номер этого сигнала. Дочернему, снятому SIGKILL, красная строка с причиной «снят SIGKILL после <N> с; группа ведения в клоне могла остаться — проверь doctor» (исход строки — _DRIVE_FAILED_OUTCOME, причина — строка вывода родителя по образцу _report_drive_failure; <N> — значение константы срока); его запись реестра снимает родитель после ожидания (метку при этом не трогает). Код чтения и уборки реестра Б-2 и запись дочернего Б-1а не меняются. Критерий: тесты п. 9 — сигнал родителю, SIGKILL по сроку, SIGHUP после SIGTERM во время остановки, запись дочернего после SIGKILL.
6. **Общий итог прогона.** Родитель ждёт все дочерние. Блок вывода каждой задачи печатается целиком по завершении её процесса — содержимое файла журнала дочернего с заголовком «[canary] <шаблон>: процесс <pid> завершён с кодом <n>, журнал <путь>»; строки разных задач не перемешиваются. Для каждого запущенного дочернего, после завершения которого в `canary_runs` нет строки его шаблона с `run_stamp` прогона, родитель пишет красную строку по образцу `_report_drive_failure` (исход `_DRIVE_FAILED_OUTCOME`, коммит в строке пуст) с причиной «процесс задачи завершился с кодом <n> без строки прогона» — на любом пути родителя, включая сигнал родителю; дочернему, снятому SIGKILL по п. 5, — причина п. 5. Шаблон, чей дочерний не запустился (исключение при открытии журнала или создании процесса), получает красную строку по тому же образцу с причиной «процесс задачи не запущен: <ошибка>»; очередь идёт дальше. Шаблон, не запущенный из-за сигнала родителю, строки не получает. Строка «прогон <run_stamp> завершён» — после всех задач (при сигнале родителю её нет, как в последовательном прогоне). Код выхода родителя — 0, только если все дочерние завершились с кодом 0, иначе ненулевой. Сигнал родителю — дочерние снимаются по п. 5, их строки «оборвана сигналом» остаются, код выхода родителя — 128 + номер сигнала. Файл результата — один на прогон, прежним отбором `_cmd_canary` по `run_stamp`: несёт строки всех задач прогона и только их. Критерий: тесты п. 9.
7. **Замер не ломается; перенос 1 из гейта SPEC части А.** Строки параллельного прогона по составу полей те же, что у последовательного (`run_stamp`, `set_name`, `models_summary`, коммит, сообщённый клоном, `verdict`). Базовую строку пары читает и пишет только дочерний процесс этой пары; строки и базовые строки других пар он не меняет. `canary_baseline`, `green_canary_runs`, `merges_since_last_green_run` и условие `pin-update` не меняются. Процесс, получивший отказ «прогон <run_stamp> уже идёт», не отдаёт `run_stamp` приёмнику ни в последовательном, ни в параллельном режиме; дочерние процессы приёмника не имеют вовсе. Критерий: тест п. 9 (перенос 1 — файл результата отказанного повтора не несёт строк чужого живого прогона).
8. **Неослабление защиты части А — без новых правок.** Код потребителей реестра (`_silence_window_reason`, `_refuse_during_canary`, `refuse_main_move_during_canary`, `live_run_note`) и код чтения реестра не меняются. Критерий: `tests/test_canary_run_task.py` (тесты Б-1а) и тесты реестра Б-2 зелёные без правок утверждений; дифф задачи не затрагивает перечисленные функции; тест п. 9 «гибель родителя — прогон живой по записи дочернего» (приёмочные тесты трёх состояний Б-1а разовые и в main не входят).
9. **Тесты.** Детерминированы, без сети, без настоящих ролей и без ожидания по часам (срок п. 5 в тестах подменяется); тесты не читают и не пишут настоящий реестр и настоящий каталог журналов пульта (песочница `ALL_CONFIG_ATTRS` из `tests/sandbox.py` или подмена каталога реестра, как в Б-2). Дочерний подменяется через функцию сборки argv п. 4 процессом интерпретатора с заданным исходом. В тестах сигнала, реестра и строк подменённый дочерний исполняет настоящий canary.cmd_canary_run_task в отдельном интерпретаторе: пути песочницы передаются файлом настроек, _run_one_task заменён заглушкой, управляемой именованным каналом (образец — _CHILD в tests/test_01m4axpy1py4ps1yafamd47vby_canary_lifecycle.py). Тест со SIGKILL по сроку содержит только дочерних, игнорирующих SIGTERM; тесты с послушными дочерними срок п. 5 не уменьшают.
