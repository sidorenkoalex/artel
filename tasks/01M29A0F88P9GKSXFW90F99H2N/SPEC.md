# SPEC: гейт заявки мутации — новые и изменённые тесты в tests/ без «Ловит мутацию» отклоняются на выходе in_dev, а не кругом ревью

## Контекст
Шесть задач за 11.09 (01M28NWK5X, 01M28NX43E, 01M28NX0M2, 01M290PP4K,
01M291EJMA, 01M29284PT) получили от ревьювера один и тот же major —
«новый тест в tests/ без заявки “Ловит мутацию: …” в докстринге»
(правило test_author из skills/test-authoring.md, строки 47–63; сверка
ревьювера — review-checklist фаза B п.3). Круг стоит ревьювер
$1.3–3.7, шаг разработчика $1.1–1.9 и ~8 минут CI ветки, хотя код не
менялся. Решение Оператора 11.09: класс закрывается кодом, не
напоминанием — проверка ложится на переход `in_dev -> verifying`, где
уже стоит гейт зон (`fsm_advance._zones_gate`) с тем же приёмом сверки
диффа с базой, и где отказ доходит до следующего шага разработчика
штатным блоком «ОТКАЗ ADVANCE (история)» без ревьювера и CI.

## Требования

1. В `scripts/guard.py` — константа `MUTATION_CLAIM` (по образцу
   `REDNESS_MARKER`) и функция `test_functions_without_mutation_claim(
   base_source: str | None, head_source: str | None) -> list[str]`: по
   AST HEAD-версии файла собирает функции и методы `test_*` (на уровне
   модуля и внутри классов), отбирает из них новые (имени нет в
   `base_source`, либо `base_source is None` — файл добавлен) и
   изменённые (текст сегмента функции в HEAD отличается от base), и
   возвращает имена тех, чей докстринг не содержит строку, начинающуюся
   с «Ловит мутацию:», с непустым текстом после двоеточия. HEAD не
   парсится (`SyntaxError`) — возвращается один элемент «<не парсится:
   текст ошибки>», не исключение.
2. В `orchestrator/fsm_advance.py` — гейт `_mutation_claim_gate(conn,
   task_id, t, branch) -> GateRefusal | None` на выходе `in_dev`, сразу
   после `_zones_gate_refuses` и до `_review_rework_gate_refuses`: база
   `gitcmd.diff_base(branch)`, файлы `gitcmd.diff_names`, отбираются
   только пути `tests/test_*.py`; base- и HEAD-содержимое читается из
   git (`git show <sha>:<path>`, удалённый в HEAD файл пропускается),
   для каждого файла зовётся функция требования 1. Есть хотя бы одно
   имя — `GateRefusal` с action «переход отклонён: гейт заявки
   мутации», detail — перечисление «<файл>: <функция>, <функция>; …» и
   текст правила («каждый новый или изменённый тест в tests/ несёт в
   докстринге строку “Ловит мутацию: <что сломали — и тест
   покраснеет>”, skills/test-authoring.md»), hint — «допиши заявку и
   повтори artel.py advance <id>». Ошибки git (база или дифф не
   определились) — отказ с именованной причиной по образцу гейта зон,
   не пропуск.
3. Гейт не звонится для канареечных задач (`t["is_canary"]`) и для
   задач с внешним target (`t["target"] != config.DEFAULT_TARGET`) —
   тем же условием, что и `_origin_push_gate`.
4. Отказ доходит до следующего шага разработчика штатным блоком «ОТКАЗ
   ADVANCE (история)» без правки `runner.py`/`brief.py`: после отказа
   `brief.advance_refusal_history(conn, task_id, "developer", "in_dev")`
   содержит перечисление файлов и функций из detail.

## Критерии приёмки

AC-1. `scripts/guard.py` несёт константу `MUTATION_CLAIM` (по образцу
`REDNESS_MARKER`) и функцию `test_functions_without_mutation_claim(
base_source: str | None, head_source: str | None) -> list[str]`,
собирающую по AST HEAD-версии все функции и методы `test_*` — на
уровне модуля и внутри классов.

AC-2. Функция различает новые функции (имени нет в `base_source`, либо
`base_source is None`) и изменённые (текст сегмента функции в HEAD
отличается от текста в base) от неизменённых; неизменённые функции без
заявки в результат не попадают ни при каких условиях (старые тесты не
трогаем).

AC-3. Новая или изменённая функция попадает в результат по имени, если
её докстринг не содержит строку, начинающуюся с «Ловит мутацию:», с
непустым текстом после двоеточия (это покрывает и полное отсутствие
строки, и строку с пустым текстом после двоеточия).

AC-4. Если HEAD-версия файла не парсится (`SyntaxError`), функция
возвращает список из одного элемента «<не парсится: текст ошибки>», не
поднимает исключение.

AC-5. `orchestrator/fsm_advance.py` несёт гейт `_mutation_claim_gate(
conn, task_id, t, branch) -> GateRefusal | None`, вызываемый в порядке
гейтов `in_dev()` сразу после `_zones_gate_refuses` и до
`_review_rework_gate_refuses`; гейт берёт базу `gitcmd.diff_base(
branch)` и список файлов `gitcmd.diff_names(base, branch)`, отбирает из
них только пути `tests/test_*.py` (остальные пути дифф не проверяются),
читает base- и HEAD-содержимое каждого через `git show <sha>:<path>`
(файл, удалённый в HEAD, пропускается), и вызывает для него функцию
из AC-1–AC-4.

AC-6. Если хотя бы для одного файла функция вернула непустой список
имён, гейт возвращает `GateRefusal` с action «переход отклонён: гейт
заявки мутации», detail — перечислением «<файл>: <функция>,
<функция>; …» по каждому затронутому файлу, сообщением, несущим текст
правила («каждый новый или изменённый тест в tests/ несёт в
докстринге строку “Ловит мутацию: <что сломали — и тест покраснеет>”,
skills/test-authoring.md»), и hint «допиши заявку и повтори artel.py
advance <id>».

AC-7. Если git не определил базу сравнения или список файлов диффа,
гейт возвращает отказ с именованной причиной (по образцу отказов
`_zones_gate` на тех же условиях), а не пропускает переход молча.

AC-8. Гейт не вызывается (возвращает `None` без проверки) для
канареечной задачи (`t["is_canary"]`) и для задачи с внешним target
(`t["target"] != config.DEFAULT_TARGET`) — тем же условием, что и
`_origin_push_gate`.

AC-9. После отказа этого гейта `brief.advance_refusal_history(conn,
task_id, "developer", "in_dev")` содержит перечисление файлов и
функций из detail отказа — отказ доходит до следующего шага
разработчика штатным блоком «ОТКАЗ ADVANCE (история)», без изменений в
`orchestrator/runner.py` и `orchestrator/brief.py`.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` ($45) ≥ $30; зона задевает механизм,
на который прямо опирается запись в `docs/invariants.md` — инвариант
№36 (docs/invariants.md, строка 67) фиксирует «семь рубежей» перехода
`in_dev -> verifying` поимённо; эта задача добавляет восьмой.

**Обоснование монолита.** Части «функция в guard.py» и «гейт в
fsm_advance.py» не режутся на самостоятельно мержимые куски:

- функция `test_functions_without_mutation_claim` без вызывающего её
  гейта — мёртвый код (никто её не зовёт), что подряд с нормой «никаких
  недоделанных внедрений» делает часть-1-без-части-2 нежизнеспособным
  промежуточным состоянием;
- гейт `_mutation_claim_gate` не существует без этой функции — жёсткая
  зависимость, не параллельная работа; отдельная подзадача на гейт не
  начала бы работу раньше, чем подзадача на функцию домержится;
- AC-9 (отказ доходит до `advance_refusal_history`) — сквозной
  критерий, проверяемый только на интеграции функции и гейта вместе;
  часть-1 в одиночку не даёт ни одного самостоятельно проверяемого
  критерия приёмки сверх «функция существует»;
- ТЗ Оператора уже calibровано под эту пару как один рамка ($45,
  6–10 критериев — типовая задача), а два круга analyst/reviewer/
  developer/test_author вместо одного увеличили бы стоимость сильнее,
  чем экономит сама задача (тот самый счёт из «Контекста», который она
  чинит).

Инвариант №36 (`docs/invariants.md`) — защищённый путь: правку счётчика
«семь» → «восемь» рубежей делает только Оператор; см. «Не входит».

  добавит абзац «новый тест в tests/ — с заявкой “Ловит мутацию: …”,

  test_author свой гейт трассируемости и маркер «Красен до

- проверка правдоподобности самой заявки о мутации — дело ревьювера,
  не гейта;
- повторный вызов агента внутри того же шага;
- правки `orchestrator/runner.py`, `orchestrator/brief.py`,
  `orchestrator/role_prompt.py`;
- CI-проверка всего каталога `tests/` (131 файл, 79 без заявки —
  проверяется только то, что дифф задачи добавил или изменил);
- правка `docs/invariants.md` (инвариант №36, счётчик «семь рубежей» →
  «восемь») — защищённый путь, вне мандата роли developer; правит
  Оператор отдельно после мержа. Комментарий-счётчик в
  `orchestrator/fsm_advance.py` (строка 1245, не защищённый путь) —
  внутри зоны задачи, его актуальность на усмотрение developer;
- ослабление или удаление существующих тестов `fsm_advance.in_dev`,
  гейта зон (`tests/test_zones_gate.py`) и `scripts/guard.py` — ТЗ
  требование 5 фиксирует это явно для данной задачи поверх общей нормы
