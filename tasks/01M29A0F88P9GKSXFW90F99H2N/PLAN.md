# PLAN: гейт заявки мутации — новые и изменённые тесты в tests/ без «Ловит мутацию» отклоняются на выходе in_dev

## Подход
Класс замечания «новый тест в `tests/` без заявки “Ловит мутацию: …”»
переносится с ревьювера на гейт `in_dev -> verifying`, по образцу уже
существующего гейта зон (`_zones_gate`): та же база сравнения
(`gitcmd.diff_base`), тот же приём чтения base/HEAD-содержимого файлов
через git, тот же fail-closed отказ на сбое git.

Два новых элемента:
1. `scripts/guard.py::test_functions_without_mutation_claim` — по AST
   HEAD-версии файла собирает функции и методы `test_*` (уровень модуля
   и внутри классов, не глубже), различает новые/изменённые/неизменённые
   сравнением текстового сегмента функции (`ast.get_source_segment`) с
   одноимённой в base, и возвращает имена тех новых/изменённых, чей
   докстринг не содержит `MUTATION_CLAIM` (та же схема regex, что
   `REDNESS_MARKER`, — «Ловит мутацию: <непустой текст>»).
2. `orchestrator/fsm_advance.py::_mutation_claim_gate` — вызывает
   функцию для каждого `tests/test_*.py` из диффа ветки, отказывает
   `GateRefusal` при первом непустом результате.

Гейт вызывается в `in_dev()` через каркас `_run_gates` (тот же приём,
что вызов `_origin_push_gate`), сразу после `_zones_gate_refuses` и до
`_review_rework_gate_refuses` — порядок из требования 2/AC-5.

Условие пропуска (канарейка / внешний target) реализовано ВНУТРИ самой
`_mutation_claim_gate` (ранний `return None`), не на месте вызова —
буквальное прочтение AC-8 («гейт не вызывается… тем же условием, что
`_origin_push_gate`») подразумевает эквивалент проверки внутри гейта,
а не обёртку на стороне `in_dev()`.

## Шаги

1. `scripts/guard.py`: константа `MUTATION_CLAIM`, приватный помощник
   `_collect_test_functions`, публичная функция
   `test_functions_without_mutation_claim`.
2. `orchestrator/fsm_advance.py`: гейт `_mutation_claim_gate` + вызов в
   `in_dev()` между `_zones_gate_refuses` и `_review_rework_gate_refuses`.
3. Юнит-тесты: `tests/test_guard_mutation_claim.py` (AC-1..AC-4) и
   `tests/test_mutation_claim_gate.py` (AC-5..AC-9), по образцу
   `tests/test_zones_gate.py`/`tests/test_capacity_gate.py`.

## Влияние на систему
Гейт добавляется как восьмой рубеж перехода `in_dev -> verifying`
(инвариант №36, `docs/invariants.md`) — счётчик «семь рубежей» правит
Оператор отдельно (см. SPEC «Не входит»), эта задача его не трогает.
Существующие гейты (`_zones_gate`, `_capacity_gate`,
`_review_rework_gate`, `_origin_push_gate`) не изменены и не ослаблены —
новый гейт вставлен как независимый элемент списка проверок, порядок
предыдущих гейтов сохранён байт-в-байт. Откат — удаление одного вызова
в `in_dev()` и одной функции в каждом из двух файлов, без побочных
структур (новых колонок БД, новых состояний FSM нет).

Гейт читает только `tests/test_*.py` верхнего уровня — остальные пути
диффа не затрагиваются, `acceptance_tests/` вне зоны проверки (у него
свой рубеж трассируемости, SPEC «Не входит»).

## Риски
- AST-сравнение сегментов функции чувствительно к любой правке текста
  функции, включая форматирование (например, автоформаттер) — это
  соответствует букве AC-2 («текст сегмента отличается»), но может
  потребовать заявки мутации и на чисто косметическую правку тела
  теста. Не смягчаю: SPEC не делает исключения для косметики, а
  занижение чувствительности сравнения — это ослабление гейта.
- Коллизия имён одноимённых `test_*` методов в разных классах одного
  файла: функция сопоставляет по имени без квалификации классом. В
  текущей кодовой базе такой коллизии не встречено (см. tests/*.py);
  SPEC называет результат как список имён, не квалифицированных путём
  класса, — реализация следует буквальному тексту требования 1.
