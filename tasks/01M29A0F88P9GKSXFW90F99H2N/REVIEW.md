## Замечания

- major — `orchestrator/fsm_advance.py:1002-1026` — R1-F2 исправлен
  только частично. Фикс различает `head_reason == "git не ответил"` и
  `head_reason.startswith("не прочитан:")` (обе ветки теперь отказывают
  переход), но третья ветка `gitcmd.show` — любой ДРУГОЙ ненулевой код
  возврата `git show` — по-прежнему безусловно трактуется кодом и
  комментарием (строки 1012-1013: «путь реально отсутствует в дереве —
  легитимное удаление») как «файл легитимно удалён» и молча
  пропускается (`continue`). Это не всегда так: `gitcmd.show`
  (`orchestrator/gitcmd.py:387-389`) возвращает эту же причину для
  ЛЮБОГО `git show`, завершившегося с ненулевым кодом — не только для
  «пути нет в дереве». Проверено воспроизведением обеих причин: для
  реально отсутствующего пути `git show HEAD:tests/test_несуществующий.py`
  отдаёт `returncode=128`, `stderr="fatal: path '...' does not exist in
  'HEAD'\n"` — а для файла, который в дереве ЕСТЬ, но `git show` не смог
  прочитать его по иной причине (повреждённый объект, ошибка ФС,
  недоступный blob), придёт тот же ненулевой `returncode` с ДРУГИМ
  текстом `stderr`, и гейт так же молча пропустит проверку заявки
  мутации для этого файла — то есть новый/изменённый тест без «Ловит
  мутацию» проскочит гейт именно в сценарии, для закрытия которого весь
  класс замечания R1-F2 и заводился (docstring гейта, строки 965-966,
  прямо обещает «тот же приём отказа на сбое git… не пропуск перехода
  молча» — без оговорки «кроме недекодируемых причин, кроме этой»).
  Исходная формулировка R1-F2 итерации 1 уже называла этот класс
  явно («либо любой другой сбой ответа git на конкретный git show») —
  фикс закрыл только два из трёх перечисленных там сбоев. Предложение:
  сузить ветку «легитимное удаление» до фактического текста `git show`
  на отсутствующий путь — `head_reason` в этом случае стабильно содержит
  `"does not exist in"` (проверено вручную, см. «Проверено исполнением»);
  любой ДРУГОЙ текст стороны ненулевого `returncode` — вести в
  `GateRefusal`, как две уже обработанные ветки, а не в `continue`. Это
  не требует правки `orchestrator/gitcmd.py` (вне зон задачи) — сверка
  делается на уже возвращаемой строке `head_reason` внутри `_mutation_claim_gate`.
