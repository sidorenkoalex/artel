# SPEC: Токены рядом с долларами: status, RETRO, report

## Контекст
Линия «Интерфейс исполнителя, часть 2» (родитель
01M31Y3RXXKS1BGC6JH3527FN0; решение Оператора 20.09: единица гейтов —
доллар, токены показываются рядом). Часть 1 нарезки смержена: строка
журнала «agent cost KNOWN/PARTIAL» уже несёт `provider=` рядом с
`model=` и датой тарифа, а разбивка токенов по видам учтена в журнале
(«agent cost KNOWN» — по видам, «agent run finished» — суммарное
число). Показаны эти числа скупо: `status`
(`orchestrator/catalog.py`) печатает только «$spent/budget», RETRO
(`orchestrator/retro.py`, блок стоимости) — доллары и одно суммарное
число токенов по роли, `report` (`orchestrator/report.py`) — доллары и
калибровку курса по модели. Задача ставит токены рядом с долларами во
всех трёх местах показа и добавляет провайдера в поля ретро-корпуса
(`orchestrator/retro_corpus.py`).

## Требования

1. `status`: по каждой задаче печатается суммарное число токенов рядом
   с «$spent/budget»; одна строка на задачу сохраняется.
2. RETRO: по каждой роли печатаются доллары, суммарные токены и
   разбивка по четырём видам (`input`, `output`, `cache_write`,
   `cache_read`).
3. RETRO: по каждой роли печатаются провайдер и модель шагов роли.
4. `report`: токены по видам показаны рядом с долларами в разрезе задач
   и в разрезе ролей.
5. Задача, роль или строка без записей токенов показывает прочерк, а не
   ноль — во всех трёх местах показа (`status`, RETRO, `report`).
6. `orchestrator/retro_corpus.py` добавляет в собираемые поля
   провайдера, если RETRO его несёт; RETRO без провайдера по-прежнему
   попадает в кэш корпуса на прежних полях (`operator`, `model`,
   `artel_sha`).
7. `docs/stack.md`: абзац «Вывод и стоимость у провайдера», написанный
   частью 1, дополняется тем, где показаны токены.
8. Тесты в `tests/` покрывают показ токенов по видам и прочерк без
   данных в `status`, RETRO и `report`; существующие
   `tests/test_report.py` и `tests/test_retro.py` остаются зелёными, а
   перечень обновлённых ожиданий этих тестов перечислен в PLAN.

## Критерии приёмки

AC-1. `status` печатает по каждой задаче суммарное число токенов рядом
с «$spent/budget», и на задачу приходится ровно одна строка вывода.

AC-2. Задача без записей токенов показывает в строке `status` прочерк,
а не ноль.

AC-3. RETRO печатает по каждой роли доллары, суммарное число токенов и
разбивку по четырём видам: `input`, `output`, `cache_write`,
`cache_read`.

AC-4. RETRO печатает по каждой роли провайдера и модель шагов этой
роли.

AC-5. Роль, по шагам которой записей токенов нет, показана в RETRO
прочерком вместо нуля (и в суммарном числе, и в разбивке по видам).

AC-6. RETRO задачи, дошедшей до `done`, остаётся в пределах 30 строк —
существующая проверка `tests/test_retro.py` зелёная.

AC-7. `report` показывает токены по видам рядом с долларами в разрезе
задач.

AC-8. `report` показывает токены по видам рядом с долларами в разрезе
ролей.

AC-9. Строка `report` без записей токенов показывает прочерк, а не
ноль.

AC-10. RETRO, несущий провайдера, попадает в кэш ретро-корпуса с полем
провайдера среди собираемых полей.

AC-11. RETRO без провайдера по-прежнему попадает в кэш ретро-корпуса на
прежних полях (`operator`, `model`, `artel_sha`), без отказа сборки.

AC-12. Абзац «Вывод и стоимость у провайдера» в `docs/stack.md` назван
местами, где показаны токены (`status`, RETRO, `report`).

AC-13. `tests/` несут тесты показа токенов по видам и показа прочерка
без данных для каждого из трёх мест показа; полный прогон `tests/`
зелёный.

AC-14. PLAN несёт перечень ожиданий существующих
`tests/test_report.py` и `tests/test_retro.py`, обновлённых этой
задачей.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны — 6 (порог 5); число критериев
приёмки — 14 (порог 10); прогноз диффа не дан. `budget_usd` $40 сигнала
не поднимает и
совпадает с рамкой Оператора из ТЗ (калибровочный ориентир класса «до
15 критериев, до 7 файлов зоны» — $45, ставка взята рамкой ТЗ, то есть
ниже ориентира).

**Обоснование монолита.** Задача сама уже часть нарезки родителя
01M31Y3RXXKS1BGC6JH3527FN0 (часть 2, «Порядок: после части 1»);
рамку и границы этой части задал Оператор заведением подзадачи.
Дальше она не режется по зонам осмысленно: требование 5 (прочерк
вместо нуля вместо данных) — одно правило показа на все три места
сразу, и части, разрезанные по местам показа (`catalog.py` /
`retro.py` / `report.py`), делили бы поперёк общие зоны `tests/` и
`docs/stack.md` — абзац «Вывод и стоимость у провайдера» описывает все
три места одним текстом, а тесты требования 8 проверяют одно и то же
правило в трёх местах. Промежуточное состояние «токены показаны в
одном месте из трёх, прочерк — только там» — ровно та несогласованность
показа, которую задача и убирает.
