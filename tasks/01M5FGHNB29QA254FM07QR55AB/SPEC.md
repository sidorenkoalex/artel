## Контекст
Две строки бэклога `docs/backlog.md` (раздел «Бэклог»), оба дефекта воспроизводятся на пине f1f805b6.

## Требования

1. **Парная запись выхода при каждом выходе из ожидания.** `_wait_for_zone` на каждом выходе, кроме освобождения зоны, до возврата `Stop` журналирует (актор `operator`, как у записи входа) запись выхода с честной причиной: команда `stop` (обе точки — до сна и во время сна), потолок ожидания, потеря lease. Текст строится новой функцией `wait_interrupted_action(reason, minutes, holder)` в `orchestrator/zone_lock.py` рядом с `wait_exit_action` и несёт причину, накопленные минуты ожидания и последнего известного держателя. Причина — тот же текст, что `Stop.reason` этого выхода: `_STOP_COMMAND_REASON` (`orchestrator/auto.py:116`) для обеих точек `stop`, `_ZONE_WAIT_CEILING_REASON` (`auto.py:100`) для потолка, `f"{_ZONE_WAIT_LEASE_LOST_REASON}: {lease_refusal}"` (`auto.py:110`, `:202`) для потери lease. Минуты — `int(elapsed_sec // 60)` от того же счётчика `elapsed_sec`, что у записи «зона свободна через» (`auto.py:216`). Текст не начинается ни с «зона свободна через», ни с «ждёт зоны» (например, «ожидание зоны прервано: <причина>; <N> мин, держал <id>»). Новая запись не печатается: вывод цикла прежний побайтно. Возвращаемый `Stop` (состояние, причина, подсказка, признак алерта), печать и последующая запись «auto остановлен» — прежние побайтно. Запись при освобождении зоны — прежняя побайтно, ровно одна.
2. **Открытость ожидания для `status`.** `wait_minutes` считает запись входа закрытой, если после неё (по id) есть любая из записей: «зона свободна через…», новая запись выхода требования 1, «auto старт», «auto остановлен», «цикл оборван». Записи «auto старт», «auto остановлен», «цикл оборван» распознаются по точному совпадению действия, записи выхода — по началу строки. Эти три литерала — константы `AUTO_START_ACTION` («auto старт»), `AUTO_STOPPED_ACTION` («auto остановлен»), `CYCLE_ABORTED_ACTION` («цикл оборван») в `orchestrator/zone_lock.py`; `orchestrator/auto.py` пишет эти записи через константы (`zone_lock.<имя>`). Запись `RELEASE_ACTION` входом в ожидание не считается. Без записи входа — `None`, как сегодня; в незакрытом ожидании — минуты от последней записи входа, как сегодня. Подпись `wait_minutes` не меняется.
3. **Неослабление механики зон.** Не меняются: `blocking_conflict`, `_start_conflict`, `_occupies`, `claim`, `refusal`, `queue_wait`, `queue_order`, `cmd_zone_release` и тексты `REFUSAL_ACTION`, `RELEASE_ACTION`, `CLAIM_ACTION`; условия выхода из цикла ожидания, интервал опроса, потолок и повтор `run` после освобождения зоны — прежние. Задача по-прежнему не стартует код в занятой зоне. В `orchestrator/zone_lock.py` меняются только маркеры ожидания (`_WAIT_*`, `wait_enter_action`, `wait_exit_action`, `wait_interrupted_action`, `wait_minutes`) и добавляются три константы записей цикла из требования 2 (`AUTO_START_ACTION`, `AUTO_STOPPED_ACTION`, `CYCLE_ABORTED_ACTION`).
4. **Подсказка отказа на гейте SPEC.** В отказе `spec_gate_declared_refusal` о потере заявленной зависимости часть после списка потерянных id ведёт по исполнимому пути: `artel.py reject <id> "<причина: аналитик, эскалируй вопрос о зависимости …>"` → аналитик эскалирует → `artel.py answer <id> <файл>` со строкой «Зависимости мержа: …» в `escalated` → `artel.py approve <id>`. Текст не предлагает `answer` на `spec_gate`: прежний хвост «снять заявленную может только Оператор: мандат «Зависимости мержа: …» в ANSWER (artel.py answer <id> <файл>)» из текста уходит, первое упоминание `answer` идёт после `reject` и называет `escalated`. Начало отказа (поле, «теряет зависимости, заявленные Оператором строкой ТЗ «Порядок: после»», список полных id) — прежнее; текст по-прежнему содержит «answer» и «эскалац» (условие долгоживущего теста `tests/test_01m45d29bqje8fjyja4jqwsyfz_spec_gate_declared.py`). Отказ о добавке без обоснования, отказ и подсказка на `merge_gate` (`merge_gate_refuses`), отказ `answer` на `spec_gate` — прежние побайтно.
5. **Тесты.** Новые тесты в `tests/` детерминированы, без сети, сон подменён приёмом `TimeWithSleep` из `tests/sandbox.py` (как в `tests/test_auto_cycle.py`) и покрывают критерии приёмки ниже. Существующие тесты и `tests/sandbox.py` не правятся.

## Критерии приёмки

AC-1. На каждом выходе из ожидания зоны, кроме освобождения, — `stop` до сна, `stop` во время сна (через `_on_sigterm`), потолок при `ZONE_WAIT_MAX_SEC = 0`, потолок при ненулевом `ZONE_WAIT_MAX_SEC` после нескольких опросов, потеря lease — в журнале задачи ровно одна запись входа «ждёт зоны …» и ровно одна новая запись выхода (актор `operator`), текст которой равен `zone_lock.wait_interrupted_action(reason, minutes, holder)` и не начинается ни с «зона свободна через», ни с «ждёт зоны»; записи «зона свободна через» нет. Здесь `reason` — точный текст `Stop.reason` этого выхода (`_STOP_COMMAND_REASON` для обеих точек `stop`, `_ZONE_WAIT_CEILING_REASON` для потолка, `f"{_ZONE_WAIT_LEASE_LOST_REASON}: {lease_refusal}"` для потери lease), и запись содержит этот текст; `holder` — id последнего известного держателя, запись содержит его; `minutes` — `int(elapsed_sec // 60)`: в сценарии с ненулевым потолком `ZONE_WAIT_MAX_SEC`, кратным `ZONE_WAIT_POLL_SEC` и равным нескольким опросам, запись несёт точное число минут `int(ZONE_WAIT_MAX_SEC // 60)`, в сценарии `ZONE_WAIT_MAX_SEC = 0` — `0`.

AC-2. На каждом выходе из AC-1 возвращаемый `Stop` (состояние, причина, подсказка, признак алерта), печатаемый вывод цикла и последующая запись «auto остановлен» совпадают побайтно с поведением до правки; новая запись выхода не печатается.

AC-3. При освобождении зоны в журнале ровно одна запись «зона свободна через …» в прежнем тексте и нет новой записи выхода требования 1.

AC-4. `wait_minutes` возвращает `None`, если после последней записи входа есть любая из записей: «зона свободна через…», новая запись выхода, «auto старт», «auto остановлен», «цикл оборван»; возвращает число минут от последней записи входа, если закрытия нет; возвращает `None` при журнале с единственной записью `RELEASE_ACTION`; возвращает `None` без записи входа; возвращает снова число при новой записи входа после закрытого ожидания.

AC-5. В `orchestrator/zone_lock.py` определены `AUTO_START_ACTION == "auto старт"`, `AUTO_STOPPED_ACTION == "auto остановлен"`, `CYCLE_ABORTED_ACTION == "цикл оборван"` (тексты записей в журнале прежние). Поведенчески: подмена каждой из трёх констант в модуле `zone_lock` на другое значение меняет текст соответствующей записи, которую журналирует `auto` (запись старта вызова `cmd_auto`, запись остановки `auto_stop`, запись исключения цикла в `cmd_auto`), на подменённое значение.

AC-6. `status` (`cmd_status`): после ожидания, прерванного командой `stop`, задача, всё ещё заблокированная зоной, не показывает «ждёт N мин», а держатель и очередь показываются как прежде.

AC-7. После каждого выхода из ожидания на занятой зоне отказ старта по зоне (`zone_lock.refusal`) отказывает так же, как до выхода, и роль не стартует; `zone-release` по-прежнему пускает задачу.

AC-8. Текст отказа `spec_gate_declared_refusal` о потере заявленной зависимости сохраняет прежнее начало (поле, «теряет зависимости, заявленные Оператором строкой ТЗ «Порядок: после»», список полных id), называет `reject`, эскалацию аналитика, `answer` со строкой «Зависимости мержа: …» в `escalated` и `approve`, содержит «answer» и «эскалац» и не предлагает `answer` на `spec_gate`: текст не содержит прежнего хвоста «снять заявленную может только Оператор: мандат «Зависимости мержа: …» в ANSWER (artel.py answer <id> <файл>)», первое вхождение `answer` в тексте стоит после первого вхождения `reject`, и в тексте есть `escalated`.

AC-9. Путь из подсказки исполним: `answer` со строкой «Зависимости мержа: …» в `escalated` меняет колонку `merge_after`, после чего тот же SPEC проходит `spec_gate_declared_refusal` без отказа; отказ о добавке без обоснования и подсказка `merge_gate_refuses` — прежние побайтно.
