## Фаза A: план

PLAN.md (`status: ready`) покрывает все 18 AC таблицей «Покрытие
требований», шаги — проверяемые единицы (крипто-примитивы → seal →
restore/единая точка расшифровки → drift-check → изоляция роли →
тесты → CI-диф-приложение), подход не конфликтует с конвенциями:
ленивый импорт `canary` внутри `catalog.cmd_init()` корректно снимает
цикл (`canary.py` уже импортирует `catalog` на уровне модуля),
`doctor.py` импортирует `canary` на уровне модуля без цикла — оба
утверждения PLAN проверил сам и подтверждены прогоном. Раздел «Риски»
честно называет асимметрию аудита (`pool_drift_warning` не поднимает
incident, `restore_pool_if_missing` — поднимает) как осознанное
решение, а не недосмотр — принимаю его как обоснованную интерпретацию
требования 5 («аудит вызова команды расшифровки», не любого internal-
сравнения). Диф-приложение к `.github/workflows/ci.yml` (защищённый
путь, требование 6) прогнан мной через `git apply --check` на текущей
голове ветки (после подтяжки main) — применяется чисто (пустой вывод,
код возврата 0), заявка PLAN подтверждена независимо, не только
доверием к докстрингу.

## Замечания

- major — `orchestrator/canary.py:151` (`_hmac_tag_hex`), `:162`
  (`_openssl_encrypt`), `:174-176` (`_openssl_decrypt`) — ключ пула и
  производный от него MAC-ключ передаются `openssl` АРГУМЕНТОМ
  командной строки (`-hmac {mac_key}`, `-pass pass:{key}`): на время
  жизни подпроцесса это значение видно в выводе `ps`/`ps aux` любому
  процессу того же пользователя (в macOS `ps` по умолчанию показывает
  полную командную строку своих процессов). Это ровно тот секрет,
  ради секретности которого существует вся задача (требования 1 и 5),
  и это не тот паттерн, что уже используется в кодовой базе:
  `orchestrator/keychain.py:18-19` получает секрет из `security`
  ЧЕРЕЗ STDOUT, никогда не кладёт его в argv нового процесса — здесь
  тот же принцип нарушен в противоположном направлении (секрет
  передаётся В процесс через argv). Ни один тест этого не проверяет:
  `test_pool_key_not_leaked.py` (AC-17) грепает только дерево
  репозитория и `role_env()`, не список процессов во время
  seal/restore. Предложение: передавать ключ через файловый дескриптор
  (`-pass fd:N` / `subprocess.run(..., pass_fds=(fd,))`) или переменную
  окружения подпроцесса, а не через `-hmac`/`-pass pass:` литералом.

- major — `orchestrator/canary.py:295-296` (`pool_drift_warning`) vs
  `:312-313` (`cmd_pool_seal`) — несогласованный фильтр файлов пула.
  `cmd_pool_seal` берёт в payload только `p.suffix == ".md"`, а
  `pool_drift_warning` сравнивает ВСЕ файлы каталога
  (`p.is_file()` без фильтра по суффиксу) с содержимым, которое
  `cmd_pool_seal` реально запечатал. Любой не-`.md` файл в
  `~/.artel-canary` (например, `.DS_Store`, который macOS Finder
  создаёт в любом просмотренном каталоге — SPEC явно называет
  macOS целевой платформой) даст `sealed_files != current_files` и
  постоянное ложное предупреждение AC-8 «незапечатанные правки» даже
  когда набор `*.md`-шаблонов не менялся ни на байт. Ни один тест
  (`CanaryPoolDriftCheckTest`, `test_pool_doctor_warning.py`) не кладёт
  в каталог пула файл без расширения `.md`, поэтому асимметрия не
  ловится планкой. Предложение: `pool_drift_warning` должен применять
  тот же фильтр `p.suffix == ".md"`, что и `cmd_pool_seal`.

- major — докстринг-заявка «Ловит мутацию: …» (skills/test-authoring.md,
  обязательна для КАЖДОГО нового/изменённого теста, review-checklist
  п.3) отсутствует у всех 6 новых классов юнит-тестов этой задачи —
  приёмочные тесты этой же задачи (`tasks/01M1NSR5M5THYRC0RFWPMVE2DW/
  acceptance_tests/*.py`) конвенцию держат образцово, а рядом стоящие
  `tests/*.py` — нет ни разу:
  - `tests/test_canary.py`: `PoolSerializationRoundtripTest`,
    `MacKeyTest`, `AuthorizedPoolPayloadRoleEnvTest`,
    `RestorePoolIfMissingNoOpTest` — докстринги описывают сценарий, но
    без заявки «Ловит мутацию:»;
  - `tests/test_doctor_canary_pool.py`: `CanaryPoolDriftCheckTest` —
    докстринга нет вовсе (ни у класса, ни у трёх методов);
  - `tests/test_new_argv_parsing.py`: `CmdCanaryDispatchTest` —
    докстринга нет вовсе (ни у класса, ни у двух методов).
  Известный повторяющийся класс (см. memory
  feedback_test_authoring_mutation_claim_gap.md) — прошу закрыть
  классом, а не по одному тесту: дописать «Ловит мутацию: …» во всех
  шести классах/их методах, называя конкретную мутацию, которую тест

- minor — «Оценка объёма и деление» SPEC.md называет зону задачи 7
