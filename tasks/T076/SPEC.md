# SPEC: Ложный инцидент целостности при отклонённом advance

## Контекст

При отклонённом переходе FSM (guard/условие не пройдено, задача остаётся
в текущем состоянии) `fixed_sha`, зафиксированный на входе в это
состояние, не обновляется. Роль тем не менее легитимно коммитит свои
артефакты внутри шага (например `tests_writing`: test_author коммитит
`acceptance_tests/`, guard отклоняет переход по маркерам красноты T064).
На следующем старте шага `fixation.check_integrity()` сравнивает голову
ветки с устаревшей фиксацией входа, видит расхождение и эскалирует
«инцидент целостности», хотя единственные новые коммиты — собственные
коммиты роли её же шага (двойная фактура: T069, T073, 29–30.08). Каждый
такой случай требует ручного разбора Оператора и `approve` по новому sha
на ровном месте, хотя успешный переход перефиксировал бы sha сам.

## Требования

1. На пути отклонённого перехода (guard или иное условие перехода не
   пройдено, задача остаётся в прежнем состоянии) система определяет,
   порождены ли ВСЕ новые коммиты между зафиксированным и текущим sha
   шагом этой же задачи — проверяемо по журналу задачи (окно
   «agent run started»/«agent run finished» шага) и/или по
   принадлежности коммитов ветке задачи с момента фиксации.
2. Если все новые коммиты порождены шагом задачи, эскалация «инцидент
   целостности» не поднимается: фиксация (`fixed_sha`) обновляется на
   текущую голову ветки, в журнал задачи пишется запись «sha
   перефиксирован после отклонённого перехода: коммиты шага», задача
   остаётся в текущем состоянии с обычной причиной отказа
   гейта/условия — как и сейчас.
3. Если среди новых коммитов есть хотя бы один, не порождённый шагом
   задачи (коммит вне окна шага или чужого авторства вне механики ролей
   и оркестратора), эскалация «инцидент целостности» поднимается как и
   сейчас.
4. Класс «грязная копия артефактов» (незакоммиченные изменения при
   отклонённом переходе) поведение не меняет — остаётся отдельным
   легитимным отказом, не эскалацией.
5. Механика фиксаций approve-по-sha (инвариант 19, T021/T033/T051) не
   ослабляется: операторский `approve` по-прежнему требует точный sha;
   меняется только реакция системы на sha-сдвиг при ОТКЛОНЁННОМ переходе
   FSM. Успешные переходы (перефиксация на успешном advance) не
   затрагиваются.

## Критерии приёмки

AC-1. Сценарий T069/T073 (роль в рамках шага закоммитила свои
артефакты, guard отклонил переход) не порождает эскалацию «инцидент
целостности»: задача остаётся в исходном состоянии с обычной причиной
отказа гейта, `fixed_sha` перефиксирован на текущую голову ветки,
журнал задачи содержит запись о перефиксации.

AC-2. Посторонний коммит (не входящий в окно шага задачи и/или не
принадлежащий её ветке с момента фиксации) при отклонённом переходе
по-прежнему приводит к эскалации «инцидент целостности», как и сейчас.

AC-3. Существующие тесты фиксаций и целостности (T021/T031/T033/T048/
T051 и смежные) остаются зелёными и не ослаблены (проверки не удалены
и не смягчены сверх требований 3–5 выше).

AC-4. Полный тестовый набор проекта зелёный.

## Не входит

- Ослабление или изменение механики approve-по-sha (операторский
  `approve` по-прежнему сверяется с точным sha).
- Изменение поведения при успешном (не отклонённом) переходе FSM.
- Класс «грязная копия артефактов» — вне объёма, поведение не меняется.
- Обход сверки целостности для чего-либо, кроме описанного в
  требованиях 1–3 случая коммитов, порождённых собственным шагом
  задачи.
