# PLAN: Ложный инцидент целостности при отклонённом advance

## Подход

Сегодня `fixed_sha` перефиксируется только на УСПЕШНОМ переходе FSM
(`store.set_state` -> `store.record_fixation`, orchestrator/store.py:431-472).
На пути отклонённого перехода (`fsm._cmd_advance` возвращает без смены
состояния — guard, трассируемость AC, лок и т.п.) фиксация никогда не
обновляется, хотя роль внутри шага могла легитимно закоммитить свои
артефакты (T069/T073: test_author коммитит `acceptance_tests/`, guard
отклоняет по маркеру красноты T064) — следующий `check_integrity()`
видит расхождение sha и эскалирует «инцидент целостности», хотя
единственные новые коммиты порождены самим шагом.

Решение — узкая добавка, не трогающая существующие точки фиксации:

1. Новый примитив `gitcmd.commit_committer_dates(since, until, repo=None)`
   — committer-даты (`%cI`) коммитов диапазона `since..until`, тем же
   стилем деградации, что у `commits_behind`/`head_sha` (`None` — git не
   ответил или диапазон недостижим).
2. Новая функция `fixation.refixate_after_rejected_transition(conn,
   task_id, target, entry_sha, current_sha)`: сверяет каждый коммит
   диапазона с закрытыми окнами `«agent run started»`/`«agent run
   finished»` журнала задачи (окна считаются с момента последней записи
   `«sha зафиксирован»` — та же точка, что и вход в текущее состояние).
   ВСЕ коммиты внутри хотя бы одного окна — `fixed_sha` перефиксируется
   на `current_sha` через `store.update_task` + отдельная журнальная
   запись `«sha перефиксирован после отклонённого перехода»` (не через
   `record_fixation` — та пишет `«sha зафиксирован»`, которая служит
   якорем окон, самозаписью её лучше не путать). Хотя бы один коммит вне
   всех окон, пустой список окон или git не ответил — `False`, фиксация
   не трогается (fail-closed: следующий `check_integrity()` эскалирует
   как и раньше).
3. Точка вызова — единственная: обёртка `fsm._advance_with_refixation`
   вокруг `_cmd_advance` в `fsm.cmd_advance`. После вызова: если
   `fixed_sha` на входе был непустым и состояние задачи НЕ изменилось
   (переход отклонён либо ещё не готов условие) — читает живое состояние
   через `fixation.read()` (не `fix()` — сверка, не точка фиксации, тот
   же принцип, что у `check_integrity`/`confirm_fixation`) и, если sha
   разошёлся, зовёт `refixate_after_rejected_transition`.

Единая точка вызова (а не расстановка по каждой ветке `_cmd_advance`)
означает, что механика симметрично покрывает ЛЮБОЙ путь отклонённого
перехода (spec_writing/review/tests_writing/in_dev), не только
конкретный сценарий T069/T073 — ровно то, что просит SPEC требование 1
(«на пути отклонённого перехода... условие перехода не пройдено»).
Безопасность для путей, которые сейчас не порождают лишних коммитов
(guard structural-отказы SPEC.md/REVIEW.md/PLAN.md без правки файла) —
тривиальна: `current == entry_sha`, функция не делает ничего.

Успешные переходы не задеты: обёртка проверяет именно «состояние НЕ
изменилось» — на успешном пути `record_fixation` уже отработал внутри
`set_state`, и `entry_sha` (прочитанный ДО вызова `_cmd_advance`)
сравнивается с уже устаревшим (старым) значением состояния, но условие
`state изменилось` замыкает обёртку раньше сравнения sha.

Класс «грязная копия» (`_dirty_refuses`) не трогается: если ничего не
закоммичено, `current == entry_sha` (голова не сдвинулась) — обёртке
нечего перефиксировать; если дерево дополнительно грязное после
коммита — `fixation.read()` всё равно вернёт `clean=False` независимо
от того, какой sha записан в `fixed_sha`, и следующий `check_integrity`
эскалирует «грязная копия» как и раньше (эта проверка не завязана на
`fixed_sha`, только на текущее состояние диска).

Approve-по-sha (инвариант 19) не трогается вообще: `confirm_fixation`
и `_cmd_approve*` этой задачей не правятся.

## Шаги

1. `orchestrator/gitcmd.py`: добавить `commit_committer_dates(since,
   until, repo=None)`.
2. `orchestrator/fixation.py`: добавить `_own_step_run_windows` и
   `refixate_after_rejected_transition`.
3. `orchestrator/fsm.py`: обернуть `_cmd_advance` в
   `_advance_with_refixation`, подключить в `cmd_advance`.
4. Юнит-тесты (`tests/test_step_refixation.py`, реальный git — тот же
   стенд `RealPultGitTest`, что и tests/test_git_fixation.py):
   собственный коммит шага перефиксирует и не эскалирует; посторонний
   коммит эскалирует как и раньше; незакрытое окно (нет `agent run
   finished`) не засчитывается; несколько окон подряд; фейковый git —
   поведение прежних тестов не меняется (регрессия).
5. `python3 scripts/codebase_map.py` — карта задета правкой `.py` в
   orchestrator/ (conventions-core).

## Влияние на систему

Новый код — чистая добавка (два новых примитива + одна точка вызова),
существующие функции `fixation.fix/read/check_integrity`,
`fsm.confirm_fixation`, `fsm._cmd_approve*`, `_dirty_refuses`,
`guard_refuses` не изменены ни строкой. Риск для инварианта 19 —
отсутствует: approve по-прежнему сверяется с точным sha, который читает
`fixation.read()` в момент approve, а не с каким-то «мягким» значением.

Единственный побочный эффект для НЕ-git песочниц (заглушка
`gitcmd.git`, большинство существующих тестов): `fixation.read()` там
всегда возвращает `("", False)` (пустой sha — git не отвечает
осмысленно на `rev-parse HEAD` под заглушкой) — обёртка видит
`current` пустым и не делает ничего, поведение этих тестов байт-в-байт
прежнее (проверено прогоном полного набора, шаг 4/AC-4).

Гейты/лимиты/инварианты рядом (approve-по-sha T021/T033/T051, лок
`acceptance_tests/` T023, грязная копия T033) не ослабляются — ни один
из них не читает `fixed_sha` иначе, чем раньше; новая функция только
СЖИМАЕТ окно ложного расхождения после отклонённого перехода, не
расширяет круг случаев, когда переход считается легитимным.

Откат — удалить точку вызова в `fsm.cmd_advance` (вернуть прямой вызов
`_cmd_advance`) и оставить неиспользуемые примитивы либо удалить их же
коммитом; данных/миграций схемы нет.

## Риски

- Committer-дата коммита неточно совпадает с окном шага при сильно
  рассинхронизированных часах машины-агента и БД (обе — один и тот же
  хост в текущей архитектуре пульта, риск теоретический).
- Диапазон `since..until`, где `since` не предок `until` (реврайт
  истории вручную) — `git log` в этом случае может вернуть неожиданно
  широкий список коммитов; безопасно — либо это не приведёт к совпадению
  со всеми окнами (fail-closed, эскалация как раньше), либо диапазон
  сам недостижим и git вернёт ошибку (тоже fail-closed).
