# SPEC: Штатный локальный прогон планки в шаге роли; шаг роли не удаляет отслеживаемые файлы вне своих путей

## Контекст
С части (б1) ADR-0021 документы задачи живут в каталоге документов
`.artel/projects/<проект>/tasks/<id>/`, а планку в рабочую копию кода
кладёт только пульт на время своего прогона
(`orchestrator/acceptance.py::plank_in_code_copy` →
`materialize_from_branch` + `drop_from_code_copy`). Правила ролей велят
гонять планку `python3 -m pytest tasks/<id>/acceptance_tests …` из рабочей
копии, а миссия шага (`orchestrator/role_prompt.py::docs_dir_note`) —
копировать её туда вручную; команды пульта для такого прогона нет, в
`orchestrator/artel.py::_ROLE_ALLOWED_COMMANDS` её нет. 03.10.2026 роли
пять раз убирали за собой весь отслеживаемый каталог задач
(`shutil.rmtree("tasks")`; в main 308 исторических каталогов, 3192 файла).
Для test_author/reviewer пульт откатывает изменения вне `tasks/<id>/`
(`orchestrator/checkpoint.py::_discard_out_of_mandate_changes`), для
developer незакоммиченное коммитит за роль
(`_commit_worktree_change`) — массовое удаление ушло бы в коммит ветки.

## Требования
1. Команда пульта `artel.py plank-run <id> [файл]` — локальный прогон
   планки задачи в шаге роли:
   - выкладывает планку в `tasks/<id>/acceptance_tests/` рабочей копии
     кода тем же узлом, что пульт (`acceptance.plank_in_code_copy` или
     его общий узел);
   - гоняет её тем же раннером и таймаутом, что пульт
     (`acceptance._pytest_command`, `config.ACCEPTANCE_TIMEOUT_SEC`);
   - печатает итог pytest и код выхода pytest;
   - убирает выкладку — только `tasks/<id>/` рабочей копии — на зелёном,
     красном исходе и на исключении внутри прогона;
   - источник планки: в состоянии `tests_writing` (шаг test_author) —
     текущий, ещё не зафиксированный черновик `acceptance_tests/`
     каталога документов задачи; в остальных состояниях — зафиксированная
     планка ссылки документов задачи;
   - аргумент `[файл]` — прогон одного файла планки.
2. Команда доступна процессу роли (входит в перечень команд роли,
   `orchestrator/artel.py::_ROLE_ALLOWED_COMMANDS` или его преемник) и не
   меняет состояния задачи, БД, ссылок и журнала. Задача без планки —
   именованный отказ (текст называет причину «планки нет»), без выкладки и
   прогона.
3. Правила ролей называют `plank-run` единственным способом локального
   прогона планки и прямым текстом с причиной (случаи 03.10.2026 —
   удаление всего отслеживаемого каталога задач) запрещают ручное
   копирование планки в рабочую копию и удаление каталогов рабочей копии
   для уборки:
   - защищённые файлы правил — `skills/test-authoring.md`,
     `skills/review-checklist.md`, `skills/coding-standards.md` —
     приложением к PLAN (unified-диф, проверенный `git apply --check`);
   - миссия шага `orchestrator/role_prompt.py::docs_dir_note` (правка
     кода в зоне задачи) перестаёт велеть копирование планки и называет
     `plank-run`.
4. После шага любой роли удалённые отслеживаемые файлы вне путей,
   которые роли разрешено менять (`tasks/<id>/`; для developer —
   дополнительно зоны задачи вместе с общими зонами
   `config.COMMON_ZONES`), восстанавливаются из HEAD и не попадают в
   коммит пульта; журнал задачи получает именованную запись с числом
   восстановленных файлов и первыми из их путей. Для developer это новое
   поведение; для test_author и reviewer — существующий откат, к которому
   добавляется та же запись журнала. Удаления внутри зон developer не
   трогаются (их судят гейт зон и гейт сохранности тестов).
5. Тесты в `tests/` с заявками «Ловит мутацию» на поведение требований
   1, 2 и 4 (перечень — AC-9).

## Критерии приёмки

AC-1. В состоянии `tests_writing` при черновике `acceptance_tests/` в
каталоге документов задачи, отличном от зафиксированной планки ссылки
документов (или при её отсутствии), `plank-run <id>` прогоняет именно
черновик: файлы черновика лежат в `tasks/<id>/acceptance_tests/` рабочей
копии кода на время прогона, команда pytest — `acceptance._pytest_command`
с таймаутом `config.ACCEPTANCE_TIMEOUT_SEC`, вывод команды содержит итог
pytest и код выхода pytest.

AC-2. В состоянии после `tests_writing` (например, `in_dev`, `review`)
`plank-run <id>` прогоняет зафиксированную планку ссылки документов, а не
расходящийся с ней файл на диске каталога документов; `plank-run <id>
<файл>` прогоняет только названный файл планки (тесты других файлов
планки не исполняются).

AC-3. После `plank-run` — на зелёном, красном исходе и при исключении,
поднятом внутри прогона, — в рабочей копии кода нет `tasks/<id>/`, а все
прочие отслеживаемые каталоги и файлы `tasks/` (исторические каталоги
задач) на месте и не изменены (`git status` рабочей копии по `tasks/`
чист).

AC-4. Процесс роли (признак шага роли в окружении) не получает отказа
диспетчера `orchestrator/artel.py` на `plank-run`; прогон `plank-run` не
меняет строку задачи в БД (состояние и прочие поля), не добавляет записей
журнала шагов и не сдвигает ссылку документов и ветку задачи.

AC-5. `plank-run <id>` на задаче без планки (ни черновика в
`tests_writing`, ни файлов `acceptance_tests/` в ссылке документов в
остальных состояниях) завершается ненулевым кодом с именованным текстом
отказа, называющим отсутствие планки; `tasks/<id>/` в рабочей копии кода
не появляется, pytest не запускается.

AC-6. Шаг developer, удаливший отслеживаемые файлы вне `tasks/<id>/` и вне
зон задачи (включая общие зоны), после шага: эти файлы восстановлены в
рабочей копии из HEAD, в коммите пульта по итогам шага их удаления нет, в
журнале задачи — одна именованная запись с числом восстановленных файлов
и первыми из их путей. Удаление отслеживаемого файла ВНУТРИ зон задачи тем
же шагом не восстанавливается и попадает в коммит пульта, как раньше.

AC-7. Шаг test_author и шаг reviewer, удалившие отслеживаемые файлы вне
`tasks/<id>/`, после шага: файлы восстановлены из HEAD (существующий
откат), в журнале задачи — та же именованная запись, что в AC-6, с числом
восстановленных файлов и первыми из их путей.

AC-8. Правила ролей: PLAN.md несёт приложение-диф к
`skills/test-authoring.md`, `skills/review-checklist.md`,
`skills/coding-standards.md`, применимое `git apply --check` на чистом
дереве; после применения каждый из трёх файлов называет `plank-run`
единственным способом локального прогона планки и прямым текстом с
причиной (случаи 03.10.2026) запрещает ручное копирование планки в рабочую
копию и удаление каталогов рабочей копии для уборки. Текст миссии
`orchestrator/role_prompt.py::docs_dir_note` не содержит указания
копировать планку (`copytree`) и называет `plank-run`.

AC-9. В `tests/` есть тесты с заявками «Ловит мутацию», покрывающие:
(а) `plank-run` выкладывает и убирает только `tasks/<id>/`, исторические
каталоги на месте после прогона, в том числе после исключения внутри
прогона; (б) `plank-run` доступна процессу роли; (в) в `tests_writing`
гоняется черновик, а не зафиксированная планка; (г) массовое удаление
исторических каталогов шагом developer восстановлено, не закоммичено, и
журнал называет число; (д) удаление внутри зон developer не
восстанавливается.

## Оценка объёма и деление
Сигналов нет: 9 критериев (< 10), одна некоммонная зона (`orchestrator/`)
плюс общие, `budget_usd` 30 (< порога). Секция не требуется.

## Не входит
- Уборка исторического каталога `tasks/` из main (операторский коммит по
  ADR-0018).
- Часть (в) ADR-0021.
- Изменение состава планки и гейтов перехода.
- Параллельный прогон (`-n`) в шаге роли.
- Запись журнала о самом прогоне `plank-run` (ТЗ допускает её только по
  требованию SPEC — не требуется; см. AC-4).
- Правка `docs/` (кроме карты), `templates/`, `scripts/guard.py`,
  `.github/`, `roles.yaml`, `targets.yaml`, `models.yaml`, `CLAUDE.md`,
  `requirements.lock`, `scripts/ci_push_class.py` — только чтение по ТЗ;
  `skills/` — только приложением к PLAN.
- Зелёный полный набор `tests/`, зелёный CI ветки, неизменность
  защищённых путей и непревышение бюджета — их держит пульт.
