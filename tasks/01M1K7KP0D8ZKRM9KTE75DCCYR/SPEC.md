# SPEC: Скилы и правила в бриф роли — из main, не из ветки задачи

## Контекст
Роль читает скилы (`skills/*.md`) и `CLAUDE.md` из рабочей копии своей
ветки задачи, которая может отставать от `main` до подтяжки —
правило, смерженное в `main` утром, не действует на роль, стартовавшую
позже по ветке, отведённой раньше. Прецедент: обязательные заявки
«Ловит мутацию» уехали в `main` утром 02.09, планка задачи, писавшаяся
днём, их не несла (замечание R1-F3) — потребовалась правка залоченной
планки по ADR-0012. Чтение артефактов ЗАДАЧИ уже ветко-корректно
(инвариант 28, `docs/invariants.md`) — этот приём нужно распространить
на компоненты брифа, являющиеся правилами системы, но с обратным
адресом: не с ветки задачи, а с `main`.

## Требования
1. Компоненты брифа роли, являющиеся ПРАВИЛАМИ системы — скилы роли
   (`skills/*.md`, перечисленные в составе роли) и `CLAUDE.md`, —
   читаются ветко-корректным чтением через git с ветки `main` пульта
   (тем же приёмом инварианта 28), а не с диска рабочей копии ветки
   задачи.
2. Артефакты задачи (`SPEC.md`, `PLAN.md`, `TZ.md`, `QUESTIONS.md`,
   `ANSWER-n.md` и прочее из `tasks/<id>/`) продолжают читаться с
   ветки задачи — способ их чтения этой задачей не меняется.
3. Sha256-fingerprint каждого компонента брифа в журнале шага
   (существующая механика) продолжает писаться и отражает содержимое,
   фактически прочитанное: main-версию для скилов/`CLAUDE.md`,
   веточную версию для артефактов задачи.
4. Роль, уже работающая в срезах через WIP-чекпоинты, при следующем
   шаге получает свежие правила — это ожидаемое поведение, не дефект;
   расхождение содержимого скила или `CLAUDE.md` между двумя срезами
   одной задачи не порождает инцидент целостности (проверка
   `fixation.check_integrity`) — правила не являются планкой задачи.
5. Тесты подтверждают: скил, изменённый в `main` после отведения
   ветки задачи, попадает в бриф/промпт роли в main-версии; артефакт
   задачи, отличающийся только в её ветке, попадает в бриф в
   веточной версии; fingerprint в журнале соответствует фактически
   прочитанному; существующий набор тестов остаётся зелёным.

## Критерии приёмки

AC-1. Скилы роли (файлы `skills/*.md` из состава роли, `roles.yaml`),
включаемые в промпт запуска, читаются ветко-корректным чтением через
git с ветки `main` пульта, а не с диска рабочей копии ветки задачи.

AC-2. `CLAUDE.md`, включаемый в бриф роли, читается ветко-корректным
чтением через git с ветки `main` пульта, а не с диска рабочей копии
ветки задачи.

AC-3. Артефакты задачи (`SPEC.md`, `PLAN.md`, `TZ.md`,
`QUESTIONS.md`, `ANSWER-n.md` и прочие файлы `tasks/<id>/`) читаются
с ветки задачи — поведение чтения артефактов задачи этой задачей не
меняется.

AC-4. Журнал шага несёт sha256-fingerprint каждого компонента брифа
(скилы, `CLAUDE.md`) той же механикой, что и до этой задачи, и
значение fingerprint соответствует фактически прочитанному
содержимому (main-версии).

AC-5. Смена содержимого скила или `CLAUDE.md` в `main` между двумя
шагами (срезами) одной и той же задачи, уже прошедшими через
WIP-чекпоинты, не порождает инцидент целостности на следующем шаге
этой задачи.

AC-6. Тест подтверждает: скил, изменённый в `main` после отведения
ветки задачи, попадает в бриф/промпт роли в версии `main`, а не в
версии, что была на момент отведения ветки.

AC-7. Тест подтверждает: артефакт задачи (например, `SPEC.md`),
отличающийся только в ветке задачи от `main`, попадает в бриф в
веточной версии.

AC-8. Тест подтверждает: sha256-fingerprint, записанный в журнал для
компонента-скила или `CLAUDE.md`, равен sha256 фактически прочитанной
main-версии этого компонента.

AC-9. Существующий набор тестов остаётся зелёным.

## Не входит
- Изменение состава скилов и брифов (какие компоненты входят в бриф
  какой роли) — меняется только источник чтения уже существующих
  компонентов-правил, не их состав.
- Чтение КОДА из `main` — роль по-прежнему работает с кодом своей
  ветки, это её предмет; из `main` читаются только компоненты-правила
  (скилы, `CLAUDE.md`).
- Самостоятельное разрешение конфликта с параллельной стройкой A7,
  если на момент реализации она ещё не смержена и её изменения
  пересекаются с `orchestrator/brief.py`: это эскалация Оператору, не
  часть объёма этой задачи.
