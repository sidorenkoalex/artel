# ANSWER-1: ответ Оператора

## Ответы

Эскалация «конфликт подтяжки main в ветку» — вариант A: конфликт
разрешает developer.

1. Подтянуть `main` в ветку задачи (`git merge main`), разрешить оба
   конфликта:
   - `docs/codebase-map.md` — `built_at_sha` взять из main; списки
     импортов объединить (карта не должна терять ни строк main, ни
     строк этой задачи).
   - `tests/test_review_package.py` — ожидаемый список git-вызовов
     шага developer объединить по смыслу: main после A7 читает SPEC.md
     с артефактной ветки (`show artifact/<id>:tasks/<id>/SPEC.md`) и
     листает `tasks/<id>/` артефактной ветки в поиске ANSWER-n.md
     (`ls-tree`), без автокоммита `add -A`; эта задача добавляет
     чтение трёх скилов и CLAUDE.md с головы `main` (`show
     main:skills/...`, `show main:CLAUDE.md`). Итоговый порядок —
     фактический порядок вызовов смерженного `orchestrator/brief.py`
     и `runner.py`, не догадка: сверить прогоном теста. Вызов
     `rev-parse --abbrev-ref HEAD` (ветко-корректное чтение SPEC.md
     с рабочей копии) в main больше не нужен — SPEC.md читается
     с артефактной ветки; если после мержа он остаётся в коде, это
     дефект мержа, не ожидание теста.
2. Прогнать полный набор `tests/` и планку задачи до итоговой строки,
   зафиксировать результат в PLAN (раздел «Влияние на систему»).
3. Ничего сверх мержа и разрешения конфликтов не менять.
