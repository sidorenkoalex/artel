# SPEC: CAS-переходы состояния задачи в БД

## Контекст

Роадмап §4 п.2а: первый шаг контура параллельности до фазы B. Lease
(T044) и worktree (T045) уже разводят сессии, но саму строку задачи
в БД ничто не защищает — все мутации состояния идут безусловным
`UPDATE tasks ... WHERE id=?`. Две сессии (или сессия + осиротевший
`auto`, или запоздавший процесс с уже протухшим lease), прочитавшие
одно состояние, могут обе выполнить переход — двойная запись в
journal/steps, двойная хэш-фиксация. Прецедент класса — топтание
T046. Lease — кооперативный механизм (снимается, протухает по TTL),
последний рубеж целостности FSM должен жить в самой мутации.

## Требования

1. `orchestrator/store.set_state` принимает обязательный параметр
   `expected_state`.
2. Мутация состояния — атомарный
   `UPDATE tasks SET state=?, updated_at=? WHERE id=? AND state=?`.
3. При `rowcount == 0` (проигрыш CAS): не выполняется запись в
   journal/steps, не выполняется хэш-фиксация; вызывателю
   возвращается/бросается понятный отказ с фактическим состоянием,
   прочитанным из БД.
4. Проигравший переход не повторяется молча — за единственным
   исключением kill (требование 6).
5. Все вызыватели `set_state` в `orchestrator/fsm.py` (advance,
   approve, эскалации, возвраты, merge) передают состояние, которое
   сами прочитали и на основании которого приняли решение о переходе;
   повторное чтение состояния непосредственно перед вызовом
   `set_state` ради успеха CAS не допускается.
6. `kill` при проигрыше CAS не завершается с ошибкой: перечитывает
   состояние и повторяет попытку с новым `expected_state`; если
   задача уже терминальна (`done`/`killed`) — сообщает и завершается
   без ошибки.
7. `kill` обязан перевести задачу в `killed` из любого нетерминального
   состояния (инвариант №14 «kill срабатывает всегда»).
8. Инвариант №15 («kill не трогает main») остаётся истинным.
9. Схема БД не меняется, миграции не добавляются.
10. `charge` (аддитивный `spent_usd = spent_usd + ?`),
    `next_task_number` (уже транзакционен, ADR-0003 3ж), leases
    (T044) и правки нетранзитных полей (`title`, `budget_usd`) через
    `update_task` CAS не получают и остаются как есть.

## Критерии приёмки

AC-1. Конкурентный сценарий: два соединения читают одно и то же
состояние задачи, оба вызывают `set_state` — ровно один вызов
побеждает (успешно меняет состояние в БД).

AC-2. У проигравшего вызова `set_state` нет следов ни в `steps`, ни
в фиксациях (hash-фиксациях артефактов).

AC-3. Отказ проигравшего вызова содержит фактическое состояние
задачи, прочитанное из БД («ожидалось X, в БД Y»).

AC-4. `set_state` требует обязательный параметр `expected_state` и
выполняет атомарный `UPDATE tasks SET state=?, updated_at=? WHERE
id=? AND state=?`.

AC-5. Все вызыватели `set_state` в `orchestrator/fsm.py` (advance,
approve, эскалации, возвраты, merge) передают ранее прочитанное
состояние, не перечитывая его непосредственно перед вызовом
`set_state`.

AC-6. `kill` при проигрыше CAS перечитывает состояние и повторяет
попытку с новым `expected_state`, не завершаясь с ошибкой.

AC-7. `kill`, вызванный для задачи, уже находящейся в `done` или
`killed`, сообщает об этом и завершается без ошибки.

AC-8. `kill` переводит задачу в `killed` из любого нетерминального
состояния даже при параллельном переходе состояния между чтением
и вызовом `kill` (инвариант №14 сохраняется).

AC-9. Все существующие тесты проходят без ослабления существующих
тестов, гейтов, лимитов, guard-проверок и инвариантов (ADR-0002).

AC-10. Схема БД не изменена, миграции не добавлены.

## Не входит

- Изменение схемы БД / добавление миграций.
- CAS для `charge` (`spent_usd = spent_usd + ?`) — операция остаётся
  аддитивной и безусловной, гонка для неё безвредна.
- Изменения `next_task_number` — уже транзакционен (ADR-0003 3ж).
- Механика leases (T044) — отдельный шаг цепочки параллельности
  («сверка свежести»), в этой задаче не трогается.
- CAS для правок нетранзитных полей (`title`, `budget_usd`) через
  `update_task` — остаются безусловными, как были.
- Файлы вне `orchestrator/store.py`, вызывателей `set_state`
  (`orchestrator/fsm.py` и др.) и тестов.
