# PLAN: CAS-переходы состояния задачи в БД

## Подход

`store.set_state` перестаёт быть безусловным `UPDATE tasks SET state=?,
updated_at=? WHERE id=?` и становится атомарным CAS: `UPDATE tasks SET
state=?, updated_at=? WHERE id=? AND state=?`. Обязательный
keyword-only параметр `expected_state` — состояние, на основании
которого вызыватель принял решение о переходе. Проигрыш CAS
(`rowcount == 0`) не пишет ни в `journal`, ни хэш-фиксацию (они стоят
ПОСЛЕ проверки rowcount) и бросает исключение `store.CasConflict`
с `expected`/`actual` (`actual` читается тут же одним `get_task`) —
готовое сообщение вида «ожидалось X, в БД Y» удовлетворяет AC-3 без
дополнительной обвязки у вызывателя.

Выбор формы отказа — исключение, не return-код. Причины: (а) SPEC
требование 3 сознательно оставляет форму открытой («возвращается/
бросается»); (б) большинство вызовов `set_state` в `fsm.py` — последняя
операция в своей ветке (после неё сразу `return`), так что исключение
не меняет поток управления там, где вызывающий и так ничего не делает
после; (в) непойманное исключение долетает до `artel.py main()` без
глобального перехватчика — то есть проигрыш CAS для advance/approve/
reject/merge объявляет о себе явно (трейсбек с читаемым сообщением),
а не тихо проглатывается. `store.py` не делает `sys.exit`, оставаясь
листом графа импортов без завязки на процесс — `sys.exit` там сделал бы
CAS-проигрыш неперехватываемым ДАЖЕ для `kill`, для которого требование
6 прямо предписывает перехват и повтор.

Все вызыватели `set_state` в `fsm.py` (advance/approve/reject/merge) и
смежные (`budget.enforce_budget`, `budget._cmd_budget`,
`runner._cmd_run`) передают `expected_state` = значение, уже прочитанное
их функцией на входе (`state`/`t["state"]`/параметр `state` у
`enforce_budget`), без повторного `store.get_task` непосредственно
перед вызовом — тот же самый `state`, по которому уже принято решение
о ветке перехода. Требование 5 SPEC касается буквально `fsm.py`, но тот
же приём применён и к `budget.py`/`runner.py`: это не расширение объёма
задачи (правка тех же вызовов `set_state`, обязательных к правке самим
изменением сигнатуры), а последовательное применение того же принципа
там, где он и так напрашивается по месту чтения.

`cleanup._cmd_kill` — единственное исключение (требование 6): перед
первой попыткой проверяет терминальность состояния (`done`/`killed`) —
если да, сообщает и ничего не мутирует (AC-7), не трогая уборку
терминальности иначе. Иначе входит в цикл `try: set_state(...,
expected_state=state) / except CasConflict: state = exc.actual`,
повторяя с состоянием, которое сама же `CasConflict` только что
прочитала из БД (без лишнего `get_task`) — до победы CAS либо до
обнаружения, что подсмотренное состояние само стало терминальным
(тот же ранний выход). Уборка хвостов (`cleanup_killed_task`) остаётся
безусловной ПОСЛЕ цикла — так же, как раньше вызывалась безусловно
(существующий нелоченный тест
`tests/test_kill_cleanup.KillCleanupTest.test_repeated_kill_finds_
nothing_and_does_not_fail` требует, чтобы повторный `kill` на уже
`killed` задаче всё равно печатал notes об уборке).

`charge`, `next_task_number`, leases и `update_task` (title/budget_usd)
CAS не получают — SPEC требование 10, «Не входит».

## Шаги

1. `orchestrator/store.py`: `CasConflict`, новая сигнатура и тело
   `set_state` (CAS-UPDATE, `rowcount` → journal/фиксация либо
   исключение).
2. `orchestrator/fsm.py`: все вызовы `store.set_state`
   (`_cmd_advance`, `_cmd_approve`, `_cmd_reject`) — `expected_state`
   из состояния, прочитанного на входе своей функции.
3. `orchestrator/budget.py`, `orchestrator/runner.py`: их вызовы
   `store.set_state` — тем же приёмом (`enforce_budget`'s параметр
   `state`, `t["state"]` у остальных).
4. `orchestrator/cleanup.py`: `_cmd_kill` — терминальная проверка +
   retry-цикл вокруг `set_state`.
5. Существующие прямые вызовы `store.set_state` в `tests/
   test_git_fixation.py` — добавить `expected_state` (значение — ранее
   заведённое состояние задачи в каждой фикстуре).
6. Юнит-тесты `tests/test_cas_set_state.py`: CAS-выигрыш/проигрыш,
   `CasConflict.actual`, обязательность `expected_state`, отсутствие
   journal/фиксации у проигравшего (юнит-уровень поверх приёмочных,
   которые уже покрывают AC-1..AC-8 сквозным сценарием).
7. Прогон `scripts/guard.py` на PLAN.md, полного `tests/` набора,
   `tasks/T050/acceptance_tests/`.

## Влияние на систему

Единственная точка мутации `tasks.state` — `store.set_state` — уже
была такой (докстринг `record_fixation`), CAS не добавляет второй путь.
Все вызыватели за пределами `fsm.py`/`budget.py`/`runner.py`/
`cleanup.py` проверены `grep`: их нет. Изменение сигнатуры —
breaking по конструкции (`expected_state` обязателен, keyword-only) —
это осознанно: молчаливый дефолт (например, `expected_state=None` →
«не проверять») свёл бы CAS на нет для любого пропущенного вызова,
включая будущие. Существующие тесты, зовущие `store.set_state`
напрямую (`tests/test_git_fixation.py`, 5 мест), — не приёмочные и не
залоченные, правятся тем же коммитом. Инвариант №14 (kill срабатывает
всегда) и №15 (kill не трогает main) не ослабляются: №14 явно
регрессирует приёмочным AC-8 под гонкой, №15 механику `cleanup_killed_
task` не трогает вовсе. Откат — `git revert` коммита(ов) этой задачи:
изменение локализовано в четырёх модулях orchestrator + тестах, без
миграций схемы.

## Риски

- Раскрытие `CasConflict` как публичного имени `store.py` — новая
  точка контракта для будущих вызывателей `set_state`; при появлении
  второго ретраящего вызывателя (не `kill`) стоит вынести retry-цикл
  в общую утилиту, но для одного вызывателя это была бы преждевременная
  абстракция (`coding-standards`).
- `set_state` теперь не делает `sys.exit`, а бросает исключение:
  непойманное долетает до `artel.py main()` трейсбеком. Это сознательный
  выбор (см. «Подход»), но стоит на заметке как расхождение со стилем
  соседних `sys.exit(...)`-отказов в `fsm.py` — при появлении
  недовольства Оператора формой вывода это первый кандидат на правку
  отдельной задачей, не расширение этой.
