# ТЗ: CAS-переходы состояния задачи в БД

## Контекст

Роадмап §4 п.2а (приоритет Оператора 27.08): контур параллельности до
фазы B. Первый шаг цепочки — CAS мутаций БД. Ядро уже есть: lease
(T044) не пускает две сессии в одну задачу, worktree (T045) разводит
рабочие копии. Но сама БД переходы не защищает: все мутации строки
задачи — безусловные `UPDATE tasks ... WHERE id=?`. Lease — механизм
кооперативный (его можно снять, он протухает по TTL); последний рубеж
целостности FSM должен жить в самой мутации.

## Проблема

Две сессии (или сессия + осиротевший auto, или сессия + запоздавший
процесс с уже снятым lease) читают одно состояние задачи, обе решают
двигать FSM — обе побеждают: двойной переход, двойной журнал в steps,
двойная хэш-фиксация. Реальный прецедент класса: топтание T046, где
запоздавшие процессы дописывали переходы поверх уже ушедшего состояния.

## Решение (принято Оператором 27.08, §4 п.2а)

Переходы состояния задачи становятся compare-and-swap.

1. `store.set_state` получает обязательный параметр ожидаемого
   состояния (`expected_state`). Мутация — атомарная:
   `UPDATE tasks SET state=?, updated_at=? WHERE id=? AND state=?`.
   `rowcount == 0` — проигрыш гонки: НИКАКОЙ записи в journal/steps,
   НИКАКОЙ фиксации, вызывателю возвращается/бросается понятный отказ
   с фактическим состоянием из БД («ожидалось X, в БД Y — перечитай
   статус»). Проигравший НЕ повторяет переход молча.
2. Все вызыватели `set_state` (fsm: advance, approve, эскалации,
   возвраты, merge; ~32 точки) передают то состояние, которое сами
   прочитали и на основании которого принимали решение. Запрещено
   читать состояние повторно «прямо перед вызовом» ради успеха CAS —
   это уничтожает смысл проверки: expected — это состояние, на котором
   строилось решение.
3. Особый случай — kill (инвариант №14 «kill срабатывает всегда»):
   kill при проигрыше CAS не падает, а перечитывает состояние и
   повторяет попытку с новым expected; если задача уже терминальна
   (done/killed) — сообщает и завершается без ошибки. Kill обязан
   завершиться переводом в killed из любого нетерминального состояния.
4. Вне зоны задачи: `charge` (аддитивный `spent_usd=spent_usd+?` —
   коммутативен, гонка безвредна), `next_task_number` (уже
   транзакционен, ADR-0003 3ж), leases (своя механика T044, отдельный
   шаг цепочки — «сверка свежести»), правки нетранзитных полей
   (title, budget_usd) через `update_task` — как были.

## Границы

- Только orchestrator/store.py + вызыватели set_state + тесты.
  Схема БД не меняется, миграций нет.
- Не ослаблять существующие тесты и инварианты (ADR-0002).
- Инвариант №14/№15 (kill всегда срабатывает, kill не трогает main)
  должны остаться истинными — п.3 выше это прямо адресует.

## Приёмка (минимум)

- Конкурентный сценарий: два соединения читают одно состояние, оба
  зовут set_state — ровно один успех; у проигравшего нет следов ни
  в steps, ни в fixations, а его отказ содержит фактическое состояние.
- kill побеждает гонку: параллельный переход между чтением и kill
  не мешает задаче стать killed.
- Все существующие тесты зелёные без ослаблений.
