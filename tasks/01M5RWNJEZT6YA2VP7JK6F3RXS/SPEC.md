# SPEC: Скорость пульта, git 2 — одна отправка ссылки документов на команду пульта

## Контекст
Каждый коммит документов задачи (`artifact_branch._write` → `update-ref` →
`_send`) сейчас сразу отправляет `refs/artifacts/<id>` в `origin` — около 11
вызовов git и своя отправка на коммит; строки паспорта из `store.set_state`
дают по коммиту и отправке на каждый переход. В тесте
`merge_outcome_gate::Ac5ProofMismatchTest` 33 коммита документов, из них 15 —
строки паспорта. Оператор решением 25.10.2026 поправил ADR-0021 п.3: внутри
команды пульта, меняющей задачу (тело `lease.run_locked`), ссылка
отправляется один раз при выходе из команды и раньше — в точках досрочной
досылки; вне команды — сразу после коммита, как сейчас. Шаг цикла `auto`
(`fsm.cmd_advance`, `runner.cmd_run`) считается отдельной командой.
Ожидание исследования — около 12 отправок меньше на названном тесте, около 3
отправок меньше на один `approve` в работе.

## Требования

1. **Область отложенной отправки** («область») — время исполнения тела
   одной команды пульта под `lease.run_locked`.
   - а) В `orchestrator/artifact_branch.py` есть менеджер контекста области
     (имя — на выбор разработчика) и открытая функция досылки
     `send_pending(task_id=None, repo=None)`: досылка одной задачи, всех
     задач одного репозитория или всех.
   - б) Внутри области `_write` после удачного `update-ref` не зовёт
     `_send`, а запоминает пару (задача, репозиторий записи) в наборе
     недосланных; набор — в памяти процесса, порядок — порядок первой
     записи, повтор пары не добавляется.
   - в) Вне области (ни одной открытой) — прежнее поведение байт в байт:
     `_send` сразу после `update-ref`.
   - г) Области вкладываются (вложенный `run_locked` в том же процессе:
     шаги `auto`, `cmd_run_and_advance`); досылка всего набора — при выходе
     из области на любом уровне вложенности, в том числе из вложенной.
     Шаг цикла `auto` досылает свои коммиты в конце шага, не в конце цикла.
   - д) `lease.run_locked` открывает область вокруг `body(sid)` внутри
     `try`; досылка идёт до `release` в `finally` (пока lease держится).
     При отказе `acquire` (тело не исполнялось) область не открывается.
2. **Досылка** — вызов прежнего `_send(task_id, repo)` по одному разу на
   каждую пару набора, в порядке набора.
   - Пара удаляется из набора до вызова `_send` — повторной досылки той же
     пары нет.
   - Правила журнала (`_journal_push_outcome`, `_last_send_failed`)
     действуют на каждую досылку так же, как сейчас на каждый коммит: отказ
     — одна запись на досылку; успех — запись только после повтора или
     после записанного раньше отказа.
   - Без `origin` — ни отправки, ни записи, ни исключения.
   - Пустой набор — ни одного вызова git и ни одного обращения к БД.
3. **Досрочная досылка до выхода из области:**
   - а) `origin_sync_refusal(task_id)` первым действием досылает эту задачу
     (`send_pending(task_id)`), затем прежняя логика; тексты отказов и
     `None` прежние; отправок за вызов не больше прежнего.
   - б) `fetch_from_origin(task_id)` досылает эту задачу,
     `fetch_all_from_origin(repo)` — все задачи этого репозитория; обе — до
     `git fetch`, чтобы своя недосланная голова не дала `FETCH_DIVERGED`.
   - в) Перед отправкой кодовой ветки задачи досылается эта задача — только
     когда отправка кодовой ветки действительно идёт: в
     `github_adapter.ensure_draft_mr` перед отправкой ветки (`:160`), в
     `github_adapter.ensure_head_in_origin` перед отправкой (`:234`, после
     сверки «голова уже в origin» — при совпадении досылки нет), в
     `fsm_merge_gate._sync_main_or_wait` перед отправкой (`:739`).
   - г) В `runner._spawn_and_wait` перед вызовом `spawn_agent` (`:1674`)
     досылается весь набор.
   - д) В `snapshot.commit_closing` после записанного коммита закрытия
     (`:138`, sha не пуст) досылается эта задача — вместе со строкой
     паспорта `done`/`killed`; коммит закрытия в `origin` до уборки,
     ожидания CI `main` и пересборки справочника.
   - е) Перед долгими этапами гейта мержа досылается весь набор: первым
     действием `fsm_merge_gate._wait_for_branch_ci_green` (`:332`),
     `_ci_ready_or_wait` (`:756`) и `_await_main_ci` (`:642`), а в
     `_full_suite_or_refuse` (`:1053`) — после проверки «прогон нужен» и до
     запуска прогона.
4. **Исключения.**
   - Тело области завершилось исключением (в том числе `SystemExit` отказа
     и `KeyboardInterrupt`) — досылка всё равно делается, затем наружу
     выходит то же исключение тела.
   - Исключение самой досылки при летящем исключении тела его не заменяет:
     печатается одной строкой в stderr, досылка остальных пар продолжается.
   - При нормальном выходе тела исключение досылки поднимается после
     попытки дослать остальные пары.
5. **Неизменные части.**
   - `push(task_id)`, `_attempt_push`, `_classify_push_failure`,
     `_journal_push_outcome`, `_origin_configured`, тексты журнала,
     `write_commit`, `commit_files`/`commit_change` (имена, сигнатуры,
     возвращаемые значения) не меняются.
   - Прямые отправки `snapshot.py:294` и
     `orchestrator/doctor/artifact_branches.py:137` не меняются.
   - Строка документации модуля `artifact_branch.py` и `_send` приведены в
     соответствие: отправка — при выходе из команды пульта и в точках
     досрочной досылки, вне команды — сразу.
6. **Тесты.** Новый файл `tests/test_01m5rwnjezt6ya2vp7jk6f3rxs_one_push_per_command.py`
   в стиле pytest (ADR-0027); в документации каждой функции — «Ловит
   мутацию:». Песочница — настоящий git с локальным bare-origin
   (`tests/sandbox.py`, `tests/fixtures.py`); счёт отправок — подменой
   `gitcmd.subprocess.run`, записывающей argv `git push … refs/artifacts/<id>`.
   Сценарии — критерии AC-1…AC-12 ниже.
7. **Число вызовов.** В PLAN — счёт вызовов git всего и по подкомандам
   `push`, `remote` на тесте
   `tests/test_01m5ddtvzea40zb9bheh4ydee7_merge_outcome_gate.py::Ac5ProofMismatchTest`
   (или его наследнике после сведения) до и после; счёт снимается шпионом
   процессов во временной копии, файл тестов не меняется. Если сокращение
   отправок меньше 6 — в PLAN разбор по точкам досылки требования 3, где
   тратятся отправки.
8. **Существующие тесты** не правятся, кроме одной правки по мандату
   Оператора (ТЗ, «Решения Оператора» п.4):
   `tests/test_review_package.py::CmdRunReviewPackageTest::test_developer_step_has_no_package`
   — в ожидаемом списке вызовов git два элемента
   `["-C", clone, "remote", "get-url", "origin"]` и
   `["-C", clone, "push", "-q", "origin", f"{ref}:{ref}"]` переносятся из
   места сразу после `["-C", clone, "update-ref", ref, "f" * 40, "0" * 40]`
   в самый конец списка, после последнего
   `["-C", clone, "rev-parse", "--verify", "--quiet", ref]`; в комментарии
   перед списком фраза о порядке («запись ссылки и её отправка в `origin`,
   затем чтение головы…») поправлена: отправка — при выходе из команды;
   остальное в тесте не трогается. Покраснел любой другой существующий
   тест — эскалация с его именем и причиной, не правка.

## Критерии приёмки

AC-1. Внутри одного `lease.run_locked` тело делает три `store.set_state` и
один `commit_files`: в конце тела отправок `refs/artifacts/<id>` 0, после
возврата — ровно одна, голова ссылки в `origin` равна локальной. Тот же
сценарий вне `run_locked` даёт 4 отправки.

AC-2. Внешний `run_locked` и два вложенных подряд, в каждом коммит: после
выхода из первого вложенного отправка уже сделана и `origin` равен локальной
голове до входа во второй; всего две отправки, у выхода внешнего — ни одной
лишней.

AC-3. Тело коммитит и бросает `RuntimeError` (и отдельно —
`SystemExit("отказ")`): отправка сделана, наружу выходит тот же объект
исключения, lease снят. Досылка, бросившая исключение при летящем исключении
тела, его не подменяет (исключение тела выходит наружу, досылка остальных
пар продолжается).

AC-4. Внутри области коммит, затем `origin_sync_refusal` даёт `None`, и
отправка одна за всю область. Внутри области коммит, затем
`fetch_from_origin` даёт `FETCH_SAME`, а не `FETCH_DIVERGED`.

AC-5. Внутри области коммит документов, затем `ensure_head_in_origin` для
ветки, которой нет в `origin`: отправка `refs/artifacts/<id>` в записанных
argv стоит раньше `push -u origin <ветка>`. Если голова кодовой ветки уже в
`origin`, досылки в этом вызове нет.

AC-6. Внутри области `set_state` и `snapshot.commit_closing`: отправка одна и
сделана до возврата из `commit_closing`; RETRO есть в `origin` сразу после
неё.

AC-7. В момент вызова `runner.spawn_agent` из `runner.cmd_run` набор
недосланных пуст, хотя до запуска был сделан недосланный коммит документов
(песочница по образцу `CmdRunReviewPackageTest` в
`tests/test_review_package.py`; коммит до запуска — подменой шага
подготовки, которая зовёт `commit_files`).

AC-8. `origin` отвергает запись (хук `pre-receive`), внутри области три
коммита — ровно одна запись журнала «push артефактной ветки FAILED» с
прежним текстом. В следующей области с исправленным `origin` — одна запись
об успехе после отказа. Ответ сервера 5xx на первой попытке — повтор и
запись «попыток 2», как у `_send`.

AC-9. Без `origin` (remote удалён): коммиты внутри области — ни одной
отправки, ни одной записи журнала, без исключения. Пустой набор при выходе
из области — ни одного вызова git, в том числе без `remote get-url`.

AC-10. Две задачи в одной области (в том числе запись с `target=` до строки
задачи в БД): по одной отправке на каждую, в порядке первой записи, каждая —
в `origin` своего репозитория.

AC-11. Внутри области коммит документов, затем
`fsm_merge_gate._wait_for_branch_ci_green`, `_ci_ready_or_wait`,
`_await_main_ci` (опрос CI подменён) и `_full_suite_or_refuse` с нужным
прогоном (прогон подменён): в момент первого опроса CI и в момент запуска
прогона ссылка в `origin` равна локальной. При ненужном прогоне
`_full_suite_or_refuse` не досылает.

AC-12. Досылка подменена так, что ничего не делает (процесс «умер» до
отправки), — `origin` отстаёт; затем `store.set_state` вне области
отправляет ссылку целиком (голова в `origin` равна локальной), а
`origin_sync_refusal` досылает и даёт `None`. У закрытой задачи
`doctor --fix` (`_fix_unsent_closed_refs`) досылает коммит закрытия.

AC-13. Вне области (нет ни одной открытой) `_write` зовёт `_send` сразу
после `update-ref`: последовательность вызовов git коммита документов вне
команды совпадает с прежней.

AC-14. PLAN.md содержит счёт вызовов git всего и по подкомандам `push`,
`remote` на `Ac5ProofMismatchTest` (или его наследнике) до и после; при
сокращении отправок меньше 6 — разбор по точкам досылки требования 3.

AC-15. Тест `tests/test_review_package.py::CmdRunReviewPackageTest::test_developer_step_has_no_package`
изменён ровно по перечню требования 8 (перенос двух элементов в конец
списка и правка фразы комментария) и зелёный; прочие его утверждения не
тронуты.

## Оценка объёма и деление
Сработавшие сигналы: зон 8 (≥ 5 файлов/модулей), критериев приёмки 15
(≥ 10), `budget_usd` 60 (≥ $30).

**Обоснование монолита (материал для решения Оператора).** Неразрезаемо
включение области в `lease.run_locked` (требование 1д) вместе с досрочными
досылками (требование 3): механизм области без подключения к `run_locked`
ничего не меняет (мержить его отдельно бессмысленно), а подключение без
досрочных досылок оставляет систему в нерабочем промежуточном состоянии —
CI ветки `task/**` читает PLAN.md из `origin` (`scripts/plan_appendix_ci.py`)
и после отправки кодовой ветки получал бы старый PLAN; `fetch_from_origin`
внутри команды давал бы `FETCH_DIVERGED` на своей недосланной голове;
`origin_sync_refusal` на гейте мержа и в `kill`, коммит закрытия до
ожидания CI `main` и документы на время шага роли отставали бы в `origin`.
Тесты (требование 6) проверяют именно связку обеих частей. Дифф кода мал
(досылка — одна строка в каждой точке), основной объём — новый файл тестов.
