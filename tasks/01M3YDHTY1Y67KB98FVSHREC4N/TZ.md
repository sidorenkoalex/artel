# ТЗ: Черновик запроса на слияние сверяет ветку с удалённой базой; массовое подтверждение инцидентов одного вида

Источник: сверка шага Ш1 плана работ (`docs/roadmap.md`, §4) 02.10.2026 —
пункт «закрытие накопленных инцидентов о черновике запроса на слияние» не
исполнен; строка копилки 02.10 «Защита черновика запроса на слияние от
пустой ветки… считает коммиты над локальным main» (`docs/backlog.md`);
PLAN задачи 01M3HP7WAXKFK3GYZ3T6HX08M0, раздел «Предложения системе»
(команда массового закрытия алертов); решение Оператора 02.10.

Факты (пин 28b09389, `origin/main` 99b954f5; числа — `state.db` 02.10):
- Задача 01M3HP7WAX (слита 27.09) поставила в
  `orchestrator/github_adapter.py::ensure_draft_mr` проверку пустой
  ветки до обращения к GitHub. Проверка `_commits_over_base(branch,
  base)` считает коммиты ветки, которых нет в ЛОКАЛЬНОЙ ветке `base`
  (`gitcmd.commits_behind`, `rev-list --count <base>..<branch>`).
  Локальная `main` главной копии — это пин, и он по построению отстаёт от
  `origin/main`, от которой растут ветки задач. Ветка без своих коммитов
  при отставшем пине «имеет коммиты» над локальной `main`, проверка её
  пропускает, `git push` и `gh pr create` уходят в GitHub, тот отвечает
  «No commits between main and task/…» — запись журнала
  `Draft MR FAILED` и инцидент `github_adapter`.
- После сдвига пина на код с проверкой (28.09 07:06Z) — 15 таких
  инцидентов (28.09–02.10), записей `Draft MR FAILED` — 18, штатных
  пропусков «в ветке нет коммитов» — 2. Свежий случай: 01M3XVW94Z 02.10
  08:41Z — код ветки 4abfce0c совпадал с вершиной `origin/main`, пин
  7f55c29a; черновик создан следующим переходом в 08:45Z.
- Открытых инцидентов `github_adapter` с текстом «No commits between» —
  148 (05.09–02.10); всего открытых `github_adapter` — 158.
- В пульте уже есть точка правды для базы сравнения ветки:
  `gitcmd.diff_base` / `gitcmd.diff_base_source` берут
  `refs/remotes/origin/<MAIN_BRANCH>`, если ref заведён, иначе локальную
  `main` (задача 01M1SG9T96, гейты зон и ёмкости). Проверка черновика
  ею не пользуется.
- `alert-ack <id> "<решение>"` (`orchestrator/doctor/cli.py::
  cmd_alert_ack`, `orchestrator/alerts.py::ack`, разбор аргументов —
  `orchestrator/artel.py`) подтверждает ровно один алерт. Закрыть 148
  записей можно только циклом в оболочке — обход вместо команды пульта.
- Подтверждение алерта снимает блокировки (стоп-кран волны, инциденты,
  останавливающие цикл; `config.py:821`, `runner.py:309`), а `trigger`
  без текста решения отказывается (`alerts.ack`).

Требуется:
1. Проверка пустой ветки перед созданием черновика сравнивает ветку с
   УДАЛЁННОЙ базой target'а, а не с локальной `main`: для self-target —
   `origin/<base>`, для внешнего target — та же база в его клоне
   (`repo_context`). Источник базы и способ его актуальности (готовый
   `refs/remotes/origin/<base>`, как в `gitcmd.diff_base`, либо свежий
   fetch через `gitcmd.fetch_ref_sha`) выбрать и обосновать в SPEC;
   устаревший ref удалённой базы не должен давать ложного «коммиты
   есть». Своего второго способа определять базу ветки не заводить —
   переиспользовать или обобщить существующий в `gitcmd`.
2. Деградация прежняя: git не ответил или база не читается — поведение
   до проверки (попытка создания и инцидент при отказе), без додумывания
   «ноль коммитов». Пропуск — запись журнала обычного уровня без
   инцидента, с названием базы, с которой сверялись.
3. Команда массового подтверждения: `alert-ack --source <источник>
   --grep <подстрока> "<решение>"`. Обязательны и источник, и подстрока,
   и текст решения. Подтверждает только открытые алерты вида `incident`
   с этим источником и подстрокой в тексте; алерты `trigger` и
   `threshold` массовым путём не подтверждаются (отказ с названием
   числа пропущенных). Без флага подтверждения (`--yes` или иное — в
   SPEC) команда только печатает перечень: число, номера, диапазон дат,
   первые строки текста — и ничего не меняет. Каждый подтверждённый
   алерт получает тот же `ack_by=operator` и текст решения, что дал бы
   одиночный `alert-ack`. Одиночная форма `alert-ack <id> "<решение>"`
   не меняется.
4. Массовая форма отказывает из-под роли так же, как одиночная (признак
   шага роли, задача 01M3XTF5506G).
5. PLAN даёт Оператору готовую команду закрытия накопленных инцидентов
   «No commits between» с текстом решения и предпросмотром; исполняет её
   Оператор после мержа и сдвига пина, не задача.
6. Тесты (tests/): ветка без своих коммитов при отставшей локальной
   `main` и свежей удалённой базе — GitHub не вызывается, инцидента нет;
   ветка со своим коммитом — черновик создаётся; удалённая база не
   читается — прежнее поведение; внешний target — сверка в его клоне;
   массовое подтверждение — предпросмотр ничего не меняет, подтверждение
   снимает только `incident` нужного источника и подстроки, `trigger`
   не снимается, пустой источник/подстрока/решение — отказ, отказ из-под
   роли. Существующие tests/test_github_adapter.py,
   tests/test_draft_mr_commits.py, tests/test_fsm_draft_mr_reentry.py,
   tests/test_doctor_wave_breaker.py,
   tests/test_01m3xtf5506gf43hd51ece230t_role_refusal.py зелёные, ни
   один не ослаблен.
