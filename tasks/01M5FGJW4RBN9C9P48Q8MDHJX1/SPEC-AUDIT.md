## Пути обхода гейтов
- **Чтение без предела.** Буква SPEC.md:43 («`remote_ref_state`») позволяет исполнителю читать голову без `-c http.lowSpeed*`, и ни один AC этого не заметит. Под мьютексом мержа замолчавший хостинг тогда держит окно всех задач проекта без потолка. Это ровно то, от чего предел и введён у kill (cleanup.py:254–255). → О-1, О-2.
- **`remote_branch_sha` вместо `remote_ref_state`.** Неответивший origin выдаётся за «нет — удалять нечего». Ветка тихо остаётся в origin, а журнал врёт, что удалять было нечего. Это проходит AC-6, если тест подставляет `None` только на push. → О-3.
- **Lease без sha.** `--force-with-lease=refs/heads/<branch>` без `:<sha>` берёт ожидание из `refs/remotes/origin/<branch>` клона. Если клон не фетчил ветку, git отказывает или сверяет с устаревшим. AC-5 это ловит при условии, что тест сдвигает ветку в origin в обход клона — так он и задан: «чтение вернуло прежнюю голову».
- Других путей обхода не найдено. Уборка на раннем выходе ловится AC-7, удаление ветки артели на kill — AC-8, лишние вызовы `gh` — AC-8.

## Вердикт
**concerns.** SPEC можно вести дальше. Ниже четыре отклонения; их может решить Оператор на гейте без возврата аналитику.

- **О-1 (буква SPEC расходится с зонами).** SPEC.md:42–43 требует читать голову через `remote_ref_state`, а SPEC.md:58–60 — читать её `ls-remote` с пределом `http.lowSpeedLimit`/`http.lowSpeedTime`. Но `orchestrator/gitcmd.py:673–687` не принимает `-c`, а gitcmd.py — только чтение. Предлагаемое решение: читать голову в `cleanup.py` через `gitcmd.in_repo(repo, "-c", …, "ls-remote", "origin", "refs/heads/<branch>")` с той же семантикой трёх исходов, что у `remote_ref_state`. Альтернатива — `remote_ref_state` без предела, но тогда требование SPEC.md:58 ослабляется.
- **О-2 (требование без критерия).** Предел lowSpeed на чтении и удалении в пути мержа (SPEC.md:58–60) не закреплён ни одним AC. Мутация «нет `-c http.lowSpeedTime` у нового `ls-remote`/push» проходит все AC-1…AC-9. Предложение — к AC-1 добавить проверку аргументов обоих вызовов git, по образцу test_01m568…_project_kill_cleanup.py:581.
- **О-3 (исход без критерия).** Исход «origin не ответил на чтение» с причиной `ls-remote` и подсказка «сначала `ls-remote`» (SPEC.md:46–47, :79–80) не закреплены отдельным AC. AC-6 (SPEC.md:123) не говорит, на каком вызове `in_repo` возвращает `None`. Предложение: AC-6 — `None` отдельно на чтении (исход «оставлено — git не ответил», подсказка `ls-remote` и подсказка удаления, push не выполняется) и отдельно на push; плюс сценарий с ненулевым кодом `ls-remote` и его stderr в причине.
- **О-4 (неполнота подсказок).** SPEC п.3 (SPEC.md:73–82) не называет подсказку для двух исходов: (а) `None` от `in_repo` на push после прочитанной головы — «git не ответил» не равно «отказ» или «хостинг промолчал»; (б) исключение внутри функции. Предлагаемый дефолт: (а) — подсказка удаления, как при молчании хостинга; (б) — без подсказки. Пусть Оператор подтвердит.

Наблюдение, не отклонение: удаление head-ветки на GitHub закрывает открытый PR. Это сказано в cleanup.py:276–277. После мержа push коммита мержа в базу обычно уже помечает PR смерженным, так что поведение сходится с п.5 «пульт PR не закрывает». Но конечный статус PR после мержа теперь зависит от GitHub, и в docs/retention.md (SPEC п.6) это можно было бы упомянуть.
