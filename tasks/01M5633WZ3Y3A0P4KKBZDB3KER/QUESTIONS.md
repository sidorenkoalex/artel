# QUESTIONS: Долгоживущие тесты внешнего проекта: правило импортов по профилю

## Вопросы

Контекст. Правило «импорт вне перечня» — `scripts/guard.py:2612-2614`
(`_allowed_import_tops`), применение `:2709-2730`, вызов из
`long_lived_sign_hits` `:2785` без сведений о проекте; три рубежа
(`orchestrator/advance_gates/tests_writing.py:351, 470`,
`orchestrator/preflight.py:186, 203`, `orchestrator/amend.py:512`) уже знают
профиль проекта (`project_profile.Profile`, в нём есть `workdir`,
`orchestrator/project_profile.py:78`). Поля профиля для перечня импортов нет
(`orchestrator/targets.py:43-60`). У sled зависимости объявлены в
`backend/pyproject.toml`/`backend/uv.lock` (оба в `no_paths` sled,
`targets.yaml:74`), имена дистрибутивов часто не совпадают с именами
импорта (`pyjwt` → `jwt`, `python-jose` → `jose`, `python-dotenv` → `dotenv`,
`psycopg2-binary` → `psycopg2`). Вариант «отключить правило у внешнего
проекта» противоречит критерию ТЗ «вне перечня — отказ» и в вопрос не
вынесен. Вопрос блокирует саму постановку требования 1: от ответа зависят
зоны задачи и то, нужна ли правка `targets.yaml`.

1. **Откуда берётся перечень разрешённых верхних имён импорта долгоживущего файла внешнего проекта?**
   - A) Новое необязательное подполе профиля `test_profile.long_lived_imports` (список верхних имён, например `[src, fastapi, httpx, sqlalchemy, pydantic]`), разрешено сверх stdlib и `tests`; текст отказа называет это подполе и его значение. Зоны задачи расширяются на `orchestrator/targets.py` (`PROFILE_FIELDS`, `PROFILE_OPTIONAL`); значение для записи sled вносит Оператор в `targets.yaml` отдельно (защищённый путь, `targets.yaml:36`).
     - ломается: ничего у артели; у sled до внесения значения в `targets.yaml` поведение прежнее (отказ, см. вопрос 2).
     - ослабляется: ничего — перечень явный и проверяемый, правило по-прежнему закрыто по умолчанию (`scripts/guard.py:2721`).
     - цена: +1 файл зоны (`orchestrator/targets.py`), примерно +$3–5 к рамке $30; плюс отдельная правка `targets.yaml` Оператором.
     - чьё решение: Оператор (расширение зон и защищённый `targets.yaml`).
   - B) Перечень выводится без нового поля: верхние пакеты/модули каталога `workdir` (у sled — `src`, `tests`, …) плюс имена зависимостей из `<workdir>/pyproject.toml` (`[project].dependencies` и группы), нормализованные заменой `-` → `_`; правки только в зонах ТЗ.
     - ломается: импорт с несовпадающим именем дистрибутива (`jwt`, `jose`, `dotenv`, `psycopg2`) получает отказ, и обойти его без нового поля нельзя; имя файла `pyproject.toml` прибивается к Python-стеку пакетирования.
     - ослабляется: детерминизм рубежа — исход зависит от содержимого файла проекта на ветке задачи, а не от декларации пульта (сегодня перечень держит `scripts/guard.py:2612-2614` в коде пульта).
     - цена: зоны ТЗ без расширения; разбор TOML и нормализация — примерно та же рамка $30.
     - чьё решение: Оператор.
   - C) Как B, но имена зависимостей берутся из lock-файла `<workdir>/uv.lock` (включая транзитивные).
     - ломается: то же расхождение имён, что у B; перечень прибит к `uv`; транзитивные зависимости становятся разрешёнными без явного решения.
     - ослабляется: то же, что B, и шире перечень — транзитивные пакеты разрешены неявно.
     - цена: как B.
     - чьё решение: Оператор.
   - дефолт: A — единственный вариант без расхождения имён дистрибутива и импорта и без привязки к менеджеру пакетов; ТЗ называет его первым; зоны расширяются на `orchestrator/targets.py` (правку Оператор увидит и утвердит на гейте SPEC).

2. **(при ответе A) Что делает рубеж у внешнего проекта, в профиле которого подполя `long_lived_imports` нет?**
   - A) Прежнее правило: разрешены только stdlib, `tests` и `stack.THIRD_PARTY_EXCEPTIONS`; текст отказа у внешнего проекта дополнительно называет подполе, которое надо заполнить.
     - ломается: ничего — исход совпадает с сегодняшним, меняется только подсказка в тексте.
     - ослабляется: ничего — закрыто по умолчанию, как `scripts/guard.py:2721`.
     - цена: в рамке вопроса 1.
     - чьё решение: Оператор.
   - B) Отказ проверки профиля целиком («нет подполя long_lived_imports»), как отсутствие профиля в `project_profile.decide`.
     - ломается: у внешнего проекта без подполя падают все три рубежа, даже если долгоживущий файл импортирует только stdlib.
     - ослабляется: ничего.
     - цена: та же.
     - чьё решение: Оператор.
   - дефолт: A — без поля поведение не меняется, подсказка указывает, как его включить.

3. **Пакеты кода внешнего проекта из перечня (например `src`) — проверять ли в них признак «закрытое имя» (`from src._x import y`)?** Сейчас признак действует только на `orchestrator`/`scripts` (`_CODE_PACKAGES`, `scripts/guard.py:2605, 2727`), у внешнего проекта он молчит; ТЗ п.2 просит сверить применимость признаков.
   - A) Да: у внешнего проекта признак «закрытое имя» действует на пакеты кода проекта (при ответе A на вопрос 1 — на имена перечня, кроме зависимостей, — то есть нужен способ их различить: отдельное подполе или верхние каталоги `workdir`).
     - ломается: долгоживущий файл sled с `from src._x import y` начнёт получать отказ.
     - ослабляется: ничего — правило становится строже.
     - цена: +1–2 критерия приёмки, около +$3.
     - чьё решение: Оператор.
   - B) Нет: в этой задаче признак «закрытое имя» у внешнего проекта не меняется; признаки «закрытый атрибут» и `sys.path` уже применимы без правок (`scripts/guard.py:2692-2706`, `:2741-2743`, `:2806`), это и перечисляется в SPEC.
     - ломается: ничего.
     - ослабляется: ничего относительно сегодняшнего — у внешнего проекта признак и сейчас не действует.
     - цена: ноль.
     - чьё решение: роль (аналитик фиксирует в SPEC «не входит»).
   - дефолт: B — ТЗ требует расширить разрешённое, а не ужесточить проверку; ужесточение без явного мандата — работа сверх ТЗ.
