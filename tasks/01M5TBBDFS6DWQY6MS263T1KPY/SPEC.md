# SPEC: Эпики Э1 — эпик как сущность пульта, команды эпика и модель доски для `status` и `epic show`

## Контекст
Линии задач в пульте нет: `status` (`orchestrator/catalog.py:982`, `cmd_status`) выводит строку на задачу с группировкой только по проекту, `report` (`orchestrator/report.py:46`) — HTML-доска с колонками-состояниями; связь задач видна только по `merge_after` и по делению на гейте SPEC (`orchestrator/fsm.py:958`, `_spawn_division_subtasks`). ADR-0028 (принят 25.10.2026, уровень 1, п. 4–7 и п. 12) вводит эпик — сущность пульта, которая объединяет задачи одного проекта общей целью, — и модель доски: одну проекцию БД и журнала, из которой строятся виды. Шаг Э1 заводит эпик в БД, его команды, связь эпика с делением и модель доски `orchestrator/board.py`, из которой строятся `status` и `epic show`.

Шаг опирается на Э0 (01M5TB6VDVV6AM8DWPGVQE8CDW): признак `closed_as` задачи и единый список состояний `fsm.STATES` (с окончательными `fsm.TERMINAL_STATES`). На текущей ветке этих имён ещё нет (есть только `cleanup.TERMINAL_STATES` и `watch._TERMINAL_STATES`), они появятся в main с Э0.

## Требования

1. **Таблица `epics`.** Миграция схемы (`orchestrator/schema.py`) заводит таблицу `epics` с колонками `id`, `project`, `title`, `goal`, `envelope_usd` (необязательно; используется шагом Э2а), `state` (`open` | `closed`), `outcome`, `created_at`, `closed_at` и колонку `tasks.epic_id` (необязательно). Миграция пишет запись журнала. Каталог `epics` входит в `config.PROJECT_DIRS` (`orchestrator/config.py:61`).
2. **Идентификатор эпика** — приставка `E` и формат идентификатора пульта (`orchestrator/idgen.py`). Он не совпадает с префиксами задач: разрешение префикса задачи (поиск задачи по id и разбор `--after`) не находит эпик, а id эпика не принимается как id задачи.
3. **Проект эпика.** Эпик принадлежит одному проекту; задача эпика — того же проекта. Привязка задачи к эпику проверяет проект при каждой привязке (`new --epic`, `epic add`, деление).
4. **Команды эпика.** Все команды ниже выполняются через `lease.run_locked` и пишут запись журнала:
   - `epic new <проект> "<название>" --goal "<цель>" [--envelope N]` — заводит эпик в состоянии `open`;
   - `epic show <id>` — показывает эпик (вид — требование 11);
   - `epic edit <id> [--title …] [--goal …]` — меняет название и/или цель;
   - `epic close <id> "<итог>"` — закрывает эпик: `state='closed'`, `outcome` — итог, `closed_at` — время закрытия (условие — требование 8);
   - `epic add <id> <задача>`, `epic remove <id> <задача>` — привязывают уже заведённую задачу к эпику и отвязывают её.
5. **`new` с эпиком.** `new "<название>" --tz <файл> --target <проект> --epic <id> [--after <id>[,<id>…]]` заводит задачу в эпике; `--after` записывает `merge_after` той же проверкой, что строка ТЗ «Порядок: после …» (`orchestrator/merge_after.py`, `merge_after.check`). Несуществующий id в `--after` — отказ.
6. **Отказы привязки.** Привязка задачи (`new --epic`, `epic add`) к закрытому эпику или к эпику другого проекта — отказ с причиной; привязка не происходит.
7. **Деление и эпик.**
   - Части деления на гейте SPEC наследуют эпик родителя.
   - `approve <id> --as-epic` на гейте SPEC у задачи с делением и без эпика создаёт эпик из родителя: проект — проект задачи; название — название задачи; цель — первый абзац раздела «Контекст» SPEC родителя; конверт не задан; части деления — задачи нового эпика; у родителя `closed_as='divided'` и запись журнала со ссылкой на эпик.
   - `--as-epic` у задачи без деления или у задачи, уже состоящей в эпике, — отказ.
   - `approve` без `--as-epic` — прежнее деление.
8. **Закрытие — только Оператор.** `epic close` при задачах эпика не в окончательных состояниях (`fsm.TERMINAL_STATES`) — отказ с их перечнем; эпик остаётся `open`. Когда все задачи эпика окончательны, `status` и `epic show` показывают «эпик готов к закрытию»; сам эпик пульт не закрывает.
9. **Модель доски.** Модуль `orchestrator/board.py`: функция строит модель проекта из БД и журнала — словарь с `schema_version` — без обращения к хостингу и сети. Ключи модели:
   - `project`, `generated_at`, `pin`, `columns` (равен `fsm.STATES`);
   - `epics` — на эпик: идентификатор, название, цель, конверт, потрачено, счётчики задач по состояниям, узлы и рёбра (рёбра `merge_after` и родитель–часть);
   - `cards` — на задачу: задача, название, эпик, состояние, `closed_as`, `waiting_on` ∈ {`operator`, `ci`, `dependency`, `role`, пусто}, зависимости, потрачено/потолок, ветка, время последнего события.
   Модель доски БД не пишет. Повторное построение без изменений БД даёт ту же модель (кроме `generated_at`).
10. **`status` из модели.** `status` группирует задачи по эпикам. Заголовок группы эпика: `потрачено / конверт` (или «без конверта»), счётчики по состояниям, «части слиты N/M» у поделённых задач, «эпик готов к закрытию» (требование 8). Затем строки задач эпика в порядке зависимостей. Задачи без эпика — прежним списком; вывод `status` для проекта без эпиков не меняется. Вид строится из модели `board.py`.
11. **`epic show` из модели.** `epic show <id>` выводит таблицу со столбцами: задача, родитель, от чего зависит, состояние, кто держит (`waiting_on`), потрачено/потолок, итог; и «эпик готов к закрытию» при условии требования 8. Вид строится из модели `board.py`.

## Критерии приёмки

AC-1. `epic new <проект> "<название>" --goal "<цель>" [--envelope N]` заводит в таблице `epics` запись этого проекта в состоянии `open` с названием, целью и конвертом (без `--envelope` — конверт не задан), идентификатор начинается с `E`; запись журнала о заведении есть.
AC-2. `epic show <id>` по заведённому эпику выводит его название, цель и таблицу задач со столбцами: задача, родитель, от чего зависит, состояние, кто держит, потрачено/потолок, итог.
AC-3. `epic edit <id> --title … --goal …` меняет название и цель эпика в БД; запись журнала есть.
AC-4. `epic add <id> <задача>` записывает `tasks.epic_id` задачи того же проекта, `epic remove <id> <задача>` снимает его; у каждой операции есть запись журнала.
AC-5. Привязка задачи другого проекта к эпику (`epic add`, `new --epic`) — отказ с причиной, `tasks.epic_id` не записан.
AC-6. Привязка задачи к закрытому эпику (`epic add`, `new --epic`) — отказ с причиной, `tasks.epic_id` не записан.
AC-7. `new "<название>" --tz <файл> --target <проект> --epic E… --after <id>` заводит задачу с `epic_id` этого эпика и записанным `merge_after`, равным id из `--after`.
AC-8. `new … --after <id>` с несуществующим id — отказ, задача не заведена.
AC-9. Разрешение id задачи по префиксу (поиск задачи и разбор `--after`) не находит эпик: id эпика, переданный как id задачи, — отказ «задача не найдена».
AC-10. `approve` на гейте SPEC задачи в эпике с делением заводит части с тем же `epic_id`, что у родителя.
AC-11. `approve <id> --as-epic` у задачи без эпика с делением заводит эпик проекта задачи с названием задачи, целью — первым абзацем раздела «Контекст» её SPEC и незаданным конвертом; части деления состоят в этом эпике; у родителя `closed_as='divided'`; запись журнала родителя называет id нового эпика.
AC-12. `approve <id> --as-epic` у задачи без деления — отказ; у задачи, уже состоящей в эпике, — отказ; в обоих случаях эпик не заведён и состояние задачи не изменено.
AC-13. `epic close <id> "<итог>"` при задаче эпика не в `fsm.TERMINAL_STATES` — отказ, текст отказа называет id этой задачи; эпик остаётся `open`.
AC-14. Когда все задачи эпика в `fsm.TERMINAL_STATES`, `status` и `epic show <id>` выводят «эпик готов к закрытию», а `epics.state` эпика остаётся `open`; последующий `epic close <id> "<итог>"` переводит эпик в `closed` с записанными `outcome` и `closed_at`.
AC-15. Модель `board.py` для проекта: `columns == fsm.STATES`; у карточки задачи в состоянии `spec_gate`, `merge_gate` и `escalated` `waiting_on == 'operator'`.
AC-16. Два построения модели `board.py` подряд без изменений БД дают равные словари после удаления `generated_at`; построение модели не меняет счётчик изменений соединения БД (`total_changes` до и после равны).
AC-17. `status` для проекта с эпиком выводит группу эпика с заголовком «потрачено / конверт» (или «без конверта») и счётчиками по состояниям, у поделённой задачи — «части слиты N/M»; строки задач эпика идут в порядке зависимостей `merge_after`.
AC-18. `status` для проекта без эпиков выводит тот же текст, что до задачи (сверка с выводом текущего main на той же фикстуре).

## Оценка объёма и деление
Сработавшие сигналы: файлов зоны вне общих — 8 (`board.py`, `epics.py`, `schema.py`, `store.py`, `catalog.py`, `fsm.py`, `merge_after.py`, `artel.py`) при пороге 5; критериев приёмки — 18 при пороге 10; `budget_usd` 75 при пороге 60.

**Обоснование монолита** (материал для решения Оператора; ТЗ — уже шаг Э1 нарезки ADR-0028 на Э0–Э4, рамка Оператора $75):
- Эпик без вида неработоспособен: требование 11 требует, чтобы `epic show` — одна из команд эпика — строился из модели `board.py`, а требование 8 («эпик готов к закрытию» в `status`/`epic show`) и отказ `epic close` опираются на ту же проекцию состояний задач эпика. Часть «таблица + команды» без `board.py` либо не может выполнить `epic show` по ТЗ, либо получает временный вид, который следующая часть выбрасывает.
- `status` по эпикам (требование 10) не имеет смысла без данных эпика (требования 1–6), а без модели доски нарушает требование «оба вида строятся из модели».
- Разрезаемо без нерабочего промежуточного состояния только одно: связь деления с эпиком (требование 7, зона `orchestrator/fsm.py` и наследование эпика в `catalog.spawn_subtask`) отдельной второй частью после первой. Это сняло бы AC-10–AC-12 (≈3 критерия, 1–2 файла), но первая часть всё равно осталась бы выше всех трёх порогов (7 файлов, 15 критериев, бюджет ≥ $45 по калибровке) — деление сигналов не снимает и добавляет вторую задачу с собственными шагами аналитика/автора тестов/ревью.

Потолок: калибровка `config.BUDGET_CALIBRATION_TABLE` даёт для 18 критериев и 8 файлов зоны $85; поставлена рамка ТЗ $75 (вниз от рекомендации).
