# SPEC: Эпики Э1 — эпик как сущность пульта, команды эпика и модель доски для `status` и `epic show`

## Контекст
Линии задач в пульте нет: `status` (`orchestrator/catalog.py:982`, `cmd_status`) выводит строку на задачу с группировкой только по проекту, `report` (`orchestrator/report.py:46`) — HTML-доска с колонками-состояниями; связь задач видна только по `merge_after` и по делению на гейте SPEC (`orchestrator/fsm.py:958`, `_spawn_division_subtasks`). ADR-0028 (принят 25.10.2026, уровень 1, п. 4–7 и п. 12) вводит эпик — сущность пульта, которая объединяет задачи одного проекта общей целью, — и модель доски: одну проекцию БД и журнала, из которой строятся виды. Шаг Э1 заводит эпик в БД, его команды, связь эпика с делением и модель доски `orchestrator/board.py`, из которой строятся `status` и `epic show`.

Шаг опирается на Э0 (01M5TB6VDVV6AM8DWPGVQE8CDW): признак `closed_as` задачи и единый список состояний `fsm.STATES` (с окончательными `fsm.TERMINAL_STATES`). На текущей ветке этих имён ещё нет (есть только `cleanup.TERMINAL_STATES` и `watch._TERMINAL_STATES`), они появятся в main с Э0.

Решения Оператора на гейте SPEC 26.10 (возвраты по аудитам 1–5) и мандат ANSWER-1 внесены в требования и критерии ниже.

## Требования

1. **Таблица `epics` и миграция.** Схема (`orchestrator/schema.py`) несёт таблицу `epics` с колонками `id`, `project`, `title`, `goal`, `envelope_usd` (необязательно; используется шагом Э2а), `state` (`open` | `closed`), `outcome`, `created_at`, `closed_at` и колонку `tasks.epic_id` (необязательно). `schema.migrate` (`orchestrator/schema.py:183`) догоняет существующую БД без таблицы и колонки: заводит их, у прежних строк `tasks.epic_id` пусто. Миграция пишет ровно одну запись журнала с `task_id` системной записи — именованной константой `config`, тем же приёмом, что `config.PIN_UPDATE_JOURNAL_TASK_ID` (`orchestrator/config.py:313`); повторный `migrate` уже догнанной БД схему не меняет и записи журнала не пишет. Миграция идемпотентна и атомарна: сначала быстрая проверка признака «догон нужен» (отсутствие колонки `tasks.epic_id`) вне транзакции — догнанная БД на ней и заканчивает, блокировка записи на открытии БД не берётся (`store.db()` зовёт `migrate` на каждом открытии); если догон нужен — повторная проверка того же признака, заведение таблицы и колонки (`ALTER`) и запись журнала о миграции идут в одной транзакции `BEGIN IMMEDIATE` (запись журнала — последней в транзакции, требование 14), поэтому при параллельном догоне одной БД двумя соединениями (процессами) запись журнала о миграции одна и ни одно из соединений не получает ошибки (прежний помощник `schema.add_column`, `orchestrator/schema.py:173-180`, проверку и `ALTER` в одну транзакцию не сводит — для этой миграции его недостаточно). На БД без таблицы `steps` (`store.db()` зовёт `migrate` на каждом открытии, такая БД бывает — `tests/test_agent_failure.py:355`) миграция догоняет схему, а запись журнала пропускает без ошибки. Каталог `epics` входит в `config.PROJECT_DIRS` (`orchestrator/config.py:61`).
2. **Идентификатор эпика** — приставка `E` и id в формате идентификатора пульта (`orchestrator/idgen.py`, `new_task_id`). Он не совпадает с префиксами задач: разрешение id задачи (поиск задачи по id/префиксу, разбор `--after`) не находит эпик. Особого случая для id эпика не вводится: id эпика, переданный как id задачи, отказывается тем текстом, который даёт существующая проверка по его фактической причине — в `--after` это причина `merge_after.check` (полный id эпика длиной 27 знаков не проходит форму `idgen.is_task_id_form`, причина — `merge_after: элемент «<id эпика>» не в формате id задачи (полный id или его префикс)`, `scripts/guard.py:5636`), в поиске задачи (`show` и др.) — текст `store.get_task` «Задача <id> не найдена» (`orchestrator/store.py:1093`).
3. **Проект эпика.** Эпик принадлежит одному проекту; задача эпика — того же проекта. Привязка задачи к эпику проверяет проект при каждой привязке (`new --epic`, `epic add`, деление).
4. **Команды эпика.** Каждая изменяющая команда ниже (`epic new`, `epic edit`, `epic close`, `epic add`, `epic remove`) пишет запись журнала. Запись журнала команды эпика несёт `task_id` = id эпика и `target` = проект эпика (`store.journal`, параметр `target`). Lease по id эпика не берётся ни одной командой (решение гейта SPEC 26.10, аудит 4):
   - команды самого эпика (`epic new`, `epic edit`, `epic close`) исполняются одной транзакцией `BEGIN IMMEDIATE` без lease: проверки команды, изменение таблицы `epics` и запись журнала — в этой транзакции; у `epic close` в ней же идут проверка «все задачи эпика окончательны» (требование 9) и закрытие;
   - команды, меняющие задачу (`epic add`, `epic remove`), берут lease ЭТОЙ задачи через `lease.run_locked` — тем же замком, что прочие команды задачи (`approve`, `orchestrator/fsm.py:951`);
   - привязка задачи к эпику — `epic add`, `new --epic` (требование 5), наследование эпика частями деления и `--as-epic` (требование 7) — идёт одной транзакцией `BEGIN IMMEDIATE`: проверка «эпик `open`, проект эпика — проект задачи» (требования 3, 6) и запись `tasks.epic_id` (у `new --epic` и у частей деления — вставка строки задачи с `epic_id`) в этой транзакции; у `new --epic` та же проверка идёт и раньше, до побочных эффектов `new` (требование 5), а в транзакции повторяется как защита от гонки. Lease задачи берётся как прежде (`epic add` и `approve` — lease задачи, `new` — без lease, как сейчас), транзакция идёт внутри него. Так `epic close` и привязка к тому же эпику взаимно исключены: либо задача уже в эпике и `epic close` отказывает по требованию 9, либо `epic close` прошёл и привязка отказывает по требованию 6;
   - `epic show` — только чтение.
   Команда с id эпика (модуль `orchestrator/epics.py`) проверяет существование эпика до lease задачи и до транзакции изменения: нет эпика с таким id — отказ с текстом «эпик <id> не найден», lease не берётся, БД не меняется.
   - `epic new <проект> "<название>" --goal "<цель>" [--envelope N]` — заводит эпик в состоянии `open`;
   - `epic show <id>` — показывает эпик (вид — требование 12). Это команда чтения: она не берёт lease (`lease.acquire` пишет запись журнала «lease взят», `orchestrator/lease.py:144`) и журнала не пишет;
   - `epic edit <id> [--title …] [--goal …]` — меняет название и/или цель;
   - `epic close <id> "<итог>"` — закрывает эпик: `state='closed'`, `outcome` — итог, `closed_at` — время закрытия (условие — требование 9);
   - `epic add <id> <задача>`, `epic remove <id> <задача>` — привязывают уже заведённую задачу к эпику и отвязывают её. `epic remove` задачи в неокончательном состоянии разрешён: `tasks.epic_id` становится пустым, запись журнала пишется. `epic add` задачи, уже состоящей в другом эпике, — отказ с причиной (сначала `epic remove` из её эпика); `epic remove` задачи, которая не состоит в названном эпике (в чужом эпике или без эпика), — отказ с причиной; в обоих отказах `tasks.epic_id` не меняется.
5. **`new` с эпиком.** `new "<название>" --tz <файл> --target <проект> --epic <id> [--after <id>[,<id>…]]` заводит задачу в эпике; lease по id эпика не берётся, заведение задачи идёт тем же порядком, что `new` сейчас (`catalog.cmd_new`); существование эпика проверяется до заведения задачи с тем же отказом «эпик <id> не найден» (требование 4). Проверка «эпик существует, `open`, проект эпика — проект задачи» (требования 3, 4, 6) идёт до побочных эффектов `new` — до создания ссылки документов задачи `refs/artifacts/<id>` (`catalog._new_task_row`, `orchestrator/catalog.py:708`), до вставки строки задачи и записи журнала: отказ по ней не оставляет ни строки `tasks`, ни ссылки `refs/artifacts/<id>`. Повторная проверка того же условия в транзакции `BEGIN IMMEDIATE` со вставкой строки (требование 4) остаётся защитой от гонки с `epic close`; ссылка документов, оставшаяся без строки задачи при отказе только в этом окне гонки, допускается (решение Оператора на гейте SPEC, 26.10). `--after` записывает `merge_after` той же проверкой, что строка ТЗ «Порядок: после …» (`merge_after.check`, `orchestrator/merge_after.py:126`). Если в ТЗ есть строка «Порядок: после …» и задан `--after`, значение `merge_after` — объединение обоих перечней с дедупликацией по полному id (сначала элементы строки ТЗ, затем элементы `--after`, чей полный id не совпал с уже вошедшим; префикс и полный id одной задачи — один элемент), и проверку `merge_after.check` проходят элементы обоих источников. Дедупликация идёт до `merge_after.check` (`check` отказывает на повторе задачи в перечне), проверяется уже объединённый перечень. Непрошедший элемент любого источника — отказ, задача не заводится. `--after` без `--epic` работает так же (записывает `merge_after` той же проверкой), задача заводится без эпика.
6. **Отказы привязки.** Привязка задачи (`new --epic`, `epic add`) к закрытому эпику или к эпику другого проекта — отказ с причиной; привязка не происходит.
7. **Деление и эпик.**
   - Части деления на гейте SPEC наследуют эпик родителя.
   - `approve <id> [sha] --as-epic` на гейте SPEC у задачи с делением и без эпика создаёт эпик из родителя: проект — проект задачи; название — название задачи; цель — первый абзац раздела «Контекст» SPEC родителя; конверт не задан; части деления — задачи нового эпика; родитель тоже входит в новый эпик (`tasks.epic_id` родителя = id эпика) с `closed_as='divided'` и виден в `epic show` этого эпика; запись журнала родителя со ссылкой на эпик.
   - Эпик по `--as-epic` заводится только вместе с заведением частей деления: если approve на гейте SPEC отказывает мягко и части не заводятся (мягкие отказы `_approve_spec_gate`, `orchestrator/fsm.py:1201-1287`), эпик не заводится и `tasks.epic_id` родителя не меняется.
   - `--as-epic` у задачи без деления или у задачи, уже состоящей в эпике, — отказ до `lease.run_locked` (lease задачи, которую `approve` берёт и сейчас, `orchestrator/fsm.py:951`) и до любых записей гейта: БД (задачи, эпики, журнал, в том числе запись о взятии lease) не меняется. Предварительное чтение SPEC родителя ради этого отказа журнала не пишет (в отличие от `_read_branch_text_or_refuse` гейта, `orchestrator/fsm.py:379`, который при отказе журнал пишет).
   - SPEC родителя на ветке при предварительном чтении не читается — отказ `--as-epic` с причиной (текст отказа говорит, что SPEC родителя не прочитан), так же до `lease.run_locked`, без записей журнала: БД (задачи, эпики, журнал) не меняется.
   - Флаг `--as-epic` в командной строке `approve` не принимается за позиционный `sha` (`orchestrator/artel.py:2006`, `_approve_sha_arg`); позиционный `sha` вместе с флагом передаётся как прежде.
   - `approve` без `--as-epic` — прежнее деление.
8. **Порядок задач эпика** — порядок зависимостей `merge_after` внутри эпика: задача идёт после всех задач эпика, от которых зависит; задачи без взаимной зависимости — по возрастанию id.
9. **Закрытие — только Оператор.** `epic close` при задачах эпика не в окончательных состояниях (`fsm.TERMINAL_STATES`) — отказ с их перечнем; эпик остаётся `open`. Проверка и закрытие — одна транзакция `BEGIN IMMEDIATE` (требование 4). Когда у эпика есть хотя бы одна задача и все его задачи окончательны, `status` и `epic show` показывают «эпик готов к закрытию»; сам эпик пульт не закрывает. Эпик без задач «эпик готов к закрытию» не показывает.
10. **Модель доски.** Модуль `orchestrator/board.py`, функция `build_model(conn, project)`, строит модель проекта из БД и журнала — словарь — без обращения к хостингу и сети. Ключи модели:
    - верхний уровень: `schema_version`, `project`, `generated_at`, `pin` (пин запущенной версии пульта — sha головы `HEAD` главной копии пульта `config.ROOT`, тем же способом, что `watch._pin_head`, `orchestrator/watch.py:354`: чтение `.git` без запуска git; не прочитан — `None`), `columns` (равен `fsm.STATES`), `epics`, `cards`;
    - элемент `epics` (на эпик проекта): `id`, `title`, `goal`, `envelope_usd`, `spent_usd` (сумма потраченного задачами эпика), `counts` (число задач эпика по состояниям), `nodes` (id задач эпика), `edges` (рёбра `merge_after` и родитель–часть; у ребра — концы и вид `merge_after` | `parent`);
    - элемент `cards` (на задачу проекта): `task`, `title`, `epic`, `state`, `closed_as`, `waiting_on`, `depends_on` (зависимости `merge_after`), `spent_usd`, `budget_usd`, `branch`, `last_event_at` (время последнего события журнала задачи).
    Модель доски БД не пишет. Повторное построение без изменений БД даёт ту же модель (кроме `generated_at`).
11. **`waiting_on` карточки.** У окончательных состояний (`fsm.TERMINAL_STATES`: `done`, `killed`) — пусто (`None`). У прочих — первое сработавшее правило в порядке operator → ci → dependency → role:
    - `operator` — состояния, которым `status` сейчас ставит отметку «ЖДЁТ ОПЕРАТОРА» (`orchestrator/catalog.py:992`): `spec_gate`, `acceptance`, `merge_gate`, `escalated`;
    - `ci` — `verifying`;
    - `dependency` — задачу держит зависимость: ожидание зоны (то же условие, по которому `status` печатает добавку ожидания зоны, `zone_lock.queue_wait`, в том числе «ждёт зону ради зависимости»), незакрытая зависимость `merge_after` или `start_after`;
    - `role` — иначе: шаг роли идёт или задача готова к нему.
    Незакрытые зависимости `merge_after` держат задачу только на гейте мержа (`merge_gate`), где раньше срабатывает `operator`; поэтому в Э1 `dependency` от `merge_after` проявляется через ожидание зоны «ради зависимости». `start_after` вводит Э2а — в Э1 его правило не срабатывает.
12. **`epic show` из модели.** `epic show <id>` выводит название, цель и таблицу задач эпика в порядке требования 8 со столбцами: задача, родитель, от чего зависит, состояние, кто держит (`waiting_on`), потрачено/потолок, итог; и «эпик готов к закрытию» при условии требования 9. Вид строится из модели `board.build_model`.
13. **`status` с эпиками.**
    - Строка задачи строится прежним кодом `cmd_status` из тех же данных; модель `board.build_model` — источник групп эпиков, их заголовков и `waiting_on`.
    - Если хотя бы у одной задачи БД есть эпик, вывод задач группируется блоками проектов: заголовок блока — имя проекта (`target`), блоки идут по возрастанию имени проекта. Внутри блока сначала идут группы эпиков этого проекта, затем задачи проекта без эпика — прежними строками в прежнем порядке.
    - Заголовок группы эпика начинается с `<id эпика> <название> — ` и несёт потрачено и конверт (`потрачено / конверт`, без конверта — «без конверта»), счётчики задач по состояниям, «части слиты N/M» у поделённой задачи эпика (N — части в `done`, M — все её части), «эпик готов к закрытию» (требование 9). Затем строки задач эпика в порядке требования 8.
    - Ни у одной задачи нет эпика — вывод `status` прежний, без блоков проектов.
14. **Ограничения реализации** (решение гейта SPEC 26.10, аудит 5):
    - `store.journal` сам делает `commit` (`orchestrator/store.py:1250`): в транзакциях `BEGIN IMMEDIATE` команд эпика, привязки (требование 4) и миграции (требование 1) запись журнала идёт последней;
    - запросы SQL модулей `orchestrator/board.py` и `orchestrator/epics.py` живут в `orchestrator/store.py` (правило `SqlOnlyInStoreTest`, `tests/test_multitarget.py:516`); сами `board.py` и `epics.py` SQL не несут;
    - дедупликация перечней строки ТЗ «Порядок: после …» и `--after` — до `merge_after.check` (требование 5).

## Критерии приёмки

AC-1. `epic new <проект> "<название>" --goal "<цель>" [--envelope N]` заводит в таблице `epics` запись этого проекта в состоянии `open` с названием, целью и конвертом N (без `--envelope` — конверт пуст); id эпика — `E` и 26 знаков алфавита идентификатора пульта; запись журнала о заведении есть.
AC-2. `epic show <id>` по эпику с задачей-родителем P (поделённой), её частью C (`parent_task_id = P`) и задачей D с `merge_after = C` выводит название и цель эпика и таблицу со столбцами: задача, родитель, от чего зависит, состояние, кто держит, потрачено/потолок, итог; в строке C столбец «родитель» называет P, в строке D столбец «от чего зависит» называет C.
AC-3. `epic edit <id> --title … --goal …` меняет название и цель эпика в БД; запись журнала есть.
AC-4. `epic add <id> <задача>` записывает `tasks.epic_id` задачи того же проекта; `epic remove <id> <задача>` у задачи в неокончательном состоянии (например `in_dev`) делает `tasks.epic_id` пустым; у каждой операции есть запись журнала.
AC-5. Привязка задачи другого проекта к эпику (`epic add`, `new --epic`) — отказ с причиной; `tasks.epic_id` не записан, `new` задачу не заводит, и после отказа `new --epic` ссылки `refs/artifacts/<id>` в репозитории задачи нет.
AC-6. Привязка задачи к закрытому эпику (`epic add`, `new --epic`) — отказ с причиной; `tasks.epic_id` не записан, `new` задачу не заводит, и после отказа `new --epic` ссылки `refs/artifacts/<id>` в репозитории задачи нет.
AC-7. `new "<название>" --tz <файл> --target <проект> --epic E… --after <id>` заводит задачу с `epic_id` этого эпика и `merge_after`, равным полному id из `--after`.
AC-8. `new … --after <id>` с id, которого нет среди задач, — отказ, задача не заведена.
AC-9. `new … --after <id эпика>` (полный id эпика) — отказ, текст которого содержит причину, возвращаемую `merge_after.check` для этого элемента: `merge_after: элемент «<id эпика>» не в формате id задачи (полный id или его префикс)`; задача не заведена. `show <id эпика>` — отказ, текст которого содержит «Задача <id эпика> не найдена» (текст `store.get_task`).
AC-10. `new --tz <файл> … --after Y`, где ТЗ несёт строку «Порядок: после X» (X и Y — существующие задачи того же проекта), заводит задачу с `merge_after = X, Y`; тот же вызов с несуществующим Y — отказ, задача не заведена, хотя X годен; с годным Y и несуществующим X в строке ТЗ — отказ, задача не заведена.
AC-11. `approve` на гейте SPEC задачи в эпике с делением заводит части с тем же `epic_id`, что у родителя.
AC-12. `approve <id> --as-epic` у задачи без эпика с делением заводит эпик проекта задачи с названием задачи, целью — первым абзацем раздела «Контекст» её SPEC — и пустым конвертом; части деления состоят в этом эпике; родитель тоже состоит в этом эпике (`tasks.epic_id` = id эпика) с `closed_as='divided'` и выводится строкой в `epic show <id эпика>`; запись журнала родителя называет id нового эпика.
AC-13. `approve <id> --as-epic` у задачи без деления — отказ; у задачи, уже состоящей в эпике, — отказ; в обоих случаях все строки таблиц `tasks`, `epics` и `steps` после вызова равны снимку до вызова (эпик не заведён, состояние задачи не изменено, записей журнала гейта и записи о взятии lease нет), а `lease.run_locked` не вызывался.
AC-14. Через CLI `orchestrator/artel.py`: `approve <id> --as-epic` проходит как approve без позиционного `sha` и заводит эпик (флаг не принят за `sha`); `approve <id> <sha> --as-epic` передаёт `<sha>` позиционным `sha` и флаг `--as-epic`.
AC-15. `epic close <id> "<итог>"` при задаче эпика не в `fsm.TERMINAL_STATES` — отказ, текст отказа называет id этой задачи; эпик остаётся `open`.
AC-16. На фикстуре эпика, задачи которого все окончательны и среди них есть задача в `done` и задача в `killed`, `status` и `epic show <id>` выводят «эпик готов к закрытию», а `epics.state` эпика остаётся `open`; последующий `epic close <id> "<итог>"` переводит эпик в `closed` с записанными `outcome` и `closed_at`.
AC-17. Эпик без задач: `status` и `epic show <id>` не выводят «эпик готов к закрытию». Фикстура `status` несёт, кроме эпика без задач, второй эпик того же проекта с задачей в неокончательном состоянии (так `status` выводит блоки проектов и группы эпиков, требование 13); «эпик готов к закрытию» в выводе нет ни для одного из двух эпиков, а группа эпика без задач, если выводится, этой строки не несёт.
AC-18. При живой чужой lease на задачу `epic add <id> <задача>` и `epic remove <id> <задача>` отказывают текстом отказа `lease.run_locked`, строки таблиц `tasks`, `epics` и `steps` не меняются. Ни одна из команд `epic new`, `epic edit`, `epic close`, `epic add`, `epic remove`, `epic show` и `new --epic <id>` не берёт lease по id эпика: ни во время исполнения, ни после него в таблице lease нет строки с id эпика, и в журнале нет записи о взятии lease с `task_id` = id эпика; после успешных `epic add`/`epic remove` lease задачи не остаётся.
AC-19. `schema.migrate` на БД прежней схемы (таблица `tasks` без `epic_id`, таблицы `epics` нет, с существующими задачами) заводит таблицу `epics` и колонку `tasks.epic_id` (у прежних задач пусто) и пишет ровно одну запись журнала с `task_id` системной записи (константа `config`); повторный `migrate` не меняет схему и не добавляет записей журнала.
AC-20. Модель `board.build_model(conn, project)` — словарь с ключами верхнего уровня ровно `schema_version`, `project`, `generated_at`, `pin`, `columns`, `epics`, `cards`; `columns == fsm.STATES`.
AC-21. Элемент `epics` модели несёт ключи `id`, `title`, `goal`, `envelope_usd`, `spent_usd`, `counts`, `nodes`, `edges`; на фикстуре AC-2 `edges` содержит ребро вида `parent` между P и C и ребро вида `merge_after` между D и C. Элемент `cards` несёт ключи `task`, `title`, `epic`, `state`, `closed_as`, `waiting_on`, `depends_on`, `spent_usd`, `budget_usd`, `branch`, `last_event_at`.
AC-22. `waiting_on` карточки: `operator` в `spec_gate`, `acceptance`, `merge_gate`, `escalated`; `ci` в `verifying`; `None` в `done` и `killed`; `role` в каждом из остальных состояний `fsm.STATES` при отсутствии ожидания зоны — проверка на каждом состоянии `fsm.STATES`.
AC-23. Задача в состоянии с `waiting_on='role'` (например `in_dev`), у которой `zone_lock.queue_wait` сообщает ожидание зоны, получает `waiting_on='dependency'`.
AC-24. Два построения модели `board.build_model` подряд без изменений БД дают равные словари после удаления `generated_at`; построение модели не меняет `total_changes` соединения БД.
AC-25. Подмена `board.build_model` функцией, возвращающей модель с изменёнными названием эпика и счётчиками, меняет соответствующие места вывода `status` и `epic show` — оба вида берут эти данные из модели.
AC-26. `status` для проекта с эпиком выводит группу эпика с заголовком, который начинается с `<id эпика> <название эпика> — ` и несёт потрачено и конверт (без конверта — «без конверта») и счётчики по состояниям, у поделённой задачи эпика — «части слиты N/M»; строки задач эпика идут в порядке зависимостей: на фикстуре, где задача с меньшим id зависит (`merge_after`) от задачи с большим id, задача с большим id выводится раньше.
AC-27. Строка задачи внутри группы эпика в `status` совпадает со строкой той же задачи, которую `status` выводит после `epic remove` этой задачи из эпика.
AC-28. На фикстуре БД с двумя проектами (`b-proj` с эпиком и задачами без эпика, `a-proj` только с задачами без эпика) `status` выводит блоки проектов с заголовком-именем проекта, блок `a-proj` раньше блока `b-proj`; в блоке `b-proj` сначала группа эпика, затем задачи без эпика в прежнем порядке; блок `a-proj` не содержит группы эпика `b-proj`.
AC-29. `status` на фикстуре без единой задачи с эпиком выводит тот же текст, что `status` кода main после мержа Э0 (01M5TB6VDVV6AM8DWPGVQE8CDW) на той же фикстуре, без заголовков блоков проектов. На шаге tests_writing тест строится от фикстуры, без эталона кода main. Эталон вывода `status` снимается кодом main ПОСЛЕ мержа Э0 и вносится в зафиксированную планку командой `amend-tests` (ADR-0012) сессией при Операторе — не разработчиком: разработчик эталон в планку не вписывает и планку не правит.
AC-30. Записи журнала команд `epic new`, `epic edit`, `epic close`, `epic add`, `epic remove` несут `task_id` = id эпика и `target` = проект эпика. `epic show <id>` журнала не пишет: число строк таблицы `steps` после вызова равно числу до вызова, lease не берётся.
AC-31. `epic add <E2> <задача>` для задачи, состоящей в эпике E1 того же проекта, — отказ с причиной, `tasks.epic_id` задачи остаётся E1; `epic remove <E2> <задача>` для задачи из E1 и для задачи без эпика — отказ с причиной, `tasks.epic_id` не меняется.
AC-32. `new --tz <файл> … --after <префикс X>`, где ТЗ несёт строку «Порядок: после X» (полный id), заводит задачу с `merge_after`, равным одному полному id X (без повтора). `new … --after <id>` без `--epic` заводит задачу без эпика (`tasks.epic_id` пуст) с `merge_after`, равным полному id.
AC-33. На фикстуре эпика с задачами A (`in_dev`, потрачено 1.5), B (`done`, потрачено 2.0) и C (`done`, потрачено 0) элемент `epics` модели `board.build_model` несёт `spent_usd == 3.5`, `counts`, где `in_dev` — 1 и `done` — 2, и `nodes`, равный множеству {A, B, C}; задача другого эпика или без эпика в `nodes` и `counts` не входит.
AC-34. `schema.migrate` на БД прежней схемы без таблицы `steps` заводит таблицу `epics` и колонку `tasks.epic_id` без исключения. Два вызова `migrate` на двух соединениях одной БД прежней схемы, в том числе с перемежением: второе соединение начинает `migrate`, пока первое держит открытую транзакцию миграции (до её `COMMIT`), — оставляют ровно одну запись журнала о миграции, и ни один вызов не поднимает исключения.
AC-35. Команды `epic show`, `epic edit`, `epic close`, `epic add`, `epic remove` и `new --epic` с id, которого нет в таблице `epics`, отказывают текстом «эпик <id> не найден»; lease не берётся (`lease.run_locked` не вызывается), строки таблиц `tasks`, `epics` и `steps` после вызова равны снимку до вызова.
AC-36. `approve <id> --as-epic` у задачи с делением без эпика, где approve гейта SPEC отказывает мягко и части деления не заводятся, — эпик не заведён. У задачи без эпика, чей SPEC на ветке не читается, `approve <id> --as-epic` — отказ, текст которого говорит, что SPEC родителя не прочитан; строки таблиц `tasks`, `epics` и `steps` после вызова равны снимку до вызова, `lease.run_locked` не вызывался.

AC-39. Фикстура: эпик `open` с одной задачей в `done` и задача T того же проекта без эпика в неокончательном состоянии. `epic add <id> T` и `epic close <id> "<итог>"` на двух соединениях одной БД, с перемежением в обе стороны (второе начинает, пока первое держит открытую транзакцию до её `COMMIT`), дают ровно один из двух исходов: либо `tasks.epic_id` T = id эпика, `epic close` отказан и эпик `open`; либо эпик `closed`, `epic add` отказан и `tasks.epic_id` T пуст. Неокончательной задачи в закрытом эпике после обоих вызовов нет, ни один вызов не поднимает исключения.

## Правка существующих тестов
Требование 1 (каталог `epics` в `config.PROJECT_DIRS`) опрокидывает утверждение с литералом-списком в `tests/test_multitarget.py::TargetInitTest::test_structure_is_created`. В раздел «Меняемое поведение» оно не входит (там только скалярные литералы); правка идёт по мандату Оператора: ANSWER-1 — «Ослабление тестов разрешено: tests/test_multitarget.py», объём — ровно это утверждение (:288-289), независимая проверка подтверждена (решение гейта 26.10, аудит 2, пп. 9).

Было (`tests/test_multitarget.py:288-289`):

    self.assertEqual(sorted(config.PROJECT_DIRS),
                     ["knowledge", "logs", "tasks", "worktrees"])

Станет:

    self.assertEqual(sorted(config.PROJECT_DIRS),
                     ["epics", "knowledge", "logs", "tasks", "worktrees"])

Почему без ослабления: вид утверждения (`assertEqual` на полный отсортированный список) и его точность сохраняются — список по-прежнему перечисляет состав целиком, а не проверяет вхождение; ожидание пополнено ровно одним элементом, которого требует требование 1; соседнее утверждение `tests/test_multitarget.py:286-287` (каждый каталог `PROJECT_DIRS` создан `target-init`) не меняется, и вместе они теперь ловят и мутацию «`target-init` не заводит `epics`». Других строк метода и других методов правка не касается.

## Оценка объёма и деление
Сработавшие сигналы: файлов зоны вне общих — 8 (`board.py`, `epics.py`, `schema.py`, `store.py`, `catalog.py`, `fsm.py`, `merge_after.py`, `artel.py`) при пороге 5; критериев приёмки — 39 при пороге 10; `budget_usd` 75 при пороге 60 (`config.SPLIT_SIGNAL_BUDGET_USD`).

**Обоснование монолита** (материал для решения Оператора; ТЗ — уже шаг Э1 нарезки ADR-0028 на Э0–Э4, рамка Оператора $75):
- Эпик без вида неработоспособен: `epic show` — одна из команд эпика — строится из модели `board.py` (требование 12), а «эпик готов к закрытию» в `status`/`epic show` (требование 9) опирается на ту же проекцию состояний задач эпика. Часть «таблица + команды» без `board.py` либо не выполняет `epic show` по ТЗ, либо получает временный вид, который следующая часть выбрасывает.
- `status` по эпикам (требование 13) не имеет смысла без данных эпика (требования 1–6), а без модели доски нарушает требование «оба вида строятся из модели».
- Разрезаемо без нерабочего промежуточного состояния только одно: связь деления с эпиком (требование 7, зона `orchestrator/fsm.py`, наследование эпика частями, CLI `--as-epic` в `orchestrator/artel.py`) отдельной второй частью. Это сняло бы AC-11–AC-14 (4 критерия), но первая часть осталась бы выше всех трёх порогов (7–8 файлов, 33 критерия, бюджет ≥ $45 по калибровке) — деление сигналов не снимает и добавляет вторую задачу со своими шагами аналитика/автора тестов/ревью.

Потолок: калибровка `config.BUDGET_CALIBRATION_TABLE` даёт для >15 критериев и 8 файлов зоны $85; поставлена рамка ТЗ $75 (вниз от рекомендации).

## Не входит
- Конверт эпика как механика (учёт, предупреждения, остановка по конверту) и `start_after` — шаг Э2а; здесь `envelope_usd` только хранится и показывается.
- `auto --epic` — шаг Э2б.
- Черновики, решения, ссылка `refs/artifacts/epic-<id>`, `epic export` — шаг Э3.
- `board --json/--md/--html`, `report` из модели доски, внешние ссылки и `link`, ссылка MR и состояние CI на карточке — шаг Э4; `orchestrator/report.py` только читается.
- Автоматическое закрытие эпика пультом — закрывает только Оператор командой `epic close`.
- Признак `closed_as` и список `fsm.STATES`/`fsm.TERMINAL_STATES` — вводит Э0 (01M5TB6VDVV6AM8DWPGVQE8CDW), здесь только используются.
- Правка `orchestrator/lease.py`, `orchestrator/watch.py`, `docs/design.md`, `docs/adr/0028-epics-and-board-projection.md` — только чтение. Lease по id эпика не вводится (решение гейта 26.10, аудит 4): `lease.py` используется как есть, с id задачи.
