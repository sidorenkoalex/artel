# SPEC-AUDIT: Эпики Э1 — эпик как сущность пульта, команды эпика и модель доски для `status` и `epic show`

## ТЗ и SPEC
Требования ТЗ 1–6, критерии, «Порядок», зоны, «Только чтение», «Не входит» и рамка $75 в SPEC отражены (SPEC.md:21–44, :8–11, :93–101). ANSWER-n у задачи нет. Расхождения:

- **А1. `lease.run_locked` для `new --epic` потерян.** В ТЗ («Команды (все — через `lease.run_locked`, с записью журнала)», TZ.md, Требуется п. 2) в этот список входит и `new … --epic … --after`. В SPEC обязательство осталось только у команд `epic …` (SPEC.md:24), в требовании 5 (SPEC.md:30) его нет. Сегодня `cmd_new` lease не берёт (`orchestrator/catalog.py:550`) — до создания id задачи брать нечего. Значит, решать должен Оператор: либо снять это требование с `new`, либо назвать, какой замок `new --epic` берёт.
- **А2. Мандат на правку существующего теста не механический.** SPEC считает строку ТЗ «правка — по ночному мандату Оператора 25.10» мандатом (SPEC.md:68). Гейт неослабления читает только строку `Ослабление тестов разрешено: …` в ANSWER-n (`orchestrator/advance_gates/mandate.py:40`; `docs/operator-gates.md:344-365`) либо объявление в «Меняемое поведение», а там допустимы только скалярные литералы (`orchestrator/advance_gates/test_integrity.py:36-41`). Изменённый аргумент `assertEqual` — находка гейта (`docs/operator-gates.md:290-293`). Без строки мандата в ANSWER-n переход `in_dev → verifying` либо откажет, либо, по меньшей мере, даст непокрытую находку. Это отклонение по правилу скила: решение Оператора не создаёт мандата.
- Лишних требований сверх ТЗ нет. AC-9 («отказ „задача не найдена“») и AC-12 («состояние задачи не изменено») — уточнения ТЗ, не новые требования.

Не подтвердилось или требует оговорки:
- **Ф1.** AC-9 (SPEC.md:56) требует одного отказа «задача не найдена» и для поиска задачи, и для разбора `--after`. Тексты на коде разные:
  - `store.get_task` печатает «Задача … не найдена» (`orchestrator/store.py:1093`);
  - `merge_after.check` для элемента без совпадений даёт «нет такой задачи» (`orchestrator/merge_after.py:147`);
  - полный id эпика (`E` + 26 знаков = 27) не проходит форму `idgen.is_task_id_form` (`orchestrator/idgen.py:59`) и отказывает текстом формы «не в формате id задачи» (`scripts/guard.py:5635-5637`), а не «не найдена».

  Тест на буквальный текст AC-9 заставит переписать сообщения `merge_after`/guard — этого никто не просил.
- **Ф2.** Миграция с записью журнала (SPEC.md:21): у `schema.migrate` сегодня записей журнала нет совсем (`orchestrator/schema.py:183`). SPEC не говорит, под каким `task_id` и один ли раз пишется запись. `migrate` идёт при каждом `store.db()`, поэтому без условия «только когда таблица/колонка действительно добавлена» журнал засоряется. Колонку `tasks.epic_id` придётся завести и в `CREATE TABLE tasks`, иначе упадёт `tests/test_store_schema_migration_parity.py:36-44` — SPEC об этом молчит, ловушка для разработчика.
- **Ф3.** `status` не принимает проект (`orchestrator/catalog.py:982`, `store.all_tasks` по возрастанию id через все проекты, `orchestrator/store.py:775-777`), а модель `board.py` — на проект (SPEC.md:38). В AC-17/AC-18 «`status` для проекта …» (SPEC.md:64-65) не определено, где стоят группы эпиков относительно плоского списка и не переупорядочатся ли задачи без эпиков по проектам, если строить вывод помодельно.
- **Ф4.** Строка `status` сегодня несёт поля, которых нет в перечне карточки (SPEC.md:41): ревью-итерации, токены (`_tokens_field`), набор моделей, `[canary]`, держатель lease по живости pid (`_lease_holder_suffix`, `orchestrator/catalog.py:823`), ожидание зоны, стоп-кран волны, аудит (`orchestrator/catalog.py:991-1032`). Держатель lease зависит от состояния ОС, не только от БД, и плохо совмещается с требованием «модель из БД и журнала, повтор даёт ту же модель» (SPEC.md:42). SPEC не решает, строится ли строка задачи целиком из модели (тогда модель шире перечня ТЗ) или из модели берутся только группировка, порядок и заголовки.
- **Ф5.** `approve <id> --as-epic`: позиционный sha `approve` — первый аргумент после id, кроме известных флагов (`orchestrator/artel.py:2006-2020`). Новый флаг, не внесённый в этот пропуск, будет прочитан как sha. Требование 7 (SPEC.md:34) не называет разбор CLI.

Не задано и для `verifying` (`ci`), ожидания зависимостей (`dependency`), агентских состояний (`role`), `done`/`killed`.

- Зоны SPEC (SPEC.md:7) совпадают с зонами ТЗ. `orchestrator/config.py`, `tests/`, `docs/codebase-map.md` — общие (`orchestrator/config.py:821`).

## Пути обхода гейтов
- **О1. Константа `waiting_on`.** `waiting_on='operator'` у каждой карточки выполняет AC-15 буквально, но «кто держит» в `epic show` становится бесполезным (В1).
- **О2. Узкая фикстура AC-18.** Голая задача без добавок проверяет «`status` не изменился» буквально, но при переписывании `cmd_status` на модель добавки строки могут пропасть незамеченными (В3).
- **О3. Модель «для галочки».** Модель строится, но `status`/`epic show` считают группы и пометки прямыми запросами к БД: AC проходят, а смысл ADR-0028 п. 12 «расхождение видов исключено устройством» не выполнен (В8).
- **О4. `epic remove` обходит отказ `epic close`.** Отвязать незакрытые задачи и закрыть эпик — требование 8 выполнено буквально, но смысл «закрытие при незавершённых — отказ» снят (SPEC.md:29, :37). Это команды Оператора, роль их не вызовет (белый список), но SPEC не задаёт поведение `remove` у задачи не в окончательном состоянии и у закрытого эпика. Решение — за Оператором.
- **О5. Пустой эпик.** «Все задачи эпика окончательны» на эпике без задач истинно, поэтому свежий `epic new` сразу «готов к закрытию» (SPEC.md:37). Буквально верно, по смыслу — нет.
- **О6. `--after` вместе со строкой ТЗ «Порядок: после …».** Объединение, приоритет или отказ — не задано (SPEC.md:30). Если `--after` записывает колонку мимо `merge_after.record_declared` (`orchestrator/merge_after.py:216`), в журнале нет записи «merge_after заявлен Оператором», хотя сверка на гейте SPEC по колонке сработает (`orchestrator/merge_after.py:252`).

## Вердикт
**concerns.** SPEC верно передаёт ТЗ и сверен с кодом, монолит обоснован. Но критерии пропускают правдоподобные поломки, а для правки существующего теста не хватает мандата. Решение за Оператором на гейте: выдать мандат и при желании вернуть SPEC аналитику (`reject`) с пунктами ниже.

Отклонения:
1. **А2 / матрица** — правка `tests/test_multitarget.py:288-289` без строки мандата `Ослабление тестов разрешено: …` в ANSWER-n; строка ТЗ мандатом для гейта не является (SPEC.md:68, `orchestrator/advance_gates/mandate.py:40`, `docs/operator-gates.md:344-365`).
2. **В1 / О1** — AC-15 не ловит константу `waiting_on`; правило отображения для остальных состояний, включая `acceptance`, не задано (SPEC.md:41, :62; `orchestrator/catalog.py:991-992`; ADR-0028:76).
3. **В2 / Ф2** — у миграции существующей БД и её записи журнала нет критерия; не названы `task_id` записи и условие однократности (SPEC.md:21; `orchestrator/schema.py:183`).
4. **В3 / О2 / Ф4** — у AC-18 не задана фикстура, и не решено, строится ли строка задачи `status` из модели (поля строки вне перечня карточки, держатель lease по pid) (SPEC.md:41-43, :65; `orchestrator/catalog.py:991-1032`). Не задано и то, к какому main (до или после Э0) привязана сверка.
5. **В4** — AC-2 проходит на эпике без задач; нужны строки с родителем и зависимостью (SPEC.md:49).
6. **В5** — AC-17 не требует порядка зависимостей, отличного от порядка id (SPEC.md:64).
7. **В6** — у `lease.run_locked` команд эпика нет критерия; у `new --epic` обязательство ТЗ потеряно (А1) (SPEC.md:24, :30).
8. **В7 / В8 / О3** — ключи `epics`/`cards` модели и «вид из модели» критериями не проверяются (SPEC.md:40-44).
9. **Ф1** — текст отказа в AC-9 расходится с кодом `merge_after.check`/guard (SPEC.md:56; `orchestrator/merge_after.py:147`; `scripts/guard.py:5635`; `orchestrator/idgen.py:59`).
10. **Ф3** — `status` общий для всех проектов, модель — на проект; место групп эпиков и порядок задач без эпиков не заданы (SPEC.md:43, :64-65; `orchestrator/store.py:775-777`).
11. **Ф5** — `--as-epic` и разбор позиционного sha `approve` (`orchestrator/artel.py:2006-2020`); AC-11/12 не требуют CLI.
12. **О4 / О5 / О6** — не заданы `epic remove` незакрытой задачи, «готов к закрытию» у пустого эпика и сочетание `--after` со строкой ТЗ «Порядок: после» (SPEC.md:29-30, :37).

Второстепенно: AC-12 проверяет только состояние, а отказ `--as-epic` после частичных записей гейта (`orchestrator/fsm.py:1311-1325`) не ловит. У AC-14 фикстура не обязана нести и `done`, и `killed`.
