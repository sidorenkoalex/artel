- `tests/test_store_schema_migration_parity.py:36-41` сверяет только колонки `tasks` свежей БД до и после `migrate`, то есть требует, чтобы `epic_id` был и в `SCHEMA`, и в `migrate`.

Не подтвердилось или не учтено:
1. **«Блока проекта» в `status` нет.** `cmd_status` печатает все задачи подряд из `store.all_tasks` в порядке `ORDER BY id` (`store.py:775-777`, `catalog.py:984`, `:991`). Задачи разных проектов перемешаны, у внешнего проекта есть только метка `[проект]` (`catalog.py:1018-1019`). Ни заголовков проектов, ни блоков нет. Требование 13 (SPEC.md:56: «Внутри блока проекта… сначала группы эпиков проекта») и AC-28 опираются на несуществующую структуру. Не определены: порядок блоков, их заголовки, порядок строк чужого проекта без эпиков в БД, где у другого проекта эпик есть. ТЗ при этом требует, чтобы «вывод для проекта без эпиков не менялся»; AC-29 проверяет только БД, где эпиков нет вовсе.
2. **AC-9 и требование 2 расходятся с `merge_after.check`.** Полный id эпика — `E` плюс 26 знаков, всего 27. `idgen.is_task_id_form` пропускает не больше 26 знаков (`orchestrator/idgen.py:59-60`). Поэтому `check` уже на проверке формы вернёт `merge_after: элемент «E…» не в формате id задачи (полный id или его префикс)` (`scripts/guard.py:5636-5637`). После «»» здесь нет « — », то есть ожидание AC-9 «строка, начинающаяся `merge_after: элемент «<id эпика>» — `» не выполняется. Отказ также отличается от отказа на несуществующий id задачи («— нет такой задачи», `merge_after.py:147`), вопреки требованию 2 («теми же текстами, что и любой несуществующий id»). Прямое использование `check` даёт тест, который останется красным. `scripts/guard.py` не в зонах.
3. **Журнал в `migrate` и БД без `steps`.** `migrate` вызывается при каждом открытии `store.db()` (`store.py:409`). Есть БД, где `tasks` есть, а `steps` нет: `schema.py:391-397` называет такие тесты, например `tests/test_agent_failure.py:355` (`MigrationTest`: `CREATE TABLE tasks (id, state)` и затем `store.db()`). Требование 1 («пишет ровно одну запись журнала») на такой БД роняет `INSERT INTO steps` и вместе с ним любое открытие БД, то есть существующий тест. SPEC этот случай не оговаривает. Не оговорена и гонка двух параллельных `store.db()` на старой БД: та же TOCTOU, что описана в `tests/test_store_schema_migration_parity.py:1-15`, даст две записи журнала.
4. **Журнал и lease на id эпика.** `lease.acquire` пишет в `steps` запись «lease взят» (`lease.py:144`). `store.journal` без `target` берёт его из `task_target`, а для id, которого нет в `tasks`, это `config.DEFAULT_TARGET` (`store.py:780-786`, `:1242-1243`). Значит, записи журнала эпика внешнего проекта (и lease, и записи команд, если target не передан) попадут в target `artel`. SPEC не задаёт `task_id`/`target` записей журнала эпика.

## Пути обхода гейтов
1. **Отказ `--as-epic` после lease.** Требование 7 (SPEC.md:37) говорит «до любых записей гейта», но не «до `lease.run_locked`». Исполнитель может поставить проверку внутри `_cmd_approve`, после `acquire`. Тогда AC-13 краснеет, и исполнитель «чинит» тест, предварительно беря lease той же сессией в фикстуре. Смысл снимка («БД не меняется») при этом обойдён: запись «lease взят» остаётся.
2. **AC-9 через особый случай.** Чтобы получить ожидаемый префикс текста, исполнитель может поставить в `merge_after.check` раннюю ветку «начинается с `E` → `_reason(item, …)`». Формально это «та же проверка», но значение получает отдельный путь в общем узле проверки `merge_after`, которым пользуются и гейт SPEC, и каналы переписывания (`merge_after.py:185-194`).
3. **Членство родителя при `--as-epic`.** SPEC.md:36 и AC-12 говорят только о частях. Если родителя в эпик не включать, ребро `parent` (AC-21) повиснет на узле вне `nodes`, а «части слиты N/M у поделённой задачи эпика» (SPEC.md:57) у эпиков, созданных через `--as-epic`, не появится никогда. Оба варианта проходят AC-12.
4. **Заголовок группы без имени эпика.** Требование 13 (SPEC.md:57) не требует id или названия эпика в заголовке. Заголовок из одних чисел проходит AC-26, и группы разных эпиков в `status` не различить. AC-25 этого не ловит: он сам предполагает, что название в выводе есть.
5. Не заданы: `epic add` задачи, уже состоящей в другом эпике (молчаливый перенос или отказ); `epic remove` задачи из чужого эпика; дедупликация объединения ТЗ и `--after`, когда один источник даёт префикс, а другой полный id (`check` отвергнет как «повтор», `merge_after.py:167-168`); `--after` без `--epic`. Каждый вариант проходит текущие AC.
