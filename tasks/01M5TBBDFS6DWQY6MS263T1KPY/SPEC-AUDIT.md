- Псевдо-`task_id` в журнале — существующий приём: `report._all_steps` отбирает записи только известных задач (`orchestrator/report.py:155-164`), `watch` обращается к задачам через `tasks_by_id.get`/фильтр (`orchestrator/watch.py:412-415`, `:712-715`) — записи журнала с `task_id` = id эпика их не роняют.

Не учтено SPEC:
- Утверждение треб. 1 «признак „догон нужен“ — отсутствие колонки `tasks.epic_id`, поэтому и при параллельном догоне … запись журнала одна» по коду не следует: проверка колонки и `ALTER TABLE` в `add_column` не атомарны (`orchestrator/schema.py:173-180`), и это прямо задокументировано как гонка «duplicate column name» при параллельных `store.db()` (`tests/test_store_schema_migration_parity.py:4-8`). Два процесса на старой БД оба видят «колонки нет»: второй либо падает на `ALTER`, либо (если ALTER обёрнут) оба пишут запись журнала. Одна запись получится только при проверке+ALTER+записи под одной транзакцией записи (`BEGIN IMMEDIATE`, как в `orchestrator/lease.py:137`) — SPEC этого не требует.
- `lease.run_locked` на id эпика проходит через `acquire`, а ветка «своя сессия держит lease другим процессом» зовёт `store.get_task(conn, task_id)` (`orchestrator/lease.py:217-231`, вызов `:162`); для id эпика это `sys.exit("Задача E… не найдена…")` вместо текста отказа lease. `lease.py` — только чтение (ТЗ), SPEC случай не называет; AC-18 покрывает только чужую сессию.

## Пути обхода гейтов
1. **AC-29, эталон «на шаге developer».** Планка фиксируется на выходе `tests_writing` (`tests_locked_sha`, `orchestrator/schema.py:207-211`; правка зафиксированной планки — только `amend-tests`, ADR-0012). SPEC требует, чтобы эталон текста `status` в тест вписал разработчик (решение №2 п. 12), но не называет канала: либо правка зафиксированного файла (откажет гейт), либо эталон, снятый разработчиком с собственного кода, — тогда AC-29 сверяет код с самим собой и не ловит изменение вывода без эпиков. Нужен явный путь: эталон снимается кодом `main` после мержа Э0 и вносится через `amend-tests` с проверкой Оператора (или тест строит эталон без кода Э1). Это решение гейта, не аналитика.
2. **AC-34 последовательными вызовами.** Буквально «два вызова `migrate` на двух соединениях» проходит последовательный тест; гонка параллельного догона (`orchestrator/schema.py:173-180`, `tests/test_store_schema_migration_parity.py:4-8`) остаётся неловленной, а треб. 1 обещает одну запись. Нужно требование транзакции записи вокруг проверки+ALTER+журнала (или перехвата `duplicate column name` с повторной проверкой) и критерий с перемежением (второе соединение проверяет колонку до коммита первого).
3. **`--as-epic` и мягкие отказы гейта SPEC.** `_approve_spec_gate` после чтения SPEC может мягко отказать (`orchestrator/fsm.py:1201-1287`: аудит `fail`, пути, `merge_after`, «Меняемое поведение») — `return` после записи журнала. SPEC не говорит, что эпик заводится только вместе с частями деления; реализация «завести эпик до `_approve_spec_gate`» проходит AC-12/AC-13 и оставляет пустой эпик при мягком отказе. Кроме того, признак «с делением» для отказа до lease требует прочитать SPEC до `run_locked`; штатный узел чтения `_read_branch_text_or_refuse` сам пишет журнал при сбое (`orchestrator/fsm.py:1220-1224`) — запись до lease, противоречащая треб. 7. Нужна строка: эпик заводится в той же ветке, что `_spawn_division_subtasks` (`orchestrator/fsm.py:1333-1336`), предварительная проверка деления журнала не пишет.

## Вердикт
concerns — SPEC можно вести на гейт; отклонения решаемы Оператором:

1. Треб. 1 / AC-34: «одна запись при параллельном догоне» не следует из признака «нет колонки» — `orchestrator/schema.py:173-180`, `tests/test_store_schema_migration_parity.py:4-8`; AC-34 не требует перемежения и пропускает гонку. 2. AC-29: эталон, вписываемый разработчиком в зафиксированную планку, — нет канала (`orchestrator/schema.py:207-211`, ADR-0012) и риск самосверки. Предложение: назвать путь `amend-tests` с эталоном, снятым кодом `main` после Э0.
3. Треб. 4 / AC-18: `lease.run_locked` на id эпика в ветке «своя сессия, другой процесс» падает текстом «Задача E… не найдена» (`orchestrator/lease.py:162`, `:226`; так же `warn_foreign_live`, `:320`); `lease.py` — только чтение. Предложение: принять как известное ограничение либо потребовать в `epics.py` проверку до `run_locked`.
4. Треб. 7 / AC-12–AC-13: не сказано, что эпик заводится только вместе с частями деления (мягкие отказы `orchestrator/fsm.py:1201-1287`), и что предварительное чтение SPEC для отказа до lease журнала не пишет (`orchestrator/fsm.py:1220-1224`).
5. Треб. 4 / AC-30: запись журнала `epic show` не покрыта критерием.
6. Треб. 10: источник `pin` не назван; пин не в БД (`orchestrator/watch.py:354`), критерия на значение нет. Мелкое.
