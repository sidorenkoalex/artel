# Эпики, шаг Э1: эпик — сущность пульта, команды эпика и модель доски для status и epic show

## Факты

ADR-0028 (принят 25.10.2026), уровень 1, п. 4–7 и п. 12; шаг Э1 после Э0 (01M5TB6VDVV6AM8DWPGVQE8CDW — признак `closed_as`, один список состояний `fsm.STATES`).

1. Сейчас линии задач нет в БД: `status` — строка на задачу (`orchestrator/catalog.py:982` `cmd_status`), группировка только по проекту; `report` — HTML-доска, колонки — состояния (`orchestrator/report.py:46`). Каталоги области проекта — `config.PROJECT_DIRS` (`orchestrator/config.py:61`).
2. Деление на гейте SPEC заводит части (`orchestrator/fsm.py:958` `_spawn_division_subtasks`); после Э0 родитель получает `closed_as='divided'`.
3. Зависимость мержа задаётся строкой ТЗ «Порядок: после …» и проверяется `merge_after.check` (`orchestrator/merge_after.py`).

## Требуется

1. **Данные.** Таблица `epics`: `id` (приставка `E` + формат идентификатора пульта; не совпадает с префиксами задач в поиске и в `--after`), `project`, `title`, `goal`, `envelope_usd` (необязательно; используется шагом Э2а), `state` (`open` | `closed`), `outcome`, `created_at`, `closed_at`. Колонка `tasks.epic_id` (необязательно). Эпик принадлежит одному проекту; задача эпика — того же проекта (проверка при привязке). Миграция схемы с записью журнала. Каталог `epics` — в `config.PROJECT_DIRS`.
2. **Команды** (все — через `lease.run_locked`, с записью журнала):
   - `epic new <проект> "<название>" --goal "<цель>" [--envelope N]`; `epic show <id>`; `epic edit <id> [--title …] [--goal …]`; `epic close <id> "<итог>"`;
   - `new "<название>" --tz <файл> --target <проект> --epic <id> [--after <id>[,<id>…]]` — `--after` записывает `merge_after` той же проверкой, что строка «Порядок: после …» ТЗ;
   - `epic add <id> <задача>`, `epic remove <id> <задача>` — для заведённых задач;
   - привязка к закрытому эпику или к эпику другого проекта — отказ с причиной.
3. **Деление и эпик.** Части деления наследуют эпик родителя. `approve <id> --as-epic` на гейте SPEC с делением у задачи без эпика создаёт эпик из родителя: проект — проект задачи; название — название задачи; цель — первый абзац раздела «Контекст» SPEC родителя; конверт — не задан; части — задачи нового эпика; у родителя `closed_as='divided'` и запись журнала со ссылкой на эпик. `--as-epic` без деления или у задачи в эпике — отказ. Без флага — прежнее деление.
4. **Закрытие — только Оператор.** `epic close` при задачах эпика не в окончательных состояниях (`fsm.TERMINAL_STATES`) — отказ с их перечнем. Когда все задачи эпика окончательны, `status` и `epic show` показывают «эпик готов к закрытию»; сам эпик не закрывается.
5. **Модель доски.** Модуль `orchestrator/board.py`: функция строит модель проекта из БД и журнала — словарь с `schema_version`, без обращения к хостингу и сети: `project`, `generated_at`, `pin`, `columns` (= `fsm.STATES`), `epics` (идентификатор, название, цель, конверт, потрачено, счётчики по состояниям, узлы и рёбра: `merge_after`, родитель–часть), `cards` (задача, название, эпик, состояние, `closed_as`, `waiting_on` ∈ {`operator`, `ci`, `dependency`, `role`, пусто}, зависимости, потрачено/потолок, ветка, время последнего события). Модель доски БД не пишет.
6. **Показ из модели.** `status` группирует задачи по эпикам: заголовок — `потрачено / конверт` (или «без конверта»), счётчики по состояниям, «части слиты N/M» у поделённых, «эпик готов к закрытию»; затем строки задач в порядке зависимостей; задачи без эпика — прежним списком (вывод для проекта без эпиков не меняется). `epic show <id>` — таблица: задача, родитель, от чего зависит, состояние, кто держит (`waiting_on`), потрачено/потолок, итог. Оба вида строятся из модели `board.py`.

Критерии приёмки:
- `epic new` / `show` / `edit` / `close` / `add` / `remove` работают; привязка задачи другого проекта или к закрытому эпику — отказ;
- `new --epic E… --after <id>` — задача в эпике, `merge_after` записан; несуществующий id в `--after` — отказ;
- деление задачи в эпике — части в том же эпике; `approve --as-epic` у задачи без эпика — новый эпик с целью из «Контекст» SPEC, части в нём, `closed_as='divided'` у родителя; `--as-epic` без деления — отказ;
- `epic close` при незакрытой задаче — отказ с её id; после окончательных состояний всех задач — «готов к закрытию» в `status`, сам эпик `open`;
- модель `board.py`: `columns == fsm.STATES`; `waiting_on='operator'` у задачи в `spec_gate`, `merge_gate`, `escalated`; повторный вызов без изменений БД даёт ту же модель (кроме `generated_at`); модель не пишет в БД (сверка числа изменений соединения);
- `status` проекта без эпиков — вывод без изменений (сверка с текущим выводом на фикстуре).
