# SPEC: Этап 3 ADR-0021, часть 3 из 3: прочие развилки, сторож и сквозной тест внешнего потока

## Контекст

ADR-0021 (пп. 8, 9, 12, 13) требует на этапе 3 удалить развилки
`target == DEFAULT_TARGET`: артель должна идти по общему потоку, как любой
проект. Части 1 и 2 этапа слиты (последняя — 01M45FK56DWMNBRKA1VWM12H19,
06.10). Они ввели профиль тестов проекта и перечень защищённых путей
проекта и сняли 16 развилок проверок пункта 8. Осталось 28 прочих развилок
поведения. ТЗ насчитало их на пине 6eb98eff. Сверка по `main` 4d6f5b77
нашла все 28 со сдвинутыми номерами строк и одну сверх перечня
(`orchestrator/fsm.py:912`). Кроме того, нет сторожа против новых развилок
в модулях проверок и ни разу не прогонялся сквозной путь внешнего проекта.
Эта часть закрывает этап: решает судьбу оставшихся развилок, добавляет
сторожа и сквозной тест внешнего потока, а карту кодовой базы приводит к
описанию всех трёх частей.

## Критерии приёмки

AC-1. Пусть две задачи одного внешнего проекта имеют пересекающиеся зоны и
одна из них уже занимает зону. Тогда вторая в `in_dev` получает конфликт
замка зон, `run` ей отказывает, а `status` показывает позицию в очереди
этой зоны. Пусть две задачи разных проектов имеют одинаковые пути зон.
Тогда они друг друга не блокируют.

AC-2. `new` внешнего проекта с зонами, пересекающими зоны живой задачи того
же проекта, пишет в журнал и выводит предупреждение о пересечении. Задача
внешнего проекта до `in_dev` получает в `status` добавку
«[зона занята: <id>]», когда её зону занимает задача того же проекта.

AC-3. Стоп-кран волны срабатывает от отказов задач внешнего проекта наравне
с задачами артели: в порог `config.WAVE_BREAKER_TASKS` идут задачи всех
проектов. Пока алерт волны открыт, `run` задачи внешнего проекта
отказывает записью `WAVE_BREAKER_REFUSAL_ACTION`, а `status` помечает её
«СТОП-КРАН ВОЛНЫ».

AC-4. После отказа git на коммите пульта незакоммиченный результат шага в
рабочей копии задачи внешнего проекта отказывает переходу из агентского
состояния (`_dirty_refuses`) и выходу из `tests_writing` так же, как у
задачи артели.

AC-5. Переход FSM задачи артели добавляет строку паспорта в её ссылку
документов `refs/artifacts/<id>` так же, как у задачи внешнего проекта.

AC-6. Запись журнала «sha зафиксирован» у задачи артели и у задачи внешнего
проекта имеет один формат и несёт поля `код=` и `артефакты=`.
`review.previous_verdict_sha` по-прежнему находит базу по полю `код=` у
обоих.

AC-7. В `orchestrator/fsm.py` нет собственного разрешения remote и базы
проекта. Подтяжка и мерж задачи внешнего проекта, чья запись `targets.yaml`
не читается, не идут на `origin` пульта: они деградируют так же, как при
неответившем git. Для артели при сломанном `targets.yaml` remote остаётся
`origin`, а база — `config.MAIN_BRANCH`.

AC-8. `show` задачи артели печатает статусы артефактов из ссылки документов:
если файл `tasks/<id>/SPEC.md` на диске `config.TASKS` несёт другой
`status`, чем в ссылке, печатается статус ссылки.

AC-9. `docs --fetch-all` заводит клон проекта из `targets.yaml`, у которого
клона ещё нет, и подтягивает его ссылки документов.

AC-10. На входе в `merge_gate` у задачи внешнего проекта заполняется
`diff_bytes` — размер диффа ветки задачи против базы в репозитории её
проекта.

AC-11. Гейт «замечания ревью не отработаны» отказывает задаче внешнего
проекта в `in_dev`, когда REVIEW.md несёт `status: changes_requested`, а
кодовая ветка после вердикта не получила коммита разработчика.

AC-12. `doctor` у задачи артели сверяет свежесть ветки с `origin/main` клона
после `fetch`. Ветка, отставшая от `origin/main` больше чем на
`config.STALE_BRANCH_WARN_COMMITS` коммитов, получает предупреждение, даже
когда локальная `main` клона не продвинута.

AC-13. Оставленные развилки требования 1 (строки 16, 18, 19, 21, 24, 25, 28,
29) узнают артель через функцию-признак `orchestrator/repo_context.py`.
Если подменить признак так, чтобы он отвечал «артель» для внешнего проекта,
каждая из этих развилок для внешнего проекта меняет ветку поведения на
ветку артели.

AC-14. Сторож из `tests/` проходит на ветке задачи. Если в любой модуль
`orchestrator/advance_gates/*.py` или в `orchestrator/fsm_merge_gate.py`
добавить сравнение с `config.DEFAULT_TARGET` (`==`, `!=`, `in`, `not in`),
сторож падает и называет файл и строку этого сравнения.

AC-15. Сквозной тест в песочнице проходит на внешнем проекте с голым
репозиторием `origin` и профилем тестов:
(а) гейт зон отказывает на файле вне зон;
(б) правка пути из `no_paths` проекта получает отказ;
(в) удаление теста без мандата получает отказ гейта неослабления;
(г) новый тест без «Ловит мутацию:» получает отказ гейта заявки мутации;
(д) `approve` на гейте мержа задачи, тронувшей защищённый путь проекта,
переводит её в `escalated`.

AC-16. Тот же проект без профиля тестов: удаление теста и новый тест без
заявки отказов неослабления и заявки мутации не получают, а журнал задачи
несёт запись о пропуске языковых проверок. Гейт зон отказывает на файле вне
зон, правка пути из `no_paths` получает отказ, а мерж задачи с защищённым
путём эскалирует.

AC-17. В `docs/codebase-map.md`, пересобранной `scripts/codebase_map.py` по
ветке задачи, строки «Назначение» модулей называют три вещи: профиль тестов
проекта, перечень защищённых путей проекта и сверку проверок пункта 8 с
репозиторием проекта (`repo_context`).

Класс задачи по калибровке — больше 15 критериев и 8 и более файлов, то
есть ~85. Миссия шага разрешает ставить `budget_usd` только вниз от дефолта
оркестратора ($50), поэтому стоит $50 при рамке ТЗ $40. Потолок задач
группы 3 по решению Оператора 05.10 — $100. Если $50 не хватит, потолок
поднимает Оператор командой `budget`. Этап 2 при рамке $60 потратил $155.

**Обоснование монолита** (материал для решения Оператора):
- Этап 3 уже поделён Оператором на три части 05.10, это последняя.
- Сторож (требование 3) нельзя отделить от требования 1. Строка 26
  (`advance_gates/review.py:355`) — прямое сравнение внутри модуля, который
  стережёт сторож. Без её удаления сторож красен на `main`, поэтому часть
  «сторож» отдельно немержима.
- Требование 2 и строки «оставить» требования 1 — одна правка тех же мест.
- Отделимы требования 4–6: сквозной тест опирается на механику частей 1–2,
  уже слитых, а не на правки требования 1, и карта тоже. Возможная нарезка:
  (1) требования 1–3, 7–8; (2) требования 4–6. Против неё: вторая часть
  повторила бы постоянные шаги analyst/test_author/review (~$15–20) ради
  двух тестов и правки докстрингов. Кроме того, в требовании 5 задача без
  профиля проходит через ту же рабочую копию внешнего проекта, которую
  меняют строки 12–13, поэтому сквозной тест полезен как проверка
  требования 1 в том же мерже.
