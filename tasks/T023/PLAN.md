# PLAN: A4 — роль test_author: приёмочные тесты до кода

## Подход

Новое состояние `tests_writing` встраивается между `spec_gate` и `in_dev`
тем же приёмом, каким уже устроены остальные состояния: роль читается
из `roles.yaml`, привязка состояние→роль — одна строка в
`config.STATE_ROLE`, промпт роли — миссия в `runner.cmd_run`. `auto`,
`doctor` (обход токенов ролей) и `cmd_status` уже читают `STATE_ROLE`
generically — им правка не нужна.

**AC-разметка и её версия.** SPEC несёт нумерацию критериев `AC-<n>.`
в разделе «Критерии приёмки» и необязательное поле `skip_tests` во
frontmatter. Чтобы не трогать T001–T022 (требование 7), правило
привязано к `schema_version`: guard требует AC-разметку только у SPEC
`schema_version >= 2` без `skip_tests`; версия 1 (весь предыдущий
беклог, включая само T023 — его SPEC писался до этой задачи) остаётся
валидной без правок. Тот же предикат (`schema_version>=2` и без
`skip_tests`) решает и маршрут на `approve` из `spec_gate`: помечен
`skip_tests` или версия SPEC ниже 2 — сразу в `in_dev`, причина в
журнале (требование 1); иначе — в `tests_writing`. `SUPPORTED_SCHEMA_VERSION`
в guard.py поднимается до 2.

**Трассируемость AC→тест — без второго документа.** Единственный
источник для FSM — `tasks/<id>/acceptance_tests/*.py` статическим
разбором текста (regex), без импорта/исполнения файлов: тот же принцип,
которым `scripts/guard.py` уже проверяет структуру, не содержательность.
Три текстовых соглашения, все внутри тестовых файлов (без нового типа
артефакта — «второй документ-сводка» из требования 3 не заводится):
- тест на AC-n — метод `def test_ac<n>_...` в любом `test_*.py`;
- критерий без прямого теста — комментарий `# AC-n: manual — <причина>`
  (проверит Оператор на приёмке) или `# AC-n: skip — <причина>`;
- критерий, который тестом в принципе не выразить, — `# AC-n: escalate —
  <вопрос>`: FSM переводит задачу в `escalated` с `escalated_from=
  tests_writing` НЕ дожидаясь общей ошибки трассируемости (требование 4,
  «неисполнимость — эскалация, не тихий skip»).

Парсер и три вспомогательные функции (`scan_acceptance_tests`,
`acceptance_traceability_errors`, `spec_ac_errors`) живут в
`scripts/guard.py` — рядом с уже существующей структурной проверкой SPEC,
одним источником для обеих сторон трассируемости (SPEC-разметка и
покрытие тестами). Выполнение тестов (требование 6, реальный прогон
`unittest`) — отдельный модуль `orchestrator/acceptance.py`: guard.py
принципиально не исполняет содержимое файлов (докстринг модуля), а
прогон гейта обязан именно исполнить. `acceptance.py` переиспользует
разбор пометок из guard.py для сводки — одно число, а не два разных
источника счёта.

**Лок acceptance_tests/ — существующая фиксация T021, без новой
инфраструктуры.** У задачи заводится колонка `tasks.tests_locked_sha`:
в момент успешного выхода `tests_writing → in_dev` она получает то же
значение, что `set_state` уже посчитал в `fixed_sha` (текущий HEAD
догфуда на этот момент — коммит test_author, если тот дописал работу
как предписано миссией). На переходе `in_dev → review` код сверяет
`git diff --quiet <locked> HEAD -- tasks/<id>/acceptance_tests` (новая
`gitcmd.diff_paths`): расхождение — отказ перехода с причиной «спор
с тестом = эскалация», без побочных эффектов (задача остаётся в
`in_dev`, как и любой другой отказ `guard_refuses`). Правка теста
Оператором через возврат в `tests_writing` (требование 5, вторая
половина) — не новая команда: `tests_locked_sha` перезатирается на
следующем успешном выходе из `tests_writing`, ручной перевод туда
средствами, которые уже есть у Оператора (прямая правка `state` —
вне зоны кода этой задачи, как и раньше для аналогичных случаев).

**Прогон приёмки на review→acceptance.** `acceptance.run(tdir)`
детерминированно гоняет `python3 -m unittest discover` по каталогу;
красный — отказ перехода тем же стилем, что и остальные отказы FSM
(журнал + печать хвоста, разработчик чинит код). Зелёный — печатает
и журналит `acceptance.summary(tdir)` (число тестов через
`TestLoader.discover(...).countTestCases()` — «сбор, не запуск»,
требование 3 — и список manual-критериев) непосредственно перед
переходом в `acceptance`: это и есть «карточка гейта», Оператор видит
её в выводе `advance`/`auto` и в журнале (`log <id>`), отдельного
хранилища не заводится. Задачи без `acceptance_tests/` (skip_tests,
либо старше T023) — `run()` возвращает «зелено» вырожденно, переход
не блокируется.

**Эскалация test_author.** Требование 8 прямо предписывает «уже
существующую механику `escalated_from`»: `STATE_ROLE["tests_writing"] =
"test_author"` — и упавший/исчерпавший ретраи агент уже уводится в
`escalated` с `escalated_from="tests_writing"` тем же кодом
`runner.cmd_run`, что и для любой другой роли (менять `runner.py` для
этого пути не нужно). Второй путь эскалации — содержательный (маркер
`escalate`, см. выше) — код FSM, а не runner: агент завершается штатно
(rc=0), но контент говорит «не могу», и это ловит `cmd_advance`.

**Роль и скил.** `roles.yaml` получает `test_author` (executor: agent,
свой token_slot `artel-test-author`, skills: conventions-core,
escalation-rules, test-authoring). Новый скил `skills/test-authoring.md`
формулирует три правила роли текстом промпта (только из критериев SPEC,
AC-n → тест/manual/skip, неисполнимость → escalate, не трогать код
и SPEC). Правки `roles.yaml`/`templates/`/`skills/` — protected-paths
(`.github/workflows/ci.yml`, job `protected-paths`, warning в Фазе 0):
SPEC T023 требование 1 явно называет эту зону и просит ревьювера
проверить состав отдельно — не блокер для кода, диф по этим путям
исчерпывается перечисленным (одна роль, один скил, разметка шаблона).

**Триггер и инварианты.** Новая строка в `docs/triggers.md` (после №20):
условие «>1 эскалации `escalate` на задачу по первым 5 задачам с
tests_writing» → механика меняется на «правка теста через ревью»
(наблюдаемый сигнал — счётчик действия `эскалация: критерий неисполним
тестом` в журнале по target). `docs/invariants.md` получает две новые
строки (#26, #27): трассируемость AC на выходе из `tests_writing` и лок
`acceptance_tests/` — оба уже кодированы новыми тестами ниже.

## Шаги

1. **schema_version 2 + AC-разметка SPEC.** `templates/SPEC.md`
   (`schema_version: 2`, раздел «Критерии приёмки» → `AC-n.`, закомменченное
   поле `skip_tests`). `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION = 2`,
   `requires_ac_markup(meta)`, `spec_ac_errors`, встроены в `check()`.
   Тесты: guard принимает валидную v2-разметку, отклоняет v2 без
   AC-n/с дублями/со старой нумерацией, пропускает v1 и v2+skip_tests
   без разметки; `guard.py --all` зелёный на T001–T022 без правок.
2. **roles.yaml + skills/test-authoring.md.** Роль `test_author` заведена,
   `roles.skills("test_author")` и `roles.token_slots("test_author")`
   читаются без ошибки (тест по образцу существующих на `roles.py`,
   если для новой роли нет — не заводить лишний, roles.py уже общий).
3. **Состояние tests_writing + маршрут из spec_gate.** `config.STATE_ROLE`,
   `fsm.cmd_approve` (spec_gate: skip_tests/версия → in_dev, иначе →
   tests_writing), `runner.cmd_run` (миссия test_author). Тест FSM
   (критерий приёмки 1): непустой SPEC v2 идёт через tests_writing;
   skip_tests и SPEC v1 — в in_dev напрямую, причина в журнале.
4. **Трассируемость AC→тест на выходе tests_writing.** `guard.
   scan_acceptance_tests`, `guard.acceptance_traceability_errors`,
   ветка `fsm.cmd_advance` для `tests_writing` (включая маршрут
   `escalate`→`escalated`). Тесты (критерий приёмки 2): AC-2 без
   теста/пометки — отказ с «AC-2» в сообщении; с `manual` — проходит;
   `escalate` — эскалация с `escalated_from=tests_writing`; лишняя
   пометка/тест на несуществующий AC-n — отказ.
5. **Лок acceptance_tests/.** Колонка `tasks.tests_locked_sha`
   (`store.py`: SCHEMA + `migrate`), `gitcmd.diff_paths`, запись
   `tests_locked_sha` при выходе из `tests_writing`, сверка в
   `fsm.cmd_advance` на `in_dev → review`. Тест (критерий приёмки 3,
   реальный git — по образцу `tests/test_git_fixation.RealPultGitTest`):
   правка залоченного файла после выхода — отказ с «эскалация» в
   причине; нетронутые тесты — переход проходит.
6. **Прогон приёмки на review→acceptance.** `orchestrator/acceptance.py`
   (`run`, `summary`), встройка в `fsm.cmd_advance` (review, status
   approved). Тест (критерий приёмки 4): красный acceptance-тест —
   отказ перехода; зелёный — переход и сводка (число/manual/skip)
   в выводе и журнале.
7. **Эскалация test_author → tests_writing.** Тест (критерий приёмки 5,
   по образцу существующих в `tests/test_agent_failure.py`): агент роли
   test_author падает во всех попытках → `escalated`,
   `escalated_from=tests_writing`; `approve` возвращает в `tests_writing`.
8. **docs/triggers.md + docs/invariants.md.** Новая строка триггера
   (после №20) и две строки инвариантов (#26, #27) со ссылками на новые
   тестовые классы.
9. **Регрессия и мутационные проверки.** Полный прогон
   `python3 -m unittest discover -s tests` (в т.ч. без `claude` в PATH —
   уже покрыто существующим стилем песочниц), `python3 scripts/guard.py
   --all`. Мутационные проверки новых отказов (см. «Влияние на систему»):
   вручную откатить каждую новую защиту и убедиться, что кодирующий её
   тест краснеет, затем вернуть.

## Влияние на систему

**Protected-paths (зона Оператора).** Диф трогает `roles.yaml`
(добавлена роль `test_author`, существующие роли не тронуты),
`templates/SPEC.md` (bump `schema_version`, разметка «Критерии приёмки»,
закомменченное поле — существующие поля не тронуты), `skills/`
(добавлен один файл `test-authoring.md`, существующие скилы не тронуты).
Это явно предписано SPEC T023 требованием 1 («Правки roles.yaml/skills/
templates — зона Оператора: подсветятся protected-paths, ревьюеру
проверить состав отдельно») — не самовольное расширение зоны задачи.
`protected-paths` в CI (`.github/workflows/ci.yml`) даёт warning, не
блокирует (Фаза 0). `.github/` и `gates.yaml` не трогаются.

**Инварианты и защиты — не ослабляются, добавляются.** Новый код не
трогает ни один из 25 существующих пунктов `docs/invariants.md`, ни один
существующий тест `test_invariants.py`/`test_git_fixation.py`/
`test_multitarget_invariants.py`. Существующая фиксация T021
(`fixation.fix/read/check_integrity`) переиспользуется КАК ЕСТЬ — новая
колонка `tests_locked_sha` читает уже посчитанный `fixed_sha`, не меняя
семантику `fix()`/`check_integrity()`. Guard остаётся структурным
(не исполняет содержимое) — принцип модуля не нарушается новыми
функциями (`acceptance_traceability_errors` и `scan_acceptance_tests`
регулярными выражениями по тексту, без импорта .py файлов). Добавляются
две новые строки в реестр инвариантов (#26 трассируемость, #27 лок) —
только Оператор вправе их снять, обычным путём ADR.

**Обратная совместимость.** T001–T022 (`schema_version` 1 или без поля)
проходят `guard.py --all` без единой правки: правило AC-разметки
условно на `schema_version>=2`. Задачи, уже находящиеся в `in_dev`/
`review`/… на момент мержа этой ветки (если такие есть), не имеют
`tests_locked_sha` (колонка NULL по миграции) — проверка лока
пропускается тем же приёмом, что и вырожденный случай отсутствия
фиксации в `fixation.py` («сверять не с чем»); они продолжают путь как
раньше. `guard.py --all` не проверяет `acceptance_tests/` каталоги
(они не `.md`-файлы под `tasks/**`) — трассируемость остаётся проверкой
момента перехода FSM, не команды CLI, во избежание неожиданного
покраснения `--all` на исторических каталогах.

**Откат.** Вся правка — новый код и два protected-пути с точечными,
перечисленными изменениями; отката единой операцией не требует —
`git revert` коммита(ов) ветки возвращает FSM к состоянию до T023
(состояние `tests_writing` просто перестаёт быть достижимым, роль
`test_author` — упоминаемой; уже созданные каталоги `acceptance_tests/`
у задач, прошедших tests_writing до отката, остаются на диске как
история, но код перестаёт их читать — те же гарантии, что и у любого
другого отката кода в этой системе).

## Риски

- **Регулярка вместо разбора Python.** `scan_acceptance_tests` читает
  текст файлов, а не импортирует их: агент-test_author технически может
  обмануть парсер (закомментировать маркер внутри строки, а не как
  реальный комментарий). Это тот же класс риска, что и у остальных
  структурных проверок guard — содержательность ловит ревью
  (review-checklist уже требует читать diff), не эта задача.
- **Одна фиксация на весь tasks/<id>.** `_fix_dogfood` считает чистоту
  по всему каталогу задачи (T021, известное ограничение гранулярности),
  не только по `acceptance_tests/`: `tests_locked_sha` наследует то же
  ограничение — лок технически завязан на HEAD всего репозитория в
  момент перехода, а не на sha конкретного поддерева. Для догфуда с
  последовательной разработкой (одна активная задача) это не создаёт
  ложных срабатываний; ложный отказ возможен только если ДРУГАЯ задача
  того же target закоммитит что-то между выходом из tests_writing и
  входом в review — маловероятно при текущей дисциплине одной активной
  задачи за раз, тот же риск уже принят в T021.
- **`unittest discover` без тестов возвращает rc=0.** Если test_author
  оставит все AC на `manual`/`skip` (без единого реального теста),
  трассируемость это пропустит (у каждого AC есть пометка), а прогон
  на review→acceptance будет тривиально зелёным. Это соответствует
  SPEC буквально (требование 3 разрешает manual/skip как валидный
  исход) — не дефект этой задачи, а следствие принятой модели; если
  окажется избыточно мягким на практике — предмет отдельного тикета,
  не блокер здесь.
