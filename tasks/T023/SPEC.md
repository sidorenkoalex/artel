# SPEC: A4 — роль test_author: приёмочные тесты до кода

## Контекст

Шестая задача фазы A (roadmap §2 A4). Сейчас приёмка — глаза
Оператора по критериям SPEC: критерии написаны текстом, исполняемой
формы у них нет, и конвергентная галлюцинация dev+reviewer (реестр
v5 №1) ничем машинным не ловится. A4 вводит исполняемую приёмку
до кода: отдельная роль пишет тесты из критериев SPEC раньше, чем
разработчик увидит задачу, и эти тесты лочатся — разработчик пишет
код под неизменяемую планку, а не планку под код.

## Требования

1. **Состояние `tests_writing`** между spec_gate и in_dev; исполняет
   роль `test_author` (roles.yaml: executor agent, свой token_slot,
   скилы — conventions-core, escalation-rules + новый скил
   test-authoring). Правки roles.yaml/skills/templates — зона
   Оператора: подсветятся protected-paths, ревьюеру проверить состав
   отдельно.
2. **AC-разметка SPEC**: шаблон SPEC получает нумерацию критериев
   (AC-1, AC-2, …) и явное поле скипа стадии (`skip_tests: <причина>`
   во frontmatter — стадия пропускается, факт и причина в журнал).
   Старые SPEC (T001–T022) остаются валидными: guard требует
   AC-разметку только у задач, проходящих tests_writing.
3. **Выход роли**: `tasks/<id>/acceptance_tests/` — тесты unittest
   ТОЛЬКО из критериев SPEC (никаких тестов на нереализованные
   фантазии сверх AC); каждый AC-n → тест(ы), либо пометка
   `manual` (проверяет Оператор руками на acceptance), либо `skip`
   с причиной. Сводка кейсов — из collect-only (unittest discover),
   отдельный документ-сводка не заводится.
4. **Трассируемость на выходе из tests_writing** (advance): AC-n
   без теста и без пометки manual/skip = невалидный выход — отказ
   перехода с именем критерия. Неисполнимость критерия тестом =
   эскалация (вопрос Оператору), не молчаливый skip.
5. **Лок**: после выхода из tests_writing файлы acceptance_tests/
   залочены — изменение детектируется сверкой фиксации T021 (sha
   каталога/файлов на переходах); диф в залоченных тестах у
   разработчика = отказ перехода in_dev → review с причиной «спор
   с тестом = эскалация». Правка залоченного теста = правка SPEC =
   только Оператор (через возврат в tests_writing решением
   Оператора).
6. **Прогон приёмки**: на переходе review → acceptance оркестратор
   прогоняет acceptance_tests задачи детерминированно (unittest);
   красный прогон = отказ перехода (разработчик чинит код, не тест);
   зелёный — сводка (пройдено / manual / skip) печатается в карточку
   гейта acceptance вместе со списком manual-критериев Оператору.
7. **Триггер пересмотра лока** — строка в docs/triggers.md:
   в среднем >1 эскалации «спор с тестом» на задачу по первым 5
   задачам с tests_writing → механика меняется на «правка теста
   через ревью» (наблюдаемый сигнал — счётчик эскалаций из журнала,
   вычислимый).
8. Маршрут эскалаций: возврат из эскалации test_author — в
   tests_writing (по механике escalated_from, уже существующей).

## Критерии приёмки

1. Тест FSM: новая задача с непустым SPEC проходит spec_gate →
   tests_writing → in_dev; с `skip_tests` — spec_gate → in_dev
   напрямую, причина в журнале.
2. Тест: выход из tests_writing с AC-2 без теста и без пометки —
   отказ с «AC-2» в сообщении; с пометкой manual — проходит.
3. Тест лока: правка файла в acceptance_tests/ после выхода
   из tests_writing — отказ перехода in_dev → review с причиной;
   нетронутые тесты — проходит.
4. Тест прогона: красный acceptance-тест — отказ перехода review →
   acceptance; зелёный — сводка и manual-список в выводе гейта.
5. Тест: эскалация test_author возвращается в tests_writing.
6. Строка триггера в docs/triggers.md с наблюдаемым сигналом.
7. Шаблон SPEC несёт AC-разметку и skip_tests; guard --all зелёный
   на всей истории T001–T022 без правок старых артефактов.
8. Все существующие тесты зелёные (в т.ч. без claude в PATH — среда
   CI); мутационные проверки новых инвариантных отказов — в PLAN.
9. Manual-критерий Оператора: прогон одной живой задачи-пустышки
   через tests_writing (test_author-агент реально пишет тесты
   из AC) — исполняется до approve acceptance этой задачи.

## Не входит

- Роль analyst и spec_writing (A5) — SPEC пишет Оператор, как сейчас.
- Verify-профили и C4 (verifier — пост-кодовая верификация).
- Изменение механики ревью и ревью-пакета (кроме отказа перехода
  по локу — п.5).
- Каталог acceptance_tests в CI-джобе репо (тесты задачи гоняет
  оркестратор на гейте, не CI пульта).
- Автоматическая правка старых SPEC под AC-разметку.
