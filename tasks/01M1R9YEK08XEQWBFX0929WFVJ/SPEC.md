# SPEC: Приёмка и мерж читают артефакты из артефактной ветки (регрессия №12)

## Контекст
После мержа регрессии №9 роли и брифы читают `tasks/<id>/` из АРТЕФАКТНОЙ
ветки, но два места пульта всё ещё доверяют диску/кодовой ветке. (1)
`approve` на гейте приёмки гоняет планку `tasks/<id>/acceptance_tests` из
worktree кодовой ветки — там этого каталога после регрессии №9 быть не
должно (роли чистят его по ходу шага), и текущий прогон трактует пустой/
непрочитанный результат как красную планку, эскалируя «приёмочные тесты
красные после подтяжки main» (наблюдалось на задаче 01M1QHQ277PQQA894X97RVEX9Y,
обход — ручная материализация Оператором). (2) Мерж переносит `tasks/<id>`
в main из кодовой ветки через обычный `git merge`, а CI-джоб `guard`
кодовой ветки валидирует именно эту (потенциально устаревшую) копию —
расхождение с артефактной веткой красило CI (наблюдалось на задаче
01M1PP0VYRT55WN8GGVG66X89Y, обход — ручная синхронизация Оператором).

## Требования
1. Прогон приёмочной планки на входе `approve` из состояния `acceptance`
   берёт `tasks/<id>/acceptance_tests/` из АРТЕФАКТНОЙ ветки задачи во
   временный каталог (`acceptance.materialize_from_branch`, как уже
   делает автогейт), не из worktree кодовой ветки; тот же источник — для
   любого другого места пульта, где сейчас планка гоняется из worktree, в
   частности прогон планки внутри узла сверки свежести ветки (общий для
   approve `acceptance` и окна `merge_gate`).
2. Материализация из артефактной ветки не находит `acceptance_tests/` там,
   где задача НЕ пропустила `tests_writing` легитимно (`skip_tests` не
   задан в SPEC) — переход отклоняется именованным отказом «планка не
   найдена в источнике» (журнал + печать, состояние не меняется), а не
   трактуется ни как красная планка с эскалацией «приёмочные тесты
   красные после подтяжки main», ни как молчаливый зелёный проход. Задачи
   с легитимно пропущенным `tests_writing` (`skip_tests` задан либо SPEC
   без AC-разметки) по-прежнему проходят зелёным при отсутствии
   `acceptance_tests/` — существующее поведение здесь не меняется.
3. На переходе `merge_gate -> done` содержимое `tasks/<id>/`, которое
   попадает в main, — это снимок АРТЕФАКТНОЙ ветки на момент `approve` в
   `merge_gate`, а не то, что несёт кодовая ветка задачи через обычный
   `git merge`. Копия `tasks/<id>/` кодовой ветки (если она есть, legacy)
   не влияет на итоговое содержимое `tasks/<id>/` в main; расхождение
   между копией кодовой ветки и снимком артефактной ветки на момент merge
   журналируется предупреждением — не отказывает переходу и не
   эскалирует.
4. CI-джоб `guard` (`.github/workflows/ci.yml`) не валидирует `tasks/<id>/`
   кодовой ветки (`task/**`) как источник истины для живых задач: джоб
   пропускает проверку `tasks/<id>` на ветках `task/**` — источником
   истины для CI остаётся артефактная ветка (`artifact/**`), проверяемая
   своим собственным прогоном на пуше (синхронизация копии пультом на
   каждый пуш не выбрана — см. «Оценка объёма и деление»). Правка вносится
   диффом-приложением к PLAN.md по протоколу защищённых путей
   (`conventions-core`).
5. Существующее поведение автогейта acceptance (SPEC T066), материализации
   артефактов (SPEC 01M1NKTF173WV5CPDZ1C3WW69K) и цикла `merge_gate` (SPEC
   T053/T087) не ослабляется ни одним из требований выше.

## Критерии приёмки

AC-1. `approve` из состояния `acceptance` — прогон приёмочной планки
читает `tasks/<id>/acceptance_tests/` из АРТЕФАКТНОЙ ветки задачи во
временный каталог, не из worktree кодовой ветки.

AC-2. Тот же источник (артефактная ветка, не worktree кодовой ветки)
применяется к прогону планки внутри общего узла сверки свежести ветки,
вызываемого и на approve `acceptance`, и внутри окна `merge_gate`.

AC-3. Материализация из артефактной ветки не находит `acceptance_tests/`
(каталог пуст либо дерево ветки не прочитано) для задачи, НЕ пропустившей
`tests_writing` легитимно (`skip_tests` не задан в SPEC), — переход
отклоняется именованным отказом «планка не найдена в источнике»: отказ
журналируется и печатается, состояние не меняется.

AC-4. Отказ AC-3 не подменяет существующую эскалацию «приёмочные тесты
красные после подтяжки main» — эта эскалация остаётся только для планки,
которая реально прогналась и упала, не для отсутствующей/непрочитанной
планки.

AC-5. Задача с легитимно пропущенным `tests_writing` (`skip_tests` задан
в SPEC, либо SPEC без AC-разметки) по-прежнему проходит прогон планки
зелёным при отсутствии `acceptance_tests/` в артефактной ветке —
требования 1-2 этот существующий вырожденный случай не меняют.

AC-6. На переходе `merge_gate -> done` содержимое `tasks/<id>/`, которое
попадает в main, — снимок артефактной ветки на момент `approve` в
`merge_gate`, не то, что приносит `git merge` из кодовой ветки задачи.

AC-7. Копия `tasks/<id>/` кодовой ветки (если она есть, legacy) не влияет
на итоговое содержимое `tasks/<id>/` в main после merge.

AC-8. Расхождение между копией кодовой ветки и снимком артефактной ветки
на момент merge журналируется предупреждением; сам переход `merge_gate ->
done` по этой причине не отказывает и не эскалирует.

AC-9. CI-джоб `guard` (`.github/workflows/ci.yml`) не запускает
`guard.py` по `tasks/<id>/` веток `task/**` как проверку источника
истины — источником истины для CI остаётся прогон на `artifact/**`.

AC-10. Тест: `approve` из `acceptance` с пустым/отсутствующим
`tasks/<id>/acceptance_tests` в worktree кодовой ветки и планкой,
присутствующей в артефактной ветке, — переход зелёный (задача уходит в
`merge_gate`).

AC-11. Тест: расхождение копии `tasks/<id>` кодовой ветки и артефактной
ветки на момент merge — после merge содержимое `tasks/<id>` в main
соответствует АРТЕФАКТНОЙ ветке, не кодовой.

AC-12. Существующие тесты остаются зелёными без ослабления: автогейт
acceptance (`tests/test_fsm_autogate.py`), материализация артефактов
(`tests/test_artifact_materialization.py`), цикл `merge_gate`
(`tests/test_merge_gate_ci_wait.py` и смежные тесты `fsm_merge_gate`).

## Оценка объёма и деление
Сработавший сигнал: число критериев приёмки (12) ≥ 10.

Монолит принят Оператором 05.09.2026. Обоснование: все три
требования — патч ОДНОГО и того же архитектурного инварианта, уже
закреплённого регрессией №9 («`tasks/<id>/` живёт только в артефактной
ветке, диск и кодовая ветка не источник истины») в трёх местах пульта,
которые до сих пор его не соблюдают. Требование 4 («Не входит» ниже)
прямо просит единый прогон тестов (№6 автогейт, №9 материализация, T053
мерж) зелёным без ослабления по всем трём сразу — деление на подзадачи
размножило бы эту сверку по каждой части, не снижая риска. ТЗ Оператора
задаёт рамку $20 и называет эту задачу «меньше» соседней B2 (ТЗ-1,
пересекающейся зоной `fsm_merge_gate.py`/`acceptance.py`) и «идёт первой»
— формулировка про одну задачу, не несколько; калибровка стоимости шага
(analyst ~$2, developer ~$3.5, test_author ~$6, reviewer ~$2.3 за
итерацию) даёт по 2-4 подзадачи расход, кратно превышающий эту рамку без
уменьшения зоны риска (каждая часть касается одного и того же общего
узла сверки свежести ветки — `_pull_main_or_escalate`, — который сам
делить между подзадачами нельзя, не оставив часть механики без
покрытия). Каждое отдельное требование при этом небольшое (точечная
правка одной функции/одного CI-джоба) — граница «нарезка вместо
монолита» здесь снижала бы, а не повышала мержимость.

## Не входит

- Материализация артефактов в брифы ролей (`orchestrator/brief.py`) —
  сделано регрессией №9, не трогается.
- Задача B2 ТЗ-1 (пересекается зонами `fsm_merge_gate.py`/
  `acceptance.py`) — идёт следующей, после этой (порядок согласован
  Оператором в ТЗ).
- Механика снапшота закрытия во внешний target (`orchestrator/
  snapshot.py`, `refs/artifacts/<id>`) — отдельный механизм от того, что
  попадает в main задачи self-target; не трогается.
- Синхронизация копии `tasks/<id>/` в кодовую ветку пультом при пуше —
  явно отклонённый вариант требования 4 (см. «Оценка объёма и деление» и
  «Контекст»): плодил бы второй источник истины там, где `conventions-
  core` уже запрещает коммитить артефакты в кодовую ветку вовсе.
- Ослабление или удаление существующих гейтов, guard-проверок и
  инвариантов (принцип целостности, ADR-0002).
