# PLAN: Приёмка и мерж читают артефакты из артефактной ветки (регрессия №12)

## Подход
Три требования SPEC — патч одного и того же инварианта («`tasks/<id>/`
живёт только в артефактной ветке») в трёх местах общего узла сверки
свежести ветки (`orchestrator/fsm.py::_pull_main_or_escalate`) и гейта
`merge_gate`, поэтому один шаг:

1. **Планка approve/merge_gate — из артефактной ветки, не из worktree**
   (требования 1-2). `_pull_main_or_escalate` — ЕДИНЫЙ узел для всех
   трёх точек сверки (`in_dev -> review`, `acceptance -> merge_gate`,
   внутри окна `merge_gate`, плюс `canary._pass_acceptance_gate`) —
   правка в одном месте закрывает AC-1/AC-2 разом. Вместо
   `acceptance.run(wt_path / "tasks" / task_id)` (worktree кодовой
   ветки) — `acceptance.materialize_from_branch(task_id, artifact_branch)`
   во временный каталог (тот же узел, что уже несёт автогейт
   `fsm_autogate.py`), с очисткой временного каталога в `finally`.

2. **Различение трёх исходов планки** (требования 1-2, AC-3/AC-4/AC-5):
   материализация не находит `acceptance_tests/` в артефактной ветке —
   читаю SPEC.md ОТТУДА ЖЕ и `guard.requires_ac_markup(meta)` (тот же
   критерий, каким `_cmd_approve` уже решает legit-skip на входе в
   `spec_gate`): `True` (SPEC несёт AC-разметку, `skip_tests` не задан)
   — новый именованный отказ `"refused"` (AC-3), состояние НЕ меняется;
   `False` (skip_tests задан либо SPEC без AC-разметки) — существующий
   вырожденный случай не изменился, `"pulled"` без прогона (AC-5).
   Планка НАЙДЕНА и реально красная — прежняя эскалация «красные после
   подтяжки» не подменяется (AC-4) — `"refused"` возвращается ТОЛЬКО из
   ветки «не найдена», не из ветки «прогналась и упала».

   Новый исход `"refused"` подключён во ВСЕХ четырёх местах, что зовут
   `_pull_main_or_escalate` и сегодня проверяют только `== "escalated"`:
   `fsm._cmd_approve` (state acceptance), `fsm_advance.in_dev`,
   `fsm_merge_gate._cmd_approve_merge_gate`, `canary._pass_acceptance_gate`
   — везде теперь `in ("escalated", "refused")` (тот же класс замечания,
   что coding-standards просит чинить «классом, не экземпляром»: замена
   в одном месте и незамена в другом дала бы тихий регресс на
   canary/in_dev путях).

3. **Снимок артефактной ветки поверх merge** (требование 3, AC-6/AC-7/
   AC-8/AC-11): новый узел `fsm_merge_gate._overlay_artifact_snapshot`,
   вызываемый в `_cmd_approve_merge_gate` сразу после успешного `git
   merge --no-ff branch` в scratch-worktree, ДО вычисления `merge_sha`
   (адрес RETRO обязан указывать на содержимое tasks/<id>/, которое
   реально попадает в main, — снимок артефактной ветки, а не на
   легаси-копию кодовой ветки, поэтому наложение — часть «результата
   merge», не последующая служебная правка вроде карты/RETRO).
   `artifact_branch.materialize_task_dir(task_id, scratch)` — уже
   существующий узел (T094), пишущий `tasks/<id>/` каталога `scratch`
   как зеркало ГОЛОВЫ артефактной ветки (добавляет/перезаписывает/
   удаляет лишнее). `git status --porcelain` после наложения решает,
   есть ли что коммитить (расхождение) или снимок уже совпадает с тем,
   что принёс merge. Расхождение коммитится отдельным коммитом
   (`{id}: снимок артефактной ветки поверх merge`); если ДО наложения
   `tasks/<id>/` в scratch уже нёс файлы (легаси-копия кодовой ветки
   существовала — типично после ручной синхронизации Оператором,
   b0c71a4e — прецедент, названный в SPEC «Контекст»), расхождение с
   ней журналируется отдельным предупреждением (AC-8), переход не
   отказывает по этой причине. Материализация не удалась (ветка не
   читается) — журналируется предупреждение, main остаётся с тем, что
   принёс обычный merge (деградация, не отказ — требование 3 явно не
   разрешает провалу materialize держать гейт).

4. **CI-джоб `guard` не валидирует `tasks/<id>/` веток `task/**`**
   (требование 4, AC-9): правка `.github/workflows/ci.yml` — защищённый
   путь (`conventions-core`), поэтому НЕ коммитится этой веткой —
   диффом-приложением к этому PLAN.md (см. «Дифф для Оператора» ниже),
   применяет и коммитит Оператор отдельным MR.

## Влияние на систему
Изменения ограничены общим узлом сверки свежести ветки (`fsm.
_pull_main_or_escalate`, единственный на все три точки гейта) и телом
`merge_gate` (`fsm_merge_gate._cmd_approve_merge_gate`) — оба уже несут
интенсивное тестовое покрытие (`tests/test_branch_freshness_gate.py`,
`tests/test_merge_gate_ci_wait.py`, `tests/test_fsm_merge_gate_done_
snapshot.py`), прогнаны без ослабления (все зелёные, часть обновлена
под новый источник планки без изменения предмета проверки — п.4 «Шаги»).

Новый исход `"refused"` НЕ подменяет существующую эскалацию «красные
после подтяжки» (AC-4, отдельная ветка кода, покрыта AC-4 приёмочным
тестом) и не ослабляет вырожденный случай legit-skip (AC-5, тот же
критерий `guard.requires_ac_markup`, что уже решает его на
`spec_gate`, — не новый критерий). Автогейт acceptance (T066,
`fsm_autogate.py`) не тронут вовсе — он уже читал планку из артефактной
ветки до этой задачи (собственный узел материализации), эта задача
только подтягивает `_pull_main_or_escalate` к тому же источнику.
Материализация артефактов в брифы (T094/A7) и цикл `merge_gate`
(T053/T087, мьютекс merge-окна, ожидание CI вне мьютекса) не изменены
структурно — новый узел `_overlay_artifact_snapshot` — дополнительный
шаг ВНУТРИ тела гейта (после merge, до push), не новый гейт и не новое
условие перехода: провал материализации деградирует («main несёт
merge как есть»), не отказывает переходу (симметрично тому, как уже
не отказывает провал регенерации карты/RETRO рядом).

CI-джоб `guard` не ослабляется требованием 4/AC-9 — структура
артефактов `tasks/<id>/` по-прежнему валидируется guard'ом, просто на
ДРУГОЙ ветке (artifact/**, уже существующий отдельный прогон того же
джоба с `--artifact-branch`), не дублируется на `task/**`, где она и
так была устаревшей копией. Откат: правки `fsm.py`/`fsm_merge_gate.py`/
`canary.py`/`fsm_advance.py` — обычный `git revert` этой ветки; дифф
`ci.yml` — не применён, пока Оператор не решит иначе (отдельный MR,
откатывается независимо).

## Риски
`_overlay_artifact_snapshot` коммитит tasks/<id>/ в main НЕЗАВИСИМО от
того, была ли легаси-копия на кодовой ветке — то есть main начинает
получать tasks/<id>/ и для задач, чья кодовая ветка НИКОГДА не несла
этот каталог (обычный случай post-A7, `checkpoint.py` исключает
`tasks/<id>/` из коммитов роли в кодовую ветку) — раньше в этом случае
main не получал бы tasks/<id>/ вовсе. Это ПРЯМОЕ следствие требования
3 SPEC («main обязан унести снимок артефактной ветки») — не
самостоятельное решение этой задачи; если Оператор этого не хотел
(разошлось с намерением SPEC), это эскалация трактовки формулировки,
не дефект реализации: сама SPEC не оговаривает исключение для «легаси
не было вовсе».

## Предложения системе
- `conventions-core.md` — класс «общий узел с несколькими точками
  вызова, каждая проверяет один и тот же результат по буквенному
  значению» (`_pull_main_or_escalate` в этой задаче — 4 точки вызова,
  каждая с собственным `== "escalated"`) натирает при добавлении
  нового исхода: 4 места правки вместо одного enum/множества. Не
  критично здесь (правка маленькая), но повторится с любым следующим
  новым исходом того же узла.
