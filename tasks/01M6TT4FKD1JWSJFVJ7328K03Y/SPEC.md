# SPEC: Источник отчёта базы для гейта исходов full_suite ci: поле ci_base компонента (main | branch)

## Контекст
Гейт неослабления по исходам у компонента `full_suite: ci` (на `verifying`
и на гейте мержа, SPEC 01M6BMG29KZV1RX21HFAXZG3CM) сравнивает отчёт задания
`ci_job` головы ветки с отчётом базы: `_judge_ci`, `_ci_base_report`
(`orchestrator/advance_gates/outcome_integrity.py:1109-1133`). Отчёт базы
ищется у точки ответвления (`gitcmd.diff_base`, `orchestrator/gitcmd.py:1955`),
иначе у её родителя с тем же деревом; не найден — сбой подготовки «нет
отчёта базы» и отказ перехода (fail-closed). Отчёт стороны читается по sha:
`_ci_report` (`outcome_integrity.py:1065`) → `forge.pipeline_status`,
`forge.job_result`, `forge.job_test_report`.

Опыт 07.11.2026 на внешнем проекте GitLab: правила CI запускают задания
тестов на всех ветках, кроме `main`, а на `main` конвейер создаётся только
по расписанию и без тестов — у коммитов `main` отчёта задания тестов нет
никогда. У такого проекта каждая задача встанет на `verifying` с отказом
«нет отчёта базы». Решение Оператора 07.11.2026 («сделать универсально —
ок»): источник результата «до» — поле записи (ADR-0031, пп. 1 и 5).

Отправка в git — единая точка `gitcmd` (`_push_plan`,
`orchestrator/gitcmd.py:1264`): белый список отправки проекта
(`_whitelist_refusal`), политика `pre-push` клона проекта `target-human`
(эталон — `gitcmd.push_policy_text`, `gitcmd.py:436`;
`orchestrator/workspace.py:112`), параметры `policy.push_options` ко всем
отправкам веток задач (`gitcmd.py:1353-1356`), проверка параметра
`targets.push_option_error` (`orchestrator/targets.py:636-657`).

## Требования

1. **Поле `ci_base` компонента.** У компонента с `full_suite: ci | both`
   допустимо поле `ci_base` со значением `main` (по умолчанию) или
   `branch`. Без поля и при `main` — прежнее поведение побайтно.
   При `branch` обязательно поле `ci_base_branch` — имя ветки отчёта базы
   в `origin` проекта: строка без подстановок, не совпадает с `base`
   записи и не подходит под шаблон веток задач записи. Необязательное
   поле `ci_base_push_options` — список параметров отправки, каждый
   проверяется `targets.push_option_error` с `push_options_forbidden`
   записи (`ci.skip` и `merge_request.*` запрещены). Любое нарушение —
   отказ загрузки записи с полным именем поля в тексте отказа.
2. **Отправка базы.** При `ci_base: branch`, когда гейту (или подготовке к
   нему) нужен отчёт базы sha `B`, а `_ci_base_report` его не нашёл, пульт
   отправляет `B` в `ci_base_branch`
   (`git push --force origin <B>:refs/heads/<ci_base_branch>` через единую
   точку отправки `gitcmd`) с параметрами `ci_base_push_options` и без
   `policy.push_options`; затем ждёт задание `ci_job` коммита `B` тем же
   опросом и пределом, что ожидание CI на `verifying`
   (`config.VERIFYING_POLL_INTERVAL_SEC`, `config.VERIFYING_CEILING_SEC`),
   и берёт отчёт ровно `B`. Если отчёт `B` уже есть (в том числе от
   отправки другой задачи) — отправки нет.
3. **Ранний запуск.** Отправка базы запускается уже на входе в `in_dev`
   (база `gitcmd.diff_base` ветки известна), не дожидаясь `verifying`, —
   ожидание CI базы идёт параллельно шагам ролей. На `verifying` —
   повторная проверка: база сдвинулась (подтяжка `main`) — новая отправка;
   гейт ждёт отчёт текущей базы.
4. **Одна ветка отчёта базы на проект, по очереди.** Отправки базы разных
   задач в `ci_base_branch` проекта идут под замком (одна за раз);
   следующая — только после того, как конвейер предыдущего sha создан
   (задание `ci_job` у него появилось), чтобы отправка не отменила чужой
   конвейер раньше его создания. Отчёт по sha читается и после того, как
   ветка ушла на другой коммит.
5. **Белый список и политика клона** пропускают ровно отправку в
   `ci_base_branch` записи, в том числе принудительную — только в неё;
   прочие отправки — по прежним правилам. Пульт `ci_base_branch` не
   удаляет; `kill` и уборка задач её не трогают.
6. **Журнал и итог.** В журнал задачи пишутся записи «отчёт базы: отправка
   <sha> в <ветка>», «отчёт базы: задание <id> коммита <sha>», при отказе —
   с причиной. Предел ожидания исчерпан, задание красное или отчёт не
   разобран — прежний отказ «нет отчёта базы» с этой причиной (не пропуск
   гейта).
7. **`doctor`** для компонента с `ci_base: branch` выводит строку о том,
   что `ci_base_branch` не защищена и отправка в неё пропускается белым
   списком и политикой клона (проверка только чтением); иначе — `warn` с
   причиной.

## Критерии приёмки

AC-1. Given вымышленная запись GitLab с компонентом `full_suite: ci`, `ci_base: branch`, у точки ответвления отчёта нет, When гейт исходов на `verifying`, Then подменённая отправка `B:refs/heads/<ci_base_branch>` выполнена с `ci_base_push_options` и без `policy.push_options`, после появления отчёта `B` гейт сравнил отчёты головы и базы и прошёл; мутация «отправка не выполнена» и мутация «к отправке добавлены `policy.push_options`» — красные.

AC-2. Given `ci_base: branch` и отчёт базы `B` уже есть, When гейт исходов, Then отправки нет.

AC-3. Given `ci_base: main` или поле `ci_base` не задано, отчёта базы нет, When гейт исходов, Then прежнее поведение: отказ «нет отчёта базы», отправки нет.

AC-4. Given задача с `ci_base: branch`, When вход в `in_dev`, Then отправка базы запущена до `verifying`; Given база сдвинулась подтяжкой `main` до `verifying`, When `verifying`, Then отправлена новая база и гейт ждёт отчёт текущей базы.

AC-5. Given две задачи одного проекта с `ci_base: branch` и разными базами, Then отправки в `ci_base_branch` идут по одной, вторая — после того как у sha первой появилось задание `ci_job` (конвейер создан); отчёт первой базы читается и после ухода ветки на второй sha.

AC-6. Given задание `ci_job` базы красное / не завершилось за предел ожидания / его отчёт не разобран, Then отказ перехода «нет отчёта базы» с соответствующей причиной, и в журнале задачи — записи «отчёт базы: отправка <sha> в <ветка>» и «отчёт базы: задание <id> коммита <sha>».

AC-7. Given запись с `ci_base: branch` без `ci_base_branch`; с `ci_base_branch`, равным `base` записи; с `ci_base_branch`, подходящим под шаблон веток задач; с параметром `ci_base_push_options`, содержащим `ci.skip` или `merge_request.*`, Then отказ загрузки записи с полным именем поля в тексте.

AC-8. Given `ci_base: branch`, When отправка в иную ветку вне шаблона веток задач (не `ci_base_branch`), Then прежний отказ белого списка; принудительная отправка пропускается только в `ci_base_branch`; When `kill` задачи, Then `ci_base_branch` в `origin` не удалена.

AC-9. Given компонент с `ci_base: branch`, When `doctor`, Then строка `ok` о том, что `ci_base_branch` не защищена и отправка в неё пропускается белым списком и политикой клона; при невыполнении любого из условий — `warn` с причиной.

AC-10. Given записи без `ci_base` (GitLab и GitHub), Then прежнее поведение гейта исходов, белого списка, политики клона и `doctor`: отправки базы нет, тексты отказов прежние.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (шесть модулей кода
`orchestrator/` плюс `tests/`); число критериев приёмки — 10 (порог 10).

**Обоснование монолита** (материал для решения Оператора; решение на гейте
SPEC — за ним). Мыслимый разрез — «поля записи + белый список/политика
клона + `doctor`» отдельно от «отправка базы, очередь, ранний запуск».
Первая часть без второй — расширение прав отправки (принудительная
отправка в ветку вне шаблона задач) без единого потребителя: свойство
безопасности ослаблено, а польза нулевая до мержа второй части; вторая
часть без первой не может отправить ничего — единая точка `gitcmd`
откажет отправке в `ci_base_branch`. Требования 2–5 описывают одну
механику (отправка через единую точку → разрешение этой отправки →
ожидание и чтение отчёта), её приёмка (AC-1, AC-8) проверяется только
целиком. Резать по `fsm_advance.py` (ранний запуск, требование 3) можно
технически, но это ~одна точка вызова той же механики — отдельная задача
стоила бы дороже своей доли.

## Не входит

- Правка настоящего локального слоя `.artel/targets.yaml` в тестах и при
  разработке (значения для проекта задаёт Оператор после мержа); тесты —
  только вымышленные записи, клоны и голый `origin` в песочнице
  `tests.sandbox`, `forge`/транспорт адаптера GitLab — подмена или
  сервер-дублёр в процессе теста, без сети и настоящего GitLab.
- Изменение CI проектов.
- Источник отчёта базы у проектов на GitHub (этап 4а ADR-0031) и
  локальный прогон базы (`full_suite: local | both`).
- Приёмка (`acceptance_suite`) — отчёт головы, как прежде.
- Удаление `ci_base_branch` пультом (в любом сценарии).
- Правка модулей только для чтения: `orchestrator/forge.py`,
  `orchestrator/gitlab_adapter.py`, `orchestrator/ci.py`,
  `orchestrator/acceptance.py`, `orchestrator/project_profile.py`,
  `tests/sandbox.py`, ADR-0026/0029/0031.
- «Существующие тесты — зелёные без правки»: полный зелёный набор
  `tests/` держит пульт; ТЗ требует при покраснении существующего теста
  эскалацию с именем теста, без его правки — раздела «Меняемое поведение»
  нет.
