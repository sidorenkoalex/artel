# SPEC: Источник отчёта базы для гейта исходов full_suite ci: поле ci_base компонента (main | branch)

## Контекст
Гейт неослабления по исходам у компонента `full_suite: ci` (на `verifying`
и на гейте мержа, SPEC 01M6BMG29KZV1RX21HFAXZG3CM) сравнивает отчёт задания
`ci_job` головы ветки с отчётом базы: `_judge_ci`
(`orchestrator/advance_gates/outcome_integrity.py:1173`), `_ci_base_report`
(`:1109-1133`). Отчёт базы ищется у точки ответвления (`gitcmd.diff_base`,
`orchestrator/gitcmd.py:1955`), иначе у её родителя с тем же деревом; не
найден — сбой подготовки «нет отчёта базы» и отказ перехода (fail-closed).
Отчёт стороны читается по sha: `_ci_report` (`outcome_integrity.py:1065`) →
`forge.pipeline_status`, `forge.job_result`, `forge.job_test_report`; годные
статусы — `_CI_FIT_STATUSES = ("success", "failed")` (`:1045`), незавершённые —
`_CI_PENDING_STATUSES` (`:1048-1049`).

Опыт 07.11.2026 на внешнем проекте GitLab: правила CI запускают задания
тестов на всех ветках, кроме `main`, а на `main` конвейер создаётся только
по расписанию и без тестов — у коммитов `main` отчёта задания тестов нет
никогда. У такого проекта каждая задача встанет на `verifying` с отказом
«нет отчёта базы». Решение Оператора 07.11.2026 («сделать универсально —
ок»): источник результата «до» — поле записи (ADR-0031, пп. 1 и 5).

Отправка в git — единая точка `gitcmd` (`_push_plan`,
`orchestrator/gitcmd.py:1264`): белый список отправки проекта
(`_whitelist_refusal`), политика `pre-push` клона проекта `target-human` —
эталон файла политики `gitcmd.push_policy_text` (`gitcmd.py:435-442`;
`orchestrator/workspace.py:111-115`), исполнитель — хук
`scripts/git-hooks/target-human/pre-push` (читает ключи `:38-50`, отказывает
ветке не по `branch_template` `:96-100`); параметры `policy.push_options` —
только к отправкам веток задач (`gitcmd.py:1351-1356`), проверка параметра —
`targets.push_option_error` (`orchestrator/targets.py:636-657`).

Решения Оператора по батчу вопросов — `ANSWER-1.md` (все пункты — вариант
A), с мандатом расширения зон на хук `pre-push`.

## Требования

1. **Поля `ci_base` компонента.** У компонента с `full_suite: ci | both` в
   разделе `description.components.<имя>` записи (рядом с `full_suite` и
   `ci_job`) допустимо поле `ci_base` со значением `main` (по умолчанию)
   или `branch`. Без поля и при `main` — прежнее поведение побайтно.
   При `branch` обязательно поле `ci_base_branch` — имя ветки отчёта базы
   в `origin` проекта: строка без подстановок, не совпадает с `base`
   записи и не подходит под шаблон веток задач записи. Необязательное
   поле `ci_base_push_options` (там же) — список параметров отправки,
   каждый проверяется `targets.push_option_error` с `push_options_forbidden`
   записи (`ci.skip` и `merge_request.*` запрещены). При `ci_base: branch`
   `base` записи обязан совпадать с `config.MAIN_BRANCH`: база `verifying`
   считается merge-base с `refs/remotes/origin/<MAIN_BRANCH>`
   (`gitcmd.diff_base`, `orchestrator/gitcmd.py:1977-1979`), а проверка
   предка (требование 6) — от `origin/<base>`, и их расхождение давало бы
   отказ отправки базы на каждой попытке (решение Оператора 2 на гейте
   SPEC). Любое нарушение — отказ загрузки записи с полным именем поля в
   тексте отказа.
2. **Отправка базы.** При `ci_base: branch`, когда гейту (или подготовке к
   нему) нужен отчёт базы sha `B`, а `_ci_base_report` его не нашёл, пульт
   отправляет `B` в `ci_base_branch`
   (`git push --force origin <B>:refs/heads/<ci_base_branch>` через единую
   точку отправки `gitcmd`) с параметрами `ci_base_push_options` и без
   `policy.push_options` и берёт отчёт ровно `B`. Отправка — только когда
   у `B` нет задания `ci_job` вовсе. Задание `ci_job` у `B` есть и в
   незавершённом статусе (`_CI_PENDING_STATUSES`) — ожидание без отправки.
   Отчёт `B` уже есть (в том числе от отправки другой задачи) — отправки
   нет.
3. **Ожидание без блокировок.** Ни один вызов пульта не ждёт отчёт базы
   или конвейер внутри себя. Ожидание отчёта базы идёт опросом
   `verifying` (`config.VERIFYING_POLL_INTERVAL_SEC`) под потолком
   `config.VERIFYING_CEILING_SEC`, отсчитанным от входа в `verifying`
   (`fsm_advance.py:516-517`): пока годность отчёта базы — проходящая
   (требование 7), а потолок не исчерпан, — отказ ожидания, а не
   эскалация. Ожидание базы журналируется новым действием «гейт исходов на
   verifying: ожидание отчёта CI базы», а не действием ожидания головы
   (`PENDING_ACTION`, `outcome_integrity.py:1465`). Исчерпание потолка
   ожидания базы — прежняя эскалация `fsm_advance` «потолок ожидания CI в
   verifying исчерпан …» (`fsm_advance.py:517-523`), её последний статус
   (`note`) содержит «нет отчёта базы: <причина>» (решение Оператора 4).
4. **Ранний запуск.** На входе в `in_dev` из `tests_writing`
   (`fsm_advance.py:665`) — и только на этом входе — пульт делает одну
   неблокирующую попытку отправки базы `gitcmd.diff_base` ветки; очередь
   (требование 5) занята — попытки нет, повтор на `verifying`. Сбой
   ранней отправки (отказ белого списка, отказ хука, сбой git) переход в
   `in_dev` не останавливает, причина пишется в журнал задачи (решение
   Оператора 5). Прочие
   входы в `in_dev` раннюю отправку не делают: база отправляется на
   `verifying`. На `verifying` — повторная проверка: база сдвинулась
   (подтяжка `main`) — новая отправка; гейт ждёт отчёт текущей базы.
5. **Одна ветка отчёта базы на проект, по очереди.** Отправки базы разных
   задач в `ci_base_branch` проекта идут под замком проекта, который
   держится только на время самой отправки (одна за раз). Перед отправкой
   пульт проверяет sha предыдущей отправки в `ci_base_branch` (по записи
   журнала): следующая отправка — только когда задание `ci_job` этого sha
   в статусе `running` или завершено; иначе отправка откладывается до
   следующего опроса. Предыдущая отправка старше
   `config.VERIFYING_CEILING_SEC` очередь не держит. Отчёт по sha читается
   и после того, как ветка ушла на другой коммит.
6. **Белый список и политика клона** пропускают ровно отправку в
   `ci_base_branch` записи, в том числе принудительную — только в неё, и
   только для sha, являющегося предком `origin/<base>`
   (`gitcmd.is_ancestor`); иначе — отказ с причиной. Белый список
   проверяет предка по свежему sha `<base>` в `origin`
   (`gitcmd.fetch_ref_sha("origin", <base>)`), а не по локальной ссылке
   `refs/remotes/origin/<base>` клона: перед проверкой она не обновляется
   (`gitcmd.py:1943-1948`), а общий каталог git клона под управлением
   роли (`gitcmd.py:462`) — её может сдвинуть роль (решение Оператора 3).
   Хук остаётся второй линией по локальной ссылке. Эталон файла
   политики пишет ключ `ci_base_branch=` только при `ci_base: branch`; хук
   `scripts/git-hooks/target-human/pre-push` пропускает по этому ключу
   отправку и принудительную отправку ровно в эту ветку и только для sha
   — предка `origin/<base>`; прочие правила хука и прочие отправки — по
   прежним правилам. Пульт `ci_base_branch` не удаляет; `kill` и уборка
   задач её не трогают.
7. **Журнал и итог.** В журнал задачи пишутся записи «отчёт базы: отправка
   <sha> в <ветка>», «отчёт базы: задание <id> коммита <sha>», при отказе —
   с причиной. Годность отчёта базы классифицируется тем же признаком
   проходящей негодности (`pending`) из `_ci_report`, что и голова
   (`outcome_integrity.py:1184-1187`; `:1080-1097`), решение Оператора 1:
   - проходящая негодность — задания нет, оно не завершено
     (`_CI_PENDING_STATUSES`), статус не прочитан, перезапуск во время
     чтения, отчёт не разобран (`:1096-1097`) — ожидание под потолком
     `verifying` (требование 3);
   - окончательная негодность — `canceled`, `skipped`/`manual` (статус вне
     `_CI_FIT_STATUSES` и вне `_CI_PENDING_STATUSES`), `failed` с
     `allow_failure` — сразу отказ «нет отчёта базы: <причина>» и
     эскалация (как прежний отказ `outcome_integrity.py:1133`, не пропуск
     гейта); у `canceled` причина — «задание отменено», повторной
     отправки нет.
   Задание `failed` с разобранным отчётом — годная база, как в режиме
   `main`.
8. **Гейт мержа.** При `ci_base: branch` и отсутствии отчёта базы мержа
   (`_merge_base_of`, `outcome_integrity.py:820-837`) пульт отправляет базу
   мержа по правилам требований 2 и 5 и отказывает прежним сбоем
   подготовки (`outcome_integrity.py:1618-1623`) с причиной «отчёт базы
   ожидается, повтори approve»; внутри окна мержа не ждёт.
9. **`doctor`** для компонента с `ci_base: branch` выводит строку `ok` о
   том, что `ci_base_branch` не защищена и отправка в неё пропускается
   белым списком и политикой клона (проверка только чтением); иначе —
   `warn` с причиной.

## Критерии приёмки

AC-1. Given вымышленная запись GitLab с компонентом `full_suite: ci`, `ci_base: branch`, у точки ответвления `B` отчёта и задания `ci_job` нет, When гейт исходов на `verifying`, Then подменённая отправка `B:refs/heads/<ci_base_branch>` выполнена с `ci_base_push_options` и без `policy.push_options`, после появления отчёта `B` гейт сравнил отчёты головы и базы и прошёл; мутация «отправка не выполнена» и мутация «к отправке добавлены `policy.push_options`» — красные.

AC-2. Given `ci_base: branch` и отчёт базы `B` уже есть, When гейт исходов, Then отправки нет.

AC-3. Given `ci_base: main` или поле `ci_base` не задано, отчёта базы нет, When гейт исходов, Then прежнее поведение: отказ «нет отчёта базы», отправки нет.

AC-4. Given `ci_base: branch` и задание `ci_job` базы `B` есть в незавершённом статусе, When две проверки гейта на `verifying` подряд после одной отправки `B`, Then отправка `B` ровно одна, а каждая проверка — отказ ожидания (не эскалация).

AC-5. Given задача с `ci_base: branch`, When вход в `in_dev` из `tests_writing`, Then одна попытка отправки базы выполнена до `verifying`, а переход не ждёт отчёт базы; Given очередь проекта занята, Then попытки нет и переход в `in_dev` выполнен; Given ранняя отправка отказана белым списком, хуком или подменённым git (сбой), Then переход в `in_dev` выполнен, а причина сбоя — в журнале задачи; очередь отправок читается из журнала через `store.steps_of_action` без правки `store.py`; Given база сдвинулась подтяжкой `main` до `verifying`, When `verifying`, Then отправлена новая база и гейт ждёт отчёт текущей базы.

AC-6. Given две задачи одного проекта с `ci_base: branch` и разными базами, Then отправки в `ci_base_branch` идут по одной: при задании `ci_job` первого sha в `created`/`pending` или его отсутствии вторая отправка отложена, при `running` или завершённом — выполнена; отчёт первой базы читается и после ухода ветки на второй sha; Given дублёр `forge`, никогда не показывающий задание первого sha, Then тест не зависает, а после истечения `config.VERIFYING_CEILING_SEC` (подменённые часы) от первой отправки вторая отправка выполнена.

AC-7. Given `ci_base: branch` на `verifying`, по отдельному случаю на каждую ветвь классификации годности отчёта базы: (а) проходящая негодность — задания нет после отправки, задание в незавершённом статусе, статус не прочитан, перезапуск во время чтения, отчёт не разобран — Then каждый случай: отказ ожидания (не эскалация), в журнале — действие «гейт исходов на verifying: ожидание отчёта CI базы», а не действие ожидания головы; (б) окончательная негодность — задание `canceled`, `skipped`, `manual`, `failed` с `allow_failure` — Then каждый случай: сразу отказ «нет отчёта базы: <причина>» и эскалация без ожидания потолка; у `canceled` причина «задание отменено» и повторной отправки нет; (в) проходящая негодность при исчерпанном потолке (подменённые часы) — Then прежняя эскалация `fsm_advance` «потолок ожидания CI в verifying исчерпан …», её `detail` содержит «нет отчёта базы: <причина>»; (г) задание базы `failed` с разобранным отчётом — Then база годна и сравнение идёт; мутация «ждать при окончательной негодности» и мутация «эскалировать при проходящей» — обе красные; во всех случаях с отправкой в журнале задачи — запись «отчёт базы: отправка <B> в <ci_base_branch>», а при найденном задании — запись «отчёт базы: задание <id> коммита <B>» ровно для sha `B`.

AC-8. Given `ci_base: branch` и у базы мержа нет отчёта и задания `ci_job`, When гейт мержа (`approve`), Then база мержа отправлена, задача осталась на гейте мержа с отказом сбоя подготовки и причиной «отчёт базы ожидается, повтори approve», ожидания внутри окна мержа нет.

AC-9. Given запись с `ci_base: branch` без `ci_base_branch`; с `ci_base_branch`, равным `base` записи; с `ci_base_branch`, подходящим под шаблон веток задач; с параметром `ci_base_push_options`, содержащим `ci.skip` или `merge_request.*`; с `ci_base: branch` и `base` записи, отличным от `config.MAIN_BRANCH`, Then отказ загрузки записи с полным именем поля в тексте; параметр `ci_base_push_options` формы `ИМЯ=значение`, допустимый `targets.push_option_error`, загрузку не отказывает.

AC-10. Given `ci_base: branch`, When отправка через белый список в иную ветку вне шаблона веток задач (не `ci_base_branch`), Then прежний отказ белого списка; принудительная отправка пропускается только в `ci_base_branch`; When отправка в `ci_base_branch` sha, не являющегося предком `origin/<base>`, Then отказ с причиной; мутация «источник не проверен» — красная; Given голый `origin` в песочнице без сети, где `<base>` стоит на своём коммите, а локальная `refs/remotes/origin/<base>` клона сдвинута тестом на коммит `X` вне `<base>` в `origin`, и отправляемый sha — предок `X`, но не предок `<base>` в `origin`, When отправка этого sha в `ci_base_branch`, Then белый список отказывает (проверка по свежему sha `gitcmd.fetch_ref_sha("origin", <base>)`); мутация «проверка по локальной ссылке» — красная.

AC-11. Given вымышленный клон `target-human` с каталогом хуков `scripts/git-hooks/target-human` и голый `origin` в песочнице, `ci_base: branch`, When настоящая отправка через единую точку `gitcmd` sha — предка `origin/<base>` в `ci_base_branch` (в том числе принудительная), Then отправка проходит хук и ветка в `origin` стоит на этом sha; When отправка в иную ветку вне шаблона или sha — не предка `origin/<base>` в `ci_base_branch`, Then хук отказывает; мутация «хук не пропускает» — красная; у записи без `ci_base` текст эталона политики прежний (`tests/test_push_hook_units.py:275-287`).

AC-12. Given `ci_base: branch` и ветка `ci_base_branch` в `origin`, When `kill` задачи и уборка задачи, Then `ci_base_branch` в `origin` не удалена.

AC-13. Given компонент с `ci_base: branch`, When `doctor`, Then строка `ok` о том, что `ci_base_branch` не защищена и отправка в неё пропускается белым списком и политикой клона; при невыполнении любого из условий — `warn` с причиной.

AC-14. Given записи без `ci_base` (GitLab и GitHub), Then прежнее поведение гейта исходов, белого списка, политики клона, хука и `doctor`: отправки базы нет, тексты отказов прежние.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (шесть модулей `orchestrator/`,
хук `pre-push`, карта и `tests/`); число критериев приёмки — 14 (порог 10);
`budget_usd` ≥ $30.

**Обоснование монолита** (материал для решения Оператора; решение на гейте
SPEC — за ним). Мыслимый разрез — «поля записи + белый список/хук/политика
клона + `doctor`» отдельно от «отправка базы, очередь, ранний запуск,
гейт мержа». Первая часть без второй — расширение прав отправки
(принудительная отправка в ветку вне шаблона задач) без единого
потребителя: свойство безопасности ослаблено, а польза нулевая до мержа
второй части; вторая часть без первой не может отправить ничего — единая
точка `gitcmd` и хук откажут отправке в `ci_base_branch`. Требования 2–8
описывают одну механику (отправка через единую точку → разрешение этой
отправки белым списком и хуком → ожидание и чтение отчёта), её приёмка
(AC-1, AC-10, AC-11) проверяется только целиком. Ранний запуск
(требование 4) — одна точка вызова той же механики в `fsm_advance.py`;
отдельная задача стоила бы дороже своей доли.

## Не входит

- Правка настоящего локального слоя `.artel/targets.yaml` в тестах и при
  разработке (значения для проекта задаёт Оператор после мержа); тесты —
  только вымышленные записи, клоны и голый `origin` в песочнице
  `tests.sandbox`, `forge`/транспорт адаптера GitLab — подмена или
  сервер-дублёр в процессе теста, без сети и настоящего GitLab.
- Изменение CI проектов.
- Источник отчёта базы у проектов на GitHub (этап 4а ADR-0031) и
  локальный прогон базы (`full_suite: local | both`).
- Приёмка (`acceptance_suite`) — отчёт головы, как прежде.
