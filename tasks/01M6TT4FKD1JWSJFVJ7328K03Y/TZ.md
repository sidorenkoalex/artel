# ТЗ: Источник отчёта базы для гейта исходов full_suite ci: поле ci_base компонента (main | branch)

# Источник отчёта базы для гейта исходов full_suite ci: поле ci_base компонента (main | branch)

## Факты

1. Гейт неослабления по исходам у компонента `full_suite: ci` на `verifying` (SPEC 01M6BMG29KZV1RX21HFAXZG3CM) и на гейте мержа сравнивает отчёт задания `ci_job` головы ветки с отчётом базы: `_judge_ci`, `_ci_base_report` (`orchestrator/advance_gates/outcome_integrity.py:1109-1133`). Отчёт базы — у точки ответвления (`gitcmd.diff_base`, `orchestrator/gitcmd.py:1955`), иначе у её родителя с тем же деревом; не найден — сбой подготовки «нет отчёта базы», отказ перехода (fail-closed).
2. Отчёт стороны читается по sha: `_ci_report` (`outcome_integrity.py:1065`) → `forge.pipeline_status`, `forge.job_result`, `forge.job_test_report`.
3. Опыт 07.11.2026 (чтение API внешнего проекта на GitLab): у проекта, где правила CI запускают задания тестов на всех ветках, кроме `main`, а на `main` конвейер создаётся только по расписанию и без тестов, у коммитов `main` отчёта задания тестов нет никогда; отчёт головы ветки задачи читается целиком. Значит, у такого проекта каждая задача встанет на `verifying` с отказом «нет отчёта базы».
4. Отправка — единая точка `gitcmd` (`_push_plan`, `orchestrator/gitcmd.py:1264`): белый список отправки проекта (`_whitelist_refusal`), политика `pre-push` клона проекта `target-human` (эталон — `gitcmd.py:436`, `orchestrator/workspace.py:112`), параметры отправки записи `policy.push_options` ко всем отправкам веток задач (`gitcmd.py:1353-1356`), проверка параметра `targets.push_option_error` (`orchestrator/targets.py:636-657`: `ci.variable=ИМЯ=значение`; `ci.skip` и `merge_request.*` запрещены).
5. Решение Оператора 07.11.2026 («сделать универсально — ок»): источник результата «до» — поле записи; ADR-0031 (`9d60fe8f`), п. 1 и п. 5.

## Требуется

1. **Поле `ci_base` компонента** с `full_suite: ci | both`: `main` (по умолчанию — прежнее поведение побайтно) или `branch`. Для `branch` обязательны `ci_base_branch` — имя ветки отчёта базы в `origin` проекта (строка, без подстановок, не совпадает с `base` записи и с шаблоном веток задач) — и необязательно `ci_base_push_options` — список параметров отправки, каждый проверяется `targets.push_option_error` с `push_options_forbidden` записи. Ошибка — отказ загрузки записи с полным именем поля. Без `ci_base` и при `main` — прежнее поведение.
2. **Отправка базы.** При `ci_base: branch`, когда гейту (или подготовке к нему) нужен отчёт базы sha `B`, а `_ci_base_report` его не нашёл, пульт отправляет `B` в `ci_base_branch` (`git push --force origin <B>:refs/heads/<ci_base_branch>` через единую точку отправки) с параметрами `ci_base_push_options` и без `policy.push_options`, затем ждёт задание `ci_job` коммита `B` тем же опросом и пределом, что ожидание CI на `verifying`, и берёт отчёт ровно `B`. Отчёт уже есть (в том числе от отправки другой задачи) — отправки нет.
3. **Ранний запуск.** Отправка базы запускается уже на входе в `in_dev` (база `gitcmd.diff_base` ветки известна), не дожидаясь `verifying`, — ожидание CI базы идёт параллельно шагам ролей; на `verifying` повторная проверка: база сдвинулась (подтяжка `main`) — новая отправка; гейт ждёт отчёт текущей базы.
4. **Одна ветка отчёта базы на проект, по очереди.** Отправки базы разных задач в `ci_base_branch` проекта — под замком (одна за раз); следующая — после того как конвейер предыдущего sha создан (задание `ci_job` у него появилось), чтобы отправка не отменила чужой конвейер раньше создания; отчёт по sha читается и после того, как ветка ушла на другой коммит.
5. **Белый список и политика клона** пропускают ровно отправку в `ci_base_branch` записи (и принудительную — только в неё); прочие отправки — прежние правила. Удаление `ci_base_branch` пультом не делается, `kill` и уборка задач её не трогают.
6. **Журнал и итог.** Записи журнала задачи: «отчёт базы: отправка <sha> в <ветка>», «отчёт базы: задание <id> коммита <sha>», отказ — с причиной; предел ожидания исчерпан, задание красное или отчёт не разобран — прежний отказ «нет отчёта базы» с этой причиной (не пропуск гейта).
7. **`doctor`** для компонента с `ci_base: branch`: строка о том, что `ci_base_branch` не защищена и отправка в неё пропускается белым списком и политикой клона (только чтение); иначе `warn` с причиной.

## Критерии приёмки

- Given вымышленная запись GitLab с `ci_base: branch`, у точки ответвления отчёта нет, When гейт исходов на `verifying`, Then подменённая отправка `B:refs/heads/<ci_base_branch>` выполнена с `ci_base_push_options` и без `policy.push_options`, после появления отчёта `B` гейт сравнил головы и базу и прошёл; мутация «отправка не выполнена» и мутация «к отправке добавлены `policy.push_options`» — красные;
- Given отчёт `B` уже есть, Then отправки нет;
- Given `ci_base: main` или поле не задано, Then прежнее поведение: отказ «нет отчёта базы», отправки нет;
- Given вход в `in_dev`, Then отправка базы запущена до `verifying`; Given база сдвинулась подтяжкой до `verifying`, Then отправлена новая база;
- Given две задачи проекта с разными базами, Then отправки идут по одной, вторая — после создания конвейера первой;
- Given задание базы красное / не завершилось за предел / отчёт не разобран, Then отказ «нет отчёта базы» с причиной;
- Given `ci_base: branch` без `ci_base_branch`, `ci_base_branch`, равный `base` или подходящий под шаблон веток задач, параметр с `ci.skip` или `merge_request.*`, Then отказ загрузки записи с именем поля;
- Given отправка в иную ветку вне шаблона задач, Then прежний отказ белого списка; `kill` задачи `ci_base_branch` не удаляет;
- `doctor` — строка `ok` / `warn` по `ci_base_branch`;
- записи без `ci_base` и проекты на GitHub — прежнее поведение; существующие тесты — зелёные без правки.

Безопасность тестов: вымышленные проекты, клоны и голый `origin` во временной песочнице (`tests.sandbox`), `forge` и транспорт адаптера GitLab — подмена или сервер-дублёр в процессе теста; без сети и настоящего GitLab; никогда — настоящий `.artel/targets.yaml` и клоны проектов.

Существующие тесты: правка не должна сделать красным ни один существующий тест; если краснеет — эскалация с именем теста, без правки.

Зоны: `orchestrator/advance_gates/outcome_integrity.py`, `orchestrator/targets.py` (поля `ci_base`, `ci_base_branch`, `ci_base_push_options`), `orchestrator/gitcmd.py` (белый список и эталон политики `pre-push` для `ci_base_branch`), `orchestrator/workspace.py` (эталон политики клона, если он там), `orchestrator/fsm_advance.py` (ранний запуск на входе в `in_dev`), `orchestrator/doctor/project_checks.py` (строка `doctor`), `docs/codebase-map.md` (только генерацией), `tests/` (долгоживущие файлы задачи).

Только чтение: `docs/adr/0031-test-runs-strategy.md`, `docs/adr/0026-project-components-and-outcome-gates.md`, `docs/adr/0029-external-delivery-via-mr.md`, `orchestrator/forge.py`, `orchestrator/gitlab_adapter.py`, `orchestrator/ci.py`, `orchestrator/acceptance.py`, `orchestrator/project_profile.py`, `tests/sandbox.py`.

Не входит:

- источник отчёта базы у проектов на GitHub (этап 4а ADR-0031) и локальный прогон базы (это `full_suite: local | both`);
- приёмка (`acceptance_suite`) — отчёт головы, как прежде.
