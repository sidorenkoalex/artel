# PLAN: Автогейт приёмки читает планку через источник артефактов

## Подход
`_autogate_conditions` (`orchestrator/fsm_autogate.py:14`) сейчас решает
условие «а» (наличие `acceptance_tests/*.py` и разбор AC-пометок
manual/skip) по диску рабочей копии (`acc_tdir.glob("*.py")` +
`guard.scan_acceptance_tests(acc_tdir)`). После A7 этот каталог на диске
пуст, поэтому условие «а» всегда отказывает — задача правит именно этот
кусок, не трогая остальное.

Условие «а» переводится на чтение через источник артефактов задачи —
тем же приёмом, что уже применяет `fsm._tests_writing_ac_state` (SPEC
T031, `orchestrator/fsm.py:338`): `branch, _ = artifact_source.resolve(conn,
task_id)`, список файлов `acceptance_tests/` — `gitcmd.ls_tree_files(branch,
...)`, содержимое каждого `.py` — `gitcmd.show(branch, path)`, разбор
AC-пометок — общее источник-агностичное ядро `guard.scan_ac_content(sources)`
(то же ядро, что уже использует и `scan_acceptance_tests`, и
`_tests_writing_ac_state`). Сканируются ВСЕ `*.py` каталога, не только
`test_*.py` — тот же приём, что `_tests_writing_ac_state` (подтверждено
докстринг-комментарием `tasks/.../acceptance_tests/_sandbox.py`, `_HASH`),
пусть это и отличается от дискового `scan_acceptance_tests`, который
фильтрует на `test_*.py`: задача переносит именно этот прецедент, а не
изобретает третий вариант разбора.

`artifact_source.resolve` после A7 для ЛЮБОГО target всегда возвращает
`foreign=True` (`orchestrator/artifact_source.py:24`) — веток-развилки
«диск vs ветка», какую несёт `_tests_writing_ac_state` для обратной
совместимости, здесь не нужно: чтение условия «а» всегда идёт через
ветку.

AC-6 требует, чтобы записи журнала, где решение зависит от планки,
называли источник — ветку и sha, с которых она прочитана
(`gitcmd.branch_head_sha(branch)`). Реализация формирует одну строку
`источник планки: ветка <branch>, sha <sha>` и:
- добавляет её в перечень `ok` при успехе условия «а» (тогда она
  попадает в `detail` перехода `acceptance -> merge_gate` через
  `store.set_state(..., detail="; ".join(ok_conditions))`);
- дописывает в скобках к строке `reason` при отказе условия «а»
  (manual/skip/пустой-или-отсутствующий каталог) — `reason` уходит в
  журнал напрямую (`store.journal(..., reason)` в
  `_maybe_autogate_acceptance`). Дописывание не меняет ведущую
  подстроку причины («автогейт: критерии manual — AC-…» и т. п.)
  — только добавляет источник в скобках следом, так что печать и
  журнал остаются обратно совместимы с прежней формулировкой (SPEC
  требование 2).

Условия б/в/г/д (`orchestrator/fsm_autogate.py:43-59`) не трогаются —
порядок, причины отказа и короткое замыкание остаются байт-в-байт (SPEC
AC-7, «Не входит»).

`acc_tdir` остаётся параметром сигнатуры `_autogate_conditions` без
изменений: удаление параметра сломало бы вызывающий код
(`_maybe_autogate_acceptance`, `orchestrator/fsm_advance.py:317`) и
сигнатуру, зафиксированную приёмочными тестами задачи (`_sandbox.py::
conditions`/`autogate`, зовут функцию пятью позиционными аргументами).
Условия б/в/г/д этот параметр не используют и раньше — задача не
добавляет новых потребителей `acc_tdir`, только перестаёт читать его в
условии «а».

## Шаги
1. `orchestrator/fsm_autogate.py`: переключить условие «а» в
   `_autogate_conditions` на чтение через `artifact_source.resolve` +
   `gitcmd.ls_tree_files`/`gitcmd.show` + `guard.scan_ac_content`,
   добавить импорт `artifact_source`/`gitcmd`; добавить пометку
   источника (ветка+sha) в `reason`/`ok` условия «а»; обновить
   докстринг функции.
2. Юнит-тесты `tests/test_fsm_autogate.py` (новый файл — у модуля
   сегодня нет собственного юнит-теста, только косвенный в
   `tests/test_git_fixation.py`): условие «а» читает по ветке (не по
   диску), фильтрует `*.py`, разбирает manual/skip через
   `guard.scan_ac_content`, размечает причину/`ok` источником
   (ветка+sha), не меняет условия б/в/г/д. Дополняет приёмочные тесты
   задачи на уровне юнита конкретной функции, не дублирует их сценарии
   один в один.
3. Прогон `scripts/guard.py` на артефактах задачи, полного набора
   `tests/`, приёмочных тестов задачи (`tasks/01M1NBWWPJMHKJMYXRDCM0W0C5/
   acceptance_tests/`) — все зелёные; коммит; `PLAN.md` → `status: ready`.

## Влияние на систему
Правка ограничена условием «а» внутри `_autogate_conditions`
(`orchestrator/fsm_autogate.py`) — единственная точка входа
(`_maybe_autogate_acceptance`) и её вызывающий код
(`fsm_advance.verifying`, материализация `acc_tdir`) не меняются (SPEC
«Не входит»), поэтому риск воздействия на другие гейты/переходы FSM
минимален.

Инварианты и гейты рядом:
- ADR-0007 (политика автогейта acceptance) — состав условий и их
  порядок не меняются (AC-7), только источник чтения условия «а»;
  ослабления гейта нет — наоборот, автогейт снова способен видеть
  планку, которую до правки не видел вовсе (не пропускает задачи,
  которые раньше блокировались бы manual/skip — эти же задачи и после
  правки не проходят автогейт, теперь по правильной причине, не по
  случайному совпадению «каталог пуст»).
- Ручной гейт приёмки (Оператор approve/reject `acceptance` вручную) не
  затронут — задача не трогает эту ветку кода (SPEC «Не входит»).
- `guard.scan_ac_content` — общее ядро, не меняется; задача только
  добавляет второго потребителя источника-по-ветке в дополнение к уже
  существующему `_tests_writing_ac_state`.
- Существующий тест `tests/test_git_fixation.py::
  AutogateMergeGateHintIncludesShaTest` мокает `_autogate_conditions`
  целиком (`return_value=(["ok"], None)`) — правки тела функции не
  касается, остаётся зелёным без изменений.

Откат: правка локальна в одном файле (`orchestrator/fsm_autogate.py`,
функция `_autogate_conditions`) — откатывается ревертом коммита без
затрагивания смежных модулей.

## Риски
- Разбор ВСЕХ `.py` файлов каталога (не только `test_*.py`) под
