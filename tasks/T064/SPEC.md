# SPEC: Guard: объяснённая краснота приёмочных тестов

## Контекст

Строка роадмапа P3 «Корректность залоченных тестов: объяснённая
краснота + сверка семантики». Три дефекта залоченных приёмочных тестов
за неделю (T051 AC-5 — мок душил git; T041/T059 — устаревший адрес
дерева; T060 AC-5 — ассерт против ADR-0003) имеют общий корень:
приёмочные тесты рождаются красными по конвенции, и красный-по-неверной-
причине неотличим от красного-по-задумке. Гейт выхода из
`tests_writing` сейчас проверяет только трассируемость AC -> тест
(`scripts/guard.py`, `acceptance_traceability_errors`), не смысл
красноты. Дефект лочится и вскрывается только когда правильная
реализация не может позеленить тест.

## Требования

1. Каждый файл приёмочных тестов `tasks/<id>/acceptance_tests/test_*.py`
   обязан нести в докстринге модуля структурированный маркер причины
   красноты: строку, начинающуюся с «Красен до реализации:», с
   объяснением, почему тест красный до появления кода задачи, либо
   строку «Зелёный с рождения:» с объяснением, почему это корректно
   (тест проверяет сохранение существующего поведения).
2. `scripts/guard.py` на выходе задачи из состояния `tests_writing` —
   там же, где сейчас проверяется трассируемость AC -> тест —
   проверяет наличие такого маркера в докстринге модуля каждого файла
   `acceptance_tests/*.py`. Файл без маркера — именованный отказ
   перехода: сообщение указывает, какому файлу какого маркера не
   хватает.
3. Guard не оценивает содержательность (смысл) объяснения — только
   формальный факт присутствия строки-маркера с непустым текстом после
   двоеточия. Оценка смысла объяснения — работа ревью и Оператора, не
   этой проверки.
4. Проверка обратно совместима: применяется только к переходам задачи
   из `tests_writing`, которые происходят после мержа этой задачи в
   main. Задачи, чей переход из `tests_writing` уже состоялся раньше
   (лок неприкосновенен, ADR-0003), этим правилом задним числом не
   пересматриваются — ни на новых прогонах `advance`, ни на прогонах
   guard по их артефактам.
5. Ни одна существующая проверка `scripts/guard.py` (трассируемость AC,
   `schema_version`, обязательные секции, допустимые статусы) не
   ослабляется и не удаляется (принцип целостности, ADR-0002) — новое
   правило только добавляется.

## Критерии приёмки

AC-1. Тест-файл `tasks/<id>/acceptance_tests/test_*.py` без строки
«Красен до реализации:» и без строки «Зелёный с рождения:» в
докстринге модуля → выход задачи из состояния `tests_writing`
отклоняется guard'ом, и сообщение отказа называет файл, которому не
хватает маркера.

AC-2. Тест-файл с такой строкой (с непустым объяснением после
двоеточия — «Красен до реализации:» или «Зелёный с рождения:») не
вызывает отказа перехода по этому основанию.

AC-3. Задачи, уже вышедшие из состояния `tests_writing` до мержа этой
задачи, этим правилом не затрагиваются: их переходы и повторные
прогоны guard по этому признаку не отклоняются, существующие каталоги
`acceptance_tests/` задним числом не проверяются и не правятся.

AC-4. Существующий набор тестов остаётся зелёным, ни одна существующая
проверка `scripts/guard.py` не ослаблена.

## Не входит

- Скиловая правка обязанностей test_author (прогон тестов, объяснение
  каждой красноты, стаб-валидация по образцу T062) — правит Оператор
  отдельным MR в `skills/`.
- Оценка семантики/качества объяснений в маркере — работа ревью и
  Оператора, не guard'а.
- Ретроактивные правки или ретроактивная проверка уже существующих
  каталогов `acceptance_tests/` прошлых задач.
- Стаб-валидация корректной реализации как обязательный шаг гейта (пока
  рекомендация скила, не проверка кода).
- Правки `templates/` и `skills/` — зона Оператора.
