# PLAN: Guard: объяснённая краснота приёмочных тестов

## Подход

Новая проверка — отдельная функция в `scripts/guard.py`, а не часть
`check_content`/`check()` (структурного слоя, который дёргает
`guard.py --all` и обычная приёмка markdown-артефактов). Причина:
AC-3 требует, чтобы задачи, уже прошедшие `tests_writing`, не
пересматривались задним числом ни новыми прогонами `advance`, ни
новыми прогонами guard по их артефактам. Если бы проверка маркера
жила в `check_content`, `guard.py --all` начал бы задним числом
находить каталоги `acceptance_tests/` прошлых задач без маркера —
именно то, что запрещает требование 4 SPEC. Вместо этого функция
подключается ровно туда же, где уже живёт трассируемость AC -> тест
(SPEC T023): `orchestrator/fsm.py::_tests_writing_ac_state`, единственное
место, которое исполняется только на выходе из состояния
`tests_writing`. Задача, чьё состояние уже ушло вперёд, этот код
попросту не вызывает — обратная совместимость (требование 4)
достигается тем же способом, каким FSM уже устроена (однонаправленный
переход состояний), без дополнительной даты/версии-отсечки.

Маркер ищется в докстринге МОДУЛЯ (`ast.get_docstring`, как уже делает
`scripts/codebase_map.py::extract_purpose` — статический разбор, без
импорта/исполнения файла, тот же принцип, которым уже живёт
`scripts/guard.py`). Разбор регуляркой докстринга (не всего текста
файла) — так `# Красен до реализации: ...` в комментарии тела теста
(не в докстринге) не засчитывается как маркер.

Правило применяется только к файлам `test_*.py` под
`acceptance_tests/` (SPEC требование 1 называет именно этот шаблон,
`_sandbox.py`/`__init__.py`/прочие вспомогательные файлы — не тест-файлы,
не размечаются).

Источник-агностичное ядро дублирует уже существующий приём этого
модуля (`scan_ac_content`/`traceability_errors_from_content`): одна
функция принимает уже прочитанные (label, текст) пары и не знает,
диск это или ветка задачи (SPEC T031) — `_tests_writing_ac_state`
в `orchestrator/fsm.py` вызывает её из обеих веток (диск / чужой
чекаут), тем же местом, где уже собирает `sources` для
`scan_ac_content`.

## Шаги

1. `scripts/guard.py`: добавить `ast` в импорты; функции
   `module_docstring(source)` (обёртка `ast.parse`/`ast.get_docstring`,
   `SyntaxError` -> `None`), `has_redness_marker(docstring)` (регэксп
   на «Красен до реализации:»/«Зелёный с рождения:» с непустым текстом
   после двоеточия), `redness_marker_errors_from_files(files)` (ядро:
   список (label, текст) -> список текстов ошибок «файл: нет маркера
   ...»), `scan_redness_markers(tdir)` (обёртка для рабочей копии:
   `acceptance_tests/test_*.py` с диска). Юнит-тесты в
   `tests/test_acceptance_tests_flow.py` на все четыре функции
   (докстринг с маркером/без, оба варианта формулировки, маркер с
   пустым текстом после двоеточия, не-test_*.py файл без маркера не
   ошибка).
2. `orchestrator/fsm.py::_tests_writing_ac_state`: в обеих ветках
   (диск и ветка задачи) собрать (label, текст) пары для файлов
   `test_*.py` под `acceptance_tests/`, вызвать
   `guard.redness_marker_errors_from_files`, добавить результат к
   `errors` до возврата. Ветка задачи уже собирает `paths` через
   `ls_tree_files` и читает их `gitcmd.show` — фильтр по имени файла
   (`Path(p).name.startswith("test_")`) добавляется туда же, где уже
   стоит фильтр `p.endswith(".py")`. Диск: `tdir / "acceptance_tests"`,
   `rglob("test_*.py")`, `label = str(f)`. Ветка: `label = p`
   (относительный путь в дереве, как уже делает `_read_branch_text_or_refuse`
   для сообщений об отказе).
3. `tests/test_acceptance_tests_flow.py`: обновить фикстуры
   `AC_TEST_BOTH_COVERED`, `AC_TEST_GREEN`, `AC_TEST_RED` — добавить
   докстринг модуля с маркером (существующие сценарии этих фикстур
   проверяют переход `tests_writing -> in_dev`/`review -> acceptance`
   независимо от маркера; без строки-маркера они начнут падать по НОВОЙ
   причине — не по той, что тестирует конкретный кейс). Фикстуры
   `AC_TEST_MISSING_AC2`/`AC_TEST_ESCALATE_AC2` таким же образом:
   маркер добавляется, где сценарий не про его отсутствие. Новый класс
   `RednessMarkerTest` (или расширение `TraceabilityTest`) с кейсами
   «нет маркера -> отказ и имя файла в сообщении», «маркер обеих форм
   -> переход проходит», «review -> acceptance не трогает» — тот же
   набор, что уже покрыт локальными `tasks/T064/acceptance_tests/`, но
   в общем наборе `tests/` (не залоченном), с более полными сценариями
   (несколько файлов test_*.py, один без маркера).
4. Прогнать `python3 scripts/guard.py --all`,
   `python3 -m unittest discover -s tests -v`,
   `python3 -m unittest discover -s tasks/T064/acceptance_tests -p 'test_*.py' -v`.

## Влияние на систему

Проверка подключается только к одной точке FSM
(`_tests_writing_ac_state`), которую уже вызывает единственный
переход `tests_writing -> in_dev`. Другие переходы (`review ->
acceptance`, `guard.py --all`, `spec_gate`, любые прочие) не задеты —
новая функция не вызывается ни из `check_content`, ни из
`acceptance.run`/`acceptance.summary` (прогон приёмки после `in_dev`).
Существующие проверки (`schema_errors`, обязательные секции,
трассируемость AC, допустимые статусы) не меняются — новая функция
добавляется рядом, не переписывает существующие. Откат — удалить
вызов `guard.redness_marker_errors_from_files` из
`_tests_writing_ac_state` и сами добавленные функции: переход снова
не проверяет маркер, поведение схлопывается к текущему.

Единственный побочный эффект за пределами прямой правки: фикстуры в
`tests/test_acceptance_tests_flow.py`, которые эмулируют полный
переход `tests_writing -> in_dev`/`review -> acceptance` через
`fsm.cmd_advance`, обязаны нести маркер в докстринге — иначе они
регрессируют не по своей причине. Это правки тестовой инфраструктуры
(не залоченный `tests/`, не `tasks/T064/acceptance_tests/`), не
ослабление проверки.

## Риски

Регэксп на «двоеточие + непустой текст» может неверно посчитать
маркер отсутствующим, если Оператор/test_author переносит объяснение
на следующую строку (`Красен до реализации:\n<текст>`). SPEC требует
«непустой текст ПОСЛЕ двоеточия» — трактую как «на той же логической
строке докстринга», по аналогии с уже существующим `AC_MARKER` в этом
же файле (`# AC-n: manual — причина`, тоже однострочный). Если
Оператору нужен перенос строки — эскалация правкой скила
test_author (вне `Не входит` этой задачи), не расширение регэкспа
явочным порядком.
