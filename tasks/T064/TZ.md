# ТЗ: Guard: объяснённая краснота приёмочных тестов

## Контекст

Строка P3 «Корректность залоченных тестов: объяснённая краснота +
сверка семантики». Три дефекта залоченных приёмочных тестов за неделю:
мок душил git (T051 AC-5, двухслойная ловушка run/Popen), устаревший
адрес дерева (тест T041, вскрыла T059), ассерт против ADR-0003 «kill
удаляет строку» (T060 AC-5). Общий корень: приёмочные тесты рождаются
красными по конвенции, и красный-по-неверной-причине неотличим от
красного-по-задумке; гейт выхода из tests_writing проверяет только
трассируемость (каждый AC покрыт), не смысл. Дефект лочится и
вскрывается только когда правильная реализация не может позеленить
тест — цена: операторская амнистия и лишние круги.

Образец правильной практики уже есть: test_author T050 объяснил
причину красноты каждого теста; test_author T062 провалидировал свои
тесты временным стабом корректной реализации.

## Решение (Оператор 28.08, конвейерная часть)

1. Каждый файл приёмочных тестов (tasks/<id>/acceptance_tests/test_*.py)
   обязан нести в докстринге модуля структурированный маркер причины
   красноты: строку, начинающуюся с «Красен до реализации:» с
   объяснением, ПОЧЕМУ тест красный до появления кода задачи (или
   явное «Зелёный с рождения: <почему это корректно>» для тестов,
   проверяющих сохранение существующего поведения).
2. scripts/guard.py на выходе из tests_writing (там же, где
   трассируемость AC) проверяет наличие маркера в каждом тест-файле;
   файл без маркера — именованный отказ перехода (какому файлу чего
   не хватает). Семантику объяснения guard не оценивает — это
   формальный якорь для ревью и Оператора.
3. Обратная совместимость: проверка применяется к задачам, чей выход
   из tests_writing происходит ПОСЛЕ мержа этой задачи; существующие
   каталоги acceptance_tests прошлых задач задним числом не правятся
   и краснотой guard не проверяются (лок неприкосновенен).
4. Скиловая часть (обязанность test_author прогнать тесты, объяснить
   причину каждой красноты, стаб-валидация по образцу T062) — вне
   этой задачи: скилы правит Оператор отдельным MR.

## Границы

- scripts/guard.py, тесты guard, карта. templates/ и skills/ не
  трогаются (зона Оператора).
- Не ослаблять существующие проверки guard (ADR-0002) — только
  добавление новой.

## Не входит

- Скиловая правка test-authoring (Оператор отдельно).
- Оценка семантики объяснений (это работа ревью/Оператора).
- Ретроактивные правки прошлых acceptance_tests.
- Стаб-валидация как обязательный шаг (пока рекомендация скила).

## Приёмка (минимум)

- Тест-файл без маркера «Красен до реализации:»/«Зелёный с рождения:»
  в докстринге модуля → выход из tests_writing отказывает с именем
  файла; с маркером — проходит.
- Прошлые задачи (уже вышедшие из tests_writing) не затронуты:
  их переходы/перепрогоны guard по этому признаку не режет.
- Существующие тесты зелёные; проверки guard не ослаблены.
