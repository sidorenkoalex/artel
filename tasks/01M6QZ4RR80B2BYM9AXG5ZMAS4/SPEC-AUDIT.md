# SPEC-AUDIT: target-set — замена блока профиля или компонента из файла

## ТЗ и SPEC
Требования 1–8 SPEC повторяют требования 1–8 ТЗ по смыслу и почти
дословно. ANSWER-n нет, решений Оператора на гейте SPEC нет. Критерии
ТЗ перенесены в AC-1…AC-8, отдельный AC-9 для справки добавлен из
требования 8 ТЗ. Раздел «Не входит» совпадает с ТЗ, только расширен
списком файлов только чтения из ТЗ. Требований сверх ТЗ нет. Потерь
нет.

Одно расхождение — в обе стороны дословное: ошибочная формулировка
критерия перешла из ТЗ в SPEC (AC-1, см. «Проверяемость», отклонение 1).

## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | **нет в нынешней формулировке** | Сравнение `targets.target(<проект>)["test_profile"]` с отображением файла не выполнимо ни при какой реализации: см. ниже. При исправленной формулировке ловит слияние вместо замены (старые поля `pytest-own` остались), отсутствие копии и журнала, неверный формат строки журнала |
| AC-2 | да | Сверка до записи пропускает отказ `merge_local`, слой записан |
| AC-3 | да | Новая форма унаследовала `NO_COMPONENT`; компонент слит, а не заменён; задеты соседние компоненты; нет `было (нет)` |
| AC-4 | да | Пути не проверяются по двум видам (`policy.*`/`machine.*` пишется), перечня видов нет в отказе |
| AC-5 | да (в основном) | Пропущена проверка комментария: `yamlmini` срезает комментарий, слой переписан — ловит «слой побайтно прежний». Несуществующий файл падает трассировкой, а не отказом. Снятая проверка «пустое» маскируется отказом `_render` пустому `dict` — поведение то же, мутация эквивалентна |
| AC-6 | да | Повтор пишет копию или журнал |
| AC-7 | да | Неверное число аргументов уходит в прежнюю форму без строки `TARGET_SET_USAGE` |
| AC-8 | да | Ветвление `--from-file` перехватило прежние формы; изменился текст прежних отказов |
| AC-9 | да | `TARGET_SET_USAGE`/справка без `--from-file`; строка продолжения с отступом 2 (краснеет `test_ac4_…`) |

**AC-1 недостижим (опыт).** У записи локального слоя с
`description.test_profile` подполя `weakening_scope` и
`mutation_claim_scope` обязательны: их нет в `PROFILE_OPTIONAL`,
`orchestrator/targets.py:93-94`, а проверяет их `_check_profile`,
`:1164-1170`. Жить они обязаны в `policy`: в `description.test_profile`
`merge_local` им отказывает (`:561-564`). При сведении `_flatten`
дописывает их в профиль (`orchestrator/targets.py:866-868`), а
`_with_env` — ещё и `env.PATH` из `machine.path` (`:842-845`). Прогон
показал:
- запись без `policy.weakening_scope` даёт отказ «нет подполя
  'test_profile.weakening_scope'»;
- у годной записи `merge_local(...)["test_profile"]` отличается от
  отображения в файле ключами `mutation_claim_scope` и `weakening_scope`,
  равенство False.

Значит, `targets.target(<проект>)["test_profile"] == отображение файла`
краснеет при любой реализации. Тест, написанный буквально, красный
навсегда; тест, подогнанный автором тестов, — это уже другой критерий,
чем в SPEC. Для того же AC-1 файл, перечисленный неполно («runner,
COMPOSE_REQUIRED, workdir, report»), не сводится: обязательны и
`long_lived_dir`/`long_lived_name` (`:1164-1170`), а `long_lived_dir`
должен лежать под левой частью `compose_mount` (`:1275-1280`).
Исправить можно так:
- либо сравнивать `description.test_profile` разобранного слоя с
  отображением файла;
- либо сравнивать сведённый профиль с файлом плюс подполя `policy`
  (и без `machine.path` в записи).

**Красная фаза.** Тесты зовут `artel.main()` в процессе, в песочнице
`initialized_tmp_root`. Ни git, ни подпроцессов, ни Docker, ни сети.
Рекурсии и порождения процессов нет, форма безопасна. До кода
четыре аргумента `<п> <путь> --from-file <ф>` уходят в прежний отказ
«значение — ровно один аргумент» (`projects.py:415-418`), слой не
тронут. Поэтому отказные случаи AC-4/AC-5 без проверки текста зелены
до кода тривиально. Различающую силу им дают текст перечня видов
(AC-4) и «слой побайтно прежний» после появления формы (AC-5). AC-2 и
AC-7 до кода красные: текст `compose` и строка `TARGET_SET_USAGE`
другие.

**Требование 5 без критерия.** Проверки «только листы под путём блока»
и «лист после разбора равен файлу» ни одним AC не закреплены. Реализация,
которая сверяет только `merge_local`, проходит AC-1…AC-9. Опыт: потоковые
списки с кавычками `yamlmini` отвергает, а скаляры `_render` берёт в
кавычки. Поэтому вход, на котором эти проверки различимы снаружи, найти
не удалось — они остаются страховкой, которую проверяет только ревью.

## Пути обхода гейтов
- **Имя компонента с точкой.** Требование 2 разрешает любое имя, которое
  `_render` запишет ключом, а `_render` точку в ключе пропускает
  (`projects.py:260-263`). Тогда `description.components.app.runner
  --from-file f` по букве SPEC — новый компонент `app.runner`, а не отказ.
  AC-4 проверяет отказ только для `description.test_profile.runner`,
  для компонентов аналога нет. Опечатка в пути заводит лишний компонент,
  если файл сам по себе годен для `merge_local`. SPEC не задаёт, делится
  ли путь по точке после `components.` (у `--key` это задано явно,
  `projects.py:515`). Буквальное исполнение проходит все AC.
- **Требование 5 без критерия** (см. выше). Исполнитель может обойтись
  одной `_merge_mismatches` и пройти все AC; ловит только ревью.
- Других обходов не найдено. Отказы `_target_set_load` и журнала
  требованиями 6 и 7 переносятся на новую форму явно.

   `description.components.<к>.<поле>` с `--from-file` — отказ с перечнем
   видов. Это стоит добавить в AC-4.

   `yamlmini.mapping("a: 1\na: 2")` → `{'a': 2}`. Это тот же класс потерь,
