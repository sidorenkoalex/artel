## Пути обхода гейтов
- **Д1.** Буквальное исполнение SPEC 1 («зона — пути, для которых
  `is_long_lived` истинно») даёт developer'у внешнего проекта право
  добавлять в `long_lived_dir` вне зон сколько угодно НОВЫХ модулей
  `test_<id>_<имя>.py`. Это исполняемый код в общем наборе тестов
  проекта: например, правка `sys.modules` или monkeypatch на уровне
  модуля влияет на соседние тесты той же сессии. Перечень долгоживущих
  файлов (`advance_gates/acceptance.py:87-135`) сверяет только СВОИ
  записи; чекпоинт developer'а такой файл как посторонний не закоммитит
  (`checkpoint.py:1770-1776`), но коммит самой роли проходит. У артели то
  же возможно через `tests/` из `COMMON_ZONES` (паритет), а ТЗ
  формулирует правило именно через `is_long_lived`, поэтому это не fail.
  Но под «собственными долгоживущими файлами задачи» по смыслу понимаются
  файлы test_author, и сужение доступно: пути из перечня (`long_lived_manifest`,
  `advance_gates/acceptance.py:51`). Решение — за Оператором.
- **Д2** (см. «Проверяемость»): реализация по `long_lived_prefix`
  проходит все AC и признаёт зоной подкаталоги
  `backend/tests/test_<id>_*/`, включая `conftest.py`.
- **Д4.** SPEC 2 без оговорки «внешний проект». Исполнитель вправе
  звать `decide` для любого проекта и дописывать причину отказа профиля
  к тексту гейта зон и у артели. Для артели с непрочитанным
  `test_profile` это меняет detail/hint вопреки SPEC 3 и ТЗ 3, а AC-1 с
  исправным профилем артели этого не увидит.
