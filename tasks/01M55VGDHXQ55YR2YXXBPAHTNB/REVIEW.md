# REVIEW: Гейт зон признаёт долгоживущие файлы задачи внешнего проекта

## Фаза A — план
- Таблица покрытия полна: требования 1–5 → шаг 1. Требование 4 — это
  сверка, сделанная в SPEC; правки вне `zones.py` нет, и PLAN это
  фиксирует.
- Шаг один и размером с MR: правка одной функции плюс уже залоченный
  долгоживущий файл. Свои тесты разработчик не добавляет, и это
  правильно: свойства покрыты долгоживущим файлом, повтор был бы
  замечанием по ADR-0020, п. 4.
- Подход не расходится с архитектурой. Источник профиля тот же, что у
  выхода из `tests_writing` (`project_profile.decide`), так что
  `config.COMMON_ZONES` не трогается. Импорт `project_profile` в
  `advance_gates/zones.py` цикла не даёт: модуль уже используется в
  `advance_gates/tests_writing.py`.
- «Влияние на систему» совпадает с diff: изменён только
  `orchestrator/advance_gates/zones.py` (+21/−2) и перегенерирована
  карта.

Тесты. Каждый метод долгоживущего файла несёт заявку «Ловит мутацию: …»
с наблюдаемым расхождением; группа — `долгоживущий`, это свойство кода
и верная граница. Три заявки я проверил временными мутациями (см. ниже),
все три покраснели. Утверждения существующих тестов не менялись: в
diff `tests/` есть только новый долгоживущий файл.

Граничный случай, который я проверил: при отказе профиля причина
дописывается к detail и тогда, когда вне зон лежит путь, вообще не
похожий на долгоживущий файл (например `docs/x.md`). Требование 2
SPEC это прямо требует («если дифф несёт пути вне зон, текст отказа
называет причину»), так что это не замечание. Ветка мандата ниже
дописывает к уже расширенному detail свой хвост — оба текста
сохраняются.

## Предложения системе
- Долгоживущий файл `tests/test_01m55vgdhxq55yr2yxxbpahtnb_zones_long_lived.py`
  выполнялся 64 с при пороге 60 с. Его метод AC-1 гоняет 8 полных
  `cmd_advance` на настоящем git, и на нагруженной машине (load ≈68)
  упирается в pytest-timeout 120 с одного теста. Класс «сценарный тест
  с циклом `for _ in range(N)` × полный advance» стоит учитывать в
  skills/test-authoring.md (N=1 там, где случайность имён не добавляет
  чувствительности), иначе ложные красные под нагрузкой будут
  повторяться.
- `plank-run` отказывает «планки нет», когда у задачи только
  долгоживущие файлы в `tests/`. Скил review-checklist предписывает
  гонять планку только через эту команду, но про такой случай молчит;
  стоит одной строкой сказать, что в нём долгоживущий файл гоняется
  прямым pytest.
