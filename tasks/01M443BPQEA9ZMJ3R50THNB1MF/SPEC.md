# SPEC: Указание Оператора роли в разработке и ревью; подтяжка main перед шагом разработчика

## Контекст
Команда `answer <id> <файл>` в `in_dev`/`review` принимает файл только со
строкой мандата зон или мандата тестов (`orchestrator/answer.py::_cmd_answer`),
иначе отказ «answer доступна только для задачи в состоянии escalated».
Доставка текста `ANSWER-n.md` роли на следующем шаге уже есть (бриф
разработчика — `orchestrator/brief.py::_answer_component` в
`developer_brief`, последний `ANSWER-n.md`; пакет ревью —
`orchestrator/review.py`, все `ANSWER-n.md`), не хватает приёма свободного
текста. Прецедент 04.10: найденные Оператором корневые причины 464 падений
тестов нельзя было передать разработчику в `in_dev`, три шага по $8–16 —
вслепую.

Подтяжка `main` в ветку задачи идёт только на переходах `in_dev →
verifying`, приёмки и ворот мержа (`fsm._pull_main_or_escalate` →
`orchestrator/pull.py::evaluate`); между захватом замка зоны
(`orchestrator/runner.py`, `zone_lock.claim`) и запуском разработчика
подтяжки нет. Прецедент этапа 2 ADR-0021: разработчик переписал
`orchestrator/workspace.py` поверх устаревшей версии, конфликт всплыл только
на `advance` — эскалация, `approve` и лишний шаг developer.

## Требования
1. `answer <id> <файл>` в состояниях `in_dev` и `review` принимает файл без
   строк мандатов как указание Оператора: `ANSWER-n.md` коммитится в
   артефактную ветку (ссылку документов задачи) тем же путём, что сейчас;
   состояние задачи не меняется; журнал получает отдельную запись
   «указание Оператора» с путём `ANSWER-n.md` в детали, отличимую и от
   записи мандата, и от записи ответа на эскалацию («ANSWER создан, ждёт
   approve»). Файл со строками мандатов — прежнее поведение без изменений.
2. Пустой файл указания (нулевой длины или только из пробельных символов)
   в `in_dev`/`review` — именованный отказ: сообщение называет причину
   «пустой файл указания»; `ANSWER-n.md` не создаётся, журнал записи
   «указание Оператора» не получает.
3. Рубеж «вызов не из окружения роли» (`runner.in_role_environment`)
   действует для указания так же, как для мандатов: вызов из окружения роли
   отказывается до чтения файла, роль не может выдать указание сама себе.
4. Указание доходит до роли на её следующем шаге: в `in_dev` — в бриф
   разработчика, в `review` — в пакет ревью. Поведение «в брифе
   разработчика последний `ANSWER-n.md`» сохраняется; дополнительно бриф
   разработчика несёт КАЖДЫЙ `ANSWER-n.md`, созданный после старта
   предыдущего шага разработчика этой задачи, — чтобы указание не вытеснило
   ещё не отработанный разработчиком ответ на эскалацию (решение по п.3 ТЗ).
5. Текущий шаг роли указание не прерывает и не меняет: команда принимается
   и при живом шаге роли (в том числе когда lease задачи держит идущий шаг
   `run`/`auto`), процесс шага не получает сигналов, состояние задачи и
   lease шага не меняются; указание применяется со следующего шага.
6. Перед каждым шагом разработчика — после захвата замка зоны и до запуска
   роли — пульт подтягивает `main` в ветку задачи тем же узлом
   `fsm._pull_main_or_escalate`, если ветка отстаёт от `origin/main`. Ветка
   не отстаёт — шаг идёт без подтяжки: голова ветки не меняется, коммита
   слияния нет. Конфликт, который пульт не разрешает сам, — прежняя
   эскалация с меткой «нужен шаг роли» (`PULL_CONFLICT_MARKED_STATES`),
   шаг роли в этом случае не запускается. Конфликт карты кодовой базы —
   прежнее авторазрешение.
7. Подтяжка из требования 6 не ломает существующих рубежей: рабочая копия
   перед шагом чистая (незакоммиченный код прошлого шага пульт уже
   коммитит), промежуточные WIP-коммиты ветки сохраняются в её истории,
   гонка с параллельным мержем соседней задачи разрешается тем же
   мьютексом merge-окна, что на остальных точках подтяжки.
8. Документация оператора: в `docs/operator-session.md`, раздел про
   `answer`, строка «указание в in_dev/review» — приложением к PLAN
   (защищённый путь); `docs/codebase-map.md` — по правилу регенерации.

## Критерии приёмки
AC-1. Задача в `in_dev` (и отдельно в `review`); `answer <id> <файл>` с
непустым файлом без строк мандатов, вызванная не из окружения роли,
завершается успешно: в ссылке документов задачи появляется следующий по
номеру `tasks/<id>/ANSWER-n.md` с текстом файла; состояние задачи после
команды то же (`in_dev` / `review`); в журнале задачи появляется запись
актора `operator`, действие которой содержит «указание Оператора», а
деталь — путь `tasks/<id>/ANSWER-n.md`.

AC-2. Действие журнальной записи указания отличается от действия записи
приёма файла с мандатом зон/тестов в `in_dev` и от действия записи ответа
в `escalated` («ANSWER создан, ждёт approve»): по одному действию можно
определить, какой из трёх случаев произошёл.

AC-3. Файл со строкой мандата зон или мандата тестов в `in_dev`/`review`
даёт ту же журнальную запись и тот же исход, что до задачи (действие
«ANSWER создан (мандат …)»), а не запись указания.

AC-4. Пустой файл (нулевой длины или только пробельные символы) в
`in_dev`/`review` — команда завершается ненулевым кодом с сообщением,
называющим пустой файл указания; новый `ANSWER-n.md` не создаётся,
записи «указание Оператора» в журнале нет.

AC-5. `answer` с файлом указания в `in_dev`/`review`, вызванная в
окружении роли (`runner.in_role_environment()` истинно), — отказ; новый
`ANSWER-n.md` не создаётся, записи «указание Оператора» в журнале нет.

AC-6. После указания в `in_dev` бриф следующего шага разработчика
(`brief.developer_brief`) содержит текст указания. Если до указания у
задачи был ответ на эскалацию `ANSWER-k.md`, созданный после старта
предыдущего шага разработчика, бриф содержит текст и `ANSWER-k.md`, и
указания `ANSWER-(k+1).md`.

AC-7. После указания в `review` пакет ревью следующего шага ревьювера
содержит текст указания.

AC-8. `answer` с файлом указания в `in_dev` при живом lease задачи,
которую держит идущий шаг роли (процесс жив), принимается: `ANSWER-n.md`
создан, запись «указание Оператора» есть, состояние задачи и lease шага не
изменились, процессу шага сигнал не посылался.

AC-9. Перед шагом разработчика (`run` в `in_dev`) после захвата замка зоны
и до запуска агента: ветка задачи, отстающая от `origin/main`, получает
подтяжку `main` (после шага `origin/main` — предок головы ветки, прежние
коммиты ветки, в том числе WIP-коммиты, — тоже её предки); ветка, не
отстающая от `origin/main`, — голова ветки не меняется, коммита слияния
нет; подтяжка с конфликтом, который пульт не разрешает сам, переводит
задачу в эскалацию с меткой «нужен шаг роли», агент роли не запускается
(записи «agent run started» нет).

## Оценка объёма и деление
Сработавшие сигналы (guard): число затрагиваемых модулей/файлов зоны
(зона `orchestrator/` — каталог целиком), затронут механизм, на который
опирается запись `docs/invariants.md` (lease/подтяжка/замок зоны), прогноз
диффа не дан.

Прогноз диффа: 40 КиБ (две независимые правки по 2–3 модуля плюс тесты;
ниже половины потолка гейта ёмкости).

Решение — **нарезка на 2 подзадачи** по двум пунктам бэклога, из которых
собрано ТЗ. Механики не пересекаются: указание живёт в `answer`/брифе
(`orchestrator/answer.py`, `orchestrator/brief.py`, `orchestrator/lease.py`),
подтяжка — в шаге разработчика (`orchestrator/runner.py`,
`orchestrator/fsm.py`, `orchestrator/pull.py`). Каждая часть мержима
отдельно с зелёной планкой: без второй части первая полностью работает
(указание доставляется, подтяжка остаётся на прежних точках), и наоборот.
Часть 1 первой — у неё приоритет 1 в бэклоге и прецедент с прямыми
потерями.

Довод за монолит, на усмотрение Оператора: ТЗ — решение Оператора 04.10
«на объединённую задачу» с рамкой $30, а планка бюджета не ниже $25 на
задачу даёт двум подзадачам суммарно не меньше $50. Если Оператор
оставляет монолит — секцию «## Деление» ниже удалить и вписать строку
решения; атомарной связи между частями при этом нет, монолит —
решение по стоимости, не по устройству.

монолит принят Оператором 04.10: объединённая задача по ТЗ, рамка $30, прогноз диффа 40 КиБ

## Не входит
- `docs/operator-session.md` — не зона: строка «указание в in_dev/review»
  едет приложением к PLAN (Приложением: docs/operator-session.md).
- CI ветки с приложениями PLAN — отдельная задача бэклога.
- Дозор хода шага (`watch`) — отдельная задача.
- Подтяжка `main` перед шагами других ролей (кроме developer).
- Изменение формата мандатов зон и тестов.
- Указание в состояниях, отличных от `in_dev`/`review`; поведение `answer`
  в `escalated` не меняется.
- Правка путей «только чтение» из ТЗ: `docs/adr/`, `docs/roadmap.md`,
  `docs/backlog.md`, `templates/`, `skills/`, `CLAUDE.md`, `models.yaml`,
  `roles.yaml`, `scripts/guard.py`, `.github/workflows/ci.yml`,
  `conftest.py`, `tests/test_invariants.py`, `docs/invariants.md`.
- Отдельные тесты в `tests/` на свойства AC-1…AC-9 сверх приёмочных тестов
  автора тестов (`tests/test_01m443bpqea9zmj3r50thnb1mf_*.py`, ADR-0020) —
  п.8 ТЗ («тесты с заявками „Ловит мутацию“ на пп. 1–6») закрывает именно
  эта планка.
- Неослабление существующих тестов, зелёный полный набор `tests/` и CI
  ветки — их держит пульт.
