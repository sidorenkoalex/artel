# ТЗ: указание Оператора роли в разработке и ревью; подтяжка main перед шагом разработчика

Источник: бэклог 04.10.2026 — строки «Указание Оператора роли в
in_dev/review без эскалации» (приоритет 1) и «Подтяжка main в ветку задачи
при входе в разработку» (приоритет 2); прецеденты этапа 2 ADR-0021
(01M42PENCS26D0656X8FR7DFA7, 04.10). Решение Оператора 04.10 «готовь ТЗ»
на объединённую задачу.

Факты (пин 16f663b4, сверка кода 04.10):
- `orchestrator/answer.py::_cmd_answer` (~149-230): в `escalated` файл
  ответа принимается любой; в `in_dev`/`review` — только если в нём есть
  строка мандата зон или мандата тестов, иначе отказ «answer доступна
  только для задачи в состоянии escalated». Рубеж «вызов не из окружения
  роли» (`runner.in_role_environment`) стоит перед чтением файла.
- Бриф разработчика уже включает текст последнего `ANSWER-n.md` задачи
  (`orchestrator/brief.py::_answer_component`, вызов в `developer_brief`
  ~675); пакет ревью — все `ANSWER-n.md` (`orchestrator/review.py` ~355).
  Доставка текста роли на следующем шаге, таким образом, уже есть —
  не хватает только приёма свободного текста командой.
- Прецедент: 04.10 Оператор нашёл две корневые причины 464 падений
  тестов, но передать их разработчику в `in_dev` не смог; разработчик
  оплатил ещё три шага по $8–16 вслепую. Обходом служил `reject` из
  `verifying` (его причина попадает в бриф), но в `in_dev` он недоступен.
- Подтяжка `main` в ветку задачи идёт только на переходах `in_dev →
  verifying` (`orchestrator/fsm_advance.py` ~554), приёмки
  (`orchestrator/fsm.py` ~982, `orchestrator/canary.py` ~1295) и ворот
  мержа (`orchestrator/fsm_merge_gate.py` ~626); точка входа —
  `fsm._pull_main_or_escalate` → `orchestrator/pull.py::evaluate`.
- Замок зоны берётся атомарно перед шагом разработчика
  (`orchestrator/runner.py` ~212, `zone_lock.claim`). Подтяжки между
  захватом и запуском роли нет.
- Прецедент: ветка этапа 2 ответвилась до мержа 01M42NBCADGSGTCBZB8NKBVDVH
  (та же зона); разработчик переписал `orchestrator/workspace.py` поверх
  устаревшей версии, конфликт всплыл только на `advance` — эскалация,
  `approve` и ещё один шаг developer.

Требуется:
1. `answer <id> <файл>` в `in_dev` и `review` принимает файл без строк
   мандатов как указание Оператора: `ANSWER-n.md` коммитится в
   артефактную ветку тем же путём, что сейчас; состояние задачи не
   меняется; журнал получает отдельную запись «указание Оператора» с
   путём `ANSWER-n.md`, отличимую от записи мандата и от ответа на
   эскалацию. Файл с мандатами — прежнее поведение без изменений.
   Пустой файл — именованный отказ.
2. Рубеж «вызов не из окружения роли» сохраняется для указания так же,
   как для мандатов: роль не может выдать указание сама себе.
3. Указание доходит до роли на её следующем шаге: в `in_dev` — до
   разработчика (бриф), в `review` — до ревьювера (пакет ревью).
   Если в брифе разработчика сейчас попадает только последний
   `ANSWER-n.md`, это сохраняется; SPEC решает, нужно ли что-то менять,
   чтобы указание не вытеснило ещё не отработанный ответ на эскалацию.
4. Текущий шаг роли указание не прерывает и не меняет: команда
   принимается и при живом шаге, применяется со следующего шага.
5. Перед каждым шагом разработчика — после захвата замка зоны и до
   запуска роли — пульт подтягивает `main` в ветку задачи тем же узлом
   `_pull_main_or_escalate`, если ветка отстаёт от `origin/main`.
   Ветка не отстаёт — шаг идёт без подтяжки и без лишних git-операций.
   Конфликт, который пульт не разрешает сам, — прежняя эскалация с
   меткой «нужен шаг роли» (`PULL_CONFLICT_MARKED_STATES`); шаг роли в
   этом случае не запускается. Конфликт карты кодовой базы — прежнее
   авторазрешение.
6. Подтяжка из требования 5 не ломает существующих рубежей: рабочая
   копия перед шагом чистая (незакоммиченный код прошлого шага пульт
   уже коммитит), промежуточные WIP-коммиты сохраняются, гонка с
   параллельным мержем соседней задачи разрешается тем же мьютексом,
   что на остальных точках подтяжки.
7. Документация оператора — `docs/operator-session.md`, раздел про
   `answer`: строка «указание в in_dev/review» — приложением к PLAN
   (защищённый путь); `docs/codebase-map.md` — по правилу регенерации.
8. Тесты в `tests/` с заявками «Ловит мутацию» на пп. 1–6, в том числе:
   указание в `in_dev` создаёт `ANSWER-n.md` и запись журнала, не меняя
   состояние; вызов из окружения роли — отказ; бриф следующего шага
   разработчика содержит текст указания; ветка, отставшая от main, перед
   шагом разработчика подтягивается, не отставшая — нет; конфликт
   подтяжки перед шагом — эскалация без запуска роли. Существующие тесты
   не ослабляются.
