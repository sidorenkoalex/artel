# ТЗ: Приёмочные тесты двух групп: пометка группы и проверки долгоживущих файлов (ADR-0020, задача 1)

# ТЗ: Приёмочные тесты двух групп — пометка группы в файле и проверки долгоживущих файлов на выходе из tests_writing

Источник: ADR-0020 (решение Оператора 28.09.2026, «ок по
рекомендациям»), пункты 1, 2, 4, 8, 10–12 — первая из трёх задач
внедрения; задачи 2 (запись долгоживущих файлов в `tests/` и фиксация
перечнем контрольных сумм) и 3 (`amend-tests` для `tests/`, дифф ревью)
зависят от неё и заводятся после её мержа. Предпосылка — задача
01M3MVXZXF25KYY2P213E0M39X (защищённые пути для `conftest.py`,
`pyproject.toml` и родственных настроек сбора тестов). Поглощает строки
бэклога 28.09 «Правило „свойство кода — двойник в tests/“ в правилах
автора тестов и разработчика» и «Правила ревьювера и разработчика:
сторож проверяется временной мутацией кода и прогоном tests/ без
приёмочных тестов».

Факты (origin/main cd255537):
- Приёмочные тесты задачи лежат в `tasks/<id>/acceptance_tests/` ветки
  документов `artifact/<id>`; каталог плоский
  (`scripts/guard.py::ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`), общий код —
  только модули `_*.py`.
- Строка красноты «Красен до реализации: …» / «Зелёный с рождения: …»
  стоит в докстринге модуля (`guard.REDNESS_MARKER`,
  `guard.scan_redness_markers`). Проверяется на выходе из
  `tests_writing` (`orchestrator/fsm.py::_tests_writing_ac_state`) и в
  `amend-tests` (`orchestrator/amend.py::_cmd_amend_tests`); CI старые
  каталоги задач этой проверкой не сканирует.
- Переход `tests_writing -> in_dev` — `orchestrator/fsm_advance.py::
  tests_writing`: трассируемость критериев, затем гейты через
  `_run_gates` из `orchestrator/advance_gates/tests_writing.py`
  (`_tests_writing_stray_plank_files_gate`,
  `_tests_writing_artifact_source_gate` со статической проверкой
  `guard.scan_artifact_disk_reads`, `_tests_writing_dry_collect_gate` —
  сухой сбор pytest).
- Строка «Ловит мутацию: …» (`guard.MUTATION_CLAIM`,
  `guard.test_functions_without_mutation_claim`) обязательна для новых и
  изменённых методов `tests/test_*.py` верхнего уровня; проверяет её
  `orchestrator/advance_gates/review.py::_mutation_claim_gate` только на
  `in_dev -> verifying`, для канарейки и внешнего target — не проверяет.
  В приёмочных тестах законна форма «Зелёный с рождения: …»
  (`skills/test-authoring.md`, раздел «Чувствительность»).
- Инвариант импортов `tests/test_invariants.py::
  StdlibOnlyImportsInvariantTest`: файлы верхнего уровня `tests/`
  импортируют только стандартную библиотеку, пакеты `orchestrator`,
  `scripts`, `tests`. Общий помощник тестов — `tests/sandbox.py`.
- Приёмочные тесты массово несут собственные помощники (`_sandbox.py` в
  118 каталогах, `_util.py` в 19), вставку в `sys.path` по глубине
  каталога и импорт помощника по голому имени — проба 27.09 дала на этом
  126 ошибок сбора при совместном прогоне.
- Корневой `conftest.py` запрещает роли полный прогон `tests/`; прогон
  названных файлов разрешён.
- Правило `skills/review-checklist.md` «Долгоживущие свойства — в
  `tests/`, не только в планке» — временная мера (ADR-0020, пункт 10).

Требуется:
1. Каждый файл `test_*.py` приёмочных тестов задачи несёт в докстринге
   модуля строку группы с одним из двух значений: долгоживущий или
   разовый (точный текст строки выбирает SPEC, по образцу
   `guard.REDNESS_MARKER`; правило разбора — в одном месте
   `scripts/guard.py`). Отсутствие строки или неизвестное значение —
   ошибка с именем файла. Проверка стоит там же, где проверка строки
   красноты: на выходе из `tests_writing` и в `amend-tests`. Модули
   `_*.py` и прочие разрешённые файлы строку не несут. Приёмочные тесты,
   зафиксированные до мержа этой задачи, не проверяются.
2. Долгоживущий файл статически проверяется на выходе из
   `tests_writing`: не читает `tasks/`, не обращается к git (модули
   `gitcmd`, `artifact_branch`, `subprocess` с `git`, база и дифф ветки),
   не ссылается на номер задачи, не вставляет пути в `sys.path` и не
   импортирует собственные помощники задачи по голому имени — импорт
   только из стандартной библиотеки, `orchestrator`, `scripts`, `tests`
   (тот же перечень, что у `StdlibOnlyImportsInvariantTest`). Перечень
   признаков выбирает SPEC по образцу `guard.scan_artifact_disk_reads`.
   Тот же разбор отказывает долгоживущему файлу при обращении к
   внутреннему устройству кода (ADR-0020, «Следствия», решение Оператора
   29.09.2026): импорт имени с подчёркиванием из `orchestrator` или
   `scripts`; подмена внутреннего имени (`patch`/`patch.object` с путём
   или атрибутом, чьё имя начинается с подчёркивания); чтение закрытого
   атрибута объекта пульта (`obj._x`). Имена `tests/sandbox.py` под
   запрет не попадают.
   Ошибка называет файл, строку и признак.
3. Каждый тестовый метод долгоживущего файла несёт строку «Ловит
   мутацию: …»; форма «Зелёный с рождения: …» для метода долгоживущего
   файла не принимается. Правило одно с
   `review._mutation_claim_gate` (общий узел в `scripts/guard.py`, без
   второй копии правила). Для разовых файлов — как сейчас.
4. Долгоживущий файл, удовлетворяющий требованию 2, собирается pytest
   как из каталога приёмочных тестов, так и из `tests/`: сухой сбор на
   выходе из `tests_writing` распространяется на него без ослабления;
   SPEC называет, как доказано второе место (тест: тот же файл в `tests/`
   песочницы собирается).
5. Нарушение требований 1–4 — отказ перехода `tests_writing -> in_dev`
   с записью в журнал задачи и подсказкой test_author «исправь файл и
   повтори»; задача остаётся в `tests_writing`, `amend-tests` не
   требуется.
6. Область: задачи target `artel` (`config.DEFAULT_TARGET`), включая
   канареечные. Для внешнего target строка группы не требуется, проверки
   требований 2–4 не применяются. Задача без приёмочных тестов
   (`skip_tests`) не затронута.
7. Правила ролей (приложениями):
   - `skills/test-authoring.md`: две группы и критерий отнесения
     (свойство кода, обязанное держаться после мержа, — долгоживущий;
     разница с базой ветки, «файл не тронут», чтение `tasks/<id>/` —
     разовый); строка группы; правила долгоживущего файла (только
     публичный интерфейс кода, «Ловит мутацию» у каждого метода,
     помощники — `tests/sandbox.py`, без своих `_util.py`/`_sandbox.py`);
     строка в докстринге модуля, называющая заменяемый чужой тест
     (ADR-0020, пункт 8; форму выбирает SPEC); свойство проверяется на
     нескольких входах, а где естественно — на входах, порождаемых при
     каждом запуске модулем `random` с печатью зерна (против подгонки
     кода под входы теста). До мержа задачи 2 долгоживущие файлы лежат
     в каталоге приёмочных тестов.
   - `skills/escalation-rules.md`: разработчик, которому зафиксированный
     тест навязывает внутреннее устройство кода, эскалирует с кодом
     причины, а не подгоняет устройство; ответ Оператора — правка теста
     командой `amend-tests` (ADR-0012).
   - `skills/coding-standards.md`: до мержа задачи 2 разработчик пишет в
     `tests/` двойника для свойства долгоживущего файла (строка бэклога
     28.09 «двойник в tests/»); сторож проверяется временной мутацией:
     временно сломать код так, как заявлено в «Ловит мутацию», прогнать
     названные файлы `tests/` без приёмочных тестов (не весь набор —
     его запрещает `conftest.py`), убедиться, что тест красный, вернуть
     код.
   - `skills/review-checklist.md`: ревьювер проверяет границу групп —
     факт задачи, помеченный долгоживущим, и свойство кода, помеченное
     разовым, — замечание; приём «временная мутация» для проверки
     сторожа; пункт «код решает задачу в общем виде, а не для входов
     приёмочного теста». Временное правило «Долгоживущие свойства — в `tests/`» не
     снимается и не переформулируется (ADR-0020, пункт 10).
8. Тесты (`tests/`, песочница `tests/sandbox.py`): файл без строки
   группы — отказ с именем файла; неизвестное значение — отказ;
   долгоживущий файл с литералом `tasks/`, с вызовом git, с номером
   задачи, со вставкой в `sys.path`, с импортом `_sandbox` по голому
   имени, с импортом имени с подчёркиванием из `orchestrator`, с
   `patch` внутреннего имени, с чтением закрытого атрибута — отказ с
   признаком (заявка мутации «проверка признака снята»);
   разовый файл с теми же признаками — не отказ; метод долгоживущего
   файла без «Ловит мутацию» или с «Зелёный с рождения» — отказ;
   внешний target — проверки не применяются; `amend-tests` с файлом без
   строки группы — отказ. Полный набор `tests/` зелёный; ни один
   существующий тест и гейт не ослаблен.

Зоны: scripts/guard.py, orchestrator/fsm.py, orchestrator/fsm_advance.py,
