# SPEC: Приёмочные тесты двух групп — строка группы в файле и проверки долгоживущих файлов на выходе из tests_writing

## Контекст
ADR-0020 (решение Оператора 28.09.2026) делит приёмочные тесты задачи на
две группы: долгоживущие (свойство кода, обязанное держаться после мержа)
и разовые (факт этой задачи: разница с базой ветки, «файл не тронут»,
чтение `tasks/<id>/`). Эта задача — первая из трёх во внедрении:
разметка группы в каждом файле `test_*.py` приёмочных тестов, статические
проверки долгоживущих файлов на переходе `tests_writing -> in_dev` и
правила ролей. Сейчас группы нет: приёмочные тесты массово несут
собственные помощники (`_sandbox.py` в 118 каталогах, `_util.py` в 19),
вставку в `sys.path` и импорт помощника по голому имени — проба 27.09
дала 126 ошибок сбора при совместном прогоне. Задачи 2 (запись
долгоживущих файлов в `tests/`, перечень контрольных сумм) и 3
(`amend-tests` для `tests/`, дифф ревью) зависят от этой и заводятся
после её мержа. Предпосылка — задача 01M3MVXZXF25KYY2P213E0M39X
(смержена).

## Требования

1. **Строка группы.** Каждый файл `test_*.py` каталога приёмочных тестов
   задачи (`tasks/<id>/acceptance_tests/`) несёт в докстринге модуля
   строку группы ровно одного из двух видов:
   - `Группа: долгоживущий`
   - `Группа: разовый`

   Правило разбора (регулярное выражение по образцу
   `guard.REDNESS_MARKER`: метка `Группа:`, значение на той же строке) и
   перечень допустимых значений живут в одном месте — `scripts/guard.py`;
   все места проверки вызывают этот узел, второй копии правила нет.
   Отсутствие строки — ошибка с именем файла; строка с иным значением —
   ошибка с именем файла и неизвестным значением. Модули `_*.py` и прочие
   файлы, разрешённые `guard.ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`, строку не
   несут и не проверяются.
2. **Где проверяется строка группы:** там же, где строка красноты — на
   выходе из `tests_writing` (`orchestrator/fsm.py::_tests_writing_ac_state`
   или рядом, в пути перехода `tests_writing -> in_dev`) и в
   `amend-tests` (`orchestrator/amend.py::_cmd_amend_tests`). Приёмочные
   тесты, зафиксированные до мержа этой задачи, не проверяются (в том
   числе в `amend-tests` задачи, чья планка зафиксирована до мержа).
3. **Статическая проверка долгоживущего файла** на выходе из
   `tests_writing` (разбор AST по образцу `guard.scan_artifact_disk_reads`,
   узел в `scripts/guard.py`). Признаки отказа:
   1. `tasks/` — строковый литерал, содержащий `tasks/`;
   2. `git-модуль` — импорт `orchestrator.gitcmd` или
      `orchestrator.artifact_branch` в любой форме (`import …`,
      `from orchestrator import gitcmd`, `from orchestrator.gitcmd import …`);
   3. `git-вызов` — вызов функции модуля `subprocess` (или `os.system`),
      в аргументах которого есть литерал `git` первым элементом команды
      либо строка, начинающаяся с `git `;
   4. `номер задачи` — строковый литерал или имя, содержащее
      идентификатор этой задачи в любом регистре;
   5. `sys.path` — вызов `sys.path.insert`/`append`/`extend` или
      присваивание в `sys.path` (целиком или по индексу/срезу);
   6. `импорт вне перечня` — импорт, чей модуль верхнего уровня не из
      стандартной библиотеки и не `orchestrator`, `scripts`, `tests`
      (тот же перечень, что у
      `tests/test_invariants.py::StdlibOnlyImportsInvariantTest`), а также
      любой относительный импорт; сюда попадает импорт собственного
      помощника задачи по голому имени (`import _sandbox`, `from _util
      import …`);
   7. `закрытое имя` — импорт из `orchestrator` или `scripts`, где
      импортируемое имя или сегмент пути модуля начинается с одного
      подчёркивания (`from orchestrator.fsm import _x`,
      `import orchestrator.advance_gates._base`);
   8. `patch закрытого` — вызов `patch`/`mock.patch`/`unittest.mock.patch`
      со строковым путём, сегмент которого начинается с подчёркивания,
      и `patch.object` с именем атрибута, начинающимся с подчёркивания;
   9. `закрытый атрибут` — обращение `obj._x` (одно подчёркивание, не
      dunder), кроме случаев, когда корень цепочки — `self`/`cls` или имя,
      привязанное импортом из стандартной библиотеки или из пакета `tests`.

   Имена `tests/sandbox.py` (и пакета `tests` в целом) под признаки 7–9
   не попадают. Ошибка называет файл, строку и признак (в формулировке
   списка выше). Разовые файлы этой проверке не подвергаются.
4. **«Ловит мутацию» у каждого метода долгоживущего файла.** Каждая
   тестовая функция/метод `test_*` долгоживущего файла несёт в докстринге
   строку `Ловит мутацию: …` (`guard.MUTATION_CLAIM`); строка «Зелёный с
   рождения: …» в докстринге метода её не заменяет. Правило — тот же узел
   `scripts/guard.py`, что использует
   `orchestrator/advance_gates/review.py::_mutation_claim_gate`
   (`guard.test_functions_without_mutation_claim`), без второй копии.
   Ошибка называет файл и метод. Для разовых файлов — как сейчас (не
   проверяется на этом переходе).
5. **Сбор pytest долгоживущего файла из двух мест.** Сухой сбор на выходе
   из `tests_writing` (`_tests_writing_dry_collect_gate`) распространяется
   на долгоживущие файлы без ослабления. Сбор того же файла из `tests/`
   доказывается тестом в `tests/`: долгоживущий файл, проходящий
   требование 3, скопированный в каталог `tests/` песочницы
   (`tests/sandbox.py`), собирается `pytest --collect-only` без ошибок.
6. **Отказ перехода.** Нарушение требований 1–5 на выходе из
   `tests_writing` — отказ перехода `tests_writing -> in_dev`: запись в
   журнал задачи с перечнем ошибок и подсказкой test_author «исправь файл
   и повтори»; задача остаётся в `tests_writing`, `amend-tests` не
   требуется.
7. **Область.** Проверки требований 1–5 применяются к задачам target
   `artel` (`config.DEFAULT_TARGET`), включая канареечные. Для внешнего
   target строка группы не требуется, проверки требований 3–5 не
   применяются. Задача с `skip_tests` не затронута.
8. **Правила ролей — приложениями к PLAN** (защищённые пути, применяет
   пульт на мерже; каждое приложение проходит `git apply --check`):
   - `skills/test-authoring.md`: две группы и критерий отнесения
     (свойство кода, обязанное держаться после мержа, — долгоживущий;
     разница с базой ветки, «файл не тронут», чтение `tasks/<id>/` —
     разовый); точный текст строки группы из требования 1; правила
     долгоживущего файла (только публичный интерфейс кода, «Ловит
     мутацию» у каждого метода, помощники — `tests/sandbox.py`, без своих
     `_util.py`/`_sandbox.py`); строка в докстринге модуля, называющая
     заменяемый чужой тест, в форме `Заменяет: tests/<файл>.py::<Класс>::<метод>`
     (ADR-0020, пункт 8); свойство проверяется на нескольких входах, а где
     естественно — на входах, порождаемых при каждом запуске модулем
     `random` с печатью зерна; до мержа задачи 2 долгоживущие файлы лежат
     в каталоге приёмочных тестов.
   - `skills/escalation-rules.md`: разработчик, которому зафиксированный
     тест навязывает внутреннее устройство кода, эскалирует с кодом
     причины, а не подгоняет устройство; ответ Оператора — правка теста
     командой `amend-tests` (ADR-0012).
   - `skills/coding-standards.md`: до мержа задачи 2 разработчик пишет в
     `tests/` двойника для свойства долгоживущего файла; сторож
     проверяется временной мутацией: временно сломать код так, как
     заявлено в «Ловит мутацию», прогнать названные файлы `tests/` без
     приёмочных тестов (не весь набор — его запрещает `conftest.py`),
     убедиться, что тест красный, вернуть код.
   - `skills/review-checklist.md`: ревьювер проверяет границу групп (факт
     задачи, помеченный долгоживущим, и свойство кода, помеченное
     разовым, — замечание); приём «временная мутация» для проверки
     сторожа; пункт «код решает задачу в общем виде, а не для входов
     приёмочного теста». Временное правило «Долгоживущие свойства — в
     `tests/`, не только в планке» не снимается и не переформулируется.
9. **Тесты в `tests/`** на песочнице `tests/sandbox.py`, каждый новый
   метод — со строкой «Ловит мутацию: …» (для проверок признаков
   требования 3 — мутация «проверка признака снята»). Полный набор
   `tests/` зелёный; ни один существующий тест и гейт не ослаблен.

## Критерии приёмки

AC-1. Файл `test_*.py` приёмочных тестов задачи target `artel` без строки
группы в докстринге модуля — отказ перехода `tests_writing -> in_dev`;
текст отказа содержит имя файла.

AC-2. Файл со строкой `Группа: <значение>`, где значение не `долгоживущий`
и не `разовый`, — отказ перехода с именем файла.

AC-3. Файлы `_*.py` и прочие разрешённые файлы каталога приёмочных тестов
без строки группы отказа не вызывают; файлы `test_*.py` с корректной
строкой любой из двух групп (и без нарушений AC-5/AC-6) переход не
блокируют.

AC-4. `amend-tests` задачи, чья планка зафиксирована после мержа этой
задачи, с файлом `test_*.py` без строки группы — отказ с именем файла;
приёмочные тесты, зафиксированные до мержа этой задачи, строкой группы не
проверяются.

AC-5. Долгоживущий файл с любым из девяти признаков требования 3
(литерал `tasks/`; импорт `gitcmd`/`artifact_branch`; вызов git через
`subprocess`; идентификатор задачи; изменение `sys.path`; импорт
`_sandbox` по голому имени или иной импорт вне перечня; импорт имени с
подчёркиванием из `orchestrator`/`scripts`; `patch`/`patch.object`
закрытого имени; чтение закрытого атрибута `obj._x`) — отказ перехода;
текст ошибки называет файл, строку и признак. Каждый признак покрыт
отдельным тестом в `tests/`.

AC-6. Разовый файл с теми же признаками, что в AC-5, отказа по ним не
получает.

AC-7. Долгоживущий файл, импортирующий `tests.sandbox` и использующий его
имена (в том числе с подчёркиванием), `patch` публичного имени и
`self._x`, отказа по требованию 3 не получает.

AC-8. Тестовый метод долгоживущего файла без строки «Ловит мутацию: …» —
отказ перехода с именем файла и метода; метод, чей докстринг несёт только
«Зелёный с рождения: …», — тоже отказ. Метод разового файла без «Ловит
мутацию» на этом переходе отказа не вызывает.

AC-9. Проверка AC-8 вызывает тот же узел `scripts/guard.py`, что и
`orchestrator/advance_gates/review.py::_mutation_claim_gate`; разбор
строки группы — одна функция/регулярное выражение в `scripts/guard.py`,
вызываемая и на выходе из `tests_writing`, и в `amend-tests`.

AC-10. Долгоживущий файл, проходящий требование 3, собирается
`pytest --collect-only` без ошибок, будучи помещён в каталог `tests/`
песочницы (тест в `tests/`); сухой сбор на выходе из `tests_writing`
применяется к долгоживущим файлам, существующие проверки сухого сбора не
ослаблены.

AC-11. При отказе по AC-1, AC-2, AC-5, AC-8 задача остаётся в
`tests_writing`, в журнале задачи — запись отказа с перечнем ошибок и
подсказкой «исправь файл и повтори»; после исправления файла повторный
`advance` проходит без `amend-tests`.

AC-12. Задача внешнего target (target ≠ `config.DEFAULT_TARGET`) с файлом
без строки группы и с файлом `Группа: долгоживущий`, несущим признаки
требования 3 и метод без «Ловит мутацию», на выходе из `tests_writing` отказа по этим проверкам не
получает; канареечная задача target `artel` проверяется так же, как
обычная.

AC-13. PLAN несёт четыре приложения — к `skills/test-authoring.md`,
`skills/escalation-rules.md`, `skills/coding-standards.md`,
`skills/review-checklist.md` — с содержанием требования 8; каждое
применяется `git apply --check` на чистом дереве; временное правило
«Долгоживущие свойства — в `tests/`, не только в планке» в
`skills/review-checklist.md` приложением не удалено и не изменено.

AC-14. Полный набор `tests/` зелёный; ни один существующий тест, гейт или
проверка guard не ослаблены и не удалены; каждый новый тестовый метод в
`tests/` несёт «Ловит мутацию: …».

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны `orchestrator/`/`scripts/`,
упомянутых в SPEC, ≥ 5 (`scripts/guard.py`, `orchestrator/fsm.py`,
`orchestrator/fsm_advance.py`, `orchestrator/advance_gates/tests_writing.py`,
`orchestrator/amend.py`, плюс упомянутые только для чтения
`orchestrator/advance_gates/review.py`); число критериев приёмки ≥ 10
(14). Прогноз диффа: 60 КиБ (guard ~15, тесты `tests/` ~30, четыре
приложения ~10, гейты/amend ~5) — ниже половины потолка гейта ёмкости.

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
задача уже есть отрезок нарезки ADR-0020 (задача 1 из 3). Внутри неё
неразрезаемо сочетание «гейт требует строку группы / признаки
долгоживущего файла» и «правило test_author говорит, какую строку писать
и чего не делать в долгоживущем файле»: гейт без приложения к
`skills/test-authoring.md` отказывает каждой задаче target `artel` на
выходе из `tests_writing`, пока правило не придёт отдельным мержем, —
промежуточное состояние конвейера нерабочее. Обратный порядок (сначала
правила ролей, затем код) технически мержим, но оставляет роли с
правилом, которое ничем не проверено, и требует отдельного цикла analyst
→ review ради текста приложений. Кодовая часть (guard + три места вызова
+ тесты) делится только поперёк `scripts/guard.py`, общего для всех
проверок. Решение — за Оператором.

оркестратора ($50). Рамка ТЗ ($30) ниже калибровки более чем на треть;

## Не входит

  на кодовую ветку, перечень контрольных сумм и его сверка, префикс имени
  файла (задача 2).
- `amend-tests` для файлов в `tests/`, исключение из диффа ревью,
  `docs/stack.md` (задача 3).

  `tests/`» (отдельная строка бэклога, ADR-0020, пункт 10).
- Исполнение заявок мутации пультом.
- Перенос приёмочных тестов смерженных задач; проверка ранее
  зафиксированных приёмочных тестов.
- Распространение на внешние target.
- Проверки требований 3–5 в `amend-tests` (там — только строка группы).
- Правка файлов только для чтения: `orchestrator/advance_gates/review.py`,
  `orchestrator/checkpoint.py`, `orchestrator/acceptance.py`,
  `orchestrator/role_prompt.py`, `orchestrator/brief.py`,
  `orchestrator/config.py`, `conftest.py`, `pyproject.toml`,
  `tests/test_invariants.py`, `docs/invariants.md`, `docs/adr/`,
  `docs/triggers.md`, `docs/backlog.md`, `templates/`, приёмочных тестов
  других задач в `tasks/`.
