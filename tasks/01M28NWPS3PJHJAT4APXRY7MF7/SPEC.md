# SPEC: гонка гейта зон при одновременном старте — проверка конфликта и захват зоны одной транзакцией

## Контекст

Занятость зоны определяется журналом: задача занимает свои зоны, когда в
текущем пребывании есть запись `agent run started` актора `developer`
(`zone_lock._occupies`). Проверка конфликта (`zone_lock.blocking_conflict`
из `runner.cmd_run`) и запись `agent run started` (`runner.run_agent_once`,
после сборки промпта и окружения) разнесены на секунды. 11.09 два цикла
`auto` стартовали developer в одну секунду (01M1THKWFX и 01M1VBEFR9, обе с
зоной `orchestrator/fsm_advance.py`): каждая проверила конфликт до того,
как другая записала старт, обе прошли; третья задача (01M27JPEGC) секундой
позже увидела занятость. Итог: два разработчика правят один файл в
параллельных ветках, у второй конфликт подтяжки на мерже гарантирован;
одну задачу пришлось снимать руками.

## Требования

1. Захват зоны — атомарно с проверкой: в `runner._cmd_run` для роли
   `developer` проверка `zone_lock.blocking_conflict` и запись признака
   занятости идут в одной транзакции SQLite (`BEGIN IMMEDIATE` через
   `store`, тем же приёмом, что compare-and-swap состояния). Признак
   занятости — отдельная журнальная запись `zone claimed` актора
   `developer` (`zone_lock.CLAIM_ACTION`), которую `_occupies` считает
   наравне с `agent run started`; пишется ДО сборки промпта и спавна
   агента, в той же транзакции, что и проверка.
2. Если после захвата шаг не стартовал (отказ бюджета, паузы, лимита
   параллельности, ошибка окружения — любая причина, из-за которой
   `_cmd_run` завершается до фактического запуска агента ролью
   `developer`) — захват снимается записью `zone claim released` в той же
   функции, чтобы задача не считалась занявшей зону без работающего
   разработчика; `_occupies` учитывает снятие (последняя из записей
   `claimed`/`released` решает).
3. `_occupies` и `blocking_conflict` не меняют семантику для остальных
   вызывающих (`catalog`, `doctor`, `auto._wait_for_zone`): задача с
   действующим захватом видна как занявшая зону так же, как с
   `agent run started`.

## Критерии приёмки

AC-1. В `runner._cmd_run` для роли `developer` проверка
`zone_lock.blocking_conflict` и запись журнальной отметки занятости
(`zone claimed`, актор `developer`, `zone_lock.CLAIM_ACTION`) выполняются
в одной транзакции SQLite (`BEGIN IMMEDIATE` через `store`, тем же приёмом,
что compare-and-swap состояния), ДО сборки промпта и спавна агента.

AC-2. `zone_lock._occupies` считает запись `zone claimed` наравне с
`agent run started`: действующий (не снятый более поздней записью)
захват актора `developer` после границы текущего пребывания
(`_stay_since_id`) делает задачу занявшей зону.

AC-3. Если в рамках того же вызова `cmd_run` шаг фактически не стартовал
после захвата (отказ бюджета, паузы, лимита параллельности, ошибка
окружения — любая причина возврата/выхода до фактического запуска
агента ролью `developer`), захват снимается записью `zone claim released`
в той же функции.

AC-4. `_occupies` учитывает снятие захвата: если после `zone claimed` для
задачи есть более поздняя (по id записи журнала) `zone claim released` и
нет более поздней `agent run started`, задача не считается занявшей зону.

AC-5. Семантика `_occupies`/`blocking_conflict` для остальных вызывающих
(`catalog`, `doctor`, `auto._wait_for_zone`) не меняется: задача с
действующим захватом видна занявшей зону так же, как с
`agent run started`.

AC-6. Тест (`tests/test_zone_lock.py` и/или `tests/test_zones_gate.py`):
два конкурентных `cmd_run` (два потока или два процесса на одной БД) для
задач с общей зоной — ровно один стартует, второй получает именованный
отказ занятости зоны; мутация «проверка блокировки вне единой транзакции с
записью захвата» делает этот тест красным (оба стартуют).

AC-7. Тест: отказ старта после захвата (например, отказ бюджета, паузы,
лимита параллельности либо ошибки окружения) снимает захват записью
`zone claim released`; после снятия следующий кандидат на ту же зону
проходит проверку блокировки.

AC-8. Существующие тесты `tests/test_zone_lock.py` и
`tests/test_zones_gate.py` (гейт зон, ожидание зоны, `zone-release`)
остаются зелёными без правки существующих утверждений.

## Не входит

- Очередь ожидания зоны с приоритетами (`zone_lock.queue_order`/
  `cmd_zone_reorder`) — не меняется этой задачей.
- Зоны для внешних target — механика остаётся только для основного
  (dogfood) target'а.
