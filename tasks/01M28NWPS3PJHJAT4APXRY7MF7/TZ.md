# ТЗ: гонка гейта зон при одновременном старте — проверка конфликта и захват зоны одной транзакцией

Источник: копилка 11.09. Занятость зоны определяется журналом: задача
занимает свои зоны, когда в текущем пребывании есть запись
`agent run started` актора `developer` (`zone_lock._occupies`).
Проверка конфликта (`zone_lock.blocking_conflict` из `runner.cmd_run`)
и запись `agent run started` (`runner.run_agent_once`, после сборки
промпта и окружения) разнесены на секунды. 11.09 два цикла `auto`
стартовали developer в одну секунду (01M1THKWFX и 01M1VBEFR9, обе с
зоной `orchestrator/fsm_advance.py`): каждая проверила конфликт до
того, как другая записала старт, обе прошли; третья задача (01M27JPEGC)
секундой позже увидела занятость. Итог: два разработчика правят один
файл в параллельных ветках, у второй конфликт подтяжки на мерже
гарантирован; одну задачу пришлось снимать руками.

Требуется:
1. Захват зоны — атомарно с проверкой: в `runner.cmd_run` для роли
   `developer` проверка `blocking_conflict` и запись признака занятости
   идут в одной транзакции SQLite (`BEGIN IMMEDIATE` через `store`,
   тем же приёмом, что compare-and-swap состояния). Признак занятости —
   отдельная журнальная запись `zone claimed` актора `developer`
   (`zone_lock.CLAIM_ACTION`), которую `_occupies` считает наравне с
   `agent run started`; пишется ДО сборки промпта и спавна агента, в той
   же транзакции, что и проверка.
2. Если после захвата шаг не стартовал (отказ бюджета, паузы, лимита
   параллельности, ошибка окружения) — захват снимается записью
   `zone claim released` в той же функции, чтобы задача не считалась
   занявшей зону без работающего разработчика; `_occupies` учитывает
   снятие (последняя из записей `claimed`/`released` решает).
3. `_occupies` и `blocking_conflict` не меняют семантику для остальных
   вызывающих (`catalog`, `doctor`, `auto._wait_for_zone`): задача с
   действующим захватом видна как занявшая зону так же, как с
   `agent run started`.
4. Тесты `tests/test_zone_lock.py` / `tests/test_zones_gate.py`:
   (а) два конкурентных `cmd_run` (два потока или два процесса на одной
   БД) для задач с общей зоной — ровно один стартует, второй получает
   именованный отказ занятости (мутация «проверка вне транзакции» —
   красная: оба стартуют); (б) отказ старта после захвата снимает захват,
   следующий кандидат проходит; (в) существующие тесты гейта зон,
   ожидания зоны и `zone-release` зелёные без правки утверждений.

Зоны: orchestrator/runner.py, orchestrator/zone_lock.py,
orchestrator/store.py, tests/.
Порядок: без зависимостей.

Не входит: очередь ожидания зоны с приоритетами; зоны для внешних target.
