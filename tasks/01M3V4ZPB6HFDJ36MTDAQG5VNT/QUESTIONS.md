# QUESTIONS: Канарейка Codex: авторизация при изолированном доме без записи в боевой профиль

## Вопросы

1. **Какой из документированных каналов учётных данных Оператор разрешает для изолированного клона канарейки?** — исследование завершено без чтения токенов, Keychain и боевого профиля. Официальная справка Codex называет `cli_auth_credentials_store = ephemeral` только хранилищем кэша текущего процесса; она не подтверждает, что этот режим или отдельный `CODEX_HOME` может безопасно читать уже существующий вход ChatGPT другого дома. Установленный Codex CLI 0.157.1 не показывает в `codex login status --help` команды переноса/разделения такого входа; доступный Cask содержит бинарник, но не исходный код механизма авторизации. Документированы два других канала: `CODEX_ACCESS_TOKEN` в окружении для временной автоматизации и WIF для Codex в управляемом ChatGPT workspace. Первый вводит секрет в процесс роли, второй требует включения beta-функции, настройки администратора, внешнего IdP и файла identity token; оба выходят за текущие инварианты, где эти переменные запрещены, а роль получает только подписочный вход Keychain. Варианты: A) разрешить ограниченный по сроку `CODEX_ACCESS_TOKEN` и отдельный доверенный держатель секрета, который передаёт его только предполёту и процессу клона; одновременно явно разрешить изменение инварианта, определить хранение, ротацию, очистку и защиту логов; B) разрешить WIF для отдельного канареечного principal в управляемом ChatGPT workspace и предоставить Оператору настройку workspace/IdP и несекретную схему переменных с identity-token file; C) назвать иной официальный механизм совместного использования уже имеющегося ChatGPT-входа между разными `CODEX_HOME`, его версию CLI и разрешённые операции с хранилищем; D) не реализовывать изменение до появления одного из разрешённых каналов. — дефолт: D, поскольку подтверждённого способа выполнить требования ТЗ без нового права на учётные данные или изменения инварианта нет.

## Контекст эскалации

- Официальная документация: [Configuration Reference](https://learn.chatgpt.com/docs/config-file/config-reference) описывает варианты credential store и `ephemeral` как память текущего процесса; [Access tokens](https://learn.chatgpt.com/docs/enterprise/access-tokens) предписывает для временной автоматизации `CODEX_ACCESS_TOKEN`, а для постоянного входа — `codex login --with-access-token`; [Workload identity federation](https://developers.openai.com/api/docs/guides/workload-identity-federation) описывает WIF для Codex как beta-функцию управляемого ChatGPT workspace.
- В пульте текущие `orchestrator/providers/codex.py::FORBIDDEN_KEY_ENV_NAMES` запрещают `CODEX_ACCESS_TOKEN`, а `CodexProvider.environment()` не передаёт секреты; `orchestrator/canary.py::_ephemeral_clone` создаёт самостоятельные `HOME` и `CODEX_HOME`. Текущий перенос указателя Keychain уже не подтверждает вход в новом доме по ТЗ и `ANSWER-1.md`.

## Блокирует

SPEC с проверяемым решением авторизации: без выбранного Оператором канала нельзя одновременно требовать реальный шаг Codex в изолированном доме, запрет записи в боевой профиль и запрет работы с учётными данными.
