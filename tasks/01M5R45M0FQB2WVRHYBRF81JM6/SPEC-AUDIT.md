Не подтвердилось:
- **Ф-1.** Требование 2 и AC-7 описывают git без `--path-format` (пол 2.30) как «ненулевой код». На деле `git rev-parse` печатает неизвестный ему флаг в stdout и отвечает кодом 0. Проверено на 2.50.1 неизвестным флагом `--path-format-bogus=absolute`: три строки — корень, сам флаг, путь индекса; код 0. Значит, на git 2.30 объединённый вызов даёт код 0 и три строки, и запасной путь включает ветка «не ровно две строки», а не ненулевой код. Попутно: на 2.30 прежний второй вызов (:2924) тоже печатает две строки, `copyfile` по склеенной строке падает, и прежний `worktree=True` там уже отвечает `None`. Запасной путь пола нужен по существу только для `worktree=False`.

## Пути обхода гейтов
- **П-1 (AC-7, требование 2).** Исполнитель может проверять число строк условием `len(lines) < 2` вместо `!= 2`. Такая реализация проходит AC-6 (заглушка из одной строки) и AC-7 (заглушка с ненулевым кодом). Реальный ответ git без `--path-format` — три строки с кодом 0 (Ф-1): он остался бы без проверки. Вред на полу 2.30 сейчас не наблюдаем, но AC, заявленный как проверка запасного пути пола, моделирует не тот отказ.
- **П-2 (требование 1ж, AC-1/AC-4).** Число вызовов в запасных путях («плюс один `rev-parse`»; при отсутствующей ссылке ровно два) ни один AC не считает. Повторный `_head` или лишнее разрешение ссылки в запасном пути пройдут все критерии.
- **Гонка в запасных путях 1а/1в/1г** выведена из охвата явно («Не входит», уточнение ТЗ 9). Это не обход, а принятое решение.
