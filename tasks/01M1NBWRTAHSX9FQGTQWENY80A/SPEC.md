# SPEC: Ответы Оператора в брифе ревьювера

## Контекст
Инцидент 04.09 (задача 01M1KCSTBYF1CRJBSY4P6VYQEA): добавка брифа с
последним `ANSWER-n.md` (`orchestrator/brief.py`, SPEC T075 AC-6)
выдаётся только analyst/test_author/developer — ревьювер её не
получает. Когда ревьювер сам эскалирует (залоченная планка красна не
по вине реализации), ответ Оператора с мандатом ADR-0012 до него не
доходит: повторный шаг ревьювера эскалирует снова тем же вопросом
(бюджет тратится впустую), и задача не может выйти из `review` иначе
как ручной правкой планки Оператором.

## Требования

1. Ревью-пакет (`orchestrator/review.py::review_package`) включает ВСЕ
   `ANSWER-n.md` задачи (не только последний) как отдельные компоненты
   пакета — границы решений Оператора, обязательные к учёту при
   вердикте.
2. Каждый добавленный этой задачей компонент `ANSWER-n.md`
   журналируется sha256-фингерпринтом той же механикой, что и
   компоненты брифа других ролей (`orchestrator/brief.py`,
   `_journal_component`-style: запись `store.journal` с
   `sha256=<хэш содержимого компонента>`). Уточнение по ответу
   Оператора (ANSWER-1): ссылка ТЗ на SPEC T101 — ошибочная, T101
   описывает несвязанный механизм (fingerprint окружения:
   версии Python/git/claude CLI), к содержимому пакета не
   применяется; журналирование распространяется ТОЛЬКО на новые
   компоненты `ANSWER-n.md`, не на уже существующие компоненты
   ревью-пакета (SPEC/PLAN/прошлый REVIEW/форма вердикта/stat/diff).
3. Компоненты `ANSWER-n.md` участвуют в существующем делении
   ревью-пакета на пронумерованные части по потолку
   (`orchestrator/context_package.py::discipline`,
   `config.CONTEXT_PART_MAX_BYTES`) наравне с остальными компонентами
   пакета — не исключаются из подсчёта ёмкости отдельным особым
   случаем.
4. Тесты покрывают: ревьювер получает `ANSWER-1..n` в пакете;
   sha256-фингерпринт компонента(ов) `ANSWER-n.md` попадает в журнал
   задачи; задача без файлов `ANSWER-n.md` даёт ревью-пакет,
   байт-в-байт идентичный пакету до этого изменения; существующий
   набор тестов остаётся зелёным.

## Критерии приёмки

AC-1. Если у задачи есть один или несколько файлов `tasks/<id>/ANSWER-n.md`,
`review.review_package` включает их ВСЕ как отдельные компоненты
пакета (не только файл с наибольшим `n`).

AC-2. Каждый включённый в пакет компонент `ANSWER-n.md` даёт в журнале
задачи запись с sha256-фингерпринтом его содержимого (той же формы,
что журнальная запись «бриф: компонент» для компонентов брифа
developer/analyst/test_author в `orchestrator/brief.py`).

AC-3. Существующие компоненты ревью-пакета (SPEC, PLAN, прошлый
REVIEW, форма вердикта, stat, diff) НЕ получают новую запись
sha256-фингерпринта в журнале в рамках этой задачи — их обработка не
меняется.

AC-4. Компоненты `ANSWER-n.md` учитываются в общем размере тела
пакета, передаваемом в `context_package.discipline`, и делятся на
пронумерованные части по общему правилу вместе с остальными
компонентами — не получают исключения из потолка части.

AC-5. Для задачи без файлов `ANSWER-n.md` `review.review_package`
возвращает пакет, байт-в-байт идентичный пакету, собираемому до этого
изменения (регресс отсутствует).

AC-6. Существующий набор тестов проходит зелёным после изменения.

## Не входит

- Изменение канала `ANSWER-n.md` для остальных ролей
  (developer/analyst/test_author) — их получение ответа не меняется.
- Авторешения ревьювера по залоченной планке приёмки — гейт остаётся
  решением Оператора, эта задача не добавляет автоматической
  разблокировки.
- Применение fingerprint окружения (SPEC T101 — версии Python/git/
  claude CLI) к ревью-пакету или его компонентам.
- Ретрофит sha256-журналирования на уже существующие компоненты
  ревью-пакета (SPEC/PLAN/прошлый REVIEW/форма/stat/diff) — только
  новые компоненты ANSWER, добавляемые этой задачей.
