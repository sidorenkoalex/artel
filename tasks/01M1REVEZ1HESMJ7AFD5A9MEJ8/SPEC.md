# SPEC: зависимости стека (P0) — файл закреплённых версий, venv пульта, установка в CI и у роли

## Контекст
Стек пульта объявлен манифестом `orchestrator/stack.py` (S1,
01M1RDCAFENSW2VVAPECHCVGMM) с правилом «только стандартная библиотека»
и пустым списком исключений. Решение Оператора 05.09 о полном переходе
на pytest (роадмап §3, фаза S) требует сторонних пакетов (`pytest`,
`pytest-timeout`, `pytest-xdist`), а значит — механизма, которым они
воспроизводимо попадают в окружение пульта, CI и роли одинаково. Без
такого механизма pytest снова окажется «инструментом из окружения
машины» — тем самым классом проблемы, который уже дал 217 логов шагов
со случайным pytest из pyenv Оператора и который S1/S3 (роль,
01M1RDCEF0JZ4AVQRE43JFH8TN) устраняют для инструментов манифеста, но не
для сторонних пакетов.

## Требования

1. Файл закреплённых версий в корне репозитория (`requirements.lock`
   либо эквивалент, формат `pip`) с точными версиями `pytest`,
   `pytest-timeout`, `pytest-xdist` и их транзитивных зависимостей.
   Список исключений манифеста (`orchestrator/stack.py`, S1) получает
   эти пакеты с причиной у каждого; инвариант «только стандартная
   библиотека» (`tests/test_invariants.py`, S1) пропускает импорты из
   списка исключений и по-прежнему падает на прочих сторонних импортах.
2. Venv пульта: `.artel/venv`, создаётся командой пульта (`artel.py
   venv-sync` либо шаг `init`) средствами стандартной библиотеки
   (`python3 -m venv` + `pip install -r <файл>`), идемпотентно;
   интерпретатор venv — тот же `sys.executable` пульта (S1
   `REQUIRED_PYTHON`). `check_stack()` (S1) дополнительно сверяет
   установленные в venv версии пакетов с файлом закреплённых версий:
   расхождение — WARN с именами пакетов, отсутствие venv — WARN с
   командой создания.
3. CI: джоб `python` ставит зависимости из того же файла (`pip install
   -r`) после `setup-python` (S2, 01M1RDCCKBQMJ5G2K9ANJP059H); версии
   пакетов не дублируются литералами в `ci.yml`. `.github/workflows/
   ci.yml` — защищённый путь: правка диф-приложением в `PLAN.md`, `git
   apply --check` на чистом `main`.
4. Роль (S3, 01M1RDCEF0JZ4AVQRE43JFH8TN, `role_env`): интерпретатор
   роли — python из `.artel/venv`, если venv существует и согласован с
   файлом закреплённых версий (по проверке требования 2); иначе шаг не
   стартует с `agent run SKIPPED` и именованной причиной, без тихого
   отката на системный python.
5. Пакеты только устанавливаются и проверяются; сам раннер pytest в
   пульте (P1) в эту задачу не входит — существующий набор `tests/`
   по-прежнему гоняет unittest.
6. Тесты: файл закреплённых версий разбирается и согласован со списком
   исключений манифеста; `venv-sync` на временном каталоге создаёт venv
   и идемпотентен (второй вызов без изменений; сеть в тестах запрещена
   — установка пакетов подменяется, проверяется состав команды);
   `check_stack` даёт WARN на расхождении версий; `role_env` берёт
   интерпретатор venv и отказывает без него; существующий набор `tests/`
   зелёный.

## Критерии приёмки

AC-1. В корне репозитория есть файл закреплённых версий
(`requirements.lock` либо эквивалент, формат `pip`) с точными версиями
`pytest`, `pytest-timeout`, `pytest-xdist` и их транзитивных
зависимостей.

AC-2. Список исключений манифеста (`orchestrator/stack.py`, S1)
содержит записи `pytest`, `pytest-timeout`, `pytest-xdist`, каждая — с
причиной.

AC-3. Инвариант «только стандартная библиотека» (`tests/
test_invariants.py`, S1) пропускает импорты пакетов из списка
исключений манифеста и по-прежнему падает на импорте стороннего пакета
вне этого списка.

AC-4. Команда пульта (`artel.py venv-sync` либо шаг `init`) создаёт
`.artel/venv` средствами стандартной библиотеки (`python3 -m venv` +
`pip install -r <файл закреплённых версий>`).

AC-5. Повторный вызов той же команды на уже созданном `.artel/venv`
идемпотентен — не пересоздаёт venv и не завершается ошибкой.

AC-6. Интерпретатор `.artel/venv` — тот же `sys.executable` пульта
(согласован с `REQUIRED_PYTHON`, S1).

AC-7. `check_stack()` (S1, `orchestrator/stack.py`) при расхождении
установленных в `.artel/venv` версий пакетов с файлом закреплённых
версий даёт статус WARN с именами расходящихся пакетов.

AC-8. `check_stack()` при отсутствии `.artel/venv` даёт статус WARN с
текстом, содержащим команду создания venv.

AC-9. CI-джоб `python` устанавливает зависимости командой `pip install
-r <файл закреплённых версий>` после шага `setup-python` (S2).

AC-10. Версии пакетов не продублированы литералами в `ci.yml` — файл
закреплённых версий остаётся единственным источником значений.

AC-11. Диф правки `.github/workflows/ci.yml` приложен к `PLAN.md`;
`git apply --check` на чистом `main` проходит без ошибок.

AC-12. `role_env` (`orchestrator/runner.py`, S3) выбирает интерпретатором
python из `.artel/venv`, если venv существует и согласован с файлом
закреплённых версий (по проверке из AC-7/AC-8).

AC-13. Если venv отсутствует или не согласован с файлом, шаг не
стартует: `agent run` завершается статусом `SKIPPED` с именованной
причиной, без тихого отката на системный python.

AC-14. Тест разбирает файл закреплённых версий и сверяет набор пакетов
со списком исключений манифеста (`orchestrator/stack.py`) — их
согласованность подтверждена тестом.

AC-15. Тест `venv-sync` на временном каталоге создаёт venv и
идемпотентен при повторном вызове; сеть в тесте запрещена — установка
пакетов подменяется (мок/заглушка), тест проверяет состав вызванной
команды (`pip install -r <файл>`).

AC-16. Существующий набор `tests/` зелёный после внесённых изменений —
регрессий нет.

## Оценка объёма и деление
Сработавшие сигналы: число критериев приёмки — 16 ≥ 10
(`SPLIT_SIGNAL_AC_COUNT`); `budget_usd` — 45 ≥ 30
(`SPLIT_SIGNAL_BUDGET_USD`); число файлов зоны вне `COMMON_ZONES`
(`tests/` в счёт не идёт) — `requirements.lock`, `orchestrator/
stack.py`, `orchestrator/venv.py`, `orchestrator/runner.py`, `PLAN.md`
— 5 ≥ 5 (`SPLIT_SIGNAL_ZONE_FILES`).

Задача делится на 4 самостоятельно мержимые части — по границам зон,
без разреза ни одной зоны поперёк (правка `check_stack()` из
требования 2 физически лежит в `orchestrator/stack.py`, том же файле,
что и требование 1, — оставлена в части A целиком, а не разнесена по
номеру требования):

- **Часть A — файл закреплённых версий + манифест** (требования 1 и
  «check_stack сверяет версии» из требования 2; AC-1, AC-2, AC-3, AC-7,
  AC-8, AC-14). Зоны: `requirements.lock` (новый), `orchestrator/
  stack.py`, `tests/`. Первая в порядке — от неё зависят части B, C, D
  (файл закреплённых версий как вход `pip install -r` и как эталон
  сверки версий). Самостоятельно мержима: сам файл закреплённых версий
  уже пригоден для ручного `pip install -r` до появления автоматизации;
  WARN `check_stack()` об отсутствующем venv корректен независимо от
  того, существует ли ещё команда его создания (часть B) — не ломает
  ничего в отсутствие частей B/C/D.
- **Часть B — venv пульта** (создание venv из требования 2, без
  check_stack; AC-4, AC-5, AC-6, AC-15). Зоны: `orchestrator/venv.py`
  (новый), `tests/`. Зависит от части A (файл закреплённых версий —
  вход установки). Самостоятельно мержима: новая независимая команда,
  не меняет поведение `runner.py`/CI — до части D роль по-прежнему
  использует прежний интерпретатор.
- **Часть C — CI ставит зависимости из файла** (требование 3; AC-9,
  AC-10, AC-11). Зона: `PLAN.md` (диф `ci.yml` приложением). Зависит
  только от части A (файл закреплённых версий как источник для `pip
  install -r`); от части B не зависит — порядок между B и C не задан
  взаимной зависимостью. Самостоятельно мержима: правка изолирована в
  джобе `python`, не трогает `orchestrator/*.py`.
- **Часть D — role_env берёт интерпретатор venv** (требование 4;
  AC-12, AC-13). Зона: `orchestrator/runner.py`. Зависит от частей A
  (сверка согласованности) и B (venv фактически существует и его можно
  создать) — последняя в порядке. Самостоятельно мержима с точки
  зрения кода и тестов; риск — операционный, не композиционный: с
  момента мержа этой части шаг роли требует существующего и
  согласованного `.artel/venv`, значит Оператору нужно прогнать
  `venv-sync` (часть B) до или сразу после мержа части D, иначе шаги
  всех ролей получают `SKIPPED` до первого запуска `venv-sync` — тот же
  риск существовал бы и при монолитном мерже всей задачи разом; деление
  на части не увеличивает его, а изолирует самую чувствительную правку
  (отказ роли без тихого отката) в наименьший по объёму, отдельно
  ревьюируемый диф.

AC-16 («существующий набор `tests/` зелёный») проверяется в каждой
части на подмножестве тестов, которое эта часть меняет или от которого
зависит — не одним общим критерием на весь объём.

Заведение подзадач под конкретные части — действие Оператора на этом
гейте (`cmd_new` из изолированного worktree аналитика не видит живой
реестр задач пульта). Критерии приёмки выше размечены на весь объём ТЗ
и остаются готовым материалом и для альтернативы — монолита, если
Оператор предпочтёт его на этом гейте.

- Параллельный прогон (P2).
- Стиль тестов (P3).

  задача расширяет их после их мержа, не создаёт заново.
- Установка отсутствующих инструментов (`python3`/`git`/`gh`/`claude`)
  — за пределами версий пакетов Python эта задача не выходит.
