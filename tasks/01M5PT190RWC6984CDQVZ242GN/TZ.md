## Требования

1. Мутации «до»: для каждой из 26 заявок — патч к коду `orchestrator/` в `tasks/<id>/mutation-<nnn>.diff` (номера подряд; одинаковые по смыслу заявки — одна мутация со списком тестов); у каждой мутации в PLAN — её заявка и что меняет патч. Таблица «до»: `mutation-run <id> --ref base --tests tests/test_01m590gjaf0edv4nbc4c99mfvh_report_outcome.py` частями `--patches` не больше 15 патчей; вывод `--wait` каждой части — в PLAN раздела «Мутации до» дословно, с шапкой и всеми строками, до старта следующей части. Мутация, «убитая» ошибкой сбора, импорта, setup (`ERROR at setup`) или только утверждением подготовки (методы подготовки из «Фактов», `key_case` :971), — не доказательство: патч переписывается так, чтобы падало утверждение теста; такие узлы роль отмечает в PLAN. Не убитая никем — находка в PLAN. Исход «оборвана по пределу» или «не прогнана (предел)» — перепрогон меньшим диапазоном на той же ревизии; патч, доводящий тест до предела, переписывается. Занятый замок — повторить в следующем шаге, не эскалировать.
2. Временные файлы (сценарии, выгрузки, черновики) в рабочей копии не создаются вовсе — ни вне зон, ни в `tests/`. Допустимо: файл первого уровня каталога документов задачи с расширением не `.md` и именем не `test_*` и не `mutation-*` (он попадает в `refs/artifacts`) либо файл в `$TMPDIR`, созданный командой `python3`. К концу каждого шага `git status --porcelain` рабочей копии называет только пути требований 3–5.
3. Песочница: строки 54–606 (50 операторов верхнего уровня, по порядку, включая неиспользуемые песочницей импорты) переносятся целиком и дословно в новый модуль `tests/report_outcome_sandbox.py` (тестов не содержит; докстринг — новый, одной строкой назначения); `ast.dump` каждого оператора верхнего уровня равен исходному — сверка в PLAN. Методы песочницы, в том числе с утверждениями, остаются в ней без изменений. `PytestSpy` и `pytest_output` — в тестовый модуль дословно; `ArtelUnchangedTest.FLAGS` — константа тестового модуля.
4. Старый путь для защищённого импортёра: файл `tests/test_01m590gjaf0edv4nbc4c99mfvh_report_outcome.py` не удаляется, а сводится к докстрингу (одна строка: переходной модуль, имена для `tests/test_invariants.py` — из `tests/report_outcome_sandbox.py`) и строке `from tests.report_outcome_sandbox import ReportSandbox, junit, vitest_report, vitest_test`; других определений и тестов в нём нет. 5. Свод: тесты файла — в новый `tests/test_report_outcome_module.py` в стиле pytest (функции, `assert`, `parametrize`, фикстуры `tests/fixtures.py` и собственные фикстуры файла). Фикстура только создаёт песочницу (`_sandbox(ReportSandbox)`) и не зовёт методов с утверждениями. Помощник, утверждающий исход (`assert_unknown`), и `key_case` в новом файле — функции модуля: первый параметр — стенд, тело дословно, `self.` заменено именем параметра; тест зовёт их голым именем; в `tests/report_outcome_sandbox.py` их не класть. Методы тестовых классов без утверждений — функции модуля по тому же правилу; если имя совпадает с другой функцией модуля или с локальной переменной вызывающего теста (`full_vitest` двух классов, `channels` :1710), функция получает префикс бывшего класса — переименовывается функция, не локальная переменная; перечень — в PLAN. Методы подготовки с утверждениями тест зовёт через стенд, как раньше. Утверждения и проверяемые свойства не меняются: ожидания дословно; литерал остаётся литералом, константа — константой (равенство значений доводом не считается); `pytest.raises(..., match=re.escape(<текст>))` — только где исходник проверял текст; голый `assertRaises(E)` → `pytest.raises(E)`; литеральные наборы `subTest` без общего состояния — `parametrize` литералами; перебор по константам кода — `parametrize` по самой константе или цикл в теле; итерации с общим состоянием, случайный выбор и `subTest` с общим состоянием песочницы — прежним циклом в одной функции; текст сообщения (`msg=`, ярлыки `subTest`, печать зерна) — вторым операндом `assert` или аргументом `pytest.fail`. `if __name__ == "__main__"` не переносится. Дубль удаляется только если (а) каждую его мутацию по таблице «до» убивает и другой сохраняемый тест и (б) каждый литерал и вид каждого утверждения удаляемого теста есть в утверждениях сохраняемого теста, убивающего те же мутации; удалённые дубли — в PLAN с мутациями. Тест, чью мутацию не убил никто, не удаляется (заявка переписывается на мутацию, которую он убивает, со своим патчем, либо находка в PLAN). У каждой функции — «Ловит мутацию:».
6. Таблица «после»: `mutation-run <id> --ref worktree --tests tests/test_report_outcome_module.py` теми же частями; вывод — в PLAN «Мутации после» дословно; перед каждой частью — вывод `git status --porcelain -- orchestrator/` рабочей копии (пустой). Каждая мутация, убитая «до», убита «после» (правила требования 1 о подготовке и пределе действуют и здесь); дерево `orchestrator/` ревизий обеих шапок совпадает (`git diff --quiet <sha до> <sha после> -- orchestrator/`), sha256 каждого патча в обеих шапках совпадает; при подтяжке main между прогонами «до» прогоняется заново, если дерево `orchestrator/` изменилось. Адресный прогон под ролью — не больше одного файла за шаг. Число тестов, строк и время адресного прогона до и после — в PLAN.
