# PLAN: ANSWER-артефакт: канал ответа Оператора на эскалацию

## Подход

Три независимых куска, все обвязаны вокруг существующей механики
эскалации, ни один её не меняет (SPEC, «Не входит»):

1. **Носитель** (AC-1): `templates/ANSWER.md` — frontmatter
   (`task`/`type: answer`/`author_role: operator`/`status`/
   `schema_version`) + секция `## Ответы`; `scripts/guard.py::RULES`
   несёт новый ключ `"answer"` (статус только `ready` — ответ Оператора
   не черновится, он либо есть, либо его нет).

2. **Команда `answer`** (AC-2): новый модуль `orchestrator/answer.py` по
   образцу `orchestrator/release.py` (маленький самостоятельный
   Operator-command модуль) — `cmd_answer(task_id, file_path)` читает
   файл, находит следующий номер (`max(существующие ANSWER-n) + 1`, не
   счёт файлов — второй раунд после `ANSWER-1.md` обязан получить
   `ANSWER-2.md`, даже если первый когда-то убрали), пишет
   `ANSWER-n.md` в worktree задачи (`workspace.ensure`, идемпотентно),
   коммитит БЕЗ `-c user.name=...` (в отличие от `catalog.cmd_new`,
   который явно проставляет служебную identity `fixation.
   FIXATION_AUTHOR_NAME/EMAIL` артефактам ТЗ) — коммит обязан остаться
   под identity Оператора, не оркестратора (SPEC AC-2, «не служебный
   артефакт»). Берёт lease тем же приёмом, что `approve`/`reject`/`run`
   (`lease.run_locked`). Диспетчеризация — новая строка таблицы команд
   `orchestrator/artel.py`.

3. **Гейт возврата** (AC-3/AC-4/AC-5) — решение, определившее объём
   работы: класс эскалации («вопрос роли» vs «лимит») различается НЕ
   разбором `escalated_from` в момент `approve` (это значение
   неоднозначно — `runner.py`/`budget.py` пишут туда `t["state"]` при
   провале агента ЛЮБОГО шага, включая `spec_writing`/`tests_writing`,
   тем же значением, что и настоящая эскалация-вопрос того же шага;
   докстринг `tasks/T075/acceptance_tests/test_ac5_*.py` формулирует
   это прямо), а фиксацией в БД **в момент самой эскалации**, там, где
   код уже безусловно знает причину. Новая колонка `tasks.
   answer_baseline` (nullable INTEGER): `NULL` — эскалация класса
   «лимит», ответ не нужен (как до этой задачи); число — снимок count
   `ANSWER-*.md` задачи на момент эскалации. `approve` из `escalated`
   с непустым `answer_baseline` требует, чтобы текущий count вырос
   строго больше снимка — иначе отказ с именем ожидаемого файла.
   Снимок, не булев флаг: отличает «ANSWER есть» от «ANSWER ЭТОГО
   раунда есть» — без этого второй раунд эскалации той же задачи
   молча засчитал бы ответ первого раунда (юнит-тест `tests/
   test_answer_gate.py` — сценарий, который приёмочные тесты T075 не
   покрывают, они гоняют только один раунд на задачу).

   Подсчёт (`fsm._answer_file_count`) — ветко-корректный (SPEC T031/
   T047, тот же приём, что и остальные чтения в `_cmd_advance`): с
   ВЕТКИ задачи, если рабочее дерево пульта на чужой ветке, иначе с
   диска. Локальная песочница приёмочных тестов (`_sandbox.py`,
   `fake_git`) явно объявляет эту ось ортогональной критериям T075 и
   не требует её — но она нужна для реальной корректности: `config.
   TASKS` главной копии пульта (T048) НЕ содержит артефактов задачи в
   процессе работы, они живут только в её worktree/ветке, и без
   branch-aware чтения гейт был бы сломан в проде при видимом зелёном
   прогоне тестов.

4. **Доставка ответа в бриф** (AC-6) — `orchestrator/brief.py`: общий
   узел `_answer_component`/`_questions_component` (текст последнего
   `ANSWER-n.md`/`QUESTIONS.md`, тем же branch-aware чтением, что и
   гейт) добавляется к `developer_brief` и `analyst_map_component`
   (только если файл есть — пустая добавка не портит состав брифа,
   регрессия проверена `tests/test_brief.py`: без ANSWER состав брифа
   не меняется). `test_author` до этой задачи не получал `brief_text`
   вовсе (`runner.py`, ветка `elif role == "test_author":`) — новая
   функция `brief.test_author_answer_component` даёт этой роли МИНИМУМ
   (только ANSWER, без SPEC/карты — их эта роль и так не получает).
   `branch`/`on_foreign_branch(branch)` считаются ОДИН раз на бриф и
   передаются вглубь параметром `foreign` — не по разу на каждый
   компонент (иначе лишний git-вызов на пустом месте; поймано регрессией
   `tests/test_review_package.py::test_developer_step_has_no_package`,
   считающим ТОЧНЫЙ список git-вызовов шага разработчика).

## Шаги

1. `templates/ANSWER.md` + `scripts/guard.py::RULES["answer"]` (AC-1).
2. `orchestrator/store.py`: колонка `tasks.answer_baseline` (SCHEMA +
   `migrate`). `orchestrator/answer.py` (новый модуль, `cmd_answer`).
   `orchestrator/artel.py`: строка `answer` в таблице команд + докстринг.
3. `orchestrator/fsm.py`: `_answer_file_count`; простановка
   `answer_baseline` в трёх местах эскалации класса «вопрос роли»
   (`spec_writing`×2 ветки чтения, `tests_writing`, `review`/`escalate`);
   гейт + сброс в `_cmd_approve`, ветка `elif state == "escalated":`
   (AC-3/AC-4/AC-5).
4. `orchestrator/brief.py` + `orchestrator/runner.py` (одна строка,
   ветка `test_author`): доставка ANSWER/QUESTIONS в бриф/промпт (AC-6).
5. Регенерация `docs/codebase-map.md` (правка `orchestrator/*.py`,
   конвенция `conventions-core`). Юнит-тесты (`tests/test_answer.py`,
   `tests/test_answer_gate.py`, добавки `tests/test_brief.py`) и починка
   двух существующих тестов, чьи фикстуры молчаливо предполагали старое
   поведение «эскалация-вопрос возвращается без ответа»
   (`tests/test_invariants.py::CountersNeverResetTest`, `tests/
   test_analyst_role.py::QuestionsEscalationTest`) — это НЕ ослабление
   инварианта (класс проверяемого поведения — «счётчики не сбрасываются
   на переходах» / «эскалация возвращает в spec_writing» — не тронут,
   только добавлен предусловный `write_answer` шаг, которого раньше не
   требовал сам продакшн-код).

## Влияние на систему

- **Новая колонка БД** (`tasks.answer_baseline`, nullable) — аддитивная
  миграция через существующий `store.add_column` (тот же приём, что и
  все прежние колонки `tasks`), старые строки получают `NULL` —
  поведение «эскалация без ответа» для них не меняется (как раз то,
  что требует AC-5 для классов «лимит»).
- **Гейт `approve` из `escalated` становится строже** ровно для трёх
  существующих путей эскалации (`spec_writing`/QUESTIONS.md,
  `tests_writing`/`AC-n: escalate`, `review`/`status: escalate`) — это
  ЦЕЛЬ задачи (SPEC AC-3), не побочный эффект; классы «лимит»/инцидент
  не тронуты (AC-5, юнит- и приёмочными тестами закрыто). Два
  существующих теста молчаливо опирались на старое (менее строгое)
  поведение именно на этих трёх путях — почищены шагом 5, не ослаблены.
- **Лишний git-вызов на бриф** — один `on_foreign_branch` (не по разу
  на каждый компонент, см. «Подход», п.4) на `developer_brief`/
  `analyst_map_component`/`test_author_answer_component`, когда рабочее
  дерево пульта на чужой ветке (обычный случай в проде после T048) —
  цена branch-корректного чтения, тот же класс, что уже платят
  `_developer_spec_text` и остальные чтения `fsm.py`.
- **Откат**: миграция колонки не откатывается назад (SQLite), но
  безвредна — код просто перестанет её читать/писать, если правку
  откатить; `escalated`-гейт откатывается снятием проверки в
  `_cmd_approve` одним диффом.
- Инварианты `docs/invariants.md` не расширены и не ослаблены — гейт
  возврата не входит в реестр (само по себе не инвариант «система не
  должна становиться хуже», а новое требование SPEC), инвариант 28
  (ветко-корректные чтения) сознательно не расширен явно ни на один AC
  этой задачи (см. докстринг `_sandbox.py` приёмочных тестов) — сама
  реализация branch-aware по тем же соображениям, что и остальной
  `fsm.py`/`brief.py`, но это решение разработчика для корректности в
  проде, не требование, зафиксированное тестом.

## Риски

- Классификация «вопрос роли» vs «лимит» опирается на то, что
  `escalated_from == "spec_writing"`/`"tests_writing"` выставляется
  СЕГОДНЯ только кодом эскалации-вопроса (fsm.py) — агентный провал
  ВНУТРИ `spec_writing`/`tests_writing` (`runner.py`, исчерпание
  попыток) тоже пишет туда `t["state"]`. Снимок `answer_baseline`
  берётся именно в момент эскалации-ВОПРОСА (3 конкретных места кода),
  агентный провал этот снимок не трогает (остаётся `NULL` с прошлого
  сброса) — конфликт нужен только если ОБА триггера сработают на одной
  задаче между двумя `approve`, что структурно невозможно (эскалация
  останавливает `run` до `approve`). Не тестировано отдельно — вне
  зоны AC.
