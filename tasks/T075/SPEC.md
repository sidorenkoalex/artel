# SPEC: ANSWER-артефакт: канал ответа Оператора на эскалацию

## Контекст

Роадмап P3, предусловие C2 (аудит 27.08): профиль эскалаций системных
задач неприемлем для внешнего target, а канала ответа Оператора на
эскалацию сегодня нет. Ответ, записанный в журнал БД, роль на
перезапуске не видит — бриф журнал не включает; фактура T073 показала
холостой перезапуск analyst с той же переэскалацией ($0.66). Рабочий
обход — дописка ответа в TZ.md коммитом Оператора — работает только для
эскалации analyst, неструктурен и не покрывает эскалации из других
ролей. Нужен именованный артефакт-ответ, гейт возврата по его наличию
и гарантированная доставка ответа в бриф роли.

## Требования

1. В `templates/` появляется шаблон `ANSWER.md` (frontmatter, включая
   номер, привязку к задаче и статус; guard.py валидирует структуру).
   Носитель ответа — файл `tasks/<id>/ANSWER-n.md` в ветке задачи
   (n — порядковый номер, парный номеру эскалации/QUESTIONS), содержащий
   ответы Оператора по пунктам вопроса.
2. CLI пульта даёт Оператору команду `answer <id> <файл-с-ответом>`
   (решение Оператора 31.08 по эскалации test_author: имя и сигнатура —
   симметрия с `new "<название>" --tz <файл>`; интерактивного ввода
   нет), которая читает текст ответа из файла, создаёт `ANSWER-n.md`
   в worktree задачи, коммитит его в ветку задачи авторством Оператора
   и журналирует создание — Оператор не правит worktree руками.
   Диспетчеризация — `orchestrator/artel.py`, той же таблицей, что
   остальные команды.
3. Возврат `approve` из эскалации, несущей структурированный вопрос
   роли, — эскалация с QUESTIONS.md (analyst, состояние `spec_writing`),
   маркер `AC-n: escalate` в acceptance_tests (test_author, состояние
   `tests_writing`), вердикт `REVIEW.md status: escalate` (reviewer,
   состояние `review`) — требует наличия нового `ANSWER-n.md` на ветке
   задачи; без него `approve` отказывает с внятным текстом, задача
   остаётся в `escalated`. Голый провал агента после исчерпания попыток
   (`config.AGENT_ATTEMPTS`) и прочие эскалации класса «лимит»
   (исчерпание итераций ревью, отказов приёмки), а также конфликт
   подтяжки главной ветки и инцидент целостности — ANSWER не требуют,
   возврат работает как сейчас. Адресация возврата не меняется:
   эскалация из `spec_writing` возвращается в `spec_writing` (analyst
   инкорпорирует ответ, повторный гейт SPEC), остальные — в состояние,
   из которого пришла эскалация (как сейчас).
4. Бриф роли, запускаемой на задаче после такого возврата, включает
   текст соответствующего `ANSWER-n.md` при следующем запуске (а для
   эскалации с QUESTIONS.md — связку вопрос → ответ), так что ответ
   гарантированно доходит до роли, а не только существует в ветке.
5. Право пересмотра залоченных приёмочных тестов по итогам ответа
   Оператора остаётся только за Оператором — эта задача его не меняет.

## Критерии приёмки

AC-1. `templates/ANSWER.md` существует и несёт frontmatter (как минимум
`task`, `type: answer`, `author_role: operator`, `status`,
`schema_version`); `scripts/guard.py`, прогнанный на файле вида
`tasks/<id>/ANSWER-n.md`, построенном по этому шаблону, не даёт
структурных нарушений.

AC-2. Команда `artel.py answer <id> <файл-с-ответом>`, вызванная
Оператором на задаче в состоянии `escalated`, создаёт `tasks/<id>/ANSWER-n.md` в
worktree задачи, коммитит его в ветку задачи с авторством Оператора и
оставляет запись в журнале задачи.

AC-3. Для задачи в `escalated`, эскалация которой пришла из
QUESTIONS.md (`spec_writing`), маркера `AC-n: escalate` (`tests_writing`)
или вердикта `REVIEW.md status: escalate` (`review`), `approve` без
нового `ANSWER-n.md` на ветке задачи отказывает, печатает, какого файла
не хватает, и не меняет состояние задачи.

AC-4. Для той же задачи после создания `ANSWER-n.md` (AC-2) `approve`
переводит задачу дальше по прежней адресации возврата: эскалация из
`spec_writing` — в `spec_writing`; эскалация из `tests_writing` или
`review` — в состояние, из которого она пришла, либо в `in_dev`, если
эскалация не зафиксировала исходное состояние (как сейчас).

AC-5. Для задачи в `escalated`, чья эскалация — исчерпание попыток
агента (`config.AGENT_ATTEMPTS`), исчерпание лимита итераций ревью или
лимита отказов приёмки, конфликт подтяжки главной ветки или инцидент
целостности, `approve` работает без `ANSWER-n.md`, как до этой задачи.

AC-6. Роль, запущенная на задаче после `approve` из AC-4, получает в
своём брифе текст `ANSWER-n.md` этой эскалации; если эскалация несла
QUESTIONS.md, бриф включает и текст исходного вопроса.

AC-7. Полный тестовый набор (`pytest`) проходит зелёным.

## Не входит

- Панель/UI Оператора — вне объёма.
- Автоматические ответы или дефолты без участия Оператора — вне объёма
  и запрещены (класс «решение Оператора», ADR-0002).
- Изменение механики самих эскалаций (когда и почему они возникают) —
  вне объёма; меняется только гейт возврата из эскалации и доставка
  ответа.
- Доведение эскалации разработчика (`status: escalate` в `PLAN.md`,
  состояние `in_dev`) до рабочего состояния — вне объёма (ответ
  Оператора 30.08 на вопрос 2 QUESTIONS.md): сегодня этот путь не
  функционален (схема `templates/PLAN.md` не допускает значения
  `escalate`, FSM его не читает для `in_dev`); заводится отдельной
  строкой роадмапа.
- Голый провал агента после исчерпания попыток (`config.AGENT_ATTEMPTS`)
  не требует ANSWER — обрабатывается как класс «лимит» (ответ Оператора
  30.08 на вопрос 1 QUESTIONS.md).
