# QUESTIONS: ANSWER-артефакт: канал ответа Оператора на эскалацию

## Вопросы

1. **Какие именно эскалации входят в «класс вопрос роли», требующий
   ANSWER-n перед `approve`?** ТЗ (требование 3) явно относит сюда
   эскалацию с QUESTIONS.md (analyst, `spec_writing`) и явно исключает
   три класса — инцидент целостности, конфликт подтяжки, лимиты — «как
   сейчас». Между этими границами в коде сегодня есть ещё три
   механизма эскалации, которые ТЗ не адресует напрямую:
   - `tests_writing` — маркер `# AC-n: escalate — <вопрос Оператору>`
     в acceptance_tests (`orchestrator/runner.py:237`, `fsm.py:758-767`)
     — маркер буквально называется «вопрос Оператору» в инструкции роли;
   - `review` — вердикт `REVIEW.md status: escalate`
     (`orchestrator/fsm.py:746-748`) — по скилу `escalation-rules`
     (общему для всех ролей) артефакт при эскалации несёт секцию
     «Вопросы», но FSM это поле сегодня не парсит;
   - провал агента шага после исчерпания попыток
     (`orchestrator/runner.py:312-319`, `config.AGENT_ATTEMPTS`) —
     свободнотекстовая причина сбоя, без структуры «вопрос + варианты
     + дефолт».

   Варианты:
   A) Все три механизма — «класс вопрос роли», ANSWER обязателен перед
      `approve` для любой эскалации, кроме буквально перечисленных в
      ТЗ исключений (инцидент целостности, конфликт подтяжки, лимиты).
   B) Только `tests_writing` (AC-n: escalate) и `review`
      (status: escalate) — оба несут структурированный вопрос по
      скилам ролей; провал агента — не вопрос роли, а сбой шага (по
      духу ближе к «лимиту»: исчерпание `AGENT_ATTEMPTS`), ANSWER не
      требует.
   C) Только буквально то, что названо в ТЗ, — QUESTIONS.md
      (`spec_writing`); `tests_writing`, `review`-эскалация и провал
      агента ANSWER не требуют, возвращаются как сейчас.
   Дефолт при молчании: **B** — эскалации со структурированным
   «вопросом роли» (AC-n:escalate, REVIEW status:escalate) гейтятся
   ANSWER; голый провал агента после исчерпания попыток ANSWER не
   требует, обрабатывается как сейчас (исчерпание `AGENT_ATTEMPTS` —
   тот же класс, что и прочие лимиты в исключении ТЗ).

2. **Разработчик (`PLAN.md`, состояние `in_dev`) сегодня не может
   оставить структурированный вопрос по скилу `escalation-rules` —
   входит ли доведение этого до рабочего состояния в объём T075?**
   Схема `templates/PLAN.md` допускает только
   `status: draft | ready | approved` (значения `escalate` нет), а
   переход `_cmd_advance` для `state == "in_dev"`
   (`orchestrator/fsm.py:792-864`) читает только `ready`/`approved` —
   `status: escalate` в PLAN.md сегодня не имеет эффекта вообще
   (не эскалирует). Единственный сегодняшний путь эскалации из
   `in_dev` — провал агента (см. вопрос 1).

   Варианты:
   A) В объёме — добавить `escalate` в схему `templates/PLAN.md` и
      чтение в FSM (`in_dev`), чтобы разработчик тоже мог эскалировать
      структурированным вопросом, гейтуемым ANSWER.
   B) Вне объёма — граница ТЗ буквальна («изменение механики самих
      эскалаций — вне объёма»); T075 обвязывает ANSWER только вокруг
      уже существующих сегодня триггеров эскалации, пробел у
      разработчика остаётся отдельным пунктом роадмапа.
   Дефолт при молчании: **B** — по разделу «Границы» ТЗ.
