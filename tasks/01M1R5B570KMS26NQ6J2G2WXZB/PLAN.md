# PLAN: плавающий тест лимитера параллельных задач — граница свежести heartbeat

## Подход

Выбранный приём (SPEC, требование 1) — **увеличение запаса у границы до
половины порога `LEASE_STALE_AFTER_SEC`**, а не подмена источника
времени. Обоснование:

- Правка сосредоточена целиком в `tests/test_parallel_limit.py` — не
  трогает `orchestrator/liveness.py`/`lease.py`/`merge_lock.py`/
  `parallel_limit.py` вовсе. Это меньший диф и меньший риск для AC-6
  («порог и механика lease не изменены по логике сверх допустимого») —
  само «допустимое» производственное изменение (параметр времени в
  `liveness._age_seconds`) становится просто не нужным.
- Запас в половину порога (`config.LEASE_STALE_AFTER_SEC // 2` = 3600
  сек при текущем пороге 7200) на три порядка больше любой реалистичной
  просадки CI-раннера (наблюдение SPEC — секунда съедена вторым
  прогоном) и на два порядка больше искусственной задержки из AC-5
  (1.2 сек) — граница перестаёт быть чувствительной к скорости машины.
- Проверено вручную (см. `tasks/.../acceptance_tests/
  test_ac1_heartbeat_edge_case_time_independence.py`, докстринг): при
  симулированном сдвиге «сейчас» почти на половину порога (через
  `mock.patch.object(liveness, "datetime", ...)`, тем же приёмом, что
  уже несёт `tests/test_report.py::_frozen_today`) запас в половину
  порога проходит, запас в 10 секунд — нет. Это внешняя, не моя,
  проверка выбранного приёма — она уже лежит в приёмочных тестах задачи
  и совпадает с рассуждением ниже.

Симметрично применяется ко всем четырём местам в файле, где `_ts_ago`
употребляется вместе с `config.LEASE_STALE_AFTER_SEC` (AC-2): два новых
хелпера `_fresh_edge_ts()`/`_stale_edge_ts()` с общей константой
`_MARGIN_SEC = config.LEASE_STALE_AFTER_SEC // 2` — было `± 1`, стало
`± _MARGIN_SEC`. Имена существующих тестовых методов не меняются
(приёмочный тест AC-4 явно опирается на них по имени через
`loadTestsFromName`).

Альтернатива (заморозка времени патчем `liveness.datetime` изнутри
каждого теста) была бы эквивалентна по надёжности, но добавляет код в
каждый из четырёх тестов и не даёт меньшего дифа — отклонена в пользу
двух статических хелперов.

## Влияние на систему

- Зона правки — только `tests/test_parallel_limit.py`. Производственный
  код (`orchestrator/liveness.py`, `lease.py`, `merge_lock.py`,
  `parallel_limit.py`) не изменён ни строкой — инвариант №32
  (`docs/invariants.md`) и порог `LEASE_STALE_AFTER_SEC` нетронуты.
- Grep по требованию AC-3 (`grep -rn "_ts_ago(config.LEASE_STALE_AFTER_SEC" tests/`)
  на момент написания плана подтверждает: единственное место с запасом
  ≤ 5 сек со стороны «ещё не протух» во всём `tests/` — это
  `tests/test_parallel_limit.py:68` (уже покрыто шагом 1). Остальные
  вхождения (`test_lease.py`, `test_merge_lock.py`, `test_release.py`) —
  либо запас со стороны «точно протух» (`+ 1`, безопасно по
  построению — просадка только отдаляет от границы), либо не привязаны
  к порогу вовсе (`_ts_ago(5)`, `_ts_ago(123)` — «свежий» heartbeat
  далеко от двухчасовой границы, не пограничный случай). Изменений там
  не требуется.
- Откат: одна правка одного тестового файла, откатывается `git revert`
  без побочных эффектов на другие тесты или производственный код.

## Риски

- Половина порога — константа времени компиляции теста
  (`config.LEASE_STALE_AFTER_SEC // 2`), не зависящая от будущих правок
  самого порога Оператором: смена `LEASE_STALE_AFTER_SEC` в другой
  задаче не потребует правки этого файла — margin пересчитается сам.
