# ТЗ: единая очередь мержа: merge-окно держится на весь цикл approve merge_gate, включая ожидание CI; второй approve ждёт в очереди FIFO

Источник: копилка 06.09 «зелёная задача на merge_gate устаревает» и
дописка 11.09 (пинг-понг двух сессий), решение Оператора 11.09 «единая
очередь мержа».

Факт 11.09: цикл approve на merge_gate у 01M283NC… с 17:46Z за 45 минут
сделал пять подтяжек main и пять полных прогонов CI (2e648868 → cf16d10e
→ 211efc9d → 5c10ca37 → 85382c93), потому что соседняя сессия параллельно
вливала свои задачи: каждый её мерж сдвигал main раньше, чем дозревал
наш CI. Потолок ожидания CI одного вызова (`MERGE_GATE_CI_WAIT_CEILING_SEC`,
3600 с) при таком ритме выходит без единого мержа.

Причина в механике: мьютекс merge-окна (`merge_locks`, `orchestrator/
merge_lock.py`) держится только на теле гейта — подтяжка, push, сам
merge — и намеренно отпускается на время ожидания CI
(`fsm_merge_gate._cmd_approve_merge_gate_cycle`, SPEC T087, требование 2).
В окно ожидания CI свободно входит чужой мерж, и подтяжка начинается
заново. Две сессии на merge_gate сдвигают main друг другу по кругу.

Требуется:
1. Резервирование merge-окна на весь цикл approve merge_gate: с первой
   подтяжки main до мержа либо выхода цикла (отказ, эскалация, потолок,
   прерывание), ВКЛЮЧАЯ ожидание CI. Держатель — та же строка
   `merge_locks`; heartbeat строки продлевается на каждом опросе CI
   (`MERGE_GATE_CI_WAIT_POLL_SEC`), чтобы `merge_lock._holder_is_dead`
   не счёл живого держателя мёртвым. Снятие — безусловно в `finally`
   цикла, как сейчас.
2. Очередь вместо отказа: approve на merge_gate при занятом окне не
   выходит с ошибкой, а ждёт освобождения опросом (тот же интервал), с
   записью журнала «ждёт merge-окна: держит <id>» при входе в очередь и
   показом в `status` добавкой «[ждёт merge-окна: занято <id>, N мин]»
   (по образцу «ждёт зоны»). Порядок — FIFO по времени входа в очередь:
   ожидающие регистрируются в новой таблице `merge_queue` (task_id,
   session_id, pid, hostname, enqueued_ts, heartbeat_ts; схема и
   миграция — `orchestrator/schema.py`), окно берёт только голова
   очереди. Потолок ожидания в очереди — новая константа
   `MERGE_QUEUE_WAIT_CEILING_SEC` (дефолт 7200); по истечении — выход
   без мержа с именованным сообщением, задача остаётся на merge_gate.
   Потолок ожидания CI (`MERGE_GATE_CI_WAIT_CEILING_SEC`) по-прежнему
   отсчитывается от первого пуша, ожидание в очереди в него не входит.
3. Мёртвые участники: держатель окна с неживым pid или протухшим
   heartbeat перешагивается как сейчас; запись очереди с неживым
   pid/протухшим heartbeat удаляется при следующем взятии окна. `doctor`
   показывает очередь и предупреждает о мёртвых записях
   (`orchestrator/doctor/leases.py` — там же, где проверка merge_lock).
4. Тесты: два approve на разные задачи параллельно (второй стартует,
   пока первый ждёт CI) — второй ждёт в очереди, после мержа первого
   подтягивает main уже с ним и мержит одной подтяжкой (мутация «окно
   отпущено на ожидании CI» — красный); третий approve встаёт за вторым
   (FIFO); потолок очереди — выход без мержа и без изменения состояния;
   мёртвый держатель перешагивается, мёртвая запись очереди чистится;
   существующие тесты `merge_lock` и цикла merge_gate — без ослабления.

Зоны: orchestrator/fsm_merge_gate.py, orchestrator/merge_lock.py,
orchestrator/schema.py, orchestrator/store.py, orchestrator/config.py,
orchestrator/catalog.py, orchestrator/doctor/leases.py, tests/.

Не входит: мерж без повторной подтяжки при «аддитивном» сдвиге main;
изменение порядка состояний и тела гейта (подтяжка, push, carpentry-merge);
`orchestrator/lease.py`; канарейка.
