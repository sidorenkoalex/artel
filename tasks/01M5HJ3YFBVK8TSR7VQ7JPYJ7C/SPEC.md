# SPEC: Тесты amend-tests для файлов с меткой без перечня лока (перенос приёмки G3б-1)

## Контекст
Независимая проверка G3б-1 (задача 01M5GXZK2WTZ89AXQ7QY2RJD9R, 22.10) нашла
три пути кода пульта, которые ни один тест не исполняет, хотя код в них
верен. Н1 — `amend-tests` для задачи с файлами с меткой при пустом перечне
долгоживущих файлов лока: путь `_amend_plank_only`
(`orchestrator/amend.py:825-856`) и путь `--from-branch`
(`orchestrator/amend.py:1194-1208`). Все существующие песочницы заводят
непустой перечень (`tests/test_01m5gxzk2wtz89axq7qy2rjd9r_amend_labelled.py:249-276`,
`tests/test_01m5aa5ts90rdj2afxb882wtpd_labelled_gates.py:1377-1392`). Н2 —
удаление долгоживущего файла с меткой, у которого имя теста перенесено в
файл планки с меткой (`_labelled_long_lived_errors`, цикл
`orchestrator/amend.py:284-289`): сейчас проверен только отказ. Н5 —
решение профиля с отказом для записи проекта из нескольких компонентов
(`orchestrator/project_profile.py:194-198`, `orchestrator/repo_context.py:161-163`)
на `approve` гейта SPEC (`orchestrator/fsm.py:1127-1129`). Задача
добавляет один файл долгоживущих тестов, который исполняет эти пути на
неизменённом коде пульта.

## Требования

1. **Н1, рабочая копия.** Задача проекта с компонентом `pult-vitest`
   (правило планки не по умолчанию) стоит в `in_dev` с локом. Планка
   состоит из файла с меткой `.test.jsx`, файла `.md` и пустого файла
   перечня (`guard.render_long_lived_manifest({})`). Долгоживущих файлов
   нет. Фикстурная проверка: `long_lived_manifest` из
   `orchestrator/advance_gates/acceptance.py` возвращает для задачи
   `({}, "")`. Имя файла с меткой не начинается с `test_` (например,
   `<случайное>.test.jsx`), и это проверяется фикстурно. Каждый случай —
   отдельный тестовый метод:
   - (а) годная правка файла с меткой проходит. Вывод не содержит
     «amend-tests: отказ». `tests_locked_sha` сдвинут и равен голове
     ссылки документов. Записей «правка планки» становится на одну
     больше. Голова кодовой ветки не меняется. Второй прогон делается
     без файла перечня вовсе (ветка `if not listed`,
     `orchestrator/advance_gates/acceptance.py:84`) и даёт тот же исход;
   - (б) файл с меткой с запретом (числовой литерал в аргументах `it`) —
     отказ «строка группы:» со строкой «… — запрещено в тексте планки»
     (`guard.PLANK_BAN_TAIL`);
   - (в) файл с меткой без строки группы — отказ «строка группы:»;
   - (г) изменён только `.md`, а неизменённый файл с меткой несёт
     запрет, — отказ «строка группы:» с `guard.PLANK_BAN_TAIL`;
   - (д) нарушенная трассируемость — отказ «трассируемость AC нарушена:»;
   - (е) удалён единственный файл с меткой, покрывавший критерий, — отказ
     «трассируемость AC нарушена:».
   Отказ проверяется по префиксу группы. В случаях (б), (в), (г) текст
   отказа несёт имя файла с меткой; в случаях (д), (е) — номер критерия
   `AC-<n>` в тексте отказа трассируемости (решение Оператора на гейте
   SPEC, круг 1). После отказа голова ссылки документов, голова кодовой
   ветки, `tests_locked_sha` и число записей «правка планки» прежние.
   Вывод несёт «amend-tests: отказ — <префикс группы>», последняя запись
   журнала «amend-tests отклонён» начинается с префикса группы.
2. **Н1, `--from-branch`.** Те же случаи (а)–(е) у той же задачи, но
   правка вносится коммитом в ссылку документов. Ожидания те же, каждый
   случай — отдельный метод.
3. **Н2.** У задачи есть долгоживущий файл с меткой и непустой перечень.
   Имя теста долгоживущего файла (по `guard.plank_test_names`) перенесено
   в файл планки с меткой, а долгоживущий файл удалён:
   - (а) в рабочей копии — проход, голова кодовой ветки сдвинута
     коммитом удаления;
   - (б) в `--from-branch` (удаление коммитом кодовой ветки) — проход.
   Признаки прохода в обоих случаях: вывод без «amend-tests: отказ»;
   `tests_locked_sha` равен голове ссылки документов; записей «правка
   планки» на одну больше; удалённого файла нет в дереве головы кодовой
   ветки; перечень в дереве нового лока пуст или отсутствует.
4. **Н5.** Проект с записью из двух компонентов, у каждого непустое
   `paths`. Фикстурные проверки: `repo_context.resolve(<проект>)` не
   `None`; `project_profile.decide(<проект>).refusal` непуст и содержит
   `targets.MULTI_COMPONENT_PENDING`. Задача стоит на `spec_gate`, её SPEC
   несёт непустой годный раздел «Заменяемые тесты» и матрицу. Ожидаемый
   исход `approve`:
   - мягкий отказ, задача остаётся в `spec_gate`;
   - запись «approve отклонён» начинается с «раздел «Заменяемые тесты» не
     сверить — решение профиля тестов проекта: отказ:» и несёт

## Критерии приёмки

AC-1. Задача с компонентом `pult-vitest` в `in_dev` с локом: в планке
файл с меткой `.test.jsx` с именем не на `test_`, `.md` и пустой перечень,
долгоживущих файлов нет, `long_lived_manifest` возвращает `({}, "")`. В
рабочей копии годная правка файла с меткой проходит:
- вывод без «amend-tests: отказ»;
- `tests_locked_sha` равен новой голове ссылки документов;
- записей «правка планки» на одну больше;
- голова кодовой ветки прежняя.
Тот же исход и без файла перечня.

AC-2. У той же задачи в рабочей копии каждый случай — отдельный метод:
- файл с меткой с запретом → отказ «строка группы:» с
  `guard.PLANK_BAN_TAIL`;
- файл с меткой без строки группы → отказ «строка группы:»;
- изменён только `.md` при неизменённом файле с меткой с запретом →
  отказ «строка группы:» с `guard.PLANK_BAN_TAIL`;
- нарушенная трассируемость → «трассируемость AC нарушена:»;
- удалён единственный файл с меткой, покрывавший критерий, →
  «трассируемость AC нарушена:».

В каждом отказе:
- в трёх случаях «строка группы:» текст отказа несёт имя файла с меткой;
  в двух случаях «трассируемость AC нарушена:» текст отказа несёт номер
  критерия `AC-<n>`;
- голова ссылки документов, голова кодовой ветки, `tests_locked_sha` и
  число записей «правка планки» прежние;
- вывод несёт «amend-tests: отказ — <префикс группы>»;
- последняя запись журнала «amend-tests отклонён» начинается с префикса
  группы.

AC-3. Те же случаи AC-1 и AC-2 правкой через `--from-branch` (коммитом в
ссылку документов) дают те же исходы. Каждый случай — отдельный метод.

AC-4. Задача с долгоживущим файлом с меткой и непустым перечнем. Имя
теста долгоживущего файла (по `guard.plank_test_names`) перенесено в файл
планки с меткой, долгоживущий файл удалён. Удаление проходит в рабочей
копии (голова кодовой ветки сдвинута коммитом удаления) и через
`--from-branch` (удаление коммитом кодовой ветки). В обоих случаях:
- вывод без «amend-tests: отказ»;
- `tests_locked_sha` равен голове ссылки документов;
- записей «правка планки» на одну больше;
- удалённого файла нет в дереве головы кодовой ветки;
- перечень в дереве нового лока пуст или отсутствует.

AC-5. Проект с записью из двух компонентов, у каждого непустое `paths`.
Фикстурно: `repo_context.resolve(<проект>)` не `None`, а
`project_profile.decide(<проект>).refusal` непуст и содержит
`targets.MULTI_COMPONENT_PENDING`. `approve` задачи на `spec_gate`, чей
SPEC несёт годный раздел «Заменяемые тесты» и матрицу:
- отказывает мягко, задача остаётся в `spec_gate`;
- запись «approve отклонён» начинается с «раздел «Заменяемые тесты» не
  сверить — решение профиля тестов проекта: отказ:» и несёт
  `decide(<проект>).refusal`;
- записи `mandate.REPLACED_TESTS_ACTION` нет.

AC-6. Все тесты AC-1–AC-5 лежат в одном новом файле
`tests/test_01m5hj3yfbvk8tsr7vq7jpyj7c_<имя>.py` с «Группа: долгоживущий»
и маркером «Зелёный с рождения». Требования к тестам:
- у каждого докстринг с «Сценарий» и «Ловит мутацию:»;
- имена проекта, файлов и тестов берутся из `random`, зерно печатается и
  входит в текст провала;
- используются настоящий git (`tests.sandbox.GitignoreCommittedRealGitSandbox`),
  без сети и Node;
- подменяются только `subprocess.Popen`,
  `github_adapter.ensure_head_in_origin`, `github_adapter.ensure_draft_mr`

  `fsm`, `project_profile`, `repo_context`, `targets`, `guard` не
  подменяются;
- самый длинный тест при отдельном прогоне файла укладывается в 15 с.

Кроме нового файла и регенерированной карты, задача ничего не меняет:

AC-7. PLAN.md несёт таблицу «мутация → красные тесты» по М1–М8

## Оценка объёма и деление

Сработавший сигнал — «число затрагиваемых модулей/файлов». Guard считает
пути, упомянутые в тексте. Почти все они — адреса кода пульта и
существующих тестов, которые задача только читает (ТЗ, «Только чтение»).
Записываются только два пути: один новый файл `tests/` и регенерированная
`docs/codebase-map.md`.

Прогноз диффа: 60 КиБ (один новый файл тестов на четыре группы сценариев
плюс строки карты).

**Обоснование монолита:** весь выход задачи — один новый файл тестов,
который ТЗ требует целиком (требование 5: «один новый файл»). Нарезать по
зонам нечего: у задачи одна зона записи. Разнести сценарии Н1, Н2 и Н5 по
разным файлам или задачам — значит отступить от оформления, которое задал
Оператор. Код пульта не меняется, поэтому промежуточного нерабочего
состояния не бывает: решение о монолите — решение об оформлении, а не о
механике.
