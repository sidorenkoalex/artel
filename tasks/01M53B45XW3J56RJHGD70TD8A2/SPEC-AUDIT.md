Отклонения проверяемости:
- **В-1 (AC-3, SPEC.md:142-147; D2-2 SPEC.md:315-317).** В песочнице теста
  нет конкурирующего помощника, поэтому `git config --get-all
  credential.helper` покажет «только помощник пульта» и без всякого
  сброса. Мутация «добавить свой помощник, не сбросив чужие (пустым
  `credential.helper=` перед своим)» тест проходит. На машине Оператора
  при этом сначала ответит его `osxkeychain` или `gh auth git-credential`
  из `~/.gitconfig`, и push уйдёт с токеном Оператора, а не проекта. Есть
  и вторая дыра: `--get-all credential.helper` не видит помощников с
  областью URL (`credential.https://github.com.helper`, его ставит
  `gh auth setup-git`), а `git credential fill` их использует. Нужно в
  AC-3 подготовить в окружении теста (`HOME`/`GIT_CONFIG_GLOBAL`/
  `GIT_CONFIG_SYSTEM`) чужой общий помощник и чужой помощник с областью
  URL, отдающие другой пароль, и проверить, что `git credential fill` по
  URL проекта возвращает токен слота.
- **В-2 (AC-5 + требование 1, механизм «проект по `-C`»).**
  `doctor/artifact_branches.py:126-138` пушит из репозитория `source`
  («клон или главная копия пульта») по URL origin клона `repo`. Когда
  `source` — главная копия (`config.ROOT`, вне `.artel/projects/<проект>/`),
  механизм проект не узнает, и push внешнего проекта уйдёт с авторизацией
  Оператора. AC-3, AC-4 и AC-5 этот путь не покрывают. Нужно либо
  назвать вызов в «Не входит», либо дать критерий «push по URL внешнего
  проекта из `-C` вне области проекта — именованный отказ или токен
  проекта».
- **В-3 (AC-11, SPEC.md:198-200).** «С абсолютным корнем пульта» пропустит
  мутацию, при которой правило собрано из другой формы пути
  (`realpath`/`resolve()`), чем строка миссий `config.ROOT /
  "orchestrator" / "artel.py"` (`role_prompt.py:238`,
  `knowledge_cards.py:953`). Префикс правила тогда не совпадёт с
  командами из миссии, и роль внешнего проекта лишится и `knowledge`, и
  `suite-run`, и `plank-run`. Нужно, чтобы AC-11 сравнивал правило
  посимвольно с той строкой, которую печатает миссия.
- **В-4 (8.4, AC-9; SPEC.md:83-86, 185-188).** Исход 8.4 (ok/warn/fail)
  при недоступных данных не задан, а требование 8 требует его у каждой
  проверки (SPEC.md:68). Если выбрать fail, `doctor` выйдет с `rc=1`
  (`doctor/cli.py:206-209`) у любого проекта, токен которого не имеет
  прав администратора на `…/protection` (GitHub отдаёт 403/404). Для
  «информационной» проверки это постоянный красный `doctor`. Нужно, чтобы
  AC-9 задавал исход «недоступно» явно (ok или warn, не fail).
- **В-5 (8.1, AC-8; SPEC.md:71-73, 173-174).** `git clone` не пишет
  `FETCH_HEAD`, а клон заводит `target-init` (`workspace.py:111`). У клона,
  который пульт ещё ни разу не fetch-ил, файла нет, и исход 8.1 не
  определён. Возможны warn, ok или исключение `FileNotFoundError`, которое
  уронит весь `doctor`. Нужно, чтобы AC-8 задал исход для «`FETCH_HEAD`
  нет».
- **В-6 (8.1, AC-8; Ф-2).** «Клона нет» можно подготовить, вообще не
  создав каталог проекта. Тогда мутация «проверять существование
  `.artel/projects/<имя>/`, а не `…/repo/.git`» тест проходит, хотя на
  пульте каталог проекта есть всегда. Нужно в AC-8 готовить состояние
  «каталог проекта есть, `repo/` нет».

## Пути обхода гейтов

- П-1 (= В-1). Помощник пульта добавлен без сброса чужих. AC-3 зелёный, а
  на пульте `git` берёт учётные данные Оператора из `~/.gitconfig`
  (`osxkeychain`/`gh auth git-credential`). Буква ТЗ п.1 «без системного
  `osxkeychain`» выполнена тестом, смысл (токен проекта, а не Оператора)
  — нет.
- П-2 (= В-2). Push по URL внешнего проекта из `-C` вне области проекта
  (`doctor/artifact_branches.py:137`, `source` = главная копия) идёт с
  авторизацией Оператора. Механизм О-4 его не видит.
- П-3. Признак процесса роли — маркер, а не граница
  (`runner.py:1061-1063`). Требование 13 держится на
  `in_role_environment`. Обойти его роль может только командой вне
  суженного списка, а `Bash(python3 <корень>/orchestrator/artel.py:*)`
  префикс `env -u ARTEL_ROLE …` не пропускает. Остаточный риск в пределах
  ADR-0023, вторая поправка п.5. Отдельного отклонения нет.
- П-4. Миссии требуют от ролей прямого `pytest`, а суженный список его
  запрещает: `role_prompt.py:89-94` (долгоживущие файлы `tests/` «тем же
  pytest» у автора тестов) и `role_prompt.py:245-246` («сначала — тесты
  затронутых модулей» у разработчика, а затронутые модули можно прогнать
  только прямым `pytest`). «Не входит» (SPEC.md, раздел «Не входит»)
  называет известным недочётом только `python3 scripts/guard.py`; эти два
  места не названы. Роль внешнего проекта упрётся в отказ CLI посреди
  шага. Это тот же класс, что и недочёт с guard, принятый Оператором;
  нужно лишь дописать его в «Не входит».
