## Пути обхода гейтов
1. **Пробный push без токена (AC-3).** С локальным `origin` буквальное
   выполнение AC-3 проходит без всякой передачи токена в git. Требование
   «токен через помощник из окружения, без `osxkeychain`» тестом не
   держится (О-1).
2. **Утечка токена на пути отказа.** Токен в argv `-c` или в URL `origin`
   не виден на успешном пути AC-5. Он всплывает в тексте инцидента,
   когда push отказан (О-2).
3. **Хостинговые операции с токеном из процесса роли.** Роль вправе
   звать `python3 <корень>/orchestrator/artel.py doctor` без `--fix`
   (artel.py:1883-1899), и суженный белый список это пропускает.
   Значит, новые проверки 8.1 (fetch в клон) и 8.2 (`push --dry-run`) с
   токеном слота пойдут из дерева процессов роли: пульт прочтёт keychain
   и положит токен в окружение дочернего git/`gh`. Требование 3
   («токен не попадает в окружение роли») буквально выполнено, но по
   смыслу роль получает канал запускать хостинговые операции с токеном
   проекта, а fetch проверки 8.1 при этом меняет ссылки клона. SPEC не
   говорит, отказывают ли хостинговые проверки `doctor` под
   `runner.in_role_environment()` (О-6).
4. Обходы суженного белого списка через `git -c alias`,
   `core.fsmonitor` и код, исполняемый `plank-run`/`suite-run`,
   оформлены как принятый остаточный риск (ANSWER-1 п.3). Отклонением не
   считаю.

## Вердикт
**concerns.** SPEC верно отражает ТЗ и ANSWER-1, ссылки на код
подтверждены. Отклонения ниже Оператор может снять на гейте ответом или
возвратом с решением.

- **О-1 (AC-3 не проверяем).** SPEC.md:113-117. С локальным `origin`
  (требование 12) git не вызывает помощник учётных данных. Пропущенный
  токен или неустранённый `osxkeychain` AC-3 не ловит. Нужен
  наблюдаемый признак, например:
  - `git config --get-all credential.helper` в окружении вызова даёт
    только помощник пульта после сброса;
  - или `git credential fill` в этом окружении возвращает токен слота.
- **О-2 (AC-5 только на успешном пути).** SPEC.md:123-126. Нужен случай
  отказанной хостинговой операции, а также запрет токена в argv
  (требование 1 говорит «через окружение», AC этого не проверяет).
- **О-3 (источники данных проверок `doctor` не заданы).** SPEC.md:59-66,
  67-70; AC-8 (SPEC.md:138-146), AC-9 8.3/8.4 (SPEC.md:149-152). Не
  названы:
  - источник «времени последнего успешного fetch»;
  - источник наличия CI на `pull_request`;
  - источник защиты ветки.

  Тесты на подставном `gh` или подготовленных файлах навяжут устройство
  (`тест-навязывает-устройство`).
- **О-4 (механизм токена в зонах не зафиксирован).** SPEC.md:321-325,
  стр. 30-40. Хостинговые git-вызовы идут из модулей вне зон.

  проекта) в SPEC не назван. Без указания механизма велик риск
  эскалации выхода за зоны посреди `in_dev`.
- **О-5 («токен артели» в 8.5 не определён).** SPEC.md:71-74,
  AC-9 SPEC.md:153-154. Сравнивать можно:
  - со значением слота `token_slot` записи артели (`artel-token`,
