# QUESTIONS: D2 — подключение внешнего проекта со стороны пульта

## Вопросы

Остальное ТЗ достаточно для SPEC. Токен п.1 укладывается в зоны: все
git-вызовы пульта, включая push из `artifact_branch.py:346`,
`fsm_merge_gate.py:697,1142` и `snapshot.py:294`, идут через
`gitcmd.git`/`gitcmd.carpentry` → `gitcmd.pult_env`
(`orchestrator/gitcmd.py:22-29`, `:43`, `:225`). Без ответа остаются
четыре места. Если по нескольким пунктам ответа не будет, SPEC будет
написан по дефолтам. Сигналы объёма срабатывают (10 зон, рамка $45),
поэтому SPEC в любом случае предложит нарезку на части: (а) токен
хостинга и проверки `doctor`; (б) проектные скилы и меры для роли.

1. **Где отказывать записи с неверным `project_skills` — `orchestrator/targets.py` в ТЗ только для чтения.** П.2 ТЗ требует «отказ проверки записи» для имени вне `skills/` или несуществующего файла. Запись сегодня проверяет `targets.check` (`orchestrator/targets.py:139-168`), а он вне зон.
   - A) Добавить `orchestrator/targets.py` в зоны и проверять в `targets.check`, тем же приёмом, что `knowledge` и `core_reference` (`:163-168`).
     - ломается: сломанный `project_skills` любой записи делает весь `targets.yaml` негодным при первом чтении (`targets.load`, `:98-99`); пульт отказывает всем командам, пока Оператор не починит файл.
     - ослабляется: ничего; проверка встаёт в общий рубеж записи.
     - цена: +1 файл зоны, ~+$3; число зон и так уже требует деления.
     - чьё решение: Оператор (расширение зон из «только чтение»).
   - B) Не трогать `targets.py`: проверять при сборке брифа (`orchestrator/brief.py`) — отказ шага роли с именем проекта, поля и скила — и отдельным пунктом `doctor` по записи.
     - ломается: ничего за пределами задач этого проекта; `targets.yaml` для остальных проектов остаётся годным.
     - ослабляется: ошибку видно не при чтении файла, а при первом шаге роли или в `doctor`; принцип «узнать о сломанной записи на первом чтении» из `targets.py:12-14` для этого поля не держится.
     - цена: без изменения зон; столько же кода, сколько в A.
     - чьё решение: роль (в пределах зон ТЗ).
   - C) Проверять в `orchestrator/projects.py` при `target-init` и в `doctor`.
     - ломается: если запись поправили после `target-init`, неверный скил обнаружится только в `doctor`; бриф должен будет молча пропускать файл или падать без названной причины.
     - ослабляется: то же, что в B, плюс окно между правкой `targets.yaml` и следующим `doctor`.
     - цена: без изменения зон.
     - чьё решение: роль.
   - дефолт: B — остаётся в зонах ТЗ, отказ названный, и сломанное поле одного проекта не останавливает пульт.

2. **Какие вызовы `python3`, кроме команд пульта, оставить роли внешнего проекта (п.4 ТЗ просит перечислить).** Сверка по `skills/` и миссиям шага:
   - команды пульта по абсолютному пути `python3 <корень пульта>/orchestrator/artel.py …`: `knowledge` (`knowledge_cards.py:954`), `suite-run` (`role_prompt.py:240-245`, `suite_run.py:232`), `plank-run` (`role_prompt.py:323`). Префикс один и стабилен;
   - `python3 scripts/guard.py` — путь относительный (`skills/spec-authoring.md:211`, миссии `role_prompt.py:59,117,217`). В рабочей копии внешнего проекта этого файла нет, вызов не сработает и под сегодняшним `python3:*`;
   - `python3 scripts/codebase_map.py` (`skills/conventions-core.md:42`) нужен только для правок кода пульта, к внешнему проекту не относится;
   - `python3 -m pytest …` (`skills/test-authoring.md:408`, `skills/coding-standards.md:103,109`, `role_prompt.py:91`) исполняет код проекта. ADR-0023, поправка 16.10, п.6 убирает это у роли внешнего проекта.
   - A) Только префикс `Bash(python3 <корень пульта>/orchestrator/artel.py:*)` вместо `Bash(python3:*)`.
     - ломается: роль внешнего проекта не может сама запустить guard и отдельный тест. guard всё равно гоняет пульт на переходе (`fsm.guard_refuses`), отказ придёт при `advance`. Тесты — только `suite-run`/`plank-run`.
     - ослабляется: ничего из сегодняшних защит; самопроверка роли до сдачи для внешнего проекта теряется.
     - цена: без доплаты; возможны лишние возвраты шага на отказе guard, ~+$2–3 за возврат.
     - чьё решение: Оператор.
   - B) A плюс `Bash(python3 <корень пульта>/scripts/guard.py:*)` по абсолютному пути.
     - ломается: ничего; но скилы и миссия велят относительную форму `python3 scripts/guard.py`, она под правило не подпадёт. Пользы не будет, пока не поменяют текст миссии (`orchestrator/role_prompt.py`, вне зон) или скила (`skills/`, защищённый путь).
     - ослабляется: ничего (guard читает только артефакты).
     - цена: +1 правило; чтобы был толк — правка `role_prompt.py` (расширение зон) или MR Оператора в `skills/`.
     - чьё решение: Оператор.
   - C) A плюс `Bash(python3 -m pytest:*)`.
     - ломается: ничего.
     - ослабляется: мера п.6 поправки 16.10 ADR-0023 (`docs/adr/0023-role-step-sandbox.md:1204-1207`) — роль снова исполняет код проекта (`conftest.py`) напрямую. Для sled (тесты через `uv run`) правило к тому же бесполезно.
     - цена: без доплаты.
     - чьё решение: Оператор (отступление от ADR).
   - дефолт: A — ровно то, что требует ADR-0023 п.6 и ТЗ п.4; guard по-прежнему держит пульт на переходе.

3. **Что считать «надёжным» сужением правила (п.4 ТЗ: «если клиент не позволяет сузить надёжно — эскалация»).** Правило-префикс Claude CLI `Bash(<префикс>:*)` в `--allowedTools` (`providers/claude.py:45`, `:158-174`) учитывает операторы оболочки (`&&`, `;`, `|`), так что `python3 <artel.py> … && python3 -c …` под него не подпадёт. Обходы остаются. Первый: `Bash(git:*)` исполняет произвольную команду через `git -c alias.x='!…'` и `core.fsmonitor`. Второй: `plank-run`/`suite-run` исполняют код, написанный ролью. ADR-0023 п.8 (`docs/adr/0023-role-step-sandbox.md:519-524`) прямо называет список «не границей».
   - A) Считать сужение достаточным в смысле ADR-0023 п.8: роль в штатной работе не зовёт `python3` напрямую. Приёмка проверяет argv шага роли — нет `Bash(python3:*)`, есть суженный префикс. Обходы через `git` и команды пульта записываются в «Не входит» как принятый остаточный риск (поправка 16.10, вторая, п.5).
     - ломается: ничего сверх вопроса 2.
     - ослабляется: ничего относительно сегодняшнего; обход через `git -c` остаётся, как и сейчас.
     - цена: без доплаты.
     - чьё решение: Оператор (уже принято в ADR-0023 п.8, подтверждение).
   - B) Сузить и `git`: запретить `git -c` и подобное через `--disallowedTools`/`permissions.deny`.
     - ломается: возможны ложные отказы штатных git-команд роли с `-c`; ТЗ этого не просит.
     - ослабляется: ничего.
     - цена: расширение объёма ТЗ, ~+$6–10; deny-правила курируемого дома (`docs/reference/role-home/`) — защищённый путь.
     - чьё решение: Оператор.
   - C) Признать сужение ненадёжным и отложить п.4 до D1а.
     - ломается: мера п.6 поправки 16.10 не вводится до D1а, хотя вторая поправка, п.3, оставляет её в D2.
     - ослабляется: роль sled сохраняет `python3:*` на хосте.
     - цена: объём задачи меньше, ~−$5.
     - чьё решение: Оператор.
   - дефолт: A — совпадает с ADR-0023 п.8 и второй поправкой, п.3.

     - чьё решение: Оператор (число).
   - B) Дата коммита головы `origin/<base>` после fetch. Старше порога (30 суток) — warn.
     - ломается: на спокойном проекте без коммитов — постоянный ложный warn.
