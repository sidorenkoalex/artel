# ТЗ: D2: подключение внешнего проекта со стороны пульта — токен проекта, проектные скилы, проверки doctor, меры для роли

# D2: подключение внешнего проекта со стороны пульта — токен проекта, проектные скилы, проверки doctor, меры для роли

## Факты

Основание — ADR-0023, вторая поправка 16.10.2026 (п.3: меры для роли остаются в D2), ТЗ-4 и ТЗ-5 исследования `docs/research/2026-09-04-external-target-readiness.md` (§5). Задача идёт параллельно D0 и не трогает исполнение тестов; профиль тестов sled вносится после D0-1.

Сейчас:
- поля записи проекта `token_slot` и `project_skills` проверяются (`orchestrator/targets.py:29-31`), но не исполняются;
- `gh` пульта запускается с окружением и авторизацией Оператора (`orchestrator/ci.py:57-59`; `--repo` для внешнего проекта — `orchestrator/github_adapter.py:103-139`); git-операции пульта с хостингом идут через системный помощник учётных данных `osxkeychain` Оператора (ADR-0023, «Сеть, секреты, пуш»);
- `roles.token_slots` и `runner.role_token` (`orchestrator/roles.py:35-49`, `orchestrator/runner.py:837-848`) — подписочный токен модели роли, к токену хостинга проекта отношения не имеют;
- скилы роли берутся только из `roles.yaml` (`orchestrator/brief.py:519-542`);
- `doctor` не проверяет клон и хостинг внешнего проекта (ТЗ-5, §2.4 исследования);
- белый список инструментов роли Claude — `Bash(git:*),Bash(python3:*)` (`orchestrator/providers/claude.py:45`); разрешённый `python3` исполняет любой код на хосте;
- окружение роли (`runner.role_env`, `orchestrator/runner.py:964`) не задаёт `GIT_CONFIG_NOSYSTEM`, и системный помощник `osxkeychain` доступен роли.

Требуется:

1. **Токен хостинга проекта.** Для внешнего проекта операции пульта с его хостингом (`gh` и git-операции пульта с `origin` клона: fetch, push веток задачи, `refs/artifacts/*`, мерж) берут токен из слота связки ключей `token_slot` записи проекта: `GH_TOKEN` в окружении `gh`, для git — помощник учётных данных из окружения этого вызова, без записи в конфигурацию клона и без системного `osxkeychain`. Нет токена в слоте — именованный отказ операции с именем слота. Для артели поведение не меняется. Токен не попадает в журналы, вывод команд и окружение роли.
2. **Проектные скилы.** `project_skills` — список имён скилов пульта (`skills/<имя>.md`); они добавляются в бриф роли для задач этого проекта после скилов из `roles.yaml`. Имя вне `skills/` или несуществующий файл — отказ проверки записи. Для артели (`project_skills: []`) бриф не меняется.
3. **Проверки `doctor` для каждой записи внешнего проекта** (ok/warn/fail; для артели — явное решение «неприменимо», не пропуск):
   1. клон в `.artel/projects/<имя>/` есть, `origin` совпадает с `url`, голова `origin/<base>` не старше порога (fetch без изменения рабочих копий);
   2. право пуша в `refs/artifacts/*` — пробный `git push --dry-run` с токеном п.1; отказ — fail;
   3. у проекта есть CI на `pull_request` — нет — warn «verifying будет ждать до потолка»;
   4. защита базовой ветки — информационно, недоступна — так и сказать;
   5. токен в слоте `token_slot` есть; общий с артелью токен — warn «одобрение своим же токеном технически возможно — `docs/triggers.md` №24» (не блокирует);
   6. пути `no_paths` существуют в дереве клона.
4. **Меры для роли внешнего проекта** (ADR-0023, поправка 16.10, п.6; вторая поправка, п.3):
   - в окружение роли — `GIT_CONFIG_NOSYSTEM=1`;
   - белый список инструментов роли Claude для задач внешнего проекта сужается: вместо `Bash(python3:*)` — только вызов команд пульта (`python3 <корень пульта>/orchestrator/artel.py …`) в той форме, которой пользуются скилы роли. Аналитик сверяет по `skills/` и брифам, какие ещё вызовы `python3` нужны роли, и перечисляет их в SPEC. Если клиент не позволяет сузить правило надёжно — эскалация до SPEC с вариантами, а не молчаливое оставление `python3:*`.
   Для артели белый список и окружение роли не меняются.
5. **Тесты** детерминированы, без сети: второй настоящий git-репозиторий как `origin` внешнего проекта; подставной исполняемый файл `gh`; слот связки ключей — подменой функции чтения слота. Проверяется: токен п.1 доходит до `gh` и git только для внешнего проекта и не появляется в журнале и окружении роли; отказ без токена; скилы п.2 в брифе; каждая проверка п.3 даёт ok/warn/fail на подготовленных состояниях; меры п.4 у роли внешнего проекта и их отсутствие у артели.

Критерии приёмки:
- у артели бриф, окружение и белый список роли, команды `gh` и git пульта не изменились;
- для учебного внешнего проекта `gh` получает `GH_TOKEN` из слота проекта, git-пуш пульта проходит с токеном слота и без `osxkeychain`; токен не встречается ни в одном журнале задачи;
- `doctor` выводит по учебному внешнему проекту все шесть проверок с ожидаемыми исходами;
- роль задачи внешнего проекта получает `GIT_CONFIG_NOSYSTEM=1` и суженный белый список.
