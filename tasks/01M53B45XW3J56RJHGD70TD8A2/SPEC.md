# SPEC: D2 — подключение внешнего проекта со стороны пульта: токен проекта, проектные скилы, проверки doctor, меры для роли

## Контекст
Поля записи проекта `token_slot` и `project_skills` проверяются
(`orchestrator/targets.py:29-31`), но пульт их не исполняет. `gh` пульта
работает с окружением и авторизацией Оператора (`orchestrator/ci.py:57-59`,
`orchestrator/github_adapter.py:103-139`). git-операции пульта с хостингом
идут через системный помощник `osxkeychain` Оператора. Скилы роли берутся
только из `roles.yaml` (`orchestrator/brief.py:519`). `doctor` не проверяет
клон и хостинг внешнего проекта. Роль Claude получает `Bash(python3:*)`
(`orchestrator/providers/claude.py:45`), а её окружение
(`orchestrator/runner.py:964`, `role_env`) не задаёт `GIT_CONFIG_NOSYSTEM`.
Основание: ADR-0023, вторая поправка 16.10.2026, п.3; ТЗ-4 и ТЗ-5
исследования `docs/research/2026-09-04-external-target-readiness.md` (§5).
Решения по батчу вопросов приняты в ANSWER-1 (17.10.2026): все пункты по
вариантам по умолчанию.

## Требования

1. **Токен хостинга проекта.** Для внешнего проекта (не артели) операции
   пульта с его хостингом берут токен из слота связки ключей, имя которого
   задано полем `token_slot` записи проекта. Операции хостинга: вызовы
   `gh` и git-операции пульта с `origin` клона (fetch, push веток задачи,
   push `refs/artifacts/*`, мерж).
   - `gh` получает токен переменной `GH_TOKEN` в окружении своего вызова.
   - git получает помощник учётных данных через окружение своего вызова.
     Конфигурация клона не меняется, системный помощник `osxkeychain` не
     участвует.
2. В слоте `token_slot` нет токена — операция хостинга внешнего проекта
   отказывает с текстом, в котором названо имя слота.
3. Значение токена п.1 не попадает в журналы задачи, вывод команд пульта и
   окружение роли.
4. Для артели вызовы `gh` и git-операции пульта не меняются: окружение и
   аргументы те же, что на main.
5. **Проектные скилы.** Скилы из `project_skills` записи проекта — имена
   скилов пульта (`skills/<имя>.md`). В бриф роли задачи этого проекта они
   добавляются после скилов из `roles.yaml`, в порядке поля.
6. Допустимы только имена, указывающие на существующий файл прямо в
   `skills/`. Имя вне `skills/` или несуществующий файл — отказ при сборке
   брифа (`orchestrator/brief.py`). В тексте отказа названы проект, поле
   `project_skills` и имя скила. Неверное поле одного проекта не делает
   `targets.yaml` негодным для остальных проектов: `orchestrator/targets.py`
   не меняется. Та же проверка выполняется отдельной проверкой `doctor` по
   записи проекта (ANSWER-1, п.1).
7. Для артели (`project_skills: []`) бриф роли не меняется.
8. **Проверки `doctor`.** Для каждой записи внешнего проекта `doctor`
   выводит шесть проверок, у каждой исход ok, warn или fail:
   1. Клон и свежесть. Клона в `.artel/projects/<имя>/` нет — fail.
      `origin` клона не совпадает с `url` записи — fail. Затем проверяется
      время последнего успешного fetch клона пультом, взятое до fetch
      самой проверки. Оно старше порога — warn с текстом «клон не
      обновлялся N ч». Порог — константа `orchestrator/config.py`, 24 ч
      (ANSWER-1, п.4). После этого проверка делает fetch, рабочие копии
      при этом не меняются. Fetch не прошёл — fail.
   2. Право пуша в `refs/artifacts/*`. Проверка делает пробный
      `git push --dry-run` с токеном п.1. Отказ — fail.
   3. CI на `pull_request`. У проекта нет CI на `pull_request` — warn
      «verifying будет ждать до потолка».
   4. Защита базовой ветки — информационная проверка. Данные недоступны —
      вывод прямо говорит, что они недоступны.
   5. Токен. Токена в слоте `token_slot` нет — fail. Токен общий с
      артелью — warn «одобрение своим же токеном технически возможно —
      `docs/triggers.md` №24». Этот warn не блокирует.
   6. `no_paths`. Каждый путь `no_paths` записи должен существовать в
      дереве клона. Отсутствующий путь даёт исход не ok, и путь назван в
      выводе.
9. Для артели `doctor` выводит по этим проверкам явное решение
   «неприменимо», а не пропускает их молча.
10. **Меры для роли внешнего проекта** (ADR-0023, поправка 16.10, п.6;
    вторая поправка, п.3):
    - окружение роли задачи внешнего проекта содержит `GIT_CONFIG_NOSYSTEM=1`;
    - в белом списке инструментов роли Claude для такой задачи нет
      `Bash(python3:*)`. Вместо него стоит только правило
      `Bash(python3 <корень пульта>/orchestrator/artel.py:*)`, где
      `<корень пульта>` — абсолютный путь (ANSWER-1, п.2).
    Сверка вызовов `python3` в `skills/` и миссиях шага (результат,
    требуемый п.4 ТЗ). Роли внешнего проекта нужны только команды пульта
    по абсолютному пути: `knowledge` (`orchestrator/knowledge_cards.py:954`),
    `suite-run` (`orchestrator/role_prompt.py:240-245`), `plank-run`
    (`orchestrator/role_prompt.py:323`). Остальные вызовы `python3` роли
    внешнего проекта не разрешаются:
    - `python3 scripts/guard.py` — guard проверяет пульт на переходе;
    - `python3 scripts/codebase_map.py` — нужен только при правке кода
      пульта;
    - `python3 -m pytest` — тесты гоняются командами пульта.
    Такое сужение достаточно в смысле ADR-0023 п.8 (ANSWER-1, п.3).
11. Для артели белый список инструментов роли и окружение роли не
    меняются.
12. **Тесты** детерминированы и не ходят в сеть. Окружение тестов:
    - `origin` внешнего проекта — второй настоящий git-репозиторий;
    - `gh` — подставной исполняемый файл;
    - слот связки ключей — подмена функции чтения слота.

## Критерии приёмки

AC-1. Для артели бриф роли, окружение роли и белый список инструментов
роли Claude совпадают с main. Окружение и аргументы вызовов `gh` и
git-операций пульта для артели тоже совпадают с main.

AC-2. Для учебного внешнего проекта подставной `gh` получает в окружении
`GH_TOKEN`, равный значению из слота `token_slot` записи проекта.

AC-3. Для учебного внешнего проекта git-push пульта в `origin` (второй
настоящий git-репозиторий) проходит. git получает токен слота через
помощник учётных данных из окружения вызова. `.git/config` клона после
операции не изменён, системный помощник `osxkeychain` в вызове не
участвует.

AC-4. Пустой слот `token_slot` у внешнего проекта: операция хостинга
(`gh` и git-операция с `origin`) отказывает, в тексте отказа названо имя
слота.

AC-5. После операций AC-2 и AC-3 значение токена не встречается ни в
одном журнале задачи (журнал шагов БД, логи прогона) и в выводе команд
пульта. В окружении роли задачи внешнего проекта значения токена тоже
нет.

AC-6. В брифе роли задачи внешнего проекта с непустым `project_skills`
есть тексты этих скилов. Они стоят после скилов роли из `roles.yaml`, в
порядке поля.

AC-7. Два неверных `project_skills`: имя вне `skills/` (например, с
переходом в родительский каталог или с абсолютным путём) и имя несуществующего файла. В каждом случае сборка брифа
отказывает, текст отказа называет проект, `project_skills` и имя скила.
Проверка `doctor` по этой записи даёт fail. `targets.yaml` остаётся
читаемым, задачи других проектов собирают бриф без отказа.

AC-8. Проверка `doctor` п.8.1 на подготовленных состояниях:
- клон свежий, `origin` совпадает с `url`, fetch проходит — ok;
- последний успешный fetch старше 24 ч — warn с текстом «клон не
  обновлялся N ч»;
- клона нет — fail;
- `origin` не совпадает с `url` — fail;
- fetch не прошёл — fail.
Рабочие копии после проверки не изменены.

AC-9. Проверки `doctor` п.8.2–8.6 на подготовленных состояниях:
- 8.2: пробный push в `refs/artifacts/*` проходит — ok, отказан — fail;
- 8.3: CI на `pull_request` есть — ok, нет — warn «verifying будет ждать
  до потолка»;
- 8.4: защита базовой ветки известна — она выведена, недоступна — вывод
  говорит о недоступности;
- 8.5: токен есть и отличен от токена артели — ok; токен общий с артелью
  — warn со ссылкой на `docs/triggers.md` №24; токена нет — fail;
- 8.6: все пути `no_paths` есть в дереве клона — ok; путь отсутствует —
  исход не ok, путь назван.

AC-10. По записи артели `doctor` выводит для проверок п.8 решение
«неприменимо».

AC-11. В argv шага роли Claude задачи внешнего проекта нет
`Bash(python3:*)`, есть `Bash(python3 <корень пульта>/orchestrator/artel.py:*)`
с абсолютным корнем пульта. Окружение этого шага содержит
`GIT_CONFIG_NOSYSTEM=1`. У задачи артели argv и окружение шага этих
изменений не несут (см. AC-1).
