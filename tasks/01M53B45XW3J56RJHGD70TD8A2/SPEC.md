# SPEC: D2 — подключение внешнего проекта со стороны пульта: токен проекта, проектные скилы, проверки doctor, меры для роли

## Контекст
Поля записи проекта `token_slot` и `project_skills` проверяются
(`orchestrator/targets.py:29-31`), но пульт их не исполняет. `gh` пульта
работает с окружением и авторизацией Оператора (`orchestrator/ci.py:57-59`,
`orchestrator/github_adapter.py:103-139`). git-операции пульта с хостингом
идут через системный помощник `osxkeychain` Оператора. Скилы роли берутся
только из `roles.yaml` (`orchestrator/brief.py:519`). `doctor` не проверяет
клон и хостинг внешнего проекта. Роль Claude получает `Bash(python3:*)`
(`orchestrator/providers/claude.py:45`), а её окружение
(`orchestrator/runner.py:964`, `role_env`) не задаёт `GIT_CONFIG_NOSYSTEM`.
Основание: ADR-0023, вторая поправка 16.10.2026, п.3; ТЗ-4 и ТЗ-5
исследования `docs/research/2026-09-04-external-target-readiness.md` (§5).
Решения по батчу вопросов приняты в ANSWER-1 (17.10.2026): все пункты по
вариантам по умолчанию. Замечания аудита SPEC О-1…О-6 решены Оператором
на гейте SPEC 17.10.2026 (возврат из `spec_gate`). Замечания повторного
аудита (В-1…В-6, П-4, Ф-1, Ф-4, Ф-5) решены Оператором на гейте SPEC
17.10.2026 (второй возврат из `spec_gate`). Слот `artel-token` записи
артели — токен подписки модели, не хостинга (Ф-4); запись sled получит
слот `sled-github-token` (запись делает Оператор).

## Требования

1. **Токен хостинга проекта.** Для внешнего проекта (не артели) операции
   пульта с его хостингом берут токен из слота связки ключей, имя которого
   задано полем `token_slot` записи проекта. Операции хостинга: вызовы
   `gh` и git-операции пульта с `origin` клона (fetch, push веток задачи,
   push `refs/artifacts/*`, мерж).
   - `gh` получает токен переменной `GH_TOKEN` в окружении своего вызова.
   - git получает помощник учётных данных через окружение своего вызова.
     Конфигурация клона не меняется, системный помощник `osxkeychain` не
     участвует.
   - Механизм для git (решение Оператора 17.10, О-4): `gitcmd.git`
     определяет проект по пути аргумента `-C`, лежащему внутри
     `.artel/projects/<проект>/`, и подставляет токен слота этого
     проекта. Сигнатура `gitcmd.git` не меняется.
   - Прямой вызов `gh` в `doctor` (`orchestrator/doctor/misc_checks.py:92`,
     `check_base_branch`) для внешнего проекта тоже получает токен
     проекта.
2. В слоте `token_slot` нет токена — операция хостинга внешнего проекта
   отказывает с текстом, в котором названо имя слота.
3. Значение токена п.1 не попадает в журналы задачи, вывод команд пульта и
   окружение роли. Это верно и для отказанной хостинговой операции (например,
   `origin` отказал в push): текст отказа, журналы и вывод токена не
   содержат. Токен не передаётся в argv ни одного вызова (git, `gh`,
   помощник учётных данных) — только через окружение (О-2).
4. Для артели вызовы `gh` и git-операции пульта не меняются: окружение и
   аргументы те же, что на main.
5. **Проектные скилы.** Скилы из `project_skills` записи проекта — имена
   скилов пульта (`skills/<имя>.md`). В бриф роли задачи этого проекта они
   добавляются после скилов из `roles.yaml`, в порядке поля.
6. Допустимы только имена, указывающие на существующий файл прямо в
   `skills/`. «Существующий файл» — файл на диске пульта
   (`config.ROOT/skills/<имя>.md`); источник один и тот же для сборки
   брифа и для проверки `doctor` (Ф-5). Имя вне `skills/` или несуществующий файл — отказ при сборке
   брифа (`orchestrator/brief.py`). В тексте отказа названы проект, поле
   `project_skills` и имя скила. Неверное поле одного проекта не делает
   `targets.yaml` негодным для остальных проектов: `orchestrator/targets.py`
   не меняется. Та же проверка выполняется отдельной проверкой `doctor` по
   записи проекта (ANSWER-1, п.1).
7. Для артели (`project_skills: []`) бриф роли не меняется.
8. **Проверки `doctor`.** Для каждой записи внешнего проекта `doctor`
   выводит шесть проверок, у каждой исход ok, warn или fail:
   1. Клон и свежесть. Клон — `.artel/projects/<имя>/repo`
      (`repo_context.clone_path`, `orchestrator/repo_context.py:75-79`), а
      не сам каталог проекта (В-6). Клона нет — fail. `origin` клона не
      совпадает с `url` записи — fail. Затем проверяется время последнего
      успешного fetch клона пультом, взятое до fetch самой проверки: время
      изменения файла `FETCH_HEAD` клона (О-3). Оно старше порога — warn с
      текстом «клон не обновлялся N ч». Порог — константа
      `orchestrator/config.py`, 24 ч (ANSWER-1, п.4). Файла `FETCH_HEAD`
      нет (свежий клон `target-init`, который пульт ещё не обновлял) —
      warn «клон ещё не обновлялся пультом», не fail (В-5). После этого
      проверка делает fetch, рабочие копии при этом не меняются. Fetch не
      прошёл — fail.
   2. Право пуша в `refs/artifacts/*`. Проверка делает пробный
      `git push --dry-run` с токеном п.1. Отказ — fail.
   3. CI на `pull_request`. Источник — разбор файлов
      `.github/workflows/*.yml` в дереве клона, без сети (О-3). Ни один
      файл не объявляет триггер `pull_request` — warn «verifying будет
      ждать до потолка».
   4. Защита базовой ветки — информационная проверка. Источник —
      `gh api repos/<владелец>/<репозиторий>/branches/<base>/protection` с
      токеном проекта п.1 (О-3). Ответ получен — сведения выводятся. Данные
      недоступны — вывод даёт сведение «недоступно», исход проверки не
      fail (В-4).
   5. Токен. Токена в слоте `token_slot` нет — fail. Проверка сравнивает
      значение токена слота `token_slot` проекта с токеном, которым `gh`
      Оператора ходит в хостинг (вывод `gh auth token`). Значения
      совпадают — warn «одобрение своим же токеном технически возможно —
      `docs/triggers.md` №24». Этот warn не блокирует. Сами значения в
      вывод не попадают (Ф-4; заменяет сравнение со слотом `token_slot`
      записи артели из О-5).
   6. `no_paths`. Каждый путь `no_paths` записи должен существовать в
      дереве клона. Отсутствующий путь даёт исход не ok, и путь назван в
      выводе.
9. Для артели `doctor` выводит по этим проверкам явное решение
   «неприменимо», а не пропускает их молча.
10. **Меры для роли внешнего проекта** (ADR-0023, поправка 16.10, п.6;
    вторая поправка, п.3):
    - окружение роли задачи внешнего проекта содержит `GIT_CONFIG_NOSYSTEM=1`;
    - в белом списке инструментов роли Claude для такой задачи нет
      `Bash(python3:*)`. Вместо него стоит только правило
      `Bash(python3 <корень пульта>/orchestrator/artel.py:*)`, где
      `<корень пульта>` — абсолютный путь (ANSWER-1, п.2). Путь
      `<корень пульта>/orchestrator/artel.py` в правиле посимвольно
      совпадает со строкой, которую печатают миссии шага
      (`config.ROOT / "orchestrator" / "artel.py"`,
      `orchestrator/role_prompt.py:238`,
      `orchestrator/knowledge_cards.py:953`) (В-3).
    Чтобы провайдер знал проект задачи, разрешено минимальное расширение
    зон: в `orchestrator/providers/base.py` и `orchestrator/providers/codex.py`
    меняется только сигнатура метода `command` (решение Оператора 17.10,
    О-4); поведение провайдера Codex не меняется.
    Сверка вызовов `python3` в `skills/` и миссиях шага (результат,
    требуемый п.4 ТЗ). Роли внешнего проекта нужны только команды пульта
    по абсолютному пути: `knowledge` (`orchestrator/knowledge_cards.py:954`),
    `suite-run` (`orchestrator/role_prompt.py:240-245`), `plank-run`
    (`orchestrator/role_prompt.py:323`). Остальные вызовы `python3` роли
    внешнего проекта не разрешаются:
    - `python3 scripts/guard.py` — guard проверяет пульт на переходе;
    - `python3 scripts/codebase_map.py` — нужен только при правке кода
      пульта;
    - `python3 -m pytest` — тесты гоняются командами пульта.
    Такое сужение достаточно в смысле ADR-0023 п.8 (ANSWER-1, п.3).
11. Для артели белый список инструментов роли и окружение роли не
    меняются.
12. **Тесты** детерминированы и не ходят в сеть. Окружение тестов:
    - `origin` внешнего проекта — второй настоящий git-репозиторий;
    - `gh` — подставной исполняемый файл;
    - слот связки ключей — подмена функции чтения слота.
13. **Токен и процесс роли** (решение Оператора 17.10, О-6). В процессе
    роли (окружение с маркером `ARTEL_ROLE`, `runner.in_role_environment`)
    токен хостинга проекта не читается ни при каких командах пульта.
    Проверки `doctor` 8.1 (fetch), 8.2 (пробный пуш) и 8.5 (сравнение
    токенов) там не выполняются и выводят именованный пропуск «только в
    сессии Оператора».
14. **Досылка коммита закрытия в `doctor`** (решение Оператора 17.10,
    В-2). Push из `orchestrator/doctor/artifact_branches.py:126-138`
    (`_push_closing_sha`) по URL `origin` клона внешнего проекта идёт с
    токеном проекта тем же механизмом, что и требование 1, в том числе
    когда репозиторий-источник `source` — главная копия пульта вне
    `.artel/projects/<проект>/`. Требования 2 и 3 действуют и для этого
    push.

## Критерии приёмки

AC-1. Для артели бриф роли, окружение роли и белый список инструментов
роли Claude совпадают с main. Окружение и аргументы вызовов `gh` и
git-операций пульта для артели тоже совпадают с main.

AC-2. Для учебного внешнего проекта подставной `gh` получает в окружении
`GH_TOKEN`, равный значению из слота `token_slot` записи проекта.

AC-3. Для учебного внешнего проекта git-push пульта в `origin` (второй
настоящий git-репозиторий) проходит, `.git/config` клона после операции
не изменён. В песочнице теста (`HOME`/`GIT_CONFIG_GLOBAL`/
`GIT_CONFIG_SYSTEM`) стоят два конкурирующих помощника учётных данных,
отдающие пароль, отличный от токена слота: глобальный
(`credential.helper`) и с областью URL проекта
(`credential.<URL проекта>.helper`) (В-1). В окружении хостингового
git-вызова пульта (О-1):
- `git config --get-all credential.helper` даёт только помощник пульта —
  чужие помощники сброшены;
- `git credential fill` по URL проекта возвращает только токен слота
  `token_slot` проекта.

AC-4. Пустой слот `token_slot` у внешнего проекта: операция хостинга
(`gh` и git-операция с `origin`) отказывает, в тексте отказа названо имя
слота.

AC-5. После операций AC-2 и AC-3 значение токена не встречается ни в
одном журнале задачи (журнал шагов БД, логи прогона) и в выводе команд
пульта. В окружении роли задачи внешнего проекта значения токена тоже
нет. То же для отказанной хостинговой операции (О-2): `origin` отказывает
в push — текст отказа, журналы задачи и вывод команд пульта значения
токена не содержат. Значения токена нет в argv ни одного вызова git,
`gh` и помощника учётных данных, сделанного при операциях этого критерия.

AC-6. В брифе роли задачи внешнего проекта с непустым `project_skills`
есть тексты этих скилов. Они стоят после скилов роли из `roles.yaml`, в
порядке поля.

AC-7. Два неверных `project_skills`: имя вне `skills/` (например, с
переходом в родительский каталог или с абсолютным путём) и имя несуществующего файла. В каждом случае сборка брифа
отказывает, текст отказа называет проект, `project_skills` и имя скила.
Проверка `doctor` по этой записи даёт fail. `targets.yaml` остаётся
читаемым, задачи других проектов собирают бриф без отказа.

AC-8. Проверка `doctor` п.8.1 на подготовленных состояниях:
- клон свежий, `origin` совпадает с `url`, fetch проходит — ok;
- время изменения `FETCH_HEAD` клона старше 24 ч — warn с текстом «клон
  не обновлялся N ч»;
- файла `FETCH_HEAD` в клоне нет (клон только что создан `git clone`) —
  warn «клон ещё не обновлялся пультом», не fail;
- клона нет: каталог проекта `.artel/projects/<имя>/` существует, а
  `.artel/projects/<имя>/repo` нет — fail;
- `origin` не совпадает с `url` — fail;
- fetch не прошёл — fail.
Рабочие копии после проверки не изменены.

AC-9. Проверки `doctor` п.8.2–8.6 на подготовленных состояниях:
- 8.2: пробный push в `refs/artifacts/*` проходит — ok, отказан — fail;
- 8.3: в дереве клона есть файл `.github/workflows/*.yml` с триггером
  `pull_request` — ok; такого файла нет — warn «verifying будет ждать до
  потолка»; сети проверка не касается;
- 8.4: подставной `gh` отвечает на
  `api repos/<владелец>/<репозиторий>/branches/<base>/protection` данными
  — сведения выведены; отказывает — вывод даёт сведение «недоступно», исход
  проверки не fail; в окружении этого вызова `GH_TOKEN` равен токену слота
  проекта;
- 8.5: токен есть и его значение отлично от того, что подставной `gh`
  отдаёт на `auth token`, — ok; значения равны — warn со ссылкой на
  `docs/triggers.md` №24; токена нет — fail; значения токенов в выводе
  нет;
- 8.6: все пути `no_paths` есть в дереве клона — ok; путь отсутствует —
  исход не ok, путь назван.

AC-10. По записи артели `doctor` выводит для проверок п.8 решение
«неприменимо».

AC-11. В argv шага роли Claude задачи внешнего проекта нет
`Bash(python3:*)`, есть `Bash(python3 <корень пульта>/orchestrator/artel.py:*)`
с абсолютным корнем пульта. Путь `<корень пульта>/orchestrator/artel.py`
в правиле посимвольно равен строке `config.ROOT / "orchestrator" /
"artel.py"`, которую печатают миссии шага (`orchestrator/role_prompt.py:238`,
`orchestrator/knowledge_cards.py:953`). Окружение этого шага содержит
`GIT_CONFIG_NOSYSTEM=1`. У задачи артели argv и окружение шага этих
изменений не несут (см. AC-1).

AC-12. В окружении с маркером `ARTEL_ROLE` (О-6):
- `doctor` по учебному внешнему проекту выводит для проверок 8.1, 8.2 и
  8.5 пропуск «только в сессии Оператора» и не делает fetch и пробный
  push;
- подменённая функция чтения слота связки ключей не вызывается ни
  `doctor`, ни хостинговой операцией пульта для этого проекта.

AC-13. Досылка коммита закрытия `doctor` (`_push_closing_sha`,
`orchestrator/doctor/artifact_branches.py:126-138`) для учебного внешнего
проекта, источник `source` — репозиторий вне `.artel/projects/<проект>/`
(как главная копия пульта), push по URL `origin` клона проекта (второй
настоящий git-репозиторий), в песочнице — конкурирующие помощники AC-3:
push проходит, в окружении этого git-вызова `git credential fill` по URL
проекта возвращает только токен слота `token_slot` проекта. Пустой слот —
отказ с именем слота. Значения токена нет в argv вызова и в выводе
`doctor`.

## Оценка объёма и деление

Сработавшие сигналы:
- число затрагиваемых модулей/файлов: 11 зон вне общих (две из них —
  `orchestrator/providers/base.py` и `orchestrator/providers/codex.py` —
  только сигнатура `command`, О-4);
- прогноз диффа дан ниже, порога не превышает;
- число критериев приёмки — 13.

Калибровка `BUDGET_CALIBRATION_TABLE` для 8 и более файлов зоны даёт ~$85,
рамка ТЗ $45. Если не делить, задача почти наверняка упрётся в потолок.

Прогноз диффа: 70 КиБ

**Нарезка на 2 подзадачи** по границам зон. Предложение не меняется с
батча вопросов, и ANSWER-1 его не оспорил.

1. **Проектные скилы и меры для роли** (требования 5–7, 10–11): зоны
   `orchestrator/brief.py`, `orchestrator/runner.py`,
   `orchestrator/providers/claude.py`, `orchestrator/providers/base.py`,
   `orchestrator/providers/codex.py` (последние две — только сигнатура
   `command`), `tests/`. Хостинг эта часть не
   трогает и самостоятельно мержима:
   - для артели всё остаётся как было;
   - для внешнего проекта бриф получает скилы, а роль — суженный список
     и `GIT_CONFIG_NOSYSTEM=1`.
   Идёт первой, потому что проверка допустимости имени скила
   (требование 6) нужна и `doctor` части 2.
2. **Токен хостинга и проверки `doctor`** (требования 1–4, 8–9, 13, 14,
   проверка `doctor` по `project_skills` из требования 6): зоны `orchestrator/gitcmd.py`,
   `orchestrator/ci.py`, `orchestrator/github_adapter.py`,
   `orchestrator/repo_context.py`, `orchestrator/projects.py`,
   `orchestrator/doctor/`, `tests/` (+ общая `orchestrator/config.py` под
   порог 24 ч). Проверки `doctor` 8.2 и 8.5 стоят на токене п.1, поэтому
   токен и `doctor` в одной части. Для артели эта часть ничего не

### D2-2: токен хостинга внешнего проекта и проверки doctor

Зоны: orchestrator/gitcmd.py, orchestrator/ci.py, orchestrator/github_adapter.py, orchestrator/repo_context.py, orchestrator/projects.py, orchestrator/doctor/, tests/
Порядок: после части 1

Часть 2 задачи 01M53B45XW3J56RJHGD70TD8A2 (D2). Требования и критерии —
SPEC родителя: требования 1–4, 8, 9, 13, 14, проверка `doctor` из
требования 6, требование 12; критерии AC-1 (`gh` и git пульта у артели),
AC-2…AC-5, пункт `doctor` из AC-7, AC-8…AC-10, AC-12, AC-13.

1. Для внешнего проекта операции пульта с хостингом берут токен из слота
   связки ключей `token_slot` записи проекта. Операции хостинга: `gh` и
   git с `origin` клона (fetch, push веток задачи, `refs/artifacts/*`,
   мерж).
   - `gh` получает токен как `GH_TOKEN` в окружении вызова. Прямой `gh`
     в `orchestrator/doctor/misc_checks.py:92` (`check_base_branch`)
     переводится на тот же токен проекта.
   - git получает помощник учётных данных из окружения вызова, без
     записи в конфигурацию клона и без системного `osxkeychain`.
     `gitcmd.git` определяет проект по пути `-C` внутри
     `.artel/projects/<проект>/` и подставляет токен слота; сигнатура
     `gitcmd.git` не меняется.
   - Наблюдаемо: в песочнице теста стоят конкурирующие помощники —
     глобальный и с областью URL проекта, отдающие чужой пароль; в
     окружении хостингового git-вызова `git config --get-all
     credential.helper` даёт только помощник пульта (чужие сброшены),
     `git credential fill` по URL проекта возвращает только токен слота.
   - Push досылки коммита закрытия `doctor`
     (`orchestrator/doctor/artifact_branches.py:126-138`) по URL `origin`
     клона внешнего проекта идёт с токеном проекта тем же механизмом, в
     том числе когда источник — главная копия пульта вне
     `.artel/projects/<проект>/`.
   Пустой слот — именованный отказ с именем слота. Токен не попадает в
   журналы, вывод команд и окружение роли — в том числе при отказанной
   хостинговой операции; в argv любых вызовов токена нет. Для артели
   ничего не меняется.
2. `doctor` для каждой записи внешнего проекта выводит проверки
   ok/warn/fail:
   1. Клон `.artel/projects/<имя>/repo` (`repo_context.clone_path`): его
      нет — fail (в тесте каталог проекта при этом существует);
      `origin` ≠ `url` — fail. Время изменения `FETCH_HEAD` клона, взятое
      до fetch самой проверки, старше 24 ч — warn «клон не обновлялся
      N ч». Порог — константа `orchestrator/config.py`. `FETCH_HEAD` нет
      (свежий клон `target-init`) — warn «клон ещё не обновлялся
      пультом», не fail. Затем fetch без изменения рабочих копий;
      неуспех — fail.
   2. Пробный `git push --dry-run` в `refs/artifacts/*` с токеном п.1:
      отказ — fail.
   3. CI на `pull_request` — разбор `.github/workflows/*.yml` в клоне,
      без сети. Триггера нет — warn «verifying будет ждать до потолка».
   4. Защита базовой ветки — информационно,
      `gh api repos/<владелец>/<репозиторий>/branches/<base>/protection`
      с токеном проекта; данные недоступны — сведение «недоступно»,
      исход не fail.
   5. Токена в слоте нет — fail. Значение токена слота проекта равно
      токену, которым `gh` Оператора ходит в хостинг (`gh auth token`), —
      warn «одобрение своим же токеном технически возможно —
      `docs/triggers.md` №24», не блокирует. Значения не печатаются.
   6. Пути `no_paths` существуют в дереве клона.
   7. `project_skills` записи — проверкой части 1.
   Для артели — явное «неприменимо», не пропуск.
3. В процессе роли (маркер `ARTEL_ROLE`) токен хостинга не читается ни
