# SPEC: Команда Оператора pull-main — подтяжка main в ветку задачи на verifying без возврата к роли

## Контекст
Задача, стоящая в `verifying`, у которой ветка отстала от main (CI новой
головы нужен со свежим main), сегодня подтягивается только через `reject`
в `in_dev` и шаг developer — лишний шаг роли «код не менять, возврат только
ради подтяжки main» (повтор 11.10, 01M4M67SGN). Нужна команда Оператора,
которая подтягивает main в ветку задачи прямо на `verifying` тем же узлом
подтяжки, что и переходы автомата (`fsm._pull_main_or_escalate` →
`orchestrator/pull.py::evaluate`), отправляет новую голову в origin и
оставляет задачу ждать CI этой головы. Команда не двигает состояние и не
проходит гейт: после неё нужен новый зелёный CI новой головы.

## Требования

1. Новая команда Оператора `pull-main <id>` (id — полный или префикс).
   Реализация — новый модуль `orchestrator/pull_main.py` по образцу
   `orchestrator/ci_rerun.py`; команда подключена в таблице команд и в
   справке `orchestrator/artel.py`.
2. Команда исполняется только для задачи в состоянии `verifying`. В любом
   другом состоянии (включая `escalated` после потолка `verifying`) —
   именованный отказ: подтяжки нет, push нет, `updated_at` не меняется,
   состояние не меняется.
3. Команда исполняется под lease задачи (`lease.run_locked`). Занятый
   живой lease другой сессии — именованный отказ: подтяжки нет, push нет,
   `updated_at` не меняется, состояние не меняется.
4. Подтяжка main выполняется тем же узлом `fsm._pull_main_or_escalate` с
   `run_plank=True` (как подтяжка на переходе `in_dev -> verifying` в
   `fsm_advance.in_dev`): после слияния гоняется планка, красная планка —
   эскалация тем же путём, что на переходе.
5. Подтяжка командой не пропускается по признаку «документный дифф main»
   (`pull._doc_only_main_advance` / `scripts/ci_push_class.py::is_doc_path`):
   если main после базы ветки несёт только документные файлы, команда всё
   равно подтягивает main в ветку. Автоматическая подтяжка перед шагом роли
   и на переходах автомата (с пропуском по документному диффу) не меняется.
6. Исход «подтянуто»: команда отправляет новую голову ветки в origin
   существующим `github_adapter.ensure_head_in_origin` (у канарейки —
   `is_canary` — не отправляет, как `fsm_advance`), пишет событие подтяжки
   в журнал задачи и оставляет задачу в `verifying`.
7. Исход «подтянуто» перезапускает отсчёт потолка `verifying`: команда
   пишет `store.update_task(conn, id, updated_at=store.now())`. Сам лимит
   `config.VERIFYING_CEILING_SEC` не меняется, `orchestrator/store.py` не
   меняется.
8. Исход «main уже в ветке» — именованный ответ: без события подтяжки в
   журнале, без push, без смены `updated_at`, состояние `verifying`.
9. Конфликт слияния, красная планка после слияния и несозданная рабочая
   копия эскалируют задачу теми же путями, что подтяжка на переходах
   (`pull.evaluate`); в этих исходах команда не делает push и не меняет
   `updated_at`. Иных смен состояния команда не производит.
10. Свойства требований 2, 3, 5, 6, 7 держат тесты в `tests/` с заявками
    «Ловит мутацию» (ТЗ п.6): мутация «команда меняет состояние задачи при
    успехе»; «подтяжка пропущена по документному диффу»; «потолок не сброшен
    после подтяжки»; «команда работает вне verifying»; «команда работает при
    занятом lease»; «голова не отправлена в origin после подтяжки». Тест,
    который это свойство уже держит приёмочной планкой автора тестов
    (`tests/test_01M4PMR5EVFK4KQDPWB1KEGM7V_*.py`, ADR-0020), повторно не
    пишется.

## Критерии приёмки

AC-1. `python3 orchestrator/artel.py pull-main <id>` распознаётся как команда (есть в таблице команд и в справке `orchestrator/artel.py`), принимает полный id и префикс id; реализация живёт в модуле `orchestrator/pull_main.py`.

AC-2. Для задачи в состоянии, отличном от `verifying` (в том числе `escalated` после потолка `verifying`), команда выдаёт именованный отказ; состояние задачи, `updated_at` и голова ветки не меняются, `fsm._pull_main_or_escalate` не вызывается, push в origin нет.

AC-3. Для задачи в `verifying` с живым lease другой сессии команда выдаёт именованный отказ; состояние задачи, `updated_at` и голова ветки не меняются, `fsm._pull_main_or_escalate` не вызывается, push в origin нет.

AC-4. Для задачи в `verifying`, у которой main ушёл вперёд без конфликта с веткой, команда вызывает `fsm._pull_main_or_escalate` с `run_plank=True`; при зелёной планке main оказывается в ветке задачи (вершина main — предок новой головы ветки).

AC-5. Если все файлы main после базы ветки документные (`scripts/ci_push_class.py::is_doc_path`), команда всё равно подтягивает main в ветку (исход «подтянуто», вершина main — предок новой головы); автоматическая подтяжка на переходах автомата в той же ситуации по-прежнему пропускает подтяжку.

AC-6. При исходе «подтянуто» у не-канареечной задачи новая голова ветки отправлена в origin через `github_adapter.ensure_head_in_origin`; у канареечной задачи (`is_canary`) отправки нет.

AC-7. При исходе «подтянуто» задача остаётся в `verifying`, в журнале задачи есть событие подтяжки, `updated_at` задачи сдвинут на момент команды (отсчёт потолка `verifying` начинается заново); `config.VERIFYING_CEILING_SEC` не меняется.

AC-8. Если main уже в ветке задачи, команда выдаёт именованный ответ; события подтяжки в журнале нет, push нет, `updated_at` не меняется, задача в `verifying`.

AC-9. Конфликт слияния, красная планка после слияния и несозданная рабочая копия переводят задачу в `escalated` тем же путём, что у подтяжки на переходах; push нет, `updated_at` командой не сдвигается.

AC-10. В `tests/` есть тесты с заявками «Ловит мутацию», каждый из которых краснеет на своей мутации: команда меняет состояние задачи при успехе; подтяжка пропущена по документному диффу; потолок не сброшен после подтяжки; команда работает вне `verifying`; команда работает при занятом lease; голова не отправлена в origin после подтяжки.

## Оценка объёма и деление

Прогноз диффа: 60 КиБ (новый модуль `orchestrator/pull_main.py`, параметр
отключения пропуска по документному диффу в `pull.py`/`fsm.py`, строка
таблицы команд и справки в `artel.py`, тесты, регенерация карты) — ниже
половины потолка гейта ёмкости (`REVIEW_SNAPSHOT_DIFF_MAX_BYTES` 256 КиБ).

Сработавшие сигналы: число файлов зоны (6 с общими зонами `tests/` и
`docs/codebase-map.md`; без общих — 4); число критериев приёмки — 10 (ровно
на пороге `SPLIT_SIGNAL_AC_COUNT`).

Предлагается монолит. Что нельзя разрезать: команда (`pull_main.py` +
`artel.py`) и отключение пропуска по документному диффу (`pull.py`/`fsm.py`)
— одно поведение одной команды; требование 5 существует только как
свойство команды, без неё изменение узла подтяжки ничем не вызывается и
непроверяемо, а команда без него нарушает требование 5 (подтяжка
пропускалась бы ровно в случае, ради которого Оператор её зовёт). Тесты
(AC-10) проверяют ту же команду и не мержимы отдельно от неё. Критерии
1–10 — грани одной команды (вход, отказы, исходы), отдельно мержимой
части с собственной ценностью среди них нет. Решение — за Оператором на
гейте SPEC.
