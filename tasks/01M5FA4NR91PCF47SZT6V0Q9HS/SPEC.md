# SPEC: Механика канарейки, часть Б-2: реестр живой канарейки

## Контекст
Часть А (коммит 25bd2f22) ввела реестр живого прогона канарейки: запись
`<run_stamp>-<pid>.json` и метку `<run_stamp>.lock` (`orchestrator/canary.py:2823`,
`_live_run_record`), сверку живости (`_live_verdict`, `:2862`), уборку
(`_drop_live_record`, `:2895`), чтение (`live_runs`, `:2911`, видит только
записи) и причину (`live_run_note`, `:2941`); потребители — окно тишины
(`orchestrator/notes.py:266`), отказ мержа (`orchestrator/fsm_merge_gate.py:1255`)
и обходы окна (`refuse_main_move_during_canary`, `orchestrator/canary.py:2959`).
Сегодня метка без записи реестром не видна: удаление записи при оставленной
метке молча снимает окно тишины и отказ мержа. Запись живого, но зависшего
процесса снимается только удалением файла руками и держится до потолка (при
`--k 5` — 41 ч); показа реестра ни командой, ни в `doctor` нет. Тест
`CmdCanaryTemplateSelectionTest` (`tests/test_canary_template_flag.py:186`) и
тесты тела окна мержа читают/пишут настоящий реестр пульта (строки бэклога
`docs/backlog.md:286`, `:287`; перенос 2 гейта SPEC части А). Решения Оператора
21.10: метка без записи при живом pid — прогон живой; предупреждение `doctor` —
для записи старше `CANARY_DRIVE_TIMEOUT_SEC` (8 ч); `--drop` — строгий
вариант (снимает только зависшее, живой прогон — отказ).

Граница задачи: новое поведение — только у метки без записи, у подкоманды
`canary live` и у проверки `doctor` реестра (одна новая строка `canary-live`),
плюс изоляция тестов; прогон канарейки, запись реестра, `live_runs` и
потребители реестра при наличии записи — прежние побайтно.

## Требования

1. **Метка без записи.** `live_runs()` не меняется: читает только записи.
   Метки без записи читает новая функция. `live_run_note` сверяет сначала
   записи (с их прежней уборкой), затем метки, у которых не осталось ни одной
   записи того же `run_stamp`. Метка, рядом с которой есть запись того же
   `run_stamp` (живая или убираемая прежним `_drop_live_record`), новой логикой
   не трогается. Для метки без записи:
   - pid в метке жив — прогон живой, причина «идёт канарейка <run_stamp>
     (запись реестра отсутствует)»; окно тишины, отказ мержа (прогон считается
     прогоном набора по умолчанию — набор неизвестен, безопасная сторона) и
     отказ обходов окна держатся;
   - метка пустая или не читается и моложе 60 с по времени правки — прогон
     живой; старше 60 с — метка убирается строкой журнала пульта
     `LIVE_RUN_SWEPT_ACTION`;
   - pid мёртв — метка убирается той же строкой журнала.
   Отказ повтора `run_stamp` при оставшейся метке — прежний.
2. **Команда `canary live`.** Без аргументов печатает реестр: по записи —
   `run_stamp`, pid, `parent_pid` и шаблон (если есть в записи), sha7, набор,
   время начала, возраст, остаток до потолка; по метке без записи —
   `run_stamp`, pid и возраст по времени правки; пусто — «живых прогонов
   канарейки нет». Мёртвые записи и метки убираются прежним путём чтения
   реестра (требование 1).
3. **Снятие записи.** `canary live --drop <run_stamp> "<основание>"` снимает
   только: (а) запись старше `CANARY_DRIVE_TIMEOUT_SEC`; (б) запись, у которой
   время старта процесса не определилось при записи или при сверке; (в) метку
   без записи. Снимаются все такие записи этого `run_stamp` и его метка;
   процессы не сигналятся. Иначе — отказ «canary live: прогон <run_stamp> жив
   (pid <pid>, возраст <ч>) — снимать нечего; дождись итога или используй
   --during-canary у конкретной команды». Строку журнала пульта без задачи
   пишет `operator` новой константой действия; деталь — имена удалённых файлов
   и основание. Если процесс прогона жив, вывод команды и деталь журнала несут
   «процесс <pid> жив — прогон продолжается без защиты окна». `<run_stamp>` —
   по шаблону `^\d{8}T\d{6}Z$`, иначе отказ до чтения каталога реестра.
   Отказы: `--drop` без `run_stamp`; пустое основание (по образцу
   `_fixes_main_arg`, `orchestrator/artel.py:1762`); лишние аргументы
   `canary live`; записей и метки с таким `run_stamp` нет — «canary live:
   прогона <run_stamp> в реестре нет». Под ролью обе формы `canary live`
   отказывают прежним механизмом `_role_allowed_command`
   (`orchestrator/artel.py:2017`) — разрешённой подкоманда не становится.
   Справка команды (`orchestrator/artel.py:181`) называет подкоманду.
4. **Реестр в `doctor`.** Проверка `canary-live`: живых прогонов нет — `ok`
   «живых прогонов канарейки нет»; есть — `ok` со списком «<run_stamp> на
   <sha7>, pid <pid>, возраст <ч>»; запись старше `CANARY_DRIVE_TIMEOUT_SEC`
   или метка без записи старше `CANARY_DRIVE_TIMEOUT_SEC` по времени правки —
   `warn` с подсказкой `canary live --drop <run_stamp> "<основание>"`. Метка без
   записи — в списке с пометкой «запись реестра отсутствует» и возрастом.
   Уборка мёртвых записей и меток — прежним путём чтения реестра, допустима и в
   `doctor` без `--fix`. Новая проверка реэкспортируется в
   `orchestrator/doctor/__init__.py` и собирается рядом с проверками канарейки
   (`orchestrator/doctor/cli.py:153`).
5. **Изоляция тестов реестра.** Классы тестов, вызов которых доходит до
   `_refuse_during_canary` при `is_artel(ctx)` и корне пульта в config (атрибут
   `ROOT`), равном настоящему корню пульта, а также
   `CmdCanaryTemplateSelectionTest`, не читают и не пишут настоящий реестр:
   песочница `ALL_CONFIG_ATTRS` (`tests/sandbox.py:90`) или подмена пути
   реестра. Для `CmdCanaryTemplateSelectionTest` — подмена `canary._live_dir`
   на временный каталог в `setUp`. Перечень таких классов разработчик приводит
   в отчёте. Класс в защищённом пути (`tests/test_invariants.py`) — эскалация,
   не правка. Это добавление изоляции: существующие утверждения не меняются и
   не удаляются.
6. Тесты задачи детерминированы, без сети, без настоящих ролей и без ожидания
   по часам; время правки метки задаётся `os.utime`.
7. Без метки без записи — прежнее поведение `note`, `doc-commit`, `approve` и
   вывод `canary`; существующие тесты (в том числе
   `tests/test_canary_live_registry_units.py`) — без правок утверждений.

## Критерии приёмки

AC-1. Метка без записи с живым pid: `note` удержан окном тишины, `approve` на
`merge_gate` отказывает, `note --now` отказывает; причина содержит «идёт
канарейка <run_stamp> (запись реестра отсутствует)».

AC-2. Пустая метка без записи моложе 60 с по времени правки (`os.utime`) —
прогон живой; такая же метка старше 60 с — убрана, в журнале пульта строка
`LIVE_RUN_SWEPT_ACTION`.

AC-3. Метка без записи с мёртвым pid — убрана, в журнале пульта строка
`LIVE_RUN_SWEPT_ACTION`.

AC-4. Метка рядом с записью того же `run_stamp` новой логикой не тронута;
`live_runs()` по-прежнему отдаёт только записи (метку без записи не
возвращает).

AC-5. `canary live` без аргументов: показ записи (`run_stamp`, pid,
`parent_pid` и шаблон при наличии в записи, sha7, набор, время начала,
возраст, остаток до потолка), показ метки без записи (`run_stamp`, pid,
возраст по времени правки) и пустого реестра — «живых прогонов канарейки нет».

AC-6. `canary live --drop <run_stamp> "<основание>"` снимает каждый из случаев:
(а) запись старше `CANARY_DRIVE_TIMEOUT_SEC`, (б) запись с неопределённым
временем старта процесса, (в) метку без записи; снимаются все такие записи
этого `run_stamp` и его метка; процесс прогона не получил сигнала.

AC-7. Успешный `--drop` пишет строку журнала пульта без задачи от `operator`
новой константой действия; деталь — имена удалённых файлов и основание. При
живом процессе прогона вывод команды и деталь журнала содержат «процесс <pid>
жив — прогон продолжается без защиты окна».

AC-8. `--drop` для живой свежей записи с определённым временем старта —
отказ «canary live: прогон <run_stamp> жив (pid <pid>, возраст <ч>) — снимать
нечего; дождись итога или используй --during-canary у конкретной команды»;
запись остаётся.

AC-9. `--drop` с `run_stamp` не по шаблону `^\d{8}T\d{6}Z$` — отказ, каталог
реестра не читался.

AC-10. Отказы `canary live`: `--drop` без `run_stamp`; пустое основание;
лишние аргументы; `run_stamp`, которого нет в реестре, — «canary live:
прогона <run_stamp> в реестре нет».

AC-11. Под ролью обе формы `canary live` (показ и `--drop`) отказывают
механизмом `_role_allowed_command`; справка команды называет подкоманду
`canary live`.

AC-12. `doctor`, проверка `canary-live`: `ok` «живых прогонов канарейки нет» на
пустом реестре; `ok` со списком «<run_stamp> на <sha7>, pid <pid>, возраст <ч>»
для живой записи (метка без записи — с пометкой «запись реестра отсутствует»
и возрастом).

AC-13. `doctor`, проверка `canary-live`: `warn` с подсказкой `canary live --drop
<run_stamp> "<основание>"` для записи старше `CANARY_DRIVE_TIMEOUT_SEC` и для
метки без записи старше `CANARY_DRIVE_TIMEOUT_SEC` по времени правки.

AC-14. Тест-шпион: при обращении каждого класса из перечня требования 5 (в том
числе `CmdCanaryTemplateSelectionTest`) путь `_live_dir()` не лежит под корнем,
снятым до подмен (`Path(orchestrator.__file__).resolve().parents[1]`).

AC-15. Без метки без записи поведение `note`, `doc-commit`, `approve` и вывод
`canary` прежние.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (шесть: `orchestrator/canary.py`,
`orchestrator/artel.py`, `orchestrator/doctor/canary_pool.py`,
`orchestrator/doctor/cli.py`, `orchestrator/doctor/__init__.py`, `tests/`);
критериев приёмки ≥ 10 (15).

Решение — обоснование монолита (материал для Оператора). Задача уже является
частью деления, утверждённого Оператором 21.10 (часть Б → Б-2 и Б-1), с
рамкой бюджета $22–27. Внутри неё всё опирается на одну механику —
чтение меток без записи (требование 1): `canary live` показывает их, случай
(в) `--drop` снимает их, `doctor` предупреждает о них. Отрезать показ/снятие и
`doctor` от требования 1 можно только ценой второй версии тех же функций
показа (без меток) и повторного прохода по тем же файлам `canary.py`/`artel.py`/
`doctor/`; часть только с требованием 1 закрывает молчаливое снятие окна, но
оставляет зависшую метку без способа её снять, кроме удаления файла руками
(до потолка). Изоляция тестов (требование 5) мала и делит зону `tests/`
с тестами остальных требований. Порог `budget_usd` ≥ $30 не задет.

Решение по монолиту утверждает Оператор на гейте SPEC.
