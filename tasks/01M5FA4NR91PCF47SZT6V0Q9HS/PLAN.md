# PLAN: Механика канарейки, часть Б-2: реестр живой канарейки

## Подход

Одна механика — метка `<run_stamp>.lock` без записи — и три её
потребителя: окно (через `live_run_note`), команда `canary live`, строка
`doctor`. `live_runs()` не меняется.

- `orchestrator/canary.py`:
  - `live_marks()` — новая функция: метки, у которых после уборки записей
    на диске не осталось ни одной записи того же `run_stamp`. Состояние
    метки (`_mark_state`): pid жив — живая; пустая/нечисловая/pid ≤ 0 —
    живая моложе 60 с по `mtime`, иначе мёртвая; pid мёртв — мёртвая.
    Мёртвая убирается строкой `LIVE_RUN_SWEPT_ACTION` от `orchestrator`
    без задачи.
  - `live_run_note()` — сначала `live_runs()` (прежняя уборка), затем
    `live_marks()`; записи дают прежнюю причину и имеют приоритет, метка —
    «идёт канарейка <run_stamp> (запись реестра отсутствует)», и её набор
    не фильтруется `default_set_only` (набор неизвестен — безопасная
    сторона мержа). Подписи `live_run_note` и
    `refuse_main_move_during_canary` прежние.
  - `_drop_live_record` — логика «метка уходит с мёртвой записью» вынесена
    в `_mark_follows_record` (то же условие байт-в-байт), чтобы её же
    использовал read-only вид реестра.
  - `registry_view()` — реестр без уборки для `doctor`: записи с вердиктом
    `_live_verdict` и метки без живой записи; метка, которую уборка унесла
    бы с мёртвой записью, помечена мёртвой.
  - `cmd_canary_live(drop, reason)` — показ (запись: `run_stamp`, pid,
    `parent_pid`/шаблон при наличии, sha7, набор, начало, возраст, остаток
    до потолка `CANARY_DRIVE_TIMEOUT_SEC × tasks + 1 ч`; метка: `run_stamp`,
    pid, возраст по `mtime`; пусто — «живых прогонов канарейки нет») и
    `--drop`: после прежней уборки снимает записи `run_stamp` старше
    `CANARY_DRIVE_TIMEOUT_SEC` или без времени старта процесса (при записи
    или при сверке), метку — только если записей `run_stamp` не осталось;
    строка журнала `operator` новой константой `LIVE_RUN_DROPPED_ACTION`
    с именами файлов, основанием и «процесс <pid> жив — прогон
    продолжается без защиты окна»; снимать нечего — отказ текстом SPEC;
    ничего нет — «canary live: в реестре нет <run_stamp>», код 0. Сигналов
    нет.
- `orchestrator/artel.py`: `_cmd_canary_live` разбирает аргументы до чтения
  реестра — `run_stamp` полным совпадением `[0-9]{8}T[0-9]{6}Z`
  (`canary.RUN_STAMP_RE.fullmatch`, без «$ перед \n»), пустое основание,
  лишние аргументы; строка справки. Отказ под ролью — прежний
  `_role_allowed_command` (подкоманда не добавлена в белый список).
- `orchestrator/doctor/canary_pool.py`: `check_canary_live()` (строка
  `canary-live`, только чтение `registry_view`) и `_fix_canary_live()`
  (`live_runs()` + `live_marks()`); реэкспорт в `doctor/__init__.py`;
  строка — после `canary-trigger` в `all_checks`, починка — в ветке `--fix`
  `cmd_doctor` до `all_checks`.
- Изоляция (требование 5): подмена `canary._live_dir` на временный каталог
  в `setUp` у `CmdCanaryTemplateSelectionTest` (в существующем кортеже
  подмен) и новый `setUp` у `DoctorFixOrderTest`; утверждения не тронуты.

Бюджет SPEC ($27) не переоценивается: число файлов и шагов совпало с
оценкой SPEC.

## Влияние на систему

- Окно тишины, отказ мержа, обходы окна: при наличии записи поведение
  прежнее (записи читаются первыми, `live_runs` побайтно прежний, условие
  снятия метки вместе с мёртвой записью вынесено без изменения). Новое —
  только у метки без записи: она теперь держит окно (раньше молча
  снимала его). Это ужесточение, не ослабление.
- `doctor`: одна новая строка `canary-live` (`ok`/`warn`, никогда не
  `fail` — код выхода `doctor` не меняется); `--fix` получает ещё одну
  уборку, пишущую прежнюю строку журнала.
- `--drop` — новый путь снятия записи, но в строгом варианте: свежую
  запись живого процесса с определённым временем старта он не снимает,
  каждое снятие — строка журнала `operator` с основанием.
- Под ролью `canary live` отказывает прежним белым списком.
- Тесты: утверждения не менялись, добавлена только подмена каталога
  реестра в `setUp` двух классов.
- Откат — revert одного merge-коммита: состояние на диске (метки,
  записи) формата не меняет.

## Риски

- Нечитаемая метка моложе 60 с держит окно до 60 с — намеренно (SPEC).
- `canary live --drop` при живом зависшем процессе снимает защиту окна —
  предупреждение в выводе и журнале, сигнал процессу не шлётся (SPEC).
