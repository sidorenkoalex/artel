# SPEC: Механика канарейки, часть Б-1а: подкоманда canary run-task и запись дочернего в реестр

## Контекст
Цель части Б-1 — короче окно канарейки: задачи прогона идут одновременно
отдельными процессами. Решением Оператора 21.10 Б-1 делится на две задачи;
эта (Б-1а) — первая: внутренняя подкоманда `canary run-task`, которая ведёт
одну задачу прогона в отдельном процессе, и запись такого дочернего процесса
в реестр живого прогона (части А и Б-2 уже смержены: 25bd2f22, 26469784).
Отдельный процесс нужен потому, что `_ephemeral_clone`
(`orchestrator/canary.py:1092`) переадресует модульные пути `config`
процесса (`_CLONE_CONFIG_ATTRS`, `orchestrator/canary.py:463`) и два клона в
одном процессе невозможны. Родителя с `--parallel` здесь ещё нет (задача
Б-1б): подкоманду никто из пульта не вызывает, тесты запускают её напрямую.

**Граница задачи:** новое поведение — только при вызове подкоманды
`canary run-task`; без её вызова поведение пульта прежнее побайтно —
прогон канарейки, вывод, строки `canary_runs`, базовые строки, файл
результата и реестр.

Ссылки `файл:строка` сверены ТЗ с коммитом 26469784.

## Требования

1. **Подкоманда `canary run-task`: разбор и отказы.** Внутренняя подкоманда
   `canary run-task --stamp <run_stamp> --template <путь шаблона> --sha
   <проверяемый sha> --set <имя набора> --summary <сводка моделей набора>`
   (сводка — поле `summary` плана набора у будущего родителя, возможно пустая
   строка) разбирается в `_cmd_canary` (`orchestrator/artel.py:1540`) до
   `--detach` и `--k`, как `live`.
   - Подкоманда в справку `artel.py` (`orchestrator/artel.py:181`) не входит.
   - Под ролью отказывает прежним механизмом `_role_allowed_command`
     (`orchestrator/artel.py:2047`) с текстом «artel.py canary run-task:
     команда недоступна процессу роли …» и разрешённой не становится.
   - Без любого из пяти аргументов — отказ с ненулевым кодом до записи
     реестра. `--stamp` сверяется с `RUN_STAMP_RE`; повтор любого из пяти
     флагов, флаг без значения и лишние аргументы (в том числе `--detach`,
     `--result-file`, `--k`) — отказ с ненулевым кодом до записи реестра.
   - Подкоманда не обращается к origin, не выбирает шаблоны, не создаёт и не
     снимает метку `<run_stamp>.lock`; приёмника `on_run_stamp` у неё нет.
   - Набор, у которого хоть одна роль на провайдере Codex (непустое поле
     `codex_roles` плана), — отказ до записи реестра и до клона текстом
     «canary run-task: набор <имя> с ролями на провайдере codex не ведётся
     отдельным процессом — профиль Codex канарейки один на машину».

2. **Порядок подкоманды.** Всё тело — внутри `_interrupt_on_signal`
   (`orchestrator/canary.py:3217`), поставленного до записи реестра:
   - (0) до записи реестра строит план набора `--set` прежним `_set_plan`
     (`orchestrator/canary.py:623`); его именованные отказы и отказ п. 1 для
     набора с ролями Codex — до записи реестра и до клона;
   - (а) пишет свою запись реестра (п. 3);
   - (б) сверяет, что метка `<run_stamp>.lock` реестра существует и несёт pid,
     равный `os.getppid()`; иначе снимает свою запись и выходит с ненулевым
     кодом без клона и без строки `canary_runs`, текст «canary run-task: метка
     прогона <run_stamp> не принадлежит родителю <ppid>»;
   - (в) сверяет поле `summary` плана из (0) с переданным `--summary`;
     расхождение — красная строка `canary_runs` своего шаблона по образцу
     `_report_drive_failure` (исход `_DRIVE_FAILED_OUTCOME`, `main_sha` пуст,
     `set_name` — имя набора, `models_summary` — переданная сводка; пустая
     `--summary` — `models_summary` None, как `plan.summary or None`;
     `task_id` и поле ожидания эскалации пусты) с причиной в выводе «набор
     изменился во время прогона», без клона, ненулевой код выхода;
   - (г) ведёт ровно одну задачу прежним `_run_one_task`
     (`orchestrator/canary.py:2610`) с `run_stamp` из `--stamp`, `target_sha`
     из `--sha`, `sha_label=None` (отдельного аргумента для пометки нет),
     `ratio` = `config.CANARY_DEVIATION_RATIO`, `codex_auth` = None и без
     входа Codex: свой эфемерный клон, своя origin-заглушка, своя БД клона,
     маркер владельца временных каталогов — pid процесса подкоманды. Свою
     строку `canary_runs` и сверку с базовой строкой своей пары пишет сам
     процесс подкоманды теми же функциями.
   - Возврат из `_run_one_task` без исключения — код 0, в том числе после
     красной строки `_report_drive_failure`; исключение — ненулевой код без
     строки.
   - SIGTERM и SIGHUP процессу подкоманды во время задачи — строка «оборвана
     сигналом <имя>» его шаблона с полями той же строки `cmd_canary`
     (`task_id` пуст, `main_sha` — `--sha`, `set_name`, `models_summary` —
     `plan.summary or None`, вердикт red) и код 128 + номер сигнала; клон и
     origin-заглушку убирает прежний `finally`.
   - Сигнал до начала (г) (запись реестра, сверка метки, план, сверка сводки)
     — код 128 + номер сигнала, строки `canary_runs` нет, запись и временный
     файл сняты.
   - Отказ `_set_plan` — ненулевой код, строки нет, записи нет.

3. **Запись дочернего в реестр.** Процесс подкоманды до сверки п. 2 (б) пишет
   запись `<run_stamp>-<свой pid>.json` в каталог реестра (`_live_dir`) с
   полями: `run_stamp` из `--stamp`, `sha` из `--sha`, `set_name` из `--set`;
   свои `pid`, `process_start` (тем же помощником, что в `_live_run_record`) и
   `started_at` (момент записи дочернего); `tasks` = 1; `parent_pid`
   (`os.getppid()`) и `template` (имя шаблона без `.md`).
   - Запись пишется приёмом `_live_run_record`: во временный файл
     `<имя>.json.tmp`, затем атомарная замена `os.replace`, внутри
     `_interrupt_on_signal`. Временный файл не попадает под маску `*.json` и
     убирается при исключении и сигналах SIGTERM и SIGHUP.
   - Метку подкоманда не создаёт (прежний `_live_run_record` не используется)
     и при снятии своей записи метку не трогает.
   - Запись и её временный файл снимаются в `finally` при любом исходе,
     включая отказы п. 2 (б) и (в), исключение и сигнал.
   - Код чтения и уборки реестра Б-2 (`live_runs`, `live_marks`,
     `registry_view`, `_drop_live_record`, `_mark_follows_record`,
     `cmd_canary_live`, `check_canary_live`) не меняется.

4. **Реестр держит прогон по записи дочернего.** `live_runs` и `live_run_note`
   считают прогон живым, пока жива хотя бы одна его запись, в том числе
   запись дочернего после гибели родителя от SIGKILL: метка родителя уходит
   вместе с его мёртвой записью прежним `_mark_follows_record`, запись
   дочернего держит прогон. Уборка мёртвой записи дочернего метку живого
   родителя не трогает.

5. **Замер не ломается.** Строка `canary_runs`, написанная подкомандой, по
   составу полей та же, что у задачи последовательного прогона (`run_stamp`,
   `set_name`, `models_summary`, `main_sha` — коммит, сообщённый клоном,
   `verdict`). Базовую строку пары читает и пишет только процесс подкоманды
   этой пары; строки и базовые строки других пар он не меняет.
   `canary_baseline`, `green_canary_runs`, `merges_since_last_green_run` и
   условие `pin-update` не меняются. Приёмника `run_stamp` у подкоманды нет.

6. **Неослабление защиты части А на файлах реестра.** Пока жива хотя бы одна
   запись параллельного прогона набора по умолчанию, `approve <id> [sha]` на
   `merge_gate` задачи артели отказывает текстом части А, `note` и
   `doc-commit` удерживаются, `note --now`, `note --flush`, `doc-commit
   --flush` и `canary pool-seal` без `--during-canary "<основание>"`
   отказывают; прогон набора не по умолчанию мерж не держит. `canary live`
   показывает строку каждой записи, у дочерних — с `parent_pid` и шаблоном;
   `canary live --drop <run_stamp>` при свежих живых записях дочерних
   отказывает «снимать нечего» и метку не снимает. После `canary live --drop
   <run_stamp>` метки при отсутствии записей следующий вызов подкоманды с
   этим `run_stamp` отказывает по п. 2 (б). Код потребителей реестра
   (`_silence_window_reason`, `_refuse_during_canary`,
   `refuse_main_move_during_canary`, `live_run_note`) не меняется.

7. **Без вызова подкоманды — прежний путь побайтно.** `cmd_canary`,
   `_run_one_task`, `_live_run_record`, `_report_drive_failure` и ветки
   `_cmd_canary` для `pool-seal`, `live`, `--detach` и `--k` не меняются;
   приём записи (временный файл и `os.replace`) и строка «оборвана сигналом»
   повторяются в новой функции подкоманды, а не выделяются из
   `_live_run_record` и `cmd_canary`. Подписи `_run_one_task` и `cmd_canary`
   прежние.

8. **Тесты.** Детерминированы, без сети, без настоящих ролей и без ожидания по
   часам. Подкоманда запускается напрямую: вызовом функции в главном потоке
   либо подменённым процессом интерпретатора с заданным исходом; ведение
   задачи (`_run_one_task` или клон) подменено. Ожидание — только событиями:
   канал или FIFO от подменённого процесса, `Popen.wait()` или `os.waitpid`
   без срока. Сигнал во время задачи шлёт подменённое ведение самому процессу
   (`os.kill(os.getpid(), …)`) или согласующий поток по событию;
   `_interrupt_on_signal` при этом стоит в главном потоке. Перед
   `os.kill(os.getpid(), …)` тест проверяет, что обработчик сигнала поставлен
   подкомандой (`signal.getsignal` не равен прежнему), иначе падает без
   отправки сигнала. Родитель строится файлами реестра и метки во временном
   каталоге; живые pid — сам процесс теста или процессы, созданные тестом и
   ждущие события; гибель родителя и состояния п. 6 строятся файлами
   реестра, а не настоящим SIGKILL. Тесты не читают и не пишут настоящий
   реестр и настоящий каталог журналов пульта (песочница `ALL_CONFIG_ATTRS`
   из `tests/sandbox.py` или подмена каталога реестра, как в Б-2). Нужда в
   новой записи `_EXCEPTIONS` в `tests/test_invariants.py` — эскалация.

AC-6. Три состояния реестра строятся файлами во временном каталоге — живы
родитель (запись и метка) и дочерние (записи с `parent_pid` и `template`);

Запись дочернего в этих состояниях — копия файла, снятая из каталога реестра
во время подменённой задачи подкоманды и восстановленная для каждого
состояния (запись, набранная тестом руками, критерием не считается). `canary
live` в состоянии «живы родитель и дочерние» показывает строку каждой записи,
у дочерних — с `parent_pid` и шаблоном; `canary live --drop <run_stamp>` при
свежих живых записях дочерних отказывает «снимать нечего» и метку не снимает;
после `canary live --drop <run_stamp>` метки при отсутствии записей следующий
вызов подкоманды с этим `run_stamp` даёт ненулевой код, клона нет, строки
`canary_runs` от подкоманды нет.

AC-7. В диффе задачи относительно main нет изменений тел `cmd_canary`,
`_run_one_task`, `_live_run_record`, `_report_drive_failure`, `live_runs`,
`live_marks`, `registry_view`, `_drop_live_record`, `_mark_follows_record`,
`cmd_canary_live`, `live_run_note`, `refuse_main_move_during_canary` и веток
`_cmd_canary` для `pool-seal`, `live`, `--detach` и `--k`, кроме вставки
разбора `run-task` в `_cmd_canary`.

AC-8. Новые тесты задачи не используют `time.sleep` с ненулевым сроком,
циклы до срока по часам и сеть; каждый тест, шлющий `os.kill(os.getpid(),

  процессов, очередь, предел одновременных процессов, остановка дочерних,
  журналы дочерних, общий итог прогона, красная строка родителя за дочерний
  без строки и отказ `--parallel` для наборов с ролями Codex — задача Б-1б.
- Перенос 1 из гейта SPEC части А (файл результата отказанного повтора) —
  задача Б-1б.
- Уборка `.json.tmp`, оставшегося после SIGKILL подкоманды, — как у записи
