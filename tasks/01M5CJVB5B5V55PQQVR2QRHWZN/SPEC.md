# SPEC: G3а-1а: гейт неослабления по исходам на выходе из `in_dev` — `PASS_TO_PASS`, нестабильность, сравнение отчётов

## Контекст
ADR-0026 («Решение», п. 6) вводит гейт неослабления по исходам тестов; эта
задача — первая часть G3а (решение Оператора 20.10: G3а-1а / G3а-1б / G3а-2).
Сегодня гейт неослабления на переходе `in_dev -> verifying`
(`orchestrator/fsm_advance.py:804`, `_test_integrity_gate_refuses`; тело —
`orchestrator/advance_gates/test_integrity.py:1722`) читает только
Python-текст тестов: тесты Vitest не проверяет ни один гейт неослабления, а
сломанный правкой или ставший нестабильным тест по исходам не ловится вовсе.
Новый гейт сравнивает исходы полного набора компонента на базе и на голове
ветки. Граница: гейт исполняется только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`) истинно
(компонент записи `components:` с полем `report`); у артели, у записи
`test_profile` и у записи из нескольких компонентов — прежнее поведение
побайтно.

## Требования

1. **Новый гейт исходов** — новый модуль
   `orchestrator/advance_gates/outcome_integrity.py`, вызов на переходе
   `in_dev -> verifying` сразу после гейта по тексту
   (`_test_integrity_gate_refuses`) и до гейта переделки ревью
   (`_review_rework_gate_refuses`). Профиль — `decide(target).profile`
   (`orchestrator/project_profile.py:184`). Если решение — отказ или пропуск
   либо `in_outcome_bounds` ложно, гейт не создаётся: ни прогона, ни записи
   журнала. Компонент — единственный компонент профиля.
2. **Прогоны.** Полный набор компонента на базе (`diff_base`,
   `orchestrator/gitcmd.py:533`) и на голове кодовой ветки в отдельных
   выписках, `components_full_suite(..., fresh=True)`
   (`orchestrator/acceptance.py:3425`). Исход стороны «неизвестно/не начат»
   (`FULL_SUITE_NOT_STARTED`) или таймаут — отказ подготовки с причиной и
   стороной, без сравнения. «Нет тестов» (`FULL_SUITE_NO_TESTS`) на базе —
   набор `PASS_TO_PASS` пуст; на ветке — все тесты базы исчезли (требование 4).
3. **`PASS_TO_PASS`.** В набор входят тесты, прошедшие на базе без повторов
   (`retries == 0`). Красный на ветке — `failed`, `error` или `passed` с
   `retries > 0`; `skipped` — не красный (это требование 4). Красный тест
   перепрогоняется ещё дважды на ветке и дважды на базе — только его файлы,
   через `_report_run` (`orchestrator/acceptance.py:793`), предел —
   `full_suite_timeout_sec` компонента; компонент `pult-vitest` без `select` —
   отказ подготовки. Перепрогон с исходом не «зелёный» и не «красный» — отказ
   подготовки; тест, пропавший из отчёта перепрогона, — красный этого
   прогона. Итог по тесту:
   - красный на ветке все три раза при трижды зелёной базе — находка
     «сломан правкой»;
   - красный хотя бы раз и зелёный хотя бы раз на ветке при трижды зелёной
     базе — находка «нестабилен после правки»;
   - база хотя бы раз красная — не находка, строка журнала «нестабилен и на
     базе: <идентификатор>».
4. **Сравнение отчётов** — отдельная функция над двумя списками
   `CaseResult` (`orchestrator/reporters/outcome.py`; идентификатор —
   `orchestrator/project_profile.py:440`, `test_id`). Находки по тесту базы:
   идентификатор исчез на ветке; «прошёл → пропущен»; на ветке `todo` или
   `fails` у прежнего идентификатора. Новый идентификатор (нет на базе) с
   исходом пропуск, `todo` или `fails` — находка на этот идентификатор. Рост
   числа пропусков компонента — итоговая строка отказа, не отдельная
   находка. Один идентификатор — одна находка, по старшинству требования 6.
5. **Мандат.** Находка покрыта, если путь её файла — элемент прежнего
   маркера «Ослабление тестов разрешено:», собранного тем же правилом, что
   `_answer_mandate` (`orchestrator/advance_gates/test_integrity.py:1074`),
   с отбраковкой ANSWER, закоммиченного автокоммитом шага роли. Для
   Python-компонента элемент `путь::имя` прежнего маркера покрывает находку
   исходов с тем же путём и полным именем.
6. **Отказ и журнал.** Непокрытые находки — одним отказом в порядке:
   исчезнувшие → «сломан правкой» → «нестабилен после правки» → прочие
   находки сравнения; внутри вида — по идентификатору; каждая строкой с
   идентификатором и исходами по прогонам. Действия журнала:
   - среди непокрытых находок есть хоть одна, кроме «сломан правкой», —
     «переход отклонён: гейт неослабления по исходам», класс «чинит
     Оператор», в отказе все находки;
   - непокрытые находки — только «сломан правкой» — «переход отклонён: гейт
     неослабления по исходам — сломан правкой», класс «чинит роль»;
   - отказ подготовки — «переход отклонён: гейт неослабления по исходам —
     подготовка», класс «чинит Оператор».
   Все три действия — в `REFUSAL_CLASSES`
   (`orchestrator/advance_gates/refusal_classes.py`),
   `tests/test_refusal_classes.py` дополняется. Пройденный гейт — запись
   журнала с числом тестов базы и ветки, перепрогонов и покрытых мандатом
   находок.
7. **Тесты** детерминированы, без сети и без Node: функция сравнения
   требования 4 — на записях `pult-vitest` (`mode=todo`, `fails=True`,
   пропуск) и `junit-xml`; сквозной сценарий — учебный проект с компонентом
   `junit-xml` на подменённом раннере, отдающем заранее заданные отчёты по
   номеру прогона. `tests/test_fsm_advance_gate_smoke.py` — без правок.

## Критерии приёмки

AC-1. У артели, у записи `test_profile` (в том числе с `report: junit-xml`) и при отказе/пропуске решения `decide` гейт исходов не создаётся: полный набор не прогоняется, записи журнала гейта исходов нет, переход `in_dev -> verifying` ведёт себя как до задачи; `tests/test_fsm_advance_gate_smoke.py` не изменён и зелёный.

AC-2. Гейт исходов вызывается после гейта неослабления по тексту и до гейта переделки ревью: при отказе гейта по тексту прогона исходов нет; при отказе гейта исходов гейт переделки ревью не исполняется.

AC-3. При истинном `in_outcome_bounds` полный набор единственного компонента прогоняется `components_full_suite(..., fresh=True)` дважды — на выписке базы `diff_base` и на выписке головы кодовой ветки, в отдельных выписках.

AC-4. Исход стороны «неизвестно/не начат» или таймаут (на базе или на ветке) даёт отказ подготовки с причиной и названной стороной, без сравнения и без находок; действие журнала — «переход отклонён: гейт неослабления по исходам — подготовка».

AC-5. В `PASS_TO_PASS` входят только тесты, прошедшие на базе с `retries == 0`: тест, прошедший на базе с повтором, в набор не входит и находкой красноты не становится; «нет тестов» на базе даёт пустой `PASS_TO_PASS`.

AC-6. Тест `PASS_TO_PASS` с исходом на ветке `failed`, `error` или `passed` с `retries > 0` перепрогоняется ещё два раза на ветке и два раза на базе через `_report_run` только по своим файлам (файлы других тестов в перепрогон не передаются), с пределом `full_suite_timeout_sec` компонента; тест `skipped` на ветке не перепрогоняется.

AC-7. Компонент `pult-vitest` без `select` при необходимости перепрогона, перепрогон с исходом не «зелёный» и не «красный» — каждый даёт отказ подготовки; тест, пропавший из отчёта перепрогона, считается красным в этом прогоне.

AC-8. Итог по тесту: красный на ветке все три раза при трижды зелёной базе — находка «сломан правкой»; красный хотя бы раз и зелёный хотя бы раз на ветке при трижды зелёной базе — находка «нестабилен после правки»; база хотя бы раз красная — находки нет, в журнале строка «нестабилен и на базе: <идентификатор>».

AC-9. Функция сравнения двух списков `CaseResult` даёт находку на: идентификатор базы, исчезнувший на ветке; «прошёл → пропущен»; `todo` или `fails` на ветке у прежнего идентификатора; новый идентификатор с исходом пропуск, `todo` или `fails` — проверено на записях `pult-vitest` (`mode=todo`, `fails=True`, пропуск) и `junit-xml`. Рост числа пропусков компонента даёт итоговую строку отказа, не отдельную находку; один идентификатор даёт не больше одной находки — старшую по порядку AC-10.

AC-10. Непокрытые находки выводятся одним отказом в порядке: исчезнувшие → «сломан правкой» → «нестабилен после правки» → прочие находки сравнения, внутри вида — по идентификатору; каждая находка — строкой с идентификатором и исходами по прогонам.

AC-11. Находка покрыта мандатом, если путь её файла — элемент маркера «Ослабление тестов разрешено:» по правилу `_answer_mandate`; для Python-компонента элемент `путь::имя` покрывает находку с тем же путём и полным именем; маркер в ANSWER, закоммиченном автокоммитом шага роли, находку не покрывает.

AC-12. Действия журнала: непокрытые находки только «сломан правкой» — «переход отклонён: гейт неослабления по исходам — сломан правкой», класс «чинит роль»; есть хоть одна непокрытая находка другого вида — «переход отклонён: гейт неослабления по исходам», класс «чинит Оператор», в отказе все находки. Все три действия гейта (с действием подготовки) — в `REFUSAL_CLASSES` со своими классами, `tests/test_refusal_classes.py` проверяет их; `auto` возвращает шаг developer на «сломан правкой» и останавливается на двух остальных.

AC-13. Пройденный гейт пишет запись журнала с числом тестов базы и ветки, числом перепрогонов и числом покрытых мандатом находок.

AC-14. Тесты задачи детерминированы, не ходят в сеть и не требуют Node; сквозной сценарий идёт на учебном проекте с компонентом `junit-xml` и подменённым раннером, отдающим заранее заданные отчёты по номеру прогона.
