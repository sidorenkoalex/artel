# SPEC: G3а-1а: гейт неослабления по исходам на выходе из `in_dev` — `PASS_TO_PASS`, нестабильность, сравнение отчётов

## Контекст
ADR-0026 («Решение», п. 6) вводит гейт неослабления по исходам тестов; эта
задача — первая часть G3а (решение Оператора 20.10: G3а-1а / G3а-1б / G3а-2).
Сегодня гейт неослабления на переходе `in_dev -> verifying`
(`orchestrator/fsm_advance.py:804`, `_test_integrity_gate_refuses`; тело —
`orchestrator/advance_gates/test_integrity.py:1722`) читает только
Python-текст тестов: тесты Vitest не проверяет ни один гейт неослабления, а
сломанный правкой или ставший нестабильным тест по исходам не ловится вовсе.
Новый гейт сравнивает исходы полного набора компонента на базе и на голове
ветки. Граница: новый гейт исполняется только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`) истинно
(компонент записи `components:` с полем `report`); у артели, у записи
`test_profile`, у записи из нескольких компонентов и у канареечной задачи —
прежнее поведение побайтно (решение Оператора на гейте SPEC №1).

## Требования

1. **Новый гейт исходов** — новый модуль
   `orchestrator/advance_gates/outcome_integrity.py`, вызов на переходе
   `in_dev -> verifying` сразу после гейта по тексту
   (`_test_integrity_gate_refuses`) и до гейта переделки ревью
   (`_review_rework_gate_refuses`). Профиль — `decide(target).profile`
   (`orchestrator/project_profile.py:184`). Если решение — отказ или пропуск
   либо `in_outcome_bounds` ложно, гейт не создаётся: ни прогона, ни записи
   журнала. Канареечная задача (`t["is_canary"]`) — гейт не создаётся, тем же
   условием, что у соседних гейтов
   (`orchestrator/advance_gates/test_integrity.py:1754`). Компонент —
   единственный компонент профиля.
2. **Прогоны.** Полный набор компонента на базе (`diff_base`,
   `orchestrator/gitcmd.py:533`) и на голове кодовой ветки в отдельных
   выписках, `components_full_suite(..., fresh=True)`
   (`orchestrator/acceptance.py:3425`). Порядок прогонов сторон SPEC не
   задаёт. Любой сбой подготовки — `diff_base` не определена, голова кодовой
   ветки не прочитана, выписка базы или головы не создана — отказ подготовки
   с причиной, без пропуска гейта. Исход стороны «неизвестно/не начат»
   (`FULL_SUITE_NOT_STARTED`) или таймаут — отказ подготовки с причиной и
   стороной, без сравнения. «Нет тестов» (`FULL_SUITE_NO_TESTS`) на базе —
   набор `PASS_TO_PASS` пуст; на ветке — все тесты базы исчезли
   (требование 4).
3. **`PASS_TO_PASS`.** В набор входят тесты, прошедшие на базе без повторов
   (`retries == 0`); тест, прошедший на базе с повтором, в набор не входит.
   Красный на ветке в полном прогоне — `failed`, `error` или `passed` с
   `retries > 0`; `skipped` — не красный (это требование 4). Красный тест
   перепрогоняется ещё дважды на ветке и дважды на базе — только его файлы,
   через `_report_run` (`orchestrator/acceptance.py:793`), предел —
   `full_suite_timeout_sec` компонента; компонент `pult-vitest` без `select` —
   отказ подготовки. Перепрогон с исходом прогона не «зелёный» и не
   «красный» — отказ подготовки. Итог каждого перепрогона определяется по
   записи этого теста, не по вердикту прогона: красный соседний тест в том же
   файле на итог не влияет.
   - На ветке: запись `failed`, `error`, `passed` с `retries > 0`, `skipped`
     или отсутствие записи — красный этого прогона; запись `passed` без
     повторов — зелёный.
   - На базе: запись `passed` без повторов — зелёный; `failed` или `error` —
     красный; `skipped` или отсутствие записи — отказ подготовки.

   Итог по тесту:
   - красный на ветке все три раза при трижды зелёной базе — находка
     «сломан правкой»;
   - красный хотя бы раз и зелёный хотя бы раз на ветке при трижды зелёной
     базе — находка «нестабилен после правки»;
   - база хотя бы раз красная — не находка, строка журнала «нестабилен и на
     базе: <идентификатор>».
4. **Сравнение отчётов** — отдельная функция над двумя списками
   `CaseResult` (`orchestrator/reporters/outcome.py`; идентификатор —
   `orchestrator/project_profile.py:440`, `test_id`). Находки по тесту базы:
   идентификатор исчез на ветке; «стал пропуском» — идентификатор базы с
   любым исходом (`passed`, `failed`, `error`), который на ветке `skipped`;
   на ветке `todo` или `fails` у прежнего идентификатора. Новый
   идентификатор (нет на базе) с исходом пропуск, `todo` или `fails` —
   находка на этот идентификатор. Рост числа пропусков компонента — итоговая
   строка отказа, не отдельная находка. Один идентификатор — одна находка, по
   старшинству требования 6.
5. **Мандат.** Находка покрыта, если путь её файла — элемент прежнего
   маркера «Ослабление тестов разрешено:», собранного тем же правилом, что
   `_answer_mandate` (`orchestrator/advance_gates/test_integrity.py:1074`),
   с отбраковкой ANSWER, закоммиченного автокоммитом шага роли. Элемент
   прежнего маркера `путь::Класс` или `путь::Класс::метод` покрывает находки
   исходов того же файла, чьё полное имя начинается с этого префикса, если
   за префиксом идёт конец имени, `::`, `[` или `#` (параметризованные
   варианты и повторы `#n`).
6. **Отказ и журнал.** Непокрытые находки — одним отказом в порядке:
   исчезнувшие → «сломан правкой» → «нестабилен после правки» → прочие
   находки сравнения; внутри вида — по идентификатору; каждая строкой с
   идентификатором и исходами по прогонам. Действия журнала:
   - среди непокрытых находок есть хоть одна, кроме «сломан правкой», —
     «переход отклонён: гейт неослабления по исходам», класс «чинит
     Оператор», в отказе все находки;
   - непокрытые находки — только «сломан правкой» — «переход отклонён: гейт
     неослабления по исходам — сломан правкой», класс «чинит роль»;
   - отказ подготовки — «переход отклонён: гейт неослабления по исходам —
     подготовка», класс «чинит Оператор».
   Все три действия — в `REFUSAL_CLASSES`
   (`orchestrator/advance_gates/refusal_classes.py`),
   `tests/test_refusal_classes.py` дополняется. Пройденный гейт — запись
   журнала с числом тестов базы и ветки, перепрогонов и покрытых мандатом
   находок.
7. **Тесты** детерминированы, без сети и без Node.
   - Функция сравнения требования 4 — на записях `pult-vitest` (`mode=todo`,
     `fails=True`, пропуск) и `junit-xml`.
   - Ветви с `retries` (тест с повтором на базе вне набора; `passed` с
     `retries > 0` на ветке — красный) проверяются на уровне записей
     `CaseResult`, в том числе `pult-vitest`; сквозной сценарий `junit-xml`
     их не покрывает.
   - Сквозной сценарий — учебный проект с компонентом `junit-xml` на
     подменённом раннере, который различает сторону по выписке (метка в
     дереве базы и в дереве головы), а не по номеру прогона. Обязательные
     сценарии: каждая находка требования 3 («сломан правкой», «нестабилен
     после правки»); порядок требования 6; перепрогон только нужных файлов;
     «нестабилен и на базе»; отказ подготовки по каждому исходу стороны и
     перепрогона; мандат на файл и на `путь::имя`; ANSWER от автокоммита
     роли находку не снимает. У артели и у записи `test_profile` — гейт не
     создан, прогона нет; `tests/test_fsm_advance_gate_smoke.py` без правок.
8. **Прежние сценарии.** Долгоживущие тесты прежних задач, проходящие
   `in_dev -> verifying` на профиле `components:` с `report`, остаются
   зелёными; их утверждения не меняются. Допускается только добавление
   подготовки (подменённый раннер для выписки базы), заявленное в PLAN.

## Критерии приёмки

AC-1. У артели, у записи `test_profile` (в том числе с `report: junit-xml`), при отказе/пропуске решения `decide` и у канареечной задачи гейт исходов не создаётся: полный набор не прогоняется, записи журнала гейта исходов нет, переход `in_dev -> verifying` ведёт себя как до задачи; `tests/test_fsm_advance_gate_smoke.py` не изменён и зелёный.

AC-2. Гейт исходов вызывается после гейта неослабления по тексту и до гейта переделки ревью: при отказе гейта по тексту прогона исходов нет; при отказе гейта исходов гейт переделки ревью не исполняется.

AC-3. При истинном `in_outcome_bounds` полный набор единственного компонента прогоняется `components_full_suite(..., fresh=True)` дважды — на выписке базы `diff_base` и на выписке головы кодовой ветки, в отдельных выписках; подменённый раннер различает сторону по метке в дереве выписки, порядок прогонов сторон не проверяется.

AC-4. Отказ подготовки с причиной (действие журнала «переход отклонён: гейт неослабления по исходам — подготовка», без сравнения и без находок) даёт каждый из случаев: `diff_base` не определена; голова кодовой ветки не прочитана; выписка базы или головы не создана; исход стороны «неизвестно/не начат» или таймаут на базе или на ветке (в отказе названа сторона). Ни в одном из них гейт не пропускается.

AC-5. В `PASS_TO_PASS` входят только тесты, прошедшие на базе с `retries == 0`: тест, прошедший на базе с повтором, в набор не входит и находкой красноты не становится; «нет тестов» на базе даёт пустой `PASS_TO_PASS`. Ветвь с повтором на базе проверена на уровне записей `CaseResult`, в том числе `pult-vitest`.

AC-6. Тест `PASS_TO_PASS` с исходом на ветке `failed`, `error` или `passed` с `retries > 0` (последнее — проверено на уровне записей `CaseResult`, в том числе `pult-vitest`) перепрогоняется ещё два раза на ветке и два раза на базе через `_report_run` только по своим файлам (файлы других тестов в перепрогон не передаются), с пределом `full_suite_timeout_sec` компонента; тест `skipped` на ветке не перепрогоняется.

AC-7. Отказ подготовки дают: компонент `pult-vitest` без `select` при необходимости перепрогона; перепрогон с исходом прогона не «зелёный» и не «красный»; на перепрогоне базы запись теста `skipped` или отсутствие записи. На перепрогоне ветки запись `failed`, `error`, `passed` с `retries > 0`, `skipped` или отсутствие записи — красный этого прогона.

AC-8. Итог по тесту определяется по записи этого теста, не по вердикту прогона: при красном соседнем тесте в том же файле и зелёной записи теста перепрогон зелёный. Красный на ветке все три раза при трижды зелёной базе — находка «сломан правкой»; красный хотя бы раз и зелёный хотя бы раз на ветке при трижды зелёной базе — находка «нестабилен после правки»; база хотя бы раз красная (`failed`/`error`) — находки нет, в журнале строка «нестабилен и на базе: <идентификатор>».

AC-9. Функция сравнения двух списков `CaseResult` даёт находку на: идентификатор базы, исчезнувший на ветке; «стал пропуском» — идентификатор базы с исходом `passed`, `failed` или `error`, ставший на ветке `skipped` (каждый из трёх исходов базы); `todo` или `fails` на ветке у прежнего идентификатора; новый идентификатор с исходом пропуск, `todo` или `fails` — проверено на записях `pult-vitest` (`mode=todo`, `fails=True`, пропуск) и `junit-xml`. Рост числа пропусков компонента даёт итоговую строку отказа, не отдельную находку; один идентификатор даёт не больше одной находки — старшую по порядку AC-10.

AC-10. Непокрытые находки выводятся одним отказом в порядке: исчезнувшие → «сломан правкой» → «нестабилен после правки» → прочие находки сравнения, внутри вида — по идентификатору; каждая находка — строкой с идентификатором и исходами по прогонам.

AC-11. Находка покрыта мандатом, если путь её файла — элемент маркера «Ослабление тестов разрешено:» по правилу `_answer_mandate`; элемент `путь::Класс` или `путь::Класс::метод` покрывает находку того же файла, чьё полное имя начинается с этого префикса, если за ним конец имени, `::`, `[` или `#` (и не покрывает, если за префиксом иной символ — например, `путь::Класс` не покрывает `путь::КлассДругой::метод`); маркер в ANSWER, закоммиченном автокоммитом шага роли, находку не покрывает.

AC-12. Действия журнала: непокрытые находки только «сломан правкой» — «переход отклонён: гейт неослабления по исходам — сломан правкой», класс «чинит роль»; есть хоть одна непокрытая находка другого вида — «переход отклонён: гейт неослабления по исходам», класс «чинит Оператор», в отказе все находки. Все три действия гейта (с действием подготовки) — в `REFUSAL_CLASSES` со своими классами, `tests/test_refusal_classes.py` проверяет их; `auto` возвращает шаг developer на «сломан правкой» и останавливается на двух остальных.

AC-13. Пройденный гейт пишет запись журнала с числом тестов базы и ветки, числом перепрогонов и числом покрытых мандатом находок.

AC-14. Тесты задачи детерминированы, не ходят в сеть и не требуют Node; сквозной сценарий идёт на учебном проекте с компонентом `junit-xml` и подменённым раннером, различающим сторону по выписке, и покрывает: «сломан правкой», «нестабилен после правки», порядок AC-10, перепрогон только нужных файлов, «нестабилен и на базе», отказ подготовки по каждому исходу стороны и перепрогона, мандат на файл и на `путь::имя`, неснятие находки ANSWER от автокоммита роли; у артели и у записи `test_profile` гейт не создан и прогона нет.

AC-15. Долгоживущие тесты прежних задач, проходящие `in_dev -> verifying` на профиле `components:` с `report`, зелёные, их утверждения не изменены; если в них что-то добавлено, это только подготовка (подменённый раннер для выписки базы), и она заявлена в PLAN.
