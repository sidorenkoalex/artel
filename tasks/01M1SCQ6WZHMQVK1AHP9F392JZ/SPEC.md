# SPEC: регрессия №15 — рубеж «замечания ревью не отработаны» сверяется с коммитом ревьювера, а не с последним коммитом REVIEW.md

## Контекст

Инцидент 05.09 на задаче P0 (01M1REVEZ1HESMJ7AFD5A9MEJ8) после мержа
регрессии №13: рубеж `orchestrator/fsm_advance.py::
_review_rework_gate_refuses` сравнивает время последнего коммита
`tasks/<id>/REVIEW.md` в артефактной ветке с временем последнего
коммита developer в кодовой ветке. Но последний коммит `REVIEW.md` —
автокоммит артефактов ШАГА DEVELOPER (developer правит леджер
замечаний в `REVIEW.md`, T100), и он всегда новее коммита кода того же
шага. Итог: штатный шаг developer после замечаний не засчитан, рубеж
отказывает переходу «замечания ревью не отработаны», хотя шаг был.
Класс: каждая задача с замечаниями ревью упирается в этот рубеж.

Опорное время рубежа должно фиксироваться моментом, когда ревьювер
вынес вердикт `changes_requested` текущей итерации, — не любым более
поздним коммитом, тронувшим тот же файл по другой причине.

## Требования

1. Опорное время рубежа `in_dev -> review`
   (`orchestrator/fsm_advance.py::_review_rework_gate_refuses`) — не
   время последнего коммита, тронувшего `tasks/<id>/REVIEW.md` в
   артефактной ветке, а время автокоммита артефактов шага РЕВЬЮВЕРА
   (автокоммит «артефакты шага reviewer» с вердиктом
   `changes_requested` текущей итерации), либо, если такого коммита
   нет, — время записи журнала `agent run finished` роли `reviewer`
   этой итерации.
2. Рубеж пропускает переход, если после опорного времени (требование
   1) есть коммит developer в кодовой ветке ИЛИ запись журнала `agent
   run finished` роли developer после записи журнала `state -> in_dev`
   этого визита. Критерий «был ли шаг developer после опорного
   момента» — общий с проверкой `auto.py` (гейт переделки цикла,
   сегодня `_role_step_since_state_entry`): один источник истины,
   вынесенный в общую функцию, не два независимых правила.
3. Отказ рубежа называет оба момента времени — опорное время
   (требование 1) и время последнего коммита developer — и источник
   опорного времени.
4. Правка developer'ом леджера замечаний в `REVIEW.md` (автокоммит
   артефактов шага developer, тронувший `REVIEW.md`) опорное время
   рубежа не сдвигает — даже будучи самым свежим коммитом, тронувшим
   `REVIEW.md`.

## Критерии приёмки

AC-1. Опорное время рубежа `in_dev -> review`
(`_review_rework_gate_refuses`) определяется коммитом автокоммита
артефактов шага РЕВЬЮВЕРА текущей итерации (сообщение вида `<id>:
артефакты шага reviewer (автокоммит оркестратора...)`, вынесший
вердикт `changes_requested`), а если такого коммита нет — записью
журнала `agent run finished` роли `reviewer` этой итерации.

AC-2. Автокоммит артефактов шага developer, тронувший `REVIEW.md`
(правка леджера замечаний, T100), не является кандидатом на опорное
время рубежа по AC-1, даже если это самый свежий по времени коммит,
затрагивающий `tasks/<id>/REVIEW.md` в артефактной ветке.

AC-3. Рубеж пропускает переход `in_dev -> review`, если ПОСЛЕ опорного
времени (AC-1) есть хотя бы один коммит developer в кодовой ветке ИЛИ
запись журнала `agent run finished` роли developer, сделанная после
записи журнала `state -> in_dev` текущего визита в состояние.

AC-4. Условие «был ли шаг developer после опорного момента» (AC-3)
реализовано ОДНОЙ общей функцией, используемой и рубежом
`orchestrator/fsm_advance.py::_review_rework_gate_refuses`, и рубежом
`orchestrator/auto.py` (гейт переделки цикла, сегодня
`_role_step_since_state_entry`) — не двумя независимо реализованными
проверками одного и того же критерия.

AC-5. Отказ рубежа называет оба момента времени — опорное время (AC-1)
и время последнего коммита developer в кодовой ветке — и источник
опорного времени (автокоммит шага reviewer либо запись журнала).

AC-6. Тест сценария инцидента: коммит кода (developer), затем
автокоммит артефактов шага developer, тронувший `REVIEW.md`, —
переход `in_dev -> review` проходит.

AC-7. Тест сценария «ревьювер вынес `changes_requested`, developer не
запускался» — рубеж отказывает переходу так же, как раньше.

AC-8. Существующие тесты регрессии №13 (`tests/test_auto_cycle.py`,
планка задачи 01M1RHFRQ2C0P4A57XJJ1WZV8N) остаются зелёными без
ослабления — ни один из них не удалён и не смягчён.

  соединения) — отдельный дефект backlog («Гейт переделки после ревью
  читает журнал через долгоживущее соединение цикла и не видит шаг
  роли»), своя задача и бюджет.
- Гейт зон (`_zones_gate_refuses`), сравнивающий дифф с локальным
  `main` (пином) вместо merge-base с `origin/main`, — отдельный дефект
  backlog («Гейт зон сверяет дифф с локальным main»), своя задача.
- Порядок мержа этой задачи относительно регрессии №14
  (01M1RNZ6V7TTTTYAHBMF8JBQQS, тоже трогающей `fsm_advance.py`) —
