# PLAN: ANSWER Оператора в in_dev — основание шага developer, а не переход по готовым артефактам

## Подход
Новый гейт рубежа `in_dev -> verifying` — `advance_gates/review.py::_answer_gate`
рядом с прецедентом `_review_rework_gate`. Встроен в
`fsm_advance.in_dev` через `_run_gates` сразу после ветки
`PLAN status: escalate` и до лока планки, подтяжки main и остальных гейтов:
переход держит неотработанный шаг роли, состояние ветки тут ни при чём,
и подтяжку не стоит делать ради перехода, который всё равно откажет.
Поэтому `auto._pre_advance_step` и ручной `advance` держатся одним и тем же
рубежом (требования 1, 3), а `auto.py` не трогается.

Разбор журнала — `_unprocessed_answer`: последняя запись `operator`
с действием, начинающимся на «ANSWER создан» (указание, мандаты, ответ на
эскалацию, `zones-extend` — все пишут `detail` = `tasks/<id>/ANSWER-n.md`),
отработана, если после неё завершился шаг developer, НАЧАТЫЙ позже неё
(требование 4: «шаг developer, начатый позже ANSWER»). Признак завершения шага —
`agent run finished` роли developer или запись `checkpoint.commit_success_checkpoint`
«код закоммичен пультом за роль». Единственный вызов этой функции —
успешное завершение шага developer в `runner` (перед `agent run finished`),
так что в живом журнале обе записи идут вместе; учёт второй нужен песочницам
долгоживущих тестов 01M446WN0V7JW4NSYQFKTBJ05C (`GateParityTest` моделирует
шаг developer автокоммитом пульта без записей `agent run …`). Шаг, шедший в
момент ANSWER (указание в `in_dev` пишется без lease, поверх идущего шага),
его не отрабатывает: бриф этого шага собран раньше ANSWER. Отказ называет
`ANSWER-n.md` последнего ANSWER (требование 1, AC-6). Сам рубеж визит не
различает: ANSWER, отработанный до текущего входа в `in_dev`, к этому
моменту уже закрыт шагом developer (требование 6).

Действие отказа `ANSWER_UNPROCESSED_REFUSAL_ACTION` = «переход отклонён: ANSWER
Оператора не отработан developer» объявлено в `refusal_classes.py` (как
`REWORK_REFUSAL_ACTION`) и внесено в `REFUSAL_CLASSES` с классом «чинит
роль», но НЕ в `ROLE_NOT_FINISHED_REFUSAL_ACTIONS`. На этот отказ `auto`
запускает developer, а бриф уже несёт ANSWER (`brief.py` не правится,
требование 2). Повтор отказа после шага developer в этом визите останавливает
цикл общим правилом `_role_step_between_repeated_refusals` (требование 5).

Бюджет SPEC (30 USD) не пересматривается.

## Влияние на систему
- Рубеж `in_dev -> verifying` получает одно дополнительное условие отказа;
  ни один существующий гейт не ослаблен и не переставлен — их порядок между
  собой прежний. Новый гейт стоит раньше подтяжки main, поэтому при
  неотработанном ANSWER подтяжки в этом вызове нет: её сделает следующий advance.
- ANSWER на эскалацию, пришедшую не от developer (например, из
  `tests_writing`), или мандат, по которому developer ещё не работал, тоже даёт
  один шаг developer перед `verifying`, если после него шагов developer не было.
  Это буква требования 1 («любого вида»): один лишний шаг роли дешевле красного CI.
- Канарейка: синтетический ANSWER при возврате из `escalated` в `in_dev` теперь
  ведёт к шагу developer перед `verifying` (`tests/test_canary*.py` зелёные).
- Откат — revert merge-коммита: правка аддитивна (одна константа, одна запись
  перечня, две функции, один вызов).

## Риски
- Порядок записей журнала в одну секунду: разбор идёт по порядку `id`
  (`store.task_steps`), а не по времени, поэтому гонок по `ts` нет.
