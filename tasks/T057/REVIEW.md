# REVIEW: Дедупликация liveness-хелперов и lease-обвязки

## Фаза A: гейт плана

1. Покрытие требований SPEC таблицей PLAN — полное (1→шаг1, 2→шаг2,
   3→шаг4, 4→шаги2,4, 5→шаги2,3,4, 6→шаги2,3,4, 7→шаги1,5); проверено
   построчно, разрывов нет.
2. Шаги — проверяемые единицы (новый модуль / новая функция обвязки /
   symmetричная функция / миграция вызывателей / прогон гейтов),
   размер MR разумный, не микрооперации и не «сделать всё».
3. Подход не конфликтует с конвенциями: `liveness.py` — лист графа
   импортов (только stdlib), `run_locked`/`run_window` сохраняют
   прежний порядок операций. Расширение периметра на
   `merge_lock.run_window` — не буквально из текста SPEC, но
   обосновано в разделе «Подход»/«Риски»: локальный приёмочный тест
   AC-3 (tasks/T057/acceptance_tests/test_ac3_shared_lease_binding.py)
   ищет голую подстроку `.acquire(`/`.release(` по всему тексту
   `fsm.py` и падает на несвязанной с задачей merge_lock-обвязке,
   если её не перенести тоже; тест — часть пакета задачи и залочен
   (tasks/T023: код чинится под тест). Перенос кода без изменения
   семантики (см. Фазу B, п.3) — приемлемое разрешение конфликта,
   риск открыто задокументирован разработчиком с путём отката.
