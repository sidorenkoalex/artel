# PLAN: Fingerprint окружения в журнале шага

## Подход

Сборщик fingerprint — одна функция `orchestrator/agent_log.py::
environment_fingerprint()`: строка из трёх частей (версия+путь
интерпретатора Python, версия git, версия claude CLI), без побочных
эффектов кроме собственного модульного кэша. Место выбрано по трём
доводам:
- `agent_log.py` уже отвечает за наблюдаемость шага (логи, трение) —
  fingerprint того же рода наблюдаемости, не нового класса;
- `runner.py` уже импортирует `agent_log` — точке журналирования
  агентного шага не нужен новый импорт;
- `fsm_advance.py` тогда получает ровно один новый импорт
  (`agent_log`), вместо того чтобы городить fingerprint в `acceptance.py`,
  который по требованию 4б журнал не пишет и соединения с БД не имеет
  (SPEC, «Материалы» + требование 6) — вкладывать туда код, целиком
  посвящённый журналированию, было бы противоречием этому же требованию.

Версии git/claude снимаются тем же приёмом, что уже есть в кодовой базе
для claude (`orchestrator/doctor.py::cli_version` — прямой
`subprocess.run([<бинарь>, "--version"], capture_output=True, text=True,
timeout=...)`), но с более коротким таймаутом (5 с — «единицы секунд»,
требование 2; `doctor.cli_version` использует 10 как предзапускную
проверку одной командой, здесь снимается ДВА значения на каждое из двух
журнальных событий шага, поэтому взят запас вдвое меньше потолка теста
приёмки в 10 с). Сырой вывод `--version` кладётся в fingerprint как есть
(без регэксп-разбора версии) — тексты вида `git version 2.43.0` и
`2.1.227 (Claude Code)` уже несут нужную подстроку, а лишний парсинг
добавил бы точку отказа без выигрыша.

Кэш — модульный global (`_environment_fingerprint_cache`), не
per-task/per-call: требование 3/AC-6 говорит о кэше «в рамках одного
процесса оркестратора» буквально, а не в рамках одного вызова
`cmd_run`/`cmd_advance» — значение остаётся верным на весь процесс
(`auto`, крутящий несколько шагов подряд, не должен снимать версии
инструментов заново на каждом из них).

Сбой снятия ОДНОГО поля (git недоступен, claude завис) не прерывает
сбор остальных и не бросает исключение наружу (требование 2): каждое
из трёх полей собирается независимо, ошибка любого превращается в
строку `"недоступно: <причина>"` для этого поля же. Вызывающий код
(`runner.py`, `fsm_advance.py`) поэтому не оборачивает вызов
`environment_fingerprint()` ни в `try`, ни в проверку на `None` — он
детерминированно возвращает строку в любом случае, что и даёт AC-3
(исход шага/приёмки не меняется) без отдельного кода на стороне
вызывающих точек.

`fsm_autogate.py` не тронут: чтением исходника подтверждено (и уже
зафиксировано в докстринге приёмочного теста AC-5), что этот модуль
нигде не вызывает `acceptance.run` — только `acceptance.run_full_suite`,
другую функцию вне области требования 4б/AC-5. Добавление fingerprint
туда было бы расширением задачи за пределы SPEC без соответствующего
критерия приёмки.

## Шаги

1. `orchestrator/agent_log.py`: функция `environment_fingerprint()` +
   приватный помощник `_tool_version_text()` + модульный кэш; импорт
   `platform`/`subprocess`.
2. `orchestrator/runner.py`: fingerprint — в детали событий
   `"agent run started"` и `"agent run finished"` (`run_agent_once`).
3. `orchestrator/fsm_advance.py`: импорт `agent_log`; fingerprint — в
   детали событий `"переход отклонён: приёмочные тесты"` и
   `"приёмочные тесты пройдены"` (`review`, ветка `acceptance.run`).
4. Юнит-тесты: `tests/test_agent_log.py` (сбор напрямую — доступные
   инструменты, недоступный бинарь, таймаут, кэш; плюс присутствие в
   обоих событиях агентного шага и неизменность исхода при сбое) и
   `tests/test_acceptance_tests_flow.py` (присутствие в обеих ветках
   исхода приёмки — зелёной и красной). Существующий
   `tests/test_step_cost.py::test_missing_cost_is_warned_but_step_survives`
   ослаблен с точного `assertEqual` детали на префикс + отдельная
   проверка длины — деталь `"agent run finished"` теперь легитимно несёт
   fingerprint, точное совпадение стало неверным тестом требования, а
   не защитой инварианта.
5. `docs/codebase-map.md`: регенерация (`scripts/codebase_map.py`) —
   правка `*.py` под `orchestrator/`.

Один шаг = один MR по факту размера (~150 строк суммарно) — Фаза 0
не разбивает задачу такого масштаба на несколько MR (см. шаблон PLAN).

## Влияние на систему

Изменённые файлы: `orchestrator/agent_log.py` (новая функция + 2 новых
импорта модуля стандартной библиотеки), `orchestrator/runner.py` (2
строки — суффикс к уже существующим `store.journal(...)`),
`orchestrator/fsm_advance.py` (1 новый импорт + 2 места использования),
`docs/codebase-map.md` (регенерация), `tests/test_agent_log.py`,
`tests/test_acceptance_tests_flow.py`, `tests/test_step_cost.py` (адаптация
одного `assertEqual` под легитимно расширившуюся деталь).

Сигнатура `store.journal()` не меняется — fingerprint только удлиняет
существующие строки `detail`, ни новых таблиц, ни новых колонок
`store.db()` не заводится (требование 4/AC-4/AC-5/AC-8 буквально).
`store.py`, `catalog.py`, `brief.py`, `fixation.py`, `doctor.py`,
`cleanup.py`, `prune.py`, `config.py` не тронуты — зона AC-8 соблюдена
(сверено локально: `git diff --name-only $(git merge-base main HEAD)
HEAD` после реализации не содержит ни одного из этих файлов вне
`tasks/T101/`, `tests/`, `docs/codebase-map.md`).

Оба места добавления сами по себе не читают `conn`/БД и не меняют
поведение существующих проверок (guard, gates.yaml, лимиты, budget) —
это чисто аддитивное расширение строки `detail`, которую до этой
задачи никто не сверял побайтово (существующие тесты либо не проверяли
эту деталь вовсе, либо использовали `assertIn`; единственное
исключение — адаптированный тест в шаге 4 — не тест инварианта, а тест
конкретного текста детали, который и должен был измениться вместе с
требованием).

Худший случай нового кода — оба внешних вызова (`git --version`,
`claude --version`) виснут одновременно: при таймауте 5с это +10с к
каждому из двух журнальных событий агентного шага (один раз на
процесс — дальше кэш), не блокирует и не роняет шаг (AC-3 подтверждена
тестами). Деньги/бюджет шага эта пауза не расходует — она стоит до
`spawn_agent`/после его завершения, не внутри самого прогона агента.

Откат: правка обратима `git revert` без каких-либо миграций —
`detail` — обычное TEXT-поле, старые записи журнала (без fingerprint)
и новые (с ним) равно читаются существующим `cmd_log`.

## Риски

- Таймаут 5с на ДВА внешних вызова на КАЖДОЕ из двух событий агентного
  шага (git и claude, `started` и `finished`) — в вырожденном случае
  зависших обоих бинарей это +20с суммарно на первый прогон процесса
  (второе событие — уже из кэша, повторного зависания нет). Признано
  приемлемым: шаг и так измеряется минутами (`AGENT_TIMEOUT_SEC=1800`).
- Формат строки fingerprint не документирован машиночитаемой схемой
  (просто конкатенация трёх частей) — «Не входит» SPEC явно исключает
  сравнение fingerprint между шагами out of scope для этой задачи, так
  что строгий формат сейчас не нужен; если T-задача сравнения появится
  позже, формат стоит зафиксировать тогда, под её собственные
  требования.

## Эскалация

REVIEW.md итерации 1 (R1-F1, major) указал на третью фактическую точку
вызова `acceptance.run` — `orchestrator/fsm.py::_pull_main_or_escalate`
(строка 204, red-исход журналируется через `store.set_state` →
`journal`) — не покрытую fingerprint'ом, и предложил либо расширить
зону AC-8 на этот файл, либо явно зафиксировать в SPEC «Не входит», что
подтяжка main вне охвата задачи.

Обе стороны этого выбора вне полномочий роли разработчика прямо сейчас,
не только по духу («конфликт зон — эскалация, не выход за границу»,
требование 6 SPEC), но и по факту двух независимых механических
барьеров:

1. Правка `orchestrator/fsm.py` красит ЛОКЕД-приёмочный тест
   `tasks/T101/acceptance_tests/test_ac8_change_zone_restricted.py`
   (`ALLOWED_EXACT` буквально перечисляет 6 путей и не включает
   `fsm.py` — правка любого файла вне этого множества — красный AC-8
   по определению теста, не по домыслу). Разблокировать это может
   только test_author (тот же файл под T023) новой итерацией теста —
   не разработчик самовольной правкой локед-теста.
2. Раздвинуть саму зону/формулировку AC-8 и AC-5 может только analyst
   правкой `tasks/T101/SPEC.md` — тоже не роль разработчика.

### Контекст
Реализация (шаги 1-3 PLAN, коммит `T101: PLAN + реализация fingerprint
окружения в журнале шага`) покрывает fingerprint в обоих требуемых
SPEC'ом местах (`runner.py` — агентный шаг; `fsm_advance.py::review` —
исход приёмки) буквально по тексту требования 4/AC-4/AC-5 и по
локед-приёмочным тестам. R1-F1 — не расхождение с буквой SPEC, а
наблюдение реестра о более широкой диагностической цели требования 1
(«расхождение версий... невосстановимо задним числом»), которую текущий
буквальный охват не закрывает полностью.
