# SPEC: команда `reference <проект>` и порог справочника ядра — настройка проекта

## Контекст
Справочник ядра артели на 722a8028 — 30 386 байт при пределе 32 768
(`config.CORE_REFERENCE_MAX_BYTES`) и пороге предупреждения 90%, за сутки
вырос с 26,7 КБ. Собирают его только бриф developer/test_author
(`brief.py`, `reference_cache.get_reference(..., reason="brief")`) и
последний шаг мержа (`fsm_merge_gate._rebuild_core_reference`,
`reason="merge"`); команды пульта нет, собрать и измерить справочник
можно только обходом (`scripts/core_reference.py` в stdout, без кэша).
Порог использования — жёсткая константа `config.CORE_REFERENCE_MIN_USES = 3`,
настроить её на проект нельзя (замер 13.10 для artel: порог 3 → 30 386
байт, 4 → 26 432, 5 → 21 290, 8 → 16 949). Решение Оператора 13.10.2026:
порог — настройкой проекта, плюс команда сборки по требованию.

## Требования

1. Запись `targets.yaml` принимает необязательное подполе `min_uses` в поле
   `core_reference`: целое число от 1 до 1000. `targets._check_reference`
   принимает такое значение и отказывает `TargetsError` с именем проекта,
   поля и подполя на любое иное (не целое, булево, меньше 1, больше 1000;
   булево `true`/`false` — не целое). Нет подполя — действует
   `config.CORE_REFERENCE_MIN_USES`.
2. `reference_cache` передаёт генератору порог из настройки проекта (или
   умолчание `config.CORE_REFERENCE_MIN_USES`) и в сборке (`_build`), и в
   сверке кэша (`_read_cache`): кэш, собранный с другим порогом, не годен и
   пересобирается. Неверное подполе `min_uses` — тот же исход, что сегодня у
   неверной настройки: справочник проекта отсутствует (`absent`) с алертом,
   без падения брифа и шага мержа.
3. В `reference_cache` есть общий вход без задачи формы
   `get_reference_for_target(conn, target, *, reason, sha)` (имя выбирает
   разработчик, форма — эта). `get_reference(conn, task_id, …)` сводится к
   нему: проект — из строки задачи, sha по умолчанию — голова ветки задачи,
   как сейчас. `orchestrator/brief.py` и `orchestrator/fsm_merge_gate.py` не
   меняются, их поведение и алерты прежние. Для повода `reference` вход не
   поднимает и не снимает ни одного алерта (ни `brief.core_reference`, ни
   других): недостатки сборки, сбои и незаписанный кэш только возвращаются в
   результате и пишутся в журнал.
4. Команда пульта `reference <проект> [--sha <sha>]`, только из главной
   копии; `reference` НЕ вносится в `artel._ROLE_ALLOWED_COMMANDS` — из
   окружения роли команда отказывает, как прочие команды Оператора.
   - Порядок проверок: сначала имя проекта через `targets.target()` до любых
     действий (неизвестное — именованный отказ с перечнем проектов;
     сломанная запись `targets.yaml`, в том числе неверный `min_uses`, —
     отказ `TargetsError` с ненулевым кодом выхода, без состояния `absent`);
     затем клон; затем sha.
   - Без `--sha` — коммит `refs/heads/<base>^{commit}` клона проекта
     (`<base>` — поле записи проекта), без `fetch`. Клона нет — именованный
     отказ с подсказкой `target-init`; ссылки нет — именованный отказ.
     `--sha` — только полный sha из 40 шестнадцатеричных знаков (форма
     `reference_cache.SHA_FORM`), иное — отказ.
   - Справочник собирается через вход требования 3 (без второй реализации
     сборки, без обхода пределов и сроков `config.CORE_REFERENCE_*`), кэш
     записывается.
   - Печатается сводка: состояние (`off` / `fresh` / `cached` / `absent` с
     причиной), sha, размер в байтах, предел `CORE_REFERENCE_MAX_BYTES`,
     доля в процентах, порог использования и его источник (настройка
     проекта или умолчание) и строка-вывод по тем же формулам, что бриф
     (`brief.py` ~781-783): «больше предела — в бриф не попадёт» при
     `size > limit`; «больше 90% предела — бриф поднимет предупреждение» при
     `size*10 > limit*9` (строго больше); иначе «в пределе» (ровно 90% —
     «в пределе»).
   - Запись журнала о сборке (как `BUILT_ACTION`, повод `reference`)
     пишется с `task_id=None` и явным `target=<проект>`.
   - Код выхода 0 — справочник собран или взят из кэша (в том числе больше
     предела: это сообщение, не ошибка команды) и при `off`; ненулевой —
     `absent`, неизвестный проект, нет клона, неверный `--sha`.
5. `target-init <имя>` (`projects.cmd_target_init`) после успешного клона
   вызывает ту же сборку для проекта с полем `core_reference` и печатает ту
   же сводку. Сбой сборки не отменяет `target-init` (каталоги и клон
   остаются) и печатается именованной причиной. БД пульта не заведена —
   строка «справочник ядра: журнал недоступен — сначала init», без падения.
   Проект без поля `core_reference` — строка «справочник ядра: выключен (нет
   поля core_reference)».
6. Справка пульта: строка команды `reference` в общем перечне команд и текст
   справки команды (с формой `--sha`); `docs/codebase-map.md` обновлён в той
   же задаче.
7. Тесты в `tests/` с заявками «Ловит мутацию» на мутации: повод
   `reference` поднял алерт (в том числе через источник
   `brief.core_reference`); запись журнала команды ушла на
   `DEFAULT_TARGET` (проверяется на проекте, отличном от artel);
   `get_reference` по задаче перестал давать прежний результат (бриф и
   мерж); граница 90%: ровно 90% — «в пределе»; `reference` выполнилась из
   окружения роли; порог из настройки не передан генератору (взят из
   `config`); порог не участвует в сверке кэша (кэш с другим порогом
   засчитан годным); неверное `min_uses` (0, 1001, `true`, строка) принято;
   `reference` на неизвестном проекте создал каталоги/кэш или вызвал git;
   `reference` без клона не отказал; сводка не называет состояние «больше
   предела» при размере больше `CORE_REFERENCE_MAX_BYTES` (тест подменяет
   предел, а не строит справочник на 32 КБ); `reference` поднял или снял
   алерт брифа; `target-init` упал или удалил клон при сбое сборки.
   Песочницы — временный `targets.yaml` и синтетический клон; настоящий
   `targets.yaml` не меняется.

## Критерии приёмки

AC-1. Запись проекта с `core_reference.min_uses`, равным целому от 1 до 1000
(в том числе 1 и 1000), проходит `targets._check_reference` без ошибки.

AC-2. `targets._check_reference` отказывает `TargetsError` на `min_uses`,
равное 0, 1001, `true`, `false` и строке; текст отказа называет имя
проекта, поле `core_reference` и подполе `min_uses`.

AC-3. Без подполя `min_uses` генератору в сборке передаётся
`config.CORE_REFERENCE_MIN_USES`; с подполем — значение подполя (и в
`_build`, и в сверке `_read_cache`).

AC-4. Кэш справочника, собранный с одним порогом, при сверке с другим
порогом настройки не засчитывается годным: вход пересобирает справочник
(состояние `fresh`, не `cached`).

AC-5. Неверное `min_uses` в настройке проекта при сборке через бриф или шаг
мержа даёт состояние `absent` с алертом, бриф и шаг мержа не падают.

AC-6. Вход `get_reference_for_target(conn, target, *, reason, sha)` (или
одноимённый по выбору разработчика той же формы) существует;
`get_reference(conn, task_id, …)` для поводов `brief` и `merge` даёт
прежние результат, sha по умолчанию (голова ветки задачи) и алерты.

AC-7. Сборка с поводом `reference` — успешная, со сбоем сборки, с
недостатками и с незаписанным кэшем — не поднимает и не снимает ни одного
алерта (в том числе с источником `brief.core_reference`); исход виден в
возвращённом результате и в журнале.

AC-8. `reference <проект>` с проектом, которого нет в `targets.yaml`,
завершается ненулевым кодом с именованным отказом, перечисляющим проекты,
и не создаёт каталогов и кэша и не вызывает git.

AC-9. `reference <проект>` при сломанной записи проекта в `targets.yaml` (в
том числе неверном `min_uses`) завершается ненулевым кодом с текстом
`TargetsError`, без состояния `absent` в выводе.

AC-10. `reference <проект>` для проекта без клона завершается ненулевым
кодом с именованным отказом, содержащим подсказку `target-init`; при клоне
без ссылки `refs/heads/<base>` — ненулевым кодом с именованным отказом.

AC-11. `reference <проект> --sha <значение>` с значением не из 40
шестнадцатеричных знаков формы `SHA_FORM` (например, короткий sha или имя
ветки) завершается ненулевым кодом с отказом; без `--sha` справочник
собирается на коммите `refs/heads/<base>^{commit}` клона, `fetch` не
вызывается.

AC-12. Успешный `reference <проект>` записывает кэш
`<область проектов>/<проект>/knowledge/derived/core-reference.md` и
печатает состояние, sha, размер в байтах, предел, долю в процентах, порог
использования с источником («настройка проекта» либо «умолчание») и
строку-вывод; код выхода 0 при `fresh`, `cached` и `off`, в том числе при
размере больше предела; ненулевой при `absent` (с причиной в выводе).

AC-13. Строка-вывод сводки: при `size > limit` — «больше предела — в бриф
не попадёт»; при `size*10 > limit*9` и `size <= limit` — «больше 90%
предела — бриф поднимет предупреждение»; при размере ровно 90% предела и
меньше — «в пределе» (проверяется подменой предела).

AC-14. Запись журнала о сборке командой `reference` пишется с действием
`BUILT_ACTION`, поводом `reference`, `task_id=None` и `target`, равным
проекту команды (на проекте, отличном от artel, запись не уходит на
`DEFAULT_TARGET`).

AC-15. `reference` нет в `artel._ROLE_ALLOWED_COMMANDS`; вызов из окружения
роли отказывает, как прочие команды Оператора, без сборки.

AC-16. `target-init <имя>` для проекта с `core_reference` после клона
печатает ту же сводку; при сбое сборки печатает именованную причину,
завершается без падения, каталоги и клон остаются на месте; без БД пульта
печатает «справочник ядра: журнал недоступен — сначала init» без падения;
для проекта без поля печатает «справочник ядра: выключен (нет поля
core_reference)».

AC-17. Общий перечень команд справки пульта содержит строку `reference`, а
справка команды называет форму `--sha <sha>`.

AC-18. В `tests/` есть тесты с заявками «Ловит мутацию» на каждую мутацию
перечня требования 7; песочницы — временный `targets.yaml` и синтетический
клон, настоящий `targets.yaml` в тестах не меняется.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны 6 (≥ 5: `orchestrator/artel.py`,
`orchestrator/reference_cache.py`, `orchestrator/targets.py`,
`orchestrator/projects.py`, `tests/`, `docs/codebase-map.md`); критериев
приёмки 18 (≥ 10); `budget_usd` = 30 (≥ $30, это рамка ТЗ).

Решение — **обоснование монолита** (материал для Оператора; утверждает
Оператор на гейте SPEC):
- Технически шов по зонам есть: часть 1 — `targets.py` + `reference_cache.py`
  (подполе `min_uses`, порог в сборке и сверке кэша, вход без задачи и
  повод `reference` без алертов, требования 1–3); часть 2 — `artel.py` +
  `projects.py` (команда `reference`, сводка, `target-init`, справка,
  требования 4–6). Часть 1 мержима отдельно с зелёной планкой.
- Против нарезки: часть 2 не имеет смысла без части 1 и целиком на неё
  опирается (вход требования 3 — единственный путь сборки команды), а
  повод `reference` без алертов в части 1 без потребителя проверяется лишь
  синтетически. Рамка Оператора $30 дана на задачу целиком; две подзадачи
  удваивают постоянную часть цены (analyst, test_author, ревью на каждую —
  по калибровке ~$12–15 сверху), то есть выводят суммарно за рамку.
- Объём кода умеренный: одна новая команда-обёртка над существующей
  сборкой, одно подполе проверки и проброс порога; генератор
  (`scripts/core_reference.py`), бриф и шаг мержа не меняются.
Если Оператор предпочтёт нарезку — шов выше, порядок: часть 1 первой.
