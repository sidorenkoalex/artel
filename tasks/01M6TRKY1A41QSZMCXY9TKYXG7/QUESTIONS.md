# QUESTIONS: Приёмка принимает итог CI для дерева кода — без условия свежести при мерже пультом, с приложениями PLAN

## Вопросы

Решения 1, 2, 4, 5 гейта SPEC сверены с кодом и переносятся в SPEC как
есть. Решение 3 в зонах задачи невыполнимо: утверждение о журнале
отправки не сходится с кодом main.

Расхождение (сверено по `orchestrator/artifact_branch.py`):
- запись об успешной отправке (`:470-472`, действие `_PUSH_OK_ACTION`,
  `:92`) несёт текст `push артефактной ветки <ссылка> — успех[ (попыток N)]`,
  sha отправленного коммита в ней нет — условие «sha ссылки в `origin` равен
  sha из этой записи» проверить не по чему;
- штатная отправка после каждого коммита ссылки — `_send` (`:393`, досылка
  `:596`, `:646`); успех она журналирует только после повтора или после
  прежнего отказа (`:529`, докстринг `:519-523`: запись на каждой строке
  паспорта «засорила бы журнал»). Полная запись на каждый успех — только у
  `push` (`:489-503`), её зовёт лишь `doctor` (`orchestrator/doctor/artifact_branches.py:168`);
- `orchestrator/artifact_branch.py` в ТЗ — «только чтение», CI
  (`scripts/plan_appendix_ci.py`) sha ссылки, которую наложил, нигде не
  сохраняет (только печать в лог, `:237-266`), и тоже только чтение.

Итог: по решению 3 буквально у типичной задачи записи «нет» → условие 2б не
установлено → итог CI с приложениями PLAN не принимается никогда. AC-3
(принят) достижим только на подложенной в тест записи, которую реальный
пульт не пишет: требование 2 в работе мёртвое.

1. **Как установить «ссылка `refs/artifacts/<id>` в `origin` не сдвигалась после начала прогона CI» (условие 2б, решение 3)?**
   - A) Расширить зоны на `orchestrator/artifact_branch.py`: успешная отправка ссылки (и `_send`, и `push`) журналирует sha отправленного коммита отдельным действием (например «отправка ссылки документов: sha <sha>») на каждый успех; приёмка берёт последнюю такую запись, сверяет её sha с головой ссылки в `origin` и её время с `started_at` проверки CI полного набора (решение 3 в остальном без изменений).
     - ломается: журнал задачи получает по записи на каждый коммит ссылки документов (строки паспорта, автокоммиты шагов) — ровно то, от чего `_send` уходит сейчас (`artifact_branch.py:519-523`); задачи, отправившие ссылку до мержа этой задачи, записи не имеют — первые приёмки после мержа идут прежним путём (локальный прогон).
     - ослабляется: ничего — проверка 2б строже прежней, доказательство из журнала пульта; тишина журнала `_send` (`artifact_branch.py:529`) ослабляется для нового действия.
     - цена: +1 файл зоны (5 файлов, ~$45 класс), новый долгоживущий тест на запись sha; рост журнала.
     - чьё решение: Оператор (зона «только чтение» ТЗ).
   - B) Снять проверку момента: условие 2б сводится к равенству локальной ссылки и `origin` (решение 2), сверки с `started_at` нет.
     - ломается: случай AC-10 решения 3 (старая дата коммита, отправка после начала CI с другими приложениями) не ловится, если приложения в `origin` сейчас равны локальным, а CI наложил прежние — мутация «приложения не сверяются с моментом прогона CI» из ТЗ не красная.
     - ослабляется: требование ТЗ 2б (момент начала CI) — снимается; держится только равенство локальной ссылки и `origin` (решение 2, `artifact_branch.py:619-658`).
     - цена: без новых зон, ~$40.
     - чьё решение: Оператор (меняет требование ТЗ).
   - C) Решение 3 буквально: запись `_PUSH_OK_ACTION` с совпадающим sha, иначе итог не принят; требование 2 в работе почти не срабатывает, принятие — только в тестах.
     - ломается: ничего не ломается, но цель ТЗ (факт 4: 28 задач, 26 с приложениями) не достигается — локальные прогоны остаются.
     - ослабляется: ничего.
     - цена: ~$40, задача без эффекта на практике.
     - чьё решение: Оператор.
   - D) Расширить зоны на `scripts/plan_appendix_ci.py` и `orchestrator/ci.py`: CI ветки публикует sha ссылки документов, которую наложил (аннотация проверки/вывод шага), приёмка читает его из итога CI и сверяет с головой ссылки в `origin` и с локальной; времени не нужно.
     - ломается: меняется шаг CI ветки (`scripts/plan_appendix_ci.py`, в ТЗ «только чтение»); старые прогоны CI sha не несут — для них прежний путь.
     - ослабляется: ничего — доказательство прямое (какие приложения CI наложил), строже сверки по времени.
     - цена: +1 файл зоны и чтение аннотации/вывода в `ci.py` сверх «только `started_at`»; ~$45.
     - чьё решение: Оператор (зоны ТЗ).
   - дефолт: A — ближе всего к решению 3 Оператора (журнал пульта, `started_at`, sha), единственная недостающая деталь — sha в записи и запись на каждый успех; цена — одна зона.
