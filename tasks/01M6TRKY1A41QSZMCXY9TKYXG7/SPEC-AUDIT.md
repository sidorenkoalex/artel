# SPEC-AUDIT: Приёмка принимает итог CI для дерева кода — без условия свежести при мерже пультом, с приложениями PLAN (ADR-0031, этап 1)

## ТЗ и SPEC

  Критерий ТЗ про `approve --fresh-suite` вынесен в отдельное требование 5
  (SPEC.md:53) — это тот же критерий, нового требования здесь нет.
  Мандат ослабления тестов, зоны и «Только чтение» перенесены точно.

  критерий ТЗ (TZ.md:35 — «незакоммиченная правка в рабочей копии») словами

Не подтвердилось или неполно:
- **Ф-1. «Незакоммиченных правок нет» (SPEC.md:38–40).** И `approve`
  (orchestrator/fsm.py:1673–1674), и автогейт
  (orchestrator/fsm_autogate.py:417–418) зовут
  `appendix_tree.suite_tree(..., branch=t["branch"])`. При приложениях дерево
  кладётся на голову ветки через `git worktree add --detach <sha>`
  (orchestrator/appendix_tree.py:185). Незакоммиченные правки переносятся
  только при `branch is None` (appendix_tree.py:189–192, путь `suite-run`).
  Значит при приложениях PLAN дерево приёмки — это всегда «голова плюс
  приложения» без правок рабочей копии. Условие 2а при этом почти тавтология:
  оно сверяет повторное наложение с тем же наложением и никаких
  незакоммиченных правок не ловит. Правка рабочей копии ловится прежним
  условием равенства деревьев (acceptance.py:4181) только без приложений,
  когда корнем служит сама рабочая копия (appendix_tree.py:269–271).
  Отсюда противоречие AC-5 (расхождение 1).
- **Ф-2. «Тот же PLAN» (SPEC.md:39) — какой PLAN видел CI.** Приёмка читает
  PLAN из ЛОКАЛЬНОЙ `refs/artifacts/<id>`: `appendix_tree.read_plan` →
  `artifact_source.resolve` → `artifact_branch.show`
  (appendix_tree.py:85–86, orchestrator/artifact_branch.py:196–201). CI
  читает ссылку в `origin` (plan_appendix_ci.py:173–193). Пуш ссылки
  документов сделан по принципу best-effort (artifact_branch.py:489–498),
  досылки бывают отложенными (artifact_branch.py:560–616), так что
  локальная ссылка может опережать `origin`. Условие 2б проверяет только
  `origin` и не сверяет локальный PLAN с PLAN `origin`.
- **Ф-3. Как наблюдать, что ссылка «сдвинулась после начала прогона CI»
  (SPEC.md:41–43).** Git не хранит время перемещения ссылки на удалённой
  стороне. Проверено опытом во временном каталоге (`/tmp/audit01m6-*`):
  коммит с датой 2026-01-01 запушен сегодня в голый `origin`;
  `ls-remote` отдаёт только sha, `log --format=%aI` даёт 2026-01-01, reflog
  голого репозитория пуст. Наблюдаемы только дата коммита головы ссылки
  (а это не момент пуша) и журнал исходов пуша пульта
  (artifact_branch.push журналирует каждый исход, artifact_branch.py:494–496).
  Какой из каналов использовать, SPEC не называет.

## Зоны
- Зоны `orchestrator/acceptance.py`, `orchestrator/ci.py` (чтение времени
  начала), `docs/codebase-map.md` (генерацией), `tests/` покрывают режим
  `local` артели. Чтение `merge_gate` (`targets.target`), ссылки в `origin`
  (`gitcmd.remote_ref_state`, orchestrator/gitcmd.py:2095) и журнала —
  вызовы модулей только для чтения, их правка не нужна.
- **З-1 (неясность объёма).** Требование 2 сформулировано для всех режимов
  (SPEC.md:44–45: «“неизвестно” в `ci`/`both`»). Но приложения есть только
  у артели (appendix_tree.py:259–261), а `accepted_full_suite` внешнему
  проекту отказывает (ci.py:1301–1302). Для `ci`/`both` время начала
  конвейера пришлось бы читать через `forge`/`gitlab_adapter`, а их в зонах
  нет. Сегодня этот путь недостижим. SPEC стоит прямо ограничить
  требование 2 режимом `local` артели, иначе исполнитель либо выйдет из
  зон, либо напишет мёртвый код.
- Защищённые пути (`.github/`, `targets.yaml`) не меняются, приложений PLAN
  требования не вынуждают. Песочница ролей не расширяется.

## Пути обхода гейтов
- **О-1 (Ф-2).** Роль или пульт кладёт в локальную `refs/artifacts/<id>`
  PLAN с новым приложением, пуш не удался или отложен
  (artifact_branch.py:489, :560). Приёмка накладывает новое приложение, CI
  прогнал дерево без него, ссылка в `origin` после начала CI не двигалась.
  2а и 2б выполнены, итог CI принят для дерева, которое CI не проверял.
  Буквальное исполнение SPEC.md:38–43 этот путь оставляет. Нужно ещё
  условие: локальная ссылка равна ссылке в `origin` (есть
  `artifact_branch.origin_sync_refusal`, artifact_branch.py:619) либо PLAN
  локальной ссылки равен PLAN ссылки в `origin`.
- **О-2 (Ф-3).** Исполнитель сравнивает дату коммита головы ссылки в
  `origin` с `started_at` прогона CI. Коммит, созданный до начала CI и
  запушенный после шага приложений CI (отложенная досылка, повтор
  неудачного пуша), проходит проверку, хотя CI его не видел. Сюда же
  добавляется расхождение часов машины пульта и GitHub. SPEC должна назвать
  наблюдаемый канал. Варианты: журнал успешного пуша ссылки пульта, или
  сверка sha ссылки в `origin` с sha, записанным на момент пуша кода, или
  консервативное правило «ссылка в `origin` равна той, что была при пуше
  головы».
- **О-3 (З-1).** Если требование 2 исполнить и для `ci`/`both`, время
  конвейера через `forge` лежит вне зон. Исполнитель может «выполнить» 2б,
  взяв время из чего-то иного (например, из `ci.py` для GitHub-артели),
  так что для внешнего проекта проверка формально пройдёт.

## Вердикт
`concerns`. SPEC близка к ТЗ, факты о коде в основном верны. Но в 2а/2б и
AC-5 остаются противоречие и пути ложного принятия итога CI. Закрыть их
может Оператор на гейте SPEC решением по содержанию; вернуть аналитику —
тоже вариант, если Оператор предпочтёт правку SPEC.

Отклонения:
1. AC-5 «(с приложением PLAN или без)» (SPEC.md:80) сверх ТЗ (TZ.md:35)
   противоречит требованию 2а: при приложениях дерево приёмки не несёт
   правок рабочей копии (orchestrator/appendix_tree.py:185–192,
   orchestrator/fsm.py:1673, orchestrator/fsm_autogate.py:417). Обоснование
   «то есть незакоммиченных правок нет» (SPEC.md:40) по коду ложно.
   Предложение: убрать «с приложением PLAN» из AC-5 либо явно сказать, что
   правка рабочей копии при приложениях не проверяется ни там, ни там.
2. Условие 2б (SPEC.md:41–43) не сверяет локальный PLAN, который
   накладывает приёмка (appendix_tree.py:85–86), с PLAN ссылки в `origin`,
   который накладывал CI (scripts/plan_appendix_ci.py:173–193). Это путь
   ложного принятия О-1. Нужно добавить условие «локальная
   `refs/artifacts/<id>` равна её голове в `origin`» (или равенство PLAN).
3. Наблюдаемый канал «сдвига после начала прогона CI» (SPEC.md:41) не
   назван. Git момента пуша не хранит (опыт в «Фактах», Ф-3), а дата коммита
   допускает путь О-2. Нужно назвать канал и источник времени начала
   (check-run `started_at` / `run_started_at` последней попытки).
4. AC-2 (SPEC.md:65–69) не требует базы, отличной от `main`. После снятия
   свежести для `operator` тест
   tests/test_01m5xzskk8gzteca2kwafhe029_ci_full_suite.py:424 больше не
   ловит мутацию «сверка с `origin/main` вместо `origin/<base>`», и свойство
   остаётся без покрытия.
5. Объём требования 2 для `ci`/`both` (SPEC.md:44–45) неясен: путь
   недостижим (appendix_tree.py:259, ci.py:1301), а для исполнения нужен
   `forge` вне зон. Предложение: ограничить требование 2 режимом `local`
   артели.
6. (Мелкое.) Требование 3 (SPEC.md:46–49) не говорит, где в записи стоит
   основание. Если поставить его перед `CI_JOB_RECORD`, сломаются
   `is_ci_result` (orchestrator/acceptance.py:4201–4204) и деталь автогейта
   (fsm_autogate.py:426). Для AC-3 тест должен проверять полную фразу
   «для дерева с приложениями PLAN»: подстрока «с приложениями PLAN» уже
   есть через `tree.mark` (appendix_tree.py:33, :114).
7. (Напоминание.) Мандат ослабления из ТЗ станет строкой мандата только в
   записи Оператора на гейте SPEC (SPEC.md «Не входит»). Без неё случаи
   `stale` (tests/test_01m4begqavvwchfcw6bebb0xvt_ci_acceptance.py:155–185)
   и `stale_base` (tests/test_01m5xzskk8gzteca2kwafhe029_ci_full_suite.py:406,
   :439) остановит гейт неослабления тестов.
