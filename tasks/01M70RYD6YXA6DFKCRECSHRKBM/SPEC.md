# SPEC: Команда suite-lock: внешний прогон под замком полных прогонов машины

## Контекст
Замок полных прогонов машины (`orchestrator/suite_lock.py`, файл
`config.LOGS/suite-run/lock.json`) держат только `suite-run`, гейты и
`notes`. Команды, которая держит замок на время произвольной команды
Оператора (замер, ручной прогон набора, проба образа), нет. 07.11.2026
замер без замка совпал с автогейтом приёмки задачи 01M6TRM2EK и вызвал
ложный отказ по таймауту; 08.11 замер взял замок сценарием напрямую через
`suite_lock.acquire` — обход. Нужна штатная команда `suite-lock`, которая
берёт замок без ожидания, держит его на время дочерней команды в пределе
времени и снимает на любом исходе.

## Требования

1. Команда `artel.py suite-lock --reason "<основание>" [--limit <секунды>] -- <команда> [аргументы…]`; реализация — новый модуль `orchestrator/suite_hold.py`, точка входа `suite_hold.cmd_suite_lock(argv: list[str]) -> int` (возвращает код выхода).
2. Замок берётся без ожидания (`suite_lock.acquire`). Занят — отказ с описанием держателя (`suite_lock.describe`), код выхода не 0, команда не запускается, чужой замок не трогается.
3. Новый вид держателя `внешний` (`suite_lock`); запись замка: `task_id` — `null`, `run` — `null`, `kind` — `внешний`, основание `reason` (переводы строк заменены пробелом, обрезано до 200 символов). `describe` такого держателя — «внешней команды «<основание>» (pid N)». Прежние виды (`suite-run`, `гейт`, `notes`) и их тексты — без изменений.
4. Держатель — pid процесса команды `suite-lock`. Команда запускается дочерним процессом в своей группе процессов; `stdin` — `/dev/null`, `stdout` и `stderr` наследуются; код выхода `suite-lock` — код команды.
5. Предел: `--limit` по умолчанию равен и не больше `config.FULL_SUITE_LOCK_WAIT_SEC − config.FULL_SUITE_TIMEOUT_SEC` (сейчас 1800 − 900 = 900 с; граница вычисляется из констант в момент вызова, не литералом). Больший `--limit`, ноль, отрицательное или нечисловое значение — отказ до взятия замка. По истечении предела группа процессов команды останавливается `liveness.terminate_process_group` (`SIGTERM`, через 10 с — `SIGKILL`); сообщение называет предел; код выхода — 124.
6. Замок снимается на любом исходе: нормальное завершение, ошибка запуска команды (нет файла), истечение предела, `SIGINT`/`SIGTERM` самой `suite-lock` (группа команды останавливается тем же способом, код выхода `128 + номер сигнала`).
7. Пустая команда (нет `--`, ничего после `--`) и пустое `--reason` — отказ до взятия замка.
8. Команда регистрируется в таблице команд `artel.main` и в справке `artel.py` (докстринг, блок «Команды:»); в `_ROLE_ALLOWED_COMMANDS` не входит — процесс роли получает отказ «команда недоступна процессу роли».
9. Тесты — в новом долгоживущем файле задачи `tests/test_01m70ryd6yxa6dfkcrecshrkbm_*.py`; каждый тест несёт строку «Ловит мутацию: …». Процесс `suite-lock` в тестах — дочерний `sys.executable -c`, который переназначает `config.LOGS` на временный каталог теста и зовёт `suite_hold.cmd_suite_lock`; запуск `artel.py` дочерним процессом не используется. Команда под замком — настоящий короткий процесс, без подмены `subprocess`. Настоящий замок машины (`.artel/logs/suite-run/lock.json` главной копии) тестами не читается и не меняется.

## Критерии приёмки

AC-1. Свободный замок: во время работы команды под `suite-lock` файл замка содержит pid процесса `suite-lock`, `kind` = `внешний`, `task_id` и `run` = `null` и основание `reason`; после завершения команды файла замка нет; код выхода `suite-lock` равен коду команды — случаи кода 0 и кода 3 отдельными тестами. Поведение — последовательность взятия, запуска и снятия, отдельной функции решения нет.
Размер проверки: большой — держатель обязан быть pid настоящего дочернего процесса `suite-lock`, а код выхода — кодом настоящей команды; подмена процессов это свойство не держит.

AC-2. Замок занят живым чужим процессом: `suite-lock` отказывает текстом, который содержит `suite_lock.describe` держателя, код выхода не 0, команда не запускалась (её файл-след не создан), запись чужого замка после вызова побайтно та же. Поведение команды на занятом замке, решение — готовое `acquire`.
Размер проверки: большой — держатель должен быть живым чужим процессом, а «команда не запускалась» проверяется по отсутствию следа настоящей команды.

AC-3. `describe` держателя вида `внешний` — ровно «внешней команды «<основание>» (pid N)»; тексты видов `suite-run` (без поля `kind`), `гейт`, `notes` не изменились (ловит общий текст для всех видов).
Поверхность решения: orchestrator.suite_lock.describe(holder: dict) -> str
Размер проверки: малый

AC-4. Предел: `--limit 1` и команда, спящая 30 с и породившая дочерний процесс, — не позже чем через 15 с от запуска и команда, и её дочерний процесс завершены, файла замка нет, код выхода 124, сообщение называет предел (ловит снятие замка без остановки команды и остановку только первого процесса группы). Поведение — последовательность остановки группы, решение предела проверяет AC-5.
Размер проверки: большой — остановка группы процессов по пределу держится только на живых процессах и сигналах.

AC-5. Разбор `--limit` до взятия замка: при подменённых в тесте `config.FULL_SUITE_LOCK_WAIT_SEC` и `config.FULL_SUITE_TIMEOUT_SEC` значение больше их разности, `0`, `-5`, `x` — отказ (каждый случаем отдельно), значение, равное разности, и отсутствие `--limit` — не отказ (граница считается от подменённых констант, не литералом 900).
Поверхность решения: orchestrator.suite_hold.refusal(argv: list[str]) -> str | None
Размер проверки: малый

AC-6. `SIGTERM` процессу `suite-lock` во время работы команды, породившей дочерний процесс: не позже чем через 15 с команда и её дочерний процесс завершены, файла замка нет, код выхода 143. Поведение — обработка сигнала и остановка группы, отдельной функции решения нет.
Размер проверки: большой — доставка сигнала живому процессу и остановка его группы подменой не проверяются.

AC-7. Команды нет: `--` без продолжения и несуществующий исполняемый файл после `--` — отказ, код выхода не 0, файла замка после вызова нет (каждый случаем). Поведение входа команды, правило пустой команды проверяет AC-10.
Размер проверки: большой — ошибка запуска несуществующего файла и снятие замка после неё держатся только на настоящем запуске процесса `suite-lock` (форма теста ТЗ).

AC-8. Гейт видит внешний держатель: `acceptance._machine_lock` при файле замка вида `внешний` у живого чужого процесса (предел ожидания `config.FULL_SUITE_LOCK_WAIT_SEC` подменён малым) ждёт и пишет запись об ожидании с текстом `suite_lock.describe` этого держателя — «внешней команды «<основание>» (pid N)» (ловит вид, не читаемый ожиданием). Поведение существующего ожидания на новом виде, код `acceptance.py` не меняется.
Размер проверки: большой — держатель обязан быть живым чужим процессом (`_alive` читает настоящий pid).

AC-9. В окружении роли (`runner.in_role_environment()` истинно) вызов `artel.main` с командой `suite-lock` и корректными аргументами — отказ с текстом «команда недоступна процессу роли», команда не запускалась, файла замка нет. Подключение к существующему белому списку, новой функции решения нет.
Размер проверки: малый

AC-10. Пустая команда и пустое основание до взятия замка: нет `--`, ничего после `--`, `--reason ""`, `--reason` без значения, нет `--reason` — отказ (каждый случаем); корректный вызов `--reason r -- true` — не отказ.
Поверхность решения: orchestrator.suite_hold.refusal(argv: list[str]) -> str | None
Размер проверки: малый

AC-11. Основание записи замка: переводы строк (`\n`, `\r`) заменены пробелом, длина обрезана до 200 символов; основание без переводов и не длиннее 200 — без изменений.
Поверхность решения: orchestrator.suite_hold.reason_text(raw: str) -> str
Размер проверки: малый

AC-12. Подключение отказов до взятия замка: для входов AC-5 и AC-10, дающих отказ, процесс `suite-lock` (`sys.executable -c` → `suite_hold.cmd_suite_lock`) завершается с кодом не 0, его вывод содержит текст `suite_hold.refusal` на том же входе, файл замка не создан, команда не запускалась (её файл-след не создан).
Размер проверки: большой — форма теста ТЗ: процесс `suite-lock` в тестах — дочерний `sys.executable -c` с переназначенным `config.LOGS`.

## Оценка объёма и деление

Сработавшие сигналы: число критериев приёмки — 12 (≥ 10); `budget_usd` = 35 (≥ $30).

Обоснование монолита (решение — за Оператором на гейте SPEC): задача —
одна новая команда с одним новым видом держателя. Нарезка «вид `внешний`
в `suite_lock` отдельно, команда отдельно» оставила бы вид держателя без
единого писателя (мёртвый код с тестом `describe`), а команду без вида —
нерабочей (замок без вида читался бы как `suite-run`). Зона — 3 модуля и
один файл тестов, рост числа критериев — от разметки поверхностей и
подключения (ADR-0032), а не от объёма. Рамка $35 — из ТЗ; калибровочный
ориентир класса (10–15 критериев, до 7 файлов) ~$45 выше рамки — ставка
по рамке Оператора.

- `SIGKILL` процесса `suite-lock`: замок мёртвого держателя снимается следующим `acquire`, команда в своей группе может продолжить работу — принятый Оператором риск.
- Правило «тяжёлые прогоны сессии — только под замком» в `docs/operator-session.md` — вносит Оператор.
- Полный набор `tests/` под `suite-lock`: предел 900 с на него не рассчитан, команда для него не предназначена.
- Изменение `orchestrator/acceptance.py`, `orchestrator/suite_run.py`, `orchestrator/config.py`, `orchestrator/liveness.py`, `orchestrator/runner.py`, `orchestrator/mutation_run.py` — только чтение.
- Изменение существующих тестов (`tests/test_suite_lock.py`, `tests/test_01m5m0kqpv0fj9nsmdcq3xb76w_help_registry.py` и прочих): не меняются; краснеет существующий тест замка из-за нового вида — эскалация с именем теста.
- Отдельный критерий на регистрацию в справке «Команды:»: соответствие таблицы команд и справки держит долгоживущий `tests/test_01m5m0kqpv0fj9nsmdcq3xb76w_help_registry.py`; требование 8 при этом остаётся в силе.
- Зелёный полный набор `tests/` и CI ветки — их держит пульт.
