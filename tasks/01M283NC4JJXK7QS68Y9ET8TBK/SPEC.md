# SPEC: выход шага developer при грязном дереве — WIP-коммит кода пультом за роль

## Контекст
Три случая за 05–06.09 (developer «путей брифа» 01M1RQ12JV…, дважды
developer P1a 01M1TKP6AA…) заканчивали ход с `rc=0`, оставив код
незакоммиченным (фоновый прогон тестов, «жду уведомления»). По `rc=0`
`orchestrator/runner.py` зовёт `checkpoint.commit_step_artifacts`,
который переносит в артефактную ветку только `tasks/<id>/`; код
developer вне `tasks/<id>/` остаётся незакоммиченным в worktree.
WIP-чекпоинты кода уже есть для таймаута (`commit_timeout_checkpoint`),
`rc≠0` и обрыва потока (`commit_abnormal_checkpoint`) и `pause --now`
(`commit_pause_now_checkpoint`) — но не для обычного успешного
завершения шага. Дальше переход `in_dev -> verifying` отказывает по
грязной копии с вводящим в заблуждение текстом «PLAN.md не
закоммичен», цикл буксует, код спасает Оператор руками.

## Требования

1. После завершения шага роли `developer` кодом возврата `rc=0` в
   обычном успешном пути (не таймаут, не `rc≠0`, не отсутствие
   обязательного артефакта, не обрыв stdout-пайпа — эти случаи уже
   обрабатываются существующими WIP-чекпоинтами `orchestrator/
   checkpoint.py` и не меняются), если рабочее дерево несёт
   незакоммиченные изменения ВНЕ `tasks/<id>/`, оркестратор коммитит
   эти изменения сам — тем же приёмом и с теми же фильтрами мандата,
   что WIP-чекпоинт таймаута (`orchestrator/checkpoint.py::
   commit_timeout_checkpoint`, обвязка `_commit_worktree_change` с
   `exclude=tasks/<id>`): только роль `developer`, только для
   догфуд-target'а (`target == config.DEFAULT_TARGET`), только если
   реально есть что коммитить, тихая деградация без git.
2. Сообщение коммита — буквально: `<id>: код закоммичен пультом за
   роль developer — шаг завершён с незакоммиченным кодом`.
3. При успешном коммите пульт пишет запись журнала: `actor=orchestrator`,
   действие «код закоммичен пультом за роль», `detail` несёт список
   закоммиченных файлов и число изменённых строк.
4. Для ролей без мандата кода (не `developer`) поведение шага `rc=0` с
   грязным деревом вне `tasks/<id>/` не меняется: откат WIP вне
   мандата — как сейчас (`_discard_out_of_mandate_changes`).
5. Чистое рабочее дерево после шага `rc=0` (для любой роли) — ни
   коммита, ни записи журнала этим механизмом.
6. `skills/coding-standards.md` несёт правило: ход разработчика
   заканчивается коммитом кода; незакоммиченный код коммитит сам
   пульт и записывает в журнал как дефект шага, а не как норму.
   Существующий запрет фоновых прогонов (раздел «Тесты») не
   дублируется.

## Критерии приёмки

AC-1. Шаг роли `developer` завершился с `rc=0` в обычном успешном пути
(не таймаут, не `rc≠0`, не отсутствие обязательного артефакта, не
обрыв stdout-пайпа) и рабочее дерево несёт незакоммиченные изменения
вне `tasks/<id>/` → оркестратор коммитит эти изменения тем же приёмом
и с теми же фильтрами мандата, что `commit_timeout_checkpoint`: только
роль `developer`, только догфуд-target, только если реально есть что
коммитить, тихая деградация без записи при отказе git.

AC-2. Сообщение созданного коммита — буквально `<id>: код закоммичен
пультом за роль developer — шаг завершён с незакоммиченным кодом`.

AC-3. При этом коммите пишется запись журнала с `actor=orchestrator`,
действием «код закоммичен пультом за роль» и `detail`, несущим список
закоммиченных файлов и число изменённых строк.

AC-4. Шаг роли `developer` с `rc=0` и чистым рабочим деревом (вне
`tasks/<id>/` изменений нет) — ни коммита этим механизмом, ни записи
журнала не появляется.

AC-5. Шаг роли без мандата кода (не `developer`) с `rc=0` и грязным
деревом вне `tasks/<id>/` — прежнее поведение сохранено: откат WIP вне
мандата, как до этой задачи.

AC-6. `skills/coding-standards.md` содержит правило «ход заканчивается
коммитом кода; незакоммиченный код пульт закоммитит сам и запишет в
журнал как дефект шага, не как норму», без дублирования существующего
запрета фоновых прогонов в разделе «Тесты».

## Оценка объёма и деление

Сработавший сигнал: «число затрагиваемых модулей/файлов» — в тексте
SPEC (guard считает по всему тексту, не только по frontmatter `zones:`)
упомянуто 5 путей вида `orchestrator/*.py`: два реальных (`orchestrator/
runner.py`, `orchestrator/checkpoint.py`) и три из раздела «Не входит»
(`orchestrator/fsm.py`, `orchestrator/pull.py`, `orchestrator/auto.py`),
названные явно, чтобы очертить границу задачи, а не как зона правки.

**Обоснование монолита.** Разрезать нечем: реальных зон правки — две
(`orchestrator/checkpoint.py` — новая функция-чекпоинт по образцу
`commit_timeout_checkpoint`; `orchestrator/runner.py` — одна точка
встройки, вызов этой функции в ветке `rc=0` без `pump.error`) плюс
текст `skills/coding-standards.md` и тесты. Функция чекпоинта без
вызова из `runner.py` не работает и не проверяется (нечего мержить как
самостоятельный кусок), вызов из `runner.py` без самой функции не
компилируется. Промежуточное состояние «код чекпоинта есть, вызова
нет» или «вызов есть, функции нет» неработоспособно и немержимо
отдельной частью — делить незачем, задача уже атомарна по существу
(один новый чекпоинт по готовому образцу трёх соседних функций того же
модуля).

## Не входит

- `orchestrator/fsm.py` — отказ перехода `in_dev -> verifying` по
  грязной копии остаётся второй линией защиты, не правится этой
  задачей.
- `orchestrator/pull.py`, `orchestrator/auto.py` — не затрагиваются.
- Класс «рабочие файлы роли в корне `tasks/<id>/` доезжают до main
  через `git add -A` чекпоинта» (копилка П1 11.09) — отдельная задача.
- Ослабление существующих тестов ради зелёной планки (уже запрещено
  `skills/conventions-core.md`) — ТЗ отдельно подчёркивает это для
  тестов requirement 4, здесь не переопределяется.
