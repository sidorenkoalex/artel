# PLAN: выход шага developer при грязном дереве — WIP-коммит кода пультом

## Подход

Новый чекпоинт `orchestrator/checkpoint.py::commit_success_checkpoint` —
по образцу трёх соседних WIP-чекпоинтов (`commit_timeout_checkpoint`/
`commit_abnormal_checkpoint`/`commit_pause_now_checkpoint`), но с двумя
отличиями, продиктованными AC-2/AC-3/AC-5:

1. Мандат — строго `developer`; роль без мандата кода не получает НИ
   отката (в отличие от `_discard_out_of_mandate_changes` у соседних
   трёх чекпоинтов), НИ коммита — функция для неё немедленно
   `return ""` без единого побочного эффекта (AC-5 требует именно
   отсутствие эффекта — «прежнее поведение» для обычного успешного пути
   и есть отсутствие эффекта, ни один из трёх аварийных чекпоинтов
   сегодня не срабатывает на `rc=0` без таймаута/провала/обрыва потока).
2. Сообщение коммита и действие журнала — буквальные строки, названные
   AC-2/AC-3 (`<id>: код закоммичен пультом за роль developer — шаг
   завершён с незакоммиченным кодом` / «код закоммичен пультом за
   роль»), не текст соседних чекпоинтов.

`detail` журнала (список файлов + число строк, AC-3) собирается новым
приватным хелпером `_staged_change_summary(wt, exclude)`: `git add -A`
+ `git reset -- exclude` (то же, что делает `_commit_worktree_change`
следом для самого коммита — вызовы идемпотентны, второй `add -A`/
`reset` не меняют уже приведённый в порядок индекс) + `git diff
--cached --numstat`, разобранный в список путей и сумму добавленных/
удалённых строк. Переиспользование существующей общей обвязки
`_commit_worktree_change` (мандат `developer`, `exclude=tasks/<id>`,
тихая деградация без git, `store.record_fixation` после коммита —
SPEC требование 1/«Материалы») без изменения её сигнатуры — три
существующих вызывающих места (`commit_timeout_checkpoint`/
`commit_abnormal_checkpoint`/`commit_pause_now_checkpoint`) и четвёртое
(`commit_pull_checkpoint`) не трогаются вовсе.

Точка встройки — `orchestrator/runner.py`, ветка `rc=0` без `pump.error`
(строки ~956-960): новый вызов `checkpoint.commit_success_checkpoint`
добавляется ПЕРЕД существующим `checkpoint.commit_step_artifacts` — тем
же порядком, что и у остальных трёх WIP-чекпоинтов (код сначала,
перенос `tasks/<id>/` в артефактную ветку потом): к моменту вызова
нового чекпоинта каталог `tasks/<id>/` на диске ещё материализован (его
уберёт `commit_step_artifacts` следующим шагом), поэтому `exclude`
обязателен и здесь, как у соседей.

`skills/coding-standards.md` — защищённый путь (AC-6, критерий manual
по решению Оператора на гейте SPEC 11.09): unified-дифф приложен ниже
в разделе «Покрытие требований», применяет Оператор; автотеста на этот
критерий нет.

## Влияние на систему

Новый чекпоинт использует ту же общую обвязку `_commit_worktree_change`,
что и три существующих WIP-чекпоинта, — не меняет её сигнатуру и
поведение, регрессии для существующих трёх чекпоинтов и для
`commit_pull_checkpoint` не создаёт (их тесты в
`tests/test_timeout_checkpoint.py`/`tests/test_pull.py` не трогаются).
Точка встройки в `runner.py` — только ветка `rc=0` без `pump.error`;
ветки таймаута/`rc!=0`/обрыва потока/отсутствия обязательного артефакта
не меняются (SPEC требование 1 явно исключает их). Гейт `fsm.py`
(отказ перехода `in_dev -> verifying` по грязной копии) остаётся второй
линией защиты, не правится — при штатной работе нового чекпоинта он
просто перестаёт срабатывать для основного класса инцидента (WIP код
developer), но продолжает ловить прочие причины грязной копии
(SPEC «Не входит»). Откатить — удалить вызов в `runner.py` и функцию в
`checkpoint.py`, поведение возвращается к состоянию до задачи.
`skills/coding-standards.md` — защищённый путь, правит только Оператор
по приложенному диффу; ничего не ослабляется — правило только уточняет
существующую практику (WIP-чекпоинты для аварийных путей уже
задокументированы кодом), не отменяет запрет фоновых прогонов.

## Риски
- Двойной вызов `git add -A`/`git reset -- exclude` (сначала в
  `_staged_change_summary`, потом внутри `_commit_worktree_change`) —
  цена нескольких лишних git-вызовов на шаг ради переиспользования
  существующей обвязки без изменения её сигнатуры; идемпотентность
  обеих команд делает это безопасным.
