# SPEC: поделённый родитель при killed — parent_task_id, добавки в status, RETRO «поделена», штатный исход канарейки

## Контекст
Решением Оператора 11.09 новое состояние FSM для поделённого родителя
пока не вводится (01M291MHKV снята), но `killed` сегодня участвует в
трёх автоматических решениях, и каждое трактует поделённого родителя
как обычную снятую задачу: `fsm_postmerge`/`snapshot.py` пишут ему
killed-RETRO с несуществующей «последней эскалацией»
(`retro.build_killed`), канарейка (`canary._kill_outcome_note`) видит
исход как «не сошлась» и запускает диагностику, а связь родитель →
подзадачи живёт только текстом в журнале и в TZ подзадачи — `status` её
не показывает. Задача устраняет эти три ложных следствия, не вводя
новое состояние FSM. Задача деления — 01M1SHJZCE0Y4DXAAWQ2W585A7.

## Требования

1. Колонка `parent_task_id` в таблице `tasks`: миграция в
   `orchestrator/schema.py::migrate` тем же приёмом, что и прежние
   добавленные колонки (`add_column(conn, "tasks", "parent_task_id",
   "TEXT")`). Заполняется в `orchestrator/catalog.py::spawn_subtask`
   через существующий `store.update_task(conn, task_id,
   parent_task_id=parent_id)` — без правки `orchestrator/store.py`
   (`update_task` уже общий и работает с любой известной схеме
   колонкой). «Родитель поделён» определяется наличием хотя бы одной
   задачи с `parent_task_id = <id>` при состоянии родителя `killed` —
   вычисляется каждый раз заново по данным `tasks`, отдельный флаг на
   строке родителя не заводится.
2. `orchestrator/catalog.py::cmd_status`: строка родителя с найденными
   подзадачами несёт добавку `[поделена: <id1>, <id2>, ...]` (идентификаторы
   всех задач с `parent_task_id = <id родителя>`, в порядке возрастания
   id — тот же порядок, что и `store.all_tasks`); строка подзадачи несёт
   добавку `[часть N/M родителя <id>]`, где `<id>` — id родителя, `M` —
   общее число подзадач этого родителя, `N` — порядковый номер этой
   подзадачи по возрастанию id среди подзадач того же родителя. Обе
   добавки — ДОБАВКОЙ в конец строки, тем же приёмом, что и
   `_zone_wait_suffix`/`_lease_holder_suffix` (не заменяют существующие
   колонки строки). Задачи без связи `parent_task_id` (ни родитель, ни
   подзадача) строку не меняют.
3. `orchestrator/retro.py::build_killed`: если у задачи есть подзадачи
   (`parent_task_id = <id задачи>`), RETRO строится в виде «поделена» —
   вместо разделов «Итог: killed — причина: ...» и цитаты последней
   эскалации (`_escalations_block(steps, full=True)`) документ несёт:
   заголовок и суть по тому же образцу, что и обычный `build_killed`
   (`_gist`/`context_line`), явную пометку итога как деления (не
   «killed»/снятие), список подзадач — id, название и состояние КАЖДОЙ
   на момент генерации RETRO, и блок стоимости родителя ДО деления
   (`_cost_block` по данным родителя, тем же вызовом, что и сегодня).
   Раздел последней эскалации в этом случае не включается. Для задачи
   БЕЗ подзадач `build_killed` не меняется ни по содержимому, ни по
   порядку разделов.
4. `orchestrator/canary.py::_kill_outcome_note`: для родителя, у
   которого есть подзадачи (`parent_task_id = <id родителя>`),
   возвращает «поделена» вместо «не сошлась»/«штатно». Исход «поделена»
   считается штатным наравне со «штатно» — код, решающий, нужна ли
   диагностика по исходу kill (`normal_outcome`/`_needs_diagnostics` в
   `cmd_canary`), не запускает диагностику ни при «штатно», ни при
   «поделена». В отчёте прогона (`_task_metrics`/вывод `cmd_canary`)
   исход «поделена» виден отдельной строкой, отличимой от «штатно» и от
   «не сошлась: ...».
5. Ни одно из требований 1–4 не вводит новое состояние FSM и не меняет
   переходы `orchestrator/fsm.py`/`orchestrator/fsm_postmerge.py`/
   `orchestrator/snapshot.py` — эти модули получают верный текст
   RETRO/классификацию исключительно через изменённые `retro.py`/
   `canary.py`, без собственной правки.

## Критерии приёмки

AC-1. Тест на `catalog.spawn_subtask`: после вызова у созданной
подзадачи в БД `parent_task_id` равен id родителя (мутация «колонка не
заполняется» — тест красный).

AC-2. Тест на `cmd_status`: вывод для родителя с двумя подзадачами
содержит `[поделена: <id1>, <id2>]` в строке родителя и `[часть 1/2
родителя <id родителя>]`/`[часть 2/2 родителя <id родителя>]` в строках
подзадач соответственно их порядку по возрастанию id.

AC-3. Тест на `retro.build_killed` для родителя с подзадачами: результат
не содержит раздела о последней эскалации (не содержит подстроку
«Эскалации:» из `_escalations_block(full=True)`) и содержит список
подзадач с их id, названиями и состояниями на момент вызова.

AC-4. Тест на `retro.build_killed` для обычной снятой задачи (без
подзадач): результат не меняется по сравнению с текущим поведением
(включая раздел последней эскалации).

AC-5. Тест на `canary._kill_outcome_note`: для родителя с подзадачами
функция возвращает «поделена»; тест на `cmd_canary` (или на функцию,
решающую нужна ли диагностика по исходу kill): исход «поделена» не
считается сбоем — диагностика не запускается, как и при «штатно».

AC-6. Существующие тесты деления (`tests/test_catalog_spawn_subtask.py`
и приёмочные тесты 01M1SHJZCE0Y4DXAAWQ2W585A7), `tests/test_retro.py`,
`tests/test_canary.py`, тесты `status` (`tests/test_catalog_status_log.py`
и смежные) остаются зелёными без ослабления и без снятия проверок.

## Оценка объёма и деление

Сработавшие сигналы: «число затрагиваемых модулей/файлов» (текст SPEC
упоминает 9 путей вида `orchestrator/<файл>.py` — но 5 из них
(`orchestrator/store.py`, `orchestrator/fsm.py`,
`orchestrator/fsm_postmerge.py`, `orchestrator/snapshot.py`,
`scripts/guard.py`) перечислены ИМЕННО в разделе «Не входит»: это модули,
которые задача по прямому требованию Оператора (ТЗ) НЕ трогает — их
упоминание нужно, чтобы явно зафиксировать границу, не чтобы описать
объём правки; реальная зона — 4 файла кода из frontmatter `zones:`);
«затронут инвариантный механизм» (сигнал сработал на том же
упоминании `scripts/guard.py` в границе «не входит», а не на правке
guard — guard в этой задаче не меняется).

Обоснование монолита: разрезать нечего — задача правит ОДИН признак
(«у родителя в `killed` есть подзадачи с `parent_task_id`»,
требование 1) и три места, которые ЧИТАЮТ этот признак каждое по
отдельности (`status`, `retro.build_killed`, `canary._kill_outcome_note`
— требования 2–4). Зоны каждого требования не пересекаются по файлам
(2 → `catalog.py`, 3 → `retro.py`, 4 → `canary.py`), но все три зависят
от ОДНОЙ миграции требования 1 (`schema.py` + заполнение колонки в
`catalog.spawn_subtask`) — часть без неё не имеет данных для проверки
условия «поделён» и не мержима как самостоятельно полезное изменение
(молчаливо не покажет/не отличит поделённого родителя, то есть
оставит ровно тот баг, который ТЗ просит исправить, только по одному
из трёх мест вместо всех). Промежуточное состояние «признак введён,
но только один из трёх потребителей его использует» не запрошено ТЗ и
не сокращает риск: два оставшихся потребителя всё так же продолжают
ложно трактовать поделённого родителя как снятого — именно то, что
Оператор просит убрать целиком (ТЗ, «Факты»). Задача и так на нижней
границе объёма — 4 файла кода, 6 критериев приёмки, потолок $25 (низ
диапазона типовой задачи) — дробление её на подзадачи только удвоило
бы стоимость ревью/интеграции без снижения риска.
