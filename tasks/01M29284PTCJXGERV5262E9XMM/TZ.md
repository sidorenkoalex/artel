# ТЗ: поделённый родитель при killed: parent_task_id в БД, добавки в status, RETRO «поделена» вместо снятия, штатный исход канарейки

Источник: решение Оператора 11.09 после первого живого деления
(01M28VZ8Q1 «единая очередь мержа» → 01M291EJMA…, 01M291EPQ2…): новое
состояние FSM для поделённого родителя пока не вводить (задача
01M291MHKV снята), но убрать ложные автоматические следствия того, что
родитель переводится в `killed` (`fsm._spawn_division_subtasks`).
Задача деления — 01M1SHJZCE0Y4DXAAWQ2W585A7.

Факты: `killed` участвует в трёх автоматических решениях, и каждое
трактует поделённого родителя как снятую задачу:
- `fsm_postmerge` при следующем мерже любой задачи собирает `killed`
  без RETRO как «долги» и пишет killed-RETRO через `retro.build_killed`
  — родитель получит RETRO снятой задачи с цитатой «последней
  эскалации», которой не было; тот же текст пишет снапшот закрытия
  (`snapshot.py`, исход `killed`).
- Канарейка (`canary._kill_outcome_note`) классифицирует исход `killed`
  по причине снятия; всё, что не «штатно», запускает диагностику —
  поделённая канареечная задача выглядит как сбой прогона.
- Связь родитель → подзадачи живёт только в тексте журнала «поделена
  на: …» и в строке-ссылке TZ подзадачи; `status` показывает родителя
  как обычную снятую задачу, подзадачи — без указания родителя.

Требуется:
1. Связь в БД: колонка `parent_task_id` в `tasks` (миграция в `orchestrator/schema.py` тем же приёмом, что прежние колонки), заполняется в `catalog.spawn_subtask` через существующий `store.update_task` (без правки `orchestrator/store.py` — файл занят); «родитель поделён» определяется наличием подзадач с `parent_task_id = <id>` при состоянии `killed`, отдельный флаг на родителе не вводится.
2. `status`: родитель с подзадачами показывается добавкой «[поделена: <id1>, <id2>]», подзадача — добавкой «[часть N/M родителя <id>]» (N — порядок подраздела деления, M — число подзадач); обе добавки в `catalog.cmd_status` по образцу «ждёт зоны».
3. RETRO поделённого родителя: `retro.build_killed` для задачи с подзадачами строит RETRO вида «поделена» — суть, список подзадач с названиями и состояниями на момент генерации, стоимость аналитики до деления — вместо разделов о снятии и последней эскалации; тем самым и долг `fsm_postmerge`, и снапшот закрытия получают правильный текст без правки этих модулей.
4. Канарейка: `canary._kill_outcome_note` для родителя с подзадачами возвращает «поделена», и этот исход считается штатным наравне со «штатно» (диагностика не запускается), в отчёте прогона исход виден отдельной строкой.
5. Тесты: `spawn_subtask` заполняет `parent_task_id` (мутация «колонка не заполняется» — красный); `status` показывает обе добавки; `build_killed` для родителя с подзадачами не содержит раздела о последней эскалации и содержит список подзадач; `build_killed` для обычной снятой задачи не меняется; `_kill_outcome_note` для родителя даёт «поделена» и не считается сбоем; существующие тесты деления (01M1SHJZCE), retro, canary, status — без ослабления.

Зоны: orchestrator/catalog.py, orchestrator/schema.py, orchestrator/retro.py, orchestrator/canary.py, tests/.

Условие старта: сразу — зоны свободны; `orchestrator/catalog.py` входит и в зоны части 2 очереди мержа (01M291EPQ2), которая стартует после части 1 — кто раньше, тот держит.

Не входит: новое состояние FSM (отложено решением Оператора 11.09); `orchestrator/store.py`, `orchestrator/fsm.py`, `orchestrator/fsm_postmerge.py`, `orchestrator/snapshot.py`; агрегация бюджета подзадач в родителя; изменение формата секции «## Деление» и guard.
