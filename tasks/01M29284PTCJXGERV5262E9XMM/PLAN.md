# PLAN: поделённый родитель при killed — parent_task_id, добавки в status, RETRO «поделена», штатный исход канарейки

## Подход

Один признак («у задачи в `killed` есть подзадачи с `parent_task_id`»)
и три независимых потребителя. Реализация идёт снизу вверх:

1. Миграция `parent_task_id` в `orchestrator/schema.py::migrate` —
   `add_column(conn, "tasks", "parent_task_id", "TEXT")`, тем же приёмом,
   что и соседние добавленные колонки. Заполнение — в
   `orchestrator/catalog.py::spawn_subtask` вызовом уже существующего
   `store.update_task(conn, task_id, parent_task_id=parent_id)`,
   `orchestrator/store.py` не трогается.

2. Каждый из трёх потребителей (`catalog.cmd_status`, `retro.build_killed`,
   `canary._kill_outcome_note`) сам вычисляет «есть подзадачи» фильтрацией
   уже существующего `store.all_tasks(conn)` (по возрастанию id) по
   `parent_task_id == <id>` — без новой сырой SQL вне `store.py` (принцип
   «SQL живёт только в store.py», ADR-0003 3ж, соблюдён: используется
   единственная существующая функция чтения, не пишется новый запрос).
   Общий вычислительный код не выносится в отдельный модуль — три
   потребителя мал'о пересекаются по контексту использования (список id
   в `status`, id+title+state в RETRO, только факт непустоты в canary),
   каждому нужен свой мини-срез тех же строк; дублирование — 2-4 строки
   list comprehension на файл, тот же масштаб, что у соседних
   `_lease_holder_suffix`/`_zone_wait_suffix` в `catalog.py`.

3. `cmd_status`: добавка «[поделена: ...]»/«[часть N/M родителя ...]»
   тем же приёмом, что `_lease_holder_suffix` — новая функция
   `_division_suffix(rows, r)`, вызываемая с уже прочитанным `rows =
   store.all_tasks(conn)` (без доп. запроса на строку).

4. `retro.build_killed`: если `_subtask_rows(conn, task_id)` непусто —
   отдельная ветка сборки документа (заголовок/суть как обычно, явная
   пометка «Итог: поделена на подзадачи», список подзадач id/title/state,
   `_cost_block` по данным родителя ДО деления, без
   `_escalations_block`). Ветка без подзадач не меняется.

5. `canary._kill_outcome_note`: сигнатура расширяется `(conn, task_id,
   steps)` — первой проверяется наличие подзадач (тогда сразу
   «поделена»), иначе прежняя логика по `steps`. Единственный вызыватель
   — `_task_metrics` — передаёт `conn`/`task_id` явно.
   `_run_one_task`: `normal_outcome = metrics["kill_note"] in ("штатно",
   "поделена")`. Печать отдельной строкой исхода уже штатно устроена
   (`outcome_note` в выводе `_run_one_task`) — правки печати не требуется,
   значение `kill_note` само по себе отличимо.

## Шаги

1. Миграция `parent_task_id` (`schema.py`) + заполнение в
   `catalog.spawn_subtask`; юнит-тест AC-1.
2. Добавка в `cmd_status` (`catalog.py`); юнит-тесты AC-2 (три сценария:
   родитель, обе подзадачи, несвязанная задача).
3. Ветка «поделена» в `retro.build_killed`; юнит-тесты AC-3 (нет раздела
   эскалации + список подзадач) и AC-4 (регресс — обычный killed не
   меняется).
4. `canary._kill_outcome_note`/`_task_metrics`/`_run_one_task`; юнит-тесты
   AC-5 (три сценария: «поделена», штатное множество без диагностики,
   контрольная ветка «не сошлась» всё ещё требует диагностику).
5. Прогон затронутых модулей тестов (`test_catalog_spawn_subtask`,
   `test_catalog_status_log`, `test_retro`, `test_canary`) + guard.

Один шаг = вся задача укладывается в один MR (4 файла кода, соседние по
одному признаку, дробить по AC-1..AC-6 нет смысла — каждый следующий
потребитель зависит от миграции первого шага и мержим только вместе).

## Влияние на систему

- `orchestrator/fsm.py`/`fsm_postmerge.py`/`snapshot.py` не правятся и
  не должны править: они получают верный текст исключительно через
  изменённые `retro.build_killed`/`canary._kill_outcome_note` — сама
  задача это не проверяет прогоном (не входит в зону), но по контракту
  `retro.build_killed(conn, task_id)` их сигнатура и место вызова не
  меняются, оба модуля видят новый текст автоматически.
- Существующий путь `build_killed` для задачи БЕЗ подзадач (подавляющее
  большинство killed-задач сегодня и всегда) должен остаться байт-в-байт
  прежним — это отдельный AC-4, регрессионный барьер.
- `_kill_outcome_note` меняет сигнатуру (добавляются `conn`/`task_id`) —
  единственный вызыватель внутри модуля (`_task_metrics`) правится тем
  же коммитом; внешних вызывателей нет (`grep` по репозиторию).
- Ослабления гейтов/тестов/лимитов нет: `_needs_diagnostics` по-прежнему
  требует диагностику для любого исхода вне явного множества {«штатно»,
  «поделена»} — AC-5 контрольный тест это фиксирует.
- Откат: три независимые правки, каждая обратима поодиночке (кроме того,
  что 2-4 зависят от колонки шага 1) простым git revert коммита.

## Риски

- Пропущенное место, читающее `_kill_outcome_note`/`build_killed` в
  обход `_task_metrics`/публичного API — проверено `grep` по репозиторию
  перед сдачей (единственный вызыватель каждой функции — тот, что
  изменён).
