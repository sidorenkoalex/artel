# PLAN: Worktree-норма: рабочая поверхность на задачу

## Подход

Новый модуль `orchestrator/workspace.py` инкапсулирует всю worktree-механику
(создание, проверка ветки, уборка) — по образцу `gitcmd`/`lease`: одна
точка правды, а не размазанная по `runner`/`cleanup`/`fsm` логика.

- `config.WORKTREES = ROOT / ".artel" / "worktrees"` — стандартное место
  (новая независимая константа, как `TASKS`/`DB`/`LOGS`; патчится в
  песочницах тем же приёмом).
- `workspace.ensure(task_id, branch)` — идемпотентно создаёт worktree на
  ветке задачи (AC-1, AC-2): ветки ещё нет в git — заводит её от `main`
  тем же действием (`git worktree add -b`); уже есть — просто
  подключает. Идемпотентность — по факту регистрации в
  `git worktree list --porcelain`, не по существованию каталога на диске.
  Явного `mkdir` нет: `git worktree add` сам создаёт нужные каталоги
  (проверено вручную) — так операция целиком остаётся под `gitcmd.git`,
  единственной точкой мокинга, которой уже пользуется весь пакет; лишнего
  сырого `Path.mkdir` в реальном дереве пульта, если тест не подменил
  `config.WORKTREES`, тем самым не возникает.
- Свежесозданный (новой веткой) worktree получает копию незакоммиченного
  `tasks/<id>/` из главной копии (`_seed_uncommitted_artifacts`): `cmd_new`
  по-прежнему пишет SPEC.md/TZ.md прямо на диск главной копии, некоммичено
  («Не входит» — cmd_new не меняем). До этой задачи роль сама делала
  `git checkout -b` В ТОЙ ЖЕ рабочей копии, где эти файлы уже лежали
  untracked, и checkout их не трогал; отдельный worktree этого не
  наследует — без явного переноса первый агентный шаг (analyst) не увидел
  бы TZ.md вовсе. Копия — только когда ветка реально новая: если она уже
  существует, нужное содержимое уже закоммичено предыдущим шагом.
- `workspace.on_task_branch(task_id, branch)` — True/False/`None`
  (не заведён — сверять не с чем) для гейта AC-8 (агентный шаг).
- `workspace.remove(task_id)` — убирает worktree (`kill`/`done`, AC-5/6);
  `--force`, чтобы неснесённый WIP не мешал kill switch'у сработать
  всегда (тот же принцип, что и у `cleanup.cleanup_killed_task`).
- `workspace.cmd_workspace(task_id)` — CLI `workspace <id>` (AC-1, AC-2).

`runner.role_cwd` для догфуда вызывает `workspace.ensure` вместо возврата
`config.ROOT` (требование 2): агентный шаг получает cwd своего worktree,
ROOT не трогается. `runner._cmd_run` добавляет предварительную сверку
(требование 3, AC-8, сценарий 1): worktree уже существует, но стоит не на
своей ветке — отказ до старта агента, без попытки самому её починить.

`fsm._cmd_approve` (`merge_gate`) добавляет симметричную сверку для
рабочей поверхности оркестратора (требование 3-4, AC-8, сценарий 2):
главная копия не на `main` — отказ вместо merge из чужой ветки; явный шаг
`git checkout main` внутри цикла merge остаётся нетронутым (нужен
неослабляемому `test_invariants.MergeOnlyFromMergeGateTest
.test_merge_gate_approve_is_that_path`, который проверяет порядок
`checkout` → `merge` в списке git-подкоманд его песочницы-заглушки —
там `current_branch()` вырожденно пустой, сверка там пропускается тем же
приёмом деградации, что и у `gitcmd.on_foreign_branch`). После успешного
`done` — `workspace.remove` (требование 5, AC-6). `cleanup.cmd_kill`
получает тот же вызов перед уборкой каталога/ветки — порядок важен:
ветку с `-D` нельзя удалить, пока её держит worktree (требование 5, AC-5).

`doctor._orphan_worktrees` берёт список worktree через
`workspace.registered_paths()` вместо своего дублирующего парсинга
porcelain и классифицирует запись как легитимную только если она лежит
ровно в `config.WORKTREES/<id>` и `<id>` есть в БД (требование 6, AC-9).

**Побочная находка, тоже в зоне требования 2**: `orchestrator/acceptance.py`
`run`/`summary` до этой задачи читали `tasks/<id>/acceptance_tests` с
диска ГЛАВНОЙ КОПИИ (`config.TASKS/<id>`), полагаясь на то, что к моменту
гейта `review → acceptance` главная копия ЧАСТО (по факту прежнего
бага) оказывалась переключена на ветку задачи — то самое поведение,
которое эта задача устраняет. После неё главная копия остаётся на `main`
всегда, и без правки `_cmd_advance` молча решал бы «acceptance_tests/ нет»
для КАЖДОЙ немерженной задачи — то есть тихо отключил бы гейт T023
(залоченные приёмочные тесты просто перестали бы запускаться). Правка:
`_cmd_advance` (`review`, ветка `approved`) считает путь тестов от
worktree задачи, если она заведена и стоит на своей ветке
(`workspace.on_task_branch(...) is True`), иначе — прежний путь от диска
главной копии (легаси-песочницы без реального git). Своего теста этой
находке нет ни в одном локальном AC — добавляю юнит-тест
(`tests/test_workspace.py`) отдельно от локальных приёмочных.

**Осознанно НЕ трогаю** (см. «Риски»): `runner.commit_timeout_checkpoint`
по-прежнему коммитит в главную копию (`config.ROOT`), не в worktree.

## Шаги

1. `config.py`: константа `WORKTREES`. `tests/sandbox.py`:
   `ALL_CONFIG_ATTRS` + `_patched_path` заводят десятый патчуемый путь —
   иначе новый код молча трогал бы `.artel/worktrees/` реального пульта
   в песочницах, которые патчат `config` не через `TmpRootTest` по
   умолчанию.
2. Новый `orchestrator/workspace.py`: `path`, `registered_paths`,
   `ensure`, `on_task_branch`, `remove`, `cmd_workspace` + юнит-тесты
   `tests/test_workspace.py`.
3. `orchestrator/runner.py`: `role_cwd` — worktree вместо `config.ROOT`
   для догфуда; `_cmd_run` — сверка чужой ветки worktree (AC-8);
   мисси-тексты трёх ролей — убрать «создай ветку от main» (гарантирован
   инфраструктурой, роли это больше не делают сами).
4. `orchestrator/artel.py`: команда `workspace <id>`.
5. `orchestrator/cleanup.py`: `cleanup_killed_task` убирает worktree
   перед веткой/каталогом (AC-5).
6. `orchestrator/fsm.py`: сверка «главная копия не на main» в
   `merge_gate` (AC-8, сценарий 2); `workspace.remove` после `done`
   (AC-6); worktree-aware путь acceptance-тестов в `review` (побочная
   находка выше).
7. `orchestrator/doctor.py`: `_orphan_worktrees` — легитимный per-task
   worktree не сирота (AC-9).
8. Точечные патчи безопасности существующих песочниц с настоящим git
   (`tests/test_git_fixation.py::RealPultGitTest`,
   `tests/test_invariants.py::KillKeepsMainIntactTest`,
   `tests/test_kill_cleanup.py::TmpRepoTest`,
   `tests/test_multitarget_invariants.py::_MultitargetInvariantsTmpRootTest`)
   — добавить `WORKTREES` в патчуемые атрибуты; без него код теперь
   реально пишет worktree РЕАЛЬНОГО репозитория (см. «Риски» T037/AC-2).
9. `tests/test_multitarget_invariants.py::test_dogfood_cwd_is_root` —
   обновить ожидание (cwd = worktree задачи, не `config.ROOT`): контроль,
   а не сам инвариант 21 (тот — про внешний target, не тронут).
10. Прогон `python3 scripts/guard.py` по своим артефактам, полный
    набор тестов, коммит.

## Влияние на систему

- Существующий тест `test_multitarget_invariants
  .ExternalWorkspaceIsolationTest.test_dogfood_cwd_is_root` — «контроль»
  (по собственному докстрингу), не сам инвариант 21 (тот — «рабочий
  каталог роли ВНЕШНЕГО target», требование 2 T020, не тронут и
  по-прежнему проходит тремя другими тестами класса). Обновляю его
  ожидание на новое, СПЕЦ-предписанное поведение (AC-3 этой задачи, тот
  же факт кодирует и залоченный `tasks/T045/acceptance_tests/
  test_ac3_ac4_agent_step_worktree.py`) — это не ослабление проверки
  (assert остаётся точным, просто на другое значение), а починка
  «контроля» под намеренно изменённую Оператором норму (roadmap
  «Worktree-норма сессий», решение 27.08).
- `test_invariants.MergeOnlyFromMergeGateTest
  .test_merge_gate_approve_is_that_path` (инвариант, ADR-0002) —
  НЕ меняю: явный шаг `git checkout main` в цикле merge остаётся, новая
  сверка «главная копия не на main» встаёт ПЕРЕД циклом и не заменяет
  его — тест по-прежнему видит `checkout` перед `merge`.
- Четыре песочницы с настоящим git получают патч `WORKTREES` (шаг 8) —
  без него `git worktree add`/`remove` из новой сверки писали бы в
  `.artel/worktrees/` РЕАЛЬНОГО репозитория пульта, а не в песочницу
  (тот же класс риска, что T037 закрывал для остальных девяти путей
  `config`). Другие псочницы с `runner.cmd_run` полностью подменяют
  `gitcmd.git` функцией-заглушкой (`fake_git`/`FakeGit`/`SpyRun`) —
  подмена на уровне функции исключает любой реальный вызов независимо
  от того, патчен ли `WORKTREES`, поэтому не трогаю их (минимум правки).
- `orchestrator/acceptance.py` не меняется — правка на стороне
  `fsm._cmd_advance` (см. «Подход», побочная находка): решение не
  дублирует ветко-корректные примитивы (`workspace.on_task_branch`,
  уже существующий), только выбирает каталог для уже существующих
  `acceptance.run`/`summary`.
- Не трогаю `runner.commit_timeout_checkpoint` (см. «Риски») —
  сознательный компромисс объёма, не пропущенный случай.
- Три мисси-текста ролей (analyst/test_author/developer) лишились шага
  «создай ветку от main» — тексту такому вреда нет (сама роль и раньше
  просто не находила бы, что делать, если ветка уже есть), а инфраструктура
  теперь гарантирует ветку/worktree до старта агента; ни один тест не
  проверяет буквальный текст мисси.
- Откат: весь механизм — новый модуль плюс точечные правки со своей
  git-историей; откат — реверт этого коммита (никаких необратимых
  миграций схемы БД).

## Риски

- `runner.commit_timeout_checkpoint` по-прежнему коммитит WIP в главную
  копию (`config.ROOT`), а не в worktree задачи, где реально работал
  агент: после этой задачи чекпоинт при таймауте для догфуда — тихий
  no-op (WIP в worktree остаётся некоммиченным, `check_integrity`
  следующего `run` уводит задачу в `escalated`, как это было ДО T041).
  Это деградация автоматизации, не порча данных и не новый вектор
  относительно состояния ДО T041 — но исправление требует переписать
  `tests/test_timeout_checkpoint.py` (сборка WIP теперь должна идти в
  worktree, не в ROOT) отдельной, полноценно протестированной правкой.
  Вне зоны T045 (не в критериях приёмки, не в «не входит» — честно
  называю здесь). Кандидат на быстрый фоллоу-ап.
- Приёмочные тесты T045 (залоченные) не проверяют семантику копии
  незакоммиченных артефактов в свежий worktree (`_seed_uncommitted_
  artifacts`) — она нужна для того, чтобы analyst реально видел
  TZ.md/SPEC.md, лежащие некоммичено в главной копии после `cmd_new`
  (иначе первый агентный шаг новой задачи буквально не находил бы файл,
  который должен прочитать). Покрыта отдельным юнит-тестом.
