# SPEC: Этап 3 ADR-0021, часть 1 из 3 — профиль тестов проекта и проверки тестов на repo_context

## Контекст
Проверки тестов пункта 8 ADR-0021 (неослабление тестов, «Ловит мутацию»,
долгоживущие файлы, строки группы, перечень сумм) сегодня включаются
сравнением `target` с `config.DEFAULT_TARGET` или признаком
`repo_context.is_artel`. Значения, зависящие от языка, зашиты в код:
команда pytest (`orchestrator/acceptance.py::_pytest_command`), область
неослабления `tests/**/*.py` (`orchestrator/advance_gates/mandate.py::in_weakening_scope`),
область заявки мутации `tests/test_*.py` верхнего уровня
(`orchestrator/advance_gates/review.py` ~224-226), префикс долгоживущего
файла `tests/test_<id>_` (`scripts/guard.py::long_lived_path_prefix`).
Для внешнего проекта эти проверки молча не выполняются. Прогон планки
артели, когда рабочая копия задачи не на её ветке, идёт в главной копии
пульта (`orchestrator/advance_gates/tests_writing.py:199`,
`orchestrator/advance_gates/acceptance.py:248`) и проверяет код пина, а не
код задачи. ADR-0021 пп. 8, 9 требует профиль тестов проекта в его записи
`targets.yaml` и проверки, которые смотрят на репозиторий проекта через
`repo_context`. Номера строк даны по пину 6eb98eff. После подтяжки `main`
с мержем задачи 01M45FJD46BX45VHC36S4VS9QN (она меняет
`orchestrator/advance_gates/test_integrity.py`) они сдвинутся. Переводится
уже изменённая версия гейта.

## Требования

1. **Профиль тестов проекта — поле `test_profile` записи `targets.yaml`.**
   Поле необязательно: запись без него описывает проект без профиля.
   Разбор и проверку выполняет `orchestrator/targets.py`. Значение поля —
   вложенное отображение (подмножество YAML, которое разбирает
   `orchestrator/yamlmini.py`) с подполями:

   | Подполе | Вид | Смысл | Значение у артели |
   |---|---|---|---|
   | `command` | потоковый список строк, непустой | начало команды прогона тестов; пути тестов и флаги пульта (без кеша, таймаут теста) добавляет пульт; первый элемент `python3` означает интерпретатор venv пульта (`stack.pytest_python_executable()`) | `[python3, -m, pytest]` |
   | `long_lived_dir` | непустая строка, относительный путь каталога | каталог долгоживущих тестов | `tests` |
   | `long_lived_name` | непустая строка, содержит `<id>` и `<name>` | шаблон имени долгоживущего файла; `<id>` — полный id задачи в нижнем регистре | `test_<id>_<name>.py` |
   | `weakening_scope` | потоковый список масок, непустой | область гейта неослабления тестов | `[tests/**/*.py]` |
   | `mutation_claim_scope` | потоковый список масок, непустой | область заявки «Ловит мутацию» | `[tests/test_*.py]` |
   | `report` | строка, допустимо только `junit-xml` | формат отчёта прогона | `junit-xml` |
   | `install` | потоковый список строк, может быть пустым | команда установки зависимостей | `[]` |

   В масках `*` — любые символы внутри одного сегмента пути, `**` — любое
   число сегментов, включая ноль. Префикс долгоживущего файла —
   `<long_lived_dir>/` плюс часть `long_lived_name` до `<name>`, где `<id>`
   подставлен. Отсутствие обязательного подполя, неверный вид значения,
   `report` вне допустимого, шаблон без `<id>` или `<name>`, неизвестное
   подполе — отказ `TargetsError`. Причина называет поле `test_profile` и
   подполе. Поля `report` и `install` описываются и проверяются, но
   пультом не исполняются.

2. **Профиль доступен проверкам через `repo_context`.** Это функция или
   поле контекста рядом с `resolve`, выбор за PLAN. Ответ различает три
   исхода: профиль есть (разобранные значения), профиля нет (у записи нет
   поля), профиль не прочитан (файл или запись не годны, причина
   названа). Профиль артели берётся из её записи `targets.yaml`, как у
   любого проекта. Значения из «Контекста» (команда pytest, область
   неослабления, область заявки мутации, префикс долгоживущего файла)
   проверки берут из профиля проекта. В коде проверок эти значения не
   зашиты.

3. **Проект без профиля работает только с разовыми тестами.** Проверки,
   зависящие от языка, у него не включаются: неослабление (переход,
   раздел изменённых утверждений пакета ревью, шаг гейта мержа), заявка
   мутации, долгоживущие файлы, строки группы, перечень сумм. Каждый
   пропуск пишет в журнал задачи запись: какая проверка не выполняется и
   почему (у проекта `<имя>` нет `test_profile` в `targets.yaml`). Молча
   не отключается ничего. Планку такого проекта пульт прогоняет своей
   командой, как сегодня у внешнего проекта.

4. **Для артели нет профиля — отказ, а не отключение (fail-closed,
   ADR-0002).** Если у записи артели нет `test_profile`, профиль не
   разбирается или `targets.yaml` не читается, переход, на котором
   работает проверка из таблицы требования 5, отклоняется. То же
   относится к `approve` гейта мержа и к команде `amend-tests`. Причина
   называет `targets.yaml` и поле. Пакет ревью без профиля артели не
   собирается, шаг ревьювера отказывает с той же причиной. Гейты
   целостности тестов пульта не отключаются ни в одном месте.

5. **Проверки тестов исполняются для любого проекта с разрешённым
   контекстом.** Они работают в клоне и рабочей копии задачи из
   `repo_context`. Все развилки по `config.DEFAULT_TARGET` и
   `repo_context.is_artel` в местах таблицы удаляются, жёсткий аргумент
   `config.DEFAULT_TARGET` вызова `workspace.on_task_branch` на
   `orchestrator/advance_gates/tests_writing.py:383` — тоже. Отбор
   канареечной задачи (`is_canary`) остаётся как есть (ANSWER-1, вопрос

## Критерии приёмки

AC-1. `targets.check` пропускает запись с полем `test_profile`, где
заданы все подполя таблицы требования 1 верного вида. Запись без поля
`test_profile` тоже проходит. Каждый дефект поля даёт `TargetsError`,
причина которого называет `test_profile` и подполе: нет обязательного
подполя, неверный вид значения, `report` не `junit-xml`, в
`long_lived_name` нет `<id>` или `<name>`, есть неизвестное подполе.

AC-2. Профиль проекта читается через `repo_context` и различает три
исхода. Для записи с `test_profile` ответ несёт значения из
`targets.yaml`. Для записи без поля ответ — «профиля нет». Для
неразборчивого поля или нечитаемого `targets.yaml` ответ — «не прочитан»
с причиной. Профиль артели читается из её записи `targets.yaml`.

AC-3. Профиль со значениями записи `artel` из таблицы требования 1 даёт
для задачи артели прежнее поведение. Команда прогона планки совпадает с
нынешней (`stack.pytest_python_executable()`, `-m pytest`, без кеша,
`pytest-timeout` с прежним таймаутом). Область неослабления совпадает с
нынешней на путях `tests/a.py`, `tests/x/y/test_b.py` (входят),
`tests/data.json`, `orchestrator/a.py` (не входят). Область заявки мутации
содержит `tests/test_a.py` и не содержит `tests/sub/test_a.py` и
`tests/helper.py`. Префикс долгоживущего файла задачи —
`tests/test_<id в нижнем регистре>_`.

AC-4. Задача артели, у записи которой нет `test_profile` (а также задача
с неразборчивым профилем или нечитаемым `targets.yaml`), получает отказ
с причиной, называющей `targets.yaml` и поле: на переходе `in_dev →
verifying`, на выходе из `tests_writing`, на прогоне приёмки, на `approve`
гейта мержа и в команде `amend-tests`. Шаг ревьювера такой задачи
отказывает, пакет ревью не собирается. Ни одна проверка тестов не
пропущена.

AC-5. Задача внешнего проекта без `test_profile` проходит переходы без
проверок, зависящих от языка. По каждой пропущенной проверке из таблицы
требования 5 в журнале задачи есть запись с названием проверки и
причиной «нет `test_profile`». Планка такой задачи прогоняется командой
пульта в её рабочей копии.

AC-6. Задача внешнего проекта с `test_profile` получает отказ на переходе
`in_dev → verifying`, если ветка задачи в клоне проекта ослабляет тест в
области `weakening_scope` её профиля. Тот же дифф вне области отказа не
даёт. Пакет ревью такой задачи несёт раздел изменённых утверждений
тестов. Шаг неослабления гейта мержа исполняется в рабочей копии мержа
клона проекта.

AC-7. Задача внешнего проекта с `test_profile` получает отказ заявки
мутации, если тестовый файл из `mutation_claim_scope` её профиля в ветке
задачи несёт метод без заявки «Ловит мутацию». Файл вне области заявки не
требует.

AC-8. У задачи внешнего проекта с `test_profile` на выходе из
`tests_writing` проверяются долгоживущие файлы по каталогу и шаблону
имени её профиля и строки группы планки, а перечень сумм записывается.
На `approve` гейта мержа сверяются лок планки и перечень. `amend-tests`
проверяет строки группы правки.

AC-9. Задача, чей контекст проекта не разрешён (`repo_context.resolve`
вернул `None`), получает отказ с причиной «контекст проекта не разрешён»
на каждом переходе, `approve` и команде из таблицы требования 5. Автогейт
приёмки такой задачи не проводится, в журнале есть запись. Ни одна
проверка не пропускается молча.

AC-10. В местах таблицы требования 5 нет сравнения `target` с
`config.DEFAULT_TARGET` и вызова `repo_context.is_artel`. Вызов
`workspace.on_task_branch` на выходе из `tests_writing` не несёт
`config.DEFAULT_TARGET` жёстким аргументом. PLAN подтверждает это
выводом поиска по изменённым функциям.

AC-11. Если рабочая копия задачи артели не выписана на ветку задачи и
завести её не вышло, выход из `tests_writing` и прогон приёмки отклоняют
переход с причиной. Ни сухой сбор, ни прогон приёмки не исполняются с
рабочим каталогом `config.ROOT`. Когда рабочая копия на ветке задачи,
прогон идёт в ней командой из профиля.

AC-12. У канареечной задачи артели неослабление на переходе, заявка
мутации и раздел изменённых утверждений пакета ревью не выполняются,
как и до этой части.

AC-13. На требования 1–6 в `tests/` есть тесты с заявками «Ловит
мутацию». PLAN перечисляет смены ожиданий существующих тестов, каждую со
ссылкой на мандат Оператора и раздел «Меняемое поведение» SPEC.
Дополнение фикстур профилем артели PLAN перечисляет отдельно.

AC-14. PLAN несёт приложения к `targets.yaml` и `tests/test_invariants.py`
по требованию 7 и подтверждает их применимость прогоном `git apply
--check`. Дифф приложения к `targets.yaml` меняет только строки поля
`test_profile` записи `artel`. Дифф приложения к `tests/test_invariants.py`
меняет только песочницу, а сценарии и утверждения инвариантов не меняет.
После наложения обоих приложений `tests/test_invariants.py` проходит.

**Обоснование монолита** (решение за Оператором на гейте SPEC). Эта задача
уже часть 1 из 3 по делению Оператора от 05.10.
- Профиль без перевода проверок мёртв: поле разбирается, но ни одна
  проверка его не читает. Кроме того, требование 4 (для артели без
  профиля — отказ) без приложения к `targets.yaml` и песочнице
  инвариантов краснит прогон в тот же мерж.
- Перевод проверок без профиля нельзя. Снятие развилок включит
  проверки на внешнем проекте с зашитыми значениями артели, а это не
  разовые тесты ADR-0021 п.9.
- Проверки таблицы требования 5 делят одно чтение профиля и одно правило
  «без профиля / контекст не разрешён». Если разрезать их по
  проверкам, получится промежуточное состояние, где часть гейтов
  целостности смотрит на профиль, а часть — на `DEFAULT_TARGET`. При этом
  у внешнего проекта перечень сумм пишется, а лок на мерже не
  сверяется.
- Требование 6 (единая ветка прогона) опирается на `command` из профиля
  и на те же места `tests_writing`/`acceptance`, что требование 5.

Бюджет: класс по калибровке — около $85 (14 критериев, больше 7 файлов
зоны). В SPEC стоит $50 по правилу миссии аналитика (не выше
дефолта). Потолок задачи $100 задан Оператором командой `budget` и
значением SPEC не перебивается (ANSWER-1, вопрос 3).

## Приложением

- `targets.yaml` — поле `test_profile` записи `artel` со значениями
  таблицы требования 1. `no_paths` и комментарий записи не меняются.
- `tests/test_invariants.py` — песочница инвариантов создаёт
  `<tmp>/targets.yaml` с записью артели и её профилем тестов. Сценарии и
  утверждения инвариантов не меняются (ANSWER-1, вопрос 1).

- Этап 4: отмена наложения снимка документов и коммита RETRO на `main`,

  песочница прогона тестов внешнего проекта: поле описывается и

  (`report`) пультом тоже не входит.
- Профиль не-Python проекта сверх полей и отключения языковых проверок
  (разбор тестов другого языка).
- Разделение журналов и базы по проектам (триггер №29); подключение
  реального внешнего проекта.
- Правка путей «только чтение» ТЗ: `docs/invariants.md` (формулировка
  инварианта 38 не меняется; если её понадобится менять — эскалация),

- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность

  держит пульт.
