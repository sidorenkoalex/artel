# QUESTIONS: Этап 3 ADR-0021, часть 1 из 3: профиль тестов проекта и проверки тестов на repo_context

## Вопросы

1. **Требование 2 (fail-closed для артели без профиля) против
   `tests/test_invariants.py` (в ТЗ — «только чтение»).** Песочница
   инвариантов подменяет `config.TARGETS` на `<tmp>/targets.yaml`
   (`tests/test_invariants.py:1601`), но сам файл не создаёт: в корень
   копируются только `templates/` и `.gitignore` (`:1562-1563`). Сегодня
   артель разрешается без чтения `targets.yaml`
   (`orchestrator/repo_context.py:72-74`), поэтому песочнице этого
   хватает. Её сценарии ведут задачу артели (не канареечную) через
   `in_dev → verifying` (`tests/test_invariants.py:809-819` и дальше:
   `:849`, `:873`, `:900`, `:945`, `:1272`), а на этом переходе работает
   гейт неослабления (`orchestrator/advance_gates/test_integrity.py:686`).
   Через `merge_gate approve` они ведут её тоже (`:516-529`), там
   работают неослабление и лок планки (`orchestrator/fsm_merge_gate.py:123`,
   `:1101`). Если профиль артели берётся из её записи `targets.yaml`, а
   его отсутствие означает отказ перехода, эти сценарии краснеют. Ни
   поправить их, ни дописать в фикстуру профиль ТЗ не даёт. Как
   поступить? Варианты:
   A) Оператор разрешает правку `tests/test_invariants.py`
   приложением к PLAN: песочница инвариантов создаёт `targets.yaml` с
   записью артели и её профилем, сценарии не меняются. Это защищённый
   путь, поэтому сторож внутри приложения и прогон CI с приложениями —
   по правилам приложений.
   B) Профиль артели задаётся константой в коде (например, в
   `orchestrator/config.py`) и действует, когда `targets.yaml` нет или в
   нём нет записи артели. Если же запись есть, а её поле профиля
   неразборчиво, это отказ. Запись `targets.yaml` получает профиль
   приложением только как декларацию. Требование 2 при этом ослабевает:
   отсутствие профиля у артели перестаёт быть отказом.
   C) Профиль артели читается из `targets.yaml` только при наличии
   файла; отсутствие самого файла для артели — прежнее поведение
   (проверки идут со значениями нынешнего кода), а запись без поля
   профиля или неразборчивое поле — отказ. Это промежуточный вариант
   между A и B, но тоже исключение из fail-closed.
   Дефолт: **A**. Только он сохраняет требование 2 в формулировке ТЗ и
   не вводит для артели исключения, которое повторяло бы уже снимаемую
   развилку по `DEFAULT_TARGET`. Цена — разрешение на правку защищённого
   файла и сценарий наложения приложения в CI ветки
   (`scripts/plan_appendix_ci.py`).

2. **Исключение канареечной задачи в тех же проверках.** Условия, которые
   снимает ТЗ, совмещают два отбора: `t["is_canary"] or t["target"] !=
   config.DEFAULT_TARGET` (`orchestrator/advance_gates/review.py:200`,
   `orchestrator/advance_gates/test_integrity.py:686`,
   `orchestrator/review.py:613`). ТЗ велит удалить «развилки
   `config.DEFAULT_TARGET`» и ничего не говорит про отбор по
   `is_canary`. Варианты: A) отбор по `is_canary` остаётся как есть,
   снимается только сравнение с проектом; B) отбор по `is_canary` тоже
   снимается, и канарейка проходит проверки тестов по профилю своего
   проекта. Дефолт: **A**. Отбор канарейки к проекту отношения не имеет,
   а его снятие меняет поведение канарейки, о котором ТЗ молчит.

3. **Потолок бюджета.** Миссия шага требует ставить `budget_usd` по
   классу задачи, но только вниз от дефолта (`DEFAULT_BUDGET_USD` = 50).
   По калибровке класс выходит ~85: больше 8 файлов зоны (repo_context,
   targets, три гейта `advance_gates/`, `review.py`, `fsm_advance.py`,
   `fsm_merge_gate.py`, `amend.py`, `acceptance.py`, `mandate.py`,
   `scripts/guard.py`, плюс тесты) и около 15 критериев. Рамка ТЗ —
   $55, потолок группы 3 — $100, этап 2 при рамке $60 обошёлся в $155.
   Варианты: A) 50 — максимум, который разрешает миссия; дальше Оператор
   поднимает потолок командой `budget` по факту; B) 55 — рамка ТЗ (выше
   дефолта, нужно разрешение Оператора); C) 85 — по классу (выше
   дефолта, но ниже потолка группы $100). Дефолт: **A**, по правилу
   миссии.
