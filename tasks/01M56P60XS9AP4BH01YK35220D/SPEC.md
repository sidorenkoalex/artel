## Контекст
Гейт неослабления тестов писался под устройство тестов артели и на
чужом Python-стеке (проект sled: `workdir: backend`, `weakening_scope:
[backend/tests/**/*.py]`, `targets.yaml:83,87`) пропускает ослабления.
Пропуск через переменную-метку (`requires_pg = pytest.mark.skipif(...)`,
`@requires_pg`) и модульные пропуски не опознаются: `SKIP_DECORATOR_NAMES`
(`scripts/guard.py:649-650`) смотрит последний сегмент имени декоратора,
`guard.py:675-697` — декораторы и тела функций, модульный уровень не
смотрится (так прошла задача 01M55SKHZ293CCAK0N7T4H7ZMR). Вызывающие
ослабленного помощника ищутся только в `tests/`
(`orchestrator/advance_gates/test_integrity.py:631-650`), модуль
переводится в путь `tests/x.py` (`guard.py:1013-1019`), импортированные
функции прослеживаются только из `tests/sandbox.py` (`guard.py:1087`).
Двусторонний прогон ищет точный id узла и на параметризованном тесте
отвечает «узел не найден» (`orchestrator/advance_gates/two_sided.py:175-187`),
изменения аргументов `@pytest.mark.parametrize` гейт не видит
(`guard.py:1765-1768`). `async def test_` не считает только
`guard.TEST_METHOD` (`guard.py:178`, якорь `^\s*def`): сборщик тестовых
методов (`guard.py:621,626`) и `TEST_AC` (`guard.py:170`, без якоря) async
уже учитывают.

## Требования
1. Имя, связанное в модуле тестов с `pytest.mark.skipif`/`pytest.mark.skip`/
   `pytest.mark.xfail` или `unittest.skip*`, использованное декоратором
   тестового метода или класса, гейт неослабления опознаёт как пропуск —
   тем же классом находки, что прямой декоратор. Формы связывания — ровно
   две: присваивание на уровне модуля `name = pytest.mark.skipif/skip/xfail(...)`
   или `name = unittest.skip*(...)` и `from <модуль тестов> import name`
   имени, связанного так в том модуле. Модуль импортированной метки
   разрешается по тем же правилам, что модуль помощника (требование 6):
   у артели — только `tests/sandbox.py`, у внешнего проекта — любой модуль
   `weakening_scope`.
2. Послабление условного пропуска с причиной (условный вид — `skipif`/
   `skipIf`/`skipUnless` с условием и причиной строковой константой, как
   у прямого декоратора, `test_integrity.py:141,293-312`) метке
   требования 1 даётся по тем же правилам, что прямому декоратору: только
   на тестовом методе, которого нет в базе сравнения
   (`test_integrity.py:447-449`), с записью об условном пропуске в
   журнале; метка декоратором класса — находка всегда, в том числе в
   новом файле (`test_integrity.py:442-446`).
3. Смена значения, связанного с именем-меткой, при прежнем тексте маркера
   (`@requires_pg` в базе и на ветке) — находка гейта неослабления на
   тестовых методах базы, помеченных этой меткой: сравнивается значение
   связанного имени, не только текст маркера. Это действует и для метки,
   импортированной из модуля тестов проекта, когда на ветке меняется
   только модуль метки, а файлы тестов с `@requires_pg` не меняются.
4. Модульные пропуски — `pytestmark = …` с маркой пропуска/ожидаемого
   провала (одна марка или список/кортеж), `pytest.skip(...,
   allow_module_level=True)` и `pytest.importorskip(...)` на уровне
   модуля — гейт неослабления опознаёт как пропуск всех тестовых методов
   файла тем же классом находки, что прямой декоратор. Послабление — по
   правилу требования 2: только тестовым методам, которых нет в базе
   сравнения; условность `pytestmark` — по правилу декоратора, условность
   модульного вызова — по правилу вызова пропуска в теле (условен только
   внутри ветки `if`/`else`, причина — строковая константа,
   `test_integrity.py:315-336`).
5. Требования 1–4 действуют и для артели (усиление существующего
   свойства).
6. Режим поиска и прослеживания задаёт признак проекта пульта
   `repo_context.is_artel`. У внешнего проекта (`is_artel` ложен) поиск
   вызывающих ослабленного помощника и прослеживание помощников идут по
   области ослабления профиля проекта задачи (`weakening_scope`) —
   импортированная функция прослеживается из любого модуля области, имя
   модуля переводится в путь от корня проекта с учётом `workdir` профиля.
   У артели (`is_artel` истинен) — как сейчас: вызывающие ищутся в
   `tests/`, импортированные функции прослеживаются только из
   `tests/sandbox.py` (критерий AC-10). Профиль, в том числе `workdir`,
   узел получает внутри зон задачи: вызовы узла из
   `orchestrator/review.py:650-652` и
   `orchestrator/fsm_merge_gate.py:144-146` не меняются.
   `guard.TestModules` и `guard.method_literal_keys` меняются обратно
   совместимо: `workdir` — необязательный аргумент, без него поведение
   прежнее; их вызов в `orchestrator/fsm.py:1053-1060` (сверка «Меняемого
   поведения» на гейте SPEC) не правится.
7. Двусторонний прогон находит параметризованный тест по базовому id
   (варианты `::test_x[...]`) и выносит вердикт по вариантам,
   существующим с обеих сторон прогона: «пройден» (`two_sided.PASSED`,
   `two_sided.py:44`) — когда каждый такой
   вариант проходит прежний критерий стороны (падение на утверждении,
   `two_sided.py:11-15`) на обеих сторонах; иначе — отказ с причиной,
   называющей вариант; нет ни одного общего варианта — отказ. Исход «узел
   не найден» для параметризованного теста, варианты которого есть в
   отчёте, не выдаётся. Смена ожидания, доказываемая прогоном, — смена
   литерала в утверждении тела метода (объявление «Меняемого поведения»
   читает литералы только утверждений, `guard.method_literal_keys`,
   `guard.py:3834-3846`); строку `parametrize` этим разделом не объявить.
8. Изменение аргументов `@pytest.mark.parametrize` у тестового метода,
   сохранившего имя (в том числе удаление варианта и марка пропуска на
   варианте `pytest.param(..., marks=…)`), — изменение тем же каналом,
   что изменённые утверждения без объявления: находка с отказом
   перехода, которую снимает только мандат Оператора
   (`test_integrity.py:1105-1111`), запись в журнале и строка в
   ревью-пакете.
9. `async def test_…` учитывается `guard.TEST_METHOD` (`guard.py:178`)
   как одноимённый `def test_…` — и тем самым его потребителями
   (`orchestrator/acceptance.py:2169`, `orchestrator/dry_run.py:70`).
10. У артели прежние исходы поиска вызывающих, прослеживания помощников и
    двустороннего прогона непараметризованных тестов (критерии AC-10,
    AC-12) зафиксированы тестами до правки и не меняются; тексты
    исходов, которые читает `orchestrator/report.py:117-123,996-1001`,
    сохраняются.
11. Тесты детерминированы, без сети; поведение чужого стека проверяется на

## Критерии приёмки
AC-1. Тест учебного проекта под `backend/tests/`, который есть в базе и получил на ветке декоратор `@requires_pg`, где в том же модуле `requires_pg = pytest.mark.skipif(<условие>)` без причины (так же — `pytest.mark.skip`, `pytest.mark.xfail`, `unittest.skip`), даёт находку гейта неослабления того же класса, что прямой `@pytest.mark.skipif`.
AC-2. Тот же случай, когда метка импортирована из модуля тестов проекта (`from tests.<модуль> import requires_pg` при `workdir: backend` — файл `backend/tests/<модуль>.py`), даёт ту же находку.
AC-3. Метка `requires_pg = pytest.mark.skipif(<условие>, reason="…")` на тестовом методе, которого нет в базе, проходит с записью об условном пропуске в журнале; та же метка, добавленная тестовому методу, который есть в базе, — находка; та же метка декоратором класса с тестовыми методами — находка и в новом файле.
AC-4. База: `requires_pg = pytest.mark.skipif(False, reason="…")` и тест базы с `@requires_pg`; ветка меняет только значение на `pytest.mark.skip` (текст `@requires_pg` у теста прежний) — находка на этом тесте. То же — когда метка импортирована и на ветке меняется только её модуль, а файл теста не меняется.
AC-5. Добавленная на уровне модуля `pytestmark = pytest.mark.skip(...)` (или список с такой маркой) в файле, тестовые методы которого есть в базе, — находка; `pytestmark = pytest.mark.skipif(<условие>, reason="…")` в новом файле, все тестовые методы которого новые, — проход с записью об условном пропуске в журнале.
AC-6. Добавленный на уровне модуля вне ветки `if` вызов `pytest.skip(..., allow_module_level=True)` в файле с тестовыми методами базы — находка.
AC-7. Добавленный на уровне модуля вне ветки `if` вызов `pytest.importorskip(...)` в файле с тестовыми методами базы — находка.
AC-8. Случаи AC-1, AC-4 (метка в том же модуле), AC-5 (первая половина), AC-6 и AC-7 на файле `tests/` артели дают те же находки; случай AC-2 у артели с меткой, связанной в `tests/sandbox.py` и импортированной `from tests.sandbox import requires_pg`, даёт ту же находку.
AC-9. Помощник `backend/tests/rbac_support.py` учебного проекта, потерявший утверждение на ветке, вызываемый из неизменённого теста `backend/tests/test_<x>.py` (импорт `from tests.rbac_support import …` при `workdir: backend`), даёт находку гейта неослабления.
AC-10. У артели исходы помощников прежние (зафиксированы тестом до правки, проходят после неё): (а) функция своего модуля без префикса `test_`, потерявшая утверждение, даёт находку на вызывающем тесте; (б) функция `tests/sandbox.py`, потерявшая утверждение, даёт находку на вызывающем тесте другого файла `tests/`; (в) функция другого модуля `tests/` (не `tests/sandbox.py`), импортированная и потерявшая утверждение, находки на вызывающем тесте не даёт; (г) функция своего модуля с префиксом `test_` помощником не прослеживается; (д) вызывающий ослабленного помощника ищется только среди файлов `tests/`.
AC-11. Двусторонний прогон смены литерала утверждения в теле параметризованного теста (`@pytest.mark.parametrize` с ≥2 вариантами, аргументы parametrize не меняются) выносит «пройден» (`two_sided.PASSED`), когда каждый вариант падает на утверждении на обеих сторонах, и отказ с id варианта в причине, когда хотя бы один вариант на одной из сторон не падает на утверждении; ни в одном случае причина не «узел не найден».
AC-12. У артели исходы двустороннего прогона непараметризованного теста прежние (зафиксированы тестом до правки, проходят после неё): падение на утверждении на обеих сторонах — «пройден» (`two_sided.PASSED`); зелёная сторона — отказ «зелёная — …»; пропуск — «пропуск (фаза …)»; ошибка сборки — «ошибка сборки (collect)»; узла `::test_x` в отчёте нет, а есть `::test_x_slow` — «узел не найден», соседний узел с общим префиксом за `::test_x` не засчитывается.
AC-13. Изменение аргументов `@pytest.mark.parametrize` у тестового метода с прежним именем и прежним телом без мандата Оператора — находка с отказом перехода, запись в журнале и строка в ревью-пакете тем же каналом, что изменённое утверждение без объявления; с мандатом Оператора на этот метод — проход.
AC-14. Удаление варианта из `@pytest.mark.parametrize` и добавление варианту марки пропуска (`pytest.param(..., marks=pytest.mark.skip)`) у метода с прежним именем — находка по AC-13.
AC-15. `async def test_x(...)` учитывается `guard.TEST_METHOD` (входит в число тестовых методов файла) так же, как одноимённый `def test_x(...)`.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` = 45 ≥ $30; число критериев приёмки 15 ≥ 10.

Решение — **нарезка** на 3 подзадачи (ТЗ, п.5: «разбивает на подзадачи
при сигнале деления»). Границы — по требованиям ТЗ, каждая часть несёт
свой кусок зоны целиком:

1. Помощники по `weakening_scope` и `workdir` (требования 6, 10 в части
   помощников; AC-9, AC-10) — перевод имени модуля в путь с учётом
   `workdir` и область поиска (`guard.py`, `test_integrity.py`). Первая:
   на этот перевод и поиск по модулю метки опирается часть 2
   (импортированная метка, AC-2, AC-4). Мержима отдельно: у артели исходы
   прежние (фиксируются тестом до правки), у чужого стека появляются
   находки.
2. Пропуски через метку и модуль, async (требования 1–5, 9; AC-1…AC-8,
   AC-15) — `guard.py`, `test_integrity.py`. Мержима отдельно: только
   усиление находок, прежние исходы артели не меняются.
3. Параметризация (требования 7, 8, 10 в части прогона; AC-11…AC-14) —
   `two_sided.py`, `guard.py`/`test_integrity.py`. Мержима отдельно по
   тем же причинам; от частей 1–2 не зависит по механике, порядок «после
   части 2» — порядок 1 → 2 → 3 общего `scripts/guard.py` под замком зоны.

Путь `workdir` до узла сравнения правок вне зон не требует: у
`review_lines`, `merge_gate_escalates` и `_test_integrity_gate` есть
`task_id` (`test_integrity.py:1237,1571,1475`), профиль проекта задачи
читается `project_profile.decide` (`test_integrity.py:1509`; модуль только
для чтения — вызывается, не правится). Если разработчик найдёт, что без
правки вызывающих вне зон не обойтись, — эскалация до правки.

Рамки подзадач — $25 × 3 = $75, порядок части 1 → 2 → 3 (решение C5
Оператора по аудиту SPEC 18.10, причина возврата из `spec_gate`).
