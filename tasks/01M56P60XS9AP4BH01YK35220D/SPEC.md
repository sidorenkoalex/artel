# SPEC: Гейт неослабления на чужом стеке: пропуск через метку, помощники, параметризация, async

## Контекст
Гейт неослабления тестов писался под устройство тестов артели и на
чужом Python-стеке (проект sled: `workdir: backend`, `weakening_scope:
[backend/tests/**/*.py]`, `targets.yaml:83,87`) пропускает ослабления.
Пропуск через переменную-метку (`requires_pg = pytest.mark.skipif(...)`,
`@requires_pg`) и модульные пропуски не опознаются: `SKIP_DECORATOR_NAMES`
(`scripts/guard.py:649-650`) смотрит последний сегмент имени декоратора,
`guard.py:656-697` — только тела функций (так прошла задача
01M55SKHZ293CCAK0N7T4H7ZMR). Вызывающие ослабленного помощника ищутся
только в `tests/` (`orchestrator/advance_gates/test_integrity.py:631-650`),
модуль переводится в путь `tests/x.py` (`guard.py:1013-1019`),
прослеживается только `tests/sandbox.py` (`guard.py:1087`). Двусторонний
прогон ищет точный id узла и на параметризованном тесте отвечает «узел не
найден» (`orchestrator/advance_gates/two_sided.py:175-187`), изменения
аргументов `@pytest.mark.parametrize` никто не видит (`guard.py:1765-1768`,
`:790-799`). `async def test_` не считается тестовым методом
(`guard.py:178`, `TEST_METHOD`).

## Требования
1. Имя, связанное в модуле тестов с `pytest.mark.skipif`/`pytest.mark.skip`/
   `pytest.mark.xfail` или `unittest.skip*` (присваиванием в том же модуле
   либо импортом из модуля тестов проекта), использованное декоратором
   теста, гейт неослабления опознаёт как пропуск — тем же классом
   находки, что прямой декоратор, и с тем же послаблением для условного
   пропуска с причиной (с записью в журнал).
2. Модульные пропуски — `pytestmark = …` с маркой пропуска/ожидаемого
   провала, `pytest.skip(..., allow_module_level=True)` и
   `pytest.importorskip(...)` на уровне модуля — гейт неослабления
   опознаёт как пропуск тем же классом находки и с тем же послаблением
   для условного пропуска с причиной, что прямой декоратор.
3. Требования 1–2 действуют и для артели (усиление существующего
   свойства).
4. Поиск вызывающих ослабленного помощника и прослеживание помощников идут
   по области ослабления профиля проекта задачи (`weakening_scope`), имя
   модуля переводится в путь от корня проекта с учётом `workdir`
   профиля. У артели исходы поиска и прослеживания — как сейчас.
5. Двусторонний прогон находит параметризованный тест по базовому id
   (все его варианты `::test_x[...]`) и выносит вердикт по совокупности
   вариантов: доказательство — только когда каждый вариант удовлетворяет
   условию двустороннего прогона; иначе — отказ с причиной, называющей
   вариант. Исход «узел не найден» для параметризованного теста,
   варианты которого есть в отчёте, не выдаётся.
6. Изменение аргументов `@pytest.mark.parametrize` у тестового метода,
   сохранившего имя, — наблюдаемое изменение тем же каналом, что
   изменённые утверждения: запись в журнал и строка в ревью-пакете.
7. `async def test_…` считается тестовым методом во всех местах разбора
   `scripts/guard.py` (`TEST_METHOD`, `TEST_AC`, `qualified_test_methods`
   и прочие разборы тестовых методов) — и тем самым у потребителей этих
   разборов.
8. У артели все прежние исходы гейта неослабления и двустороннего
   прогона, кроме усилений требований 1–3 и 7, зафиксированы тестами до
   правки и не меняются.
9. Тесты детерминированы, без сети; поведение чужого стека проверяется на
   учебном проекте с `workdir: backend` и `weakening_scope:
   [backend/tests/**/*.py]`.

## Критерии приёмки
AC-1. Тест учебного проекта под `backend/tests/`, получивший на ветке декоратор `@requires_pg`, где в том же модуле `requires_pg = pytest.mark.skipif(<условие>)` без причины (или `pytest.mark.skip`/`pytest.mark.xfail`), даёт находку гейта неослабления того же класса, что прямой `@pytest.mark.skipif`.
AC-2. Тот же случай, когда метка импортирована из модуля тестов проекта (`from tests.<модуль> import requires_pg` при `workdir: backend` — файл `backend/tests/<модуль>.py`), даёт ту же находку.
AC-3. Условный пропуск с причиной через имя-метку (`requires_pg = pytest.mark.skipif(<условие>, reason="…")`) получает то же послабление, что прямой условный декоратор с причиной, и запись об условном пропуске в журнале.
AC-4. Добавленная на уровне модуля `pytestmark = pytest.mark.skip(...)` (или список с такой маркой) — находка гейта неослабления (условная с причиной — послабление с журналом).
AC-5. Добавленный на уровне модуля `pytest.skip(..., allow_module_level=True)` — находка гейта неослабления.
AC-6. Добавленный на уровне модуля `pytest.importorskip(...)` — находка гейта неослабления (или послабление условного пропуска с журналом, тем же правилом, что прямой декоратор).
AC-7. Случаи AC-1, AC-4, AC-5 и AC-6 на файле `tests/` артели дают те же находки.
AC-8. Помощник `backend/tests/rbac_support.py` учебного проекта, потерявший утверждение на ветке, вызываемый из неизменённого теста `backend/tests/test_<x>.py` (импорт `from tests.rbac_support import …` при `workdir: backend`), даёт находку гейта неослабления.
AC-9. У артели поиск вызывающих и прослеживание помощников дают прежние исходы: набор сценариев, зафиксированный тестом до правки, проходит после неё без изменений.
AC-10. Двусторонний прогон смены ожидания параметризованного теста (`@pytest.mark.parametrize` с ≥2 вариантами) выносит вердикт «доказано», когда каждый вариант удовлетворяет условию прогона, и отказ с именем варианта, когда хотя бы один не удовлетворяет; ни в одном из случаев причина не «узел не найден».
AC-11. Двусторонний прогон непараметризованного теста у артели даёт прежний исход: сценарий, зафиксированный тестом до правки, проходит после неё без изменений.
AC-12. Изменение аргументов `@pytest.mark.parametrize` у тестового метода с прежним именем и прежним телом даёт запись наблюдения в журнале и строку в ревью-пакете тем же каналом, что изменённое утверждение.
AC-13. `async def test_x(...)` учитывается `guard.TEST_METHOD` (в числе тестовых методов файла), `guard.qualified_test_methods` и `TEST_AC` (`async def test_ac1_…` — тест критерия AC-1), как одноимённый `def test_x(...)`.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` = 45 ≥ $30; число критериев приёмки 13 ≥ 10.

Решение — **нарезка** на 3 подзадачи (ТЗ, п.5: «разбивает на подзадачи
при сигнале деления»). Границы — по требованиям ТЗ, каждая часть несёт
свой кусок зоны целиком:

1. Async и пропуски (требования 1–3, 7; AC-1…AC-7, AC-13) — механика
   разбора тестовых методов в `scripts/guard.py`, на которую опираются
   обе другие части (какие функции вообще тестовые). Самостоятельно
   мержима: только усиление существующих находок, прежние исходы артели
   не меняются.
2. Помощники по `weakening_scope` (требования 4, 8 в части помощников;
   AC-8, AC-9) — `guard.py` (перевод модуля в путь, прослеживание) и
   `test_integrity.py` (поиск вызывающих). Мержима отдельно: у артели
   исходы прежние (фиксируются тестом до правки), у чужого стека
   появляются находки.
3. Параметризация (требования 5, 6, 8 в части прогона; AC-10…AC-12) —
   `two_sided.py` (вердикт по вариантам), `guard.py`/`test_integrity.py`
   (наблюдение изменения аргументов). Мержима отдельно по тем же
   причинам.

Все части делят `scripts/guard.py` — замок зоны пустит их по очереди;
части 2 и 3 идут после части 1. Сумма рамок подзадач ($25 × 3 = $75)
выше рамки ТЗ ($45): $25 — нижняя планка задачи
(`skills/spec-authoring.md`), меньше на подзадачу не назначить; решение
о делении с такой суммой — за Оператором на гейте SPEC.
