# PLAN: Сухой сбор планки на выходе tests_writing

## Подход

Три независимых, но последовательных изменения в одном гейте
`fsm_advance.tests_writing`:

1. `orchestrator/acceptance.py::collect(tdir, cwd)` — сухой сбор
   `pytest --collect-only -q` тем же `_pytest_command`, что и `run()`
   (общие флаги окружения: интерпретатор venv, `-p no:cacheprovider`,
   явная загрузка `-p timeout`). Различает три исхода по коду возврата
   pytest (эмпирически проверено): `0` — собралось (`True`, хвост);
   `5` (`NO_TESTS_COLLECTED`) — планка синтаксически валидна, но пуста
   (`False`, ровно `"планка не содержит ни одного теста"` — точный текст
   критерия AC-3); любой другой код (`2` — ошибка импорта/синтаксиса при
   сборе, и т.п.) — `False`, хвост сырого вывода pytest (AC-2). Отличие
   кодов 5 и 2 — единственный надёжный способ не спутать «планка пуста» с
   «планка не импортируется»: оба исхода печатают фразу «no tests
   collected» в stdout, полагаться на неё текстом нельзя.

2. `fsm_advance.tests_writing` — после существующей проверки
   трассируемости AC (`errors`), до `store.set_state(..., "in_dev", ...)`,
   добавляются два гейта через существующий каркас `_run_gates`:
   - гейт AC-8 (посторонние файлы планки как последняя запись визита) —
     ПЕРВЫМ, до сухого сбора: он про диагностику дефекта уже
     ИЗВЕСТНОГО (checkpoint уже отбросил файлы), сухой сбор на планке,
     которая заведомо ссылается на отброшенное, дал бы менее точный
     общий текст ошибки импорта вместо прямого «планка ссылается на
     отброшенные файлы: <список>»;
   - гейт сухого сбора (`acceptance.collect`) — вторым.
   Каталог/cwd планки для сухого сбора — новая функция
   `_tests_writing_acceptance_dir`, повторяющая (не рефакторящая) уже
   существующий трёхветочный выбор `_acceptance_run_refuses`/
   `_review_approved` (внешний target -> workspace target'а; self на
   своей ветке -> worktree задачи; иначе -> `tdir`/`config.ROOT`) —
   отдельная функция, не рефакторинг `_acceptance_run_refuses`: та
   функция уже несёт плотное покрытие тестами T023-семьи, трогать её
   логику ради переиспользования 6 строк — риск регрессии не по зоне
   этой задачи (тот же тип дублирования уже есть в самом модуле между
   `_review_approved` и `_acceptance_run_refuses` — устоявшийся идиом,
   не новый антипаттерн).

3. Гейт AC-8 читает журнал (`store.task_steps`) от последней записи
   `state -> tests_writing` (либо от начала журнала, если такой записи
   нет — вырожденный случай лёгких песочниц, где `set_state` не
   журналируется помимо самого перехода) и сравнивает ПОСЛЕДНЮЮ запись
   визита с действием `checkpoint.STRAY_ACCEPTANCE_FILES_ACTION`.
   Действие и текст детали чекпоинта вынесены в две константы
   `checkpoint.py` (`STRAY_ACCEPTANCE_FILES_ACTION`/
   `STRAY_ACCEPTANCE_FILES_DETAIL_PREFIX`), которые гейт использует
   для сравнения и для извлечения списка отброшенных файлов из
   `detail` — не заводит независимую копию текста (тот же приём, что
   уже применён к `STRAY_WORKTREE_FILES_ACTION`). Сама механика
   checkpoint.py (что откидывается, когда журналируется) не меняется —
   меняется только то, как fsm_advance трактует уже существующую
   запись.

Требование 3 SPEC явно ограничивает область: «отказ шага» реализуется
ИСКЛЮЧИТЕЛЬНО через гейт tests_writing (AC-8), не правкой checkpoint.py
— `tests_writing` вызывается только для роли `test_author` (FSM:
1 состояние = 1 роль), поэтому не нужно отдельно проверять, что запись
оставлена именно этой ролью: любая запись `STRAY_ACCEPTANCE_FILES_ACTION`
как последняя запись визита `tests_writing` по построению — результат
шага `test_author` (AC-9 для прочих ролей выполняется автоматически,
без дополнительного кода, поскольку они этот гейт не проходят вовсе).

## Влияние на систему

Гейт `tests_writing` получает два новых способа отказать переход;
оба — через существующий каркас `_run_gates` (тот же журнал/печать, что
и у остальных гейтов модуля), новых состояний FSM не заводится.
Стоп-кран T038 (`orchestrator/auto.py`) и история отказов брифа
(`brief.advance_refusal_history`) не меняются и не нуждаются в правке —
оба уже общие для ЛЮБОГО отказа `tests_writing` по префиксу «переход
отклонён»/фильтру `actor == "fsm"» (закрывает AC-6, подтверждено
существующей архитектурой, не новым кодом; планка задачи несёт
регресс-тест на этот факт, AC-12).

Дополнительная стоимость: один субпроцесс pytest (`--collect-only`,
без прогона тел) на КАЖДЫЙ `advance`/`auto`-шаг `tests_writing`,
дошедший до трассируемости — дешевле полного `acceptance.run()`,
который и так следует чуть позже на `in_dev -> verifying`; при отказе
сухого сбора код так и не доходит до полного прогона (переход
блокируется раньше).

Существующие тесты `tests_writing`/`checkpoint`/`acceptance`
(`tests/test_acceptance_tests_flow.py`, `tests/test_acceptance.py`,
`tests/test_checkpoint_stray_acceptance_files.py`,
`tests/test_fsm_advance_gate_*.py` и смежные) не ослаблены и не
удалены — новые гейты добавлены строго ПОСЛЕ существующей проверки
трассируемости, планки существующих зелёных тестов синтаксически
валидны и содержат хотя бы один метод, поэтому проходят и сухой сбор
без изменений в самих тестах (проверено прогоном, см. ниже).

Откат: удаление вызовов двух новых гейтов из `tests_writing()` и
самой функции `acceptance.collect` — гейт `tests_writing` возвращается
к прежнему поведению (только трассируемость AC), никакие данные не
портятся необратимо (лок `tests_locked_sha` не переставляется до
прохода обоих гейтов).

## Риски

- Дополнительный субпроцесс на каждом шаге `tests_writing` — таймаут
  тот же `ACCEPTANCE_TIMEOUT_SEC`, отдельного бюджета не заводилось
  (SPEC не просит).
- Различение кодов возврата pytest (0/5/иное) — эмпирически проверенное
  поведение текущей версии pytest в venv пульта, не документированный
  публичный контракт pytest; при смене мажорной версии pytest стоит
  перепроверить (тот же класс риска, что уже несёт остальной модуль
  `acceptance.py` в комментариях про `TimeoutExpired.stdout`).

## Предложения системе

- `_review_approved`/`_acceptance_run_refuses`/новая
  `_tests_writing_acceptance_dir` — уже третья копия одного и того же
  трёхветочного выбора каталога планки (внешний target / self на своей
  ветке / иначе) в одном файле; при следующей задаче, трогающей эту
  логику, стоит подумать про общий helper вместо четвёртой копии — не
  делаю рефакторинг сейчас, чтобы не расширять периметр зоны этой
  задачи и не рисковать плотно покрытым тестами `_acceptance_run_refuses`.
