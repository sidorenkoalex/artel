# SPEC: Команда проверки артефакта для роли и миссии ролей внешнего проекта по профилю

## Контекст
Миссии analyst, developer и spec_auditor велят прогнать `scripts/guard.py`
на своём артефакте (`orchestrator/role_prompt.py:64`, `:120`, `:272`). У роли
внешнего проекта разрешён только `Bash(python3 <корень пульта>/orchestrator/artel.py:*)`
(`orchestrator/providers/claude.py:114-122`), а `scripts/guard.py` в рабочем
каталоге проекта нет: в шагах sled 01M55SKHZ293CCAK0N7T4H7ZMR «guard требует
подтверждения», и роль сдаёт формат вслепую. В белом списке команд роли
(`orchestrator/artel.py:1907-1910`, `_ROLE_ALLOWED_COMMANDS`) команды
проверки артефакта нет. Пункт 5 миссии test_author (`role_prompt.py:88-95`,
хвост `_long_lived_run_note` `:216-221`) велит прогонять долгоживущие файлы
командой `python3 -m pytest … -p timeout` из рабочего каталога. У sled
(`runner: pytest-own`, `workdir: backend`, `command: [uv, run, --frozen,
pytest, …]`) эта команда неверна, а `plank-run` по путям долгоживущих файлов
не умеет: `[файл]` принимается только из планки
(`orchestrator/plank_run.py:58-69`, отказ `:150-155`), а без `test_*.py` в
источнике планки команда отказывает «планки нет» раньше разбора `[файл]`
(`:146-148`). Миссия ревьювера (`role_prompt.py:141-145`) пишет «Права не
сужены»; у внешнего проекта это неверно.

Решение Оператора по батчу (ANSWER-1, 18.10.2026): вариант A, зона
расширена на `orchestrator/plank_run.py` — только приём и прогон путей
долгоживущих файлов задачи. Решения Оператора по аудиту SPEC (возврат с
гейта SPEC, 18.10.2026): расширение `plank-run` действует для любого
проекта, где путь проходит `Profile.is_long_lived` задачи (у артели —
`tests/test_<id>_*.py`), прежние вызовы без таких путей не меняются; прежний
исход `plank-run` фиксируется тестом до правки; эталон команды проверки —
`scripts/guard.py`, вызванный по файлам артефактов задачи (режим, которым
миссии пользуются сегодня, `scripts/guard.py:4479-4481`), с той же
путь-меткой в строках нарушений.

Имя новой команды — `guard`: она исполняет то же правило, что
`scripts/guard.py`, и одно имя у скрипта артели и у команды пульта не
оставляет роли двух названий одной проверки.

## Требования

1. В `orchestrator/artel.py` появляется команда `guard <id> [<файл>]`.
   Она проверяет артефакты задачи `<id>` в каталоге документов задачи тем
   же правилом, что `scripts/guard.py` (функции модуля `scripts/guard.py`,
   без своей копии правил). `<файл>` — имя артефакта в каталоге документов
   (`SPEC.md`) или путь `tasks/<id>/<файл>`.
2. Эталон команды — `python3 scripts/guard.py <путь файла в каталоге
   документов> …`, режим по файлам (не `--all`): к проверке структуры
   (`check`) добавляются `spec_path_errors` и `plan_appendix_errors`
   (`scripts/guard.py:4478-4481`), записки шагов и паспорт задачи
   пропускаются (`:4472-4477`). С `<файл>` проверяется этот файл; без
   `<файл>` — все `*.md` первого уровня каталога документов задачи, одним
   вызовом. Строки нарушений — те же, что у эталона на тех же файлах, с той
   же путь-меткой: путём файла в каталоге документов, как его получил бы
   эталон. Код выхода — 0, когда нарушений нет, ненулевой, когда они есть.
3. Команда `guard` только читает: строка задачи, журнал, ссылки, ветка
   задачи и файлы каталога документов не меняются, lease не берётся.
   Команда внесена в `_ROLE_ALLOWED_COMMANDS` и в окружении роли не
   отказывается ни для задачи артели, ни для задачи внешнего проекта.
4. Миссии analyst, developer и spec_auditor задачи внешнего проекта
   называют команду пульта в форме, которую разрешает белый список роли
   внешнего проекта: `python3 <корень пульта>/orchestrator/artel.py guard
   <id> …` (`<корень пульта>` — `config.ROOT`), вместо `scripts/guard.py`;
   строки `scripts/guard.py` в них нет.
5. `plank-run <id> [<файл>]` в аргументе `[<файл>]` дополнительно принимает
   путь долгоживущего файла своей задачи: путь от корня рабочей копии кода,
   для которого `Profile.is_long_lived(<id>, путь)` профиля проекта задачи
   истинно, а файл есть в рабочей копии кода. Это действует для любого
   проекта с профилем, артель включительно. К пути можно приписать узел
   pytest `::<тест>`. Такой путь прогоняется тем же раннером, что планка:
   командой и в каталоге профиля `pytest-own` проекта задачи, иначе
   раннером пульта; код выхода `plank-run` — код этого прогона.
6. Вызов с путём долгоживущего файла своей задачи работает и тогда, когда в
   источнике планки нет ни одного `test_*.py`: отказа «планки нет» ему нет.
7. Прочие вызовы `plank-run` дают прежний исход: прежний набор целей
   прогона, прежние отказы, прежний код выхода. В частности: вызов без
   аргумента и с файлом планки — как прежде; путь, который не входит ни в
   планку, ни в шаблон долгоживущего файла своей задачи (долгоживущий файл
   другой задачи, путь вне каталога `long_lived_dir`, имя вне шаблона),
   отклоняется прежним отказом («файла … нет в планке», а при пустой
   планке — «планки нет»), pytest при этом не запускается. Вызов без
   аргумента не начинает гнать долгоживущие файлы. Тесты, фиксирующие этот
   прежний исход, написаны и зелёные на коде до правки (ТЗ, требование 5).
8. Пункт 5 миссии test_author задачи внешнего проекта велит прогонять
   долгоживущие файлы задачи командой пульта `python3 <корень
   пульта>/orchestrator/artel.py plank-run <id> <путь долгоживущего
   файла>`, где путь назван каталогом и префиксом профиля
   (`<long_lived_dir>/<long_lived_prefix(id)>…`). Строки `python3 -m pytest`
   в миссии нет.
9. Миссия ревьювера задачи внешнего проекта перечисляет доступные роли
   проверки — команды пульта из белого списка ролей в форме `python3
   <корень пульта>/orchestrator/artel.py <команда>`, не меньше `guard`,
   `plank-run` и `suite-run`. Строки «Права не сужены» в ней нет.
10. У задачи артели тексты миссий analyst, developer, spec_auditor,
    test_author и reviewer совпадают с текстами до правки байт в байт, а
    `_ROLE_ALLOWED_COMMANDS` отличается от прежнего ровно одной командой
    `guard`. Поведение команд артели не меняется, кроме добавленной команды
    `guard` и добавления из требований 5–6 (`plank-run` принимает пути
    долгоживущих файлов своей задачи); вызовы `plank-run` без таких путей не
    меняются (требование 7). Тесты, фиксирующие миссии и белый список,
    написаны и зелёные на коде до правки (ТЗ, требование 5).
11. Тесты детерминированы и не ходят в сеть.

## Критерии приёмки

AC-1. Команда `python3 <корень пульта>/orchestrator/artel.py guard <id>
SPEC.md`, вызванная в окружении роли (`runner.role_env`) для задачи внешнего
проекта и для задачи артели, на артефакте без нарушений завершается кодом 0.
На артефакте с нарушением она завершается ненулевым кодом и выводит те же
строки нарушений, с той же путь-меткой, что `python3 scripts/guard.py
<путь SPEC.md в каталоге документов>`. Это выполняется для каждого из трёх
видов нарушения: структурного (`check`), нарушения путей SPEC
(`spec_path_errors`) и нарушения приложения PLAN (`plan_appendix_errors`, на
`PLAN.md`).

AC-2. Без аргумента `<файл>` команда `guard <id>` проверяет все артефакты
`*.md` первого уровня каталога документов задачи; записки шагов и паспорт
задачи нарушениями не становятся. Если нарушение есть хотя бы в одном
артефакте, код выхода ненулевой, и строки нарушений совпадают со строками
`python3 scripts/guard.py <те же файлы каталога документов>`.

AC-3. После `guard <id>` (с файлом и без) строка задачи и её журнал в БД,
ссылка документов `refs/artifacts/<id>`, ветка задачи и содержимое каталога
документов не меняются, lease задачи не взят. `guard` входит в
`_ROLE_ALLOWED_COMMANDS`.

AC-4. Миссии analyst, developer и spec_auditor задачи учебного внешнего
проекта не содержат строки `scripts/guard.py` и содержат строку `python3
<config.ROOT>/orchestrator/artel.py guard <id>`.

AC-5. Для задачи внешнего проекта с профилем `pytest-own` вызов `plank-run
<id> <путь долгоживущего файла этой задачи>` прогоняет этот файл командой
профиля (`command` профиля, `workdir` профиля); код выхода `plank-run` — код
этого прогона. Вызов работает и тогда, когда в источнике планки нет ни
одного `test_*.py` (отказа «планки нет» нет). С путём `<путь>::<тест>`
прогоняется этот узел.

AC-6. Вызов `plank-run <id> <путь>` с долгоживущим файлом другой задачи или
с путём вне шаблона долгоживущего файла (другой каталог, имя вне шаблона)
отклоняется прежним отказом, и прогона нет. Вызов `plank-run <id>` без
аргумента и с файлом планки даёт прежний исход: тот же набор целей прогона,
те же отказы и тот же код выхода. Тесты этого критерия зелёные и на коде до
правки.

AC-7. Пункт 5 миссии test_author задачи учебного внешнего проекта с
профилем содержит строку `python3 <config.ROOT>/orchestrator/artel.py
plank-run <id> <long_lived_dir>/<long_lived_prefix(id)>` (каталог и префикс
профиля этого проекта) и не содержит строки `python3 -m pytest`.

AC-8. Миссия ревьювера задачи учебного внешнего проекта не содержит строки
«Права не сужены» и содержит строки `python3
<config.ROOT>/orchestrator/artel.py guard`, `python3
<config.ROOT>/orchestrator/artel.py plank-run` и `python3
<config.ROOT>/orchestrator/artel.py suite-run`.

AC-9. Для задачи артели (`conn=None` и задача проекта артели в БД) тексты
миссий analyst, developer, spec_auditor, test_author и reviewer совпадают
байт в байт с эталонами, снятыми с кода до правки. Множество
`_ROLE_ALLOWED_COMMANDS` равно прежнему множеству с добавленной командой
`guard`.

## Оценка объёма и деление

сигналов нет: зон 4, критериев 9.

Материал для решения Оператора — монолит. Нарезка по зонам дала бы
«команда `guard` + миссии guard/ревьювера» (`artel.py`, `role_prompt.py`) и
«`plank-run` по путям + пункт 5 test_author» (`plank_run.py`,
`role_prompt.py`). Но обе части правят `role_prompt.py`, то есть одну зону с
одним эталоном неизменности миссий артели (AC-9), а миссия ревьювера
(AC-8) называет обе команды. Части малы: на два прохода конвейера ушло бы
больше рамки. Каждая часть по отдельности мержима, так что неразрезаемости
механики нет. Довод за монолит — цена и общая зона `role_prompt.py`.
