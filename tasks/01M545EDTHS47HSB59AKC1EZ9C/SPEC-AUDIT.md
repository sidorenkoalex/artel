## Пути обхода гейтов
- П-1. Отсутствие поля `token_slot` в записи. Требование 2 говорит «в
  слоте нет токена», а про запись без поля (как фикстуры тестов,
  `tests/test_doctor.py:632-636`) молчит. Исполнитель может трактовать «нет
  поля → прежняя авторизация Оператора». Существующие тесты остаются
  зелёными, а реальный внешний проект с опечаткой в имени поля тихо ходит в
  хостинг токеном Оператора, и смысл треб. 1 теряется. `targets.py` поле
  проверяет (`orchestrator/targets.py:29`), но запись без него может
  пройти проверку (это неочевидно и в зону не входит).
- П-2. AC-1 буквально выполним тестом только из `config.ROOT`. Помощник со
  слотом `artel-token` у вызовов в клоне артели тестом не ловится (О-2).
- П-3. Токен «не в argv»: AC-5 проверяет argv, но помощник вида
  `!f(){ echo password=$VAR; }; f` в `GIT_CONFIG_VALUE_n` несёт имя
  переменной, а не значение. Обход тут не виден, но тест должен проверять
  именно значение во всех `GIT_CONFIG_VALUE_*` (это окружение, не argv).
  AC-5 это покрывает только для окружения роли, не для окружения самого
  git-вызова. Отклонения нет, это риск для автора тестов.

## Вердикт
concerns. Отклонения, решение за Оператором на гейте:

- **О-5 (главное).** Существующие тесты против требований 1–2. Пример —
  `tests/test_doctor.py:670-692`: внешний `"sled"` без `token_slot`, ждут
  `"ok"`/`"warn"` от `check_base_branch`. По требованиям 1–2 они станут
  красными или полезут в настоящую связку ключей (`orchestrator/keychain.py:18`),
  а это нарушает требование 9. То же для сценариев песочницы с хостингом
  внешних проектов (матрица, строка 2). В SPEC нет ни раздела «Меняемое
  поведение», ни матрицы, ни способа сохранить детерминизм. Варианты:
  - а) общая подмена `keychain.token` в `tests/sandbox.py` (зона `tests/`)
    плюс правило для записи без `token_slot`;
  - б) строки «Меняемое поведение» для `test_doctor.py:670-692` (`'ok'` →
    `'…'`);
  - в) запись без поля `token_slot` — прежняя авторизация, но тогда это
    надо явно записать в SPEC (см. П-1).
- **О-1.** «Хостинговая git-операция» не определена на уровне `gitcmd.git`
  (`SPEC.md`, требование 1: «fetch, push … мерж»). `gitcmd.git` видит
  только argv: подставлять ли токен (и отказывать ли при пустом слоте,
  треб. 2) для любого `-C` под `.artel/projects/<проект>/` или только для
  подкоманд, говорящих с remote (`fetch`/`push`/`ls-remote`/`pull`)? При
  первом прочтении каждая локальная команда в клоне читает связку ключей,
  а при пустом слоте отказывают и `status`/`rev-parse`. Не задано и то, что
  делает хостинговая операция в процессе роли (треб. 7): отказ с
  названием или ход без токена. AC-10 проверяет только отсутствие чтения
  слота.
- **О-2.** AC-1 (`SPEC.md`, AC-1) не фиксирует вызовы `gitcmd.git("-C",
  …)` с путями внутри `.artel/projects/artel/` (клон и рабочие копии
  артели). Определение проекта по `-C` без исключения артели подставит
  помощник со слотом `artel-token` — это токен модели (Ф-4 родителя,
  выпал из «Контекста» SPEC). Критерий такую мутацию не ловит.
- **О-3.** AC-3, п.1 (`git config --get-all credential.helper` «только
  помощник пульта») расходится с механизмом сброса через окружение
  (опыт, Ф-2): `--get-all` всё равно печатает глобальный помощник. Тогда
  обязательна подмена `GIT_CONFIG_GLOBAL` для хостинговых вызовов, и из
  них уходят `user.*`/`insteadOf` Оператора, а у мержа в клоне
  (треб. 1: «мерж») может пропасть идентичность. Нужно решение: либо
  «сброшены» значит «пустое значение перед помощником пульта, `credential
  fill` даёт только токен слота», либо изоляция глобального конфига
  принята.
- **О-4.** Строка требования 1 про `check_base_branch`
  (`orchestrator/doctor/misc_checks.py:92`) не покрыта ни одним AC: AC-2 не
  называет вызов, а AC-8, п.5.4 касается другого вызова `gh api …/protection`.
- **Ф-1.** Вызовы `ci.gh` без `repo=` (`orchestrator/ci.py:1148,1207,1240`,
  их звонящие `ci_rerun.py:232,298`, `fsm_merge_gate.py:290` вне зон)
  токен проекта получить не могут. Требование 1 («вызовы `gh`») нужно
  сузить строкой в «Не входит».
