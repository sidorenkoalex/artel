## Пути обхода гейтов

- **П-1. Тесты песочницы в окружении роли.** Треб. 7 (SPEC.md:117-124)
  требует отказа хостинговой операции внешнего проекта в процессе роли,
  треб. 9 (SPEC.md:142-145) — чтобы фикстуры с `token_slot` оставались
  «под механизмом требования 1». Роль запускает тесты адресным `pytest`
  под `ARTEL_ROLE` и через `suite-run`, а там `HOME` = `config.ROLE_HOME`
  (`orchestrator/suite_run.py:781-782`, `orchestrator/runner.py:1132-1141`).
  Буквальное исполнение SPEC валит в шаге роли каждый существующий тест
  push/fetch внешнего проекта. У разработчика остаются два плохих
  выхода, и SPEC ни один не запрещает: подменить
  `runner.in_role_environment` в общей песочнице целиком — тогда AC-10
  проверяет подмену, а не код, — или править существующие тесты, что
  ослабляет набор без мандата. SPEC должен сказать, как песочница
  нейтрализует признак роли для тестов, предмет которых — не роль
  (например, песочница снимает `ARTEL_ROLE` и задаёт свой `HOME`; AC-10
  ставит признак явно).
- **П-2. Источник `token_slot`.** SPEC не говорит, откуда механизм берёт
  запись проекта: из `targets.yaml` по имени каталога `-C` или из `entry`,
  который передан вызывающему (`check_base_branch(name, entry)`). От этого
  зависит А-1. Без явного правила разработчик вправе выбрать любой
  источник, и один из них ломает `tests/test_doctor.py:629-692`.
- **П-3.** Механизм токена в doctor обходится через `subprocess`, а AC
  этого не видят (В-1).
- Противоречие треб. 2 и 7 для записи без `token_slot` в процессе роли:
  треб. 2 (SPEC.md:70-73) — «прежняя авторизация», треб. 7 — «хостинговая
  операция внешнего проекта там отказывает». Какое правило старше, не
  сказано (мелкое; дефолт — отказ по треб. 7, токен ведь всё равно не
  читается).
