# SPEC: D2-2 — токен хостинга внешнего проекта и проверки doctor

## Контекст
Часть 2 задачи 01M53B45XW3J56RJHGD70TD8A2 (D2). Требования и критерии
взяты из SPEC родителя: требования 1–4, 8, 9, 12, 13, 14 и проверка
`doctor` из требования 6; критерии AC-1 (только `gh` и git пульта у
артели), AC-2…AC-5, пункт `doctor` из AC-7, AC-8…AC-10, AC-12, AC-13.
Сейчас `gh` пульта работает с авторизацией Оператора
(`orchestrator/ci.py`, `orchestrator/github_adapter.py`,
`orchestrator/doctor/misc_checks.py:92`). git-операции пульта с
хостингом идут через системный помощник `osxkeychain` Оператора. Поле
`token_slot` записи проекта пульт не исполняет. `doctor` не проверяет клон
и хостинг внешнего проекта. Часть 1 (01M545EB0A9F191WTDSPCH36GA, в main)
дала проверку `project_skills` без сборки брифа —
`brief.project_skills_refusal(target, entry)`.

## Требования

1. **Токен хостинга проекта.** Для внешнего проекта (не артели) операции
   пульта с его хостингом берут токен из слота связки ключей, имя которого
   задано полем `token_slot` записи проекта. Операции хостинга: вызовы
   `gh` и git-операции пульта с `origin` клона (fetch, push веток задачи,
   push `refs/artifacts/*`, мерж).
   - `gh` получает токен переменной `GH_TOKEN` в окружении своего вызова.
     Прямой вызов `gh` в `doctor` (`orchestrator/doctor/misc_checks.py:92`,
     `check_base_branch`) для внешнего проекта тоже получает токен проекта.
   - git получает помощник учётных данных через окружение своего вызова.
     Конфигурация клона не меняется, системный помощник `osxkeychain` не
     участвует.
   - `gitcmd.git` определяет проект по пути аргумента `-C`, лежащему внутри
     `.artel/projects/<проект>/`, и подставляет токен слота этого проекта.
     Сигнатура `gitcmd.git` не меняется.
   - В окружении хостингового git-вызова пульта чужие помощники учётных
     данных сброшены: глобальный (`credential.helper`) и с областью URL
     проекта (`credential.<URL проекта>.helper`) не участвуют.
2. В слоте `token_slot` нет токена — операция хостинга внешнего проекта
   отказывает с текстом, в котором названо имя слота.
3. Значение токена п.1 не попадает в журналы задачи, вывод команд пульта и
   окружение роли. Это верно и для отказанной хостинговой операции
   (например, `origin` отказал в push). Токен не передаётся в argv ни
   одного вызова (git, `gh`, помощник учётных данных) — только через
   окружение.
4. Для артели вызовы `gh` и git-операции пульта не меняются: окружение и
   аргументы те же, что на main.
5. **Проверки `doctor`.** Для каждой записи внешнего проекта `doctor`
   выводит проверки, у каждой исход ok, warn или fail:
   1. Клон и свежесть. Клон — `.artel/projects/<имя>/repo`
      (`repo_context.clone_path`), а не сам каталог проекта. Клона нет —
      fail. `origin` клона не совпадает с `url` записи — fail. Время
      изменения файла `FETCH_HEAD` клона, взятое до fetch самой проверки,
      старше порога — warn с текстом «клон не обновлялся N ч». Порог —
      константа `orchestrator/config.py`, 24 ч. Файла `FETCH_HEAD` нет
      (свежий клон `target-init`) — warn «клон ещё не обновлялся
      пультом», не fail. После этого проверка делает fetch, рабочие копии
      при этом не меняются. Fetch не прошёл — fail.
   2. Право пуша в `refs/artifacts/*`: пробный `git push --dry-run` с
      токеном п.1. Отказ — fail.
   3. CI на `pull_request`: разбор файлов `.github/workflows/*.yml` в
      дереве клона, без сети. Ни один файл не объявляет триггер
      `pull_request` — warn «verifying будет ждать до потолка».
   4. Защита базовой ветки — информационная проверка:
      `gh api repos/<владелец>/<репозиторий>/branches/<base>/protection` с
      токеном проекта п.1. Ответ получен — сведения выводятся. Данные
      недоступны — вывод даёт сведение «недоступно», исход не fail.
   5. Токен. Токена в слоте `token_slot` нет — fail. Значение токена слота
      проекта совпадает с токеном, которым `gh` Оператора ходит в хостинг
      (вывод `gh auth token`), — warn «одобрение своим же токеном
      технически возможно — `docs/triggers.md` №24», не блокирует. Сами
      значения в вывод не попадают.
   6. `no_paths`. Каждый путь `no_paths` записи должен существовать в
      дереве клона. Отсутствующий путь даёт исход не ok, путь назван в
      выводе.
   7. `project_skills` записи — проверкой части 1
      (`brief.project_skills_refusal`): отказ — fail.
6. Для артели `doctor` выводит по проверкам п.5 явное решение
   «неприменимо», а не пропускает их молча.
7. **Токен и процесс роли.** В процессе роли (окружение с маркером
   `ARTEL_ROLE`, `runner.in_role_environment`) токен хостинга проекта не
   читается ни при каких командах пульта. Проверки `doctor` 5.1, 5.2 и 5.5
   там не выполняются и выводят именованный пропуск «только в сессии
   Оператора».
8. **Досылка коммита закрытия в `doctor`.** Push из
   `orchestrator/doctor/artifact_branches.py:126-138` (`_push_closing_sha`)
   по URL `origin` клона внешнего проекта идёт с токеном проекта тем же
   механизмом, что и требование 1, в том числе когда репозиторий-источник
   `source` — главная копия пульта вне `.artel/projects/<проект>/`.
   Требования 2 и 3 действуют и для этого push.
9. **Тесты** детерминированы и не ходят в сеть. Окружение тестов:
   - `origin` внешнего проекта — второй настоящий git-репозиторий;
   - `gh` — подставной исполняемый файл;
   - слот связки ключей — подмена функции чтения слота.

## Критерии приёмки

AC-1. Для артели окружение и аргументы вызовов `gh` и git-операций пульта
совпадают с main.

AC-2. Для учебного внешнего проекта подставной `gh` получает в окружении
`GH_TOKEN`, равный значению из слота `token_slot` записи проекта.

AC-3. Для учебного внешнего проекта git-push пульта в `origin` (второй
настоящий git-репозиторий) проходит, `.git/config` клона после операции
не изменён. В песочнице теста (`HOME`/`GIT_CONFIG_GLOBAL`/
`GIT_CONFIG_SYSTEM`) стоят два конкурирующих помощника учётных данных,
отдающие пароль, отличный от токена слота: глобальный
(`credential.helper`) и с областью URL проекта
(`credential.<URL проекта>.helper`). В окружении хостингового git-вызова
пульта:
- `git config --get-all credential.helper` даёт только помощник пульта —
  чужие помощники сброшены;
- `git credential fill` по URL проекта возвращает только токен слота
  `token_slot` проекта.

AC-4. Пустой слот `token_slot` у внешнего проекта: операция хостинга
(`gh` и git-операция с `origin`) отказывает, в тексте отказа названо имя
слота.

AC-5. После операций AC-2 и AC-3 значение токена не встречается ни в
одном журнале задачи (журнал шагов БД, логи прогона) и в выводе команд
пульта. В окружении роли задачи внешнего проекта значения токена тоже
нет. То же для отказанной хостинговой операции: `origin` отказывает в
push — текст отказа, журналы задачи и вывод команд пульта значения
токена не содержат. Значения токена нет в argv ни одного вызова git,
`gh` и помощника учётных данных, сделанного при операциях этого критерия.

AC-6. Неверный `project_skills` записи внешнего проекта (имя вне `skills/`
либо имя несуществующего файла): проверка `doctor` по этой записи даёт
fail.

AC-7. Проверка `doctor` п.5.1 на подготовленных состояниях:
- клон свежий, `origin` совпадает с `url`, fetch проходит — ok;
- время изменения `FETCH_HEAD` клона старше 24 ч — warn с текстом «клон
  не обновлялся N ч»;
- файла `FETCH_HEAD` в клоне нет (клон только что создан `git clone`) —
  warn «клон ещё не обновлялся пультом», не fail;
- клона нет: каталог проекта `.artel/projects/<имя>/` существует, а
  `.artel/projects/<имя>/repo` нет — fail;
- `origin` не совпадает с `url` — fail;
- fetch не прошёл — fail.
Рабочие копии после проверки не изменены.

AC-8. Проверки `doctor` п.5.2–5.6 на подготовленных состояниях:
- 5.2: пробный push в `refs/artifacts/*` проходит — ok, отказан — fail;
- 5.3: в дереве клона есть файл `.github/workflows/*.yml` с триггером
  `pull_request` — ok; такого файла нет — warn «verifying будет ждать до
  потолка»; сети проверка не касается;
- 5.4: подставной `gh` отвечает на
  `api repos/<владелец>/<репозиторий>/branches/<base>/protection` данными
  — сведения выведены; отказывает — вывод даёт сведение «недоступно»,
  исход проверки не fail; в окружении этого вызова `GH_TOKEN` равен токену
  слота проекта;
- 5.5: токен есть и его значение отлично от того, что подставной `gh`
  отдаёт на `auth token`, — ok; значения равны — warn со ссылкой на
  `docs/triggers.md` №24; токена нет — fail; значений токенов в выводе
  нет;
- 5.6: все пути `no_paths` есть в дереве клона — ok; путь отсутствует —
  исход не ok, путь назван.

AC-9. По записи артели `doctor` выводит для проверок п.5 решение
«неприменимо».

AC-10. В окружении с маркером `ARTEL_ROLE`:
- `doctor` по учебному внешнему проекту выводит для проверок 5.1, 5.2 и
  5.5 пропуск «только в сессии Оператора» и не делает fetch и пробный
  push;
- подменённая функция чтения слота связки ключей не вызывается ни
  `doctor`, ни хостинговой операцией пульта для этого проекта.

AC-11. Досылка коммита закрытия `doctor` (`_push_closing_sha`,
`orchestrator/doctor/artifact_branches.py:126-138`) для учебного внешнего
проекта, источник `source` — репозиторий вне `.artel/projects/<проект>/`
(как главная копия пульта), push по URL `origin` клона проекта (второй
настоящий git-репозиторий), в песочнице — конкурирующие помощники AC-3:
push проходит, в окружении этого git-вызова `git credential fill` по URL
проекта возвращает только токен слота `token_slot` проекта. Пустой слот —
отказ с именем слота. Значения токена нет в argv вызова и в выводе
`doctor`.
