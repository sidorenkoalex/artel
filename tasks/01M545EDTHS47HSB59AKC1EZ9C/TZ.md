1. Для внешнего проекта операции пульта с хостингом берут токен из слота
   связки ключей `token_slot` записи проекта. Операции хостинга: `gh` и
   git с `origin` клона (fetch, push веток задачи, `refs/artifacts/*`,
   мерж).
   - `gh` получает токен как `GH_TOKEN` в окружении вызова. Прямой `gh`
     в `orchestrator/doctor/misc_checks.py:92` (`check_base_branch`)
     переводится на тот же токен проекта.
   - git получает помощник учётных данных из окружения вызова, без
     записи в конфигурацию клона и без системного `osxkeychain`.
     `gitcmd.git` определяет проект по пути `-C` внутри
     `.artel/projects/<проект>/` и подставляет токен слота; сигнатура
     `gitcmd.git` не меняется.
   - Наблюдаемо: в песочнице теста стоят конкурирующие помощники —
     глобальный и с областью URL проекта, отдающие чужой пароль; в
     окружении хостингового git-вызова `git config --get-all
     credential.helper` даёт только помощник пульта (чужие сброшены),
     `git credential fill` по URL проекта возвращает только токен слота.
   - Push досылки коммита закрытия `doctor`
     (`orchestrator/doctor/artifact_branches.py:126-138`) по URL `origin`
     клона внешнего проекта идёт с токеном проекта тем же механизмом, в
     том числе когда источник — главная копия пульта вне
     `.artel/projects/<проект>/`.
   Пустой слот — именованный отказ с именем слота. Токен не попадает в
   журналы, вывод команд и окружение роли — в том числе при отказанной
   хостинговой операции; в argv любых вызовов токена нет. Для артели
   ничего не меняется.
2. `doctor` для каждой записи внешнего проекта выводит проверки
   ok/warn/fail:
   1. Клон `.artel/projects/<имя>/repo` (`repo_context.clone_path`): его
      нет — fail (в тесте каталог проекта при этом существует);
      `origin` ≠ `url` — fail. Время изменения `FETCH_HEAD` клона, взятое
      до fetch самой проверки, старше 24 ч — warn «клон не обновлялся
      N ч». Порог — константа `orchestrator/config.py`. `FETCH_HEAD` нет
      (свежий клон `target-init`) — warn «клон ещё не обновлялся
      пультом», не fail. Затем fetch без изменения рабочих копий;
      неуспех — fail.
   2. Пробный `git push --dry-run` в `refs/artifacts/*` с токеном п.1:
      отказ — fail.
   3. CI на `pull_request` — разбор `.github/workflows/*.yml` в клоне,
      без сети. Триггера нет — warn «verifying будет ждать до потолка».
   4. Защита базовой ветки — информационно,
      `gh api repos/<владелец>/<репозиторий>/branches/<base>/protection`
      с токеном проекта; данные недоступны — сведение «недоступно»,
      исход не fail.
   5. Токена в слоте нет — fail. Значение токена слота проекта равно
      токену, которым `gh` Оператора ходит в хостинг (`gh auth token`), —
      warn «одобрение своим же токеном технически возможно —
      `docs/triggers.md` №24», не блокирует. Значения не печатаются.
   6. Пути `no_paths` существуют в дереве клона.
   7. `project_skills` записи — проверкой части 1.
   Для артели — явное «неприменимо», не пропуск.
3. В процессе роли (маркер `ARTEL_ROLE`) токен хостинга не читается ни
   при каких командах пульта; проверки 8.1, 8.2, 8.5 там не выполняются

4. Тесты детерминированы и не ходят в сеть:
   - `origin` — второй настоящий git-репозиторий;
   - `gh` — подставной исполняемый файл;
   - слот — подмена функции чтения слота.
