# SPEC: GitLab Б2.3-1: отказ при сбое вместо пропуска

## Контекст
Часть 1 из 4 деления задачи 01M6EXF3TMNRKCZH8CS9BXXG1Z (GitLab Б2.3);
основание — ADR-0029 и находки проверяющих приёмки Б2.1а, Б2.1б, Б2.2 и
В1.1 (01.11). Сейчас в гейте мержа и в единой точке отправки несколько
мест, где сбой чтения записи проекта (`targets.TargetsError`) или БД
(`sqlite3.Error`) не отказывает, а молча пропускает проверку: задача
внешнего проекта может уйти путём слияния в `base`, мимо предела
`max_awaiting`/`max_in_flight` или мимо проверки статуса MR. Задача идёт
до открытия `gitlab`/`target-human` (часть 4): каждый такой путь должен
отказывать с причиной.

## Критерии приёмки

AC-1. Задача внешнего проекта (не артели) на гейте мержа: сбой чтения записи в `github_adapter.people_entry`/`targets.target` внутри `fsm_merge_gate` даёт отказ гейта мержа с причиной «гейт мержа неизвестен»; слияния в `base`, отправки и открытия MR нет; состояние задачи и БД не изменились.

AC-2. То же для задачи проекта `github` + `merge_gate: operator`: сбой чтения записи на гейте мержа тоже даёт отказ «гейт мержа неизвестен» без слияния, отправки и открытия MR, состояние задачи и БД не изменились.

AC-3. Единая точка отправки (`gitcmd`): сбой чтения записи проекта вне артели внутри точки отправки даёт отказ отправки с причиной «гейт мержа неизвестен»; `git push` не вызван.

AC-4. `_awaiting_limit_refuses`: сбой чтения записи (`TargetsError` в чтении `targets.target` внутри гейта) даёт отказ с причиной, а не пропуск предела `max_awaiting`; MR не открыт, состояние задачи и БД не изменились.

AC-5. `gitcmd.in_flight_refusal`: подменённый `TargetsError` в точке чтения возвращает отказ с причиной, а не `None`.

AC-6. `gitcmd.in_flight_refusal`: подменённый `sqlite3.Error` в точке чтения возвращает отказ с причиной, а не `None`.

AC-7. `gitcmd._push_plan`: `sqlite3.Error` в проверке `policy.max_in_flight` даёт отказ отправки с причиной; `git push` не вызван.

AC-8. `gitcmd.in_repo`: `sqlite3.Error` в чтении `in_repo` при отправке в проект вне артели, чья запись под белым списком (`targets.push_whitelisted`) или не прочитана, даёт отказ отправки с причиной; `git push` не вызван.

AC-9. `gitcmd.in_repo`: `sqlite3.Error` в чтении `in_repo` при отправке артели и при отправке проекта с `merge_gate: operator` отказа не даёт — отправка идёт как прежде.

AC-10. `github_adapter` (`:173`): отказ пределом отправок распознаётся по коду результата отправки — результат с кодом предела не даёт алерта и вызова `gh`; результат с обычным кодом сбоя, в stderr которого стоит строка `IN_FLIGHT_LIMIT_REASON`, отказом пределом не считается.

AC-11. `_mr_incident_stops`: статус MR вне `opened`/`merged`/`closed` (`locked`, пустая строка) даёт отказ гейта с причиной, задача остаётся на гейте, черновик не снят, исполнитель не назначен, слияния нет.

AC-12. Тест правила признака (а) `mr_sync`: у открытого MR, чей `sha` — предок `origin/<base>`, `mr-sync <id> --confirm` без `--by-content` отказывает; тест краснеет на мутации `state == "merged"` → `True` в `orchestrator/mr_sync.py`.

AC-13. Загрузка записи с `full_suite: ci` (или `both`) для хостинга, реализация которого не читает отчёт задания, отказывает `TargetsError` в процессе, где модуль `orchestrator/ci` не импортирован, так же как в процессе с ним; строка `targets.hosting_registry = …` в `orchestrator/ci.py` отсутствует.

AC-14. Вне `orchestrator/targets.py` нет новых сравнений значения `forge`/`merge_gate` с литералом, и множество `EXEMPT` сторожа ac9 (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py`) не получило новых элементов.

AC-15. Артель и проекты `github` + `merge_gate: operator` при читаемых записи и БД: путь гейта мержа и отправки прежний (слияние/отправка проходят так же, как на main), утверждения существующих тестов прежние.

## Оценка объёма и деление
Сработавшие сигналы: файлов зоны ≥ 5 (пять модулей `orchestrator/` + `tests/`),
критериев приёмки ≥ 10 (15), `budget_usd` ≥ $30 ($40 — рамка ТЗ).

Материал для решения Оператора — обоснование монолита. Задача уже сама
является частью 1 из 4 деления родителя 01M6EXF3TMNRKCZH8CS9BXXG1Z,
рамка $40 задана Оператором. Ядро задачи — одно свойство «сбой чтения
записи/БД отказывает, а не пропускает» в двух связанных точках: гейт
мержа (требования 1, 3, 8) и единая точка отправки (2, 4–7), причём
требование 1 прямо требует одинакового отказа обеих точек («Так же
отказывает единая точка отправки»). Разрез по модулям оставил бы
промежуточное состояние, где гейт мержа отказывает, а отправка в том же
сбое проходит (или наоборот) — тот самый обход, ради которого задача
заведена. Требования 9–10 малы (тест `mr_sync` без правки кода;
снятие подстановки реестра в `ci.py`/`targets.py`) и отдельной задачи
по цене шага не окупают.
