# SPEC: GitLab Б2.3-1: отказ при сбое вместо пропуска

## Контекст
Часть 1 из 4 деления задачи 01M6EXF3TMNRKCZH8CS9BXXG1Z (GitLab Б2.3);
основание — ADR-0029 и находки проверяющих приёмки Б2.1а, Б2.1б, Б2.2 и
В1.1 (01.11). Сейчас в гейте мержа и в единой точке отправки несколько
мест, где сбой чтения записи проекта (`targets.TargetsError`) или БД
(`sqlite3.Error`) не отказывает, а молча пропускает проверку: задача
внешнего проекта может уйти путём слияния в `base`, мимо предела
`max_awaiting`/`max_in_flight` или мимо проверки статуса MR. Задача идёт
до открытия `gitlab`/`target-human` (часть 4): каждый такой путь должен
отказывать с причиной.

Решения Оператора на гейте SPEC (возврат из `spec_gate`, решения по
аудиту 1–5) вошли в требования ниже: форма отказа гейта мержа и шов
подмены (решение 2 → требования 1, 3, 12), код отказа пределом
(решение 3 → требование 7), адресат-URL (решение 4 → требование 2),
исключение только артели для мест `gitcmd` (решение 5 → требования 4–6),
смысл «состояние не изменилось» (решение 1 → требование 12).

## Требования

1. Гейт мержа (`orchestrator/fsm_merge_gate.py:1516`, вызов
   `github_adapter.people_entry`, `orchestrator/github_adapter.py:347-355`,
   сейчас `TargetsError` → `None`): `github_adapter.people_entry` различает
   «гейт проекта не `target-human`» (возврат `None`) и «запись проекта не
   прочитана» (бросает `targets.TargetsError`). Место вызова в
   `fsm_merge_gate` ловит `TargetsError` и для задачи любого проекта,
   кроме артели (`config.DEFAULT_TARGET`), отказывает гейтом мержа тем же
   устройством, что `_people_refusal`: возврат `("stopped",)` и запись
   журнала действием отказа гейта мержа `PEOPLE_REFUSED_ACTION`
   («approve отклонён») с причиной «запись проекта не прочитана:
   <причина>», а не путь слияния в `base`. Задача остаётся на гейте.
   Задачи артели — без изменений.
2. Единая точка отправки (`orchestrator/gitcmd.py:928-932`) при сбое
   чтения записи проекта вне артели отказывает «гейт мержа неизвестен».
   Для проекта, узнанного по месту вызова или локальному пути, это уже
   выполнено на main (`gitcmd.py:884-886`, `:928-932`) — тест остаётся
   сторожем регрессии. Не выполнено для адресата-URL: при непрочитанной
   записи (`entries is None`) URL не сопоставляется с проектом и отправка
   считается отправкой артели (`gitcmd.py:812-816`). Требуется: отправка
   по адресу-URL внешнего проекта (URL, не совпадающий с адресом `origin`
   репозитория артели) при непрочитанной записи — отказ отправки «гейт
   мержа неизвестен — targets.yaml не читается».
3. `fsm_merge_gate._awaiting_limit_refuses` (`:1789-1808`, сейчас
   `TargetsError` → `False` на `:1796-1797`): сбой чтения записи — отказ
   гейта мержа тем же устройством, что в требовании 1 (`("stopped",)`,
   журнал `PEOPLE_REFUSED_ACTION` с причиной «запись проекта не
   прочитана: <причина>»), а не пропуск предела `max_awaiting`; MR не
   открывается.
4. `gitcmd.in_flight_refusal` (`:768-775`): сбой `TargetsError` или
   `sqlite3.Error` — отказ с причиной вместо `None` для задачи любого
   проекта, кроме артели (и `operator`, и `target-human`). Задача артели
   при сбое чтения `targets.yaml` — `None`, как прежде: пульт работает
   над собой и при сломанном файле (`orchestrator/repo_context.py:85-89`).
   Проект задачи не прочитан из БД (`sqlite3.Error` в чтении проекта) —
   задача не известна как задача артели, отказ.
5. `gitcmd._push_plan` (`:956-961`, проверка `policy.max_in_flight`):
   `sqlite3.Error` — отказ отправки с причиной вместо `waiting = None`
   для отправки в любой проект, кроме артели; у артели — как прежде.
6. `gitcmd.in_repo` (`:1242-1245`): `sqlite3.Error` — отказ отправки с
   причиной вместо `refusal = None` для отправки в любой проект вне
   артели (запись под белым списком, `merge_gate: operator` или запись не
   прочитана). Отправки артели при сбое БД идут как прежде.
7. Отказ единой точки отправки пределом `policy.max_in_flight` несёт в
   результате `gitcmd.git`/`gitcmd.in_repo` свой код возврата — именованную
   константу `gitcmd` (например `IN_FLIGHT_REFUSAL`), отличную от кода
   прочих отказов точки отправки. `orchestrator/github_adapter.py:173`
   распознаёт отказ пределом по этому коду, а не по вхождению
   `IN_FLIGHT_LIMIT_REASON` в stderr; прочие отказы и сбои за отказ
   пределом не принимаются.
8. `fsm_merge_gate._mr_incident_stops` (`:1661-1702`): статус MR вне
   `opened`/`merged`/`closed` (например `locked` или пустой) — отказ
   гейта с причиной, а не проход (сейчас проход на `:1695-1698`).
9. Правило ANSWER-1 п. 3 Б2.2 (`orchestrator/mr_sync.py:356`; код
   `mr_sync.py` не меняется, только тест в `tests/`): у открытого MR, чей
   `sha` уже предок `origin/<base>`, признак (а) не засчитывается, и
   `mr-sync <id> --confirm` без `--by-content` отказывает.
10. Проверка записи «`full_suite: ci|both` только для хостинга с чтением
    отчёта задания» (В1.1) не зависит от того, загружен ли модуль `ci`:
    реестр хостингов не подставляется при импорте `ci`
    (`orchestrator/ci.py:28`, `orchestrator/targets.py:1098`), и загрузка
    записи в `doctor` без `ci` отказывает так же, как с ним.
    `orchestrator/targets.py` в этой задаче трогается только ради этого
    требования.
11. Признак гейта проекта определяется помощниками `targets.py`
    (`push_whitelisted`, `merged_by_project_people`): сравнение значения
    `forge`/`merge_gate` с литералом вне `targets.py` и новые элементы
    `EXEMPT` сторожа ac9
    (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:416-421`)
    запрещены.
12. Тесты отказа при сбое (AC-1…AC-11) устроены так:
    - сбой подменяется в точке чтения внутри гейта или отправки, а не
      постоянной подменой загрузчика (постоянный `TargetsError`
      отказывает раньше, в `repo_context.resolve` —
      `orchestrator/fsm_merge_gate.py:1508-1514`,
      `orchestrator/repo_context.py:93-96`; постоянный `sqlite3.Error`
      валит отправку исключением в `gitcmd._project_tasks` —
      `orchestrator/gitcmd.py:215-220`; такой тест зелёный и без правки).
      Для записи шов подмены — `targets.target` (чтение внутри
      `people_entry`/`fsm_merge_gate` и `gitcmd`); для БД — чтение
      названного места (`in_flight_refusal`, проверка `max_in_flight` в
      `_push_plan`, `in_repo`);
    - тест сверяет возвращённый отказ с причиной (у гейта мержа —
      `("stopped",)` и запись журнала, у отправки — результат с
      ненулевым кодом и причиной), а не летящее исключение;
    - «состояние не изменилось» значит: состояние задачи, поля задачи,
      ссылки и ветки после отказа не изменились; ровно одна запись
      журнала об отказе допустима и обязательна;
    - шпион не видит слияния, отправки или открытия MR.

## Критерии приёмки

AC-1. Задача внешнего проекта с `merge_gate: target-human` на гейте мержа: `TargetsError`, подменённый в `targets.target` после `repo_context.resolve`, даёт возврат `("stopped",)` и ровно одну запись журнала действием `PEOPLE_REFUSED_ACTION` с причиной, начинающейся «запись проекта не прочитана:»; слияния в `base`, отправки и открытия MR нет; состояние задачи, поля задачи, ссылки и ветки не изменились.

AC-2. То же для задачи проекта `github` + `merge_gate: operator`: сбой чтения записи на гейте мержа даёт тот же отказ (`("stopped",)`, одна запись журнала `PEOPLE_REFUSED_ACTION` «запись проекта не прочитана: …») без слияния, отправки и открытия MR; состояние задачи, поля, ссылки и ветки не изменились.

AC-3. `github_adapter.people_entry`: при `TargetsError` в `targets.target` бросает `targets.TargetsError`; при читаемой записи с гейтом не `target-human` возвращает `None`; при `target-human` — запись.

AC-4. Единая точка отправки (`gitcmd`): сбой чтения записи проекта вне артели, узнанного по месту вызова, даёт отказ отправки с причиной «гейт мержа неизвестен»; `git push` не вызван (сторож регрессии, на main уже зелёный).

AC-5. Единая точка отправки: при непрочитанной записи отправка по адресу-URL, не совпадающему с адресом `origin` артели, даёт отказ отправки с причиной «гейт мержа неизвестен — targets.yaml не читается»; `git push` не вызван. Отправка артели в `origin` при непрочитанной записи проходит как прежде.

AC-6. `_awaiting_limit_refuses`: `TargetsError` в чтении `targets.target` внутри гейта даёт отказ гейта (`("stopped",)`, одна запись журнала `PEOPLE_REFUSED_ACTION` «запись проекта не прочитана: …»), а не пропуск предела `max_awaiting`; MR не открыт; состояние задачи, поля, ссылки и ветки не изменились.

AC-7. `gitcmd.in_flight_refusal` для задачи внешнего проекта (и `operator`, и `target-human`): подменённый `TargetsError` и, отдельно, подменённый `sqlite3.Error` в точке чтения возвращают отказ с причиной, а не `None`.

AC-8. `gitcmd.in_flight_refusal` для задачи артели при `TargetsError` в чтении записи возвращает `None`; `amend-tests` задачи артели при сломанном `targets.yaml` не отказывает пределом `max_in_flight` (`orchestrator/amend.py:857`).

AC-9. `gitcmd._push_plan`: `sqlite3.Error` в проверке `policy.max_in_flight` при отправке в проект вне артели даёт отказ отправки с причиной; `git push` не вызван.

AC-10. `gitcmd.in_repo`: `sqlite3.Error` в чтении `in_repo` при отправке в проект вне артели — под белым списком, с `merge_gate: operator` и с непрочитанной записью — даёт отказ отправки с причиной; `git push` не вызван.

AC-11. `gitcmd.in_repo`: `sqlite3.Error` в чтении `in_repo` при отправке артели отказа не даёт — отправка идёт как прежде.

AC-12. Отказ единой точки отправки пределом `policy.max_in_flight` возвращает из `gitcmd.git` и `gitcmd.in_repo` результат с кодом именованной константы `gitcmd` (отказ пределом); прочие отказы точки отправки (например «гейт мержа неизвестен») этот код не несут. `github_adapter` (`:173`) по результату с этим кодом не поднимает алерта и не зовёт `gh`; результат с иным ненулевым кодом, в stderr которого стоит строка `IN_FLIGHT_LIMIT_REASON`, отказом пределом не считается.

AC-13. `_mr_incident_stops`: статус MR вне `opened`/`merged`/`closed` (`locked`, пустая строка) даёт отказ гейта с причиной, задача остаётся на гейте, черновик не снят, исполнитель не назначен, слияния нет.

AC-14. Тест правила признака (а) `mr_sync`: у открытого MR, чей `sha` — предок `origin/<base>`, `mr-sync <id> --confirm` без `--by-content` отказывает; тест краснеет на мутации `state == "merged"` → `True` в `orchestrator/mr_sync.py`.

AC-15. Загрузка записи с `full_suite: ci` (или `both`) для хостинга, реализация которого не читает отчёт задания, отказывает `TargetsError` в процессе, где модуль `orchestrator/ci` не импортирован, так же как в процессе с ним; строка `targets.hosting_registry = …` в `orchestrator/ci.py` отсутствует.

AC-16. Вне `orchestrator/targets.py` нет новых сравнений значения `forge`/`merge_gate` с литералом, и множество `EXEMPT` сторожа ac9 (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py`) не получило новых элементов.

AC-17. Артель и проекты `github` + `merge_gate: operator` при читаемых записи и БД: путь гейта мержа и отправки прежний (слияние/отправка проходят так же, как на main), утверждения существующих тестов прежние.

## Оценка объёма и деление
Сработавшие сигналы: файлов зоны ≥ 5 (пять модулей `orchestrator/` + `tests/`),
критериев приёмки ≥ 10 (17), `budget_usd` ≥ $30 ($40 — рамка ТЗ).

Материал для решения Оператора — обоснование монолита. Задача уже сама
является частью 1 из 4 деления родителя 01M6EXF3TMNRKCZH8CS9BXXG1Z,
рамка $40 задана Оператором. Ядро задачи — одно свойство «сбой чтения
записи/БД отказывает, а не пропускает» в двух связанных точках: гейт
мержа (требования 1, 3, 8) и единая точка отправки (2, 4–7), причём
требование 1 прямо требует одинакового отказа обеих точек («Так же
отказывает единая точка отправки»). Разрез по модулям оставил бы
промежуточное состояние, где гейт мержа отказывает, а отправка в том же
сбое проходит (или наоборот) — тот самый обход, ради которого задача
заведена. Требования 9–10 малы (тест `mr_sync` без правки кода;
снятие подстановки реестра в `ci.py`/`targets.py`) и отдельной задачи
по цене шага не окупают.
