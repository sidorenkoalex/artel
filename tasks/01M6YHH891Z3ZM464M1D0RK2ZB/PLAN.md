# PLAN: Ускорение тестов suite_run без ослабления

## Подход
Одна смена, как и предлагает SPEC: шаг опроса переезжает в `config`, а
тестовый файл `tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py`
переводится по мандату `ANSWER-1.md` (только требования 2–7).

- `config.SUITE_RUN_POLL_SEC = 1.0`; `suite_run._wait`/`wait_request` и
  опрос `mutation_run --wait` читают его в момент паузы, своей `_POLL_SEC`
  у `suite_run.py` больше нет. Без смены поведения по умолчанию.
- Копия `config.py` песочницы дописывает `SUITE_RUN_POLL_SEC = 0.1`.
- `stop_everything`: `pids.discard(os.getpid())` после цикла сбора.
  Записи `pid`/`ppid` потомков остаются.
- Пределы: `TIMEOUT_SEC = 8` у трёх классов, гейт ac16 — 3 с плюс
  `assertEqual(result.outcome, acceptance.FULL_SUITE_TIMEOUT)`.
- ac24: у исходов, кроме «предел», `self.report(...)` без «не уложился»;
  у «зелёной» и «красной» лог базы (лог прогона из вывода запуска с
  суффиксом `-base`, как у `suite_run._log_path(..., "-base")`) содержит
  итоговую строку pytest (`PYTEST_SUMMARY`).
- Паузы ac3/ac4 (`assert_no_run`), ac9, ac20, ac21 заменены проверкой:
  сначала один снимок `/bin/ps -axww -o pid=,ppid=,command=`
  (`process_snapshot`; снимок без `os.getpid()` — провал «снимок процессов
  не получен»), затем журналы. `assert_no_process` ищет в argv id задачи,
  путь пробы и корень песочницы (в двух видах: как есть и после realpath)
  как целый путь, а не как префикс чужого пути. В ac21 процессы прогона A —
  это `holder` и его потомки по `ppid` в том же снимке. Им прощаются только
  проба и корень; id и рабочая копия B проверяются у всех процессов.
- Паузы ac6 и ac8 не трогаются.

## Риски
- Проверка процессов берёт снимок сразу после возврата команды.
  Процесс, добитый SIGKILL группы вызова, но ещё не умерший, может попасть
  в снимок. Для путей отказа (без фона) таких процессов нет. Ложный красный
  возможен лишь теоретически.
- ac24 «предел» с пределом 8 с держится запасом над быстрой частью
  прогона (около 1–1,5 с в CI). Если CI станет медленнее, первым признаком
  будет «не уложился» у зелёной или красной базы, а не молча пропущенный
  исход.

## Предложения системе
- В шаге роли `pytest -n` (xdist) падает «node down: Not properly
  terminated» на всех воркерах. Видимо, это предел числа процессов роли
  (`orchestrator/doctor/role_nproc.py`). Тесты затронутого модуля пришлось
  гонять серийно (170 с). Стоит сказать об этом в миссии или скиле.
- Запись во временный каталог `/tmp` из Bash роли отклоняется. Для
  временной мутации остаётся только правка инструментом Edit и возврат им
  же. В скиле о мутационной проверке сторожа это не сказано.
