# SPEC: Прогон планки после подтяжки main исполняет долгоживущую группу; планка без `.md` без заголовочного блока

## Контекст
После шага разработчика пульт подтягивает main в ветку задачи и прогоняет
планку: `orchestrator/pull.py:558` — `acceptance.run(tdir, cwd=wt_path)`
без `extra`, то есть только каталог `tasks/<id>/acceptance_tests/`.
Переход `in_dev → verifying` (`orchestrator/advance_gates/acceptance.py:237-260`)
и автогейт приёмки прогоняют обе группы — разовую и долгоживущую (перечень
`long_lived_manifest`, затем `acceptance.run(…, extra=long_lived)`).
Планка, целиком долгоживущая по ADR-0020 (в каталоге только
`long_lived.sha256.txt` и, возможно, README), после подтяжки даёт pytest
«collected 0 items» (код 5) — пульт считает это красным и переводит задачу в
`escalated`. 02.10 так ложно встали 01M3SA3ANYZ7036AAGXZG753E3 и
01M3XTFJCC5TG63FHW907GQM4D. Отдельно: test_author клал в `acceptance_tests/`
`README.md` без заголовочного блока; снимок артефактной ветки переносит его в
main, где `scripts/guard.py --all` требует блок у любого `.md` в `tasks/` —
30.09 main был красным 3 ч 47 мин. Правила об этом в
`skills/test-authoring.md` нет.

## Требования
1. `orchestrator/pull.py`: прогон планки после подтяжки main исполняет и
   разовую, и долгоживущую группу — тем же перечнем (`long_lived_manifest`)
   и тем же вызовом `acceptance.run(…, extra=…)`, что переход
   `in_dev → verifying`; без второй копии правила выбора файлов. Задача с
   непустым перечнем и пустой разовой группой не даёт «collected 0 items».
2. Сбой чтения перечня при подтяжке — именованный отказ (fail-closed,
   ADR-0002), не молчаливый прогон одной разовой группы.
3. Задача без перечня (прежние задачи) проходит подтяжку как сегодня.
4. `skills/test-authoring.md`: правило — в `acceptance_tests/` не класть
   файлы `.md`; пояснения к планке — в докстрингах тестов и в PLAN/SPEC
   (снимок артефактной ветки переносит каталог в main, где `guard --all`
   требует заголовочный блок у каждого `.md`). Путь защищённый — правка
   оформляется приложением PLAN (unified-диф), применяет пульт на мерже.
5. Тесты в `tests/test_pull_long_lived_plank.py`, каждый с докстрингом
   «Ловит мутацию: …», покрывают сценарии AC-1…AC-4.

## Критерии приёмки
AC-1. Целиком долгоживущая планка (в `acceptance_tests/` только перечень),
main подтянут, долгоживущий тест зелёный — задача остаётся в `in_dev`,
эскалации нет. Тест несёт «Ловит мутацию: прогон после подтяжки снова
берёт только каталог acceptance_tests/».

AC-2. Тот же случай с красным долгоживущим тестом — задача переходит в
`escalated`, как сегодня при красной планке после подтяжки. Тест несёт
«Ловит мутацию: долгоживущая группа передана, но её исход не учитывается».

AC-3. Перечень долгоживущей группы не читается при подтяжке — исход
подтяжки — именованный отказ (текст называет сбой чтения перечня), а не
зелёный прогон одной разовой группы. Тест несёт «Ловит мутацию: сбой
перечня молча сводится к пустой группе».

AC-4. Задача без перечня долгоживущей группы проходит подтяжку с прежним
поведением: прогоняется только каталог `acceptance_tests/`, зелёная планка
даёт тот же исход, что и до правки.

AC-5. Прогон после подтяжки получает долгоживущую группу через
`long_lived_manifest` и `acceptance.run(…, extra=…)` — `orchestrator/pull.py`
не несёт собственного правила выбора долгоживущих файлов.

AC-6. PLAN.md несёт приложение-диф к `skills/test-authoring.md`, добавляющее
правило: в `acceptance_tests/` не класть файлы `.md`, пояснения к планке —
в докстрингах тестов и в PLAN/SPEC, с причиной (снимок переносит каталог в
main, где `guard --all` требует заголовочный блок у каждого `.md`).
Приложение применяется `git apply --check` на чистом дереве.

задача удвоила бы цену шагов без выигрыша в мержимости.
