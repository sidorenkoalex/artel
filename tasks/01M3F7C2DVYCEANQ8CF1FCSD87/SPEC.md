# SPEC: Команда пульта ci-rerun: повтор упавшего CI ветки на verifying

## Контекст

В состоянии `verifying` цикл `auto` читает статус CI головы ветки задачи
и при завершённом красном останавливается с причиной
`config.AUTO_STOP_VERIFYING_RED` («CI ветки красный — решение
Оператора»). Команды, которая исполняет это решение, у пульта нет:
остаются `reject` в `in_dev` (лишний шаг разработчика, ~$2–5) либо
перезапуск руками через `gh run rerun` — 26.09 так было сделано дважды
для 01M3EKCZ, оба раза падал один нестабильный тест
(`tests/test_models.py::test_command_writes_nothing`, красный прогон
push при зелёном pull_request того же sha). Узел повтора в системе уже
есть и работает на гейте мержа — `orchestrator/ci.py::trigger_rerun`
(поиск прогона по sha с предпочтением упавшего, `gh run rerun --failed`,
ожидание `gh run watch` до `config.CI_RERUN_WAIT_SEC`), но на
`verifying` он не вызывается. Обратная сторона повтора известна: 22–26.09
главная ветка была красна по тесту каталога, и перезапуск тогда
маскировал бы дефект главной ветки, а не гасил флейк (урок 12.09 в
копилке — перезапуск CI замаскировал реальный дефект), поэтому команда
обязана сначала отличить флейк ветки от красноты главной ветки.

## Требования

1. Команда пульта `ci-rerun <id> --reason "<основание>"` зарегистрирована
   в `orchestrator/artel.py` — и в таблице команд, и в тексте usage.

2. Предусловие состояния и статуса: команда работает только для задачи в
   `verifying`, у которой CI головы ветки завершён и красный (исход
   `ci.VERIFYING_RED` функции `ci.verifying_status` — все проверки
   коммита `completed`, хотя бы одна с не-зелёным заключением). Любой
   другой случай — именованный отказ, называющий текущее состояние
   задачи и текущий статус CI; ничего не перезапускается, состояние
   задачи не меняется.

3. `--reason` обязателен: отсутствующее или пустое основание — именованный
   отказ до любого обращения к `gh`. Основание Оператора попадает в
   запись журнала задачи.

4. Сверка головы ветки: sha, по которому цикл остановился (sha красного
   статуса CI из последней такой записи журнала задачи), обязан совпасть
   с текущей головой ветки задачи (`ci.head_sha`). Расхождение —
   именованный отказ, называющий оба sha; повтор не запускается. Голова
   уехала — красный статус относится уже не к тому коммиту, и повторять
   по нему нечего.

5. Сверка с главной веткой: собираются имена завершённых не-зелёных
   check-run'ов головы ветки задачи и имена завершённых не-зелёных
   check-run'ов вершины главной ветки (голова `origin/<config.MAIN_BRANCH>`).
   Непустое пересечение этих двух множеств — именованный отказ «дефект
   main, не флейк» с именем совпавшего задания и sha главной ветки;
   ничего не перезапускается.

   Обоснование способа сверки (требование 2 ТЗ — обосновать в SPEC).
   Сверяются именно ИМЕНА заданий check-run'ов, потому что имя задания —
   единственная величина, общая у двух разных коммитов: sha и id прогона
   у ветки и у главной ветки различны по определению, а заключение
   различается по форме провала (`failure`/`timed_out`/`cancelled`) при
   одной и той же сломанной проверке. Имена заданий стабильны — оба
   коммита гоняются одним и тем же workflow. Сверка по именам устойчива и
   к тому, что один sha несёт два прогона (push и pull_request): имена
   заданий в них одни и те же, а множество имён дублей не создаёт. Смысл
   сверки — отличить флейк («задание красно только на ветке») от дефекта
   главной ветки («то же задание красно и на её вершине»), и повторять
   имеет смысл только первое.

6. Неизвестный статус на сверке требования 5 — отказ, а не повтор:
   вершина главной ветки не определена либо её check-run'ы не прочитаны
   (`gh` не ответил, ответ не разобран, список неполон) — именованный
   отказ, ничего не перезапуская. Это та же трактовка молчания CI, что
   несёт инвариант 19 (`docs/invariants.md`): неизвестный статус —
   не зелёный. Иначе первый же сбой `gh` превращал бы команду в тот
   самый маскирующий дефект главной ветки повтор.

7. Повтор исполняется существующим узлом `orchestrator/ci.py::trigger_rerun`
   (тот же поиск прогона по sha с предпочтением упавшего, `gh run rerun
   --failed`, ожидание `gh run watch`). Дублирующего кода поиска прогона,
   запуска повтора и ожидания не заводить.

8. Итог — запись журнала задачи (`store.journal`): основание Оператора,
   id прогона и исход ожидания (зелёный / снова красный / `gh` не
   ответил). Best-effort: сбой `gh` — не исключение и не трейсбек, а
   именованный отказ с той же записью журнала.

9. Команда сама не меняет состояние задачи и не запускает роль: после
   зелёного повтора цикл `auto` в `verifying` читает новый статус CI и
   идёт дальше штатно; после снова красного задача остаётся в
   `verifying`, а запись журнала называет этот исход.

10. Повторный вызов `ci-rerun` по той же задаче допустим только с новым
    основанием: `--reason`, дословно совпадающий с основанием последней
    записи `ci-rerun` этой задачи, — именованный отказ; новое основание
    проходит.

11. Документация: в `docs/operator-session.md` (раздел «Правки main
    только командами» либо «Запуски и рабочие копии») — строка о команде
    и о правиле «красно и на main — не перезапускать»; текст usage в
    `orchestrator/artel.py`.

12. Тесты в `tests/`: `gh` подменяется, сети нет ни в одном тесте.

## Критерии приёмки

AC-1. Задача в любом состоянии, кроме `verifying` (например `in_dev`):
`ci-rerun <id> --reason "..."` отказывает именованным отказом, текст
которого называет текущее состояние задачи и статус CI; `ci.trigger_rerun`
не вызывается, состояние задачи в БД не меняется.

AC-2. Задача в `verifying`, статус CI ветки не красный (зелёный, «проверки
идут» либо «проверок нет вовсе»): команда отказывает именованным отказом
со статусом CI; `ci.trigger_rerun` не вызывается.

AC-3. Вызов без `--reason` либо с пустым основанием: именованный отказ,
ни одного обращения к подменённому `gh` и ни одного вызова
`ci.trigger_rerun`.

AC-4. Sha красного статуса, на котором остановился цикл, не совпадает с
текущей головой ветки задачи: именованный отказ, называющий оба sha;
`ci.trigger_rerun` не вызывается.

AC-5. Среди не-зелёных завершённых check-run'ов вершины главной ветки
есть задание с тем же именем, что упало на ветке задачи: именованный
отказ «дефект main, не флейк», текст которого называет имя этого задания
и sha вершины главной ветки; `ci.trigger_rerun` не вызывается, состояние
задачи не меняется.

AC-6. Вершина главной ветки не определена либо её check-run'ы не
прочитаны (подменённый `gh` отвечает ошибкой): именованный отказ,
`ci.trigger_rerun` не вызывается.

AC-7. Штатный путь — задача в `verifying`, CI ветки красный, голова
совпадает, имена упавших заданий ветки не пересекаются с не-зелёными
заданиями вершины главной ветки: вызывается `ci.trigger_rerun` с веткой
задачи (ровно один раз, `gh` подменён), и в журнале задачи появляется
запись, несущая основание Оператора, id прогона и исход ожидания.

AC-8. Повтор завершился снова красным: запись журнала называет исход
«снова красный», состояние задачи остаётся `verifying`, роль не
запускается и перехода FSM не происходит.

AC-9. Подменённый `gh` не отвечает на запуск повтора или на ожидание:
команда завершается именованным отказом (не исключением и не
трейсбеком), запись журнала называет исход «`gh` не ответил».

AC-10. После зелёного повтора цикл `auto` в `verifying` с подменённым
статусом CI читает новый статус и продолжает штатно — сама команда
`ci-rerun` состояния задачи не меняла.

AC-11. Повторный `ci-rerun` с основанием, дословно совпадающим с
основанием последней записи `ci-rerun` этой задачи, отказывает
именованным отказом; тот же вызов с новым основанием проходит по
штатному пути AC-7.

AC-12. Текст usage `orchestrator/artel.py` несёт строку команды
`ci-rerun <id> --reason "<основание>"`, а `docs/operator-session.md` —
строку о команде и о правиле «красно и на main — не перезапускать».

## Оценка объёма и деление

Сработавшие сигналы: «число затрагиваемых модулей/файлов» (текст SPEC
называет ≥5 путей вида `orchestrator/*.py`, включая читаемые только на
чтение) и «число критериев приёмки» (12 ≥ 10).

Прогноз диффа: 20 КиБ.

Решение — **монолит**, деление не предлагается. Задача добавляет ровно
одну команду пульта, и её части неразрезаемы:

- предусловия (состояние, красный CI, совпадение головы, сверка с
  главной веткой) без самого повтора — команда, которая ничего не
  делает: нечего мержить и нечего принимать;
- повтор без предусловий — ровно тот маскирующий дефект главной ветки
  перезапуск, против которого задача и заведена (урок 12.09, красная
  главная ветка 22–26.09); такое промежуточное состояние нельзя мержить
  даже с зелёной планкой;
- регистрация команды в `orchestrator/artel.py`, строка usage и строка
  документации без тела команды — обещание Оператору несуществующего
  поведения.

Фактический объём при этом невелик: новая команда переиспользует
существующий `ci.trigger_rerun` и существующее чтение статуса
`ci.verifying_status`, а первый уровень сигнала (число файлов зоны) даёт
по зонам 4 файла — `orchestrator/ci.py`, `orchestrator/artel.py`,
`orchestrator/fsm.py`, `docs/operator-session.md` — плюс общая зона
`tests/`.

## Не входит

- Починка самих нестабильных тестов — отдельная задача от 26.09.
- Автоматический повтор без Оператора на `verifying`: решение остаётся
  за Оператором, это его команда; `orchestrator/auto.py` в части своей
  остановки по `config.AUTO_STOP_VERIFYING_RED` не меняется.
- Повтор CI главной ветки: её краснота — только условие отказа, ничего
  на ней не перезапускается.
- Правка гейта мержа: `orchestrator/fsm_merge_gate.py` не меняется, узел
  повтора там переиспользуется через `orchestrator/ci.py::trigger_rerun`.
- Новых состояний и переходов FSM задача не вводит: команда не двигает
  автомат, поэтому `tests/test_invariants.py` (защищённый путь) не
  правится.
- Только чтение, без правок: `orchestrator/fsm_merge_gate.py`,
  `orchestrator/auto.py`, `orchestrator/config.py` (действующий
  `CI_RERUN_WAIT_SEC`), `orchestrator/store.py`, `.github/workflows/ci.yml`,
  `docs/backlog.md`, `tests/test_invariants.py`.
