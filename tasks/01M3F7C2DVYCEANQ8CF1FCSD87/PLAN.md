# PLAN: Команда пульта ci-rerun: повтор упавшего CI ветки на verifying

## Подход

Команда — один новый узел в `orchestrator/fsm.py` (`cmd_ci_rerun`) плюс
три маленьких помощника в `orchestrator/ci.py`. Адрес тела выбран так, а
не новым модулем: SPEC называет зоны `orchestrator/fsm.py`/
`orchestrator/ci.py`/`orchestrator/artel.py`, а `fsm.py` уже держит
операторские команды над задачей (`cmd_approve`, `cmd_reject`) и
константу `VERIFYING_STATUS_ACTION`, из записи которой команда читает sha
остановки цикла (требование 4). Импорт `ci` в `fsm.py` цикла не создаёт:
`orchestrator/ci.py` импортирует только `config` и `gitcmd`.

**Повтор — существующим узлом** (требование 7): `ci.trigger_rerun(branch)`
вызывается один раз, своего поиска прогона/`gh run rerun`/`gh run watch`
команда не заводит. Сигнатура `trigger_rerun` не меняется — её второй
вызыватель, гейт мержа (`orchestrator/fsm_merge_gate.py`), SPEC объявил
неизменяемым.

**Три помощника в `orchestrator/ci.py`** — там, где живёт знание о формате
текстов, которые сам этот модуль и порождает (тот же приём, что уже несут
`verifying_is_red`/`status_kind`):

- `failed_check_names(sha)` -> `(множество имён | None, причина)` — имена
  ЗАВЕРШЁННЫХ не-зелёных check-run'ов коммита. Один источник и для головы
  ветки задачи, и для вершины главной ветки (требование 5 сверяет два
  коммита одним и тем же вопросом), поэтому дублирования разбора ответа
  `gh` не возникает.
- `red_status_sha(note)` — короткий sha из `note` красного исхода
  `verifying_status` (парный к `verifying_is_red`: тот отвечает «красный
  ли», этот — «про какой коммит»).
- `rerun_started(note)` — запустился ли повтор по `note` из
  `trigger_rerun`. Нужен, чтобы отличить исход «`gh` не ответил на
  ЗАПУСК» от исхода ожидания: без него сбой запуска журналировался бы как
  состоявшийся повтор (AC-9).

**Сверка по именам заданий** (требование 5, обоснование — в SPEC): имя
задания — единственная величина, общая у двух разных коммитов.
Пересечение непусто -> отказ «дефект main, не флейк».

**Неизвестный статус вершины главной ветки — отказ** (требование 6,
инвариант 19). Сюда же отнесён случай «у вершины main нет ни одной
проверки CI»: SPEC перечисляет причины отказа как «`gh` не ответил, ответ
не разобран, список неполон», и пустой список формально не из них, но
сверить красноту с коммитом, у которого проверок нет, невозможно —
отличить флейк от дефекта main нечем. Трактовка взята у соседа по модулю:
`ci.branch_status` для того же обстоятельства уже отвечает «нет ни одной
проверки CI — статус неизвестен». Расхождение с буквой требования 6
отмечено здесь явно, чтобы ревью решало его как решение, а не как
недосмотр.

**Вершина главной ветки** читается существующей `fsm._origin_main_sha`
(голова `origin/<config.MAIN_BRANCH>` через `gitcmd.fetch_ref_sha`, без
правки локального `refs/heads/main`), без параметра `repo`: чтение
check-run'ов (`ci.check_runs`) и так умеет только self-репозиторий, и
вводить половинчатую поддержку внешнего target'а эта задача не будет.

**Журнал** — одна запись действия `CI_RERUN_ACTION` на состоявшийся
повтор: текст `trigger_rerun` (несёт id прогона), исход ожидания
(зелёный / снова красный / `gh` не ответил) и основание Оператора
ПОСЛЕДНИМ полем за маркером `основание Оператора: `. Последним — чтобы
повторный вызов (требование 10) доставал прежнее основание дословно
одним `rpartition`, не ломаясь на многострочном основании. Отказы
журналируются ДРУГИМ действием (`ci-rerun отклонён`) — тем же приёмом и
по той же причине, что `amend._refuse_traceability` не переиспользует
`AMEND_ACTION`: отказ не должен засчитываться как состоявшийся повтор
при сверке требования 10.

**Исход определяется повторным чтением статуса** `ci.verifying_status` уже
после `gh run watch`, а не пересказом вывода `gh`: зелёный -> «стал
зелёным», красный -> «снова красный», всё остальное (нет ответа, идёт)
-> «исход неизвестен — `gh` не ответил». Так запись журнала несёт
собственный вердикт пульта, а не чужое слово из stderr.

**Состояние задачи команда не трогает** (требование 9): ни `set_state`,
ни запуска роли — после зелёного повтора задачу двигает следующий опрос
`fsm.cmd_advance` в `verifying`, единственная точка движения автомата.

**Lease** берётся как у сестринской операторской команды
`amend.cmd_amend_tests` (`lease.run_locked`): `ci-rerun` пишет журнал и
дёргает внешний CI по задаче — параллельная сессия не должна делать это
одновременно.

Потолок задачи не переоценивается: SPEC взял $30 рамкой Оператора
осознанно (раздел «Материалы» SPEC), и число файлов/шагов этого плана
совпадает с оценкой SPEC (4 файла зоны + `tests/`) — оснований поднимать
потолок нет.

## Влияние на систему

**Что затрагивается за пределами правки.** Новый публичный узел
`fsm.cmd_ci_rerun` и три новые функции `orchestrator/ci.py`.
Существующие функции не меняются ни одна: `ci.trigger_rerun`,
`ci.find_run_id`, `ci.verifying_status`, `ci.check_runs`,
`fsm._origin_main_sha` вызываются как есть, с прежними сигнатурами.
`orchestrator/fsm.py` получает новый импорт `ci` — цикла нет
(`orchestrator/ci.py` импортирует только `config`/`gitcmd`), карта
кодовой базы перегенерируется тем же коммитом.

**Инварианты, гейты, лимиты рядом — и почему не ослаблены.**

- Инвариант 19 («неизвестный статус — не зелёный») новой командой не
  ослабляется, а распространяется на новую поверхность: неизвестный
  статус вершины main отказывает повтору. `tests/test_invariants.py`
  (защищённый путь) не правится — новых состояний и переходов FSM задача
  не вводит.
- Гейт мержа (`orchestrator/fsm_merge_gate.py`) не тронут: узел повтора
  переиспользуется, его поведение и текст возврата прежние. Тесты
  `tests/test_ci_status.py::TriggerRerunTest`,
  `tests/test_ci_status_kind_gate.py`, `tests/test_merge_gate_ci_wait.py`
  остаются зелёными без правки ассертов.
- Единственная точка движения автомата (`fsm.cmd_advance`) сохранена:
  `cmd_ci_rerun` не зовёт ни `store.set_state`, ни `runner`. Остановка
  цикла `auto` по `config.AUTO_STOP_VERIFYING_RED` не меняется —
  `orchestrator/auto.py` и `orchestrator/config.py` не правятся.
- Замок параллельных сессий (`lease`) не ослабляется — новая команда
  сама проходит через `lease.run_locked`, как остальные мутирующие
  команды задачи.
- Ни один существующий тест, гейт, лимит или guard-проверка не
  удаляются и не смягчаются.

**Откат.** Revert одного merge-коммита: новая команда — чистое
добавление (новые функции + запись в таблице команд + строки usage и
документации). После revert поведение пульта побайтно прежнее — ни
одной существующей ветки кода команда не переписывает.

## Риски

- Потолок $30 при 12 критериях приёмки и 12 файлах планки: вторая-третья
  итерация ревью может его исчерпать. Поднимать не стал — рамку задал
  Оператор явно; если потолок упрётся, это его решение через `budget`.
- Пустой список check-run'ов вершины main трактуется как «статус
  неизвестен» (отказ) — чуть строже буквы требования 6. Разобрано в
  «Подходе»; если ревью прочтёт требование 6 буквально, правка
  однострочная.
- `ci.check_runs` не умеет внешний target (`repo=` у неё нет) — команда
  наследует это ограничение, как и `ci.verifying_status`, которую
  `verifying` уже вызывает для любого target'а. Расширение — не эта
  задача.

## Предложения системе

- `config.AUTO_STOP_VERIFYING_RED` подсказывает Оператору только
  `reject <id>` — после этой задачи у красного CI на `verifying` есть
  второй, дешёвый путь (`ci-rerun`), но подсказка цикла о нём не знает
  (`orchestrator/config.py`/`orchestrator/auto.py` объявлены в SPEC
  «Не входит»). Строка подсказки и команда живут в разных задачах —
  класс «команда добавлена, подсказка остановки не обновлена».
- `orchestrator/ci.py` — единственный модуль, чьи решения передаются
  между узлами СТРОКОЙ, разбираемой по подстроке (`verifying_is_red`,
  `status_kind`, теперь `rerun_started`/`red_status_sha`). Приём каждый
  раз документируется заново как вынужденный; похоже, узлу пора
  возвращать структуру исхода, а текст собирать на границе журнала.
