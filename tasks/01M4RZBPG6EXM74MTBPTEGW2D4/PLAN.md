# PLAN: Записка следующему шагу и «Чего не хватило» (К-2б)

## Подход

Один контракт с двух сторон — сохранение (`checkpoint.py`) и доставка
(`brief.py` + `role_prompt.py`), плюс освобождение записки от структурной
проверки (`guard.py`, `fsm_merge_gate.py`). Задача монолитом, как в SPEC.

- **guard.** Кортеж `STEP_NOTE_ROLES` (пять агентских ролей);
  `TASK_ROOT_ALLOWED_MD` дополняется точными именами `NOTE-<роль>.md`,
  собранными из кортежа (`re.escape`), не маской. `is_step_note(path)` —
  по образцу `is_task_passport`: имя из кортежа и `path.parent.parent.name
  == "tasks"`. `guard --all` исключает записку из обхода `*.md` (как
  паспорт), проверка одного файла печатает пометку пропуска и не зовёт
  `check`/`spec_path_errors`/`plan_appendix_errors`.
- **Гейт мержа.** `_task_docs_violations` пропускает `is_step_note` рядом с
  паспортом. Записка в `acceptance_tests/` и подкаталогах — как прежде.
- **Автокоммит.** `_journal_stray_step_artifacts(conn, task_id, files,
  role=None, baseline_sha="")` после фильтра посторонних файлов
  отфильтровывает записки (`_filter_step_notes`):
  - `role is None` (старт шага, `harvest_code_copy_docs`) — любой
    `NOTE-<роль>.md` отброшен с записью «записка из рабочей копии кода
    отброшена: автор не определён»;
  - иначе записка «написана шагом» (`_note_written_by_step`) — если её
    байты не совпадают с объектом git того же пути в выкладке
    `baseline_sha`, а при пустой выкладке — в голове ссылки. Сравнение по
    sha объекта git (`git rev-parse <rev>:<путь>` против sha1 `blob N\0…`
    байтов) — побайтно, без декодирования. Неизменённая выкладка остаётся
    в `files` без журнала, дальше её обрабатывает конфликт-гвард как прежде;
  - написанная шагом чужая — отброшена, «чужая записка отброшена» (имя
    файла, роль шага);
  - своя крупнее `STEP_NOTE_STORE_MAX_BYTES` = 65536 — отброшена, «записка
    слишком велика» (роль, размер).
  После успешного коммита `_commit_step_artifacts_to_branch` (непустая
  деталь) `_commit_external_step_artifacts` журналирует «записка шага
  сохранена» для своей записки, написанной шагом и оставшейся в `files`.
  Деталь `<роль>: <N> байт, sha256=<hex>` собирает `step_note_saved_detail`,
  разбирает `parse_step_note_saved` — обе в `checkpoint.py`.
- **Бриф.** `brief.step_notes_block(conn, task_id, role)` — публичный
  сборщик блока: журнал задачи → разбор записей «записка шага сохранена»
  (`checkpoint.parse_step_note_saved`, ленивый импорт — без цикла
  `checkpoint → workspace → runner → brief`) → последняя запись на роль →
  своя + самая свежая по `id` записи из `STEP_NOTE_FOREIGN_AUTHORS[R]`
  (одна таблица в `brief.py`). Текст — `artifact_branch.show` по ветке
  `artifact_source.resolve`; sha256 `text.encode()` сверяется с записью
  (иначе пометка + запись журнала «записка изменена вне шага: не
  включена»); не прочитана — пометка «записка не прочитана: <причина>»;
  пустая после `.strip()` — пропуск. Усечение по `STEP_NOTE_MAX_BYTES` =
  4096 байтам с откатом к границе символа и пометкой вне границы.
  Компонент — `_journal_component` с новым необязательным `body`: хэш —
  от текста записки до нейтрализации, в границу идёт тело, где id запуска
  заменён (поддельный маркер этого запуска перестаёт быть маркером).
  Заголовок компонента — файл, роль-автор, время записи о сохранении.
  Нет ни одного элемента — пустая строка, журнал не трогается.
- **Миссия.** `role_prompt.step_note_note(task_id, role, docs_dir)` по
  образцу `docs_dir_note`: один абзац (без пустых строк) с путём
  `<docs_dir>/NOTE-<роль>.md`, разделами, потолками
  `str(STEP_NOTE_MAX_BYTES)`/`str(STEP_NOTE_STORE_MAX_BYTES)` и
  обязательными фразами; test_author — фраза требования 6, spec_auditor и
  reviewer — фраза требования 7. Добавляется только при `docs_dir`.
  `mission_brief_package` дописывает блок записок к `brief_text` (у
  reviewer/test_author без брифа блок им становится).

## Шаги

1. guard: `STEP_NOTE_ROLES`, белый список, `is_step_note`, `--all` и
   проверка одного файла; гейт мержа.
2. checkpoint: константы, фильтр записок, запись о сохранении, сборка и
   разбор детали.
3. brief + role_prompt: блок записок, абзац миссии; подмена сборщика
   блока в пяти тестах требования 14.
4. Юнит-тесты сверх долгоживущих файлов задачи: разбор/сборка детали
   записи о сохранении, нейтрализация маркера при усечённой записке.
   Карта `docs/codebase-map.md`.

## Влияние на систему

- Белый список корня каталога задачи расширяется пятью точными именами;
  `NOTE.md`/`NOTE-<не роль>.md` остаются посторонними. Освобождение от
  структурной проверки — только `is_step_note` первого уровня, PLAN/SPEC/
  REVIEW проверяются как прежде; записка в `acceptance_tests/` — как
  прежде (`.+\.md` планки → `check_content`).
- Конфликт-гвард не меняется: неизменённая выкладка чужой записки
  проходит в него как любой другой файл.
- `wrap_boundary` не меняется; нейтрализация — только в компоненте
  записки.
- Пять существующих тестов получают одну дополнительную подмену
  `brief.step_notes_block`; утверждения не меняются.
- Откат — revert merge-коммита: записки в ссылках останутся файлами,
  которые guard снова начнёт называть посторонними; данных схемы БД нет.

## Риски

- Записка, которую роль не трогала, но выкладка которой не состоялась

  повторную запись о сохранении — та же запись с тем же sha, бриф от неё
  не портится.

## Предложения системе

- `orchestrator/plank_run.py`: у задачи, где планка — только долгоживущие
