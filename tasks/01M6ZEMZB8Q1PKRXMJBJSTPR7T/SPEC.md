# SPEC: Тёплый байткод интерпретатора в прогонах pytest пульта: свежий префикс наполняется шаблоном путей интерпретатора

## Контекст
`_pytest_env` (`orchestrator/acceptance.py:72-93`) и `_own_env`
(`:190-213`) дают каждому прогону pytest пульта свежий пустой
`PYTHONPYCACHEPREFIX` (SPEC 01M3Y7G6T3MK7A899521VF9N7B): так устаревший
байткод рабочей копии не исполняется. Побочный эффект — каждый прогон
заново компилирует всё импортируемое из путей интерпретатора (pytest,
pluggy, xdist, execnet, стандартная библиотека) в главном процессе и в
каждом рабочем процессе xdist: замер 09.11 — 0,89 с против 0,27 с при
`-n 1` на проекте из трёх тестов. Решение Оператора 09.11.2026: тёплый
кеш делает пульт; свежим и не разделяемым между прогонами остаётся
байткод всего, что лежит вне путей интерпретатора, байткод путей
интерпретатора берётся готовым из шаблона.

## Требования
1. **Шаблон байткода интерпретатора.** Для каждого интерпретатора
   прогона пульт держит шаблон — каталог в формате `PYTHONPYCACHEPREFIX`
   с байткодом только файлов из путей этого интерпретатора.
   - Пути интерпретатора — `sys.prefix`, `sys.base_prefix`,
     `sys.exec_prefix` и каталоги `site-packages`, как их сообщает сам
     этот интерпретатор (не процесс пульта). Путь, равный корню файловой
     системы, путём интерпретатора не считается.
   - Ключ шаблона — реальный путь исполняемого файла, его версия и
     `sys.prefix`: исполняемый файл venv — символьная ссылка на базовый
     интерпретатор, реальный путь у разных venv одного базового Python
     один и тот же, а `site-packages` у них разные.
   - Место шаблонов — константа `config.PYCACHE_TEMPLATES_DIR`: вне
     `config.ROOT`, вне `config.WORKTREES` и `config.PROJECTS` (рабочие
     копии и клоны), не выводится из `HOME` (HOME роли —
     `.artel/home` внутри `config.ROOT`). Тесты подменяют её каталогом
     песочницы.
   - Сборка (решение аналитика по п. 1 ТЗ): шаблона для ключа нет или он
     повреждён — пульт собирает его перед прогоном пробным прогоном
     pytest этим интерпретатором в пустом временном каталоге с отдельным
     временным префиксом и без `PYTHONDONTWRITEBYTECODE` в окружении
     пробного прогона (с одним рабочим процессом xdist, если xdist у
     интерпретатора есть), затем оставляет в шаблоне только файлы,
     допущенные правилом требования 2. Так шаблон держит ровно тот
     байткод путей интерпретатора, который импортирует прогон pytest, и
     собирается при `PYTHONDONTWRITEBYTECODE=1` у самого прогона.
   - Обновление (решение аналитика по п. 1 ТЗ): собранный шаблон не
     обновляется; модуль пути интерпретатора, изменённый после сборки,
     отбрасывается проверкой свежести самого Python и компилируется в
     префикс прогона заново (тот же механизм, что у запуска Python вне
     пульта). Обновить шаблон — удалить его каталог: следующий прогон
     соберёт заново.
   - Интерпретатор прогона: у раннера пульта — первый элемент команды
     `_pytest_command` (по умолчанию `stack.pytest_python_executable()`);
     у `pytest-own` — `command[0]` профиля, только если его базовое имя —
     `python`, `python3` или `python3.<N>`; иначе (обёртка, `uv run` и
     т.п.) интерпретатор пульту не известен, команда проекта ради его
     выяснения не исполняется, прогон идёт с пустым префиксом без строки
     о сбое.
2. **Наполнение свежего префикса.** `_pytest_env` и `_own_env`
   по-прежнему заводят на каждый прогон новый каталог префикса во
   временном каталоге и убирают его на выходе (в том числе по таймауту и
   исключению); перед прогоном каталог наполняется полной копией файлов
   шаблона своего интерпретатора (решение аналитика по п. 2 ТЗ: копия,
   не ссылки, — запись прогона в свой префикс не меняет шаблон). В
   префикс попадает только файл шаблона, чей исходный путь лежит под
   путём интерпретатора и не лежит ни под `cwd` прогона, ни под
   `config.WORKTREES`, ни под `config.PROJECTS`; прочие файлы шаблона
   при наполнении пропускаются. `config.ROOT` целиком не исключается:
   venv пульта `config.VENV_DIR` лежит под ним (`orchestrator/config.py:131`),
   а файлы `config.ROOT` вне путей интерпретатора отсекает основное
   правило.
3. **Отказ шаблона не ломает прогон.** Шаблона нет и он не собирается,
   повреждён (нет отметки завершённой сборки, копирование из него падает
   ошибкой ОС) — прогон идёт с пустым префиксом, как сейчас, исход
   прогона от этого не зависит; в stderr пульта — одна строка, которая
   начинается с `шаблон байткода интерпретатора недоступен`.
4. **Гонка.** Сборка — во временный каталог рядом с местом шаблона с
   атомарной заменой: параллельные прогоны (xdist набора, параллельные
   задачи) видят либо отсутствие шаблона, либо собранный целиком.
   Проигравший гонку сборщик оставляет уже стоящий шаблон и убирает свой
   временный каталог.
5. Поведение гейтов, исходы прогонов и все свойства SPEC
   01M3Y7G6T3MK7A899521VF9N7B, кроме пустоты префикса, не меняются;
   залоченный `tests/test_01m3y7g6t3mk7a899521vf9n7b_pycache.py` зелёный
   без правки.
6. **Свидетельства (не тесты).** В отчёте разработчика — замер прогона
   пульта на проекте из трёх тестов (факт 2 ТЗ) до и после: с собранным
   шаблоном при `-n 1` не больше 0,5 с на машине Оператора. На приёмке —
   сумма времени junit CI ветки не больше суммы прогона базы задачи, ни
   один тест не сменил исход.

## Критерии приёмки

AC-1. Given шаблон интерпретатора пульта собран (место шаблонов — каталог
песочницы), When прогон пульта (`acceptance.run` с `cwd` на рабочую копию)
на рабочей копии, где у модуля лежит `.pyc`, устаревший относительно
исходника с тем же временем изменения и размером, Then исполняется
текущий исходник, а префикс прогона в момент вызова pytest содержит копию
байткода шаблона (непуст). Поверхности решения нет: это сквозное
поведение настоящего прогона pytest, правила отбора держат AC-2 и AC-3.
Размер проверки: средний

AC-2. Путь файла внутри каталога в формате `PYTHONPYCACHEPREFIX`
переводится в абсолютный путь исходника: `<каталог>/<имя>.<тег>.pyc`
относительно префикса даёт `/<каталог>/<имя>.py`; путь, который не
кончается на `.pyc` или не несёт тега интерпретатора в имени, даёт
`None`.
Поверхность решения: orchestrator.acceptance.pycache_source(relative_path: str) -> str | None
Размер проверки: малый

AC-3. Исходник допускается в префикс тогда и только тогда, когда он
лежит под одним из путей интерпретатора (путь `/` не в счёт) и не лежит
ни под одним исключённым каталогом; «лежит под» — по границе компонента
пути (`/a/lib` не покрывает `/a/lib2/x.py`, сам `/a/lib/x.py` покрыт).
Поверхность решения: orchestrator.acceptance.template_admits(source: str, interpreter_paths: list[str], excluded: list[str]) -> bool
Размер проверки: малый

AC-4. Given шаблон, в который подложен байткод файла из `cwd` прогона и
файла под `config.ROOT` вне путей интерпретатора, When прогон пульта
(`acceptance.run`, `acceptance.collect`, `acceptance.run_full_suite`),
Then в префиксе в момент вызова pytest нет ни одного файла, чей исходный
путь (AC-2) не допущен правилом AC-3 с исключёнными `cwd` прогона,
`config.WORKTREES` и `config.PROJECTS`, а подложенный байткод не
исполняется. Критерий подключения правила AC-3 к наполнению.
Размер проверки: средний

AC-5. Given шаблон, When два прогона подряд, и каждый пишет байткод в
свой префикс (без `PYTHONDONTWRITEBYTECODE`), Then содержимое шаблона
(перечень файлов и их байты) не меняется, префиксы прогонов — разные
новые каталоги, ни один из них не совпадает с каталогом шаблона и не
ведёт в него ссылкой. Поверхности решения нет: это поведение файловой
системы при прогоне, отдельного решения в нём нет.
Размер проверки: средний

AC-6. Given шаблона нет и сборка его падает, или каталог шаблона
повреждён (нет отметки завершённой сборки), When прогон пульта, Then
исход прогона тот же, что с пустым префиксом, префикс в момент вызова
пуст, и в stderr пульта ровно одна строка, начинающаяся с `шаблон
байткода интерпретатора недоступен`. Критерий подключения требования 3;
поведение без отдельной функции решения.
Размер проверки: средний

AC-7. Каталог шаблона — прямой потомок `config.PYCACHE_TEMPLATES_DIR`;
одинаковые реальный путь, версия и `sys.prefix` дают один каталог,
различие любого из трёх — разные каталоги.
Поверхность решения: orchestrator.acceptance.template_dir(executable: str, version: str, prefix: str) -> str
Размер проверки: малый

AC-8. `config.PYCACHE_TEMPLATES_DIR` после `os.path.realpath` не лежит
под `config.ROOT`, `config.WORKTREES` и `config.PROJECTS`. Факт
константы, поверхности решения нет.
Размер проверки: малый

AC-9. Given несколько сборок шаблона одного ключа идут одновременно,
When они завершаются, Then каталог шаблона в любой момент наблюдения
либо отсутствует, либо несёт отметку завершённой сборки и полный набор
файлов; после завершения стоит ровно один шаблон, временных каталогов
сборки рядом с ним не осталось. Поведение последовательности действий с
файловой системой, поверхности решения нет.
Размер проверки: средний

AC-10. Given в окружении пульта `PYTHONDONTWRITEBYTECODE=1` и шаблона
нет, When прогон пульта, Then шаблон собран и содержит байткод модулей
путей интерпретатора (в том числе pytest), а префикс прогона в момент
вызова наполнен им. Поведение сборки, поверхности решения нет.
Размер проверки: средний

AC-11. Интерпретатор прогона `pytest-own` распознаётся по `command[0]`
профиля: базовое имя `python`, `python3` или `python3.<N>` — возвращается
сам `command[0]`; любое другое (`uv`, `./run-tests.sh`, `pytest`) и
пустая команда — `None`.
Поверхность решения: orchestrator.acceptance.own_interpreter(command: list[str]) -> str | None
Размер проверки: малый

AC-12. Given профиль `pytest-own`, When прогон с `command[0]`,
распознанным AC-11, Then префикс в момент вызова наполнен шаблоном этого
интерпретатора; When прогон с нераспознанным `command[0]`, Then префикс
пуст, строки о сбое шаблона нет, команда проекта ради выяснения
интерпретатора не исполнялась. В обоих случаях `HOME` и префикс — новые
каталоги, убранные после возврата. Критерий подключения AC-11.
Размер проверки: средний

AC-13. Тесты этой задачи вместе с
`tests/test_01m3y7g6t3mk7a899521vf9n7b_pycache.py` убивают каждую из
мутаций `artel.py mutation-run <id> --ref head --tests <файл приёмочных
тестов задачи>` и `--tests tests/test_01m3y7g6t3mk7a899521vf9n7b_pycache.py`:
«префикс наполняется и байткодом путей `cwd`», «шаблон копируется
ссылкой на сам каталог, запись прогона меняет шаблон», «префикс не
наполняется, а подменяется самим шаблоном», «префикс убран из окружения
прогона» (последнюю — ac6 залоченного теста). Факт задачи о силе тестов,
поверхности решения нет.
Размер проверки: большой — убитость мутации видна только прогоном
мутаций командой пульта с дочерними процессами pytest.

## Оценка объёма и деление
Сработавшие сигналы: число критериев приёмки ≥ 10 (13); `budget_usd` ≥ $30
($50).

**Обоснование монолита** (материал для решения Оператора): вся механика
— в одном модуле `orchestrator/acceptance.py` (плюс одна константа
`config`). Сборка шаблона без наполнения префикса не даёт эффекта и
мёртвым кодом лежит в main; наполнение без сборки наполнять нечем.
Разрез «сборка / наполнение» режет зону `orchestrator/acceptance.py`
поперёк, и ни одна часть не проверяема своими критериями отдельно: AC-1,
AC-4, AC-5, AC-10 требуют обеих половин. Объём кода умеренный (по оценке
— две-три функции правила, сборка, наполнение), число критериев выросло
от раскладки правил на малые проверки по ADR-0032.

  (только чтение).
- Автоматическое обновление собранного шаблона (по смене пакетов
  интерпретатора, по времени) и команда пульта для его сброса.
- Выяснение интерпретатора `pytest-own` исполнением команды проекта.
- Замеры требования 6 — свидетельства в отчёте разработчика и на
  приёмке, не тесты набора.
- Зелёный полный набор `tests/` и CI ветки, неизменность защищённых
  путей — их держит пульт.
