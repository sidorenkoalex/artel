# SPEC: R2 — `fsm_advance.py`: гейты `in_dev` и `review` как предикаты с единым исходом

## Контекст
Роадмап §3, фаза R, пункт R2. Замер 06.09 (после мержа №15): `review` —
173 строки, `in_dev` — 127, `_capacity_gate_refuses` — 89,
`_review_rework_gate_refuses` — 92. Переходы `in_dev -> review` и
`review -> verifying` держат цепочку гейтов (ёмкость, зоны, рубеж
«замечания не отработаны», свежесть/подтяжка, guard PLAN/REVIEW), каждый
гейт — своя копия связки «проверка → запись отказа в журнал → подсказка
Оператору»; регрессии №13 и №15 обе жили в этих копиях. Задача убирает
дублирование, не трогая поведение.

## Требования
1. Единый неизменяемый тип исхода гейта (например `GateRefusal(action,
   detail, hint)`) либо `None` — гейт пройден.
2. Каждый гейт — функция-предикат `(conn, task_id, t, ...) ->
   GateRefusal | None` без побочных эффектов: не пишет в журнал, не
   печатает.
3. Общий каркас — одна функция, которая применяет список гейтов по
   порядку и на первом отказе делает то, что сегодня делает каждая
   копия: запись `store.journal(..., "переход отклонён: ...", detail)`,
   печать подсказки, возврат прежнего состояния. Порядок гейтов и их
   тексты (action/detail/hint) — прежние; PLAN.md перечисляет их
   таблицей «гейт → прежнее место → текст».
4. Тела `in_dev` и `review` после разбора — короткие композиции (цель
   ≤ 40 строк тела каждой), без новых уровней вложенности условий.
   Сигнатуры точек входа `in_dev(conn, task_id, t, tdir, target,
   state)`, `review(conn, task_id, t, tdir, target, state)` и модульные
   функции, которые тесты подменяют через `mock.patch.object
   (fsm_advance, ...)`, сохраняются.
5. Юнит-тесты на каркас: порядок применения гейтов, остановка на первом
   отказе, ровно один вызов журнала на отказ, отсутствие записей при
   прохождении.
6. Смоук: три записанных сценария (отказ гейта ёмкости, отказ гейта
   зон, отказ рубежа «замечания не отработаны» регрессий №13/№15) дают
   тот же журнал и stdout байт-в-байт, что до правки — фикстура
   снимается до правки кода.
7. Поведение не меняется: тексты отказов и записей журнала байт-в-байт
   те же; существующие тесты проходят без правки утверждений; защиты и
   инварианты не затрагиваются.

## Критерии приёмки
AC-1. Существует единый неизменяемый тип исхода гейта, несущий данные,
достаточные для воспроизведения текущего действия отказа (текст для
`store.journal` и текст подсказки для печати); отсутствие отказа
выражается значением `None`.

AC-2. Каждый гейт — функция-предикат `(conn, task_id, t, ...) ->
<тип исхода> | None` без побочных эффектов: не вызывает `store.journal`
и не печатает.

AC-3. Существует одна функция-каркас, которая применяет список гейтов
по порядку и останавливается на первом гейте, вернувшем отказ, не
вызывая последующие гейты списка.

AC-4. На первом отказе каркас делает ровно одну запись
`store.journal(..., "переход отклонён: ...", detail)` и печатает
подсказку — переход не происходит (возвращается прежнее состояние).

AC-5. Порядок применения гейтов и тексты отказов (action/detail/hint)
для переходов `in_dev -> review` и `review -> verifying` не изменились
относительно кода до рефакторинга; PLAN.md несёт таблицу «гейт →
прежнее место → текст», подтверждающую соответствие.

AC-6. Тела функций `in_dev(conn, task_id, t, tdir, target, state)` и
`review(conn, task_id, t, tdir, target, state)` после рефакторинга —
короткие композиции вызовов, каждая ≤ 40 строк, без новых уровней
вложенности условий; публичные сигнатуры и имена модульных функций,
подменяемых тестами через `mock.patch.object(fsm_advance, ...)`,
сохранены.

AC-7. Существующие тесты проходят без правки их утверждений.

AC-8. Юнит-тесты на каркас проверяют: порядок применения гейтов
соответствует заданному списку; остановку на первом отказе (гейты
после отказавшего не вызываются); ровно один вызов `store.journal` на
отказ; отсутствие записей в журнале и печати при прохождении всех
гейтов списка.

AC-9. Для трёх сценариев, зафиксированных фикстурой до правки кода
(отказ гейта ёмкости, отказ гейта зон, отказ рубежа «замечания не
отработаны» регрессий №13/№15), журнал (`store.journal`) и вывод stdout
после рефакторинга совпадают байт-в-байт со снятой фикстурой.

## Оценка объёма и деление
Сработавший сигнал: «бюджет» (`budget_usd: 35` ≥ порога $30,
`orchestrator/config.py::SPLIT_SIGNAL_BUDGET_USD`).

Обоснование монолита — задачу нельзя разрезать без атомарной потери
смысла:
- Требование 1 явно про ЕДИНЫЙ тип исхода гейта, общий для `in_dev` и
  `review`; введение типа/каркаса только под одну из функций и перенос
  второй отдельной подзадачей оставляет вторую функцию на старом
  ад-хок паттерне до мержа второй части — тот самый дубль связки
  «проверка → журнал → подсказка», который и есть предмет задачи,
  сохранился бы в системе дольше, чем нужно.
- Обе функции живут в одном файле (`orchestrator/fsm_advance.py`) —
  единственная заявленная зона задачи. Деление по функциям не делит
  зону: обе части претендовали бы на тот же файл и физически не могут
  идти параллельно (zone-lock сериализует их в любом случае), то есть
  раздельные шаги analyst/reviewer/developer/test_author на каждую
  часть добавили бы накладные расходы (роадмап §4 копилка: цена шага
  стабильна, цену задачи задаёт число шагов) без выигрыша в
  параллельности, которую деление обычно даёт.
- Роадмап уже выполнил деление на уровне пункта: R2 (гейты `in_dev`/
  `review`) отделён от R3 (`fsm.py`) как отдельная работа — это и есть
  границы, которые Оператор счёл мержимыми по отдельности; дальнейшее
  дробление внутри самого R2 не запрошено ТЗ.
- Смоук (требование 6/AC-9) сверяет три сценария одной фикстурой,
  снятой до правки, — все три относятся к цепочке гейтов перехода
  `in_dev -> review`; проверка «поведение не изменилось» естественно
  идёт одним прогоном по итоговому состоянию обеих функций, а не двумя
  частичными.

Решение утверждает Оператор на гейте SPEC (docs/operator-gates.md).
