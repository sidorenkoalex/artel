# PLAN: Учёт стоимости шага при таймауте и обрыве потока

## Подход

Сегодня `orchestrator/spend.py::parse_cost_event` берёт стоимость только
из события `type: result`; если его нет (таймаут `AGENT_TIMEOUT_SEC` в
`runner.run_agent_once`, либо обрыв stdout-пайпа — `OutputPump.error` в
`orchestrator/agent_log.py`), `spend.charge_step` пишет в журнал warning
«agent cost UNKNOWN» и молча оставляет `spent_usd` без изменений — это
и есть дефект SPEC.

Перед реализацией проверено (агент `claude-code-guide`, документация
Claude Code): промежуточные события потока `--output-format stream-json`
(`type: assistant`) несут `message.usage` — счётчики токенов, — но
**не несут** `total_cost_usd`: доллары CLI считает только один раз, в
финальном `result`, по внутреннему прайс-листу, нигде публично не
экспонированному. Это подтверждено и локально: залоченные приёмочные
тесты `tasks/T040/acceptance_tests/test_step_cost_on_missing_final_event.py`
прямым текстом фиксируют — «курс токена в доллары нигде в кодовой базе
сегодня не задан», и сознательно не проверяют конкретное число для ветки
«частичная сумма». Значит подбирать курс самому (внешний прайс-лист
Anthropic, зависящий от модели и типа токена — input/output/cache read/
cache write) в этой задаче нельзя: это отдельное, рискованное
финансовое допущение вне зоны SPEC, а не деталь реализации. Отсюда
решение — «частичная сумма» считается по **токенам**, не по долларам:
это единственная величина, которую реально несёт поток без домысла.

Ключевые решения:

1. **`spend.charge_step` не меняется.** Три существующих теста зовут её
   напрямую с сигнатурой `(conn, task_id, role, cost, numbered)`
   (`tests/test_multitarget.py::ProgramSpendTest`,
   `tests/test_multitarget_invariants.py::ProgramSpendAcrossTargetsTest`,
   `tests/test_doctor.py::ProgramThresholdAlertTest`) — менять сигнатуру
   значит ломать их (AC-4). Новая ветка (таймаут/обрыв без финального
   события) — отдельная функция `spend.charge_missing_result`, которую
   `runner.run_agent_once` зовёt ВМЕСТО `charge_step` только когда
   `pump.cost is None and (timed_out or pump.error is not None)`.
   Обычный путь (`pump.cost` есть, либо cost=None без таймаута/обрыва —
   старый «тихий» warning из `tests/test_step_cost.py::
   test_missing_cost_is_warned_but_step_survives`) не трогается —
   этим и достигается требование 6 / AC-3.
2. **`OutputPump` копит токены промежуточных usage-событий налету**,
   пока качает поток (тот же приём, что уже ловит `pump.cost` из
   финального события) — читать это после обрыва потока неоткуда,
   кроме как во время самого чтения. Новые поля: `partial_tokens`
   (сумма по всем увиденным usage-событиям) и `saw_usage_event` (флаг:
   был ли хоть один такой ивент — отдельно от суммы, чтобы «увидели
   0 токенов» не спутать с «не увидели usage вовсе»).
3. **`spend.stream_usage_tokens(raw_line)`** — новый разбор: токены из
   usage ЛЮБОГО события потока (`type: result` — `usage` на верхнем
   уровне, `type: assistant` — `message.usage`), а не только
   финального. Использует существующий `spend.step_tokens` — который
   уже умеет суммировать 4 счётчика usage и не изобретается заново.
4. **Развилка партиальная/неизвестна** — в `charge_missing_result`:
   - `saw_usage_event=True` → журнал `agent cost PARTIAL`, текст несёт
     пометку «частичная» и число токенов, `store.charge` НЕ зовётся
     (курса в доллары нет — записывать фиктивную сумму в `spent_usd`
     хуже, чем не записывать), алерт не заводится (по формулировке
     AC-1/2 — «либо…либо»).
   - `saw_usage_event=False` → журнал `agent cost LOST` с фразой
     «стоимость шага неизвестна» (буквальное совпадение с AC-1/2), и
     `alerts.raise_alert(conn, target, "incident", "spend.unknown_cost",
     ...)`. Дедуп самого `raise_alert` (совпадение target/kind/source/
     message среди неподтверждённых) защищает от дублей при повторных
     таймаутах с тем же текстом попытки — использую как есть, не трогаю.
5. **Причина (`cause`) в текст журнала/алерта** — `"таймаут шага"` при
   `timed_out`, иначе `"обрыв stdout-пайпа"` (условие обрыва — то же,
   что уже использует `close_pump` для «agent log INCOMPLETE»:
   `pump.error is not None`; отдельного нового способа определить обрыв
   не завожу — совпадение с уже существующим сигналом).
6. **`budget.check_program_spend`/`enforce_budget` не трогаю** —
   вызываются как раньше с `pump.cost` (в обеих новых ветках это
   `None`), поэтому автоматически не реагируют — ровно требование 4
   («меняется только полнота данных»).
7. **Инвариант в реестр**: добавляю строку в `docs/invariants.md`
   (раздел «Кодированные тестами») — по шаблону «Как добавить
   инвариант» в конце файла, ссылкой на локальные приёмочные тесты
   T040. Файл в PROTECTED-списке CI, но добавление новой строки —
   штатный, документированный процесс задачи, вводящей инвариант
   (прецеденты — T021 → строка 25, T023 → 26/27), не ослабление.

## Шаги

1. `orchestrator/spend.py`: `stream_usage_tokens` (разбор usage любого
   события потока) + `charge_missing_result` (журнал «частичная»/
   «неизвестна» + алерт, без `store.charge`). Юнит-тесты на оба в
   `tests/test_step_cost.py`.
2. `orchestrator/agent_log.py`: `OutputPump.partial_tokens`/
   `saw_usage_event`, накопление в `catch_cost` через
   `spend.stream_usage_tokens`. Юнит-тесты в `tests/test_agent_log.py`.
3. `orchestrator/runner.py::run_agent_once`: развилка после
   `close_pump` — `charge_missing_result` вместо `charge_step`, когда
   `pump.cost is None and (timed_out or pump.error is not None)`.
   Прогон локальных приёмочных тестов T040 (AC-1..AC-3) + добавление
   собственного end-to-end юнит-теста на ветку «частичная» (таймаут с
   usage-событиями в потоке до обрыва — приёмочные тесты её сознательно
   не фиксируют числом, но код обязан её реально проходить).
4. `docs/invariants.md`: новая строка реестра на этот инвариант
   («стоимость шага не остаётся неучтённой молча»).

## Влияние на систему

- **Бюджетная механика не меняется**: `enforce_budget`,
  `check_program_spend`, `budget_block` по-прежнему видят только
  `pump.cost` (словарь с `usd`) или `None` — в обеих новых ветках
  `None`, как и раньше при отсутствии финального события. Тесты
  `tests/test_spec_budget.py`, `tests/test_multitarget*.py`,
  `tests/test_invariants.py::ExhaustedBudgetIsNotBypassableTest` этот
  путь не трогают и остаются зелёными без правок.
- **`spend.charge_step` не меняется** — три внешних вызова
  (`test_multitarget.py`, `test_multitarget_invariants.py`,
  `test_doctor.py`) продолжают работать с прежней сигнатурой.
- **Существующий «тихий» путь неизвестной стоимости** (rc=0, чистый
  EOF, но без события `result` — `tests/test_step_cost.py::
  test_missing_cost_is_warned_but_step_survives`) остаётся байт-в-байт
  как был: новая развилка условием `timed_out or pump.error is not
  None` его не задевает.
- **`docs/invariants.md`** в PROTECTED-списке CI (предупреждение в
  Фазе 0, не блок) — правка добавляет строку, ничего не ослабляет и не
  удаляет; откатывается одной строкой при необходимости.
- **Откат**: оба новых поля `OutputPump` и обе новые функции
  `spend.py` — чистое добавление (никаких сигнатур существующих
  публичных функций не меняется), откат — удаление добавленного кода
  без затрагивания остального.
- Пересчёта задним числом (требование 5) не будет — новая логика
  участвует только в новых прогонах `run_agent_once`, старые записи
  `spent_usd`/журнала не трогаются никаким шагом.

## Риски

- «Частичная» ветка (токены без долларов) при сегодняшнем поведении
  CLI формально недостижима через реальный процесс (только через
  синтетические потоки в тестах) — намеренно: без прайс-листа в
  кодовой базе честный частичный доллар не собрать, риск явно назван
  и подтверждён исследованием, не домыслен. Если Оператору нужна
  именно денежная частичная сумма — отдельная задача с явным решением
  о курсе токена в доллары (Оператор через ADR или SPEC с готовым
  прайс-листом), не эта.
