# ИИ-настройки внешнего проекта — полем записи, вне рабочей копии роли и вне правок задач

## Факты

Решение Оператора 25.10.2026 (строки бэклога П1 ee693e48 и уточнение 1f02aff4): ИИ-настройки подключаемого проекта (`CLAUDE.md`, `AGENTS.md`, `.claude/`, `.mcp.json`, а у отдельных проектов — свои каталоги обвязки, например `harness/`, `aireview/`, `.devcontainer/`, `.vscode/` в feedback) — чужие для пульта (ADR-0003 п.14 «агентская обвязка целевого не наследуется»). Пульт их не исполняет, ролям не передаёт и в репозитории проекта не трогает.

Сейчас:
1. Список обвязки зашит: `orchestrator/doctor/preflight.py:516` `TARGET_WRAPPER_MARKERS = (".claude", ".mcp.json", "CLAUDE.md", "AGENTS.md")`; `check_target_wrapper` (`:519`) только предупреждает о найденных путях в клоне проекта и ничего не исключает.
2. Рабочая копия задачи внешнего проекта — полный `git worktree add` (`orchestrator/workspace.py:185`, `ensure`): все файлы обвязки лежат в каталоге шага роли (`runner.role_cwd`, `orchestrator/runner.py:1151`), роль читает их и может запустить (роли разрешён `Bash(python3:*)` — `python3 harness/agent.py` исполним).
3. Запрет правки — только то, что Оператор вписал в `policy.no_paths` записи проекта (`orchestrator/targets.py:32`); обвязку туда вносят руками (у sled в локальном слое — `.claude/`, `CLAUDE.md`, `AGENTS.md` и др.).
4. Поле `knowledge` компонента (`orchestrator/targets.py:99`, бриф — `orchestrator/brief.py`, `_knowledge_of`) может назвать файлы обвязки: у sled в локальном слое `knowledge: [CLAUDE.md, AGENTS.md, .claude/rules/]` и `[frontend/CLAUDE.md, frontend/.claude/]`.

## Требуется

Касается только внешних проектов (target не равен `config.DEFAULT_TARGET`); у артели поведение не меняется.

1. **Поле записи.** В `policy` записи проекта — необязательное поле `agent_wrapper`: список путей репозитория (файл или каталог с «/»), формат и проверка — как у `no_paths`. Действующий список обвязки проекта = стандартные маркеры (`.claude/`, `.mcp.json`, `CLAUDE.md`, `AGENTS.md` в корне и в любом каталоге — `**/CLAUDE.md`, `**/AGENTS.md`, `**/.claude/`) ∪ `agent_wrapper`. Стандартные маркеры объявлены в одном месте (одна константа), `doctor` берёт их оттуда же.
2. **Запрет правки.** Действующий список обвязки входит в действующий `no_paths` задачи автоматически (на всех гейтах, где сейчас сверяется `no_paths`), без дописывания руками. Поведение при правке пути обвязки — то же, что у любого `no_paths`.
3. **Отказ записи.** Элемент `knowledge` любого компонента, совпадающий с путём обвязки или лежащий внутри него, — запись проекта не загружается, отказ называет компонент, элемент и путь обвязки. (Конвенции проекта в бриф идут отдельной задачей — из файла пульта, не из обвязки.)
4. **Рабочая копия роли без обвязки.** Рабочая копия задачи внешнего проекта выписывается без путей действующего списка обвязки (git sparse-checkout, режим без конусов, с исключающими шаблонами; настройка — только для этой рабочей копии, не для клона и не для других рабочих копий). Ветка, коммиты и дифф задачи не меняются: файлы обвязки остаются в дереве git, их просто нет на диске рабочей копии. Повторный `ensure` идемпотентен; уже существующая рабочая копия без исключений приводится к ним при следующем `ensure`. Сбой настройки исключений — именованный отказ `ensure` (роль не стартует в рабочей копии с обвязкой).
5. **doctor.** Проверка `target-wrapper` показывает действующий список обвязки проекта (стандартные + `agent_wrapper`) и для каждой рабочей копии задач проекта — исключены ли пути обвязки с диска; есть на диске — `warn` с путём. Предупреждение о наличии обвязки в клоне больше не нужно (в клоне она есть всегда) — смысл проверки меняется на «исключена ли».
6. Проверка, что суммарный набор тестов и гейтов задачи внешнего проекта (планка, `suite-run`, гейт зон, дифф ревью) работает на рабочей копии без обвязки — тестом на песочнице с файлами обвязки в дереве проекта.

Критерии приёмки:
- запись с `policy.agent_wrapper: [harness/]` и правка `harness/x.py` в ветке задачи — отказ гейта, как у `no_paths`; без поля — правка `CLAUDE.md` или `sub/AGENTS.md` всё равно отказ;
- `knowledge: [CLAUDE.md]` или `knowledge: [.claude/rules/]` — запись отказывает с названием элемента; `knowledge: [docs/arch.md]` — загружается;
- в рабочей копии задачи песочного проекта с `CLAUDE.md`, `.claude/x`, `harness/a.py` (при `agent_wrapper: [harness/]`) этих файлов на диске нет, прочие файлы есть; `git -C <рабочая копия> diff <база>` пуст сразу после `ensure`; коммит роли в другой файл не удаляет файлы обвязки из ветки;
- у артели (`DEFAULT_TARGET`) рабочая копия полная, `CLAUDE.md` пульта на месте;
- `doctor` на проекте с обвязкой на диске рабочей копии — `warn` с путём; после `ensure` — `ok`.

Зоны: `orchestrator/targets.py`, `orchestrator/workspace.py`, `orchestrator/doctor/preflight.py`, `orchestrator/doctor/__init__.py`, `orchestrator/runner.py` (только если сверка `no_paths` или старт роли живут там), `tests/` (долгоживущие файлы задачи). Аналитик сверяет по коду, где сверяется `no_paths`, и вносит эти файлы в зоны SPEC поимённо.

Только чтение: `orchestrator/brief.py`, `orchestrator/config.py`, `orchestrator/project_profile.py`, `docs/adr/0003-target-projects.md`, `.artel/targets.yaml`.

Существующие тесты: если требование противоречит существующему тесту (например, проверке `check_target_wrapper` или полной рабочей копии внешнего проекта), аналитик перечисляет такие тесты в SPEC поимённо; правка существующих тестов — только по мандату Оператора на гейте SPEC. Иная правка — эскалация.

Не входит: правка самих файлов обвязки (`.claude/`, `.mcp.json`, `CLAUDE.md`, `AGENTS.md`, `harness/` и др.) в любом репозитории, в том числе артели; конвенции проекта в бриф ролей и файл `conventions.md` (отдельная задача); правка записи sled в локальном слое (делает Оператор до мержа этой задачи — убрать файлы обвязки из `knowledge`); ограничение чтения файлов вне рабочей копии; запись feedback.
