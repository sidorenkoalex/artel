# SPEC: ИИ-настройки внешнего проекта — полем записи, вне рабочей копии роли и вне правок задач

## Контекст
ИИ-настройки подключаемого проекта (`CLAUDE.md`, `AGENTS.md`, `.claude/`,
`.mcp.json`, у отдельных проектов — свои каталоги вроде `harness/`) чужие для
пульта (ADR-0003 п.14). Сейчас их список зашит в
`orchestrator/doctor/preflight.py:516` (`TARGET_WRAPPER_MARKERS`) и только
инвентаризуется в клоне. Рабочая копия задачи внешнего проекта выписана
полностью (`orchestrator/workspace.py:186`, `ensure`), так что роль видит
обвязку и может её запустить. Запрет правки обвязки есть только там, где
Оператор вписал её в `policy.no_paths` руками. Поле `knowledge` компонента
может назвать файлы обвязки.

Решения Оператора (ANSWER-1, 25.10.2026):
- вопрос 1 — A: обвязка входит в `repo_context.protected_paths(ctx)`
  внешнего проекта, это одна точка для всех мест сверки;
- вопрос 2 — A: `config.is_protected_path` понимает запись `**/<каталог>/`;
  «только чтение» с `orchestrator/config.py` снято;
- вопрос 3: прежняя проверка `target-wrapper` не меняется ни у кого;
  исключение обвязки с диска показывает новая отдельная проверка `doctor`.

Всё ниже касается только внешних проектов (target не равен
`config.DEFAULT_TARGET`), если требование не говорит об артели явно. У артели
поведение не меняется.

## Требования

1. **Константа стандартных маркеров.** В `orchestrator/config.py` объявлена
   одна константа `AGENT_WRAPPER_MARKERS` со значением ровно
   `("**/.claude/", ".mcp.json", "**/CLAUDE.md", "**/AGENTS.md")`, в этом
   порядке. Новая проверка `doctor` (требование 9) и тесты мандата ANSWER-1
   берут маркеры из неё. В `config.PROTECTED_PATHS` маркеры не добавляются:
   константа и её 19 записей не меняются.
2. **Формула `**/<каталог>/`.** `config.is_protected_path` дополнительно
   понимает запись вида `**/<каталог>/` (с завершающим `/`). Она покрывает
   путь, в котором `<каталог>` стоит компонентом-каталогом на любой глубине,
   включая корень, то есть за этим компонентом в пути идёт `/`.
   Запись `**/<имя>` без завершающего `/` сверяется по-прежнему: только с
   последним компонентом пути. Прочие записи, как и раньше, сверяются
   префиксом.
3. **Поле записи `agent_wrapper`.** В `policy` записи проекта `targets.yaml`
   (и локального слоя) есть необязательное поле `agent_wrapper`: список
   путей репозитория (файл или каталог с завершающим `/`). Формат и проверка
   у него те же, что у `no_paths`. Значение, которое не прошло бы проверку
   `no_paths`, — отказ загрузки записи. Без поля значение — пустой список.
4. **Действующий список обвязки** проекта — `AGENT_WRAPPER_MARKERS`, за ними
   элементы `agent_wrapper` записи в их порядке. Элемент, который уже есть в
   списке той же строкой, повторно не добавляется.
5. **Перечень защищённых путей внешнего проекта.** Для внешнего проекта
   `repo_context.protected_paths(ctx)` возвращает кортеж: элементы `no_paths`
   записи в их порядке, затем элементы действующего списка обвязки
   (требование 4), которых ещё нет в кортеже той же строкой. Дубль — только
   совпадение строки: `.claude/` из `no_paths` и маркер `**/.claude/` — две
   разные записи, обе остаются. Тем самым обвязка попадает во все места
   сверки, которые зовут `protected_paths`: гейт зон на `in_dev -> verifying`,
   гейт диффа на мерже, допуск приложения PLAN, пометка зон ТЗ на `new` и
   зон SPEC на гейте SPEC, подсветка Draft MR. При правке пути обвязки
   поведение то же, что у любого пути `no_paths`. У артели
   `protected_paths` по-прежнему возвращает `tuple(config.PROTECTED_PATHS)`.
6. **Зоны под маской каталога.** Элемент зон ТЗ (`new`) или SPEC (`approve`
   на `spec_gate`, `guard.protected_zones`) внешнего проекта отказывает как
   защищённый, если он называет сам каталог обвязки из записи `**/<каталог>/`
   с завершающим `/` или без него (`.claude/`, `sub/.claude/`, `sub/.claude`)
   либо путь внутри такого каталога. Сверка путей файлов (гейты диффа) идёт
   по формуле требования 2: файл `frontend/.claude` без вложения не защищён.
   Сверка зон по перечню артели даёт прежний результат.
7. **Отказ записи по `knowledge`.** Элемент `knowledge` любого компонента
   записи внешнего проекта отказывает загрузке записи, если он совпадает с
   путём действующего списка обвязки этого проекта или лежит внутри него.
   Сверка идёт по формуле `config.is_protected_path`; элемент-каталог —
   также как зона по требованию 6. Текст отказа называет компонент, элемент
   и путь (запись) обвязки, под которую элемент попал.
8. **Рабочая копия без обвязки.** `workspace.ensure` выписывает рабочую копию
   задачи внешнего проекта без путей действующего списка обвязки: git
   sparse-checkout в режиме без конусов, с исключающими шаблонами. Настройка
   действует только для этой рабочей копии — не для клона и не для других
   рабочих копий того же клона. Ветка, коммиты и дифф задачи не меняются:
   файлы обвязки остаются в дереве git, на диске рабочей копии их нет.
   Повторный `ensure` идемпотентен. Уже существующая рабочая копия, в которой
   исключений нет, приводится к ним при следующем `ensure`. Сбой настройки
   исключений — именованный отказ `ensure` (вторая позиция результата): роль
   не стартует в рабочей копии с обвязкой. У артели рабочая копия
   выписывается полностью, как сейчас.
9. **Новая проверка doctor.** Рядом с `target-wrapper` в `doctor` есть новая
   проверка `target-wrapper-worktrees` на каждый объявленный проект.
   У внешнего проекта detail называет действующий список обвязки
   (стандартные маркеры и `agent_wrapper`). Для каждой рабочей копии задач
   проекта проверка смотрит, есть ли на диске путь, который покрывает этот
   список. Есть хоть один — `warn` с путём (рабочая копия и путь на диске).
   Иначе — `ok`, в том числе когда рабочих копий нет. У артели —
   `ok` с пояснением «рабочие копии артели полные по замыслу». Прежняя
   проверка `target-wrapper` (`check_target_wrapper`, инвентаризация клона,
   `warn` при найденной обвязке) и `TARGET_WRAPPER_MARKERS` не меняются ни у
   какого проекта.
10. **Источник перечня в Draft MR.** Текст источника перечня в подсветке
    Draft MR внешнего проекта (`github_adapter._protected_paths_source`)
    называет и `no_paths` записи проекта, и обвязку. В тексте нет подстроки
    « (». У артели текст прежний — `config.PROTECTED_PATHS`.
11. **Сквозная проверка на песочнице.** Тестом на песочном внешнем проекте,
    в дереве которого есть файлы обвязки: на рабочей копии без обвязки
    работают планка задачи, `suite-run`, гейт зон и дифф ревью.

## Критерии приёмки

AC-1. `config.AGENT_WRAPPER_MARKERS == ("**/.claude/", ".mcp.json", "**/CLAUDE.md", "**/AGENTS.md")`. Ни одной записи этой константы нет в `config.PROTECTED_PATHS`, а сама `config.PROTECTED_PATHS` совпадает со значением на main (19 записей в прежнем порядке).

AC-2. `config.is_protected_path(p, ("**/.claude/",))` истинно для `.claude/rules/x.md` и `frontend/.claude/rules/x.md`. Для `frontend/claude/x.md`, `x.claude` и `frontend/.claude` (файл без вложения) — ложно.

AC-3. На фиксированном наборе путей — корневые и вложенные, с компонентами `.claude`, `conftest.py`, `CLAUDE.md`, `skills`, `templates` — каждая запись `config.PROTECTED_PATHS`, взятая перечнем из одной записи, даёт тот же результат `config.is_protected_path`, что формула main. Перечень целиком (`protected=None`) — тоже.

AC-4. `scripts/ci_protected_paths.py` и `scripts/guard.py` (`protected_zones` и сверка приложения PLAN) на перечне артели дают на наборе путей из AC-3 тот же результат, что на main.

AC-5. Запись внешнего проекта с `policy.agent_wrapper: [harness/]` загружается, и `protected_paths` её контекста содержит `harness/`. Запись с `agent_wrapper`, которую проверка `no_paths` не пропустила бы (не список или элемент не путь репозитория), не загружается. Запись без поля загружается.

AC-6. При `no_paths: ["zz/"]` без `agent_wrapper` `protected_paths` внешнего проекта равен `("zz/", "**/.claude/", ".mcp.json", "**/CLAUDE.md", "**/AGENTS.md")`. При `no_paths: []` — равен `config.AGENT_WRAPPER_MARKERS`. При `no_paths`, содержащем `.claude/` и `CLAUDE.md`, и `agent_wrapper: [harness/, .mcp.json]` ни одна строка в результате не встречается дважды, а порядок соответствует требованиям 4–5.

AC-7. У артели `repo_context.protected_paths(resolve(config.DEFAULT_TARGET)) == tuple(config.PROTECTED_PATHS)`.

AC-8. Ветка задачи внешнего проекта без поля `agent_wrapper`, правящая любой из путей `CLAUDE.md`, `sub/AGENTS.md`, `.claude/x`, `frontend/.claude/rules/x.md`, получает на `in_dev -> verifying` отказ «защищённый путь» — тот же, что у пути `no_paths`. При `agent_wrapper: [harness/]` правка `harness/x.py` даёт тот же отказ.

AC-9. Путь обвязки (`CLAUDE.md`, а при `agent_wrapper: [harness/]` и `harness/x.py`) в диффе задачи внешнего проекта на гейте мержа даёт тот же отказ или эскалацию, что путь `no_paths`.

AC-10. Подсветка Draft MR внешнего проекта с `CLAUDE.md` в диффе называет его защищённым. Текст источника перечня называет `no_paths` и обвязку и не содержит подстроки « (». У артели текст источника — `config.PROTECTED_PATHS`.

AC-11. Зоны внешнего проекта `sub/.claude/`, `sub/.claude` и `.claude/` отказывают как защищённые на трёх сверках: «Зоны:» ТЗ на `new`, `zones:` SPEC на `approve` гейта SPEC и `guard.protected_zones` с перечнем проекта. Зона `docs/` того же проекта не отказывает.

AC-12. Запись внешнего проекта с компонентом, у которого `knowledge: [CLAUDE.md]`, не загружается. То же для `knowledge: [.claude/rules/]` и, при `agent_wrapper: [harness/]`, для `knowledge: [harness/a.md]`. Текст отказа называет компонент, элемент и путь обвязки. Запись с `knowledge: [docs/arch.md]` загружается.

AC-13. В песочном внешнем проекте в дереве есть `CLAUDE.md`, `.claude/x`, `harness/a.py`, `src/m.py`, запись несёт `agent_wrapper: [harness/]`. Сразу после `workspace.ensure` в рабочей копии задачи нет на диске `CLAUDE.md`, `.claude/x` и `harness/a.py`, а `src/m.py` есть. `git -C <рабочая копия> diff <база>` пуст, `git status --porcelain` пуст.

AC-14. В рабочей копии из AC-13 роль правит `src/m.py` и коммитит штатным путём пульта — чекпоинтом шага. После этого в дереве головного коммита ветки задачи по-прежнему есть `CLAUDE.md`, `.claude/x` и `harness/a.py` с прежним содержимым.

AC-15. Повторный `ensure` той же рабочей копии возвращает причину `None`, а набор файлов на диске не меняется. Рабочая копия, заведённая полным `git worktree add` без исключений, после `ensure` теряет с диска файлы обвязки, и её `git diff <база>` пуст. В клоне проекта и в другой рабочей копии того же клона, заведённой без `ensure`, файлы обвязки остаются на диске.

AC-16. Если настройка исключений не удалась (сбой подменённой команды git sparse-checkout), `ensure` возвращает непустую именованную причину, и шаг роли в этой рабочей копии не стартует.

AC-17. У артели рабочая копия задачи после `ensure` полная: `CLAUDE.md` пульта на месте, sparse-checkout в ней не включён.

AC-18. Проверка `target-wrapper-worktrees` у внешнего проекта даёт `warn`, если в его рабочей копии на диске есть файл обвязки, и detail называет путь. После `ensure` этой рабочей копии — `ok`. Detail в обоих случаях называет действующий список обвязки, включая элемент `agent_wrapper`. У артели проверка даёт `ok` с пояснением «рабочие копии артели полные по замыслу».

AC-19. На песочном внешнем проекте из AC-13 на рабочей копии без обвязки зелено проходят: планка задачи (`plank-run`), `suite-run`, гейт зон на `in_dev -> verifying` (ветка без правок обвязки — без отказа) и сборка диффа ревью. Дифф ревью не называет файлы обвязки удалёнными.
