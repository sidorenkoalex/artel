# SPEC: ИИ-настройки внешнего проекта — полем записи, вне рабочей копии роли и вне правок задач

## Контекст
ИИ-настройки подключаемого проекта (`CLAUDE.md`, `AGENTS.md`, `.claude/`,
`.mcp.json`, у отдельных проектов — свои каталоги вроде `harness/`) чужие для
пульта (ADR-0003 п.14). Сейчас их список зашит в
`orchestrator/doctor/preflight.py:516` (`TARGET_WRAPPER_MARKERS`) и только
инвентаризуется в клоне. Рабочая копия задачи внешнего проекта выписана
полностью (`orchestrator/workspace.py:186`, `ensure`), так что роль видит
обвязку и может её запустить. Запрет правки обвязки есть только там, где
Оператор вписал её в `policy.no_paths` руками. Поле `knowledge` компонента
может назвать файлы обвязки.

Решения Оператора:
- ANSWER-1, вопрос 1 — A: обвязка входит в `repo_context.protected_paths(ctx)`
  внешнего проекта, одна точка для всех мест сверки;
- ANSWER-1, вопрос 2 — A: `config.is_protected_path` понимает запись
  `**/<каталог>/`; «только чтение» с `orchestrator/config.py` снято;
- ANSWER-1, вопрос 3: прежняя проверка `target-wrapper` не меняется ни у
  кого; исключение обвязки с диска показывает новая отдельная проверка;
- ANSWER-2, ответ 1: отказ записи по `knowledge` не касается корневых
  `CLAUDE.md` и `AGENTS.md`; канал этих файлов и элемента-предка в бриф
  закрывает задача 01M5T18K1YFBYA7MM1BBRV869A;
- ANSWER-2, ответ 2 — A: `ensure` убирает с диска неотслеживаемые и
  игнорируемые файлы под списком обвязки;
- ANSWER-2, ответ 3 — A: запись `extensions.worktreeConfig` в конфиг клона
  допустима, минимум git — 2.35;
- ANSWER-2, ответ 4 — A: `agent_wrapper` — и плоское поле слоя репозитория,
  и поле раздела `policy` локального слоя;
- ANSWER-2, ответ 6 — A: `TARGET_WRAPPER_MARKERS` выводится из единой
  константы маркеров;
- ANSWER-2, ответ 7: монолит, `budget_usd: 75`.

Всё ниже касается только внешних проектов (target не равен
`config.DEFAULT_TARGET`), если требование не говорит об артели явно. У артели
поведение не меняется.

## Требования

1. **Константа стандартных маркеров.** В `orchestrator/config.py` объявлена
   одна константа `AGENT_WRAPPER_MARKERS` со значением ровно
   `("**/.claude/", ".mcp.json", "**/CLAUDE.md", "**/AGENTS.md")`, в этом
   порядке. Код задачи, новая проверка `doctor` (требование 10) и тесты
   мандата ANSWER-1 берут маркеры из неё. В `config.PROTECTED_PATHS` маркеры
   не добавляются: константа и её 19 записей не меняются.
2. **Прежняя константа doctor из единой.**
   `orchestrator/doctor/preflight.py` `TARGET_WRAPPER_MARKERS` не задаётся
   литералом, а выводится из `config.AGENT_WRAPPER_MARKERS`: имя маркера без
   префикса `**/` и без завершающего `/`, в том же порядке. Её значение
   остаётся прежним — `(".claude", ".mcp.json", "CLAUDE.md", "AGENTS.md")`;
   поведение проверки `target-wrapper` не меняется.
3. **Формула `**/<каталог>/`.** `config.is_protected_path` дополнительно
   понимает запись вида `**/<каталог>/` (с завершающим `/`). Она покрывает
   путь, в котором компонент, равный `<каталог>` целиком, стоит
   компонентом-каталогом на любой глубине, включая корень, — то есть за
   этим компонентом в пути идёт `/`. Запись `**/<имя>` без завершающего `/`
   сверяется по-прежнему: только с последним компонентом пути. Прочие
   записи, как и раньше, сверяются префиксом.
4. **Поле записи `agent_wrapper`.** Необязательное поле `agent_wrapper` —
   список путей репозитория (файл или каталог с завершающим `/`). Оно есть
   в двух местах: плоским полем записи слоя репозитория
   (`.artel/targets.yaml`) и полем раздела `policy` локального слоя — там же,
   где `sandbox`. Проверка — та же, что у `no_paths` («список строк»);
   значение, которое не прошло бы её, — отказ загрузки записи. Без поля
   значение — пустой список. Сведение слоёв (`targets._flatten`) переносит
   поле из `policy` локального слоя; `targets-migrate`
   (`projects._split_entry`) кладёт плоское поле в раздел `policy`.
5. **Действующий список обвязки** проекта — `AGENT_WRAPPER_MARKERS`, за ними
   элементы `agent_wrapper` записи в их порядке. Элемент, который уже есть в
   списке той же строкой, повторно не добавляется.
6. **Перечень защищённых путей внешнего проекта.** Для внешнего проекта
   `repo_context.protected_paths(ctx)` возвращает кортеж: элементы `no_paths`
   записи в их порядке, затем элементы действующего списка обвязки
   (требование 5), которых ещё нет в кортеже той же строкой. Дубль — только
   совпадение строки: `.claude/` из `no_paths` и маркер `**/.claude/` — две
   разные записи, обе остаются. Тем самым обвязка попадает во все места
   сверки, которые зовут `protected_paths`: гейт зон на `in_dev -> verifying`,
   гейт диффа на мерже, допуск приложения PLAN, пометка зон ТЗ на `new` и
   зон SPEC на гейте SPEC, подсветка Draft MR. При правке пути обвязки
   поведение то же, что у любого пути `no_paths`. У артели
   `protected_paths` по-прежнему возвращает `tuple(config.PROTECTED_PATHS)`.
7. **Зоны под маской каталога.** Элемент зон ТЗ (`new`) или SPEC (`approve`
   на `spec_gate`, `guard.protected_zones`) внешнего проекта отказывает как
   защищённый, если он называет сам каталог обвязки из записи `**/<каталог>/`
   с завершающим `/` или без него (`.claude/`, `.claude`, `sub/.claude/`,
   `sub/.claude`) либо путь внутри такого каталога. Сверка путей файлов
   (гейты диффа) идёт по формуле требования 3: файл `frontend/.claude` без
   вложения не защищён. Сверка зон по перечню артели даёт прежний результат.
8. **Отказ записи по `knowledge`.** Элемент `knowledge` любого компонента
   записи внешнего проекта сначала нормализуется так же, как его читает бриф
   (ведущий `./` и прочие `.`-компоненты сводятся, `posixpath.normpath`).
   Нормализованный элемент отказывает загрузке записи, если он совпадает с
   путём действующего списка обвязки этого проекта или лежит внутри него,
   **кроме** корневых `CLAUDE.md` и `AGENTS.md` (в том числе записанных как
   `./CLAUDE.md`, `./AGENTS.md`) — они загружаются. Сверка идёт по формуле
   `config.is_protected_path`; элемент-каталог — также как зона по
   требованию 7. Элемент-каталог выше обвязки (`./`, `docs/`, `frontend/`)
   отказа не получает. Текст отказа называет компонент, элемент и путь
   (запись) обвязки, под которую элемент попал.
9. **Рабочая копия без обвязки.** `workspace.ensure` выписывает рабочую копию
   задачи внешнего проекта без путей действующего списка обвязки: git
   sparse-checkout в режиме без конусов, с исключающими шаблонами. Маркеры
   `**/…` исключаются на любой глубине, `.mcp.json` — только в корне,
   элементы `agent_wrapper` — по своему пути. Настройка исключений действует
   только для этой рабочей копии — не для клона и не для других рабочих
   копий того же клона; запись `extensions.worktreeConfig = true` в общий
   конфиг клона допустима. Ветка, коммиты и дифф задачи не меняются: файлы
   обвязки остаются в дереве git, на диске рабочей копии их нет.
   Каждый `ensure` приводит шаблоны исключений рабочей копии к ТЕКУЩЕМУ
   действующему списку обвязки: копия без исключений и копия с
   исключениями по прежнему списку приводятся одинаково. Повторный `ensure`
   при неизменном списке идемпотентен. Перед стартом роли `ensure` удаляет с
   диска рабочей копии неотслеживаемые и игнорируемые файлы под действующим
   списком обвязки. Сбой настройки исключений — именованный отказ `ensure`
   (вторая позиция результата): роль не стартует в рабочей копии с
   обвязкой. У артели рабочая копия выписывается полностью, как сейчас.
10. **Новая проверка doctor.** Рядом с `target-wrapper` в `doctor` есть новая
    проверка `target-wrapper-worktrees` на каждый объявленный проект.
    У внешнего проекта detail называет действующий список обвязки
    (стандартные маркеры и `agent_wrapper`). Для каждой рабочей копии задач
    проекта проверка смотрит, есть ли на диске путь, который покрывает этот
    список (на любой глубине для маркеров `**/…`). Есть хоть один — `warn`
    с путём (рабочая копия и путь на диске). Иначе — `ok`, в том числе
    когда рабочих копий нет. У артели — `ok` с пояснением «рабочие копии
    артели полные по замыслу». Прежняя проверка `target-wrapper`
    (`check_target_wrapper`, инвентаризация клона, `warn` при найденной
    обвязке) не меняется ни у какого проекта.
11. **Источник перечня в Draft MR.** Текст источника перечня в подсветке
    Draft MR внешнего проекта (`github_adapter._protected_paths_source`)
    называет и `no_paths` записи проекта, и обвязку. В тексте нет подстроки
    « (». У артели текст прежний — `config.PROTECTED_PATHS`.
12. **Минимум git.** Объявленный минимум git в стеке пульта
    (`orchestrator/stack.py`, `REQUIRED_TOOLS["git"]`) — `(2, 35, 0)`.
13. **Сквозная проверка на песочнице.** Тестом на песочном внешнем проекте,
    в дереве которого есть файлы обвязки: на рабочей копии без обвязки
    работают планка задачи, `suite-run`, гейт зон и дифф ревью.
