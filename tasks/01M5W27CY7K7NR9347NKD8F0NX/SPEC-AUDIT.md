## Пути обхода гейтов
1. **`auto` через `run`** (см. AC-4). Проверка только в `runner._cmd_run` выполняет SPEC буквально, ведь `auto` вызывает `cmd_run` (auto.py:958). Но до него цикл делает `fsm.cmd_advance` с git и переходами состояний. Смысл «вход `auto`, до подтяжки» обойдён, и AC-4 это пропускает.
2. **`new` после клона** (см. AC-2). Проверка после `workspace.ensure_clone` (catalog.py:829) проходит AC-2, но клонирует репозиторий неподдержанного хостинга — побочный эффект, который требование 3 запрещает.
3. **`new` только в CLI-обёртке.** Формулировка «`new … --target`» (SPEC.md:48) допускает проверку в `catalog.new_cli_target` (catalog.py:491, вызывается только из artel.py:2010). Тогда `epic draft promote` (epics.py:796 → `catalog.cmd_new(target=epic["project"])`) заведёт задачу неподдержанного проекта мимо отказа. AC-2 проверяет только CLI `new --target` и этого не поймает. SPEC не называет место проверки (`catalog.cmd_new` после `_checked_target`).
4. **Сторож через «поддержанный» литерал** (см. AC-9): `forge != "github"` вне targets.py дублирует список и проходит сторожа.
5. Для сведения, не отклонение (ТЗ не перечисляет эти команды): `advance` (`fsm_advance.in_dev` → `github_adapter.ensure_head_in_origin`, github_adapter.py:211 — отправка ветки без проверки `forge`), `pull-main`, `ci-rerun`. Для новых задач они недостижимы: `approve` на `spec_gate` откажет раньше. Но задача, которая уже была в полёте или проект которой сменил запись после `new`, дойдёт до них без отказа. Достаточно ли перечня ТЗ — решать Оператору.
