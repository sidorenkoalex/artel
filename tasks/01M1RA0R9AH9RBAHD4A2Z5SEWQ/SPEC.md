# SPEC: Перегенерированная карта после шага роли не ломает подтяжку main

## Контекст
Роли перегенерируют `docs/codebase-map.md` в worktree по правилу «после
правки *.py» и часто оставляют её незакоммиченной (карту коммитит пульт
на мерже). На следующем переходе подтяжка main (`fsm._pull_main_or_
escalate`) получает от git отказ «Your local changes to the following
files would be overwritten by merge» ещё ДО попытки самого merge (это
не конфликт содержимого, а грязное рабочее дерево) и уводит готовую к
приёмке задачу в `escalated` как «конфликт подтяжки» — так дважды за
день (зоны часть 3, плавающий тест) 05.09 готовые задачи ушли в
эскалацию, а помощник Оператора вернул их в разработку вручную.

Пересекается по `orchestrator/fsm.py` с другим ТЗ Оператора (условно
«B2 ТЗ-1»); код этой задачи короткий и мержится первым.

## Требования

1. Перед вызовом `git merge` в `_pull_main_or_escalate` (все три точки
   вызова — `in_dev -> review`, `acceptance -> merge_gate`,
   `merge_gate -> done`) worktree задачи приводится в чистое состояние:
   незакоммиченная `docs/codebase-map.md` отбрасывается (эквивалент
   `git checkout -- docs/codebase-map.md`) — карту всё равно
   перегенерирует и закоммитит сам merge (обычный успешный merge либо
   существующий `_auto_resolve_map_conflict`, если карта всё же
   конфликтует по содержимому, SPEC T067).
2. Прочие незакоммиченные изменения worktree (кроме
   `docs/codebase-map.md`), оставшиеся после пункта 1, фиксируются
   WIP-чекпоинтом по мандату роли `developer` — той же механикой, что
   уже несёт `commit_timeout_checkpoint`/`commit_abnormal_checkpoint`/
   `commit_pause_now_checkpoint` (SPEC 01M1NBWTSXEJB24PXR417YF1VA,
   `orchestrator/checkpoint.py`): код вне `tasks/<id>/` коммитится
   служебным коммитом оркестратора (мандат кода в этом worktree всегда
   у `developer` — единственной роли, чей WIP попадает в кодовую
   ветку). Это чекпоинт, не отказ перехода — подтяжка продолжается
   дальше как обычно.
3. После пунктов 1-2 отказ `git merge` с текстом «local changes …
   would be overwritten by merge» больше не возникает по причине
   незакоммиченной `docs/codebase-map.md` или прочего WIP worktree —
   оба источника устранены очисткой до вызова merge.
4. Если такой отказ («would be overwritten by merge») всё же произошёл
   (очистка сама не удалась — например, git не ответил на одном из
   своих шагов), задача уходит в `escalated`, журнал называет
   конкретные незакоммиченные файлы, вызвавшие отказ, и заводится alert
   `kind=incident` — не текст «конфликт подтяжки», которым помечается
   обычный merge-конфликт содержимого (это разные причины отказа для
   Оператора: инцидент очистки/git против спора версий, требующего
   ручного разрешения).
5. Настоящий конфликт содержимого при `git merge` (конфликтующие файлы
   за пределами случая «только карта», уже закрытого SPEC T067)
   по-прежнему уводит задачу в `escalated` с текстом «конфликт
   подтяжки» — поведение байт-в-байт как сейчас, не ослабляется.

## Критерии приёмки

AC-1. Перед вызовом `git merge` в `_pull_main_or_escalate` worktree
задачи с незакоммиченной изменённой `docs/codebase-map.md` (и больше
ничем) приводится в чистое состояние отбрасыванием этого файла —
`git merge` в таком сценарии не получает отказ «local changes … would
be overwritten by merge».

AC-2. Прочие незакоммиченные изменения worktree, кроме
`docs/codebase-map.md`, оставшиеся после AC-1, фиксируются
WIP-чекпоинтом по мандату роли `developer` (та же механика, что
`commit_timeout_checkpoint`, SPEC 01M1NBWTSXEJB24PXR417YF1VA) — код вне
`tasks/<id>/` коммитится служебным коммитом оркестратора; после этого
`git merge` не получает отказ «would be overwritten by merge» по
причине этих файлов.

AC-3. Чекпоинт по AC-1/AC-2 сам по себе не является отказом
перехода — задача с ТОЛЬКО таким WIP в worktree не уходит в
`escalated` из-за самого факта его наличия; подтяжка main продолжается
дальше обычным путём (fresh/pulled) после очистки.

AC-4. Тест: worktree с незакоммиченной изменённой
`docs/codebase-map.md` (без иных изменений) успешно подтягивает main
без эскалации задачи.

AC-5. Тест: worktree с незакоммиченными изменениями кода роли
`developer` вне `tasks/<id>/` (не считая карты) получает WIP-чекпоинт
(коммит) и после этого успешно подтягивает main без эскалации задачи.

AC-6. Если отказ «would be overwritten by merge» всё же произошёл
после попытки очистки (сама очистка не удалась), задача уходит в
`escalated`, журнал называет конкретные незакоммиченные файлы, и
заводится alert `kind=incident`; текст отказа/эскалации НЕ содержит
формулировку «конфликт подтяжки».

AC-7. Тест: настоящий конфликт содержимого при `git merge`
(конфликтующие файлы за пределами случая «только карта», SPEC T067)
по-прежнему уводит задачу в `escalated` с текстом «конфликт подтяжки» —
поведение не ослаблено.

AC-8. Существующие тесты подтяжки/конфликта
(`tests/test_fsm_map_conflict_autoresolve.py`,
`tests/test_branch_freshness_gate.py`) остаются зелёными без изменения
проверяемого ими поведения.

## Не входит

- Правило регенерации карты в скилах ролей (`skills/conventions-core.md`
  не меняется этой задачей).
- Координация мержа с пересекающимся по `orchestrator/fsm.py` ТЗ
  Оператора (условно «B2 ТЗ-1») сверх факта «эта задача мержится
  первой» — саму координацию делает Оператор.
