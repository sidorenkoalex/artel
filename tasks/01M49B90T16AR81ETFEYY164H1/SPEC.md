# SPEC: CI ветки задачи — полный набор tests/ один раз на sha

## Контекст
Каждый push ветки `task/**` с открытым черновиком PR запускает workflow `ci`
дважды — на событие `push` и на событие `pull_request`, — и задания полного
набора `python` и `python-min` (`.github/workflows/ci.yml`, ~179 и ~232) идут
в обоих прогонах: условие на них только `needs.changes.outputs.code != 'false'`.
У части 3 этапа 3 ADR-0021 (01M484RNV3) это дало шесть полных прогонов CI на
три коммита. Пульт (`orchestrator/ci.py::verifying_status` ~487,
`branch_status` ~628) засчитывает `skipped` зелёным (`ci.GREEN`), поэтому
простое снятие заданий с прогона `push` без правки пульта дало бы ложный
зелёный до завершения прогона `pull_request`. Задача: полный набор — один раз
на head-коммит ветки с PR, без потери fail-closed ожидания CI пультом.
`.github/workflows/ci.yml` — защищённый путь: правка едет приложением к PLAN.

## Требования
1. На один head-коммит ветки `task/**` с открытым PR задания полного набора
   (`python`, `python-min`) выполняются один раз — в прогоне `pull_request`;
   в прогоне `push` той же ветки они `skipped`. Способ, которым CI узнаёт о
   наличии PR у ветки (условие на задании, шаг запроса API, иное), выбирает
   разработчик в PLAN; фильтры `paths`/`paths-ignore` в триггере запрещены
   (ADR-0016, инвариант 36) — лишние проверки снимаются условием на задании.
2. Push ветки `task/**` без открытого PR (первый push до `gh pr create`,
   ветка, PR которой закрыт) гоняет полный набор в прогоне `push`, как
   сегодня. Поведение CI для `main` не меняется.
3. Ожидание CI пультом (`verifying`, гейт мержа, `approve`) не засчитывает
   зелёным коммит, у которого задание полного набора есть только `skipped` в
   прогоне `push`, а прогона `pull_request` ещё нет или он не завершён:
   каждое задание полного набора обязано завершиться (исполниться) хотя бы в
   одном прогоне коммита. Fail-closed: если событие прогона не определилось —
   ждать, как сегодня. Правило действует только на задания из объявленного
   перечня полного набора (требование 8).
4. Ре-ран (`ci.find_run_id`, `ci.trigger_rerun`) нацеливается на прогон, в
   котором задание полного набора реально шло (не на прогон, где оно
   `skipped`).
5. Изменение `.github/workflows/ci.yml` — приложение к PLAN с точным текстом;
   проверка приложения `scripts/plan_appendix_ci.py --check-workflow`
   проходит.
6. Тесты в `tests/` с заявками «Ловит мутацию» на свойства требований 3, 4 и
   2 (последнее — со стороны пульта: push без PR, полный набор считается
   нужным). Существующие тесты не ослабляются.
7. В PLAN — замер по истории Actions: число прогонов задания `python` на
   коммит ветки задачи до изменения (по последним задачам) и ожидаемое после.
8. Перечень заданий полного набора (`python`, `python-min`) объявлен явно в
   одном месте — именами заданий либо `name` их проверок; форму и место
   объявления в зонах задачи выбирает разработчик в PLAN. Правило
   требования 3 действует только на задания этого перечня. Прочие
   проверки со статусом `skipped` (например, «Карта кодовой базы
   генерируется и свежа», `ci.yml` ~294, `if: github.ref ==
   'refs/heads/main'`, — на ветке `task/**` `skipped` в обоих прогонах) и
   коммиты проектов без объявленного перечня (внешние target'ы, адрес
   форджа которых `orchestrator/ci.py` принимает параметром `repo`,
   ~42–82) засчитываются так же, как сегодня (`skipped` — зелёный).

## Критерии приёмки

AC-1. Приложение к PLAN к `.github/workflows/ci.yml` несёт точный текст
правки, применяется к `main` (`git apply --check`), и
`python3 scripts/plan_appendix_ci.py --check-workflow` на дереве с наложенным
приложением завершается успехом.

AC-2. В `ci.yml` с наложенным приложением задания `python` и `python-min`
на событии `push` ветки `task/**` с открытым PR имеют условие, дающее
`skipped`, а на событии `pull_request` — исполняются; в триггерах `push` и
`pull_request` нет ключей `paths`/`paths-ignore`.

AC-3. В `ci.yml` с наложенным приложением на событии `push` ветки `task/**`
без открытого PR и на событии `push` ветки `main` задания `python` и
`python-min` исполняются при `needs.changes.outputs.code != 'false'`, как до
изменения.

AC-4. `ci.verifying_status` для коммита, у которого задание полного набора
(`python` или `python-min`) есть только со статусом `skipped` в прогоне
`push`, а прогона `pull_request` нет, не возвращает `ci.VERIFYING_GREEN`.

AC-5. `ci.verifying_status` для коммита, у которого задание полного набора
`skipped` в прогоне `push`, а прогон `pull_request` есть, но задание в нём не
завершено, не возвращает `ci.VERIFYING_GREEN`.

AC-6. `ci.verifying_status` для того же коммита с заданием полного набора
`skipped` в прогоне `push` и завершённым `success` в прогоне `pull_request`
(прочие проверки зелёные) возвращает `ci.VERIFYING_GREEN`.

AC-7. `ci.branch_status` (ожидание CI гейта мержа и `approve`) на коммитах из
AC-4 и AC-5 не возвращает зелёного, на коммите из AC-6 — возвращает.

AC-8. Если событие прогона, к которому относится `skipped` задание полного
набора, не определилось (индекс прогонов коммита недоступен), ни
`ci.verifying_status`, ни `ci.branch_status` не засчитывают коммит зелёным.

AC-9. Push без PR: коммит, у которого задание полного набора исполнено
(`success`) в прогоне `push` и прогона `pull_request` нет, засчитывается
зелёным `ci.verifying_status` и `ci.branch_status`; тот же коммит с заданием
`skipped` в `push` и без `pull_request` — не засчитывается (полный набор
считается нужным).

AC-10. `ci.find_run_id` для коммита, у которого упавшее задание полного
набора шло в прогоне `pull_request`, а в прогоне `push` то же задание
`skipped`, возвращает id прогона `pull_request`; `ci.trigger_rerun` с этим
коммитом нацеливается на тот же прогон.

AC-11. Тесты в `tests/` на свойства AC-4…AC-10 несут заявки «Ловит мутацию».
PLAN содержит замер по истории Actions: число прогонов `python` на коммит
ветки задачи до (по последним задачам, с указанием задач) и ожидаемое после.

AC-12. Проверка со статусом `skipped` в обоих прогонах коммита (`push` и
`pull_request`), не входящая в перечень полного набора (пример — «Карта
кодовой базы генерируется и свежа» на ветке `task/**`), не мешает
`ci.verifying_status` вернуть `ci.VERIFYING_GREEN` и `ci.branch_status` —
зелёный, если задания перечня завершились успехом и прочие проверки
зелёные.

AC-13. Коммит внешнего проекта (вызов `ci.verifying_status`/`ci.branch_status`
с `repo` внешнего target), для которого перечень полного набора не объявлен,
оценивается как до изменения: набор check-run'ов, засчитанный зелёным до
изменения (в том числе со `skipped` проверками без исполненного близнеца в
другом прогоне), засчитывается зелёным и после.

AC-14. Перечень полного набора совпадает с именами заданий (либо `name` их
проверок — в той форме, в которой объявлен перечень)
`.github/workflows/ci.yml` с наложенным приложением PLAN: тест в `tests/`
краснеет, если задание перечня в `ci.yml` переименовано или отсутствует.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` ≥ $30 (рамка Оператора в ТЗ — $30); число
критериев приёмки ≥ 10; возможно — зона задевает механизм записи
`docs/invariants.md` (инвариант 36 о триггерах CI).

Обоснование монолита (материал для решения Оператора): правка `ci.yml`
(снятие полного набора с прогона `push` при открытом PR) и правка
`orchestrator/ci.py` (`skipped` полного набора без завершённого прогона
`pull_request` — не зелёный) — одна атомарная смена механики. Правка `ci.yml`
без правки пульта даёт ложный зелёный: `skipped` входит в `ci.GREEN`, и
`verifying`/гейт мержа пропустили бы коммит до завершения прогона
`pull_request`. Правка пульта без правки `ci.yml` безвредна, но не даёт
эффекта задачи; при этом приложение к `ci.yml` едет в той же задаче по
определению механики приложений PLAN — разрезать его отдельно от пульта
нельзя. Зоны кода — 4 пути, объём ограничен `orchestrator/ci.py` и тестами.

## Не входит
- CI ветки `main` (её поведение не меняется — требование 2).
- Повторное использование итогов полного прогона на гейтах пульта (задача
  01M48WT5X7).
- Автогейт по зелёному CI (строка бэклога A4).
- Время одного прогона CI.
- Правка `orchestrator/github_adapter.py`, `scripts/plan_appendix_ci.py`,
  `conftest.py`, `tests/test_invariants.py`, `docs/invariants.md`,
  `docs/adr/`, `docs/roadmap.md`, `docs/backlog.md`,
  `docs/operator-session.md`, `templates/`, `skills/`, `CLAUDE.md`,
  `models.yaml`, `roles.yaml`, `targets.yaml` — только чтение по ТЗ.
- Неослабление существующих тестов — её держит пульт (гейт неослабления),
  отдельного критерия нет.
