| AC-3 | да | пустой каталог всегда/никогда не отбирается (нет файлов → `max()` по пустому → пропуск или падение) |
| AC-4 | да | `_suite_run_candidates` без `_kept_task_ids` |
| AC-5 | да | сравнение с замком по иному ключу; игнор живого `pid`; отбор `pending-journal`/`tmp-x` (снят `is_task_id_form`); переход по ссылке |

Отклонения:
1. **AC-2/AC-5 не ловят «пересторожную» мутацию по `run.json`.** Каждый
   реальный каталог `suite-run/<id>/` содержит `run.json` с `pid`
   (`orchestrator/suite_run.py:127–129`); у старого прогона этот `pid`
   мёртв. SPEC требует (SPEC.md:46–52), чтобы мёртвый, не целый,
   отсутствующий `pid` и нечитаемый `run.json` признаком живого прогона не
   были, но ни один AC не утверждает, что старый каталог с `run.json`
   мёртвого (или нецелого) `pid` **отбирается**. Мутация «есть `run.json` →
   не отбирать» (или «есть ключ `pid` → не отбирать») проходит AC-1…AC-15,
   а на боевом пульте не удалит ни одного из 94 каталогов — смысл задачи
   (CR-2026-10-22-9) теряется при зелёной планке. Нужен AC: старый каталог
   закрытой задачи вне 20 с `run.json`, где `pid` мёртвого процесса (и
   отдельно — `pid` не целое/`run.json` нечитаем), отбирается и удаляется.
2. **AC-5 не ловит «замок вообще есть → ничего не отбирать».** SPEC.md:45
   — исключается только каталог задачи, за которой замок. Нет AC, что при
   `lock.json` с id **другой** задачи старый каталог отбирается. Замок
   мёртвого держателя остаётся на диске (`suite_lock.py:184–189` снимает
   только свой), так что мутация «`holder()` не `None` → пропустить всё»
   правдоподобна и на практике блокирует уборку надолго; все AC зелёные.
