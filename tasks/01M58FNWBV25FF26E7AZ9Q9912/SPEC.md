# SPEC: G1а (часть 1) — компоненты проекта в записи targets.yaml: схема, profile_of, выбор по путям

## Контекст
Первая задача волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`, принят Оператором 19.10.2026; «Решение» п. 1–3). Сегодня профиль тестов проекта — одно поле записи `test_profile` (`orchestrator/targets.py:43-73`, проверка `check` `:182-190` и `_check_profile` `:290-318`). Его разбирает `orchestrator/project_profile.py` (`Profile`, `decide` `:143`, `for_task` `:175`, `full_suite_limit` `:178`), источник — `repo_context.profile_of` (`orchestrator/repo_context.py:139-151`). Проект из нескольких частей с разными раннерами (sled: backend и frontend) так не описать. Задача вводит схему `components:`, её чтение читателями профиля и выбор компонентов по путям. Исполнение прогонов по компонентам — задача G1б.

По ответу Оператора (ANSWER-1, п. 9) это **часть 1** прежней G1а. Проверки `doctor` (`tools`, `paths_source`, `workdir`; п. 5 ТЗ) и ключ кэша итога (п. 6 ТЗ) вынесены в отдельную задачу «G1а-2» после мержа этой. `targets.yaml` разбирает `orchestrator/yamlmini.py` (`targets.load`, `targets.py:111`), и этот модуль не меняется (ANSWER-1, п. 1). Поэтому `components:` — отображение, а не блочный список.

## Требования

1. Запись проекта в `targets.yaml` может нести поле `components:` вместо `test_profile`. Оба поля в одной записи — отказ проверки записи (`targets.check`).
2. Форма `components:` (ANSWER-1, п. 1) — непустое отображение «имя компонента → поля компонента», и `targets.load` читает его без правки `yamlmini.py`. Имя компонента — ключ отображения, отдельного поля `name` нет. Имя не содержит `:` (иначе идентификатор требования 7 неразборчив). Поля компонента — непустое отображение.
3. Поля компонента и их формы (ТЗ п. 1; ANSWER-1, пп. 1, 3, 5, 8). Каждое поле проверяется по форме. Отказ называет проект, компонент и поле. Неизвестное поле компонента (в том числе `name`) — отказ.
   - Прежние подполя профиля — тех же видов, что в `targets.PROFILE_FIELDS`: `command`, `long_lived_dir`, `long_lived_name`, `weakening_scope`, `mutation_claim_scope`, `full_suite_timeout_sec`, `runner`, `workdir`, `env`, `long_lived_imports`. Исключения — ниже.
   - `report` — `junit-xml` или `pult-vitest`. `pult-vitest` — только допустимое значение, отчётчика нет (G1б).
   - `install`, `checks_local` — одна команда: непустой список непустых строк.
   - `workdir` и `env` у компонента допустимы при любом `runner`. Правило `targets.PROFILE_OWN_RUNNER_ONLY` (`targets.py:71`, `:310-318`) на компонент не действует.
   - `long_lived` — шаблон пути от корня репозитория с обязательным `<id>`; кроме него допустимы только заполнители `<dir>` и `<name>`. В одном компоненте — либо `long_lived`, либо пара `long_lived_dir`/`long_lived_name`; обе формы сразу — отказ.
   - `plank_layout` — шаблон пути с обязательным `<id>`.
   - `repo` — непустая строка; без поля — имя записи проекта.
   - `report_args`, `select`, `failure_errors`, `layers` — списки непустых строк.
   - `knowledge` — список путей от корня репозитория: относительных, без `..` и без ведущего `/`. Это не имя файла `*.yaml`, как у одноимённого поля записи (`targets.py:80-81`).
   - `tests`, `test_support` — списки масок `project_profile.mask_matches`. Маска с `{` или `}` — отказ с причиной «альтернативы `{a,b}` не поддерживаются — разверните в несколько масок».
   - `paths` — регулярные выражения путей от корня репозитория: одна строка или потоковый список. Каждое выражение компилируется `re.compile`. Выражение с `"`, `'`, `,`, `[` или `]` — отказ формы с причиной. У записи с несколькими компонентами `paths` обязательно у каждого компонента.
   - `paths_source` — необязательное отображение ровно из подполей `file` и `key`, оба — непустые строки.
   - `depends_on` — отображение «имя компонента-поставщика → поля». Поставщик — другой компонент той же записи, не сам компонент. Поля — ровно `via` и `paths`, оба обязательны. `via` — одно из `paths`, `files`, `contract`. `paths` — той же формы, что `paths` компонента. `contract` только разбирается и проверяется по форме.
   - `tools` — отображение «имя инструмента → строка требуемой версии»; значение не строка — отказ.
4. Для записей с `test_profile` (артель, sled сегодня) всё прежнее: разбор, поля `Profile`, исходы `decide`/`for_task`/`full_suite_limit`, все тексты, в том числе отказ `test_profile.report` («ожидается junit-xml», `targets.PROFILE_REPORTS`). Такая запись читается как один компонент с именем `default`. Прежнее поведение закрепляется тестами до правки кода (ТЗ п. 2).
5. `repo_context.profile_of` (ANSWER-1, п. 2):
   - запись с одним компонентом — исход PRESENT, его подполя из `targets.PROFILE_FIELDS` — значения профиля. Дальше `decide`/`for_task` ведут себя как для записи с теми же подполями в `test_profile`.
   - у такого компонента нет подполя, обязательного у `test_profile` (`command`, `long_lived_dir`, `long_lived_name`, `weakening_scope`, `mutation_claim_scope`) — исход UNREAD с причиной, называющей компонент и подполе. `decide` отвечает отказом, исключения нет.
   - запись с несколькими компонентами — исход UNREAD с причиной «запись проекта с несколькими компонентами исполняется после G1б».
6. Выбор компонентов (ТЗ п. 3). Функция пульта по проекту и набору путей возвращает затронутые компоненты.
   - Компонент затронут, если путь подходит под его `paths` (`re.search` по пути от корня репозитория) или под маску его `test_support` (`mask_matches`).
   - Компонент затронут и как потребитель: если путь подходит под `paths` элемента его `depends_on` вида `paths` или `files`. Вид `contract` выбор не расширяет.
   - Если хоть один путь набора не задел ни одного компонента, выбор — все компоненты (не пустой).
   - У записи с одним компонентом (в том числе `default` из `test_profile`) выбор — он, при любом наборе путей.
7. Идентификатор теста компонента (ADR-0026 п. 3): формирование и разбор `<компонент>:<путь файла от корня репозитория>::<полное имя>[#<n>]`. Полное имя может само содержать `::` (класс и метод). Формат зон задачи и `no_paths` не меняется.
8. Отказ до G1б во всех читателях профиля (ТЗ п. 4; ANSWER-1, п. 2). Для записи с несколькими компонентами причина «запись проекта с несколькими компонентами исполняется после G1б» доходит:
   - до `decide`/`for_task` — отказ задаче;
   - до `full_suite_limit` — `TargetsError`;
   - до `suite_run._profile_command` — отказ. Его ветка UNREAD уже есть, `suite_run.py` не меняется.
9. `acceptance._task_own_profile` на исходе UNREAD (любой причины, в том числе требования 5) отказывает с причиной из `profile_of` и не возвращает `None`. Полный набор задачи тогда не идёт прежней формой пульта (`full_suite` без профиля). Ограничение ТЗ «в `acceptance.py` только ключ кэша» для этой функции снято Оператором (ANSWER-1, п. 2). Исходы ABSENT и PRESENT с `runner: pult-pytest` — прежние (`None`, прежний вызов).
10. Тесты задачи детерминированы и без сети. Учебные записи с одним и двумя компонентами (`depends_on` вида `files`) записываются текстом файла и читаются через `targets.load`, а не только словарём в `targets.check` (ТЗ п. 7).

## Критерии приёмки

AC-1. Учебный текст `targets.yaml` с записью из двух компонентов `backend` и `frontend` проходит `targets.load` без отказа. Запись несёт `paths`, `test_support`, `depends_on` вида `files` у `frontend` на `backend`, `paths_source`, `tools`, `install`, `long_lived` и `knowledge` в формах требования 3. Разобранные значения доходят до вызывающего: имена компонентов, `depends_on.backend.via == "files"`.

AC-2. Неверная форма поля даёт отказ `targets.check`, называющий компонент и поле. Случаи:
- неизвестное поле, в том числе `name`;
- запись с несколькими компонентами, у компонента которой нет `paths`;
- выражение `paths` не компилируется;
- выражение `paths` содержит `,`, `[` или `]`;
- маска `tests`/`test_support` с `{` — отказ с текстом «альтернативы `{a,b}` не поддерживаются — разверните в несколько масок»;
- `depends_on` на несуществующий компонент или на сам компонент;
- `via` вне `paths|files|contract`;
- `depends_on` без `paths`;
- `long_lived` без `<id>` или с иным заполнителем;
- `long_lived` вместе с `long_lived_dir`;
- `plank_layout` без `<id>`;
- значение `tools` не строка;
- `paths_source` без `key`;
- пустой `install`;
- `report` вне `junit-xml|pult-vitest`;
- имя компонента с `:`.

`report: pult-vitest` и `workdir`/`env` без `runner` у компонента — без отказа.

AC-3. Запись, несущая одновременно `test_profile` и `components:`, — отказ проверки записи.

AC-4. Записи с `test_profile` (артель и учебная запись внешнего проекта) ведут себя как до правки: `Profile`, исходы `decide`/`for_task`/`full_suite_limit` и их тексты те же. Тот же текст и у отказа `test_profile.report: pult-vitest`. Выбор компонентов (требование 6) для такой записи — один компонент `default`.

AC-5. Запись с одним элементом `components:` даёт от `decide`/`for_task` тот же `Profile`, что запись с теми же подполями в `test_profile`. Если у единственного компонента нет `long_lived_dir`, `decide` отвечает отказом с причиной, называющей это подполе, а не исключением.

AC-6. Выбор компонентов на учебной записи AC-1, где `frontend` зависит от `backend` по `depends_on` вида `files`:
- путь backend вне `paths` того `depends_on` → только `backend`;
- путь, попавший в `paths` того `depends_on` → `backend` и `frontend`;
- путь, попавший в маску `test_support` компонента и не в его `paths` → этот компонент;
- путь `docs/x.md` → все компоненты;
- набор из пути backend и `docs/x.md` → все компоненты;
- у записи с одним компонентом любой путь → он.

AC-7. Идентификатор теста компонента: формирование из (компонент, путь, полное имя[, n]) и разбор обратно дают исходные части. Проверяются форма без `#<n>`, форма с `#<n>` и полное имя с `::`.

AC-8. Проект, запись которого несёт два компонента. Отказ `decide`/`for_task`, `TargetsError` от `full_suite_limit` и отказ `suite_run._profile_command` содержат текст «запись проекта с несколькими компонентами исполняется после G1б». Ни один из них не даёт профиль, исход «пропуск» или прежний предел `config`.

AC-9. Проект с исходом `profile_of` UNREAD (запись из двух компонентов и запись с битым `test_profile`). `acceptance.acceptance_suite` не зовёт `full_suite` прежней формой и отказывает с причиной из `profile_of`. Исход ABSENT и PRESENT с `runner: pult-pytest` — прежний вызов `full_suite`.

## Меняемое поведение
Требование 9 по решению Оператора (ANSWER-1, п. 2: «строгость, не ослабление; перечислить в „Меняемое поведение“») меняет ожидание существующего метода `tests/test_acceptance_suite_profile.py::AcceptanceSuiteProfileTest::test_own_profile_passed_other_profiles_keep_old_call`.

Его подслучай `runner="не прочитан"` сегодня утверждает прежний вызов `full_suite(Path("/tmp"), "T001", **tail)` при исходе UNREAD (стр. 57-58, 77-80). После правки исход UNREAD — отказ, и вызова нет.

Это смена вида ожидания («вызван прежней формой» → «отказ без вызова»), а не пара скалярных литералов. Строкой формата `` `было` → `стало` `` раздел её не выражает: такую строку `approve` гейта SPEC отказал бы. Поэтому смена записана здесь свободным текстом, без пункта списка.

Если гейт неослабления на `in_dev -> verifying` сочтёт правку этого метода ослаблением, нужна строка мандата Оператора `Ослабление тестов разрешено: tests/test_acceptance_suite_profile.py::AcceptanceSuiteProfileTest::test_own_profile_passed_other_profiles_keep_old_call`. Добавить её Оператор может на гейте SPEC — в ANSWER-1 мандатов нет. Иначе разработчик эскалирует, не обходя гейт.
