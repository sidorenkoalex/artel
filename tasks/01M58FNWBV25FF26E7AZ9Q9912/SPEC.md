# SPEC: G1а — компоненты проекта в записи targets.yaml: схема, выбор по путям, проверки doctor

## Контекст
Первая задача волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`, принят Оператором 19.10.2026; «Решение» п. 1–3, «Описание sled после ADR», «Порядок исполнения» — строка G1а). Сегодня профиль тестов проекта — одно поле записи `test_profile` (`orchestrator/targets.py:43-73`, проверка `:175-190`, `:300-320`), его разбирает `orchestrator/project_profile.py` (`Profile`, `decide` `:143`, `for_task` `:175`) из `repo_context.profile_of` (`orchestrator/repo_context.py:139-151`). Проект из нескольких частей с разными раннерами (sled: backend и frontend, CI `ci.yml:58-63`, `BACKEND_RE`/`FRONTEND_RE`) так не описать. Кроме того, ключ кэша итога полного набора собственного раннера проекта (`orchestrator/acceptance.py:2146-2158`, `_own_suite_result_key`) не учитывает файлы блокировки зависимостей и версии инструментов проекта — после смены зависимостей устаревший зелёный итог сходит за свежий, а `doctor` (`orchestrator/doctor/project_checks.py`) не проверяет ни версии инструментов, ни согласованность карты путей с CI проекта. Задача вводит схему и выбор компонентов; исполнение прогонов по компонентам — следующая задача G1б.

## Требования

1. Запись проекта в `targets.yaml` может нести поле `components:` (список компонентов) вместо `test_profile`. Оба поля в одной записи — отказ проверки записи.
2. Компонент несёт прежние подполя профиля — `command`, `long_lived_dir`/`long_lived_name` или новое `long_lived`, `weakening_scope`, `mutation_claim_scope`, `report`, `install`, `full_suite_timeout_sec`, `runner`, `workdir`, `env`, `long_lived_imports` — и новые поля ADR-0026 п. 1: `name` (уникальное в записи), `repo` (по умолчанию — имя записи), `report_args`, `select`, `failure_errors`, `paths` (регулярные выражения путей от корня репозитория; обязательное у записи с несколькими компонентами), `paths_source` (необязательное: `{file, key}` — откуда в CI проекта взяты `paths`), `depends_on` (список `{component, via: paths|files|contract, paths}`; `contract` — только разбор и проверка формы, без исполнения), `tests`, `test_support`, `long_lived`, `plank_layout`, `tools` (`{имя инструмента: требуемая версия}`), `knowledge`, `layers`, `checks_local`.
3. Каждое поле компонента проверяется по форме с понятным отказом, называющим поле; неизвестное поле компонента — отказ. Допустимые значения `report` дополняются `pult-vitest` (только как допустимое значение; отчётчик — G1б).
4. Прежнее поле `test_profile` читается как один компонент с именем `default`; разбор, поля `Profile`, исходы `for_task`/`decide` и все тексты для записей с `test_profile` (артель, sled сегодня) — прежние. Это поведение закреплено тестами, написанными до правки кода.
5. Функция пульта по проекту и набору путей возвращает затронутые компоненты: те, чьи `paths` или `test_support` задевают путь, плюс их потребители по `depends_on` вида `paths` и `files`. Путь, не задевший ни одного компонента, даёт все компоненты (выбор не пустой). У записи с одним компонентом выбор — он.
6. Идентификатор теста компонента формируется и разбирается в форме `<компонент>:<путь файла от корня репозитория>::<полное имя>[#<n>]` (ADR-0026 п. 3).
7. Пока исполнения по компонентам нет (G1б): для записи с несколькими компонентами `for_task`/`decide` отказывают задаче с явным текстом «запись проекта с несколькими компонентами исполняется после G1б». Запись с одним элементом `components:` ведёт себя как запись с `test_profile`.
8. `doctor` для каждого проекта с `components:`:
   - (а) для каждого инструмента `tools` компонента — запуск `<инструмент> --version` с окружением компонента (`env.PATH`) и сравнение с требуемой версией (совпадение главной части версии): совпадение — ok; несовпадение — fail; инструмента нет — fail; сбой запуска — skip с причиной;
   - (б) `paths_source`: значение переменной `key` в файле `file` клона проекта сравнивается с `paths` компонента (и с `paths` его `depends_on` вида `paths`/`files`); расхождение — warn, в тексте обе строки;
   - (в) каждый `workdir` компонента существует в клоне проекта.
   У записей с `test_profile` новых строк `doctor` нет.
9. Ключ кэша итога полного набора собственного раннера проекта (`_own_suite_result_key`) включает суммы файлов блокировки зависимостей в `workdir` (`uv.lock`, `package-lock.json`, `poetry.lock`, `yarn.lock`, `pnpm-lock.yaml` — какие есть) и `tools` компонента. У артели ключ прежний.
10. Тесты задачи детерминированы и без сети: учебные записи с одним и двумя компонентами (`depends_on` вида `files`), подмена запуска инструментов для `doctor`, учебный клон с CI-файлом для `paths_source`.

## Критерии приёмки

AC-1. Учебная запись проекта с двумя компонентами (в том числе с `depends_on` вида `files`, `paths_source`, `tools`) проходит проверку записи `targets.yaml` без отказа.

AC-2. Каждое поле компонента из требования 2 с неверной формой даёт свой отказ проверки записи, называющий это поле; неизвестное поле компонента — отказ; повтор `name` в записи — отказ; запись с несколькими компонентами, у компонента которой нет `paths`, — отказ; `report: pult-vitest` — допустимое значение.

AC-3. Запись, несущая одновременно `test_profile` и `components:`, — отказ проверки записи.

AC-4. Для записей с `test_profile` (артель и учебная запись внешнего проекта): `Profile`, исходы `decide`/`for_task` и их тексты совпадают с поведением до правки; запись читается как один компонент с именем `default`.

AC-5. Запись с одним элементом `components:` даёт те же исходы `decide`/`for_task` (профиль с теми же полями), что запись с теми же подполями в `test_profile`.

AC-6. Выбор компонентов на учебной записи с компонентами backend и frontend (frontend зависит от backend по `depends_on` вида `files`): путь backend → только backend; путь, попавший в `paths` того `depends_on`, → и backend (поставщик), и frontend (потребитель); путь `docs/x.md` → все компоненты; путь, попавший в `test_support` компонента, → этот компонент. У записи с одним компонентом любой путь → он.

AC-7. Идентификатор теста компонента: формирование из (компонент, путь, полное имя[, n]) и разбор обратно дают исходные части, для формы без `#<n>` и с `#<n>`.

AC-8. Задача проекта, запись которого несёт несколько компонентов, получает от `for_task`/`decide` отказ с текстом «запись проекта с несколькими компонентами исполняется после G1б».

AC-9. `doctor`, проверка `tools` с подменённым запуском инструмента: вывод `v22…` при требуемой `22` — ok; `v20…` при требуемой `22` — fail; инструмента нет — fail; сбой запуска — skip с причиной.

AC-10. `doctor`, проверка `paths_source` на учебном клоне с CI-файлом: значение переменной `key`, отличное от `paths` компонента, — warn, текст содержит обе строки; совпадающее — без warn. Отсутствующий в клоне `workdir` компонента — строка `doctor` не ok.

AC-11. Для записей с `test_profile` набор строк `doctor` тот же, что до правки (новых строк нет).

AC-12. Смена содержимого `package-lock.json` (или `uv.lock`) в `workdir` компонента меняет ключ кэша итога полного набора собственного раннера проекта; смена `tools` компонента — тоже. У артели ключ кэша и все тексты прежние.

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны вне общих зон — 6 (`orchestrator/targets.py`, `orchestrator/project_profile.py`, `orchestrator/repo_context.py`, `orchestrator/doctor/project_checks.py`, `orchestrator/doctor/cli.py`, `orchestrator/acceptance.py`) при пороге 5; число критериев приёмки — 12 при пороге 10.

Предлагается **монолит** — материал для решения Оператора:
- Ядро задачи — схема компонентов и её разбор (`targets.py`, `project_profile.py`, `repo_context.py`) — неделимо: новое поле записи без разбора и без отказа `for_task`/`decide` для нескольких компонентов (требование 7) оставляет пульт в состоянии, где проверка записи принимает `components:`, а гейты читают такую запись как «нет профиля» (у внешнего проекта — пропуск проверок тестов, `project_profile.decide:161`).
- Проверки `doctor` (требование 8) и ключ кэша (требование 9) — тонкие потребители той же схемы (`tools`, `paths_source`, `workdir`); отделить их технически можно, но каждая часть стала бы задачей в 1–2 файла с отдельными шагами аналитика, аудита и ревью, что дороже экономии. Оператор уже выделил G1а единицей в ADR-0026 («Порядок исполнения», оценка $30–40), а исполнение по компонентам — отдельной G1б.
- Если Оператор предпочтёт нарезку, естественная граница: (1) схема, разбор, выбор, отказ до G1б; (2) `doctor` + ключ кэша — после части 1.

- Смена формата зон задачи и `no_paths` — формат прежний.

Потребность в правке вне зон — эскалация.
- Зелёный полный набор `tests/`, зелёный CI ветки, неизменность защищённых путей, непревышение бюджета — их держит пульт.
