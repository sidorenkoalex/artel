# SPEC: canary runs — история прошедших прогонов канарейки командой пульта

## Контекст
Находка ревизии кода 22.10 CR-2026-10-22-7: стоимость, вердикт и причину
отказа прошедших прогонов канарейки сессия Оператора берёт SQL-запросами к
таблице `canary_runs` (66 запросов за 12 дней) или из `logs/canary/run-*.json`
— это замещение недостающей команды. `canary live`
(`orchestrator/canary.py:3129`, `cmd_canary_live`) показывает только реестр
живых прогонов. Нужна читающая команда пульта `canary runs`, выводящая
прошедшие прогоны из `canary_runs` (схема — `orchestrator/store.py:1563`,
чтение — `store.all_canary_runs`, `orchestrator/store.py:1710`).

Адреса на HEAD ветки задачи: `_cmd_canary` — `orchestrator/artel.py:1547`
(ветка `live` — 1565), строка справки `canary live` — `orchestrator/artel.py:185`;
`canary._acceptance_summary` — `orchestrator/canary.py:2031`,
`canary._diagnostics_dir` — 2067, `canary.RUN_STAMP_RE` — 2803
(`[0-9]{8}T[0-9]{6}Z`, без якорей); `run_stamp` — метка UTC старта прогона
(`orchestrator/canary.py:3295`, 3579); реестр живых прогонов читают
`canary._live_dir` (2806) и `canary.live_runs` (2930).

Решения Оператора на гейте SPEC 23.10.2026 (круг 1) внесены в требования
2–5 и критерии AC-2, AC-4, AC-6, AC-9–AC-12.

## Требования

1. Новая подкоманда `canary runs [--since <ГГГГ-ММ-ДД> | <run_stamp>]`:
   разбор — в `orchestrator/artel.py` (ветка `_cmd_canary` рядом с `live`),
   исполнение — новая функция
   `canary.cmd_canary_runs(since: str | None = None, run_stamp: str | None = None) -> None`.
2. Отказы — в разборе, до чтения БД, с ненулевым кодом выхода:
   - текст использования (сообщение отказа содержит строку
     `canary runs [--since <ГГГГ-ММ-ДД> | <run_stamp>]`) — для аргумента,
     начинающегося с `-`, кроме `--since`; для второго позиционного
     аргумента; для повторного `--since`; для `--since` без значения
     (последний аргумент) и для `--since`, значение которого начинается с
     `--`;
   - значение `--since`, не проходящее одновременно регулярное выражение
     `\d{4}-\d{2}-\d{2}` (проверка строки целиком) и
     `datetime.strptime(<значение>, "%Y-%m-%d")` (в том числе календарно
     недопустимая дата `2026-02-30`), — «canary runs: --since ждёт дату
     ГГГГ-ММ-ДД»;
   - позиционный аргумент, не проходящий `canary.RUN_STAMP_RE.fullmatch`
     (совпадение только начала строки отказом не спасается; любое иное
     значение, например `foo`, — тоже), — «canary runs: run_stamp
     <значение> не по шаблону ГГГГММДДTЧЧММССZ»;
   - `--since` вместе с `run_stamp` — «canary runs: --since и <run_stamp>
     несовместимы».
3. Отбор прогонов. Прогон — группа строк одного `run_stamp`; прогоны
   выводятся от нового к старому по времени старта прогона — по
   `run_stamp` (метка UTC старта; порядок строк `ГГГГММДДTЧЧММССZ`
   совпадает с хронологическим), независимо от порядка `id`; строки внутри
   группы — по `id`.
   - без аргументов — последние в этом порядке
     `canary.CANARY_RUNS_DEFAULT_COUNT = 10` прогонов;
   - `--since <дата>` — все прогоны, у которых самая ранняя строка группы
     (наименьший `created_at`) не раньше `<дата> 00:00:00Z` — граница
     включительно (`>=`);
   - `<run_stamp>` — один этот прогон; его нет — «canary runs: прогона
     <run_stamp> нет», ненулевой код выхода.
   Пустая таблица (или пустой отбор `--since`) — одна строка «прогонов
   канарейки нет», код выхода 0.
4. Формат вывода (поля по колонкам `canary_runs`; значение `NULL`
   печатается как `—`):
   - заголовок прогона: `<run_stamp>  набор=<set_name>  sha=<main_sha первые 8 знаков>  задач=<N>  зелёных=<число verdict='green'>  $<сумма cost_usd, два знака>`;
     значения `набор=` и `sha=` берутся из первой строки группы по `id`; при
     суммировании `cost_usd` значение `NULL` считается нулём;
   - строка задачи с отступом в два пробела: `<title>  <task_id>  вердикт=<verdict>  исход=<outcome>  $<cost_usd, два знака>  шагов=<steps>  ревью-итераций=<review_iterations>  эскалаций=<escalations>`,
     затем ` (роли: <escalation_roles>)`, если `escalation_roles` непуст, и
     `  [расхождение маркера]`, если `marker_mismatch` = 1;
   - под строкой задачи с отступом в четыре пробела — причина отказа
     автогейта тем же текстом, что
     `canary._acceptance_summary(acceptance_route, autogate_refusal, False)`
     без ведущих пробелов, если он непуст;
   - под ней же — `    диагностика: .artel/canary/<run_stamp>/<task_id>`
     (путь относительно корня пульта, без завершающей `/`), если каталог
     `.artel/canary/<run_stamp>/<task_id>/` под корнем пульта существует.
5. Команда только читает: строки — `store.all_canary_runs(store.db())`,
   подключение к БД — только через `store`. Ленивое заведение внутри
   `store.all_canary_runs` — `CREATE TABLE IF NOT EXISTS`, `add_column`,
   перезапись `set_name IS NULL` набором по умолчанию
   (`orchestrator/store.py:1605`) и миграция `canary_baseline` на ключ с
   набором (`orchestrator/store.py:1607`, 1611–1640) — часть заведения, как
   при любом чтении; команда его не меняет и не обходит. Сверх него — ни
   записей журнала, ни правок `canary_runs`/`canary_baseline`, ни сетевых
   вызовов, ни чтения реестра живых прогонов.
6. Подкоманды `canary live`, `canary pool-seal`, `canary run-task` и запуск
   прогона (`--k`) не меняются; отказ «нужен параметр --k» для прочих
   аргументов — прежний.
7. Справка `orchestrator/artel.py`: строка
   `canary runs [--since <ГГГГ-ММ-ДД> | <run_stamp>]` рядом со строкой
   `canary live`.
8. Тесты в `tests/` — детерминированные, без сети: строки заводятся прямой
   вставкой в `canary_runs` песочницы (по образцу записи
   `canary._record_canary_run` или `INSERT`), корень пульта — песочница
   `tests/sandbox.py`; покрывают критерии приёмки ниже. Существующие тесты
   не правятся.

## Критерии приёмки

AC-1. Три прогона по две задачи с разными вердиктами, стоимостью и причиной
отказа: `canary runs` через `artel.main` печатает три заголовка от нового к
старому с верными суммами `cost_usd` и счётом зелёных, строки задач с полями
требования 4 и строку причины отказа автогейта (тем же текстом, что
`canary._acceptance_summary(acceptance_route, autogate_refusal, False)` без
ведущих пробелов). На текущем коде критерий красный — прежний отказ «нужен
параметр --k».

AC-2. Порядок групп — по времени старта прогона (`run_stamp`), от нового к
старому, а не по `id`: при трёх прогонах, вставленных так, что прогон с
более ранним `run_stamp` несёт бо́льшие `id`, а строки двух прогонов
перемежаются по `id`, заголовки идут по убыванию `run_stamp`; строки задач
внутри каждой группы — по возрастанию `id`.

AC-3. При 12 прогонах в таблице `canary runs` без аргументов показывает 10
прогонов с наибольшими `run_stamp` (`canary.CANARY_RUNS_DEFAULT_COUNT = 10`).

AC-4. `canary runs --since <дата>`: прогон, самая ранняя строка которого
имеет `created_at` ровно `<дата> 00:00:00Z`, выводится (граница
включительно); прогон, самая ранняя строка которого — `<дата − 1 день>
23:59:59Z`, а другая строка — позже `<дата> 00:00:00Z`, не выводится (дата
по самой ранней строке группы); прогон целиком раньше даты не выводится.

AC-5. `canary runs <run_stamp>` выводит ровно один этот прогон; неизвестный
(по шаблону корректный) `run_stamp` — отказ «canary runs: прогона
<run_stamp> нет» и ненулевой код выхода.

AC-6. Каждый отказ требования 2 завершается ненулевым кодом выхода со своим
текстом и происходит до чтения БД (при `store.db`, подменённом функцией,
падающей при вызове, она не вызывается):
- текст использования — `canary runs --bogus`;
  `canary runs 20261023T120000Z 20261024T120000Z`;
  `canary runs --since 2026-10-01 --since 2026-10-02`; `canary runs --since`;
  `canary runs --since --x`;
- «canary runs: --since ждёт дату ГГГГ-ММ-ДД» — `--since 20261023`,
  `--since 2026-1-5`, `--since 2026-02-30`;
- «canary runs: run_stamp <значение> не по шаблону ГГГГММДДTЧЧММССZ» —
  `20261023T120000Zxx` и `foo`;
- «canary runs: --since и <run_stamp> несовместимы» —
  `--since 2026-10-01 20261023T120000Z`.

AC-7. Пустая таблица `canary_runs` — вывод одной строкой «прогонов канарейки
нет», код выхода 0.

AC-8. После выполнения `canary runs` число строк таблиц `steps`,
`canary_runs` и `canary_baseline` не изменилось.

AC-9. Строка с `marker_mismatch` = 1 и непустым `escalation_roles` несёт
пометки ` (роли: <escalation_roles>)` и `  [расхождение маркера]`; `NULL` в
`main_sha` первой строки группы — `sha=—` в заголовке; группа, где `set_name`
и `main_sha` первой по `id` строки отличаются от последующих строк, — в
заголовке значения первой строки; `NULL` в `cost_usd` одной из строк — сумма
заголовка считает его нулём, а строка этой задачи печатает `$—`. `набор=—`
критерием не проверяется (`NULL` в `set_name` переписывает ленивое заведение,
требование 5).

AC-10. Если каталог `.artel/canary/<run_stamp>/<task_id>/` под корнем пульта
существует, под строкой задачи стоит ровно
`    диагностика: .artel/canary/<run_stamp>/<task_id>`; если не существует —
строки `диагностика:` у этой задачи нет.

AC-11. Чтение только через `store`: при `sqlite3.connect`, подменённом
обёрткой, которая падает, если её вызывает код вне модуля
`orchestrator.store`, `canary runs` печатает прогоны (вызова обёртки извне
`store` нет).

AC-12. Ни реестра живых прогонов, ни сети: при `canary.live_runs`,
`canary._live_dir`, `subprocess.Popen` и `socket.socket`, подменённых
функциями, падающими при вызове, `canary runs` печатает прогоны и ни одна из
подмен не вызвана.

AC-13. `orchestrator/artel.py` в справке несёт строку
`canary runs [--since <ГГГГ-ММ-ДД> | <run_stamp>]` рядом со строкой
`canary live`; `canary` без `--k` с прочими аргументами по-прежнему отказывает
«нужен параметр --k».

тексте SPEC: `store.py`, `config.py`, `canary_drive.py`, `pool_seal.py`,
`models.py` ТЗ объявляет только для чтения. Меняются только
`orchestrator/canary.py` (новая функция, константа и помощники вывода),
`orchestrator/artel.py` (ветка `runs` и строка справки) и новый тестовый
файл в `tests/`.

Прогноз диффа: 24 КиБ (одна функция вывода с помощниками, ветка разбора,
один тестовый файл) — ниже половины потолка гейта ёмкости
(`REVIEW_SNAPSHOT_DIFF_MAX_BYTES` = 256 КиБ).

Обоснование монолита: делить нечего. Ветка разбора в `artel.py` без
`canary.cmd_canary_runs` вызывает несуществующую функцию, а функция без
ветки недоступна из CLI и не проверяется критериями приёмки через
`artel.main`. Все критерии проверяют одну команду целиком, поэтому
промежуточная часть мержилась бы без проверяемого поведения.
