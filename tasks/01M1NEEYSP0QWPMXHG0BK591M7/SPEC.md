# SPEC: Предупреждение при чужом живом lease (pause, release)

## Контекст
Инцидент 02.09.2026: ассистентская сессия диагностировала задачу
в `verifying` и рекомендовала действие по её ветке (push), не увидев,
что задачу в этот момент активно ведёт другая сессия с живым lease.
Замок от параллельных мутирующих циклов уже есть (advisory lease
T044: второй `run`/`auto` отвергается с именем держателя). Слой
операторских команд, которые lease не блокирует, исполняется молча —
без сигнала «ты вмешиваешься в задачу, которую прямо сейчас ведёт
другая сессия».

Проверка по коду (QUESTIONS.md этой задачи, ответ Оператора
ANSWER-1) показала: из семи команд ТЗ только `pause`
(`orchestrator/pause.py::cmd_pause`) и `release`
(`orchestrator/release.py::cmd_release`) сегодня исполняются
безусловно при чужом lease. Остальные пять (`approve`, `reject`,
`budget`, `kill`, `answer`) уже проходят через
`lease.run_locked(..., on_refusal="exit")` — при чужом живом lease
это отказ ДО выполнения тела команды, не «выполнение как раньше».
Оператор выбрал вариант A: эта задача покрывает предупреждением
только `pause` и `release`; поведение остальных пяти команд не
меняется (см. «Не входит»).

## Требования
1. Команды `pause` и `release`, при ЧУЖОМ живом lease у задачи
   (heartbeat свежий, pid адресуем, session_id не равен текущей
   сессии), печатают предупреждение ДО выполнения: держатель
   (session_id), возраст heartbeat, роль/шаг — если известны.
   Команда выполняется как раньше — предупреждение информирует,
   не блокирует и не запрашивает подтверждения.
2. Собственный живой lease текущей сессии и мёртвый/протухший чужой
   lease предупреждения не вызывают.
3. Предупреждение дублируется событием журнала задачи (тем же
   журнальным API, с session_id) — постфактум видно, что
   вмешательство было предупреждённым.
4. Read-only команды (`status`, `log`, `show`, `doctor`) предупреждение
   не печатают ни при каких условиях lease.
5. Поведение `approve`, `reject`, `budget`, `kill`, `answer` при чужом
   живом lease не меняется этой задачей (см. «Не входит»).

## Критерии приёмки

AC-1. При выполнении `pause` для задачи с ЧУЖИМ живым lease (heartbeat
свежий, pid адресуем, session_id ≠ текущей сессии) до выполнения
команды печатается предупреждение, содержащее session_id держателя
и возраст heartbeat (роль/шаг — если известны).

AC-2. Команда `pause` при этом выполняется как раньше: предупреждение
не блокирует выполнение и не запрашивает подтверждения.

AC-3. При выполнении `release` для задачи с ЧУЖИМ живым lease до
выполнения команды печатается предупреждение с тем же составом
данных (держатель, возраст heartbeat, роль/шаг — если известны),
и команда выполняется как раньше.

AC-4. Если lease принадлежит текущей сессии (session_id совпадает),
предупреждение не печатается ни для `pause`, ни для `release`.

AC-5. Если чужой lease мёртвый или протухший (heartbeat не свежий или
pid не адресуем), предупреждение не печатается ни для `pause`, ни
для `release`.

AC-6. Предупреждение при чужом живом lease дублируется событием
в журнале задачи (тот же журнальный API, что и у прочих событий,
с session_id держателя) — для `pause` и для `release`.

AC-7. Read-only команды `status`, `log`, `show`, `doctor` не печатают
предупреждение при чужом живом lease задачи.

AC-8. Тесты покрывают: предупреждение при чужом живом lease для
`pause` и `release`; отсутствие предупреждения при своём lease;
отсутствие предупреждения при мёртвом/протухшем чужом lease;
отсутствие предупреждения у read-only команд (`status`, `log`,
`show`, `doctor`); фактическое выполнение `pause`/`release` несмотря
на предупреждение; запись события журнала при предупреждении;
существующие тесты остаются зелёными.

## Не входит
- Изменение поведения `approve` (`orchestrator/fsm.py::cmd_approve`),
  `reject` (`cmd_reject`), `budget` (`orchestrator/budget.py::cmd_budget`),
  `kill` (`orchestrator/cleanup.py::cmd_kill`) и `answer`
  (`orchestrator/answer.py::cmd_answer`) при чужом живом lease. Сегодня
  все пять уже проходят через `lease.run_locked(..., on_refusal="exit")`
  и при чужом живом lease отказывают целиком (T044) — замена этого
  хард-блока на «предупреждение + выполнение» была бы ослаблением
  существующей защиты и по ADR-0002 (принцип целостности) требует
  отдельного ADR Оператора, не тихой правки в рамках этой задачи.
  Зафиксировано по находке analyst (QUESTIONS.md) и решению Оператора
  (ANSWER-1, вариант A).
- Блокировка операторских команд или запрос подтверждения при чужом
  lease — для `pause`/`release` только предупреждение, выполнение не
  прерывается.
- Изменение механики `lease.py` / `liveness.py` (проверки живости,
  advisory-замка) и лимитера параллельных задач.
- Регистрация read-only наблюдателей задачи.
