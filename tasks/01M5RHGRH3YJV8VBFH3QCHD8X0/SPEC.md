11. Перенос тел.

    - Помощники с утверждениями (`answer_accepted`, `answer_assert_refused`,
      `plan_approve_spec`, `spec_gate_assert_refused`,
      `status_show_with_dependencies`, `status_show_status_line`,
      `new_declares_declared`, `new_declares_assert_refused_without_traces`,

      дословно, форма — `assert …` (ADR-0027). «То же утверждение» —
      соответствие `assertEqual(a, b)` ↔ `assert a == b`,
      `assertNotEqual(a, b)` ↔ `assert a != b`, `assertIsNone(x)` ↔ `assert x
      is None`, `assertIsNotNone(x)` ↔ `assert x is not None`, `assertIn(a,
      b)` ↔ `assert a in b`, `assertNotIn(a, b)` ↔ `assert a not in b`,
      `assertTrue(x)` ↔ `assert x`, `assertFalse(x)` ↔ `assert not x`,
      `assertRegex(t, p)` ↔ `assert re.search(p, t)`; `self.<помощник>` ↔
      функция модуля, `self` ↔ имя фикстуры; текст `msg=` или позиционного
      сообщения — вторым операндом `assert`. Совпадение нормальной формы guard
      не требуется.

      ярлык — суффиксом `+ "; " + f"<ключ>={<значение>!r}"` с ключом и
      значением прежнего `subTest` в тексте сообщения каждого утверждения
      подслучая.
    - Помощник с утверждениями, вызванный в подслучае прямо или через другой
      помощник (`answer_accepted`, `answer_assert_refused`;
      `plan_approve_spec` через `plan_prepared_task` и `plan_rejected_case`;
      `new_declares_declared`, `new_declares_assert_refused_without_traces`),
      получает последний необязательный параметр `case: str = ""`;
      промежуточный помощник передаёт его дальше; сообщение утверждения тела —
      `… + case`. Исключение — `plan_rejected_case`, у которого параметр
      `case` уже есть (имя варианта): ярлык передаётся последним
      необязательным параметром `label: str = ""`, промежуточный помощник
      передаёт его дальше, сообщение утверждения тела — `… + label`. Иных
      отличий тела нет.
    - Глотание `SystemExit`, подмены, вложенные функции и замыкания —
      дословно.

## Критерии приёмки

AC-1. Патчи и заявки.
- В каталоге документов задачи первым уровнем лежат патчи
  `mutation-<nnn>.diff`, номера подряд с 001 без пропусков, по порядку файлов
  `answer`, `guard`, `plan`, `spec_gate`, `status_show`, `new_declares`;
  каждый патч меняет только файлы под `orchestrator/` или `scripts/guard.py`.
- Каждая из 33 заявок сопоставлена в PLAN патчу (у заявки с неодинаковыми по
  смыслу альтернативами — патчу на каждую альтернативу); у каждой мутации
  названы заявка, прежний файл и что меняет патч. Одинаковые по смыслу заявки
  сведены в одну мутацию со списком тестов.

AC-2. Раздел «Мутации до» в PLAN.
- В нём выводы частей `mutation-run <id> --ref base --tests <шесть файлов
  волны> --copy-table --wait-lock 4`, перенесённые дословно, с шапкой и всеми
  строками.
- Каждая часть — не больше 25 патчей; патч, способный зациклить общий узел
  (`check`, `_cycle_path`, разбор строки «Порядок:» и перечня элементов,
  поиск однозначного префикса), — один в своей части.
- В таблицах есть каждый патч набора; ни один засчитанный патч не дал
  `Timeout`.

AC-3. У каждой мутации в PLAN для таблиц «до» и «после» приведена строка
падения из лога прогона патча: файл:строка упавшего утверждения и строка
вызова в теле теста.

AC-4. Засчитывание мутаций.
- Ни одна мутация не засчитана доказательством, если её «убили» только:
  ошибка сбора, импорта, setup или фикстуры; исключение без падения
  утверждения; таймаут pytest-timeout; утверждение подготовки (`accepted`
  :198, :233, :242, :261 `answer`; `approve_spec` :160 `plan`;
  `with_dependencies` :104, :108 `status_show`; `declared` в вызове :419
  `new_declares`; метод `git` песочницы); утверждение наблюдения
  `status_line` (:116 `status_show`, :180 `new_declares`); утверждение-
  предпосылка или до действия теста (:160 `guard`, :276 и :305 `spec_gate`).
- Строки этих утверждений «до» и их новые места «после» приведены в PLAN.
- Ни одна мутация с исходом «итог неизвестен», «патч не применяется», «патч
  трогает тесты» или «не прогнана» не засчитана ни убитой, ни выжившей.
- Мутации, которые «до» не убил никто, перечислены в PLAN находками.

AC-5. Детерминированность.
- У каждой мутации в PLAN есть фраза, почему её убийство не зависит от зерна.
- Ни одна засчитанная мутация не убивается только веткой, зависящей от зерна
  (перечень «Контекста»: сырой перенос префиксов, сортировка id, только прямая
  обратная ссылка цикла, включение завершённых зависимостей в добавку, обе
  альтернативы `test_ac13_no_suffix_without_field_or_all_done`, вторая
  альтернатива `test_ac9_justified_plan_value_replaces_db_value`, раздельные
  «скобка не режет»/«точка не режет»); альтернатива «склеивает продолжение на
  следующей строке» переписана.
- Ни у одной мутации исход «убита / не убита» в «до», «после» и повторе не
  расходится; зерно ни в одном тесте не зафиксировано; тест без
  детерминированной мутации не удалён и назван находкой.

## Оценка объёма и деление

Сработавшие сигналы:
- `budget_usd` ≥ $30 — ставка $60 из ТЗ («Бюджет: $60»);
- число критериев приёмки ≥ 10 — их 16;
- прогноз диффа выше половины потолка гейта ёмкости. Прогноз диффа: 210 КиБ
  (оценка ТЗ, уточнение 7: дописка около 108 КБ плюс удаление 97,6 КБ;
  потолок — 256 КиБ).

Обоснование монолита (материал для решения Оператора на гейте SPEC).
Оператор уже разрезал волну 3м-2б: седьмой файл (`merge_gate`) отложен в
волну 3м-2в вместе со `spec_gate_declared`, чтобы дифф уложился в гейт
ёмкости; решение сессии при Операторе 25.10 — дописка шести файлов в модуль
остаётся одной задачей. Внутри задачи части связаны:
- Доказательство «до/после» ведётся одним набором патчей при неизменных
  `orchestrator/` и `scripts/` и одной таблицей «после» по одному файлу
  модуля; общие определения (`CROCKFORD`, `WAIT_PREFIX`, `ids_of`) живут в
  разделе первого по порядку прежнего файла, остальные разделы на них
  опираются.
- Мандат — один `answer` на шесть путей.
- Перенос без удаления исходных файлов оставляет полные дубли; удаление без
  переноса теряет покрытие.

Возможный разрез (например, `answer`/`guard`/`plan` отдельно от
`spec_gate`/`status_show`/`new_declares`) — решение Оператора; ТЗ ставит
шесть файлов одной волной с общим набором патчей.
