# PLAN: Деление переписывает merge_after зависящих задач

## Подход
Новая функция `orchestrator/merge_after.py::replace_divided(conn, parent_id,
successor_id)`: обходит `store.all_tasks`, у каждой задачи, в чьём
`merge_after` есть родитель, заменяет этот элемент на `successor_id` на той
же позиции (прочие элементы и порядок сохраняются) и пишет значение через
уже существующий `rewrite` — он же кладёт запись «merge_after изменён»
«было → стало» в журнал ЗАВИСЯЩЕЙ задачи (канал «деление на гейте SPEC»,
актор `operator` — деление идёт из approve Оператора).

`orchestrator/fsm.py::_spawn_division_subtasks` зовёт её сразу после
перевода родителя в `killed`, до уборки хвостов родителя, с последней
подзадачей `new_ids[-1]`. Сбой уборки (`_cleanup_divided_parent`) тем самым
не может оставить зависящие задачи на убитом родителе.

`check` перед записью не зовётся намеренно: он отказал бы значению, пока в
нём ещё стоит родитель в `killed`, а новое значение отличается от уже
принятого одним элементом — только что заведённой подзадачей, которая сама
ни от кого из зависящих не зависит (цикла не создаёт).

Канал записи не содержит id родителя: AC-2 (и долгоживущий тест
`test_ac2_…`) требует, чтобы правая часть «стало» его не называла;
родитель виден в левой части «было».

## Влияние на систему
- Затронут узел деления на гейте SPEC: теперь он, кроме родителя и
  подзадач, пишет колонку `merge_after` и журнал чужих (зависящих) задач.
  Гейт мержа (`merge_gate_refuses`) не ослаблен: убитая зависимость по-
  прежнему отказ; просто после деления в значении стоит живая подзадача, и
  отказ становится законным «ждёт мержа зависимостей», пока Sn не в done.
- Проверки значений `merge_after` (`check`, каналы PLAN/мандата) не
  тронуты; поле `merge_after` этого PLAN не задано — порядок мержа самой
  задачи не меняется.
- Откат — revert одного merge-коммита; данные: уже переписанные колонки
  остаются валидными значениями, их можно сменить мандатом Оператора.

## Риски
- Зависящая задача в `done`/`killed` тоже будет переписана (SPEC требует
  «каждой задачи, зависящей от родителя»); для закрытых задач колонка
  больше не исполняется — лишь лишняя запись журнала.

## Предложения системе
- `rewrite` вписывает канал в правую часть записи «было → стало» в
  скобках; если канал содержит id, он «попадает» в новое значение для
  разбора текстом (`split("→")`) — тест AC-2 поймал это на первом прогоне.
  Формат записи стоит сделать разбираемым однозначно (канал до стрелки).
