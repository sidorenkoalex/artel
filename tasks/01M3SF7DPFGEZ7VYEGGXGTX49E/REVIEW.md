## Замечания

- **major — orchestrator/ci.py:423-436, 519-536 (`_commit_touches_code` и снятие `skipped_here`).** Правило снимает проверку с обхода, только если коммит, где она пропущена, меняет код относительно первого родителя. Но check-runs есть только у голов push'ей: промежуточные коммиты мержа CI не гоняет, это сказано в самом PLAN.
  - Голова push'а гейта мержа — коммит «RETRO задачи», а его дифф с первым родителем — только `docs/retro/…`. Job `changes` классифицирует push по диапазону `before..after`, поэтому `python` на этой голове исполняется. А `protected-paths` и `id-format-greplint` (`if: github.event_name == 'pull_request'`, `.github/workflows/ci.yml:61, 249`) остаются пропущенными на документной голове.
  - Коммиты, которые меняют код (merge-коммиты задач), check-runs не имеют, и `skipped_here` на них пуст. В итоге PR-only проверки разрешаются только на редком прямом push'е Оператора с кодом.
  - На сегодняшнем origin/main такой push — `ae6dc9d8` (`canary/guids.txt`), на глубине ~138 коммитов первой линии. Значит, сейчас каждый вызов — ~140 запросов `gh`. В `_await_main_ci` эти запросы повторяются на каждом опросе раз в 90 с.
  - Через несколько мержей (~8 коммитов первой линии на мерж) линия превысит `MAIN_LINE_MAX_COMMITS = 200`. После этого `main_line_status` всегда возвращает `unknown`: `pin-update` отказывает «CI не подтверждён» на любом зелёном коммите (AC-2), `doctor` навсегда `warn` (AC-3), а ожидание после мержа заканчивается «не дождался» на первом опросе (AC-4).
  - Воспроизведено (см. «Проверено исполнением»): на `FakeLine` с топологией гейта (голова RETRO с `python=success` и `protected-paths=skipped`, под ней снимок и merge-коммит с кодом без проверок) исход — `unknown | проверки protected-paths не исполнялись на 200 коммитах линии`, опрошено 200 коммитов.
  - Тест `tests/test_main_ci_line.py::MainLineStatusTest::test_check_skipped_on_code_commit_stops_the_walk` зелёный только потому, что даёт проверки коммиту с кодом. На main такой топологии нет. Посылка «Рисков» PLAN («~25–30 вызовов», «до первого коммита с кодом») неверна по той же причине.
  - **Предложение:** класс push'а для коммита с проверками считать по диапазону от предыдущего коммита линии, у которого есть check-runs (это аналог `before..after` job'а `changes`), а не по первому родителю. Другой вариант: признак «push класса код» — на этом коммите исполнилась проверка, которую документный push пропускает. Нужен тест на топологию гейта: голова — документ, код только в промежуточном коммите без проверок, обход останавливается на первой голове и не уходит к потолку.
- **minor — orchestrator/fsm.py (`_approve_merge_gate`), orchestrator/fsm_merge_gate.py (`_cmd_approve_merge_gate_cycle`).** `**({"fixes_main": fixes_main} if fixes_main else {})` в двух местах передаёт параметр условно, чтобы подмены тела в старых тестах не упали на новой сигнатуре. Устройство кода подогнано под сигнатуру тестовых подмен; читатель не видит, что параметр передаётся всегда. Предложение: передавать именованный аргумент явно, а подмены, которые на этом падают, адаптировать (`**kwargs` в подменах). Это не блокирует.
