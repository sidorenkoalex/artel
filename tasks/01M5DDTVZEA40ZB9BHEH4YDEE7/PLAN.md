# PLAN: G3а-2а — гейт исходов на гейте мержа, пакет ревьювера, двусторонний прогон по имени ошибки

## Подход
Одна механика — строка доказательства в записи `PASSED_ACTION`
(`orchestrator/advance_gates/outcome_integrity.py`):

- Ядро гейта исходов параметризуется базой: `_checkouts` получает sha базы
  параметром (на `in_dev` — `gitcmd.diff_base`, как прежде; на мерже —
  `git merge-base <голова> <sha main>`, где sha main — повторный фетч
  `fsm_merge_gate._origin_main_sha(ctx)` после «fresh»).
- Сразу после выписок — ключ компонента
  `acceptance._report_suite_result_key(<голова>^{tree}, profile, False,
  root=<выписка головы>)`; `None` — `_Prepare` (сбой подготовки), до
  прогонов и до поиска доказательства.
- Запись `PASSED_ACTION`: строка чисел, затем строка
  `голова <sha40>; база <sha40>; ключ <ключ>; мандат <отпечаток>`, дальше
  прежние строки. Отпечаток — sha256 отсортированных уникальных элементов
  мандата, покрывших находки (`\n`, utf-8), иначе «нет». Для этого
  `covering`/`_covering` получают парный помощник, возвращающий и элемент
  мандата (публичные `covering`/`_covering` — прежние сигнатуры и исходы).
- На мерже: поиск записи `PASSED_ACTION` с той же головой, базой, ключом и
  отпечатком ТЕКУЩЕГО мандата над покрытыми находками той записи (id
  находок разбираются из её строк «… — покрыто мандатом ANSWER-n»). Есть —
  запись «гейт исходов: доказан для головы <sha7> и базы <sha7>», без
  прогона. Нет — прогон тем же `_judge`; пройден — та же запись
  `PASSED_ACTION` (второй вход тела гейта за тот же `approve` её
  переиспользует).
- Исходы на мерже (`outcome_integrity.merge_gate_escalates`): находка без
  мандата — запись «merge отклонён: гейт неослабления по исходам» с
  находками и `escalated`; сбой подготовки — запись
  «merge отклонён: гейт неослабления по исходам — подготовка» и
  `sys.exit` с «повтори artel.py approve <id>», задача на `merge_gate`,
  push нет.
- `fsm_merge_gate._outcome_integrity_merge_gate` — новый шаг тела окна
  между «fresh» и `_acceptance_locks_refuse`; цель и признак канарейки —
  из БД (`store.task_target`, `store.get_task`). Граница по цели
  проверяется до чтения строки задачи: вне границы шаг не трогает БД сверх
  `task_target`, без фетча, без записей (иначе краснел
  `tests/test_full_suite_reuse.py::MergeGateFreshSuiteTest` с
  `conn=object()` — пойман прогоном suite-run №1, исправлено).
- Пакет ревьювера (`review._changed_assertions_part`): для профиля в
  границе (не канарейка) раздел есть всегда, к строкам гейта по тексту
  добавлены строки гейта исходов для текущей головы (`outcome_integrity.
  review_lines`) либо «гейт исходов для головы <sha7> не исполнялся». Вне
  границы — прежний код ветки без изменений.
- Двусторонний прогон (`two_sided._run_side_report`): для профиля в
  границе `failed`/`error` и `passed` с повтором классифицируются
  `tests_writing._check_failure_kind` (отложенный импорт); пусто — провал
  проверки, иначе запись несёт вид, и `_verdict` возвращает «упал не на
  проверке: <вид>». Вне границы — прежнее правило.
- `REFUSAL_CLASSES` — ключ «merge отклонён: гейт неослабления по исходам»
  → «чинит Оператор».

## Влияние на систему
- Гейт исходов на `in_dev` сохраняет прежние отказы и числа; добавлен
  новый отказ подготовки (ключ `None`) — ужесточение, не ослабление.
- Гейт мержа для профиля в границе получает до двух полных наборов плюс
  перепрогоны под замком очереди мержа (принятая цена SPEC); вне границы
  шаг возвращается до фетча и записей — прежний маршрут побайтно.
- FAIL_TO_PASS не меняется: `_check_failure_kind` только импортируется.
- Откат — revert merge-коммита задачи; формат записи обратно совместим
  (старые записи — просто не доказательство).
