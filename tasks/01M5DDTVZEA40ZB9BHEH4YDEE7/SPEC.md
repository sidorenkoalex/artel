# SPEC: G3а-2а — гейт исходов на гейте мержа, пакет ревьювера, двусторонний прогон по имени ошибки

## Контекст
Третья часть G3а волны G по ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`,
«Решение» п. 6): гейт неослабления по исходам должен стоять не только на
выходе из `in_dev` (сделан G3а-1а, fe751fae; мандат по идентификатору —
G3а-1б, уже в main), но и на гейте мержа; двусторонний прогон по отчёту
должен считать «упал на проверке» по имени ошибки из отчёта, а не по
любому `failed`. Сейчас запись пройденного гейта
(`orchestrator/advance_gates/outcome_integrity.py:51`, `PASSED_ACTION`)
не несёт sha головы и базы и не годится доказательством; маршрут мержа
(`orchestrator/fsm_merge_gate.py:1480–1487`) гейта исходов не исполняет;
пакет ревьювера (`orchestrator/review.py:609`, `_changed_assertions_part`)
у компонента без Python раздела о тестах не показывает; двусторонний
прогон (`orchestrator/advance_gates/two_sided.py:336/365`) считает
проверкой любой `outcome == FAILED` и принимает `passed` с повтором.

**Граница задачи:** новое поведение — только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`)
истинно; у артели, у записи `test_profile` и у записи из нескольких
компонентов — гейт мержа, двусторонний прогон и пакет ревьювера прежние
побайтно.

## Требования

1. **Запись пройденного гейта.** Запись журнала `PASSED_ACTION` после
   строки чисел дополняется строкой
   `голова <sha40>; база <sha40>; ключ <ключ компонента>; мандат <отпечаток>`,
   где ключ компонента — `_report_suite_result_key`
   (`orchestrator/acceptance.py:3170`) по дереву головы, отпечаток — sha256
   отсортированных элементов мандата, покрывших находки, либо «нет», если
   таких элементов нет. Прежние записи без этой строки доказательством не
   являются.
2. **Гейт исходов на маршруте мержа.** Для профиля в границе гейт исходов
   исполняется в окне мержа после того, как `_sync_main_or_wait` вернула
   «свежий main» (`orchestrator/fsm_merge_gate.py:1484`), и до
   `_acceptance_locks_refuse` (`orchestrator/fsm_merge_gate.py:1487`).
   Базой служит sha main, против которого шла сверка свежести
   (`_origin_main_sha`, `orchestrator/fsm_merge_gate.py:150`), а не
   повторный `diff_base`: `_checkouts` получает базу параметром; вызов на
   выходе из `in_dev` — прежний. Цель задачи и признак канарейки на мерже
   берутся из БД (`store.task_target`, строка задачи).
3. **Доказательство без прогона.** Если в журнале задачи есть запись
   `PASSED_ACTION` с той же головой, той же базой, тем же ключом
   компонента и тем же отпечатком мандата (текущего набора элементов
   мандата, покрывающего находки той записи), гейт на мерже не прогоняет
   наборы и пишет запись журнала
   «гейт исходов: доказан для головы <sha7> и базы <sha7>». Иначе — прогон.
4. **Исходы на мерже.** Находка без мандата, включая «сломан правкой», —
   задача уходит в `escalated` с текстом находок, действие журнала
   «merge отклонён: гейт неослабления по исходам», класс этого действия
   в `REFUSAL_CLASSES` (`orchestrator/advance_gates/refusal_classes.py:92`)
   — «чинит Оператор». Сбой подготовки (выписка, «не начат», таймаут,
   прочее исключение) — отказ без push: задача остаётся на `merge_gate`
   с подсказкой «повтори artel.py approve»; пропуска гейта нет.
   `_full_suite_or_refuse` (`orchestrator/fsm_merge_gate.py:1046`) по
   дереву с применёнными приложениями PLAN — прежний (двойной прогон при
   приложениях — принятая цена). Гейт на мерже идёт под замком очереди
   мержа (до двух полных наборов плюс перепрогоны — ожидаемая задержка
   очереди).
5. **Пакет ревьювера.** Для профиля в границе раздел «Изменённые
   утверждения тестов» (`orchestrator/review.py:72`) есть всегда и
   дополняется строками гейта исходов для текущей головы — по записи
   `PASSED_ACTION` с этой головой: числа тестов базы и ветки, находки,
   покрытые мандатом (идентификатор и ANSWER), «нестабилен и на базе»,
   перепрогоны. Записи с этой головой нет — строка
   «гейт исходов для головы <sha7> не исполнялся». Вне границы — прежнее
   условие появления раздела и прежний текст побайтно.
6. **Двусторонний прогон по имени ошибки.** В `_run_side_report`
   (`orchestrator/advance_gates/two_sided.py:336`) для профиля в границе
   «упал на проверке» — только запись, для которой классификатор провала
   проверки `_check_failure_kind`
   (`orchestrator/advance_gates/tests_writing.py:750`) даёт пусто;
   `failed` с другим именем ошибки, `error`, таймаут — «упал не на
   проверке» с видом; `passed` с повтором на любой стороне — не
   доказательство (сбой стороны с видом «повтор»). Классификатор
   `two_sided.py` берёт из `tests_writing.py` отложенным импортом, без
   переноса; поведение гейта FAIL_TO_PASS не меняется. Вне границы —
   прежнее побайтно.
7. **Правило G3а-1а (утверждено Оператором 20.10):** запись `passed` с
   повтором на перепрогоне базы — красная база, «нестабилен и на базе»,
   находки нет.
8. **Тесты** детерминированы, без сети и без Node: учебный проект с
   компонентом `junit-xml` на подменённом раннере, сторона — по метке
   выписки. `tests/test_component_report_gates.py` — единственная правка:
   подмена нового шага в списке подмен помощника `merge`
   (`tests/test_component_report_gates.py:416`), без изменения
   утверждений; прочие существующие тесты (в том числе тесты планки
   G3а-1а, сверяющие числа записи `PASSED_ACTION` подмножеством) — без
   правок.

## Критерии приёмки

AC-1. Запись журнала `PASSED_ACTION`, сделанная гейтом исходов, после строки чисел несёт строку `голова <sha40>; база <sha40>; ключ <ключ компонента>; мандат <отпечаток>`: ключ — `_report_suite_result_key` по дереву головы, отпечаток — sha256 отсортированных элементов мандата, покрывших находки, либо «нет» при их отсутствии.

AC-2. На гейте мержа профиля в границе находка без мандата (в том числе «сломан правкой») переводит задачу в `escalated` с текстом находок, пишет действие журнала «merge отклонён: гейт неослабления по исходам»; в `REFUSAL_CLASSES` это действие имеет класс «чинит Оператор».

AC-3. Сбой подготовки гейта исходов на мерже (выписка, «не начат», таймаут, прочее исключение) оставляет задачу на `merge_gate`, push не выполняется, в отказе — подсказка «повтори artel.py approve»; гейт не пропускается.

AC-4. При наличии записи `PASSED_ACTION` с той же головой, той же базой, тем же ключом компонента и тем же отпечатком текущего мандата гейт на мерже не запускает прогон и пишет запись журнала «гейт исходов: доказан для головы <sha7> и базы <sha7>».

AC-5. Запись `PASSED_ACTION`, отличающаяся от текущей четвёрки базой, ключом компонента или отпечатком мандата (мандат отозван), доказательством не служит — гейт на мерже запускает прогон.

AC-6. Прежняя запись `PASSED_ACTION` без строки `голова …; база …` доказательством не служит — гейт на мерже запускает прогон.

AC-7. Базой гейта исходов на мерже служит sha main, против которого шла сверка свежести (`_origin_main_sha`), а не повторный `diff_base`; гейт исполняется после того, как `_sync_main_or_wait` вернула «свежий main», и до `_acceptance_locks_refuse`; цель задачи и признак канарейки берутся из БД. Вызов гейта на выходе из `in_dev` работает с базой `diff_base`, как прежде.

AC-8. Пакет ревьювера профиля в границе при наличии записи `PASSED_ACTION` с текущей головой содержит в разделе «Изменённые утверждения тестов» строки гейта исходов: числа тестов базы и ветки, находки, покрытые мандатом (идентификатор и ANSWER), «нестабилен и на базе», перепрогоны.

AC-9. Пакет ревьювера профиля в границе без записи `PASSED_ACTION` с текущей головой содержит строку «гейт исходов для головы <sha7> не исполнялся».

AC-10. У компонента без Python (профиль в границе, строк гейта по тексту нет) раздел «Изменённые утверждения тестов» в пакете ревьювера присутствует.

AC-11. Двусторонний прогон по отчёту для профиля в границе: запись `failed` с именем ошибки вне списка компонента, запись `error` и таймаут — «упал не на проверке» с видом, не «упал на проверке»; «упал на проверке» — только запись, для которой `_check_failure_kind` даёт пусто.

AC-12. Двусторонний прогон по отчёту для профиля в границе: `passed` с повтором на любой стороне — сбой стороны с видом «повтор», не доказательство.

AC-13. Запись `passed` с повтором на перепрогоне базы гейта исходов — красная база: «нестабилен и на базе», находки нет.

AC-14. Для профиля вне границы (артель, запись `test_profile`, запись из нескольких компонентов) гейт мержа, двусторонний прогон и пакет ревьювера дают прежний результат побайтно: гейт исходов на мерже не исполняется, раздел пакета появляется по прежнему условию с прежним текстом, двусторонний прогон классифицирует стороны прежним правилом.

AC-15. Поведение гейта FAIL_TO_PASS (`_check_failure_kind` и его вызывающий) не меняется; в `tests/test_component_report_gates.py` единственная правка — подмена нового шага в списке подмен помощника `merge`, утверждения файла не меняются.

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (пять модулей
`orchestrator/` плюс `tests/`); число критериев приёмки ≥ 10 (15).

Материал для решения Оператора — **обоснование монолита**:
- Требования 1–5 и 7 — одна механика: строка sha в `PASSED_ACTION`
  (требование 1) — носитель доказательства для гейта на мерже
  (требование 3) и источник строк пакета ревьювера (требование 5).
  Гейт на мерже без строки sha либо прогоняет наборы всегда, либо
  принимает старые записи (последнее ТЗ запрещает); пакет ревьювера без
  неё не может отличить запись текущей головы. Разрезать по этим зонам —
  значит мержить носитель без читателя или читателя без носителя.
- Требование 6 (`two_sided.py`) от этой механики не зависит и
  технически отделимо в самостоятельную подзадачу (зоны
  `orchestrator/advance_gates/two_sided.py, tests/`). Отдельная задача
  добавит собственный проход конвейера (минимум ~$25) при объёме правки
  в одну функцию; ТЗ задаёт работу одной задачей с бюджетом $45–55, и
  деление G3а-2 на 2а/2б уже выполнено Оператором. Решение — за
  Оператором на гейте SPEC.
