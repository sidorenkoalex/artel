## Пути обхода гейтов
- О-1. Ключ компонента `None`. `_report_suite_result_key` возвращает
  `None` при сбое чтения (`acceptance.py:3176-3196`; при `base=False` без
  `root` — всегда). SPEC не говорит, что ключ `None` — сбой подготовки:
  запись «ключ None» на `in_dev` и «ключ None» на мерже совпадут, и
  доказательство пройдёт без настоящего ключа. Также не задано, ключ
  считается как для коммита (`base=True`) или для рабочей копии
  (`base=False`, с файлами блокировки) — при разных режимах у писателя и
  читателя доказательство не сработает никогда (не обход, но слепое
  место AC-4).
- О-2. Приложения PLAN. Гейт исходов на мерже сравнивает голову кодовой
  ветки без приложений; приложение, затрагивающее файлы тестов
  компонента (защищённый путь проекта), попадает в мерж мимо сравнения
  исходов — `_full_suite_or_refuse` (`fsm_merge_gate.py:1046`) лишь
  требует зелёного набора, исчезнувший или ставший пропуском тест он не
  видит. ТЗ «прежний» `_full_suite_or_refuse` принимает, но этот путь
  SPEC не назван и в «Не входит» не вынесен.
- О-3. Сдвиг main между сверкой и гейтом (следствие Ф-1). При повторном
  фетче база может оказаться новее main, против которого ветка признана
  свежей: тесты, добавленные в main после сверки, на голове
  отсутствуют → ложная находка «исчез» → ложная `escalated`. Это не
  ослабление, но ложный отказ с классом «чинит Оператор».
- О-4. Канарейка в пакете ревьювера. Треб. 5: для профиля в границе
  раздел «есть всегда»; `_changed_assertions_part` для канареечной задачи
  возвращает `None` (`review.py:635-637`, AC-11 прежней SPEC). Буквально
  исполнитель может либо сломать прежнее правило канарейки, либо оставить
  его — SPEC не говорит, какое правило старше.
