# GitLab, шаг В2: профиль проверок проекта `verify` — ручные проверки `human:<имя>`, команды `verify-ok` и `verify-fail`

## Факты

ADR-0029 (принят 26.10.2026), п. 10; ADR-0003 п. 10; инварианты 3 и 18 (`docs/invariants.md`). Влиты: В1.1, В1.2, перенос гейта по исходам на `verifying`. Аналитик сверяет строки по коду после их мержа.

1. Этап `verifying` — `fsm_advance.verifying` (`orchestrator/fsm_advance.py:441`): зелёный CI головы (и гейт по исходам для `ci` после переноса) → `review`; иначе ожидание до `config.VERIFYING_CEILING_SEC`, затем эскалация. Других проверок этапа нет; поля `verify` в записи проекта нет (`targets.py`).
2. Кто держит задачу — `board.waiting_on` (`orchestrator/board.py:25`): `OPERATOR_STATES` → `operator`, `CI_STATES` → `ci`; `verifying` — в `CI_STATES`.
3. Команды Оператора, которые `auto` не вызывает (инвариант 18), — `test_auto_cycle.AutoNeverPassesAGateTest` и обход команд в `tests/test_invariants.py`.
4. Числовой лимит циклов (инвариант 3) — счётчики возвратов не обнуляются эскалацией (`test_invariants.CountersNeverResetTest`).

## Требуется

1. **Поле записи `verify`** (в `description` проекта; по умолчанию пусто — поведение прежнее): список проверок этапа `verifying` из каталога типов. Тип `ci` — существующее ядро, в профиле не объявляется (объявление — отказ загрузки). Тип `human:<имя>` (имя — `[a-z0-9-]+`, уникально в списке) — исполняется. Типы `agent:<имя>` и `script:<имя>` есть в каталоге, но не исполняются: объявление — отказ загрузки «тип не реализован (пункт C4)». Неизвестный тип, повтор имени, не список — отказ загрузки с именем поля.
2. **Ожидание ручной проверки**: после зелёного CI головы (и гейта по исходам, если он на `verifying`) задача с непустым `verify` не уходит в `review`, пока по текущей голове нет отметки `verify-ok` для каждой проверки `human:*`. Запись журнала и `status`: «ждёт проверки <имя> по sha <sha>»; `waiting_on` — `operator`; `watch` уведомляет при входе в ожидание. Потолок `VERIFYING_CEILING_SEC` к ожиданию отметки не применяется (ожидание человека, не CI); алерт — по общему правилу долгого ожидания Оператора.
3. **`verify-ok <id> <имя> <sha> "<итог>"`** — команда Оператора: задача в `verifying`, имя — из профиля, sha — текущая голова ветки (иначе отказ «отметка для другой головы»), итог непустой. Пишет отметку в БД и журнал; при всех отметках — переход в `review` тем же путём, что сейчас. Отметка действительна только для этой головы: новая голова (возврат в `in_dev`, подтяжка) — проверка заново.
4. **`verify-fail <id> <имя> "<причина>"`** — команда Оператора: возврат в `in_dev` с причиной в журнале и в передаче разработчику; возврат считается в цикле с пределом (инвариант 3): после предела — эскалация. Предел — тем же механизмом и значением, что у возвратов ревью; счётчик не обнуляется эскалацией.
5. **`auto` и надзор эпика** не вызывают `verify-ok` и `verify-fail` никогда (инвариант 18).
6. Пульт стенд не разворачивает и заданий конвейера не запускает: `verify` только ждёт отметки.
7. **Инварианты** (приложением PLAN к `tests/test_invariants.py`): `verify-ok`, `verify-fail` в обходе команд; строка 18 — команды Оператора.

Критерии приёмки (песочницы — вымышленные проекты):
- проверка записи: `verify: [ci]`, `agent:x`, `script:x`, неизвестный тип, повтор имени, не список — отказ загрузки с именем поля; `human:stand` — загружается; без поля — поведение прежнее;
- `verify: [human:stand]`, CI зелёный → задача в `verifying`, журнал «ждёт проверки stand по sha …», доска — `waiting_on: operator`, `review` не наступает при подменённом истечении `VERIFYING_CEILING_SEC`;
- `verify-ok` с текущим sha → `review`; со старым sha — отказ, состояние прежнее; для задачи не в `verifying` или неизвестного имени — отказ;
- две проверки `human:a`, `human:b`: после одной отметки — ожидание второй; после обеих — `review`;
- новая голова после `verify-ok` (возврат в `in_dev` и снова `verifying`) — отметка не действует, ожидание заново;
- `verify-fail` → `in_dev`, причина в журнале и в передаче разработчику; после предела возвратов — `escalated`; эскалация счётчик не обнуляет;
- шпион команд: `auto` и надзор эпика не вызывают `verify-ok`/`verify-fail` ни в одном сценарии;
- артель и проекты без `verify`: существующие тесты `verifying`, доски и `auto` зелёные без правки.
