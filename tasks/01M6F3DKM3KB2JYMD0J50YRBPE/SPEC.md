# SPEC: GitLab В2 — профиль проверок `verify`: ручные проверки `human:<имя>`, команды `verify-ok` и `verify-fail`

## Контекст
ADR-0029 п. 10 (ADR-0003 п. 10; инварианты 3 и 18 `docs/invariants.md`).
Сейчас этап `verifying` (`orchestrator/fsm_advance.py:442`, `fsm_advance.verifying`)
знает только зелёный CI головы и гейт по исходам (`verifying_gate`, влит
01M6BMG29KZV1RX21HFAXZG3CM): по их проходу задача уходит в `review`, иначе
ждёт до `config.VERIFYING_CEILING_SEC` и эскалирует. Других проверок этапа
нет, поля `verify` в записи проекта нет (`orchestrator/targets.py`).
`board.waiting_on` (`orchestrator/board.py:27`) относит `verifying` к
`CI_STATES` → `ci`. Задача добавляет проекту профиль проверок этапа
`verifying` с исполняемым типом ручной проверки `human:<имя>` и две команды
Оператора, которыми человек отмечает итог проверки. Пульт стенд не
разворачивает и заданий конвейера не запускает — `verify` только ждёт
отметки. Итерация 2: требования 2–5 и критерии уточнены решениями Оператора
по первому аудиту SPEC (возврат из `spec_gate`, пункты 1–6). Итерация 3:
решения Оператора по второму аудиту (возврат из `spec_gate`, пункты 1–9):
удержание надзором при красном CI, проверка исхода в AC-19/AC-20, запись
«ждёт проверки» в пределах визита `verifying`, имя проверки, пустая причина,
причина при эскалации по пределу, место поля `verify`.

## Требования

1. **Поле записи проекта `verify`** — допустимо только в разделе
   `description` записи локального слоя (`targets.local.yaml`,
   `targets.merge_local`); по умолчанию отсутствует/пусто, и тогда поведение
   прежнее. Поле `verify` в плоской записи (вне раздела `description`) и в
   записи слоя репозитория (`targets.yaml`) — отказ загрузки с именем поля
   (`verify`). Значение — список проверок этапа `verifying` из каталога
   типов:
   - `ci` — существующее ядро; в профиле не объявляется: объявление `ci` —
     отказ загрузки записи;
   - `human:<имя>` — исполняется; имя по `[a-z0-9-]+`, уникально в списке;
     имя вне `[a-z0-9-]+` (в том числе пустое) — отказ загрузки;
   - `agent:<имя>`, `script:<имя>` — есть в каталоге, но не исполняются:
     объявление — отказ загрузки с текстом «тип не реализован (пункт C4)»;
   - неизвестный тип, повтор имени, значение не список — отказ загрузки.
   Каждый отказ загрузки по полю называет имя поля (`verify`).
2. **Ожидание ручной проверки.** После зелёного CI головы и прохода гейта
   по исходам на `verifying` задача, у проекта которой `verify` непуст, не
   уходит в `review`, пока по текущей голове ветки нет отметки `verify-ok`
   для каждой проверки `human:*` профиля. На время ожидания:
   - при входе в ожидание в текущем визите `verifying` (после последней
     записи входа задачи в `verifying`) по текущей голове, для которых его
     ещё не было, `verifying` пишет запись журнала «ждёт проверки <имя> по
     sha <sha>» (имя — первой неотмеченной проверки, sha — текущая голова) и
     ставит ту же строку `status`; запись пишется только после зелёного CI
     этой головы и прохода гейта по исходам в этом визите;
   - запись журнала и уведомление `watch` о входе в ожидание — по одному
     разу на визит `verifying` и голову: повторные опросы `verifying` в том
     же визите по той же голове их не повторяют; новая голова (новый sha)
     или новый визит `verifying` (в том числе с той же головой — после
     `verify-fail`, `reject` или иного возврата) — новый вход в ожидание,
     требующий нового зелёного CI, прохода гейта по исходам и новой записи;
   - строка `status` после отметки одной из нескольких проверок называет
     следующую неотмеченную проверку той же головы;
   - `board.waiting_on` задачи — `operator`;
   - `watch` уведомляет Оператора при входе задачи в ожидание;
   - потолок `config.VERIFYING_CEILING_SEC` к ожиданию отметки не
     применяется (ожидание человека, не CI): истечение потолка во время
     ожидания отметки не эскалирует и не переводит задачу в `review`;
   - алерт на ожидание отметки не заводится: уведомления `watch` при входе в
     ожидание достаточно.
3. **Команда Оператора `verify-ok <id> <имя> <sha> "<итог>"`.** Предусловия
   (каждое нарушение — отказ, состояние и отметки прежние): задача в
   `verifying`; `<имя>` — проверка `human:<имя>` профиля проекта задачи;
   `<sha>` — текущая голова ветки задачи (иначе отказ с текстом «отметка
   для другой головы»); в журнале после последней записи входа задачи в
   `verifying` есть запись «ждёт проверки … по sha <sha>», написанная
   `verifying` при входе в ожидание по текущей голове (требование 2; одна
   на визит и голову, имя в ней — первой неотмеченной проверки, отметка
   любой проверки профиля по этой голове опирается на неё; запись прошлого
   визита `verifying` основанием не служит), —
   иначе отказ с текстом «проверка не ожидается для этой головы» (в том
   числе до зелёного CI головы и до прохода гейта по исходам в текущем
   визите); `<итог>` непустой. Команда пишет отметку (задача, имя, sha, итог) в БД и запись
   в журнал; когда по текущей голове отмечены все проверки `human:*`
   профиля, задача переходит в `review` тем же путём, что сейчас переход
   `verifying -> review`. Отметка действительна только для своей головы:
   после новой головы (возврат в `in_dev`, подтяжка main) проверка
   требуется заново.
4. **Команда Оператора `verify-fail <id> <имя> "<причина>"`.** Предусловия
   — задача в `verifying`, имя из профиля, непустая причина (пустая —
   отказ); нарушение — отказ, состояние прежнее. Команда возвращает задачу в
   `in_dev`; причина — в журнале и в передаче разработчику (раздел «Причина
   возврата» брифа следующего шага developer). Возврат считается в цикле с пределом
   (инвариант 3): число возвратов `verify-fail` задачи хранится отдельным
   полем задачи (БД, `orchestrator/schema.py`/`orchestrator/store.py`);
   предел — то же значение, что у возвратов ревью
   (`config.LIMIT_REVIEW_ITERS`), и тот же механизм, что
   `fsm_advance._review_changes_requested`: возврат, доводящий счётчик до
   предела, переводит задачу в `escalated` вместо `in_dev`; причина этого
   (последнего) `verify-fail` — в тексте записи перехода в `escalated` и
   через него — в разделе «Причина возврата» брифа developer после возврата
   из эскалации (`orchestrator/brief.py:1560-1568` берёт текст записи
   `state -> escalated`). Счётчик эскалацией (и возвратом из неё) не
   обнуляется. `review_iters` `verify-fail` не меняет.
5. **`auto` и надзор эпика.**
   - `auto` и надзор эпика (`auto --epic`) не вызывают `verify-ok` и
     `verify-fail` никогда (инвариант 18).
   - Задача в ожидании отметки (требование 2): `auto <id>` останавливается
     без алерта, как на гейте Оператора, и снимает lease задачи;
     надзор эпика считает такую задачу ждущей Оператора (как задачу на
     гейте) и не перезапускает её `auto`.
   - После `verify-ok`, переведшего задачу в `review`, и после
     `verify-fail` надзор эпика подхватывает задачу штатно.
   - Остановка `auto` на красном CI в `verifying` и удержание такой задачи
     надзором эпика до действия Оператора — как сейчас
     (`orchestrator/auto.py:528-532`, `:1170`, `:1251-1256`): признак
     «не удерживает место» (`_NOT_HOLDING_STOP_STATES` или его замена)
     распространяется только на ожидание отметки, не на состояние
     `verifying` целиком.
   - Правка `orchestrator/auto.py` — только для этого (признак остановки на
     ожидании отметки).
6. Пульт по `verify` стенд не разворачивает и заданий конвейера не
   запускает: этап только ждёт отметок.
7. **Инварианты** — приложением PLAN к защищённому
   `tests/test_invariants.py`: команды `verify-ok` и `verify-fail` входят в
   обход команд (`FsmTest.commands`, `tests/test_invariants.py:400`) как
   команды Оператора с годными аргументами: у песочницы обхода есть профиль
   `verify: [human:stand]`, и задача стоит в ожидании отметки по текущей
   голове. Вызов каждой из них в обходе срабатывает — код выхода 0 и
   эффект команды (`verify-ok` — отметка в БД и переход в `review`;
   `verify-fail` — переход в `in_dev`), а не только не падает. Существующие
   свойства обхода (ни одна команда, кроме решений Оператора, не проходит
   гейт; команды FSM не стартуют агента и т.п.) остаются зелёными с ними.
8. Команды зарегистрированы в CLI `orchestrator/artel.py` и описаны в его
   справке.

## Критерии приёмки
Песочницы — вымышленные проекты.

AC-1. Загрузка записи проекта отказывает с именем поля `verify` для каждого из значений в разделе `description` локального слоя: `verify: [ci]`; `verify: [agent:x]` и `verify: [script:x]` (текст отказа содержит «тип не реализован (пункт C4)»); неизвестный тип; повтор имени (`[human:a, human:a]`); значение не список; имя вне `[a-z0-9-]+` — `human:Stand`, `human:` (пустое имя), `human:a b`.
AC-2. Поле `verify: [human:stand]` в плоской записи локального слоя (вне раздела `description`) и в записи слоя репозитория (`targets.yaml`) — отказ загрузки, текст отказа называет поле `verify`.
AC-3. Запись локального слоя с `verify: [human:stand]` в разделе `description` загружается; запись без поля `verify` загружается, и задача её проекта проходит `verifying -> review` по зелёному CI так же, как до задачи.
AC-4. Проект с `verify: [human:stand]`, CI головы зелёный, гейт по исходам пройден: после `advance` задача остаётся в `verifying`, журнал несёт запись «ждёт проверки stand по sha <голова>», строка `status` — та же, `waiting_on` доски — `operator`.
AC-5. В сценарии AC-4 повторные `advance` в том же визите `verifying` по той же голове не добавляют вторую запись «ждёт проверки stand по sha <голова>» и не дают повторного уведомления `watch`.
AC-6. В сценарии AC-4 при подменённом истечении `VERIFYING_CEILING_SEC` очередной `advance` не переводит задачу ни в `review`, ни в `escalated`.
AC-7. `watch` выдаёт уведомление при входе задачи в ожидание проверки из AC-4.
AC-8. `verify-ok <id> stand <текущий sha> "<итог>"` в сценарии AC-4 переводит задачу в `review`; отметка лежит в БД, запись — в журнале.
AC-9. Проект с `verify: [human:stand]`, задача в `verifying` с текущим sha головы: при CI головы в ожидании или красном, а также при CI зелёном и не пройденном гейте по исходам `verify-ok <id> stand <текущий sha> "<итог>"` отказывает с текстом «проверка не ожидается для этой головы»; состояние задачи прежнее (`verifying`), отметки в БД нет.
AC-10. `verify-ok` со старым sha отказывает с текстом «отметка для другой головы», состояние задачи прежнее (`verifying`); `verify-ok` для задачи не в `verifying` и для имени, которого нет в профиле, — отказ, состояние прежнее; пустой итог — отказ.
AC-11. Проект с `verify: [human:a, human:b]`: после `verify-ok` по `a` задача в `verifying`, строка `status` — «ждёт проверки b по sha <голова>»; после `verify-ok` по `b` — `review`.
AC-12. После `verify-ok` по голове X задача возвращена в `in_dev`, получила новую голову Y и снова в `verifying` с зелёным CI: отметка по X не действует, журнал — «ждёт проверки stand по sha Y», `review` не наступает до новой отметки по Y.
AC-13. Повторный вход с той же головой: в сценарии AC-4 (запись «ждёт проверки stand по sha X» есть) `verify-fail` возвращает задачу в `in_dev`, и она снова входит в `verifying` без новых коммитов (голова X). Пока CI головы в этом визите не зелёный или гейт по исходам не пройден, `verify-ok <id> stand X "<итог>"` отказывает с текстом «проверка не ожидается для этой головы», отметки в БД нет, состояние `verifying`; после зелёного CI и прохода гейта `advance` пишет новую запись «ждёт проверки stand по sha X» после записи входа в этот визит и даёт новое уведомление `watch`, и только после этого `verify-ok` по X переводит задачу в `review`.
AC-14. `verify-fail <id> stand "<причина>"` из `verifying` переводит задачу в `in_dev`; причина — в журнале и в разделе «Причина возврата» брифа developer; `review_iters` задачи не изменился; для задачи не в `verifying`, неизвестного имени или с пустой причиной — отказ, состояние прежнее (`verifying` в последнем случае).
AC-15. Возврат `verify-fail`, доводящий счётчик возвратов `verify-fail` (отдельное поле задачи) до `config.LIMIT_REVIEW_ITERS`, переводит задачу в `escalated`; текст записи перехода в `escalated` содержит причину этого `verify-fail`, и после возврата из эскалации в `in_dev` раздел «Причина возврата» брифа developer её содержит; после эскалации и возврата из неё счётчик не уменьшился, и следующий `verify-fail` снова эскалирует.
AC-16. `auto <id>` на задаче в ожидании отметки (сценарий AC-4) останавливается: запись остановки в журнале, открытого алерта нет, lease задачи снят; надзор эпика с такой задачей не запускает ей дочерний `auto` и относит её к ждущим Оператора.
AC-17. Проект с `verify: [human:stand]` и проект без `verify`: задача эпика в `verifying` с красным CI головы — дочерний `auto` останавливается, и надзор эпика на следующих опросах удерживает её так же, как до задачи (не запускает ей дочерний `auto` повторно до действия Оператора).
AC-18. После `verify-ok`, переведшего задачу эпика в `review`, и после `verify-fail`, вернувшего её в `in_dev`, надзор эпика на следующем опросе запускает ей дочерний `auto`.
AC-19. Исход, не вызовы: после прогона `auto <id>` и надзора эпика на задаче в ожидании отметки (сценарий AC-4) и в остальных сценариях AC-16–AC-18 в БД не появилось отметок проверок, в журнале нет записей отметки `verify-ok`/возврата `verify-fail`, и задача не перешла из `verifying` ни в `review`, ни в `in_dev` иначе, чем командой Оператора.
AC-20. Приложение PLAN к `tests/test_invariants.py` вносит `verify-ok` и `verify-fail` в обход команд `FsmTest.commands` на песочнице, у записи которой `verify: [human:stand]`, а задача стоит в ожидании отметки по текущей голове; в обходе каждый из двух вызовов завершается с кодом выхода 0 и даёт эффект (`verify-ok` — отметка в БД и задача в `review`; `verify-fail` — задача в `in_dev`); обход с ними зелёный, и `git apply --check` приложения проходит на чистом дереве.

## Оценка объёма и деление
Сработавшие сигналы: файлов зоны ≥ 5 (11: десять модулей `orchestrator/` и
`tests/`); критериев приёмки ≥ 10 (20); `budget_usd` ≥ $30 (40 — рамка
Оператора из ТЗ; калибровка для 8+ файлов зоны и 15+ критериев даёт ~85,
рамка ниже неё);
зона задевает механизм записей `docs/invariants.md` (инварианты 3 и 18).

Материал для решения Оператора — **обоснование монолита**:
- Поле `verify` без ожидания и команд в отдельной части даёт
  неработоспособное промежуточное состояние: проект, объявивший
  `human:stand`, загружается, а задача уходит в `review` без проверки —
  объявленная проверка молча не исполняется (ослабление ADR-0029 п. 10).
  Альтернатива — первая часть отказывает и `human:*` — делает её поле
  бесполезным, и смысл мержа отдельно пропадает.
- Ожидание отметки без `verify-ok` держит задачу в `verifying` навсегда
  (потолок к нему не применяется по требованию 2) — нет выхода, кроме
  `kill`; `verify-ok` без ожидания не имеет предмета (требование 3 требует
  записи ожидания).
- Остановка `auto` на ожидании (требование 5) без самого ожидания не имеет
  предмета; ожидание без неё оставляет `auto` в бесконечном опросе с
  удержанием lease.
- `verify-fail` (возврат с пределом) отделим теоретически, но без него
  ожидание имеет только положительный исход, а отказ проверки — только
  `kill`; это неполное поведение этапа.
Разрез возможен по линии «`verify-ok`/ожидание» | «`verify-fail`», но обе
части делят одни и те же модули (`orchestrator/verify.py`, `store.py`,
`schema.py`, `artel.py`), и их зоны пересекались бы — разрез режет зону
поперёк.

## Не входит
- Строки `docs/invariants.md` (в том числе строка 18) — doc-commit Оператора после мержа.
- Исполнение типов `agent:*` и `script:*` (пункт C4) — только отказ загрузки.
- `mr-sync` (Б2.2); строки `doctor` (Б2.3).
- Развёртывание стенда и запуск заданий конвейера пультом (требование 6).
- Алерт на ожидание отметки (решение Оператора: уведомления `watch` достаточно).
- Правка `orchestrator/auto.py` сверх остановки на ожидании отметки и подхвата надзором эпика (требование 5).
- Правка `orchestrator/fsm.py`, `orchestrator/ci.py`, `orchestrator/advance_gates/outcome_integrity.py`, ADR-0029, ADR-0003 — только чтение.
- Правка `review_iters` и механизма возвратов ревью.
- Безлимитный `reject` Оператора из `verifying` (`orchestrator/fsm.py:1877-1889`) рядом с ограниченным `verify-fail` — вне задачи (решение Оператора: строка копилки Оператора).
- Правка `orchestrator/brief.py`: причина при эскалации по пределу доходит до брифа через текст записи `state -> escalated` (`brief.py:1560-1568`).
- Правка существующих тестов `tests/`: по ТЗ не ожидается; раздел «Меняемое поведение» отсутствует. Иное — эскалация.
- Зелёный полный набор `tests/` (в том числе существующие тесты `verifying`, доски и `auto` у артели и проектов без `verify` — ТЗ требует их зелёными без правки), зелёный CI ветки, неизменность защищённых путей и непревышение бюджета — её держит пульт.
