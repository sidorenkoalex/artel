# SPEC: Наблюдатель роста карты, часть 2 — блок report и оценка в деньгах

## Контекст
Часть 1 (родительская задача 01M1RFVWV6WWTXRC5F40K61632) добавляет ряд
записей журнала «карта: размер» на каждом мерже и относительный
самокалибрующийся порог `doctor.check_map_growth`, но не даёт Оператору
ни истории размера карты, ни денежного ориентира: сегодня алерт
`map.growth` при `ack` не сопровождается ничем, кроме текста триггера.
Эта задача — часть (б) того же деления (требования 4–5 и критерии
AC-16..AC-19 исходного SPEC родителя, перенесённые сюда дословно):
блок в `artel report` по каждому target с историей ряда и оценка
«стоимость карты за шаг developer» в долларах — только материал для
решения Оператора, без новых алертов и без влияния на FSM.

## Требования
1. Оценка «стоимость карты за шаг developer» (`orchestrator/report.py`):
   `tokens` = `bytes_projection` последней записи ряда «карта: размер»
   target, если поле есть, иначе `bytes_total`, делённое на 3 (без
   токенизатора); `calls` — медиана числа вызовов инструментов агента
   `developer` по логам его шагов за последние 10 задач глобально по
   всем target (курс роли один на все target, `config.TOKEN_RATES`);
   при нехватке данных — константа-ориентир из `config` с пометкой
   «оценка»; `cost_usd` = `tokens × calls × cache_read_usd_per_token`
   + `tokens × cache_creation_usd_per_token` роли `developer`.
2. Оценка не заводит алертов и не влияет ни на один переход или гейт:
   только число-ориентир для решения Оператора при `ack` алерта
   `map.growth`.
3. Блок в `artel report` по каждому target: таблица последних 12
   записей «карта: размер» (дата, `bytes_total`, `bytes_projection`
   при наличии, `sections_total`, `bytes_by_dir`), медиана окна
   калибровки, если уже посчитана, список открытых алертов
   `map.growth` этого target, оценка из требования 1.
4. Target без единой записи «карта: размер» — строка «измерений нет:
   карта ни разу не регенерировалась после мержа этой версией» вместо
   таблицы, без ошибки.
5. Тесты: блок на фикстурном ряде записей (константы `MAP_*` и
   ориентир вызовов — из `config`, не литералами); «измерений нет» на
   пустом ряде; оценка при наличии и отсутствии `bytes_projection`;
   независимость рядов двух target (инвариант 22); существующие
   `tests/test_report.py` зелёные без правки существующих ассертов.

## Критерии приёмки

AC-1. Оценка «стоимость карты за шаг developer» вычисляет `tokens`:
`bytes_projection` последней (самой свежей) записи ряда «карта:
размер» ЭТОГО target, если ключ `bytes_projection` присутствует в этой
записи, иначе `bytes_total` той же записи — результат делится на 3
(целочисленный литерал, не токенизатор).

AC-2. `calls` — медиана числа вызовов инструментов агента `developer`
по логам его шагов ЗА ПОСЛЕДНИЕ 10 ЗАДАЧ ГЛОБАЛЬНО (по всем target
разом, не только текущему): курс роли в `config.TOKEN_RATES` один на
все target, поэтому и выборка для медианы не делится по target.

AC-3. Логов шагов `developer` в выборке AC-2 нет вовсе (retention уже
вычистил файлы логов, либо ни одна из последних 10 задач ещё не дошла
до шага `developer`) — `calls` берётся из новой именованной константы-
ориентира в `orchestrator/config.py` (не литерала); значение оценки в
блоке `report`, вычисленное с этой константой, помечено словом
«оценка».

AC-4. `cost_usd` = `tokens × calls × cache_read_usd_per_token` роли
`developer` (`config.TOKEN_RATES["developer"]`) плюс `tokens ×
cache_creation_usd_per_token` той же записи `TOKEN_RATES["developer"]`.

AC-5. Оценка AC-1..AC-4 не вызывает `alerts.raise_alert`/
`raise_attention_alert`/любую другую функцию `alerts.py` и не читается
ни одним переходом `fsm.py`/`fsm_advance.py`/`fsm_autogate.py` —
единственный потребитель значения — вывод команды `artel report`.

AC-6. Блок `artel report` по КАЖДОМУ target, у которого есть хотя бы
одна запись «карта: размер», показывает таблицу последних 12 таких
записей (не больше; хронологически, самые свежие): дата, `bytes_total`,
`bytes_projection` — только для записей, где поле присутствует,
`sections_total`, `bytes_by_dir`.

AC-7. Тот же блок показывает медиану окна калибровки `map.growth` этого
target ТЕМ ЖЕ алгоритмом, что `doctor.check_map_growth` (часть 1,
01M1RFVWV6WWTXRC5F40K61632): окно — первые
`config.MAP_GROWTH_CALIBRATION_MERGES` записей ряда после точки
отсчёта (момент последнего подтверждённого, `ack_ts` не `NULL`, алерта
`map.growth` этого target, либо начало ряда, если такого алерта ещё не
было) — ТОЛЬКО когда это окно уже заполнено; окно ещё не заполнено —
медиана не показывается (без ошибки, без нуля вместо неё).

AC-8. Тот же блок показывает список открытых (`ack_ts IS NULL`)
алертов `source="map.growth"` этого target (`store.open_alerts`,
отфильтрованных по target и source).

AC-9. Тот же блок показывает оценку AC-1..AC-4, посчитанную для этого
target.

AC-10. Target БЕЗ единой записи «карта: размер»: его блок в `report`
вместо таблицы (AC-6) и оценки (AC-1..AC-4 — вычислить нечего, нет
`bytes_total`/`bytes_projection`) показывает строку «измерений нет:
карта ни разу не регенерировалась после мержа этой версией», без
ошибки (исключения, traceback) и без прежнего поведения `report` на
target без данных.

AC-11. Существующие `tests/test_report.py` остаются зелёными без
правки существующих ассертов — новые случаи (AC-1..AC-10) добавляются
отдельными тестами.

AC-12. Новые тесты используют фикстурный ряд записей «карта: размер»
(не реальный прогон `doctor`/мержа) и читают пороговые константы
`config.MAP_*` и константу-ориентир числа вызовов (AC-3) через модуль
`config`, не литералами (skills/test-authoring.md); независимость
таблицы, калибровки и оценки одного target от данных другого target
покрыта отдельным тестом (инвариант 22, `docs/invariants.md`).

## Оценка объёма и деление
Сигнал сработал: критериев приёмки 12 (порог `config.
SPLIT_SIGNAL_AC_COUNT` ≥ 10). Остальные сигналы не сработали: зона —
2 файла кода (`orchestrator/report.py`, `orchestrator/config.py`) +
`tests/`, порог файлов зоны ≥ 5 не достигнут; `budget_usd` = 15 при
пороге ≥ 30 (рамка Оператора в ТЗ — «$15», ниже дефолта); в ТЗ нет
«ориентировочно»/«весь оркестратор»/«по факту затронутых мест»;
прогноз диффа не заявлен.

Обоснование монолита: пункты 1 (денежная оценка) и 3 (блок отчёта)
неразделимы. У оценки нет отдельного потребителя и отдельной команды —
требование 2 прямо называет её «только число-ориентир» ВНУТРИ вывода
`report`; часть, реализующая только оценку без места отображения, не
мержима самостоятельно с пользой Оператору. Симметрично: блок отчёта
без денежной оценки не покрывал бы требование 1 буквально, а буквальное
покрытие требования 1 — то, ради чего эта задача (в отличие от части 1)
вообще заведена отдельно. Это уже вторая половина деления родительской
задачи 01M1RFVWV6WWTXRC5F40K61632 (её SPEC, раздел «Оценка объёма и
деление»: Оператор 05.09 принял нарезку на часть (а)/источник данных и
часть (б)/потребитель) — грань «источник / потребитель» уже проведена
на уровне родителя, и это единственная содержательная граница внутри
самого потребителя: дальше делить нечего, кроме как по границе «оценка
/ таблица», которая, как показано выше, не даёт двух самостоятельно
полезных частей. Рамка Оператора $15 (ниже дефолта и ниже порога
сигнала бюджета) — тоже сигнал того, что задача уже воспринимается
Оператором как малая, не подлежащая дальнейшему дроблению.
