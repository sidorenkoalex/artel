# SPEC: G3а-2б-1 — ошибка уровня файла в отчёте и «новый модуль» в честном FAIL_TO_PASS

## Контекст
Пятая часть G3а волны G по ADR-0026
(`docs/adr/0026-project-components-and-outcome-gates.md`, «Решение» п. 5):
ошибка уровня файла засчитывается красным только при новом модуле в зонах
и показывается отдельной строкой. Решения Оператора 19.10 (засчитывание
ошибки уровня файла вынесено из G2б в G3а) и 21.10 (G3а-2б поделена на
G3а-2б-1 — эта задача — и G3а-2б-2; засчитывание показывается ревьюверу
строкой пакета). Сейчас отчётчик Vitest
(`orchestrator/reporters/pult_vitest_reporter.js:82`, `onTestRunEnd`; обход
`allTests` на `:86`) пишет только тесты модулей — ошибка модуля (импорт,
сбор) в отчёт не попадает, файл пропадает; разбор JUnit
(`orchestrator/reporters/outcome.py:132`, `parse_junit`) отбрасывает текст
записи сбора pytest (`_junit_failure`, `:123`); гейт честного FAIL_TO_PASS
(`orchestrator/advance_gates/tests_writing.py:885`) на любую ошибку уровня
файла даёт находку `FILE_LEVEL_FINDING` (`:634`) из `_file_level_findings`
(`:805`), даже когда причина — ещё не написанный модуль из зон задачи.
Плюс два переноса из независимых проверок приёмок G2б-2 (10 и 15).

**Граница задачи:** новое поведение — только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`)
истинно; у артели и у записи `test_profile` разбор, исходы, гейты и пакет
ревьювера прежние побайтно (новые поля записи `CaseResult` объявлены со
значениями по умолчанию; профиль вне границы их не читает).

## Требования

1. **Запись уровня файла.**
   - `CaseResult` (`orchestrator/reporters/outcome.py:38`) получает поля
     `file_level: bool = False` и `detail: str = ""`; прежние поля всех
     записей и разбор у артели и `test_profile` не меняются.
   - Отчётчик `pult_vitest_reporter.js` для модуля с непустым `errors()`
     пишет в `tests` запись
     `{file, name: "<ошибка уровня файла>", state: "fail", file_level: true, error_name, error_message}`.
   - `parse_vitest` (`outcome.py:190`) для такой записи даёт `CaseResult`
     с исходом `error`, `file_level=True`, `failure=error_name`,
     `detail=error_message`.
   - `parse_junit` у записи с `message="collection failure"` (xunit2:
     `classname=""`, `name` — точечный путь модуля от `workdir`,
     трассировка — в тексте элемента) ставит `file_level=True` и `detail`
     — текст элемента (первые 2000 символов); `id`, `outcome`, `failure`
     — прежние. Подпись `parse_junit` не меняется.
   - Путь файла записи сбора гейт FAIL_TO_PASS сопоставляет по точечному
     имени с файлами планки прогона; не сопоставлен — прежняя находка
     уровня файла. Второе правило `_file_level_findings` (файл Vitest без
     записей) остаётся запасным.
   - В `outcome_integrity.compare`
     (`orchestrator/advance_gates/outcome_integrity.py:137`) записи
     `file_level` идентификаторами тестов не считаются.
2. **Новый модуль.** В гейте честного FAIL_TO_PASS запись `file_level`
   файла планки без маркера «Зелёный с рождения:» засчитывается красным,
   только если выполнены оба условия:
   - (а) существует путь P — элемент `zones` задачи, равный пути файла
     буквально (элементы-каталоги не считаются), отсутствующий в дереве
     `diff_base` кодовой ветки (ветки нет — в HEAD рабочей копии
     прогона; git не ответил — отказ подготовки);
   - (б) ошибка — неразрешённый импорт именно P: у Python `detail` несёт
     `ModuleNotFoundError: No module named '<M>'`, где M — путь P от
     `workdir` без `.py` через точки (или `__init__.py` пакета P); у
     Vitest спецификатор из сообщения, разрешённый от каталога файла в
     выкладке `plank_layout`, равен P без расширения или `P/index`.

   Засчитанный файл не даёт ни находки уровня файла, ни находок «теста
   нет в отчёте» по критериям, все файлы которых засчитаны. Долгоживущие
   файлы — прежняя находка. Засчитывание пишет запись журнала
   «ошибка уровня файла засчитана красным: новый модуль <P> (файл <имя>)».
   Условие ADR «все тесты `AC-<n>` файла на ветке присутствуют и зелёные»
   исполняет существующая проверка ветки на `in_dev → review`
   (`branch_criterion_problems`,
   `orchestrator/advance_gates/acceptance.py:378`, не меняется) — это
   закрепляется тестом.
3. **Пакет ревьювера.** Для профиля в границе раздел строк гейта исходов
   (`orchestrator/review.py:684`, `_outcome_gate_lines`) дополняется по
   одной строке на каждый различный текст записи журнала задачи
   «ошибка уровня файла засчитана красным: …» (дословно, без повторов);
   записей нет — строки нет. Вне границы — прежнее побайтно.
4. **Переносы из приёмок.**
   - (10) у компонента `junit-xml` запись `failed` с `TypeError` при
     списке ошибок проверки `[AssertionError]` — не провал проверки
     (`_check_failure_kind`, `tests_writing.py:752`), отказ гейта
     FAIL_TO_PASS;
   - (15) только в отказе `FAIL_TO_PASS_REFUSAL_ACTION`
     (`tests_writing.py:961`) деталь журнала не несёт «\nдальше:»,
     подсказка печатается один раз через `hint`; отказы на
     `tests_writing.py:393`, `:404`, `:414` — прежние.
5. **Тесты** детерминированы, без сети и без Node: форма записи уровня
   файла закреплена тестом `parse_vitest` на фикстуре JSON. Существующие
   тесты — без правок.

## Критерии приёмки

AC-1. `CaseResult` несёт поля `file_level` (по умолчанию `False`) и `detail` (по умолчанию `""`). `parse_vitest` на фикстуре JSON с записью `{file, name: "<ошибка уровня файла>", state: "fail", file_level: true, error_name, error_message}` даёт `CaseResult` с исходом `error`, `file_level=True`, `failure` = `error_name`, `detail` = `error_message`.

AC-2. `parse_junit` на отчёте xunit2 с записью сбора pytest (`classname=""`, `name` — точечный путь модуля, `message="collection failure"`, трассировка в тексте элемента) даёт запись с `file_level=True` и `detail`, равным первым 2000 символам текста элемента; `id`, `outcome` и `failure` этой записи совпадают с прежним разбором.

AC-3. У артели и у записи `test_profile` разбор и исходы прежние: прежние поля (`id`, `outcome`, `failure`, `skip_reason`, `time`, `mode`, `fails`, `retries`) записей `parse_junit`/`parse_vitest` и вердикт `verdict` совпадают с прежними; гейты и пакет ревьювера вне границы дают прежний результат.

AC-4. Гейт честного FAIL_TO_PASS сопоставляет запись сбора JUnit по точечному имени с файлом планки прогона; запись, не сопоставленная ни с одним файлом планки, даёт прежнюю находку уровня файла. Файл Vitest без записей в отчёте по-прежнему даёт находку уровня файла (второе правило `_file_level_findings`).

AC-5. В `outcome_integrity.compare` запись `file_level` не считается идентификатором теста: отчёт базы с записью `file_level` и отчёт ветки без неё (ошибка исправлена) не дают находки об исчезнувшем тесте по этой записи.

AC-6. Профиль в границе, файл планки без маркера «Зелёный с рождения:», запись `file_level`, путь P — элемент `zones`, буквально равный пути импортируемого модуля и отсутствующий в дереве `diff_base`, ошибка — неразрешённый импорт P (у Python `ModuleNotFoundError: No module named '<M>'` с M от `workdir` через точки, в том числе `__init__.py` пакета P; у Vitest спецификатор, разрешённый от каталога файла в выкладке `plank_layout`, равен P без расширения или `P/index`): гейт не даёт находки уровня файла по этому файлу и пишет запись журнала «ошибка уровня файла засчитана красным: новый модуль <P> (файл <имя>)».

AC-7. Каждое из условий (а) и (б) отдельно ломает засчитывание — гейт даёт прежнюю находку уровня файла, когда: в `zones` есть только каталог, содержащий модуль (не путь буквально); путь P есть в дереве `diff_base`; в ошибке другое имя модуля; ошибка другого вида (не неразрешённый импорт P).

AC-8. Файл с маркером «Зелёный с рождения:» и долгоживущий файл при прочих условиях AC-6 засчитыванием не пользуются — прежняя находка уровня файла.

AC-9. Находки «теста нет в отчёте» подавляются только по критериям, все файлы которых засчитаны: у критерия, один файл которого засчитан, а другой нет, находка по незасчитанному файлу остаётся.

AC-10. Если git не ответил при проверке отсутствия P в дереве `diff_base` (или в HEAD рабочей копии прогона, когда кодовой ветки нет), гейт FAIL_TO_PASS даёт отказ подготовки, а не засчитывание.

AC-11. Засчитанный файл и проверка ветки на `in_dev → review`: тест критерия этого файла на ветке отсутствует — отказ «переход отклонён: приёмочные тесты — тест критерия не в отчёте» с деталью «AC-<n> — теста нет в отчёте прогона ветки»; тест критерия на ветке красный — тот же отказ с деталью «AC-<n> — тест критерия не прошёл на ветке».

AC-12. Пакет ревьювера профиля в границе в разделе строк гейта исходов содержит ровно по одной строке на каждый различный текст записи журнала задачи «ошибка уровня файла засчитана красным: …» (дословно, повторяющиеся записи дают одну строку); без таких записей строки нет. Вне границы раздел пакета прежний побайтно.

AC-13. Компонент `junit-xml` со списком ошибок проверки `[AssertionError]`: запись `failed` с `TypeError` — не провал проверки, гейт FAIL_TO_PASS даёт отказ.

AC-14. В отказе `FAIL_TO_PASS_REFUSAL_ACTION` деталь записи журнала не содержит «\nдальше:», а подсказка печатается один раз (через `hint`); детали отказов на `tests_writing.py:393`, `:404`, `:414` по-прежнему несут «\nдальше: <подсказка>».

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (пять файлов `orchestrator/`
без общей зоны `tests/`); число критериев приёмки ≥ 10 (14).

Материал для решения Оператора — **обоснование монолита**:
- Задача уже результат деления: G3а-2б поделена Оператором 21.10 на
  G3а-2б-1 (эта) и G3а-2б-2; запрет плагинов повторов и прочие переносы
  ушли во вторую часть.
- Требования 1–3 — одна механика: запись `file_level` (носитель,
  `outcome.py` и отчётчик) читают засчитывание «нового модуля» в гейте
  FAIL_TO_PASS (`tests_writing.py`), `compare` (исключение из
  идентификаторов) и пакет ревьювера (строка засчитывания). Носитель без
  `compare` даёт мнимые «исчезнувшие» идентификаторы в гейте исходов
  (ТЗ, факт про `outcome_integrity.py`); засчитывание без носителя
  невозможно; строка пакета без засчитывания пуста.
- Технически отделимы переносы 10 и 15 (требование 4, только
  `tests_writing.py` и `tests/`), но они правят тот же файл, что
  требование 2, и отдельная задача добавила бы проход конвейера (минимум
  ~$25) при объёме в несколько строк; ТЗ задаёт работу одной задачей с
  бюджетом $35–45.
