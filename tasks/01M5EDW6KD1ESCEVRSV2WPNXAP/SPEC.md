# SPEC: G3а-2б-1 — ошибка уровня файла в отчёте и «новый модуль» в честном FAIL_TO_PASS

## Контекст
Пятая часть G3а волны G по ADR-0026
(`docs/adr/0026-project-components-and-outcome-gates.md`, «Решение» п. 5):
ошибка уровня файла засчитывается красным только при новом модуле в зонах
и показывается отдельной строкой. Решения Оператора 19.10 (засчитывание
ошибки уровня файла вынесено из G2б в G3а) и 21.10 (G3а-2б поделена на
G3а-2б-1 — эта задача — и G3а-2б-2; засчитывание показывается ревьюверу
строкой пакета). Сейчас отчётчик Vitest
(`orchestrator/reporters/pult_vitest_reporter.js:82`, `onTestRunEnd`; обход
`allTests` на `:86`) пишет только тесты модулей — ошибка модуля (импорт,
сбор) в отчёт не попадает, файл пропадает; разбор JUnit
(`orchestrator/reporters/outcome.py:132`, `parse_junit`) отбрасывает текст
записи сбора pytest (`_junit_failure`, `:123`); гейт честного FAIL_TO_PASS
(`orchestrator/advance_gates/tests_writing.py:885`) на любую ошибку уровня
файла даёт находку `FILE_LEVEL_FINDING` (`:634`) из `_file_level_findings`
(`:805`), даже когда причина — ещё не написанный модуль из зон задачи.
Плюс два переноса из независимых проверок приёмок G2б-2 (10 и 15).

Решения Оператора на гейте SPEC 21.10 (круг 1, по отклонениям аудита)
вошли в требования 1, 2, 4, 6 и в критерии AC-3, AC-4, AC-6…AC-11, AC-13,
AC-15.

**Граница задачи:** новое поведение — только у профиля, для которого
`in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213`)
истинно; у артели и у записи `test_profile` разбор, исходы, гейты и пакет
ревьювера прежние побайтно (новые поля записи `CaseResult` объявлены со
значениями по умолчанию; профиль вне границы их не читает).

## Требования

1. **Запись уровня файла.**
   - `CaseResult` (`orchestrator/reporters/outcome.py:38`) получает поля
     `file_level: bool = False` и `detail: str = ""`; прежние поля всех
     записей и разбор у артели и `test_profile` не меняются.
   - Отчётчик `pult_vitest_reporter.js` для модуля с непустым `errors()`
     пишет в `tests` запись
     `{file, name: "<ошибка уровня файла>", state: "fail", file_level: true, error_name, error_message}`.
   - `parse_vitest` (`outcome.py:190`) для такой записи даёт `CaseResult`
     с исходом `error`, `file_level=True`, `failure=error_name`,
     `detail=error_message`.
   - `parse_junit` у записи с `message="collection failure"` (xunit2:
     `classname=""`, `name` — точечный путь модуля от `workdir`,
     трассировка — в тексте элемента) ставит `file_level=True` и `detail`
     — текст элемента (первые 2000 символов); `id`, `outcome`, `failure`
     — прежние. Подпись `parse_junit` не меняется.
   - Для засчитывания (требование 2) запись сбора JUnit сопоставляется с
     файлом планки прогона по ПОЛНОМУ точечному пути файла от `workdir`,
     не по последнему сегменту; не сопоставлена — прежняя находка уровня
     файла. Прежнее сопоставление по последнему сегменту для текста
     находки уровня файла (`tests_writing.py:809`, `:818`) не меняется.
     Второе правило `_file_level_findings` (файл Vitest без записей)
     остаётся запасным.
   - В `outcome_integrity.compare`
     (`orchestrator/advance_gates/outcome_integrity.py:137`) записи
     `file_level` идентификаторами тестов не считаются.
2. **Новый модуль.** В гейте честного FAIL_TO_PASS запись `file_level`
   файла планки без маркера «Зелёный с рождения:» засчитывается красным,
   только если выполнены оба условия:
   - (а) существует путь P — элемент `zones:` опорной версии SPEC, которую
     гейт уже читает (`tests_writing.py:906`, `_spec_anchor_check`; зоны,
     добавленные `zones-extend`, не учитываются), равный пути файла
     буквально (элементы-каталоги не считаются) и отсутствующий в дереве
     `diff_base` кодовой ветки; кодовой ветки нет — P ищется в HEAD рабочей
     копии прогона; git не ответил — отказ подготовки;
   - (б) ошибка — неразрешённый импорт именно P:
     - у Python M берётся из итоговой строки исключения в `detail` —
       последней непустой строки вида
       `E   ModuleNotFoundError: No module named '<M>'` (или той же строки
       без префикса `E   `); M сравнивается на равенство с ожидаемым
       именем — путём P от `workdir` без `.py` через точки (для
       `__init__.py` — именем пакета P). Вхождение такого текста в другом
       месте `detail` признаком не является;
     - у Vitest сообщение (`detail`) распознаётся в двух формах —
       `Failed to resolve import "<спецификатор>" from "<файл>"` и
       `Cannot find module '<спецификатор>'`; иная форма — не
       засчитывание. Спецификатор, разрешённый от каталога файла в
       выкладке `plank_layout`, равен P без расширения или `P/index`.

   Засчитанный файл не даёт ни находки уровня файла, ни находок «теста
   нет в отчёте» по критериям, все файлы которых засчитаны. Долгоживущие
   файлы — прежняя находка. Каждое засчитывание пишет запись журнала
   задачи с действием «ошибка уровня файла засчитана красным» и деталью
   «новый модуль <P> (файл <имя>)». Условие ADR «все тесты `AC-<n>` файла
   на ветке присутствуют и зелёные» исполняет существующая проверка ветки
   на `in_dev → review` (`branch_criterion_problems`,
   `orchestrator/advance_gates/acceptance.py:378`, не меняется) — это
   закрепляется тестом.
3. **Пакет ревьювера.** Для профиля в границе раздел строк гейта исходов
   (`orchestrator/review.py:684`, `_outcome_gate_lines`) дополняется
   строкой «ошибка уровня файла засчитана красным: <деталь>» — по одной на
   каждую различную деталь записей журнала задачи с действием «ошибка
   уровня файла засчитана красным» (без повторов); записей нет — строки
   нет. Вне границы — прежнее побайтно.
4. **Переносы из приёмок.**
   - (10) у компонента `junit-xml` запись `failed` с `TypeError` при
     списке ошибок проверки `[AssertionError]` — не провал проверки
     (`_check_failure_kind`, `tests_writing.py:752`), отказ гейта
     FAIL_TO_PASS;
   - (15) в отказе `FAIL_TO_PASS_REFUSAL_ACTION` (`tests_writing.py:961`)
     подсказка «дальше:» остаётся в детали записи журнала (её читает бриф
     test_author, `orchestrator/brief.py:1204`) и печатается один раз:
     подсказка отказа (`hint`, печать `orchestrator/advance_gates/_base.py:36-37`)
     её не повторяет. Отказы на `tests_writing.py:393`, `:404`, `:414` —
     прежние.
5. **Тесты** детерминированы, без сети и без Node: форма записи уровня
   файла закреплена тестом `parse_vitest` на фикстуре JSON. Существующие
   тесты — без правок.
6. **Смена итога `pult-vitest` (усиление).** Прогон компонента
   `pult-vitest` с ошибкой модуля, который сегодня даёт итог «неизвестно»
   (файл пропадает из отчёта, ненулевой код возврата —
   `outcome.py:243-245`), после требования 1 даёт итог «красный» (запись
   `error`) во всех потребителях итога: повторы, полный набор, гейт
   исходов. Это усиление, не ослабление.

## Критерии приёмки

AC-1. `CaseResult` несёт поля `file_level` (по умолчанию `False`) и `detail` (по умолчанию `""`). `parse_vitest` на фикстуре JSON с записью `{file, name: "<ошибка уровня файла>", state: "fail", file_level: true, error_name, error_message}` даёт `CaseResult` с исходом `error`, `file_level=True`, `failure` = `error_name`, `detail` = `error_message`; полный набор компонента `pult-vitest` по такому отчёту даёт итог «красный», не «неизвестно».

AC-2. `parse_junit` на отчёте xunit2 с записью сбора pytest (`classname=""`, `name` — точечный путь модуля, `message="collection failure"`, трассировка в тексте элемента) даёт запись с `file_level=True` и `detail`, равным первым 2000 символам текста элемента; `id`, `outcome` и `failure` этой записи совпадают с прежним разбором.

AC-3. У артели и у записи `test_profile` прежние поля (`id`, `outcome`, `failure`, `skip_reason`, `time`, `mode`, `fails`, `retries`) записей `parse_junit`/`parse_vitest` и вердикт `verdict` совпадают с прежними. Запись `test_profile` с `report: junit-xml`: гейт FAIL_TO_PASS на записи сбора даёт прежнюю находку `FILE_LEVEL_FINDING` даже при выполненных условиях (а) и (б), записи журнала с действием «ошибка уровня файла засчитана красным» нет, пакет ревьювера не содержит строки «ошибка уровня файла засчитана красным: …».

AC-4. Засчитывание требует сопоставления записи сбора JUnit с файлом планки по полному точечному пути файла от `workdir`: при долгоживущем `tests/test_x.py` и файле планки `…/test_x.py` запись сбора долгоживущего файла не засчитывает файл планки — гейт даёт находку уровня файла, записи журнала о засчитывании нет. Запись, не сопоставленная ни с одним файлом планки, даёт прежнюю находку уровня файла. Файл Vitest без записей в отчёте по-прежнему даёт находку уровня файла (второе правило `_file_level_findings`).

AC-5. В `outcome_integrity.compare` запись `file_level` не считается идентификатором теста: отчёт базы с записью `file_level` и отчёт ветки без неё (ошибка исправлена) не дают находки об исчезнувшем тесте по этой записи.

AC-6. Python, профиль в границе: файл планки без маркера «Зелёный с рождения:», запись сбора `file_level`, путь P — элемент `zones:` опорной версии SPEC, буквально равный пути модуля и отсутствующий в дереве `diff_base`, последняя непустая строка `detail` — `E   ModuleNotFoundError: No module named '<M>'` (и, отдельным случаем, та же строка без префикса `E   `; и случай `__init__.py` пакета P), M равно пути P от `workdir` через точки: гейт не даёт находки уровня файла по этому файлу и пишет запись журнала с действием «ошибка уровня файла засчитана красным» и деталью «новый модуль <P> (файл <имя>)».

AC-7. Vitest, профиль в границе, при прочих условиях AC-6: `detail` в форме `Failed to resolve import "<спецификатор>" from "<файл>"` и (отдельным случаем) `Cannot find module '<спецификатор>'`, спецификатор, разрешённый от каталога файла в выкладке `plank_layout`, равен P без расширения (и, отдельным случаем, `P/index`): гейт не даёт находки уровня файла по этому файлу и пишет ту же запись журнала, что в AC-6.

AC-8. Условие (а) и исключения ломают засчитывание — гейт даёт прежнюю находку уровня файла и не пишет записи журнала о засчитывании, когда при прочих условиях AC-6: в `zones:` опорного SPEC есть только каталог, содержащий модуль; путь P есть в дереве `diff_base`; P добавлен в зоны только командой `zones-extend`, а в `zones:` опорного SPEC его нет; файл несёт маркер «Зелёный с рождения:»; файл долгоживущий.

AC-9. Условие (б) у Python ломает засчитывание (прежняя находка уровня файла, записи журнала нет), когда при прочих условиях AC-6: M в итоговой строке не равно ожидаемому имени (другое имя модуля, в том числе имя, лишь содержащее ожидаемое); итоговая строка — исключение другого вида; файл планки падает на `raise RuntimeError("ModuleNotFoundError: No module named '<M>'")` с ожидаемым M.

AC-10. Условие (б) у Vitest ломает засчитывание (прежняя находка уровня файла, записи журнала нет), когда при прочих условиях AC-7: спецификатор, разрешённый от каталога файла в выкладке `plank_layout`, не равен ни P без расширения, ни `P/index`; сообщение — иной формы, чем `Failed to resolve import "…" from "…"` и `Cannot find module '…'`.

AC-11. Кодовой ветки нет, P ищется в HEAD рабочей копии прогона: P нет в HEAD — засчитывание (как в AC-6); P есть в HEAD — прежняя находка уровня файла, записи журнала нет. Git не ответил при проверке отсутствия P (в дереве `diff_base` или в HEAD) — гейт FAIL_TO_PASS даёт отказ подготовки, а не засчитывание.

AC-12. Находки «теста нет в отчёте» подавляются только по критериям, все файлы которых засчитаны: у критерия, один файл которого засчитан, а другой нет, находка по незасчитанному файлу остаётся.

AC-13. Засчитанный файл и проверка ветки на `in_dev → review`: тест критерия этого файла на ветке отсутствует — отказ «переход отклонён: приёмочные тесты — тест критерия не в отчёте» с деталью «AC-<n> — теста нет в отчёте прогона ветки»; тест критерия на ветке красный — тот же отказ с деталью «AC-<n> — тест критерия не прошёл на ветке».

AC-14. Пакет ревьювера профиля в границе в разделе строк гейта исходов содержит строку «ошибка уровня файла засчитана красным: <деталь>» ровно по одной на каждую различную деталь записей журнала задачи с действием «ошибка уровня файла засчитана красным» (повторяющиеся записи дают одну строку); без таких записей строки нет. Вне границы раздел пакета прежний побайтно.

AC-15. Переносы: (10) компонент `junit-xml` со списком ошибок проверки `[AssertionError]` — запись `failed` с `TypeError` не провал проверки, гейт FAIL_TO_PASS даёт отказ; (15) при отказе `FAIL_TO_PASS_REFUSAL_ACTION` печать отказа содержит «дальше:» ровно один раз, а деталь записи журнала содержит «\nдальше:»; детали отказов на `tests_writing.py:393`, `:404`, `:414` по-прежнему несут «\nдальше: <подсказка>».

## Оценка объёма и деление

без общей зоны `tests/`); число критериев приёмки ≥ 10 (15).

Материал для решения Оператора — **обоснование монолита**:
- Задача уже результат деления: G3а-2б поделена Оператором 21.10 на
  G3а-2б-1 (эта) и G3а-2б-2; запрет плагинов повторов и прочие переносы
  ушли во вторую часть.
- Требования 1–3 — одна механика: запись `file_level` (носитель,
  `outcome.py` и отчётчик) читают засчитывание «нового модуля» в гейте
  FAIL_TO_PASS (`tests_writing.py`), `compare` (исключение из
  идентификаторов) и пакет ревьювера (строка засчитывания). Носитель без
  `compare` даёт мнимые «исчезнувшие» идентификаторы в гейте исходов
  (ТЗ, факт про `outcome_integrity.py`); засчитывание без носителя
  невозможно; строка пакета без засчитывания пуста.
- Технически отделимы переносы 10 и 15 (требование 4, только
  `tests_writing.py` и `tests/`), но они правят тот же файл, что
  требование 2, и отдельная задача добавила бы проход конвейера (минимум
  ~$25) при объёме в несколько строк; ТЗ задаёт работу одной задачей с
  бюджетом $35–45.
