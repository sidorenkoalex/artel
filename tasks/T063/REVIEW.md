## Фаза A: проверка плана
Требования 1–4 SPEC покрыты единственным шагом плана, шаг — проверяемая
единица разумного размера, подход не конфликтует с конвенциями
(приватные функции, регенерация карты тем же коммитом). Формальная
структура плана в порядке.

Содержательно сам «Подход» несёт корень найденного ниже blocker'а:
`_first_sentence` обрезает «по первой точке» без разбора, является ли
эта точка границей предложения — раздел «Риски» PLAN называет это
нишевым случаем («сокращения с точкой, например «т.е.»»), но по факту
это доминирующий случай на реальных данных репозитория (см. ниже), а
не редкое исключение. План не квалифицировал масштаб риска и поэтому
не потребовал более аккуратного правила обрезки уже на этапе
проектирования.

## Замечания

- **blocker** — `orchestrator/retro.py:64-73` (`_first_sentence`), и оба
  места, которые её используют — `orchestrator/retro.py:76-81`
  (`_first_context_sentence`, вызывается из `build_done:195`) и
  `orchestrator/retro.py:232` (прямое применение к `tz_text` в
  `build_killed`) — `normalized.find(".")` находит ЛЮБУЮ первую точку в
  тексте, а не границу предложения. На реальных данных это ломается
  систематически, не как редкий крайний случай:
  - Мотивирующий пример из самого SPEC.md этой задачи — SPEC T042.
    Первое предложение раздела «Контекст» T042: `` `docs/codebase-map.md`
    — автогенерируемый файл (`scripts/codebase_map.py`), но за его
    свежесть в `main` не отвечает никто один: ... `` (обрывается на
    двоеточии). Старое поведение (`_first_context_line`, обрезка по
    строке) давало: `` `docs/codebase-map.md` — автогенерируемый файл
    (`scripts/codebase_map.py`), `` — усечено по запятой, это и есть
    баг, который SPEC ставит целью исправить. Новое поведение
    (`_first_context_sentence`) на этом же входе даёт `` `docs/codebase-map.``
    — оборвано на точке внутри имени файла, ПОСЛЕ первого слова.
    Результат не просто не «полное первое предложение» — он хуже
    старого фолбэка по содержательности. Проверено запуском
    `retro._first_context_sentence` на `tasks/T042/SPEC.md` из рабочей
    копии ветки.
  - Не единичный случай: прогон `_first_context_sentence` по разделам
    «Контекст» всех `tasks/T0*/SPEC.md` в репозитории (скрипт см. ниже)
    показал обрывки короче 20–40 символов минимум для T003, T007,
    T015, T016, T030, T032, T033, T035, T036, T038, T039, T041, T042,
    T048, T049, T050–T053, T056–T058, T063 (и это не исчерпывающий
    список) — то есть для заметной доли уже существующих SPEC.md
    задач, не для гипотетической экзотики. Причины обрыва — не только
    сокращения («п.», «т.е.»), но и файловые пути/расширения
    (`orchestrator/artel.py`, `docs/design.md`), номера версий пунктов
    роадмапа, даты в формате `ДД.ММ` (`27.08` → обрыв на `27.`).
  - Требование 2 (killed из ТЗ) подвержено тому же классу: журнал
    `kill` хранит текст `TZ.md`, который так же может содержать даты,
    пути и сокращения до первой смысловой точки.
  - Предложение: правило обрезки должно отличать точку-конец-
    предложения от точки внутри токена — минимум: не резать по точке,
    за которой сразу следует цифра/строчная буква/непробельный символ
    (характерно для `27.08`, `codebase-map.md`, `п.5`), либо требовать
    после точки пробел + заглавную букву/конец текста. Это не полная
    NLP-сегментация (которую SPEC не требует), но нынешняя реализация
    не проходит даже собственный мотивирующий пример SPEC.

- **minor** — `tests/test_retro.py` и
  `tasks/T063/acceptance_tests/test_retro_gist_sentence.py` — все
  синтетические тексты для `_first_sentence`/`build_done`/`build_killed`
  подобраны так, что до конца первого предложения не встречается ни
  одной «лишней» точки (только запятые и переносы строк). Из-за этого
  ни один тест не поймал бы найденный выше blocker — мутационный тест
  «добавить дату или путь с точкой до конца первого предложения» никак
  не диагностируется текущим набором. Стоит добавить кейс с точкой
  внутри токена (дата `ДД.ММ`, путь/расширение файла или сокращение)
  до реальной границы предложения — как для `_first_sentence`
  напрямую, так и через `build_done`/`build_killed`.
