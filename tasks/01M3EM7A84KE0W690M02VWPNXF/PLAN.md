# PLAN: Конфликт подтяжки на приёмке и гейте мержа: возврат из эскалации требует шага разработчика

## Подход

Содержательная правка — одно условие в `orchestrator/pull.py::
_handle_merge_failure` (строка 266 на входе в задачу): `if state ==
"in_dev"` становится проверкой принадлежности набору трёх состояний,
из которых возврат из эскалации ведёт в `in_dev`.

Набор выносится отдельной модульной константой рядом с
`PULL_CONFLICT_ROLE_STEP_MARKER` (строка 60), а не литеральным кортежем
внутри функции: константа — то место, где живёт ПРИЧИНА набора
(«эскалация подтяжки не пишет `escalated_from`, поэтому возврат из неё
уходит в `in_dev` из любого из трёх»), и она же адрес, по которому
четвёртая точка подтяжки, если такая появится, будет добавлена одной
строкой. Имя набора — `PULL_CONFLICT_MARKED_STATES`; экспортировать его
наружу задача не обязана (`orchestrator/auto.py` — «Не входит»), но и
приватным подчёркиванием не прячет: константа документирует инвариант,
а не деталь реализации функции.

Комментарий у записи метки переписывается целиком (требование 3):
сегодняшнее утверждение «`acceptance`/`merge_gate` … не заводят шага
роли на возврате из escalated, метить их нечем» ложно и заменяется
основанием из «Контекста» SPEC. Модульный комментарий у самой константы
`PULL_CONFLICT_ROLE_STEP_MARKER` (строка 49: «эскалация `in_dev` по
НЕРАЗРЕШЁННОМУ конфликту») тоже сужает факт до одного состояния —
правится тем же шагом: иначе в одном файле останутся два комментария,
противоречащие друг другу и коду, а приёмочный тест AC-5 сверяет
комментарии ВСЕГО файла, не только соседние с записью строки.

Требование 4 (стоп-кран серии меток) выполняется без единой правки
`orchestrator/auto.py` — обоснование в «Контексте» SPEC проверено по
коду: `_pull_conflict_marker_streak` (`orchestrator/auto.py`, строка
694) сбрасывает счёт любым `state -> X`, кроме `escalated`/`in_dev`, а
`_pre_advance_step` (строка 782) требует, чтобы метку добавил ТОТ ЖЕ
вызов `cmd_advance`. Метки требования 1 пишутся на путях `approve`
(приёмка, гейт мержа), то есть заведомо не внутри предварительного
advance, — серия остаётся единичной. Условие записи метки не
дублируется вторым блоком `store.journal`: один конфликт обязан
оставлять РОВНО одну запись метки, иначе серия достигает порога
стоп-крана с первого же конфликта (мутация, которую ловит приёмочный
AC-4).

Планка задачи залочена (`tasks/<id>/acceptance_tests/`) — прогон до
правки зафиксирован как красный на 5 тестах из 9 ровно теми
assert'ами, которые называют докстринги планки; правке подлежит код,
не планка.

## Шаги

1. **`orchestrator/pull.py`: набор состояний + комментарии.** Константа
   `PULL_CONFLICT_MARKED_STATES = ("in_dev", "acceptance", "merge_gate")`
   с обоснованием набора; `if state == "in_dev"` ->
   `if state in PULL_CONFLICT_MARKED_STATES`; комментарий у записи метки
   переписан (ложного утверждения нет, основание названо); комментарий у
   `PULL_CONFLICT_ROLE_STEP_MARKER` расширен с `in_dev` на набор.
   Юнит-тесты — новый файл `tests/test_pull_conflict_marker_states.py`:
   матрица «состояние -> есть ли метка» по всем трём состояниям набора и
   по состоянию вне него (`review`) через `pull.evaluate`; сверка
   `detail` метки с `detail` записи эскалации; полнота набора
   (константа равна ровно трём состояниям — ни одного лишнего);
   воспроизведение случая 21.09 заглушками git (конфликт на гейте мержа
   -> `approve` -> `auto` журналирует `auto.REWORK_REFUSAL_ACTION` и
   отдаёт шаг developer без предварительного advance) и сценарий
   требования 4 (шаг developer разрешает конфликт -> повторная подтяжка
   чистая -> цикл не остановлен стоп-краном, метка на весь сценарий
   одна). Тем же коммитом — `python3 scripts/codebase_map.py` (правятся
   `orchestrator/*.py` и `tests/*`).

Один шаг = один MR: требование и его покрытие неразделимы (раздел
«Деление» SPEC — монолит).

## Влияние на систему

**Что затрагивается за пределами правки.** Ровно один читатель метки —
`orchestrator/auto.py`: `_role_step_since_state_entry` (анкер рубежа
переделки, строка 325) и `_pre_advance_step` (стоп-кран серии, строка
742). Оба читают метку по фиксированному тексту `action`, не по
состоянию, из которого она записана, — расширение набора состояний их
кода не касается и правки не требует (раздел «Не входит» SPEC). Файл
задачей не изменяется вовсе; приёмочный AC-4 держит это диффом файла.

**Инварианты и гейты рядом.** Ни один не ослабляется: правка только
ДОБАВЛЯЕТ записи журнала для двух состояний, где их не было, и ни одной
не убирает. Условие сохраняет отрицательную половину (состояние вне
набора метки не получает) — требование 2, приёмочный AC-2; снятие
условия целиком было бы ослаблением и запрещено. Сама эскалация
(`store.set_state` в `escalated`), авторазрешение конфликта карты (SPEC
T067), инцидент очистки worktree и красная планка после чистого merge не
трогаются ни для одного состояния.

**Существующие тесты.** `tests/test_pull.py`,
`tests/test_branch_freshness_gate.py`,
`tests/test_fsm_map_conflict_autoresolve.py`,
`tests/test_artifact_escalation_marker.py`,
`tests/test_auto_cycle.py`, `tests/test_auto_escalated_return_rework_
gate.py` — прогоняются как есть, без правки ассертов; приёмочный AC-5
отдельно держит сам факт наличия перечисленных методов. Красный
существующий тест здесь — сигнал, что набор состояний задан неверно, не
повод править тест.

**Откат.** Revert одного merge-коммита: правка — одно условие, одна
новая константа, два комментария и один новый тестовый файл, внешнего
состояния (БД, файлы, ветки) не меняет.

## Риски

- `tests/test_branch_freshness_gate.py::test_approve_escalates_on_pull_
  conflict_and_aborts` эскалирует конфликт с пути `approve` — если он
  сверяет журнал на РАВЕНСТВО набору записей, новая запись метки его
  покраснит. Проверяется прогоном на шаге 1; починка — код теста не
  трогаем, а разбираемся, чего именно тест требует (ослабление ассерта
  запрещено; если тест действительно требует отсутствия метки для
  `acceptance`/`merge_gate` — это противоречие с SPEC и эскалация).
- Состояние `acceptance` подтяжку зовут две точки — `fsm::
  _approve_acceptance` и `canary::_pass_acceptance_gate`. Вторая — путь
  канарейки: она получит метку тоже. Это не расширение зоны задачи
  (`canary.py` не правится) и не вред: возврат из этой эскалации ведёт
  в `in_dev` там точно так же, канарейка гоняет тот же `auto`.
