# SPEC: Конфликт подтяжки на приёмке и гейте мержа: возврат из эскалации требует шага разработчика

## Контекст

Неразрешённый конфликт подтяжки main в ветку задачи переводит задачу в
`escalated` и метит её в журнале меткой
`PULL_CONFLICT_ROLE_STEP_MARKER` — но только при `state == "in_dev"`
(`orchestrator/pull.py`, ветка `state == "in_dev"` внутри
`_handle_merge_failure`, ~стр. 266). Комментарий рядом утверждает, что из
`acceptance` и `merge_gate` возврат из эскалации шага роли не заводит и
метить их нечем. Утверждение ложно: эта эскалация не пишет
`escalated_from`, а возврат берёт состояние как `escalated_from or
"in_dev"` — значит из всех трёх состояний задача возвращается в `in_dev`,
где следующий шаг — шаг разработчика. Без метки `auto` после возврата
делает предварительный advance, снова подтягивает main, ловит тот же
конфликт и эскалирует повторно — теперь из `in_dev` и уже с меткой;
Оператор платит за каждый такой конфликт лишним кругом `answer`/`approve`
(живой случай 21.09, задача 01M31DRD81: `approve` на гейте мержа →
`escalated`, `answer` + `approve` в 10:00:20 → `in_dev`, через 4 с снова
`escalated`, шага developer между ними нет).

Обоснование требования 2 ТЗ (состояние, из которого возврат уходил бы НЕ
в `in_dev`). Подтяжку зовут четыре точки, все через
`orchestrator/fsm.py::_pull_main_or_escalate`: `_approve_acceptance`
(state `acceptance`), `orchestrator/fsm_advance.py` обработчик `in_dev`
(state `in_dev`), `orchestrator/fsm_merge_gate.py::_sync_main_or_wait`
(state `merge_gate`) и `orchestrator/canary.py::_pass_acceptance_gate`
(state `acceptance`) — итого три различных состояния. Возврат из
`escalated` во всех трёх реализациях считает состояние как
`escalated_from or "in_dev"`, а `escalated_from` пишут только эскалации
собственных классов (провал агента, потолок бюджета, эскалация по
содержимому артефакта роли — адреса в «Материалах»), каждая
непосредственно перед своей же сменой состояния, и возврат его обнуляет.
Эскалация подтяжки `escalated_from` не пишет — следовательно ни одного
состояния, из которого возврат уходил бы не в `in_dev`, сегодня нет, и
метка правдива для всех трёх. Исключение, предусмотренное требованием 2
ТЗ, не требуется; альтернативный механизм возврата (запись
`escalated_from`) не нужен — метка возможна.

Обоснование требования 3 ТЗ (стоп-кран серии меток). Стоп-кран
срабатывает только когда метку добавил ТОТ ЖЕ вызов `cmd_advance`, а
серия сбрасывается любой сменой состояния, кроме `-> escalated` и
`-> in_dev`. Метки требования 1 пишутся на путях `approve` (приёмка,
гейт мержа), не внутри предварительного advance, а в сценарии ТЗ
«конфликт на гейте мержа → ответ → шаг developer → повторная подтяжка
без конфликта» серия остаётся единичной и гасится переходом в следующее
состояние. Правка `orchestrator/auto.py` не требуется, вопрос расширения
зон Оператору не заводится.

## Требования

1. Неразрешённый конфликт содержимого подтяжки — та ветка
   `orchestrator/pull.py`, которая делает `git merge --abort` и переводит
   задачу в `escalated`, — пишет в журнал метку
   `PULL_CONFLICT_ROLE_STEP_MARKER` не только при `state == "in_dev"`, но
   и при `state == "acceptance"`, и при `state == "merge_gate"`. Текст
   метки, её `detail` и `actor` записи — те же, что сегодня у случая
   `in_dev`.
2. Метка пишется только для состояний, из которых возврат из эскалации
   действительно ведёт в `in_dev`, то есть ровно для перечисленных трёх
   (требование 2 ТЗ, обоснование — «Контекст»): состояние вне этого
   набора метку не получает.
3. Комментарий рядом с записью метки в `orchestrator/pull.py` приведён в
   соответствие с фактом: он не утверждает, что возврат из эскалации
   `acceptance`/`merge_gate` не заводит шага роли, и называет основание —
   эскалация подтяжки не пишет `escalated_from`, поэтому возврат из неё
   уходит в `in_dev` из любого из трёх состояний.
4. Стоп-кран серии меток конфликта подтяжки не срабатывает из-за меток,
   добавленных требованием 1: сценарий «конфликт на гейте мержа → ответ →
   шаг developer → повторная подтяжка без конфликта» проходит без
   остановки цикла. `orchestrator/auto.py` для этого не правится.
5. Тесты в `tests/`: конфликт подтяжки из `in_dev`, `acceptance`,
   `merge_gate` (метка в журнале в каждом случае); отсутствие метки для
   состояния вне этих трёх; воспроизведение случая 21.09 заглушками git —
   после `approve` возврата `auto` не делает предварительный advance до
   шага developer; сценарий требования 4. Существующие тесты подтяжки и
   эскалаций остаются зелёными, ни один не ослаблен и не удалён.

## Критерии приёмки

AC-1. Конфликт подтяжки, эскалирующий задачу, пишет в журнал запись с
`action == pull.PULL_CONFLICT_ROLE_STEP_MARKER` в каждом из трёх случаев:
`state == "in_dev"`, `state == "acceptance"`, `state == "merge_gate"`;
`detail` записи метки совпадает с `detail` записи эскалации.

AC-2. Тот же конфликт подтяжки при состоянии вне этих трёх метки в журнал
не пишет (запись с `action == pull.PULL_CONFLICT_ROLE_STEP_MARKER`
отсутствует), а сама эскалация происходит как прежде.

AC-3. Воспроизведение случая 21.09 заглушками git: конфликт подтяжки на
гейте мержа → `approve` возврата из эскалации переводит задачу в `in_dev`
→ `auto` не делает предварительный advance, а журналирует отказ рубежа
переделки (`auto.REWORK_REFUSAL_ACTION`) и отдаёт шаг роли developer.

AC-4. Сценарий «конфликт подтяжки на гейте мержа → возврат из эскалации →
шаг developer → повторная подтяжка без конфликта» проходит без остановки
цикла стоп-краном серии меток конфликта подтяжки; файл
`orchestrator/auto.py` задачей не изменён.

AC-5. Комментарий рядом с записью метки в `orchestrator/pull.py` не
содержит утверждения, что из `acceptance`/`merge_gate` возврат из
эскалации шага роли не заводит; полный прогон `tests/` зелёный, ни один
существующий тест подтяжки или эскалаций не ослаблен и не удалён.

## Оценка объёма и деление

Сработал один сигнал — «число затрагиваемых модулей/файлов»: guard
считает все упоминания путей `orchestrator/*.py` по тексту SPEC, а их
здесь больше пяти, притом менять задача будет ровно один файл
(`orchestrator/pull.py`) плюс тесты; остальные упомянутые модули — адреса
вызывающих точек и механизма возврата, перечисленные в «Не входит»
только чтением. Прогноз диффа: 6 КиБ.

Монолит. Резать нечего: содержательная правка — условие записи метки и
её комментарий в одной функции одного файла, и без тестов из требования 5
она не проверяема, а без неё тесты краснеют. Любая половина оставила бы
систему в промежуточном состоянии — либо метка без покрытия, либо тесты
без механики.
