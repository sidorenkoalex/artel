# SPEC-AUDIT: ADR-0027, часть А1 — общие фикстуры-песочницы в стиле pytest и их подключение

Проверено по рабочему каталогу на HEAD 2b187a3d (ветка задачи = main + бэклог; `tests/sandbox.py`, `conftest.py`, `orchestrator/config.py` совпадают с пином 8cff887c по всем названным местам). ANSWER-n.md и решений Оператора на гейте SPEC у задачи нет.

## ТЗ и SPEC
Требования ТЗ 1, 2 и 4 перенесены в SPEC полностью: ТЗ п.1 → SPEC требования 1–5, ТЗ п.2 → требования 6–7, ТЗ п.4 → требование 9. «Не входит», зоны, «только чтение», бюджет и Приложение 1 совпадают с ТЗ; Приложение 1 перенесено байт-в-байт. Лишних требований в SPEC нет. Решения ADR-0027 п.2 (набор фикстур «уточняет SPEC» — ТЗ добавил `tmp_dir`) и п.9 (деление на А1/А2/Б — по ТЗ) с SPEC согласованы.

Расхождение:

- **A-1. Содержание тестов ТЗ п.3 не привязано к файлу `tests/`.** ТЗ п.3 требует, чтобы тесты (а)–(е) лежали в новом файле `tests/` и были долгоживущей защитой фикстур. В SPEC пункты (а)–(е) превратились в AC-2…AC-8 (SPEC.md, «Критерии приёмки»), но ни одно требование не говорит, где эти тесты должны лежать. Требование 8 и AC-9 проверяют только форму нового файла `tests/` (функции, `parametrize`, «Ловит мутацию:», явный импорт), а не его содержание.
  - Как SPEC выполняется буквально без смысла: разработчик кладёт в `tests/` файл из одной функции, которая проходит AC-9, а (а)–(е) остаются только в планке `tasks/<id>/acceptance_tests/`.
  - Последствие: после мержа планка в полном прогоне `tests/` на main не участвует, и регрессию фикстур (например, снятую проверку возврата `doCleanups()`) не поймает ничто.
  - Что поправить: требование 8 или AC-9 должно прямо требовать, чтобы новый файл `tests/` покрывал (а)–(е), то есть AC-2…AC-8.

## Факты против кода
Подтвердилось (файл:строка):
- Строки классов в `tests/sandbox.py` верны: `TmpDirTest` :683 (только `tdir`, :690–693), `TmpRootTest` :1581, `InitializedTmpRootTest` :1765, `RealGitSandbox` :1897 (свой `setUp` без `super()`, :1916–1954), `OriginRealGitSandbox` :2011 (`add_origin`/`bare` :2020–2025), `LightTransitionSandbox` :2124 (атрибуты и методы :2163–2246).
- Список и настройки: `ALL_CONFIG_ATTRS` :90; `PATCHED_ATTRS = ALL_CONFIG_ATTRS` :1599; `REAL_RETRY_PAUSE` :1600; `ARTEL_CLONE_IS_ROOT` :1914; `TASK_TITLE` :2163; `self.assertEqual` в `git()` :1959.
- Шаблоны под `functools.cache`: `_real_git_template` :1496–1497.
- Побочные эффекты импорта `tests.sandbox`: `shutil.which = _stub_which` :141, `config.ROLES`/`config.MODELS_LOCAL` :437–440, `config.TWO_SIDED_OBSERVATION = False` :446.
- По умолчанию `config.TWO_SIDED_OBSERVATION = True` (`orchestrator/config.py:217`), так что проверка AC-6 отличает импорт с побочным эффектом от импорта без него.
- Защищённые пути: маска `**/conftest.py` — в `orchestrator/config.py:774`.
- Контекст хунка Приложения 1 совпадает с `conftest.py:24-29`. `index ada960f` совпадает с блобом `HEAD:conftest.py` (`ada960f5…`). `git apply --check` на чистом дереве: «Checking patch conftest.py...», код 0.
- Поведение `doCleanups()` вне раннера проверено пробой на Python 3.13.12. Экземпляр, у которого действие уборки бросает `ZeroDivisionError`, возвращает `False`, `_outcome` у него `None`, исключение никуда не выводится. Утверждение SPEC верно.
- `cls()` без `methodName` создаётся (та же проба), `tests/__init__.py` существует.
- Фикстур с именами `tmp_dir`/`tmp_root`/`initialized_tmp_root`/`real_git`/`origin_real_git`/`light_transition` в `tests/` и корневом `conftest.py` сейчас нет, конфликта имён после подключения не будет.

Неточности:
- **B-1. «Текст причины» не получить из `doCleanups()`.** Требование 2 требует, чтобы `RuntimeError` нёс «текст причины». Проба выше показала: вне раннера `doCleanups()` теряет исключение уборки и отдаёт только `False`. Причины в возвращаемом значении нет.
  - Чтобы её передать, фикстуре нужен свой способ собрать ошибку: собственный `_outcome` с результатом или обёртка над действиями уборки. SPEC этого не говорит, а AC-4 текст сообщения не проверяет.
  - Как SPEC выполняется буквально: сообщение-константа вроде «уборка не удалась», без исключения, из-за которого она не удалась.
  - Что не определено в пути падения `setUp()` (требование 3): если там `doCleanups()` тоже вернул `False`, ошибка уборки пропадает молча.
- **B-2. Комментарий Приложения 1 неточен.** Комментарий утверждает: «подключение не меняет состояние процесса для прогонов, которые песочницу не берут». Но импорт `tests.fixtures` исполняет `tests/__init__.py:12`: `prefer_direct_git(os.environ)` на macOS вставляет каталог в `PATH` (`tests/direct_git.py:42-72`) и может вызвать `xcode-select`.
  - После Приложения 1 это затронет каждый прогон pytest в дереве артели, в том числе планки, которые `tests.*` не импортируют.
  - Похоже, это безвредно (предпочтение прямого git), но утверждение приложения не точно, а AC-6 этот эффект не охватывает. Решение за Оператором: приложение — его текст.

Отклонения проверяемости:
- **C-1. AC-1 не требует точного класса.** AC-1 говорит «экземпляр соответствующего класса». Проверка через `isinstance` пропускает правдоподобные мутации, где фикстура отдаёт подкласс: `tmp_root` → `InitializedTmpRootTest`, `real_git` → `OriginRealGitSandbox`, `tmp_root` → `LightTransitionSandbox`. - Замечание, не отклонение: AC-8 («возвращают результат без ошибки») не фиксирует значение. Свою мутацию (нет `setUp()`) он ловит; точнее было бы сверять `state()` с состоянием только что заведённой задачи, а `git("rev-parse", "--abbrev-ref", "HEAD")` — с `config.MAIN_BRANCH`.

## Пути обхода гейтов
- **E-1. Планка выносится из `tests/`** — это путь A-1. Защита фикстур живёт только в планке задачи, файл `tests/` формально проходит AC-9, а после мержа регрессию фикстур не ловит ни один тест полного прогона.
- **E-2. Подключение на настоящем дереве никем не проверяется.** По решению ТЗ п.2 собственные тесты на подключение не опираются, а AC-7 проверяет временный проект. Значит, ни один тест после мержа не покраснеет, если строку `pytest_plugins` из корневого `conftest.py` потеряют или сломают. Это выбор Оператора в ТЗ (п.2), поэтому как отклонение не поднимается; отмечено для гейта: потерю подключения заметит только первая планка, которая возьмёт фикстуру без явного импорта.
- **E-3. Текст причины — константа** — путь B-1/C-2: требование 2 выполнено буквально, причина сбоя уборки в отчёт не попадает.
- **E-4. AC-6 внутри процесса.** Если тест AC-6 проверяет импорт в процессе прогона, а не в подпроцессе, `tests.sandbox` там уже импортирован другими тестами, и проверка вырождается. Формулировка AC-6 («в процессе, где `tests.sandbox` ещё не импортирован») это закрывает; отклонением не считается.

## Вердикт
**concerns.** Все отклонения правятся формулировкой AC или требований на гейте SPEC; возвращать SPEC аналитику не нужно.

1. **A-1 / E-1** (`SPEC.md`, «Требования» п.8 и AC-9): содержание тестов ТЗ п.3 (а)–(е) не привязано к новому файлу `tests/`. Достаточно дописать в AC-9: «новый файл `tests/` покрывает AC-2…AC-8».
2. **B-1 / C-2 / E-3** (`SPEC.md`, «Требования» п.2–3, AC-4; основание — проба `doCleanups()` на Python 3.13.12): «текст причины» нельзя получить из возврата `doCleanups()`, а AC-4 его не проверяет. Вопрос Оператору: требовать ли, чтобы сообщение `RuntimeError` называло класс песочницы и исключение упавшего действия уборки, а AC-4 проверял это через `match=`; и что делать с ошибкой уборки в пути падения `setUp()`.
3. **C-1** (`SPEC.md`, AC-1; `tests/sandbox.py:1765`, `:2011`, `:2124`): «экземпляр соответствующего класса» пропускает подмену подклассом. Нужно «ровно этого класса».
4. **B-2** (`SPEC.md`, «Материалы», Приложение 1; `tests/__init__.py:12`, `tests/direct_git.py:42-72`): комментарий приложения «подключение не меняет состояние процесса» неточен — на macOS меняется `PATH` всех прогонов дерева артели. Решение Оператора: принять как безвредное или поправить текст комментария (приложение — его текст).
