Пробелы:
- **О-7** — ни один AC не проверяет `manual`-задание из
  `ci_required_jobs` (см. «ТЗ и SPEC»).
- **О-8 — порядок стадий.** Требование 6 (SPEC.md:133-134) задаёт
  порядок стадий как «порядок их первого появления в выдаче заданий».
  Выдача `GET /projects/:id/pipelines/:id/jobs` упорядочена по id
  задания, а не по стадиям: она не несёт индекса стадии. Насколько я
  знаю GitLab, по умолчанию это порядок по убыванию id (это знание о
  внешнем API, кодом пульта не проверяется). Тогда «первое появление»
  переворачивает стадии: `created` в поздней стадии окажется «раньше»
  `manual`. Фикстуры AC-4 и AC-5 составит сам исполнитель в том порядке,
  в котором написан его код, поэтому инверсия тестом не ловится. Цена
  ошибки в одну сторону — ложный `green`: задание `created` перед
  `manual` сочтут стоящим «за ручным». Устойчивое правило — порядок стадий
  по наименьшему id задания стадии (задания создаются при создании
  конвейера в порядке стадий) плюс AC с фикстурой в порядке выдачи
  GitLab. Решение за Оператором.

## Пути обхода гейтов
- **П-4 (О-7).** Если исполнить SPEC.md:131 буквально, обязательное
  ручное задание из `ci_required_jobs` даёт `green`, и смысл
  `ci_required_jobs` (шаг Б1) обходится.
- **П-5 (О-8).** Фикстуры AC-4 и AC-5 в «удобном» порядке стадий
  проходят, а на настоящей выдаче GitLab правило «за ручным» работает
  наоборот.
- **П-6 (О-9).** Запись `EXEMPT` без названной функции позволяет
  освободить широкую функцию `forge.py` (например, `pipeline_status`) и
  разместить в ней сравнение `forge == "gitlab"`, которое проверяет уже
  поддержку, а не выбирает реализацию. Матрица называет запись «местом
  реестра», но функцию не указывает.
- Наблюдение, не отклонение SPEC (ТЗ и ADR-0029 п. 8 говорят «конвейеры
  ровно этого sha»): у конвейера merged results sha — это коммит
  слияния, а не голова ветки. Запрос `pipelines?sha=<голова>` его не
  вернёт, и красный MR-конвейер такого вида на итог не повлияет. Для
  А1 вреда нет (`SUPPORTED_FORGES` закрыт, мерж — гейт людей). Вопрос
  стоит к Б1/В1.

## Вердикт
**concerns.** Отклонения О-1…О-6 прошлого аудита закрыты решениями гейта
и редакцией SPEC. Каждое новое отклонение снимается строкой решения
Оператора или точечной правкой SPEC; невыполнимых требований нет.

1. **О-7, `manual` из `ci_required_jobs`.** SPEC.md:131-135 и :506
   расходятся с ТЗ п. 2 («`created`/`skipped`/`manual` … не перечислены в
   `policy.ci_required_jobs`»), и AC на этот случай нет. Предложение:
   задание `manual`, перечисленное в `ci_required_jobs`, даёт не `green`
   (`running` или `unknown`), плюс AC.
2. **О-8, порядок стадий.** SPEC.md:133-134 выводит порядок стадий из
   порядка выдачи заданий, который у GitLab идёт по id, а не по стадиям.
   AC-4/AC-5 инверсию не ловят. Предложение: порядок стадий — по
   наименьшему id задания стадии, плюс AC с фикстурой, где задания идут
   в порядке убывания id.
3. **О-9, форма записи `EXEMPT`.** SPEC.md:59 и матрица SPEC.md:626:
   пара `EXEMPT` — это (файл, функция) (origin/main
   unsupported_project.py:418-423, :461-464), а функция реестра не
   названа. При реестре-словаре запись не нужна вовсе. Предложение:
   назвать функцию или записать «запись только если реестр выбирает
   реализацию сравнением, в одной названной функции».
