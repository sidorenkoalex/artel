## Пути обхода гейтов
- **П-1 (О-3), диспетчер в обход сторожа А0 AC-9.** Сторож ловит только
  `ast.Compare` поля `forge` с `ast.Constant`-литералом (origin/main
  …unsupported_project.py:444-470). Буквально исполняя «Функции выбирают
  реализацию по полю `forge`» (SPEC.md:33-34), разработчик либо красит
  сторож (`entry["forge"] == "gitlab"` в `forge.py`/`ci.py`), либо
  обходит его: `forge == GITLAB` с именованной константой или
  `{"gitlab": …}.get(entry["forge"])`. Обходной приём одинаково годится и
  для проверки поддержки, ради запрета которой сторож и написан.
  Расширение `EXEMPT` — правка теста А0, а SPEC.md:465-466 требует для неё
  эскалации. SPEC обязан назвать допустимую форму выбора реализации,
  например одну таблицу «forge → модуль» в `forge.py`, без проверок
  поддержки, или мандат на дополнение `EXEMPT` поимённо.
- **П-2, единственная точка запроса без структурной проверки.** AC-1/AC-2
  проверяют функцию запроса. Но ни один AC не требует, чтобы это был
  единственный вызов `urllib` в `gitlab_adapter.py`/`forge.py`. Помощник,
  который зовёт `urllib.request.urlopen` напрямую, например для скачивания
  отчёта, обходит белый список. Функциональные тесты на подменённом
  транспорте это поймают только для функций с ожидаемыми данными. Можно
  добавить AC: в модулях адаптера нет иного вызова HTTP, кроме функции
  запроса (разбор `ast`), либо транспорт подменяется на уровне `urllib` и
  тест ловит обход.
- **П-3 (О-2), ложный `green` по видимым заданиям.** См. «Проверяемость»:
  итог считается по `/jobs`, а статус конвейера (`failed` при скрытых
  мостах) не учитывается.

## Вердикт
**concerns.** Решить отклонения может Оператор на гейте: каждое снимается
строкой решения или правкой SPEC. Невыполнимых требований нет. Перечень:

1. **О-1 (Ф-1), неверный факт о тесте А0** — SPEC.md:463-465 против
   tests/sandbox.py:656-670, :1619 и origin/main
   tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:60-66,
   :346-386. Токен в песочнице получен, и после части 2 `doctor.all_checks`
   в `test_ac7` пойдёт живым HTTP на `https://localhost`. Нужно решение:
   (а) часть 2 подменяет транспорт GitLab по умолчанию в
   `isolate_keychain_and_role`/`tests/sandbox.py` (правка помощника — под
   гейтом неослабления); (б) правка теста А0 по мандату; (в) принять живой
   отказ соединения как есть.
2. **О-2, статус конвейера и мосты** — SPEC.md:84-108 (треб. 6), :101-102.
   `green` не требует согласия со статусом самого конвейера, а задания
   `trigger:` в `/jobs` не видны. Конвейер `failed` с видимыми `success`
   даёт `green`, хотя ADR-0029 п.8 говорит «неполный статус — не зелёный».
   Сюда же — постраничное чтение и сверка `X-Total` для списка конвейеров
   sha. Предлагаемое правило: статус конвейера `failed` → `red`/`unknown`,
   никогда не `green`; плюс AC на это.
3. **О-3, сторож А0 AC-9 и форма диспетчера** — SPEC.md:33-34, треб. 10,
   треб. 11 против origin/main
   …unsupported_project.py:411-520 (`EXEMPT` :418-423). SPEC не называет
   сторож и допустимую форму выбора реализации (П-1).
4. **О-4, отображение итогов для github** — SPEC.md:50-52, AC-13
   (SPEC.md:244-250). Соответствие check runs итогам
   `green`/`red`/`running`/`none`/`unknown` не задано, и AC-13 пропускает
   `pipeline_status` с постоянным `green` для github. Шаги Б1/В1 будут на
   него опираться.
5. **О-5, пустые клетки таблицы треб. 10** — SPEC.md:137
   (`running` → `failed_check_names` «—») и :139 (`unknown` →
   `verifying_status` «не GREEN и не RED»). Потребитель `ci_rerun.py:274`,
   :289 зовёт `failed_check_names` и для вершины main, которая может быть
   `running`. Сейчас вреда нет, потому что `trigger_rerun` для gitlab
   отказывает, но контракт не определён. Для `unknown` лучше назвать один
   вид (`VERIFYING_NONE`).
6. **О-6 (П-2), нет AC на единственность точки HTTP** в модулях адаптера
   (SPEC.md:66-83, AC-1/AC-2).

Мелкие замечания, не блокируют: значение `TOKEN_EXPIRY_WARN_DAYS` нигде не
задано (треб. 14); не сказано, как классифицируется отказ соединения и
