# SPEC-AUDIT: GitLab А1 — адаптер хостинга: общий интерфейс, реализация GitLab, проверочная команда только на чтение

Сверка шла по рабочему каталогу (HEAD 58d9b72) и, для фактов А0
(`targets.SUPPORTED_FORGES`, `unsupported_reason`, строка doctor
`project-support-*`), по `origin/main` (5705cfd): А0 смержен в main, но в
рабочий каталог ещё не подтянут. ANSWER-n и решений Оператора на гейте SPEC
у задачи нет.

## ТЗ и SPEC

ТЗ → SPEC: требования 1–5 и критерии ТЗ перенесены почти дословно
(SPEC.md:31-99, AC-1…AC-15). При этом SPEC перенёс без разрешения
противоречия, которые были в самом ТЗ. Разрешить их SPEC обязан: дальше их
встретит разработчик посреди работы.

1. **Белый список (требование 3) против требований 7–8.** Список SPEC.md:53-60
   (дословно из ТЗ) разрешает чтение конвейеров *по sha*, заданий, отчётов,
   MR, пользователя токена, сведений о токене, защищённых веток и тегов, а
   «участников» прямо запрещает. Требования при этом ждут вот чего:
   - `check_base_branch` для GitLab сверяет базовую ветку «через адаптер»
     (SPEC.md:82-85, AC-14). Ветка проекта по умолчанию в API v4 есть только
     в `GET /projects/:id` (`default_branch`), а чтения проекта в списке нет.
     Ни одна функция интерфейса требования 1 (SPEC.md:33-44) не отдаёт базу
     проекта.
   - `forge-probe` печатает «роль пользователя токена в проекте»
     (SPEC.md:90, AC-15). Роль берётся либо из `GET /projects/:id`
     (`permissions`, чтения проекта в списке нет), либо из
     `GET /projects/:id/members/all/:user_id` (это «участники», они
     запрещены).
   - `forge-probe` печатает «последний конвейер базовой ветки»
     (SPEC.md:91, AC-15). Это `GET /projects/:id/pipelines?ref=<base>`,
     то есть чтение по ref, а не «по sha». Интерфейс такой функции тоже не
     даёт: `pipeline_status(target, sha)` требует sha, а sha базы из
     хостинга прочесть нечем, потому что ветки запрещены.

   Выходит, что AC-14 и AC-15 буквально не выполнить, не добавив в белый
   список пар сверх требования 3 («любая другая пара — отказ», SPEC.md:57-60)
   и функций сверх требования 1. ADR-0029 п. 8
   (docs/adr/0029-external-delivery-via-mr.md:63) перечисляет белый список
   ещё уже и тоже без чтения проекта. Значит, расширение — вопрос Оператору,
   а не выбор исполнителя.
2. **ADR-0029 п. 8 «Неполный статус — не зелёный (инвариант 19)»**
   (docs/adr/0029-external-delivery-via-mr.md:62) в требование 4 SPEC
   (SPEC.md:61-72) не попал. Правила SPEC не говорят, какой итог дают:
   задание или конвейер `canceled`, статусы `waiting_for_resource`,
   `preparing`, `scheduled` и неизвестные, а также неполная выдача заданий.
   У `GET /pipelines/:id/jobs` по умолчанию `per_page=20`. Для GitHub тот же
   класс поломки закрыт постраничным чтением со сверкой `total_count`
   (orchestrator/ci.py:8-10). Для GitLab требования нет, значит нет и теста.
3. **Срок токена.** ADR-0029 п. 8 (стр. 64): токен без срока даёт
   «предупреждение после порога числа задач проекта». ТЗ и SPEC
   (SPEC.md:87-88) говорят «информационно». ТЗ здесь сужает ADR, SPEC
   следует ТЗ. Отклонением не считаю, отмечаю для Оператора.

SPEC → ТЗ: лишних требований нет. Уточнения SPEC укладываются в ТЗ и
допустимы: исходы `check_base_branch` (SPEC.md:83-85), отказ правки MR по
полю `state_event` (AC-2), сохранение `test_doctor.py:670` без правки
(SPEC.md:273-277, 293-298).

## Пути обхода гейтов

1. **Пустой зелёный при неполной выдаче.** Буквально по требованию 4
   функция читает первую страницу заданий (20 по умолчанию) и даёт `green`,
   хотя упавшее задание — на второй странице. Ни одно требование и ни один
   AC этого не запрещают, а инвариант 19 и ADR-0029:62 запрещают.
2. **Расширение белого списка «по нужде» в части 2.** Чтобы выполнить
   AC-14/AC-15, разработчик добавит `GET /projects/:id` или
   `GET /projects/:id/members/...` в таблицу пар. Последнее — категория
   «участники», которую требование 3 запрещает. Тест AC-1 этого не поймает:
   там нет пары чтения участников.
3. **Правка MR «полем черновик (заголовок)».** Белый список, сверяющий
   только имя поля `title`, пропускает любую смену заголовка, а не только
   префикс `Draft:`. AC-2 разрешённым считает само поле. Риск мал (не
   слияние и не закрытие), но смысл «только черновик» не держится.
   Достаточно оговорить, что разрешена лишь смена префикса черновика.
4. **Отказ `trigger_rerun` как «запущен».** Текст «не поддержано для
   gitlab» без «не запущен» `ci.rerun_started` прочтёт как запущенный
   повтор, и `ci-rerun` пойдёт читать новый статус (см. матрицу).
5. **`head_sha` с фиктивным HTTP.** Чтобы буквально выполнить AC-13,
   исполнитель добавит лишний сетевой вызов, которого не требует
   поведение. Это либо чтение веток вопреки белому списку, либо обход
   смысла AC.
