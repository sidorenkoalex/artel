# SPEC: GitLab А1 — адаптер хостинга: общий интерфейс, реализация GitLab, проверочная команда только на чтение

## Контекст
Сейчас хостинг проекта — только GitHub через `gh`. Внешние входы
`orchestrator/ci.py`: `verifying_status`, `main_line_status`,
`branch_status`, `head_sha`, `failed_check_names`, `trigger_rerun`,
`accepted_full_suite`, `find_run_id`, `check_run_workflow_run`, `gh`.
Входы `orchestrator/github_adapter.py`: `ensure_draft_mr`, `undraft_mr`,
`ensure_head_in_origin`; `_is_github_target` пропускает не-GitHub. Для
не-GitHub `doctor/misc_checks.py:check_base_branch` отдаёт `skip`.
ADR-0029 (принят 26.10.2026), п. 8 вводит проект на GitLab. Шаг А1 —
адаптер хостинга, он идёт после А0 (`targets.unsupported_reason`). Токен
проекта лежит в слоте связки ключей `token_slot` записи; для `gh` он
передаётся как `GH_TOKEN` (`doctor/misc_checks.py::gh_env`). Внешние
HTTP-адреса в тестах запрещает сторож
`tests/test_invariants.py::NoNetworkAddressesInTestsTest`, поэтому сеть в
тестах — только подменой. Требования ниже учитывают ответ Оператора
ANSWER-1 (решения 1A, 2A, 3A, 4A, 5A, 6A, 7A, 8A, 9A, 10A, 11A, 12B, 13A)
и решения гейта SPEC 26.10 по отклонениям аудита (О-1…О-6 и мелкие
замечания).

## Требования

1. **Интерфейс адаптера** — новый модуль `orchestrator/forge.py`. Функции
   выбирают реализацию по полю `forge` записи проекта:
   - `pipeline_status(target, sha)` — итог CI ровно этого sha (`green` /
     `red` / `running` / `none` / `unknown`, у не-`green` есть причина) и
     список заданий с именами и статусами;
   - `job_result(target, sha, job_name)` — статус задания с этим именем в
     конвейере этого sha;
   - `job_test_report(target, sha, job_name)` — разобранный отчёт тестов
     задания (идентификатор теста → исход) либо `None` с причиной;
   - `open_mr(target, branch, base, title, body, draft, assignee)`,
     `undraft_mr(target, mr)`, `assign_mr(target, mr, assignee)`,
     `mr_status(target, mr)`;
   - только чтение: `token_user(target)`, `token_expiry(target)`,
     `protections(target)`; «сведения проекта» — ветка проекта по
     умолчанию и уровень доступа пользователя токена в проекте;
     «последний конвейер ветки» — sha, итог и задания последнего конвейера
     названной ветки.

   Выбор реализации (решение гейта SPEC 26.10, О-3) — один реестр в
   `forge.py`, ключи которого — значения поля `forge`. `ci.py`, `doctor` и
   прочие потребители выбирают реализацию через `forge`. Иных сравнений
   значения `forge` с литералами `"github"`/`"gitlab"` эта задача не
   добавляет. Сторож А0
   `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py::test_ac9_no_support_literals_outside_targets`
   дополняется в `EXEMPT` одной записью для `forge.py` — места реестра.
   Это правка долгоживущего теста задачи эпика А0 по мандату Оператора
   26.10 с матрицей неослабления (раздел ниже). Других правок этого файла
   нет.
2. **Реализация GitHub в `forge`** (ANSWER-1, п. 2; решение гейта SPEC
   26.10, О-4).
   `pipeline_status` для `forge: github` оборачивает нынешнее чтение check
   runs из `ci` и не меняет поведение и вывод `ci`. Итог по check runs
   коммита, в порядке проверки:
   - есть run с исходом `failure`, `cancelled` или `timed_out` — `red`;
   - есть run со статусом `queued` или `in_progress` — `running`;
   - check runs нет — `none`;
   - все runs завершены с исходом `success`, `skipped` или `neutral` —
     `green`;
   - всё прочее (иной исход или статус, чтение не удалось) — `unknown`.

   Все остальные функции
   `forge` для `forge: github` возвращают именованный отказ «не
   реализовано для github» и `gh` не вызывают. GitHub-потребители
   по-прежнему зовут `ci`/`github_adapter` напрямую. Внешние входы `ci.py`
   и `github_adapter.py` сохраняют сигнатуры и для GitHub работают как
   сейчас.
3. **Реализация GitLab** — новый модуль `orchestrator/gitlab_adapter.py`.
   Запросы идут к HTTP API v4 средствами стандартной библиотеки, без новых
   зависимостей. Адрес сервера и путь проекта берутся из `url` записи,
   токен — из слота `token_slot`. Токен передаётся заголовком
   `PRIVATE-TOKEN` и не попадает в журнал, вывод и сообщения ошибок.
4. **Без токена — без запроса** (ANSWER-1, п. 9). Если токен не получен
   (у записи нет слота, связка ключей отказала, слот пуст, вызов из
   процесса роли), адаптер не делает запроса и отдаёт именованную причину.
5. **Единственная функция запроса** `gitlab_adapter` с таблицей
   разрешённых пар «метод — шаблон пути». Разрешено:
   - чтение конвейеров по sha;
   - чтение конвейеров ветки (`GET /projects/:id/pipelines?ref=<ветка>`);
   - чтение проекта (`GET /projects/:id`); из ответа используются только
     `default_branch` и уровень доступа токена из `permissions`;
   - чтение заданий конвейера, отчёта тестов конвейера или задания, MR,
     пользователя токена, сведений о токене, защищённых веток и тегов;
   - создание MR;
   - правка MR только двумя полями. «Исполнитель» — любое значение.
     «Черновик» — заголовок, причём новый заголовок может отличаться от
     текущего только наличием или отсутствием префикса `Draft: `.

   Любая другая пара — отказ до отправки запроса, с именем пары. Сюда
   входят слияние, закрытие MR, комментарии, запуск, повтор и отмена
   заданий, теги, релизы, ветки, настройки, переменные, участники
   (`/members…`). Правка заголовка MR с иной сменой текста — тоже отказ до
   отправки запроса правки.

   Сеть (решение гейта SPEC 26.10, О-6): `urllib` и `http.client`
   вызываются только в одной функции транспорта `gitlab_adapter`. Эту
   функцию тесты и подменяют. Транспорт вызывается только функцией
   запроса. В `forge.py` и в остальном `gitlab_adapter.py` нет других
   вызовов `urllib`/`http.client`.
6. **Зелёный CI на GitLab** (ADR-0029 п. 8; ANSWER-1, пп. 5–6), итог
   `pipeline_status`:
   - берутся все конвейеры ровно этого sha. Если их несколько (ветка и
     MR), `green` только при зелёных всех. Список конвейеров sha читается
     постранично до конца, число сверяется с заголовком `X-Total`; обрыв
     чтения или расхождение чисел — `unknown`;
   - статус самого конвейера (решение гейта SPEC 26.10, О-2): `green`
     возможен, только если статус конвейера `success` или `manual` (стоит
     на ручном задании) и задания удовлетворяют правилам ниже. Конвейер
     `failed` — `red`, даже если все видимые задания `success` (задания-мосты
     `trigger:` в выдаче заданий не видны). Конвейер `running`, `pending`,
     `waiting_for_resource`, `preparing` или `scheduled` — `running`: это
     те же идущие статусы, что у заданий (ANSWER-1, п. 5), а «иной» статус
     решения гейта — статус, не названный в этом требовании.
     Конвейер `canceled` или с любым иным статусом — `unknown`. Ни в одном
     из этих случаев итог не `green`;
   - `green` требует, чтобы все завершённые задания без права падать были
     `success`;
   - задание `manual` допустимо. Задание `created` или `skipped` допустимо,
     только если в том же конвейере есть задание `manual` в более ранней
     стадии. Порядок стадий — порядок их первого появления в выдаче
     заданий. Кроме того, допустимое задание не должно быть перечислено в
     `policy.ci_required_jobs` записи (поле читается, если есть; его
     объявление — шаг Б1);
   - есть `failed` без права падать — `red`;
   - есть `running`, `pending`, `waiting_for_resource`, `preparing` или
     `scheduled` — `running`;
   - у sha нет конвейера — `none` с причиной «конвейер не создан (ветка не
     под правилом workflow?)»;
   - итог `unknown` с причиной дают: `canceled` у задания без права падать
     или у конвейера; статус задания или конвейера, не названный в этом
     требовании; неполная выдача. Задания читаются постранично до конца,
     их число сверяется с заголовком `X-Total`; если чтение страницы
     оборвалось или числа не сошлись — `unknown`. `unknown` и `none`
     никогда не `green`;
   - упавшее задание с правом падать даёт пометку в итоге с именем
     задания (для ревьюера).
7. **`job_result`** (ANSWER-1, п. 13) — статус задания с запрошенным
   именем. Если такого задания в конвейерах sha нет — именованная
   причина. Если у имени несколько попыток (повторы) — статус последней.
8. **`job_test_report`** (ANSWER-1, п. 7) — разбирает отчёт тестов GitLab
   (`test_suites[].test_cases[]`). Идентификатор теста —
   `<classname>::<name>`, значение — исход. Если ключи в одном отчёте
   совпали — `None` с причиной «неоднозначный идентификатор». Если отчёта
   нет или он истёк — `None` с причиной.
9. **Ошибки HTTP** GitLab (401, 403, 404, 429, 5xx, таймаут) — именованные
   причины, не исключения. Повтор — только на 429 и 5xx, с ограниченным
   числом попыток. Прочие `URLError` и отказ соединения (решение гейта
   SPEC 26.10) — именованная причина «сеть недоступна: <текст>»; для
   `pipeline_status` это итог `unknown` с этой причиной.
10. **Подключение `ci` для `forge: gitlab`** (ANSWER-1, пп. 3, 8, 10):
    - `verifying_status`, `branch_status` и `failed_check_names` берут итог
      через `forge.pipeline_status`. Каждый итог GitLab отображается в те
      же виды, что у GitHub, так, как в таблице ниже;
    - `head_sha` остаётся локальным (`git rev-parse` в клоне), транспорт
      хостинга не вызывается, сигнатура не меняется;
    - `main_line_status`, `trigger_rerun`, `find_run_id` и
      `check_run_workflow_run` возвращают именованный отказ «не поддержано
      для gitlab» и не вызывают `gh`. Отказ `trigger_rerun` содержит
      подстроку «не запущен». `main_line_status` отдаёт вид
      `ci.MAIN_UNKNOWN`. `find_run_id` и `check_run_workflow_run` отдают
      `("", причина)`.

    | Итог `pipeline_status` | `verifying_status` | `verifying_is_red(note)` | `branch_status` | `status_kind(note)` | `failed_check_names` |
    |---|---|---|---|---|---|
    | `green` | `VERIFYING_GREEN` | `False` | `(True, …)` | — | пустое множество |
    | `red` | `VERIFYING_RED`, `note` содержит «CI коммита <sha[:8]> не зелёный:» | `True` | `(False, …)` | `"red"` | имена упавших заданий без права падать |
    | `running` | `VERIFYING_RUNNING` | `False` | `(False, …)`, `note` содержит «ещё идёт» | `"running"` | пустое множество (упавших заданий нет) |
    | `none` | `VERIFYING_NONE` | `False` | `(False, …)`, `note` содержит «неизвестен» | `"unknown"` | `(None, причина)` |
    | `unknown` | `VERIFYING_NONE` | `False` | `(False, …)`, `note` содержит «неизвестен» | `"unknown"` | `(None, причина)` |

    Клетки `running` и `unknown` заданы решением гейта SPEC 26.10 (О-5).
    Для `running` в решении сказано «пустой список». `failed_check_names`
    возвращает множество (`ci.py:1116`), поэтому здесь это пустое
    множество, как у `green`.

    Для `red_status_sha(note)` у красного `note` результат — `sha[:8]`,
    `rerun_started` у отказа `trigger_rerun` — `False`.

## Критерии приёмки

AC-1. Каждая запрещённая пара функции запроса `gitlab_adapter` — отказ до
вызова HTTP: подменённый транспорт не вызван, причина отказа называет
пару. Проверяются пары: слияние MR, закрытие MR, комментарий, запуск
задания, повтор задания, удаление ветки, создание тега, чтение участников
проекта (`/members…`).

AC-2. Каждая разрешённая пара требования 5 доходит до подменённого
транспорта. Это чтение конвейеров по sha и по ветке, проекта, заданий,
отчёта тестов, MR, пользователя токена, сведений о токене, защищённых
веток и тегов; создание MR; правка MR полем «исполнитель»; правка
заголовка, которая добавляет или снимает префикс `Draft: `. Отказ до
отправки запроса правки дают: правка заголовка с иной сменой текста и
правка любым другим полем (например, `state_event`).

AC-3. Если токен не получен (у записи нет `token_slot` или связка ключей
отдала пусто либо отказ), функции `forge` для `forge: gitlab` возвращают
именованную причину, а подменённый транспорт не вызван.

AC-4. `forge.pipeline_status` для GitLab на подменённых ответах API даёт
`green` в двух случаях. Первый — задания `success` и `manual`. Второй —
задание `created` или `skipped` стадией позже задания `manual` того же
конвейера, не перечисленное в `policy.ci_required_jobs`.

AC-5. `pipeline_status` даёт итог не `green` в двух случаях. Первый —
задание `created`, перечисленное в `policy.ci_required_jobs` записи.
Второй — задание `created`, перед которым в более ранней стадии нет
задания `manual`, даже если оно не перечислено в `ci_required_jobs`.

AC-6. `pipeline_status`: задание `failed` без права падать → `red`; задание
`failed` с правом падать (`allow_failure`) → `green` с пометкой, которая
называет это задание.

AC-7. `pipeline_status`:
- у sha два конвейера (ветка и MR), один из них `red` → `red`;
- задание `running`, `pending`, `waiting_for_resource`, `preparing` или
  `scheduled` без `failed` → `running`;
- конвейеров у sha нет → `none` с причиной «конвейер не создан (ветка не
  под правилом workflow?)».

AC-8. `pipeline_status` даёт `unknown` с причиной в шести случаях:
- задание `canceled` без права падать;
- конвейер `canceled`;
- статус задания не из перечисленных в требовании 6;
- статус конвейера не из перечисленных в требовании 6 (например,
  `skipped`), при всех заданиях `success`;
- число прочитанных заданий не совпало с `X-Total`;
- число прочитанных конвейеров sha не совпало с `X-Total`.

Кроме того, задание `failed` на второй странице выдачи даёт `red`, а не
`green`: проверяется число вызовов транспорта по страницам. Конвейер
`red` на второй странице списка конвейеров sha тоже даёт `red`.

AC-9. `forge.job_result` для GitLab в конвейере с двумя заданиями разных
статусов возвращает статус задания с запрошенным именем. Если задания с
таким именем нет — именованная причина. Если у имени несколько попыток —
статус последней.

AC-10. `forge.job_test_report` для GitLab разбирает фикстуру отчёта тестов
GitLab в отображение `<classname>::<name>` → исход. Два теста с одинаковым
`name` в разных `classname` дают два разных ключа. Совпадение ключей в
одном отчёте даёт `None` с причиной «неоднозначный идентификатор».
Отсутствующий или истёкший отчёт даёт `None` с причиной.

AC-11. Ответы 401, 403, 404, 429, 5xx и таймаут транспорта — именованные
причины, а не исключения. На 429/5xx запрос повторяется ограниченное число
раз, на 401/403/404 — не повторяется. Проверяется по числу вызовов
подменённого транспорта.

AC-12. Фикстурное значение токена не встречается в журнале шагов, выводе
`doctor`, выводе `forge-probe` и тексте именованных причин ошибок (включая
401/403).

AC-13. `forge.pipeline_status` для `forge: github` берёт итог из чтения
check runs `ci` (подменённого) и не вызывает транспорт GitLab. На
подменённых check runs итоги такие (требование 2):
- все runs `completed` с исходами `success`, `skipped`, `neutral` — `green`;
- один run `failure` (то же для `cancelled` и `timed_out`) при остальных
  `success` — `red`;
- один run `in_progress` (то же для `queued`) при остальных `success` —
  `running`;
- пустой список runs — `none`;
- run с исходом `action_required` при остальных `success` — `unknown`;
- чтение check runs не удалось — `unknown`.

Реализация с постоянным `green` на непустом ответе этот критерий не
проходит. Остальные
функции `forge` для `forge: github` (`job_result`, `job_test_report`,
`open_mr`, `undraft_mr`, `assign_mr`, `mr_status`, `token_user`,
`token_expiry`, `protections`, сведения проекта, последний конвейер ветки)
возвращают именованный отказ «не реализовано для github», не вызывая ни
`gh`, ни транспорт GitLab.

AC-14. Для записи `forge: gitlab` на подменённом транспорте каждый итог
`pipeline_status` (`green`, `red`, `running`, `none`, `unknown`) даёт
значения `ci.verifying_status`, `ci.verifying_is_red`,
`ci.red_status_sha`, `ci.branch_status`, `ci.status_kind` и
`ci.failed_check_names` по таблице требования 10; `gh` не вызван. Ни
`none`, ни `unknown`, ни `red` не дают `VERIFYING_GREEN` и не дают
`branch_status` = `True`. Итог `unknown` даёт ровно `VERIFYING_NONE`;
итог `running` даёт `failed_check_names` = `(set(), …)`. `ci.head_sha` для `forge: gitlab` читает голову
локально и транспорт не вызывает; сигнатура `head_sha` не изменена.

AC-15. Для записи `forge: gitlab` функции `ci.main_line_status`,
`ci.trigger_rerun`, `ci.find_run_id` и `ci.check_run_workflow_run`
возвращают именованный отказ «не поддержано для gitlab». Они не обращаются
ни к `gh`, ни к HTTP. Кроме того:
- отказ `trigger_rerun` содержит «не запущен», и `ci.rerun_started` на нём
  даёт `False`;
- `main_line_status` отдаёт вид `ci.MAIN_UNKNOWN`;
- `find_run_id` и `check_run_workflow_run` отдают `("", причина)`.

AC-16. `doctor.check_base_branch` для `forge: gitlab` на подменённом API
сверяет базу записи с `default_branch` проекта. Совпадает — `ok`,
расходится — `warn`. Без токена — `skip` с именованной причиной, транспорт
не вызван.

AC-17. Строка `doctor` о сроке токена GitLab на подменённом API:
- срок через `TOKEN_EXPIRY_WARN_DAYS` дней или меньше — `warn`;
- срок дальше порога — не `warn`;
- токен без срока при числе задач проекта меньше
  `TOKEN_NO_EXPIRY_TASKS_WARN` — информационная строка, не `warn`;
- токен без срока при числе задач проекта не меньше порога — `warn`.

AC-18. `forge-probe <проект> --job <имя>` на подменённом API печатает
пользователя токена и уровень доступа, срок токена, защищённые ветки и
теги, последний конвейер базовой ветки (sha, итог, задания) и сводку
отчёта тестов по исходам. Все вызовы транспорта за прогон — метод `GET`.
Команда работает для записи с неподдержанным хостингом.

AC-19. `pipeline_status` для GitLab по статусу самого конвейера
(требование 6):
- конвейер `failed`, все видимые задания `success` → `red`;
- конвейер `manual`, задания `success` и `manual` → `green`;
- конвейер `running`, все видимые задания `success` → `running`, не
  `green`.

AC-20. В `orchestrator/forge.py` и `orchestrator/gitlab_adapter.py`
обращения к `urllib` и `http.client` стоят только внутри одной функции
транспорта `gitlab_adapter`, а саму функцию транспорта вызывает только
функция запроса. Проверяется разбором `ast` обоих модулей. Сторож ловит
вставленный вне транспорта вызов `urllib.request.urlopen` и вызов
транспорта из функции, которая не является функцией запроса.

AC-21. В тесте под `tests/sandbox.py::isolate_keychain_and_role`, который
не подменил транспорт `gitlab_adapter` сам, запрос адаптера к записи
`forge: gitlab` с полученным токеном песочницы не открывает сетевого
соединения. Проверяется подменой `socket.create_connection`, которая
фиксирует вызов. Запрос возвращает именованную причину, а строка
`doctor.check_base_branch` для такой записи — `skip`. Транспорт,
подменённый самим тестом, вызывается вместо подмены песочницы.

AC-22. Подменённый транспорт поднимает `URLError` (отказ соединения).
Функции адаптера возвращают причину, которая начинается с «сеть
недоступна:», а не исключение. `pipeline_status` даёт `unknown` с этой
причиной.

Рамка: $50

Часть 1 деления задачи 01M5W670PHF08VPZWDRM5BY56W (ADR-0029 п. 8; шаг А1
после А0 — `targets.unsupported_reason`). Требования и критерии взяты из
SPEC родителя с учётом ANSWER-1 родителя и решений его гейта SPEC 26.10
(О-2…О-6): требования 1–10 и 14; AC-1…AC-15, AC-19, AC-20, AC-22. AC-12
здесь проверяет журнал и тексты причин ошибок; вывод
`doctor`/`forge-probe` проверяет часть 2.

Требуется:
1. Модуль `orchestrator/forge.py`. Реализация выбирается одним реестром в
   `forge.py`, ключи которого — значения поля `forge`; `ci.py` выбирает
   реализацию через `forge`. Иных сравнений значения `forge` с литералами
   `"github"`/`"gitlab"` нет. В `EXEMPT` сторожа А0
   `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py::test_ac9_no_support_literals_outside_targets`
   добавляется одна запись для `forge.py` как места реестра. Это правка
   долгоживущего теста задачи эпика А0 по мандату Оператора 26.10 с
   матрицей неослабления SPEC родителя; других правок этого файла нет.
   Функции:
   - `pipeline_status(target, sha)` — итог
     `green`/`red`/`running`/`none`/`unknown` с причиной и задания с
     именами и статусами;
   - `job_result(target, sha, job_name)`;
   - `job_test_report(target, sha, job_name)` — «идентификатор теста →
     исход» или `None` с причиной;
   - `open_mr(target, branch, base, title, body, draft, assignee)`,
     `undraft_mr(target, mr)`, `assign_mr(target, mr, assignee)`,
     `mr_status(target, mr)`;
   - только чтение: `token_user(target)`, `token_expiry(target)`,
     `protections(target)`, «сведения проекта» (ветка по умолчанию и
     уровень доступа токена), «последний конвейер ветки» (sha, итог,
     задания).
2. Реализация GitHub. `pipeline_status` оборачивает нынешнее чтение check
   runs `ci` без изменения его поведения. Итог по check runs, по порядку:
   есть `failure`/`cancelled`/`timed_out` — `red`; есть
   `queued`/`in_progress` — `running`; check runs нет — `none`; все
   `success`/`skipped`/`neutral` — `green`; иное — `unknown`. Остальные
   функции — именованный
   отказ «не реализовано для github», `gh` не вызывается. Внешние входы
   `ci.py`/`github_adapter.py` сохраняют сигнатуры и поведение для GitHub.
3. Модуль `orchestrator/gitlab_adapter.py`: HTTP API v4 средствами
   стандартной библиотеки. Сервер и путь проекта — из `url` записи. Токен
   — слот `token_slot`, заголовок `PRIVATE-TOKEN`; в журнал, вывод и
   сообщения ошибок он не попадает. Если токен не получен (нет слота,
   отказ, пустой слот, процесс роли), запроса нет, возвращается
   именованная причина.
4. Единственная функция запроса с таблицей разрешённых пар «метод —
   шаблон пути». Разрешено:
   - чтение конвейеров по sha;
   - чтение конвейеров ветки (`GET /projects/:id/pipelines?ref=`);
   - чтение проекта (`GET /projects/:id`), из ответа используются только
     `default_branch` и `permissions`;
   - чтение заданий, отчёта тестов, MR, пользователя токена, сведений о
     токене, защищённых веток и тегов;
   - создание MR;
   - правка MR: «исполнитель» и заголовок, причём заголовок может только
     получить или потерять префикс `Draft: `.

   Иная пара (в том числе участники `/members…`) или иная смена заголовка
   — отказ до отправки запроса, с именем пары. `urllib`/`http.client`
   вызываются только в одной функции транспорта `gitlab_adapter`, которую
   подменяют тесты; транспорт вызывается только функцией запроса.
5. Зелёный CI:
   - берутся конвейеры ровно этого sha; если их несколько — зелёными
     должны быть все. Список конвейеров sha читается постранично со
     сверкой числа с `X-Total`;
   - статус самого конвейера: `green` возможен только при `success` или
     `manual` и при соблюдении правил заданий ниже; `failed` — `red`
     (даже при всех видимых заданиях `success`);
     `running`/`pending`/`waiting_for_resource`/`preparing`/`scheduled`
     — `running`; `canceled` или иной статус — `unknown`; ни в одном из
     этих случаев не `green`;
   - завершённые задания без права падать — `success`;
   - `manual` допустимо; `created`/`skipped` допустимо, только если в том
     же конвейере есть `manual` в более ранней стадии (порядок стадий — по
     первому появлению в выдаче) и задание вне
     `policy.ci_required_jobs` (поле читается, если есть);
   - `failed` без права падать — `red`;
   - `running`/`pending`/`waiting_for_resource`/`preparing`/`scheduled` —
     `running`;
   - конвейера нет — `none` с причиной «конвейер не создан (ветка не под
     правилом workflow?)»;
   - `unknown` с причиной: `canceled` у задания без права падать или у
     конвейера, неизвестный статус задания или конвейера, неполная выдача. Задания читаются
     постранично до конца со сверкой числа с `X-Total`;
   - `unknown` и `none` никогда не `green`;
   - упавшее задание с правом падать — пометка в итоге с именем задания.
6. `job_result`: статус задания с запрошенным именем; если задания нет —
   именованная причина; если попыток несколько — статус последней.
   `job_test_report`: ключ `<classname>::<name>`; совпадение ключей —
   `None` с причиной «неоднозначный идентификатор»; отчёта нет или он
   истёк — `None` с причиной.
7. Ошибки HTTP (401, 403, 404, 429, 5xx, таймаут) — именованные причины.
   Повтор — только на 429/5xx, ограниченно. Прочие `URLError` и отказ
   соединения — причина «сеть недоступна: <текст>»; для `pipeline_status`
   — итог `unknown` с этой причиной.
8. `ci` для `forge: gitlab`:
   - `verifying_status`, `branch_status` и `failed_check_names` берут итог
     через `forge.pipeline_status` и отображают его в виды GitHub по
     таблице требования 10 SPEC родителя. `red` даёт `note` с «CI коммита
     <sha[:8]> не зелёный:». `running` даёт «ещё идёт» и
     `failed_check_names` = пустое множество. `none` и `unknown` дают
     `VERIFYING_NONE` и «неизвестен» и не бывают зелёными;
   - `head_sha` остаётся локальным, транспорт не вызывается;
   - `main_line_status`, `trigger_rerun`, `find_run_id` и
     `check_run_workflow_run` возвращают именованный отказ «не поддержано
     для gitlab» без вызова `gh`. Отказ `trigger_rerun` содержит «не
     запущен». `main_line_status` отдаёт вид `MAIN_UNKNOWN`.
     `find_run_id`/`check_run_workflow_run` отдают `("", причина)`.
9. Константы `TOKEN_EXPIRY_WARN_DAYS = 14`, `TOKEN_NO_EXPIRY_TASKS_WARN =
   10`, число повторов и таймаут живут в `gitlab_adapter.py`/`forge.py`.
   `orchestrator/config.py` не трогать: его зону держит Б1.
   `targets.SUPPORTED_FORGES` не расширяется.

Не входит: `doctor`, команда `forge-probe` и подмена транспорта в
`tests/sandbox.py` (часть 2); создание и снятие
черновика MR в потоке задачи (Б1/Б2); чтение отчётов в гейте по исходам
