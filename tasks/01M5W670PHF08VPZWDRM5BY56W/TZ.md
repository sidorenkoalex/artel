# GitLab, шаг А1: адаптер хостинга — общий интерфейс, реализация GitLab, проверочная команда только на чтение

## Факты

ADR-0029 (принят 26.10.2026), п. 8; шаг А1 после А0 (`targets.unsupported_reason`, именованный отказ для неподдержанного хостинга).

1. Хостинг сейчас — только GitHub через `gh`: `orchestrator/ci.py` (1694 строки; внешние входы — `verifying_status`, `main_line_status`, `branch_status`, `head_sha`, `failed_check_names`, `trigger_rerun`, `accepted_full_suite`, `find_run_id`, `check_run_workflow_run`, `gh`), `orchestrator/github_adapter.py` (`ensure_draft_mr`, `undraft_mr`, `ensure_head_in_origin`; `_is_github_target` — пропуск для не-GitHub). `doctor` — `doctor/misc_checks.py:check_base_branch` (для не-GitHub — `skip`).
2. Токен проекта — слот связки ключей `token_slot` записи; для `gh` подставляется как `GH_TOKEN` (`doctor/misc_checks.py` `gh_env`).
3. Внешние HTTP-адреса в тестах запрещены сторожем `tests/test_invariants.py` `NoNetworkAddressesInTestsTest`; сеть в тестах — только подменой.

## Требуется

1. **Интерфейс адаптера** — модуль `orchestrator/forge.py`: функции по хостингу записи проекта (выбор по полю `forge`):
   - `pipeline_status(target, sha)` — итог CI ровно этого sha (`green` / `red` / `running` / `none` с причиной), список заданий с именами и статусами;
   - `job_result(target, sha, job_name)` — статус задания по имени в конвейере этого sha;
   - `job_test_report(target, sha, job_name)` — разобранный отчёт тестов задания (идентификатор теста → исход) или `None` с причиной (используется шагом В1);
   - `open_mr(target, branch, base, title, body, draft, assignee)`, `undraft_mr(target, mr)`, `assign_mr(target, mr, assignee)`, `mr_status(target, mr)` (используются шагами Б1/Б2);
   - `token_user(target)`, `token_expiry(target)`, `protections(target)` — только чтение (для `doctor` и проверочной команды).
   Реализация GitHub — обёртка над нынешними `ci`/`github_adapter` без изменения их поведения и вывода; внешние входы `ci.py` сохраняют сигнатуры и для GitHub работают как сейчас.
2. **Реализация GitLab** — модуль `orchestrator/gitlab_adapter.py`, HTTP API v4 средствами стандартной библиотеки (без новых зависимостей), адрес сервера и путь проекта — из `url` записи, токен — из слота `token_slot` (заголовок `PRIVATE-TOKEN`, в журнал и вывод не попадает).
   - **Единственная функция запроса** с таблицей разрешённых пар «метод — шаблон пути»: чтение конвейеров по sha, заданий конвейера, отчёта тестов конвейера/задания, MR, пользователя токена, сведений о токене, защищённых веток и тегов; создание MR; правка MR только полями «черновик» (заголовок) и «исполнитель». Любая другая пара (слияние, закрытие MR, комментарии, запуск/повтор/отмена заданий, теги, релизы, ветки, настройки, переменные, участники) — отказ до отправки запроса, с именем пары.
   - **Зелёный CI на GitLab** (ADR-0029 п. 8): конвейеры ровно этого sha (если их несколько — ветка и MR — зелёными должны быть все); все завершённые задания без права падать — `success`; задания `created`/`skipped`/`manual` допустимы, только если стоят за ручным заданием и не перечислены в `policy.ci_required_jobs` записи (поле читается, если есть; объявление поля — шаг Б1); есть `failed` без права падать — `red`; `running`/`pending` — `running`; конвейера нет — `none` с причиной «конвейер не создан (ветка не под правилом workflow?)». Упавшее задание с правом падать — пометка в итоге (для ревьюера).
   - Ошибки HTTP (401, 403, 404, 429, 5xx, таймаут) — именованные причины, не исключения; повтор — только на 429/5xx с ограниченным числом попыток.
3. **Подключение к потребителям — без изменения их поведения для GitHub:** внешние входы `ci.py`, которыми пульт ждёт CI ветки (`verifying_status`, `branch_status`, `head_sha`, `failed_check_names`), для проекта с `forge: gitlab` идут через `forge`/`gitlab_adapter`. `main_line_status`, `trigger_rerun`, `find_run_id` для GitLab — именованный отказ «не поддержано для gitlab» (нужны только режиму `operator`, который для GitLab не поддерживается — п. 5).
4. **`doctor` и проверочная команда.**
   - `check_base_branch` для GitLab — сверка базовой ветки через адаптер (вместо `skip`); строка срока токена: предупреждение за `gitlab_adapter.TOKEN_EXPIRY_WARN_DAYS` дней, токен без срока — информационно.
   - Команда `forge-probe <проект> [--job <имя>]` — только чтение: пользователь токена и его роль в проекте, срок токена, защищённые ветки и теги, последний конвейер базовой ветки (sha, итог, задания), при `--job` — сводка отчёта тестов задания (число тестов по исходам). Ничего не создаёт и не меняет; вызовы — только чтение из белого списка.
5. **Поддержка остаётся закрытой.** `targets.SUPPORTED_FORGES` в этой задаче НЕ расширяется: `forge: gitlab` поддерживается только вместе с `merge_gate: target-human`, а он исполняется шагом Б2 — там и расширение. `forge-probe` и `doctor` работают и для неподдержанной записи (только чтение).

Критерии приёмки:
- белый список: каждая запрещённая пара (слияние MR, закрытие MR, комментарий, запуск задания, повтор, удаление ветки, тег) — отказ до вызова HTTP (подменённый транспорт не вызван); разрешённые пары доходят до транспорта;
- правила зелёного CI — таблица сценариев на подменённых ответах API: `success`+`manual` за ручным → `green`; `created` обязательного задания из `ci_required_jobs` → не `green`; `failed` без права падать → `red`; `failed` с правом падать → `green` с пометкой; два конвейера sha (ветка и MR), один `red` → `red`; конвейера нет → `none` с причиной;
- `job_test_report` разбирает отчёт тестов GitLab (фикстура ответа) в «идентификатор теста → исход»; отчёта нет / истёк — `None` с причиной;
- токен не появляется в журнале, выводе `doctor`/`forge-probe` и сообщениях ошибок (сторож по фикстурному значению токена);
- для GitHub все существующие тесты `ci`, `github_adapter`, `doctor` зелёные без правки, кроме перечисленных в «Существующие тесты»;
- `forge-probe` на подменённом API печатает пользователя, срок, защиты, последний конвейер и сводку отчёта; ни одного запроса вне чтения;
- `main_line_status`/`trigger_rerun`/`find_run_id` для `gitlab` — именованный отказ.
