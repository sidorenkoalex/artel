# QUESTIONS: GitLab А1 — адаптер хостинга: общий интерфейс, реализация GitLab, проверочная команда только на чтение

## Вопросы
Батч — по возврату аудита SPEC (SPEC-AUDIT.md, вердикт fail, 1 из 2).
ТЗ противоречит само себе и ADR-0029 п. 8. Без решения Оператора
SPEC либо нарушает белый список ТЗ, либо требует критерии, которые

1. **Белый список против `doctor`/`forge-probe`.** ТЗ п. 2 разрешает
   чтение конвейеров *по sha* и запрещает «участников». При этом ТЗ
   п. 4 требует трёх вещей. (а) Сверить базовую ветку: в API v4
   `default_branch` отдаёт только `GET /projects/:id`. (б) Показать роль
   пользователя токена в проекте: это поле `permissions` из
   `GET /projects/:id` или `GET /projects/:id/members/all/:user_id`, то
   есть «участники». (в) Показать последний конвейер базовой ветки: это
   `GET /projects/:id/pipelines?ref=<base>`, чтение по ref, не по sha.
   ADR-0029 п. 8 (docs/adr/0029-external-delivery-via-mr.md, «Белый
   список вызовов API GitLab») разрешает «чтение конвейеров» без
   уточнения «по sha». Чтения проекта в нём нет. Какие пары чтения
   добавить?
   - A) Добавить две пары только на чтение: `GET /projects/:id` (из
     ответа берутся только `default_branch` и уровень доступа токена из
     `permissions`) и `GET /projects/:id/pipelines?ref=<ветка>`
     (последний конвейер ветки). «Участники» (`/members…`) по-прежнему
     запрещены.
     - ломается: ничего; появляются функции интерфейса `forge`
       «сведения проекта» и «последний конвейер ветки», которых нет в
       ТЗ п. 1.
     - ослабляется: белый список ТЗ п. 2 расширяется на две пары
       чтения. Запрет записи и «участников» держится таблицей пар
       `gitlab_adapter` (новый модуль) и AC-1.
     - цена: +2 пары, +2 функции, +1–2 критерия; объём части 1 растёт
       примерно на 10%.
     - чьё решение: Оператор (белый список — граница ADR-0029 п. 8).
   - B) Добавить только `GET /projects/:id/pipelines?ref=<ветка>`.
     Базу сверять по защищённым веткам: база записи должна быть среди
     защищённых. «Роль в проекте» из `forge-probe` убрать.
     - ломается: `forge-probe` не печатает роль. `check_base_branch` для
       GitLab сверяет не «ветку по умолчанию», а «база защищена» — это
       другой смысл строки, чем у GitHub
       (orchestrator/doctor/misc_checks.py:90).
     - ослабляется: сверка базы: расхождение с веткой по умолчанию
       проекта не ловится.
     - цена: +1 пара, +1 функция; ТЗ п. 4 меняется (Оператор правит ТЗ).
     - чьё решение: Оператор.
   - C) Белый список не расширять. `check_base_branch` для GitLab
     остаётся `skip` с причиной «нет пары чтения проекта». Из
     `forge-probe` убрать роль и последний конвейер базы.
     - ломается: ТЗ п. 4 по сверке базы и `forge-probe` выполняется
       частично. `tests/test_doctor.py:670` остаётся как есть.
     - ослабляется: ничего не ослабляется относительно сегодняшнего
       `skip` (misc_checks.py:98-100).
     - цена: меньше объём; требование ТЗ п. 4 снимается правкой ТЗ.
     - чьё решение: Оператор.
   - дефолт: A — единственный вариант, при котором ТЗ п. 4 выполняется
     буквально. Пары только на чтение, «участники» остаются под запретом.

2. **Реализация GitHub для функций `forge` без аналога.** По ТЗ п. 1
   реализация GitHub — «обёртка над нынешними `ci`/`github_adapter`».
   Но `github_adapter.ensure_draft_mr(conn, task_id, t)` и
   `undraft_mr(conn, task_id, t)` (orchestrator/github_adapter.py:118,
   :301) принимают строку задачи и сами строят заголовок и тело. Под
   сигнатуры `open_mr(target, branch, base, title, body, draft,
   assignee)`/`undraft_mr(target, mr)` их не обернуть. У `job_result`,
   `job_test_report`, `assign_mr`, `mr_status`, `token_user`,
   `token_expiry`, `protections` в `ci`/`github_adapter` аналога нет
   совсем. Что эти функции делают для `forge: github`?
   - A) `pipeline_status` для GitHub оборачивает нынешнее чтение check
     runs `ci`, не меняя его поведения. Все остальные функции `forge`
     для `github` возвращают именованный отказ «не реализовано для
     github», `gh` не вызывают. Критерий проверяет и обёртку, и отказ.
     - ломается: ничего; GitHub-потребители продолжают звать
       `ci`/`github_adapter` напрямую.
     - ослабляется: ничего; поведение GitHub держат существующие тесты
       `ci`/`github_adapter`.
     - цена: минимальная; полноценную GitHub-реализацию оставить шагам,
       где она понадобится (Б1/Б2/В1).
     - чьё решение: Оператор.
   - B) Все функции для GitHub реализуются новыми вызовами `gh`/REST:
     `gh pr create/ready/edit/view`, `gh api user`, ветки и защиты.
     `open_mr`/`undraft_mr` пишутся заново, `github_adapter` не трогается.
     - ломается: ничего существующего, но появляются новые сетевые
       операции GitHub, включая запись (создание MR, правку
       исполнителя), с новой поверхностью отказов.
     - ослабляется: ничего; нужен свой белый список для `gh`, которого
       ТЗ не задаёт.
     - цена: +7–9 функций и их критериев; задача выходит за потолок
       $70 — деление на 3 части.
     - чьё решение: Оператор.
   - C) Перевести `github_adapter.ensure_draft_mr`/`undraft_mr` на
     `forge.open_mr`/`undraft_mr`, то есть рефакторинг `github_adapter`
     под новый интерфейс. Остальные функции — как в A.
     - ломается: внутреннее устройство `github_adapter` (ТЗ разрешает
       там «только вынос в интерфейс без изменения поведения»); есть риск
       для тестов `github_adapter`.
     - ослабляется: ничего, если существующие тесты остаются зелёными
       без правки.
     - цена: средняя, +1 итерация ревью.
     - чьё решение: Оператор.
   - дефолт: A — ТЗ требует для GitHub «без изменения поведения», а
     новых сетевых операций GitHub ТЗ не заказывает.

5. **«Неполный статус — не зелёный» (ADR-0029 п. 8, инвариант 19).** В ТЗ
   правила нет. Какой итог `pipeline_status` дают: задание или конвейер
   `canceled`; статусы `waiting_for_resource`, `preparing`, `scheduled`
   и любой неизвестный; неполная выдача заданий
   (`GET /pipelines/:id/jobs` по умолчанию отдаёт 20 на страницу)? У
   GitHub тот же класс закрыт постраничным чтением со сверкой
   (orchestrator/ci.py:8-10).
   - A) Пятый итог `unknown` с причиной. Он наступает при `canceled` у
     задания без права падать или у конвейера, при неизвестном статусе и
     при неполной выдаче: задания читаются постранично до конца, число
     сверяется с заголовком `X-Total`; если чтение оборвалось или числа
     не сошлись — `unknown`. `waiting_for_resource`/`preparing`/
     `scheduled` дают `running`. `unknown` никогда не зелёный. Добавляются
     критерии на `canceled`, неизвестный статус и вторую страницу с
     `failed`.
     - ломается: набор итогов ТЗ п. 1 (`green`/`red`/`running`/`none`)
       расширяется пятым значением.
     - ослабляется: ничего; правило ADR приходит в SPEC.
     - цена: +2–3 критерия.
     - чьё решение: Оператор (расширение набора итогов ТЗ).
   - B) Без нового значения: `canceled` даёт `red`, неизвестный статус и
     неполная выдача — `none` с именованной причиной,
     `waiting_for_resource`/`preparing`/`scheduled` — `running`.
     - ломается: `none` перестаёт означать только «конвейер не создан» —
       потребитель различает случаи по причине.
     - ослабляется: ничего по зелёности; различимость `none` слабее.
     - цена: +2–3 критерия.
     - чьё решение: Оператор.
   - дефолт: A — отдельный итог не путает «конвейера нет» с «статус не
     прочитан», и инвариант 19 держится явно.

6. **Как определять «стоит за ручным заданием» по данным API.** ТЗ
   допускает `created`/`skipped`/`manual`, только если задание стоит за
   ручным. Список заданий конвейера отдаёт `stage` и `status`, но не
   граф `needs`.
   - A) По стадиям. Задание `manual` допустимо само по себе.
     `created`/`skipped` допустимо, если в том же конвейере есть задание
     `manual` в более ранней стадии (порядок стадий — по порядку их
     первого появления в выдаче). Плюс в любом случае задание не должно
     быть в `policy.ci_required_jobs`. Критерий: `created` не за ручным
     и вне `ci_required_jobs` — не `green`.
     - ломается: ничего.
     - ослабляется: точность: задание стадией позже ручного, но не
       зависящее от него по `needs`, сочтётся «за ручным».
     - цена: +1 критерий.
     - чьё решение: Оператор.
   - B) Строго: допустимы только сами `manual`; любое `created`/
     `skipped` — не `green`.
     - ломается: конвейер, где задание стадией позже ручного ждёт его
       (`created`), не станет зелёным без запуска ручного — уже, чем
       ADR-0029 п. 8.
     - ослабляется: ничего (строже).
     - цена: +1 критерий.
     - чьё решение: Оператор.
   - C) По `needs`: дочитывать граф отдельным запросом (GraphQL или
     `/pipelines/:id/jobs` с `include_retried` не отдают `needs`) — новая
     пара белого списка.
     - ломается: ничего.
     - ослабляется: белый список (новая пара).
     - цена: +1 пара, сложнее разбор, +1–2 критерия.
     - чьё решение: Оператор.
   - дефолт: A — данные есть в разрешённом чтении, правило ADR держится.
