# SPEC: Механическая проверка ТЗ в `new`: вызывающие вне зон и ссылки `файл:строка`

## Контекст
У задач волны G (01M58FNWBV25FF26E7AZ9Q9912, 01M58PG72PG64GS790XM2EWS61,
01M590GJAF0EDV4NBC4C99MFVH) было по 3–4 круга аудита SPEC и 1–2 эскалации.
Около половины вопросов — неполные зоны: функцию, которую меняет ТЗ,
вызывают модули вне зон (`repo_context.profile_of`,
`acceptance._task_own_profile`, `suite_run._profile_command`); часть —
неверные ссылки `файл:строка`. ADR-0022 п. 1 требует проверки ТЗ не
автором, а `new` сейчас проверяет только форму ТЗ
(`orchestrator/catalog.py:584-612`: пути и зоны, «Порядок:», «Проект:»).
Задача добавляет в `new` две механические проверки содержания ТЗ по
дереву проекта — ссылки `файл:строка` и вызывающих вне зон.

## Требования

1. `new` с ТЗ выполняет две новые проверки (требования 3–4) **после**
   `workspace.ensure_clone` и **до** `idgen.new_task_id`
   (`orchestrator/catalog.py:617-620`). Дерево проверки — `origin/main`
   клона проекта (`workspace.repo(target)`), у артели — HEAD главной
   копии. Канарейка (`cmd_new(canary=True)`) и `catalog.spawn_subtask`
   этих проверок не выполняют.
2. Вывод проверок: первая строка `проверка ТЗ: N отказов, M
   предупреждений`, затем по строке на каждую находку; без находок не
   печатается ничего. Отказ — только вывод и прекращение `new`, без
   следов в БД (нет строки задачи, нет ссылки документов). При успешном
   заведении задачи предупреждения пишутся в журнал созданной задачи
   записью «проверка ТЗ» после `_new_task_row`.
3. Ссылки `файл:строка` в тексте ТЗ — формы `путь/файл.py:123` и
   `путь/файл.py:123-145` (путь от корня репозитория проекта), а также
   `файл.py:123`, если имя файла однозначно в дереве проверки:
   1. файла нет в дереве или строка (либо граница диапазона) вне длины
      файла — **отказ** `new`, перечисляющий все такие ссылки разом;
   2. в той же строке ТЗ рядом со ссылкой названо имя в обратных кавычках
      (`` `имя` `` или `` `модуль.имя` ``), а в окне ±3 строки
      указанного места файла этого имени нет — **предупреждение**.
4. Вызывающие вне зон:
   1. кандидаты берутся из текста от начала ТЗ до первой строки,
      начинающейся меткой из `_TZ_ZONES_LABEL` или `_TZ_DECLARING_LABELS`
      (`orchestrator/catalog.py:170-171`): имена в обратных кавычках вида
      `модуль.функция` или `Класс.метод` и функции, на которые указывает
      ссылка `файл.py:строка` (определение `def`/`class` в этой строке
      или ближайшее объемлющее выше);
   2. вызывающие — строки файлов `*.py` дерева проверки, кроме `tests/`,
      где имя функции встречается целым словом как вызов `имя(` или
      обращение `.имя` (поиск `git grep` по дереву). Имя короче 4
      символов или из списка общих имён (`run`, `main`, `load`, `get`,
      `set`, `check`, `parse`, `cmd`, `new`) не ищется — находка с
      пометкой «общее имя — не проверено»;
   3. вызывающий файл, не покрытый «Зонами» (с вложенностью и
      `config.COMMON_ZONES`) и не названный в «Только чтение…», «Не
      входит», «Приложением», — **предупреждение** «в зонах нет
      вызывающих `X`: `файл:строка`, … — назови в Зонах, в „Не входит“
      или в „Только чтение“»; не больше 20 вызывающих на имя, остаток —
      числом;
   4. предупреждения `new` не останавливают; флаг `new --strict-tz`
      превращает их в отказ. `_NEW_USAGE` (`orchestrator/artel.py:1440`)
      дополняется `[--strict-tz]`.
5. Тексты и исходы прежних проверок `new` не меняются: ТЗ без ссылок
   `файл:строка` и без имён в обратных кавычках даёт построчно прежний
   вывод `new`. Это свойство закрепляется тестами до правки кода.
6. Тесты детерминированы, без сети: учебный проект (артель и учебный
   `--target`) с модулями, вызывающими функцию из зоны и вне её; ссылки
   верные, неверные, за концом файла.

## Критерии приёмки

AC-1. ТЗ со ссылкой `путь/файл.py:N` на файл, которого нет в дереве
проверки, — `new` отказывает; вывод начинается строкой `проверка ТЗ: N
отказов, M предупреждений` и называет ссылку; в БД нет строки задачи и
нет ссылки документов.

AC-2. ТЗ со ссылкой на строку (или диапазон `:a-b`, граница которого)
за концом существующего файла — отказ `new` без записи в БД; при
нескольких неверных ссылках в одном ТЗ отказ перечисляет все их разом.

AC-3. Ссылка `файл.py:N` без каталога, имя файла однозначно в дереве —
ссылка проверяется как полная (верная — без отказа, за концом файла —
отказ).

AC-4. В строке ТЗ рядом со ссылкой названо имя в обратных кавычках, а в
окне ±3 строки указанного места файла этого имени нет — предупреждение;
имя есть в окне — находки нет.

AC-5. Функция, названная в тексте ТЗ до «Зоны:» (в обратных кавычках
`модуль.функция` или через ссылку `файл.py:строка` на её `def`), которую
вызывает модуль вне зон, — предупреждение «в зонах нет вызывающих `X`:
…» с `файл:строка` вызывающего.

AC-6. Вызывающий, названный в «Только чтение…» или «Не входит», —
без предупреждения; вызывающий, покрытый «Зонами» или
`config.COMMON_ZONES`, — без предупреждения.

AC-7. Вызывающие из `tests/` не учитываются; больше 20 вызывающих на
имя — в предупреждении 20 мест и остаток числом.

AC-8. Общее имя из списка требования 4.2 и имя короче 4 символов дают
пометку «общее имя — не проверено», поиск по дереву для них не
выполняется.

AC-9. Без `--strict-tz` предупреждения не останавливают `new`: задача
заводится, предупреждения записаны в журнал задачи записью «проверка
ТЗ»; с `--strict-tz` то же ТЗ даёт отказ без записи в БД. Справка `new`
(`_NEW_USAGE`) содержит `[--strict-tz]`; прежние утверждения
`tests/test_new_argv_parsing.py` не меняются.

AC-10. ТЗ без ссылок `файл:строка` и без имён в обратных кавычках —
вывод `new` построчно прежний, строки `проверка ТЗ:` нет; канарейка
(`cmd_new(canary=True)`) и `spawn_subtask` проверки не выполняют даже
при ТЗ, которое дало бы находки.

AC-11. У внешнего проекта (`--target`) проверки идут по дереву
`origin/main` его клона: ссылка, верная только в главной копии артели,
но не в дереве клона, даёт отказ, и наоборот.

AC-12. (ручной) PLAN.md несёт раздел «Замер на волне G» — таблицу
«задача / предупреждений / совпало с вопросами аналитика» по живым ТЗ
трёх задач волны G (тексты — `refs/artifacts/<id>:tasks/<id>/TZ.md`,
вопросы — `QUESTIONS.md` тех же задач).

## Оценка объёма и деление

Сработавший сигнал: число критериев приёмки ≥ 10 (12).

Обоснование монолита (материал для решения Оператора): обе проверки
живут в одних и тех же зонах — `orchestrator/tz_check.py` (новый модуль),
одна точка вызова в `cmd_new` (`orchestrator/catalog.py`) и разбор флага
в `orchestrator/artel.py`; нарезка по зонам невозможна — любая часть
режет те же три файла поперёк. Общая механика (дерево проверки
`origin/main`/HEAD, разбор ссылок `файл:строка`, единая строка `проверка
ТЗ: N отказов, M предупреждений`, журнал «проверка ТЗ», `--strict-tz`)
нужна обеим проверкам, а кандидаты проверки вызывающих (требование 4.1)
берутся в том числе из разбора ссылок (требование 3). Рамка Оператора в
ТЗ — $45 на задачу целиком; число файлов зоны — 3 плюс `tests/`.

## Не входит

- Индекс вызовов и разбор синтаксиса: поиск — `git grep` по дереву;
  методы ищутся по имени метода; ложные срабатывания допустимы
  (предупреждение).
- Вызовы через `getattr`, таблицы команд и строки — известный предел
  поиска.
- Аудит ТЗ агентом и консультация роли (поправка ADR-0022, не принята).
- Правило эскалации аналитика.
- Задачи волны G (их ТЗ только читаются для замера AC-12).
- Правка `orchestrator/repo_context.py`, `orchestrator/workspace.py`,
  `orchestrator/canary_drive.py`, `scripts/guard.py`,
  `scripts/codebase_map.py`, `scripts/core_reference.py`,
  `orchestrator/advance_gates/test_integrity.py`,
  `docs/adr/0022-handoff-audit.md`, `docs/operator-session.md`,
  `docs/backlog.md` — только чтение; правка вне зон — эскалация.
- Смена текстов и исходов прежних проверок `new` (пути/зоны,
  «Порядок:», «Проект:», калибровка) — требование 5 их сохраняет.
