# SPEC: guard на артефактных ветках — черновики не красят CI, сданные артефакты проверяются строго

## Контекст
CI гоняет `guard.py --all` на каждый пуш ветки `artifact/<id>` (T094,
требование 7), а каждый шаг роли заканчивается автокоммитом
промежуточных, по определению неполных артефактов (SPEC в `status:
draft` без `zones`, PLAN в работе, ANSWER без секции). За сутки 58 из
100 прогонов CI пришлись на артефактные ветки, почти все красные —
настоящие нарушения формы (ANSWER без «## Ответы», ready-SPEC без
секции оценки объёма) тонут в шуме «ещё пишется», а Оператор получает
уведомление о каждом прогоне.

## Требования

1. `scripts/guard.py` умеет включаемый «режим артефактной ветки»
   проверки (параметр функции и/или CLI-флаг/переменная окружения —
   решает разработчик на этапе PLAN). Без этого режима (значение по
   умолчанию, в том числе все существующие вызовы из `orchestrator/
   fsm.py` на переходах `advance`/гейтах) поведение не меняется ни на
   бит: обязательные секции, поле `zones`, секция «Оценка объёма и
   деление», AC-разметка критериев приёмки, маркеры красноты
   проверяются независимо от `status`, как сегодня — черновик там не
   проходит переход, как сейчас.
2. С включённым режимом артефактной ветки для артефактов типов `spec`,
   `plan`, `review`, `test_report` со `status: draft` проверяются
   только базовые условия: frontmatter читается, поля `task`/`type`/
   `schema_version` на месте, `schema_version` не выше
   `SUPPORTED_SCHEMA_VERSION`. Для тех же четырёх типов с любым
   `status`, отличным от `draft` (для `spec`/`plan`/`review` это
   `ready`/`approved`/`escalate`/`changes_requested` — по множеству
   статусов, валидных для типа в `RULES`; для `test_report` это
   `passed`/`failed`), проверяются все текущие правила содержания без
   исключений.
3. Типы `tz`, `questions`, `answer` не несут понятия «черновик» в
   терминах этой задачи (`answer` вообще не имеет статуса `draft`) —
   режим артефактной ветки их проверку не меняет ни для одного
   статуса: полная проверка, как сегодня, при любом `status`.
4. CLI: `python3 scripts/guard.py --all` с новым флагом (или
   переменной окружения) включает режим артефактной ветки для всех
   файлов данного запуска. В этом режиме нарушение у артефакта со
   `status`, отличным от `draft` (по правилу требования 2), —
   ошибка, ведущая к exit-коду процесса 1; нарушение у артефакта со
   `status: draft` — предупреждение в stdout, не влияющее на exit-код.
   Если нарушений у «сданных» артефактов нет, процесс завершается
   успешно (0), даже если черновики несут предупреждения.
5. В режиме артефактной ветки первая строка вывода — сводка вида
   «сдано N / черновиков M / нарушений K»: N — число проверенных
   артефактов со `status`, отличным от `draft`, M — число артефактов
   со `status: draft`, K — суммарное число найденных нарушений (и по
   сданным, и по черновикам). Без флага/переменной формат вывода не
   меняется.
6. `.github/workflows/ci.yml`, джоб `guard`: на пуш ветки `artifact/**`
   вызывает `guard.py --all` с новым флагом/переменной; на `main` и
   `task/**` — вызов остаётся `guard.py --all` без него, поведение
   прежнее. Правка защищённого пути — диффом-приложением к PLAN.md для
   Оператора (`skills/conventions-core.md`), с прогоном `git apply
   --check` перед сдачей.

## Критерии приёмки

AC-1. Вызов guard без включённого режима артефактной ветки (в т.ч.
всё, что сегодня зовёт `guard.check`/`guard.check_content` из
`orchestrator/fsm.py` на переходах и гейтах) не меняет поведение:
обязательные секции, `zones`, «Оценка объёма и деление», AC-разметка,
маркеры красноты проверяются независимо от `status` — черновик не
проходит переход, как сейчас.

AC-2. С включённым режимом артефактной ветки и `status: draft`
артефакта типа `spec`/`plan`/`review`/`test_report` — нарушения
обязательных секций, `zones`, «Оценка объёма и деление», AC-разметки,
маркеров красноты не считаются ошибками (только предупреждение);
нарушения frontmatter (`task`/`type`/`schema_version` отсутствуют,
`schema_version` выше `SUPPORTED_SCHEMA_VERSION`) остаются ошибками.

AC-3. С включённым режимом артефактной ветки и `status`, отличным от
`draft`, у тех же четырёх типов — все текущие правила содержания
применяются без исключений, результат совпадает с проверкой без
режима.

AC-4. С включённым режимом артефактной ветки артефакты типов `tz`,
`questions`, `answer` проверяются как и без режима — при любом
`status`, который валиден для типа.

AC-5. `guard.py --all` с новым флагом/переменной окружения включает
режим артефактной ветки для всего набора файлов запуска; без
флага/переменной — поведение как до этой задачи.

AC-6. В режиме артефактной ветки нарушение у «сданного» (`status`,
отличный от `draft`) артефакта делает exit-код процесса 1; нарушение
только у черновиков — exit-код 0, нарушения черновиков напечатаны как
предупреждения.

AC-7. Первая строка stdout в режиме артефактной ветки — сводка «сдано
N / черновиков M / нарушений K» с фактическими числами по проверенному
набору файлов.

AC-8. `.github/workflows/ci.yml`: джоб `guard` на пуш `artifact/**`
вызывает guard с новым флагом/переменной; на `main` и `task/**` —
без него. Диф приложен к PLAN.md, `git apply --check` пройден.

AC-9. Тесты: draft-SPEC (schema_version 4) без `zones` — предупреждение
в режиме артефактной ветки, ошибка при вызове guard без режима (в т.ч.
эмуляция перехода `advance`); ready-SPEC без `zones` — ошибка в обоих
случаях; ANSWER без секции «## Ответы» — ошибка независимо от режима;
`tests/test_guard*.py` и `tests/test_invariants.py::
GuardKeepsTheIntegritySectionTest` (инвариант 17, docs/invariants.md
строка 44) остаются зелёными без ослабления проверяемого ими
поведения.

## Оценка объёма и деление
Сработавшие сигналы: «затронут инвариантный механизм» (зона задевает
`scripts/guard.py`, который `docs/invariants.md` называет напрямую как
несущий класс проверок guard'а — строка 82); «прогноз диффа не дан»
(секция ниже прогноза не несла, а хотя бы один другой сигнал уже
сработал).

**Обоснование монолита.** Требования 1–6 — одна атомарная смена
поведения одной функции `guard.check_content` (плюс её вызывающий код
в `main()` и джоб `guard` в `.github/workflows/ci.yml`): различение
`draft`/«сдан» и превращение нарушений черновика в предупреждение —
одна ветвление внутри одного и того же прохода по правилам `RULES`, а
не независимые куски. Разрезать на «сначала логика различения статусов
в `guard.py`, потом CLI-флаг» или «сначала guard.py, потом ci.yml»
оставляет систему в нерабочем промежуточном состоянии: код различения
без CLI-переключателя недостижим ни из одного вызова (мёртвый код,
непроверяемый приёмочными тестами требования 4), а правка `ci.yml` без
готового флага в `guard.py` включит в CI режим, которого сам guard ещё
не понимает (`unrecognized argument` вместо ожидаемого поведения).
Каждая часть нарезки по отдельности не мержима с зелёной планкой —
задача монолитна.

## Не входит

- Отключение CI на артефактных ветках — джоб продолжает гоняться на
  каждый пуш `artifact/**`.
- Смена схемы артефактов — новых полей frontmatter, нового
  `schema_version`, изменений в `templates/*.md` эта задача не вносит;
  режим артефактной ветки — поведение guard на существующей схеме.
- Правила guard для `main` — на `main` (и на `task/**`) поведение
  джоба и самого guard не меняется.
- Новая запись в `docs/invariants.md`, документирующая режим
  артефактной ветки, — по требованию 6 правится диффом «при
  необходимости»; решение вносить её или нет — за разработчиком на
  этапе PLAN, не обязательный критерий приёмки этой задачи.
- Изменение состава валидных значений `status` для любого типа
  артефакта (`RULES` в `scripts/guard.py`).
