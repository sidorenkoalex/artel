# SPEC: Критерий приёмки не дублирует проверки, которые держит пульт

## Контекст

Аналитик добавляет в SPEC критерий о зелёном полном наборе `tests/`, хотя
эту проверку уже выполняют пульт и CI. Такой критерий невозможно покрыть
планкой без рекурсивного запуска, поэтому test_author помечает его
`skip` или `manual`; из-за этого автогейт приёмки переводит задачу на
ручную приёмку. Правило нужно закрепить в скилах обеих ролей и защитить
проверкой их текста.

## Требования

1. В `skills/spec-authoring.md` описано правило: проверки, которые пульт
   выполняет для любой задачи, не становятся критериями приёмки SPEC.
   Перечень ограничен полным зелёным набором `tests/`, зелёным CI ветки,
   неизменностью защищённых путей и непревышением бюджета. Если такое
   требование дано в ТЗ, аналитик указывает его в разделе «Не входит»
   одной строкой с указанием, что его держит пульт.
2. В `skills/test-authoring.md` описано правило для критерия из этого
   перечня, который всё же попал в SPEC: test_author эскалирует его
   пометкой `escalate` с вопросом «критерий держит пульт — убрать из
   SPEC?», а не помечает `skip` или `manual`.
3. Готовые изменения обоих скилов оформлены приложением к PLAN для
   защищённого пути; пульт применяет приложение при мерже.
4. В `tests/` есть проверка текстов обоих скилов по устойчивым ключевым
   фразам. Она подтверждает наличие правила в каждом скиле, упоминание
   полного `tests/` и CI ветки и перестаёт проходить, если правило удалить
   из скила.

## Критерии приёмки

AC-1. `skills/spec-authoring.md` запрещает включать в критерии приёмки
проверки, которые пульт выполняет для любой задачи, и называет полный
набор `tests/`, CI ветки, неизменность защищённых путей и непревышение
бюджета; для такого требования из ТЗ скил предписывает одну строку в
разделе «Не входит» с указанием, что его держит пульт.

AC-2. `skills/test-authoring.md` для такого критерия, оставшегося в SPEC,
предписывает `escalate` с вопросом «критерий держит пульт — убрать из
SPEC?» вместо пометок `skip` или `manual`.

AC-3. PLAN содержит применимое приложение с готовыми правками
`skills/spec-authoring.md` и `skills/test-authoring.md`, предназначенное
для применения пультом при мерже.

AC-4. Проверка в `tests/` подтверждает правило в текстах обоих скилов и
наличие в нём полного `tests/` и CI ветки; удаление правила из любого из
скилов делает эту проверку красной.

## Оценка объёма и деление

Сработавший сигнал: зона `tests/` затрагивает инвариантный механизм.
Прогноз диффа: 6 КиБ.

Обоснование монолита: правило аналитика, правило test_author и одна
проверка, подтверждающая их совместное наличие, составляют единый
маршрут предотвращения ложной ручной приёмки. Отдельный мерж только
одного правила оставляет второй путь к `skip`/`manual` без требуемого
поведения, а отдельный мерж проверки не подтверждает результат для
обеих ролей. Поэтому промежуточный результат не закрывает дефект и не
имеет самостоятельной зелёной планки.

## Не входит

- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность
  защищённых путей и непревышение бюджета: эти проверки держит пульт.
- Изменение автогейта приёмки: он по-прежнему отказывает при любом
  `skip` или `manual`.
- Программная проверка текста SPEC в `scripts/guard.py`.
- Критерий CI в канарейке.
