# REVIEW: Учёт стоимости шага и потолок бюджета

## Гейт плана (Фаза A)

Аппрув плана. Таблица покрытия полна: все шесть требований SPEC отображены
на шаги 1–3, лишних шагов нет. Шаги — единицы одного MR (учёт стоимости,
потолок, тесты); объединение в один MR обосновано: тесты шага 3 проверяют
поведение, которого без шагов 1–2 нет, а потолок без учёта стоимости не
срабатывает никогда. Конвенции не нарушены: правится только
`orchestrator/artel.py` и добавляется `tests/test_step_cost.py`, запретные
пути (`.github/`, `gates.yaml`, `roles.yaml`, `templates/`, `skills/`) не
тронуты.

Два решения плана расходятся с буквой SPEC — оба принимаю осознанно:

- Стоимость снимается с потока, а не из `.artel/logs/` (SPEC п.1 предлагал
  изучить формат по логам). Проверил по коду: успешное событие
  `type: result` `render_agent_line` гасит (artel.py:242 — `return ""`),
  а ошибочное отрисовывает одной строкой «! ошибка агента» без цифр
  (artel.py:240-241) — самой стоимости в файле лога нет ни в одном случае,
  формат по логам изучить и правда нельзя. Источник тот же, канал другой.
- Стоимость считается за каждую попытку, не только за успешную (SPEC п.2
  называет запись «agent run finished»). Расширение необходимое: после T006
  на шаг приходится до трёх попыток, и учёт только успешных превращал бы
  ретраи в дыру в потолке из п.4. Реализация не теряет и букву п.2 —
  в «agent run finished» стоимость пишется.

## Замечания

- minor — orchestrator/artel.py:806 (`cmd_budget`) — снятие блокировки
  опирается на инвариант «если `spent_usd >= budget_usd`, то эскалация
  могла быть только бюджетной» (PLAN.md:69-73), но сама же команда
  разрешает опустить потолок ниже израсходованного, и тогда инвариант
  ложен. Сценарий (воспроизвёл на копии кода): задача эскалирована
  ревьювером или провалом агента (`state=escalated`, `escalated_from=review`,
  budget 5.00, spent 1.00) → Оператор урезает потолок `budget T001 0.5`
  («этого мало», блокировка остаётся) → передумывает и возвращает
  `budget T001 5` → задача уезжает в `review` с причиной «бюджет поднят,
  продолжаем», `escalated_from` обнуляется. Чужая эскалация снята, причину
  никто не разобрал. Предложение: снимать блокировку только когда эскалация
  была бюджетной — например, сверять причину последней записи
  `state -> escalated` в журнале, либо не давать опускать потолок ниже
  `spent_usd` (отдельным сообщением), и тогда инвариант становится честным.

- minor — tests/test_step_cost.py:287 (и далее до 399) — граница «≥» самого
  потолка не запинена ни одним тестом: во всех сценариях `spent` строго
  больше `budget` (0.5 против 0.3) или строго меньше (0.4 против 0.5).
  Проверил мутацией на копии: `spent >= budget` → `spent > budget`
  (artel.py:738) и `spent < budget` → `spent <= budget` (artel.py:720)
  одновременно — все 113
  тестов остаются зелёными, хотя задача с ровно израсходованным бюджетом
  начинает запускать агента. SPEC п.4 говорит именно «≥». Предложение:
  один тест на равенство — budget 0.5, стоимость шага 0.5 → `escalated`
  и `budget_block` не None. Порог 70% так уже запинен (0.7 при бюджете 1.0),
  это тот же приём.

- minor — orchestrator/artel.py:749 (`enforce_budget`) — предупреждение о
  70% печатается и пишется в журнал после каждой попытки, а не один раз при
  пересечении порога: шаг из трёх попыток за порогом даёт три одинаковые
  записи «бюджет: предупреждение», и дальше по записи на каждый следующий
  запуск. Читающий журнал видит шум там, где событие одно. Предложение (на
  усмотрение): сравнивать `spent` до и после прибавки и писать только на
  пересечении; если решение осознанное («каждая попытка тратит деньги») —
  достаточно строки в комментарии.
