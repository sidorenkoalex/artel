# SPEC: G5а — документы `knowledge` компонента в брифе ролей внешнего проекта

## Контекст
Задача волны G по ADR-0026 («Решение» п. 11: документы `knowledge`
компонента идут в бриф). Поле `knowledge` компонента схема записи
проекта принимает (`orchestrator/targets.py:98`, вид `repo_paths`), но
нигде не читает: у `Profile` такого поля нет, `_with_component_fields`
(`orchestrator/project_profile.py`) его не копирует. Конвенции внешнего
проекта в брифе сегодня — только фиксированный список
`PROJECT_CONVENTIONS = ("CLAUDE.md", "AGENTS.md")`
(`orchestrator/brief.py:44`), читаемый из корня ветки базы
(`_read_project_conventions`, `orchestrator/brief.py:550`;
`_project_conventions_parts`, `orchestrator/brief.py:586`). Решение
Оператора 21.10: документы `knowledge` — дополнение к `CLAUDE.md` и
`AGENTS.md`, не замена; предел — 20 файлов на элемент-каталог; G5
делится на G5а (эта задача) и G5б.

Граница одной фразой (ТЗ): новое поведение — только у задачи с профилем
из записи `components:`, у единственного компонента которой есть поле
`knowledge`; у артели, у записи `test_profile` и у компонента без
`knowledge` бриф всех ролей прежний побайтно.

Круг 2: учтены решения Оператора на гейте SPEC (круг 1) по отклонениям
аудита — состав дерева через `ls-tree -z`, фикстуры AC-7 с полем
`knowledge`, имена файлов из листинга каталога только внутри границы
недоверенных данных, уточнение неоднозначностей каталога (символьные
ссылки и подмодули, каталог без `*.md`, «/» у файла, «уже показанный»
путь, место и журнал строки предела).

Круг 3: учтены решения Оператора на гейте SPEC (круг 2) — пометка сбоя
git/не UTF-8 у файла из каталога без пути и stderr, смысл M в «документ
<k> из <M>», сравнение путей по виду `ls-tree -z`, эталон AC-9 —
литерал или фикстура, «показан» — передан в `render`.

## Требования

1. **Условие.** Новое поведение включается, только если
   `project_profile.decide(target).profile` взят из записи `components:`
   (`from_components`) и у её единственного компонента
   (`project_profile.components(target)[0]`, поля — `.fields`) есть поле
   `knowledge`. Поле записи `knowledge` (`orchestrator/targets.py:124`,
   `KNOWLEDGE_FIELD` — файл карточек знаний) задача не меняет и не
   читает как источник документов.
2. **Порядок кусков.** `_project_conventions_parts` сначала выдаёт
   прежние куски `PROJECT_CONVENTIONS` — побайтно прежние, включая
   пометки, — затем куски элементов `knowledge` в порядке записи,
   пропуская пути, уже показанные выше. «Показанный» путь — путь, кусок
   которого передан в `render` вызывающего (в том числе `CLAUDE.md`/
   `AGENTS.md` и повтор между элементами `knowledge`); решение о пропуске
   повтора принимается до `render`, и пропуск файла по размеру внутри
   `render` его не меняет. Пути с пометкой «файла нет» или «конвенции
   проекта не прочитаны» показанными не считаются. Пути сравниваются в
   том виде, в каком их вернул `ls-tree -z`; элемент записи сводится к
   тому же пути дерева (`CLAUDE.md` с префиксом «точка, косая черта» и
   без него — один путь).
3. **Состав дерева.** Состав дерева базы (и для элемента-файла, и для
   элемента-каталога) читается `ls-tree -z` (разделитель NUL, имена без
   кавычек и восьмеричных escape), так что не-ASCII (например,
   кириллические) имена файлов читаются верно.
4. **Элемент-файл** (без `/` на конце): состав — `ls-tree` коммита базы
   с этим путём буквально (`--literal-pathspecs`), путь в подкаталоге
   виден; текст — `show` коммита базы.
5. **Элемент-каталог** (с `/` на конце): все обычные файлы `*.md` под
   ним рекурсивно (`ls-tree -r`), отсортированные по пути; повторы уже
   показанных путей убираются до отсчёта предела; не более
   `KNOWLEDGE_DIR_MAX_FILES = 20` (константа `orchestrator/brief.py`).
   - Сверх предела — строка «документы knowledge: каталог <элемент> —
     показаны первые 20 файлов из <N>», стоящая после кусков своего
     каталога, и запись журнала с действием «бриф: документы knowledge
     сокращены» и деталью — элемент записи и N.
   - Символьные ссылки и подмодули внутри элемента-каталога в документы
     не входят и в N не считаются; если они есть — строка «документы
     knowledge: каталог <элемент> — пропущено не обычных файлов: <n>»
     без их имён.
   - Элемент-каталог без единого `*.md` — строка «документы knowledge:
     каталог <элемент> — файлов *.md нет».
6. **Пометки элементов.**
   - элемент без `/`, оказавшийся каталогом, — пометка «конвенции
     проекта не прочитаны: <элемент>: каталог — элемент-каталог пишется
     с «/» на конце» с записью журнала;
   - элемент с `/` на конце, который в дереве базы — файл, — пометка
     «конвенции проекта не прочитаны: <элемент>: не каталог —
     элемент-файл пишется без «/»» с записью журнала;
   - элемент-файл — символьная ссылка или подмодуль — пометка
     «конвенции проекта не прочитаны» с причиной «не обычный файл» с
     записью журнала;
   - пути нет в дереве базы — пометка «файла нет»;
   - сбой git и текст не в UTF-8 у элемента-файла — прежняя пометка
     «конвенции проекта не прочитаны» с записью журнала;
   - сбой git и текст не в UTF-8 у файла из элемента-каталога — пометка
     без пути файла и без stderr git: «конвенции проекта не прочитаны:
     каталог <элемент>, документ <k>: <класс причины>», где класс
     причины — «текст не в UTF-8» или «сбой git»; запись журнала — та же
     строка.
7. **Подписи и граница недоверенных данных.** Имена файлов из листинга
   каталога чужого репозитория выводятся только внутри границы
   недоверенных данных:
   - кусок элемента-файла (путь задан записью Оператора) — подпись
     «<путь> (knowledge компонента <имя>, ветка <base> проекта
     <target>)»;
   - кусок файла из элемента-каталога — подпись «knowledge компонента
     <имя>, каталог <элемент записи>, документ <k> из <M> (ветка <base>
     проекта <target>)», а путь файла — первой строкой текста куска
     («путь: <путь>») внутри границы; M — число показанных документов
     этого каталога (после убирания повторов и предела, не больше 20);
   - пометки и строки вне границы (в том числе пометки п. 5 и п. 6 о
     файлах каталога и записи журнала к ним) путей из листинга каталога
     не содержат.
   Оформление — тот же `render` вызывающего (`_manifest_component`,
   `_journal_component`, `review._conventions_component`). Подпись куска
   в `review.py` не меняется; правка `review.py` не требуется.
8. **База не прочитана.** Одна прежняя пометка «конвенции проекта не
   прочитаны»; перечень в ней — `PROJECT_CONVENTIONS` и элементы
   `knowledge`.
9. **Прежний вывод побайтно.** Отказ и пропуск `decide`, `test_profile`,
   компонент без `knowledge`, запись из нескольких компонентов (отказ
   `decide` `MULTI_COMPONENT_PENDING` до G3б), исключение модуля
   `targets` (ошибка записи проекта) при чтении записи для `decide` или
   `components` — прежний вывод побайтно; такое исключение сборку брифа
   не останавливает. У артели функция не вызывается, как сегодня.
10. **Потребители.** Поведение действует у всех пяти потребителей:
    developer (`orchestrator/brief.py:1050`), аудитор SPEC
    (`orchestrator/brief.py:1120`), аналитик
    (`orchestrator/brief.py:1421`), test_author
    (`orchestrator/brief.py:1459`), ревьювер (пакет ревьювера,
    `orchestrator/review.py:941`) — через правку внутри
    `_project_conventions_parts`, без правки вызывающих вне зоны.
11. **Тесты** детерминированы, без сети: учебный git-проект с
    компонентом и полем `knowledge`; эталон прежнего вывода снят с кода
    пина при постоянном `run_id` (`brief.new_run_id` подменён) и лежит в
    тесте литералом или файлом-фикстурой — вызов кода в момент прогона
    эталоном не является; существующие тесты без правок.

## Критерии приёмки

AC-1. У задачи с профилем из `components:`, у единственного компонента
которой есть `knowledge`, бриф несёт после прежних кусков `CLAUDE.md`/
`AGENTS.md` (побайтно прежних, включая пометки) куски элементов
`knowledge` в порядке записи с текстом из коммита базы; кусок
элемента-файла подписан «<путь> (knowledge компонента <имя>, ветка
<base> проекта <target>)»; элемент-файл в подкаталоге показан
(буквальный путь, `--literal-pathspecs`).

AC-2. Элемент-каталог с `/` на конце даёт куски всех обычных файлов
`*.md` под ним рекурсивно, отсортированных по пути; файлы не `*.md` не
показаны. Кусок файла из каталога подписан «knowledge компонента <имя>,
каталог <элемент записи>, документ <k> из <M> (ветка <base> проекта
<target>)», где M — число показанных документов этого каталога (после
убирания повторов и предела, не больше 20), первая строка его текста —
«путь: <путь>»; ни подпись, ни
пометки и строки вне границы недоверенных данных, ни записи журнала
путей файлов из листинга каталога не содержат.

AC-3. При числе `*.md` в элементе-каталоге больше
`KNOWLEDGE_DIR_MAX_FILES = 20` (константа `orchestrator/brief.py`)
показаны первые 20; после кусков этого каталога стоит строка «документы
knowledge: каталог <элемент> — показаны первые 20 файлов из <N>», в
журнале — запись с действием «бриф: документы knowledge сокращены» и
деталью с элементом записи и N. Пути, уже показанные выше, убираются до
отсчёта предела.

AC-4. Символьные ссылки и подмодули внутри элемента-каталога в документы
не входят и в N не считаются, и выводится строка «документы knowledge:
каталог <элемент> — пропущено не обычных файлов: <n>» без их имён;
элемент-каталог без единого `*.md` даёт строку «документы knowledge:
каталог <элемент> — файлов *.md нет».

AC-5. Элемент без `/`, оказавшийся каталогом, даёт пометку «конвенции
проекта не прочитаны: <элемент>: каталог — элемент-каталог пишется с
«/» на конце» и запись журнала; элемент с `/` на конце, который в
дереве — файл, даёт пометку «конвенции проекта не прочитаны: <элемент>:
не каталог — элемент-файл пишется без «/»» и запись журнала;
элемент-файл — символьная ссылка или подмодуль — пометку «конвенции
проекта не прочитаны» с причиной «не обычный файл» и запись журнала.

AC-6. Путь, кусок которого уже передан в `render` выше (`CLAUDE.md` в
`knowledge`, в том числе записанный с префиксом «точка, косая черта»; повтор между
элементами), второй раз не выводится; пропуск файла по размеру внутри
`render` повтор не открывает; путь с пометкой «файла нет» или «конвенции
проекта не прочитаны» показанным не считается; отсутствующий в дереве
базы путь даёт пометку «файла нет»; текст не в UTF-8 и сбой git у
элемента-файла дают прежнюю пометку «конвенции проекта не прочитаны» и
запись журнала; у файла из элемента-каталога оба случая дают пометку
«конвенции проекта не прочитаны: каталог <элемент>, документ <k>: <класс
причины>» (класс — «текст не в UTF-8» или «сбой git») и запись журнала
той же строкой, причём путь файла и stderr git в пометке и в записи
журнала отсутствуют.

AC-7. Элемент-файл и файл внутри элемента-каталога с кириллическими
именами показаны текстом из коммита базы, без ложной пометки «файла
нет» (состав дерева — `ls-tree -z`).

AC-8. Если база не прочитана, вывод — одна прежняя пометка «конвенции
проекта не прочитаны», перечень в которой — `PROJECT_CONVENTIONS` и
элементы `knowledge`.

AC-9. Выход `_project_conventions_parts` в трёх способах оформления
(`_manifest_component`, `_journal_component`,
`review._conventions_component`) у записи `test_profile` и у компонента
без `knowledge` побайтно совпадает с эталоном, снятым с кода пина при
постоянном `run_id` (`brief.new_run_id` подменён); эталон лежит в тесте
литералом или файлом-фикстурой — вызов кода в момент прогона эталоном
не является.

AC-10. Учебная запись из нескольких компонентов (отказ `decide` до G3б)
и одиночный компонент с отказом `decide` — у обоих компоненты несут поле
`knowledge` — дают прежний вывод побайтно (обход `decide` чтением
`components(target)[0]` этим ловится); пропуск `decide` и исключение
модуля `targets` при чтении записи для `decide` или `components` дают
прежний вывод побайтно, и сборка брифа не останавливается; у артели
`_project_conventions_parts` не вызывается.

AC-11. Куски `knowledge` присутствуют в брифе developer, аудитора SPEC,
аналитика и test_author; в пакете ревьювера куски `knowledge`
присутствуют и стоят после кусков `PROJECT_CONVENTIONS` в порядке записи
(проверяются только присутствие и порядок, не пакет целиком — его строки
меняет G3а-2б-1).

## Оценка объёма и деление

Сработавшие сигналы: «число затрагиваемых модулей/файлов» — счёт идёт
по путям, упомянутым в тексте SPEC; большинство из них (`review.py`,
`role_prompt.py`, `project_profile.py`, `targets.py` и др.) — только
чтение по ТЗ и адреса в «Не входит»/«Материалах». Реально меняемые зоны
— две: `orchestrator/brief.py` и `tests/`. «Число критериев приёмки ≥
10» — 11 критериев: решения Оператора на гейте SPEC (круг 1) добавили
к прежним 8 критерии про `ls-tree -z`, границу недоверенных данных и
неоднозначности элемента-каталога; все они — про ту же одну функцию.

Прогноз диффа: 48 КиБ (правка `_project_conventions_parts` и чтения
конвенций в `orchestrator/brief.py` ~12 КиБ, тесты с учебным
git-проектом и эталоном ~36 КиБ) — ниже половины потолка гейта ёмкости
(128 КиБ).

**Обоснование монолита** (материал для решения Оператора): изменение —
одна функция сборки кусков конвенций в одном модуле и тесты к ней;
зону `orchestrator/brief.py` не разрезать по границам зон, а часть
«код без тестов» и часть «тесты без кода» по отдельности не мержимы
(тесты на новое поведение красны без кода; код без тестов нарушает
требование 2 ТЗ). Деление G5 на G5а/G5б Оператор уже выполнил в ТЗ.

  выбор компонента по диффу — G3б.

  меняется.

  аналитика и test_author — нет); новый предел не вводится.
- Отдельный критерий на `--literal-pathspecs` (решение Оператора, круг
  1, п. 4): требование 4 остаётся, отдельной проверки нет.
- Зелёный полный набор `tests/` («существующие тесты … зелёные») — его
  держит пульт; правок существующих тестов задача не делает, раздела
  «Меняемое поведение» нет.
