# PLAN: Механика зон, часть 1: машиночитаемое поле `zones` и общий список зон

## Подход

Реализация закрывает требования 1–3/AC-1..AC-5 буквально и проходит весь
залоченный приёмочный набор (`tasks/01M1NKVPD2A79PQ6K0JVV1B2Q1/
acceptance_tests/`, 6/6 зелёных). Код:

1. `scripts/guard.py` — `SUPPORTED_SCHEMA_VERSION` поднят 3 -> 4 (шаг,
   который заставляет `requires_zones`/`spec_zones_errors` считать
   версию 4 «понятной», а не «новее поддерживаемой») и новая пара
   `requires_zones`/`spec_zones_errors`, версия-гейтинг тем же приёмом,
   что `requires_ac_markup`/`requires_split_assessment` — SPEC версии
   ниже 4 (включая версию 3, дефолт ДО этой задачи, в т.ч. SPEC САМОЙ
   этой задачи) не обязан нести `zones`; версии 4 и выше — обязан,
   отказ называет поле `zones` по имени (AC-1).
2. `orchestrator/config.py` — `COMMON_ZONES`: именованный кортеж с
   четырьмя путями общих зон буквально из требования 2 (AC-4).
3. `orchestrator/store.py` — колонка `zones TEXT` в `SCHEMA` (свежая БД)
   и `migrate()` (БД, созданная до этой задачи) — тот же приём, что
   `split_assessment`/`diff_bytes` рядом (AC-3, часть).
4. `orchestrator/fsm.py::_cmd_approve` — на ветке `state == "spec_gate"`,
   сразу после чтения `meta` (общей и с бюджетом, и с уже читающимся
   `split_assessment`), `store.update_task(conn, task_id,
   zones=meta.get("zones"))`: SPEC без поля (версия < 4) даёт `None` —
   колонка остаётся `NULL`, не пустой строкой (AC-3).
5. Защищённые пути (`templates/SPEC.md` — комментарий про поле `zones:`
   и подсказка-пример в frontmatter; `templates/PLAN.md`/`REVIEW.md`/
   `TEST_REPORT.md` — синхронный подъём `schema_version` 3 -> 4;
   `skills/spec-authoring.md` — инструкция analyst заполнять `zones:` из
   ТЗ, AC-2) НЕ закоммичены в ветку задачи (conventions-core,
   `PROTECTED_PATHS`) — приложены диффом `tasks/01M1NKVPD2A79PQ6K0JVV1B2Q1/
   protected-paths.patch`, `git apply --check` на чистом дереве main
   проходит (проверено этим шагом).
6. Юнит-тесты `tests/test_guard_zones.py` (версия-гейтинг `requires_zones`
   по отдельности — версия 4/выше/3/отсутствует/нечисловая/булева,
   `spec_zones_errors` — не-`spec` тип/старая версия/новая версия без
   поля/с полем/с пустой строкой, сквозной путь через `check_content`,
   точный состав `COMMON_ZONES`) и `tests/test_zones_approve.py`
   (сохранение `zones` на `spec_gate` через реальный git — SPEC без поля
   не роняет approve и оставляет `NULL`, значение не пишется задаче,
   заведённой мимо `spec_gate`, миграция легаси-БД добавляет колонку).
   Каждый тестовый метод несёт докстринг-заявку «Ловит мутацию: …» там,
   где название метода не исчерпывает мутацию самостоятельно (coding-
   standards, прецедент R1-F2 задачи 01M1KS8K9RXWHX2PW3ZKB0P903).

Требование 4 SPEC («Не входит») — уже вне рамок этой части нарезки:
единственный найденный по ходу пункт, который потребовал бы правки, не
покрыт «Не входит» — не обнаружен.

## Влияние на систему

Подъём `scripts/guard.py::SUPPORTED_SCHEMA_VERSION` с 3 до 4 —
единственный способ дать локально приемлемое поведение по AC-1
(залоченная приёмочная фикстура `tasks/01M1NKVPD2A79PQ6K0JVV1B2Q1/
acceptance_tests/_sandbox.py::NEW_ZONES_VERSION = 4` жёстко фиксирует
это число): без подъёма версия 4 всегда отказывалась бы по ДРУГОЙ
причине («новее поддерживаемой»), даже с заполненным `zones`, и второй
сценарий AC-1 (`test_ac1_new_version_with_zones_present_passes`) не
проходил бы никогда.

Подъём этой ОДНОЙ константы задевает `tests/test_guard_schema.py::
TemplatesCarryTheVersionTest` — существующий тест, не из этой задачи,
который требует, чтобы КАЖДЫЙ из четырёх шаблонов (`SPEC.md`, `PLAN.md`,
`REVIEW.md`, `TEST_REPORT.md`) нёс `schema_version`, РАВНЫЙ `guard.
SUPPORTED_SCHEMA_VERSION`. Это исторически сложившийся инвариант (все
четыре шаблона уже синхронно несут `schema_version: 3`, хотя предметное
требование версии 3 — только у REVIEW.md, `requires_registry`) — подъём
общего счётчика без синхронного подъёма ВСЕХ ЧЕТЫРЁХ шаблонов ломает
тест структурно, не по вине конкретной механики зон.

Три из четырёх шаблонов (`PLAN.md`, `REVIEW.md`, `TEST_REPORT.md`) —
защищённые пути ВНЕ зоны этой задачи (зона части 1 — только `SPEC.md`
из шаблонов, и то лишь комментарием про `zones:`, ЗБ «Оценка объёма и
деление» SPEC). Правка защищённых путей — не право разработчика
(conventions-core). Протокол диф-приложения (прецедент
01M1KS8K9RXWHX2PW3ZKB0P903, abddc895) уже покрывает СЛУЧАЙ «нужно
трогать шаблон/скил», но НЕ покрывает СЛУЧАЙ «между коммитом кода на
ветку задачи и применением Оператором диффа к main существующий тест
красный на самой ветке задачи, потому что зависит от файла, который
патч ещё не тронул». `docs/operator-gates.md`/`docs/roadmap.md` не
описывают момент, когда Оператор применяет такой дифф относительно
прогона CI/гейта приёмки — этот разрыв процесса обнаружен впервые
именно здесь (см. «Предложения системе»).

Полный прогон `tests/` на этой ветке (после шагов 1–6): 1433 теста,
**4 красных** — все четыре подтеста `TemplatesCarryTheVersionTest`
(`шаблон='SPEC.md'`/`'PLAN.md'`/`'REVIEW.md'`/`'TEST_REPORT.md'`),
причина одна и та же: `3 != 4`. Остальные 1429 — зелёные, включая
1415 существовавших до этой задачи (полный прогон на чистом `main` до
правок — та же цифра, проверено). `python3 scripts/guard.py --all` —
«ок» (427 файлов): красноту `TemplatesCarryTheVersionTest` guard --all
не ловит (шаблоны сами по себе структурно валидны, просто их
`schema_version` не совпадает с кодом). Приёмочная планка — 6/6.

Откат: тривиален — сама механика (`scripts/guard.py`, `orchestrator/
config.py`/`store.py`/`fsm.py`) не трогает существующие инварианты/
гейты/тесты, только добавляет новые; откатывается ревертом этих файлов
без побочных эффектов на другие задачи. Применение `protected-paths.
patch` синхронизирует все четыре шаблона одним действием — тот же
момент, что закрывает красноту `TemplatesCarryTheVersionTest`.

## Риски

- До применения `protected-paths.patch` любой прогон `tests/` на этой
  ветке (включая CI-джоб `unittest discover -s tests` на `push`) красит
  ровно эти 4 подтеста — предсказуемо и объяснимо (см. выше), не
  скрытая регрессия, но формально это КРАСНЫЙ CI на живой ветке задачи,
  пока Оператор не применит дифф.
- Часть 2 и часть 3 нарезки (`orchestrator/auto.py`/`doctor.py`/
  `catalog.py`; `orchestrator/fsm_advance.py::in_dev`) читают `zones`/
  `COMMON_ZONES` из БД/конфига этой части — их разработчикам предстоит
  тот же класс синхронизации, если версия схемы ещё раз поднимется
  (маловероятно в их зоне: обе части не трогают `schema_version`).

## Предложения системе

- `docs/operator-gates.md`/`docs/roadmap.md` не описывают момент, когда
  Оператор применяет диф-приложение защищённых путей (`protected-paths.
  patch`, прецедент 01M1KS8K9RXWHX2PW3ZKB0P903) относительно прогона
  CI/гейта приёмки живой ветки задачи. Пока протокол не описан, любая
  задача, чей код меняет что-то, за синхронность с чем отвечает и
  защищённый шаблон (здесь — общий счётчик `SUPPORTED_SCHEMA_VERSION`,
  который по конвенции синхронно несут все четыре шаблона), рискует
  красным CI на собственной ветке до применения патча — стоит явно
  зафиксировать: патч применяется Оператором ДО оценки «существующие
  тесты зелёные» на гейте приёмки, а не после.

## Эскалация

### Вопросы

**Вопрос 1 (блокирует — без ответа `status: ready` невозможен).**
Подъём `scripts/guard.py::SUPPORTED_SCHEMA_VERSION` с 3 до 4 (мандатный
для локальной приёмочной планки, `_sandbox.py::NEW_ZONES_VERSION = 4`)
красит существующий `tests/test_guard_schema.py::
TemplatesCarryTheVersionTest` (4 подтеста), потому что три из четырёх
шаблонов, синхронный подъём которых чинит тест (`templates/PLAN.md`,
`REVIEW.md`, `TEST_REPORT.md`), — защищённые пути вне зоны этой части
нарезки. Как поступить?

- **(a) Применить `protected-paths.patch` сейчас — дефолт, если
  Оператор промолчит.** Патч (готов, `git apply --check` на main
  пройден) синхронно поднимает `schema_version` всех четырёх шаблонов
  до 4, добавляет комментарий/пример поля `zones:` в `SPEC.md` и
  инструкцию analyst в `skills/spec-authoring.md`. После применения
  `TemplatesCarryTheVersionTest` зелёный, полный `tests/` — 1433/1433.
  Самый узкий вариант: применяется буквально то, что уже подготовлено и
  проверено этим шагом.
- **(b) Оператор применяет патч НЕ сейчас, а непосредственно перед
  мержем (на `merge_gate`).** Ветка остаётся с 4 красными тестами до
  этого момента — сознательно принятый временный красный CI, ничего
  не меняет в коде, но противоречит принципу целостности до момента
  применения и создаёт риск, что Оператор забудет применить патч перед
  мержем (тот же класс риска, что уже отмечен прецедентом
  01M1KS8K9RXWHX2PW3ZKB0P903 для протокола гейта SPEC).
- **(c) Отложить подъём `SUPPORTED_SCHEMA_VERSION` до части, где будет
  явно решён протокол применения защищённых патчей.** Не проходит:
  залоченная приёмочная планка НЕ пройдёт без версии 4 (см. «Влияние
  на систему») — правка планки не в праве разработчика.
