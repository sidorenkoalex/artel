# SPEC: Механика зон, часть 1: машиночитаемое поле `zones` и общий список зон

## Контекст
Сегодня зоны задачи — текст в ТЗ/SPEC: ревьювер сверяет дифф с ними
глазами, конвейер не знает, какие зоны заняты другими живыми задачами.
Волна из десяти задач с пересечениями по `checkpoint.py`/`doctor.py`/
`gitcmd.py`/`ci.yml` держалась паузами и очередью мержей вручную
(решение Оператора 04.09; копилка роадмапа §4 «механики зон в
конвейере нет»). Нужна машиночитаемая механика: зоны как поле SPEC,
проверка занятости перед стартом кода и сверка фактического диффа с
заявленными зонами.

Деление принято Оператором 04.09.2026 на гейте SPEC (см. «Оценка объёма
и деление»): эта задача — часть 1 (поле и общий список); занятость зоны
на старте кода и сверка диффа при переходе в ревью — отдельные задачи,
заведённые Оператором с текстовой привязкой к этому родителю.

## Требования
1. Машиночитаемые зоны: поле `zones:` во frontmatter SPEC — список
   путей и масок (файлы/каталоги). `guard.py` требует поле для новой
   версии схемы SPEC. Analyst заполняет поле из ТЗ. При `approve` на
   гейте SPEC зоны сохраняются в БД задачи. Поле общее с механикой
   «Оценка объёма и деление» (01M1KS8K9RXWHX2PW3ZKB0P903), которая уже
   структурирует зоны для сигналов деления, — одно поле на обе
   механики.
2. Общие зоны вне конфликта: именованный список в конфиге — пути,
   которые трогают все задачи и конфликты по которым текстовые
   (`orchestrator/config.py`, `docs/codebase-map.md`, `tests/`,
   `roles.yaml`). Пересечение по ним не считается конфликтом.
3. Тесты: `guard` требует поле `zones:` для SPEC новой версии схемы и
   не требует для старой; `approve` на гейте SPEC сохраняет `zones` в
   БД; общий список объявлен в конфиге и читается одной функцией;
   существующий набор тестов остаётся зелёным без ослабления.

## Критерии приёмки
AC-1. Frontmatter SPEC несёт поле `zones:` (список путей/масок);
`guard.py` требует поле для SPEC новой версии схемы (version-gated —
старые SPEC не ломаются, по образцу существующих проверок
`requires_ac_markup`/`requires_split_assessment`).

AC-2. Analyst заполняет `zones:` из ТЗ при написании SPEC.

AC-3. При `approve` на гейте SPEC значение `zones` сохраняется в БД
задачи.

AC-4. В `orchestrator/config.py` объявлен именованный список общих
зон (`orchestrator/config.py`, `docs/codebase-map.md`, `tests/`,
`roles.yaml`); пересечение по путям из этого списка не считается
конфликтом зон ни на одной из проверок ниже.

AC-5. Существующий набор тестов (`tests/`) остаётся зелёным; ни один
существующий тест, гейт, лимит или guard-проверка не ослаблены и не
отключены этой задачей.

## Оценка объёма и деление
Сработавшие сигналы подозрения на большой объём:
- **число затрагиваемых модулей/файлов зоны ≥ 5** — механика трогает
  `orchestrator/store.py` (схема БД), `orchestrator/config.py`
  (общие зоны), `orchestrator/fsm.py`/`orchestrator/fsm_advance.py`
  (сохранение при approve, отказ перехода `in_dev → review`),
  `orchestrator/auto.py` (причина «ждёт зоны»), `orchestrator/
  doctor.py`/`orchestrator/catalog.py` (отображение ожидания),
  `scripts/guard.py` (требование поля) — 7 модулей.
- **число критериев приёмки ≥ 10** — 16 (AC-1..AC-16).
- **бюджет ≥ $30** — `budget_usd: 15` (рамка Оператора в ТЗ).

Деление принято Оператором 04.09.2026; SPEC сужен до части 1, части
2 и 3 заведены отдельными задачами. Исходное решение аналитика —
**нарезка на 3 подзадачи**, границы совпадают с границами
зон ниже; каждая часть самостоятельно мержима с зелёной планкой
(не оставляет систему в промежуточном нерабочем состоянии, не ломает
существующие тесты) и заводится Оператором командой `cmd_new` при
подтверждении этого решения на гейте SPEC — эта аналитическая сессия
выписана в изолированном worktree задачи и не имеет доступа к живому
реестру задач пульта, поэтому подзадачи не заведены отсюда; текстовая
привязка к родителю (01M1NKVPD2A79PQ6K0JVV1B2Q1) — в ТЗ каждой.

1. **«Зоны: машиночитаемое поле и общий список»** (требования 1, 2;
   AC-1..AC-4, AC-16 в части своих тестов). Зоны: `orchestrator/
   store.py`, `orchestrator/config.py`, `orchestrator/fsm.py` (запись
   `zones` при `approve` на `spec_gate`), `scripts/guard.py`, `tests/`.
   Правки защищённых путей (`templates/SPEC.md` — комментарий про
   поле `zones:`, `skills/spec-authoring.md` — инструкция analyst)
   идут диф-приложением к PLAN.md для Оператора, как в прецеденте
   01M1KS8K9RXWHX2PW3ZKB0P903 (abddc895). Мержима первой: добавляет
   только данные (поле, хранение, общий список), не меняет ни одного
   существующего перехода или отказа; поле version-gated — старые
   SPEC не ломаются.
2. **«Зоны: занятость на старте кода»** (требования 3, 5; AC-5..AC-10,
   AC-14, AC-15, AC-16 в части своих тестов). Зоны: `orchestrator/
   auto.py`, блокировка первого шага developer (модуль решает PLAN —
   по образцу существующих блокировок `budget_block`/`parallel_limit.
   refusal`, не новое состояние FSM), `orchestrator/doctor.py`,
   `orchestrator/catalog.py` (отображение), `tests/`. Зависит от
   части 1 (читает `zones`/общий список из БД и конфига).
3. **«Зоны: сверка диффа при переходе in_dev → review»** (требование
   4; AC-11..AC-13, AC-16 в части своих тестов). Зоны: `orchestrator/
   fsm_advance.py` (функция `in_dev`, обрабатывающая переход в
   `review`), `tests/`. Зависит от части 1; независима от части 2 —
   пересекается с ней только по чтению общих данных, не по коду.

Части 2 и 3 обе зависят только от части 1 и не пересекаются друг с
другом по коду — порядок между ними не важен, обе могут идти после
части 1 в любой последовательности.

## Не входит
- Занятость зоны на старте кода, «ждёт зоны», очередь и снятие ожидания
  (требования 3, 5 ТЗ) — часть 2, отдельная задача.
- Сверка диффа с зонами при переходе `in_dev → review` и расширение зон
  по PLAN (требование 4 ТЗ) — часть 3, отдельная задача.
- Автоматическое переупорядочивание задач в очереди на зону —
  переставляет только Оператор явной командой (AC-15).
- Зоны для внешних target — после B2 (по ТЗ).
- Механика родительских задач как таковая — связь подзадачи с
  родителем текстовая (в ТЗ подзадачи), отдельного поля/механики
  родительства эта задача не вводит.
- Само заведение подзадач (`cmd_new`) — действие Оператора при
  подтверждении решения на гейте SPEC (см. «Оценка объёма и деление»);
  эта SPEC описывает разбиение, не выполняет его.
