# PLAN: Отбор циклов на старом коде не зависит от погрешности времени процесса в ОС

## Подход
Вариант (б) SPEC: время старта процесса цикла — интервал возможного
настоящего старта, отбор `stale_cycles` раскладывает цикл по интервалу.

- `orchestrator/doctor/stale_cycles.py::_proc_start_interval(pid)` — точный
  источник Linux. `starttime` (22-е поле `/proc/<pid>/stat`, считается от
  последней `)`, имя команды может нести пробелы) — тики `CLOCK_BOOTTIME`.
  Момент загрузки = `time.time() - time.clock_gettime(CLOCK_BOOTTIME)`, а не
  целосекундный `btime`. Так уходит вторая потеря секунды, которую несёт
  `ps` на Linux. Интервал `[старт − 0,05 с, старт + тик + 0,05 с]` при
  `CLK_TCK` = 100 даёт погрешность до 0,06 с, то есть ≤ 0,1 с (требование 1).
  Таблица читается в процессе (`open`): долгоживущий файл задачи скрывает
  её подменой `open`/`stat`, через подпроцесс её не скрыть. Не Linux, нет
  `CLOCK_BOOTTIME` или сбой чтения либо разбора — `None`.
- `start_interval(pid)` — сначала `/proc`, иначе `doctor.process_start_time`
  (`ps -o lstart=`, без изменений) → `[ответ, ответ + 2 с)`, иначе `None`.
- `stale_cycles` один для `pin.cmd_pin_update` и `check_stale_cycles`.
  Правила: начало интервала `>=` момента сдвига — цикл «новый», не назван;
  конец интервала `>=` момента сдвига — `borderline: True`; иначе «старый».
  `None` — как сейчас, «не удалось определить».
- `stale_cycle_lines`: у пограничного цикла к времени старта дописывается
  « (время старта не различимо от сдвига)», остальные поля строки те же
  (требование 3). `pin.py` и `doctor/__init__.py` не меняются: формат строк
  и фасад прежние, ключ `borderline` читается через `c.get`.

Бюджет SPEC не пересматривается.

## Риски
- На Linux поведение `/proc` проверено арифметикой с подменой и AC-1
  долгоживущего файла. AC-1 на macOS пропускается, впервые он исполнится на
  Linux-раннере CI.
- Если часы стены переставить скачком между стартом цикла и отбором,
  оценка `/proc` сдвинется. Тот же сдвиг даёт `ps`: он тоже считает от
  загрузки.

  источника.

## Эскалация
Код причины: `тест-навязывает-устройство`.

**Вопросы**
1. (блокирует) Метод
   `tests/test_01m3y75gcresc2kds9vprjk4ps_stale_cycles.py::PinUpdateRobustnessTest::test_ac5_undetermined_start_time_is_marked_and_pin_still_moves`
   делает «время старта неопределимо» так: ломает каждую внешнюю команду,
   кроме git (`subprocess.run`/`Popen`). Тем самым он навязывает коду
   внутреннее устройство: время старта читается только внешней командой.
   По требованию 1 SPEC на Linux с доступной `/proc` время берётся из
   `/proc` в процессе и в этом сценарии определимо: цикл стартовал за 1,5 с
   до сдвига, он «старый», пометки «не удалось определить» нет. На
   Linux-раннере CI этот метод станет красным, и main останется красным уже
   на нём, а не на AC-3. На macOS он зелёный, потому что `/proc` там нет.
   Моделирование на macOS (подмена `_proc_start_interval` реальным
   интервалом) даёт провал
   `'не удалось определить' not found … старт процесса 2026-10-02 16:51:41Z`.
   Варианты:
   - (а) `amend-tests` для одного метода. В
     `test_ac5_undetermined_start_time_is_marked_and_pin_still_moves`
     скрыть ещё и таблицу `/proc`: подменить `open`/`io.open`/`os.open`/
     `os.stat` для путей под `/proc` (приём `proc_table_hidden` из
     `tests/test_01m3yqb4kmady0bet5n8279n6b_start_precision.py`).
     Утверждения метода не меняются, `GAP_SEC` тоже. Вводная докстринга
     «не завися от того, какой системной утилитой реализация читает таблицу
     процессов» станет верна и для чтения без утилиты.
   - (б) Брать `/proc` только когда ответил и `ps`. Тест пройдёт, но это
     расходится с требованием 1 («ни один источник не дал ответа —
     неопределимо») и подгоняет код под тест — не рекомендую.
   - (в) Иное решение Оператора.
   **Дефолт при молчании:** (а). Код задачи под (а) готов, менять его не
   нужно. После `amend-tests` сдам PLAN `ready` без правок кода.
