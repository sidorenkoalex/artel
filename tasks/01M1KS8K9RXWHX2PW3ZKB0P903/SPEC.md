# SPEC: Оценка объёма задачи и решение о делении на этапе SPEC

## Контекст

Решение Оператора 03.09.2026 по фактуре трёх сквозных задач: A7 (диф
518 КБ, 56 шагов developer, $135, семь правок планки, пробитый гейт
ёмкости), T094 ($82.50), «Наблюдаемость сессий» ($59, семь раундов
ревью). Все три заведены монолитом без формальной оценки объёма;
вопрос деления A7 обсуждался при заведении и был отклонён без
измеримой цены. Гейт ёмкости диффа (256 КиБ) ловит переразмер ПОСЛЕ
реализации — код уже написан, планка залочена, деление стоит дороже
монолита. Нужен механизм, который заставляет analyst оценить объём
на этапе SPEC, до того как код написан, и заставляет Оператора явно
принять деление либо монолит — с записью, чтобы цена решения была
измерима.

## Требования

1. Система вычисляет из содержимого SPEC набор именованных сигналов
   «подозрения на большой объём» по порогам, заданным именованными
   константами: число затрагиваемых модулей/файлов ≥ 5; число
   критериев приёмки ≥ 10; в тексте зон встречаются слова
   «ориентировочно», «весь оркестратор» или «по факту затронутых
   мест»; `budget_usd` ≥ $30; прогноз размера диффа выше половины
   потолка гейта ёмкости; задача меняет механизм, на который
   опирается запись в `docs/invariants.md`.
2. `templates/SPEC.md` содержит обязательную секцию «Оценка объёма
   и деление»: при срабатывании хотя бы одного сигнала analyst
   перечисляет сработавшие сигналы и даёт либо нарезку на 2–4
   подзадачи (границы зон, порядок, обоснование независимой
   мержимости каждой части с зелёной планкой), либо обоснование
   монолита (что именно нельзя разрезать — атомарная смена
   механики, где промежуточное состояние неработоспособно). Без
   сигналов секция допустима пустой или отсутствующей.
3. `scripts/guard.py` отказывает SPEC, в котором сработал хотя бы
   один сигнал из требования 1, а секция «Оценка объёма и деление»
   не заполнена; отказ называет сработавшие сигналы (тот же класс
   проверки, что «Влияние на систему» в PLAN, инвариант 17). SPEC
   без сработавших сигналов guard принимает независимо от секции.
4. Протокол гейта SPEC (`docs/operator-gates.md`) содержит пункт:
   при наличии сигналов Оператор явно принимает деление либо
   монолит. Решение «монолит» фиксируется в SPEC строкой вида
   «монолит принят Оператором <дата>: <причина>» (правка SPEC на
   гейте для внесения этой строки — законный ход, прецедент T037).
   При решении «деление» analyst заводит подзадачи командой
   `cmd_new`, указывая родительскую задачу в тексте ТЗ каждой
   подзадачи (общая связка текстом; отдельной механики
   родительства в объёме этой задачи нет).
5. `skills/spec-authoring.md` описывает правила нарезки при делении:
   границы частей совпадают с границами зон, каждая часть
   самостоятельно мержима с зелёной планкой, порядок частей — по
   зависимостям, первой идёт часть с механикой, на которую
   опираются остальные; а также описывает шаг «завести подзадачи
   через `cmd_new` с указанием родителя в ТЗ» из требования 4.
6. Команда `artel report` показывает по каждой закрытой задаче
   фактический размер диффа, число шагов и стоимость рядом с
   наличием и содержанием секции «Оценка объёма и деление» — без
   какой-либо автоматической корректировки порогов; материал
   для пересмотра порогов Оператором по факту.
7. Пороги сигналов из требования 1 читаются из именованных констант
   в `orchestrator/config.py`, а не захардкожены внутри проверки.

## Критерии приёмки

AC-1. Пороги сигналов «подозрения на большой объём» заданы именованными
константами в `orchestrator/config.py`: число затрагиваемых
модулей/файлов ≥ 5, число критериев приёмки ≥ 10, `budget_usd` ≥ $30,
прогноз размера диффа выше половины текущего потолка гейта ёмкости.
Прогноз размера диффа — явное поле SPEC (`diff_forecast_kib` во
frontmatter либо строка «Прогноз диффа: N КиБ» в секции «Оценка
объёма и деление»), которое analyst обязан заполнить; отсутствие
поля при прочих сигналах — само по себе сигнал (редактура Оператора
на гейте 04.09).

AC-2. Сигнал «формулировки неопределённости» срабатывает, если текст
зон SPEC содержит хотя бы одно из выражений: «ориентировочно», «весь
оркестратор», «по факту затронутых мест».

AC-3. Сигнал «затронут инвариантный механизм» срабатывает, если хотя
бы один путь из зон SPEC (модуль или файл) упомянут в тексте
`docs/invariants.md` — сопоставление по путям, вычислимое из двух
текстов, без оценки смысла (редактура Оператора на гейте 04.09).

AC-4. `templates/SPEC.md` содержит секцию «Оценка объёма и деление» с
инструкцией по заполнению: при срабатывании сигнала — либо нарезка на
2–4 подзадачи с границами зон, порядком и обоснованием независимой
мержимости каждой части, либо обоснование монолита (что нельзя
разрезать и почему промежуточное состояние неработоспособно); без
сигналов секция может быть пустой или отсутствовать.

AC-5. `scripts/guard.py` отказывает SPEC, в котором сработал хотя бы
один сигнал из AC-1–AC-3, а секция «Оценка объёма и деление» пуста
или отсутствует; сообщение отказа называет каждый сработавший сигнал.

AC-6. `scripts/guard.py` принимает SPEC, в котором не сработал ни
один сигнал, независимо от наличия и содержания секции «Оценка
объёма и деление».

AC-7. `scripts/guard.py` принимает SPEC, в котором сработал сигнал и
секция «Оценка объёма и деление» заполнена (нарезкой либо
обоснованием монолита).

AC-8. `docs/operator-gates.md` содержит в протоколе гейта SPEC пункт:
при наличии сработавших сигналов Оператор явно принимает один из двух
исходов — деление или монолит.

AC-9. Решение «монолит» фиксируется в SPEC строкой вида «монолит
принят Оператором <дата>: <причина>».

AC-10. `skills/spec-authoring.md` содержит правило нарезки при
делении: границы частей — по границам зон, каждая часть
самостоятельно мержима с зелёной планкой, порядок частей — по
зависимостям, первой идёт часть с механикой, на которую опираются
остальные.

AC-11. `skills/spec-authoring.md` описывает, что при решении
«деление» analyst заводит подзадачи командой `cmd_new`, указывая
родительскую задачу в тексте ТЗ каждой подзадачи.

AC-12. `artel report` показывает для каждой закрытой задачи
фактический размер диффа, число шагов и стоимость рядом с наличием и
содержанием секции «Оценка объёма и деление» (если она была).

AC-13. Существующий набор тестов остаётся зелёным.

## Не входит

- Автоматическое деление задачи кодом.
- Механика родительских/дочерних задач в БД.
- Изменение самого гейта ёмкости диффа (текущий потолок 256 КиБ).
