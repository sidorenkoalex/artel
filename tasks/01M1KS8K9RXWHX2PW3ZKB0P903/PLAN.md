# PLAN: Оценка объёма задачи и решение о делении на этапе SPEC

## Подход

Шесть сигналов «подозрения на большой объём» (требование 1) вычисляются
из уже написанного текста SPEC — тем же приёмом, что и существующие
структурные проверки `scripts/guard.py` (регэксп по тексту, без
импорта/исполнения). Пороги — именованные константы `orchestrator/
config.py` (требование 7, AC-1, имена и значения из ANSWER-1):
`SPLIT_SIGNAL_ZONE_FILES=5`, `SPLIT_SIGNAL_AC_COUNT=10`,
`SPLIT_SIGNAL_BUDGET_USD=30`, `SPLIT_SIGNAL_DIFF_FORECAST_RATIO=0.5`.

Источники сигналов:
- число файлов зоны — пути вида `orchestrator/<имя>.py`/`scripts/<имя>.py`
  в разделе `## Зоны` SPEC (ANSWER-1, AC-3) — тот же путь-паттерн
  переиспользуется для сигнала AC-3 (пересечение с `docs/invariants.md`
  по подстроке);
- число критериев приёмки — уже существующий `guard.AC_ITEM` по секции
  «Критерии приёмки» (переиспользуется, не дублируется);
- формулировки неопределённости (AC-2) — поиск трёх фраз по всему тексту
  SPEC (не только по «Зонам»: SPEC не обязан держать «Зоны» отдельной
  секцией, формулировки неопределённости встречаются где угодно в тексте
  требований);
- `budget_usd` — уже разобранное поле frontmatter;
- прогноз диффа (AC-1) — `diff_forecast_kib` frontmatter либо строка
  «Прогноз диффа: N КиБ» в секции «Оценка объёма и деление»; порог —
  половина `REVIEW_SNAPSHOT_DIFF_MAX_BYTES` в КиБ; отсутствие поля само
  по себе сигнал, но только если сработал хотя бы один ДРУГОЙ сигнал
  (ANSWER-1, редактура Оператора 04.09) — иначе «чистый» SPEC без единого
  реального сигнала не заставляли бы вписывать прогноз просто по факту
  отсутствия поля.

Guard отказывает (требование 3, AC-5) только если сигналы есть и секция
«Оценка объёма и деление» пуста/отсутствует; при заполненной секции
принимает независимо от того, СКОЛЬКО сигналов сработало (AC-7) — сама
секция не обязана перечислять сигналы дословно тем же текстом, которым
их называет guard, только не быть пустой. Проверка версионирована тем же
приёмом, что `requires_ac_markup`/`requires_registry` (`schema_version
>= 3`, требование этой задачи): SPEC старше версии 3 (весь беклог до
неё) не подпадает под сигналы задним числом — регресс без этого гейта
пойман прогоном полного набора `tests/` (`tests/test_spec_budget.py`,
фикстура `schema_version: 1` с `budget_usd` выше нового порога стала
красной без версии-гейтинга при первой реализации шага 2).

`diff_bytes`/`split_assessment` (требование 6, AC-12) — новые колонки
`tasks`, заполняются НЕ гейтом, а информационным снимком на переходе
`acceptance -> merge_gate` (ANSWER-1/ANSWER-2: тот же переход для обеих
колонок) — сбой git там не блокирует merge, колонка остаётся NULL,
`artel report` показывает прочерк (уже существующий вырожденный случай
для колонок этого рода, например `fixed_sha`). Diff — только self
target, тем же доводом, что и существующий `fsm_advance.
_capacity_gate_refuses`: `git diff` в `config.ROOT` не видит код
внешнего target. `split_assessment` читает секцию с артефактной ветки
(`tasks/<id>/` живёт только там, A7) независимо от target — это чтение
метаданных задачи, не кода.

Правки защищённых путей (`templates/SPEC.md` — AC-4, `skills/
spec-authoring.md` — AC-10/AC-11) готовятся диффом-приложением к этому
PLAN.md для Оператора (скил conventions-core) — не коммитятся в ветку
задачи. `docs/operator-gates.md` не входит в `PROTECTED_PATHS`
(проверено: списка нет в файле) — правится и коммитится прямо (AC-8).

## Шаги

1. `orchestrator/config.py` — четыре именованные константы порогов
   (требование 7, ANSWER-1): `SPLIT_SIGNAL_ZONE_FILES`,
   `SPLIT_SIGNAL_AC_COUNT`, `SPLIT_SIGNAL_BUDGET_USD`,
   `SPLIT_SIGNAL_DIFF_FORECAST_RATIO`.

2. `scripts/guard.py` — сигналы объёма и проверка секции «Оценка объёма
   и деление» (требования 1, 3): `split_signal_names(text, meta)`
   (шесть сигналов, ANSWER-1 правила для AC-1/AC-3) и
   `split_assessment_errors(path, text, meta)`, подключённая в
   `check_content` для `atype == "spec"`. Юнит-тесты нового поведения —
   `tests/test_guard_split_signals.py` (не приёмочные — те уже
   зафиксированы `tests_writing` и покрывают AC-1..AC-7 чёрным ящиком;
   этот файл добавляет разбор самих функций и граничные случаи,
   которые приёмочная планка не обязана перечислять: например, что
   «прогноз диффа не дан» сам по себе НЕ сигнал без другого сработавшего).

3. `orchestrator/store.py` — колонки `diff_bytes` (INTEGER) и
   `split_assessment` (TEXT) в `SCHEMA`/`migrate()`. `orchestrator/fsm.py`
   — снимок на переходе `acceptance -> merge_gate` (`_cmd_approve`,
   ветка `state == "acceptance"`): читает диф тем же путём, что и
   `_capacity_gate_refuses` (`review.git_diff_part`, только self target),
   и секцию «Оценка объёма и деление» с артефактной ветки (`artifact_
   source.resolve` + `gitcmd.show` + `guard.section_body`) — пусто или
   отсутствует -> буквальная строка «сигналов нет». Сбой git по любой
   из двух колонок не блокирует переход, колонка остаётся NULL.
   `tests/test_split_assessment_merge_gate.py` — новый файл (единственная
   часть задачи, для которой приёмочные тесты НЕ пишут проверку —
   `test_ac_manual_and_escalate_markers.py` фиксирует AC-12 только на
   уровне схемы/отчёта, не на уровне переходной механики; регресс этой
   механики без юнит-теста не поймать никаким гейтом).

4. `orchestrator/report.py` — секция «Закрытые задачи»: по каждой
   `done`-задаче — `diff_bytes` (или прочерк), число записей журнала,
   `spent_usd`, `split_assessment` (или прочерк). Использует уже
   загруженные `tasks`/`steps` из `cmd_report` — ни одного нового
   обращения к git (требование 9 T092 не подвинуто).

5. `docs/operator-gates.md` — пункт 6 раздела «Гейт SPEC»: при наличии
   сработавших сигналов Оператор явно принимает деление либо монолит;
   решение «монолит» — строка «монолит принят Оператором <дата>:
   <причина>» в SPEC (требование 4, AC-8, AC-9 — сам формат AC-9
   остаётся вписываемым Оператором вручную, не валидируется кодом,
   см. пометку `manual` в приёмочных тестах).

6. Диф-приложение к этому PLAN.md (не коммит в ветку задачи) —
   `templates/SPEC.md`: секция «Оценка объёма и деление» с инструкцией
   (AC-4, требование 2); `skills/spec-authoring.md`: правила нарезки
   при делении (AC-10, требование 5) и шаг «заведи подзадачи `cmd_new`
   с указанием родителя в ТЗ» (AC-11, требование 4) — оба диффа
   `git apply --check` перед сдачей.

## Влияние на систему

Новые сигналы и проверка секции затрагивают ТОЛЬКО SPEC (`atype ==
"spec"` в `check_content`) — PLAN/REVIEW/QUESTIONS/ANSWER/TZ не
подвинуты, их существующие тесты (`tests/test_guard_schema.py`,
`tests/test_yaml_parsing.py`, `tests/test_review_registry_gate.py` и
др.) не задеты по построению (новая ветка `if atype == "spec"`, не
общий путь). Существующие проверки `spec_ac_errors` (AC-разметка) не
меняются — новая проверка добавляется РЯДОМ, не переписывает их.

Новые колонки `tasks` (`diff_bytes`, `split_assessment`) — аддитивная
миграция (`add_column`, тот же приём, что и все прежние догоны схемы в
`migrate()`); строки старше миграции читаются как NULL, `update_task`
и без того сверяет имена полей со схемой (`ValueError` на неизвестной
колонке) — новый код не ослабляет эту проверку. `store.all_tasks`
(`SELECT *`) видит новые колонки автоматически, ничего в `report.py`
за пределами новой секции не подвинуто.

Снимок на `acceptance -> merge_gate` — побочный эффект перехода, не
условие: сбой git здесь не должен и не будет отказывать переходу (в
отличие от `_capacity_gate_refuses`, которая ИМЕННО отказывает) — тесты
`tests/test_capacity_gate.py` и существующие тесты `acceptance ->
merge_gate` (`tests/test_branch_freshness_gate.py`,
`tests/test_git_fixation.py`) не должны покраснеть от добавки: снимок
оборачивается в `try`-эквивалент через проверку `reason`/`is None`,
никогда не бросает и не журналирует отказ перехода.

Инвариант 17 (docs/invariants.md, PLAN без «Влияние на систему») —
аналог по классу, не задет: эта задача не меняет PLAN-проверку. Guard
для SPEC остаётся обратно совместим: SPEC без единого сигнала проходит
независимо от секции (AC-6) — старый беклог `tasks/T*/SPEC.md` без
секции «Оценка объёма и деление» и без сигналов не начнёт красниться
(предположение проверено выборочно: `budget_usd` большинства старых
SPEC ниже 30, критериев приёмки почти везде меньше 10 — но задача не
даёт формальной гарантии на 100% беклога, это ожидаемый побочный эффект
introduction нового структурного правила, тем же классом, каким когда-то
была сама AC-разметка T023).

Откат — правка тривиальна: убрать вызов `split_assessment_errors` из
`check_content` возвращает guard к прежнему поведению; колонки `tasks`
можно оставить (не участвуют ни в одном гейте, только в отчёте).

## Риски

- Путь-паттерн `orchestrator/<имя>.py`/`scripts/<имя>.py` для AC-3/
  зон-файлов — буквальный из ANSWER-1, не покрывает пути с `-`/`.` в
  имени модуля за пределами последнего сегмента (`scripts/id_format_
  patterns.txt` — не `.py`, не считается зоной с этой стороны никогда,
  что ожидаемо: это не код-модуль). Не устраняется в рамках задачи —
  сама формула сигнала зафиксирована ANSWER-1 буквально.
- Секция «Оценка объёма и деление» — обычная секция markdown в SPEC,
  а `templates/SPEC.md` в объёме задачи НЕ коммитится в ветку (защищён)
  — до применения диффа Оператором analyst пишет секцию по SPEC этой
  же задачи как примеру и по описанию в PLAN/ревью, не по шаблону.

## Порядок коммита Оператором

1. Оператор применяет оба диффа выше к `main` (или своей ветке правки
   защищённых путей) — оба проверены `git apply --check` на чистом
   дереве этой ветки задачи (та же версия `templates/SPEC.md`/
   `skills/spec-authoring.md`, что и на момент написания этого PLAN.md).
2. Коммит защищённых путей — отдельно от ветки этой задачи (тот же
   порядок, что T046/T072).
