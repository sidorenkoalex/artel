## Подход

Реализация уже закрывает АНSWER-1/ANSWER-2 буквально и проходит весь

   `SPLIT_SIGNAL_BUDGET_USD=30`, `SPLIT_SIGNAL_DIFF_FORECAST_RATIO=0.5`)
   — имена и значения буквально из ANSWER-1.
2. `scripts/guard.py` — `split_signal_names`/`split_assessment_errors`,
   вычисляющие шесть сигналов (число зон, число AC, бюджет, три фразы

3. `orchestrator/store.py`/`orchestrator/fsm.py` — колонки
   `diff_bytes`/`split_assessment`, заполняются
   `_snapshot_split_assessment` побочным эффектом входа в `merge_gate`

   `_capacity_gate_refuses`), секция — с артефактной ветки
   (`artifact_source.resolve`). Сбой git по любой из двух колонок не
   держит гейт (NULL — сигнал «неизвестно», не отказ).
4. `orchestrator/report.py` — секция «Закрытые задачи»: диф/шаги/
   стоимость рядом с `split_assessment`, `_DASH` для NULL (AC-12).
5. `docs/operator-gates.md` — пункт 6 протокола гейта SPEC: явное
   решение Оператора «деление» либо «монолит» при сработавших сигналах
   (AC-8).
6. Юнит-тесты `tests/test_guard_split_signals.py` (сигналы по
   отдельности, версия-гейтинг, старый беклог не ловится) и
   `tests/test_split_assessment_merge_gate.py` (сама механика снимка на
   `merge_gate`, единственная часть без прямого покрытия приёмочной
   планкой — см. докстринг файла).
7. Защищённые пути (`templates/SPEC.md` — секция «Оценка объёма и
   деление», AC-4; `skills/spec-authoring.md` — правила нарезки и шаг

   задачи (conventions-core, PROTECTED_PATHS) — приложены диффом
   `tasks/01M1KS8K9RXWHX2PW3ZKB0P903/protected-paths.patch`,
   `git apply --check` на чистом дереве main проходит (проверено этим
   шагом).

Вся реализация выше — рабочая и покрывает требования 1–7/AC-1–13. Но

## Влияние на систему

Полный прогон `python3 scripts/guard.py --all` на этой ветке (407
файлов до правки → красный после) обнаружил системную регрессию,
которую сама реализация — при полном соответствии SPEC/ANSWER-1/
ANSWER-2 и залоченной приёмочной планке — вносит непреднамеренно:

- `guard --all` валидирует КАЖДЫЙ `tasks/*/SPEC.md` в дереве, не
  только SPEC текущей задачи (CI-джоб `guard` в
  `.github/workflows/ci.yml` вызывает его же на `push` в `task/**`,
  `artifact/**` и `main`).
- Версия-гейтинг новой проверки (`requires_split_assessment`,
  `schema_version >= 3` — тот же приём, что `requires_registry` для
  T100) должен был защитить старый беклог, но НЕ защищает: `schema_
  version: 3` — уже текущий дефолт `templates/SPEC.md` ДО этой задачи
  (используется повсеместно), а не версия, которую вводит эта задача.
  У T100 (`requires_registry`) совпадение оказалось безопасным
  случайно — проверено: ни один существующий `REVIEW.md` на `schema_
  version >= 3` не потерял бы «Реестр замечаний» (0 нарушений). Для
  этой задачи совпадение НЕ безопасно.
- Итог: `guard --all` красит СЕЙЧАС 6 файлов — 5 чужих, уже
  смерженных в `main` задач (`tasks/01M1GCHKG8DDK4DCZWCE3DYKWC/
  SPEC.md`, `tasks/01M1GCN1FPSC1A6WK9WD1Q1V8X/SPEC.md`, `tasks/
  01M1GV6H5DDDCWW4G3GW1D3A1X/SPEC.md`, `tasks/01M1H224X5A8W159MKF1Q24R5Y/
  SPEC.md`, `tasks/01M1KCSTBYF1CRJBSY4P6VYQEA/SPEC.md`) и SPEC САМОЙ
  этой задачи (`tasks/01M1KS8K9RXWHX2PW3ZKB0P903/SPEC.md` — сама несёт
  ≥10 критериев, фразу «по факту затронутых мест» из требования 1
  буквально, и не заполняла секцию, которой на момент её `spec_gate`
  ещё не существовало).
- `docs/retention.md`, «Журнал БД и артефакты гейтов»: «Вечны.
  Retention их не касается никогда» — SPEC/PLAN/REVIEW смерженных
  задач НЕ будут убраны `prune` или чем-либо ещё; проблема не
  рассосётся сама и не разовая, а постоянная — ЛЮБАЯ ветка, где
  `guard --all` затрагивает эти файлы (включая `main` после мержа),
  будет красной, пока кто-то не закроет секцию в этих файлах либо
  не изменит правило.
- Откат: тривиален — сама механика (`scripts/guard.py`, `orchestrator/
  config.py`/`store.py`/`fsm.py`/`report.py`) не трогает существующие
  инварианты/гейты/тесты, только добавляет новый; откатывается ревертом
  этих файлов без побочных эффектов на другие задачи.
- Почему это не решается в рамках этой задачи без Оператора: залоченная
  приёмочная планка (`tasks/01M1KS8K9RXWHX2PW3ZKB0P903/acceptance_
  tests/_sandbox.py`, `SPEC_TEMPLATE`, строка 45) фиксирует фикстуру
  ровно на `schema_version: 3` и требует, чтобы проверка была АКТИВНА
  на этой версии (AC-5/AC-7) — поднять порог версии-гейтинга (например
  до 4) сломало бы саму залоченную планку, править которую разработчик
  не вправе (conventions-core, tasks/T023). Править содержимое чужих
  закрытых задач тоже вне зоны этой задачи (coding-standards,
  «Изменения вне зоны задачи — дефект»). Оба выхода требуют решения,
  которое по конвенции проекта принимает только Оператор (тот же
  класс, что ANSWER-1 — именование констант) — см. «Эскалация» ниже.

## Риски

- До решения Оператора эта ветка (и `main` после мержа) будет красной
  на джобе `guard` CI из-за файлов вне зоны задачи — не только из-за
  своего кода.
- Любая новая задача, чей SPEC случайно наберёт сигнал (обычный случай
  — ≥10 AC не редкость), тоже упрётся в guard, пока действует текущая
  версия-гейтинга — это ОЖИДАЕМОЕ поведение новой задачи (то и есть
  цель SPEC), в отличие от исторических файлов выше.

## Эскалация

### Вопросы

**Вопрос 1 (блокирует — без ответа `status: ready` невозможен).**
Версия-гейтинг новой проверки guard (`schema_version >= 3`) ловит не
только новые SPEC, но и 6 уже одобренных исторических файлов (5 чужих
смерженных задач + SPEC этой задачи), которые `docs/retention.md`
объявляет вечными. Как поступить?

- **(a) Backfill — дефолт, если Оператор промолчит.** Отдельным шагом
  (Оператора либо новой маленькой задачи) дописать короткую секцию
  «Оценка объёма и деление» (или строку «монолит принят Оператором
  <дата>: <причина>» для SPEC этой задачи, раз её `spec_gate` уже
  пройден — прецедент правки на гейте, T037) в шесть перечисленных
  файлов. Ничего не меняет в коде/гейтах, самый узкий и обратимый
  вариант.
- **(b) Исключение по состоянию задачи.** Завести в `guard.py` отдельное
  правило: SPEC задачи, у которой уже есть `docs/retro/<id>.md`
  (задача закрыта ДО появления этой проверки), не подпадает под
  `split_assessment_errors` вовсе. Требует новой развилки в коде
  guard'а (сейчас функция ничего не знает о состоянии FSM/файловой
  системе задачи за пределами своего текста) — больше объёма и
  прецедент («старые закрытые задачи освобождены от новых правил
  guard навсегда»), который стоит явно принять, а не подразумевать.
- **(c) Новый номер схемы вместо переиспользования 3.** Поднять
  `requires_split_assessment` до `schema_version >= 4` и дефолт
  `templates/SPEC.md` — до 4 для новых SPEC. Не позволяет вариант «как
  есть»: локальная фикстура приёмочной планки (`acceptance_tests/
  _sandbox.py:45`, залочена) фиксирует `schema_version: 3` и требует
  проверку активной на этой версии — потребует также попросить
  test_author (или Оператора) пересмотреть залоченную планку, что само
  по себе исключение из «тесты залочены».

**Вопрос 2 (частный случай вопроса 1, для SPEC самой этой задачи).**
Независимо от выбора по вопросу 1 для пяти чужих задач — нужно ли
Оператору прямо сейчас (на этой сессии) дописать секцию/строку
монолита в `tasks/01M1KS8K9RXWHX2PW3ZKB0P903/SPEC.md`, чтобы разблокировать
именно эту ветку? Дефолт при молчании — да, тем же способом, что и
вариант (a) вопроса 1.
