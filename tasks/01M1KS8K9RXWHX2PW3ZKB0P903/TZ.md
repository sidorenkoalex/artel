# ТЗ: Оценка объёма задачи и обязательное решение о делении на этапе SPEC

Источник: решение Оператора 03.09 по фактуре трёх сквозных задач:
A7 (diff 518 КБ, 56 шагов developer, $135, семь правок планки,
пробитый гейт ёмкости), T094 ($82.50), «Наблюдаемость сессий»
($59, семь раундов ревью). Все три заведены монолитом без формальной
оценки объёма; вопрос деления A7 обсуждался при заведении и был
отклонён без измеримой цены. Гейт ёмкости диффа (256 КиБ) ловит
переразмер ПОСЛЕ реализации — слишком поздно: код уже написан,
планка залочена, деление стоит дороже монолита.

Суть: оценка объёма — обязанность analyst на этапе SPEC; наличие
оценки и решения о делении при «подозрении на большой объём» —
проверяет guard; само решение (делить / осознанный монолит) —
Оператор на spec_gate, с записью, чтобы цена решения была измерима.
Механизм ЗАСТАВЛЯЕТ оценить, а не режет сам.

Требуется:
1. Сигналы «подозрения на большой объём», вычислимые из SPEC (набор
   и пороги — именованные константы, стартовые значения): число
   затрагиваемых модулей/файлов зоны ≥ 5; число критериев приёмки
   ≥ 10; в описании зон слова «ориентировочно», «весь оркестратор»,
   «по факту затронутых мест»; рамка бюджета ≥ $30; прогноз размера
   диффа выше половины потолка гейта ёмкости; задача меняет механизм,
   на который опираются инварианты (docs/invariants.md).
2. Обязательная секция SPEC «Оценка объёма и деление» (шаблон
   templates/SPEC.md — мандат этим ТЗ): при любом сигнале analyst
   перечисляет сработавшие сигналы и даёт ЛИБО нарезку на 2–4
   подзадачи (границы зон, порядок, что каждая самостоятельно
   мержима с зелёной планкой), ЛИБО обоснование монолита (что именно
   нельзя разрезать — атомарная смена механики, где промежуточное
   состояние неработоспособно). Без сигналов секция допустима
   пустой/отсутствующей.
3. guard: при наличии сигналов SPEC без заполненной секции — отказ
   (тот же класс, что «Влияние на систему» в PLAN, инвариант 17);
   отказ называет сработавшие сигналы.
4. Гейт SPEC (docs/operator-gates.md — мандат): пункт протокола —
   Оператор явно принимает деление либо монолит; решение «монолит»
   фиксируется в SPEC строкой «монолит принят Оператором <дата>:
   <причина>» (правка на гейте — законный ход, прецедент T037).
   При делении analyst заводит подзадачи через `cmd_new` с указанием
   родителя в ТЗ (общая связка в тексте; отдельной механики
   родительства в объёме нет).
5. skills/spec-authoring.md (мандат): правила нарезки — по границам
   зон, каждая часть мержима отдельно, порядок по зависимостям,
   первой — часть с механикой, на которую опираются остальные.
6. Калибровка (без автоматики): отчётность (`artel report`) показывает
   по закрытым задачам фактический размер диффа, число шагов и
   стоимость рядом с наличием/содержанием оценки — материал для
   пересмотра порогов Оператором по факту.
7. Тесты: guard отказывает SPEC с сигналами без секции и называет
   сигналы; принимает SPEC без сигналов без секции; принимает SPEC с
   сигналами и заполненной секцией (нарезка либо монолит); пороги
   читаются из констант; существующие тесты зелёные.

Зоны: templates/SPEC.md, scripts/guard.py, skills/spec-authoring.md,
docs/operator-gates.md (мандаты этим ТЗ), orchestrator/config.py
(константы порогов), orchestrator/report.py (п.6), tests/. Конфликт
зон с активными задачами — эскалация.

Не входит: автоматическое деление задачи кодом; механика
родительских/дочерних задач в БД; изменение самого гейта ёмкости.

Рамка: $25.
