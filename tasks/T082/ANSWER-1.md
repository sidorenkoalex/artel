## Вопрос 1 — сигнал классификации: гибрид A+B

Классификация — по подстроке в выводе провалившейся попытки
(stdout+stderr, без учёта регистра). Для классов с живой фактурой
SPEC фиксирует ДОСЛОВНЫЕ сигнатуры, снятые Оператором с реальных
логов инцидентов (вариант A):

- **Класс 1а (auth/403, лимит окна)** — из `.artel/logs/T043-developer-*.log`
  (инцидент 27.08, 4 попытки):
  `Failed to authenticate. API Error: 403 Request not allowed`
  Якорные подстроки: `403`, `Failed to authenticate`.

- **Класс 1б (сетевой отказ до API)** — из
  `.artel/logs/T075..T078-*.log` (инцидент 31.08, ~40 мин):
  `API Error: Connection refused — a firewall or proxy may be
  blocking it (ConnectionRefused)`
  Якорные подстроки: `Connection refused`, `ConnectionRefused`.

- **Обрыв потока (подслучай (в), связка со spend.unknown_cost)** —
  из `.artel/logs/T043-developer-*.log`:
  `API Error: Connection lost mid-response. The response above may
  be incomplete.`
  Якорная подстрока: `Connection lost mid-response`.

Общий якорь всех системных ошибок CLI — префикс `API Error:`
(наблюдён во всех трёх сигнатурах): строка с ним = кандидат
в системный класс даже при промахе мимо конкретных подстрок.

- **Класс 2 (session limit подписки)** — живого инцидента НЕ было;
  список предположительный (вариант B), версия 1 эвристики:
  `session limit`, `usage limit`, `5-hour limit`, `resets at`.
  В SPEC пометить явно: уточнить дословной сигнатурой по первому
  срабатыванию (приём наблюдателя-без-полного-знания, триггер №15).

Промах классификатора мимо новой формулировки CLI — признанный
риск: нераспознанная ошибка обрабатывается как сейчас (обычный
провал попытки), хуже текущего поведения не становится; список
подстрок пополняется точечной правкой по факту.

## Уточнение объёма

Сырой текст ошибки провалившейся попытки (или его якорный фрагмент)
отныне должен попадать в журнал шага структурно (не только в лог-файл):
без этого пополнение списка по будущим инцидентам снова упрётся
в «текст нигде не сохранился». Включить в требования.
