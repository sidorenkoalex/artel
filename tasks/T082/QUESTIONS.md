# QUESTIONS: Эвристики ошибок агента: классы отказов и бэкофф

## Вопросы

1. **Каким наблюдаемым сигналом runner отличает друг от друга классы
   отказов, названные в ТЗ (403/лимит окна, сетевой отказ до API,
   session limit подписки) — от обычного провала и друг от друга?**

   Сегодня исход попытки агента (`orchestrator/runner.py:691-872`,
   `run_agent_once`) различает только `rc == 0` / `rc != 0` / таймаут /
   `pump.error` — текст вывода агента (stdout+stderr) никуда программно
   не попадает: он либо просто пишется построчно в лог/консоль
   (`agent_log.render_agent_line`), либо усечённым хвостом уходит в
   причину провала (`agent_log.log_tail`, до `LOG_TAIL_LINES`/
   `LOG_TAIL_CHARS`) — но НИКАК не разбирается кодом на признаки
   403/rate-limit/session-limit/connection-refused. Единственное
   структурное событие ошибки в stream-json — `type: result,
   is_error: true` с полем `result` (человекочитаемый текст, не код
   ошибки) — тоже сейчас только рендерится, не сохраняется для решения.

   Буквального текста реальных ошибок фактур 27.08 (T043) и 31.08
   (T075–T078) нигде в git не осталось: `tasks/T043/PLAN.md` и
   `docs/retro/T043.md`/`T075.md`…`T078.md` пересказывают факт
   («auth 403 посреди шага», «Connection refused»), но не цитируют
   сырой вывод CLI; сами логи (`.artel/logs/T043-*.log`,
   `.artel/logs/T075..T078-*.log`) вне git и вне зоны, куда мне (analyst,
   worktree задачи) есть доступ.

   Это блокирует SPEC содержательно, не только по форме: роль
   test_author пишет приёмочные тесты ДО кода (`tests_writing`
   предшествует `in_dev`) — без зафиксированного в SPEC сигнала
   критерии для классов 1(а) 403/лимит окна, 1(б) сетевой отказ и 2
   (session limit) не собрать детерминированной фикстурой
   (`tests/sandbox.py:126-145`, `claude_only_run`/`claude_only_popen`
   умеют задать `claude_stdout`/`claude_returncode` как угодно — вопрос
   именно в том, ЧТО туда класть, чтобы тест соответствовал реальному
   CLI, а не выдумке).

   Варианты:
   A) Оператор прикладывает буквальные фрагменты (или файлы целиком)
      логов инцидентов — `.artel/logs/T043-*.log` (403) и
      `.artel/logs/T075-*.log`…`T078-*.log` (connection refused), ещё
      живущие на диске пульта, — SPEC фиксирует дословные подстроки из
      них как канонический сигнал. Точнее всего, но требует ручного
      шага Оператора вне git.
   B) SPEC фиксирует документированный предположительный набор
      паттернов (подстрока в stdout+stderr провалившейся попытки, без
      учёта регистра), без сверки с реальными логами:
      — класс 1(а) 403/лимит окна: любая из «403», «forbidden»,
        «rate limit», «429»;
      — класс 1(б) сетевой отказ до API: любая из «connection refused»,
        «econnrefused», «failed to connect», «network error»;
      — класс 2 session limit подписки: любая из «session limit»,
        «usage limit», «5-hour limit», «resets at».
      Промах мимо точной формулировки реального CLI — признанный риск
      первой версии эвристики, чинится точечной правкой списка после
      следующего срабатывания (тот же приём наблюдатель-без-полного-
      знания, что у триггера №15 docs/triggers.md).
   C) Классифицировать не по тексту, а по факту «все попытки шага
      провалились одна за другой быстро» (общая эмпирика обеих
      фактур — секунды между попытками вместо содержательной работы) —
      не различает подкласс (а) от (б) вовсе и не годится для класса 2
      (session limit «ждёт reset», а не «работает быстро»), тот всё
      равно нуждается в текстовом сигнале.
   Дефолт при молчании: **B** — документированный список из этого
   вопроса, версия 1 эвристики; дальнейшая точность — по факту
   следующего срабатывания, не блокирует эту задачу.

затем `approve`: analyst перезапускается с обновлённым ТЗ. Второй батч
по тому же ТЗ — только после ответа на этот; пока задача в `escalated`,
`run` для неё не стартует.
