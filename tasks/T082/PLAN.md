# PLAN: Эвристики ошибок агента: классы отказов и бэкофф

## Подход

Классификатор — чистая функция `runner.classify_attempt_failure(text)`
по подстроке, без учёта регистра, из дословных сигнатур ANSWER-1.
Специфичные списки (1а/1б/обрыв потока/класс 2) проверяются раньше
общего якоря «API Error:» (класс 1, «системный кандидат») — иначе он
перехватывал бы и их (требование 1, «страховка от промаха»).

Классификация вызывается только в ветке `rc != 0` `run_agent_once`
(«неудачная попытка» — буквальная формулировка требований 1-2), на
ПОЛНОМ тексте лога этой попытки (`agent_log.new_agent_log` заводит файл
заново на каждый вызов — чтение целиком не подмешивает соседние
попытки), а не на усечённом `agent_log.log_tail` — иначе длинный вывод
мог бы унести сигнатуру за пределы хвоста. `run_agent_once` возвращает
класс третьим элементом кортежа (`outcome, reason, failure_class`) —
единственный вызыватель, `cmd_run`, использует его для решения о
бэкоффе/немедленном отказе. Внешних вызывателей `run_agent_once` кроме
`cmd_run` в кодовой базе нет (сверено `grep`), сигнатура меняется без
шима обратной совместимости.

`cmd_run`: связка «транзиентное системное» (1а/1б/системный кандидат) —
новая константа `config.TRANSIENT_SYSTEM_BACKOFF_SEC=120` вместо
`RETRY_BACKOFF_SEC=5` в той же формуле удвоения; класс 2 (session limit)
обрывает цикл `for attempt in ...` через `break` сразу после первого
провала — остаток `AGENT_ATTEMPTS` не тратится (требование 4/AC-9), а
эскалация несёт пометку про лимит сессии подписки и reset (AC-10,
печатается тем же `store.set_state`, что уже печатает `detail`).

Алерты (обрыв потока → `spend.unknown_cost`, класс 2 → `alerts
kind=trigger` триггера №15) заводятся явно в новом хелпере
`runner._record_failure_classification` — НЕ внутри `spend.py`
(`charge_missing_result`/`charge_step` не трогаются): требование 5
прямо требует независимости от пути учёта стоимости, а вплетение туда
классификации текста ошибки смешало бы два разных слоя (деньги и
эвристику отказов). Та же функция журналирует сырой текст структурно
(требование 6/AC-13) — отдельной записью `agent failure classified`, не
полагаясь на то, что короткий текст поместится в существующий
`log_tail` хвоста «agent run FAILED» (тот тоже остаётся, не трогается).

Ре-ран CI на `merge_gate` (требование 7/AC-14..17) — правка
`fsm._cmd_approve_merge_gate` ПЛЮС новая пара функций `ci.find_run_id`/
`ci.trigger_rerun`, которых не было в итерации 1 (ревью T082, замечание
blocker): первый красный `ci.branch_status(branch)` теперь ведёт к
`ci.trigger_rerun(branch)` — настоящему повторному прогону
(`gh run rerun <id> --failed`, id ищется отдельным опросом
`actions/runs?head_sha=`, потому что check-run'ы, которые видит
`branch_status`, id прогона не несут), с ожиданием завершения
(`gh run watch <id>`, отдельный, куда больший таймаут
`config.CI_RERUN_WAIT_SEC=1200` — workflow реально идёт минуты, не
секунды REST-опроса) — и только ПОСЛЕ этого гейт спрашивает
`ci.branch_status(branch)` второй раз за итоговым вердиктом (тем же
способом чтения check-runs, что и первый раз, а не заключением
`gh run watch`, у которого свои критерии зелёности). Приёмочный тест
AC-14..17 (`test_ci_flake_rerun.py`) мокает `ci.branch_status` напрямую
и по докстрину сознательно не фиксирует механизм триггера — он не
задет: `ci.branch_status` по-прежнему вызывается ровно дважды при
красном первом статусе, `ci.trigger_rerun` просто встаёт МЕЖДУ ними.
Триггер и ожидание — best-effort (`ci.trigger_rerun` не бросает
исключений): сбой (`gh` недоступен, прогон не найден) не вешает гейт,
второй `branch_status` в этом случае честно увидит тот же красный
статус. Запись журнала на каждый исход — та же, что и раньше
(`статус CI ветки (ре-ран)` + `flake-rate` с различимым текстом
«флейк»/«подтверждённый красный»), плюс новая `ре-ран CI запущен` с
заметкой `trigger_rerun` (видно, что реально произошло — триггернулся
ли прогон, дождались ли завершения, или сорвалось и почему).

## Влияние на систему

Инвариант 3 (числовой лимит цикла, `docs/invariants.md`) не ослаблен:
`AGENT_ATTEMPTS` не меняется нигде, только пауза между попытками
(связка «транзиентное системное») и момент остановки РАНЬШЕ потолка
(класс 2 — то же самое исключение, что уже допускает требование 4 явно,
не новый прецедент). Инвариант 5 (транзиентный ретрай — не итерация
цикла) тоже цел: `review_iters`/`accept_rejects` эта задача не трогает.

`run_agent_once` меняет публичную сигнатуру возврата (2-кортеж →
3-кортеж) — единственный вызыватель в кодовой базе (`cmd_run`,
сверено `grep -rn "run_agent_once("`), внешних потребителей нет.

Гейт `merge_gate` (инвариант 7) не ослаблен: ре-ран добавляет ВТОРОЙ
шанс на зелёный статус, но подтверждённый красный по-прежнему
безусловно отказывает (`sys.exit`), задача остаётся на гейте — то же
поведение, что и сегодня, только после одной дополнительной проверки.
Существующие тесты гейта (`tests/test_invariants.MergeNeedsGreenCiTest`)
не мокают `ci.branch_status` напрямую (мокают `gh`/`git`), поэтому
второй вызов `branch_status` внутри них идёт по тому же мок-пути, что и
первый — красный остаётся красным, зелёный остаётся зелёным, проверено
прогоном полного набора тестов. `ci.trigger_rerun` между ними не
проверяемый ими путь дополнительно ломает: он вызывает `ci.head_sha`/
`ci.gh` (в этих тестах смокан тем же приёмом, что и `branch_status`),
а любой сбой — best-effort, без исключения, второй `branch_status`
после него отрабатывает как прежде.

Внешняя зависимость `gh` (уже обязательная для гейта, `orchestrator/
ci.py`) не расширяется новой командой качественно иначе — `run rerun`/
`run watch` те же права, что уже требует `api commits/.../check-runs`
(чтение и управление Actions одного репозитория); отдельного разрешения
токена ре-ран не заводит новым классом секретов.

Откат — правка одним коммитом-ревертом четырёх файлов (config.py,
runner.py, fsm.py, ci.py); новых миграций схемы БД, новых таблиц, новых
внешних зависимостей нет — `alerts` уже существующая таблица/модуль,
`gh` уже обязательная зависимость гейта.

## Риски

- Список сигнатур класса 2 (session limit) — версия 1, предположительная
  (ANSWER-1, «Не входит»): реальный текст CLI при первом живом
  срабатывании может не совпасть буквально. Промах — не хуже сегодняшнего
  поведения (обычный провал, требование 1/AC-6), только не даёт
  преимущества требования 4. Уточнение — отдельная точечная задача.
- `TRANSIENT_SYSTEM_BACKOFF_SEC=120` — число не зафиксировано SPEC
  («крутилка реализации», см. докстринг приёмочного теста AC-7), взято
  с запасом над порогом критерия (60 с) и с оглядкой на фактуру 31.08
  (минутный бэкофф должен был пережидать ~40-минутный отказ за
  `AGENT_ATTEMPTS`=3 попытки — 120с/240с суммарно даёт запас, не
  переживает весь инцидент целиком, но заметно эффективнее секундного).
