## Замечания

- **blocker** — `orchestrator/fsm.py:1129` (плюс контекст `orchestrator/ci.py:125-153`, не менявшийся этим MR) — «ре-ран» реализован как повторный вызов `ci.branch_status(branch)`, который делает `gh api repos/{owner}/{repo}/commits/{sha}/check-runs` — чистое ЧТЕНИЕ уже существующих check-run'ов того же sha, без единого вызова, который триггерил бы повторное выполнение CI (`gh run rerun`, `gh workflow run` и т.п. нигде в диффе нет — проверено `grep -rn "rerun\|workflow run\|rerequest" orchestrator/ci.py orchestrator/fsm.py`). GitHub не меняет `conclusion` уже `completed` check-run'а сам по себе: сценарий поломки — реально красный (упавший тест, `conclusion=failure`, `status=completed`) CI-прогон на реальном `approve` вызовет `ci.branch_status` дважды подряд без какой-либо паузы и получит ИДЕНТИЧНЫЙ red-результат оба раза (проверено чтением `branch_status`: она детерминированно вычисляет `green`/`note` из ответа `gh api`, не из внутреннего состояния вызова) — гейт всегда пойдёт в ветку «подтверждённый красный» и откажет, ни для одного реального флейка ре-ран не даст задаче ни единого шанса пройти. Приёмочные тесты (`tasks/T082/acceptance_tests/test_ci_flake_rerun.py`) это не ловят, потому что мокают `ci.branch_status` напрямую с `side_effect=[RED, GREEN]` — сценарий, не соответствующий тому, как реальная `branch_status` себя ведёт (сама тестовая обвязка это признаёт в докстринге: «сам механизм триггера ре-рана... тестами не фиксируется»). SPEC сам разводит это явно в разделе «Не входит»: «...эта задача про один ре-ран самого CI-прогона на гейте, не про сетевую надёжность опроса GitHub API» — то есть требуется настоящий повторный запуск CI, а не повторное чтение того же результата (что реализация и делает, вопреки собственной формулировке SPEC). Предложение: заменить второй вызов `ci.branch_status` на реальный триггер повторного прогона (`gh run rerun <run-id> --failed` для головного коммита ветки, с ожиданием его завершения) перед повторной проверкой статуса; если такая трактовка спорна — эскалировать вопрос Оператору явно (SPEC даёт основания для одной интерпретации, реализация выбрала другую без обоснования в PLAN «Риски»), а не решать втихую.

- **major** — `orchestrator/runner.py:91` (`_record_failure_classification`) — сырой текст в журнал пишется как `text.strip()[:config.LOG_TAIL_CHARS]` — срез С НАЧАЛА строки, тогда как весь остальной код (`agent_log.log_tail`, `agent_log.py:44-55`) намеренно берёт ХВОСТ (`text.splitlines()[-LOG_TAIL_LINES:]`, затем `tail[-LOG_TAIL_CHARS:]`) именно потому, что «в них причина падения». Воспроизведено: для текста из ~40 строк обычного вывода агента (2520 символов) перед строкой с сигнатурой `Connection refused` голова `[:1000]` сигнатуру не содержит, а хвост `[-1000:]` — содержит (проверено `python3 -c` с этим текстом). Сценарий поломки: реальный лог попытки агента (stream-json события, tool_use блоки) почти всегда длиннее 1000 символов до финальной ошибки — записанный в `store.journal` «сырой текст» для такой попытки не будет содержать совпавшую сигнатуру, что напрямую противоречит цели требования 6 («доступен для последующего пополнения списков подстрок по будущим инцидентам», ANSWER-1.md, «Уточнение объёма») — по такой записи нельзя будет понять, что именно совпало. Приёмочный тест AC-13 (`test_ac13_journal_raw_text.py`) это не ловит, потому что использует единственную короткую строку на попытку (сигнатура всегда в первых 1000 символах) — сам тест это явно признаёт в докстринге («не доказывает "структурности" хранения... эта грань критерия... тест не проверяет»). Предложение: `text.strip()[-config.LOG_TAIL_CHARS:]` (тот же хвостовой срез, что и `log_tail`), либо вырезать контекст вокруг реально совпавшего фрагмента.

- **minor** — `orchestrator/runner.py:438` — `detail=f"агент не отработал за {attempt} попытки{note}: ..."`: при классе 2 (`session_limit`) `attempt` всегда равен 1 (`break` на первой попытке), и текст получается «за 1 попытки» — грамматически некорректная форма (нужно «за 1 попытку»/«за одну попытку»). Не влияет на AC-10 (текст всё равно опознаётся тестом по словам «session»/«лимит сесси»/«подписк» и «reset»/«сброс»), чисто стилистическая шероховатость в тексте, который увидит Оператор.

## Вердикт

changes_requested — блокер по требованию 7 (ре-ран CI не перезапускает CI-прогон, только повторно читает тот же уже завершённый статус — реального «детекта флейка» в проде не происходит) обязателен к исправлению.
