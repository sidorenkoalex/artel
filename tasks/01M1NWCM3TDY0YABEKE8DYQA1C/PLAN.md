# PLAN: Стоимость частичного шага при таймауте: курс токенов вместо тишины

## Подход

Эскалация вопроса 1 (курс для `developer` против локнутых тестов T040)
уже разрешена Оператором в `ANSWER-2.md` (вариант A: курс заводится на
все четыре роли конвейера, `developer` включительно; два теста T040
переписывает разработчик под новое поведение). Приёмочные тесты
AC-1..AC-9 уже написаны test_author и фиксируют форму реализации
(`config.TOKEN_RATES`, `config.STEP_COST_ESTIMATE_USD`) буквально — план
реализует именно под них, без дополнительных решений по форме.

Ключевые решения:

1. **Курс — таблица словарей в `config.py`**, ключ — идентификатор роли
   (`analyst`, `test_author`, `developer`, `reviewer`), значение —
   `{input_usd_per_token, output_usd_per_token, calibrated_at}`. Одна и
   та же ставка на все четыре роли сегодня: `roles.yaml` не несёт поля
   модели по роли (переход на тариф по модели — отдельная задача,
   ANSWER-1.md, бэклог 04.09). `roles.yaml` не правится (AC-1).

2. **Формула частичной суммы** — `partial_tokens` (уже просуммированное
   число без разбивки на входные/выходные) умножается на среднее цены
   входного и выходного токена роли. AC-2 сознательно не фиксирует
   точную формулу («сумма ненулевая» — единственное жёсткое условие),
   среднее — простейшая честная оценка без разбивки по типу токена.
   Вынесено отдельной чистой функцией `spend.partial_cost_usd(role,
   tokens)`, чтобы юнит-тест мог проверить формулу независимо от
   журнала/БД.

3. **`spent_estimate_usd`** — новая колонка `tasks`, накопительная,
   отдельная от `spent_usd` (решение Оператора ANSWER-1.md вариант B).
   Миграция — `add_column` тем же приёмом, что и остальные колонки
   `store.migrate`; DEFAULT 0 не бэкфиллит прошлые задачи (требование
   9/AC-9). Новые функции `store.charge_estimate`/`store.total_estimate`
   — по образцу существующих `charge`/`total_spent` (SQL живёт только в
   `store.py`, `tests/test_multitarget.py::SqlOnlyInStoreTest`).

4. **`spend.charge_missing_result`** — три ветки вместо двух: без единого
   usage-события поведение T040 не меняется (требование 4); с
   usage-событиями и известным курсом роли — частичная сумма по курсу в
   `spent_usd` (требование 2); с usage-событиями и НЕизвестным курсом —
   верхняя оценка в `spent_estimate_usd` + алерт `kind=threshold`
   (требование 3, повторный отказ прибавляет оценку заново, дедуп только
   у алерта).

5. **Бюджетный гейт** (`budget.budget_block`/`enforce_budget`) — сравнение
   с потолком через новую чистую функцию `budget.spent_with_estimate(t)`
   = `spent_usd + spent_estimate_usd` (требование 5).

6. **`report`/`retro`** — отдельная строка/метрика верхней оценки, не
   слитая с точным расходом (требования 6-7): report показывает её
   всегда (даже $0.00 — фиксированная метрика панели), RETRO — только
   когда `spent_estimate_usd > 0` (условная строка, как решено AC-7).

Архитектурно не значимо — правка внутри уже существующего механизма
T040, новый ADR не нужен.

## Шаги

1. `config.py`: `TOKEN_RATES`, `STEP_COST_ESTIMATE_USD`.
2. `store.py`: колонка `spent_estimate_usd` (схема + `migrate`),
   `charge_estimate`, `total_estimate`.
3. `spend.py`: `partial_cost_usd`, три ветки `charge_missing_result`.
4. `budget.py`: `spent_with_estimate`, `budget_block`/`enforce_budget`
   считают по сумме.
5. `report.py`: `_metrics_html`/`_render`/`cmd_report` — метрика верхней
   оценки отдельной строкой.
6. `retro.py`: `_cost_block` — условная строка оценки, `build_done`/
   `build_killed` передают `spent_estimate_usd`.
7. Правка локнутых тестов T040 (`tests/test_step_cost.py`,
   `ChargeMissingResultTest.test_partial_tokens_are_journaled_without_
   touching_spent`, `CmdRunPartialCostTest.test_timeout_with_usage_
   events_charges_a_partial_token_sum`) под новое поведение — решение
   Оператора ANSWER-2.md, вариант A.
8. Юнит-тесты новых функций (store/spend/budget/report/retro) —
   дополняют приёмочные AC-1..AC-9 угла «чистая функция без БД/journал».

Для Фазы 0 все шаги — один MR (объём одной задачи, все правки в одних и
тех же нескольких файлах, разделять по MR нечего).

## Влияние на систему

Затронуты: `config.py` (новые константы, никакие старые не менялись),
`store.py` (новая колонка со значением по умолчанию 0 — старые строки
не меняют поведение до первого нового частичного шага, требование 9),
`spend.py` (новая ветка внутри уже существующей функции, вызываемой
только из пути таймаут/обрыв пайпа — обычный путь `charge_step` не
тронут), `budget.py` (сумма вместо одной колонки — при
`spent_estimate_usd=0`, то есть у ВСЕХ задач до первого частичного шага
без курса, поведение бит-в-бит прежнее), `report.py`/`retro.py`
(добавленная метрика/строка, существующие не переставлены и не
удалены).

Инварианты и лимиты не ослабляются: бюджетный гейт становится СТРОЖЕ
(считает сумму, а не только `spent_usd` — раньше верхняя оценка нигде
не считалась вовсе), не мягче. Тесты T007/T012 и существующие тесты
T040 остаются зелёными, кроме двух, чьё ожидание переписано решением
Оператора ANSWER-2.md (ADR-0002, класс «изменение теста только решением
Оператора») — само решение и его причина зафиксированы в докстрингах
переписанных тестов.

Откат — правка локальна к перечисленным пяти модулям и одной колонке
БД; откат = revert коммита, новая колонка останется неиспользуемой
(DEFAULT 0), поведение вернётся к T040 без курса.

## Риски

- Формула частичной суммы (среднее цены входного/выходного токена) —
  приближение, а не точный пересчёт (SPEC сознательно не требует
  точности, «не входит»: раздельные счётчики токенов по типу для
  ЧАСТИЧНОГО потока не собираются, только сумма). Задокументировано в
  докстринге `spend.partial_cost_usd`.
- `config.STEP_COST_ESTIMATE_USD = 5.0` — фиксированная оценка без
  привязки к реальной телеметрии несуществующего сегодня прогона роли
  без курса (`verifier`, `executor: none`, агента не запускает).
  Разумный порядок величины для одного шага, не результат расчёта по
  инцидентам — эта ветка кода сегодня не задействуется ни одной реально
  работающей ролью.
