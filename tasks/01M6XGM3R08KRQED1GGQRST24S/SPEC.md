# SPEC: Поверхность решения и размер проверки в критериях SPEC — правила для analyst, аудитора, test_author и ревьювера (ADR-0032, этап 3)

## Контекст
ADR-0032 (принят Оператором 08.11.2026, `e4de84a0`), пп. 1 и 3: критерий-правило
(разбор входа, условие отказа, текст сообщения, выбор ветки) называет в тексте AC
публичную функцию решения; связку команды с функцией держит критерий подключения
по всем состояниям; каждый критерий несёт размер проверки (малый / средний /
большой), большой — с обоснованием. Сейчас правило «свойство без песочницы —
модульным тестом» (`skills/test-authoring.md:192-196`) держится только там, где
SPEC сам назвал публичную функцию, а аналитик называть её не обязан
(`skills/spec-authoring.md:165`). Этап 3 — правила в скилах и шаблоне SPEC; код
пульта не меняется. Скилы и шаблоны — защищённые пути, меняются только
приложениями PLAN (прецедент — задача 01M5NHXJA3X7C66XTJN4J3E25W).

## Требования
1. PLAN.md несёт Приложения 1–5 из `TZ.md` этой задачи (`skills/spec-authoring.md`,
   `templates/SPEC.md`, `skills/spec-audit.md`, `skills/test-authoring.md`,
   `skills/review-checklist.md`) без изменений текста; разработчик переносит их
   как есть. Диффы сделаны против `origin/main` `d87d7d7c`; на этой базе все пять
   проходят `git apply --check` (проверено аналитиком).
2. Новый долгоживущий файл в `tests/` закрепляет, что форма критерия по новым
   правилам совместима с проверками guard: SPEC, у критериев которого есть строки
   «Поверхность решения: …» и «Размер проверки: …» (в том числе
   «большой — <обоснование>»), проходит `scripts.guard.check_content` так же, как
   без них; число критериев и сверка покрытия тестами `test_ac<n>_…`
   (`scripts.guard.traceability_errors_from_content`) не меняются.
3. Ни одного изменения вне `tests/` (новые файлы) и приложений PLAN.

## Критерии приёмки

AC-1. Given ветка задачи на текущей базе с наложенными приложениями PLAN.md, When сравнить пять файлов приложений (`skills/spec-authoring.md`, `templates/SPEC.md`, `skills/spec-audit.md`, `skills/test-authoring.md`, `skills/review-checklist.md`) с результатом наложения Приложений 1–5 из `TZ.md` этой задачи на ту же базу, Then содержимое совпадает. Поверхности решения нет: критерий — факт задачи (разовая группа), отдельного решения в нём нет.
Размер проверки: средний — настоящий git во временной копии.

AC-2. Given текст SPEC в памяти с тремя критериями, у каждого — строка «Размер проверки» (у первого «малый», у второго «средний», у третьего «большой — <обоснование>»), у первого — строка «Поверхность решения: <модуль>.<имя>(<вход>) -> <выход>», When `check_content`, Then отказов нет и найдено ровно три критерия; та же SPEC без этих строк — тот же исход.
Поверхность решения: scripts.guard.check_content(label, text) -> list
Размер проверки: малый

AC-3. Given та же SPEC, где строка размера записана с ведущей цифрой и точкой (`1. Размер проверки: малый`), When `check_content`, Then она отказывает как на пункте без AC-разметки — правила разбора не ослаблены.
Поверхность решения: scripts.guard.check_content(label, text) -> list
Размер проверки: малый

AC-4. Given та же SPEC (со строками поверхности и размера) и набор тестов `test_ac1_…`–`test_ac3_…`, When `traceability_errors_from_content`, Then каждый критерий покрыт, лишних и непокрытых нет.
Поверхность решения: scripts.guard.traceability_errors_from_content(spec_text, meta, tested, markers) -> list
Размер проверки: малый

AC-5. Мутация «`PLAIN_NUMBERED_ITEM` (`scripts/guard.py:169`) срабатывает на строке, начинающейся со слова» делает тесты долгоживущего файла AC-2–AC-4 красными. Поверхности решения нет: критерий — форма тестов.
Размер проверки: малый

Безопасность тестов (для всех критериев): тексты SPEC и тестов — строками в памяти; временная копия для AC-1 — во временном каталоге; каталоги задач и служебный каталог пульта не читаются и не пишутся; без сети.

## Оценка объёма и деление
Сработавшие сигналы: «затронут инвариантный механизм» — текст SPEC называет
`scripts/guard.py`, на который опираются записи `docs/invariants.md`; «прогноз
диффа не дан» — закрыт строкой ниже.

Прогноз диффа: 16 КиБ

Обоснование монолита: `scripts/guard.py` задача только читает (тесты зовут его
функции, код guard не меняется — «Не входит»), так что инвариантный механизм не
меняется. Объём мал: пять приложений из ТЗ (~9 КиБ текста) и один новый файл
`tests/` (~5–7 КиБ), пять критериев, одна зона. Деление по границам зон
невозможно: зона одна (`tests/`), а приложения и тест — единое свойство «новая
форма критерия описана в правилах и совместима с guard»; часть с одними
приложениями оставила бы форму без сторожа совместимости, часть с одним тестом
закрепляла бы форму, которой правила ещё не вводят.

## Не входит
- Правила guard о размерах тестов и метки `pytest.mark.size` (этап 4 ADR-0032).
- Проверка guard'ом наличия строки «Размер проверки» в SPEC — её делает аудитор SPEC.
- Сводка числа больших проверок в выводе гейта SPEC — Оператор читает их в SPEC.
- Правка кода пульта (`orchestrator/`, `scripts/`) и существующих тестов `tests/`.
- Перевод существующих тестов на поверхность решения (этап 8 ADR-0032).
- Зелёный полный набор `tests/` — его держит пульт. Покраснеет существующий тест,
  читающий шаблон SPEC или тексты скилов (например
  `tests/test_01m4rzbdfshnessbqreh5mky9b_role_templates.py`), — эскалация с именем
  теста, без правки теста.
- Неизменность защищённых путей вне приложений PLAN — её держит пульт.
