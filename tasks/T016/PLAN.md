# PLAN: Актуализация design.md по итогам Фазы 0+

## Подход

Документ приводится к факту **статусными пометками внутри существующих
формулировок**, а не переписыванием: целевой дизайн (MVP и полная версия)
остаётся тем же текстом, рядом появляется «Реализовано в Фазе 0, Txxx» либо
«В Фазе 0 не реализовано, …». Так документ продолжает читаться как проект
системы, а не как отчёт о состоянии, и diff остаётся обозримым для ревью.

Источники факта — только репозиторий: docstring `orchestrator/artel.py`,
`orchestrator/config.py` (лимиты и потолки), `docs/invariants.md`,
`docs/adr/0001`, `0002`, `.github/workflows/ci.yml`, `gates.yaml`,
`roles.yaml`, `git log` (даты и состав смерженных задач), SPEC'и задач
T001–T015. Ни одного утверждения «по памяти».

Три решения, которые стоит отметить явно:

1. **Ссылка на источник у каждой правки.** Где механизм пришёл задачей —
   ставится `Txxx`; где он пришёл вместе со скелетом Фазы 0 и задачи-источника
   не существует (гейт плана в одном прогоне, отсутствие REQUEST.md,
   отсутствие branch protection) — ставится `ADR-0001`, который эти
   компромиссы и зафиксировал. Критерий приёмки 2 читается как
   «прослеживаемость до артефакта-источника», и ADR-0001 такой артефакт.
2. **Факт важнее формулировки требования.** Требование SPEC 2 (§6) называет
   фактическую модель запуска «поллинг вместо вебхуков». В коде нет ни того,
   ни другого: `grep` по `orchestrator/*.py` не находит ни одного обращения
   к CI (`subprocess` вызывает только `git` и `claude`), FSM двигают
   исключительно команды Оператора `advance`/`run`/`auto`. В §6 пишется этот
   факт, а не формулировка требования — иначе задача «документ отражает
   факт» решается наполовину. Отмечено в «Рисках».
3. **Юнит-тестов в задаче нет.** Изменение — текст документа; кода не
   добавляется. Проверка «тестом на docs/design.md» означала бы новый файл
   в `tests/`, то есть diff за пределами разрешённого требованием 5
   (`docs/design.md` + `tasks/T016/`) и новый гейт вне зоны задачи.
   Вместо тестов — воспроизводимые проверки шага 3.

## Шаги

1. **Инвентаризация** (таблица ниже) — выполнена до правок, покрывает
   преамбулу и §1–§16.
2. **Правки `docs/design.md`** по колонке «правка» таблицы: §2, §3, §4, §6,
   §7, §8, §9, §10, §11, §12, §13. Один MR — правки связаны одной
   темой и порознь не проверяются.
3. **Проверки** (команды, воспроизводимые ревьювером; результат прогона —
   в скобках):
   - `python3 scripts/guard.py --all` — ок, 38 файлов;
   - `python3 -m unittest discover -s tests` — 249 тестов, OK (регресса нет,
     кода не трогали);
   - `git diff --name-only main...HEAD` = `docs/design.md` + `tasks/T016/*`
     — критерий приёмки 4;
   - `grep -nE 'targets|пульт-приложение|ассистент Оператора' docs/design.md`
     — пусто по всему файлу, не только на добавленных строках:
     критерий приёмки 3;
   - критерий приёмки 2 проверяется **поблочно**, а не построчно: добавленные
     абзацы многострочные, и ссылка стоит внутри абзаца, а не в каждой его
     строке. Проверка: разбить `git diff -U0 -- docs/design.md` по ханкам
     и убедиться, что в каждом ханке есть `T0\d\d`, `ADR-000\d` или
     `инвариант` (17 ханков из 17);
   - целостность правки — **ни одна строка не удалена и не переписана**:
     в diff шесть «удалённых» строк, и все шесть — строки, дополненные
     на месте (5 ячеек таблиц §2/§7 и пункт §10); сверка по ячейкам
     показывает, что исходный текст каждой сохранён дословно как префикс;
   - разнобоя колонок в markdown-таблицах после правки нет (все блоки
     таблиц проверены на равенство числа колонок).

## Влияние на систему

- **Зона изменения** — один файл документации `docs/design.md` и артефакты
  задачи. Исполняемого кода, тестов, конфигов, скилов и CI задача не
  касается: поведение системы после мержа побитово то же.
- **Защиты рядом.** `docs/design.md` — источник, на который ссылается
  колонка «Откуда» реестра `docs/invariants.md` (§2, §4, §6, §7, §10).
  Ни одна правка не отменяет и не смягчает утверждение, на которое
  сослан инвариант: добавляются пометки «реализовано в Txxx» и «в Фазе 0
  не реализовано», сами формулировки требований остаются дословно.
  Ослабления защиты быть не может по конструкции правки — проверяется
  тем, что ни одна строка design.md не удаляется и не переписывается,
  только дополняется (видно в diff).
- **Защищённые пути не затрагиваются.** `PROTECTED` в CI —
  gates.yaml, roles.yaml, .github/, templates/, skills/,
  tests/test_invariants.py, docs/invariants.md; ни один не в diff.
  Предупреждение job'а `protected-paths` не сработает.
- **Откат** — `git revert` одного коммита с правкой документа; никаких
  миграций, состояний в БД и внешних эффектов.
- **Риск занижения статуса.** Обратная опасность тоже учтена: пометка
  «реализовано» на механизме, которого нет, дороже отсутствия пометки —
  поэтому каждое «реализовано» в правке опирается на строку кода, тест
  или инвариант из таблицы инвентаризации, а «не реализовано» ставится
  там, где `grep` по коду пуст (телеграм, CI-триггеры, codebase-map).

## Риски

- **Расхождение с формулировкой требования 2 (§6).** SPEC называет модель
  Фазы 0 «поллинг вместо вебхуков»; фактически CI-триггеров нет вообще.
  Пишется факт (решение 2 в «Подходе»). Если Оператор имел в виду именно
  плановую формулировку — это правка одной строки на ревью.
- **Стареющий README.** В README «Оркестратор — CLI: FSM в SQLite,
  поллинг CI» — та же неточность, что снимается в §6. Правка README
  явно исключена SPEC («Не входит»), поэтому README остаётся расходящимся
  с design.md до отдельной задачи. Зафиксировано здесь, чтобы расхождение
  не потерялось.
- **Объём правок шире минимума требования 2** (добавлены §2, §3, §8, §9,
  §10, §13). Все они — статусные пометки со ссылкой на источник, найденные
  инвентаризацией, которую требует требование 1; каждая занимает одну-две
  строки. Если ревью сочтёт их выходом за зону задачи, они снимаются
  по отдельности, не задевая обязательный минимум.
