# ТЗ: Курс opus-5 и сверка курса с фактом при записи шага

Источник: строка копилки П2 20.09 «Курс токенов в коде устарел после
смены модели» и план провайдеров ролей, принятый Оператором 20.09
(задача 0). Временная правка до переезда тарифа на модель в каталог
`models.yaml` (задача 2 плана).

Факты:
- `orchestrator/config.py::TOKEN_RATES` — четыре цены за токен на
  каждую из четырёх agent-ролей, одинаковые для всех ролей, калибровка
  05.09 под цены Sonnet ($3 вход, $15 выход, $3.75 запись кэша, $0.30
  чтение кэша за миллион). Роли переведены на `claude-opus-5` 13.09
  (roles.yaml, поле `model`), курс не менялся.
- `orchestrator/spend.py::charge_step` пишет «agent cost KNOWN» с
  фактом CLI (`total_cost_usd`) и разбивкой по видам
  (`_tokens_by_type_text`) и прибавляет ФАКТ к `spent_usd`;
  `charge_missing_result` при обрыве шага считает частичную стоимость
  по курсу роли (`partial_cost_usd`) и пишет «agent cost PARTIAL».
  Курс читают только эти две функции и отчёт.
- `orchestrator/report.py::token_rate_divergence` считает коэффициент
  расхождения курса с фактом по роли: сумма расчёта по всем строкам
  KNOWN против суммы фактов, порог
  `config.TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD = 0.5`, алерт через
  `alerts.raise_token_rate_divergence_alert` (дедуп по роли). Считается
  ТОЛЬКО при вызове `report`; с 13.09 отчёт не запускался, алерта нет,
  хотя по 93 шагам с 13.09 факт к расчёту 1.52–1.92 по всем ролям.
- Сверка 20.09 по тем же 93 шагам: прейскурант opus-5 ($5 вход, $25
  выход, $6.25 запись кэша, $0.50 чтение кэша) даёт коэффициент 1.009
  (факт $432.38, расчёт $428.39). Подбор курса по журналу неустойчив
  (входных токенов почти нет, всё через кэш) — курс задаётся по
  прейскуранту и подтверждается сверкой.
- Ущерб от устаревшего курса: один шаг PARTIAL с 13.09 (таймаут
  developer 01M2DC6S) недоучтён примерно на $40 ($57.72 по курсу против
  ≈$97 по прейскуранту).

Требуется:
1. Курс: `TOKEN_RATES` всех четырёх ролей — цены opus-5 (0.000005 /
   0.000025 / 0.00000625 / 0.0000005 за токен), `calibrated_at:
   "2026-09-20"`; комментарий над таблицей дополняется абзацем о
   калибровке 20.09 (модель, коэффициент 1.009 по 93 шагам, метод —
   прейскурант плюс сверка, подгонка по журналу отвергнута и почему).
2. Источник стоимости в журнале: строка «agent cost KNOWN» несёт
   `источник=факт CLI`, строка «agent cost PARTIAL» —
   `источник=расчёт по тарифу`; формат разбивки и поле `actual_usd`
   не меняются (их читает `report._known_cost_breakdown`).
3. Сверка при записи шага: `charge_step` после записи KNOWN считает
   коэффициент расхождения роли тем же способом, что
   `report.token_rate_divergence` (сумма расчёта против суммы фактов),
   но только по строкам KNOWN этой роли с даты `calibrated_at` её
   курса — старые строки другой модели в сверку не входят. Значение
   пишется в ту же строку KNOWN (`расчёт по курсу=$…,
   коэффициент роли с <дата>=…`); коэффициент выше порога
   `TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD` — алерт через существующий
   `alerts.raise_token_rate_divergence_alert` (дедуп по роли
   сохраняется). Общая логика выносится в одну функцию (в spend.py или
   report.py), `report.token_rate_divergence` зовёт её же — два расчёта
   с разной математикой не допускаются. Отказ CLI отдать usage
   (tokens_by_type пуст) — сверка пропускается молча, как сегодня в
   отчёте.
4. Отчёт: `report.token_rate_divergence` по умолчанию тоже считает с
   даты `calibrated_at` роли; строка отчёта называет дату и число шагов
   в сверке.
5. Тесты (tests/): курс всех ролей равен прейскуранту opus-5 и несёт
   дату 20.09; KNOWN несёт источник, расчёт и коэффициент; при
   коэффициенте выше порога алерт заводится в момент `charge_step`, а
   не только в `report`; ниже порога — не заводится; повтор по той же
   роли не плодит алерты; строки KNOWN старше `calibrated_at` в сверку
   не входят; PARTIAL несёт источник «расчёт по тарифу»; `spent_usd`
   по-прежнему получает факт CLI, не расчёт. Существующие
   `tests/test_step_cost.py` остаются зелёными (ожидаемые числа курса
   в них обновляются, если они привязаны к ценам Sonnet — перечислить
   в PLAN).
