# SPEC: Курс opus-5 и сверка курса с фактом при записи шага

## Контекст
`orchestrator/config.py::TOKEN_RATES` несёт четыре цены за токен на каждую
из четырёх agent-ролей, откалиброванные 05.09 под цены Sonnet ($3 вход,
$15 выход, $3.75 запись кэша, $0.30 чтение кэша за миллион). Роли
переведены на `claude-opus-5` 13.09 (`roles.yaml`, поле `model`), курс не
менялся: по 93 шагам с 13.09 факт к расчёту составляет 1.52–1.92 по всем
ролям. Самокорректирующийся контур (`orchestrator/report.py::
token_rate_divergence`) считает расхождение ТОЛЬКО при вызове `report`, а
отчёт с 13.09 не запускался — алерта нет, и один шаг PARTIAL (таймаут
developer 01M2DC6S) недоучтён примерно на $40 ($57.72 по курсу против
≈$97 по прейскуранту). Задача поднимает курс до прейскуранта opus-5 и
переносит сверку курса с фактом в момент записи шага, чтобы расхождение
больше не ждало запуска отчёта. Временная правка до переезда тарифа на
модель в каталог `models.yaml`. Источник — строка копилки П2 20.09 «Курс
токенов в коде устарел после смены модели» и план провайдеров ролей,
принятый Оператором 20.09 (задача 0).

## Требования

1. Курс: `TOKEN_RATES` всех четырёх ролей несёт цены opus-5 — 0.000005
   (вход) / 0.000025 (выход) / 0.00000625 (запись кэша) / 0.0000005
   (чтение кэша) за токен, `calibrated_at: "2026-09-20"`. Комментарий над
   таблицей дополняется абзацем о калибровке 20.09: модель, коэффициент
   1.009 по 93 шагам, метод — прейскурант плюс сверка, и почему подгонка
   курса по журналу отвергнута (входных токенов почти нет, всё через кэш —
   подбор неустойчив).
2. Источник стоимости в журнале: строка «agent cost KNOWN» несёт
   `источник=факт CLI`, строка «agent cost PARTIAL» — `источник=расчёт по
   тарифу`. Формат разбивки по видам и поле `actual_usd` не меняются — их
   читает `report._known_cost_breakdown`.
3. Сверка при записи шага: `charge_step` после записи KNOWN считает
   коэффициент расхождения роли тем же способом, что
   `report.token_rate_divergence` (сумма расчёта против суммы фактов), но
   только по строкам KNOWN этой роли с даты `calibrated_at` её курса —
   строки KNOWN старше этой даты (другая модель) в сверку не входят.
   Значение пишется в ту же строку KNOWN: `расчёт по курсу=$…, коэффициент
   роли с <дата>=…`.
4. Коэффициент выше порога `config.TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD`
   — алерт через существующий `alerts.raise_token_rate_divergence_alert`
   (дедуп по роли сохраняется), заведённый в момент `charge_step`, а не
   только при `report`.
5. Отказ CLI отдать usage (`tokens_by_type` пуст) — сверка пропускается
   молча, как сегодня в отчёте: ни записи коэффициента, ни алерта, шаг не
   падает.
6. Общая логика расчёта выносится в одну функцию (в `orchestrator/spend.py`
   либо `orchestrator/report.py`), `report.token_rate_divergence` зовёт её
   же — два расчёта с разной математикой не допускаются.
7. Отчёт: `report.token_rate_divergence` по умолчанию тоже считает с даты
   `calibrated_at` роли; строка отчёта называет дату и число шагов,
   вошедших в сверку.
8. `spent_usd` на пути `charge_step` по-прежнему получает факт CLI
   (`total_cost_usd`), не расчёт по курсу.
9. Тесты (`tests/`) покрывают: курс всех ролей равен прейскуранту opus-5 и
   несёт дату 20.09; KNOWN несёт источник, расчёт и коэффициент; при
   коэффициенте выше порога алерт заводится в момент `charge_step`; ниже
   порога — не заводится; повтор по той же роли не плодит алерты; строки
   KNOWN старше `calibrated_at` в сверку не входят; PARTIAL несёт источник
   «расчёт по тарифу»; `spent_usd` получает факт CLI. Существующие
   `tests/test_step_cost.py` остаются зелёными — ожидаемые числа курса в
   них обновляются, если привязаны к ценам Sonnet, и перечисляются в PLAN.

## Критерии приёмки

AC-1. `config.TOKEN_RATES` для каждой из четырёх agent-ролей (`analyst`,
`test_author`, `developer`, `reviewer`) несёт `input_usd_per_token`
0.000005, `output_usd_per_token` 0.000025, `cache_creation_usd_per_token`
0.00000625, `cache_read_usd_per_token` 0.0000005 и `calibrated_at`
`"2026-09-20"`.

AC-2. Комментарий над `TOKEN_RATES` несёт абзац о калибровке 20.09,
называющий модель, коэффициент 1.009 по 93 шагам, метод «прейскурант плюс
сверка» и причину отказа от подгонки курса по журналу.

AC-3. Строка журнала «agent cost KNOWN» несёт `источник=факт CLI`, строка
«agent cost PARTIAL» — `источник=расчёт по тарифу`; разбивка по видам и
поле `actual_usd` в KNOWN сохраняют прежний формат —
`report._known_cost_breakdown` читает эту строку без изменений.

AC-4. После записи KNOWN `charge_step` дописывает в ту же строку журнала
расчёт по курсу и коэффициент расхождения роли в виде `расчёт по курсу=$…,
коэффициент роли с <дата>=…`, где `<дата>` — `calibrated_at` курса этой
роли.

AC-5. В сверку входят только строки KNOWN этой роли с даты `calibrated_at`
её курса: строка KNOWN, записанная раньше этой даты, на коэффициент не
влияет.

AC-6. Коэффициент выше `config.TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD`
заводит алерт через `alerts.raise_token_rate_divergence_alert` в момент
`charge_step` (без вызова `report`); коэффициент ниже порога алерт не
заводит; повторный `charge_step` той же роли при том же превышении второй
открытый алерт не плодит.

AC-7. `charge_step` с пустым `tokens_by_type` не пишет коэффициент, не
заводит алерт и не прерывает учёт шага.

AC-8. Расчёт «сумма расчёта против суммы фактов» живёт в одной функции;
`report.token_rate_divergence` вызывает её же, по умолчанию считает с даты
`calibrated_at` роли, и строка отчёта о расхождении называет эту дату и
число шагов, вошедших в сверку.

AC-9. `spent_usd` после `charge_step` увеличивается на факт CLI
(`cost["usd"]`), не на расчёт по курсу; прогон `tests/test_step_cost.py`
зелёный.

## Оценка объёма и деление
Прогноз диффа: 20 КиБ

Сработал один сигнал — «число затрагиваемых модулей/файлов»: по всему
тексту SPEC упомянуто шесть путей `orchestrator/*.py`. Из них правятся
только три (`config.py`, `spend.py`, `report.py`), остальные три
(`alerts.py`, `runner.py`, `store.py`) названы именно как «только чтение» в
разделе «Не входит» — сигнал считает упоминания, а не правки. Остальные
сигналы не сработали: критериев приёмки 9, `budget_usd` 25, формулировок
неопределённости нет, инвариантный механизм (`docs/invariants.md`) зоны не
задевают, прогноз диффа 20 КиБ — ниже половины потолка гейта ёмкости.

Решение — **монолит**. Резать нечего: курс (требование 1) и сверка курса с
фактом (требования 3-7) — одна смена механики учёта. Часть «только новый
курс» оставила бы систему в состоянии, где `report.token_rate_divergence`
считает расхождение по строкам KNOWN двух разных моделей вперемешку (фильтр
по `calibrated_at` ещё не введён) — коэффициент по журналу с 13.09 сразу
перевалил бы порог и завёл ложный алерт по каждой роли. Часть «только
сверка» без нового курса заводит те же алерты по заведомо устаревшему
курсу. Тесты (требование 9) проверяют ровно эту связку и отдельно от неё не
мержимы.
