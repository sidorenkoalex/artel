# REVIEW: Курс opus-5 и сверка курса с фактом при записи шага

## Фаза A: гейт плана

1. **Покрытие требований полно.** Таблица PLAN «Покрытие требований»
   несёт все девять требований SPEC, каждое привязано к шагу 1.
   Пропусков нет.
2. **Размер шага.** Один шаг = один MR (Фаза 0), три файла зоны плюс
   новый тестовый модуль, ~570 строк — размер MR, не микрооперация и не
   «сделать всё». Обоснование монолита (SPEC «Деление»: раздельные части
   оставляют систему с ложным алертом по каждой роли) выдерживает
   критику.
3. **Подход не конфликтует с архитектурой** — с одной оговоркой. Выбор
   `spend` как дома общего расчёта (PLAN, решение 1) верен: `spend` —
   низкий слой, `report` — представление, обратная зависимость развернула
   бы «учёт денег зависит от отчёта». Решение 2 (считать коэффициент ДО
   записи строки) корректно закрывает AC-4+AC-5 без UPDATE журнала,
   который SPEC держит на чтении.
   **Дефект гейта плана:** решение 4 меняет форму возврата публичной
   `report.token_rate_divergence` с `{роль: float}` на
   `{роль: dict}` и объявляет единственным потребителем
   `report.cmd_report`. Это неверно — потребитель есть ещё один, и он
   залочен. PLAN «Влияние на систему» утверждает «Ни один тест `tests/`
   не привязан…», но проверка велась grep'ом ТОЛЬКО по `tests/`;
   `tasks/*/acceptance_tests/` в обзор не попали. Отсюда R1-F1 ниже.
