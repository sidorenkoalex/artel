# SPEC: Очередь мержа FIFO вместо отказа, мёртвые записи очереди, doctor

## Контекст

Мьютекс merge-окна (`orchestrator/merge_lock.py`, SPEC T053) теперь
резервируется на весь цикл `approve` `merge_gate`, включая ожидание CI
(родительская подзадача 01M291EJMA995AZ61MEMDZKWRY, часть 1) — второй
`approve` на занятое окно по-прежнему сразу отказывает
(`merge_lock.acquire`, именованный текст «занято сессией …»), задаче
приходится вручную повторять команду. Решение Оператора 11.09 «единая
очередь мержа»: вместо немедленного отказа второй `approve` должен
ждать освобождения окна в очереди FIFO и получить его сам, без нового
ручного вызова. Эта задача — часть 2 из 2 родительской задачи
01M28VZ8Q1QTP5PRDVJJQ9AQV0, зависит от уже смерженной части 1.

## Требования

1. `approve` на `merge_gate`, встретив занятый мьютекс merge-окна, не
   завершается отказом немедленно, а входит в очередь ожидания и
   опрашивает освобождение окна с интервалом
   `MERGE_GATE_CI_WAIT_POLL_SEC` (тот же, что ожидание CI); вход в
   очередь журналируется записью «ждёт merge-окна: держит <id>»;
   `artel.py status` показывает ожидающую задачу добавкой «[ждёт
   merge-окна: занято <id>, N мин]», по образцу «ждёт зоны»
   (`orchestrator/zone_lock.py::wait_enter_action`/`wait_minutes`,
   `orchestrator/catalog.py::cmd_status`).
2. Ожидающие регистрируются в новой таблице `merge_queue` (колонки
   `task_id`, `session_id`, `pid`, `hostname`, `enqueued_ts`,
   `heartbeat_ts`; схема и миграция — `orchestrator/schema.py`, тем же
   приёмом, что таблица `merge_locks`). Порядок — FIFO по времени входа
   в очередь. Освободившееся окно берёт только голова очереди — прочие
   ожидающие продолжают ждать, даже если мьютекс на момент их опроса
   свободен.
3. Потолок ожидания в очереди — новая именованная константа
   `MERGE_QUEUE_WAIT_CEILING_SEC` (`orchestrator/config.py`, дефолт
   7200 секунд). По истечении — `approve` выходит без merge с
   именованным сообщением, задача остаётся на `merge_gate` (переход
   состояния не выполняется).
4. Потолок ожидания CI (`MERGE_GATE_CI_WAIT_CEILING_SEC`) по-прежнему
   отсчитывается от первого пуша ветки этого `approve`; время,
   проведённое в очереди мержа до входа в окно, в него не засчитывается.
5. Запись `merge_queue` с неживым pid (на своём хосте) или протухшим
   heartbeat (тот же признак мёртвого участника, что
   `merge_lock._holder_is_dead`) удаляется при следующем взятии
   освободившегося окна.
6. `doctor` показывает содержимое очереди `merge_queue` и отдельно
   предупреждает о мёртвых записях в ней — там же, где уже проверяется
   `merge_lock` (`orchestrator/doctor/leases.py::check_merge_lock`).
7. Существующее поведение мьютекса merge-окна и цикла `merge_gate`
   (часть 1: держится на весь цикл `approve`, включая ожидание CI;
   перехват мёртвого держателя; безусловное снятие) не ослабляется.

## Критерии приёмки

AC-1. `approve`, поданный на `merge_gate` при занятом мьютексе
merge-окна, не завершается отказом сразу — регистрируется в очереди
ожидания и опрашивает освобождение окна с интервалом
`MERGE_GATE_CI_WAIT_POLL_SEC`, получая окно после освобождения без
нового ручного вызова Оператора (мутация «второй `approve` отказывает
вместо ожидания в очереди» — красная).

AC-2. Вход в очередь журналируется записью «ждёт merge-окна: держит
<id занявшей задачи>»; `artel.py status` для ожидающей задачи
показывает добавку вида «[ждёт merge-окна: занято <id>, N мин]», по
образцу существующей добавки «ждёт зоны».

AC-3. Ожидающие `approve` регистрируются в новой таблице `merge_queue`
(колонки `task_id`, `session_id`, `pid`, `hostname`, `enqueued_ts`,
`heartbeat_ts`; схема и миграция `orchestrator/schema.py`, тем же
приёмом, что `merge_locks`) и обслуживаются в порядке FIFO по времени
входа в очередь: третий `approve`, поданный пока первые два заняты
окном/в очереди, встаёт третьим.

AC-4. Освободившееся окно merge получает только голова очереди
`merge_queue` — задача не в голове очереди продолжает ждать, даже если
мьютекс на момент её опроса свободен.

AC-5. Два `approve` на разные задачи параллельно: второй встаёт в
очередь, пока первый ждёт CI; после успешного merge первого второй
подтягивает main уже с его изменениями и мержит одной подтяжкой (без
отдельной повторной подтяжки на промежуточном состоянии).

AC-6. Потолок ожидания в очереди — именованная константа
`MERGE_QUEUE_WAIT_CEILING_SEC` (`orchestrator/config.py`, дефолт 7200
секунд): по его истечении `approve` выходит без merge с именованным
сообщением, задача остаётся на `merge_gate`, переход состояния не
выполняется.

AC-7. Потолок ожидания CI `MERGE_GATE_CI_WAIT_CEILING_SEC` отсчитывается
от первого пуша ветки этого `approve` и не увеличивается временем,
проведённым в очереди мержа до входа в окно.

AC-8. Запись `merge_queue` с неживым pid (на своём хосте) либо с
`heartbeat_ts` старше порога, по которому `merge_lock._holder_is_dead`
признаёт держателя мёртвым, удаляется при следующем взятии
освободившегося окна.

AC-9. `doctor` (`orchestrator/doctor/leases.py`) показывает текущее
содержимое очереди `merge_queue` и отдельно предупреждает о мёртвых
записях в ней — рядом с существующей проверкой `merge_lock`
(`check_merge_lock`).

AC-10. Существующие тесты мьютекса merge-окна и цикла `merge_gate`
(держание на весь цикл `approve`, включая ожидание CI — часть 1
родительской задачи) проходят без ослабления и без изменения
содержательных проверок.

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей зоны (5: `schema.py`,
`store.py`, `config.py`, `catalog.py`, `fsm_merge_gate.py` — без учёта
`doctor/leases.py`, не покрытого шаблоном подсчёта); число критериев
приёмки (10); рекомендуемый потолок ($70).

Обоснование монолита: задача реализует ОДНО связное поведение — второй
`approve` ждёт в очереди FIFO вместо немедленного отказа — и его
данные/логика/наблюдаемость технически не режутся по границе зон, не
оставляя рабочую систему в исправном промежуточном состоянии:

- таблица `merge_queue` (`schema.py`) без кода, который в неё пишет и
  из неё вычитывает голову очереди (`fsm_merge_gate.py`), — мёртвая
  схема, не проверяемая приёмочными тестами требования 7 ни в одном
  сценарии;
- логика ожидания/дозы очереди (`fsm_merge_gate.py`, требования 1-5)
  без наблюдаемости в `doctor` (требование 6) — это ровно тот пробел,
  который эта же задача обязана закрыть: новый блокирующий механизм
  ожидания с потолком до 2 часов (`MERGE_QUEUE_WAIT_CEILING_SEC`) без
  видимости мёртвых участников в `doctor` — тот же класс риска, ради
  которого `merge_lock` с самого начала (SPEC T053) получил проверку
  `doctor.check_merge_lock` ОДНИМ шагом с самим мьютексом, не отдельной
  последующей задачей;
- добавка в `status` (`catalog.py`, требование 1) — та же зависимость:
  она показывает состояние ИМЕННО таблицы `merge_queue` и порядка её
  готовы данные появляются только вместе с кодом требований 1-2.

Деление по границам зон в этом случае разрезало бы единственную
механику (очередь) на «данные без потребителя» либо «поведение без
наблюдаемости», а не на две самостоятельно ценных части — оба
получившихся куска либо не мержимы отдельно (пустая таблица), либо
мержимы, но в нарушение уже принятого в этой кодовой базе принципа
«новый lock/wait-механизм получает `doctor`-видимость тем же шагом»
(прецедент T053). Решение утверждает Оператор на гейте SPEC.
