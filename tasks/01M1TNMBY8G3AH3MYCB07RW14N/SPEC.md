## Требования
1. По умолчанию `artel.py auto <id>` и `artel.py run <id>` запускают
   цикл отдельным отвязанным процессом (собственная сессия ОС, не
   наследует управляющий терминал); его стандартные потоки уходят в
   лог цикла (для `auto` — `.artel/logs/<id>-auto-<n>.log`, где `n` —
   порядковый номер запуска). Вызывающая команда сразу печатает pid
   отвязанного процесса, путь лога и подсказку «наблюдать: artel.py
   log <id>» и возвращается, не дожидаясь завершения цикла.
2. Флаг `--attach` у `run`/`auto` сохраняет прежнее (до этой задачи)
   поведение — цикл выполняется в переднем плане вызывающего процесса,
   без отвязки.
3. Lease задачи, взятый отвязанным циклом, несёт pid именно этого
   отвязанного процесса (не pid короткоживущей вызывающей команды) и
   его session_id; heartbeat lease обновляется самим отвязанным
   циклом по ходу шагов, а не вызывающей оболочкой.
4. `doctor` и `artel.py status <id>` показывают живость цикла,
   определённую по pid и heartbeat lease отвязанного процесса.
5. Новая команда `artel.py stop <id>` посылает отвязанному циклу
   задачи штатный сигнал завершения между шагами: текущий шаг роли
   (включая автокоммит и переход FSM) доигрывается до конца, цикл
   пишет запись в журнал задачи и завершается сам.
6. `artel.py kill <id>` по-прежнему прерывает работу задачи немедленно
   — включая принудительное завершение отвязанного процесса цикла,
   если тот ещё жив.
7. Обрыв самого отвязанного цикла не через `stop` (сигнал,
   необработанное исключение) оставляет в журнале задачи запись с
   причиной обрыва, если цикл успевает её записать до завершения.
8. `doctor` различает по pid и последней журнальной записи цикла три
   состояния: цикл жив, цикл завершился штатно, цикл умер.

## Критерии приёмки
AC-1. `artel.py auto <id>` без `--attach` возвращает управление сразу,
напечатав pid отвязанного процесса, путь лога цикла
(`.artel/logs/<id>-auto-<n>.log`) и подсказку `artel.py log <id>`, а
сам цикл run+advance продолжает исполняться в отвязанном процессе
после возврата команды.

AC-2. `artel.py run <id>` без `--attach` так же возвращает управление
сразу, напечатав pid отвязанного процесса, путь собственного лога
цикла и ту же подсказку «наблюдать: artel.py log <id>».

AC-3. Стандартные потоки (stdout/stderr) отвязанного цикла `auto`
пишутся в файл `.artel/logs/<id>-auto-<n>.log`.

AC-4. `artel.py auto <id> --attach` и `artel.py run <id> --attach`
выполняются в переднем плане вызывающего процесса — прежнее (до этой
задачи) поведение команд, без отвязки.

AC-5. Завершение процесса-родителя (промежуточной оболочки),
запустившего отвязанный цикл, не останавливает сам цикл — он
продолжает шаги задачи после того, как породившая его оболочка уже
завершилась.

AC-6. Lease, взятый отвязанным циклом, несёт pid этого отвязанного
процесса, а не pid короткоживущей вызывающей команды.

AC-7. Heartbeat lease отвязанного цикла обновляется самим циклом по
ходу его шагов, а не вызывающей командой.

AC-8. `artel.py status <id>` и `doctor` показывают живость цикла на
основе pid/heartbeat отвязанного процесса, а не факта существования
вызывающей оболочки.

AC-9. `artel.py stop <id>` посылает отвязанному циклу задачи штатный
сигнал завершения; текущий шаг роли (включая автокоммит и переход
FSM), уже начатый к моменту сигнала, доигрывается до конца, после чего
цикл пишет в журнал задачи запись о своём завершении и выходит сам —
`stop` не прерывает уже идущий шаг.

AC-10. `artel.py kill <id>` немедленно прерывает работу задачи, в том
числе принудительно завершает отвязанный процесс цикла, если тот ещё
жив.

AC-11. Обрыв отвязанного цикла сигналом или необработанным
исключением (не через `stop`) оставляет в журнале задачи запись с
причиной обрыва — если цикл успевает её записать до своего завершения.

AC-12. `doctor` различает состояния «цикл жив» (pid жив, свежий
heartbeat lease), «цикл завершился штатно» (в журнале задачи есть
запись о штатном завершении цикла) и «цикл умер» (pid мёртв, записи о
штатном завершении в журнале нет).

AC-13. `tests/test_auto_cycle.py` и существующие тесты lease/liveness
остаются зелёными без ослабления их проверок.

## Оценка объёма и деление

Сработавшие сигналы: число критериев приёмки ≥ 10 (13); `budget_usd`
≥ $30 (ровно порог).

Обоснование монолита: единая механика отвязанного цикла — детач
запуска (`orchestrator/artel.py`), флаг штатной остановки и его
проверка на границе между шагами (`orchestrator/auto.py`),
принудительный захват lease и досылка сигнала прежнему держателю
(`orchestrator/lease.py`, `orchestrator/cleanup.py`). Части не
мержимы по отдельности: `stop` в `artel.py` без флага-обработчика в
`auto.py` не на что слать; `force` в `lease.py` без вызова из
`cleanup.py` — мёртвый параметр; `--attach` без самого детача —
негде проверить, что он воспроизводит прежнее поведение. Реализация
уже целиком выполнена и провалидирована на ветке `keep/
01m1nwchvt-code` (закрытая задача 01M1NWCHVTYQ0M8PCJ1YJ2N78P,
11 из 14 приёмочных методов зелены на момент закрытия) — переносится
готовым диффом (cherry-pick/ручной перенос), не пишется заново;
резать готовую, уже согласованную реализацию поперёк механики только
ради формального деления не даёт самостоятельно мержимых частей.

## Не входит
- Демон-планировщик, запускающий задачи по расписанию или без прямой
  команды Оператора.
- Запуск нескольких циклов одной командой.
- Изменение лимита параллельных задач.
- Изменение механик, с которыми конфликтовала старая приёмочная
  планка закрытой задачи (лимит буксования цикла, гейт ёмкости диффа,
  PATH роли из манифеста стека) — они правятся своими задачами, эта
  задача их только учитывает.
- Ручные правки планки Оператором.
