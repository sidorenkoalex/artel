# REVIEW: Циклы run/auto отвязаны от процесса сессии Оператора (второй заход)

## Фаза A: проверка плана

PLAN.md покрывает все 8 требований SPEC (таблица «Покрытие требований»),
шаг разбит на проверяемые файловые единицы (artel.py / auto.py /
lease.py / cleanup.py / docs / 2 тестовых файла), подход (трёхстороннее
слияние готового диффа `keep/01m1nwchvt-code` с двумя чужими,
смерженными позже механиками) не конфликтует с конвенциями — сверено
прогоном `python3 scripts/codebase_map.py --check` (карта свежая) и
самим diff (зоны PLAN совпадают с фактически изменёнными файлами
+ обязательный спутник `docs/codebase-map.md`). Монолит обоснован
Оператором в SPEC — сверка не требуется повторно.

Один пробел плана: раздел «Подход»/«Влияние на систему» PLAN.md сам
явно фиксирует, что `run`-процессы (без цикла) НЕ получают обработчик
`SIGTERM` и `stop` для них «ведёт себя как раньше» (неперехваченный
сигнал завершает процесс) — но этот пробел не отражён в шаге 5
(правка `docs/operator-session.md`), из-за чего операторская
документация вышла двусмысленной (см. Замечание 2 ниже). План стоило
явно завести отдельным пунктом «стоп для голого run — прежнее резкое
поведение, задокументировать отдельно», чтобы шаг 5 не потерял эту
оговорку по пути из PLAN в docs.

## Замечания

- major — `tests/test_detached_cycle.py` (весь файл, все 24 теста: классы
  `TaskIdAndAttachTest` х5, `LaunchDetachedTest` х5, `CmdStopTest` х5,
  `LeaseForceTest` х4, `KillSignalsDetachedHolderTest` х5) — ни один
  тест не несёт докстринг-заявку «Ловит мутацию: …» (`skills/
  test-authoring.md`, review-checklist Фаза B п.3: «заявки нет вовсе →
  замечание»). Файл целиком новый (создан этим MR), поэтому исключение
  «старый файл, конвенция появилась позже» не применяется — тем более
  что СОСЕДНИЕ артефакты той же задачи (`tasks/01M1TNMBY8G3AH3MYCB07RW14N/
  acceptance_tests/test_ac9_*.py:40-49`, `test_ac11_*.py:40-47`) и
  файлы, которые этот же MR прогоняет как контрольные (`tests/
  test_liveness.py`, `tests/test_lease.py` — 11/32 тестов) конвенцию
  соблюдают, значит она актуальна и достижима. Без заявки нельзя
  проверить, что тест ловит именно заявленную мутацию, а не совпадение;
  сами тесты по чтению выглядят целенаправленными (проверил прогоном —
  все 24 зелёные), но это не заменяет обязательный докстринг.
  Предложение: дописать `Ловит мутацию: …` в докстринг каждого теста
  (или хотя бы каждого метода, где мутация неочевидна из имени) —
  тем же приёмом, что уже применён в `test_ac9`/`test_ac11` этой же
  задачи.

- major — `docs/operator-session.md:150-152` (текст: «`stop <id>`
  останавливает уже идущий цикл штатно (доиграет текущий шаг)») и
  `orchestrator/artel.py:501` `_cmd_stop` — формулировка обещает
  Оператору штатную доигровку шага для ЛЮБОГО отвязанного цикла
  (`run` ИЛИ `auto`, оба «сами отвязываются» по тому же абзацу), но
  `_cmd_stop` адресует SIGTERM ПРОСТО держателю lease (`store.
  lease_row`), не различая, что за процесс его держит. Обработчик
  `SIGTERM` (`orchestrator/auto.py` `_on_sigterm`/`_stop_requested`)
  установлен ТОЛЬКО внутри `auto.cmd_auto` — голый `artel.py run <id>`
  (без `--attach`) такого обработчика не ставит вовсе, и PLAN.md
  (раздел «Влияние на систему») это прямо признаёт: «SIGTERM для них
  ведёт себя как раньше (неперехваченный сигнал завершает процесс)».
  Сценарий поломки: Оператор запускает `artel.py run <id>` (отвязанно),
  видит в доке, что `stop` «доиграет текущий шаг», зовёт `artel.py stop
  <id>` посреди шага роли — процесс обрывается НЕМЕДЛЕННО обычным
  `SIGTERM`-по-умолчанию (без запуска `finally` в `lease.run_locked`,
  без журнальной записи, без завершения автокоммита/перехода FSM,
  которые как раз в процессе) — предсказуемо на каждый такой вызов, не
  изредка. Требование 5 SPEC говорит «отвязанному циклу задачи» без
  явного исключения `run`, и раз требование 1 объявляет отвязанными
  ОБА (`run` и `auto`), а `docs/operator-session.md` не разделяет их в
  предложении про `stop`, текущая документация вводит Оператора в
  заблуждение. Предложение: либо (а) явно оговорить в
  `docs/operator-session.md`, что штатная доигровка `stop` гарантирована
  только для `auto` (для `run` `stop` ведёт себя как раньше — резко),
  либо (б) распространить тот же (или упрощённый — `run` не крутит
  цикл, ему просто нужно доиграть текущий шаг и не начинать следующий)
  механизм на `runner.cmd_run`.

- minor — `orchestrator/artel.py:457` `_launch_detached` — не проверяет
  занятость lease ПЕРЕД спавном отвязанного процесса: до этой задачи
  повторный `run <id>`/`auto <id>` при уже идущем цикле отказывал
  СИНХРОННО, с текстом отказа прямо на экране вызывающей сессии; теперь
  вызывающая команда ВСЕГДА печатает «отвязан от сессии: pid …» и
  возвращается успешно, а сам факт отказа (`сессия занята`) осядет
  только в лог свежесозданного, тут же упавшего процесса — Оператору
  придётся сходить в `artel.py log <id>`, чтобы это заметить. SPEC/AC
  этого не требуют явно, поэтому не blocker, но это заметная потеря
  непосредственной обратной связи по сравнению с поведением ДО задачи.
  Предложение: дешёвая проверка `lease.is_live`-подобная ДО спавна (не
  меняя семантику самого захвата lease внутри процесса) вернула бы
  немедленный отказ на экран, как раньше.

## Предложения системе
- `skills/test-authoring.md` (или `review-checklist.md`, Фаза B п.3):
  проверка «Ловит мутацию» — обязательное поле, но у большого числа
  СТАРЫХ тестовых файлов (напр. `tests/test_kill_cleanup.py` — 0 из 17)
  его нет вовсе; конвенция, судя по всему, введена позже создания этих

  test-authoring явно и заметно требовал докстринг для каждого теста —
  сегодня разработчик, глядя на соседние старые файлы того же модуля
  (`tests/test_lease_pgid_store.py`, `tests/test_kill_cleanup.py`) без
  заявок, мог принять их за актуальный образец и пропустить конвенцию
  (ровно это, похоже, и произошло в R1-F1).
