- blocker — `tasks/01M1NBWPKNBXP9ZXXQDJM7AXPJ/acceptance_tests/_sandbox.py` (добавлен `OriginDivergedSandbox.write_acceptance_plank`, вызов из `setUp`) и `tasks/01M1NBWPKNBXP9ZXXQDJM7AXPJ/acceptance_tests/test_ac3_entry_points_ignore_local_pin.py` (assert `self.state()` изменён с `"review"` на `"verifying"`, докстринг «Ловит мутацию» переписан) — обе правки меняют ЗАФИКСИРОВАННУЮ приёмочную планку задачи 01M1NBWPKNBXP9ZXXQDJM7AXPJ (`done`, `tests_locked_sha` уже проставлен), но ни коммит (`git log -1 --format=%B 59608a88`, `git show 59608a88` — грепом по «ADR» ни разу «ADR-0012»), ни диф ветки целиком (`git diff d6a5a99e...HEAD | grep ADR-0012` — пусто) не несут ссылку на ADR-0012; журнального события штатной команды `amend-tests` тоже нет — правка сделана обычным коммитом в КОДОВОЙ ветке ЭТОЙ задачи (01M1TKP...), а не вызовом `orchestrator/amend.py::cmd_amend_tests` (та команда работает в WORKTREE ЦЕЛЕВОЙ задачи и коммитит плотницки в ЕЁ артефактную ветку `artifact/01m1nbwpknbxp9zxxqdjm7axpj`, обновляя `tests_locked_sha` — ничего из этого не произошло: `tests_locked_sha` задачи 01M1NBWP этой правкой не тронут). ADR-0012 отдаёт право править зафиксированную планку только Оператору («Оператор вправе...», «Инициатива — диагноз Оператора... правка исполняется по воспроизведённому Оператором (или по его команде ассистентом) диагнозу») и ограничивает легальные основания двумя классами (§1): (а) механический конфликт теста с другой защитой системы (линт/guard/формат), воспроизведённый исполнением, либо (б) дефект ФОРМЫ, не меняющий проверяемых свойств (докстринги/маркеры/литералы). Правка `_sandbox.py` ещё может быть отнесена к классу (а) (новый guard `requires_ac_markup` конфликтует с пустым `acceptance_tests/` черновой планки — воспроизведено: 6/9 тестов красны без правки). Но правка `test_ac3_...py` меняет само проверяемое свойство — ОЖИДАЕМОЕ КОНЕЧНОЕ СОСТОЯНИЕ перехода (`"review"` → `"verifying"`), это не дефект формы (докстринг/маркер/литерал), а изменение существа утверждения; по ADR-0012 §1 такой спор о существе идёт «полным циклом пересмотра (эскалация → решение Оператора → test_author заново), не правкой» — эта правка не подпадает ни под одно из двух легальных оснований ADR-0012 вообще, независимо от канала.
  Последствие: планка `done`-задачи изменена в обход единственного признаваемого системой канала (ADR-0012/`amend-tests`) — нарушение принципа целостности (ADR-0002); прецедент, легитимирующий будущие правки чужих locked-планок обычным коммитом в СВОЕЙ ветке без лока/журнала/ADR, если он останется незамеченным.
  Предложение: провести обе правки через фактическую команду `amend-tests` (или ручной путь ADR-0012 — коммит со ссылкой на ADR-0012 + `store.update_task(..., tests_locked_sha=...)` + запись в журнал), выполняемую Оператором на ветке `01M1NBWPKNBXP9ZXXQDJM7AXPJ`, а не разработчиком этой задачи в своей ветке; для правки `test_ac3_...py` — если она действительно нужна (ADR-0015 сдвинул контракт) — провести через полный цикл пересмотра планки (эскалация → решение Оператора → test_author), поскольку меняется существо утверждения, а не форма. До этого текущий diff по обоим файлам `tasks/01M1NBWPKNBXP9ZXXQDJM7AXPJ/acceptance_tests/` из ветки этой задачи стоит убрать.

## Предложения системе

- ADR-0012 различает «форму» и «существо» правки locked-планки (§1), но ни один автоматический гейт (`guard.py`, FSM-переходы) не проверяет фактическое основание правки чужой locked-планки, сделанной обычным коммитом в СВОЕЙ ветке задачи, — только ревьювер вручную сверяет коммит/журнал. Стоило бы завести guard-проверку: диф, трогающий `tasks/<foreign-id>/acceptance_tests/` ЧУЖОЙ (не своей) задачи без соответствующего журнального события `amend-tests` этой чужой задачи в её строке `steps`, — минимум предупреждение, по аналогии с уже существующим `sandbox_reuse_check` этой же задачи.
