## Требования

1. Для записи проекта с `commit_author` окружение роли (`runner.role_env`)
   получает этого автора и коммиттера.
2. Для записи с `commit_author` коммиты пульта в ветке задачи и в
   `refs/artifacts/<id>` — чекпоинт, фиксация, документы задачи, коммит
   `amend-tests`, коммит закрытия, сжатый коммит, merge-коммит подтяжки,
   коммит авторазрешения конфликта подтяжки (`pull.py:462-463`) — получают
   автора и коммиттера `commit_author`.
3. `co_author` дописывается строкой `Co-authored-by` в сообщение каждого
   коммита из требования 2 — пультом при создании коммита, не настройкой,
   которую может сменить роль. Коммиты роли без сжатия не переписываются.
4. Каждый коммит пульта из требования 2 несёт трейлер
   `Artel-Actor: orchestrator`; запись журнала о таком коммите — с `actor`
   `orchestrator`. Трейлер — только сведение: решения гейтов на трейлер без
   журнала не опираются; кода различения коммитов пульта и роли по автору
   или трейлеру задача не заводит.
5. До первой отправки ветки — сверка `commit_author` с владельцем токена
   через адаптер (`forge.token_user`, А1). Пока адаптера нет — шаг
   пропускается с записью журнала «сверка автора — после адаптера».
6. Подготовка ветки на каждом переходе `in_dev → verifying` (ADR-0015
   п. 2): сжатие и перебазирование выполняются ПОСЛЕ всех рубежей перехода
   (`fsm_advance.py:776-821`, в том числе `_review_rework_gate` `:816`),
   непосредственно перед отправкой (`_origin_push_gate`, `:831`) и
   переходом. Рубежи видят ветку, не переписанную этим переходом, — коммиты
   роли.
7. При `squash_before_mr: true` коммиты задачи от точки ответвления от
   `origin/<base>` сжимаются в один с сообщением по `commit_template`
   (`{text}` — название задачи).
8. Метод подтяжки `freshness` на переходе `in_dev → verifying`:
   `merge` — как сейчас, на `fsm_advance.py:771`; `rebase` — перебазирование
   ветки задачи на `origin/<base>` в месте после рубежей (после сжатия),
   только в рабочей копии задачи, `base` не меняется; подтяжки `merge` на
   `:771` при `rebase` нет.
9. Конфликт перебазирования — прежний путь конфликта подтяжки: задача в
   `escalated` с меткой `PULL_CONFLICT_ROLE_STEP_MARKER`
   (`pull.py:575,589`), перебазирование прервано (незавершённого
   перебазирования в рабочей копии не остаётся).
10. `freshness` действует только на переходе `in_dev → verifying`; все
    прочие вызовы узла подтяжки — перед шагом разработчика
    (`runner.py:643`), `pull-main` (`pull_main.py:66`), `approve` приёмки
    (`fsm.py:1577`), гейт мержа (`fsm_merge_gate.py:727`), приёмка канарейки
    (`canary.py:1384`) — прежний `merge` при любом `freshness`.
11. Итоговую (переписанную) голову проверяют приёмка
    (`_acceptance_run_refuses`, `fsm_advance.py:833`, после отправки), CI
    отправленной головы и гейт неослабления по исходам на гейте мержа;
    порядок, при котором приёмка идёт после отправки на итоговой голове,
    сохраняется.
12. Без новых полей записи поведение перехода `in_dev → verifying` не
    меняется.
13. Перезапись своей ветки (после сжатия/перебазирования) — только
    `push --force-with-lease=refs/heads/<ветка>:<sha>`, где `<sha>` — из
    последней записи журнала задачи «ветка отправлена: <sha>» (её пишет
    единая точка отправки части 1 после успешной отправки). Записи нет —
    первая отправка, без перезаписи.
14. Голова на сервере не совпала с этим sha — чужой коммит: эскалация
    задачи в `_origin_push_gate` (`advance_gates/tests_writing.py`), без
    перезаписи.
15. На гейте мержа (`fsm_merge_gate.py:701`) поведение без изменений —
    перезаписи там нет. В `github_adapter.py` меняется только место
    отправки ветки; поведение черновика MR не меняется.
16. Пакет ревью (`review.py`): если ветка задачи перезаписана после
    прошлого ревью (sha прошлого вердикта не предок головы), пакет несёт
    полный дифф задачи с явной пометкой «ветка перезаписана — дифф полный»,
    а не инкрементальный дифф от sha прошлого вердикта; без перезаписи пакет
    прежний.

## Критерии приёмки

AC-1. Перезапись: `--force-with-lease` несёт sha последней записи журнала
«ветка отправлена»; без такой записи — отправка без перезаписи; голова
сервера другая — на переходе `in_dev → verifying` задача в `escalated`,
отправки нет.

AC-2. `squash_before_mr: true` и `freshness: rebase` на фикстурном
репозитории: после перехода в `verifying` в ветке задачи один коммит с
сообщением по шаблону `commit_template`, автором и коммиттером
`commit_author`, строкой `Co-authored-by` и трейлером
`Artel-Actor: orchestrator`; ветка поверх `origin/<base>`, `base` не
изменён.

AC-3. `freshness: merge`, `origin/<base>` впереди, без сжатия: merge-коммит
подтяжки и коммит авторазрешения конфликта (`pull.py:462-463`) — с автором
`commit_author`, строкой `Co-authored-by` и трейлером
`Artel-Actor: orchestrator`.

AC-4. `freshness: merge`, `origin/<base>` впереди, `squash_before_mr: true`:
после перехода в `verifying` в ветке один коммит поверх `origin/<base>` с
`commit_author` и строкой `Co-authored-by`.

AC-5. Конфликт перебазирования — задача в `escalated` и метка
`PULL_CONFLICT_ROLE_STEP_MARKER`, как у конфликта `merge`; незавершённого
перебазирования в рабочей копии задачи нет.

AC-6. После `changes_requested` без коммита developer
(`squash_before_mr: true`, `freshness: rebase`, `origin/<base>` впереди)
`advance` из `in_dev` отказан рубежом переделки ревью, задача в `in_dev`,
голова ветки не изменилась.

AC-7. Запись с `commit_author`: окружение роли и коммиты пульта — чекпоинт,
документ в `refs/artifacts/<id>`, коммит `amend-tests` (`amend.py:799`),
коммит закрытия (`snapshot.py:272`) — несут этого автора, строку
`Co-authored-by` и трейлер `Artel-Actor: orchestrator`; без адаптера — в
журнале задачи запись «сверка автора — после адаптера».

AC-8. Ветка перезаписана сжатием/перебазированием после прошлого ревью —
пакет ревью следующей итерации несёт полный дифф задачи и пометку «ветка
перезаписана — дифф полный»; без перезаписи — прежний инкрементальный дифф.

AC-9. `freshness: rebase`: подтяжка перед шагом разработчика, `pull-main`,
`approve` приёмки, гейт мержа и приёмка канарейки (`canary.py:1384`) —
прежний `merge`.

  даёт ревьюверу дифф от sha, не являющегося предком головы, — пакет
  ревью следующей итерации неверен;

  `snapshot.py`, `artifact_branch.py`, `runner.py`) теоретически
  отделимы, но выдают одно и то же правило подписи коммита пульта, на
  которое опирается сжатие; отдельная часть дала бы ещё один цикл гейтов
  ради 1–2 файлов при той же рамке родителя.
Новые поля без перечисленного не включаются (требование 12), так что
промежуточного состояния на main с полями по умолчанию нет, — но
разрезанные части с новыми полями по отдельности неработоспособны.
