## Пути обхода гейтов
- **Е1 — отказ отправки не по сети.** Тр. 16 (SPEC.md:159-168) различает только «чужую голову» (успешный `ls-remote`, sha другой) и «сбой сети». Не определены исходы, когда `ls-remote` прошёл и sha совпал, а `push --force-with-lease` отвергнут сервером:
  - lease устарел из-за гонки — чужой коммит пришёл между `ls-remote` и отправкой;
  - запрет force-push на защищённой ветке GitLab/GitHub;
  - отказ хука `pre-receive`.

  Сегодня любой такой отказ — «переход отклонён: голова не в origin» (`advance_gates/tests_writing.py:64-67`). Исполнитель может буквально выполнить SPEC и:
  - классифицировать гонку lease как «сеть». Тогда чужой коммит не эскалируется, а повторный `advance` при новом `ls-remote` увидит чужую голову — в лучшем случае на круг позже;
  - оставить локальную ветку переписанной: возврат к голове до сжатия обязателен только для трёх перечисленных исходов (SPEC.md:164-168).

  Нужно решение: lease отвергнут → «чужой коммит» (эскалация); прочий отказ сервера → отказ перехода; во всех случаях — возврат ветки.
- **Е2 — отказ сверки автора на переходе.** Сверка (тр. 6) стоит в точке отправки, то есть после сжатия/перебазирования. На переходе её отказ эскалирует задачу (SPEC.md:91-93), но в перечень возврата локальной ветки (SPEC.md:166-168) он не входит. После такой эскалации ветка задачи остаётся сжатой и неотправленной. Следующий шаг разработчика идёт по переписанной истории, которую не видел ни один рубеж-наблюдатель на origin. Решение гейта №3 п.3 называет только «сеть» и «чужой коммит», но смысл решения («рабочая копия и ветка — как до переписывания») распространяется и на этот исход.
- **Е3 (низкая важность) — `refs/artifacts/<id>` до сверки.** Сверка закрывает только первую отправку ветки задачи (SPEC.md:87-89). Коммиты `refs/artifacts/<id>` с `commit_author` (тр. 2) уходят на origin через `artifact_branch._send` с первого документа задачи (`new`, `tests_writing`) — до всякой сверки. Буквально тр. 6 это не запрещает. ТЗ («До первой отправки — сверка») тоже читается про ветку задачи, поэтому это пункт к сведению Оператора, не нарушение.
- **Сверка автора без `commit_author`** — п.1 вердикта: при буквальном исполнении закрытая по умолчанию сверка либо ломает отправки проекта без поля, либо меняет журнал артели.

Других обходов не найдено:
- рубеж переделки ревью при сжатии держится — место после `:816`, AC-8;
- WIP не коммитится после рубежей — тр. 8, AC-5, AC-7;
- `freshness` вне перехода закрыт — AC-15.

## Вердикт
`concerns`: это решения Оператора на гейте, а не возврат аналитику. Гейт №3 объявлен последним возвратом, и отклонения точечные.

1. **Область сверки автора.** Тр. 6 (SPEC.md:83-101) и AC-12 (SPEC.md:259-275) не оговаривают, что сверка выполняется только для записи с `commit_author`. Буквально без поля:
   - (а) журнал артели получает «сверка автора — после адаптера» при каждой первой отправке — противоречие SPEC.md:82 и тр. 14 SPEC.md:149-151; риск для `tests/test_01m44enqcrk02t2mwzb9hc3xhh_origin_push.py:126-127`;
   - (б) для forge не `github` закрытая сверка отказывает каждую отправку.

   Предлагаемое решение: «сверка — только при `commit_author`; без поля — ни вызова `token_user`, ни записи журнала», плюс пункт AC-12.
2. **Отказ `push --force-with-lease` не по сети** (lease отвергнут гонкой, запрет force-push, хук) не определён: ни класс исхода («чужой коммит» или отказ перехода), ни возврат локальной ветки (SPEC.md:159-168, AC-1 SPEC.md:181-191).
3. **Отказ сверки автора на переходе после сжатия** не входит в перечень возврата локальной ветки к голове до сжатия (SPEC.md:166-168 против SPEC.md:91-93).
4. **Номера строк:**
   - ёмкость и зоны — `fsm_advance.py:786`/`:788`, не `:782`/`:784` (SPEC.md:41, матрица SPEC.md:293);
   - вызов узла перед шагом разработчика — `runner.py:665`, не `:643` (SPEC.md:140, унаследовано из ТЗ).

   Суть не меняется.
5. **К сведению:** коммиты `refs/artifacts/<id>` с `commit_author` уходят на origin до сверки автора (Е3), что согласуется с буквой ТЗ.
