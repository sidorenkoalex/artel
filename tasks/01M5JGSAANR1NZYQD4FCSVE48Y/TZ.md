## Требуется

1. **Компонент задачи.** `project_profile.task_components(target, zones) -> tuple[str, ...]` — компоненты, чьи `paths` или маски `test_support` задевают путь зон, без расширения потребителями `depends_on`, в порядке записи; пути вне всех компонентов выбор не расширяют. `project_profile.decide_task(target, zones) -> Decision`: сначала `decide(target)`; выбор компонента по зонам — только когда это отказ записи из нескольких компонентов (`profile_of(target).multi`), иначе результат `decide` как есть побайтно (артель, `test_profile`, запись из одного компонента, неразрешённый контекст, `TargetsError`, подмены `decide` в тестах); у записи из нескольких компонентов: зоны не заданы — отказ «зоны задачи не заданы — компонент задачи на записи из нескольких компонентов не выбран»; ни одного компонента — отказ «зоны задачи не задевают ни одного компонента записи»; два и более — отказ «задача затрагивает несколько компонентов (<имена>) — дели задачу по компонентам (решение Оператора 20.10)»; ровно один — профиль этого компонента с полями, как у `with_tools` единственного компонента (обязательные подполя профиля — та же проверка, что у `profile_of`, отказ с именем компонента). Каждый текст отказа `decide_task` включает причину `decide` дословно (решение Оператора 22.10, вопрос 2-Б): тест `tests/test_01m5hj3yfbvk8tsr7vq7jpyj7c_amend_plank_only.py::Ac5MultiComponentDecisionTest::test_ac5_multi_component_decision_refusal_on_approve` остаётся зелёным без правок. `for_task(conn, task_id)` = `decide_task(<проект задачи>, task_zone_paths(<строка задачи>))`; зоны строки задачи читаются только у записи из нескольких компонентов. `decide(target)` и `profile_of` у записи из нескольких компонентов — прежний отказ; текст `MULTI_COMPONENT_PENDING` — «запись проекта с несколькими компонентами: профиль выбирается по зонам задачи».
2. **Места задачи — через `for_task`.** Каждое место, берущее профиль в контексте задачи, — `for_task` вместо `decide(target)`; `acceptance._task_profile` и `_task_own_profile` — профиль компонента задачи вместо `ComponentsPending`; `ComponentsPending` — только при отказе `for_task` у записи из нескольких компонентов, у прочих отказ — прежний `None`, `conn=None` — прежний путь; уборка выкладки (`orchestrator/acceptance.py:2166`) у задачи с компонентом убирает выкладку компонента. У записи из нескольких компонентов ни одно место не превращает отказ `for_task` в пропуск проверки: `_bounds`, `_test_integrity_diff_gate`, автогейт, пакет ревьювера — отказ или эскалация с причиной; у прочих записей — прежнее поведение (тест `tests/test_01m5cjvb5b5v55pqqvr2qrhwzn_outcome_gate.py::Ac1OutOfBoundsTest::test_ac1_decide_skip_refusal_and_canary_no_gate` без правок). Автогейт: граница у записи из нескольких компонентов — компонент задачи в `in_outcome_bounds` и не канарейка; у прочих `_plank_rule_refusal(rule, t)` со строкой без зон и id — как прежде. Предел полного набора в контексте задачи — `component_limit` компонента задачи; сам полный набор на мерже — `_selected_components` по диффу, без сужения до компонента задачи. Мандат ослабления (решение Оператора 22.10, вопрос 1-А): элемент «Ослабление тестов разрешено:» годен для находки любого компонента записи в границе гейта исходов — `_weakening_scope_refusal` и `_test_id_refusal` (`orchestrator/advance_gates/mandate.py`) меняются только в этой части: находка «сломан правкой» в компоненте-потребителе у задачи другого компонента снимается мандатом, выданным `answer`; ложного текста «компонента нет в записи» для компонента, который в записи есть, нет.
3. **Компоненты гейта по диффу.** Гейт исходов на обоих рубежах берёт компоненты `select_components(<проект>, <пути диффа>)` (с потребителями; сбой чтения диффа — отказ подготовки гейта, как в G3б-2), профиль каждого — `component_profiles`; компоненты — в порядке записи; каждый компонент в границе `in_outcome_bounds` — свой прогон ядра `_gate` и своя запись пройденного гейта; первый отказ останавливает гейт, деталь отказа — «компонент <имя>: …»; компонент вне границы — строка записи «компонент <имя>: вне границы гейта исходов», не молчание; гейт без прогона — только когда вне границы все компоненты. `review_lines` выдаёт строки записи гейта каждого компонента для головы. У записи из одного компонента — прежний профиль (`_bounds`), ключ записи гейта не меняется.
4. **Планка чужого компонента.** На выходе из `tests_writing` у записи из нескольких компонентов файл планки, который правило планки относит к компоненту, отличному от компонента задачи, — отказ `FAIL_TO_PASS_REFUSAL_ACTION` «файл планки <имя> — компонента <X>, задача — компонента <Y>»; молчаливого пропуска в `criterion_files` нет.
5. **Бриф и роли по компоненту задачи.** Документы `knowledge`, задание test_author по правилу планки, сводки прогонов Vitest и итоговая строка `plank-run` у задачи на записи из нескольких компонентов идут по компоненту задачи — те же тексты, что у записи из одного такого компонента; отказ `for_task` — прежний вывод без `knowledge` и прежнее задание.
6. Тесты детерминированы, без сети и без Node: учебный проект из двух компонентов (`backend` — `junit-xml` с pytest, `frontend` — `pult-vitest` с подменённым раннером, `depends_on` вида `files` на `backend/seed/`): задача на `frontend` — профиль `frontend` на каждом месте требования 2 (перечень мест — тестом по каждому рубежу: выход из `tests_writing`, выход из `in_dev` — гейт текста, заявка мутации, гейт исходов; гейт мержа — гейт текста, гейт исходов, полный набор, перечень долгоживущих; автогейт; пакет ревьювера; бриф пяти ролей; `plank-run`; `amend-tests`; предпроверка; чекпоинт); задача на `backend` с правкой `backend/seed/` — гейт исходов гоняет оба компонента, профиль задачи — `backend`; зоны в обоих компонентах, вне компонентов, без зон — отказ своим текстом на каждом рубеже, ни одного пропуска; файл планки чужого компонента — отказ; `decide(target)` записи из нескольких компонентов — прежний отказ. У артели, `test_profile` и записи из одного компонента — эталон, снятый с кода пина, побайтно. Существующие тесты без правок и зелёные, в том числе `tests/test_01m5hj3yfbvk8tsr7vq7jpyj7c_amend_plank_only.py::Ac5MultiComponentDecisionTest::test_ac5_multi_component_decision_refusal_on_approve` и `tests/test_01m5cjvb5b5v55pqqvr2qrhwzn_outcome_gate.py::Ac1OutOfBoundsTest::test_ac1_decide_skip_refusal_and_canary_no_gate`; мандат «Ослабление тестов разрешено:» на находку «сломан правкой» в `frontend` у задачи на `backend` снимает находку, текста «компонента нет в записи» нет; тесты, закрепляющие отказы «до G3б» (прежний вывод записи из нескольких компонентов у задачи с зонами одного компонента, `ComponentsPending` у мест прогона), меняются только по мандату: аналитик выносит перечень таких тестов с матрицей неослабления до SPEC (эскалация за мандатом); под вопросом — `tests/test_01m5ddtvzea40zb9bheh4ydee7_merge_outcome_gate.py::Ac14OutOfBoundsTest::test_ac14_test_profile_and_multi_component_keep_prior_results` (случай «г»), решение о нём — в описи аналитика.
