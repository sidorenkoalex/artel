## ТЗ и SPEC

Требования 1–6 ТЗ и оба решения Оператора 22.10 (1-А, 2-Б) в SPEC перенесены: требования 1–5 SPEC почти дословно повторяют ТЗ, решение 2-Б — AC-3 («каждый из трёх текстов содержит причину `decide(target)` дословно»), решение 1-А — требование 2 и AC-11. Граница задачи, «Не входит», модули «только чтение» и ограничение зон по смыслу перенесены полностью. Требований сверх ТЗ в SPEC нет. Расхождения:

1. **Матрица неослабления не вынесена.** ТЗ, требование 6, говорит: «аналитик выносит перечень таких тестов с матрицей неослабления до SPEC». В SPEC есть только опись («Материалы»), а матрицы нет совсем — ни раздела, ни таблицы. Вывод описи «ни одного теста менять не нужно» снимает вопрос о мандате на правку тестов. Строк матрицы на свойства, которые задача меняет, он не заменяет (см. раздел «Матрица неослабления» ниже).
2. **`_profile_refusal_exit` не назван.** ТЗ («Факты») прямо говорит, что гейт текста на мерже «держится отказом `orchestrator/fsm_merge_gate.py:1413` (`_profile_refusal_exit`, вызов — `:1491`)». В SPEC этой функции нет ни в «Контексте», ни в требованиях, ни в AC. При этом именно она сейчас первой отказывает записи из нескольких компонентов на `approve` гейта мержа: `decide(target)` стоит в `fsm_merge_gate.py:1418`. Пока она остаётся на `decide`, мерж любой задачи на такой записи отказывает. SPEC покрывает её только общей фразой «каждое место» (см. «Проверяемость», п. 1).
3. Прочее совпадает: AC-17 переносит перечень рубежей ТЗ (требование 6) без потерь, AC-21 — эталон пина, AC-20 — планка чужого компонента и прежний отказ `decide`.

## Пути обхода гейтов

1. **Пропуск через неназванные места.** Буквальное прохождение AC-17 оставляет на `decide`/`profile_of` места из «Проверяемости», п. 1. Сейчас они отказывают, а не пропускают, так что прямого пропуска проверки нет, но есть одно исключение. `acceptance_suite` (`orchestrator/acceptance.py:3490-3495`) ловит `ComponentsPending` и молча идёт без `checks_local`. Если `_task_profile` будет поднимать `ComponentsPending` при отказе `for_task`, на `approve` и в автогейте `checks_local` компонента у записи из нескольких компонентов будут пропущены без записи. Требование 2 («ни одно место не превращает отказ `for_task` в пропуск проверки») этот перехват не называет, AC-8 его не проверяет.
2. **Видимость гейта в пакете ревьювера.** У задачи, чей компонент без `report`, а потребитель с `report`, гейт исходов прогонит потребителя (AC-13). Но `orchestrator/review.py:691` по профилю задачи не покажет ревьюверу его строки, а «логика не меняется» вне `outcome_integrity` это узаконивает.
3. **Автогейт при компоненте задачи вне границы.** Граница AC-9 — только компонент задачи. Потребитель в границе гейтом исходов прогнан, но автогейт по правилу планки откажет «до G3б». Это fail-closed, не обход. Отмечено для полноты.
4. **Долгоживущий файл чужого компонента** (`orchestrator/advance_gates/acceptance.py:288-289`) по-прежнему молча выпадает из FAIL_TO_PASS: требование 4 называет только файлы планки. Практически это держит гейт зон: такой файл лежит в зоне чужого компонента, `task_components` даёт два компонента, `for_task` отказывает. Но только пока под зоной нет маски `test_support` другого компонента, совпадающей с путём долгоживущего файла.
5. Иных обходов не найдено. Выбор компонента задачи по зонам закрыт гейтом зон: правка вне зон отказывает, расширение зоны другим компонентом даёт отказ «несколько компонентов». Дифф с путями вне компонентов `select_components` расширяет до всех компонентов (`orchestrator/project_profile.py:453-454`).

## Вердикт

**concerns.** SPEC верно отражает ТЗ и решения 22.10, факты о коде в основном подтвердились, опись существующих тестов точна. Отклонения ниже — неполнота перечня и проверяемости, а не неверное направление; решить их может Оператор на гейте (вернув аналитику либо уточнив решением):

1. Перечень мест «в контексте задачи» не закрыт, AC-17 не ловит пропущенные: `orchestrator/suite_run.py:334`, `:634`; `orchestrator/pull.py:665`; `orchestrator/acceptance.py:3491`; `orchestrator/runner.py:1325`; `orchestrator/fsm_merge_gate.py:1418` (`_profile_refusal_exit`, названный в ТЗ и пропущенный в SPEC). Отсюда AC-10 для `suite-run` и перехват `ComponentsPending` в `acceptance_suite` (`acceptance.py:3492-3495`) как возможный молчаливый пропуск `checks_local`.
2. AC-19 («отказ своим текстом AC-3 на каждом рубеже AC-17») противоречит AC-16 (бриф при отказе — прежний вывод) и AC-8 («отказ или эскалация»): нет таблицы «рубеж → исход» (SPEC.md, AC-16, AC-19; `orchestrator/review.py:639-641`, `:752-758`; `orchestrator/checkpoint.py:455`).
3. Маркеры мандата смешаны: `_test_id_refusal` обслуживает «Ослабление теста по идентификатору разрешено:» (`orchestrator/advance_gates/mandate.py:51`, `:365`), не «Ослабление тестов разрешено:» (`:38`, `:253`). AC-11 правку `_test_id_refusal` не ловит, и не решено, распространяется ли решение 22.10 (1-А) на мандат по идентификатору (подсказка `outcome_integrity.py:1111-1114` предлагает оба).
4. Матрицы неослабления нет (требование 6 ТЗ). Расширение годности мандата (`mandate.py:301-303`) — ослабление проверки, оно должно стоять строкой матрицы со ссылкой на решение 22.10.
5. AC-13 не задаёт исход и носитель строки «вне границы гейта исходов», в том числе когда вне границы все компоненты. А `orchestrator/review.py:691` по профилю задачи скрывает строки компонента-потребителя, и при ограничении «вне `outcome_integrity` — только источник» AC-14 для такого пакета не выполнить.
6. Неточность «Контекста»: «на `approve` гейта SPEC зоны строки задачи ещё не записаны» — верно только для фикстуры. В штатной задаче действуют зоны ТЗ с `new`. На выводы SPEC не влияет.
