# SPEC: G3б-3: компонент задачи по зонам, компоненты гейтов по диффу и снятие отказа записи из нескольких компонентов

## Контекст
Третья и последняя часть G3б волны G по ADR-0026 («Решение», п. 2 и п. 13). Сейчас запись `components:` из двух и более компонентов отказывает везде: `orchestrator/repo_context.py:142` (`profile_of`, признак `multi`) → `orchestrator/project_profile.py:190` (`decide`) → `targets.MULTI_COMPONENT_PENDING` («исполняется после G1б»), а места прогона поднимают `targets.ComponentsPending` (`orchestrator/acceptance.py:3578`, `:3563`, `:3476`, `:2166`). `for_task` (`orchestrator/project_profile.py:228`) зон задачи не читает. Гейт исходов гоняет единственный компонент профиля решения (`_bounds`), поэтому у записи из нескольких компонентов ни один его рубеж не создаётся. Мандат ослабления проверяется по единственному профилю (`orchestrator/advance_gates/mandate.py:194`, `:281`, текст `:302`). Файл планки без компонента гейт FAIL_TO_PASS молча пропускает (`orchestrator/advance_gates/acceptance.py:258`). G3б-2 (01M5J0JYW3) смержена, гейты неослабления полные, так что отказ можно снимать.

**Граница задачи:** новое поведение появляется только у задачи на записи `components:` из двух и более компонентов. У артели, записи `test_profile` и записи из одного компонента решение по профилю, гейты, бриф и вывод команд остаются прежними побайтно. `decide(target)` без задачи у записи из нескольких компонентов по-прежнему отказывает.

## Требования

1. **Компонент задачи.**
   - `project_profile.task_components(target, zones) -> tuple[str, ...]` возвращает компоненты, чьи `paths` или маски `test_support` задевают путь зон. Потребители по `depends_on` не добавляются. Порядок — порядок записи. Пути вне всех компонентов выбор не расширяют.
   - `project_profile.decide_task(target, zones) -> Decision` сначала зовёт `decide(target)`. Компонент по зонам выбирается, только если результат — отказ записи из нескольких компонентов (`profile_of(target).multi`). Во всех остальных случаях возвращается результат `decide` как есть, побайтно: артель, `test_profile`, запись из одного компонента, неразрешённый контекст, `TargetsError`, подмены `decide` в тестах.
   - У записи из нескольких компонентов:
     - зоны не заданы — отказ «зоны задачи не заданы — компонент задачи на записи из нескольких компонентов не выбран»;
     - ни одного компонента — отказ «зоны задачи не задевают ни одного компонента записи»;
     - два и более — отказ «задача затрагивает несколько компонентов (<имена>) — дели задачу по компонентам (решение Оператора 20.10)»;
     - ровно один — профиль этого компонента с теми же полями, что у `with_tools` единственного компонента. Обязательные подполя профиля проверяются той же проверкой, что у `profile_of`, отказ называет компонент.
   - Каждый текст отказа `decide_task` включает причину `decide` дословно (решение Оператора 22.10, вопрос 2-Б).
   - `for_task(conn, task_id)` = `decide_task(<проект задачи>, task_zone_paths(<строка задачи>))`. Зоны строки задачи читаются только у записи из нескольких компонентов.
   - `decide(target)` и `profile_of` у записи из нескольких компонентов дают прежний отказ. Текст `MULTI_COMPONENT_PENDING` меняется на «запись проекта с несколькими компонентами: профиль выбирается по зонам задачи».
2. **Места задачи — через `for_task`.**
   - Каждое место, которое берёт профиль в контексте задачи, зовёт `for_task` вместо `decide(target)`.
   - `acceptance._task_profile` и `_task_own_profile` возвращают профиль компонента задачи вместо `ComponentsPending`. `ComponentsPending` поднимается только при отказе `for_task` у записи из нескольких компонентов. У прочих отказ остаётся прежним `None`, а `conn=None` идёт прежним путём. Уборка выкладки (`orchestrator/acceptance.py:2166`) у задачи с компонентом убирает выкладку этого компонента.
   - У записи из нескольких компонентов ни одно место не превращает отказ `for_task` в пропуск проверки. `_bounds`, `_test_integrity_diff_gate`, автогейт и пакет ревьювера дают отказ или эскалацию с причиной. У прочих записей поведение прежнее.
   - Автогейт: у записи из нескольких компонентов граница — компонент задачи в `in_outcome_bounds` и задача не канарейка. У прочих — `_plank_rule_refusal(rule, t)` со строкой без зон и id, как прежде.
   - Предел полного набора в контексте задачи — `component_limit` компонента задачи. Сам полный набор на мерже берёт `_selected_components` по диффу, без сужения до компонента задачи.
   - Мандат ослабления (решение Оператора 22.10, вопрос 1-А): элемент «Ослабление тестов разрешено:» годен для находки любого компонента записи в границе гейта исходов. `_weakening_scope_refusal` и `_test_id_refusal` (`orchestrator/advance_gates/mandate.py`) меняются только в этой части.
3. **Компоненты гейта по диффу.**
   - Гейт исходов на обоих рубежах (выход из `in_dev`, мерж) берёт компоненты `select_components(<проект>, <пути диффа>)` с потребителями. Сбой чтения диффа — отказ подготовки гейта, как в G3б-2. Профиль каждого компонента — `component_profiles`, порядок — порядок записи.
   - Каждый компонент в границе `in_outcome_bounds` получает свой прогон ядра `_gate` и свою запись пройденного гейта. Первый отказ останавливает гейт, деталь отказа — «компонент <имя>: …».
   - Компонент вне границы даёт строку записи «компонент <имя>: вне границы гейта исходов», а не молчание. Гейт без прогона допустим, только когда вне границы все компоненты.
   - `review_lines` выдаёт строки записи гейта каждого компонента для головы.
   - У записи из одного компонента профиль прежний (`_bounds`), ключ записи гейта не меняется.
4. **Планка чужого компонента.** У записи из нескольких компонентов на выходе из `tests_writing` проверяется каждый файл планки. Если правило планки относит файл к компоненту, отличному от компонента задачи, — отказ `FAIL_TO_PASS_REFUSAL_ACTION` «файл планки <имя> — компонента <X>, задача — компонента <Y>». Молчаливого пропуска в `criterion_files` нет.
5. **Бриф и роли по компоненту задачи.** У задачи на записи из нескольких компонентов документы `knowledge`, задание test_author по правилу планки, сводки прогонов Vitest и итоговая строка `plank-run` идут по компоненту задачи. Тексты те же, что у записи из одного такого компонента. При отказе `for_task` вывод прежний: без `knowledge` и с прежним заданием.
6. **Тесты.**
   - Тесты детерминированы, без сети и без Node.
   - Учебный проект из двух компонентов: `backend` — `junit-xml` с pytest; `frontend` — `pult-vitest` с подменённым раннером, `depends_on` вида `files` на `backend/seed/`.
   - Сценарии и эталоны — в AC-17 – AC-21.

## Критерии приёмки

AC-1. `project_profile.task_components(target, zones)` возвращает кортеж имён компонентов, чьи `paths` или маски `test_support` задевают хотя бы один путь зон, в порядке записи `components:`. Потребители по `depends_on` в кортеж не входят. Путь зон вне всех компонентов выбор не расширяет.

AC-2. У артели, записи `test_profile`, записи из одного компонента, при неразрешённом контексте, `TargetsError` и подменённом в тесте `decide` результат `project_profile.decide_task(target, zones)` побайтно совпадает с `decide(target)` при любых зонах.

AC-3. У записи из нескольких компонентов `decide_task` отказывает своими текстами:
- зоны не заданы — «зоны задачи не заданы — компонент задачи на записи из нескольких компонентов не выбран»;
- зоны не задевают ни одного компонента — «зоны задачи не задевают ни одного компонента записи»;
- задеты два и более — «задача затрагивает несколько компонентов (<имена>) — дели задачу по компонентам (решение Оператора 20.10)» с именами задетых компонентов.

Каждый из трёх текстов содержит причину `decide(target)` дословно.

AC-4. У записи из нескольких компонентов, когда зоны задевают ровно один компонент, `decide_task` возвращает профиль этого компонента с полями, как у `with_tools` записи из одного этого компонента. Если у компонента нет обязательного подполя профиля — отказ, называющий компонент. Проверка та же, что у `profile_of`.

AC-5. `for_task(conn, task_id)` возвращает `decide_task(<проект задачи>, task_zone_paths(<строка задачи>))`. Колонки зон строки задачи читаются только у записи из нескольких компонентов: у прочих записей `for_task` работает и с таблицей задач без колонок `zones`/`zones_extension`.

AC-6. `decide(target)` и `profile_of(target)` у записи из нескольких компонентов без задачи — прежний отказ. Текст `targets.MULTI_COMPONENT_PENDING` — «запись проекта с несколькими компонентами: профиль выбирается по зонам задачи».

AC-7. У задачи с одним компонентом на записи из нескольких компонентов `acceptance._task_profile` и `_task_own_profile` возвращают профиль компонента задачи.
- `ComponentsPending` поднимается только при отказе `for_task` у записи из нескольких компонентов. У прочих записей при отказе возвращается `None`, при `conn=None` — прежний путь.
- Уборка выкладки (`orchestrator/acceptance.py:2166`) у задачи с компонентом убирает выкладку этого компонента.

AC-8. У записи из нескольких компонентов при отказе `for_task` граница гейта исходов (`_bounds`), гейт текста на мерже (`_test_integrity_diff_gate`), автогейт и пакет ревьювера дают отказ или эскалацию с причиной. Пропуска проверки нет. У прочих записей поведение прежнее: тест `tests/test_01m5cjvb5b5v55pqqvr2qrhwzn_outcome_gate.py::Ac1OutOfBoundsTest::test_ac1_decide_skip_refusal_and_canary_no_gate` зелёный без правок.

AC-9. Автогейт у записи из нескольких компонентов считает задачу в границе, только когда компонент задачи в `in_outcome_bounds` и задача не канарейка. У прочих записей — `_plank_rule_refusal(rule, t)` со строкой задачи без зон и id, исход прежний.

AC-10. Предел полного набора в контексте задачи на записи из нескольких компонентов — `component_limit` компонента задачи. Полный набор на мерже — `_selected_components` по диффу ветки, без сужения до компонента задачи.

AC-11. У задачи на `backend` с находкой «сломан правкой» в компоненте `frontend`:
- элемент мандата «Ослабление тестов разрешено:», выданный командой `answer`, снимает находку;
- текста «компонента … нет в записи components: проекта» для компонента, который в записи есть, нет ни на `answer`, ни на рубеже.

`_weakening_scope_refusal` и `_test_id_refusal` у записи из одного компонента и у артели отказывают так же, как прежде.

AC-12. Гейт исходов на выходе из `in_dev` и на мерже берёт компоненты `select_components(<проект>, <пути диффа>)` вместе с потребителями по `depends_on`, а профиль каждого — `component_profiles`. Сбой чтения диффа — отказ подготовки гейта, как в G3б-2.

AC-13. Каждый выбранный компонент в границе `in_outcome_bounds` получает свой прогон ядра `_gate` и свою запись пройденного гейта, в порядке записи `components:`.
- Первый отказ останавливает гейт, деталь отказа начинается с «компонент <имя>: ».
- Компонент вне границы даёт строку записи «компонент <имя>: вне границы гейта исходов».
- Гейт не прогоняется, только когда вне границы все выбранные компоненты.

AC-14. `review_lines` для головы выдаёт строки записи гейта каждого компонента. У записи из одного компонента профиль гейта берётся прежним путём (`_bounds`), ключ записи гейта и строки побайтно прежние.

AC-15. У записи из нескольких компонентов на выходе из `tests_writing`, если правило планки относит файл планки к компоненту, отличному от компонента задачи, — отказ `FAIL_TO_PASS_REFUSAL_ACTION` с текстом «файл планки <имя> — компонента <X>, задача — компонента <Y>». Молчаливого пропуска такого файла в `criterion_files` нет.

AC-16. У задачи на записи из нескольких компонентов с одним компонентом задачи документы `knowledge` в брифе, задание test_author по правилу планки, сводки прогонов Vitest и итоговая строка `plank-run` побайтно совпадают с выводом для записи из одного этого компонента. При отказе `for_task` — прежний вывод без `knowledge` и прежнее задание.

AC-17. Тесты этой задачи используют учебный проект из двух компонентов: `backend` (`junit-xml`, pytest) и `frontend` (`pult-vitest` с подменённым раннером, `depends_on` вида `files` на `backend/seed/`). Сети и Node нет, исход детерминирован. У задачи на `frontend` профиль `frontend` берётся на каждом месте требования 2 — по отдельному тесту на каждый рубеж:
- выход из `tests_writing`;
- выход из `in_dev`: гейт текста, заявка мутации, гейт исходов;
- гейт мержа: гейт текста, гейт исходов, полный набор, перечень долгоживущих;
- автогейт;
- пакет ревьювера;
- бриф пяти ролей;
- `plank-run`;
- `amend-tests`;
- предпроверка;
- чекпоинт.

AC-18. У задачи на `backend` с правкой под `backend/seed/` гейт исходов гоняет оба компонента, `backend` и `frontend`, а профиль задачи — `backend`.

AC-19. Каждый из трёх вариантов зон даёт на каждом рубеже AC-17 отказ своим текстом AC-3, пропуска проверки нет:
- зоны в обоих компонентах;
- зоны вне компонентов;
- зоны не заданы.

AC-20. На учебном проекте AC-17 файл планки компонента `backend` у задачи на `frontend` получает отказ AC-15. `decide(target)` записи без задачи — прежний отказ AC-6.

AC-21. У артели, записи `test_profile` и записи из одного компонента вывод мест требования 2 побайтно совпадает с эталоном, снятым с кода пина.

## Оценка объёма и деление
Сработавшие сигналы:
- в зоне 23 файла и каталог `tests/`;
- 21 критерий приёмки;
- `budget_usd` 85 ≥ $30.

**Обоснование монолита.** Задача — уже третья часть деления G3б по решению Оператора 21.10. Нельзя резать вот что:
- снятие отказа записи из нескольких компонентов (требование 1);
- перевод мест задачи на `for_task` без пропусков (требование 2);
- гейт исходов по компонентам диффа (требование 3);
- отказ планки чужого компонента (требование 4).

Если снять отказ (1) без (2) или (4), то у записи из нескольких компонентов места, которые сейчас пропускают проверку при отказе `decide` (`_bounds`, `_test_integrity_diff_gate`, автогейт, `criterion_files`), пропустят задачу без проверки. Если сделать (1)+(2) без (3), то гейт исходов задачи прогонит только её компонент и не заметит поломку компонента-потребителя по `depends_on`. Оба промежуточных состояния — ослабление гейтов неослабления, запрещённое без ADR (ADR-0002). А пока отказ стоит, части (2)–(4) без (1) не наблюдаемы: у записи из нескольких компонентов в них не попадает ни одна задача. Требование 5 (бриф и роли) отделить можно, но оно опирается на `for_task` части 1 и занимает малую долю объёма. Если Оператор предпочтёт деление, разумная граница — «1–4» и «5».

## Не входит
- Задача сразу на несколько компонентов (одна задача на `backend` и `frontend`). В этой задаче она получает отказ требования 1 с причиной; поддержка — отдельной задачей позже (решение Оператора 21.10).
- Строка `doctor` о пределе полного прогона записи из нескольких компонентов: остаётся прежний `skip`.
- Раздел «Заменяемые тесты» и его сверки (G3б-1, G3б-2).
- Строгий режим, исключения в коде, прежние версии тестов (G3б-2).
- Многорепозиторный случай и `depends_on` вида `contract` (отдельный ADR).
- Запись sled в `targets.yaml` и проба (этап 2 плана).
- Предупреждение `doctor` о файлах поддержки (бэклог 21.10).
- Ключ компонента записи гейта исходов и замены (уже в G3б-2).
- Смена логики гейтов. Вне `orchestrator/project_profile.py` и `orchestrator/advance_gates/outcome_integrity.py` меняются только источник профиля задачи (`decide(target)` → `for_task`), предел набора по компоненту и отказ требования 4. В `orchestrator/advance_gates/mandate.py` меняются только `_weakening_scope_refusal` и `_test_id_refusal` в части компонента записи.
