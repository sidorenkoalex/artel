# SPEC: G3б-3: компонент задачи по зонам, компоненты гейтов по диффу и снятие отказа записи из нескольких компонентов

## Контекст
Третья и последняя часть G3б волны G по ADR-0026 («Решение», п. 2 и п. 13). Сейчас запись `components:` из двух и более компонентов отказывает везде: `orchestrator/repo_context.py:142` (`profile_of`, признак `multi`) → `orchestrator/project_profile.py:190` (`decide`) → `targets.MULTI_COMPONENT_PENDING` («исполняется после G1б»), а места прогона поднимают `targets.ComponentsPending` (`orchestrator/acceptance.py:3578`, `:3563`, `:3476`, `:2166`). `for_task` (`orchestrator/project_profile.py:228`) зон задачи не читает. Гейт исходов гоняет единственный компонент профиля решения (`_bounds`), поэтому у записи из нескольких компонентов ни один его рубеж не создаётся. Мандаты ослабления проверяются по единственному профилю: «Ослабление тестов разрешено:» (`orchestrator/advance_gates/mandate.py:38`) — в `_weakening_scope_refusal` (`:194`), «Ослабление теста по идентификатору разрешено:» (`:51`) — в `_test_id_refusal` (`:281`, текст «компонента … нет в записи» — `:302`). Файл планки без компонента гейт FAIL_TO_PASS молча пропускает (`orchestrator/advance_gates/acceptance.py:258`). Явное `layers: []` у компонента с командой pytest сейчас неотличимо от отсутствия поля (`orchestrator/project_profile.py:300`, `:309`): оба дают `python-ast`. G3б-2 (01M5J0JYW3) смержена, гейты неослабления полные, так что отказ можно снимать.

**Граница задачи:** новое поведение появляется только у задачи на записи `components:` из двух и более компонентов (и у компонента с явным `layers: []`, требование 7). У артели, записи `test_profile` и записи из одного компонента решение по профилю, гейты, бриф и вывод команд остаются прежними побайтно. `decide(target)` без задачи у записи из нескольких компонентов по-прежнему отказывает.

## Требования

1. **Компонент задачи.**
   - `project_profile.task_components(target, zones) -> tuple[str, ...]` возвращает компоненты, чьи `paths` или маски `test_support` задевают путь зон. Потребители по `depends_on` не добавляются. Порядок — порядок записи. Пути вне всех компонентов выбор не расширяют.
   - «Путь зон задевает компонент» (решение на гейте SPEC 22.10, круг 3, п. 7): зона-файл задевает компонент, если путь сопоставляется с регулярным выражением `paths` компонента или с его маской `test_support`. Зона-каталог (префикс, оканчивается на «/», конвенция `orchestrator/zone_lock.py:243`) задевает компонент, если хоть один файл репозитория на базе (`git ls-files`) под этим префиксом так сопоставляется. Сбой получения перечня файлов — отказ `decide_task` (fail-closed), не пустой выбор.
   - `project_profile.decide_task(target, zones) -> Decision` сначала зовёт `decide(target)`. Компонент по зонам выбирается, только если результат — отказ записи из нескольких компонентов (`profile_of(target).multi`). Во всех остальных случаях возвращается результат `decide` как есть, побайтно: артель, `test_profile`, запись из одного компонента, неразрешённый контекст, `TargetsError`, подмены `decide` в тестах.
   - У записи из нескольких компонентов:
     - зоны не заданы — отказ «зоны задачи не заданы — компонент задачи на записи из нескольких компонентов не выбран»;
     - ни одного компонента — отказ «зоны задачи не задевают ни одного компонента записи»;
     - два и более — отказ «задача затрагивает несколько компонентов (<имена>) — дели задачу по компонентам (решение Оператора 20.10)»;
     - ровно один — профиль этого компонента с теми же полями, что у `with_tools` единственного компонента. Обязательные подполя профиля проверяются той же проверкой, что у `profile_of`, отказ называет компонент.
   - Каждый текст отказа `decide_task` включает причину `decide` дословно (решение Оператора 22.10, вопрос 2-Б).
   - `for_task(conn, task_id)` = `decide_task(<проект задачи>, task_zone_paths(<строка задачи>))`. Зоны строки задачи читаются только у записи из нескольких компонентов.
   - `decide(target)` и `profile_of` у записи из нескольких компонентов дают прежний отказ. Текст `MULTI_COMPONENT_PENDING` меняется на «запись проекта с несколькими компонентами: профиль выбирается по зонам задачи».
2. **Места задачи — через `for_task`.**
   - Каждое место, которое берёт профиль в контексте задачи, зовёт `for_task` вместо `decide(target)`/`profile_of(target)`. Перечень мест закрыт — таблица «Места задачи и исход при отказе `for_task`» ниже.
   - `acceptance._task_profile` и `_task_own_profile` возвращают профиль компонента задачи вместо `ComponentsPending`. `ComponentsPending` поднимается только при отказе `for_task` у записи из нескольких компонентов. У прочих отказ остаётся прежним `None`, а `conn=None` идёт прежним путём. Уборка выкладки (`orchestrator/acceptance.py:2166`) у задачи с компонентом убирает выкладку этого компонента.
   - Перехват `ComponentsPending` в `acceptance_suite` (`orchestrator/acceptance.py:3492–3495`) не превращает отказ `for_task` в молчаливый пропуск `checks_local`: у записи из нескольких компонентов при отказе `for_task` итог — отказ с причиной.
   - У записи из нескольких компонентов ни одно место перечня не превращает отказ `for_task` в пропуск проверки: исход каждого места — по таблице. У прочих записей поведение прежнее.
   - Автогейт: у записи из нескольких компонентов граница — компонент задачи в `in_outcome_bounds` и задача не канарейка. У прочих — `_plank_rule_refusal(rule, t)` со строкой без зон и id, как прежде.
   - Предел полного набора в контексте задачи (в том числе `suite-run <id>`, `orchestrator/suite_run.py:634`, и `acceptance.full_suite`, `orchestrator/acceptance.py:3360`) — `component_limit` компонента задачи. Сам полный набор на мерже берёт `_selected_components` по диффу, без сужения до компонента задачи.
   - Область помощников гейта текста (`_external_helpers`, `orchestrator/advance_gates/test_integrity.py:1299`) — `workdir`/`in_weakening_scope` компонента задачи. У записи из нескольких компонентов при отказе `for_task` молчаливого отката на область по умолчанию (`:1300–1301`) нет: исход — отказ гейта текста.
   - Мандаты ослабления (решение Оператора 22.10, вопрос 1-А; решения на гейте SPEC 22.10, круг 1, п. 3, круг 2, п. 4, круг 3, пп. 3–4): элементы «Ослабление тестов разрешено:» и «Ослабление теста по идентификатору разрешено:» годны для находки любого компонента записи в границе гейта исходов. Условие границы — `in_outcome_bounds` профиля компонента находки; признак канарейки в условии мандата не проверяется (у канарейки гейт исходов не исполняется, находок нет). Для компонента записи вне границы элемент не годен — отказ тем же текстом, что сейчас даёт профиль задачи вне границы (`orchestrator/advance_gates/mandate.py:270–278`, `:296–300`). Ложного текста «компонента … нет в записи components: проекта» для компонента, который в записи есть, нет.
   - Матрица неослабления мандата (`matrix_refusals`, `orchestrator/advance_gates/mandate.py:584`; `_covered` `:538–554`, `_component_covered` `:513–531`; решение 22.10, 1-А, и на гейте SPEC 22.10, круг 3, п. 4): ссылка в ячейке «Чем покрыто после» засчитывается покрытием, если её покрывает элемент любого компонента записи в границе гейта исходов — идентификатор `<компонент>:…` с путём в области этого компонента либо путь файла его области. В `orchestrator/advance_gates/mandate.py` меняются три места: `_weakening_scope_refusal`, `_test_id_refusal` и покрытие в `matrix_refusals`. У записи из одного компонента и у артели все три дают прежний результат.
3. **Компоненты гейта по диффу.**
   - Гейт исходов на обоих рубежах (выход из `in_dev`, мерж) берёт компоненты `select_components(<проект>, <пути диффа>)` с потребителями. Сбой чтения диффа — отказ подготовки гейта, как в G3б-2. Профиль каждого компонента — `component_profiles`, порядок — порядок записи.
   - Каждый компонент в границе `in_outcome_bounds` получает свой прогон ядра `_gate` и свою запись пройденного гейта. Первый отказ останавливает гейт, деталь отказа — «компонент <имя>: …».
   - По каждому компоненту вне границы в запись гейта пишется строка «компонент <имя>: вне границы гейта исходов».
   - Если вне границы все выбранные компоненты, исход перехода прежний (гейт без прогона), и пишется запись пропуска тем же действием, что у пропуска проверки сейчас (`project_profile.SKIP_ACTION`, форма `journal_skip`): «проверка тестов не выполняется: гейт неослабления по исходам». Деталь — строка «голова <sha>» и строки «компонент <имя>: вне границы гейта исходов» по каждому компоненту (решение на гейте SPEC 22.10, круг 2, п. 5).
   - `review_lines` выдаёт строки записей гейта всех компонентов для головы. Если для головы есть только запись пропуска — прежняя строка «гейт исходов для головы <h> не исполнялся» (`NOT_RUN_LINE`) и за ней строки «гейт исходов: компонент <имя>: вне границы гейта исходов» из записи пропуска (`orchestrator/advance_gates/outcome_integrity.py:1123`). Пакет ревьювера показывает эти строки: в `_outcome_gate_lines` (`orchestrator/review.py:691`) фильтр по границе профиля задачи заменяется только сменой источника — строки берутся из `review_lines`; прочая логика `orchestrator/review.py` не меняется. У задачи, чей компонент вне границы, а компонент-потребитель в границе прогнан гейтом, пакет ревьювера показывает строки записей гейта компонентов в границе (решение на гейте SPEC 22.10, круг 3, п. 6).
   - У записи из одного компонента профиль прежний (`_bounds`), ключ записи гейта не меняется.
4. **Планка чужого компонента.** У записи из нескольких компонентов на выходе из `tests_writing` правило планки относит каждый файл планки к компоненту-владельцу. Файл компонента X, отличного от компонента задачи Y (решения на гейте SPEC 22.10, круг 2, п. 6, круг 3, п. 2):
   - X в границе гейта FAIL_TO_PASS (`in_outcome_bounds` профиля X) — файл проверяется гейтом FAIL_TO_PASS компонента-владельца X, граница берётся по X: отказ `FAIL_TO_PASS_REFUSAL_ACTION` «файл планки <имя> — компонента <X>, задача — компонента <Y>». Молчаливого пропуска такого файла в `criterion_files` нет. Это действует и у задачи, чей компонент Y вне границы: условие добавления гейта по профилю задачи (`orchestrator/fsm_advance.py:609–613`) файл X в границе не пропускает.
   - X вне границы — прежнее поведение: файл не проверяется, отказа нет.
5. **Бриф и роли по компоненту задачи.** У задачи на записи из нескольких компонентов документы `knowledge`, задание test_author по правилу планки, сводки прогонов Vitest и итоговая строка `plank-run` идут по компоненту задачи. Тексты те же, что у записи из одного такого компонента. При отказе `for_task` вывод прежний: без `knowledge` и с прежним заданием.
6. **Тесты.**
   - Тесты детерминированы, без сети и без Node.
   - Учебный проект из двух компонентов: `backend` — `junit-xml` с pytest; `frontend` — `pult-vitest` с подменённым раннером, `depends_on` вида `files` на `backend/seed/`.
   - Сценарии и эталоны — в AC-22 – AC-28.
7. **Явное `layers: []` (решение Оператора на гейте SPEC 22.10, п. 7 — перенос независимой проверки G3б-2).** У компонента с командой pytest явное пустое поле `layers: []` включает строгий режим гейта исходов. `_with_component_fields`/`layers_of` (`orchestrator/project_profile.py:287`, `:304`) различают «поля нет» (у pytest — `python-ast` по умолчанию, как сейчас) и «поле пусто» (строгий режим).

## Критерии приёмки

AC-1. `project_profile.task_components(target, zones)` возвращает кортеж имён компонентов, чьи `paths` или маски `test_support` задевают хотя бы один путь зон, в порядке записи `components:`. Потребители по `depends_on` в кортеж не входят. Путь зон вне всех компонентов выбор не расширяет.

AC-2. У артели, записи `test_profile`, записи из одного компонента, при неразрешённом контексте, `TargetsError` и подменённом в тесте `decide` результат `project_profile.decide_task(target, zones)` побайтно совпадает с `decide(target)` при любых зонах.

AC-3. У записи из нескольких компонентов `decide_task` отказывает своими текстами:
- зоны не заданы — «зоны задачи не заданы — компонент задачи на записи из нескольких компонентов не выбран»;
- зоны не задевают ни одного компонента — «зоны задачи не задевают ни одного компонента записи»;
- задеты два и более — «задача затрагивает несколько компонентов (<имена>) — дели задачу по компонентам (решение Оператора 20.10)» с именами задетых компонентов.

Каждый из трёх текстов содержит причину `decide(target)` дословно.

AC-4. У записи из нескольких компонентов, когда зоны задевают ровно один компонент, `decide_task` возвращает профиль этого компонента с полями, как у `with_tools` записи из одного этого компонента. Если у компонента нет обязательного подполя профиля — отказ, называющий компонент. Проверка та же, что у `profile_of`.

AC-5. `for_task(conn, task_id)` возвращает `decide_task(<проект задачи>, task_zone_paths(<строка задачи>))`. Колонки зон строки задачи читаются только у записи из нескольких компонентов: у прочих записей `for_task` работает и с таблицей задач без колонок `zones`/`zones_extension`.

AC-6. `decide(target)` и `profile_of(target)` у записи из нескольких компонентов без задачи — прежний отказ. Текст `targets.MULTI_COMPONENT_PENDING` — «запись проекта с несколькими компонентами: профиль выбирается по зонам задачи».

AC-7. У задачи с одним компонентом на записи из нескольких компонентов `acceptance._task_profile` и `_task_own_profile` возвращают профиль компонента задачи.
- `ComponentsPending` поднимается только при отказе `for_task` у записи из нескольких компонентов. У прочих записей при отказе возвращается `None`, при `conn=None` — прежний путь.
- Уборка выкладки (`orchestrator/acceptance.py:2166`) у задачи с компонентом убирает выкладку этого компонента.

AC-8. `acceptance_suite` (`orchestrator/acceptance.py:3476`) у задачи с одним компонентом на записи из нескольких компонентов исполняет `checks_local` этого компонента. При отказе `for_task` у записи из нескольких компонентов `approve` приёмки и автогейт отказывают с текстом отказа `for_task`; итога без `checks_local` и без записи о причине нет.

AC-9. У задачи на записи из нескольких компонентов с отказом `for_task` каждое место таблицы «Места задачи и исход при отказе `for_task`» даёт исход своей строки таблицы: переходы, гейты и команды — отказ, причина содержит текст AC-3; бриф, `knowledge` и итоговая строка `plank-run` — прежний вывод; чекпоинт и засчитывание test_author — запись журнала с причиной. Ни одно место не пропускает проверку молча. Эскалация — только у мест, эскалирующих сейчас.

AC-10. У прочих записей (артель, `test_profile`, один компонент) исход мест таблицы прежний: тест `tests/test_01m5cjvb5b5v55pqqvr2qrhwzn_outcome_gate.py::Ac1OutOfBoundsTest::test_ac1_decide_skip_refusal_and_canary_no_gate` зелёный без правок.

AC-11. Автогейт у записи из нескольких компонентов считает задачу в границе, только когда компонент задачи в `in_outcome_bounds` и задача не канарейка. У прочих записей — `_plank_rule_refusal(rule, t)` со строкой задачи без зон и id, исход прежний.

AC-12. Предел полного набора в контексте задачи на записи из нескольких компонентов — `component_limit` компонента задачи, в том числе у `suite-run <id>` (`orchestrator/suite_run.py:634`) и у `acceptance.full_suite` (`orchestrator/acceptance.py:3360`). Полный набор на мерже — `_selected_components` по диффу ветки, без сужения до компонента задачи.

AC-13. У задачи на `backend` с находкой «сломан правкой» в компоненте `frontend` элемент «Ослабление тестов разрешено:» (`_weakening_scope_refusal`), выданный командой `answer` с матрицей, где строка свойства — «остаётся» и в ячейке «Чем покрыто после» ссылка `frontend:…` или путь файла области `frontend`, снимает находку; ни на `answer` (в том числе `matrix_refusals` — «свойство остаётся и не покрыто»), ни на рубеже нет отказа «путь вне области» по области компонента задачи. Если компонент находки — компонент записи вне границы гейта исходов (у варианта учебного проекта `frontend` без поля `report`), элемент на путь этого компонента не годен: отказ тем же текстом, что сейчас у профиля вне границы (`orchestrator/advance_gates/mandate.py:270–278`), находку он не снимает.

AC-14. У задачи на `backend` с находкой «сломан правкой» в компоненте `frontend` элемент «Ослабление теста по идентификатору разрешено:» с идентификатором `frontend:…` (`_test_id_refusal`), выданный командой `answer` с матрицей, где строка свойства — «остаётся, покрыто `frontend:…`», снимает находку; ни текста «компонента «frontend» нет в записи components: проекта», ни отказа `matrix_refusals` «свойство остаётся и не покрыто» нет ни на `answer`, ни на рубеже. Идентификатор компонента, которого в записи нет, по-прежнему получает этот отказ. Идентификатор компонента записи вне границы гейта исходов (у варианта учебного проекта `frontend` без поля `report`) не годен: отказ «мандат по идентификатору действует только у компонента записи components: с полем report …» (`orchestrator/advance_gates/mandate.py:296–300`).

AC-15. `_weakening_scope_refusal`, `_test_id_refusal` и покрытие в `matrix_refusals` у записи из одного компонента и у артели дают тот же результат, что прежде, в том числе у задачи-канарейки.

AC-16. Гейт исходов на выходе из `in_dev` и на мерже берёт компоненты `select_components(<проект>, <пути диффа>)` вместе с потребителями по `depends_on`, а профиль каждого — `component_profiles`. Сбой чтения диффа — отказ подготовки гейта, как в G3б-2.

AC-17. Каждый выбранный компонент в границе `in_outcome_bounds` получает свой прогон ядра `_gate` и свою запись пройденного гейта, в порядке записи `components:`.
- Первый отказ останавливает гейт, деталь отказа начинается с «компонент <имя>: ».
- По каждому компоненту вне границы запись гейта несёт строку «компонент <имя>: вне границы гейта исходов».
- Если вне границы все выбранные компоненты, гейт не прогоняется (исход перехода прежний). Пишется запись пропуска действием «проверка тестов не выполняется: гейт неослабления по исходам» (`project_profile.SKIP_ACTION`, форма `journal_skip`). Её деталь — строка «голова <sha>» и строка «компонент <имя>: вне границы гейта исходов» по каждому компоненту.
- `review_lines` (`orchestrator/advance_gates/outcome_integrity.py:1123`) для головы, у которой есть только такая запись пропуска, выдаёт прежнюю строку «гейт исходов для головы <h> не исполнялся» и за ней по строке «гейт исходов: компонент <имя>: вне границы гейта исходов» на каждый компонент.

AC-18. `review_lines` для головы выдаёт строки записей гейта всех компонентов. Пакет ревьювера задачи на `backend`, чей гейт прогнал и `frontend` (компонент-потребитель), показывает строки записи гейта `frontend`. То же у задачи, чей компонент вне границы гейта исходов (вариант учебного проекта: `backend` без поля `report`), а `frontend` в границе прогнан гейтом: пакет ревьювера показывает строки записи гейта `frontend`. У записи из одного компонента профиль гейта берётся прежним путём (`_bounds`), ключ записи гейта, строки `review_lines` и раздел пакета побайтно прежние.

AC-19. У записи из нескольких компонентов на выходе из `tests_writing`, если правило планки относит файл планки к компоненту X, отличному от компонента задачи Y, и X в границе гейта FAIL_TO_PASS (`in_outcome_bounds` профиля X), — отказ `FAIL_TO_PASS_REFUSAL_ACTION` с текстом «файл планки <имя> — компонента <X>, задача — компонента <Y>». AC-20. У задачи на записи из нескольких компонентов с одним компонентом задачи документы `knowledge` в брифе, задание test_author по правилу планки, сводки прогонов Vitest и итоговая строка `plank-run` побайтно совпадают с выводом для записи из одного этого компонента. AC-21. У компонента с командой pytest и явным `layers: []` правка существующего файла `test_support` с расширением `.py` даёт находку строгого режима (`STRICT_EDIT`, «строгий режим — правка существующего файла»). ## Оценка объёма и деление
Сработавшие сигналы:
- в зоне 23 файла и каталог `tests/`;
- 28 критериев приёмки;
- `budget_usd` 85 ≥ $30.

**Обоснование монолита.** Задача — уже третья часть деления G3б по решению Оператора 21.10. Нельзя резать вот что:
- снятие отказа записи из нескольких компонентов (требование 1);
- перевод мест задачи на `for_task` без пропусков (требование 2);
- гейт исходов по компонентам диффа (требование 3);
- отказ планки чужого компонента (требование 4).

Если снять отказ (1) без (2) или (4), то у записи из нескольких компонентов места, которые сейчас пропускают проверку при отказе `decide` (`_bounds`, `_test_integrity_diff_gate`, автогейт, `criterion_files`, `checks_local` в `acceptance_suite`), пропустят задачу без проверки. Если сделать (1)+(2) без (3), то гейт исходов задачи прогонит только её компонент и не заметит поломку компонента-потребителя по `depends_on`. Оба промежуточных состояния — ослабление гейтов неослабления, запрещённое без ADR (ADR-0002). А пока отказ стоит, части (2)–(4) без (1) не наблюдаемы: у записи из нескольких компонентов в них не попадает ни одна задача. Требования 5 и 7 отделить можно, но 5 опирается на `for_task` части 1, а оба занимают малую долю объёма. Если Оператор предпочтёт деление, разумная граница — «1–4» и «5, 7».
