# PLAN: Канарейка: повтор developer на красной планке (вариант а)

## Подход

`canary._drive_task` ведёт задачу циклом `auto.cmd_auto` + обработчиками
гейтов. Красная приёмочная планка на выходе `in_dev` сегодня — тупик:
`fsm` отказывает переходом («переход отклонён: приёмочные тесты»),
`auto` останавливается своим стоп-краном T038 на втором подряд
одинаковом отказе, не дав `developer` ни одного шанса на повтор внутри
самого прогона `auto`, а generic-ветка стагнации `_drive_task`
(`CANARY_MAX_STALL_ITERS=3`) убивает задачу раньше, чем Оператор успел
бы вручную позвать `run <id>`.

Решение — распознать этот конкретный класс отказа СРАЗУ после
`auto.cmd_auto` внутри `_drive_task` (до generic-ветки `runner.step_role
is not None`) и воспроизвести ручной возврат Оператора самим кодом
цикла: `runner.cmd_run(task_id)` напрямую (без `session_id` — то же,
что уже делают прочие синтетические гейт-проходы этого модуля, не
через `auto`), затем `continue` тем же циклом на очередной
`auto.cmd_auto`. Детектор смотрит на ПОСЛЕДНЮЮ запись журнала задачи:
либо прямая запись `fsm` с action `"переход отклонён: приёмочные
тесты"`, либо запись `"auto остановлен"` (стоп-кран T038), несущая тот
же текст внутри `detail` — оба пути покрыты приёмочными тестами задачи
(`tasks/01M2ARQD7C472KZACB3SZXGF1N/acceptance_tests/
test_canary_dev_retry.py`, AC-2/AC-7).

Счётчик повторов — локальная переменная цикла `_drive_task`
(`dev_retries`), сбрасываемая в 0 на каждой итерации, где новое
состояние после `auto.cmd_auto` не `in_dev` (обнуление «при уходе из
`in_dev`», требование 3/AC-4). Повтор — прогресс: `continue` идёт мимо
generic-ветки стагнации, `stall_streak` явно обнуляется тем же приёмом,
что уже применяет ветка `escalated`/переход по гейту. Превышение
потолка — `_kill_inconclusive` тем же путём, что и два уже существующих
потолка цикла (эскалации, стагнация): журналируется причина, поднимается
`alert kind=threshold`, `cleanup.cmd_kill`.

Отчёт (требование 5) читает число повторов из журнала задачи — тот же
приём, что и остальные метрики `_task_metrics` (`_step_count`,
`_escalation_notes`): каждый повтор развода журналируется отдельной
записью `actor=canary` с фиксированным литералом действия ДО вызова
`runner.cmd_run`, `_task_metrics` считает такие записи. Это не заводит
новое состояние или таблицу — тот же журнал, что уже несёт
`steps.txt`/выдержку.

Разночтения SPEC не встретил: оба пути детектора (напрямую fsm / через
обёртку «auto остановлен») буквально описаны требованием 2 и покрыты
приёмочными тестами задачи, реализация под них подгоняется напрямую, не
по своей интерпретации.

## Шаги

1. `orchestrator/config.py`: константа `CANARY_MAX_DEV_RETRIES = 2` рядом
   с `CANARY_MAX_ESCALATION_CYCLES`/`CANARY_MAX_STALL_ITERS`, тем же
   стилем докстринг-комментария.
2. `orchestrator/canary.py`: литерал `_ACCEPTANCE_TESTS_REFUSAL_ACTION`,
   детектор `_acceptance_refusal_blocks_in_dev`, счётчик `dev_retries` и
   новая ветка в `_drive_task` (retry/kill), журнальная запись повтора,
   счётчик `_dev_retry_count` и его подключение в `_task_metrics`, поле
   «повторов developer=…» в строке отчёта `_run_one_task`.
3. Юнит-тесты `tests/test_canary.py` (AC-7, AC-8, AC-9 — зеркало
   приёмочных сценариев задачи, размещённое в зоне разработчика, как
   того требует SPEC).

## Влияние на систему

Правка целиком внутри `canary.py`/`config.py` — новая ветка `_drive_task`
срабатывает ТОЛЬКО когда: (а) задача канареечная (`_drive_task` вызывается
только из `canary.py`), (б) состояние `in_dev`, (в) последняя запись
журнала — именно этот литерал отказа. Поведение `auto` для обычных задач
не меняется ни строкой (файл `auto.py` не тронут, «Не входит» SPEC).
Прочие классы отказа на выходе `in_dev` (планка не найдена в источнике,
зоны, гейт заявки мутации, лок планки) не совпадают с литералом и
продолжают идти прежним путём стагнации `CANARY_MAX_STALL_ITERS` — это
явно проверяет приёмочный тест `test_canary_other_class_refusal.py`
(AC-5), являющийся зелёным уже до этой задачи (сценарий не касается
новых строк).

Новый потолок `CANARY_MAX_DEV_RETRIES` — независимая от
`CANARY_MAX_STALL_ITERS`/`CANARY_MAX_ESCALATION_CYCLES` защита от
бесконечного цикла: превышение ведёт туда же, куда и оба существующих
потолка (`_kill_inconclusive` → `threshold`-алерт → `cleanup.cmd_kill`),
не открывает новый способ завершения прогона. Откат — удаление ветки и
константы, поведение возвращается к текущему (стагнация до
`CANARY_MAX_STALL_ITERS`).

Ни один существующий тест/гейт/лимит не ослабляется — добавляется новая
ветка и новый потолок, ничего не удаляется и не смягчается.

## Риски

Детектор завязан на буквальный текст `"переход отклонён: приёмочные
тесты"`, дублируемый (не импортируемый) из `fsm_advance.py` — тот же
класс дублирования литералов, что уже есть между `store.py`/`auto.py`
(`REFUSAL_ACTION_PREFIX`) и между `auto.py`/`brief.py`
(`ROLE_NOT_FINISHED_REFUSAL_ACTIONS`); будущая правка текста в
`fsm_advance.py` без синхронной правки здесь тихо выключит повтор
(отказ этого класса снова пойдёт по пути стагнации, не поломав ничего
сверх этого). Не мой файл — `fsm_advance.py` вне зоны этой задачи
(«Не входит» не называет его прямо, но он и не в зоне SPEC), трогать не
буду.
