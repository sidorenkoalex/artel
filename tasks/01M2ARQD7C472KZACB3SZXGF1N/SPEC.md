# SPEC: Канарейка: повтор developer на красной планке (вариант а)

## Контекст
Прогон канарейки 20260912T113132Z (docs/backlog.md, строка П1 от 12.09,
коммит 85ca2927) уходит в kill не по существу: `in_dev` отказывает
переходом по красной приёмочной планке («переход отклонён: приёмочные
тесты»), `auto` останавливается стоп-краном T038 на двух подряд
одинаковых отказах не запуская роль, а `canary._drive_task` трактует эту
неизменность (состояние, потраченное) как стагнацию и убивает задачу
через `CANARY_MAX_STALL_ITERS` проходов — быстрее, чем developer вообще
получает шанс починить код. В реальном конвейере на этом месте Оператор
вручную возвращает developer командой `run <id>`; решение Оператора
12.09 (вариант а) — воспроизвести этот же возврат ВНУТРИ цикла
канарейки, не трогая поведение `auto` для обычных задач.

## Требования

1. Новая именованная константа `orchestrator/config.py::
   CANARY_MAX_DEV_RETRIES = 2` — докстринг-комментарий по образцу
   соседних потолков цикла канарейки (`CANARY_MAX_ESCALATION_CYCLES`,
   `CANARY_MAX_STALL_ITERS`).
2. `canary._drive_task`: после `auto.cmd_auto`, если задача осталась в
   состоянии `in_dev`, а последняя относящаяся к этому запись журнала —
   отказ перехода «переход отклонён: приёмочные тесты» (журналируется
   либо напрямую `fsm`, либо как причина, из-за которой `auto`
   остановился своим стоп-краном — тот же текст в этом случае несёт
   запись «auto остановлен»), — цикл вызывает `runner.cmd_run(task_id)`
   (developer получает бриф с блоком «ОТКАЗ ADVANCE (история)», как при
   ручном возврате Оператора) и продолжает цикл очередным
   `auto.cmd_auto`.
3. Счётчик повторов developer ведётся на один визит состояния `in_dev`
   (обнуляется при уходе из `in_dev`). Повтор считается прогрессом
   цикла: `stall_streak` сбрасывается, потраченное растёт. Превышение
   `config.CANARY_MAX_DEV_RETRIES` повторов подряд — `_kill_inconclusive`
   с текстом «canary: `<CANARY_MAX_DEV_RETRIES>` повторов developer на
   красной планке — задача не сходится» (по образцу текстов
   `_kill_inconclusive` для соседних потолков).
4. Отказы другого класса на выходе `in_dev` (планка не найдена в
   источнике, зоны, гейт заявки мутации, лок планки) повтором developer
   не лечатся — прежнее поведение (стагнация до
   `config.CANARY_MAX_STALL_ITERS`, `_kill_inconclusive` по стагнации)
   сохраняется байт-в-байт.
5. Строка отчёта задачи прогона канарейки (`шагов=… исход=…`) несёт поле
   «повторов developer=`<n>`» — число выполненных за прогон задачи
   повторов developer видно в отчёте, не только в journal/steps.txt.

## Критерии приёмки

AC-1. `orchestrator/config.py` несёт константу `CANARY_MAX_DEV_RETRIES`
со значением `2` и докстринг-комментарий в стиле соседних потолков
(`CANARY_MAX_ESCALATION_CYCLES`, `CANARY_MAX_STALL_ITERS`).

AC-2. `canary._drive_task`: если после `auto.cmd_auto` задача осталась в
`in_dev`, а причина — отказ перехода «переход отклонён: приёмочные
тесты» (журналирован напрямую `fsm`, либо тем же текстом внутри причины
остановки `auto` стоп-краном, запись «auto остановлен»), цикл вызывает
`runner.cmd_run(task_id)` и продолжает работу очередным вызовом
`auto.cmd_auto` — тем же путём, каким Оператор возвращает developer
командой `run <id>` в реальном конвейере.

AC-3. Повтор developer засчитывается циклом как прогресс: после него
`stall_streak` не растёт (обнулён/остаётся не увеличенным по сравнению
со стагнацией), потраченное (`spent_usd`) задачи растёт.

AC-4. Счётчик повторов developer ведётся на один визит состояния
`in_dev` (обнуляется при уходе из этого состояния); превышение
`config.CANARY_MAX_DEV_RETRIES` повторов подряд по причине требования 2
влечёт `_kill_inconclusive` с текстом «canary:
`<CANARY_MAX_DEV_RETRIES>` повторов developer на красной планке —
задача не сходится».

AC-5. Отказ другого класса на выходе `in_dev` (планка не найдена в
источнике, зоны, гейт заявки мутации, лок планки) не вызывает повтор
developer: `runner.cmd_run` циклом не зовётся, поведение — прежняя
стагнация до `config.CANARY_MAX_STALL_ITERS` и `_kill_inconclusive` по
стагнации, без изменений.

AC-6. Строка отчёта задачи прогона канарейки (несущая `шагов=…` и
`исход=…`) дополнена полем «повторов developer=`<n>`», где `<n>` —
число выполненных за прогон этой задачи повторов developer из
требования 2.

AC-7. Тест в `tests/test_canary.py`: стенд, где первый `auto.cmd_auto`
оставляет задачу в `in_dev` с журнальной записью «переход отклонён:
приёмочные тесты», — цикл вызывает `runner.cmd_run` ровно один раз и
продолжает работу (мутация «повтор не вызывается» красит тест).

AC-8. Тест в `tests/test_canary.py`: `config.CANARY_MAX_DEV_RETRIES + 1`
отказов подряд по причине требования 2 — цикл убивает задачу через
`_kill_inconclusive` с текстом из AC-4, а `runner.cmd_run` за весь визит
состояния вызван не более `config.CANARY_MAX_DEV_RETRIES` раз (сверх
потолка — не вызывается).

AC-9. Тест в `tests/test_canary.py`: отказ другого класса в `in_dev`
(требование 4) — `runner.cmd_run` циклом не вызывается ни разу, кил
происходит прежним путём стагнации (`config.CANARY_MAX_STALL_ITERS`);
отчёт прогона несёт «повторов developer=…» (AC-6); ни один существующий
тест `tests/test_canary.py` не ослаблен (условия существующих тестов не
смягчены, не удалены).

## Оценка объёма и деление

Сработали сигналы: «число затрагиваемых модулей/файлов» и производный
от него «прогноз диффа не дан». Оба — артефакт того, что раздел «Не
входит» (по образцу самого ТЗ, строка 96) и «Материалы» дословно
называют `orchestrator/auto.py`, `orchestrator/runner.py`,
`orchestrator/fsm_advance.py`, `orchestrator/pin.py` как файлы, которые
эта задача НЕ трогает и трогать не вправе (готовый, независимо
работающий возврат developer, который цикл канарейки только ВЫЗЫВАЕТ,
не меняет) — guard считает упоминания путей по всему тексту SPEC, а не
только по факту правки. Реальная зона правки — 2 файла
(`orchestrator/canary.py`, `orchestrator/config.py`) плюс `tests/`,
ниже порога `SPLIT_SIGNAL_ZONE_FILES = 5`.

**Обоснование монолита.** Задача — одна неделимая механика: константа
`CANARY_MAX_DEV_RETRIES` (требование 1) не имеет смысла без ветки
повтора в `_drive_task` (требования 2–4), которая её единственный
потребитель, а строка отчёта (требование 5) отчитывается именно об
этом же счётчике повторов. Разрезать на «константа отдельно» и «логика
отдельно» — оставить между частями недостижимое промежуточное
состояние (объявленный, но нигде не используемый потолок либо логика
без потолка, которая не компилируется без константы). Как единственный
потребитель константы, использующий её в единственном месте вызова
цикла, эта задача не делится на самостоятельно мержимые части без
дробления самой механики поперёк.
