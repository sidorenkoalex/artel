# PLAN: Частичная стоимость шага по видам токенов, калибровка курса

## Подход

Два независимых узла:

1. **Расчёт по видам вместо средней ставки** (`orchestrator/spend.py`,
   требования 1-3, AC-1..AC-5). `config.TOKEN_RATES[role]` несёт
   четыре цены за токен — по одной на каждый счётчик
   `config.USAGE_TOKEN_KEYS` (`input_usd_per_token`,
   `output_usd_per_token`, `cache_creation_usd_per_token`,
   `cache_read_usd_per_token`) — публичные пропорции Anthropic между
   входом/выходом/записью кэша/чтением кэша ($3/$15/$3.75/$0.30 за
   миллион), а не единая эмпирическая ставка $0.45/млн Оператора
   04.09 (та ставка была временной мерой ровно до этой задачи, SPEC
   «Контекст»). Разбор usage-события больше не суммирует счётчики
   сразу (`spend.step_tokens` был единственным путём) — новая
   `spend.usage_tokens_by_type(usage)` отдаёт словарь по видам,
   `step_tokens` теперь тонкая обёртка над ней (сумма для мест, которым
   нужно только общее число, например `parse_cost_event["tokens"]`,
   не тронутого требованиями). Симметрично для потока:
   `spend.stream_usage_by_type` (было `stream_usage_tokens`) и
   `spend.partial_tokens_from_log` возвращают словарь-разбивку, не
   int; `agent_log.OutputPump.partial_tokens` — тоже словарь,
   накапливаемый по ключу, а не одним счётчиком. Сердце требования 2 —
   `spend.partial_cost_usd(role, tokens_by_type)`: сумма произведений
   «количество вида × цена вида» по `config.USAGE_TOKEN_KEYS`, без
   среднего. Курс роли не несёт одной из четырёх цен — `ValueError`
   (требование 3, AC-5): именованный отказ, не тихий пропуск вида или
   ноль. `spend.charge_missing_result` (сценарий таймаута/обрыва
   пайпа) зовёт эту же функцию по разбивке, а не считает сам — одна
   формула на обе точки, а не две рассинхронные (тот же источник
   инцидента 04.09, AC-3 — регресс-проверка именно этого сценария).
   `spend.charge_step` (путь с известным `total_cost_usd` из
   финального события) при известной разбивке пишет ОТДЕЛЬНУЮ строку
   журнала «agent cost KNOWN» с фактической ценой и разбивкой — не
   заменяет существующую «agent cost»/`cost_note` (требование 6,
   AC-8) — источник данных калибровки узла 2.

2. **Калибровка курса** (`orchestrator/report.py`, требования 4-5,
   AC-6/AC-7). `report.token_rate_divergence(conn)` читает записи
   журнала «agent cost KNOWN» по всем задачам, для каждой пересчитывает
   расчётную цену той же разбивки через `spend.partial_cost_usd` по
   курсу роли и сравнивает с фактической: коэффициент — суммарное
   расхождение по всем известным шагам роли `abs(Σрасчёт - Σфакт) /
   Σфакт`, не среднее по шагам (не даёт мелким шагам топить крупный
   расходящийся). Роль без записей — не в результате вовсе, не 0.0.
   Курс роли неполон — её шаги пропускаются молча (это дело
   `partial_cost_usd` в её собственной точке вызова, не калибровки).
   Часть панели `report` (`_metrics_html`/`_divergence_html`), не
   отдельная команда — выбор разработчика, требование 4 явно оставляет
   его на усмотрение. Коэффициент выше именованного порога
   `config.TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD` (0.5, по аналогии с
   `CANARY_DEVIATION_RATIO`) поднимает `alerts` `kind=warning`,
   `target=None` (расхождение — по роли поперёк задач и target'ов, не
   про одну задачу); новый вид `warning` добавлен в `alerts.KINDS`.
   `cmd_report` перестаёт быть строго read-only (докстринг
   `_render`/`cmd_report` фиксирует это явно) — единственное,
   локализованное исключение, обоснованное этой же SPEC.

Оба узла делят один и тот же контракт данных — словарь по
`config.USAGE_TOKEN_KEYS` — поэтому вносятся одним диффом, без
промежуточного состояния «расчёт по видам, но калибровка ещё не умеет
её читать».

## Шаги

1. `orchestrator/config.py`: `TOKEN_RATES[role]` — четыре цены на
   каждую из четырёх ролей (analyst/test_author/developer/reviewer);
   `TOKEN_RATE_DIVERGENCE_ALERT_THRESHOLD = 0.5`.
2. `orchestrator/spend.py`: `usage_tokens_by_type`/`stream_usage_by_type`
   (разбор по видам, замена `step_tokens`-суммирования как единственного
   пути и `stream_usage_tokens`); `partial_tokens_from_log` возвращает
   разбивку; `partial_cost_usd(role, tokens_by_type)` — сумма
   произведений по видам, `ValueError` на неполном курсе;
   `charge_missing_result`/`charge_step` — разбивка вместо int, новая
   строка журнала «agent cost KNOWN» в `charge_step`.
3. `orchestrator/agent_log.py`: `OutputPump.partial_tokens` — словарь,
   `catch_cost` копит по видам через `stream_usage_by_type`.
4. `orchestrator/pause.py`: `_account_partial_cost` — `{}` вместо `0`
   на пути «лога нет».
5. `orchestrator/alerts.py`: `warning` в `KINDS` + докстринг.
6. `orchestrator/report.py`: `token_rate_divergence`, разбор записи
   «agent cost KNOWN» (`_known_cost_breakdown`), `_divergence_html`,
   `cmd_report` считает и передаёт `divergence` в `_render`/
   `_metrics_html`.
7. `tests/test_step_cost.py`, `tests/test_agent_log.py` — миграция
   существующих тестов под новую сигнатуру (словарь вместо int) без
   ослабления проверяемого поведения (переименованные методы сохраняют
   исходный ассерт, только на новом контракте данных); новые тесты
   `PartialCostUsdTest` на `ValueError` неполного курса и на то, что
   разные виды тарифицируются разными ставками.
8. Регрессия предшествующей задачи 01M1NWCM3TDY0YABEKE8DYQA1C
   (требование 7/AC-9): её приёмочные тесты (`tasks/
   01M1NWCM3TDY0YABEKE8DYQA1C/acceptance_tests/
   test_ac2_known_rate_partial_charge.py`,
   `test_ac3_unknown_rate_alert_and_estimate.py`) звали
   `spend.charge_missing_result(..., partial_tokens=1000/777, ...)` —
   плоским `int`, старым контрактом. Эти два файла — приёмочная планка
   ЗАВЕРШЁННОЙ задачи, не текущей (лок `tasks/<id>/acceptance_tests/`
   правилом «код чинится под них» касается только планки ЭТОЙ задачи,
   `tasks/01M1PP0VYRT55WN8GGVG66X89Y/acceptance_tests/`); интерфейс
   меняется этой SPEC намеренно (её же собственный тест
   `test_ac3_timeout_cost_matches_type_breakdown.py` фиксирует смену
   типа `partial_tokens` буквально), поэтому оба места переведены на
   `{"input_tokens": N}` — то же число токенов, та же проверяемая
   сумма/текст журнала/алерт, только адресованное конкретному виду
   счётчика (тот же приём, что уже применён к `tests/test_step_cost.py`
   в этой же ветке) — не ослабление, только адаптация вызова под
   новую сигнатуру. Третий файл этой же задачи
   (`test_ac4_no_usage_events_unchanged.py`, `partial_tokens=0`) не
   тронут — сценарий `saw_usage_event=False` возвращается из
   `charge_missing_result` до первого обращения к разбивке, `int`
   там безопасен независимо от типа параметра.

Работа наследует WIP-чекпоинт `0dc2aa67` (шаги 1-7 — таймаут
предыдущего захода `in_dev`, код и тесты уже были готовы и зелены);

## Влияние на систему

- Тронутые модули: `spend.py` (сигнатуры четырёх функций меняются с
  `int`/суммы на словарь-разбивку — все вызывающие в `orchestrator/`
  обновлены тем же диффом: `agent_log.py`, `pause.py`, `runner.py` уже
  звал `pump.partial_tokens` напрямую, правки не потребовал), `config.py`
  (данные, не код), `alerts.py` (новый элемент кортежа `KINDS`, не
  ломает существующие `kind=` — проверено `grep` по вызывающим `raise_
  alert`), `report.py` (новая функция + один новый аргумент `_render`/
  `_metrics_html` со значением по умолчанию `None`, обратная
  совместимость вызывающих внутри модуля сохранена).
- `grep` по всей кодовой базе (`orchestrator/`, `tests/`) на старые
  имена `stream_usage_tokens`/`step_tokens`-как-единственный-путь не
  нашёл ни одного оставшегося вызывающего с прежней сигнатурой —
  единственный класс регрессии этого рефакторинга (переименование +
  смена типа возврата) закрыт полностью, не точечно.
- Гейты/лимиты/инварианты не ослаблены: `spend.partial_cost_usd` на
  неполном курсе теперь ПАДАЕТ (`ValueError`) там, где раньше молча
  считала бы по средней ставке — строже прежнего, не слабее (AC-5).
  `cmd_report` перестаёт быть строго read-only — осознанное,
  документированное в докстринге исключение, ограниченное одним
  вызовом `alerts.raise_alert` внутри `token_rate_divergence`
  (обоснование — в самом требовании 5 этой SPEC).
- Совместимость (требование 6/AC-8) проверена приёмочным тестом AC-8:
  записи журнала до этой задачи не читаются задним числом ничем новым
  (`token_rate_divergence` фильтрует по `action ==
  "agent cost KNOWN"` — действие, которого не существовало до этой

  попадают в выборку).

  `spend.py`/`agent_log.py`/`pause.py`/`report.py`/`alerts.py`/
  `config.py` не зависит от новой формы данных (список выше — полный,
  по `grep`).
- Изменение шага 8 — правка тестовых файлов ЗАВЕРШЁННОЙ задачи
  01M1NWCM3TDY0YABEKE8DYQA1C, не текущей: не ослабление (тот же

## Риски

- Числа `TOKEN_RATES` — публичные пропорции Anthropic ($3/$15/$3.75/
  $0.30 за миллион), не повторная эмпирическая калибровка по факту
  CLI этого пульта: `report.token_rate_divergence` — самокорректирующийся
  контур ИМЕННО для того, чтобы поймать расхождение с фактом раньше,
  чем оно снова всплывёт эскалацией по бюджету (SPEC «Контекст»);
  следующая правка чисел — по его сигналу, не наугад.

  read-only дизайна `cmd_report` (tasks/T092/SPEC.md, требование 9):
  ограничено одним вызовом `alerts.raise_alert`, дедуп уже несёт сам
  `alerts.raise_alert` (не заводит дубликат открытого алерта).
