# SPEC: Частичная стоимость шага по видам токенов (чтения кэша по своей цене), калибровка курса

## Контекст
Первое боевое срабатывание тарифа 04.09 (задача 01M1NWCM3TDY0YABEKE8DYQA1C)
показало: `spend.step_tokens`/`spend.stream_usage_tokens` суммируют ВСЕ
счётчики usage потока (`config.USAGE_TOKEN_KEYS`: вход, выход, запись
кэша, чтение кэша), а `spend.partial_cost_usd` умножает эту сумму на
среднее цены входного и выходного токена роли (`config.TOKEN_RATES`).
Чтения кэша — почти весь объём шага и стоят на порядок дешевле входа:
эффективная ставка завышала частичную стоимость таймаута примерно в 20
раз (developer канарейки ч.1: $83.58 за 9,3 млн токенов при реальных
~$4). Временная мера Оператора 04.09 — единая эмпирическая ставка
$0.45/млн на оба вида токена в `config.TOKEN_RATES`; эта задача
заменяет её точным расчётом по видам токенов и добавляет калибровку,
которая заметит следующее расхождение курса с фактом раньше, чем это
снова всплывёт в эскалации по бюджету.

## Требования

1. `config.TOKEN_RATES[role]` несёт четыре цены за токен вместо двух —
   по одной на каждый счётчик `config.USAGE_TOKEN_KEYS` (вход, выход,
   запись кэша, чтение кэша), например `input_usd_per_token`,
   `output_usd_per_token`, `cache_creation_usd_per_token`,
   `cache_read_usd_per_token` — по аналогии с уже существующими двумя
   ключами.
2. Расчёт частичной стоимости токенов usage-события (`message.usage`/
   `result.usage` потока `stream-json`: `input_tokens`, `output_tokens`,
   `cache_creation_input_tokens`, `cache_read_input_tokens`) накапливает
   их РАЗДЕЛЬНО по видам (не одной суммой, как сегодня
   `spend.step_tokens`/`spend.stream_usage_tokens`) и переводит в доллары
   умножением каждого вида на свою цену из `config.TOKEN_RATES[role]`, а
   не средней ставкой по сумме всех видов.
3. Курс роли, в котором не хватает одной из четырёх цен требования 1, —
   именованный отказ (явно определённая ошибка/маркер), а не тихий ноль
   или пропуск этого вида токена при расчёте.
4. Пульт умеет по завершённым шагам (журнал `store.journal`, записи с
   фактической ценой из финального события потока `type: result`,
   `total_cost_usd`) сравнить эту фактическую цену с расчётной ценой по
   видам токенов требования 2 и напечатать коэффициент расхождения по
   роли — новой командой пульта либо частью существующей команды
   `report` (`orchestrator/report.py`), на усмотрение разработчика.
5. Коэффициент расхождения калибровки требования 4 больше именованного
   порога (константа `config.py`, по аналогии с `SPLIT_SIGNAL_*`/
   `STEP_COST_ESTIMATE_USD`) поднимает алерт `alerts` с `kind=warning`.
6. Совместимость: записи журнала «agent cost PARTIAL» и значения
   колонки `spent_estimate_usd`, зафиксированные ДО этой задачи, не
   пересчитываются задним числом. Формат НОВЫХ записей журнала шага
   дополняется разбивкой токенов по видам, не заменяя существующие
   поля записи.
7. Существующие тесты тарифа — `tests/test_step_cost.py` (механика
   T007/T012/T040) и тесты задачи 01M1NWCM3TDY0YABEKE8DYQA1C — остаются
   зелёными без ослабления состава проверок (переформулировка
   отдельных assert'ов под новую сигнатуру расчёта — не ослабление,
   если проверяемое поведение не сузилось).

## Критерии приёмки

AC-1. `config.TOKEN_RATES[role]` несёт четыре цены за токен: вход,
выход, запись кэша, чтение кэша — по одной на каждый счётчик
`config.USAGE_TOKEN_KEYS`.

AC-2. Частичная стоимость шага с известной по видам разбивкой usage
считается суммой произведений «количество токенов вида × цена этого
вида по курсу роли», а не средней ставкой по сумме всех видов токенов
сразу.

AC-3. Частичная стоимость ТАЙМАУТА шага (`orchestrator.spend.
charge_missing_result`, сценарий обрыва потока без финального события)
с известной по видам разбивкой usage равна сумме стоимостей по видам
(регресс-проверка AC-2 в этом конкретном сценарии — источник эскалации
04.09).

AC-4. Токены чтения кэша (`cache_read_input_tokens`) тарифицируются по
своей цене чтения кэша, а не по цене входного токена.

AC-5. Курс роли без одной из четырёх цен требования 1 — именованный
отказ (явно определённая ошибка/маркер), а не тихий ноль или пропуск
этого вида токена при расчёте.

AC-6. Пульт по завершённым шагам сравнивает фактическую цену из
финального события потока (`type: result`, `total_cost_usd`) с
расчётной ценой по видам токенов и печатает коэффициент расхождения по
роли.

AC-7. Коэффициент расхождения калибровки больше именованного порога
(константа `config.py`) поднимает алерт `kind=warning`.

AC-8. Записи журнала «agent cost PARTIAL», зафиксированные ДО этой
задачи, и уже накопленные ДО этой задачи значения колонки
`spent_estimate_usd` не пересчитываются задним числом; формат НОВЫХ
записей журнала шага дополняется разбивкой токенов по видам, не
заменяя существующие поля записи.

AC-9. Существующие тесты тарифа — `tests/test_step_cost.py` (механика
T007/T012/T040) и тесты задачи 01M1NWCM3TDY0YABEKE8DYQA1C — остаются
зелёными без ослабления состава проверок.
