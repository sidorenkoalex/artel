# SPEC: разрез orchestrator/doctor.py на пакет проверок

## Контекст
`orchestrator/doctor.py` — 1856 строк, 24 функции `check_*` из 65
функций в 17 разделах. Каждая задача, добавляющая свою проверку,
объявляет зоной весь файл и держит его весь свой цикл — по данным
06.09 это первый по частоте файл отказов очереди зон (11 отказов из
31). Задача разрезает файл на пакет `orchestrator/doctor/` с фасадом,
не меняя логику проверок и не меняя механику зон, чтобы будущие задачи
занимали зоной только нужный подмодуль.

Порядок запуска: разработчик стартует ПОСЛЕ мержа всех задач,
держащих или ждущих `orchestrator/doctor.py` на момент старта (по
состоянию на 06.09: 01M1TQ0ZCY, 01M1TQ0X14, 01M1THKRK8, 01M1SHK3MD,
01M1R5B33C, 01M1SG9WPV) — перенос всего файла конфликтует с любой их
правкой. Сверить по `status` этих задач перед стартом.

## Требования

1. Пакет `orchestrator/doctor/` с `__init__.py`-фасадом, экспортирующим
   ВСЕ публичные имена сегодняшнего `doctor.py` (функции проверок,
   `all_checks`, `cmd_doctor`, `Check`, константы, коллаборанты
   `gitcmd`/`subprocess`/`shutil`/`store`/`config` и прочие имена, на
   которые ссылаются `tests/` и планки — перечень снять
   `grep -rho "doctor\.[a-zA-Z_]*"` по `tests/`, `tasks/*/acceptance_tests/`,
   `orchestrator/`, `scripts/`). `import orchestrator.doctor as doctor`
   и `from orchestrator import doctor` работают как раньше.
2. Разделы файла переезжают в подмодули по границам сегодняшних
   комментариев-разделителей (один раздел — один файл; точные имена
   файлов решает PLAN). Тело функций не переписывается: перенос, не
   рефакторинг логики.
3. Коллаборанты в подмодулях читаются через фасад `orchestrator.doctor`
   в момент вызова (ленивое обращение к атрибуту фасада), единым
   приёмом на весь пакет, описанным в докстринге `__init__.py`; прямой
   `import subprocess`/`import shutil`/`from orchestrator import
   gitcmd` в подмодуле проверки — дефект.
4. `all_checks` — состав и порядок проверок прежние (сверка вывода
   `doctor` без аргументов на пустой БД до и после разреза).
5. `docs/codebase-map.md` регенерируется штатно
   (`python3 scripts/codebase_map.py`); `docs/invariants.md`, если
   называет `orchestrator/doctor.py` путём, обновляется на пакет;
   `COMMON_ZONES`/механика зон не трогаются.
6. Весь существующий `tests/` проходит без правки ассертов и без
   правки целей `mock.patch`/`mock.patch.object`.
7. Планки закрытых задач не гоняются и не правятся. Если планка живой
   задачи патчит `doctor.<имя>` и после разреза краснеет —
   разработчик эскалирует с перечнем таких имён/задач, а не правит
   планку.

## Оценка объёма и деление

Сработавшие сигналы: `budget_usd` = 40 ≥ `SPLIT_SIGNAL_BUDGET_USD` (30);
число критериев приёмки = 12 ≥ `SPLIT_SIGNAL_AC_COUNT` (10).

Обоснование монолита (решение уже дано Оператором в ТЗ): перенос
разделов `doctor.py` в подмодули по одному, отдельными задачами, оставил
бы на время между ними два источника коллаборантов (часть подмодулей
берёт `gitcmd`/`subprocess`/`shutil` через фасад, часть — ещё нет) и
двойной порядок `all_checks` (часть проверок уже в подмодулях, часть
ещё в монолитном хвосте `doctor.py`) — оба переходных состояния
нарушают инвариант AC-4/AC-5 этой же задачи и негде мержить
промежуточный результат с зелёной планкой. Атомарная единица смены
механики — весь файл разом: фасад, все подмодули и точки чтения
коллаборантов должны появиться одним коммитом/мержем.

Границы зон (`orchestrator/doctor.py`, `orchestrator/doctor/`,
`tests/`, `docs/invariants.md`) и порядок запуска (после мержа задач,
держащих/ждущих `doctor.py` на 06.09 — раздел «Контекст») ограничивают
блокировку одной задачей, а не размером зоны — деление на подзадачи не
уменьшило бы конфликтность, а добавило бы промежуточные нерабочие
состояния. Монолит принят Оператором по факту формулировки ТЗ (пункт
«Порядок» ТЗ прямо предвидит это обоснование: «перенос разделов по
одному оставил бы два источника коллаборантов и двойной порядок
all_checks»).

## Не входит

- Изменение логики проверок (`check_*` и прочих функций) — только
  перенос между файлами.
- Изменение механики зон (`zone_lock`, единица зоны — файл).
- Разрез `fsm_advance.py`, `fsm.py`, `guard.py` — следующие кандидаты
  по итогам этого разреза; `fsm_advance.py` уже режется в отдельной
  задаче (R2).
- Прогон или правка планок закрытых задач.
- Правка планок живых задач, патчащих `doctor.<имя>`, — при конфликте
  эскалация (AC-12), не правка.
