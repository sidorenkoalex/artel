# PLAN: разрез orchestrator/doctor.py на пакет проверок

## Подход

Механический перенос: 17 разделов монолитного `orchestrator/doctor.py`
(1856 строк, границы — комментарии-разделители на строках, перечисленных
в SPEC «Материалы») разъезжаются по 17 файлам пакета
`orchestrator/doctor/`, плюс `__init__.py`-фасад. Тело функций не
переписывается — перенесено байт-в-байт, кроме одной механической
правки: обращения к коллаборантам (`gitcmd`, `subprocess`, `shutil`,
`store`, `config`, `alerts`, `artifact_branch`, `canary`, `coldstart`,
`liveness`, `projects`, `roles`, `runner`, `snapshot`, `spend`, `stack`,
`targets`, `workspace`, `zone_lock`) и ссылки на имена из ДРУГИХ файлов
пакета (`Check`, приватные помощники вроде `_auto_ack_gone`, сами
`check_*`-функции внутри `all_checks`) заменены на ленивое чтение через
атрибут фасада `doctor.<имя>` в момент вызова.

Ключевое архитектурное решение — единый узел связывания: подмодуль
пакета НИКОГДА не импортирует другой подмодуль или коллаборанта
напрямую, только `from orchestrator import doctor` и обращение
`doctor.<имя>` внутри тела функции. Это работает даже во время
инициализации самого пакета (Python регистрирует частично собранный
модуль в `sys.modules` до выполнения тела `__init__.py`, подмодуль
получает ссылку на него и обращается к атрибутам только ПОЗЖЕ, при
реальном вызове, когда фасад уже полностью собран) и сохраняет
работоспособность существующих `mock.patch.object(doctor, "gitcmd", …)`
без правки целей моков (AC-8) — САМАЯ важная находка при реализации:
это правило пришлось распространить не только на межфайловые ссылки, но
и на ссылки МЕЖДУ функциями ОДНОГО файла (`_orphan_artifact_branches`
вызывает `_remote_artifact_branch_names`, `sweep_orphan_artifact_
branches` вызывает `_orphan_artifact_branches`) — юнит-тесты
`test_default_argument_computes_remote_itself`/`test_default_argument_
computes_orphans_itself` патчат именно фасадный атрибут и ждут, что
вызывающий код внутри ТОГО ЖЕ файла это увидит; первая версия разреза
(с исключением «своё видно напрямую») эти два теста ломала.

Единственное исключение из «единого приёма» — сигнатуры с
non-literal-дефолтом (`def f(x=_UNSET)`): дефолт вычисляется РАЗ, при
определении функции (загрузка модуля), до того как фасад успевает
собрать себя целиком — обёртка `doctor._UNSET` в позиции дефолта дала
бы `AttributeError` при импорте пакета. `_UNSET` в позиции дефолта
остаётся локальной ссылкой (определена раньше в том же файле), внутри
тела функции сравнение `remote is doctor._UNSET` уже читает атрибут
фасада как обычно — работает, потому что фасад реэкспортирует ТОТ ЖЕ
объект (`from .orphan_branches import _UNSET`).

Стандартные модули без коллаборантской роли (`os`, `re`, `json`,
`socket`, `statistics`, `sys`, `tempfile`, `time`, `pathlib.Path`) в это
правило не попадают — их никто не подменяет в тестах, подмодули
импортируют их обычным образом на своём уровне.

Перенос делался инструментом, не руками посимвольно: скрипт на `ast`
разбирал исходный `doctor.py`, размечал каждое верхнеуровневое
определение по разделу (по номеру строки), затем для каждого раздела
находил через AST все обращения к коллаборантам/соседним разделам и
вставлял префикс `doctor.` точными байтовыми вставками в исходный
текст — без regex по сырому тексту (в файле сплошь docstring'и и
сообщения с Cyrillic-текстом, где подстроки вида `config.py`,
`targets.yaml`, `doctor.cleanup.artifact_branches` живут ВНУТРИ строк и
не должны быть тронуты) и без `ast.unparse` (потерял бы обычные `#`
комментарии внутри тел функций, которых в файле много, и что менее
важно — перефарматировал бы код). Первая версия скрипта наивно
трактовала `col_offset` AST как индекс Python-строки — но `col_offset`
это смещение в БАЙТАХ UTF-8, а файл полон кириллицы (по 2 байта на
символ) — вставки уезжали в середину идентификаторов на строках с
кириллицей перед точкой вставки (испортило, например,
`config.CLI_VERSION_PIN` в middle of `VERSION`). Исправлено декодом
префикса байт строки перед вычислением реального символьного индекса.

Обе выборки — карта «раздел → строки файла» и хэши AST каждой функции
для регресс-теста AC-3 — сняты с ОРИГИНАЛЬНОГО `doctor.py` (git-ревизия
непосредственно перед этой задачей) один раз, до переноса, и записаны в
`tasks/01M1TT9BPBRYMDXXEWVZSRG51V/acceptance_tests/_shared.py` — файл,
на который ссылаются локальные приёмочные тесты этой задачи, но
которого не было на диске на старте шага (см. «Риски»/эскалация ниже
снята: файл — чисто механический вычислимый вывод, не решение о дизайне
кода).

## Риски

- `tasks/01M1TT9BPBRYMDXXEWVZSRG51V/acceptance_tests/_shared.py`
  отсутствовал на диске на старте шага, хотя оба остальных файла пакета
  приёмочных тестов (`test_doctor_split_contract.py`,
  `test_doctor_split_structure.py`) импортируют из него фиксированные
  списки (`ALL_REQUIRED_FACADE_NAMES`, `SECTION_MARKERS`,
  `EXPECTED_CHECKS_IN_ORDER`, `FUNCTION_LOGIC_HASHES`) — без него
  локальный пакет приёмочных тестов не импортируется вовсе (`ImportError`
  на уровне сбора тестов, до любого содержательного ассерта). Проверено
  по `git log --all` — файла не было НИ В ОДНОЙ ревизии ни одной ветки;
  это не конфликт версий и не гонка параллельной сессии, а факт
  отсутствия. Не эскалировал: содержимое файла — не решение о дизайне
  кода задачи, а чисто механический, детерминированный вывод методики,
  УЖЕ описанной самой SPEC текстом («перечень снять `grep -rho
  "doctor\.[a-zA-Z_]*"`…», требование 1) и докстрингами уже существующих
  тестов пакета («сверено `grep` 06.09», «AST-дерево… снятое до
  переноса»); я как исполнитель этой методики не более субъективен, чем
  снял бы её `test_author` — правки уже написанных тестов (`test_doctor_
  split_contract.py`/`test_doctor_split_structure.py`) НЕ потребовалось,
  только добавление отсутствовавшей опорной фикстуры, на которую они уже
  ссылались. Значения `FUNCTION_LOGIC_HASHES`/`EXPECTED_CHECKS_IN_ORDER`
  сняты ДО переноса кода (проверочным прогоном на ещё не тронутом
  `doctor.py`) — я не мог подогнать их под получившийся у меня результат
  задним числом.
- Скрипт переноса — одноразовый инструмент этой задачи, не сохранён в
  репозитории (не часть решения, не тест, не CI-обвязка) — при следующем
  подобном разрезе (`fsm_advance.py`, `fsm.py`, `guard.py`, SPEC «Не
  входит») его придётся написать заново; сам приём (AST, а не regex по
  сырому тексту с кириллицей; UTF-8 байт-vs-символ ловушка `col_offset`)
  стоит учитывать сразу, а не переоткрывать.

## Предложения системе

- `scripts/codebase_map.py:discover_module_paths` — обходит только
  `orchestrator/*.py`/`scripts/*.py`/`tests/*.py` верхнего уровня
  (`dir_path.glob("*.py")`, без рекурсии); после этого разреза
  `orchestrator/doctor/` — первый пакет-подкаталог под `orchestrator/` —
  полностью выпал из `docs/codebase-map.md` (ни `__init__.py`, ни один
  из 17 файлов раздела не описаны, притом что раньше `doctor.py` имел
  свою секцию с назначением/публичными функциями/импортами). SPEC этой
  задачи прямо называет `fsm_advance.py`, `fsm.py`, `guard.py`
  следующими кандидатами на такой же разрез — каждый повторит эту же
  потерю видимости в карте, если генератор не научится обходить
  подкаталоги-пакеты. Вне зоны этой задачи (`scripts/` не входит в
  `zones:` SPEC) — не правил.
