# PLAN: Инкрементальный дифф ревью поздних итераций

## Подход

Сборка пакета (`orchestrator/review.py`) получает две новые величины —
номер итерации ревью и sha предыдущего вердикта — от вызывающего кода
(`orchestrator/runner.py`), а не вычисляет их сама: `runner.py` уже
знает `t["reviewed_iter"]` (номер последнего учтённого вердикта) и
имеет `conn` для чтения журнала.

- `iteration = t["reviewed_iter"] + 1` — то же значение, что уже сейчас
  идёт в текст миссии ревьювера (`iteration: {t['reviewed_iter'] + 1}`).
  `iteration == 1` — SPEC требование 1, без изменений в сборке.
- Sha предыдущего вердикта (требование 3) — из журнала hash-фиксации
  (T021): каждый переход FSM пишет ровно одну запись «sha зафиксирован»
  (`store._record_fixation`, вызывается из `store.set_state` на любом
  переходе). Между входом в `review` итерации N-1 и входом в `review`
  итерации N лежит ровно два перехода — `review -> in_dev` (вердикт
  `changes_requested`, фиксирует sha МОМЕНТА ВЕРДИКТА) и `in_dev ->
  review` (правка разработчика, фиксирует новый sha == текущий
  `fixed_sha`). Значит на момент сборки пакета итерации N искомый sha —
  предпоследняя по порядку запись «sha зафиксирован» в журнале задачи
  (последняя — текущий `fixed_sha`, тот, что уже дал старт этому шагу).
  Новая функция `review.previous_verdict_sha(conn, task_id)` читает
  `store.task_steps` и возвращает sha из detail предпоследней записи
  (парсинг тем же паттерном `sha=([0-9a-f]{4,40})`, что и у
  `store._record_fixation`, который его пишет). Меньше двух записей или
  sha не распознан (git не ответил в момент фиксации, вырожденный
  случай, уже существующий в T021) — пустая строка, и вызывающий код
  трактует это как «нечем сравнивать», откатываясь на полный diff —
  тот же приём деградации, что уже есть в `fixation.py` для `sha == ""`.

`review.review_package` получает `iteration` и `prev_sha` именованными
параметрами со значениями по умолчанию (`iteration=1, prev_sha=""`) —
существующие вызовы без них (тесты `test_review_package.py`) сохраняют
поведение итерации 1 без правок. Внутри пакета:

- `git_diff_part` меняет сигнатуру с `(branch, *flags)` на
  `(base, branch, *flags)` — база diff'а (`main` или `prev_sha`)
  становится параметром, а не константой `config.MAIN_BRANCH` внутри
  функции. Единственный вызывающий код — сам `review_package`, внешних
  контрактов нет.
- `incremental = iteration > 1 and bool(prev_sha)`; `base = prev_sha if
  incremental else config.MAIN_BRANCH`; `diff_type = "инкрементальный"
  if incremental else "полный"`.
- И стат-список, и diff строятся от одной и той же `base` — оба куска
  показывают один и тот же диапазон изменений, иначе заголовок
  «Изменённые файлы» и тело «Diff» расходились бы по смыслу.
- Потолки (`truncate_diff`, `truncate_package`) применяются к
  результату без изменений — они уже не знают, чей это diff (SPEC
  требования 6, 7).
- При `incremental` в пакет добавляется отдельный абзац с явной
  git-командой полного diff (`git diff main...branch`) — требование 5.
  Инструкция — не переключатель: она называет команду, но не выполняет
  и не автоматизирует запрос полного diff (SPEC, «Не входит»).
- `review_package` возвращает в словаре дополнительные поля
  `diff_type` и `iteration` (наряду с существующими `text`, `chars`,
  `bytes`, `diff_lines`, …).

`package_note` (журнал «ревью-пакет собран») дописывает тип diff и
номер итерации в конец строки размера, когда эти поля присутствуют в
пакете (`package.get("diff_type")`) — старые вызовы `package_note` с
вручную собранным словарём (без этих ключей, `test_review_package.py`)
не меняют поведения. Требования 7, 8 закрываются одной строкой заметки
без нового формата журнала.

`runner.cmd_run` в ветке `role == "reviewer"` считает `iteration =
t["reviewed_iter"] + 1` один раз (используется и в тексте миссии, и
как параметр пакета), достаёт `prev_sha` через
`review.previous_verdict_sha` только когда `iteration > 1` (пустая
строка иначе — не тратим чтение журнала на типичный случай первой
итерации), и передаёт оба значения в `review.review_package`.

Новый механизм учёта sha не заводится (SPEC, «Не входит») —
`fixation.py` не трогается вообще.

## Шаги

1. `orchestrator/review.py`: обобщить `git_diff_part` на параметр
   `base`; добавить `iteration`/`prev_sha` в `review_package` с расчётом
   `incremental`/`base`/`diff_type`, инструкцией полного diff и новыми
   полями в возвращаемом словаре; дописать `package_note`; добавить
   `previous_verdict_sha`.
2. `orchestrator/runner.py`: посчитать `iteration`, получить `prev_sha`
   при `iteration > 1`, передать оба значения в `review.review_package`.
3. Юнит-тесты `tests/test_review_package.py`: новые кейсы на
   `git_diff_part(base, branch, …)`, `review_package(iteration=2,
   prev_sha=...)` (diff/stat от `prev_sha`, инструкция полного diff,
   поля `diff_type`/`iteration`), `package_note` с новыми полями,
   `previous_verdict_sha` (меньше двух записей, sha не распознан,
   нормальный случай — на фейковом журнале через `store`).
4. Прогон `tasks/T029/acceptance_tests/test_incremental_diff.py` и
   всего пакета тестов (`python3 -m unittest discover -s tests`).

## Влияние на систему

Меняются только `orchestrator/review.py` (сигнатура `git_diff_part` —
внутренняя, единственный вызывающий код в том же модуле) и
`orchestrator/runner.py` (место вызова `review_package`). Публичный
контракт `review_package`/`package_note` расширяется обратно
совместимо (новые параметры и поля — не ломают существующие вызовы с
дефолтами). Ничего не ослабляется: потолки усечения, guard, приёмочные
тесты и hash-фиксация — как есть, T029 их не касается. Откат —
`git revert` коммита(ов) задачи: `runner.py` вернётся к вызову без
именованных параметров, `review.py` — к старой сигнатуре
`git_diff_part(branch, *flags)`.

## Риски

- Если между входом в `review` итерации N-1 и N произойдёт лишний
  переход FSM сверх обычной пары (например, эскалация ревьювера с
  последующим ручным возвратом Оператора в `in_dev`), «предпоследняя
  запись» перестанет быть sha именно предыдущего вердикта. SPEC не
  описывает этот сценарий отдельно и явно выводит изменение подсчёта
  итераций за рамки задачи; деградация при таком расхождении — более
  широкий, чем ожидалось, diff (не пустой и не падение), не порча
  пакета. Если это неприемлемо — уточнение у Оператора отдельной
  задачей.
