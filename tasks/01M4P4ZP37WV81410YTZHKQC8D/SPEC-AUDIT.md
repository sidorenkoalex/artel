## Пути обхода гейтов

- Е1. Предпроверка проверяет не то, что роль сдаёт. Каталог документов
  материализуется из головы ссылки на старте шага, а в ссылку правки роли
  попадают только автокоммитом после шага (artifact_branch.py:604–626;
  skills/conventions-core.md, «Артефакты»). `plank-run` по этой причине в
  `tests_writing` берёт черновик с диска каталога документов
  (orchestrator/plank_run.py:12–15). Требование 5 (SPEC.md:68–69) велит
  читать планку из ссылки. Тогда test_author в середине шага получит отказ
  трассируемости по старой (на первом визите — пустой) планке, хотя черновик
  полон, либо «пройден» по старой планке, хотя черновик сломан. На `in_dev`
  PLAN.md берётся с ссылки (fsm_advance.py:671–676), код — с головы
  `t["branch"]`; незакоммиченный код, который по конвенции коммитит пульт
  после шага, предпроверка не увидит (кроме довеска неотслеживаемых путей у
  гейта зон, zones.py:252–256). Переход это не обходит: на сдаче он проверит
  настоящее состояние. Но цель ТЗ при буквальном исполнении не достигается, а
  ложное «пройден» хуже отсутствия предпроверки. SPEC должен назвать
  источник каждого входа: черновик каталога документов (как `plank-run`) или
  ссылка; голова ветки или рабочая копия. И добавить AC «черновик в каталоге
  документов отличается от ссылки — предпроверка судит по черновику» (или
  явно противоположное, с решением Оператора).
- Е2. Запись в БД процессом роли. Если `_zones_gate` пометить в реестре
  исполняемым без условия (Б4), то у задачи с разделом «Расширение зон» и
  мандатом предпроверка из окружения роли выполнит
  `store.update_task(zones_extension=…)` (zones.py:297). Под Codex с БД
  `mode=ro` это исключение, под Claude — молчаливая запись состояния задачи
  ролью. Заглушки AC-12 `update_task` не запрещают, AC-2 сверяет «состояние
  задачи», а не колонки строки. Требование 16/AC-12 должно запрещать всякую
  запись `store.*` (`update_task`, `set_state`, `journal`) и
  `two_sided.run`/подтяжку main.
- Е3. Предпроверка — бесследный оракул гейтов: роль может перебирать правки
  (например, форму изменения теста против `_evaluate`), пока ядро не перестанет
  находить ослабление, и журнал не покажет попыток. ТЗ прямо требует «без
  журнала», логика гейтов и так открыта в коде, а двусторонний прогон и
  повторная сверка на мерже (`merge_gate_escalates`, test_integrity.py:1380)
  остаются. Это остаточный риск, не отклонение; Оператору — для сведения.
- Е4. Реестр, по которому идёт переход, может пропустить шаг, помеченный
  «не проверяется», если флаг реестра по ошибке управляет и переходом.
  Сторож требования 16 ловит «шаг перехода, которого нет в реестре», но не
  «шаг реестра, которого не исполнил переход». Отчасти это держат
  поведенческие тесты гейтов. Стоит добавить к сторожу обратное направление.

**fail** — второй возврат аналитику (первый — по SPEC 08ce83ec…). SPEC
выполним буквально, но предпроверка в нём судит по ссылке документов и голове
ветки, то есть по состоянию до шага роли. Цель ТЗ «узнать об отказе до сдачи»

закреплённый тестом порядок подключения гейта неослабления, и SPEC этого не
