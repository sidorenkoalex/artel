# SPEC: ADR-0014, часть 1 — потолок ролей и обязательный budget_usd в SPEC

## Контекст

`config.DEFAULT_BUDGET_USD = 50` сегодня одновременно и дефолт задачи
без оценки, и единственная верхняя граница для `budget_usd` из SPEC
(`budget.spec_budget`: значение выше константы отвергается,
инвариант 10). Поле `budget_usd` в SPEC необязательное
(`templates/SPEC.md`, `scripts/guard.py` его не требует).

Оператор принял ADR-0014 (`docs/adr/0014-budget-default-and-role-cap.md`,
05.09): дефолт остаётся $50, но появляется отдельный потолок ролей $100,
`budget_usd` в SPEC становится обязательным и применяется потолком в
обе стороны в его пределах. Родительская задача
01M1SHDCW7FGJPTMD0FSFWGZ5S разделена Оператором на гейте SPEC на две
части (решение 06.09); эта задача — часть 1: потолок ролей и обязательное
поле `budget_usd` в SPEC. Часть 2 (однократная переоценка `budget_usd`
на PLAN) — отдельная задача, идёт второй, опирается на `ROLE_BUDGET_CAP`
и guard-проверку потолка ролей этой части.

При расхождении этого SPEC и ADR-0014 нормативен ADR.

## Требования

1. `orchestrator/config.py`: `DEFAULT_BUDGET_USD` остаётся 50. Новая
   константа `ROLE_BUDGET_CAP = 100.0` с комментарием-ссылкой на
   ADR-0014 — верхняя граница потолка, который вправе выставить роли
   без участия Оператора.

2. `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION` поднимается до
   следующего значения (5), тем же приёмом version-gating, что уже
   несут `requires_ac_markup`/`requires_registry`/
   `requires_split_assessment`/`requires_zones`: новое правило не должно
   задним числом ловить уже открытые задачи текущей версии 4. Новая
   проверка отказывает SPEC (`type: spec`) с `schema_version >= 5` без
   поля `budget_usd` или со значением, не разбираемым как число тем же
   разбором, что и сегодня (`budget.spec_budget`/`spend.cli_number`);
   SPEC с `schema_version < 5` этим правилом не проверяется.

3. `scripts/guard.py`, независимо от `schema_version` (проверка значения
   уже существующего необязательного поля, не факта его присутствия):
   SPEC ИЛИ PLAN с `budget_usd`, разобранным как число выше
   `ROLE_BUDGET_CAP`, — отказ guard (не тихое усечение) с подсказкой
   поделить задачу (оценка объёма, 01M1KS8K9RXWHX2PW3ZKB0P903) либо
   эскалировать вопрос бюджета Оператору.

4. `budget.spec_budget`/`budget.apply_spec_budget`: на переходе
   `spec_writing -> spec_gate` значение из SPEC применяется потолком
   задачи в обе стороны (и выше, и ниже сегодняшнего дефолта) при
   условии `0 < value <= ROLE_BUDGET_CAP` (сравнение с `ROLE_BUDGET_CAP`
   заменяет сегодняшнее сравнение с `DEFAULT_BUDGET_USD`). Потолок с
   `budget_source = operator` значением из SPEC не перебивается — как
   сегодня.

5. Справка `orchestrator/artel.py` (абзац о применении `budget_usd` из
   SPEC) переписывается под новую семантику: потолок применяется в обе
   стороны в пределах потолка ролей, а не только понижается от дефолта.

6. Исчерпание потолка, эскалация «бюджет исчерпан», команда `budget`,
   стоп-лосс программы (`PROGRAM_STOP_LOSS_USD`, ADR-0010) — без
   изменений; ни один существующий тест на них не ослабляется.

7. `docs/invariants.md`, инвариант 10, переформулируется (SPEC-часть
   новой формулировки, без упоминания PLAN — переоценка на PLAN не
   входит в эту задачу): «поднять потолок выше `ROLE_BUDGET_CAP` может
   только Оператор командой `budget`; в пределах потолка ролей потолок
   задаёт SPEC на гейте SPEC». `tests/test_invariants.py` дополняется:
   SPEC со значением выше `ROLE_BUDGET_CAP` потолок не поднимает (отказ
   guard); потолок Оператора не перебивается значением из SPEC.

8. `config.SPLIT_SIGNAL_BUDGET_USD` (сегодня $30, порог сигнала
   «подозрение на большой объём» в `scripts/guard.py`) пересчитывается
   так, чтобы типовая задача по новой калибровке сигнал не поднимала, а
   класс «>10 критериев приёмки или ≥5 файлов зоны» — по-прежнему
   поднимал: новое значение строго больше $45 и не больше $70.
   Именованная константа `config` с комментарием-обоснованием.

9. Приложением к PLAN.md (защищённые пути, применяет Оператор,
   `git apply --check` на чистом дереве перед сдачей):
   - unified-диф `templates/SPEC.md` (комментарий поля `budget_usd` по
     новой семантике требования 4), плюс синхронный подъём
     `schema_version: 4 -> 5` во всех четырёх шаблонах, которые сегодня
     разделяют это число (`SPEC.md`, `PLAN.md`, `REVIEW.md`,
     `TEST_REPORT.md`) — тем же приёмом, каким версия 4 поднималась во
     всех четырёх сразу задачей 01M1NKVPD2A79PQ6K0JVV1B2Q1 (иначе поле
     `budget_usd` требования 2 не станет обязательным ни для одной новой
     задачи: гейт version >= 5 не увидит версии, которую никто не
     пишет); поле `budget_usd` во frontmatter `templates/PLAN.md` тем же
     подъёмом версии добавляется, но само поле функционально потребляет
     часть 2 (эта задача его не читает);
   - unified-диф `skills/spec-authoring.md`: калибровка по ADR-0014 п.7
     (до 5 критериев и до 3 файлов зоны ~$35, 6–10 критериев ~$45,
     больше 10 критериев или 5 и более файлов ~$70 либо деление; планка
     — не ниже $25; поле `budget_usd` обязательно).

10. Тесты: guard отказывает SPEC (`schema_version >= 5`) без поля
    `budget_usd`; SPEC `budget_usd: 80` на гейте SPEC даёт потолок $80
    (`budget_source = spec`); SPEC `budget_usd: 120` — отказ guard;
    потолок Оператора $60 не перебивается значением из SPEC.
    Существующие `tests/test_spec_budget.py`, `tests/test_step_cost.py`,
    `tests/test_invariants.py` остаются зелёными без ослабления
    ассертов — включая пересмотр тестов, зафиксировавших старую
    семантику «выше дефолта — отказ», на новую «выше `ROLE_BUDGET_CAP`
    — отказ».

## Критерии приёмки

AC-1. `orchestrator/config.py` несёт `ROLE_BUDGET_CAP = 100.0` с
комментарием-ссылкой на ADR-0014; `DEFAULT_BUDGET_USD` остаётся 50.

AC-2. `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION` поднят до 5. Новая
проверка отказывает SPEC (`type: spec`) с `schema_version >= 5` без
поля `budget_usd` или со значением, которое не разбирается как число;
SPEC с `schema_version < 5` (весь сегодняшний беклог, включая уже
открытые задачи версии 4) этой проверкой не затрагивается.

AC-3. `scripts/guard.py` отказывает SPEC или PLAN, чей `budget_usd`
разбирается как число выше `ROLE_BUDGET_CAP`, независимо от
`schema_version`, с подсказкой поделить задачу
(01M1KS8K9RXWHX2PW3ZKB0P903) либо эскалировать вопрос бюджета
Оператору.

AC-4. `budget.spec_budget`/`budget.apply_spec_budget`: на переходе
`spec_writing -> spec_gate` значение SPEC применяется потолком задачи и
выше, и ниже сегодняшнего дефолта, при `0 < value <= ROLE_BUDGET_CAP`;
потолок с `budget_source = operator` значением из SPEC не перебивается.

AC-5. Абзац о бюджете из SPEC в справке `orchestrator/artel.py`
переписан под новую семантику (обе стороны, потолок ролей, не только
понижение от дефолта).

AC-6. Исчерпание потолка, эскалация «бюджет исчерпан», команда
`budget`, стоп-лосс программы (`PROGRAM_STOP_LOSS_USD`) — поведение и
существующие тесты не изменены и не ослаблены.

AC-7. `docs/invariants.md`, инвариант 10, переформулирован (SPEC-часть):
«поднять потолок выше `ROLE_BUDGET_CAP` может только Оператор командой
`budget`; в пределах потолка ролей потолок задаёт SPEC на гейте SPEC».

AC-8. `tests/test_invariants.py` дополнен: SPEC со значением выше
`ROLE_BUDGET_CAP` потолок не поднимает (отказ guard); потолок Оператора
не перебивается значением из SPEC.

AC-9. `config.SPLIT_SIGNAL_BUDGET_USD` пересчитан значением строго
больше $45 и не больше $70 (именованная константа с комментарием) —
SPEC с `budget_usd: 45` сигнал «подозрение на большой объём» не
поднимает, SPEC с `budget_usd: 70` — поднимает.

AC-10. Тесты в `tests/`: guard отказывает SPEC (`schema_version >= 5`)
без `budget_usd`; SPEC `budget_usd: 80` на гейте SPEC даёт потолок $80
(`budget_source = spec`); SPEC `budget_usd: 120` — отказ guard; потолок
$60, выставленный командой `budget`, не перебивается значением из SPEC.
Существующие `tests/test_spec_budget.py`, `tests/test_step_cost.py`,
`tests/test_invariants.py` остаются зелёными без ослабления ассертов —
включая пересмотр тестов, зафиксировавших старую семантику «выше
дефолта — отказ», на новую «выше `ROLE_BUDGET_CAP` — отказ».

AC-11. Приложением к PLAN.md (защищённые пути, применяет Оператор,
каждый диф проверен `git apply --check` на чистом дереве перед сдачей):
unified-диф `templates/SPEC.md` (новая семантика поля `budget_usd`) с
синхронным подъёмом `schema_version: 4 -> 5` во всех четырёх шаблонах,
разделяющих это число (`SPEC.md`, `PLAN.md`, `REVIEW.md`,
`TEST_REPORT.md`, с добавлением поля `budget_usd` во frontmatter
`templates/PLAN.md`); unified-диф `skills/spec-authoring.md`
(калибровка ADR-0014 п.7: до 5 AC и 3 файлов ~$35, 6–10 AC ~$45, >10 AC
или ≥5 файлов ~$70 либо деление, планка не ниже $25, поле обязательно).

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (6:
`orchestrator/config.py`, `scripts/guard.py`, `orchestrator/budget.py`,
`orchestrator/artel.py`, `docs/invariants.md`, `tests/` — порог 5);
затронут инвариантный механизм (`scripts/guard.py`/`docs/
invariants.md`, инвариант 10).

Деление уже утверждено Оператором на гейте SPEC родительской задачи
01M1SHDCW7FGJPTMD0FSFWGZ5S (решение 06.09): нарезка на 2 части по
границам зависимости, эта задача — часть 1, идёт первой (вводит
`ROLE_BUDGET_CAP` и общую для SPEC и PLAN guard-проверку потолка
ролей, на которую опирается часть 2). Самостоятельно мержима с зелёной
планкой: после мержа система уже требует и применяет `budget_usd` из
SPEC в обе стороны в пределах $100, поведение PLAN не меняется вовсе
(остаётся как сегодня) — рабочее состояние без полуготовых кусков.
Повторного деления эта часть не требует; дальнейшая нарезка не нужна —
рамка $40 (см. ТЗ) укладывается в самостоятельно мержимый объём.

## Не входит

- Однократная переоценка `budget_usd` на PLAN (часть 2, отдельная
  задача).
- Автоматический подъём потолка при исчерпании.
- Изменение стоп-лосса программы (`PROGRAM_STOP_LOSS_USD`, ADR-0010).
- Прямая правка `templates/SPEC.md`, `templates/PLAN.md`,
  `templates/REVIEW.md`, `templates/TEST_REPORT.md`,
  `skills/spec-authoring.md` — только unified-диф приложением к
  PLAN.md, применяет Оператор.
