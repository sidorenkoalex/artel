# SPEC: бриф роли называет артефакты путём от рабочего каталога роли, не от корня пульта

## Контекст
Два инцидента 05.09 (ревьюверы стека ч.3 и стека ч.2): роль получает
путь артефакта, вычисленный от корня пульта (`config.TASKS / task_id /
rel`, `orchestrator/brief.py:466`), пытается записать REVIEW.md
инструментом Write вне своего рабочего каталога (worktree задачи) —
режим `acceptEdits` требует подтверждения, headless-шаг его не получает,
роль завершает шаг без артефакта. Оркестратор при этом журналирует шаг
как `agent run finished` (rc=0) — успех, хотя REVIEW.md не появился;
цикл ретраев (`runner._cmd_run`) повторяет попытку только при исходе
`failed`, поэтому ложный «успех» съедает попытку и бюджет впустую, а
проблему обнаруживает только более поздний гейт `advance`.

`orchestrator/runner.py` пересекается с кодом стека ч.3 (в ревью на
момент написания этого SPEC): правка `runner.py` в рамках этой задачи
ждёт мержа ч.3, чтобы не множить конфликт — SPEC и приёмочная планка
пишутся сейчас, реализация (`developer`) стартует после мержа ч.3.

## Требования
1. Все пути к артефактам задачи в брифе и в подсказках ролям (SPEC.md,
   PLAN.md, REVIEW.md, ANSWER-*.md, acceptance_tests/) — относительные
   к рабочему каталогу роли (`runner.role_cwd`), вида `tasks/<id>/...`;
   абсолютные пути от `config.ROOT`/`config.TASKS` в тексте брифа не
   встречаются.
2. Промпт каждой из ролей analyst, test_author, developer, reviewer
   несёт явную строку: «рабочий каталог шага — <абсолютный путь
   worktree>; все пути ниже относительно него; запись вне него
   недоступна» — с фактическим значением `runner.role_cwd` этого шага.
3. Роль, у которой артефакт — обязательный выход шага (reviewer —
   REVIEW.md, analyst — SPEC.md/QUESTIONS.md, developer — PLAN.md,
   test_author — acceptance_tests/), завершает шаг с rc=0, но нужный
   файл/каталог в рабочем каталоге роли по завершении отсутствует —
   получает журнальную запись «шаг завершён без артефакта <имя>» и
   итоговый статус шага `failed` (не `agent run finished`/`ok`), чтобы
   цикл ретраев (`runner._cmd_run`) не считал шаг успешным.
4. Штатный случай (нужный файл/каталог на месте) не регрессирует:
   успешный шаг с артефактом на диске по-прежнему журналируется как
   `agent run finished`/`ok`.

## Критерии приёмки

AC-1. Промпт (миссия + бриф) каждой из ролей analyst, test_author,
developer, reviewer не содержит `str(config.ROOT)` и `str(config.TASKS)`
— все упоминания SPEC.md, PLAN.md, REVIEW.md, ANSWER-*.md,
acceptance_tests/ этой задачи даны путём вида `tasks/<id>/...`,
относительным к рабочему каталогу роли.

AC-2. Промпт каждой из ролей analyst, test_author, developer, reviewer
содержит строку «рабочий каталог шага — <абсолютный путь>; все пути
ниже относительно него; запись вне него недоступна», где
`<абсолютный путь>` совпадает со значением, которое для этого шага
вернул `runner.role_cwd`.

AC-3. Шаг роли reviewer завершается с rc=0, но `REVIEW.md` отсутствует
в рабочем каталоге роли — в журнал задачи пишется запись «шаг завершён
без артефакта REVIEW.md», итоговый статус шага — `failed`.

AC-4. Шаг роли analyst завершается с rc=0, но ни `SPEC.md`, ни
`QUESTIONS.md` не появились в рабочем каталоге роли — в журнал задачи
пишется запись «шаг завершён без артефакта SPEC.md/QUESTIONS.md»,
итоговый статус шага — `failed`.

AC-5. Шаг роли developer завершается с rc=0, но `PLAN.md` отсутствует
в рабочем каталоге роли — в журнал задачи пишется запись «шаг завершён
без артефакта PLAN.md», итоговый статус шага — `failed`.

AC-6. Шаг роли test_author завершается с rc=0, но каталог
`acceptance_tests/` отсутствует в рабочем каталоге роли — в журнал
задачи пишется запись «шаг завершён без артефакта acceptance_tests/»,
итоговый статус шага — `failed`.

AC-7. Шаг любой из четырёх ролей завершается с rc=0, и нужный
файл/каталог присутствует в рабочем каталоге роли — исход и журнальная
запись прежние (`agent run finished`, статус `ok`), новая проверка не
меняет штатный путь.

AC-8. Существующий набор тестов, покрывающий бриф и промпт роли
(`tests/test_brief.py`, `tests/test_agent_prompt.py` и смежные), остаётся
зелёным после правки.

## Не входит

- Смена режима прав CLI (`--permission-mode`).
- Расширение `allowedTools`.
- Реализация правки `runner.py` до мержа стека ч.3 (см. «Контекст») —
  сама зависимость по срокам не критерий приёмки, а операционное
  ограничение на порядок работы.
