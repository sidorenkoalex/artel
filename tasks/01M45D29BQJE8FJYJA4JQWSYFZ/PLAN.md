# PLAN: new разбирает «Порядок: после …» ТЗ и заявляет merge_after до аналитика

## Подход

Вариант «б» SPEC: заявленное значение пишется при `new` сразу в колонку
`tasks.merge_after`; гейт SPEC сверяет поле SPEC с колонкой ДО её
перезаписи. Вся механика — в `orchestrator/merge_after.py`, вызыватели
(`catalog.cmd_new`, `fsm._approve_spec_gate`) только зовут её узлы.

- **Разбор строки** — `merge_after.declared_from_tz(conn, tz_raw, target)`:
  `^Порядок:[ \t]+после(?!\w)` с первой позиции; хвост режется на первой
  «(» или «.»; элементы — `guard.merge_after_items`; проверка —
  `merge_after.check(conn, None, items, target=target)`. Две и более
  строки — отказ «повторена»; строка без id — отказ (не молчаливое
  «зависимостей нет»).
- **`check` для незаведённой задачи** — новый keyword-only `target`:
  если передан, target заводимой задачи берётся из него, а не из строки
  БД (`store.task_target` для отсутствующей строки молча дал бы target по
  умолчанию). `task_id=None` — форма проверяется без «id самой задачи»,
  цикл замкнуться не может (новый id никто не называет), обход графа на
  `None` ничего не находит. Правила проверки не копируются.
- **`cmd_new`** — `target` вычисляется до ветки ТЗ; разбор идёт тем же
  рубежом, что `_tz_path_refusal` (до клона, id, ссылки документов, ветки,
  строки БД); причины сверки путей и строки «Порядок:» склеиваются в один
  `sys.exit` с хвостом «задача не заведена». Текст отказа только по путям
  не меняется. Канарейка (`canary=True`) строку не разбирает. После
  заведения строки — `merge_after.record_declared`: колонка + журнал
  «merge_after заявлен Оператором» с полными id. `spawn_subtask` не
  тронут.
- **Гейт SPEC** — `merge_after.spec_gate_declared_refusal(conn, task_id,
  t, meta, new_value, spec_text)` после `spec_gate_value` и до
  `update_task`: сверка действует, только если колонка непуста И задача
  ещё ни разу не проходила гейт SPEC (в журнале нет `state ->
  tests_writing`/`state -> in_dev`). Второе условие нужно, потому что
  существующий `tests/test_01m44ep0d47f498tee08mngbyt_status_show_merge_after.py::
  test_ac14_show_lists_all_dependencies_with_states` проводит задачу
  через гейт SPEC дважды с разными значениями: без него второй approve
  счёл бы рабочее значение заявленным и отказал по «добавке». Потеря —
  отказ с полными id и обоими каналами снятия (мандат в ANSWER через
  `artel.py answer`, эскалация аналитика). Добавка — принимается, только
  если раздел `## Обоснование зависимостей мержа` называет её полным id
  или элементом поля словом целиком (короткий префикс внутри чужого id
  не засчитывается). Принятая добавка — отдельная запись журнала
  «merge_after: добавлено аналитиком» после записи колонки. На дисковом
  пути `_approve_spec_gate` (`spec_text == ""`) текст для раздела
  обоснования читается отдельно (`fsm._disk_spec_text`), чтобы не
  включать там сверку путей и деление, которых сегодня нет.
- **Мандат до гейта SPEC** (п. 7) — без нового кода: `answer` в
  `escalated` уже пишет колонку `merge_after.rewrite`, а колонка и есть
  заявленное значение.
- **`status`** — `status_suffix` в `spec_writing`/`spec_gate` печатает
  `[мерж после: <id> (<состояние>), …]` для зависимостей не в `done`;
  `[ждёт мержа: …]` в `acceptance`/`merge_gate` и пустая добавка в прочих
  состояниях не меняются. `show` уже печатает `show_line` в любом
  состоянии.
- **Карта** — первая строка docstring `merge_after.py` (строка
  «Назначение» карты) называет «Порядок: после», заявленное значение в
  колонке, сверку на гейте SPEC и добавку `status`; карта регенерирована.

Бюджет SPEC ($25) не переоценивается: три модуля кода и один файл
юнит-тестов, как SPEC и предполагал.

## Влияние на систему

- **Гейт SPEC** получает новый мягкий отказ, срабатывающий только у
  задач с непустой колонкой `merge_after` до первого прохода гейта —
  сегодня таких нет (колонку до гейта писал лишь мандат в `escalated`),
  задачи без заявленного проходят как раньше (AC-13; существующие тесты
  `test_01m44ep0d47f498tee08mngbyt_spec_gate_merge_after.py` зелёные).
  Существующие проверки (`spec_gate_value`, сверка путей) не тронуты и
  идут раньше.
- **`new`**: новый отказ только при строке «Порядок: после …» с первой
  позиции; исторические строки «Порядок: без зависимостей»/«первая, без
  зависимостей» его не вызывают. Текст отказа только по путям не изменён.
  Заявленные рёбра раньше участвуют в проверке циклов `check` у других
  задач — это исправление (ТЗ, «Факты»).
- **`status`**: новая добавка только в `spec_writing`/`spec_gate`;
  `[ждёт мержа:` не меняется (`test_ac13_no_suffix_in_other_state`
  зелёный — он проверяет только `[ждёт мержа:`).
- Гейт мержа, канал PLAN, мандат — без изменений правил; читают ту же
  колонку.
- Тесты не ослаблены, существующие методы не менялись.
- Откат — revert коммита задачи; схема БД не менялась.

## Риски

- Признак «гейт SPEC уже пройден» читается по журналу переходов `state ->
  tests_writing`/`state -> in_dev`. Задача, переведённая в эти состояния
  мимо `set_state` (правкой БД руками), будет считаться не прошедшей
  гейт — для неё сверка с колонкой на повторном `spec_gate` возможна.
  Штатного пути туда нет.
- Добавка аналитика сравнивается по полным id после разрешения: если
  заявленная задача и добавка — одна и та же задача под разными
  префиксами, это не добавка (так и задумано).
