# SPEC: new разбирает «Порядок: после …» ТЗ и заявляет merge_after до аналитика

## Контекст

Зависимость мержа, названная Оператором в ТЗ строкой «Порядок: после …»,
сегодня доходит до пульта только пересказом аналитика в поле `merge_after`
SPEC. Потеря зависимости молча проходит гейт SPEC: `approve` на `spec_gate`
(`orchestrator/fsm.py::_approve_spec_gate`) перезаписывает колонку
`tasks.merge_after` значением SPEC, а SPEC без поля стирает её. Ошибка в id
всплывает только на гейте SPEC — после оплаченного шага аналитика. Задача
переносит разбор строки и проверку id в `new --tz` (до заведения задачи),
хранит заявленное Оператором значение с самого `new` и заставляет гейт SPEC
сверять SPEC с заявленным.

Принятые этим SPEC решения по пунктам, которые ТЗ оставило SPEC:
- **Хранение — вариант «б»** ТЗ: заявленное значение пишется сразу в
  существующую колонку `tasks.merge_after` (образец
  `catalog._record_preliminary_zones`), отдельной колонки нет. До первого
  `approve` на `spec_gate` колонку пишут только `new` и мандат Оператора
  «Зависимости мержа: …» в `escalated` (канал PLAN действует лишь на
  `in_dev -> verifying`, `reject` на `spec_gate` колонок не пишет) — значит,
  до этого `approve` колонка и есть заявленное значение, и сверка на гейте
  читает её до перезаписи. Повторный проход `spec_writing -> spec_gate` после
  `reject` сверяется с тем же заявленным значением: `reject` его не трогает.
  «Добавлено аналитиком» — элементы поля SPEC, которых нет в колонке до
  перезаписи.
- **Несколько строк «Порядок: после …»** в одном ТЗ — отказ `new`, не
  объединение: значение задаёт одна строка (тот же приём, что
  `merge_after.lines_refusal` у мандата).
- **Сверка на переходе `spec_writing -> spec_gate` не дублируется** —
  потерю ловит `approve` на `spec_gate`, возврат аналитику — штатным
  `reject`.
- **Требование обоснования добавки** действует, только когда заявленное
  значение непусто: задача без заявленных зависимостей (ТЗ без строки,
  без ТЗ, подзадача деления, канарейка, заявленное снято мандатом «нет»)
  ведёт себя на гейте SPEC как сегодня (п. 7 ТЗ; иначе меняются ожидания
  существующего `tests/test_01m44ep0d47f498tee08mngbyt_spec_gate_merge_after.py::
  test_ac5_prefixes_written_as_full_ids_in_spec_order`, который п. 9 ТЗ
  запрещает менять).

## Требования

1. **Разбор строки при `new --tz`.** Строка ТЗ, которая начинается (с
   первой позиции, без отступа) с «Порядок:», затем пробелы и слово
   «после», заявляет зависимости мержа. Хвост после слова «после» — перечень
   элементов через запятую; перечень кончается на первом из: конец строки,
   открывающая круглая скобка «(», точка «.» — всё с этого места и
   следующие строки в перечень не входят. Перечень разбирается тем же
   узлом, что поле `merge_after` (`guard.merge_after_items` и проверка
   формы `guard.merge_after_form_errors`). Строка «Порядок:», за меткой
   которой не стоит слово «после» (например «без зависимостей», «первая,
   без зависимостей»), зависимостей не заявляет. Элемент хвоста, не
   являющийся id задачи по форме, — отказ `new` с названием элемента.
   Две и более строки «Порядок: после …» в одном ТЗ — отказ `new`
   («строка «Порядок: после» повторена»).
2. **Проверка до заведения.** Тем же рубежом, что `_tz_path_refusal`
   (`orchestrator/catalog.py::cmd_new`, до клона, id, ссылки документов,
   ветки и строки БД), каждая заявленная зависимость проходит проверку
   `orchestrator/merge_after.py::check`: задача существует, префикс
   однозначен, не `killed`, тот же target, что у заводимой задачи (target
   аргумента `new`, без него — `config.DEFAULT_TARGET`), нет повтора и
   цикла. `check` получает target заводимой задачи явно, не из её строки
   БД (строки ещё нет), и вызывается без id ещё не заведённой задачи —
   правила проверки не копируются в `orchestrator/catalog.py`. Любая
   причина — отказ `new` с элементом и причиной и словами «задача не
   заведена», без следов в БД и git. Если ТЗ не прошло и сверку путей,
   оба отказа печатаются одним вызовом `new`.
3. **Запись заявленного.** Прошедшее значение (полные id в порядке
   строки ТЗ) пишется тем же вызовом `new` в колонку `tasks.merge_after`,
   и журнал задачи получает запись с действием «merge_after заявлен
   Оператором» и полными id в деталях.
4. **`status`/`show` с самого `new`.** В состояниях `spec_writing` и
   `spec_gate` строка задачи в `status` несёт добавку
   `[мерж после: <id> (<состояние>), …]` — зависимости из колонки, ещё не
   в `done`, состояние читается из БД на каждый вызов; все в `done` (или
   колонка пуста) — добавки нет. Добавка `[ждёт мержа: …]` в
   `acceptance`/`merge_gate` и отсутствие её в прочих состояниях не
   меняются. `show <id>` печатает строку зависимостей мержа сразу после
   `new`.
5. **Сверка на гейте SPEC.** `approve` на `spec_gate` до записи колонок
   `zones`/`merge_after` сверяет поле `merge_after` SPEC (полные id после
   разрешения префиксов) с заявленным значением (колонка до перезаписи).
   Отсутствие в SPEC хоть одной заявленной зависимости, в том числе SPEC
   без поля при непустом заявленном, — мягкий отказ тем же способом, что
   нынешние отказы `merge_after` (журнал «approve отклонён», задача на
   `spec_gate`, колонки не пишутся); причина называет полный id каждой
   потерянной зависимости и каналы снятия: мандат Оператора «Зависимости
   мержа: …» в ANSWER (`artel.py answer`) либо эскалация аналитика.
6. **Добавка аналитика.** При непустом заявленном значении элемент поля
   `merge_after` SPEC, которого нет среди заявленных, принимается, только
   если раздел SPEC `## Обоснование зависимостей мержа` называет его (полным
   id либо тем же элементом, что стоит в поле). Добавка без обоснования —
   мягкий отказ гейта SPEC тем же способом, что в п. 5, с полным id
   добавленной зависимости. Принятая добавка проходит проверки п. 2
   (нынешний `merge_after.spec_gate_value`), и журнал задачи получает
   отдельную запись «добавлено аналитиком: <полные id>».
7. **Мандат до гейта SPEC.** Мандат «Зависимости мержа: …», принятый
   `answer` в `escalated` до первого `approve` на `spec_gate`, меняет
   заявленное значение (колонку) — сверка п. 5–6 идёт уже с новым
   значением; «Зависимости мержа: нет» делает заявленное пустым.
8. **Прочее — как сегодня.** После гейта SPEC значение меняют только
   прежние каналы (PLAN, мандат в ANSWER) без изменения их правил;
   `merge_gate_refuses` и гейт мержа читают ту же колонку. Задача без
   строки «Порядок: после …» в ТЗ, задача без ТЗ, подзадача деления
   (`catalog.spawn_subtask`) и задача канарейки (`cmd_new(..., canary=True)`,
   `orchestrator/canary_drive.py`) строку не разбирают и ведут себя как
   сегодня: колонка `merge_after` после заведения пуста, записи журнала
   о заявлении нет, гейт SPEC — без сверки п. 5–6.
9. **Карта.** `docs/codebase-map.md` (регенерация
   `scripts/codebase_map.py` из docstring модулей) в строке «Назначение»
   `orchestrator/merge_after.py` называет заявление зависимостей при `new`
   строкой «Порядок: после», хранение заявленного в колонке `merge_after`,
   сверку с заявленным на гейте SPEC и добавку `status` до `acceptance`.
10. **Приложение PLAN.** PLAN несёт приложение-диф к
    `skills/spec-authoring.md`: зависимости, заявленные Оператором строкой
    «Порядок: после …», переносятся в поле `merge_after` все без
    исключения; снять заявленную может только Оператор (эскалация с
    вопросом); своя добавка — только с обоснованием в разделе
    `## Обоснование зависимостей мержа`. И приложение-диф к
    `templates/SPEC.md`: закомментированное пояснение поля `merge_after`
    дополнено тем же правилом. Оба дифа применяются `git apply --check`.
11. Покрытие п. 9 ТЗ (тесты с заявками «Ловит мутацию» на пп. 1–7) несут
    долгоживущие приёмочные тесты автора тестов в `tests/` по критериям
    ниже; отдельный повтор тех же свойств в `tests/` не требуется.

## Критерии приёмки

AC-1. `new --tz` с ТЗ, несущим строку «Порядок: после <e1>, <e2>» (элементы —
полные id или однозначные префиксы существующих живых задач того же
target), заводит задачу; колонка `merge_after` — полные id в порядке
строки; журнал задачи несёт запись «merge_after заявлен Оператором» с этими
полными id. Строка с одним id — так же, одним id.

AC-2. Конец перечня: строка «Порядок: после <e1>, <e2> (пояснение).» с
продолжением текста на следующей строке заявляет ровно `<e1>, <e2>`; то же
для хвоста, оборванного точкой без скобок.

AC-3. ТЗ со строкой «Порядок: без зависимостей» (или «Порядок: первая, без
зависимостей») и ТЗ без строки «Порядок:» — задача заводится, колонка
`merge_after` пуста, записи «merge_after заявлен Оператором» нет.

AC-4. Строка «Порядок: после …», хвост которой содержит элемент, не
являющийся id по форме (например «после мержа «CI до ревью»»), — отказ
`new`, вывод называет неразобранный элемент и «задача не заведена»; в БД
нет новой строки задачи, нет ссылки документов и ветки задачи.

AC-5. ТЗ с двумя строками «Порядок: после …» — отказ `new` с причиной
повтора строки, без следов в БД и git.

AC-6. Заявленная зависимость — несуществующий id, неоднозначный префикс,
задача в `killed`, задача другого target или повтор одной задачи — отказ
`new`, вывод называет элемент и причину и «задача не заведена»; новой
строки задачи в БД, ссылки документов и ветки нет.

AC-7. ТЗ, которое не проходит сверку путей и одновременно несёт негодную
строку «Порядок: после …», — один вызов `new` печатает обе причины отказа.

AC-8. Сразу после `new` с заявленной незавершённой зависимостью `status` в
`spec_writing` и в `spec_gate` печатает в строке задачи
`[мерж после: <id> (<состояние>)]` и не печатает `[ждёт мержа:`; после
перевода зависимости в `done` добавки нет; `show <id>` сразу после `new`
печатает строку зависимостей мержа с этим id.

AC-9. Задача с заявленными зависимостями на `spec_gate`: SPEC, в поле
`merge_after` которого нет одной из заявленных (или SPEC без поля), —
`approve` мягко отказывает: задача на `spec_gate`, колонка `merge_after`
равна заявленному значению, журнал «approve отклонён» называет полный id
каждой потерянной зависимости и канал снятия (мандат в ANSWER либо
эскалация аналитика).

AC-10. SPEC, поле которого содержит все заявленные (полными id или
префиксами, в любом порядке), — `approve` проходит и пишет значение SPEC в
колонку. SPEC с добавочной зависимостью, названной в разделе
`## Обоснование зависимостей мержа`, — `approve` проходит, журнал несёт
запись «добавлено аналитиком: <полный id>». Та же добавка без упоминания в
этом разделе — мягкий отказ, причина называет полный id добавки.

AC-11. После `reject` на `spec_gate` и повторного прохода
`spec_writing -> spec_gate` колонка `merge_after` по-прежнему равна
заявленному, и `approve` сверяет SPEC с ним так же, как в AC-9/AC-10.

AC-12. Задача с заявленными зависимостями, эскалированная из
`spec_writing`: `answer` с мандатом «Зависимости мержа: <X>» в `escalated`
меняет колонку на X; на гейте SPEC SPEC с `merge_after: X` без прежних
заявленных проходит без обоснования, SPEC без X — отказ по п. 5. Мандат
«Зависимости мержа: нет» — SPEC без поля проходит.

AC-13. Задача без заявленных зависимостей (ТЗ без строки, без ТЗ, подзадача
деления, канарейка `cmd_new(..., canary=True)` с ТЗ, несущим строку
«Порядок: после …») после заведения имеет пустую колонку `merge_after` и
без записи о заявлении; её `approve` на `spec_gate` с SPEC, несущим
`merge_after` без раздела обоснования, проходит и пишет значение SPEC,
как сегодня.

AC-14. В `docs/codebase-map.md`, регенерированном `scripts/codebase_map.py`,
строка «Назначение» `orchestrator/merge_after.py` упоминает «Порядок: после»,
заявленное значение, гейт SPEC и `status`.

AC-15. PLAN.md несёт приложения-дифы к `skills/spec-authoring.md` и
`templates/SPEC.md`, каждое проходит `git apply --check` на дереве
`main`; добавленный текст скила содержит правило «все без исключения»,
«снять может только Оператор» и название раздела
`## Обоснование зависимостей мержа`.

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов (упомянуты
`orchestrator/catalog.py`, `orchestrator/merge_after.py`,
`orchestrator/fsm.py`, `orchestrator/answer.py`,
`orchestrator/canary_drive.py` и др.), число критериев приёмки (15).

Прогноз диффа: 60 КиБ (основная часть — долгоживущие приёмочные тесты;
кода — правки `cmd_new`, `merge_after.check`/`status_suffix`, гейта SPEC).

**Обоснование монолита.** Запись заявленного значения при `new` (пп. 1–4) и
сверка на гейте SPEC (пп. 5–7) — одна атомарная смена механики: без сверки
нынешний `approve` на `spec_gate` перезаписывает колонку значением SPEC, и
SPEC без поля молча стирает заявленное Оператором (ТЗ, «Факты», вывод о
записи при `new`) — часть «только `new`» оставила бы систему в состоянии,
где заявление теряется на первом же гейте. Обратная часть «только гейт»
без записи при `new` сверять не с чем. Делить по зонам тоже нечего: обе
половины живут в `orchestrator/` и тестах `tests/`.

Бюджет: рамка Оператора в ТЗ — $25, `budget_usd: 25`; калибровочная
таблица `config.BUDGET_CALIBRATION_TABLE` по числу критериев (15) относит
задачу к уровню ~$45 — материал Оператору на гейте SPEC для решения о
потолке.

- Перестановка FIFO очереди merge-окна.

- Дублирование сверки п. 5 на переходе `spec_writing -> spec_gate`
  (`orchestrator/fsm_advance.py::spec_writing`) — решение этого SPEC.

  (CI ветки идёт без приложений).
- Неослабление и неизменность ожиданий существующих тестов `tests/`, в
  том числе `test_ac13_no_suffix_in_other_state`, полный зелёный набор,

- Только чтение (ТЗ): `scripts/guard.py`, `docs/adr/`, `docs/roadmap.md`,
