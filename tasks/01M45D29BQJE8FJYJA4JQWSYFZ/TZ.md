- Скил аналитика (спецификация SPEC) уже велит заполнять `merge_after`

  закомментированное поле с тем же правилом. Ни тот, ни другой не
  говорят, что заявленное Оператором нельзя терять.

Требуется:
1. `new --tz` распознаёт в ТЗ строку, начинающуюся с «Порядок: после»,
   и разбирает её хвост перечнем id тем же узлом, что поле `merge_after`
   (`merge_after_items` и проверка формы). Формат строки — «Порядок:
   после <id>[, <id>…]»; SPEC фиксирует точное правило конца перечня
   (точка, пояснение в скобках, перенос строки) и поведение для
   строки «Порядок:» без слова «после» (например «без зависимостей») —
   такая строка зависимостей не заявляет. Строка «Порядок: после …»,
   хвост которой не разбирается целиком в id, — отказ `new` с названием
   неразобранного элемента, а не молчаливый пропуск. Несколько строк
   «Порядок: после …» в одном ТЗ — отказ либо объединение, решает SPEC.
2. До заведения задачи (до клона, id, артефактной ветки и строки БД —
   тем же рубежом, что `_tz_path_refusal`) каждая заявленная зависимость
   проходит те же проверки, что на гейте SPEC: задача существует,
   префикс однозначен, не `killed`, тот же target, что у заводимой
   задачи, нет повтора и цикла. Проверка — тем же узлом `merge_after.
   check` (SPEC решает, как передать ему target и id ещё не заведённой
   задачи), а не копией правил. Любая ошибка — отказ `new` с именем
   элемента и причиной, «задача не заведена», без следов в БД и git.
   Если ТЗ не прошло и сверку путей, оба отказа печатаются за один
   заход.
3. Прошедшее значение (полные id) пишется в БД как заявленное
   Оператором тем же вызовом `new`, с записью журнала задачи (действие
   и полные id). Способ хранения выбирает SPEC из двух:
   а) отдельная колонка «заявлено Оператором» (миграция `add_column`),
   рабочая колонка `merge_after` до гейта SPEC пуста либо равна ей;
   б) запись сразу в существующую колонку `merge_after` по образцу
   `_record_preliminary_zones`, гейт SPEC сверяет SPEC с колонкой ДО её
   перезаписи.
   В обоих вариантах сверка на гейте SPEC обязана различать
   «заявлено Оператором» и «добавлено аналитиком», а мандат «Зависимости
   мержа: …», принятый в `escalated` до первого approve гейта SPEC,
   меняет именно заявленное значение (это тоже решение Оператора). SPEC
   обосновывает выбор, в том числе что будет с различением при
   повторном проходе `spec_writing -> spec_gate` после `reject`.
4. `status` показывает заявленное ожидание сразу после `new`: в
   состояниях до `acceptance` (как минимум `spec_writing` и `spec_gate`)
   строка задачи несёт добавку, вычисляемую заново из БД на каждый
   вызов, только пока есть заявленные зависимости не в `done`. Текст
   добавки отличается от «[ждёт мержа:» (SPEC выбирает, например «[мерж
   после: <id> (<состояние>), …]»): добавка «[ждёт мержа: …]» в
   `acceptance`/`merge_gate` и её отсутствие в прочих состояниях не
   меняются. `show <id>` выводит заявленные зависимости с самого `new`.
5. Гейт SPEC (`approve` на `spec_gate`) до записи колонок сверяет поле
   `merge_after` SPEC с заявленным: каждая заявленная зависимость
   обязана присутствовать (сравнение по полным id после разрешения
   префиксов). Потеря хоть одной, в том числе SPEC без поля при
   непустом заявленном, — мягкий отказ тем же способом, что нынешние
   отказы `merge_after` (журнал «approve отклонён», задача на
   `spec_gate`, колонки не пишутся), причина называет каждую потерянную
   зависимость и канал её снятия (мандат Оператора в ANSWER либо
   эскалация аналитика). SPEC решает, дублировать ли эту сверку на
   переходе `spec_writing -> spec_gate`, чтобы SPEC с потерей
   возвращался аналитику без участия Оператора.
6. Аналитик вправе добавить свою зависимость сверх заявленных только с
   обоснованием; место обоснования (раздел SPEC) и его проверку задаёт
   SPEC. Добавка без обоснования — отказ гейта SPEC с именем
   добавленной зависимости. Принятая добавка проходит проверки п. 2 и
   отмечается в журнале отдельно от заявленных («добавлено
   аналитиком: …»).
7. Дальнейшая смена значения после гейта SPEC — только прежними
   каналами (PLAN, мандат «Зависимости мержа: …» в ANSWER) без изменения
   их правил; гейт мержа и `merge_gate_refuses` читают ту же рабочую
   колонку, что сегодня. Задача без строки «Порядок: после …» в ТЗ, без
   ТЗ, подзадача деления и задача канарейки ведут себя как сегодня.
8. `docs/codebase-map.md` описывает разбор строки при `new`, место
   хранения заявленного значения, сверку на гейте SPEC и добавку
   `status`.
9. Тесты в `tests/` с заявками «Ловит мутацию» на пп. 1–7, в том числе:
   разбор строки с одним и несколькими id и префиксами; строка
   «Порядок:» без «после» — задача заводится без зависимостей; хвост с
   неразобранным элементом — отказ; несуществующая, неоднозначная,
   убитая и чужого target зависимость — отказ `new` без строки в БД и
   без артефактной ветки; успешный `new` пишет заявленное значение и
   журнал; добавка `status` в `spec_writing` сразу после `new` и её
   исчезновение, когда зависимость в `done`; гейт SPEC отказывает при
   потере заявленной зависимости и при SPEC без поля, называя её;
   добавка аналитика с обоснованием проходит, без обоснования —
   отказ; мандат в `escalated` до гейта SPEC меняет заявленное
   значение. Существующие тесты не ослабляются и их ожидания не
   меняются, в том числе `test_ac13_no_suffix_in_other_state`.
