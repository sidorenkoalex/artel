# ТЗ: нагрузка машины в записи полного прогона и сигнал роста времени прогона

Источник: разбор инцидента 07.10 (решение Оператора 07.10 «ок по
рекомендациям», меры 1–3). Виртуальная машина Docker Desktop с 04.10
занимала ~11 ядер из 16, load average 28–59; это три дня не замечали.
Полный прогон гейта вырос со 144–207 с (02.10 – 04.10 09:01, 3 737–4 021
тестов) до 450–840 с (05.10 13:23 – 07.10, 4 324–4 616 тестов): в 3,8 раза
при +15 % тестов. Таймауты прогонов, git и канарейки объяснялись нашей
параллельной нагрузкой; предел полного прогона 06.10 поднят до 1500 с по
прогонам под чужой нагрузкой.

Факты (пин 79a703e4, сверка 07.10):
- Полный прогон гейта — `orchestrator/acceptance.py::full_suite` (~1082),
  лог пишет `_write_full_suite_log` (~785) в `.artel/logs/<id>-fullsuite-<n>.log`;
  итог pytest («N passed … in S s») в логе есть, в журнал задачи время и
  число тестов отдельной записью не пишутся.
- Фоновый прогон `suite-run` — `orchestrator/suite_run.py` (`background` ~461,
  запуск ~600–700); отчёт о таймауте называет предел и его источник, но не
  нагрузку машины.
- Образец сигнала по ряду журнала — наблюдатель роста карты
  `orchestrator/doctor/map_growth.py` (`map.growth`): ряд записей журнала
  «карта: размер», медиана окна калибровки, перекалибровка по `ack`,
  алерт `kind=trigger`. Каталог сигналов — строка 27 в `docs/triggers.md`.
- Процессы машины доктор уже читает: `orchestrator/doctor/hung_test_watchdog.py::_running_processes`
  (`ps -axww -o pid=,etime=,command=`).

Требуется:
1. Каждый полный прогон (гейт `full_suite` и `suite-run`) пишет в журнал
   задачи запись «прогон: время» с полями: длительность, число тестов
   (passed + failed + skipped по итогу pytest), время на тест, число
   процессов xdist, load average за 1 и 5 минут на старте и на конце,
   число ядер машины, три процесса машины с наибольшей загрузкой
   процессора вне дерева самого прогона (pid, % процессора, имя). Запись
   пишется на любом исходе, в том числе при таймауте и при отказе.
2. Отказ гейта и отчёт `suite-run` по таймауту называют load average и
   три главных посторонних процесса из той же записи — одной строкой.
3. Doctor: проверка нагрузки машины — предупреждение (не отказ), если
   load average за 5 минут выше числа ядер ИЛИ посторонний процесс выше
   порога ядер (именованная константа `config`, решение SPEC; ориентир —
   4 ядра). Строка называет процесс, его загрузку и время жизни.
4. Сигнал `suite.duration` по образцу `map.growth`: время на тест
   последнего прогона против медианы окна калибровки выше коэффициента
   (именованные константы `config`, решение SPEC с обоснованием по ряду
   логов 02.10–07.10 — сигнал обязан сработать на прогонах 04.10 вечером
   и не срабатывать на 02.10–04.10 утром); перекалибровка по `ack`; алерт
   `kind=trigger` несёт в тексте нагрузку машины прогона, давшего сигнал.
   Строка каталога — в `docs/triggers.md` (приложением к PLAN, точный
   текст).
5. Тесты в `tests/` с заявками «Ловит мутацию»: запись «прогон: время»
   на зелёном, красном и таймауте; посторонние процессы не включают дерево
   прогона; отказ по таймауту несёт нагрузку; проверка doctor молчит на
   свободной машине и предупреждает на перегруженной (процессы и load
   average подменяются, без реальных `ps`/`os.getloadavg` в проверке
   свойства); `suite.duration` срабатывает на ряду с ростом времени на
   тест и молчит на ряду с ростом числа тестов без роста времени на тест;
   `ack` переносит точку отсчёта. Существующие тесты не ослабляются.
6. В PLAN — ряд времени на тест по логам `.artel/logs/*-fullsuite-*.log`
   02.10–07.10 и выбор порогов по нему.
