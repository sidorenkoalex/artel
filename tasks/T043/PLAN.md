# PLAN: RETRO: дайджест задачи в main на переходе в done/killed

## Подход

Решение (d) Оператора (`tasks/T043/TZ.md`, «Ответ на эскалацию
test_author») задаёт разделение: `kill` (`orchestrator/cleanup.py`)
никак не меняется — main он не трогал и не будет; вся генерация и
коммит RETRO (и done, и killed-долги) происходят только в
merge-последовательности `orchestrator/fsm.py::cmd_approve`, ветка
`state == "merge_gate"`, тем же приёмом, что регенерация карты кодовой
базы (T042): между `git merge --no-ff` и `git push`.

Генерацию контента (парсинг журнала steps, фронтматтеров, вёрстка
текста) выношу в отдельный модуль `orchestrator/retro.py` — чистые
функции без побочных эффектов, юнит-тестируемые без git и БД-песочницы
FSM (тот же принцип разделения, что `orchestrator/review.py`/
`orchestrator/acceptance.py`: сборка пакета/сводки отдельно от
`fsm.py`, который отвечает за переходы и git). `orchestrator/fsm.py`
остаётся точкой оркестрации побочных эффектов (запись файла, `git add`,
`git commit`) и обработки провала как некритичного инцидента — тем же
кодом, что и `_regenerate_and_commit_map`.

Ключевые решения генератора (`orchestrator/retro.py`):

1. **Источник данных** — `store.task_steps` (журнал) и
   `tasks/<id>/SPEC.md` (фронтматтер + первая строка «Контекст» через
   `guard.section_body`), `tasks/<id>/acceptance_tests/` (через уже
   существующие `guard.scan_acceptance_tests`/`count_test_methods` —
   то же ядро, что использует `orchestrator/acceptance.py`, без
   повторного изобретения разбора AC-пометок). Ничего не запускается
   (`unittest`), только статический разбор — соответствует требованию 3
   (детерминизм) без специальных усилий: входы уже детерминированы, чтение
   файла и SQL-запрос по неизменным данным сами по себе повторяемы.

2. **Стоимость по шагам — агрегация по actor, не по каждому событию.**
   Требование 5 просит «стоимость по шагам (actor, $, токены)»; список из
   одной строки на КАЖДОЕ событие `agent run finished` не гарантировал бы
   лимит 30 строк для задачи с длинной историей итераций ревью (до
   `config.LIMIT_REVIEW_ITERS` попыток на каждую итерацию). Разбор
   регуляркой `детали` события (формат `rc=0, попытка N/M, стоимость
   $X.XXXX, токенов K` — `orchestrator/spend.charge_step`/`cost_note`) и
   суммирование по `actor` даёт компактную, ограниченную по числу строк
   (число ролей в конвейере — константа) и при этом детерминированную
   разбивку.

3. **Эскалации — счётчик + текст ПОСЛЕДНЕЙ, разной полноты для done и
   killed.** Требование 5 («эскалации с причинами») для done и
   требование 7 («полный текст ПОСЛЕДНЕЙ эскалации») для killed
   трактую одним общим правилом «только последняя», но с разной формой
   цитаты: количество эскалаций (`state -> escalated` в журнале) плюс
   для killed — дословная цитата последней ЦЕЛИКОМ (требование 7,
   объём цитаты явно выведен из-под лимита требованием 4), для done —
   только ПЕРВАЯ строка `detail` последней эскалации (плюс многоточие,
   если строк было больше одной). Правка ред. Оператора после
   REVIEW.md итерации 1 (замечание-1, blocker): исходная версия этого
   решения ошибочно утверждала, что цитирование последней эскалации
   «единственный способ гарантировать лимит 30 строк для done без
   исключения» — это неверно само по себе, поскольку `detail` записи
   `state -> escalated` НЕ гарантированно однострочный ни в БД, ни в
   коде `orchestrator/runner.py`: самый частый путь эскалации
   (исчерпание попыток агента, `runner.py:239-241`) тянет в `detail`
   хвост лога агента (`agent_log.log_tail`, до `config.LOG_TAIL_LINES`
   = 15 строк, склеенных `\n`) ОДНОЙ f-строкой — при таком `detail`
   старая версия `_escalations_block` вставляла его в файл целиком, и
   лимит 30 строк для done нарушался на реалистичном сценарии
   (воспроизведено ревьювером, тест
   `test_build_done_truncates_multiline_escalation_to_first_line`).
   Теперь `orchestrator/retro.py::_escalations_block(steps, *, full)`
   явно разводит два случая (`full=False` — done, только первая строка;
   `full=True` — killed, весь текст) — лимит 30 строк для done
   гарантирован СТАТИЧЕСКИ (по конструкции: ровно одна строка на
   последнюю эскалацию), а не тем, что в реальных данных `detail`
   оказался однострочным. У эскалаций теоретически нет верхнего
   предела по количеству (цикл escalated → approve → снова escalated),
   поэтому список показывает счётчик, не полный перечень.

4. **Адрес артефактов (требование 8)** — `merge_sha` берётся ОДИН раз,
   сразу после успешного `git merge`, ДО `_regenerate_and_commit_map` и
   до записи RETRO: это гарантирует, что зафиксированный sha —
   действительно sha коммита мержа, а не более позднего служебного
   коммита (карты или самого RETRO), даже если между ними появятся
   собственные коммиты. `tasks.fixed_sha` для этого не годится:
   `fixation._fix_dogfood` при ещё не удалённой ветке задачи после мержа
   вернёт sha ГОЛОВЫ ВЕТКИ задачи (`on_foreign_branch` истинен, ветка
   существует и отлична от `main`), а не sha коммита мержа на `main` —
   это разные коммиты при `--no-ff`.

5. **killed-долги.** На каждом `merge_gate` (после генерации/коммита
   done-RETRO текущей задачи) оркестратор проходит ВСЕ задачи в
   состоянии `killed`, у которых на диске ещё нет
   `docs/retro/<id>.md`, и генерирует/коммитит killed-RETRO каждой —
   отдельным коммитом на каждую задачу-долг (не одним огромным коммитом
   со всеми сразу): провал одной не должен мешать журналировать/чинить
   остальные по отдельности, и `git log` остаётся читаемым (один коммит
   = одна задача, тем же принципом, что и коммит done-RETRO).
   `tasks/<killed_id>/` к моменту подбора долга обычно уже удалён
   `cleanup.cleanup_killed_task` — генератор killed-RETRO построен так,
   чтобы не падать на отсутствующих SPEC/acceptance_tests (пустые
   значения полей), только БД остаётся источником истины для
   killed-задач, что и требует решение (d) («данные для RETRO
   killed-задачи и так вечны в журнале БД»).

6. **Провал — некритичный инцидент**, тем же приёмом и тем же
   `source`-префиксом (`fsm.retro`), что `fsm.map_regen` у T042:
   генерация контента, запись файла, `git add`, `git commit` — каждый
   шаг обёрнут так, чтобы исключение/ненулевой код возврата не
   прерывали остальную последовательность merge_gate (`push` всегда
   выполняется). **Привязка инцидента killed-долга — к `debt_id`, не к
   мержащейся задаче.** Правка ред. Оператора после REVIEW.md итерации
   1 (замечание-2, major): в цикле подбора долгов
   (`orchestrator/fsm.py::_generate_and_commit_retro`, ветка по
   killed-задачам) провал ГЕНЕРАЦИИ и провал КОММИТА killed-RETRO
   ошибочно передавали в `_retro_incident`/`_commit_retro` внешний
   `task_id` (мержащуюся в данный `merge_gate` задачу) вместо `debt_id`
   (собственно убитую задачу-долг) — расходясь с соседней строкой того
   же цикла (`_write_and_stage_retro(conn, debt_id, ...)`, где
   привязка к `debt_id` уже была верной). Следствие: запись «RETRO
   FAILED» в журнале и incident-алерт (с `target`, вычисленным по
   ЧУЖОМУ `task_id`) уходили не туда — оператор, читающий `log
   <debt_id>` убитой задачи, не видел причину отсутствия её RETRO в
   main, а в мультитаргетной установке алерт мог уйти в очередь не
   того target'а. Исправлено: обе точки (`_retro_incident` при провале
   генерации, `_commit_retro` при провале коммита) теперь получают
   `debt_id` первым аргументом — тем же способом, что и
   `_write_and_stage_retro`. Тесты:
   `tests/test_fsm_retro.py::GenerateAndCommitRetroTest.
   test_killed_debt_generation_failure_attributes_incident_to_debt_not_task`
   и `test_killed_debt_commit_failure_attributes_incident_to_debt_not_task`
   (второй — с разными `target` у долга и мержащейся задачи, проверяет
   и журнал, и `target` алерта).

**Требование 12 (backfill).** Решил НЕ делать
`scripts/retro_backfill.py` в этой задаче. Причина: для уже закрытых
задач T001–T042 у оркестратора нет надёжного способа детерминированно
восстановить именно sha КОММИТА МЕРЖА (не любой коммит той же
задачи) — `tasks.fixed_sha` для догфуда, как показано в пункте 4 выше,
после мержа фиксирует голову ВЕТКИ задачи, а не коммит мержа на `main`
(они расходятся при `--no-ff`, а ветки задач к тому же обычно уже
удалены); эвристика по `git log --merges --grep` не детерминирована
(сообщения коммитов мержа менялись за 42 задачи и не гарантированно
парсятся однозначно) и не «дёшево» в смысле требования 12 — риск
записать в main НЕВЕРНЫЙ контент-адресный адрес хуже отсутствия
файла, поскольку требование 8 явно требует, чтобы адрес «оставался
верным независимо от состояния» — заведомо шаткая эвристика этому
противоречит. Скрипт не заводится; сама возможность (опциональный,
отдельный) остаётся неотмененной для будущей задачи, если появится
надёжный источник sha мержа по каждой из T001–T042 (например, из
`git log` вручную сверенный Оператором).

**Требование 13 (зеркало в БД).** Решил НЕ делать. Тривиального
способа нет: понадобилась бы новая таблица/колонка (миграция схемы
`orchestrator/store.py`) и новый читатель для «будущей панели», которой
сегодня нет ни кода, ни потребителя — это уже не «тривиально», а
отдельная задача с собственным SPEC. Текстовый файл в main остаётся
единственным источником, как и допускает требование 13.

## Влияние на систему

Единственная новая точка записи в `main` — внутри уже существующей
`merge_gate` последовательности `cmd_approve`, СТРОГО между `merge` и
`push`, тем же способом, что и карта кодовой базы T042: новый шаг не
создаёт альтернативного пути коммита в `main` и не меняет условие
«зелёный CI» или сам `push` (инвариант `MergeOnlyFromMergeGateTest`
цел — единственная точка входа не размножается). `orchestrator/
cleanup.py` НЕ меняется вовсе: инвариант 15 («kill не изменяет main»,
`tests/test_invariants.py::KillKeepsMainIntactTest`) остаётся целым
буквально, а не «ослабленным под RETRO» — решение (d) Оператора
устраняет саму возможность конфликта, а не конфликт после факта.
Провал шага RETRO (генерация/запись/`add`/`commit`, на любом из двух
путей — done или killed-долг) не бросает исключение и не делает
`sys.exit`: `push` в `cmd_approve` выполняется независимо от исхода,
переход в `done` не блокируется — тем же принципом отказоустойчивости,
что и `fsm.map_regen`, новый incident `fsm.retro` читается тем же
`doctor`/`alert-ack`, ничего нового заводить не нужно. Новые git-вызовы
идут только через `gitcmd.git` (AC-5, проверено статическим тестом по
образцу T042, расширенным на `orchestrator/cleanup.py`, который в этой
задаче не меняется и такую проверку и так проходит). `.github/`,
`skills/`, `templates/` не затрагиваются — новый код не требует правки
CI (существующий джоб `protected-paths` — единственная проверка этого
свойства, она не меняется). Существующий набор тестов
(`tests/`, `tasks/*/acceptance_tests/`) остаётся зелёным — новые файлы
только добавляются, ни один существующий тест не редактируется и не
ослабляется. Откат — `git revert` коммита(ов) этой задачи:
`merge_gate` вернётся к поведению без шага RETRO, `docs/retro/`
останется как исторический артефакт уже сгенерированных файлов (их
удаление откатом не требуется — они корректные записи о прошлом).

## Риски

- Для задач с ЧРЕЗВЫЧАЙНО долгой историей (много разных `actor` в
  разбивке стоимости — на практике ограничено ролями конвейера, их
  штук 5–6) done-RETRO теоретически может приблизиться к лимиту в 30
  строк. Не считаю риском требующим отдельной защиты: число различных
  actor в любой задаче ограничено составом ролей `roles.yaml`, не
  числом попыток/итераций (агрегация по actor, не по событию — решение
  2 выше).
- killed-долг для ОЧЕНЬ старой killed-задачи, для которой к моменту
  подбора у target'а сменился состав ролей/схема БД, — деградирует до
  пустых полей (0 тестов, без причины эскалации), не падает: то же
  свойство отказоустойчивости, что и у отсутствующего `tasks/<id>/`.

  `cmd_approve` (единственная точка входа в `_regenerate_and_commit_map`

  RetroSandboxTest`, которая наследует `FsmTest` и патчит `config.ROOT`
