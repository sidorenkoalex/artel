# ТЗ: RETRO: дайджест задачи в main на переходе в done/killed

RETRO.md — детерминированный дайджест задачи в main на переходе в done/killed (строка беклога P3 «RETRO.md»; решения Оператора 26.08).

Проблема: знания о прошлых задачах живут в двух местах, недоступных одним взглядом: артефакты tasks/<id>/ (после A7 уедут в .artel — вне main, в гитигноре, только локальная копия) и журнал БД state.db (только локально, в гитигноре). Рабочая память проекта — прецеденты, стоимость, итерации, эскалации — не видна ни агентам в чужих контекстах, ни параллельным сессиям, ни людям из main. Ссылки вида «прецедент T022», «правила T015» сегодня опираются на файлы, которые после A7 из main исчезнут.

Решения Оператора (зафиксированы, не обсуждаются в SPEC):
- RETRO живёт в MAIN: docs/retro/<id>.md — и остаётся в main после A7, когда артефакты переедут в .artel;
- генерация ДЕТЕРМИНИРОВАННАЯ, без LLM: только чтение журнала steps и фронтматтеров артефактов; повторная генерация по тем же данным даёт тот же файл байт в байт;
- размер — не более 30 строк на задачу;
- RETRO — единственный вход о прошлых задачах в чужие контексты (К2, К3, ассистент) и «оглавление архива»: по нему решают, надо ли идти в полные артефакты.

Что сделать: на переходе задачи в done (в merge-последовательности merge_gate, после мержа — тем же приёмом, что регенерация карты T042) и при kill (cleanup) оркестратор генерирует docs/retro/<id>.md и коммитит его в main тем же push. Содержимое (все поля — из БД и фронтматтеров, адреса точные): id и название; итог (done: sha мержа / killed: причина из журнала); стоимость итоговая и по шагам (actor, $, токены — из событий agent run finished); итерации ревью и отказы приёмки; эскалации с причинами (записи state -> escalated); число приёмочных тестов и пометок manual/skip; одна строка сути — название задачи + первая строка раздела «Контекст» SPEC (детерминированное извлечение, не пересказ); адрес артефактов (tasks/<id>/ до A7; строка формируется так, чтобы пережить переезд — например «артефакты: tasks/T042/ (до A7) / .artel/projects/artel/tasks/T042/ (после)»).

Границы и отказоустойчивость:
- провал генерации или коммита RETRO не отменяет merge/kill и не блокирует переход: журнал + алерт kind=incident (source вида fsm.retro), образец — fsm.map_regen из T042;
- git-вызовы — через gitcmd.git (образец T036);
- .github/, skills/, templates/ не трогаются; CI и гейты не меняются;
- задним числом RETRO для уже закрытых задач T001–T042 в этой задаче не генерируется (опционально: отдельный скрипт-backfill scripts/retro_backfill.py, решает исполнитель в PLAN — если дёшево, сделать, это сразу наполнит docs/retro/ историей);
- опция (решить в PLAN с обоснованием): зеркальная строка дайджеста в таблицу БД для будущей панели — только если тривиально; текстовый файл в main — первичен.

Критерии приёмки (ориентир): (1) задача, прошедшая merge_gate, оставляет в main docs/retro/<id>.md не длиннее 30 строк с полями выше, коммит уходит тем же push, что и merge; (2) kill задачи создаёт docs/retro/<id>.md с причиной снятия; (3) провал генерации/коммита RETRO не отменяет merge/kill: переход состоялся, в журнале запись, в alerts открыт incident fsm.retro; (4) детерминизм: повторный прогон генератора по тому же журналу даёт идентичный файл; (5) новые git-вызовы — через gitcmd.git; (6) существующий набор тестов зелёный; (7) .github/, skills/, templates/ в диффе не затронуты.

## Ответ Оператора на батч (26.08, вопрос 1)

Принят вариант **A** (дефолт батча): RETRO при `kill` генерируется и
коммитится в main ТОЛЬКО если рабочее дерево уже стоит на
`config.MAIN_BRANCH`; в любом другом случае — пропуск с записью в
журнал (тем же стилем, что существующие пометки уборки). `kill` не
приобретает новых побочных эффектов: веток не переключает, его
неослабляемая семантика «срабатывает всегда» не затрагивается —
RETRO-шаг строго дополнительный и некритичный. Push после коммита —
как в merge_gate; провал любого шага RETRO — журнал + алерт
kind=incident (source вида fsm.retro), сам kill при этом завершён.
Критерий приёмки (2) в SPEC формулируется с этой оговоркой явно.

Два дополнения к ТЗ тем же решением:

1. **RETRO killed-задачи — расширенный.** Для killed ветка задачи
   удаляется без мержа — git-история main её содержимого НЕ хранит,
   RETRO становится единственным выжившим носителем. Поэтому сверх
   общих полей он включает: причину снятия (запись kill в журнале)
   и полный текст последней эскалации, если была (записи
   `state -> escalated` и их detail из журнала steps) — извлечение
   детерминированное, из БД, без пересказа. Лимит 30 строк для
   killed допустимо превышать на объём цитаты эскалации.

2. **Адрес артефактов — в вечной форме.** Строка адреса в RETRO
   done-задачи: `<merge-sha>:tasks/<id>/` — контент-адресная ссылка
   в историю git, которая остаётся верной при живом каталоге, после
   его чистки из рабочего дерева и после любых будущих переездов
   артефактов; формулировка «до A7 / после A7» из исходного ТЗ
   снимается в пользу этой. Для killed-задачи адрес не пишется
   (истории нет), вместо него — пометка «артефакты не сохранены
   (ветка удалена при kill)».

## Ответ Оператора на эскалацию test_author (27.08, AC-2/AC-8/AC-9)

Эскалация обоснована: вариант A в части «kill коммитит RETRO в main»
конфликтует с неослабляемым инвариантом 15 «kill не изменяет main»
(tests/test_invariants.py::KillKeepsMainIntactTest::
test_kill_never_commits_to_main) — этого не увидели ни ТЗ, ни SPEC.
Ни один из вариантов (a)/(b)/(c) не принят; принято решение (d):

**killed-RETRO доставляет в main не kill, а следующий merge_gate.**

- `kill` НЕ трогает main вообще — ни генерации файла в рабочее дерево,
  ни коммита, ни push: инвариант 15 сохраняется буквально, прежняя
  оговорка «kill с ветки main» снимается за ненадобностью (поведение
  kill относительно RETRO больше не зависит от текущей ветки).
  Данные для RETRO killed-задачи и так вечны в журнале БД.
- Оркестратор в merge-последовательности merge_gate (там, где он уже
  легально коммитит в main: карта T042, done-RETRO этой задачи) перед
  push дополнительно ПОДБИРАЕТ ДОЛГИ: для каждой задачи в состоянии
  killed, у которой нет docs/retro/<id>.md, генерирует killed-RETRO
  (требования 6–8) и коммитит его (отдельным коммитом или вместе с
  done-RETRO — решает исполнитель в PLAN). Лаг доставки до ближайшего
  мержа — принят Оператором: killed-RETRO — архивная запись, генерация
  детерминирована, файл от ожидания не меняется.
- Провал подбора долгов — некритичен тем же правилом, что и остальной
  RETRO-шаг: merge не отменяется, журнал + алерт fsm.retro.

Следствия для SPEC: требование 2 и AC-2 переформулировать под (d) —
«kill main не изменяет; killed-RETRO появляется в main на ближайшем
merge_gate после kill»; AC-8/AC-9 (killed-форма) разблокируются этим
же решением; оговорка про ветку при kill удаляется; сценарий AC-2
проверяется как: kill (с любой ветки) → main нетронут → следующий
merge_gate любой задачи → в main появились и done-RETRO смерженной,
и killed-RETRO убитой.
