# QUESTIONS: RETRO: дайджест задачи в main на переходе в done/killed

## Вопросы

1. **Как RETRO попадает в main при `kill`, если у `kill` сегодня нет ни
   одного git-коммита/push вообще?** ТЗ формулирует общее правило одной
   фразой: «на переходе задачи в done (...) и при kill (cleanup)
   оркестратор генерирует docs/retro/<id>.md и коммитит его в main тем же
   push» (TZ.md, «Что сделать»). Для `done` это буквально повторяет приём
   T042 — на `merge_gate` (`orchestrator/fsm.py`, ветка `state ==
   "merge_gate"`) оркестратор уже стоит на `main` (явный `git checkout
   main` + `git pull --ff-only` перед мержем, `orchestrator/fsm.py:518-521`)
   и уже делает `git push` (`orchestrator/fsm.py:533`) — коммит RETRO
   просто встаёт в ту же последовательность, как карта кодовой базы.

   Для `kill` такого «того же push» не существует: `cleanup_killed_task`
   (`orchestrator/cleanup.py:79-107`) не делает ни `git checkout`, ни
   `git commit`, ни `git push` — только локальный `rmtree` каталога
   задачи и `git branch -D` ветки задачи. Более того, `cmd_kill` не
   требует, чтобы текущая ветка была `main`: единственная существующая
   проверка — пропустить уборку, если текущая ветка совпадает именно с
   веткой убиваемой задачи (`orchestrator/cleanup.py:95-101`, подсказка
   пользователю «перейди на main и повтори kill»); если HEAD стоит на
   какой-то третьей ветке, уборка сегодня всё равно выполняется. Это
   расходится и с критерием ТЗ (2) «kill задачи создаёт
   docs/retro/<id>.md» — сформулированным безусловно, без оговорки про
   текущую ветку. Кроме того, `kill switch` документирован как
   неослабляемый инвариант «срабатывает всегда» (тест
   `tests/test_kill_cleanup.py`, docs/design.md §6) — любое новое
   git-действие в этом пути должно быть однозначно неблокирующим и не
   менять поведение существующей уборки.

   Варианты:
   - A) Консервативно: RETRO генерируется и коммитится в main при `kill`
     ТОЛЬКО если оркестратор в этот момент уже находится на ветке `main`
     (обычный случай — Оператор запускает kill с main). Если текущая
     ветка не `main` (в т.ч. ветка самой убиваемой задачи — уже
     обрабатывается отдельно) — генерация/коммит RETRO пропускаются с
     пометкой в журнале, аналогично существующей пометке про уборку
     каталога/ветки; `git push` после коммита — как в merge_gate, провал
     push (нет сети/remote) некритичен, уходит в alert `fsm.retro`.
     Ветки пользователя `kill` не переключает — побочный эффект команды
     не расширяется сверх уборки (SPEC T008).
   - B) Оркестратор сам переключается на `main` перед записью RETRO
     (`git checkout main`, тем же приёмом, что merge_gate), независимо от
     того, где сейчас HEAD, затем коммитит и пушит; провал любого шага
     (checkout/commit/push) — некритичен, alert `fsm.retro`. Даёт RETRO
     безусловно на каждый kill (буквально соответствует критерию ТЗ (2)),
     но вводит новый побочный эффект для команды, которая сегодня ветки
     не трогает.
   - C) Push при kill не делается вовсе — RETRO коммитится только
     локально в `main` (при выполнении предпосылки варианта A или B по
     ветке); уезжает в origin позже, при ближайшем `git push` (например
     на следующем merge_gate) или руками Оператора.

   Дефолт при молчании: **A** — не меняет существующее поведение `kill`
   в части переключения веток и не вводит для kill-switch новых
   предпосылок сверх уже задокументированных; ценой того, что критерий
   ТЗ (2) в SPEC будет сформулирован с оговоркой «если kill выполняется
   с ветки main» вместо безусловного «kill задачи создаёт RETRO», а push
   выполняется как в merge_gate (без отдельной проверки на remote,
   провал — некритичный инцидент).
