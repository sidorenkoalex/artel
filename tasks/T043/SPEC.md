# SPEC: RETRO: дайджест задачи в main на переходе в done/killed

## Контекст

Знания о прошлых задачах сегодня живут в двух местах, недоступных
одним взглядом: артефакты `tasks/<id>/` (после A7 уедут в `.artel` —
вне main, в гитигноре, только локальная копия) и журнал БД `state.db`
(только локально, в гитигноре). Рабочая память проекта — прецеденты,
стоимость, итерации, эскалации — не видна ни агентам в чужих
контекстах, ни параллельным сессиям, ни людям из main; ссылки вида
«прецедент T022» опираются на файлы, которые после A7 из main исчезнут.
`docs/retro/<id>.md` закрывает это: детерминированный дайджест задачи,
который остаётся в main и после переезда артефактов, и служит
единственным входом о прошлых задачах в чужие контексты (К2, К3,
ассистент) — «оглавлением архива», по которому решают, идти ли в
полные артефакты.

## Требования

1. На переходе задачи в `done` (в merge-последовательности
   `merge_gate`, после мержа — тем же приёмом, что регенерация карты
   кодовой базы T042: `orchestrator/fsm.py`, ветка `state ==
   "merge_gate"`) оркестратор генерирует `docs/retro/<id>.md` и
   коммитит его в main тем же `git push`, что и merge.
2. `kill` main НЕ изменяет (ред. Оператора 27.08, решение (d) по
   эскалации test_author): ни генерации файла RETRO в рабочее дерево,
   ни коммита, ни push при kill не происходит — инвариант 15 («kill
   не изменяет main», tests/test_invariants.py::KillKeepsMainIntactTest)
   сохраняется буквально, существующая уборка (каталог задачи, ветка
   задачи) не меняется. killed-RETRO доставляет в main следующий
   `merge_gate`: в merge-последовательности, там же, где коммитится
   done-RETRO (требование 1), оркестратор перед push подбирает долги —
   для каждой задачи в состоянии killed без `docs/retro/<id>.md`
   генерирует killed-RETRO (требования 6–8) и коммитит его (отдельным
   коммитом или вместе с done-RETRO — решает исполнитель в PLAN).
   Лаг доставки до ближайшего мержа принят Оператором; провал подбора
   долгов некритичен тем же правилом, что требование 9.
3. Генерация детерминированная, без LLM: источник данных — только
   журнал шагов (steps) БД и фронтматтеры артефактов задачи; повторный
   прогон генератора по тем же входным данным даёт тот же файл байт в
   байт.
4. Размер `docs/retro/<id>.md` — не более 30 строк на задачу; для
   killed-задачи лимит допустимо превышать на объём цитаты последней
   эскалации (требование 7).
5. RETRO задачи, дошедшей до `done`, содержит поля: id и название
   задачи; итог — sha коммита мержа; итоговая стоимость и стоимость по
   шагам (actor, $, токены — из событий agent run finished журнала
   steps); число итераций ревью и отказов приёмки; эскалации с
   причинами (записи `state -> escalated` журнала steps); число
   приёмочных тестов и пометок manual/skip; одна строка сути —
   название задачи + первая строка раздела «Контекст» SPEC
   (детерминированное извлечение, не пересказ); адрес артефактов
   (требование 8).
6. RETRO задачи, снятой через `kill` (при выполнении условия
   требования 2), содержит те же поля, что в требовании 5, за
   исключением итога и адреса артефактов, вместо которых: причина
   снятия (запись kill в журнале steps) и адрес артефактов в форме
   требования 8.
7. Сверх общих полей (требование 5/6) RETRO killed-задачи включает:
   полный текст последней эскалации, если она была (записи `state ->
   escalated` журнала steps и их detail) — извлечение
   детерминированное, из БД, без пересказа.
8. Адрес артефактов: для done-задачи — в форме `<merge-sha>:tasks/<id>/`
   (контент-адресная ссылка в историю git, верная независимо от
   состояния рабочего дерева и будущих переездов артефактов); для
   killed-задачи адрес не пишется (ветка удалена, истории в main нет),
   вместо него — пометка «артефакты не сохранены (ветка удалена при
   kill)».
9. Провал генерации или коммита RETRO (на любом из путей — done или
   kill) не отменяет и не блокирует сам переход (merge/kill): переход
   состоявшийся, в журнале шагов — запись, в alerts — открытый
   инцидент `kind=incident`, `source` вида `fsm.retro` (образец —
   `fsm.map_regen` из T042).
10. Новые git-вызовы в реализации RETRO выполняются через
    `gitcmd.git` (образец — T036).
11. `.github/`, `skills/`, `templates/` в изменениях не затрагиваются;
    существующие CI и гейты не меняются.
12. Ретроактивная генерация RETRO для уже закрытых задач T001–T042 не
    выполняется автоматически в рамках этой задачи. Отдельный
    скрипт-backfill `scripts/retro_backfill.py` — опциональный;
    решение, делать ли его, и обоснование — за разработчиком на этапе
    PLAN (если дёшево — сделать).
13. Зеркальная строка дайджеста в таблицу БД (для будущей панели) —
    опциональна и делается только если тривиально; решение и
    обоснование — за разработчиком на этапе PLAN. Текстовый файл в
    main остаётся первичным источником независимо от этого решения.

## Критерии приёмки

AC-1. Задача, прошедшая `merge_gate`, оставляет в main
`docs/retro/<id>.md` не длиннее 30 строк с полями из требования 5,
коммит которого уходит тем же push, что и merge.

AC-2. `kill` задачи (с любой текущей ветки) не изменяет main: не
создаёт ни коммитов, ни файлов RETRO в рабочем дереве; существующая
уборка (каталог, ветка) выполняется как прежде, без исключений.
Ближайший `merge_gate` любой задачи после такого kill оставляет в main
`docs/retro/<id>.md` убитой задачи с полями из требований 6–8 (в т.ч.
причиной снятия) — тем же push, что и merge.

AC-3. Провал генерации или коммита RETRO (на любом из путей — done или
kill) не отменяет переход: переход состоялся, в журнале шагов есть
запись, в alerts открыт инцидент `kind=incident`, `source` вида
`fsm.retro`.

AC-4. Повторный прогон генератора RETRO по тем же данным журнала и
фронтматтеров даёт идентичный (байт в байт) файл.

AC-5. Все новые git-вызовы в реализации выполнены через `gitcmd.git`.

AC-6. Существующий набор тестов остаётся зелёным.

AC-7. `.github/`, `skills/`, `templates/` не затронуты в дифф задачи.

AC-8. killed-RETRO, доставленный по AC-2, содержит
полный текст последней эскалации, если она была, извлечённый
детерминированно из записей `state -> escalated` журнала steps; лимит
30 строк для этого файла допустимо превышать на объём цитаты
эскалации.

AC-9. Адрес артефактов в RETRO done-задачи записан в форме
`<merge-sha>:tasks/<id>/`; в RETRO killed-задачи вместо адреса
записана пометка «артефакты не сохранены (ветка удалена при kill)».

## Не входит

- Ретроактивная генерация `docs/retro/<id>.md` для уже закрытых задач
  T001–T042 в рамках выполнения этой задачи (возможный backfill —
  отдельный опциональный скрипт, решение за PLAN).
- Изменения `.github/`, `skills/`, `templates/`, CI и существующих
  гейтов.
- Новые побочные эффекты `kill` сверх RETRO-шага при выполнении на
  main: команда по-прежнему не переключает ветки и не меняет
  существующую уборку каталога/ветки задачи.
- Обязательное зеркалирование дайджеста в таблицу БД — делается только
  если разработчик на этапе PLAN сочтёт это тривиальным.
