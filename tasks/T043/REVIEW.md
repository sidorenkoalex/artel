# REVIEW: RETRO: дайджест задачи в main на переходе в done/killed

## Гейт плана (Фаза A)

Покрытие таблицы PLAN полное (требования 1–10 → шаги 1/2, 11 — не
трогается, 12/13 — обоснованный отказ). Шаги — проверяемые единицы,
подход follows T042 (генерация между `merge` и `push`), конфликтов с
конвенциями и архитектурой не вижу.

Одно замечание к самому обоснованию плана: PLAN, «Подход», решение 3
(«Эскалации — счётчик + дословный текст ПОСЛЕДНЕЙ») утверждает, что
цитирование только последней эскалации — «единственный способ
гарантировать лимит 30 строк для done без исключения». Это утверждение
неверно: журнал `state -> escalated` не гарантирует однострочный
`detail` (см. Замечание-1 ниже) — гарантии нет ни в БД, ни в
реализации `retro.py`. Тот же дефект, что и в коде.

## Замечания

- **blocker** — `orchestrator/retro.py:120-131` (`_escalations_block`/
  `_escalations`), используется в `build_done` (`orchestrator/retro.py:155`)
  и `build_killed` (`orchestrator/retro.py:185`) — цитата последней
  эскалации вставляется в файл ЦЕЛИКОМ, без учёта того, что `detail`
  записи `state -> escalated` в журнале НЕ гарантированно однострочный.
  Самый частый путь эскалации в системе — исчерпание попыток агента
  (`orchestrator/runner.py:239-241`): `reason` там включает
  `agent_log.log_tail(log_path)` (`orchestrator/agent_log.py:44-55`) —
  до `config.LOG_TAIL_LINES` = 15 (`orchestrator/config.py:61`) строк
  трейсбека/лога, склеенных через `\n`, и весь этот текст уходит в
  `detail` эскалации одной строкой f-string. Требование 4 SPEC.md
  разрешает превышать 30 строк ТОЛЬКО для killed (объём цитаты
  эскалации), для done исключения нет. Воспроизведено (песочница,
  ROOT/TASKS/DB во tmpdir, вне рабочего дерева): задача с ОДНОЙ такой
  эскалацией (без учёта строк стоимости/actor, которые в реальной
  задаче есть всегда) даёт `build_done` в 28 строк уже почти без
  прочих полей — с любой реальной разбивкой по actor (`_cost_block`)
  файл гарантированно уйдёт за 30 строк. Ни один текущий тест
  (`tests/test_retro.py::
  test_build_done_escalations_show_count_and_last_verbatim` и
  `tasks/T043/acceptance_tests/test_retro_done.py::Ac1DoneRetroTest`)
  не проверяет многострочный `detail` — оба используют однострочные
  фикстуры-эскалации, поэтому дефект не поймали.
  Предложение: для done-пути (в отличие от killed, где полная цитата —
  явно разрешённое требованием 4 исключение) урезать цитату эскалации
  до одной строки (например, первая строка `detail` + многоточие) или
  вовсе не давать `detail` эскалации попадать в RETRO многострочным
  куском — решение по форме за разработчиком, но лимит 30 строк должен
  быть гарантирован статически, а не «повезёт с однострочным текстом».

- **major** — `orchestrator/fsm.py:161-166` (цикл подбора killed-долгов
  внутри `_generate_and_commit_retro`) — при провале ГЕНЕРАЦИИ
  killed-RETRO долга (`_retro_incident(conn, task_id, ...)`, строка 161)
  и при провале КОММИТА killed-RETRO долга (`_commit_retro(conn,
  task_id, ...)`, строка 165) в обоих случаях передаётся ВНЕШНИЙ
  `task_id` (мержащаяся в данный merge_gate задача), а не `debt_id`
  (собственно убитая задача, чей RETRO не удалось сгенерировать/
  закоммитить). Это расходится с тем же циклом строкой выше (164:
  `_write_and_stage_retro(conn, debt_id, debt_text)` — при провале
  записи/`git add` внутри неё инцидент корректно привязывается к
  `debt_id`), т.е. привязка внутри одного и того же блока непоследовательна.
  Последствия: (1) `store.journal` (`_retro_incident`,
  `orchestrator/fsm.py:100`) пишет запись «RETRO FAILED» в журнал ТЕКУЩЕЙ
  мержащейся задачи, а не убитой — оператор, читающий `log <debt_id>`
  убитой задачи, не увидит причину, почему её RETRO так и не появился в
  main; в журнале постороннего мержащегося task_id появляется путающая
  запись о чужой проблеме. (2) `alerts.raise_alert(conn,
  store.task_target(conn, task_id), ...)` (`orchestrator/fsm.py:101-102`)
  вычисляет `target` ПО ЧУЖОМУ `task_id` — в мультитаргетной установке
  (`orchestrator/targets.py`) если у убитой задачи-долга target
  отличается от target текущей мержащейся задачи, incident-алерт уйдёт
  в очередь НЕ ТОГО target'а, где его никто не ждёт.
  Воспроизведено: прогон `_generate_and_commit_retro` с фейковым git,
  проваливающим `commit` killed-RETRO долга T901 при мерже T900 —
  запись «RETRO FAILED» ушла в журнал T900, журнал T901 её не содержит.
  Предложение: в обеих строках (161, 165) передавать `debt_id` вместо
  `task_id` — тем же способом, каким уже сделано для
  `_write_and_stage_retro` на строке 164.
