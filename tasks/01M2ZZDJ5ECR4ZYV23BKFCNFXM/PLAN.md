# PLAN: Ревью-пакет: артефакты из артефактной ветки и инкрементальный diff по якорю вердикта

## Подход

Вся правка живёт в `orchestrator/review.py` (зона задачи) — там же, где
обе половины дефекта: чтение артефактов и выбор/содержимое базы diff
сходятся в одной функции `review_package` и в одной строке журнала
`package_note`. `orchestrator/runner.py` не трогается (SPEC «Не входит»),
поэтому канал алерта остаётся прежним: `runner._build_prompt` заводит
`warning`, когда пакет несёт непустой `not_collected`, и закрывает
открытые алерты того же источника, когда он пуст — значит причина отката
требования 7 обязана приехать в runner именно полем `not_collected`
(требование 7 так и формулирует: «по тому же каналу, которым сегодня
доносится „diff не собран“»). Чтобы запись журнала при этом не врала
словом «не собран» о собранном diff, пакет несёт вторую, отдельную
пометку `fallback`, и `package_note` печатает откат своей формулировкой.

`orchestrator/role_prompt.py` объявлен зоной, но правки не требует:
`prev_sha` он уже берёт у `previous_verdict_sha`, а рабочий каталог шага
`review_package` вычисляет сама — иначе вызов пакета напрямую (без
`runner._build_prompt`) остался бы без источника-отката, а именно так его
зовут и залоченная планка, и существующие юнит-тесты.

Четыре решения, которые стоит назвать явно:

1. **Источник трёх артефактов** — `artifact_source.resolve` (артефактная
   ветка), откат — каталог `tasks/<id>/` РАБОЧЕГО КАТАЛОГА ШАГА.
   Формула каталога не переписывается заново: `review.py` зовёт
   `runner.role_cwd_path(task_id, target)` отложенным импортом внутри
   функции — тем же приёмом и по той же причине, по которой
   `review_package` уже импортирует `fsm` внутри тела (`runner` импортирует
   `review` на верхнем уровне, импорт на уровне модуля дал бы цикл).
   Копия формулы «worktree задачи для self, workspace target'а — для
   внешнего» в двух модулях разошлась бы при следующей правке.
2. **Форма вердикта** (`templates/REVIEW.md`) читается как сегодня — с
   КОДОВОЙ ветки задачи, откат на `config.ROOT`. Поэтому `artifact_text`
   получает два keyword-параметра (`disk_root`, `disk_note`) вместо
   разветвления на две почти одинаковые функции: тело чтения одно,
   различаются только адрес отката и пометка об источнике.
3. **Якорь вердикта** — последний по журналу переход `state -> in_dev` с
   detail «замечания ревью, итерация …», база — `код=` ближайшей
   следующей за ним записи «sha зафиксирован». Запасного пути на
   `entries[-2]` не остаётся вовсе (AC-5 второй тест ловит именно его).
4. **Содержимое инкремента** — pathspec из путей собственных коммитов
   ветки: `git log --first-parent --no-merges --format= --name-only`
   на диапазоне `<база>..<ветка>`. Каждый путь уходит в pathspec с
   магией `:(literal)` (имя файла с `*`/`[` иначе стало бы глобом), а
   действующее исключение `:!tasks/<id>/` сохраняется рядом — правило
   каталога задачи остаётся ровно одно, тем же pathspec, и для diff, и
   для `--stat`.

Расхождения с оценкой SPEC нет — `budget_usd` не переопределяется.

## Шаги

1. `orchestrator/review.py` — чтение артефактов задачи: `artifact_text`
   получает адрес отката и пометку об источнике параметрами;
   `review_package` читает SPEC/PLAN/REVIEW с артефактной ветки
   (`artifact_source.resolve`, один резолв на весь вызов — он же для
   ANSWER-n.md) с откатом на `tasks/<id>/` рабочего каталога шага,
   форму вердикта — как сегодня (требования 1-3).
2. `orchestrator/review.py` — `previous_verdict_sha` по якорю вердикта
   вместо предпоследней записи журнала; деградация на пустую строку
   сохраняется (требования 4-5).
3. `orchestrator/review.py` — содержимое инкремента: `own_commit_paths`
   (обход по первому родителю без merge-коммитов), pathspec инкремента,
   откат на полный diff от базы вердикта при пустом инкременте и
   непустых правках, штатная пустота без алерта, заметки под diff'ом на
   все три случая (требования 6-8).
4. `orchestrator/review.py` — `package_note`: источник артефактов и база
   инкремента в записи «ревью-пакет собран» (требование 9).
5. `tests/` — новые юнит-тесты на настоящем git-репозитории
   (`tests/sandbox.py::RealGitSandbox`) и обновление ожиданий
   существующих тестов, привязанных к старому источнику артефактов и к
   «предпоследней записи» (требование 10).

Один MR: шаги 1-4 правят одну функцию сборки и одну строку журнала,
разрезать их по коммитам значило бы оставить ветку в состоянии, где
тесты шага 5 красные по построению.

6. **Итерация 2 — замечания ревью итерации 1** (реестр REVIEW.md
   размечен целиком, все три записи `fixed`):
   - R1-F1 (major, требование 6): `own_commit_paths` зовёт `git log` с
     `--no-renames` — без него `--name-only` отдаёт только новое имя
     переименованного файла, прежний путь не попадает в pathspec, и
     инкремент прячет от ревьювера исчезновение старого файла (для
     `tests/` — прямо удалённые ассерты), причём откат требования 7 этого
     не ловит: инкремент не пуст. Тесты — на настоящем git
     (`OwnCommitPathsTest`): перечень несёт оба пути пары, а стат-список
     инкремента по этому перечню совпадает со стат-списком полного diff
     от базы.
   - R1-F2 (minor, требование 3): строка отсутствия получила оговорку
     `STEP_WORKDIR_MISSING_HINT` — она называет фактический каталог
     («дерево» здесь — рабочий каталог шага). Сам ярлык «в дереве — »
     переписан не был намеренно: требование 3 велит сохранить строку
     дословно, а залоченная планка AC-3
     (`acceptance_tests/test_ac3_missing_everywhere_named_reason.py:28-29`)
     сверяет этот литерал регуляркой — правка ярлыка покрасила бы планку,
     а её изменение — эскалация, не правка. Оговорка идёт ПОСЛЕ
     закрывающей скобки, форма строки поэтому прежняя, и приписана ко
     всем трём исходам чтения с диска (`FileNotFoundError`, `OSError`,
     `UnicodeDecodeError`) — класс, не экземпляр.
   - R1-F3 (minor, требование 9): `from_worktree` теперь собирается по
     `note == WORKTREE_NOTE`, то есть несёт только то, что действительно
     прочитано из рабочего дерева ПУЛЬТА (сегодня — форма вердикта); три
     артефакта задачи из него ушли, их источник журнал получает полем
     `artifact_source` фактическим именем.

## Влияние на систему

- **Что затрагивается за пределами правки.** `git_diff_part` — общий с
  `orchestrator/fsm.py::_snapshot_split_assessment` и
  `orchestrator/advance_gates/capacity.py` (гейт ёмкости): его сигнатура и
  поведение не меняются ни на байт, новый pathspec собирает вызывающий
  код. `EMPTY_DIFF_TEXT` — тот же общий признак «diff пуст, а не
  несобран», которым уже пользуется гейт ёмкости; новая ветка отката
  читает его, а не переопределяет.
- **Инварианты рядом.** Запись 28 `docs/invariants.md`
  («артефакто-чтения оркестратора ветко-корректны») требованием 1
  распространяется на ревью-пакет — ослабления нет, есть ещё одно место
  чтения, приведённое к инварианту; сам реестр не правлю (вне зон,
  правка docs — отдельный MR Оператора). Инвариант 33 («тесты не пишут в
  настоящий репозиторий пульта») и инвариант 37 (`PATCHED_ATTRS` покрывает
  `WORKTREES`) — прямо задеты: откат чтения переезжает с `config.ROOT` на
  `config.WORKTREES`, поэтому `ReviewPackageTest` получает патч
  `WORKTREES`, а новые тесты живут на `tests/sandbox.py::RealGitSandbox`
  (патч всех `ALL_CONFIG_ATTRS`), как того и требует AC-11.
- **Гейты и алерты.** Логика алерта в `runner._build_prompt` не
  меняется: тот же `raise_diff_not_collected_alert`/
  `close_diff_not_collected_alerts`, тот же порядок (закрытие — после
  сборки пакета). Ни один гейт, лимит и guard-проверка не ослабляются.
- **Как откатить.** Revert одного merge-коммита ветки: правка целиком
  внутри `orchestrator/review.py` и `tests/`, схема БД, формат журнала
  (новые поля — добавка к строке detail, не замена) и артефакты задач не
  меняются.

## Риски

- Пакет итерации > 1 при пустом инкременте делает до двух лишних пар
  вызовов git (инкремент + полный diff от базы). Плата — за то, чтобы
  отличить дефект от штатной пустоты; на итерации 1 и при непустом
  инкременте лишних вызовов нет.
- `not_collected` несёт причину отката, не будучи сбоем сборки —
  сознательная плата за неизменность `runner.py` (см. «Подход»).
  Строка журнала при этом честная: откат печатается своей
  формулировкой, слово «не собран» остаётся за настоящими сбоями git.
- Путь, который правили и разработчик, и подтяжка main, попадает в
  инкремент целиком от базы до головы — принятая граница способа
  (SPEC «Не входит»), не дефект реализации.

## Предложения системе

- Замечание ревью может просить поменять формулировку, которую ДОСЛОВНО
  фиксируют и SPEC, и залоченная планка (здесь — R1-F2 против требования
  3 и `acceptance_tests/test_ac3_missing_everywhere_named_reason.py`).
  Штатных ходов у разработчика два, и оба хуже дела: `rejected` (замечание
  по делу, ревьювер прав) либо эскалация на правку планки ради minor. Здесь
  нашёлся третий — дописать оговорку, не трогая литерал, — но он частный:
  класс «ревьювер не видит, что просит менять залоченное» стоит называть
  в скиле ревьювера или в самом реестре отдельным статусом.
- `orchestrator/review.py::review_package` вынужденно зовёт
  `runner.role_cwd_path` отложенным импортом (второй такой случай в одной
  функции после `fsm`): «рабочий каталог шага по (task_id, target)» —
  знание уровня `workspace`/`config`, а живёт в `runner`, который тянет
  за собой половину пакета. Место для отдельной задачи: вынести формулу
  в модуль-лист, как `artifact_source.resolve` вынес «ветку-источник».
- Инвариант 37 (`PATCHED_ATTRS` покрывает `WORKTREES`) сторожит только
  наследников `tests.sandbox.TmpRootTest`. Классы вроде
  `tests/test_review_package.py::ReviewPackageTest` — обычные
  `unittest.TestCase` со своим ad-hoc набором `mock.patch.object(config,
  …)`, и скан их не видит: пока эта задача не добавила им `WORKTREES`,
  любое чтение/запись по этому пути уходило в `.artel/worktrees`
  НАСТОЯЩЕГО репозитория пульта, и ни один гейт этого не замечал (в
  одном из прогонов по ходу задачи там остался каталог `T001/`).
  Класс проблемы — «сторож смотрит на подкласс песочницы, а не на факт
  подмены пути».
