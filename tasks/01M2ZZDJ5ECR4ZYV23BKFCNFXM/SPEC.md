# SPEC: Ревью-пакет: артефакты из артефактной ветки и инкрементальный diff по якорю вердикта

## Контекст

Ревью-пакет — вход ревьювера, который собирает оркестратор, а не сам
агент. Сегодня он не доносит до ревьювера ни артефакты задачи, ни
честный инкремент правок.

Первое: `orchestrator/review.py` читает SPEC.md, PLAN.md и REVIEW.md
задачи из КОДОВОЙ ветки, а при промахе — из главной копии пульта. С
11.09 эти файлы живут в артефактной ветке задачи и в каталоге
`tasks/<id>/` рабочего каталога шага, то есть ни одного из двух
источников пакета больше нет: у всех 25 задач с ≈11.09 по 01M2ZNTHSN
обе секции промпта — «(не показан: в ветке — path does not exist; в
дереве — файл не найден)». Ревьюверы дочитывают файлы с диска сами,
гейт плана держится на их инициативе, а не на пакете.

Второе: база инкрементального diff (итерация > 1) берётся как
ПРЕДПОСЛЕДНЯЯ запись «sha зафиксирован» журнала — исходя из того, что
между двумя входами в `review` ровно два перехода. Сегодня записей
больше: фиксация пишется на каждом переходе, на каждом автокоммите
артефактов и на чекпоинте. У задачи 01M2ZNTHSN вердикт итерации 1
вынесен на коде 550c53cc, а предпоследняя запись перед входом в review
итерации 2 — 23ca007b, голова ветки после автокоммита подтяжки main:
пакет обеих задач 20.09 сообщил «строк diff 0, diff инкрементальный,
итерация 2» при пяти правленых файлах. Алерт при этом не срабатывает —
diff собран, просто пуст. Класс ловили в T082 и T087; ревьювер лечит
его руками по sha из своего же REVIEW итерации 1.

Третье: даже с верной базой в диапазон попадают коммиты подтяжки main —
честный инкремент это правки разработчика за итерацию, а не изменения
главной ветки.

## Требования

1. Артефакты задачи в пакете. SPEC.md, PLAN.md и REVIEW.md задачи
   читаются сборщиком `orchestrator/review.py` из артефактной ветки
   задачи — той, которую отдаёт общий резолвер источника артефактов,
   тем же приёмом, что уже применяет бриф разработчика: сначала ветка,
   при отсутствии файла в ней — каталог `tasks/<id>/` РАБОЧЕГО КАТАЛОГА
   ШАГА (worktree задачи для self-target, workspace target'а — для
   внешнего). Кодовая ветка задачи и главная копия пульта источниками
   этих трёх артефактов больше не являются.

2. Шаблон вердикта. Источник части «форма вердикта» не меняется: она
   читается как сегодня.

3. Именование источника. Заголовок части пакета называет источник
   артефакта (артефактная ветка или рабочий каталог шага) — тем же
   приёмом, что сегодня даёт пометка о рабочем дереве. Файла нет ни в
   ветке, ни в рабочем каталоге шага — прежняя именованная строка «(не
   показан: в ветке — …; в дереве — …)», где обе причины фактические
   (ветка-источник и рабочий каталог шага), без абсолютного пути в
   тексте.

4. База инкрементального diff — якорь вердикта. Sha кодовой ветки, на
   котором вынесен предыдущий вердикт, ищется так: последняя по журналу
   задачи запись перехода `state -> in_dev` с detail «замечания ревью,
   итерация …»; база — поле `код=` ближайшей СЛЕДУЮЩЕЙ за ней записи
   «sha зафиксирован». «Предпоследняя запись журнала» базой быть
   перестаёт. Якорь однозначен по построению: такой detail пишет ровно
   одно место кода (переход `review -> in_dev` по вердикту
   `changes_requested`), а фиксация идёт непосредственно следующей
   записью того же перехода — поэтому лишние записи фиксации между
   итерациями (автокоммит артефактов, чекпоинт, подтяжка main) на выбор
   базы не влияют.

5. Деградация без якоря. Якоря в журнале нет (задача заведена до этой
   правки; вход в `review` не через вердикт) либо `код=` следующей за
   ним записи не распознан — прежняя деградация: полный diff от главной
   ветки с именованной причиной в тексте пакета, как сегодня при
   ненайденной базе. Трейсбека нет.

6. Содержимое инкремента. Инкрементальный diff несёт правки
   разработчика за итерацию и не несёт изменений main, пришедших
   коммитами подтяжки: diff от базы вердикта до головы ветки
   ограничивается путями, которые тронули СОБСТВЕННЫЕ коммиты ветки с
   момента базы (обход по первому родителю без merge-коммитов);
   действующее исключение каталога `tasks/<id>/` сохраняется, список
   изменённых файлов (`--stat`) собирается по тому же правилу, что и
   показанный diff. Путь, который правили и разработчик, и подтяжка,
   показывается целиком от базы до головы — изменения main по такому
   пути остаются в diff (принятая граница способа, см. «Не входит»).
   Заметка под diff'ом называет базу и голову ветки, как сегодня.

7. Откат при пустом инкременте и непустых правках. Инкрементальный diff
   пуст, а diff кодовой ветки от базы вердикта до головы (без каталога
   `tasks/<id>/`) не пуст — пакет показывает этот полный diff от базы
   вердикта, называет причину отката дословно «инкрементальный diff пуст
   при непустых правках — показан полный» в заметке под diff'ом и в
   записи журнала о сборке пакета, и по тому же каналу, которым сегодня
   доносится «diff не собран», заводится алерт `kind=warning` с той же
   причиной в тексте.

8. Пустой инкремент без правок. Инкрементальный diff пуст И diff от
   базы вердикта пуст — это штатный исход: алерт не заводится, ранее
   открытый алерт того же источника закрывается прежним механизмом, а
   заметка пакета прямо говорит, что правок с предыдущего вердикта нет.

9. Журнал сборки пакета. Запись «ревью-пакет собран» дополняется
   источником артефактов задачи (артефактная ветка / рабочий каталог
   шага / не найден) и базой инкремента (sha) — чтобы дефект такого
   класса был виден по журналу, а не по промпту.

10. Тесты. Поведение требований 1–9 закрывается тестами в `tests/`
    (перечень — в критериях приёмки). Существующие
    `tests/test_review_package.py`, `tests/test_review_freshness.py`,
    `tests/test_fsm_review_rework_sha_gate.py` остаются зелёными;
    ожидания, привязанные к «предпоследней записи», обновляются
    перечнем в PLAN.

## Критерии приёмки

AC-1. SPEC.md, PLAN.md и REVIEW.md задачи есть в её артефактной ветке и
отсутствуют в кодовой — собранный ревью-пакет несёт тела всех трёх
(заголовок части с размером и sha256), а не строку «(не показан: …)».

AC-2. Тех же файлов нет в артефактной ветке, но они есть в каталоге
`tasks/<id>/` рабочего каталога шага — пакет несёт их тела, а заголовок
части называет источником рабочий каталог, отличая его от артефактной
ветки.

AC-3. Файла нет ни в артефактной ветке, ни в рабочем каталоге шага —
часть пакета несёт именованную строку «(не показан: …)» с обеими
фактическими причинами (ветка и рабочий каталог шага); абсолютного пути
в тексте нет.

AC-4. Часть «форма вердикта» попадает в пакет тем же источником и тем
же текстом, что до задачи.

AC-5. Между вердиктом итерации 1 и входом в `review` итерации 2 журнал
задачи несёт лишние записи «sha зафиксирован» (автокоммит артефактов,
чекпоинт, подтяжка main) — базой инкрементального diff выбран `код=`
записи фиксации, следующей за переходом `state -> in_dev` с detail
«замечания ревью, итерация 1», а не предпоследняя запись журнала.

AC-6. Журнал задачи не несёт ни одного перехода `state -> in_dev` с
detail «замечания ревью, итерация …» либо `код=` следующей за ним
записи не распознан, а итерация > 1 — пакет остаётся на полном diff от
главной ветки и называет причину текстом; исключения не возникает.

AC-7. С базы вердикта в ветку задачи пришли и правка разработчика (файл
A), и подтяжка main merge-коммитом (файл B, разработчиком не тронут) —
инкрементальный diff пакета несёт изменения A и не несёт изменений B;
заметка под diff'ом называет базу (sha вердикта) и голову ветки.

AC-8. Инкрементальный diff пуст, а diff кодовой ветки от базы вердикта
до головы (без каталога `tasks/<id>/`) не пуст — пакет несёт полный
diff от базы вердикта; заметка под diff'ом и запись журнала «ревью-пакет
собран» несут причину «инкрементальный diff пуст при непустых правках —
показан полный»; по завершении шага сборки промпта ревьювера (не только
самой функции пакета) алерт `kind=warning` с той же причиной в тексте
остаётся открытым.

AC-9. Инкрементальный diff пуст И diff от базы вердикта пуст — текст
пакета прямо сообщает, что правок с предыдущего вердикта нет; алерт не
заводится, а открытый ранее алерт того же источника закрывается.

AC-10. Запись журнала «ревью-пакет собран» на итерации > 1 несёт
источник артефактов задачи (артефактная ветка / рабочий каталог шага /
не найден) и базу инкремента (sha); на итерации 1 та же запись несёт
источник артефактов и не несёт базы инкремента.

AC-11. Прогон `tests/test_review_package.py`,
`tests/test_review_freshness.py`,
`tests/test_fsm_review_rework_sha_gate.py` — зелёный; новые тесты
задачи в `tests/` пользуются общей песочницей `tests/sandbox.py` и не
меняют настоящий репозиторий пульта.

## Оценка объёма и деление

Прогноз диффа: 20 КиБ.

Сработавшие сигналы:
- «число критериев приёмки» — 11 при пороге `SPLIT_SIGNAL_AC_COUNT` =
  10. Критерии дробны не из-за объёма работы, а из-за числа ВЕТОК одного
  и того же поведения (источник артефакта: ветка / рабочий каталог /
  нет нигде; инкремент: якорь / деградация / откат / штатная пустота) —
  каждая ветка обязана иметь свой тест, слить их значило бы отдать
  test_author непроверяемую формулировку.
- «число затрагиваемых модулей/файлов» — в тексте SPEC упомянуты 8
  путей вида `orchestrator/*.py` при пороге `SPLIT_SIGNAL_ZONE_FILES` =
  5, но правятся из них ровно два (`orchestrator/review.py`,
  `orchestrator/role_prompt.py`); остальные шесть перечислены в
  «Материалы» и «Не входит» как чтение — сигнал считает упоминания, а
  не зоны.

Не сработали: `budget_usd` = 35 при пороге `SPLIT_SIGNAL_BUDGET_USD` =
60; формулировок неопределённости нет; ни один путь зон не встречается
в `docs/invariants.md`; прогноз диффа 20 КиБ ниже половины потолка
гейта ёмкости.

Решение — монолит. Обе половины задачи (источник артефактов и база/
содержимое инкремента) живут в одной функции сборки пакета
`review_package` одного файла `orchestrator/review.py` и сходятся в
одной строке журнала «ревью-пакет собран» (требование 9 называет и
источник артефактов, и базу инкремента). Нарезка резала бы одну зону
поперёк — запрещённый скилом случай: часть без своего куска зоны
`orchestrator/review.py` не мержима отдельно, а две части, правящие ту
же функцию, дадут конфликт правок и второй прогон того же ревью. Объём
работы этого не требует: правка — одна функция чтения артефактов, одна
функция выбора базы, фильтр путей инкремента и строка журнала.

Бюджет $35 — рамка ТЗ; при шагах analyst ($2) + test_author ($6) +
developer ($3.5) + две итерации ревью ($2.3 каждая) + доработка ($3.5)
она перекрывает задачу с запасом.

## Не входит

- Сторож роли `docs/reference/role-home/claude/settings.json` (запрет
  `python3 -c` и env-префикса) — отдельная строка копилки.
- Изменение состава ревью-пакета сверх SPEC/PLAN/REVIEW/ANSWER, потолок
  размера пакета и деление его на части.
- Правка брифов других ролей: `orchestrator/brief.py` — только чтение,
  образец приёма «ветка → диск» и источник резолва.
- Правка `orchestrator/artifact_source.py`: резолвер ветки-источника
  переиспользуется как есть.
- Правка `orchestrator/store.py` (журнал и фиксация читаются как есть),
  `orchestrator/alerts.py` (канал алерта зовётся как есть),
  `orchestrator/runner.py` (точка вызова алерта и журналирования пакета
  не меняется), `orchestrator/fsm_advance.py` (переход, пишущий якорь,
  не меняется).
- Правка `templates/REVIEW.md` и `skills/review-checklist.md`: описание
  капкана в скиле остаётся; правка скила возможна только приложением к
  PLAN.md для Оператора, если разработчик сочтёт нужным.
- Правка артефактов чужих задач: `tasks/<id>/` читается пакетом, не
  правится.
- Полное отделение изменений main от правок разработчика по файлу,
  который тронули оба: такой файл показывается целиком от базы до
  головы (требование 6). Разрешение конфликтов подтяжки, живущее в
  merge-коммитах, в инкремент не попадает — при пустом результате его
  ловит откат требования 7.
- Ветка задачи, подтянувшая main перемоткой (fast-forward), а не
  merge-коммитом: собственных коммитов у такой ветки нет, отделить
  правки разработчика нечем — поведение остаётся прежним.
