# ТЗ: Автогейт acceptance по политике gates.yaml (ADR-0007)

## Контекст

ADR-0007 (принят 28.08): политика гейтов в gates.yaml, первый и пока
единственный автоматизируемый гейт — acceptance. Статистика: 0 reject
за 65 прохождений, на acceptance ни одной находки Оператора сверх
пойманного тестами; при N=5 подтверждение зелёного — главный
потребитель внимания. Дефолт всех гейтов — manual; kill-switch —
правка gates.yaml.

## Решение (ADR-0007, п.2–3)

1. gates.yaml получает секцию политики гейтов:
   `gates: {spec_gate: manual, acceptance: auto, merge_gate: manual}`
   (формат — решение developer в PLAN, консистентный с существующим
   содержимым файла). Неизвестное значение или отсутствие секции =
   manual (fail-closed к ручному).
2. Переход review -> acceptance: если политика acceptance = auto,
   оркестратор сам исполняет проверку условий автопрохода — ВСЕ
   обязательны:
   а) каталог приёмочных тестов задачи существует и непуст, среди
      разметки 0 manual и 0 skip критериев;
   б) прогон приёмочных тестов задачи в worktree ветки — зелёный;
   в) полный набор tests/ в worktree ветки — зелёный;
   г) бюджет задачи не превышен; программные пороги (A1) не пробиты;
   д) вердикт REVIEW текущей итерации — approved (фиксируется явной
      проверкой, хотя переход и так её требует).
   Все условия выполнены -> гейт проходится автоматически: переход
   acceptance -> merge_gate тем же действием, журнал actor=autogate
   с перечнем выполненных условий, вывод команды явно говорит
   «acceptance пройден автогейтом (политика gates.yaml)».
3. Любое условие не выполнено (есть manual/skip, что-то красное,
   бюджет, политика manual, gates.yaml не читается) -> поведение
   СЕГОДНЯШНЕЕ: задача останавливается в acceptance и ждёт Оператора;
   причина «почему не автогейт» — в выводе и журнале (одной строкой).
4. Инвариант 7 в docs/invariants.md переформулируется по ADR-0007
   («approve/reject Оператора ЛИБО автогейт по политике gates.yaml»);
   текст строки готовит developer в PLAN, вносит Оператор при мерже.
   Тест ManualGatesNeedTheOperatorTest корректируется ТОЛЬКО в этих
   рамках: при политике manual (дефолт песочниц) поведение прежнее
   байт-в-байт — тест обязан остаться зелёным без ослабления своих
   сценариев; новый сценарий автогейта — отдельным тестом.
5. Инвариант 18 не меняется: автогейт — не действие auto-цикла, а
   исполнение объявленной политики в точке перехода; auto по-прежнему
   не зовёт approve/reject. merge_gate и spec_gate от этой задачи
   не получают никакого auto-пути (ADR-0007 п.4–5).

## Границы

- orchestrator/ (fsm и смежные), gates.yaml (секция политики — правка
  файла в задаче разрешена ЭТИМ ТЗ как исполнение ADR-0007; сам файл
  остаётся в PROTECTED), тесты, карта.
- Не ослаблять существующие тесты/гейты/инварианты сверх рамок п.4
  (ADR-0002 + явная санкция ADR-0007).
- Дефолт в свежесозданных песочницах/инсталляциях — manual для всех
  гейтов; auto для acceptance включается значением в gates.yaml
  реального пульта (коммитится в этой же задаче).

## Не входит

- Автогейт merge_gate (ждёт детекторов деградации, ADR-0007 п.4)
  и spec_gate (без горизонта, п.5).
- Изменение механики reject/эскалаций.
- UI/status-доработки сверх отличимой строки журнала.

## Приёмка (минимум)

- Политика acceptance=auto, все условия выполнены -> переход
  review -> acceptance -> merge_gate без операторского approve;
  журнал несёт actor=autogate и перечень условий.
- Есть manual-критерий (или skip, или красный тест, или превышен
  бюджет) -> задача стоит в acceptance, ждёт Оператора; причина
  в журнале/выводе.
- Политика manual (или секции нет, или gates.yaml нечитаем) ->
  поведение байт-в-байт прежнее.
- merge_gate и spec_gate автопути не имеют ни при какой политике
  этой задачи.
- ManualGatesNeedTheOperatorTest зелёный (при manual-политике его
  сценарии не изменились); новый тест автогейта зелёный; полный
  набор зелёный.
