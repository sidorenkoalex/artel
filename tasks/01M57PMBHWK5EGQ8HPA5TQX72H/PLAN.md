# PLAN: Несколько проектов: проект в report и алерты пульта в наблюдении внешнего проекта

## Подход
Правка двух модулей зоны: `orchestrator/report.py` и `orchestrator/watch.py`;
`orchestrator/catalog.py` не правится (метка в `status` уже есть).

- `report.py`: один источник проекта строки задачи — `_project(row)`
  (NULL и строка без ключа `target` → `config.DEFAULT_TARGET`, как у
  `_tile_html` и `status`); метка ` [<проект>]` — `_project_suffix`/
  `_project_label` — ставится сразу за id в очереди гейтов, закрытых
  задачах, разрезе задач, трении и шагах test_author. На плитке скобки
  стоят снаружи элемента `tile-project`, собственный текст элемента — ровно
  имя проекта, `tile-id` — ровно id. Сигнатуры, которые зовут тесты
  (`_friction_by_task`, `_metrics_html`, `_tokens_by_task`, `_tile_html`),
  не меняются; `_test_author_html`/`_test_author_row_html`/`_alerts_html`
  получили необязательный параметр с прежним значением по умолчанию.
- Панель алертов (ANSWER-2, п.2): проекты — имена `targets.yaml`
  (`_declared_projects`; негодный/отсутствующий файл — пустой набор) и
  проекты задач выборки. Метка `[<проект>]` — у алерта, чей `target` —
  проект, отличный от артели; значение, не названное ни проектом, ни id
  задачи БД, печатается в скобках как есть; NULL, артель и id задачи —
  прежний вид строки.
- Задача с `tasks.target` NULL (ANSWER-2, п.1) во всех строках `report` —
  как задача артели, без метки и без `[None]` (`_project`).
- Сигнатуры `_gate_ratio`/`_metrics_html` прежние (ANSWER-2, п.3):
  `tests/test_report.py:87-111, 185-203` не меняются.
- «Экономика» и доля acceptance: если разных проектов в выборке задач
  (после замены NULL на артель) больше одного — по строке на проект с
  префиксом `<проект>: `, значения считаются по задачам проекта и записям
  журнала его задач (окно — последние `GATE_RATIO_WINDOW` записей проекта);
  иначе — прежние строки побайтно (те же `store.total_spent`/
  `total_estimate`).
- `watch.py`, `_observation_events`: в набор допустимых `target` алерта
  добавлен `None`; поле проекта у такого алерта — `-`. Позиция «оповещено»
  уже по наблюдению (`next_alert` пишется в строку наблюдения), поэтому
  каждое наблюдение получает алерт ровно один раз. `observe events` идёт
  через ту же функцию (требование 6). Обычный `watch` без наблюдения не
  тронут.

## Шаги
1. `report.py`: метки проекта в строках задач и алертов, разбивка метрик по
   проекту. `watch.py`: доставка алертов с `target` NULL каждому наблюдению
   с `-` в поле проекта. Регенерация `docs/codebase-map.md`.

## Влияние на систему
- Меняется вывод дозора наблюдения и `observe events`: алерт с `target`
  NULL теперь выводится каждому наблюдению — цель задачи (раздел SPEC
  «Меняемое поведение»). Существующие тесты наблюдения зелены без правки.
- `report` у базы только артели — побайтно прежний (планка AC-8).
- Гейты, лимиты, guard, инварианты не затрагиваются; БД не пишется
  (кроме прежнего `token_rate_divergence`). Откат — revert merge-коммита.

## Риски
- Id задачи для правила метки алерта — из задач БД (`all_tasks`): алерт с
  `target` = id задачи, строки которой в БД нет, получит метку как
  неизвестное значение (ANSWER-2, п.2 — печать как есть).

## Предложения системе
- Бэклог (требование 9 SPEC, ANSWER-1 п.1): алерты уровня пульта и алерты
  проекта артели смешаны под одним `target` = `config.DEFAULT_TARGET` —
  стоп-кран `orchestrator/alerts.py:238`, `orchestrator/doctor/orphans.py:185`,
  `doctor/map_growth.py`, `doctor/recovery.py`, `doctor/suite_duration.py`;
  перевести алерты уровня пульта на `target` NULL, чтобы наблюдение
  внешнего проекта получало их без доступа к алертам проекта артели.
- `suite-run` одной задачи отказывает, пока идёт прогон другой задачи
  машины, и не умеет встать в очередь — шагу приходится повторять команду
  вручную.
