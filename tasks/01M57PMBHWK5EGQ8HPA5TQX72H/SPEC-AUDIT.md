## Пути обхода гейтов
- Эталон AC-8 «вывод до правки» можно получить в тесте вызовом того же кода в момент прогона (сравнить `report`/`status`/`watch` с ними же) — тест зелёный при любой правке. SPEC и AC-8 не требуют, чтобы эталон хранился литералом (или файлом), снятым на коде до правки; без этого треб. 7 проверяется тавтологией (вердикт, п.4).
- Через треб. 3 буквально: считать «число разных `tasks.target`» с NULL как отдельным значением — у базы артели с задачей `target` NULL появится разбивка со строкой `None`; гейт «у артели тексты прежние» это поймает, только если фикстура AC-8 содержит NULL-задачу (вердикт, п.1).
- Иных путей не нашёл: требование «не править `artel.py`/`alerts.py`/`store.py`» держит гейт зон.

## Вердикт
concerns — SPEC можно вести дальше, четыре отклонения решаются Оператором на гейте:

1. Треб. 3 / AC-4 (SPEC, «Требования» п.3: «число проектов — число разных `tasks.target`»): NULL в `tasks.target` возможен (`orchestrator/schema.py:115`), его создаёт долгоживущий тест (`tests/test_01m563e1sh9sb63s2mw4a9b82n_project_label.py:79`), а `orchestrator/report.py:554-555` и `orchestrator/catalog.py:973` считают его артелью. Предпосылка решения Оператора 4 «NULL у задач не бывает» с кодом не сходится; при буквальном счёте база «артель + NULL» даёт разбивку. Предлагаю: в треб. 3 считать проект задачи как `target or DEFAULT_TARGET` (как в треб. 1), в AC-4 добавить задачу с NULL в базу «только артели».
2. AC-2 (треб. 2): требование оставляет без метки строку панели report у алерта с `target` = id задачи (`orchestrator/alerts.py:116-120`), но AC-2 проверяет такой алерт только в дозоре. Мутация «метка у любого `target` ∉ {None, `DEFAULT_TARGET`}» (`[01M…]` у attention-алерта) проходит AC-2. Строка алерта с `target` = id задачи артели в треб. 2 тоже не названа. Предлагаю: в AC-2 проверить строку панели report у алерта с `target` = id задачи `sled` и id задачи артели — без метки.
3. AC-3 (треб. 3, окно `GATE_RATIO_WINDOW`, `orchestrator/report.py:58, 362`): мутацию «взять глобальные последние 10 записей, затем разбить по проекту» критерий не ловит, если записей перехода не больше 10. Предлагаю: в AC-3 требовать фикстуру, где у каждого проекта больше `GATE_RATIO_WINDOW` записей перехода acceptance вперемешку, и окно каждого проекта отличается от среза глобального окна.
4. AC-8 (треб. 7): не сказано, что эталон хранится литералом/файлом, снятым на коде до правки; эталон, построенный тем же кодом при прогоне, — тавтология. Предлагаю дописать это в AC-8; заодно назвать нормализацию зависящих от времени частей HTML `report` (окна по дате, `orchestrator/report.py:834-842`).
