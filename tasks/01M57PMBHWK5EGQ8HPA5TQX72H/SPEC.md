# SPEC: Несколько проектов: проект в report и алерты пульта в наблюдении внешнего проекта

## Контекст
Пульт ведёт задачи нескольких проектов (артель и внешний, например sled);
`status` уже помечает задачу внешнего проекта меткой `[<проект>]`
(`orchestrator/catalog.py:973-974`). `report` метит проект только на плитке
борда и в другом виде (`orchestrator/report.py:553-558`, имя без скобок), а
очередь гейтов, закрытые задачи, разрез задач, трение и панель алертов
проект не показывают; итоги «Экономика» и доля acceptance считаются суммой
по всем проектам. Дозор наблюдения (`orchestrator/watch.py:303-308`) не
доставляет ни одному наблюдению алерты с `target` NULL — алерты уровня
пульта, не привязанные к проекту, — и Оператор, ведущий задачу внешнего
проекта, о них не узнаёт. Решения по неясностям ТЗ — `ANSWER-1.md`.

## Требования

1. `report`: в каждой строке, которая представляет задачу, — плитка борда
   (`_tile_html`), очередь гейтов (`_gate_queue_html`), закрытые задачи
   (`_closed_tasks_html`), разрез задач (`_tokens_by_task`), значения
   трения по задачам (`_friction_html`), — у задачи внешнего проекта сразу
   за id стоит метка `[<проект>]`, как в `status`. У задачи артели
   (`target` равен `config.DEFAULT_TARGET` или NULL) метки нет, вид строки
   прежний. Плитка внешнего проекта меняет нынешний текст `<проект>` на
   `[<проект>]` (ANSWER-1, п.3).
2. `report`, панель незакрытых алертов (`_alerts_html`): у алерта с
   `target` внешнего проекта выводится метка `[<проект>]`; у алерта
   артели и алерта с `target` NULL вид строки прежний (требование 3 ТЗ:
   смешение проектов в зоне `report.py`).
3. `report`, блок «Экономика» (`$/задачу (done)`, суммарный расход,
   суммарная верхняя оценка) и блок «Доля acceptance: автогейт vs
   Оператор» (за всю историю и за последние 10 задач): если в выборке
   задач больше одного проекта — значения даны с разбивкой по проекту
   (по строке на проект с его именем); если проект один — вывод блоков
   прежний (ANSWER-1, п.2).
4. Дозор наблюдения: алерт с `target` NULL (алерт уровня пульта,
   ANSWER-1, п.1) доставляется каждому активному наблюдению, независимо
   от проектов его задач. Правило «оповещено» — по наблюдению: каждое
   наблюдение отмечает свою позицию, одно наблюдение не получает один и
   тот же алерт повторно, отметка одного наблюдения не снимает доставку
   другому. Доставка алертов с `target` = `config.DEFAULT_TARGET` и
   алертов по задачам/проектам набора — прежняя.
5. В строке дозора наблюдения у алерта с `target` NULL поле проекта
   печатается `-` (как секция триггеров `status`, `catalog.py:990`;
   ANSWER-1, п.4).
6. У базы с задачами только артели тексты `status`, `report` и `watch`
   прежние; это фиксируется тестами, написанными до правки кода
   (требование 4 ТЗ).
7. Тесты детерминированы и без сети: задачи артели и учебного внешнего
   проекта в одной БД, два наблюдения (требование 5 ТЗ).
8. Смешение алертов уровня пульта и алертов проекта артели под одним
   `target` = `config.DEFAULT_TARGET` (стоп-кран `alerts.py:238`,
   `doctor/orphans.py:185` рядом с `doctor/map_growth.py`,
   `doctor/recovery.py`, `doctor/suite_duration.py`) в этой задаче не
   устраняется: разработчик записывает его строкой для бэклога в раздел
   «Предложения системе» PLAN.md (ANSWER-1, п.1).

## Критерии приёмки

AC-1. В БД с задачей артели и задачей внешнего проекта `sled` HTML `report` в плитке борда, очереди гейтов, списке закрытых задач, разрезе задач и значениях трения содержит у задачи `sled` текст `[sled]` сразу за её id, а у задачи артели — id без метки проекта.

AC-2. В той же БД панель незакрытых алертов `report` показывает у алерта с `target` `sled` метку `[sled]`, а строка алерта с `target` артели и строка алерта с `target` NULL — без метки, в прежнем виде.

AC-3. В БД с задачами двух проектов блок «Экономика» `report` (`$/задачу (done)`, суммарный расход, суммарная верхняя оценка) и блок доли acceptance «автогейт vs Оператор» дают значения отдельно по каждому проекту, и значение каждого проекта считается только по его задачам.

AC-4. В БД с задачами только одного проекта блоки «Экономика» и доли acceptance `report` совпадают с выводом до правки.

AC-5. При двух активных наблюдениях (одно на задачу артели, другое на задачу `sled`) алерт с `target` NULL выводится дозором каждого наблюдения ровно один раз, в том числе при повторных циклах дозора каждого из них.

AC-6. Строка дозора наблюдения у алерта с `target` NULL несёт в поле проекта `-`.

AC-7. В БД с задачами только артели тексты `status`, `report` и `watch` совпадают с выводом до правки (эталон зафиксирован тестом до правки кода).

## Оценка объёма и деление

Прогноз диффа: 30 КиБ

Сработавший сигнал — число файлов/модулей, упомянутых в тексте SPEC
(`SPLIT_SIGNAL_ZONE_FILES`). Правится по ТЗ три модуля зоны
(`orchestrator/report.py`, `orchestrator/watch.py`, при необходимости
`orchestrator/catalog.py`) и `tests/`; `orchestrator/alerts.py`,
`orchestrator/doctor/*`, `orchestrator/store.py` и прочие пути названы
только как адреса мест заведения алертов и образцов вывода — они вне зон
и не правятся. Критериев приёмки 7, рамка $25.

Обоснование монолита: части связаны общим эталоном «у артели тексты
прежние» (требование 6, AC-7), фиксируемым тестом до правки сразу для
`status`, `report` и `watch`; деление на «report» и «watch» дало бы две
задачи по ~$25 с дублем эталонного теста при объёме, который укладывается
в одну рамку. Решение — за Оператором на гейте SPEC.

  строка в «Предложения системе» PLAN (требование 8).

  actor=operator по дням, тренд трения, калибровка курса токенов, рост
  карты (ANSWER-1, п.2).
- Правка `orchestrator/artel.py`, `orchestrator/alerts.py`,
  `orchestrator/store.py`, `docs/triggers.md`, `docs/backlog.md` — только
  чтение по ТЗ.
- Обычный `watch` без наблюдения (`watch.py:468-473`) — ТЗ говорит о
  дозоре наблюдения.
