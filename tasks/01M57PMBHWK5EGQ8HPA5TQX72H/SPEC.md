# SPEC: Несколько проектов: проект в report и алерты пульта в наблюдении внешнего проекта

## Контекст
Пульт ведёт задачи нескольких проектов (артель и внешний, например sled);
`status` уже помечает задачу внешнего проекта меткой `[<проект>]`
(`orchestrator/catalog.py:973-974`). `report` метит проект только на плитке
борда и в другом виде (`orchestrator/report.py:553-558`, имя без скобок), а
очередь гейтов, закрытые задачи, разрез задач, трение, шаги test_author и
панель алертов проект не показывают; итоги «Экономика» и доля acceptance
считаются суммой по всем проектам. Дозор наблюдения
(`orchestrator/watch.py:303-308`) не доставляет ни одному наблюдению — в
том числе наблюдению артели — алерты с `target` NULL (алерты уровня пульта,
не привязанные к проекту), и Оператор, ведущий задачу внешнего проекта, о
них не узнаёт. Решения по неясностям ТЗ — `ANSWER-1.md` и решения Оператора
при возврате со `spec_gate` (итерация 2 SPEC; визит 2 аудита — итерация 3).

## Требования

1. `report`: в каждой строке, которая представляет задачу, — плитка борда
   (`_tile_html`), очередь гейтов (`_gate_queue_html`), закрытые задачи
   (`_closed_tasks_html`), разрез задач (`_tokens_by_task`), значения
   трения по задачам (`_friction_html`), строки блока «Шаги test_author»
   (`report.py:965`), — у задачи внешнего проекта в отрендеренном тексте
   строки сразу за id стоит метка `[<проект>]`, как в `status`. У задачи
   артели (`target` равен `config.DEFAULT_TARGET` или NULL) метки нет, вид
   строки прежний. На плитке метка — вложенная разметка: внутренний
   элемент сохраняет собственный текст ровно `<проект>`, скобки стоят
   снаружи него (`[<span>sled</span>]`); элемент id плитки по-прежнему
   несёт ровно id задачи (ANSWER-1, п.3; решение Оператора 1).
2. `report`, панель незакрытых алертов (`_alerts_html`): у алерта с
   `target` внешнего проекта выводится метка `[<проект>]`; у алерта
   артели и алерта с `target` NULL вид строки прежний (требование 3 ТЗ:
   смешение проектов в зоне `report.py`). Алерт, привязанный к задаче
   внешнего проекта (`target` = id задачи, например `attention`,
   `alerts.py:116-120`), доставляется дозором наблюдения, в набор
   которого входит эта задача, как сейчас (решение Оператора 6); строка
   такого алерта в панели `report` метки проекта не несёт: метка ставится
   только алерту, чей `target` — имя внешнего проекта, а не любому
   `target` вне {NULL, `config.DEFAULT_TARGET`} (решение Оператора при
   возврате, визит 2, п.2).
3. `report`, блок «Экономика» (`$/задачу (done)`, суммарный расход,
   суммарная верхняя оценка) и блок «Доля acceptance: автогейт vs
   Оператор» (за всю историю и за последние 10 задач): если в выборке
   задач больше одного проекта — значения даны с разбивкой по проекту
   (по строке на проект с его именем); если проект один (в том числе
   единственный внешний) — вывод блоков прежний (ANSWER-1, п.2). Задача
   относится к проекту по `tasks.target`; задача с `tasks.target` NULL
   считается задачей артели (`config.DEFAULT_TARGET`) — так же, как
   сейчас `report.py:554-555` и `catalog.py:973`; число проектов — число
   разных значений `tasks.target` в выборке задач после этой замены
   (решение Оператора при возврате, визит 2, п.1). Окно «за последние 10 задач» для
   проекта — то же правило отбора записей, что сейчас (записи перехода
   acceptance, последние `GATE_RATIO_WINDOW` из них, `report.py:58,
   355-363`), применённое к записям задач этого проекта. Алерты с
   `target` NULL в агрегатах задач не участвуют (решение Оператора 4).
4. Дозор наблюдения: алерт с `target` NULL (алерт уровня пульта,
   ANSWER-1, п.1) доставляется каждому активному наблюдению, независимо
   от проектов его задач. Правило «оповещено» — по наблюдению: каждое
   наблюдение отмечает свою позицию, одно наблюдение не получает один и
   тот же алерт повторно, отметка одного наблюдения не снимает доставку
   другому. Доставка алертов с `target` = `config.DEFAULT_TARGET` и
   алертов по задачам/проектам набора — прежняя.
5. В строке дозора наблюдения у алерта с `target` NULL поле проекта
   печатается `-` (как секция триггеров `status`, `catalog.py:990`;
   ANSWER-1, п.4).
6. Команда `observe <наблюдение> events` (`artel.py:1132-1133`) выводит
   события тем же `watch._observation_events`, что и дозор; поэтому
   алерт с `target` NULL в её окне позиций выводится и ею, с `-` в поле
   проекта — это названное побочное изменение требований 4–5 (решение
   Оператора 7); `orchestrator/artel.py` не правится.
7. У базы с задачами только артели тексты `status`, `report` и `watch`
   прежние — кроме строк доставки алертов с `target` NULL дозором
   наблюдения и `observe events` (требования 4–6, решение Оператора 2);
   это фиксируется тестами, написанными до правки кода (требование 4 ТЗ),
   с эталоном, снятым на коде до правки, а не построенным тем же кодом
   при прогоне (решение Оператора при возврате, визит 2, п.4).
8. Тесты детерминированы и без сети: задачи артели и учебного внешнего
   проекта в одной БД, два наблюдения (требование 5 ТЗ).
9. Смешение алертов уровня пульта и алертов проекта артели под одним
   `target` = `config.DEFAULT_TARGET` (стоп-кран `alerts.py:238`,
   `doctor/orphans.py:185` рядом с `doctor/map_growth.py`,
   `doctor/recovery.py`, `doctor/suite_duration.py`) в этой задаче не
   устраняется: разработчик записывает его строкой для бэклога в раздел
   «Предложения системе» PLAN.md (ANSWER-1, п.1).

## Критерии приёмки

AC-1. В БД с задачей артели и задачей внешнего проекта `sled` отрендеренный текст (без разметки) строк HTML `report` — плитки борда, очереди гейтов, списка закрытых задач, разреза задач, значений трения и шагов test_author — у задачи `sled` содержит `[sled]` сразу за её id, а у задачи артели — id без метки проекта; на плитке задачи `sled` есть элемент с собственным текстом ровно `sled`, а элемент id плитки несёт ровно id задачи.

AC-2. В той же БД панель незакрытых алертов `report` показывает у алерта с `target` `sled` метку `[sled]`, а строка алерта с `target` артели, строка алерта с `target` NULL и строка алерта с `target` = id задачи `sled` (вид `attention`, `alerts.py:116-120`) — без метки проекта, в прежнем виде; алерт с `target` = id задачи `sled` выводится дозором наблюдения, в набор которого входит эта задача.

AC-3. В БД с задачами двух проектов, где у каждого проекта записей перехода acceptance больше `GATE_RATIO_WINDOW` (`report.py:58`), блок «Экономика» `report` (`$/задачу (done)`, суммарный расход, суммарная верхняя оценка) и блок доли acceptance «автогейт vs Оператор» (вся история и окно последних записей) дают значения отдельно по каждому проекту, и значение каждого проекта считается только по записям и задачам этого проекта: окно проекта — последние `GATE_RATIO_WINDOW` записей этого проекта, а не его доля среди последних `GATE_RATIO_WINDOW` записей всех проектов.

AC-4. В БД с задачами только артели (в том числе с задачей, у которой `tasks.target` NULL, рядом с задачей `target` = `config.DEFAULT_TARGET`) и в БД с задачами только одного внешнего проекта блоки «Экономика» и доли acceptance `report` выводятся без разбивки по проекту, в прежнем виде.

AC-5. При двух активных наблюдениях (одно на задачу артели, другое на задачу `sled`) алерт с `target` NULL выводится дозором каждого наблюдения ровно один раз, в том числе при повторных циклах дозора каждого из них.

AC-6. Строка дозора наблюдения у алерта с `target` NULL несёт в поле проекта `-`.

AC-7. `observe <наблюдение> events` с окном позиций, включающим алерт с `target` NULL, выводит этот алерт с `-` в поле проекта.

AC-8. В БД с задачами только артели тексты `status`, `report` и `watch` совпадают с выводом до правки, кроме строк алертов с `target` NULL в дозоре наблюдения. Эталон — литерал в тесте или файл рядом с ним, снятый на коде до правки; тест не строит эталон тем же кодом при прогоне. Зависящие от времени части HTML `report` нормализуются так: текущий момент `report` зафиксирован в тесте литералом (`datetime.now` модуля `report` и аргумент `now` рендера), а метки времени журнала фикстуры — литералы; этим закреплены окна от текущего момента — записи actor=operator по дням (`OPERATOR_WINDOW_DAYS`, `report.py:366-380`), «Шаги test_author» (`report.py:834-842`) и «Разведка ролей» (`EXPLORE_WINDOW_DAYS`, `report.py:975-979`); прочие части HTML сравниваются без нормализации.

## Меняемое поведение

Ожидания существующих тестовых методов `tests/` требования не меняют.
Меняется вывод дозора наблюдения и `observe events`, в том числе у базы
только с задачами артели: алерт с `target` NULL, раньше не доставлявшийся
ни одному наблюдению, теперь выводится каждым (требования 4–6) — это цель
задачи. Поиском по `tests/` (`insert_alert`/`raise_alert` с `target`
NULL в тестах наблюдения и `watch`) тест, закрепляющий недоставку таких
алертов, не найден; если разработчик его найдёт — эскалация за мандатом,
не правка теста (решение Оператора 2). Долгоживущий тест плитки
`tests/test_01m563e1sh9sb63s2mw4a9b82n_project_label.py:126` остаётся
верным без правки за счёт вложенной разметки (требование 1).

в одну рамку. Решение — за Оператором на гейте SPEC.

- Мьютекс мержа по проекту — отдельная задача (граница ТЗ); ожидание
  merge-окна в `status` остаётся общим.
- Правка мест заведения алертов (`orchestrator/alerts.py`,
  `orchestrator/doctor/*`) и разделение алертов пульта и проекта артели
  под `config.DEFAULT_TARGET` — зоны не расширяются (ANSWER-1, п.1); только
  строка в «Предложения системе» PLAN (требование 9).

  actor=operator по дням, тренд трения, калибровка курса токенов, рост
  карты (ANSWER-1, п.2).
- Метка проекта в строках «Разведки ролей» `report` — они id задачи не
  несут (`report.py:975-983`).
- Правка `orchestrator/artel.py`, `orchestrator/alerts.py`,
  `orchestrator/store.py`, `docs/triggers.md`, `docs/backlog.md` — только
  чтение по ТЗ.
- Обычный `watch` без наблюдения (`watch.py:468-473`) — ТЗ говорит о
  дозоре наблюдения.
