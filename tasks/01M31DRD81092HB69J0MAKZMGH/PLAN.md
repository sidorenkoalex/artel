# PLAN: Трение конвейера: список защищённых путей в CI, карта в гейте ёмкости, калибровка бюджета

## Подход

Три независимых источника трения — три независимые правки, одной задачей
(монолит по решению SPEC, «Оценка объёма и деление»). Общего кода у них
нет, общий у них только факт: каждая снимает своё трение целиком, а не
наполовину.

**1. Список защищённых путей — из базы сравнения.** Новый модуль
`scripts/ci_protected_paths.py` (stdlib, без аргументов командной строки,
база переменной окружения `BASE_SHA`) — тот же приём выноса логики джоба
в тестируемый модуль, что у `scripts/ci_push_class.py` (ADR-0016). Список
читается из ТЕКСТА `orchestrator/config.py` базы (`git show
<base>:orchestrator/config.py`), а не импортом `orchestrator.config`:
импорт взял бы список ВЕТКИ (сегодняшнее поведение однострочника) и всё
так же красил бы PR, который создаёт файл и тем же изменением вносит его
в список. Разбор — модульным AST, не регуляркой и не импортом: регулярка
не переживает переноса кортежа на вторую строку (а он там есть,
`orchestrator/config.py:615-618`), импорт исполнил бы код базы. Сверка
остаётся префиксной — ровно тот же смысл, что нёс `grep -E "^($PROTECTED)"`
в bash, поэтому `skills/` по-прежнему ловит файл внутри каталога.
Нечитаемая база — код возврата 2 с названной причиной (fail-closed,
ADR-0002); нарушение — 1 с перечислением путей.

**2. Карта вне меры гейта ёмкости.** В pathspec первой (решающей) меры
`orchestrator/advance_gates/capacity.py` добавлено исключение
`:!docs/codebase-map.md` рядом с существующим `:!tasks/<id>/` — именно
исключением pathspec, не вычитанием размера постфактум. Вторая цифра
отказа вынесена в общий узел `_excluded_note`: три исхода (байты,
«0 байт (изменений нет)», «неизвестен (git не ответил: …)») теперь
считаются по одному правилу для обеих исключённых частей, и разъехаться
цифрам негде. Дедупликация здесь не «заодно»: SPEC требует, чтобы карта
исключалась и называлась ТЕМ ЖЕ приёмом, что артефакты задачи, — два
скопированных трёхветочных блока это требование как раз и нарушали бы.

**3. Калибровка бюджета.** Таблица `config.BUDGET_CALIBRATION_TABLE`
получает четвёртый уровень и пересмотренные нижние — значения из
SPEC, требование 6, дословно ($25 / $40 / $45 / $85). Читатель
`budget.recommended_budget_usd` не меняется: правило «первый уровень,
чьи оба потолка не превышены» уже даёт нужные ответы, новый уровень
встаёт ПЕРЕД неограниченным «всё остальное». Комментарий над таблицей
несёт дату пересчёта, выборку и правило 80-го перцентиля.

Бюджет SPEC ($45) не переоценивается: фактический объём — три файла зоны,
один новый модуль stdlib, три новых файла тестов и одна обновлённая
фикстура; это ровно та оценка, из которой SPEC исходил.

## Влияние на систему

**Что затронуто за пределами правки.**

- `.github/workflows/ci.yml`, джоб `protected-paths` — приложение 1.
  Пока Оператор его не применил, джоб продолжает работать по-старому
  (список из ветки); модуль в ветке при этом уже есть и уже
  оттестирован. Разъехаться они не могут: своего перечня защищённых
  путей ни джоб, ни модуль не несут.
- Читатели `config.PROTECTED_PATHS` — `advance_gates/zones.py`,
  `advance_gates/plan_appendix.py`, `fsm_merge_gate.py` — не тронуты и
  по-прежнему читают список ГЛАВНОЙ копии. Это сознательно: задача
  меняет источник списка только для джоба CI (SPEC, «Не входит»).
- `config.REVIEW_SNAPSHOT_DIFF_MAX_BYTES` не меняется (сейчас 320 000 —
  временный подъём Оператора 21.09). Возврат к 262 144 — его решение
  после мержа 01M300A14K, и после этой задачи возврат становится
  дешевле: карта из меры ушла.
- `docs/adr/0014-budget-default-and-role-cap.md` не правится: п.7
  решения чисел не называет, а делегирует их
  `config.BUDGET_CALIBRATION_TABLE` (сверено по тексту,
  `docs/adr/0014-…:67-72`) — пересчёт идёт в рамках уже принятого
  решения (SPEC, требование 9).
- `docs/codebase-map.md` регенерирована тем же коммитом
  (`python3 scripts/codebase_map.py`).

**Какие защиты рядом и почему они не ослабляются.**

- Гейт ёмкости остаётся fail-closed на сбое git первой (решающей) меры —
  ветка `if reason: return GateRefusal(...)` не тронута. Сбой git на
  ВТОРОЙ мере (цифры сообщения) отказа не отменяет и пропуска не даёт:
  `_excluded_note` в этом случае возвращает «неизвестен», решение уже
  принято первой цифрой. Это требование SPEC 5/AC-7 и поведение,
  которое уже было у цифры артефактов.
- Исключение карты из меры — не ослабление потолка: потолок не
  двигается, из меры уходит файл, которого ревьювер не читает построчно
  (он приходит ему отдельным компонентом пакета,
  `orchestrator/context_package.py`). Предмет ревью измеряется точнее,
  а не мягче. Обратная сторона — гейт больше не видит раздувание самой
  карты; её рост отслеживается отдельно
  (`report.map_size_table_rows`/`map_growth_open_alerts`).
- Новый джоб строго строже прежнего на нечитаемой базе: там, где bash
  мог отдать пустой `$PROTECTED` и пропустить, модуль падает с
  причиной. Непригодное значение списка (пустой кортеж, не-строка
  внутри) — тоже отказ, а не «нарушений нет».
- Калибровочная таблица — ориентир и текст предупреждения, не запрет:
  потолок задачи по-прежнему задаёт SPEC и поднимает только Оператор
  (ADR-0014). `BUDGET_CALIBRATION_FLOOR_USD` ($25) не меняется, ни один
  уровень новой таблицы ниже пола не опускается.
- `tests/test_invariants.py` (защищённый путь) не тронут — прогнан,
  зелёный.

**Обновлённые ожидания существующих тестов** (SPEC, требование 10):
ровно одно — `tests/test_fsm_advance_gate_smoke.py::CapacityGateSmokeTest`

## Риски

- **Приложение 1 и модуль расходятся во времени.** Пока Оператор не
  применил приложение, защита работает по-старому — то есть трение
  требования 1 снимается только на мерже. Это заложено механикой
  приложений, обойти её нельзя; ни одного промежуточного состояния
  хуже сегодняшнего при этом не возникает.
- **`git show <base>:orchestrator/config.py` требует полной истории.**
  Джоб уже ходит с `fetch-depth: 0`, приложение этого не трогает; при
  shallow-чекауте модуль упал бы fail-closed с внятной причиной, а не
  пропустил бы проверку.
- **Числа калибровки живут в двух местах** — в таблице и прозой в
  `skills/spec-authoring.md`. Задача синхронизирует оба, но машинной
  сверки между ними нет: следующий пересчёт может снова развести их.
  См. «Предложения системе».

## Предложения системе

- `orchestrator/config.py:443-453` — комментарий временного подъёма
  `REVIEW_SNAPSHOT_DIFF_MAX_BYTES` до 320 000 несёт строку «Кандидат в
  копилку: исключать docs/codebase-map.md из меры гейта». Кандидат
  закрыт этой задачей; сам подъём и его комментарий — зона Оператора
  (класс «лимит», ADR-0002), поэтому здесь не тронуты. Класс: «крутилка
  поднята обходом, а причина обхода устранена другой задачей — вернуть
  крутилку некому».
- `skills/spec-authoring.md:30-36` повторяет числа
  `config.BUDGET_CALIBRATION_TABLE` прозой, а комментарий над самой
  таблицей до этой задачи утверждал обратное («скил ссылается на имя
  константы, не повторяет числа»). Расхождение прожило от
  01M1TQ11K4WJZD7ZE3MR0J4ZK4 до сегодня и обнаружилось только потому,
  что аналитик проверил текст скила руками. Класс: «константа
  продублирована прозой в защищённом пути, машинной сверки нет» —
  кандидат на линт «числа скила совпадают с таблицей», как уже сделано
  для `scripts/id_format_patterns.txt` (общий источник образцов для
  джоба и для проверки перехода).
- Логика двух джобов CI теперь живёт модулями (`ci_push_class.py`,
  `ci_protected_paths.py`), а два соседних (`id-format-greplint`,
  `canary-guid-leak`) — по-прежнему bash-однострочниками в yaml, то
  есть в ветке задачи нетестируемы тем же способом. Класс:
  «исполняемая логика в защищённом пути, недоступном тестам ветки».
