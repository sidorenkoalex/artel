# SPEC: К3-канарейка: команда canary, метрики, бейзлайн

## Контекст
К3 роадмапа (канарейка конвейера, аудит v3, находка А2 «регрессии
конвейера нечем ловить»). Дизайн согласован Оператором 28.08:
канарейка — синтетические типовые ТЗ с неподвижным входом (не реальная
прошлая задача — её решение уже в git-истории и подсмотрит прогон, а
кодовая база дрейфует и забивает сигнал шумом): меняется только
конвейер, сдвиг метрик читается как его регрессия. Бейзлайн = первый
прогон набора, отдельный вопрос «какую задачу взять эталоном» снят
дизайном.

## Требования
1. Новая команда `artel.py canary <каталог-ТЗ>`: для каждого файла
   `*.md` в переданном каталоге заводит отдельную задачу через
   существующий `catalog.cmd_new` (`--tz`). Сами тексты канареечных ТЗ
   держит Оператор вне репозитория — команда обязана работать с любым
   переданным каталогом `*.md`, не только с тремя эталонными.
2. Внутри canary-прогона каждая заведённая задача проводится обычным
   `auto`-циклом (run+advance) до каждого ручного гейта. По достижении
   `spec_gate` и `acceptance` гейт проходится автоматически (по
   действию эквивалентно операторскому `approve`) с пометкой `canary`
   в журнале задачи (`store.journal`). Это отдельный кодовый путь
   команды `canary`, не через существующие `cmd_approve`/`auto`:
   инвариант 18 («`auto` не проходит гейты») не затрагивается, у
   продуктовых задач нового пути мимо гейта не появляется.
3. По достижении `merge_gate` задача НЕ approve — она убивается
   (`kill`) с пометкой canary/причина; `merge_gate` canary-задача не
   проходит никогда. `main` при этом не изменяется (инварианты 12, 15).
4. По завершении прогона набора — отчёт в stdout и файл
   `.artel/canary/<timestamp>.json`. На каждую задачу набора: число
   шагов, суммарная стоимость, число итераций ревью, факт(ы)
   эскалации по стадиям, исход (killed at merge_gate или иной).
   Суммарно по набору — сравнение сумм (стоимость, шаги) с
   бейзлайном. Оценка «уместности» эскалации по ожиданиям из
   канареечного ТЗ в отчёт не входит (LLM-оценка качества — вне
   объёма, см. «Не входит») — отчёт несёт факты, не суждения.
5. Прогон, для которого файла `.artel/canary/baseline.json` ещё нет,
   пишет его с суммарными метриками набора (стоимость, шаги) —
   бейзлайн. Любой следующий прогон при существующем `baseline.json`
   сравнивает свои суммарные метрики с бейзлайном и предупреждает в
   отчёте, если |отклонение| по стоимости или по шагам превышает
   порог (дефолт 50%); файл бейзлайна при этом не перезаписывается.
   Перезапись — только по отдельному явному флагу команды (имя и
   формат флага — решение developer в PLAN).
6. Каждая заведённая командой `canary` задача помечена в БД как
   canary — механизм: ТОЛЬКО колонка БД; пометка в title ЗАПРЕЩЕНА
   (правка Оператора на гейте 28.08: title виден ролям в промпте,
   а канареечная задача обязана быть неотличимой от продуктовой для
   ролей — иначе возможна «притирка» к канарейке; класс контаминации
   бенчмарка). Пометкой задача отличима от продуктовых задач в
   `status`/`show`/RETRO-статистике; при этом её расход учитывается в
   `total_spent` и порогах A1 наравне с продуктовыми задачами (честный
   учёт, не скрытые деньги).
7. Бюджет canary-задачи — обычный дефолтный потолок задачи; никакого
   отдельного обхода `orchestrator/budget.py` для canary-задач.
8. Существующие инвариантные тесты, в частности 7, 12, 14, 15, 18, 19
   (`docs/invariants.md`), остаются зелёными без ослабления:
   автопроход гейтов существует только внутри кода команды `canary` и
   только для задач, заведённых ею же самой.

## Критерии приёмки

AC-1. Запуск `canary <каталог>` на каталоге из двух тестовых ТЗ-файлов
заводит по задаче на каждый файл, проводит обе через `spec_gate` и
`acceptance` автоматически с пометкой `canary` в журнале, на
`merge_gate` каждую убивает (`kill`) с пометкой; sha `main` до и после
прогона идентичен; итоговый отчёт (stdout и файл
`.artel/canary/<timestamp>.json`) содержит метрики (шаги, стоимость,
итерации ревью, эскалации, исход) по обеим задачам.

AC-2. Прогон `canary`, для которого файла `.artel/canary/baseline.json`
ещё нет, создаёт этот файл с суммарными метриками набора (стоимость,
шаги).

AC-3. Повторный прогон `canary` того же набора при существующем
`baseline.json` сравнивает суммарные метрики текущего прогона с
бейзлайном и печатает предупреждение, если |отклонение| по стоимости
или по шагам превышает порог (дефолт 50%); содержимое
`baseline.json` после прогона не изменилось (перезапись возможна
только явным флагом пересъёма).

AC-4. Задачи, заведённые командой `canary`, отличимы от продуктовых
задач в `status`/БД и в RETRO-статистике по этой пометке; их расход
при этом учтён в `total_spent` наравне с прочими задачами.

AC-5. Инвариантные тесты 7, 12 и 18 (`tests/test_invariants.py`:
`ManualGatesNeedTheOperatorTest`, `MergeOnlyFromMergeGateTest`,
`AutoNeverPassesAGateTest`) остаются зелёными без изменений:
продуктовые `approve`/`auto` не получают нового пути автопрохода
гейта — автопроход существует только внутри команды `canary` для
задач, заведённых ею же.

## Не входит

- Сами тексты канареечных ТЗ (Оператор готовит их отдельно, вне
  репозитория).
- LLM-оценка качества артефактов канарейки, включая суждение об
  «уместности» эскалации относительно ожиданий из ТЗ — отчёт несёт
  только детерминированные метрики.
- Планировщик регулярных прогонов canary — запуск остаётся ручным,
  операторским.
- Изменение продуктовых FSM-путей (переходов, гейтов) вне кода команды
  `canary`.

## Материалы
- `docs/invariants.md` — инварианты 7, 12, 14, 15, 18, 19 (границы,
  которые команда `canary` не ослабляет).
- `orchestrator/catalog.cmd_new` — существующий способ завести задачу
  из файла ТЗ (`--tz`).
- `orchestrator/auto.py`, `orchestrator/fsm.py` — существующий цикл
  `auto` и переходы гейтов, которые команда `canary` переиспользует и
  дополняет отдельным путём автопрохода.
- `orchestrator/budget.py` — учёт `total_spent` и порогов A1, который
  canary-задачи проходят наравне с продуктовыми.
