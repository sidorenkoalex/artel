# PLAN: К3-канарейка: команда canary, метрики, бейзлайн

## Подход

Новый модуль `orchestrator/canary.py` с командой `cmd_canary(tz_dir, *,
rewrite_baseline=False)`, подключённой в таблицу `orchestrator/artel.py::main`
как `canary <каталог> [--rewrite-baseline]`.

Заведение задач переиспользует `catalog.cmd_new(title, tz_path=..., canary=True)`
— существующая функция получает новый keyword-only параметр `canary: bool =
False` (дефолт не меняет поведение продуктовых вызовов) и теперь возвращает
`task_id`, чтобы вызывающий код мог его собрать. Пометка canary — ТОЛЬКО
колонка БД `tasks.is_canary` (правка Оператора 28.08 на гейте SPEC,
требование 6): `store.insert_task` получает тот же keyword-only параметр и
пишет его в новую колонку схемы; `title` канареечной задачи — имя файла ТЗ
без пометки.

Прогон каждой заведённой задачи — цикл: зовём существующий `auto.cmd_auto`
(тот самый run+advance, которым Оператор гоняет продуктовые задачи) до его
останова; смотрим, в каком состоянии задача остановилась:

- `spec_gate`/`acceptance` — это ручной гейт, на котором `auto` останавливается
  по инварианту 18 («`auto` не проходит гейты») и остаётся стоять. `canary.py`
  здесь НЕ зовёт `fsm.cmd_approve` — пишет свой переход напрямую через
  `store.set_state(..., actor="canary", ...)`, скопировав ровно ту логику
  ветвления (spec_gate: `tests_writing` при AC-разметке SPEC, иначе `in_dev`;
  acceptance: сверка свежести ветки `fsm._pull_main_or_escalate` и переход в
  `merge_gate`), которую несёт `fsm._cmd_approve` для этих двух состояний —
  без обращения к самой `cmd_approve`/`auto` как к точкам входа. Так
  инвариант 18 не затрагивается (`auto` как модуль по-прежнему не проходит
  ни один гейт ни для одной задачи), а у продуктовых задач нового пути мимо
  гейта не появляется: путь существует только внутри `canary.py` и только
  для задач, которые сама же команда завела. `actor="canary"` на переходе —
  и есть пометка канарейки в журнале (требование 2): `store.set_state`
  журналирует actor вместе с переходом, отдельного вызова не нужно.
  Цикл продолжается: после перехода снова зовём `auto.cmd_auto` (дальше
  либо следующий агентский шаг, либо следующий ручной гейт).
- `merge_gate` — не approve никогда (требование 3): пишем причинную запись в
  журнал (`actor="canary"`) и зовём существующий `cleanup.cmd_kill`. `main`
  этим путём не трогается (`cmd_kill` не мержит).
- `escalated`/`done`/иное — canary дальше не ведёт, это конец для задачи
  (в разработанных приёмочных сценариях недостижимо, но не должно уронить
  прогон остальных задач набора при реальном использовании).
- останов `auto` без смены на одно из вышеперечисленных состояний (истрачен
  `AUTO_MAX_STEPS` за один вызов, задача ещё в агентском состоянии) — не
  повод останавливаться: `runner.step_role(t) is not None` после останова
  значит «есть кому работать дальше», цикл зовёт `auto.cmd_auto` заново.

Подтверждение фиксации (`fsm.confirm_fixation`, ADR-0003 п.15) в
canary-переходах не нужно: это защита от TOCTOU между тем, что увидел
Оператор, и тем, что реально лежит в артефактах на момент его `approve` —
у canary нет человека, глядящего на sha заранее, весь путь «фиксация →
переход» выполняется одним автоматическим вызовом без временного разрыва.

Метрики задачи (требование 4) считаются по её журналу и строке `tasks`
после того, как цикл для неё завершился: `steps` — число записей
`"state -> …"` (переходов FSM, независимо от того, что конкретно исполнял
шаг — устойчиво к подмене `runner.cmd_run` в приёмочной песочнице, где
собственная журнализация "agent run …" настоящего `cmd_run` не происходит);
`cost_usd` — `tasks.spent_usd`; `review_iterations` — `tasks.review_iters`;
`escalations` — список `detail` всех записей `"state -> escalated"`;
`outcome` — конечное состояние задачи (`killed`/`escalated`/…).

Отчёт прогона (требование 4) — `{"tasks": {<id>: {...}}, "summary":
{"cost_usd": ..., "steps": ...}}`, файл `.artel/canary/<UTC-таймстамп>.json`
+ печать в stdout. Бейзлайн (требования 5) — тот же `summary`-словарь,
`.artel/canary/baseline.json`: нет файла — пишется без всяких условий;
есть — сравнивается (`|отклонение| > config.CANARY_DEVIATION_RATIO`,
дефолт 0.5, деление на ноль в бейзлайне трактуется как «любое ненулевое
значение — полное отклонение») и печатается предупреждение при
превышении, файл не трогается. Перезапись — только явным флагом CLI
`--rewrite-baseline` (имя/формат — решение этого PLAN).

Отличимость канареечной задачи для Оператора (требование 6): `catalog.
cmd_status` печатает пометку `[canary]` в конце строки, когда
`tasks.is_canary` истинно (не в `title`, не в промпте роли — роль его не
видит вовсе, у неё нет доступа к колонке БД). `orchestrator/retro.py`
(`build_done`/`build_killed`) добавляет строку «Канареечная задача: да»
при том же условии — тем же способом, RETRO-статистика отличима, не
затрагивая текст, который не завязан на колонку.

`store.total_spent` и пороги A1 (`orchestrator/budget.py`) не меняются:
они уже суммируют `spent_usd` по всем строкам `tasks` без фильтра —
расход канареечной задачи учитывается наравне с продуктовой самой
структурой существующего кода (требование 6, вторая часть). Бюджет
canary-задачи — тот же путь `budget.apply_spec_budget` на переходе
`spec_writing -> spec_gate`, что и у продуктовой (требование 7):
специального обхода `orchestrator/budget.py` не заводится.

## Шаги

1. Схема БД: колонка `tasks.is_canary` (SCHEMA + `migrate()`),
   `store.insert_task(..., *, is_canary: bool = False)`.
2. `catalog.cmd_new` — keyword-only `canary: bool = False`, передаёт его в
   `insert_task`, возвращает `task_id`. `catalog.cmd_status` — пометка
   `[canary]` по колонке.
3. `orchestrator/retro.py` — пометка «Канареечная задача: да» в
   `build_done`/`build_killed` по той же колонке.
4. `orchestrator/canary.py` — цикл прогона задачи (auto + свой переход
   гейтов spec_gate/acceptance + kill на merge_gate), сбор метрик,
   запись отчёта и сверка/запись бейзлайна; `orchestrator/artel.py` —
   команда `canary <каталог> [--rewrite-baseline]` в таблице диспетчера
   и в докстринге-справке.
5. Юнит-тесты нового кода (`tests/test_canary.py`): схема/маркировка,
   чистые функции отклонения от бейзлайна и сборки отчёта, CLI-отказы
   (нет каталога, нет *.md).

Приёмочные тесты `tasks/T065/acceptance_tests/` (AC-1..AC-5) уже
залочены (T023) — шаги 1-4 подгоняют код под них, не наоборот; шаг 5 не
дублирует их сценарии целиком (реальный git, реальный `auto`-цикл — уже
покрыто приёмкой), а закрывает то, что приёмка не изолирует (чистая
арифметика бейзлайна, поведение CLI на плохом вводе, факт колонки/пометки
изолированно от полного прогона).

## Влияние на систему

- Новая колонка `tasks.is_canary` — аддитивная миграция (`add_column`,
  тот же приём, что и у всех прежних колонок этой таблицы), дефолт 0:
  существующие строки и весь код, читающий `tasks` по имени колонки
  через `store.update_task`/`SELECT *`, не ломаются. Ни одна из
  существующих колонок не переименовывается и не убирается.
- `catalog.cmd_new` и `store.insert_task` получают новый keyword-only
  параметр с дефолтом, сохраняющим прежнее поведение байт-в-байт для
  всех существующих вызывателей (grep по вызовам обеих функций в
  пакете и тестах — позиционные вызовы без изменений); возврат
  `task_id` из `cmd_new` — новое расширение сигнатуры (было `None`),
  ни один существующий вызыватель возвращаемое значение не использует.
- Гейт-логика продуктовых задач (`fsm.py`) не меняется ни строкой: новый
  код читает те же артефакты и ту же схему `tasks`, но живёт в отдельном
  модуле `canary.py` и вызывается только из команды `canary`. Инварианты
  7, 12, 18 (`docs/invariants.md`) проверены приёмочным AC-5
  (`tasks/T065/acceptance_tests/test_ac5_invariant_tests_stay_green.py`)
  — гоняет `ManualGatesNeedTheOperatorTest`, `MergeOnlyFromMergeGateTest`,
  `AutoNeverPassesAGateTest` без изменений и требует их зелёными.
  Инвариант 15 (`kill` не трогает main) — canary на merge_gate зовёт
  штатный `cleanup.cmd_kill`, ту же функцию, что и Оператор руками;
  инвариант 14 (kill switch срабатывает всегда) не затронут тем же
  доводом. Инвариант 9/10 (бюджет, потолок только Оператором) не
  затронут — canary не трогает `budget.py`.
- `retro.py`/`catalog.cmd_status` — добавление строки/суффикса под
  условием новой колонки, существующий текст для НЕ-canary задач
  (`is_canary` ложно) байт-в-байт тот же, что и до изменения — проверено
  явно приёмочным AC-4 (`product_line`/`product_retro` без пометки).
- Откат: колонка не читается никаким кодом вне `canary.py`/`catalog.
  cmd_status`/`retro.py` — удаление этих трёх мест и самого `canary.py`
  (и его подключения в `artel.py`) возвращает систему к состоянию до
  задачи; колонку в БД можно оставить (аддитивная, не мешает).

## Риски

- Определение «шаг» = число переходов FSM (`"state -> …"` в журнале), а
  не число агентских прогонов: для настоящего (не приёмочного) canary-
  прогона это немного другое число, чем «сколько раз запускался агент»
  (переход `review -> in_dev -> review` — один цикл ревью, но это
  по-прежнему и число реальных `cmd_run`). Решение сознательное (см.
  «Подход») — деривация из журнала, устойчивая к подмене `cmd_run` в
  приёмочной песочнице; для реального прогона оба числа совпадают
  почти всегда (один `cmd_run` = один шаг = один переход, кроме
  случаев, когда `advance` отказывает без смены состояния — тогда
  «шагов» в этом смысле меньше, чем прогонов агента). Если Оператору
  впоследствии понадобится именно число агентских прогонов — отдельное
  требование, не эта задача.
- Порог отклонения бейзлайна (0.5, `config.CANARY_DEVIATION_RATIO`) —
  константа кода, не CLI-флаг: SPEC называет его «дефолт», но не требует
  делать настраиваемым через командную строку в этой задаче — при
  необходимости смены значения правка тривиальна (одна константа).

## Предложения системе

- `docs/invariants.md` не даёт готового рецепта «отдельный кодовый путь
  вместо переиспользования штатной команды approve/auto» для будущих
  задач с похожей формой (детерминированный прогон конвейера без
  Оператора) — пришлось выводить границу из формулировки инварианта 18
  и контекста SPEC. Стоит явно описать этот паттерн (копия узкой ветки
  логики гейта вместо вызова публичной команды) рядом с инвариантом 18,
  раз он уже встретился во второй задаче класса «автоматизация поверх
  конвейера» (после `auto` самого).
