# ТЗ: К3-канарейка: команда canary, метрики, бейзлайн

## Контекст

К3 роадмапа (канарейка конвейера, аудит v3 находка А2 «регрессии
конвейера нечем ловить»). Дизайн согласован Оператором 28.08:
канарейка — НЕ реальная прошлая задача (решение уже в git-истории —
прогон подсмотрит; кодовая база дрейфует — шум забивает сигнал), а
синтетические типовые ТЗ с неподвижным входом: меняется только
конвейер — сдвиг метрик читается как его регрессия. Бейзлайн =
первый прогон набора; старый вопрос «какую задачу взять эталоном»
снят.

## Решение (Оператор 28.08)

1. Новая команда `artel.py canary <каталог-ТЗ>`: для каждого файла
   *.md в каталоге (канареечные ТЗ Оператор держит ВНЕ репозитория,
   чтобы роли их не увидели в истории) — завести задачу через
   существующий cmd_new (--tz), прогнать auto до первого ручного
   гейта... СТОП — гейты ручные. Уточнение механики: canary-прогон
   идёт с автопроходом гейтов В ПРЕДЕЛАХ canary-задачи: spec_gate и
   acceptance проходятся автоматически С ПОМЕТКОЙ canary в журнале
   (это НЕ ослабление инварианта 7 «гейты проходит только Оператор»:
   команда canary — операторская, запуск = операторское решение по
   всем гейтам набора; кодируется явно и только для задач,
   заведённых самим canary-прогоном), merge_gate НЕ проходится
   никогда: на merge_gate canary-задача убивается (kill) с пометкой.
   main не изменяется (инварианты 12, 15 нетронуты).
2. По завершении набора — отчёт метрик в stdout и файл
   .artel/canary/<timestamp>.json: на задачу — шаги, стоимость,
   итерации ревью, эскалации (и их уместность по ожиданию из ТЗ),
   исходы; суммарно — сравнение с бейзлайном (первый сохранённый
   прогон) с порогом отклонения (предупреждение при |дельта| выше
   порога, дефолт 50% по стоимости/шагам).
3. Бейзлайн: первый прогон пишет baseline.json; последующие сравнивают
   и НЕ перезаписывают его (пересъём бейзлайна — явный флаг команды).
4. Канареечные задачи помечаются в БД (колонка/пометка canary или
   префикс в title — выбор developer в PLAN) и исключаются из
   продуктовых метрик §5 (total_spent их видит — деньги настоящие,
   но status/RETRO-статистика отличает).
5. Три эталонных ТЗ готовит Оператор отдельно (вне этой задачи):
   «малая фича с тестами», «удаление рудимента», «правка с подвохом»
   (ожидаемая эскалация — канарейка честности ролей). Команда обязана
   работать с любым каталогом *.md.

## Границы

- orchestrator/ (новый модуль canary.py + artel.py + смежные), тесты,
  карта. Инварианты 7/12/14/15/18/19 не ослабляются: автопроход гейтов
  существует ТОЛЬКО внутри canary-команды для задач, заведённых ею же,
  и кодируется отдельным путём, не трогающим cmd_approve/auto
  (инвариант 18 «auto не проходит гейты» остаётся истинным).
- Бюджет canary-задач — дефолтный потолок задач; расход учитывается
  честно (total_spent, пороги A1).

## Не входит

- Сами тексты канареечных ТЗ (Оператор, вне репозитория).
- LLM-оценка качества артефактов канарейки (только детерминированные
  метрики).
- Планировщик регулярных прогонов (запуск — ручной операторский).
- Изменение продуктовых FSM-путей.

## Приёмка (минимум)

- canary на каталоге из 2 тестовых ТЗ: заводит задачи, проходит их
  гейты с пометкой canary, на merge_gate убивает, main не изменён
  (sha main до/после идентичен), отчёт содержит метрики обеих задач.
- Первый прогон пишет baseline.json; второй прогон сравнивает и
  предупреждает при отклонении выше порога; бейзлайн не перезаписан.
- Инвариантные тесты (7, 12, 18) зелёные без ослабления: продуктовые
  approve/auto не получили новых путей мимо гейтов.
- Канареечные задачи отличимы в status/БД от продуктовых.
