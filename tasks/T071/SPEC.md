# SPEC: Ветко-корректное чтение SPEC в approve

## Контекст

T047 завела общий узел `_read_branch_text_or_refuse` (`orchestrator/fsm.py`),
через который читаются артефакты задачи с ВЕТКИ задачи (а не с диска
рабочей копии) для переходов `spec_writing`/`review`/`in_dev`. Остался
последний непереведённый читатель: чтение `SPEC.md` в переходе
`spec_gate` внутри `_cmd_approve` (`orchestrator/fsm.py:1092-1101`)
по-прежнему вызывает `gitcmd.show` напрямую. Единственное содержательное
отличие этого места от общего узла — реакция на отказ (`sys.exit` вместо
печати и `return`); пока чтение живёт отдельно, оно не получает
исправлений и гарантий узла и остаётся местом, где закрытый T047 класс
ошибок («читаем не ту версию артефакта, когда рабочую копию двигают
параллельные сессии») может воспроизвестись.

## Требования

1. Чтение `SPEC.md` в переходе `spec_gate` внутри `_cmd_approve`, при
   истинном `gitcmd.on_foreign_branch(branch)`, идёт через общий узел
   `_read_branch_text_or_refuse`, а не через прямой вызов `gitcmd.show`.
2. Наблюдаемое поведение отказа для approve/spec_gate сохраняется:
   когда SPEC.md ветки не прочитан, `approve` останавливает попытку
   именованным отказом и не переводит задачу в другое состояние.
   Точный текст сообщения и код выхода допустимо привести к стилю
   общего узла, если это не меняет решений FSM (какое состояние
   получает задача) — выбор фиксируется в PLAN.
3. Ветвление по `gitcmd.on_foreign_branch(branch)` (переход через узел
   при чужом чекауте, прежний путь чтения с диска иначе) сохраняется
   без изменений.
4. После правки чтение `SPEC.md` на переходе `spec_gate` нигде не
   обращается к `gitcmd.show` в обход `_read_branch_text_or_refuse`.

## Критерии приёмки

AC-1. Чтение `SPEC.md` в переходе `spec_gate` внутри `_cmd_approve`
(ветка `gitcmd.on_foreign_branch(branch)` истинна) вызывает общий узел
`_read_branch_text_or_refuse`, а не прямой `gitcmd.show`.

AC-2. При отказе узла (SPEC.md ветки не прочитан) `approve` в состоянии
`spec_gate` останавливает попытку именованным отказом и не переводит
задачу в другое состояние — прежнее наблюдаемое поведение сохранено.

AC-3. Сценарий «SPEC.md переходa approve/spec_gate читается с ветки
задачи, а не с диска рабочей копии» покрыт тестом для этого пути (по
образцу тестов T047, `tasks/T047/acceptance_tests/test_branch_correct_status_reads.py`).

AC-4. После правки чтение `SPEC.md` на переходе `spec_gate` нигде не
обращается к `gitcmd.show` в обход `_read_branch_text_or_refuse`.

AC-5. Полный тестовый набор (`pytest`) зелёный.

## Не входит

- Другие читатели артефактов в `orchestrator/fsm.py`, уже переведённые
  на общий узел T047 (`spec_writing`, `review → acceptance/in_dev`), и
  `_tests_writing_ac_state` (T031) — не трогаются, вне границ ТЗ.
- Правка модулей помимо `orchestrator/fsm.py` — вне границ ТЗ.
- Ослабление или удаление проверок общего узла `_read_branch_text_or_refuse`,
  существующих тестов, гейтов, лимитов и инвариантов (принцип
  целостности, ADR-0002).
- Изменение решений FSM (в какое состояние переходит задача при отказе
  или успехе) — только унификация текста/кода выхода отказа, если она
  не меняет решений.
