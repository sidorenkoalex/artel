# PLAN: Команда pause — штатная приостановка задачи

## Подход
Пометка паузы — колонка `tasks.paused` (INTEGER DEFAULT 0), не файл:
БД уже несёт lease/merge-lock той же логикой (одна БД — источник правды
для нескольких рабочих копий), SPEC требование 4 прямо просит именно
это. Новая колонка заводится тем же приёмом, что и все прошлые догоны
схемы (`store.add_column` в `store.migrate`, DEFAULT в `SCHEMA` — те же
два места, что несут `is_canary`).

Новый модуль `orchestrator/pause.py` — по образцу `orchestrator/
release.py`: одна пара команд, свой файл, без завязки на FSM (только
`store`). `cmd_pause`/`cmd_resume` не берут lease и не проходят
`parallel_limit` — они не мутируют шаг задачи, только пометку (тот же
довод, что у `cmd_release`, требования SPEC 6-8 явно исключают `kill`/
`approve`/`reject`/`advance` из проверки паузы — значит и сама пауза не
имеет права заходить в их машинерию).

Единственная точка проверки пометки — `runner._cmd_run`, сразу после
резолвинга роли шага (роль `None` — состояние не агентское, паузе
нечего блокировать) и до всего, что реально стартует агента (worktree,
pre-flight, spawn). Это даёт `run` и `auto` (он вызывает `cmd_run`)
одну и ту же проверку без дублирования логики (auto уже штатно
обрабатывает «run отказался стартовать без исключения» — тот же путь,
что и отказ по чужой ветке worktree). `kill`, `approve`/`reject`,
`advance` эту точку не проходят вовсе — SPEC требования 6-8 закрываются
самим тем, что их модули пометку не читают.

CLI: `pause <id>` / `resume <id>` в таблице команд `artel.py`, без
нового состояния FSM (SPEC требование 4, `docs/invariants.md` не
трогается).

## Шаги
1. `orchestrator/store.py`: колонка `paused` в `SCHEMA` (CREATE TABLE
   tasks) и в `migrate()` (`add_column`, DEFAULT 0) — свежая и
   догнанная БД дают одну и ту же схему (тот же приём, что уже
   документирован для колонки `target`).
2. `orchestrator/pause.py`: `is_paused(task_row) -> bool`,
   `cmd_pause(task_id)`, `cmd_resume(task_id)` — читают/пишут только
   `paused` и журнал, состояние (`state`) не трогают (AC-6).
3. `orchestrator/runner.py`: импорт `pause`, проверка `pause.is_paused(t)`
   в `_cmd_run` сразу после резолвинга роли — отказ печатью + журналом
   (`actor=role`, action `"run отклонён: задача на паузе"`), без
   `sys.exit` (тот же стиль, что у отказа «чужая ветка worktree»),
   `auto` подхватывает без правок (общий путь «run отказался стартовать
   без исключения»).
4. `orchestrator/artel.py`: `pause`/`resume` в таблицу команд CLI и в
   докстринг (список команд, список модулей пакета).
5. `tests/test_pause.py`: юнит-тесты `is_paused`/`cmd_pause`/
   `cmd_resume` (по образцу `tests/test_release.py`) — не дублируют
   приёмочные (`tasks/T070/acceptance_tests/`), а закрывают функции
   модуля отдельно от сквозных FSM-сценариев.
6. `python3 scripts/codebase_map.py` — новый модуль пакета меняет карту.

## Влияние на систему
Новая колонка БД — аддитивная миграция (DEFAULT 0), старые строки
получают её значением `0`/«не на паузе» без отдельного `UPDATE» — тот
же путь, что уже проходили `fixed_sha`, `tests_locked_sha`, `is_canary`.
FSM (состояния, переходы, гейты, `docs/invariants.md`) не меняется —
пауза не проход через `set_state`, `advance`, `approve`/`reject`
вообще не читают новую колонку. Единственная новая точка отказа —
внутри `_cmd_run`, до spawn агента, поэтому существующие тесты
`run`/`auto` (без пометки паузы, колонка по умолчанию 0) поведения не
меняют. Откат — удаление проверки в `runner.py` и модуля `pause.py`;
колонка в БД может остаться неиспользуемой без вреда (тот же класс, что
и у прошлых аддитивных миграций).

## Риски
Нет риска гонки паузы против уже стартовавшего шага: проверка стоит
строго до `spawn_agent`, поэтому пауза, поставленная параллельной
сессией во время работы агента, не имеет способа прервать уже идущий
процесс (AC-3) — она лишь не даст начаться следующему.
