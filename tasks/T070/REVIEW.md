# REVIEW: Команда pause — штатная приостановка задачи

## Фаза A — гейт плана

Диапазон, отданный на это ревью (`9b96765...HEAD`), сам по себе не
содержит правки пометки паузы — там только слияние T071 и подтяжка
main. Фактическая правка, закрывающая blocker итерации 1, лежит внутри
коммита-границы `9b96765` («T070: WIP-чекпоинт Оператора после паузы»):

печать+`return`), `orchestrator/auto.py` (`except SystemExit` отдельно

`config.AUTO_STOP_PAUSE`), `orchestrator/config.py` (`AUTO_STOP_PAUSE`),
`tests/test_auto_cycle.py` (`AutoStopsOnPauseRefusalTest`) и синхронно
обновлённый `tasks/T070/PLAN.md`. Читал эти файлы точечно (вне пакета),
т.к. без них нельзя было оценить, закрыт ли blocker итерации 1 — сам
диапазон диффа этого не показывает.

Обновлённый PLAN верно диагностирует причину прошлого blocker'а (шаг 3
итерации 1 полагался на аналогию с «отказ по чужой ветке worktree» без
эмпирической проверки) и меняет решение на `sys.exit`, тем же приёмом,
что `budget_block`/`parallel_limit.refusal` в той же функции — `_cmd_auto`
уже ловит `SystemExit` вокруг `runner.cmd_run`, поэтому цикл
останавливается на первой же попытке без нового канала связи. Шаг 3b
(отдельная проверка `pause.is_paused` внутри `except`, чтобы итоговое
сообщение называло именно паузу) — обоснован и напрямую покрывает п.2

не конфликтует с конвенциями, FSM/gates/roles не тронуты. Гейт плана —
пройден.

## Замечания

- major — `orchestrator/auto.py:110-127` (`except SystemExit` вокруг
  `runner.cmd_run` внутри `_cmd_auto`) — итоговое сообщение `auto
  остановлен` определяет причину остановки НЕ по тому, что реально
  вызвало этот конкретный `sys.exit`, а по независимому свежему опросу
  `pause.is_paused(store.get_task(conn, task_id))`. Если `sys.exit`
  фактически вызван ДРУГИМ отказом внутри `_cmd_run`, стоящим раньше
  проверки паузы по коду (`budget.budget_block`,
  `orchestrator/runner.py:86-88`, или `parallel_limit.refusal`,
  `orchestrator/runner.py:96-99`), а задача ПРИ ЭТОМ одновременно
  находится на паузе (обе пометки — независимые состояния, оператор
  может выставить оба: например, снизить бюджет команды `artel.py
  budget <id> <usd>` down и поставить `pause` на одну и ту же задачу,
  когда хочет остановить её понадёжнее), — `except`-блок всё равно
  считает причиной остановки паузу и печатает/журналирует «задача на
  паузе» + подсказку `artel.py resume <id> снимет пометку`, хотя
  реальная блокирующая причина — бюджет (или лимит параллельных задач)
  и `resume` её не снимет. Воспроизведено прогоном (сборка на
  `tasks/T070/acceptance_tests/_sandbox.py::PauseSandbox`, `budget_usd=1.0,
  spent_usd=2.0` + `pause.cmd_pause`, `state=in_dev`, вызов
  `auto.cmd_auto`):
  ```
  [T001] auto: старт из in_dev, лимит 30 шагов за вызов
  [T001] бюджет исчерпан: $2.00 из $1.00 — агент не запускается.
    подними потолок: artel.py budget T001 <usd>
    или закрой задачу: artel.py kill T001
  [T001] auto остановлен: задача на паузе
    состояние: in_dev
    дальше: artel.py resume T001 снимет пометку
  ```
  Настоящая причина (бюджет) видна только в предпоследнем блоке — том
  самом `print(str(exc))` двумя строками выше в `auto.py:114`; но
  итоговая строка `auto остановлен: ...` и журнальная запись (`auto_stop`,
  actor `operator`, action «auto остановлен») называют паузу и советуют
  `resume`, который проблему не решает: следующий `auto` после `resume`
  просто повторит тот же бюджетный отказ, на этот раз с верным итоговым
  сообщением. Не blocker — эффект ограничен одним лишним циклом
  «resume → auto → тот же отказ, уже с верной причиной», без потери
  данных, без некорректного перехода FSM; но это предсказуемо ломается
  при пересечении паузы с ЛЮБОЙ другой существующей причиной отказа
  `run`, а не гипотетический случай — обе пометки (`paused`,
  `budget_usd`/`spent_usd`) независимо выставляются Оператором, и
  сценарий «остановить понадёжнее — снизить бюджет и поставить паузу
  одновременно» правдоподобен для этой же самой задачи (штатная
  остановка). Предложение: в `except`-блоке определять причину не
  повторным опросом текущего `is_paused`, а по тому, что фактически
  журналировал именно этот вызов `runner._cmd_run` — например, сверкой
  последней записи журнала задачи после вызова с действием `"run
  отклонён: задача на паузе"` (её пишет `orchestrator/runner.py:118-120`
  непосредственно перед `sys.exit`, синхронно с самим отказом, а не
  постфактум), тем же приёмом, каким `_advance_refusal` в этом же файле
  (`orchestrator/auto.py:12-24`) уже находит запись, добавленную именно
  текущим вызовом, а не текущее состояние вообще. Тест: `budget_usd`/
  `spent_usd` выставлены так, что `budget_block` не `None`, отдельно
  `pause.cmd_pause` — итоговое сообщение `auto остановлен` обязано
  называть бюджет, не паузу.

## Вердикт

changes_requested — исправить п.1 (major): `_cmd_auto` должен различать
причину `SystemExit`, а не приписывать любой отказ паузе только потому,
что пометка паузы сейчас стоит — иначе сочетание паузы с бюджетным/
лимитным отказом даёт Оператору неверную итоговую подсказку. Добавить
тест на это пересечение (бюджет исчерпан + пауза одновременно →
итоговое сообщение называет бюджет).

## Предложения системе

- Класс дефекта «`_cmd_auto` восстанавливает причину остановки
  постфактум опросом текущего состояния вместо разбора того, что
  реально произошло в упавшем вызове» повторился на второй итерации той
  же задачи (сперва — потерянное различение из-за `print+return` без
  исключения, итерация 1; теперь — различение есть, но опирается на
  состояние, а не на факт конкретного отказа). Стоит завести для
  `_cmd_auto` единый принцип «причина стопа читается из журнальной
  записи ЭТОГО вызова» (уже есть для одного случая —
  `_advance_refusal`) и применять его последовательно ко всем веткам
  `except SystemExit`, а не изобретать отдельный опрос под каждую новую
  причину отказа `run`.
