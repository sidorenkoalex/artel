## Замечания

- major — `tests/test_canary.py:179-206,1084-1130` — пять новых тестов
  (`test_test_author_visited_true_when_tests_writing_in_journal:179`,
  `test_test_author_visited_false_when_tests_writing_skipped:194`,
  `test_ac1_spec_only_on_artifact_branch_goes_to_tests_writing:1084`,
  `test_ac2_skip_tests_on_artifact_branch_goes_to_in_dev:1104`,
  `test_ac3_spec_not_found_anywhere_kills_inconclusive_not_in_dev:1112`)
  не несут в докстринге явную заявку `Ловит мутацию: …`
  (skills/test-authoring.md, обязательный формат — см.
  review-checklist «Тесты»: «заявки нет вовсе → замечание»).
  `test_ac2_skip_tests_on_artifact_branch_goes_to_in_dev:1104` вообще
  без докстринга. Остальные четыре описывают сценарий/AC, но не
  формулируют claim о конкретной мутации, которую тест обязан ловить —
  для сравнения, все существующие тесты того же файла (например
  `MergesSinceLastGreenRunTest.test_red_verdict_is_ignored`) несут
  явное «Ловит мутацию: …». Последствие: без claim ревьювер (в том
  числе в следующей итерации) не может сверить тест с заявленным
  свойством, а не мысленным мутационным тестом по наитию — сама
  проверка, которую требует review-checklist, невозможна формально.
  Предложение: добавить каждому из пяти тестов докстринг с явным
  «Ловит мутацию: …», описывающим конкретную мутацию и наблюдаемое
  расхождение (благо по существу тесты вполне осмысленны — например
  для `test_ac2_…` это можно сформулировать как «мутация, роняющая
  чтение `skip_tests` из frontmatter артефактной ветки (например,
  игнорирование этого поля в `meta`), красит тест — ожидание `in_dev`
  не совпадёт»).

- minor — `ad24afa3` (слияние `origin/main` по инструкции ANSWER-2) —
  сообщение коммита дефолтное git-сообщение «Merge remote-tracking
  branch 'origin/main' into task/…», не в формате `<id>: <что сделано>`
  (skills/conventions-core.md). Последующая повторная подтяжка
  (`95f5eed2`) уже оформлена правильно («01M2A22CG2P0E69H00RDHFF3K4:
  подтяжка main»), так что расхождение — разовое и не создаёт риска на
  будущее, но для полноты: тот же класс стоит держать в уме при
  следующей ручной подтяжке через `git merge` без `-m`.
