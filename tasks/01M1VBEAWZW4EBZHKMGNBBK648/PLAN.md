# PLAN: ожидание зоны штатно в пульте — `auto --wait-zone`, `escalated` держит зону

## Подход

Два независимых, но пересекающихся по файлам изменения:

1. **`escalated` — занимающее состояние** (требование 5, AC-7/AC-8в):
   добавить `"escalated"` в `zone_lock.BLOCKING_STATES`. `_occupies`
   (старт developer после `_stay_since_id`) уже реализует нужный фильтр
   «занимает, только если уже начала код в текущем пребывании» — менять
   её не нужно, только диапазон состояний, которые `blocking_conflict`
   вообще сканирует как кандидатов.

2. **`auto <id> --wait-zone`** (требования 1-3,6-7, AC-1..AC-6,
   AC-8а/б): цикл `_cmd_auto`/`_role_run_step` при отказе `run`
   `zone_lock.REFUSAL_ACTION` сегодня безусловно возвращает `Stop`
   (`config.AUTO_STOP_ZONE_WAIT`). Новый параметр `wait_zone` (плюс
   `config.AUTO_WAIT_ZONE_DEFAULT`) переключает это место на цикл
   ожидания внутри `_role_run_step`: опрашивает `zone_lock.
   blocking_conflict` каждые `config.ZONE_WAIT_POLL_SEC`, продлевает
   heartbeat lease (`lease.acquire` тем же `session_id`, что уже держит
   `_cmd_auto` на входе), журналирует вход/выход ровно по одному разу
   (AC-2/AC-3), останавливается по потолку `config.ZONE_WAIT_MAX_SEC`
   (AC-4) — задача остаётся `in_dev`. После освобождения зоны —
   повторный `runner.cmd_run` ТЕМ ЖЕ вызовом (AC-3), без выхода из
   `_role_run_step`.

   Потолок считается НАКОПЛЕННЫМ временем опросов (счётчик секунд внутри
   самой функции ожидания), не разницей `store.now()`: секундная
   точность `store.now()` не различает опросы внутри одного и того же
   реального вызова (AC-8б гоняет несколько РЕАЛЬНЫХ опросов по
   `0.02`сек — доли секунды, `store.now()` их не различит).

   `status` (`catalog._zone_wait_suffix`, требование 4, AC-6) добавляет
   минуты ожидания, читая метку времени последней записи входа в
   ожидание (то же действие, что журналирует цикл ожидания) и вычисляя
   разницу со `store.now()` — независимый от `auto` снимок, тем же
   приёмом, что уже применяет сама функция для держателя/очереди.

3. **`docs/operator-session.md`** (требование 7, AC-9): раздел «Запуски
   и рабочие копии» описывает `--wait-zone` вместо внешнего
   `zone_wait_auto.sh`.

**Итерация 2 (REVIEW.md, реестр замечаний R1-F1/R1-F2):**
`orchestrator/auto.py::_wait_for_zone` внутри `while` обновляет
`path`/`occupier_id`/`occupier_state` из СВЕЖЕГО `conflict` на каждой
итерации опроса (не только до входа в цикл) — запись выхода теперь
называет фактического ПОСЛЕДНЕГО держателя при передаче зоны между
конкурентами (R1-F1, major). Возврат `lease.acquire` внутри того же
цикла больше не отбрасывается: живой чужой отказ останавливает цикл
именованной причиной `_ZONE_WAIT_LEASE_LOST_REASON` (R1-F2, minor) —
не только логируется, реализован «лучший» вариант из двух, предложенных
ревью.

## Шаги

1. `orchestrator/zone_lock.py`: `BLOCKING_STATES` += `"escalated"`.
   Обновить докстринг модуля (уже упоминает диапазон буквально).
2. `orchestrator/config.py`: `AUTO_WAIT_ZONE_DEFAULT` (bool, `False`),
   `ZONE_WAIT_POLL_SEC`, `ZONE_WAIT_MAX_SEC` — новые константы рядом с
   `AUTO_STOP_ZONE_WAIT`.
3. `orchestrator/auto.py`: `cmd_auto`/`_cmd_auto`/`_role_run_step`
   принимают `wait_zone: bool = False`; новая функция ожидания

   вместо немедленного `Stop`, когда `wait_zone or config.
   AUTO_WAIT_ZONE_DEFAULT` истинно.
4. `orchestrator/catalog.py`: `_zone_wait_suffix` добавляет минуты
   ожидания добавкой к уже показанному держателю.
5. `docs/operator-session.md`: правка раздела «Запуски и рабочие
   копии».
6. Юнит-тесты новых функций (`tests/test_auto_cycle.py` дополнить
   классом на `wait_zone`, `tests/test_zone_lock.py` — на `escalated`,
   `tests/test_catalog_status_log.py` — на минуты ожидания в `status`).
   Итерация 1 (R1-F4): диф ошибочно не содержал ни одного из трёх файлов
   — закрыто итерацией 2, шаг реально выполнен (см. «Реестр замечаний»
   REVIEW.md).

`orchestrator/artel.py` (парсинг флага `--wait-zone` из argv) сознательно
ВНЕ этого PLAN — файл не входит в `zones:` SPEC (4 файла, зоны и
бюджет посчитаны только под них — «Оценка объёма и деление»), а
расширение зон без мандата Оператора (раздел «## Расширение зон» +
ANSWER) — эскалация, которую этот параметр не заслуживает: требование
1/AC-5 полностью закрывается программным параметром `wait_zone` плюс
`config.AUTO_WAIT_ZONE_DEFAULT` (Оператор включает разом для ВСЕХ
вызовов правкой `config.py` — COMMON_ZONE, доступен без расширения).
CLI-флаг на каждый отдельный вызов — естественное расширение, но
отдельным MR поверх смерженных зон, если Оператор решит, что он нужен
вдобавок к глобальному дефолту.

## Влияние на систему

- `BLOCKING_STATES` += `"escalated"` расширяет диапазон, который
  сканирует `blocking_conflict`/`refusal`/`queue_position` — уже
  существующий фильтр `_occupies` (старт developer в текущем
  пребывании) не даёт задаче, ещё не начавшей код, ложно считаться
  занявшей; закрыто тестами AC-7/AC-8в на оба исхода и на границу
  пребывания отдельно.
- Цикл ожидания `--wait-zone` — новая ветка поведения ТОЛЬКО при явном
  флаге или включённой Оператором настройке (`AUTO_WAIT_ZONE_DEFAULT`
  дефолт `False`, AC-5) — сегодняшнее поведение `auto`/`run` без флага
  не меняется ни на бит, включая существующие `tests/test_auto*.py`
  (требование 6/AC-8, ассерты не правятся).
- Потолок ожидания (AC-4) не эскалирует — задача остаётся `in_dev`,
  так что существующие пути эскалации/бюджета не задеты.
- Heartbeat lease продлевается штатным `lease.acquire` (тот же
  `session_id`, что уже держит lease с начала `_cmd_auto`) — не новый
  механизм продления, переиспользование существующего.
- Откат: убрать `"escalated"` из `BLOCKING_STATES`, убрать параметр
  `wait_zone` и функцию ожидания — оба изменения независимо
  reversible, без миграций схемы БД (новых колонок не добавляется).

## Риски

- Потолок `ZONE_WAIT_MAX_SEC`/интервал `ZONE_WAIT_POLL_SEC` — значения
  не зафиксированы SPEC численно, выбраны по аналогии с
  `VERIFYING_POLL_INTERVAL_SEC`/`LEASE_STALE_AFTER_SEC` (см. комментарий
  в `config.py`). Оператор может счесть их не подходящими — меняются
  без миграции, только константа.
- Требование 1/AC-1 названы буквально `auto <id> --wait-zone` (CLI-
  синтаксис), но `zones:` SPEC не включает `orchestrator/artel.py` (где
  живёт разбор argv) — решение: реализовать параметр `wait_zone`
  программно + `config.AUTO_WAIT_ZONE_DEFAULT` (закрывает AC-1..AC-9
  дословно, все они зовут `cmd_auto` напрямую, не через CLI), argv-флаг
  не заводить в этом MR. Если Оператору нужен именно per-вызов CLI-флаг
  поверх уже работающего глобального дефолта — отдельная маленькая
  задача на `orchestrator/artel.py` (одна строка диспетчера).
