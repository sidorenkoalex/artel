# SPEC: ожидание зоны штатно в пульте — `auto --wait-zone`, `escalated` держит зону

## Контекст

За 05–06.09 внешний ожидатель зоны (сценарий `zone_wait_auto.sh` сессии
Оператора: опрос `status` раз в 90 секунд, при свободной зоне — `auto`)
применялся 9 раз, потому что `auto` при отказе «ждёт зоны»
(`zone_lock.REFUSAL_ACTION`) останавливается
(`auto._run_zone_wait_refusal`), и цикл нужно перезапускать руками
после мержа держателя. Оба наблюдавшихся сбоя такого внешнего
ожидателя — из дыр самой механики занятости зоны: (а)
`zone_lock.BLOCKING_STATES` не включает `escalated` — задача с уже
начатым кодом на время эскалации (бюджет, вопрос, конфликт подтяжки)
отпускает зону, и внешний ожидатель успевает запустить соседнюю задачу
по тем же файлам (06.09, две пары задач параллельно правили
`doctor.py`, конфликт переехал на подтяжку main); (б) зависимость
порядка старта («после мержа X») пульт вообще не исполняет — это
отдельный механизм (`after:` в SPEC), не предмет этой задачи (см. «Не
входит» и «Оценка объёма и деление»).

Эта задача закрывает штатную поддержку ожидания зоны ВНУТРИ `auto`
(режим `--wait-zone`) и дыру (а) — `escalated` перестаёт молча отпускать
зону, которую задача уже начала занимать. Источник: аудит обходных
сценариев Оператора 06.09 (решение «заводи»); строки копилки 06.09 и
бэклога «Ожидание зоны штатно в пульте».

## Требования

1. `auto <id> --wait-zone` (и настройка по умолчанию в config,
   управляющая тем же поведением для всех вызовов `auto` без явного
   флага, — Оператор включает её сам, если решит): при отказе «ждёт
   зоны» (`zone_lock.REFUSAL_ACTION`) цикл не останавливается, а ждёт —
   опрашивает `zone_lock.blocking_conflict` с интервалом
   `config.ZONE_WAIT_POLL_SEC`, на каждом опросе продлевает heartbeat
   lease задачи. Сообщения (журнал/`status`) при нескольких конкурентах
   за одну и ту же зону называют очередь тем же приёмом, что уже
   применяют существующие `status`/`doctor` (`zone_lock.queue_order`/
   `queue_position`).
2. Вход в ожидание пишет РОВНО одну запись журнала «ждёт зоны <путь>:
   держит <id> (<state>)»; освобождение зоны (конкурент перестал её
   занимать) пишет РОВНО одну запись «зона свободна через N мин, держал
   <id>», после чего цикл продолжает как обычно (переходит к запуску
   роли).
3. Потолок ожидания `config.ZONE_WAIT_MAX_SEC`: по истечении цикл
   останавливается с именованной причиной — задача остаётся в `in_dev`,
   НЕ переводится в `escalated`.
4. `status` показывает время ожидания зоны в минутах для заблокированной
   задачи — добавкой к уже показываемому держателю зоны
   (`catalog.cmd_status`), а не только внутри собственного вывода цикла
   `auto`.
5. `escalated` считается занимающим состоянием НА ТЕХ ЖЕ условиях, что и
   остальные состояния диапазона `in_dev`…`merge_gate` (`zone_lock.
   BLOCKING_STATES`): держит зону, только если в ТЕКУЩЕМ пребывании уже
   был старт developer (тот же признак, что и сегодня проверяет
   `zone_lock._occupies`). Граница пребывания (последняя запись `"state
   -> tests_writing"`) не меняется.
6. Существующие `tests/test_zone_lock.py`, `tests/test_zones_gate.py`,
   `tests/test_auto*.py` остаются зелёными без правки их ассертов;
   каждый новый тест ловит заявленную мутацию (в частности: мутация
   «потолок ожидания не действует» красит новый тест на потолок,
   мутация «`escalated` не проверяет старт developer» красит новый тест
   на `escalated`).
7. `docs/operator-session.md`, раздел «Запуски и рабочие копии»:
   внешние ожидатели зоны (сценарий вида `zone_wait_auto.sh`) больше не
   нужны — раздел описывает режим `--wait-zone` вместо них.

## Критерии приёмки

AC-1. `auto <id> --wait-zone` при отказе «ждёт зоны» не останавливает
цикл, а ждёт: опрашивает `zone_lock.blocking_conflict` с интервалом
`config.ZONE_WAIT_POLL_SEC` и на каждом опросе продлевает heartbeat
lease задачи.

AC-2. Вход в ожидание зоны пишет ровно одну запись журнала «ждёт зоны
<путь>: держит <id> (<state>)».

AC-3. Освобождение зоны (конкурент перестал её занимать) пишет ровно
одну запись журнала «зона свободна через N мин, держал <id>», и цикл
`auto` продолжает — стартует роль developer тем же вызовом, без ручного
перезапуска.

AC-4. По истечении потолка ожидания `config.ZONE_WAIT_MAX_SEC` цикл
останавливается с именованной причиной; задача остаётся в `in_dev`, не
переводится в `escalated`.

AC-5. Конфигурационная настройка включает поведение `--wait-zone` по
умолчанию для ВСЕХ вызовов `auto`, без необходимости передавать флаг на
каждый вызов; значение по умолчанию не меняет сегодняшнее поведение
(режим ожидания включён только при явном выборе — флагом или этой
настройкой).

AC-6. `status` показывает время ожидания зоны в минутах для задачи,
сейчас заблокированной занятостью зоны.

AC-7. `escalated` считается занимающим зону состоянием на тех же
условиях, что и остальные состояния диапазона `in_dev`…`merge_gate`:
задача в `escalated`, в текущем пребывании которой уже был старт
developer, держит зону; задача в `escalated` без такого старта — не
держит. Граница текущего пребывания (последняя запись `"state ->
tests_writing"`) не меняется этой задачей.

AC-8. Существующие `tests/test_zone_lock.py`, `tests/test_zones_gate.py`,
`tests/test_auto*.py` проходят без правки их ассертов; новые тесты
покрывают: (а) `--wait-zone` в песочнице с занятой зоной ждёт и после
`done`/`killed` держателя стартует developer тем же вызовом, журнал несёт
вход и выход с длительностью ожидания; (б) исчерпанный потолок ожидания
останавливает цикл (мутация «потолок не действует» красит тест); (в)
задача в `escalated` со стартом developer в текущем пребывании держит
зону для других кандидатов, без такого старта — не держит.

AC-9. `docs/operator-session.md`, раздел «Запуски и рабочие копии»,
описывает режим `--wait-zone` вместо внешнего ожидателя (внешний
скрипт-ожидатель зоны больше не нужен).

## Оценка объёма и деление

Полный объём ТЗ Оператора для этой задачи нёс три пункта: (1) `auto
--wait-zone`, (2) `escalated` как занимающее состояние, (3) поле SPEC
`after:` — зависимость старта от завершения других задач (со своим
guard, предусловием старта developer, подсказкой `new` и проверкой
циклов зависимостей в doctor). Вместе все три пункта задевают ≥5
файлов зоны (модуль ожидания зон, каталог статуса, доктор, guard,
конфиг) — сигнал ТЗ явно предвидел это и предложил на выбор монолит
(«один узел ожидания для зон и зависимостей») либо нарезку «п.1+2 /
п.3».

Решение аналитика — **нарезка**, не монолит: пункт (3) по тексту ТЗ сам
явно требует «тот же механизм и то же ожидание (п.1)» — то есть
физически не может быть сделан раньше, чем механизм ожидания из п.1
существует и смержен; это ровно тот случай, когда первая часть несёт
механику, на которую опирается вторая (`skills/spec-authoring.md`).
Кроме того, отдельно взятые пункты (1)+(2) — самостоятельно мержимая,
законченная и полезная задача (штатное ожидание зоны и корректная
занятость на эскалации), не оставляющая систему в промежуточном
нерабочем состоянии; то же верно для пункта (3) отдельно, если он
стартует уже поверх смерженного механизма ожидания.

**Эта SPEC сужена до части «п.1+2»** (полностью описана выше —
Требования 1-3,5-7, AC-1..AC-9); зоны и бюджет посчитаны только для неё
(4 файла, 9 критериев — сигнал «число файлов» этой части не срабатывает,
только «до 10» критериев по счётчику guard, что и определило класс
бюджета $45).

**Часть «п.3»** — отдельная задача, которую заводит Оператор (у роли
analyst в рамках этого шага нет доступа к общей БД пульта вне своего
worktree, командой `cmd_new` эту задачу завести не из чего — см.
«Предложения системе» ниже) ПОСЛЕ мержа этой. Её объём по ТЗ: поле SPEC
`after: <id>[, <id>]` (необязательное, список ULID; guard проверяет
только ФОРМАТ элементов как правдоподобных идентификаторов задачи — по
образцу уже существующей проверки образца ULID в приёмочных тестах,
БЕЗ обращения к БД: guard сегодня нигде не читает состояние задач, это
архитектурное свойство, не пробел этой задачи); предусловие первого
шага developer — все перечисленные задачи в `done`/`killed`, иначе
отказ «ждёт задачи <id> (<state>)» ТЕМ ЖЕ механизмом ожидания и тем же
`--wait-zone`, что уже смержен этой задачей; `new` переносит строку
«Порядок: после …» из ТЗ в подсказку аналитику (не парсит ULID из
прозы); doctor предупреждает о циклах зависимостей между живыми
задачами (A→B→A и длиннее). Родительская задача для неё —
01M1VBEAWZW4EBZHKMGNBBK648 (эта).

## Не входит

- Поле SPEC `after:`, его guard, предусловие старта developer по
  зависимости задач, подсказка `new` и проверка циклов зависимостей в
  doctor — часть «п.3», отдельная задача (см. «Оценка объёма и
  деление»), стартует после мержа этой.
- Разрез толстых файлов на пакеты проверок (задача 01M1TT9BPB, уже
  ведётся отдельно).
- Замок на время шага (рычаг 3 анализа 06.09, отдельный ADR).
- Явный флаг/настройка отключения `--wait-zone` (`--no-wait-zone` или
  подобная) — ТЗ такого не просит.
- Порядок старта задач, зависящий от смысла (не от пересечения файлов
  зон) — та зависимость, что решает часть «п.3»; эта задача решает
  только занятость зоны и `escalated`.

  SPEC, а не буквальный вызов `cmd_new` ролью.
