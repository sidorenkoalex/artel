# REVIEW: Пересечение зон при заведении и аддитивные конфликты документов при подтяжке main

## Гейт плана (фаза A)

1. **Покрытие SPEC шагами полно.** Таблица PLAN несёт все 11 требований
   (1→шаги 1-2, 2→2, 3→1-2, 4-9→3, 10→4, 11→5); фактический дифф ровно
   этим и ограничен — 4 файла кода/документа + 4 новых тестовых файла,
   ничего вне зон SPEC (`docs/codebase-map.md` — `COMMON_ZONES`).
2. **Шаги — проверяемые единицы.** Ни микрооперации, ни «сделать всё»:
   каждый шаг — один модуль плюс его тесты.
3. **Подход не конфликтует с архитектурой.** Прогноз собран из тех же
   примитивов (`_own_paths`/`_shared_zone`/`_paths_overlap`), отказ
   `blocking_conflict`/`refusal` не тронут; авторазрешение подтяжки
   расширяет одну существующую ветку `_handle_merge_failure`.
4. **Пробелы плана** (оба вылились в замечания ниже): PLAN «Риски»
   разбирает у union-слияния только ПОРЯДОК добавок, но не то, что
   union дублирует строки базы при двух близких хунках (R1-F1); PLAN
   нигде не проверил, что колонка `tasks.zones` у состояний
   `spec_writing`/`spec_gate` ещё пуста (R1-F2) — то есть «Влияние на
   систему» описало механику, которая для двух из трёх заявленных
   состояний не наблюдаема.

## Замечания

- **blocker — orchestrator/pull.py:214** (`_union_merged_text`, вместе с
  `_side_is_additive` на :193) — union-слияние по трём стадиям объявляет
  конфликт аддитивным и коммитит результат, в котором строки БАЗЫ
  продублированы, а добавка ветки попала в чужой раздел документа. Обе
  стороны при этом честно аддитивны (`numstat` = «2 добавлено, 0
  удалено» у каждой), поэтому сверка требования 5 проходит, а
  требование 8 (fail-closed) не срабатывает: git ответил успешно на все
  шаги. Сценарий поломки — воспроизведён прогоном ПРОДУКТОВОГО пути
  (`pull.evaluate` в `RealGitSandbox`, см. «Проверено исполнением»): база
  документа `## Open / - open: A / ## Closed / - closed: B`, ветка
  добавляет по пункту в оба списка, main — тоже по пункту в оба;
  расстояние между хунками (2 строки базы) меньше контекста git, git
  склеивает их в одну конфликтную область, и `merge-file --union`
  конкатенирует области целиком. Итог, который пульт коммитит как
  удачную подтяжку (`Pulled`, задача остаётся в `in_dev`, эскалации нет):
  `## Open / - open: A / - open: MAIN / ## Closed / - closed: B /
  - closed: MAIN-C / - open: BRANCH / ## Closed / - closed: B /
  - closed: BRANCH-C` — заголовок `## Closed` и пункт `- closed: B`
  встречаются ДВАЖДЫ, а `- open: BRANCH` оказался внутри раздела
  «Closed». Это ровно класс документов, на котором задача и построена
  (растущие вниз списки `docs/operator-session.md`, бэклог, копилка), и
  до задачи такой конфликт уходил в безопасную эскалацию. Порог
  срабатывания проверен отдельно: дублирование возникает при зазоре база
  ≤ 3 строк между хунками, при 4 и больше — итог корректен.
  Предложение: после union добавить fail-closed пост-проверку, что итог
  есть РОВНО «база плюс добавки» — число строк итога == число строк
  стадии базы + колонки «добавлено» обоих `--numstat` (они уже
  считаются в `_side_is_additive`); расхождение закрывает путь
  автоматики и эскалирует прежним текстом. На разобранном сценарии
  проверка ловит дефект (4 + 2 + 2 = 8 против 9 строк итога), на
  сегодняшнем зелёном тесте — нет (3 + 1 + 1 = 5 == 5). Если Оператор
  предпочтёт принять дублирование как штатное, это решение уровня
  SPEC/ADR, и тогда оно обязано появиться в `docs/stack.md` и в PLAN
  «Риски» — сегодня оба обещают обратное («ни одна строка не
  выбрасывается» читается как «документ остаётся корректным»). Вопрос 1
  эскалации.

## Вердикт

`escalate`. Механика собрана аккуратно и почти вся проверяема
исполнением (fail-closed ветки подтяжки закрыты все четыре, порядок
добавок и единственность коммита подтверждены прогоном), но два
замечания упираются в сам SPEC, а не в исполнение:

- R1-F1 — предписанный требованием 5 механизм не держит обещание
  безопасности, на котором построено требование 8: есть достижимый
  вход, где пульт не эскалирует и не теряет строк, а тихо портит
  документ дублированием;
- R1-F2 — требования 1 и 3 опираются на данные, которых в БД до гейта
  SPEC нет, а минимальная починка лежит в файле, который SPEC отнёс к
  «только чтение».

Обе развилки — решение Оператора; код в обоих случаях соответствует
букве SPEC, поэтому ни `changes_requested`, ни `approved` честными не
будут. R1-F3, R1-F4, R1-F5 — обычные замечания разработчику, ответа
Оператора не требуют и закрываются в следующей итерации тем же id.

## Эскалация

- **Вопросы**

  1. (блокирует R1-F1 и требование 5) `git merge-file --union` при двух
     аддитивных хунках в пределах 3 строк базы дублирует строки базы и
     переставляет добавку ветки в чужой раздел; сверка аддитивности
     сторон этого не видит (обе стороны честно «+N, −0»), git отвечает
     кодом 0, и пульт коммитит порчу как удачную подтяжку. Варианты:
     **(A)** добавить в `orchestrator/pull.py` fail-closed
     пост-проверку «итог union == число строк стадии базы + добавки
     обеих сторон» (числа уже считаются `--numstat`), расхождение —
     прежняя эскалация; **(B)** признать дублирование штатным и
     зафиксировать это в `docs/stack.md` и PLAN «Риски» (сегодня оба
     обещают обратное), решением уровня ADR; **(C)** снять аддитивное
     слияние документов из задачи, оставив только требование 9 (карта
     вместе с документами). **Дефолт при молчании — (A)**: он держится
     внутри зон задачи, не спорит с требованием 5 (механизм слияния
     остаётся `merge-file --union`) и продолжает требование 8 в ту же
     сторону, что SPEC уже выбрал, — «сомнение решается в пользу
     прежней эскалации».
  2. (блокирует R1-F2 и требования 1, 3) Колонка `tasks.zones`
     заполняется только на approve spec_gate
     (`orchestrator/fsm.py:794`), поэтому прогноз никогда не видит
     кандидатов в `spec_writing`/`spec_gate` и никогда не ставит им
     добавку `status` — то есть ровно волна из «Контекста» SPEC не
     ловится. Варианты: **(A)** разрешить этой задаче правку
     `orchestrator/fsm_advance.py` (SPEC отнёс его к «только чтение») —
     писать `zones` там же, где уже применяется потолок SPEC, на
     переходе `spec_writing -> spec_gate` (одна строка; делает живыми
