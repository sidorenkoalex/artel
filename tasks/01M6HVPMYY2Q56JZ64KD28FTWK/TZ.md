# ТЗ: Надзор эпика: перезапуск остановленных задач, места параллельности, завершение, answer при ожидании зоны

# Надзор эпика: перезапуск остановленных задач, места параллельности, завершение и ответ Оператора при ожидании зоны

## Факты

Строки копилки 26.10–03.11 (волна 2 линии GitLab, эпик E01M5W66QH7MNY4XWVRTP4TAWRP): каждый пункт ниже потребовал ручного `epic retry` или обхода и давал простой задач.

1. После `reject` на `verifying`, после `amend-tests`, после `stop`/`pause --now` + `resume` надзор эпика (`auto --epic`, `orchestrator/auto.py`) задачу сам не перезапускает: запись «дочерний auto вышел без записи об остановке», задача стоит.
2. Задача с циклом, остановленным штатно в ожидании зоны, не перезапускается, когда держатель зоны влит: две задачи стояли в очереди к одному файлу с пометкой «не держит очередь» без держателя (`orchestrator/zone_lock.py`, `queue_wait`, `_holds_queue`).
3. Задачи, ждущие зону, занимают места лимита параллельности надзора: новая задача эпика не стартовала, пока две другие ждали файл.
4. Надзор завершается «все задачи эпика окончательны» в окне между мержем последней задачи и заведением следующей (`new … --epic`), хотя эпик открыт.
5. `answer` отказывает «задачу прямо сейчас ведёт процесс», пока цикл задачи только ждёт зону или CI без агентного шага (`orchestrator/answer.py`); указание Оператора не доставлялось 2 часа, понадобились `stop`, `answer`, `epic retry`.

## Требуется

1. **Перезапуск надзором**: задача эпика в незавершённом состоянии с ролью, которая может идти (не на гейте Оператора, не на паузе, не в эскалации), без живого дочернего `auto` — перезапускается на ближайшем опросе надзора, независимо от причины выхода прежнего цикла (reject, amend-tests, stop, resume, падение процесса). Повторный перезапуск после подряд идущих аварийных выходов — с паузой и пределом (как сейчас для агентных сбоев); после предела — алерт, не бесконечный цикл.
2. **Освобождение зоны**: когда держатель зоны уходит в окончательное состояние, первая задача очереди к этой зоне с остановленным циклом перезапускается надзором (или любым запуском `auto`), не ожидая ручного `epic retry`.
3. **Лимит параллельности** считает только задачи с идущим агентным шагом или готовые к нему; задачи, ждущие зону, CI или Оператора, место не занимают.
4. **Завершение надзора**: надзор открытого эпика (не `epic close`) не завершается сам при всех окончательных задачах — ждёт новых задач эпика с опросом раз в N минут; завершается по `epic stop` или закрытию эпика.
5. **`answer` при ожидании**: когда цикл задачи держит lease, но агентного шага нет (ожидание зоны, CI, гейта), `answer` кладёт ANSWER-n и возвращает подсказку «дойдёт до роли на следующем шаге» — как при отсутствии цикла; при идущем агентном шаге — прежний отказ.

Критерии приёмки (песочница, подменённые процессы `auto` и часы):
- для каждой причины выхода из п. 1 — надзор перезапускает задачу на следующем опросе; три аварийных выхода подряд — алерт и остановка перезапусков;
- держатель зоны влит → первая задача очереди со остановленным циклом запущена без `epic retry`; вторая в очереди — нет;
- две задачи ждут зону, лимит 2 → третья, готовая к шагу, стартует;
- все задачи эпика окончательны, эпик открыт → надзор жив; новая задача эпика стартует; `epic stop` → надзор завершён;
- `answer` при цикле, ждущем зону → ANSWER-n создан; при идущем агентном шаге → отказ как сейчас;
- гейты Оператора, пауза и эскалация задачу не перезапускают (надзор не обходит гейт — инвариант 18).

Зоны: `orchestrator/auto.py`, `orchestrator/zone_lock.py` (только признак остановленного цикла и выбор первой задачи очереди), `orchestrator/answer.py` (только проверка lease), `orchestrator/epics.py` (только признак открытого эпика для надзора), `tests/` (долгоживущие файлы задачи).

Только чтение: `orchestrator/fsm.py`, `orchestrator/lease.py`, `orchestrator/runner.py`.

Существующие тесты: правка — нет ожидаемой; если тесты закрепляют прежнее завершение надзора или счёт лимита — эскалация с перечнем.

Не входит: поведение `auto <id>` вне эпика сверх п. 2 и п. 5; доска и `watch`.
