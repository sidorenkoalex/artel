# SPEC-AUDIT: G2а-2 — выкладка планки компонента по `plank_layout` и `plank-run` по правилу планки

Третий аудит, после второго возврата с гейта SPEC (решение Оператора №2, пункты 1–6). Сверка — по рабочему каталогу (main `c2dc427f`, голова ветки `f039c1ad`; код в `orchestrator/` с `c2dc427f` не менялся).

## ТЗ и SPEC
Решения Оператора №1 (пункты 1–7) остались в SPEC; решения №2 перенесены полностью:
- п. 1: `--ignore` только при команде pytest; AC-6 дополнен веткой полного набора `pytest-own` без `report`. Где: требование 7, AC-6.
- п. 2: нормализация пути, отказ на «.», «..» и пустом сегменте, критерий на `a/./<id>` и `.artel-plank/../src/<id>`. Где: требование 3 (первый пункт), AC-4.
- п. 3: последний сегмент в точности равен «<id>». Где: требование 3, AC-4.
- п. 4: отказ «нет plank_layout» — только при выкладке файлов компонента; долгоживущий `plank-run` и прогон только `extra` прежние; проверка требования 6 идёт после этого отказа. Где: требование 5, AC-11.
- п. 5: у правила по умолчанию текст отказа `plank-run` прежний. Где: требование 8, AC-7.
- п. 6: третий случай касается только `components:`, `test_profile` — всегда прежнее поведение. Где: требование 5, AC-5.

Требования ТЗ п. 1–7, критерии ТЗ и решения по умолчанию ТЗ отражены (требования 1–10, «Не входит»). Требований сверх ТЗ и решений Оператора нет.

Расхождение:
1. **Условие «report, отличным от pult-pytest» (SPEC требование 5, AC-5) по коду всегда истинно.** Формулировка дословно повторяет решение Оператора №2 п. 6, но `pult-pytest` в коде — значение `runner`, а не `report`:
   - `PROFILE_RUNNER_DEFAULT = "pult-pytest"` — `orchestrator/targets.py:69`;
   - у компонента `report` бывает только `junit-xml` или `pult-vitest`, либо поля нет — `orchestrator/targets.py:106`, `:449-452`.

   Буквально условие сужается до «любой компонент записи `components:`», в том числе без `report`. ТЗ п. 2 ограничивал отказ компонентом «с отчётом». Возможны два прочтения:
   - (а) «`report` задан» — как в ТЗ;
   - (б) «любой компонент `components:`» — как в тексте SPEC.

   Для `pult-vitest` и для `junit-xml` оба прочтения дают одно и то же. Расходятся они только на компоненте `components:` без `report` с командой не pytest. Решить это может Оператор на гейте.

## Пути обхода гейтов
Прежние обходы закрыты:
- сегмент «.» — требование 3, первый пункт;
- «<id>» внутри сегмента — требование 3, второй пункт;
- отказ «нет plank_layout» на путях без выкладки — требование 5, AC-11;
- пустая маска у умолчания — требование 8.

Остались:
3. **Порядок отказа правила (требование 1) и путей без выкладки (требование 5, AC-11) не задан.** Требование 1 велит отказывать «подготовке прогона и `plank-run`» без оговорок, а требование 5 и AC-11 оставляют прежними побайтно `plank-run` долгоживущего файла (`orchestrator/plank_run.py:221-229`) и прогон только `extra` (`orchestrator/acceptance.py:1337-1339`). Для правила с `refusal` (`pult-vitest` без `tests`, `orchestrator/project_profile.py:473-477`) не сказано, какой из двух исходов у этих путей. Не сказано и чей текст побеждает у `pult-vitest` без `tests` и без `plank_layout`: `refusal` правила или «нет plank_layout». Тест, написанный на одно прочтение, красит реализацию другого. Пункт решается одной строкой на гейте.
4. (риск, не отклонение) Профиль из отклонения 2 при буквальном исполнении остаётся без выкладки. AC это не ловят — см. «Проверяемость».

## Вердикт
**concerns** — SPEC годна к гейту. Решения Оператора №1 и №2 перенесены полностью, адреса SPEC сходятся с кодом. Отклонения решаются уточнением Оператора:

1. Условие «report, отличным от pult-pytest» (SPEC требование 5, AC-5; решение Оператора №2 п. 6) по коду всегда истинно: `pult-pytest` — значение `runner` (`orchestrator/targets.py:69`), а `report` бывает только `junit-xml` или `pult-vitest` (`orchestrator/targets.py:106`). 3. Не задан порядок отказа правила (требование 1, AC-3) и прежних путей без выкладки (требование 5, AC-11) для правила с `refusal` (`orchestrator/plank_run.py:221-229`, `orchestrator/acceptance.py:1337-1339`, `orchestrator/project_profile.py:473-477`).
