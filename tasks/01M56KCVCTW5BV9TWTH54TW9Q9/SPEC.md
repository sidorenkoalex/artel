# SPEC: Окружение шага роли внешнего проекта: PATH, сводка и логи suite-run

## Контекст
PATH роли состоит только из каталогов объявленных инструментов
(`orchestrator/runner.py::_role_path_dirs`). Прогон `pytest-own`
наследует PATH вызывающего процесса (`orchestrator/acceptance.py::_own_env`:
`_OWN_INHERITED_VARS = ("PATH", "LANG", "LC_ALL")`). Поэтому `suite-run`
из шага роли на sled 01M55SKHZ293CCAK0N7T4H7ZMR дал 201 ложное падение
(`FileNotFoundError: 'bash'` — 196, `'date'` — 5). Гейты пульта этого не
видят: они гоняют набор из своего процесса с полным PATH. Кроме того,
разбор итоговой строки pytest (`acceptance._RUN_CATEGORY`) не знает слова
`deselected`. На строке sled «201 failed, 4309 passed, 1156 skipped,
4 deselected, 13 warnings in 52s» он взял хвост «13 warnings in 52s» и
показал «прошло: 0, упало: 0». И наконец: если исполняемого файла команды
профиля нет, `FileNotFoundError` в `acceptance.run`/`collect`/`run_plank`
не перехвачен, и пользователь видит трейсбек вместо отказа.

Места запуска профиля `pytest-own` ниже — восемь мест перечня `PLACES`
долгоживущего теста
`tests/test_01m52eefna1wh31962hvnt0yz9_pytest_own_places.py`:
`acceptance.run`, `acceptance.collect`, `acceptance.run_repeat`,
`acceptance.run_plank`, `_run_full_suite_now` без observe,
`_run_full_suite_now` с observe, `_run_full_suite_to_log`,
`two_sided._run_side`.

## Требования

1. PATH прогона `pytest-own` в каждом из восьми мест запуска профиля
   (всё, что идёт через `acceptance._place_env` → `_own_env`, включая
   `two_sided._run_side`) собирается так, в порядке приоритета:
   (а) PATH вызывающего процесса без изменений, как сегодня;
   (б) каталог исполняемого файла первой команды профиля `command[0]`:
   - абсолютный путь — его каталог;
   - относительный путь, содержащий `/` (например `.venv/bin/pytest`), —
     его каталог, разрешённый от `workdir` профиля (оттуда же его
     разрешает запуск процесса);
   - голое имя — каталог файла, который находит поиск по PATH
     вызывающего;
   - голое имя, которое поиск по PATH не находит, — шаг (б) пропускается;
     сборка PATH при этом не падает, а сам запуск даёт отказ требования 3;
   (в) `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`.
   Каталог из (б) и (в) добавляется в конец, только если его ещё нет в
   PATH; повторов нет. `PATH`, заданный в `test_profile.env`, по-прежнему
   перекрывает собранное значение (явное решение Оператора в
   `targets.yaml`). Сам PATH прогона из процесса пульта и из шага роли
   разный (он начинается с PATH вызывающего); одинаково для обоих случаев
   наличие в нём каталогов (б) и (в).
   Обоснование порядка (ANSWER-1, ответ 3 — вариант A): у процесса пульта
   PATH уже содержит каталог `command[0]` и системные каталоги, поэтому
   прогоны гейтов не меняются. У роли первыми остаются каталоги
   объявленных инструментов, и интерпретатор пульта не затеняется.
   Добавки в хвосте закрывают `bash`/`date` и не перехватывают уже
   найденные команды. PATH самого процесса роли (`runner.role_env`) не
   меняется.
2. Разбор итоговой строки прогона (`acceptance.run_summary_line` и всё,
   что считает по ней «прошло/упало/пропущено», в том числе
   `suite-run`) узнаёт категорию `deselected` наряду с уже известными
   `xfailed`/`xpassed`. На строке sled из «Контекста» берётся вся
   итоговая строка, и счёт выходит такой: прошло 4309, упало 201,
   пропущено 1156.
3. Если исполняемого файла команды профиля нет (`FileNotFoundError` при
   запуске), каждое место запуска профиля в `orchestrator/acceptance.py`
   (первые семь мест перечня) завершает прогон именованным отказом с
   текстом «команда профиля <имя> не найдена», где <имя> — `command[0]`.
   Трейсбека нет. Отказ идёт тем же каналом, что сегодняшний отказ
   `workdir` этого места:
   - `acceptance.run`, `acceptance.collect` — `(False, текст отказа)`;
   - `acceptance.run_repeat` — красный повтор (`RedTest`) каждого файла с
     текстом отказа;
   - `acceptance.run_plank` — код `REFUSED_EXIT_CODE` и текст отказа;
   - три пути полного прогона — «прогон не начат»: вывод с префиксом
     `FULL_SUITE_NOT_STARTED`, итог классифицируется как
     `FULL_SUITE_NOT_STARTED` (не «красный прогон»), в кеш итогов
     полного прогона не сохраняется и при следующем прогоне повторно не
     используется.
   `two_sided._run_side` сохраняет свой текст отказа («pytest не
   запустился: …»); `FileNotFoundError` наружу не выходит и там.
4. У артели (профиль `pult-pytest`) argv, окружение и `cwd` прогонов не
   меняются. Это свойство закрепляется тестом до правки кода.

## Критерии приёмки

AC-1. Учебный проект с профилем `pytest-own` прогоняется зелёным при
урезанном PATH «как у роли», в котором нет `/usr/bin` и `/bin`, а есть
только каталог интерпретатора. Команда профиля — обёртка, которая
вызывает `bash` и `date` по имени. Прогон идёт и через
`acceptance.run_plank`, и через полный прогон набора. Падений
`FileNotFoundError` по `bash`/`date` нет.

AC-2. В каждом из восьми мест перечня `PLACES`
(`tests/test_01m52eefna1wh31962hvnt0yz9_pytest_own_places.py`) PATH,
который получает прогон `pytest-own`, начинается с PATH вызывающего без
изменений. Затем идёт каталог `command[0]` (если его не было), затем те
из `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`, которых не было, в этом
порядке, без повторов. Если `test_profile.env` задаёт `PATH`, прогон в
каждом из этих мест получает ровно это значение.

AC-3. Каталог (б) требования 1 по видам `command[0]`: для абсолютного
пути — его каталог; для относительного пути с `/` — его каталог,
разрешённый от `workdir` профиля, а не от каталога вызывающего процесса;
для голого имени, которое поиск по PATH вызывающего не находит, PATH
прогона — PATH вызывающего плюс недостающие каталоги (в), без каталога
(б), и сборка PATH не бросает исключения.

AC-4. `acceptance.run_summary_line` на выводе, который заканчивается
строкой «201 failed, 4309 passed, 1156 skipped, 4 deselected, 13 warnings
in 52s», возвращает всю эту строку. `suite_run.parse` на том же выводе
даёт прошло 4309, упало 201, пропущено 1156.

AC-5. Профиль `pytest-own`, чья первая команда указывает на
несуществующий исполняемый файл, в каждом из восьми мест перечня
`PLACES` не выпускает `FileNotFoundError` наружу. В семи местах
`orchestrator/acceptance.py` отказ несёт текст «команда профиля <имя> не
найдена» (<имя> — `command[0]`) и идёт каналом места: `run`/`collect` —
`(False, текст)`; `run_repeat` — `RedTest` каждого файла с этим текстом;
`run_plank` — `REFUSED_EXIT_CODE` и этот текст; каждый из трёх путей
полного прогона — вывод с префиксом `FULL_SUITE_NOT_STARTED`. В
`two_sided._run_side` — отказ со своим текстом «pytest не запустился: …».

AC-6. Полный прогон гейта, отказавший с «команда профиля <имя> не
найдена», даёт итог `FULL_SUITE_NOT_STARTED`, а не «красный прогон», и не
записывает итог в кеш итогов полного прогона: следующий полный прогон
того же дерева после появления команды выполняется заново, а не берёт
прежний итог из кеша.

AC-7. У проекта артели (профиль `pult-pytest`) argv, окружение (в том
числе `PATH`) и `cwd` прогонов те же, что до правки. Ожидание в тесте —
независимое литеральное значение: argv и `cwd` — литералы, окружение —
`os.environ` процесса теста плюс `PYTHONPYCACHEPREFIX`; ожидание не
вычисляется той же функцией пульта, что строит фактическое окружение
(`_pytest_env`, `_place_env`). Тест зелёный и на main до правки, и на
ветке после неё.
