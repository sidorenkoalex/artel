# QUESTIONS: Окружение шага роли внешнего проекта: PATH, сводка и логи suite-run

## Вопросы

Требования 1–3, 5, 6 ТЗ достаточны для SPEC. Блокирует требование 4
(каталог логов `suite-run` вторым `--add-dir` у Claude). Оно переворачивает
свойство, которое сегодня держат два существующих теста `tests/`, а форма
их правки не проходит через раздел SPEC «Меняемое поведение». Утверждения
там сравнивают списки, а раздел принимает только скалярные литералы
(skills/spec-authoring.md, «Меняемое поведение»). Значит, нужен мандат
Оператора:

- `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_step_suite_dirs.py::…::test_ac7_claude_step_has_no_new_add_dir_or_env`
  (стр. 288–310) — долгоживущий приёмочный тест задачи
  01M4KG7VHHXTVTW5TTX2PGY5RY. Утверждение
  `self.assertEqual(opened, [real(self.docs_dir())])`: у шага Claude ровно
  один `--add-dir`, это каталог документов. Имя метода и докстринг
  («Ловит мутацию: … у Claude появляется второй `--add-dir`») прямо
  запрещают то, чего требует ТЗ. Проверка окружения в том же методе
  (`assertNotIn(mark, str(value))` по `config.LOGS`/`suite-run`) требованию 4
  не противоречит: каталог передаётся argv, а не переменной.
- `tests/test_docs_dir_layout.py::…::test_add_dir_only_when_docs_dir_given_and_model_stays_last`
  (стр. 504–541), ветка `else` для claude:
  `self.assertEqual(opened[:at] + opened[at + 2:], bare)`. Это значит, что
  argv с каталогом документов отличается от argv без него ровно одной
  парой `--add-dir <docs>`. Вторая пара делает утверждение красным.

1. **Как поступить с двумя тестами, которые запрещают второй `--add-dir` у Claude?**
   - A) Мандат «Ослабление тестов разрешено» на два названных метода. Разработчик меняет их по смыслу требования 4: у Claude значения `--add-dir` — `[каталог документов, каталог логов suite-run задачи]`. Метод `test_ac7_…` переименовывается или получает новый докстринг. Проверка окружения (нет `config.LOGS` в переменных роли) остаётся как есть.
     - ломается: перевёрнуто свойство «шаг Claude не открывает каталогов пульта сверх документов» (решение SPEC 01M4KG7VHHXTVTW5TTX2PGY5RY, AC-7); в долгоживущем тесте другой задачи меняется ожидание и, вероятно, имя метода.
     - ослабляется: исключительность каталога документов среди `--add-dir` Claude — `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_step_suite_dirs.py:302` и `tests/test_docs_dir_layout.py:538`. Взамен новый тест этой задачи закрепит точный состав (`[docs, suite-run/<id>]`), поэтому запрет на прочие корни сохраняется.
     - цена: в рамках $35, правка двух методов входит в зону `tests/`.
     - чьё решение: Оператор (мандат на ослабление/смену вида утверждения, ADR-0002).
   - B) Требование 4 исключить из этой задачи, остальные (1–3, 5, 6) делать сейчас. Каталог логов для Claude — отдельной задачей с мандатом на эти тесты.
     - ломается: ничего; developer внешнего проекта на Claude по-прежнему не может открыть лог `suite-run` («лог открыть не дали») и видит только сводку в выводе команды.
     - ослабляется: ничего.
     - цена: потом ещё одна задача, около $25.
     - чьё решение: Оператор.
   - C) Не открывать каталог через `--add-dir`, а печатать нужные куски лога в выводе `suite-run`.
     - ломается: расходится с буквой требования 4 ТЗ («вторым `--add-dir`, как у Codex»); правка уходит в `orchestrator/suite_run.py`, а он в ТЗ «только чтение».
     - ослабляется: ничего.
     - цена: нужна правка ТЗ (зона), объём больше.
     - чьё решение: Оператор.
   - дефолт: B. Без явного мандата менять ожидание существующего теста нельзя (ADR-0002), а B ничего не ослабляет и не задерживает требования 1–3, 5, 6.

2. **Какой именно каталог открывать Claude: каталог логов своей задачи или весь каталог `suite-run`?** (имеет смысл только при ответе A на вопрос 1)
   - A) Только `config.LOGS / "suite-run" / <id задачи>`, где лежат `<id>-suiterun-<n>.log` (`orchestrator/suite_run.py:54`) — буквально «каталог логов suite-run своей задачи» из ТЗ. Если каталога нет, провайдер создаёт его так же, как Codex создаёт свой (`orchestrator/providers/codex.py:437-439`).
     - ломается: ничего; от Codex отличается шириной (Codex открыт весь `suite_lock.directory()`, нужный ему на запись замка из песочницы `workspace-write`; по ТЗ Claude каталог нужен для чтения лога своей задачи, а при прогоне `suite-run` из шага Claude сегодня `PermissionError` не наблюдался — в ТЗ он не назван).
     - ослабляется: ничего; логи и замок чужих задач Claude не открываются.
     - цена: в `command()` провайдера Claude нужен id задачи (параметр или имя каталога документов); `providers/codex.py` не трогаем.
     - чьё решение: роль (выведено из буквы ТЗ), Оператор подтверждает.
   - B) Весь `suite_lock.directory()` (`config.LOGS / "suite-run"`), один в один как у Codex.
     - ломается: Claude открывает на чтение и запись (`--permission-mode acceptEdits`) логи и файл замка `lock.json` всех задач машины.
     - ослабляется: изоляция каталогов задач друг от друга для инструментов Read/Edit/Write Claude.
     - цена: столько же.
     - чьё решение: Оператор.
   - дефолт: A — буква ТЗ и меньшая поверхность.

3. **Порядок и состав PATH прогона `pytest-own` (требование 1; ТЗ поручает обоснование аналитику) — подтвердить предлагаемое?**
   - A) PATH прогона = PATH вызывающего процесса (как сегодня, `orchestrator/acceptance.py:163`), затем каталог исполняемого файла `command[0]` (абсолютный путь — его каталог, иначе `shutil.which` по PATH вызывающего), затем `/usr/bin`, `/bin`, `/usr/sbin`, `/sbin`. Каждый каталог добавляется только если его ещё нет, дубликаты не повторяются. `PATH` из `test_profile.env` по-прежнему перекрывает всё (порядок `env.update(profile.env)`, стр. 166): это явное решение Оператора в `targets.yaml`. Обоснование: у процесса пульта PATH уже содержит каталог `command[0]` и системные каталоги, так что прогон гейтов остаётся прежним. У роли первыми идут каталоги объявленных инструментов (`runner._role_path_dirs`), и интерпретатор пульта не затеняется. Добавки в хвосте закрывают `bash`/`date`, не перехватывая уже найденные команды.
     - ломается: ничего у гейтов пульта; у роли прогон начинает находить системные утилиты.
     - ослабляется: ничего; PATH самого процесса роли (`runner.role_env`) не меняется, расширяется только PATH дочернего прогона `pytest-own`.
     - цена: в рамках задачи.
     - чьё решение: роль (поручено ТЗ), Оператор вправе переопределить.
   - B) Каталог `command[0]` и системные каталоги — в начало PATH.
     - ломается: у процесса пульта может смениться резолв команд, которые обёртка профиля зовёт по имени (например `python3` из `/usr/bin` вместо pyenv Оператора), то есть прогоны гейтов меняются.
     - ослабляется: неизменность прогона гейтов пульта для внешних проектов.
     - цена: столько же.
     - чьё решение: Оператор.
   - дефолт: A.
