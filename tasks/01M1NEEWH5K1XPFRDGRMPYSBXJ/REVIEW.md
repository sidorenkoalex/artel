## Замечания

- blocker — `orchestrator/canary.py:256-286` (`_drive_task`) в связке с
  `orchestrator/canary.py:221-253` (`_pass_escalated_with_synthetic_answer`),
  `orchestrator/fsm_advance.py:268-274` (лимит `review_iters`) и
  `orchestrator/runner.py:129-131`/`orchestrator/auto.py:266-294`
  (`budget_block` -> `SystemExit`, состояние НЕ меняется) — внешний
  `while True` в `_drive_task` не имеет верхней границы числа итераций
  и не отличает «есть прогресс» от «прогресса нет». Конкретный сценарий
  поломки: канареечная задача трижды подряд получает
  `changes_requested` (`iters >= config.LIMIT_REVIEW_ITERS`) → уходит в
  `escalated` → `_pass_escalated_with_synthetic_answer` отвечает
  синтетическим ANSWER и переводит её обратно в `in_dev`, но
  `review_iters` при этом НЕ сбрасывается (ни в этой функции, ни в
  оригинале `fsm._cmd_approve`, откуда она скопирована, — общее
  свойство FSM) → на следующем же вердикте `changes_requested` условие
  `iters >= LIMIT_REVIEW_ITERS` снова истинно немедленно (не через ещё
  3 раунда, а через один) → эскалация повторяется, ответ снова
  синтетический, и так по кругу. Каждый круг реально тратит бюджет
  задачи (developer + reviewer — настоящие агентские шаги), пока
  `t["spent_usd"]` не достигнет `budget_usd` (`config.DEFAULT_BUDGET_USD`
  = $50, `catalog.cmd_new` вызывается без переопределения). С этого
  момента `runner._cmd_run` отказывает ДО смены состояния
  (`budget.budget_block` → `sys.exit`), `auto._cmd_auto` ловит
  `SystemExit`, печатает `auto_stop` и возвращается, состояние остаётся
  прежним (агентским) — а `_drive_task` видит, что `runner.step_role(t)`
  всё ещё не `None`, и уходит на `continue`: с этой точки
  `auto.cmd_auto(task_id)` вызывается заново на каждой итерации `while
  True` и каждый раз немедленно отказывает по тому же бюджету — цикл
  без сна и без выхода, который не завершится сам никогда (это уже не
  «часовой хват реального ожидания», диагностированный в ANSWER-2/
  ANSWER-3 для другой причины, а безусловный busy-loop). Последствие:
  весь прогон `cmd_canary` виснет на ЭТОЙ ОДНОЙ задаче навсегда — цикл
  `for template_path in templates` в `cmd_canary` (`orchestrator/
  canary.py:433-434`) последовательный, остальные k-1 задач пула не
  запустятся никогда, никакого алерта/исключения не будет (весь
  прогон обрывается только ручным `kill -9` процесса), а сам сценарий
  (эскалация класса «лимит ревью», не класса «QUESTIONS.md analyst») ни
  разу не проверен планкой этой задачи — `test_ac6_...` эскалирует
  ИСКЛЮЧИТЕЛЬНО через `spec_writing`/QUESTIONS.md (`ESCALATE_TITLE_
  MARKER`), другого класса эскалации механика вообще не касается. Это
  прямое следствие требования 6 этой задачи: в v1 escalated был
  терминальным для `_drive_task` (задача просто останавливалась), в v2
  зацикливание стало возможным впервые именно из-за автопродолжения.
  Предложение: либо (а) завести счётчик повторных эскалаций/итераций
  внутри `_drive_task` и принудительно `cleanup.cmd_kill` задачу как
  «inconclusive» после разумного потолка (или по общему потолку
  времени/бюджета), либо (б) явно детектировать «состояние после
  `auto.cmd_auto` не изменилось» и останавливать `_run_one_task` для
  этой задачи с алертом, не роняя прогон остальных k-1 шаблонов.

- minor — `orchestrator/store.py:929-948` (`_ensure_canary_tables`,
  вызывается лениво из `insert_canary_run`/`canary_baseline`/
  `set_canary_baseline`) расходится с описанием в PLAN.md, раздел
  «Подход»: «новые функции ... рядом с остальными по тому же идиому
  (SCHEMA + блок в `migrate()`)». В реализации таблицы `canary_runs`/
  `canary_baseline` НЕ входят ни в `SCHEMA`, ни в `migrate()` — заводятся
  первым обращением. Сама по себе ленивая схема работает (проверил:
  `tests/test_store_schema_migration_parity.py` зелёный, самосогласована
  через `_ensure_canary_tables()` в каждой из трёх функций) — это не
  дефект поведения, а расхождение документации с кодом: PLAN — часть
  контракта, по которому Оператор и будущие читатели понимают
  архитектуру; текст стоит поправить под факт (или наоборот — перенести
  создание таблиц в `migrate()`, раз PLAN уже это обещал).

- minor — `orchestrator/canary.py:221-234` — докстринг
  `_pass_escalated_with_synthetic_answer` называет её «прямой копией»
  ветки `elif state == "escalated"` `fsm._cmd_approve` (orchestrator/
  fsm.py:800-834). Функция не проверяет `answer_baseline`/фактическое
  число ANSWER-файлов (fsm.py:810-822) и не вызывает
  `_maybe_ensure_draft_mr` при `back == "in_dev"` (fsm.py:832-833).
  Сегодня это не баг: canary сама безусловно пишет ровно один новый
  ANSWER файл ПЕРЕД переходом (проверка в оригинале стала бы
  тавтологией), а `_maybe_ensure_draft_mr` для канареечных задач и так
  no-op (`github_adapter.py:62`, `is_canary`). Но при будущей правке
  `fsm._cmd_approve` (например, добавят новую содержательную проверку
  в эту ветку) «прямая копия» тихо разойдётся с оригиналом — комментарий
  стоит смягчить до «повторяет эффект», не «прямая копия», чтобы не
  вводить в заблуждение следующего читателя/разработчика.
