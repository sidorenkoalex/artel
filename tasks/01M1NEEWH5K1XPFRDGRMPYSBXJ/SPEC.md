# SPEC: Канарейка v2 (часть 1): пул вне корня, эфемерный клон, метрики, изоляция пула от ролей

## Контекст

После мержа A7 (01M1H224X5A8W159MKF1Q24R5Y) запущенная версия получила три
регрессии нового флоу (маршрут analyst, канал ANSWER, перенос удалений
артефактов) — планка из 44 тестов их не поймала. Обновление пина
запущенной версии прошло 03.09 без прогона канарейки: доверия к пину
без гейта нет (ADR-0013). Канарейка v1 (`orchestrator/canary.py`,
tasks/T065) гоняет фиксированный набор ТЗ прямо в каталоге пульта — её
дыра: RETRO убитых канареечных задач протекает в main. Триггер К3
«первое обновление пина CLI» сработал 03.09 без прогона — первый
прогон v2 является немедленным долгом и одновременно бейзлайном К3
(решение Оператора 01.09). Старт этой задачи — после мержа hotfix A7
(01M1KT0792125J9ZNJNZJ86E9Q), уже смерженного в main.

Деление принято Оператором 04.09 (калибровка «сквозные ТЗ делить»):
эта задача — часть 1 (механика прогона, метрики, бейзлайн, изоляция
пула); часть 2 — привязка пина, триггер doctor и откат пина —
отдельная задача, заведённая с указанием этой как родителя; она
опирается на журнал прогонов части 1.

## Требования

1. Механика конвейера читает пул ТЗ-шаблонов из каталога вне корня
   пульта (`~/.artel-canary`) и умеет отобрать случайную выборку k из
   N доступных шаблонов для одного прогона.
2. Полный цикл каждой выбранной задачи проходит только в отдельном
   эфемерном клоне пульта: свой рабочий каталог, своя БД состояния,
   свой origin-заглушка (не настоящий git-remote).
3. Прогон не оставляет в основном пульте следов канареечных задач — ни
   новых веток, ни RETRO, ни записей копилки/алертов инцидента, ни
   снапшотов артефактов — ни для успешных, ни для убитых задач прогона.
4. Каталог эфемерного клона удаляется по завершении прогона.
5. Метрики прогона (шаги ролей, итерации ревью, эскалации, стоимость,
   вердикты гейтов — по каждой задаче) сохраняются в БД пульта
   отдельной таблицей/пометкой, отдельно от журнала живых продуктовых
   задач.
6. Механика умеет довести канареечную задачу через цикл эскалации:
   состояние `escalated` обрабатывается синтетическим ANSWER-ответом
   Оператора (заглушкой), после чего прогон задачи продолжается без
   участия живого Оператора.
7. Каждый шаблон пула несёт canary-GUID; CI пульта отклоняет
   коммит/PR, если этот GUID (любого шаблона пула) обнаружен в
   skills/, templates/ или docs/ пульта.
8. Механика читает в шаблоне ТЗ машиночитаемый маркер «ожидается
   эскалация» и по завершении прогона задачи сверяет его с фактическим
   исходом (была ли эскалация); расхождение отражается в отчёте
   прогона.
9. Бейзлайн канарейки считается и сохраняется per-task (по каждой
   задаче пула отдельно), не суммой по набору.
10. Первый успешный прогон пула v2 фиксируется как бейзлайн К3.
11. Прогон канареечной задачи обходит гейт `verifying` (не ждёт CI
    ветки — как в v1).
12. Отклонение метрик прогона от бейзлайна сверх порога поднимает
    алерт Оператору — без автоматического исправления/действия.

13. Изоляция пула от ролей (решение Оператора 04.09): (а) курируемый
    слой роли (`CLAUDE_CONFIG_DIR` роли, `.artel/home/.claude/
    settings.json`) несёт запрещающие правила: чтение путей под
    каталогом пула (`~/.artel-canary`), команды `gh repo clone`/
    `git clone`/`git remote add` с именем репозитория пула — CLI роли
    отказывает до исполнения; (б) после каждого прогона канарейки и
    на каждом `doctor` логи шагов ролей проверяются на упоминание
    каталога пула, имени его репозитория и любого GUID шаблона —
    совпадение поднимает алерт `kind=incident`; (в) `doctor`
    предупреждает, если токен ролей (слот keychain) имеет доступ
    более чем к одному репозиторию (ограничение токена — настройка
    Оператора, «Не входит»); (г) skills/conventions-core.md и
    CLAUDE.md курируемого слоя несут текстовый запрет как напоминание.

## Критерии приёмки

AC-1. Команда прогона канарейки читает шаблоны ТЗ из каталога
`~/.artel-canary` (вне корня пульта) и принимает параметр выборки k,
отбирая k случайных шаблонов из доступных N.

AC-2. Полный цикл каждой выбранной задачи проходит в отдельном
эфемерном клоне пульта: собственный рабочий каталог, собственная БД
состояния, собственный origin-заглушка (не настоящий git-remote).

AC-3. После завершения прогона в основном пульте не появляется новых
веток задач, записей RETRO, записей копилки/алертов инцидента или
снапшотов артефактов, связанных с канареечными задачами прогона — ни
для успешных, ни для убитых задач.

AC-4. Каталог эфемерного клона удаляется по завершении прогона
(независимо от исхода прогона).

AC-5. Метрики прогона (шаги ролей, итерации ревью, эскалации,
стоимость, вердикты гейтов — по каждой задаче) сохраняются в БД
пульта отдельной таблицей/пометкой, отличной от журнала живых
продуктовых задач.

AC-6. Если заведённая канареечная задача переходит в состояние
`escalated`, механика прогона отвечает синтетическим ANSWER-ответом
Оператора (заглушкой), и задача возвращается в работу без остановки
прогона и без участия живого Оператора.

AC-7. Каждый шаблон пула, использованный в прогоне, несёт
canary-GUID; CI-джоб пульта отклоняет коммит/PR, в содержимом
которого (skills/, templates/, docs/) обнаружен canary-GUID любого
известного шаблона пула.

AC-8. По завершении прогона задачи механика сверяет наличие
машиночитаемого маркера «ожидается эскалация» в исходном шаблоне ТЗ
с фактическим исходом задачи (была ли эскалация); расхождение
отражается в отчёте прогона.

AC-9. Бейзлайн канарейки вычисляется и сохраняется per-task (по
каждой задаче пула отдельно), а не суммой метрик по набору.

AC-10. Первый успешный прогон пула v2 фиксируется как бейзлайн К3.

AC-11. Прогон канареечной задачи не ждёт гейт `verifying` (обходит
ожидание CI ветки).

AC-12. Отклонение метрик прогона от бейзлайна сверх порога поднимает
алерт Оператору и не запускает никакого автоматического
исправления/действия.

AC-13. Существующий набор тестов (`tests/`) остаётся зелёным после
изменений.

AC-14. Курируемый слой роли содержит запрещающие правила CLI на чтение
путей под каталогом пула и на команды клонирования/подключения
репозитория пула; тест: роль с этими правилами получает отказ CLI на
такой вызов до исполнения.

AC-15. После прогона канарейки и при `doctor` логи шагов ролей
проверяются на упоминание каталога пула, имени его репозитория и
GUID любого шаблона; тест: лог с таким упоминанием поднимает алерт
`kind=incident`, лог без него — не поднимает.

AC-16. `doctor` предупреждает, если токен ролей имеет доступ более чем
к одному репозиторию; тест на оба исхода.

## Не входит

- Привязка пина к зелёной канарейке, триггер doctor «N мержей с
  последнего прогона» и откат пина `pin --to` — часть 2 (отдельная
  задача, родитель — эта).
- Ограничение токена ролей одним репозиторием (fine-grained token) —
  разовая настройка Оператора; задача только предупреждает.

- Шифрование пула шаблонов (решение 29.08 — не до B3).
- Авторешения по красной канарейке (реакция — только алерт Оператору,
  см. AC-16).
- Содержание и создание конкретных ТЗ-шаблонов пула (10–15 шт., их
  сюжеты и GUID-разметка) — пишут Оператор и ассистент руками, вне
  git и вне конвейера.
- Инициализация каталога пула `~/.artel-canary` и его приватного
  git-remote для резервирования — разовая ручная настройка Оператором
  вне конвейера; механика читает уже существующий пул.
- Обеспечение того, какие именно сюжеты (маршрут analyst нового
  флоу, конкретный сценарий эскалации, удаление артефакта ролью)
  представлены в конкретных шаблонах пула — свойство содержимого
  шаблонов (см. пункт выше), не механики прогона.
