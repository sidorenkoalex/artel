# SPEC: канарейка — диагностика незелёного прогона и бейзлайн только с зелёного исхода

## Контекст

Прогон `canary --k 2` 20260905T191514Z (пин 681174ac) снял обе задачи
пула (`canary-version-json` — эскалация против маркера «без эскалаций»;
`canary-usage-invariant` — «3 прохода без прогресса»), но `_ephemeral_
clone` уничтожил клон вместе с `.artel/state.db` и логами ролей ДО того,
как причины провала попали куда-либо за пределы 12 строк вывода команды
— восстановить их невозможно. В тот же день `canary_baseline` второй раз
принял шаги/стоимость задачи с исходом `killed` (первый раз —
20260905T175403Z, сброшено руками): бейзлайн, построенный на незавершённом
прогоне, не сравним с последующими зелёными прогонами. Оба наблюдения —
копилка 06.09, приоритет 1 — блокируют мерж канарейки части 2
(01M1NGFK3N).

## Требования

1. При исходе задачи пула, отличном от `done` без расхождения маркера
   ожидания эскалации, `canary` до удаления эфемерного клона сохраняет
   диагностику задачи в `.artel/canary/<run_stamp>/<task_id>/` пульта:
   журнал задачи (`steps`) текстом, логи ролей `.artel/logs/<task_id>-
   *.log` клона, последние PLAN/REVIEW из артефактной ветки клона, если
   они там есть. Путь сохранённой диагностики печатается в выводе
   команды `canary`.
2. Вывод `canary` для каждой задачи набора — не одна итоговая строка, а
   выдержка журнала: переходы состояний и записи «эскалация»/«переход
   отклонён»/«auto остановлен», не более 20 строк на задачу.
3. `canary_baseline` обновляется только при исходе задачи `done` без
   расхождения маркера. Строки `canary_runs` с исходом `killed` или с
   расхождением маркера по-прежнему сохраняются в таблице, но не
   участвуют ни в обновлении бейзлайна, ни в сравнении отклонений
   текущего прогона от бейзлайна.
4. `.artel/canary/` внесён в `.gitignore` и исключён из автокоммита
   артефактов задачи; `prune` применяет к нему то же правило хранения
   (порог давности `docs/retention.md`), что и к `.artel/logs/`.

## Критерии приёмки

AC-1. При исходе задачи пула, отличном от `done` без расхождения
маркера ожидания эскалации, `canary` до удаления эфемерного клона
сохраняет в `.artel/canary/<run_stamp>/<task_id>/` пульта журнал задачи
(`steps`) текстом.

AC-2. В том же случае тот же каталог несёт логи ролей клона
`.artel/logs/<task_id>-*.log`, скопированные до удаления клона.

AC-3. В том же случае тот же каталог несёт последние PLAN.md/REVIEW.md
из артефактной ветки клона, если они там есть; их отсутствие в клоне не
приводит к отказу команды `canary`.

AC-4. При исходе задачи `done` без расхождения маркера диагностика НЕ
сохраняется — каталог `.artel/canary/<run_stamp>/<task_id>/` для этой
задачи не заводится.

AC-5. Путь сохранённой диагностики (AC-1..AC-3) печатается в выводе
команды `canary`.

AC-6. Вывод `canary` несёт для каждой задачи набора выдержку журнала
(переходы состояний и записи «эскалация»/«переход отклонён»/«auto
остановлен»), не более 20 строк на задачу, вместо одной итоговой строки
исхода.

AC-7. `canary_baseline` обновляется только при исходе задачи пула
`done` без расхождения маркера ожидания эскалации.

AC-8. Строки `canary_runs` с исходом `killed` или с расхождением
маркера сохраняются в таблице, но не используются ни для обновления
`canary_baseline`, ни для вычисления предупреждений об отклонении
текущего прогона от бейзлайна.

AC-9. `.artel/canary/` внесён в `.gitignore`, исключён из автокоммита
артефактов задачи, и `prune` применяет к содержимому этого каталога тот
же порог давности (`config.LOG_RETENTION_DAYS`, `docs/retention.md`),
что и к `.artel/logs/`.

## Оценка объёма и деление

Сработавший сигнал: `budget_usd` = 30 (порог ≥ $30).

Обоснование монолита: оба наблюдения копилки 06.09 — потеря диагностики
не-`done`-исхода (AC-1..AC-6) и ложный бейзлайн из `killed`-исхода
(AC-7..AC-8) — происходят из ОДНОГО и ТОГО ЖЕ прогона `_run_one_task` и
вычисляются из одних и тех же значений (`metrics["outcome"]`, `mismatch`)
в одном и том же месте кода; Оператор уже объединил их в одно ТЗ, а не
завёл двумя. Рубеж AC-7/AC-8 (не писать бейзлайн и не сравнивать
отклонения для не-зелёного исхода) без рубежа AC-1..AC-3 (сохранить
диагностику) оставляет открытым исходный дефект — расследовать
`killed`/расхождение по-прежнему нечем, только избавляет от одного из
двух его симптомов. Обратно, AC-1..AC-3 без AC-7/AC-8 чинят потерю
диагностики, но оставляют ложные бейзлайны из `killed`-прогонов —
второй симптом того же дефекта, воспроизведённый дважды за один день
(20260905T175403Z, 20260905T191514Z). `.gitignore`/`prune` (AC-9) —
инфраструктура вокруг каталога, который заводит AC-1: без него
`.artel/canary/` либо попадёт в автокоммит артефактов, либо будет расти
бессрочно — сама по себе, без AC-1..AC-3, эта часть не несёт
самостоятельной ценности (каталога, который она обслуживает, ещё нет).
Граница зон (`orchestrator/canary.py` vs `orchestrator/prune.py`/
`.gitignore`) здесь не совпадает с границей независимо мержимых частей.
