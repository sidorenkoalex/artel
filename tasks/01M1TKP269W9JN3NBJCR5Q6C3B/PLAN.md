# PLAN: канарейка — диагностика незелёного прогона и бейзлайн только с зелёного исхода

## Подход

ANSWER-1.md (вариант Б) закрывает главную неоднозначность SPEC: «исход
`done`» — не буквальный статус FSM (канареечная задача никогда не
достигает `done`, она всегда `killed`), а функциональный «штатный
исход»: kill на `merge_gate`/`verifying`, который `canary.
_kill_outcome_note` уже умеет отличать как «штатно» от «не сошлась».
Правило одно на оба требования SPEC: диагностика (AC-1..AC-4) и
бейзлайн/сравнение (AC-7/AC-8) применяются СИММЕТРИЧНО — единственный
случай, где диагностика НЕ нужна и где бейзлайн/сравнение ПРИМЕНЯЮТСЯ,
это «штатно И без расхождения маркера» одновременно; во всех остальных
случаях (не штатно, ИЛИ расхождение маркера, ИЛИ оба) — наоборот.

Реализовано одной точкой принятия решения — `canary._needs_diagnostics
(normal_outcome, mismatch)` — переиспользуемой в обоих местах
`_run_one_task` (решение сохранять диагностику и решение применять
бейзлайн/сравнение — второе как `not _needs_diagnostics(...)`), чтобы
эти два требования SPEC не могли разъехаться разными условиями по
недосмотру при будущей правке.

Диагностика сохраняется ИЗНУТРИ `with _ephemeral_clone()`, ДО его
выхода (значит, до `shutil.rmtree` клона) — `_save_diagnostics` читает
журнал БД клона (уже в руках вызывающего кода, `store.task_steps`),
`config.LOGS` клона (патчено `_ephemeral_clone` на время блока) и
артефактную ветку клона (`gitcmd.show`, читает `config.ROOT`, тоже
патчено) — и пишет результат под путём, посчитанным от `outer_root`
(`config.ROOT`, захваченного ДО входа в блок, то есть путь СНАРУЖИ
клона). Никакой новой обвязки эфемерного клона не потребовалось — все
три источника уже читаются через модульные атрибуты `config`, которые
`_ephemeral_clone` и так пересчитывает.

Вывод команды (AC-5/AC-6) переработан: вместо одной строки исхода —
выдержка журнала (`_journal_excerpt_lines`, фильтр по префиксам
`state -> `/`переход отклонён`/литералу `auto остановлен`, потолок 18
строк — с запасом на итоговую строку метрик и строку пути диагностики,
чтобы суммарный вывод по задаче не превышал 20 строк требования 2),
затем прежняя строка метрик (несёт `(штатно)`/`РАСХОЖДЕНИЕ`/
`[бейзлайн создан]`/`[ВНИМАНИЕ...]`, как и раньше), затем строка пути
диагностики, если она была сохранена.

`prune` (AC-9, вторая половина) получает `_canary_diag_candidates` —
тот же порог давности `config.LOG_RETENTION_DAYS`, что и у `.artel/
logs/`, но БЕЗ фильтра «последние N закрытых задач»: `task_id` в пути
диагностики — id уже уничтоженного эфемерного клона, никогда не
попадающий в `store.all_tasks` пульта (тот датовый отбор для него
бессмысленен). `.gitignore` (AC-9, первая половина) уже несёт `.artel/`
без уточнения подкаталога — покрывает `.artel/canary/` тривиально, без
правки; зафиксировано `test_ac9_gitignore_excludes_canary_dir.py`
(зелёный с рождения) и не требует изменений файла.

## Влияние на систему

Изменения — только внутри `orchestrator/canary.py` (командный код
синтетического прогона, не боевой FSM) и `orchestrator/prune.py`
(явная операторская команда retention, не срабатывает на переходах
FSM ни одной боевой задачи — инвариант 16 не затронут: диагностика
канарейки — новый вид данных со своей явно объявленной политикой
хранения, тем же приёмом, что и `.artel/logs/`, docs/retention.md).
Никакой существующий тест/гейт/лимит не ослаблен: `_needs_diagnostics`
СУЖАЕТ условие обновления бейзлайна (было — всегда на первом прогоне
шаблона, стало — только на штатном исходе без расхождения), это и есть
цель SPEC (AC-7/AC-8), не побочный эффект. Формат `canary_runs`/
`canary_baseline` (схема БД) не меняется — меняется только то, какие
строки участвуют в записи бейзлайна и в сравнении, не сама схема.
Откат — правка этого же файла до предыдущей версии `_run_one_task`,
данных не теряет (`canary_runs` по-прежнему пишется для каждого
прогона независимо от исхода, требование 3 SPEC).

`docs/retention.md` дополнен разделом `.artel/canary/`, аналогичным
существующему разделу `.artel/logs/` — по образцу, на который ссылается
SPEC.

— при отсутствии PLAN.md/REVIEW.md в клоне (задача убита раньше
`in_dev`) код не отказывает (AC-3, вторая половина) — покрыто
`test_ac3_missing_plan_and_review_do_not_fail_the_command` в залоченной
планке.
