# SPEC: Бриф роли внешнего проекта: конвенции и карта проекта, а не пульта

## Контекст
Бриф роли у задачи внешнего проекта (например, sled, 01M55SKHZ293CCAK0N7T4H7ZMR) собирается так же, как у артели. Он несёт карту кодовой базы пульта (`config.ROOT/docs/codebase-map.md`, `orchestrator/brief.py:28`; сверка свежести и регенерация — `:310-416`; проекция — `:912-913`). У developer sled это около 77 КБ, и бриф режется на 4 части. Вместе с картой идёт `MAP_PROJECTION_NOTE` (`:36-39`) со ссылкой на файл, которого в рабочем каталоге sled нет. Вместо конвенций проекта бриф developer несёт `CLAUDE.md` с main пульта (`CONVENTIONS_REL`, `:40`, `:914`). Собственные `CLAUDE.md` и `AGENTS.md` проекта роль не видит: `--setting-sources user` (`orchestrator/config.py:72`) отключает проектную память клиента. Ещё один побочный эффект: сборка брифа внешней задачи может регенерировать и откатывать карту в рабочей копии пульта и заводит с задачей sled алерты карты (`:364-369`, `:375-376`, `:794-798`). Задача — дать роли внешнего проекта конвенции её проекта и убрать из брифа всё, что относится к карте пульта. Бриф артели при этом не меняется.

## Требования
1. Принадлежность задачи внешнему проекту определяется тем же признаком проекта задачи, что у остальных потребителей (`repo_context` / `project_profile`). Для задачи артели всё ниже не действует.
2. Для задачи внешнего проекта бриф ролей developer, analyst, spec_auditor и test_author не содержит карты кодовой базы пульта (ни её проекции), ни её пометки свежести (стухлости), ни `MAP_PROJECTION_NOTE`.
3. При сборке брифа задачи внешнего проекта не вызываются ни сверка свежести карты пульта, ни её регенерация. Рабочая копия пульта (`config.ROOT`) не меняется. Алерты карты не заводятся: ни о размере карты, ни о стухлости или неудачной регенерации, ни об откате регенерированной карты.
4. Бриф задачи внешнего проекта не содержит `CLAUDE.md` пульта. Вместо него он несёт файлы конвенций проекта — фиксированный список `CLAUDE.md` и `AGENTS.md` из корня базовой ветки проекта. Базовая ветка читается по той же ссылке, что у `reference_cache.branch_commit` (`orchestrator/reference_cache.py:293-309`): локальная `refs/heads/<base>` клона проекта, без `fetch`. Каждый найденный файл — отдельный компонент брифа.
5. Форма компонента конвенций — та же, что у соседних компонентов брифа этой роли. У ролей, чей бриф сегодня несёт опись (developer и spec_auditor, `_manifest_component`, `brief.py:446-469`), компонент идёт в опись с путём, размером и sha256, как сегодня `CONVENTIONS_REL`. У ролей, где соседи компонента конвенций идут без описи (analyst и test_author, `_journal_component`), компонент конвенций оформлен так же, как эти соседи, и у самого компонента конвенций описи нет. Справочник ядра в брифе test_author (`brief.py:846-848`, идёт с описью) не меняется.
6. Конвенции проекта (требование 4) получают все роли, чей бриф собирает `orchestrator/brief.py`. У developer они заменяют `CLAUDE.md` пульта. У analyst, spec_auditor и test_author это новый компонент брифа. Поэтому добавка брифа test_author у задачи внешнего проекта собирается всегда, даже без ANSWER, причины возврата и справочника ядра.
7. Если базовая ветка проекта прочитана, а какого-то файла из списка требования 4 нет в её корне, бриф всё равно собирается, а на месте файла стоит именованная пометка «файла нет» с именем файла. Шаг из-за этого не отказывает. Это относится к обоим файлам списка и ко всем ролям требования 6.
8. Если базовую ветку проекта прочитать не удалось (клона нет, ветки базы в клоне нет, git не ответил, контекст проекта не разрешён), бриф всё равно собирается: сбой чтения конвенций не завершает шаг `sys.exit` и не даёт отказа. Вместо компонентов конвенций в брифе стоит отдельная пометка «конвенции проекта не прочитаны: <причина>», отличимая от пометки «файла нет» (требование 7). В журнал задачи пишется запись с той же причиной. Отказ сборки брифа при нечитаемом `SPEC.md` задачи (`sys.exit` на `brief.py:646-648` и `:653-655`) остаётся как есть и имеет приоритет: если `SPEC.md` прочитать нельзя, шаг отказывает по нему, как сегодня.
9. Если базовая ветка проекта прочитана, а чтение файла из списка требования 4, который в ней есть, не удалось по другой причине (например, git не ответил на чтение файла), на месте этого файла в брифе стоит пометка «конвенции проекта не прочитаны: <причина>», а не пометка «файла нет»; в журнал задачи пишется запись с той же причиной. Шаг из-за этого не отказывает.
10. Для задачи внешнего проекта миссии ролей говорят правду о составе брифа:
   - миссия developer (сегодня `orchestrator/role_prompt.py:95-97`: «SPEC задачи, карта кодовой базы, конвенции проекта … — целиком в БРИФЕ РОЛИ ниже») говорит, что в брифе — конвенции проекта, а правила работы роли — в скилах пульта;
   - миссии analyst (`role_prompt.py:42-43`) и spec_auditor (`role_prompt.py:240-242`) не говорят о карте кодовой базы в брифе.
11. Для задачи артели бриф, опись и миссии всех ролей не меняются ни на байт. Это фиксируется тестами до правки: эталон — бриф (с описью) и миссии артели, снятые тем же тестом с кода до правки при зафиксированном `run_id` (генератор `run_id` в тесте подменён); сравнение с эталоном побайтное.
12. Существующие тесты шагов внешнего проекта — `tests/test_multitarget_invariants.py:375-397` и `tests/test_01m545eb0a9f191wtdspch36ga_project_role_step.py:199-224` — не правятся.
13. Тесты детерминированы и обходятся без сети. Они используют учебный внешний проект с `CLAUDE.md` в базовой ветке и варианты этого проекта: с `CLAUDE.md` и `AGENTS.md`, у которых версии на `refs/heads/<base>` клона отличаются от версий в рабочем дереве клона, в worktree задачи и на ветке задачи; без `CLAUDE.md`, с нечитаемой базовой веткой, со сбоем чтения файла при прочитанной базовой ветке.

## Критерии приёмки
AC-1. Для задачи артели бриф и опись ролей developer, analyst, spec_auditor и test_author, а также миссии всех ролей совпадают побайтно с эталоном. Эталон — бриф, опись и миссии артели, снятые тем же тестом с кода до правки при зафиксированном `run_id`: генератор `run_id` в тесте подменён. Проверка — побайтное равенство, не проверка «содержит».

AC-2. Учебный внешний проект с `CLAUDE.md` в корне базовой ветки: бриф developer содержит текст этого `CLAUDE.md`. Он не содержит проекции карты пульта, пометки свежести карты, `MAP_PROJECTION_NOTE` и текста `CLAUDE.md` пульта.

AC-3. Тот же учебный проект: бриф analyst содержит текст `CLAUDE.md` проекта и не содержит проекции карты пульта, пометки свежести карты, `MAP_PROJECTION_NOTE` и текста `CLAUDE.md` пульта.

AC-4. Тот же учебный проект: бриф spec_auditor содержит текст `CLAUDE.md` проекта и не содержит проекции карты пульта, пометки свежести карты, `MAP_PROJECTION_NOTE` и текста `CLAUDE.md` пульта.

AC-5. Тот же учебный проект без ANSWER, причины возврата и справочника ядра: добавка брифа test_author не `None` и содержит текст `CLAUDE.md` проекта. Она не содержит проекции карты пульта, пометки свежести карты, `MAP_PROJECTION_NOTE` и текста `CLAUDE.md` пульта.

AC-6. Если в корне базовой ветки учебного проекта лежат и `CLAUDE.md`, и `AGENTS.md`, бриф каждой из ролей developer, analyst, spec_auditor и test_author содержит тексты обоих файлов, каждый — отдельным компонентом. В этой фикстуре `CLAUDE.md` и `AGENTS.md` на `refs/heads/<base>` клона отличаются по содержимому от своих версий в рабочем дереве клона, в worktree задачи и на ветке задачи: бриф каждой роли несёт тексты версий базовой ветки и не содержит ни одного из текстов других версий. У developer и spec_auditor каждый из них стоит в описи с путём, размером и sha256, как сегодня `CONVENTIONS_REL`. У analyst и test_author компонент конвенций оформлен так же, как его соседи без описи, и у компонента конвенций нет описи с размером и sha256 (справочник ядра test_author в этой проверке не участвует).

AC-7. Учебный внешний проект без `CLAUDE.md` в прочитанной базовой ветке: бриф каждой из ролей developer, analyst, spec_auditor и test_author собирается без отказа шага и содержит пометку «файла нет» с именем `CLAUDE.md`.

AC-8. Учебный внешний проект с `CLAUDE.md`, но без `AGENTS.md` в прочитанной базовой ветке: бриф каждой из ролей developer, analyst, spec_auditor и test_author содержит пометку «файла нет» с именем `AGENTS.md`.

AC-9. Базовую ветку учебного внешнего проекта прочитать нельзя — в каждом из сценариев «клона нет», «ветки базы в клоне нет», «git не ответил», «контекст проекта не разрешён»: бриф каждой из ролей developer, analyst, spec_auditor и test_author собирается без `SystemExit`. Он содержит пометку «конвенции проекта не прочитаны: <причина>» и не содержит пометки «файла нет». В журнале задачи есть запись с той же причиной. Для developer и spec_auditor сценарии «клона нет» и «контекст проекта не разрешён» проверяются при читаемых документах задачи: тест подменяет только чтение базовой ветки проекта, `SPEC.md` задачи читается.

AC-10. Базовая ветка учебного внешнего проекта прочитана, `CLAUDE.md` в ней есть, но чтение этого файла не удаётся (сбой подменён в тесте): бриф каждой из ролей developer, analyst, spec_auditor и test_author собирается без `SystemExit`, на месте `CLAUDE.md` содержит пометку «конвенции проекта не прочитаны: <причина>» и не содержит пометки «файла нет» с именем `CLAUDE.md`. AC-12. Сборка тех же брифов для задачи учебного внешнего проекта не заводит ни одного алерта карты: ни о размере карты, ни о стухлости, неудачной регенерации или откате карты. Это проверяется при карте пульта, которая превышает потолок файла брифа и стухла относительно main.

AC-13. Для задачи учебного внешнего проекта миссия developer говорит, что в брифе — конвенции проекта, а правила работы роли — в скилах пульта. Фразы «карта кодовой базы, конвенции проекта … целиком в БРИФЕ РОЛИ» в ней нет.

AC-14. Для задачи учебного внешнего проекта миссии analyst и spec_auditor не упоминают карту кодовой базы в брифе.

AC-15. Ветка задачи не меняет `tests/test_multitarget_invariants.py` и `tests/test_01m545eb0a9f191wtdspch36ga_project_role_step.py`: diff ветки относительно базы этих файлов не содержит.
