# PLAN: Инвариант: пульт исполняется только из главной копии

## Подход

Guard живёт в `orchestrator/artel.py::main()`, первой инструкцией — до
разбора `-h`/`--help` и до диспетчерской таблицы команд, то есть до
любого обращения к БД (требование 1 SPEC). Признак worktree —
`config.ROOT / ".git"` является файлом, а не каталогом (требование 2):
у главной копии `.git` — каталог, у worktree — файл-ссылка
`gitdir: <main>/.git/worktrees/<id>`. Проверка `is_file()` уже сама по
себе прозрачна для тестовых песочниц (требование 5): временный каталог
без `.git` вовсе — `is_file()` даёт `False`, guard молча возвращается,
поведение не меняется.

Путь главной копии для сообщения об отказе разбирается из содержимого
файла: всё до подстроки `/.git/worktrees/`. Разбор по подстроке, а не
по фиксированному числу компонент пути, не зависит от имени, которое
git выбрал каталогу worktree в `.git/worktrees/<id>` (оно не обязано
совпадать с `task_id` — например, если рабочий каталог назван иначе).

Отказ — `sys.exit(<сообщение>)`: тот же приём, что уже используют
`_tz_arg` и остальные ранние отказы `artel.py`/`fsm.py` (не
исключение без сообщения, а понятный текст в stderr и ненулевой код
возврата). Сообщение называет оба пути (фактический `ROOT` и главную
копию) и содержит подсказку «перезапусти» — ровно то, что проверяет
приёмочный тест AC-1.

Дешёвый доп.признак «путь ROOT содержит `.artel/worktrees/`» из
требования 2 не добавляется отдельно: он не нужен для корректности
(файловый признак уже достаточен и дёшев — одно `os.stat` через
`is_file()`), а добавление второго пути проверки увеличило бы
поверхность инварианта без выигрыша.

Ни `config.py`, ни `gitcmd.py`, ни `workspace.py` не трогаются: вся
логика — одна маленькая функция в `artel.py`, читающая только
`config.ROOT` (уже импортируемый модуль `config` добавляется в импорт
`artel.py`). Worktree-механика T045 (`workspace.ensure`,
`on_task_branch`) не меняется — SPEC явно выводит её из зоны.

## Влияние на систему

Изменение — новая проверка на входе CLI, не затрагивающая существующие
инварианты, гейты, лимиты или тесты: `_refuse_if_worktree()` только
читает `config.ROOT` и файловую систему (`.git` файл/каталог), не пишет
ничего и не участвует в FSM. Она встаёт строго перед диспетчерской
таблицей `main()`, поэтому не меняет ни один из путей выполнения команд
из главной копии (AC-2, проверено байт-в-байт приёмочным тестом) и не
меняет поведение тестовых песочниц (`tests/sandbox.py::TmpRootTest`,
`tests/test_invariants.py` и другие, патчащие `config.ROOT` на
временный каталог без файла `.git`) — они просто не подпадают под
признак worktree.

Риск ослабления: единственный существующий похожий guard — worktree-
норма T045 (`docs/invariants.md`, если бы там уже был явный номер) не
существовала как код-инвариант, только как дисциплина; эта задача
добавляет тест, а не убирает или ослабляет что-либо. Новый тест —
`tests/test_invariants.py`, попадает в неослабляемый реестр наравне с
остальными: снятие или ослабление — только Оператором через ADR.

Откат: удаление вызова `_refuse_if_worktree()` из `main()` и самой
функции, плюс соответствующего теста и строки в `docs/invariants.md` —
локальная правка одного файла и одного теста, без миграций и без
состояния БД.

Строка для `docs/invariants.md` (вносит Оператор при мерже, таблица
«Кодированные тестами», следующий свободный номер — 31):

## Риски

- Формат `.git`-файла worktree (`gitdir: <path>`) — стабильный формат
  git, но не документирован как публичный API; если git когда-либо
  сменит формат, guard перестанет срабатывать (fail-open, не fail-closed
  — команда просто выполнится как раньше). Не блокер для этой задачи:
  живой инцидент подтверждает текущий формат, а разбор defensively не
  падает на неожиданном содержимом (просто не находит `/.git/worktrees/`
  и печатает `?` вместо пути главной копии, но всё равно отказывает).

## Предложения системе
