# SPEC: Возврат с гейта SPEC файлом решения

## Контекст
`reject <id> "<причина>"` на `spec_gate` (`orchestrator/fsm.py:1890`,
ветка `if state == "spec_gate"` в `_cmd_reject`) принимает свободный текст
и проверяет только его непустоту (`orchestrator/fsm.py:1912`); текст уходит
в журнал с префиксом «возврат из spec_gate: » (`orchestrator/fsm.py:1919`,
`brief.SPEC_GATE_RETURN_PREFIX`, `orchestrator/brief.py:76`) и попадает в
бриф аналитика и аудитора разделом «Решения Оператора на гейте SPEC»
(`brief._spec_gate_reasons`). Инцидент 04.11 (01M6JJ4J4NBV2Y1Q4XHE3C3FVT):
из десяти кругов SPEC около половины вызвано решениями Оператора на гейте
— ложное утверждение о git, условие, невыполнимое в зонах, опасная форма
теста, незаданный канал подстановки, противоречие двух решений; мандат на
правку теста подан текстом причины, а не строкой мандата в ANSWER.
Правило сверки следствий (`docs/operator-session.md`, «Уроки 04.11», п. 1)
пульт сегодня не проверяет. Задача вводит форму возврата файлом решения
с обязательными полями сверки, проверяемыми по форме, номерам и наличию
мандата.

## Требования
1. `reject <id> --decision <файл>` на `spec_gate`. Ключ `--decision`
   разбирается в `orchestrator/artel.py` явно, а не как текст причины.
   Позиционные сигнатуры `fsm.cmd_reject(task, reason)` и
   `fsm._cmd_reject(conn, task, reason)` сохраняются; новый аргумент —
   именованный, по умолчанию `None`.
2. Файл решения — по форме шаблона `templates/SPEC-GATE-DECISION.md`
   (приложение п. 9): раздел «## Решения», в нём подразделы
   «### Решение <n>», у каждого шесть полей — «Текст», «Утверждения о коде
   и поведении», «Чем проверяется», «Существующие тесты», «Прежние
   решения», «Зоны». Отказ `reject` с именем решения и поля (или с
   указанием на отсутствие раздела), состояние задачи не меняется, если:
   отсутствует раздел «## Решения»; поле отсутствует или пусто; поле не по
   форме — в частности, «Утверждения о коде и поведении» не содержит ни
   `файл:строка`, ни «опыт:», ни «нет»; в поле оставлена заглушка шаблона
   «<…>».
3. Разбор файла решения — в новом модуле `orchestrator/spec_gate_decision.py`;
   во время работы он не читает каталог шаблонов: форма зашита в модуле.
4. Номера решений: решение n возврата k — «k.n», где k — номер возврата
   с гейта SPEC этой задачи, тот же, что «№k» в брифе; возврат текстом
   имеет номер «k».
5. На отказе `reject` (форма `--decision`) и в подсказке остановки `auto`
   на `spec_gate` (`orchestrator/auto.py`) пульт печатает перечень прежних
   решений задачи: для возврата файлом — номер «k.n» и текст поля «Текст»
   каждого решения; для возврата текстом — номер «k» и первые 120 знаков
   причины. Переносы строк в печатаемом тексте свёрнуты.
6. Поле «Прежние решения» ссылается на номера прежних решений задачи
   («k.n» / «k»); ссылка на номер, которого нет среди прежних решений
   задачи, — отказ `reject` с именем решения и поля, состояние не меняется.
7. Элемент «мандат: <строка>» в поле «Существующие тесты» — отказ
   `reject` с именем решения и поля, если такой строки мандата нет ни в
   одном ANSWER-n задачи, поданном до этого `reject`; строки мандата
   распознаются тем же разбором, что у команды `answer`
   (`orchestrator/answer.py`, `orchestrator/advance_gates/mandate.py`).
8. Принятый файл решения переводит задачу `spec_gate -> spec_writing`;
   его текст целиком уходит в журнал тем же префиксом
   «возврат из spec_gate: », устройство брифа аналитика и аудитора не
   меняется.
9. Прежняя форма `reject <id> "<причина>"` на `spec_gate` работает
   по-прежнему и дополнительно печатает предупреждение «решение без сверки
   следствий — для сессии Оператора обязательна форма --decision».
   В остальных состояниях `reject` не меняется.
10. Документация: `docs/operator-session.md` («Уроки 04.11», п. 1 —
    ссылка на форму `--decision`), `docs/operator-gates.md` (гейт SPEC),
    `docs/codebase-map.md` (регенерация под новый модуль), справка
    команды `reject` в `orchestrator/artel.py`.
11. Приложением к PLAN (защищённые пути; коммит Оператора воротами мержа)
    — дословно диффы ТЗ, разделы PLAN «## Приложение: <путь> — урок 04.11»:
    новый файл `templates/SPEC-GATE-DECISION.md`; правка
    `skills/spec-audit.md` (дописывает абзацы и продолжает строку
    «поломку, — отклонение.» новыми предложениями, прочие существующие
    строки не меняются); правка `skills/spec-authoring.md` (только
    добавляет раздел «## Решения Оператора на гейте SPEC — не дословно»).
    Применимость проверяет гейт применимости приложений PLAN.

## Критерии приёмки
AC-1. `reject <id> --decision <файл>` на `spec_gate` с полностью и
верно заполненным файлом переводит задачу в `spec_writing`; в журнале —
запись с префиксом «возврат из spec_gate: » и полным текстом файла;
бриф аналитика следующего шага содержит этот текст в разделе «Решения
Оператора на гейте SPEC».

AC-2. Файл без раздела «## Решения» — отказ `reject`, задача остаётся в
`spec_gate`, журнал возврата не пополнен.

AC-3. Для каждого из шести полей: файл, в котором у одного решения это
поле пусто (или отсутствует), — отказ с именем этого решения
(«Решение <n>») и именем поля; задача остаётся в `spec_gate`.

AC-4. Поле «Утверждения о коде и поведении» без `файл:строка`, «опыт:» и
«нет» — отказ с именем решения и поля; задача остаётся в `spec_gate`.

AC-5. Поле с оставленной заглушкой шаблона «<…>» — отказ с именем решения
и поля; задача остаётся в `spec_gate`.

AC-6. Поле «Прежние решения» со ссылкой на несуществующий номер — отказ с
именем решения и поля; ссылка на существующий номер прежнего решения
(«k.n» возврата файлом или «k» возврата текстом) проходит.

AC-7. «Существующие тесты» с элементом «мандат: <строка>», когда ни один
ANSWER-n задачи не несёт этой строки мандата, — отказ, задача в
`spec_gate`; после `answer` с той же строкой мандата тот же файл решения
проходит и переводит задачу в `spec_writing`.

AC-8. Вывод отказа `reject --decision` перечисляет прежние решения задачи:
для возврата файлом — номер «k.n» и текст поля «Текст», для возврата
текстом — номер «k» и не более первых 120 знаков причины; переносы строк
свёрнуты.

AC-9. Подсказка остановки `auto` на `spec_gate` перечисляет прежние
решения задачи в той же форме, что AC-8.

AC-10. Прежняя форма `reject <id> "<причина>"` на `spec_gate` переводит
задачу в `spec_writing`, как и раньше, и печатает предупреждение
«решение без сверки следствий — для сессии Оператора обязательна форма
--decision».

AC-11. `fsm.cmd_reject(task, reason)` и `fsm._cmd_reject(conn, task,
reason)` вызываются позиционно, как сегодня; новый параметр файла
решения — именованный со значением по умолчанию `None`.

AC-12. Модуль `orchestrator/spec_gate_decision.py` разбирает файл решения
без чтения каталога `templates/`: разбор проходит при отсутствии
`templates/SPEC-GATE-DECISION.md` на диске.

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (`orchestrator/fsm.py`,
`orchestrator/artel.py`, `orchestrator/auto.py`,
`orchestrator/spec_gate_decision.py`, `docs/operator-gates.md`,
`docs/operator-session.md`; общие зоны не в счёт); число критериев
приёмки ≥ 10 (12).

Материал для решения Оператора — монолит: разбор файла
(`spec_gate_decision.py`) без ключа `--decision` в `artel.py` и ветки в
`fsm._cmd_reject` недостижим из CLI и не проверяем по AC-1…AC-8;
ключ без разбора неработоспособен. Перечень прежних решений (AC-8, AC-9)
читает номера «k.n», которые появляются только вместе с формой
`--decision`, — отдельная часть «подсказка auto» без неё печатала бы
только номера «k». Документация описывает именно эту форму. Объём
кода невелик (один новый модуль, ветка `_cmd_reject`, ключ CLI,
дополнение подсказки), бюджет — уровень «до 15 критериев и до 7 файлов».
Альтернатива — нарезка «разбор + reject --decision» / «перечень в
подсказке auto + документация» — возможна, но вторая часть мала и
удвоит накладные шаги.

  `orchestrator/brief.py`, `orchestrator/answer.py`,
  `orchestrator/advance_gates/mandate.py`, `orchestrator/rounds.py`,
  `orchestrator/role_git.py`.

  без правки» (ТЗ, критерии) — её держит пульт: полный зелёный набор
  `tests/` и гейт неослабления тестов; раздела «Меняемое поведение» у
  задачи нет. Существующие тесты, которые это затрагивает: позиционные

  процессов сверх команд пульта и без меняющих команд против настоящего
  репозитория.
