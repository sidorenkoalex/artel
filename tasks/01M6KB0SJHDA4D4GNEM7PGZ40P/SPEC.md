# SPEC: Возврат с гейта SPEC файлом решения

## Контекст
`reject <id> "<причина>"` на `spec_gate` (`orchestrator/fsm.py:1890`,
ветка `if state == "spec_gate"` в `_cmd_reject`) принимает свободный текст
и проверяет только его непустоту (`orchestrator/fsm.py:1912`); текст уходит
в журнал с префиксом «возврат из spec_gate: » (`orchestrator/fsm.py:1919`,
`brief.SPEC_GATE_RETURN_PREFIX`, `orchestrator/brief.py:76`) и попадает в
бриф аналитика и аудитора разделом «Решения Оператора на гейте SPEC»
(`brief._spec_gate_reasons`). Инцидент 04.11 (01M6JJ4J4NBV2Y1Q4XHE3C3FVT):
из десяти кругов SPEC около половины вызвано решениями Оператора на гейте
— ложное утверждение о git, условие, невыполнимое в зонах, опасная форма
теста, незаданный канал подстановки, противоречие двух решений; мандат на
правку теста подан текстом причины, а не строкой мандата в ANSWER.
Правило сверки следствий (`docs/operator-session.md`, «Уроки 04.11», п. 1)
пульт сегодня не проверяет. Задача вводит форму возврата файлом решения
с обязательными полями сверки, проверяемыми по форме, номерам и наличию
мандата.

## Требования
1. `reject <id> --decision <файл>` на `spec_gate`. Ключ `--decision`
   разбирается в `orchestrator/artel.py` явно, а не как текст причины.
   Сигнатуры: `fsm.cmd_reject(task_id, reason, session_id=None, *,
   decision_file=None)` — новый аргумент только именованный, после
   `session_id`; `fsm._cmd_reject(conn, task_id, reason)` позиционно
   сохраняется, новый параметр тела — тоже только именованный, по
   умолчанию `None`. При `decision_file=None` `cmd_reject` зовёт тело
   прежним вызовом `_cmd_reject(conn, tid, reason)` без именованных
   аргументов (держит `tests/test_lease_run_task_command.py:177–182`:
   `kwargs == {}`, `args[1:] == (FULL, "причина")`).
2. Файл решения — по форме шаблона `templates/SPEC-GATE-DECISION.md`
   (приложение п. 11): раздел «## Решения», в нём подразделы
   «### Решение <n>», у каждого шесть полей. Формы полей:
   - «Текст» — непуст;
   - «Утверждения о коде и поведении» — содержит `файл:строка`, или
     «опыт:», или «нет»;
   - «Чем проверяется» — содержит `AC-<n>` и одно из «временный дублёр» /
     «не меняет файлов»;
   - «Существующие тесты» — «нет», либо перечень путей `tests/…` с «не
     ломаются», либо «мандат: <строка мандата>»;
   - «Прежние решения» — по требованию 6;
   - «Зоны» — «выполнимо в зонах SPEC» либо перечень путей.
   Отказ `reject` с именем решения и поля (или с указанием на отсутствие
   раздела), состояние задачи не меняется, если: отсутствует раздел
   «## Решения»; поле отсутствует или пусто; поле не по форме выше; в поле
   оставлена заглушка шаблона.
3. Заглушка шаблона — дословный текст любой заглушки из шаблона (строки
   «<…>» шаблона `templates/SPEC-GATE-DECISION.md` как они есть). Прочие
   угловые скобки в тексте поля (например `<id>`) допустимы.
4. Разбор файла решения — в новом модуле `orchestrator/spec_gate_decision.py`;
   во время работы он не читает каталог шаблонов: форма и заглушки зашиты
   в модуле.
5. Номера решений: решение n возврата k — «k.n», где k — номер возврата
   с гейта SPEC этой задачи, тот же, что «№k» в брифе; возврат текстом
   имеет номер «k». Возврат считается возвратом файлом, если текст записи
   журнала после префикса «возврат из spec_gate: » начинается с заголовка
   шаблона «# Решение Оператора на гейте SPEC» — тогда номера «k.n»; иначе
   — «k». На отказе `reject` (форма `--decision`) и в подсказке остановки
   `auto` на `spec_gate` (`orchestrator/auto.py`) пульт печатает перечень
   прежних решений задачи: для возврата файлом — номер «k.n» и текст поля
   «Текст» каждого решения; для возврата текстом — номер «k» и первые 120
   знаков причины. Переносы строк в печатаемом тексте свёрнуты. Подсказка
   остановки на `spec_gate` (`config.AUTO_STOP["spec_gate"]`,
   `orchestrator/config.py`) называет форму `--decision`.
6. Поле «Прежние решения»: если у задачи есть прежние возвраты с гейта
   SPEC, поле обязано перечислить ВСЕ номера прежних решений задачи
   («k» или «k.n» по требованию 5) и содержать «противоречий нет»; «первое
   решение» допустимо только когда прежних возвратов нет. Иначе — в том
   числе пропущенный номер, ссылка на номер, которого нет среди прежних
   решений задачи, «первое решение» при наличии прежних возвратов — отказ
   `reject` с именем решения и поля, состояние не меняется.
7. Элемент «мандат: <маркер> <элементы>» в поле «Существующие тесты»:
   элементы разбираются `mandate.elements`
   (`orchestrator/advance_gates/mandate.py`); каждый элемент обязан входить
   в элементы строк того же маркера в ANSWER-n задачи, поданных до этого
   `reject`. Иначе — отказ `reject` с именем решения и поля, состояние не
   меняется.
8. Принятый файл решения переводит задачу `spec_gate -> spec_writing`;
   его текст целиком уходит в журнал тем же префиксом
   «возврат из spec_gate: », устройство брифа аналитика и аудитора не
   меняется.
9. Прежняя форма `reject <id> "<причина>"` на `spec_gate` работает
   по-прежнему и дополнительно печатает предупреждение «решение без сверки
   следствий — для сессии Оператора обязательна форма --decision».
   В остальных состояниях `reject` без `--decision` не меняется.
10. Отказы команды без смены состояния: `--decision` без значения;
    несуществующий или нечитаемый файл; `--decision` вместе с позиционной
    причиной; `--decision` в состоянии, отличном от `spec_gate`, — с
    текстом «--decision применим только на spec_gate».
11. Документация: `docs/operator-session.md` («Уроки 04.11», п. 1 —
    ссылка на форму `--decision`), `docs/operator-gates.md` (гейт SPEC),
    `docs/codebase-map.md` (регенерация под новый модуль), справка
    команды `reject` в `orchestrator/artel.py`.
12. Приложением к PLAN (защищённые пути; коммит Оператора воротами мержа)
    — диффы ТЗ, разделы PLAN «## Приложение: <путь> — урок 04.11»:
    новый файл `templates/SPEC-GATE-DECISION.md`; правка
    `skills/spec-audit.md` (дописывает абзацы и продолжает строку
    «поломку, — отклонение.» новыми предложениями, прочие существующие
    строки не меняются); правка `skills/spec-authoring.md` (только
    добавляет раздел «## Решения Оператора на гейте SPEC — не дословно»).
    При переносе диффов ТЗ в PLAN закрывающие ``` — с новой строки (в ТЗ
    они склеены с последней строкой диффа). В комментарии шаблона «с пятью
    полями» заменяется на «с шестью полями» (правка строки нового файла в
    приложении). Прочее — дословно. Применимость проверяет гейт
    применимости приложений PLAN.

## Критерии приёмки
AC-1. `reject <id> --decision <файл>` на `spec_gate` с полностью и
верно заполненным файлом переводит задачу в `spec_writing`; в журнале —
запись с префиксом «возврат из spec_gate: » и полным текстом файла;
бриф аналитика следующего шага содержит этот текст в разделе «Решения
Оператора на гейте SPEC».

AC-2. Файл без раздела «## Решения» — отказ `reject`, задача остаётся в
`spec_gate`, журнал возврата не пополнен.

AC-3. Для каждого из шести полей: файл, в котором у одного решения это
поле пусто (или отсутствует), — отказ с именем этого решения
(«Решение <n>») и именем поля; задача остаётся в `spec_gate`.

AC-4. Поле не по форме требования 2 — отказ с именем решения и поля,
задача остаётся в `spec_gate`; по одному случаю на поле: «Утверждения о
коде и поведении» без `файл:строка`, «опыт:» и «нет»; «Чем проверяется»
без `AC-<n>` либо без «временный дублёр» / «не меняет файлов»;
«Существующие тесты» не «нет», не перечень `tests/…` с «не ломаются» и не
«мандат: …»; «Зоны» не «выполнимо в зонах SPEC» и не перечень путей.
Поля по форме проходят.

AC-5. Поле с дословной заглушкой шаблона (строкой «<…>» шаблона как она
есть) — отказ с именем решения и поля; задача остаётся в `spec_gate`.
Поле с прочими угловыми скобками (например `<id>`) отказа по заглушке не
вызывает.

AC-6. «Прежние решения»: при наличии прежних возвратов поле, перечисляющее
все их номера («k.n» возврата файлом, «k» возврата текстом) и
«противоречий нет», проходит; поле без одного из номеров, со ссылкой на
несуществующий номер, без «противоречий нет» или с «первое решение» —
отказ с именем решения и поля. Без прежних возвратов «первое решение»
проходит.

AC-7. «Существующие тесты» с элементом «мандат: <маркер> <элементы>»,
когда не каждый элемент (по `mandate.elements`) входит в элементы строк
того же маркера в ANSWER-n задачи, поданных до `reject`, — отказ, задача
в `spec_gate`; после `answer` с той же строкой мандата тот же файл
решения проходит и переводит задачу в `spec_writing`.

AC-8. Вывод отказа `reject --decision` и подсказка остановки `auto` на
`spec_gate` перечисляют прежние решения задачи: возврат, чья запись
журнала после префикса начинается с «# Решение Оператора на гейте SPEC», —
номерами «k.n» и текстом поля «Текст»; прочий возврат — номером «k» и не
более первых 120 знаков причины; переносы строк свёрнуты. Подсказка
остановки на `spec_gate` называет форму `--decision`.

AC-9. Прежняя форма `reject <id> "<причина>"` на `spec_gate` переводит
задачу в `spec_writing`, как и раньше, и печатает предупреждение
«решение без сверки следствий — для сессии Оператора обязательна форма
--decision».

AC-10. `fsm.cmd_reject(task_id, reason, session_id)` вызывается
позиционно, как сегодня; `decision_file` — только именованный, после
`session_id`, по умолчанию `None`; при `decision_file=None` тело зовётся
`_cmd_reject(conn, tid, reason)` без именованных аргументов — существующий
`tests/test_lease_run_task_command.py:177–182` (`kwargs == {}`,
`args[1:] == (FULL, "причина")`) зелёный без правки.

AC-11. Разбор файла решения не зависит от файла шаблона: тест в песочнице
удаляет или меняет `templates/SPEC-GATE-DECISION.md`, результат разбора
того же файла решения прежний.

AC-12. `reject <id> --decision` без значения — отказ, состояние не
меняется.

AC-13. `reject <id> --decision <файл>` с несуществующим или нечитаемым
файлом — отказ, состояние не меняется.

AC-14. `reject <id> "<причина>" --decision <файл>` (ключ вместе с
позиционной причиной) — отказ, состояние не меняется.

AC-15. `reject <id> --decision <файл>` в состоянии, отличном от
`spec_gate`, — отказ с текстом «--decision применим только на
spec_gate», состояние не меняется.

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (`orchestrator/fsm.py`,
`orchestrator/artel.py`, `orchestrator/auto.py`,
`orchestrator/spec_gate_decision.py`, `docs/operator-gates.md`,
`docs/operator-session.md`; общие зоны не в счёт); число критериев
приёмки ≥ 10 (15); `budget_usd` ≥ $30.

Материал для решения Оператора — монолит: разбор файла
(`spec_gate_decision.py`) без ключа `--decision` в `artel.py` и ветки в
`fsm._cmd_reject` недостижим из CLI и не проверяем по AC-1…AC-8;
ключ без разбора неработоспособен. Перечень прежних решений (AC-8)
читает номера «k.n», которые появляются только вместе с формой
`--decision`, — отдельная часть «подсказка auto» без неё печатала бы
только номера «k». Документация описывает именно эту форму. Объём
кода невелик (один новый модуль, ветка `_cmd_reject`, ключ CLI,
дополнение подсказки), бюджет — уровень «до 15 критериев и до 7 файлов».
Альтернатива — нарезка «разбор + reject --decision» / «перечень в
подсказке auto + документация» — возможна, но вторая часть мала и
удвоит накладные шаги.
