# SPEC: Возврат с гейта SPEC файлом решения

## Контекст
`reject <id> "<причина>"` на `spec_gate` (`orchestrator/fsm.py:1890`,
ветка `if state == "spec_gate"` в `_cmd_reject`) принимает свободный текст
и проверяет только его непустоту (`orchestrator/fsm.py:1912`); текст уходит
в журнал с префиксом «возврат из spec_gate: » (`orchestrator/fsm.py:1919`,
`brief.SPEC_GATE_RETURN_PREFIX`, `orchestrator/brief.py:76`) и попадает в
бриф аналитика разделом «Причина возврата» (последний возврат,
`orchestrator/brief.py:1584–1596`, `:1627–1630`) и в бриф аудитора разделом
«Решения Оператора на гейте SPEC» (все возвраты, `brief._spec_gate_reasons`,
`orchestrator/brief.py:1343`, `:1325`). Инцидент 04.11 (01M6JJ4J4NBV2Y1Q4XHE3C3FVT):
из десяти кругов SPEC около половины вызвано решениями Оператора на гейте
— ложное утверждение о git, условие, невыполнимое в зонах, опасная форма
теста, незаданный канал подстановки, противоречие двух решений; мандат на
правку теста подан текстом причины, а не строкой мандата в ANSWER.
Правило сверки следствий (`docs/operator-session.md`, «Уроки 04.11», п. 1)
пульт сегодня не проверяет. Задача вводит форму возврата файлом решения
с обязательными полями сверки, проверяемыми по форме, номерам и наличию
мандата.

## Требования
1. `reject <id> --decision <файл>` на `spec_gate`. Ключ `--decision`
   разбирается в `orchestrator/artel.py` явно, а не как текст причины.
   Сигнатуры: `fsm.cmd_reject(task_id, reason, session_id=None, *,
   decision_file=None)` — новый аргумент только именованный, после
   `session_id`; `fsm._cmd_reject(conn, task_id, reason)` позиционно
   сохраняется, новый параметр тела — тоже только именованный, по
   умолчанию `None`. При `decision_file=None` `cmd_reject` зовёт тело
   прежним вызовом `_cmd_reject(conn, tid, reason)` без именованных
   аргументов (держит `tests/test_lease_run_task_command.py:177–182`:
   `kwargs == {}`, `args[1:] == (FULL, "причина")`).
   В теле `cmd_reject` — ровно один вызов `lease.run_task_command`;
   ветвление по `decision_file` — внутри одной лямбды третьего аргумента:
   при `None` — `_cmd_reject(conn, tid, reason)` без именованных
   аргументов, иначе — `_cmd_reject(conn, tid, reason,
   decision_file=decision_file)`. Чтение файла решения, ANSWER-n и журнала
   задачи — внутри `_cmd_reject`; `store.db` в теле `cmd_reject` не
   появляется (держит AST-линтеры обвязки
   `tests/test_lease_run_task_command.py:133–157` и
   `tests/test_01m5mhvrs39cdp5v4hbwy4k7wk_run_task_command.py:225–257`:
   нет `store.db`/`store.resolve_task_id`/`lease.run_locked`, один
   `lease.run_task_command`, вторым аргументом `session_id`, id задачи в
   `_cmd_*` лямбды — её параметр).
2. Файл решения — по форме шаблона `templates/SPEC-GATE-DECISION.md`
   (приложение п. 12): файл начинается строкой
   «# Решение Оператора на гейте SPEC», в нём раздел «## Решения», в нём
   подразделы «### Решение <n>», у каждого шесть полей. HTML-комментарий
   (`<!-- … -->`) при разборе пропускается. Устройство поля: метка поля
   «<Поле>:» распознаётся только в начале строки; та же метка в середине
   строки (например «Зоны:» внутри строки поля «Текст») — часть значения
   поля, не метка. Значение — остаток строки после «<Поле>:» и следующие
   строки до следующей метки поля в начале строки или строки
   «### Решение»; порядок полей в решении свободный; повтор поля в одном
   решении — отказ. Термины форм: `файл:строка` — токен
   `<путь>:<целое>`, где путь без пробелов и содержит «/» или расширение
   (точку, за которой идут буквы); «путь» в полях «Существующие тесты» и
   «Зоны» — токен без пробелов, содержащий «/». Формы полей:
   - «Текст» — непуст;
   - «Утверждения о коде и поведении» — значение целиком равно «нет»
     после снятия пробелов; иначе содержит `файл:строка` или «опыт:»;
   - «Чем проверяется» — содержит `AC-<n>` и одно из «временный дублёр» /
     «не меняет файлов»;
   - «Существующие тесты» — значение целиком равно «нет» после снятия
     пробелов; иначе содержит перечень путей `tests/…` с «не ломаются»
     либо «мандат: <строка мандата>»;
   - «Прежние решения» — по требованию 6;
   - «Зоны» — «выполнимо в зонах SPEC» либо перечень путей.
   n в «### Решение <n>» — целое; номера подразделов уникальны и идут
   подряд с 1.

   заголовка, раздела, на номер подраздела), состояние задачи не
   меняется, если: файл не начинается строкой «# Решение Оператора на
   гейте SPEC»; отсутствует раздел «## Решения»; n подраздела не целое,
   повторяется или номера идут не подряд с 1; поле отсутствует или пусто;
   поле повторено в одном решении; поле не по форме выше; в поле оставлена заглушка шаблона.

## Критерии приёмки
AC-1. `reject <id> --decision <файл>` на `spec_gate` с полностью и
верно заполненным файлом переводит задачу в `spec_writing`; в журнале —
запись с префиксом «возврат из spec_gate: » и полным текстом файла;
бриф аналитика следующего шага содержит этот текст в разделе «Причина
возврата», бриф аудитора — в разделе «Решения Оператора на гейте SPEC».

AC-2. Файл без раздела «## Решения», файл, первая строка которого не
«# Решение Оператора на гейте SPEC», и файл, где номера подразделов
«### Решение <n>» не целые, повторяются или идут не подряд с 1, — каждый
отказ `reject`, задача остаётся в `spec_gate`, журнал возврата не
пополнен.

AC-3. Для каждого из шести полей: файл, в котором у одного решения это
поле пусто, отсутствует или повторено, — отказ с именем этого решения
(«Решение <n>») и именем поля; задача остаётся в `spec_gate`. Решение с
полями в ином порядке, чем в шаблоне, и с многострочным значением поля
(продолжение до следующей метки поля в начале строки или «### Решение»)
проходит. Метка поля в середине строки (например «Зоны:» внутри строки
поля «Текст») — часть значения: повтором поля «Зоны» не считается и
значение «Текст» не обрывает.

AC-4. Поле не по форме требования 2 — отказ с именем решения и поля,
задача остаётся в `spec_gate`; по одному случаю на поле: «Утверждения о
коде и поведении» не равно целиком «нет» и без `файл:строка` и «опыт:»
(в том числе «не проверял, ответа нет», а также «проверено 04.11: 3
раза», «AC-3:1», «нет:2» — не `файл:строка`); «Чем проверяется»
без `AC-<n>` либо без «временный дублёр» / «не меняет файлов»;
«Существующие тесты» не равно целиком «нет», не перечень `tests/…` с «не
ломаются» и не «мандат: …» (в том числе «проверок нет»); «Зоны» не
«выполнимо в зонах SPEC» и не перечень путей (токенов без пробелов с
«/»). Поля по форме проходят, в том числе «нет» с пробелами вокруг и
`orchestrator/fsm.py:1863` как `файл:строка`.

AC-5. Поле, содержащее дословный текст поля шаблона после двоеточия
целиком (внешняя пара «<…>» со всем вложенным), — отказ с именем решения
и поля; задача остаётся в `spec_gate`. Поле только с вложенным фрагментом
шаблона (например «мандат: <строка мандата>» без внешней пары) или с
прочими угловыми скобками (например `<id>`) отказа по заглушке не
вызывает; HTML-комментарий шаблона в файле отказа не вызывает.

AC-6. «Прежние решения»: при наличии прежних возвратов поле со ссылками
«№…» на все их номера («№k.n» возврата файлом, «№k» возврата текстом) и
«противоречий нет» проходит, в том числе когда в поле есть «AC-3», дата
«04.11» или «2026-11-04», id задачи; номер без «№» ссылкой не
засчитывается. Поле без ссылки на один из номеров, со ссылкой на
несуществующий номер (например «№4» при трёх возвратах, «№2.5» при трёх
решениях возврата 2), без «противоречий нет» или с «первое решение» —
отказ с именем решения и поля. Без прежних возвратов «первое решение»
проходит.

AC-7. «Существующие тесты» с элементом «мандат: <строка мандата>»:
когда не каждый элемент (по `mandate.line_elements`, у маркера по
идентификатору — `mandate.id_elements`) входит в элементы строк того же
маркера в ANSWER-n задачи, поданных до `reject`, — отказ, задача в
`spec_gate`; после `answer` с той же строкой мандата тот же файл решения
проходит и переводит задачу в `spec_writing`. Строка мандата с маркером
«Расширение зон разрешено:», «Зависимости мержа:» или без известного
маркера — отказ с текстом «на spec_gate — только мандат тестов», задача в
`spec_gate`.

AC-8. Вывод отказа `reject --decision` по содержанию файла и подсказка
остановки `auto` на `spec_gate` перечисляют прежние решения задачи,
k — порядковый номер записи среди возвратов, которые находит
`brief._spec_gate_reasons`: возврат, поданный через `--decision`, —
номерами «k.n» и текстом поля «Текст»; прочий возврат (в том числе
запись с заголовком, но не по форме) — номером «k» и не более первых 120
знаков причины; переносы строк свёрнуты. Отказы AC-12…AC-15 перечня не
печатают. Подсказка остановки на `spec_gate` и справка команды `reject`
в `orchestrator/artel.py` называют форму `--decision`.

AC-9. Прежняя форма `reject <id> "<причина>"` на `spec_gate` переводит
задачу в `spec_writing`, как и раньше, и печатает предупреждение

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (`orchestrator/fsm.py`,
`orchestrator/artel.py`, `orchestrator/auto.py`,
`orchestrator/spec_gate_decision.py`, `docs/operator-gates.md`,
`docs/operator-session.md`; общие зоны не в счёт); число критериев
приёмки ≥ 10 (15); `budget_usd` ≥ $30.

Материал для решения Оператора — монолит: разбор файла
(`spec_gate_decision.py`) без ключа `--decision` в `artel.py` и ветки в
`fsm._cmd_reject` недостижим из CLI и не проверяем по AC-1…AC-8;
ключ без разбора неработоспособен. Перечень прежних решений (AC-8)
читает номера «k.n», которые появляются только вместе с формой
`--decision`, — отдельная часть «подсказка auto» без неё печатала бы
только номера «k». Документация описывает именно эту форму. Объём
кода невелик (один новый модуль, ветка `_cmd_reject`, ключ CLI,
дополнение подсказки), бюджет — уровень «до 15 критериев и до 7 файлов».
Альтернатива — нарезка «разбор + reject --decision» / «перечень в
подсказке auto + документация» — возможна, но вторая часть мала и
удвоит накладные шаги.
