## Пути обхода гейтов
- **Файл решения без заголовка.** Требование 2 не обязывает файл
  начинаться с «# Решение Оператора на гейте SPEC». Признак «возврат
  файлом» в требовании 5 — именно этот заголовок. Файл без него, с
  пустой строкой или комментарием перед ним проходит `reject`, а потом
  числится возвратом текстом с одним номером «k». Следующему решению
  достаточно сослаться на «k», а не на каждое «k.n», и сверка с
  отдельными решениями обходится. Обратный случай: причина текстом,
  начатая с этого заголовка, разбирается как файл. Если «## Решения» в
  ней нет, номеров не будет, и возврат выпадет из перечня и из
  обязательных ссылок требования 6.
- **Номера в «Прежних решениях».** Набор номеров из свободного текста
  не задан. «Ссылка на номер, которого нет» и «перечислены все»
  проверяются разбором, который выберет разработчик. Кроме того, нет
  требования, чтобы n в «### Решение <n>» было целым и неповторяющимся:
  два «Решение 1» дают один номер «k.1» на два решения.

## Вердикт
`concerns`. Девять пунктов прошлого аудита закрыты решением №1 и SPEC.
Факты о коде верны, зоны достаточны, диффы приложения применимы.
Отклонения для решения Оператора на гейте:
1. **AST-линтеры `cmd_reject` не названы.** «Не входит» (SPEC.md, «Не
   входит», перечень тестов) не называет
   `tests/test_lease_run_task_command.py:133–157` и
   `tests/test_01m5mhvrs39cdp5v4hbwy4k7wk_run_task_command.py:225–257`.
   Они требуют ровно один `lease.run_task_command` в `cmd_reject` и
   запрещают в нём `store.db`. Требование 1 «при `None` зовёт тело
   прежним вызовом» подталкивает к двум вызовам обвязки — это красный
   полный набор. Нужна строка: ветка `decision_file` — внутри одной
   лямбды, а чтение ANSWER и журнала — в `_cmd_reject`.
2. **Признак файла по заголовку.** Требование 2 не требует заголовка
   «# Решение Оператора на гейте SPEC», а требование 5 по нему
   различает «k.n» и «k» (SPEC.md, требования 2, 5; AC-8). Это обход
   сверки с отдельными решениями. Не задано и то, как нумеровать причину
   текстом с этим заголовком, но без «## Решения». Варианты: отказ
   `reject` на файл без заголовка первой строкой; для записи журнала
   признак «заголовок и разбор прошёл», иначе «k».
3. **Номера решений.** Не задано, что считается номером в поле «Прежние
   решения» (SPEC.md, требование 6; AC-6): `AC-3`, `04.11`, id задачи.
   Не задано и то, что n в «### Решение <n>» — целое, уникальное (и,
   при желании, подряд с 1).
4. **Набор заглушек.** У шаблона вложенные заглушки
   (`<…«опыт: <что сделано и что увидено>»…>`, `<…«мандат: <строка
   мандата>»…>`) и `<n>` в комментарии (TZ.md, дифф шаблона). Требование
   3 / AC-5 не говорит, входят ли внутренние `<…>` и `<n>` в «дословный
   текст заглушки». От этого зависит, отказывают ли «мандат: <строка
   мандата>» и «Решение <n>» в поле.
5. **AC-11 слаб.** Он не ловит чтение шаблона по `__file__` из
   репозитория пульта: тест в песочнице этот путь не меняет. Сильнее —
   добавить проверку, что модуль не открывает файлов (или не ссылается
   на `templates`).
6. **Разбор мандата.** Решение №1 п. 5 / требование 7 называют
   `mandate.elements`, а ТЗ п. 3 — разбор `answer`, то есть
   `line_elements` с `id_elements` для маркера по идентификатору
   (`orchestrator/answer.py:264–267`,
   `orchestrator/advance_gates/mandate.py:118–125`). Не задано и то,
   что делать с «мандат: …» без известного маркера или с маркером зон
   либо `merge_after`. На `spec_gate` такой ANSWER не принимается
   (`answer.py:250–259`), значит, отказ всегда.
