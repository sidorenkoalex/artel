## Замечания

- **blocker** — `orchestrator/budget.py:176-223` (`reseed_program_spend`), вызывается из `orchestrator/catalog.py:41` (`cmd_init`) — **`reseed_program_spend` систематически задваивает суммарный программный расход на любом «тёплом» пульте (БД не потеряна), а не только на холодном старте.** Функция безусловно суммирует «Стоимость итого» ИЗ ВСЕХ `docs/retro/T*.md` и кладёт результат в `spent_usd` синтетической строки `PROGRAM-SPEND-RESEED`; эта сумма складывается поверх уже существующих `tasks.spent_usd` строк ТЕХ ЖЕ самых задач — строки `tasks` не архивируются и не удаляются после `done`, а `retro.build_done`/`build_killed` (`orchestrator/retro.py:192,228`) берут «Стоимость итого» именно из `t["spent_usd"]` той же строки. `store.total_spent` (используется `check_program_spend` для порогов 70%/90%) суммирует `spent_usd` по ВСЕМ строкам без разбора — реальная задача и её RETRO-дубликат считаются дважды.

  Сценарий поломки (воспроизведён): задача `T001` в БД со `spent_usd=$50` (обычное, не потерянное состояние), у неё есть `docs/retro/T001.md` с «Стоимость итого: $50.00» (то, что и пишет сама система по завершении задачи). Оператор повторно зовёт `init` (PLAN «Подход», п.3, явно называет это поддерживаемым сценарием: «расход и так пересчитывается заново при каждом `init`, что покрывает и ... повторный прогон после новых RETRO») — `store.total_spent(conn)` до второго `init` = `$50.00`, после = `$100.00`. Каждый следующий реальный `init` после появления новых RETRO будет искажать сумму снова. Итог: пороги стоп-лосса программы (`check_program_spend`) считают вдвое больше реального расхода — ложные алерты `threshold` на пустом месте, либо (при иной комбинации сумм) маскировка реального пробоя другой ложной цифрой. Это не гипотетический край: PLAN сам описывает повторный `init` как штатный способ обновить пересев, то есть баг сработает при первом же штатном использовании фичи после того, как хотя бы одна задача дошла до `done`/`killed` на непотерянной БД.

  PLAN «Влияние на систему» этот эффект не обсуждает вовсе — рассуждение там ограничено тем, что юнит-тесты (без `docs/retro/`) не ломаются, и ручной проверкой AC-3, где RETRO-фикстуры `T001`/`T002` заведены БЕЗ соответствующих строк `tasks` (не отражают реальный «тёплый» пульт, где строка задачи и её RETRO сосуществуют). Предложение: не суммировать в пересев те задачи, чьи строки `tasks.spent_usd` всё ещё присутствуют в БД (действительно нужен только расход СТРОК, потерянных вместе с БД), либо ограничить сам вызов `reseed_program_spend` истинным холодным стартом (например, когда до пересева `tasks` пуста), а не каждым `init`.

- **major** — `orchestrator/store.py:160-196` (`seed_task_counters`), `orchestrator/doctor.py:559-583` (`check_task_counters`) — **посев и проверка счётчика номеров задач фактически работают только для `config.DEFAULT_TARGET`; для «прочих target» механизм не срабатывает даже там, где PLAN явно обещает, что он сработает.** `top` в `seed_task_counters` строится из принудительной записи `{DEFAULT_TARGET: 0}` и строк таблицы `tasks` (store.py:183-186) — если у target'а вообще нет строк в `tasks` (а именно это и есть «холодный старт» второго target'а: БД потеряна/пуста, но на диске в `.artel/projects/<target>/tasks/` уже есть задачи), этот target никогда не попадает в `top`, `coldstart.observed_max_task_number(target)` для него не вызывается (store.py:187-190), строка `task_counters` для него не заводится вовсе. Следующий `next_task_number(target)` (store.py:228-263) лениво стартует счётчик с `1` (store.py:250), игнорируя реально существующие на диске номера. `doctor.check_task_counters` наследует тот же слепой участок: `checked_targets = {DEFAULT_TARGET} ∪ store.counter_targets(conn)` (doctor.py:569) не включает target без строки `task_counters`, то есть ДО коллизии `doctor` тоже не предупредит.

  Воспроизведено: target `sled` с существующим `tasks/T005` на диске (`.artel/projects/sled/tasks/T005`) и без единой строки в БД — после `cmd_init`: `store.counter_targets(conn) == {'artel'}` (без `sled`), `store.peek_task_number(conn, 'sled') == 1` (не `6`), `doctor.check_task_counters(conn).status == 'ok'` (не увидел проблему). Следующая `new` для `sled` выдаст задаче номер `T001`, хотя наблюдаемый max для этого target'а — `5`: ровно «тихая коллизия номеров», которую требование 3 SPEC называет причиной заводить алерт.

  Формулировки SPEC (требования 1-3) говорят про «target'а» без ограничения DEFAULT_TARGET, а сам PLAN «Подход», п.1 прямо заявляет: «для прочих target источник — их собственный `tasks/` под `.artel/projects/<target>/`» — код этого не делает. Предложение: `seed_task_counters` должна перебирать targets не только по строкам `tasks`, но и по каталогам `.artel/projects/*/` (или иному реестру target'ов, например `targets.yaml`), чтобы холодный посев для «прочих target» действительно происходил, как заявлено в PLAN.

## Вердикт

changes_requested — до мержа исправить:
1. (blocker) убрать двойной учёт в `budget.reseed_program_spend` — пересев не должен складываться с уже присутствующими в БД `tasks.spent_usd` тех же задач.
2. (major) расширить `store.seed_task_counters` (и, соответственно, множество target'ов, проверяемых `doctor.check_task_counters`) до реального перебора «прочих target», как это заявлено в PLAN «Подход», п.1 — либо, если разработчик считает, что multi-target для этой задачи вне объёма, явно сузить формулировку PLAN/эскалировать расхождение с буквальной формулировкой требований 1-3 SPEC, а не оставлять код и текст PLAN противоречащими друг другу.

## Предложения системе
- Синтетическая строка `tasks` для программных агрегатов (пересев расхода, `orchestrator/budget.py:214-223`) — общий антипаттерн класса «переиспользование предметной таблицы для несвязанного агрегата»: `store.total_spent` не умеет отличить «настоящую задачу» от «агрегата», и как только оба источника считают один и тот же факт, получается двойной учёт (см. Замечание 1). Для будущих задач, вводящих программные агрегаты поверх `tasks`, стоит с самого начала заводить отдельное хранилище (таблицу/поле), а не подкладывать синтетическую строку в таблицу, из которой уже считается сумма.
