## Замечания

Проверка предыдущих замечаний (перечитан полный код функций, не только diff-контекст):

- **Замечание 1 (blocker, итерация 1) — закрыто.** `orchestrator/budget.py:213-215`: `if store.task_exists(conn, path.stem): continue` — фильтр верный, `path.stem` для файла `T001.md` даёт `"T001"`, что совпадает с id строки `tasks`. Архивации задач в системе нет (`tasks` — единственная и постоянная таблица, грепом подтверждено отсутствие archive-механики), так что `task_exists() == False` действительно означает «строка потеряна вместе с БД», а не «задача архивирована при живой БД» — предположение фикса корректно. Регресс-тесты `test_retro_of_task_still_in_db_is_not_double_counted` и `test_mixes_lost_and_live_rows_without_double_counting` воспроизводят оба сценария из замечания и проходят.
- **Замечание 2 (major, итерация 1) — закрыто.** `orchestrator/store.py:195-200` и `orchestrator/doctor.py:575-580` расширяют множество target'ов декларацией `targets.yaml` (best-effort — `TargetsError` → пустое множество, не роняет посев/проверку, тот же приём что и в остальном `doctor.all_checks`). `coldstart.observed_max_task_number` (`orchestrator/coldstart.py:27-35`) для НЕ-default target сканирует только `.artel/projects/<target>/tasks/` (без git-подпроцессов) — соответствует PLAN «Подход», п.1, лишней стоимости на «прочие» target не добавлено. Регресс-тесты `MultiTargetSeedAndCheckTest` воспроизводят оба симптома прошлой итерации (посев не видит target, `doctor` не видит расхождение) и проходят.

Новых замечаний по инкременту (только к правкам этой итерации) не найдено — оба фикса точечные, не расширяют зону задачи, не трогают защищённые пути, не ослабляют существующие проверки (наоборот, `check_task_counters` теперь строже — видит больше target'ов).

## Предложения системе
- Синтетическая строка `tasks` для программных агрегатов (пересев расхода) — общий антипаттерн класса «переиспользование предметной таблицы для несвязанного агрегата»; в этой итерации риск двойного учёта закрыт точечным фильтром (`task_exists`), но конструкция остаётся хрупкой к следующему подобному агрегату. Наблюдение подтверждается второй раз (было в REVIEW итерации 1) — для будущих задач, вводящих программные агрегаты поверх `tasks`, стоит с самого начала заводить отдельное хранилище, а не подкладывать синтетическую строку в таблицу, из которой уже считается сумма.
