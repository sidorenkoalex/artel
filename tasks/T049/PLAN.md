# PLAN: Холодный старт пульта: посев от наблюдаемого мира (ADR-0005)

## Подход

Три независимых дыры (SPEC «Контекст») закрываются тремя независимыми
механизмами, объединёнными общей точкой входа `catalog.cmd_init`:

**1. Счётчик номеров задач.** Наблюдаемый мир сканирует новый модуль
`orchestrator/coldstart.py` (`observed_max_task_number(target)`):
каталоги `tasks/T*`, ветки `task/t*` (через новый `gitcmd.list_branches`),
файлы `docs/retro/T*.md`, история `main` (`git log --format=%s`,
дословные коммиты `cmd_new`/`build_done`/`build_killed` начинаются с
`Tnnn:`) — источники ветки/retro/история проверяются только для
`config.DEFAULT_TARGET`: сегодня `cmd_new` заводит задачи только этого
target'а (ADR-0005 п.6, «id второго target — решение вместе с командой,
которая заводит его задачи», tasks/T020/PLAN.md); для прочих target
источник — их собственный `tasks/` под `.artel/projects/<target>/`.
Git-сканирование (два subprocess-вызова) пропускается, если `.git` у
`config.ROOT` не существует вовсе (`.exists()`, не `.is_dir()` — у
worktree это файл-gitlink, T045) — почти все юнит-песочницы без
настоящего git не платят даже за неудачный вызов.

`orchestrator/store.seed_task_counters` расширяется: для target'а, ещё
не имеющего строки `task_counters` (та же ветка `if target not in
known`, что и раньше), максимум берётся не только из строк `tasks`, но
и из `coldstart.observed_max_task_number`. Дорогой скан (FS+git) платится
РОВНО ОДИН РАЗ на target — как только строка счётчика заведена, `target
in known` и скан больше не зовётся ни одним следующим `store.db()`
(а он вызывается на каждой команде CLI). `coldstart` импортируется
внутри функции лениво — тем же приёмом, что `store.record_fixation`
уже лениво зовёт `fixation` (docstring `record_fixation`): `store.py`
остаётся листом графа импортов на момент загрузки модуля.

`catalog.cmd_init` после `create_schema` явно зовёт
`store.seed_task_counters(conn)` — раньше эта же функция срабатывала
бы лениво при первом же следующем `store.db()` (через `migrate()`), но
явный вызов делает посев частью самого `init`, как и просит требование 2,
а не побочным эффектом первого `new`.

**2. Проверка `doctor`.** Новая `doctor.check_task_counters(conn)`: для
`{DEFAULT_TARGET} ∪ store.counter_targets(conn)` сравнивает
`store.peek_task_number(target)` (не расходуя счётчик) с тем же
`coldstart.observed_max_task_number(target)` — расхождение (счётчик
СТРОГО ниже наблюдаемого max, требование 3 — «≥» это здоровое
состояние) заводит `incident`-алерт через `alerts.raise_alert`. Добавлена
в `doctor.all_checks`. Модель проверки — по образцу уже существующих
точечных проверок `check_orphans`/`check_leases` (именованный алерт +
`Check`, без блокировки шага).

**3. Программный расход.** `orchestrator/retro.py` получает
`parse_total_cost(text)` — тот же regex-приём, что уже есть в модуле
(`COST_RE`/`TOKENS_RE`), но по первой строке `_cost_block`
(`Стоимость итого: $X.XX`). `orchestrator/budget.reseed_program_spend(conn)`
сканирует `docs/retro/T*.md`, суммирует и пишет журнал «расход пересеян
из RETRO: $X по N задачам» (дословно требование 5). Сумма обязана
учитываться тем же `store.total_spent` (`SUM(spent_usd) FROM tasks`),
которым уже считаются пороги программы (`check_program_spend`) — без
отдельного контура учёта под пересев кладётся в `spent_usd`
синтетической строки `tasks` с зарезервированным id
(`config.PROGRAM_SPEND_RESEED_TASK_ID`, вне пространства `Tnnn`, никогда
не коллизирует). Строка не участвует в FSM (`state="done"`), только
несёт число. Пересев идемпотентен — сумма каждый раз ПЕРЕЗАПИСЫВАЕТ
(не прибавляет) `spent_usd` строки: повторный `init` после появления
новых RETRO не задваивает расход. Нечего пересевать (`docs/retro/`
отсутствует или пуст) — функция не создаёт строку и не журналирует,
чтобы не заводить фантомную запись «$0.00 по 0 задачам» в каждой
песочнице, которая когда-либо звала `cmd_init` (таких сотни в `tests/`).
Зовётся из `cmd_init` (требование 4 явно допускает и `init`, и отдельную
команду — выбран `init`, отдельной команды не заводится: расход и так
пересчитывается заново при каждом `init`, что покрывает и «холодный
старт», и «повторный прогон после новых RETRO»).

**4. Слой ролей `.artel/home`.** Место референса (требование 8) —
`docs/reference/role-home/`: копия целиком становится содержимым
`.artel/home` при `init`, если каталог ещё не существует
(`config.ROLE_HOME.exists()` — проверка, не перезапись существующего
курируемого Оператором содержимого). Содержимое референса — намеренно
минимальное: `.claude/CLAUDE.md` с текстом, объясняющим сам механизм
(«этот HOME куратор пульта, не HOME Оператора», ADR-0003 п.14) — не
инструкция роли (та приходит промптом шага, `runner`+`skills/*.md`).
Проверено грепом (`grep -rEi "token|secret|api[_-]?key|password"
docs/reference/role-home/`) — совпадений нет; аутентификация роли идёт
через keychain (`orchestrator/keychain.py`), не через файлы HOME
(утверждение требования 10). Сопроводительный `docs/reference/role-home.md`
(соседний файл, НЕ часть развёртываемого поддерева — не засоряет
`.artel/home` документацией) объясняет структуру и то, что содержимое
курирует Оператор по мере необходимости, редактируя РЕФЕРЕНС в репо
(не сам `.artel/home` — тот эфемерен).

**5. `check_backup_age`.** Требование 6 SPEC явно разрешает два исхода —
снять функцию или деградировать до информационной строки без алерта;
выбрана деградация (не снятие): маркер уже используется как честный
диагностический сигнал («когда был последний бэкап, если Оператор его
всё же ведёт по своей воле») — снятие стирало бы и эту информацию,
деградация её сохраняет, просто без гейта. Функция больше не зовёт
`alerts.raise_alert` ни в одной ветке и явно ack'ает свои же прежние
открытые алерты (`_auto_ack_gone(..., lambda _msg: False)`), закрывая
исторический шум, накопленный ДО этой правки.

**6. `docs/invariants.md`.** Требование 7 условно («если снятие/
деградация check_backup_age требует правки») — проверено (грепом по
файлу): ни один из 30 закодированных инвариантов и ни одна строка
таблицы «на ревью» не упоминает `check_backup_age`/`backup-marker`/
бэкап `.artel` — условие requirement 7 не наступает, приложенного диффа
не требуется. `docs/invariants.md` не трогается (AC-7).

**7. Честная документация о задачах в полёте (требование 11).**
`cmd_init` печатает одну строку о том, что строки БД задач в полёте
(ветки `task/*` без записи) не восстанавливаются автоматически — тем
же способом, каким уже печатаются финальные подсказки других команд
(`catalog.cmd_new`/`fsm`).

Архитектурно значимых решений сверх уже принятого ADR-0005 нет — новый
ADR не заводится.

## Шаги

1. `orchestrator/gitcmd.py`: `list_branches(prefix)` — список локальных
   веток по `refs/heads/<prefix>` (`git for-each-ref`), `None` — git не
   ответил.
2. Новый `orchestrator/coldstart.py`: `observed_max_task_number(target)`
   и приватные сканеры (каталоги задач, ветки, RETRO, история main);
   git-сканеры пропускаются без `.git` у `config.ROOT`.
3. `orchestrator/store.py`: `seed_task_counters` — расширение
   наблюдаемым миром (ленивый импорт `coldstart`) для target'а без
   строки счётчика; новые `counter_targets(conn)` и `task_exists(conn,
   task_id)`.
4. `orchestrator/doctor.py`: `check_task_counters(conn)` (новая
   проверка, требование 3), добавлена в `all_checks`; `check_backup_age`
   — деградация без алерта (требование 6).
5. `orchestrator/retro.py`: `parse_total_cost(text)`.
   `orchestrator/budget.py`: `reseed_program_spend(conn)` (требования
   4–5); `config.PROGRAM_SPEND_RESEED_TASK_ID`.
6. `docs/reference/role-home/.claude/CLAUDE.md` + сопроводительный
   `docs/reference/role-home.md` (требование 8, критерий 10).
7. `orchestrator/catalog.py`: `cmd_init` — явный
   `store.seed_task_counters`, разворачивание `.artel/home` из
   референса при отсутствии, вызов `budget.reseed_program_spend`,
   честная строка про задачи в полёте (требование 11).
8. Юнит-тесты: `tests/test_coldstart.py` (сканеры + расширенный
   `seed_task_counters` + `check_task_counters`), дополнение
   `tests/test_retro.py` (`parse_total_cost`), новый
   `tests/test_program_spend_reseed.py` (`reseed_program_spend`,
   идемпотентность), дополнение `tests/test_doctor.py`
   (`check_backup_age` больше не заводит incident при просроченном
   маркере — до этой задачи такого теста не было, только «маркер
   свежий» в составе `healthy_mocks`).
9. `python3 scripts/codebase_map.py` (правка `orchestrator/*.py`,
   `tests/*.py` — конвенция `conventions-core.md`), полный прогон
   `python3 -m unittest discover -s tests`, приёмочные тесты
   `tasks/T049/acceptance_tests/`, `scripts/guard.py`.

## Влияние на систему

Новый код — три добавленных модульных места (`coldstart.py`, функции
в `store.py`/`doctor.py`/`retro.py`/`budget.py`) и расширение
`cmd_init`; ни одна существующая публичная функция не убрана, только
`check_backup_age` меняет тело (сигнатура `(conn) -> Check` та же —
вызывающий код `all_checks`/тесты не меняют форму вызова).

Дорогой скан наблюдаемого мира (git-подпроцессы) платится не на каждый
`store.db()` (а он вызывается на каждой команде CLI), а не более одного
раза на target — как только заведена строка `task_counters`, дальнейшие
вызовы её не трогают (см. «Подход», п.1). Проверено: ни один
существующий тест (`tests/test_multitarget.py::...total_spent...`,
`tests/test_spec_budget.py`/`tests/test_step_cost.py`, проверяющие
вывод `cmd_status` через `assertIn`) не читает точный список/количество
строк `tasks` — добавление синтетической строки пересева расхода
(только когда `docs/retro/` реально непусто — что в юнит-песочницах без
специальной подготовки никогда не так) их не задевает; сохранённое
поведение `check_program_spend` (порог считается по `total_spent`)
проверено вручную сценарием AC-3 «пересев засчитывается в порог 90%».

`check_backup_age` перестаёт заводить `incident` — это ослабление
диагностики, но легализованное ADR-0005 п.3 явным текстом («check_
backup_age... теряет основание — снимается или деградирует»), не
самовольное решение задачи: принцип целостности (ADR-0002) требует
права Оператора на такое изменение — оно уже дано ADR-0005 при подписи
27.08. Существующие тесты `tests/test_doctor.py`, использующие
`touch_backup()` как условие «здорового» прогона, продолжают проходить
(маркер больше не обязателен для «ок», но его наличие тоже не мешает);
единственный тест, завязанный именно на поведение auto-ack backup_age
(`test_backup_age_auto_ack_does_not_touch_orphan_sources`), проверяет
изоляцию источников алертов, а не факт заведения самого backup_age —
не меняет смысл после правки.

`docs/invariants.md`, `templates/`, `skills/`, `.github/` не затронуты
диффом ветки напрямую (AC-7, проверено юнит-тестом
`tasks/T049/acceptance_tests/test_ac6_ac7_regression_and_protected_paths.py`,
реальный `git diff main...HEAD`). Требование 7 (подготовленный дифф
`docs/invariants.md`) не наступает — файл не упоминает снимаемую
проверку (см. «Подход», п.6) — поэтому и подготовленного диффа к этой
задаче не приложено.

Откат: все правки — новый код и расширения существующих функций без
удаления прежнего поведения (кроме `check_backup_age`, разбор — выше);
`git revert` коммитов ветки полностью восстанавливает прежнее
поведение, миграция схемы БД не заводится (используется уже
существующая таблица `tasks` для строки пересева, никаких ALTER).

## Риски

- Сканирование истории `main` (`git log --format=%s`) читает ВСЮ
  историю ветки — на пульте с очень длинной историей это разовая
  стоимость одного `init`/первого посева target'а, не постоянная
  (см. «Подход», п.1: платится один раз на target). Если это когда-нибудь
  станет заметно медленным — ограничение глубины (`--max-count`) можно
  добавить отдельной правкой без изменения контракта функции.
- `.claude/CLAUDE.md` референса — текст, а не пустой файл: минимальный,
  но не нулевой риск, что кто-то сочтёт его «инструкцией роли» и станет
  туда дописывать промпт-логику. Разграничение (это НЕ промпт роли, тот
  формирует `runner`+`skills/*.md`) явно проговорено в самом файле и в
  `docs/reference/role-home.md`.
- Синтетическая строка `tasks` для пересеянного расхода видна в
  `catalog.cmd_status`/`cmd_show` как обычная задача — сознательный
  компромисс (переиспользование уже существующего контура `SUM
  (spent_usd)`, не новый параллельный учёт); `id` подобран так, чтобы
  визуально не походить на настоящий `Tnnn` и никогда с ним не
  коллизировать.
