## Требуется

1. **Раздел SPEC «## Заменяемые тесты»** (`guard.REPLACED_TESTS_SECTION`). Пункт — строка `` - `<идентификатор теста компонента>` → AC-<n>: <причина> ``. Форма проверяется там же, где «Меняемое поведение» (общая проверка SPEC и переход `spec_writing -> spec_gate`); нарушение называет строку: идентификатор не в обратных кавычках или не той формы (разбор guard совпадает с `project_profile.parse_test_id` на одном наборе примеров), нет `→ AC-<n>:`, критерия `AC-<n>` нет в «Критерии приёмки», пустая причина, повтор идентификатора. Строка непустого раздела, не начинающаяся с «- », — ошибка формы. Раздела нет, он пуст или несёт шаблонную заглушку — ошибок нет, прежнее поведение.
2. **Утверждение на гейте SPEC.** `approve` на `spec_gate` после сверки «Меняемое поведение» и тем же мягким отказом («approve отклонён», задача остаётся на гейте) проверяет непустой раздел: профиль задачи (`project_profile.for_task`) в границе `in_outcome_bounds`; решение профиля с отказом (`for_task`: несколько компонентов, неразрешённый контекст) — отказ `approve` с причиной решения (как в `mandate._test_id_refusal`); иначе при профиле вне границы отказ «раздел «Заменяемые тесты» действует только у компонента с отчётом; у проекта <проект> — раздел «Меняемое поведение» или мандат Оператора»; компонент каждого идентификатора — компонент профиля задачи; путь — под масками `tests` компонента и есть в голове `main` репозитория задачи (git не ответил — отказ с причиной); матрица неослабления SPEC — `mandate.matrix_refusals(spec_text, [], conn=conn, task_id=task_id, test_ids=<идентификаторы>)` без находок. Прошло — запись журнала `mandate.REPLACED_TESTS_ACTION = "утверждены заменяемые тесты"` со строками раздела как есть и печать «[<id>] утверждены заменяемые тесты:» с ними же. Канареечная задача — ни сверки, ни записи. `approve` на `spec_gate` при пустом или отсутствующем разделе, если у задачи уже есть запись `REPLACED_TESTS_ACTION`, пишет новую запись с пустой деталью (отзыв); `approved_replacements` по ней — пусто. Чтение — `mandate.approved_replacements(conn, task_id) -> dict` {идентификатор: номер критерия} по последней такой записи; записи нет — пусто.
3. **Аудит SPEC.** `spec_audit.signals` дописывает сигнал «а) раздел «Заменяемые тесты» непуст» сразу после строки «а) раздел «Меняемое поведение» непуст»; прочие сигналы и их порядок — прежние.
4. **Сверка на гейте планки.** В `_tests_writing_fail_to_pass_gate` сразу после `_spec_anchor_check`, до построения правила планки: каждый `AC-<n>` из `approved_replacements` обязан входить в множество критериев, покрытых тестом; иначе отказ нового действия `refusal_classes.REPLACEMENT_REFUSAL_ACTION = "переход отклонён: заменяемые тесты"` (класс «чинит роль») с деталью «заменяемый тест <идентификатор> сопоставлен AC-<n>, а у AC-<n> нет теста планки» по строке на нарушение.
5. **Запреты планки (перенос 13).** `_ban_findings` узнаёт шаблонную таблицу: цепочка с `.each`, за которой шаблонный литерал, — аргументы вызова — первая пара скобок после литерала (числовой литерал и объект с ключом `retry`/`timeout` там — находка); литерал имени с меткой `AC-<n>: ` в начале запрещён у `suite` так же, как у `describe`. `_test_calls` узнаёт имя теста шаблонной таблицы так же, как у `.each(…)(…)`. Тексты прочих находок и разбор файлов без метки — прежние.
6. **`amend-tests` для файлов с меткой.** Отказ `LABELLED_REFUSAL` снимается. Отказ любой из проверок ниже — прежними текстами через `_refuse_group_lines` или `_refuse_traceability`, до любой записи; лок не сдвигается. Сбор и прогон в `amend-tests` — прежним путём `acceptance._task_own_profile`; в тестах Vitest заменён подставным объектом, как в существующих классах-песочницах; без Node. Удаление файла планки с меткой — трассируемостью по правилу, как у Python; удаление долгоживущего файла с меткой сверяется по именам тестов `guard.plank_test_names`: имя, которого нет ни в планке, ни в оставшихся долгоживущих файлах, — отказ прежним текстом «удаление снимает методы …». При правиле планки не по умолчанию оба пути команды проверяют файлы с меткой тем же составом, что выход из `tests_writing`: строки группы и запреты текста — по правилу (`guard.group_line_errors_from_files(…, rule)`, `guard.plank_ban_errors`), файлы планки для проверок — `guard.acceptance_test_files(…, rule)`, без условия `plank_has_group_lines`; строки группы — `guard.group_line_errors_from_files(files, rule)`; долгоживущий файл в планке — `guard.long_lived_plank_errors(…, rule=rule)`; запреты — `guard.plank_ban_errors(files, rule)`; долгоживущие файлы с меткой — тем же составом, что `orchestrator/advance_gates/tests_writing.py:500–510`: `guard.long_lived_group_errors(…, profile.long_lived_dir, rule)`, `guard.long_lived_errors_from_files(…, rule=rule)`, `guard.plank_ban_errors(…, rule)` с `rule = project_profile.long_lived_rule(...)`; трассируемость — по правилу, как сейчас. Толкование переноса 7: проверяются все файлы с меткой снимка планки после правки и изменённые долгоживущие файлы с меткой; неизменённый долгоживущий файл не перепроверяется — как у файлов Python. Правило по умолчанию — прежний путь побайтно.
7. **Приложением к PLAN** (коммит Оператора): в `templates/SPEC.md` — раздел «## Заменяемые тесты» после «Меняемое поведение» с формой пункта и правилом «только смена поведения по требованию; ослабление сюда не входит»; в `skills/spec-authoring.md` — правило аналитика: когда тест заменяется, а не меняется («Меняемое поведение» — только Python-тесты артели), строка матрицы неослабления на каждый идентификатор, у компонента без Python-слоя (строгий режим) любая правка существующего файла `tests` или `test_support`, в том числе файла заменяемого теста, требует мандата Оператора на путь файла (маркер «Ослабление тестов разрешено:»), а утверждённая замена снимает только находки «исчез» и «прежняя версия красная» своего теста. Существующие строки обоих файлов не меняются; проверка — гейт применимости приложений PLAN.
