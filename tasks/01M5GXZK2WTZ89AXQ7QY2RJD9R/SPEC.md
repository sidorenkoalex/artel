# SPEC: G3б-1 — заменяемые тесты в SPEC, сверка на гейте планки, запреты планки и amend-tests для файлов с меткой

## Контекст
Первая из трёх частей G3б волны G по ADR-0026 («Решение» п. 7: перечень
заменяемых тестов пишет аналитик в SPEC, строки этого перечня входят в
матрицу неослабления, Оператор утверждает перечень на гейте SPEC,
утверждённая замена служит мандатом, гейт планки сверяет сопоставление
замены с тестом `AC-<n>`). Сейчас у SPEC есть только раздел «Меняемое
поведение» (Python-тесты артели). Шаблонные таблицы `.each` и `suite('AC-1: …')`
обходят запреты планки (перенос 13 из замечаний проверки приёмки G2б-2).
`amend-tests` отказывает файлам планки с меткой `AC-<n>: ` временным
отказом «до G3б» (`orchestrator/amend.py:239`, `LABELLED_REFUSAL`).
Решения Оператора 19.10 и 21.10 оставляют `amend-tests` для файлов с меткой в
этой задаче. Проверку «прежняя версия заменяемого теста красная на коде
ветки» исполняет G3б-2 по журнальной записи, которую заводит эта задача.

Граница задачи: новое поведение появляется только у SPEC с непустым разделом
«## Заменяемые тесты» и у файлов планки с меткой `AC-<n>: `. У артели и у
записи `test_profile` без этого раздела гейт SPEC, гейты `tests_writing` и
`amend-tests` работают побайтно как раньше. Если раздел есть у задачи вне
границы `in_outcome_bounds`, `approve` отказывает: раздел не принимается
молча.

## Требования

1. **Раздел SPEC «## Заменяемые тесты»** (имя — константа
   `guard.REPLACED_TESTS_SECTION`). Пункт — строка
   `` - `<идентификатор теста компонента>` → AC-<n>: <причина> ``. Форма
   проверяется там же, где «Меняемое поведение»: в общей проверке SPEC
   (`scripts/guard.py`, CLI) и на переходе `spec_writing -> spec_gate`.
   Каждое нарушение называет свою строку. Нарушения: идентификатор не в
   обратных кавычках или не той формы (разбор guard совпадает с
   `project_profile.parse_test_id` на одном наборе примеров); нет
   `→ AC-<n>:`; критерия `AC-<n>` нет в разделе «Критерии приёмки»; пустая
   причина; повтор идентификатора; строка непустого раздела не начинается с
   «- ». Если раздела нет, он пуст или несёт шаблонную заглушку, ошибок нет
   и поведение прежнее.
2. **Утверждение на гейте SPEC.** `approve` на `spec_gate` проверяет
   непустой раздел после сверки «Меняемое поведение». Отказ тот же мягкий,
   что у этой сверки: «approve отклонён», задача остаётся на гейте.
   Проверки по порядку:
   - профиль задачи (`project_profile.for_task`) в границе `in_outcome_bounds`;
   - решение профиля с отказом (несколько компонентов, неразрешённый
     контекст) — отказ `approve` с причиной решения, как в
     `mandate._test_id_refusal`;
   - профиль вне границы — отказ «раздел «Заменяемые тесты» действует только
     у компонента с отчётом; у проекта <проект> — раздел «Меняемое поведение»
     или мандат Оператора»;
   - компонент каждого идентификатора — компонент профиля задачи;
   - путь лежит под масками `tests` компонента и есть в голове `main`
     репозитория задачи; если git не ответил — отказ с причиной;
   - матрица неослабления SPEC без находок по вызову
     `mandate.matrix_refusals(spec_text, [], conn=conn, task_id=task_id, test_ids=<идентификаторы>)`.

   Если все проверки прошли: журнал получает запись с действием
   `mandate.REPLACED_TESTS_ACTION = "утверждены заменяемые тесты"`, деталь —
   строки раздела как есть; печатается «[<id>] утверждены заменяемые тесты:» с
   теми же строками. У канареечной задачи нет ни сверки, ни записи. Если
   раздел пуст или отсутствует, а у задачи уже есть запись
   `REPLACED_TESTS_ACTION`, `approve` на `spec_gate` пишет новую запись с
   пустой деталью (отзыв). Чтение —
   `mandate.approved_replacements(conn, task_id) -> dict`
   {идентификатор: номер критерия} по последней такой записи. Если записи нет
   или последняя запись — отзыв, результат пуст. Правка раздела после
   `approve` на `approved_replacements` не влияет.
3. **Аудит SPEC.** `spec_audit.signals` выдаёт сигнал «а) раздел
   «Заменяемые тесты» непуст» сразу после строки «а) раздел «Меняемое
   поведение» непуст». Прочие сигналы и их порядок прежние.
4. **Сверка на гейте планки.** В `_tests_writing_fail_to_pass_gate` сразу
   после `_spec_anchor_check` и до построения правила планки: каждый
   `AC-<n>` из `approved_replacements` обязан входить в множество критериев,
   покрытых тестом. Иначе — отказ нового действия
   `refusal_classes.REPLACEMENT_REFUSAL_ACTION = "переход отклонён: заменяемые тесты"`
   с классом «чинит роль». Деталь — по строке на нарушение: «заменяемый тест
   <идентификатор> сопоставлен AC-<n>, а у AC-<n> нет теста планки».
5. **Запреты планки (перенос 13).**
   - `_ban_findings` узнаёт шаблонную таблицу: цепочку с `.each`, за которой
     идёт шаблонный литерал. Аргументы вызова — первая пара скобок после
     литерала. Числовой литерал или объект с ключом `retry`/`timeout` в этих
     скобках — находка.
   - Литерал имени с меткой `AC-<n>: ` в начале запрещён у `suite` так же,
     как у `describe`.
   - `_test_calls` узнаёт имя теста шаблонной таблицы так же, как у
     `.each(…)(…)`.
   - Тексты прочих находок и разбор файлов без метки прежние.
6. **`amend-tests` для файлов с меткой.** Отказ `LABELLED_REFUSAL`
   снимается.
   - Отказ любой из проверок ниже выдаётся прежними текстами через
     `_refuse_group_lines` или `_refuse_traceability` до любой записи; лок не
     сдвигается. Сбор и прогон идут прежним путём
     `acceptance._task_own_profile`.
   - Удаление файла планки с меткой проверяется трассируемостью по правилу,
     как у Python. Удаление долгоживущего файла с меткой сверяется по именам
     тестов `guard.plank_test_names`: если имени нет ни в планке, ни в
     оставшихся долгоживущих файлах, — отказ прежним текстом «удаление
     снимает методы …».
   - При правиле планки не по умолчанию оба пути команды (рабочая копия и
     `--from-branch`) проверяют файлы с меткой тем же составом, что выход из
     `tests_writing`:
     - файлы планки для проверок — `guard.acceptance_test_files(…, rule)`,
       без условия `plank_has_group_lines`;
     - строки группы — `guard.group_line_errors_from_files(files, rule)`;
     - долгоживущий файл в планке — `guard.long_lived_plank_errors(…, rule=rule)`;
     - запреты — `guard.plank_ban_errors(files, rule)`;
     - долгоживущие файлы с меткой — тем же составом, что
       `orchestrator/advance_gates/tests_writing.py:500–510`:
       `guard.long_lived_group_errors(…, profile.long_lived_dir, rule)`,
       `guard.long_lived_errors_from_files(…, rule=rule)`,
       `guard.plank_ban_errors(…, rule)` с
       `rule = project_profile.long_lived_rule(...)`;
     - трассируемость — по правилу, как сейчас.
   - Объём проверки (перенос 7): все файлы с меткой снимка планки после
     правки и изменённые долгоживущие файлы с меткой. Неизменённый
     долгоживущий файл не перепроверяется, как у файлов Python.
   - При правиле по умолчанию путь прежний побайтно.
7. **Приложение к PLAN** (защищённые пути, коммит Оператора).
   - `templates/SPEC.md`: раздел «## Заменяемые тесты» после «Меняемое
     поведение» с формой пункта и правилом «только смена поведения по
     требованию; ослабление сюда не входит».
   - `skills/spec-authoring.md`: правило аналитика. Когда тест заменяется, а
     не меняется («Меняемое поведение» — только Python-тесты артели). На
     каждый идентификатор — строка матрицы неослабления. У компонента без
     Python-слоя (строгий режим) любая правка существующего файла `tests`
     или `test_support`, в том числе файла заменяемого теста, требует
     мандата Оператора на путь файла (маркер «Ослабление тестов
     разрешено:»). Утверждённая замена снимает только находки «исчез» и
     «прежняя версия красная» своего теста.
   - Существующие строки обоих файлов не меняются. Применимость проверяет
     гейт применимости приложений PLAN.
8. **Тесты.** Детерминированные, без сети и без Node. В `amend-tests` прогон
   Vitest (`acceptance._task_own_profile`) заменён подставным объектом, как в
   существующих классах-песочницах. Существующие тесты, которые закрепляют
   временный отказ `LABELLED_REFUSAL`, переписываются на новое ожидание (не
   удаляются) только по мандату Оператора — строкой ANSWER на гейте SPEC с
   матрицей неослабления:
   - `tests/test_01m5aa5ts90rdj2afxb882wtpd_labelled_gates.py::Ac11AmendLabelledRefusalTest::test_ac11_worktree_mode_refuses_labelled_files`;
   - `tests/test_01m5aa5ts90rdj2afxb882wtpd_labelled_gates.py::Ac11AmendLabelledRefusalTest::test_ac11_from_branch_mode_refuses_labelled_files`;
   - константа `AMEND_REFUSAL` того же файла (строка 1371);
   - `tests/test_01m5aqh8m2dkbv30nby86j34a7_fail_to_pass.py::Ac25AmendAndTemplateTest::test_ac25_amend_md_only_plank_labelled_long_lived_refused`;
   - константа `AMEND_REFUSAL` того же файла (строка 2362).

   Свойство «файлы с меткой не обходят проверки через `amend-tests`» покрывают
   новые тесты требования 6. Прочие существующие тесты не правятся.

Ограничение зон по смыслу: в `orchestrator/fsm.py` правятся только
`_approve_spec_gate` и новая функция сверки раздела рядом с
`_behavior_change_declaration`; в `orchestrator/advance_gates/tests_writing.py`
— только `_tests_writing_fail_to_pass_gate`. Подписи функций, которые зовут
другие модули (`parse_test_id`, `for_task`, `signals`, `_approve_spec_gate`,
`plank_ban_errors`, `scan_ac_content`, `plank_test_names`, общая проверка
SPEC, `matrix_refusals`, гейты `tests_writing`), не меняются.

## Критерии приёмки

AC-1. Каждое нарушение формы раздела «## Заменяемые тесты» даёт ошибку guard с указанием строки и в CLI, и на переходе `spec_writing -> spec_gate`: идентификатор не в обратных кавычках; идентификатор не той формы; нет `→ AC-<n>:`; критерия `AC-<n>` нет в «Критерии приёмки»; пустая причина; повтор идентификатора; строка непустого раздела не начинается с «- ».

AC-2. На одном наборе примеров (годных и негодных) разбор идентификатора в guard и `project_profile.parse_test_id` дают одинаковый исход: принят или отвергнут.

AC-3. SPEC без раздела «## Заменяемые тесты», с пустым разделом или с шаблонной заглушкой не получает от guard ни одной новой ошибки.

AC-4. В каждом из случаев ниже `approve` на `spec_gate` для SPEC с непустым разделом отказывает мягким отказом «approve отклонён», задача остаётся в `spec_gate`, записи `REPLACED_TESTS_ACTION` нет:
- профиль вне границы `in_outcome_bounds`: артель, запись `test_profile`, компонент без `report`; отказ несёт текст «раздел «Заменяемые тесты» действует только у компонента с отчётом; у проекта <проект> — раздел «Меняемое поведение» или мандат Оператора»;
- решение профиля с отказом; отказ несёт причину решения.

AC-5. В каждом из случаев ниже `approve` отказывает мягко, задача остаётся в `spec_gate`: компонент идентификатора не совпадает с компонентом профиля; путь вне масок `tests` компонента; файла нет в голове `main` репозитория задачи; git не ответил (отказ с причиной); в матрице неослабления SPEC идентификатор не назван (`mandate.matrix_refusals` с `test_ids` даёт находку).

AC-6. `approve` на `spec_gate` с годным разделом пишет запись журнала `"утверждены заменяемые тесты"` (`mandate.REPLACED_TESTS_ACTION`) со строками раздела как есть и печатает «[<id>] утверждены заменяемые тесты:» с теми же строками. `mandate.approved_replacements(conn, task_id)` возвращает {идентификатор: номер критерия}.

AC-7. Правка раздела в SPEC.md после `approve` не меняет результат `approved_replacements`. У задачи без записи результат пуст.

AC-8. Повторный `approve` на `spec_gate` без раздела (или с пустым разделом) после `approve` с разделом пишет запись `REPLACED_TESTS_ACTION` с пустой деталью, после чего `approved_replacements` пуст.

AC-9. У канареечной задачи `approve` на `spec_gate` не сверяет раздел и не пишет запись `REPLACED_TESTS_ACTION`.

AC-10. `spec_audit.signals` для SPEC с непустым разделом «Заменяемые тесты» выдаёт сигнал «а) раздел «Заменяемые тесты» непуст» сразу после «а) раздел «Меняемое поведение» непуст». Для SPEC без раздела список сигналов и их порядок прежние.

AC-11. Если критерий `AC-<n>` из `approved_replacements` не входит в множество покрытых тестом критериев, выход из `tests_writing` (`_tests_writing_fail_to_pass_gate`) отказывает действием `"переход отклонён: заменяемые тесты"` (`refusal_classes.REPLACEMENT_REFUSAL_ACTION`). Деталь: «заменяемый тест <идентификатор> сопоставлен AC-<n>, а у AC-<n> нет теста планки» по строке на нарушение. `refusal_classes.refusal_class` относит действие к классу «чинит роль».

AC-12. `plank_ban_errors` даёт находку на файл с меткой, где шаблонная таблица `` it.each`…` `` вызывается с числовым литералом `5000` в первой паре скобок после литерала, и на такую же таблицу с объектом `{ timeout: 1 }`.

AC-13. `plank_ban_errors` даёт находку на `suite('AC-1: …')` так же, как на `describe('AC-1: …')`.

AC-14. Имя теста шаблонной таблицы `` it.each`…`('AC-1: …', …) `` попадает в трассируемость (`_test_calls`) так же, как имя у `.each(…)(…)`: критерий `AC-1` получает тест.

AC-15. Тексты прежних находок запретов и разбор файлов без метки не меняются: существующие тесты запретов и трассируемости зелёные без правок.

AC-16. `amend-tests` в обоих путях (рабочая копия и `--from-branch`) при правиле планки не по умолчанию принимает годный файл планки с меткой и сдвигает лок. Отказа `LABELLED_REFUSAL` больше нет.

AC-17. `amend-tests` в обоих путях отказывает прежним текстом `_refuse_group_lines`/`_refuse_traceability` до любой записи и без сдвига лока в каждом из случаев: файл с меткой с запретом; файл с меткой без строки группы; нарушенная трассируемость; долгоживущий файл с меткой и запретом; долгоживущий файл с меткой без строки группы.

AC-18. `amend-tests` отказывает текстом «удаление снимает методы …» без сдвига лока, если удаляется долгоживущий файл с меткой, чей тест есть только в нём, даже когда трассируемость критерия держит другой тест.

AC-19. `amend-tests` в обоих путях принимает годный изменённый долгоживущий файл с меткой.

AC-20. У артели и у записи `test_profile` на SPEC без раздела «Заменяемые тесты» вывод `approve` на `spec_gate`, гейтов выхода из `tests_writing` и `amend-tests` (правило по умолчанию) побайтно совпадает с прежним.

AC-21. Методы `Ac11AmendLabelledRefusalTest::test_ac11_worktree_mode_refuses_labelled_files`, `Ac11AmendLabelledRefusalTest::test_ac11_from_branch_mode_refuses_labelled_files` (`tests/test_01m5aa5ts90rdj2afxb882wtpd_labelled_gates.py`) и `Ac25AmendAndTemplateTest::test_ac25_amend_md_only_plank_labelled_long_lived_refused` (`tests/test_01m5aqh8m2dkbv30nby86j34a7_fail_to_pass.py`) остаются в наборе и проверяют новое ожидание, а не отказ `LABELLED_REFUSAL`.

AC-22. Приложение к PLAN для `templates/SPEC.md` добавляет раздел «## Заменяемые тесты» после «Меняемое поведение» с формой пункта и правилом «только смена поведения по требованию; ослабление сюда не входит». Приложение для `skills/spec-authoring.md` добавляет правило требования 7. Ни одна существующая строка обоих файлов не удалена и не изменена.

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (7 файлов кода
и `tests/`); число критериев приёмки (22).

Прогноз диффа: 100 КиБ. Код — около 40 КиБ (guard: раздел и запреты; fsm:
сверка на гейте; amend: проверки файлов с меткой). Тесты — около 55 КиБ.
Приложения к PLAN — около 5 КиБ. Это ниже половины потолка гейта ёмкости
(128 КиБ).

**Обоснование монолита (материал для решения Оператора).**
- Границу этой задачи уже провёл Оператор 21.10, когда делил G3б на три
  задачи, и тогда же оставил `amend-tests` для файлов с меткой здесь.
- Требование 6 зависит от требования 5: `amend-tests` проверяет файлы с
  меткой через `guard.plank_ban_errors`, и случай «файл с запретом»
  (AC-17) должен ловить и шаблонную таблицу. Если вынести запреты
  отдельно, `amend-tests` либо снимет `LABELLED_REFUSAL` с дырой в
  запретах, либо будет ждать этой части.
- Требования 1–4 — одна цепочка: раздел, затем утверждение, затем
  `approved_replacements`, затем сверка на гейте планки. Без записи журнала
  сверка гейта планки не имеет входа, без сверки запись не действует.
