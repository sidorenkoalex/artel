# SPEC: G3б-1 — заменяемые тесты в SPEC, сверка на гейте планки, запреты планки и amend-tests для файлов с меткой

## Контекст
Первая из трёх частей G3б волны G по ADR-0026 («Решение» п. 7: перечень
заменяемых тестов пишет аналитик в SPEC, строки этого перечня входят в
матрицу неослабления, Оператор утверждает перечень на гейте SPEC,
утверждённая замена служит мандатом, гейт планки сверяет сопоставление
замены с тестом `AC-<n>`). Сейчас у SPEC есть только раздел «Меняемое
поведение» (Python-тесты артели). Шаблонные таблицы `.each` и `suite('AC-1: …')`
обходят запреты планки (перенос 13 из замечаний проверки приёмки G2б-2).
`amend-tests` отказывает файлам планки с меткой `AC-<n>: ` временным
отказом «до G3б» (`orchestrator/amend.py:239`, `LABELLED_REFUSAL`).
Решения Оператора 19.10 и 21.10 оставляют `amend-tests` для файлов с меткой в
этой задаче. Проверку «прежняя версия заменяемого теста красная на коде
ветки» исполняет G3б-2 по журнальной записи, которую заводит эта задача.

Граница задачи: новое поведение появляется только у SPEC с непустым разделом
«## Заменяемые тесты» и у файлов планки с меткой `AC-<n>: `. У артели и у
записи `test_profile` без этого раздела гейт SPEC, гейты `tests_writing` и
`amend-tests` работают побайтно как раньше. Если раздел есть у задачи вне
границы `in_outcome_bounds`, `approve` отказывает: раздел не принимается
молча.

## Требования

1. **Раздел SPEC «## Заменяемые тесты»** (имя — константа
   `guard.REPLACED_TESTS_SECTION`). Пункт — строка
   `` - `<идентификатор теста компонента>` → AC-<n>: <причина> ``. Форма
   проверяется там же, где «Меняемое поведение»: в общей проверке SPEC
   (`scripts/guard.py`, CLI) и на переходе `spec_writing -> spec_gate`.
   Каждое нарушение называет свою строку. Нарушения: идентификатор не в
   обратных кавычках или не той формы (разбор guard совпадает с
   `project_profile.parse_test_id` на одном наборе примеров); нет
   `→ AC-<n>:`; критерия `AC-<n>` нет в разделе «Критерии приёмки»; пустая
   причина; повтор идентификатора; строка непустого раздела не начинается с
   «- ». Если раздела нет, он пуст или несёт шаблонную заглушку, ошибок нет
   и поведение прежнее.
2. **Утверждение на гейте SPEC.** `approve` на `spec_gate` сверяет непустой
   раздел сразу после сверки «Меняемое поведение» и до записи «объявлена
   смена поведения тестов» (`orchestrator/fsm.py:1207`). Записи
   `DECLARED_CHANGE_ACTION` и `REPLACED_TESTS_ACTION` (включая отзыв)
   пишутся только после того, как прошли обе сверки, в порядке: сначала
   DECLARED (как сейчас), затем `REPLACED_TESTS_ACTION`; отклонённый
   `approve` не оставляет ни одной из них. Отказ тот же мягкий, что у сверки
   «Меняемое поведение»: «approve отклонён», задача остаётся на гейте.
   Текст SPEC — тот же источник, что у сверки «Меняемое поведение»
   (`spec_text if foreign else _disk_spec_text(task_id)`, `fsm.py:1202`:
   ветка документов либо диск).
   Проверки по порядку:
   - форма раздела — той же функцией guard, что в общей проверке SPEC
     (требование 1); нарушения — мягкий отказ с текстами guard, как у
     `_behavior_change_declaration` (`fsm.py:1056–1058`);
   - профиль задачи (`project_profile.for_task`) в границе `in_outcome_bounds`;
   - решение профиля с отказом (несколько компонентов, неразрешённый
     контекст) — отказ `approve` с причиной решения, как в
     `mandate._test_id_refusal`;
   - профиль вне границы, в том числе решение `skip` (у проекта нет профиля
     тестов, `project_profile.py:208`; так же, как `_outcome_profile`,
     `mandate.py:257–265`, `:283–287`), — отказ «раздел «Заменяемые тесты»
     действует только у компонента с отчётом; у проекта <проект> — раздел
     «Меняемое поведение» или мандат Оператора»;
   - компонент каждого идентификатора — компонент профиля задачи;
   - путь лежит под масками `tests` компонента и есть в голове `main`
     репозитория задачи; если git не ответил — отказ с причиной;
   - матрица неослабления SPEC без находок по вызову
     `mandate.matrix_refusals(spec_text, [], conn=conn, task_id=task_id, test_ids=<идентификаторы>)`.

   Если все проверки прошли: журнал получает запись с действием
   `mandate.REPLACED_TESTS_ACTION = "утверждены заменяемые тесты"`, деталь —
   строки пунктов, разобранные функцией формы guard, по одной на пункт;
   печатается «[<id>] утверждены заменяемые тесты:» с теми же строками.
   `approved_replacements` разбирает деталь тем же разбором строки пункта. У канареечной задачи нет ни сверки, ни записи. Если
   раздел пуст или отсутствует, а у задачи уже есть запись
   `REPLACED_TESTS_ACTION`, `approve` на `spec_gate` пишет новую запись с
   пустой деталью (отзыв). Чтение —
   `mandate.approved_replacements(conn, task_id) -> dict`
   {идентификатор: номер критерия} по последней такой записи. Если записи нет
   или последняя запись — отзыв, результат пуст. Правка раздела после
   `approve` на `approved_replacements` не влияет.

## Критерии приёмки

AC-1. Каждое нарушение формы раздела «## Заменяемые тесты» даёт ошибку guard с указанием строки и в CLI, и на переходе `spec_writing -> spec_gate`: идентификатор не в обратных кавычках; идентификатор не той формы; нет `→ AC-<n>:`; критерия `AC-<n>` нет в «Критерии приёмки»; пустая причина; повтор идентификатора; строка непустого раздела не начинается с «- ».

AC-2. На одном наборе примеров (годных и негодных) разбор идентификатора в guard и `project_profile.parse_test_id` дают одинаковый исход: принят или отвергнут.

AC-3. SPEC без раздела «## Заменяемые тесты», с пустым разделом или с шаблонной заглушкой не получает от guard ни одной новой ошибки.

AC-4. В каждом из случаев ниже `approve` на `spec_gate` для SPEC с непустым разделом отказывает мягким отказом «approve отклонён», задача остаётся в `spec_gate`, записи `REPLACED_TESTS_ACTION` нет:
- профиль вне границы `in_outcome_bounds`: артель, запись `test_profile`, компонент без `report`, проект без профиля тестов (решение `skip`); отказ несёт текст «раздел «Заменяемые тесты» действует только у компонента с отчётом; у проекта <проект> — раздел «Меняемое поведение» или мандат Оператора»;
- решение профиля с отказом; отказ несёт причину решения.

AC-5. В каждом из случаев ниже `approve` отказывает мягко, задача остаётся в `spec_gate`: компонент идентификатора не совпадает с компонентом профиля; путь вне масок `tests` компонента; файла нет в голове `main` репозитория задачи; git не ответил (отказ с причиной); в матрице неослабления SPEC идентификатор не назван (`mandate.matrix_refusals` с `test_ids` даёт находку).

AC-6. `approve` на `spec_gate` с годным разделом пишет запись журнала `"утверждены заменяемые тесты"` (`mandate.REPLACED_TESTS_ACTION`) с деталью из строк пунктов раздела, разобранных функцией формы guard, по одной на пункт, и печатает «[<id>] утверждены заменяемые тесты:» с теми же строками. `mandate.approved_replacements(conn, task_id)` возвращает {идентификатор: номер критерия}.

AC-7. Правка раздела в SPEC.md после `approve` не меняет результат `approved_replacements`. У задачи без записи результат пуст.

AC-8. Повторный `approve` на `spec_gate` без раздела (или с пустым разделом) после `approve` с разделом пишет запись `REPLACED_TESTS_ACTION` с пустой деталью, после чего `approved_replacements` пуст.

AC-10. `spec_audit.signals` для SPEC с непустым разделом «Заменяемые тесты» выдаёт сигнал «а) раздел «Заменяемые тесты» непуст» сразу после «а) раздел «Меняемое поведение» непуст». ## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (7 файлов кода
и `tests/`); число критериев приёмки (25).

Прогноз диффа: 110 КиБ. Код — около 45 КиБ (guard: раздел, запреты, общий
предикат файла с меткой; fsm: сверка на гейте; amend: проверки файлов с
меткой в обоих путях). Тесты — около 60 КиБ.
Приложения к PLAN — около 5 КиБ. Это ниже половины потолка гейта ёмкости
(128 КиБ).

**Обоснование монолита (материал для решения Оператора).**
- Границу этой задачи уже провёл Оператор 21.10, когда делил G3б на три
  задачи, и тогда же оставил `amend-tests` для файлов с меткой здесь.
- Требование 6 зависит от требования 5: `amend-tests` проверяет файлы с
  меткой через `guard.plank_ban_errors`, и случай «файл с запретом»
  (AC-17) должен ловить и шаблонную таблицу. Если вынести запреты
  отдельно, `amend-tests` либо снимет `LABELLED_REFUSAL` с дырой в
  запретах, либо будет ждать этой части.
- Требования 1–4 — одна цепочка: раздел, затем утверждение, затем
  `approved_replacements`, затем сверка на гейте планки. Без записи журнала
  сверка гейта планки не имеет входа, без сверки запись не действует.
- Приложение к PLAN (требование 7) описывает раздел и строгий режим разом.
  Его деление дало бы два коммита Оператора в защищённые пути по одной теме.
- Задача ускорения набора стоит в очереди после слияния G3б-1, потому что
  правит тот же файл тестов. Деление удлинит эту очередь.

Технически отделима пара «требования 1–4» и «требования 5–6 + правка
существующих тестов»: каждая часть мержима отдельно с зелёной планкой, у
каждой — свой кусок зоны (`fsm.py`/`mandate.py`/`spec_audit.py`/`tests_writing.py`
и `amend.py`; `guard.py` — общий). Если Оператор решит делить, нарезка такая,
первой — 5–6.
