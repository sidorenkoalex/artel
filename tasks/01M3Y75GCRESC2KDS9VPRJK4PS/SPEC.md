# SPEC: pin-update называет живые циклы auto/run, запущенные на старом коде

## Контекст
`orchestrator/pin.py::cmd_pin_update` (строки 50–76 на 28b09389) делает
fetch, сверку канарейки (ADR-0013), `git merge --ff-only` и пишет журнал
«pin обновлён» (`config.PIN_UPDATE_JOURNAL_TASK_ID`). О живых циклах
`auto`/`run` команда не сообщает. Отвязанный цикл — отдельный процесс
Python (`orchestrator/artel.py::_launch_detached`), который загрузил
модули пульта при старте и после сдвига пина исполняет прежний код до
своего завершения. Ожидание зоны может длиться до
`config.ZONE_WAIT_MAX_SEC` = 6 ч. 02.10 из-за этого задача
01M3XTF5506GF43HD51ECE230T дважды эскалировала. Процесс pid 2063 стартовал
до мержа исправления 01M3XTF1CEBXT4J7P0EKG5J342 и до пина 393172e4.
Цикл 01M3SF7DPF… ждал зону на старом коде. Оба цикла Оператор
перезапустил вручную (`stop` + `auto`).

Живые циклы видны по lease: `store.all_leases` → task_id, pid, hostname,
heartbeat_ts. pid в lease — это pid процесса цикла, потому что lease
берёт `lease.run_locked` внутри спавненного процесса. Аргументы
наблюдения отвязанного запуска лежат в `observed_runs` (task_id, pid,
observation_id) и в `observations` (client, chat).

## Требования
1. После успешного сдвига пина (`git merge --ff-only` прошёл) `pin-update`
   печатает и пишет в журнал перечень циклов `auto`/`run`, которые
   одновременно:
   - живы на этой машине: lease с `hostname` этой машины и живым pid;
   - стартовали раньше сдвига пина.

   Журнал — запись «pin обновлён» либо отдельная запись рядом с ней.
   Для каждого цикла указываются id задачи, pid, время старта процесса,
   текущее состояние задачи и готовые команды перезапуска: сначала
   `stop <id>`, затем `auto <id>`. Если цикл был под наблюдением, команда
   `auto` получает его аргументы `--client <client> --chat <chat>`.
   Признак наблюдения: для этих task_id и pid есть строка `observed_runs`,
   а `client`/`chat` берутся из связанной строки `observations`.
2. `pin-update` не останавливает и не перезапускает циклы и не шлёт
   сигналов их процессам. Решение остаётся за Оператором.
3. `doctor` получает проверку «циклы на коде старше пина». Она выдаёт
   предупреждение с тем же перечнем, что и требование 1, пока такие
   процессы живы. Момент пина для неё — время последней записи журнала
   «pin обновлён». Когда таких циклов нет, проверка не предупреждает.
4. Время старта процесса берётся из системных сведений о процессе по
   pid: время старта процесса в таблице процессов ОС, например
   `ps -o lstart= -p <pid>`. Обоснование выбора:
   - запись журнала «auto старт» (`orchestrator/auto.py:1062`) не несёт
     pid, поэтому её нельзя надёжно связать с процессом из lease, если у
     задачи было несколько запусков;
   - `observed_runs.started_at` есть только у отвязанных запусков под
     наблюдением и пишется родителем при спавне, а не самим процессом;
   - время старта процесса ОС — ровно тот момент, когда процесс загрузил
     модули пульта. Его можно получить для любого живого pid этой машины.

   Если время старта определить не удалось (ошибка вызова, пустой или
   неразборчивый ответ), цикл всё равно попадает в перечень с пометкой
   «не удалось определить» вместо времени. Такая ошибка не молчит и не
   приводит к отказу `pin-update`.
5. Тесты — в новом файле `tests/test_pin_update_stale_cycles.py`. Каждый
   тест несёт строку «Ловит мутацию: …».

## Критерии приёмки
AC-1. После успешного `pin-update` цикл с lease этой машины и живым pid,
чей процесс стартовал раньше сдвига, назван в выводе и в журнале. Указаны
id задачи, pid, время старта, состояние задачи и команды `stop <id>` и
`auto <id>`.

AC-2. Цикл под наблюдением (есть строка `observed_runs` для его task_id и
pid) получает команду `auto <id> --client <client> --chat <chat>` со
значениями из связанной строки `observations`. Цикл без наблюдения
получает `auto <id>` без этих аргументов.

AC-3. Цикл, чей процесс стартовал после сдвига пина, в перечне
`pin-update` не назван.

AC-4. Lease с мёртвым pid в перечне `pin-update` не назван.

AC-5. Если время старта процесса определить не удалось, цикл назван с
пометкой «не удалось определить», а `pin-update` завершается успешно:
пин сдвинут, запись «pin обновлён» сделана.

AC-6. `pin-update` не шлёт сигналов процессам циклов: ни
`os.kill`/`os.killpg`, ни `liveness.terminate_process_group` не
вызываются.

AC-7. `doctor` выдаёт предупреждение «циклы на коде старше пина» с тем же
перечнем, что в AC-1, когда живой цикл этой машины стартовал раньше
последней записи «pin обновлён». Если такого цикла нет, предупреждения
нет.

## Оценка объёма и деление
Прогноз диффа: 20 КиБ. Это намного ниже половины потолка гейта ёмкости:
`REVIEW_SNAPSHOT_DIFF_MAX_BYTES` = 256 КиБ.

Сработал сигнал «число затрагиваемых модулей/файлов». Зона
`orchestrator/doctor/` задана каталогом, и guard считает её по числу
файлов внутри. Фактически задача меняет около 4 файлов:
- `orchestrator/pin.py`;
- новая проверка в `orchestrator/doctor/` и её регистрация в
  `orchestrator/doctor/cli.py` или `orchestrator/doctor/__init__.py`;
- новый тестовый файл;
- карта кодовой базы.

Обоснование монолита: AC-7 требует от проверки `doctor` ровно «тот же
перечень», что печатает `pin-update` (AC-1, AC-2). Отбор живых циклов,
время старта и команды перезапуска — одна механика, на которую опираются
обе точки вывода. Подзадача только с `doctor` или только с `pin-update`
либо дублирует отбор, либо оставляет вторую точку без перечня. Объём при
этом мал: 7 критериев, бюджет на планке $25.
