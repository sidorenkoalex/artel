# SPEC: Инварианты системы как неослабляемые тесты

## Контекст
Принцип целостности (ADR-0002) запрещает ослаблять защиты, но сами
системные инварианты существуют как текст в README/design.md и
проверяются только суждением ревьювера. Инвариант, закодированный
тестом, ловится CI механически. Часть инвариантов уже покрыта тестами
де-факто (свежесть вердикта — T004, ретраи — T006, уборка — T008),
но они не собраны, не помечены как неослабляемые и есть дыры.

## Требования
1. Провести инвентаризацию системных инвариантов оркестратора
   и оформить её в PLAN.md: какие уже покрыты тестами (и какими),
   какие кодируемы, но не покрыты, какие тестом не выражаются
   (остаются на ревью). Источники: README «Инварианты», design.md §4/§6,
   CLAUDE.md.
2. Непокрытые кодируемые инварианты закрыть тестами в отдельном модуле
   `tests/test_invariants.py`. Минимальный обязательный набор:
   - merge выполняется только из состояния merge_gate (никакой другой
     путь не приводит к git merge);
   - переход review → acceptance невозможен без свежего вердикта
     (интеграционно, поверх существующих юнитов fresh_verdict);
   - исчерпанный бюджет блокирует запуск агента и не обходится
     через advance/approve;
   - счётчики итераций не сбрасываются ни одним переходом
     (включая эскалацию и возврат из неё);
   - kill не изменяет main и не удаляет содержимое, попавшее в main;
   - ручные гейты (spec_gate, acceptance, merge_gate) не проходят
     ни одной командой, кроме approve/reject Оператора.
3. Пометить инварианты как неослабляемые: маркер в коде тестов
   (комментарий-шапка с ссылкой на ADR-0002 в test_invariants.py
   и в существующих тестах-инвариантах) + перечень в docs — файл
   `docs/invariants.md` со списком «инвариант → тест(ы) → откуда».
4. Существующие тесты не переписываются и не переносятся — только
   помечаются; новые тесты не дублируют существующие юниты, а
   закрывают дыры.
5. CI: protected-paths дополняется предупреждением при изменении
   `tests/test_invariants.py` и `docs/invariants.md` (той же warning-
   логикой, что для конфигов системы; fail — после разделения токенов).

## Критерии приёмки
1. `docs/invariants.md` существует: каждый инвариант со ссылкой на
   тест(ы) либо с пометкой «на ревью» и почему не кодируем.
2. `tests/test_invariants.py` покрывает минимум шесть инвариантов
   из требования 2, все зелёные.
3. Умышленная поломка любого из шести (мысленный мутационный тест —
   описать в PLAN, как проверялось) валит соответствующий тест.
4. `python3 -m unittest discover -s tests` зелёный, guard и CI зелёные.

## Не входит
- Изменение поведения оркестратора (если тест выявит расхождение
  поведения с инвариантом — это эскалация, не молчаливый фикс).
- Policy-движок gates.yaml, команда auto.
- Перенос/рефакторинг существующих тестов.
