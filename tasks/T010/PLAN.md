# PLAN: Инварианты системы как неослабляемые тесты

## Подход

Инварианты сегодня существуют как текст (README «Инварианты»,
docs/design.md §2/§4/§6, ADR-0002) и как побочный эффект тестов задач
T004–T008: свежесть вердикта, ретраи, бюджет и уборка проверяются, но
никто не называет эти тесты защитами, и часть инвариантов не проверяется
ничем. Задача — не менять поведение оркестратора, а сделать текстовые
инварианты механически ловимыми и явно неослабляемыми.

Ключевые решения:

- **Новый модуль `tests/test_invariants.py`, существующие тесты не
  трогаем по существу.** Требование 4 прямо запрещает перенос; и по делу:
  тесты T004–T008 проверяют поведение своих задач в деталях, а модуль
  инвариантов — утверждения о системе целиком («X невозможен ни одной
  командой»). Это разные уровни, слить их значило бы потерять оба.
  Существующие модули получают только шапку-маркер в docstring.
- **Инвариант формулируется как отрицание по всему пространству команд,
  а не как проверка одной ветки кода.** Отсюда форма тестов: цикл по всем
  девяти состояниям FSM × всем командам CLI с утверждением «merge не
  случился», «агент не запущен», «гейт не пройден». Тест на одну ветку
  (`approve` из merge_gate мержит) ловит поломку этой ветки; цикл ловит
  ещё и новый обходной путь, которого сегодня нет — а инвариант именно
  об этом.
- **К каждому запрету — контрольный тест, что защищаемое действие вообще
  возможно.** «merge не случился» зелен и в системе, где merge удалён
  совсем; поэтому рядом `test_merge_gate_approve_is_that_path`,
  `test_only_the_operator_ceiling_unblocks_the_run`,
  `test_operator_approve_passes_each_gate`. Без контроля запретительный
  тест деградирует молча.
- **`subprocess.run` подменён на весь класс FSM-тестов.** Тесты выясняют,
  при каких условиях оркестратор зовёт git, — значит настоящий git им
  не нужен и запрещён: `cmd_approve` в merge_gate работает с `cwd=ROOT`,
  то есть с рабочим репозиторием. Шпион запоминает команду и не исполняет
  её. Тест уборки (`KillKeepsMainIntactTest`) — исключение: там нужны
  реальные ответы git, поэтому ROOT уводится во временный репозиторий,
  как в tests/test_kill_cleanup.py.
- **Интеграционный тест свежести вердикта идёт от `spec_writing`.**
  Юниты `fresh_verdict_iteration` уже есть (T004) — дублировать их нечем;
  дыра была в другом: что вердикт нельзя обойти *другой командой*
  и что возврат из escalated не делает старый вердикт свежим.
- **Маркер неослабляемости — шапка в docstring модуля, не декоратор.**
  Декоратор пришлось бы импортировать из общего модуля тестов, то есть
  трогать существующие тесты по существу (требование 4). Шапка видна
  и тому, кто открыл файл, и `grep -r НЕОСЛАБЛЯЕМЫЕ tests/`.
- **`docs/invariants.md` — реестр, а не пересказ.** Каждая строка ведёт
  на конкретный класс/метод теста; инварианты, тестом не выразимые,
  перечислены со своей причиной, чтобы «не покрыт» и «непокрываем»
  не смешивались.

Архитектурно значимого решения нет — ADR не требуется (сам ADR-0002 уже
предписал эту задачу в разделе «Раскатка»).

потому что закрываются той же оснасткой и тоже были дырами.

**Группа В — тестом не выражаются, остаются на ревью.** Полный список
с причинами — вторая таблица docs/invariants.md. Кратко: свежесть
контекста ревьювера и «артефакт — единственный канал» проверяемы только
снаружи процесса; разделение прав ролей в Фазе 0 живёт в промптах (один
токен, ADR-0001); защита конфигов системы — job `protected-paths` в CI,
а не код; неотключаемость guards — branch protection; policy-движка
(design §4) в Фазе 0 нет вовсе; идемпотентность шага проверяется реальным
прогоном; «ослабление защит — только через ADR» процессный по природе.

## Шаги

1. `tests/test_invariants.py`: восемь классов-инвариантов (группа Б),
   песочница FSM с неисполняемым git и отдельная песочница с настоящим
   временным репозиторием для уборки.
2. Маркеры неослабляемости в шапках существующих тестов-инвариантов:
   test_review_freshness.py, test_step_cost.py, test_kill_cleanup.py,
   test_agent_failure.py, test_agent_log.py — только docstring, ни одного
   ассерта.
3. `docs/invariants.md`: реестр «инвариант → тест(ы) → откуда», таблица
   «на ревью» с причинами и правило добавления нового инварианта.

Шаги 1–3 — один MR: реестр без тестов и тесты без реестра по отдельности
бессмысленны. Требование 5 (CI) — см. «Эскалация»: путь `.github/`
роль не правит.

## Мутационная проверка

Критерий приёмки 3. Проверялось не мысленно, а прогоном: копия
репозитория, одна умышленная поломка инварианта в коде, прогон
соответствующего класса тестов. Ожидание — красный.

| Мутация | Результат |
|---|---|
| `approve` из acceptance мержит сразу (гейт merge_gate схлопнут) | `MergeOnlyFromMergeGateTest` красный (1 падение) |
| `advance` из in_dev вызывает `git merge` ветки задачи | `MergeOnlyFromMergeGateTest` красный (1) |
| `fresh_verdict_iteration` возвращает итерацию всегда | `FreshVerdictGuardsAcceptanceTest` красный (3) |
| `budget_block` всегда возвращает None | `ExhaustedBudgetIsNotBypassableTest` красный (3) |
| `approve` из escalated обнуляет `review_iters` | `CountersNeverResetTest` красный (2) |
| `drop_task_dir` сносит каталог до всех проверок | `KillKeepsMainIntactTest` красный (1) |
| уборка делает коммит в main | `KillKeepsMainIntactTest` красный (5) |
| `advance` автопроходит spec_gate / acceptance / merge_gate | `ManualGatesNeedTheOperatorTest` красный (9) |
| `cmd_run` запускает разработчика из любого состояния | `AgentRunsOnlyFromRunTest` красный (7) |
| guard перестаёт требовать «Влияние на систему» | `GuardKeepsTheIntegritySectionTest` красный (1) |

Две первые редакции мутаций (для merge и для kill) остались зелёными —
и это оказалось не дырой в тестах, а защитой в глубину в самом коде:
`approve` из acceptance до merge не доходит из-за более ранней ветки, а
`drop_task_dir` после снятия проверки «в main» упирается в проверку «в
индексе» (T008). Мутации заменены на настоящие нарушения инварианта,
после чего оба теста краснеют. Факт стоит знать: обе защиты двойные,
и ослабление одной половины тестами не ловится — ловится ослабление
инварианта, а не строки.

## Влияние на систему

Изменение аддитивно: новый тестовый модуль, новый документ и пять
docstring. Кода оркестратора, guard'а, шаблонов, скилов и CI задача не
касается — `git diff --stat` по `orchestrator/` и `scripts/` пуст.

- **Ни один существующий тест не ослаблен и не удалён**: правки в пяти
  модулях — только текст docstring, ассерты и фикстуры не тронуты; было
  128 тестов, стало 154, прежние 128 на месте и зелёные.
- **Гейты, лимиты и guard не изменены**: пороги (`LIMIT_REVIEW_ITERS`,
  `LIMIT_ACCEPT_REJECTS`, `AGENT_RETRIES`, `BUDGET_ALERT_RATIO`) и
  секции guard читаются тестами, а не переписываются.
- **Направление изменения — ужесточение**: часть поведения, которая
  раньше держалась на суждении ревьювера, теперь падает в CI. Побочный
  эффект честный: правка, ломающая инвариант, станет красной, даже если
  автор считает её улучшением. Это и есть цель ADR-0002.
- **Риск ложного срабатывания в чужой задаче**: тест инварианта краснеет
  на изменении поведения, которое сам инвариант и запрещает. Разбор —
  через docs/invariants.md (инвариант → источник) и эскалацию, а не
  через правку теста.
- **Рабочий репозиторий защищён от самих тестов**: `subprocess.run`
  подменён на весь класс FSM-тестов, git-сценарии живут во временном
  репозитории. Без этого `cmd_approve` в merge_gate выполнил бы
  настоящий merge в рабочем дереве.
- **Откат**: удалить `tests/test_invariants.py` и `docs/invariants.md`,
  снять пять шапок. Состояния, схемы БД и артефактов задача не меняет,
  миграции нет — откат полный и без следов.

## Риски

- **Реестр устаревает молча.** docs/invariants.md ссылается на классы
  тестов по имени; переименование класса реестр не ломает и CI не
  краснит. Проверка имён — на ревью; автоматическая сверка реестра
  с кодом (парсинг таблицы) — отдельная задача, здесь это было бы
  расширением объёма.
- **Цикл «все состояния × все команды» — самый дорогой тест модуля**
  (81 подтест на класс, ~2 с на модуль из-за git-сценариев уборки).
  Сейчас это доли общего прогона; при росте числа команд стоит смотреть
  на время, а не расширять цикл механически.
- **`FSM_STATES` — список, а не производная от кода.** Новое состояние
  FSM придётся добавить сюда руками, иначе инвариант в нём не проверится.
  Вывести список из кода нечем: состояния в Фазе 0 — строковые литералы
  в `cmd_*`, реестра состояний нет; заводить его — изменение оркестратора,
  то есть выход за «Не входит» этого SPEC.
- **Инвариант «оркестратор не думает» проверен по факту запуска агента**,
  а не по отсутствию суждения в коде. Более сильной формулировки,
  выразимой тестом, у меня нет; остаток — на ревью.

## Эскалация

**Вопрос.** Требование 5 просит дополнить job `protected-paths`
в `.github/workflows/ci.yml` предупреждением на изменение
`tests/test_invariants.py` и `docs/invariants.md`. Путь `.github/`
CLAUDE.md и skills/conventions-core.md относят к тем, которые «меняет
только Оператор отдельным MR». Что делает Оператор:

(а) применяет патч ниже сам отдельным MR (реализация требования 5
    остаётся за пределами этой ветки);
(б) разрешает этой задаче тронуть `.github/` — тогда правка ложится
    сюда следующей итерацией, ADR не нужен, достаточно решения в REVIEW;
(в) считает требование 5 избыточным (маркеры в тестах и реестр уже
    делают ослабление видимым в diff) и снимает его из SPEC.

**Контекст.** Требования 1–4 выполнены и зелёные: 154 теста,
`guard.py --all` чистый. Правка требования 5 — одна строка, диапазон
защиты только расширяется (ослабления нет), но канал изменения не мой:
design.md §4 прямо описывает «агент правит собственную политику своим же
MR» как вектор, ради которого конфиги вынесены в отдельные права.
Готовый патч `.github/workflows/ci.yml`, строка 46:

```diff
-PROTECTED='^(gates\.yaml|roles\.yaml|\.github/|templates/|skills/)'
+PROTECTED='^(gates\.yaml|roles\.yaml|\.github/|templates/|skills/|tests/test_invariants\.py|docs/invariants\.md)'
```

Той же warning-логикой, что для конфигов системы: `exit 0` и
`::warning::`, fail — после разделения токенов (ADR-0001), как и сказано
в требовании 5.

**Блокирует.** Только требование 5. Остальная работа завершена, поэтому
артефакт идёт со `status: ready`, а не `escalate`: статус `escalate`
шаблоном PLAN не предусмотрен (guard завернёт), и задача встала бы
в `in_dev`, не доехав до ревью. Вопрос адресован Оператору через
ревьювера — REVIEW.md со `status: escalate` доводит его до инбокса
штатным путём FSM.
