# SPEC: Ветко-корректные чтения артефактов задачи

## Контекст
Контрольная задача T030 вскрыла класс дефекта: оркестратор читает
артефакты задачи (`SPEC.md`, `REVIEW.md`, `PLAN.md`, `acceptance_tests/`)
из рабочей копии пульта, молча предполагая, что дерево стоит на ветке
этой задачи. Когда это не так, наблюдались три разные беды: маршрутизация
`spec_gate` увела задачу мимо `tests_writing` вместо отказа, сборка
брифа упала голым `FileNotFoundError`-трейсбеком, а догфуд-фиксация
сверила approve-по-sha с чужой веткой и пропустила его. Задача закрывает
строку беклога P3 «Артефакто-чтения ветко-зависимы» (docs/roadmap.md).

## Требования
1. Все чтения артефактов задачи оркестратором — маршрутизация FSM,
   сборка брифа, трассируемость критериев приёмки, проверка лока
   приёмочных тестов (все места) — становятся ветко-корректными:
   источник истины — ветка задачи (`git show <branch>:<path>` —
   механизм git-первички T021 уже даёт способ), либо, там где чтение
   из ветки в конкретном месте невозможно, — жёсткий именованный отказ
   «дерево не на ветке задачи». Молчаливых дефолтов и голых
   трейсбеков быть не должно ни в одном из этих мест.
2. Догфуд-фиксация (`fixation.fix`/`fixation.read` для target по
   умолчанию) привязана к ветке задачи, а не к текущему чекауту
   рабочей копии.
3. Разобрано по журналу/логам, что переключило рабочее дерево на
   ветку `task/t029-...` перед approve T030 (журнал T030, около 17:35
   25.08.2026). Если это дыра механики (агент или оркестратор оставил
   чужой чекаут) — она названа и закрыта в этой же задаче. Если решение
   вне зоны задачи — в `PLAN.md` добавлена явная строка в разделе
   «Риски».
4. Существующие тесты не ослаблены и не удалены. Новые инварианты,
   введённые для закрытия этого класса дефекта, зарегистрированы в
   реестре `docs/invariants.md` с парными тестами по его правилам.

## Критерии приёмки

AC-1. Когда рабочее дерево стоит не на ветке задачи, маршрутизация
`spec_gate` не трактует недоступный на текущей ветке `SPEC.md` как
«schema_version 1 без AC-разметки» по умолчанию: она либо читает
`SPEC.md` с ветки задачи и маршрутизирует по нему как обычно, либо
явно отказывает «дерево не на ветке задачи» вместо молчаливого перехода
мимо `tests_writing`.

AC-2. Когда рабочее дерево стоит не на ветке задачи, сборка брифа роли
не падает голым `FileNotFoundError`-трейсбеком: она либо читает
SPEC/TZ с ветки задачи, либо явно отказывает «дерево не на ветке
задачи».

AC-3. Проверка трассируемости критериев приёмки (переход
`tests_writing` → `in_dev`) и проверка лока приёмочных тестов (переход
`in_dev` → `review`) читают состояние `acceptance_tests/` ветки задачи,
а не рабочей копии: при рабочем дереве на другой ветке результат этих
проверок не зависит от того, какая ветка сейчас выписана.

AC-4. sha, который вычисляет и с которым сверяется догфуд-фиксация
(`fix()`, `read()`, `check_integrity()` для target по умолчанию), —
head ветки задачи, а не HEAD текущего чекаута: approve-по-sha не
проходит по sha чужой ветки, если рабочее дерево оказалось выписано не
на ветку задачи.

AC-5. Ни одно из мест, перечисленных в AC-1–AC-4, не продолжает работу
молча с ошибочным предположением о текущей ветке и не падает
необработанным исключением: каждое такое место либо читает ветку
задачи корректно, либо завершается именованным отказом «дерево не на
ветке задачи» с записью в журнал задачи.

AC-6. Причина переключения рабочего дерева на ветку `task/t029-...`
перед approve T030 (журнал T030, ~17:35 25.08.2026) установлена и
названа. Если это дефект механики оркестратора или агента — он закрыт
в этой же задаче. Если решение вне её зоны — в `PLAN.md` этой задачи
добавлена явная строка в разделе «Риски» с указанием причины.

AC-7. Ни один существующий тест не ослаблен, не заскипан и не удалён.
Новые инварианты, введённые этой задачей, добавлены в реестр
`docs/invariants.md` (таблица «Кодированные тестами») с парным тестом
по правилам этого реестра.

## Не входит

- Фиксация и чтения артефактов кода для внешних target'ов
  (`.artel/projects/<target>`, `fixation._fix_external`/`_read_external`):
  ТЗ называет проблему чекаута только для догфуда (требование 2) —
  внешний target уже коммитит свой репозиторий целиком отдельно от
  рабочего дерева пульта.
- Право Оператора ослаблять существующие тесты, гейты или инварианты
  через ADR — не предмет этой задачи (принцип целостности, ADR-0002).
