# PLAN: Ветко-корректные чтения артефактов задачи

## Подход

Источник истины для каждого из перечисленных в SPEC мест — ВЕТКА задачи
(`git show <branch>:<path>` / `git ls-tree -r <branch> -- <dir>`), не
рабочая копия пульта. Переключаться на этот источник только когда есть
чем доказать расхождение, а не всегда, — иначе весь существующий стенд
заглушек `gitcmd.git` (`fake_git`, возвращающий пустой успех на любые
аргументы, десяток тестовых файлов) и песочницы, где роль ещё не успела
сделать свой `git checkout -b` (RealPultGitTest и другие — вся работа
идёт прямо на `main`), сломались бы или начали молча отвечать пустым
содержимым вместо реального. Поэтому в основе — один общий предикат
`gitcmd.on_foreign_branch(branch)`:

```
on_foreign_branch(branch) = branch и current_branch() и
                            current_branch() != branch и
                            branch_exists(branch)
```

True — только когда рабочее дерево ДОКАЗУЕМО стоит не на ветке задачи, и
сама ветка задачи реально существует в git. Ложь во всех остальных
случаях (свой чекаут; ветка ещё не создана ролью — легитимный ранний
момент жизни задачи, ADR-0003 3д; git не ответил на вопрос «какая ветка
сейчас», в т.ч. полностью заглушенный `gitcmd.git` в старых тестах) —
тогда каждое место читает как раньше, до T031, байт в байт то же
поведение. Каждое из 5 мест (spec_gate, brief, traceability, PLAN.md-гейт
+ лок, fixation sha) само решает `on_foreign_branch` один раз и либо
берёт содержимое с ветки (`gitcmd.show`/`gitcmd.ls_tree_files`), либо
идёт прежним путём через диск/`HEAD`.

Разбор AC-разметки и структурная проверка (`scripts/guard.py`) не должны
раздваиваться по источнику файла — диск или ветка. Поэтому `guard.py`
рефакторен: три источник-агностичных ядра (`scan_ac_content`,
`traceability_errors_from_content`, `check_content`), принимающих уже
прочитанный текст, а не путь; прежние дисковые функции
(`scan_acceptance_tests`, `acceptance_traceability_errors`, `check`)
становятся тонкими обёртками над ними же — поведение с диска не меняется
ни на бит, только источник для ветки берёт то же самое ядро.

Не архитектурно значимое решение — ADR не заводится: это починка класса
дефекта внутри уже существующего механизма git-первички (T021), не новый
механизм.

## Шаги

1. `orchestrator/gitcmd.py`: примитивы `show`, `ls_tree_files`,
   `branch_head_sha`, `on_foreign_branch`; заодно — `res is None`
   null-safety в `current_branch`/`branch_exists` (тот же класс
   вырожденного случая, что уже несут `head_sha`/`is_clean`/`diff_paths`,
   но сами эти две функции его не несли — стало заметно, когда
   `on_foreign_branch` попал на горячий путь `set_state`, вызываемый на
   каждом переходе FSM). `orchestrator/store.py`: `task_branch` —
   деградация та же, что у `task_target`.
2. `scripts/guard.py`: рефактор без изменения поведения дисковых функций
   — три источник-агностичных ядра, `_section_body` → `section_body`
   (публичная, переиспользуется вне модуля).
3. `orchestrator/fsm.py`, AC-1: `cmd_approve`, ветка `spec_gate` —
   SPEC.md читается с ветки задачи при `on_foreign_branch`, иначе как
   раньше; отказ «дерево не на ветке задачи» — именованный `sys.exit` +
   журнал.
4. `orchestrator/fsm.py`, AC-3: `cmd_advance`, ветка `tests_writing`
   (трассируемость AC) и ветка `in_dev` (гейт статуса PLAN.md +
   лок `acceptance_tests/`, было — сверка с литералом `"HEAD"`, стало —
   с веткой задачи при чужом чекауте). Гейт статуса PLAN.md пришлось
   чинить тем же приёмом, хотя AC-3 называет только сам лок: иначе на
   чужом чекауте гейт «PLAN.md не ready» молча держит переход, и лок
   ниже не достигается вовсе — тест `LockBranchTest` (see acceptance_tests)
   это поймал первой же итерацией прогона.
5. `orchestrator/brief.py`, AC-2: `developer_brief` — SPEC.md с ветки
   при `on_foreign_branch`, именованный `sys.exit` вместо голого
   `FileNotFoundError` также и на обычном дисковом пути (ветка ещё не
   создана — файла может не быть и там).
6. `orchestrator/fixation.py`, AC-4/требование 2: `_fix_dogfood` — sha
   головы ветки задачи при `on_foreign_branch`, иначе `HEAD` текущего
   чекаута, как и было (SPEC, требование 3, T021).
7. AC-6/требование 3: разбор инцидента T030 по `git reflog` пульта —
   см. «Риски».
8. Юнит-тесты (`tests/test_gitcmd_branch_reads.py` — новый; расширение
   `tests/test_acceptance_tests_flow.py` тремя классами на источник-
   агностичные ядра guard; `tests/test_review_package.py` — обновлён
   `FakeGit` и один список ожидаемых git-вызовов под новый легитимный
   вызов `rev-parse --abbrev-ref HEAD` из брифа, без ослабления
   проверки — см. «Влияние на систему»). Полный прогон
   `python3 -m unittest discover -s tests`, приёмочные тесты задачи,
   `scripts/guard.py --all`. Регистрация инварианта 28.

## Влияние на систему

Затронуты 5 модулей вне непосредственной зоны «нового кода»:
`orchestrator/gitcmd.py`, `orchestrator/fsm.py`, `orchestrator/brief.py`,
`orchestrator/fixation.py`, `scripts/guard.py` — все пять уже несли
плотное покрытие существующими тестами (569 тестов до этой задачи),
и весь прогон остаётся зелёным (590 тестов после — 569 прежних + 21
новый — 14 в `test_gitcmd_branch_reads.py`, 7 в `test_acceptance_tests_flow.py`),
за вычетом 3 предсуществующих падений
`test_multitarget.RoleEnvTest`, не связанных с этой задачей (тянут
`user.name`/`user.email` из реального `~/.gitconfig` машины, а не из
песочницы — воспроизводится на `main` без единой правки этой ветки).

Единственный тест, чью проверку пришлось скорректировать —
`test_review_package.CmdRunReviewPackageTest.test_developer_step_has_no_package`
(SPEC T011, «не входит»): он сверяет ТОЧНЫЙ список git-вызовов шага
разработчика, чтобы поймать регресс «шагу разработчика по ошибке собрали
ревью-пакет». Эта гарантия не ослаблена — сверка осталась точным списком,
не подмножеством; в список добавлен ровно один новый легитимный вызов
(`rev-parse --abbrev-ref HEAD` — сам `on_foreign_branch` брифа), а
`FakeGit` заглушки дополнен обработкой `rev-parse`, возвращающей пустой
ответ (тот же вырожденный случай «git не ответил», которым уже отвечают
остальные заглушки пакета) — иначе он по случайности попадал в общую
ветку `else: stdout = self.diff` и подсовывал брифу нечитаемую диагностику
вместо пустого ответа.

Задействованный инвариант 25 (docs/invariants.md, «FSM решает только по
зафиксированным хэшам») не ослаблен: `_fix_dogfood` по-прежнему решает
по sha чего-то одного (либо ветки задачи, либо текущего чекаута) —
неоднозначности «а что если оба» нет, `on_foreign_branch` — чистая
дизъюнкция без общей области. Инвариант 26/27 (трассируемость AC, лок
`acceptance_tests/`) не ослаблен: правило трассируемости и правило лока
остались в одной функции каждое (`guard.traceability_errors_from_content`,
`gitcmd.diff_paths`), источник входа для них теперь может быть веткой —
само правило не изменилось ни строкой.

Откат: `git revert` этого MR — новый код только ДОБАВЛЯЕТ ветвление
(`if on_foreign_branch(...): ... else: <прежний код>`), прежняя ветка
`else` везде дословно совпадает с кодом до T031 (кроме двух точечных
null-safety фиксов в `gitcmd.current_branch`/`branch_exists`, которые
сами по себе строго более безопасны и не участвуют в ветвлении).

## Риски

**AC-6 (требование 3): причина переключения ветки перед approve T030.**
Установлена по `git reflog show --date=iso HEAD` пульта (не по журналу
БД — тот пишет только действия оркестратора, не ручные git-команды):

```
57b6277 HEAD@{2026-08-25 20:29:51 +0300}: checkout: moving from task/t030-komanda-version to task/t029-inkrementalnyy-diff-revyu-pozd
...
208155b HEAD@{2026-08-25 20:37:18 +0300}: checkout: moving from task/t029-inkrementalnyy-diff-revyu-pozd to task/t030-komanda-version
```

Ошибочный `approve T030` (журнал задачи, запись id 754: `state -> in_dev`
в 17:35:02Z = 20:35:02 MSK) пришёлся ровно на окно между этими двумя
checkout — рабочее дерево в этот момент стояло на
`task/t029-inkrementalnyy-diff-revyu-pozd`, ветке уже смерженной и
закрытой задачи T029 (её `done` — 15:10:35Z, на час раньше).

Это НЕ дыра механики: `git checkout <ветка>` вызывается ровно в двух
местах orchestrator целиком (`grep -rn '"checkout"' orchestrator/`) —
`orchestrator/fsm.py:388` (`cmd_approve`, merge_gate, всегда на
`config.MAIN_BRANCH`, никогда не на ветку другой задачи) и
`orchestrator/brief.py:86` (`git checkout -- docs/codebase-map.md`,
восстановление ОДНОГО ФАЙЛА после регенерации карты, не переключение
ветки). Ни один из них не мог произвести
«moving from task/t030-... to task/t029-...». Единственное объяснение —
ручная команда `git checkout task/t029-...`, выполненная Оператором
напрямую в рабочем дереве пульта (правдоподобно — чтобы посмотреть на
только что смерженную и закрытую T029), без возврата на исходную ветку
перед следующей командой `artel.py approve T030`.

Причина в дизайне, не в конкретной ошибке: рабочее дерево пульта для
target'а по умолчанию (`config.DEFAULT_TARGET`, ADR-0003 3д, «особый
случай» до A7) — ЕДИНОЕ на все задачи и общее с ручными командами
Оператора; ничто в CLI не проверяет и не предупреждает, что чекаут
разошёлся с задачей, с которой Оператор сейчас работает через `artel.py`.
Устранение самой ВОЗМОЖНОСТИ ручного стороннего чекаута — вне зоны этой
задачи (означало бы гейт или предупреждение на КАЖДУЮ команду CLI, не
только на 4 места чтения из SPEC AC-1–4, и это отдельное архитектурное
решение, не однострочная правка). Эта задача не устраняет причину, а
закрывает её ПОСЛЕДСТВИЕ: после T031 такой же ручной чекаут в то же окно
времени для АК-1–4-путей уже не приводит к неверной маршрутизации,
зависшему трейсбеку или sha чужой ветки — `on_foreign_branch` эти 4 места
переключает на чтение с ВЕТКИ ЗАДАЧИ независимо от того, что стоит
выписано в рабочем дереве. Возможное дальнейшее смягчение (предупреждение
`artel.py`, если текущий чекаут не совпадает ни с одной активной задачей)
— кандидат в `docs/roadmap.md`, не предмет этой задачи.
