## Замечания

- **major — tasks/01M3FQ3JVC3DGGM33XCX8TC7ME/PLAN.md:162-166 (адрес
  эффекта — orchestrator/acceptance.py:322)** — PLAN утверждает, что лог
  полного набора «попадает под проверку утечки пула
  (`doctor.check_role_log_pool_leak` — полезно)». Проверка полезной здесь
  не является, а даёт НОВЫЙ класс ложных срабатываний в детекторе, у
  которого ровно этот класс закрывала отдельная задача
  (01M3F7BYE82S9AQCBSP1RTQQTR, требование 7 — сужение до логов шагов
  ролей). Сценарий (проверен исполнением): имя `<id>-fullsuite-1.log`
  удовлетворяет `doctor/canary_pool.py:_ROLE_LOG_STEM`
  (`^[^-]+-.+-\d+$`), то есть читается как лог шага роли; красный полный
  набор с падением в `tests/test_canary.py` (строки 504, 1597) или
  `tests/test_doctor_canary_pool.py` (строка 294) пишет в этот файл
  полный вывод pytest, а pytest в traceback печатает и докстринг упавшей
  функции — вместе с литералом `~/.artel-canary`; следующий `doctor`
  заводит `kind=incident` `doctor.canary-pool-leak` «лог роли … упоминает
  каталог пула канарейки», авто-ack для него намеренно не заведён, и
  после ack он возвращается, пока файл не уйдёт ротацией. Оператор
  разбирает утечку контекста роли, которой не было. Кода это, на мой
  взгляд, не касается: имя файла предписано SPEC требованием 3, а
  `orchestrator/doctor/` вне зон задачи. Предложение: привести пункт
  «Влияние на систему» в соответствие с фактом (проверка утечки читает
  этот файл и даёт ложный incident на красном прогоне канареечных
  модулей) и вписать класс в «Предложения системе» тем же адресом
  (`orchestrator/doctor/canary_pool.py::_is_role_step_log` — отбор по
  форме имени не отличает лог прогона набора от лога шага роли), рядом с
  уже записанным там же классом про `report._task_step_logs`. Правки
  кода не требую; если сочтёшь нужным менять имя файла или детектор —
  это эскалация (SPEC предписывает имя, doctor вне зон).

- **minor — tests/test_acceptance.py:192-209
  (`test_digest_is_bounded_by_the_log_tail_config`)** — заявка ловит две
  мутации («только по символам или только по строкам»), тест ловит одну.
  Проверено: на фикстуре теста строка длиной 106 символов, поэтому при
  мутации «ограничение только по символам» выжимка = 1000 символов и
  10 строк — оба ассерта проходят, мутация выживает; ловится только
  «только по строкам» (15×106 > 1000). То есть потолок по СТРОКАМ
  фактически не проверен ничем, и его снятие не покраснит набор. На
  коротких nodeid та же мутация даёт 47 строк. Предложение: добавить в
  этот же тест (или соседним subTest) случай с коротким именем —
  200 строк вида `FAILED t.py::C::t{i}` — и оставить оба ассерта: тогда
  заявка совпадёт с тем, что тест ловит.

## Предложения системе

- Реестр замечаний и правило вердикта расходятся на minor: `_registry_gate`
  (`orchestrator/advance_gates/tests_writing.py:63`) блокирует `approved`
  при ЛЮБОЙ записи со статусом не `accepted`, а skills/review-checklist.md
  предписывает `approved` при «0 blocker/major». Итог: одно minor-замечание
  стоит полной итерации разработчика — либо ревьювер молчит о minor, либо
  платит шагом. Стоит либо разрешить `approved` с открытыми minor-записями,
  либо убрать из скила правило «0 blocker/major → approved».
- `orchestrator/canary.py::_pass_acceptance_gate` называет себя
  «эквивалент operator approve», но после этой задачи `approve` гоняет
  полный набор, а канареечный гейт — нет. Класс: «дубль гейта, заявленный
  как эквивалент, расходится с оригиналом при каждой правке оригинала».
