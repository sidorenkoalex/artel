# SPEC: Граница git для ролей — git из каталогов пульта не доходит до репозитория пульта, отказ `git clean` и git в репозитории пульта, команда удаления файла задачи

## Контекст
Инцидент 04.11 (задача 01M6HWP40X94FYE7FS0N63VMCS, роль test_author): `rm`
роли недоступен, и роль, убирая свой временный файл, выполнила
`git -C <ROOT>/.artel/projects/<проект>/tasks/<id> clean -fX -- stubcheck.py`.
Каталог документов задачи — не репозиторий, git поднялся до репозитория
пульта (`config.ROOT`) и удалил игнорируемые файлы пульта (`.artel/models.yaml`,
`.artel/canary/`, `.artel/notes-pending/`, локальные каталоги проекта,
`.artel/home/.claude`). Каталоги области проекта лежат внутри репозитория пульта
(`config.PROJECTS`, `orchestrator/config.py:57`; `artifact_branch.docs_dir`).
Белый список роли Claude — `Bash(git:*)` (`orchestrator/providers/claude.py:45`,
`:114`) — пропускает любую подкоманду и любые `-C`/`--git-dir`/`--work-tree`/`-c`;
у Codex разрушительную часть закрывает песочница `workspace-write`
(`orchestrator/providers/codex.py:136`, `:437-444`), у Claude — ничто. Вдобавок
роль внешнего проекта не может удалить свой неотслеживаемый файл иначе как
`git clean -f <файл>`.

Модель угрозы — ошибочная команда роли, а не намеренный обход: механизм
отклоняет прямой вызов git в перечисленных формах; обход через произвольный
интерпретатор (`python3 -c` роли артели) и абсолютный путь к git — вне задачи
(`docs/stack.md`, «Паритет безопасности роли»).

## Требования

1. **Граница подъёма git.** В окружении шага роли (`runner.role_env`; оба
   провайдера — Claude и Codex; любой проект — артель и внешний)
   `GIT_CEILING_DIRECTORIES` или равный по действию механизм не даёт git,
   запущенному из самого `<ROOT>/.artel` или из каталога внутри него, который
   сам не репозиторий (сам `config.PROJECTS`, корень проекта, `tasks/`, каталог
   документов задачи, `knowledge/`, `logs/`, `epics/`), найти репозиторий
   пульта: git завершается отказом «not a git repository». Git в рабочей копии
   задачи и в клоне проекта работает как прежде. Потолок сравнивается с
   разрешённым путём (на macOS `/tmp` → `/private/tmp`). Основание для
   `<ROOT>/.artel` (опыт Оператора, возврат 3, 04.11): при потолке, равном ровно
   `<ROOT>/.artel`, git, запущенный из самого `<ROOT>/.artel`, находит
   репозиторий пульта. Отсюда потолок фактически равен `<ROOT>` (решение
   Оператора, возврат 5, 04.11) и остаётся в окружении дочерних процессов пульта,
   запущенных ролью (требование 5): вызовы git пульта, исполняемые из
   подкаталога `<ROOT>` без `-C`, идут с текущим каталогом `<ROOT>` или с
   `-C <ROOT>` (проверяет AC-14).
2. **Отказ git в репозитории пульта и в чужой задаче.** Прямой вызов git шагом
   роли отклоняется до исполнения (ненулевой код возврата, строка причины) по
   каждому пути, который задаёт его репозиторий или рабочее дерево: текущий
   каталог вызова, `-C` (с учётом нескольких `-C` подряд, относительных — от
   предыдущего), `--git-dir`, `--work-tree`, `-c core.worktree=…`, переменные
   `GIT_DIR`, `GIT_WORK_TREE`. Путь проверяется после разрешения (абсолютный
   вид, символические ссылки, на macOS `/tmp` → `/private/tmp`) на вложенность,
   а не на буквальное равенство корню (решение Оператора, возврат 3, 04.11):
   - отказ, если разрешённый путь лежит внутри `config.ROOT` — сам корень или
     любой его подкаталог (`<ROOT>/.artel`, `<ROOT>/docs`, каталог документов
     задачи и т. п.); опыт Оператора: `git -C <ROOT>/.artel clean -ndX`
     перечислил `models.yaml`, `logs`, `projects/*/tasks`;
   - отказ, если разрешённый путь лежит внутри рабочей копии другой задачи —
     сама копия или любой её подкаталог;
   - не отказ (исключение из первого пункта, если путь не внутри рабочей копии
     другой задачи): собственная рабочая копия задачи и её подкаталоги; клон
     проекта своей задачи — `<ROOT>/.artel/projects/<проект задачи>/repo` — и
     его подкаталоги, в том числе его общий каталог `.git`
     (`<ROOT>/.artel/projects/<проект задачи>/repo/.git`), общий для
     собственной рабочей копии.

   Строка причины отказа — собственная строка механизма, отличимая от сообщений
   git (решение Оператора, возврат 5, 04.11): она не совпадает с отказом git
   «not a git repository» и называет причину — для пути внутри `config.ROOT`
   словами «репозиторий пульта» с указанием команды `task-rm` (требование 4)
   как способа убрать свой файл, для пути внутри рабочей копии другой задачи —
   словами «рабочая копия другой задачи». Рабочая копия другой задачи сама лежит
   внутри `config.ROOT`; для пути внутри неё главная строка причины — «рабочая
   копия другой задачи» (более точная), строка «репозиторий пульта» — для прочих
   путей внутри `config.ROOT` (решение Оператора, возврат 6, 04.11). Отказ механизма не зависит от границы
   требования 1: он наступает и в окружении, из которого граница убрана.

   Репозитории вне `config.ROOT` (например, временные каталоги тестов) не
   затрагиваются.
3. **Отказ `git clean`.** Прямой `git clean` шага роли с любыми флагами и путями
   отклоняется до исполнения, если его репозиторий лежит внутри `config.ROOT`
   (репозиторий пульта, клоны и рабочие копии в `.artel`, включая свою рабочую
   копию). Покрываемые формы:
   - подкоманда `clean` напрямую;
   - псевдоним из конфигурации, раскрывающийся в `clean`;
   - любой псевдоним с `!` — и заданный `-c alias.x='!…'`, и из конфигурации
     рабочей копии: отказ любого `!`-псевдонима;
   - `-c`, `--config-env`, `GIT_CONFIG_PARAMETERS`,
     `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>`, задающие
     псевдоним, `core.worktree`, `core.pager` или `core.fsmonitor`.

   «Конфигурация рабочей копии» (здесь и в критериях, где сказано
   «`.git/config` рабочей копии») — оба файла, которые git читает для рабочей
   копии задачи: `config` общего каталога `.git` клона проекта (конфигурация
   клона) и `config.worktree` собственной рабочей копии
   (`<клон>/.git/worktrees/<имя>/config.worktree`, при
   `extensions.worktreeConfig`).

   Объём отказа (решение Оператора на гейте SPEC, возврат 2, 04.11): для
   псевдонима без `!` отказ наступает, когда псевдоним раскрывается в `clean`.
   Для `core.pager` и `core.fsmonitor` отказ — на верхнем уровне: механизм
   отклоняет до исполнения вызов git (любой подкоманды) в репозитории внутри
   `config.ROOT`, если значение `core.pager` или `core.fsmonitor` — из `-c`,
   `--config-env`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/
   `GIT_CONFIG_VALUE_<n>`, файлов конфигурации git, которые читает вызов (в том
   числе конфигурация рабочей копии), — или переменная `GIT_PAGER` содержат вызов
   git как команду (например, `git clean -fX`). Значения без вызова git (`cat`,
   `less`) допустимы: `git -c core.pager=cat log` в своей рабочей копии проходит.
   Основание верхнего уровня: git ставит свой exec-path первым в PATH дочерних
   процессов, поэтому вложенный git из pager, fsmonitor или `!`-псевдонима идёт
   мимо обёртки на PATH и ею не перехватывается. `GIT_EXEC_PATH` механизм не
   подменяет. Отказ любого `!`-псевдонима — как выше, по ТЗ. Строка отказа
   называет команду удаления из требования 4. Репозитории вне `config.ROOT` не
   затрагиваются.
4. **Команда пульта удаления файла задачи.** `orchestrator/artel.py` получает
   команду `task-rm <id> <путь>…` (новый модуль `orchestrator/task_files.py`).
   - Команда вносится в `_ROLE_ALLOWED_COMMANDS` (`orchestrator/artel.py:2562`)
     с дополнением комментария над перечнем (что команда пишет и в каких
     пределах).
   - Удаляет перечисленные файлы, только если каждый после разрешения
     символических ссылок лежит внутри рабочей копии задачи `<id>` или каталога
     её документов (`artifact_branch.docs_dir`). В каталоге документов
     удаляются только файлы, которых нет в ветке артефактов задачи (созданные
     после последнего автокоммита); файл, лежащий в ветке артефактов, — отказ.
   - Символическая ссылка: удаляется сама ссылка, не её цель. Команда не идёт
     по ссылке за пределы двух корней: ссылка, цель которой лежит вне них, и
     путь, родительский каталог которого через ссылку выводит за корни, —
     отказ.
   - Каталог, путь вне двух корней (в том числе через `../`), путь, равный
     `.git` (файл или каталог) любого уровня вложенности — в том числе файл
     `.git` самой рабочей копии, — или лежащий внутри такого `.git`,
     символическая ссылка, ведущая наружу, — отказ всей команды: ни один файл
     набора не удаляется (без частичного удаления). Основание для `.git`
     (опыт Оператора, возврат 3, 04.11): после удаления файла `.git` рабочей
     копии git в процессе пульта (автокоммит, `clean -fdx` в
     `orchestrator/workspace.py`) находит репозиторий пульта — условие
     инцидента.
   - Признак роли — то же условие, что у диспетчера `artel.py`:
     `runner.in_role_environment` (`ARTEL_ROLE` либо `HOME`, равный дому роли,
     `orchestrator/runner.py:1195`). Под признаком роли задача берётся из
     `ARTEL_TASK`: `<id>`, отличный от `ARTEL_TASK`, и признак роли без
     `ARTEL_TASK` — отказ. Вызов Оператора (без признака роли) — с явным id
     любой задачи.
   - Миссии ролей (`orchestrator/role_prompt.py`, там, где перечислены команды
     пульта для роли) называют эту команду: миссия каждой роли, которой открыт
     каталог документов задачи, — абзац `docs_dir_note`
     (`orchestrator/role_prompt.py:503`, вызов — `:197`).
5. **Различение вызовов.** Механизм требований 2–3 не зависит от протокола

   пульта и запускаемых им команд (граница требования 1 остаётся). Способ
   снятия — единственный (решение Оператора, возврат 8, 04.11, Е-1 аудита):
   диспетчер удаляет из PATH дочерних процессов каталог обёртки
   `orchestrator/role_bin/`; прочие элементы PATH и их порядок не меняются.
   Переменной-выключателя нет: никакая переменная окружения — ни
   `ARTEL_PULT_GIT`, ни `ARTEL_GIT_GUARD_ROOT` (требование 10), ни любая новая —

   `GIT_CEILING_DIRECTORIES` (требование 1) и `ARTEL_GIT_GUARD_ROOT` в окружении
   дочерних процессов остаются. Временная

   одном процессе, не зависят от порядка. Маркер `ARTEL_PULT_GIT` (`orchestrator/gitcmd.py:25`)

     `<корень>/.artel/projects/<проект>/repo`; отдельных каналов для них нет.
   - Переменной нет — fail-closed: защищается корень, вычисленный от
     расположения файла обёртки, проверка не пропускается.

## Критерии приёмки
Проверка — в песочнице пульта с подменёнными процессами агента: команды
исполняются под окружением, собранным `runner.role_env` для роли
соответствующего провайдера. Все тесты задачи, исполняющие меняющие команды
git (`clean`, `reset --hard`, `checkout -- .` — любые формы AC-2, AC-4, AC-6,
AC-7, в том числе в окружении без границы требования 1), работают только
против временного дублёра ROOT — временного каталога с репозиторием,
подставленного вместо `config.ROOT`/`config.PROJECTS`, — и никогда против
настоящего репозитория пульта, его клона или рабочей копии кода задачи
(решение Оператора, возврат 6, 04.11): при мутации механизма тест портит
только дублёр. «Песочница пульта» и «`<ROOT>`» в критериях ниже — этот
дублёр. Обязательная форма подстановки дублёра (решение Оператора, возврат 7,
04.11; требование 10): тест в своём процессе подменяет `config.ROOT` и
`config.PROJECTS` (monkeypatch) на дублёр (`config.PROJECTS` —
`<дублёр>/.artel/projects`) и вызывает `runner.role_env`; дочерний git получает
дублёр через `ARTEL_GIT_GUARD_ROOT` и потолок `GIT_CEILING_DIRECTORIES` из
этого окружения — другого канала подстановки тест не использует.

AC-1. `git status` с cwd, равным каталогу документов задачи, `tasks/`, корню
проекта, самому `config.PROJECTS`, самому `<ROOT>/.artel` и каталогу внутри
`<ROOT>/.artel`, но вне `config.PROJECTS` (`<ROOT>/.artel/logs`):
(а) под окружением роли Claude и под окружением роли Codex — ненулевой код,
состояние репозитория пульта не выведено; (б) под тем же окружением, из
которого убран механизм требований 2–3 так, как его убирает диспетчер для
дочерних процессов (граница требования 1 на месте), — ненулевой код с «not a
git repository». Тот же `git status` в рабочей копии задачи и в клоне проекта
— успех (код 0) в обоих окружениях. Критерий краснеет на мутации: потолок
подъёма равен ровно `<ROOT>/.artel`.

AC-2. Под окружением роли `git -C <ROOT> status`, `git -C <ROOT>/.artel status`,
`git -C <ROOT>/docs reset --hard`, `git --git-dir=<ROOT>/.git status`,
`GIT_DIR=<ROOT>/.git git status`, `git -c core.worktree=<ROOT> status`,
`git -C <рабочая копия чужой задачи> status` и
`git -C <подкаталог рабочей копии чужой задачи> status` отклоняются до
исполнения: ненулевой код и строка причины механизма требования 2; после
`reset --hard` изменённый отслеживаемый файл песочницы пульта сохраняет
изменение.
`git -C <своя рабочая копия> status` и
`git -C <подкаталог своей рабочей копии> status` — успех.
«Строка причины» здесь и в формах ниже — строка отказа механизма требования 2,
не сообщение git: вывод не содержит «not a git repository» и содержит слова
«репозиторий пульта» и `task-rm` для пути внутри `ROOT` вне рабочих копий чужих
задач, а для пути внутри рабочей копии чужой задачи (сама копия и её
подкаталог) — «рабочая копия другой задачи» как главную строку причины; AC-2
проверяет обе строки. Каждая отклоняемая
форма AC-2 (основная и дополнительная) проверяется дважды: под окружением роли и
под окружением роли, сборка которого подменена в тесте так, что отсутствует
граница требования 1, а механизм требований 2–3 на месте (подмена, как в
AC-17), — чтобы отказ давал механизм, а не потолок; в обоих прогонах — ненулевой
код, строка причины, изменённый отслеживаемый файл дублёра ROOT цел.
Дополнительные формы (каждая — ненулевой код и строка причины до исполнения,
если не сказано иное):
- cwd внутри `ROOT` вне `<ROOT>/.artel` для команды не `clean`: с cwd, равным
  `<ROOT>/docs`, `git reset --hard` и `git checkout -- .` отклоняются;
  изменённый отслеживаемый файл песочницы пульта сохраняет изменение. Критерий
  краснеет на мутации: текущий каталог вызова проверяется только у `clean`.
- несколько `-C` подряд и относительный `-C` — путь вычисляется как у git,
  каждый следующий `-C` относительно предыдущего: с cwd, равным временному
  каталогу вне `ROOT`, `git -C <своя рабочая копия> -C ../.. status`
  отклоняется (`../..` от своей рабочей копии лежит внутри `ROOT`);
  `git -C <временный каталог вне ROOT> -C <относительный путь от него до ROOT> status`
  отклоняется; `git -C <ROOT> -C <своя рабочая копия абсолютным путём> status` —
  успех. Критерий краснеет на мутациях: учитывается только первый `-C`;
  относительный `-C` разрешается от исходного cwd, а не от предыдущего `-C`.
- символическая ссылка во временном каталоге вне `ROOT`, ведущая прямо в
  `<ROOT>`: `git -C <ссылка> status` и `git status` с cwd, равным этой ссылке,
  отклоняются. Критерий краснеет на мутации: путь приводится к абсолютному
  виду без разрешения символических ссылок (`abspath` вместо `realpath`) —
  ошибку ловит именно форма `-C <ссылка>` в окружении без границы требования 1.

Критерий в целом краснеет на каждой из мутаций механизма требования 2: текущий
каталог вызова проверяется только у `clean`; путь сравнивается на равенство
корню, а не на вложенность; учитывается только первый `-C`; относительный `-C`
разрешается от исходного cwd, а не от предыдущего `-C`; `abspath` вместо
`realpath`; строка отказа — сообщение git вместо собственной строки механизма.

AC-3. Под окружением роли из своей рабочей копии
`git --work-tree=<ROOT> status`, `GIT_WORK_TREE=<ROOT> git status`,
`git --work-tree=<рабочая копия чужой задачи> status` и
`GIT_WORK_TREE=<рабочая копия чужой задачи> git status` отклоняются до
исполнения: ненулевой код и строка причины.

AC-4. Под окружением роли `git clean -n` и `git clean -fX -- <файл>` в своей
рабочей копии и в репозитории пульта, а также `git clean -n` с cwd, равным
`<ROOT>/.artel`, и `git -C <ROOT>/.artel clean -ndX` отклоняются; строка отказа
называет команду `task-rm`; игнорируемые файлы песочницы остаются на месте.

AC-5. Под окружением роли в своей рабочей копии отклоняются
`git -c alias.cl=clean cl`, `git -c alias.x='!git clean -fX' x`, вызов
псевдонима `cl = clean`, записанного в `.git/config` рабочей копии, и вызов
псевдонима, заданного через `GIT_CONFIG_PARAMETERS`; игнорируемые файлы
песочницы остаются на месте.

AC-6. Под окружением роли в своей рабочей копии отклоняются: вызов псевдонима
`cl`, заданного `--config-env=alias.cl=<переменная>` со значением переменной
`clean`; вызов псевдонима `cl`, заданного `GIT_CONFIG_COUNT=1`,
`GIT_CONFIG_KEY_0=alias.cl`, `GIT_CONFIG_VALUE_0=clean`; вызов `!`-псевдонима,
записанного в `.git/config` рабочей копии (и с телом `!git clean -fX`, и с
безвредным телом `!echo ok`); `git -c alias.x='!echo ok' x`. Ненулевой код,
игнорируемые файлы песочницы на месте.

AC-7. Под окружением роли в своей рабочей копии на верхнем уровне, до исполнения,
отклоняются вызовы, где `core.pager`, `core.fsmonitor` или `GIT_PAGER` содержат
вызов git `git clean -fX`: `git -c core.pager='git clean -fX' log`,
`git -c core.fsmonitor='git clean -fX' status`, `GIT_PAGER='git clean -fX' git log`;
те же значения `core.pager`/`core.fsmonitor`, заданные через `--config-env`,
`GIT_CONFIG_PARAMETERS` и `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`;
`core.pager` и `core.fsmonitor` со значением `git clean -fX`, записанные в
`.git/config` рабочей копии (вызовы `git log` и `git status`). Для каждого:
ненулевой код возврата, строка отказа называет `task-rm`, игнорируемые файлы
песочницы на месте — значения pager и fsmonitor не исполнялись. «`.git/config`
рабочей копии» в AC-5–AC-7 — конфигурация рабочей копии требования 3: каждая
запись проверяется и в `config` общего каталога `.git` клона, и в
`config.worktree` собственной рабочей копии. Рекурсии и
зависания нет: каждый вызов теста идёт с явным таймаутом 30 с, превышение
таймаута — провал критерия. `git -c core.pager=cat log` и
`git -c core.pager=less log` в своей рабочей копии — успех (код 0). Критерий
краснеет на мутации: механизм не читает `core.pager`/`core.fsmonitor` из
`.git/config` рабочей копии.

AC-8. Под окружением роли `git clean -f` во временном репозитории вне `ROOT` —
успех, неотслеживаемый файл удалён.

AC-9. Воспроизведение инцидента: в корне песочницы пульта лежит игнорируемый

AC-11. `task-rm` отклоняет набор, содержащий хотя бы один из: файл каталога

## Не входит
- Физический перенос каталогов области проектов за пределы репозитория пульта
  (строка бэклога 04.11, через ADR).
- Резервная копия локального слоя пульта (строка копилки 04.11).
- Обход через произвольный интерпретатор (`python3 -c` роли артели) или
  абсолютный путь к git (модель угрозы).
- Принятые ограничения модели угрозы (решение Оператора на гейте SPEC, возврат
  04.11; записываются в таблицу паритета `docs/stack.md`, требование 8): код и
  тесты роли, исполняемые `plank-run`/`suite-run`/`mutation-run`, идут без
  механизма требований 2–3 (требование 5); `xcrun git …` обходит обёртку на
  PATH (класс «абсолютный путь к git»).
- Отказ по `core.pager`/`core.fsmonitor`/`GIT_PAGER`, значение которых не
  содержит вызова git (`cat`, `less`), и подмена `GIT_EXEC_PATH` (требование 3 —
  решение Оператора, возврат 2).
- `skills/` — защищённый путь: упоминание команды `task-rm` туда не вносится.
- Правка локального слоя пульта `.artel/home/`, `.artel/models.yaml` и каталогов
  `tasks/`; перенос строки `deny` в рабочий HOME — ручной шаг Оператора после
  мержа.
- Правка существующих тестов `tests/`: не ожидается; если существующий тест
  закрепляет прежнее окружение или PATH роли иначе, чем в требовании 6, —
  эскалация с перечнем методов, не правка.
