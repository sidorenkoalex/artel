- **П1.** Требование 3, абзац «Объём отказа»: «Вложенный `git clean`, который
  запускают pager, fsmonitor или `!`-псевдоним, отклоняется тем же механизмом

  машине пульта: git при старте ставит свой exec-path ПЕРВЫМ в PATH дочерних
  процессов. `git -c alias.p='!echo "$PATH" …; command -v git' p` выводит
  PATH[0] = `/Library/Developer/CommandLineTools/usr/libexec/git-core`, а
  `git` там разрешается в `…/libexec/git-core/git` — настоящий git, мимо
  обёртки, стоящей вторым элементом. Pager и хук fsmonitor наследуют то же
  окружение. Обёртка на PATH, сделанная буквально по требованию 6, вложенный
  `git clean` из `core.pager`/`core.fsmonitor` не поймает, и AC-7 упадёт.
  Решение Оператора п. 6 («ловится обёрткой на PATH») опирается на ту же
  предпосылку.

**П2.** AC-7, форма `core.fsmonitor`. Проверка во временном репозитории вне
ROOT: `git -c core.fsmonitor='git clean -fX' status` не завершился за 120 с
(остановлен вручную). Вероятная причина: вложенный git наследует `-c` через
`GIT_CONFIG_PARAMETERS` и снова вызывает тот же хук — рекурсия. Кроме того,
хук fsmonitor git вызывает с аргументами (версия, токен), которые для
вложенного `git clean -fX` становятся путями-фильтрами. Итог: без механизма
форма виснет, а не удаляет файлы, — критерий «не удаляет ни одного
игнорируемого файла» мутацию «вложенный вызов не отклонён» не ловит, а тест
без таймаута сам повиснет в наборе. Нужно уточнение формы (тело хука,
обрывающее рекурсию, например с `-c core.fsmonitor=` во вложенном вызове), и
явный таймаут в критерии.
