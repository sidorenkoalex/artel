# Предел числа процессов шага роли: размножение процессов роли не исчерпывает машину

## Факты

1. Инцидент 04.11: роль test_author задачи 01M6JJ4J4NBV2Y1Q4XHE3C3FVT в красной фазе приёмочных тестов запустила тест формы `core.fsmonitor`. Хук fsmonitor вызывал `git clean`, тот снова хук — цепочка из 3645 процессов `git`. Таблица процессов пользователя исчерпана (`kern.maxprocperuid` = 4000), команды пульта и сессии Оператора падали с «fork failed: resource temporarily unavailable». Цепочку погасила сама роль. Строка копилки 04.11, приоритет 1.
2. Процесс агента шага запускается `runner.spawn_agent` (`orchestrator/runner.py:83`, вызов — `orchestrator/runner.py:1806`) в своей группе процессов (`start_new_session=True`); таймаут шага, `kill`, `pause --now`, `release` снимают группу целиком (`orchestrator/liveness.py:140`, `:151`). После обычного завершения шага группа не снимается; закрытие канала вывода — `runner.close_pump` (`orchestrator/runner.py:1876`, ожидание до `PUMP_JOIN_TIMEOUT_SEC`). Цепочка инцидента ушла из группы шага: её корень осиротел.
3. Опыт 04.11 (macOS, python3, дважды — сессия Оператора и независимый проверяющий): `resource.setrlimit(RLIMIT_NPROC, (N, N))` ограничивает число процессов ПОЛЬЗОВАТЕЛЯ для этого процесса и его потомков; при N = текущее число процессов пользователя + 10 запустилось 15–18 дочерних, затем отказ `EAGAIN` (errno 35); процесс без ограничения продолжает запускать дочерние. Ограничение наследуют потомки, в том числе ушедшие в новую сессию. Поднять жёсткое ограничение без прав администратора нельзя; значение выше `kern.maxprocperuid` macOS молча урезает. Сейчас на машине мягкое ограничение 4000, жёсткое 6000. На Linux (раннер CI ubuntu) `kern.maxprocperuid` нет, а `RLIMIT_NPROC` считает и потоки.
4. Обёртка git ролей (задача 01M6JJ4J4NBV, `orchestrator/role_bin/git`, `orchestrator/role_git.py`) на каждый вызов git добавляет два кратких процесса (вложенная оболочка и `git config --list`, `orchestrator/role_git.py:249`); при исчерпании ограничения обёртка отказывает (`orchestrator/role_git.py:375`), а не пропускает вызов.
5. Пульт и сессия Оператора работают под тем же пользователем, что и роли. В пульте бывают живые потоки (`OutputPump` прошлой попытки, `threading.Timer` в `orchestrator/gitcmd.py:1650`), поэтому код в дочернем процессе до `exec` должен быть минимальным.

## Модель угрозы

Ошибочный тест или команда роли, порождающие процессы без предела (рекурсия хука, псевдонима, вызов самого себя), а не намеренный обход.

## Требуется

1. Процесс агента шага роли (оба провайдера — Claude и Codex) запускается с мягким и жёстким `RLIMIT_NPROC`, равным min(`kern.maxprocperuid` − запас, текущее мягкое ограничение пульта, текущее жёсткое ограничение пульта). Запас — константа `config` (имя выбирает SPEC), по умолчанию 1000. Значение вычисляет пульт в своём процессе до запуска; в дочернем процессе до `exec` выполняется только `resource.setrlimit` с готовым числом — без чтения sysctl, вызова `ps` и импортов. Процесс пульта не ограничивается.
2. Если `kern.maxprocperuid` прочитать нельзя (Linux, сбой) — значение от безопасного значения по умолчанию (константа `config`) с тем же min по текущим ограничениям; одна запись-предупреждение в журнале шага. Предупреждение не меняет прочие записи шага: существующие тесты, сверяющие журнал шага, остаются зелёными.
3. На старте шага, если процессов пользователя уже не меньше вычисленного ограничения, шаг не запускается: отказ с именованной причиной («запас процессов пользователя исчерпан: N из M») и тревога Оператору, без повторов попыток.
4. Отказ `fork` у роли из-за ограничения — обычная ошибка внутри шага: пульт продолжает работать, его команды и сессия Оператора запускают процессы.
5. По завершении шага любым исходом пульт снимает оставшуюся группу шага тем же механизмом, что на таймауте (`liveness`), ДО `close_pump`; запись в журнал — только если в группе оставались процессы. Текст записи «agent run finished» на обычном исходе не меняется.
6. Строка `doctor`: действующий `kern.maxprocperuid` (или «недоступен»), вычисленное ограничение шага и текущее число процессов пользователя; `warn`, если процессов пользователя больше ограничения шага; при недоступном sysctl — `ok` с пометкой «значение по умолчанию».
7. Документация: `docs/stack.md`, раздел «Провайдер исполнителя роли» — ограничение, его значение, наследование потомками, общий на пользователя запас; `docs/codebase-map.md`.
