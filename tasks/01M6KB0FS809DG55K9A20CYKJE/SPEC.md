# SPEC: Предел числа процессов шага роли

## Контекст
Инцидент 04.11: тест test_author задачи 01M6JJ4J4NBV2Y1Q4XHE3C3FVT в красной
фазе запустил хук `core.fsmonitor`, который вызывал `git clean`, а тот снова
хук. Получилась цепочка из 3645 процессов `git`, и таблица процессов
пользователя исчерпалась (`kern.maxprocperuid` = 4000). Команды пульта и
сессия Оператора падали с «fork failed: resource temporarily unavailable».
Агент шага запускается `runner.spawn_agent` (`orchestrator/runner.py:83`,
вызов — `orchestrator/runner.py:1805`) в своей группе процессов. Предела
числа процессов у него нет. После обычного завершения шага группа не
снимается, корень цепочки осиротел. Опыт 04.11 (факт 3 ТЗ) показал:
`RLIMIT_NPROC`, выставленный процессу, наследуют все потомки, в том числе
ушедшие в новую сессию. Поднять жёсткое ограничение без прав администратора
нельзя. Модель угрозы — ошибочный тест или команда роли, которые порождают
процессы без предела (рекурсия хука, псевдонима, вызов самого себя). Намеренный
обход в модель угрозы не входит.

## Требования

1. Процесс агента шага роли запускается с мягким и жёстким `RLIMIT_NPROC`,
   равными min(`kern.maxprocperuid` − запас, текущее мягкое `RLIMIT_NPROC`
   пульта, текущее жёсткое `RLIMIT_NPROC` пульта). Ограничение пульта,
   равное `resource.RLIM_INFINITY`, в min не участвует (решение Оператора
   О-1): если оба ограничения пульта бесконечны, ограничение шага равно
   первому члену формулы (`kern.maxprocperuid` − запас либо, по требованию 2,
   `config.ROLE_NPROC_FALLBACK_MAXPROC` − запас). Это касается обоих
   провайдеров, Claude и Codex: оба идут через `runner.spawn_agent`. Запас —
   константа `config.ROLE_NPROC_RESERVE`, значение 1000.
   Устройство вычисления (решение Оператора О-7):
   - ограничение вычисляет одна функция `runner.role_nproc_limit() -> int`
     без аргументов (решение Оператора, возврат 6, Р-2) в процессе пульта до
     запуска; её зовёт `runner._run_developer_step`
     (`orchestrator/runner.py:302`) ОДИН раз на шаг до цикла попыток
     `runner._run_attempts` (`orchestrator/runner.py:889`, вызов —
     `orchestrator/runner.py:333`), то есть внутри `try/finally` снятия
     захвата зоны в `runner._cmd_run` (`orchestrator/runner.py:286–299`;
     решение Оператора, возврат 7, С-1), не `runner._spawn_and_wait`; готовое число
     передаётся в каждую попытку и дальше в `spawn_agent(nproc_limit=…)`
     (вызов `spawn_agent` — `runner.py:1805`; решение Оператора, возврат 6,
     Р-1). Её же зовёт строка `doctor` требования 6;
   - `runner.spawn_agent` получает готовое число именованным аргументом
     `nproc_limit` и ставит `preexec_fn` только когда аргумент задан; без
     аргумента поведение `spawn_agent` прежнее, прочие вызовы `spawn_agent`
     и тесты, подменяющие его, не меняются.
   В дочернем процессе до `exec` выполняется только
   `resource.setrlimit(RLIMIT_NPROC, (N, N))` с готовым числом: без чтения
   sysctl, без вызова `ps` и без импортов. Процесс пульта не ограничивается:
   его собственные `RLIMIT_NPROC` после запуска шага прежние.
2. Если `kern.maxprocperuid` прочитать нельзя, в формулу требования 1 вместо
   него подставляется константа `config.ROLE_NPROC_FALLBACK_MAXPROC`,
   значение 4000 (действующее значение машины, факт 3 ТЗ). Тот же min по
   текущим ограничениям пульта (с правилом `RLIM_INFINITY` требования 1)
   сохраняется. Запись в журнал (решение Оператора О-6, меняет требование 2
   ТЗ в части записи):
   - на macOS, когда `kern.maxprocperuid` прочитать не удалось (неожиданный
     сбой), в журнал задачи при старте шага пишется ОДНА запись-предупреждение
     на шаг, не на попытку;
   - на платформе без этого параметра (Linux, раннер CI) значение по
     умолчанию берётся без записи в журнал.
   Точка подмены чтения (решение Оператора Н-1) — одна функция
   `runner._read_maxprocperuid() -> tuple[int | None, str]`: значение и
   исход — `"ok"` (прочитано), `"absent"` (параметра нет на платформе) либо
   `"failed"` (сбой чтения); значение `None` при исходах `"absent"` и
   `"failed"`. Платформу функция определяет сама по `sys.platform`, отдельного
   источника платформы нет. Выбор между записью-предупреждением и её
   отсутствием делается по исходу этой функции: `"failed"` — запись,
   `"absent"` — без записи.
   Пустой вывод чтения либо код возврата 0 без числа в выводе (в том числе
   у подменённого в тестах `subprocess`, например `SpyRun`) — исход
   `"failed"` на macOS, как прочий сбой чтения (решение Оператора, возврат 4,
   п. 3).
   Прочие записи шага предупреждение не меняет; существующие тесты журнала
   шага на CI не меняются.
3. На старте шага пульт сравнивает текущее число процессов пользователя с
   вычисленным ограничением. Если процессов уже не меньше ограничения, шаг
   не запускается. Отказ несёт именованную причину «запас процессов
   пользователя исчерпан: N из M» (N — число процессов, M — ограничение).
   Оператору поднимается тревога — тем же механизмом тревог, что у прочих
   остановок цикла. Повторных попыток нет.
   Устройство отказа (решение Оператора, возврат 4, п. 1): при исчерпанном
   запасе `runner.cmd_run` отказывает через `SystemExit` с этой именованной
   причиной — как прочие отказы стартовать (бюджет, пауза, занятость зоны), —
   а не исходом `"skipped"` из `runner.run_agent_once`. Цикл `auto` превращает
   такой `SystemExit` в остановку «run отказался стартовать» с тревогой
   (`auto._role_run_step`, `orchestrator/auto.py:948`, остановка —
   `orchestrator/auto.py:1017`); `orchestrator/auto.py` не меняется.
   Однократность (решение Оператора, возврат 4, п. 2): ограничение
   (требования 1–2) и проверка запаса вычисляются ОДИН раз на шаг — до цикла
   попыток `runner._run_attempts` (`orchestrator/runner.py:889`), в
   `runner._run_developer_step` (`orchestrator/runner.py:302`) внутри
   `try/finally` снятия захвата зоны в `runner._cmd_run`
   (`orchestrator/runner.py:286–299`; решение Оператора, возврат 7, С-1);
   готовое число передаётся в каждую попытку. Записи-предупреждения
   требований 2 и 3 пишутся один раз на шаг.
   Захват зоны (решение Оператора, возврат 7, С-2): отказ по исчерпанному
   запасу (`SystemExit`) не оставляет захвата зоны — `finally` в
   `runner._cmd_run` снимает захват, как у прочих отказов до старта агента
   (`zone_lock.claimed_but_not_started`).
   Число процессов пользователя даёт одна функция
   `runner._user_process_count() -> int` (точка подмены, решение Оператора
   Н-1); её же зовёт строка `doctor` требования 6.
   Сбой счёта процессов пользователя (решение Оператора Н-3, вариант (б)):
   если `runner._user_process_count` не дала число (нет `ps`, отказ `fork`,
   таймаут — функция бросает исключение), шаг запускается с вычисленным
   ограничением, сравнение пропускается. В журнал задачи пишется ОДНА
   запись-предупреждение на шаг, не на попытку: «счёт процессов пользователя
   недоступен: <причина>». Прочие записи шага не меняются.
   Пустой вывод счёта либо код возврата 0 без числа в выводе (в том числе у
   подменённого в тестах `subprocess`, например `SpyRun`) — тот же исход
   «счёт недоступен»: `runner._user_process_count` бросает исключение
   (решение Оператора, возврат 4, п. 3).
   Независимость от PATH роли (решение Оператора Н-3): чтение
   `kern.maxprocperuid` и счёт процессов идут по абсолютным путям
   (`/usr/sbin/sysctl`; `ps` — тем же способом, что
   `liveness._ps_executable`, `orchestrator/liveness.py:89`) либо без
   подпроцесса.
4. Отказ `fork` у роли из-за ограничения — обычная ошибка внутри шага. Пульт
   продолжает работать, его команды и сессия Оператора запускают процессы.
5. По завершении шага любым исходом пульт снимает оставшуюся группу процессов
   шага. Механизм тот же, что на таймауте: `liveness.terminate_process_group`.
   Снятие идёт ДО вызова `runner.close_pump` в `runner._spawn_and_wait`
   (`orchestrator/runner.py:1876`). Снятие идёт только при
   `isinstance(agent_pid, int)` — то же условие, что у ветки таймаута
   (`orchestrator/runner.py:1864`): прежние тесты с подменным процессом
   агента не меняются. Запись в журнал шага появляется,
   только если в группе оставались процессы (текст —
   `liveness.group_kill_detail`). Текст записи «agent run finished» на
   обычном исходе не меняется.
6. Строка `doctor` показывает три значения: действующий `kern.maxprocperuid`
   (или «недоступен»), вычисленное ограничение шага и текущее число процессов
   пользователя. Ограничение строка берёт той же функцией
   `runner.role_nproc_limit`, что и шаг (решение Оператора О-5). Статус
   строки:
   - `warn`, если процессов пользователя не меньше ограничения шага (N ≥ M —
     та же граница, что отказ шага в требовании 3; решение Оператора О-5);
   - `warn` с пометкой «счёт недоступен», если
     `runner._user_process_count` не дала число (решение Оператора Н-3);
   - `ok` с пометкой «значение по умолчанию», если `kern.maxprocperuid`
     недоступен (в том числе на платформе без этого параметра);
   - `ok` в остальных случаях.
   Если недоступны оба источника (`kern.maxprocperuid` и счёт процессов),
   строка — `warn` и показывает обе пометки: «счёт недоступен» и «значение
   по умолчанию» (решение Оператора, возврат 4, п. 3).
   Строка переживает `FileNotFoundError` у вызова `sysctl` (исход
   «недоступен», не исключение `doctor`); если чтение идёт без подпроцесса —
   так же переживает сбой чтения (решение Оператора, возврат 5, П-2).

   Значение `kern.maxprocperuid` и признак «недоступен» строка берёт из
   `runner._read_maxprocperuid()` (исход не `"ok"` — недоступен), число
   процессов — из `runner._user_process_count()`; других источников этих
   значений у строки нет (решение Оператора Н-1).

   Строка зарегистрирована в наборе проверок `doctor`.

## Критерии приёмки

AC-1. Процесс, запущенный `runner.spawn_agent` с аргументом `nproc_limit`,
равным значению `runner.role_nproc_limit()`, несёт мягкий и жёсткий
`RLIMIT_NPROC`, равные этому значению; дочерний процесс читает своё
ограничение сам. Значение не выше текущих мягкого и жёсткого ограничений
пульта. `resource.getrlimit(RLIMIT_NPROC)` процесса теста (пульта) после
запуска равен прежнему. Без аргумента `nproc_limit` процесс, запущенный
`runner.spawn_agent`, несёт те же `RLIMIT_NPROC`, что процесс теста.
Шаг, запущенный через `runner.cmd_run`, зовёт `runner.spawn_agent` с
аргументом `nproc_limit`, равным значению `runner.role_nproc_limit()` того же
шага (проверка — подменой `runner.spawn_agent` и сверкой переданного
аргумента; решение Оператора, возврат 5, П-1): реализация, в которой шаг не
передаёт `nproc_limit`, этот критерий не проходит.

AC-2. Тест подменяет ограничение на «текущее число процессов пользователя +
10» (аргумент `nproc_limit`) и запускает через `runner.spawn_agent` дочерний
процесс, который пытается
породить до 90 процессов `sleep`. Критерий выполнен, если верно всё
перечисленное:
- дочерний процесс получает отказ `EAGAIN` раньше, чем исчерпает попытки
  (ноль успешных запусков допустим);
- процесс теста, у которого ограничения нет, после этого запускает процесс;
- все порождённые процессы завершаются в пределах теста.

AC-3. `runner._read_maxprocperuid` подменена и возвращает `(None, "failed")`
либо `(None, "absent")`. Тогда `runner.role_nproc_limit()` вычисляет
ограничение от `config.ROLE_NPROC_FALLBACK_MAXPROC` с тем же min по текущим
ограничениям. Журнал задачи:
- при `(None, "failed")` (сбой чтения на macOS) — ровно одна
  запись-предупреждение на шаг, в том числе когда шаг сделал больше одной
  попытки;
- при `(None, "absent")` (платформа без этого параметра) — ни одной
  записи-предупреждения.
На macOS при подменённом `subprocess`, у которого чтение `sysctl` дало пустой
вывод либо код 0 без числа, `runner._read_maxprocperuid` возвращает
`(None, "failed")`.

AC-4. `resource.getrlimit` подменена и возвращает для `RLIMIT_NPROC`
`(resource.RLIM_INFINITY, resource.RLIM_INFINITY)` (решение Оператора Н-4:
реализация вызывает `resource.getrlimit` через модуль — `import resource`, не
`from resource import getrlimit`). Тогда при `runner._read_maxprocperuid`, подменённой
на `(V, "ok")`, `runner.role_nproc_limit()` даёт V − `config.ROLE_NPROC_RESERVE`,
а при подменённой на `(None, "failed")` или `(None, "absent")` —
`config.ROLE_NPROC_FALLBACK_MAXPROC` − `config.ROLE_NPROC_RESERVE`.

AC-5. `runner._user_process_count` подменена и возвращает N, не меньшее
вычисленного ограничения M (в том числе N = M). Тогда шаг не запускается:
агент не порождён, отказ несёт причину «запас процессов пользователя
исчерпан: N из M», повторной попытки нет, Оператору открыта тревога (тот же
механизм тревог, что у прочих остановок цикла). Проверяется двумя прогонами:
- `runner.cmd_run` выходит `SystemExit` с этой причиной, агент не порождён;
- прогон через цикл `auto`: агент не порождён ни разу, цикл остановлен
  («run отказался стартовать»), тревога открыта, повторов шага нет;
- developer-шаг (задача в `in_dev`) при исчерпанном запасе: `runner.cmd_run`
  выходит `SystemExit` с этой причиной, и после отказа у задачи нет захвата
  зоны.

AC-6. Роль оставила процесс в группе шага, и шаг завершился обычным исходом.
Тогда после завершения шага этот процесс снят, а в журнале шага есть запись о
снятии группы. Если в группе не осталось процессов, такой записи нет.
Оставленный ролью процесс держит stdout агента: шаг завершается без ожидания
`config.PUMP_JOIN_TIMEOUT_SEC` и без записи «agent log INCOMPLETE».
Безопасность теста (решение Оператора, возврат 4, п. 5): оставленный ролью
процесс ограничен по времени — живёт не дольше 30 с; тест сам снимает группу
агента в завершении (`os.killpg`), в том числе в красной фазе, когда снятия
пультом ещё нет.

AC-7. Подменены только `runner._read_maxprocperuid` и
`runner._user_process_count` (в последнем случае списка — вместо первой
`subprocess.run`). Строка `doctor` из требования 6 даёт:
- `warn`, когда `runner._user_process_count` возвращает число не меньше
  ограничения шага (в том числе равное);
- `ok`, когда меньше;
- `ok` с пометкой «значение по умолчанию», когда `runner._read_maxprocperuid`
  возвращает `(None, "failed")` или `(None, "absent")`;
- `warn` с обеими пометками «счёт недоступен» и «значение по умолчанию»,
  когда `runner._read_maxprocperuid` возвращает `(None, "failed")` или
  `(None, "absent")`, а `runner._user_process_count` бросает исключение;
- `ok` с пометкой «значение по умолчанию» и без исключения `doctor`, когда
  `runner._read_maxprocperuid` не подменена, а подменённый `subprocess.run`
  бросает `FileNotFoundError` на запуск `sysctl` (`runner._user_process_count`
  подменена и возвращает число меньше ограничения); если чтение
  `kern.maxprocperuid` идёт без подпроцесса — тот же исход при сбое этого
  чтения (решение Оператора, возврат 5, П-2).
Ограничение, которое показывает строка, равно значению, которое
`runner.role_nproc_limit()` даёт шагу при тех же подменах.

AC-8. `runner._user_process_count` подменена и бросает исключение. Тогда:
- шаг запущен (агент порождён);
- в журнале задачи ровно одна запись-предупреждение «счёт процессов
  пользователя недоступен: <причина>» на шаг, в том числе когда шаг сделал
  больше одной попытки;
- строка `doctor` требования 6 даёт `warn` с пометкой «счёт недоступен».
То же верно, когда не подменена сама функция, а подменённый `subprocess`
дал на счёт процессов пустой вывод либо код 0 без числа.
Прежний тест `tests/test_agent_log.py:540` проходит без правки.

## Оценка объёма и деление
Сигналы объёма: в зоне 6 элементов, из них три общие зоны
(`orchestrator/config.py`, `docs/codebase-map.md`, `tests/`). Критериев
приёмки 8, бюджет $45 (ниже порога сигнала $60).

Если guard засчитывает сигнал по числу файлов зоны, делить не предлагается
(обоснование монолита — материал Оператору). Вычисление ограничения одно на
`runner` и `doctor`, и оба места читают одни константы `config`. Строка
`doctor` без ограничения шага показывала бы несуществующее значение. Без
строки `doctor` ограничение остаётся мержимым, но задача в сумме укладывается
в один класс калибровки, и отдельная подзадача добавила бы шагов дороже самой
строки. Решение — за Оператором на гейте SPEC.

  `plank-run`): они наследуют ограничение шага через процесс роли — принятое
  следствие.

  шагов всех задач и у канарейки — принятое следствие.

- Linux-специфичные механизмы (cgroups).
- Правка `docs/adr/0023-role-step-sandbox.md`: её п. 8 «нет лимитов числа
  процессов» устаревает, правит отдельно Оператор.
- Правка скилов сверх приложения требования 8.
- Правка файлов «только чтение» ТЗ: `orchestrator/liveness.py`,
  `orchestrator/providers/claude.py`, `orchestrator/providers/codex.py`,
  `orchestrator/role_git.py`, `orchestrator/gitcmd.py`,
