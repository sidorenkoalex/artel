# ТЗ: Метрика «трение»: непродуктивные токены шага в report

# ТЗ: Метрика «трение» — доля непродуктивных токенов шага

Источник: роадмап P3, строка «Метрика «трение»» ($15) — «обязана
существовать к go/no-go».

Суть: детерминированный разбор stream-json логов шагов
(`.artel/logs/<id>-<role>-N.log`) — какая доля токенов/событий шага
ушла не на предмет задачи: повторные чтения одного файла, ошибки
инструментов и ретраи вызовов, перечитывания больших кусков.
Точный состав сигналов «трения» — решение исполнителя в SPEC/PLAN
по фактическому формату логов (формат смотреть в живых логах;
парсер уже частично существует — `orchestrator/agent_log.py`,
учёт стоимости/токенов T040/T082).

Требуется:
1. Детерминированная функция расчёта метрики по логу шага (без LLM);
   агрегация на задачу (по шагам) и на корпус (по задачам).
2. Отображение — блоком в `artel report` (T092): трение по последним
   задачам, тренд; report остаётся read-only и самодостаточным.
3. Метрика считается лениво при генерации report (по файлам логов,
   доступным на машине; недоступные логи — честный пропуск, не
   ошибка) ЛИБО пишется в журнал по завершении шага — выбор
   исполнителя в SPEC с обоснованием (учесть retention логов:
   лог может быть уже вычищен prune).
4. Зоны: `orchestrator/agent_log.py` (расширение парсера),
   `orchestrator/report.py`, при выборе журнального пути — точка
   завершения шага. НЕ трогать: catalog/store-ядро, fsm-фиксации,
   ветко-чтения, guard, coldstart, canary — зона параллельной M1
   (T094); при конфликте зон — эскалация, не выход за границу.

Не входит: пороги/алерты по трению (сначала накопить фактуру);
регресс-флаги (отдельная строка B-вставки); правки формата логов.

Рамка: $15.
