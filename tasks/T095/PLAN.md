# PLAN: Метрика «трение» — доля непродуктивных токенов шага

## Подход

Выбор SPEC требование 4 — **вариант (а): ленивый расчёт при генерации
`report`**. Обоснование (SPEC AC-7):

- retention логов (`docs/retention.md`, `orchestrator/prune.py`) чистит
  файлы `.artel/logs/*.log` независимо от `state.db` — вариант (б)
  (запись в журнал по завершении шага) требовал бы либо считать метрику
  ДО того, как лог может быть вычищен (гонка с `prune`, которую нечем
  выиграть детерминированно), либо переживать её отдельным полем
  `steps`/`tasks` уже после прунинга — новая колонка в схеме БД, которую
  трогать эта задача не вправе (зона — `agent_log.py`/`report.py`, не
  `store.py`);
- вариант (а) не имеет этой проблемы по построению: `report` в момент
  генерации либо находит файл лога на диске и считает по нему, либо
  честно пропускает шаг — то же самое отсутствие данных, что уже
  показывают метрики T092 при пустой истории (`report._cost_per_done_task`
  → `None`, `report._gate_ratio` → пустой `_ratio`);
- вариант (а) не требует новой точки записи на завершении шага —
  изменения умещаются в уже разрешённые SPEC требование 5 два файла
  (`agent_log.py`, `report.py`), без прикосновения к `runner.py`/
  `checkpoint.py`, что снижает риск конфликта с параллельной T094 (зона
  guard/coldstart/canary) до нуля: эти файлы вообще не тронуты (AC-6/AC-8).

Плата за вариант (а) — трение задачи, у которой ВСЕ логи шагов уже
вычищены `prune`, в `report` попросту не отобразится (данных для
расчёта нет). Это принято осознанно: SPEC требование 3 просит «значения
по последним задачам» — у недавних задач логи, как правило, ещё не
вычищены (retention целится в старые), а алертов/порогов по пропущенным
данным SPEC явно запрещает (AC-9).

**Низкоуровневая функция** — `orchestrator.agent_log.step_friction
(log_path: Path) -> float`, сигнатура и модуль зафиксированы залоченными
приёмочными тестами (`tasks/T095/acceptance_tests/_sandbox.py`,
докстринг). Разбирает построчно реальный формат
`--output-format stream-json` (тот же приём, что `render_agent_line`/
`spend.stream_usage_tokens`: `raw_line.lstrip().startswith("{")`, иначе
строка — не JSON и пропускается) и выделяет вызовы инструментов
(`type: assistant`, блоки `tool_use`) вместе с их результатами
(`type: user`, блоки `tool_result`, связка по `tool_use_id`).

Числа usage (`step_tokens`/`stream_usage_tokens`, T040/T082) в фикстурах
приёмочных тестов НЕ участвуют (события собраны без поля `usage`) — SPEC
AC-1 сам допускает единицу измерения «токенов/**событий**», поэтому
знаменатель — число вызовов инструментов шага (событие = один вызов
инструмента), не токены. Токены логов и без того недоступны для многих
исторических логов (частичные/оборванные потоки, T040) — событийный
знаменатель работает при любом состоянии usage-данных, токенный работал
бы только при их наличии.

Три сигнала непродуктивности ТЗ, все — по вызовам инструментов, в
порядке появления в потоке; вызов может получить сразу несколько
сигналов — не считается дважды (множество id непродуктивных вызовов, не
сумма счётчиков):

1. **повторное чтение файла** — вызов `Read` с `file_path`, уже
   встречавшимся среди более ранних `Read` того же шага;
2. **ошибка инструмента и ретрай** — вызов, чей `tool_result` несёт
   `is_error: true` (сама ошибка), И следующий вызов с тем же именем
   инструмента и тем же ключевым аргументом (сам ретрай);
3. **перечитывание большого куска** — `tool_result.content`, длина
   которого ≥ `LARGE_TOOL_RESULT_CHARS` (модульная константа
   `agent_log.py`, не порог алерта — SPEC «не входит» про пороги
   касается порогов ГЕЙТОВАНИЯ метрики, не внутреннего размера
   «крупного» результата, без которого сигнал 3 попросту не отличить от
   обычного чтения), встретившийся текстом ранее в том же шаге —
   безотносительно к тому, каким инструментом/файлом получен (сигнал не
   привязан к `Read`, в отличие от сигнала 1: большой вывод `Bash`/`Grep`,
   повторённый дословно, — тот же паттерн).

Формула — `len(unproductive_call_ids) / len(tool_calls)`; шаг без
единого вызова инструмента (сплошной текст/размышление) — `0.0` (нечему
делить, и такой шаг по определению не тратит вызовы вхолостую).
Детерминированность — прямое следствие того, что вход и обход строго
последовательны, без часов/randomness/сети.

**Агрегация** (AC-2) — в `report.py`, тем же приёмом, что уже
существующие метрики гейтовой нагрузки T092 (чистые функции над уже
прочитанными данными, без новых чтений `store.py` сверх `all_tasks`,
которая и так уже читается):

- на задачу — среднее `step_friction` по ВСЕМ файлам `.artel/logs/
  <id>-*-*.log`, читаемым на диске (`config.LOGS.glob`), с честным
  пропуском (`try/except OSError`) отдельного лога, ставшего недоступным
  между `glob` и чтением (AC-5, гонка с `prune` уже во время самой
  генерации отчёта — маловероятна, но пропуск бесплатен и по коду
  идентичен пропуску полностью отсутствующего лога);
- на корпус — список пар (задача, среднее) по «последним» задачам
  (`store.all_tasks`, уже отсортированы по возрастанию `id`, берётся
  хвост) плюс тренд: сравнение среднего трения первой и второй половины
  ИЗВЕСТНЫХ (не `None`) значений этого списка — простейшая
  детерминированная мера направления без статистики (`statistics.median`
  и подобное — сигнатура регресс-флага, явно запрещённого AC-10).

**Отображение** (AC-3) — новая секция `<section>` в `_render()`,
заголовок несёт слово «трение» (буквальное имя метрики SPEC/ТЗ, как и
существующий заголовок «Метрики гейтовой нагрузки» T092), подзаголовок
«Тренд» — тем же приёмом markup-агностичной проверки, что уже
`_metrics_html` (просто текст, без попытки нарисовать график: SPEC не
просит графику, просто «значения» и «тренд»).

## Шаги

1. `orchestrator/agent_log.py`: приватные разборщики событий потока
   (`_tool_use_calls`, `_tool_results`), константа
   `LARGE_TOOL_RESULT_CHARS`, публичная `step_friction(log_path) ->
   float`. Юнит-тесты в `tests/test_agent_log.py` на форму трёх сигналов
   по отдельности и на границы (пустой лог, лог без единого
   `tool_use`) — приёмочные тесты (`tasks/T095/acceptance_tests/
   test_ac1_*.py`) уже покрывают направление и детерминизм, юниты
   добавляют покрытие деталей (несколько сигналов на одном вызове,
   отсутствие ложных срабатываний на непохожих ключах).
2. `orchestrator/report.py`: агрегаторы `_task_friction_values`
   (задача → среднее/число учтённых логов) и `_friction_trend`, рендер
   `_friction_html`, включение блока в `_render()`. Юнит-тесты в
   `tests/test_report.py` на агрегаторы (чистые функции над
   сфабрикованными списками задач/путями логов — тем же приёмом, что уже
   `RatioTest`/`GateRatioTest`) и на рендер (форма HTML, наличие слов
   «трение»/«тренд», честный пропуск задачи без логов).
3. Регенерация `docs/codebase-map.md` (`python3 scripts/codebase_map.py`
   — оба правленых файла в `orchestrator/`, conventions-core) тем же
   коммитом. Прогон `tasks/T095/acceptance_tests/` (залочены T023 —
   правка не в этой роли) и `scripts/guard.py` на diff; полного набора
   `tests/` (AC-12); `PLAN.md` → `status: ready`.

Один шаг = один MR по факту (Фаза 0, конвенция шаблона), три пункта
списка — последовательные подзадачи одного и того же MR.

## Влияние на систему

Зона изменений — строго `orchestrator/agent_log.py` (добавление функции
и приватных помощников, ни одна существующая публичная функция не
меняет сигнатуру/поведение — `render_agent_line`/`tee_lines`/
`stream_to_log`/`OutputPump` не тронуты, AC-11) и
`orchestrator/report.py` (добавление секции рендера и агрегаторов —
`cmd_report()` остаётся read-only относительно `state.db`: новые чтения
идут ТОЛЬКО в файлы `.artel/logs/`, ни одного `INSERT`/`UPDATE`, ни
одного вызова git, AC-4). `catalog.py`, `store.py`, `fsm*.py`,
`fixation.py`, `gitcmd.py`, `guard.py`, `coldstart.py`, `canary.py` —
не затронуты (зона параллельной T094).

Новых внешних зависимостей, сети, демонов — нет: `step_friction` читает
единственный файл `Path.read_text`, агрегация в `report.py` — то же
самое чтение файлов плюс уже существующие функции `store.py`. Формат
`--output-format stream-json`, который пишет CLI агента, не меняется —
`agent_log.py` расширяет РАЗБОР, не запись (AC-11); существующие
характеризующие тесты `tests/test_agent_log.py` на
`render_agent_line`/`tee_lines`/`OutputPump` продолжают идти без правок
как регресс-страховка.

Откат — удаление добавленных функций/секции и обратная регенерация
карты; `state.db`/файлы логов не меняются этой задачей ни в одной
ветке кода, откатывать в них нечего.

Задача не добавляет пороги/алерты (AC-9) и не добавляет регресс-флаги
(AC-10, `docs/roadmap.md` строка «регресс-флаги» — отдельная будущая
задача): блок трения — только числа и словесный тренд, без вызовов
`alerts.raise_alert` и без сравнения с медианой.

## Риски

- Событийный (не токенный) знаменатель — решение, зафиксированное здесь
  явно: если позже потребуется токенная версия метрики, это расширение
  сигнатуры/семантики `step_friction`, не эта задача (SPEC явно отдаёт
  выбор состава/порогов разработчику, требование 1).
- `LARGE_TOOL_RESULT_CHARS` — эвристический размер «крупного куска», не
  порог гейтования (AC-9 запрещает пороги ДЛЯ АЛЕРТОВ/гейтов метрики,
  не любую числовую константу в реализации сигнала; guard-тесты AC-9/
  AC-10 проверяют это же различие механически, по regex на
  `alerts.raise_alert`/имя `THRESHOLD`/`ПОРОГ`/`median`/
  `kind="threshold"" — ни один из паттернов в реализации не встречается).
