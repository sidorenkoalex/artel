# SPEC: CI быстрее — проверка на минимальной версии Python отдельным параллельным заданием; песочница FsmTest не сорит в каталог задач корня запуска

## Контекст
Замер Оператора 03.10.2026 по прогону CI `main`: задание `python`
(«Синтаксис и тесты оркестратора», `.github/workflows/ci.yml`) идёт
314 с — полный `tests/` параллельно (193 с) и затем, последовательно в
том же задании, `tests/test_invariants.py` на минимальной версии Python
в один процесс (110 с). Остальные задания CI идут 8–12 с, так что время
CI задаёт именно `python`; задача проходит CI ветки 1–4 раза и CI `main`
после мержа. Локально `tests/test_invariants.py` с `-n auto` — около 48 с
против 116 с в один процесс.

Отдельно: песочница `FsmTest` (`tests/test_invariants.py`) кладёт каталог
задачи `self.tdir = config.TASKS / <ULID>` в настоящий каталог задач корня
запуска и убирает его только `addCleanup`. Прерванный прогон оставляет
каталог в рабочей копии кода — случай 03.10: таймаут шага developer задачи
01M41AB597B330P2RCXCMVRZPE (18:13Z) оставил `tasks/01M41FFG8P1GFYHJJXD76AS4QQ`,
гейт зон отказал переходу.

`.github/workflows/ci.yml` и `tests/test_invariants.py` правятся
приложением к PLAN (ТЗ: «Приложением»).

## Требования
1. Проверка `tests/test_invariants.py` на минимальной объявленной версии
   Python выносится из задания `python` в отдельное задание CI, идущее
   параллельно заданию полного `tests/`, с теми же условиями запуска, что
   у задания `python`: `needs: changes` и его условие пропуска для пушей
   без кода (`if: ${{ !cancelled() && needs.changes.outputs.code != 'false' }}`).
2. В новом задании `tests/test_invariants.py` гоняется параллельно
   (`-n auto -p xdist`) с тем же таймаутом отдельного теста
   (`-o timeout=120`). Если на минимальной версии Python `-n auto` даёт
   нестабильность, это названо явно, и задание остаётся последовательным
   (требование 1 при этом сохраняется).
3. Покрытие и строгость не меняются: тот же набор тестов, та же минимальная
   версия из манифеста (`scripts/stack_ci.py --min`), те же зависимости из
   `requirements.lock`, та же сверка ссылок для полного прогона; ни один шаг
   не удаляется и не становится необязательным; новое задание красит прогон
   CI так же, как сейчас красит шаг.
4. Правка `.github/workflows/ci.yml` — приложением к PLAN, проверенным
   `git apply --check`. Тест или код пульта, читающий структуру `ci.yml`
   (имена заданий, шаги), поправлен в объёме переноса, перечень таких мест —
   в PLAN.
5. В PLAN — оценка времени задания `python` до и после по замерам CI ветки
   задачи (имена и длительности заданий из прогона ветки).
6. Песочница `FsmTest` в `tests/test_invariants.py` подменяет `config.TASKS`
   временным каталогом (как уже подменяет `DB`, `LOGS`, `WORKTREES`,
   `PROJECTS`); утверждения тестов не меняются. Правка — приложением к PLAN.
7. В `tests/` — сторож с заявкой «Ловит мутацию»: песочница `FsmTest` не
   пишет в каталог задач корня запуска.

## Критерии приёмки

AC-1. В `.github/workflows/ci.yml` (с применённым приложением PLAN) шаги
минимальной версии Python — определение версии `scripts/stack_ci.py --min`,
установка зависимостей из `requirements.lock` для неё и прогон
`tests/test_invariants.py` — стоят в отдельном задании, а не в задании
`python`; это задание не зависит от задания `python` (не перечисляет его в
`needs`), несёт `needs: changes` и то же условие `if:`, что задание `python`.

AC-2. В новом задании `tests/test_invariants.py` запускается с
`-n auto -p xdist` и `-o timeout=120`; либо, если на минимальной версии
Python параллельный прогон нестабилен, нестабильность названа в PLAN
(наблюдение из прогона), а задание запускает тот же файл последовательно с
`-o timeout=120`.

AC-3. Задание `python` после правки сохраняет все прочие шаги без изменения
их команд: версия Python из манифеста, зависимости из `requirements.lock`,
`py_compile`, снимок ссылок, `pytest tests -n auto -p timeout -p xdist -o
timeout=120`, сверка ссылок после прогона; ни у одного шага старого или
нового задания нет `continue-on-error` или иного признака необязательности,
и провал нового задания делает прогон CI красным так же, как провал шага
делал это до правки.

AC-4. Приложение PLAN к `.github/workflows/ci.yml` проходит `git apply
--check` на чистом дереве, и PLAN это подтверждает; PLAN перечисляет тесты
и код пульта, читающие структуру `ci.yml` (имена заданий, шаги), и каждый
затронутый переносом поправлен (либо PLAN фиксирует, что таких нет).

AC-5. PLAN содержит оценку времени задания `python` до и после правки с
именами и длительностями заданий из прогона CI ветки задачи.

AC-6. Приложение PLAN к `tests/test_invariants.py` подменяет в `FsmTest.setUp`
`config.TASKS` временным каталогом песочницы, `self.tdir` лежит под ним;
утверждения тестов файла не меняются, и `tests/test_invariants.py` проходит.

AC-7. В `tests/` есть тест с заявкой «Ловит мутацию», который проверяет, что
песочница `FsmTest` не создаёт и не оставляет каталог задачи в каталоге задач
корня запуска, и краснеет при возврате `self.tdir` в настоящий
`config.TASKS` корня запуска.

## Оценка объёма и деление
Сработавшие сигналы (guard): «затронут инвариантный механизм» (зона
`tests/` и правка `tests/test_invariants.py`) и «прогноз диффа не дан».

Прогноз диффа: 12 КиБ (два приложения — перенос ~4 шагов CI в новое
задание и подмена `config.TASKS` в `FsmTest.setUp` — плюс один файл
сторожа в `tests/`, при необходимости правка `tests/test_stack_ci.py`).

**Обоснование монолита** (материал для решения Оператора). Атомарной смены
механики здесь нет: часть CI (требования 1-5) и часть песочницы
(требования 6-7) технически независимы и мержимы по отдельности. Довод за
одну задачу — объём, а не неделимость: всего 7 критериев, 3 зоны, прогноз
~12 КиБ, обе правки — приложения к PLAN одного шага developer. Деление
удвоило бы число шагов analyst/test_author/reviewer при планке $25 на
каждую подзадачу против рамки Оператора $15 на всю работу. Механизм
инварианта (песочница `FsmTest`) затронут только подменой пути, утверждения
тестов не меняются (требование 6).
