# PLAN: WIP-чекпоинт после таймаута: зона роли и артефактная ветка

## Подход
Таблица «роль → мандат путей кодовой ветки» из ANSWER-1 реализуется
веткой `if role == "developer"` в `checkpoint.commit_timeout_checkpoint`:
`developer` коммитит в кодовую ветку весь worktree, кроме `tasks/<id>/`
(новый параметр `exclude` у `_commit_worktree_change` — `git reset -q --
<exclude>` ПОСЛЕ `add -A`, тем же приёмом, каким функция уже отделяет
«застейджено» от «закоммичено»); любая другая роль (`analyst`,
`test_author`, `reviewer`) не коммитит в кодовую ветку ничего — WIP вне
`tasks/<id>/` откатывается новой `_discard_out_of_mandate_changes`
(AC-2/AC-3).

Откат читает `git status --porcelain=v1 --untracked-files=all`, а не
`diff`, — только `status` различает «новый нетрекенный путь» (буква `?`
— `git checkout --` над ним не властен, путь без истории в HEAD) от
«изменение отслеживаемого» (`git checkout --` восстанавливает из HEAD).
Число строк для журнала (AC-3) — `git diff HEAD --numstat` (add+del) для
трекенных путей, длина файла для новых нетрекенных: тот же смысл
«сколько отброшено», что у обычного `diff --stat`, посчитанный вручную
там, где самого коммита для `--stat` ещё нет.

Перенос `tasks/<id>/` в артефактную ветку (AC-4/AC-5, требование 2) —
не новый код, а новый вызов уже существующей `_commit_external_step_
artifacts` (SPEC T094) из `commit_timeout_checkpoint`, для ЛЮБОЙ роли,
включая `developer`, ПОСЛЕ ветки код/откат выше. Новый параметр
`timeout: bool = False` добавляет пометку «WIP после таймаута» в
сообщение коммита артефактной ветки (AC-5) без изменения поведения при
`timeout=False` (обычный `commit_step_artifacts`, вызывающий эту же
функцию, не передаёт `timeout` вообще). Кандидат на удаление внутри
`_commit_external_step_artifacts` (AC-9, регресс) сверяется ПРЕФИКСОМ
общей части сообщения (`own_commit_marker`), не точным текстом — иначе
чередование обычного шага и обрыва по таймауту той же роли переставало
бы находить «последний коммит — автокоммит этой же роли» уже на второй
итерации (докстринг функции, наблюдение зафиксировано там же).

Ветка задачи была на 44 коммита позади `main` — зависимость по зонам
из SPEC («Не входит»), задача 01M1KVG3KSCY47HWXWF5HM0E76 («Автокоммит
артефактов шага учитывает .gitignore»), к моменту работы уже смержена в
`main`. Код-фаза начата подтяжкой `main` (см. коммит-мерж в истории
ветки) — единственный конфликт был в той же функции
`_commit_external_step_artifacts` (обе задачи трогают её): сведено так,
что фильтр `.gitignore` (`check_ignore`) применяется, как в `main`,
ДО вычисления `message`/`own_commit_marker` с пометкой таймаута — обе
правки не пересекаются по смыслу (одна решает «что считается файлом»,
другая — «как называется коммит»), просто делили один и тот же
диапазон строк. Карта кодовой базы перегенерирована отдельным шагом
подтяжки (конвенция).

## Шаги

1. `checkpoint._commit_worktree_change` — новый параметр `exclude`
   (`git reset -q -- <exclude>` после `add -A`).
2. `checkpoint._discard_out_of_mandate_changes` — новая функция: откат
   WIP вне `tasks/<id>/` для роли без мандата кода, строка для журнала.
3. `checkpoint.commit_timeout_checkpoint` — ветка по роли
   (`developer` → шаг 1 с `exclude=tasks/<id>`; иначе → шаг 2), плюс
   безусловный вызов `_commit_external_step_artifacts(..., timeout=True)`
   для ЛЮБОЙ роли.
4. `checkpoint._commit_external_step_artifacts` — параметр
   `timeout: bool`, пометка сообщения, сверка удаления по префиксу.
5. Юнит-тесты (`tests/test_timeout_checkpoint.py`,
   `tests/test_checkpoint_external_step_artifacts.py`) — по одному
   случаю на AC-1..AC-6, плюс приёмочные тесты test_author (AC-7/AC-8,
   уже красные до этой правки, зафиксированы шагом test_author) —
   зелёные без правки самих тестов.
6. Подтяжка `main` (зависимость по зонам из SPEC уже смержена) —
   разрешение конфликта в той же функции, регенерация карты кодовой
   базы.

## Влияние на систему
Затронут только `checkpoint.py` — единственная точка WIP-чекпоинта
таймаута (`commit_timeout_checkpoint`) и уже существующая точка переноса
артефактов (`_commit_external_step_artifacts`, SPEC T094). Точка вызова
(`runner.py:619`) и резолвер роли (`config.STATE_ROLE`) не тронуты —
роль уже приходит туда как параметр, правка только использует её.

Не ослабляет ни один существующий инвариант: `commit_abnormal_checkpoint`
и `commit_pause_now_checkpoint` не меняются и не получают `exclude` —
у них нет мандата в SPEC, поведение прежнее (единственная строка,
которую это могло бы задеть, — сигнатура `_commit_worktree_change`,
новый параметр `exclude` необязательный со значением по умолчанию
`None`, оба других вызывающих не передают его, поведение идентично
прежнему).

Фильтр `.gitignore` (`check_ignore`, задача 01M1KVG3KSCY47HWXWF5HM0E76,
уже в `main`) в `_commit_external_step_artifacts` не тронут этой
правкой по существу — только раздвинут по месту в теле функции при
сведении подтяжки, логика (что игнорируется) идентична смерженной из
`main`.

Откат: правка локализована в четырёх функциях одного файла
(`checkpoint.py`) — реверт коммита возвращает прежнее безусловное
поведение `commit_timeout_checkpoint` (весь worktree в кодовую ветку
независимо от роли) без остаточного состояния (новых таблиц/миграций
схемы нет; журнальные записи — обычные строки `store.journal`, ничем
не отличаются от прочих по схеме).

Регрессионный щит: планка A7 (существующие тесты `tests/`) прогнана
целиком после подтяжки `main` и сведения конфликта — зелёная (AC-9);
приёмочные тесты `tasks/01M1NBWTSXEJB24PXR417YF1VA/acceptance_tests/`
(зафиксированы test_author, локальная правка запрещена) — зелёные без
единой правки их текста.

## Риски
`_discard_out_of_mandate_changes` удаляет с диска новые нетрекенные
файлы напрямую (`path.unlink()`), не через git (`checkout --` не
властен над путём без истории в HEAD) — необратимо для конкретного
файла в рамках этого чекпоинта, но это ровно то, что требует SPEC
(«откатываются») для WIP вне мандата роли; артефакты `tasks/<id>/` эту
функцию не видят (исключены префиксом до сбора списка), риска потери
результата роли нет.
