# PLAN: Канарейка на наборе ролей: провайдер и модели ролей в клоне, бейзлайн по набору

## Подход

Набор живёт ровно в двух местах: в локальном слое пульта (чтение,
`canary_sets:`) и в локальном слое эфемерного клона (запись, собранная
прогоном). Ни `roles.yaml`, ни `models.yaml`, ни один файл главной копии
прогоном не меняются — `config.MODELS_LOCAL` уже переадресован в клон
(`canary._CLONE_CONFIG_ATTRS`), и этого канала достаточно для обеих
половин: модели ролей (`tiers:`) и их провайдера (новый ключ
`role_providers:`, читает `roles.provider`).

Ключевые решения.

1. **Разбор набора — в `orchestrator/models.py`**, рядом с разбором
   остального локального слоя (`load_local`), а не в `canary.py`: формат
   слоя — предмет одного модуля, и `doctor` обязан читать набор тем же
   разбором, каким его читает прогон. Новые входы:
   `models.load_canary_sets()` (отображение «имя набора → роль →
   `CanarySetRole(provider, model)`») и `models.local_template_layer()`
   (ярусы ШАБЛОНА разобранными — источник ярусов, которых набор не
   называет). `LocalLayer` получает четвёртое поле `role_providers`.

2. **Провайдер роли — переопределение в `roles.provider`**, ПОСЛЕ
   сегодняшнего чтения записи роли: роль, не описанная в `roles.yaml`,
   по-прежнему `RolesError` с прежним текстом, и только уже разрешённое
   значение поля `provider:` замещается слоем. Слоя нет или он не
   разобран — `None`, то есть прежнее поведение байт-в-байт (о нечитаемом
   слое говорит своя строка `doctor`; тот же приём защитной деградации,
   что у `providers.name_for_role`).

3. **Карта `role_providers:` слоя клона покрывает КАЖДУЮ agent-роль,
   чей ярус набор сдвинул**, а не только роли, названные набором. Это
   единственное место, где два требования SPEC сходятся в одной точке и
   требуют выбора, поэтому решение названо явно: слой клона ключуется
   ЯРУСОМ (требование 4, отказ 6г), а все четыре agent-роли сегодняшнего
   `roles.yaml` стоят на ярусе `strong`. Набор «один developer на Codex»
   неизбежно переводит на модель Codex и `analyst`, и `test_author` — их
   модель приходит из того же яруса. Если оставить их провайдера как в
   `roles.yaml` (буквальное чтение «роль, не названная в наборе, идёт как
   в наборе по умолчанию», требование 3), то предполёт ИХ шага в клоне
   отказал бы расхождением «провайдер роли ≠ провайдер её модели»
   (`doctor.check_model_provider_cli`, вызывается по конкретной роли,
   `preflight.py:676`) — то есть ЛЮБОЙ набор ронял бы прогон на первом же
   шаге analyst, и вся механика была бы неработоспособна с рождения.
   Провайдер яруса при этом определён однозначно: модель одна на ярус
   (отказ 6г), а её провайдер обязан совпадать с провайдером записи
   набора (отказ 6д). Требование 3 остаётся в силе там, где оно
   проверяемо, — для роли, чей ярус набор НЕ называет (её модель и её
   провайдер остаются шаблонными). Форма карты — та, которую требует
   требование 5 и AC-5: «роль → провайдер», не «ярус → провайдер».

4. **Отказы по набору — в `canary.cmd_canary` ДО `_resolve_target_sha` и
   до `_ephemeral_clone`** (требование 6): за опечатку в имени набора
   Оператор не платит ни `git clone`, ни строкой в `tasks`. Один вход
   `canary._set_plan(set_name)` отдаёт `CanarySetPlan(name, entries,
   layer_text, summary)` либо именованно отказывает; имя набора по
   умолчанию (`config.CANARY_DEFAULT_SET`) в `canary_sets:` не ищется
   вовсе и локального слоя не читает — ветка «как пульт» остаётся
   байт-в-байт прежней (AC-14), включая нульарный вызов
   `_ephemeral_clone()`, от которого зависит залоченная планка задачи
   01M1SC3Y20YBTTJVQDJBF2NDQW.

5. **Слой клона пишется ПОСЛЕ `catalog.cmd_init()`**, перезаписывая
   положенный им шаблон, а не до него: порядок «сначала слой, потом
   init» работал бы только за счёт того, что `models.ensure_local_template`
   не трогает существующий файл, — зависимость неочевидная и ломкая.

6. **Ключ бейзлайна — пара (шаблон, набор)** сменой PRIMARY KEY таблицы
   `canary_baseline` с переносом строк (`ALTER TABLE ... RENAME` +
   `INSERT ... SELECT` + `DROP`), не `DROP TABLE`: живые бейзлайны
   (13.09, $6.54) — единственная точка сравнения прогонов, и терять их
   миграцией нельзя (AC-8). Новые колонки `canary_runs`
   (`set_name`, `models_summary`) стоят и в `CREATE TABLE IF NOT EXISTS`,
   и в цепочке `add_column` — на свежей БД `ALTER TABLE` не выполняется
   вовсе (класс TOCTOU-гонки, `tests/test_store_schema_migration_parity.py`).

7. **Зелёная канарейка для пина — только набор по умолчанию.**
   `store.green_canary_runs` получает параметр `set_name` со значением по
   умолчанию `config.CANARY_DEFAULT_SET` и фильтрует по нему. Иначе
   документированное правило требования 10 («прогон на другом наборе
   зелёной канарейкой для сдвига пина не считается») держалось бы ТОЛЬКО
   текстом документа, а код двигал бы пин по прогону конвейера, которым
   пульт не работает: оба потребителя (`canary.merges_since_last_green_run`
   для `pin.cmd_pin_update`/`doctor.check_canary_trigger` и
   `store.latest_green_canary_run` для `pin.cmd_pin_to`) ходят через эту
   одну функцию. Правило только ужесточает существующий гейт и ни одного
   существующего вызова не меняет: все сегодняшние строки прогонов
   миграция размечает набором по умолчанию.

Архитектурно значимого решения, требующего ADR, здесь нет: новый ключ
локального слоя и новая колонка метрик — расширение уже принятых
механик (три слоя моделей, ленивые таблицы канарейки).

## Влияние на систему

**Что затрагивается за пределами непосредственной правки.**

- `roles.provider` — самый горячий из изменённых входов: его зовут
  `providers.name_for_role` (каждый шаг роли), `providers.role_providers`
  (`doctor`), `stack.model_providers`. Добавляется одно чтение файла
  локального слоя на вызов. Поведение без ключа `role_providers:`
  (сегодняшний слой и шаблон) — прежнее значение, прежние исключения,
  прежний порядок проверок; файл нечитаем — тоже прежнее значение.
- `store.green_canary_runs`/`latest_green_canary_run` — гейт сдвига пина
  (`pin.cmd_pin_update`, `pin.cmd_pin_to`) и триггер
  `doctor.check_canary_trigger`. Фильтр по набору только УЖЕСТОЧАЕТ гейт
  (прогон чужого набора перестаёт годиться для сдвига пина, см. решение 7
  «Подхода»); все существующие строки миграция размечает набором по
  умолчанию, поэтому для сегодняшней БД ответ функции не меняется.
- `models.LocalLayer` — четвёртое поле. Ни один код вне `models.py` этот
  namedtuple не конструирует (проверено `grep "LocalLayer("`), поэтому
  распаковки по позиции не ломаются.
- `models.LOCAL_TEMPLATE` — текст шаблона меняется, а его кладут `init` и
  `doctor --fix`. Существующий файл Оператора не перезаписывается
  (`ensure_local_template`), то есть на живом пульте раздел-образец
  появится только у нового клона; сверку шаблона с
  `docs/reference/models-local.example.yaml` держит существующий тест.

**Инварианты, гейты, лимиты и тесты рядом — и почему не ослабляются.**

- `tests/test_canary.py::CloneConfigAttrsInvariantTest` (каждый путь
  `config` под `ROOT/.artel` либо переадресован в клон, либо освобождён с
  причиной) — новых путей `config` задача не заводит, списки не трогает.
- `tests/test_store_schema_migration_parity.py` — про колонки `tasks`;
  задача их не добавляет. Тот же КЛАСС дефекта (колонка только в цепочке
  `add_column`) в таблицах канарейки закрыт решением 6 «Подхода».
- `doctor.check_model_provider_cli` — блокирующая проверка предполёта; не
  ослабляется, наоборот, решение 3 «Подхода» существует именно ради того,
  чтобы она оставалась зелёной в клоне честно, а не в обход.
- Существующие тесты бейзлайна (`CanaryBaselineStoreRoundtripTest`,
  включая `test_second_write_overwrites_the_same_title`) приводятся к
  новой схеме БЕЗ правки: новые параметры имеют значение по умолчанию
  «набор по умолчанию», и перезапись по тому же `title` остаётся
  перезаписью той же строки.
- Ни один тест, гейт, лимит или guard-проверка не удаляется и не
  ослабляется; приёмочная планка задачи залочена и не правится.

**Как откатить.** Revert одного merge-коммита. Единственный необратимый
след — форма таблицы `canary_baseline` в уже миграцированной БД: после
revert'а колонка `set_name` остаётся, а прежний код пишет и читает по
`title` (колонка не в `NOT NULL`, PRIMARY KEY пары шире прежнего), то
есть строки остаются читаемыми по прежнему ключу. Новых файлов на диске
прогон не оставляет: слой набора живёт внутри эфемерного клона и
уничтожается вместе с ним.

## Риски

- **Потолок задачи $45 ниже калибровки (~$85).** Расхождение назвал сам
  SPEC («Оценка объёма и деление») как материал решения Оператора на
  гейте, и гейт SPEC был пройден с рамкой $45 — то есть решение уже
  принято тем, кто вправе его принимать. Однократная переоценка потолка
  на PLAN (ADR-0014 п.3) поэтому НЕ используется: поднимать её значило бы
  переигрывать явное решение Оператора, а не сообщать ему число, которого
  он не видел. Если работа упрётся в потолок, это операторская команда
  `budget`, а не правка PLAN — второго шанса у канала PLAN уже не будет.
- **Ярус `strong` у всех четырёх agent-ролей** делает любой набор
  сдвигом яруса целиком (решение 3 «Подхода»). Пока это так, набор
  «только developer на Codex» физически не отличим от «все agent-роли на
  Codex» по МОДЕЛИ — отличим только по записи набора и по сводке прогона.
  Разведение ролей по ярусам — правка `roles.yaml`, защищённый путь и
  отдельное решение Оператора; задача его не делает и не предполагает.
- **Тариф модели набора в клоне** переносится из локального слоя пульта
  только для моделей САМОГО набора (требование 4). Модель, на которую
  указывает ярус шаблона (`claude-opus-5`), переопределения пульта в
  клоне не получает — ровно как и сегодня, когда слой клона есть чистый
  шаблон; расширять перенос на модели шаблона значило бы менять метрику
  прогона по набору по умолчанию, то есть ломать AC-14.

## Предложения системе

- `config.ROLES`/`config.MODELS` якорятся на РЕАЛЬНЫЙ корень при загрузке
  модуля и сознательно не входят в `canary._CLONE_CONFIG_ATTRS`: внутри
  эфемерного клона карта исполнителей и каталог моделей читаются из
  ГЛАВНОЙ копии, а не из checkout'а целевого sha. Для этой задачи разницы
  нет (оба файла — защищённые пути и меняются редко), но прогон
  канарейки на sha, где `roles.yaml`/`models.yaml` отличаются от пина,
  тестирует не тот состав ролей, который заявлен целевым sha. Класс:
  «клон канарейки не полностью изолирован от главной копии».
- `skills/coding-standards.md` не описывает случай, когда два требования
  одного SPEC пересекаются в одной точке и буквальное исполнение обоих
  невозможно (здесь — требования 3 и 4/6г, решение 3 «Подхода»): правило
  говорит либо «не выбирать интерпретацию на свой вкус», либо
  «эскалировать», а середина — «выбрать единственное работоспособное
  прочтение и назвать выбор в PLAN» — не описана, хотя встречается.
