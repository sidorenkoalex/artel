# SPEC: Канарейка на наборе ролей: провайдер и модели ролей в клоне, бейзлайн по набору (задача 6б линии Codex)

## Контекст

Канарейка сегодня всегда гоняет роли на Claude: эфемерный клон
(`orchestrator/canary.py`, `_ephemeral_clone`) переадресует
`MODELS_LOCAL` на свой каталог и зовёт `catalog.cmd_init()`, который
кладёт шаблон `models.LOCAL_TEMPLATE` — все ярусы на `claude-opus-5`;
`provider:` у ролей в `roles.yaml` целевого sha не задан, значит
`orchestrator/roles.py::provider` отдаёт `claude`. Прогнать конвейер на
ролях другого провайдера нечем: параметра провайдера или набора ролей у
команды нет, а перевод роли на Codex требует правки защищённого
`roles.yaml` в главной копии — то есть боевого перевода пульта, а не
пробного прогона.

Бейзлайн при этом ключуется ТОЛЬКО именем шаблона пула
(`canary_baseline.title` PK, `orchestrator/store.py`): прогон на другом
наборе моделей сравнивался бы с бейзлайном прежнего набора и переписывал
бы его. Цена уже видна на одной модели: бейзлайн шаблона
`canary-version-json` снят 13.09 на $6.54, прогоны 26.09 дали $16.97 и
$17.66 — предупреждение «отклонение сверх 50%» на каждом прогоне.

Задача даёт канарейке именованный набор «роль → (провайдер, модель)»,
действующий только внутри эфемерного клона, и бейзлайн, ключуемый этим
набором. Живого Codex она не запускает и ни одной роли пульта на Codex
не переводит.

## Требования

1. **Флаг набора.** Команда — `canary --k <N> [--sha <sha>] [--set
   <имя>]`. Без `--set` действует набор по умолчанию (имя набора —
   константа кода, например `default`). `--set` без значения следующим
   аргументом — именованный отказ, тем же приёмом, что `_sha_arg`
   (`orchestrator/artel.py`). Подкоманда `canary pool-seal` `--set` не
   принимает и разбирается, как сегодня, до флагов.

2. **Формат набора.** Набор живёт в локальном слое пульта
   (`config.MODELS_LOCAL`, файл вне git) под новым ключом верхнего
   уровня `canary_sets:` — отображение «имя набора → {роль: {provider,
   model}}»:

   ```yaml
   canary_sets:
     codex-strong:
       developer: {provider: codex, model: gpt-5.6-terra}
       reviewer:  {provider: codex, model: gpt-5.6-terra}
   ```

   Обоснование формата (требование ТЗ «формат обосновать в SPEC»):
   ключ верхнего уровня в уже существующем локальном слое, а не новый
   файл — выбор конкретного пульта (какие подписки и CLI на этой
   машине) лежит ровно в том слое, что и ярусы, и уже переадресуется в
   клон (`canary._CLONE_CONFIG_ATTRS`, `MODELS_LOCAL`), то есть не
   требует ни нового пути `config`, ни новой записи в инварианте
   переадресации (`tests/test_canary.py::CloneConfigAttrsInvariantTest`).
   Ключ набора — имя роли (не ярус), потому что ТЗ задаёт набор именно
   как «роль → (провайдер, модель)» и потому что провайдер — поле роли.
   Обе половины (`provider`, `model`) обязательны у каждой записи: роль
   с моделью без провайдера (и наоборот) — ровно то расхождение, за
   которым сегодня следит `doctor.check_model_provider_cli`.
   Набор вправе называть подмножество ролей; роль, не названная в
   наборе, идёт как в наборе по умолчанию (требование 3) — иначе
   прогон «один developer на Codex» требовал бы переписать все роли.

3. **Набор по умолчанию.** Набор по умолчанию воспроизводит сегодняшнее
   поведение байт-в-байт: локальный слой клона — текст
   `models.LOCAL_TEMPLATE` (как его кладёт `catalog.cmd_init()` сегодня),
   провайдер ролей — из `roles.yaml` целевого sha, argv команды шага
   роли не меняется. Именно это значение ТЗ называет набором «как
   пульт», и именно эту читку фиксирует требование 6 ТЗ («набор по
   умолчанию воспроизводит сегодняшнее поведение байт-в-байт (argv,
   шаблон слоя)»): живой локальный слой Оператора в клон по-прежнему не
   попадает — иначе правка слоя по ходу прогона меняла бы модель
   синтетических шагов, против чего заведена переадресация
   `MODELS_LOCAL`.

4. **Локальный слой клона из набора.** При `--set <имя>` клон получает
   локальный слой, собранный из набора, а не шаблон `LOCAL_TEMPLATE`:
   `tiers:` — ярус каждой названной роли (`roles.model_tier` целевого
   sha) на модель набора, ярусы остальных ролей — как в шаблоне;
   `allow_experimental:` — `true` для каждой модели набора со статусом
   `experimental` в каталоге; `overrides:` — переопределения тарифа
   выбранных моделей, снятые из локального слоя пульта ДО клона (если
   они там есть), чтобы стоимость шага в клоне считалась по тарифу
   пульта, а не по прейскуранту каталога.

5. **Провайдер ролей в клоне.** Провайдер роли в клоне берётся из
   набора способом, не требующим правки `roles.yaml` ни в главной
   копии, ни в клоне: переопределяющая карта «роль → провайдер» живёт в
   том же локальном слое клона (новый ключ, собираемый вместе со слоем
   требования 4) и читается `orchestrator/roles.py::provider` как
   переопределение поля `provider:` роли. Обоснование: `roles.yaml` —
   защищённый путь и приходит из целевого sha, а локальный слой уже
   переадресован в клон и уже несёт «выбор этого пульта»; ключа нет —
   `provider` ведёт себя байт-в-байт как сегодня (поле роли, иначе
   `providers.DEFAULT_PROVIDER`).

6. **Отказы до клона.** Каждый из случаев ниже — именованный отказ
   команды ДО создания эфемерного клона (ни `git clone`, ни задачи в
   БД): (а) `--set` называет набор, которого нет в `canary_sets:`
   (текст называет известные имена); (б) набор называет роль, которой
   нет в `roles.yaml` целевого sha; (в) набор называет модель, которой
   нет в каталоге `models.yaml`; (г) набор даёт двум ролям ОДНОГО яруса
   разные модели — слой клона ключуется ярусом (требование 4) и такой
   набор в нём невыразим; (д) провайдер роли в наборе не совпадает с
   провайдером её модели в каталоге — та самая пара, которую
   `doctor.check_model_provider_cli` называет расхождением, и пускать её
   в клон значит купить оплаченную попытку чужого CLI.

7. **Бейзлайн и прогоны по набору.** Ключ `canary_baseline` — пара
   (имя шаблона, имя набора); строка `canary_runs` несёт имя набора и
   сводку «роль → модель» прогона. Миграция схемы сохраняет
   существующие строки обеих таблиц как строки набора по умолчанию, с
   прежними значениями метрик (образец —
   `tests/test_store_schema_migration_parity.py`). Отклонение
   (`canary._deviation_exceeds`, `config.CANARY_DEVIATION_RATIO`)
   считается против бейзлайна ТОГО ЖЕ набора; первый штатный прогон
   набора заводит его бейзлайн ровно так же, как сегодня первый прогон
   шаблона. Имя набора и модели ролей видны в выводе `canary` и в
   строке журнала прогона.

8. **Стоимость шага в клоне.** Канарейка стоимость не пересчитывает:
   метрики задачи читают `spent_usd` задачи, как сегодня. Провайдер без
   стоимости из CLI (`cost_from_cli: false`) считается по тарифу
   каталога тем же кодом пульта, что и вне канарейки; метрики прогона
   от провайдера не зависят.

9. **Doctor.** Согласованность наборов проверяется строкой `doctor`:
   каждый набор ссылается на существующие роли, на модели каталога и на
   известных реестру провайдеров. Статус: `fail` — битая ссылка (роль,
   модель или провайдер); `warn` — наборов в локальном слое нет вовсе;
   `ok` — наборы согласованы. Модель со статусом `experimental` в
   наборе сама по себе `fail` не даёт — разрешение на неё собирается в
   слой клона (требование 4).

10. **Документация.** `docs/stack.md` (раздел про канарейку/провайдеров)
    описывает набор: формат `canary_sets:`, флаг `--set`, что набор
    действует только внутри клона и ни одной роли пульта не переводит.
    `docs/operator-session.md` рядом с пунктом «Обновление пина после
    починки — только после зелёной канарейки» несёт: канарейка на
    наборе, отличном от набора по умолчанию, гоняется по требованию и
    зелёной канарейкой для сдвига пина не считается.
    `docs/reference/models-local.example.yaml` несёт закомментированный
    образец `canary_sets:` (тот же текст, что `models.LOCAL_TEMPLATE`,
    — сегодня их сверяет тест). Текст usage в `orchestrator/artel.py`
    называет `--set`.

11. **Тесты.** Новые тесты покрывают: разбор `--set` и отказы
    требования 6 до клона; сборку локального слоя клона из набора
    (подмена clone/init приёмом
    `tests/test_canary.py::EphemeralCloneConfigRemapTest`); провайдер
    ролей в клоне по набору; бейзлайн, отклонение и строку прогона по
    набору; миграцию, сохраняющую старые строки; тождество набора по
    умолчанию сегодняшнему поведению; независимость метрик от
    провайдера; строку `doctor`. Живой Codex не запускается — всё
    синтетическое.

## Критерии приёмки

AC-1. `canary --k <N> --set <имя>` разбирается: имя набора доезжает до
`canary.cmd_canary` отдельным параметром; без `--set` параметр несёт имя
набора по умолчанию; `--set` последним аргументом без значения — отказ с
названной причиной, без прогона.

AC-2. `--set` с именем, которого нет в `canary_sets:` локального слоя, —
отказ с названной причиной и перечнем известных имён, до создания
эфемерного клона (ни одного `git clone`, ни одной строки в `tasks`).

AC-3. Битый набор — отказ с названной причиной до клона, по случаю на
каждый: (а) роль вне `roles.yaml`; (б) модель вне каталога
`models.yaml`; (в) две роли одного яруса с разными моделями; (г)
провайдер роли не совпадает с провайдером её модели в каталоге.

AC-4. При `--set <имя>` локальный слой клона собран из набора, а не из
`models.LOCAL_TEMPLATE`: ярус каждой названной роли указывает на модель
набора, ярусы остальных ролей — как в шаблоне, каждая
`experimental`-модель набора разрешена записью `allow_experimental`,
переопределения тарифа выбранных моделей из локального слоя пульта
перенесены в `overrides:` слоя клона.

AC-5. В клоне при `--set <имя>` `roles.provider(<роль набора>)` отдаёт
провайдера набора, а `roles.yaml` ни в клоне, ни в главной копии не
изменён (содержимое файла совпадает с содержимым целевого sha).

AC-6. Для набора, прошедшего проверки AC-3, проверка
`doctor.check_model_provider_cli(<роль набора>)` в клоне не отдаёт
`fail` по причине «провайдер роли ≠ провайдер её модели».

AC-7. Бейзлайн ключуется парой (имя шаблона, имя набора): первый штатный
прогон набора заводит его бейзлайн с пометкой «бейзлайн создан»; прогон
набора A по тому же шаблону не читает и не перезаписывает бейзлайн
набора B.

AC-8. БД со строками `canary_baseline`/`canary_runs`, заведёнными до
этой задачи, после миграции несёт те же строки под именем набора по
умолчанию, с прежними значениями `steps`, `cost_usd`,
`review_iterations`; ни одна строка не потеряна.

AC-9. Строка `canary_runs` прогона несёт имя набора и сводку «роль →
модель», по которой прогон шёл.

AC-10. Вывод `canary` по прогону и строка журнала называют имя набора и
модели ролей набора.

AC-11. Отклонение считается против бейзлайна того же набора: метрика в
пределах `CANARY_DEVIATION_RATIO` от бейзлайна СВОЕГО набора не поднимает
ни предупреждения, ни алерта, даже если она вне порога бейзлайна другого
набора по тому же шаблону; превышение порога своего набора — поднимает.

AC-12. Метрики задачи-канарейки не зависят от провайдера: при одинаковых
`spent_usd`, числе шагов и итераций ревью сводка задачи совпадает для
роли на `claude` и на провайдере с `cost_from_cli: false`; собственного
пересчёта стоимости канарейка не делает (стоимость читается из
`spent_usd` задачи).

AC-13. Строка `doctor` по наборам: `fail` с названием битой ссылки, если
набор называет несуществующую роль, модель вне каталога или неизвестного
провайдера; `warn`, если наборов в локальном слое нет; `ok` при
согласованных наборах; набор с `experimental`-моделью каталога `fail` не
даёт.

AC-14. Прогон без `--set` воспроизводит сегодняшнее поведение
байт-в-байт: текст локального слоя клона совпадает с
`models.LOCAL_TEMPLATE`, провайдер ролей берётся из `roles.yaml` клона,
argv команды шага роли не изменился.

AC-15. Документация: `docs/stack.md` описывает формат `canary_sets:` и
флаг `--set`; `docs/operator-session.md` несёт правило «канарейка на
наборе, отличном от набора по умолчанию, — по требованию и не считается
зелёной канарейкой для сдвига пина»;
`docs/reference/models-local.example.yaml` несёт образец `canary_sets:` и
по-прежнему совпадает с шаблоном локального слоя по своей сверке; usage
`orchestrator/artel.py` называет `--set`.

AC-16. `tests/test_canary.py`, `tests/test_doctor_canary_pool.py`,
`tests/test_models_doctor.py`, `tests/test_store_schema_migration_parity.py`
зелёные, ни один существующий тест не удалён и не ослаблен; ни один тест
задачи не запускает живой CLI провайдера.

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (11 путей
против порога `SPLIT_SIGNAL_ZONE_FILES` = 5); число критериев приёмки
(16 против порога `SPLIT_SIGNAL_AC_COUNT` = 10). Прогноз диффа —
70 КиБ (`diff_forecast_kib` во frontmatter), ниже половины потолка гейта
ёмкости, отдельным сигналом не становится. Бюджет $45 ниже порога
`SPLIT_SIGNAL_BUDGET_USD` = 60 и сигналом не становится.

Решение — **монолит**. Что нельзя разрезать: набор и бейзлайн по набору
— одна смена механики. Часть «только `--set`» (набор доезжает до клона,
бейзлайн остаётся ключуемым именем шаблона) мержима технически, но
оставляет систему в состоянии ХУЖЕ сегодняшнего: первый же прогон на
Codex-наборе либо заведёт бейзлайн шаблона по чужому набору, либо
сравнится с бейзлайном Claude и поднимет алерт отклонения, а этот же
бейзлайн — вход гейта сдвига пина (зелёная канарейка,
`canary.merges_since_last_green_run`/`pin`). Обратная часть («только
бейзлайн по набору») бессмысленна отдельно: набора, по которому его
ключевать, ещё нет. Границы зон делению тоже не помогают:
`orchestrator/canary.py` — единственное место и сборки слоя клона, и
сверки с бейзлайном, и его пришлось бы резать поперёк, а часть без
своего куска этой зоны не мержима.

Калибровка: по числу файлов зоны (11, класс «8 и более файлов»)
ориентир `BUDGET_CALIBRATION_TABLE` — ~$85. Рамка Оператора в ТЗ — $45,
и в `budget_usd` стоит она; гейт SPEC на этой паре напечатает «рамка
ниже калибровки: $45.00 против ~$85.00». Разрыв назван здесь как
материал для решения Оператора на гейте: либо поднять потолок задачи,
либо принять монолит в рамке $45.
