# ТЗ: Зоны сверяет пульт: new --tz и гейт SPEC отказывают по неклассифицированному пути

Источник: бэклог docs/backlog.md, строка П1 «Зоны задачи сверяет пульт,
не память ассистента: new --tz и spec_gate отказывают по
неклассифицированному пути» (решение Оператора 12.09 «вноси в бэклог»).
Решение Оператора 19.09: заводить сейчас.

Факты:
- Четыре отказа гейта зон по одной причине: файл назван в тексте ТЗ или
  SPEC, но не в зонах (06.09: answer.py, doctor.py, docs/adr; 12.09:
  docs/reference/role-home.md у 01M2B6K3EM). Правило «в зонах каждый
  названный файл» держится текстом в памяти ассистента и не работает.
- `orchestrator/catalog.py::cmd_new` читает ТЗ как свободный текст;
  `_tz_calibration_inputs` разбирает только строки «Рамка: $N»,
  «Требуется:» и «Зоны:» (регулярными выражениями `_TZ_RAMA_RE`,
  `_TZ_TREBUETSYA_RE`, `_TZ_ZONES_RE`; число путей —
  `budget.count_zone_paths`). Сверки упомянутых путей с зонами нет.
- `scripts/guard.py::_zone_paths` уже собирает упоминания путей из
  текста SPEC (регулярное выражение `ZONE_PATH`, только
  `orchestrator/*.py` и `scripts/*.py`) для сигнала деления;
  `spec_zones_errors` проверяет лишь непустоту `zones:`;
  `division_section_errors` уже сверяет зоны подразделов деления с зонами
  родителя через `zone_lock._covered_by`/`_is_common_zone` (учёт
  вложенности каталог/файл и `config.COMMON_ZONES`).
- На approve гейта SPEC (`orchestrator/fsm.py::_approve_spec_gate`)
  значение `zones:` пишется в `tasks.zones` (fsm.py:~707) без сверки с
  текстом SPEC.
- Гейт зон на `in_dev -> review` (`orchestrator/advance_gates/zones.py`)
  отказывает по факту диффа — поздно: шаг developer уже оплачен.
- ТЗ Оператора сегодня несут разделы «Зоны:», «Только чтение (не менять):»,
  «Приложением:», «Не входит:» (пример: tasks/01M2XFSE8G3MBRHHQR38H53J1M/
  TZ.md); SPEC — frontmatter `zones:`, разделы «## Не входит» и
  «## Материалы».

Требуется:
1. Общий сборщик упоминаний путей в `scripts/guard.py`: из свободного
   текста извлекаются кандидаты вида `каталог/…/файл.расш` и
   `каталог/` (расширения py, md, yaml, yml, txt, json, toml; каталоги с
   завершающим `/`) и оставляются только существующие в репозитории
   (относительно `config.ROOT`). Прежний `ZONE_PATH`/`_zone_paths` для
   сигнала деления не меняется.
2. Классификация для ТЗ в `catalog.cmd_new` при `--tz`: путь считается
   классифицированным, если покрыт «Зоны:» (с учётом вложенности и
   `config.COMMON_ZONES`, тем же приёмом, что `division_section_errors`)
   либо назван в разделах «Не входит:», «Только чтение…:»,
   «Приложением:». Путь из любого другого места ТЗ, не
   классифицированный, — отказ `new` ДО заведения задачи (номер не
   расходуется, ветка не создаётся) с перечнем путей и подсказкой
   «назови в Зонах, в «Не входит» или в «Только чтение/Приложением»».
   Путь из «Зоны:» под `config.PROTECTED_PATHS` — отказ «защищённый путь
   только приложением».
3. Та же сверка для SPEC на гейте (`fsm._approve_spec_gate`, до записи
   `tasks.zones`): классифицирующие множества — frontmatter `zones:`,
   разделы «## Не входит» и «## Материалы»; неклассифицированный путь
   из «## Контекст», «## Требования», «## Критерии приёмки» — отказ
   approve тем же текстом, задача остаётся на spec_gate (переход не
   выполняется). Проверка живёт в `scripts/guard.py` функцией, которую
   зовёт гейт; в `check()`/`main()` guard (CI по всему `tasks/`) не
   включается — исторические SPEC не перепроверяются.
4. Ложные срабатывания: упоминание пути внутри кода в обратных кавычках
   и в обычном тексте считается одинаково (путь есть путь); пути в
   строках «Зоны:»/`zones:` каталогом (`tests/`, `docs/adr/`) покрывают
   вложенные файлы; несуществующий в репозитории путь (файл, который
   задача только создаст) не проверяется и не отказывает.
5. Тесты (tests/): ТЗ с путём в «Требуется» вне зон — отказ `new` с
   именем файла и без побочных эффектов (нет строки в БД, нет
   артефактной ветки); тот же путь в «Не входит» либо «Только чтение» —
   `new` проходит; путь под каталогом из «Зоны:» — проходит; защищённый
   путь в «Зоны:» — отказ, в «Приложением:» — проходит; SPEC с путём в
   требованиях вне `zones:`/«Не входит»/«Материалы» — отказ approve на
   spec_gate, задача остаётся на гейте; тот же SPEC с путём в
   «Материалы» — approve проходит. Существующие
   `tests/test_catalog_tz_zones_parsing.py`, `tests/test_new_argv_parsing.py`,
   `tests/test_guard_zones.py`, `tests/test_guard_split_signals.py`,
   `tests/test_guard_division_section.py` остаются зелёными.

Зоны: orchestrator/catalog.py, scripts/guard.py, orchestrator/fsm.py,
