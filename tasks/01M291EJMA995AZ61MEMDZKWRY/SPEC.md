# SPEC: Мьютекс merge-окна держится на весь цикл approve merge_gate

## Контекст

Мьютекс merge-окна (`merge_locks`, `orchestrator/merge_lock.py`, SPEC
T053) сегодня берётся/отпускается вокруг КАЖДОГО отдельного захода в
тело гейта (`_cmd_approve_merge_gate`), а на время ожидания CI между
заходами (`_wait_for_branch_ci_green`, SPEC T087, требование 2)
намеренно отпускается. Факт 11.09: цикл `approve` на `merge_gate`
задачи 01M283NC… за 45 минут сделал пять подтяжек main и пять полных
прогонов CI (2e648868 → cf16d10e → 211efc9d → 5c10ca37 → 85382c93),
потому что в открытое на время ожидания CI окно свободно входил чужой
параллельный мерж и сдвигал main раньше, чем дозревал CI задачи.
Родительское решение Оператора 11.09 «единая очередь мержа»
(01M28VZ8Q1QTP5PRDVJJQ9AQV0) делится на две части; эта задача —
часть 1: резервирование окна на весь цикл. Часть 2 (очередь FIFO
вместо немедленного отказа второму `approve`) заводится отдельно и
зависит от этой части.

## Требования

1. Мьютекс merge-окна (`merge_locks`) резервируется на весь цикл
   `_cmd_approve_merge_gate_cycle` — от первой подтяжки main до выхода
   из цикла (успешный merge в `done`, отказ, эскалация, истечение
   потолка ожидания CI `MERGE_GATE_CI_WAIT_CEILING_SEC`, прерывание),
   ВКЛЮЧАЯ время ожидания CI внутри `_wait_for_branch_ci_green`, а не
   только тело одного захода `_cmd_approve_merge_gate`, как сейчас.
2. Держатель мьютекса (строка `merge_locks`, поле `session_id`) не
   меняется между заходами в тело гейта одного и того же цикла
   `approve` — строка не пересоздаётся и не освобождается между
   заходом, вернувшим `("wait", ...)`, и следующим заходом в тело.
3. Heartbeat строки-держателя (`merge_locks.heartbeat_ts`) продлевается
   на каждом опросе CI внутри `_wait_for_branch_ci_green` (каждая
   итерация цикла ожидания, интервал `MERGE_GATE_CI_WAIT_POLL_SEC`),
   чтобы `merge_lock._holder_is_dead` не признал живого держателя
   мёртвым из-за истечения `LEASE_STALE_AFTER_SEC` за время долгого
   ожидания CI.
4. Снятие мьютекса выполняется безусловно в `finally` ВНЕШНЕГО цикла
   `_cmd_approve_merge_gate_cycle` — единая точка освобождения на весь
   цикл (успех, отказ через `sys.exit`, `KeyboardInterrupt`), не в
   `finally` вокруг каждого отдельного захода в тело гейта, как
   сегодня.
5. Перехват мёртвого держателя (протухший heartbeat согласно
   `LEASE_STALE_AFTER_SEC` либо неживой pid на своём хосте —
   `merge_lock._holder_is_dead`, `merge_lock.acquire`) работает так же,
   как сейчас, в том числе когда мьютекс удерживается дольше тела
   одного захода — весь цикл, включая ожидание CI.
6. Второй `approve` другой задачи, поданный на занятое окно (включая
   момент, когда держатель ждёт CI внутри своего цикла), по-прежнему
   завершается существующим именованным отказом `merge_lock.acquire`
   («занято сессией …», heartbeat N сек назад) без изменения состояния
   второй задачи — эта задача не меняет текст или условия отказа,
   только удлиняет промежуток времени, в течение которого окно может
   быть занятым.
7. Порядок состояний FSM и содержимое тела гейта (подтяжка main, push,
   plotницкий merge, снимок артефактов, публикация) не меняются;
   существующее поведение `orchestrator/merge_lock.py` (взятие своей
   строки, отказ, перехват мёртвого держателя, безусловное
   освобождение) не ослабляется.

## Критерии приёмки

AC-1. После исхода `("wait", ...)` заходa в тело гейта строка
`merge_locks` остаётся у той же сессии-держателя (не освобождается) до
следующего захода в тело либо до завершения цикла.

AC-2. `merge_locks.heartbeat_ts` держателя обновляется на каждой
итерации опроса CI внутри `_wait_for_branch_ci_green`, а не только на
входе/выходе из тела гейта.

AC-3. Второй `approve` другой задачи, поданный пока первая сессия ждёт
CI внутри своего цикла `_cmd_approve_merge_gate_cycle`, получает
именованный отказ `merge_lock.acquire` («занято сессией …») и не
меняет состояние своей задачи (не зависает и не проходит).

AC-4. Держатель с протухшим heartbeat (старше `LEASE_STALE_AFTER_SEC`)
либо неживым pid на своём хосте перехватывается новой сессией даже
когда мьютекс удерживается циклом дольше тела одного захода — включая
случай, когда heartbeat протух во время ожидания CI (не только между
заходами в тело).

AC-5. Мьютекс снимается безусловно по завершении внешнего цикла
`_cmd_approve_merge_gate_cycle` в любом исходе — merge в `done`, отказ
(`sys.exit`), эскалация, истечение потолка ожидания CI — не только по
завершении одного захода в тело гейта.

AC-6. Существующие тесты `tests/test_merge_lock.py` (взятие, отказ,
перехват мёртвого держателя, освобождение) проходят без ослабления и
без изменения содержательных проверок.

AC-7. Существующий тест
`tests/test_merge_gate_ci_wait.py::OuterCycleDeadlineTest::test_mutex_acquired_and_released_around_each_body_call`
сегодня утверждает освобождение мьютекса между каждым заходом в тело
гейта (`fsm_merge_gate.py:182-213`) — это прямо противоположно
требованию 1/2 этой задачи и обязан быть переписан под новое
поведение (мьютекс берётся один раз на весь цикл, освобождается один
раз при выходе); соседний тест того же класса
`test_ceiling_not_reset_by_a_second_wait_outcome` (потолок ожидания не
пересчитывается вторым `("wait", ...)`) продолжает проходить без
ослабления.

## Не входит

- очередь FIFO вместо немедленного отказа второму `approve` (часть 2
  родительской задачи, отдельная подзадача, зависит от этой части);
- таблица `merge_queue` или любая другая структура очереди;
- изменение порядка состояний FSM и содержимого тела гейта (подтяжка
  main, push, plotницкий merge, снимок артефактов/карта/RETRO,
  `_cmd_approve_merge_gate` как узел шагов);
- `orchestrator/lease.py` (lease задачи — отдельный замок, не
  затрагивается);
- канарейка (`orchestrator/canary.py`).
