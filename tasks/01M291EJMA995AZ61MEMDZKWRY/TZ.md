# ТЗ: Часть 1: мьютекс merge-окна держится на весь цикл approve merge_gate

Родительская задача: 01M28VZ8Q1QTP5PRDVJJQ9AQV0 — единая очередь мержа: merge-окно держится на весь цикл approve merge_gate, включая ожидание CI; второй approve ждёт в очереди FIFO
Зоны: orchestrator/fsm_merge_gate.py, orchestrator/merge_lock.py, tests/
Порядок: первая, без зависимостей

Источник: копилка 06.09 «зелёная задача на merge_gate устаревает»,
дописка 11.09 (пинг-понг двух сессий), решение Оператора 11.09 «единая
очередь мержа» — родительская задача 01M28VZ8Q1QTP5PRDVJJQ9AQV0, часть
1 из 2 (часть 2 — очередь FIFO — зависит от этой и заводится отдельно).

Факт 11.09: цикл approve на merge_gate у 01M283NC… с 17:46Z за 45
минут сделал пять подтяжек main и пять полных прогонов CI (2e648868 →
cf16d10e → 211efc9d → 5c10ca37 → 85382c93), потому что соседняя сессия
параллельно вливала свои задачи: каждый её мерж сдвигал main раньше,
чем дозревал наш CI. Причина — мьютекс merge-окна (`merge_locks`,
`orchestrator/merge_lock.py`) держится только на теле гейта (подтяжка,
push, сам merge) и намеренно отпускается на время ожидания CI
(`fsm_merge_gate._cmd_approve_merge_gate_cycle`, SPEC T087, требование
2): в окно ожидания CI свободно входит чужой мерж, подтяжка начинается
заново.

Требуется:
1. Резервировать merge-окно на весь цикл approve merge_gate: с первой
   подтяжки main до мержа либо выхода цикла (отказ, эскалация,
   потолок, прерывание) — ВКЛЮЧАЯ ожидание CI. Держатель — та же
   строка `merge_locks`. Heartbeat строки продлевается на каждом
   опросе CI (`MERGE_GATE_CI_WAIT_POLL_SEC`), чтобы
   `merge_lock._holder_is_dead` не счёл живого держателя мёртвым за
   время долгого ожидания. Снятие мьютекса — безусловно в `finally`
   ВНЕШНЕГО цикла (`_cmd_approve_merge_gate_cycle`), не тела одного
   захода, как сейчас.
2. Держатель окна с неживым pid или протухшим heartbeat по-прежнему
   перешагивается тем же приёмом, что и сейчас (`merge_lock.
   _holder_is_dead`, `merge_lock.acquire`) — покрыть тестом, что
   перехват мёртвого держателя работает и когда мьютекс удерживается
   дольше (весь цикл, включая ожидание CI), а не только тело одного
   захода.
3. Второй approve другой задачи на занятое окно — пока без очереди (её
   вводит часть 2) — по-прежнему завершается существующим именованным
   отказом (`merge_lock.acquire`, текст «занято сессией …») без
   изменения состояния задачи; эта часть НЕ меняет поведение отказа,
   только удлиняет промежуток времени, в течение которого окно может
   быть занято.
4. Тесты: после первого исхода `("wait", ...)` мьютекс остаётся у той
   же сессии (не освобождается) до следующего захода тела гейта;
   heartbeat строки-держателя обновляется на каждом опросе
   `_wait_for_branch_ci_green`; второй approve на другую задачу,
   поданный пока первый ждёт CI, получает существующий отказ «занято»
   (не зависает и не проходит); мёртвый держатель (протухший
   heartbeat/неживой pid) перехватывается новой сессией даже во время
   ожидания CI; существующие тесты `orchestrator/merge_lock.py` и
   внешнего цикла `merge_gate` — без ослабления.

Не входит: очередь FIFO вместо отказа (часть 2, отдельная подзадача);
таблица `merge_queue`; изменение порядка состояний FSM и тела гейта
(подтяжка, push, carpentry-merge); `orchestrator/lease.py`; канарейка.
