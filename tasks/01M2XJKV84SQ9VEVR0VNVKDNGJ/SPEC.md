# SPEC: Роль запускается по абсолютному пути из манифеста, модель роли сверяется с версией CLI до старта агента

## Контекст

Две строки копилки `docs/backlog.md` (П1 06.09 «Runner зовёт инструменты
роли по имени через PATH», П2 19.09 «Модель роли не сверяется с
возможностями установленного CLI») живут в одних и тех же модулях
(`orchestrator/runner.py`, `orchestrator/stack.py`) и заведены Оператором
19.09 одним ТЗ.

Первая: `runner._resolve_declared_tools` (`orchestrator/runner.py:550`)
резолвит объявленные манифестом инструменты через `shutil.which`, а
`_role_path_dirs` (`:572`) собирает из их каталогов PATH роли — но
`role_cmd()` (`:778`) начинается с литерала `"claude"`, и бинарник
ищется по PATH роли в момент запуска, а не берётся из `resolved["claude"]`.
Инцидент 06.09 (планка отвязки циклов, 01M1NWCHVT): подставной `claude`
планки затенён настоящим из `/opt/homebrew/bin`, потому что каталог `gh`
стоит в PATH роли раньше — любой одноимённый бинарник в каталоге другого
объявленного инструмента подменяет объявленный.

Вторая: `stack.REQUIRED_TOOLS["claude"]` (`orchestrator/stack.py:84`) —
`ToolRequirement((1, 0, 0), …)`, минимальная версия без связи с моделями
ролей; `check_stack` (`:342`) печатает строку на инструмент и о моделях
`roles.yaml` не знает; проверки «модель принимается установленным CLI»
перед стартом шага нет. 19.09 (задачи 01M2XFSJ1Z и 01M2XFSE8G) после
смены модели developer/reviewer на `claude-fable-5-1` шаг падал за 0
токенов с «API Error: 400 … does not support this model; version 2.1.251
or newer is required»; `failure_classification.classify_attempt_failure`
относит «API Error:» к классу «системный кандидат» —
`config.TRANSIENT_SYSTEM_BACKOFF_SEC` = 120 с и `config.AGENT_ATTEMPTS`
попыток, после чего эскалация, хотя отказ детерминирован и повторами не
лечится, а причина известна до запуска агента.

## Требования

## Критерии приёмки

AC-1. `argv[0]` команды шага роли — абсолютный путь из резолва манифеста
(`resolved["claude"]`, тот же резолв, что даёт каталоги PATH роли); в
`argv[0]` нет литерала `claude`.

AC-2. Прочий состав запуска не меняется: набор и порядок флагов
`role_cmd()` те же, что до задачи (включая `--setting-sources` и
`--strict-mcp-config`), `--model` по-прежнему довеском после них; PATH
роли (состав и порядок каталогов, `.artel/venv/bin` первым) тот же, что
до задачи.

AC-3. Сценарий затенения: в PATH роли каталог с подставным `claude`
стоит позже каталога другого объявленного инструмента, несущего
настоящий `claude` — шаг запускает объявленный (резолв манифеста)
бинарник, а не подставной.

AC-4. `role_cmd()` — единственный источник argv шага, вызывается из
`orchestrator/doctor/isolation.py` без аргументов; структурная сверка
`--strict-mcp-config` в `doctor.isolation_smoke` остаётся и продолжает
ловить свою мутацию (`tests/test_doctor.py::IsolationSmokeTest` зелёный),
`orchestrator/doctor/` при этом не меняется.

AC-5. `orchestrator/stack.py` несёт таблицу `MODEL_MIN_CLI_VERSION` рядом
с манифестом с записью `"claude-fable-5-1": (2, 1, 251)`; код требований
3–5 читает таблицу, а не повторяет числа по месту; модель, которой в
таблице нет, отказа не вызывает ни в одной из трёх точек.

AC-6. Модель шага есть в таблице, установленная версия CLI ниже
минимальной: агент не запускается ни разу (`runner.spawn_agent` не
вызван), в журнале шага — запись «модель роли не поддерживается CLI:
<модель> требует claude ≥ X, установлен Y», записей «agent run retry»
нет, состояние задачи не переходит в `escalated`.

AC-7. Тот же отказ останавливает цикл `auto`, и в его выводе есть
подсказка «обнови CLI либо смени model роли в roles.yaml».

AC-8. Модель шага в таблице отсутствует: ровно одна запись
предупреждения «модель не в таблице совместимости» на шаг, агент
запускается, argv и поведение шага в остальном прежние.

AC-9. `failure_classification.classify_attempt_failure` относит вывод
попытки с текстом «does not support this model» к отдельному классу (не
к «системному кандидату»); такая попытка не повторяется — следующая
попытка не запускается, паузы между попытками нет, исход шага — тот же
именованный отказ, что в AC-6/AC-7, без перехода в `escalated`.

AC-10. `stack.check_stack()` даёт по одной строке на каждую agent-роль
`roles.yaml` с полем `model`: `ok` с текстом вида «модель роли developer
claude-fable-5-1: CLI 2.1.267 ≥ 2.1.251 — ok», `fail` при версии CLI ниже
минимальной для этой модели, `warn` для модели вне таблицы; строки
попадают в вывод `doctor` и `version` без правки `orchestrator/doctor/` и
`orchestrator/version.py`.

AC-11. Тесты сценариев AC-1..AC-10 лежат в `tests/`; существующие
`tests/test_runner_role_model.py`, `tests/test_stack.py`,

## Оценка объёма и деление

Сработавшие сигналы:
- **затронут инвариантный механизм** — зона `tests/` встречается в
  `docs/invariants.md`; по существу задача стоит рядом с инвариантом 3
  («у каждого цикла числовой лимит; после лимита — Оператор, не ретрай» —
  требование 4 заводит класс без повторов, как уже сделано для класса 2
  session_limit, число попыток `config.AGENT_ATTEMPTS` не меняется) и
  инвариантом 31 (флаги изоляции в argv шага — требование 1 меняет
  `argv[0]`, флаги оставляет на месте);
- **число критериев приёмки** — 11 при пороге
  `config.SPLIT_SIGNAL_AC_COUNT` = 10.

Решение: **монолит**. Обоснование:

- Обе механики сходятся в одной функции и одном резолве:
  `role_cmd()`/`_resolve_declared_tools` (требование 1) и предполётная
  проверка модели (требование 3) — соседние строки одного пути запуска
  шага в `orchestrator/runner.py`. Разрез «абсолютный путь» /
  «совместимость модели» прошёл бы поперёк зоны `orchestrator/runner.py`
  (и поперёк `tests/`): обе части правили бы один файл, зона одной из них
  не была бы самостоятельной, а вторая ждала бы мержа первой на
  зоно-локе — ровно то, что скил запрещает («не режь зону поперёк»).
- Оба требования 3 и 4 обязаны давать ОДИН И ТОТ ЖЕ именованный исход
  шага (требование 4: «исход шага — тот же именованный отказ, что и в
  требовании 3»). Часть, вводящая только один из двух входов в этот
  исход, оставляет систему в состоянии, где один и тот же отказ
  оформляется двумя разными способами, — промежуточное состояние
  заведомо хуже как исходного, так и целевого.
- Числа объёма невелики: 3 файла кода (`runner.py`, `stack.py`,
  `failure_classification.py`) плюс тесты, 11 критериев — это плотность
  проверок на одну небольшую механику, а не ширина зоны; сигнал «число
  затрагиваемых модулей/файлов» (порог 5) не сработал.

Рамка Оператора в ТЗ — $35, `budget_usd` взят по ней. Калибровочная
таблица (`config.BUDGET_CALIBRATION_TABLE`) при 11 критериях
рекомендовала бы уровень выше; расхождение сознательное и названо здесь —
поднять потолок вправе Оператор командой `budget`.

## Материалы

**Решение по форме сверки (требование 1).** Сравнение — **по базовому
имени** (`Path(argv[0]).name == "claude"`), не по абсолютному пути.
Обоснование:

- Сама офлайн-сверка `doctor.isolation_smoke`
  (`orchestrator/doctor/isolation.py:112-116`) смотрит на наличие флага
  `--strict-mcp-config` в списке argv и от `argv[0]` не зависит вовсе —
  требование 1 её не ослабляет ни в какой форме сравнения.
- Реальные сверки «это вызов CLI роли, а не `git`/`python3` в том же
  моке» живут в тестовом слое: `tests/sandbox.py::claude_only_run`
  (`:452`), `claude_only_popen` (`:462`), `tests/test_git_fixation.py:492`
  и `:943`. Абсолютный путь там зависит от машины прогона (homebrew,
  npm-global, стаб `/artel-test-stub-bin/claude` из
  `tests/sandbox.py::_stub_which`, `:105`) — сверка по нему проходила бы
  или падала по причине, не относящейся к предмету проверки. Базовое имя
  даёт этим местам ту же различающую силу, что и сегодня.
- Сила «запущен именно объявленный бинарник» при этом не растворяется, а
  прибавляется: её закрепляет отдельный тест затенения (AC-3), который
  сверяет `argv[0]` с абсолютным путём резолва манифеста. Сегодня такого
  теста нет ни в каком виде — после задачи он есть, то есть сверка
  строго сильнее прежней.
