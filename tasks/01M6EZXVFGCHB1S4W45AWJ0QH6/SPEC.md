# SPEC: GitLab Б2.3-2: хук pre-push в клоне, его строка doctor, клон подмодулей и сверки перед отправкой

## Контекст
Часть 2 из 4 деления задачи 01M6EXF3TMNRKCZH8CS9BXXG1Z (GitLab Б2.3);
основание — ADR-0029 п. 13 и решение R3-F1 (Б1.1) сессии при Операторе
26.10. Единая точка отправки пульта — `orchestrator/gitcmd.py`, но
псевдоним в аргументах команды (`-c alias.*`, `!`-форма, `--config-env`),
прячущий назначение отправки в значении, перебором форм в `gitcmd` не
закрывается. Его закрывает второй рубеж: постоянный `core.hooksPath`
клона на каталог хуков пульта и хук `pre-push` с теми же правилами, что у
`gitcmd`, плюс строка `doctor`, сверяющая хук, его файл политики и
`core.hooksPath`. Сейчас `core.hooksPath` у клонов уже стоит на
`<config.ROOT>/scripts/git-hooks` (`orchestrator/workspace.py:68-75`), но
хук `scripts/git-hooks/pre-push` — лишь общая защита `main`, пропускающая
всё при `ARTEL_PULT_GIT=1`; вызовы отправки пульта `-c core.hooksPath` не
задают; сверок конфигурации и окружения перед отправкой нет.

## Требования
1. В клоне проекта с `merge_gate: target-human` и в его рабочих копиях
   задач git при отправке вызывает хук `pre-push` из каталога хуков пульта
   (вне зон записи ролей). Пульт прописывает этот `core.hooksPath` клона
   при подготовке клона (`orchestrator/workspace.py`) и в `doctor --fix`.
   Правила держит именно файл `pre-push`, который git вызывает в этом
   клоне (файл с другим именем git сам не вызовет).
2. Хук `pre-push` в таком клоне проверяет те же правила, что `gitcmd`:
   проходят только ветка задачи по шаблону ветки проекта и
   `refs/artifacts/*`; отправка в `base`, удаление веток, теги и
   `refs/heads/*` вне шаблона — отказ.
3. Проект, шаблон ветки, `base` и префикс `refs/artifacts` хук берёт из
   файла политики, который пульт пишет в каталог `.git` клона (общий для
   его рабочих копий задач) при подготовке клона — там же, где задаёт
   `core.hooksPath`, — и в `doctor --fix`. Файла нет или он не читается —
   хук отказывает любой отправке с причиной. В хуке по-прежнему только
   POSIX sh и git (`scripts/git-hooks/pre-push:10-11`).
4. Хук срабатывает при отправке из клона любой формой, которая запускает
   хуки, в том числе псевдонимом и коротким именем удалённого репозитория.
   Маркер `ARTEL_PULT_GIT=1` правил `target-human` не снимает.
5. Каждый вызов отправки пульта из клона проекта с `target-human` задаёт
   `-c core.hooksPath=<каталог хуков пульта>` (новое поведение).
6. Защита `main` главной копии и клонов прочих проектов
   (`scripts/git-hooks/pre-push:14-30`) сохраняется без изменений.
7. Строка `doctor` по клону проекта с `target-human` сверяет: контрольную
   сумму хука `pre-push`, который git вызывает в клоне, контрольную сумму
   файла политики хука и значение `core.hooksPath` клона (а также
   постоянный `core.hooksPath` в конфигурации рабочих копий задач клона —
   модель угроз ТЗ, п. 1). Эталон суммы хука — содержимое файла хука в
   коммите `HEAD` главной копии пульта (`config.ROOT`), а не файл на диске;
   эталон файла политики — содержимое, которое пульт пишет по текущей
   записи проекта. Расхождение — `fail`; `doctor --fix` возвращает хук и
   файл политики к эталону, а `core.hooksPath` клона — к каталогу хуков
   пульта.
8. Строка `clone-hooks` у клонов прочих проектов остаётся `warn`, как
   сейчас (`orchestrator/doctor/git_hooks.py:148-172`).
9. Клон подмодулей проекта при подготовке клона идёт тем же слотом токена
   (`token_slot` записи), что и клон проекта.
10. Перед отправкой для проекта под белым списком
    (`targets.push_whitelisted`) `gitcmd` сверяет:
    - `remote.origin.url` клона совпадает с адресом записи;
    - в действующей конфигурации нет `url.*.insteadOf`/`pushInsteadOf`,
      `core.sshCommand` и иного `core.hooksPath`, чем каталог хуков пульта;
    - в окружении вызова сняты `GIT_DIR`, `GIT_WORK_TREE`,
      `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`.
    Нарушение — отказ отправки с именем находки до вызова git.
11. Признак проекта определяется только помощниками `targets.py`
    (`push_whitelisted`, `merged_by_project_people`). Сравнение значения
    `forge`/`merge_gate` с литералом вне `targets.py` и новые исключения
    `EXEMPT` сторожа ac9
    (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:416-421`)
    запрещены.
12. Артель и проекты `github` + `operator`: поведение и существующие тесты
    прежние.

## Критерии приёмки
Песочницы — вымышленные проекты с локальным `origin`.

AC-1. В клоне проекта с `target-human` хук `pre-push` отказывает
отправке в `base`, отправке тега, удалению ветки и отправке ветки вне
шаблона ветки проекта.

AC-2. В клоне проекта с `target-human` те же отправки (AC-1)
отказываются хуком и при отправке через `git -c alias.p=push`, через
`!`-псевдоним, через короткое имя удалённого репозитория и при
`ARTEL_PULT_GIT=1` в окружении.

AC-3. В клоне проекта с `target-human` отправка ветки задачи по шаблону
проекта и отправка `refs/artifacts/*` проходят хук.

AC-4. В клоне проекта с `target-human` при отсутствии файла политики в
`.git` клона или при нечитаемом файле политики любая отправка
отказывается хуком с причиной.

AC-5. В главной копии и в клоне проекта `github` + `operator` хук ведёт
себя как прежде: отправка в `main` без маркера `ARTEL_PULT_GIT=1`
отказывается, с маркером проходит.

AC-6. `gitcmd` отказывает отправке до вызова git (шпион не видит `push`)
с именем находки при каждом из: подменённый `remote.origin.url`,
`url.*.insteadOf`, `url.*.pushInsteadOf`, `core.sshCommand`, чужой
`core.hooksPath` в действующей конфигурации клона.

AC-7. `gitcmd` отказывает отправке до вызова git (шпион не видит `push`)
с именем находки при любой из `GIT_DIR`, `GIT_WORK_TREE`,
`GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` в окружении
вызова.

AC-8. `gitcmd` отказывает отправке до вызова git (шпион не видит `push`)
при `!`-псевдониме в аргументах команды с `-c core.hooksPath=` в теле.

AC-9. Отправка пульта из клона проекта с `target-human`, прошедшая
сверки, несёт в вызове git `-c core.hooksPath=<каталог хуков пульта>`.

AC-10. `doctor` по клону проекта с `target-human`: хук `pre-push`,
изменённый против эталона из `HEAD` главной копии пульта, даёт строку
`fail`; после `doctor --fix` хук равен эталону и строка — `ok`.

AC-11. `doctor` по клону проекта с `target-human`: файл политики,
изменённый против эталона по записи проекта, даёт строку `fail`; после
`doctor --fix` файл равен эталону и строка — `ok`.

AC-12. `doctor` по клону проекта с `target-human`: чужой
`core.hooksPath` клона даёт строку `fail`; после `doctor --fix`
`core.hooksPath` указывает на каталог хуков пульта и строка — `ok`.

AC-13. Постоянный `core.hooksPath`, заданный в конфигурации рабочей
копии задачи клона проекта с `target-human` (как это сделала бы роль),
даёт строку `doctor` `fail` с этим значением, а отправка пульта из этой
рабочей копии отказывается до вызова git (шпион не видит `push`).

AC-14. Клон подмодулей проекта при подготовке клона идёт слотом токена
проекта: подменённый git видит тот же слот, что и при клоне проекта.

AC-15. Строка `clone-hooks` по клону проекта не `target-human`
(`github` + `operator`) остаётся со статусом `warn` при прежних условиях.

## Оценка объёма и деление
Сработавшие сигналы: число критериев приёмки ≥ 10 (15); `budget_usd` ≥
$30 ($40 — рамка Оператора в ТЗ).

Материал к решению «монолит» (решение — за Оператором на гейте SPEC):
задача уже сама является частью 2 деления 01M6EXF3TMNRKCZH8CS9BXXG1Z,
нарезанной по зонам родителя. Её механика атомарна: хук `pre-push` и его
файл политики, запись политики и `core.hooksPath` при подготовке клона,
`-c core.hooksPath` в вызовах пульта и сверка «иного `core.hooksPath`»
перед отправкой, строка `doctor` с эталонами хука и политики — одна
связка. Сверка `gitcmd` против «иного `core.hooksPath`, чем каталог
хуков пульта» без хука с правилами `target-human` проверяет каталог,
который `target-human` не защищает; хук без файла политики, который пишет
пульт, отказывает любой отправке (требование 3) и останавливает работу с
проектом; строка `doctor` без хука и политики не имеет эталона. Отдельно
отделимы лишь клон подмодулей слотом токена (требование 9, AC-14) и
сверки окружения (AC-7) — их вынос даёт подзадачу на 1–2 критерия при
цене отдельного прогона конвейера, бо́льшей, чем экономия.

## Не входит
- Прочие строки `doctor` проекта и `forge-probe` — часть 3 деления.
- Открытие `gitlab`/`target-human` — часть 4 деления.
- Запрет отправки роли из оболочки формами, выключающими хуки в самом
  вызове (`--no-verify`, `-c core.hooksPath=…`): хук их не держит (модель
  угроз ТЗ); в вызовах пульта их закрывают сверки требования 10 и уже
  существующий отказ псевдонима в аргументах (`gitcmd.py:887-901`).
- Удержание хуком постоянного `core.hooksPath`, заданного ролью в
  конфигурации клона или рабочей копии: его обнаруживает строка `doctor`
  (требование 7), а отправку пульта отказывает сверка требования 10.
- Изменение защиты `main` главной копии и клонов прочих проектов.
