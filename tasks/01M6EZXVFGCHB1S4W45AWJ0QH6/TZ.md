# ТЗ: GitLab Б2.3-2: хук pre-push в клоне, его строка doctor, клон подмодулей и сверки перед отправкой

Родительская задача: 01M6EXF3TMNRKCZH8CS9BXXG1Z — GitLab Б2.3: хук pre-push в клоне, сверки отправки, строки doctor, отказ при сбое, открытие gitlab и target-human
Зоны: orchestrator/gitcmd.py, orchestrator/workspace.py, scripts/git-hooks/, orchestrator/doctor/git_hooks.py, tests/
Порядок: после части 1
Рамка: $40

Часть 2 из 4 деления задачи 01M6EXF3TMNRKCZH8CS9BXXG1Z (GitLab Б2.3). Основание — ADR-0029 п. 13 и решение сессии при Операторе 26.10 по замечанию R3-F1 (Б1.1).

ADR-0029 п. 13: единая точка отправки, хук — второй рубеж, пульт задаёт каталог хуков в самом вызове, `doctor` сверяет контрольную сумму хука. Решение R3-F1: псевдоним в аргументах команды (`-c alias.*`, `!`-форма, `--config-env`), прячущий назначение отправки в значении, перебором форм в `gitcmd` не закрывается. Его закрывает постоянный `core.hooksPath` клона на каталог хуков пульта и хук `pre-push` с теми же правилами.

Состояние кода (main):
- Единая точка отправки и белый список ссылок — `orchestrator/gitcmd.py` (Б1.1). Переменные окружения git, которые пульт задаёт и снимает, — `gitcmd.py:150-190`, `:640`. Вызовы отправки пульта `-c core.hooksPath` сейчас не задают.
- `core.hooksPath` у клонов уже стоит на абсолютный путь пина `<config.ROOT>/scripts/git-hooks`: `workspace.set_clone_hooks` (`orchestrator/workspace.py:68-75`), строка `doctor` `clone-hooks` со статусом `warn` (`orchestrator/doctor/git_hooks.py:148-172`), `--fix` в `_fix_project_clones` (`:175-192`).
- git вызывает из этого каталога только файл `pre-push`. Сейчас это общий хук защиты `main` (`scripts/git-hooks/pre-push`): он пропускает всё при `ARTEL_PULT_GIT=1` (`:14-16`).

Требуется:
1. Хук `pre-push` в клоне проекта с `target-human`.
   - В клоне такого проекта и его рабочих копиях задач git при отправке вызывает хук `pre-push` из каталога хуков пульта вне зон записи ролей. Пульт прописывает этот `core.hooksPath` при подготовке клона (`orchestrator/workspace.py`) и в `doctor --fix`. Отдельный файл с другим именем git сам не вызовет: правила должен держать хук, который git вызывает в этом клоне.
   - Хук проверяет те же правила, что `gitcmd`: проходят только ветка задачи по шаблону проекта и `refs/artifacts/*`; отправка в `base`, удаление веток, теги и `refs/heads/*` вне шаблона — отказ.
   - Проект, шаблон ветки, `base` и префикс `refs/artifacts` хук берёт из файла политики. Этот файл пульт пишет в каталог `.git` клона (общий для его рабочих копий задач) при подготовке клона, там же, где задаёт `core.hooksPath`, и в `doctor --fix`. Если файла нет или он не читается, хук отказывает отправке с причиной. В хуке по-прежнему только POSIX sh и git (`scripts/git-hooks/pre-push:10-11`).
   - Хук срабатывает при отправке из клона любой формой, которая запускает хуки, в том числе псевдонимом и коротким именем удалённого репозитория. Маркер `ARTEL_PULT_GIT=1` правил `target-human` не снимает.
   - Каждый вызов отправки пульта из клона проекта с `target-human` задаёт `-c core.hooksPath=<каталог хуков пульта>`. Это новое поведение.
   - Защита `main` главной копии и клонов прочих проектов (`scripts/git-hooks/pre-push:14-30`) сохраняется без изменений.
   - Модель угроз:
     - формы, выключающие хуки в самом вызове (`--no-verify`, `-c core.hooksPath=…`), хук не держит. В вызовах пульта их закрывают сверки п. 4 и отказ псевдонима в аргументах (`gitcmd.py:887-901`);
     - постоянный `core.hooksPath` в конфигурации клона или его рабочей копии, заданный ролью, хук тоже не держит. Его обнаруживает строка `doctor` п. 2 (значение и контрольные суммы), а пульт отказывает своей отправке при значении, отличном от каталога хуков пульта (сверка п. 4).
2. Строка `doctor` о хуке: контрольная сумма хука `pre-push`, который git вызывает в клоне проекта с `target-human`, контрольная сумма файла политики хука и значение `core.hooksPath` клона.
   - Эталон суммы хука — содержимое файла хука в коммите главной копии пульта (`HEAD` `config.ROOT`), а не сам файл на диске. Эталон файла политики — содержимое, которое пульт пишет по текущей записи проекта.
   - При расхождении — `fail`; `doctor --fix` возвращает хук и файл политики к эталону, а `core.hooksPath` клона — к каталогу хуков пульта.
   - Строка `clone-hooks` у клонов прочих проектов остаётся `warn`, как сейчас.
3. Клон подмодулей проекта при подготовке клона идёт тем же слотом токена, что и клон проекта.
4. Сверки `gitcmd` перед отправкой для проекта под белым списком (`targets.push_whitelisted`):
   - `remote.origin.url` клона совпадает с адресом записи;
   - в действующей конфигурации нет `url.*.insteadOf`/`pushInsteadOf`, `core.sshCommand` и иного `core.hooksPath`, чем каталог хуков пульта;
   - в окружении вызова сняты `GIT_DIR`, `GIT_WORK_TREE`, `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`.
   Нарушение — отказ отправки с именем находки до вызова git.

Признак проекта — помощники `targets.py` (`push_whitelisted`, `merged_by_project_people`). Сравнение значения `forge`/`merge_gate` с литералом вне `targets.py` и новые исключения `EXEMPT` сторожа ac9 (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:416-421`) запрещены.

Критерии приёмки (песочницы — вымышленные проекты с локальным `origin`):
- хук в клоне проекта с `target-human`:
  - отправка в `base`, тега, удаление ветки и отправка ветки вне шаблона отказываются хуком;
  - то же через `git -c alias.p=push`, `!`-псевдоним, короткое имя удалённого и при `ARTEL_PULT_GIT=1` в окружении;
  - ветка задачи и `refs/artifacts/*` проходят;
  - файла политики в `.git` клона нет или он не читается — любая отправка отказывается хуком с причиной;
- в главной копии и клоне проекта `github` + `operator` хук ведёт себя как прежде: отправка в `main` без маркера отказывается, с маркером проходит;
- `gitcmd`, отказ до вызова git (шпион не видит `push`):
  - подменённый `remote.origin.url`, `insteadOf`, `pushInsteadOf`, `core.sshCommand`, чужой `core.hooksPath`;
  - любая из `GIT_DIR`, `GIT_WORK_TREE`, `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` в окружении;
  - `!`-псевдоним в аргументах с `-c core.hooksPath=` в теле;
- прошедшая сверки отправка несёт `-c core.hooksPath=<каталог хуков пульта>`;
- `doctor` по клону проекта с `target-human`:
  - хук изменён против эталона из `HEAD` — `fail`; `--fix` возвращает эталон, строка `ok`;
  - файл политики изменён против эталона по записи — `fail`; `--fix` возвращает эталон, строка `ok`;
  - чужой `core.hooksPath` клона — `fail`; `--fix` чинит, строка `ok`;
  - постоянный `core.hooksPath`, заданный в конфигурации рабочей копии задачи клона (как это сделала бы роль), — `doctor` даёт `fail` с этим значением, а отправка пульта из этой рабочей копии отказывается до вызова git (шпион не видит `push`);
- клон подмодулей идёт слотом токена проекта (подменённый git видит тот же слот);
- артель и проекты `github` + `operator`: поведение и существующие тесты прежние.

Не входит: прочие строки `doctor` проекта и `forge-probe` (часть 3); открытие `gitlab`/`target-human` (часть 4); запрет отправки роли из оболочки формами, выключающими хуки (`--no-verify`).
