# PLAN: A1 — мультитаргет в конфиге, БД и CLI

## Подход

Задача закладывает фундамент мультитаргета, не двигая догфуд-флоу:
артефакты задач артели остаются в `tasks/` пульта (ADR-0003 3д,
«особый случай до A7»), логи прогонов — в `.artel/logs/`. Всё новое
аддитивно: новый файл декларации, новый модуль-читатель, новые
колонки и таблица в БД, новая команда CLI.

Ключевые решения:

1. **targets.yaml читает отдельный модуль `orchestrator/targets.py`** —
   той же идиомой, что `roles.py` читает roles.yaml: `TargetsError`
   с текстом причины вместо трейсбека, разбор через `yamlmini`.
   Формат записи — вложенное отображение с потоковыми списками
   (`no_paths`, `project_skills`): ровно то подмножество YAML, которое
   `yamlmini` разбирает. Проверяются ВСЕ записи файла при любом чтении,
   а не только запрошенная: «невалидный targets.yaml — внятный отказ»
   (требование 1) относится к файлу, а не к одной записи.
2. **Структура target'а — команда `target-init <name>`** (модуль
   `orchestrator/projects.py`): создаёт `.artel/projects/<target>/`
   с `workspace/`, `tasks/`, `knowledge/`, `logs/`. Идемпотентность —
   свойство `mkdir(exist_ok=True)`, а не проверка «уже есть»: вызов
   печатает, что создано и что уже было. Имя target'а обязано быть
   объявлено в targets.yaml — каталог без декларации был бы сиротой
   (их ищет doctor, A3). Git-слоя внутри нет: `git init`, коммиты
   на переходах и sha в журнал — A2b.
3. **SQL консолидируется в store.py** (требование 6, ADR-0003 3ж).
   Вне store.py прямых запросов не остаётся: DDL схемы, миграции
   колонок, чтения списков и все `UPDATE tasks` становятся именованными
   функциями. Правки полей строки задачи собраны в одну
   `store.update_task(conn, id, **fields)` — имена полей сверяются
   со списком колонок, чтобы точка сборки запроса не стала точкой
   инъекции. `updated_at` вызывающий передаёт явно: до T019 счётчики
   ревью его не трогали, и менять это молча — правка поведения вне
   зоны задачи.
4. **Колонка `target` — миграцией с DEFAULT** (`ALTER TABLE ... ADD
   COLUMN target TEXT DEFAULT 'artel'`): существующие строки получают
   `artel` самой ALTER TABLE, без отдельного UPDATE, и схема остаётся
   переносимой (без SQLite-экзотики). Колонка добавляется и в `tasks`,
   и в `steps`; `store.journal` берёт target задачи из её строки —
   журнал не может разойтись с каталогом задач.
5. **Нумерация — таблица `task_counters (target, next_number)`**
   вместо `COUNT(*)`. Счётчик засевается миграцией по МАКСИМАЛЬНОМУ
   существующему номеру задач target'а (не по их количеству): строка,
   ушедшая в архив, номер не освобождает (ADR-0003 3ж). Чтение и сдвиг
   счётчика — одна транзакция на запись (`BEGIN IMMEDIATE` до SELECT):
   python открывает транзакцию только на UPDATE, поэтому без неё два
   одновременных `new` читают один номер и второй `insert_task` падает
   IntegrityError. WAL (решение 6) заводится ровно ради второго процесса
   на этой БД, так что гонка достижима. Диалектен здесь синтаксис
   транзакции, а не схема: переносимость схемы (ADR-0003 3ж) это
   не трогает. Формат
   идентификатора не меняется (`T019`): задачи заводятся только для
   target'а догфуда, командой `new` без выбора target'а — префикс
   идентификатора для второго target'а понадобится вместе с командой,
   которая заводит его задачи (см. «Риски»).
6. **WAL включается при открытии БД** (`store.db`) и не роняет CLI,
   если файловая система его не поддерживает: фактический режим
   возвращается вызывающему, а не проглатывается.
7. **Пороги расхода программы считаются в момент пересечения**:
   сумма `spent_usd` по всем задачам всех target против стоп-лосса
   $2000 (roadmap §5). Событие пишется, когда шаг перевёл сумму через
   70% или 90%, а не пока сумма выше порога, — иначе каждый следующий
   шаг повторял бы ту же строку. Носитель — журнал и консоль;
   таблица alerts появится в A3.
8. **HOME/CLAUDE_CONFIG_DIR роли задаёт пульт** (ADR-0003 п.14):
   процесс агента получает `HOME=.artel/home` и
   `CLAUDE_CONFIG_DIR=.artel/home/.claude`. Каталог создаётся перед
   запуском; не создался — шаг не начинается (исход `skipped` с
   причиной), тихого отката на HOME Оператора нет ни в одной ветке.
9. **Курируемый слой несёт git-идентичность роли.** Смена HOME уводит
   из-под роли и `~/.gitconfig` Оператора, а `user.email` в этом
   репозитории задан только глобально: без переноса `git commit`
   внутри шага падает с rc=128 («Author identity unknown»), то есть
   предписанный роли коммит не проходит и ветка задачи остаётся пустой
   при отработавшем агенте (ревью 1, замечание 1). Переносится ровно
   идентичность — `GIT_AUTHOR_*`/`GIT_COMMITTER_*`, снятые
   `git config --get` в окружении Оператора: git читает эти переменные
   поверх конфига, и в шаг не попадает остальной user-слой (алиасы,
   `core.hooksPath`, `includeIf`). Ставятся через `setdefault` —
   заданная Оператором переменная сильнее конфига, как и у самого git.
   Идентичность не прочиталась — переменных нет, но перед запуском
   пишется предупреждение в журнал и консоль: молча уводить шаг
   в rc=128 нельзя. Это не откат изоляции: HOME и CLAUDE_CONFIG_DIR
   остаются пультовыми в любой ветке.

## Шаги

Один шаг = один MR (Фаза 0), внутри — независимо проверяемые единицы:

1. `targets.yaml` + `orchestrator/targets.py` + тесты чтения и отказов.
2. `orchestrator/projects.py` + команда `target-init` + тесты структуры
   и идемпотентности.
3. `store.py`: схема с `target`, миграция колонок, `task_counters`,
   WAL, именованные функции для всех запросов; перевод `catalog`,
   `fsm`, `budget`, `runner`, `spend` на них + тесты миграции,
   нумерации, WAL и grep-тест «SQL только в store.py».
4. Пороги расхода программы в `budget.py`, вызов из `runner` после
   учёта стоимости шага + тесты обоих порогов, включая тест уровня
   `cmd_run`: снятый вызов из `run_agent_once` обязан ронять набор.
5. Отдельный HOME/CLAUDE_CONFIG_DIR роли в `runner.py` и git-идентичность
   в этом окружении + тесты окружения процесса и пробный `git commit`
   с ним; в песочницы тестов, которые зовут `cmd_run`, добавлены пути
   этого слоя — иначе прогон набора заводил бы каталог в настоящем
   `.artel/` репозитория.
6. README: команда `target-init` и `targets.yaml` в структуре.

## Влияние на систему

**Что затрагивается за пределами непосредственной правки.**
Консолидация SQL (требование 6) — единственная правка, которая
касается пяти модулей сразу: `catalog`, `fsm`, `budget`, `runner`,
`spend`. Она механическая — запрос переезжает в store.py под именем,
поведение сохраняется дословно (те же поля, те же коммиты, тот же
`updated_at` там, где он был, и его отсутствие там, где его не было).
Схема БД меняется только добавлением: колонки с DEFAULT и новая
таблица; ни одна существующая колонка не удаляется и не меняет тип,
данные T001–T018 не переписываются.

**Инварианты, гейты, тесты и лимиты рядом.** Не ослабляются:

- инварианты 8–10 (бюджет задачи): порог программы — второй, ВНЕШНИЙ
  контур учёта, он ничего не разрешает. Потолок задачи, блокировка
  `run` и право Оператора поднимать потолок не тронуты;
- инвариант 11 (журнал пишется всегда): записей стало больше
  (порог программы), ни одна не убрана;
- инварианты 1–7, 12–19 (гейты, счётчики, merge по зелёному CI,
  kill switch): код этих путей меняется только заменой инлайн-запроса
  на вызов store — ни одно условие перехода не тронуто;
- guard, `gates.yaml`, `.github/`, `templates/`, `skills/`,
  `docs/invariants.md` не меняются.

**Правка `tests/test_invariants.py` — названа отдельно**, потому что
файл стоит в PROTECTED job'а `protected-paths`. Правка ровно одна и
в обеих его песочницах одинаковая: в список подменяемых путей config
добавлены `ROLE_HOME` и `ROLE_CONFIG_DIR`. Ни одна проверка, ни один
ассерт и ни один инвариант не тронуты — без этих двух строк прогон
набора создавал бы каталог слоя ролей в настоящем `.artel/`
репозитория, то есть тест писал бы вне песочницы. Того же вида правка
внесена ещё в СЕМЬ модулей тестов (они не защищены):
`test_agent_failure`, `test_agent_log`, `test_agent_prompt`,
`test_auto_cycle`, `test_review_freshness`, `test_review_package`,
`test_step_cost`. Если Оператор считает, что в защищённый файл
не должна заходить и такая правка, — её можно снять ценой этого
побочного эффекта, поведение системы от неё не зависит.

**Правки тестов от git-идентичности (решение 9) — тоже названы
поимённо.** Подмена `subprocess.Popen` в тестах глобальна, а
`role_env` теперь зовёт `gitcmd.git`, поэтому три модуля получили
правку фикстуры:

- `test_agent_log.py` — в `CmdRunLoggingTest.setUp` добавлена подмена
  `gitcmd.git` (иначе настоящий `git config` уходит в фейковый Popen
  и роняет 11 тестов класса). Ассерты не тронуты;
- `test_step_cost.py` — существующий `fake_git` научен отвечать на
  `config --get user.*` (пустой ответ означал бы «идентичность
  не задана» и добавлял предупреждение в вывод каждого прогона).
  Ассерты не тронуты;
- `test_review_package.py:720` — единственный изменённый ассерт.
  Было `self.git.calls == []`, стало — точный список из двух вызовов
  `config --get`. Строгость сохранена: любой `show` или `diff` в шаге
  разработчика по-прежнему валит тест, а требование «контекст
  разработчика не меняется» проверяется тем же способом.

`targets.yaml` в список PROTECTED job'а `protected-paths`
НЕ добавляется: `.github/` правит только Оператор. Строка для него —
кандидат в A2/A3 вместе с проверкой no_paths (отмечено в «Рисках»).

**Как откатить.** Код — revert коммита. БД: добавленные колонки и
таблица остаются, но старым кодом не читаются и ничему не мешают
(`SELECT *` их просто вернёт); WAL снимается
`PRAGMA journal_mode=delete`. Каталоги `.artel/projects/` и
`.artel/home/` — вне git, удаляются вручную.

## Риски

1. **Смена HOME уводит из-под роли всё, что жило в HOME Оператора.**
   Эффектов у этого два, и они разной природы.
   *Git-идентичность* — закрыт в коде (решение 9): без переноса
   `git commit` шага падает с rc=128, ветка задачи остаётся пустой,
   и догфуд-флоу встаёт на первом же прогоне разработчика. Проверено
   пробным коммитом в песочнице с этим окружением
   (`RoleEnvTest.test_commit_of_the_step_passes_with_that_environment`)
   и обратной пробой — без переменных тот же коммит падает.
   *Аутентификация CLI* — открытый вопрос 18 аудита v4 (ADR-0003 п.14),
   решается B-спайком. Здесь реализовано как требует SPEC (п.8):
   подстановка безусловна, тихого отката нет. Наблюдаемый отказ — шаг
   падает с ненулевым rc и после трёх попыток эскалирует с хвостом
   лога, то есть проблема видна Оператору сразу, а не молча меняет
   периметр. Проверка реальным прогоном — за Оператором на приёмке
   (критерий 8); если аутентификация не заведётся, курируемый слой
   `.artel/home/.claude` наполняет Оператор (это и есть «курируемый
   user-слой»), а не код. Что ещё может понадобиться шагу из HOME
   Оператора, покажет тот же прогон: правило — переносить адресно
   и явно, как идентичность, а не открывать слой целиком.
2. **Идентификаторы задач глобальны, а счётчик — per-target.** Пока
   задачи заводятся только для `artel`, коллизии не возникает; второй
   target потребует префикса в идентификаторе (или составного ключа)
   вместе с командой заведения его задач. Это вне объёма A1 (SPEC
   «Не входит»: инварианты мультитаргета — A2), но след оставлен
   здесь, а не в коде-заглушке.
3. **`no_paths` артели объявлены в двух местах** — targets.yaml
   и PROTECTED в `.github/workflows/ci.yml`. Сейчас декларация
   не исполняется кодом (исполнение — A2/A3), расхождение возможно.
   Свести списки в один источник — задача той же A2/A3, где no_paths
   получат исполнителя; в A1 это было бы правкой `.github/`.
4. **Порог программы считается по сумме `spent_usd`.** Шаги, у
   которых стоимость не извлеклась (`agent cost UNKNOWN`), в сумму
   не входят — сумма занижена ровно на них. Это то же свойство, что
   у потолка задачи, и меняется оно вместе с ним, а не отдельно.
