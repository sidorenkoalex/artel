# SPEC: A1 — мультитаргет в конфиге, БД и CLI

## Контекст

Вторая задача фазы A (roadmap §2 A1). Конвейер знает один проект —
сам пульт: нет декларации целевых (targets.yaml), нет каталожной
структуры для их артефактов, БД не различает проекты, нумерация
задач — COUNT(*) (переиспользование номеров при архивации строк),
роли запускаются с HOME Оператора (его ~/.claude/CLAUDE.md, хуки
и MCP исполняются в ролях — конфиг-инъекция, ADR-0003 п.14).
Задача закладывает мультитаргетный фундамент, не ломая текущий
догфуд-флоу (артефакты задач артели остаются в tasks/ пульта
до A7 — ADR-0003 3д, «особый случай»).

## Требования

1. `targets.yaml` в корне пульта, читается кодом (yamlmini):
   поля записи — forge (github|gitlab), url, базовая ветка,
   token_slot, no_paths, project_skills, исполнитель гейта мержа
   (ADR-0003 п.2). Первая запись — artel (forge: github, base:
   main). Невалидный targets.yaml — внятный отказ, не трейсбек.
2. Структура `.artel/projects/<target>/` (workspace/, tasks/,
   knowledge/, logs/ — ADR-0003 3д) создаётся командой подключения/
   инициализации target. Без git-слоя — git init, коммиты
   на переходах и sha в журнал — это A2b.
3. Колонка `target` в таблицах БД (tasks, журнал); существующие
   строки получают target='artel' миграцией. Схема остаётся
   переносимой (без SQLite-экзотики, ADR-0003 3ж).
4. Нумерация задач — персистентный счётчик per-target вместо
   COUNT(*) (orchestrator/catalog.py:47–48): архивация строк
   не переиспользует номера.
5. `PRAGMA journal_mode=WAL` при открытии БД.
6. SQL консолидируется в store.py: вне store.py прямых SQL-запросов
   не остаётся (ADR-0003 3ж «SQL только в store.py»).
7. Пороги суммарного расхода программы: сумма spent_usd по всем
   задачам всех target против стоп-лосса $2000 (roadmap §5);
   при пересечении 70%/90% — предупреждение CLI + событие
   в журнал (таблица alerts появится в A3 — здесь событие журнала).
8. Роли запускаются с отдельным контролируемым
   HOME/CLAUDE_CONFIG_DIR под управлением пульта (ADR-0003 п.14):
   каталог курируемого user-слоя в .artel/, подстановка в окружение
   процесса роли. Если аутентификация CLI из отдельного HOME
   не работает (открытый вопрос 18, решается B-спайком) —
   эскалация с фактурой, не тихий откат на HOME Оператора.

## Критерии приёмки

1. Юнит-тест: чтение targets.yaml с записью artel; невалидная
   запись (нет forge) — отказ с именем поля.
2. Команда инициализации target создаёт структуру 3д; повторный
   вызов идемпотентен (тест).
3. После миграции старые задачи читаются с target='artel'; статусы
   и стоимость T001–T017 не изменились (тест на снапшоте схемы).
4. Тест: создание задачи после архивации строки не переиспользует
   номер.
5. Тест или проверка: journal_mode БД == wal.
6. grep SQL (SELECT/INSERT/UPDATE/DELETE/PRAGMA) вне store.py
   по orchestrator/ пуст (допустимы тесты).
7. Тест: суммарный расход выше 70% порога — предупреждение
   и событие в журнале; выше 90% — второе событие.
8. Запуск роли несёт HOME/CLAUDE_CONFIG_DIR из .artel/ (тест
   на окружение процесса); реальный прогон агента с отдельным
   HOME — ручная проверка Оператора на приёмке.
9. Все существующие тесты и guard --all зелёные; текущий догфуд-флоу
   (задача в tasks/ пульта) работает без изменений.

## Не входит

- Git-первичка projects/<target> (A2b: init, коммиты переходов,
  approve-по-sha).
- doctor, таблица alerts, смоук-тест изоляции, пин CLI (A3).
- Флаги `--setting-sources`/`--strict-mcp-config` (B1a) и адаптеры
  forge (B1b).
- Изменение места артефактов догфуда (до A7 — tasks/ пульта).
- Инварианты мультитаргета и изоляция workspace тестовым слоем (A2).
