# SPEC: Реестр замечаний ревью: жизненный цикл каждого замечания

## Контекст
Сегодня замечание ревью — строка свободного текста в REVIEW.md; код не
отслеживает его судьбу между итерациями. Разработчик может молча не
исправить и не ответить, а следующий вердикт `approved` формально
валиден, хотя замечание никем явно не закрыто (класс дефекта
«замечание рассосалось»; смежный прецедент — T041/T044 в шаблоне
REVIEW.md). Нужно превратить замечание в запись со стабильным
идентификатором и машинно проверяемым жизненным циклом, симметричным
для исходов `fixed` и `rejected` (ANSWER-1: закрытие любого из них —
только явным `accepted` ревьювера, самозакрытие разработчиком
запрещено — тот же класс, что инвариант 6 «молчание ≠ согласие»).

Разработчик увидит только этот SPEC, не исходное ТЗ (`developer_brief`
не читает TZ.md) — поэтому границы зоны и предоставленные ТЗ мандаты
на правку обычно защищённых путей (`templates/`, `skills/`)
перенесены сюда явно (требования 9–11).

## Требования

1. Формат и место хранения записи (решение и обоснование — см. ниже):
   новая обязательная секция `## Реестр замечаний` в
   `templates/REVIEW.md` и в `tasks/<id>/REVIEW.md`, применяется только
   когда `schema_version >= 3` (требование 6). Каждая запись — файл/
   строка (или явная пометка «не применимо»), суть, последствие,
   ожидаемое решение, статус (требование 2) и id вида `R<iteration>-
   F<n>`: `iteration` — номер итерации ревью, в которой запись впервые
   заведена (совпадает с полем `iteration` фронтматтера REVIEW.md той
   итерации), `n` — порядковый номер внутри итерации, с 1, без
   пропусков. Секция кумулятивна: REVIEW.md каждой следующей итерации
   несёт статус каждой ещё не `accepted` записи любой прошлой итерации
   этой задачи; уже `accepted` записи допустимо не повторять — они
   восстановимы из git-истории файла (требование 8).

   Решение: отдельный тип артефакта не заводится, запись живёт внутри
   существующего REVIEW.md. Обоснование: исходное ТЗ даёт мандат
   только на правку `templates/REVIEW.md` и `scripts/guard.py` под
   новый формат — не на новый `type` в `RULES` guard.py и новый
   шаблон; структурная секция внутри уже читаемого ролями артефакта —
   решение с минимальным расширением этого мандата.

2. Статус записи — одно из пяти значений: `open` (заведено ревьювером,
   ждёт разработчика), `fixed` (разработчик отметил исправленным с
   описанием, что исправлено), `rejected` (разработчик отклонил с
   обоснованием, код не менялся), `accepted` (ревьювер подтвердил
   закрытие — терминальный статус), `needs_work` (ревьювер вернул
   запись на новую попытку — разработчик обязан снова разметить её
   `fixed`/`rejected` в следующем цикле, тем же id).

3. Разработчик обязан явно разметить статус `fixed` или `rejected` для
   каждой записи со статусом `open` или `needs_work` до следующего
   выхода из `in_dev` в `review` — правкой той же секции «Реестр
   замечаний» файла `tasks/<id>/REVIEW.md` (это артефакт задачи в
   `tasks/<id>/`, не текст в чате и не сообщение коммита).

4. И `fixed`, и `rejected` закрываются (переходят в `accepted`) ТОЛЬКО
   явным решением ревьювера в следующей итерации ревью — той же
   схемой для обоих исходов, без асимметрии между ними (ANSWER-1).
   Ревьювер в каждой итерации обязан явно пройтись по каждой записи со
   статусом `fixed`/`rejected` прошлых итераций и перевести её в
   `accepted` либо `needs_work`, прежде чем его вердикт `approved`
   вообще сможет пройти гейт требования 5.

5. Машинный гейт: переход `review -> acceptance` (вердикт `approved`)
   отклоняется, если в секции «Реестр замечаний» текущего REVIEW.md
   задачи (`schema_version >= 3`) есть хотя бы одна запись со статусом,
   отличным от `accepted` (`open`, `fixed`, `rejected` или
   `needs_work` — все считаются незакрытыми одинаково). Отказ называет
   id каждой незакрытой записи. Проверка — код в
   `orchestrator/fsm_advance.py::review()` (ветка `status ==
   "approved"`, до перехода в `verifying`), не дисциплина ролей; чтение
   REVIEW.md переиспользует существующий механизм ветко-корректного
   чтения артефактов (например `fsm._read_branch_text_or_refuse`) —
   сам механизм не меняется. Это дополнительное условие поверх уже
   существующей проверки свежести вердикта (инварианты 13, 25 —
   `docs/invariants.md`) — та не ослабляется.

6. Совместимость: REVIEW.md без поля `schema_version` либо с
   `schema_version < 3` не подчиняется требованиям 1–5 — ни guard, ни
   гейт требования 5 не применяют к нему проверки реестра; такие
   задачи и их REVIEW.md проходят guard и переходы без изменений
   поведения. Поддерживаемая версия схемы (`SUPPORTED_SCHEMA_VERSION`
   в `scripts/guard.py`) повышается с 2 до 3; требования реестра
   действуют только при `schema_version >= 3` REVIEW.md — тем же
   приёмом, что guard.py уже применяет к AC-разметке SPEC при
   `schema_version >= 2` (`requires_ac_markup`).

7. `scripts/guard.py` структурно проверяет секцию «Реестр замечаний»
   REVIEW.md со `schema_version >= 3`: секция обязана присутствовать;
   id записей уникальны в пределах файла и соответствуют формату
   `R<число>-F<число>`; статус каждой записи — одно из пяти значений
   требования 2; у каждой записи заполнены все обязательные поля
   требования 1. Содержательность (верно ли выбран статус, действительно
   ли фикс закрывает суть замечания) — не дело guard, как и остальные
   структурные проверки этого файла.

8. История разрешения каждого замечания восстановима из git-истории
   артефактов задачи (коммиты REVIEW.md на каждом переходе —
   существующая hash-фиксация, T021) — отдельное хранилище не
   заводится.

9. `templates/REVIEW.md` и `scripts/guard.py` — пути, правка которых
   обычно требует отдельного MR Оператора (`conventions-core`); мандат
   на их правку под формат реестра этой задачей предоставлен исходным
   ТЗ Оператора и подтверждается им на spec_gate этой задачи.

10. `skills/review-checklist.md` (протокол ревьювера: как присваивать
    id и заполнять поля записи, как оценивать `fixed`/`rejected` →
    `accepted`/`needs_work`) и `skills/coding-standards.md` (протокол
    разработчика: разметка `fixed`/`rejected` перед выходом в review)
    дополняются протоколом реестра. Мандат на правку `skills/` под это
    ТЗ предоставлен тем же исходным ТЗ, подтверждается Оператором на
    spec_gate.

11. Зона задачи: `templates/REVIEW.md`, `scripts/guard.py`,
    `orchestrator/review.py`, тело обработчика `review()` в
    `orchestrator/fsm_advance.py`, `skills/review-checklist.md`,
    `skills/coding-standards.md`. НЕ трогать: `orchestrator/brief.py`,
    `orchestrator/store.py`, `orchestrator/catalog.py`,
    `orchestrator/fixation.py`, `orchestrator/doctor.py`,
    `orchestrator/cleanup.py`, `orchestrator/prune.py`,
    `orchestrator/config.py` — зона параллельной задачи M1 (T094).
    Конфликт зон с этой параллельной задачей — эскалация, не выход за
    границу.

## Критерии приёмки

AC-1. REVIEW.md со `schema_version: 3` и хотя бы одной записью в
секции «Реестр замечаний» — каждая запись несёт id формата
`R<iteration>-F<n>`, поля файл/строка (или пометка «не применимо»),
суть, последствие, ожидаемое решение, статус.

AC-2. `scripts/guard.py` отклоняет REVIEW.md со `schema_version >= 3`,
где секции «Реестр замечаний» нет вовсе.

AC-3. `scripts/guard.py` отклоняет REVIEW.md, где id двух записей
реестра совпадают.

AC-4. `scripts/guard.py` отклоняет запись реестра со статусом вне
множества {open, fixed, rejected, accepted, needs_work}.

AC-5. `scripts/guard.py` отклоняет запись реестра, где отсутствует
хотя бы одно из обязательных полей требования 1 (файл/строка-или-
пометка, суть, последствие, ожидаемое решение).

AC-6. REVIEW.md без поля `schema_version`, либо с `schema_version < 3`,
проходит guard без применения к нему AC-1–AC-5 — так же, как REVIEW.md
прежнего формата до этой задачи.

AC-7. Переход `review -> acceptance` (вердикт `approved`) отклоняется,
если в секции «Реестр замечаний» текущего REVIEW.md (`schema_version
>= 3`) есть хотя бы одна запись со статусом `open`; отказ называет её
id.

AC-8. Тот же переход отклоняется, если есть хотя бы одна запись со
статусом `fixed` без последующего перевода в `accepted` — `fixed` сам
по себе не закрывает замечание.

AC-9. Тот же переход отклоняется, если есть хотя бы одна запись со
статусом `rejected` без последующего перевода в `accepted` —
`rejected` сам по себе не закрывает замечание (симметрия с AC-8,
ANSWER-1).

AC-10. Тот же переход отклоняется, если есть хотя бы одна запись со
статусом `needs_work`.

AC-11. Тот же переход проходит (при прочих условиях перехода,
не изменённых этой задачей: вердикт `approved`, свежий вердикт,
зелёные acceptance_tests), если все записи реестра имеют статус
`accepted`, либо записей в реестре нет вовсе.

AC-12. Переход `review -> acceptance` для REVIEW.md со `schema_version
< 3` (или без поля) не подвергается проверкам AC-7–AC-11 — ведёт себя
как до этой задачи.

AC-13. `skills/review-checklist.md` описывает протокол ревьювера для
реестра (присвоение id и заполнение полей записи, оценка
`fixed`/`rejected` → `accepted`/`needs_work`); `skills/coding-
standards.md` описывает протокол разработчика (разметка
`fixed`/`rejected` перед выходом в review).

## Не входит

- Одноразовый токен раунда ревью (источник задачи, п.4 документа-
  исследования).
- Машинный лимит длины финального ответа ревьювера (источник задачи,
  п.10).
- Доменные критерии ревью (источник задачи, п.7).
- Ретроспективная миграция закрытых задач: REVIEW.md уже завершённых
  задач не переводится на `schema_version: 3` задним числом.
- Отдельный машинный гейт на переходе `in_dev -> review`, проверяющий,
  что разработчик разметил `fixed`/`rejected` перед выходом в ревью:
  исходное ТЗ называет явный машинный гейт (требование 5 этого SPEC)
  только для перехода `review -> acceptance`. Обязанность разработчика
  (требование 3) обеспечивается протоколом ревьювера
  (`skills/review-checklist.md`, требование 10) и транзитивно тем же
  гейтом требования 5 — неразмеченная запись никогда не станет
  `accepted`, значит `approved` никогда не пройдёт гейт, пока
  разработчик её не разметит.
- Правка `orchestrator/brief.py`, `store.py`, `catalog.py`,
  `fixation.py`, `doctor.py`, `cleanup.py`, `prune.py`, `config.py` —
  зона параллельной задачи M1 (T094); конфликт зон с ней — эскалация,
  не выход за границу.
