# PLAN: Реестр замечаний ревью: жизненный цикл каждого замечания

## Подход

Замечание ревью становится строкой markdown-таблицы в новой секции
`## Реестр замечаний` REVIEW.md (id, статус, файл/строка, суть,
последствие, решение) — тем же приёмом версии-гейтинга, что
`requires_ac_markup` уже применяет к AC-разметке SPEC:
`SUPPORTED_SCHEMA_VERSION` поднимается 2 → 3, а сами проверки
применяются только когда `schema_version >= 3` конкретного REVIEW.md
(SPEC, требование 6). Легаси-REVIEW.md (версия ниже 3 или без поля)
проходит guard и переходы без изменения поведения — AC-6, AC-12.

Машинный гейт требования 5 — одна дополнительная проверка в
`orchestrator/fsm_advance.py::review()`, ветка `status == "approved"`,
перед прогоном `acceptance.run` и переходом в `verifying`: если
`schema_version >= 3` и в реестре есть хотя бы одна запись со статусом
не `accepted`, переход отклоняется с перечислением незакрытых id.
Проверка читает уже провалидированный guard'ом REVIEW.md (та же
переменная `review_text`/`meta`, что и выше по функции) — отдельного
чтения с диска или ветки не заводится, чтение остаётся тем же
ветко-корректным механизмом, что уже есть (`_read_branch_text_or_refuse`,
SPEC требование 5).

Разбор таблицы реестра — новые функции в `scripts/guard.py`
(`requires_registry`, `registry_table_rows`, `registry_records`,
`registry_record_errors`, `registry_errors`), переиспользуемые и
структурной проверкой (`check_content`), и гейтом FSM (`registry_records`
— та же логика разбора, не два парсера одной таблицы). Guard проверяет
только форму (id уникален и в формате `R<n>-F<m>`, статус — одно из
пяти значений, все обязательные поля заполнены) — содержательность
(верно ли выбран статус) вне его мандата (докстринг модуля).

Симметрия `fixed`/`rejected` (ANSWER-1, вариант B) реализуется тем, что
гейт требования 5 не различает исходы разработчика вовсе: единственный
статус, пропускающий переход, — `accepted`; `fixed`, `rejected`,
`open`, `needs_work` — все блокируют одинаково. Самоаппрув разработчиком
структурно невозможен: FSM не даёт разработчику стадии, на которой он
мог бы записать `accepted` — это поле выставляет только ревьювер на
следующей итерации REVIEW.md.

Ход работы застал залоченные `tasks/T100/acceptance_tests/` в
переходном состоянии: первый коммит теста (`e412015`) использовал
термин «Леджер замечаний», унаследованный от названия ветки задачи, —
разошедшийся с уже переименованным (коммит `46924ea`) текстом SPEC.md
(«Реестр замечаний»). Коммит `3caf328` (тот же test_author) привёл
тексты и id тестов к текущей терминологии SPEC.md до начала
реализации — вся эта PLAN и код написаны уже по выровненным
`acceptance_tests/`, разночтения на момент сдачи нет. См. «Предложения
системе» — сам класс происшествия стоит зафиксировать на будущее.

## Шаги

1. `scripts/guard.py`: `SUPPORTED_SCHEMA_VERSION` 2 → 3; функции разбора
   и структурной проверки секции «Реестр замечаний»; вызов
   `registry_errors` в `check_content` для `type: review`. Заодно —
   `schema_version` во всех четырёх `templates/*.md` поднят до 3
   (см. «Влияние на систему»: существующий `tests/test_guard_schema.py::
   TemplatesCarryTheVersionTest` требует, чтобы КАЖДЫЙ шаблон нёс
   текущую поддерживаемую версию, не только `REVIEW.md`).
2. `templates/REVIEW.md`: секция `## Реестр замечаний` — формат таблицы,
   формат id, пятёрка статусов, кумулятивность (требования 1, 2, 6, 8).
3. `orchestrator/fsm_advance.py::review()`: машинный гейт требования 5 —
   ветка `status == "approved"`, до прогона `acceptance.run` и до
   перехода в `verifying`.
4. `skills/review-checklist.md` и `skills/coding-standards.md`:
   протокол реестра — как ревьювер присваивает id/статусы и закрывает
   `fixed`/`rejected`, как разработчик обязан разметить запись перед
   выходом в review (требование 10, AC-13).
5. Юнит-тесты `scripts/guard.py` (функции разбора/валидации по
   отдельности — `tests/test_guard_schema.py`) и гейта FSM
   (`orchestrator/fsm_advance.py::review()` — новый файл
   `tests/test_review_registry_gate.py`, песочница `FsmTest`, тот же
   приём, что `tasks/T100/acceptance_tests/
   test_ac7_ac12_review_gate_registry_status.py`, но по функциям
   отдельно — несколько незакрытых записей разом и молчание гейта на
   пустом реестре, случаи, которых нет в залоченных приёмочных тестах).

## Влияние на систему

- `SUPPORTED_SCHEMA_VERSION` 2 → 3 расширяет диапазон принимаемых версий
  вверх, не сужает его: любой существующий артефакт `tasks/*/*.md` с
  `schema_version` ≤ 2 (или без поля) продолжает проходить guard без
  изменения поведения (AC-6, AC-12; вся история задач ниже T100 не
  переиндексируется — требование «Не входит»).
- Новые структурные проверки (`registry_errors`) и новый машинный гейт
  (`orchestrator/fsm_advance.py::review()`) применяются ТОЛЬКО когда
  сам REVIEW.md несёт `schema_version >= 3` — ни один существующий
  REVIEW.md в `tasks/` (все ≤ 2 на момент этой задачи) не подпадает под
  них задним числом.
- `schema_version: 3` в `templates/SPEC.md`, `PLAN.md`, `TEST_REPORT.md`
  — чисто механическая правка одного поля frontmatter, не меняет ни
  одного версии-гейтированного правила этих типов (`requires_ac_markup`
  у SPEC гейтится на `>= 2`, уже выполнено; PLAN/TEST_REPORT версии-
  гейтированных правил не несут вовсе) — правка нужна только чтобы не
  сломать существующий `TemplatesCarryTheVersionTest`, не привносит
  нового поведения. Эти три файла — вне явной «зоны задачи» требования
  11, но и не в списке «НЕ трогать» (тот список — про `orchestrator/*.py`
  параллельной задачи M1); принцип целостности (нельзя ослаблять/ломать
  существующий тест) в данном случае весит больше буквы зоны при
  однострочной механической правке без функциональных последствий —
  альтернатива (не трогать шаблоны) сломала бы зелёный тест не по
  требованию этой задачи, а как побочный эффект.
- Ни `gates.yaml`, ни `roles.yaml`, ни `.github/` не тронуты.
- Откат: диф аддитивен и version-гейтирован — `git revert` возвращает
  `SUPPORTED_SCHEMA_VERSION` к 2 и убирает гейт/проверки; ни одна
  существующая задача не потеряет данные (записи реестра остаются
  текстом внутри REVIEW.md, восстановимы из git-истории — требование 8).

  коммитом теста SPEC.md менялся.
