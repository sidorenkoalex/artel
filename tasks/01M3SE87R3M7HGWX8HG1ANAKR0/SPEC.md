# SPEC: Признак «процесс — шаг роли» для всех провайдеров

## Контекст

Текущий признак окружения роли зависит от `HOME` и
`CLAUDE_CONFIG_DIR`, поэтому для роли на codex он ложен, хотя шаг уже
несёт общий маркер роли. Из-за этого отказы команд пульта, которыми
защищены действия из-под роли, не срабатывают для codex. Признак должен
работать единообразно для окружений шагов всех провайдеров, сохраняя
совместимость с прежним признаком для claude.

## Требования

1. Признак `in_role_environment(env=None)` определяет процесс как шаг
   роли при непустом `ARTEL_ROLE` в переданном окружении или, если оно не
   передано, в окружении процесса; прежняя проверка по `HOME` и
   `CLAUDE_CONFIG_DIR` остаётся альтернативным достаточным условием.
2. Все потребители этого признака используют функцию без изменения
   собственной логики и отказывают роли на codex так же, как роли на
   claude.
3. Офлайн-смок изоляции каждого провайдера проверяет, что собранное
   окружение шага распознаётся как окружение роли.
4. Документация описывает признак и отражает отказ команд пульта
   из-под роли в таблице паритета безопасности для claude и codex.
5. Тесты покрывают распознавание окружений codex, claude и Оператора, а
   также отказы `answer`, `note` и расшифровки пула для роли на codex.
6. Обычные тесты пульта не зависят от `ARTEL_ROLE` окружения, в котором
   запущен pytest; тесты отказов из-под роли задают этот маркер явно.
   Сторож сбора в `conftest.py`, читающий `ARTEL_ROLE`, сохраняет
   действующую защиту.

## Критерии приёмки

AC-1. `in_role_environment(env=None)` возвращает истину, если в
переданном `env` (или в `os.environ` при отсутствии аргумента) задан
непустой `ARTEL_ROLE`; она также возвращает истину при прежнем сочетании
`HOME` и `CLAUDE_CONFIG_DIR`, даже если маркер отсутствует.

AC-2. Все потребители признака продолжают обращаться к
`in_role_environment` без изменения своей логики и отказывают вызовы
из окружения шага роли codex так же, как из окружения роли claude.

AC-3. Офлайн-смок изоляции каждого провайдера проверяет, что
`in_role_environment(env)` возвращает истину для собранного окружения
шага этого провайдера.

AC-4. `docs/stack.md` описывает признак «процесс — шаг роли», а таблица
паритета безопасности содержит для claude и codex значение «да» в
строке отказа команд пульта из-под роли.

AC-5. Тесты подтверждают: окружение шага codex распознаётся как роль;
окружение шага claude распознаётся как роль; окружение Оператора без
`ARTEL_ROLE` и с чужим `HOME` не распознаётся как роль; `answer` в
`in_dev`, `note` и расшифровка пула отказывают для окружения роли codex.

AC-6. При запуске pytest с `ARTEL_ROLE` в окружении все тесты `tests/`,
которые вызывают `answer`, `zones-extend`, `note` или расшифровку пула,
остаются зелёными; проверки отказов из-под роли устанавливают маркер
явно. В частности, зелёными остаются четыре сценария
`ZonesExtendCommandTest` из `tests/test_answer.py` и сценарий
`CanaryPoolDriftCheckTest.test_diverging_pool_warns` из
`tests/test_doctor_canary_pool.py`. Сторож сбора `conftest.py`, читающий
`ARTEL_ROLE` при сборе, не ослаблен.
