# PLAN: канарейка переживает эскалацию по бюджету и позволяет выбрать шаблон

## Подход

Две механики в одном модуле `orchestrator/canary.py` плюс разбор флага в
`orchestrator/artel.py` и две справки. Потолок задачи из SPEC ($40) не
переоценивается: файлов зоны четыре, шагов плана два, оценка SPEC сходится.

**1. Выбор шаблона (требования 1-5).** Рядом с существующей случайной
выборкой `_sample_pool_templates` встаёт вторая, ИМЕНОВАННАЯ ветка
`_named_pool_templates(pool_dir, k, titles)`; развилка — одна, в
`cmd_canary`, по `templates is None`. Прежняя ветка не переписывается
вовсе (требование 4, AC-3): случайная выборка остаётся ровно тем же
вызовом `random.sample` по тому же отфильтрованному списку `*.md`.

Порядок прогона = порядок имён во флаге: `_named_pool_templates`
возвращает `[pool_dir / f"{title}.md" for title in titles]` по СПИСКУ,
не по множеству и не по `sorted` — иначе воспроизвести сценарий пула
командой было бы нельзя (AC-1).

Четыре отказа требования 3 живут там же и срабатывают ДО
`_resolve_target_sha` (он один ходит к origin) и до первого
`_ephemeral_clone`: `--template` без значения — в `artel._template_arg`
(тем же приёмом, что `_set_arg`/`_sha_arg`), остальные три — в
`_named_pool_templates`, куда уже передан прочитанный каталог пула.
Порядок проверок: пустой пул -> число имён ≠ `--k` -> повтор имени ->
неизвестное имя (последнее перечисляет доступные имена, AC-2).

`--k` остаётся обязательным и разбирается первым (требование 2):
`_cmd_canary` зовёт `_k_arg(rest)` раньше `_template_arg(rest)`, поэтому
`canary --template <имя>` без `--k` даёт прежний отказ «нужен параметр
--k».

Первая строка вывода (требование 5) — та же строка «прогон <штамп>: N
задач из пула …», в неё добавляется перечень `stem`'ов в порядке
прогона. Отдельной строки не заводится: строка уже печатается до входа в
цикл по задачам, то есть до первого `git clone` (AC-4), и вторая строка
рядом с ней только удлиняла бы вывод.

**2. Подъём потолка и новый исход (требования 6-11).** Признак
бюджетной эскалации — `detail` последнего перехода `state -> escalated`
с текстом `budget.enforce_budget` (`orchestrator/budget.py:219`), как и
велит требование 6. Сам `budget.py` не правится: согласованный литерал
`_BUDGET_ESCALATION_DETAIL_MARK` живёт в `canary.py` — тем же приёмом,
которым модуль уже дублирует `_AUTO_STOPPED_ACTION` и
`_ACCEPTANCE_TESTS_REFUSAL_ACTION` (оба не экспортируются своими
модулями как публичные имена).

Ветка `escalated` в `_drive_task` получает развилку ПЕРЕД счётчиком
`escalation_cycles`: бюджетная эскалация идёт своим путём и потолок
повторных эскалаций не расходует, все прочие эскалации остаются
байт-в-байт прежними (раздел «Не входит» SPEC).

* первая бюджетная эскалация -> `_raise_task_ceiling`: потолок задачи
  умножается на новую константу `config.CANARY_BUDGET_CEILING_FACTOR`
  (= 2.0), факт подъёма журналируется литералом `_CEILING_RAISE_ACTION`,
  и задача возвращается в `escalated_from` СУЩЕСТВУЮЩИМ
  `_pass_escalated_with_synthetic_answer` — тот же канал возврата, что и
  у остальных эскалаций прогона, включая ANSWER в артефактной ветке;
* вторая (потолок уже поднят) -> `_kill_ceiling_exhausted`: своя
  причина исхода «исчерпан потолок задачи: $X из $Y на шаге <роль>»,
  свой литерал-маркер `detail` (`_CEILING_EXHAUSTED_KILL_DETAIL`), свой
  алерт и штатный `cleanup.cmd_kill`.

«Подъём уже был» читается ИЗ ЖУРНАЛА задачи (`_ceiling_already_raised`),
не из переменной цикла `_drive_task`: переменная обнулялась бы на уходе
из состояния (как `dev_retries`), и поднятый потолок перестал бы быть
конечной верхней границей расхода (требование 8, AC-5).

Числа причины исхода берутся из строки задачи в момент снятия —
`budget.spent_with_estimate(t)` (та же сумма, которой потолок и
пробивается) и `t["budget_usd"]`; роль шага — `config.STATE_ROLE` по
`escalated_from`, который `enforce_budget` записал перед эскалацией.

Исход виден в отчёте прогона потому, что `_kill_outcome_note` узнаёт
новый литерал-маркер и возвращает саму причину, без приписки «не
сошлась» (AC-6). Вердикт строки `canary_runs` — третье значение
`_VERDICT_CEILING_EXHAUSTED = "ceiling"`: `store.green_canary_runs`
отбирает строго `verdict='green'`, поэтому ни `store.py`, ни
`orchestrator/pin.py` не правятся и условие ADR-0013 не ослабляется
(AC-7). Однократный подъём сам по себе вердикт не красит: формула
`_run_verdict` спрашивает про исчерпание поднятого потолка, а в
остальном остаётся прежним `not _needs_diagnostics(...)` (AC-8).

## Влияние на систему

**Что затрагивается за пределами правки.** Строки `canary_runs`
получают третье значение `verdict` («ceiling» рядом с «green»/«red»).
Единственный читатель колонки — `store.green_canary_runs`
(`verdict='green'`), поэтому вход гейта сдвига пина
(`canary.merges_since_last_green_run` -> `pin.cmd_pin_update`,
`doctor.check_canary_trigger`) видит новую строку ровно так же, как
видел бы «red»: не годной для сдвига пина. Новых колонок в
`canary_runs` не добавляется, `orchestrator/schema.py` не правится,
миграции не нужны.

**Инварианты, гейты, лимиты и тесты рядом — и почему не ослабляются.**

* Условие ADR-0013 (`orchestrator/pin.py`, `store.green_canary_runs`)
  не меняется ни строкой: новый исход не зелёный, и это проверяется
  прямым сравнением файла `pin.py` с общим предком ветки и main
  (планка AC-7).
* Потолки `CANARY_MAX_ESCALATION_CYCLES` / `CANARY_MAX_STALL_ITERS` /
  `CANARY_MAX_DEV_RETRIES` сохраняются как есть: бюджетная эскалация
  уходит в свою ветку `_drive_task` ДО счётчика, счётчик при этом не
  обнуляется — то есть прочие эскалации по-прежнему упираются в свой
  потолок с прежним числом кругов.
* Новая константа `CANARY_BUDGET_CEILING_FACTOR` — не ослабление
  лимита, а НОВАЯ верхняя граница там, где её не было: сегодня
  канареечная задача с пробитым потолком не имеет ни подъёма, ни
  границы, она просто снимается как несошедшаяся. Поднятый потолок
  конечен (подъём один за жизнь задачи), а расход прогона ограничен
  «потолок из SPEC × множитель × число задач прогона» (требование 8).
* Прежняя случайная выборка не переписывается: ветка без `--template`
  зовёт ту же `_sample_pool_templates` с теми же двумя отказами `--k`
  (`tests/test_canary.py::SamplePoolTemplatesTest`,
  `CmdCanaryBadInputTest` остаются зелёными без правки).
* `tests/test_canary.py::RunOneTaskVerdictUsesNormalOutcomeTest`
  проверяет формулу вердикта для комбинаций
  `(normal_outcome, mismatch)` — новая ветка `_run_verdict` спрашивает
  третий признак и в остальном сохраняет ту же таблицу истинности,
  поэтому тест держится без правки.
* Ни один существующий тест `tests/` не правится и не удаляется;
  добавляются два новых файла.

**Откат.** Revert одного merge-коммита: правка целиком аддитивна
(новая константа, новые функции, новая ветка `escalated`, новый флаг),
состояние в БД после отката читается прежним кодом — строка
`canary_runs` со значением `verdict='ceiling'` для
`store.green_canary_runs` остаётся просто не зелёной, как и была.

## Риски

* **Чужая залоченная планка смерженной задачи краснеет по построению.**
  `tasks/01M3FQ2Z2PY0E9T5F5WQ207NP5/acceptance_tests/_util.py::set_param_name`
  утверждает, что у `canary.cmd_canary` РОВНО ОДИН параметр помимо `k`
  и `sha`, и падает `AssertionError` при любом следующем параметре
  команды. Требования 1-2 моей SPEC велят завести флаг `--template`
  именно у этой команды (и прямо отвергают второй режим разбора
  аргументов), так что параметр `templates` неизбежен. Правка чужой
  залоченной планки — эскалация, а не правка (tasks/T023), мандата на
  неё эта задача не получала, поэтому планка оставлена как есть.
  Машинного эффекта у этого нет: CI пульта гоняет только `tests/`
  (`.github/workflows/ci.yml:218`), ни один гейт чужие планки не
  исполняет, а `tests/` ничьей подписи `cmd_canary` не читает (проверено
  grep'ом по `inspect`/`signature`). Обходной вариант — второй публичный
  вход `cmd_canary_named_templates` ради того, чтобы интроспекция чужой
  планки осталась довольна, — отвергнут: он ухудшал бы API команды для
  каждого следующего читателя ради теста, который никто не запускает.
  Решение, нужен ли той планке мандат на обновление, за Оператором.
* Значение множителя 2.0 даёт канареечной задаче потолок $50 при
  минимуме $25 по скилу аналитика — наблюдавшийся максимум расхода
  ($26.25, прогон 20260927T123258Z) укладывается с запасом, но при
  дальнейшем росте цены шага крутилку придётся двигать: она для этого и
  названа константой.
* `_pass_escalated_with_synthetic_answer` зовётся теперь и на бюджетной
  эскалации, то есть прогон пишет ANSWER-n.md и на ней. Это осознанно:
  возврат из `escalated` в системе один, и второй канал возврата
  (прямой `set_state` мимо ANSWER) расходился бы с тем, что делает
  Оператор руками.

## Предложения системе

* Планка, утверждающая «ровно один новый параметр» через
  `inspect.signature` публичной команды
  (`tasks/01M3FQ2Z2PY0E9T5F5WQ207NP5/acceptance_tests/_util.py::set_param_name`),
  враждебна любому следующему флагу той же команды: она ловит не
  дефект, а факт развития. Класс — «планка фиксирует форму подписи, а
  не поведение»; стоит записать его в `skills/test-authoring.md`
  запретом на утверждения о ПОЛНОМ составе параметров публичной
  функции.
* `docs/backlog.md`/копилка не знают правила «чужая залоченная планка
  смерженной задачи стала красной от законной правки»: у разработчика
  нет канала закрыть её, кроме раздела «Риски» PLAN, а у Оператора нет
  сигнала, что мандат нужен. Класс подтверждён этой задачей впервые.
