# SPEC: `amend-tests` гоняет трассируемость AC перед сдвигом лока планки

## Контекст

`orchestrator/amend.py` несёт два входа, сдвигающих `tests_locked_sha`:
`_cmd_amend_tests` (правка в worktree) и `_cmd_amend_tests_from_branch`
(расхождение между `tests_locked_sha` и головой артефактной ветки). Ни
один из них не вызывает `guard.acceptance_traceability_errors`: правка
планки может снять тест критерия или поставить пометку `# AC-n: manual`
с отступом, и лок сдвинется без отказа. Гейт `tests_writing -> in_dev`
эту проверку уже делает; `amend-tests` — второй вход в ту же планку,
проверка должна быть той же (копилка 11.09, инцидент 01M1THKWFX,
AC-7).

Зависимость: детекцию маркера `# AC-n: manual` с отступом добавляет
задача 01M28NX43E в модуль `guard` (вне зон этой задачи); на момент
написания этого SPEC она не смержена в main. AC-6 (тест на индентацию)
зависит от этого мержа — до него тест красен по причине вне зоны этой
задачи, не по дефекту реализации.

## Требования

1. `_cmd_amend_tests` (worktree): после проверки «есть изменения и
   только в `acceptance_tests/`» и до коммита в артефактную ветку /
   сдвига `tests_locked_sha` вызывается `guard.acceptance_traceability_
   errors(tdir)` по правленной планке; непустой список — отказ.
2. `_cmd_amend_tests_from_branch`: та же проверка по содержимому головы
   артефактной ветки (SPEC.md и `acceptance_tests/` с ветки, не с
   диска worktree), до сдвига `tests_locked_sha`.
3. Проверка не ослабляет существующие: прогон планки (`acceptance.
   run`), маркеры «Красен до реализации» (`guard.scan_redness_
   markers`), сверка содержимого с артефактной веткой — остаются как
   были; порядок — сначала трассируемость, потом прогон.
4. Тесты покрывают: (а) правку, снимающую единственный тест критерия
   без пометки; (б) правку, ставящую пометку `# AC-n: manual` с
   отступом; (в) корректную правку; (г) те же (а) и (в) для
   `--from-branch`; (д) существующие тесты `amend-tests` остаются
   зелёными без правки их утверждений.

## Критерии приёмки

AC-1. В `_cmd_amend_tests` (worktree-путь) после проверки «есть
изменения и только в `acceptance_tests/`» и до коммита в артефактную
ветку / сдвига `tests_locked_sha` вызывается `guard.acceptance_
traceability_errors(tdir)` по правленной планке; непустой результат —
отказ `sys.exit` с текстом «[<id>] amend-tests: отказ — трассируемость
AC нарушена: <ошибки guard через '; '>», `tests_locked_sha` не
сдвинут, коммита в артефактную ветку нет.

AC-2. Такой отказ пишет запись в журнал задачи актором `operator`.

AC-3. В `_cmd_amend_tests_from_branch` та же проверка выполняется по
содержимому SPEC.md и `acceptance_tests/` головы артефактной ветки (не
с диска worktree), до сдвига `tests_locked_sha`; непустой результат —
отказ тем же текстом, что AC-1; `tests_locked_sha` не сдвигается.

AC-4. Существующие проверки (`acceptance.run`, `guard.scan_redness_
markers`, сверка содержимого с артефактной веткой) не ослаблены;
порядок — сначала трассируемость, затем прогон планки.

AC-5. Тест: правка worktree, снимающая единственный тест критерия без
пометки, — отказ, называющий критерий, `tests_locked_sha` не сдвинут.

AC-6. Тест: правка worktree, ставящая пометку `# AC-n: manual` с
отступом, — отказ тем же путём детекции, что у гейта `tests_writing ->
in_dev` (задача 01M28NX43E); тест зависит от мержа 01M28NX43E в main.

AC-7. Тест: корректная правка worktree — `tests_locked_sha` сдвинут
как раньше.

AC-8. Тест: сценарии AC-5 («снят единственный тест критерия без
пометки» — отказ) и AC-7 («корректная правка» — лок сдвинут) — те же
для `--from-branch`.

AC-9. Существующие тесты `amend-tests` остаются зелёными без правки их
утверждений.

## Не входит

- Изменение правил трассируемости `guard` (регулярки, формат пометок,
  формулировки ошибок) — эта задача только вызывает существующую
  `guard.acceptance_traceability_errors`, не меняет её.
- Ретро-проверка уже сдвинутых локов (задним числом по задачам,
  прошедшим `amend-tests` до этой правки).
