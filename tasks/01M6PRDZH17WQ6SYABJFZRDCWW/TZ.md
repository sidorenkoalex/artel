# Тест compose с настоящим Docker: каталог дополнений Docker в подставном DOCKER_CONFIG

## Факты

1. Тест `test_ac17_real_docker_compose_run` (`tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py`, задача 01M6PAJ61D4PYAP79ADRPA6MWV, смержена a8dbea5e) поднимает настоящий стенд Docker Compose через `acceptance.report_run` и проверяет: прогон зелёный, отказа нет (`:326`), проектов compose с префиксом задачи после прогона не осталось (`:327`); в `finally` снимает оставшиеся проекты `down -v` (`:331`).
2. Тест пропускается при условии `SKIP_REASON is not None` (`:259`); причины — `docker_skip_reason` (`:93-123`): выставлена `CI`, программы `docker` нет в PATH или она не отвечает, нет образа `alpine:3` в локальном кэше. Проба выполняется при импорте модуля (`:126`: `docker version`, `docker image inspect` — только чтение).
3. Перед прогоном тест подставляет пустой временный каталог: `docker_config = Path(tempfile.mkdtemp(prefix="artel-docker-config-"))` (`:314`), очистка `shutil.rmtree` (`:315`), `monkeypatch.setenv("DOCKER_CONFIG", str(docker_config))` (`:316`), `HOME` — родитель этого каталога (`:317`); окружение `env` для `compose_projects` снимается после подмены (`:321`).
4. Docker Desktop ищет дополнение `compose` в `<DOCKER_CONFIG>/cli-plugins`. В пустом каталоге его нет: `DOCKER_CONFIG=$(mktemp -d) docker compose version` — «docker: unknown command: docker compose», код 1; с символической ссылкой `cli-plugins` в том же каталоге — версия Compose, код 0, Docker в каталоге ничего не создаёт; `shutil.rmtree` удаляет ссылку, не трогая содержимое цели.
5. Опыт Оператора 05.11 на a8dbea5e: с образом `alpine:3` в кэше тест красный — `report_run` возвращает отказ «отказ запуска compose: … config --format json вернул код 125: unknown flag: --project-name; стенд не поднимался». Со ссылкой `cli-plugins` в подставном каталоге — 6 passed, стенд поднят и снят, контейнеров и сетей `artel-*` не осталось. Без образа — 5 passed, 1 skipped; поэтому в CI и у ролей дефект не виден.
6. Утверждение `:327` и очистка `finally` сейчас ничего не проверяют: `compose_projects` (`:246-256`) зовёт `docker compose ls` с окружением подставного каталога, команда неизвестна, пустой вывод разбирается как `[]`. После правки обе проверки начинают работать — правка тест усиливает.
7. Код ядра дефекта не содержит: окружение вызова `docker` у пульта — `DOCKER_CONFIG`, заданный у пульта, иначе `<HOME>/.docker` (`orchestrator/acceptance.py:871-872`), то есть настоящая конфигурация с дополнениями.

## Требуется

1. В файле `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py` — вспомогательная функция `docker_config_sandbox() -> Path`: создаёт пустой временный каталог (как `:314`) и, если существует каталог дополнений настоящей конфигурации, кладёт в него символическую ссылку `cli-plugins` на этот каталог. Настоящая конфигурация определяется по окружению в момент вызова, тем же правилом, что `acceptance.py:871-872`: `os.environ.get("DOCKER_CONFIG")` (пустая строка — отсутствие), иначе `os.environ.get("HOME") or Path.home()`, затем `/.docker`; цель ссылки — `Path(<настоящая>) / "cli-plugins"`. Каталога дополнений нет — ссылка не создаётся. Возвращает подставной каталог.
2. В подставной каталог не попадает ничего, кроме этой ссылки: `config.json` и прочие файлы настоящей конфигурации не копируются и не связываются ссылками; каталог дополнений не копируется (только ссылка).
3. `test_ac17_real_docker_compose_run` получает подставной каталог вызовом `docker_config_sandbox()` до подмены `DOCKER_CONFIG` и `HOME` вместо прямого `tempfile.mkdtemp` (`:314`); очистка (`:315`) и подмена (`:316-317`) берут результат помощника.
4. Условие пропуска (`:259`), утверждения `:326-327`, очистка стенда в `finally` и прочие тесты файла не меняются; докстринги модуля (`:8`) и теста (`:269`) дополняются строкой о ссылке `cli-plugins`. Правка добавляет строки подготовки и не меняет утверждений и маркеров пропуска; находка гейта неослабления тестов — эскалация с именем теста.

Критерии приёмки (новые тесты — в новом долгоживущем файле задачи; проверка подготовки сама `docker` не вызывает, проба при импорте модуля — прежняя):
- при `DOCKER_CONFIG`, указывающем на вымышленную конфигурацию во временной песочнице с каталогом `cli-plugins` и файлом `config.json`, `docker_config_sandbox()` возвращает каталог, в котором есть ровно один элемент — символическая ссылка `cli-plugins`, `os.readlink` которой равен `<вымышленная>/cli-plugins` (не самой конфигурации), файла `config.json` нет;
- при неустановленном `DOCKER_CONFIG` и вымышленном `HOME` с `<HOME>/.docker/cli-plugins` ссылка ведёт на `<HOME>/.docker/cli-plugins`; при `DOCKER_CONFIG=""` — так же;
- при отсутствии каталога дополнений в настоящей конфигурации ссылка не создаётся, помощник не падает и возвращает пустой каталог;
- после `shutil.rmtree` возвращённого каталога цель ссылки и её содержимое на месте (ловит копирование вместо ссылки и очистку по ссылке);
- два вызова подряд при `DOCKER_CONFIG`, указывающем на вымышленные конфигурации A и B (у каждой есть `cli-plugins`), дают ссылки на `A/cli-plugins` и `B/cli-plugins` соответственно (ловит вычисление пути при импорте модуля и кэширование);
- статическая проверка (`ast`) тела `test_ac17_real_docker_compose_run`: есть присваивание `<имя> = docker_config_sandbox()` раньше вызова `acceptance.report_run`; `monkeypatch.setenv("DOCKER_CONFIG", str(<имя>))` и `real_git.addCleanup(shutil.rmtree, <имя>, …)` используют это имя; вызова `tempfile.mkdtemp` в теле нет.

Проверяют ревьювер и разработчик (не автотестом): условие пропуска, утверждения и `finally` теста `test_ac17_real_docker_compose_run` не изменены (утверждения и маркеры пропуска держит гейт неослабления тестов, `finally` — ревьювер по диффу); при `CI=1` прежний файл даёт 5 passed, 1 skipped.

Безопасность тестов: в новых тестах задачи настоящие конфигурации Docker не читаются и не меняются — только вымышленные во временной песочнице через подмену `DOCKER_CONFIG`/`HOME`; образы не скачиваются, контейнеры не запускаются; `test_ac17_real_docker_compose_run` у Оператора только ссылается на настоящий каталог `cli-plugins`, ничего в нём не создавая. Настоящий прогон с Docker — проверка Оператора вне шага роли (решение Оператора 05.11: шаг роли Docker не получает).

Существующие тесты: правка `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py` по требованиям 1–4 (без изменения утверждений и маркеров пропуска); правка других существующих тестов — эскалация.

Зоны: `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py`, `tests/` (долгоживущие файлы задачи).

Только чтение: `orchestrator/acceptance.py`, `orchestrator/advance_gates/test_integrity.py`.

Не входит:
- правка кода раннера `compose` и окружения вызова `docker`;
- дополнения Docker, найденные через `cliPluginsExtraDirs` в `config.json` или в системных каталогах (правка верна для расположения дополнений Docker Desktop в `<DOCKER_CONFIG>/cli-plugins`);
- молчаливый `[]` в `compose_projects` при ошибке разбора вывода (`:246-256`) — отдельной строкой бэклога: её пишет сессия Оператора командой `note`, роль — в разделе «Предложения системе»;
- новая команда пульта для правки тестов после мержа (решение Оператора 05.11: такие дефекты — отдельной задачей);
- скачивание образов и прогоны с настоящим Docker в шаге роли.
