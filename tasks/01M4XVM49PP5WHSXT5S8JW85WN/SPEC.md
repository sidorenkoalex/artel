# SPEC: Полный suite-run из шага developer: машинное соблюдение контракта

## Контекст

Контракт developer разрешает планку, тесты затронутых модулей и повтор упавших, но запрещает новый полный набор. Публичный `cmd_suite_run` сейчас запускает полный набор фоном со снятым `ARTEL_ROLE`, а миссия developer предлагает такой запуск. Это приводит к лишним полным прогонам и отказам среды роли. Ответ Оператора ANSWER-1.md от 14.10.2026 с принятым ADR-0024 согласовал адресную миграцию пяти прежних сценариев и подтверждение developer по существующему process/lease-контексту.

## Требования

1. До исправления воспроизвести через публичный `cmd_suite_run` вызов без `--failed` из подтверждённого шага developer: подменить запуск процесса и зафиксировать попытку нового полного запуска. Настоящий полный `tests/` для этого не запускать. После исправления тот же маршрут должен завершаться именованным отказом, называющим контракт developer и допустимые адресные тесты, планку и `suite-run --failed`.
2. Отказ новому полному запуску developer происходит до открытия БД с правом записи или создания БД, `deliver_journal`, любых новых записей, файлов, лога, замка, фонового PID и иных побочных эффектов. Для установления process/lease-контекста допустимо только чтение существующей БД без побочных эффектов. Уже идущий прогон не изменяется.
3. Подтверждение developer означает установленную по существующим сведениям process/lease принадлежность вызывающего процесса живому шагу и точную роль этого шага. Контракт одинаков для Codex, Claude и других провайдеров; имя CLI не является источником роли. Один HOME, `ARTEL_ROLE`, пара `ARTEL_ROLE`/`ARTEL_TASK` или состояние задачи запрошенного прогона сами по себе не удостоверяют вызывающий шаг. При подтверждённой принадлежности developer потеря `ARTEL_ROLE` не разрешает новый полный запуск. Когда принадлежность и роль не доказаны, действует прежний маршрут, включая случайную роль и общий HOME без маркера. Нельзя выводить роль Оператора из состояния запрошенной задачи. При невозможности переносимого подтверждения необходима эскалация, без новой песочницы или ослабления существующих guard'ов.
4. Запрет относится только к новому полному запуску: developer сохраняет адресные тесты, планку, `--failed` по прежним условиям, чтение статуса уже идущего прогона обычным `suite-run <id>` и `--wait`. Статус и ожидание не запускают второй прогон. Команда не снимает признаки developer для разрешения запрещённого полного запуска.
5. Полные запуски Оператора и прочих ролей, обязательные полные гейты и CI сохраняют прежние исходы, таймауты, общий замок, повторное использование результатов и метрики. Отделённый фоновый разрешённый прогон, включая ветку и базу, не получает ошибочную блокировку вследствие наследования контекста роли. Существующая очистка окружения разрешённого прогона сохраняется; она не используется для обхода требования 2.
6. Миссия developer в `orchestrator/role_prompt.py` согласована с запретом нового полного запуска: содержит разрешённые адресные проверки, планку, команды повтора упавших, статуса и ожидания с полным путём пульта. Обычная команда без флага описана как чтение статуса уже идущего прогона. Существующие утверждения теста миссии сохраняются. В `orchestrator/runner.py` допустимы только чтение/передача подтверждённого контекста.
7. По ANSWER-1.md и ADR-0024 миграция прежнего разрешения developer ограничена пятью методами из матрицы ниже. Для разрешённых запусков сохраняются имена методов, виды и строгость assertions, прежние исходы и защитные свойства отчётов green/red, отложенного журнала и досыла, общего замка в обоих направлениях, пределов/timeout, размещения логов ветки и базы. Простое исключение developer без новых проверок раннего отказа и его разрешённых операций недопустимо. Мандат не распространяется на общие helpers или весь файл; потребность изменить общий helper требует новой эскалации с точным адресом. Удаление, переименование, skip/xfail, retries, повышение лимитов и смягчение assertions не разрешены.
8. Инвентаризация вызовов, тестов, скилов и брифов `suite-run`/`suite_run` фиксирует старые и новые исходы и сохранённые свойства пятиколоночной матрицей. Новые проверки проходят через публичный `cmd_suite_run` и проверяют наблюдаемое поведение, включая отсутствие побочных эффектов отказа, провайдеры и разрешённые маршруты. Проверки свойства, уже удерживаемого долгоживущим тестом, повторно отдельным тестом не заказываются: сохраняется существующий носитель; новые сценарии покрывают изменённую границу.

## Критерии приёмки

AC-1. На исходном коде публичный `cmd_suite_run` без `--failed` из подтверждённого живого шага developer достигает подменённого запуска полного набора; факт и способ воспроизведения отражены в PLAN. Настоящий полный `tests/` при воспроизведении и в шагах ролей для проверки задачи не запускается (требования 1, 8).

AC-2. После исправления новый полный запуск подтверждённого developer получает именованный отказ с контрактом и допустимыми адресными тестами, планкой, `--failed`. Наблюдение побочных эффектов подтверждает отсутствие открытия БД на запись/создания БД, новых записей, вызова `deliver_journal`, файлов, лога, замка, фонового PID и запуска; чтение существующей БД без побочных эффектов допустимо (требования 1–2).

AC-3. В контекстах живого шага Codex и Claude, подтверждённых через существующие process/lease, новый полный запуск developer запрещён и при наличии, и при потере `ARTEL_ROLE`. Решение относится к вызывающему шагу, а не только к состоянию или id запрошенной задачи; имя провайдерского CLI не определяет решение. Один маркер или пара переменных без подтверждения процесса не считаются удостоверением developer (требование 3).

AC-4. При недостаточном или противоречивом контексте, не подтверждающем принадлежность живому developer-шагу, новый запрет не применяется. Старые сценарии случайного `ARTEL_ROLE` и HOME роли без маркера сохраняют запуск ветки и отчёт `--wait`; существующие assertions `RoleEnvironmentTest::test_ac22_role_process_is_not_refused` не заменяются ожиданием отказа. Потеря маркера при доказанной принадлежности проверяется отдельно по AC-3 (требование 3).

AC-5. Оператор и прочие роли сохраняют полный запуск. Разрешённый отделённый фон доходит до прогонов ветки и базы без ложного отказа по роли; прежняя проверка отсутствия `ARTEL_ROLE` в окружении разрешённых прогонов сохраняется. Состояние запрошенной задачи `in_dev` само по себе не блокирует Оператора (требования 3, 5).

AC-6. Подтверждённый developer может выполнить `suite-run --failed`: повторяет только ранее упавшие проверки по прежним условиям. Прежние исходы при отсутствии прошлого прогона или упавших сохраняются; новый полный прогон вместо повтора не запускается. Доступность планки и тестов затронутых модулей не меняется (требование 4).

AC-7. При уже идущем прогоне обычный `suite-run <id>` подтверждённого developer сообщает статус без второго запуска и изменения идущего прогона; `--wait` сохраняет прежние отчёт, исходы завершения и ожидания, не запускает новый прогон (требования 2, 4).

AC-8. Сформированная миссия developer явно запрещает новый полный набор и содержит адресные тесты, планку, формы `python3 <путь пульта>/orchestrator/artel.py suite-run <id>` для статуса уже идущего прогона, `--wait` и `--failed`. Метод `MissionTest::test_ac25_developer_mission_names_suite_run_with_pult_path` сохраняет все прежние утверждения (требование 6).

AC-9. Существующий метод `ReadonlyDbOutcomeTest::test_ac4_readonly_db_run_reaches_same_outcome_and_report` сохраняет проверки разрешённых прогонов с БД только на чтение: зелёный отчёт с успешным исходом, красный с кодом 1, отсутствие обрыва исключением и записи в журнал из процесса без права записи. Отдельный подтверждённый developer получает ранний отказ AC-2 (требование 7).

AC-10. Метод `JournalRedeliveryTest::test_ac5_pult_process_delivers_journal_record` сохраняет прежние проверки: разрешённый прогон с БД только на чтение оставляет отложенную запись, штатный процесс пульта её досылает в журнал задачи. Новый отказ developer не создаёт и не досылает запись (требования 2, 7).

AC-11. Метод `SharedLockTest::test_ac6_role_suite_run_and_gate_share_one_lock_file` сохраняет оба направления общей блокировки: при замке гейта разрешённая роль не запускает фон и получает id держателя; при замке разрешённого suite-run гейт не запускает pytest и возвращает прежний исход «прогон не начат». Новый полный запуск developer отказывает до взятия замка (требования 2, 5, 7).

AC-12. Метод `LimitUnchangedTest::test_ac8_readonly_db_run_keeps_profile_limit_and_timeout_outcome` сохраняет проверки предела из профиля и его источника для ветки и базы разрешённого прогона. При прежнем тестовом пределе 3 секунды превышение даёт прежний текст с пределом и источником и код 1; пределы не повышаются (требования 5, 7).

AC-13. Метод `LogPlacementTest::test_ac9_suite_run_logs_live_under_suite_run_dir` сохраняет прежние проверки разрешённых запусков: логи ветки и базы находятся в каталоге suite-run, новые логи вне него отсутствуют, указанные в отчёте пути существуют. Отказ developer не создаёт файлов (требования 2, 7).

AC-14. Сохраняются обязательность полных гейтов/CI и их свойства: действующие таймауты, общий замок, условия повторного использования результатов и метрики. Существующее покрытие этих свойств из инвентаризации сохраняется; новый запрет вызывающего developer не блокирует штатный полный прогон гейта (требование 5). Это проверка неизменности маршрутов, а не отдельный заказ полного набора в шаге роли.

AC-15. Инвентаризация и матрица согласованы с итоговой правкой: каждое изменённое разрешение имеет новый проверяемый исход, каждое сохраняемое свойство — прежний носитель проверки либо новое покрытие изменённой границы. Миграция старых сценариев ограничена пятью указанными методами; имена, виды и строгость assertions, пределы и исходы разрешённых запусков сохранены, helpers не изменены на основании этого мандата. Простое удаление developer из общего набора ролей без проверок AC-2–AC-7 не принимается (требования 7–8).

## Оценка объёма и деление

Сигнал большого объёма — 15 критериев приёмки (порог 10). Планируемый объём — три модуля кода и несколько тестовых файлов, до семи файлов без автогенерируемой карты; бюджет $45 соответствует классу до 15 критериев / до 7 файлов, включает две итерации ревью и не повышает исходную рамку $50. Зона `tests/` не означает заказ правок всех найденных файлов: сохраняемые свойства остаются в существующих носителях.

Обоснование монолита: запрет публичного запуска, подтверждение вызывающей роли, согласование миссии и адресная миграция прежних сценариев образуют одну смену контракта. Выпуск запрета отдельно оставляет прежние тестовые гарантии успешного developer-запуска и миссию противоречащими поведению; выпуск миграции тестов отдельно оставляет новый запрет непроверяемым на действующей механике. Независимых законченных изменений по границам разрешённых зон здесь не выделено. Решение о монолите остаётся за Оператором на гейте SPEC.

## Не входит

- Выборочные тесты по покрытию, изменение cache CI и цен; повышение потолка задачи.
- Запрет suite-run Оператору, изменение доступа прочих ролей, состава полного набора или обязательности гейтов; общая песочница и новое удостоверение вне существующих каналов runner.
- Обещание блокировать произвольный самостоятельный `python -m pytest` сверх существующего сторожа; ослабление существующих guard'ов.
- Ручная правка защищённых путей. `skills/coding-standards.md` — только чтение; необходимость дополнительных согласований защищённых скилов/брифов оформляется приложением PLAN по существующей механике. Прямые зоны этой задачи их не включают.
- Изменения `orchestrator/runner.py` вне чтения/передачи подтверждённого контекста и `orchestrator/role_prompt.py` вне миссии developer.
- Изменение общих helpers и иных старых тестов по адресному мандату ANSWER-1.md; если такой мандат потребуется, необходима эскалация с точным носителем. Защищённые тестовые пути внутри tests/ также не разрешены широкой зоной.
- Новый переход FSM, публикация ADR ролью и изменение решения ADR-0024. Принятый текст ADR уже содержится в ANSWER-1.md; его публикация остаётся действием Оператора.
- Полный зелёный набор tests/, зелёный CI ветки, неизменность защищённых путей и соблюдение бюджета как отдельные AC — их держит пульт. Проверка CI main после мержа, названная в ТЗ, относится к сопровождению мержа пультом/Оператором, не к запуску полного набора ролью.
