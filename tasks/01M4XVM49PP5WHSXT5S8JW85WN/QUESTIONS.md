# QUESTIONS: Полный suite-run из шага developer

## Вопросы

1. **Как согласовать запрет полного запуска developer с прежними тестами, которые прямо требуют такого запуска?** В `tests/test_01m4kg7vhhxtvtw5ttx2pgy5ry_suite_run_readonly_db.py:60,155,219–220` выбирается в том числе `developer`, передаются `ARTEL_ROLE` и `ARTEL_TASK`, а задача находится в `in_dev` (183). Пять методов ниже требуют успешного запуска или отказа именно по занятому замку. Это конфликт контракта, а не только смена скалярного ожидаемого значения. Пункт 4 ТЗ требует решения до SPEC; общего мандата «без ослабления» недостаточно для молчаливого исключения developer из старых сценариев.
   - A) Согласовать миграцию сценариев: прежние проверки полного разрешённого прогона сохранить для Оператора и остальных ролей, а для подтверждённого developer проверять ранний отказ без побочных эффектов; разрешённые developer `--failed`, статус и `--wait` проверять отдельно. Дать адресный мандат на изменение области сценариев пяти перечисленных методов; если сужение прежнего охвата квалифицируется как ослабление, оформить решение Оператора через ADR до реализации.
     - ломается: прежняя гарантия полного запуска из developer заменяется запретом; проверки отчётов, досыла журнала, замка, таймаутов и размещения логов для разрешённых запусков сохраняются. Простое удаление developer из ROLES без нового покрытия не разрешается.
     - ослабляется: прежняя область гарантии «полный запуск из любой из трёх ролей» сужается для developer; носители — указанный файл:60,155,219–220 и методы:303,341,407,435,473. Защитные свойства разрешённых прогонов не ослабляются; сокращение области требует решения Оператора, не обхода гейта.
     - цена: согласование пяти сценариев и новые проверки запрета/разрешённых путей в рамках $50; при необходимости — отдельное операторское ADR.
     - чьё решение: Оператор.
   - B) Сохранить прежний контракт и все сценарии без изменений; отложить машинный запрет developer до отдельного решения о миграции контракта.
     - ломается: требование 1 текущего ТЗ не реализуется; полный запуск developer остаётся возможным.
     - ослабляется: ничего в существующих тестах и гейтах; сохраняется известное расхождение с `skills/coding-standards.md:107–115`.
     - цена: остановка текущей задачи и отдельное согласование; дальнейшая разработка запрета не начинается.
     - чьё решение: Оператор.
   - дефолт: B — без адресного решения прежние гарантии не сужать. Дефолт относится к пропущенному пункту ответа, а не разрешает продолжить без ответа на батч.

2. **Какие признаки считаются достаточным подтверждением developer и что делать при неполном/противоречивом контексте?** Общий HOME и `runner.in_role_environment` не дают точную роль. `runner.role_env` передаёт точную роль и задачу, но ТЗ запрещает опираться на один ненадёжный маркер. От этого выбора зависит, какие вызовы обязаны получить отказ и какие старые тесты затрагиваются.
   - A) Достаточно согласованной пары runner: `ARTEL_ROLE=developer` и `ARTEL_TASK` существующей задачи, для которой `runner.step_role` подтверждает developer. Речь о задаче вызывающего шага, а не обязательно об id запрошенного прогона. Без этой совокупности новый запрет не применяется: один общий HOME, случайная роль, отсутствующий/неизвестный ARTEL_TASK или противоречие роли состоянию сохраняют прежний маршрут. Штатная команда не снимает признаки ради разрешения нового полного запуска.
     - ломается: полный запуск при подтверждённой паре developer/задача становится отказом; удаление/подмена части контекста самим процессом не покрывается новой гарантией. Это ограничение должно быть явно принято в SPEC.
     - ослабляется: ничего в существующих guard'ах; старые разрешения случайной роли и HOME без маркера сохраняются (`tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py:579–601`). Конфликт полных запусков developer из вопроса 1 остаётся и требует его решения.
     - цена: чтение/сверка существующего контекста и проверки полного, неполного и противоречивого окружения; без нового канала удостоверения шага.
     - чьё решение: Оператор определяет достаточность подтверждения; реализация — роль developer.
   - B) Пары переменных и состояния недостаточно: требовать подтверждения принадлежности вызывающего процесса живому шагу runner через существующие сведения о процессе/lease; при такой подтверждённой принадлежности developer запрет сохраняется и после потери ARTEL_ROLE. Когда принадлежность и точная роль не доказаны, сохранять старый разрешённый маршрут, включая HOME без маркера и случайную роль. Не выводить developer только из состояния запрошенной задачи.
     - ломается: вызовы из подтверждённого живого шага developer блокируются также при неполном окружении; синтетические вызовы без привязки к живому шагу сохраняют старый исход. Полный операторский запуск не должен ошибочно наследовать роль задачи.
     - ослабляется: ничего в прежних guard'ах и разрешениях общего HOME; источник процесса уже существует (`orchestrator/runner.py:74–92,1570–1583`), но доступность и переносимость подтверждения для дочерних команд Codex/Claude предстоит проверить. Нельзя объявить любой HOME подтверждением developer.
     - цена: дополнительная проверка связки процесса, живого шага и роли, включая отделённый фоновый разрешённый прогон; при невозможности уложиться в существующие каналы/зоны потребуется новая эскалация, не новая песочница.
     - чьё решение: Оператор определяет требуемую силу подтверждения; реализация — роль developer.
   - дефолт: A — наиболее узкое изменение на явно передаваемом runner контексте с сохранением старых исходов при недостатке данных; допустимо только после принятия указанного ограничения Оператором.

## Контекст

ТЗ прочитано целиком. БД проверена только чтением: `spec_writing`, target `artel`, рамка $50, `merge_after` не задан. SPEC не создавался и не изменялся. Код и тесты не менялись; полный набор не запускался. Воспроизведение с подменой процесса пока не выполнялось: приведённые выводы получены чтением кода, а не выдаются за эксперимент.

`orchestrator/suite_run.py:726–798`: публичный вход открывает БД через `_db`, досылает журнал (734), далее обрабатывает ожидание и текущий запуск, берёт замок (767), создаёт лог и запускает процесс (784), снимая `ARTEL_ROLE` (781–782). `_db` сначала вызывает пишущий `store.db` (158–166). Поэтому требование отказа без побочных эффектов затрагивает и открытие БД, а не только Popen или deliver_journal.

`orchestrator/runner.py:1042–1045` передаёт роль/задачу; `1051–1068` даёт только общий признак роли. `step_role` определяет роль состояния задачи, не идентичность вызывающего процесса. В `1570–1583` runner записывает pgid агента в существующий lease; отсутствие lease предусмотрено. Никакой из этих источников сам по себе не делает общий HOME доказательством developer.
