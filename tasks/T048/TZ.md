# ТЗ: ТЗ рождается в ветке задачи (ADR-0005 п.9)

ТЗ рождается в ветке задачи (ADR-0005 п.9; решение Оператора 27.08, строка P3 «ТЗ рождается в ветке задачи — после T045»).

Проблема и принцип: по ADR-0005 п.9 изменения от конвейера попадают в main единственным путём — merge-последовательностью merge_gate; прямых коммитов конвейера в main вне этого окна не появляется. Сейчас cmd_new создаёт tasks/<id>/TZ.md и SPEC.md (шаблон) в рабочей копии main untracked, и их коммитит Оператор руками («Tnnn: ТЗ Оператора» — ручной шаг, забывание которого стоило $9 буксовки в T035; страхует только стоп-кран T038). Класс закрывается конструкцией: ТЗ и шаблон SPEC рождаются сразу в ветке задачи.

Что сделать: cmd_new (orchestrator/catalog.py) после проверок и выдачи номера: (1) создаёт ветку задачи task/<id>-<slug> от config.MAIN_BRANCH (ветки ещё нет — создать; есть — именованный отказ, задача не создаётся, номер не расходуется — тем же принципом «сначала все проверки, потом побочные эффекты», что существующий отказ при нечитаемом ТЗ); (2) создаёт worktree задачи штатной механикой T045 (workspace) и пишет TZ.md + SPEC.md-шаблон в worktree; (3) коммитит их в ветку одним коммитом с сообщением «<id>: ТЗ Оператора (<название>)» — авторство коммита оркестраторское (образец FIXATION_AUTHOR в fixation.py); (4) рабочая копия main НЕ затрагивается вовсе: ни файлов, ни коммитов, ни переключений веток. Git-вызовы — через gitcmd (образец T036). new без --tz — то же самое, только без TZ.md (шаблон SPEC коммитится в ветку).

Killed-судьба: при kill ветка (и с ней ТЗ) удаляется как раньше; текст ТЗ до удаления кладётся в журнал БД записью kill (детерминированно, полный текст; запись в журнал — не запись в main, инвариант 15 не затрагивается), чтобы killed-RETRO (T043, подбор долгов на merge_gate) мог процитировать суть из журнала — закрывает «суть-заглушку» killed-RETRO (аудит 27.08).

Границы: инварианты уборки и kill (14, 15, тесты T008/T020) не ослабляются — main до мержа не тронут by construction; analyst продолжает читать TZ ветко-корректно (T031/T047 — чтения уже покрыты; сверить, что вход analyst читает ТЗ из ветки/worktree, и закрыть, если нет — тот же класс); ручной коммит «Tnnn: ТЗ Оператора» из флоу исчезает (строку-практику снять из роадмапа отдельной правкой Оператора после мержа); .github/, skills/, templates/, docs/invariants.md не трогать (изменение реестра инвариантов, если понадобится, — подготовленным диффом, образец T046/T047).

Критерии приёмки (ориентир): (1) new "<название>" --tz <файл> оставляет рабочую копию main нетронутой (git status пуст, ветка main без новых коммитов), а в ветке задачи — коммит «<id>: ТЗ Оператора (<название>)» с TZ.md и шаблонным SPEC.md; (2) new без --tz — то же с одним шаблонным SPEC.md; (3) существующая ветка с именем задачи — именованный отказ, задача не создана, счётчик не израсходован; (4) немедленный kill свежесозданной задачи оставляет main чистым (инвариант 15/T008 живы), текст ТЗ — в журнале, и последующий merge_gate любой задачи доставляет killed-RETRO с сутью из ТЗ; (5) analyst стартует по задаче, созданной новым флоу, и читает ТЗ без ручных действий Оператора; (6) полный набор тестов зелёный; (7) защищённые пути в диффе не затронуты.
