# SPEC: ТЗ рождается в ветке задачи (ADR-0005 п.9)

## Контекст
По ADR-0005 п.9 изменения от конвейера попадают в main единственным
путём — merge-последовательностью `merge_gate`; прямых коммитов
конвейера в main вне этого окна не появляется. Сейчас `cmd_new`
(`orchestrator/catalog.py`) кладёт `tasks/<id>/TZ.md` и шаблонный
`SPEC.md` в рабочую копию main untracked, и их коммитит Оператор руками
(«Tnnn: ТЗ Оператора» — ручной шаг, забывание которого стоило $9
буксовки в T035; страхует только стоп-кран T038). Класс закрывается
конструкцией: ТЗ и шаблон SPEC рождаются сразу в ветке задачи, main до
мержа не трогается вовсе.

## Требования

1. `cmd_new` после существующих проверок и выдачи номера задачи создаёт
   ветку `task/<id>-<slug>` от `config.MAIN_BRANCH` (через `gitcmd`,
   образец T036); если ветка с таким именем уже существует — именованный
   отказ, задача не создаётся, номер счётчика не расходуется (тот же
   принцип «сначала все проверки, потом побочные эффекты», что у
   существующего отказа при нечитаемом файле ТЗ).
2. `cmd_new` заводит worktree задачи штатной механикой T045
   (`orchestrator/workspace.py`) и пишет `TZ.md` (если передан `--tz`) и
   шаблонный `SPEC.md` в этот worktree, а не в рабочую копию main.
3. `cmd_new` коммитит написанные файлы в ветку задачи одним коммитом с
   сообщением `<id>: ТЗ Оператора (<название>)`; авторство коммита —
   оркестраторское (образец `FIXATION_AUTHOR_NAME`/`FIXATION_AUTHOR_EMAIL`
   из `orchestrator/fixation.py`). `new` без `--tz` коммитит тем же путём
   только шаблонный `SPEC.md` (без `TZ.md`).
4. Рабочая копия main не затрагивается ни на одном шаге `cmd_new`: ни
   новых файлов на диске main, ни коммитов в main, ни переключений
   текущей ветки main.
5. При `kill` задачи текст `TZ.md` (если он существовал) до удаления
   ветки читается и кладётся в журнал БД (`store.journal`) записью `kill`
   целиком и детерминированно, до уборки ветки/worktree
   (`orchestrator/cleanup.py`), которая происходит как раньше. Запись —
   в журнал БД, не в main; инвариант 15 не затрагивается.
6. Дальнейшая генерация killed-RETRO (`orchestrator/retro.py`,
   `build_killed`) на ближайшем `merge_gate` любой другой задачи строит
   «Суть» из текста ТЗ, положенного в журнал по требованию 5, а не из
   пустого шаблона-заглушки SPEC.md.
7. Вход роли `analyst` (запуск роли шага, `orchestrator/runner.py`)
   определяет наличие `TZ.md` по ветке/worktree задачи, а не только по
   диску рабочей копии main — тот же класс ветко-корректных чтений, что
   уже закрыт для статусов SPEC/REVIEW/QUESTIONS (T031/T047); если
   сейчас определение роли зависит от диска main, оно приводится к тому
   же виду.

## Критерии приёмки

AC-1. `new "<название>" --tz <файл>` оставляет рабочую копию main
нетронутой (`git status` пуст, ветка `main` без новых коммитов), а в
ветке задачи `task/<id>-<slug>` появляется коммит
`<id>: ТЗ Оператора (<название>)` с `TZ.md` и шаблонным `SPEC.md`.

AC-2. `new "<название>"` без `--tz` даёт тот же результат (ветка задачи
+ один коммит с тем же сообщением), но без `TZ.md` — в коммите только
шаблонный `SPEC.md`.

AC-3. Если ветка с именем создаваемой задачи уже существует — именованный
отказ: задача не создаётся (нет новой строки в БД, нет каталога
`tasks/<id>/`), номер счётчика не расходуется.

AC-4. Немедленный `kill` только что созданной задачи оставляет main
чистым (инвариант 15 и тесты T008/T020 живы), полный текст `TZ.md`
(если он был) попадает в журнал БД записью `kill`, и последующий
`merge_gate` любой другой задачи доставляет killed-RETRO, чья «Суть»
построена из текста ТЗ, взятого из журнала.

AC-5. Роль `analyst` стартует на задаче, созданной новым флоу
(`new ... --tz`), и читает `TZ.md` без ручных действий Оператора.

AC-6. Полный набор тестов пакета зелёный.

AC-7. Дифф задачи не затрагивает защищённые пути: `.github/`, `skills/`,
`templates/`, `docs/invariants.md`.

## Не входит

- Снятие строки-практики «Tnnn: ТЗ Оператора» из текста роадмапа —
  отдельная правка Оператора после мержа этой задачи, не часть неё.
- Правка `.github/`, `skills/`, `templates/`, `docs/invariants.md`.
  Если по факту исполнения понадобится изменить реестр инвариантов —
  готовится подготовленным диффом Оператору (образец T046/T047), не
  применяется этой задачей напрямую.
- Ослабление инвариантов уборки и kill (14, 15, тесты T008/T020) — они
  остаются в силе без правок, конструкция задачи closes класс тем, что
  main до мержа не трогается by construction, а не изменением этих
  инвариантов.
