# PLAN: A5 — роль analyst: SPEC из свободного ТЗ Оператора

## Подход

**Обратная совместимость через ролевую функцию, не через `STATE_ROLE`.**
`config.STATE_ROLE` — статический словарь `состояние -> роль`, и на нём
стоят три потребителя (`runner.cmd_run`, `auto.cmd_auto`, `doctor.
all_checks`) и два существующих теста-инварианта (`test_invariants.
FsmStatesCoverTheCodeTest`, `test_auto_cycle.AutoStopsWhereTheOperatorIsNeededTest.
test_stop_table_covers_every_state_outside_state_role`), которые в один
голос читают `spec_writing` как состояние ВНЕ агентских — задача без
`TZ.md` обязана продолжать жить прежним флоу (требование 1: «старые
тесты не меняются семантически»). Добавить `"spec_writing": "analyst"`
в сам словарь означало бы включить агентский шаг для КАЖДОЙ задачи,
независимо от наличия ТЗ, — `tests/test_auto_cycle.py` (класс
`AutoStopsWhereTheOperatorIsNeededTest`) при этом красит сразу три теста,
потому что заводит task без `TZ.md` и ждёт немедленной остановки цикла
с текстом «SPEC ещё пишется».

Решение — не трогать `config.STATE_ROLE` и `config.AUTO_STOP` вовсе,
а завести в `runner.py` единственную функцию `step_role(t) -> str | None`:
сначала смотрит в `STATE_ROLE` (все прежние состояния — без изменений),
и только если там пусто и состояние — `spec_writing`, проверяет файл
`tasks/<id>/TZ.md` — есть он — роль `analyst`, нет — `None` (ровно то,
что было до этой задачи). `runner.cmd_run` и `auto.cmd_auto` зовут эту
функцию вместо прямого обращения к словарю — конфигурация условности
живёт в одном месте, а не размножается по потребителям (требование 2:
«STATE_ROLE-условность — решение разработчика, лишь бы отказ был
именованным»). `doctor.all_checks` не трогается: она обходит только
статические ключи `STATE_ROLE` для health-check токенов — analyst
получает свою проверку токена через `preflight_checks` в момент
реального запуска шага, как и остальные роли; расширение статического
обхода вне объёма требований этой задачи.

**Именованный отказ без ТЗ.** `cmd_run` при `step_role(t) is None`
и состоянии `spec_writing` не падает генериком «агент не запускается»,
а называет причину буквально: «SPEC пишет Оператор — TZ.md не заведён»
(критерий приёмки 1). Остальным состояниям без роли — старое сообщение,
без изменений.

**TZ.md — новый тип артефакта, минимальный по структуре.** `scripts/
guard.py` получает запись `RULES["tz"]` с пустым списком секций (тело
свободное, как того явно требует SPEC) — общий фронтматтер-контракт
(`task`, `type`, `author_role`, `status`) не выделяется для `tz`
отдельным более узким правилом: `guard.check()` остаётся ЕДИНЫМ проходом
для всех типов артефактов (архитектура T017 — один код на все типы),
а не обрастает вторым, более узким контрактом ради одного нового типа.
SPEC перечисляет «task, type: tz, schema_version» как минимум для тела
свободного текста — это не запрещает общие `author_role`/`status`,
которые `catalog.cmd_new` подставляет сама (`author_role: operator`,
`status: draft`), а Оператору руками писать их не нужно. Разночтение
не меняет наблюдаемое поведение (Оператор не пишет фронтматтер вручную
в обоих случаях) и не требует особого случая в guard — риск неверной
трактовки принят осознанно как более простой и однородный путь.

**Заведение ТЗ — флаг `new`, не отдельная команда.** `catalog.cmd_new`
получает необязательный `tz_path`; CLI: `artel.py new "<название>"
--tz <файл>`. Файл читается как есть (свободный текст Оператора),
оборачивается минимальным фронтматтером и заголовком, пишется
в `tasks/<id>/TZ.md`. Без флага — поведение `cmd_new` не меняется
вообще (обратная совместимость требования 1 на уровне кода, не только
FSM).

**Батч вопросов — файл-маркер, тем же приёмом, что `escalate`
в tests_writing (T023).** `QUESTIONS.md` — второй новый тип артефакта
guard'а (обязательная секция «Вопросы», структура без глубокой проверки
содержимого — guard проверяет форму, не полноту батча). `fsm.cmd_advance`
в ветке `spec_writing` смотрит на файл ДО чтения статуса `SPEC.md`: файл
есть и проходит guard — задача уходит в `escalated` с `escalated_from=
"spec_writing"` немедленно (требование 4), тем же generic-механизмом
`cmd_approve`, что уже возвращает test_author в `tests_writing` (T023) —
новой ветки в `cmd_approve` не требуется. Второй батч по тому же ТЗ
блокируется самой FSM: пока задача в `escalated`, `run` для неё не
стартует (`escalated` не входит в агентские состояния), а значит
и второго прогона analyst до `approve` быть не может — требование
«второй батч только после ответа на первый» закрывается устройством
автомата, а не отдельной проверкой. Разрешение батча (правка `TZ.md`
и/или пометки в `QUESTIONS.md` самим Оператором) заведено в промпт
роли (skills/spec-authoring.md): analyst обязан убрать `QUESTIONS.md`
перед тем, как написать готовый `SPEC.md`, иначе файл продолжит
эскалировать задачу на каждом следующем `advance` — то же допущение
на дисциплину промпта, что и у пометок AC-n в acceptance_tests/ (T023,
docs/invariants.md, «На ревью — тестом не выражаются»).

**`no_paths` из требования 3 — не новое поле SPEC, а промпт.**
Раздел «Не входит» SPEC T025 явно исключает правку шаблона SPEC
(готов в T023) — новых frontmatter-полей `templates/SPEC.md` не
заводит. `no_paths` в требовании 3 — существующее понятие уровня
target (`targets.yaml`), не SPEC: analyst обязан уважать его при
формулировке требований (skills/spec-authoring.md), но это не
код и не новая структура, а часть промпта роли.

**Выход SPEC — существующая механика T017/T023, без нового кода.**
Guard уже проверяет структуру и AC-разметку на переходе `spec_writing
-> spec_gate` независимо от того, кто писал `SPEC.md` — Оператор
или analyst (требование 3, критерий приёмки 2 — регрессионный тест
на существующий путь, не новая защита).

**Роль и скилы.** `roles.yaml`: `analyst.executor: human` ->
`agent`, `token_slot: null` -> `artel-analyst` (по образцу остальных
ролей), `skills: [conventions-core, escalation-rules, spec-authoring]`.
Новый скил `skills/spec-authoring.md` формулирует контракт роли текстом
промпта: источник — только ТЗ (без карты — она за объёмом задачи,
«Не входит»), batch-эскалация вместо угадывания, AC-разметка выхода,
уважение `no_paths` и потолка бюджета только вниз.

## Шаги

1. **guard.py: типы `tz` и `questions`.** `RULES["tz"]` (секции: `[]`,
   статусы `{draft, ready}`), `RULES["questions"]` (секции: `["Вопросы"]`,
   статусы `{draft, ready}`). Тесты: `guard.check()` принимает валидный
   `TZ.md`/`QUESTIONS.md`, отклоняет без фронтматтера/с недостающей
   секцией «Вопросы»/с неизвестным статусом.
2. **`templates/QUESTIONS.md`.** Шаблон батча: фронтматтер + секция
   «Вопросы» с форматом одного вопроса (варианты, дефолт), инструкция
   про сортировку по блокирующести. `TZ.md` шаблона не получает — тело
   свободное по требованию 1, оборачивает его код `catalog.cmd_new`.
3. **`catalog.cmd_new(title, tz_path=None)`.** Читает файл `tz_path`,
   оборачивает фронтматтером (`type: tz, author_role: operator,
   status: draft, schema_version: 2`) и заголовком, пишет `TZ.md`.
   Без `tz_path` — поведение прежнее, разница только в сигнатуре
   с дефолтом. Нечитаемый файл ТЗ — `sys.exit` с причиной, задача не
   создаётся наполовину. `artel.py`: разбор `--tz <файл>` в таблице
   команд, строка справки. Тесты (критерий приёмки 1, часть 1):
   `--tz` создаёт валidный по guard `TZ.md`; без флага — `TZ.md` не
   появляется и старые вызовы `cmd_new(title)` работают как прежде;
   нечитаемый путь — `sys.exit` с текстом причины.
4. **`runner.step_role(t)`.** Резолвинг роли шага: `STATE_ROLE` как
   было, `spec_writing` — `analyst` только при существующем `TZ.md`,
   иначе `None`. `cmd_run` зовёт её вместо прямого `config.STATE_ROLE.
   get(...)`; при `None` и состоянии `spec_writing` — именованный отказ
   «SPEC пишет Оператор»; иначе — старый текст без изменений. Миссия
   `analyst` в `cmd_run` (по образцу test_author/developer/reviewer):
   читать `TZ.md`, писать `SPEC.md` по шаблону либо `QUESTIONS.md`
   батчем, не трогать код. Тесты (критерий приёмки 1, часть 2): задача
   с `TZ.md` в `spec_writing` — `run` стартует агента с ролью `analyst`
   (промпт содержит «Роль: аналитик», путь TZ.md); без `TZ.md` — `run`
   не зовёт `Popen`, текст отказа содержит «SPEC пишет Оператор»;
   прочие состояния без роли — старый текст не изменился (регрессия).
5. **`auto.cmd_auto`: `runner.step_role` вместо словаря.** Условие цикла
   и печать шага переведены на `step_role(t)` — семантика для всех
   прежних состояний идентична (функция при непустом результате
   `STATE_ROLE.get` возвращает его же), для `spec_writing` без `TZ.md`
   цикл останавливается как раньше (`config.AUTO_STOP["spec_writing"]`
   не трогается и не достижим иначе). Регрессия: весь
   `tests/test_auto_cycle.py` зелёный без правок (критерий приёмки 1,
   «старые тесты не меняются семантически»). Отдельный новый тест:
   `TZ.md` есть — `auto` запускает `analyst` из `spec_writing` без
   ручного `run` (требование 2, «run/auto запускают analyst»).
6. **`fsm.cmd_advance`, ветка `spec_writing`: батч вопросов.** До чтения
   статуса `SPEC.md` — проверка `QUESTIONS.md`: файла нет — старое
   поведение; файл есть, но не проходит `guard` — отказ перехода
   с причиной (как и для остальных guard-условий); файл валиден —
   `escalated_from="spec_writing"`, переход в `escalated`. Тесты
   (критерий приёмки 3): валидный `QUESTIONS.md` эскалирует немедленно,
   `escalated_from` выставлен; `approve` из `escalated` возвращает
   в `spec_writing` (существующий generic-путь `cmd_approve`, тест —
   регрессионное подтверждение, не новый код); невалидный `QUESTIONS.md`
   (без секции «Вопросы») блокирует переход причиной guard, не
   эскалирует.
7. **Регрессия AC-2 (существующая механика).** Тест: `SPEC.md` версии 2
   без AC-разметки, статус `ready`, состояние `spec_writing` — `advance`
   отказывает с причиной guard'а (`spec_ac_errors`), независимо от того,
   что автором значится `analyst`. Кода в этом шаге нет — тест фиксирует,
   что T017/T023 механика уже покрывает этот путь.
8. **`roles.yaml` + `skills/spec-authoring.md`.** `analyst`: `executor:
   agent`, `token_slot: artel-analyst`, `skills: [conventions-core,
   escalation-rules, spec-authoring]`. Новый скил — контракт роли:
   источник только `TZ.md` (без карты, «Не входит»), результат — SPEC
   по шаблону с AC-разметкой либо один батч вопросов в `QUESTIONS.md`,
   бюджет только вниз от дефолта, уважение `no_paths` target'а, запрет
   трогать код/SPEC чужой задачи. Тест: `roles.skills("analyst")` и
   `roles.token_slots("analyst")` читаются без ошибки (по образцу
   существующих проверок `roles.py`, если такого теста ещё нет для
   новых ролей — не заводить лишний, `roles.py` уже общий).
9. **Прогон регрессии и мутационные проверки.** `python3 -m unittest
   discover -s tests`, `python3 scripts/guard.py --all` — оба зелёные
   (критерий приёмки 4; вторая среда — без `claude` в PATH — уже
   покрыта существующим стилем песочниц, ничего нового не подмешивает).
   Мутационные проверки: убрать проверку `TZ.md` в `step_role` — красит
   регрессионные тесты `test_auto_cycle`/новый тест `run` без ТЗ; убрать
   проверку `QUESTIONS.md` до чтения статуса `SPEC.md` — красит тест
   эскалации; убрать `guard.RULES["questions"]` — красит тест guard.

## Влияние на систему

**Protected-paths (зона Оператора).** Диф трогает `roles.yaml`
(правка одной существующей роли `analyst` — executor и skills, по
прямому предписанию SPEC T025 требования 2, остальные роли не тронуты)
и `skills/` (один новый файл `spec-authoring.md`, существующие скилы
не тронуты) и `templates/` (один новый файл `QUESTIONS.md` — новый
тип артефакта этой задачи, не правка существующих четырёх шаблонов;
`templates/SPEC.md` не трогается — «Не входит» явно исключает эту
правку). Тот же прецедент, что T023 (SPEC которой прямо разрешает
это самой роли конвейера, ревьюеру — «проверить состав отдельно»):
`protected-paths` в CI даёт warning, не блокирует (Фаза 0). `.github/`
и `gates.yaml` не трогаются.

**Инварианты и защиты — не ослабляются.** Ни один из 27 существующих
пунктов `docs/invariants.md` не тронут: `config.STATE_ROLE` и
`config.AUTO_STOP` как словари не меняются ни на одну запись — условность
`spec_writing` живёт в отдельной функции `runner.step_role`, которую
уже существующие тесты `test_invariants.FsmStatesCoverTheCodeTest`
и `test_auto_cycle.*` продолжают видеть как раньше (оба сверяются
со статическим словарём, не с поведением). Ручные гейты (`spec_gate`,
`acceptance`, `merge_gate`) не тронуты — требование 5 буквально «без
изменений», код гейта `spec_gate` в `cmd_approve` не редактируется.
Guard остаётся структурным (не исполняет содержимое) — новые правила
`tz`/`questions` того же вида, что и четыре существующих. Новой строки
в `docs/invariants.md` эта задача не заводит: устройство «второй батч
только после ответа» — следствие существующего инварианта 6/7
(ручной гейт и агентский запуск возможны только из подходящего
состояния), а не новая защита, которую можно молча ослабить отдельно
от них.

**Обратная совместимость.** Задачи без `TZ.md` (весь текущий беклог
T001–T024 и любая новая задача, заведённая без `--tz`) проходят
`spec_writing` тем же флоу, что и до этой задачи: `run` называет отказ
«SPEC пишет Оператор» вместо старого generic-текста (единственное
наблюдаемое отличие текста для ЭТОГО конкретного случая — само требование
1 явно просит именованный отказ), `auto` останавливается с прежним
`config.AUTO_STOP["spec_writing"]`. `python3 -m unittest discover -s
tests` без единой правки существующих файлов тестов подтверждает это
регрессией (шаг 9).

**Откат.** Правка — новый код (`runner.step_role`, ветка `spec_writing`
в `fsm.cmd_advance`, `catalog.cmd_new` с необязательным параметром) плюс
точечные добавления в protected-пути (одна роль, один скил, один
шаблон). `git revert` коммитов ветки возвращает `analyst` к `executor:
human`, убирает `spec-authoring.md`/`QUESTIONS.md`/шаг `--tz`; уже
заведённые `TZ.md`/`QUESTIONS.md` у задач, прошедших через новый флоу
до отката, остаются на диске как история, но код перестаёт их читать —
та же гарантия, что и у откатов T023.

## Риски

- **Прочтение «минимального фронтматтера ТЗ» как строго task/type/
  schema_version без author_role/status.** Разночтение задокументировано
  в «Подходе»; если это не то, что имел в виду Оператор — правка
  тривиальна (сузить `REQUIRED_META` только для `tz`), без переделки
  архитектуры.
- **Дисциплина промпта для уборки `QUESTIONS.md`.** Как и AC-пометки
  test_author (T023), код не может механически проверить, что analyst
  на повторном прогоне удалил старый батч перед новым `SPEC.md` —
  оставленный файл продолжит эскалировать задачу. Тот же принятый
  класс риска, что «На ревью — тестом не выражаются» в
  docs/invariants.md; ловит ревью и Оператор на гейте, не эта задача.
- **`no_paths` — не код.** Требование 3 упоминает `no_paths`, но
  правки шаблона SPEC исключены «Не входит» — трактовано как указание
  для промпта роли (skills/spec-authoring.md), не как новое поле;
  если это неверно — предмет отдельного уточнения Оператором, не
  блокер этой задачи.
