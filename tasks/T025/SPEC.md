# SPEC: A5 — роль analyst: SPEC из свободного ТЗ Оператора

## Контекст

Последняя ролевая задача фазы A (roadmap §2 A5). Сейчас SPEC пишет
Оператор руками — это самый дорогой по его времени шаг конвейера.
A5 переносит написание внутрь: Оператор даёт ТЗ свободным текстом,
роль analyst превращает его в SPEC по шаблону; Оператор остаётся
редактором на spec_gate, не автором. Шаблон SPEC с AC-разметкой уже
готов (T023).

## Требования

1. **Вход — ТЗ артефактом**: свободный текст Оператора сохраняется
   в `tasks/<id>/TZ.md` (минимальный frontmatter: task, type: tz,
   schema_version; тело свободное — guard проверяет только шапку).
   CLI: `new "название" --tz <файл>` или последующая команда —
   точная форма за разработчиком. Задача БЕЗ ТЗ-артефакта живёт
   прежним флоу (SPEC пишет Оператор) — обратная совместимость,
   старые тесты не меняются семантически.
2. **spec_writing исполняет analyst** при наличии ТЗ: roles.yaml —
   analyst становится executor: agent (token_slot уже объявлен),
   скилы: conventions-core, escalation-rules + новый скил
   spec-authoring (правки roles.yaml/skills — зона Оператора,
   protected-paths подсветит). `run`/`auto` запускают analyst
   из spec_writing; STATE_ROLE-условность «роль есть только при ТЗ»
   — решение разработчика, лишь бы отказ был именованным.
3. **Выход**: SPEC.md по шаблону — AC-разметка, budget_usd
   по классу задачи (только вниз от дефолта), no_paths и skip_tests
   при необходимости, status: ready; строго из ТЗ — «не входит»
   обязано отражать границы ТЗ, требования сверх ТЗ запрещены.
   Выход валидируется guard'ом на переходе (механика T017); SPEC
   закоммичен в ветку задачи — фиксация T021 требует чистоты.
4. **Батч вопросов**: неясность ТЗ → ОДИН батч всех вопросов
   (отсортирован по блокирующести, каждый с вариантами и дефолтом)
   в `tasks/<id>/QUESTIONS.md` + эскалация. Ответ Оператора —
   правка/дополнение TZ.md (и/или пометки в QUESTIONS.md) + approve:
   analyst перезапускается с обновлённым ТЗ. Второй батч по тому же
   ТЗ — только после ответа на первый.
5. **spec_gate без изменений**: Оператор может править SPEC
   до approve (редактор); approve-по-sha как для всех гейтов.

## Критерии приёмки

AC-1. Тест: задача с TZ.md в spec_writing — `run` запускает
analyst; без TZ.md — именованный отказ «SPEC пишет Оператор»
(прежний флоу цел: существующие тесты зелёные без семантических
правок).

AC-2. Тест: невалидный выход analyst (SPEC без AC-разметки) —
переход в spec_gate отказан guard-механикой с причиной.

AC-3. Тест: эскалация analyst возвращается в spec_writing
(escalated_from); QUESTIONS.md с батчем — валидный артефакт guard.

AC-4. Тесты и guard --all зелёные в обеих средах (с claude в PATH
и без).

AC-5. (manual) Живой прогон: задача-пустышка с настоящим ТЗ
проходит spec_writing настоящим агентом analyst — SPEC по шаблону,
AC-разметка из ТЗ, ничего сверх ТЗ; исполняется Оператором
до approve acceptance. Урок T024: прогон делать с чекаутом кода
задачи, пустышку убить и убрать.

## Не входит

- Срез карты во вход analyst — карты ещё нет (отдельная задача
  фазы A); вход = ТЗ; подключение карты — с задачей карты.
- Механика ANSWER-артефакта (P3) — ответы через правку TZ.md.
- Изменение spec_gate, шаблона SPEC (готов в T023), ревью.
- LLM-триаж входящих и постановка без Оператора.
