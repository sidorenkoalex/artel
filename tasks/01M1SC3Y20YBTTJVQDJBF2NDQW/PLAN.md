# PLAN: идемпотентность `workspace.ensure` не зависит от символических ссылок в пути

## Подход

Три независимых, но связанных изменения в границах зон SPEC
(`orchestrator/workspace.py`, `orchestrator/canary.py`, `tests/`):

1. `workspace._registered` сравнивает `wt_path.resolve()` с
   `Path(p).resolve()` для каждой строки `registered_paths()`, вместо
   сравнения сырых строк. `ensure`/`on_task_branch`/`remove` уже зовут
   `_registered` как единственную точку сравнения — правка одной
   функции закрывает все три (AC-2).

2. `canary._drive_task`: в начале каждого прохода цикла читается
   последняя запись журнала шага (`store.task_steps`) — если это
   `agent run SKIPPED` с деталью, содержащей «рабочий каталог роли не
   создан» или «каталог окружения роли не создан», задача убивается
   немедленно через `_kill_inconclusive` с текстом причины из журнала,
   не дожидаясь `CANARY_MAX_STALL_ITERS` (AC-3, AC-6). Пустой журнал
   или любая другая последняя запись — короткое замыкание не
   срабатывает, генуинная стагнация по-прежнему упирается в полный
   стоп-кран (AC-7, `test_canary.py::DriveTaskStallCapTest` не
   тронут).

3. `canary._run_one_task`/`_task_metrics`: для исхода `killed`
   добавлено поле `kill_note` — «штатно» на журнальном маркере
   `_kill_at_merge_gate`/`_kill_at_verifying`, иначе «не сошлась:
   <причина>» с причиной из записи `_kill_inconclusive` (её `detail` —
   фиксированный литерал-маркер «прогон дальше эту задачу не ведёт —
   cleanup.cmd_kill», по которому запись узнаётся среди прочих записей
   актора `canary`; сама причина лежит в поле `action` той же записи).
   Строка печатается в отчёте прогона рядом с существующим
   `исход=...` (AC-4).

Разбора по ADR не требуется — оба изменения точечные, без новых
абстракций и без изменения публичных сигнатур (`ensure`/`on_task_branch`/
`remove`/`_drive_task`/`_run_one_task` — сигнатуры те же).

## Шаги

1. `workspace._registered`: `Path.resolve()` с обеих сторон сравнения
   (AC-1, AC-2, AC-5).
2. `canary._drive_task`: короткое замыкание холостых проходов на
   `agent run SKIPPED` с одной из двух причин ТЗ (AC-3, AC-6, AC-7).
3. `canary._task_metrics`/`_run_one_task`: причина исхода `killed` в
   отчёте прогона — «штатно» / «не сошлась: <причина>» (AC-4).
4. Юнит-тесты по каждому шагу (см. «Покрытие требований») — залоченные
   `tasks/01M1SC3Y20YBTTJVQDJBF2NDQW/acceptance_tests/` уже покрывают
   AC-1, AC-2, AC-3, AC-4, AC-5, AC-6, AC-7; отдельных новых юнит-тестов
   `tests/` не потребовалось — приёмочные тесты этой задачи и есть
   искомое покрытие поведения из требований, регрессия существующих
   `tests/test_workspace.py`/`tests/test_canary.py` проверена прогоном.

## Влияние на систему

- `workspace._registered` — единственная точка сравнения пути worktree
  с `git worktree list`; резолв путей строже прежнего сравнения (было:
  точное совпадение строк), не слабее — ложноположительных совпадений
  `Path.resolve()` не даёт (два разных реальных каталога не резолвятся
  в один и тот же путь). Не трогает `doctor._orphan_worktrees`/
  `doctor.check_orphans` (вне зоны, «Не входит» SPEC) — они читают
  `registered_paths()` отдельно и не разделяют `_registered`.
- `canary._drive_task`: короткое замыкание проверяет ТОЛЬКО две
  конкретные подстроки причины `agent run SKIPPED` — остальные причины
  того же журнального действия (промпт не собран, `claude CLI не
  найден` и т.п.) по-прежнему идут через существующий путь
  `stall_streak`/`CANARY_MAX_STALL_ITERS`, не изменены («Не входит»
  SPEC). Проверка читает журнал в цикле каждый проход — дешёвый
  `SELECT ... ORDER BY id` по task_id, не new I/O за пределами БД,
  которую `_drive_task` и так держит открытой.
- `canary._task_metrics`/`_run_one_task`: новое поле `kill_note` в
  словаре метрик — внутренний word, не публичный API/схема БД
  (`canary_runs` не тронута, требование 5 SPEC не расширяется).
- Ни один существующий тест/гейт/лимит не ослаблен: `tests/
  test_workspace.py` (22/22) и `tests/test_canary.py` (45/45) зелёные
  после правки; `CANARY_MAX_STALL_ITERS`/
  `CANARY_MAX_ESCALATION_CYCLES` не изменены.
- Откат — точечный revert трёх правок (`workspace.py::_registered`,
  `canary.py::_drive_task` + константы, `canary.py::_task_metrics`/
  `_run_one_task` + `_kill_outcome_note`/`_last_role_skip_reason`), без
  зависимостей от прочего кода.
- `docs/codebase-map.md` регенерирована этим же коммитом
  (`python3 scripts/codebase_map.py`) — публичные функции
  `workspace.py`/`canary.py` не изменились (новые функции приватные,
  с `_`), диф карты — только сдвиг `built_at_sha` и разделы модулей,
  отставших от главной ветки до начала этого шага (не follow-up этой
  задачи).

## Риски

- Короткое замыкание AC-3 читает ТОЛЬКО последнюю запись журнала —
  если `auto.cmd_auto` в одном проходе журналирует несколько записей
  подряд и `agent run SKIPPED` не последняя, короткое замыкание не
  сработает и задача продолжит холостые проходы до стоп-крана. По коду
  `runner.run_agent_once`/`role_cwd`/`role_env` эта запись — последнее
  действие перед возвратом (SKIPPED сразу приводит к выходу из шага),
  так что на практике она и есть последняя; тест AC-3 это подтверждает
  прогоном.
