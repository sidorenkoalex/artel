# SPEC-AUDIT: Слежение за ценой набора тестов по отчёту junit CI main (ADR-0032, этап 1)

Ответов Оператора (ANSWER-n.md) и решений Оператора на гейте SPEC в брифе
нет. Сверка шла по ТЗ, SPEC, коду рабочего каталога и `docs/adr/0032-test-cost-and-growth.md`.

## ТЗ и SPEC

Требования 1–6 ТЗ, критерии, «Не входит», заметка о шуме xdist и условия
тестов перенесены в SPEC почти дословно (SPEC.md:34-146). Требований
сверх ТЗ нет. Расхождения:

1. **Матрица неослабления ТЗ потеряла форму таблицы.** В SPEC она
   пересказана одной фразой в «Материалах» (SPEC.md, последний пункт
   «Материалов»). Строки «Где держится / Чем покрыто» не сохранились; строка
   паритета схемы, как и в ТЗ, опирается на тест, который новую таблицу не
   держит (см. «Матрица неослабления»).
2. **«Алерт» ADR-0032 п. 6 сведён к слову.** ADR (docs/adr/0032-test-cost-and-growth.md:73)
   и факт 1 ТЗ: «`doctor` предупреждает при 75 %, алерт — при 85 %». SPEC
   (SPEC.md:63-65, :83, :131) вводит уровень `alert` у `limit_level` и
   «тревогу» в строке doctor. Как этот уровень показывается, не сказано
   нигде: статус `doctor.Check` (`ok`/`warn`/`fail`/`skip`,
   `orchestrator/doctor/__init__.py:114`, `LABELS` в `orchestrator/doctor/cli.py`)
   или запись в таблицу `alerts`, как у `suite.duration`
   (`orchestrator/doctor/suite_duration.py:66`). Неоднозначность идёт ещё из ТЗ:
   её надо снять вопросом Оператору, а не выбором разработчика.
3. Требование 5 «в перечень команд, разрешённых роли, команда не входит»
   (SPEC.md:76-77) ни одним AC не закреплено (см. «Проверяемость»).

   пропускает. Обрыв — тот самый случай, ради которого у сводки есть «попытка
   без отчёта» (требования 2 и 4) и строка CI в doctor. Ложный факт идёт из
   факта 4 ТЗ. Чтобы выполнить требование буквально, пришлось бы менять
   `green_base_commit`, а его держат тесты строки doctor об отчёте базы

   `green_base_commit` и противоречия не видит.
2. **Имя артефакта `junit` уже есть константой**:
   `targets.CI_REPORT_ARTIFACT_DEFAULT = "junit"` (`orchestrator/targets.py:175`).
   Требование 2 (SPEC.md:44-45) заводит вторую константу в `config`.
   Дублирование значения — замечание, не блокер.
3. **«Отбор как в `suite_duration._series`»** (SPEC.md:81-82) шире, чем
   «отбор по проекту» из факта 4 ТЗ. `_series` отбрасывает записи до ack алерта
   `suite.duration` (`orchestrator/doctor/suite_duration.py:21,26`), записи без
   `seconds_per_test` (`:32`) и всё до последней смены `xdist_workers`
   (`:36-40`). После ack такого алерта строка локального прогона пропадёт
   («записи нет»), хотя записи есть. Какой из двух смыслов задуман, SPEC не
   говорит.
4. `project_profile.full_suite_limit` возвращает кортеж `(значение, источник)`
   и бросает `targets.TargetsError` (`orchestrator/project_profile.py:431-439`).
   Что делает строка doctor при непрочитанном профиле, SPEC не говорит, а
   необработанное исключение уронит весь `doctor.all_checks`.
5. Опыт с поведением `git log --first-parent prev..sha` во временном каталоге
   поставить не удалось: запуск отклонили разрешения шага. Форма команды

## Проверяемость критериев

Тест до кода: AC-1, AC-2 краснеют на атрибуте `forge.*`, AC-3…AC-5 — на
импорте `orchestrator.suite_cost` в теле теста, AC-6, AC-7 — на неизвестной
команде или отсутствии строки doctor. Рекурсии, порождения процессов и
меняющих команд против настоящего репозитория формы критериев не задают:
`gh` подменяется в процессе, git — во временной песочнице `tests.sandbox`.

## Пути обхода гейтов

1. `--record-latest` через `green_base_commit`, подменённый в AC-6: тест
   зелёный, а красные и оборванные прогоны `main` не записываются никогда.
   Строка CI в doctor тогда по построению видит только успешные прогоны, то
   есть короче 40 мин, и до обрыва не поднимет тревогу на основе последнего
   оборванного прогона.
2. «`TestReport` не меняется» обходится добавлением поля со значением по
   умолчанию: AC-1 сравнивает экземпляры, а не состав класса.
3. Попытку без отчёта можно не записывать вовсе: ни AC-6, ни AC-7 её не
   требуют, а требование 4 (SPEC.md:70-71) остаётся невыполненным при
   зелёной планке.
4. Таблица только в `SCHEMA` без `migrate()`: все AC зелёные на свежей БД,
   а на БД пульта (старой) `suite-cost --record` упадёт с `no such table`.
5. `--record <sha>` для коммита только документов запишет пропущенную
   попытку (около 0 с, без отчёта) как последнюю сводку, и строка CI покажет
   норму.
