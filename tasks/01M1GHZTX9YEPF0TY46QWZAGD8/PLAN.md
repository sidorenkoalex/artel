# PLAN: approve — полный sha в подсказках и приём уникального префикса

## Подход

Два независимых, но связанных изменения вокруг `approve`:

1. **Sha в подсказках.** Везде, где пульт печатает готовую команду
   `artel.py approve <id>` для перехода, у которого уже есть
   зафиксированный sha, — подставить его сразу, строкой, готовой к
   копированию. Источник значения — тот же, что уже использует
   `fsm.confirm_fixation` для ветки `sha is None` (живое чтение
   `fixation.read(task_id, target)`, не колонка `tasks.fixed_sha`
   напрямую): подсказка обязана называть ровно то значение, которое
   реальный `approve` потом сверит. Новый общий узел —
   `fixation.approve_sha_hint(task_id, target) -> str` (пусто, если
   фиксации нет — вырожденный случай без реального git, подсказка
   остаётся байт-в-байт прежней).

   Точки вставки — по требованию 1 SPEC, три категории:
   - **остановки `auto`** — `config.AUTO_STOP` несёт новый плейсхолдер
     `{sha}` в шаблонах `spec_gate`/`acceptance`/`merge_gate`/`escalated`
     (ровно `fsm.APPROVE_NEEDS_SHA`); `auto.auto_stop_advice` вычисляет
     `sha_hint` только для этих состояний и подставляет его в `.format`;
   - **переход в `merge_gate`** — оба места, где `acceptance ->
     merge_gate` печатает следующую команду (`fsm._cmd_approve`, ветка
     `acceptance`, и `fsm_autogate._maybe_autogate_acceptance` для
     автогейта);
   - **статусные подсказки эскалаций с фиксацией** — оба места
     `runner._cmd_run`, где шаг сам уводит задачу в `escalated`
     (инцидент целостности — там раньше был буквальный плейсхолдер
     `<sha>`, и провал агента после исчерпанных попыток).

   `fsm_merge_gate.py` (повторные попытки `approve` уже НА `merge_gate`
   — красный CI, упавший push, чужая ветка root) сознательно не тронут:
   это не одна из трёх перечисленных категорий (не остановка auto, не
   вход в merge_gate, не эскалация) — задача просто остаётся на том же
   гейте, Оператор и так видит последний approve с sha, если тот был
   нужен для входа.

2. **Приём префикса.** `fsm.confirm_fixation` сравнивает `sha` с
   зафиксированным `current` через `current.startswith(sha)` вместо
   строгого `==`, но только после отдельной проверки минимальной длины
   (`APPROVE_SHA_PREFIX_MIN = 8`) — короче восьми символов отклоняется
   ДО сравнения с текстом отказа «короче минимальной длины», не «не
   совпадает». И полный sha (совпадает с собой целиком), и любой его
   префикс от 8 символов проходят одинаково; несовпадающее значение той
   же длины — прежний отказ «не совпадает с зафиксированным {current}»
   байт-в-байт. Один эталон (эта же задача), не поиск среди кандидатов
   — не тот же код, что `store.resolve_task_id` (T094), только тот же
   дух приёма.

Оба изменения живут в уже существующих узлах (`fixation.py`, `fsm.py`,
`fsm_autogate.py`, `auto.py`, `runner.py`, `config.py`) — новых модулей
не заводится.

## Шаги

1. `fixation.approve_sha_hint` + `config.AUTO_STOP` с `{sha}` +
   `auto.auto_stop_advice` считает sha для `fsm.APPROVE_NEEDS_SHA`.
2. `fsm._cmd_approve` (переход `acceptance -> merge_gate`) и
   `fsm_autogate._maybe_autogate_acceptance` печатают sha в подсказке
   входа в `merge_gate`.
3. `runner._cmd_run` — обе точки эскалации (инцидент целостности, провал
   агента) печатают sha вместо плейсхолдера/его отсутствия.
4. `fsm.confirm_fixation` — минимальная длина префикса + сравнение через
   `startswith`, именованные отказы по AC-3/AC-4.
5. Юнит-тесты на каждый узел (1–4); прогон локальных приёмочных тестов
   AC-1..AC-5 (уже зелёные — они писались под этот план, красных не
   было при первом прогоне после реализации).

## Влияние на систему

Sha, который печатают подсказки, — то же самое значение, что уже
сравнивает `confirm_fixation`; новый узел `fixation.approve_sha_hint`
только читает (`fixation.read`), никогда не коммитит — тот же принцип,
которым уже руководствуется сам `confirm_fixation` и `check_integrity`
(REVIEW.md T021, замечание 1). Ни один существующий гейт, тест или
инвариант не ослаблен: отказы «approve требует sha» и «sha не
совпадает» остаются текстуально прежними для тех же условий (AC-3, AC-5
защищают это явно), добавляется только третий, более ранний отказ
(короткий префикс) и более широкий набор значений, проходящих
успешно (префикс вместо только полного sha). Формат подсказок
(`config.AUTO_STOP`, `fsm.py`, `fsm_autogate.py`, `runner.py`) при
отсутствии зафиксированного sha форматируется в точности как раньше
(`{sha}` -> `""`) — проверено существующими тестами `test_auto_cycle.py`
(подстрочные проверки `artel.py approve {id}`, не точное совпадение) и
не потребовало их правки.

Откат — правка тех же пяти файлов до предыдущего содержимого; данных
не мигрирует, схема БД не меняется.

## Риски

- Оператор мог привыкнуть копировать `<id>` без sha и печатать его сам
  — эта задача не убирает возможность так делать (полный sha и без
  него `approve` остаются легальным вводом, AC-5), только добавляет
  готовую строку туда, где раньше её не было.
- `fixation.approve_sha_hint` — лишний вызов `fixation.read()`
  (git-операция) на каждый auto-stop/эскалацию в состояниях
  `APPROVE_NEEDS_SHA`; по стоимости он того же порядка, что уже платит
  `confirm_fixation` на каждом `approve`, и вызывается не чаще.
