# ТЗ: Шум журнала и алертов: предупреждения один раз на состояние, запрос на слияние после первого коммита

# ТЗ: Шум журнала и алертов: повторяющиеся предупреждения один раз на задачу, черновик запроса на слияние после первого коммита

Источник: docs/audits/code-revision-2026-09-26.md, находка
CR-2026-09-26-7 (вторая часть) и CR-2026-09-26-10; строка копилки 05.09
«Draft MR FAILED: No commits between…»; решение Оператора 27.09.
Задача вне линии провайдеров.

Факты (origin/main a6da0abe; числа — журнал 13–27.09):
- `orchestrator/runner.py:354` пишет запись журнала `pre-flight WARNING`
  на КАЖДОМ шаге роли — 162 записи за неделю об одной и той же версии
  CLI.
- `orchestrator/budget.py::apply_spec_budget` (:95, :101) пишет «бюджет
  из SPEC не применён» при каждом проходе гейта — 39 записей;
  `enforce_budget` (:219) пишет «бюджет: предупреждение» на каждом
  переходе после порога — 56 записей.
- `orchestrator/fsm.py::_maybe_ensure_draft_mr` зовёт
  `orchestrator/github_adapter.py::ensure_draft_mr` при входе в in_dev,
  когда в кодовой ветке ещё нет ни одного коммита; GitHub отвечает
  «No commits between main and task/…», адаптер пишет запись журнала
  `Draft MR FAILED` и поднимает инцидент `github_adapter`. Открытых
  инцидентов этого вида 121 (05.09–27.09); запрос на слияние при этом
  создаётся позже штатно.

- Наблюдение 27.09 (задача 01M3H3T8RKTVKTJJYEAGW19BPS): на прямом пути
  без возвратов запрос на слияние не создаётся вовсе — попытка при входе
  в in_dev отказывает на пустой ветке и не повторяется; запись перехода
  «MR готов — жду зелёного CI ветки» при этом печатается, а CI идёт
  только по событию push (7 проверок вместо 14). Запрос появляется лишь
  при повторном входе в in_dev после возврата (задачи 01M3H1Z4, 01M3H3JW
  — запросы 142, 143).

Требуется:
1. Предупреждение с тем же текстом для той же задачи журналируется один
   раз на пребывание задачи в состоянии; повторы не пишутся отдельными
   записями, а считаются — способ учёта (счётчик в записи, сводная
   запись на выходе из состояния, иное) выбрать и обосновать в SPEC.
   Три места: `pre-flight WARNING`, «бюджет из SPEC не применён»,
   «бюджет: предупреждение». Тексты предупреждений не меняются; смена
   текста (другая версия CLI, другой порог) — новая запись.
2. Вывод в stdout команд не сокращается: Оператор у терминала видит
   предупреждение как раньше; дедупликация касается журнала.
3. Черновик запроса на слияние не создаётся, пока в кодовой ветке нет
   коммитов относительно базы: проверка локальная, до обращения к
   GitHub; пропуск — запись журнала обычного уровня без инцидента.
   Черновик создаётся при первом переходе, когда коммит в ветке уже
   есть, в том числе на выходе из in_dev в verifying — задача не
   доходит до CI без запроса на слияние; текст записи перехода
   соответствует факту. Остальные отказы создания (сеть, права, targets.yaml) —
   инцидент как сегодня.
4. Накопленные открытые инциденты `github_adapter` с текстом «No commits
   between» закрываются этой задачей НЕ автоматически: PLAN даёт
   Оператору команду либо сценарий закрытия с решением (одна команда
   `alert-ack` на вид инцидента — если её нет, предложение в
   «Предложения системе»).
5. Тесты (tests/): три предупреждения — одна запись на состояние при
   нескольких шагах, новая запись при смене текста; черновик не
   запрашивается у GitHub при пустой ветке и запрашивается после
   коммита; инцидент при сетевом отказе сохраняется; существующие
   tests/test_github_adapter.py, tests/test_fsm_draft_mr_reentry.py,
   tests/test_spec_budget.py, tests/test_runner_model_preflight.py
   зелёные, ни один не ослаблен.
