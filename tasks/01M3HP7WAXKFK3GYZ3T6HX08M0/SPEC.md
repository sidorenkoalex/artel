# SPEC: Шум журнала и алертов: повторяющиеся предупреждения один раз на пребывание в состоянии, черновик запроса на слияние после первого коммита

## Контекст

Журнал шагов и таблица alerts зашумлены механическими повторами.
`orchestrator/runner.py:354` пишет запись `pre-flight WARNING` на КАЖДОМ
шаге роли — 162 записи за 13–27.09 об одной и той же версии CLI;
`orchestrator/budget.py::apply_spec_budget` (:95, :101) пишет «бюджет из
SPEC не применён» при каждом проходе гейта (39 записей), а
`enforce_budget` (:219) — «бюджет: предупреждение» на каждом переходе
после порога (56 записей). Отдельно:
`orchestrator/fsm.py::_maybe_ensure_draft_mr` зовёт
`orchestrator/github_adapter.py::ensure_draft_mr` при входе в `in_dev`,
когда в кодовой ветке ещё нет ни одного коммита, — GitHub отвечает «No
commits between main and task/…», адаптер пишет `Draft MR FAILED` и
поднимает инцидент `github_adapter` (121 открытый инцидент этого вида за
05.09–27.09). Наблюдение 27.09: на прямом пути без возвратов черновик
запроса на слияние не создаётся ВОВСЕ — попытка при входе в `in_dev`
отказывает на пустой ветке и больше не повторяется, при этом запись
перехода «MR готов — жду зелёного CI ветки» печатается, а CI идёт только
по событию push (7 проверок вместо 14). Источник: ревизия кода 26.09,
находки CR-2026-09-26-7 (вторая часть) и CR-2026-09-26-10; строка
копилки 05.09 «Draft MR FAILED: No commits between…»; решение Оператора
27.09; ответ Оператора на батч вопросов (ANSWER-1, 27.09).

## Требования

1. Предупреждение одного вида для одной задачи журналируется один раз на
   пребывание задачи в состоянии; повтор в пределах того же пребывания
   отдельной записью журнала НЕ пишется. Три места: `pre-flight WARNING`
   (`orchestrator/runner.py:354`), «бюджет из SPEC не применён»
   (`orchestrator/budget.py:95`, `:101`), «бюджет: предупреждение»
   (`orchestrator/budget.py:219`).
2. Повторы нигде не считаются: числа повторов в журнале не появляется, ни
   счётчиком в записи, ни сводной записью на выходе из состояния — журнал
   остаётся только дописываемым (ANSWER-1, п. 1).
3. Ключ подавления. Для `pre-flight WARNING` и «бюджет из SPEC не
   применён» ключ — текст предупреждения: другой текст (другая версия
   CLI, другая причина «не применён») даёт новую запись. Для «бюджет:
   предупреждение» ключ — пересечённый порог
   (`config.BUDGET_ALERT_RATIO`), а не текст: текст несёт текущие суммы и
   меняется на каждом шаге.
4. Граница пребывания в состоянии — последняя запись `state -> <состояние>`
   журнала этой задачи (тот же приём скоупа без новой колонки, которым
   уже пользуется история отказов advance). Повторный вход в то же
   состояние сдвигает границу: после него то же предупреждение
   журналируется снова.
5. Подавление касается только трёх мест требования 1. Остальные записи
   этих же модулей пишутся как сегодня, в том числе `pre-flight FAILED`,
   «бюджет из SPEC отклонён», «бюджет из SPEC», запись об ИСЧЕРПАНИИ
   бюджета и эскалация по бюджету (ANSWER-1, п. 1).
6. Вывод в stdout не сокращается ни в одном из трёх мест: Оператор у
   терминала видит предупреждение на каждом срабатывании, как раньше.
   Дедупликация касается только журнала.
7. Тексты самих предупреждений не меняются.
8. Черновик запроса на слияние не создаётся, пока в кодовой ветке нет
   коммитов относительно базы target'а: проверка локальная и выполняется
   ДО любого обращения к GitHub (до `git push -u origin <branch>` и до
   `gh pr create`). Пропуск — запись журнала обычного уровня, без
   инцидента и без открытия алерта; признак «черновик заведён» при
   пропуске не выставляется, так что следующий переход пробует снова.
9. Черновик создаётся при первом переходе, когда коммит в ветке уже есть,
   в том числе на выходе из `in_dev` в `verifying`: для github-target и
   не канареечной задачи задача не входит в `verifying` (и не доходит до
   CI) без заведённого запроса на слияние. Текст записи перехода
   соответствует факту.
10. Остальные отказы создания черновика при наличии коммита (сеть, права,
    `targets.yaml`) — запись `Draft MR FAILED` и инцидент
    `github_adapter`, как сегодня.
11. Накопленные открытые инциденты `github_adapter` с текстом «No commits
    between» этой задачей автоматически НЕ закрываются. PLAN даёт
    Оператору команду либо сценарий их закрытия с решением; если одной
    команды `alert-ack` на вид инцидента в пульте нет — предложение
    заводится строкой в секции «Предложения системе» PLAN.
12. Тесты в `tests/`: три предупреждения — одна запись на пребывание в
    состоянии при нескольких шагах и новая запись при смене ключа;
    черновик не запрашивается у GitHub на пустой ветке и запрашивается
    после коммита; инцидент при сетевом отказе сохраняется. Существующие
    `tests/test_github_adapter.py`, `tests/test_fsm_draft_mr_reentry.py`,
    `tests/test_spec_budget.py`, `tests/test_runner_model_preflight.py`
    зелёные, ни один из них не ослаблен.

## Критерии приёмки

AC-1. Два шага роли подряд в одном пребывании задачи в состоянии, оба с
одним и тем же предупреждением pre-flight (совпадающий текст), дают в
журнале задачи РОВНО одну запись действия `pre-flight WARNING`.

AC-2. В том же пребывании в состоянии предупреждение pre-flight с ДРУГИМ
текстом даёт вторую запись `pre-flight WARNING` — подавление ключом
текста, не видом записи.

AC-3. После повторного входа задачи в то же состояние (новая запись
`state -> <состояние>`) то же самое предупреждение pre-flight
журналируется снова: одна запись в прошлом пребывании, одна в новом.

AC-4. Два прохода гейта с «бюджет из SPEC не применён» в одном
пребывании задачи в состоянии дают одну запись журнала с этим действием.

AC-5. Несколько шагов подряд после порога `config.BUDGET_ALERT_RATIO` в
одном пребывании в состоянии дают одну запись «бюджет: предупреждение»,
несмотря на разные суммы в тексте каждого срабатывания.

AC-6. Каждое срабатывание всех трёх предупреждений печатается в stdout
команды, включая подавленные в журнале повторы: число печатей равно числу
срабатываний.

AC-7. Исчерпание бюджета журналируется и эскалирует задачу независимо от
того, была ли в этом пребывании в состоянии запись «бюджет:
предупреждение».

AC-8. Вход в `in_dev` с кодовой веткой без коммитов относительно базы: ни
`git push`, ни `gh pr create` не вызываются, в журнал идёт запись
обычного уровня о пропуске, открытых алертов `github_adapter` эта попытка
не добавляет.

AC-9. Ветка с коммитом относительно базы (github-target, не канарейка):
черновик запроса на слияние заведён, и к моменту входа задачи в
`verifying` запрос на слияние существует — переход `in_dev -> verifying`
не оставляет задачу без него.

AC-10. Отказ push или создания запроса на слияние при наличии коммита
(сеть/права) даёт запись `Draft MR FAILED` и открытый инцидент
`github_adapter` — как сегодня.

## Оценка объёма и деление

Сработали два сигнала.

- **Число затрагиваемых модулей/файлов.** guard считает упоминания путей
  вида `orchestrator/*.py` по ВСЕМУ тексту SPEC, а здесь помимо четырёх
  файлов зоны названы читатели журнала из раздела «Только чтение» ТЗ
  (`orchestrator/store.py`, `orchestrator/retro.py`,
  `orchestrator/report.py`), путь возможного расширения зон
  (`orchestrator/fsm_advance.py`) и адрес идиомы в «Материалах»
  (`orchestrator/alerts.py`). Фактическая зона правки — четыре файла кода
  (`orchestrator/runner.py`, `orchestrator/budget.py`,
  `orchestrator/github_adapter.py`, `orchestrator/fsm.py`) плюс общая
  зона `tests/`.
- **Число критериев приёмки** — ровно 10, на самом пороге: десять
  критериев покрывают двенадцать требований, из них AC-1..AC-7 —
  дедупликация трёх мест по двум разным ключам, AC-8..AC-10 — черновик
  запроса на слияние. Дробить критерии мельче незачем, склеивать —
  потерять различимые проверки.

Прогноз диффа 14 КиБ против порога 128 КиБ; прочие сигналы не сработали.

**Решение: монолит.** Материал для решения Оператора, без приукрашивания:
формально задача делится по половинам — требования 1–7 (дедупликация
журнала, зоны `orchestrator/runner.py` и `orchestrator/budget.py`) и
требования 8–11 (черновик запроса на слияние, зоны
`orchestrator/github_adapter.py` и `orchestrator/fsm.py`); зоны половин не
пересекаются, и каждая половина сама по себе мержима с зелёной планкой —
атомарной смены механики, которую нельзя разрезать, здесь нет. Против
деления — цена: обе половины лечат один класс дефекта (шум
наблюдаемости) из одной ревизии кода 26.09, кода в них на два-три
десятка строк каждая, а нарезка даёт две подзадачи уровня $25 (то есть
~$50 против $40) и два полных цикла SPEC/PLAN/REVIEW вместо одного.
Требование 11 (закрытие накопленных инцидентов) осмысленно только вместе
с требованиями 8–10: закрывать инциденты, которые продолжают
накапливаться, незачем — при делении эти части обязаны идти одной.
