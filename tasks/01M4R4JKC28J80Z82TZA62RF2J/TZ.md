# ТЗ: Отвеченный батч вопросов аналитика не эскалирует задачу повторно

Источник: копилка 12.10, приоритет 2 («Повторная эскалация analyst после
ANSWER…», задача 01M4PMQSYPR2KD6N1JCVG9ZABV). Решение Оператора 12.10.2026 —
заводить.

Факты (origin/main 8543e24e):
- `orchestrator/fsm_advance.py` (`spec_writing`, ~100-160): обе ветки (чужая
  ветка документов и диск) эскалируют по самому наличию `QUESTIONS.md`,
  даже если на батч уже есть ANSWER-n и SPEC.md `status: ready`.
- Снять это может только аналитик, удалив файл; в песочнице роли `rm` и
  `/bin/rm` запрещены. 12.10 аналитик написал SPEC по ANSWER-1, не смог
  удалить QUESTIONS.md, задача эскалировала повторно ($1.29 + круг
  answer/approve); обход — ANSWER-2 «удалить через python os.remove».
- `approve` из escalated (`fsm._approve_escalated` ~1348-1392) сверяет число
  ANSWER с `answer_baseline` и при возврате сбрасывает `answer_baseline`.
  Рубеж «сначала шаг аналитика» после возврата —
  `ARTIFACT_ESCALATION_ROLE_STEP_MARKER` (fsm.py ~69,
  `auto._role_step_since_state_entry`).
- Колонки БД заводит только `orchestrator/schema.py`; `store.update_task`
  пишет лишь существующие колонки.

Требуется:
1. Признак «батч отвечен» ставится в `_approve_escalated`, если выполнено
   всё: `escalated_from = spec_writing`, `answer_baseline` не пуст, сверка
   числа ANSWER с `answer_baseline` пройдена, в каталоге документов есть
   `QUESTIONS.md`. Тогда до смены состояния пишется строка журнала задачи
   (действие-константа в `orchestrator/fsm.py`, «батч вопросов отвечен») с
   `sha256=<хэш>` и номером последнего ANSWER-n. Схема БД и миграции не
   меняются. Не удалось прочитать файл — строка не пишется, approve
   проходит (худший исход — прежняя повторная эскалация).
2. Хэш — sha256 от текста файла в UTF-8, одной функцией для ветки
   документов и диска; сравнение по хэшу, не по времени и не по sha объекта
   git.
3. `spec_writing`: если хэш текущего `QUESTIONS.md` совпадает с хэшем
   ПОСЛЕДНЕЙ строки «батч вопросов отвечен» этой задачи — батч не
   эскалирует, переход идёт дальше по SPEC.md, как если бы батча не было;
   `guard_refuses(QUESTIONS.md)` для такого батча не выполняется. Совпадение
   с более ранней отвеченной строкой не засчитывается. Иной хэш (новый или
   изменённый батч) — эскалация и проверка guard, как сегодня.
4. Отвеченный батч остаётся в каталоге документов (история); бриф аналитика
   по-прежнему видит последний батч и ответ на него.
5. Журнал: при каждом пропуске — строка «батч вопросов признан отвеченным
   (ANSWER-n)»; при переходе `spec_writing -> spec_audit` та же
   формулировка входит в detail перехода (или `spec_writing -> spec_gate` у задачи без ТЗ).
6. Рубеж «сначала шаг аналитика» не меняется: после approve из эскалации и
   до шага аналитика advance не пропускает старый SPEC.md со статусом ready,
   даже если батч признан отвеченным.
7. Тесты в `tests/` с заявками «Ловит мутацию»: отвеченный неизменный батч
   эскалирует; изменённый батч не эскалирует; возврат к тексту более
   раннего отвеченного батча не эскалирует; признание без ANSWER после
   эскалации; признание снимает рубеж «сначала шаг аналитика».
   Существующие тесты не ослабляются.

Матрица неослабления (независимая проверка 12.10): любое изменение
содержимого батча меняет хэш и эскалирует, как сегодня; пропуск — только
для батча, на который в approve подтверждён новый ANSWER; рубеж шага
аналитика, аудит и гейт SPEC не меняются.
