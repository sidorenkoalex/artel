# SPEC: Отвеченный батч вопросов аналитика не эскалирует задачу повторно

## Контекст
`orchestrator/fsm_advance.py::spec_writing` (стр. 102-163 на main 8543e24e)
эскалирует задачу по самому наличию `QUESTIONS.md` — и на ветке документов,
и на диске, — даже если на этот батч уже есть ANSWER-n, а SPEC.md стоит в
`status: ready`. Снять эскалацию может только аналитик, удалив файл, но в
песочнице роли `rm` запрещён: 12.10 (задача 01M4PMQSYPR2KD6N1JCVG9ZABV)
это стоило лишнего шага ($1.29) и круга answer/approve. Нужно, чтобы батч,
на который Оператор ответил и вернул задачу через `approve`, больше не
эскалировал, пока его содержимое не изменилось. Признак «отвечен» держится
строкой журнала задачи (схема БД не меняется), сравнение — по sha256
текста файла.

## Требования
1. `fsm._approve_escalated` ставит признак «батч отвечен», только если
   выполнено всё: `escalated_from = spec_writing`, `answer_baseline` не
   пуст, сверка числа ANSWER с `answer_baseline` пройдена, в каталоге
   документов задачи есть `QUESTIONS.md`. Признак — строка журнала задачи с
   действием-константой в `orchestrator/fsm.py` («батч вопросов отвечен»),
   detail которой несёт `sha256=<хэш>` и номер последнего ANSWER-n;
   пишется до смены состояния. Схема БД и миграции не меняются.
2. Не удалось прочитать `QUESTIONS.md` — строка признака не пишется, approve
   проходит как сегодня.
3. Хэш батча — sha256 от текста файла в UTF-8, одной функцией для ветки
   документов и для диска; сравнение — по этому хэшу, не по времени и не
   по sha объекта git.
4. `spec_writing` (оба пути — ветка документов и диск): если хэш текущего
   `QUESTIONS.md` совпадает с хэшем ПОСЛЕДНЕЙ строки «батч вопросов
   отвечен» этой задачи — батч не эскалирует, `guard_refuses` для
   `QUESTIONS.md` не выполняется, переход идёт дальше по SPEC.md, как если
   бы батча не было. Совпадение только с более ранней строкой признака не
   засчитывается. Иной хэш (новый или изменённый батч) — эскалация и
   проверка guard, как сегодня.
5. Отвеченный батч остаётся в каталоге документов (история); бриф аналитика
   по-прежнему видит последний батч и ответ на него.
6. Журнал: при каждом пропуске батча — строка «батч вопросов признан
   отвеченным (ANSWER-n)»; при переходе `spec_writing -> spec_audit` (или
   `spec_writing -> spec_gate` у задачи без ТЗ) та же формулировка входит в
   detail перехода.
7. Рубеж «сначала шаг аналитика» (`fsm.ARTIFACT_ESCALATION_ROLE_STEP_MARKER`,
   `auto._role_step_since_state_entry`) не меняется: после approve из
   эскалации и до шага аналитика advance не пропускает старый SPEC.md со
   статусом ready, даже если батч признан отвеченным.
8. Тесты в `tests/` с заявками «Ловит мутацию» на мутации: отвеченный
   неизменный батч эскалирует; изменённый батч не эскалирует; возврат к
   тексту более раннего отвеченного батча не эскалирует; признание без
   ANSWER после эскалации; признание снимает рубеж «сначала шаг
   аналитика». Существующие тесты не ослабляются.

## Критерии приёмки

AC-1. `approve` задачи в `escalated` с `escalated_from = spec_writing`,
непустым `answer_baseline`, числом ANSWER больше `answer_baseline` и
`QUESTIONS.md` в каталоге документов пишет в журнал задачи строку с
действием-константой из `orchestrator/fsm.py` («батч вопросов отвечен»),
detail которой содержит `sha256=<sha256 текста QUESTIONS.md в UTF-8>` и
номер последнего ANSWER-n; строка записана раньше записи смены состояния
этого approve.

AC-2. Строка признака не пишется, если не выполнено хотя бы одно условие
AC-1: `escalated_from` отличен от `spec_writing`; `answer_baseline` пуст;
approve отклонён сверкой числа ANSWER (нового ANSWER нет); `QUESTIONS.md` в
каталоге документов нет.

AC-3. Если `QUESTIONS.md` при approve прочитать не удалось, строка признака
не пишется, а approve проходит: задача возвращается в `spec_writing`.

AC-4. Хэш одного и того же текста `QUESTIONS.md` одинаков при чтении с
ветки документов и с диска (одна функция) и равен sha256 его UTF-8 байтов;
от времени изменения файла и sha объекта git он не зависит.

AC-5. `advance` в `spec_writing` (и путь ветки документов, и путь диска)
при `QUESTIONS.md`, хэш которого совпадает с хэшем последней строки «батч
вопросов отвечен», не эскалирует задачу и не вызывает `guard_refuses` для
`QUESTIONS.md`; при SPEC.md `status: ready` задача переходит в
`spec_audit` (задача с ТЗ) или `spec_gate` (задача без ТЗ), при SPEC.md не
в ready — остаётся в `spec_writing` без эскалации. `QUESTIONS.md` после
этого остаётся в каталоге документов.

AC-6. `advance` в `spec_writing` эскалирует задачу и проверяет
`QUESTIONS.md` guard'ом, как сегодня, если его хэш не совпадает с хэшем
последней строки «батч вопросов отвечен»: новый батч без строки признака,
изменённый после признания батч, а также батч, текст которого совпадает
только с более ранней (не последней) строкой признака.

AC-7. Каждый пропуск батча по AC-5 пишет в журнал задачи строку «батч
вопросов признан отвеченным (ANSWER-n)» с номером ANSWER из строки
признака; detail перехода `spec_writing -> spec_audit` (или
`spec_writing -> spec_gate`) при таком пропуске содержит ту же
формулировку.

AC-8. После approve из эскалации по батчу и до шага аналитика старый
SPEC.md со `status: ready` не продвигается из `spec_writing` (рубеж
`ARTIFACT_ESCALATION_ROLE_STEP_MARKER` / `auto._role_step_since_state_entry`
держит), даже если батч признан отвеченным.

AC-9. В `tests/` есть тесты с заявками «Ловит мутацию», каждый из которых
краснеет на своей мутации: (а) отвеченный неизменный батч эскалирует;
(б) изменённый батч не эскалирует; (в) возврат к тексту более раннего
отвеченного батча не эскалирует; (г) признание батча без нового ANSWER
после эскалации; (д) признание батча снимает рубеж «сначала шаг
аналитика».

## Оценка объёма и деление
Сработавший сигнал: число путей, упомянутых в SPEC (≥ 5), — его дают
перечни «только чтение» в «Не входит» и адреса в «Материалах»; меняемых
зон четыре (`orchestrator/fsm_advance.py`, `orchestrator/fsm.py`, `tests/`,
`docs/codebase-map.md`), критериев девять, `budget_usd` 30 — ниже порога.

Прогноз диффа: 30 КиБ (две функции кода, константа и тесты — около
половины диффа), ниже половины потолка гейта ёмкости (128 КиБ).

Обоснование монолита: запись признака (`fsm._approve_escalated`) и его
чтение (`fsm_advance.spec_writing`) — две стороны одной механики. Часть
только с записью оставляет мёртвую строку журнала без эффекта; часть
только с чтением не срабатывает никогда, потому что признака никто не
пишет, и её тесты не на чем выразить. Общая функция хэша нужна обеим
сторонам. Тесты на мутации (AC-9) проверяют связку целиком.
