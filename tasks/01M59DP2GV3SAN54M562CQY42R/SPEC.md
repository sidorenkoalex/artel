# SPEC: Метрика «круги до кода»: аудиты SPEC, возвраты и эскалации на задачу — в report и оповещение по порогу

## Контекст
Разбор ночи 18–19.10.2026: у задач волны G (01M58FNWBV25FF26E7AZ9Q9912,
01M58PG72PG64GS790XM2EWS61, 01M590GJAF0EDV4NBC4C99MFVH) было 3–4 круга
аудита SPEC и 1–2 эскалации с вопросами на задачу. Это стало видно только
утром по ручному разбору журнала `steps`: ни `report`, ни оповещения число
кругов до кода не показывают. Нужен общий подсчёт кругов по задаче, блок в
`report` и одноразовое оповещение из цикла `auto` при превышении порога.

## Требования

1. Новый модуль `orchestrator/rounds.py` — подсчёт по задаче, общий для
   `report` и оповещения. По журналу `steps` задачи он даёт:
   - аудиты SPEC — число событий `state -> spec_audit`;
   - возвраты аудита — число событий с действием
     `аудит SPEC: возврат аналитику по fail`;
   - возвраты с гейта SPEC — число событий `state -> spec_writing` с detail,
     начинающимся «возврат из spec_gate:»; `state -> spec_writing` с detail
     «эскалация разрешена, продолжаем» (снятие эскалации) и с detail
     «аудит SPEC: вердикт fail…» возвратом с гейта не считаются;
   - эскалации — число событий `state -> escalated`;
   - итерации ревью — значение `tasks.review_iters`;
   - расход «до планки» — сумма стоимостей событий `agent cost KNOWN` этой
     задачи из шагов с `actor` `analyst` и `spec_auditor`;
   - расход всего — сумма стоимостей всех событий `agent cost KNOWN` этой
     задачи.
   Стоимость одного события — фактическая цена `actual_usd`, первый элемент
   результата существующего разбора detail `spend.known_cost_breakdown`
   (`orchestrator/spend.py:579`; им же читает отчёт —
   `report._known_cost_breakdown`); событие, для которого разбор вернул
   `None`, в сумму не входит. Нового разбора стоимости не пишется.
2. `report` получает новый блок «Круги до кода» — таблицу по задачам,
   созданным за `report.OPERATOR_WINDOW_DAYS` дней (по `created_at` задачи),
   со столбцами: задача, проект, аудиты SPEC, возвраты, эскалации, итерации
   ревью, расход до планки / всего. Числа берутся из подсчёта требования 1.
   Столбец «возвраты» показывает два числа подсчёта раздельно, в той же
   форме «X / Y», что и столбец расхода: возвраты аудита / возвраты с гейта
   SPEC (возврат с гейта отличён от возврата аудита — критерий приёмки ТЗ).
3. В блоке «Круги до кода» строки, где аудитов SPEC ≥ 3 или эскалаций ≥ 2,
   выделены (отличимы в HTML от прочих строк).
4. Блок «Круги до кода» завершается строкой итога: медиана и среднее по
   каждому числу таблицы отдельно — аудиты SPEC; возвраты аудита; возвраты
   с гейта SPEC; эскалации; итерации ревью; расход до планки; расход всего.
   В составных столбцах («возвраты», «расход») итог показывается в той же
   форме «X / Y» — медиана (и среднее) первого числа / второго числа.
   Медиана — обычная: при чётном числе задач — среднее двух средних
   значений.
5. При задачах больше одного проекта блок «Круги до кода» строится по
   проекту — так же, как остальные блоки `report` разбиты по проекту.
6. Цикл `auto` после каждого перехода задачи сверяет подсчёт требования 1 с
   порогом — аудитов SPEC ≥ 3 или эскалаций ≥ 2 — и при достижении порога
   поднимает `alerts.raise_alert(conn, <проект задачи>, "warning", "rounds",
   …)` с текстом «задача <id>: N аудитов SPEC, M эскалаций до кода — ТЗ
   недоопределено?» (N, M — числа подсчёта). Оповещение внимания
   (`raise_attention_alert`) для этого не используется. Обе ветви порога
   действуют независимо: и переход, после которого `auto` продолжает цикл
   (третий вход в `spec_audit`), и переход в `escalated`, после которого
   `auto` останавливается (условие цикла `orchestrator/auto.py:1015`), —
   сверка с порогом выполняется в том же вызове `auto`, до его выхода.
7. Оповещение `rounds` поднимается не больше одного раза на задачу. Признак —
   запись в `steps` задачи с действием «круги до кода: оповещение», которая
   пишется при подъёме оповещения; при её наличии повторное оповещение не
   поднимается — в том числе после того, как переход задачи закрыл
   оповещения внимания (`store.set_state` → `close_attention_alerts`).
8. Пороги (аудитов SPEC 3, эскалаций 2) — именованные константы
   `orchestrator/config.py`; блок `report` (требование 3) и оповещение
   (требование 6) используют одни и те же константы. `orchestrator/config.py`
   — общая зона (`config.COMMON_ZONES`, `orchestrator/config.py:803`):
   правка в нём не выходит за зоны ТЗ, поэтому в поле `zones` он не
   перечисляется.
9. Прежние блоки `report`, прежние оповещения и их тексты не меняются.
   Утверждения тестов `tests/test_report.py`,
   `tests/test_report_project_label.py`,
   `tests/test_01m57pmbhwk5egq8hpa5tqx72h_report.py`,
   `tests/test_01m4rzayh3swjw4wfbw4qw15fp_command_report.py` не меняются.
   Если новый блок меняет порядок или число секций, которые проверяют эти
   тесты, — разработчик эскалирует, а не правит тесты.
10. Тесты детерминированы: учебная база с журналом задачи (аудиты SPEC,
    возвраты аудита, возвраты с гейта SPEC, снятия эскалации, эскалации,
    стоимости шагов) проверяет подсчёт, блок отчёта и однократность
    оповещения; прежнее поведение `report` и оповещений зафиксировано
    тестами до правки.

## Критерии приёмки

AC-1. Подсчёт `orchestrator/rounds.py` по учебному журналу задачи даёт
ожидаемые числа по каждому столбцу: аудиты SPEC (число `state -> spec_audit`),
возвраты аудита (`аудит SPEC: возврат аналитику по fail`), эскалации
(`state -> escalated`), итерации ревью (`tasks.review_iters`).

AC-2. В учебном журнале, где есть `state -> spec_writing` с detail
«возврат из spec_gate: …», с detail «аудит SPEC: вердикт fail…» и с detail
«эскалация разрешена, продолжаем», подсчёт возвратов с гейта SPEC
засчитывает только первое; возврат с гейта SPEC отличён от возврата аудита,
снятие эскалации возвратом не считается.

AC-3. Расход «до планки» равен сумме `actual_usd` (по
`spend.known_cost_breakdown`) событий `agent cost KNOWN` этой задачи из шагов
с `actor` `analyst` и `spec_auditor`, расход всего — сумме `actual_usd` всех
событий `agent cost KNOWN` этой задачи; шаги других ролей (например
`developer`) в расход до планки не входят, события `agent cost KNOWN` другой
задачи учебной базы не входят ни в одну из сумм.

AC-4. HTML `report` содержит блок «Круги до кода» с таблицей по задачам,
созданным в окне `OPERATOR_WINDOW_DAYS` (по `created_at`): задача, проект,
аудиты SPEC, возвраты, эскалации, итерации ревью, расход до планки / всего;
столбец «возвраты» показывает «возвраты аудита / возвраты с гейта SPEC» с
различными числами для учебной задачи, где они различаются; задача,
созданная раньше окна, в таблицу не попадает.

AC-5. В блоке «Круги до кода» строка задачи с аудитами SPEC ≥ 3 и строка
задачи с эскалациями ≥ 2 выделены, строка задачи ниже обоих порогов — нет.

AC-6. Блок «Круги до кода» содержит строку итога с медианой и средним по
каждому числу таблицы (аудиты SPEC, возвраты аудита, возвраты с гейта SPEC,
эскалации, итерации ревью, расход до планки, расход всего); значения
совпадают с ожидаемыми для учебного набора задач, в котором медиана и
среднее различаются по каждому из этих чисел.

AC-7. При задачах двух проектов блок «Круги до кода» разбит по проекту так
же, как остальные блоки `report`.

AC-8. Третий вход задачи в аудит SPEC (при одной эскалации), пройденный
через цикл `auto`, поднимает ровно одно оповещение с `source` `rounds`,
`kind` `warning`, target — проект задачи, текстом «задача <id>: N аудитов
SPEC, M эскалаций до кода — ТЗ недоопределено?», и пишет в `steps` задачи
запись с действием «круги до кода: оповещение».

AC-9. Вторая эскалация задачи (при числе аудитов SPEC меньше 3), пройденная
через цикл `auto`, поднимает ровно одно оповещение `rounds` с тем же
`kind`, target и формой текста, что в AC-8, и пишет в `steps` задачи запись
с действием «круги до кода: оповещение» — в том же вызове `auto`, который
останавливается на `escalated`.

AC-10. Четвёртый вход в аудит SPEC (и следующая эскалация) нового оповещения
`rounds` не поднимает, в том числе после того, как переход задачи закрыл
оповещения внимания, и после подтверждения (`ack`) первого оповещения
`rounds`.

AC-11. Пороги — именованные константы `orchestrator/config.py`: при задаче с
двумя аудитами SPEC и одной эскалацией оповещение `rounds` не поднимается и
строка в блоке не выделена.

AC-12. Прежние блоки `report` и прежние оповещения не меняются: утверждения
тестов `tests/test_report.py`, `tests/test_report_project_label.py`,
`tests/test_01m57pmbhwk5egq8hpa5tqx72h_report.py`,
`tests/test_01m4rzayh3swjw4wfbw4qw15fp_command_report.py` проходят без
изменения, оповещение внимания цикла `auto` (`orchestrator/auto.py`)
поднимается с прежним текстом.

## Оценка объёма и деление

Сработавшие сигналы: число критериев приёмки ≥ 10 (12); `budget_usd` ≥ $30
(35 — рамка Оператора из ТЗ, «Рамка: $35»). Прочие сигналы не срабатывают:
файлов зоны вне общих зон — три (`orchestrator/report.py`,
`orchestrator/auto.py`, `orchestrator/rounds.py`); `orchestrator/config.py`,
`docs/codebase-map.md` и `tests/` — общие зоны (`config.COMMON_ZONES`,
`orchestrator/config.py:803`) и в счёт не идут; всего с общими — пять
путей, из них считаемых три; слов-маркеров нет,
механизмы `docs/invariants.md` не задеваются (новых состояний FSM нет).

Материал для решения Оператора — обоснование монолита: подсчёт
`orchestrator/rounds.py` ТЗ прямо заказывает как общий для `report` и
оповещения; без потребителя он мёртвый код, а блок `report` и оповещение
`auto` — две тонкие обёртки над ним (по одному вызову и одному формату
вывода). Нарезка «подсчёт + report» / «оповещение auto» возможна по границам
зон, но удваивает число шагов конвейера (аналитик, аудит, тесты, ревью) при
объёме кода, сопоставимом с одной типовой задачей; рамка $35 рассчитана
Оператором на одну задачу. Большая часть критериев — разные столбцы одного
подсчёта (AC-1…AC-3), а не независимые механизмы.

## Не входит

- Оповещение при ручном ведении задачи (`fsm.cmd_approve`/`fsm.cmd_advance`
  без `auto`) — такие задачи видны только в блоке `report`.
- Аудит ТЗ и консультация роли (поправка ADR-0022).
- Правило эскалации аналитика.
- Изменения конвейера (FSM, состояния, гейты).
- Правка `orchestrator/store.py`, `orchestrator/alerts.py`,
  `orchestrator/spend.py`, `orchestrator/fsm.py`, `orchestrator/fsm_advance.py`,
  `docs/backlog.md` — только чтение; правка вне зон — эскалация.
- Новый разбор стоимости шага — используется `spend.known_cost_breakdown`.
  `spend.known_cost_pairs`, названный в ТЗ, — сводка по паре (роль, модель)
  по всем задачам с отсечкой по тарифу (`orchestrator/spend.py:630–680`),
  расхода одной задачи он не даёт; ТЗ ссылается на `report.py:397` — это
  комментарий над `report._known_cost_breakdown`, обёрткой
  `spend.known_cost_breakdown`.
- Полный зелёный набор `tests/` и CI ветки — их держит пульт.
