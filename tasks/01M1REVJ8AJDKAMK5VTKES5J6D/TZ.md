# ТЗ: механика зон — ждущая задача зону не держит, возврат из ревью занятость не перепроверяет

Источник: бэклог 05.09 (`docs/backlog.md`, «Зоны: взаимная блокировка
при возврате из ревью») и копилка («цепочки ожиданий»). Факты 05.09:
(а) задача, переведённая в `in_dev` и остановленная «ждёт зоны», сама
числится занимающей СВОИ зоны — B2 (01M1R5B33C…, семь файлов зон, ни
одного коммита кода) заблокировала пять задач: регрессию №12, карту,
гейт ёмкости, стек ч.1 и через него ч.2–ч.3; (б) владелец зоны
(«переход до роли», 01M1R8B3ZK…) после `review -> in_dev` встал «ждёт
зоны» сам, потому что проверка идёт перед первым шагом КАЖДОГО визита
`in_dev`, а ждущие его задачи уже в `in_dev`. Оператор трижды снимал
ожидание `zone-release` вручную.

Требуется:
1. Занимающей зону считается только задача, у которой в текущем
   пребывании в фазах `in_dev`…`merge_gate` был хотя бы один
   стартовавший шаг developer (запись `agent run started` роли developer
   после последнего `state -> in_dev`) либо снятие ожидания Оператором.
   Задача в `in_dev` без такого шага (ждёт зоны сама) зон не держит.
2. Возврат `review -> in_dev` (и любой повторный визит `in_dev` той же
   задачи после начатого кода) занятость не перепроверяет: владелец
   зоны остаётся владельцем до `done`/`killed`.
3. Очередь ожидания (`queue_order`, `zone-reorder`) сохраняет
   поведение; отказ «ждёт зоны» называет фактического владельца по
   новому правилу (задачу со стартовавшим кодом), не ждущего соседа.
4. Тесты: две задачи с общей зоной, обе в `in_dev` без стартов — первая
   по очереди стартует, вторая ждёт именно её; владелец после возврата
   из ревью стартует без проверки; ждущая задача не блокирует третью с
   пересечением только с ней; существующие тесты зон частей 1–3 и
   приёмочные планки (01M1NKVPD2…, 01M1P9QAG6…, 01M1P9QCHP…) зелёные
   без ослабления.

Зоны: orchestrator/zone_lock.py, tests/. Не пересекается с живыми
задачами. Не входит: смена диапазона фаз занятости, автоматическое
снятие ожидания, изменение формата `zones:`.
