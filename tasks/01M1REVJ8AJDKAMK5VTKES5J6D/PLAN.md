# PLAN: механика зон — ждущая задача зону не держит, возврат из ревью занятость не перепроверяет

## Подход

Единственная точка правки — `orchestrator/zone_lock.py::blocking_conflict`
и вспомогательная функция границы «текущего пребывания». Оба факта SPEC
(а — ждущая задача блокирует остальных; б — возврат `review -> in_dev`
сдвигает границу и заново блокирует владельца) — следствие одного и того
же дефекта: занятость сегодня либо не проверяется вовсе (для кандидатов
цикла), либо проверяется по границе «последний визит `in_dev`»
(`_visit_since_id`), которая сдвигается на каждый повторный визит внутри
одного и того же непрерывного пребывания в диапазоне
`in_dev`…`merge_gate`.

Правка:

1. Заменить границу `_visit_since_id(conn, task_id, "in_dev")` (последняя
   запись `"state -> in_dev"`) на `_stay_since_id(conn, task_id)` — id
   последней записи `"state -> tests_writing"` этой задачи (`0`, если
   такой записи нет — задача заведена в обход `set_state`, тот же
   фолбэк, что и раньше). `tests_writing` — фаза, предшествующая всему
   диапазону `BLOCKING_STATES`, и проходится ровно один раз за
   пребывание, в отличие от `in_dev`, куда пребывание может заходить
   повторно (`review -> in_dev`) — граница на ней не сдвигается
   промежуточными визитами (требование 2, AC-3/AC-7).
2. Обернуть проверку «есть ли в текущем пребывании `agent run started`
   роли developer либо `RELEASE_ACTION` после этой границы» в отдельную
   функцию `_occupies(conn, task_id)` — раньше эта проверка выполнялась
   только для САМОЙ проверяемой задачи; теперь она же применяется к
   КАЖДОМУ кандидату цикла `blocking_conflict` по `store.all_tasks`
   (требование 1, AC-1/AC-8): кандидат в `BLOCKING_STATES` с
   пересекающейся зоной, но без `_occupies`, — пропускается, не
   считается занявшим.
3. `refusal`, `queue_order`, `cmd_zone_reorder`, `queue_position` — не
   трогаются вовсе (требование 3, AC-5): они уже опираются на
   `blocking_conflict` (либо не зависят от занятости совсем — `queue_
   order`/`cmd_zone_reorder`), правка одной функции покрывает их
   транзитивно.

Никакой новой колонки/состояния FSM — тот же приём, что и в частях 1-3
(маркерные записи журнала, не новая схема).

## Шаги

1. `orchestrator/zone_lock.py`: заменить `_visit_since_id`/инлайновую
   проверку в `blocking_conflict` на `_stay_since_id` + `_occupies`;
   применить `_occupies` к каждому кандидату цикла; обновить докстринги
   модуля и `blocking_conflict`, описывающие старую границу «первый
   шаг по последнему визиту `in_dev`».
2. `tests/test_zone_lock.py`: обновить фикстуры тестов, где занявшая
   зону задача заводится без `"agent run started"` и тем не менее ждёт
   конфликт (`test_directory_zone_conflicts_with_file_inside_it`,
   `test_own_directory_containing_a_common_file_is_not_itself_common`,
   `test_occupier_in_each_blocking_state_conflicts`,
   `test_refusal_names_path_task_and_state`,
   `test_release_before_boundary_does_not_lift_a_later_visit` —
   последний не назван в SPEC буквально, но того же класса); развернуть
   `test_first_step_boundary_uses_current_in_dev_visit` на
   противоположное ожидание (AC-3, требование 2 — прямое следствие, не
   нарушение).
3. Прогнать приёмочную планку (`tasks/01M1REVJ8AJDKAMK5VTKES5J6D/
   acceptance_tests/`, залочена — не правится) и весь
   `tests/test_zone_lock.py`, убедиться в зелёном исходе.

Один шаг размера MR (Фаза 0) — вся правка укладывается в один модуль +
его юнит-набор.

## Влияние на систему

Зона правки — `orchestrator/zone_lock.py` (в SPEC-зоне) и его юнит-набор
`tests/test_zone_lock.py` (тоже в зоне: `tests/`). Публичный интерфейс
модуля (`blocking_conflict`/`refusal`/`queue_order`/`queue_position`/
`cmd_zone_release`/`cmd_zone_reorder`) не меняется — сигнатуры и вызовы
из `auto.py`/`catalog.py`/`doctor.py`/`runner.py`/`artel.py` не трогаются.
`BLOCKING_STATES`/диапазон занимающих фаз, формат поля `zones:`,
`cmd_zone_release` как единственный ручной способ снять ожидание —
не меняются («Не входит» SPEC). Приёмочная планка задачи (залочена,
tasks/T023) уже фиксирует новое поведение AC-1..AC-9 — код правится под
неё, планка не правится. Инвариант «зоны — только dogfood target»
(`config.DEFAULT_TARGET`) не затрагивается. Откат — `git revert` одного
коммита: правка локальна, новых миграций/колонок БД нет.

## Риски

Правка фикстур существующего юнит-набора (`tests/test_zone_lock.py`) —
пограничный случай между «починкой под новое условие» и «ослаблением
теста»: для каждой правленой фикстуры добавляется маркер `"agent run
started"` занявшей задаче, а не меняется ассерт результата — сам тест
продолжает проверять то же утверждение (конфликт есть/названа нужная
задача), только по корректному условию AC-1/AC-2. Разворот ожидания
`test_first_step_boundary_uses_current_in_dev_visit` — прямое
требование SPEC (AC-3, «эта правка теста является прямым следствием
требования 2, не его нарушением»), зафиксировано в её докстринге явно.
