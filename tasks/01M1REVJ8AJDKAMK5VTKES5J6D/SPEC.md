# SPEC: механика зон — ждущая задача зону не держит, возврат из ревью занятость не перепроверяет

## Контекст

`orchestrator/zone_lock.py` (части 1-3, SPEC 01M1NKVPD2A79PQ6K0JVV1B2Q1/
01M1P9QAG65GVF69YJEV0V18D9/01M1P9QCHPHSCEA6TK13PV85SP) считает занявшей
зону ЛЮБУЮ задачу в диапазоне состояний `BLOCKING_STATES`
(`in_dev`…`merge_gate`) с пересекающейся зоной — цикл в
`blocking_conflict` (zone_lock.py:198-205) не проверяет, начал ли САМ
занявший ряд разработку, а только освобождает от проверки САМУ
проверяемую задачу (по её собственной записи `"agent run started"`
после последнего `"state -> in_dev"`, zone_lock.py:193-197). Факты
05.09 (`docs/backlog.md`, «Зоны: взаимная блокировка при возврате из
ревью»):

(а) задача, остановленная «ждёт зоны» сама (ни одного стартовавшего
шага developer), тем не менее считается занимающей СВОИ зоны для всех
остальных — B2 (01M1R5B33C…, семь файлов зон, ни одного коммита кода)
заблокировала пять других задач;

(б) граница «первый шаг уже был» (`_visit_since_id`, zone_lock.py:156-
163) — это id последней записи `"state -> in_dev"` ТЕКУЩЕЙ задачи;
после `review -> in_dev` эта граница сдвигается на новый визит, и
задача-владелец (уже стартовавшая код в предыдущем визите) снова
проходит проверку как «первый шаг», видит ждущих соседей в `in_dev` с
той же зоной и сама встаёт «ждёт зоны» — Оператор трижды снимал
`zone-release` вручную.

Оба факта — следствие одного и того же: занятость должна определяться
фактом «код по этой зоне уже стартовал в ТЕКУЩЕМ непрерывном
пребывании задачи в диапазоне `in_dev`…`merge_gate`», а не «задача
сейчас физически в одном из этих состояний» и не «был ли шаг именно
после ПОСЛЕДНЕГО, а не ПЕРВОГО входа в `in_dev` этого пребывания».

## Требования

1. Занимающей зону считается только задача, в текущем непрерывном
   пребывании которой в фазах `in_dev`…`merge_gate` (от входа из
   `tests_writing` до выхода в `done`/`killed`) был хотя бы один
   стартовавший шаг developer (запись `"agent run started"` роли
   developer после начала этого пребывания) либо снятие ожидания
   Оператором (`RELEASE_ACTION`). Задача в `in_dev` без такого события
   (ждёт зоны сама) зон не держит — ни для проверки самой себя
   (существующее поведение частей 1-3), ни, ВПЕРВЫЕ, для проверки
   ДРУГИХ задач, которые её сканируют как потенциального занявшего
   (`blocking_conflict`, цикл по `store.all_tasks`).
2. Возврат `review -> in_dev` (и любой повторный визит `in_dev` той же
   задачи в рамках того же непрерывного пребывания, начатого пунктом
   1) не запускает повторную проверку занятости для НЕЁ САМОЙ: если
   пребывание уже несёт признак из пункта 1 к моменту возврата,
   `blocking_conflict` для неё возвращает «не заблокирована» без
   сравнения зон — владелец остаётся владельцем до `done`/`killed`,
   независимо от числа промежуточных визитов `in_dev`.
3. Очередь ожидания (`queue_order`, `cmd_zone_reorder`, `queue_position`)
   сохраняет поведение частей 1-3 без изменений: сортировка по маркеру
   approve/операторской перестановке, ранжирование среди конкурентов
   по конкретной зоне.
4. Отказ `zone_lock.refusal` называет фактического владельца зоны по
   обновлённому определению (пункт 1) — задачу со стартовавшим кодом
   либо со снятым ожиданием, — не первую попавшуюся задачу в
   блокирующем состоянии, даже если такая (сама ждущая) задача
   встречается раньше владельца при переборе `store.all_tasks`.

## Критерии приёмки

AC-1. Задача A (в `in_dev`, зона пересекается с задачей B), у которой в
текущем пребывании нет ни одной записи `"agent run started"` роли
developer и нет `RELEASE_ACTION`, не считается занимающей свои зоны:
`blocking_conflict`, вызванный для ЛЮБОЙ третьей задачи, чья зона
пересекается ТОЛЬКО с A (не с реальным владельцем), возвращает `None`
по этой паре — A её не блокирует.

AC-2. Задача, в текущем пребывании которой был хотя бы один
`"agent run started"` роли developer либо `RELEASE_ACTION`, считается
занимающей свои зоны независимо от того, в каком состоянии диапазона
`in_dev`…`merge_gate` она сейчас находится — `review`, `verifying`,
`acceptance`, `merge_gate` включительно, не только `in_dev` буквально
(существующее поведение частей 1-3 по диапазону состояний не меняется
— меняется лишь дополнительное условие «начала кода» для каждого
кандидата на этот статус).

AC-3. Задача, чьё текущее пребывание уже несёт признак из AC-2 ДО
возврата `review -> in_dev`, после этого возврата проходит
`blocking_conflict` без отказа даже при наличии других задач в `in_dev`
с пересекающейся зоной, которые сами ещё не стартовали код — повторная
проверка для владельца не выполняется.

AC-4. `zone_lock.refusal` для задачи, заблокированной пересечением с
несколькими задачами блокирующего диапазона одной зоны, называет id и
состояние именно той из них, что удовлетворяет AC-2 (фактический
владелец), а не задачи, которая сама лишь ждёт эту же зону (не
удовлетворяет AC-2).

AC-5. `zone_lock.queue_order`, `zone_lock.cmd_zone_reorder`,
`zone_lock.queue_position` ведут себя как в частях 1-3: сортировка по
маркеру approve SPEC / явной операторской перестановке, ранжирование
среди конкурентов по конкретной зоне — эта задача их не меняет.

AC-6. Сценарий: две задачи в `in_dev` с общей зоной, ни у одной нет
`"agent run started"` — первая, чей `run`/`auto` фактически запускает
разработческий шаг раньше (журналирует `"agent run started"` первой),
после этого проходит без отказа по зоне; вторая, всё ещё без
собственного `"agent run started"`, получает от `zone_lock.refusal`
отказ, называющий именно первую (по AC-4).

AC-7. Сценарий: задача-владелец (со стартовавшим кодом в текущем
пребывании) прошла `review -> in_dev` — её следующий `run`/`auto`
проходит без отказа по зоне, даже если другие задачи с той же зоной
уже стоят в `in_dev` в режиме ожидания (по AC-3).

AC-8. Сценарий: задача Y ждёт зону (без `"agent run started"`, не
владелец) и пересекается зоной ТОЛЬКО с третьей задачей Z, у которой
нет реального владельца в этой зоне, кроме самой Y, — Z не
блокируется задачей Y: `blocking_conflict` для Z по этой зоне
возвращает `None` (по AC-1).

AC-9. Существующие юнит-тесты `tests/test_zone_lock.py` (части 1-3) и
приёмочные планки задач 01M1NKVPD2A79PQ6K0JVV1B2Q1,
01M1P9QAG65GVF69YJEV0V18D9, 01M1P9QCHPHSCEA6TK13PV85SP остаются
зелёными без ослабления проверяемых ими утверждений. Ожидаемая правка
фикстур (не регресс, не ослабление): тесты, где занявшая зону задача
сейчас заводится БЕЗ записи `"agent run started"` и тем не менее
ожидает конфликт (например
`test_directory_zone_conflicts_with_file_inside_it`,
`test_own_directory_containing_a_common_file_is_not_itself_common`,
`test_occupier_in_each_blocking_state_conflicts`,
`test_refusal_names_path_task_and_state` —
tests/test_zone_lock.py:125,157,182,304), должны получить такую запись
в фикстуре, чтобы продолжать проверять факт конфликта по новому
условию AC-1/AC-2, а не проверять его случайно устаревшим способом.
Отдельно: `test_first_step_boundary_uses_current_in_dev_visit`
(tests/test_zone_lock.py:218-236) сейчас буквально фиксирует ошибку
(б) — ожидает конфликт ПОСЛЕ `review -> in_dev` для задачи, уже
стартовавшей код в предыдущем визите; по AC-3 это поведение должно
измениться на противоположное (`blocking_conflict` возвращает `None`)
— эта правка теста является прямым следствием требования 2, не его
нарушением.

## Не входит

- Смена диапазона фаз занятости (`BLOCKING_STATES`, `in_dev`…
  `merge_gate`) — остаётся как в частях 1-3.
- Автоматическое снятие ожидания зоны без команды Оператора
  (`cmd_zone_release` остаётся ручным).
- Изменение формата поля `zones:` (часть 1, строка через запятую).
- Зоны для внешних target — по-прежнему только dogfood
  (`config.DEFAULT_TARGET`), без изменений в этой задаче.
