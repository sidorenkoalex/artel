# SPEC: повторное использование итога полного прогона tests/ на гейтах пульта для того же дерева

## Контекст
Полный набор `tests/` (~4540 тестов, 10–15 мин на гейтах пульта, под
нагрузкой параллельных прогонов в 4–5 раз дольше с ложными красными по
pytest-timeout — замер Оператора 06.10) гоняется на задачу около пяти раз,
и часть прогонов идёт на том же содержимом дерева: автогейт приёмки
красный → `approve` в `acceptance` (в том числе `--accept-red`) гоняет
набор заново на том же коммите; у задачи с приложениями PLAN автогейт
гоняет «ветка + приложения», гейт мержа — «слияние с main + приложения»,
и при несдвинутом main содержимое совпадает. Итог прогона уже
сохраняется (`orchestrator/acceptance.py::_remember_gate_failures` →
`save_failures(sha, …)` в `config.LOGS/fullsuite-results/<sha>.json`), но
ключ — sha коммита только чистого дерева, а читает его только `suite-run`
(`saved_failures`) для прогона базы. Гейты итогом не пользуются. Решение
Оператора 06.10: гейт берёт итог завершённого прогона с тем же ключом
вместо нового прогона.

Единственный вход полного прогона гейтов — `orchestrator/acceptance.py::
full_suite` поверх `run_full_suite`; вызовы гейтов: автогейт
`orchestrator/fsm_autogate.py`, `approve` в `acceptance`
`orchestrator/fsm.py::_acceptance_full_suite_ok`, гейт мержа
`orchestrator/fsm_merge_gate.py::_full_suite_or_refuse` (scratch-дерево с
наложенными приложениями, без коммита).

Решение Оператора 06.10 на гейте SPEC (строка бэклога «Итог базы
suite-run по дереву кода, а не по sha коммита», приоритет 1) включило в
задачу итог прогона базы `suite-run`. Прогон базы части 3 этапа 3
(01M484RNV3) шёл трижды (~41 мин машины: 753/840/870 с): main сдвигали
документные коммиты копилки, а итог базы ищется по sha
(`orchestrator/suite_run.py::_base` ~384, sha — `gitcmd.diff_base`). При
этом в `.artel/logs/fullsuite-results/` нет ни одного итога базы, хотя
`_base` (~402) зовёт `acceptance.save_failures`. Отсюда требования 12–13,
AC-14–AC-15 и зона `orchestrator/suite_run.py` — отступление от зон ТЗ по
этому решению Оператора.

## Требования
1. Ключ итога полного прогона гейта — содержимое дерева, на котором шёл
   прогон, плюс отпечаток окружения прогона:
   - содержимое — хеш дерева git каталога прогона; для дерева с
     незакоммиченным содержимым (scratch-дерево гейта мержа и дерево
     автогейта/`approve` с наложенными приложениями PLAN) — хеш дерева
     вместе с этим содержимым, снятый через временный индекс (индекс
     самого каталога не меняется);
   - отпечаток окружения — версия Python, отпечаток установленных пакетов
     окружения пульта, команда прогона (в том числе команда из профиля
     тестов проекта, когда гейт её передаёт).
   Два прогона с одинаковым содержимым дерева и одинаковым отпечатком
   окружения имеют один ключ; отличие любой составляющей — другой ключ.
2. Запись итога хранит ключ, время завершения прогона, исход (зелёный /
   красный), итоговую строку pytest, перечень упавших тестов и путь к
   файлу лога прогона.
3. Предел возраста итога — именованная константа
   `config.FULL_SUITE_REUSE_MAX_AGE_SEC`, значение 86400 (24 ч: автогейт,
   `approve` и гейт мержа одной задачи разнесены часами ожидания
   Оператора, в том числе через ночь).
4. Гейт — автогейт приёмки, `approve` в `acceptance`, гейт мержа — при
   найденном итоге с тем же ключом, возраст которого не больше
   `config.FULL_SUITE_REUSE_MAX_AGE_SEC`, берёт этот итог вместо прогона:
   `run_full_suite` не вызывается, замок полных прогонов машины не
   берётся.
5. Исход гейта на повторном итоге тот же, что был бы при прогоне с тем же
   итогом: зелёный итог — гейт проходит; красный — тот же отказ с теми же
   упавшими тестами и итоговой строкой pytest; `approve --accept-red
   "<основание>"` по повторному красному итогу проводит приёмку и пишет в
   журнал основание, имена упавших тестов и итоговую строку pytest, как
   по свежему прогону.
6. Запись журнала и `detail` гейта на повторном итоге содержат фразу
   «итог прогона <время>, дерево <хеш>, лог <путь> — использован
   повторно» с временем завершения исходного прогона, хешем дерева ключа
   и путём к логу исходного прогона.
7. Для повторного использования сохраняются и берутся только завершённые
   прогоны (исход зелёный или красный) с итоговой строкой pytest в выводе.
   Исходы «таймаут», «прогон не начат» (замок машины), «нет tests/» не
   сохраняются как итог для повторного использования и не берутся: следующий
   гейт на том же дереве гоняет набор.
8. Повторно используется только итог прогона на чистом дереве: в каталоге
   прогона нет неотслеживаемых файлов вне `tasks/` (туда пульт выкладывает
   планку), не попадающих в хеш содержимого. Каталог с такими файлами —
   обычный прогон, его итог для повторного использования не сохраняется.
9. Любое сомнение в ключе — обычный прогон (fail-closed): git не ответил
   или ответил ошибкой на любом шаге снятия хеша дерева, каталог не
   репозиторий git, отпечаток окружения не определился (версия Python или
   отпечаток пакетов не снялись), запись итога не читается или не
   разбирается. Итог такого прогона для повторного использования не
   сохраняется, если не определился его ключ.
10. Оператор может принудить новый прогон флагом `approve <id> [sha]
    --fresh-suite` в состояниях `acceptance` и `merge_gate`: с флагом гейт
    гоняет набор, даже если подходящий итог есть; итог нового прогона
    сохраняется по обычным правилам. Флаг сочетается с `--accept-red`.
    Строка использования `approve` в `orchestrator/artel.py` называет флаг.
11. Гейты по-прежнему не берут итоги `suite-run`: гейт не берёт итог,
    записанный прогоном `suite-run` (ни прогоном ветки, ни прогоном базы),
    даже при совпадении содержимого дерева; итог базы `suite-run` гейтам
    не отдаётся.
12. Итог прогона базы `suite-run` ищется и сохраняется по ключу
    «содержимое дерева кода базы без каталога `docs/` плюс отпечаток
    окружения прогона» (отпечаток — тот же, что в требовании 1: версия
    Python, отпечаток установленных пакетов окружения пульта, команда
    прогона), а не по sha коммита базы:
    - две базы, различающиеся только файлами под `docs/` (документные
      коммиты main), имеют один ключ — сохранённый итог базы берётся без
      прогона базы;
    - отличие любого файла вне `docs/` или любой составляющей отпечатка
      окружения — другой ключ, база прогоняется;
    - любое сомнение в ключе (git не ответил или ответил ошибкой при
      снятии содержимого дерева, отпечаток окружения не определился,
      запись итога не читается или не разбирается) — прогон базы
      (fail-closed, как требование 9); итог прогона, ключ которого не
      определился, не сохраняется.
    Режим `suite-run --failed` ищет итог базы по тому же ключу.
13. Сохранение итога завершённого прогона базы `suite-run` гарантировано:
    причина, по которой итог базы сегодня не сохраняется (в
    `.artel/logs/fullsuite-results/` нет ни одной записи базы при вызове
    `acceptance.save_failures` в `suite_run._base` ~402), названа в PLAN.md
    с местом в коде и устранена; после завершённого прогона базы с
    определённым ключом файл записи итога базы есть. Незавершённый прогон
    базы (таймаут) итог по-прежнему не сохраняет.
14. Поведение из требований 4–10 закреплено тестами в `tests/` с заявками
    «Ловит мутацию» (долгоживущие приёмочные тесты автора тестов этим
    засчитываются): `approve` после автогейта на том же дереве не запускает
    прогон; изменение одного файла, другое окружение или истёкший срок —
    прогон идёт; гейт мержа узнаёт дерево автогейта при неизменном main;
    таймаут повторно не используется; флаг принудительного прогона.

## Критерии приёмки
AC-1. Автогейт приёмки на дереве ветки задачи завершил полный прогон
красным с итоговой строкой pytest; затем `approve` в `acceptance` на том
же дереве (тот же коммит, те же приложения, то же окружение) в пределах
`config.FULL_SUITE_REUSE_MAX_AGE_SEC` не вызывает `run_full_suite`,
отказывает приёмке с теми же упавшими тестами и итоговой строкой pytest,
что дал автогейт.

AC-2. В сценарии AC-1 запись журнала и `detail` отказа `approve` содержат
«итог прогона <время>, дерево <хеш>, лог <путь> — использован повторно»,
где время — время завершения прогона автогейта, хеш — хеш дерева ключа,
путь — путь к логу прогона автогейта.

AC-3. В сценарии AC-1 `approve <id> --accept-red "<основание>"` не
вызывает `run_full_suite`, проводит приёмку и пишет в журнал основание,
имена упавших тестов и итоговую строку pytest повторного итога.

AC-4. Автогейт на голове ветки с наложенными приложениями PLAN завершил
прогон зелёным; main с тех пор не сдвинулся; гейт мержа на scratch-дереве
слияния с наложенными приложениями (без коммита) не вызывает
`run_full_suite`, проходит прогонное условие как зелёное и пишет в журнал
фразу требования 6.

AC-5. После сохранённого итога изменён один файл дерева (отслеживаемый,
незакоммиченный либо новым коммитом) — следующий гейт на этом дереве
вызывает `run_full_suite`.

AC-6. После сохранённого итога отличается одна составляющая отпечатка
окружения — версия Python, отпечаток установленных пакетов или команда
прогона — следующий гейт на том же дереве вызывает `run_full_suite`.

AC-7. Сохранённый итог старше `config.FULL_SUITE_REUSE_MAX_AGE_SEC` —
следующий гейт на том же дереве вызывает `run_full_suite`; итог не старше
предела — не вызывает.

AC-8. Прогон гейта завершился таймаутом (а также исходом «прогон не
начат» и «нет tests/») — следующий гейт на том же дереве с тем же
окружением вызывает `run_full_suite`. Прогон без итоговой строки pytest в
выводе повторно не используется так же.

AC-9. Git не отвечает или отвечает ошибкой при снятии хеша дерева
(каталог не репозиторий git — в том числе) либо отпечаток окружения не
определился — гейт вызывает `run_full_suite`, исход гейта определяется
этим прогоном, и повторное использование итога не происходит.

AC-10. Каталог прогона с неотслеживаемым файлом вне `tasks/` — итог
прогона для повторного использования не сохраняется, и следующий гейт на
том же каталоге вызывает `run_full_suite`.

AC-11. `approve <id> --fresh-suite` в `acceptance` и `approve <id>
--fresh-suite` в `merge_gate` при наличии подходящего итога вызывают
`run_full_suite`; исход гейта — по новому прогону; итог нового прогона
сохраняется, и следующий гейт без флага на том же дереве берёт уже его.

AC-12. Итоги `suite-run` гейтом не используются: после `suite-run`
задачи (прогон ветки и прогон базы завершены и сохранены) гейт на дереве
ветки и гейт на дереве базы с тем же окружением вызывают
`run_full_suite`.

AC-13. Запись итога завершённого прогона гейта содержит ключ (хеш дерева
и отпечаток окружения), время завершения, исход, итоговую строку pytest,
перечень упавших тестов и путь к логу прогона.

AC-14. После завершённого прогона базы `suite-run` (итоговая строка pytest
есть, ключ определился) в `acceptance.suite_results_dir()` есть файл
записи итога этой базы.

AC-15. После сохранённого итога базы в main появляется новый коммит,
меняющий только файлы под `docs/`; следующий `suite-run` задачи от новой
базы берёт сохранённый итог базы без прогона базы (обёртка профиля вне
рабочей копии задачи не вызвана, отчёт несёт число «падают и на базе»
сохранённого итога). Новый коммит main, меняющий хотя бы один файл вне
`docs/`, — следующий `suite-run` прогоняет базу.

## Меняемое поведение
Итог прогона гейта хранит ключ полного дерева и команду гейта, итог базы
`suite-run` — ключ дерева без `docs/` и команду `suite-run` (профиль
проекта плюс `-vv`); по требованию 12 итог гейта поэтому итогом базы
`suite-run` больше не служит. Существующий тест, ожидающий обратного:

- `tests/test_01m462qaceh29rprd2rzhghqfm_suite_run.py::BaseComparisonTest::test_ac13_gate_full_suite_result_is_reused_as_base`: `self.assertEqual(len(self.base_calls()), before,` → `self.assertEqual(len(self.base_calls()), before + 1,` (требование 12)

## Оценка объёма и деление
Сработавшие сигналы: число затрагиваемых файлов зоны ≥ 5
(`orchestrator/acceptance.py`, `orchestrator/fsm_autogate.py`,
`orchestrator/fsm.py`, `orchestrator/fsm_merge_gate.py`,
`orchestrator/artel.py`, `orchestrator/suite_run.py` вне общих зон);
число критериев приёмки ≥ 10 (15).

Материал для решения Оператора — обоснование монолита:
- Механика (ключ, запись, выбор итога вместо прогона) живёт в одном узле
  `acceptance.full_suite`, через который идут все три гейта; правки
  `fsm_autogate.py`/`fsm.py`/`fsm_merge_gate.py` — проводка ключа/флага и
  текста журнала к этому узлу, отдельно от узла они не мержимы и не имеют
  смысла.
- Часть «механика без флага `--fresh-suite`» оставила бы Оператора без
  способа принудить прогон при сомнении в повторном итоге (ложный зелёный
  из-за внешнего фактора) — промежуточное состояние, в котором гейт
  нельзя перепроверить без ручной чистки `config.LOGS`. Флаг же без
  механики ничего не делает. Резать по зонам `fsm.py`/`artel.py` против
  `acceptance.py` нельзя без такого состояния.
- Итог базы `suite-run` (требования 12–13) Оператор включил в эту задачу
  решением 06.10: ключ базы берёт тот же отпечаток окружения, что ключ
  гейта (требование 1), и без узла отпечатка не собирается; отдельная
  часть до основной механики потребовала бы второго узла отпечатка.
- Рамка ТЗ — $35; калибровка `config.BUDGET_CALIBRATION_TABLE` для 15
  критериев и 6 файлов зоны — $45, поставлено $45 (ниже дефолта $50).
  Решение по рамке — за Оператором на гейте SPEC.

## Не входит
- CI GitHub (push и pull_request) — повторное использование итогов там
  не вводится.
- Повторное использование гейтами итогов `suite-run` роли — после задачи
  об окружении `suite-run` (строка бэклога «suite-run роли — в окружении
  пульта»).
- Изменение `config.FULL_SUITE_TIMEOUT_SEC` и `config.FULL_SUITE_WORKERS`.
- Удаление существующего сохранения итога гейта по sha
  (`acceptance.save_failures`/`saved_failures` из `_remember_gate_failures`)
  — его ожидания держат существующие тесты; меняется только поиск и
  сохранение итога базы `suite-run` (требование 12).
- Правка файлов под `docs/` (кроме `docs/codebase-map.md`): `docs/` в
  требовании 12 и AC-15 назван только как каталог, исключённый из ключа
  итога базы.
- Прогон ветки задачи в `suite-run` (не базы) — повторное использование
  его итога не вводится.
- Изменение прогона планки задачи (`acceptance.run`) и прогона `notes`/
  `doc-commit` — только полный прогон гейтов через `acceptance.full_suite`.
- Выкладка планки в `tasks/` каталога прогона — не меняется; `tasks/`
  в требовании 8 и AC-10 назван только как исключение из проверки
  чистоты дерева.
- Неослабление существующих тестов — её держит пульт (гейт
  неослабления), отдельного критерия нет.
- Полный зелёный набор `tests/` и зелёный CI ветки — их держит пульт.
- Правка путей только для чтения из ТЗ: `docs/drafts/2026-10-05/
  tz-k6-suite-reuse.md`, `conftest.py`, `tests/test_invariants.py`,
  `docs/invariants.md`, `docs/adr/`, `docs/roadmap.md`, `docs/backlog.md`,
  `docs/operator-session.md`, `templates/`, `skills/`, `CLAUDE.md`,
  `models.yaml`, `roles.yaml`, `targets.yaml`, `.github/workflows/ci.yml`.
