# SPEC: Codex: вход по подписке ChatGPT вместо ключа API; ожидание каталога в test_models

## Контекст

Провайдер `codex` заведён предшественником 01M32NH6P053978AER66P0X4GN на
авторизации ключом API: `CodexProvider.environment`
(`orchestrator/providers/codex.py`) отдаёт шагу `OPENAI_API_KEY` из слота keychain
`config.OPENAI_API_KEY_SLOT`, `secret_env_names()` называет эту переменную
секретом провайдера, а предполётная строка `codex-api-key`
(`orchestrator/doctor/preflight.py`) смотрит только наличие ключа. Решением
Оператора 22.09.2026 (`docs/research/providers-codex-plan.md`, раздел 6 п.1)
путь ключа отменён: роли авторизуются входом по подписке ChatGPT.

Живые запуски Codex CLI 0.155.1 22.09 (`docs/research/codex-live-check-2026-09-22.md`)
показали, почему сегодняшний контур не годится даже механически: `codex exec`
читает ключ из `CODEX_API_KEY`, а не из `OPENAI_API_KEY`, то есть зелёная
строка `codex-api-key` не доказывала авторизацию вовсе; ключ Оператора при этом
без баланса. Вход ChatGPT хранит и продлевает сам CLI в системном Keychain при
`cli_auth_credentials_store=keyring` и `forced_login_method=chatgpt`, а
`codex login status` с домом роли отвечает «Logged in using ChatGPT» — это и
есть проверяемый факт вместо «ключ в слоте есть».

Заодно ключ течёт в чужие шаги: `OPENAI_API_KEY` стоит в белом списке
`stack.ROLE_ENV_ALLOWLIST`, поэтому заданный Оператором ключ копируется и в
окружение шага роли на Claude (об этом сегодня говорит жёлтая строка
`foreign-provider-secrets`, `orchestrator/doctor/isolation.py`).

Отдельным хвостом задача закрывает красный на пине `fd83eb5d` тест каталога
моделей (`tests/test_models.py`, 1 из 37): он ждёт ровно три модели Claude, а
приложение `models.yaml` части 1 добавило пять моделей OpenAI при мерже, уже
после CI ветки. Без этого ни у одной ветки этой линии не будет зелёной планки.

## Требования

Требования 1-9 — из ТЗ Оператора (`tasks/01M3EKCZJY9NGCW6VT878RX9JZ/TZ.md`),
своими номерами. Следующая задача линии 01M32NH9QTC1T6FNH8JD79662R (разбор
вывода Codex) стартует после мержа этой: обе меняют
`orchestrator/providers/codex.py`.

1. **Один способ авторизации у входа и у шага.** В команду шага `codex`
   добавляются переопределения `cli_auth_credentials_store=keyring` и
   `forced_login_method=chatgpt`; те же ключи с теми же значениями — в
   референсе `config.toml` дома роли
   (`docs/reference/role-home/codex/config.toml`). Проверка изоляции
   продолжает требовать дословного совпадения двух половин (пара за парой, в
   обе стороны), а не только наличия новых ключей.

2. **Окружение шага без секретов.** `CodexProvider.environment` отдаёт только
   дом роли (`HOME`, `CODEX_HOME`) и не читает keychain; ключ API роли не
   передаётся ни из слота, ни из окружения Оператора. Запись в Keychain
   Оператора (`artel-openai-api-key`) пульт не удаляет и не читает.

   **Судьба константы `config.OPENAI_API_KEY_SLOT` — удалить.** Обоснование:
   после требований 2 и 4 у неё не остаётся ни одного читателя в коде
   (сегодня их ровно два — `CodexProvider.environment` и
   `doctor.check_codex_api_key`, оба уходят этой задачей; третье упоминание —
   текст описания переменной в `stack.ROLE_ENV_ALLOWLIST`, которая уходит
   требованием 3). Оставленная «с пометкой не используется», она остаётся
   ИМЕНОВАННЫМ адресом слота внутри пульта: ближайшие задачи линии (разбор
   вывода, паритет безопасности) читают её как действующий канал секрета роли
   и легко возвращают ключ в окружение «по аналогии» — ровно то, что
   требование 3 запрещает. Саму запись keychain Оператора константа не держит:
   удаление имени в коде её не трогает (требование 2), а история слота остаётся
   в `docs/research/codex-live-check-2026-09-22.md` и в артефактах
   предшественника.

3. **Белый список окружения.** `OPENAI_API_KEY` убирается из
   `stack.ROLE_ENV_ALLOWLIST`: ключ API OpenAI не получает ни одна роль, ни на
   Codex, ни на Claude. `CODEX_API_KEY` и `CODEX_ACCESS_TOKEN` в белый список
   не входят и не добавляются. Тест фиксирует отсутствие всех трёх в собранном
   окружении шага роли на обоих провайдерах при заданных ambient-переменных.

4. **Проверка `codex-api-key` заменяется на `codex-chatgpt-auth`.** Новая
   проверка зовёт `codex login status` с окружением дома роли (`HOME`,
   `CODEX_HOME`) и теми же переопределениями авторизации, что у шага
   (требование 1). `ok` — только код выхода 0 и подтверждённый вход ChatGPT.
   Вывод CLI в строку `doctor` не попадает (секреты). Вызов ограничен
   таймаутом. Отказ называет, что сделать Оператору: указатель связки ключей
   для дома роли и команду входа. Проверка действует там же, где сегодняшняя
   `codex-api-key`: только когда `codex` — нужный инструмент. Остаток лимита
   подписки проверка не доказывает — это сказано в тексте строки или в
   документации.

5. **Проверки изоляции.** У провайдера `codex` нет секрета, приходящего через

   `OPENAI_API_KEY`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN` в собранном
   окружении шага Codex — провал `codex-isolation-smoke`. Строка

6. **`AGENTS.md` референса дома роли** (`docs/reference/role-home/codex/AGENTS.md`):

## Критерии приёмки

AC-1. `CodexProvider().command()` несёт `-c cli_auth_credentials_store=keyring`
и `-c forced_login_method=chatgpt`, каждый по индексу МЕНЬШЕ элемента `exec`;
прежние переопределения (выключенная сеть песочницы, политика подтверждений
«никогда») и все одиннадцать `--disable` в команде остались.

AC-2. `docs/reference/role-home/codex/config.toml` несёт значение `keyring` для
`cli_auth_credentials_store` и `chatgpt` для `forced_login_method`; сверка двух
половин дословная и двусторонняя — для каждой `-c`-пары команды шага в файле
есть та же пара «ключ = значение», и число `-c`-пар команды равно числу
соответствующих им пар файла (потеря или переименование пары в любой из двух
половин краснеет).

AC-3. `CodexProvider().environment(role, task_id)` отдаёт ровно `HOME` и
`CODEX_HOME` курируемого дома роли: ни `OPENAI_API_KEY`, ни `CODEX_API_KEY`, ни

имён, ни при непустом слоте keychain; `keychain.token` метод не зовёт ни разу;

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (7 путей зон,
внутри них 6-8 файлов правки), число критериев приёмки (15).

Прогноз диффа: 20 КиБ.

Решение — **монолит**. Требования 1-5 — одна смена механики авторизации,
разложенная по файлам, а не пять независимых правок:

- Убрать ключ из окружения (требование 2) без замены проверки (требование 4)
  значит смержить состояние, где предполёт зеленеет по наличию ключа, которого
  шагу уже никто не передаёт, — то есть `doctor` доказывает авторизацию, уже
  ставшую невозможной.
- Добавить переопределения авторизации в команду шага (требование 1) отдельно
  от `config.toml` нельзя механически: сверка двух половин двусторонняя (AC-2),
  и часть, правящая одну половину, краснеет на собственной планке.
- Убрать `OPENAI_API_KEY` из белого списка (требование 3) отдельно от
  требования 2 оставило бы `CodexProvider.environment`, который добывает ключ из
  keychain, и `codex-api-key`, который его требует, при окружении, куда ключ уже
  не попадает: шаг Codex падал бы на авторизации с зелёным предполётом.
- Требование 5 — проверки того же инварианта («у codex нет секрета в
  окружении»), которого до требований 2-3 просто нет.

Документация (требования 6-7) — тот же заход: абзацы, описывающие слот ключа,
становятся ложными ровно в момент мержа требований 2-3, и отдельной задачей
были бы правкой «вслед» по уже разошедшемуся описанию.

Требование 8 выглядит отделимым (своя зона `tests/`), но отдельной подзадачей не
мержимо: тест красный на пине, значит ветка ЛЮБОЙ части этой линии не получает
зелёной планки, пока ожидание каталога не поправлено, — часть «смена
авторизации» без него не доходит до `merge_gate` вовсе. Разрез дал бы две
части, из которых первая не мержима без второй, а вторая содержит одну правку
теста.

Материал Оператору для решения на гейте: по калибровке класс задачи — 15
критериев и 7 файлов зоны, потолок $45 (рамка ТЗ — $50). Правок кода немного,
вся площадь — существующие модули и их тесты; риск итераций ревью — в
требовании 4 (новая проверка с подпроцессом) и в требовании 9 (перечень
обновлённых ожиданий существующих наборов).
