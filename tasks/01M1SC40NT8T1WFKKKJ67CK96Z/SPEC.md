# SPEC: R1 — разбор цикла `auto` на шаги с явным контрактом

## Контекст
`orchestrator/auto.py::_cmd_auto` — 246 строк одной функции: предварительный
advance по готовым артефактам (с рубежами регрессии №13), запуск роли, разбор
отказов (guard, зоны, лимит параллельности, бюджет, CI, лок планки),
стоп-краны (буксование, повтор одинакового отказа), лимит шагов, журнал и
подсказки Оператору. Три регрессии 05.09 (№11, №13 и повтор эскалации после
ANSWER) сидели именно здесь; каждая правка требовала читать функцию целиком.
Задача — разбить функцию на именованные шаги с явным контрактом входа/выхода,
не меняя поведение (рефакторинг ≠ фикс).

## Требования
1. `_cmd_auto` разобрать на именованные функции по числу шагов цикла, каждая —
   отдельная функция с одним делом и явным входом/выходом:
   (а) решение «нужен ли пред-advance» (правила №13 — возврат с
   неотработанным основанием переделки, возврат из `escalated` — в одном
   месте);
   (б) выполнение пред-advance и разбор его исхода;
   (в) запуск шага роли и разбор исхода (finished/failed/skipped/timeout);
   (г) стоп-краны (буксование N шагов без перехода, повтор одинакового
   отказа, лимит шагов за вызов);
   (д) остановка с журналом и подсказкой (`auto_stop`).
   `_cmd_auto` становится короткой композицией этих функций.
2. Исходы шагов — явные значения (перечисление или маленький dataclass):
   `advanced`, `role_ran`, `refused(<причина>)`, `stop(<причина>)`, без
   передачи состояния через локальные переменные цикла и флаги.
3. Тексты журнальных записей, подсказок и печати сохраняются буквально:
   `tests/test_auto_cycle.py` и приёмочные тесты задач
   01M1R8B3ZKXQT0Z0G6QQQDV906 и 01M1RHFRQ2C0P4A57XJJ1WZV8N сверяют их.
4. Смоук байт-в-байт: на живом журнале пульта (копия БД в песочнице)
   сценарии `auto` из существующих тестов дают тот же журнал и тот же вывод
   до и после рефакторинга; отдельный тест сравнивает вывод старого и нового
   цикла на трёх записанных сценариях (фикстура — записанный вывод текущей
   реализации).
5. Существующие тесты `tests/test_auto_cycle.py` и приёмочные тесты задач
   01M1R8B3ZKXQT0Z0G6QQQDV906 и 01M1RHFRQ2C0P4A57XJJ1WZV8N зелёные без
   правки утверждений.

## Критерии приёмки

AC-1. `orchestrator/auto.py::_cmd_auto` разобрана на отдельные именованные
функции — по одной на каждый из пяти шагов цикла: (а) решение о
необходимости пред-advance (правила регрессии №13, включая возврат из
`escalated`, в одном месте); (б) выполнение пред-advance и разбор его
исхода; (в) запуск шага роли и разбор исхода (finished/failed/skipped/
timeout); (г) стоп-краны (буксование N шагов без перехода, повтор
одинакового отказа, лимит шагов за вызов); (д) остановка с журналом и
подсказкой (`auto_stop`). Сама `_cmd_auto` после разбора — короткая
композиция вызовов этих функций.

AC-2. Исходы шагов передаются между функциями явными значениями
(перечисление либо маленький dataclass) с именованными вариантами,
покрывающими как минимум `advanced`, `role_ran`, `refused(<причина>)`,
`stop(<причина>)`; состояние итерации цикла не передаётся через локальные
переменные-флаги, разбросанные по телу `_cmd_auto`.

AC-3. Тексты журнальных записей (`store.journal`), подсказок Оператору
(`auto_stop`, `auto_stop_advice`) и печатаемого вывода (`print`) после
рефакторинга совпадают буквально с текстами до рефакторинга — без единой
правки формулировок.

AC-4. `tests/test_auto_cycle.py` проходит без изменения ни одного
существующего утверждения (assertion).

AC-5. Приёмочные тесты задач 01M1R8B3ZKXQT0Z0G6QQQDV906 и
01M1RHFRQ2C0P4A57XJJ1WZV8N проходят без изменения ни одного существующего
утверждения.

AC-6. Добавлен новый тест, сравнивающий вывод (журнал задачи и печатаемый
stdout) цикла `auto` на трёх записанных сценариях с фикстурой — записанным
байт-в-байт выводом текущей (дорефакторинговой) реализации на тех же
сценариях, зафиксированным до правки кода.
