# PLAN: R1 — разбор цикла `auto` на шаги с явным контрактом

## Подход

Чистый структурный рефакторинг `orchestrator/auto.py::_cmd_auto` без
изменения поведения. Пять шагов SPEC становятся пятью новыми сущностями
модуля:

- (а) `_rework_gate_blocks` — решение «нужен ли пред-advance» (рубеж
  регрессии №13); возвращает `bool`, сам журналирует/печатает отказ
  ровно тем же текстом, что и раньше (побочный эффект остаётся здесь,
  а не переезжает в `_cmd_auto`).
- (б) `_pre_advance_step` — выполнение пред-advance и разбор исхода,
  включая часть стоп-кранов (г): «два подряд одинаковых отказа» и «N
  шагов без перехода» считаются по факту попытки пред-advance, поэтому
  их код естественно остаётся в этой же функции, не выносится в
  отдельную ради формального разделения. Возвращает `Advanced | Refused
  | Stop | None`.
- (в) `_role_run_step` — запуск `runner.cmd_run` и разбор исхода
  (finished / отказ стартовать: пауза, занятость зоны, бюджет, лимит
  параллельности — через перехват `SystemExit`). Возвращает `RoleRan |
  Stop`.
- (г) `_step_limit_stop` — третий стоп-кран (лимит шагов за вызов),
  проверяемый в начале каждой итерации, до пред-advance.
- (д) `auto_stop` — уже существовал, не менялся; каждый `Stop`,
  вернувшийся из шагов (б)/(в)/(г), доводится до него композицией в
  `_cmd_auto`.

Исходы — четыре маленьких frozen-dataclass верхнего уровня (AC-2):
`Advanced(before, after)`, `RoleRan(role, before, after)`,
`Refused(reason)`, `Stop(state, reason, hint, alert)`. Состояние
итерации, которое раньше жило в локальных флагах `_cmd_auto`
(`idle_steps`, `prev_refusal`), переехало в поля отдельного
mutable-объекта `_CycleState`, которым владеет и который мутирует
только `_pre_advance_step` — `_cmd_auto` создаёт `_CycleState()` один
раз и передаёт его дальше, ни разу не читая и не записывая эти два поля
сама (проверено тестом AC-2 на голые `ast.Name`).

`_cmd_auto` после разбора — цикл `while`, тело которого: проверка
`state == "verifying"` (не менялась), `_step_limit_stop`,
`_rework_gate_blocks` → (если не блокирует) `_pre_advance_step`,
безусловный запуск `_role_run_step`, разбор исхода через `isinstance` и
переход к следующей итерации. Ни один из четырёх текстовых литералов,
запрещённых тестом AC-1 (`runner.cmd_run(`, `_REWORK_GATE_STATES`, `>=
config.AUTO_MAX_STEPS`, `>= config.AUTO_STALL_STEPS_LIMIT`), в теле
`_cmd_auto` не встречается — они остаются внутри новых функций.

Побочный эффект решения «не увеличивать число вызовов `store.get_task`
искусственно ценой усложнения контракта функций»: после `Advanced` и
после `RoleRan` `_cmd_auto` делает собственный `store.get_task`, хотя
внутренняя функция уже читала свежую строку секундой раньше для своих
целей (проверка перехода / текст лога). Лишнее чтение — `SELECT` без
побочных эффектов (`store.get_task` не пишет и не журналирует), поэтому
на наблюдаемый вывод (журнал, stdout) оно не влияет; альтернатива —
протаскивать `sqlite3.Row` через возвращаемое значение исхода — усложнила
бы контракт исходов ради экономии одного дешёвого чтения БД на итерацию.

Никаких новых веток поведения не заводится: каждая ветвь исхода в
`_cmd_auto` — прямой перенос соответствующего `if`/`continue`/`return`
из дорефакторинговой реализации, без изменения порядка вызовов
(`fsm.cmd_advance` → чтение состояния → анализ отказа → `runner.cmd_run`)
и без изменения ни одного текста.

## Влияние на систему

Зона задачи — `orchestrator/auto.py` и `tests/`; ничего за её пределами
не трогается. Поведение цикла `auto` не меняется ни в одной ветке — это
проверяется буквально: существующий `tests/test_auto_cycle.py` (~90
тестов, сверяющих журнал/print по тексту) остаётся зелёным без правки
ни одного assert, плюс новый тест сравнивает три сценария байт-в-байт с
фикстурой дорефакторинговой реализации (AC-6). Приёмочные тесты
01M1RHFRQ2C0P4A57XJJ1WZV8N (рубеж регрессии №13) прогнаны и зелёные —
это тот самый код, который переехал в `_rework_gate_blocks`/
`_pre_advance_step`, и его поведение не изменилось.
01M1R8B3ZKXQT0Z0G6QQQDV906 (пред-advance до шага роли) — половина
критерия без стенда в этой ветке, см. `acceptance_tests/
test_ac5_referenced_tasks_acceptance_suites_stay_green.py`, помечена
`manual`; сама механика пред-advance, которую он проверяет, — это
`_pre_advance_step`, перенесённая без изменений текста.

Инварианты (`docs/invariants.md`) не заводятся и не трогаются — задача
не меняет условие выхода цикла, только его внутреннюю структуру.
Откат — `git revert` коммита рефакторинга: новые dataclass/функции не
используются ничем снаружи `orchestrator/auto.py`, публичный контракт
модуля (`cmd_auto`, `auto_stop`, `auto_stop_advice`) не менялся.

## Риски

Главный риск рефакторинга такого рода — тихо изменить порядок вызовов
или потерять побочный эффект (журнальную запись, print) при переносе
кода между функциями. Смягчено тем, что перенос делался почти
дословно (тот же порядок операций, те же f-строки), и что оба вида
проверки (существующий набор + новая байт-в-байт фикстура) ловят любое
расхождение текста на первой же разошедшейся строке, не только факт
падения теста.
