# PLAN: A2b — git-первичка артефактов и approve-по-sha

## Подход

Единая точка входа для hash-фиксации — `store.set_state`: это уже
единственный код, через который проходит ЛЮБОЙ переход FSM (grep
подтверждает — прямых `UPDATE tasks SET state=` вне него нет). Хук
внутри него гарантирует «на каждом переходе» по построению, а не по
дисциплине расстановки вызовов в fsm.py/budget.py/runner.py/cleanup.py
(8+мест) — с тем самым риском, о котором предупреждает
skills/coding-standards.md: точечный фикс части мест вместо всего
класса.

Чтобы `store.py` остался «единственным модулем с SQL» (ADR-0003 3ж) и
листовым слоем пакета (SqlOnlyInStoreTest), git-логика лежит в новом
модуле `orchestrator/fixation.py`, а `store.set_state` подключает его
ОТЛОЖЕННЫМ импортом (`from . import fixation` внутри функции): `store`
не тянет `fixation` при загрузке модуля, `fixation` спокойно импортирует
`store` сверху (использует `store.get_task`/`task_target` для
`check_integrity`) — цикла на уровне загрузки модулей не возникает,
потому что к моменту вызова `store.set_state` модуль `store` уже
полностью загружен.

`fixation.fix(task_id, target)` — единая точка вычисления `(sha, чисто)`
с двумя ветками:
- **Догфуд** (`target == config.DEFAULT_TARGET`, особый случай до A7):
  ничего не коммитит — читает уже закоммиченное состояние пульта
  (`gitcmd.head_sha()` + `gitcmd.is_clean(f"tasks/{task_id}")`).
  Существующий флоу артефактов (коммитит их сама роль внутри шага) не
  меняется (требование 3).
- **Внешний target**: коммитит артефактный git-репо целиком
  (`.artel/projects/<target>/`, `git add -A` + commit при наличии
  застейдженного диффа) — будущие типы артефактов попадают в тот же
  коммит без правки этой функции (требование 2, ADR-0003 п.15).
  Identity коммита — фиксированная («Artel Orchestrator»), не
  Оператора: коммит служебный, не авторский.

`sha == ""` в обеих ветках означает «git не ответил или фиксировать
нечего» — вырожденный случай, на котором approve/run ведут себя как до
T021 (см. ниже). Это не обход инварианта, а осознанная деградация:
единственный источник такого состояния в проде — сломанный git, что уже
inherently «не работает» по всей системе; в песочницах существующих
тестов (test_invariants.FsmTest и другие, где `gitcmd.git`/`subprocess.run`
подменены заглушками без реального репозитория) это и есть путь,
которым флоу T001–T020 остаётся неизменным без правки их кода
(требование 3, критерий 3).

**Approve-по-sha** (`fsm.cmd_approve(task_id, sha=None)`) на входе в
любое из 4 approve-состояний (`spec_gate`, `acceptance`, `merge_gate`,
`escalated`) живьём пересчитывает `fixation.fix()` (не читает
устаревшее значение из БД) и:
- фиксации нет (`sha == ""`) — пропускает проверку, старое поведение;
- фиксация есть, sha не передан — печатает текущий и просит повторить,
  переход не происходит (мягкий возврат, не отказ);
- fixed sha есть и передан, но не совпадает или копия грязная — жёсткий
  отказ (`sys.exit`, тем же стилем, что и отказ merge по красному CI);
- совпадает и чисто — обычная логика гейта (не менялась), которая сама
  вызовет `store.set_state` и перезафиксирует уже подтверждённое
  состояние.

**Сверка при старте шага** (`runner.cmd_run`, перед определением роли
и подготовкой промпта): `fixation.check_integrity(conn, task_id)`
сравнивает ЖИВОЕ состояние с `tasks.fixed_sha`, записанным на
последнем переходе. Историческая фиксация пуста — сверять не с чем
(тот же вырожденный случай). Есть и разошлась (другой sha) или грязная
копия — задача уходит в `escalated` с `escalated_from`, агент не
стартует (`Popen` не вызывается).

`git -C <repo>` вместо `subprocess.run(..., cwd=...)`: существующие
тесты подменяют саму функцию `gitcmd.git` заглушками с сигнатурой
`(*args: str)` (test_multitarget.py, test_multitarget_invariants.py,
test_agent_failure.py, test_step_cost.py, test_auto_cycle.py) — приняв
`cwd=` вторым параметром `git()`, я бы уронил все эти заглушки
`TypeError`. `-C` остаётся обычным позиционным аргументом, который эти
заглушки уже умеют разобрать, и сигнатура `gitcmd.git(*args: str)` не
меняется вовсе.

## Влияние на систему

Хук в `store.set_state` касается КАЖДОГО перехода FSM в системе — самое
широкое изменение в этой задаче. Смягчено тем, что:
- на все существующие песочницы (git замокан заглушками без реального
  репозитория) хук вырождается в отсутствие эффекта — «фиксации нет,
  сверка отключена», записанное поведение до T021, без правки старых
  тестов, кроме одного точечного `dirs()` (шаг 8, прямое следствие
  требования 1, не побочный эффект).
- `store.py` не приобретает новых SQL-путей и остаётся единственным
  модулем с SQL (`SqlOnlyInStoreTest` не меняется и продолжает
  проходить) — весь non-SQL код фиксации живёт в `fixation.py`.
- `approve` и `run` не получают новых способов ОБОЙТИ существующие
  гейты/лимиты — только новый способ ИМ ОТКАЗАТЬ (жёстче, не мягче):
  принцип целостности (ADR-0002) не нарушается, инвариантов не снято.
- CLI `approve` принимает необязательный второй аргумент — обратная
  совместимость вызова `approve <id>` сохранена везде, где фиксации нет.

Новый инвариант 25 в docs/invariants.md добавляется, не заменяет и не
ослабляет ни один из 1–24. Мутационная проверка: убрать вызов
`fixation.check_integrity(...)` в `runner.cmd_run` (или закомментировать
`if incident is not None: ...`) — `FsmDecidesOnlyOnFixedHashesTest`
в `tests/test_git_fixation.py` краснеет (агент стартует на разошедшемся
sha).

Откат: все изменения — новый модуль `fixation.py` + аддитивные правки
(новая колонка БД со значением по умолчанию NULL, новая необязательная
секция логики в существующих функциях). Откат — `git revert` коммита(ов)
задачи; колонка `fixed_sha` в откаченной схеме просто перестаёт
использоваться (SQLite не требует явного DROP COLUMN для отката
поведения).

## Риски

- Внешний target: `fix()` для чужого target читает и коммитит
  `.artel/projects/<target>/` напрямую через `store.set_state` — САМ
  `fsm.cmd_advance` пока не умеет читать артефакты внешнего target
  (у него `tdir = config.TASKS / task_id` захардкожен на пульт, это
  зона будущей задачи, не A2b: SPEC T021 не включает переподключение
  `advance`/`run` на чтение из `.artel/projects/<target>/tasks/`).
  Поэтому тесты требования 2 фиксацию вызывают напрямую через
  `store.set_state`, как это уже делает `test_multitarget_invariants.py`
  для synthetic-задач — тот же приём, не новый.
- (найдено на MR, закрыто) `check_integrity()` — точка ПРОВЕРКИ, не
  фиксации, и не имеет права мутировать репозиторий: изначально она
  читала состояние тем же `fix()`, что и переходы FSM, а `fix()` для
  внешнего target безусловно делает `add -A` + `commit`. Итог — сверка
  перед стартом шага задачи B коммитила заодно и незакоммиченный
  артефакт ЧУЖОЙ задачи A того же target (роль A ещё пишет файл), сдвигая
  HEAD, который A не просила сдвигать — ложный инцидент целостности у A
  на следующем её переходе. Починено отдельной нечитающей веткой
  `fixation._read()`/`_read_external()`: без `add -A`/`commit`,
  `check_integrity` теперь только читает. Остаточное ограничение (не
  дефект, а следствие требования 2 — коммит внешнего репо «целиком», не
  по задачам): «чисто» для внешнего target репо-широкое, поэтому WIP
  задачи A временно блокирует и `run` задачи B того же target тоже (обе
  уходят в ожидание, история при этом не портится) — известное сужение
  гранулярности фазы A2b при нескольких одновременно активных задачах
  одного target, снимается вместе с переподключением `advance`/`run` на
  чтение артефактов из `.artel/projects/<target>/tasks/` (см. пункт выше,
  не входит в A2b). Тесты: `tests/test_git_fixation.py`,
  `ExternalIntegrityIncidentBlocksRunTest`.
- Идентичность коммита фиксации внешнего target — фиксированная
  константа, не git-конфиг Оператора: если позже потребуется другая
  identity (например, сервисный бот с другим именем), это отдельное
  решение Оператора, не блокер этой задачи.
- `git -C` есть в git ≥ 1.8.5 (2013) — тот же минимальный уровень, что
  уже принят кодовой базой (`git init -b` используется с git ≥ 2.28,
  test_multitarget_invariants.py уже полагается на него).
