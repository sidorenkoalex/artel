# REVIEW: A2b — git-первичка артефактов и approve-по-sha

## Фаза A — гейт плана

Покрытие: все 7 требований SPEC отображены в таблице покрытия PLAN на
конкретные шаги 1–10; шаги — цельные, ревьюабельные единицы (по модулю),
не микрооперации и не «сделать всё». Подход (единая точка хука в
`store.set_state`, `fixation.py` как отдельный не-SQL модуль, отложенный
импорт против цикла, `git -C` вместо `cwd=` ради существующих заглушек)
не конфликтует с конвенциями (`SqlOnlyInStoreTest`, ADR-0003 3ж) и
архитектурой. План был обоснованно принимаем на момент гейта.

Ретроспективно (уже по факту реализации) в плане не хватало одной вещи:
формулировка «`fixation.fix()` — единая точка вычисления (sha, чисто)»
не проговаривает, что эта же функция, вызванная из
`check_integrity()` (то есть из «проверки», а не «фиксации»), будет
стейджить и коммитить рабочее дерево внешнего target как побочный
эффект сравнения. Это стоило явно назвать в PLAN как риск — см.
замечание 1 ниже, найденное уже на MR.

## Замечания

- major — `orchestrator/fixation.py:51-75` (`_fix_external`), вызывается
  из `orchestrator/runner.py:39` через `check_integrity` —
  `check_integrity()` документирован и используется как проверка
  («Сверяет ЖИВОЕ состояние... закрытие TOCTOU»), но для внешнего target
  он вызывает `fix()`, которая безусловно делает `git add -A` и, если
  есть застейдженный дифф, **коммитит** его (fixation.py:64-70) — то
  есть «проверка» перед стартом шага реально мутирует артефактный
  git-репозиторий target'а. Поскольку требование 2 сознательно коммитит
  каталог `.artel/projects/<target>/` целиком (не по задачам), а
  `fixed_sha`/`check_integrity` при этом ведутся per-task, отсюда
  конкретный сценарий поломки: задача A стоит в `in_dev` с
  незакоммиченным файлом в `.artel/projects/<target>/tasks/A/`
  (например, роль ещё пишет PLAN.md); Оператор запускает `artel.py run
  B` для ДРУГОЙ задачи B того же target. `check_integrity(B)` вызывает
  `fix()`, та стейджит и коммитит вместе с состоянием B и незакоммиченный
  файл A — HEAD артефактного репо сдвигается коммитом, который A не
  просила. При следующем `run`/`approve` задачи A её `fixed_sha`
  (записанный до вмешательства B) уже не совпадает с живым HEAD —
  A уходит в `escalated` с «инцидент целостности», которого сама A не
  совершала. Это ложный срабатывание ключевого инварианта 25 на ровном
  месте, ничем не описанное в разделе PLAN «Риски». Предложение: сделать
  `check_integrity` не мутирующей операцией для внешнего target (сравнение
  `git status`/незакоммиченного диффа без `add -A`+`commit`), либо, если
  сведение в один коммит каталога — намеренное ограничение фазы A2b при
  нескольких активных задачах одного target, явно зафиксировать это как
  известное ограничение в PLAN/SPEC и решить, кто про это должен узнать
  (Оператор через doctor, A3?).

- major (тесты) — `tests/test_git_fixation.py`: `IntegrityIncidentBlocksRunTest`
  (строка 405) и `FsmDecidesOnlyOnFixedHashesTest` (строка 444) — оба
  наследуют только `RealPultGitTest` (догфуд-песочница). Вызов
  `fixation.check_integrity` внутри `runner.cmd_run` (runner.py:39) для
  ВНЕШНЕГО target не проверен ни одним тестом — `TmpRootTest`-песочница
  используется только в `ArtifactRepoInitTest`/`NoRemoteCheckTest`/
  `ExternalTransitionCommitsTest`, ни один из них не вызывает
  `runner.cmd_run`. Между тем `runner.role_cwd` (runner.py:207) уже
  умеет запускать шаг для внешнего target (не только для догфуда), то
  есть это реальный, а не гипотетический код-путь. Именно этот пробел
  и не поймал дефект из замечания 1. Предложение: добавить
  `TmpRootTest`-класс, аналогичный `IntegrityIncidentBlocksRunTest`, где
  после approve по sha артефакт внешнего target подменяется мимо гейта
  и вызывается `runner.cmd_run` — с проверкой и что происходит с чужой
  незакоммиченной задачей того же target по сценарию замечания 1.

- minor — `tests/test_git_fixation.py:375` (`ApproveByShaTest`) — все
  три теста проходят подтверждение sha только через `spec_gate`
  (`enter_spec_gate`/`enter_in_dev`). Состояние `escalated` тоже входит
  в `fsm.APPROVE_NEEDS_SHA` (fsm.py:110) и это единственный путь выхода
  из инцидента целостности после замечания в требовании 5, но ни один
  тест не вызывает `fsm.cmd_approve(task_id, sha)` НА escalated с
  реально совпадающим sha, чтобы проверить полный цикл
  «инцидент → approve с напечатанным sha → возврат в
  escalated_from». Стоит добавить такой тест — это ровно тот путь,
  которым Оператор будет закрывать инциденты на практике.
