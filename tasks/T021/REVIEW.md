## Замечания

- **blocker** — `orchestrator/fsm.py:127` (`confirm_fixation`), вызывается
  из `cmd_approve` (fsm.py:147) на любой попытке approve в состояниях
  `APPROVE_NEEDS_SHA` (`spec_gate`, `acceptance`, `merge_gate`,
  `escalated`) — тот же класс дефекта, что закрыт в этой же итерации для
  `check_integrity` (замечание 1, итерация 1), но НЕ закрыт здесь:
  `confirm_fixation` сравнивает текущее состояние через
  `fixation.fix(task_id, target)` (fsm.py:127), а не через нечитающий
  `fixation._read()`, который для этой же цели уже добавлен в
  `fixation.py` в этом MR. `fix()` для внешнего target безусловно делает
  `git add -A` + `commit` (fixation.py:71-83) — то есть каждый вызов
  approve, включая ЗАПРОС текущего sha без параметра (SPEC требование 4:
  «мягкий возврат, не отказ», состояние не должно меняться) и ОТКАЗАННЫЙ
  approve с неверным sha (`sys.exit`), коммитит артефактный репо ЦЕЛОГО
  target'а целиком — подхватывая и чужой незакоммиченный WIP.

  Воспроизвёл трижды напрямую (реальный git, без моков, тот же приём, что
  в `TmpRootTest`):
  1. Task A в `spec_gate`; task B того же target в `in_dev` пишет
     `PLAN.md`, не коммитит (обычный WIP роли). Оператор вызывает
     `artel.py approve A` БЕЗ sha — просто посмотреть, что подтверждать.
     Функция печатает sha и возвращает `False` (переход НЕ происходит, A
     остаётся в `spec_gate`) — но HEAD артефактного репо `sled` сдвинулся,
     и незакоммиченный `PLAN.md` задачи B ушёл в этот коммит (`git status`
     до вызова: `?? tasks/SLED-T002/`; после — пусто).
  2. То же самое с ОТКАЗАННЫМ approve (`approve A <неверный sha>`,
     `sys.exit`, состояние A не меняется) — HEAD всё равно сдвигается,
     WIP задачи B всё равно коммитится.
  3. Более серьёзный сценарий: у task B уже ЕСТЬ легитимный `fixed_sha`
     (записан её собственным переходом в `in_dev`), и пока её роль
     дописывает `PLAN.md` без коммита (штатный флоу некоммитящей роли для
     внешнего target), Оператор УСПЕШНО подтверждает approve СОВСЕМ
     ДРУГОЙ задачи A правильным sha. `confirm_fixation` для A по пути
     коммитит WIP B; `tasks.fixed_sha` задачи B в БД не менялся (B не
     переходила), но живой HEAD репо сдвинулся мимо неё. Следующий вызов
     `fixation.check_integrity(conn, "B")` (путь `runner.cmd_run`, который
     эта же итерация только что защитила от мутации) возвращает `"sha
     разошёлся с зафиксированным"` — B уходит в `escalated` с инцидентом
     целостности, которого не совершала. Ровно тот же механизм, что
     замечание 1 итерации 1 описывало для `check_integrity`, только
     источник мутации теперь `approve` ДРУГОЙ задачи, а не сам
     `check_integrity`.

  Итог: фикс этой итерации закрыл один из двух путей, которыми `fix()`
  (мутирующая функция) вызывается там, где нужно только сравнение, —
  `check_integrity`. Второй путь с той же природой — `confirm_fixation`/
  `cmd_approve` — остался нетронутым, хотя `fixation._read()`, уже
  добавленный ради первого фикса, для этой цели готов: сравнение sha на
  входе approve не обязано коммитить — легитимный коммит перехода A
  случится позже, в `store.set_state` → `_record_fixation` → `fix()`,
  если сверка сошлась. Предложение: `confirm_fixation` (fsm.py:127)
  сравнивает через `fixation._read(task_id, target)` (сделав её публичной
  или добавив тонкую публичную обёртку в `fixation.py`, раз её теперь
  предлагается использовать и из `fsm.py`, не только внутри самого
  модуля), а не через `fixation.fix()`. Тест: аналог
  `ExternalIntegrityIncidentBlocksRunTest`, но для `fsm.cmd_approve`
  внешнего target — approve/reject задачи A с незакоммиченным WIP задачи
  B того же target рядом, проверка что HEAD репо B не сдвигается и WIP B
  остаётся некоммиченным.

## Вердикт

changes_requested — до мержа нужно закрыть blocker: `confirm_fixation`
должна сверяться нечитающим путём (`fixation._read`), а не мутирующим
