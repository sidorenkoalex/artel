# SPEC: A2b — git-первичка артефактов и approve-по-sha

## Контекст

Четвёртая задача фазы A (roadmap §2 A2b). Артефакты — управляющий
вход системы: SPEC ведёт разработчика, REVIEW двигает FSM; их
модификация в обход гейтов = управление конвейером (ADR-0003 п.15).
Сейчас фиксации нет: approve подтверждает «то, что лежит на диске
в момент approve», и между «Оператор посмотрел» и «шаг стартовал»
артефакт может измениться незамеченным (TOCTOU). Решение принято
в ADR-0003 пп.15, 17: hash-фиксация через git-первичку (sha коммита
вместо пофайловых хэшей), approve с привязкой к sha, сверка
на гейтах И при старте каждого шага. Особый случай догфуда до A7:
артефакты артели живут в ветках задач git пульта (ADR-0003 3д) —
носитель фиксации для них уже существует, нужен только учёт sha.

## Требования

1. Артефактный git-репозиторий внешнего target: команда
   инициализации target (T019) делает `git init`
   в `.artel/projects/<target>/`; workspace/ и logs/ — в .gitignore
   этого репо; remote отсутствует; повторная инициализация
   идемпотентна (ADR-0003 3д).
2. Оркестратор коммитит артефактный репо целевого на каждом переходе
   FSM его задач; sha коммита пишется в журнал БД (ADR-0003 п.15:
   коммит фиксирует каталог целиком, будущие типы артефактов —
   автоматически).
3. Догфуд-артель (до A7): на каждом переходе FSM в журнал пишется
   head sha ветки задачи пульта и признак чистоты `tasks/<id>/`
   в рабочей копии — существующий флоу артефактов не меняется.
4. **Approve с привязкой к sha** (закрытие TOCTOU показа): `approve
   <id> <sha>` подтверждает конкретный sha; расхождение
   с текущим зафиксированным = отказ. `approve <id>` без sha
   не проходит молча: печатает текущий зафиксированный sha
   и требует повторить команду с ним.
5. **Сверка при старте каждого шага и на гейтах** (ADR-0003 п.17,
   безусловное правило): вход шага сверяется с sha, зафиксированным
   журналом/approve; расхождение или грязная копия артефактов =
   инцидент целостности — стоп задачи с эскалацией, агент
   не запускается.
6. Новый инвариант в реестр (docs/invariants.md + тест): «FSM
   принимает решения только по артефактам, чьи хэши зафиксированы
   его журналом» (формулировка — ADR-0003 п.15).
7. Функция проверки «у артефактного репо целевого нет remote»
   (потребитель — doctor, подключение в A3; здесь — функция + тест).

## Критерии приёмки

1. Тест: инициализация фиктивного target создаёт git-репо без
   remote с нужным .gitignore; повторная инициализация не меняет
   состояния и не падает.
2. Тест: переход FSM задачи фиктивного target создаёт коммит
   артефактного репо, sha записан в журнал.
3. Тест: для догфуд-задачи на переходе в журнале появляется head
   sha ветки и признак чистоты; флоу T001–T021 не изменился
   (существующие тесты зелёные без правок семантики).
4. Тест: `approve <id> <sha>` с несовпадающим sha — отказ;
   `approve <id>` без sha на гейте, требующем фиксации, — отказ
   с печатью текущего sha; с совпадающим — проходит.
5. Тест: изменение артефакта после approve (или грязная копия
   tasks/<id>) — старт шага отказывает, задача в escalated
   с причиной «инцидент целостности», агент не запущен.
6. Инвариант-строка в docs/invariants.md с парным тестом;
   мутационная проверка зафиксирована в PLAN (какую строку снять —
   какой тест краснеет).
7. Все существующие тесты и guard --all зелёные.

## Не входит

- doctor как команда и его прогон проверок (A3) — здесь только
  функция п.7.
- Публикация следа, ветка artel целевого, права записи
  (docs/deferred/publication.md — отложено целиком).
- Изменение места хранения артефактов догфуда (до A7).
- Подписанные коммиты (триггер №14 docs/triggers.md).
- Кнопки/панель approve (этап 2 панели).
