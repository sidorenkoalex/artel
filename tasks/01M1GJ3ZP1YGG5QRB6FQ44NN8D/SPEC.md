# SPEC: Сухой прогон приёмки — предпросмотр без исполнения

## Контекст

Протокол ручных гейтов (docs/operator-gates.md, гейт приёмки) требует,
чтобы Оператор до `approve` сверился с приёмочными тестами — число
тестов против AC, каждая пометка manual/skip прочитана. Сегодня для
этого нет отдельной команды: либо смотреть файлы `tasks/<id>/
acceptance_tests/` руками (ветко-зависимо, легко ошибиться чекаутом),
либо ждать реального прогона на переходе гейта. Нужна дешёвая read-only
команда предпросмотра, которая по построению не может быть принята за
прохождение приёмки.

## Требования

1. Новая read-only CLI-команда сухого прогона приёмки по id задачи,
   регистрируется в `orchestrator/artel.py`; имя команды и остальное
   место реализации — решение разработчика. Команда показывает:
   обнаруженные тестовые файлы и тестовые методы в `tasks/<id>/
   acceptance_tests/`; все AC-маркеры (manual/skip/escalate) с
   причинами; сводку трассируемости — какой AC покрыт тестом либо
   пометкой, какие AC не покрыты.
2. Разбор тестовых файлов и маркеров переиспользует
   `scripts/guard.py::scan_acceptance_tests` — тот же код, что уже
   держит трассируемость AC на переходе `tests_writing` и сводку
   карточки гейта `acceptance` (`orchestrator/acceptance.py::summary`)
   — без дублирования логики разбора: расхождение источников должно
   быть невозможно по построению.
3. Команда read-only: не запускает unittest, не пишет в БД и журнал
   задачи, не меняет состояние задачи, не берёт lease — тот же класс
   команд, что `status`/`log`.
4. Вывод явно маркирован как сухой прогон, не эквивалент прохождения
   приёмки: содержит текст «сухой прогон — не является прохождением
   приёмки»; результат команды нигде не записывается и не может быть
   предъявлен как пройденная приёмка (эквивалент `passed: null`).
5. Чтение `tasks/<id>/acceptance_tests/` — ветко-корректное (инвариант
   28, `docs/invariants.md`): источник истины — ветка задачи через git
   (`git show`/`git ls-tree`), чужой чекаут рабочей копии её не
   подменяет.
6. Ветки задачи нет, либо на ней нет каталога `acceptance_tests/` —
   команда завершается честным именованным отказом с указанием, чего
   не хватает (нет ветки / нет каталога), не пустой сводкой.

## Критерии приёмки

AC-1. Команда существует, зарегистрирована в `orchestrator/artel.py`,
принимает id задачи, read-only, и печатает список обнаруженных
тестовых файлов и тестовых методов из `tasks/<id>/acceptance_tests/`
ветки задачи.

AC-2. Команда печатает все AC-маркеры (manual/skip/escalate) с их
причинами.

AC-3. Команда печатает сводку трассируемости: для каждого AC из SPEC —
покрыт тестом, покрыт пометкой, или не покрыт; непокрытые AC названы
явно (номерами).

AC-4. Разбор тестовых файлов и AC-маркеров команда получает через
`scripts/guard.py::scan_acceptance_tests` (либо разбирающее его ядро
`scan_ac_content` над содержимым, прочитанным с ветки) — без
собственной параллельной реализации того же разбора.

AC-5. Команда не запускает unittest, не пишет строк в журнал задачи и
БД, не меняет состояние (`status`) задачи, не берёт lease задачи.

AC-6. Вывод команды содержит текст «сухой прогон — не является
прохождением приёмки»; результат команды не записывается ни в один
артефакт, БД или журнал задачи.

AC-7. Чтение `acceptance_tests/` ветко-корректно: под чужим чекаутом
рабочей копии пульта (не на ветке задачи) команда всё равно читает
содержимое `tasks/<id>/acceptance_tests/` с ветки задачи через git, а
не с диска рабочей копии.

AC-8. Ветки задачи нет, либо на ней нет каталога `acceptance_tests/` —
команда завершается именованным отказом, называющим отсутствующее
(ветку либо каталог), а не пустой/нулевой сводкой.

AC-9. Все существующие тесты проходят зелёными.

## Не входит

- Запуск приёмочных тестов в каком-либо режиме, включая «безопасный»
  или «пробный» — команда только читает и разбирает, unittest не
  вызывается.
- Изменение механики перехода `acceptance` и автогейта
  (`orchestrator/fsm_advance.py`, `orchestrator/fsm_autogate.py`).
- Изменение формата AC-маркеров и разметки тестов (`scripts/guard.py`
  не меняется, переиспользуется как есть).
- Правка `orchestrator/catalog.py` — зона задачи «Наблюдаемость
  сессий», ещё не смержена.
- Правка `orchestrator/fsm_advance.py` — зона задачи «Лимиты пакетов»,
  ещё не смержена. Конфликт зон с этими задачами — повод для эскалации
  разработчиком, не выход за границу.
