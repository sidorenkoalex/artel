# PLAN: Эпики Э2а — конверт бюджета эпика и зависимость запуска start_after

## Подход
Сверка интерфейсов Э1 (раздел SPEC «Порядок разработки»): Э1 смержен
(f909b7dd9). `orchestrator/epics.py` (`epic new … --envelope`, `epic show`,
`show_lines`), `orchestrator/board.py` (`build_model`, карточки `task`/
`waiting_on`, элемент эпика `spent_usd`/`envelope_usd`), `new --epic`/
`new --after` (`catalog.cmd_new`, `merge_after.declared_for_new`) совпадают
с требованиями 9, 11, 14, 19 и AC-14/19/24/25 и с долгоживущими тестами
задачи — расхождения нет, эскалации нет.

Ключевые решения:
- **Одна формула потрачено по эпику** — `budget.epic_spent(conn, epic_id)`
  = сумма `spent_with_estimate` задач эпика. Её зовут через атрибут модуля
  (`budget.epic_spent`) `board._epic_item` (вместо своей суммы `spent_usd`),
  проверка конверта в `runner`, `budget.check_epic_alert`, строка `watch`.
  Порог — `budget.EPIC_ALERT_RATIO = 0.8`, признак «порог достигнут» —
  `budget.epic_envelope_warning(spent, envelope)`; `envelope is None` —
  всегда `False` (требование 10).
- **Алерт 80 %** — `budget.check_epic_alert(conn, task_id)`: под
  `BEGIN IMMEDIATE` читает последнюю из записей журнала эпика «конверт
  эпика изменён» / «алерт 80 % конверта эпика»; последняя — алерт → при этом
  конверте алерт уже был (в том числе после `alert-ack`); иначе запись
  журнала эпика (её commit закрывает транзакцию) и `alerts.raise_alert`
  (`kind=threshold`, `target`=id эпика, текст с id эпика). Новой колонки
  схемы для признака не нужно: `epic envelope` пишет запись журнала
  (требование 3) — она и начинает счёт заново (требование 5). Вызов — в
  общем хвосте `runner._charge_attempt` рядом с `check_program_spend`
  (после обеих ветвей) и в `pause._account_partial_cost` после
  `charge_missing_result`.
- **Первый шаг** — в журнале задачи нет записи «agent run started»
  (`store.last_task_step_of`). Проверки конверта и `start_after` —
  в `runner._refuse_before_start` сразу после стоп-крана волны, тем же
  приёмом (`store.journal` с именованным действием + `("exit", текст)`),
  только перед первым шагом; задачу без эпика и без `start_after` они не
  трогают и записей не пишут (требование 20).
- **`start_after`** — колонка `tasks.start_after` (тот же формат, что
  `merge_after`: полные id через «, »). Запись — `merge_after.
  start_after_value(conn, task_id, items, target=…)`: подстановка
  поделённой задачи последним id записи «поделена на: …» по цепочке
  (требование 12), затем `merge_after.check(..., column="start_after")`.
  `check` строит граф цикла из `merge_after ∪ start_after` всех задач;
  у проверяемой задачи — новое значение своего канала плюс текущее
  значение другого канала (требование 14) — так цикл видят все каналы
  `merge_after` (гейт SPEC, PLAN, мандат, `new`), идущие через `check`.
- **Каналы записи `start_after`**: `new … --start-after <ids>` (проверка
  до заведения, как `--after`; запись в колонку с журналом после строки
  задачи) и `epic start-after <задача> <id>… | нет` (значение целиком,
  под lease задачи, запись журнала «было → стало»; «нет» снимает все — это
  и есть канал «снять зависимость» из подсказки требования 16).
  `--start-after` не требует `--epic`: SPEC пишет флаг рядом с `--epic`,
  но не запрещает его без эпика; ограничение было бы лишним отказом.
- **`replace_divided`** обходит и `start_after` тем же правилом (та же
  позиция, `successor_id`, запись журнала зависящей задаче) — `fsm.py` не
  меняется.
- **`auto`**: отказ `run` с действием журнала конверта/`start_after`
  этого вызова — `Stop` без алерта со своей причиной и подсказкой
  «artel.py epic envelope <эпик> N» / «ждёт start_after: <ids>».
- **Показ**: `status` (заголовок группы эпика) и `epic show` печатают
  «потрачено / конверт» из модели и предупреждение при пороге; модель
  несёт `envelope_warning`. `board.waiting_on` — `dependency` также для
  задачи без первого шага с `start_after` не в `done`.
- **`watch`**: на записях «agent cost KNOWN/PARTIAL/ESTIMATED» задачи эпика
  с конвертом — `budget.epic_spent` при обработке; память сессии «до» —
  значение предыдущего события того же эпика; строка — при «до» < порога ≤
  «после», один раз на эпик за сессию; в БД не пишет.
- **`new --epic`** при исчерпанном конверте — задача заводится, печать
  предупреждения (требование 9).

Оценка SPEC ($50) не пересматривается.

## Шаги
1. Схема и модель данных: `tasks.start_after` (DDL + `add_column`);
   `budget.epic_spent`, `EPIC_ALERT_RATIO`, `epic_envelope_warning`,
   `check_epic_alert`; `board` через `budget.epic_spent`, `envelope_warning`,
   `waiting_on='dependency'` по `start_after`.
2. `merge_after`: граф цикла `merge_after ∪ start_after` в `check`,
   подстановка поделённых, `start_after_value`, `rewrite_start_after`,
   `replace_divided` по обеим колонкам.
3. Команды: `epic envelope`, `epic start-after`; `new --start-after`;
   предупреждение `new --epic`; показ `status`/`epic show`.
4. `runner`: проверки конверта и `start_after` перед первым шагом; вызов
   `check_epic_alert` после начисления; `pause --now` — то же.
5. `auto`: остановка на отказе конверта/`start_after` со своей подсказкой.
6. `watch`: строка предупреждения по эпику.
7. Тесты: долгоживущие файлы задачи (6 файлов) + свои на непокрытые
   свойства; карта кодовой базы.

## Влияние на систему
- `merge_after.check` — общий узел всех каналов `merge_after`: граф цикла
  расширен рёбрами `start_after`, то есть проверка стала только строже
  (больше отказов, ни одного нового допуска). Пока колонка `start_after`
  пуста у всех задач, граф совпадает с прежним — поведение существующих
  каналов байт-в-байт прежнее.
- `runner._refuse_before_start` — новые отказы срабатывают только у задачи
  эпика с конвертом или с `start_after` и только до первой записи «agent
  run started»; прочие задачи проходят без новых записей журнала.
- `board._epic_item.spent_usd` теперь включает `spent_estimate_usd` (одна
  формула требования 1) — у задач без оценки значение прежнее.
- Схема: одна новая nullable-колонка `tasks.start_after`, без изменения
  существующих колонок; миграция идемпотентна (`add_column`).
- Гейты, лимиты, потолки задач (`budget_block`, `enforce_budget`) не
  меняются; существующие тесты не правятся.
- Откат — revert merge-коммита задачи; колонка `start_after` остаётся в
  БД пустой и ничего не ломает.

## Риски
- Порядок проверок в `_refuse_before_start`: конверт/`start_after` стоят
  после паузы и стоп-крана волны, до проекта/провайдера/pre-flight —
  задача на паузе отказывает паузой, как раньше.
- Дедуп алерта по журналу эпика: запись журнала эпика с `task_id` = id
  эпика уже практикуется Э1 (`epic new`/`add`).
- `replace_divided` заменяет элемент `start_after` переданным
  `successor_id` (тем же, что и в `merge_after`, — «тем же правилом»
  требования 17); при записи `start_after` на уже поделённую задачу
  подставляется последний id записи «поделена на: …» (требование 12).
