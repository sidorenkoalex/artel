# SPEC: Эпики Э2а — конверт бюджета эпика и зависимость запуска start_after

## Контекст
ADR-0028 (принят 25.10.2026), уровень 2, п. 8–9; шаг Э2а после Э1
(01M5TBBDFS6DWQY6MS263T1KPY — таблица `epics` с `envelope_usd`,
`tasks.epic_id`, команды `epic …`, модель доски `orchestrator/board.py`).
Сейчас бюджет есть только у задачи (`orchestrator/budget.py`, потрачено с
оценкой — `spent_with_estimate`, `budget.py:251`), суммы по линии задач нет.
Проверки перед шагом роли стоят в `orchestrator/runner.py`, функция
`_refuse_before_start` (`:323`): пауза (`:341`) и стоп-кран волны (`:353`),
строго до подготовки рабочего каталога и запуска агента. Зависимость мержа
`merge_after` (`orchestrator/merge_after.py`) разработке не мешает;
зависимости запуска нет. Задача вводит конверт бюджета эпика и зависимость
запуска `start_after`, обе — проверкой в той же точке `runner.py`.

Редакция 3 учитывает решения Оператора на гейте SPEC 26.10: возврат
аналитику по аудиту 1 (пункты 1–9, редакция 2) и по аудиту 2 (пункты 1–7,
сессия при Операторе, права волны G).

## Требования

1. **Потрачено по эпику** — сумма `budget.spent_with_estimate` всех задач
   эпика; считает ОДНА функция `budget.epic_spent(conn, epic_id)`. Её
   используют проверка запуска в `runner.py` (требование 7), алерт 80 %
   (требование 5) и модель `board.py`, из которой показывают `status` и
   `epic show`. Вторая формула «потрачено по эпику» где-либо в коде —
   дефект.
2. **Порог 80 %** — константа `budget.EPIC_ALERT_RATIO = 0.8`;
   предупреждение и алерт 80 % срабатывают при потрачено по эпику ≥
   `EPIC_ALERT_RATIO` × конверт. `orchestrator/config.py` не меняется.
3. **`epic envelope <id> N`** задаёт конверт эпика; число разбирается
   `spend.cli_number`. Годно только значение > 0; неразборное, `0` и
   отрицательное — отказ с причиной, конверт не меняется. Подъём и
   понижение конверта разрешены. Каждое изменение конверта (задание,
   подъём, понижение) пишет запись журнала.
4. **Предупреждение 80 %.** `status` показывает предупреждение по эпику,
   когда потрачено по эпику ≥ порога (требование 2). `watch` печатает
   строку предупреждения по эпику при событии начисления стоимости шага
   задачи эпика, пересекающем порог 80 % (до него потрачено по эпику было
   ниже порога, после — не ниже), — один раз на эпик за сессию `watch`.
   Показ ничего не пишет в БД.
5. **Алерт 80 %.** Алерт Оператору поднимает одна функция
   `budget.check_epic_alert(conn, task_id)`: когда после начисления
   потрачено по эпику задачи ≥ порога (требование 2). Она вызывается после
   КАЖДОГО начисления стоимости шага: в общей точке `runner.py` после
   обеих ветвей начисления (`spend.charge_step` и
   `spend.charge_missing_result`), рядом с `budget.check_program_spend`
   (`runner.py:1843`), и в `pause.py` после `spend.charge_missing_result`
   (`pause.py:154`, `pause --now`). Один алерт на порог на значение
   конверта: последующие начисления при том же конверте второго алерта не
   поднимают, в том числе после `alert-ack` этого алерта. После изменения
   конверта командой `epic envelope` счёт начинается заново: следующее
   начисление, при котором потрачено ≥ порога нового конверта, поднимает
   новый алерт.
6. **Первый шаг роли.** Задача ещё не получала шага роли, если в её
   журнале нет ни одной записи «agent run started». Записи отказов пульта
   до старта агента (пауза, стоп-кран волны, конверт, `start_after`)
   первым шагом не считаются.
7. **Порог 100 %.** Когда потрачено по эпику ≥ конверта, пульт не
   запускает первый шаг роли (требование 6) у задачи эпика, в том числе
   аналитика в `spec_writing`. Проверка стоит в `_refuse_before_start`
   (`runner.py`) рядом с проверками паузы и стоп-крана волны тем же
   приёмом: до подготовки рабочего каталога, pre-flight и запуска агента;
   запись журнала с именованным действием отказа и причиной; отказ `run`
   с текстом причины. Поэтому её не обходят ни `run`, ни `auto <id>`, ни
   повторный запуск после отказа.
8. Задача эпика, у которой шаг роли уже был, получает следующие шаги при
   исчерпанном конверте под своим потолком; потолки задач конверт не
   меняет.
9. `new --epic <id>` при исчерпанном конверте задачу заводит (не
   отказывает) и печатает предупреждение об исчерпанном конверте.
10. Эпик без конверта — без проверки конверта, без предупреждений и
    алертов 80/100 %.
11. **Колонка `tasks.start_after`** — список идентификаторов задач.
    Задаётся `new --epic <id> … --start-after <id>[,<id>…]` и командой
    `epic start-after <задача> <id>…`.
12. **Подстановка поделённой при записи.** Элемент записи `start_after` —
    поделённая задача (`closed_as='divided'`) — заменяется её последней
    частью ДО проверки `merge_after.check`. Последняя часть — последний id
    записи журнала родителя «поделена на: …» (`fsm.py:978`). Цепочка
    делений разрешается до неподелённой задачи: последняя часть, сама
    поделённая, заменяется своей последней частью, и так далее.
13. Запись `start_after` после подстановки (требование 12) проверяется как
    `merge_after` (`merge_after.check`, `merge_after.py:126`): существование
    задачи, тот же проект; элемент — задача в `killed` без деления — отказ
    записи с причиной. Нарушение — отказ записи, значение не меняется.
14. **Цикл — по объединённому графу.** Цикл ищется по графу из рёбер
    `merge_after` ∪ `start_after` всех задач в ОБОИХ каналах записи: при
    записи `start_after` (оба канала требования 11) и при записи
    `merge_after` любым каналом — строка ТЗ «Порядок: после …» при `new`,
    `new --after`, поле SPEC на гейте SPEC, поле PLAN
    (`merge_after.apply_plan`, `merge_after.py:320`), строка мандата ответа
    Оператора (`merge_after.value_refusals`, `:358`;
    `merge_after.mandate_value`, `:382`). Цикл — отказ записи, значение не
    меняется.
15. Задача не получает первый шаг роли (требование 6), пока все задачи её
    `start_after` не в `done`. Отказ — в той же точке `runner.py`, что
    конверт (требование 7), тем же приёмом, с перечнем ожидаемых задач.
16. Задача из `start_after` в состоянии `killed` (не поделённая) — отказ
    первого шага с подсказкой снять зависимость.
17. Задача из `start_after`, поделённая после записи зависимости,
    заменяется в `start_after` зависящих задач её последней частью — в
    `merge_after.replace_divided` (`merge_after.py:299`), расширенной на
    колонку `start_after` тем же правилом (та же позиция, запись журнала
    зависящей задаче); `fsm.py` не меняется.
18. **`auto` на отказе конверта и `start_after`.** `auto <id>`,
    остановленный отказом `run` по конверту (требование 7) или по
    `start_after` (требования 15, 16), останавливается со своей причиной и
    подсказкой: для конверта — «epic envelope <id эпика> N», для
    `start_after` — «ждёт start_after: <ids>». Подсказки «budget … или
    kill» и алерта `attention` в этих случаях нет (`auto.py:966-968`).
19. **Показ.** `status` и `epic show` показывают по эпику «потрачено /
    конверт» и предупреждение 80 %. У задачи, ждущей `start_after`, в
    модели `board.py` признак `waiting_on='dependency'`.
20. Задача без эпика и без `start_after` — поведение `runner.py` не
    меняется.

## Критерии приёмки

AC-1. Эпик с конвертом $10, по задачам эпика потрачено $8,5: `status`
показывает по эпику «потрачено / конверт» и предупреждение 80 %;
повторный вызов `status` не меняет БД (алертов и записей журнала не
добавляет).

AC-2. Эпик с конвертом $10, по задачам эпика потрачено ровно $8,0:
`status` показывает предупреждение 80 %.

AC-3. Эпик с конвертом $10: начисление стоимости шага задачи эпика
веткой `spend.charge_step` в `runner.py`, после которого потрачено по эпику
$8,5, поднимает ровно один алерт 80 % этого эпика; следующее начисление при
том же конверте второго алерта не поднимает — ни при открытом алерте, ни
после его `alert-ack`.

AC-4. Эпик с конвертом $10: начисление веткой `spend.charge_missing_result`
в `runner.py` (шаг без итога стоимости — таймаут или обрыв пайпа), после
которого потрачено по эпику ≥ $8,0, поднимает алерт 80 % этого эпика.

AC-5. Эпик с конвертом $10: частичное начисление `pause --now`
(`pause.py`), после которого потрачено по эпику ≥ $8,0, поднимает алерт
80 % этого эпика.

AC-6. После `alert-ack` алерта из AC-3 конверт изменён `epic envelope`
на $10,5; следующее начисление, после которого потрачено ≥ $8,4,
поднимает новый алерт 80 % этого эпика.

AC-7. Сессия `watch`, эпик с конвертом $10: событие начисления, после
которого потрачено по эпику переходит с $7,5 на $8,5, даёт в выводе строку
предупреждения 80 % по эпику; следующее событие начисления задачи того же
эпика в той же сессии второй строки предупреждения не даёт.

AC-8. Эпик с конвертом $10, потрачено $10,2: `run` задачи эпика без
единой записи «agent run started» в журнале (состояние `spec_writing`)
отказан — агент не запускался, рабочий каталог не готовился, в журнале
задачи запись отказа с причиной (исчерпан конверт эпика).

AC-9. Эпик с конвертом $10, потрачено ровно $10,0: `run` задачи эпика без
записи «agent run started» отказан проверкой конверта.

AC-10. При $10,2 из $10 два `run` подряд одной задачи эпика без записи
«agent run started» отказаны оба: запись отказа первого `run` не делает
второй разрешённым.

AC-11. При $10,2 из $10 `auto <id>` той же задачи не запускает агента,
пишет запись отказа в журнал и останавливается с причиной конверта и
подсказкой «epic envelope <id эпика> N»; подсказки «budget» в выводе нет,
алерт `attention` не открыт.

AC-12. При $10,2 из $10 задача того же эпика с записью «agent run started»
в журнале следующий шаг получает; её потолок (`budget_usd`) не изменён.

AC-13. `epic envelope <id> N` поднимает конверт выше потраченного (пишет
запись журнала) — после этого `run` задачи из AC-8 не отказывается
проверкой конверта. Понижение конверта принимается и пишет запись
журнала. Неразборное `N` (по `spend.cli_number`), `0` и отрицательное `N`
— отказ, конверт прежний.

AC-14. `new --epic <id>` при исчерпанном конверте заводит задачу и
печатает предупреждение об исчерпанном конверте.

AC-15. Эпик без конверта: при любом потраченном `run` новой задачи эпика
проверкой конверта не отказывается, предупреждения 80 % нет, алерт 80 %
при начислении не поднимается.

AC-16. Задача с `start_after` на задачу не в `done`: первый шаг роли отказан
до рабочего каталога и агента, отказ и запись журнала перечисляют
ожидаемые задачи; после перевода зависимости в `done` первый шаг
разрешён.

AC-17. `auto <id>` задачи из AC-16 (зависимость не в `done`)
останавливается с подсказкой «ждёт start_after: <ids>», где перечислены
ожидаемые задачи; подсказки «budget» в выводе нет, алерт `attention` не
открыт.

AC-18. Запись `start_after` (через `new --epic … --start-after` и через
`epic start-after`) отказывает и значение не меняет: на несуществующую
задачу; на задачу другого проекта; на задачу в `killed` без деления (с
причиной); при цикле через `merge_after` (A `start_after` B при B
`merge_after` A).

AC-19. Запись `merge_after` отказывает при цикле через `start_after` (B
`merge_after` A при A `start_after` B) во всех каналах: `new --after`,
строка ТЗ «Порядок: после …» при `new`, поле SPEC на гейте SPEC, поле PLAN
(`merge_after.apply_plan`), строка мандата ответа Оператора
(`merge_after.value_refusals` / `merge_after.mandate_value`); значение
`merge_after` не меняется.

AC-20. Запись `start_after` (через `epic start-after`) на уже поделённую
задачу (`closed_as='divided'`) записывает вместо неё последний id записи
журнала родителя «поделена на: …»; запись не отказана проверкой
`killed`.

AC-21. Цепочка из двух делений: задача P поделена, последняя часть — Q;
Q поделена, последняя часть — R (R не поделена). Запись `start_after` на P
записывает R.

AC-22. Задача из `start_after` в `killed` (не поделённая) к моменту
запуска: первый шаг роли отказан, текст отказа подсказывает снять
зависимость.

AC-23. Задача из `start_after` поделена после записи зависимости
(`closed_as='divided'`): `merge_after.replace_divided` заменяет её
идентификатор в `start_after` зависящей задачи последней частью.

AC-24. Подмена `budget.epic_spent` меняет и потрачено по эпику, которое
показывают `status` и `epic show` (модель `board.py`), и решение проверки
конверта в `runner.py`, и подъём алерта `budget.check_epic_alert`.

AC-25. `epic show` показывает «потрачено / конверт» эпика и
предупреждение 80 % при пороге; в модели `board.py` у задачи, ждущей
`start_after`, `waiting_on` равно `'dependency'`.

AC-26. Задача без эпика и без `start_after`: `run` проходит те же проверки
и пишет те же записи журнала, что до задачи (проверки конверта и
`start_after` не срабатывают и записей не пишут).

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (13 модулей + `tests/`); критериев
приёмки ≥ 10 (26); `budget_usd` ≥ $30 ($50 — рамка ТЗ).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
ТЗ задаёт Э2а одним шагом плана ADR-0028 («Порядок исполнения», строка
Э2а), а ADR — одну точку проверки запуска в `runner.py` для конверта и
`start_after` («Инварианты»: «оба через одну точку `runner.py`»). Обе
части делят одни и те же зоны (`runner.py`, `auto.py`, `schema.py`,
`store.py`, `artel.py`, модуль команд эпика, `board.py`): нарезка по зонам
здесь невозможна — части резали бы одни файлы поперёк и выстроились бы в
очередь зон друг за другом. Технически возможна нарезка по механике
(«конверт» первым, затем «`start_after`» с той же точкой в `runner.py` и
`auto.py`), каждая часть была бы самостоятельно мержима; это удваивает
шаги аналитика/ревью на тех же файлах при рамке ТЗ $50 (оценка ADR —
$35–50). Рост числа критериев с 22 до 26 и зон с 11 до 13 в третьей
редакции — решения Оператора по аудиту 2 (ветви начисления, `pause.py`,
`auto.py`, цепочка делений), не новый объём механики. Решение — за
Оператором.
