# SPEC: Эпики Э2а — конверт бюджета эпика и зависимость запуска start_after

## Контекст
ADR-0028 (принят 25.10.2026), уровень 2, п. 8–9; шаг Э2а после Э1
(01M5TBBDFS6DWQY6MS263T1KPY — таблица `epics` с `envelope_usd`,
`tasks.epic_id`, команды `epic …`, модель доски `orchestrator/board.py`).
Сейчас бюджет есть только у задачи (`orchestrator/budget.py`, потрачено с
оценкой — `spent_with_estimate`, `budget.py:251`), суммы по линии задач нет.
Проверки перед шагом роли стоят в `orchestrator/runner.py`, функция
`_refuse_before_start` (`:323`): пауза (`:341`) и стоп-кран волны (`:353`),
строго до подготовки рабочего каталога и запуска агента. Зависимость мержа
`merge_after` (`orchestrator/merge_after.py`) разработке не мешает;
зависимости запуска нет. Задача вводит конверт бюджета эпика и зависимость
запуска `start_after`, обе — проверкой в той же точке `runner.py`.

Редакция 2 учитывает решения Оператора на гейте SPEC 26.10 (возврат
аналитику по аудиту SPEC, пункты 1–9).

## Требования

1. **Потрачено по эпику** — сумма `budget.spent_with_estimate` всех задач
   эпика. Величину считает ОДНА функция; её используют и проверка запуска
   в `runner.py`, и подъём алерта 80 % (требование 4), и модель
   `board.py`, из которой показывают `status` и `epic show`. Вторая
   формула «потрачено по эпику» где-либо в коде — дефект.
2. **`epic envelope <id> N`** задаёт конверт эпика; число разбирается
   `spend.cli_number`. Годно только значение > 0; неразборное, `0` и
   отрицательное — отказ с причиной, конверт не меняется. Подъём и
   понижение конверта разрешены. Каждое изменение конверта (задание,
   подъём, понижение) пишет запись журнала.
3. **Предупреждение 80 %.** Когда потрачено по эпику ≥ 80 % конверта,
   `status` и `watch` показывают предупреждение по эпику. Показ ничего не
   пишет в БД.
4. **Алерт 80 %.** Алерт Оператору поднимается в точке начисления
   стоимости шага (`runner.py`, после `spend.charge_step`, `:1839`), когда
   после начисления потрачено по эпику задачи ≥ 80 % конверта. Один алерт
   на порог на значение конверта: последующие начисления при том же
   конверте второго алерта не поднимают, в том числе после `alert-ack`
   этого алерта. После изменения конверта командой `epic envelope` счёт
   начинается заново: следующее начисление, при котором потрачено ≥ 80 %
   нового конверта, поднимает новый алерт.
5. **Первый шаг роли.** Задача ещё не получала шага роли, если в её
   журнале нет ни одной записи «agent run started». Записи отказов пульта
   до старта агента (пауза, стоп-кран волны, конверт, `start_after`)
   первым шагом не считаются.
6. **Порог 100 %.** Когда потрачено по эпику ≥ конверта, пульт не
   запускает первый шаг роли (требование 5) у задачи эпика, в том числе
   аналитика в `spec_writing`. Проверка стоит в `_refuse_before_start`
   (`runner.py`) рядом с проверками паузы и стоп-крана волны тем же
   приёмом: до подготовки рабочего каталога, pre-flight и запуска агента;
   запись журнала с именованным действием отказа и причиной; отказ `run`
   с текстом причины. Поэтому её не обходят ни `run`, ни `auto <id>`, ни
   повторный запуск после отказа.
7. Задача эпика, у которой шаг роли уже был, получает следующие шаги при
   исчерпанном конверте под своим потолком; потолки задач конверт не
   меняет.
8. `new --epic <id>` при исчерпанном конверте задачу заводит (не
   отказывает) и печатает предупреждение об исчерпанном конверте.
9. Эпик без конверта — без проверки конверта, без предупреждений и
   алертов 80/100 %.
10. **Колонка `tasks.start_after`** — список идентификаторов задач.
    Задаётся `new --epic <id> … --start-after <id>[,<id>…]` и командой
    `epic start-after <задача> <id>…`.
11. Запись `start_after` проверяется как `merge_after` (`merge_after.check`,
    `merge_after.py:126`): существование задачи, тот же проект. Элемент —
    поделённая задача (`closed_as='divided'`) — при записи заменяется её
    последней частью; элемент — задача в `killed` без деления — отказ
    записи с причиной. Нарушение — отказ записи, значение не меняется.
12. **Цикл — по объединённому графу.** Цикл ищется по графу из рёбер
    `merge_after` ∪ `start_after` всех задач в ОБОИХ каналах записи: при
    записи `start_after` (оба канала требования 10) и при записи
    `merge_after` любым каналом — строка ТЗ «Порядок: после …» при `new`,
    `new --after`, поле SPEC на гейте SPEC, поле PLAN, строка мандата
    ответа Оператора. Цикл — отказ записи, значение не меняется.
13. Задача не получает первый шаг роли (требование 5), пока все задачи её
    `start_after` не в `done`. Отказ — в той же точке `runner.py`, что
    конверт (требование 6), тем же приёмом, с перечнем ожидаемых задач.
14. Задача из `start_after` в состоянии `killed` (не поделённая) — отказ
    первого шага с подсказкой снять зависимость.
15. Задача из `start_after`, поделённая после записи зависимости,
    заменяется в `start_after` зависящих задач её последней частью — в
    `merge_after.replace_divided` (`merge_after.py:299`), расширенной на
    колонку `start_after` тем же правилом (та же позиция, запись журнала
    зависящей задаче); `fsm.py` не меняется.
16. **Показ.** `status` и `epic show` показывают по эпику «потрачено /
    конверт» и предупреждение 80 %. У задачи, ждущей `start_after`, в
    модели `board.py` признак `waiting_on='dependency'`.
17. Задача без эпика и без `start_after` — поведение `runner.py` не
    меняется.

## Критерии приёмки

AC-1. Эпик с конвертом $10, по задачам эпика потрачено $8,5: `status`
показывает по эпику «потрачено / конверт» и предупреждение 80 %;
повторный вызов `status` не меняет БД (алертов и записей журнала не
добавляет).

AC-2. Эпик с конвертом $10, по задачам эпика потрачено ровно $8,0:
`status` показывает предупреждение 80 %.

AC-3. Эпик с конвертом $10: начисление стоимости шага задачи эпика,
после которого потрачено по эпику $8,5, поднимает ровно один алерт 80 %
этого эпика; следующее начисление при том же конверте второго алерта не
поднимает — ни при открытом алерте, ни после его `alert-ack`.

AC-4. После `alert-ack` алерта из AC-3 конверт изменён `epic envelope`
на $10,5; следующее начисление, после которого потрачено ≥ $8,4,
поднимает новый алерт 80 % этого эпика.

AC-5. Тот же эпик ($8,5 из $10): вывод `watch` несёт предупреждение 80 %
по эпику.

AC-6. Эпик с конвертом $10, потрачено $10,2: `run` задачи эпика без
единой записи «agent run started» в журнале (состояние `spec_writing`)
отказан — агент не запускался, рабочий каталог не готовился, в журнале
задачи запись отказа с причиной (исчерпан конверт эпика).

AC-7. Эпик с конвертом $10, потрачено ровно $10,0: `run` задачи эпика без
записи «agent run started» отказан проверкой конверта.

AC-8. При $10,2 из $10 два `run` подряд одной задачи эпика без записи
«agent run started» отказаны оба: запись отказа первого `run` не делает
второй разрешённым.

AC-9. При $10,2 из $10 `auto <id>` той же задачи тоже не запускает агента
и останавливается на том же отказе с записью журнала.

AC-10. При $10,2 из $10 задача того же эпика с записью «agent run started»
в журнале следующий шаг получает; её потолок (`budget_usd`) не изменён.

AC-11. `epic envelope <id> N` поднимает конверт выше потраченного (пишет
запись журнала) — после этого `run` задачи из AC-6 не отказывается
проверкой конверта. Понижение конверта принимается и пишет запись
журнала. Неразборное `N` (по `spend.cli_number`), `0` и отрицательное `N`
— отказ, конверт прежний.

AC-12. `new --epic <id>` при исчерпанном конверте заводит задачу и
печатает предупреждение об исчерпанном конверте.

AC-13. Эпик без конверта: при любом потраченном `run` новой задачи эпика
проверкой конверта не отказывается, предупреждения 80 % нет, алерт 80 %
при начислении не поднимается.

AC-14. Задача с `start_after` на задачу не в `done`: первый шаг роли отказан
до рабочего каталога и агента, отказ и запись журнала перечисляют
ожидаемые задачи; после перевода зависимости в `done` первый шаг
разрешён.

AC-15. Запись `start_after` (через `new --epic … --start-after` и через
`epic start-after`) отказывает и значение не меняет: на несуществующую
задачу; на задачу другого проекта; на задачу в `killed` без деления (с
причиной); при цикле через `merge_after` (A `start_after` B при B
`merge_after` A).

AC-16. Запись `merge_after` отказывает при цикле через `start_after` (B
`merge_after` A при A `start_after` B) — в каналах `new --after`, строки
ТЗ «Порядок: после …» при `new` и поля SPEC на гейте SPEC; значение не
меняется.

AC-17. Запись `start_after` (через `epic start-after`) на уже поделённую
задачу (`closed_as='divided'`) записывает вместо неё её последнюю часть.

AC-18. Задача из `start_after` в `killed` (не поделённая) к моменту
запуска: первый шаг роли отказан, текст отказа подсказывает снять
зависимость.

AC-19. Задача из `start_after` поделена после записи зависимости
(`closed_as='divided'`): `merge_after.replace_divided` заменяет её
идентификатор в `start_after` зависящей задачи последней частью.

AC-20. Потрачено по эпику, которое показывают `status` и `epic show`
(модель `board.py`), и потрачено, по которому отказывает проверка
конверта в `runner.py`, — значение одной функции: подмена этой функции
меняет и показ, и решение проверки.

AC-21. `epic show` показывает «потрачено / конверт» эпика и
предупреждение 80 % при пороге; в модели `board.py` у задачи, ждущей
`start_after`, `waiting_on` равно `'dependency'`.

AC-22. Задача без эпика и без `start_after`: `run` проходит те же проверки
и пишет те же записи журнала, что до задачи (проверки конверта и
`start_after` не срабатывают и записей не пишут).

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (11 модулей + `tests/`); критериев
приёмки ≥ 10 (22); `budget_usd` ≥ $30 ($50 — рамка ТЗ).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
ТЗ задаёт Э2а одним шагом плана ADR-0028 («Порядок исполнения», строка
Э2а), а ADR — одну точку проверки запуска в `runner.py` для конверта и
`start_after` («Инварианты»: «оба через одну точку `runner.py`»). Обе
части делят одни и те же зоны (`runner.py`, `schema.py`, `store.py`,
`artel.py`, модуль команд эпика, `board.py`): нарезка по зонам здесь
невозможна — части резали бы одни файлы поперёк и выстроились бы в
очередь зон друг за другом. Технически возможна нарезка по механике
(«конверт» первым, затем «`start_after`» с той же точкой в `runner.py`),
каждая часть была бы самостоятельно мержима; это удваивает шаги
аналитика/ревью на тех же файлах при рамке ТЗ $50 (оценка ADR — $35–50).
Рост числа критериев с 14 до 22 во второй редакции — уточнения решений
Оператора 26.10 (границы, повторный отказ, алерт, обратный канал цикла),
не новый объём механики. Решение — за Оператором.
