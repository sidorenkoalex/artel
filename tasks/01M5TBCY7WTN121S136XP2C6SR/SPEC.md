# SPEC: Эпики Э2а — конверт бюджета эпика и зависимость запуска start_after

## Контекст
ADR-0028 (принят 25.10.2026), уровень 2, п. 8–9; шаг Э2а после Э1
(01M5TBBDFS6DWQY6MS263T1KPY — таблица `epics` с `envelope_usd`,
`tasks.epic_id`, команды `epic …`, модель доски `orchestrator/board.py`).
Сейчас бюджет есть только у задачи (`orchestrator/budget.py`, потрачено с
оценкой — `spent_with_estimate`, `budget.py:251`), суммы по линии задач нет.
Проверки перед шагом роли стоят в `orchestrator/runner.py` — пауза (`:341`)
и стоп-кран волны (`:352`), строго до подготовки рабочего каталога и
запуска агента. Зависимость мержа `merge_after` (`orchestrator/merge_after.py`)
разработке не мешает; зависимости запуска нет. Задача вводит конверт
бюджета эпика и зависимость запуска `start_after`, обе — проверкой в той же
точке `runner.py`.

## Требования

1. **Потрачено по эпику** — сумма `budget.spent_with_estimate` всех задач
   эпика.
2. **`epic envelope <id> N`** задаёт или поднимает конверт эпика; число
   разбирается `spend.cli_number`, неразборное значение — отказ без
   изменения конверта. Каждое изменение конверта пишет запись журнала.
3. **Порог 80 %.** Когда потрачено по эпику ≥ 80 % конверта:
   предупреждение в `status`, в `watch` и алерт Оператору — один алерт на
   порог (повторные показы `status`/`watch` и последующие шаги второго
   такого алерта для того же эпика не создают).
4. **Порог 100 %.** Когда потрачено по эпику ≥ конверта, пульт не
   запускает первый шаг роли у задачи эпика, у которой в журнале ещё не
   было ни одного шага роли (в том числе аналитика в `spec_writing`).
   Проверка стоит в `runner.py` рядом с проверками паузы и стоп-крана
   волны тем же приёмом: до подготовки рабочего каталога, pre-flight и
   запуска агента; запись журнала с именованным действием отказа и
   причиной; отказ `run` с текстом причины. Поэтому её не обходят ни
   `run`, ни `auto <id>`.
5. Задача эпика, у которой шаг роли уже был, получает следующие шаги при
   исчерпанном конверте под своим потолком; потолки задач конверт не
   меняет.
6. `new --epic <id>` при исчерпанном конверте задачу заводит (не
   отказывает) и печатает предупреждение об исчерпанном конверте.
7. Эпик без конверта — без проверки конверта и без предупреждений 80/100 %.
8. **Колонка `tasks.start_after`** — список идентификаторов задач.
   Задаётся `new --epic <id> … --start-after <id>[,<id>…]` и командой
   `epic start-after <задача> <id>…`.
9. Запись `start_after` проверяется как `merge_after` (`merge_after.check`):
   существование задачи, тот же проект, отсутствие цикла — в том числе
   цикла через `merge_after` (граф из рёбер `start_after` и `merge_after`).
   Нарушение — отказ записи, значение не меняется.
10. Задача не получает первый шаг роли, пока все задачи её `start_after` не
    в `done`. Отказ — в той же точке `runner.py`, что конверт (требование 4),
    тем же приёмом, с перечнем ожидаемых задач.
11. Задача из `start_after` в состоянии `killed` (не поделённая) — отказ
    запуска с подсказкой снять зависимость.
12. Задача из `start_after`, поделённая (`closed_as='divided'`), заменяется
    в `start_after` зависящих задач её последней частью — тем же правилом,
    что `merge_after.replace_divided` (`merge_after.py:299`) для
    `merge_after`.
13. **Показ.** `status` и `epic show` показывают по эпику «потрачено /
    конверт» и предупреждение 80 %. У задачи, ждущей `start_after`, в
    модели `board.py` признак `waiting_on='dependency'`.
14. Задача без эпика и без `start_after` — поведение `runner.py` не
    меняется.

## Критерии приёмки

AC-1. Эпик с конвертом $10, по задачам эпика потрачено $8,5: `status`
показывает по эпику «потрачено / конверт» и предупреждение 80 %; открыт
ровно один алерт Оператору по порогу 80 % этого эпика, повторный вызов
`status` второго алерта не создаёт.

AC-2. Тот же эпик ($8,5 из $10): вывод `watch` несёт предупреждение 80 %
по эпику.

AC-3. Тот же эпик, потрачено $10,2: `run` задачи эпика, у которой ещё не
было ни одного шага роли (состояние `spec_writing`), отказан — агент не
запускался, рабочий каталог не готовился, в журнале задачи запись отказа
с причиной (исчерпан конверт эпика).

AC-4. При тех же $10,2 из $10 `auto <id>` той же задачи тоже не запускает
агента и останавливается на том же отказе с записью журнала.

AC-5. При тех же $10,2 из $10 задача того же эпика, у которой шаг роли уже
был, следующий шаг получает; её потолок (`budget_usd`) не изменён.

AC-6. `epic envelope <id> N` поднимает конверт выше потраченного (пишет
запись журнала) — после этого `run` задачи из AC-3 не отказывается
проверкой конверта. Неразборное `N` (по `spend.cli_number`) — отказ,
конверт прежний.

AC-7. `new --epic <id>` при исчерпанном конверте заводит задачу и печатает
предупреждение об исчерпанном конверте.

AC-8. Эпик без конверта: при любом потраченном `run` новой задачи эпика
проверкой конверта не отказывается, предупреждения 80 % нет.

AC-9. Задача с `start_after` на задачу не в `done`: первый шаг роли отказан
до рабочего каталога и агента, отказ и запись журнала перечисляют
ожидаемые задачи; после перевода зависимости в `done` первый шаг
разрешён.

AC-10. Запись `start_after` (через `new --epic … --start-after` и через
`epic start-after`) отказывает и значение не меняет: на несуществующую
задачу; на задачу другого проекта; при цикле, в том числе через
`merge_after` (A `start_after` B при B `merge_after` A).

AC-11. Задача из `start_after` в `killed` (не поделённая): первый шаг роли
отказан, текст отказа подсказывает снять зависимость.

AC-12. Задача из `start_after` поделена (`closed_as='divided'`): в
`start_after` зависящей задачи её идентификатор заменён последней частью.

AC-13. `epic show` показывает «потрачено / конверт» эпика и
предупреждение 80 % при пороге; в модели `board.py` у задачи, ждущей
`start_after`, `waiting_on` равно `'dependency'`.

AC-14. Задача без эпика и без `start_after`: `run` проходит те же проверки
и пишет те же записи журнала, что до задачи (проверки конверта и
`start_after` не срабатывают и записей не пишут).

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (11 модулей + `tests/`); критериев
приёмки ≥ 10 (14); `budget_usd` ≥ $30 ($50 — рамка ТЗ).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
ТЗ задаёт Э2а одним шагом плана ADR-0028 («Порядок исполнения», строка
Э2а), а ADR — одну точку проверки запуска в `runner.py` для конверта и
`start_after` («Инварианты»: «оба через одну точку `runner.py`»). Обе
части делят одни и те же зоны (`runner.py`, `schema.py`, `store.py`,
`artel.py`, модуль команд эпика, `board.py`): нарезка по зонам здесь
невозможна — части резали бы одни файлы поперёк и выстроились бы в
очередь зон друг за другом. Технически возможна нарезка по механике
(«конверт» первым, затем «`start_after`» с той же точкой в `runner.py`),
каждая часть была бы самостоятельно мержима; это удваивает шаги
аналитика/ревью на тех же файлах при рамке ТЗ $50 (оценка ADR — $35–50).
Решение — за Оператором.
