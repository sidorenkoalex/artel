# SPEC: Трассируемость AC видит долгоживущие файлы test_author в tests/ кодовой ветки (исправление 01M3N3Z1ZHTGMSQZ4SNRYNJ2SJ)

## Контекст
Красная канарейка 20260929T004220Z на вершине main a4cf36bb — первый
прогон схемы ADR-0020 после мержа 01M3N3Z1ZHTGMSQZ4SNRYNJ2SJ. В
канареечной задаче 01M3N9SNEZSNC2G4X2Y2DGEY4R test_author по
`skills/test-authoring.md` записал долгоживущий файл
`tests/test_01m3n9snezsnc2g4x2y2dgey4r_version_json.py`. Выход из
`tests_writing` трижды отказал: «трассируемость AC — AC-n: нет теста и
нет пометки». Переход прошёл только на четвёртой попытке, когда тесты
были продублированы в `acceptance_tests/`. Итог: четыре шага test_author
($18.70), прогон $38.98 при потолке $25. Сквозного теста «test_author
записал файл → чекпоинт → выход из `tests_writing` засчитал покрытие» нет:
`tests/test_long_lived_manifest.py` и `tests/test_long_lived_transitions.py`
проверяют узлы по отдельности.

Что аналитик установил по коду (a4cf36bb):
- Порядок «чекпоинт → проверка перехода» в коде соблюдён.
  `runner._finish_ok` (`orchestrator/runner.py:1477`) вызывает
  `checkpoint.commit_success_checkpoint`, а тот для test_author вызывает
  `_test_author_checkpoint` (`orchestrator/checkpoint.py:581`). Это
  происходит до журнала «agent run finished», то есть до `advance`.
- Трассируемость читает долгоживущие файлы только из ГОЛОВЫ кодовой
  ветки: `_tests_writing_code_diff` (`orchestrator/advance_gates/tests_writing.py:231`)
  берёт `diff_name_status(base, branch)` и `gitcmd.show(branch, path)`,
  а не рабочий каталог. Весь блок вызывается только при
  `gitcmd.branch_exists(t["branch"])` (`orchestrator/fsm_advance.py:352`).
  Иначе в `fsm._tests_writing_ac_state` передаётся пустой
  `long_lived_sources`.
- Отсюда: файл, которого нет в коммите на голове кодовой ветки, для
  трассируемости не существует. Гейт «только добавление» его тоже не
  видит — он читает тот же дифф. Остаётся ровно наблюдаемый отказ «нет
  теста». На пути чекпоинта test_author есть места тихого выхода без
  коммита и без записи в журнал:
  - `_test_author_own_paths` вернул `None` (git не ответил на `status`,
    `diff_base` или `ls_tree_files`, `orchestrator/checkpoint.py:249-266`);
  - `_commit_worktree_change` вернул «не закоммичено»
    (`orchestrator/checkpoint.py:1112-1140`);
  - `branch_exists` ложен в корне пульта.

  При любом из них файл остаётся незакоммиченным в рабочей копии.
- Диагностику канарейки
  (`.artel/canary/20260929T004220Z/01M3N9SNEZSNC2G4X2Y2DGEY4R/`) аналитику
  недоступна (путь вне рабочего каталога шага). Её прочитал Оператор
  (журнал `steps.txt` и логи test_author, возврат со `spec_gate`):
  1. После шага test_author-1 запись журнала «sha зафиксирован» даёт
     `код=a4cf36bb` — голова кодовой ветки равна main. Чекпоинт файл
     test_author НЕ закоммитил, и записи журнала об этом нет (тихий
     выход).
  2. В шаге test_author-2 роль сама выполнила
     `git add tests/test_01m3n9snezsnc2g4x2y2dgey4r_version_json.py` и
     `git commit`. Голова кодовой ветки стала `d0eb9b05` (журнал:
     `код=d0eb9b05…`), файл несёт «Группа: долгоживущий». Трассируемость
     всё равно отказала «AC-1: нет теста».
- Итого дефектов ДВА, оба в зоне задачи:
  - **Дефект А — чекпоинт не коммитит.** Файл test_author, оставшийся
    только в рабочей копии, чекпоинт шага в кодовую ветку не переносит
    и молча выходит (кандидаты мест тихого выхода — перечень выше).
  - **Дефект Б — чтение трассируемости не видит закоммиченный файл.**
    Даже когда файл уже на голове кодовой ветки, `advance` из
    `tests_writing` его не засчитывает. Какое звено цепочки
    `branch_exists` → `_tests_writing_code_diff` (`diff_base`,
    `diff_name_status`, `show`) → `long_lived_sources` →
    `fsm._tests_writing_ac_state` теряет файл, SPEC не утверждает —
    устанавливает разработчик.
  Конкретное место каждого дефекта разработчик называет в PLAN (AC-6).
- Карта кодовой базы на выходе из `tests_writing` (проверено по коду
  a4cf36bb). Проверки свежести `docs/codebase-map.md` среди гейтов
  выхода нет. Гейты — по порядку в `fsm_advance.tests_writing`
  (`orchestrator/fsm_advance.py:338-411`): дифф кодовой ветки,
  трассируемость, посторонние файлы планки, группы, «только
  добавление», сухой сбор, перечень. Свежесть карты сверяет только
  CI-джоб `codebase-map` (`.github/workflows/ci.yml:277-310`). Гейт
  «только добавление» (`_diff_entry_error`,
  `orchestrator/advance_gates/tests_writing.py:268`) отказывает по
  `docs/codebase-map.md`, только если карта попала в дифф кодовой ветки
  (закоммичена). Устаревшая, не закоммиченная карта в дифф не попадает,
  поэтому выход из `tests_writing` из-за неё не отказывает. Правка карты
  test_author откатывается чекпоинтом как путь вне мандата. Правило
  конвенций («регенерируй карту тем же коммитом при правке `*.py` в
  `tests/`») и гейт «только добавление» для test_author противоречат
  друг другу — об этом написал test_author канарейки (см. «Не входит»).

## Требования
1. Долгоживущий файл test_author с префиксом задачи
   (`tests/test_<id в нижнем регистре>_<имя>.py`) засчитывается
   трассируемостью на выходе из `tests_writing` того же шага, если он
   записан в `tests/` рабочей копии задачи во время шага test_author.
   Критерий, покрытый методом `test_ac<n>_…` такого файла, считается
   покрытым. Это верно в обоих случаях: файл остался только в рабочей
   копии (его переносит в кодовую ветку чекпоинт шага — дефект А) и файл
   уже закоммичен в кодовую ветку самой ролью (его видит чтение
   трассируемости — дефект Б). Исправлены оба дефекта.
2. Перечень контрольных сумм (`long_lived.sha256.txt`) для этих файлов
   пишется в том же проходе `advance`. К ним применяются гейт «только
   добавление» и проверки задачи 01M3N0BWYQ9KHVN41Z4G72706R (строка
   «Группа: долгоживущий», признаки, «Ловит мутацию»). Поведение, заданное
   задачей 01M3N3Z1ZHTGMSQZ4SNRYNJ2SJ, не ослабляется.
3. Сквозной тест в `tests/` на песочнице `tests/sandbox.py` покрывает
   зачёт файла с префиксом задачи в обоих случаях требования 1 (только
   рабочая копия; уже закоммичен в кодовую ветку) и сохранение отказа для
   файла без префикса.
4. Причина прежнего отказа названа в SPEC (раздел «Контекст» — два
   дефекта по диагностике канарейки и коду) и в PLAN (конкретное место
   кода каждого из двух дефектов).

## Критерии приёмки
AC-1. Шаг test_author записывает в `tests/` рабочей копии задачи (target
`artel`, состояние `tests_writing`) долгоживущий файл с префиксом задачи.
Методы `test_ac<n>_…` этого файла покрывают все AC SPEC; в
`acceptance_tests/` покрытия этих AC нет. Тогда после чекпоинта шага и
`advance` задача оказывается в `in_dev`, а журнал задачи не несёт записи
«переход отклонён: трассируемость AC». Это выполняется в двух вариантах:
(а) агент оставил файл только в рабочей копии — после чекпоинта файл
закоммичен в кодовую ветку (голова кодовой ветки отлична от базы и
содержит файл); (б) агент сам закоммитил файл в кодовую ветку до конца
шага.

AC-2. В сценарии AC-1 в том же проходе `advance` в ветку документов
записан перечень `long_lived.sha256.txt`. Он содержит путь этого файла и
его sha256 по байтам файла на голове кодовой ветки. В журнале есть запись
«перечень долгоживущих тестов записан».

AC-3. Долгоживущий файл с префиксом задачи, записанный тем же путём, что
в AC-1, но нарушающий гейт «только добавление» или проверки задачи
01M3N0BWYQ9KHVN41Z4G72706R (например, без строки «Группа: долгоживущий»
либо с методом без «Ловит мутацию»), отклоняет выход из `tests_writing`
тем же отказом, что до этой задачи. Задача остаётся в `tests_writing`.
`tests/test_long_lived_manifest.py` и `tests/test_long_lived_transitions.py`
не ослаблены и проходят.

AC-4. В `tests/` есть сквозной тест на песочнице `tests/sandbox.py`.
Подменённый агент шага test_author создаёт долгоживущий файл в `tests/`
рабочей копии задачи и SPEC с AC, покрытыми только этим файлом. Тест
покрывает оба варианта AC-1: (а) файл только в рабочей копии; (б) файл,
уже закоммиченный агентом в кодовую ветку. В каждом варианте после
чекпоинта и `advance` тест проверяет три вещи: задача в `in_dev`, перечень
записан, в журнале нет отказа трассируемости. Метод теста несёт заявку
«Ловит мутацию: трассируемость не читает долгоживущие файлы кодовой ветки
— отказ «нет теста»».

AC-5. Сквозной тест AC-4 содержит второй сценарий: тот же файл без
префикса задачи. После чекпоинта и `advance` задача остаётся в
`tests_writing`, а в журнале есть отказ трассируемости AC либо отказ
гейта «только добавление» — как задано задачей
01M3N3Z1ZHTGMSQZ4SNRYNJ2SJ.

AC-6. PLAN.md называет причину прежнего отказа канарейки 20260929T004220Z
(задача 01M3N9SNEZSNC2G4X2Y2DGEY4R) — ОБА дефекта «Контекста», для
каждого конкретное место кода: дефект А (почему чекпоинт test_author-1
не закоммитил файл и не оставил записи в журнале) и дефект Б (почему
трассируемость test_author-2 не увидела файл на голове кодовой ветки
`d0eb9b05`). Каждая причина подтверждена диагностикой канарейки либо
тем, что соответствующий вариант сквозного теста AC-4 ((а) — для А,
(б) — для Б) краснеет на коде до исправления.
