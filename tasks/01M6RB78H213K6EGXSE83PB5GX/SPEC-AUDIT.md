## ТЗ и SPEC
- Требования ТЗ 1–3 и критерии ТЗ перенесены в SPEC (требования 1–4,
  AC-1…AC-4) без потерь; зоны и «Только чтение» ТЗ — в `zones` и «Не
  входит» SPEC. ANSWER-n нет, решений на гейте SPEC нет.
- Лишнего против ТЗ нет; уточнения SPEC («читается в момент вызова»,

## Факты против кода
Подтвердилось:
- `_bounded` — `orchestrator/cleanup.py:258-262`, ставит `-c
  http.lowSpeedLimit=1 -c http.lowSpeedTime=<config.GH_TIMEOUT_SEC>`;
  `_delete_origin_branch` — `:265-281`; `cleanup_project_remote` — `:284`;
  второй вызов `_delete_origin_branch` из уборки смерженной задачи —
  `:390`; `ls-remote` через `_bounded` — `:357`.
- `_whitelist_refusal` — `orchestrator/gitcmd.py:970`; перед `push`
  разрешена только `-C` (`:976-980`). `push_whitelisted` —
  `orchestrator/targets.py:610` (`merge_gate != "operator"`).
- Песочницы тестов из «Материалов» — `merge_gate: operator`
  (`tests/test_01m568xfym68eyhh0c16y7d7f0_project_kill_cleanup.py:74`,
  `tests/test_01m5fgjw4rbn9c9p48q8mdhjx1_merged_remote_cleanup.py:59`);
  пары `-c` закреплены на `:673-676` и `:373-377` соответственно.
- Артель: `cleanup_project_remote` выходит на `is_artel` до удаления
  (`orchestrator/cleanup.py:302-303`) — AC-4 для артели верен.

Не подтвердилось:
1. **Белый список отказывает удаление ветки задачи и без `-c`.**
   `orchestrator/gitcmd.py:1012-1017`: при флаге `--delete` разрешена
   только ссылка вида `artifacts` (`refs/artifacts/<id>`), иначе отказ
   «--delete <spec> — удаление только refs/artifacts/<id> задачи
   проекта»; форма `:ref` — отказ «удаление формой …» (`:1012-1013`).
   Проверено вызовом `gitcmd._whitelist_refusal` с глобальными опциями
   только `["-C", …]` и обеими формами пуша `_delete_origin_branch`
   (`push origin --delete task/x` и
   `push --force-with-lease=refs/heads/task/x:<sha> origin --delete
   refs/heads/task/x`): обе дают отказ «--delete … — удаление только
   refs/artifacts/<id> задачи проекта». То есть требование 1 (ветка
   удаляется через белый список) и требование 3 (белый список не
   расширяется) совместно невыполнимы при правке только
   `orchestrator/cleanup.py`. Опыт 06.11 просто остановился на первой
   проверке (`-c`, `:976-980`), до проверки `--delete`.
2. **Существующий тест закрепляет обратное AC-1.**
   `tests/test_01m6n7cykdamakenx60cbk7vqx_people_flow.py:878-907`
   (`test_ac9_kill_before_send_keeps_pr_notes_branch_outcome`): проект
   `github` + `target-human`, ветка в голом origin, записи «ветка
   отправлена» нет — ровно сценарий AC-1 — и `assert
   stand.origin_has(branch)` (`:904`) после `kill`; докстринг прямо
   называет это поведением: «белый список отправок проекта людей
   отказывает её удаление, как у `gitlab` + `target-human`» (`:885-886`).
   Тест сейчас зелёный (прогон `-k "ac9 or ac10"` этого файла — 6 passed).
   Выполненный AC-1 сделает его красным; SPEC («Материалы», «Не входит»)
   утверждает, что существующие тесты останутся зелёными, и называет
   лишь два теста `operator` — этот тест пропущен.
3. «Ограничение времени процесса вызова, как у прочих отправок пульта»
   (требование 2) — у `gitcmd.git` срока нет (`subprocess.run` без
   `timeout`, `orchestrator/gitcmd.py:1440`), `in_repo` его не принимает
   (`:1648`). Срок есть у `gitcmd.read(timeout=)` (`:1700-1731`), который
   проходит `_push_plan` (`:1720`), но не подставляет токен хостинга:
   `_hosting_project`/`hosting_token` — только в `git()` (`:1425-1438`).
   Перевод пуша удаления на `read` у проекта с `token_slot` потерял бы
   авторизацию. SPEC этот выбор не называет; при правке только
   `cleanup.py` (gitcmd — только чтение) годного канала «срок + токен +
   белый список» в `gitcmd` нет.

## Пути обхода гейтов
- Буквальное выполнение AC-1 при запрете правки `gitcmd.py` толкает к
  прямому `subprocess.run(["git", …, "push", …])` из `cleanup.py` мимо
  `_push_plan` — обход белого списка целиком (и хука политики
  `target-human`, `gitcmd.py:482`), формально не «расширяющий»
  `_whitelist_refusal`. SPEC не запрещает этот путь явно.
- Тот же итог даёт удаление ветки API хостинга из `cleanup.py`.
