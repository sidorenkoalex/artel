# SPEC: Гейт свежести — документные коммиты main без подтяжки

## Контекст
Гейт свежести (`pull.evaluate`, вызывается из `fsm._pull_main_or_escalate`
на трёх точках сверки: `in_dev -> review`, `acceptance -> merge_gate`,
`merge_gate -> done`) сегодня подтягивает main при ЛЮБОМ числе коммитов
`origin/<main>`, которых нет в ветке — включая чисто документные коммиты
`note` (копилка/бэклог, по одному коммиту на строку) и операторские
документные коммиты (роадмап, ADR). 11.09 три записи копилки подряд
сбили цикл мержа задачи 01M283NC… после шестой подтяжки; 12.09 push
мержа части 2 (01M291EPQ2) был отклонён из-за записи копилки посреди
цикла. Класс пуша ADR-0016 (`scripts/ci_push_class.py`) уже умеет
отличать документный путь от кодового — эта задача переиспользует ту же
классификацию в `pull.evaluate`, чтобы чисто документные коммиты main не
вызывали подтяжку, когда они не пересекаются с файлами самой ветки.

## Требования
1. `pull.evaluate` признаёт ветку `Fresh` не только при `behind == 0`, но
   и когда ВСЕ файлы, изменённые в main от точки расхождения
   (`merge-base(branch, base)`) до `base`, одновременно (а) документные по
   классификации `scripts.ci_push_class.is_doc_path` и (б) не пересекаются
   с файлами диффа самой ветки от той же точки расхождения. Оба условия
   обязательны; любой недокументный либо пересекающийся файл — прежнее
   поведение (подтяжка) байт-в-байт.
2. Пропуск подтяжки по требованию 1 журналируется записью «свежесть: N
   документных коммитов main без подтяжки» с перечнем путей (первые 10) в
   `detail`.
3. Правило действует одинаково на всех трёх точках сверки свежести; на
   `merge_gate -> done` сверка зелёного CI по-прежнему идёт по sha головы
   ветки — новых требований к CI эта задача не добавляет.
4. `scripts/ci_push_class.py` несёт публичное имя `is_doc_path` (старое
   `_is_doc_path` — алиас либо переименовано вместе с его тестами в
   `tests/test_ci_push_class.py`, без ослабления тестов); само
   регулярное выражение `_DOC_PATTERN` не меняется.
5. `tests/test_pull.py` (стенд с bare origin по образцу существующих)
   покрывает сценарии (а)–(г) ниже; существующие тесты `tests/test_pull.py`
   и тестов `merge_gate` — без ослабления.

## Критерии приёмки

AC-1. Когда `behind > 0`, но все файлы диффа main от точки расхождения
(`merge-base(branch, base)`) до `base` документные по
`scripts.ci_push_class.is_doc_path` И не пересекаются с файлами диффа
ветки от той же точки расхождения до `branch` — `pull.evaluate`
возвращает `Fresh` (подтяжка не выполняется).

AC-2. Если хотя бы один файл диффа main из AC-1 не документный либо
пересекается с файлами диффа ветки — `pull.evaluate` ведёт себя прежним
образом (выполняет подтяжку) байт-в-байт.

AC-3. Пропуск подтяжки по AC-1 журналируется (`store.journal`) записью с
действием «свежесть: N документных коммитов main без подтяжки», где N —
число таких файлов, и `detail`, перечисляющим первые 10 путей.

AC-4. Правило из AC-1–AC-2 действует одинаково на всех трёх точках
сверки свежести (`in_dev -> review`, `acceptance -> merge_gate`,
`merge_gate -> done`) за счёт реализации в общей `pull.evaluate`, без
правок `fsm.py`/`fsm_merge_gate.py`.

AC-5. На переходе `merge_gate -> done` сверка зелёного CI по-прежнему
выполняется по sha головы ветки задачи — требования к CI не меняются.

AC-6. `scripts/ci_push_class.py` несёт публичное имя `is_doc_path`;
регулярное выражение `_DOC_PATTERN` не изменено.

AC-7. `tests/test_pull.py`, сценарий (а): main продвинулся только
коммитом `docs/backlog.md`, в ветке задачи нет merge-коммита подтяжки,
`pull.evaluate` возвращает `Fresh`, в журнале есть запись «свежесть: …»;
мутационный тест, эмулирующий «подтяжка всё равно выполняется», —
красный.

AC-8. `tests/test_pull.py`, сценарий (б): main продвинулся коммитом,
затрагивающим `docs/x.md` и `orchestrator/a.py`, — `pull.evaluate`
возвращает `Pulled` (прежняя подтяжка).

AC-9. `tests/test_pull.py`, сценарий (в): main изменил документный файл
(например `docs/backlog.md`), который ветка задачи тоже правит, —
`pull.evaluate` возвращает `Pulled` (подтяжка выполняется, несмотря на
документность).

AC-10. `tests/test_pull.py`, сценарий (г): классификация
`ci_push_class.is_doc_path` относит корневой `README.md` к документным,
а `skills/x.md` — нет.

AC-11. Существующие тесты `tests/test_pull.py` и тесты `merge_gate`
проходят без ослабления — ни один существующий тест не изменён в
сторону смягчения проверки.

## Оценка объёма и деление
Сработавшие сигналы: `budget_usd` = $30 (≥ $30); число критериев приёмки
= 11 (≥ 10).

Обоснование монолита: изменение — одна функция `pull.evaluate` (плюс
экспорт `is_doc_path` из `scripts/ci_push_class.py`, от которого она
зависит), применяемая одновременно на всех трёх точках сверки
(требование 3/AC-4). Разрезать по точкам сверки нельзя — это не три
независимых места, а один общий узел `pull.evaluate`, вызываемый из
`fsm._pull_main_or_escalate` без ветвления по точке вызова; частичное
внедрение оставило бы поведение неконсистентным (часть точек сверки
пропускает документные коммиты, часть — ещё нет), что прямо противоречит
требованию 3 ТЗ. Выделять экспорт `is_doc_path` в отдельную часть тоже
бессмысленно: без него `pull.evaluate` не реализовать, а мерж одного
только переименования не даёт наблюдаемого поведения без потребителя.

## Не входит

  — отдельное решение, не эта задача).

  `orchestrator/fsm_merge_gate.py`.

- Изменение самого регулярного выражения класса документного пути
  (`_DOC_PATTERN` в `scripts/ci_push_class.py`).
