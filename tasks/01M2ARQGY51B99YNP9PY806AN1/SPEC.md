# SPEC: Гонка на FETCH_HEAD — приватная ссылка fetch в трёх местах

## Контекст
Три места оркестратора получают голову удалённой ветки через
`git fetch` в общий `FETCH_HEAD` `config.ROOT` (или клона target'а), а
следующим отдельным вызовом читают этот же `FETCH_HEAD` — между двумя
вызовами параллельный шаг другой задачи в том же репозитории (push/
fetch артефактной ветки) может перезаписать файл. Инцидент 12.09 07:15Z
у канарейки 01M2A22CG2: merge-коммит 9a7f06c4 «подтяжка main» вторым
родителем принёс голову ЧУЖОЙ артефактной ветки вместо `origin/main`,
шаг разработчика ушёл впустую, ветку пришлось восстанавливать
(reset + cherry-pick + честная подтяжка) и принудительно push'ить.

## Требования
1. Один примитив в `orchestrator/gitcmd.py` получает голову удалённой
   ветки БЕЗ обращения к `FETCH_HEAD`: `git fetch <remote>
   +refs/heads/<ref>:refs/artel/fetch/<pid>-<uuid>` в приватную ссылку,
   `git rev-parse --verify` этой ссылки, затем `git update-ref -d` её —
   ссылка своя у каждого процесса, гонки на общем файле нет; объекты
   при этом реально попадают в объектную базу.
2. Все три существующих места одного приёма (`fsm._origin_main_sha`,
   `fsm_merge_gate._origin_main_sha`, `gitcmd.fetch_head_sha`)
   переводятся на этот примитив, сохраняя свои прежние имена и
   сигнатуры.
3. После задачи литерал `FETCH_HEAD` в вызовах git модуля
   `orchestrator/` не встречается — только в докстрингах-пояснениях
   истории.

## Критерии приёмки

AC-1. В `orchestrator/gitcmd.py` есть новый примитив, который получает
голову удалённой ветки через временную приватную ссылку
`refs/artel/fetch/<pid>-<uuid>`: `git fetch <remote>
+refs/heads/<ref>:refs/artel/fetch/<pid>-<uuid>`, затем `git rev-parse
--verify` этой ссылки — без единого обращения к `FETCH_HEAD`.

AC-2. Примитив удаляет приватную ссылку (`git update-ref -d`) и на
успехе, и на отказе `rev-parse` (`try`/`finally`); принимает параметр
`repo` для работы в клоне target'а, по образцу `gitcmd.in_repo`.

AC-3. Примитив возвращает `(sha, "")` при успехе либо `("", причина)`
при отказе — по образцу `gitcmd.fetch_head_sha`.

AC-4. `fsm._origin_main_sha`, `fsm_merge_gate._origin_main_sha` и
`gitcmd.fetch_head_sha` переведены на новый примитив с сохранением
прежних имён и сигнатур (включая параметр `repo` у `fsm.
_origin_main_sha`); потребители `gitcmd.fetch_head_sha` —
`orchestrator/workspace.py` (`ensure`) и `orchestrator/
artifact_branch.py:145` — не изменяются.

AC-5. После задачи литерал `FETCH_HEAD` в вызовах git в
`orchestrator/` не встречается — остаётся только в
докстрингах-пояснениях истории.

AC-6. Новый(е) тест(ы) `tests/test_gitcmd_*.py`: примитив возвращает
голову удалённой ветки, объекты после вызова присутствуют в локальной
объектной базе (`git cat-file -e`), приватная ссылка после вызова
удалена.

AC-7. Новый тест `tests/test_gitcmd_*.py`: между `fetch` и `rev-parse`
подменённый `FETCH_HEAD` (тест пишет в него чужой sha) не влияет на
результат примитива — мутация «примитив на самом деле читает
`FETCH_HEAD`» red.

AC-8. Новый тест `tests/test_gitcmd_*.py`: отказ `fetch` (remote
недоступен) даёт `("", причина)`, приватной ссылки после вызова не
остаётся.

AC-9. `tests/test_pull.py` и `tests/test_fsm_merge_gate_*.py` остаются

## Оценка объёма и деление
Сигнал «число затрагиваемых модулей/файлов» сработал формально: guard
считает пути формата `orchestrator/<имя>.py` по ВСЕМУ тексту SPEC, не
только по фактической зоне — счёт включает файлы из «Не входит» и
«Материалы» (`workspace.py`, `artifact_branch.py`, `pull.py`), которые
эта задача НЕ трогает. Реальная зона правки — три файла
(`orchestrator/gitcmd.py`, `orchestrator/fsm.py`,
`orchestrator/fsm_merge_gate.py`) плюс `tests/` (frontmatter `zones:`).

**Обоснование монолита.** Разрезать нельзя: новый примитив в
`gitcmd.py` и перевод на него всех трёх мест одного и того же приёма —
атомарная смена механики устранения ОДНОЙ гонки (общий `FETCH_HEAD`).
Смержить примитив без перевода хотя бы одного из трёх мест оставило бы
систему в промежуточном нерабочем состоянии: гонка, из-за которой
заведена задача (инцидент 12.09, канарейка 01M2A22CG2), сохранилась бы
на непереведённом месте — часть работы «мержима», но не закрывает ни
один критерий приёмки и не снимает риск инцидента. Три места малы и
однородны (каждое — 1-2 строки вызова), отдельная подзадача на
перевод одного места создала бы больше накладных расходов (сдача,
ревью, зависимость по порядку от первой части — примитив), чем сама
правка.
