# PLAN: Возврат из эскалации test_author: пред-advance не повторяет старую пометку escalate до шага роли

## Подход

Переиспользуем ровно тот приём, которым `orchestrator/pull.py:60-61`
(`PULL_CONFLICT_ROLE_STEP_MARKER`) уже закрыл тот же класс для эскалации
`in_dev` по конфликту подтяжки: отдельная запись журнала с фиксированным
`action` сразу после `state -> escalated`, которую
`auto._role_step_since_state_entry` читает как «запись возврата,
следующая за маркером, — анкер рубежа, а не пропуск».

Ключевые решения:

1. **Место константы — `orchestrator/fsm.py`**
   (`ARTIFACT_ESCALATION_ROLE_STEP_MARKER`, рядом с
   `VERIFYING_STATUS_ACTION`, `fsm.py:37`). Обе точки записи
   (`fsm_advance.tests_writing`, `fsm_advance.spec_writing`) уже
   импортируют `fsm`; читатель `auto.py` тоже (`auto.py:11`). Ни одного
   нового импорта и ни одного обратного цикла. Значение — своё, текст
   `pull.py` не переносится и не переиспользуется (SPEC «Не входит»).
2. **Запись маркера — сразу после `store.set_state(..., "escalated", ...)`**
   в трёх местах `fsm_advance.py`: `tests_writing` (пометка `AC-n:
   escalate`, `fsm_advance.py:298`) и обе ветки `spec_writing` по батчу
   `QUESTIONS.md` — ветка-источник (`fsm_advance.py:91`) и путь через диск
   (`fsm_advance.py:114`). `detail` маркера — тот же текст, что у самой
   эскалации (как в `pull.py:271`). Хук фиксации sha внутри `set_state`
   пишет свою запись между `state -> escalated` и маркером — на всех
   переходах без исключения, планка задачи это учитывает
   (`_sandbox.meaningful_rows`), чтение анкера её не разбирает.
3. **Чтение — в `auto._role_step_since_state_entry`**: единственная
   правка — ветка `if action == pull.PULL_CONFLICT_ROLE_STEP_MARKER`
   становится `if action in _ROLE_STEP_REQUIRED_MARKERS` (кортеж из двух
   маркеров, новая константа модуля). Вся механика гашения (расход первой
   записью `state -> {state}`, сброс любым другим `state -> X`, `X` не
   `escalated`) — уже существующая, для нового маркера ничего своего не
   требуется (требование 4 закрывается тем же циклом).
4. **Стоп-кран «дважды подряд без шага роли»** (`auto._pre_advance_step`,
   `_pull_conflict_marker_streak`) на новый маркер НЕ распространяется:
   повторная эскалация после шага роли по оставленной пометке легитимна
   (требование 5, AC-5), и после каждого возврата рубеж (а) снова даёт
   роли шаг — цикл «эскалация → ответ → шаг роли → эскалация» держится
   на решениях Оператора, не крутится сам.

Расхождения с оценкой SPEC нет: зона правки та же (три модуля + тесты),
`budget_usd` не переоценивается.

## Шаги

1. `orchestrator/fsm.py`: константа `ARTIFACT_ESCALATION_ROLE_STEP_MARKER`
   с комментарием «почему» (тот же класс, что маркер конфликта подтяжки;
   кто пишет, кто читает).
2. `orchestrator/fsm_advance.py`: запись маркера после `set_state(...,
   "escalated")` в `tests_writing` и в обеих ветках батча `spec_writing`.
3. `orchestrator/auto.py`: кортеж `_ROLE_STEP_REQUIRED_MARKERS`, чтение
   его в `_role_step_since_state_entry`; докстринг функции дополнен новым
   основанием.
4. Юнит-тесты `tests/test_artifact_escalation_marker.py`:
   - анкер: запись возврата после маркера держит рубеж без шага роли и
     отпускает после `agent run finished` роли (для `tests_writing`/
     `test_author` и `spec_writing`/`analyst`, включая первый вход в
     `spec_writing` без записи `state -> spec_writing`);
   - гашение: расход первой записью возврата, сброс другим переходом
     (`state -> in_dev` между эскалациями), запись возврата без маркера
     по-прежнему пропускается (существующее поведение не тронуто);
   - запись маркера точками эскалации: лёгкая песочница поверх
     `tests/test_auto_cycle.py::AutoCycleTest` — `fsm.cmd_advance` из
     `tests_writing` с пометкой `escalate` и из `spec_writing` с
     `QUESTIONS.md` оставляет маркер сразу за `state -> escalated`
     (за вычетом записи фиксации sha); эскалация другого класса
     (`_review_escalate`) маркера не ставит.
   Каждый тест — с заявкой «Ловит мутацию».
5. Регенерация `docs/codebase-map.md` тем же коммитом
   (`python3 scripts/codebase_map.py`); прогон планки задачи,
   `tests/test_auto_escalated_return_rework_gate.py`,
   `tests/test_auto_cycle.py`, `tests/test_pull.py`,
   `tests/test_fsm_branch_correct_status_reads.py`,
   `tests/test_acceptance_tests_flow.py`, `tests/test_analyst_role.py`,
   нового модуля; `scripts/guard.py`.

## Влияние на систему

- **Гейты/инварианты.** Новых состояний FSM и новых переходов нет
  (инвариант 36): добавляется только запись журнала и одно условие в
  чтении анкера. Ни один существующий рубеж не ослабляется: пред-advance
  начинает ДЕРЖАТЬСЯ там, где раньше пропускал (строже, не мягче).
  `_pre_advance_step`, `_review_escalate`, `_in_dev_plan_escalate`,
  обработчик `review` — не тронуты.
- **Цена.** После возврата из эскалации по содержимому артефакта цикл
  `auto` всегда тратит один шаг роли до следующего advance — ровно то,
  что требует SPEC (ANSWER должен дойти до роли). Для возврата из
  эскалаций других классов поведение прежнее.
- **Существующие тесты.** `tests/test_auto_escalated_return_rework_gate.py`
  не меняется (AC-7): записи возврата без предшествующего маркера
  обрабатываются как раньше. Тесты `tests_writing`/`spec_writing`
  (`test_acceptance_tests_flow.py`, `test_analyst_role.py`,
  `test_fsm_branch_correct_status_reads.py`) читают состояние и вывод,
  не число записей журнала после эскалации — дополнительная запись их не
  красит (проверяется прогоном, шаг 5).
- **Наблюдаемость.** `cmd_log`/`watch`/бриф показывают маркер как обычную
  запись журнала с actor `fsm`; `brief.advance_refusal_history` фильтрует
  по префиксу «переход отклонён» — маркер в блок «почини это» не попадает.
- **Откат.** Revert одного merge-коммита: маркер перестаёт писаться и
  читаться, старые записи в журналах существующих задач становятся
  инертными строками (читатель их не знает), FSM не затрагивается.

## Риски

- Задача, эскалированная по содержимому артефакта ДО этого изменения и
  возвращаемая после него, маркера в журнале не несёт — для неё повтор
  инцидента остаётся возможным один раз (обход прежний: `run` вместо
  `auto`). Ретроактивно чинить журнал не входит в задачу.
- Заглушка `_sandbox.escalation_marker_index` планки ждёт маркер
  непосредственно за `state -> escalated` за вычетом фиксации sha и
  записей `lease` — любая будущая запись между `set_state` и маркером
  (например, новый хук `set_state`) покрасит AC-1/AC-2; это дефект
  порядка, а не планки.

## Предложения системе

- `orchestrator/pull.py:56-59`: комментарий у `PULL_CONFLICT_ROLE_STEP_MARKER`
  утверждает, что значение «скопировано в `orchestrator/brief.py`», но в
  `brief.py` такой копии нет (там только
  `_ROLE_NOT_FINISHED_REFUSAL_ACTIONS`). Комментарий-пересказ разошёлся
  с кодом; класс «комментарий ссылается на несуществующее место» — вне
  зоны этой задачи, не правил.
