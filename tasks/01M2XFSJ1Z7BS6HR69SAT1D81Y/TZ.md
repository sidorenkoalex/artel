# ТЗ: Возврат из эскалации test_author: пред-advance не повторяет старую пометку escalate до шага роли

Источник: копилка docs/backlog.md, строка П1 13.09 «После answer +
approve эскалации test_author цикл auto снова увёл задачу в escalated
по той же старой пометке». Решение Оператора 19.09: заводить сейчас, до
волны 5.

Инцидент 13.09, задача 01M2CYQR03 (журнал пульта):
- 09:32:53 — шаг test_author закончен, планка несёт «# AC-3: escalate»,
  `state -> escalated` («критерий неисполним тестом — AC-3»).
- 09:38:22 — Оператор: ANSWER-1 создан, approve → `state ->
  tests_writing` («эскалация разрешена, продолжаем»).
- 09:38:23 — auto старт; в ту же секунду, без запуска роли и без
  стоимости: `state -> escalated` с тем же текстом про AC-3, запись
  «шаг test_author не нужен: переход выполнен по готовым артефактам
  (tests_writing -> escalated)», auto остановлен.
- 09:39:14 и 09:39:21 — approve отклонён: «не хватает ANSWER-2»
  (повторная эскалация подняла answer_baseline). Оператор написал
  ANSWER-2 (дубль ANSWER-1), approve, затем запустил роль через `run`
  вместо auto. Потеря: две ручные команды, дубль ответа, ложная запись
  эскалации в журнале; обход держится только на памяти Оператора.

Причина (по коду):
- `orchestrator/auto.py::_pre_advance_step` зовёт `fsm.cmd_advance` ДО
  шага роли; обработчик `orchestrator/fsm_advance.py::tests_writing`
  перечитывает пометки планки из артефактной ветки и на любой пометке
  escalate эскалирует заново — он не знает, что на эту пометку уже дан
  ответ.
- Гейт переделки `auto._rework_gate_blocks` не держит пред-advance:
  запись возврата «эскалация разрешена, продолжаем» входит в
  `_ESCALATED_RETURN_DETAILS` и при поиске анкера пропускается, анкером
  остаётся исходный `state -> tests_writing` (09:14), после которого шаг
  test_author уже был (09:32) — «роль отработала», advance не
  задерживается. Для эскалации по конфликту подтяжки тот же класс уже
  решён маркером `pull.PULL_CONFLICT_ROLE_STEP_MARKER`: запись возврата,
  которой предшествовал маркер, сама становится анкером.
- `orchestrator/fsm.py::_approve_escalated` сбрасывает
  `answer_baseline` в None и переводит в `escalated_from`; больше ничего
  о природе эскалации не остаётся.

Требуется:
1. Эскалация, поднятая содержимым артефакта роли (пометка `AC-n:
   escalate` в планке — `fsm_advance.tests_writing`), помечает себя в
   журнале маркером «ответ Оператора должен дойти до роли» тем же
   приёмом, что `PULL_CONFLICT_ROLE_STEP_MARKER`: запись сразу после
   `state -> escalated`, до возврата.
2. `auto._role_step_since_state_entry`: запись возврата из escalated,
   которой предшествовал этот маркер, становится анкером — гейт
   переделки держит пред-advance до `agent run finished` роли состояния
   (test_author) после возврата. Маркер гасится первым же следующим
   переходом состояния, как и маркер конфликта подтяжки.
3. После шага роли обработчик `tests_writing` работает как сегодня:
   пометка снята — переход в in_dev; пометка оставлена или поставлена
   новая — новая эскалация с новым `answer_baseline` (это легитимно).
4. Тот же класс в spec_writing (QUESTIONS.md — `fsm_advance.
   spec_writing`) и review (`REVIEW.md status: escalate`): аналитик
   сверяет по коду, повторяет ли пред-advance после возврата старую
   эскалацию; если да — те же требования 1-2 для этого состояния в
   рамках этой задачи, если нет — фиксирует в SPEC, почему.
5. Тесты (tests/): сценарий инцидента — escalate test_author → answer →
   approve → auto: роль запускается с ANSWER в брифе, повторной
   эскалации за 0 секунд нет, approve после возврата не требует
   ANSWER-2; после шага роли без пометки — переход в in_dev; с новой
   пометкой — новая эскалация. Существующий
   `tests/test_auto_escalated_return_rework_gate.py` остаётся зелёным.

Зоны: orchestrator/auto.py, orchestrator/fsm_advance.py,
orchestrator/fsm.py, tests/.

Только чтение (не менять): orchestrator/pull.py (образец маркера —
переиспользовать приём, константу не переносить), orchestrator/answer.py
(механика ANSWER не меняется).

Не входит: правка пометок планки пультом (артефакт роли пишет только
роль); канал Оператор → роль без эскалации (отдельная строка копилки
12.09); изменение брифа роли.
