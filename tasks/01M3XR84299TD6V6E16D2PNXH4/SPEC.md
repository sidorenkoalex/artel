# SPEC: Правило о тестовых методах в tests/ и счёт его срабатываний

## Контекст
Гейт неослабления тестов (инвариант 38, с 27.09) отказывает переходу
`in_dev → verifying`, если из `tests/` пропал тестовый метод, а мандат на
это команда `answer` принимает только в `escalated`. Дважды
(01M3SK48D7RDQPSEN78894GDA5, 01M3V4ZPB6HFDJ36MTDAQG5VNT) разработчик
переименовывал тесты молча, и мандат приходил обходом «разовое
исключение»; во втором случае пропала проверка, остававшаяся верной.
Решение Оператора 02.10.2026: сначала правило в скиле разработчика и
наблюдение по числам; задача на код гейта — по триггеру №31, если
правило не сработает.

## Требования
1. В раздел «Тесты» скила `skills/coding-standards.md` добавляется пункт:
   - существующий тестовый метод в `tests/` не удаляется и не
     переименовывается молча; при переписывании теста под новую
     механику имя метода сохраняется, проверки, которые остаются
     верными, не выбрасываются;
   - если метод действительно нужно удалить или переименовать —
     эскалация ДО сдачи шага (по `skills/escalation-rules.md`) с
     перечнем `tests/<файл>.py::<Класс>::<метод>`, причиной и заменой;
     мандат приходит штатным ответом на эскалацию.
   Путь защищённый: правка поставляется приложением PLAN (готовый
   текст), применяет его пульт на мерже; в кодовой ветке файл скила не
   меняется.
2. Новая программа `scripts/test_rule_stats.py` — подсчёт только на
   чтение: БД пульта `.artel/state.db` (таблица `steps`) и мержи
   `origin/main`; аргумент `--since YYYY-MM-DD`. Основа — черновик
   Оператора из ТЗ (см. «Материалы»), приведённый к
   `skills/coding-standards.md`. Печатает четыре группы задач за окно:
   1. разработчик эскалировал с перечнем тестовых методов
      (`tests/<файл>.py::<Класс>::<метод>`) до отказа гейта неослабления
      (или без отказа вовсе);
   2. фон — смерженные в `origin/main` задачи, мерж которых меняет
      существующие файлы `tests/` (изменённые, не новые), без отказа
      гейта и не попавшие в группы 1 и 3;
   3. задачи с отказом гейта неослабления без предварительного вопроса
      (включая задачи, где эскалация с перечнем была ПОСЛЕ отказа);
   4. задачи с записью журнала «Разовое исключение: запись ANSWER в
      in_dev»;
   и строку о достижении порога триггера №31, если группа 3 не пуста.
3. Программа ничего не пишет в БД: открывает её только на чтение.
4. Тест `tests/test_test_rule_stats.py` проверяет программу на
   синтетической БД и синтетическом git-репозитории — без настоящего
   `.artel/state.db` и без сети.

## Критерии приёмки
AC-1. Приложение PLAN к `skills/coding-standards.md` добавляет в раздел
«Тесты» пункт: существующий тестовый метод в `tests/` не удаляется и не
переименовывается молча; при переписывании теста под новую механику имя
метода сохраняется; проверки, которые остаются верными, не
выбрасываются.

AC-2. Тот же пункт требует при действительной необходимости удалить или
переименовать метод эскалировать ДО сдачи шага с перечнем
`tests/<файл>.py::<Класс>::<метод>`, причиной и заменой, и называет
штатный ответ на эскалацию каналом мандата.

AC-3. `scripts/test_rule_stats.py` принимает аргумент `--since
YYYY-MM-DD` и считает события журнала `steps` и мержи `origin/main` не
раньше этой даты.

AC-4. Задача, где разработчик эскалировал с перечнем тестовых методов
вида `tests/<файл>.py::<Класс>::<метод>` и отказа гейта неослабления до
этой эскалации не было, попадает в группу 1.

AC-5. Задача, смерженная в `origin/main`, мерж которой меняет
существующий файл `tests/`, без отказа гейта неослабления и без
эскалации группы 1, попадает в группу 2 (фон); мерж, только
добавляющий новые файлы `tests/`, в группу 2 не попадает.

AC-6. Задача с отказом гейта неослабления без предварительной эскалации
с перечнем попадает в группу 3; задача, где такая эскалация случилась
ПОСЛЕ отказа гейта, относится к группе 3, а не к группе 1.

AC-7. Задача с записью журнала «Разовое исключение: запись ANSWER в
in_dev» попадает в группу 4.

AC-8. При непустой группе 3 программа печатает строку о достижении
порога триггера №31; при пустой группе 3 этой строки нет.

AC-9. Прогон программы не меняет БД пульта: она открыта только на
чтение (содержимое синтетической БД после прогона совпадает с исходным,
запись через соединение программы невозможна).

  пульт.
