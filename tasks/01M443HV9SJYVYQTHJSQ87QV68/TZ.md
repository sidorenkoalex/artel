# ТЗ: CI ветки задачи проверяет код вместе с приложениями PLAN

Источник: бэклог — строка «CI ветки не видит приложений PLAN: задача, чьи
тесты зависят от правки защищённого файла, не проходит verifying»
(приоритет 2, поднят Оператором 04.10.2026 по прецеденту этапа 2
ADR-0021); копилка 04.10 «Тупик порядка ворот» (приоритет 1). Решение
Оператора 04.10 «заводи».

Факты (пин 16f663b4, сверка 04.10):
- Порядок ворот: `verifying` ждёт зелёного CI головы ветки задачи
  (`orchestrator/fsm_advance.py::verifying`), а приложения PLAN к
  защищённым путям накладывает только ворота мержа
  (`orchestrator/fsm_merge_gate.py::_apply_plan_appendices`, `git apply`
  в рабочей копии мержа, затем полный прогон `tests/`).
- CI ветки (`.github/workflows/ci.yml`) гоняет `tests/` и отдельно
  `tests/test_invariants.py` на дереве ветки без приложений. Если код
  задачи требует совместимой правки защищённого теста, CI ветки красный
  по построению, задача стоит в `verifying` до потолка и эскалирует.
- Прецедент 04.10 (01M42PENCS26D0656X8FR7DFA7): 6 тестов
  `tests/test_invariants.py` падали на ветке и проходили с приложением 1
  (71 passed). Выход — Оператор вручную внёс приложение в `main`
  (1dc7c20f) и через `reject` велел разработчику убрать его из PLAN,
  потому что ворота мержа накладывают приложение обычным `git apply` и
  на уже наложенной правке отказывают. Цена — коммит Оператора, лишний
  шаг developer и прогон CI.
- Разбор приложений PLAN: `guard.PlanAppendix` (`scripts/guard.py`,
  только чтение), применимость на выходе `in_dev` —
  `orchestrator/advance_gates/plan_appendix.py`.

Требуется:
1. Зелёный CI ветки означает зелёные тесты на том содержимом, которое
   окажется в `main` после мержа: код ветки плюс приложения её PLAN.
   Способ — в SPEC (например, шаг CI накладывает приложения PLAN задачи
   из копии `tasks/<id>/PLAN.md` в ветке перед тестами отдельным
   сценарием; либо пульт сам сверяет тесты с приложениями до
   `verifying`). Ветка без приложений — поведение CI не меняется.
2. Наложение в CI не становится обходом защиты: приложения по-прежнему
   попадают в `main` только через ворота мержа; CI ничего не коммитит и
   не пушит; неприменимое приложение — красный CI с именем приложения.
3. Ворота мержа считают приложение, уже наложенное в подтянутом `main`
   (`git apply --reverse --check` проходит), применённым: не
   отказывают и не возвращают задачу, а пишут в журнал, что приложение
   уже в `main`. Частично наложенное — прежний отказ.
4. Изменение `.github/workflows/ci.yml` — приложением к PLAN (защищённый
   путь); сторож, проверяющий шаг CI с приложениями, — в том же
   приложении или в `tests/` так, чтобы CI ветки этой задачи был зелёным
   до мержа (урок части «CI быстрее»: сторож свойства, которое приносит
   приложение, не может стоять на ветке без него).
5. Тесты в `tests/` с заявками «Ловит мутацию» на пп. 1–3: ветка с
   приложением, без которого защищённый тест красный, — CI-сценарий
   зелёный; неприменимое приложение — красный с именем; приложение,
   уже наложенное в `main`, — ворота мержа проходят и журналируют;
   частично наложенное — отказ. Существующие тесты не ослабляются.

Зоны: orchestrator/, scripts/plan_appendix_ci.py, tests/,
docs/codebase-map.md.

Приложением: .github/workflows/ci.yml, docs/operator-session.md.

Только чтение (не менять): scripts/guard.py, docs/adr/, docs/roadmap.md,
docs/backlog.md, templates/, skills/, CLAUDE.md, models.yaml, roles.yaml,
conftest.py, tests/test_invariants.py, docs/invariants.md.

Не входит: прогон CI на машине пульта вместо GitHub; изменение формата
приложений PLAN; приложения к путям вне защищённого списка.
