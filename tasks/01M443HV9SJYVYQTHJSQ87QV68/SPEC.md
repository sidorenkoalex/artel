# SPEC: CI ветки задачи проверяет код вместе с приложениями PLAN

## Контекст
`verifying` ждёт зелёного CI головы ветки задачи
(`orchestrator/fsm_advance.py::verifying`), а приложения PLAN к
защищённым путям накладывают только ворота мержа
(`orchestrator/fsm_merge_gate.py::_apply_plan_appendices`: `git apply` в
рабочей копии мержа, затем полный прогон `tests/`). CI ветки гоняет
`tests/` (job `python`) и `tests/test_invariants.py` (job `python-min`) на
дереве ветки без приложений. Если код задачи требует совместимой правки
защищённого теста, CI ветки красный по построению: задача стоит в
`verifying` до потолка и эскалирует. Прецедент 04.10
(01M42PENCS26D0656X8FR7DFA7): 6 тестов `tests/test_invariants.py` падали
на ветке и проходили с приложением 1; выход — ручной коммит Оператора в
`main` и `reject`, потому что ворота мержа на уже наложенной правке
отказывают.

Кодовая ветка задачи не несёт `tasks/<id>/PLAN.md` (ADR-0021: документы
живут в ссылке документов `refs/artifacts/<id>`, которую пульт отправляет
в `origin`). Источник PLAN для шага CI — эта ссылка в `origin`, не копия
в ветке. Разбор приложений — `guard.PlanAppendix` (`scripts/guard.py`,
только чтение).

## Требования
1. В прогоне CI по пушу ветки задачи (`task/**`) перед тестами jobs
   `python` и `python-min` отдельный сценарий `scripts/plan_appendix_ci.py`
   накладывает на рабочее дерево раннера все приложения PLAN этой задачи
   (разбор `guard.PlanAppendix`, PLAN — из ссылки документов задачи в
   `origin`); тесты идут на дереве «код ветки плюс приложения её PLAN».
2. Ветка задачи без приложений (нет ссылки документов, нет PLAN.md в ней
   или в PLAN нет приложений) — сценарий ничего не меняет, тесты идут на
   дереве ветки как прежде. Прогоны CI на `main` и прочих не-`task/**`
   ветках не меняются.
3. Приложение, которое не накладывается на дерево ветки, — сценарий
   завершается ненулевым кодом, CI красный, в выводе названо имя
   (заголовок/номер) неприменимого приложения.
4. Сценарий и шаг CI ничего не коммитят и не пушат: правка остаётся только
   в рабочем дереве раннера; в `main` приложения по-прежнему попадают
   только через ворота мержа.
5. Ворота мержа считают приложение, уже наложенное в подтянутом `main`
   (`git apply --reverse --check` проходит), применённым: не отказывают,
   не возвращают задачу и пишут в журнал задачи строку, что приложение
   (с его именем) уже в `main`. Остальные приложения той же задачи
   обрабатываются прежним порядком.
6. Частично наложенное в `main` приложение (не проходит ни прямой
   `git apply --check`, ни `--reverse --check`) — прежний отказ ворот
   мержа с прежним исходом.
7. Правка `.github/workflows/ci.yml` (шаг сценария в jobs `python` и
   `python-min`) и описание нового поведения в `docs/operator-session.md`
   — приложениями к PLAN. Сторож того, что шаг CI с приложениями есть в
   `ci.yml`, — внутри того же приложения либо в `tests/` в форме, зелёной
   на ветке этой задачи без её приложений.
8. Тесты в `tests/` с заявками «Ловит мутацию» на требования 1, 3, 5, 6.
   Существующие тесты не ослабляются.

## Критерии приёмки
AC-1. Сценарий `scripts/plan_appendix_ci.py` на дереве, где защищённый
тест красный без приложения PLAN, накладывает это приложение и завершается
кодом 0; тот же тест на получившемся дереве зелёный. Тест в `tests/` с
заявкой «Ловит мутацию» (сценарий, не накладывающий приложения, роняет
тест).

AC-2. Сценарий при PLAN без приложений, при отсутствии PLAN.md и при
отсутствии ссылки документов задачи завершается кодом 0 и не меняет
рабочее дерево (`git status --porcelain` пуст).

AC-3. Сценарий при неприменимом приложении завершается ненулевым кодом, и
его вывод содержит имя этого приложения. Тест в `tests/` с заявкой «Ловит
мутацию» (сценарий, проглатывающий отказ `git apply`, роняет тест).

AC-4. После прогона сценария в репозитории не появилось новых коммитов и
не изменились ссылки (`git for-each-ref` до и после совпадают, кроме
ссылки, подтянутой самим сценарием для чтения PLAN, если она заведена в
отдельном пространстве), и сценарий не вызывает `git commit`/`git push`.

AC-5. Ворота мержа на задаче, чьё приложение уже наложено в подтянутом
`main`, не отказывают и не возвращают задачу, а журнал задачи содержит
запись, что приложение с этим именем уже в `main`. Тест в `tests/` с
заявкой «Ловит мутацию» (ворота, применяющие только прямой `git apply`,
отказывают — тест красный).

AC-6. Ворота мержа на задаче, чьё приложение наложено в `main` частично,
отказывают с прежним исходом (тот же возврат, что для неприменимого
приложения сегодня). Тест в `tests/` с заявкой «Ловит мутацию» (ворота,
считающие применённым любое приложение с непрошедшим прямым `--check`,
роняют тест).

AC-7. В PLAN задачи есть приложение к `.github/workflows/ci.yml`,
добавляющее шаг `scripts/plan_appendix_ci.py` перед тестами в jobs
`python` и `python-min` только для пушей `task/**`, и приложение к
`docs/operator-session.md`, описывающее наложение приложений в CI ветки и
приём уже наложенного в `main` приложения воротами мержа; оба проходят
`git apply --check` на чистом дереве ветки.

AC-8. Сторож наличия шага CI с приложениями в `ci.yml` присутствует: либо
внутри приложения AC-7, либо в `tests/` и зелёный на дереве ветки задачи
без её приложений.

элемента, критериев — 8, прогноз диффа мал.

1–4, 7). Атомарной смены механики между ними нет. Довод за монолит —
стоимостной: нижняя планка бюджета — $25 на задачу, две части дают ≥ $50
против рамки ТЗ $40, а приложение `docs/operator-session.md` описывает
обе части сразу. Решение — за Оператором на гейте SPEC.

## Не входит
- Прогон CI на машине пульта вместо GitHub.
- Изменение формата приложений PLAN; приложения к путям вне защищённого
  списка.
- Изменение гейта применимости приложений на выходе `in_dev`
  (`orchestrator/advance_gates/plan_appendix.py`) — ТЗ требует приёма уже
  наложенного приложения только воротами мержа.
- Правка путей «только чтение» ТЗ: `scripts/guard.py`, `docs/adr/`,
  `docs/roadmap.md`, `docs/backlog.md`, `templates/`, `skills/`,
  `CLAUDE.md`, `models.yaml`, `roles.yaml`, `conftest.py`,
  `tests/test_invariants.py`, `docs/invariants.md`.
- `.github/workflows/ci.yml`, `docs/operator-session.md` — только
  приложением к PLAN, не правкой в ветке.
- Зелёный CI ветки, полный набор `tests/`, неизменность защищённых путей,
  непревышение бюджета — их держит пульт.
