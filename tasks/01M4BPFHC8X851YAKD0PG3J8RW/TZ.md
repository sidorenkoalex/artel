# ТЗ: Сессия при Операторе в чате Codex — запуск и дозор задач штатными командами

Приоритет: первый (решение Оператора 07.10.2026).

Источник: решение Оператора 07.10.2026 — вести задачи из чата Codex
наравне с Claude Code: подписка Claude заканчивается, сессия
при Операторе временно переходит в Codex. Пункт operator-session.md:437 запретом не был:
на 02.10 пульт под Codex ещё дорабатывался, теперь пробуем снова.
Способ доставки событий — штатный Stop-хук Codex (решение Оператора
07.10); копилка 30.09 (`docs/backlog.md`, строки
«Нет штатной связки watch с продолжением завершённого хода Codex»,
«Дозор задач в чате Codex не доставил уведомления об эскалациях
автоматически», «Анализ зависимости от хуков: … .codex/hooks.json и
guard-artel-bg.py»).

Факты (пин d76f804a, сверка 07.10):
- Пульт уже принимает клиента Codex: `run`/`auto` без `--attach` и
  `observe register` требуют `--client codex|claude --chat <ID>`
  (`orchestrator/artel.py::_cycle_args` ~749, `_launch_detached` ~757,
  `_cmd_observe` ~863). Отсоединённый запуск разрешён только при свежем
  наблюдении: `watch --observation <ID>` отмечает связь каждые 30 с
  (`config.OBSERVATION_HEARTBEAT_PERIOD`), связь старше 90 с
  (`OBSERVATION_STALE_SECONDS`) — отказ.
- `docs/operator-session.md:437`: «значение `codex` допустимо кодом, но
  сессии при Операторе на Codex больше не ведутся». Порядок «Фоновые
  запуски под наблюдением» (там же, ~452–611) описан только для Claude
  Code: идентификатор чата — `CLAUDE_CODE_SESSION_ID`, наблюдатель —
  инструмент Monitor, таблица отказов предлагает только `--client claude`.
  `orchestrator/cycle_hint.py` печатает подсказку с переданным клиентом,
  но источник идентификатора чата для Codex нигде в репозитории не назван.
- Codex передаёт идентификатор чата в окружение команд переменной
  `CODEX_THREAD_ID` (используется пользовательским хуком
  `~/.codex/hooks/project-monitor/monitor.py`, вне репозитория).
- 30.09 дозор в чате Codex не доставил эскалации: `watch` зафиксировал
  события 01M3SK48 и 01M3SE87, а сессия прочитала их только после
  вопроса Оператора о статусе. Обход того же дня — пользовательский
  Stop-хук `~/.codex/hooks.json` + `project-monitor/monitor.py`
  (регистрация задач чата командой `arm`, продолжение хода на событии
  Stop, предел трёх продолжений за ход, отключение на Interrupt). Хук
  лежит вне репозитория, работа доставки не проверена.
- В главной копии стоит игнорируемый git локальный `.codex/hooks.json`
  с PreToolUse-хуком `.codex/hooks/guard-artel-bg.py`: он требует
  `run_in_background` — поле протокола Claude Code, которого у Codex нет.
  Команда `hook-migrate inspect|apply|restore --client codex|claude`
  (`orchestrator/artel.py` ~950–1060) уже умеет находить и снимать такие
  подключения.
- Наблюдатель, ход шага, классы событий `watch` одинаковы для ролей
  Claude и Codex (`orchestrator/watch.py`); различается только клиент
  сессии Оператора.

Требуется:
1. Полный порядок «зарегистрировать наблюдение → поставить наблюдателя →
   проверить свежесть → запустить `auto`/`run` → остановить» исполним из
   чата Codex штатными командами пульта, с
   `--client codex --chat "$CODEX_THREAD_ID"`. Подсказки пульта
   (`cycle_hint`, тексты отказов `run`/`auto`/`observe`) для клиента
   Codex называют `$CODEX_THREAD_ID`, для Claude — `$CLAUDE_CODE_SESSION_ID`.
2. Наблюдатель в чате Codex держит связь наблюдения свежей всё время,
   пока сессия ведёт задачи, а не только в пределах одного хода. Способ
   (фоновый процесс сессии Codex, отдельный процесс вне хода и т.п.)
   выбирает SPEC и обосновывает проверкой в живом Codex 0.157.
3. Событие «ЖДЁТ ОПЕРАТОРА» и отказ перехода задачи из набора
   наблюдения доходят до чата Codex без вопроса Оператора о статусе.
   Механизм доставки — штатный Stop-хук Codex (решение Оператора
   07.10), хранится в репозитории (образец
   настроек рабочего места Оператора для Codex и команда пульта,
   которая его ставит, сверяет и снимает); пользовательский
   `~/.codex/hooks/project-monitor` заменяется им. Ни хук, ни механизм
   доставки не меняют состояние задач, БД и гейты и не разрешают
   запусков.
4. Локальный PreToolUse-хук `guard-artel-bg` больше не мешает штатному
   запуску из Codex: снимается командой `hook-migrate` либо заменяется
   проверкой, совместимой с Codex. Решение — в SPEC, с обоснованием.
5. `doctor` сообщает, готово ли рабочее место Codex к ведению задач
   (механизм доставки поставлен и ему выдано доверие, мешающего хука
   нет), — проверка срабатывает, только когда сессия Оператора на
   Codex заявлена (наблюдение с `client=codex` или явный флаг).
6. `docs/operator-session.md`: пункт «сессии при Операторе на Codex
   больше не ведутся» заменён; порядок фоновых запусков и таблица
   отказов даны для обоих клиентов. `docs/stack.md` — абзац о клиенте
   сессии Оператора.

Критерии приёмки (направление; планку пишет test_author):
- Подсказки и отказы для `--client codex` называют `$CODEX_THREAD_ID`.
- Команда установки механизма доставки ставит образец в заданный каталог
  настроек Codex, повторный вызов ничего не меняет, снятие возвращает
  исходный файл; чужие хуки пользователя не затрагиваются.
- Механизм доставки на событии задачи из набора наблюдения своего чата
  выдаёт продолжение хода; на чужом чате, вне каталога проекта, в
  окружении роли (`runner.in_role_environment`) и после прекращения
  наблюдения — ничего не выдаёт.
- AC-manual: в живом чате Codex зарегистрировано наблюдение на задачу,
  запущен `auto`, задача доходит до эскалации или гейта — событие
  появляется в чате без вопроса Оператора. Исполняет Оператор (или
  сессия при нём) до approve приёмки.
