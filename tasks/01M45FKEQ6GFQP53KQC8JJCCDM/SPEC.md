# SPEC: Этап 3 ADR-0021, часть 3 из 3 — прочие развилки DEFAULT_TARGET, сторож, сквозной тест внешнего потока

## Контекст
ADR-0021 (пп. 8, 9, 12, 13) переводит пульт на одинаковую работу с любым
проектом: этап 3 переводит проверки на `repo_context` и удаляет развилки
`config.DEFAULT_TARGET`. Части 1 и 2 этапа (профиль тестов проекта,
перечень защищённых путей проекта, 16 развилок проверок п.8) идут раньше
этой. Остаются 28 прочих развилок поведения, признак
`repo_context.is_artel`, который сам сделан сравнением с
`config.DEFAULT_TARGET`, дубль `resolve` в `orchestrator/fsm.py`, а также нет
сторожа против возврата прямых сравнений в модули проверок п.8 и нет
сквозного теста потока внешнего проекта. Эта часть закрывает этап 3.

Номера строк ниже — по пину 6eb98eff (сверка ТЗ 05.10). После мержа частей 1 и
2 они сдвинутся: разработчик сверяет места по `main` с их мержем, опираясь
на имя функции в таблице.

2. **Дубль `resolve`.** В `orchestrator/fsm.py` (~140–165) нет собственного
   разрешения адреса удалённого источника и базы проекта: оно сведено к
   `repo_context.resolve`. Неразрешимый проект (неизвестное имя, сломанный
   `targets.yaml`) по-прежнему даёт деградацию, а не откат на `"origin"`
   пульта.
3. **Итог в PLAN.** PLAN несёт новую разбивку строк с
   `config.DEFAULT_TARGET` в `orchestrator/` по тем же категориям, что и ТЗ:
   комментарии/докстринги, определение, значение по умолчанию,
   намеренная константа, развилки поведения.
4. **Сторож.** Тест в `tests/` разбирает исходники модулей проверок п.8
   (`orchestrator/advance_gates/` и гейт мержа —
   `orchestrator/fsm_merge_gate.py`). На прямом сравнении с
   `config.DEFAULT_TARGET` он падает и называет найденное место
   (файл и строку).
5. **Сквозной тест внешнего потока** в песочнице (`tests/sandbox.py`).
   Внешний проект с локальным «форджем» (голый репозиторий как `origin`) и
   профилем тестов. На нём:
   - гейт зон отказывает на файле вне зон;
   - правка пути из `no_paths` проекта получает отказ;
   - удаление теста без мандата получает отказ неослабления;
   - новый тест без заявки получает отказ заявки мутации;
   - мерж такой задачи эскалирует защищённый путь.

   Тот же проект без профиля: языковые проверки не включаются, запись
   журнала об этом есть, гейт зон и защищённые пути работают.
6. **Карта.** `docs/codebase-map.md` (генерируется `scripts/codebase_map.py`
   из докстрингов модулей) описывает профиль тестов проекта, перечень
   защищённых путей проекта и перевод проверок всех трёх частей этапа 3.
7. **Тесты и смена ожиданий.** Новые тесты в `tests/` по требованиям 1, 4,
   5 несут заявки «Ловит мутацию». Если существующий тест ждёт прежнего
   поведения (например, «задача не-артели не участвует в замке зон / в
   стоп-кране»), роль выносит смену его ожиданий эскалацией с точным
   списком: файл, тест, прежнее и новое ожидание. Изменение проводится по
   мандату Оператора разделом SPEC «Меняемое поведение» механикой задачи
   «Смена поведения в существующих тестах», перечень — в PLAN. Заранее,
   до мандата, существующие тесты не меняются.

## Критерии приёмки

AC-1. Замок зон между задачами работает внутри одного внешнего проекта.
Задача внешнего проекта в `in_dev`, чья зона пересекается с зоной уже
занявшей её задачи того же проекта, получает отказ первого шага
разработчика по зоне (`zone_lock.blocking_conflict` не `None`). Она стоит в
очереди этой зоны (`queue_position`). `new` такой задачи пишет в журнал
предупреждение о пересечении зон, `status` до `in_dev` печатает добавку
«зона занята». Задачи разных проектов с одинаковыми путями зон друг друга
не блокируют.

AC-2. Стоп-кран волны работает по проекту. Отказы одного класса у задач
внешнего проекта сверх порога заводят алерт стоп-крана с `target` этого
проекта. Пока алерт открыт, `run` задачи этого проекта отклоняется до
старта шага, а `status` помечает её задачи. Задачи артели (другого проекта)
алерт не блокирует и не помечает, и наоборот: алерт артели не блокирует
задачи внешнего проекта.

AC-3. Задача внешнего проекта с незакоммиченным результатом шага (после
отказа git на коммите пульта) получает отказ перехода `advance` с
названием результата шага — так же, как задача артели: на выходе из
`in_dev` и на выходе из `tests_writing`.

AC-4. На переходе FSM задачи артели в её ссылку документов дописывается
строка паспорта, как у внешнего проекта. Запись журнала «sha зафиксирован»
у задачи артели и у задачи внешнего проекта несёт один набор полей:
`target=`, `sha=`, `чисто=`, `код=`, `артефакты=`. Поле `код=` у обеих —
голова кодовой ветки задачи.

AC-5. Сверка свежести ветки задачи внешнего проекта в `orchestrator/fsm.py`
берёт удалённый источник и базу из `repo_context.resolve`. Для проекта,
которого `repo_context.resolve` не разрешает, сверка деградирует (не
сравнивает с `main` пульта и не мержит его). В `orchestrator/fsm.py` нет
функции, которая сама читает запись `targets.yaml` ради адреса удалённого
источника или базы.

AC-6. `show` задачи внешнего проекта и задачи артели печатает статусы
SPEC/PLAN/REVIEW, прочитанные из ссылки документов задачи. `docs --fetch-all`
заводит клон внешнего проекта из `targets.yaml`, если его ещё нет, и
делает в нём fetch.

AC-7. На входе в `merge_gate` у задачи внешнего проекта заполняется
`diff_bytes` — размер диффа её кодовой ветки относительно базы в клоне
проекта.

AC-8. Гейт отработки замечаний ревью (`_review_rework_gate`) отказывает
задаче внешнего проекта с REVIEW.md `status: changes_requested`, у которой
нет нового коммита разработчика после вердикта, — так же, как задаче
артели.

AC-9. Задача артели, чья ветка отстала от `origin/main` клона артели больше
чем на `config.STALE_BRANCH_WARN_COMMITS` коммитов, получает предупреждение
`doctor` `branch-freshness` той же веткой логики, что и задача внешнего
проекта: fetch базы в клоне и сравнение с `origin/<base>`.

AC-10. В функциях таблицы требования 1 с решением «оставить» (`resolve`,
`_gh_repo_kwargs`, `_repo_kwargs`, `_main_copy_reader`,
`observed_max_task_number`, `_tasks_dir`, `_fix_unsent_closed_ref`) и в
функциях с решением «удалить» нет прямого сравнения (`==`, `!=`) с
`config.DEFAULT_TARGET`. Признак артели в оставленных местах проверяется
вызовом одной функции признака, и поведение этих мест для артели и внешнего
проекта прежнее.

AC-11. Сторож требования 4 зелёный на коде ветки. Если вписать прямое
сравнение с `config.DEFAULT_TARGET` в любой модуль
`orchestrator/advance_gates/` или в `orchestrator/fsm_merge_gate.py`, сторож
падает, а его сообщение называет файл и строку этого сравнения.

AC-12. Сквозной тест, проект с профилем: правка файла вне зон задачи
получает отказ гейта зон, и отказ называет этот файл.

AC-13. Сквозной тест, проект с профилем: правка пути из `no_paths` записи
проекта получает отказ, и отказ называет этот путь.

AC-14. Сквозной тест, проект с профилем: удаление существующего теста без
мандата Оператора получает отказ гейта неослабления тестов.

AC-15. Сквозной тест, проект с профилем: новый тест без заявки «Ловит
мутацию» получает отказ гейта заявки мутации.

AC-16. Сквозной тест, проект с профилем: на гейте мержа задача, правящая
путь из `no_paths` проекта, не мержится в базу голого репозитория-`origin`,
а эскалирует с названием защищённого пути.

AC-17. Сквозной тест, тот же проект без профиля тестов: языковые проверки
(неослабление и заявка мутации) не включаются. В журнале задачи есть запись
о том, что они не включены. Гейт зон отказывает на файле вне зон, а правка
пути из `no_paths` получает отказ.

AC-18. `docs/codebase-map.md`, пересобранная `scripts/codebase_map.py` на
ветке, называет в разделах модулей профиль тестов проекта, перечень
защищённых путей проекта и перевод проверок на признак проекта. Карта
совпадает с выводом генератора (свежа).

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых файлов зоны ≥ 5 (около 14 модулей
`orchestrator/` и новые тесты `tests/`); число критериев приёмки ≥ 10 (18).

Решение — **материал для обоснования монолита** (решает Оператор на гейте
SPEC):
- Оператор уже поделил этап 3 на три части (решение 05.10), эта — последняя.
  Зоны оставшейся работы (`orchestrator/`, `tests/`) у всех её кусков общие.
  Нарезка по границам зон невозможна: любая подзадача резала бы зону
  родителя поперёк.
- Каждая часть этапа мержится при пустом конвейере с канарейкой до сдвига
  пина (ADR-0021 п.13). Ещё одно деление добавило бы цикл канарейки и пина
  при тех же зонах.
- Сторож (требование 4) и сквозной тест (требование 5) проверяют итоговое
  состояние этапа, а не промежуточное.

Бюджет: `budget_usd: 50` — потолок по правилу «только вниз от дефолта»
(`config.DEFAULT_BUDGET_USD` = 50). Это выше рамки ТЗ ($40). Класс задачи
по калибровочной таблице (больше 15 критериев и 8 и более файлов) — около
$85, этап 2 потратил $155 при рамке $60. Потолок задач группы 3 по решению
Оператора 05.10 — $100: поднять потолок до него Оператор может командой
`budget`.
