## Замечания

- major — `orchestrator/context_package.py:63-101` (`discipline`/
  `split_into_parts`), вызывается из `orchestrator/review.py:185-190` —
  деление тела ревью-пакета/брифа на части идёт по границам СТРОК всего
  тела целиком, не по границам компонентов: diff, чей собственный размер
  меньше `CONTEXT_PART_MAX_BYTES`, может оказаться физически разорван
  между двумя «ЧАСТЬ N/M», если предшествующие ему компоненты (SPEC,
  PLAN, прошлый REVIEW, форма вердикта, стат-список — каждый по
  отдельности под `CONTEXT_FILE_MAX_BYTES`, так что ни один не
  исключается по AC-2) в сумме подводят накопленный размер тела почти
  вплотную к границе части. Прямо нарушает AC-8 («Diff... чей размер не
  превышает потолок части... включается в пакет целиком одним куском»):
  воспроизведено напрямую против `context_package.discipline` — тело из
  ~65246 байт заполнителя + diff-блока из ~5 строк (~700 байт) даёт 2
  части, причём заголовок «### Diff» попадает в часть 1, а последняя
  строка diff — уже в часть 2 (последняя строка diff отсутствует в
  части 1, только в части 2). Довод PLAN «деление diff'а — частный
  случай деления всего пакета... что закрывает AC-8/AC-9 без
  специального кода для diff» неверен именно в этом сценарии — он верен
  только пока diff доминирует в размере тела, а SPEC приводит собственные
  p99-оценки (SPEC.md, «Материалы»: SPEC/PLAN/REVIEW.md по p99 около 30
  КБ каждый), при которых сумма трёх артефактов уже сама по себе
  превышает потолок части (65536 байт) даже без diff. Тест
  `test_ac8_small_diff_whole.py` не ловит это — там SPEC/PLAN в
  `_sandbox.py` заведомо крошечные, тело пакета никогда не приближается к
  потолку части без нарочно раздутого diff/PLAN. Предложение: обращаться
  с каждым отрендеренным компонентом (и с diff-блоком) как с атомарной
  единицей при делении — например, форсировать границу части
  непосредственно перед `### Diff`, либо делить каждый компонент
  отдельно и упаковывать получившиеся куски в части, а не гнать всё тело
  одним потоком строк.

- major — `orchestrator/fsm_advance.py:390` (`_capacity_gate_refuses`) —
  `diff, _, _ = _review_git_diff_part(config.MAIN_BRANCH, t["branch"])`
  отбрасывает третий элемент кортежа — причину сбоя git, которую
  `review.git_diff_part` специально возвращает отдельно (см. его же
  докстринг: «причину возвращаем отдельно от текста... в журнале "строк
  diff 0" у не собранного и у пустого diff выглядит одинаково»). Когда
  git не отвечает на `git diff main...branch` (сеть/повреждённый
  git/удалённая ветка и т.п.), `git_diff_part` возвращает короткую
  строку `"(не собран: <reason>)"` как `diff` — гейт меряет байты ИМЕННО
  этой короткой строки, находит её меньше
  `REVIEW_SNAPSHOT_DIFF_MAX_BYTES` и возвращает `False` (переход
  разрешён), хотя фактический размер снимка так и не определён. Это
  ровно тот случай, который в этом же файле двумя функциями выше
  (проверка лока `acceptance_tests/`, строки ~449-464) явно разобран как
  fail-closed по принципу ADR-0002 («неизвестный статус — это нельзя») —
  здесь тот же принцип не применён, гейт fail-open. Ни один из 36
  приёмочных тестов и ни один тест в `tests/test_review_package.py` не
  бьёт по этому пути ни для гейта, ни для `review_package` (там сбой git
  тоже не считается размером — но там это конструктивно верно, потому
  что `review_package` показывает причину сбоя в тексте пакета
  явно (`test_silent_git_becomes_a_visible_reason`), а гейт ёмкости
  ничего не показывает ревьюверу — просто пропускает переход).
  Предложение: проверять третий элемент `_review_git_diff_part` — при
  непустой причине сбоя отказывать переходу отдельным журналируемым
  отказом («гейт ёмкости: git не ответил на diff — сверка невозможна»),
  тем же fail-closed приёмом, что уже есть в этом файле для лока
  acceptance_tests/.

- minor — `orchestrator/brief.py:39-42` (`component_hash`) и
  `orchestrator/context_package.py:16-17` (`sha256_of`) — две функции
  вычисляют идентичный `hashlib.sha256(text.encode("utf-8")).hexdigest()`
  независимо друг от друга; `_manifest_component` (brief.py:154-168)
  зовёт первую для журнала и передаёт текст в `render_component`,
  который внутри зовёт вторую для тела пакета — тот же текст хэшируется
  дважды разными функциями с одинаковой логикой. Не дефект поведения
  (значения совпадают), но лишнее дублирование. Предложение:
  `_manifest_component` может переиспользовать `context_package.sha256_of`
  вместо собственной копии в `brief.py`, либо наоборот.

- minor — `orchestrator/brief.py:108-115` (`_mark_stale`) в связке с
  `orchestrator/brief.py:317-320` (`developer_brief`) — когда карта
  помечена стухшей, `_mark_stale` подмешивает служебную пометку «[КАРТА
  НЕАКТУАЛЬНА: ...]» В НАЧАЛО `map_text` ДО того, как этот текст уходит
  в `_manifest_component`/`render_component` под путём
  `docs/codebase-map.md`. Размер и sha256 в описи в этом случае
  посчитаны по аннотированному тексту, а не по реальному содержимому
  файла на диске — расходится с собственной декларацией
  `render_component` (`context_package.py:49-51`): «Размер и sha256
  считаются по ИСХОДНОМУ... тексту — опись обязана отвечать байт в байт
  содержимому, которое действительно читал бы инструмент чтения этого же
  пути». В момент стухшей карты это не так: `sha256sum
  docs/codebase-map.md` и sha256 из описи разойдутся. Узкий, редкий
  случай (карта регенерируется автоматически почти всегда — пометка
  остаётся только при сбое самой регенерации/сверки), ни одну AC
  буквально не нарушает, но стоит либо посчитать size/sha256 по
  исходному тексту карты (пометку показать отдельно, вне описи), либо
  явно задокументировать, что путь описи в этом случае — «текст карты,
  как показан роли», а не файл на диске.
