# SPEC: Лимиты пакетов контекста и гейт ёмкости диффа ревью

## Контекст
Сборка контекста единым документом уже есть — ревью-пакет (T011), бриф
разработчика (T028), инкрементальный diff поздних итераций (T029). Не
хватает дисциплины размера и доказательства полноты: роль перечитывает
уже включённое, инструмент чтения молча усекает длинный файл/diff, и
неограниченный diff уходит ревьюверу молча — вердикт по объёму, не
помещающемуся в один контекст, ненадёжен по построению. Источник:
docs/research/2026-09-01-evidence-gates-proposals.md, п.3.

## Требования
1. Машинная опись пакета — для брифа разработчика (`brief.developer_brief`)
   и ревью-пакета (`review.review_package`): для каждого включённого
   целиком компонента — путь, размер в байтах, sha256; для не влезшего
   целиком — запись с путём, размером и причиной пропуска вместо
   содержимого.
2. Именованные константы в `config.py`: потолок размера одного
   включённого файла и потолок размера части пакета (порог, начиная с
   которого пакет делится на части). Точные значения — ниже, по фактике
   реальных пакетов (см. «Материалы»).
3. Пакет, чей итоговый размер превышает потолок части, делится на
   нумерованные части фиксированного размера по границам строк; опись
   несёт размер и sha256 каждой части; промпт роли требует прочитать все
   части по порядку; конкатенация частей побайтово равна полному пакету.
4. Diff в ревью-пакете подчиняется той же дисциплине: до потолка части —
   целиком, крупнее — той же нумерованной разбивкой со sha256; текущее
   молчаливое усечение (`review.truncate_diff`, `review.truncate_package`)
   для diff и пакета этой дисциплиной заменяется — молчаливая потеря
   хвоста исключается конструкцией.
5. Новый гейт ёмкости на переходе `in_dev → review`: отказывает, если
   полный diff снимка (тот же расчёт, что и «полный» `diff_type` в
   `review.review_package` при `iteration == 1`, т.е. от
   `config.MAIN_BRANCH` до HEAD ветки задачи) превышает потолок гейта
   (именованная константа); причина отказа — «снимок не помещается в
   один контекст ревью — разделить задачу» с id/названием задачи. Отказ
   журналируется тем же способом, что остальные отказы `advance` в
   `fsm_advance.py` (`store.journal`). Гейт сам не делит задачу и не
   поднимает лимит — решение дальше принимает Оператор.
6. Инкрементальный diff (T029, `iteration > 1` с `prev_sha`) сохраняет
   текущую точку отсчёта и поведение без изменений и получает ту же
   опись/дисциплину частей (требование 3–4); потолок гейта ёмкости
   (требование 5) на каждом входе в `in_dev → review` считается по
   полному diff снимка, а не по инкременту, даже когда ревью-пакет этой
   итерации показывает инкрементальный diff.
7. Промпт роли (`role_prompt.py`) и скилы затронутых ролей (developer,
   reviewer) дополняются протоколом описи: части читать по порядку,
   включённое в опись целиком — не перечитывать инструментом чтения
   повторно, пропущенное (исключённый файл) — читать адресно по ссылке
   из описи. Мандат на правку `skills/` под эту задачу предоставлен ТЗ.
8. Тесты: опись соответствует фактическому содержимому (sha256); файл
   больше потолка — пропущен со ссылкой и причиной; пакет делится на
   части и конкатенация частей равна целому; гейт ёмкости отказывает на
   diff больше предела и пропускает на меньшем; отказ журналируется;
   поведение T011/T028/T029 не регрессирует; существующие тесты зелёные.

## Критерии приёмки

AC-1. Текст `brief.developer_brief` и текст `review.review_package` несут
опись: для каждого включённого целиком компонента (SPEC/TZ/PLAN/REVIEW/
карта кодовой базы/конвенции/ANSWER) в описи есть путь, размер в байтах
и sha256.

AC-2. Компонент, чей размер превышает потолок одного файла (131072
байт = 128 КиБ), не включается в текст пакета целиком: опись несёт по
нему путь, размер и причину пропуска («превышен лимит файла») вместо
содержимого.

AC-3. `config.py` несёт именованную константу потолка размера одного
включённого файла со значением 131072 (байт) и именованную константу
потолка размера части пакета/diff со значением 65536 (байт).

AC-4. `config.py` несёт именованную константу потолка гейта ёмкости
diff снимка со значением 262144 (байт).

AC-5. Текст пакета (брифа или ревью-пакета), чей итоговый размер
превышает потолок части (65536 байт), делится на нумерованные части по
границам строк — ни одна строка не разрывается внутри части.

AC-6. Каждая часть несёт в описи номер, размер в байтах и sha256;
конкатенация частей в порядке номеров побайтово равна полному тексту
пакета до деления.

AC-7. Когда пакет поделён на части (AC-5) больше одной, текст,
собираемый `role_prompt.py` для роли, явно требует прочитать все части
по порядку, прежде чем действовать.

AC-8. Diff в `review.review_package`, чей размер не превышает потолок
части (65536 байт), включается в пакет целиком одним куском.

AC-9. Diff в `review.review_package`, чей размер превышает потолок
части, делится на ту же нумерованную разбивку со sha256 каждой части,
что и в AC-5/AC-6, — не усекается по числу строк или байт с потерей
хвоста.

AC-10. Ни diff, ни любой другой компонент ревью-пакета или брифа
разработчика после этой задачи не усекается молча (текущее поведение
`truncate_diff`/`truncate_package` с потерей хвоста и словом «усечён»
прекращается): контент либо показан целиком, либо явно поделён на
части (AC-5/AC-9), либо явно исключён записью в описи (AC-2).

AC-11. Инкрементальный diff (T029, `iteration > 1`, есть `prev_sha`)
считается от `prev_sha`, как и до этой задачи, и несёт ту же опись и ту
же дисциплину частей, что в AC-8/AC-9.

AC-12. Переход `in_dev → review` отказывает, если размер полного diff
снимка (`git diff config.MAIN_BRANCH...<ветка задачи>`, тот же расчёт,
что «полный» `diff_type` в `review_package` при `iteration == 1`)
превышает 262144 байт (потолок AC-4).

AC-13. Отказ по AC-12 несёт причину «снимок не помещается в один
контекст ревью — разделить задачу» и id/название задачи и
журналируется через `store.journal`, тем же способом, что остальные
отказы `advance` в `fsm_advance.py`.

AC-14. Отказ по AC-12 не выполняет и не предлагает автоматически
никакого действия — задача остаётся в `in_dev` до вмешательства
Оператора (нет ни авторазделения задачи, ни автоповышения лимита).

AC-15. Потолок AC-12 при повторном входе в `in_dev → review`
(итерация 2+, после `changes_requested`) считается по полному diff
снимка заново, а не по инкременту прошлой итерации.

AC-16. Переход `in_dev → review` при полном diff снимка не больше
262144 байт проходит гейт AC-12 без отказа (при прочих условиях
перехода выполненных).

AC-17. Скилы ролей developer и reviewer дополнены протоколом описи:
части читать по порядку, включённое в опись — не перечитывать
инструментом чтения, исключённое по AC-2 — читать адресно по ссылке из
описи.

AC-18. Существующий состав компонентов, включаемых в бриф
разработчика и ревью-пакет (T011, T028), не меняется этой задачей —
меняется только дисциплина размера и опись (AC-1–AC-11).

AC-19. Поведение инкрементального diff (T029) вне описи/дисциплины
частей (выбор точки отсчёта, вырожденный откат на полный diff без
`prev_sha`) не регрессирует.

AC-20. Все существующие тесты в `tests/` остаются зелёными после
изменений этой задачи.

## Не входит

- Границы недоверенных данных в брифах (п.6 документа-источника) —
  отдельная задача ПОСЛЕ мержа этой, та же зона сборки пакетов.
- Изменение состава включаемого в брифы: перечень артефактов-кандидатов
  (SPEC/TZ/PLAN/REVIEW/карта/конвенции/ANSWER/diff) остаётся тем же,
  что до этой задачи.
- Ретроспективная правка уже собранных/показанных старых пакетов.
- Автоматическое разделение задачи гейтом ёмкости (AC-14) — только
  явный отказ и решение Оператора.
- Опись для брифа analyst (`brief.analyst_map_component`) и для
  добавки test_author (`brief.test_author_answer_component`) —
  требование 1 ТЗ называет только бриф разработчика и ревью-пакет.
- Повышение любого из потолков (AC-3/AC-4) после мержа этой задачи —
  класс «лимит», только Оператор через ADR-0002.
- Зона параллельной задачи «Наблюдаемость сессий»
  (01M1GCHKG8DDK4DCZWCE3DYKWC): `orchestrator/lease.py`, `liveness.py`,
  `store.py` сверх существующего API, `runner.py`, `doctor.py`,
  `catalog.py`, `cleanup.py`, `release.py`, `pause.py`.
