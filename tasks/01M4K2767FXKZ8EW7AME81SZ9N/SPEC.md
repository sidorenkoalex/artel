# SPEC: Полный прогон — предел notes из профиля, сигнал «длительность близка к пределу»

## Контекст
Предел полного прогона `tests/` артели — 1500 с из профиля тестов проекта
(`targets.yaml`, `full_suite_timeout_sec`, `project_profile.full_suite_limit`),
но `notes` (`orchestrator/notes.py` ~1010, `acceptance.run_full_suite(work_dir)`)
гоняет набор с запасным пределом `config.FULL_SUITE_TIMEOUT_SEC` (900 с,
источник «config»). Метрики прогона уже считаются (`acceptance._suite_metrics`:
длительность, число тестов, нагрузка), но сигнала о том, что прогон подошёл к
своему пределу, нет: рост времени набора замечают только по факту отказа
(копилка 05.10–07.10; 06.10 — 80% предела). Прецедент сигнала — наблюдатель
роста карты (`orchestrator/doctor/map_growth.py`, алерт `map.growth` в
`status`). Канарейка из задачи исключена решением Оператора (ANSWER-1, п.1):
с 01M4BEG0003CH0QA1GY0PXAT03 полный набор в клоне канарейки пропускается
(`config.CANARY_SKIP_FULL_SUITE`).

## Требования

1. `notes`: полный прогон берёт предел из профиля тестов проекта так же, как
   гейты (`project_profile.full_suite_limit` target'а артели); источник
   предела виден в выводе команды. Без профиля — прежний запасной предел
   `config.FULL_SUITE_TIMEOUT_SEC` с источником «config».
2. Сигнал: полный прогон — гейта, `suite-run` или `notes`, — длившийся не
   меньше 80% своего предела, оставляет:
   - запись журнала задачи «длительность близка к пределу» с длительностью,
     пределом, источником предела и нагрузкой (у `notes`, где задачи нет, —
     строку вывода с теми же данными);
   - алерт `alerts.raise_alert` kind=trigger, видимый в `status` до
     подтверждения (по образцу `map.growth`).
   Порог 80% — именованная константа (вне `orchestrator/config.py`: файл в
   ТЗ — только чтение). Исход прогона сигнал не меняет: зелёный остаётся
   зелёным, красный — красным, отказ по истечению предела — отказом.
3. Открытый алерт «длительность близка к пределу» — один на проект
   (target), как у `map.growth`. Пока он не подтверждён, следующие прогоны у
   предела дают только запись журнала задачи (у `notes` — строку вывода),
   нового алерта нет; после подтверждения следующий прогон у предела
   поднимает новый алерт (ANSWER-1, п.2).
4. `docs/triggers.md` несёт строку нового триггера: условие (длительность
   полного прогона ≥ порога от предела, с именем константы), источник данных,
   реакция Оператора при подтверждении, где виден (`status`, alerts
   kind=trigger).
5. Ослабления нет: пределы не повышаются, замок полных прогонов машины
   (`orchestrator/suite_lock.py`) не снимается раньше, чем сейчас, отказ по
   истечению предела остаётся отказом. Зона `orchestrator/suite_lock.py`
   правится, только если она нужна для сигнала (ANSWER-1, п.1).
6. Смена ожидания существующих тестовых методов `tests/` — только перечнем
   раздела «Меняемое поведение» этого SPEC (инвариант 38); на момент SPEC
   таких методов не выявлено.

## Критерии приёмки

AC-1. `notes` при профиле тестов проекта с пределом 1500 с: полный прогон
получает предел 1500 и источник профиля, источник предела виден в выводе
команды.

AC-2. `notes` без профиля тестов проекта: полный прогон получает предел 900
(`config.FULL_SUITE_TIMEOUT_SEC`) и источник «config», источник виден в
выводе.

AC-3. Полный прогон гейта длительностью 85% своего предела (подменённые
часы) оставляет запись журнала задачи «длительность близка к пределу» с
длительностью, пределом, источником предела и нагрузкой и поднимает алерт
kind=trigger.

AC-4. Полный прогон длительностью 70% своего предела не оставляет ни записи
журнала «длительность близка к пределу», ни алерта.

AC-5. Красный прогон длительностью не меньше 80% предела тоже даёт запись и
алерт, а его исход остаётся прежним (красный — не зелёный, отказ гейта —
отказ); прогон, оборванный истечением предела, остаётся отказом.

AC-6. Полный прогон `suite-run` длительностью 85% предела оставляет запись
журнала задачи «длительность близка к пределу» и поднимает алерт.

AC-7. Полный прогон `notes` длительностью 85% предела печатает строку вывода
«длительность близка к пределу» с длительностью, пределом, источником и
нагрузкой и поднимает алерт.

AC-8. `status` показывает неподтверждённый алерт «длительность близка к
пределу»; его подтверждение (ack) убирает алерт из `status`.

AC-9. Пока алерт проекта не подтверждён, второй прогон у предела того же
target'а даёт запись журнала (у `notes` — строку вывода), но не второй
открытый алерт; после подтверждения следующий прогон у предела поднимает
новый алерт.

AC-10. Порог сигнала — именованная константа: её подмена (например, на 0.9)
меняет исход для прогона в 85% предела (сигнала нет), и её имя названо в
строке нового триггера `docs/triggers.md`.

есть деление дороже рамки целиком. Решение — за Оператором на гейте SPEC.
