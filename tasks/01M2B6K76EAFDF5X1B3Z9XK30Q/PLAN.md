# PLAN: Приёмка: печать того, что проверит `approve`

## Подход

Единственная точка входа задачи в `acceptance` во всей кодовой базе —
`fsm_autogate._maybe_autogate_acceptance` (её же зовёт `fsm_advance.
_review_approved` ровно один раз на переходе, вне зон этой задачи) —
поэтому и печать/журнал требования 1 достаточно повесить туда: тот же
вызов покрывает и «остановку auto на acceptance» (auto использует тот
же `advance` изнутри), и «advance без auto» одним и тем же местом, без
второго хука в `auto.py` и без риска задвоить запись.

Добавляю в `orchestrator/fsm_autogate.py`:
- `_acceptance_manual_criteria` — сканирует ВСЕ manual/skip/escalate
  критерии планки через `guard.scan_ac_content` целиком (не через
  `_autogate_conditions`, которая замыкается на первом отказе и не
  даст увидеть остальные критерии, SPEC требование 3);
- `_acceptance_pull_merge_commits` — merge-коммиты кодовой ветки задачи
  (`git log --merges`); в этой системе единственный вид merge-коммита
  на кодовой ветке — подтяжка main (docstring `fsm_advance.
  _PULL_MAIN_COMMIT_INFIX`), поэтому текстовый фильтр по сообщению не
  нужен — само наличие merge-коммита уже и есть «родитель подтяжки»;
- `_acceptance_checklist_detail` — собирает обе группы (а/б) в одну
  строку: группа «а» — фиксированные 4 пункта (источник+sha через те же
  `artifact_source.resolve`/`gitcmd.branch_head_sha`, что уже несёт
  условие «а» `_autogate_conditions`), группа «б» — manual-критерии +
  факт про зоны + подтяжки (если были) + REVIEW.md/итерация, либо
  «автогейт пройдёт сам», если manual-критериев нет вовсе (AC-4/AC-8);
- `_log_acceptance_checklist` — журналирует и печатает это одной
  записью (AC-1).

`_maybe_autogate_acceptance` зовёт `_log_acceptance_checklist` сразу
после отсечки `gates.policy() != AUTO` (её поведение не меняется —
политика не auto, функция по-прежнему не печатает и не журналирует
ничего, старый инвариант T066 AC-5), до вычисления `_autogate_
conditions` — печать не зависит от исхода гейта.

`config.AUTO_STOP["acceptance"]` получает отсылку к записи журнала
(требование 3/AC-6) — правка текста хинта, без изменения структуры
словаря.

`docs/operator-gates.md` правится приложением unified diff к этому
PLAN (требование 4) — не напрямую: раздел «Гейт приёмки» лишается
пунктов 3 (прогон приёмочных тестов) и 4 (полный `tests/`), которые
теперь целиком в группе «автоматически при approve».

## Влияние на систему

Изменение аддитивное: новая запись журнала и новая строка печати на
уже существующем, не меняемом переходе (`_autogate_conditions`
вызывается тем же образом, тем же местом, что и раньше — требование
«Не входит» СПЕК). Риск — двойная печать записи на один вход в
acceptance: исключён тем, что `_maybe_autogate_acceptance` вызывается
РОВНО один раз на переход (единственный вызывающий код —
`fsm_advance._review_approved`), а не из `auto.py` отдельно.
`docs/operator-gates.md` не редактируется в рамках кода задачи —
только приложением diff'а, применимость которого проверена `git apply
--check` на чистом дереве (см. приложение). Существующие тесты
`tests/test_auto_cycle.py`/`tests/test_fsm_autogate.py` не изменены
(AC-9) — прогон подтверждён отдельной командой ниже.

## Риски

`_acceptance_pull_merge_commits` не фильтрует merge-коммиты по тексту
сообщения (только по факту `--merges`) — в реальной системе это
безопасно (единственный источник merge-коммитов на кодовой ветке
задачи — автослияние подтяжки main), но если когда-нибудь появится
другой законный merge-коммит на этой ветке, он тоже попадёт в
«родители подтяжек» группы «б» — не ошибка по существу (Оператору
всё равно полезно видеть любой merge в истории ветки на приёмке), но
стоит знать при будущем расширении механики.

## Предложения системе

- `fsm_advance._PULL_MAIN_COMMIT_INFIX`/аналогичная своя копия в
  `fsm_autogate.py` дублируют один и тот же литерал по модулю (тот же
  класс, что уже отмечен в `pull.py`/`brief.py` докстринге
  `PULL_CONFLICT_ROLE_STEP_MARKER`) — кандидат на будущий общий модуль
  констант, если появится третье место с той же надобностью.

## Приложение: unified diff `docs/operator-gates.md`

Итерация 2 (закрытие R1-F1): прежнее приложение несло вручную набранный
диф, где пустые context-строки внутри хунков потеряли обязательный
ведущий пробел-маркер, а второй хунк — ещё и завершающую пустую
context-строку (реальная граница файла перед «Отказ: ...» на строке
103) — `git apply` не может классифицировать такую строку и падает
`corrupt patch at line 33`. Новое приложение ниже сгенерировано
`git diff docs/operator-gates.md` после применения того же
содержательного изменения Edit-инструментом (не набрано руками) —
маркеры context-строк и оба хунка воспроизведены байт-в-байт из
реального diff. Применимость перепроверена `git apply --check` на
чистом дереве ветки (без `--recount`) непосредственно перед сдачей —
проходит без ошибок. Оператор применяет этот diff отдельным коммитом
в main — код задачи его не коммитит (zones не включают `docs/`).
