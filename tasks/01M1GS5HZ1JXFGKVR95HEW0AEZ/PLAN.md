# PLAN: Вход в verifying требует голову ветки на origin

## Подход

Общий хелпер `github_adapter.ensure_head_in_origin(conn, task_id, branch)`
сверяет `git ls-remote origin refs/heads/<branch>` (конкретный sha, не
факт присутствия ветки) с `gitcmd.branch_head_sha(branch)`. Совпадают —
no-op, ничего не журналируется (AC-1/AC-8). Расходятся — авто-`git push
-u origin <branch>` (тот же вызов, что `ensure_draft_mr`): успех
журналируется и хелпер возвращает `(True, "")`; провал журналируется
хелпером и возвращает `(False, "голова ветки не в origin, push не
удался: <ошибка>")` — решение о смене состояния/эскалации остаётся за
вызывающим кодом (fsm_advance.py / fsm_merge_gate.py), сам хелпер
состояние не трогает.

Два вызывающих места:
- `fsm_advance.py::review`, ветка `status == "approved"` — вызов ДО
  `store.update_task(conn, task_id, reviewed_iter=iteration)`, а не
  «непосредственно перед `set_state`» буквально: сдвиг `reviewed_iter`
  раньше push-проверки съел бы свежесть вердикта на первом же провале
  push и заблокировал повторный `advance` после починки origin (AC-5).
  Провал — `store.journal` + `return False`, тот же приём, что у
  остальных отказов этой функции (реестр замечаний, красные
  acceptance_tests) — не `sys.exit`.
- `fsm_merge_gate.py::_cmd_approve_merge_gate`, самой первой строкой
  (до сверки главной копии на main) — та же причина: SPEC требование 7
  и AC-9 требуют проверки «в начале КАЖДОГО approve», а не только на
  входе в merge_gate, потому что расхождение может появиться уже ПОСЛЕ
  входа (новый коммит на ветке задачи). Провал — graceful `return
  ("stopped",)` (тот же приём, что и у сверки главной копии несколькими
  строками ниже), задача остаётся на `merge_gate` без эскалации.

Опрос CI в `verifying` (`ci.verifying_status`) отдельно: HTTP 422
(«коммит не найден») от `check_runs`/`check_runs_page` сегодня
заворачивается в нейтральное «статус неизвестен» вместе с сырым текстом
gh. Добавлен приватный `ci._commit_not_found_in_origin(why)` (сверка по
подстроке "422", тот же приём, что `verifying_is_red`/`status_kind` уже
применяют к своим `note`) — срабатывает ТОЛЬКО когда `check_runs`
вернул `None` (реальный сбой ответа, не пустой список легитимных нулевых
проверок) с этим сигналом; тогда `verifying_status` возвращает новый
текст «голова ветки не в origin ... подсказка: git push -u origin
<branch>» вместо прогона через `run_list`-фолбэк — сам `run_list` в этом
случае бесполезен (коммита на GitHub нет вовсе, раннер не найдёт с ним
никакой прогон).

## Шаги

1. `orchestrator/gitcmd.py`: `remote_branch_sha(branch) -> str` — sha
   ветки в origin по `git ls-remote origin refs/heads/<branch>`; пустая
   строка — ветки там нет или git не ответил.
2. `orchestrator/github_adapter.py`: `ensure_head_in_origin(conn,
   task_id, branch) -> tuple[bool, str]` — сверка + авто-push +
   журналирование, как описано в «Подходе». Используется обоими
   вызывающими местами шага 3.
3. `orchestrator/fsm_advance.py::review` и
   `orchestrator/fsm_merge_gate.py::_cmd_approve_merge_gate` — вызовы
   хелпера шага 2 в точках, описанных в «Подходе».
4. `orchestrator/ci.py`: `_commit_not_found_in_origin` +
   правка `verifying_status` для различения HTTP 422.
5. Юнит-тесты на все AC (приёмочные тесты `acceptance_tests/` уже
   покрывают AC-1..AC-9 сквозным сценарием на настоящем git; юнит-тесты
   добавляются на уровне `gitcmd`/`github_adapter`/`ci` — более узкие
   и быстрые проверки того же поведения без настоящего bare-origin).

## Влияние на систему

Затрагивает только два перехода FSM (`review -> verifying`,
`merge_gate` approve) и один узел опроса CI — оба места уже делают
сетевые git/gh-вызовы сегодня, новый хелпер их не заменяет, а добавляет
перед ними ту же проверку. Ни один существующий гейт/лимит/тест не
ослабляется: push выполняется автоматически ТОЛЬКО когда голова реально
отсутствует в origin (сверка по точному sha, AC-2), а не как
безусловный побочный эффект каждого перехода — оба AC-1/AC-8 это
контролируют явно. Откат — удалить оба вызова хелпера и правку
`ci.verifying_status`; поведение возвращается к состоянию до задачи
байт-в-байт (регресс-тест AC-1 гарантирует, что путь «уже допушено»
инвариантен).

Единственная новая зона взаимного влияния — `fsm_merge_gate.py`: push-
проверка добавлена САМОЙ первой строкой `_cmd_approve_merge_gate`, то
есть выполняется на КАЖДОМ заходе тела гейта, включая повторные заходы
цикла ожидания CI (`_cmd_approve_merge_gate_cycle`, T087) после
`("wait", branch)`. На этих повторных заходах голова уже была
запушена этим же циклом секундами раньше — хелпер увидит совпадение sha
и не сделает лишнего push/журнала (AC-1-класс инвариант, тот же
принцип).

## Риски

- `git ls-remote` — сетевой вызов без таймаута (как и остальные
  git push/pull вызовы этого модуля сегодня — `gitcmd.git` таймаутов не
  ставит нигде); согласованно с существующим поведением, не новый риск
  этой задачи.
- Приватная сверка `_commit_not_found_in_origin` по подстроке "422" в
  тексте ошибки `gh` — тот же приём, что `verifying_is_red`/
  `status_kind` уже применяют к своим `note`; ложное срабатывание
  потребовало бы, чтобы "422" встретилось в тексте `gh` по другой
  причине (не найденный коммит) — риск тот же, что и у существующих
  подстрочных сверок этого модуля.
