# ТЗ: Вход в verifying требует голову ветки на origin

Источник: четыре инцидента одного дня 02.09.2026 (T101 утром, затем
одновременно три задачи волны укрепления). Класс дефекта: конвейер
переводит задачу в `verifying` и начинает опрос CI по sha локальной
головы ветки, не убедившись, что этот коммит допушен в origin.
Поздние коммиты (артефакты ревью-итераций, разрешённые конфликты
подтяжки) остаются локальными; `gh` отвечает «No commit found»
(HTTP 422), опрос крутится до потолка времени verifying (T086)
и эскалирует, хотя лечение — один `git push`. Оператор чинит руками
четвёртый раз за день.

Требуется:
1. Переход, вводящий задачу в `verifying`, машинно проверяет, что
   sha головы ветки задачи присутствует в origin (сравнение с
   `git ls-remote` либо push-состоянием — способ выбирает
   разработчик по существующему коду `github_adapter`/`gitcmd`).
2. Голова не допушена — конвейер сначала пробует штатный push ветки
   задачи (тем же механизмом, которым ветка была опубликована
   изначально); успешный push журналируется и переход продолжается.
3. Push не удался (сеть, права) — переход отказывает именованной
   причиной «голова ветки не в origin, push не удался: <ошибка>»
   и журналирует её; задача не входит в verifying с заведомо
   невидимым для CI sha. Отказ не эскалирует задачу сам по себе —
   повторный advance после восстановления сети продолжает штатно.
4. Опрос CI в уже идущем `verifying` при ответе «коммит не найден»
   (HTTP 422) различает этот случай в журнале как «голова не
   в origin» с подсказкой команды push — вместо нейтрального
   «статус неизвестен», маскирующего причину.
5. Тесты: переход с допушенной головой (без изменений поведения);
   с недопушенной и успешным авто-push; с недопушенной и упавшим
   push (именованный отказ, задача не в verifying); различение 422
   в опросе; существующие тесты зелёные.

Зоны: orchestrator/fsm_advance.py (переход в verifying),
orchestrator/ci.py (разбор ответа опроса), orchestrator/
github_adapter.py, orchestrator/gitcmd.py (при необходимости),
tests/. ЗАПУСКАТЬ ПОСЛЕ мержа задач «Лимиты пакетов» (зона
fsm_advance.py) и «Наблюдаемость сессий»; конфликт зон — эскалация.

Не входит: изменение потолка времени verifying (T086); ретраи
push по расписанию; работа с force-push и перезаписью истории
ветки (обнаруженное расхождение истории — именованный отказ,
решение Оператора).
