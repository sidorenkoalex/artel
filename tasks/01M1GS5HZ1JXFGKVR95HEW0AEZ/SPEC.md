# SPEC: Вход в verifying требует голову ветки на origin

## Контекст
Четыре инцидента одного дня (02.09.2026: T101 утром, затем одновременно
три задачи волны укрепления) одного класса: переход `review -> verifying`
(`orchestrator/fsm_advance.py::review`) заводит опрос CI по sha локальной
головы ветки задачи, не убедившись, что этот коммит допушен в origin.
Поздние коммиты (артефакты ревью-итераций, разрешённые конфликты
подтяжки) остаются локальными; `gh` отвечает «No commit found»
(HTTP 422), опрос (`orchestrator/fsm_advance.py::verifying`,
`orchestrator/ci.py::verifying_status`) крутится до потолка времени
verifying (T086) и эскалирует, хотя лечение — один `git push`. Оператор
чинит руками четвёртый раз за день.

## Требования

1. Переход, вводящий задачу в `verifying` (`orchestrator/fsm_advance.py::
   review`, ветка `status == "approved"`, непосредственно перед
   `store.set_state(..., "verifying", ...)`), машинно проверяет, что sha
   головы ветки задачи присутствует в origin (сравнение с `git ls-remote`
   либо push-состоянием — конкретный способ выбирает разработчик по
   существующему коду `gitcmd`/`github_adapter`).
2. Голова не допушена — конвейер сначала пробует штатный push ветки
   задачи тем же механизмом, которым ветка была опубликована изначально
   (`git push -u origin <branch>`, тот же вызов, что и в
   `orchestrator/github_adapter.py::ensure_draft_mr`); успешный push
   журналируется, и переход в `verifying` продолжается тем же вызовом
   `advance`, без повторного захода Оператора.
3. Push не удался (сеть, права) — переход отказывает именованной
   причиной «голова ветки не в origin, push не удался: <ошибка>» и
   журналирует её; задача не входит в `verifying` с заведомо невидимым
   для CI sha и остаётся в прежнем состоянии. Отказ не эскалирует задачу
   сам по себе — повторный `advance` после восстановления сети (или
   устранения причины) продолжает переход штатно, тем же приёмом, что и
   прочие отказы `orchestrator/fsm_advance.py` («переход отклонён» без
   смены состояния).
4. Опрос CI в уже идущем `verifying` (`orchestrator/ci.py::
   verifying_status`, через `check_runs_page`/`check_runs`) при ответе
   «коммит не найден» (HTTP 422) различает этот случай в журнале как
   «голова не в origin» с подсказкой команды push — вместо нейтрального
   «статус неизвестен», маскирующего причину.
5. Зоны: `orchestrator/fsm_advance.py` (переход в `verifying`),
   `orchestrator/ci.py` (разбор ответа опроса), `orchestrator/
   github_adapter.py`, `orchestrator/gitcmd.py` (при необходимости),
   `tests/`. Задача запускается после мержа задач «Лимиты пакетов»
   (та же зона `fsm_advance.py`) и «Наблюдаемость сессий» — конфликт зон
   по ходу реализации эскалируется, не решается самостоятельным выходом
   за границу.
6. Тесты покрывают: переход с уже допушенной головой (поведение не
   меняется); переход с недопушенной головой и успешным авто-push;
   переход с недопушенной головой и упавшим push (именованный отказ,
   задача не входит в `verifying`, следующий `advance` после устранения
   причины продолжает штатно); различение HTTP 422 в опросе CI
   `verifying`; существующий набор `tests/` остаётся зелёным.

## Критерии приёмки

AC-1. Переход `review -> verifying` при уже допушенной в origin голове
ветки задачи не меняет поведения относительно текущего: нет попытки
push и нет новых журнальных записей сверх существующих.

AC-2. Переход `review -> verifying` перед сменой состояния машинно
проверяет присутствие sha головы ветки задачи в origin (сравнением с
`git ls-remote` либо эквивалентным push-состоянием).

AC-3. Если голова ветки задачи отсутствует в origin, конвейер выполняет
push ветки задачи тем же механизмом, которым ветка публикуется штатно
(`git push -u origin <branch>`); успешный push журналируется, и переход
в `verifying` продолжается в рамках того же вызова `advance`.

AC-4. Если push из AC-3 не удался, переход отказывает с именованной
причиной «голова ветки не в origin, push не удался: <ошибка>», отказ
журналируется, и задача не входит в `verifying`.

AC-5. Отказ по AC-4 не переводит задачу в `escalated` — задача остаётся
в прежнем состоянии, и последующий `advance` после устранения причины
отказа штатно продолжает переход в `verifying`.

AC-6. Опрос CI уже идущего `verifying`, получив от GitHub API ответ
«коммит не найден» (HTTP 422), записывает в журнал причину как «голова
ветки не в origin» с подсказкой команды push — вместо нейтрального
«статус неизвестен».

AC-7. Существующий набор `tests/` остаётся зелёным после изменений.

## Не входит

- Изменение потолка времени ожидания CI в `verifying` (T086).
- Плановые/фоновые повторные попытки push по расписанию — повтор
  происходит только по явному следующему `advance`.
- Работа с force-push и перезаписью истории ветки задачи — обнаруженное
  расхождение истории (non-fast-forward) — именованный отказ, решение
  принимает Оператор, не эта задача.
