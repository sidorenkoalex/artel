# SPEC: ADR-0021, этап 2 — клон и рабочие копии задач в области проекта; главная копия пульта перестаёт меняться

## Контекст
Сейчас задачи артели работают прямо в git главной копии пульта
(`config.ROOT`). Там лежат рабочие копии `.artel/worktrees/<id>`
(`orchestrator/workspace.py:21-80`), ветки `task/*`, ссылки
`refs/artifacts/<id>` (`orchestrator/artifact_branch.py:69-103`), там же
создаётся временная рабочая копия мержа (`orchestrator/fsm_merge_gate.py:158-176`)
и выполняется push. Внешний проект использует один общий
`.artel/projects/<имя>/workspace` на все задачи. ADR-0021 (пп. 1, 2, 6, 7,
10, 12, 13) требует, чтобы на этапе 2 у каждого проекта, включая артель,
был свой клон и отдельная рабочая копия на каждую задачу в области проекта,
а git главной копии в ходе задачи не менялся. Если сделать путь артели
клоном, часть шагов мержа и проверок молча отключится: сегодня они
включаются сравнением пути с `config.ROOT`. Поэтому каждое такое место
переводится на признак проекта.

## Требования

1. **Область проекта.** У любого проекта, включая артель, есть:
   - `.artel/projects/<имя>/repo` — клон репозитория проекта; его `origin` —
     поле `url` записи проекта в `targets.yaml`, для артели тоже;
   - `.artel/projects/<имя>/worktrees/<id>/` — git-рабочая копия клона на
     ветке `task/<id>-…`, своя у каждой задачи.

   Рабочий каталог роли (`runner.role_cwd`), каталог кода для `plank-run`,
   уборки чекпоинтов и прогона планки — это `worktrees/<id>/` проекта
   задачи. Общий `workspace/` внешнего проекта пульт больше не создаёт и не
   использует. Каталоги `.artel/worktrees/<id>` пульт больше не создаёт.

   Как заводится клон (решение по п.1 ТЗ): идемпотентно командами `init` и
   `doctor --fix`, а также командой `new`, если у проекта задачи клона ещё
   нет. Свежесть клона: `fetch origin` перед заведением рабочей копии
   задачи, перед подтяжкой `main` и перед мержем. Если клон создать не
   удалось, `new` отказывает и называет причину. Отката на главную копию
   или на `workspace/` нет.

2. **Все git-операции задачи — в клоне проекта.** В git клона проекта
   выполняются: ветка `task/*`, рабочая копия задачи, подтяжка `main`,
   автокоммиты и чекпоинты, запись и push ссылки документов
   `refs/artifacts/<id>`, push ветки задачи, временная рабочая копия мержа
   и рабочая копия проверки приложений PLAN, коммит мержа, push `main`,
   уборка веток и рабочих копий (`cleanup.py`, `doctor` в части сирот и
   веток задач). В ходе задачи в git главной копии не появляются и не
   меняются ветки, ссылки, коммиты (HEAD), рабочие копии (`git worktree
   list`), не меняется и её рабочее дерево. Git главной копии меняют только
   `pin-update`/`pin --to` и ремонт самого пульта (хуки главной копии в
   `doctor --fix`).

3. **Шаги, включаемые сравнением с `config.ROOT`, переводятся на признак
   проекта.** Признак — «проект задачи — артель» (`target ==
   config.DEFAULT_TARGET`), не путь. Для артели шаг продолжает работать и
   работает на клоне (или на временной рабочей копии мержа в клоне). Для
   внешнего проекта поведение прежнее. Ни одно место не отключается молча.
   Перечень мест и их замена:

   | Место | Что включается | Замена |
   |---|---|---|
   | `fsm_merge_gate.py` ~87 | защищённые пути в диффе | признак «артель», дифф по клону |
   | `fsm_merge_gate.py` ~121 | сохранность тестов в диффе | признак «артель», дифф по клону |
   | `fsm_merge_gate.py` ~483 | `guard --all` | признак «артель», прогон в рабочей копии мержа клона |
   | `fsm_merge_gate.py` ~515, ~558 | цвет CI `main` | признак «артель», линия `main` по клону |
   | `fsm_merge_gate.py` ~877 | приложения PLAN | признак «артель», наложение в рабочей копии мержа клона |
   | `fsm_merge_gate.py` ~946 | карта кодовой базы и RETRO | признак «артель», регенерация и коммит в рабочей копии мержа клона |
   | `repo_context.py:56` (`path_or_none`) | «`repo=` не подставлять» для артели | путь клона для любого разрешённого контекста; `None` — только когда контекст не разрешён |
   | `repo_context.py:64` (`git`) | `gitcmd.git` без `-C` для артели | всегда `gitcmd.in_repo(ctx.path, …)` |
   | `artifact_branch.py:75-76, 87-89, 95, 101` | репозиторий ссылок артели = `config.ROOT` | клон артели (`repo_context.resolve`); особого случая `config.ROOT` нет |
   | `checkpoint.py` ~1091-1095 | каталог кода задачи; «не главная копия» | `worktrees/<id>/` проекта; при отсутствии — пропуск, как сейчас |
   | `plank_run.py` ~93 | отказ, если каталог кода — главная копия | отказ, если `worktrees/<id>/` задачи нет |
   | `acceptance.py` ~404 | не трогать главную копию при уборке | убирается только выкладка в `worktrees/<id>/`; главная копия по-прежнему не трогается |

   Если разработчик найдёт ещё одно место, где шаг включается сравнением
   пути с `config.ROOT`, он вносит его в PLAN с заменой по тому же
   правилу. Полное снятие развилок `DEFAULT_TARGET` в объём не входит.

4. **`gitcmd` без явного репозитория не используется для работы с
   проектом.** Вызовы, относящиеся к задаче или проекту (включая
   `gitcmd.check_ignore`, `list_branches`, `diff_name_status`,
   `diff_paths`, `is_ancestor`, `branch_exists`, `branch_merged`,
   `current_branch`, а также прямые `gitcmd.git(...)` в
   `advance_gates/review.py`, `advance_gates/plan_appendix.py`,
   `fsm_autogate.py`, `review.py`, `brief.py` — карта для брифа, `ci.py` —
   линия `main`, `coldstart.py`, `cleanup.py`, `workspace.py`,
   `artifact_cleanup.py`, `doctor/*` в части задач), получают репозиторий
   проекта явно. По главной копии остаются только вызовы из этого
   перечня:

   | Вызов | Причина |
   |---|---|
   | `pin.py` (`pin-update`, `pin --to`: `head_sha`, `fetch`, `merge --ff-only`, `reset --hard`, `is_ancestor`) | единственная разрешённая смена HEAD главной копии (ADR-0021 п.1) |
   | `doctor/root_pin.py` (`head_sha`, `ls-remote`, `is_ancestor`, `log`) | сверка пина с `origin/main` пульта, только чтение |
   | `doctor/git_hooks.py` в части главной копии | проверка и ремонт хуков самого пульта |
   | `catalog.py` ~408 (`head_sha` в предупреждении о расхождении пина) | версия пульта, только чтение |
   | `canary.py` (`head_sha`, разрешение `--sha`, `is_ancestor`, `merges_between`, `fetch_ref_sha` на выбор проверяемого коммита) | версия пульта и выбор коммита канарейки; не операция задачи |
   | `canary_drive.py` ~52 (`head_sha`) | коммит кода, загруженного в процесс (в канарейке — её клон пульта) |
   | `snapshot.py` (`head_sha` для `artel_sha` и строки «Итог: done») | версия пульта, закрывшего задачу, только чтение |
   | `runner.git_identity`, `snapshot._operator_identity` (`git config --get`) | git-идентичность Оператора, только чтение |

   Все прочие вызовы `gitcmd` в `orchestrator/` либо передают репозиторий
   проекта, либо работают в репозитории, выданном вызывающему коду
   явно (рабочая копия мержа, клон).

5. **Команды Оператора, пишущие в `main` артели** (`note`, `doc-commit`,
   `canary pool-seal`), коммитят и отправляют изменения в `origin` через
   клон артели `.artel/projects/artel/repo`. Рабочее дерево и git главной
   копии они не меняют. База для сверки удержанных записей
   (`notes.py` ~287, ~778, ~885, ~887, ~1105) — `origin/main` клона, а не
   HEAD главной копии. Решение по п.5 ТЗ: `.artel/notes-work` упраздняется —
   пульт его не создаёт и не использует, его роль берёт клон. Очередь
   удержанных записей `.artel/notes-pending` остаётся.

6. **Хуки защиты `main` в клоне берутся из пина.** `core.hooksPath` клона
   (и, значит, его рабочих копий задач) указывает на абсолютный путь
   `<config.ROOT>/scripts/git-hooks`, а не на `scripts/git-hooks` внутри
   проверяемого кода клона. Значение ставится при заведении клона и командой
   `doctor --fix`. `doctor` проверяет хуки в главной копии (как сейчас) и в
   клоне. Если в клоне `core.hooksPath` не задан или указывает в другое
   место, это предупреждение с именем клона.

7. **Канарейка** строит в своём временном каталоге область
   `projects/artel` (`repo/` и `worktrees/<id>/` своей задачи) тем же кодом,
   что и боевой пульт. Она исполняет код проверяемого коммита (ADR-0021
   п.10). Боевые `.artel/projects/artel` и git главной копии прогон
   канарейки не меняет.

8. **Переход.**
   - После этапа исторические ссылки `refs/artifacts/*` артели (238 в git
     главной копии) доступны для чтения: `docs <id> [файл]`,
     `docs --fetch-all`, пересборка кэша `retro_corpus` и `show` работают
     через клон артели и `origin`. Ссылку, которая есть в git главной
     копии, но которой нет в `origin`, тоже можно прочитать. Способ
     выбирается в PLAN; git главной копии при этом не меняется.
   - Каталоги `.artel/worktrees/` пульт больше не создаёт.
   - Живых задач на момент мержа нет (ADR-0021 п.13), переноса нет.

9. **Инварианты — приложением к PLAN.** Защищённые пути `docs/invariants.md`
   и `tests/test_invariants.py` (и `targets.yaml`, если PLAN понадобится
   поле записи артели) меняются приложением. Применимость приложения
   подтверждена в PLAN прогоном `git apply --check` на чистом дереве.
   Приложение содержит:
   - инварианты 20 и 21 в редакции таблицы п.12 ADR-0021: на любой
     проект, включая артель; каталог роли — `worktrees/<id>/` плюс каталог
     документов задачи на запись;
   - новый инвариант «git главной копии пульта не меняется в ходе задачи»
     и его проверку в `tests/test_invariants.py` тем же приложением. Это
     сквозной прогон FSM задачи артели в песочнице, после которого ветки,
     ссылки, HEAD и рабочие копии главной копии те же, что до прогона.

   `tests/test_multitarget_invariants.py` (`PultArtifactIsolationTest`,
   `ExternalWorkspaceIsolationTest`) меняется только в объёме ADR-0021,
   перечень изменений — в PLAN.

10. **Тесты.** На требования 1–7 есть тесты в `tests/` с заявками «Ловит
    мутацию». Свойство, которое уже держит долгоживущий приёмочный тест
    автора тестов этой задачи (`tests/test_01m42pencs26d0656x8fr7dfa7_*.py`),
    второй раз не требуется. Сторож свойства, которое доставляет приложение
    к защищённому пути, лежит внутри того же приложения. Существующие
    тесты не ослабляются. Они меняются только в объёме, прямо требуемом
    ADR-0021 (например, ожидание рабочей копии артели под
    `.artel/worktrees/`), перечень изменений — в PLAN.

## Критерии приёмки

AC-1. После `new` задачи артели в песочнице есть клон
`.artel/projects/artel/repo`, ветка `task/<id>-…` в клоне и рабочая копия
`.artel/projects/artel/worktrees/<id>/` на этой ветке. В git главной копии
нет ветки `task/<id>-…` и новой записи `git worktree list`; каталог
`.artel/worktrees/<id>` не создан.

AC-2. После `new` задачи внешнего проекта в песочнице есть клон
`.artel/projects/<имя>/repo` и рабочая копия
`.artel/projects/<имя>/worktrees/<id>/`. Рабочий каталог роли шага этой
задачи — `worktrees/<id>/`, не `workspace/`; каталог `workspace/` пульт не
создаёт.

AC-3. Если клона проекта нет, его заводят `init`, `doctor --fix` и `new`;
повторный вызов не меняет существующий клон. Если клонирование не удалось,
`new` отказывает, причина названа, и ни ветки, ни рабочей копии задачи не
появляется ни в главной копии, ни в `workspace/`.

AC-4. Сквозной прогон FSM задачи артели в песочнице от `new` до `done` (с
автокоммитом шага, подтяжкой `main` и мержем) оставляет неизменными
`refs/heads/*`, `refs/artifacts/*`, HEAD и `git worktree list` главной
копии. Ссылка документов задачи, коммит мержа и `main` после push
находятся в клоне и в его `origin`.

AC-5. Для задачи артели при пути контекста `repo_context`, отличном от
`config.ROOT`, на гейте мержа исполняется каждый шаг требования 3:
проверка защищённых путей, проверка сохранности тестов, `guard --all`,
цвет CI `main`, наложение приложений PLAN, регенерация карты кодовой базы
и RETRO. Наблюдаемо: нарушение даёт отказ, иначе появляется коммит в
рабочей копии мержа клона. Для задачи внешнего проекта эти шаги, как и
сейчас, не исполняются.

AC-6. `repo_context.resolve("artel").path` —
`.artel/projects/artel/repo`. `repo_context.path_or_none` возвращает этот
путь для артели. `repo_context.git` для артели исполняется в клоне.
`artifact_branch.repo_for_target("artel")` — клон артели.

AC-7. Уборка выкладки чекпоинта, `plank-run` и уборка планки после прогона
(`acceptance.drop_from_code_copy`) работают с `worktrees/<id>/` проекта
задачи. `plank-run` отказывает, если `worktrees/<id>/` задачи нет.
`tasks/` главной копии ни одна из них не меняет.

AC-8. Каждый вызов `gitcmd` без явного репозитория в `orchestrator/`
входит в перечень требования 4. PLAN подтверждает это выводом поиска по
`orchestrator/`.

AC-9. `note`, `doc-commit` и `canary pool-seal` в песочнице коммитят и
отправляют в `origin` через клон `.artel/projects/artel/repo`. HEAD,
ветки, ссылки и `git status` главной копии после команды те же, что до
неё. Каталог `.artel/notes-work` не создаётся.

AC-10. Сверка удержанной записи `note`/`doc-commit` берёт базу из
`origin/main` клона. Если HEAD главной копии отличается от `origin/main`
клона, исход сверки определяет `origin/main` клона.

AC-11. Заведённый пультом клон имеет `core.hooksPath`, равный абсолютному
пути `<config.ROOT>/scripts/git-hooks`. Ручной коммит в `main` клона без
маркера пульта получает отказ хука. `doctor` предупреждает, если у клона
`core.hooksPath` не задан или указывает в другое место (в том числе на
относительный `scripts/git-hooks`); проверка главной копии прежняя.
`doctor --fix` ставит значение в клоне.

AC-12. Прогон канарейки строит в своём временном каталоге
`projects/artel/repo` и `projects/artel/worktrees/<id>/` своей задачи и
исполняет код проверяемого коммита. Боевые `.artel/projects/artel` и git
главной копии после прогона те же, что до него.

AC-13. Для закрытой исторической задачи, чья ссылка `refs/artifacts/<id>`
есть в git главной копии, `docs <id> SPEC.md` возвращает документ: и когда
ссылка есть в `origin`, и когда её там нет. `docs --fetch-all` и
пересборка кэша `retro_corpus` читают ссылки через клон артели. Ссылки
главной копии после этого не меняются.

AC-14. PLAN несёт приложение к `docs/invariants.md` и
`tests/test_invariants.py` (и к `targets.yaml`, если оно понадобилось),
применимость подтверждена `git apply --check`. После наложения инварианты
20 и 21 распространяются на любой проект, включая артель. Новый инвариант
«git главной копии пульта не меняется в ходе задачи» держит тест в
`tests/test_invariants.py`: сквозной прогон FSM задачи артели в
песочнице. Тест краснеет, если временная рабочая копия мержа или ветка
задачи заводятся в git главной копии.

AC-15. На требования 1–7 в `tests/` есть тесты с заявками «Ловит
мутацию». Изменения существующих тестов и
`tests/test_multitarget_invariants.py` перечислены в PLAN, каждое со
ссылкой на пункт ADR-0021, который его требует.

## Оценка объёма и деление

Сработали сигналы:
- число критериев приёмки ≥ 10 (15);
- зона задевает механизм, на который опираются записи
  `docs/invariants.md` (20, 21, 33 и новый инвариант);
- зона `orchestrator/` — каталог, фактически это десятки модулей:
  упоминаний `config.ROOT` 190 в 57 модулях.

**Обоснование монолита** (решение за Оператором на гейте SPEC):
- Нельзя разрезать смену пути артели в `repo_context`/`artifact_branch`
  с `config.ROOT` на клон. От этого пути одновременно зависят все шаги
  требования 3, вызовы `gitcmd` требования 4, рабочие копии задач и
  рабочая копия мержа. Часть, которая переключит путь без перевода шагов
  мержа на признак проекта, молча отключит проверку защищённых путей,
  сохранности тестов, `guard --all`, приложения PLAN и карту. Обратный
  порядок (сначала признаки, потом путь) ничего не проверяет, пока путь —
  `config.ROOT`.
- Канарейку (требование 7) нельзя отделить от этой смены. Порядок ADR-0021
  п.13 — «мерж → канарейка на новом коммите → `pin-update`». Код с
  клонами, у которого канарейка не строит `projects/artel`, канарейку не
  пройдёт, и пин сдвинуть нельзя.
- Инварианты (требование 9) по ADR-0021 п.12 меняются одним мержем с
  кодом.
- Отделить можно только команды Оператора (требование 5) вместе с
  заведением клона и хуками (требования 1 в части клона, 6). Но хуки клона
  нужны и основной части (push `main` на мерже идёт из клона), а
