# PLAN: Пробный период и приостановка пары набора

## Подход

Вся логика наборов остаётся в `orchestrator/models.py` (там уже живут
допуск пары/набора, правило вины, разрешение модели шага задачи); SQL —
только в `orchestrator/store.py` (инвариант «SQL только в store»); схема —
в `orchestrator/schema.py` одним DDL-литералом на `SCHEMA` и `migrate()`.

**Хранение (БД пульта, не `model_sets.yaml`).** Две таблицы:
- `pair_verdicts` — вердикты ревью настоящих задач на паре набора по роли
  `developer` (`return` / `approved`), с автоинкрементным `id` — порядок
  событий по `id`, а не по секундным меткам времени (в одну секунду
  укладываются несколько вердиктов);
- `pair_suspensions` — автоматические приостановки пар: роль, модель,
  набор, задача, причина, метка; снятие — `resumed_ts`, текст решения и
  `resumed_after_verdict` (наибольший `pair_verdicts.id` на момент
  снятия: вердикты не старше него в «подряд» не засчитываются, AC-10).
  Действующая приостановка — строка пары с `resumed_ts IS NULL`.

**Пробный период (треб. 1–2).** В `fsm_autogate._autogate_conditions`
безусловный отказ части 2 заменяется отказом «автогейт: пробная задача
набора <имя>, N из 3 — приёмка ручная (ADR-0019 п.5)» для настоящей
задачи с набором, у которой настоящих задач в `done` с тем же
записанным составом (`model_set_members`, сравнение разобранных
отображений) меньше трёх; N = их число + 1. Счёт — `models.set_trial_done`
по строкам `store.all_tasks`. Проверка остаётся первым условием, как была
у части 2: решение пробного периода от остальных условий не зависит, а
полный набор стоит минут. Следствие: отказ автогейта по вине роли
(треб. 4) возможен только у задач после пробного периода — ровно так
SPEC описывает второй триггер («отказ автогейта четвёртой и последующих
задач», раздел «Обоснование монолита»). Канареечная задача с набором
пробного периода не несёт (треб. 1 — только настоящие задачи) и идёт
на общих условиях.

**Возврат ревью (треб. 3).** Точка возврата `fsm_advance.
_review_changes_requested` вне зон; единственный узел любого перехода —
`store.set_state` (в зонах), где уже живут хуки перехода
(`_close_attention_alert`). Добавляется хук: переход `review -> in_dev`
(возврат) и `review -> acceptance` (одобрение) зовёт
`models.record_review_verdict` (отложенный импорт, тот же приём, что
`record_fixation`). Других переходов из `review` в эти состояния в коде
нет (сверено grep по `set_state`). Вердикт пишется паре, если задача
настоящая, у неё в составе набора `developer` на не-боевой модели и
последний шаг `developer` этой задачи («agent run started», поле
`model=`) шёл именно на этой модели («где developer шёл на этой паре»).
На возврате — правило «подряд» среди вердиктов пары после последнего
снятия: (а) у этой задачи уже есть возврат на паре; (б) предыдущая по
времени (по `id` вердикта) другая настоящая задача с вердиктом на паре
получила возврат ревью — дословно SPEC: «тоже получила возврат ревью».
Уже приостановленная пара повторно не приостанавливается.

**Отказ автогейта (треб. 4).** В `fsm_autogate._maybe_autogate_acceptance`
после отказа зовётся `models.suspend_on_autogate_refusal`: только
настоящая задача с набором, вина `роль` по `autogate_refusal_blame`,
виновная роль — из перечня части 1, который превращается в отображение
«начало причины → роль» (критерии `manual`/`skip` → `test_author`,
красный полный набор / критерий `ci` → `developer`); кортеж
`_ROLE_BLAME_STARTS` сохраняется (производный от отображения), поведение
`autogate_refusal_blame` не меняется. Пара виновной роли — из
записанного состава задачи; модель, совпадающая с боевой, не
приостанавливается.

**Приостановка (треб. 5).** Одна функция `models._suspend_pair`: строка
`pair_suspensions`, запись журнала задачи «пара набора приостановлена»
(роль, модель, набор, причина), алерт `kind=incident`,
`source=pair_suspension`, `target` — id задачи, сообщение называет роль,
модель, набор, задачу, причину и команду снятия. Перекрытие
`model_sets.yaml`:
- `set_admitted` (вход `new --set` и `set-models`) — пара с действующей
  приостановкой даёт отказ «пара роль → модель приостановлена пультом …»;
- `_set_pair_withdrawn` (старт шага, `resolve_task_role`) — то же
  основание, шаг на боевой модели; текст отката дополняется именем
  боевой модели (AC-6: запись называет роль, модель набора, боевую модель
  и причину).

**Снятие (треб. 6).** `artel.py pair-resume <роль> <модель> "<решение>"`
→ `models.cmd_pair_resume`: без действующей приостановки — `sys.exit` с
текстом до любой записи в БД; иначе `store.resume_pair_suspension` и
запись журнала задачи, вызвавшей приостановку («пара набора снята с
приостановки», роль, модель, решение). Команда вне белого списка ролей
(закрыта для процесса роли по умолчанию).

**Чистота канарейки (треб. 8).** `unclean_reason`: при выполненной
ожидаемой эскалации и `escalations > 1` — причина «эскалаций N, ожидаемая
одна». Остальные ветки не меняются.

## Влияние на систему

- `store.set_state` — единственная точка переходов; новый хук срабатывает
  только на `review -> in_dev`/`review -> acceptance` и только у задач с
  набором, сбой разбора набора (`ModelsError`) переход не роняет (переход
  к этому моменту уже записан, CAS не меняется).
- Автогейт: задачи без набора — поведение байт-в-байт прежнее; задачи с
  набором — ручной гейт в пробном периоде (как было), после — общие
  условия. Тест части 2 `test_ac13_task_with_set_stays_on_manual_
  acceptance_naming_the_set` остаётся зелёным без правки (первая задача
  набора — пробная, причина называет набор) — SPEC «Не входит».
- Схема: две новые таблицы, общий литерал DDL для свежей и догнанной БД
  (класс `test_store_schema_migration_parity`). Откат — revert коммита
  задачи; таблицы в БД остаются неиспользуемыми, не мешают.
- `model_sets.yaml` не пишется ни одной новой веткой кода (AC-2, AC-4).
- Гейты, лимиты, guard не ослабляются; `unclean_reason` строже, не мягче.

## Риски

- Определение «шёл на паре» читает формат записи «agent run started»
  (`model=<id>,`) — формат стабилен (его же читают тесты части 2), но
  это связь по тексту журнала; при смене формата вердикт перестанет
  засчитываться (fail-open в сторону «не приостановить»). Альтернатива —
  колонка модели шага в БД — шире зоны задачи.
- Толкование «предыдущая задача тоже получила возврат ревью» — дословное
  (любой возврат предыдущей задачи после последнего снятия), а не
  «последний вердикт предыдущей задачи — возврат». AC-5 покрывает только
  предшественника с одним одобрением — оба толкования его проходят.

## Предложения системе

- Модель шага роли живёт в БД только текстом записи «agent run started»
  (`model=<id>`): правило «где developer шёл на паре» читает его разбором
  строки журнала. Колонка модели шага (или отдельная таблица шагов роли)
  сняла бы связь решений пульта с форматом текста журнала
  (`orchestrator/runner.py::_prepare_step`).
- Хуки предметной логики копятся в `store.set_state` (паспорт, attention,
  теперь вердикт ревью) — у «листа графа импортов» уже три отложенных
  импорта; кандидат на явный реестр наблюдателей перехода.
