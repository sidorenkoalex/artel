# SPEC: Ядро раннера compose

## Контекст
Часть 1 деления задачи 01M6P22XBCQS49HE92YGAB25N9 («Раннер тестов
внешнего проекта в контейнере Docker Compose»). Доверенный внешний
проект, тесты которого требуют служб (СУБД, брокер, кэш) и идут в
контейнере сервиса Compose-файла проекта, под раннером `pytest-own` не
исполним: голый pytest на машине не видит служб, команда `docker compose
… run` в профиле пишет отчёт по пути машины, которого нет в контейнере,
свой `HOME` отрезает Docker от его конфигурации, службы никто не
поднимает и не снимает. Поправка Оператора 05.11.2026 к ADR-0023
(77e9ca9ca, пп. 1–2) разрешает такому проекту раннер `compose` с
перекрытием пульта. Эта часть вводит раннер во все места прогона с
отчётом (`acceptance._report_run` и его потребители); окружение шага роли
и `doctor` — часть 2.

Опыт 05.11 вне пульта (ТЗ родителя, факт 6): `up -d --wait` — 6 с, сборка
образа — 177 с, полный набор `-n 8` — 176 с; JUnit-отчёт под
смонтированным каталогом читается с машины, `classname` — от рабочего
каталога контейнера (= `workdir`) без перевода; `down -v
--remove-orphans` — 1 с.

Требования 1–11 и AC-1…AC-16 перенесены дословно из SPEC родителя (с

## Требования

1. **Вид раннера и поля записи.** `runner: compose` входит в
   `targets.PROFILE_RUNNERS`, допустим в `test_profile` и в `components:`.
   Поля записи (подполя профиля и поля компонента, одни имена):
   - `compose_file` — путь Compose-файла в дереве (обязательно);
   - `compose_service` — имя сервиса тестов (обязательно);
   - `compose_env_file` — путь файла окружения Compose в дереве
     (обязательно);
   - `compose_env_template` — путь шаблона, из которого пульт копирует
     `compose_env_file` (обязательно);
   - `compose_mount` — ровно одна пара строкой
     `<каталог дерева>:<каталог в контейнере>`: слева относительный путь
     каталога (правило вида `dir`, `.` — корень дерева), справа абсолютный
     путь (обязательно);
   - `compose_up_down_sec` — слагаемое предела на подъём и снятие служб,
     целое > 0 (необязательно, требование 9);
   - `workdir` — при `compose` обязательно (решение гейта 3.2; у прочих
     раннеров необязательность прежняя, `targets.py:76-77`): правило
     «отсутствие равно `.`» к `compose` не применяется — оно расходится
     с выкладкой планки (`plank_layout.py:44-45`);
   - `command` — команда pytest в контейнере; при `compose`
     необязательна, без неё — `["pytest"]`; у прочих раннеров
     обязательность `command` прежняя (`targets.py:57`). Канал умолчания
     (решение гейта SPEC 05.11, второй круг, 1): `targets.load` подставляет
     `["pytest"]` в отдаваемую копию записи `compose` без `command` — рядом
     с `_with_long_lived_pairs` (`targets.py:268-272`); все потребители
     записи (в том числе `repo_context.profile_of`,
     `repo_context.py:183-188`, вне зон, не меняется) видят уже
     подставленное значение.

   Поля `compose_*` при другом раннере — отказ загрузки с именем поля.
   `compose` проходит те же проверки и ветки, что `pytest-own`:
   `project_profile.reported`, `acceptance._own` (или его аналог для
   `compose`), `test_integrity._own_profile`, `workdir`, `machine.path`
   (`targets.py:755-773`). Умолчание `command` (`["pytest"]`) действует и
   в проверках загрузки — в запрете повторов (`targets._check_rerun_ban`,
   `targets.py:1194-1199`) и в правиле `layers`
   (`targets.py:1237-1239`): у записи `compose` без `command` эти
   проверки идут как у команды pytest (решение гейта 6).
2. **Проверка загрузки.** Отказ загрузки, текст которого называет поле:
   нет любого из обязательных полей `compose_file`, `compose_service`,
   `compose_env_file`, `compose_env_template`, `compose_mount`;
   `compose_mount` без пары или с двумя и более парами (решение второго
   круга 4); поле `env` у плоской записи `compose` слоя репозитория
   (решение второго круга 6); путь `compose_file`/`compose_env_file`/`compose_env_template`/левая
   часть `compose_mount` абсолютный или с `..`; правая часть
   `compose_mount` не абсолютна; нет `workdir` (решение гейта 3.2); нет
   `report: junit-xml`; есть `install`,
   `tools` или `checks_local`; есть `env` — проверяется по полю `env`
   раздела `description` (профиля или компонента) до сведения разделов,
   так как после сведения `machine.path` лежит в `env["PATH"]`
   (`targets.py:776-793`); `workdir` или `long_lived_dir` записи не лежит
   под левой частью `compose_mount` (решение гейта 9; отказ запуска
   требования 8 остаётся); путь планки после раскладки не лежит под
   левой частью `compose_mount` в любом случае раскладки (решение гейта
   2.3): при `long_lived_dir` вне `workdir` планка лежит без раскладки в
   `tasks/<id>/acceptance_tests` дерева (`acceptance.py:2068`,
   `plank_layout.py:41-47`) — этот каталог (при любом id задачи) не под
   левой частью — отказ с именем `long_lived_dir`; у компонента `compose`
   с `plank_layout` (`acceptance.py:1277-1301`) каталог `plank_layout` не
   под левой частью — отказ с именем `plank_layout`; `--reruns` или `-p rerunfailures` в
   `report_args`/`select` записи `compose` без `command` — отказ, как у
   pytest (решение гейта 6). `machine.path` при `compose` допустим (у
   компонента — по прежнему правилу единственного компонента) и задаёт
   только `PATH` вызова `docker` (требование 6), в контейнер не идёт.
3. **Поиск `docker` и прогон.** Программу `docker` пульт ищет по `PATH`
   вызывающего (`shutil.which`); не найдена — отказ запуска с именем
   `docker`. Идентификатор прогона `<прогон>` — 8 строчных
   шестнадцатеричных знаков, новый на каждый вызов места. Имя проекта
   Compose — `artel-<id задачи строчными>-<прогон>`, только `[a-z0-9-]`;
   эта форма — единственная, запасной формы без id нет (решение
   четвёртого круга 1).
   Канал id задачи (решение четвёртого круга 1): узел `_report_run`
   (`acceptance.py:806`) и его публичное имя `report_run`
   (`acceptance.py:3706`) получают явный аргумент `task_id`, обязательный
   для профиля `compose`; у прочих профилей он необязателен со значением
   по умолчанию, вызовы и поведение прежние. Все вызывающие места
   `compose` передают id задачи: `acceptance.run_repeat`
   (`acceptance.py:1731`), гейт исходов `outcome_integrity`
   (`orchestrator/advance_gates/outcome_integrity.py:445`, `:736`),

   модуля `acceptance`. Вызов `_report_run` с профилем `compose` без id
   задачи — отказ запуска с текстом, `docker` не вызывается.
   Канал id доводится до всех мест вызова прогона `compose` (решение
   пятого круга 1), чтобы повтор файла с зерном, фоновый `suite-run` и
   `plank-run` долгоживущего файла у `compose` работали, а не отказывали:

     `orchestrator/advance_gates/acceptance.py` передаёт id задачи в вызов

     `task_id`;
   - `acceptance.run_plank` (`acceptance.py:2042`) получает отдельный
     необязательный параметр id задачи для имени проекта Compose
     (например, `compose_task_id`), который раскладку планки не включает
     (решение шестого круга 1). Прежний параметр `task_id` у `run_plank`
     смысла не меняет: он по-прежнему значит «цели лежат в планке задачи
     `tasks/<id>/acceptance_tests`» и включает раскладку
     (`_plank_plan`/`_laid_plank`, `plank_layout.plank_layout`);
     `orchestrator/plank_run.py` передаёт новый параметр в вызов
     `run_plank` долгоживущего файла (`:267-269`) — по-прежнему только
     передача id, `task_id` в этот вызов не передаётся. Источник id имени

   `tests/test_01m5n8asj63zkf3m9etc7a3p5v_plank_layout_names.py:331-373`).
4. **Сборка конфигурации и перекрытие** (ADR-0023, поправка 05.11, п. 2).
   Порядок проверок перед сборкой конфигурации (решение третьего круга
   4): сначала `DOCKER_HOST` не `unix://` (требование 5), затем `git
   ls-files` файла окружения, затем копирование шаблона; отказ на
   раннем шаге — поздние шаги не выполняются.
   До копирования шаблона пульт проверяет, что `compose_env_file` не
   отслеживается git в дереве прогона (`git ls-files --error-unmatch`);
   отслеживается — отказ запуска с именем файла, шаблон не копируется
   (решение гейта 8). Шаблона `compose_env_template` нет в дереве прогона
   (в том числе в копии базы и дереве стороны двустороннего прогона) —
   отказ запуска с именем файла (решение второго круга 6). Затем пульт
   копирует `compose_env_template` в `compose_env_file` дерева прогона
   (перезапись на каждом прогоне).
   Сборка — `docker compose --project-name <имя> --project-directory
   <каталог compose_file в дереве прогона> -f <compose_file в дереве
   прогона> --env-file <compose_env_file в дереве прогона> config
   --format json` (вывод — JSON; опытом не проверено). Вызов `config` —
   с пределом времени `config.COMPOSE_CONFIG_TIMEOUT_SEC` (новая
   константа, 60 с; решение третьего круга 1); ненулевой код, вывод не JSON или превышение
   предела — отказ запуска с текстом вызова, `up`, `run` и `down` не
   зовутся (стенд не поднимался; решение второго круга 2). В собранной
   конфигурации пульт снимает `ports` у каждого сервиса, ставит
   `internal: true` каждой сети, включая неявную `default` (нет в
   конфигурации — добавляет), ставит контейнерам и сетям метки живого
   прогона `artel.run-pid`, `artel.run-host`, `artel.run-started` (pid,
   хост и время старта процесса пульта, ведущего прогон, — тройка
   `lease.process_alive`) и пишет результат одним файлом во временный
   каталог прогона. Стенд поднимается только этим файлом: все команды
   стенда — `docker compose --project-name <имя> --project-directory
   <каталог compose_file в дереве прогона> -f <файл пульта> …`.
5. **Отказы запуска по собранной конфигурации** (проверяются по выводу
   `config`, не по исходному файлу; стенд не поднимается, `up`/`run` не
   зовутся), текст называет сервис, сеть или том:
   - сервис с `network_mode`;
   - сеть с `external: true`;
   - монтирование сокета Docker (решение гейта 4), два правила:
     - безусловно: источник bind-монтирования, равный `/var/run/docker.sock`,
       `/run/docker.sock` или каталогу, их содержащему (`/var/run`,
       `/run`, `/var`, `/`), — отказ с именем сервиса независимо от того,
       есть ли такой путь на машине;
     - сверкой: источник, чей `realpath` равен `realpath` сокета Docker
       или является каталогом, его содержащим; сокет Docker — `realpath`
       пути `unix://` из `DOCKER_HOST` окружения вызова, `realpath`
       сокета текущего контекста Docker пульта (`docker context inspect`)
       и `realpath` `/var/run/docker.sock`, если он есть;
     - обходы (решение второго круга 3; решение третьего круга 3):
       любой именованный том с `driver_opts` у драйвера `local` или без
       указания драйвера — отказ с именем тома, без разбора значения `o`
       и пути (этим закрыты и `o: "bind,ro"`, `o: rbind`); `volumes_from`
       у сервиса — отказ с именем сервиса;
       `secrets` или `configs` с `file:`, указывающим на литерал сокета,
       содержащий его каталог (по безусловному правилу) или на путь, чей
       `realpath` совпадает с сокетом Docker или содержит его (по правилу
       сверки), — отказ с именем секрета или конфигурации;
   - `container_name` у любого сервиса — без условий;
   - явное `name:` сети или тома, не равное `<имя проекта>` и не
     начинающееся с `<имя проекта>_`.
   `DOCKER_HOST` окружения вызова задан и не начинается с `unix://`
   (удалённый демон) — отказ запуска с именем переменной `DOCKER_HOST`,
   до сборки конфигурации (решение гейта 4). Compose-файл проекта пульт
   не правит.
6. **Окружение вызова `docker` вне процесса роли** (ANSWER-1, вопрос 1):
   ровно переменные `PATH`, `DOCKER_CONFIG`, `DOCKER_HOST` (только если
   задан в окружении пульта), `LANG`/`LC_ALL` (если заданы у пульта) и
   `TMPDIR`; `HOME` и прочие переменные пульта не передаются. `PATH` —
   каталоги `machine.path` записи (если задано), затем каталог найденной
   программы `docker` (без разрешения ссылки), затем
   `acceptance._OWN_SYSTEM_PATH_DIRS` (`acceptance.py:156`), без повторов;
   `PATH` вызывающего служит только для поиска `docker`. `DOCKER_CONFIG`
   — заданный у пульта, иначе `<дом Оператора>/.docker`. Подстановка
   `${…}` Compose видит только эти переменные; окружение pytest в
   контейнере — из Compose-файла и файла окружения проекта.
   Правило действует для каждого вызова `docker` места, а не только для
   `docker compose run`/`up`/`down`/`kill`: в том числе для сборки
   конфигурации (требование 4); `os.environ` пульта целиком не
   передаётся ни одному вызову (решение гейта 3.1, в части вызовов
   места). Каталоги `machine.path` входят в `PATH` вызова, относящегося
   к одной записи (место).
7. **Раннер `compose` в процессе роли — отказ** (решение седьмого круга
   2, решение Оператора 05.11; заменяет правило ANSWER-1, вопрос 3, о
   `DOCKER_CONFIG`/`DOCKER_HOST` из окружения процесса роли). Процесс роли
   распознаётся `runner.in_role_environment()` (`runner.py:1364-1381`):
   признак `ARTEL_ROLE` или `HOME`, равный дому роли, в том числе у
   фонового `suite-run`. В нём прогон с раннером `compose` — именованный
   отказ запуска до любого вызова `docker` (в том числе поиска
   конфигурации, `docker context inspect`, `config`, `up`, `run`, `down`)
   с текстом «раннер compose в шаге роли не исполняется — прогон в
   контейнере делают гейты пульта»; конфигурация Docker пульта не
   читается, шаблон в `compose_env_file` не копируется. Вне процесса роли
   — прежнее правило требования 6 (конфигурация Docker пульта). Основание
   (решение Оператора): Docker Desktop открывает виртуальной машине
   `/Users`, роль с Docker читала бы и писала любые файлы Оператора.
8. **Жизненный цикл, отчёт и пути.**
   - Службы, от которых зависит сервис (`depends_on` в собранной
     конфигурации), — `up -d --wait <службы>`; зависимостей нет — `up` не
     зовётся. Провал `up` — отказ прогона с выводом Compose, исход тестов
     не засчитан; после провала `up` — тоже `down -v --remove-orphans` с
     тем же именем проекта (стенд мог подняться частично; решение
     третьего круга 2). `up` идёт с пределом
     `config.COMPOSE_UP_TIMEOUT_SEC` (новая константа, 300 с; решение
     третьего круга 1); превышение — отказ по таймауту, стенд снимается.
   - Прогон — `run --rm -w <образ workdir> <сервис> <command> <цели>
     --junitxml <путь отчёта в контейнере> …`; образ `workdir` — его путь
     по `compose_mount`; `workdir` вне левой части `compose_mount` — отказ
     запуска.
   - Отчёт — `<каталог дерева>/.artel-report/<прогон>.xml` под левой
     частью `compose_mount`; pytest получает путь в контейнере, пульт
     читает файл с машины; итог — по отчёту. После прогона пульт удаляет
     только свой файл отчёта `<прогон>.xml`; каталог `.artel-report` —
     только если он после этого пуст; отчёт параллельного прогона в той
     же рабочей копии (например, фоновый `suite-run`,
     `appendix_tree.py:259-261`) не трогается (решение гейта 7).
     `.artel-report` и `compose_env_file` внесены в `info/exclude` дерева
     прогона (как в `acceptance._link_deps`).
   - Путь машины в аргументах места, лежащий под левой частью
     `compose_mount`, переводится в путь контейнера; не лежащий под ней —
     отказ запуска с именем пути.
   - После прогона — всегда `down -v --remove-orphans` с тем же именем
     проекта (у сервиса без `image:` — с `--rmi local`), в том числе по
     таймауту, отказу после подъёма стенда и исключению внутри прогона.
     По таймауту и исключению перед `down` пульт снимает контейнеры прогона
     `docker compose --project-name <имя> kill` (с тем же `-f` и
     `--project-directory`), чтобы контейнер one-off без `--rm` не держал
     сеть (решение гейта 13; решение второго круга 5). Снятие группы
     процессов пульта сигналом извне стенд не снимает: обработчики
     сигналов `auto` не меняются, остатки ловит строка `doctor` «забытые
     стенды» (часть 2; решение второго круга 5).
   - Снятие стенда (`kill` и `down` вместе) идёт со своим пределом
     `config.COMPOSE_TEARDOWN_TIMEOUT_SEC` (новая константа, 120 с;
     решение третьего круга 1), в том числе после исчерпания предела
     `run`. Превышение предела снятия — запись журнала с именем проекта
     Compose (остатки ловит строка `doctor` части 2) — `store.journal`
     задачи, id которой передан в `_report_run` (решение четвёртого
     круга 1), прогон не висит;
     исход прогона — прежний (по таймауту — прежний отказ по таймауту).
   - Двусторонний прогон и гейт исходов для `compose` идут веткой отчёта
     (`_report_run`), без `-p <плагин пульта>` и `PYTHONPATH` пульта.
9. **Время.** Предел прогона места `compose` — прежний предел места плюс
   `compose_up_down_sec` записи, без него — `config.COMPOSE_UP_DOWN_SEC`
   (новая константа, 300 с: сборка образа 177 с, подъём 6 с, снятие 1 с —
   ТЗ родителя, факт 6). Таймаут снимает и стенд (требование 8).
   Предел вызова `run` — остаток предела места после `up` (решение
   третьего круга 1). Соотношение пределов (решение четвёртого круга 2):
   сборка конфигурации (`config`) и `docker context inspect` входят в
   предел места; `docker context inspect` идёт с пределом
   `config.COMPOSE_CONFIG_TIMEOUT_SEC`, превышение — отказ запуска; предел
   `up` — меньшее из `config.COMPOSE_UP_TIMEOUT_SEC` и остатка предела
   места; если остаток для `run` после `up` не больше нуля — отказ по
   таймауту без вызова `run`, стенд снимается (`kill`, затем `down`).
   Пределы вызовов стенда — именованные константы
   `orchestrator/config.py`: `COMPOSE_CONFIG_TIMEOUT_SEC = 60`,
   `COMPOSE_UP_TIMEOUT_SEC = 300`, `COMPOSE_TEARDOWN_TIMEOUT_SEC = 120`
   (требования 4, 8); тесты подменяют эти константы.
10. **Ключ итога.** Смена любого поля `compose_*` (кроме
    `compose_up_down_sec`), `command` или правила перекрытия меняет ключ
    `acceptance._report_suite_result_key`; правило перекрытия
    представлено в ключе константой модуля `acceptance`, которую меняет
    любая правка правила.
11. **Прежние раннеры.** У `pytest-own` и `pult-pytest` argv, окружение и
    ключ итога прогонов побайтно прежние.
12. **Документация**: `docs/codebase-map.md` регенерирована.
13. **Форма тестов** (ТЗ родителя, «Критерии приёмки», «Безопасность
    тестов»; решения гейта 2, 3, 2.4, 2.6, 3.1).
    Обязательные тесты — без настоящего Docker: программа `docker`
    подменена исполнителем в каталоге `PATH` теста, который записывает
    argv и окружение, отвечает на `config` заданным текстом (в том числе
    зависанием и ненулевым кодом) и пишет отчёт в смонтированный каталог
    дерева. Зависание подменённого `docker` — `exec sleep <n>` в
    исполнителе (без дочернего процесса-внука); тест снимает группу
    процессов в `finally`. Отказы по сокету Docker (требование 5)
    проверяются через ответ `config --format json` подменённого
    `docker`: литералы сокета отказываются без проверки существования
    путей, сверка `realpath` — по сокету-файлу во временной песочнице, на
    который указывает `DOCKER_HOST=unix://…` теста; подмена
    `os.path.exists` и прочих функций модуля не нужна и единственным
    каналом не допускается (решение гейта 2.4). Окружение каждого вызова
    подменённого `docker` тест сверяет так: в `os.environ` теста
    выставлены `HOME` пульта и переменная-метка теста, в записанном
    окружении вызова нет ни того, ни другого (решение гейта 3.1); тест
    вне процесса роли снимает `ARTEL_ROLE` из своего окружения (решение
    второго круга 6). Зависание `config`, `up` и снятия стенда тест
    проверяет с подменёнными константами пределов
    (`COMPOSE_CONFIG_TIMEOUT_SEC`, `COMPOSE_UP_TIMEOUT_SEC`,
    `COMPOSE_TEARDOWN_TIMEOUT_SEC`; решение третьего круга 1), настоящие
    файлы не меняются.
    Необязательные тесты с настоящим Docker — прогон вымышленного
    Compose-файла с образом из локального кэша, без сети, с `down -v` в
    `finally`. Они пропускаются с именованной причиной, если Docker не
    отвечает, нужного образа нет в локальном кэше (`docker image
    inspect`) или выставлена переменная окружения `CI`; проба Docker —
    с пределом времени 10 с (решение второго круга 6). Их вымышленный
    Compose-файл несёт у каждого сервиса `pull_policy: never` — это
    требование к файлу теста, не условие пропуска (решение третьего
    круга 4); сеть и
    скачивание образов исключены.
    Проекты — вымышленные во временной песочнице; `config.ROOT` и
    `DOCKER_CONFIG` — каталоги песочницы; никогда — настоящий клон,
    настоящий локальный слой, настоящий `~/.docker`; в текстах тестов —
    ни имён, ни адресов реальных проектов.

## Критерии приёмки

AC-1. Запись с `runner: compose` и полями требования 1 загружается в `test_profile` и в `components:`; запись `compose` с `machine.path` загружается; без `command` команда в контейнере — `["pytest"]`.

AC-2. Отказ загрузки с именем поля: запись `compose` без `workdir` — отказ с именем `workdir`; `compose` без `report: junit-xml`; путь `compose_file`, `compose_env_file`, `compose_env_template` или левая часть `compose_mount` абсолютный или с `..`; правая часть `compose_mount` не абсолютна; `compose` с `install`, `tools` или `checks_local`; `compose` с `env` в разделе `description`; `workdir` или `long_lived_dir` вне левой части `compose_mount`; `long_lived_dir` вне `workdir`, когда `tasks/<id>/acceptance_tests` дерева не под левой частью `compose_mount`, — отказ с именем `long_lived_dir`; компонент `compose` с `plank_layout` вне левой части `compose_mount` — отказ с именем `plank_layout` (вымышленные записи песочницы); компонент `compose` без `command` с `--reruns` в `report_args`; поле `compose_*` при другом раннере; запись `compose` без каждого из полей `compose_file`, `compose_service`, `compose_env_file`, `compose_env_template`, `compose_mount` — по случаю на поле, отказ с его именем; `compose_mount` без пары и с двумя парами — отказ с именем `compose_mount`; поле `env` у плоской записи `compose` слоя репозитория — отказ с именем `env`. Запись `compose` без `command` после `targets.load` несёт `command` `["pytest"]` (вымышленная запись песочницы), и запрет повторов на ней срабатывает. Профиль `pytest-own` без `command` по-прежнему отказ «нет подполя».

AC-3. Прогон планки профиля `compose`: argv прогона — `docker compose --project-name artel-<id строчными>-<8 hex> --project-directory <каталог compose_file в дереве прогона> -f <файл пульта> run --rm -w <образ workdir> <сервис> pytest <цели> --junitxml <путь в контейнере> …`; путь отчёта в контейнере соответствует `<каталог дерева>/.artel-report/<прогон>.xml` на машине; итог — по отчёту, прочитанному с машины.

AC-4. Сборка конфигурации — `config` с тем же `--project-name` и `--project-directory`, `-f <compose_file>` и `--env-file <compose_env_file>` дерева прогона; перед ней `compose_env_file` перезаписан копией `compose_env_template`. В файле пульта у каждой сети, включая `default`, — `internal: true`, ни у одного сервиса нет `ports`, у контейнеров и сетей — метки `artel.run-pid`, `artel.run-host`, `artel.run-started`.

AC-5. Отказ запуска с именем сервиса или сети, `up` и `run` не зовутся: собранная конфигурация (ответ `config`) несёт `network_mode` у сервиса; сеть `external: true`; bind-монтирование сокета Docker, в том числе источником-ссылкой на сокет и каталогом, содержащим сокет (сокет — файл во временной песочнице, на который указывает `DOCKER_HOST=unix://…` теста); источник `/var/run/docker.sock`, `/run/docker.sock`, `/var/run`, `/run`, `/var` или `/` — отказ без проверки существования этих путей. Канал всех случаев — ответ `config --format json` подменённого `docker`; функции модуля (`os.path.exists` и прочие) не подменяются. `DOCKER_HOST=tcp://…` — отказ запуска с именем `DOCKER_HOST`, `config` не зовётся. Обходы правила сокета — отказ с именем тома, секрета, конфигурации или сервиса: именованный том с `driver_opts` у драйвера `local` или без указания драйвера — по случаю на `o: bind`, `o: "bind,ro"`, `o: rbind`, `type: none` с `device` и `type: tmpfs` с `driver_opts` — отказ с именем тома при любом значении; сервис с `volumes_from` — отказ с именем сервиса; `secrets` или `configs` с `file:` на литерал сокета или его каталог и на путь, чей `realpath` — сокет песочницы; источник bind-монтирования, чей `realpath` — сокет песочницы, на который указывает ответ `docker context inspect` подменённого `docker` при не заданном `DOCKER_HOST`. Подменённый `config` с ненулевым кодом, с выводом не JSON и зависающий дольше предела `config.COMPOSE_CONFIG_TIMEOUT_SEC` (тест подменяет константу малым значением) — отказ запуска с текстом вызова за предел; в записанных argv нет `up`, `run` и `down`.

AC-6. Отказ запуска с именем: `container_name` у сервиса; `name:` сети, не равное имени проекта и без префикса `<имя проекта>_`; такое же `name:` тома; имя вида `<имя проекта>2_db`.

AC-7. Путь машины в аргументах места вне левой части `compose_mount` — отказ запуска с именем пути; путь под ней — в argv переведён в путь контейнера.

AC-8. `down -v --remove-orphans` с тем же именем проекта вызывается при зелёном исходе, красном исходе, таймауте и исключении; у сервиса без `image:` — с `--rmi local`; на таймауте и на исключении внутри прогона порядок argv — `kill` с тем же именем проекта, затем `down -v --remove-orphans`. Провал `up` — отказ прогона с текстом вывода Compose, исход тестов не засчитан, и в argv после `up` есть `down -v --remove-orphans` с тем же именем проекта. С подменёнными константами пределов: зависающий `up` — отказ по таймауту за предел `COMPOSE_UP_TIMEOUT_SEC`, затем `down` с тем же именем проекта; зависающий `down` — прогон завершается за предел `COMPOSE_TEARDOWN_TIMEOUT_SEC`, не висит, в журнале задачи, id которой передан в `_report_run` (`store.journal`), — запись с именем проекта Compose. Соотношение пределов (решение четвёртого круга 2): остаток предела места для `run` после `up` не больше нуля — отказ по таймауту, `run` в argv нет, `kill` и `down -v --remove-orphans` с тем же именем проекта вызваны; предел `up` не больше остатка предела места; зависающий `docker context inspect` (при не заданном `DOCKER_HOST`) — отказ за предел `COMPOSE_CONFIG_TIMEOUT_SEC` (тест подменяет константу малым значением).

AC-9. Последовательные прогоны базы и головы одного места и одновременные прогоны разных процессов получают разные имена проекта Compose; имя — из id задачи строчными, только `[a-z0-9-]`. Имя проекта Compose в argv каждого места `compose` — прогон планки, полный набор, `run_repeat`, двусторонний прогон и гейт исходов (`outcome_integrity`, оба вызова `report_run`, в том числе перепрогон стороны через `_rerun`) — несёт id задачи, переданный аргументом `task_id` (решение четвёртого круга 1); в том числе повтор файла с зерном (`_seed_repeats_escalate` → `run_repeat`), фоновый `suite-run` (`run_full_suite`) и `plank-run` долгоживущего файла (`run_plank`) задачи с профилем `compose` — `docker` подменён временным дублёром, настоящие файлы не меняются (решения пятого круга 1–2). У `plank-run` долгоживущего файла задачи с профилем `compose` имя проекта Compose несёт id задачи, переданный новым необязательным параметром `run_plank` (решение шестого круга 1), а раскладки планки нет: каталог `tasks/<id>/acceptance_tests` в рабочей копии не создаётся и не читается, прогон не падает на его отсутствии. Оба вызова `plank-run` задачи с профилем `compose` — планки (`run_plank` с `task_id`, без `compose_task_id`) и долгоживущего файла (`run_plank` с `compose_task_id`) — дают имя проекта Compose с id задачи (решение седьмого круга 1; `docker` подменён временным дублёром, настоящие файлы не меняются). Вызов `report_run` с профилем `compose` без `task_id` — отказ запуска с текстом, `docker` не вызван. Профили `pytest-own` и `pult-pytest` вызываются без `task_id` прежним образом.

AC-10. Двусторонний прогон (`two_sided`) для профиля `compose` и гейт исходов (`outcome_integrity`) для компонента `compose` идут веткой отчёта: в argv нет `-p <плагин пульта>`, в окружении нет `PYTHONPATH` пульта. Гейт исходов проверяется только на компоненте `compose`: `test_profile` вне границы `in_outcome_bounds` (`orchestrator/advance_gates/acceptance.py:213-218`; решение третьего круга 4).

AC-11. Вне процесса роли (тест снимает `ARTEL_ROLE` из своего окружения) окружение каждого вызова `docker` места, в том числе сборки конфигурации `config`, — ровно `PATH`, `DOCKER_CONFIG`, `TMPDIR`, а также `DOCKER_HOST`, `LANG`, `LC_ALL`, только если заданы у пульта; `HOME` и прочих переменных пульта нет; `PATH` — ровно каталоги `machine.path`, каталог подменённого `docker` и `_OWN_SYSTEM_PATH_DIRS` в этом порядке, без каталогов `PATH` вызывающего; `DOCKER_CONFIG` без значения у пульта — `<HOME пульта>/.docker`.

AC-12. В процессе роли — при заданном `ARTEL_ROLE` и, отдельным случаем, без `ARTEL_ROLE` с домом роли в `HOME` (как у фонового `suite-run`) — прогон места с раннером `compose` завершается отказом запуска с текстом «раннер compose в шаге роли не исполняется — прогон в контейнере делают гейты пульта»; подменённый `docker` не вызван ни разу (записанных argv нет), шаблон в `compose_env_file` не скопирован; при заданных в окружении `DOCKER_CONFIG` и `DOCKER_HOST` — тот же отказ. Без признака роли (тест снимает `ARTEL_ROLE`, `HOME` — не дом роли) тот же прогон идёт и вызывает подменённый `docker` (решение седьмого круга 2; проверка решения, названная в нём «AC-11», лежит здесь — AC-11 этого SPEC держит окружение вызова вне процесса роли; `docker` подменён временным дублёром, настоящие файлы не меняются).

AC-13. После прогона `compose` его файла отчёта нет; пустой каталог `.artel-report` убран; при двух прогонах в одной рабочей копии первый завершившийся не удаляет отчёт второго и каталог с ним. `.artel-report` и `compose_env_file` внесены в `info/exclude` дерева прогона. `compose_env_file`, отслеживаемый git в дереве прогона (вымышленный репозиторий песочницы), — отказ запуска с именем файла, шаблон не скопирован, `docker` не вызван. Шаблона `compose_env_template` нет в дереве прогона (копия базы, дерево стороны двустороннего прогона) — отказ запуска с именем файла, `docker` не вызван. Порядок проверок: при `DOCKER_HOST=tcp://…` — отказ с именем `DOCKER_HOST`, шаблон в `compose_env_file` не скопирован; при отслеживаемом `compose_env_file` шаблон не скопирован.

AC-14. Предел времени прогона места `compose` больше предела того же места без стенда на `compose_up_down_sec` записи, без поля — на `config.COMPOSE_UP_DOWN_SEC`; по таймауту стенд снимается.

AC-15. Смена `compose_file`, `compose_service`, `compose_env_file`, `compose_env_template`, `compose_mount`, `command` или константы правила перекрытия меняет ключ `_report_suite_result_key`.

AC-16. Профили `pytest-own` и `pult-pytest`: argv, окружение и ключ итога прогонов побайтно прежние.

AC-17. Необязательные тесты с настоящим Docker — прогон вымышленного Compose-файла (требование 13) — пропускаются с именованной причиной при каждом из условий: Docker не отвечает на пробу в пределах 10 с; нужного образа нет в локальном кэше по `docker image inspect`; выставлена переменная `CI`. Вымышленный Compose-файл этих тестов несёт у каждого сервиса `pull_policy: never` — требование к файлу теста, не условие пропуска.

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны — 12 (порог 5; `outcome_integrity.py` —
решения четвёртого круга 1 и пятого круга 2,
`advance_gates/acceptance.py`, `suite_run.py`, `plank_run.py` — решение
пятого круга 1; во всех четырёх только передача `task_id`); критериев
приёмки — 17
(порог 10); `budget_usd` $60 ≥ $30.

Материал для решения Оператора — **обоснование монолита**: задача уже
часть 1 деления родителя 01M6P22XBCQS49HE92YGAB25N9 (утверждённого на
гейте SPEC), граница и рамка $60 взяты из подраздела «Деление» родителя.
Дальнейший разрез по зонам оставляет нерабочее промежуточное состояние:
запись `runner: compose` (`targets.py`, `project_profile.py`) без
прогона в `acceptance.py` загружается, но любое место прогона с таким
профилем не исполнимо; прогон без перекрытия и отказов запуска
(требования 4–5) поднимал бы стенд проекта без изоляции сети и меток,
что ADR-0023 (поправка 05.11, п. 2) не разрешает; `two_sided.py` и
`test_integrity.py` — ветки того же признака `compose`, без них
двусторонний прогон и гейт неослабления пошли бы по ветке пульта
(AC-10). Ключ итога (требование 10) и предел времени (требование 9) —
свойства того же прогона.
