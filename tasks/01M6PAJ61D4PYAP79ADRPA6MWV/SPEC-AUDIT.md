# SPEC-AUDIT: Ядро раннера compose

Это третий визит аудита. Прошлый вердикт (SPEC 94e9bb21) назвал пять
отклонений. Оператор ответил на них решениями третьего круга гейта SPEC
1–4, и SPEC вносит их с пометкой «решение третьего круга N». Все пять
прошлых отклонений по содержанию сняты — сверка ниже. Новая существенная
находка одна: не задан канал id задачи в узле прогона `_report_run`. Он
нужен для имени проекта Compose и для записи журнала. Остальные находки
мелкие.

## Пути обхода гейтов

1. **Имя проекта без id задачи.** Без названного канала id исполнитель
   может в узле `_report_run`:
   - взять неточный признак (имя каталога дерева, проект записи);
   - подставить постоянную заглушку для вызовов без id
     (`outcome_integrity._rerun`).

   Тест AC-9 на месте с id (планка, двусторонний прогон) пройдёт, а гейт
   исходов поднимет стенды с именем, которое строка `doctor` части 2 не
   свяжет с задачей. Другой вариант — скрытое состояние модуля, которое
   ставит `components_full_suite`. Его гонки при параллельных задачах в
   одном процессе критерий не ловит.
2. **Запись журнала зависшего снятия.** Носитель не назван: БД-журнал
   задачи, лог прогона или журнал Python. Буквально подходит
   `logging.warning`, который никто не читает. AC-8 («в журнале») такой
   вариант не отличит.

## Вердикт

**concerns.** Пять отклонений прошлого визита сняты решениями третьего
круга 1–4. Ложных фактов в решениях нет: `in_outcome_bounds` сверен по

Новые отклонения:

1. **Канал id задачи в узле `_report_run` не задан.**
   - Где: SPEC.md:115-116 (имя проекта), :248-249 (запись журнала);
     AC-8 :325, AC-9; `acceptance.py:806-808`, `project_profile.py:66-106`.
   - Почему отклонение: `outcome_integrity.py:445`, `:736` — только
     чтение — зовут `report_run` без id. Профили там из
     `component_profiles(target, …)` (:1349), деревья — во временном
     каталоге (:1401). У `acceptance.run_repeat` (:1731) id тоже нет.
   - Что решить Оператору:
     - канал id: поле `Profile` (`compare=False`), которое заполняет
       `project_profile` при выборе профилей задачи, либо явный
       аргумент `_report_run` с правкой вызывающих в зонах;
     - что делать в вызовах без id — например, имя
       `artel-run-<прогон>` и отдельный признак для `doctor`; либо
       внести `outcome_integrity.py` в зоны;
     - носитель «записи журнала» — например, `store.journal` задачи при
       известном id, иначе лог прогона.
2. **Мелкое: соотношение пределов не задано до конца.**
   - Где: SPEC.md:215-218, :256-258.
   - Что не задано:
     - предел `up` (300 с) не ограничен остатком предела места. При
       `compose_up_down_sec` меньше длительности `up` остаток для `run`
       может стать ≤ 0, и исход этого не сказан: отказ по таймауту или
       отказ без запуска;
     - не сказано, входит ли время `config` (до 60 с) в предел места;
     - предел вызова `docker context inspect` (правило сверки,
       SPEC.md:167-170) не назван. Это вызов `docker` вне перечня
       «вызовов стенда», и зависший контекст держит прогон без предела.
   - Что предложить: «остаток ≤ 0 — отказ по таймауту без `run`, стенд
     снимается»; `config` и `context inspect` — внутри предела места
     (`context inspect` — с пределом `COMPOSE_CONFIG_TIMEOUT_SEC`).
