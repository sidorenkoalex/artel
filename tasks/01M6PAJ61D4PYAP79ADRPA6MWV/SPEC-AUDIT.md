отклонения:
- канал id задачи в узле `_report_run`;
- соотношение пределов времени.

Оператор снял оба решениями четвёртого круга 1–2, SPEC вносит их с
пометкой «решение четвёртого круга N». Новая находка вытекает из решения
четвёртого круга 1. Правило «`compose` без `task_id` — отказ» задевает три
места вызова узла вне зон SPEC, у которых id задачи нет. Для `compose`
эти места будут отказывать всегда.

## Пути обхода гейтов

1. **Неявный id в `run_repeat`.** Явного канала в зонах нет. Исполнитель
   может вывести id из имени `cwd` (каталог worktree называется по id
   задачи) или из состояния модуля. На рабочей копии тест AC-9 пройдёт.
   На дереве с другим именем (копия, временный каталог) имя проекта
   Compose получит чужой «id», а строка `doctor` части 2 свяжет стенд не
   с той задачей. Буква решения 1 («явный аргумент») при этом нарушена,
   но AC-9 этого не ловит.
2. **Заглушка `task_id` в `suite_run`/`plank_run`.** Эти файлы вне зон,
   поэтому исполнитель может вовсе не трогать места и оставить для
   `compose` постоянный отказ. AC-9 перечисляет только места `acceptance`
   и гейтов, и такой исход его не нарушает.

## Вердикт

**concerns.** Оба отклонения прошлого визита сняты решениями четвёртого
круга 1–2. Утверждения решений о коде верны: `outcome_integrity.py:445`,
`:736`; `acceptance.py:806-808`; отсутствие ломающихся тестов.

Отклонения:

1. **Канал id задачи не доходит до трёх мест вызова вне зон.** Правило
   «`compose` без `task_id` — отказ» (SPEC.md:121-133; AC-9
   SPEC.md:352) делает эти места для `compose` постоянным отказом:
   - **`run_repeat`.** Сам узел (`acceptance.py:1731`) параметра id не
     имеет. Единственный вызывающий —
     `advance_gates/acceptance.py:174` (`_seed_repeats_escalate`), он
     вне зон (SPEC.md:411). SPEC называет `run_repeat` местом, которое
     передаёт id (SPEC.md:126, AC-9), но канала id в сам `run_repeat` не
     задаёт. Следствие: повтор файла с зерном у `compose` всегда красен,
     и гейт эскалирует задачу ложно (`advance_gates/acceptance.py:680`).
   - **`suite-run`.** `suite_run.py:607`, `:680` (только чтение, ТЗ)
     зовут `run_full_suite` без id. Штатный полный прогон роли для
     `compose` отказывает. Это расходится с SPEC.md:244, где фоновый
     `suite-run` назван параллельным прогоном той же рабочей копии.
   - **`plank-run` долгоживущего файла.** `plank_run.py:267-269` (вне
     зон) зовёт `run_plank` без `task_id`, прогон отказывает.

   Что решить Оператору (варианты):
   - а) внести в зоны с ограничением «только передача `task_id`» файлы
     `advance_gates/acceptance.py` (вызов :174),
     `orchestrator/suite_run.py` (:607, :680) и `orchestrator/plank_run.py`
     (:267-269). Для `run_repeat` — новый необязательный параметр
     `task_id`;
   - б) назвать эти места в «Не входит» как отказ для `compose` в части
     1, с текстом отказа. Для `run_repeat` это значит ложную эскалацию
     гейта — её надо принять явно или запретить долгоживущие файлы с
     зерном у `compose`;
   - в) разрешить для этих мест вывод id из дерева прогона. Это
     противоречит решению 1 («явный аргумент», «без запасной формы»).
2. **Мелкое: объём «только передачи» в `outcome_integrity.py`.**
   `_rerun` (`outcome_integrity.py:430`) id не получает. Передача требует
   нового параметра `_rerun` и правки его вызовов :757 и :972.
   Формулировку SPEC.md:128-129 и :408-410 стоит понимать как «передача
   `task_id` до вызовов `report_run`, включая параметр `_rerun`». Иначе
   гейт неослабления по зонам (diff) может счесть правку сигнатуры
   выходом за мандат.
