# SPEC: Очередь зоны решает старт

## Контекст
Часть 2 деления задачи 01M4JASKTKX6XYG5P2SACJYJH7 («Порядок старта в
очереди зоны»). Сегодня первый шаг разработчика пускает только занятость
зоны: `orchestrator/zone_lock.py::blocking_conflict` (~398) и `claim`
(~459) решают по `_occupies` (~349) и не учитывают ни других ожидающих
задач, ни `queue_order` (~567), ни `merge_after`. Освободившуюся зону
берёт тот, чей опрос пришёл первым: 05.10 часть 3 этапа 3 (зависящая от
части 2) заняла зону раньше части 2 — взаимная блокировка; после мержа
01M462QACE зону взяла задача на позиции 4. `queue_position` (~590)
считает конкурентами только задачи с ТОЧНО тем же путём конфликта
(`conflict[0] == path`, ~609) — вложенные зоны (`orchestrator/` и
`orchestrator/ci.py`) попадают в разные очереди. `cmd_zone_reorder`
(~617) пишет `zone_queue_position` и печатает «переставлена», в том числе
без аргументов, но старт не решает.

Термины: «ожидающая задача» — задача в `in_dev`, которая ещё не занимает
свои зоны в текущем пребывании (`_occupies` ложно), т.е. та, кого сегодня
проверяет `blocking_conflict`; «пересекающиеся зоны» — собственные зоны
задач (без общих зон), пересекающиеся с учётом вложенности путей
(`_paths_overlap`, ~204).

## Требования

1. Зону, которую никто не держит (ни одна задача с пересекающейся зоной
   её не занимает в смысле `_occupies`), получает первая по очереди
   (требование 2) задача среди ожидающих задач того же проекта с
   пересекающимися зонами; пересечение — с учётом вложенности путей
   (`_paths_overlap`). Остальные ожидающие получают именованный отказ,
   текст которого содержит «ждёт очереди зоны: впереди <id>», где `<id>`
   — задача, стоящая впереди.
2. Порядок очереди: явная позиция Оператора (`zone-reorder`,
   `zone_queue_position`) главнее всего; без неё — зависимость раньше
   зависящей задачи (топологический порядок по `merge_after`); затем
   нынешние ключи `queue_order` (момент approve SPEC, затем
   `updated_at`).
3. Задача, у которой незавершённая (не `done`) зависимость `merge_after`
   ждёт пересекающуюся зону, зону не получает: отказ, текст которого
   содержит «ждёт зону ради зависимости <id>», где `<id>` — эта
   зависимость.
4. Ожидающая задача, которая сама не может стартовать, очередь не
   держит: при выборе первой по очереди (требование 1) она
   пропускается. Не может стартовать — цикл `run`/`auto` по ней не идёт
   (нет живого lease), задача на паузе (`pause`), задача в эскалации,
   задача, сама получающая отказ требования 3.
5. `zone_lock.queue_position`, вывод `status` (`orchestrator/catalog.py`)
   и проверка `doctor` (`orchestrator/doctor/`) показывают ту же очередь,
   что решает старт по требованиям 1–4: тот же состав конкурентов (с
   учётом вложенности путей) и тот же порядок. Ожидающая задача, которая
   очередь не держит (требование 4), из показа НЕ выпадает: она остаётся
   в очереди на своём месте порядка требования 2 и входит в «всего»
   (`queue_position` возвращает ей позицию, как и прочим), а строки
   `status` и `doctor` несут у неё после «очередь N/M» пометку «не держит
   очередь». Зону при этом получает первая по позиции задача без такой
   пометки. При занятой зоне конфликт и отказ ожидающей по-прежнему
   называют держателя зоны («занята <id>»), как сегодня.
6. `zone-reorder` без аргументов — отказ с подсказкой формы вызова
   (`zone-reorder <id1> <id2> ...`): ни одна `zone_queue_position` не
   меняется, «переставлена» не печатается.
7. Новые отказы требований 1 и 3 доходят до цикла ожидания зоны
   `auto._wait_for_zone` и до отказа `run` (`runner`) через интерфейс
   `zone_lock.blocking_conflict`/`claim`, без правки `orchestrator/auto.py`
   и `orchestrator/runner.py`.
8. Смена ожидания существующих тестовых методов `tests/` — только
   перечнем раздела SPEC «Меняемое поведение» (инвариант 38).

## Критерии приёмки

AC-1. Зона свободна, две задачи A и B в `in_dev` с живым циклом ждут
вложенные зоны (`orchestrator/` и `orchestrator/ci.py`), SPEC задачи B
утверждён раньше SPEC задачи A: `claim` задачи A отказывает текстом с
«ждёт очереди зоны: впереди B», `claim` задачи B проходит.

AC-2. В условиях AC-1 `zone-reorder A B` меняет исход: `claim` задачи A
проходит, `claim` задачи B отказывает текстом с «ждёт очереди зоны:
впереди A». То же — при одинаковой (не вложенной) зоне.

AC-3. Цепочка из трёх задач на одной зоне (C зависит от B, B от A по
`merge_after`; порядок approve SPEC обратный — C, B, A; все в `in_dev` с
живым циклом, зона свободна): первой зону получает A, затем (после
освобождения зоны задачей A) B, затем C; ни на одном шаге при свободной
зоне не остаётся так, что ни одна из задач не может её получить.

AC-4. Задача C с незавершённой зависимостью `merge_after` = A, которая
ждёт пересекающуюся зону, получает отказ с «ждёт зону ради зависимости
A» — в том числе когда `zone-reorder` поставил C впереди A; в этом
случае зону получает A.

AC-5. Первая по очереди ожидающая задача без живого цикла, на паузе или
в эскалации очередь не держит: `claim` следующей по очереди задачи с
живым циклом проходит (по одному случаю на каждое из трёх условий).

AC-6. Для набора ожидающих задач с вложенными зонами порядок, который
показывают `queue_position`, `status` и `doctor`, совпадает с порядком,
в котором `claim` пропускает задачи: первая по позиции задача без
пометки «не держит очередь» — та, чей `claim` проходит; вложенные зоны
считаются одной очередью (общее «всего»). Если первая по позиции задача
очередь не держит (условия AC-5), она остаётся в показе на позиции 1 с
пометкой «не держит очередь», а `claim` проходит у следующей по позиции
задачи без пометки.

AC-7. `zone-reorder` без аргументов завершается отказом с подсказкой
`zone-reorder <id1> <id2> ...`, не печатает «переставлена» и не меняет
`zone_queue_position` ни одной задачи.

AC-8. Отказ «ждёт очереди зоны: впереди <id>» доходит до `run` и до
ожидания зоны `auto`: `run` ожидающей задачи не впереди очереди при
свободной зоне не запускает шаг разработчика и пишет в журнал
`zone_lock.REFUSAL_ACTION`; `auto._wait_for_zone` такой задачи не
выходит из ожидания, пока задача впереди не заняла зону и не
освободила её.

## Оценка объёма и деление

Сработавший сигнал: `budget_usd` ≥ $30 (рамка ТЗ — $40). Возможный
второй — зона задевает механизм замка зон, на который опираются записи
`docs/invariants.md`. Число собственных файлов зоны — три
(`orchestrator/zone_lock.py`, `orchestrator/catalog.py`,
`orchestrator/doctor/`; `tests/` и `docs/codebase-map.md` — общие зоны),
критериев — 8: класс «до 10 критериев, до 4 файлов» (~$40).

Решение: **монолит** (материал для решения Оператора). Задача уже
является частью деления родителя 01M4JASKTKX6XYG5P2SACJYJH7. Правило
старта (требования 1–4) и показ очереди (требование 5) — одна механика:
выделенный отдельно показ без правила старта показывал бы порядок,
который старт не соблюдает (нынешний дефект `queue_position`), а правило
старта без показа давало бы Оператору позиции, расходящиеся с тем, кто
реально стартует; в обоих промежуточных состояниях AC-6 красен.
Требование 6 (`zone-reorder` без аргументов) — несколько строк в той же
`zone_lock.py`, отдельная задача стоила бы дороже собственного объёма.
