## Замечания

- major — `scripts/guard.py:2218-2225` (`_FixtureScope._data`: `_HelperScope(module, None)`), а также `scripts/guard.py:2335` (`_changed_fixture_names`). Помощник фикстуры, импортированный из другого модуля `tests/` (`from tests.helpers_x import make`; `return make()`), в запись данных фикстуры не попадает. Требование 3 SPEC прослеживает «помощника, вызванного фикстурой» на один уровень. Исключены только второй уровень и константы модуля, источник помощника не ограничен. Требование 4 требует, чтобы записи доходили «так же, как сейчас записи помощника первого уровня», а у тестов прежний `_HelperScope(own, modules)` идёт в импортированные модули `tests/`. Комментарий кода ссылается на «Не входит» SPEC, но этого исключения там нет. Сценарий: фикстура файла теста возвращает `make()`, где `make` взят из `tests/helpers_x.py`. Правка `return 5` → `return 500` в помощнике не даёт ни различия записей (проба: записи теста на обеих сторонах одинаковы), ни имени в `weakened_helpers` для `tests/helpers_x.py` (проба: `set()`). Гейт неослабления такую правку не видит. Это как раз маршрут «данные в общем модуле», ради которого вводится А1 (`tests/fixtures.py` с помощниками). Предложение: прослеживать помощника фикстуры через `_HelperScope(module, self.modules)` (с происхождением помощника чужого модуля). Чтобы поиск вызывающих вне диффа нашёл тест, `weakened_helpers` при смене тела обязан назвать такого помощника, на которого ссылается фикстура (в любом модуле). Если считаешь ограничение «только свой модуль» намеренным, эскалируй вопрос Оператору: в SPEC его нет. Тест на этот сценарий — в `tests/` (свой файл разработчика).
