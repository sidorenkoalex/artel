Расхождения:

- А2. Остаток круга 1, п. 1: записи фикстуры доходят до `method_literal_keys` (требование 4). Значит, проверка `approve` пропустит строку «Меняемое поведение» с литералом фикстуры в «было» (guard.py:5256–5268, `behavior_change_refusals`). Гейт же такую находку объявлением не снимает (требование 4, AC-10). Получается мёртвый путь: объявление проходит проверку, но ничего не даёт. Вреда нет, но Оператора на гейте это может запутать. Справочно.

  - `_constant_roles` :2279, `long_lived_errors_from_files` :3982.
- `_helper_callers` — `orchestrator/advance_gates/test_integrity.py:788`.
- Роль литерала. Записи без роли `_strictness_sign` даёт `SIGN_UNRATED` (guard.py:2390–2392). Любой признак `_change_reason` относит к ослаблению (test_integrity.py:1132–1133), объявление его не снимает. Мандат на путь снимает: путь файла теста — через `Finding.mandate_elements`; путь файла фикстуры — через `_helper_paths`, при происхождении из одного файла (test_integrity.py:649–658). Исход AC-10 достижим без правки test_integrity.py.
- Модули стороны грузятся по пути (`_side_modules`, test_integrity.py:771–778). Значит, `tests/fixtures.py`, который тест не импортирует, guard может прочитать для своей стороны. AC-1, сценарий 2, исполним.
- Исключение `lint_base` — по `test_lint.top_level_functions`, ключ «Класс::метод» или «функция» (`_method_dumps`, guard.py:4048–4056; `lint_errors_from_files`, :4059–4086). Фикстуры и `pytest_generate_tests` — функции верхнего уровня, ключ у них есть. Для модульного оператора нужен новый ключ «<модуль>», как и задаёт SPEC.

Неточно или не названо:
- Б1. Код потребителей не принимает узел записи-литерала. По SPEC нормальная форма записи фикстуры — «`ast.dump` узла литерала» (требование 3), а «правила потребителей прежние» (требование 8). Но потребители `_assertion_records` предполагают, что узел — утверждение:
  - `_expectation_pairs` вызывает `_constant_roles(base_node)` (guard.py:2446). Для узла не-`Assert` тот вызывает `_assertion_kind(node)` (:2342), а `_assertion_kind` читает `node.func` (:2220). На `ast.Constant`/`ast.List` это `AttributeError`, то есть сбой гейта неослабления ровно на сценарии AC-10 (`return 5` → `return 500`);
  - `_other_change_sign` вызывает `_assertion_kind` для всех свободных кандидатов (:2269–2270). Если у метода хоть одно своё утверждение осталось без пары, а среди добавленных записей есть запись фикстуры, будет тот же сбой.

  Разработчик это увидит на первом же тесте. Но SPEC не говорит, как поступать с записью фикстуры в этих местах: какой у неё «вид» (`_assertion_kind`) и может ли она сопоставиться с утверждением. Отсюда вопрос В1 вердикта.
- Б2. Что значит «ключ записи». В коде первый элемент записи `_assertion_records` — это и нормальная форма, и ключ мультимножества (`test_assertions`, guard.py:1964; `assertion_changes`, :2484–2498). SPEC называет ключом «(файл, имя фикстуры, порядковый номер литерала)», а нормальной формой — `ast.dump` литерала, но не говорит, что из этого идёт в первый элемент записи. Три прочтения:
  - (1) только `ast.dump`. Обмен значениями внутри фикстуры (`a = 5; b = 7` → `a = 7; b = 5`) или между двумя фикстурами одного теста не меняет мультимножество, находки нет (Е1);
  - (2) только (файл, имя, номер). Смена значения не видна. Это прочтение ловит AC-10;
  - (3) (файл, имя, номер, `ast.dump`). Видны и смена значения, и обмен. Вставка литерала в начало фикстуры сдвигает номера, и находка выйдет на каждом следующем литерале (строже).

  Ни один AC не различает (1) и (3).
- Б3 (справочно). Адреса SPEC «`assertion_changes` (`scripts/guard.py:2476`)» и «`method_literal_keys` (`scripts/guard.py:5263`)» указывают на строку вызова `_assertion_records`, а не на `def` (:2456 и :5256). Найти по ним можно, не отклонение.

## Пути обхода гейтов
- Е1. Обмен значениями литералов фикстур (Б2, прочтение 1). Если первый элемент записи — только `ast.dump` литерала, то обмен значениями между двумя присваиваниями одной фикстуры или между двумя фикстурами одного теста не меняет мультимножество. Например, `limit = 5; expected = 500` → `limit = 500; expected = 5`. `assertion_changes` не даёт находки (guard.py:2484–2492), храповик не убывает. SPEC называет ключ с порядковым номером, но не связывает его с первым элементом записи, и ни один AC обмен не проверяет.
- Е2. Нелитеральные данные фикстуры. Записываются только литералы, которые возвращаются или присваиваются (требование 3, буква ТЗ). Значения внутри выражений в запись не попадают: `return Config(limit=5)` → `Config(limit=500)`, `return make(5)`, `request.cls.x = 5`, `x += 5`. Поиск вызывающих запустится, потому что `weakened_helpers` назовёт фикстуру по телу (требование 5). Но записи вызывающих по обе стороны одинаковы, и находки нет (test_integrity.py:985–990 → `_assertion_observation`). Это в границах ТЗ. ADR-0027 п. 3 говорит, однако, что «правка фикстуры, которой пользуется залоченный тест, видна гейту». Вариант закрыть: писать в запись все константы тела фикстуры (`ast.walk`), а не только возвращаемые и присваиваемые. Это решение Оператора, а не аналитика. Не определено и само слово «присваиваемые»: относятся ли к ним `AnnAssign`, `AugAssign`, присваивание атрибуту.
