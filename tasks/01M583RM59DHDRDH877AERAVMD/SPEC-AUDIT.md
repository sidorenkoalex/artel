  `kwargs.setdefault("start_new_session", True)`), то есть процесс

  на :2348 его не достаёт вовсе. Механизм сироты suite в этом окне
  другой (это скорее класс строки бэклога 01M4XVD8GF — группы ролей не
  снимаются). Пункт вне зон и закрыт ANSWER-1, но строка бэклога,
  которую Оператор заведёт по этому тексту, унаследует неверный
  механизм.
- (б-2) SPEC.md:36: `artel.py:1597` — «не процессы канарейки». Это
  `_detach_canary` (artel.py:1587-1598) — отвязанный запуск самой команды
  `canary`. Вывод «не относится» верен (отвязанный процесс канарейки по
  замыслу живёт независимо от запустившего), но основание неверно.
- (б-3) Способ SPEC.md:44-46 отвергает `pthread_sigmask` тем, что ведение
  унаследует блокировку и SIGTERM снимет его только через SIGKILL. Но
  действующий обработчик `interrupt` первым делом ставит
  `signal.SIG_IGN` (canary.py:2743), а `SIG_IGN` наследуется через
  fork+exec. Если откладывающий обработчик, по образцу действующего,
  поставит `SIG_IGN` на сигнал, пришедший в Python-части `Popen` до
  fork (окно SPEC начинается «от вызова `subprocess.Popen`»), ведение и
  его потомки родятся с игнорируемым SIGTERM/SIGHUP — ровно тот дефект,
  ради которого отвергнута маска (снятие только SIGKILL через
  `GROUP_TERMINATE_GRACE_SEC` = 3 с, liveness.py:46). SPEC не
  запрещает это устройство, оставляя его разработчику (SPEC.md:47).

## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да | нет откладывания (база) → ведение живо; отложенный сигнал поднят вне защищённого `try` → ведение живо; сигнал отложен и проглочен → ведение `sleep 90` не снято, `communicate(timeout=20)` падает; строка без имени сигнала / код ≠ 128+n → `assertIn`/код. Не ловит: (а-1) потерю отложенного сигнала на ветке исключения `Popen`; (б-3) `SIG_IGN` до fork — точка `os.kill` стоит ПОСЛЕ создания процесса. |
| AC-2 | да, с оговоркой | нет откладывания SIGINT → `KeyboardInterrupt` из `Popen` мимо защищённого ожидания → ведение живо. Оговорка: если процесс прогона тестов наследует `SIGINT=SIG_IGN` (фоновый запуск без job control), Python в дочернем `_CHILD` не ставит `default_int_handler`, `os.kill(SIGINT)` ничего не делает — тест краснеет таймаутом, не по поведению. SPEC не требует от теста явно восстановить обработчик SIGINT в дочернем процессе; это риск недетерминизма, противоречащий требованию 5. |

## Пути обхода гейтов
- (е-1) Тест раннего окна, вероятно, повторит `_CHILD` с `os.kill` в
  подменённом `Popen`. Если автор теста параметризует общий `_CHILD`/
  `launch_signalled` (tests/...canary_lifecycle.py:23-57, :112-137),
  существующие ac1-ac3 поедут через изменённый помощник; SPEC фиксирует
  только предел 20 с помощника (SPEC.md:82), но не то, что точка сигнала
  существующих методов (после возврата `Popen`, во время ожидания)
  остаётся прежней. Буквально «те же методы и утверждения» соблюдены, а
  ac1-ac3 могли бы перестать проверять сигнал ВО ВРЕМЯ ожидания.
- (е-2) Требование 3 «`OSError` → код 127 как сейчас» допускает
  реализацию, теряющую отложенный сигнал на этой ветке (см. а-1); ни
  один AC её не ловит.
- (е-3) AC-4 «открытых каналов» без наблюдаемого признака выполняется
  любым тестом, вызвавшим `communicate`.
