# QUESTIONS: Канарейка: сигнал остановки в момент запуска процесса ведения задачи не оставляет его живым

## Контекст обхода мест (ТЗ, требование 3)

- `orchestrator/canary.py:2333-2335` (`_drive_in_clone`) — процесс ведения
  в своей сессии. Окно есть: `try` вокруг `Popen` ловит только `OSError`
  (:2336), защищённое ожидание начинается на :2338. Место в зоне — пойдёт
  в требования. Способ, который я заложу в SPEC: отложенная доставка
  сигнала флагом на участке «`Popen` … присваивание `proc`», с подъёмом
  отложенного сигнала уже внутри защищённого ожидания. Маску
  `pthread_sigmask` не беру: ребёнок наследует её через exec, и SIGTERM от
  `liveness.terminate_process_group` не снял бы ведение до перехода на
  SIGKILL.
- `orchestrator/suite_run.py:801-805` (`cmd_suite_run`) — группа прогона
  тестов (suite), её снимает уборка клона `canary.py:1236-1244` по pid из
  `run.json`. pid пишется в `run.json` только на `suite_run.py:810`
  (после `_hand_lock`, :809). Когда канарейка снимает группу ведения
  (`canary.py:2348`, SIGTERM всей группе) и попадает в окно :801–:810,
  команда suite-run, состоящая в этой группе, умирает раньше записи
  `run.json`. Сессия suite остаётся жить, а уборка верхнего уровня её не
  находит. Класс окна тот же, но место **вне зон** задачи. По ТЗ
  (требование 3) это эскалация до SPEC, отсюда вопрос 1.
- `acceptance.py:277/1821/1870`, `runner.py:92` — группы прогонов и ролей
  внутри ведения. По ТЗ они не входят (строка бэклога 01M4XVD8GF).
  `artel.py:984/1597` не относятся к канарейке.

## Вопросы

1. **Окно группы suite-run (`orchestrator/suite_run.py:801-810`) лежит вне зон. Как с ним поступить?**
   - A) Расширить зоны на `orchestrator/suite_run.py`: требование «pid группы suite виден уборке канарейки при любом моменте снятия группы ведения» плюс отдельный детерминированный тест этого окна.
     - ломается: ничего из наблюдаемого; меняется порядок записи `run.json`/доставки сигнала в `cmd_suite_run`
     - ослабляется: ничего; сейчас свойство держится только вне окна (`suite_run.py:810`, `canary.py:1238-1244`)
     - цена: +1 файл зоны, +2–3 критерия, бюджет ~$40 вместо ~$35; затронут общий модуль suite-run, которым пользуются и роли
     - чьё решение: Оператор (смена зон ТЗ)
   - B) Зоны не менять: SPEC закрывает только окно `canary.py:2333-2338`, окно suite-run уходит в «Не входит» с адресом и предложением отдельной строки бэклога.
     - ломается: ничего
     - ослабляется: ничего нового; известное окно `suite_run.py:801-810` остаётся открытым (сирота suite при попадании снятия в окно)
     - цена: в рамке $35; отдельная задача потом
     - чьё решение: Оператор
   - C) Зоны не менять, а закрыть окно suite из `canary.py`: уборка клона ищет сессии suite не только по `run.json`, но и по признаку принадлежности клону (например, по таблице процессов: cwd/argv под каталогом клона).
     - ломается: уборка начинает зависеть от `ps`/`lsof`-подобного чтения таблицы процессов (платформенный код)
     - ослабляется: точность адресации — снимается всё, что похоже на процесс клона, а не записанный pid (`canary.py:1238-1244` сейчас адресует ровно по pid)
     - цена: ~$40, хрупкий тест, риск снять чужой процесс
     - чьё решение: Оператор
   - дефолт: B — ТЗ прямо держит зону `orchestrator/canary.py` + `tests/`, а B не трогает общий модуль suite-run и не расширяет рамку.

2. **«Прерывание с терминала» (SIGINT) в требовании 1: какой исход нужен в раннем окне?** Сейчас `_interrupt_on_signal` (`canary.py:2737-2752`) обрабатывает только SIGTERM и SIGHUP. Ctrl-C во время ожидания идёт `KeyboardInterrupt`: группа ведения снимается (`canary.py:2344-2350`), но строка прогона не пишется (`canary.py:2812` ловит только `CanaryInterrupted`). Требование 1 («прогон записан незелёным с точным именем сигнала, код `128 + номер`») расходится с критерием «сигнал во время ожидания — исходы и тексты прежние».
   - A) SIGINT в раннем окне даёт тот же исход, что SIGINT во время ожидания сегодня: группа ведения снята и дождана, клон и origin удалены, `KeyboardInterrupt` уходит наверх, строки прогона нет. Запись с именем сигнала и код `128 + номер` — только для SIGTERM/SIGHUP.
     - ломается: ничего; поведение SIGINT во время ожидания прежнее
     - ослабляется: ничего; запись исхода для SIGINT как не было, так и нет
     - цена: в рамке
     - чьё решение: Оператор
   - B) Добавить SIGINT в `_interrupt_on_signal`: и в раннем окне, и во время ожидания Ctrl-C пишет строку «оборвана сигналом SIGINT», вердикт red, код 130.
     - ломается: исход SIGINT во время ожидания меняется (строка в БД, текст, путь выхода через `SystemExit(130)` вместо `KeyboardInterrupt`). Это противоречит критерию ТЗ «исходы и тексты прежние»
     - ослабляется: ничего
     - цена: +1–2 критерия, в рамке
     - чьё решение: Оператор
   - дефолт: A — единственное прочтение, совместимое с критерием «сигнал во время ожидания — исходы и тексты прежние».
