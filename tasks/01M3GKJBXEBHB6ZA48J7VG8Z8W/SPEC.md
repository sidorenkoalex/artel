# SPEC: answer — проверка строки мандата при записи и подсказка approve после ответа

## Контекст

Строка мандата Оператора («Расширение зон разрешено: …», «Ослабление
тестов разрешено: …») разбирается сегодня в трёх местах независимо:
команда `answer` (`orchestrator/answer.py`), гейт зон и гейт
неослабления тестов. Элемент, не совпавший ни с одним путём, гейтом
молча не засчитывается — ни при записи файла ответа, ни при проверке
отказа нет. Прецедент 26.09: мандат «Расширение зон разрешено:
orchestrator/artel.py — только разбор аргументов…» в ANSWER-1 задачи
01M3FQ3J молча не сработал (элемент после пути — пояснение, не путь).
Вторая половина того же прецедента: ответ в `escalated` эскалацию не
снимает — её снимает `approve`, а `answer` об этом не сообщает, и цикл
`auto` останавливается сразу после ответа. Источник — строка бэклога
26.09 «answer: проверка строки мандата и подсказка approve», условие
старта (мерж 01M3FQ2V) наступило.

## Требования

1. Один разбор строки мандата на все три места: функция в
   `orchestrator/advance_gates/` — «маркер → список элементов» (строка
   со `strip`, отсечение префикса-маркера, деление по запятым,
   отбрасывание пустых элементов). Её зовут `orchestrator/answer.py`,
   `orchestrator/advance_gates/zones.py` и
   `orchestrator/advance_gates/test_integrity.py`; собственного разбора
   «маркер → элементы» ни один из трёх модулей больше не несёт. Правила
   накопления элементов по строкам и по файлам ANSWER остаются за
   потребителями — меняется только разбор одной строки. Поведение на
   валидных строках не меняется. Второй вариант размещения из ТЗ
   (`scripts/guard.py`) не берётся: этот путь в зоны задачи не входит.
2. Проверка при записи: `answer` до коммита ANSWER разбирает все строки
   мандатов файла (оба маркера) и отказывает именованно, если
   а) элемент содержит пробел либо не похож на путь репозитория;
   б) для мандата зон — элемент не существует в дереве кодовой ветки
   задачи ни файлом, ни каталогом (с учётом `/` на конце);
   в) для мандата ослабления — путь не под `tests/` либо нарушена форма
   `путь::имя`;
   г) после маркера пустой список элементов.
   Отказ называет строку, элемент и причину. При отказе файл ANSWER не
   создаётся: ни коммита в артефактную ветку, ни записи в журнал.
3. Подсказка после ответа: в состоянии `escalated` успешный `answer`
   печатает строку «дальше: artel.py approve <id> (снятие эскалации)» и
   пишет в журнал задачи запись «ANSWER создан, ждёт approve».
4. Документация `docs/operator-gates.md`: формат строки мандата (только
   пути через запятую, пояснения — отдельным абзацем), проверка при
   записи и шаг `approve` после ответа в `escalated`.
5. Тесты в `tests/`: отказ на элемент с тире/пояснением, на
   несуществующий путь, на путь вне `tests/` для мандата ослабления, на
   пустой список; валидный мандат с отступом проходит; три потребителя
   разбирают одну и ту же строку одинаково; подсказка и запись журнала в
   `escalated`. Существующие тесты не правятся в ожиданиях и не
   ослабляются.

## Критерии приёмки

AC-1. Разбор строки мандата живёт в одной функции модуля
`orchestrator/advance_gates/`; `orchestrator/answer.py`,
`orchestrator/advance_gates/zones.py` и
`orchestrator/advance_gates/test_integrity.py` зовут её и своего разбора
«маркер → элементы» не содержат. На одной и той же строке мандата все
три потребителя получают один и тот же список элементов.

AC-2. `answer` с файлом, где элемент мандата содержит пробел (тире или
пояснение внутри элемента — строка прецедента «Расширение зон
разрешено: orchestrator/artel.py — только разбор аргументов»),
отказывает; текст отказа называет строку, элемент и причину; `ANSWER-n.md`
на артефактной ветке не появляется и записи в журнале задачи нет.

AC-3. `answer` с мандатом зон на путь, которого нет в дереве кодовой
ветки задачи, отказывает именованно; мандат на существующий файл и на
существующий каталог (в том числе записанный с `/` на конце) проходит и
ANSWER коммитится.

AC-4. `answer` с мандатом ослабления на путь вне `tests/` отказывает
именованно, как и на нарушенную форму `путь::имя`; мандат вида
`tests/<файл>.py` и `tests/<файл>.py::<Класс>::<метод>` проходит и
ANSWER коммитится.

AC-5. `answer` с маркером мандата, после которого нет ни одного
непустого элемента, отказывает именованно; ANSWER не создаётся.

AC-6. Валидная строка мандата с ведущими пробелами (отступом) проверку
проходит: ANSWER коммитится, элементы разобраны те же, что и без
отступа.

AC-7. В состоянии `escalated` успешный `answer` печатает строку
«дальше: artel.py approve <id> (снятие эскалации)» и пишет в журнал
задачи запись «ANSWER создан, ждёт approve».

AC-8. `docs/operator-gates.md` несёт формат строки мандата (только пути
через запятую, пояснения — отдельным абзацем), описание проверки при
записи и шаг `approve` после ответа в `escalated`.

AC-9. Полный прогон `tests/` зелёный; `tests/test_answer.py`,
`tests/test_answer_gate.py`, `tests/test_answer_branch_reads.py`,
`tests/test_zones_gate.py`, `tests/test_test_integrity_gate.py` зелёные
без правки существующих ожиданий, ни один тест не удалён, не
переименован и не ослаблен.

## Оценка объёма и деление

Прогноз диффа: 22 КиБ

Сработавшие сигналы: «число затрагиваемых модулей/файлов» и «затронут
инвариантный механизм» — оба от перечня путей в тексте. Перечень набран
в основном путями режима «только чтение» (`orchestrator/artel.py`,
`orchestrator/fsm.py`, `scripts/guard.py`, `orchestrator/store.py`):
правятся четыре адреса — `orchestrator/answer.py`, два модуля
`orchestrator/advance_gates/` плюс новый общий узел там же,
`docs/operator-gates.md` и `tests/`. Инвариантный механизм задет
чтением: мандаты зон (инвариант 34) и неослабления тестов (инвариант
38) меняют не семантику, а место разбора строки и момент проверки.

`budget_usd: 25` — рамка ТЗ Оператора. Калибровка на 9 AC-n и 4 файлах
зон ориентирует на ~$40 и на гейте напечатает «рамка ниже калибровки»:
разрыв не от объёма, а от дробности разметки — восемь из девяти
критериев проверяют один и тот же вход `answer` разными строками
мандата. Планка поднимается командой `budget`, если ревью потребует
третьей итерации.

Решение — **монолит**. Требование 1 атомарно по построению: общий узел
без переключённых на него потребителей — мёртвый код, а перевод одного
потребителя без двух других оставляет два разбора вместо одного, то
есть ровно тот дефект, ради которого задача заведена. Требование 2
опирается на этот же узел (проверка разбирает те же строки тем же
разбором) и без него мержится только вместе со своей копией разбора.
Требование 3 — две строки в той же функции `_cmd_answer`, что и
проверка требования 2; отдельной частью оно дало бы задачу дешевле
одного шага роли. Требования 4-5 — документация и тесты той же правки,
отдельно не мержимы с зелёной планкой.

## Не входит

- Новые виды мандатов — проверяются только два существующих маркера
  («Расширение зон разрешено:», «Ослабление тестов разрешено:»).
- Изменение семантики гейта зон и гейта неослабления тестов: что именно
  мандат покрывает и как гейт на это реагирует, остаётся прежним.
- Автоматический `approve` после ответа: флаг `--continue` — следующей
  задачей, когда `orchestrator/artel.py` свободен (разбор аргументов —
  зона задачи 01M3FQ3J в полёте).
- Проверка элементов при записи в команде `zones-extend`: требование 2
  названо только для `answer`.
- Только чтение (не менять): `orchestrator/artel.py` (зона задачи
  01M3FQ3J в полёте, usage не меняется), `orchestrator/fsm.py`,
  `scripts/guard.py` (второй вариант размещения общего разбора из ТЗ —
  потребовал бы расширения зон), `orchestrator/store.py`,
  `docs/operator-session.md` (зона задачи 01M3FQ3J в полёте),
  `docs/backlog.md`, `tests/test_invariants.py`.
