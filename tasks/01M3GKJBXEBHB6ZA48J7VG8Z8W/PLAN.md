# PLAN: answer — проверка строки мандата при записи и подсказка approve после ответа

## Подход

Потолок SPEC (`budget_usd: 25`) не переоцениваю: правка — один новый
модуль плюс точечные замены в трёх существующих, планка задачи уже
выписана и разметка требований однозначна.

**Общий узел — новый модуль `orchestrator/advance_gates/mandate.py`.**
Он становится единственным адресом всего, что относится к ОДНОЙ строке
мандата Оператора:

- оба маркера (`_ZONES_MANDATE_MARKER`, `TEST_WEAKENING_MANDATE_MARKER`)
  переезжают сюда из `zones.py`/`test_integrity.py`, а прежние модули их
  реэкспортируют — `zones._ZONES_MANDATE_MARKER`,
  `test_integrity.TEST_WEAKENING_MANDATE_MARKER` и реэкспорт
  `fsm_advance.*` остаются рабочими именами, ни один внешний вызов не
  правится;
- туда же переезжает `_split_zone_paths` («деление по запятым, отбрасывание
  пустых элементов» — шаг того же разбора по требованию 1) и
  реэкспортируется в `zones.py`, где его продолжают звать `zones:`/`Пути:`
  и откуда его импортирует `test_integrity.py`;
- разбор «маркер → элементы» — `mandate.elements(line, marker)`:
  `strip` строки, отсечение префикса маркера, деление по запятым.
  `None` — строка мандатом не является (после `strip` не начинается с
  маркера), `[]` — маркер есть, непустых элементов нет. Различение нужно
  требованию 2г: сегодня оба случая дают `[]`, и голый маркер
  неотличим от обычного текста.

Маркеры переезжают вместе с разбором, а не остаются на местах, именно
потому, что проверка требования 2 обязана перебрать ОБА вида мандата: с
маркерами по старым адресам узел проверки не может их импортировать
(`mandate` → `test_integrity` → `zones` → `mandate` — цикл).

**Проверка при записи — `mandate.refusals(text, code_branch)`** в том же
модуле: перебирает ВСЕ строки файла ответа (не первую, «Материалы» SPEC),
на каждой пробует оба маркера и возвращает список причин «строка → элемент
→ причина». Правила — ровно четыре подпункта требования 2. Существование
пути проверяется ТОЛЬКО для мандата зон (требование 2б) и только по дереву
КОДОВОЙ ветки задачи (`gitcmd.ls_tree_files(code_branch, ".")`); мандат
ослабления существованием не проверяется сознательно — его штатный предмет
как раз УДАЛЁННЫЙ файл тестов, которого в дереве ветки уже нет.

**Молчание git — fail-open для проверки существования.** `ls_tree_files`
вернул `None` (кодовой ветки ещё нет, git не ответил) — проверка 2б не
применяется, остальные три правила применяются всегда. Довод: проверка при
записи — удобство Оператора, а не рубеж защиты; настоящий рубеж — гейт
зон, и он остаётся fail-closed без изменений. Обратное решение сломало бы
и живой сценарий (`tests/test_answer.py`, задача, у которой кодовой ветки
в песочнице нет вовсе), и саму механику: отказывать исправному мандату на
сбое git значит запретить Оператору отвечать на эскалацию.

**Потребители зовут узел, своего разбора не держат.**
`answer._zones_mandate_marker_paths`, `zones._answer_zones_mandate` и
`test_integrity._answer_mandate` теряют свои `line[len(МАРКЕР):]` и зовут
`mandate.elements`; накопление по строкам и по файлам ANSWER остаётся в
каждом потребителе своим (требование 1). Имя
`answer._zones_mandate_marker_paths` сохраняется: его зовут существующие
тесты (AC-9 запрещает их правку).

**Подсказка approve (требование 3)** — в `answer._cmd_answer`: в состоянии
`escalated` успешный вызов печатает `дальше: artel.py approve <id>
(снятие эскалации)` и пишет действие журнала `ANSWER создан, ждёт
approve`. Ветка `in_dev`/`review` с мандатом свою запись «мандат на
расширение зон: …» сохраняет байт-в-байт: планка AC-1 считает записи с
этой пометкой и ждёт ровно одну на один вызов с мандатом зон.

## Шаги

1. `orchestrator/advance_gates/mandate.py` — новый модуль: оба маркера,
   `_split_zone_paths`, `elements`, `refusals` и её помощники
   (`_looks_like_path`, форма `путь::имя` через `guard.TEST_NAME_SEP`,
   существование элемента в дереве с учётом `/` на конце).
2. `orchestrator/advance_gates/zones.py` и
   `orchestrator/advance_gates/test_integrity.py` — реэкспорт маркеров и
   `_split_zone_paths` из `mandate`, свой разбор строки мандата заменён
   вызовом `mandate.elements`.
3. `orchestrator/answer.py` — `_zones_mandate_marker_paths` через
   `mandate.elements`; проверка строк мандатов до коммита ANSWER (общая
   для обеих принимающих ветвей состояния); подсказка `approve` и запись
   журнала для `escalated`.
4. `docs/operator-gates.md` — раздел «Гейт эскалации»: формат строки
   мандата (только пути через запятую, пояснения отдельным абзацем),
   проверка при записи и шаг `approve` после ответа.
5. `tests/test_answer_mandate.py` — юнит-тесты разбора, каждого класса
   отказа, fail-open на молчании git и согласия трёх потребителей на
   одной строке; регенерация `docs/codebase-map.md`.

## Влияние на систему

- **Инварианты 34 и 38** (мандат зон, мандат ослабления тестов) семантики
  не меняют: оба гейта получают на той же строке тот же список элементов,
  меняется только адрес разбора. Проверка при записи — новый, более ранний
  рубеж ПЕРЕД ними; ни один из существующих рубежей не ослабляется и не
  снимается. Отказ по молчанию git на гейтах (fail-closed на переходе,
  fail-open на мерже) не тронут.
- **Реэкспорт как способ не ломать вызовы.** `fsm_advance` реэкспортирует
  `_ZONES_MANDATE_MARKER`/`_split_zone_paths` из `zones`, а
  `TEST_WEAKENING_MANDATE_MARKER` из `test_integrity`; оба модуля после
  правки реэкспортируют их из `mandate`. Цепочка `fsm_advance.<имя>`,
  которой пользуются `orchestrator/answer.py` и 4 тестовых файла,
  сохраняется — это тот же приём, которым пакет `advance_gates` уже
  переживает свой разрез.
- **Новое поведение команды `answer`** — отказ там, где раньше был коммит.
  Риск ложного отказа снят fail-open на молчании git (см. «Подход») и
  прогоном пяти наборов, названных AC-9, плюс `tests/test_canary.py`
  (`canary` зовёт `cmd_answer` синтетическим текстом без строк мандата).
- **Смена действия журнала** в `escalated` с `ANSWER создан` на
  `ANSWER создан, ждёт approve`: точного равенства этому действию не
  требует ни один существующий тест (проверено `git grep`), читатели
  журнала (`store.refusal_history`, `report`) отбирают записи по другим
  префиксам.
- **Откат** — revert одного merge-коммита: новый модуль удаляется,
  реэкспорты и три вызова возвращаются к прежнему виду, документация и
  тесты откатываются тем же коммитом.
- Правятся `*.py` — `docs/codebase-map.md` регенерируется тем же коммитом
  (`python3 scripts/codebase_map.py`).

## Риски

- Планка AC-1 проверяет «один разбор» по AST: отсечение префикса
  ИМЕНОВАННОГО маркера не должно остаться ни в одном другом модуле пакета.
  Снимается тем, что шаг 2 убирает оба выражения полностью, а не
  оборачивает их.
- Проверка «не похож на путь репозитория» — новое правило формы; слишком
  строгий набор допустимых символов отказал бы исправному мандату.
  Набор ограничен буквами/цифрами/`_`/`-`/`.`/`/`, запрещены абсолютный
  путь и сегмент `..`; элемент мандата ослабления проверяется этим
  правилом только в своей путевой части, до `::`.
- Следствие требования 2б, уже названное SPEC: мандат зон на файл,
  которого в ветке ещё нет, не пройдёт — обходной путь Оператора —
  мандат на каталог. Правило реализовано буквально по SPEC и вынесено в
  документацию шага 4.

## Предложения системе

- Требование 2б («элемент существует в дереве кодовой ветки») по построению
  запрещает мандат зон на ещё не созданный файл — самый частый случай
  расширения зон при заведении нового модуля. SPEC называет обходной путь
  (мандат на каталог), но правило стоит переосмыслить отдельной задачей:
  проверка «путь существует ИЛИ существует его родительский каталог» даёт
  тот же улов опечатки без этого ограничения.
