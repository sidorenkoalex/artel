# SPEC: answer отказывает на ключ вместо файла; approve эскалации «нужен шаг роли» без нового ANSWER — только с флагом `--no-answer`

## Контекст
Прецедент 02.10.2026 (задача 01M3Y75GCR): `answer <id> --from <файл>`
отказал общим «файл ответа не прочитан», следующий `approve` через 54 с
снял эскалацию конфликта подтяжки без ANSWER — подготовленный ответ
разработчику не дошёл. Сегодня разбор аргументов `answer`
(`orchestrator/artel.py::main`, ~1546) вызывает
`answer.cmd_answer(rest[0], rest[1])` без проверки: «--from» становится
путём файла, `answer <id>` без файла падает `IndexError`, лишние
аргументы молча отбрасываются. `approve` из `escalated`
(`orchestrator/fsm.py::_approve_escalated`, ~1035-1069) проверяет ANSWER
только при `answer_baseline is not None`; эскалация конфликта подтяжки
(`orchestrator/pull.py` ~480-506, метка `PULL_CONFLICT_ROLE_STEP_MARKER`)
`answer_baseline` не пишет и снимается `approve` без ответа, хотя её
возврат ведёт к шагу developer. Справка `artel.py` по `answer`
(~429-446) устарела: с задачи 01M443BPQEA9ZMJ3R50THNB1MF `answer` в
`in_dev`/`review` принимает файл без строк мандатов как указание
Оператора.

Термины SPEC:
- **эскалация с меткой «нужен шаг роли»** — эскалация, после последней
  записи журнала «state -> escalated» которой в журнале задачи есть
  запись с действием из `orchestrator/auto.py::_ROLE_STEP_REQUIRED_MARKERS`
  (`pull.PULL_CONFLICT_ROLE_STEP_MARKER`,
  `fsm.ARTIFACT_ESCALATION_ROLE_STEP_MARKER`);
- **ANSWER после эскалации** — запись журнала задачи о создании ANSWER
  (действие, начинающееся с «ANSWER создан», от команд `answer` и
  `zones-extend`), стоящая после последней записи «state -> escalated».

## Требования

1. `answer` отказывает в разборе аргументов (`orchestrator/artel.py`) —
   до любого чтения файла, коммита, записи в журнал и взятия lease, —
   если второй аргумент начинается с «--», если файла по второму
   аргументу нет (в том числе аргумент отсутствует) или если аргументов
   после команды больше двух. Текст отказа называет полученный аргумент
   (или его отсутствие) и синтаксис `artel.py answer <id>
   <файл-с-ответом>`. ANSWER не создаётся, lease не берётся, необработанного
   исключения нет. Отказ одинаков для `escalated`, `in_dev`/`review`
   (указание и мандат) и прочих состояний.
2. `approve` из `escalated` для эскалации с меткой «нужен шаг роли» без
   ANSWER после эскалации и без флага `--no-answer` отклоняется
   именованным текстом: ANSWER после эскалации нет; команда ответа
   `artel.py answer <id> <файл>`; флаг снятия без ответа `--no-answer`.
   Состояние не меняется; в журнал пишется запись отказа. ANSWER,
   созданный до последней записи «state -> escalated», не засчитывается.
3. Флаг `--no-answer` (`approve <id> [sha] --no-answer`) снимает такую
   эскалацию без ответа: переход прежний (то же состояние возврата —
   `escalated_from` или `in_dev`, тот же текст записи перехода «эскалация
   разрешена, продолжаем»), плюс отдельная запись журнала с актором
   Оператора о снятии эскалации без ответа, несущая текст последней
   эскалации (detail последней записи «state -> escalated»). Метка «нужен
   шаг роли» после такого возврата по-прежнему ведёт к шагу developer.
4. Флаг не обходит существующую проверку `answer_baseline`: эскалация со
   структурированным вопросом роли без нового ANSWER отказывает
   прежним отказом «approve отклонён: нет ANSWER» и с флагом.
5. `orchestrator/artel.py::_approve_sha_arg` не принимает `--no-answer`
   за sha. Флаг разрешён только в состоянии `escalated`; `approve` с
   флагом в любом другом состоянии — именованный отказ, называющий флаг и
   то, что он допустим только в `escalated`; переход не выполняется.
6. Эскалации без метки «нужен шаг роли» (перечень фактов ТЗ: подтяжка
   отказала после очистки рабочей копии, рабочая копия не создана,
   красная приёмка после подтяжки, потолок ожидания CI в `verifying`,
   лимит итераций ревью, лимит отказов приёмки, провал агента после всех
   попыток, инцидент целостности на старте шага, расхождение ссылки
   документов, защищённый путь/конфликт мержа на `merge_gate`,
   непокрытое ослабление тестов на `merge_gate`) снимаются `approve` без
   ANSWER и без флага, как сегодня. Эскалация с меткой и ANSWER после неё
   снимается `approve` без флага, как сегодня.
7. Подсказки пульта, которые сегодня печатают `artel.py approve <id>`
   после эскалации с меткой «нужен шаг роли» без ANSWER после неё,
   печатают форму с `--no-answer` либо команду ответа `artel.py answer
   <id> <файл>`. Перечень по коду:
   - подсказка остановки цикла в `escalated` —
     `orchestrator/config.py::AUTO_STOP["escalated"]`, выдаваемая
     `orchestrator/auto.py::auto_stop_advice` (~555-588);
   - подсказка остановки по серии конфликтов подтяжки —
     `orchestrator/auto.py` ~864-866 («artel.py answer/approve <id>»).
   Подсказки после эскалаций без метки (`orchestrator/runner.py` ~414,
   ~766) и подсказка `orchestrator/answer.py` ~304 (печатается, когда
   ANSWER уже создан) не меняются.
8. Справка `orchestrator/artel.py` по `answer` (~429-446) и `approve`
   (~143) описывает действующее поведение: в `in_dev`/`review`
   принимается файл без строк мандатов как указание Оператора; отказ на
   ключ/отсутствующий файл/лишние аргументы; флаг `--no-answer`
   у `approve`. В `docs/operator-session.md` — строка о флаге
   `--no-answer` и о том, что снятие эскалации без ответа видно в
   журнале задачи.
9. Свойства критериев AC-1…AC-8 покрыты тестами в `tests/` с заявками
   «Ловит мутацию»; свойство, которое уже держит долгоживущий приёмочный
   тест автора тестов (`tests/test_01m44enw1b73z80pr73hp1c9cg_*.py`),
   повторно не пишется.

## Критерии приёмки

AC-1. `artel.py answer <id> --from <существующий-файл>` в `escalated` и
в `in_dev` отказывает текстом, называющим полученный аргумент «--from» и
синтаксис `artel.py answer <id> <файл-с-ответом>`; ANSWER-*.md не
создан, в журнале задачи нет новой записи, lease не взят. Тот же отказ
(без необработанного исключения) — для `artel.py answer <id>` без файла,
для несуществующего пути файла и для трёх и более аргументов после
`answer`.

AC-2. `approve` из `escalated` после эскалации конфликта подтяжки
(запись `PULL_CONFLICT_ROLE_STEP_MARKER` после последней «state ->
escalated») без ANSWER после эскалации и без флага отклоняется: текст
называет отсутствие ANSWER после эскалации, команду `artel.py answer
<id> <файл>` и флаг `--no-answer`; состояние остаётся `escalated`; в
журнале — запись отказа.

AC-3. ANSWER, созданный до последней записи «state -> escalated», не
засчитывается: `approve` без флага отклоняется, как в AC-2. ANSWER,
созданный после неё (командой `answer` или `zones-extend`), снимает
эскалацию `approve` без флага с прежним переходом и прежним текстом
записи «эскалация разрешена, продолжаем».

AC-4. Тот же случай, что в AC-2, с `approve <id> --no-answer`: задача
переходит в прежнее состояние возврата с записью перехода «эскалация
разрешена, продолжаем»; в журнале есть отдельная запись Оператора о
снятии эскалации без ответа, содержащая detail последней записи «state ->
escalated»; после возврата метка «нужен шаг роли» ведёт к шагу developer
(предварительный advance `auto` не выполняется до шага роли).

AC-5. Эскалация со структурированным вопросом роли (`answer_baseline`
задан) без нового ANSWER-*.md отклоняется прежним отказом «approve
отклонён: нет ANSWER» и при `approve <id> --no-answer`; состояние
остаётся `escalated`.

AC-6. Эскалация без метки «нужен шаг роли» (например, провал агента
после всех попыток) снимается `approve <id>` без ANSWER и без флага с
прежним переходом и прежним текстом записи перехода.

AC-7. `approve <id> --no-answer` не принимает `--no-answer` за sha
(`_approve_sha_arg` возвращает отсутствие sha; при `approve <id> <sha>
--no-answer` sha — `<sha>`). `approve <id> --no-answer` в состоянии,
отличном от `escalated`, — именованный отказ, называющий флаг и
`escalated`; состояние не меняется.

AC-8. Для задачи в `escalated` с меткой «нужен шаг роли» без ANSWER после
эскалации подсказка `auto_stop_advice` и подсказка остановки по серии
конфликтов подтяжки (`auto.py` ~864-866) содержат `--no-answer` либо
`artel.py answer <id> <файл>` и не предлагают голый `artel.py approve
<id>` без флага; для эскалации без метки подсказка `auto_stop_advice`
прежняя. Справка `artel.py` по `answer` упоминает указание Оператора в
`in_dev`/`review` без строк мандатов и отказ на ключ; справка по
`approve` — флаг `--no-answer`; `docs/operator-session.md` содержит
строку о `--no-answer` и о видимости снятия без ответа в журнале.

## Оценка объёма и деление

Сработавшие сигналы (guard): число затрагиваемых модулей/файлов (в
тексте SPEC адресно названы `orchestrator/artel.py`, `answer.py`,
`fsm.py`, `auto.py`, `config.py`, `pull.py`, `runner.py`,
`docs/operator-session.md` — правятся из них пять-шесть, `pull.py` и
`runner.py` упомянуты как неизменяемые адреса), затронут инвариантный
механизм (переходы FSM из `escalated`), прогноз диффа не был дан.

Прогноз диффа: 30 КиБ (код ~8-10 КиБ: разбор аргументов `answer`, флаг
`approve`, проверка в `_approve_escalated`, две подсказки, справка; тесты
~20 КиБ).

**Обоснование монолита.** Технически задача режется по двум
требованиям бэклога — (а) отказ `answer` на ключ (AC-1) и (б) флаг
`--no-answer` и проверка ANSWER на `approve` (AC-2…AC-8), и каждая часть
по отдельности оставляет систему рабочей. Монолит предлагается по
стоимости и по зонам, не по атомарности механики: обе части правят один
и тот же диспетчер и справку `orchestrator/artel.py` и одну строку
`docs/operator-session.md` (деление режет эти файлы поперёк и даёт два
конфликтующих диффа одного места); новый отказ `approve` (AC-2) в
тексте называет команду `answer`, чьё поведение на ключ меняет часть
(а) — прецедент ТЗ возникает именно на стыке обеих частей; объём
небольшой (8 критериев, прогноз 30 КиБ), а каждая подзадача несла бы
собственные шаги analyst/test_author/review — дороже Рамки ТЗ ($20)
вдвое. Изменение FSM — только новая ветка отказа внутри существующего
перехода `escalated -> <возврат>`, без нового промежуточного состояния:
число шагов между состояниями маршрута не меняется, правка
`tests/test_invariants.py` (путь «только чтение») не ожидается.
Решение — за Оператором на гейте SPEC.
