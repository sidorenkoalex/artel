Требуется:
1. `answer` отказывает до любого чтения файла, коммита и записи в журнал,
   если второй аргумент начинается с «--», если файла нет или если
   аргументов больше двух. Текст отказа называет полученный аргумент и
   синтаксис `artel.py answer <id> <файл-с-ответом>`; ANSWER не создан,
   lease не берётся. Отказ стоит в разборе аргументов, одинаково для
   `escalated`, `in_dev`/`review` (указание и мандат) и прочих
   состояний.
2. `approve` из `escalated` для эскалации с меткой «нужен шаг роли»
   (решение Оператора 05.10: флаг — только там, где ответ дошёл бы до
   роли; прочие эскалации из перечня фактов снимаются `approve` без
   флага, как сегодня): если после последней записи «state ->
   escalated» в журнале задачи нет записи о создании ANSWER (любой из
   записей `answer` и `zones-extend`: «ANSWER создан…»), переход без
   флага отклоняется с именованным текстом: что ANSWER после эскалации
   нет, команда ответа `artel.py answer <id> <файл>` и флаг снятия без
   ответа. Состояние не меняется; журнал — запись отказа.
3. Флаг `--no-answer` (`approve <id> [sha] --no-answer`) снимает
   эскалацию без ответа: переход прежний (тот же `escalated_from`/
   `in_dev`, тот же текст записи «эскалация разрешена, продолжаем», от
   которого зависит `auto`), плюс отдельная запись журнала Оператора о
   снятии без ответа с текстом последней эскалации. Флаг не обходит
   существующую проверку `answer_baseline`: эскалация со
   структурированным вопросом роли без нового ANSWER отказывает и с
   флагом. `_approve_sha_arg` флаг за sha не принимает. Флаг
   разрешён только в `escalated`; в других состояниях — именованный
   отказ.
4. Эскалации из перечня фактов без метки «нужен шаг роли» снимаются
   `approve` без ANSWER и без флага, как сегодня; с меткой — с ANSWER
   без флага, без ANSWER — с `--no-answer`. Снятие бюджетной эскалации командой `budget` и
   синтетический возврат канарейки не меняются (они не идут через
   `approve`). Подсказки пульта, которые сегодня печатают
   `artel.py approve <id>` после эскалаций с меткой «нужен шаг роли»
   без ответа, печатают
   форму с `--no-answer` либо команду ответа — SPEC перечисляет такие
   подсказки по коду.
5. Справка `orchestrator/artel.py` по `answer` (~429-446) и `approve`
   (~143) приводится к действующему поведению: указание Оператора в
   `in_dev`/`review` без строк мандатов, новый отказ на ключ, флаг
   `--no-answer`. В `docs/operator-session.md` — строка о флаге и о том,
   что снятие эскалации без ответа видно в журнале.
6. Тесты в `tests/` с заявками «Ловит мутацию»: `answer <id> --from
   <файл>` — именованный отказ с синтаксисом, ANSWER не создан, журнал
   без записи (в `escalated` и в `in_dev`); `answer <id>` без файла —
   тот же отказ без необработанного исключения; `approve` из escalated
   (конфликт подтяжки) без ANSWER после эскалации — отказ, состояние
   прежнее; тот же случай с `--no-answer` — переход, текст записи
   перехода прежний, запись о снятии без ответа есть, метка «нужен шаг
   роли» по-прежнему ведёт к шагу developer; с ANSWER после эскалации —
   прежнее поведение без флага; ANSWER до эскалации не засчитывается;
   структурированная эскалация без ANSWER — отказ и с флагом;
   эскалация без метки «нужен шаг роли» (например, провал агента) —
   `approve` без ANSWER и без флага проходит, как сегодня;
   `approve <id> --no-answer` не принимает флаг за sha. Существующие
   тесты не ослабляются.
