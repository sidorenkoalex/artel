# SPEC: ADR-0014, часть 2 — однократная переоценка бюджета на PLAN

## Контекст

Часть 1 ADR-0014 (`docs/adr/0014-budget-default-and-role-cap.md`) вводит
`ROLE_BUDGET_CAP` и делает потолок из `budget_usd` SPEC применимым в обе
стороны в пределах этого потолка ролей. ADR-0014 п.3 предусматривает ещё
один канал пересмотра потолка — однократный, на стороне разработчика: PLAN
вправе один раз, при первой сдаче, поднять потолок задачи выше значения из
SPEC, если по факту числа файлов/шагов оценка SPEC оказалась заниженной.
Эта задача — часть 2 деления, реализует именно этот канал в
`orchestrator/fsm_advance.py::in_dev`, дополняет `docs/invariants.md`
(инвариант 10) и `tests/test_invariants.py`. Старт — после мержа части 1:
`ROLE_BUDGET_CAP`, обязательность и двусторонний потолок `budget_usd` в
SPEC уже существуют к моменту разработки этой части.

## Требования

1. При первой сдаче PLAN.md со `status: ready` для задачи (`review_iters
   == 0` и переоценка бюджета по PLAN для этой задачи ещё ни разу не
   срабатывала) значение `budget_usd` из frontmatter PLAN.md, если оно
   выше текущего потолка задачи, поднимает потолок до этого значения, но
   не выше `ROLE_BUDGET_CAP`; источником потолка становится `budget_source
   = plan`; в журнал задачи попадает запись со старым потолком, новым
   потолком и источником.
2. Если PLAN.md не несёт поля `budget_usd`, потолок задачи не меняется.
3. Если `budget_usd` из PLAN.md не выше текущего потолка задачи, потолок
   не меняется; в журнал попадает запись «не применён: ниже потолка».
4. После возврата задачи в `in_dev` из ревью (вердикт `changes_requested`)
   или из приёмки (`reject`) повторная сдача PLAN.md со `status: ready`
   потолок не меняет, независимо от значения `budget_usd` в ней.
5. Потолок, заданный Оператором командой `budget` (`budget_source =
   operator`), значением `budget_usd` из PLAN.md не перебивается ни на
   первой, ни на любой последующей сдаче PLAN.md.
6. `budget_usd` из PLAN.md выше `ROLE_BUDGET_CAP` не проходит переход
   `in_dev` вовсе — гейт guard, введённый частью 1, отказывает переходу
   раньше, чем логика переоценки успевает сработать; эта задача не
   добавляет для этого случая отдельной обработки.
7. `docs/invariants.md`, инвариант 10, дополняется формулировкой: в
   пределах `ROLE_BUDGET_CAP` потолок задачи вправе задать не только SPEC
   на гейте SPEC, но и один раз PLAN при первой сдаче; подъём потолка
   ВЫШЕ `ROLE_BUDGET_CAP` остаётся исключительно действием Оператора
   командой `budget`.
8. `tests/test_invariants.py` получает тестовое покрытие переоценки по
   PLAN: значение выше `ROLE_BUDGET_CAP` потолок не поднимает; переоценка
   срабатывает не более одного раза за всю жизнь задачи и не срабатывает
   повторно после возврата задачи в `in_dev`; потолок, заданный
   Оператором, значением из PLAN не перебивается.
9. К PLAN.md этой задачи прикладывается unified-диф скила разработчика
   (`skills/coding-standards.md`) с правилом однократной переоценки:
   основание — число файлов и шагов PLAN, применяется только при
   расхождении с оценкой бюджета из SPEC, с обоснованием расхождения в
   разделе «Подход» PLAN.md.

## Критерии приёмки

AC-1. На первой сдаче PLAN.md со `status: ready` (`review_iters == 0`,
переоценка по PLAN для задачи ещё ни разу не срабатывала) со значением
`budget_usd`, которое выше текущего потолка задачи (пример: PLAN `$90`
при потолке `$45`), потолок задачи поднимается до этого значения (в
примере — до `$90`), не выше `ROLE_BUDGET_CAP`; `budget_source` становится
`plan`; в журнал попадает запись со старым потолком, новым потолком и
источником `plan`.

AC-2. На той же первой сдаче, если PLAN.md не несёт поля `budget_usd`,
потолок задачи остаётся прежним.

AC-3. На той же первой сдаче, если `budget_usd` из PLAN.md не выше
текущего потолка (пример: PLAN `$30` при потолке `$45`), потолок остаётся
прежним, а в журнал попадает запись «не применён: ниже потолка».

AC-4. После возврата задачи в `in_dev` из ревью (`changes_requested`) или
из приёмки (`reject`) повторная сдача PLAN.md со `status: ready` — даже с
более высоким `budget_usd` (пример: `$100` после того, как потолок уже
был поднят переоценкой до `$90`) — потолок не меняет.

AC-5. Потолок, заданный Оператором командой `budget` (`budget_source =
operator`, пример: `$60`), не перебивается значением `budget_usd` из
PLAN.md (пример: `$90`) ни на первой, ни на любой последующей сдаче
PLAN.md.

AC-6. PLAN.md с `budget_usd` выше `ROLE_BUDGET_CAP` не проходит переход
`in_dev` вовсе — отказывает гейт guard, введённый частью 1, до того, как
логика переоценки этой задачи успевает сработать; потолок задачи при этом
не меняется, и эта задача не вводит для такого случая отдельной обработки.

AC-7. `docs/invariants.md`, инвариант 10, несёт формулировку: потолок
задачи в пределах `ROLE_BUDGET_CAP` вправе задать один раз и PLAN при
первой сдаче — не только SPEC на гейте SPEC; подъём потолка ВЫШЕ
`ROLE_BUDGET_CAP` остаётся исключительно действием Оператора командой
`budget`.

AC-8. `tests/test_invariants.py` покрывает тестами: (a) PLAN.md с
`budget_usd` выше `ROLE_BUDGET_CAP` потолок задачи не поднимает; (b)
переоценка по PLAN срабатывает не более одного раза за всю жизнь задачи и
не срабатывает повторно после возврата задачи в `in_dev`; (c) потолок,
заданный Оператором, значением `budget_usd` из PLAN.md не перебивается.

AC-9. PLAN.md этой задачи несёт приложением unified-диф к
`skills/coding-standards.md`, вводящий правило однократной переоценки
бюджета разработчиком: основание — число файлов и шагов PLAN, применяется
только при расхождении с оценкой бюджета из SPEC, с обоснованием
расхождения в разделе «Подход» PLAN.md.

## Не входит

- Всё из части 1: константа `ROLE_BUDGET_CAP`, обязательность поля
  `budget_usd` в SPEC, двусторонний потолок из SPEC на гейте SPEC,
  guard-проверка потолка ролей для SPEC и PLAN, поле `budget_usd` в
  `templates/PLAN.md` — уже сделано частью 1, эта задача только
  пользуется готовым.
- Правки самого guard — проверка потолка ролей для `budget_usd` PLAN уже
  введена частью 1, эта задача её не повторяет и не расширяет.
- Автоматический подъём потолка при исчерпании бюджета.
- Стоп-лосс программы (`PROGRAM_STOP_LOSS_USD`, ADR-0010).
