# PLAN: Hotfix A7 — маршрут analyst и канал ANSWER через источник артефактов

## Подход
Три места, названные в SPEC «Материалы», переводятся на источник
артефактов (`artifact_source.resolve`) точечно, без переноса
однобраншевой ветки кода задач прежнего флоу:

1. `runner.step_role` — проверка наличия `TZ.md` через
   `artifact_source.resolve` ДОБАВЛЕНА поверх старой проверки
   (`on_foreign_branch`/диск `config.TASKS`), не заменяет её (AC-2
   требует, чтобы задачи прежнего флоу продолжали находиться старым
   путём). Читается первой: у задачи нового флоу код-ветки в git ещё
   нет вовсе, старая проверка на ней молчит.
2. `answer._cmd_answer` переписана целиком по варианту A из
   ANSWER-1.md (вопрос 1): `answer` ВСЕГДА коммитит `ANSWER-n.md`
   плотницки в артефактную ветку через `artifact_branch.commit_files`
   (по образцу `checkpoint._commit_external_step_artifacts`), не
   трогая worktree/кодовую ветку задачи вовсе. Отдельного пути
   «прежнего флоу» для `answer` не заводится — по обоснованию
   Оператора он структурно недостижим после A7 (артефактная ветка есть
   у любой задачи). `n` считается по содержимому артефактной ветки
   (`gitcmd.ls_tree_files`), не диска. AC-5 помечен `skip` в самом
   тестовом файле (решение test_author по ANSWER-1) — не мой выбор,
   принят и обоснован Оператором заранее.
3. `checkpoint._commit_external_step_artifacts` — перенос удалений
   (требование 4/AC-6). Здесь НЕДОСТАТОЧНО наивного полного диффа
   «всё, что было в артефактной ветке, минус то, что сейчас на диске»:
   `tests/test_checkpoint_external_step_artifacts.py::
   test_second_step_accumulates_onto_the_first_not_replaces_it`
   (существующий, зелёный, НЕ трогать) требует, чтобы файл ОДНОЙ роли
   (`PLAN.md` разработчика) пережил автокоммит ДРУГОЙ роли (`REVIEW.md`
   ревьювера) на том же шаге — а `task_dir` у роли пуст на каждом шаге
   (сама эта функция wipe'ает его после любого успешного коммита), так
   что «нет на диске» само по себе не отличает «роль удалила файл» от
   «эта роль его просто не трогает». Разрешение конфликта: кандидатом
   на удаление считается путь, ПОСЛЕДНИЙ коммит которого на артефактной
   ветке — автокоммит ЭТОЙ ЖЕ роли (сообщение коммита уникально для
   пары task_id/role — `git log -1 --format=%s <branch> -- <path>`);
   файл, последний раз тронутый другой ролью или другим механизмом
   (PASSPORT.md переходов, ANSWER Оператора), никогда не кандидат,
   независимо от локального отсутствия. `artifact_branch.write_commit`/
   `commit_files` получили новый опциональный параметр `remove` —
   `update-index --force-remove` поверх `read-tree parent`, ПОСЛЕ
   применения `files`.

   Итерация 2 (закрытие REVIEW.md R1-F1): «последний коммит — той же
   роли» само по себе совпадает и с легитимным сценарием (QUESTIONS.md
   analyst), и с реальным ненамеренным (developer, повторный шаг В ТОМ
   ЖЕ состоянии — auto-цикл `in_dev` пока PLAN.md не `ready`, `reject`
   из `acceptance` — не гарантирует, что роль перепишет файл, который
   хочет сохранить: `task_dir` пуст на каждом шаге, `developer_brief`
   не кладёт содержимое прежнего PLAN.md в промпт). Добавлено второе,
   обязательное условие: frontmatter `type` кандидата обязан быть в
   `checkpoint._DELETABLE_ARTIFACT_TYPES` (сейчас — только `questions`,
   единственный документированный скилом spec-authoring сценарий).
   PLAN.md/REVIEW.md/SPEC.md (`type: plan/review/spec`) никогда не
   кандидаты, независимо от совпадения автора последнего коммита.

WIP-заглушка test_author (коммит e69cf08, упомянута в ANSWER-1
«Дополнительно») к моменту работы уже была отменена в индексе
worktree (staged revert, не закоммичена) — переписана здесь заново по
собственной логике, ничего из неё не унаследовано буквально; отличие
от заглушки — п.3 (заглушка не трогала `checkpoint.py` вовсе) и
идентичность коммита `answer` (заглушка использовала дефолтную
`fixation.FIXATION_AUTHOR_*` `commit_files` без обсуждения — тот же
выбор, но здесь он объяснён явно в докстринге модуля).

## Шаги
1. `orchestrator/artifact_branch.py`: `write_commit`/`commit_files` —
   параметр `remove` (список путей, принудительно убираемых из дерева
   результата после применения `files`).
2. `orchestrator/checkpoint.py`: `_commit_external_step_artifacts` —
   вычисление `removed` по правилу «последний коммит пути — автокоммит
   этой же роли» и передача его в `commit_files(..., remove=removed)`;
   коммит совершается и когда `files` пуст, но `removed` не пуст
   (роль убрала всё, что писала).
3. `orchestrator/runner.py`: `step_role` — чтение TZ.md через
   `artifact_source.resolve` поверх старой проверки.
4. `orchestrator/answer.py`: `_cmd_answer` — коммит `ANSWER-n.md`
   плотницки в артефактную ветку; docstring модуля переписан под новую
   механику (снят более неверный тезис про identity Оператора —
   плотницкая запись не читает ничей git-конфиг).
5. Юнит-тесты: `tests/test_answer.py` (счётчик номера по списку путей,
   не по диску; happy path переведён на артефактную ветку взамен
   worktree-сценариев, снятых с повестки A7), `tests/
   test_checkpoint_external_step_artifacts.py` (два новых теста —
   удаление файла той же роли; отсутствие побочного удаления файла
   чужой роли).
6. `python3 scripts/guard.py` по своим артефактам, полный прогон
   `tests/` и приёмочных тестов A7, коммит.

## Влияние на систему
- `artifact_branch.write_commit`/`commit_files` — новый опциональный
  параметр `remove` с дефолтом `None`; существующие вызывающие места
  (`catalog._new_external_artifact_branch`, `snapshot.
  publish_and_cleanup`, `checkpoint.commit_step_artifacts` до этой
  правки) не передают его и получают старое поведение байт-в-байт
  (проверено полным прогоном `tests/`).
- `checkpoint._commit_external_step_artifacts` — единственное
  поведенческое расширение: сверх «не трогать существующие пути» (уже
  проверено `test_second_step_accumulates...`) добавлен один НОВЫЙ
  класс события — «путь, последний раз тронутый ЭТОЙ ЖЕ ролью,
  отсутствующий на диске сейчас И несущий frontmatter `type` из
  `_DELETABLE_ARTIFACT_TYPES` (сейчас только `questions`), убирается».
  Второе условие добавлено итерацией 2 (закрытие R1-F1) — без него
  инвариант «чужая роль ничего не теряет» держал только чужеролевой
  случай (`test_same_role_deletion_does_not_remove_another_roles_file`),
  но не однoролевой ненамеренный (та же роль, второй шаг, файл другого
  ТИПА не переписан) — теперь его держит новый `test_same_role_
  second_step_in_the_same_state_does_not_drop_an_untouched_file`.
  Функция получает 1 новый git-вызов (`log -1 --format=%s`) и, для
  кандидатов с совпавшим автором, ещё 1 (`git show`, чтение содержимого
  для frontmatter) НА КАЖДЫЙ путь-кандидат (обычно 0-1 путь за шаг —
  разница между содержимым ветки и локальным диском редко больше пары
  файлов) — цена приемлема для операции, которая и так делает несколько
  git-вызовов на шаг.
- `answer.py` перестаёт трогать worktree/кодовую ветку задачи —
  инвариант «`answer` не заводит кодовую ветку» теперь верен для
  ЛЮБОЙ задачи, не только нового флоу (AC-3 второй тест). Ни один
  существующий гейт/лимит/тест не ослаблен: `answer` по-прежнему
  доступна только из `escalated`, отказы на нечитаемом файле и вне
  состояния — без изменений.
- `runner.step_role` — новая ветка проверки строго ДОБАВЛЯЕТ случай
  (TZ.md в артефактной ветке), не убирает старый; `RunWithoutAgentTest`/
  `test_analyst_role.py` целиком зелёные без правок.
- Откат: все четыре правки независимы и точечны (разные функции,
  разные файлы) — откат любой из них через `git revert` не задевает
  остальные.

## Риски
- Правило «последний коммит пути = автокоммит той же роли» коррелирует
  поведение `checkpoint.py` с ТЕКСТОМ commit message, порождаемым им же
  (`f"{task_id}: артефакты шага {role} (автокоммит оркестратора)"`) —
  смена этого текста в будущем без синхронной правки проверяющего кода
  тихо отключит перенос удалений (не поломает существующие тесты,
  которые сеют сообщения тем же кодом, но сделает откат исторических
  данных нечитаемым). Отмечено в докстринге функции.
- (закрыто итерацией 2, R1-F1) То же правило само по себе совпадало и с
  реальным ненамеренным авто-повтором развернутой роли в ТОМ ЖЕ
  состоянии (auto-цикл `in_dev`/`reject` из `acceptance`) — сужено
  вторым условием, обязательным frontmatter `type` кандидата из
  `_DELETABLE_ARTIFACT_TYPES`. Остаточный риск того же класса не нулевой:
  если В БУДУЩЕМ появится роль, которая пишет в `task_dir` ДВА файла
  одного и того же удаляемого `type` за один шаг (сегодня такого нет —
  `questions` несёт только QUESTIONS.md analyst), либо сама роль
  формирует произвольный `type: questions` не по конвенции — сужение не
  спасёт. Не входит в объём этой задачи (SPEC «Не входит»): такой
  сценарий сегодня не существует ни у одной роли/скила.
- WIP-заглушка test_author (коммит e69cf08) остаётся в истории кодовой
  ветки как отдельный коммит — не переписывалась/не ужималась
  (`git commit --amend`/`rebase` не входят в мандат разработчика);
  текущий коммит полностью её перекрывает содержимым.
