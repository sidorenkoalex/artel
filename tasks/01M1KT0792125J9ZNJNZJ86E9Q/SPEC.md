# SPEC: Hotfix A7 — маршрут analyst и канал ANSWER через источник артефактов

## Контекст
После мержа A7 (01M1H224X5A8W159MKF1Q24R5Y) артефакты новых задач
артели живут в артефактной ветке пульта (`artifact/<id>`), а не в
кодовой ветке `task/*`. Два места не переведены на источник
артефактов (`artifact_source.resolve`) и читают/пишут кодовую ветку:

1. `orchestrator/runner.py` (выбор роли для `spec_writing`, строки
   ~84–89): наличие `TZ.md` проверяется по `t["branch"]` (кодовая
   ветка) — у задачи, заведённой новым флоу, TZ лежит в артефактной
   ветке, и роль analyst не подключается («SPEC пишет Оператор»).
   Инцидент 03.09: задача 01M1KS8K9RXWHX2PW3ZKB0P903 не смогла
   стартовать analyst.
2. `orchestrator/answer.py`: `ANSWER-n.md` коммитится в worktree
   кодовой ветки, тогда как возврат из эскалации (`fsm.py`,
   `_answer_baseline`/счёт ANSWER) читает артефактную ветку через
   `artifact_source.resolve` — ответ Оператора не доходит. Инцидент
   03.09: задачи 01M1HNNHDMP2C1AJTH5QF1BTN2 и 01M1KCSTBYF1CRJBSY4P6VYQEA
   не вернулись из эскалации после `answer`.

Планка A7 (44 приёмочных теста) проверяла полный флоу без эскалации
и без маршрута analyst для задачи нового флоу — оба пути остались
непокрытыми. SPEC написан Оператором (запасной путь без TZ: маршрут
analyst для новой задачи сломан этой же регрессией).

## Требования
1. Выбор роли для `spec_writing` (`runner.py`) определяет наличие
   `TZ.md` через `artifact_source.resolve(conn, task_id)` — тем же
   приёмом, что чтения SPEC/QUESTIONS в `fsm_advance.py` (T094
   требование 10): у задачи с артефактной веткой — из неё, у задачи
   прежнего флоу — как сейчас.
2. `answer` записывает `ANSWER-n.md` туда, откуда его читает возврат
   из эскалации: для задачи с артефактной веткой — коммитом без
   чекаута в артефактную ветку (`artifact_branch.write_commit`, по
   образцу автокоммита артефактов шага `checkpoint.py`), нумерация
   `n` считается по той же ветке; для задачи прежнего флоу —
   поведение не меняется.
3. Возврат из эскалации (`approve` в `escalated`) видит ANSWER,
   записанный командой `answer` из п.2, и продолжает штатно; `run`
   после возврата подключает analyst у задачи нового флоу.
4. Существующие тесты остаются зелёными; поведение задач прежнего
   флоу (кодовая ветка с `tasks/<id>/`) не меняется.

## Критерии приёмки

AC-1. Для задачи, заведённой `cmd_new --tz` после A7 (артефактная
ветка, кодовой ветки с `tasks/<id>/` нет), `run` в состоянии
`spec_writing` подключает роль analyst (TZ.md найден в артефактной
ветке), а не отвечает «SPEC пишет Оператор».

AC-2. Для задачи прежнего флоу (TZ.md в кодовой ветке) выбор роли
analyst работает как до этой задачи.

AC-3. `answer <id> <файл>` у задачи с артефактной веткой создаёт
`tasks/<id>/ANSWER-n.md` в артефактной ветке (коммит без чекаута,
кодовая ветка и рабочее дерево не меняются); `n` — следующий номер
по содержимому артефактной ветки.

AC-4. После `answer` из AC-3 `approve` в состоянии `escalated`
возвращает задачу в работу (ANSWER засчитан: число файлов ANSWER
выросло относительно `answer_baseline`), а не отказывает «не хватает
ANSWER-n.md».

AC-5. У задачи прежнего флоу `answer` и возврат из эскалации работают
как до этой задачи.

AC-6. Полный набор `tests/` зелёный; приёмочные тесты A7
(tasks/01M1H224X5A8W159MKF1Q24R5Y/acceptance_tests, 44) зелёные.
