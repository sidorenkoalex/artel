# SPEC: D2-1 — проектные скилы и меры для роли внешнего проекта

## Контекст
Это часть 1 задачи 01M53B45XW3J56RJHGD70TD8A2 (D2). В неё входят требования
5, 6 (без проверки `doctor`), 7, 10, 11 и 12 SPEC родителя, а также его
критерии AC-1 (только бриф, окружение и белый список роли), AC-6, AC-7
(без пункта про `doctor`) и AC-11. Основание — ADR-0023, вторая поправка
16.10.2026, п.3.

Что сейчас не так:
- Поле `project_skills` записи проекта проверяется только на тип
  (`orchestrator/targets.py:31`). Скилы роли берутся только из
  `roles.yaml` (`orchestrator/brief.py:519`, `skills_text`).
- Роль Claude получает `Bash(python3:*)` (`orchestrator/providers/claude.py:45`,
  `ALLOWED_TOOLS`).
- Окружение роли (`orchestrator/runner.py:964`, `role_env`) не задаёт
  `GIT_CONFIG_NOSYSTEM`.

Для задачи внешнего проекта это даёт роли больше, чем ей нужно, и не
доставляет ей проектные скилы.

## Требования

1. **Проектные скилы.** Элементы `project_skills` записи проекта — имена
   скилов пульта (`skills/<имя>.md`). В бриф роли задачи этого проекта они
   добавляются после скилов роли из `roles.yaml`, в порядке поля.
2. **Допустимость имени.** Допустимо только имя, которое указывает на
   существующий файл прямо в `skills/` (без подкаталогов).
   «Существующий файл» и текст проектного скила берутся из одного
   источника — головы `main` пульта, по действующему правилу скилов роли
   (`orchestrator/brief.py:521-526`, `:543`: `gitcmd.show(config.MAIN_BRANCH,
   "skills/<имя>.md", repo=config.ROOT)`). Файл, который есть на диске
   пульта, но не в голове `main`, считается несуществующим:
   незакоммиченный `skills/` до роли не доходит (решение Оператора 17.10,
   заменяет решение Ф-5 родителя «файл на диске пульта»).
   - Имя вне `skills/`, имя с подкаталогом внутри `skills/` или имя
     несуществующего файла — отказ сборки брифа. Текст отказа называет
     проект, поле `project_skills` и имя скила.
   - `orchestrator/targets.py` не меняется: сломанное поле одного проекта
     не делает `targets.yaml` негодным для остальных проектов.
   - Проверка допустимости имени вызывается и отдельно от сборки брифа,
     по записи проекта: её вызовет `doctor` части 2. Источник у брифа и у
     этой проверки один, отказ — тот же.
3. Для артели (`project_skills: []`) бриф роли не меняется.
4. Окружение роли задачи внешнего проекта содержит `GIT_CONFIG_NOSYSTEM=1` —
   у шага любого провайдера (Claude и Codex).
5. **Белый список роли Claude для задачи внешнего проекта.**
   - `Bash(python3:*)` убран.
   - Вместо него стоит только правило
     `Bash(python3 <абсолютный корень пульта>/orchestrator/artel.py:*)`.
     Путь в правиле посимвольно равен строке
     `config.ROOT / "orchestrator" / "artel.py"`, которую печатают миссии
     шага (`orchestrator/role_prompt.py:238`,
     `orchestrator/knowledge_cards.py:953`).
   - `Bash(git:*)` остаётся.
6. Для артели белый список роли Claude и окружение роли не меняются.
7. Чтобы провайдер знал проект задачи, в `orchestrator/providers/base.py`
   и `orchestrator/providers/codex.py` меняется только сигнатура метода
   `command` (решение Оператора 17.10, О-4). Поведение провайдера Codex
   не меняется.
8. Тесты детерминированы и не ходят в сеть.
9. **Проект задачи на пути запуска шага.** На пути запуска шага роли
   (сборка брифа — `orchestrator/runner.py:476`; окружение —
   `orchestrator/runner.py:1457` → `role_env`, `orchestrator/runner.py:964`;
   argv — `orchestrator/runner.py:1550`) проект задачи определяется явно.
   Сбой определения проекта — именованный отказ шага: агент не
   запускается, текст отказа называет задачу и причину. Правила артели по
   умолчанию в этом случае не применяются (решение Оператора 17.10).
   - `store.task_target` (`orchestrator/store.py:701-707`) подставляет
     проект артели, когда задача без target, — это fail-open источник.
     На пути шага роли для определения проекта он не используется
     (сейчас его зовут `orchestrator/runner.py:1184` и `:1469`).
   - Определение проекта с отказом делается в `orchestrator/runner.py`;
     `orchestrator/store.py` не меняется (решение Оператора 17.10).

## Критерии приёмки

AC-1. Для задачи артели на пути запуска шага роли (требование 9) бриф
роли, окружение роли и argv шага роли Claude, переданные в запуск агента,
совпадают с main. Значение `--allowedTools` целиком равно
`Bash(git:*),Bash(python3:*)`.

AC-2. В брифе роли задачи внешнего проекта с непустым `project_skills`
есть тексты этих скилов из головы `main` пульта
(`skills/<имя>.md` в `config.MAIN_BRANCH`). Они стоят после скилов роли
из `roles.yaml`, в порядке поля.

AC-3. Проверяются неверные `project_skills` внешнего проекта:
- имя вне `skills/` — с переходом в родительский каталог или с
  абсолютным путём;
- имя с подкаталогом внутри `skills/` (вида `sub/name`);
- имя несуществующего файла;
- имя файла, который есть на диске пульта, но не в голове `main`.

В каждом случае сборка брифа роли отказывает. Текст отказа называет
проект, `project_skills` и имя скила. `targets.yaml` при этом остаётся
читаемым, а задача другого проекта с верным полем собирает бриф без
отказа.

AC-4. Для задачи внешнего проекта на пути запуска шага роли
(требование 9) argv шага роли Claude, переданный в запуск агента, несёт
`--allowedTools` со значением целиком, посимвольно равным
`Bash(git:*),Bash(python3 <корень>/orchestrator/artel.py:*)`, где
`<корень>/orchestrator/artel.py` — строка
`config.ROOT / "orchestrator" / "artel.py"`. Окружение этого шага
содержит `GIT_CONFIG_NOSYSTEM=1`.

AC-5. argv шага роли провайдера Codex совпадает с main, и для задачи
артели, и для задачи внешнего проекта.

AC-6. Окружение шага роли провайдера Codex задачи внешнего проекта на
пути запуска шага (требование 9) содержит `GIT_CONFIG_NOSYSTEM=1`.

AC-7. Проверка допустимости `project_skills` вызывается по записи
проекта без сборки брифа. Для каждого неверного имени из AC-3 она
отказывает тем же текстом, что и сборка брифа; для верного поля отказа
нет.

AC-8. Проект задачи на пути запуска шага роли не определяется. Проверяются
два случая:
- target задачи не объявлен в `targets.yaml` (`orchestrator/targets.py:117-125`);
- `targets.yaml` не читается.

В каждом случае шаг отказывает именованным отказом, агент не
запускается. Шаг не уходит с белым списком и окружением артели.

## Оценка объёма и деление

Сработавший сигнал: число файлов зоны — 6 (`orchestrator/brief.py`,
`orchestrator/runner.py`, три файла `orchestrator/providers/`, `tests/`).
Два из них, `orchestrator/providers/base.py` и
`orchestrator/providers/codex.py`, меняются только в сигнатуре `command`
(О-4).

**Обоснование монолита** (решение за Оператором на гейте SPEC):
- Эта задача уже часть 1 деления родителя 01M53B45XW3J56RJHGD70TD8A2.
  Её рамку ($25) задал Оператор.
- Сигнатуру `command` в `base.py`/`codex.py` нельзя отделить от
  `claude.py`: смена сигнатуры без всех реализаций и без места вызова в
  `runner.py` оставляет провайдеров несогласованными с вызовом.
- Проектные скилы (`brief.py`) от мер для роли (`runner.py`/`providers/`)
  отрезать можно. Но каждая половина получится на 2–3 критерия, а цена
  задачи складывается из числа шагов, так что две задачи обойдутся
  дороже одной в пределах той же рамки.

## Не входит

- Проверка `doctor` по `project_skills` и остальные проверки `doctor`.
  Это часть 2 задачи D2 (требования 1–4, 8, 9, 13, 14 родителя). Здесь
  требуется только, чтобы проверку имени можно было вызвать отдельно от
  брифа (требование 2).
- Токен хостинга проекта, `GH_TOKEN`, помощник учётных данных git — часть 2.
- Обходы через `git -c alias`/`core.fsmonitor` и через код, исполняемый
  командами пульта. Это принятый остаточный риск (ADR-0023, вторая
  поправка, п.5).
- Правка `skills/`, `roles.yaml`, `orchestrator/targets.py`,
  `orchestrator/store.py`.
- Изменение поведения провайдера Codex: меняется только сигнатура
  `command`.
- Вызовы `role_env`/`command` вне пути запуска шага (`runner.role_cmd`,
  `orchestrator/runner.py:1204`; `orchestrator/doctor/isolation.py:201`;
  прямой вызов `runner.role_env("developer", "01ABCDEF")` в
  `tests/test_multitarget.py:702`): требование 9 к ним не относится, их
  поведение не меняется.
- Правка `orchestrator/role_prompt.py` и `orchestrator/knowledge_cards.py`:
  строка миссий шага — образец для правила белого списка, она не меняется.
- Полный зелёный набор `tests/` и неизменность защищённых путей — их
  держит пульт.
