## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да | сужение белого списка / `GIT_CONFIG_NOSYSTEM` / проектные скилы применены ко всем задачам, включая артель |
| AC-2 | да | проектные скилы не добавлены; добавлены ДО скилов роли; порядок поля не соблюдён |
| AC-3 | частично | нет проверки имени (`..`/абсолютный путь читаются); отказ без имени проекта/поля/скила; проверка положена в `targets.check` (краснеет «другой проект собирает бриф») |
| AC-4 | частично | `Bash(python3:*)` оставлен; правило с относительным путём; `GIT_CONFIG_NOSYSTEM` не задан |

Отклонения:
- П-1 (AC-4, SPEC.md:85-92): критерий проверяет наличие/отсутствие
  отдельных правил, а треб. 5 (SPEC.md:52) говорит «стоит ТОЛЬКО правило».
  Не ловится мутация «в список добавлено лишнее правило» — например
  `Bash(python3 -m pytest:*)`, `Bash(python3 scripts/guard.py:*)` или
  широкое `Bash(python3 :*)`/`Bash(python3*)` (не равно буквально
  `Bash(python3:*)`, но разрешает тот же любой код). Нужна проверка точного
  значения `--allowedTools` целиком:
  `Bash(git:*),Bash(python3 <config.ROOT>/orchestrator/artel.py:*)`.
- П-2 (AC-4, AC-1): «argv шага» не привязан к пути запуска. Тест,
  зовущий `ClaudeProvider().command(..., <проект>)` напрямую, не ловит
  мутацию «`runner` (`runner.py:1550`) не передаёт проект задачи» — шаг
  внешнего проекта пойдёт со старым `Bash(python3:*)`. То же для
  окружения: `role_env` с явным проектом против `role_env` пути шага.
  Критерий стоит читать как argv/окружение, переданные в `spawn_agent` при
  запуске шага задачи внешнего проекта; SPEC это не фиксирует.
- П-3 (треб. 2, SPEC.md:45-47): у требования «проверка допустимости имени
  вызывается отдельно от сборки брифа, по записи проекта» нет критерия.
  Мутация «проверка вшита в сборку брифа, отдельного вызова нет» не
  ловится ни одним AC, а от этого вызова зависит `doctor` части 2.
- П-4 (AC-3, SPEC.md:75-78): не проверяется имя с подкаталогом внутри
  `skills/` (`sub/name`) — треб. 2 говорит «прямо в `skills/`». Мутация
  «допускаются вложенные пути» проходит. Мелкое.
- П-5 (треб. 4, SPEC.md:49): треб. 4 не ограничено провайдером, а AC-4
  проверяет окружение только у шага Claude. Окружение шага Codex
  внешнего проекта не проверено (оно собирается в `runner.role_env`, не в
  провайдере). Мелкое: Codex на внешних проектах вне рамки родителя.

## Пути обхода гейтов
- Е-1 (А-1, правило «скилы — с `main`»): если исполнитель буквально
  прочтёт текст проектного скила с диска `config.ROOT/skills/<имя>.md`
  (как написано в AC-2, SPEC.md:72), в бриф роли внешнего проекта попадёт
  незакоммиченный текст защищённого пути `skills/` из рабочей копии
  пульта — мимо ревью MR Оператора, которое `skills/` держит
  (`config.PROTECTED_PATHS`) и мимо правила `brief.py:521-526`. Если же
  существование проверять на диске, а текст читать с `main`, то файл,
  есть на диске и нет в `main`, пройдёт проверку и уронит сборку общим
  отказом `skills_text` (`brief.py:544-545`) без имени проекта и поля —
  нарушение треб. 2 по тексту отказа. SPEC должен назвать один источник
  и для существования, и для текста.
- Е-2 (fail-open по проекту): новый параметр проекта у `command` и
  определение проекта в `role_env` естественно делать с дефолтом
  «артель» (так требуют зеро-арг вызовы `runner.py:1204`,
  `doctor/isolation.py:201` и `tests/test_multitarget.py:702`). Тогда
  любой сбой определения проекта задачи внешнего проекта (задачи нет в
  БД, исключение чтения) молча даёт роли широкий `Bash(python3:*)` и
  окружение без `GIT_CONFIG_NOSYSTEM`. SPEC не требует, чтобы на пути
  шага задачи проект определялся явно и неудача была отказом, а не
  дефолтом артели. Частично закрывается П-2 (AC через путь запуска).
- Е-3 (П-1): буквальное выполнение AC-4 допускает лишние широкие
  правила `python3` рядом с разрешённым.
- Обходы через `git -c alias`/`core.fsmonitor` и код, исполняемый
  `plank-run`/`suite-run`, — принятый остаточный риск (ADR-0023, вторая
  поправка, п.5; SPEC «Не входит») — отклонением не считаются.

## Вердикт
concerns — SPEC можно вести дальше; отклонения решаются Оператором на
гейте SPEC уточнением формулировок, без возврата аналитику:

1. А-1 / Е-1 — источник текста проектного скила не задан и расходится с
   правилом «скилы — с головы `main`» (`orchestrator/brief.py:521-526`,
   `:543`; SPEC.md:37-39, :71-73). Предложение: существование и текст —
   из одного источника; если Оператор оставляет диск (решение Ф-5
   родителя) — явно принять, что незакоммиченный `skills/` пульта доходит
   до роли внешнего проекта; иначе — `main` пульта для обоих.
2. П-1 / Е-3 — AC-4 (SPEC.md:85-90) должен требовать точное значение
   `--allowedTools` целиком, а не наличие/отсутствие отдельных правил
   (треб. 5 «только правило», SPEC.md:52).
3. П-2 / Е-2 — AC-1/AC-4 не привязаны к пути запуска шага
   (`orchestrator/runner.py:1550`, `runner.py:964`); не требуется, чтобы
   сбой определения проекта на пути шага был отказом, а не дефолтом
   артели.
4. П-3 — у треб. 2 «проверка вызывается отдельно от сборки брифа»
   (SPEC.md:45-47) нет критерия приёмки.
5. П-4 (мелкое) — AC-3 (SPEC.md:75-78) не проверяет имя с подкаталогом
   внутри `skills/`.
6. П-5 (мелкое) — треб. 4 (SPEC.md:49) для шага Codex внешнего проекта не
   покрыто критерием.

достаточны; ослаблений тестов и расширения песочницы нет.
