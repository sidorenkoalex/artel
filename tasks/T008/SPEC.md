# SPEC: Очистка хвостов задачи при kill

## Контекст
`kill` меняет только состояние в БД. Каталог `tasks/<id>/` с артефактами
убитой задачи остаётся в рабочем дереве — при прогоне T001 шаблонный
SPEC убитой T002 попал в коммит чужой ветки через `git add -A`
разработчика (ревьювер поймал как мусор в шине артефактов). По дизайну
(docs/design.md §6 «Завершение и уборка») уборка — обязанность
оркестратора.

## Требования
1. `kill <id>` дополнительно к смене состояния убирает хвосты задачи:
   - каталог `tasks/<id>/` — удаляется, если его содержимое не попало
     в main (незакоммиченное или закоммиченное только в ветке задачи);
     если артефакты уже в main (задача убита после мержа) — не трогать;
   - локальная ветка задачи — удаляется, если не смержена в main;
     смержённая не трогается.
2. Всё удалённое перечисляется в журнале шагов (что именно убрано:
   каталог, ветка) — уборка прозрачна и разбираема постфактум.
3. `kill` уже убитой/несуществующей задачи ведёт себя как сейчас
   (не падает на повторе, отсутствие — понятная ошибка).
4. Логи прогонов в `.artel/logs/` НЕ удаляются (история наблюдаемости).
5. Юнит-тесты в tests/: убитая до коммита задача — каталог удалён;
   убитая с ветку-only артефактами — каталог и ветка удалены; убитая
   после мержа (артефакты в main) — ничего не удалено; журнал содержит
   перечень убранного. Git-операции в тестах — через временный
   репозиторий или подмену вызовов.

## Критерии приёмки
1. Сценарий T002 больше не воспроизводится: `new` → `kill` → каталога
   `tasks/<id>/` нет, `git status` чист, следующая задача не может
   захватить чужой шаблон.
2. `kill` задачи, чьи артефакты в main (например, done-задача),
   не удаляет ничего и говорит об этом.
3. `python3 -m unittest discover -s tests` зелёный, guard и CI зелёные.

## Не входит
- Уборка веток/каталогов на remote (GitHub) — только локально.
- Автоматическая уборка при done (ветку после мержа чистим отдельной
  задачей, если понадобится).
- Команда `auto` и оптимизация контекста ревьювера.
