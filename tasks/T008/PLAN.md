# PLAN: Очистка хвостов задачи при kill

## Подход

`cmd_kill` (orchestrator/artel.py:814-818) сейчас делает ровно две вещи:
проверяет, что задача есть, и переводит её в `killed`. Каталог
`tasks/<id>/` и локальная ветка задачи остаются в рабочем дереве — так
шаблонный SPEC убитой T002 и попал в чужую ветку. Добавляем в `kill`
шаг уборки: тонкая обёртка над git (`git(...)`), набор проверок
«что можно трогать» и одна запись журнала с перечнем убранного и
оставленного.

Ключевые решения:

- **Уборка идёт после смены состояния и никогда не отменяет её.**
  Смена состояния — контракт `kill`, уборка — следствие. Любой сбой git
  или файловой системы становится строкой «оставлен: <причина>» в
  журнале, а не исключением: kill switch обязан срабатывать всегда.
- **Признак «артефакты в main» — наличие каталога в дереве main**
  (`git ls-tree -r --name-only main -- tasks/<id>`), а не сравнение
  содержимого. Задача, убитая после мержа, имеет свои артефакты в main
  (`docs/design.md` §6: артефакты остаются как история) — такой каталог
  не трогаем целиком. Частичное совпадение (часть файлов в main, часть
  нет) трактуем как «в main»: удалить каталог, кусок которого уже
  история, хуже, чем оставить лишнее.
- **Каталог и ветка убираются независимо друг от друга.** Требование 1
  задаёт два разных условия («содержимое не в main» и «ветка не
  смержена»), и они расходятся: у смержённой задачи ветка может нести
  лишний коммит сверх main, у неслитой — каталога в рабочем дереве может
  не быть вовсе.
- **Не смержена = `git branch --merged main` её не показывает.** Это тот
  же критерий, которым git защищает `-d`; удаляем через `-D`, потому что
  `-d` на неслитой ветке отказывает — а по требованию 1 удалить надо
  именно неслитую.
- **Ветка задачи под HEAD — уборка пропускается целиком.** Агент
  разработчика работает в том же рабочем дереве (`cmd_run` запускает
  claude с `cwd=ROOT`), поэтому к моменту `kill` HEAD вполне может стоять
  на ветке задачи. Удалить checked-out ветку git не даст, а удалить
  каталог, закоммиченный в неё же, — значит оставить грязное дерево,
  ровно тот мусор, от которого задача избавляется. Поэтому пишем в
  журнал и консоль «переключись на main и повтори kill»: повтор
  безопасен по требованию 3 и доводит уборку до конца.
- **Отслеживаемый каталог не удаляется, чья бы ветка ни была под HEAD.**
  Защиты «ветка задачи под HEAD» мало: каталог убитой задачи мог уехать
  в *чужую* ветку через `git add -A` разработчика — это и есть инцидент
  T002 из SPEC «Контекст». Перед `rmtree` спрашиваем git, отслеживается
  ли каталог сейчас (`git ls-files -- tasks/<id>`, индекс — потому что
  просто добавленный `git add` каталог опасен так же, как закоммиченный);
  непустой ответ означает «оставлен» с причиной и способом довести
  уборку до конца. Иначе `rmtree` оставил бы в дереве удаления
  отслеживаемых файлов, и следующий `git add -A` утащил бы их в тот же
  чужой коммит — мусор вместо уборки.
- **Уборка перечисляется одной записью журнала `уборка`** — списком
  через `; `, включая оставленное и причину. Требование 2 просит
  перечень убранного; оставленное там же делает разбор постфактум
  однозначным (критерий приёмки 2: «не удаляет ничего и говорит об
  этом»), а одна запись читается в `log <id>` как один абзац.
- **`.artel/logs/` не упоминается в коде уборки вовсе.** Требование 4
  выполняется тем, что трогать логи нечему; фиксируем это тестом, а не
  комментарием.
- **git вызывается через `git(*args)`** — `subprocess.run` с `cwd=ROOT`,
  `capture_output`, без `check`. Отсутствие git (`OSError`) превращается
  в ненулевой код возврата, поэтому каждая проверка отвечает «не знаю» →
  «не трогаем». Мерж в `cmd_approve` на новую обёртку не переводим:
  это чужая зона задачи, там свой разбор ошибок с `sys.exit`.

Архитектурно значимого решения нет — ADR не требуется.

## Шаги

1. `orchestrator/artel.py`: обёртка `git()` и проверки состояния
   репозитория (`current_branch`, `branch_exists`, `branch_merged`,
   `artifacts_in_main`, `artifacts_tracked_here`); `cleanup_killed_task`
   — удаление каталога
   `tasks/<id>/` и неслитой локальной ветки со сбором перечня;
   вызов из `cmd_kill` после `set_state` с записью журнала `уборка`.
2. `tests/test_kill_cleanup.py`: временный git-репозиторий вместо
   рабочего (ROOT/TASKS/LOGS/DB уводятся в него, templates копируются) —
   сценарии «убита до коммита», «артефакты только в ветке», «убита после
   мержа», перечень в журнале, сохранность `.artel/logs/`, повторный
   kill, kill несуществующей задачи, ветка задачи под HEAD, каталог
   задачи в чужой ветке и в индексе main, немой git на каждой проверке.

Шаги 1–2 — один MR: тесты проверяют поведение, которого без шага 1 нет.

## Риски

- Уборка удаляет данные — единственная разрушительная операция Фазы 0
  после `merge`. Защита строится на отказе по умолчанию: любой
  невыясненный факт (git промолчал, main не найден, HEAD на ветке
  задачи) означает «не трогаем». Худший исход — мусор остался и виден в
  журнале, а не «удалено лишнее».
- Незакоммиченная работа на неслитой ветке пропадает вместе с веткой
  безвозвратно (`-D`, reflog живёт ограниченно). Это и есть смысл
  `kill`, но подтверждения у команды нет — как и раньше.
- Каталог удаляется целиком, включая файлы, которых оркестратор не
  создавал (черновики, заметки в `tasks/<id>/`). Уборка по списку
  известных артефактов оставляла бы каталог непустым и не решала бы
  исходный инцидент.
- Проверка «в main» смотрит на локальный main. Ветка, смержённая в
  origin/main, но не подтянутая локально, будет выглядеть неслитой и
  удалится. Уборка remote вне объёма (SPEC «Не входит»), а локальный
  main оркестратор обновляет сам при мерже (`cmd_approve`).
