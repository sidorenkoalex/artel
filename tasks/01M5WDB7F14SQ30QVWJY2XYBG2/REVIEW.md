## Замечания

- major — `orchestrator/gitcmd.py` (`_push_plan`, ветка определения проекта:
  `if project is None and dest and not _is_url(dest): project =
  _project_of_path(cwd / dest.removeprefix("file://"))`).
  `_is_url("file:///…")` истинно (в адресе есть `://`), поэтому для
  `file://`-адреса проверка пути не выполняется вовсе, и
  `removeprefix("file://")` — мёртвый код. Дальше `project_by_url` не находит
  записи (её `url` — адрес сервера). Проект падает в `config.DEFAULT_TARGET`,
  и `_push_plan` не проверяет ничего.
  Сценарий воспроизведён пробой
  (`tasks/01M5WDB7F14SQ30QVWJY2XYBG2/probe_file_url.py`, прямой вызов
  `_push_plan` из корня пульта):
  - запись `target-human`, `push <projects>/qhuman/repo main` — отказ
    «отправка не из клона проекта»;
  - тот же вызов `push file://<projects>/qhuman/repo main` — план без
    отказа;
  - при испорченном `targets.yaml`: простой путь — отказ «гейт мержа
    неизвестен», `file://` — без отказа.

  Это нарушение требования 3 (г) («отправки по URL или пути, ведущему в клон
  внешнего проекта … откуда бы ни шла команда») и обход (в): отправка в
  `main`, тег или `+refspec` в клон проекта под белым списком проходит без
  проверок. Других мест этого класса в diff нет: проект по назначению
  определяется только здесь.
  Предложение: снимать `file://` до проверки `_is_url` (например, проверять
  путь для `dest` без схемы и для `file://`-адреса). Добавить в
  `tests/test_gitcmd_push_point.py` случай `file://` рядом с простым путём:
  отказ до процесса — при записи `target-human` и при испорченном
  `targets.yaml`.
