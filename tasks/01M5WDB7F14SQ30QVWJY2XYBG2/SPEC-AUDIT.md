# SPEC-AUDIT: GitLab Б1.1 — поля записи, ветка по шаблону, единая точка отправки с журналом и белым списком

## ТЗ и SPEC
Требования ТЗ 1–3 перенесены в SPEC почти дословно (SPEC.md:36-112), «Не
входит» и «Только чтение» — тоже (SPEC.md:184-210). Требований сверх ТЗ нет:
уточнения «обязано компилироваться» (SPEC.md:44-45) и «иное значение — отказ»
(SPEC.md:46-47) повторяют проверку формы из ТЗ. Расхождения:

1. Критерий ТЗ «артель и проект с полями по умолчанию: существующие тесты
   `new`, деления, отправок, `cleanup` зелёные без правки» в SPEC — не AC-n, а
   пункт «Не входит» со словами «её держит пульт» (SPEC.md:204-210). По смыслу
   свойство держится (гейт неослабления тестов, мандат — эскалацией), но
   формулировка внутри «Не входит» читается как «не забота этой задачи».
   Мелкое.
2. В SPEC нет фактов ТЗ «несколько ссылок одной системы сейчас допустимы»,
   «отправки идут из клона проекта, не из рабочей копии задачи» и отсылки
   `artifact_cleanup.py:103` как формы удаления `refs/artifacts/<id>`. Ни одно
   требование от этого не теряется. Информационно.
3. Поле `policy.push_options_forbidden` есть в ТЗ и SPEC только как ссылка
   (SPEC.md:58, AC-1 SPEC.md:120), но в перечне полей требования 1
   (SPEC.md:36-65) его нет: ни раздела, ни вида, ни умолчания. ADR-0029 его
   тоже не называет (grep по `orchestrator/` и ADR пуст). Разработчику
   придётся додумать его форму, а запись с ним без объявления не загрузится
   (см. «Факты», п. 4). Отклонение.

## Факты против кода
Подтвердилось:
- Ветка задачи — `orchestrator/catalog.py:918` `f"task/{task_id.lower()}-{slugify(title)}"`
  в `_new_task_row` (SPEC.md:18 даёт :918; в ТЗ было :912 — SPEC поправил
  верно). При делении ветка строится в `spawn_subtask` → `_new_task_row`
  (catalog.py:1031), до `store.copy_external_refs` (catalog.py:1038).
- `fsm._spawn_division_subtasks` — fsm.py:1037; цикл частей — fsm.py:1070-1073;
  родитель уходит в `killed` после всех частей — fsm.py:1088.
- `gitcmd.HOSTING_SUBCOMMANDS` — gitcmd.py:37; `_declared_targets` при
  `TargetsError` возвращает `{}` — gitcmd.py:86-91; определение проекта —
  gitcmd.py:94-118, токен — :121-142.
- Точки запуска: `git` :164 (`subprocess.run` :187), `carpentry` :341 (:369),
  `read` :413 (:434), `read_env` :441 (`Popen` :451), `read_stream` :469
  (`Popen` :481). Только `git()` сейчас зовёт `_hosting_project`; остальные
  четыре проекта не определяют — требование 3(г) это и покрывает.
- `targets.unsupported_reason` — targets.py:270-290 (А0 влит в ветку,
  5705cfdf8); `REF_REQUIRED_FIELD`/`REF_SYSTEMS_FIELD` — targets.py:320-321;
  `catalog._new_refs` — catalog.py:582-609.

Не совпало или не сказано:
1. «Пять точек запуска git» (SPEC.md:20-22, 106-108) — в `gitcmd` есть шестой
   `subprocess.run`: `check_ignore`, gitcmd.py:549. Аргументы фиксированы
   (`check-ignore`), отправки через него нет. Мелкое, в счёт не идёт.
2. `{id}` по умолчанию — это `task_id.lower()` (catalog.py:918). SPEC
   (SPEC.md:38-40) не говорит, что `{id}` подставляется в нижнем регистре:
   «по умолчанию — нынешнее поведение» выполняется, только если это так, а для
   шаблонов не по умолчанию регистр `{id}` не определён. Мелкое.
3. Отказ деления (SPEC.md:77-82) не привязан к месту. В коде есть правило
   «отказанное деление не оставляет ни zones, ни merge_after, ни потолка»
   (комментарий fsm.py:1396-1400, `_division_check` на fsm.py:1403). После него
   записи идут так: журнал заявленных изменений (fsm.py:1409-1426), `zones`/
   `merge_after` (fsm.py:1431-1433), `apply_spec_budget` (fsm.py:1444), эпик
   `approve --as-epic` (`epics.create_from_division`, fsm.py:1066-1069) —
   до первой части. Отказ внутри `_spawn_division_subtasks` формально даст
   «частей нет, родитель в spec_gate», но оставит эти записи и пустой эпик.
   SPEC должна требовать отказ в `_division_check` (до первой записи и до
   эпика). Отклонение.
4. `targets._check_local_sections` отказывает неизвестному полю раздела
   (targets.py:441-443): каждое новое поле нужно внести в `LOCAL_FIELDS`
   (targets.py:326-337) и в `_flatten` (targets.py:585-588). Для
   `push_options_forbidden` (см. «ТЗ и SPEC», п. 3) SPEC не задаёт даже
   раздела. Подтверждает отклонение «ТЗ и SPEC», п. 3.
5. `cleanup.py:268` уже сам передаёт `--force-with-lease={ref}:{head}` с
   `head` не из журнала. SPEC (SPEC.md:100-102) говорит, что эту форму
   «строит сама точка отправки», а AC-6 (SPEC.md:159-160) передаёт флаг от
   вызывающего. Как часть 2 будет просить перезапись — флагом или
   параметром, — не определено. Для проектов `operator` это не важно
   (SPEC.md:110-112), для `target-human` cleanup — это Б2. Неоднозначность
   интерфейса, мелкое.
6. Журнал (`store.journal`, store.py:1551) пишется по `task_id`. Отказ
   отправки, не связанной ни с одной задачей (в `main`, в `feature/PROJ-8`,
   тег, без refspec), по SPEC «с записью журнала» (SPEC.md:96-104; AC-6
   SPEC.md:157-158), но в журнал какой задачи — не сказано. Отклонение (см.
   «Проверяемость»).
7. Противоречие требований. 3(г) «нечитаемая запись проекта для пути клона
   проекта — отказ отправки» (SPEC.md:108-109) против «у проекта `operator` …
   отправки, кроме (а) и (б), прежние» (SPEC.md:110-112). Если запись не
   читается, `merge_gate` неизвестен, поэтому отказ ляжет на ВСЕ внешние
   проекты, в том числе `operator`. Сейчас отправка там идёт с прежней
   авторизацией: `_declared_targets` → `{}` (gitcmd.py:86-91), а
   `_hosting_project` → `None` (gitcmd.py:106-118). Это смена поведения
   проектов `operator`, SPEC её не называет. Тестом на прежнее поведение не
   держится (grep `tests/` по `_declared_targets`/`_hosting_project` пуст).
   Отклонение: решение за Оператором — принять смену явно или сузить отказ.

## Пути обхода гейтов
1. Белый список проверяет только refspec, но не репозиторий назначения
   (SPEC.md:91-105). Отправка своей ветки или `refs/artifacts/*` по чужому URL
   проходит. Проект по URL определяется только при читаемой записи
   (gitcmd.py:111-117, `project_by_url` :76-77): при испорченном
   `targets.yaml` отправка по URL из корня пульта (так шлёт
   `doctor/artifact_branches.py:140`) не узнаётся как отправка проекта и идёт
   мимо отказа 3(г), который SPEC ограничивает «путём клона проекта»
   (SPEC.md:108-109). Помощник учётных данных отдаёт токен любому хосту
   (gitcmd.py:41-43). Отклонение: ТЗ требует проверять «любую отправку на
   сервер», а SPEC не называет ни допустимого remote, ни отказа при
   неопределённом проекте.
2. `push --dry-run` с кодом 0 по букве (а) (SPEC.md:86-88) оставляет «ветка
   отправлена: <sha>», хотя на сервер ничего не ушло. Пробные `--dry-run` в
   коде уже есть (`doctor/project_checks.py:98`). Такой sha затем проходит
   сверку `--force-with-lease` (SPEC.md:102-104), и перезапись опирается на
   голову, которой на сервере не было. Отклонение: исключить `--dry-run` из
   (а) или отказывать ему.
3. Запреты флагов — перечень (SPEC.md:99-100), а не список разрешённых. Флаги
   вне перечня (`--prune`, `--receive-pack`/`--exec`, `--repo=<url>`,
   `--force-with-lease` без `=<ref>:<sha>`) буквой SPEC не запрещены. Голый
   `--force-with-lease` перезаписывает по удалённой отслеживающей ветке, без
   журнала. Отклонение: требование «единственная форма перезаписи»
   (SPEC.md:100-101) есть, но AC-6 его обход не проверяет.
4. Форма элемента `push_options` (SPEC.md:56-57) не держится критерием, а
   запрещены только `ci.skip` и имена из `push_options_forbidden`. Опции
   GitLab `merge_request.create`, `merge_request.merge_when_pipeline_succeeds`,
   `merge_request.target=…` создают и вливают MR при отправке, то есть в
   обход гейта мержа и людей проекта. Если такой элемент окажется в записи
   (формой `ИМЯ=значение` он проходит), (б) приложит его к каждой отправке
   ветки задачи. Отклонение: добавить в отказ `merge_request.*` или проверить
   форму элемента в AC-1.
5. Деление: отказ можно поставить после записей гейта или после заведения
   эпика `--as-epic`, и AC-5 это пропустит (см. «Факты», п. 3). Две части с
   одинаковым slug при `feature/{slug}` получат одну ветку, сверка с сервером
   и с БД этого не увидит (SPEC.md:80-82).

## Вердикт
**concerns.** Отклонения есть, все решаемы Оператором на гейте SPEC
(уточнением SPEC или явным принятием). Ответ Оператора для самого вердикта не
нужен.

1. Противоречие: 3(г) «нечитаемая запись → отказ» против «`operator` —
   прежние» — SPEC.md:108-112; gitcmd.py:86-91, 106-118.
2. Атомарность отказа деления: место отказа не задано (нужно
   `_division_check`, fsm.py:1403, до записей fsm.py:1409-1446 и эпика
   fsm.py:1066-1069); AC-5 этого не ловит — SPEC.md:77-82, 144-148.
3. Конфликт имён частей между собой при шаблоне без `{id}` не назван —
   SPEC.md:80-82.
4. Журнал отказа отправки, не связанной с задачей, не определён —
   SPEC.md:96-104, 157-158; store.py:1551.
5. `policy.push_options_forbidden` не объявлено (раздел, вид, умолчание) —
   SPEC.md:56-58, 120; targets.py:326-337, 441-443.
6. AC-4 проверяет занятость имени только у `done`, а не у `killed` —
   SPEC.md:139-140; ADR-0029:54.
7. AC-6 не ловит голый `--force-with-lease`/`--force-with-lease=<ref>` и флаги
   вне перечня — SPEC.md:99-101, 155-160.
8. `--dry-run` оставляет «ветка отправлена» — SPEC.md:86-88;
   doctor/project_checks.py:98.
9. Репозиторий назначения не ограничен; отправка по URL при нечитаемой записи
   идёт мимо отказа 3(г) — SPEC.md:91-109; gitcmd.py:41-43, 76-77, 111-117;
   doctor/artifact_branches.py:140.
10. `push_options`: форма элемента не держится AC, опции `merge_request.*` не
    запрещены — SPEC.md:56-58, 116-122.
11. Вид `machine.commit_author` не задан — SPEC.md:52-53, 125.
12. Мелкое: регистр `{id}` (catalog.py:918, SPEC.md:38-40); `ref_pattern` без
    `{ref}` (SPEC.md:70-71, ADR-0029:53); интерфейс перезаписи «строит сама
    точка» против флага от вызывающего (SPEC.md:100-102, 159-160;
    cleanup.py:268); критерий ТЗ о зелёности существующих тестов перенесён в
    «Не входит» (SPEC.md:204-210); «пять точек» без `check_ignore`
    (gitcmd.py:549).
