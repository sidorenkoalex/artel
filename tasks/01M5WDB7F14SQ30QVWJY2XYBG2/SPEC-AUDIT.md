## Пути обхода гейтов
1. **`-o ci.skip` и запрещённые переменные мимо проверки загрузки.** Запрет
   `ci.skip` и имён из `push_options_forbidden` SPEC ставит только загрузке записи
   (SPEC.md:61-66); в точке отправки флаг `-o <опция>` разрешён с единственным
   исключением `merge_request.*` (SPEC.md:114). Вызывающий код, передав
   `-o ci.skip` или `-o ci.variable=SECRET=…` в argv, пройдёт белый список —
   ADR-0029 п. 11 («`-o ci.skip` запрещён») держится только для опций из записи.
2. **Глобальные опции git перед `push`.** Белый список SPEC — флаги `push`
   (SPEC.md:113-120); про опции до подкоманды (`git -c remote.origin.url=…`,
   `-c url.<x>.pushInsteadOf=…`, `-c core.hooksPath=…`) SPEC молчит, а
   распознавание отправки в `_hosting_project` (gitcmd.py:97-105) пропускает
   только пары `-C`/`-c` — `git --git-dir=… push` или `git --no-pager push` вообще
   не распознаются как отправка. Буквально выполненный SPEC: «назначение —
   `origin`» проверено по argv, а `-c` переадресовал `origin`. Нужна норма: какие
   глобальные опции допустимы при отправке (пульт сам ставит `-c http.lowSpeed*` —
   cleanup.py:257, и `-c push.followTags=false` — SPEC.md:125) и как распознаётся
   «отправка» при прочих глобальных опциях.
3. **Отправка по URL не из клона при нечитаемом `targets.yaml`.** SPEC.md:132-135
   отказывает отправке «из клона» внешнего проекта; отправка из главной копии пульта
   по URL проекта (так шлёт `doctor/artifact_branches.py:140`, `source` — клон или
   главная копия) определяется через `project_by_url`, а при нечитаемом слое он даёт
   `None` (gitcmd.py:73-83) — проект не определён, отказа нет, белый список не
   применяется.
4. **«Запись нечитаема» против «записи нет».** SPEC.md:132 и AC-7 говорят об
   испорченном `targets.yaml`. Клон под `.artel/projects/<имя>/` при читаемом
   слое без записи `<имя>` (`_declared_targets().get(name)` → `None`,
   gitcmd.py:107-110) — `merge_gate` тоже неизвестен; SPEC не говорит, отказ это или
   прежнее поведение. Одно прочтение даёт обход (необъявленный проект без белого
   списка), другое может покраснить существующие тесты с областью проекта без записи.

## Вердикт

отклонения решаемы Оператором на гейте (возврат был один, «дальше approve»):

1. SPEC.md:114 (+ :61-66) — точка отправки не отказывает `-o ci.skip` и `-o` с
   именем из `push_options_forbidden`; запрет ADR-0029 п. 11 обходится передачей
   опции в argv. AC-6 этот случай не держит. (Обход 1.)
2. SPEC.md:113-125 — нет нормы для глобальных опций git перед `push` (`-c …`,
   `--git-dir`) и для распознавания отправки (gitcmd.py:97-105); назначение и
   хук обходятся `-c`. (Обход 2.)
3. SPEC.md:126-129 — «журнал задачи, в контексте которой выполняется команда»:
   механизма контекста в `gitcmd` нет (`ARTEL_TASK`, config.py:103, ставится только
   окружению роли — runner.py:1182; команды Оператора его не несут), SPEC его не

   вид алерта (`alerts.KINDS`, alerts.py:103) не назван.
4. SPEC.md:132-135, AC-7 — отказ при нечитаемом слое только «из клона»: отправка
   по URL не из клона проходит (gitcmd.py:73-83; doctor/artifact_branches.py:140);
   случай «слой читаем, записи проекта нет» не определён (gitcmd.py:107-110).
   (Обходы 3, 4.)
5. SPEC.md:119 против `orchestrator/doctor/project_checks.py:98` (только чтение) —
   пробный `push --dry-run` doctor 5.2 для записи ≠ `operator` станет отказом;

6. AC-3, AC-4 (SPEC.md:168-174) — «задачи нет» не требует отсутствия ссылки

9. AC-9 (SPEC.md:216-218) — «отправленный локальный sha» проверяем мутацией

10. SPEC.md:86-87 — `_division_check` указан строкой вызова fsm.py:1403, функция —
