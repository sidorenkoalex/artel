## Пути обхода гейтов
1. **Инъекция конфигурации клона.** Рабочие копии задач делят `config` с
   клоном проекта. Роль, работающая в рабочей копии, может записать
   `push.pushOption=merge_request.create` или
   `merge_request.merge_when_pipeline_succeeds`,
   `remote.origin.pushurl=<чужой адрес>`, `remote.origin.push=<refspec>`,
   `remote.origin.mirror=true`. Следующая отправка пульта с токеном
   Оператора выглядит в argv как разрешённая (`push -u origin <своя ветка>`),
   но git добавит опции и назначение из конфигурации. Белый список проверяет
   только argv. SPEC закрывает этот класс одним `-c push.followTags=false`
   (SPEC.md:141), то есть сам класс признан, но закрыт не полностью.
   Решения №1.10 («`merge_request.*` запрещены всегда») и №1.9 («назначение
   — только `origin`/`url`») обходятся. Это PLAUSIBLE: запись в общий
   `config` из шага роли зависит от песочницы, проверить её здесь нельзя.
   Отклонение 4.
2. **Глобальные опции вне перечня.** `--config-env=<ключ>=<переменная>`
   равносилен `-c`, но в перечне SPEC.md:127-131 его нет. Переменные
   `GIT_CONFIG_COUNT/KEY/VALUE` в `env` точек `carpentry`/`read_env`
   (`gitcmd.py:341,441`) дают тот же эффект. Отклонение 5.
3. **Распознавание только по подкоманде `push`** (SPEC.md:127). `send-pack`
   и псевдоним из конфигурации клона (`alias.p=push`) — тоже отправки, но
   проверку не проходят. Сейчас пульт ими не пользуется, обход остаётся на
   будущее. Отклонение 5.
4. **TOCTOU деления.** Имена проверяются в `_division_check` (`fsm.py:1403`),
   а части заводятся после записей гейта (`fsm.py:1414-1444`, затем
   `:1455`). В этом окне имя может занять другая задача. Окно короткое и
   заслоняется `approve` под lease. Отмечено, в вердикт не выносится.

## Вердикт
**concerns.** SPEC верен по фактам и прослеживается к ТЗ и обоим решениям
Оператора. Отклонения ниже Оператор может снять на гейте, переписывать SPEC
аналитику для этого не нужно.

1. **Пример `X` против нормы формы `push_options`.** Тр. 1 (SPEC.md:59-63)
   и AC-1 (SPEC.md:170-172) требуют отказа загрузки для элемента без `=`.
   Тр. 3 (в) (SPEC.md:124-127) проверяет `-o` в argv «той же нормой». При
   этом AC-9 (SPEC.md:262) строит запись `push_options: [X, Y]`, которая не
   загрузится, а AC-6 (SPEC.md:239) ждёт, что `-o X` пройдёт. Исполнитель
   выберет одно из двух: ослабить норму формы или пропустить AC-9/AC-6.
   Нужен пример формы `ИМЯ=значение` (например `[A=1, B=2]`) и уточнение,
   что «та же норма» для argv включает проверку формы.
2. **`--delete` для `refs/artifacts/<id>`.** Флаги — только белым списком
   `-u`/`-q`/`-o`/`--force-with-lease` (SPEC.md:122-124), а «иные удаления
   (`--delete`, `:<ref>`)» — отказ (SPEC.md:132-133). При этом удаление
   `refs/artifacts/<id>` разрешено, и AC-6 (SPEC.md:240-241) ждёт, что оно
   пройдёт. Форма не названа: разрешён ли `--delete refs/artifacts/<id>` или
   только `:refs/artifacts/<id>`. Тест может закрепить любую из двух.
3. **Место предиката `merge_gate`.** SPEC не говорит, что предикат
   «`merge_gate` ≠ `operator`» должен жить в `targets.py`. Сравнение с
   литералом в `gitcmd.py` красит долгоживущий тест
   `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:474`.
4. **Инъекция конфигурации клона (PLAUSIBLE).** Проверка argv не закрывает
   отправку, которую меняет общий `config` клона: `push.pushOption`,
   `remote.origin.pushurl`/`push`/`mirror`. Защищён только `followTags`
   (SPEC.md:141). Вероятная мера: точка отправки сама добавляет
   `-c push.pushOption=` (сброс списка) и отказывает при `pushurl`/`push`/
   `mirror` у `origin`. Решение за Оператором: принять в этой части или
   отнести к хуку `pre-push` Б2.
5. **Неполный перечень глобальных опций и подкоманд.** Нет
   `--config-env`, переменных `GIT_CONFIG_*` в `env` точек
   (`gitcmd.py:341,441`) и подкоманд кроме `push` (`send-pack`, псевдонимы)
   (SPEC.md:127-131).
6. **Параметр `task_id` никто не передаст.** Ни одна команда пульта не
   передаёт его в этой задаче: все отправляющие команды вне зон или только
   для чтения (`github_adapter.py:166,241`, `artifact_branch.py:427`,
   `snapshot.py:297`, `cleanup.py:265,268`, `fsm_merge_gate.py:744,1316`).
   Журнал отказа из сессии Оператора на практике уйдёт в алерт `incident`.
   Это не нарушает AC-6, его проверяют прямым вызовом. Стоит назвать в
   SPEC, что передачу параметра из этих команд делает Б2 или отдельная
   задача (SPEC.md:146-148).
7. **Артель под областью проектов.** Клон артели `.artel/projects/artel/repo`
   лежит под `projects_root()` (`repo_context.py:78-82`), а тр. 3 (г)
   (SPEC.md:150-157) не исключает его явно. Это расходится с
   `repo_context.py:85-89` (артель работает при сломанном `targets.yaml`).
   Нужна формулировка «клон внешнего проекта под областью проектов».
8. **Поля для записей слоя репозитория.** `_flatten` (`targets.py:579`)
   действует только для локального слоя. Для записи слоя репозитория
   (артель) SPEC не говорит, допустимы ли новые поля и откуда берётся `[]`
   у `ci_required_jobs` (SPEC.md:67-70, AC-2).
9. **(а) при удалении с lease.** Пишет ли (а) «ветка отправлена» при
   удалении ветки с `--force-with-lease` (`cleanup.py:268-269`, проект
   `operator`), не определено: sha у удаления нет. Стоит прямо исключить
   удаления из (а) (SPEC.md:109-112).
