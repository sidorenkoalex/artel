Требуется:
1. Поля записи (`targets.py`, проверка при загрузке, значения по умолчанию — нынешнее поведение; отказ загрузки называет имя поля): `policy.branch_template` (по умолчанию `task/{id}-{slug}`, подстановки `{id}`, `{slug}`, `{ref}`; `{ref}` — ключ ссылки системы `policy.ref_required`; шаблон с `{ref}` без `ref_required` — отказ); `policy.ref_pattern` (регулярное выражение ключа, полное совпадение); `policy.freshness` `merge` (по умолчанию) | `rebase` (`rebase` без `squash_before_mr: true` — отказ); `policy.squash_before_mr` (по умолчанию `false`); `policy.commit_template` (по умолчанию `{id}: {text}`, подстановки `{id}`, `{ref}`, `{text}`; отличный от умолчания без `squash_before_mr: true` — отказ); `machine.commit_author` (имя и email) и `policy.co_author` (строка `Co-authored-by: …`) — необязательны; `policy.push_options` (список, по умолчанию пуст; элемент — `ci.variable=ИМЯ=значение` или `ИМЯ=значение`; отказ на `ci.skip` и на элемент, чьё `ИМЯ` есть в `policy.push_options_forbidden`); `policy.ci_required_jobs` (список, по умолчанию пуст); `policy.mr_assignee`, `policy.draft_mr` (по умолчанию `true`), `policy.max_in_flight` — только объявление и проверка. Проверка формы: `freshness` — одно из `merge`, `rebase`; `ref_pattern` — компилируемое регулярное выражение; `commit_author` — имя и email; `co_author` — строка, начинающаяся с `Co-authored-by: `; `mr_assignee` — непустая строка; `draft_mr` — булево; `max_in_flight` — целое > 0; `ci_required_jobs` — список строк. Поля `freshness`, `squash_before_mr`, `commit_template`, `commit_author`, `co_author` исполняет часть 2.
2. Ветка задачи: `new` строит имя по `branch_template`; `{ref}` — ключ ссылки системы `ref_required`, при шаблоне с `{ref}` такая ссылка у `new` ровно одна — больше одной — отказ `new`; её ключ не по `ref_pattern` — отказ до заведения задачи. Только когда `branch_template` отличен от умолчания (или без `{id}`): `new` и деление отказывают, если ветка с этим именем уже есть на сервере (`ls-remote`) или у любой задачи проекта в любом состоянии (БД); сбой `ls-remote` — отказ с причиной «имя ветки не проверено». У артели и проектов с полями по умолчанию сетевого вызова нет. Деление при шаблоне с `{ref}` — отказ с причиной «ветка по ключу трекера: делите задачу в трекере», атомарно: частей нет, родитель остаётся на гейте SPEC. При шаблоне не по умолчанию без `{ref}` имена всех частей проверяются до заведения первой; конфликт хоть одной — отказ деления, ни одна часть не заведена. При шаблоне по умолчанию деление прежнее.
3. Единая точка отправки (`gitcmd`): (а) после каждой успешной (код 0) отправки ветки задачи (любой проект) пишет в журнал задачи запись «ветка отправлена: <sha>» с отправленным локальным sha; неудачная отправка записи не оставляет — по этой записи часть 2 берёт sha для `--force-with-lease`; (б) ко всем отправкам ветки задачи проекта добавляет `-o <опция>` на каждую строку `policy.push_options` (к `refs/artifacts/*` — нет); (в) белый список — только для проекта с `merge_gate`, отличным от `operator` (ADR-0029 п. 13): любая отправка на сервер проверяется до вызова git; «своя ветка» — имя ветки задачи этого проекта из БД в любом состоянии, кроме `killed` и `done`, совпавшее с назначением refspec; разрешены только своя ветка, `refs/artifacts/*` и удаление `refs/artifacts/<id>` задач этого проекта (`artifact_cleanup.py:103`); отправка в `base`, в ветку, не являющуюся своей, иные удаления (`--delete`, `:<ref>` — в том числе своей ветки), теги, отправка без явного refspec, флаги `--tags`, `--follow-tags`, `--mirror`, `--all`, `--force`/`-f` и refspec с `+` — отказ с причиной и записью журнала; единственная форма перезаписи — `--force-with-lease=<ref>:<sha>`, которую строит сама точка отправки; `<sha>` в ней сверяется с последней записью журнала задачи «ветка отправлена: <sha>» — другой sha или нет записи — отказ с причиной и записью журнала; отправка такого проекта идёт с `-c push.followTags=false`; (г) проверка — в одной внутренней функции, через которую проходят все пять точек запуска git в `gitcmd`, либо в каждой из них; нечитаемая запись проекта для пути клона проекта — отказ отправки. У проекта `operator` (в том числе с нестандартным `branch_template`), у артели и проектов с полями по умолчанию отправки, кроме (а) и (б), прежние — мерж и уборка пульта не меняются. Первичная защита — код единой точки отправки; хук `pre-push` — не в этой части.

Критерии приёмки:
- проверка записи: шаблон с `{ref}` без `ref_required`, `commit_template` без сжатия, `freshness: rebase` без `squash_before_mr: true`, `push_options` с `ci.skip` — отказ загрузки с именем поля; при `push_options_forbidden: [SECRET]` элементы `ci.variable=SECRET=1` и `SECRET=1` — отказ с именем поля `push_options`, `ci.variable=OTHER=1` — загружается; один параметризованный критерий формы полей — `freshness: squash`, `ref_pattern: "PROJ-("`, `commit_author` без email, `co_author: "Reviewed-by: X"`, `mr_assignee: ""`, `draft_mr: "yes"`, `max_in_flight: 0`, `ci_required_jobs: build` — каждый отказ загрузки с именем своего поля, допустимое значение загружается; запись без новых полей — значения по умолчанию;
- `new --ref tracker:PROJ-7` при `branch_template: feature/{ref}`, `ref_required: tracker`, `ref_pattern: PROJ-\d+` — ветка `feature/PROJ-7`; `--ref tracker:PROJ-7x` — отказ, задачи нет; `--ref tracker:PROJ-7 --ref tracker:PROJ-9` — отказ, задачи нет; ветка `feature/PROJ-7` уже на сервере (подменённый `ls-remote`) или у задачи проекта в `done` — отказ; сбой `ls-remote` — отказ «имя ветки не проверено»; при шаблоне по умолчанию `ls-remote` не вызывается (ни `new`, ни деление);
- деление при `feature/{ref}` — отказ с причиной «ветка по ключу трекера: делите задачу в трекере», ни одна часть не заведена (ни строки БД, ни ссылки документов), родитель в `spec_gate`; деление при `feature/{slug}`, когда занято имя второй части, — отказ, ни одна часть не заведена, родитель в `spec_gate`;
- белый список (запись с `merge_gate: target-human` в тесте; живого такого проекта до Б2 нет): отправка в `feature/PROJ-8`, которой нет среди веток задач проекта; в ветку задачи в `done`/`killed`; в `main`; удаление своей ветки (`--delete` и `:<ref>`); удаление `refs/artifacts/<id>` задачи, которой нет в БД проекта; тег; отправка без явного refspec; своя ветка с `--tags`, `--follow-tags`, `--mirror`, `--all`, `--force`, `-f` или `+<ветка>` — отказ до вызова git (шпион `subprocess.run` не вызван), запись журнала с причиной; отправка ветки живой задачи проекта, её перезапись `--force-with-lease=refs/heads/<ветка>:<sha>` с sha последней записи «ветка отправлена», отправка `refs/artifacts/<id>` и удаление `refs/artifacts/<id>` задачи проекта — проходят, вызов несёт `-c push.followTags=false`; перезапись с sha, отличным от последней записи «ветка отправлена», или без такой записи — отказ до вызова git и запись журнала с причиной;
- отправка в `main` через каждую из точек `git`, `carpentry`, `read`, `read_env`, `read_stream` — отказ до запуска процесса (шпионы `subprocess.run` и `subprocess.Popen` не вызваны); нечитаемая запись проекта (испорченный `targets.yaml`) — отправка из клона проекта отказана до запуска процесса;
- проект `operator` с `branch_template: feature/{ref}`: отправка в `base` и удаление своей ветки не отказываются;
- успешная отправка ветки задачи (запись по умолчанию и `target-human`) оставляет в журнале «ветка отправлена: <sha>» с отправленным локальным sha, отправка с ненулевым кодом — не оставляет; `push_options: [X, Y]` — отправка ветки задачи несёт `-o X -o Y`, `refs/artifacts/<id>` и пустой список — без `-o`;
- артель и проект с полями по умолчанию: существующие тесты `new`, деления, отправок, `cleanup` зелёные без правки. Если правка существующего теста всё же понадобится — только разделом «Меняемое поведение» и матрицей неослабления SPEC этой части (мандат Оператора 26.10), иначе эскалация.
