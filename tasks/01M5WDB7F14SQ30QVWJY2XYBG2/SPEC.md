# SPEC: GitLab Б1.1 — поля записи, ветка по шаблону, единая точка отправки с журналом и белым списком

## Контекст
Часть 1 деления задачи 01M5W67E0AYGKF03SEM6E2AQX2 (ADR-0029 п. 4–6, 11, 13;
решения Оператора — ANSWER-1.md родителя и два возврата с гейта SPEC
родителя, 26.10.2026). Сейчас имя ветки задачи строится жёстко
(`orchestrator/catalog.py:918`, `f"task/{task_id.lower()}-{slugify(title)}"`,
в `_new_task_row`; при делении — тоже там, до копирования ссылок частям),
части деления заводятся по одной в цикле `fsm._spawn_division_subtasks`
(`orchestrator/fsm.py:1037`), родитель уходит в `killed` после всех частей.
Все отправки на сервер идут через `gitcmd` (`HOSTING_SUBCOMMANDS`,
`orchestrator/gitcmd.py:37`; определение проекта и токена — `gitcmd.py:86-118`,
`_declared_targets` при нечитаемом `targets.yaml` возвращает `{}`), процессы
git запускают пять точек: `git` (`:164`), `carpentry` (`:341`), `read`
(`:413`), `read_env` (`:441`, `Popen`), `read_stream` (`:469`, `Popen`).
Токен Developer подключаемого проекта может отправлять в любые незащищённые
ветки — защита только кодом пульта. Задача вводит поля записи проекта для
доставки через MR, ветку по шаблону и единую точку отправки с журналом
отправленного sha и белым списком для проектов с `merge_gate`, отличным от
`operator`. А0 (`targets.unsupported_reason`) отказывает `new`/`run`/`auto`/
`approve` проекту с `merge_gate: target-human` и `forge: gitlab`, поэтому
сценарии `new` и деления проверяются на записях `forge: github`,
`merge_gate: operator`, а белый список — на уровне `gitcmd`.

   поля.

     `{id}`, `{slug}`, `{ref}`; `{id}` подставляется в нижнем регистре, как
     сейчас (`catalog.py:918`); `{ref}` — ключ ссылки системы
     `policy.ref_required`; шаблон с `{ref}` без `ref_required` — отказ.

     обязано компилироваться; `ref_pattern` при шаблоне без `{ref}` — отказ
     загрузки.
   - `policy.freshness` — `merge` (по умолчанию) | `rebase`; иное значение —
     отказ; `rebase` без `squash_before_mr: true` — отказ.
   - `policy.squash_before_mr` — по умолчанию `false`.
   - `policy.commit_template` — по умолчанию `{id}: {text}`, подстановки
     `{id}`, `{ref}`, `{text}`; значение, отличное от умолчания, без
     `squash_before_mr: true` — отказ.

     `Co-authored-by: `, иначе отказ.

     переменных), по умолчанию пуст; иной вид — отказ.

   `co_author` в этой части только объявляются и проверяются — исполняет их

   Новые поля объявляются только для записей локального слоя

3. Единая точка отправки (`orchestrator/gitcmd.py`):
   - (а) после каждой успешной (код 0) отправки ветки задачи (любой проект)
     пишет в журнал задачи запись «ветка отправлена: <sha>» с отправленным
     локальным sha; неудачная отправка, отправка с `--dry-run` и удаление
     ветки (в том числе с `--force-with-lease`) записи не оставляют.
   - (б) ко всем отправкам ветки задачи проекта добавляет `-o <опция>` на
     каждую строку `policy.push_options`; к `refs/artifacts/*` — нет.
   - (в) белый список — только для проекта с `merge_gate`, отличным от
     `operator` (ADR-0029 п. 13): любая отправка на сервер проверяется до
     вызова git. Действует ли белый список, решает функция-предикат в
     `orchestrator/targets.py` («`merge_gate` проекта отличен от
     `operator`»); `gitcmd.py` вызывает её и не сравнивает `merge_gate`/
     `forge` с литералами (сторож А0
     `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py`,
     `test_ac9_no_support_literals_outside_targets`, не правится). «Своя
     ветка» — имя ветки задачи этого проекта из БД в любом состоянии, кроме
     `killed` и `done`, совпавшее с назначением refspec. Разрешены только
     своя ветка, `refs/artifacts/*` и удаление `refs/artifacts/<id>` задач
     этого проекта. Удаление `refs/artifacts/<id>` — только формой
     `--delete refs/artifacts/<id>` (как `artifact_cleanup.py`) и только для
     id задачи этого проекта, существующей в БД; `--delete` с иным
     назначением — отказ; форма `:<ref>` — отказ всегда, в том числе
     `:refs/artifacts/<id>`. Назначение отправки — только `origin` клона
     проекта или URL, равный `url` записи проекта; иное назначение — отказ.
     Флаги `push` — только белым списком: `-u`/`--set-upstream`, `-q`,
     `-o <опция>`, `--force-with-lease=<ref>:<sha>`, `--delete` (только с
     `refs/artifacts/<id>`, см. выше); любой иной флаг — отказ. Опция `-o`
     в argv проверяется той же нормой, что элемент `policy.push_options` при
     загрузке, включая форму: опция вне форм `ci.variable=ИМЯ=значение` и
     `ИМЯ=значение` (например `-o novalue`), `ci.skip`, любая
     `merge_request.*` и опция, чьё `ИМЯ` есть в `push_options_forbidden`,
     — отказ. Отправка распознаётся по подкоманде git после всех глобальных
     опций; глобальные опции перед `push` — `-c`, `--config-env`,
     `--git-dir`, `--work-tree` и `-C` с путём вне клона проекта — отказ
     (опции, которые добавляет сама точка отправки, в том числе
     `-c push.followTags=false` и `-c push.pushOption=`, этой проверке не
     подлежат). Переменные `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`,
     `GIT_CONFIG_VALUE_*`, `GIT_CONFIG_PARAMETERS` в окружении отправки —
     отказ (переменные, которые добавляет сама точка отправки —
     `gitcmd.hosting_env`, — этой проверке не подлежат). Подкоманда
     `send-pack` — отказ; подкоманда, являющаяся псевдонимом (`alias.*`) в
     конфигурации клона, — отказ. Отказ также: отправка в `base`; в ветку,
     не являющуюся своей; иные удаления (`--delete` не по
     `refs/artifacts/<id>`, `:<ref>` — в том числе своей ветки); теги;
     отправка без явного refspec; refspec с `+`. Флаги `--tags`,
     `--follow-tags`, `--mirror`, `--all`, `--force`/`-f`, `--dry-run` — вне
     белого списка, то есть отказ. Единственная форма перезаписи —
     `--force-with-lease=<ref>:<sha>`, которую строит сама точка отправки;
     голый `--force-with-lease` и форма без `<sha>` — отказ; `<sha>`
     сверяется с последней записью журнала задачи «ветка отправлена: <sha>»
     — другой sha или нет записи — отказ. Отправка такого проекта идёт с
     `-c push.followTags=false` и `-c push.pushOption=` (сброс списка
     опций из конфигурации). До запуска процесса отправки точка отказывает,
     если в конфигурации клона у `origin` задан `pushurl`, `push` или
     `mirror`, либо на уровне клона непуст `push.pushOption`.
     Всё перечисленное в (в), включая сброс `push.pushOption` и проверку
     конфигурации клона, — только для проектов, где предикат говорит
     «белый список действует».
   - Каждый отказ (в) и (г) — с причиной и записью: в журнал задачи, к
     ветке или ссылке которой относится отправка; отправка без своей задачи
     — в журнал задачи из контекста команды; без контекста — запись в
     `alerts` вида `incident` с источником `branch_push_whitelist`.
     Контекст задачи — переменная окружения `ARTEL_TASK` (шаг роли,
     `runner.role_env`) либо явный параметр `task_id` точки отправки,
     который передают команды пульта, отправляющие от имени задачи.
   - (г) проверка — в одной внутренней функции, через которую проходят все
     пять точек запуска git в `gitcmd` (`git`, `carpentry`, `read`,
     `read_env`, `read_stream`), либо в каждой из них. Нечитаемый слой
     `targets.yaml` или отсутствие записи проекта (`merge_gate` неизвестен)
     — отказ любой отправки, чьё назначение относится к клону внешнего
     проекта под областью проектов пульта: отправки из клона внешнего
     проекта и отправки по URL или пути, ведущему в клон внешнего проекта
     под областью проектов (`repo_context.projects_root()`), откуда бы ни
     шла команда; в том числе проекта, чья запись при читаемом
     `targets.yaml` — `operator`. Клон артели
     (`repo_context.clone_path` артели, `.artel/projects/artel/repo`)
     исключён явно: его отправки этим правилом не отказываются.
   - У проекта `operator` с читаемой записью (в том числе с нестандартным
     `branch_template`), у артели и у проектов с полями по умолчанию
     отправки, кроме (а) и (б), прежние — мерж и уборка пульта не меняются.

## Критерии приёмки

AC-1. Проверка записи: шаблон ветки с `{ref}` без `ref_required`;
`commit_template`, отличный от умолчания, без `squash_before_mr: true`;
`freshness: rebase` без `squash_before_mr: true`; `push_options` с
`ci.skip` — каждый отказ загрузки записи с именем своего поля. При
`push_options_forbidden: [SECRET]` элементы `ci.variable=SECRET=1` и
`SECRET=1` — отказ с именем поля `push_options`, `ci.variable=OTHER=1` —
запись загружается. Элемент `push_options` вне обеих форм (`novalue`, без
`=`) и элемент `merge_request.target=main` при пустом
`push_options_forbidden` — отказ с именем поля `push_options`.
`ref_pattern: PROJ-\d+` при `branch_template` без `{ref}` — отказ загрузки с
именем поля `ref_pattern`.

AC-2. Один параметризованный критерий формы полей: `freshness: squash`,
`ref_pattern: "PROJ-("` (при шаблоне с `{ref}`), `commit_author` без email,
`commit_author` с `name: ""`, `commit_author` строкой `"X <x@y>"`,
`co_author: "Reviewed-by: X"`, `mr_assignee: ""`, `draft_mr: "yes"`,
`max_in_flight: 0`, `ci_required_jobs: build`, `push_options_forbidden: SECRET`
— каждый отказ загрузки с именем своего поля; допустимое значение каждого
поля (для `commit_author` — `{name: X, email: x@y}`) загружается. Запись
локального слоя без новых полей загружается, и её плоская запись
`targets.target()` — без новых ключей (прежнего вида). Через загрузчик записи
`targets.target()`: запись с `policy.ci_required_jobs: [build, test]` даёт в
плоской записи ключ `ci_required_jobs` со значением `["build", "test"]`;
у записи без поля ключа нет, и `.get("ci_required_jobs") or []` даёт `[]`.

AC-3. `new --ref tracker:PROJ-7` при `branch_template: feature/{ref}`,
`ref_required: tracker`, `ref_pattern: PROJ-\d+` — задача заведена с веткой
`feature/PROJ-7`; `--ref tracker:PROJ-7x` — отказ;
`--ref tracker:PROJ-7 --ref tracker:PROJ-9` — отказ. После каждого отказа
задачи нет: число строк `tasks` прежнее и новой ссылки `refs/artifacts/*` в
репозитории нет.

AC-4. При том же шаблоне: ветка `feature/PROJ-7` уже на сервере
(подменённый `ls-remote`), у задачи проекта в `done` или у задачи проекта в
`killed` — каждое отказ `new`; сбой `ls-remote` — отказ с причиной «имя
ветки не проверено». После каждого отказа задачи нет: ни новой строки
`tasks`, ни новой ссылки `refs/artifacts/*`. При шаблоне по умолчанию
`ls-remote` не вызывается ни в `new`, ни в делении.

AC-5. Каждый из четырёх случаев деления — отказ `approve` гейта SPEC, после
которого ни одна часть не заведена (ни строки БД, ни ссылки документов),
эпика нет (в том числе при `approve --as-epic`), у родителя не изменились
`zones`, `merge_after` и потолок, родитель в `spec_gate`: (1) шаблон
`feature/{ref}` — причина «ветка по ключу трекера: делите задачу в трекере»;
(2) шаблон `feature/{slug}`, имя второй части занято (сервер или БД);
(3) шаблон `feature/{slug}`, две части с одинаковым slug; (4) шаблон
`feature/{id}-{slug}`, имя второй части, построенное по её заранее
выданному id, занято (подменённый `ls-remote` отвечает на это имя). При
шаблоне `feature/{id}-{slug}` без конфликта части заведены, и ветка каждой
части — ровно то имя, которое проверялось (`ls-remote` вызван с ним).

AC-6. Белый список (запись с `merge_gate: target-human` в тесте): отправка в
`feature/PROJ-8`, которой нет среди веток задач проекта; в ветку задачи в
`done`/`killed`; в `main`; удаление своей ветки (`--delete` и `:<ref>`);
удаление `--delete refs/artifacts/<id>` задачи, которой нет в БД проекта;
удаление `:refs/artifacts/<id>` задачи проекта, существующей в БД; тег;
отправка без явного refspec; своя ветка с `--tags`, `--follow-tags`,
`--mirror`, `--all`, `--force`, `-f`, `--dry-run`, флагом вне белого списка
(`--prune`, `--receive-pack=x`) или `+<ветка>`; своя ветка с
`-o merge_request.create`, с `-o ci.skip`, с `-o novalue` и (при
`push_options_forbidden: [SECRET]`) с `-o ci.variable=SECRET=1`; своя ветка
с глобальной опцией перед `push` — `-c core.sshCommand=x`,
`--config-env=core.sshCommand=VAR` и `--git-dir=<путь>`; своя ветка с
каждой из переменных окружения `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`,
`GIT_CONFIG_VALUE_0`, `GIT_CONFIG_PARAMETERS`, переданных в окружении
отправки; своя ветка подкомандой `send-pack`; своя ветка по URL,
отличному от `url` записи;
голый `--force-with-lease` и `--force-with-lease=refs/heads/<ветка>` без
sha; перезапись `--force-with-lease=refs/heads/<ветка>:<sha>` с sha,
отличным от последней записи «ветка отправлена», или без такой записи —
каждое отказ до вызова git (шпион `subprocess.run` не вызван) с причиной.
Журнал отказа: отказ, относящийся к задаче проекта, оставляет запись с
причиной в её журнале; отказ без своей задачи (отправка в `main`) при
`ARTEL_TASK=<id>` в окружении и, отдельно, при явном параметре `task_id`
точки отправки — запись с причиной в журнале этой задачи; тот же отказ без
`ARTEL_TASK` и без `task_id` — открытый алерт вида `incident` с источником
`branch_push_whitelist`. Отправка ветки живой задачи

последней записи «ветка отправлена», отправка `refs/artifacts/<id>` и
удаление `--delete refs/artifacts/<id>` задачи проекта, существующей в БД, —

AC-7. Для записи `target-human` отправка в `main` через каждую из точек
`git`, `carpentry`, `read`, `read_env`, `read_stream` — отказ до запуска
процесса (шпионы `subprocess.run` и `subprocess.Popen` не вызваны).
Нечитаемая запись (испорченный `targets.yaml`) — отправка из клона
внешнего проекта отказана до запуска процесса, в том числе из клона
проекта, чья запись в исправном `targets.yaml` — `merge_gate: operator`;
так же отказана отправка, запущенная вне клона (рабочий каталог — корень
пульта) по URL-пути, ведущему в клон под `repo_context.projects_root()`.
При читаемом `targets.yaml` без записи проекта, чей клон лежит под
областью проектов, — та же отправка из клона и по URL-пути отказана.
Отправка из клона артели под областью проектов при испорченном
`targets.yaml` этим правилом не отказана.
Подставы конфигурации клона для записи `target-human` (отправка своей
ветки с разрешённым argv): в конфигурации клона задан
`remote.origin.pushurl`; задан `remote.origin.push`; задан
`remote.origin.mirror=true`; на уровне клона задан непустой
`push.pushOption`; подкомандой служит псевдоним клона (`alias.p=push`,
вызов `p origin <своя ветка>`) — каждое отказ с причиной, процесс отправки
не запущен (ни один вызов шпионов `subprocess.run`/`subprocess.Popen` не
несёт подкоманду отправки). Те же подставы у проекта `merge_gate:
operator` отправку не отказывают, и вызов не несёт `-c push.pushOption=`.

AC-8. Проект `merge_gate: operator` с `branch_template: feature/{ref}`:
отправка в `base` и удаление своей ветки не отказываются.

AC-9. Успешная отправка ветки задачи (запись по умолчанию и `target-human`)
оставляет в журнале задачи «ветка отправлена: <sha>» с отправленным

отправка `refs/artifacts/<id>` и отправка при пустом списке — без `-o`.
