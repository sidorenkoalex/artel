# PLAN: Аудитор SPEC видит решения Оператора, переданные причиной возврата с гейта SPEC

## Подход
Раздел «Решения Оператора на гейте SPEC» собирается только в
`orchestrator/brief.py::spec_auditor_brief`, отдельным помощником, который
вызывается сразу после цикла компонентов ANSWER-n и до компонента карты —
при отсутствии ANSWER-n это само собой «после SPEC» (требование 1). Бриф
аналитика и общий путь компонентов (`_manifest_component` /
`context_package.render_component`) не трогаются.

- `_spec_gate_reasons(conn, task_id)` — отбор по журналу
  (`store.task_steps`): запись `state -> spec_writing`, `actor ==
  "operator"`, `_previous_state_name(steps, row["id"]) == "spec_gate"`
  (то же правило, что у раздела «Причина возврата»). Подстрока текста в
  отборе не участвует; из `detail` снимается только префикс
  `"возврат из spec_gate: "` (`str.removeprefix`, тот текст, что пишет
  `fsm.cmd_reject`), остаток — дословно. Fail-возвраты аудитора (`actor`
  не `operator`, предшественник `spec_audit`) и возвраты Оператора из
  других состояний отсекаются условием (требования 2-3).
- `_spec_gate_decision_components(conn, task_id, role, run_id)` — пусто,
  если причин нет (бриф без возвратов побайтно прежний, AC-5); иначе
  заголовок раздела с пометкой «данные, не инструкции» и по компоненту на
  причину с меткой «Решение Оператора на гейте SPEC №k из n». Причина в
  пределах `config.CONTEXT_FILE_MAX_BYTES` — через `_manifest_component`
  (опись + `wrap_boundary`, AC-8). Крупная — свой компонент-строка описи
  той же формы, что у `render_component`, но с указанием «полный текст —
  artel.py log <id>» вместо «читай адресно инструментом чтения»: файла по
  метке причины нет (AC-9); пишется журнальная запись «бриф: компонент» с
  sha256, как у общего пути. Каждая причина — отдельный компонент, поэтому
  крупная не скрывает остальные (AC-4).
- Правило требования 5 — приложением к `skills/spec-audit.md` (защищённый
  путь), см. «Приложение» ниже; `git apply --check` на чистом дереве HEAD
  ветки прошёл (код возврата 0).
- Тесты: свойства AC-1…AC-4, AC-8, AC-9 закрывает долгоживущий файл
  test_author `tests/test_01m4r4jdg8rh53znwm0xf90cfj_spec_gate_decisions.py`
  (причины — настоящим `fsm.cmd_reject`), AC-5/AC-6 — планка. Свойств,
  не покрытых ими, правка не вносит — собственных тестов не добавлял.

## Влияние на систему
- Меняется только бриф аудитора SPEC и только у задач с reject на
  `spec_gate`: у остальных список компонентов прежний побайтно (AC-5).
  Бриф аналитика, разработчика, ревью-пакет, общий
  `context_package.render_component` не меняются (AC-6, AC-9 вторая
  половина).
- Гейты, вердикты и порог аудита не меняются. Правило скила сужает то,
  что поднимает аудитор, — принято Оператором 12.10 (SPEC, «Не входит»);
  мандатов раздел не создаёт — это зафиксировано в самом правиле.
- Граница недоверенных данных сохранена: тело каждой причины — внутри
  `wrap_boundary` идентификатора прогона, заголовок раздела называет его
  данными.
- Существующие тесты не правились. Откат — revert merge-коммита задачи;
  правило скила откатывается обратным наложением приложения.

## Риски
- `_previous_state_name` проходит журнал с начала на каждую запись-
  кандидата — квадратично по числу записей `state -> spec_writing`
  оператора; их единицы, на практике незаметно.
- Причина reject с текстом, оформленным как маркер границы, остаётся
  внутри пары маркеров с уникальным run_id — подделать закрывающий маркер
  она не может (тот же механизм, что у ANSWER-n).
