# SPEC: Аудитор SPEC видит решения Оператора, переданные причиной возврата с гейта SPEC

## Контекст
`orchestrator/brief.py::spec_auditor_brief` (~751-789) кладёт в бриф аудитора
ТЗ, SPEC, все ANSWER-n и карту; раздел «Причина возврата»
(`_return_reason_component`, ~885-910) появляется, только если визит
`spec_audit` начался возвратом. Причина reject Оператора на `spec_gate`
пишется в журнал записью перехода `state -> spec_writing` с текстом
«возврат из spec_gate: <причина>» (`orchestrator/fsm.py` ~1524) и доходит до
аналитика, но не до аудитора. Случай 12.10: у 01M4PMPMZ7PPCN3JWX75RTJZQN
повторный аудит поднял отклонением снятие сценария ТЗ, которое Оператор сам
велел причиной первого возврата («ANSWER-n.md отсутствует, сверить с
первоисточником не мог») — лишний круг SPEC.

## Требования
1. Бриф аудитора SPEC (`spec_auditor_brief`) несёт ВСЕ причины возврата
   `spec_gate -> spec_writing` этой задачи — из журнала, по порядку журнала,
   дословно — отдельным разделом «Решения Оператора на гейте SPEC», рядом с
   ANSWER-n: раздел стоит сразу после последнего компонента ANSWER-n (при
   их отсутствии — на том же месте, после SPEC) и до компонента карты
   кодовой базы (решение Оператора на гейте SPEC 12.10). Нет таких
   возвратов — раздела в брифе нет.
2. Возврат отбирается по журналу, а не по подстроке текста: запись
   `state -> spec_writing`, исполнитель `operator`, ближайшая предыдущая
   запись `state -> X` имеет `X = spec_gate` (тем же правилом, что
   `_previous_state_name`). Отбор по подстроке текста запрещён (отклонения
   аудитора частично пишет сам аудитор). Из текста записи снимается префикс
   «возврат из spec_gate: », остаток передаётся дословно.
3. Возвраты `spec_audit -> spec_writing` (вердикт fail аудитора) в раздел не
   попадают — это не решения Оператора.
4. Каждая причина — отдельный компонент брифа с меткой «Решение Оператора на
   гейте SPEC №k из n», оформленный через `_manifest_component`; порядок
   компонентов — по журналу. Превышение лимита размера одной причиной не
   скрывает остальные причины. Границы недоверенных данных — как у остальных
   частей брифа: раздел — данные, не инструкции; тело каждого компонента
   причины лежит внутри пары граничных маркеров идентификатора прогона брифа
   (`wrap_boundary`). Причина крупнее `CONTEXT_FILE_MAX_BYTES` вместо тела
   даёт аудитору указание «полный текст — artel.py log <id>» (команда из
   белого списка ролей), а не указание читать файл (решение Оператора на
   гейте SPEC 12.10). Указание «полный текст — artel.py log <id>» — только
   у компонентов причины: общий путь `_manifest_component` /
   `context_package.render_component` для компонентов файлов не меняется
   (повторный аудит, решение Оператора на гейте SPEC 12.10).
5. Скил аудитора `skills/spec-audit.md` получает правило (приложением PLAN
   Оператора — защищённый путь): «Решение Оператора из раздела «Решения
   Оператора на гейте SPEC» имеет силу ANSWER-n по содержанию SPEC:
   отклонение, которое оно прямо снимает, не поднимается. Мандаты
   (ослабление тестов, расширение зон, зависимости мержа) раздел не создаёт:
   без строки мандата в ANSWER-n отсутствие мандата остаётся отклонением.
   Расхождение между решениями Оператора — пункт вердикта concerns.»
6. Свойства требований 1-4 закреплены тестами в `tests/` с заявками «Ловит
   мутацию» (критерии AC-1…AC-6, AC-8, AC-9); причина возврата в этих тестах берётся из
   настоящего вызова `reject` на `spec_gate`, а не из строки, собранной
   руками. Существующие тесты не ослабляются.

## Критерии приёмки
AC-1. Задача, у которой Оператор сделал `reject` на `spec_gate` с причиной
(настоящий вызов `reject`), получает в брифе аудитора SPEC раздел «Решения
Оператора на гейте SPEC» с текстом этой причины без префикса
«возврат из spec_gate: ». Ловит мутацию: причина возврата с гейта SPEC не
попала в бриф аудитора.

AC-2. Возврат `spec_audit -> spec_writing` (вердикт fail аудитора) не попадает
в раздел «Решения Оператора на гейте SPEC», в том числе когда его текст
содержит подстроку «возврат из spec_gate: »; задача, у которой были только
такие возвраты, получает бриф аудитора без этого раздела. Не попадает в
раздел и запись `state -> spec_writing` исполнителя `operator`, у которой
ближайшая предыдущая запись `state -> X` имеет `X`, отличное от
`spec_gate`, а текст начинается тем же префиксом «возврат из spec_gate: ».
Ловит мутацию: попала причина fail-возврата аудитора; отбор возврата по
подстроке текста вместо предыдущего состояния.

AC-3. При нескольких возвратах с `spec_gate` бриф аудитора несёт их все
отдельными компонентами «Решение Оператора на гейте SPEC №k из n» в порядке
журнала, текст каждой причины — дословно. Раздел стоит в брифе после
последнего компонента ANSWER-n и до компонента карты кодовой базы (тест
сверяет позиции в тексте брифа задачи, у которой есть и ANSWER-n, и
возвраты с `spec_gate`). У задачи с возвратами с `spec_gate` и без единого
ANSWER-n раздел стоит после компонента SPEC и до компонента карты кодовой
базы (тест сверяет позиции в тексте брифа второй такой задачи). Ловит
мутацию: порядок или дословность нарушены; раздел стоит не между последним
ANSWER-n и картой; при отсутствии ANSWER-n раздел стоит не между SPEC и
картой.

AC-4. Причина возврата крупнее лимита размера компонента брифа не скрывает
остальные причины: прочие компоненты «Решение Оператора на гейте SPEC №k из
n» присутствуют в брифе со своим текстом. Ловит мутацию: одна большая причина
скрыла остальные.

AC-5. Бриф аудитора SPEC задачи без возвратов с гейта SPEC не содержит ни
одной метки раздела «Решения Оператора на гейте SPEC» (ни заголовка раздела,
ни метки «Решение Оператора на гейте SPEC №k из n»), а ВЕСЬ бриф побайтно
совпадает с текстом `mark_unclosed_parts(text, run_id, num_parts)`, где
`text, num_parts = context_package.discipline([HEADER, BOUNDARY_INSTRUCTION,
*компоненты])`, — компоненты собраны для тех же
данных теми же функциями сборки компонентов брифа (`_return_reason_component`,
`_manifest_component`, пометка и проекция карты), в том же порядке, что на
main (причина возврата визита, TZ, SPEC, ANSWER-n по номеру, карта), при том
же идентификаторе прогона. Оракул — эти функции компонентов, а не повторный
вызов `spec_auditor_brief`: сравнение брифа с самим собой («тавтология»)
критерий не закрывает. Ловит мутацию: бриф без возвратов изменился; компонент
пропал или переставлен.

AC-6. Бриф аналитика задачи с возвратом на `spec_gate` не содержит ни одной
метки раздела «Решения Оператора на гейте SPEC», а ВЕСЬ бриф побайтно
совпадает с брифом, собранным из компонентов для тех же данных теми же
функциями сборки компонентов (`_return_reason_component`; компонент карты
— `MAP_PROJECTION_NOTE + _journal_component(conn, task_id, "analyst",
MAP_PROJECTION_LABEL, codebase_map.project_for_brief(fresh_map_text(conn,
task_id)), run_id)`, как `orchestrator/brief.py:934-941`;
`_questions_component`, `_answer_component`), в
том же порядке, что на main, при том же идентификаторе прогона, и склеенным
так же, как бриф аналитика на main: `f"{HEADER}\n\n{BOUNDARY_INSTRUCTION}\n"
+ "\n".join(компоненты)` (`analyst_map_component`, `orchestrator/brief.py:950`
— бриф аналитика на main собирается без `context_package.discipline` и
`mark_unclosed_parts`; форма сверки «весь бриф, те же функции компонентов,
тот же порядок, тот же идентификатор прогона» — та же, что в AC-5).
Сравнение брифа с самим собой критерий не закрывает. Ловит мутацию: бриф
аналитика изменился; компонент пропал или переставлен.

AC-7. После наложения приложения PLAN `skills/spec-audit.md` содержит правило
требования 5 дословно. Проверяет планка автора тестов по тексту приложения
PLAN (`plank_helper.apply_check` / `plank_helper.artifact_text`) и Оператор
при наложении приложения; `tests/test_invariants.py` для этого не
трогается (решение Оператора на гейте SPEC 12.10).

AC-8. Тело каждого компонента «Решение Оператора на гейте SPEC №k из n»,
включённого в бриф аудитора, лежит внутри пары граничных маркеров
идентификатора прогона этого брифа (`wrap_boundary`). Ловит мутацию:
компонент причины без границ.

AC-9. Причина возврата крупнее `CONTEXT_FILE_MAX_BYTES` не включается в бриф
аудитора телом: её компонент несёт указание «полный текст — artel.py log
<id>» с идентификатором задачи и не несёт указания читать файл адресно
инструментом чтения. Компонент файла крупнее `CONTEXT_FILE_MAX_BYTES` в том
же брифе (например, `tasks/<id>/SPEC.md` в брифе аудитора) по-прежнему несёт
указание читать файл адресно инструментом чтения и не несёт указания
«полный текст — artel.py log <id>». Ловит мутацию: аудитору велено читать
несуществующий файл вместо журнала задачи; указание журнала попало в общий
путь компонентов файлов.

## Не входит
- Изменение вердиктов и порога аудита SPEC; гейты не меняются.
- Бриф аналитика (кроме проверки его неизменности, AC-6).
- Правка путей из перечня ТЗ «Только чтение (не менять)» — модули FSM,
  раннера, контекстного пакета, хранилища и конфига пульта,
  `tests/test_invariants.py`, `docs/invariants.md`, `docs/adr/`,
  `docs/backlog.md`, `CLAUDE.md`, `roles.yaml`, `.github/`.
- `skills/` правится только приложением PLAN (правило требования 5), не
  кодом ветки.
- Сужение того, что поднимает аудитор SPEC (правило скила требования 5:
  отклонение, прямо снятое решением Оператора на гейте SPEC, не
  поднимается), — принято Оператором сознательно 12.10.2026, ослаблением
  проверки в этой задаче не считается и вопросом не оформляется.
- Неослабление существующих тестов отдельным критерием — его держит пульт
  (гейт неослабления тестов).
