# ТЗ: Аудитор SPEC видит решения Оператора, переданные причиной возврата с гейта SPEC

Источник: копилка 12.10, приоритет 2 («Аудитор SPEC не видит решений
Оператора, переданных причиной reject на spec_gate…»). Решение Оператора
12.10.2026 — заводить.

Факты (origin/main 8543e24e):
- `orchestrator/brief.py::spec_auditor_brief` (~751-787) кладёт в бриф
  аудитора ТЗ, SPEC, все ANSWER-n и карту; раздел «Причина возврата» — только
  если визит `spec_audit` начался возвратом (`_return_reason_component`,
  ~887-912). Возврат `spec_gate -> spec_writing` (reject Оператора с
  причиной) попадает в бриф аналитика, но не аудитора.
- Причина reject пишется в журнал задачи записью перехода
  «возврат из spec_gate: <причина>» (`orchestrator/fsm.py` ~1522).
- Случай 12.10: у 01M4PMPMZ7PPCN3JWX75RTJZQN повторный аудит поднял как
  отклонение снятие сценария ТЗ, которое Оператор сам велел причиной
  первого возврата («ANSWER-n.md отсутствует, сверить с первоисточником не
  мог»), — лишний круг SPEC.

Требуется:
1. Бриф аудитора SPEC несёт ВСЕ причины возврата `spec_gate -> spec_writing`
   этой задачи (из журнала, по порядку, дословно) отдельным разделом
   «Решения Оператора на гейте SPEC», рядом с ANSWER-n. Нет таких возвратов
   — раздела нет. Возврат отбирается по журналу: запись
   `state -> spec_writing`, исполнитель `operator`, ближайшая предыдущая
   запись `state -> X` имеет `X = spec_gate` (как `_previous_state_name`).
   Отбор по подстроке текста запрещён (отклонения аудитора частично пишет
   сам аудитор). Из текста снимается префикс «возврат из spec_gate: »,
   остаток передаётся дословно; в тестах причина берётся из настоящего
   вызова `reject` на `spec_gate`, а не из строки, собранной руками.
2. Возвраты `spec_audit -> spec_writing` (вердикт fail аудитора) в этот
   раздел не попадают — это не решения Оператора.
3. Каждая причина — отдельный компонент «Решение Оператора на гейте SPEC
   №k из n» через `_manifest_component`, порядок по журналу; превышение
   лимита размера одной причиной не скрывает остальные; границы
   недоверенных данных — как у остальных частей.
4. Скил аудитора `skills/spec-audit.md` — правило (приложением PLAN
   Оператора, защищённый путь): «Решение Оператора из раздела «Решения
   Оператора на гейте SPEC» имеет силу ANSWER-n по содержанию SPEC:
   отклонение, которое оно прямо снимает, не поднимается. Мандаты
   (ослабление тестов, расширение зон, зависимости мержа) раздел не
   создаёт: без строки мандата в ANSWER-n отсутствие мандата остаётся
   отклонением. Расхождение между решениями Оператора — пункт вердикта
   concerns.»
5. Тесты в `tests/` с заявками «Ловит мутацию»: причина возврата с гейта
   SPEC не попала в бриф аудитора; попала причина fail-возврата аудитора;
   порядок/дословность нарушены; одна большая причина скрыла остальные;
   бриф задачи без возвратов с гейта SPEC побайтно совпадает с прежним;
   бриф аналитика не меняется. Существующие тесты не ослабляются.

Матрица неослабления: аудитор получает больше входа, вердикты и гейты не
меняются; раздел — данные, не инструкции.
