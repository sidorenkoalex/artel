# SPEC: Рост долгоживущих тестов: правило автора тестов и замер времени файлов задачи

## Контекст
Долгоживущих файлов задач в `tests/` за 12 дней стало 94 (851 метод), 63 % из
них — на `RealGitSandbox` (настоящий git, часто FSM), последние 12 задач
добавили тестов в 5,3 раза больше кода, полный прогон при `-n 4` вырос с 632 с
(05.10) до 688 с (07.10). Два долгоживущих теста 07.10 краснели случайно из-за
ожидания по реальному времени. Правила автора тестов (`skills/test-authoring.md`)
не запрещают ни песочницу для свойства без песочницы, ни метод на каждый вариант
перечня, ни ожидание по реальному времени, а рубеж `in_dev -> verifying`,
прогоняющий долгоживущие файлы задачи
(`orchestrator/advance_gates/acceptance.py::_acceptance_run_body`, пути прогона —
`orchestrator/acceptance.py`), не показывает, сколько стоит каждый файл.

## Требования

1. PLAN несёт приложение к защищённому пути `skills/test-authoring.md` с точным
   текстом правила из трёх пунктов:
   (а) свойство, проверяемое без песочницы (чистая функция, разбор, формат
   текста, таблица решений), проверяется модульным тестом без `TmpRootTest`/
   `RealGitSandbox`; песочница с git/FSM — только для свойства самой связки
   «команда — FSM — база — git», и тогда в докстринге теста сказано, какую
   связку тест держит;
   (б) короткий конечный перечень вариантов перебирается целиком в одном тесте
   (`subTest`), а не методом на вариант;
   (в) тест не ждёт по реальному времени (sleep/опрос с таймаутом ради
   наступления события): время и паузы подменяются; предел времени в тесте —
   только страховка от зависания, не условие проверки.
2. На рубеже `in_dev -> verifying` пульт пишет в журнал задачи время прогона
   каждого долгоживущего файла задачи по отдельности (путь файла и его время).
3. Файл, чьё время прогона на рубеже больше порога, даёт предупреждение
   (называет файл, его время и порог); файл в пределах порога предупреждения не
   даёт. Предупреждение не меняет исход рубежа: переход не отклоняется из-за
   времени и не пропускается вопреки красному прогону.
4. Порог — именованная константа `orchestrator/config.py`
   `LONG_LIVED_FILE_WARN_SEC = 60` (секунд), с комментарием-обоснованием по
   замеру (см. «Материалы»: замер аналитика и замер PLAN по требованию 7).
5. Итог замера последнего прогона рубежа (время по файлам и предупреждения о
   превышении) виден в записи журнала «приёмка: что проверит approve»
   (`orchestrator/fsm_autogate.py`, `orchestrator/fsm.py`).
6. Тот же итог виден в ревью-пакете ревьювера
   (`orchestrator/review.py::review_package`).
7. PLAN содержит замер времени долгоживущих файлов текущего `main` по файлам —
   топ-20 по убыванию времени — как основание порога требования 4.
8. Свойства требований 2–6 (время по файлам пишется в журнал; файл сверх порога
   даёт предупреждение, файл в пределах — нет; предупреждение не меняет исход
   рубежа; итог виден в карточке приёмки и в ревью-пакете) держат тесты в
   `tests/` с заявками «Ловит мутацию». Свойство, которое уже держит
   долгоживущий приёмочный тест этой задачи в `tests/`, повторно отдельным
   тестом не дублируется.

## Критерии приёмки

AC-1. PLAN.md задачи несёт приложение к `skills/test-authoring.md`, которое
применяется к `main` (`git apply --check`) и добавляет пункт (а) требования 1:
свойство, проверяемое без песочницы (чистая функция, разбор, формат текста,
таблица решений), проверяется модульным тестом без `TmpRootTest`/
`RealGitSandbox`; песочница с git/FSM — только для свойства связки «команда —
FSM — база — git», и тогда докстринг теста называет связку.

AC-2. То же приложение добавляет пункт (б): короткий конечный перечень вариантов
перебирается целиком в одном тесте (`subTest`), а не методом на вариант.

AC-3. То же приложение добавляет пункт (в): тест не ждёт по реальному времени
(sleep/опрос с таймаутом ради наступления события), время и паузы
подменяются, предел времени в тесте — только страховка от зависания, не
условие проверки.

AC-4. Переход `in_dev -> verifying` задачи с долгоживущими файлами в `tests/`
пишет в журнал задачи время прогона каждого из этих файлов отдельно: в записи
есть путь каждого долгоживущего файла задачи и его время.

AC-5. Долгоживущий файл, чьё время прогона на рубеже больше
`config.LONG_LIVED_FILE_WARN_SEC`, даёт предупреждение, в котором названы путь
файла, его время и порог.

AC-6. Долгоживущий файл, чьё время прогона на рубеже не больше
`config.LONG_LIVED_FILE_WARN_SEC`, предупреждения не даёт.

AC-7. Предупреждение о превышении порога не меняет исход рубежа: при зелёном
прогоне с файлом сверх порога переход `in_dev -> verifying` выполняется, как
без предупреждения; при красном прогоне переход отклоняется, как без
предупреждения.

AC-8. `orchestrator/config.py` несёт константу `LONG_LIVED_FILE_WARN_SEC`
со значением 60, и рубеж сравнивает время файла именно с ней: смена значения
константы меняет, какой файл даёт предупреждение.

AC-9. Запись журнала «приёмка: что проверит approve» задачи, прошедшей рубеж
с долгоживущими файлами, содержит итог замера последнего прогона рубежа: время
по файлам и предупреждения о превышении порога (если они были).

AC-10. Ревью-пакет ревьювера (`review_package`) задачи, прошедшей рубеж с
долгоживущими файлами, содержит тот же итог замера: время по файлам и
предупреждения о превышении порога (если они были).

AC-11. PLAN.md задачи содержит замер времени долгоживущих файлов текущего
`main` по файлам — не меньше 20 строк «файл — время», упорядоченных по
убыванию времени, — названный основанием порога `LONG_LIVED_FILE_WARN_SEC`.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны вне общих зон — 5
(`orchestrator/advance_gates/acceptance.py`, `orchestrator/acceptance.py`,
`orchestrator/review.py`, `orchestrator/fsm_autogate.py`, `orchestrator/fsm.py`)
при пороге 5; число критериев приёмки — 11 при пороге 10.

Обоснование монолита (материал для решения Оператора). Замер по файлам
(`orchestrator/acceptance.py`, рубеж в `orchestrator/advance_gates/acceptance.py`),
порог в `config` и вывод итога в карточку приёмки и ревью-пакет — одна смена
механики: итог в карточке/пакете без замера показывать нечего, а замер без
вывода видит только журнал рубежа, то есть промежуточная часть не даёт того,
ради чего заведена (ТЗ, требование 2, называет оба места вывода частью одного
требования). Правило автора тестов (AC-1..AC-3) отделимо по зонам — это одно
приложение к `skills/test-authoring.md`, — но отдельная подзадача стоила бы
своей планки бюджета ($25) сверх рамки всей задачи ($35), а её содержание —
три абзаца готового текста из ТЗ. Объём каждой части невелик: правки — точечные
вставки в существующие функции, без новых модулей.
