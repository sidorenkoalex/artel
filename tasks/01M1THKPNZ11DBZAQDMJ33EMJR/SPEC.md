# SPEC: стоп-кран волны, часть 1 — счётчик класса отказа по волне и алерт

## Контекст

Родительская задача 01M1SHK1JGQFD73B735WK5YTNY («стоп-кран волны: класс
отказа у нескольких задач подряд останавливает циклы всем») разделена
Оператором на гейте SPEC на две части (решение 06.09, «Оценка объёма и
деление» родителя, часть 1). Эта задача — первая часть: только счётчик
и алерт. Классификация отказа попытки уже есть
(`orchestrator/failure_classification.py`: классы 1а/1б/«системный
кандидат», `TRANSIENT_SYSTEM_CLASSES`), но сейчас она видна только по
одной задаче за раз — при системном отказе, бьющем сразу по нескольким
задачам, никто не агрегирует это в единый видимый Оператору сигнал.
Эта часть даёт такой сигнал: функцию подсчёта числа РАЗНЫХ задач
target self, отказавших одним классом за окно, и алерт `kind=incident`
при достижении порога. Поведение `run`/`auto` не меняется — блокировка
старта шага и снятие по `alert-ack` вынесены во вторую часть.

## Требования

1. Новые константы `orchestrator/config.py`: `WAVE_BREAKER_WINDOW_SEC`
   (по умолчанию 900 — 15 минут) и `WAVE_BREAKER_TASKS` (по умолчанию
   3); функция подсчёта и порог срабатывания читают их оттуда, не
   хардкодят.
2. Функция подсчёта по журналу шагов (`steps`) числа РАЗНЫХ задач
   target self с отказом ОДНОГО класса в пределах
   `WAVE_BREAKER_WINDOW_SEC`: классы — `TRANSIENT_SYSTEM_CLASSES` (1а,
   1б, системный кандидат) плюс отдельный класс «таймаут шага» (запись
   журнала `"agent run TIMEOUT"`, `orchestrator/runner.py`). Считаются
   задачи, не события — несколько отказов одной и той же задачи одного
   класса дают 1, не N.
3. При достижении `WAVE_BREAKER_TASKS` в пределах окна — алерт
   `kind=incident`, сообщение «стоп-кран волны: класс <класс> у N задач
   за M минут». Дедуп — на ОТКРЫТЫЙ алерт этого же класса (ключ дедупа
   target+kind+source+класс, не буквальный текст сообщения: N/M в
   сообщении меняются от срабатывания к срабатыванию), тем же приёмом,
   что уже применён в `alerts.raise_token_rate_divergence_alert`. Вызов
   — из двух точек `orchestrator/runner.py`, где уже журналируется
   классифицированный отказ (`failure_classification.
   _record_failure_classification`) и таймаут шага (`"agent run
   TIMEOUT"`).
4. Инциденты сторожа зависших прогонов тестов (функция
   `check_hung_test_runs` модуля `doctor`, источник
   `doctor.hung_test_runs`) — иной класс, в счётчик стоп-крана не
   входят.
5. Функция подсчёта учитывает только задачи target self
   (`config.DEFAULT_TARGET`, догфуд); задачи любого другого target
   счётчиком не учитываются.

## Критерии приёмки

AC-1. `orchestrator/config.py` несёт `WAVE_BREAKER_WINDOW_SEC=900` и
`WAVE_BREAKER_TASKS=3`; функция подсчёта и порог срабатывания читают
именно эти константы (правка констант меняет поведение без правки
остального кода).

AC-2. Три РАЗНЫЕ задачи target self отказали классом 1б (сетевой отказ
до API) в пределах `WAVE_BREAKER_WINDOW_SEC` — заводится алерт
`kind=incident` с текстом, называющим класс, число задач и окно.

AC-3. Две РАЗНЫЕ задачи с тем же классом за то же окно — алерт НЕ
заводится.

AC-4. Отказы РАЗНЫХ классов (по одной задаче на 1а, на 1б, на
«таймаут шага») не суммируются в общий счётчик ни одного отдельного
класса.

AC-5. Несколько отказов ОДНОЙ И ТОЙ ЖЕ задачи одного класса в пределах
окна считаются как одна задача, не как несколько событий.

AC-6. Таймаут шага (журнальная запись «agent run TIMEOUT») учитывается
отдельным классом наравне с классами `TRANSIENT_SYSTEM_CLASSES`.

AC-7. Инцидент сторожа зависших прогонов тестов
(`doctor.check_hung_test_runs`) не увеличивает счётчик ни одного
класса стоп-крана.

AC-8. Пока алерт стоп-крана данного класса уже открыт, повторное
достижение порога тем же классом не заводит второй такой же алерт
(дедуп по target+kind+source+класс).

AC-9. Отказы задачи внешнего target (не self) не учитываются счётчиком
стоп-крана self.

## Не входит

- Блокировка старта нового агентного шага `run`/`auto` открытым
  алертом стоп-крана — часть 2 (задача 01M1SHK1JGQFD73B735WK5YTNY,
  требование 5).
- `alert-ack`-снятие блокировки и заведение нового алерта того же
  класса после ack — часть 2 (требование 6); в этой части
  `alert-ack <id>` работает над алертом стоп-крана как над любым
  другим `incident`-алертом, без специальной механики.
- Вывод открытого алерта стоп-крана первым пунктом в `doctor` и
  пометка у задач в `status` — часть 2 (требования 7-8).
- Изменение бэкоффа/числа попыток одной задачи (T082) — механика
  ретраев не трогается.
- Ослабление существующих тестов T082 (бэкофф/эскалация транзиентных
  системных отказов) и тестов `orchestrator/alerts.py` — эта задача
  добавляет новую механику поверх существующей, не меняет её.
