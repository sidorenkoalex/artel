# PLAN: Авторазрешение конфликта карты при подтяжке

## Подход

Вся логика — внутри `orchestrator/fsm.py::_pull_main_or_escalate` (T051),
единственной функции подтяжки для всех трёх точек вызова (`in_dev ->
review`, `acceptance -> merge_gate`, окно `merge_gate` по T053) —
требование 6 SPEC запрещает дублирование по точкам, а функция и так уже
единственный узел.

Сегодня при неудачном `git merge --no-ff` код безусловно вызывает `git
merge --abort` и эскалирует, не разбирая, ЧТО именно конфликтует. Меняю
порядок: при `merge.returncode != 0` СНАЧАЛА читаю список конфликтующих
файлов (`git diff --name-only --diff-filter=U` внутри worktree задачи,
тем же приёмом, что уже применяет `_handle_merge_conflict` для другого
merge — main <- ветка при финальном approve, T052) и только потом решаю,
абортить или разрешать. `git diff --name-only` без `--quiet` возвращает 0
и в конфликтном, и в пустом случае — не спутать с `commits_behind`,
который кодирует ответ кодом возврата; тут смотрю `stdout`.

Список == РОВНО `["docs/codebase-map.md"]` → авторазрешение: `git
checkout --theirs docs/codebase-map.md`, регенерация `python3
scripts/codebase_map.py` с `cwd=<worktree задачи>` (не `config.ROOT` —
требование 2: карта регенерируется НА СЛИТОМ дереве worktree, не главной
копии пульта; тот же бинарный вызов, что `_regenerate_and_commit_map`
T042, но другой `cwd` и без сверки "изменилось ли содержимое" — здесь
перезапись безусловна, потому что до регенерации файл несёт разрешённую
`checkout --theirs` версию одной из сторон конфликта, не финальный
снимок), `git add`, `git commit` (без `-m`-текста заново — использую тот
же формат сообщения, что и исходный `git merge -m`, поскольку то
сообщение, приготовленное git в `MERGE_MSG`, при конфликте не
считается использованным до явного commit). Успех — журнал
(actor=orchestrator, файл, способ) и функция продолжает точно так же,
как «pulled»: приёмочные тесты в подтянутом дереве, дальше — без
изменений (требование 2, AC-1). Любой сбой шага (checkout/regen/add/
commit) — тот же `git merge --abort` + эскалация, что и для
неразрешаемого конфликта (требование 5, AC-5) — никакого отдельного
пути диагностики не завожу, только общий `note` из stderr исходного
merge, который уже несёт слово «конфликт» через обёртку `detail` строкой
ниже.

Список конфликтующих файлов ЛЮБОЙ ДРУГОЙ (карта + что-то ещё, карта
вовсе не в списке, git не ответил осмысленно) → тот же код, что был до
T067 буквально: `git merge --abort` + эскалация (требования 4, AC-3,
AC-4) — веткой это не разбито на отдельную функцию специально: любое
расщепление кода тут превратилось бы в риск разойтись местами, а SPEC
явно требует «байт-в-байт».

Побочный эффект: существующий юнит-тест `tests/test_branch_freshness_
gate.py` мокает `gitcmd.in_repo` заглушкой, которая распознаёт только
вызовы `merge`/`merge --abort` и падает `AssertionError` на что-то ещё —
после этой задачи `_pull_main_or_escalate` при конфликте всегда сначала
зовёт `git diff --name-only --diff-filter=U`, так что заглушка обязана
научиться отвечать и на него (список из файла, отличного от карты, —
поведение теста как было: эскалация). Это правка тестовой инфраструктуры
под новый (не ослабленный) вызов, не ослабление проверки — сам тест
по-прежнему требует эскалации на произвольном конфликте.

## Шаги

1. `orchestrator/fsm.py`: список конфликтующих файлов
   (`_conflicting_files`) + авторазрешение конфликта карты
   (`_auto_resolve_map_conflict`), подключение обеих внутрь
   `_pull_main_or_escalate` вместо безусловного abort+escalate.
2. `tests/test_branch_freshness_gate.py`: заглушка `gitcmd.in_repo` для
   существующих конфликт-сценариев отвечает и на `git diff --name-only
   --diff-filter=U` (не-карта в списке — эскалация как раньше); новые
   юнит-тесты авторазрешения (карта-only → продолжение без эскалации,
   карта+другое → эскалация как раньше, провал регенерации → abort +
   эскалация) — той же лёгкой техникой (мок `gitcmd.in_repo`, без
   реального git; полный прогон реального git и генератора уже покрыт
   залоченными `tasks/T067/acceptance_tests/`).
3. `scripts/guard.py`/`python3 scripts/codebase_map.py` — карта
   кодовой базы не меняется этой задачей по содержанию модулей `fsm.py`
   (публичные функции модуля не меняются — `_conflicting_files`/
   `_auto_resolve_map_conflict` приватные), но конвенция
   `conventions-core` требует регенерации при правке `.py` в
   `orchestrator/` — прогоняю и коммичу тем же коммитом на всякий
   случай (детерминированная сверка содержимым покажет отсутствие
   диффа, если публичный интерфейс модуля правда не сдвинулся).

## Влияние на систему

Затрагивается только `_pull_main_or_escalate` (единственная функция
подтяжки, T051/T053) — три точки вызова получают новое поведение
автоматически, без правки самих точек. Инвариант 19 (merge внутри окна
`merge_gate` не выполняется тем же вызовом, что подтяжка, T053) не
задет: авторазрешение — часть самой подтяжки (branch-local merge с
`config.MAIN_BRANCH` внутри worktree ЗАДАЧИ), не тот merge задачи в
main, который инвариант 19 запрещает совмещать с подтяжкой; вызывающий
код (`_cmd_approve_merge_gate`) как и раньше видит только "fresh" /
"pulled" / "escalated" и останавливается на "pulled" до отдельного
`approve`.

`_handle_merge_conflict`/`_cmd_approve_merge_gate` (T052/T053, финальный
merge ветки задачи в main при approve из `merge_gate`) не трогаются —
SPEC явно ограничивает объём одной функцией подтяжки, не финальным
merge в main; там конфликт — это конфликт КОДА задачи с main, авторешать
который нечем (Не входит: «Изменение эскалационных путей T051/T052 для
конфликтов, не сводящихся к чистому случаю „только карта“»).

Откат: правка сосредоточена в одной функции одного файла — `git revert`
коммита(ов) этой задачи возвращает прежнее безусловное
abort+escalate без остаточных структур (новых таблиц/колонок БД нет).

## Риски

Регенерация карты внутри `_auto_resolve_map_conflict` запускается ДО
завершения merge-коммита (в разрешаемом, но ещё не закоммиченном
дереве) — `built_at_sha` в результирующей карте будет называть sha
родителя (ветки задачи ДО merge), не сам merge-коммит. Это тот же
эффект, что уже есть у обычного `git commit` внутри merge вообще (SHA
коммита неизвестен до его создания) и SPEC его не нормирует — критерии
приёмки сверяют карту без строки `built_at_sha` (тем же приёмом, что и
`_map_content_without_sha` T042).
