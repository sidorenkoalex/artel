# SPEC: регрессия №14 — приёмка гоняет планку на коде кодовой ветки, а не на коде пульта

## Контекст

`acceptance.materialize_from_branch` кладёт приёмочную планку
(`tasks/<id>/acceptance_tests/`) из артефактной ветки во временный
каталог (`tempfile.mkdtemp`), а `acceptance.run` запускает
`python3 -m unittest discover -s <планка>` с `cwd=config.ROOT`. Планки
задач вычисляют корень репозитория от `__file__`
(`Path(__file__).resolve().parents[3]`) и вставляют его в `sys.path`:
во временном каталоге на этом пути `orchestrator/` нет, импорт
проваливается на запасной путь через `cwd` — корень пульта, то есть
код MAIN (пина), а не код кодовой ветки задачи. Итог: планка проверяет
не тот код. Стек ч.3 (01M1RDCEF0…, AC-4) и критерий сироты
(01M1REVP9W…, AC-6) покраснели на подтяжке main при зелёной планке в
worktree; любая задача с планкой на новое поведение теперь не проходит
приёмку и подтяжку. Источник истины (артефактная ветка, решение
регрессии №12, 01M1R9YEK08XEQWBFX0929WFVJ) не пересматривается — чинится
только каталог материализации и `cwd` прогона.

## Требования

1. Планка из артефактной ветки материализуется в рабочий каталог кода
   задачи (worktree self-target либо workspace внешнего target — тот
   же узел выбора, что функция `role_cwd` модуля `runner`) по штатному
   пути `tasks/<id>/acceptance_tests/`, поверх устаревшей копии, если
   она там есть, а не во временный каталог.
2. `acceptance.run` запускает прогон с `cwd`, равным этому рабочему
   каталогу кода задачи (не `config.ROOT`) — импорт `orchestrator` из
   планки резолвится в код ветки и через `__file__`, и через `cwd`.
3. То же для прогона после подтяжки main (`fsm._pull_main_or_escalate`)
   и для автогейта acceptance (`fsm_advance.review`/
   `fsm_advance.verifying`, ведущие в `fsm_autogate`): один вход
   материализации и один вход прогона, без дублей логики по точкам.
4. Отказ приёмки (красная планка) называет в `detail`, из какого
   каталога и с каким `cwd` шла планка, одной строкой.

## Критерии приёмки

AC-1. Материализация приёмочной планки из артефактной ветки кладёт
`tasks/<id>/acceptance_tests/` в рабочий каталог кода задачи (worktree
self-target либо workspace внешнего target), не во временный каталог
(`tempfile.mkdtemp`); устаревшая копия на этом пути заменяется
содержимым ветки (лишние файлы, которых в ветке уже нет, убираются).

AC-2. `acceptance.run` запускает прогон приёмочной планки с `cwd`,
равным рабочему каталогу кода задачи (тем же, куда материализовано по
AC-1) — не `config.ROOT`.

AC-3. Планка, вычисляющая корень репозитория от `__file__`
(`Path(__file__).resolve().parents[3]`), после материализации по AC-1
и прогона по AC-2 резолвит `orchestrator/` кодовой ветки задачи и через
`__file__`, и через `cwd` — оба указывают на один и тот же код.

AC-4. Прогон приёмочной планки после подтяжки main в
`fsm._pull_main_or_escalate` использует ту же материализацию (AC-1) и
тот же прогон (AC-2), что и остальные точки, — общий вход, не отдельная
копия логики.

AC-5. Автогейт acceptance (вызовы `acceptance.run` в
`fsm_advance.review`/`fsm_advance.verifying`, предшествующие
`fsm_autogate._maybe_autogate_acceptance`) использует ту же
материализацию (AC-1) и тот же прогон (AC-2) — общий вход, без дублей.

AC-6. Отказ приёмки (красная планка) называет в `detail` одной строкой
каталог, из которого шла планка, и `cwd`, с которым она запускалась.

AC-7. Тест на фикстуре: ветка задачи несёт изменённую функцию, планка
на новое поведение импортирует `orchestrator` от `__file__` — прогон
через материализацию и `cwd` по AC-1/AC-2 зелёный на ветке с новым
поведением и красный при прогоне на коде без него (main/устаревшая
копия).

AC-8. Тест: материализация по AC-1 поверх существующей устаревшей
копии `tasks/<id>/acceptance_tests/` в рабочем каталоге заменяет её
содержимым текущей головы артефактной ветки; прогон после подтяжки
main (AC-4) использует тот же материализованный путь, что и остальные
точки.

AC-9. Существующие тесты регрессии №12
(`tests/test_artifact_materialization.py`, `tests/test_fsm_autogate.py`)
остаются зелёными без ослабления.
