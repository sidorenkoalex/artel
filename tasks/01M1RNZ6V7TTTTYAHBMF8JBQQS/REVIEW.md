## Замечания

- major — `orchestrator/acceptance.py:89` (`gitcmd.ls_tree_files(...) or
  []`) в связке с прунингом `orchestrator/acceptance.py:97-103` —
  `ls_tree_files` документированно возвращает `None`, когда git НЕ
  ОТВЕТИЛ, отдельно от легитимного пустого списка (`gitcmd.py:306-315`,
  докстринг: «Пустой список — легитимный ответ... не путать с None»).
  `materialize_from_branch` эту разницу теряет через `or []`: `wanted`
  становится пустым словарём и в случае «в ветке правда пусто», и в
  случае «git не ответил». Раньше (до этой задачи) это было безопасно
  — материализация шла во ФРЕШ временный каталог, и пустой `wanted`
  просто не создавал `acceptance_tests/` вовсе (цикл записи создавал
  каталог только на непустом `wanted`), что дальше ловил явный guard
  «не найдена в источнике» (fsm.py:340-373). Теперь материализация идёт
  НА МЕСТО поверх уже существующего каталога: если планка уже была
  реально материализована РАНЬШЕ (тот же `wt_path`/workspace
  переиспользуется на всём протяжении задачи — `workspace.ensure`,
  `config.PROJECTS/<target>/workspace`), а на ПОВТОРНОМ вызове (второй
  проход review после changes_requested, повторная подтяжка main и
  т.п.) git разово не ответил на `ls_tree_files` — прунинг
  (`orchestrator/acceptance.py:97-103`) удаляет с диска РЕАЛЬНЫЕ файлы
  планки, каталог остаётся (пустым, но `is_dir()` всё ещё True), guard
  «не найдена в источнике» не срабатывает (каталог существует), и
  `acceptance.run` гоняет `unittest discover` на пустом каталоге.
  Voспроизведено эмпирически (см. «Проверено исполнением»): первый
  вызов кладёт реальный тест, второй с замоканным `ls_tree_files ->
  None` стирает его до пустого каталога, `acceptance.run` после этого
  возвращает `green=False` с текстом `NO TESTS RAN` — то есть не
  тихий зелёный проход, а ЛОЖНЫЙ КРАСНЫЙ (задача уходит в escalated
  «приёмочные тесты красные после подтяжки» или отказ ревью с текстом,
  который выглядит как реальный провал тестов, хотя тесты в ветке
  целы, просто временно не прочитаны git'ом и стёрты с диска на их
  месте). Это тот же класс проблемы, который PLAN сам называет
  прецедентом для этой функции — `artifact_branch.materialize_task_dir`
  (`orchestrator/artifact_branch.py:178-180`) — и там разница `None`
  учтена явно: `if paths is None: return ""` ДО прунинга, диск не
  трогается вовсе при сбое git. `materialize_from_branch` этот же
  паттерн скопировал не полностью — прунинг остался безусловным.
  Предложение: перед построением `wanted` проверить `paths is None` и
  в этом случае вернуть `tdir` НЕ трогая диск (как в
  `materialize_task_dir`), чтобы сбой git не путался с легитимной
  пустотой ветки.

- minor — `tests/test_branch_freshness_gate.py:284`
