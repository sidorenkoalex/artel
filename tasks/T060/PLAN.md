# PLAN: Лимитер параллельных задач: MAX_PARALLEL_TASKS=2

## Подход
Лимитер — не новый конечный автомат, а чтение уже существующей
lease-механики (T044): «занятая другая задача» — строка
`store.all_leases`, чей `heartbeat_ts` не старше
`config.LEASE_STALE_AFTER_SEC` (`liveness._age_seconds`) и чей `pid`
адресуем **на своём host** (`liveness._pid_alive`), исключая строки с
`task_id`, равным стартующей задаче. Для строк с чужим `hostname` (не
равным `socket.gethostname()`) `_pid_alive` не зовётся вовсе — pid
другой машины нельзя ни подтвердить, ни опровергнуть локально, такая
строка считается занятой без проверки pid (тот же приём, что уже
использует `doctor.check_leases`/`check_merge_lock` и
`merge_lock._holder_is_dead`), heartbeat при этом по-прежнему решает
как host-независимая проверка.

Новый модуль `orchestrator/parallel_limit.py` (по образцу `budget.py`/
`merge_lock.py` — маленький модуль, читающий store+liveness, без
собственного состояния) с двумя функциями:
- `busy_other_tasks(conn, task_id)` — список живых lease чужих задач;
- `refusal(conn, task_id)` — именованный текст отказа (id каждой занятой
  задачи, `session_id` держателя, значение `MAX_PARALLEL_TASKS`) или
  `None`, если можно стартовать.

Единственная точка встраивания — `runner._cmd_run` (требование 2 SPEC
называет только команды `run`/`auto`; `auto` внутри каждого шага цикла и
так зовёт `runner.cmd_run`, отдельного встраивания в `auto.py` не нужно —
тот же приём, каким уже работает `budget.budget_block`). Проверка встаёт
сразу после существующей проверки бюджета и до резолвинга роли/worktree/
pre-flight: как и бюджет, она не зависит от состояния задачи, а от
общесистемного ресурса (слотов параллельности).

Отказ обязан появиться в журнале задачи даже при одиночном (не через
`auto`) вызове `run` (AC-1) — в отличие от `budget_block`, чей текст
попадает в журнал только через `auto.auto_stop` (сам `budget_block` не
журналирует), лимитер журналирует явно сам, ДО прерывания управления, тем
же приёмом, что и отказ по чужой ветке worktree чуть ниже по файлу.
Прерывание — `sys.exit(refusal)`, не `print+return`: это даёт `auto`
поймать отказ через уже существующий `except SystemExit` в
`_cmd_auto` и остановить цикл на первом же шаге через `auto_stop`
(вместо того, чтобы после «псевдо-успешного» `run` по ошибке попытаться
`advance` несуществующий результат шага) — то же поведение, что уже даёт
`budget_block` бюджету.

## Шаги

1. `orchestrator/config.MAX_PARALLEL_TASKS = 2` — новая константа рядом с
   `LEASE_STALE_AFTER_SEC` (требование 1).
2. `orchestrator/parallel_limit.py` — `busy_other_tasks`/`refusal`
   (требование 2, 3).
3. Встраивание в `orchestrator/runner._cmd_run`: вызов `refusal`,
   `store.journal` + `sys.exit` при отказе (требования 2-4).
4. Юнит-тесты `tests/test_parallel_limit.py` на сами функции модуля

## Влияние на систему
Новый модуль только читает `store.all_leases`/`liveness` — не пишет
lease, не меняет `lease.py`/`merge_lock.py`, не заводит новую таблицу.
Единственная точка записи — журнал (`store.journal`) при отказе, тем же
способом, что уже используют соседние отказы `_cmd_run`.

Единственная точка встраивания — начало `_cmd_run`, до резолвинга роли:
поведение существующих pre-start проверок (бюджет, роль, worktree,
pre-flight, fixation) не меняется, они просто не достигаются при отказе
лимитера — так же, как сейчас не достигаются при отказе бюджета.
`kill`/`status`/`approve`/`reject`/`budget`/`log`/`doctor`/`new` лимитер
не импортируют и не вызывают — требование 5 выполняется самой
локальностью встраивания, не отдельной проверкой «эта команда не
считается».

`AUTO_MAX_STEPS`, `LIMIT_REVIEW_ITERS`, `LIMIT_ACCEPT_REJECTS` и прочие
существующие лимиты не трогаются. `MAX_PARALLEL_TASKS` — новый лимит того
же класса (ADR-0002, правило 2): значение меняет только Оператор правкой
`config.py`; тест инварианта в `tests/test_invariants.py` защищён тем же
процессом (правка/удаление/skip — только через ADR), что и остальной
модуль.

Откат: удаление модуля `parallel_limit.py`, вызова в `_cmd_run` и
константы в `config.py` — три локальных правки без миграции схемы БД
(таблица `leases` не меняется).

Существующие тесты (`test_auto_cycle.py`, `test_lease.py`,
`test_invariants.py`, весь пакет) не ослабляются — новый лимит по
умолчанию не блокирует однопоточные прогоны тестов: песочницы либо не
заводят чужих lease вовсе (обычный `all_leases` пуст или содержит только
lease самой тестируемой задачи, который лимитер исключает), либо (этот
файл) заводят их намеренно ровно там, где проверяют лимитер.

## Риски
- `tasks/T060/acceptance_tests/test_max_parallel_tasks.py::
  Ac5GateAndReadonlyCommandsIgnoreLimiterTest::test_ac5_kill_ignores_the_limiter`
  красный независимо от лимитера: ассерт `assertIsNone(row)` ожидает, что
  `cleanup.cmd_kill` удаляет строку `tasks` из БД. Это никогда не было
  поведением `cmd_kill` (`orchestrator/cleanup.py:150-178`,
  `_cmd_kill`/`cleanup_killed_task` только переводят `state` в `killed`
  и чистят ветку/worktree/каталог — строка остаётся историей, docs/
  design.md §6 «уборка... не может отменить», `tests/test_kill_cleanup.py`
  проверяет это тем же способом во всех сценариях, включая полную
  локальную уборку). Воспроизведено без сидинга «занятых» задач вовсе —
  причина не в лимитере T060. Правка `cmd_kill` под этот ассерт нарушила
  бы принцип целостности (сломала бы весь `test_kill_cleanup.py`) и вне
  зоны SPEC T060 (материалы SPEC называют только lease.py/liveness.py/
  store.all_leases). Файл теста залочен (T023) — не правлю. Остальные 11
  из 12 тестов файла (включая три других сценария AC-5 — approve/reject/
  status) зелёные.
- Значение `MAX_PARALLEL_TASKS=2` жёстко в коде — смена требует правки
  `config.py` Оператором (осознанно, SPEC требование 6). Отдельной
  команды/конфига под него SPEC не просит («Не входит»).
- Лимитер читает `store.all_leases` без блокировки транзакции: TOCTOU
  между подсчётом и стартом агента (две сессии одновременно проходят
  проверку на пустом слоте) в объём SPEC не входит — тот же класс гонки,
  что и до T044 у самого lease, там его закрывает `BEGIN IMMEDIATE`
  внутри `lease.acquire`, здесь отдельного write-пути нет, править нечего
  без выдумывания нового лока за рамками задачи.

## Предложения системе
- `tasks/T060/acceptance_tests/test_max_parallel_tasks.py::
  Ac5GateAndReadonlyCommandsIgnoreLimiterTest::test_ac5_kill_ignores_the_limiter`
  проверяет несуществующее поведение `cmd_kill` (удаление строки `tasks`)

  test-authoring (роль test_author) не имеет доступа прогнать

  чужую команду (`kill`), — стоило бы явно сверяться с существующими
  тестами затрагиваемых команд, а не только со SPEC своей задачи.
