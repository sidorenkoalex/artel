# SPEC: Лимитер параллельных задач: MAX_PARALLEL_TASKS=2

## Контекст
Контур параллельности (lease T044, worktree T045, CAS T050, сверка
свежести T051, возврат T052, merge queue T053, изоляция хуков T058,
автокоммит T059) собран, но формального потолка числа одновременно
работающих задач в системе нет — неявная бесконечность, сдерживаемая
только дисциплиной Оператора. Решение Оператора 28.08 (очередь п.2б
роадмапа): ввести код-лимит `MAX_PARALLEL_TASKS = 2`, читающий уже
существующую lease-механику, а не новый конечный автомат.

## Требования
1. Новая константа `orchestrator/config.MAX_PARALLEL_TASKS = 2`, по
   аналогии с существующими числовыми порогами (`LEASE_STALE_AFTER_SEC`,
   `AUTO_MAX_STEPS`).
2. Перед стартом агентного шага (команды `run` и `auto`) считается
   число ДРУГИХ задач (`task_id`, отличный от текущей), находящихся в
   работе прямо сейчас: из `store.all_leases` берутся строки, чей
   `heartbeat_ts` не старше `config.LEASE_STALE_AFTER_SEC`
   (`liveness._age_seconds`) И чей `pid` адресуем на своём host
   (`liveness._pid_alive`). Протухшие по heartbeat и мёртвые по pid
   lease в счёт не идут. Lease самой текущей задачи (её собственный
   `task_id`) в счёт не входит независимо от того, чей это `session_id`.
3. Если посчитанное число ≥ `config.MAX_PARALLEL_TASKS`, шаг не
   стартует: именованный отказ, перечисляющий id каждой засчитанной
   занятой задачи, `session_id` её держателя и значение потолка;
   отказ пишется в журнал задачи (`store.journal`) так же, как прочие
   отказы `run`/`auto` (budget_block, чужая ветка worktree). Никакого
   ожидания или ретрая в цикле — тот же немедленный отказ, что у уже
   существующих pre-start проверок `_cmd_run`.
4. Если посчитанное число < `config.MAX_PARALLEL_TASKS`, шаг стартует
   как раньше — лимитер не меняет никакое другое поведение старта
   шага.
5. Команды, не запускающие агентный шаг — `status`, `log`, `doctor`,
   `approve`, `reject`, `kill`, `budget`, `new` — лимитер не
   затрагивает: их поведение при достигнутом потолке не меняется.
6. Лимит — защита класса «лимит» (ADR-0002, правило 2): значение
   `MAX_PARALLEL_TASKS` меняет только Оператор правкой
   `orchestrator/config.py`; проверка кодируется тестом в
   `tests/test_invariants.py`, который сам является неослабляемым
   (правки/удаление/skip этого теста — только Оператором через ADR).
7. Существующие тесты (в т.ч. `tests/test_auto_cycle.py`,
   `tests/test_lease.py`, `tests/test_invariants.py`) остаются
   зелёными без ослабления.

## Критерии приёмки
AC-1. Две задачи держат живые lease (heartbeat не старше
`LEASE_STALE_AFTER_SEC`, pid адресуем) чужих (по отношению к третьей
задаче) сессий → `run` третьей задачи отказывает именованным отказом,
перечисляющим id обеих занятых задач, `session_id` их держателей и
значение `MAX_PARALLEL_TASKS`; запись об отказе появляется в журнале
третьей задачи; `auto` третьей задачи отказывает тем же образом на
первом же шаге цикла.

AC-2. Только одна другая задача занята (её lease живой) — запуск
второй задачи проходит без отказа лимитера.

AC-3. Другая задача формально держит lease, но он протух
(`heartbeat_ts` старше `LEASE_STALE_AFTER_SEC`) или её `pid` мёртв —
такая задача не засчитывается против потолка; запуск второй задачи в
этих условиях проходит.

AC-4. Собственный lease задачи (тот же `task_id`, что и у стартующей
команды) не засчитывается против неё самой: повторный `run` (или
внутренний `run` внутри `auto`) той же задачи, чей lease она сама и
держит, лимитером не блокируется.

AC-5. `kill`, `status`, `approve`, `reject` любой задачи выполняются
без отказа лимитера, даже когда число других занятых задач ≥
`MAX_PARALLEL_TASKS`.

AC-6. Неослабляемый тест инварианта в `tests/test_invariants.py`
подтверждает: запуск шага (`run`/`auto`) при достигнутом потолке
отказывает, и этот отказ не обходится ни повторным вызовом `run`, ни
вызовом `advance` следующим за отказавшим шагом.

AC-7. Все существующие тесты пакета зелёные после изменения.

## Не входит
- Изменение lease-механики: порог свежести, команда явного
  release — отдельная строка очереди (P3).
- Очередь ожидания освобождающегося слота или автозапуск при
  освобождении: отказ немедленный, без ретрая в цикле.
- Per-target потолки — лимит один, глобальный на весь пульт.
- Правка `docs/invariants.md`: текст строки готовится в PLAN (по
  образцу T058), вносит Оператор при мерже.
