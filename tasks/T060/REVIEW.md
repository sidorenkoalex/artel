## Замечания

- major — `orchestrator/parallel_limit.py:23` (и модульный докстринг, строка 7) — `busy_other_tasks` зовёт `liveness._pid_alive(row["pid"])` для КАЖДОЙ строки `leases`, не проверяя `row["hostname"] == socket.gethostname()`. SPEC требование 2 явно квалифицирует условие: «чей `pid` адресуем **на своём host**». `_pid_alive` — это `os.kill(pid, 0)` на ЛОКАЛЬНОЙ машине; для строки с чужим `hostname` число `pid` относится к процессной таблице ДРУГОЙ машины и не значит вообще ничего на этой. В самом же кодовом окружении задачи (leases несут `hostname` не просто так) уже есть ТРИ прецедента, и все три гейтят `_pid_alive` по хосту, прежде чем его звать: `orchestrator/doctor.py:610-613` (`check_leases`: `row["hostname"] == host and not liveness._pid_alive(...)`), `orchestrator/doctor.py:647-651` (`check_merge_lock`: чужой host — `"pid не проверяется"`, замок остаётся held), `orchestrator/merge_lock.py:38-39` (`row["hostname"] == socket.gethostname() and not liveness._pid_alive(...)`). Во всех трёх «чужой host» трактуется как «нельзя опровергнуть — считаем живым», не как «неважно, проверим локально».
  Сценарий поломки: пульт общий на несколько host (сама модель данных `leases.hostname` + прецеденты выше это предполагают). Задачи T901/T902 реально работают на host-B (их lease свежие, pid живы там). Оператор на host-A запускает `run` третьей задачи. `busy_other_tasks` вызывает `os.kill(pid_T901, 0)`/`os.kill(pid_T902, 0)` уже на host-A — с вероятностью, близкой к «почти всегда» (числа pid host-локальны), там нет процесса с таким pid → `ProcessLookupError` → обе строки исключаются как «мёртвые» → лимитер видит 0 занятых → третья задача стартует, хотя реально заняты 2 из 2 слотов. Лимит, единственная цель которого — не дать разрастись рою параллельных `auto` (контекст TZ.md: «runaway-выводок auto уже случался»), обходится тихо, без единого отказа. Обратный случай (совпадение номера pid с посторонним локальным процессом) даёт симметричную ошибку — живой чужой lease посчитан мёртвым или мёртвый посчитан живым, в обе стороны непредсказуемо.
  Предложение: как и в трёх прецедентах — исключать по pid только строки со своим host (`row["hostname"] == socket.gethostname()`); для чужого host не звать `_pid_alive` вовсе и считать занятой (протухшую по heartbeat — по-прежнему не считать, это host-независимая проверка). Заодно стоит поправить формулировку в PLAN.md «Подход» (сейчас без «на своём host» — см. Фазу A выше), раз уж по ней писался код.

- minor (informational, не требует правки T060) — `tasks/T060/acceptance_tests/test_max_parallel_tasks.py::Ac5GateAndReadonlyCommandsIgnoreLimiterTest::test_ac5_kill_ignores_the_limiter` красный. Перепроверено вручную (`python3 -m unittest tasks.T060.acceptance_tests.test_max_parallel_tasks -v`): 11/12 зелёных, этот один падает с тем же диагнозом, что и в PLAN.md «Риски» — ассерт ожидает удаления строки `tasks`, чего `cleanup.cmd_kill` никогда не делал (`orchestrator/cleanup.py:150-178`, состояние переводится в `killed`, строка остаётся историей). Подтверждено чтением `cleanup._cmd_kill` и независимо тем, что `tests/test_kill_cleanup.py` целиком проверяет именно это поведение как штатное. Файл теста залочен (T023), правка вне полномочий разработчика и вне зоны SPEC T060. Само поведение команды `kill` (не блокируется лимитером) реализовано верно — три других сценария AC-5 (approve/reject/status) зелёные и подтверждают требование 5 независимо от этого теста.

## Предложения системе

- Тот же класс бага («забыли гейтить `liveness._pid_alive` по хосту перед
  вызовом») теперь всплывал трижды как ПРАВИЛЬНО решённый прецедент
  (`doctor.py` x2, `merge_lock.py`) и один раз как дефект (T060,
  `parallel_limit.py`) — конвенция существует только как повторяемый
  паттерн в трёх местах, не как единая точка. Стоит вынести в
  `liveness.py` сам хелпер вида `pid_alive_on_own_host(row)` (принимает
  строку с `hostname`/`pid`, сам сравнивает с `socket.gethostname()`),
  чтобы четвёртый читатель `leases`/`merge_locks` физически не мог забыть
  проверку — материалы SPEC новых задач, читающих lease-механику, тогда
  указывали бы на неё, а не на голый `_pid_alive`.
