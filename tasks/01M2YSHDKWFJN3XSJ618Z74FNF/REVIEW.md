## Фаза A: гейт плана

1. **Покрытие требований.** Таблица PLAN («Покрытие требований») полна:
   требования 1-7 ↔ шаги 1-6, и каждый шаг найден в диффе
   (`scripts/guard.py` — разбор, `orchestrator/advance_gates/
   plan_appendix.py` — гейт, `orchestrator/auto.py` — класс отказа,
   `orchestrator/fsm_merge_gate.py` — применение, `orchestrator/
   fsm_postmerge.py` — строка RETRO, `tests/test_plan_appendix.py` +
   `docs/codebase-map.md`). За итерацию 3 PLAN дополнен разделом «Подход»
   п.1 (ограда на колонке 0 с доводом про префикс строки unified-диффа и
   своя ошибка переименования) — текст PLAN и фактический дифф совпадают.
2. **Размер шагов.** Шесть шагов — проверяемые единицы размера MR; ни
   микроопераций, ни «сделать всё».
3. **Конфликт с конвенциями/архитектурой.** Нет. Гейт повторяет форму
   `advance_gates/zones.py` (`GateRefusal`/`_run_gates`, обёртка
   `_xxx_gate_refuses`, пропуск внешнего target), применение на мерже
   встроено между `_perform_carpentry_merge` и `_publish_merge_artifacts`
   без правки соседей.
4. **«Влияние на систему» = фактический дифф.** Коммиты задачи
   (`264b449e`, `958a52c7`, `b919b42a`) трогают ровно зоны SPEC; в
   `tests/` за все три коммита изменён РОВНО один файл — новый
   `tests/test_plan_appendix.py` (`git show --stat` по каждому коммиту),
   ни одного существующего ассерта не изменено и не удалено; планка
   `acceptance_tests/` в итерации 3 не правилась (коммит `b919b42a` —
   `scripts/guard.py`, `tests/test_plan_appendix.py`,
   `docs/codebase-map.md`), то есть ADR-0011/0012 не задействованы.
   Пометок `manual`/`skip` в планке нет — автогейт acceptance задачи цел.
   Путь отката («revert merge-коммита») реален.
   Замечанием не является, но для точности: фраза «задача без приложений
   не платит ни одним новым вызовом git» верна для гейта `in_dev`
   (выход по пустому списку до `diff_base`), а на мерже один новый вызов
   всё же есть — чтение PLAN.md с ветки-источника
   (`fsm_merge_gate.py:_plan_appendices_or_refuse`, `gitcmd.show`). AC-13
   («нет ни коммита приложений, ни полного прогона, ни записи журнала»)
   этим не нарушен, сценария поломки нет — отсюда и не замечание.

## Предложения системе

- Сборщик ревью-пакета (`orchestrator/review.py`) ТРЕТИЙ раз подряд на
  этой задаче не нашёл SPEC.md и PLAN.md («в ветке — path does not exist;
  в дереве — файл не найден»), хотя оба лежат в рабочем каталоге шага
  (`tasks/<id>/`, материализованы из артефактной ветки). Ревьювер каждый
  раз читает их инструментом сам; класс «пакет молча теряет обязательный
  компонент вместо отказа сборки» подтверждён на одной задаче трижды —
  дешевле починить поиск (искать в рабочем каталоге, раз ветка кода
  артефактов не несёт), чем платить чтением на каждой итерации.
- Инкрементальный diff пакета пуст и на этой итерации — по той же
  причине, что и на прошлой (sha «прошлого вердикта» совпадает с HEAD,
  потому что коммит правок роли лёг после вердикта). Обходной приём
  описан в `skills/review-checklist.md`, но чинить стоит выбор базы в
  сборщике: ревьювер без этого абзаца скила решил бы, что ветка не
  менялась, и аппрувнул бы неотсмотренный коммит.
