## Замечания

- **major — scripts/guard.py:264 (`_DIFF_FENCE_CLOSE`; парная строка 263
  `_DIFF_FENCE_OPEN`) — контекстная строка диффа ` ``` ` закрывает блок
  ```diff досрочно: корректное приложение к защищённому markdown-файлу,
  несущему ограду кода, разбирается в ОБРЕЗАННЫЙ патч.**
  `_DIFF_FENCE_CLOSE = re.compile(r"^\s*```\s*$")` допускает ведущий
  пробел, а контекстная строка unified-диффа — это ровно «пробел +
  строка файла». Файл `docs/adr/0003-target-projects.md` (защищённый
  путь, `docs/adr/` в `config.PROTECTED_PATHS`) несёт две ограды в
  начале строки — приложение, чей хунк захватывает такую строку
  контекстом, режется на ней.
  Сценарий поломки (воспроизведён на настоящем git, см. «Проверено
  исполнением»): Оператор правит абзац ADR рядом с примером команды,
  `git diff` даёт патч, который `git apply` принимает с кодом 0;
  `guard.plan_appendices` того же текста возвращает приложение с диффом,
  обрезанным на строке ` ``` `, и `git apply` разобранного патча
  отвечает `error: corrupt patch at line 11`. Гейт `in_dev` отказывает
  переходу действием «переход отклонён: приложение PLAN неприменимо» —
  то есть классом «роль ещё не закончила»: `auto` тратит гарантированный
  шаг developer, роль читает «почини unified-дифф», хотя её дифф
  корректен, чинить нечего, и на повторе задача встаёт `Stop`'ом. Это
  тот же тупик «отказ, который роль не может починить», против которого
  заведены R1-F2 и R1-F4, только на другом входе.
  Класс ограничен одним местом: разбор оград — единственная точка
  (`scripts/guard.py:263-264`), мерж читает тот же результат
  (`fsm_merge_gate.py:576` через `guard.plan_appendices`), своего
  разбора не имеет.
  Предложение: закрепить ограду на колонке 0 — `_DIFF_FENCE_OPEN =
  r"^```diff\s*$"`, `_DIFF_FENCE_CLOSE = r"^```\s*$"` (контекст диффа
  всегда несёт ведущий пробел/`+`/`-`, поэтому перестаёт закрывать
  блок). Проверено: с этой правкой все 20 сегодняшних PLAN с разделом
  «## Приложение» разбираются байт-в-байт как сейчас (0 расхождений), а
  приложение с оградой внутри хунка разбирается целиком. Тест на угол:
  приложение к md-файлу, чей хунк несёт контекстную строку ` ``` `,
  отдаёт дифф без потери строк.

- **minor — scripts/guard.py:386 — заголовок `diff --git a/<старый>
  b/<новый>` (переименование) отвергается ошибкой, текст которой
  утверждает обратное: «приложение PLAN: нет заголовка diff --git».**
  Проверка `any(old != new for old, new in headers)` по существу верна
  (тест `test_rename_header_with_two_different_paths_is_refused`
  объясняет почему), но переиспользует `APPENDIX_NO_HEADER_ERROR`.
  Последствие: роль, вставившая вывод `git diff -M` по
  переименованному файлу `skills/`, читает в брифе, что заголовка нет,
  видит его на месте и чинит наугад — и каждая попытка снова стоит
  гарантированного шага developer (класс AC-6).
  Предложение: своя именованная ошибка вида «приложение PLAN: заголовок
  `diff --git` называет разные пути a/ и b/ — переименование приложением
  не поддерживается», с собственным тестом.

## Предложения системе

- Сборщик ревью-пакета (`orchestrator/review.py`) второй раз подряд не
  нашёл SPEC.md и PLAN.md задачи («в ветке — path does not exist; в
  дереве — файл не найден»), хотя оба лежат в рабочем каталоге шага.
  Наблюдение уже записано ревью итерации 1 — повторяю, потому что класс
  «пакет молча теряет обязательный компонент вместо отказа сборки»
  подтверждён дважды на одной задаче.
- Инкрементальный diff пакета этой итерации пуст: sha предыдущего
  вердикта (958a52c7) совпал с HEAD ветки, хотя коммит с правками
  итерации 1 — это он и есть. Предупреждение скила
  (`skills/review-checklist.md`, «Инкрементальный diff пакета») сработало
  ровно как описано, но ревьювер каждый раз восстанавливает базу вручную;
  стоит чинить выбор базы в сборщике, а не держать обходной приём в скиле.
