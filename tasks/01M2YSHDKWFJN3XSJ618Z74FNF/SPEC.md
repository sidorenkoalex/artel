# SPEC: Приложения PLAN к защищённым путям: гейт применимости на выходе in_dev и применение пультом на мерже

## Контекст

Защищённые пути (`config.PROTECTED_PATHS`) роль менять не вправе: гейт
зон на выходе `in_dev` и гейт защищённых путей на merge_gate отказывают
безусловно с подсказкой «предложи правку приложением к PLAN (unified-
дифф)». Формат приложения сложился практикой (раздел PLAN.md с
заголовком, начинающимся на «## Приложение», внутри блок(и) ```diff с
`diff --git a/<путь> b/<путь>`; сегодня в `tasks/` восемь таких
разделов), но никто их не разбирает: guard и автогейты приложения не
читают, применимость не проверяется (инцидент 11.09 — хунк без
диапазонов, `git apply --check` отвечает «patch with only garbage»),
а применение остаётся ручным коммитом Оператора в main. После включения
хуков защиты main (01M2XMCC83) этот последний путь закрыт: приложение к
`skills/test-authoring.md` из PLAN задачи 01M2XJKKPH применить некому.
Задача закрывает обе дыры: разбор и проверку применимости до ревью и
применение приложений самим пультом в цикле мержа.

## Требования

1. Разбор приложений. Функция в `scripts/guard.py` (рядом с
   `section_body`) возвращает список приложений PLAN.md: по каждому
   блоку ```diff внутри разделов, заголовок которых начинается на
   «## Приложение», — пути из заголовков `diff --git` и текст диффа.
   Блок без корректного заголовка `diff --git` либо с путём вне
   `config.PROTECTED_PATHS` даёт именованную ошибку: «приложение PLAN:
   нет заголовка diff --git» / «приложение PLAN: путь <путь> не
   защищённый — правь в ветке задачи».

2. Гейт применимости на выходе `in_dev`. Новый гейт в пакете
   `orchestrator/advance_gates/`, точка подключения — список гейтов
   `in_dev` в `orchestrator/fsm_advance.py`. Каждое приложение PLAN
   проходит `git apply --check` против дерева базы сравнения ветки
   (`gitcmd.diff_base` — тот же выбор базы, что у гейта зон
   `orchestrator/advance_gates/zones.py`). Отказ — именованное действие
   журнала «переход отклонён: приложение PLAN неприменимо» с путём и
   текстом git; класс отказа — «роль ещё не закончила»: шаг developer
   повторяется, отказ доносится до роли историей отказов брифа. PLAN без
   приложений гейт не трогает. Класс отказа задаётся в
   `orchestrator/auto.py::_pre_advance_step` по образцу отказа гейта зон
   «мандат есть, раздел PLAN не оформлен» (редактура Оператора 20.09):
   на этом действии шаг developer запускается, стоп-кран двух одинаковых
   отказов не срабатывает; повтор того же отказа ПОСЛЕ шага developer —
   `Stop` как сегодня, то есть один гарантированный шаг.

3. Применение на мерже. В теле гейта merge_gate
   (`orchestrator/fsm_merge_gate.py`, цикл `approve`) после плотницкого
   merge и ДО снимка артефактов приложения применяются в scratch-дереве
   (`git apply`) и коммитятся одним коммитом «<id>: приложения Оператора
   — <пути>».

4. Неприменимость на мерже (main сдвинулся) — не `sys.exit`: задача
   возвращается в `in_dev` с причиной «приложение PLAN неприменимо после
   подтяжки: <путь>» тем же путём, что возврат по конфликту merge,
   scratch-дерево убирается.

5. Проверка после применения. Если хоть одно приложение трогает `tests/`
   или `.github/`, перед push в scratch-дереве выполняется
   `acceptance.run_full_suite(scratch)`; красный прогон — именованный
   отказ мержа «приложения ломают тесты: <хвост>»: задача остаётся на
   merge_gate, scratch убирается, приложения не публикуются. Для
   остальных защищённых путей (skills, templates, docs/adr,
   docs/invariants.md, конфигурация) прогон не требуется — их проверит
   CI main.

6. Журнал и RETRO. На мерже журналируется запись «приложения применены:
   <пути> (sha)»; RETRO задачи несёт строку с перечнем применённых путей
   (сборка RETRO — `orchestrator/fsm_postmerge.py`, зона задачи).

7. Тесты в `tests/` на всё перечисленное (критерии приёмки ниже).
   Перечисленные в AC-13 существующие тесты остаются зелёными БЕЗ
   правок; прочие существующие тесты правятся только там, где новое
   поведение законно меняет их ожидания.

## Критерии приёмки

AC-1. Разбор PLAN.md с разделом «## Приложение …», несущим блок ```diff
с заголовком `diff --git a/<защищённый путь> b/<защищённый путь>`,
возвращает одно приложение: путь из заголовка и текст диффа; несколько
блоков в разделе (или несколько разделов) дают несколько приложений в
порядке появления.

AC-2. Блок ```diff без корректного заголовка `diff --git` даёт ошибку
«приложение PLAN: нет заголовка diff --git».

AC-3. Блок ```diff с путём вне `config.PROTECTED_PATHS` даёт ошибку
«приложение PLAN: путь <путь> не защищённый — правь в ветке задачи».

AC-4. PLAN.md без разделов «## Приложение» даёт пустой список приложений
и ни одной ошибки.

AC-5. Гейт применимости на выходе `in_dev`: PLAN с приложением, которое
не проходит `git apply --check` против базы сравнения ветки, отказывает
переходу — состояние не меняется, в журнале запись с действием «переход
отклонён: приложение PLAN неприменимо», detail несёт путь приложения и
текст ответа git.

AC-6. Отказ AC-5 относится к классу «роль ещё не закончила»: `auto`
(`_pre_advance_step`) не останавливается на нём для Оператора, а
запускает шаг developer заново, и отказ попадает в историю отказов брифа
роли; тот же отказ, повторившийся ПОСЛЕ шага developer, останавливает
`auto` как сегодня (один гарантированный шаг).

AC-7. PLAN с применимым приложением гейт AC-5 пропускает; PLAN без
приложений проходит переход `in_dev` в точности как до задачи.

AC-8. На мерже приложение применено в scratch-дереве, и главная ветка
после merge несёт отдельный коммит «<id>: приложения Оператора — <пути>»
с изменением защищённого пути из приложения; коммит стоит ДО коммита
снимка артефактов.

AC-9. Приложение, не применимое в scratch-дереве после подтяжки main:
цикл мержа не завершает процесс `sys.exit`'ом — задача переводится в
`in_dev` с причиной «приложение PLAN неприменимо после подтяжки:
<путь>», scratch-дерево убрано.

AC-10. Приложение, трогающее `tests/` (или `.github/`), запускает
`acceptance.run_full_suite` в scratch-дереве до push; красный прогон даёт
отказ мержа «приложения ломают тесты: <хвост>» — задача остаётся на
merge_gate, scratch убран, main не продвинут, приложения не
опубликованы.

AC-11. Приложение только к защищённому пути вне `tests/` и `.github/`
(например к `skills/`) полного прогона не запускает, мерж идёт дальше.

AC-12. После успешного мержа с приложениями журнал задачи несёт запись
«приложения применены: <пути> (sha)», а RETRO задачи — строку с
перечнем применённых путей.

AC-13. PLAN без приложений: мерж идёт прежним путём байт-в-байт — нет ни
коммита приложений, ни полного прогона, ни записи журнала о приложениях;
существующие `tests/test_protected_paths_gate.py`,
`tests/test_merge_gate_ci_wait.py`,
`tests/test_fsm_merge_gate_done_snapshot.py`,
`tests/test_fsm_merge_gate_scratch_worktree_cleanup.py` остаются
зелёными без правок.

## Оценка объёма и деление

Прогноз диффа: 30 КиБ

Сработавшие сигналы: число затрагиваемых модулей/файлов (семь зон:
`scripts/guard.py`, `orchestrator/advance_gates/`,
`orchestrator/fsm_advance.py`, `orchestrator/fsm_merge_gate.py`,
`orchestrator/fsm_postmerge.py`, `orchestrator/auto.py`, `tests/`); число критериев приёмки (13);
затронут инвариантный механизм (`scripts/guard.py` и строка «Защищённые
пути меняет только Оператор» в `docs/invariants.md`). Бюджет ($45) и
прогноз диффа (30 КиБ против порога 128 КиБ) сигналами не являются.

Предложение — **монолит**. Нарезка по границам зон возможна ровно одна:
часть 1 «разбор + гейт применимости» (`scripts/guard.py`,
`orchestrator/advance_gates/`, `orchestrator/fsm_advance.py`, `tests/`),
часть 2 «применение на мерже» (`orchestrator/fsm_merge_gate.py`,
`orchestrator/fsm_postmerge.py`, `tests/`). Против неё три факта:
цель задачи (инцидент 20.09 — приложение применить некому) закрывает
ТОЛЬКО часть 2, часть 1 в одиночку ужесточает вход, не открывая выхода;
часть 2 без части 1 не существует вовсе (нет разбора), значит порядок
строго последовательный и выигрыша в параллельности нет; цена деления —
полный второй конвейер шагов (analyst + test_author + developer + две
итерации ревью, ~$20) при диффе ~30 КиБ, который укладывается в один
ревью-пакет (потолок гейта ёмкости 256 КиБ).

Честный довод в пользу нарезки: часть 1 сама по себе мержима с зелёной
планкой и систему в нерабочем состоянии не оставляет (приложения до
части 2 применяет Оператор вручную с маркером обхода, как и сегодня) —
то есть «атомарной сменой механики» монолит не является. Решение за
Оператором на гейте SPEC. Монолит принят Оператором 20.09: цель задачи
закрывает только применение на мерже, а часть «разбор + гейт» без неё
ужесточает вход, не открывая выхода.

Рамка ТЗ ($45) принята потолком задачи; калибровка скила для класса «5 и
более файлов зоны / больше 10 критериев» даёт ~$70 — если потолок
исчерпается, поднять его вправе только Оператор командой `budget`.
