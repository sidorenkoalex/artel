# PLAN: Приложения PLAN к защищённым путям: гейт применимости на выходе in_dev и применение пультом на мерже

## Подход

Механика делится на три независимо проверяемых узла, и ни один из них не
переписывает соседей:

1. **Разбор** — чистая функция `scripts/guard.py::plan_appendices(text)`
   рядом с `section_body`: один текстовый аргумент, возврат
   `(список PlanAppendix, список ошибок)`. `PlanAppendix` — NamedTuple
   `(paths, diff)`: пути берутся ИЗ ВСЕХ заголовков `diff --git a/<p>
   b/<p>` блока (не из заголовка раздела), текст диффа — весь блок без
   ограды ```` ``` ````. Раздел ищется тем же приёмом, что `section_body`,
   но по ПРЕФИКСУ заголовка («## Приложение…», SPEC требование 1),
   поэтому собственный разборщик разделов, а не вызов `section_body` по
   точному имени.

   Путей у приложения несколько, потому что `git diff` по двум файлам
   даёт ОДИН текст с двумя заголовками, и Оператор вставляет его одним
   блоком (образец — `tasks/01M1THKTJ7YT1K410G1KS17MK6/PLAN.md`, пять
   заголовков в одном блоке): защищённость проверяется у каждого пути, и
   каждый едет в `git add` на мерже. Дифф, оставшийся ВНЕ блоков ```diff
   (голая ограда ``` ), — именованная ошибка, а не молчание: молчаливый
   пропуск и есть способ потерять правку Оператора бесследно.

   Ограда блока распознаётся ТОЛЬКО на колонке 0 (R2-F1): в unified-диффе
   каждая строка содержимого начинается с пробела, `+` или `-`, поэтому
   ограда с допуском ведущих пробелов закрывалась бы контекстной строкой
   ` ``` ` — приложение к защищённому md-файлу с примером кода
   (`docs/adr/0003-target-projects.md` — реальный такой файл) резалось бы
   в обрезанный патч, и гейт отказывал бы переходу диффом, в котором роли
   нечего чинить. Разбор всех сегодняшних PLAN с разделом «## Приложение»
   от этого закрепления не меняется (проверено прогоном: 39 файлов,
   0 расхождений).

   Каждый повод отказа несёт СВОЮ именованную ошибку — в том числе
   заголовок-переименование `diff --git a/<старый> b/<новый>` (R2-F2):
   общий текст «нет заголовка diff --git» на два разных повода посылал бы
   роль искать то, что у неё на месте, ценой гарантированного шага
   developer.

2. **Гейт применимости** — новый модуль `orchestrator/advance_gates/
   plan_appendix.py` по образцу `zones.py`: `GateRefusal`/`_run_gates` из
   `_base.py`, сохранённая публичная обёртка `_plan_appendix_gate_refuses`,
   реэкспорт в `fsm_advance.py`, вызов в списке гейтов `in_dev` сразу после
   `_zones_gate_refuses` (оба читают PLAN.md и базу сравнения — соседство
   естественное; приёмочная планка от места в списке не зависит по
   построению, `_sandbox.py` докстринг).

   `git apply` требует РАБОЧЕГО ДЕРЕВА, а SPEC называет базой
   `gitcmd.diff_base(branch)` — поэтому гейт заводит временный detached
   worktree на sha базы (тот же приём, что `fsm_merge_gate::
   _scratch_worktree` уже несёт для мержа) и убирает его в `finally`.
   Дерево заводится ТОЛЬКО когда приложения в PLAN реально есть: PLAN без
   раздела «## Приложение» не платит ни одним вызовом git (AC-7, AC-13).

   Приложения кладутся на это дерево ПОДРЯД настоящим `git apply`, а не
   порознь через `--check`: мерж применяет их последовательно на одном
   дереве, и приложение, опирающееся на строку предыдущего, при проверке
   порознь против чистой базы отказывало бы ложно — отказом, который
   роль не может починить ничем, кроме склейки блоков. Дерево
   одноразовое, применённые правки уходят вместе с ним.

   Инфраструктурный отказ гейта (git не ответил на `diff_base`, дерево
   базы не развёрнуто) несёт СВОЁ действие журнала
   `PLAN_APPENDIX_GATE_FAILURE_ACTION` — тем же разделением, что у
   соседнего гейта зон: причина такого отказа не в PLAN.md роли, и шаг
   developer на нём был бы сожжён впустую.

3. **Применение на мерже** — отдельный шаг `_apply_plan_appendices` в
   `orchestrator/fsm_merge_gate.py`, зовётся в `_cmd_approve_merge_gate`
   МЕЖДУ `_perform_carpentry_merge` и `_publish_merge_artifacts`. Такое
   место даёт требуемый AC-8 порядок коммитов (приложения → снимок
   артефактов → карта/RETRO) без правки самого `_publish_merge_artifacts`,
   чьи существующие свойства AC-13 обязывает сохранить.

Ключевое решение по классам отказа (принцип «отказ чинит тот, чей
артефакт виноват»):

| Отказ | Форма | Кто чинит |
|---|---|---|
| Гейт `in_dev`: приложение неприменимо | `GateRefusal`, состояние не меняется | роль (класс «роль ещё не закончила») |
| Гейт `in_dev`: git не ответил (база, дерево базы) | `GateRefusal` ОТДЕЛЬНЫМ действием, вне класса «роль ещё не закончила» | Оператор |
| Мерж: `git apply` упал в scratch | `state -> in_dev`, БЕЗ `sys.exit` | роль |
| Мерж: красный полный прогон | журнал «merge FAILED» + `sys.exit` | Оператор, задача на `merge_gate` |
| Мерж: приложения не разобраны (ошибки требования 1) | журнал «merge FAILED» + `sys.exit` | Оператор (гейт `in_dev` такое уже не пропустил бы — значит PLAN правили на гейте) |

Ошибки разбора (AC-2/AC-3) гейт `in_dev` тоже считает отказом тем же
именованным действием: блок без заголовка `diff --git` иначе потерялся бы
бесследно — ровно тот молчаливый пропуск, против которого требование 1
вводит именованную ошибку.

Применение приложений — ТОЛЬКО для self-target (`ctx.path ==
config.ROOT`), тем же доводом, что карта и RETRO в
`_publish_merge_artifacts`: `config.PROTECTED_PATHS` — файлы пульта, у
внешнего target'а их либо нет, либо это не те же файлы.

Бюджет SPEC ($45) не переоценивается: шесть файлов зоны и шесть шагов ниже
— ровно тот объём, который SPEC и оценил.

## Влияние на систему

**Что затрагивается за пределами правки.** Выход `in_dev -> verifying`
получает восьмой рубеж, а цикл `merge_gate -> done` — ещё один шаг между
merge и публикацией артефактов. Оба узла — горячий путь КАЖДОЙ задачи
артели, поэтому оба построены так, что задача без приложений не платит ни
одним новым вызовом git: гейт выходит по `if not appendices: return None`
до создания worktree, шаг мержа — по тому же условию до `git apply`
(AC-7, AC-13 — именно это и проверяют).

**Инварианты и гейты рядом — почему не ослабляются.**
- Инвариант «защищённые пути меняет только Оператор» (docs/invariants.md)
  НЕ ослабляется, а впервые получает исполнимый канал: правка попадает в
  main отдельным коммитом только из раздела PLAN, который Оператор видел
  и пропустил на гейте, и только если путь входит в
  `config.PROTECTED_PATHS` (AC-3 отказывает всему остальному). Роль
  по-прежнему не может закоммитить защищённый путь в свою ветку — гейт зон
  и гейт защищённых путей на мерже не трогаются вовсе.
- `config.PROTECTED_PATHS` — только чтение, список не меняется.
- Гейт зон (`advance_gates/zones.py`), гейт защищённых путей мержа
  (`fsm_merge_gate::_protected_path_diff_gate`), `_guard_task_root_or_
  refuse`, автогейт acceptance — ни одна строка не меняется.
- Стоп-кран `auto` не ослабляется: новое действие получает РОВНО одну
  поблажку — первый шаг developer, ту же, что уже есть у отказа гейта зон
  «мандат есть, раздел PLAN не оформлен»; повтор того же отказа ПОСЛЕ
  завершённого шага роли останавливает цикл (AC-6, третий тест).
  Инфраструктурный отказ того же гейта поблажки не получает вовсе — он
  несёт отдельное действие и в `_IN_DEV_ROLE_FIXABLE_REFUSAL_ACTIONS` не
  входит.
- Красный полный прогон НЕ понижается до предупреждения: приложение к
  `tests/`/`.github/` не публикуется вовсе (AC-10).

**Деградации, выбранные сознательно.** PLAN.md, не прочитанный с
ветки-источника на мерже (git не ответил, ветка недоступна), — не отказ
мержа, а журналируемое предупреждение и «приложений нет»: тем же
принципом, что `_overlay_artifact_snapshot` уже применяет к провалу
материализации снимка. Довод: к моменту мержа применимость приложений уже
проверена гейтом `in_dev`, а превращать сбой чтения git в отказ мержа
значит добавить новую причину застревания задач на гейте — при этом
ничего некорректного в main такая деградация не пропускает (не применено
ничего).

**Откат.** Revert одного merge-коммита ветки задачи. Разбор в `guard.py` —
новые имена, ни одна существующая функция не меняется; вызовы в
`fsm_advance`/`auto`/`fsm_merge_gate`/`fsm_postmerge` — по одной строке
каждый, все под условием «приложения есть».

## Риски

- **Временный worktree базы сравнения на гейте `in_dev`.** Цена — один
  `git worktree add` на advance задачи, у которой в PLAN есть приложения.
  Уборка в `finally`, чтобы отказ/исключение не оставляли записи
  `.git/worktrees/`. Риск остаточного мусора при жёстком убийстве
  процесса — тот же, что уже несёт scratch-дерево мержа, и лечится тем же
  `git worktree prune`.
- **Полный прогон в scratch на мерже.** Приложение к `tests/` или
  `.github/` добавляет к merge-окну время полного набора
  (`FULL_SUITE_TIMEOUT_SEC`) под удерживаемым мьютексом мержа. Это прямое
  требование 5 SPEC; смягчение — прогон запускается РОВНО для двух классов
  путей, для `skills/`/`templates/`/`docs/` его нет (AC-11).
- **Приложение, применимое к базе сравнения, но не к сдвинувшемуся main.**
  Закрыто требованием 4: возврат в `in_dev`, не порча main половиной
  хунков.

## Предложения системе

- `skills/coding-standards.md` требует прогонять «планку задачи и тесты
  затронутых модулей», но планка этой задачи (`test_ac13_*`) сама
  запускает четыре чужих набора целиком — оценить время шага по числу
  «своих» тестов нельзя. Стоит назвать в скиле, что планка вправе быть
  дороже собственного модуля.
- Формат раздела «## Приложение» до этой задачи существовал только как
  практика (восемь разделов в `tasks/`), без единой строки в
  `templates/PLAN.md`. Класс «механика сложилась практикой, а носитель
  формата её не знает» стоит закрывать подсказкой в шаблоне в тот же
  момент, когда появляется разборщик, — иначе следующая роль напишет
  раздел наугад.
