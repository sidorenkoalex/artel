# PLAN: suite-run доступен роли на Codex (песочница workspace-write)

## Подход
Три правки в зоне SPEC; `acceptance.py`, `store.py`, `runner.py` не трогаются.

1. **Корень записи шага Codex.** `suite_lock.directory()` (`config.LOGS / "suite-run"`)
   — новый единый адрес каталога замка и хозяйства `suite-run`;
   `suite_lock.path()` и `suite_run._state_dir()` выводятся из него.
   `providers/codex.py::command` при заданном `docs_dir` (то есть в шаге)
   добавляет вторую пару `--add-dir <suite_lock.directory()>` после пары каталога
   документов и до `-m`. Каталог заводится там же (`mkdir`, сбой подавлен):
   из песочницы его не создать, потому что родитель `.artel/logs` роли закрыт.
   Без `docs_dir` команда прежняя (сторож «без каталога документов» не меняется).
   Claude не трогается.
2. **Логи прогона — внутрь хозяйства.** `suite_run._log_path` теперь возвращает
   `_task_dir(id) / "<id>-suiterun-<n>[-base].log"`. Номер прогона выдаёт
   `suite_run._new_log`, а не `agent_log.new_agent_log`, который создаёт
   файл в `config.LOGS`. Номер берётся следующим за наибольшим из логов каталога
   задачи и номеров `run.json`/`result.json`: после переноса логов номер не
   начинается с 1 заново, иначе `--wait` принял бы старый `result.json` №1 за
   отчёт нового №1. `background` заводит каталог лога сам: его зовут и в обход
   команды.
3. **Журнал без права записи в БД (требование 3).** Запись журнала делает узел
   пульта `acceptance._signal_near_limit`: он вне зоны и сбой записи уже
   перехватывает. Поэтому `suite_run.background` на время `_run` оборачивает
   `store.journal` (`_journal_deferred`): `sqlite3.Error` откладывает запись
   файлом в `suite_lock.directory()/pending-journal/` (`suite_lock.defer_journal`,
   с identity сессии роли и временем) и пробрасывается дальше. Вызывающий видит
   сбой как прежде, итог прогона не меняется. Досыл `suite_lock.deliver_journal()`:
   файл забирается переименованием (двойной досыл исключён), пишется в журнал своей
   задачи с пометкой «дослано процессом пульта». При отказе БД файл возвращается,
   а мусор и запись о неизвестной задаче убираются. Досыл зовут
   `suite_run.cmd_suite_run` (любой режим, в том числе `--wait` Оператора) и
   `suite_lock.wait_acquire` (гейты и `notes` перед полным прогоном).
   Если `store.db()` не открывается на запись, `suite_run._db()` переходит на
   соединение только для чтения: это риск WAL из «Материалов» SPEC. Команде и
   прогону из БД нужно только прочесть задачу.
4. **«Прогон уже идёт» сверяется с замком.** `suite_run._running` признаёт прогон
   идущим только тогда, когда замок держит его pid (`suite_lock.holder()`). Без
   этого AC-6 падал примерно в половине запусков. Если случайный порядок ставил
   «роль держит замок» первым, оставался `run.json` с живым чужим pid, и при
   замке гейта команда отвечала «уже идёт» с кодом 0, а не отказом с
   держателем. Тот же изъян бывает и в жизни: pid переиспользован.

## Шаги

   команде, `_running` со сверкой замка.

## Влияние на систему
- Песочница Codex расширена ровно на `config.LOGS / "suite-run"`. `config.LOGS`,
  `fullsuite-results`, `.artel/` и БД не открываются (AC-2). В открытом каталоге
  лежат замок (роль и так берёт его штатно), хозяйство `suite-run` и очередь
  отложенных записей. Подложенная ролью запись станет записью журнала её задачи
  с пометкой «дослано процессом пульта». На гейты и итоги approve она не
  влияет: эти ссылаются на `fullsuite-results`, а он закрыт.
- Замок, пределы (`project_profile.full_suite_limit`), `--sandbox workspace-write`,
  сторож главной копии не тронуты. Сбой записи журнала по-прежнему виден узлу
  пульта: обёртка исключение пробрасывает.
- Роль на Claude: argv и окружение прежние (AC-7). Для всех меняется только место
  лога `suite-run` (требование 4), а отчёт по-прежнему называет путь.
- Сменённое ожидание существующего метода одно, и оно объявлено в SPEC:
  `tests/test_docs_dir_layout.py::CommandWithoutDocsDirTest::test_add_dir_only_when_docs_dir_given_and_model_stays_last`
  (у codex: без всех пар `--add-dir` argv равен bare, значения пар — каталог
  документов и `config.LOGS / "suite-run"`). Помощник `launch` в
  `tests/test_suite_run.py` теперь подменяет `suite_run._new_log` вместо
  `agent_log.new_agent_log` (путь подмены). Утверждения
  `test_command_takes_lock_before_background_start` (`"run": 7`) не тронуты.
- Откат: revert одного merge-коммита. Логи прогонов, сделанных после мержа,
  останутся в `.artel/logs/suite-run/<id>/`. Прежний код их не читает, а `--wait`
  старого кода найдёт `run.json`/`result.json` на прежнем месте.

## Риски
- Живой Codex не проверен: тесты моделируют песочницу открытием БД `mode=ro`.
  Есть два неизвестных. Первое: открывает ли SQLite в WAL файл только на чтение
  внутри Seatbelt (для этого есть запасной путь `_db()`). Второе: принимает ли
  Codex `--add-dir` (для этого каталог заводится до шага). Проверка — первый
  шаг роли на Codex с `suite-run`.
- Прогон базы делает `git worktree add` в клоне: это запись в `.git` клона вне
  корней песочницы. Это в «Не входит» SPEC (зависание git в песочнице). Если
  `git worktree add` откажет, отчёт скажет «база не посчитана», и прогон ветки
  от этого не пострадает.
- Файл, забранный досылающим процессом, который упал до записи
  (`*.claimed`), повторно не досылается. Окно — между переименованием и
  записью в БД.
