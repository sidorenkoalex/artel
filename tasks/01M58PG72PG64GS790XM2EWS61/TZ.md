# G1а-2: компоненты проекта — проверки doctor (версии инструментов, карта путей CI, каталоги) и ключ кэша итога

## Факты

Вторая часть задачи G1а (01M58FNWBV25FF26E7AZ9Q9912), вынесенная при её делении (ANSWER-1 той задачи, п. 9; ответы 4, 6, 7-A). ADR-0026 (`docs/adr/0026-project-components-and-outcome-gates.md`), «Решение» п. 1, 4.

- G1а ввела схему `components:` в записи `targets.yaml` и функции `orchestrator/project_profile.py`: `components(target)` (компоненты в порядке записи; у `test_profile` — один `default`), `select_components(target, paths)`, `test_id`/`parse_test_id`; запись с несколькими компонентами даёт `profile_of` → UNREAD с признаком «несколько компонентов». Поля компонента разбираются: `tools` (отображение «имя → строка версии»), `paths`, `depends_on`, `paths_source` (`file`, `key`), `workdir`.
- `doctor` вызывает `targets.load`/проверку записи (`orchestrator/doctor/cli.py:93-94`) без перехвата `TargetsError`: корректная запись с двумя компонентами роняет всю команду `doctor` (SPEC-AUDIT G1а, п. 3 — вынесено сюда).
- `doctor` не проверяет версии инструментов проекта и согласованность `paths` с CI проекта (`orchestrator/doctor/project_checks.py`).
- Ключ кэша итога полного набора собственного раннера — `orchestrator/acceptance.py:2146` (`_own_suite_result_key(tree, profile, base)`): `tree` — `git write-tree` рабочего дерева (отслеживаемые файлы блокировки уже в нём); игнорируемый git файл блокировки ключ не меняет; объявленные `tools` в ключ не входят; корня рабочей копии у функции нет.
- Живой пример — sled: `.github/workflows/ci.yml:58-63`, переменные `BACKEND_RE`, `FRONTEND_RE` вида `^(a|b|c)`; `frontend/.nvmrc` — `22`; на машине пульта Node v22.23.3 (`/Users/al.sidorenko/.nvm/versions/node/v22.23.3/bin`).

## Требуется

1. `doctor` не падает на корректной записи с `components:`: ошибка проверки записи — строка `fail` с причиной, остальные проверки идут.
2. `doctor` для каждого компонента проекта с `components:` (у записей с `test_profile` новых строк нет):
   - (а) `tools`: для каждого инструмента — запуск `<инструмент> --version` с окружением компонента (`env.PATH`); требуемая версия — текст значения до первого пробела (пометка в скобках — комментарий); совпадение — по стольким числовым частям, сколько их в требуемой (`22` ↔ `v22.23.3` — да; `3.12` ↔ `3.12.4` — да; `3.12` ↔ `3.11.9` — нет); из вывода берётся первая подстрока `\d+(\.\d+)*`. Несовпадение — fail; инструмента нет — fail; сбой запуска или вывод без версии — skip с причиной;
   - (б) `paths_source`: значение переменной `key` в файле `file` клона проекта разбирается на множество альтернатив верхнего уровня (`^(a|b|c)` и `a|b|c` → `{a, b, c}`) и сравнивается с объединением альтернатив `paths` компонента и `paths` его `depends_on` вида `paths`/`files`; порядок не важен; расхождение — warn с обеими строками; строку, которую так не разобрать, или отсутствие файла/переменной — skip с причиной;
   - (в) `workdir` каждого компонента существует в клоне проекта — иначе fail.
3. Ключ кэша итога полного набора собственного раннера: отдельным элементом — суммы файлов блокировки в `workdir` (`uv.lock`, `package-lock.json`, `poetry.lock`, `yarn.lock`, `pnpm-lock.yaml` — какие есть; из объекта дерева, а для неотслеживаемого или игнорируемого — из рабочей копии задачи) и объявленные `tools` компонента. У `Profile` — необязательное поле `tools` (пустое у записей с `test_profile`). У артели (`pult-pytest`) ключ прежний.
4. У записей с `test_profile` (артель, sled сегодня) — исходы и тексты `doctor` и ключ кэша прежние; зафиксировать тестами до правки.
5. Тесты детерминированы, без сети: подмена запуска инструментов; учебный клон с CI-файлом (`BACKEND_RE`, `FRONTEND_RE`); учебная запись с двумя компонентами.

Критерии приёмки:
- `doctor` на корректной записи с двумя компонентами завершается и печатает строки проверок; запись с ошибкой — строка `fail`, команда не падает;
- `tools`: `22` при выводе `v22.23.3` — ok; `v20.15.1` — fail; инструмента нет — fail; `3.12` при `Python 3.11.9` — fail; вывод без версии — skip;
- `paths_source`: совпадение множеств при ином порядке — ok; лишняя или недостающая альтернатива — warn с обеими строками; неразбираемая строка — skip;
- нет `workdir` в клоне — fail;
- смена игнорируемого файла блокировки при том же `tree` меняет ключ; смена `tools` меняет ключ; у артели ключ прежний.

Зоны: `orchestrator/doctor/project_checks.py`, `orchestrator/doctor/cli.py`, `orchestrator/acceptance.py` (только `_own_suite_result_key` и его вызов), `orchestrator/project_profile.py` (только поле `tools` у `Profile`), `tests/`.

Только чтение: `targets.yaml`, `.github/workflows/ci.yml` (sled, пример), `orchestrator/targets.py`, `orchestrator/repo_context.py`, `orchestrator/yamlmini.py`, `docs/adr/0026-project-components-and-outcome-gates.md`, `docs/backlog.md`. Правка вне зон — эскалация до SPEC.

Не входит: исполнение прогонов по компонентам, отчёт, окружение Vitest, установка зависимостей пультом (G1б); перевод записи sled (этап 2 плана).
