# SPEC: G1а-2: компоненты проекта — проверки doctor (версии инструментов, карта путей CI, каталоги) и ключ кэша итога

## Контекст
Вторая часть задачи G1а (01M58FNWBV25FF26E7AZ9Q9912), вынесенная при её
делении (ANSWER-1 той задачи, п. 9; ответы 4, 6, 7-A); ADR-0026, «Решение»
п. 1, 4. G1а ввела схему `components:` в записи `targets.yaml` и функции

`test_id`/`parse_test_id`). Сейчас корректная запись с двумя компонентами
роняет всю команду `doctor`: `full_suite_timeout_check`

2, 4-6) и ANSWER-2 этой задачи (ответ 1 пересматривает ответы 1 и 3
ANSWER-1; ответы 2-4 — вариант A).

## Требования
1. `doctor` не падает на записи `targets.yaml` с `components:`. У записи,
   которая проходит `targets.load`, но роняет проверку записи (например,
   единственный компонент без обязательного подполя профиля), строка
   `full-suite-timeout-<имя>` — `fail` с причиной; строки проверок этой и
   остальных записей печатаются. У корректной записи с несколькими
   компонентами строка `full-suite-timeout-<имя>` — `skip` с причиной
   `targets.MULTI_COMPONENT_PENDING` (ANSWER-1, ответ 4).
2. Новые строки `doctor` по компонентам (ANSWER-2, ответ 3) — в блоке записи
   проекта, рядом с `project_entry_checks` (cli.py:101), по образцу имён
   `project-<вид>-<проект>` (project_checks.py:26-29):
   `project-tools-<проект>-<компонент>-<инструмент>` — строка на каждый
   инструмент; `project-paths-<проект>-<компонент>` — строка на компонент с
   `paths_source`; `project-workdir-<проект>-<компонент>` — строка на
   компонент с `workdir`.
3. Проверка `tools` (строка `project-tools-…`): для каждого инструмента
   компонента — запуск `<инструмент> --version`. `PATH` запуска —
   `env.PATH` компонента, если задан, иначе `PATH` процесса `doctor`
   (ANSWER-1, ответ 6а); наличие инструмента определяется по тому же
   `PATH`. Запуск — через `doctor.subprocess.run`, наличие —
   `doctor.shutil.which` (тот же шов, что у проверок `gh`,
   project_checks.py:182-191); таймаут — как у прочих вызовов `doctor`,
   истечение — сбой запуска (ANSWER-2, ответ 4). Требуемая версия — текст
   значения до первого пробела (пометка после него — комментарий). Версия
   ищется в stdout, при её отсутствии там — в stderr: берётся первая
   подстрока `\d+(\.\d+)*`. Совпадение — по стольким числовым частям,
   сколько их в требуемой версии, сравниваются числа частей, не префикс
   строки (`22` ↔ `v22.23.3` — да; `3.12` ↔ `3.12.4` — да; `3.12` ↔
   `3.11.9` — нет; `3.1` ↔ `3.12.0` — нет; `2` ↔ `22.1` — нет). Исходы:
   совпадение — ok; несовпадение — fail; инструмента нет — fail; сбой
   запуска, ненулевой код выхода `--version` (причина называет код;
   ANSWER-1, ответ 6б) или вывод без версии в обоих потоках — skip с
   причиной.
4. Проверка `paths_source` (строка `project-paths-…`): значение переменной
   `key` в файле `file` клона проекта разбирается на множество альтернатив
   верхнего уровня и сравнивается с объединением альтернатив `paths`
   компонента и `paths` его записей `depends_on` с `via` `paths` или
   `files`; порядок не важен. Совпадение — ok; расхождение — warn, в тексте
   обе сравниваемые строки; строка значения, которую не разобрать,
   отсутствие файла или переменной — skip с причиной.
5. Правило разбора одной строки регулярного выражения (ANSWER-2, ответ 2):
   снимается один ведущий `^`; если остаток целиком — одна группа `(…)` со
   сбалансированными скобками (закрывающая скобка группы — последний
   символ), делится её содержимое, иначе — весь остаток; деление — по `|`
   верхнего уровня (`|` внутри скобок `()`/`[]` и после `\` не делит).
   `^(a|b(c|d))` → `{a, b(c|d)}`; `^(a|b|c)` и `a|b|c` → `{a, b, c}`.
   Неразбираемая строка: пустое значение, несбалансированные скобки, пустая
   альтернатива (`a||b`, `(a|)`), хвост после ведущей группы (`^(a|b)c`).
   `paths` компонента и `paths` его `depends_on` — строка или список строк;
   каждая строка разбирается тем же правилом, множества объединяются;
   неразбираемая строка в `paths` — тоже skip, причина называет эту строку.
6. Переменная `key` в файле `file` ищется в формах (ANSWER-1, ответ 5):
   - ключ YAML `KEY: значение` с отступом или без; значение в одинарных
     или двойных кавычках — без кавычек, без кавычек — как есть;
   - ключ YAML с блоком `>-`, `>`, `|-`, `|`: значение — строки со
     следующей строки с отступом больше отступа ключа, по правилам YAML
     (у `>`/`>-` строки склеиваются пробелом); блок из одной строки
     сравнивается как обычное значение; блок из нескольких строк — skip с
     причиной «многострочное значение не сравнивается»;
   - присваивание оболочки `KEY=значение`, допустимо с `export` впереди;
     кавычки снимаются так же.
   Строки-комментарии (`#` первым непробельным символом) при поиске
   пропускаются.
7. Проверка `workdir` (строка `project-workdir-…`): каталог `workdir`
   компонента существует в клоне проекта; нет — fail. Компонент без
   `workdir` строки `project-workdir-…` не получает (ANSWER-1, ответ 6в).
8. У записей с `test_profile` новых строк `doctor` нет.
9. `Profile` (`orchestrator/project_profile.py`) получает необязательное
   поле `tools` — объявленные инструменты компонента; у записей с
   `test_profile` оно пустое. Заполняет его один помощник `project_profile`,
   берущий `tools` единственного компонента записи с одним компонентом из
   `components(target)`; его вызывают `decide` (`project_profile.py`) и
   `_task_own_profile` (`orchestrator/acceptance.py`). `repo_context.py` и
   `suite_run.py` не меняются (ANSWER-2, ответ 1).
10. Ключ кэша итога полного набора собственного раннера, ключ рабочего
    дерева (`base=False`; автогейт приёмки и гейт мержа), при непустых
    `Profile.tools` включает отдельным элементом объявленные `tools` и
    суммы файлов блокировки в `workdir` (`uv.lock`, `package-lock.json`,
    `poetry.lock`, `yarn.lock`, `pnpm-lock.yaml` — какие есть):
    отслеживаемый — из объекта дерева, игнорируемый git — из рабочей копии
    задачи (ANSWER-1, ответ 2; ANSWER-2, ответ 1).
11. Ключ базы (`base=True`) — прежний при любых `tools`: без `tools` и без
    сумм файлов блокировки; он одинаков у гейта мержа (сохранение,
    acceptance.py:2318-2322, профиль из `decide`) и у `suite-run` (поиск,
    suite_run.py:521-524, профиль из `_profile_command`) (ANSWER-2, ответ 1;
    ответ 3 ANSWER-1 отменён).
12. При пустых `Profile.tools` ключ кэша итога (обоих видов) — прежний, байт
    в байт: у записей с `test_profile` (артель — `pult-pytest`; sled
    сегодня — `pytest-own` с `workdir: backend`), в том числе при смене
    игнорируемого файла блокировки в `workdir`. Исходы и тексты строк
    `doctor` у записей с `test_profile` прежние. Прежние ключ и строки
    фиксируются тестами до правки кода.
13. Тесты детерминированы и без сети: запуск инструментов подменяется
    (`doctor.subprocess.run`/`doctor.shutil.which` либо учебный исполняемый
    файл в каталоге `env.PATH` компонента); учебный клон с CI-файлом в форме
    sled (`.github/workflows/ci.yml:59-64` sled: внутри `env:` ключ
    `BACKEND_RE: '…'` в одинарных кавычках и `FRONTEND_RE: >-` со значением
    одной строкой на следующей строке с большим отступом), учебный
    многострочный блок, учебное присваивание оболочки; учебная запись с
    двумя компонентами.

## Критерии приёмки
AC-1. `doctor` на корректной учебной записи с двумя компонентами
завершается без исключения и печатает строки проверок этой записи, в том
числе `project-tools-<проект>-<компонент>-<инструмент>` на каждый
инструмент, `project-paths-<проект>-<компонент>` на компонент с
`paths_source`, `project-workdir-<проект>-<компонент>` на компонент с
`workdir`; строка `full-suite-timeout-<имя>` этой записи — `skip` с
причиной `targets.MULTI_COMPONENT_PENDING`.

AC-2. Учебная запись, проходящая `targets.load`, но с единственным
компонентом без обязательного подполя профиля: строка
`full-suite-timeout-<имя>` — `fail` с причиной; команда не падает; строки
проверок другой записи того же `targets.yaml` напечатаны.

AC-3. Проверка `tools`: требуемая `22` при выводе `v22.23.3` — ok; при
выводе `v20.15.1` — fail; требуемая `3.12` при выводе `Python 3.11.9` —
fail, при `Python 3.12.4` — ok; требуемая `3.1` при выводе `3.12.0` —
fail; требуемая `2` при выводе `22.1` — fail; пометка после пробела в
значении версии на исход не влияет.

AC-4. Проверка `tools`: запуск идёт с `PATH` из `env.PATH` компонента, а у
компонента без `env.PATH` — с `PATH` процесса `doctor`. Наличие инструмента
определяется по `env.PATH` компонента: инструмент, который есть в `PATH`
процесса `doctor`, но отсутствует в каталогах `env.PATH` компонента, —
строка `project-tools-…` fail.

AC-5. Проверка `tools`: инструмента нет — fail (в том числе случай AC-4:
инструмент есть только в `PATH` процесса, но не в `env.PATH` компонента);
вывод без версии в stdout и stderr — skip с причиной; версия только в
stderr — сравнивается (`22` при stderr `v22.23.3` и пустом stdout — ok);
сбой запуска — skip с причиной; истечение таймаута `--version` — skip с
причиной, команда `doctor` не падает и печатает строки остальных проверок;
ненулевой код выхода `--version` — skip, причина называет код.

AC-6. Проверка `paths_source` на учебном клоне в форме sled (`BACKEND_RE`
в одинарных кавычках, `FRONTEND_RE` блоком `>-` с одной строкой): для
каждой из двух переменных множества альтернатив и `paths` компонента (с
`paths` его `depends_on` вида `paths`/`files`) совпадают при ином порядке —
ok. Запись `depends_on` вида `contract` в сравнении не участвует: её
`paths` в объединение не входят (при её `paths`, отсутствующих в значении
переменной, исход — ok, не warn).

AC-7. Проверка `paths_source`: присваивание оболочки `KEY='…'` и
`export KEY=…` находится и сравнивается; строка-комментарий `# KEY: …`
значением не считается.

AC-8. Проверка `paths_source`: лишняя или недостающая альтернатива — warn,
текст содержит обе сравниваемые строки; отсутствие файла или переменной —
skip с причиной; блок из нескольких строк — skip с причиной «многострочное
значение не сравнивается».

AC-9. Разбор строки: значение `^(a|b(c|d))` даёт множество `{a, b(c|d)}`
(при `paths` компонента `a` и `b(c|d)` — ok; деление по каждому `|` даёт
warn и тест его ловит); `^(a|b|c)` и `a|b|c` дают `{a, b, c}`; `paths`
компонента списком строк объединяется с `paths` его `depends_on`.

AC-10. Неразбираемая строка значения — skip с причиной для каждого из
случаев: пустое значение, несбалансированные скобки, пустая альтернатива
(`a||b`), хвост после ведущей группы (`^(a|b)c`); неразбираемая строка в
`paths` компонента — skip, причина называет эту строку.

AC-11. Компонент, чьего `workdir` нет в клоне проекта, — строка
`project-workdir-…` fail; компонент без `workdir` строки
`project-workdir-…` не получает.

AC-12. `decide` для учебной записи с одним компонентом с `tools` даёт
`Profile` с этими `tools`; `_task_own_profile` для той же записи — тоже;
для записи с `test_profile` оба дают `Profile` с пустыми `tools`.

AC-13. Ключ рабочего дерева (`base=False`) через реальные входы: для
учебной записи с одним компонентом с `tools` профиль `_task_own_profile` и
профиль `decide` дают одинаковый ключ; смена объявленных `tools` меняет
ключ; смена игнорируемого git файла блокировки в `workdir` при том же
`tree` меняет ключ.

AC-14. Ключ базы (`base=True`) для той же записи: профиль `decide` и
профиль `suite_run._profile_command` дают одинаковый ключ; смена `tools` и
смена игнорируемого файла блокировки ключ базы не меняют.

AC-15. При пустых `tools` ключ кэша итога прежний: у артели
(`pult-pytest`) и у профиля вида sled (`pytest-own`, `workdir`) значение
ключа (обоих видов, `base=False` и `base=True`) равно значению до правки, в
том числе при смене игнорируемого файла блокировки в `workdir`. У записей
с `test_profile` набор, исходы и тексты строк `doctor` прежние — строк
`project-tools-…`/`project-paths-…`/`project-workdir-…` нет.
