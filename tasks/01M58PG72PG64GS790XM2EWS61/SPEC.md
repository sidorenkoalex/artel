# SPEC: G1а-2: компоненты проекта — проверки doctor (версии инструментов, карта путей CI, каталоги) и ключ кэша итога

## Контекст
Вторая часть задачи G1а (01M58FNWBV25FF26E7AZ9Q9912), вынесенная при её
делении (ANSWER-1 той задачи, п. 9; ответы 4, 6, 7-A); ADR-0026, «Решение»
п. 1, 4. G1а ввела схему `components:` в записи `targets.yaml` и функции
`orchestrator/project_profile.py` (`components`, `select_components`,
`test_id`/`parse_test_id`). Сейчас корректная запись с двумя компонентами
роняет всю команду `doctor`: `full_suite_timeout_check`
(`orchestrator/doctor/cli.py:13-20`, вызов cli.py:94) → `full_suite_limit`
(project_profile.py:184-188) поднимает `TargetsError` на UNREAD `multi`.
`doctor` не проверяет версии инструментов компонента, согласованность его
`paths` с CI проекта и наличие `workdir`. Ключ кэша итога полного набора
собственного раннера (`orchestrator/acceptance.py::_own_suite_result_key`,
acceptance.py:2150) не видит игнорируемых git файлов блокировки и
объявленных `tools`. Решения по неясным местам ТЗ — ANSWER-1 этой задачи
(ответы 1-6, все — вариант A, ответ 5 дополнен по живому файлу sled).

## Требования
1. `doctor` не падает на записи `targets.yaml` с `components:`. У записи,
   которая проходит `targets.load`, но роняет проверку записи (например,
   единственный компонент без обязательного подполя профиля), строка
   `full-suite-timeout-<имя>` — `fail` с причиной; строки проверок этой и
   остальных записей печатаются. У корректной записи с несколькими
   компонентами строка `full-suite-timeout-<имя>` — `skip` с причиной
   `targets.MULTI_COMPONENT_PENDING` (ANSWER-1, ответ 4).
2. Для каждого компонента записи с `components:` `doctor` выдаёт проверку
   `tools`: для каждого инструмента компонента — запуск
   `<инструмент> --version`. `PATH` запуска — `env.PATH` компонента, если
   задан, иначе `PATH` процесса `doctor` (ANSWER-1, ответ 6а). Требуемая
   версия — текст значения до первого пробела (пометка после него —
   комментарий). Из вывода берётся первая подстрока `\d+(\.\d+)*`.
   Совпадение — по стольким числовым частям, сколько их в требуемой версии
   (`22` ↔ `v22.23.3` — да; `3.12` ↔ `3.12.4` — да; `3.12` ↔ `3.11.9` —
   нет). Исходы: совпадение — ok; несовпадение — fail; инструмента нет —
   fail; сбой запуска, ненулевой код выхода `--version` (причина называет
   код; ANSWER-1, ответ 6б) или вывод без версии — skip с причиной.
3. Для каждого компонента с `paths_source` `doctor` выдаёт проверку: значение
   переменной `key` в файле `file` клона проекта разбирается на множество
   альтернатив верхнего уровня (`^(a|b|c)` и `a|b|c` → `{a, b, c}`) и
   сравнивается с объединением альтернатив `paths` компонента и `paths`
   его записей `depends_on` с `via` `paths` или `files`; порядок не важен.
   Совпадение — ok; расхождение — warn, в тексте обе строки; строка,
   которую так не разобрать, отсутствие файла или переменной — skip с
   причиной.
4. Переменная `key` в файле `file` ищется в формах (ANSWER-1, ответ 5):
   - ключ YAML `KEY: значение` с отступом или без; значение в одинарных
     или двойных кавычках — без кавычек, без кавычек — как есть;
   - ключ YAML с блоком `>-`, `>`, `|-`, `|`: значение — строки со
     следующей строки с отступом больше отступа ключа, по правилам YAML
     (у `>`/`>-` строки склеиваются пробелом); блок из одной строки
     сравнивается как обычное значение; блок из нескольких строк — skip с
     причиной «многострочное значение не сравнивается»;
   - присваивание оболочки `KEY=значение`, допустимо с `export` впереди;
     кавычки снимаются так же.
   Строки-комментарии (`#` первым непробельным символом) при поиске
   пропускаются.
5. Для каждого компонента с `workdir` `doctor` проверяет, что этот каталог
   существует в клоне проекта; нет — fail. Компонент без `workdir` строки
   проверки `workdir` не получает (ANSWER-1, ответ 6в).
6. У записей с `test_profile` новых строк `doctor` нет.
7. `Profile` (`orchestrator/project_profile.py`) получает необязательное
   поле `tools` — объявленные инструменты компонента; у записей с
   `test_profile` оно пустое. `decide` заполняет его из `tools`
   единственного компонента записи с одним компонентом (`components(target)`
   того же модуля); `orchestrator/repo_context.py` не меняется (ANSWER-1,
   ответ 1).
8. Ключ кэша итога полного набора собственного раннера
   (`_own_suite_result_key`) при непустых `Profile.tools` включает
   отдельным элементом объявленные `tools` и, для ключа рабочего дерева
   (`base=False`), суммы файлов блокировки в `workdir` (`uv.lock`,
   `package-lock.json`, `poetry.lock`, `yarn.lock`, `pnpm-lock.yaml` —
   какие есть): отслеживаемый — из объекта дерева, игнорируемый git — из
   рабочей копии задачи (ANSWER-1, ответы 2, 3). Ключ базы (`base=True`)
   при непустых `tools` включает только `tools`, без сумм файлов
   блокировки; оба места ключа базы (сохранение гейтом,
   acceptance.py:2318-2322, и поиск `suite-run`, suite_run.py:521-524)
   считают его одинаково.
9. При пустых `Profile.tools` ключ кэша итога — прежний, байт в байт: у
   записей с `test_profile` (артель — `pult-pytest`; sled сегодня —
   `pytest-own` с `workdir: backend`), в том числе при смене игнорируемого
   файла блокировки в `workdir`. Исходы и тексты строк `doctor` у записей
   с `test_profile` прежние. Прежние ключ и строки фиксируются тестами до
   правки кода.
10. Тесты детерминированы и без сети: запуск инструментов подменяется;
    учебный клон с CI-файлом в форме sled (`.github/workflows/ci.yml:59-64`
    sled: внутри `env:` ключ `BACKEND_RE: '…'` в одинарных кавычках и
    `FRONTEND_RE: >-` со значением одной строкой на следующей строке с
    большим отступом), учебный многострочный блок, учебное присваивание
    оболочки; учебная запись с двумя компонентами.

## Критерии приёмки
AC-1. `doctor` на корректной учебной записи с двумя компонентами
завершается без исключения и печатает строки проверок этой записи;
строка `full-suite-timeout-<имя>` этой записи — `skip` с причиной
`targets.MULTI_COMPONENT_PENDING`.

AC-2. Учебная запись, проходящая `targets.load`, но с единственным
компонентом без обязательного подполя профиля: строка
`full-suite-timeout-<имя>` — `fail` с причиной; команда не падает; строки
проверок другой записи того же `targets.yaml` напечатаны.

AC-3. Проверка `tools`: требуемая `22` при выводе `v22.23.3` — ok; при
выводе `v20.15.1` — fail; требуемая `3.12` при выводе `Python 3.11.9` —
fail, при `Python 3.12.4` — ok; пометка после пробела в значении версии на
исход не влияет.

AC-4. Проверка `tools`: запуск идёт с `PATH` из `env.PATH` компонента, а у
компонента без `env.PATH` — с `PATH` процесса `doctor`.

AC-5. Проверка `tools`: инструмента нет — fail; вывод без версии — skip с
причиной; сбой запуска — skip с причиной; ненулевой код выхода `--version`
— skip, причина называет код.

AC-6. Проверка `paths_source` на учебном клоне в форме sled (`BACKEND_RE`
в одинарных кавычках, `FRONTEND_RE` блоком `>-` с одной строкой): для
каждой из двух переменных множества альтернатив и `paths` компонента (с
`paths` его `depends_on` вида `paths`/`files`) совпадают при ином порядке —
ok.

AC-7. Проверка `paths_source`: присваивание оболочки `KEY='…'` и
`export KEY=…` находится и сравнивается; строка-комментарий `# KEY: …`
значением не считается.

AC-8. Проверка `paths_source`: лишняя или недостающая альтернатива — warn,
текст содержит обе сравниваемые строки; неразбираемая строка значения,
отсутствие файла или переменной — skip с причиной; блок из нескольких
строк — skip с причиной «многострочное значение не сравнивается».

AC-9. Компонент, чьего `workdir` нет в клоне проекта, — строка fail;
компонент без `workdir` строки проверки `workdir` не получает.

AC-10. `decide` для учебной записи с одним компонентом с `tools` даёт
`Profile` с этими `tools`; для записи с `test_profile` — `Profile` с
пустыми `tools`.

AC-11. Ключ кэша итога (`base=False`) для `Profile` из записи с одним
компонентом с `tools` (полученного через `decide`): смена игнорируемого git
файла блокировки в `workdir` при том же `tree` меняет ключ; смена
объявленных `tools` меняет ключ.

AC-12. Ключ базы (`base=True`) при непустых `tools`: смена `tools` меняет
ключ; смена игнорируемого файла блокировки ключ не меняет; ключ,
сохранённый гейтом, и ключ, по которому ищет `suite-run`, для одного
коммита и профиля совпадают.

AC-13. При пустых `tools` ключ кэша итога прежний: у артели
(`pult-pytest`) и у профиля вида sled (`pytest-own`, `workdir`) значение
ключа (обоих видов, `base=False` и `base=True`) равно значению до правки, в
том числе при смене игнорируемого файла блокировки в `workdir`.

AC-14. У записей с `test_profile` набор, исходы и тексты строк `doctor`
прежние — новых строк проверок компонентов нет.

  зависимостей пультом (G1б).
- Ключ кэша и `Profile` записи с несколькими компонентами: `Profile` у неё
  нет (UNREAD `multi`, repo_context.py:161-163) — G1б.

  `Profile.tools`) смена игнорируемого файла блокировки ключ не меняет —
  как сегодня у всех записей; закрывается переводом записей и G1б.

  «Неотслеживаемый» файл блокировки отдельным случаем не рассматривается:
  при неотслеживаемом файле вне `tasks/` ключа нет вовсе
  (acceptance.py:2041-2048).
- Перевод записи sled на `components:` (этап 2 плана).
- Правка вне зон: `targets.yaml`, `.github/workflows/ci.yml` (sled),
  `orchestrator/targets.py`, `orchestrator/repo_context.py`,
  `orchestrator/yamlmini.py`, `orchestrator/suite_run.py`,
  `docs/adr/0026-…`, `docs/backlog.md` — только чтение; потребность в их
  правке — эскалация.
- В `orchestrator/acceptance.py` меняются только `_own_suite_result_key` и
  цепочка его вызова; в `orchestrator/project_profile.py` — только поле
  `tools` у `Profile` и его заполнение в `decide`.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность
  защищённых путей, непревышение бюджета — их держит пульт.
