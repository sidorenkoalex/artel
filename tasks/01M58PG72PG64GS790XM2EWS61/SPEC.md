# SPEC: G1а-2: компоненты проекта — проверки doctor (версии инструментов, карта путей CI, каталоги) и ключ кэша итога

## Контекст
Вторая часть задачи G1а (01M58FNWBV25FF26E7AZ9Q9912), вынесенная при её
делении (ANSWER-1 той задачи, п. 9; ответы 4, 6, 7-A); ADR-0026, «Решение»
п. 1, 4. G1а ввела схему `components:` в записи `targets.yaml` и функции
`orchestrator/project_profile.py` (`components`, `select_components`,
`test_id`/`parse_test_id`). Сейчас корректная запись с двумя компонентами
роняет всю команду `doctor` (SPEC-AUDIT G1а, п. 3); `doctor` не проверяет
версии инструментов компонента, согласованность его `paths` с CI проекта и
наличие `workdir`. Ключ кэша итога полного набора собственного раннера
(`orchestrator/acceptance.py::_own_suite_result_key`) не видит
игнорируемых git файлов блокировки и объявленных `tools`.

## Требования
1. `doctor` не падает на корректной записи с `components:`: ошибка
   проверки записи проекта — строка `fail` с причиной, остальные проверки
   `doctor` выполняются.
2. Для каждого компонента записи с `components:` `doctor` выдаёт проверку
   `tools`: для каждого инструмента компонента — запуск
   `<инструмент> --version` с окружением компонента (`env.PATH`).
   Требуемая версия — текст значения до первого пробела (пометка в скобках
   после него — комментарий). Из вывода берётся первая подстрока
   `\d+(\.\d+)*`. Совпадение — по стольким числовым частям, сколько их в
   требуемой версии (`22` ↔ `v22.23.3` — да; `3.12` ↔ `3.12.4` — да;
   `3.12` ↔ `3.11.9` — нет). Исходы: совпадение — ok; несовпадение —
   fail; инструмента нет — fail; сбой запуска или вывод без версии — skip
   с причиной.
3. Для каждого компонента с `paths_source` `doctor` выдаёт проверку: значение
   переменной `key` в файле `file` клона проекта разбирается на множество
   альтернатив верхнего уровня (`^(a|b|c)` и `a|b|c` → `{a, b, c}`) и
   сравнивается с объединением альтернатив `paths` компонента и `paths`
   его записей `depends_on` с `via` `paths` или `files`; порядок не важен.
   Совпадение — ok; расхождение — warn, в тексте обе строки; строка,
   которую так не разобрать, отсутствие файла или переменной — skip с
   причиной.
4. Для каждого компонента `doctor` проверяет, что его `workdir` существует
   в клоне проекта; нет — fail.
5. У записей с `test_profile` новых строк `doctor` нет.
6. `Profile` (`orchestrator/project_profile.py`) получает необязательное
   поле `tools` — объявленные инструменты компонента; у записей с
   `test_profile` оно пустое.
7. Ключ кэша итога полного набора собственного раннера для профиля из
   записи с `components:` включает отдельным элементом суммы файлов
   блокировки в `workdir` (`uv.lock`, `package-lock.json`, `poetry.lock`,
   `yarn.lock`, `pnpm-lock.yaml` — какие есть; отслеживаемый — из объекта
   дерева, неотслеживаемый или игнорируемый — из рабочей копии задачи) и
   объявленные `tools` компонента.
8. У записей с `test_profile` (артель — `pult-pytest`; sled сегодня —
   `pytest-own` с `workdir: backend`) исходы и тексты `doctor` и ключ кэша
   итога прежние, байт в байт; это фиксируется тестами до правки кода.
9. Тесты детерминированы и без сети: запуск инструментов подменяется;
   учебный клон с CI-файлом (переменные `BACKEND_RE`, `FRONTEND_RE` вида
   `^(a|b|c)`, как `.github/workflows/ci.yml:58-63` sled); учебная запись с
   двумя компонентами.

## Критерии приёмки
AC-1. `doctor` на корректной учебной записи с двумя компонентами
завершается без исключения и печатает строки проверок; на записи с ошибкой
проверки — строка `fail` с причиной, команда не падает, остальные проверки
напечатаны.

AC-2. Проверка `tools`: требуемая `22` при выводе `v22.23.3` — ok; при
выводе `v20.15.1` — fail; требуемая `3.12` при выводе `Python 3.11.9` —
fail, при `Python 3.12.4` — ok; пометка после пробела в значении версии на
исход не влияет; запуск идёт с `PATH` из `env` компонента.

AC-3. Проверка `tools`: инструмента нет — fail; вывод без версии — skip с
причиной; сбой запуска — skip с причиной.

AC-4. Проверка `paths_source` на учебном клоне: множества альтернатив
переменной CI и `paths` компонента (с `paths` его `depends_on` вида
`paths`/`files`) совпадают при ином порядке — ok.

AC-5. Проверка `paths_source`: лишняя или недостающая альтернатива — warn,
текст содержит обе сравниваемые строки; неразбираемая строка значения,
отсутствие файла или переменной — skip с причиной.

AC-6. Компонент, чьего `workdir` нет в клоне проекта, — строка fail.

AC-7. Ключ кэша итога для профиля из записи с `components:`: смена
игнорируемого git файла блокировки в `workdir` при том же `tree` меняет
ключ; смена объявленных `tools` меняет ключ.

AC-8. У записей с `test_profile` ключ кэша итога прежний: у артели
(`pult-pytest`) и у профиля вида sled (`pytest-own`, `workdir`) значение
ключа равно значению до правки, в том числе при смене игнорируемого файла
блокировки в `workdir`.

AC-9. У записей с `test_profile` набор, исходы и тексты строк `doctor`
прежние — новых строк проверок компонентов нет.

## Оценка объёма и деление
Сработал сигнал: число файлов зоны — 5 (`tests/` — общая зона, в
калибровке бюджета не считается: кодовых файлов 4). Прогноз диффа: 60 КиБ
(четыре кодовых файла в пределах названных функций плюс тесты с учебным
клоном и учебной записью) — ниже половины потолка гейта ёмкости
(256 КиБ). Критериев приёмки 9, бюджет $30 — ниже порогов.

Материал для решения — обоснование монолита: задача уже вынесена делением
G1а (ANSWER-1 той задачи, п. 9) с рамкой $30. Технически части «проверки
doctor» (требования 1-5, зоны `orchestrator/doctor/`) и «ключ кэша»
(требования 6-8, зоны `orchestrator/acceptance.py`,
`orchestrator/project_profile.py`) мержимы раздельно, но обе опираются на
одну учебную запись с двумя компонентами и одну фиксацию прежнего
поведения записей с `test_profile` (требование 8); дальнейшее деление
удваивает шаги аналитика, аудита и автора тестов при объёме каждой части
меньше нижнего класса калибровки. Решение — за Оператором на гейте SPEC.
