Подтвердилось:

Других читателей профиля в `orchestrator/doctor/` нет (grep `profile_of|full_suite_limit|components(`). Значит, правка в зоне `cli.py` закрывает тр. 1.
- `orchestrator/acceptance.py:2107-2168` — `suite_result_key` и `_own_suite_result_key` (def на 2150, а не на 2146, как в ТЗ; диапазон SPEC 2107-2164 обрезает конец функции на 2168 — неточность без последствий). В ключе нет корня рабочей копии и `tools`: подтверждено.
- `orchestrator/targets.py:84-115` — поля компонента, `COMPONENT_DEPENDS_VIA` (targets.py:108), `COMPONENT_PATHS_SOURCE` (targets.py:109), форма `tools` (targets.py:482-489), `depends_on` (targets.py:547-572): подтверждено.
- `orchestrator/repo_context.py:142-172` — `profile_of`: подтверждено.
- `orchestrator/suite_run.py:523` — вызов ключа базы: подтверждено.
- sled: `targets.yaml:81-84` — `test_profile`, `runner: pytest-own`, `workdir: backend`: подтверждено. `frontend/.nvmrc` и `.github/workflows/ci.yml:58-63` sled не сверены: клон `.artel/projects/sled/repo` закрыт роли на чтение.

Не подтвердилось или не учтено SPEC:
- **Ф1. `tools` в `Profile` записи с `components:` взять неоткуда в зонах.** `Profile.from_values` (project_profile.py:86-99) строится из `answer.values` функции `repo_context.profile_of`, а она отбирает только `targets.PROFILE_FIELDS` (repo_context.py:171-172). `tools` в `PROFILE_FIELDS` нет (targets.py:44-59; `tools` есть только в `COMPONENT_FIELDS`, targets.py:103). Есть два способа передать `tools` в `Profile`, и оба выходят за зоны: правка `repo_context.profile_of` (по ТЗ и SPEC — только чтение) или правка `project_profile.decide` (project_profile.py:143-151), которая шире «только поле `tools` у `Profile`». Для записи с несколькими компонентами `profile_of` отдаёт UNREAD (repo_context.py:161-163), и `Profile` нет вовсе. То есть тр. 7 сегодня достижимо только для записи с одним компонентом, а SPEC этого не говорит.
- **Ф2. Профиль «из записи с `components:`» неотличим от профиля `test_profile`.** Тр. 7 добавляет суммы блокировок только профилю из записи с `components:`. Тр. 8 и AC-8 требуют, чтобы у `pytest-own` с `workdir` (вид sled) ключ не менялся «в том числе при смене игнорируемого файла блокировки». Но `_own_suite_result_key` получает только `Profile` (acceptance.py:2150), а долгоживущий тест `tests/test_01m58fnwbv25ff26e7az9q9912_components.py:657-694` требует, чтобы `Profile` единственного компонента был РАВЕН `Profile` записи `test_profile` с теми же подполями (строка 694). Признак происхождения в `Profile` либо ломает это равенство, либо вводится полем с `compare=False` — это обход смысла теста. Единственный различитель в рамках SPEC — непустые `tools`. Тогда компонент без `tools` не получит сумм блокировок, и тр. 7 будет выполнено лишь частично (см. «Пути обхода», О2).
- **Ф3. Ключ базы.** Ключ базы считают два места, и они обязаны совпадать: `acceptance.py:2318-2322` сохраняет итог `base`, `suite_run.py:521-524` ищет его (дерево коммита, `worktree=False`, корня рабочей копии нет). Тр. 7 не говорит, входят ли суммы блокировок в ключ при `base=True`. Если входят из рабочей копии, ключи двух мест расходятся, и `suite-run` молча перестаёт находить сохранённый итог базы. Само место `suite_run.py:523` SPEC объявил неизменяемым.
- **Ф4.** «Неотслеживаемый — из рабочей копии» для ключа гейта недостижимо: `suite_tree_hash` возвращает `None` при любом неотслеживаемом неигнорируемом файле вне `tasks/` (acceptance.py:2041-2048), и ключа нет. Реальный случай — только игнорируемый файл. Это неточность формулировки, не блокер.

## Пути обхода гейтов
- **О1.** `tools` добавлено в `Profile`, но нигде не заполняется из `targets.yaml` (Ф1). AC-7, проверенный на `Profile(tools=…)`, собранном тестом, зелен, а у живой записи ключ не видит `tools`.
- **О2.** Суммы блокировок включаются только при непустых `tools` — единственный различитель, совместимый с AC-8 и тестом равенства (Ф2). AC-7 зелен (тест задаёт `tools`), но у компонента без `tools` смена игнорируемого `package-lock.json` выдаёт из кэша итог старого окружения — ровно то, от чего защищает тр. 7.
- **О3.** Признак происхождения вводится полем `Profile` с `compare=False`: тест равенства (components.py:694) зелен, а его смысл («`Profile` одинаков») обойдён.
- **О4.** Вторая половина AC-1 проходит на неизменённом коде (cli.py:88-92). Разработчику достаточно обернуть только cli.py:94.
- **О5.** Учебный CI-файл задаёт форму переменной (AC-4/AC-5), разработчик разбирает ровно её. На живом `ci.yml` sled проверка даёт skip «нет переменной», и doctor молча не сверяет карту путей.

## Вердикт
**fail.** Тр. 7 в заявленных зонах и при действующем долгоживущем тесте выполнимо только частично или обходом. Это решение по устройству, его должен сформулировать аналитик (при нужде — вопросом Оператору о зонах), а не разработчик посреди работы.

1. Тр. 6-7, AC-7: `tools` не доходят до `Profile` из записи — `repo_context.py:171-172` отбирает только `PROFILE_FIELDS` (`targets.py:44-59`), правка вне зон (`repo_context.py` — только чтение; `project_profile.py` — «только поле `tools`»).
