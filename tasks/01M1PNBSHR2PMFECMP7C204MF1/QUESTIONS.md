# QUESTIONS: Роль в своей группе процессов: таймаут, kill, pause --now бьют дерево; сторож зависших прогонов

## Вопросы

1. **Требование 3 ТЗ буквально говорит «поднимает алерт `kind=warning`»,
   но `orchestrator/alerts.py:31` жёстко ограничивает допустимые
   значения `KINDS = ("incident", "threshold", "trigger", "attention")`
   — `raise_alert` бросает `ValueError` на любом другом значении
   (`alerts.py:44-45`). Значения `"warning"` в системе не существует
   нигде: ближайшее похожее — статус `"warn"` в `doctor.LABELS`
   (`doctor.py:1161`), но это отдельный словарь меток для консольного
   отчёта `Check`, не поле `kind` таблицы `alerts`, и оно не участвует
   в persistence/`auto_ack` (у `Check`-кортежей вообще нет состояния
   ack — они пересчитываются каждый прогон). А требование прямо просит
   персистентный alert с «авто-ack при исчезновении» — это однозначно
   про таблицу `alerts` и `alerts.auto_ack`, а не про `Check.status`.
   Значит `kind=warning` из ТЗ — либо неточная формулировка (спутано
   с `doctor.LABELS["warn"]`), либо запрос на расширение перечня
   `alerts.KINDS`. Ближайший прецедент в кодовой базе — `check_leases`
   (`doctor.py:780-831`), который для того же класса ситуации
   (осиротевший процесс без живого lease) заводит `kind="incident"`
   и использует тот же паттерн `_auto_ack_gone`. Как поступить?**

   Варианты:
   - A) Использовать существующий `kind="incident"` — по прямому
     прецеденту `check_leases` для того же класса находки (процесс без
     живого lease); `orchestrator/alerts.py` не трогается, задача не
     выходит за перечисленные в ТЗ зоны (`alerts.py` в списке зон нет).
   - B) Добавить новое значение `"warning"` в `alerts.KINDS`
     (`orchestrator/alerts.py:31`) — буквально по тексту ТЗ; расширяет
     зону задачи на `orchestrator/alerts.py`, не названный в перечне
     зон ТЗ, и меняет разделяемый контракт (`alerts.KINDS` читают все
     вызовы `raise_alert` по всей кодовой базе).

   Дефолт при молчании: **A** — не требует правки файла вне
   объявленных ТЗ зон и совпадает с уже действующим прецедентом для
   идентичного класса алерта (осиротевший процесс, `check_leases`).

2. **Требование 2 перечисляет пять путей принудительного завершения,
   которые должны бить группу процессов целиком: таймаут шага
   (`runner`), `kill`, `pause --now`, `release` мёртвого lease и
   «уборка после обрыва (`doctor`)». Первые четыре — команды, которые
   действуют немедленно, без флага `--fix` (в системе нет такого флага
   у `run`/`kill`/`pause --now`/`release`). Пятый пункт — «уборка после
   обрыва (`doctor`)» — по всей видимости это существующая проверка
   `check_leases` (`doctor.py:780-831`), которая находит осиротевший
   (мёртвый pid) lease; сейчас она ЧИСТО наблюдательная — только
   заводит алерт, не мутирует систему ни в обычном прогоне `doctor`,
   ни под `--fix` (мутирующие действия под `--fix` сейчас — только
   `sweep_orphan_artifact_branches` и `_fix_ignored_artifact_files`,
   `doctor.py:1041-1121`). Требование 3 для НОВОГО сторожа зависших
   тестовых прогонов явно разводит поведение по флагу: без `--fix` —
   только отчёт, `doctor --fix` — снимает группой. Должна ли группа
   зависшего процесса при обнаружении мёртвого lease (`check_leases`,
   пункт требования 2) сниматься безусловно при каждом прогоне
   `doctor` — симметрично остальным четырём немедленным путям того же
   требования — или только под `doctor --fix`, симметрично новому
   сторожу требования 3 и действующему в `doctor.py` принципу
   «наблюдение по умолчанию, мутация только под явный `--fix`»?**

   Варианты:
   - A) Безусловно на каждом прогоне `doctor` (без `--fix`) — по
     аналогии с остальными путями требования 2, которые все бьют
     группу немедленно, без отдельного флага.
   - B) Только под `doctor --fix` — по аналогии с новым сторожем
     требования 3 и действующим в `doctor.py` контрактом «обычный
     `doctor` — только отчёт, мутирует лишь `--fix`»; `check_leases`
     без `--fix` остаётся чисто наблюдательной, как сейчас.

   Дефолт при молчании: **B** — сохраняет уже установленный в
   `doctor.py` и ожидаемый операторами контракт (обычный `doctor` не
   мутирует систему), не меняя молча поведение существующей проверки
   `check_leases` для тех, кто полагается на её текущую безопасность.
