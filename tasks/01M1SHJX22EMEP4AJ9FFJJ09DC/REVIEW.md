## Замечания

- **blocker** — `orchestrator/budget.py:82-90` (вызывается из `orchestrator/fsm.py:665`, `_approve_spec_gate`) — `apply_spec_budget` пропускает применение значения из SPEC, если `t["budget_source"]` уже не `None` — НЕЗАВИСИМО от того, изменилось ли само значение относительно уже применённого. Требование 4/5 предполагает, что Оператор правит SPEC ПРЯМО на гейте (уже после того, как `spec_writing -> spec_gate` применил исходное значение, выставив `budget_source=spec`), и `approve` обязан подхватить новое значение. Но именно в этом, основном сценарии перечитывание молча не срабатывает: второй вызов `apply_spec_budget` видит `source == "spec"` (не `None`) и уходит в ветку «уже применён» — тот же код, что защищает потолок Оператора (`budget_source=operator`) от перезаписи, блокирует и легитимное повторное чтение из SPEC.
  Проверено исполнением (не входит в диф задачи, временный скрипт через `ApproveSandbox`, удалён после прогона): SPEC при входе на `spec_gate` нёс `budget_usd: 45` (применилось на `advance`, `budget_source=spec`, потолок $45); Оператор правит SPEC на гейте на `budget_usd: 35`; `approve <id> <sha>` печатает `бюджет из SPEC не применён: $35.00 — уже применён, остаётся $45.00` — потолок остаётся $45, хотя должен был стать $35. Это буквально сценарий, которым SPEC мотивирует всю задачу («Контекст»: «SPEC $35, потолок остался $45»).
  Существующие приёмочные тесты (`test_ac6_spec_gate_approve_rereads_budget.py`, `test_ac8_changed_value_is_journaled.py`) эту дыру не ловят — оба сценария «значение меняется» стартуют с `budget_source is None` (SPEC без `budget_usd` при входе на гейт, значение появляется впервые ПРЯМО в момент перечитывания approve), то есть проверяют только ПЕРВОЕ применение, не повторное чтение уже применённого из SPEC значения. `test_ac8_unchanged_value_no_duplicate_journal_record.py` стартует с `budget_source=spec` и ТЕМ ЖЕ значением — не отличает «не изменилось, поэтому не применяем» от «не применяем никогда, раз source не None» (мутация «убрать сравнение значений и всегда отказывать при `source is not None`» тест не ловит).
  Предложение: либо `apply_spec_budget` (или новая точка вызова в `_approve_spec_gate`) должна сравнивать НОВОЕ прочитанное значение с уже применённым и обновлять потолок при расхождении (оставляя нетронутым `budget_source=operator`), либо, если такое поведение сочтено чрезмерным для этой задачи, эскалировать разработчику для уточнения объёма требования 4 у Оператора — текущая реализация не решает задачу, которую сама SPEC ставит в «Контекст».

- **major** — `orchestrator/fsm.py:590-592` (подсказка повтора в ветке `sha is None`, случай расхождения) — при расхождении живого и зафиксированного sha подсказка `перепроверь артефакты и повтори: artel.py approve {task_id} {fixed or current}` называет ЗАФИКСИРОВАННЫЙ sha, а не живой. Явный путь (`orchestrator/fsm.py:601`, `matches = current.startswith(sha)`) сравнивает переданный sha с ЖИВЫМ `current`, а не с зафиксированным — при реальном расхождении `current != fixed`, и подсказанная команда `approve <id> <fixed_sha>` детерминированно проваливается второй раз («sha ... не совпадает с зафиксированным ...», тот же класс отказа). Правильная команда для осознанного подтверждения расхождения (требование 2, «способ осознанно подтвердить расхождение») — `approve <id> <current_sha>` (живой), не `<fixed_sha>`.
  Проверено исполнением (временный скрипт через `ApproveSandbox`, удалён после прогона, сценарий как в `test_ac3_diverged_or_dirty_refuses_named.py`): после стороннего коммита мимо гейта отказ печатает `... повтори: artel.py approve <id> <fixed_sha>`; буквальный повтор с этим sha снова отклоняется (`sha <fixed_sha> не совпадает с зафиксированным <current_sha>`, состояние не изменилось); повтор с ЖИВЫМ sha (`current_sha`) вместо предложенного — проходит и переводит задачу дальше.
  Ни один из приёмочных тестов (`test_ac3_diverged_or_dirty_refuses_named.py`) не проверяет работоспособность подсказанной команды — только присутствие обоих sha в тексте отказа (`assertIn(fixed_sha, out)`, `assertIn(live_sha, out)`), поэтому дефект не поймался планкой.
  Предложение: в ветке расхождения печатать `{current}` вместо `{fixed or current}` (в ветке «грязная копия» current==fixed, подстановка не меняется).

- **major** — новая логика (автосверка `confirm_fixation` при `sha is None`, требования 1-2; перечитывание бюджета на approve spec_gate, требования 4-5) не имеет постоянного покрытия в `tests/` — только в `tasks/01M1SHJX22EMEP4AJ9FFJJ09DC/acceptance_tests/` (эфемерная, задаче-scoped директория: в постоянное дерево `tests/` не копируется и не продвигается никаким механизмом пульта — подтверждено обходом `orchestrator/`/`scripts/`/`.github/`, а также прецедентом других задач, добавлявших отдельные постоянные тесты в `tests/` именно для регрессионной защиты нового поведения). Диф `tests/test_git_fixation.py` в этой задаче — это ПЕРЕИМЕНОВАНИЕ и правка ОДНОГО существующего метода (`ApproveByShaTest`), не новый тест. Сам PLAN.md (раздел «Подход», шаг 2) обещает «юнит-тесты на новую сверку `confirm_fixation` и на перечитывание бюджета на approve (дополнительно к уже залоченным `acceptance_tests/`)» — в фактическом дифе этого дополнения нет. После мержа задачи и исчезновения `tasks/<id>/acceptance_tests/` из рабочего дерева новое поведение (автопереход approve без sha при совпадении; перечитывание бюджета на гейте) останется без единого постоянного регрессионного теста.
  Предложение: перенести ключевые сценарии (как минимум — совпадение/расхождение/грязная копия для `confirm_fixation`, и «перечитывание меняет потолок» для бюджета) в `tests/test_git_fixation.py`/`tests/test_spec_budget.py` как постоянные тесты, раз уж `acceptance_tests/` этой цели не служат.
