# SPEC: approve без набора sha: сверка фиксации механикой; перечитывание budget_usd на гейте SPEC

## Контекст

`approve <id>` на гейтах spec_gate, acceptance, merge_gate и escalated
сегодня требует, чтобы Оператор набрал полный sha из подсказки
(`fsm.py::confirm_fixation`, «approve требует sha — зафиксирован …») —
ритуал копирования, на котором 05.09 Оператор набрал sha с опечаткой.
Смысл требования — подтвердить, что живое состояние артефактов
совпадает с тем, что пульт зафиксировал на последнем переходе
(`tasks.fixed_sha`, ADR-0003 п.15/п.17, инвариант 25); сама сверка
сегодня доверена набору текста руками, а не машине, у которой уже есть
всё нужное для сравнения.

Отдельно: потолок задачи из SPEC применяется один раз, на переходе
`spec_writing -> spec_gate` (`budget.apply_spec_budget`). Правка SPEC
Оператором прямо на гейте (например, сужение рамки) и последующий
`approve` потолок не пересчитывают — Оператор должен отдельно вызывать
`budget` руками, хотя SPEC под курсором уже несёт другое число
(наблюдение по карте 05.09: SPEC $35, потолок остался $45).

## Требования

1. `approve <id>` без явного sha на гейтах spec_gate, acceptance,
   merge_gate и escalated сам читает живой sha артефактов задачи тем же
   источником, которым сегодня печатается подсказка, и сверяет его с
   зафиксированным на последнем переходе sha (`tasks.fixed_sha`) и
   чистотой рабочей копии/артефактной ветки:
   - совпало — approve проходит без ввода sha и журналирует sha, с
     которым согласован переход;
   - разошлось — именованный отказ, называющий оба sha (живой и
     зафиксированный), с подсказкой перепроверить артефакты; состояние
     задачи не меняется.
2. Явный `approve <id> <sha>` (полный sha либо его префикс не короче
   действующей минимальной длины) остаётся способом осознанно
   подтвердить расхождение — сверка и отказ по несовпадению/грязной
   копии не меняются ни для одного из четырёх гейтов (прежняя
   семантика).
3. Строка правила «sha только копированием» удаляется из
   `docs/operator-session.md`. Правку готовит разработчик unified-диффом,
   приложенным к PLAN.md (с подтверждением `git apply --check` на чистом
   дереве) — применяет её Оператор, сама правка не входит в коммит
   кодовой ветки задачи.
4. `approve` на гейте spec_gate перечитывает `budget_usd` из SPEC
   артефактной ветки (тем же чтением, каким сегодня читает SPEC guard) и
   применяет прочитанное значение функцией `apply_spec_budget`, с теми
   же границами применения, что действуют у этой функции на момент
   мержа этой задачи. Потолок, выставленный Оператором командой
   `budget` (`budget_source = operator`), этим перечитыванием не
   перебивается ни в одну сторону.
5. Если перечитывание на approve spec_gate меняет потолок задачи — в
   журнал задачи пишется запись об изменении; если применённое значение
   совпадает с уже действующим потолком — новой записи об изменении нет.
6. Строка инварианта 25 в `docs/invariants.md`, сегодня описывающая
   «approve без подтверждённого sha не проходит гейт», уточняется под
   поведение требования 1 — без изменения самого принципа фиксации (FSM
   и approve решают только по зафиксированным хэшам, требование 2, «Не
   входит»).

## Критерии приёмки

AC-1. `approve <id>` без аргумента на гейтах spec_gate, acceptance,
merge_gate и escalated читает живой sha артефактов задачи тем же
источником, которым сегодня печатается подсказка approve, и сверяет его
с зафиксированным на последнем переходе sha и чистотой рабочей
копии/артефактной ветки.

AC-2. Живой sha совпадает с зафиксированным и копия чистая — approve
проходит без ввода sha и журналирует sha, с которым согласован переход.

AC-3. Живой sha расходится с зафиксированным, либо копия грязная —
approve без sha отклоняется именованным отказом, называющим оба sha
(живой и зафиксированный) и подсказку перепроверить артефакты; состояние
задачи не меняется.

AC-4. Явный `approve <id> <sha>` (полный sha или его префикс не короче
действующей минимальной длины) остаётся осознанным подтверждением
расхождения — сверка и отказ при несовпадении/грязной копии не
меняются ни для одного из четырёх гейтов.

AC-5. Строка правила «sha только копированием» («approve без sha
печатает зафиксированный sha — брать его копированием из вывода,
никогда не набирать по памяти») удалена из `docs/operator-session.md`;
правка подготовлена unified-диффом, приложенным к PLAN.md, с
подтверждением `git apply --check`, и не закоммичена кодовой веткой
задачи.

AC-6. approve на гейте spec_gate перечитывает `budget_usd` из SPEC
артефактной ветки и применяет прочитанное значение функцией
`apply_spec_budget` с теми же границами применения, что действуют у
неё на момент мержа этой задачи.

AC-7. Потолок, выставленный Оператором командой `budget`
(`budget_source = operator`), approve на spec_gate не перебивает — ни
при совпадающем, ни при отличающемся значении `budget_usd` в SPEC.

AC-8. Перечитывание на approve spec_gate меняет потолок задачи — в
журнал задачи пишется запись об изменении; значение совпало с уже
применённым — новой записи об изменении нет.

AC-9. Строка инварианта 25 в `docs/invariants.md` отражает новое
поведение approve без sha (автоматическая сверка вместо обязательного
ввода), не ослабляя словесно принцип «FSM и approve решают только по
зафиксированным хэшам»; существующие `tests/test_fsm*.py`,
`tests/test_spec_budget.py`, а также приёмочные планки задач
01M1GHZTX9… и T021 (approve-по-sha как принцип фиксации) остаются
зелёными без ослабления проверок.

## Оценка объёма и деление

Сработавшие сигналы: число затрагиваемых модулей/файлов (текст SPEC
называет 5 путей `orchestrator/*.py` — 4 в зоне задачи и один,
`orchestrator/fsm_autogate.py`, упомянутый в «Не входит» как НЕ
затрагиваемый; сигнал считает упоминания в тексте, не саму зону);
бюджет (`budget_usd` $30 — на пороге $30); прогноз диффа не дан (поле
не заполнено, при уже сработавшем другом сигнале).

Обоснование монолита: Часть А (требования 1–3, AC-1..AC-5) и Часть Б
(требования 4–5, AC-6..AC-8) обе меняют один и тот же диспетчер —
`orchestrator/fsm.py::_cmd_approve` (Часть А — общий для всех гейтов
узел `confirm_fixation`; Часть Б — ветка `spec_gate` того же
диспетчера) — и делят одну и ту же зону `orchestrator/fsm.py`. Нарезка
на 2 подзадачи по границам зон, как того требует правило нарезки
(границы частей = границы зон, skills/spec-authoring.md), здесь
невозможна без того, чтобы обе подзадачи всё равно объявили
`orchestrator/fsm.py` своей зоной — то есть конкуренция за эту зону
(ТЗ уже называет её занятой тремя другими задачами) нарезкой не
снимается, а два отдельных прохода конвейера (SPEC/PLAN/REVIEW дважды)
только добавляют накладные расходы без выигрыша в параллельности.
Обе части независимо мержимы с зелёной планкой сами по себе (ни одна не
зависит от механики другой), но раздельный мерж не решает проблему
общей зоны — решение оставлено монолитом. Утверждает Оператор на гейте
SPEC.

монолит принят Оператором 06.09.2026: обе части правят один диспетчер `_cmd_approve` и одну зону fsm.py, нарезка конкуренцию за зону не снимает.

## Не входит

- Автогейты (`orchestrator/fsm_autogate.py`) — не затрагиваются, approve
  остаётся ручным гейтом Оператора.
- Само правило фиксации approve-по-sha как принцип (T021: FSM и approve
  решают только по зафиксированным хэшам) — не меняется; меняется
  только способ подтверждения (машинная сверка вместо ручного набора
  sha).
- ADR-0014 (дефолт $50, потолок ролей $100, `budget_usd` обязателен в
  SPEC) сама по себе — отдельная задача 01M1SHDCW7…. Часть Б этой
  задачи опирается на `apply_spec_budget` и её текущие границы как
  есть, границы применения потолка эта задача не меняет: если к моменту
  мержа этой задачи ADR-0014 уже слита, `apply_spec_budget` перечитывает
  в её границах (до `ROLE_BUDGET_CAP`); если нет — в прежних (только
  вниз от дефолта).
