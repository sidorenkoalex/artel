## Проверяемость критериев
Красная фаза: все тесты идут через подменённый `docker` песочницы `stand`;
до кода отказа нет, стенд «поднимается» подменённым `docker`, который
пишет только отчёт под `<дерево>/<left>` (`:150-156`). Рекурсии, порождения
процессов, настоящего Docker и меняющих команд против настоящего
репозитория нет. Пути «вне дерева» — строки без создания; висячая ссылка
`<root>/link` создаётся внутри временного каталога теста. Безопасно.

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да; до кода красен | bind не проверяется по дереву; короткая строковая форма пропущена в новой проверке |
| AC-2 | да; до кода красен | `file` секрета/конфигурации проверяется только на сокет |
| AC-3 | да; до кода красен | `build.context` не проверен; `docker-image://` или `oci-layout://` принят целиком. Отдельная ветка «адрес git» ненаблюдаема — эти значения не абсолютны и уже отклоняются правилом «закрыто по умолчанию»; это не дефект |
| AC-4 | да; до кода красен (кроме «inner проходит») | `startswith` без границы компонента (`t2`, `<root>2`); сверка без `realpath` источника (ссылка); сырая строка без нормализации (`../..`); запрет всех ссылок (inner) |
| AC-5 | да; до кода красен | `realpath` относительного пути от рабочего каталога процесса; `TypeError` на `None` |
| AC-6 | да; до кода красен | любая из восьми привилегий не проверена |
| AC-7 | да; зелёный с рождения | проверка путей у `volume`/`tmpfs`/`image`; `service:` отклоняется; сверка с рабочим каталогом процесса |
| AC-8 | да; зелёный с рождения | нет `realpath(tree)` |
| AC-9 | да; зелёный с рождения | новая проверка bind поставлена раньше сокетной — **только для bind** (см. отклонение 2) |
| AC-10 | да; до кода красен | правило не сменило версию/текст |

Отклонения раздела:
1. **Граница «совпадает с деревом» не покрыта ни одним AC.** Требование 1
   (SPEC «Требования» п. 1: «совпадает с `os.path.realpath(tree)` или лежит
   под ним») допускает путь, равный дереву. AC-7 берёт `build.context`
   подкаталогом (`base_config` — `@TREE@/<deploy>`), AC-8 — `realpath(дерева)/<подкаталог>`,
   AC-4 — только соседа и подкаталоги. Мутация «внутри — только строго под
   деревом» (`real.startswith(tree + os.sep)` без `real == tree`) проходит
   все критерии, а в работе отказывает самой частой форме — `build: .` или
   `.:/work` при compose-файле в корне дерева. Нужен случай в AC-7 (или
   AC-8): `build.context` или bind-источник, равный дереву.
2. **Порядок «сокет раньше новых проверок» (требование 4) для
   `secrets.*.file` / `configs.*.file` не покрыт.** AC-9 — только bind.
   Существующий `test_ac5_assembled_config_refusals_name_object`
   (`tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py:841`, случаи
   `secret_literal`, `secret_link`, `config_literal`, `config_link`)
   проверяет лишь имя объекта в тексте (`assert_refused_naming`, `:823-838`),
   а новый текст «вне дерева» тоже называет секрет — мутация «проверка
   дерева раньше сокетной для секрета» проходит всё. Нужен случай AC-9 для
   секрета или конфигурации с `file` на сокет вне дерева с прежним текстом
   («file на сокет Docker или его каталог», `orchestrator/acceptance.py:1115`).
3. **`oci-layout://<путь в дереве>` в положительной конфигурации AC-7 нет.**
   Требование 1 проверяет `oci-layout://` как путь (то есть внутри дерева
   — проходит); мутация «любой `oci-layout://` — отказ» проходит все
   критерии. Мелкое.
4. **AC-10 — «называет новые отказы — «вне дерева», привилегии и SSH»:**
   литерал задан только для «вне дерева»; что тест ищет для «привилегии» и
   «SSH» (`privileged`? `привилег`? `ssh` в любом регистре?) — не задано.
   Тест, ищущий конкретную подстроку, навяжет формулировку правила.
   Стоит назвать подстроки явно (например, `вне дерева`, `privileged`,
   `ssh`) или разрешить тесту любой регистр. Мелкое.
5. **AC-4, «равноценный вариант»** перечисляет только соседа-строку и
   висячую ссылку; случаи `…/sub/../../<сосед>` и «ссылка `inner` на
   подкаталог — проходит» в нём не названы. Буквальное чтение позволяет
   автору тестов выбрать вариант с меньшим набором случаев (мутация
   «запрет всех ссылок» тогда не ловится). Стоит указать, что все четыре
   случая обязательны в любом варианте. Мелкое.

## Пути обхода гейтов
- Проверяется вывод `config`, а стенд поднимается из файла пульта, собранного
  из того же `cfg` (`_compose_override`, `pult_file`, `:1296-1300`): сверенное
  и исполняемое совпадают — обхода через расхождение исходного файла и
  вывода нет.
- Отклонение 1 — путь «буквального» исполнения: строгая граница проходит
  все AC и ломает штатную форму `build: .`.
- Отклонение 2 — перестановку проверок для секретов не ловит ни один тест.
- Форма записи, не названная в SPEC: `build` не словарь, элемент `volumes`
  не словарь и не строка, `additional_contexts` списком (`["n=path"]`) —
  требование 1 задаёт «закрыто по умолчанию» для значений, но не для
  формы контейнера; наивный `service["build"].get(...)` на подменённом
  ответе даст `AttributeError`, а не отказ. Вывод `config` нормализует эти
  поля, поэтому в работе риск низкий; стоит дописать «форма поля не та —
  отказ» к требованию 1. Мелкое (отклонение 6).
- Вне ТЗ, не отклонение: `security_opt` (`seccomp=unconfined`,
  `systempaths=unconfined`), `userns_mode: host`, `cgroup: host`, `uts: host`
  в списке привилегий нет; `env_file`/`include`/`extends.file` ТЗ выносит
  в «Не входит» явно. Наблюдение для Оператора — кандидат строки бэклога.
