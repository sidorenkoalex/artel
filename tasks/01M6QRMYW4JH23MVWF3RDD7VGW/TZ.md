# Раннер compose: файлы машины и привилегии стенда — только внутри дерева прогона

## Факты

1. Раннер `compose` (ADR-0023, поправка 05.11.2026; ядро — задача 01M6PAJ61D4PYAP79ADRPA6MWV) перед подъёмом стенда проверяет собранную конфигурацию — вывод `docker compose … config --format json` — функцией `_compose_config_refusal(cfg, project, sockets)` (`orchestrator/acceptance.py:1077-1117`, вызов `:1286`). Отказ запуска называет сервис, сеть, том, секрет или конфигурацию; `up` и `run` после отказа не зовутся (`:1287-1290`).
2. Для bind-монтирований сервиса (`_bind_sources`, `:1063-1074`) и файлов секретов и конфигураций (`secrets.*.file`, `configs.*.file`, `:1112-1116`) проверяется только одно: источник — не сокет Docker и не каталог, его содержащий (`_socket_source`, `:1049-1060`). Любой другой путь машины пульта проходит: сервис стенда может смонтировать `~/.ssh`, `~/.kube`, каталог связки ключей или домашний каталог Оператора, и код тестов проекта в контейнере его прочитает. Короткая строковая форма в `_bind_sources` принимает и относительные источники (`./x`, `~/x`, `:1070-1073`).
3. Не проверяются вовсе: контекст сборки (`services.*.build.context`, `build.additional_contexts`), проброс агента и ключей SSH в сборку (`build.ssh`), привилегии сервиса (`privileged`, `pid: host`, `ipc: host`, `cap_add`, `devices`). В Docker Desktop привилегированный контейнер достаёт до виртуальной машины Docker, где смонтирован `/Users`, — это обходит любое правило монтирований.
4. Дерево прогона — аргумент `tree` функции `_compose_report_run` (`:1201`): рабочая копия задачи или дерево мержа. Compose-файл, файл окружения и монтирование отчёта лежат внутри него (`_ComposePlace`, `:938-962`; `:1262`). Законное монтирование кода проекта — левая часть `compose_mount` внутри дерева.
5. `docker compose config --format json` выдаёт монтирования в длинной форме с абсолютным `source` и абсолютный `build.context` (относительные пути разрешаются от `--project-directory`). На macOS временные каталоги и `/var` — ссылки (`/var` → `/private/var`): сравнение «внутри ли» требует `realpath` обеих сторон и границы компонента пути — образец `_own_cwd` (`:222-224`), `_ComposePlace.container` (`:944-955`).
6. Версия правила `COMPOSE_OVERRIDE_RULE` (`:830-834`) входит в ключ итога прогона (`:3676`); комментарий `:827-829` требует менять её при любой правке `_compose_config_refusal`.
7. Тесты отказов ядра — `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`: `REFUSAL_CASES` (`:749-758`), `refusal_variant` (`:762-820`), `test_ac5_assembled_config_refusals_name_object` (`:841`). Сокетные случаи и случаи секретов монтируют пути вне дерева и ожидают отказ с именем объекта — отказ по сокету срабатывает первым при сохранении порядка. Все подменённые ответы `config` в тестах ядра используют источники `@TREE@/…` внутри дерева (`base_config`, `:397-417`); других вызовов `_compose_config_refusal` нет. Корень песочницы `RealGitSandbox` уже разрешён (`tests/sandbox.py:1946`, `.resolve()`).
8. Тест с настоящим Docker `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py` монтирует `../{left}:/work` внутри дерева (`:49`).

## Требуется

1. `_compose_config_refusal` получает дерево прогона (новый параметр; вызов `:1286` передаёт `tree`). Путь «внутри дерева» — строка, абсолютный путь, `os.path.realpath` которого совпадает с `realpath(tree)` или лежит под ним по границе компонента. Отказ запуска, если не внутри дерева:
   - источник bind-монтирования сервиса (длинная и короткая форма);
   - `file` секрета или конфигурации (секрет без `file` — через `environment`/`content` — не проверяется);
   - `build.context` сервиса;
   - значение `build.additional_contexts`: проходит только `service:<имя>`; `oci-layout://<путь>` проверяется как путь (часть после схемы); любое другое значение со схемой (`docker-image://`, `https://` и т. д.) — отказ;
   - `build.context` с адресом git (`https://…`, `git@…`, `….git#…`) — отказ.
   Значение не строка, пустая строка, `null`, относительный путь, путь с `~` — отказ («закрыто по умолчанию»), не исключение.
2. Отказ запуска, если у сервиса: `privileged: true`; `pid: host`; `ipc: host`; непустой `cap_add`; непустой `devices`; непустой `build.ssh`; `build.privileged: true`; непустой `build.entitlements`.
3. Текст отказа называет объект (сервис, секрет, конфигурацию), поле и значение и говорит, почему (вне дерева прогона / привилегия / SSH); `up` и `run` после отказа не зовутся — тот же путь возврата, что у прочих отказов.
4. Проверка сокета Docker (`_socket_source`) для того же объекта остаётся раньше новых проверок: текст отказа по сокету — прежний.
5. Монтирования `type: volume`, `tmpfs`, `image` и именованные тома новой проверкой путей не затрагиваются (короткая строка без `/`, `.` и `~` в начале по-прежнему читается как именованный том, `:1070-1073`; вывод `config` даёт длинную форму) (`driver_opts` у `local` уже отвергается, `:1106-1108`).
6. `COMPOSE_OVERRIDE_RULE` получает новую версию (номер версии в начале строки увеличен) и называет новые отказы.
7. Прежние отказы, их порядок и тексты, перекрытие `_compose_override` — без изменений; правка только добавляет проверки.

## Критерии приёмки

Тесты — в новом долгоживущем файле задачи, по образцу песочницы `stand` файла ядра: подменённый `docker`, ответ `config --format json` — единственный канал; функции модуля не подменяются. Каталоги, которые тест создаёт, — только под его собственным временным каталогом; пути «вне дерева», которые тест не создаёт, подаются строкой без создания (`realpath` работает и без существующего пути). Настоящие каталоги Оператора (`~/.ssh` и т. п.) не используются и не читаются.

- AC-1: bind-монтирование сервиса с источником вне дерева прогона — длинная форма и короткая строка `"/<вне дерева>:/y"` отдельными случаями — отказ запуска; текст называет сервис и путь; в журнале вызовов подменённого `docker` нет `up` и `run`.
- AC-2: то же для `secrets.<имя>.file` и `configs.<имя>.file` вне дерева — отказ с именем секрета или конфигурации.
- AC-3: `build.context` вне дерева — отказ; `build.context` `https://h/r.git`, `git@h:r.git`, `h/r.git#main` — отказ (каждый случаем); `additional_contexts` со значениями: путь вне дерева, `oci-layout://<путь вне дерева>`, `docker-image://alpine` — отказ (каждый случаем).
- AC-4: граница и ссылки: тест создаёт под своим временным каталогом родителя с деревом `t` и соседом `t2`; дерево прогона — `t`. Источник `<родитель>/t2/x` — отказ; `<родитель>/t/sub/../../t2` — отказ; ссылка `t/link` на `t2` — отказ; ссылка `t/inner` на `t/sub` — проходит. Равноценный вариант без второго репозитория: дерево — `sandbox.root` песочницы `stand`, сосед — строка `<root>2/x` без создания, ссылка — висячая ссылка `<root>/link` на `<root>2`.
- AC-5: закрыто по умолчанию: источник bind `~/x`, `./x`, пустая строка и `null`, `build.context: null` — отказ запуска, а не исключение (ловит `realpath` от рабочего каталога процесса и `TypeError`).
- AC-6: привилегии: по отдельному случаю `privileged: true`, `pid: host`, `ipc: host`, `cap_add: [SYS_ADMIN]`, `devices: [/dev/x:/dev/x]`, `build.ssh: [default]`, `build.privileged: true`, `build.entitlements: [security.insecure]` — отказ с именем сервиса и поля.
- AC-7: положительная конфигурация: bind на подкаталог дерева, `build.context` в дереве, секрет-файл в дереве, `additional_contexts` `service:<имя>`, именованный том проекта `type: volume`, `tmpfs` и `type: image` — отказа нет, `config`, `up` и `run` зовутся как раньше (ловит «проверяются все типы монтирований» и сверку с рабочим каталогом процесса).
- AC-8: дерево через ссылку: тест создаёт ссылку `<tmp теста>/alias` на дерево и передаёт `alias` как дерево прогона; источник записан явно через `realpath(дерева)/<подкаталог>` (не подстановкой пути дерева) — отказа нет (ловит отсутствие `realpath` у дерева).
- AC-9: bind сокета Docker вне дерева — прежний текст отказа по сокету (ловит перестановку проверок).
- AC-10: `COMPOSE_OVERRIDE_RULE` не равен литералу прежней строки (значение на `38c27013`, `:830-834`), начинается с увеличенного номера версии и называет новые отказы — «вне дерева», привилегии и SSH (ловит правку правила без смены версии ключа итога).

Каждый тест — со строкой «Ловит мутацию: …».

Безопасность тестов: настоящий Docker не вызывается; образы не скачиваются; каталоги вне временного каталога теста не создаются, не читаются и не меняются.

Существующие тесты: не меняются. Если тест ядра краснеет из-за новой проверки — эскалация с именем теста, а не правка теста.

Зоны: `orchestrator/acceptance.py`, `tests/` (долгоживущие файлы задачи).

Только чтение: `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`, `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py`, `tests/sandbox.py`, `docs/adr/0023-role-step-sandbox.md`.

Не входит:
- `env_file`, `label_file`, `extends.file`, `include` — их читает сам `docker compose config` на машине до проверки пульта; оставляет ли вывод `config --format json` эти поля, не проверено. Роль пишет это в «Предложения системе»; строку бэклога — сессия Оператора командой `note`;
- `build.dockerfile` с абсолютным путём вне контекста;
- лимиты памяти и процессора стенда, проверка образов и реестров;
- изоляция шага роли (круг 1) и чтение файлов машины клиентом модели;
- правка ADR-0023 (поправку пишет Оператор отдельно).
