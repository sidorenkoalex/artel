# SPEC: Раннер compose: файлы машины и привилегии стенда — только внутри дерева прогона

## Контекст
Раннер `compose` (ADR-0023, поправка 05.11.2026; ядро — задача
01M6PAJ61D4PYAP79ADRPA6MWV) перед подъёмом стенда проверяет собранную
конфигурацию (`docker compose … config --format json`) функцией
`_compose_config_refusal(cfg, project, sockets)`
(`orchestrator/acceptance.py:1077-1117`, вызов `:1286`). Для
bind-монтирований сервиса (`_bind_sources`, `:1063-1074`) и `file`
секретов/конфигураций (`:1112-1116`) сейчас проверяется только одно —
источник не сокет Docker и не его каталог (`_socket_source`,
`:1049-1060`); любой другой путь машины пульта (`~/.ssh`, `~/.kube`,
домашний каталог Оператора) проходит и читается кодом тестов проекта в
контейнере. Контекст сборки, `build.ssh` и привилегии сервиса
(`privileged`, `pid: host`, `ipc: host`, `cap_add`, `devices`) не
проверяются вовсе, а привилегированный контейнер в Docker Desktop
достаёт до ВМ Docker, где смонтирован `/Users`, — в обход любого правила
монтирований. Элемент `volumes`, не являющийся ни словарём, ни строкой,
`_bind_sources` молча пропускает (`:1066-1073`). Задача сужает
разрешённые файлы машины до дерева прогона (аргумент `tree` функции
`_compose_report_run`, `:1201`: рабочая копия задачи или дерево мержа)
и отказывает в привилегиях стенда.

## Требования
1. `_compose_config_refusal` получает дерево прогона новым параметром;
   вызов `orchestrator/acceptance.py:1286` передаёт `tree`. Путь
   «внутри дерева» — строка, абсолютный путь, `os.path.realpath`
   которого совпадает с `os.path.realpath(tree)` или лежит под ним по
   границе компонента пути (образец — `_own_cwd`, `:222-224`;
   `_ComposePlace.container`, `:944-955`). Путь, равный самому дереву,
   — внутри. Отказ запуска, если не внутри дерева:
   - источник bind-монтирования сервиса (длинная и короткая форма);
   - `file` секрета или конфигурации (секрет/конфигурация без `file` —
     через `environment`/`content` — не проверяется);
   - `build.context` сервиса (`build` строкой — это `build.context`);
   - значение `build.additional_contexts`: проходит только
     `service:<имя>`; `oci-layout://<путь>` проверяется как путь (часть
     после схемы); любое другое значение со схемой (`docker-image://`,
     `https://` и т. д.) — отказ;
   - `build.context` с адресом git (`https://…`, `git@…`, `….git#…`) —
     отказ.
   Значение не строка, пустая строка, `null`, относительный путь, путь
   с `~` — отказ («закрыто по умолчанию»), а не исключение.
   Неверная форма поля — отказ запуска с именем объекта, а не
   исключение: `build` не словарь и не строка; элемент `volumes` сервиса
   не словарь и не строка; `build.additional_contexts` не словарь;
   элемент раздела `secrets`/`configs` не словарь.
2. Отказ запуска, если у сервиса: `privileged: true`; `pid: host`;
   `ipc: host`; `userns_mode: host`; `cgroup: host`; `uts: host`;
   элемент `security_opt`, содержащий `unconfined`, `label=disable` или
   `label:disable`; непустой `cap_add`; непустой `devices`; непустой
   `build.ssh`; `build.privileged: true`; непустой `build.entitlements`.
   Прочие значения `security_opt` (например `no-new-privileges:true`)
   проходят.
3. Текст отказа называет объект (сервис, секрет, конфигурацию), поле и
   значение и говорит причину (вне дерева прогона / привилегия / SSH);
   `up` и `run` после отказа не зовутся — тот же путь возврата
   `ReportRun(refusal=…)`, что у прочих отказов (`:1287-1290`).
4. Проверка сокета Docker (`_socket_source`) для того же объекта
   остаётся раньше новых проверок — для bind-монтирования сервиса и для
   `file` секрета и конфигурации: текст отказа по сокету — прежний
   (`:1096-1097` для bind, `:1115-1116` для секрета и конфигурации).
5. Монтирования `type: volume`, `tmpfs`, `image` и именованные тома
   новой проверкой путей не затрагиваются: короткая строка без `/`, `.`
   и `~` в начале по-прежнему читается как именованный том
   (`:1070-1073`); отказ по `driver_opts` у `local` (`:1106-1108`)
   остаётся как есть.
6. `COMPOSE_OVERRIDE_RULE` (`:830-834`; входит в ключ итога прогона,
   `:3676`) получает новую версию — номер версии в начале строки
   увеличен — и называет новые отказы.
7. Прежние отказы, их порядок и тексты, перекрытие `_compose_override`
   — без изменений; правка только добавляет проверки.

## Критерии приёмки
Тесты — в новом долгоживущем файле задачи `tests/test_01m6qrmyw4jh23mvwf3rdd7vgw_*.py`
по образцу песочницы `stand` файла ядра
(`tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`): подменённый
`docker`, ответ `config --format json` — единственный канал; функции
модуля не подменяются. Каталоги, которые тест создаёт, — только под его
собственным временным каталогом; пути «вне дерева», которые тест не
создаёт, подаются строкой без создания. Настоящие каталоги Оператора
(`~/.ssh` и т. п.) не используются и не читаются; настоящий Docker не
вызывается, образы не скачиваются. Каждый тест несёт строку «Ловит
мутацию: …».

AC-1. Bind-монтирование сервиса с источником вне дерева прогона — длинная
форма и короткая строка `"/<вне дерева>:/y"` отдельными случаями — отказ
запуска; текст называет сервис и путь; в журнале вызовов подменённого
`docker` нет `up` и `run`.

AC-2. `secrets.<имя>.file` и `configs.<имя>.file` вне дерева — отказ
запуска с именем секрета или конфигурации; `up` и `run` не зовутся.

AC-3. `build.context` вне дерева — отказ; `build.context` со значениями
`https://h/r.git`, `git@h:r.git`, `h/r.git#main` — отказ (каждое
отдельным случаем); `build.additional_contexts` со значениями: путь вне
дерева, `oci-layout://<путь вне дерева>`, `docker-image://alpine` — отказ
(каждое отдельным случаем).

AC-4. Граница компонента и ссылки — все четыре случая обязательны в
любом из двух вариантов раскладки, каждый отдельным случаем:
(а) источник на соседа — отказ; (б) путь `…/sub/../../<сосед>` — отказ;
(в) ссылка из дерева на соседа — отказ; (г) ссылка внутри дерева на его
подкаталог — проходит.
Вариант 1: тест создаёт под своим временным каталогом родителя с деревом
`t` и соседом `t2`; дерево прогона — `t`; случаи: (а) `<родитель>/t2/x`,
(б) `<родитель>/t/sub/../../t2`, (в) обычная ссылка `t/link` на `t2`,
(г) ссылка `t/inner` на `t/sub`.
Вариант 2 (без второго репозитория): дерево — `sandbox.root` песочницы
`stand`; случаи: (а) строка `<root>2/x` без создания, (б)
`<root>/sub/../../<имя root>2`, (в) висячая ссылка `<root>/link` на
`<root>2`, (г) ссылка `<root>/inner` на `<root>/sub`.

AC-5. Закрыто по умолчанию и неверная форма: источник bind `~/x`, `./x`,
пустая строка и `null` (последние два — полем `source` длинной формы),
`build.context: null`, `build: 5`, `volumes: [5]`,
`build.additional_contexts: ["n=/x"]` — каждое отдельным случаем — отказ
запуска с именем сервиса, а не исключение (ловит `realpath` от рабочего
каталога процесса, `TypeError`/`AttributeError` и молчаливый пропуск
элемента неверной формы).

AC-6. Привилегии: отдельным случаем каждое из `privileged: true`,
`pid: host`, `ipc: host`, `userns_mode: host`, `cgroup: host`,
`uts: host`, `security_opt: [seccomp:unconfined]`,
`security_opt: [apparmor:unconfined]`, `security_opt: [label=disable]`,
`security_opt: [label:disable]`, `cap_add: [SYS_ADMIN]`,
`devices: [/dev/x:/dev/x]`, `build.ssh: [default]`,
`build.privileged: true`, `build.entitlements: [security.insecure]` —
отказ запуска с именем сервиса и поля.

AC-7. Положительная конфигурация — отказа нет, `config`, `up` и `run`
зовутся как раньше; случаи: bind на подкаталог дерева; bind с
источником, равным самому дереву; `build.context` в дереве;
`build.context`, равный самому дереву (так `config` выдаёт `build: .`
Compose-файла в корне дерева); секрет-файл в дереве;
`additional_contexts` `service:<имя>`; `additional_contexts`
`oci-layout://<путь внутри дерева>`; `security_opt:
[no-new-privileges:true]`; именованный том проекта `type: volume`,
`tmpfs` и `type: image`. Ловит мутации: «проверяются все типы
монтирований», сверка с рабочим каталогом процесса, «внутри — только
строго под деревом» (`startswith(tree + os.sep)` без равенства),
«любой `oci-layout://` — отказ», «любой `security_opt` — отказ».

AC-8. Дерево через ссылку: тест создаёт ссылку `<tmp теста>/alias` на
дерево и передаёт `alias` как дерево прогона; источник записан явно
через `realpath(дерева)/<подкаталог>` (не подстановкой пути дерева) —
отказа нет (ловит отсутствие `realpath` у дерева).

AC-9. Сокет Docker вне дерева — прежний текст отказа по сокету, отдельным
случаем каждое: bind сервиса (текст «bind-монтирование сокета Docker или
его каталога»), `secrets.<имя>.file` и `configs.<имя>.file` (текст
«file на сокет Docker или его каталог»), а не новый текст «вне дерева»
(ловит перестановку проверок — проверка дерева раньше сокетной для
bind, секрета или конфигурации).

AC-10. `COMPOSE_OVERRIDE_RULE` не равен литералу прежней строки
(значение на `38c27013`, `orchestrator/acceptance.py:830-834`),
начинается с увеличенного номера версии (прежняя начинается с «1: ») и
содержит, без учёта регистра, подстроки «вне дерева», «privileged» и
«ssh»; формулировку остального текста правила тест не навязывает (ловит
правку правила без смены версии ключа итога).

## Оценка объёма и деление

Сработавшие сигналы: критериев приёмки — 10 (порог 10); `budget_usd`
$30 ≥ $30 (рамка Оператора из ТЗ).

Материал для решения Оператора — **обоснование монолита**: зона — одна
функция `_compose_config_refusal` (с её вызовом и строкой версии
`COMPOSE_OVERRIDE_RULE`) в одном файле `orchestrator/acceptance.py` плюс
новый долгоживущий файл тестов. Десять критериев — это разные входы одной
проверки, а не разные механики. Разрез (например, «пути» отдельно от
«привилегий») дал бы две правки одной функции и две смены версии
`COMPOSE_OVERRIDE_RULE` в ключе итога подряд — двойную инвалидацию
сохранённых итогов прогона без выигрыша; при этом промежуточное
состояние «пути закрыты, привилегии открыты» оставляет обход правила
монтирований через привилегированный контейнер (факт 3 ТЗ), то есть
частичная защита ничего не гарантирует.

## Не входит
- `env_file`, `label_file`, `extends.file`, `include` — их читает сам
  `docker compose config` на машине до проверки пульта; оставляет ли
  вывод `config --format json` эти поля, не проверено. Роль пишет это в
  «Предложения системе»; строку бэклога — сессия Оператора командой
  `note`.
- `build.dockerfile` с абсолютным путём вне контекста.
- Лимиты памяти и процессора стенда, проверка образов и реестров.
- Изоляция шага роли (круг 1) и чтение файлов машины клиентом модели.
- Правка ADR-0023 (поправку пишет Оператор отдельно).
- Правка существующих тестов: `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_run.py`,
  `tests/test_01m6paj61d4pyap79adrpa6mwv_compose_docker.py`,
  `tests/sandbox.py` — только чтение. Если тест ядра краснеет из-за
  новой проверки — эскалация с именем теста, а не правка теста. По
  фактам ТЗ (7, 8) краснота не ожидается: подменённые ответы `config` в
  тестах ядра используют источники `@TREE@/…` внутри дерева, корень
  песочницы уже разрешён (`tests/sandbox.py:1946`), сокетные случаи
  отказывают прежней проверкой раньше новых, тест с настоящим Docker
  монтирует `../{left}:/work` внутри дерева.
- Зелёный полный набор `tests/` и CI ветки — их держит пульт.
