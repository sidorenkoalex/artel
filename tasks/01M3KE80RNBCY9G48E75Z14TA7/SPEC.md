# SPEC: Ретроспектива в снимке артефактов — верный исход и счётчики приёмочных тестов

## Контекст

Снимок закрытия задачи (`refs/artifacts/<id>` репозитория целевого) несёт
`tasks/<id>/RETRO.md`, и для СМЕРЖЕННОЙ задачи эта ретроспектива сегодня
лжёт: на origin/main d345c66e у задачи 01M3HP7WAXKFK3GYZ3T6HX08M0
(смержена 27.09 18:25Z) снимок несёт «Итог: killed — причина: причина не
найдена в журнале» и «Адрес артефактов: артефакты не сохранены (ветка
удалена при kill)», тогда как `docs/retro/<id>.md` в `main` для той же
задачи — «Итог: done, sha …». Причина: `orchestrator/cleanup.py:414`
передаёт в публикацию снимка литерал `"killed"` всегда, в том числе на
пути закрытия смерженной задачи.

Второй дефект — счётчики: `docs/retro/<id>.md` последних задач несёт
«Приёмочные тесты: 0 тест(ов), 0 manual, 0 skip» при непустом каталоге
приёмочных тестов (01M3HP7WAXKFK3GYZ3T6HX08M0 — 10 тестов,
01M3HJQV2QV9BXNXSH3F8STAYH — 36), потому что `orchestrator/retro.py:439`
считает по `config.TASKS / <id>` главной копии, где каталога закрываемой
задачи в момент записи нет вовсе.

Источник задачи: две строки копилки 27.09 (разбор читателей каталога
`tasks/`) и ADR-0018, «Следствия» — верный исход и счётчики в
ретроспективе снимка названы там ПЕРВЫМ условием уборки каталога `tasks/`
из `main`.

## Требования

1. Исход, передаваемый в публикацию снимка закрытия, соответствует
   состоянию задачи: `done` для смерженной, `killed` для ликвидированной.
   Литерала «killed» на пути закрытия смерженной задачи не остаётся.
2. Ретроспектива в снимке смерженной задачи несёт «Итог: done» и sha
   мержа. Строка причины («— причина: …») остаётся только у исхода
   `killed`.
3. Строка «Адрес артефактов» в ретроспективе снимка смерженной задачи
   называет `refs/artifacts/<id>` (ADR-0005, пункт 4; ADR-0018, пункт 1),
   а не «артефакты не сохранены (ветка удалена при kill)».
4. Ретроспектива в снимке ликвидированной задачи остаётся как сегодня:
   «Итог: killed — причина: <причина из журнала>» и прежняя строка адреса.
5. Счётчики приёмочных тестов (число тестов, manual, skip) в ОБЕИХ
   ретроспективах (`docs/retro/<id>.md` и ретроспектива снимка) считаются
   по каталогу приёмочных тестов АРТЕФАКТНОЙ ВЕТКИ задачи, читаемому через
   git, а не по каталогу задачи в главной копии. Ядро подсчёта —
   существующее (`scripts/guard.py`, статический разбор каталога), новой
   копии правил подсчёта не появляется.
6. Артефактной ветки в момент записи ретроспективы уже нет — счётчики
   нули, генерация не падает: сегодняшняя тихая деградация сохраняется.
7. Порядок вызовов при закрытии не меняется: снимок публикуется строго до
   удаления кодовой и артефактной веток (ADR-0005, пункт 4) — на обоих
   путях закрытия, и через мерж, и через `kill`. Канареечный прогон снимок
   по-прежнему не публикует.
8. Тесты в `tests/`: смерженная задача — в снимке «Итог: done» и адрес по
   ссылке; ликвидированная — «Итог: killed» с причиной, как сейчас;
   счётчики равны числу тестов каталога приёмочных тестов при отсутствии
   каталога задачи в главной копии; канареечный прогон снимка не
   публикует. Корень и пути подменяются через общие помощники
   `tests/sandbox.py`.
9. `docs/stack.md` — в разделе о закрытии задачи одно предложение об
   исходе в ретроспективе снимка.

**Обоснование источника чтения (требование 5), как просит ТЗ.** Источник —
артефактная ветка задачи, не её снимок. В оба момента записи
ретроспективы ЗАКРЫТИЯ ветка ещё жива: публикация снимка читает дерево
ветки до её удаления (`orchestrator/snapshot.py:93` против `:120`), а
`docs/retro/<id>.md` смерженной задачи пишется на шаге публикации
артефактов мержа ДО публикации снимка (`orchestrator/fsm_merge_gate.py:945`
против `:950`) — требование 7 этот порядок закрепляет. Снимок как источник
не годится по двум причинам: в момент записи ретроспективы он ещё не
существует (ею же и наполняется), а чтение уже опубликованного снимка —
это `refs/artifacts/<id>` в origin ЦЕЛЕВОГО, то есть сетевой fetch внутри
генератора ретроспективы, где сегодня ни одного сетевого вызова нет.
Единственный путь, где ветки уже нет, — долговая генерация
`docs/retro/<id>.md` ликвидированной задачи (подбор долга на следующем
мерже, `orchestrator/fsm_postmerge.py`): там счётчики остаются нулями по
требованию 6, и верные числа для той задачи уже лежат в ретроспективе её
снимка.

## Критерии приёмки

AC-1. Задача закрыта путём мержа: в снимке `refs/artifacts/<id>` файл
`tasks/<id>/RETRO.md` несёт строку «Итог: done, sha <sha>» с непустым sha
мержа; строк «Итог: killed» и «причина:» в этой ретроспективе нет.

AC-2. Та же ретроспектива снимка несёт строку «Адрес артефактов:
refs/artifacts/<id>»; подстроки «артефакты не сохранены» в ней нет.

AC-3. Задача закрыта командой `kill`: ретроспектива её снимка несёт «Итог:
killed — причина: <последняя причина из журнала>» и прежнюю строку адреса
— поведение этого пути не изменилось.

AC-4. Сообщение коммита снимка называет фактический исход: «снапшот
закрытия (done)» для смерженной задачи и «снапшот закрытия (killed)» для
ликвидированной.

AC-5. Каталога задачи в главной копии нет, а артефактная ветка несёт
каталог приёмочных тестов с N тестами, M manual, K skip (N > 0):
ретроспектива снимка несёт «Приёмочные тесты: N тест(ов), M manual, K
skip» с теми же числами.

AC-6. В тех же условиях `docs/retro/<id>.md` смерженной задачи несёт те же
числа, а не «0 тест(ов), 0 manual, 0 skip».

AC-7. Артефактной ветки задачи нет вовсе: генерация ретроспективы
проходит без исключения и даёт «Приёмочные тесты: 0 тест(ов), 0 manual, 0
skip».

AC-8. На обоих путях закрытия push снимка в `refs/artifacts/<id>`
происходит ДО удаления кодовой и артефактной веток; при неудавшемся push
артефактная ветка не удаляется.

AC-9. Канареечный прогон при закрытии снимок не публикует: ссылка
`refs/artifacts/<id>` не появляется — как сегодня.

## Оценка объёма и деление

Сработали два сигнала.

- **Число затрагиваемых модулей/файлов.** guard считает упоминания путей
  вида `orchestrator/*.py`/`scripts/*.py` по ВСЕМУ тексту SPEC, а здесь
  помимо трёх файлов зоны названы читаемые, но не правимые адреса из
  раздела «Только чтение» ТЗ (`orchestrator/fsm_merge_gate.py`,
  `orchestrator/fsm_postmerge.py`, `orchestrator/artifact_branch.py`,
  `scripts/guard.py`) и один адрес идиомы в «Материалах»
  (`orchestrator/acceptance.py`). Фактическая зона правки — три файла кода
  (`orchestrator/cleanup.py`, `orchestrator/snapshot.py`,
  `orchestrator/retro.py`), одно предложение в `docs/stack.md` и общая
  зона `tests/`.
- **Затронут инвариантный механизм.** Сигнал даёт упоминание
  `scripts/guard.py`: этот путь назван в `docs/invariants.md`. Задача его
  только читает — ядро подсчёта тестов остаётся прежним (требование 5),
  правки guard в зонах нет. Инвариант 33 (`tests/` не пишут в настоящий
  репозиторий пульта: набор ссылок `refs/heads/*`, `refs/artifacts/*` не
  меняется) относится к тестам требования 8 напрямую — отсюда подмена
  корня и путей через `tests/sandbox.py`, а не самодельная песочница.

Прогноз диффа 12 КиБ против порога 128 КиБ; остальные сигналы не
сработали (9 критериев приёмки против порога 10, бюджет $30 против порога
$60, формулировок неопределённости нет). Бюджет: рамка ТЗ — $30, ниже
калибровочного ориентира гейта ($45 при девяти критериях и пяти
элементах поля `zones:`) — ставка вниз от ориентира, пол $25 соблюдён.
Фактическая цена задачи — четыре-пять шагов (analyst, test_author,
developer, одна-две итерации reviewer), $30 их покрывает.

**Решение: монолит.** Материал для решения Оператора без приукрашивания.
Формально задача распадается на две: исход и адрес (требования 1–4,
`orchestrator/cleanup.py` + `orchestrator/snapshot.py`) и счётчики
(требования 5–6). Против деления — не «атомарность механики», а границы
зон: обе части правят ОДИН файл `orchestrator/retro.py` (сборка строк
«Итог»/«Адрес артефактов» и подсчёт тестов живут там же) и обе пишут в
общую зону `tests/` — нарезка режет зону поперёк, чего границы частей
делать не вправе. Объём тоже против: один класс дефекта из одной пары
строк копилки 27.09, три файла кода, прогноз диффа 12 КиБ, рамка $30 —
две подзадачи дали бы ~$50 и два полных цикла SPEC/PLAN/REVIEW вместо
одного. Промежуточное состояние при этом работоспособно: часть, правящая
только исход, оставила бы снимок с верным итогом и нулевыми счётчиками —
то есть ровно половину первого условия ADR-0018 на уборку `tasks/` из
`main`, а условие считается исполненным только целиком.

## Не входит

- Отмена наложения снимка на `main` (ADR-0018, пункт 4) — отдельная
  задача.
- Уборка каталога `tasks/` из `main` и вторые копии для каталогов, у
  которых нет ни снимка, ни ветки.
- Правка формата `docs/retro/`: строка «Адрес артефактов» в
  `docs/retro/<id>.md` смерженной задачи остаётся контент-адресной
  (`<sha мержа>:tasks/<id>/`) — требование 3 говорит только о
  ретроспективе снимка.
- Переписывание ретроспектив и снимков УЖЕ закрытых задач, включая
  01M3HP7WAXKFK3GYZ3T6HX08M0 и 01M3HJQV2QV9BXNXSH3F8STAYH: история не
  переписывается, исправление прошлых снимков — отдельное решение
  Оператора.
- Источник строки «Суть» (`orchestrator/retro.py:253` читает SPEC.md
  главной копии тем же промахом). ТЗ называет эту строку в перечне
  причин, но требование 3 ТЗ говорит только о счётчиках приёмочных
  тестов — этой задачей чтение SPEC.md не меняется. Материал для решения
  Оператора на гейте SPEC, а не молчаливое расширение объёма.
- Новый носитель sha мержа (колонка БД, запись журнала): ретроспектива
  снимка берёт sha из того же источника, который уже доступен пути
  закрытия.
- Только чтение, правок не требуют и не получают:
  `orchestrator/fsm_merge_gate.py`, `orchestrator/fsm_postmerge.py`,
  `orchestrator/artifact_branch.py`, `scripts/guard.py`, `docs/adr/`,
  `docs/backlog.md`, `tests/test_invariants.py`.
- Ослабление или правка существующих тестов и инвариантов. Нового
  промежуточного состояния FSM задача не вводит (порядок вызовов при
  закрытии сохраняется требованием 7), так что краснота инвариантных
  тестов от числа шагов здесь не ожидается; если инвариантный тест всё же
  покраснеет — это эскалация Оператору, а не правка теста.
