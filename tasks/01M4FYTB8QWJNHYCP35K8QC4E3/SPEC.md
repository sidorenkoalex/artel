# SPEC: Лишняя база в рабочей копии задачи — изоляция тестов, проверка перед полным прогоном, кэш итога

## Контекст
09.10 полный прогон приёмки задачи 01M4C954HBJWEGD3AZS7Q3EHA4 дважды подряд
был красным одними и теми же 7 тестами (`sqlite3.OperationalError: no such
table: tasks`). Причина — пустой `.artel/state.db` (4096 байт, без таблиц)
внутри рабочей копии задачи: `config.DB` указывает в корень дерева, из
которого импортирован пакет, `store.db()` заводит файл при первом открытии,
а читатели (`artifact_branch.task_repo` и др.) принимают наличие файла за
готовую схему. Ключ кэша итога полного прогона (`acceptance.suite_tree_hash`)
не видит игнорируемый git каталог `.artel/`, поэтому после уборки файла
`approve` выдал тот же красный итог из кэша, не назвав `--fresh-suite`.
Задача закрывает хрупкость читателей, изолирует тесты, добавляет проверку
рабочей копии перед полным прогоном, учёт файла БД в кэше, сигнал `doctor`
со штатной командой уборки и строку в контракт сессии.

## Требования

Термины. **Файлы БД пульта в дереве** — `.artel/state.db` и его спутники
SQLite `.artel/state.db-wal`, `.artel/state.db-shm`, `.artel/state.db-journal`
относительно корня дерева (рабочей копии задачи). **Пригодная БД** — файл
`config.DB` существует и содержит таблицу `tasks`. **Перечень читателей** —
места из ТЗ, которые сегодня проверяют `config.DB.exists()` перед обращением
к БД:
- `artifact_branch.task_repo` (`orchestrator/artifact_branch.py` ~90);
- `workspace.task_target` (`orchestrator/workspace.py` ~56);
- `acceptance.journal_suite_metrics` (`orchestrator/acceptance.py` ~308);
- `acceptance._plank_helper_text` — ветка задачи из БД (~772);
- `acceptance.full_suite` — target задачи и признак `recordable` (~1518–1527);
- `models.live_task_set_providers` (`orchestrator/models.py` ~1392);
- проверка приостановки пары в `models.py` ~1465 (`pair_suspension_refusal`
  после `_pair_refusal`).

1. Проверка «БД пригодна» реализована в одном месте (функция в
   `orchestrator/store.py` или `orchestrator/schema.py`) и используется
   каждым местом перечня читателей вместо `config.DB.exists()`. Пустой файл
   (0 байт или SQLite без таблицы `tasks`) и чужой файл (не SQLite) на месте
   `config.DB` дают читателю тот же итог, что отсутствие файла; исключения
   `no such table` и иные `sqlite3.Error` из-за непригодности файла наружу
   не выходят. При пригодной БД читатели возвращают значения из неё, как
   сегодня.
2. Чтение БД не создаёт её: ни проверка пригодности, ни место перечня
   читателей не заводит файл `config.DB` (и не меняет существующий файл),
   когда его нет или он непригоден. Читающими путями в этой задаче
   считаются ровно места перечня читателей. Создание файла остаётся за
   `init` (`catalog.cmd_init`) и путями записи (команды, открывающие
   `store.db()` для изменения состояния).
3. Тесты `tests/`, которые сейчас обращаются к `store.db()` (прямо или
   через перечень читателей) без подмены пути БД, получают изолированную
   БД во временном каталоге: семь названных в ТЗ
   (`tests/test_acceptance.py::MaterializeFromBranchGitFailureTest`,
   `tests/test_fsm_autogate.py::SourceNoteOnPassTest`,
   `DiskAccTdirIgnoredForConditionATest`, `CiMarkerConditionTest`,
   `ChecklistNamesRealChecksTest`) и найденные поиском по `tests/`.
   Утверждения тестов не ослабляются.
4. Перед полным прогоном `tests/` гейта приёмки (автогейт и `approve` в
   `acceptance` — общий узел `acceptance.full_suite`/`acceptance_suite`) и
   гейта мержа (`fsm_merge_gate`) пульт проверяет рабочую копию задачи на
   файлы БД пульта в дереве. Найден хотя бы один — **именованный отказ**:
   полный набор не запускается; исход — «полный набор не проверен», не
   красный итог прогона; итог в кэш полного прогона не записывается; текст
   отказа (журнал задачи и вывод команды) называет путь каждого найденного
   файла и команду уборки `artel.py worktree-db-clean <id>` (требование 6).
   Обоснование выбора отказа против прогона с вынесенной БД: (а) кто
   создаёт файл, не установлено (ТЗ, «Факты»), — молчаливый вынос прятал
   бы повторение причины, отказ делает его видимым Оператору с первого
   раза; (б) вынос БД во временный каталог на время прогона требует
   подмены `config.DB` в процессе набора, то есть механики вне зон задачи
   (`orchestrator/config.py`, `orchestrator/runner.py` — только чтение);
   (в) уборка штатной командой стоит одну команду и не теряет файл.
5. Кэш итога полного прогона: ключ повторного использования
   (`acceptance.suite_tree_hash`/`suite_result_key`) учитывает файлы БД
   пульта в корне дерева — наличие каждого и содержимое (хэш). Появление,
   уборка или изменение такого файла при неизменном git-дереве дают другой
   ключ, и сохранённый итог повторно не используется. Итог, взятый из
   кэша, в своём тексте (тот, что попадает в отказ `approve` и запись
   гейта) называет флаг `--fresh-suite` как способ прогнать набор заново.
6. Новая команда пульта `artel.py worktree-db-clean <id>` переносит файлы
   БД пульта из рабочей копии задачи `<id>` в каталог логов пульта
   (`config.LOGS`, `.artel/logs/`) под именем, несущим id задачи и метку
   времени, не перезаписывая существующие файлы; содержимое переносится
   без изменений, файлы не удаляются; вывод называет каждый перенесённый
   файл (откуда → куда). Файлов нет — команда сообщает об этом, ничего не
   меняет и завершается успешно. `doctor` получает проверку рабочих копий
   задач в областях проектов (`.artel/projects/<проект>/worktrees/<id>/`):
   есть файл БД пульта в дереве — статус `warn` с путём и командой уборки
   `artel.py worktree-db-clean <id>`; нет ни в одной — `ok`.
7. `docs/operator-session.md`, в блоке о красном полном наборе приёмки
   (пункты «Что проверяет приёмка» / «Красный набор не по вине задачи»):
   строка «одни и те же тесты красные два прогона подряд — не случайный
   сбой: сравнить с чистым клоном и проверить игнорируемые файлы рабочей
   копии».

## Критерии приёмки

AC-1. В дереве, где на месте `config.DB` лежит пустой файл (0 байт), SQLite-файл без таблицы `tasks` или файл не SQLite, каждый читатель перечня даёт тот же итог, что при отсутствии файла (`artifact_branch.task_repo` и `workspace.task_target` — проект по умолчанию, `live_task_set_providers` — пустое множество и т.д.), без исключения; при пригодной БД с задачей другого проекта — значение из БД.

AC-2. В дереве без файла `config.DB` вызов каждого читателя перечня (в том числе чтение target задачи) не создаёт файл `config.DB`; непригодный файл после вызова остаётся байт в байт прежним.

AC-3. Семь названных в требовании 3 тестов зелёные и при пустом `.artel/state.db` в корне дерева прогона.

AC-4. Полный прогон гейта приёмки и гейта мержа на рабочей копии с файлом БД пульта в дереве не запускает набор и даёт отказ «не проверен» (не красный итог), текст которого называет путь найденного файла и `artel.py worktree-db-clean <id>`; записи итога в кэш полного прогона при этом нет.

AC-5. При неизменном git-дереве появление, уборка или изменение содержимого файла БД пульта в корне дерева меняет ключ кэша полного прогона: итог, сохранённый в одном состоянии, в другом повторно не используется; без файлов БД ключ стабилен между вызовами.

AC-6. Итог полного прогона, взятый из кэша, несёт в тексте флаг `--fresh-suite`.

AC-7. `doctor` выдаёт `warn` с путём файла и командой `artel.py worktree-db-clean <id>`, когда в рабочей копии задачи лежит файл БД пульта, и `ok`, когда его нет.

AC-8. `artel.py worktree-db-clean <id>` переносит файл БД пульта из рабочей копии задачи в `.artel/logs/` с неизменным содержимым (в рабочей копии файла больше нет, в каталоге логов есть); повторный вызов ничего не меняет и завершается успешно.

AC-9. `docs/operator-session.md` содержит строку требования 7 в блоке о красном полном наборе приёмки.

снять штатно. Требование 3 (изоляция тестов) опирается на требование 1:
