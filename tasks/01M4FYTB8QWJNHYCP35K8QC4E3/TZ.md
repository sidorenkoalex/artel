# ТЗ: Лишняя база в рабочей копии задачи: изоляция тестов, проверка перед полным прогоном, кэш итога

# ТЗ: Лишняя база в рабочей копии задачи — изоляция тестов, проверка перед полным прогоном, кэш итога

Источник: решение Оператора 09.10.2026 после приёмки 01M4C954HBJWEGD3AZS7Q3EHA4.
Копилка 09.10 (`docs/backlog.md`): «Автогейт приёмки 01M4C954… дважды
красный … лишний пустой .artel/state.db в worktree задачи», «approve на
acceptance … повторно использовал красный итог полного прогона».

Что произошло (09.10): полный прогон автогейта приёмки задачи
01M4C954HBJWEGD3AZS7Q3EHA4 был красным дважды подряд (fullsuite-2 08.10,
fullsuite-3 09.10) одними и теми же 7 тестами с `sqlite3.OperationalError:
no such table: tasks`:
`tests/test_acceptance.py::MaterializeFromBranchGitFailureTest`,
`tests/test_fsm_autogate.py::SourceNoteOnPassTest`,
`DiskAccTdirIgnoredForConditionATest`, `CiMarkerConditionTest` (2),
`ChecklistNamesRealChecksTest` (2). Причина — пустой файл
`.artel/state.db` (4096 байт, ни одной таблицы) внутри рабочей копии
задачи `.artel/projects/artel/worktrees/<id>/`, появившийся 08.10 09:49Z во
время шага developer-4. В чистом клоне ветки те же тесты зелёные; после
переноса файла свежий прогон (fullsuite-4) эти 7 тестов прошёл. Сессия при
Операторе сначала сочла падение случайным сбоем и потеряла круг приёмки.
Кроме того, первый `approve` после уборки файла выдал тот же отказ без
прогона: итог взят из кэша, потому что ключ кэша не видит файла.

Факты (main после мержа 01M4C954, сверка 09.10):
- `config.DB = ROOT / ".artel" / "state.db"`, где `ROOT` — корень дерева,
  из которого импортирован пакет (`orchestrator/config.py:12`). Полный
  прогон идёт в рабочей копии задачи, значит `config.DB` указывает внутрь
  неё.
- `store.db()` (`orchestrator/store.py:162`) создаёт каталог и файл БД при
  первом же открытии; `schema.migrate` на БД без таблицы `tasks` ничего не
  делает (`orchestrator/schema.py:180`, «схему ставит `init`»). Итог —
  пустой файл, если `store.db()` позвали там, где БД нет.
- Читатели считают наличие файла признаком готовой схемы:
  `artifact_branch.task_repo` (`orchestrator/artifact_branch.py:90`) зовёт
  `store.task_target(store.db(), …)` при `config.DB.exists()`; тот же
  приём — `acceptance.py` ~308, ~773, ~1518 (здесь отказ `no such table:
  tasks` уже перехвачен), `models.py` ~1392, ~1465, `workspace.py` ~56.
  Комментарий в `acceptance.py` ~1513 прямо называет эту хрупкость.
- Ключ кэша полного прогона — `acceptance.suite_tree_hash`
  (~1349): снимок git-дерева; неотслеживаемые файлы учитываются
  только неигнорируемые (`ls-files --others --exclude-standard`), а
  `.artel/` игнорируется git (`.gitignore:1`). Флаг `approve --fresh-suite`
  есть (`artel.py` ~1448), но отказ из кэша его не называет.
- Кто создал файл на шаге developer-4, по логу шага не установлено: лог
  обрезает строки команд (копилка 08.10, строка о «no tests ran»).

Требуется:
1. Читатели БД не принимают наличие файла за готовую схему: проверка
   «БД пригодна» (есть таблица `tasks`) в одном месте, её используют все
   перечисленные места. Пустой или чужой файл ведёт себя как отсутствие
   БД, а не как исключение `no such table`.
2. Чтение БД не создаёт её: путь, которому нужна только справка
   (target задачи, ссылка документов и т.п.), не заводит файл
   `.artel/state.db`. Создание файла остаётся за `init` и путями записи.
   SPEC перечисляет, какие пути считаются читающими.
3. Тесты, которые сейчас ходят в `store.db()` без подмены пути (семь
   названных выше и найденные поиском по `tests/`), получают изолированную
   БД во временном каталоге. Утверждения тестов не ослабляются;
   правка долгоживущих тестов — через объявление в «Меняемое поведение»
   SPEC по инварианту 38.
4. Перед полным прогоном автогейта приёмки и гейта мержа пульт проверяет
   рабочую копию задачи на `.artel/state.db` (и иные файлы БД пульта)
   и при находке отказывает именованно, называя путь и команду уборки,
   либо прогоняет набор с БД, вынесенной во временный каталог, — выбор
   за SPEC с обоснованием.
5. Кэш итога полного прогона: ключ учитывает файлы БД пульта внутри
   рабочей копии (наличие и содержимое), либо кэш не используется при
   их наличии. Отказ, выданный из кэша, называет `--fresh-suite`.
6. `doctor` сообщает о `.artel/state.db` внутри рабочих копий задач
   (статус `warn`, путь, команда уборки). Команда уборки — штатная
   команда пульта, не ручной `mv`/`rm`; переносит файл в каталог логов,
   а не удаляет.
7. `docs/operator-session.md`: строка «одни и те же тесты красные два
   прогона подряд — не случайный сбой: сравнить с чистым клоном и
   проверить игнорируемые файлы рабочей копии» в разделе разбора
   красного полного прогона.

Критерии приёмки (направление; планку пишет test_author):
- Пустой `.artel/state.db` в корне дерева: `artifact_branch.task_repo` и
  остальные читатели из перечня дают тот же итог, что при отсутствии
  файла; исключения нет.
- Чтение target задачи в дереве без БД не создаёт файл.
- Семь названных тестов зелёные и при пустом `.artel/state.db` в корне
  дерева прогона.
- Полный прогон гейта на рабочей копии с лишним файлом БД — именованный
  отказ или прогон с вынесенной БД (по SPEC); в обоих случаях без
  ложного красного итога.
- Кэш: появление или уборка файла БД в рабочей копии меняет решение о
  повторном использовании итога; отказ из кэша называет `--fresh-suite`.
- `doctor` выдаёт `warn` на лишний файл БД в рабочей копии задачи и `ok`
  без него; команда уборки переносит файл, повторный вызов ничего не
  меняет.
