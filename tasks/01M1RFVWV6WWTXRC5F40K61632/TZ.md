# ТЗ: наблюдатель роста карты кодовой базы — история, самокалибрующийся порог, атрибуция

Источник: решение Оператора 05.09 после замера карты в брифе (ТЗ
`tz-brief-map-projection.md`, задача 01M1RFQ52S0VD22J628TXX96XS).
Сегодня у карты один абсолютный порог — потолок файла брифа
`CONTEXT_FILE_MAX_BYTES` (`brief._handle_map_size_alert`, алерт-инцидент
«компонент пропущен»). Между «карта вписалась» и «карта выпала из
брифа» механизм ничего не видит: истории размера нет, темп роста не
считается, к какому модулю рост относится — неизвестно. Для внешних
целевых (ADR-0003 п.12, фаза B) абсолютные пороги неизвестны вовсе:
размер карты чужого проекта заранее не задать, а потолок брифа один
на все target. Правило `docs/triggers.md`: условие без наблюдателя не
срабатывает, а обнаруживается пробоем — сейчас ровно так.

Принцип: порог не константа, а собственная история target. Абсолютных
чисел про «нормальный размер карты» в задаче нет; есть измерение на
каждом мерже, окно калибровки и отклонение от медианы окна. Единственный
абсолютный порог остаётся прежним — потолок файла брифа.

Требуется:
1. Функция статистики карты в `scripts/codebase_map.py`: чистая
   `map_stats(map_text: str) -> dict` (без диска и git) — байт всего,
   байт проекции для брифа (`project_for_brief` из задачи
   01M1RFQ52S…; пока функции нет — поле отсутствует, не ноль), число
   секций, байт по каталогам верхнего уровня перечня (`orchestrator/`,
   `scripts/`, `tests/`), пять самых крупных секций с размерами.
   Формат — компактный JSON одной строкой, пригодный для поля `detail`
   журнала.
2. Измерение на каждом мерже: `fsm_postmerge._regenerate_and_commit_map`
   после регенерации (и когда содержательных отличий нет — тоже) пишет
   в журнал задачи запись `actor=orchestrator`, `action="карта: размер"`,
   `detail` = JSON из п.1 плюс sha коммита карты. Запись есть у КАЖДОГО
   мержа — ряд без пропусков; провал регенерации по-прежнему уходит в
   `_map_regen_incident`, записи размера в этом случае нет. Запись
   привязана к target задачи — ряд per-target по построению.
3. Оценка в `doctor` (наблюдатель ползучих порогов по `docs/triggers.md`):
   новая проверка `check_map_growth(conn)` по каждому target с рядом
   из п.2. Окно калибровки — первые `MAP_GROWTH_CALIBRATION_MERGES`
   записей (константа `config`, ориентир 8): пока ряд короче, проверка
   печатает «калибровка: N/8 измерений», алертов нет. После окна —
   два сигнала, оба относительные:
   - ползучий рост: байт полной карты последней записи больше медианы
     окна на `MAP_GROWTH_RATIO` (ориентир 0.25);
   - скачок: прирост между двумя соседними записями больше
     `MAP_JUMP_RATIO` (ориентир 0.10) байт предыдущей.
   Срабатывание — `alerts` kind=`trigger`, source `map.growth`, с
   атрибуцией в тексте: каталог верхнего уровня с наибольшим приростом
   и три самые крупные секции текущей карты с размерами. Дедуп
   встроенный (`alerts.raise_alert`); ack по правилу реестра триггеров
   обязан нести решение (проекция, деление модуля, вынос тестов из
   перечня, повышение окна). Проверка не трогает потолок
   `CONTEXT_FILE_MAX_BYTES` — он остаётся инцидентом брифа, как сейчас.
4. Следствие в деньгах, а не только в байтах: та же проверка печатает
   оценку «стоимость карты за шаг developer» = токены проекции (байт/3,
   без токенизатора) × медиана ходов developer за последние 10 задач
   (число вызовов инструментов из логов шага либо, если недоступно,
   константа-ориентир из `config` с пометкой «оценка») × курс кэш-чтения
   роли из `TOKEN_RATES`, плюс одно создание кэша. Число — ориентир для
   решения Оператора при ack, не порог.
5. Блок в `artel report`: по каждому target ряд последних 12 записей
   (дата мержа, байт всего, байт проекции, секций, байт по каталогам),
   медиана окна, открытые алерты `map.growth`, оценка из п.4. Пустой
   ряд — строка «измерений нет: карта ни разу не регенерировалась после
   мержа этой версией».
6. Внешний target: механизм ничего не знает о том, как у target
   появляется карта (ADR-0003 п.12 — фаза B); контракт один — текст
   карты в формате генератора и запись в журнал на мерже. Когда карта
   target появится, ряд начнётся с калибровки без единой правки здесь;
   первое измерение при подключении — пункт чек-листа B2 (строка в
   `docs/roadmap.md`, правит Оператор).
7. Тесты: `map_stats` на фикстурной карте трёх каталогов считает байты
   по каталогам и топ секций; постмержевой путь пишет запись размера и
   при изменившейся, и при неизменной карте, и не пишет при провале
   регенерации; doctor молчит в окне калибровки, поднимает trigger при
   росте выше `MAP_GROWTH_RATIO` и при скачке выше `MAP_JUMP_RATIO`,
   текст алерта называет каталог и три секции; повторный прогон не
   дублирует алерт; ряды двух target независимы (инвариант 22);
   report печатает ряд и «измерений нет» на пустом; константы
   читаются из `config`, не литералами (skills/test-authoring.md);
   существующие тесты `test_fsm_map_regen.py`, `test_doctor.py`,
   `test_report.py` зелёные без изменения ассертов.

Зоны: scripts/codebase_map.py (статистика), orchestrator/fsm_postmerge.py
(запись на мерже), orchestrator/doctor.py (проверка), orchestrator/
report.py (блок), orchestrator/config.py (константы), tests/. Пять
файлов зоны — сигнал «Оценки объёма»: analyst вправе разделить на две
части — (а) статистика + запись на мерже + doctor, (б) блок report и
оценка в деньгах; часть (б) без (а) смысла не имеет. Порядок: после
мержа 01M1RFQ52S… (поле проекции) и задач, держащих `doctor.py`
(стек S1/S3, критерий сироты) — сверить по `status` перед `new`.

Сопутствующие правки Оператора (не в задаче): строка №27 в
`docs/triggers.md` («рост карты кодовой базы; сигнал — ряд «карта:
размер» в журнале; наблюдает doctor, alerts kind=trigger»); пункт
«первое измерение карты target» в чек-лист B2 роадмапа §3.

Не входит: абсолютные пороги размера карты для любого target; изменение
потолков `CONTEXT_*`; генерация карты внешнего target (ADR-0003 п.12);
автоматические действия по алерту (проекция, деление модуля) — только
сигнал и атрибуция, решение за Оператором.
