# SPEC: Наблюдатель роста карты кодовой базы: история, самокалибрующийся порог, атрибуция

## Контекст
Сегодня у карты кодовой базы один абсолютный порог — потолок файла
брифа `config.CONTEXT_FILE_MAX_BYTES` (`brief._handle_map_size_alert`):
между «карта вписалась» и «карта выпала из брифа» механизм ничего не
видит — истории размера нет, темп роста не считается, атрибуция роста
к модулю неизвестна (`docs/triggers.md`: условие без наблюдателя не
срабатывает, а обнаруживается пробоем). Для внешних target (ADR-0003
п.12, фаза B) абсолютный порог и вовсе неизвестен заранее — нужен
порог, который калибруется по собственной истории каждого target, а
не по константе, общей на все target. Задача добавляет измерение
размера карты на каждом мерже, самокалибрующийся относительный порог
роста в `doctor` и атрибуцию срабатывания (какой каталог/секция
выросли), не трогая существующий абсолютный потолок брифа.

## Требования
1. Чистая функция `scripts/codebase_map.py::map_stats(map_text: str) ->
   dict` (без диска и git): общий размер карты в байтах, число секций,
   размер по трём каталогам верхнего уровня перечня (`orchestrator/`,
   `scripts/`, `tests/`), пять самых крупных секций с размерами;
   размер проекции для брифа — только если в `codebase_map.py` уже
   есть функция `project_for_brief` (задача 01M1RFQ52S0VD22J628TXX96XS;
   на момент написания этого SPEC функции нет — поле в словаре
   отсутствует, не 0). Результат сериализуется в компактный
   однострочный JSON, пригодный для поля `detail` записи журнала.
2. `orchestrator/fsm_postmerge.py::_regenerate_and_commit_map` после
   регенерации — и когда карта содержательно изменилась, и когда нет —
   пишет запись журнала `actor="orchestrator"`, `action="карта:
   размер"`, `detail` = JSON из требования 1 плюс sha коммита карты.
   Ряд записей идёт без пропусков; провал регенерации (путь
   `_map_regen_incident`) записи размера не создаёт. Запись несёт
   `target` задачи, чей merge её вызвал, — ряд per-target получается
   фильтрацией без отдельного кода привязки.
3. Новая проверка `orchestrator/doctor.py::check_map_growth(conn)` по
   каждому target с рядом из требования 2. Окно калибровки — ПЕРВЫЕ
   `config.MAP_GROWTH_CALIBRATION_MERGES` записей ряда (ориентир 8):
   пока ряд короче — «калибровка: N/8 измерений», без алертов. По
   достижении длины окна медиана `bytes_total` этих первых записей —
   ФИКСИРОВАННАЯ база сравнения (окно не скользит дальше при
   появлении новых записей — тот же принцип «однократно
   зафиксированного бейзлайна», что уже применяет `store.
   canary_baseline`/`set_canary_baseline`). Два относительных сигнала:
   ползучий рост (`bytes_total` последней записи выше медианы окна на
   `config.MAP_GROWTH_RATIO`, ориентир 0.25) и скачок (прирост между
   двумя соседними записями выше `config.MAP_JUMP_RATIO`, ориентир
   0.10, от значения предыдущей). Срабатывание — `alerts` `kind=
   trigger`, `source="map.growth"`, текст называет каталог верхнего
   уровня с наибольшим приростом и три самые крупные секции текущей
   карты. Дедуп — встроенный (`alerts.raise_alert`); ack по правилу
   реестра триггеров (`docs/triggers.md`) обязан нести решение.
   Проверка не трогает `config.CONTEXT_FILE_MAX_BYTES`.
4. Оценка «стоимость карты за шаг developer» в деньгах, не только в
   байтах: токены проекции (байт/3, без токенизатора; если поля
   проекции ещё нет — байт всей карты) × медиана числа вызовов
   инструментов агента `developer` по логам его шагов за последние 10
   задач (глобально по всем target — курс роли `TOKEN_RATES` один на
   все target уже сегодня, см. `orchestrator/config.py:363`), либо, при
   нехватке данных, константа-ориентир из `config` с пометкой «оценка»
   × курс кэш-чтения роли `developer` из `TOKEN_RATES`, плюс одно
   создание кэша (та же ставка `cache_creation`). Число — только
   ориентир для решения Оператора при `ack`, не порог и не источник
   алертов.
5. Блок в `artel report` (`orchestrator/report.py`): по каждому target
   — ряд последних 12 записей «карта: размер» (дата, байт всего, байт
   проекции, число секций, байт по каталогам), медиана окна
   калибровки, открытые алерты `map.growth`, оценка из требования 4.
   Target без единой записи — строка «измерений нет: карта ни разу не
   регенерировалась после мержа этой версией».
6. Внешний target: механизм не завязан на способ появления карты
   target — контракт один (текст в формате генератора + запись в
   журнал на мерже); специального кода под внешний target эта задача
   не пишет, ряд начинается с калибровки автоматически, когда первая
   запись появится (правка `docs/roadmap.md`/чек-листа B2 — отдельно,
   Оператором, не в этой задаче).
7. Тесты (`tests/`): `map_stats` на фикстурной карте трёх каталогов;
   постмерджевая запись — на изменённой и неизменной карте, и её
   отсутствие при провале регенерации; `doctor` — молчание в окне
   калибровки, срабатывание обоих сигналов, детерминированный текст с
   атрибуцией, отсутствие дубликата алерта при повторном прогоне;
   независимость рядов двух target (инвариант 22); `report` — ряд и
   «измерений нет»; константы читаются из `config`, не литералами;
   существующие `tests/test_fsm_map_regen.py`, `tests/test_doctor.py`,
   `tests/test_report.py` остаются зелёными без правки существующих
   ассертов.

## Критерии приёмки
AC-1. `scripts/codebase_map.py::map_stats(map_text: str) -> dict` —
чистая функция: не читает диск, не зовёт git, принимает только текст
карты.

AC-2. Результат `map_stats` содержит: `bytes_total` (размер текста
карты в байтах), `sections_total` (число секций верхнего уровня),
`bytes_by_dir` — байты по каждому из трёх каталогов перечня
(`orchestrator/`, `scripts/`, `tests/`), `top_sections` — пять самых
крупных секций с именем и размером в байтах по убыванию размера.

AC-3. Ключ `bytes_projection` присутствует в результате `map_stats`
ТОЛЬКО если в `scripts/codebase_map.py` определена функция
`project_for_brief`; на сегодняшний день (функции нет) ключ в словаре
отсутствует — не 0 и не `null`.

AC-4. `map_stats` сериализуется в компактный однострочный JSON (без
переносов строк и незначащих пробелов), пригодный для записи в поле
`detail` записи журнала.

AC-5. `fsm_postmerge._regenerate_and_commit_map` после регенерации
карты — независимо от того, был ли коммит сделан или откачен из-за
отсутствия содержательных отличий — пишет запись журнала
`store.journal(conn, task_id, "orchestrator", "карта: размер", detail)`,
где `detail` — JSON `map_stats(текст карты)` плюс поле с sha коммита
карты: HEAD-sha репозитория ПОСЛЕ завершения регенерации (новый
коммит карты, если он был сделан; иначе — тот же sha, что стоял до
вызова).

AC-6. Запись «карта: размер» есть у КАЖДОГО успешного мержа без
пропусков в ряду; при провале регенерации (путь `_map_regen_incident`)
запись размера не пишется — фиксируется только существующая
failure-запись журнала.

AC-7. Запись журнала несёт `target` задачи, чей merge её вызвал
(существующий механизм `store.journal`/`task_target`, без правки):
ряд измерений per-target получается фильтрацией записей действия
«карта: размер» по полю `target`.

AC-8. `orchestrator/doctor.py::check_map_growth(conn)` добавлена в
`all_checks(conn)`; для каждого target, у которого в журнале есть хотя
бы одна запись «карта: размер», строит хронологический ряд этих
записей.

AC-9. Пока длина ряда target меньше `config.MAP_GROWTH_CALIBRATION_MERGES`
(ориентир 8) — `Check` в статусе `ok` с текстом «калибровка: N/8
измерений» (N — фактическая длина ряда), алертов не заводит.

AC-10. Ряд достиг длины `MAP_GROWTH_CALIBRATION_MERGES` — окном
калибровки становятся ПЕРВЫЕ `MAP_GROWTH_CALIBRATION_MERGES` записей
ряда; медиана их `bytes_total` — фиксированная база сравнения, не
пересчитывается при появлении новых записей позже (окно не «скользит»).

AC-11. Ползучий рост: `bytes_total` ПОСЛЕДНЕЙ записи ряда превышает
медиану окна калибровки (AC-10) более чем на долю
`config.MAP_GROWTH_RATIO` (ориентир 0.25) — заводится алерт
`alerts.raise_alert(conn, target, "trigger", "map.growth", message)`.

AC-12. Скачок: `bytes_total` последней записи превышает `bytes_total`
предпоследней записи более чем на долю `config.MAP_JUMP_RATIO`
(ориентир 0.10) от значения предпоследней — заводится алерт тем же
способом (`kind=trigger`, `source=map.growth`), независимо от AC-11.

AC-13. Текст алерта в обоих случаях (AC-11/AC-12) называет: каталог
верхнего уровня перечня с наибольшим приростом байт между сравниваемыми
записями и три самые крупные секции из `top_sections` последней записи
с их размерами.

AC-14. Повторный прогон `doctor` без нового измерения в ряду не
заводит вторую копию алерта: дедуп `alerts.raise_alert` по (target,
kind, source, message); текст алерта, вычисленный из одного и того же
ряда, детерминирован — не содержит текущего времени или иной
меняющейся между прогонами величины.

AC-15. `check_map_growth` не читает и не изменяет
`config.CONTEXT_FILE_MAX_BYTES` и не влияет на алерт-инцидент брифа,
несущий этот потолок.

AC-16. Функция расчёта оценки «стоимость карты за шаг developer»
(`orchestrator/report.py`): `tokens` = (`bytes_projection` последней
записи ряда, если есть; иначе `bytes_total`) / 3; `calls` — медиана
числа вызовов инструментов агента `developer` по логам его шагов за
последние 10 задач глобально (по всем target); если данных
недостаточно — константа-ориентир из `config` с пометкой «оценка» в
комментарии; `cost_usd` = `tokens × calls ×
TOKEN_RATES["developer"]["cache_read_usd_per_token"] + tokens ×
TOKEN_RATES["developer"]["cache_creation_usd_per_token"]`.

AC-17. Оценка AC-16 не заводит алертов и не влияет ни на один переход
или гейт — только печатается как число-ориентир для решения Оператора
при `ack` алерта `map.growth`.

AC-18. `artel report` — новый блок по каждому target: таблица
последних 12 записей действия «карта: размер» (дата записи,
`bytes_total`, `bytes_projection` при наличии, `sections_total`,
`bytes_by_dir`), медиана окна калибровки (если уже посчитана — AC-10),
список открытых алертов `map.growth` этого target, оценка AC-16.

AC-19. Target без единой записи «карта: размер» в журнале — блок
печатает строку «измерений нет: карта ни разу не регенерировалась
после мержа этой версией» вместо таблицы, без ошибки.

AC-20. Ряды двух разных target независимы: запись, калибровка, алерт
и оценка одного target не читают и не меняют данные другого
(инвариант 22, `docs/invariants.md`).

AC-21. Существующие тесты `tests/test_fsm_map_regen.py`,
`tests/test_doctor.py`, `tests/test_report.py` остаются зелёными без
правки существующих ассертов — новые случаи добавляются отдельными
тестами.

AC-22. `MAP_GROWTH_CALIBRATION_MERGES`, `MAP_GROWTH_RATIO`,
`MAP_JUMP_RATIO` и константа-ориентир числа вызовов инструментов
developer (AC-16) объявлены в `orchestrator/config.py` и читаются
тестами через модуль (`config.ИМЯ`), не литералами
(skills/test-authoring.md).

## Оценка объёма и деление
Сработавшие сигналы подозрения на большой объём:
- **число затрагиваемых модулей/файлов зоны ≥ 5** — `zones:` несёт 6
  путей: `scripts/codebase_map.py`, `orchestrator/fsm_postmerge.py`,
  `orchestrator/doctor.py`, `orchestrator/report.py`,
  `orchestrator/config.py`, `tests/`.
- **число критериев приёмки ≥ 10** — 22 (AC-1..AC-22).
- **бюджет ≥ $30** — `budget_usd: 45` (рамка Оператора в ТЗ).

Решение — **нарезка на 2 подзадачи**, ровно по границе, которую ТЗ уже
называет («Пять файлов зоны — сигнал... вправе разделить на две
части»). Часть (б) без части (а) смысла не имеет — зависимость строго
однонаправленная, порядок между частями не альтернативен.

1. **«Наблюдатель роста карты: статистика, запись на мерже, doctor»**
   (требования 1–3, 6–7 в части своих тестов; AC-1..AC-15, AC-20,
   AC-21 в части `test_fsm_map_regen.py`/`test_doctor.py`, AC-22 в
   части `MAP_GROWTH_*`). Зоны: `scripts/codebase_map.py`,
   `orchestrator/fsm_postmerge.py`, `orchestrator/doctor.py`,
   `orchestrator/config.py`, `tests/`. Мержима первой и самостоятельно:
   заводит измерение, запись и наблюдатель порога без единой правки
   `report.py` — `artel report` до мержа части (б) просто не показывает
   новый блок, ничего существующего не ломает.
2. **«Наблюдатель роста карты: report-блок и оценка в деньгах»**
   (требования 4–5, 7 в части своих тестов; AC-16..AC-19, AC-21 в
   части `test_report.py`, AC-22 в части константы числа вызовов
   developer). Зоны: `orchestrator/report.py`, `orchestrator/config.py`,
   `tests/`. Зависит от части 1 (читает её ряд журнала и `bytes_total`/
   `bytes_projection` из её `detail`, показывает её открытые алерты
   `map.growth`) — без части 1 в журнале нет записей «карта: размер»,
   блок отчёта был бы вечно пуст.

Бюджет по частям — по рамке ТЗ: часть 1 — $25, часть 2 — $15 (обе
закладывают две итерации ревью, ориентир из skills/spec-authoring.md).

Заведение подзадачи под часть 2 — действие Оператора командой `cmd_new`
при подтверждении этого решения на гейте SPEC: эта аналитическая сессия
выписана в изолированном worktree задачи и не имеет доступа к живому
реестру задач пульта, подзадача отсюда не заводится; текстовая привязка
к родителю (01M1RFVWV6WWTXRC5F40K61632) — в ТЗ подзадачи. Эта же задача
(01M1RFVWV6WWTXRC5F40K61632) при принятии нарезки сужается на гейте до
части 1 (SPEC/AC/зоны/бюджет — до перечисленного в пункте 1 выше), по
образцу 01M1NKVPD2A79PQ6K0JVV1B2Q1 (коммит 630f00d7).

Отдельно от границы частей — ТЗ отмечает внешний порядок: старт части 1
(команда `new`/`run`) стоит сверить по `status` с мержем задачи
01M1RFQ52S0VD22J628TXX96XS (поле `project_for_brief`, AC-3) и с
задачами, держащими `orchestrator/doctor.py` (стек S1/S3) — сама SPEC
не требует их завершения (AC-3 корректна в обоих исходах), это
организационная заметка Оператору о зоне `doctor.py`, не требование
кода.

## Не входит
- Абсолютные пороги размера карты для любого target — только
  относительные (медиана/доля) сигналы.
- Изменение потолка `config.CONTEXT_FILE_MAX_BYTES` или любого другого
  потолка `CONTEXT_*` — остаётся ровно как есть, механизм его не
  трогает (AC-15).
- Генерация карты кодовой базы внешнего target (ADR-0003 п.12, фаза
  B) — контракт («текст в формате генератора + запись в журнал на
  мерже») уже общий, специального кода под внешний target эта задача
  не пишет.
- Автоматические действия по алерту `map.growth` (проекция, деление
  модуля, вынос тестов из перечня, повышение окна и т.п.) — только
  сигнал и атрибуция; решение и его текст при `ack` — за Оператором
  (`docs/triggers.md`).
- Правка `docs/triggers.md` (строка 27) и `docs/roadmap.md` (пункт
  чек-листа B2) — работа Оператора вне этой задачи (ТЗ, раздел
  «Сопутствующие правки Оператора»).
- Заведение подзадачи под часть 2 нарезки (`cmd_new`) — действие
  Оператора при подтверждении решения на гейте SPEC (см. «Оценка
  объёма и деление»); эта SPEC описывает разбиение, не выполняет его.
- Денежная оценка (AC-16/AC-17) как порог или условие алерта — только
  информационная величина при `ack`.
