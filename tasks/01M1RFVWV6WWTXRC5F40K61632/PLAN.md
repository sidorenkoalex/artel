# PLAN: Наблюдатель роста карты кодовой базы (часть а)

## Подход
Три независимых, но последовательно зависящих друг от друга слоя,
ровно по требованиям SPEC:

1. `scripts/codebase_map.py::map_stats(map_text)` — чистая функция:
   парсит уже готовый текст карты той же структурной опорой, что и
   приёмочные фикстуры (`## <путь>` до следующего `## ` или EOF),
   считает `bytes_total`/`sections_total`/`bytes_by_dir`/`top_sections`.
   `bytes_projection` кладётся только если `project_for_brief` уже
   существует в модуле (`globals().get(...)`, сегодня — нет, ключ
   отсутствует, AC-3).
2. `orchestrator/fsm_postmerge.py::_regenerate_and_commit_map` — после
   ветвления «изменилось/не изменилось содержимое» (существующий код,
   не трогается) добавляется ОДНА точка записи журнала: sha читается
   ОДИН раз, `gitcmd.head_sha(repo)`, ПОСЛЕ завершения git-операций
   (commit или checkout) — коммит уже сдвинул HEAD, если он был; текст,
   на котором считается `map_stats`, — регенерированный при изменении,
   исходный (`committed`) при откате (то, что реально осталось на
   диске). Точка записи — только на успешных ветках (после того как
   `add`/`commit` или `checkout` уже прошли без ошибки); ни в одной из
   веток `_map_regen_incident` запись не добавляется — они все
   заканчиваются `return` раньше.
3. `orchestrator/doctor.py::check_map_growth(conn)` — по каждому target
   с хотя бы одной записью «карта: размер» строит ряд `detail` этого
   target, отфильтрованный по точке отсчёта (последний `ack_ts` алерта
   `kind=trigger, source=map.growth` этого target, либо всё от начала).
   Пока записей после точки отсчёта НЕ БОЛЬШЕ `config.
   MAP_GROWTH_CALIBRATION_MERGES` (условие `len(series) <= K`, не `<
   K` — правка REVIEW итерации 1, R1-F2) — `ok`/«калибровка: N/K
   измерений», без алертов; ровно на K-й записи окно ещё не оценивает
   ряд, чтобы не сравнивать завершающую калибровку запись с базой,
   посчитанной с её же участием (самоссылочность). Начиная с (K+1)-й
   записи окно калибровки ФИКСИРУЕТСЯ как первые K записей после точки
   отсчёта (`series[:K]`, не пересчитывается при появлении новых
   записей); медиана их `bytes_total` — база сравнения. Два сигнала
   считаются независимо от последней записи ряда:
   ползучий рост — против медианы окна; скачок — против
   ПРЕДПОСЛЕДНЕЙ записи ряда (не окна). Сработал любой — единое
   детерминированное сообщение (без времени/id), заводится
   `alerts.raise_alert(..., "trigger", "map.growth", message)` — дедуп и
   неповторяемость по одному и тому же ряду достаются от самого
   `raise_alert`, не пишутся заново. Атрибуция каталога — по разнице
   `bytes_by_dir` между последней записью и записью сравнения (skачок —
   предпоследняя; чистый ползучий рост без соседней — первая запись
   окна); три первых элемента `top_sections` последней записи.
4. `orchestrator/config.py` — три новые константы рядом с
   `CONTEXT_FILE_MAX_BYTES`/`TOKEN_RATES`: `MAP_GROWTH_CALIBRATION_
   MERGES = 8`, `MAP_GROWTH_RATIO = 0.25`, `MAP_JUMP_RATIO = 0.10` —
   ориентиры SPEC буквально.

Внешний target (требование 4) — специального кода не пишется:
контракт (текст в формате генератора + запись журнала на мерже) уже
общий для любого target, ряд стартует калибровкой на первой же записи
без правки этой задачи.

## Влияние на систему
Новый код только добавляет: `map_stats` — чистая функция без побочных
эффектов, не меняет поведение `codebase_map.main`/`render`/CI-джоба
свежести карты. Запись «карта: размер» — новая строка журнала на
каждом успешном мерже; не меняет существующие журнальные записи и не
влияет на `_map_content_without_sha`/логику коммита/отката —
подтверждено существующими тестами `test_fsm_map_regen.py`, которые
не проверяют отсутствие такой записи и остаются зелёными без правки.
`check_map_growth` — новая независимая проверка `all_checks`; статус
`warn` (не `fail`) не блокирует код возврата `doctor` и не может
провалить существующие тесты, фильтрующие проверки по имени
(`test_broken_repo_output_names_the_reasons` и подобные, сверено
чтением). Не трогает `config.CONTEXT_FILE_MAX_BYTES` и не заводит
incident брифа (AC-15, проверяется текстовым поиском в тесте). Ряды
target читаются `WHERE target=?` — не пересекаются (AC-16, инвариант
22). Откат — правки локальны в трёх файлах и трёх новых константах,
`git revert` коммита достаточен.

## Риски
- Формат `detail` (JSON-схема `map_stats` + `sha`) — локальная
  конкретизация теста (SPEC не называет точных имён полей сверх
  `bytes_total`/`sections_total`/`bytes_by_dir`/`top_sections`/
  `bytes_projection`); приёмочные тесты уже зафиксировали именно эту
  схему — код обязан ей буквально соответствовать, отклонение — не
  вариант интерпретации, а расхождение с локом.
- Атрибуция каталога роста для одновременного срабатывания обоих
  сигналов не специфицирована тестами буквально (SPEC/тесты намеренно
  строят фикстуры так, чтобы сигналы не пересекались) — выбранное
  правило (сравнение с предпоследней записью, либо с первой записью
  окна для чистого ползучего роста без обоих) детерминировано и не
  противоречит ни одному критерию, но это конкретизация developer, не
  SPEC.
- (снят в итерации 1 по REVIEW, R1-F2) Граница ровно `k` записей —
  самоссылочная база сравнения при условии `len(series) < k` (k-я
  запись оценивалась против окна, включающего её саму). Решение:
  условие заменено на `len(series) <= k`, оценка стартует с (k+1)-й
  записи; добавлен юнит `test_exact_calibration_length_is_still_silent`
  (`tests/test_doctor.py`, класс `MapGrowthCheckTest`), воспроизводящий
  сценарий ревью и подтверждающий отсутствие алерта на k-й записи.
- (снят после возврата из verifying, CI: `tests/test_multitarget
  SqlOnlyInStoreTest`) `_map_growth_reference_point`/`_map_growth_series`
  и `check_map_growth` читали `alerts`/`steps` прямой SQL в
  `orchestrator/doctor.py` — нарушение инварианта «SQL только в
  store.py» (ADR-0003 3ж); `store.py` вне зон этой задачи, поэтому
  новую функцию туда не добавляли. Решение: три места переписаны на
  композицию уже существующих функций store в Python —
  `store.all_tasks`/`store.task_steps` (собрать записи «карта: размер»
  по всем задачам, отфильтровать по target и action в Python; порядок
  сохраняется сортировкой по общему автоинкременту `steps.id`) и
  `store.alerts_older_than(conn, <sentinel в будущем>)` (получить все
  алерты и отфильтровать по target/kind/source/ack_ts в Python — приём
  предложен в причине возврата). Прямой SQL в `orchestrator/*.py` вне
  `store.py` отсутствует (`SqlOnlyInStoreTest.test_no_sql_outside_store`
  зелёный); поведение не изменилось — вся приёмочная планка
  (`tests/test_doctor.py`, `tests/test_fsm_map_regen.py`,
  `tests/test_codebase_map.py`, `tests/test_multitarget_invariants.py`,
  `tasks/01M1RFVWV6WWTXRC5F40K61632/acceptance_tests/`) зелёная.
