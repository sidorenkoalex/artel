# SPEC: Отказ advance доносится до следующего запуска роли

## Контекст

Роадмап, P3-строка «Отказ advance не доносится до следующего запуска
роли». Фактура T069 (29.08): после «переход отклонён: трассируемость
AC» повторный запуск test_author не получил причину отказа в промпт —
прогон шёл вслепую по исходному брифу, роль перечитала свои файлы
и заключила «всё сделано, менять нечего» ($1.23 холостых). Стык
со стоп-краном T038 (ловит повторные ОТКАЗЫ advance двух подряд шагов
`auto` и останавливает цикл, но роль между попытками так и не узнаёт,
что чинить) — эта задача чинит именно пробел с той стороны, откуда
роль получает контекст для следующей попытки.

## Требования

1. Бриф роли, запускаемой в состоянии, из которого предыдущий advance
   этой задачи был отклонён guard'ом/условием перехода (журнальная
   запись с полем `action`, начинающимся с «переход отклонён»),
   включает последние такие записи журнала ИМЕННО по этому состоянию —
   текст причины целиком, как его печатает guard/условие перехода
   (адреса файлов и требований).
2. Блок с причиной(ами) отказа несёт явную рамку «предыдущая попытка
   сдать шаг отклонена вот почему — почини это» (или формулировка той
   же смысловой рамки).
3. Записей может быть несколько — включаются N последних по состоянию,
   с разумным потолком, чтобы бриф не разбухал бесконтрольно.
4. Отказы другого состояния той же задачи и отказы других задач в
   бриф не попадают.
5. Если по текущему состоянию задачи отказов advance не было — бриф
   не меняется вовсе (ноль регрессии для чистого пути).

## Критерии приёмки

AC-1. Сценарий T069: после отклонённого advance следующий запуск роли
того же состояния несёт в собранном промпте шага причину отказа (текст
журнальной записи «переход отклонён»), проверяемо по собранному
промпту шага.

AC-2. Запуск роли в состоянии без предыстории отказов advance — бриф
не содержит нового блока причины отказа.

AC-3. Отказы другого состояния той же задачи и отказы других задач не
просачиваются в бриф роли, запускаемой в конкретном состоянии.

AC-4. Полный тестовый набор (`tests/`) зелёный.

## Не входит

- Механика самих отказов advance и guard, включая тексты сообщений,
  которые они печатают/журналируют (соседняя задача ревизии guard) —
  используются как есть.
- ANSWER-механика (T075) — канал Оператора при эскалации; здесь речь о
  доставке машинного отказа guard той же роли без участия Оператора,
  ANSWER не дублируется и не подменяется.
- Ослабление стоп-крана T038 (потолок топтания `auto` по повторным
  ОТКАЗАМ advance) — правило T038 сохраняется как есть.
