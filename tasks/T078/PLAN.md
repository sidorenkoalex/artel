# PLAN: Отказ advance доносится до следующего запуска роли

## Подход

Журнал шагов (`steps`) уже несёт всё нужное: `store.set_state` пишет
запись `action="state -> {state}"` на КАЖДОМ переходе FSM (включая вход
в состояние, из которого потом отказывает advance), а сами отказы уже
журналируются `fsm.py` записями `action` вида `"переход отклонён..."`
(`guard_refuses`, `_cmd_advance` — трассируемость AC, приёмочные тесты,
чужая ветка и т.д.). Задача — прочитать эти записи при сборке промпта
следующего запуска той же роли и включить их в бриф с явной рамкой,
если они есть.

Скоуп по состоянию (требования 1, 4) без новой колонки в БД: нижняя
граница выборки — id ПОСЛЕДНЕЙ записи `"state -> {текущее состояние}"`
этой задачи. Всё, что журналируется после неё и до следующего перехода,
по построению происходит, пока задача находится именно в этом
состоянии (отказ advance state не меняет). У первого состояния задачи
(`spec_writing`, задача рождается в нём напрямую через `insert_task`,
не через `set_state`) такой записи никогда нет — граница 0, отбираются
все отказы задачи, что корректно: раньше первого состояния задача не
существовала. Ревизит того же состояния позже (например, `review`
после `changes_requested -> in_dev -> review`) автоматически отсекает
отказы прошлого визита — новая запись `state -> review` сдвигает
границу вперёд.

Фильтр по задаче (требование 4, чужая задача) — обычный `task_id=?`,
он уже есть у `store.task_steps`.

Новая функция `store.refusal_history(conn, task_id, state, limit)`
инкапсулирует эту выборку (тот же принцип, что и остальной доступ к
`steps` — только через `store.py`, минуя сырой SQL в других модулях).
Новая функция `brief.advance_refusal_history(conn, task_id, role, state)`
форматирует найденные записи в блок с рамкой требования 2 (или
возвращает `""` — требование 5, ноль регрессии) и журналирует свой
компонент тем же приёмом, что и остальные компоненты брифа
(`brief._journal_component`).

Точка подключения — не разбор по ролям (`role == "test_author"`/
`"developer"` и т.д. в `runner._cmd_run`, как показывает SPEC на
`orchestrator/runner.py`), а ОДНО место сразу после сборки `prompt`
для всех ветвей: механика «отказ advance для этого состояния» не
зависит от роли, читающей бриф, и раздельное подключение к каждой
ветке `if role == ...` дублировало бы один и тот же вызов четыре раза.
Ровно это и чинит пробел SPEC: `test_author` в `tests_writing` сегодня
вообще не получает `brief_text` (веткa `role == "test_author"` его не
собирает) — единая точка после сборки `prompt` покрывает и её тоже,
без отдельной правки текста миссии test_author.

## Шаги

1. `orchestrator/store.py`: `refusal_history(conn, task_id, state, limit)`
   — выборка записей `"переход отклонён..."` этой задачи, ограниченная
   текущим визитом состояния (граница — последняя `"state -> {state}"`),
   с потолком `limit`, в хронологическом порядке.
2. `orchestrator/brief.py`: `advance_refusal_history(conn, task_id, role,
   state)` — форматирование в блок с рамкой требования 2 или `""`;
   журналирование компонента через `_journal_component`. Константа
   потолка записей (требование 3).
3. `orchestrator/runner.py` (`_cmd_run`): после сборки `prompt` (после
   ветки `package`, до цикла попыток) — вызов `brief.advance_refusal_history`
   и добавление блока к `prompt`, если он не пуст.
4. Юнит-тесты: `store.refusal_history` (скоуп по состоянию, потолок,
   хронологический порядок, задача без записей) и
   `brief.advance_refusal_history` (пустая история → `""`, непустая →
   рамка + текст детали + журнал компонента).

## Влияние на систему

Новый код только читает `steps` и добавляет текст к промпту — не
меняет ни один существующий переход, guard, лимит или тест. Стоп-кран
T038 (потолок топтания `auto` по повторным ОТКАЗАМ advance) не
трогается: эта задача не меняет условие остановки `auto`, только даёт
роли увидеть причину раньше следующей попытки — стоп-кран остаётся
прежним подстраховочным потолком на случай, если роль всё равно не
справится.

Потолок записей (`ADVANCE_REFUSAL_LIMIT`) — константа в коде, не в
SPEC/ADR: значение мягкое (не инвариант, не лимит из docs/invariants.md),
меняется как обычная правка кода при необходимости.

Откат: удаление вызова в `runner._cmd_run` и двух новых функций —
чистая правка, никакая существующая колонка/таблица не тронута.

## Риски

- Формат блока (рамка + текст) — из своего понимания требования 2, не
  зафиксирован SPEC буквально одной строкой; текст рамки взят близко
  к формулировке SPEC/ТЗ.
