# SPEC: Автор коммитов пульта для проекта на GitLab: автопоиск, сторож, отказ new, сверка перед отправкой

## Контекст
Поле `machine.commit_author` (`{name, email}`, `orchestrator/targets.py:715-720`)
задаёт автора коммитов пульта и ролей проекта. Читают его
`gitcmd.commit_author` / `pult_identity` / `pult_identity_args`
(`orchestrator/gitcmd.py:559-582`). Поле необязательно: без него коммиты
подписаны автором по умолчанию (`fixation.FIXATION_AUTHOR_EMAIL`). GitLab
с серверным хуком `pre-receive` отклоняет push, если email нового
коммита не совпадает с адресом учётной записи отправителя. Для бота
токена проекта это `commit_email` пользователя токена. 06.11 первая
задача внешнего проекта успела сделать пять коммитов с автором по
умолчанию до первой отправки. Отправку отклонили, задачу закрыли
обходом. Задача должна поймать неверного автора раньше: автопоиск
адреса в `doctor --fix`, сторож в `doctor`, отказ `new` и сверка в
единой точке отправки `gitcmd._push_plan` (`orchestrator/gitcmd.py:1264`).

## Требования

1. **Адрес учётной записи токена.** `forge.TokenUser`
   (`orchestrator/forge.py:96`) несёт, кроме `username`, поля `name` и
   `commit_email`. Адаптер GitLab (`gitlab_adapter.token_user`) кладёт в
   `commit_email` поле `commit_email` ответа `GET /user`, а если его
   нет — поле `email` того же ответа. Прочие адаптеры новые поля не
   заполняют.
2. **Автопоиск в `doctor --fix`.** Условие: проект с `forge: gitlab` и
   `token_slot`, у записи нет `machine.commit_author`. Тогда
   `doctor --fix` записывает в локальный слой `machine.commit_author` =
   `{name: <name пользователя токена>, email: <commit_email>}`. Запись
   идёт путём `target-set` (`orchestrator/projects.py`:
   `_target_set_load`, `_rendered`, `_target_set_write`): копия прежнего
   файла, сверка до записи, строка журнала. Если в ответе API нет
   адреса или API отказал, запись не делается, а строка `doctor`
   называет причину. Уже заданный `commit_author` автопоиск не
   перезаписывает.
3. **Сторож в `doctor`.** Новая проверка `project-commit-author-<проект>`
   для проекта с `forge: gitlab` и `token_slot`:
   - `ok` — `commit_author.email` равен адресу учётной записи токена;
   - `fail` — поле не задано, текст «автор коммитов не задан: doctor --fix»;
   - `fail` — адрес другой, текст «токен сменился или автор задан
     неверно: <записано> против <адрес токена>; doctor --fix не
     перезаписывает — правка target-set»;
   - `warn` — API не ответил или не дал адреса.

   Значения токена в вывод не попадают.
4. **Отказ `new`.** `new --target <проект>` для проекта, на котором
   проверка требования 3 даёт `fail`, отказывает текстом этой проверки.
   Отказ происходит до создания задачи и артефактной ветки. При `warn`
   (API не ответил) задача заводится, в выводе — предупреждение.
5. **Сверка перед отправкой.** Условие: проект под белым списком с
   заданным `commit_author`, отправка идёт через `_push_plan`. Сверке
   подлежит каждый отправляемый коммит, которого ещё нет в origin, то
   есть он не достижим ни из текущего значения назначения в origin, ни
   из ссылок слежения `refs/remotes/origin/*`. У такого коммита email
   автора и email коммитера обязаны быть равны `commit_author.email`.
   Иначе отправка отказывает до вызова git. Текст отказа перечисляет sha
   несовпавших коммитов и их адреса: не больше 10, остальные — «и ещё N».
   Удаление (`--delete`, `:<ветка>`) сверку не проходит.
6. У проектов без `commit_author` и у проекта артели отправка ведёт
   себя как прежде. Прежние отказы белого списка не меняются: ни их
   порядок, ни тексты. Новая сверка идёт после них.

## Критерии приёмки

AC-1. Подменённый ответ `GET /user` с `name` и `commit_email`:
`gitlab_adapter.token_user` возвращает `TokenUser` с этими `name` и
`commit_email`. Ответ без `commit_email`, но с `email`: в `commit_email`
стоит `email`. Ответ без обоих: адреса нет. Адаптеры других хостингов
поля `name`/`commit_email` не заполняют.

AC-2. Вымышленная запись GitLab с `token_slot`, без `commit_author`, ответ
`GET /user` подменён (`name`, `commit_email`). После `doctor --fix` в
разобранном локальном слое `machine.commit_author` = `{name: <name>,
email: <commit_email>}`, рядом создана копия прежнего файла, в журнале —
строка записи. Повторный `doctor --fix` слой не меняет.

AC-3. Ответ `GET /user` без `commit_email`, но с `email`: `doctor --fix`
записывает `email`. Ответ без обоих адресов или отказ API: файл
локального слоя побайтно прежний, строка `doctor` называет причину.

AC-4. Проверка `project-commit-author-<проект>`:
- `commit_author.email` равен адресу токена — `ok`;
- адрес другой — `fail`, в тексте записанный адрес и адрес токена;
  `doctor --fix` поле не меняет;
- поля нет — `fail` с подсказкой `doctor --fix`;
- API не ответил — `warn`.

Ни в одном исходе значение токена в выводе не встречается.

AC-5. Проверка требования 3 для проекта даёт `fail`. Тогда
`new --target <проект>` отказывает текстом проверки, задачи в БД нет,
артефактной ветки (ссылки документов) нет.

AC-6. Проверка требования 3 даёт `warn` (API не ответил). Тогда
`new --target <проект>` заводит задачу, в выводе есть предупреждение.

AC-7. Клон с двумя недосланными коммитами, у одного из них чужой адрес
автора (или коммитера); у проекта белый список и `commit_author`.
Отправка через `_push_plan` отказывает до вызова git, отказ называет sha
и адрес чужого коммита. Если таких коммитов больше 10, перечислены 10,
дальше «и ещё N».

AC-8. Все недосланные коммиты с адресом `commit_author`: отправка идёт.
Коммиты, уже достижимые из значения назначения в origin или из
`refs/remotes/origin/*`, сверку не проходят, даже если адрес у них
чужой. Удаление (`--delete`, `:<ветка>`) проходит без сверки.

AC-9. Проект без `commit_author` и проект артели: решение `_push_plan`
то же, что до задачи. Прежние отказы белого списка срабатывают раньше
новой сверки, с прежними текстами.

## Оценка объёма и деление

Сработавший сигнал: 7 файлов кода в зоне (порог
`SPLIT_SIGNAL_ZONE_FILES` = 5): `forge.py`, `gitlab_adapter.py`,
`doctor/project_checks.py`, `doctor/cli.py`, `projects.py`, `catalog.py`,
`gitcmd.py`. Число критериев (9) и бюджет ($45) порогов не достигают.

Материал для решения Оператора, монолит или нарезка:
- Требования 1–4 опираются на одно и то же: адрес токена (требование 1)
  и проверку требования 3. Ту же проверку запускают `doctor`,
  `doctor --fix` (требование 2, условие «поля нет») и `new`
  (требование 4). Резать эту часть по файлам нельзя: проверка без
  адаптера ничего не сверит, а отказ `new` без проверки не на что
  опереть.
- Требования 5–6 (`gitcmd._push_plan`) от требований 1–4 по коду не
  зависят: они читают только уже существующее поле `commit_author`
  (`gitcmd.commit_author`). Их можно выделить в самостоятельно мержимую
  подзадачу с зоной `orchestrator/gitcmd.py`.
- Против нарезки — цена. Каждая подзадача проходит свои шаги
  analyst/test_author/developer/reviewer, планка не ниже $25. Две части
  стоят ≥ $50 при рамке Оператора $45 на всю задачу. В части 1 всё
  равно остаётся 6 файлов зоны, то есть тот же сигнал.

Предложение аналитика — монолит. Механику нельзя разрезать атомарно
только в части требований 1–4; требования 5–6 отделимы, но деление
дороже рамки. Решение — за Оператором на гейте SPEC.

## Не входит

- Автопоиск и сторож для GitHub и других хостингов (адаптеры, кроме
  GitLab, новые поля `TokenUser` не заполняют — требование 1).
- Переподпись уже сделанных коммитов.
- Исключение для коммитов после rebase/cherry-pick (AuthorDate ≠
  CommitDate): сверка требования 5 его не делает.
- Правка `docs/target-onboarding.md` — документ Оператор правит отдельно.
- Правка настоящего локального слоя `.artel/targets.yaml` в тестах и при
  разработке. Записи, слой и клоны — вымышленные, во временной песочнице
  (`tests.sandbox`). Ответ API подменяется через
  `gitlab_adapter.request`/транспорт, без сети. Отправка идёт в локальный
  голый репозиторий-дублёр origin. Связку ключей тесты не трогают.
- Правка файлов «только чтение» ТЗ: `orchestrator/targets.py`,
  `orchestrator/runner.py`, `orchestrator/artifact_branch.py`,
  `orchestrator/github_adapter.py`, `orchestrator/artel.py`,
  `tests/sandbox.py`.
- «Существующие тесты — зелёные без правки» — эту проверку держит пульт.
  Правка ожиданий существующих тестов этой задачей не заказана, раздела
  «Меняемое поведение» нет. По ТЗ, если существующий тест краснеет
  (например, тест заводит задачу `new` на вымышленной записи GitLab с
  `token_slot` без `commit_author` или сверяет точный перечень проверок
  `doctor`), разработчик эскалирует с именем теста и тест не правит.
