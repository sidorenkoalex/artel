# SPEC: Автор коммитов пульта для проекта на GitLab: автопоиск, сторож, отказ new

## Контекст
Поле `machine.commit_author` (`{name, email}`, `orchestrator/targets.py:715-720`)
задаёт автора коммитов пульта и ролей проекта. Читают его
`gitcmd.commit_author` / `pult_identity` / `pult_identity_args`
(`orchestrator/gitcmd.py:559-582`). Поле необязательно: без него коммиты
подписаны автором по умолчанию (`fixation.FIXATION_AUTHOR_EMAIL`). GitLab
с серверным хуком `pre-receive` отклоняет push, если email нового
коммита не совпадает с адресом учётной записи отправителя. Для бота
токена проекта это `commit_email` пользователя токена. 06.11 первая
задача внешнего проекта успела сделать пять коммитов с автором по
умолчанию до первой отправки. Отправку отклонили, задачу закрыли
обходом. Задача должна поймать неверного автора до заведения задачи:
автопоиск автора в `doctor --fix`, сторож в `doctor` и отказ `new`.

Имя автора — логин владельца токена (`username`), не отображаемое имя:
сверка автора перед первой отправкой ветки задачи уже требует
`commit_author.name == username` (`gitcmd._author_check_refusal`,
`orchestrator/gitcmd.py:625-660`). 06.11 задача внешнего проекта с
отображаемым именем бота в `commit_author.name` была эскалирована
отказом этой сверки (решение Оператора 1 на гейте SPEC).

## Требования

1. **Адрес учётной записи токена.** `forge.TokenUser`
   (`orchestrator/forge.py:96`) несёт, кроме `username`, поля `name` и
   `commit_email`. Адаптер GitLab (`gitlab_adapter.token_user`) кладёт в
   `commit_email` поле `commit_email` ответа `GET /user`, а если его
   нет — поле `email` того же ответа. Прочие адаптеры новые поля не
   заполняют.
2. **Автопоиск в `doctor --fix`.** Условие: проект с `forge: gitlab` и
   `token_slot`, у записи нет `machine.commit_author`. Тогда
   `doctor --fix` записывает в локальный слой `machine.commit_author` =
   `{name: <username пользователя токена>, email: <commit_email, иначе
   email>}`. Уже заданный `commit_author` автопоиск не перезаписывает.
   Если в ответе API нет адреса или API отказал, запись не делается, а
   строка `doctor` называет причину.
3. **Запись поля для `doctor --fix`.** Запись идёт путём `target-set`
   (`orchestrator/projects.py`: `_target_set_load`, `_rendered`,
   `_target_set_write`) функцией, которая возвращает причину отказа, а
   не завершает процесс: `sys.exit` хелперов `target-set` в `doctor` не
   зовётся. Функция делает:
   - копию прежнего файла в `config.LOGS` (как `_backup_copy`,
     `orchestrator/projects.py:986`);
   - сверку до записи, где изменённым листом считается отображение
     `machine.commit_author` целиком, а не один лист (сейчас сверка
     `target-set` требует ровно один изменённый лист,
     `orchestrator/projects.py:889-893`);
   - строку журнала о записи.

   Отказ записи — строка `doctor` с причиной. `doctor` после неё
   продолжает прочие проверки.
4. **Сторож в `doctor`.** Новая проверка `project-commit-author-<проект>`
   для проекта с `forge: gitlab` и `token_slot`:
   - `ok` — `commit_author.name` равен `username` владельца токена и
     `commit_author.email` равен адресу его учётной записи
     (требование 1);
   - `fail` — поле не задано, API ответил: текст «автор коммитов не
     задан: doctor --fix»;
   - `fail` — имя или адрес не совпадает (любой из двух): текст
     называет записанное и значение токена для каждого несовпадения и
     содержит «doctor --fix не перезаписывает — правка поля
     machine.commit_author локального слоя Оператором»;
   - `warn` — API не ответил или не дал адреса (при заданном поле и
     при его отсутствии).

   Значения токена в вывод не попадают. В процессе роли проверка
   пропускается (`skip`, `ROLE_SKIP`), как прочие проверки проекта
   (`orchestrator/doctor/project_checks.py:53-66`).
5. **Отказ `new`.** `new --target <проект>` для проекта, на котором
   проверка требования 4 даёт `fail`, отказывает текстом этой проверки.
   Отказ происходит до создания задачи и артефактной ветки и идёт после
   прежней проверки поддержки проекта (`targets.unsupported_reason`,
   `orchestrator/catalog.py:856`): у неподдержанного проекта отказ —
   прежний. При `warn` задача заводится, в выводе — предупреждение.
6. **Существующие тесты.** Существующим тестам, чьи вымышленные записи
   GitLab без `commit_author` заводят задачи, разрешено добавить в эти
   записи поле `machine.commit_author` с адресом, равным адресу
   подменённого владельца токена, — и только это. Утверждения, имена
   тестов и прочие поля записей не меняются. Мандат Оператора (ANSWER-1,
   решение 2 на гейте SPEC) — на два файла:
   `tests/test_01m6ezxvfg405y1btfdsgbks8e_pair_support.py`,
   `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py`.
7. **Отправка проектов — прежняя.** `orchestrator/gitcmd.py` в задаче
   не правится (кроме чтения `token_user` через адаптер). Сверка автора
   недосланных коммитов в `_push_plan` не добавляется.

## Критерии приёмки

AC-1. Подменённый ответ `GET /user` с `username`, `name` и
`commit_email`: `gitlab_adapter.token_user` возвращает `TokenUser` с
этими `username`, `name` и `commit_email`. Ответ без `commit_email`, но
с `email`: в `commit_email` стоит `email`. Ответ без обоих: адреса нет.
Адаптеры других хостингов поля `name`/`commit_email` не заполняют.

AC-2. Вымышленная запись GitLab с `token_slot`, без `commit_author`, ответ
`GET /user` подменён, `username` и `name` в нём различны. После
`doctor --fix` в разобранном локальном слое `machine.commit_author` =
`{name: <username>, email: <commit_email>}`; копия прежнего файла
создана в `config.LOGS`; в журнале — строка записи. Повторный
`doctor --fix` слой не меняет.

AC-3. Ответ `GET /user` без `commit_email`, но с `email`: `doctor --fix`
записывает `email`. Ответ без обоих адресов, отказ API или отказ записи
(сверка до записи не прошла): файл локального слоя побайтно прежний,
строка `doctor` называет причину, процесс не завершается, прочие
проверки `doctor` выполнены и выведены.

AC-4. Проверка `project-commit-author-<проект>` (ответ API подменён,
`username` и `name` различны):
- `commit_author.name` = `username`, `commit_author.email` = адрес
  токена — `ok`;
- адрес другой — `fail`, в тексте записанный адрес и адрес токена;
- адрес совпадает, имя другое (в том числе равно `name`, а не
  `username`) — `fail`, в тексте записанное имя и `username`;
- при обоих `fail` о несовпадении — `doctor --fix` поле не меняет,
  текст содержит «doctor --fix не перезаписывает — правка поля
  machine.commit_author локального слоя Оператором»;
- поля нет, API ответил — `fail` с подсказкой `doctor --fix`;
- API не ответил или не дал адреса — `warn`;
- в процессе роли — `skip`.

Ни в одном исходе значение токена в выводе не встречается.

AC-5. Проверка требования 4 для проекта даёт `fail` (поле не задано, API
ответил, либо несовпадение). Тогда `new --target <проект>` отказывает
текстом проверки, задачи в БД нет, артефактной ветки (ссылки
документов) нет. У проекта, который отказывает по
`targets.unsupported_reason`, текст отказа `new` — прежний.

AC-6. Проверка требования 4 даёт `warn` (поле не задано, API не
ответил). Тогда `new --target <проект>` заводит задачу, в выводе есть
предупреждение.

AC-7. Отправка проектов — прежняя: в `orchestrator/gitcmd.py` ветки нет
изменений относительно базы (диф ветки по файлу пуст), сверка автора
недосланных коммитов в `_push_plan` не добавлена.

## Решения Оператора на гейте SPEC

- Решение 1 (имя = `username`; сторож сверяет имя и адрес) —
  требования 2, 4; проверяется AC-1, AC-2, AC-4 (подменённый ответ, где
  `username` и `name` различны; `fail` при совпадающем адресе и другом
  имени). Дублёр — вымышленный локальный слой и подменённый ответ API
  во временной песочнице. Сверено с кодом: `_author_check_refusal`
  (`orchestrator/gitcmd.py:625-660`) отказывает при
  `commit_author.name != username`.
- Решение 2 (требование отказа `new` сохраняется; мандат на фикстуры
  двух тестов; `fail`/`warn` при отсутствии поля) — требования 5, 6;
  проверяется AC-5, AC-6. Дублёр — вымышленный локальный слой во
  временной песочнице.
- Решение 3 (сверка в `_push_plan` снята) — требование 7, «Не входит»;
  проверяется AC-7, файлов не меняет. В решении критерий назван AC-9 —
  после снятия прежних AC-7…AC-9 нумерация сквозная, это AC-7.
- Решение 4 (запись функцией с причиной отказа, без `sys.exit`; копия в
  `config.LOGS`; сверка по отображению целиком; текст `fail`; пропуск в
  роли; порядок после `unsupported_reason`) — требования 3, 4, 5;
  проверяется AC-2, AC-3, AC-4, AC-5. Дублёр — вымышленный локальный
  слой во временной песочнице. Сверено с кодом:
  `orchestrator/projects.py:889-893` (один лист), `:986` (копия в
  `config.LOGS`), `orchestrator/doctor/project_checks.py:53-66` (пропуск
  проверок проекта в роли).

- Все требования опираются на одно: адрес и логин токена (требование 1)
  и проверку требования 4. Ту же проверку запускают `doctor`,

  решением Оператора 3, других независимых кусков нет. Деление дало бы
  части по $25+ каждая при рамке $45 на всю задачу.
