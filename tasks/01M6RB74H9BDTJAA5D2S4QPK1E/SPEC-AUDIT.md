## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да | `commit_email` без запасного `email`; адрес из `public_email`; `name` подставлен в `username`; поля заполнены у GitHub. До кода: у `TokenUser` нет `name`/`commit_email` — красный, без побочных эффектов |
| AC-2 | да | в `name` пишется отображаемое имя (ответ, где `username` ≠ `name`); нет копии в `config.LOGS`; нет строки журнала; повтор перезаписывает или плодит копии. До кода: слой не меняется — красный |
| AC-3 | частично (В-1) | API отказал, а слой всё равно переписан; `sys.exit` при отказе обрывает `doctor`. Ветку «сверка до записи не прошла» снаружи вызвать нечем — см. В-1 |
| AC-4 | да | сверяется только адрес; при несовпадении `doctor --fix` перезаписывает поле; в тексте нет обоих значений; значение токена (`test-token-<слот>` песочницы, `tests/sandbox.py:657-660`) попадает в вывод; в роли нет `skip` |
| AC-5 | да | проверка стоит после создания строки `tasks` или ссылки документов; проверка поставлена раньше `unsupported_reason` — текст у неподдержанного меняется. До кода: `new` заводит задачу — красный |

В-1 (AC-3). У исхода «отказ записи (сверка до записи не прошла)» нет
внешнего способа вызвать отказ. При правильной сборке текста сверка
по построению проходит. Тест, написанный до кода, может уронить её только
подменой внутреннего помощника, а его имя автор теста не знает. Это
случай «тест-навязывает-устройство» (skills/escalation-rules.md).
Внешние триггеры отказа записи есть, и критерий стоило назвать ими:
- запись проекта лежит в `targets.yaml` репозитория, а не в локальном
  слое (`orchestrator/projects.py:456`);
- в локальном слое есть строка-комментарий (`:473`);
- журнал БД недоступен (`store.db_usable`, `:635` у блока).

Ещё одна неточность AC-3: «процесс не завершается». `cmd_doctor` в
конце сам выходит с кодом 1 при любом `fail`
(`orchestrator/doctor/cli.py:352-355`), а в песочнице `fail` дают и
прочие строки (клон и т. п.). Проверять надо «строки `all_checks`
выведены после строки отказа записи», а не код выхода. В нынешнем виде
формулировку можно прочесть как требование кода 0.

В-2 (AC-7). Критерий «диф ветки по `gitcmd.py` пуст» — проверка дифа,
не поведения. Он зелёный с рождения. Как долгоживущий тест в `tests/`
он бессмыслен после мержа: базы сравнения нет, и следующая задача,
законно правящая `gitcmd.py`, его покраснит. Безопасная форма — только
планка через помощник `_pult.branch_diff` либо опора на гейт зон.

Безопасность красной фазы: рекурсии, хуков и порождения процессов
критерии не требуют. API подменяется через `gitlab_adapter.transport`
или `request`. Песочница по умолчанию отказывает живому HTTP
(`tests/sandbox.py:668-696`). Одна оговорка: AC-2/AC-3 через полный
`cmd_doctor(fix=True)` идут и через `_fix_project_clones`
(`orchestrator/doctor/git_hooks.py:363-376`). Без заранее заведённого
клона тот зовёт `workspace.ensure_clone` — `git clone` на `url` записи
(в тестах `https://localhost/...`). Обращение быстро отказывает, такой
путь уже есть у существующих тестов `--fix`. Но тесту AC-2/AC-3 стоит
заводить каталог клона заранее, как это делает
`tests/test_01m6ezxvfg405y1btfdsgbks8e_pair_support.py:176`.

Д-1. Предпосылка ANSWER-1 и решения 2 («требование 4 краснит
`pair_support.py:161` и `unsupported_project.py:399`») верна для
прежней версии SPEC, где `fail` ставился при любом отсутствии поля. При
нынешнем делении (решение 2: поле не задано и API не ответил — `warn`)
эти тесты зелёные без правки, и вот почему. Обе песочницы
(`LightTransitionSandbox`) зовут `isolate_keychain_and_role`
(`tests/sandbox.py:2153`, `:2195` → `TmpRootTest.setUp`, `:1643`), а тот подменяет транспорт GitLab
отказом соединения (`:692-696`). Отсюда: `token_user` с причиной →
`warn` → `new` заводит задачу. Ни одно утверждение этих тестов
(`code == 0`, одна строка `tasks`, нет «не поддержан») не задето.
Вдобавок слова мандата «адрес, равный адресу подменённого владельца
токена» в этих файлах не на что опереть: владельца токена там никто не
подменяет. Мандат не вредит, но и не нужен. Разработчику стоит не
пользоваться им, пока тест действительно не покраснеет.

Д-2. Тр. 4 называет область строки («для проекта с `forge: gitlab` и
`token_slot`»), но прямо не говорит, что у артели и у GitHub строки нет.
Если положить имя в `_names`, артель получит девятую строку `skip`, и
`gitlab_doctor_lines.py:819` покраснеет. По «Не входит» SPEC это
эскалация, а не правка теста. Риск — лишний круг, не ослабление.

## Пути обхода гейтов
- Е-1 (AC-5). Тр. 5 ставит отказ «после `unsupported_reason`
  (`catalog.py:856`)», то есть внутрь `cmd_new`. Но AC-5 проверяет только
  CLI `new --target`. Отказ, положенный в CLI-обёртку
  `catalog.new_cli_target`, пройдёт AC-5, а `epic draft promote` зовёт
  `cmd_new` мимо обёртки и заведёт задачу проекту с неверным автором.
  Прецедент того же обхода закреплён в
  `tests/test_epic_draft_promote_unsupported_project.py:1`. AC-5 стоило
  дополнить путём `epic draft promote`.
- Е-2. `doctor --fix` в процессе роли не задан: тр. 4 даёт `skip`
  только строке проверки. Починка, которая зовёт `token_user`, в роли
  пошла бы в связку ключей или к API. Сейчас её удерживает только
  граница окружения роли, а не требование.
- Е-3 (AC-3, В-1). Исполнитель может не делать сверку до записи вовсе:
  AC-3 без внешнего триггера её отсутствие не поймает.
- Обход через `warn` («API не ответил» → задача заводится) — осознанное
  решение 2, не отклонение.
