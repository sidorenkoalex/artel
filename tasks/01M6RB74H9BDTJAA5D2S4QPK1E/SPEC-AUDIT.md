Не подтвердилось или SPEC умолчал:
- **Ф-1. Имя автора из автопоиска не пройдёт существующую сверку автора.**
  Требование 2 (SPEC.md:38-39) пишет `name` = поле `name` ответа `GET /user`,
  то есть отображаемое имя. Но `_push_plan` уже зовёт
  `gitcmd._author_check_refusal` (`orchestrator/gitcmd.py:625-659`, вызов
  `:1361`) до первой отправки каждой ветки задачи. Эта функция требует
  `commit_author.name == username` пользователя токена (`:656-658`). У бота
  токена проекта GitLab отображаемое имя (имя токена) и `username` вида
  `project_<id>_bot_<хэш>` различаются. Запись, которую сделает автопоиск,
  откажет первую отправку ветки любой задачи: «сверка автора: commit_author
  <name> не совпадает с владельцем токена token_user <username>». Строка
  `doctor` при этом скажет `ok`, потому что сравнивает только email. SPEC эту
  сверку не упоминает. ТЗ (факт 2) прямо говорит, что имя сервер не
  проверяет, — значит, писать `username` в `name` с сервером совместимо.
  Источник имени — решение Оператора.
- **Ф-2. «Правка target-set» в тексте `fail` отсылает к правке, которой нет.**
  Текст на SPEC.md:50-52 советует Оператору исправить автора через
  target-set. Но команда `machine.commit_author` не пишет:
  - путь `machine.commit_author.<поле>` и путь к уже заданному отображению
    отказывают как «вложенное отображение» (`orchestrator/projects.py:784-789`);
  - `--key` работает только для `machine.submodule_tokens` (`:384`);
  - `--from-file` работает только для блоков `description` (`:655-670`).

  Это подтверждает строка копилки 06.11 (коммит ae3f45093, `docs/backlog.md`):
  «target-set не пишет machine.commit_author». Добавить такую правку в
  `target-set` требования не заказывают.
- **Ф-3. «Путь target-set» в `doctor --fix` нельзя взять как есть.**
  - Сверка одиночной правки `_target_set_mismatches` требует, чтобы
    изменился ровно один лист (`orchestrator/projects.py:889-893`). Запись
    `{name, email}` меняет два листа. Подходит только сверка блочного вида
    (`_target_set_block_mismatches`, `:900`), и SPEC не говорит, какая сверка
    нужна.
  - `_target_set_load`, `_rendered` и `_target_set_write`
    (`:451-515`) отказывают через `sys.exit`: комментарий в слое, записи нет
    в локальном слое, БД журнала недоступна, файл не записан. В
    `doctor --fix` (`orchestrator/doctor/cli.py:312-342`) такой выход
    оборвёт весь `doctor`, и ни одна строка проверок не напечатается.
    Требование 2 обещает «строку `doctor` с причиной» только для двух случаев
    (нет адреса, отказ API), но не для отказов самого пути записи.
- **Ф-4. Копия прежнего файла кладётся не «рядом».** AC-2 (SPEC.md:84) пишет
  «рядом создана копия прежнего файла». На деле копия ложится в `config.LOGS`
  как `targets-<штамп>.yaml` (`orchestrator/projects.py:986-1003`). Автор
  тестов, ищущий копию рядом со слоем, напишет тест, который не позеленеет.
- **Ф-5. Ссылки слежения в клоне устаревают — сверка ложно откажет.**
  Требование 5 (SPEC.md:62-64) считает коммит отправленным, если он
  достижим из `refs/remotes/origin/*`. Но ветку задачи пульт заводит от
  свежей базы через `fetch_ref_sha(..., tracking_refs=False)`
  (`orchestrator/workspace.py:279-287,318-325`). Этот вызов идёт с
  `--refmap=` и не обновляет `refs/remotes/origin/<base>`
  (`orchestrator/gitcmd.py:2144-2154`). Сценарий:
  1. В клоне `refs/remotes/origin/main` отстал.
  2. Ветка задачи заведена от свежего main, и между отставшей ссылкой и
     этим main есть чужие коммиты людей проекта — с их собственными адресами.
  3. При первой отправке ветки этих коммитов в origin как назначения ещё
     нет, и из ссылок слежения они не достижимы.
  4. Сверка требования 5 откажет отправку, перечислив коммиты, которые
     сервер уже содержит.

  Опыт во временном каталоге запустить в этом шаге не удалось (запуск
  скрипта требует подтверждения). Вывод опирается на код и докстринг
  `fetch_ref_sha` («`--refmap=`: git не обновляет попутно ссылку
  отслеживания»). Рядом — та же дыра для отправки по URL вместо имени
  `origin` и для случая, когда «текущее значение назначения в origin» не
  получено (ls-remote не ответил): SPEC не говорит, отказывать в этих
  случаях или пропускать.

## Пути обхода гейтов
- **Е-1.** Ссылки `refs/remotes/origin/*` локальны и в клоне правятся
  свободно: `update-ref` и `fetch` с любой refspec ролям доступны
  (`orchestrator/role_git.py:56-69` — встроенные, не запрет). Роль может
  объявить свой коммит «уже в origin» и пройти сверку требования 5
  буквально. Последствие ограничено: сервер всё равно отклонит отправку.
  Сверка — ранний сигнал, а не гейт безопасности. Отклонение мелкое, решение
  Оператора.
- **Е-2.** Разрыв В-1 позволяет выполнить требования 3–4 буквально и обойти
  смысл отказа `new`. Если сначала спросить API и на отказ API отвечать
  `warn`, проект без `commit_author` заводит задачи при любом сбое сети,
  а набор тестов при этом зелёный. Это и есть путь, на котором Д-1 «чинится»
  без правки тестов: в лёгкой песочнице `GET /user` отказывает, отсюда
  `warn` и задача заведена.
- **Е-3.** Отказ `new` охватывает только `cmd_new`. Подзадачи деления
  (`catalog.spawn_subtask` → `_new_task_row`, `orchestrator/catalog.py:1007`)
  заводятся мимо проверки. ТЗ называет только `new`, так что это не
  отклонение, а наблюдение для Оператора.

9. **Ф-4.** «Рядом создана копия» (SPEC.md:84) — на деле копия в
