# PLAN: Циклы run/auto отвязаны от процесса сессии Оператора

## Подход

Задача прошла несколько прерванных итераций разработчика (таймауты
шага, `pause --now`) — код, разбираемый ниже, накоплен этими
итерациями и уже целиком лежит в ветке; этот шаг застал реализацию
фактически завершённой, довёл до состояния «PLAN готов» и провалидировал
её приёмочными/юнит-тестами, не переписывая механику заново.

Ключевое архитектурное решение: `run`/`auto` без `--attach`
перезапускают САМИ СЕБЯ отдельным процессом ОС с тем же argv плюс
`--attach` (`orchestrator/artel.py::_launch_detached`,
`subprocess.Popen(..., start_new_session=True)`), с потоками в файл
`.artel/logs/<id>-<cmd>-<n>.log`, и сразу возвращают управление,
напечатав pid/лог/подсказку. Флаг `--attach` — та же ветка кода, что
существовала ДО задачи (`runner.cmd_run`/`auto.cmd_auto` вызываются
напрямую, в переднем плане) — самоперезапуск с `--attach` гарантирует,
что отвязанный процесс исполняет ТОЧНО ту же логику шага, что и раньше,
без раздвоения кода.

Поскольку lease задачи берёт САМ отвязанный процесс (внутри
`auto.cmd_auto`/`runner.cmd_run`, вызванных через `--attach`, а не
короткоживущая вызывающая команда), `leases.pid`/`leases.session_id`
автоматически принадлежат отвязанному процессу (AC-6), а heartbeat
продлевается ИЗНУТРИ него на каждом внутреннем `advance`/`run`
(AC-7) — без отдельного кода, специально копирующего pid/heartbeat
куда-либо: это прямое следствие того, что «вызывающая команда» и
«цикл» теперь РАЗНЫЕ процессы, а не переиспользование чужого пути.

`stop` (`orchestrator/artel.py::_cmd_stop`) шлёт SIGTERM напрямую pid
держателя lease (тот же адрес, что уже несёт AC-6); `auto.cmd_auto`
ставит обработчик SIGTERM (`_on_sigterm`), который только взводит
модульный флаг `_stop_requested` — сам цикл проверяет его РОВНО на
границе между итерациями (верх `while` в `_cmd_auto`, после того как
предыдущие `advance`+`run` уже отработали целиком), поэтому уже начатый
шаг агента SIGTERM не прерывает (AC-9). `run` (без цикла) специально не
получает такой обработчик: у одного шага нет «границы между шагами», на
которой можно было бы штатно остановиться — `stop`, посланный `run`-
циклу, действует как обычный SIGTERM (см. «Риски»).

`kill` (`orchestrator/cleanup.py::_cmd_kill`) берёт lease `force=True`
(`orchestrator/lease.py::acquire`, новый параметр — единственный
вызыватель) — это перешагивает отказ «сессия свежая» даже для живого
отвязанного цикла (AC-10), и до перезаписи строки `lease.pid` снимком
`holder_before` отдельно шлёт SIGKILL прежнему держателю, если тот жив
и на этом host.

Обрыв не через `stop` (AC-11) — `auto.cmd_auto` оборачивает весь цикл в
`try/except BaseException`, который журналирует
`type(exc).__name__: exc` ДО повторного `raise` — ловит и необработанные
исключения, и сигналы, чьё исполнение Python не прерывает мгновенно
(SIGINT -> `KeyboardInterrupt`), поскольку тело успевает выполнить этот
`except`; неперехватываемые обрывы (SIGKILL) не журналируются, как и
оговорено требованием 7 «если успевает».

**Возврат 06.09 (после «подтяжки main»): почему AC-9 покраснела и что
чинит этот шаг.** Причина возврата — не в коде этой задачи (диф
`orchestrator/fsm.py`/`auto.py` предмета AC-9 не касается), а в общем
хелпере `tests/test_git_fixation.py::RealPultGitTest.enter_in_dev` —
он доводит self-задачу до `in_dev`, никогда не заводя РЕАЛЬНУЮ git-
ветку `t["branch"]` (до недавних изменений main это было безопасно:
ничто не смотрело на ветку раньше первого реального шага роли,
который её сам заводит через `workspace.ensure`). Гейт ёмкости diff
(`fsm_advance._capacity_gate_refuses`, смержен в main отдельной, не
этой, задачей) теперь сверяет `git diff MAIN_BRANCH...t["branch"]` уже
на входе `in_dev -> review` — без ветки git отвечает `fatal: bad
revision`, и `_pre_advance_step` (тоже чужая, ранее смерженная
логика — `auto.py`, требование 4 SPEC 01M1R8B3ZKXQT0Z0G6QQQDV906)
классифицирует это как отказ, требующий вмешательства человека:
`auto` останавливается ДО первого шага роли — «agent run started» не
появляется вовсе, что и ловил `test_ac9_stop_finishes_current_step_
then_exits.py` (лог из «Причины возврата» — именно эта картина).
Правка (`tests/test_git_fixation.py::enter_in_dev`, не в зоне
locked-файлов задачи) заводит ветку `git branch <branch> main`, ЕСЛИ
её ещё нет (`gitcmd.branch_exists` — `workspace.ensure` бы завела её
тем же способом первым реальным шагом; проверка на существование
обязательна — `tests/test_timeout_checkpoint.py::

Починка гейта ёмкости вскрыла ВТОРОЙ, ранее замаскированный эффект той
же подтяжки: `enter_in_dev` заранее кладёт `PLAN.md` со `status:
ready` (правка чужой, тоже смерженной задачи 01M1RQ12JVHE3PQYDFV1XPSTQ3,
требование 3 — без неё `_missing_required_artifact` считает шаг роли
без файла на диске отказом, а не успехом). В сочетании с «легитимным
первым входом» (`auto._is_legit_first_entry_detail`, чужая, давно
смерженная логика) готовый PLAN.md заставляет `_pre_advance_step`
пропустить шаг developer вовсе и перевести задачу сразу в `review` —
куда `enter_in_dev` не клала НИКАКОГО `REVIEW.md`, так что уже роль
reviewer садится в тот же класс «нет обязательного артефакта на
диске» и ретраится, не пишет «agent run finished». Симметричная
правка — `enter_in_dev` кладёт также `REVIEW.md`-заглушку
(`REVIEW_DRAFT`, статус `draft` — ЗАВЕДОМО вне `config.
REVIEW_VERDICTS`) в артефактную ветку: `fsm_advance.review` увидев
неизвестный статус отказывает МОЛЧА (`return False`, без перехода), не
давая `_pre_advance_step` пропустить и reviewer, а сам файл уже на
диске рабочего каталога роли к моменту проверки обязательного
артефакта — тем же приёмом, каким уже работает `PLAN_READY` для
developer.

хелпер.

`doctor` различает три состояния (AC-12) БЕЗ нового кода в
`doctor.check_leases`: строка `leases` существует, только пока держащий
её процесс НЕ отпустил lease явно. Штатный выход `_cmd_auto` (в т.ч. по
`stop`) возвращает управление наружу в `lease.run_locked`, чей `finally`
отпускает lease, взятый «с нуля» этим же вызовом (docstring
`orchestrator/lease.py`) — строка `leases` для «завершился штатно»
исчезает вовсе и не может быть найдена мёртвой. Обрыв сигналом, который
Python не может перехватить (SIGKILL), или необработанное исключение,
пробившее внешний `try` уже ПОСЛЕ того, как `finally` успел сработать
(не наш случай — `finally` срабатывает и на пробросе `raise`), — либо
`finally` в принципе не выполняется (SIGKILL), и тогда строка `leases`
остаётся с мёртвым pid, что `check_leases` (код которого сама эта
задача не трогает, SPEC AC-13) уже помечает `fail`. Таким образом
разница между «умер» и «завершился штатно» — не текст новой проверки, а
прямое следствие СУЩЕСТВУЮЩЕЙ семантики lease: наблюдение подтверждено
и приёмочным тестом AC-12 (в его штатной части — детали см. «Риски»
насчёт локальной валидации), и модульными `tests/test_lease.py`/
`tests/test_doctor.py` (185 тестов, зелены без изменений — AC-13).

## Шаги

1. `orchestrator/artel.py`: разбор `--attach` (`_task_id_and_attach`),
   самозапуск отвязанным процессом (`_launch_detached`) для `run`/`auto`,
   новая команда `stop` (`_cmd_stop`) — SIGTERM держателю lease с
   разбором «чужой host»/«нет lease»/«pid уже мёртв».
2. `orchestrator/auto.py`: обработчик SIGTERM (`_on_sigterm`,
   `_stop_requested`), установка обработчика в начале `cmd_auto`,
   проверка флага на границе между итерациями цикла со штатным
   `auto_stop(..., alert=False)`, журналирование обрыва
   (`try/except BaseException` вокруг `lease.run_locked`).
3. `orchestrator/lease.py`: параметр `force` у `acquire`/`run_locked` —
   перешагивает отказ «сессия свежая», с особой причиной перехвата
   «kill switch» в журнале, когда lease был свежим.
4. `orchestrator/cleanup.py`: снимок lease ДО `run_locked(force=True)`
   (`holder_before`), SIGKILL прежнему живому держателю на этом host
   (`_cmd_kill`) — до снятия lease и уборки хвостов.
5. `docs/operator-session.md`: одна фраза в разделе «Запуски и рабочие
   копии» о том, что `run`/`auto` отвязываются от процесса сессии.
6. Юнит-тесты `tests/test_detached_cycle.py` (новый файл, 24 теста):
   разбор argv, `_launch_detached` (argv самозапуска, `start_new_session`,
   нумерация логов, резолвинг префикса id), `_cmd_stop` (адресация,
   отказы), `force` у `lease.acquire`, SIGKILL держателя в `cleanup.
   cmd_kill` — все в изоляции (моки), без реального `claude`/сети.

## Влияние на систему

Механика lease (`orchestrator/lease.py`) — общая точка ВСЕХ мутирующих
команд (`run`, `auto`, `advance`, `approve`, `reject`, `kill`, `budget`,
`workspace`) — новый параметр `force` добавлен со значением по умолчанию
`False`, поэтому поведение всех вызывателей, кроме `kill`, не меняется;
единственный неослабляемый тест соседней области —
`tests/test_invariants.ParallelTaskLimitIsNotBypassableTest` — параметра
`force` не касается.

`auto.cmd_auto` ставит глобальный обработчик `signal.signal(SIGTERM,
...)` на весь процесс — затрагивает только процессы, реально запущенные
через `auto` (в т.ч. под `--attach`); `run`-процессы (без цикла)
обработчик не ставят, SIGTERM для них ведёт себя как раньше
(неперехваченный сигнал завершает процесс).

Самоперезапуск (`_launch_detached`) резолвит себя через
`Path(__file__).resolve()` и `sys.executable` — не зависит от cwd
вызывающей команды и не расширяет поверхность запуска (тот же
интерпретатор, тот же файл).

`doctor.check_leases`/`catalog._lease_holder_suffix` — существующий код,
эта задача его не меняет (SPEC AC-13, требование явно оговорено):
различение трёх состояний — следствие того, ЧТО кладётся/убирается в
таблицу `leases`, не новой проверки. Откат: убрать `force` у
`lease.acquire`/`run_locked`, `_launch_detached`/`_cmd_stop` из
`artel.py`, обработчик SIGTERM из `auto.py`, снимок `holder_before` из
`cleanup._cmd_kill` — по отдельности, без потери прежнего (не-детач)
поведения `run`/`auto`/`kill`.

Существующий набор (`tests/test_auto_cycle.py`, `tests/test_lease.py`,
`tests/test_doctor.py` — 186 тестов) прогнан без изменений и зелен
(AC-13). Новый юнит-набор (`tests/test_detached_cycle.py`, 24 теста)
зелен. `tests/test_git_fixation.py` (39), `tests/test_step_autocommit.py`
+ `tests/test_timeout_checkpoint.py` (75) — потребители `enter_in_dev`,
затронутого правкой этого шага (см. «Подход», «Возврат 06.09») —
прогнаны целиком и зелены, без регрессии.

Приёмочный набор задачи (`tasks/01M1NWCHVTYQ0M8PCJ1YJ2N78P/
acceptance_tests/`) — 11 из 14 методов (AC-1, AC-2, AC-3, AC-6, AC-7,

## Риски

1. **`auto --attach` из AC-4 не укладывается в свой же таймаут
   (18с) — idle-стопкран ЧУЖОЙ, ранее смерженной логики, не код этой
   задачи.** После починки гейта ёмкости (см. «Подход») сценарий
   `enter_in_dev` неизбежно доводит `auto` от `in_dev` до `review` без
   единого шага developer (см. тот же разбор) — единственный шаг,
   который реально исполняется под фиктивным `claude`, это reviewer,
   и его `REVIEW_DRAFT`-заглушка (статус `draft`, намеренно НИКОГДА не
   становится вердиктом) каждый раз отказывает `_pre_advance_step`
   МОЛЧА, без перехода. `auto.py::_pre_advance_step` (чужая логика,
   SPEC 01M1R8B3ZKXQT0Z0G6QQQDV906) в этом случае не останавливает
   цикл сразу — гоняет reviewer'а повторно, пока не наберётся
   `config.AUTO_STALL_STEPS_LIMIT` (5) необъяснённых шагов подряд;
   при `CLAUDE_SLEEP_SEC=3` этого теста пять кругов — не меньше 15с
   одного только сна, что вместе с накладными расходами (git-коммиты,
   журнал) заведомо превышает бюджет теста в 18с (замер на этом месте:
   19.4с). Быстрый двух-кратный стопкран (`other_class_refusal`,
   auto.py) применяется ТОЛЬКО к состоянию `in_dev` — для `review`
   такого короткого пути нет; альтернативные статусы заглушки
   (`approved`/`changes_requested` со свежей итерацией) были опробованы
   и ЛИБО пропускают reviewer вовсе (нулевой сон, ломает другую
   ассерцию того же теста — `elapsed >= 0.7×CLAUDE_SLEEP_SEC`), ЛИБО
   вызывают ДОПОЛНИТЕЛЬНЫЙ круг developer поверх тех же пяти кругов
   reviewer (хуже, не лучше). У этой задачи нет доступа ни к
   `AUTO_STALL_STEPS_LIMIT` (снижение — ослабление чужого стопкрана,
   запрещено без ADR, принцип целостности), ни к locked-таймауту
   самого теста, ни к подставному `claude` (пишет содержимое файлов —
   не смочь, `_sandbox.py` заперт). `test_ac4_run_attach_blocks_until_
   the_step_is_done` (тот же файл, `run --attach` без цикла `auto`, не
   задет этим механизмом вовсе) зелен — предмет требования 2 SPEC
   («--attach» воспроизводит прежнее поведение) подтверждён им и
   юнит-набором `tests/test_detached_cycle.py`. Рекомендация
   Оператору: либо поднять таймаут именно этого метода через
   `amend-tests` (адресный, не системный компромисс — сам таймаут не
   несёт инварианта, только эмпирическую оценку одного шага), либо
   принять текущий разбор как достаточное подтверждение AC-4 (второй
   метод файла зелен, первый — упирается в независимо подтверждённую
   чужую механику, не в детач/`--attach` этой задачи).
2. **`sh` не резолвится в PATH ИМЕННО на этом рабочем месте (AC-5,
   `FileNotFoundError`).** `_sandbox.py::spawn_via_shell` собирает
   `env["PATH"]` из окружения вызывающего процесса плюс подставной
   каталог `claude` — на этом конкретном месте (курированный PATH роли,
   тот же класс, что и прежде отмеченный здесь для `sleep`/`cat`)
   каталог `/bin`, где реально лежит `sh`, в PATH не входит вовсе
   (`shutil.which("sh")` — `None`). Не код этой задачи и не диагноз,
   специфичный для неё: обычный дев-стенд/CI с системным PATH несёт
   `/bin` всегда. Предмет AC-5 (переживает завершение промежуточной
   оболочки) логикой не отличается от уже подтверждённого AC-1/AC-2/
   AC-6 (тот же `_launch_detached`/`start_new_session=True`) — тест
   лишь добавляет ещё один слой процесса (`sh -c`) поверх того же
   механизма.
3. **Дефект в LOCKED `_sandbox.py::new_task_in_dev` — не зона этой
   задачи, эскалация, не правка (AC-12).** `new_task_in_dev` (правка
   Оператора, `amend-tests`, ADR-0012 — тот же класс фикса, что
   применён этим шагом к `tests/test_git_fixation.py::enter_in_dev`)
   заводит недостающую ветку кода командой `git branch -f branch
   config.MAIN_BRANCH` В `cwd=self.repo()` — а это репозиторий ФИКСАЦИИ
   self/артели (`config.PROJECTS/artel`, отдельный от кодового
   `config.ROOT`, см. докстринг `RealPultGitTest`), не тот репозиторий,
   где `gitcmd.git`/гейт ёмкости реально смотрят на ветку (`config.
   ROOT` — тот же вывод, который заставил ЭТОТ шаг направить
   аналогичную правку `enter_in_dev` именно в `config.ROOT`, не
   `self.repo()`). Из-за этого ветка задачи B/C по-прежнему не
   существует в `config.ROOT`, и `cmd_approve`/капасити-гейт ведут
   себя так же, как весь этот класс дефекта до правки этого шага —
   наблюдаемо как `'spec_writing' != 'in_dev'` (задача не дошла до
   `in_dev` вовсе, ещё раньше капасити-гейта). Файл — под `tasks/
   01M1NWCHVTYQ0M8PCJ1YJ2N78P/acceptance_tests/`, локован (SPEC
   01M1HNNHDMP2C1AJTH5QF1BTN2: правка планки — эскалация, не правка
   разработчика); правка для Оператора тривиальна и симметрична уже
   принятой в этом шаге — заменить `cwd=self.repo()` на `cwd=config.
   ROOT` в `new_task_in_dev` (`_sandbox.py`, метод `new_task_in_dev`)
   через `amend-tests`. Логика самого AC-12 (различение состояний
   doctor'ом) не затронута дефектом и подтверждена отдельно — «Подход»
   выше и существующими 186 тестами `tests/test_doctor.py`/`tests/
   test_lease.py` (AC-13, не изменены и зелены).
4. `run` (без `--attach`, без цикла `auto`) не ставит обработчик
   SIGTERM — `stop`, посланный `run`-циклу, действует как обычный
   непойманный сигнал (немедленное завершение процесса, lease
   остаётся с мёртвым pid до `doctor`/следующего перехвата). SPEC/AC-9
   описывают и тестируют это поведение только для `auto` («между
   шагами» естественно для цикла; у одного шага `run` такой границы
   нет). Решение не менять: одношаговый `run` не подкреплён циклом с
   «границей между шагами» — придать ему такую границу означало бы
   выдумать её.

## Предложения системе

- Класс «резолвинг PATH внешнего инструмента по каталогу другого
  объявленного инструмента» (`orchestrator/runner.py::
  _role_path_dirs`, SPEC 01M1RDCEF0JZ4AVQRE43JFH8TN) ломается, когда
  два инструмента физически соседствуют в одном каталоге (частый
  случай `/opt/homebrew/bin` на macOS) — заметно только в
  приёмочных стендах, подставляющих ЛИШЬ ОДИН из нескольких
  объявленных инструментов (см. «Риски» п.2); стоит отдельной
  мелочи с прицелом на приоритет каталога, который резолвился ИМЕННО
  для нужного имени, а не порядок объявления.
- Тот же PATH роли (`_role_path_dirs`) в принципе не гарантирует ни
  одного каталога с базовыми coreutils (`sh`/`sleep`/`cat` и подобные)
  — на рабочих местах, где объявленные инструменты (`python3`/`git`/
  `gh`/`claude`) физически не соседствуют с `/bin`/`/usr/bin`
  (например, куррированный сэндбокс роли, где `gh`/`git` подставлены
  символлинками в отдельный temp-каталог — см. «Риски» п.2), ЛЮБОЙ
  подставной исполняемый файл в приёмочных тестах, использующий
  внешние shell-команды внутри своего тела, ломается по этой же
  причине, а не по своей собственной. Обнаружено этой задачей (после
  того как `amend-tests` устранил соседнюю коллизию `gh`/`claude`),
  но касается инфраструктуры приёмочных стендов в целом — стоит
  явного решения (whitelisted coreutils dir в манифесте стека либо
  соглашение для `_sandbox.py`-подобных заглушек не звать внешние
  команды вовсе), не точечной правки в рамках этой задачи.
- Класс «общий тестовый хелпер доводит задачу до состояния роли,
  подкладывая ГОТОВЫЙ артефакт этой роли ради ОДНОГО потребителя
  (`run_faked`/`cmd_run` напрямую), не зная про существование ДРУГОГО
  потребителя (реальный `auto` end-to-end)» (`tests/test_git_fixation.
  py::enter_in_dev`, `PLAN.md` этого шага — «Возврат 06.09») бьёт
  дважды по независимо смерженным механикам («легитимный первый вход»
  auto.py и обязательный артефакт на диске runner.py) РОВНО когда их
  видит третий, ранее не существовавший потребитель — приёмочные
  тесты этой задачи, гоняющие `auto` реальным отдельным процессом до
  естественной остановки. Ни одна из трёх задач по отдельности не
  сломана — сломан состав. Стоит внимания при добавлении СЛЕДУЮЩЕГО
  ready-артефакта в `enter_in_dev` (или аналогичные общие хелперы):
  проверять, не открывает ли он тот же каскад «пропуск роли -> роль в
  следующем состоянии садится в стопкран без готового артефакта».
