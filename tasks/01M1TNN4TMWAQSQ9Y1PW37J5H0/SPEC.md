# SPEC: рабочие файлы роли не доезжают до артефактной ветки и main — белый список каталога задачи, guard до снимка

## Контекст
Инцидент 06.09: ревьювер задачи 01M1REVMB50SND1KJ3CYQMV2ST оставил в
корне `tasks/<id>/` пять копий карты кодовой базы и пустой файл
сравнения — рабочие файлы, не артефакты. Автокоммит шага
(`checkpoint.commit_step_artifacts`) перенёс их в артефактную ветку без
разбора имён; guard на CI артефактной ветки покраснел («нет
frontmatter»), но эту красноту никто не проверяет; шаг «снимок
артефактной ветки поверх merge» (`fsm_merge_gate`) перенёс каталог как
есть в main ДО какой-либо проверки guard — main покраснел на трёх
коммитах подряд. Снято руками Оператора; черновики разошлись по
артефактным веткам пяти задач, унаследовавших их от main при заведении.

Задача 01M1SAA01YRRTWAVADT2F81RRQ закрыла тот же класс для каталога
планки приёмки (`acceptance_tests/`): `ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`
в `scripts/guard.py` и `_is_stray_acceptance_test_file` в
`orchestrator/checkpoint.py`. Корень `tasks/<id>/` остался без
аналогичного белого списка и без проверки ДО того, как содержимое
уходит в main.

## Требования

1. Белый список допустимых имён первого уровня `tasks/<id>/` — одно
   место в `scripts/guard.py`, по образцу
   `ACCEPTANCE_TESTS_ALLOWED_TOP_LEVEL`: `SPEC.md`, `PLAN.md`,
   `REVIEW.md`, `TEST_REPORT.md`, `QUESTIONS.md`, `TZ.md`,
   `ANSWER-<n>.md`, каталог `acceptance_tests/`, приложения `*.patch`.
   Файл вне списка — именованная ошибка guard «посторонний файл в
   каталоге задачи» в режиме `--all` (с флагом `--artifact-branch` и
   без) — не попытка разобрать его как артефакт с frontmatter.
   Существующий `tasks/<id>/mockup.html` на main обрабатывается по
   решению, которое разработчик фиксирует в PLAN.md: либо явное
   исключение из правила с указанием конкретной задачи, либо удаление
   отдельным приложением к PLAN.
2. Автокоммит артефактов шага (`checkpoint.commit_step_artifacts` и
   чекпоинты таймаута/аварии/паузы, идущие тем же путём) переносит в
   артефактную ветку только файлы из белого списка требования 1;
   посторонние файлы в коммит не попадают, шаг роли из-за этого не
   проваливается, в журнал шага пишется одна запись с перечнем
   отброшенных путей (по образцу «посторонние файлы в каталоге
   планки» из 01M1SAA01YRRTWAVADT2F81RRQ). Критерий допустимости —
   один источник истины: функция/список в `scripts/guard.py`,
   `orchestrator/checkpoint.py` её импортирует, не копирует
   независимой регуляркой.
3. Шаг наложения снимка артефактной ветки поверх merge
   (`orchestrator/fsm_merge_gate.py`) прогоняет guard на каталог
   `tasks/<id>/` в scratch-репозитории — ДО `git push` в main, не
   после. Красный результат отказывает переходу с именованной причиной
   (перечень посторонних файлов/нарушений); задача остаётся на
   `merge_gate` (без эскалации), main не тронут — `git push` в этом
   случае не выполняется. Отказ журналируется тем же классом записи,
   что прочие отказы `merge_gate` (CI красный, конфликт merge, push
   FAILED).
4. Тесты покрывают: (а) guard называет посторонний файл в корне
   каталога задачи в обоих режимах (`--all`, `--all --artifact-branch`)
   и молчит на полном штатном наборе имён требования 1, включая
   `ANSWER-7.md` и `x.patch`; (б) автокоммит с посторонним файлом в
   `tasks/<id>/` переносит в артефактную ветку только допустимые
   файлы и журналирует отброшенные пути одной записью — тот же фильтр
   у чекпоинта таймаута; (в) снимок поверх merge с посторонним файлом в
   артефактной ветке отказывает ДО `git push`, main остаётся без
   изменений (песочница по образцу `tests/sandbox.py`); (г)
   существующие `tests/test_guard*.py`, `tests/test_checkpoint*.py`,
   `tests/test_fsm_merge_gate*.py` остаются зелёными без правки
   ассертов, и каждый новый тест ловит заявленную мутацию (белый
   список расширен на `*`, фильтр в checkpoint снят, guard в
   merge_gate запускается после push вместо до).
5. Скилы ревьювера и разработчика (приложением к PLAN.md, unified-диф
   по защищённому пути `skills/`, применимость которого разработчик

   Оператор) несут новую строку: «рабочие файлы — только во временном
   каталоге сессии; в `tasks/<id>/` пишутся только артефакты по
   шаблону, остальное автокоммит отбрасывает».

## Критерии приёмки

AC-1. `scripts/guard.py` несёт единый белый список допустимых имён
первого уровня `tasks/<id>/`: `SPEC.md`, `PLAN.md`, `REVIEW.md`,
`TEST_REPORT.md`, `QUESTIONS.md`, `TZ.md`, `ANSWER-<n>.md`, каталог
`acceptance_tests/`, приложения `*.patch`.

AC-2. Guard в режиме `--all` (с флагом `--artifact-branch` и без)
называет файл вне списка AC-1 именованной ошибкой «посторонний файл в
каталоге задачи» — не пытается разобрать его как артефакт с
frontmatter; на полном штатном наборе имён, включая `ANSWER-7.md` и
`x.patch`, guard молчит.

AC-3. Существующий на main `tasks/<id>/mockup.html` обработан решением
PLAN — явное исключение из правила AC-1/AC-2 с указанием конкретной
задачи, либо удаление отдельным приложением к PLAN; после применения
решения guard `--all` на main не называет этот файл посторонним.

AC-4. `checkpoint.commit_step_artifacts` и чекпоинты таймаута/аварии/
паузы, идущие тем же путём, переносят в артефактную ветку только файлы
из белого списка AC-1: посторонние файлы исключены из коммита, шаг
роли из-за этого не проваливается.

AC-5. В журнал шага, перенёсшего посторонние файлы, пишется одна
запись с перечнем отброшенных путей (по образцу «посторонние файлы в
каталоге планки» из 01M1SAA01YRRTWAVADT2F81RRQ), не по записи на файл.

AC-6. `orchestrator/checkpoint.py` импортирует критерий допустимости
(список/функцию) из `scripts/guard.py` — один источник истины; не
дублирует его независимой регуляркой.

AC-7. Шаг наложения снимка артефактной ветки поверх merge
(`orchestrator/fsm_merge_gate.py`) прогоняет guard на каталог
`tasks/<id>/` в scratch-репозитории ДО `git push` в main.

AC-8. Красный guard на шаге AC-7 отказывает переходу с именованной
причиной (перечень посторонних файлов/нарушений); задача остаётся на
`merge_gate` без эскалации, `git push` в main не выполняется, main не
изменён; отказ журналируется тем же классом записи, что прочие отказы
`merge_gate`.

AC-9. Существующие `tests/test_guard*.py`, `tests/test_checkpoint*.py`,
`tests/test_fsm_merge_gate*.py` остаются зелёными без правки ассертов;
каждый новый тест ловит заявленную мутацию — расширение белого списка
на `*`, снятие фильтра в `checkpoint`, перенос запуска guard в
`merge_gate` на после push вместо до.

## Оценка объёма и деление

Сработавшие сигналы:
- «затронут инвариантный механизм» — `docs/invariants.md` (строка 84)
  буквально содержит подстроку `scripts/guard.py` в записи о свойстве
  guard «новые правила действуют на живые задачи, история не
  переписывается» (исключение закрытых задач из `split_assessment`).
  Это текстовое совпадение с зоной задачи, не отношение к затрагиваемой
  этой задачей механике: требования 1-3 не меняют и не ослабляют
  поведение, которое несёт эта строка инварианта (закрытые задачи
  по-прежнему не подпадают под новые правила guard задним числом —
  правило белого списка корня действует так же, как и любое другое
  новое правило guard).
- «прогноз диффа не дан» — вторичный сигнал (срабатывает автоматически
  вслед за первым, если `diff_forecast_kib` не заполнен); прогноз
  диффа не даю: правки сосредоточены в существующих функциях трёх
  файлов зоны и новых тестах, оценка объёма — по числу файлов и
  критериев ниже, не по КиБ.

Прочие сигналы не сработали: зона касается 3 файлов кода
(`scripts/guard.py`, `orchestrator/checkpoint.py`,
`orchestrator/fsm_merge_gate.py`, порог — 5), критериев приёмки 9
(порог — 10), `budget_usd` 20 (порог — 30), формулировок
неопределённости в тексте нет.

Обоснование монолита: три требования (1-3) — один источник истины на
одном шаге инцидента каждое. Белый список без checkpoint-фильтра
(требование 2) не мешает попаданию посторонних файлов в артефактную
ветку — инцидент повторится на первом же шаге. Checkpoint-фильтр без
guard на merge_gate (требование 3) не защищает main, если посторонний
файл уже попал в артефактную ветку другим путём (правка Оператора,
старая ветка, отставшая от нового фильтра) — ровно сценарий факта
06.09, где черновики уже разошлись по пяти артефактным веткам ДО этой
задачи. Guard на merge_gate без белого списка требования 1 нечего
проверять — сам список является источником критерия для обеих
точек контроля (требование 2 явно требует одного источника истины).
Промежуточное состояние «только часть из трёх точек починена» не
закрывает класс инцидента и не мержимо как самостоятельное улучшение.
