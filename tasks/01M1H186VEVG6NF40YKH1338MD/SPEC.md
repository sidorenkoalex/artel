# SPEC: Проверка формата идентификатора на выходе tests_writing, до лока

## Контекст

Инцидент 02.09.2026 (задача «Наблюдаемость сессий»): приёмочный тест
зашил формат идентификатора задачи («T и три цифры») в проверку вывода
`status`. CI-проверка формата (T094, job id-format-greplint,
`.github/workflows/ci.yml`) поймала это только на пулл-реквесте — когда
каталог `acceptance_tests/` уже был зафиксирован локом (инвариант 27,
ADR-0003) и роль законно не могла его править. Развязка потребовала
операторского вмешательства, отката правки конвейером и лишних кругов
ревью. Дефект планки приёмки надо ловить ДО того, как планка становится
неприкасаемой — на переходе `tests_writing -> in_dev`, тем же местом,
где уже проверяются трассируемость AC (T023) и маркеры красноты (T064)
(`orchestrator/fsm.py::_tests_writing_ac_state`,
`orchestrator/fsm_advance.py::tests_writing`).

## Требования

1. Проверка новых строк содержимого `tasks/<id>/acceptance_tests/` на
   образцы формата идентификатора задачи (тот же набор образцов, что в
   CI-job id-format-greplint, `.github/workflows/ci.yml`) выполняется на
   переходе `tests_writing -> in_dev` — до записи фиксации лока
   (`tests_locked_sha`). Найденный образец — именованный отказ перехода:
   сообщение называет файл, строку и несёт подсказку «формат
   идентификатора знает только генератор; строй проверку от фактического
   идентификатора».
2. Набор образцов — единый источник для CI-job id-format-greplint и для
   проверки на переходе (способ выбирает разработчик: файл с образцами,
   читаемый обоими, либо скрипт, вызываемый обоими) — CI и переход не
   могут разойтись по набору образцов. Job id-format-greplint остаётся,
   меняется только источник, откуда он берёт образцы.
3. Отказ перехода по этому основанию не переводит задачу в состояние
   `escalated` — обрабатывается тем же шагом, что и прочие отказы выхода
   из `tests_writing` (маркеры красноты T064, трассируемость AC T023):
   test_author правит тесты и повторяет `advance` без вмешательства
   Оператора.
4. Ни одна существующая проверка (трассируемость AC, маркеры красноты,
   `schema_version`, обязательные секции, CI-job id-format-greplint в
   его нынешнем виде) не ослабляется и не удаляется (принцип целостности,
   ADR-0002) — новая проверка только добавляется.

## Критерии приёмки

AC-1. Содержимое `tasks/<id>/acceptance_tests/`, содержащее образец
формата идентификатора задачи (тот же набор образцов, что использует
CI-job id-format-greplint), отклоняет переход `tests_writing -> in_dev`
до записи фиксации лока (`tests_locked_sha` не обновляется); сообщение
отказа называет файл и строку и несёт подсказку «формат идентификатора
знает только генератор; строй проверку от фактического идентификатора».

AC-2. Содержимое `tasks/<id>/acceptance_tests/` без такого образца не
вызывает отказа перехода по этому основанию — переход `tests_writing ->
in_dev` происходит как прежде.

AC-3. Набор образцов формата идентификатора задачи — общий источник,
используемый и CI-job id-format-greplint, и проверкой на переходе
`tests_writing -> in_dev`: изменение набора образцов в этом общем
источнике меняет поведение обеих проверок без правки кода перехода.

AC-4. Отказ перехода по этому основанию не переводит задачу в состояние
`escalated` и не требует ответа Оператора — задача остаётся в
`tests_writing`, test_author правит `acceptance_tests/` и повторяет
`advance` тем же путём, что при отказе по трассируемости AC или
маркеру красноты.

AC-5. Существующий набор тестов (`tests/`) остаётся зелёным, ни одна
существующая проверка `scripts/guard.py`, `orchestrator/fsm.py` или
CI-job id-format-greplint не ослаблена.

## Не входит

- Изменение самого набора образцов (какие форматы ловим) — объём T094,
  не этой задачи.
- Штатная команда операторской правки залоченной планки приёмки с
  обновлением лока — смежный пробел той же истории (инцидент 02.09),
  отдельная задача по отдельному решению Оператора.
- Распространение проверки формата идентификатора на артефакты, отличные
  от `tasks/<id>/acceptance_tests/` (например SPEC.md, PLAN.md, REVIEW.md).
