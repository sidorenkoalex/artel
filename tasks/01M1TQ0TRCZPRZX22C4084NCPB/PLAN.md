# PLAN: CI кодовой ветки до ревью: порядок in_dev -> verifying -> review (ADR-0015)

## Подход

Разбор SPEC доведён до конкретного диффа (описан ниже целиком, чтобы
решение Оператора по эскалации не требовало повторного анализа), но
реализация не начата — см. «Эскалация»: код `orchestrator/fsm_advance.py`
уже переписан ДРУГОЙ живой задачей несовместимым с этим SPEC образом.

Целевой дизайн (если/когда конфликт снят):

1. **`fsm_advance.in_dev`** (сегодня строки 883-1009): все семь рубежей
   перехода `in_dev -> review` (лок `acceptance_tests/`, подтяжка main
   `fsm._pull_main_or_escalate`, `_capacity_gate_refuses`,
   `_zones_gate_refuses`, `_review_rework_gate_refuses` — уже стоят
   инлайн в этой функции; плюс два рубежа, переезжающие СЮДА из
   `review()` — прогон `acceptance.run` и сверка
   `github_adapter.ensure_head_in_origin`) остаются на переходе из
   `in_dev`, но целевое состояние финального `store.set_state` меняется
   с `"review"` на `"verifying"`; `verifying_attempts` обнуляется здесь
   же (сегодня это делает `review()` перед входом в `verifying`).
2. **`fsm_advance.review`** (сегодня строки 119-291): ветка
   `status == "approved"` лишается блока push-проверки (переезжает в
   `in_dev`, см. п.1) и блока `acceptance.run` (туда же); реестр
   замечаний (`guard.requires_registry`) остаётся здесь без изменений
   (это НЕ один из семи рубежей SPEC требования 1). После реестра —
   вместо перехода в `verifying` — прямой переход в `acceptance` с той
   же материализацией `acc_tdir`, что сегодня делает `verifying()` перед
   вызовом `fsm_autogate._maybe_autogate_acceptance` (строки 314-330);
   сам вызов автогейта переезжает сюда же, аргумент `iteration` — уже
   посчитанная в этой функции свежая переменная, не устаревший
   `t["reviewed_iter"]`.
3. **`fsm_advance.verifying`** (сегодня строки 294-349): на зелёном CI —
   переход в `"review"` вместо `"acceptance"`; блок материализации
   `acc_tdir`/вызов автогейта (строки 314-330) удаляется целиком (переехал
   в `review()`, см. п.2). Опрос CI, счётчик попыток, потолок ожидания —
   без изменений (SPEC требования 5, AC-14/AC-15).
4. **`orchestrator/review.py::review_package`**: новая часть пакета,
   несущая последнюю по времени запись журнала `fsm.
   VERIFYING_STATUS_ACTION` этой задачи (`store.task_steps` + фильтр по
   `action`) — её `detail` уже несёт sha/число проверок/причину, которую
   журналирует сегодняшний `fsm_advance.verifying` (строки 307-309);
   ревьювер получает строку статуса CI без нового опроса `ci.py`.
5. **`orchestrator/auto.py`**: изменений не требует — цикл дизъюнкции
   `while role is not None or (state == "verifying" ...)` (строка 637) и
   `_advance_verifying_poll` не зависят от того, что стоит ДО/ПОСЛЕ
   `verifying` в цепочке состояний; подсказка `AUTO_STOP_VERIFYING_RED`
   уже называет `reject`, а `_cmd_reject` уже ведёт `verifying -> in_dev`
   (`orchestrator/fsm.py:1001-1012`) — AC-14..AC-16 проходят без правки
   кода `auto.py`.
6. **Документация** (AC-17..AC-19): `docs/invariants.md` — новая строка
   реестра с цепочкой `in_dev -> verifying -> review -> acceptance ->
   merge_gate` и правка строк 27/34 (там, где текст называет рубеж на
   переходе `in_dev -> review`, — теперь `in_dev -> verifying`, рубеж
   физически переехал вместе с кодом п.1); `docs/roadmap.md` — новый
   пункт живого хвоста §2 с той же цепочкой (историческая строка 155,
   зафиксированный маршрут задачи T014 «Фиксация К3», не трогается — это
   протокол прошлого прогона, не описание текущего флоу); `orchestrator/
   artel.py:8` — схема состояний докстринга дополняется `verifying`
   между `in_dev` и `review`, строка 20 (лок `acceptance_tests/`)
   переносит название рубежа на `in_dev -> verifying`.
7. **Тесты `tests/test_fsm*.py`/`test_auto*.py`/`test_review*.py`**
   (AC-20): правка по факту прогона после реализации п.1-4 — заранее
   единственное известное надёжно: `tests/test_review_freshness.py`,
   `tests/test_auto_cycle.py` (в т.ч. `FSM_STATES`, строка 58) и `tests/
   test_review_package.py` фиксируют сегодняшний порядок сценариями
   `in_dev -> review -> verifying -> acceptance` и потребуют правки
   промежуточных ожидаемых состояний на `in_dev -> verifying -> review
   -> acceptance`; конкретный список правок с обоснованием — по
   прогону, не может быть добросовестно перечислен ДО реализации.

## Влияние на систему

Не оценено полностью: реализация не начата (см. «Эскалация»). Целевой
дизайн (п.1-4 «Подхода») не ослабляет ни один гейт/инвариант — семь
рубежей `in_dev -> review` переезжают на `in_dev -> verifying` тем же
кодом, без потери проверки ни на одном пути (SPEC требование 1 буквально
это и требует); реестр замечаний, лимит итераций ревью, автогейт
acceptance, потолок ожидания CI — все остаются на месте, только на
новых именах переходов. Открытый вопрос — конфликт с `01M1TKNXX5YN5KT
4WHG4T44JWV` (см. «Эскалация»): именно ЭТУ оценку («не ослабляет,
переезжает без потери») невозможно довести до конца, пока не решено,
чей код (этой задачи или `01M1TKNXX5...`) реализуется первым на
`fsm_advance.py`.

     `dc3f99f4`), а её приёмочная планка (`tasks/
     01M1TKNXX5YN5KT4WHG4T44JWV/acceptance_tests/`) явно фиксирует
     СТАРЫЙ порядок состояний как требование приёмки: SPEC AC-5 —
     «порядок применения гейтов и тексты отказов… для переходов
     `in_dev -> review` и `review -> verifying` не изменились
     относительно кода до рефакторинга», и `test_ac6_entry_point_shape.
     py` («Зелёный с рождения» / `_BASELINE_IF_NESTING`) меряет тело
     `in_dev`/`review` ≤ 40 строк и вложенность `if` не выше базовой,
     снятой с СЕГОДНЯШНЕЙ (дореформенной) структуры этих функций. SPEC
     этой задачи, раздел «Не входит», отдельно называет R2 и объявляет
     её «формой той же функции, независимой от порядка переходов»,
     разруливаемой зона-локом — но зона-лок разруливает ОЧЕРЁДНОСТЬ
     запуска, не смысловой конфликт: чей бы код ни смержился первым,
     планка R2 после реформы этой задачи либо перестанет отражать
     реальный маршрут (транзиты `in_dev -> review`/`review ->
     verifying`, которые эта SPEC упраздняет), либо реализация этой
     задачи (добавляющая в `in_dev` два рубежа из `review()`, см.
     «Подход» п.1) нарушит зафиксированный R2 потолок 40 строк тела —
     что делать с этим конфликтом раньше кода?

       Оператора ДО того, как R2 продолжит движение к ревью — это
       правка ЧУЖОЙ залоченной планки, вне права разработчика этой
       задачи (`conventions-core`: «правка залоченного теста — только
       через возврат в tests_writing той задачи»).
     - Вариант (б) — сначала довести R2 до merge (её код уже готов,
       PLAN.md status: ready, ждёт `review`), затем эта задача
       стартует НЕ с сегодняшнего `fsm_advance.py`, а с версии R2 после
       мержа — часть «Подход» п.1-3 придётся пересчитать под уже
       рефакторенные `GateRefusal`/каркас R2.
     - Вариант (в) — отложить/эскалировать саму R2 (снять с ревью,
       вернуть в `tests_writing` для правки планки под новый порядок)

     - Дефолт при молчании Оператора: не выбираю сам — оба варианта (б)
       и (в) меняют судьбу ЧУЖОЙ задачи, оба (а) требуют права правки

       любому из них — риск потерять либо работу R2, либо эту.
