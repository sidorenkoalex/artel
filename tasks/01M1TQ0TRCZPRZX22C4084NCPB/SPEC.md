# SPEC: CI кодовой ветки до ревью: порядок in_dev -> verifying -> review (ADR-0015)

## Контекст

Сегодня FSM ведёт задачу по маршруту `in_dev -> review -> verifying ->
acceptance -> merge_gate`: ревьювер читает код и выносит вердикт ДО
того, как код проверен на CI подтянутой головы. Сквозные инварианты
(например «SQL только в store.py») живут в `tests/` и гоняются только
CI — планка задачи их не покрывает, а ревьювер их не видит. 06.09
зафиксировано 18 эскалаций «приёмочные тесты красные после подтяжки
main» у 10 задач за двое суток; в частности наблюдатель 01M1RFVWV6:
ревью approved итерации 2, а красный сквозной инвариант всплыл только
в `verifying`, что стоило возврата и лишней итерации ревью ($5.55).
ADR-0015 (предложен 06.09, подтверждается на гейте SPEC этой задачи)
меняет порядок так, чтобы CI подтянутой головы проходил ДО того, как
ревьювер тратит вердикт.

## Требования

1. Порядок состояний FSM меняется на `in_dev -> verifying -> review ->
   acceptance -> merge_gate`. Все рубежи, сегодня стоящие на переходе
   `in_dev -> review` (подтяжка main, прогон приёмочной планки после
   подтяжки, гейт зон, гейт ёмкости, лок планки, гейт «замечания
   ревью не отработаны», сверка головы ветки на origin), переезжают на
   переход `in_dev -> verifying` целиком, без ослабления и без
   дублирования на переходе `verifying -> review`.
2. Переход `verifying -> review` происходит только по зелёному статусу
   CI подтянутой головы — по той же механике, по которой сегодня
   устроен переход `verifying -> acceptance`.
3. Возврат из ревью со статусом `changes_requested` ведёт в состояние
   `in_dev`. Повторный вход в ревью на следующей итерации снова идёт
   через `verifying`. Счётчики итераций ревью и лимит в три итерации
   не меняются.
4. Ревью-пакет несёт строку статуса CI головы (sha, число проверок,
   идентификатор прогона), построенную из данных, которые состояние
   `verifying` уже журналирует — ревьювер не гадает, проверен ли код.
5. В цикле `auto` состояние `verifying` остаётся состоянием с опросом
   CI, из которого цикл сам продолжает движение дальше. Остановка
   цикла «CI красный — решение Оператора» и потолок ожидания CI не
   меняются по существу, но теперь наступают до ревью. Подсказка
   «дальше:», которую `auto` показывает после красного статуса CI,
   называет команду `reject` применительно к состоянию `in_dev`.
6. `docs/invariants.md`, раздел `docs/roadmap.md` про флоу и текст
   схемы состояний в выводе `artel.py --help` отражают новый порядок
   состояний.
7. Планки закрытых задач в рамках этой задачи не гоняются и не
   правятся. Если существующая приёмочная планка живой задачи
   фиксирует старый порядок состояний — задача эскалируется с
   перечнем таких планок вместо их правки.

## Критерии приёмки

AC-1. Порядок состояний FSM — `in_dev -> verifying -> review ->
acceptance -> merge_gate` (вместо сегодняшнего `in_dev -> review ->
verifying -> acceptance -> merge_gate`).

AC-2. Рубеж «подтяжка main» стоит на переходе `in_dev -> verifying` и
не задействован повторно на переходе `verifying -> review`.

AC-3. Рубеж «прогон приёмочной планки после подтяжки» стоит на
переходе `in_dev -> verifying` и не задействован повторно на переходе
`verifying -> review`.

AC-4. Гейт зон стоит на переходе `in_dev -> verifying` и не
задействован повторно на переходе `verifying -> review`.

AC-5. Гейт ёмкости стоит на переходе `in_dev -> verifying` и не
задействован повторно на переходе `verifying -> review`.

AC-6. Лок приёмочной планки стоит на переходе `in_dev -> verifying` и
не задействован повторно на переходе `verifying -> review`.

AC-7. Гейт «замечания ревью не отработаны» стоит на переходе `in_dev
-> verifying` и не задействован повторно на переходе `verifying ->
review`.

AC-8. Сверка головы ветки задачи на origin стоит на переходе `in_dev
-> verifying` и не задействована повторно на переходе `verifying ->
review`.

AC-9. Переход `verifying -> review` происходит только по зелёному
статусу CI подтянутой головы ветки задачи.

AC-10. Возврат из ревью со статусом `changes_requested` переводит
задачу в состояние `in_dev`.

AC-11. Повторный вход в ревью на следующей итерации (после возврата
из `changes_requested`) снова проходит через состояние `verifying`.

AC-12. Счётчики итераций ревью и лимит в три итерации не меняются
новым порядком переходов (поведение при достижении лимита — как
сегодня).

AC-13. Ревью-пакет несёт строку статуса CI головы: sha, число
проверок, идентификатор прогона — построенную из данных, которые
состояние `verifying` уже журналирует.

AC-14. В цикле `auto` состояние `verifying` остаётся состоянием с
опросом CI, из которого цикл сам продолжает движение дальше без
ручного вмешательства.

AC-15. Остановка цикла `auto` «CI красный — решение Оператора» и
потолок ожидания CI в состоянии `verifying` не изменены по существу
относительно сегодняшнего поведения на переходе `verifying ->
acceptance`.

AC-16. Подсказка «дальше:», которую `auto` показывает после красного
статуса CI в состоянии `verifying`, называет команду `reject`
применительно к состоянию `in_dev`.

AC-17. `docs/invariants.md` описывает порядок состояний
`in_dev -> verifying -> review -> acceptance -> merge_gate`.

AC-18. Раздел `docs/roadmap.md` про флоу FSM описывает порядок
состояний `in_dev -> verifying -> review -> acceptance -> merge_gate`.

AC-19. Текст схемы состояний в выводе `artel.py --help` отражает
порядок состояний `in_dev -> verifying -> review -> acceptance ->
merge_gate`.

AC-20. Существующие тесты `tests/test_fsm*.py`, `tests/test_auto*.py`,
`tests/test_review*.py` остаются зелёными; правка ассерта в них
допущена только там, где ассерт фиксирует старый порядок состояний
(`in_dev -> review -> verifying`), и каждая такая правка перечислена в
`PLAN.md` с обоснованием, какой именно ассерт и почему фиксировал
старый порядок.

AC-21. В рамках этой задачи не запускаются и не правятся приёмочные
планки закрытых задач.

AC-22. Если приёмочная планка живой задачи (не закрытой) фиксирует
старый порядок состояний FSM, задача эскалируется списком таких задач
вместо правки их планок.

## Оценка объёма и деление

Сработавшие сигналы «подозрения на большой объём»:
- число критериев приёмки (22) ≥ 10;
- число файлов/модулей зоны (`orchestrator/fsm.py`,
  `orchestrator/fsm_advance.py`, `orchestrator/auto.py`,
  `orchestrator/review.py`, `orchestrator/config.py`,
  `docs/invariants.md`, `docs/roadmap.md`, `tests/`) ≥ 5;
- `budget_usd` (40) ≥ 30;
- зона задевает механизм, на который опирается запись в
  `docs/invariants.md` (инвариант 13, свежесть вердикта ревью, и
  формулировка маршрута `review -> acceptance`, которую нужно
  переписать под новый порядок).

**Обоснование монолита.** Смена порядка переходов атомарна: рубежи
перехода `in_dev -> review` (подтяжка main, прогон планки, гейт зон,
гейт ёмкости, лок планки, гейт «замечания не отработаны», сверка
головы на origin) и семантика перехода `verifying -> review` по
зелёному CI образуют один маршрут, который либо весь стоит на новом
переходе, либо не стоит вовсе. Промежуточное состояние, где часть
рубежей уже переехала на `in_dev -> verifying`, а часть (или переход
по CI) осталась на старом месте, оставляет систему в состоянии, когда
либо код входит в ревью без прохождения части рубежей, либо рубежи
срабатывают дважды — оба исхода нарушают требование 1 буквально.
Разрезать по границам зон тоже нельзя: FSM-переходы (`orchestrator/
fsm.py`, `orchestrator/fsm_advance.py`), опрос в `auto` и содержимое
ревью-пакета (`orchestrator/review.py`) меняются согласованно одним
рефакторингом маршрута — часть без остальных не мержима с зелёной
планкой (тесты `tests/test_fsm*.py`/`test_auto*.py`/`test_review*.py`
будут падать, пока не поменяны согласованно все стороны маршрута).

## Не входит

- Замена CI локальным прогоном `tests/` в worktree — отдельный
  кандидат, если очередь GitHub станет узким местом.
- Изменение `merge_gate`: второй рубеж CI на этом переходе остаётся
  как есть (ADR-0013).
- Гейт ёмкости и трёхточечный дифф (01M1SG9T96) — сама механика гейта
  ёмкости этой задачей не меняется, меняется только переход, на
  котором она стоит.
- Рефакторинг гейтов `in_dev`/`review` в предикаты с единым исходом
  (R2, 01M1TKNXX5) и вынос подтяжки main в модуль `pull.py` (R3,
  01M1TKP08P) — эти задачи меняют форму тех же функций независимо от
  порядка переходов; на момент SPEC обе ещё не смержены в main (стоят
  в `tests_writing`, кода нет), реальную очерёдность разруливает
  зона-лок оркестратора.
- Правка `docs/adr/0009-verifying-route.md` и создание/правка
  `docs/adr/0015-ci-before-review.md` — вне зон этой задачи; ADR-0015
  подтверждается Оператором на гейте SPEC, а не правкой файла этой
  задачей.
- Правка `docs/design.md` (диаграмма FSM там уже отмечена как
  устаревшая проекция, не источник истины).
- Правка/запуск приёмочных планок закрытых задач (см. AC-21).

## Материалы

- ADR-0009 (`docs/adr/0009-verifying-route.md`) — решение, которым
  `verifying` было вставлено между `review` и `acceptance`; эта задача
  меняет местами `review` и `verifying`, не убирая ни одно из них.
- Наблюдатель 01M1RFVWV6 (06.09) — конкретный случай двойной итерации
  ревью из-за красного сквозного инварианта, обнаруженного в
  `verifying` после approved-вердикта.
