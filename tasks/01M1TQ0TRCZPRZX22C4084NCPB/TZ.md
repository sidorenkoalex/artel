# ТЗ: CI кодовой ветки до ревью: порядок in_dev -> verifying -> review (ADR-0015)

# ТЗ: CI кодовой ветки до ревью — порядок in_dev → verifying → review (ADR-0015)

Источник: ADR-0015 (`docs/adr/0015-ci-before-review.md`, предложен
06.09, подтверждается на гейте SPEC этой задачи) и анализ причин
06.09: 18 эскалаций «приёмочные тесты красные после подтяжки main» у
10 задач за двое суток; наблюдатель 01M1RFVWV6 — ревью approved
итерации 2, красный инвариант «SQL только в store.py» в `verifying`,
возврат, итерация 3 за $5.55. Сквозные инварианты живут в `tests/` и
гоняются только CI; планка задачи их не покрывает по построению, а
ревьювер сегодня читает код до CI.

Сегодня: `in_dev -> review -> verifying -> acceptance -> merge_gate`;
подтяжка main (`fsm._pull_main_or_escalate`), прогон планки после
подтяжки, гейт зон, гейт ёмкости и сверка лока планки стоят на
`in_dev -> review` (`fsm.py`, `fsm_advance.py:review`); ожидание CI —
`fsm_advance.py:verifying` с опросом из `auto` (SPEC T086).

Требуется:
1. Порядок состояний `in_dev -> verifying -> review -> acceptance ->
   merge_gate`. Все рубежи перехода `in_dev -> review` (подтяжка main,
   прогон планки после подтяжки, гейт зон, гейт ёмкости, лок планки,
   гейт «замечания ревью не отработаны», сверка головы на origin)
   переезжают на `in_dev -> verifying` без ослабления и без
   дублирования; `verifying -> review` — только по зелёному CI
   подтянутой головы, как сегодня `verifying -> acceptance`.
2. Возврат из ревью (`changes_requested`) ведёт в `in_dev`; повторный
   вход в ревью снова через `verifying`. Счётчики итераций ревью и
   лимит три — без изменений.
3. Ревью-пакет несёт строку статуса CI головы (sha, число проверок,
   идентификатор прогона) — из данных, которые `verifying` уже
   журналирует; ревьювер не гадает, проверен ли код.
4. `auto`: `verifying` остаётся состоянием с опросом CI, из которого
   цикл сам идёт дальше (T086); остановки цикла «CI красный — решение
   Оператора» и потолок ожидания — без изменений, но теперь до ревью.
   Подсказка «дальше:» после красного CI называет `reject` в `in_dev`.
5. `docs/invariants.md`, `docs/roadmap.md` §флоу и `README`/схема
   состояний в `artel.py --help` — обновить порядок (документы вне
   защищённых путей правит разработчик; текст help — в коде).
6. Тесты: (а) переходы FSM в новом порядке, включая возврат из ревью
   и повторный `verifying`; (б) все рубежи требования 1 срабатывают
   именно на `in_dev -> verifying` (по одному тесту на рубеж: подтяжка,
   планка, зоны, ёмкость, лок, «замечания не отработаны», голова на
   origin) и НЕ срабатывают повторно на `verifying -> review`;
   (в) ревью-пакет несёт строку CI; (г) существующие
   `tests/test_fsm*.py`, `tests/test_auto*.py`, `tests/test_review*.py`
   зелёные — правка ассертов допускается только там, где ассерт
   фиксирует старый порядок состояний, и каждая такая правка
   перечислена в PLAN с обоснованием; каждый новый тест ловит
   заявленную мутацию (рубеж оставлен на старом переходе / вход в
   ревью без CI).
7. Планки закрытых задач не гоняются и не правятся (история не
   переписывается); если существующая планка живой задачи фиксирует
   старый порядок — эскалация с перечнем, не правка.

Зоны: orchestrator/fsm.py, orchestrator/fsm_advance.py,
orchestrator/auto.py, orchestrator/review.py, orchestrator/config.py,
docs/invariants.md, docs/roadmap.md, tests/.
Порядок: после мержа R2 (01M1TKNXX5, гейты `fsm_advance` как
предикаты) и R3 (01M1TKP08P, подтяжка в `pull.py`) — они перекраивают
те же функции; сверить по `status`. Сигналы деления сработают
(инварианты, ≥5 файлов): ожидается обоснование монолита — смена порядка
переходов атомарна, промежуточное состояние с рубежами на двух
переходах неработоспособно.

Не входит: замена CI локальным прогоном `tests/` в worktree (отдельный
кандидат, если очередь GitHub станет узким местом); изменение
`merge_gate` (второй рубеж CI остаётся, ADR-0013); гейт ёмкости и
трёхточечный дифф (01M1SG9T96).
