# SPEC: reject на гейте SPEC: возврат аналитику с причиной, гейт переделки и бриф «Причина возврата»

## Контекст

Протокол гейта SPEC (`docs/operator-gates.md`, раздел «Гейт SPEC»,
строки 82–85) называет отказ (`reject`) одним из двух исходов помимо
`approve`, но `orchestrator/fsm.py::_cmd_reject` (строки 893–932)
принимает только `merge_gate`, `verifying` и `acceptance` — на
`spec_gate` команда отвечает «reject применим только в acceptance,
merge_gate или verifying». Инцидент 20.09 (задача 01M2YSHDKW: SPEC
расходился с кодом — класс отказа в `auto.py` требовал зоны, которой не
было) оставил Оператору единственный рычаг — ручную редактуру текста
аналитика; 11.09 и 20.09 сессия писала SPEC в артефактную ветку
функциями пульта сценарием, обход дважды записан в копилку. Механика
возврата с причиной для других состояний уже есть: запись `state ->
<состояние>` с detail «возврат из <state>: <причина>», гейт переделки
`orchestrator/auto.py::_rework_gate_blocks` (состояние `spec_writing`
уже входит в `_REWORK_GATE_STATES`) и раздел «Причина возврата» брифа
роли (`orchestrator/brief.py`, `RETURN_REASON_HEADER`). Задача
достраивает этот же приём на `spec_gate`.

## Требования

1. Команда `reject <id> "<причина>"` в состоянии `spec_gate` переводит
   задачу в `spec_writing` — записью `state -> spec_writing` с detail
   «возврат из spec_gate: <причина>», тем же приёмом, каким `_cmd_reject`
   возвращает задачу из `verifying`.
2. Этот возврат не увеличивает счётчики `review_iters` и
   `accept_rejects`.
3. Этот возврат не пишет `tasks.zones` и `budget_usd` отклонённого SPEC:
   оба значения остаются такими, какими были до команды (они пишутся
   только на `approve`).
4. Пустая причина на `spec_gate` — отказ команды: состояние не меняется,
   запись в журнал о переходе не появляется.
5. Аналитик после такого возврата получает причину: раздел «Причина
   возврата» его брифа несёт текст detail этой записи — то есть
   `orchestrator/brief.py` строит раздел для `spec_writing` по записи
   `state -> spec_writing` возврата так же, как строит его для `in_dev`
   (сегодня приход из `spec_gate` возвратом не считается).
6. Гейт переделки: после записи `state -> spec_writing` с основанием
   возврата предварительный `advance` по готовому SPEC (`status: ready`
   в ветке задачи) не уводит задачу обратно на `spec_gate` до
   завершённого шага analyst — запись возврата служит анкером
   `auto._role_step_since_state_entry` (её detail не входит в
   `_ESCALATED_RETURN_DETAILS`). После завершённого шага analyst переход
   на `spec_gate` снова возможен.
7. Поведение `reject` в остальных состояниях не меняется: возврат из
   `acceptance`/`merge_gate`/`verifying` — как сегодня; в состояниях,
   где команда неприменима, — прежний именованный отказ.
8. `docs/operator-gates.md`, раздел «Гейт SPEC»: фраза «отказ (`reject`)»
   получает форму команды и порядок — `reject` с причиной → `auto` →
   аналитик переписывает SPEC → новый `approve`; редактура Оператором
   остаётся законным ходом для правок в одну-две строки.
9. Тесты в `tests/` покрывают требования 1–7; существующие тесты
   `reject`/`auto`/брифа остаются зелёными.

## Критерии приёмки

AC-1. Задача в `spec_gate`; `reject <id> "причина"` → состояние
`spec_writing`, в журнале шагов есть запись `state -> spec_writing` с
detail «возврат из spec_gate: причина».

AC-2. После возврата AC-1 `review_iters` и `accept_rejects` задачи равны
значениям до команды.

AC-3. После возврата AC-1 `tasks.zones` и `budget_usd` задачи равны
значениям до команды — содержимое отклонённого SPEC в них не записано.

AC-4. Задача в `spec_gate`; `reject <id> ""` (причина пустая или из одних
пробелов) → команда отказывает, состояние остаётся `spec_gate`, записи
`state -> spec_writing` в журнале нет.

AC-5. `reject` из `acceptance`, `merge_gate` и `verifying` ведёт себя как
до задачи (состояние-исход, detail записи, счётчики); `reject` в
состоянии, где он неприменим (например `in_dev`), по-прежнему отказывает
прежним текстом отказа.

AC-6. Бриф роли analyst, собранный после возврата AC-1, несёт раздел
«Причина возврата» с дословным текстом причины Оператора.

AC-7. После возврата AC-1 при SPEC со `status: ready` в ветке задачи
цикл `auto` запускает шаг analyst, а не переводит задачу на `spec_gate`;
после записи о завершённом шаге analyst переход на `spec_gate` снова
проходит.

AC-8. `docs/operator-gates.md`, раздел «Гейт SPEC», содержит форму
команды `reject <id> "<причина>"` и порядок «`reject` → `auto` →
аналитик переписывает SPEC → новый `approve`», сохраняя редактуру
Оператором как законный ход для правок в одну-две строки.

AC-9. Полный прогон `tests/` зелёный — включая существующие тесты
`reject`, `auto` и брифа.

## Оценка объёма и деление

Сработавший сигнал: число затрагиваемых модулей/файлов зоны — в тексте
SPEC упомянуты пять путей кода (`orchestrator/fsm.py`,
`orchestrator/auto.py`, `orchestrator/brief.py` как зоны;
`orchestrator/fsm_advance.py`, `orchestrator/artifact_branch.py` — как
границы «не входит»), порог `config.SPLIT_SIGNAL_ZONE_FILES` = 5.
Прогноз диффа: 12 КиБ (порог сигнала — 128 КиБ).

Решение: **монолит**. Резать нечего: `reject` на `spec_gate` без анкера
гейта переделки (требование 6) возвращает задачу аналитику и тут же
уводит её обратно на `spec_gate` предварительным `advance` по тому же
готовому SPEC — возврат не состоится; без раздела «Причина возврата»
(требование 5) аналитик переписывает SPEC, не видя причины отказа, и
повторяет его. Обе части — по одной функции в своём модуле, и обе
обслуживают один переход; промежуточное состояние (любая часть без
остальных) даёт рабочую команду с неработающим циклом переделки, то
есть систему в нерабочем состоянии. Фактически задача — три правки по
5–20 строк плюс тесты и абзац документации.

## Не входит

- Команда пульта для операторской редактуры SPEC на гейте: правка текста
  остаётся ручной, обход при необходимости — записью в копилку.
  `orchestrator/artifact_branch.py` этой задачей не легализуется и не
  меняется (только чтение).
- `reject` на `escalated` — там работает `answer`.
- Изменение шаблона SPEC (`templates/SPEC.md`).
- `orchestrator/fsm_advance.py`: обработчик `spec_writing` не меняется
  (только чтение).
- Введение отказа на пустую причину для `reject` в
  `acceptance`/`merge_gate`/`verifying`: сегодня `_cmd_reject` не
  проверяет причину ни в одном состоянии, а ТЗ (пункт 5) требует от
  прочих состояний «поведение как сегодня» — требование 4 вводит проверку
  только на `spec_gate`.
- `docs/backlog.md` — источник задачи, не меняется (только чтение).
