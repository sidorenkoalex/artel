## Пути обхода гейтов
- Фильтр алертов можно переписать как «проекты задач набора +
  `DEFAULT_TARGET`», выбросив ветку id задачи и ветку проекта наблюдения.
  AC-4..AC-6 такую правку пропустят, и алерты `attention`/`warning`
  с `target` = id задачи (`orchestrator/alerts.py:120`, `:143`) пропадут из
  дозора наблюдения. Сегодня их держит только код, тестом это не
  закреплено. Закрывается отклонениями 1–2.
- Требование 6 разрешает метку «в строке задачи» в любом месте. Метка
  перед id формально выполняет AC-8, но ломает поиск строки по
  `startswith(task_id)` в существующих тестах. Разработчик может пойти
  «чинить» эти тесты, а это смена существующих методов `tests/` без
  раздела «Меняемое поведение». Закрывается отклонением 3.
- Требование 7 разработчик может выполнить так: дописать `target=` в вызовы
  `_row(...)` существующих тестов `TileHtmlTest`/`BoardHtmlTest`.
  Утверждения при этом не меняются, и гейт неослабления
  (docs/invariants.md:68) это пропустит. Но SPEC такой правки не
  предусматривает (отклонение 4).
- Других путей обхода нет: AC-5 требует, чтобы тест проходил и на коде
  до правки; отказы `_launch_observation` кроме проекта держат
  существующие тесты.

## Вердикт
concerns. Ни одно отклонение не мешает вести SPEC дальше, все решаются
уточнением на гейте:

1. AC-4/AC-5 не держат алерт с `target` = id задачи набора (требование 3,
   `orchestrator/watch.py:299`, ветка `in task_ids`). Снятие этой ветки
   никакой тест не поймает; реальные алерты с таким `target` —
   `orchestrator/alerts.py:120`, `:143`, `orchestrator/models.py:1682`.
   Предложение: в AC-4 добавить алерт с `target` = id внешней задачи,
   в AC-5 — с `target` = id задачи артели.
2. Ветка «проект наблюдения» требования 3 (`row["target"]`, watch.py:299)
   не отличима ни в одном AC: проект наблюдения всегда совпадает с
   проектом одной из задач. Чтобы её поймать, нужен случай вроде
   «`observe remove` убрал все задачи проекта P, алерт P виден» — либо
   решение Оператора, что эта ветка необязательна.
3. Требование 6 не задаёт место метки `[<проект>]`. Существующие тесты
   ищут строку `status` по `startswith(task_id)`
   (`tests/test_01m484rnv3qbdy3b0m16j916zp_zone_lock_projects.py:68`,
   `tests/test_01m484rnv3qbdy3b0m16j916zp_wave_breaker_projects.py:184`,
   `:190`), поэтому метку надо ставить после id.
4. Требование 7 «для каждой задачи» конфликтует с фикстурами
   `tests/test_report.py:44-46`, `:205-231`: словари без ключа `target`,
   `row["target"]` даст `KeyError`. SPEC не решает, расширяются ли эти
   фикстуры или `_tile_html` читает проект терпимо. Там же: колонка
   `tasks.target` допускает NULL (`orchestrator/schema.py:115`, `DEFAULT`
   без `NOT NULL`), а `store.task_target` считает NULL артелью. SPEC не
   говорит, что `status`/`report` показывают для такой задачи (не
   `[None]`).
5. AC-9 «плитка содержит проект»: проверка вхождением ложно пройдёт,
   если имя проекта есть в `title`/`id` фикстуры. Это указание автору
   тестов: брать название без имени проекта или проверять поле плитки.
6. Факт: фильтр алертов — `orchestrator/watch.py:299`, не `:297`
   (SPEC, «Контекст», «Материалы»). Не названо: `observe events`
   (`orchestrator/artel.py:1085-1093`) меняется вместе с `watch` через
   общий `_observation_events`.

Монолит при пяти зонах обоснован в «Оценке объёма и деления»; решение
по нему SPEC оставляет Оператору на гейте.
