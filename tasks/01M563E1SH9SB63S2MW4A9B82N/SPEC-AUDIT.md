## Пути обхода гейтов
- Фильтр `observe events` можно оставить старым, если расширенный набор целей передавать в `_observation_events` только из `_watch_observation`. Буквально SPEC выполнен («`watch` выводит…»), AC зелёные, а `observe events` — тот же канал разбора событий для сессии Оператора — молча теряет алерты внешнего проекта и пульта. Это отклонение 2.
- Проект наблюдения можно брать из отсортированного списка `_validated_observation_tasks`. Тогда AC-3 «проект первой задачи» проходит на тесте, где первая задача — минимальная по сортировке, а на деле зависит от id. Это отклонение 1.
- Гейтов пульта (зоны, неослабление, бюджет) задача не трогает. Существующих тестов, которые пришлось бы ослаблять, нет: фактов по `tests/` выше и проверки поиском по литералам снимаемых отказов достаточно.

## Вердикт
concerns. SPEC годен к гейту, но три пункта стоит закрыть условием критериев.

Отклонения:
1. **AC-3 не ловит сортировку.** Правило «без `--project` — проект первой задачи из `--tasks`» (SPEC тр.2, AC-3) пропускает правдоподобную мутацию. Проект можно взять из `sorted(set(...))` результата `_validated_observation_tasks` (`orchestrator/artel.py:1160`), а не из `--tasks[0]`. Нужно условие в AC-3: первая задача `--tasks` не минимальна по сортировке id (например, внешняя `T002` перед артельной `T001` → проект внешней).
2. **`observe events` без критерия.** В SPEC тр.3 сказано, что `observe events` меняется вместе с `watch` (`orchestrator/artel.py:1085-1093`), но ни одного AC на это нет. Расширенный фильтр, переданный только из `watch._watch_observation` (`orchestrator/watch.py:392`), проходит все AC-4–AC-6, а `observe events` остаётся на старом фильтре `watch.py:299`. Нужен AC: `observe events` на смешанном наблюдении выводит алерты проекта внешней задачи и проекта артели и не выводит алерт третьего проекта.
3. **ТЗ п.5 для внешнего проекта закреплено не полностью.** ТЗ п.5 требует «зафиксировать тестами до правки» для наблюдения одного проекта. SPEC закрепляет это (тест проходит на коде до правки) только для наблюдения артели (AC-5). У AC-6 нет условия, что проверка прежних событий и алертов своего проекта и отсутствия третьего проекта у наблюдения одного внешнего проекта проходит до правки; добавка алертов артели должна проверяться отдельно. Вопрос на гейте: принять как есть или добавить это условие.

Замечания (не отклонения, на усмотрение Оператора):
4. AC-8 «содержит `[sled]` после id» не требует метки сразу за id: метка в конце строки тоже проходит. Решение Оператора №1 п.3 говорит «после id», так что формально совпадает.
5. Если снять сверку проекта в `orchestrator/artel.py:882`, текст отказа `:883-885` «другой сессии или проекту» станет неточным. Правя текст, нужно сохранить подстроку «другой сессии» — её держит `tests/test_launch_observation_refusals.py:64`. SPEC этого якоря не называет.
6. Принято в «Не входит» (ANSWER-1, ответ 1), но стоит знать: задача sled в наблюдении артели без флага `--observation` получает отказ `orchestrator/artel.py:873-876` с советом `observe add` к наблюдению, где она уже есть. Совет ведёт по кругу до отдельной задачи автоподбора.
