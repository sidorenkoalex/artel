# QUESTIONS: Одно наблюдение на задачи разных проектов; проект задачи в status

## Вопросы

Требования 1–3, 5 и 6 ТЗ укладываются в зоны `orchestrator/artel.py`,
`orchestrator/watch.py`, `orchestrator/catalog.py`, `orchestrator/report.py`,
`tests/`. Требование 4 в эти зоны не укладывается. ТЗ прямо велит
эскалировать правку вне зон до SPEC, поэтому вопрос ниже.

1. **Требование 4: наблюдение для `run`/`auto` без флага `--observation` выбирает `store.matching_observation` (`orchestrator/store.py:223-234`, условие `o.target=?` с проектом задачи), а `store.py` по ТЗ только на чтение. Задачу sled в наблюдении, заведённом на артель, этот выбор не находит. Та же фильтрация по проекту стоит в `store.session_observations` (`orchestrator/store.py:237-249`). Через неё подсказка запуска `cycle_hint.launch_hint` (`orchestrator/cycle_hint.py:17-21`, вне зон) предложит `observe register` вместо существующего наблюдения. Что входит в требование 4?**
   - A) Только именованное `--observation <ID>`: в `_launch_observation` (`orchestrator/artel.py:882`) снимается сверка `observer["target"] != target`, остаётся сверка сессии, состояния и членства задачи. Без флага выбор прежний, по проекту задачи. Подсказка запуска не меняется. В «Не входит» SPEC — автоподбор без флага и подсказка.
     - ломается: `run <sled-id>` без `--observation`, когда sled-задача есть только в наблюдении артели, отказывает как сегодня («нет активного наблюдения текущей сессии и проекта») — Оператор обязан назвать `--observation`; подсказка запуска по-прежнему советует `observe register`
     - ослабляется: ничего; сверка сессии и членства в `orchestrator/artel.py:882-895` остаётся
     - цена: в рамке $30, зоны не меняются
     - чьё решение: Оператор (трактовка требования 4)
   - B) Именованное и автоподбор, без правки `store.py`: в `artel.py` добавляется свой запрос выбора наблюдения без условия на проект (дубль логики `matching_observation` в зоне задачи). Подсказка `cycle_hint` не меняется.
     - ломается: ничего из сегодняшнего; подсказка запуска для смешанного наблюдения остаётся неверной
     - ослабляется: единственное место правила выбора наблюдения (`orchestrator/store.py:223` — docstring «наблюдение сессии и проекта», SPEC 01M4FZ6QYPPKYQZFEX14QH8XT6, требование 1): правил становится два, они могут разойтись
     - цена: в рамке $30, зоны не меняются
     - чьё решение: Оператор
   - C) Именованное и автоподбор с расширением зон: в зоны входят `orchestrator/store.py` (`matching_observation`, `session_observations` ищут наблюдение сессии с включённой задачей, без условия на проект наблюдения; схема БД не меняется) и `orchestrator/cycle_hint.py` (подсказка находит смешанное наблюдение).
     - ломается: выбор наблюдения без флага при нескольких активных наблюдениях сессии разных проектов может пасть на наблюдение другого проекта, если задача включена в оба; порядок остаётся прежним (свежесть связи, затем время создания)
     - ослабляется: привязка выбора к проекту в `orchestrator/store.py:230`; сессия и членство задачи остаются
     - цена: +2 файла зоны (7 файлов): класс ~$45 по калибровке и сигнал деления «≥ 5 файлов» (он есть и сейчас), выше рамки $30
     - чьё решение: Оператор (зоны, рамка)
   - дефолт: A — буквальное чтение «`auto --observation`» в ТЗ, без выхода за зоны и рамку; автоподбор и подсказку можно вынести отдельной задачей.

2. **Требование 1: проект наблюдения при `observe register` со смешанным набором задач. Сейчас проект берётся у первой задачи из `--tasks`, а `--project`, не совпавший с ним, отказывает (`orchestrator/artel.py:1041-1044`). Какое правило записать в SPEC?**
   - A) Поле `target` наблюдения — проект по умолчанию: `--project`, если он задан, иначе проект первой задачи. `--project` отказывает, только если ни одна задача из `--tasks` не принадлежит этому проекту. Для набора одного проекта поведение прежнее (требование 5).
     - ломается: `observe register --tasks <sled>,<artel> --project artel` сегодня отказывает, после правки проходит — так задумано
     - ослабляется: сверка `--project` с проектом задачи (`orchestrator/artel.py:1043`) сужается до «хотя бы одна задача этого проекта»
     - цена: в рамке, без изменения схемы БД
     - чьё решение: роль (ТЗ отдаёт выбор аналитику), вынесено сюда, потому что батч уже идёт
   - B) Проект первой задачи, `--project` сверяется только с ней, как сейчас.
     - ломается: ничего; на смешанном наборе правильность `--project` зависит от того, какая задача стоит первой в списке
     - ослабляется: ничего
     - цена: в рамке
     - чьё решение: роль
   - дефолт: A — проект по умолчанию задаётся явно и не зависит от порядка задач в `--tasks`.
