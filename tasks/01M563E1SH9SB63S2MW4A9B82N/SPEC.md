# SPEC: Одно наблюдение на задачи разных проектов; проект задачи в status

## Контекст
Наблюдение привязано к одному проекту. `observe register|add` отказывает
задаче другого проекта (`orchestrator/artel.py:1150-1160`,
`_validated_observation_tasks`: «задача … принадлежит другому проекту»).
17.10 для задачи sled пришлось заводить второе наблюдение и второй `watch`.
Фильтр алертов дозора (`orchestrator/watch.py:299`) пропускает алерт только
по id задачи наблюдения или по проекту наблюдения. Поэтому алерты уровня
пульта, заведённые на проект артели (стоп-кран волны, `alerts.py:238`;
лишняя рабочая копия, `doctor/orphans.py:185`), наблюдению sled не видны.
`status` и `report` не показывают проект задачи
(`orchestrator/catalog.py:970-977`, `orchestrator/report.py:544`), и задачи
артели и sled в их выводе не различить.

## Требования

1. `observe register` и `observe add|remove` принимают задачи любых
   проектов. Проверка «задача принадлежит другому проекту»
   (`orchestrator/artel.py:1157-1158`) снимается. Несуществующая задача
   отказывается как сегодня, наблюдение и его набор задач не меняются.
2. Поле проекта наблюдения (`target` в `store.observation`) остаётся. Это
   проект наблюдения по умолчанию (ANSWER-1, ответ 2):
   - `observe register --project P` записывает проект `P`. Отказ — только
     когда ни одна задача из `--tasks` не принадлежит `P`; наблюдение тогда
     не создаётся.
   - Без `--project` записывается проект первой задачи из `--tasks`.
   - Порядок задач в `--tasks` при заданном `--project` на результат не
     влияет.
   - `observe add|remove` проект наблюдения не меняют.
   Схема БД не меняется.
3. `watch --observation <ID>` выводит события шагов всех задач набора
   наблюдения, какого бы проекта они ни были. Из алертов выводится алерт,
   у которого `target` совпадает с одним из четырёх:
   - id задачи набора;
   - проект любой задачи набора;
   - проект наблюдения — в том числе когда в наборе после `observe remove`
     не осталось ни одной задачи этого проекта;
   - проект артели (`config.DEFAULT_TARGET`, алерты уровня пульта).
   Алерт, `target` которого не совпадает ни с одним из четырёх, не
   выводится. `observe events` читает события той же функцией
   (`watch._observation_events`, `orchestrator/artel.py:1085-1093`) и
   меняется вместе с `watch`.
4. `run <id> --observation <ID>` и `auto <id> --observation <ID>` принимают
   задачу, если её проект не совпадает с проектом названного наблюдения:
   задачу внешнего проекта в наблюдении артели и задачу артели в
   наблюдении внешнего проекта. Сверка проекта наблюдения с проектом
   задачи в `_launch_observation` (`orchestrator/artel.py:882`) снимается.
   Остальные отказы остаются: наблюдение другой сессии, не найдено, не
   активно, задачи нет в наборе, гейт свежести связи.
5. У наблюдения, все задачи которого принадлежат одному проекту, поведение
   `observe` и `watch` не меняется:
   - тот же проект наблюдения и тот же набор задач у `register`/`add`/`remove`;
   - те же события шагов;
   - те же алерты, плюс единственная добавка из требования 3 — алерты
     проекта артели у наблюдения внешнего проекта.
   У наблюдения артели вывод `watch` прежний полностью. Это поведение
   фиксируется тестами, которые проходят на коде до правки.
6. `status` показывает проект задачи меткой `[<проект>]` в строке задачи,
   если проект не артель (например, `[sled]`). Метка стоит после id задачи:
   строка по-прежнему начинается с id (существующие тесты ищут её по
   `startswith(task_id)`). Строка задачи артели не меняется. Задача с
   `target` NULL показывается как задача артели: без метки, без `[None]`.
7. `report` показывает проект задачи внешнего проекта на её плитке
   (`orchestrator/report.py`, `_tile_html`) отдельным элементом плитки,
   содержимое которого — имя проекта. Плитка задачи артели — с `target`,
   равным проекту артели, с `target` NULL или без ключа `target` в строке —
   метки проекта не несёт и не меняется. `_tile_html` читает проект
   терпимо: отсутствие ключа `target` не приводит к ошибке. Фикстуры
   `tests/test_report.py` (строки без ключа `target`, `:44-46`) не
   правятся.
8. Тесты требований 1–7 детерминированы и без сети. В них наблюдение
   держит задачу артели и задачу внешнего проекта.

## Критерии приёмки

AC-1. `observe register --tasks <задача артели>,<задача внешнего проекта>`
завершается успешно, и в наборе наблюдения обе задачи. `observe register`
или `observe add` с несуществующей задачей в `--tasks` отказывает, и
наблюдение не создаётся либо его набор не меняется.

AC-2. `observe add <ID> --tasks <задача внешнего проекта>` к наблюдению
артели завершается успешно, и задача попадает в набор. Это же работает в
обратную сторону: задача артели добавляется к наблюдению внешнего проекта.
`observe remove` убирает такую задачу из набора.

AC-3. Проект наблюдения при `observe register`:
- без `--project` — проект первой задачи из `--tasks`;
- с `--project P`, где хотя бы одна задача набора принадлежит `P`, — `P`
  при любом порядке задач в `--tasks`;
- с `--project Q`, где ни одна задача набора не принадлежит `Q`, — отказ,
  наблюдение не создаётся.

AC-4. На наблюдении с задачей артели и задачей внешнего проекта
`watch --observation <ID>` выводит:
- события шагов обеих задач;
- алерт с `target` — id внешней задачи;
- алерт с `target` — проектом внешней задачи;
- алерт с `target` — проектом артели (алерт уровня пульта).

Алерт с `target` третьего проекта, не связанного ни с одной задачей набора
и не совпадающего ни с проектом наблюдения, ни с проектом артели, не
выводится.

Наблюдение внешнего проекта `P` (`observe register --project P`) с задачей
артели и задачей проекта `P`: после `observe remove` задачи проекта `P` в
наборе остаётся только задача артели, и `watch --observation <ID>` всё равно
выводит алерт с `target` = `P`.

AC-5. У наблюдения, все задачи которого из одного проекта артели,
`observe register|add` даёт тот же проект наблюдения и тот же набор задач,
что до правки. `watch` даёт те же события шагов и те же алерты, что до
правки: алерт с `target` — id задачи артели из набора выводится, алерт
третьего проекта по-прежнему не выводится. Тест этого критерия проходит и на
коде до правки.

AC-6. У наблюдения, все задачи которого из одного внешнего проекта,
`watch` выводит его прежние события шагов и алерты своего проекта. К ним
добавляются алерты проекта артели. Алерт третьего проекта не выводится.

AC-7. `run <задача внешнего проекта> --observation <наблюдение артели с этой
задачей в наборе>` не отказывает по проекту наблюдения. То же в обратную
сторону: задача артели в наблюдении внешнего проекта. Для `auto
--observation` — то же. Отказы для наблюдения другой сессии, неактивного
наблюдения и задачи вне набора сохраняются.

AC-8. В выводе `status` строка задачи внешнего проекта `sled` начинается с
id задачи и содержит `[sled]` после id. Строка задачи артели совпадает с
выводом до правки и метки проекта не содержит. Строка задачи с `target`
NULL метки проекта не содержит и не содержит `[None]`.

AC-9. Плитка задачи внешнего проекта в HTML `report` несёт отдельный элемент
с именем её проекта. Тест находит этот элемент в разметке плитки и сверяет
его содержимое с именем проекта, а не ищет имя проекта вхождением в текст
плитки; имя проекта в фикстуре не совпадает с `title` и `id` задачи и не
входит в них. Плитка задачи артели — с `target` проекта артели, с `target`
NULL и без ключа `target` в строке — такого элемента не несёт, и
`_tile_html` на строке без ключа `target` не падает.

## Оценка объёма и деление

Сработавшие сигналы:
- в зонах 5 элементов: `orchestrator/artel.py`, `orchestrator/watch.py`,
  `orchestrator/catalog.py`, `orchestrator/report.py` и `tests/`;
- `budget_usd` равен $30 — это рамка ТЗ.

Обоснование монолита (решение — за Оператором на гейте SPEC).

Нельзя разрезать часть наблюдения: требования 1–5, `artel.py` + `watch.py`.
Без требования 3 наблюдение примет задачу внешнего проекта (требование 1),
но `watch` не покажет алерты её проекта. Это промежуточное состояние хуже
сегодняшнего: сегодня второе наблюдение хотя бы видит алерты своего
проекта, а смешанное наблюдение молча теряло бы их. Без требования 4 задачу
внешнего проекта в наблюдении артели нельзя запустить через
`--observation`.

Часть `status`/`report` (требования 6–7, `catalog.py` + `report.py`)
технически отделима. Это две точечные правки вывода. Отдельная подзадача
добавит свои шаги analyst/test_author/reviewer (не меньше $25 по планке) и
выйдет за рамку ТЗ $30 на всю задачу. ТЗ ставит обе части в одни критерии
приёмки: одно наблюдение ведёт задачи двух проектов, а различить их в
`status`/`report` нужно для того же сценария. Прогноз диффа мал: четыре
модуля и новые тесты.
