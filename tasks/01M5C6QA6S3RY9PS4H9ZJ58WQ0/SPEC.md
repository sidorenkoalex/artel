# SPEC: Механика канарейки, часть А — реестр живого прогона, окно тишины, мерж и обходы окна во время канарейки

## Контекст
Правило `docs/operator-session.md:422`: канарейка идёт на вершине
`origin/main`, которая станет пином; пока она идёт, main не двигать,
заметки ждут `--flush`. Сегодня правило держится только дисциплиной
сессии: 19.10 мерж 01M59DP2GV одобрен во время канарейки, а запись
бэклога 59f42db4 сдвинула main с b5a8fda3, на котором шла канарейка.
Реестра живых прогонов нет (`orchestrator/artel.py:1586`,
`_detach_canary`), окно тишины `note`/`doc-commit`
(`orchestrator/notes.py:266`, `_silence_window_reason`) канарейку не
видит, файл результата отвязанного запуска собирает строки
`canary_runs` по номеру (`orchestrator/artel.py:1563`, `previous_id`) и
захватывает строки чужого одновременного прогона. Основание — решения
Оператора 19.10 (бэклог, коммит 49ce342c, пункты 1 и 2) и 20.10.

## Требования

1. **Реестр живого прогона.** `cmd_canary` (`orchestrator/canary.py:2807`)
   после выбора проверяемого sha и до первого клона пишет запись прогона
   отдельным файлом (имя — `run_stamp` и pid) в каталог состояния пульта
   вне git. Запись несёт: pid процесса прогона, время старта этого
   процесса, `run_stamp`, проверяемый sha, имя набора, время начала,
   число задач. Запись снимается в конце прогона при любом исходе,
   включая сигнал и исключение. Путь реестра считается от корня пульта и
   подменяется песочницей тестов (`tests/sandbox.py:90`,
   `ALL_CONFIG_ATTRS`). `cmd_canary` возвращает свой `run_stamp`.
2. **Чтение реестра.** Одна функция чтения отдаёт живые прогоны: запись
   живая, если pid жив, время старта процесса совпало с записанным и
   возраст записи меньше `CANARY_DRIVE_TIMEOUT_SEC`
   (`orchestrator/canary.py:279`), умноженного на число задач, плюс час.
   Остальные записи не живые: функция их убирает и пишет строку в журнал
   пульта (запись без задачи). Функция признака живого pid
   (`orchestrator/liveness.py:56`) не меняется.
3. **Повтор `run_stamp`.** Запуск канарейки при живом прогоне с тем же
   `run_stamp` — отказ.
4. **Окно тишины.** `_silence_window_reason` открывает окно при живом
   прогоне канарейки любого набора, с причиной
   «идёт канарейка <run_stamp> на <sha7>». `note` и `doc-commit`
   удерживаются; после прогона `--flush` досылает их прежним путём.
5. **Мерж во время канарейки.** `approve <id> [sha]` на `merge_gate`
   задачи артели при живом прогоне канарейки набора по умолчанию
   (`config.CANARY_DEFAULT_SET`) — отказ с текстом
   «идёт канарейка <run_stamp> на <sha7>: мерж сдвинет main под
   проверяемым коммитом — дождись итога или повтори с --during-canary
   "<основание>"». Проверка стоит при каждом заходе в тело окна мержа
   (`orchestrator/fsm_merge_gate.py:1379`, `_cmd_approve_merge_gate`) до
   push в main — так ловится и одобрение, ждавшее очередь или CI. Отказ
   оставляет задачу на `merge_gate`, мьютекс мержа снимает прежний путь.
6. **Флаг `--during-canary "<основание>"`.** С флагом мерж идёт прежним
   путём, основание пишется строкой журнала задачи. Флаг входит в
   `_approve_reason_indices` (`orchestrator/artel.py:1772`): основание не
   читается как sha. Флаг без основания и флаг не на `merge_gate` —
   отказы по образцу `--no-answer`.
7. **Кто мерж не держит.** Задачи внешних проектов и прогоны канарейки не
   набора по умолчанию мерж не держат.
8. **Обходы окна во время канарейки.** При живом прогоне канарейки любого
   набора `note --now`, `note --flush`, `doc-commit --flush` и
   `canary pool-seal` (`orchestrator/pool_seal.py:316`, пишет в main)
   отказывают текстом «идёт канарейка <run_stamp> на <sha7>: команда
   сдвинет main — дождись итога или повтори с --during-canary
   "<основание>"»; с флагом `--during-canary` и непустым основанием идут
   прежним путём, основание пишется строкой журнала пульта.
9. **Файл результата** отвязанного запуска отбирает строки `canary_runs`
   по `run_stamp`, который вернул `cmd_canary`, а не по номеру строки.
10. **Без живого прогона** — прежнее поведение побайтно: `note`,
    `doc-commit` (включая `--now`/`--flush`), `canary pool-seal`,
    `approve` и вывод `canary`.
11. Тесты требований детерминированы, без сети, без настоящих ролей и без
    ожидания по часам; тесты окна тишины не зависят от настоящей
    канарейки на машине.

## Критерии приёмки

AC-1. `cmd_canary` после выбора проверяемого sha и до первого клона пишет в каталог реестра (путь от корня пульта, вне git, подменён песочницей через `ALL_CONFIG_ATTRS`) отдельный файл с именем из `run_stamp` и pid; файл несёт pid процесса прогона, время старта процесса, `run_stamp`, проверяемый sha, имя набора, время начала и число задач.
AC-2. Запись реестра снимается при штатном конце прогона.
AC-3. Запись реестра снимается, когда прогон оборван исключением.
AC-4. Запись реестра снимается, когда прогон оборван сигналом.
AC-5. Функция чтения реестра не отдаёт запись с мёртвым pid, запись с живым pid, но другим временем старта процесса, и запись старше `CANARY_DRIVE_TIMEOUT_SEC` × число задач + час; каждую такую запись она убирает и пишет строку в журнал пульта без задачи.
AC-6. Запуск канарейки при живом прогоне с тем же `run_stamp` — отказ.
AC-7. При живом прогоне канарейки любого набора `note` и `doc-commit` удерживаются с причиной «идёт канарейка <run_stamp> на <sha7>»; без живого прогона — отправлены; после прогона `--flush` досылает удержанное прежним путём. Тесты окна не зависят от настоящей канарейки на машине.
AC-8. `approve <id>` на `merge_gate` задачи артели при живом прогоне набора по умолчанию — и с sha, и без sha — отказ с текстом «идёт канарейка <run_stamp> на <sha7>: мерж сдвинет main под проверяемым коммитом — дождись итога или повтори с --during-canary "<основание>"»; задача остаётся на `merge_gate`, мьютекс мержа снят, push в main нет.
AC-9. Одобрение, вошедшее в тело окна мержа (`_cmd_approve_merge_gate`) после старта прогона канарейки (ждавшее очередь или CI), — отказ тем же текстом до push в main.
AC-10. `approve <id> [sha] --during-canary "<основание>"` на `merge_gate` при живом прогоне мержит прежним путём, основание не читается как sha, в журнале задачи — строка с основанием.
AC-11. `--during-canary` без основания и `--during-canary` не на `merge_gate` — отказы по образцу `--no-answer`.
AC-12. Задача внешнего проекта на `merge_gate` и живой прогон набора не по умолчанию мерж не держат: `approve` проходит прежним путём.
AC-13. При живом прогоне канарейки любого набора `note --now`, `note --flush`, `doc-commit --flush` и `canary pool-seal` отказывают текстом «идёт канарейка <run_stamp> на <sha7>: команда сдвинет main — дождись итога или повтори с --during-canary "<основание>"»; с `--during-canary` и непустым основанием идут прежним путём, в журнале пульта — строка с основанием.
AC-14. `cmd_canary` возвращает свой `run_stamp`; файл результата отвязанного запуска при двух прогонах в одной БД содержит только строки `canary_runs` своего `run_stamp`.
AC-15. Без живого прогона поведение `note`, `doc-commit` (включая `--now`/`--flush`), `canary pool-seal`, `approve` и вывод `canary` — прежние побайтно.
