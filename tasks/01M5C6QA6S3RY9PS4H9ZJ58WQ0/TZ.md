# Механика канарейки, часть А: реестр живого прогона, окно тишины и мерж во время канарейки

## Факты

Решения Оператора 19.10: строка бэклога «Частота канарейки и неподвижный main на время её прогона — механикой пульта» (коммит 49ce342c, пункты 1 и 2). Правило — `docs/operator-session.md:422`: канарейка идёт на вершине `origin/main`, которая станет пином; пока она идёт, main не двигать, заметки ждут `--flush`. Сегодня правило держится только дисциплиной сессии: 19.10 мерж 01M59DP2GV одобрен во время канарейки; вечером того же дня запись бэклога 59f42db4 сдвинула main с b5a8fda3, на котором шла канарейка.

- Прогон канарейки — `orchestrator/canary.py:2807` (`cmd_canary`): штамп прогона с точностью до секунды — `orchestrator/canary.py:2848` (`run_stamp`), задачи идут по одной; функция ничего не возвращает.
- Отвязанный запуск — `orchestrator/artel.py:1586` (`_detach_canary`); отдельного реестра живых прогонов нет.
- Файл результата собирает строки `canary_runs` с номером больше последнего до запуска — `orchestrator/artel.py:1563` (`previous_id`), без отбора по `run_stamp`: строки другого прогона, идущего одновременно, попадут в чужой файл результата.
- Признак живого pid в модуле liveness — проверка сигналом 0 (`orchestrator/liveness.py:56`); функция не меняется, у неё много вызывающих вне зон: повторно выданный номер мёртвого процесса читается как живой. Маркер владельца временного каталога канарейки — `orchestrator/liveness.py:27` (`CANARY_OWNER_MARKER`), он о клоне одной задачи, не о прогоне.
- Предел времени процесса задачи канарейки — `orchestrator/canary.py:279` (`CANARY_DRIVE_TIMEOUT_SEC`).
- Окно тишины `note` и `doc-commit` — `orchestrator/notes.py:266` (`_silence_window_reason`): живой держатель мьютекса мержа артели или задача артели в состоянии из `NOTE_SILENCE_WINDOW_STATES` (`orchestrator/config.py:515`); живой прогон канарейки окна не открывает. Удержание — `orchestrator/notes.py:1312` (`_run`), досылка — `orchestrator/notes.py:1262` (`_flush_pending`).
- Обходы окна: `note --now` — `orchestrator/notes.py:1312` (`_run`, флаг bypass_window), `--flush` — без проверки окна; `canary pool-seal` коммитит и отправляет в main — `orchestrator/pool_seal.py:316` (`cmd_pool_seal`).
- Одобрение: разбор флагов с основанием — `orchestrator/artel.py:1772` (`_approve_reason_indices`, образец — `--no-answer`); `approve <id>` без sha на `merge_gate` тоже мержит — sha сверяет сама команда. Очередь окна мержа — `orchestrator/merge_queue.py:111` (`wait_for_window`), цикл ожидания CI — `orchestrator/fsm_merge_gate.py:1509` (`_cmd_approve_merge_gate_cycle`), тело окна до push в main — `orchestrator/fsm_merge_gate.py:1379` (`_cmd_approve_merge_gate`). Одобрение, начатое до канарейки, может дойти до push посреди неё.
- Песочница тестов подменяет пути `config` из перечня `tests/sandbox.py:90` (`ALL_CONFIG_ATTRS`).

## Требуется

1. **Реестр живого прогона.** `cmd_canary` после выбора проверяемого sha и до первого клона пишет запись прогона отдельным файлом (имя — `run_stamp` и pid) в каталог состояния пульта вне git: pid процесса прогона, время старта этого процесса, `run_stamp`, проверяемый sha, имя набора, время начала, число задач. Запись снимается в конце прогона при любом исходе, включая сигнал и исключение. Одна функция чтения отдаёт живые прогоны: живой pid и совпавшее время старта процесса и возраст записи меньше `CANARY_DRIVE_TIMEOUT_SEC`, умноженного на число задач, плюс час. Остальные записи не живые: функция их убирает и пишет строку в журнал пульта, запись без задачи. Запуск при живом прогоне с тем же `run_stamp` — отказ. Путь реестра считается от корня пульта и подменяется песочницей тестов (`ALL_CONFIG_ATTRS`). `cmd_canary` возвращает свой `run_stamp`.
2. **Окно тишины.** `_silence_window_reason` открывает окно при живом прогоне канарейки любого набора, с причиной «идёт канарейка <run_stamp> на <sha7>». `note` и `doc-commit` удерживаются; после прогона `--flush` досылает их прежним путём.
3. **Мерж во время канарейки.** `approve <id> [sha]` на `merge_gate` задачи артели при живом прогоне канарейки набора по умолчанию — отказ с текстом «идёт канарейка <run_stamp> на <sha7>: мерж сдвинет main под проверяемым коммитом — дождись итога или повтори с --during-canary "<основание>"». Проверка стоит при каждом заходе в тело окна мержа (`_cmd_approve_merge_gate`) до push в main — так ловится и одобрение, ждавшее очередь или CI. Отказ оставляет задачу на `merge_gate`, мьютекс снимает прежний путь. С флагом `--during-canary "<основание>"` мерж идёт прежним путём, основание пишется строкой журнала задачи. Флаг входит в `_approve_reason_indices`: основание не читается как sha. Флаг без основания и флаг не на `merge_gate` — отказы по образцу `--no-answer`. Задачи внешних проектов и прогоны не набора по умолчанию мерж не держат.
4. **Обходы окна во время канарейки.** При живом прогоне канарейки любого набора `note --now`, `note --flush` и `doc-commit --flush`, а также `canary pool-seal` (пишет в main) отказывают текстом «идёт канарейка <run_stamp> на <sha7>: команда сдвинет main — дождись итога или повтори с --during-canary "<основание>"»; с флагом и непустым основанием идут прежним путём, основание пишется строкой журнала пульта. Без живого прогона — прежнее поведение побайтно. Решение Оператора 20.10.
5. **Файл результата** отвязанного запуска отбирает строки `canary_runs` по `run_stamp`, который вернул `cmd_canary`, а не по номеру строки.
6. Тесты детерминированы, без сети, без настоящих ролей и без ожидания по часам (проверка детерминированности тестов): реестр — запись, снятие при штатном конце, при исключении и при сигнале; мёртвый pid; совпавший pid с другим временем старта; запись старше потолка; повтор `run_stamp`. Окно тишины — `note` удержан при живом прогоне и отправлен без него; тесты окна тишины не зависят от настоящей канарейки на машине. `approve` на `merge_gate` с sha и без — отказ; одобрение, вошедшее в тело окна после старта прогона, — отказ; проход с `--during-canary` и строка журнала; оба отказа флага; внешняя задача не держится. Обходы п. 4 — отказ при живом прогоне, проход с основанием и строка журнала, прежнее поведение без прогона. Файл результата при двух прогонах в одной БД — только свои строки. Без живого прогона — прежнее поведение `note`, `doc-commit`, `approve` и вывод `canary`.

Зоны: orchestrator/canary.py, orchestrator/pool_seal.py, orchestrator/artel.py, orchestrator/notes.py, orchestrator/fsm.py, orchestrator/fsm_merge_gate.py, orchestrator/liveness.py, orchestrator/config.py, tests/
