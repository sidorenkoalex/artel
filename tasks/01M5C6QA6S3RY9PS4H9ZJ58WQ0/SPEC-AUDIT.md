## Пути обхода гейтов
1. **Мёртвый по построению реестр.** SPEC не называет источник «времени
   старта процесса» ни для записи, ни для сверки (SPEC.md:32-33, :38-41).
   Записав `time.time()`/`datetime.now()` при старте `cmd_canary`, а
   сверяя с `ps -o lstart` (`doctor/stale_cycles.py:42-65`, точность —
   секунда, местное время), исполнитель получит «другое время старта» для
   каждой записи: функция чтения уберёт живой прогон, окно и запрет мержа
   не откроются никогда. Тесты AC-5/AC-7/AC-8 с подменённым помощником
   пройдут. Тот же класс — отказ определения времени (`None` при сбое
   `ps`): по букве SPEC запись «не живая» и УДАЛЯЕТСЯ, хотя процесс жив —
   один сбой `ps` снимает защиту до конца прогона (fail-open).
2. **Канарейка, стартовавшая посреди тела окна.** «Проверка стоит при
   каждом заходе в тело» (SPEC.md:56-58) буквально выполняется проверкой в
   начале `_cmd_approve_merge_gate` (`fsm_merge_gate.py:1429`). Между
   началом тела и push (`:1470`) идут плотницкий merge, приложения PLAN с
   прогоном полного набора, `guard --all`, карта (`:1455-1469`) — минуты.
   Канарейка, стартовавшая в этом промежутке, получит сдвиг main ровно
   сценарием инцидента 19.10. Формулировка унаследована из ТЗ п.3; AC-9
   ловит только одобрение, вошедшее в тело ПОСЛЕ старта прогона.
3. **Повтор `run_stamp` без атомарности.** Требование 3 выполнимо
   «прочитал реестр — нет такого — записал»: два запуска в одну секунду
   оба проходят проверку (имена файлов различны из-за pid). Последствие —
   смешение строк `canary_runs` одного `run_stamp`, ради которого отказ и
   введён. Низкая вероятность; SPEC атомарности (например, эксклюзивного
   создания файла-метки `run_stamp`) не требует.

## Вердикт
`concerns` — SPEC соответствует ТЗ, адреса верны, зоны достаточны,
ослаблений нет; отклонения решаемы Оператором на гейте:

1. **Источник и сбой времени старта процесса не заданы** —
   SPEC.md:32-33, :38-42, AC-5 (SPEC.md:89). Риск: реестр, мёртвый по
   построению, и удаление записи живого прогона при сбое `ps`. Предложение:
   записывать и сверять время старта одним помощником
   (`orchestrator/doctor/stale_cycles.py:42`, `process_start_time`), а
   неопределимое время (`None`) читать как «живой, не удалять».
2. **Место проверки мержа** — SPEC.md:56-58, AC-9 (SPEC.md:93):
   проверка «при заходе в тело» пропускает канарейку, стартовавшую между
   началом тела и push (`orchestrator/fsm_merge_gate.py:1455-1470`).
   Предложение: проверка непосредственно перед `_push_merged_main`
   (`fsm_merge_gate.py:1470`) — она тоже «в теле до push» и ловит оба
   случая; AC-9 дополнить сценарием «канарейка стартовала после входа в
   тело».
3. **Файл результата на обрыве** — SPEC.md:74-75, AC-14 (SPEC.md:98):
   на исключении и сигнале `cmd_canary` ничего не возвращает
   (`orchestrator/canary.py:2864-2871`), а `_cmd_canary` пишет `runs` в
   `finally` (`orchestrator/artel.py:1573-1580`). По букве SPEC красная
   строка оборванного прогона (`canary.py:2866-2870`), которую файл
   результата несёт сегодня, из него пропадёт. Нужно правило: например,
   `run_stamp` доступен вызывающему и до возврата (атрибут исключения /
   раннее сообщение), и файл обрыва несёт свои строки — плюс AC.
4. **«По образцу `--no-answer`» для флага без основания** — SPEC.md:63-64,
   AC-11 (SPEC.md:95): у `--no-answer` основания нет
   (`orchestrator/artel.py:1782-1787`), образец отказа «нет основания» —
   `_accept_red_arg`/`_fixes_main_arg` (`artel.py:1730-1765`); образец
   отказа «не в том состоянии» — `fsm.py:1528-1530`. Уточнить образец
   каждого из двух отказов.
5. **Строка журнала с основанием при флаге без живого прогона** —
   SPEC.md:60-61, :72-73 молчат: писать ли основание `--during-canary`,
   когда канарейки нет. Требование 10 («побайтно») касается вывода;
   разумный дефолт — флаг без живого прогона принимается молча, журнал не
   пишется; лучше сказать явно.
6. (мелкое) Повтор `run_stamp` не атомарен — SPEC.md:45-46; см. «Пути
   обхода» п.3.
