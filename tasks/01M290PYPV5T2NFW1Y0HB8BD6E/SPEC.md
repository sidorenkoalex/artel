# SPEC: `auto` после эскалации по конфликту подтяжки начинает с шага роли, не с предварительного advance

## Контекст
Копилка 11.09 отмечает два дефекта одного семейства вокруг предварительного
advance цикла `auto` (SPEC 01M1R8B3ZK) и брифа с историей отказов (SPEC
T078, `brief.advance_refusal_history`):

- П1: задача 01M1VBEKRN, 11.09 03:04Z/03:05Z — `PLAN.md` уже `ready`,
  `auto._pre_advance_step` из `in_dev` сразу пробует переход, подтяжка
  main упирается в конфликт содержимого (`pull.py`, исход `Conflict`) →
  `escalated`. `answer` + `approve` возвращают в `in_dev`
  (`fsm._approve_escalated`, `escalated_from`), но следующий `auto`
  повторяет предварительный advance БЕЗ шага developer — разрешать
  конфликт некому. Обход — прямой `run <id>`.
- П2: отказы предварительного advance класса «роль ещё не закончила»
  («нет шага developer после возврата», «PLAN.md ветки не прочитан …
  does not exist») журналируются как обычный «переход отклонён»;
  `store.refusal_history` берёт все отказы визита состояния без разбора
  класса, и бриф роли получает блок «Предыдущая попытка сдать шаг
  отклонена — почини это», хотя роль ещё ничего не сдавала (11.09,
  промпты developer-2 у 01M283NC… и developer-1 у 01M283NJ…).

## Требования

1. Эскалация состояния `in_dev` по конфликту подтяжки (исход `pull.
   Conflict`/переход задачи в `escalated` изнутри `fsm._pull_main_or_
   escalate`/`pull.evaluate` по причине неразрешённого конфликта
   содержимого) помечает задачу признаком «нужен шаг роли до следующего
   предварительного advance» — поле задачи либо запись журнала с
   фиксированным текстом, тем же приёмом, что уже отличает возврат с
   неотработанными замечаниями ревью в `auto._role_step_since_state_
   entry`. После возврата из `escalated` по этому основанию (`answer` +
   `approve`) следующий вызов `auto` начинает со шага роли текущего
   состояния (developer в `in_dev`), а не с `_pre_advance_step`. Бриф
   роли после такого возврата несёт ANSWER Оператора и перечень
   конфликтующих файлов подтяжки (`pull.Conflict.files`).
2. То же правило действует для любого повторного входа в `escalated` из
   предварительного advance с тем же основанием подряд: если второй раз
   подряд задача эскалирует по тому же основанию БЕЗ единого шага роли
   между двумя эскалациями — это не новая эскалация, а остановка `auto`
   именованной причиной «предварительный advance дважды упёрся в
   <основание> без шага роли — решение Оператора» (стоп-кран одной
   задачи, не даёт циклу жечь эскалации по кругу).
3. Отказы `_pre_advance_step` класса «роль ещё не закончила» пишутся в
   журнал с текстом из единого перечня-константы этого класса — общего
   источника, откуда его читают и `brief.advance_refusal_history`, и (в
   отдельной задаче) дозор `watch`. `brief.advance_refusal_history` не
   включает такие отказы в блок «почини это»; настоящие отказы сдачи
   шага (гейты, guard, зоны) — включает как сейчас.
4. Существующие тесты `orchestrator/auto.py`, `orchestrator/pull.py`,
   `orchestrator/fsm.py`, `orchestrator/brief.py` — без ослабления
   (ни одна текущая проверка не удаляется и не смягчается).

## Критерии приёмки

AC-1. Эскалация `in_dev` по конфликту подтяжки (`pull.Conflict`,
неразрешённый конфликт содержимого) помечает задачу признаком «нужен шаг
роли до следующего предварительного advance» (поле задачи либо запись
журнала фиксированным текстом).

AC-2. После возврата из `escalated` по основанию AC-1 (`answer` +
`approve`) следующий вызов `auto` запускает шаг роли текущего состояния
(developer в `in_dev`), а не `_pre_advance_step`; мутация, отключающая
чтение маркера AC-1, красит приёмочный тест этого критерия.

AC-3. Бриф роли после возврата по основанию AC-1 несёт ANSWER Оператора
и перечень конфликтующих файлов подтяжки (`pull.Conflict.files`).

AC-4. Повторный вход в `escalated` из предварительного advance с тем же
основанием подряд, без единого шага роли между двумя эскалациями, не
эскалирует повторно — вместо этого `auto` останавливается именованной
причиной «предварительный advance дважды упёрся в <основание> без шага
роли — решение Оператора».

AC-5. Отказы `_pre_advance_step` класса «роль ещё не закончила»
(включая «нет шага роли после возврата», «дерево не на ветке задачи»)
журналируются с текстом из единого перечня-константы этого класса,
общего источника для `brief.py` и (задача вне этой зоны) `watch.py`.

AC-6. `brief.advance_refusal_history` не включает в блок «почини это»
отказы класса AC-5; отказы гейтов/guard/зон (настоящие отказы сдачи
шага) включает как прежде — с приёмочным тестом на оба случая (бриф без
блока после отказа «нет шага developer после возврата», бриф с блоком
после отказа гейта).

AC-7. Существующие тесты `tests/test_auto_cycle.py`,
`tests/test_pull.py`, тесты `orchestrator/fsm.py` (в т.ч.
`tests/test_fsm_merge_conflict_note.py`, `tests/test_auto_escalated_
return_rework_gate.py`) и `tests/test_brief.py` проходят без ослабления
— ни одна существующая проверка не удалена и не смягчена.

## Оценка объёма и деление

Сработавшиеся сигналы: число упомянутых в тексте модулей
`orchestrator/*.py` ≥ 5 (`auto.py`, `pull.py`, `fsm.py`, `brief.py` в
зоне; `store.py`, `watch.py`, `fsm_advance.py` упомянуты в «Не входит»/
«Контексте» границами задачи).

Обоснование монолита: единая механика одного маркера эскалации —
проставляется в точке эскалации конфликта подтяжки (`orchestrator/
pull.py`/`orchestrator/fsm.py`, требование 1), читается циклом `auto`
для выбора шага роли вместо `_pre_advance_step` и для стоп-крана
повторной эскалации (`orchestrator/auto.py`, требования 1-2), участвует
в едином перечне класса «роль ещё не закончила» (требование 3), который
фильтрует `orchestrator/brief.py`. Части не мержимы по отдельности
осмысленно: маркер AC-1 без чтения в `auto.py` — мёртвое поле без
наблюдаемого поведения и без содержательного теста; стоп-кран AC-4 без
маркера AC-1 ловить нечего; перечень-константа AC-5 без филиального
изменения точки эскалации (тот же маркер, тот же класс текста) не из
чего собрать. Бюджет $45 (Оператор, «Рамка») — в границах калибровки
6-10 критериев приёмки, деление на 2-4 подзадачи увеличило бы
суммарную стоимость (накладные расходы каждой на PLAN/REVIEW) без
пользы для мержимости — каждая часть сама по себе не даёт наблюдаемого
исправления дефекта копилки 11.09.
