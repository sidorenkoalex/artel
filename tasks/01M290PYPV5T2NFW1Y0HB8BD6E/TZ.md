# ТЗ: auto после эскалации по конфликту подтяжки начинает с шага роли, не с предварительного advance; ожидаемые отказы pre-advance не попадают в бриф

Источник: копилка 11.09 П1 «`auto` зацикливается на конфликте подтяжки
main, если PLAN.md уже `ready`» и П2 «ожидаемые отказы предварительного
advance попадают в бриф роли как „почини это“». Предварительный advance —
SPEC 01M1R8B3ZK (R1); бриф с историей отказов — SPEC T078
(`brief.advance_refusal_history`); возврат из `escalated` —
`fsm._approve_escalated`.

Факты:
- 11.09, задача 01M1VBEKRN (03:04Z и 03:05Z): две эскалации подряд за
  минуту. `auto._pre_advance_step` из `in_dev` по готовому PLAN.md сразу
  пробует переход, подтяжка main упирается в конфликт содержимого
  (`pull.py`, класс «подтяжка отказала и обязана эскалировать») →
  `escalated`; `answer` + `approve` возвращают в `in_dev`
  (`escalated_from`), следующий `auto` повторяет предварительный advance
  БЕЗ шага developer — конфликт разрешать некому. 06.09 у P1a тот же
  конфликт разрешился только потому, что предварительный переход отклонил
  гейт «замечания ревью не отработаны» и цикл запустил разработчика.
  Обход — прямой `run <id>`: шаг роли идёт с ANSWER в брифе.
- Отказы предварительного advance класса «роль ещё не закончила» («нет
  шага developer после возврата», «PLAN.md ветки не прочитан … does not
  exist») журналируются как обычный «переход отклонён»; `store.refusal_history`
  берёт все отказы визита состояния, и бриф получает блок «Предыдущая
  попытка сдать шаг отклонена — почини это». 11.09 подтверждено по
  промптам developer-2 у 01M283NC… и developer-1 у 01M283NJ…, ещё ничего
  не сдававших: роль получает ложную задачу.

Требуется:
1. Эскалация по конфликту подтяжки помечает задачу «нужен шаг роли до следующего предварительного advance» (поле задачи либо запись журнала с фиксированным текстом — как маркер возврата с замечаниями ревью в `auto._role_step_since_state_entry`); после возврата из `escalated` по этому основанию `auto` начинает с шага роли текущего состояния (developer в `in_dev`), а не с `_pre_advance_step`; бриф роли несёт ANSWER и перечень конфликтующих файлов подтяжки (`pull` уже отдаёт `files`).
2. То же правило для любого повторного входа в `escalated` из предварительного advance с тем же основанием подряд: второй раз подряд без шага роли между ними — не эскалация, а остановка `auto` именованной причиной «предварительный advance дважды упёрся в <основание> без шага роли — решение Оператора» (стоп-кран одной задачи), чтобы цикл не жёг эскалации по кругу.
3. Класс отказа в журнале: отказы `_pre_advance_step` класса «роль ещё не закончила» пишутся с префиксом класса в `detail` (единая константа-перечень текстов, откуда их читают и `brief`, и дозор `watch` — отдельная задача); `brief.advance_refusal_history` такие отказы в блок «почини это» не включает; настоящие отказы сдачи шага (гейты, guard, зоны) — включает как сейчас.
4. Тесты: PLAN `ready` + конфликт подтяжки → `escalated`; `answer`+`approve` → следующий `auto` запускает developer, а не предварительный advance (мутация «маркер не читается» — красный); повторная эскалация по тому же основанию без шага роли — остановка с именованной причиной; бриф developer после pre-advance-отказа «нет шага developer после возврата» без блока «почини это», а после отказа гейта — с блоком; существующие тесты auto, pull, fsm и brief — без ослабления.

Зоны: orchestrator/auto.py, orchestrator/pull.py, orchestrator/fsm.py,
orchestrator/brief.py, tests/.

Не входит: `orchestrator/store.py` (занят 01M28NWPS3 и 01M28VZ8Q1 —
`refusal_history` не меняется, фильтр живёт в `brief.py`);
`orchestrator/watch.py` (задача дозора); авторазрешение конфликтов
подтяжки; порядок состояний FSM.
