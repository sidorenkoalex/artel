# QUESTIONS: GitLab Б1 — ветка по ключу трекера, автор и шаблон коммита, сжатие и перебазирование, единая точка отправки

## Вопросы

Сверка по коду (origin/main 5705cfdf8, А0 уже в main): `targets.unsupported_reason`
(`targets.py:270-290` на origin/main) отказывает проектам с `merge_gate`, отличным
от `operator`, и с `forge` без адаптера. Значит, до Б2 единственные живые проекты,
на которых сработают новые поля, — `forge: github` + `merge_gate: operator`. Отсюда
вопрос 1.

1. **Белый список отправок (требование 6) у проекта с `merge_gate: operator` и нестандартным `branch_template` ломает мерж и уборку пульта.** ТЗ включает белый список при «`branch_template` отличен от умолчания ИЛИ `merge_gate` не `operator`». Для проекта `operator` с `branch_template: feature/{ref}` гейт мержа отправляет в `base` (`fsm_merge_gate.py:1316` `push origin <sha>:refs/heads/<base>`), а уборка удаляет ветку задачи (`cleanup.py:265`, `cleanup.py:268` `push --delete`) — по белому списку обе отправки отказаны, а оба файла в ТЗ «только чтение». ADR-0029 п. 13 включает белый список только для `target-human`.
   - A) Белый список включается только при `merge_gate` не `operator` (буква ADR-0029 п. 13); при нестандартном `branch_template` у проекта `operator` отправки прежние.
     - ломается: ничего в мерже и уборке; чужие ветки `feature/*` у проекта `operator` с нестандартным шаблоном защищены только кодом мест отправки, как сейчас (ТЗ, факт 5).
     - ослабляется: защита чужих веток для `operator`-проекта с шаблоном не появляется (сейчас её нет нигде — `gitcmd.py:95-118` только выбирает токен).
     - цена: ноль сверх задачи; до Б2 белый список проверяется только тестами (живого `target-human` проекта нет — А0).
     - чьё решение: Оператор.
   - B) Условие ТЗ буквально, но у проекта с `merge_gate: operator` белый список дополнительно пропускает отправку в `base` и удаление ветки своей задачи (сверка имени с задачей в БД); чужие ветки, теги и `refs/heads/*` вне шаблона — отказ.
     - ломается: ничего; правки `fsm_merge_gate.py`/`cleanup.py` не нужны — исключения в `gitcmd`.
     - ослабляется: ничего относительно сейчас; критерий «отправка в `main` — отказ» проверяется на записи с `merge_gate: target-human`.
     - цена: +1–2 ветки проверки в `gitcmd` и тесты к ним, ~$3–5.
     - чьё решение: Оператор.
   - C) Условие ТЗ буквально, без исключений: проект `operator` с нестандартным шаблоном пульт не мержит и не убирает (отправка в `base` и удаление отказаны); дополнительно — отказ загрузки записи `operator` с нестандартным `branch_template`, чтобы такой проект не завёлся вовсе.
     - ломается: сочетание «гейт Оператора + шаблон ветки трекера» невозможно; отказ загрузки — новое требование сверх ТЗ.
     - ослабляется: ничего.
     - цена: малая в коде; потеря сценария GitHub-проекта с веткой по ключу трекера.
     - чьё решение: Оператор.
   - дефолт: B — сохраняет условие ТЗ (защиту чужих веток при нестандартном шаблоне) и не ломает гейт мержа и уборку, которые задача трогать не вправе.

2. **Проверка занятости имени ветки (требование 2): для всех проектов или только при нестандартном шаблоне, и что при сбое `ls-remote`.** Шаблон по умолчанию `task/{id}-{slug}` несёт уникальный `{id}` — совпадение исключено, а `ls-remote` добавляет сетевой вызов каждому `new` артели (критерий «тесты `new` артели зелёные без правки» — существующие тесты `new` сети не ждут).
   - A) Сверка (сервер и БД) — при любом шаблоне; сбой `ls-remote` — отказ `new` с причиной.
     - ломается: `new` артели без сети отказывает; существующие тесты `new` могут потребовать подмены `ls-remote` — правка тестов вне мандата ТЗ.
     - ослабляется: ничего.
     - цена: сетевой вызов на каждый `new`; риск эскалации по тестам.
     - чьё решение: Оператор.
   - B) Сверка — только когда `branch_template` отличен от умолчания (или шаблон без `{id}`); сбой `ls-remote` — отказ `new`/деления с причиной (имя не проверено — задача не заводится).
     - ломается: ничего для артели и проектов с полями по умолчанию.
     - ослабляется: ничего (с `{id}` коллизия невозможна по построению, `idgen.new_task_id`).
     - цена: ноль сверх задачи.
     - чьё решение: Оператор.
   - C) Как B, но сбой `ls-remote` — предупреждение в журнал и заведение задачи (проверка только по БД).
     - ломается: ничего.
     - ослабляется: гарантия «ветки с этим именем нет на сервере» при сбое сети.
     - цена: ноль.
     - чьё решение: Оператор.
   - дефолт: B — поведение артели неизменно, отказ при непроверенном имени безопаснее.

3. **Зоны: места кода, без которых требования 4–5 не исполнимы, в зоны ТЗ не вошли.** Подтяжка на `in_dev → verifying` живёт не в `fsm_advance.py`, а в `fsm._pull_main_or_escalate` (`fsm.py:236`) → `pull.evaluate` (`pull.py:762`), `git merge --no-ff` — `pull._run_merge` (`pull.py:535`), откат конфликта — `pull._handle_merge_failure` (`pull.py:543`). Отправка ветки задачи на переходе в `verifying` у `forge: github` — `github_adapter.py:166`, `:241` (`push -u origin <ветка>`): после сжатия/перебазирования обычная отправка отказана как не fast-forward, а требование 5 велит `--force-with-lease`.
   - A) Добавить в зоны `orchestrator/pull.py`, `orchestrator/fsm.py`, `orchestrator/github_adapter.py`.
     - ломается: ничего; зона шире ТЗ на три файла (всего 13 файлов зоны).
     - ослабляется: ничего.
     - цена: зона пересекается с большим числом параллельных задач (ожидание зон).
     - чьё решение: Оператор.
   - B) Только `pull.py` и `fsm.py`; перезапись делает единая точка `gitcmd` (подмена `push <ветка>` на `--force-with-lease` для ветки своей задачи), `github_adapter.py` не трогается.
     - ломается: ничего; `gitcmd` неявно меняет аргументы отправки — менее прозрачно.
     - ослабляется: ничего.
     - цена: та же.
     - чьё решение: Оператор.
   - дефолт: A — места отправки ветки задачи вносятся поимённо, как велит ТЗ («Зоны»).

4. **Объём: монолит в рамке $70 или деление.** Сработают сигналы guard: файлов зоны ≥ 5 (10–13), критериев ≥ 10, `budget_usd` ≥ $30; калибровка (`config.BUDGET_CALIBRATION_TABLE`) для 8+ файлов — ~$85 либо деление.
   - A) Деление на две части. Первая (механика): требования 1, 2, 6 — поля записи и их проверка, имя ветки по шаблону и его поиск, белый список и хук (`targets.py`, `catalog.py`, `coldstart.py`, `gitcmd.py`). Вторая (после первой): требования 3–5 — автор/соавтор, сжатие, `rebase`, перезапись с `--force-with-lease` (`runner.py`, `checkpoint.py`, `artifact_branch.py`, `fsm_advance.py`, `pull.py`, `fsm.py`, `github_adapter.py`, `pull_main.py`). Каждая мержима: поля по умолчанию держат прежнее поведение.
     - ломается: ничего; `merge_after` второй части — первая.
     - ослабляется: ничего.
     - цена: ~$40 + ~$45, два прохода гейтов; меньше риск упереться в потолок.
     - чьё решение: Оператор.
   - B) Монолит в рамке $70 (`budget_usd: 70`).
     - ломается: ничего.
     - ослабляется: ничего.
     - цена: риск превышения рамки по калибровке (~$85) и подъёма потолка по ходу.
     - чьё решение: Оператор.
   - дефолт: A — части разделимы по зонам, атомарной смены механики между ними нет.

5. **Метод подтяжки `freshness` вне перехода в `verifying`.** Требование 4 задаёт `freshness` только на `in_dev → verifying`, но зоны ТЗ называют и подтяжку перед шагом разработчика (`runner._pull_before_developer_step`, `runner.py:620`), и `pull-main` (`pull_main.py`).
   - A) `freshness` — только на `in_dev → verifying`; подтяжка перед шагом разработчика и `pull-main` — прежний `merge`.
     - ломается: ничего; в ветке `rebase`-проекта между переходами могут появиться merge-коммиты — следующий вход в `verifying` их выпрямит.
     - ослабляется: ничего.
     - цена: ноль.
     - чьё решение: Оператор.
   - B) Все три подтяжки по `freshness`.
     - ломается: `pull-main` на `verifying` перезаписывает уже отправленную ветку — каждый раз перезапись по требованию 5.
     - ослабляется: ничего.
     - цена: +требование и тесты, ~$5.
     - чьё решение: Оператор.
   - дефолт: A — буква требования 4.

6. **Соавтор (`co_author`) в коммитах роли.** «Дописывается строкой в сообщение каждого коммита задачи пультом». Коммиты пульта (чекпоинты, фиксация, документы) пульт подписывает сам; коммиты роли пишет роль.
   - A) Строка — в каждом коммите, который пишет пульт (чекпоинты, фиксация, документы, сжатый коммит); коммиты роли без сжатия не переписываются.
     - ломается: ничего.
     - ослабляется: при `squash_before_mr: false` коммиты роли в ветке без `Co-authored-by`.
     - цена: ноль.
     - чьё решение: Оператор.
   - B) Плюс переписывание сообщений коммитов роли на входе в `verifying` (история меняется → перезапись по требованию 5 и без сжатия).
     - ломается: каждый вход в `verifying` перезаписывает ветку.
     - ослабляется: ничего.
     - цена: +требование и тесты, ~$5.
     - чьё решение: Оператор.
   - дефолт: A — без сжатия история роли не переписывается.
