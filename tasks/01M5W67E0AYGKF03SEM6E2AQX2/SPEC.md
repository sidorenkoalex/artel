# SPEC: GitLab Б1 — ветка по ключу трекера, автор и шаблон коммита, сжатие и перебазирование, единая точка отправки

## Контекст
ADR-0029 (принят 26.10.2026), п. 1, 4–6, 11, 13; шаг Б1 после А0
(`targets.unsupported_reason`). Подключаемый проект на GitLab требует ветку
по ключу трекера, своего автора и шаблон коммита, сжатие и перебазирование
перед MR. Токен Developer такого проекта может отправлять в любые
незащищённые ветки (в том числе `feature/*` коллег), вливать и удалять их —
защита только кодом пульта, а отправки сейчас разбросаны по модулям
(`github_adapter.py:166,241`, `fsm_merge_gate.py:744,1316`,
`cleanup.py:265,268`, `artifact_branch.py:427`, `artifact_cleanup.py:103`,
`snapshot.py:297` и др.), все через `gitcmd`. Имя ветки строится только в
`catalog.py:912`.

Решения Оператора: по батчу вопросов — `ANSWER-1.md` (26.10.2026); по
отклонениям первого аудита SPEC — первый возврат с гейта SPEC 26.10.2026
(хук `pre-push` и поиск веток по шаблону сняты из Б1); по отклонениям
второго аудита — второй возврат с гейта SPEC 26.10.2026 (11 решений:

строк `push_options`, единственная ссылка `{ref}`, коммит авторазрешения
подтяжки, трейлер коммитов пульта).

## Требования

1. **Поля записи** (`targets.py`, проверка при загрузке; значения по
   умолчанию — нынешнее поведение):
   - `policy.branch_template` (по умолчанию `task/{id}-{slug}`), подстановки
     `{id}`, `{slug}`, `{ref}`; `{ref}` — ключ ссылки системы
     `policy.ref_required`; шаблон с `{ref}` без `ref_required` — отказ
     загрузки;
   - `policy.ref_pattern` — регулярное выражение допустимого ключа (полное
     совпадение);
   - `policy.freshness`: `merge` (по умолчанию) | `rebase`;
   - `policy.squash_before_mr` (по умолчанию `false`);
   - `policy.commit_template` (по умолчанию `{id}: {text}`), подстановки
     `{id}`, `{ref}`, `{text}`; шаблон, отличный от умолчания, без
     `squash_before_mr: true` — отказ загрузки;
   - `machine.commit_author` (имя и email) и `policy.co_author` (строка
     `Co-authored-by: …`) — необязательны;
   - `policy.push_options` (список, по умолчанию пуст); элемент — строка
     вида `ci.variable=ИМЯ=значение` или `ИМЯ=значение`; отказ загрузки на
     `ci.skip` и на элемент, чьё `ИМЯ` есть в `policy.push_options_forbidden`
     (список имён переменных, которые запись запрещает передавать);
   - `policy.ci_required_jobs` (список имён заданий, по умолчанию пуст);
   - `policy.mr_assignee`, `policy.draft_mr` (по умолчанию `true`),
     `policy.max_in_flight` — только объявление и проверка формы.
   Отказ загрузки называет имя поля.
2. **Ветка задачи.**
   - `new` строит имя ветки по `branch_template`. `{ref}` — ключ ссылки
     системы `ref_required`; при шаблоне с `{ref}` у `new` должна быть
     ровно одна ссылка этой системы — больше одной — отказ `new`. Ключ этой
     ссылки не по `ref_pattern` — отказ до заведения задачи.
   - Когда `branch_template` отличен от умолчания (или не несёт `{id}`),
     `new` и деление отказывают, если ветка с этим именем уже есть на
     сервере (`ls-remote`) или у любой задачи проекта в любом состоянии
     (БД); сбой `ls-remote` — отказ `new`/деления с причиной «имя ветки не
     проверено». При шаблоне по умолчанию сетевого вызова нет.
   - Деление при шаблоне с `{ref}` — отказ деления с причиной «ветка по
     ключу трекера: делите задачу в трекере», атомарно: ни одна часть не
     заведена, родитель остаётся на гейте SPEC. При шаблоне не по
     умолчанию без `{ref}` имена всех частей проверяются на занятость до
     заведения первой части; конфликт имени хоть одной части — отказ
     деления, ни одна часть не заведена. При шаблоне по умолчанию деление
     прежнее.
3. **Автор, соавтор и трейлер пульта.**
   - Для записи с `commit_author` окружение роли и коммиты пульта в ветке
     задачи и в `refs/artifacts/<id>` получают этого автора и коммиттера.
   - `co_author` дописывается строкой в сообщение каждого коммита, который
     пишет пульт (чекпоинты, фиксация, документы, коммит `amend-tests`,
     коммит закрытия, сжатый коммит, merge-коммит подтяжки, коммит
     авторазрешения конфликта подтяжки `pull.py:462-463`), — не
     настройкой, которую может сменить роль; коммиты роли без сжатия не
     переписываются. Merge-коммит подтяжки и коммит авторазрешения — тоже с
     `commit_author`.
   - Каждый коммит, который пишет пульт, несёт строку-трейлер
     `Artel-Actor: orchestrator`, а запись журнала о нём — `actor`
     `orchestrator`. Когда задан `commit_author` (автор пульта и роли
     совпадает), коммиты пульта отличаются от коммитов роли по этому
     трейлеру и журналу: место различения `checkpoint.py:962-966` сверяет
     трейлер.
   - До первой отправки — сверка `commit_author` с владельцем токена через
     адаптер (`forge.token_user`, А1); пока адаптера нет — шаг пропускается
     с записью журнала «сверка автора — после адаптера».
4. **Подготовка ветки на входе в `verifying`** (каждый переход
   `in_dev → verifying`):
   - Сжатие и перебазирование выполняются ПОСЛЕ всех рубежей перехода —
     после `_review_rework_gate` и прочих (`fsm_advance.py:776-821`),
     непосредственно перед отправкой ветки (`_origin_push_gate`,
     `fsm_advance.py:831`) и переходом. Рубеж переделки ревью и прочие
     рубежи видят ветку, не переписанную этим переходом, — коммиты роли.
   - При `squash_before_mr: true` коммиты задачи от точки ответвления от
     `origin/<base>` сжимаются в один с сообщением по `commit_template`
     (`{text}` — название задачи).
   - Подтяжка методом `freshness`: `merge` — как сейчас, на
     `fsm_advance.py:771`; `rebase` — перебазирование ветки задачи на
     `origin/<base>` в указанном выше месте (после сжатия), только в рабочей
     копии задачи, `base` не меняется; подтяжки `merge` на
     `fsm_advance.py:771` при `rebase` нет.
   - Конфликт перебазирования — прежний путь конфликта подтяжки: состояние
     `escalated` с записью журнала-меткой `PULL_CONFLICT_ROLE_STEP_MARKER`
     (`pull.py:575,589`), не прямой переход в `in_dev`; перебазирование
     прервано.
   - `freshness` действует только на переходе `in_dev → verifying`; все
     прочие подтяжки — перед шагом разработчика (`runner.py:643`),
     `pull-main` (`pull_main.py:66`), `approve` приёмки (`fsm.py:1577`), гейт
     мержа (`fsm_merge_gate.py:727`) — прежний `merge` при любом
     `freshness`.
   - Без новых полей поведение перехода не меняется.
5. **Перезапись своей ветки** (после сжатия/перебазирования) — только
   `push --force-with-lease=refs/heads/<ветка>:<sha>`, где `<sha>` — из
   последней записи журнала задачи «ветка отправлена: <sha>»
   (требование 6); такой записи нет — первая отправка, без перезаписи.
   Голова на сервере не совпала с этим sha — эскалация задачи (на входе в
   `verifying` — в `_origin_push_gate`, `advance_gates/tests_writing.py`),
   без перезаписи. На гейте мержа (`fsm_merge_gate.py:701`) поведение без
   изменений — перезаписи там нет. Поведение черновика MR
   (`github_adapter.py`) не меняется — меняется только место отправки
   ветки.
6. **Единая точка отправки** (`gitcmd`):
   - после каждой успешной (код 0) отправки ветки задачи (любой проект)
     пишет в журнал задачи запись «ветка отправлена: <sha>», где `<sha>` —
     отправленный локальный sha; неудачная отправка записи не оставляет;
   - ко всем отправкам ветки задачи проекта добавляет `-o <опция>` на каждую
     строку `policy.push_options` (к `refs/artifacts/*` — нет);
   - белый список — только для проекта, у которого `merge_gate` не
     `operator` (ADR-0029 п. 13): любая отправка на сервер проверяется до
     вызова git. «Своя ветка» — имя ветки задачи этого проекта из БД в любом
     состоянии, кроме `killed` и `done`, совпавшее с назначением refspec.
     Разрешены только своя ветка и `refs/artifacts/*`; отправка в `base`, в
     ветку, не являющуюся своей, удаление веток (`--delete`, `:<ref>`),
     теги, отправка без явного refspec, флаги `--tags`, `--follow-tags`,
     `--mirror`, `--all`, `--force`/`-f` и refspec с `+` — отказ с причиной
     и записью журнала. Единственная разрешённая форма перезаписи —
     `--force-with-lease=<ref>:<sha>`, которую строит сама точка отправки.
     Отправка такого проекта идёт с `-c push.followTags=false`;
   - проверка стоит в одной внутренней функции, через которую проходят все
     пять точек запуска git в `gitcmd` (`git`, `carpentry`, `read`,
     `read_env`, `read_stream`), либо в каждой из них; запись проекта для
     пути клона проекта не читается — отказ отправки;
   - для проектов с `merge_gate: operator` (в том числе с нестандартным
     `branch_template`), для артели и проектов с полями по умолчанию
     отправки, кроме записи журнала и `-o` из `push_options`, прежние.

## Критерии приёмки

AC-1. Запись с шаблоном ветки, несущим `{ref}`, без `policy.ref_required` — отказ загрузки с именем поля `branch_template`.
AC-2. Запись с `commit_template`, отличным от `{id}: {text}`, без `squash_before_mr: true` — отказ загрузки с именем поля `commit_template`.
AC-3. Запись с `push_options`, несущим `ci.skip`, — отказ загрузки с именем поля `push_options`; при `push_options_forbidden: [SECRET]` элементы `ci.variable=SECRET=1` и `SECRET=1` — каждый отказ загрузки с именем поля `push_options`, а `ci.variable=OTHER=1` — загружается.
AC-4. Запись без новых полей загружается, значения по умолчанию: `branch_template` `task/{id}-{slug}`, `freshness` `merge`, `squash_before_mr` `false`, `commit_template` `{id}: {text}`, `push_options` и `ci_required_jobs` пусты, `draft_mr` `true`.
AC-5. `new --ref tracker:PROJ-7` при `branch_template: feature/{ref}`, `ref_required: tracker`, `ref_pattern: PROJ-\d+` — ветка задачи `feature/PROJ-7`.
AC-6. `new --ref tracker:PROJ-7x` при том же `ref_pattern` — отказ, задача не заведена.
AC-7. `new --ref tracker:PROJ-7 --ref tracker:PROJ-9` при `branch_template: feature/{ref}` — отказ, задача не заведена.
AC-8. Ветка `feature/PROJ-7` уже на сервере (подменённый `ls-remote`) или у задачи проекта в `done` — `new` отказывает, задача не заведена; сбой `ls-remote` — отказ с причиной «имя ветки не проверено».
AC-9. Деление при `branch_template: feature/{ref}` — отказ деления с причиной «ветка по ключу трекера: делите задачу в трекере»; ни одна часть не заведена (ни строки БД, ни ссылки документов), родитель остаётся в `spec_gate`.
AC-10. Деление при `branch_template: feature/{slug}`, когда имя ветки второй части уже занято (на сервере или у задачи проекта в БД), — отказ деления с причиной; ни одна часть не заведена, родитель остаётся в `spec_gate`.
AC-11. При шаблоне по умолчанию `new` и деление не вызывают `ls-remote`.
AC-12. Белый список (запись с `merge_gate: target-human`): отправка в `feature/PROJ-8`, которой нет среди веток задач проекта в БД; в ветку задачи проекта в `done` или `killed`; в `main`; удаление своей ветки (`--delete` и `:<ref>`); тег; отправка без явного refspec; отправка своей ветки с любым из флагов `--tags`, `--follow-tags`, `--mirror`, `--all`, `--force`, `-f` или с refspec `+<своя ветка>` — отказ до вызова git (шпион `subprocess.run` не вызван) и запись журнала с причиной.
AC-13. Белый список (та же запись): отправка ветки задачи проекта в состоянии, отличном от `killed`/`done`, с совпавшим назначением refspec, её перезапись формой `--force-with-lease=refs/heads/<ветка>:<sha>` и отправка `refs/artifacts/<id>` проходят; вызов git несёт `-c push.followTags=false`.
AC-14. Белый список (та же запись): отправка в `main`, запущенная через каждую из точек `gitcmd.git`, `gitcmd.carpentry`, `gitcmd.read`, `gitcmd.read_env`, `gitcmd.read_stream`, отказывается до запуска процесса git (шпионы `subprocess.run` и `subprocess.Popen` не вызваны).
AC-15. Запись проекта для пути клона проекта не читается (испорченный `targets.yaml`) — отправка из клона этого проекта отказывается до запуска процесса git.
AC-16. Проект с `merge_gate: operator` и `branch_template: feature/{ref}`: отправка в `base` и удаление ветки своей задачи не отказываются белым списком.
AC-17. Успешная (код 0) отправка ветки задачи через единую точку (запись с полями по умолчанию и запись `target-human`) оставляет в журнале задачи запись «ветка отправлена: <sha>» с отправленным локальным sha; отправка, завершившаяся ненулевым кодом, такой записи не оставляет.
AC-18. При `push_options: [X, Y]` отправка ветки задачи несёт `-o X -o Y`; отправка `refs/artifacts/<id>` — без `-o`; при пустом `push_options` — без `-o`.
AC-19. Перезапись своей ветки после сжатия/перебазирования несёт `--force-with-lease=refs/heads/<ветка>:<sha>` с sha последней записи «ветка отправлена»; без такой записи — отправка без перезаписи.
AC-20. Голова ветки на сервере отличается от sha последней записи «ветка отправлена» — на переходе `in_dev → verifying` задача в `escalated`, отправки нет.
AC-21. `squash_before_mr: true`, `freshness: rebase` на фикстурном репозитории: после перехода в `verifying` в ветке задачи один коммит от `origin/<base>` с сообщением по `commit_template`, автором и коммиттером `commit_author`, строкой `Co-authored-by` из `co_author` и трейлером `Artel-Actor: orchestrator`; ветка лежит поверх `origin/<base>`, `base` не изменён.
AC-22. `freshness: merge` на фикстурном репозитории, `origin/<base>` впереди ветки: (а) без сжатия — merge-коммит подтяжки и коммит авторазрешения конфликта подтяжки (`pull.py:462-463`) несут автора и коммиттера `commit_author`, строку `Co-authored-by` из `co_author` и трейлер `Artel-Actor: orchestrator`; (б) с `squash_before_mr: true` — после перехода в `verifying` в ветке один коммит поверх `origin/<base>` с автором и коммиттером `commit_author` и строкой `Co-authored-by`.
AC-23. Конфликт перебазирования на входе в `verifying` — состояние `escalated` и запись журнала `PULL_CONFLICT_ROLE_STEP_MARKER`, как у конфликта подтяжки `merge`; незавершённого перебазирования в рабочей копии нет.
AC-24. После вердикта `changes_requested` без коммита developer (`squash_before_mr: true`, `freshness: rebase`, `origin/<base>` впереди ветки) `advance` из `in_dev` отказывается рубежом переделки ревью: задача остаётся в `in_dev`, голова ветки задачи не изменилась (сжатия и перебазирования не было).
AC-25. Для записи с `commit_author` окружение роли несёт `GIT_AUTHOR_*`/`GIT_COMMITTER_*` этого автора; коммиты пульта — чекпоинт (`checkpoint.py:1882`), документ в `refs/artifacts/<id>` (`artifact_branch.py`), коммит `amend-tests` (`amend.py:799`), коммит закрытия (`snapshot.py:272`) — несут того же автора и коммиттера, строку `Co-authored-by` и трейлер `Artel-Actor: orchestrator`.
AC-26. Для записи с `commit_author` коммит роли (без трейлера `Artel-Actor: orchestrator`) не считается коммитом пульта, а коммит пульта с трейлером — считается, хотя автор у них один.
AC-27. Без адаптера `forge.token_user` сверка автора пропускается с записью журнала «сверка автора — после адаптера».
AC-28. При `freshness: rebase` подтяжка перед шагом разработчика, `pull-main`, `approve` приёмки и гейт мержа выполняются прежним `merge` (перебазирования нет).
AC-29. Артель и проект с полями по умолчанию: существующие тесты `new`, деления, подтяжки, отправок, `cleanup` зелёные без правки.

Перезапись своей ветки (после сжатия/перебазирования) — только `push --force-with-lease=refs/heads/<ветка>:<sha>`, где `<sha>` — из последней записи журнала задачи «ветка отправлена: <sha>» (её пишет единая точка отправки части 1 после успешной отправки); записи нет — первая отправка, без перезаписи. Голова на сервере не совпала с этим sha — чужой коммит: эскалация задачи в `_origin_push_gate` (`advance_gates/tests_writing.py`), без перезаписи. На гейте мержа (`fsm_merge_gate.py:701`) поведение без изменений — перезаписи там нет. В `github_adapter.py` меняется только место отправки ветки; поведение черновика MR не меняется.

Критерии приёмки:
- перезапись: `--force-with-lease` несёт sha последней записи «ветка отправлена»; без записи — отправка без перезаписи; голова сервера другая — на переходе `in_dev → verifying` задача в `escalated`, отправки нет;
- `squash_before_mr: true` и `freshness: rebase` на фикстурном репозитории: после перехода в `verifying` в ветке один коммит с сообщением по шаблону, автором и коммиттером `commit_author`, строкой `Co-authored-by` и трейлером `Artel-Actor: orchestrator`, ветка поверх `origin/<base>`, `base` не изменён;
- `freshness: merge`, `origin/<base>` впереди: без сжатия merge-коммит подтяжки и коммит авторазрешения конфликта (`pull.py:462-463`) — с `commit_author`, строкой `Co-authored-by` и трейлером; с `squash_before_mr: true` — после перехода один коммит поверх `origin/<base>` с `commit_author` и строкой `Co-authored-by`;
- конфликт перебазирования — `escalated` и метка `PULL_CONFLICT_ROLE_STEP_MARKER`, как у конфликта `merge`; незавершённого перебазирования нет;
- после `changes_requested` без коммита developer (`squash_before_mr: true`, `freshness: rebase`, `origin/<base>` впереди) `advance` из `in_dev` отказан рубежом переделки ревью, задача в `in_dev`, голова ветки не изменилась;
- запись с `commit_author`: окружение роли и коммиты пульта — чекпоинт, документ в `refs/artifacts/<id>`, коммит `amend-tests` (`amend.py:799`), коммит закрытия (`snapshot.py:272`) — несут этого автора, строку `Co-authored-by` и трейлер `Artel-Actor: orchestrator`; коммит роли без трейлера не считается коммитом пульта, коммит с трейлером — считается; без адаптера — запись журнала «сверка автора — после адаптера»;
- `freshness: rebase`: подтяжка перед шагом разработчика, `pull-main`, `approve` приёмки и гейт мержа — прежний `merge`;
- артель и проект с полями по умолчанию: существующие тесты подтяжки, отправок, `cleanup` зелёные без правки. Если правка существующего теста всё же понадобится — только разделом «Меняемое поведение» и матрицей неослабления SPEC этой части (мандат Оператора 26.10), иначе эскалация.

Матрица неослабления части: сжатие и перебазирование против рубежа переделки ревью (`advance_gates/review.py:110-129`, `fsm_advance.py:816`) — свойство остаётся (место после рубежей), покрыто критерием про `changes_requested`; различимость коммитов пульта и роли по автору (`checkpoint.py:962-966`) при `commit_author` — заменой на трейлер `Artel-Actor: orchestrator` и журнал, покрыто критерием про трейлер.
