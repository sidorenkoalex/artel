# SPEC: CI быстрее — проверка на минимальной версии Python отдельным параллельным заданием; песочница FsmTest не сорит в каталог задач корня запуска

## Контекст
Время прогона CI определяет задание `python` («Синтаксис и тесты
оркестратора», `.github/workflows/ci.yml:189`): замер Оператора 03.10.2026
по CI `main` — 314 с, из них полный `tests/` с `-n auto` 193 с и
`tests/test_invariants.py` на минимальной версии Python в один процесс
110 с, последовательно в том же задании (`ci.yml:232-245`). Остальные
задания идут 8–12 с; задача проходит CI ветки 1–4 раза и CI `main` после
мержа. Отдельно: песочница `FsmTest` в `tests/test_invariants.py` кладёт
`self.tdir` в настоящий `config.TASKS` корня запуска и убирает его только
`addCleanup`, поэтому прерванный прогон оставляет каталог задачи
песочницы в рабочей копии кода (случай 03.10: таймаут шага developer
задачи 01M41AB597B330P2RCXCMVRZPE оставил каталог
01M41FFG8P1GFYHJJXD76AS4QQ, гейт зон отказал переходу). Повторное
заведение ликвидированной задачи 01M41JYGHTP8ZVXVPEF8K8W381.

## Требования
1. Проверка `tests/test_invariants.py` на минимальной объявленной версии
   Python (`scripts/stack_ci.py --min`) выносится из задания `python` в
   отдельное задание CI, которое идёт параллельно с заданием полного
   `tests/`: не зависит от задания `python` (`needs` не ссылается на
   него), а условия запуска совпадают с заданием `python` — `needs:
   changes` и то же условие `if` пропуска пушей без кода.
2. В новом задании `tests/test_invariants.py` гоняется параллельно
   (`-n auto`, `-p xdist`) с тем же таймаутом отдельного теста
   (`-o timeout=120`, `-p timeout`). Известной нестабильности `-n auto`
   на минимальной версии на дату SPEC нет: `pytest-xdist==3.8.0` из
   `requirements.lock` поддерживает 3.11 (`stack_ci.py --min` → 3.11),
   полный `tests/` уже идёт с `-n auto`, локально
   `tests/test_invariants.py` с `-n auto` — около 48 с.
3. Покрытие и строгость не меняются: тот же набор тестов
   (`tests/test_invariants.py` на минимальной версии, полный `tests/` на
   версии манифеста), та же минимальная версия из манифеста
   (`scripts/stack_ci.py --min`), те же зависимости из
   `requirements.lock` (установка в новом задании), та же сверка ссылок
   для полного прогона (снимок до и сверка после остаются в задании
   `python`); ни один шаг не удаляется и не становится необязательным
   (`continue-on-error` и подобного не появляется); новое задание красит
   прогон CI так же, как сейчас красит шаг.
4. Правка `.github/workflows/ci.yml` — приложением к PLAN, проверенным
   `git apply --check` на чистом дереве. Если тест или код пульта читает
   структуру `ci.yml` (имена заданий, шаги) — он поправлен в объёме
   переноса, перечень таких мест — в PLAN.
5. В PLAN — оценка времени задания `python` до и после по замерам CI
   ветки задачи (имена и длительности заданий из прогона ветки).
6. Песочница `FsmTest` в `tests/test_invariants.py` подменяет
   `config.TASKS` временным каталогом (как уже подменяет `DB`, `LOGS`,
   `WORKTREES`, `PROJECTS`): `self.tdir` больше не лежит в настоящем
   каталоге задач корня запуска. Утверждения существующих тестов не
   меняются. Правка — приложением к PLAN.
7. Сторож требования 6 — новый тестовый метод с заявкой «Ловит мутацию»
   внутри того же приложения к `tests/test_invariants.py`: песочница
   `FsmTest` не создаёт и не оставляет каталог задачи в каталоге задач
   корня запуска; метод краснеет при возврате `self.tdir` в настоящий
   `config.TASKS`. Отдельный файл-сторож в `tests/` ветки задачи не
   заводится (CI ветки идёт без приложений, гейт мержа ждёт зелёный CI
   ветки до их наложения — `orchestrator/fsm_merge_gate.py`).

## Критерии приёмки
Всё, что проверяется по `.github/workflows/ci.yml` и
`tests/test_invariants.py`, проверяется по копии дерева с наложенным
приложением PLAN; тесты, ищущие сторожа отдельным файлом `tests/*.py`
ветки, не пишутся (ТЗ, п.7).

AC-1. В `ci.yml` с наложенным приложением есть отдельное от `python`
задание, которое ставит минимальную версию Python из
`scripts/stack_ci.py --min`, устанавливает зависимости из
`requirements.lock` и запускает pytest на `tests/test_invariants.py`;
задание `python` больше не содержит шага `stack_ci.py --min` и прогона
`tests/test_invariants.py` на минимальной версии.

AC-2. Новое задание идёт параллельно заданию `python`: его `needs` равен
`changes` (не содержит `python`), а условие `if` совпадает с условием
задания `python` (`!cancelled() && needs.changes.outputs.code != 'false'`
на пине a5df6f64).

AC-3. Команда pytest нового задания содержит `-n auto`, `-p xdist`,
`-p timeout` и `-o timeout=120`.

AC-4. Задание `python` с наложенным приложением сохраняет все прочие
шаги: версия Python из манифеста (`scripts/stack_ci.py` без `--min`),
установка `requirements.lock`, `py_compile`, снимок ссылок до прогона,
`pytest tests -n auto -p timeout -p xdist -o timeout=120`, сверка ссылок
после прогона; ни в задании `python`, ни в новом задании нет
`continue-on-error`.

AC-5. Приложение PLAN к `.github/workflows/ci.yml` и к
`tests/test_invariants.py` применяется к чистому дереву ветки
(`git apply --check` без ошибок); PLAN перечисляет тесты/код, читающие
структуру `ci.yml`, поправленные в объёме переноса (или фиксирует, что
таких нет).

AC-6. PLAN содержит оценку времени задания `python` до и после по
прогону CI ветки задачи: имена заданий и их длительности.

AC-7. В дереве с наложенным приложением прогон
`tests/test_invariants.py` (класс `FsmTest` и его наследники) не создаёт
каталогов в настоящем `config.TASKS` корня запуска: набор записей
`<корень>/tasks/` до и после прогона совпадает; `FsmTest.setUp`
подменяет `config.TASKS` временным каталогом и `self.tdir` лежит под
ним.

AC-8. В дереве с наложенным приложением `tests/test_invariants.py`
содержит новый тестовый метод-сторож с заявкой «Ловит мутацию», который
зелёный с правкой `setUp` и красный в копии, где `self.tdir` возвращён в
настоящий `config.TASKS` (правка `setUp` откатана).

AC-9. Приложение к `tests/test_invariants.py` не меняет утверждения
существующих тестовых методов: дифф этого файла добавляет подмену
`config.TASKS` в песочнице и новый метод-сторож, существующие `assert*`
не удалены и не ослаблены.

## Оценка объёма и деление
Сигналы по порогам `orchestrator/config.py` для этого SPEC не ожидаются
(3 зоны, 9 критериев, `budget_usd` 25). Если guard назовёт сигнал
«механизм, на который опирается запись в `docs/invariants.md`»
(`tests/test_invariants.py` — реестр инвариантов): монолит — подмена
`config.TASKS`, сторож и перенос задания CI правятся одним приложением
к защищённым путям и сливаются вместе; деление на части не уменьшает
зону, а ветка без приложения не меняется вовсе (ТЗ, п.7).

## Не входит
- Ускорение отдельных медленных тестов (отдельный разбор по замеру
  `--durations`).
- Смена раннера, кэш зависимостей.
- Отмена CI на `artifact/**` (часть (в) ADR-0021).
- Отдельный файл-сторож в `tests/` ветки задачи (ТЗ, п.7).
- Возврат нового задания к последовательному прогону: известной
  нестабильности `-n auto` на минимальной версии нет (требование 2);
  если она проявится на CI ветки — это эскалация разработчика с
  прогоном-доказательством, не тихий откат.
- Правка `orchestrator/`, `docs/adr/`, `docs/roadmap.md`,
  `docs/backlog.md`, `docs/operator-session.md`, `templates/`,
  `targets.yaml`, `models.yaml`, `roles.yaml`, `CLAUDE.md`,
  `scripts/guard.py`, `scripts/ci_push_class.py`, `requirements.lock` —
  только чтение по ТЗ.
- Зелёный полный `tests/`, зелёный CI ветки, неизменность защищённых
  путей в кодовой ветке и непревышение бюджета — их держит пульт.
