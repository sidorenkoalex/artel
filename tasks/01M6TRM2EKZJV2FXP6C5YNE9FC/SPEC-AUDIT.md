## Пути обхода гейтов
- AC-4 при k = 3 опросах CI ветки (две паузы) выполняется буквально и на
  реализации с отсчётом от `start` внешнего цикла — см. отклонение 1.

  `_refuse_if_main_red` для новой головы; «от начала ожидания этим мержем»
  читается как «от начала каждого ожидания» — ожидание CI main не входит в
  общий потолок `MERGE_GATE_CI_WAIT_CEILING_SEC` (`:2036`). Требованиям ТЗ
  это не противоречит; отмечаю, не отклонение.

## Вердикт
concerns. Отклонения:

1. **AC-4 не ловит две из трёх мутаций отсчёта на нижней границе k.** SPEC
   (`tasks/01M6TRM2EKZJV2FXP6C5YNE9FC/SPEC.md`, AC-4) задаёт «k ≥ 3 опросов
   CI ветки задачи с паузой» и окно отказа «15–20 подставных минут». По коду
   `_wait_for_branch_ci_green` пауза идёт после каждого незелёного опроса
   (`orchestrator/fsm_merge_gate.py:381-392`): три опроса с зелёным третьим —
   две паузы, 180 с. Правильная реализация откажет через 18 мин от начала
   ожидания CI main (12 пауз по 90 с); мутация «от `start` внешнего цикла»
   (`:2035`, он же практически вход в `approve`) — через 18 − 3 = 15 мин,
   внутри окна, в том числе с допуском образца `main_ci.py:857`
   (`assertGreaterEqual(elapsed, WAIT_MIN_SEC)`, `WAIT_MIN_SEC` = 15 мин,
   `:121`). Тест проходит на мутации. Закрыть: «k ≥ 3 пауз
   `MERGE_GATE_CI_WAIT_POLL_SEC`» (≥ 270 с, мутация даёт ≤ 13,5 мин) либо
   нижняя граница окна строго выше 15 мин (например, не раньше
   `MAIN_CI_WAIT_LIMIT_SEC` от начала ожидания CI main). Решить может
   Оператор на гейте уточнением формулировки.
2. **Неточный факт в записке составителю тестов** (решение №3.5, SPEC
   «Меняемое поведение»): счётчик опросов подставного `gh` свой у каждого sha
   (`tests/test_01m3sf7dpfgez7vyeggxgtx49e_main_ci.py:98-99`), общий — порог
   `pending_polls` (`:104`). Совет записки остаётся работоспособным; поправить
   формулировку, чтобы составитель не строил сценарий на ложной модели.
