# SPEC-AUDIT: Мерж не ждёт CI main под замком: цвет main сверяет следующий мерж, идущий CI main он дожидается

## ТЗ и SPEC
Требования ТЗ 1–5 перенесены в SPEC 1–5 без потерь. Критерии ТЗ
соответствуют AC-1…AC-7 SPEC. Безопасность тестов, «Не входит» и «Только
чтение» ТЗ перенесены в «Не входит» SPEC.

Отличия SPEC от ТЗ, у каждого есть основание:
- AC-8 и дополнение к требованию 2 о сбое `gh` во время ожидания —
  решение 3 гейта SPEC.
- Раздел «Меняемое поведение» и файл `tests/test_01m3sf7dpfgez7vyeggxgtx49e_main_ci.py`
  в зонах — решение 1 и мандат ANSWER-1.
- Форма тестов с подставными часами — решение 2.
- Записка разработчику — решение 4.

ТЗ требовало эскалации, если покраснеет тест, закрепляющий ожидание после
мержа. Эскалация прошла: первый аудит её нашёл, Оператор ответил ANSWER-1.

SPEC согласован с ADR-0031: п. 6 (`docs/adr/0031-test-runs-strategy.md:34`),
строка этапа 2 (`:41`) и строка матрицы (`:53`). Предел 18 мин и отказ по
пределу ADR не задаёт, их задаёт ТЗ. `budget_usd: 40` не выходит за рамку
ТЗ $45.

Расхождений по существу нет.

## Факты против кода
Подтверждено по рабочему каталогу:
- `MAIN_CI_WAIT_LIMIT_SEC = 18 * 60` — `orchestrator/fsm_merge_gate.py:56`.
- `MAIN_CI_AFTER_MERGE_ACTION` — `:63`.
- `_refuse_if_main_red` — `:607-650`, вызов `:1547`. Отказ только на
  `MAIN_RED`; идущий и неизвестный CI — запись журнала и проход
  (`:640-643`). `--fixes-main` — `:632-638`.
- `_await_main_ci` — `:653-692`, вызов `:1570`. `send_pending()` стоит
  первым (`:666`); предел считается по `time.monotonic()` (`:668`, `:683`);
  пауза — `config.VERIFYING_POLL_INTERVAL_SEC` (`:687`, в config.py:361 —
  90 с); heartbeat — `:672-673`. Исход «неизвестно» содержит «не дождался»
  (`:682`; SPEC называет `:684`, это строка исхода по пределу; подстрока
  та же, расхождение несущественно).
- `repo_context.is_artel` — первая проверка обеих функций.
- Отказ через `sys.exit` под замком: `merge_lock.run_window` освобождает
  замок в `finally` (`orchestrator/merge_lock.py:172-175`). Значит, отказ
  по пределу выйдет прежним путём, как отказ «main красный».

Решение 4 гейта SPEC:
- `tests/test_main_ci_line.py:300-327` действительно требует «не дождался»
  в выводе и в журнале `_await_main_ci` при `MAIN_UNKNOWN`.
- `_refuse_if_main_red` не печатает исход в вывод вне `--fixes-main` и
  отказа (`:640-643`).
- `tests/test_01m4s24ebvb72b8wyj3jy96y0e_merge_reference.py:491-494` ждёт
  запись `MAIN_CI_AFTER_MERGE_ACTION`.

Решение 2: образец подставных часов —
`tests/test_01m3sf7dpfgez7vyeggxgtx49e_main_ci.py:200-211` и `:231-234`.
Верно, но у образца потолок подставной паузы 10 суток (`:233`), а не
«предел с запасом». Безопасности это не вредит: подставные часы двигаются,
и прежний цикл ограничен 18 подставными минутами.

Решение 3: `:640-643` — проход с записью. Верно.

Решение 1: на main ожидание после мержа закрепляют ровно `:776` и `:831`
этого файла. Первый аудит проверил это опытом. Прочие тесты, которые зовут
обе функции или их подменяют, совместимы с SPEC:
- `tests/test_01m5rwnjezt6ya2vp7jk6f3rxs_one_push_per_command.py:729-734`
  (`send_pending` до первого опроса) — требование 1 его сохраняет.
- `tests/test_full_suite_reuse.py:78` и `tests/test_report_outcome_module.py:1761`
  подменяют `_refuse_if_main_red` целиком.

Утверждений о поведении внешних инструментов (git, ОС) в SPEC нет — опыт
не нужен.

Что сделает тест, запущенный до кода:
- AC-2, AC-4, AC-8 и два переписанных теста защищены формой с подставными
  часами.
- AC-1, AC-3 и AC-5 (и мутации AC-7) на прежнем коде доходят до мержа и
  входят в цикл `_await_main_ci` (`fsm_merge_gate.py:667-688`) с идущим CI
  новой головы. Так, AC-1 по определению ставит идущий CI, а AC-5 с
  `--fixes-main` мержит, после чего прежний код ждёт.
- SPEC требует подставные часы только для AC-2/4/8 (абзац «Форма тестов»).
  Если тест AC-1/3/5 подменит паузу счётчиком без сдвига часов, прежний
  код будет крутить опрос настоящие 18 минут. На харнесе с подставным `gh`

  порождает процесс — класс прецедента 04.11.
- Это **отклонение 2**: форму нужно распространить на все критерии, где
  `approve` идёт при идущем CI `main`.

Раздел «Меняемое поведение»:
- Обе строки проходят форму guard (`scripts/guard.py:5689-5743`). «Было»
  есть среди литералов утверждений метода на main: `"done"` — `:792`,
  `"не дождал"` — `:851`, `:854`. Смены вида утверждения, удаления и
  пропуска строки не объявляют.
- **Отклонение 3:** строка `'done'` → `'done'` не объявляет смены значения
  вовсе. Настоящая смена `:776` — переписанный сценарий: две задачи,
  ожидание следующим мержем. При этом утверждения об опросе новой головы
  (`:793-795`) и о строке вывода с зелёным CI main (`:803-805`) в новом
  сценарии под вопросом. По решению 4 сверка до мержа в вывод не печатает,
  значит строку `:803-805` сможет дать только чтение после второго мержа
  при зелёной второй голове. SPEC не говорит, какие утверждения `:776`
  остаются. Гейт неослабления засчитает любую правку метода мандатом на
  файл, так что строка формальна. Решение — за Оператором: принять так
  или уточнить, какие утверждения `:776` сохраняются.

## Пути обхода гейтов
- **Отклонение 4:** мандат ANSWER-1 записан на весь файл. Гейт
  неослабления засчитывает мандатом любую находку в этом файле
  (`orchestrator/advance_gates/test_integrity.py:1366-1372`, `_covering_source`).
  Поэтому ослабление прочих тестов файла — `:908-958`, `:967`
  (`--fixes-main`, красный main), `:860` — машина не отличит от
  разрешённой правки двух тестов. Ограничение «прочие тесты файла не
  меняются» держится только текстом пояснения мандата и ревью.
- Для методов, покрытых мандатом, двусторонний прогон не идёт
  (`test_integrity.py:1345-1356`: покрытая мандатом смена ожидания уходит
  в `outcomes` без `run`). Красноту переписанных `:776`/`:831` на базе
  машина не доказывает; это остаётся на тестах задачи (AC-7) и ревью.
- Буквальное исполнение «ждёт под замком» через внешний цикл гейта
  (возврат исхода ожидания и выход из окна мьютекса) требованию 2
  противоречит. Обхода нет.

## Вердикт
concerns. SPEC можно вести дальше; четыре отклонения Оператор решает на
гейте.

1. AC-1 «`ci.main_line_status` вызван один раз» буквально неверен:
   `_refuse_if_main_red` зовёт его до мержа (`orchestrator/fsm_merge_gate.py:631`).
   Правильная реализация даёт 2 вызова за `approve`. Нужно «один раз для
   новой головы `main`» (SPEC, AC-1).
2. Безопасная форма красной фазы (подставные часы и падающая пауза)
   задана только для AC-2/4/8 (SPEC, абзац «Форма тестов»). AC-1, AC-3 и
   AC-5 на прежнем коде входят в цикл `_await_main_ci`
   (`fsm_merge_gate.py:667-688`) с идущим CI. С паузой без сдвига часов
   это 18 настоящих минут опроса; на харнесе с подставным `gh`
   (`tests/test_01m3sf7dpfgez7vyeggxgtx49e_main_ci.py:77-115`) каждый
   опрос — новый процесс.
3. Строка «Меняемое поведение» `'done'` → `'done'` формальна. SPEC не
   говорит, какие утверждения `:776` сохраняются (`:793-795`, `:803-805`).
   С решением 4 строку вывода `:803-805` даст только чтение после второго
   мержа.
4. Мандат на весь файл: гейт неослабления пропустит ослабление любого
   теста файла (`orchestrator/advance_gates/test_integrity.py:1366-1372`),
   а двусторонний прогон для покрытых мандатом методов не идёт
   (`:1345-1356`). «Прочие тесты не меняются» — только текст и ревью.
