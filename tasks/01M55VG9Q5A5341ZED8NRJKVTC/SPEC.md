# SPEC: Неустойчивый тест предела полного прогона: детерминированное доказательство

## Контекст
`tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py::SuiteRunProfileLimitTest::test_ac5_suite_run_cuts_at_profile_limit_and_reports_it`
(долгоживущий файл задачи 01M48WRE8BHFDY011Q0HQGQ91B) краснел на CI четыре
раза при зелёном коде (07.10, 11.10, 13.10, 17.10); каждый раз — ручной
повтор CI. Прошлая «стабилизация» (01M4P9PHCTT7TXWF422E3Y9GXN) подняла N
до 11–13 с, но не убрала зависимость от реального времени.

**Причина падения 17.10 (установлена по коду, требование 1 ТЗ) — дефект
теста, не пульта и не нагрузки:**

- строка отчёта таймаута, которую проверяет тест, строится в
  `orchestrator/suite_run.py:439` (`render`) и начинается с id задачи:
  `[<id>] suite-run №<n> (полный набор): прогон не уложился в предел <N> с
  (источник: профиль тестов проекта <target>) и оборван — …`;
- id задачи фикстуры — `"01M"` + 23 случайных символа из `ALPHABET`, в
  котором есть цифры (тест `:45`, `:164-165`);
- помощник `standalone` (`:119-120`, `(?<![\d.:])<n>(?![\d.:])`) считает
  число отдельно стоящим и между буквами; id вида `…K60X…` даёт в строке
  отдельно стоящее `60` = `COPY_LIMIT` (`:515`), и `assertFalse`
  `:621-622` краснеет;
- имя проекта (`"p" + word()` из `LETTERS` без цифр, `:46`, `:535`) и номер
  прогона (`№1`) дать 60 не могут — источник только id;
- вероятность по симуляции той же строки на 200 000 зёрен — около 1%
  на прогон (1,0% у аналитика, 1,08% у аудитора); от нагрузки машины и от N
  она не зависит;
- значение config в строку отчёта пульт не подставляет: предел и источник
  приходят из `project_profile.full_suite_limit` (профиль задачи → N) в
  `render(..., limit)` (`orchestrator/suite_run.py:559`, `:593`). Случай
  требования 3 ТЗ (отчёт под нагрузкой действительно называет значение
  config) не подтвердился — эскалации и правки кода пульта нет.

Сверка с 07.10 (гейт мержа 01M48WTP12, прогон 37564791553): копилка
сохранила только приставку контекста «N=4; отчёт (код 1)». Код 1 у
`suite-run --wait` не различает исходы: его дают и полученный «не
зелёный» отчёт (`orchestrator/suite_run.py:721-723`, `sys.exit(1)`), и
пропавший фоновый процесс без отчёта (`:725-732`), и истёкшее ожидание
`--wait` (`:734-739`) — последние два через `sys.exit(<строка>)`. Значит,
по сохранённым данным неизвестно, был ли отчёт и какое утверждение
(`:617-622`) упало. При N=4 под нагрузкой правдоподобен второй, зависящий
от времени механизм — «пробник не стартовал до обрыва»: обрыв наступил
раньше, чем пробник записал событие «start», и краснеет `:617`; копилка
07.10 (коммит `8f6a4e4a`) так и пишет: «предел срабатывает не там».
Механизм id (17.10) с сигнатурой 07.10 тоже совместим. Доказать для 07.10
какой-то один из них по сохранённым данным нельзя.

Независимо от причины 17.10 тест держит исход на реальных часах: обрыв
наступает через N = 11–13 с реального времени при пробнике на 100 с
(`:562`), ожидание отчёта — `--wait 1` с таймаутом вызова 100 с
(`:606-614`); требование 1 убирает эту зависимость, и вместе с ней —
механизм «пробник не стартовал до обрыва».

## Требования
1. Свойство теста — фоновый `suite-run` обрывает прогон по пределу
   профиля N и называет в строке «не уложился» N, а не значение config
   копии пульта — доказывается без зависимости от реального времени и
   нагрузки машины: подменой часов или предела на уровне, где пульт
   читает время, либо иным детерминированным приёмом (способ выбирает
   разработчик) при условии:
   - подменяется только источник времени или таймаута, который читает код
     копии пульта; сам обрыв выполняет код копии пульта по переданному ему
     пределу — место подмены не выше `orchestrator/acceptance.py:1548`
     (`proc.communicate(timeout=limit[0])`); заменять заглушкой
     `acceptance.run_full_suite`, `_run_full_suite_now` или иной код
     между `suite_run._run` и этой строкой нельзя;
   - подмена — только в копии пульта в песочнице теста; код пульта
     рабочего дерева (`orchestrator/`) не меняется.
2. Утверждения метода не удаляются и не ослабляются — все пять:
   `:612` (`assertIn("запущен", …)`), `:617` (событие «start» пробника),
   `:619` (строка «не уложился» есть), `:620` (отдельно стоящее N в
   строке «не уложился»), `:621-622` (отдельно стоящего значения config
   копии пульта в этой строке нет).
3. Устраняется установленная причина падения 17.10: данные фикстуры,
   попадающие в строку «не уложился» (id задачи, имя проекта, номер
   прогона), не могут дать в ней отдельно стоящее значение config ни при
   каком зерне — правкой фикстуры, не правкой утверждения.
4. Правка смерженного долгоживущего файла
   `tests/test_01m48wre8bhfdy011q0hqgq91b_full_suite_limit_runs.py` идёт
   по общим правилам `tests/` и гейта неослабления, без ослабления;
   утверждения метода не удаляются (решение Оператора 18.10: канал
   `amend-tests` для смерженного файла неприменим, ADR-0020 п.6,
   `docs/adr/0020-long-lived-acceptance-tests-in-tests.md:141-145`).
5. Тест прогоняется 50 раз подряд под искусственной нагрузкой — все 50
   прогонов зелёные. Нагрузка: `os.cpu_count()` параллельных процессов
   `python3 -c "while True: pass"`, запущенных до первого прогона и
   снятых после последнего — снятие обязательно и при сбое или обрыве
   серии (например, `trap`/`finally` или внешний `timeout` у каждого
   процесса нагрузки), сиротские процессы нагрузки на машине не
   остаются. Прогон — 50 отдельных запусков
   `python3 -m pytest '<nodeid теста>'` (каждый со своим случайным
   зерном). Команда, число ядер и итог 50/50 записываются в PLAN.md.

## Критерии приёмки
AC-1. Обрыв прогона по пределу N в тесте наступает без того, чтобы N
секунд реального времени прошло: часы или предел, которые читает пульт
копии, подменены детерминированно (требование 1). Ни одно ожидание теста
по реальным часам, от которого зависит исход, не длиннее 5 с. Пределы
`cli(timeout=…)` и `--wait` — страховочные потолки: исход они не держат и
в счёт 5 с не идут.

AC-2. Исход теста не зависит от нагрузки машины: он не определяется
соотношением реального времени работы пробника/пульта и предела N
(требование 1).

AC-3. Обрыв выполняет код копии пульта по переданному ему пределу:
подменён только источник времени или таймаута, место подмены не выше
`orchestrator/acceptance.py:1548`; `acceptance.run_full_suite`,
`_run_full_suite_now` и код между `suite_run._run` и этой строкой в копии
заглушкой не заменены (требование 1).

AC-4. В методе по-прежнему есть все пять утверждений `:612`, `:617`,
`:619`, `:620`, `:621-622` (на main): запуск фона, старт пробника,
наличие строки «не уложился», отдельно стоящее N из профиля в ней и
отсутствие в ней отдельно стоящего значения config копии пульта; ни одно
не удалено и не ослаблено (требования 2, 4).

AC-5. При любом зерне фикстуры id задачи, имя проекта и номер прогона в
строке «не уложился» не содержат отдельно стоящего значения config копии
пульта (требование 3).

AC-6. Мутация «фоновый `suite-run` берёт `config.FULL_SUITE_TIMEOUT_SEC`,
а не предел профиля» (докстринг теста `:601-604`) — тест краснеет, в
том числе когда предел config подставлен в
`proc.communicate(timeout=…)` (`orchestrator/acceptance.py:1548`) вместо
переданного предела.

AC-7. Мутация «отчёт о таймауте печатает значение config, а не N»
(докстринг теста `:601-604`) — тест краснеет.

AC-8. 50 прогонов теста подряд под нагрузкой из требования 5 зелёные;
команда, число ядер и итог 50/50 записаны в PLAN.md (требование 5).
