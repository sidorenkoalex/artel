# SPEC: П2′: artel report — HTML из state.db + метрики гейтовой нагрузки

## Контекст
Роадмап §3 «Панель» требует этап 1 (П2′): статический HTML-отчёт из
живых данных пульта, на замену ручному просмотру `state.db` и журнала.
Утверждённый макет `tasks/T080/mockup.html` уже задаёт раскладку (борд
по состояниям, карточки, алерты, очередь гейтов) — report реализует
тот же вид на реальных данных. Отдельной строкой сюда же переносится
носитель метрик гейтовой нагрузки, отложенный решениями Оператора
31.08 по аудиту v6 (MJ-1/MJ-10): доля автогейта против ручного
прохождения, операторская нагрузка по дням, базовая экономика задач
(включая отчётную веху ADR-0010 — суммарный расход программы).

## Требования
1. Новая команда `report` в CLI: регистрируется минимальной строкой в
   `orchestrator/artel.py`, реализация — в новом модуле (например
   `orchestrator/report.py`).
2. Команда генерирует один самодостаточный HTML-файл из `state.db` и
   журнала: без демона, без HTTP, без JS-фреймворков и без шага сборки
   — как `tasks/T080/mockup.html`.
3. Путь выходного файла выбирает исполнитель (разумный дефолт — внутри
   `.artel/`); после генерации путь печатается в консоль.
4. HTML-файл включает борд задач, сгруппированных по текущему
   состоянию FSM.
5. HTML-файл включает карточку по каждой задаче: статус, бюджет и
   расход, число итераций ревью, эскалации.
6. HTML-файл включает блок незакрытых алертов.
7. HTML-файл включает очередь ожиданий Оператора: задачи, стоящие на
   ручных гейтах.
8. HTML-файл включает блок метрик гейтовой нагрузки (носитель
   контрольных точек 31.08, решения Оператора по MJ-1/MJ-10 аудита
   v6):
   а) доля задач, прошедших acceptance автогейтом (актор `autogate`)
      против прошедших руками (актор `operator`) на переходе — из
      журнала, отдельно за всю историю и за последние 10 задач;
   б) число журнальных записей актора `operator` по дням, за последние
      14 дней;
   в) базовая экономика: $/задачу по done-задачам и суммарный расход
      программы (отчётная веха ADR-0010).
9. Команда `report` read-only: не пишет в `state.db`, не двигает
   состояния задач, не вызывает git и не обращается в сеть.
10. Повторный запуск `report` перегенерирует файл на прежнем месте;
    истории прежних отчётов не сохраняется.
11. Реализация не трогает `orchestrator/fsm.py`, `orchestrator/
    runner.py`, `orchestrator/auto.py`, `orchestrator/doctor.py` —
    ни строкой. Чтение состояния и журнала — через существующие
    функции `orchestrator/store.py`.

## Критерии приёмки
AC-1. Запуск команды `report` без аргументов задачи генерирует ровно
один HTML-файл на диск и печатает в консоль путь к сгенерированному
файлу.

AC-2. Сгенерированный HTML-файл самодостаточен: не содержит ссылок на
внешние скрипты/стили (CDN, JS-фреймворки) и не требует шага сборки —
открывается напрямую из файловой системы.

AC-3. Сгенерированный HTML-файл содержит борд задач, сгруппированных
по текущему состоянию FSM каждой задачи.

AC-4. Сгенерированный HTML-файл содержит для каждой задачи карточку с
полями: статус, бюджет и расход, число итераций ревью, эскалации (если
задача эскалирована).

AC-5. Сгенерированный HTML-файл содержит блок незакрытых алертов.

AC-6. Сгенерированный HTML-файл содержит очередь ожиданий Оператора —
задачи, стоящие на ручных гейтах.

AC-7. Сгенерированный HTML-файл содержит долю задач, прошедших
acceptance автогейтом (актор `autogate`) против прошедших руками
(актор `operator`), рассчитанную по журналу отдельно за всю историю и
за последние 10 задач.

AC-8. Сгенерированный HTML-файл содержит число журнальных записей
актора `operator` по дням за последние 14 дней.

AC-9. Сгенерированный HTML-файл содержит $/задачу по done-задачам и
суммарный расход программы.

AC-10. Прогон команды `report` не меняет ни одной строки в `state.db`
(состояния задач, счётчики, алерты и прочие таблицы остаются
побайтово прежними) и не порождает записей в журнале шагов.

AC-11. Повторный запуск `report` перезаписывает файл по тому же пути
— без сохранения прежних версий отчёта.

AC-12. Дифф реализации не касается `orchestrator/fsm.py`,
`orchestrator/runner.py`, `orchestrator/auto.py`,
`orchestrator/doctor.py`.

## Не входит
- Демон или API (Г0, решение после go/no-go).
- Панель этапа 2 (интерактивная, за пределами статического отчёта).
- Новые записи в БД или журнал сверх того, что уже пишут существующие
  команды.
- Правки любых модулей, кроме нового модуля report и минимальной
  строки регистрации команды в `orchestrator/artel.py`.
