# PLAN: П2′: artel report — HTML из state.db + метрики гейтовой нагрузки

## Подход
Новый лист-модуль `orchestrator/report.py` с единственной публичной
функцией `cmd_report()` (без аргументов — интерфейс, который уже
предполагают залоченные приёмочные тесты tasks/T092/acceptance_tests/,
по образцу `prune.cmd_prune`/`doctor.cmd_doctor`). Регистрация в CLI —
одна строка импорта + одна строка диспетчера в `orchestrator/artel.py`.

Источник данных — ТОЛЬКО уже существующие функции `orchestrator/store.py`
(требование 11): `store.all_tasks` даёт список задач, `store.task_steps`
на каждую задачу — журнал, слитый и отсортированный по `id` (сквозной
autoincrement `steps.id` восстанавливает хронологию через все задачи без
отдельного SQL-запроса по всей таблице разом — такой функции в store.py
нет, а заводить её эта задача не вправе, «Не входит» SPEC). `store.
open_alerts(conn)` — незакрытые алерты, `store.total_spent(conn)` —
суммарный расход программы (ADR-0010).

Разметка — по духу утверждённого макета `tasks/T080/mockup.html`: один
файл, один инлайновый `<style>`, без CDN/JS-фреймворков/шага сборки.
Борд и карточка задачи объединены в одну сущность — плитку борда, несущую
сразу все поля требования 5 (статус, бюджет/расход, итерации ревью,
эскалация): отдельная секция-дубликат карточки не нужна, приёмочные
тесты (AC-4, `_sandbox.all_scopes`) ищут поля РЯДОМ с id задачи, не в
конкретном блоке разметки. Очередь ожиданий Оператора (требование 7) —
отдельная секция, перечисляющая задачи в состояниях `spec_gate`,
`acceptance`, `merge_gate`, `escalated` (тот же список, что уже даёт
флаг «ЖДЁТ ОПЕРАТОРА» `catalog.cmd_status`, и что описан в докстринге
AC-6 как «ручные гейты независимо от gates.yaml» для spec_gate/merge_gate
и escalated по построению; `acceptance` включён туда же, ровно как в
`cmd_status`, — попадание в очередь не обязано совпадать с фактическим
автогейтом, у задачи в `acceptance` решение ещё не принято автогейтом
или Оператором). Секция гейтов подписывает запись именем СОБСТВЕННОГО
состояния задачи — тем самым не создаёт для приёмочного теста борда
(AC-3, `label_chunks`) чужеродной метки: любое повторное упоминание id
задачи в документе оказывается под тем же именем состояния, что и её
настоящее место на борде.

Метрики гейтовой нагрузки (требование 8) — чистые функции над списком
уже прочитанных строк журнала:
- доля acceptance автогейт/оператор — фильтр `action == "state ->
  merge_gate"` и `actor in ("autogate", "operator")` (то же действие и
  та же пара акторов, что реально пишет `fsm._maybe_autogate_acceptance`/
  ручной путь `approve` через `store.set_state`); окно «последние 10» —
  последние 10 таких записей по возрастанию `id` (сквозная хронология),
  не последние 10 задач по номеру — в типичном случае (одна acceptance
  на задачу) оба совпадают, а SPEC требование 8а называет именно
  «журнал»;
- записи actor=operator по дням за 14 дней — группировка по первым 10
  символам `steps.ts` (`YYYY-MM-DD`, тот же формат, что и `store.now()`),
  отсечка `datetime.now(UTC).date() - 14 дней`;
- $/задачу (done) и суммарный расход программы — `store.total_spent`
  напрямую для второго, среднее `spent_usd` по строкам `state == "done"`
  для первого.

Путь отчёта — `config.ROOT / ".artel" / "report.html"`, вычисляется
внутри `cmd_report()` (не модульной константой на импорте — тесты
патчат `config.ROOT` уже ПОСЛЕ импорта модуля через `mock.patch.object`,
константа на уровне модуля заморозила бы старое значение). Один и тот
же путь на каждый вызов даёт перезапись без истории версий (требования
10, AC-11) без отдельной логики удаления: `Path.write_text` сам
перезаписывает существующий файл.

Все текстовые поля (title, message, source, id, state) экранируются
`html.escape` — HTML генерируется из данных БД (title задачи — вход
Оператора/analyst), непроверенная подстановка была бы инъекцией в
собственный отчёт.

## Влияние на систему
Новый модуль и две строки в `orchestrator/artel.py` — ничего в
`orchestrator/fsm.py`, `runner.py`, `auto.py`, `doctor.py` не трогается
(требование 11, AC-12 — проверяется приёмочным тестом на реальный diff
ветки). `orchestrator/store.py` не правится — используются только уже
существующие публичные функции; агрегация «весь журнал сразу» собирается
в `report.py` по задачам, не добавлением нового SQL-запроса в store.py
(вне зоны этой задачи по «Не входит» SPEC).

Команда `report` — чистый читатель: ни одного `INSERT`/`UPDATE` в коде
модуля, ни одного вызова `git`. Единственная точка касания БД —
`store.db()`, та же, что открывает любая другая read-команда
(`cmd_status`, `cmd_log`); `store.db()` внутри вызывает идемпотентный
`migrate()` (используется каждым существующим read-путём пульта уже
сегодня, ничего нового не добавляется этой задачей) — сам факт того,
что состояние читается через уже отработанный путь, а не новый SQL,
и есть аргумент, почему AC-10 (побайтовая неизменность `state.db`)
не нарушается.

Гейты/тесты/лимиты не ослабляются — новых веток кода в защищённых
модулях нет, инвариантов пульт не приобретает новых зависимостей.
Откат — удаление `orchestrator/report.py` и двух добавленных строк в
`artel.py`; никаких данных, миграций схемы или файлов вне
`.artel/report.html` изменение не создаёт.

## Риски
- Отчёт совмещает борд-плитку и карточку задачи в одну разметку вместо
  двух секций макета T080 — сокращает объём HTML, но расходится с
  визуальным макетом; SPEC фиксирует ТОЛЬКО данные (борд, карточка,
  очередь, алерты, метрики), не разметку — риск невысокий, приёмочные
  тесты это уже учитывают (ищут поля субстрокой рядом с id, не по
  классам/тегам).
- «Последние 10 задач» (требование 8а) реализовано как «последние 10
  журнальных записей перехода в merge_gate», а не «последние 10 задач
  по номеру, если у задачи была такая запись» — при повторном
  прохождении acceptance одной и той же задачей (после отказа и
  повторного цикла) эти два толкования разошлись бы; в системе такой
  повтор возможен (отказ приёмки, но потолок `LIMIT_ACCEPT_REJECTS=1`
  делает его редким), приёмочный тест AC-7 использует по одной записи
  на задачу и не различает эти толкования.
