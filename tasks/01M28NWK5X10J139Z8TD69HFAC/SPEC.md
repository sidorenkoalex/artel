# SPEC: класс пуша (ADR-0016) не маскирует красный main — документный пуш наследует итог тестов родителя

## Контекст

Копилка 11.09: операторский коммит cb122d21 (диффы защищённых путей)
уронил один тест, прогон CI этого коммита красный, но два следующих
документных коммита в main (роадмап, копилка) получили «success»: job
`changes` (`.github/workflows/ci.yml`, «Класс пуша — менялся ли код»,
ADR-0016) для пуша в main, где все файлы под `docs/`, `tasks/` или
`*.md` в корне, выставляет `code=false` безусловно, job `python`
пропускается, а пропущенный job не портит итог workflow. Краснота main
всплыла только на подтяжке main в ветку задачи (мерж отклонён), между
тем `pin-update` и гейт свежести канарейки читают именно итог прогона
main. Задача чинит классификатор так, чтобы документный пуш наследовал
итог тестов родительского коммита, а не маскировал его.

## Требования

1. Классификатор пуша выносится из bash внутри `ci.yml` в отдельный
   скрипт `scripts/ci_push_class.py` на stdlib (без сторонних
   пакетов). Вход — имя события, ref, `before`, HEAD и список
   изменённых файлов (либо сам скрипт вызывает `git diff --name-only`).
   Выход на stdout — `code=true`/`code=false` и строка причины.
2. Логика классификации ADR-0016 сохраняется дословно: `artifact/**` —
   `code=false` без диффа; `task/**` и `pull_request` — всегда
   `code=true`; любая неопределённость (нет базы диффа, принудительный
   пуш, ошибка диффа) — `code=true` (fail-closed).
3. Новое правило для документного пуша в main (все изменённые файлы под
   `docs/`, `tasks/` или `*.md` в корне): `code=false` только если
   последний завершённый прогон workflow `ci` для родительского
   коммита (`before`) на ветке main (запрос `gh api
   repos/{owner}/{repo}/actions/runs?head_sha=<before>&branch=main`)
   завершился `conclusion == success`.
4. При `conclusion != success`, при отсутствии прогона для `before`
   либо при любой ошибке запроса к API — классификатор присваивает
   `code=true` (тесты идут). Документный коммит поверх красного main
   даёт красный прогон, а не зелёную плашку.
5. Классификатор печатает в лог задания причину решения одной строкой:
   «документный пуш, родитель <sha> зелёный — тесты пропущены» /
   «родитель <sha> красный — тесты идут» / «нет данных о родителе —
   тесты идут», подставляя фактический sha родителя.
6. `.github/workflows/ci.yml` (защищённый путь) правится так, чтобы job
   `changes` вызывал `python3 scripts/ci_push_class.py` вместо
   inline-логики bash и передавал `GITHUB_TOKEN` в окружение вызова.
7. `docs/adr/0016-ci-jobs-by-push-class.md` (защищённый путь)
   дополняется абзацем «наследование итога родителя», фиксирующим новое
   правило документного пуша.
8. Правки требований 6–7 сдаются unified-диффом приложением к PLAN.md,
   каждый дифф проверен `git apply --check` на чистом дереве перед
   сдачей.
9. `tests/test_ci_push_class.py` покрывает: все ветки классификации
   ADR-0016 на подставных входах — те же ответы, что давал bash;
   документный пуш при красном родителе (`code=true`), при зелёном
   родителе (`code=false`), при ошибке запроса к API (`code=true`);
   строку причины на stdout, называющую sha родителя; зелёный прогон
   существующих тестов.

## Критерии приёмки

AC-1. `scripts/ci_push_class.py` существует, использует только stdlib,
принимает на входе имя события, ref, `before`, HEAD и список
изменённых файлов (либо сам вызывает `git diff --name-only`), печатает
на stdout `code=true` или `code=false` и строку причины.

AC-2. Логика классификации ADR-0016 сохранена дословно: `artifact/**` →
`code=false`; `task/**` и событие `pull_request` → `code=true`; любое
сомнение (нет базы диффа, принудительный пуш, ошибка диффа) →
`code=true` (fail-closed).

AC-3. Для документного пуша в main (все изменённые файлы под `docs/`,
`tasks/` или `*.md` в корне) классификатор запрашивает GitHub API
(`gh api repos/{owner}/{repo}/actions/runs?head_sha=<before>&branch=main`)
о прогоне workflow `ci` для родительского коммита `before` и
присваивает `code=false` только если ответ содержит завершённый прогон
с `conclusion == success`.

AC-4. Если ответ API содержит `conclusion != success`, не содержит
прогона для `before`, либо запрос завершился ошибкой — классификатор
присваивает `code=true`.

AC-5. Классификатор печатает одну из строк-причин: «документный пуш,
родитель <sha> зелёный — тесты пропущены» / «родитель <sha> красный —
тесты идут» / «нет данных о родителе — тесты идут», где `<sha>` —
фактический sha родительского коммита.

AC-6. `.github/workflows/ci.yml` правится unified-диффом (приложение к
PLAN.md, защищённый путь): job `changes` вызывает `python3
scripts/ci_push_class.py` вместо inline bash-логики и передаёт
`GITHUB_TOKEN` в окружение вызова; дифф проходит `git apply --check` на
чистом дереве.

AC-7. `docs/adr/0016-ci-jobs-by-push-class.md` дополняется unified-
диффом (приложение к PLAN.md, защищённый путь) абзацем «наследование
итога родителя», описывающим правило AC-3/AC-4; дифф проходит `git
apply --check` на чистом дереве.

AC-8. `tests/test_ci_push_class.py` проверяет все ветки классификации
ADR-0016 (AC-2) на подставных входах теми же ответами, что давала
bash-версия job `changes`.

AC-9. `tests/test_ci_push_class.py` проверяет документный пуш при
красном родителе (`code=true`), при зелёном родителе (`code=false`),
при ошибке запроса к API (`code=true`), проверяет, что строка причины
на stdout называет sha родителя, и что полный набор существующих
тестов остаётся зелёным.

## Не входит

- Изменение набора заданий CI (job'ов помимо `changes`/`python`).
- Двойной прогон push+pull_request на один sha (отдельная строка
  копилки, вне объёма этой задачи).
- Пропуск тестов для веток задач (`task/**` — всегда `code=true`, без
  исключений).
