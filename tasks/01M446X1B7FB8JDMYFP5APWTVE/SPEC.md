# SPEC: Дозор показывает ход шага роли

## Контекст
Шаг роли идёт до `config.AGENT_TIMEOUT_SEC` = 2700 с (45 мин), и между
записями журнала «agent run started» и «agent run finished»/«TIMEOUT»/
«FAILED» в `steps` ничего не появляется — `watch` (`orchestrator/watch.py::
cmd_watch`) молчит всё это время. Итоговая строка pytest («N failed, M
passed …») сейчас есть только в живом потоке, в `tool_results` провайдера
(`orchestrator/providers/claude.py::ClaudeProvider._user_event` ~381-400,
`orchestrator/providers/codex.py` ~714), в лог шага и в журнал она не
попадает. Прецедент 04.10 (этап 2 ADR-0021): пять шагов developer по 45 мин,
ход виден Оператору только по ручным запросам и чтению лога, число падений
тестов Оператор измерял сам отдельными прогонами по 22 мин. Задача — дать
дозору редкий и короткий сигнал о ходе живого шага.

## Требования

1. Пульт записывает в журнал задачи (`steps`) итоговую строку каждого прогона
   pytest внутри шага роли — строку вида «N failed, M passed …» или
   «N passed …» из результата инструмента — отдельным действием журнала
   «прогон pytest» (actor — роль шага, detail — итоговая строка без
   обрамляющих «=»). На один прогон — не больше одной записи. Поведение
   одинаково для провайдеров Claude и Codex. Прочие результаты инструментов
   ни в журнал, ни в лог шага не попадают; результат инструмента без
   итоговой строки pytest записи не даёт.
2. `watch` получает новый класс событий `pytest` (записи действия «прогон
   pytest»), входящий в набор классов по умолчанию (`_DEFAULT_EVENTS`) и,
   значит, показываемый `watch --observation` без `--events`. Класс
   принимается `--events`/`--exit-on` наравне с остальными. Строка
   печатается существующим форматом `_print_line`
   («<ts>  <id>  <actor>  прогон pytest  | <итоговая строка>»).
3. Новая константа `config.WATCH_PROGRESS_PERIOD_MIN` = 10 (минут). Пока у
   задачи выборки идёт живой шаг роли, `watch` печатает одну строку сводки
   по задаче, когда с начала шага прошло k·N минут (N — эта константа,
   k = 1, 2, …), на первой итерации опроса после этого момента, один раз
   на каждое k; пропущенные k (дозор запущен посреди шага) задним числом
   не печатаются. Сводка содержит: прошедшие и полные минуты шага
   («M/45 мин», полные — из `config.AGENT_TIMEOUT_SEC`), последние 2–3
   вызова инструментов из лога шага (строки «· <Tool> <аргумент>»
   `orchestrator/agent_log.py`, каждая сжата до не более 40 символов),
   число изменённых файлов рабочей копии задачи. Длина строки сводки — не
   более 240 символов.
4. Живой шаг — последняя запись задачи «agent run started» не сопровождается
   более поздней записью «agent run finished», «agent run TIMEOUT» или
   «agent run FAILED» той же задачи. Начало шага — `ts` записи «agent run
   started», лог шага — путь из её detail («лог: <path>»). Без живого шага
   сводки и предупреждения не печатаются.
5. Ранние предупреждения — одной строкой каждое, не больше одного раза каждого
   вида за шаг:
   - «нет коммитов»: с начала шага прошло не меньше
     `config.WATCH_NO_COMMIT_WARN_SEC` = 2100 с (35 из 45 мин), а у ветки
     задачи нет ни одного коммита новее начала шага;
   - «стоимость шага»: стоимость шага, посчитанная по usage, уже лёгшему в
     лог шага (`spend.partial_tokens_from_log` + `spend.partial_cost_usd`),
     превысила `config.WATCH_STEP_COST_WARN_USD` = 5.0 $. Стоимость не
     разрешилась (`None`) — предупреждения этого вида нет.
6. Строки сводки и предупреждений печатаются тем же форматом `_print_line`
   с actor `watch` и действием «ход шага» (сводка) либо «предупреждение»
   (предупреждения); формат существующих строк `watch` не меняется.
   Сводки и предупреждения не являются классом `--events`/`--exit-on` и не
   останавливают цикл `watch`.
7. Верхняя граница вывода — `config.WATCH_PROGRESS_LINES_PER_HOUR` = 16
   новых строк (класс `pytest` + сводки + предупреждения вместе) на задачу
   за любые скользящие 60 минут. Строка сверх границы не печатается;
   журнал от этого не меняется; предупреждение, не напечатанное из-за
   границы, считается выданным за этот шаг. Сводок по таймеру при N = 10 —
   не больше 6 в час.
8. Описание новых строк дозора, класса `pytest` и границы строк в час
   добавлено в `docs/operator-session.md`.
9. Тесты в `tests/` с заявками «Ловит мутацию» на требования 1–7: запись
   итоговой строки pytest из потока Claude и из потока Codex; сводка
   печатается по таймеру и не печатается без живого шага; предупреждение
   35/45 печатается один раз за шаг. Существующие тесты
   `tests/test_watch.py`, `tests/test_agent_log.py` не ослабляются.

## Критерии приёмки

AC-1. Событие результата инструмента потока Claude, текст которого содержит
итоговую строку pytest («3 failed, 120 passed in 12.30s» или «120 passed in
9.10s», в том числе в обрамлении «=»), даёт ровно одну запись журнала
задачи с действием «прогон pytest», actor — роль шага, detail — итоговая
строка без обрамляющих «=»; результат инструмента без итоговой строки
pytest записи не даёт; текст результата инструмента в лог шага не пишется.

AC-2. То же для события результата команды потока Codex: итоговая строка
pytest даёт ровно одну запись «прогон pytest» с той же формой detail,
результат без неё — ни одной.

AC-3. `watch --observation <ID>` и `watch --tasks <id>` без `--events`
печатают новую запись «прогон pytest» строкой
«<ts>  <id>  <actor>  прогон pytest  | <итоговая строка>»; `--events pytest`
принимается, а неизвестный класс у `--events` по-прежнему даёт отказ,
перечисляющий все доступные классы, включая `pytest`.

AC-4. При живом шаге (последняя «agent run started» без последующих
finished/TIMEOUT/FAILED) и прошедших с его начала ≥ `WATCH_PROGRESS_PERIOD_MIN`
минутах `watch` печатает ровно одну строку сводки с actor `watch` и
действием «ход шага», содержащую «M/45 мин», не более трёх последних
вызовов инструментов из лога шага (каждый ≤ 40 символов) и число изменённых
файлов рабочей копии задачи; длина строки ≤ 240 символов. Следующая сводка
появляется только после следующего кратного N, не на каждой итерации опроса.

AC-5. Без живого шага (записи «agent run started» нет либо за ней есть
«agent run finished»/«TIMEOUT»/«FAILED») `watch` не печатает ни сводок, ни
предупреждений, сколько бы времени ни прошло.

AC-6. При живом шаге, прошедших ≥ 2100 с и отсутствии коммитов ветки задачи
новее начала шага `watch` печатает предупреждение «нет коммитов» ровно один
раз за шаг — на последующих итерациях того же шага повтора нет; при
наличии такого коммита предупреждения нет; новый шаг (новая «agent run
started») может выдать его снова.

AC-7. При живом шаге, чья стоимость по usage лога шага превысила
`WATCH_STEP_COST_WARN_USD`, `watch` печатает предупреждение «стоимость
шага» ровно один раз за шаг; стоимость не разрешилась или не выше порога —
предупреждения нет.

AC-8. За любые скользящие 60 минут `watch` печатает по одной задаче не
больше `WATCH_PROGRESS_LINES_PER_HOUR` строк класса `pytest`, сводок и
предупреждений вместе; строки сверх границы не печатаются, записи журнала
при этом не меняются.

AC-9. Константы `WATCH_PROGRESS_PERIOD_MIN` = 10, `WATCH_NO_COMMIT_WARN_SEC`
= 2100, `WATCH_STEP_COST_WARN_USD` = 5.0, `WATCH_PROGRESS_LINES_PER_HOUR` = 16
объявлены в `orchestrator/config.py`; `docs/operator-session.md` описывает
класс `pytest`, строки «ход шага»/«предупреждение» и границу строк в час.

## Оценка объёма и деление

Сработавшие сигналы (guard): число затрагиваемых модулей/файлов (по
упоминаниям путей SPEC: `watch.py`, `config.py`, `agent_log.py`,
`runner.py`, провайдеры Claude/Codex, `spend.py` как источник, тесты,
`docs/operator-session.md`); затронут инвариантный механизм (зона ТЗ
`orchestrator/` упомянута в `docs/invariants.md` — зона задана самим ТЗ,
сузить её аналитик не вправе); прогноз диффа не был дан.

Прогноз диффа: 40 КиБ (код дозора и записи строки pytest — порядка
300-500 строк, тесты — сопоставимо; далеко ниже половины потолка гейта
ёмкости).

**Обоснование монолита** (материал для решения Оператора на гейте SPEC):
задача делима технически по шву «запись строки pytest в журнал
(провайдеры/runner, требование 1)» → «дозор: класс `pytest`, сводки,
предупреждения, граница строк (`watch.py`/`config.py`, требования 2-8)»,
и обе части мержимы с зелёной планкой. Довод за монолит — не атомарность
механики, а объём и цена: ТЗ — одна строка бэклога «волны один» с рамкой
$25; граница строк в час (требование 7) считается по строкам класса
`pytest` вместе со сводками, то есть вторая часть проверяет первую в
одном счётчике; две подзадачи дают две фиксированные стоимости цикла
(анализ, планка, ревью — планка калибровки не ниже $25 каждая) при общем
диффе около 40 КиБ. Если Оператор предпочтёт нарезку — шов выше, первой
идёт запись строки pytest.

- Сообщение о задаче без живого цикла `auto`/`run` (живость процесса цикла
  не проверяется; живой шаг определяется только по журналу, требование 4).
- Изменение формата существующих строк `watch`.
- Запись в журнал или лог прочих результатов инструментов, кроме итоговой
  строки pytest.
- Правка путей «только чтение» ТЗ: docs/adr/, docs/roadmap.md,
  docs/backlog.md, templates/, skills/, CLAUDE.md, models.yaml, roles.yaml,
  scripts/guard.py, .github/workflows/ci.yml, conftest.py,
  tests/test_invariants.py, docs/invariants.md.
- Неослабление существующих тестов `tests/test_watch.py`,
  `tests/test_agent_log.py` отдельным AC не заказывается — её держит пульт
  (гейт неослабления тестов и полный зелёный набор `tests/`).
