# SPEC: Авто-коммит регенерированной карты кодовой базы оркестратором на merge

## Контекст
`docs/codebase-map.md` — автогенерируемый файл (`scripts/codebase_map.py`),
но за его свежесть в `main` не отвечает никто один: developer регенерирует
карту в ветке задачи по конвенции скила `conventions-core`, Оператор — руками,
а на самих мержах — никто. Факты 26.08: три красных прогона CI `main`
«карта не свежа» после мержей и конфликт мержа T041 по карте (файл
регенерирован параллельно и в ветке, и в `main`); четвёртая регенерация —
руками Оператора. Красный `main` обесценивает CI как сигнал и маскирует
настоящие падения.

Решение Оператора 26.08 (пересмотр первоначального ТЗ): авто-коммит делает
не CI-джоб, а оркестратор в merge-последовательности `merge_gate`. Причина
пересмотра — вариант с CI-джобом требует правки `.github/workflows/ci.yml`,
защищённого пути (`no_paths`, скил `conventions-core`); вариант с
оркестратором закрывает ту же проблему без касания защищённых путей, логика
ложится в `orchestrator/fsm.py` под обычные тесты. Роли конвейера от стухшей
карты в git не страдают уже сейчас — бриф developer регенерирует карту сам
(`orchestrator/brief.py`, T028); карта в git нужна людям, параллельным
сессиям и CI-детектору `codebase-map`, который этой задачей не меняется.

## Требования
1. В merge-последовательности `merge_gate` (`orchestrator/fsm.py`, ветка
   `cmd_approve` при `state == "merge_gate"`), после успешного
   `git merge --no-ff` и до `git push`, оркестратор прогоняет
   `scripts/codebase_map.py`.
2. Если регенерированная карта содержательно отличается от закоммиченной
   (сверка содержимым, игнорируя строку `built_at_sha` — тем же принципом,
   что CI-джоб `codebase-map`, ред. Оператора 26.08: `built_at_sha` меняется
   при каждой регенерации и сам по себе не повод для коммита) — оркестратор
   коммитит регенерированную карту отдельным коммитом с сообщением вида
   «карта кодовой базы: регенерация после merge `<id>`».
3. Если содержательных отличий нет — оркестратор откатывает регенерацию
   (`git checkout -- docs/codebase-map.md`, по образцу `brief.py`) и не
   коммитит ничего.
4. Оркестратор пушит как раньше: merge-коммит и, если был сделан, коммит
   карты уходят одним `git push`.
5. Провал регенерации карты или коммита карты не отменяет merge и не
   блокирует переход задачи в `done`: `git push` выполняется в любом случае;
   при провале шага карты — запись в журнал и алерт `kind=incident`
   (`source` вида `fsm.map_regen`).
6. Новые git-вызовы в рамках этой логики идут только через обёртку
   `gitcmd.git` (образец T036).

## Критерии приёмки
AC-1. Merge ветки, после которого карта содержательно стухла, оставляет в
`main` два коммита — merge-коммит и коммит регенерированной карты; карта
после этого содержательно свежа.

AC-2. Merge, не меняющий карту содержательно, второго коммита не порождает;
рабочее дерево после `merge_gate` остаётся чистым.

AC-3. Провал регенерации или коммита карты не отменяет merge: задача уходит
в `done`, в журнале есть запись о провале, в `alerts` открыт инцидент
`kind=incident` с `source` вида `fsm.map_regen`.

AC-4. Все новые git-вызовы этой задачи идут через `gitcmd.git`.

AC-5. Существующий набор тестов остаётся зелёным.

AC-6. `.github/` и `skills/` в диффе задачи не затронуты.

## Не входит
- Изменение CI-джоба `codebase-map` (`.github/workflows/ci.yml`) — джоб не
  трогается, остаётся детектором единственного непокрытого случая: ручная
  правка `.py` Оператором прямо в `main` мимо конвейера.
- Правки `.github/`, `skills/`, `templates/` и прочих защищённых путей —
  не затрагиваются вовсе.
- Изменение конвенции developer «правишь `.py` — регенерируй карту тем же
  коммитом» (скил `conventions-core`) — конвенция остаётся без изменений;
  её пересмотр (и вместе с ним исчезновение класса конфликтов карты при
  merge) — отдельный шаг Оператора после этой задачи.
- Разрешение конфликта мержа по карте на `merge_gate` — существующее
  поведение (отказ merge при конфликте) сохраняется как есть; это отдельная
  строка беклога «Возврат из merge_gate».
