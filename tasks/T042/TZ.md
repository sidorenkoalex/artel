# ТЗ: Авто-коммит регенерированной карты кодовой базы оркестратором на merge

Решение Оператора 26.08 (пересмотр первоначального ТЗ): авто-коммит
делает НЕ CI-джоб, а оркестратор в merge-последовательности merge_gate.
Причина пересмотра: вариант с джобом требует правки .github/workflows/
ci.yml — защищённого пути (no_paths, enforcement, скил conventions-core),
то есть либо прецедента доступа агента в .github/, либо ручного MR
Оператора с логикой в bash без тестов. Вариант с оркестратором закрывает
ту же проблему без касания защищённых путей, а логика ложится в
orchestrator/fsm.py под обычные тесты.

Проблема: docs/codebase-map.md — автогенерируемый файл (scripts/
codebase_map.py), но за его свежесть в main не отвечает никто один:
developer регенерирует в ветке по конвенции, Оператор — руками, а на
мержах — никто. Факты 26.08: три красных прогона CI main «карта не
свежа» после мержей; конфликт мержа T041 по карте (файл регенерирован
и в ветке, и в main параллельно); четвёртая регенерация — руками
Оператора. Красный main обесценивает CI как сигнал и маскирует
настоящие падения. При этом роли конвейера от стухшей карты в git не
страдают — бриф developer регенерирует карту сам (orchestrator/brief.py,
T028); карта в git нужна людям, параллельным сессиям и CI-детектору.

Что сделать: в merge-последовательности merge_gate (orchestrator/
fsm.py, ветка cmd_approve state == "merge_gate") после успешного
`git merge --no-ff` и до `git push` оркестратор:
1) прогоняет scripts/codebase_map.py;
2) если регенерированная карта СОДЕРЖАТЕЛЬНО отличается от
закоммиченной — коммитит её отдельным коммитом с сообщением вида
«карта кодовой базы: регенерация после merge <id>»; сверка
содержимым — игнорируя строку built_at_sha, тем же принципом, что
CI-джоб codebase-map (ред. Оператора 26.08): built_at_sha меняется
при каждой регенерации и сам по себе не повод для коммита;
3) если содержательных отличий нет — откатывает регенерацию
(git checkout -- docs/codebase-map.md, образец brief.py) и ничего
не коммитит: лишний коммит на каждый merge не нужен;
4) пушит как раньше — merge-коммит и, если был, коммит карты уходят
одним push.

Отказоустойчивость: merge к этому моменту уже совершён — провал
регенерации или коммита карты НЕ отменяет merge и НЕ блокирует переход
в done. Порядок: push выполняется в любом случае; при провале шага
карты — запись в журнал и алерт kind=incident (source вида
fsm.map_regen). Красный CI main от стухшей карты в этом случае —
штатная работа детектора, он остаётся страховкой.

Границы:
- Новые git-вызовы — только через обёртку gitcmd.git (образец T036).
- CI-джоб codebase-map НЕ трогается: остаётся детектором на
  единственный непокрытый случай — ручная правка .py Оператором
  прямо в main мимо конвейера.
- .github/, skills/, templates/ и прочие защищённые пути не
  затрагиваются вовсе.
- Конвенция developer «правишь .py — регенерируй карту тем же
  коммитом» в этой задаче не меняется (правка скилов — отдельный шаг
  Оператора после мержа; после её снятия исчезнет и класс конфликтов
  карты при merge). Конфликт мержа по карте в этой задаче не
  разрешается — существующее поведение (отказ merge) сохраняется,
  это отдельная строка беклога «Возврат из merge_gate».

Критерии приёмки (ориентир): (1) merge ветки, после которого карта
содержательно стухла, оставляет в main два коммита — merge и коммит
регенерированной карты, карта после этого содержательно свежа;
(2) merge, не меняющий карту содержательно, второго коммита не
порождает, рабочее дерево остаётся чистым; (3) провал регенерации или
коммита карты не отменяет merge: задача уходит в done, в журнале
запись, в alerts открыт incident fsm.map_regen; (4) новые git-вызовы
идут через gitcmd.git; (5) существующий набор тестов зелёный;
(6) .github/ и skills/ в диффе задачи не затронуты.
