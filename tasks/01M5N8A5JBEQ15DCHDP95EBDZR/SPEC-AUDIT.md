# SPEC-AUDIT: Сброс удержанных записей копилки, бэклога и doc-commit — одним пушем

## ТЗ и SPEC
Сверено в обе стороны: требования ТЗ 1–7 и решения гейта SPEC (круг 1: О-1…О-5; круг 2: О-1…О-3) в SPEC есть.
- Требование 1 ТЗ → требование 1 SPEC; требование 2 ТЗ → требование 3 SPEC; требование 3 ТЗ → требования 4–6 SPEC; требование 4 ТЗ → требование 7 SPEC (уточнено решением О-1 круга 1); требование 5 ТЗ → требование 9 SPEC; пункты (а)–(д) требования 6 ТЗ → AC-1, AC-2, AC-3, AC-4, AC-5; требование 7 ТЗ → раздел «Не входит» (SPEC.md, строка «Правка существующих тестов»).
- ТЗ 6(а) предлагает «шпион на `gitcmd`». SPEC (требование 10) считает пуши на стороне bare-origin — так решил Оператор (О-4 круга 1). Расхождения нет.
- Решения круга 2 вошли в SPEC: О-1 — в AC-7 (SPEC.md:128), О-2 — в AC-10 (SPEC.md:150), О-3 — в требование 2 (SPEC.md:36–44).
- **Расхождение внутри требования 2 (см. О-1 вердикта).** Требование 2 одновременно требует двух вещей:
  1. «исход сверки каждой записи пакета совпадает с исходом последовательной отправки»;
  2. для первой записи `known` — «свежий `origin/main`» (SPEC.md:36 вместе с :40–44).

  Для первой записи эти условия несовместимы. При последовательной отправке `known` первой записи — это `_known_origin_main` до fetch (`orchestrator/notes.py:1257`), а не свежий origin. Решение О-3 круга 2 говорит «голова пакета перед этой записью». Для первой записи пакета эти слова не обязывают брать свежий origin/main: это прочтение аналитика.

Неполнота (низкая): SPEC называет два входа в сброс — `note --flush`/`doc-commit --flush` (:1452–1453, :1566–1567) и попутный сброс. Третий вызов `_flush_pending` есть в публичной `doc_commit_content` (`orchestrator/notes.py:1633–1634`). Через неё пакетный сброс и новые строки вывода требования 7 доходят и до её вызывающих. Поведение от этого не ломается, но SPEC этот вход не упоминает.

Механика `known` при последовательной отправке, сверена по коду:
- `known` читается до fetch (:1257, :695–704).
- `git fetch origin main` и `git push origin HEAD:main` двигают `refs/remotes/origin/main`. Поэтому у k-й записи (k>1) `known` — это результат push предыдущей записи, то есть голова пакета.
- У первой записи `known` — состояние клона на момент прошлой отправки, не свежий origin.
- Сетевой отказ fetch в `_run` удерживает `--apply` без `base_blob`: :1349 `break` → :1363 `_hold_pending`. `_hold_pending` добавляет базу только записи `doc-commit` (:345–347). На сбросе такая запись `--apply` проходит через `_foreign_base_refusal` с `known` (:1006–1009).

Мутация «`known` первой записи = свежий origin/main», которую требование 2 к тому же прямо предписывает, проходит все AC-1…AC-10.

## Пути обхода гейтов
- **Обход сверки через первую запись пакета (О-1).** Разработчик буквально выполняет требование 2: `known` первой записи = свежий origin/main. После этого пиновая сверка и проверка чужой правки `--apply` молча пропускают запись, а все AC зелёные.

  Сценарий:
  1. `note --apply` удержан после сетевого отказа fetch (notes.py:1349 → :1363), `base_blob` у него нет.
  2. Оператор с другой машины правит `docs/backlog.md` в origin.
  3. `note --flush`.

  При последовательной отправке запись получает `APPLY_FOREIGN_BASE_REFUSAL`: чужой коммит лежит в `known..FETCH_HEAD` (:921–922). В пакете по требованию 2 проверка проходит, и заготовка целиком затирает чужую правку. То же происходит с удержанным `doc-commit` без `held_base` (запись до SPEC 01M3Y75X, :1301–1306) и `DOC_COMMIT_BASE_REFUSAL`.
- Других путей обхода не нашёл. AC-10 закрывает перестройку через rebase. Требование 10 закрывает подсчёт пушей шпионом, который можно обмануть, если обойти `gitcmd`.

- **О-1 (среднее/высокое).** Требование 2 (SPEC.md:35–44): «для первой записи — свежий `origin/main`» в роли `known` противоречит первой фразе того же требования о совпадении с последовательной отправкой.
  - При последовательной отправке `known` первой записи — `_known_origin_main` до fetch (`orchestrator/notes.py:1257`, :695–704). При `known` = свежий origin пиновая сверка `doc-commit` без `held_base` (:851–854) и сверка чужой правки `--apply` без `base_blob` (:962–971) пусты: blob сравнивается сам с собой.
  - Это ослабление проверки без мандата. Запись `--apply` без `base_blob` достижима: удержание после сетевого отказа fetch, :1349 → :1363.
  - Ни один AC это не ловит.
  - Предложение: в требовании 2 точка отсчёта первой записи — свежий origin/main, а `known` первой записи — прежний `_known_origin_main` клона до fetch этого сброса (для k>1 — голова пакета перед записью, как сейчас). Плюс AC: удержанная `--apply` без `base_blob` (или `doc-commit` без `held_base`) идёт первой в пакете; в origin есть чужая правка её файла после известной клону головы. Ожидается прежний отказ `APPLY_FOREIGN_BASE_REFUSAL` (или `DOC_COMMIT_BASE_REFUSAL`), запись остаётся удержанной, остальные записи уходят одним push.
- **О-2 (низкое).** Контекст SPEC (SPEC.md:14–18) не называет третий вход в `_flush_pending` — публичную `doc_commit_content` (`orchestrator/notes.py:1633–1634`). Пакетный сброс и новые строки вывода требования 7 пойдут и через неё. Поведение от этого не ломается, достаточно упомянуть этот вход.
