Если исполнитель возьмёт `known` один раз на весь пакет (как в `_attempt`), то у записи doc-commit без `held_base` пиновая сверка :852–854 разойдётся с последовательной. Пример: вторая запись того же пути получит `DOC_COMMIT_BASE_REFUSAL`, хотя при последовательной отправке прошла бы.
- Такие записи бывают только из удержаний до появления `held_base`, отсюда `NO_BASE_WARNING` на :1301–1306. Ни один AC этот случай не проверяет. Отклонение О-3 (низкое).

## Проверяемость критериев
| Критерий | Проверяем | Ловимая мутация |

| AC-3 | частично | Ловит: после non-fast-forward нет повтора; повтор без fetch. Не ловит: перестройку пакета через rebase или cherry-pick готовых коммитов без повторного `_build_*`, то есть без сверки баз. Чужой коммит в AC-3 не обязан задевать путь записи — отклонение О-2. |
| AC-4 | да | Правка конфигурации вошла в пакет (без гейта набора или вместе с ним), или ушла до пакета. |
| AC-5 | да | Попутный сброс (`explicit=False`) идёт старым путём по одному push. |
| AC-6 | да | sha первой или последней записи печатается для всех; строка заметки отсутствует; журнал пишется с sha не той записи; отказавшая запись пишет журнал. |

AC-7 не смотрит ни журнал, ни вывод, а последняя фраза SPEC 8 («записи неотправленного пакета записи журнала об отправке не получают», SPEC.md:66–70) другим AC не покрыта — отклонение О-1. |

Замечание к AC-7 и SPEC 10 (не отклонение). Отказ non-fast-forward git-клиент выносит сам, так что «ровно `MAX_PUSH_ATTEMPTS` попыток» на стороне origin видно только при особой постановке: например, origin сдвигается из клиентского `pre-push` рабочего клона, и тогда отказ получает уже серверная транзакция. SPEC.md:183–187 оставляет этот выбор автору тестов, это допустимо.

## Пути обхода гейтов
1. Перестройку пакета при non-fast-forward (SPEC 5) можно сделать через `git rebase` или cherry-pick уже построенных коммитов на свежий `origin/main`, не вызывая `_build_*` заново. Тогда сверки баз SPEC 2 (`held_base`, `base_blob`) против чужого коммита не выполнятся. Если чужой коммит тронул тот же `docs/**` или `docs/backlog.md`, запись затрёт его: rebase без конфликта проходит, если правки в разных строках. Это ровно тот сценарий, от которого защищают сверки. AC-3 этого не ловит (О-2).
2. Писать журнал при сборке коммита пакета, до push. AC-6 проходит, потому что push в нём успешен, а AC-7 журнал не проверяет (О-1).

## Вердикт
concerns — отклонения есть, все решаемы Оператором на гейте уточнением AC, возврат аналитику не нужен.

- **О-1** (среднее). Последняя фраза SPEC 8 — «записи неотправленного пакета записи журнала об отправке не получают» (SPEC.md:66–70) — не держится ни одним AC. AC-7 (SPEC.md:123–127) не проверяет ни журнал, ни строки sha. Мутацию «журнал и вывод пишутся до push» (сейчас порядок держит notes.py:1203–1206) тесты не ловят. Предложение: в AC-7 добавить «ни строки об отправке, ни записи журнала `_journal_commit` нет».
- **О-2** (среднее). AC-3 (SPEC.md:96–100) не требует, чтобы чужой коммит задевал путь удержанной записи. Перестройка без повторной сверки баз (rebase или cherry-pick вместо повторного `_build_*`, вопреки SPEC 2 и 5, SPEC.md:34, :49) проходит AC-3. Предложение: в AC-3 или новым AC — чужой коммит меняет путь удержанного doc-commit с `held_base` между построением и push. После перестройки эта запись получает `DOC_COMMIT_STALE_REFUSAL` и остаётся удержанной, остальные уходят.
- **О-3** (низкое). SPEC 2 и 9 (SPEC.md:34–41, :73–79) называют параметром только точку FETCH_HEAD. Пиновая сверка doc-commit без `held_base` (notes.py:851–854) зависит ещё и от `known` (notes.py:695, :1257). При последовательной отправке `known` идёт вперёд после каждого push, а в пакете, взятый один раз, расходится с последовательным исходом. Касается только старых удержаний без `held_base` (:1301–1306), AC нет. Предложение: в SPEC 2 явно указать, что `known` записи пакета — голова пакета перед ней.
