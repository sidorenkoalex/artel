## Пути обхода гейтов
1. **Пиновая сверка записи k>1 на перестройке (среднее/низкое).** Правило
   SPEC.md:49 — для k>1 `known` равен голове пакета перед записью — на
   повторном построении после non-ff даёт голову, которая УЖЕ содержит чужой
   коммит, сдвинувший origin. При последовательной отправке `_attempt`
   вычисляет `known` один раз до цикла (:1257). На повторе запись k>1 сверяется
   с головой origin после записи k-1, то есть с ДО чужого коммита. Тогда чужая
   правка её файла даёт `DOC_COMMIT_BASE_REFUSAL` (:853–854). В пакете по
   буквальному правилу SPEC `known` = точка отсчёта, сверка пуста, и запись
   затирает чужую правку. Это нарушает и «исход совпадает с последовательной
   отправкой» (SPEC.md:36), и «пиновая сверка не ослабляется» (SPEC.md:50).
   Касается `doc-commit` без `held_base` (только старые записи, см. «Факты»).
   Для `--apply` без `base_blob` то же произойдёт, если при перестройке запись
   перечитать из файла удержания: тогда `base_blob`, записанный первым
   построением (:1010), теряется. При последовательной отправке словарь
   переживает повтор, и следующий повтор ловит `APPLY_STALE_BASE_REFUSAL`.
   SPEC не говорит, сохраняется ли `base_blob` первого построения при
   перестройке. AC-10 закрывает только `held_base`, AC-11 — только первую
   запись и только первое построение.
2. **Неоднозначность «первая запись пакета».** Если первая удержанная запись
   отказала по валидации, вторая — «первая запись пакета» (SPEC.md:46,
   `known` до fetch) или «k>1» (`known` = голова пакета = свежий origin)?
   При последовательной отправке у неё `known` уже свежий: fetch первой записи
   сдвинул `refs/remotes/origin/main`. Ни одно прочтение не ослабляет текущее
   поведение, но тесты автора и код разработчика могут понять это по-разному.
   Низкое.
