# PLAN: Пагинация CI-гейта — учитывать все проверки, не первую страницу

## Подход

Дыра одна и узкая: `ci.check_runs` спрашивал у `gh` одну страницу
(`repos/{owner}/{repo}/commits/<sha>/check-runs`, умолчание API — 30 записей)
и отдавал её вызывающему как «все проверки коммита». Ответ при этом сам
называет, сколько проверок у коммита на самом деле — поле `total_count`
рядом с `check_runs`. Правка живёт целиком внутри `check_runs`: интерфейс
(`list | None`, причина строкой) и все решения `branch_status` про
зелёное/красное/идущее не трогаются — SPEC это прямо исключает.

Три решения, которые стоит назвать явно.

1. **Пагинация руками, а не `gh api --paginate`.** У `--paginate` на этом
   endpoint'е нет пригодного вывода: страницы печатаются как несколько
   JSON-объектов подряд (это не разбирается одним `json.loads`), а
   склейка в массив — флаг `--slurp` из `gh` 2.32+. Гейт merge не должен
   зависеть от версии CLI на машине Оператора, и главное — при `--paginate`
   `total_count` теряется в шуме страниц, а требование 2 SPEC построено
   именно на сверке с ним. Ручной цикл по `page=` даёт и то, и другое:
   счётчик из первого ответа и явную точку, где ответ признаётся неполным.

2. **Критерий полноты — точное равенство `len(runs) == total_count`.**
   Не «≥», не «набрали хоть сколько-то». Меньше обещанного — очевидная
   неполнота (критерий приёмки 1). Больше обещанного — тоже отказ: так
   выглядит API, повторяющий одну и ту же страницу на любой `page=`, и
   молча считать 60 записей за 31 проверку значит вернуть ту же дыру
   с другой стороны. Разошлось — «статус неизвестен», то есть отказ merge
   (инвариант 19).

3. **Ответ без `total_count` остаётся допустимым — по длине страницы.**
   Настоящий GitHub счётчик отдаёт всегда, но требовать его — значит
   ужесточить контракт шире SPEC (там сверка идёт «с `total_count` ответа»)
   и покраснеть на фикстурах, которые счётчика не знают. Поэтому: счётчик
   есть — решает он; счётчика нет — последней считается страница короче
   запрошенного размера, то есть ровно поведение до T018, и опрос всё
   равно ограничен потолком страниц. Нечисловой счётчик (строка, `true`,
   отрицательное) — не «нет счётчика», а неразобранный ответ: отказ.

## Шаги

1. **Постраничный запрос** (требование 1). `ci.check_runs_page(sha, page)` —
   выделенный из прежнего `check_runs` разбор одного ответа: те же четыре
   отказа (`gh` не ответил, ответ не JSON, нет списка `check_runs`, элемент
   не объект), но возвращается весь payload, а не только список — счётчик
   нужен вызывающему. Запрос получает
   `?per_page={config.CI_CHECKS_PER_PAGE}&page={page}`: размер страницы
   задаётся явно (100 — потолок API), а не берётся из умолчания в 30.
   `ci.check_runs(sha)` становится циклом по страницам, накапливающим
   `runs`; интерфейс функции прежний, поэтому `branch_status` и `fsm`
   не меняются вовсе.

2. **Fail-closed на неполноте** (требование 2). `total_count` читается
   из первого ответа. Цикл идёт, пока набранное меньше обещанного и
   страницы приходят полными; после цикла — сверка `len(runs) != total`
   → `(None, "получено N проверок из M обещанных — список неполон")`,
   а `branch_status` превращает это в «статус CI коммита … неизвестен»,
   то есть отказ merge. Оборвавшаяся выдача (пустая или короткая страница
   раньше `total_count`) выходит на ту же сверку. Потолок опроса —
   `config.CI_CHECKS_MAX_PAGES` (20 страниц по 100): исчерпан, а ответ
   не сошёлся — снова «неизвестен», а не «сколько успели». Обе константы
   живут в `config.py` с обоснованием, как остальные лимиты.

3. **Инвариант 19** (требование 3). В `MergeNeedsGreenCiTest.NOT_GREEN`
   добавляется случай «проверок больше, чем в ответе»: `total_count: 31`
   при 30 зелёных записях — вход из ревью T017, на котором до T018 гейт
   мержил. Фикстура `GREEN_CI` получает `total_count: 3` (ответ GitHub
   счётчик содержит всегда — фикстура становится честнее). Полнота ответа
   как таковая разбирается новым `test_ci_status.PaginationTest`
   (10 тестов: обе страницы читаются, упавшая и идущая проверка со второй
   страницы видны, короткая/пустая/повторяющаяся страница и исчерпанный
   потолок — «неизвестен», ответ без счётчика читается по длине страницы,
   нечисловой счётчик — отказ, размер страницы задаётся запросом).
   Строка 19 в `docs/invariants.md` дополняется словом «неполный»
   и ссылками на новый тест и SPEC T018.

4. **Проверки**: `python3 -m unittest discover -s tests`,
   `python3 scripts/guard.py --all`, проверка мутацией по трём точкам
   правки (результаты — в разделе «Проверки»).

## Покрытие требований

## Влияние на систему

- **Зона изменения** — `orchestrator/ci.py` (функция `check_runs` и её
  новая половина `check_runs_page`), две константы в `orchestrator/config.py`,
  `tests/test_ci_status.py`, `tests/test_invariants.py`, строка 19
  в `docs/invariants.md`. Вызывающий код (`fsm.cmd_approve` через
  `ci.branch_status`) не меняется: сигнатура и семантика возвращаемого
  значения `check_runs` те же.

- **Защищённые пути в diff — и почему.** В `PROTECTED` job'а
  `protected-paths` попадают два файла: `tests/test_invariants.py`
  и `docs/invariants.md`. Оба — прямое требование SPEC 3 (расширение
  инварианта 19) и предписанная процедура самого документа («Как добавить
  инвариант», пп. 3–4). `gates.yaml`, `roles.yaml`, `.github/`,
  `templates/`, `skills/` не трогаются.

- **Ни одна защита не ослабляется.** По классам:
  - тесты — ни один не удалён, не заскипан и не смягчён; 316 → 326.
    В `test_invariants.py` правки две: **добавлен** случай в свип
    `NOT_GREEN` и в фикстуру `GREEN_CI` добавлено поле `total_count: 3`
    (ассерты и число зелёных проверок прежние). В `test_ci_status.py` —
    только новый класс, существующие `BranchStatusTest`, `HeadShaTest`,
    `GhCallTest` не тронуты и проходят на новом коде без правок;
  - гейты — merge-гейт становится строже ровно на один вход (неполный
    ответ), послаблений нет; ручных гейтов не убавилось;
  - лимиты — существующие не менялись; добавлены два новых
    (`CI_CHECKS_PER_PAGE`, `CI_CHECKS_MAX_PAGES`), и оба работают
    на отказ: упёрлись в потолок — «статус неизвестен»;
  - инварианты — 19 расширен, остальные 18 не тронуты.

- **Цена в вызовах `gh`.** Обычный коммит (3 проверки) — по-прежнему один
  вызов: первая же страница короче 100 и сходится с `total_count`. Второй
  и следующие запросы появляются только у коммита со 101+ проверкой,
  чего в этом репозитории нет. Предел ожидания `config.GH_TIMEOUT_SEC`
  действует на каждый вызов, то есть худшее время гейта в теории — 20 × 60 с;
  практически недостижимо (страницы обрываются раньше), но названо здесь
  честно как единственный побочный эффект пагинации.

- **Откат** — `git revert` одного merge-коммита: миграций, состояния
  и изменений формата артефактов нет.

## Риски

- **Поведение при отсутствии `total_count`.** Решение 3 «Подхода»: такой
  ответ читается по длине страницы, как до T018. Если Оператор считает,
  что ответ без счётчика сам по себе должен быть «статусом неизвестен»,
  это ужесточение на одну строку в `check_runs` — но оно шире SPEC,
  поэтому здесь не сделано.
- **`per_page=100` — потолок GitHub API.** Значение больше API молча
  урежет до 100; тогда полные страницы перестанут быть «полными» с точки
  зрения цикла, и ответ уйдёт в «неизвестен» — то есть в отказ, а не
  в ложное зелёное. Константа снабжена комментарием об этом.
