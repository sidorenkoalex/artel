# PLAN: guard называет маркер AC-n с отступом, а не глотает его

## Подход
`scripts/guard.py::AC_MARKER` заякорен на `^#` (начало строки) и уже
сегодня осознанно не матчит строки, где перед `#` есть что-то ещё — это
защита от R1-F2 (буквальный пример синтаксиса маркера внутри
комментария/докстринга). Проблема SPEC — другая крайность того же
якоря: строка с отступом (`    # AC-7: manual`) не матчится вообще
ничем и тихо теряется — ни ошибки, ни предупреждения.

Решение — отдельная регулярка `INDENTED_AC_MARKER` (`^[ \t]+#\s*AC-...`),
симметричная `AC_MARKER`, но требующая ненулевой отступ перед `#`.
Строка внутри строкового литерала/докстринга исключается через
`ast.parse` (`_string_literal_lines` — те же узлы `ast.Constant` со
строковым значением, что `module_docstring` уже использует для
докстринга модуля, только по всем строковым литералам файла, не только
первому). Файл с `SyntaxError` — `ast` не разбирает, множество строк
пустое, и тогда единственным критерием остаётся сама форма регулярки
(«строка начинается с отступа и `#`») — ровно тот запасной путь, что
явно разрешает требование 2 SPEC.

Новые функции (`indented_ac_marker_errors_from_files`/
`scan_indented_ac_markers`) построены по образцу уже существующей пары
`redness_marker_errors_from_files`/`scan_redness_markers` (SPEC T064):
ядро над уже прочитанными (label, текст) парами + обёртка над диском.

Интеграция в guard-выход (в рамках зоны `scripts/guard.py`, без правки
`orchestrator/`):
- `acceptance_traceability_errors(tdir)` (уже вызывается
  `orchestrator/fsm.py::_tests_writing_ac_state` на переходе
  `tests_writing -> in_dev` для рабочей копии) теперь добавляет
  `scan_indented_ac_markers(tdir)` к своему списку ошибок — переход
  блокируется без единой правки fsm.py.
- `main()` в режиме `--all` (в т.ч. с `--artifact-branch`, тем режимом,
  которым CI красит пуш `artifact/<id>` после `amend-tests`, коммитящего
  правку планки напрямую в артефактную ветку, минуя
  `tests_writing -> in_dev`) теперь сканирует `scan_indented_ac_markers`
  по каждому каталогу задачи как ошибку (не предупреждение,
  `DRAFT_LENIENT_TYPES` её не гасит — это не .md артефакт), тем же
  проходом, что уже собирает `sandbox_reuse_warnings`.

Ветка-based путь `_tests_writing_ac_state` (чужой чекаут, `gitcmd.
on_foreign_branch`) вызывает `guard.traceability_errors_from_content`
напрямую, не через `acceptance_traceability_errors` — эта функция не
видит сырые тексты файлов и не может сама просканировать индент без
правки сигнатуры (что потянуло бы правку fsm.py, вне зоны задачи).
Разобрано в «Риски» — покрыто только для типового случая (рабочая
копия на своей ветке) и для пост-коммита CI `--all`, не для этого
редкого fallback-пути.

## Шаги

1. `scripts/guard.py`: `INDENTED_AC_MARKER`, `_string_literal_lines`,
   `indented_ac_marker_errors_from_files`, `scan_indented_ac_markers`;
   подключение в `acceptance_traceability_errors` и в `main()` (`--all`).
2. `tests/test_acceptance_tests_flow.py`: новый класс
   `IndentedAcMarkerTest` — отступ отказан с номером строки (AC-3а),
   начало строки распознаётся как раньше (AC-3б), докстринг/строковый
   литерал не отказ (AC-3в); прогон существующих классов файла без
   правки их утверждений (AC-3г).

## Влияние на систему
Расширение затрагивает только новую детекцию — существующие регулярки
(`AC_MARKER`, `AC_ITEM`, `REDNESS_MARKER`) и их вызовы не тронуты,
`acceptance_traceability_errors` только ДОБАВЛЯЕТ ошибки к своему
прежнему списку (старые сценарии этой функции — `AcceptanceTraceability
FunctionTest` — не меняют поведение, что и подтверждает требование
3г/AC-3г прогоном без правки их утверждений). `main() --all` тоже
только расширяет список ошибок, не переопределяет прежние.

Гейт `tests_writing -> in_dev` — единственный сегодня гейт, до этой
правки МОЛЧА пропускавший отступленный маркер (то самое, что и
предписывает исправить SPEC); теперь он красный на таком дереве, как и
задумано. Обратной совместимости в опасном смысле нет: задача, у
которой в `acceptance_tests/test_*.py` реально лежит строка вида
`    # AC-n: manual`, сегодня в живых задачах не встречается (проверено
`grep -RnE '^[ \t]+#\s*AC-[0-9]+:\s*(manual|skip|escalate|ci)\b'
tasks/*/acceptance_tests/ 2>/dev/null` — пусто) — правило не роняет ни
одну текущую живую задачу.

Откат — правка изолирована новыми функциями и двумя точками подключения
(`acceptance_traceability_errors`, `main()`), git revert одним коммитом
безопасен.

## Риски
- Ветка-based fallback `_tests_writing_ac_state` (чужой чекаут рабочей
  копии) не получает новую проверку без правки `orchestrator/fsm.py`,
  которая вне зоны задачи (`zones: scripts/guard.py, tests/`) — та же
  причина, по которой этот путь не переиспользует
  `acceptance_traceability_errors` целиком уже сегодня (он передаёт guard
  уже извлечённые из git тексты, а не `tdir`). Для типового случая
  (рабочая копия на своей ветке, самый частый путь роли developer) и для
  постфактум-проверки CI (`--all` на артефактной ветке после
  `amend-tests`) правило действует. Если это расхождение критично —
  отдельная задача на `orchestrator/fsm.py` (добавить в
  `_tests_writing_ac_state` вызов нового ядра
  `indented_ac_marker_errors_from_files` над уже читаемыми git-текстами).

## Предложения системе
- `orchestrator/amend.py::_cmd_amend_tests`/`_cmd_amend_tests_from_branch`
  не вызывают `guard.acceptance_traceability_errors` вовсе (только
  `scan_redness_markers`, и только когда прогон не зелёный) — правка
  планки НЕ проверяет покрытие AC при самом коммите, только постфактум
  через CI `--all` артефактной ветки (эта задача добавила туда индент-
  проверку). Класс «amend-tests коммитит планку с дырой в трассируемости
  AC до следующего пуша CI» — кандидат отдельной задачи на
  `orchestrator/amend.py` (вне зоны этой).
