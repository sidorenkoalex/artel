# PLAN: Правила аналитика — матрица последствий в вопросах и проверяемое «Меняемое поведение» (ADR-0022 п.4)

## Подход

Две половины ТЗ пишут в `scripts/guard.py`; `orchestrator/fsm.py` только
зовёт новый разбор guard. Второй реализации разбора в `fsm.py` нет
(требование 7).

**Матрица QUESTIONS (требования 2–3).** `guard.questions_matrix_errors`
подключён в `_content_errors` для `type: questions` при наличии раздела
«Вопросы», без оглядки на `status`. Разбор `_questions_batch` проходит
строки раздела: `^(\d+)\.\s` без отступа — вопрос; `^\s*-\s+[A-Z]\)` —
вариант; `- <буква не ASCII>)` — чужая буква (отказ с номером вопроса,
и она же обрывает текущий вариант, чтобы её метки не ушли соседу);
`^\s*(?:-\s+)?дефолт:` — граница варианта; метка
`^\s*(?:-\s+)?(ломается|ослабляется|цена|чьё решение):` засчитывается
только открытому варианту. Отказы: нет ни одного вопроса; вопрос без
вариантов (номер); вариант без метки (номер и буква). Отказ guard на
`advance` из `spec_writing` уже оставляет задачу неэскалированной
(`fsm_advance.py` не меняется, AC-3 это подтверждает).

**Сверка «Меняемого поведения» на approve (требования 5–7).** В guard:
`method_literal_keys(source, path, name, modules)` — ключи
`_value_key` литералов `_literal_positions` по узлам `_assertion_records`
метода (сам метод + помощники первого уровня `_helper_calls`, в том
числе базовые классы из другого файла `tests/` и функции
`tests/sandbox.py` через `TestModules`). Это те же позиции, что сравнивает
гейт неослабления; докстринги и комментарии туда не попадают, потому что
это не утверждения. `behavior_change_refusals(item, literals)` проверяет
каждую пару по порядку: а) обе стороны — вызовы утверждений
(`_is_assertion`) разного вида (`_assertion_kind`) → причина с
`SIGN_OTHER_KIND` и обоими видами, «вопросом Оператору», без «нужен
литерал»; б) сторона не читается `literal_pair_keys` → «нужен литерал» с
адресом метода и фрагментом; в) сторона — list/tuple/set/frozenset/dict
→ «нужен скалярный литерал»; г) ключ «было» не среди литералов метода →
отказ с адресом и фрагментом. В `fsm._behavior_change_declaration` после
существующей сверки существования метода (то есть после ранних выходов
для канарейки и проектов не артели, требование 6) строится
`guard.TestModules` поверх `gitcmd.show(head, …)` той же головы main, и
отказы всех пар собираются в одну причину мягкого отказа (задача остаётся
в `spec_gate`, запись объявления не пишется).

**Фикстуры (требование 10).** Только данные: `base_two` получил
необязательные `first_was`/`second_was` — те же случайные «было»
кладутся в тела методов утверждениями `assertNotEqual(app.VALUE, <было>)`
(по умолчанию тела прежние, тесты ac3 не тронуты);
`undeclared_scenario` — `test_kept` получил
`self.assertGreaterEqual(app.VALUE, 1)` (одинаков на базе и в голове,
зелёный при VALUE ≥ 10, пара `1` → `2` отличается от фактической пары
`test_value`, `test_value` в разделе по-прежнему не назван, ветка «раздела
нет» сохранена). QUESTIONS-фикстуры `QUESTIONS_READY`,
`QUESTIONS_VALID`, `QUESTIONS_MD` (×2), `QUESTIONS_TEXT` (×2) переписаны
построчно с матрицей. Ни одно утверждение не менялось. Прочие фикстуры
QUESTIONS (`tests/test_answer_branch_reads.py`,
`tests/test_checkpoint_external_step_artifacts.py`, `tests/test_brief.py`,
`QUESTIONS_NO_SECTION`) guard в своих тестах не проходят — их тесты
зелёные без правки, они не тронуты.

**Защищённые пути** — приложениями ниже, `git apply --check` каждого
выполнен на чистом дереве HEAD ветки (см. «Шаги», 5). Пример строки
раздела в `templates/SPEC.md` оставлен с отступом (`  - `…), поэтому
`behavior_change_lines` его не считает строкой раздела;
`tests/test_guard_division_section.py` и
`tests/test_task_id_prefix_regression.py` прогнаны зелёными с наложенными
правками шаблонов.

Бюджет SPEC ($55) не пересматривается.

## Влияние на систему

- Гейт неослабления (`advance_gates/test_integrity.py`, `two_sided.py`),
  `fsm_advance.py` не меняются; новые функции guard только читают его
  разбор (`_assertion_records`, `_literal_positions`, `_value_key`,
  `literal_pair_keys`, `_is_assertion`, `_assertion_kind`) — их поведение
  не менялось.
- guard строже к QUESTIONS.md: батч без матрицы теперь отказывается (в
  том числе `draft`). Следствие, названное SPEC в «Не входит»: QUESTIONS.md
  живой задачи, оставшийся в ссылке документов, может покрасить гейт
  мержа — проверку живых задач делает Оператор перед мержем (решение А-4).
- approve гейта SPEC строже: строка «Меняемого поведения», которую гейт
  неослабления всё равно не засчитал бы, отказывается раньше. Отказ мягкий
  (как отказ по несуществующему методу).
- Сверка «было» опирается на чтение модулей помощников из головы main;
  непрочитанный модуль ведёт к отказу (fail-closed), не к проходу.
- Откат — revert merge-коммита; приложения к защищённым путям
  откатываются тем же revert.

## Риски

- Строка дефолта узнаётся без учёта регистра (`Дефолт:` тоже граница) —
  только строже требования 2; иное не затронуто.
- Строчная латинская буква варианта (`- a)`) не вариант и не ошибка —
  SPEC такую форму не называет; её метки уйдут предыдущему варианту.

## Предложения системе

- `skills/coding-standards.md`/миссия шага: в окружении роли нет `ls`/`cat`
  в PATH (`command not found`), а циклы `for … done` в Bash требуют
  подтверждения — разбор файлов пришлось делать `python3 -c`; стоит
  назвать это в миссии, чтобы роль не тратила шаги на пробы.
