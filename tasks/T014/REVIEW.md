# REVIEW: Команда auto — цикл до ближайшего гейта

## Фаза A: гейт плана

Аппрув плана.

1. **Покрытие полно.** Таблица PLAN перечисляет все 7 требований SPEC (1 —
   двумя строками, отдельно цикл и отдельно условия остановки); шага без
   требования и требования без шага нет.
2. **Шаги — единицы размера MR.** Три штуки: команда в оркестраторе, тестовый
   модуль, инвариант с записью в реестре. Каждый проверяем отдельно, ни один
   не «сделать всё».
3. **Подход не конфликтует с архитектурой.** Цикл вокруг `cmd_run`/`cmd_advance`
   без копирования их тел — единственный подход, при котором бюджет, ретраи и
   вердикты FSM не могут разойтись с ручным режимом. Условие выхода из
   `STATE_ROLE`, а не из копии списка состояний, — верное решение: новое
   агентское состояние подхватится, новое ручное остановит.

Проверил заявление PLAN про CI: `docs/invariants.md` действительно стоит в
`PROTECTED` (`.github/workflows/ci.yml:44`), и job `protected-paths` печатает
`::warning::` без `exit 1` — красным PR от этого не станет. Читал workflow,
потому что от этого зависит критерий приёмки 3 («CI зелёные»).

## Замечания

- **major — orchestrator/artel.py:143-144 — подсказка для `escalated` называет
  `approve`, хотя самая частая эскалация внутри цикла — исчерпанный потолок,
  и там нужна `budget`; Оператор, идущий по подсказке, делает два лишних хода
  и упирается в отказ.**

  Сценарий (воспроизвёл на песочнице, задача в `review`, потолок $25,
  потрачено $26 после шага):

  ```
  [T001] -> escalated  (бюджет исчерпан: $26.00 из $25.00)
    дальше: artel.py budget T001 <usd>  (или kill)      <- верная команда
  [T001] auto шаг 1/30: reviewer review -> escalated, лог: —
  [T001] auto остановлен: эскалация — нужен Оператор
    состояние: escalated
    дальше: разберись: artel.py log T001, затем artel.py approve T001
  ```

  Последняя строка — ровно тот итог, ради которого существует требование 2, —
  перекрывает верную подсказку `cmd_run`. Дальше по ней: `approve` вернёт
  задачу в `review` и напечатает «дальше: artel.py run», а `run` откажется
  («бюджет исчерпан: $26.00 из $25.00») — проверил, обе команды отрабатывают
  именно так. Денег это не жжёт, но это тот самый класс «Оператор выполнил не
  ту механическую команду», ради устранения которого задача и заведена.

  Асимметрия видна внутри самого `cmd_auto`: отказ `run` **до** шага получает
  правильную подсказку (artel.py:1202-1203, `budget`/`kill`), а эскалация по
  потолку **после** шага — нет.

  Предложение: подсказку для `escalated` выбирать по факту, а не по имени
  состояния — если `budget_block(get_task(conn, task_id))` не `None`, печатать
  `artel.py budget {id} <usd>  (или kill)`, иначе прежнюю строку про `log` и
  `approve`. Тест: остановка auto на эскалации по исчерпанному потолку называет
  `budget`, на эскалации после падения агента — `approve`. Остальные шесть
  строк `AUTO_STOP` (artel.py:134-149) я сверил с `cmd_advance` и `cmd_approve`
  — они называют верные команды, этот класс исчерпывается одной записью.

- **major — tasks/T014/PLAN.md:153-154 и tests/test_auto_cycle.py:344-348 —
  заявленная в «Проверке мутацией» защита лимита не существует: мутация
  проходит зелёной, а реальное удаление лимита вешает прогон вместо того,
  чтобы его уронить.**

  PLAN утверждает: «удвоенный `AUTO_MAX_STEPS` → `AutoStepLimitTest`
  (2 теста)». Проверил на копии дерева: заменил `AUTO_MAX_STEPS = 30` на
  `= 60` — `AutoStepLimitTest` зелёный (3 теста, OK), весь набор тоже.
  Причина в том, что оба утверждения читают саму константу
  (`assertEqual(len(self.agent.calls), artel.AUTO_MAX_STEPS)`,
  `assertIn(f"лимит {artel.AUTO_MAX_STEPS} шагов", out)`), поэтому подстроятся
  под любое её значение. Остальные три мутации из этого подраздела я тоже
  прогнал, и они честно красные: `cmd_approve` в теле цикла — 12 падений в
  `AutoNeverPassesAGateTest`; неперехваченный `SystemExit` — 3 ошибки в
  `AutoStopsOnBudgetRefusalTest`; убранное перечитывание состояния —
  падение `test_escalation_inside_the_step_stops_the_cycle_before_advance`.
  Ложное утверждение ровно одно, четвёртое.

  Хуже сама мутация, которую подраздел должен был закрыть. Удалил блок
  `if steps >= AUTO_MAX_STEPS` (artel.py:1186-1191) — `AutoStepLimitTest` не
  падает, а **зависает навсегда**: `FakeRun` состояние не двигает, выхода из
  цикла больше нет. Прогон пришлось снять по таймауту. В `ci.yml` у job
  `python` нет `timeout-minutes`, то есть такая правка не покраснит CI, а
  съест дефолтные 6 часов GitHub Actions; локально Оператор увидит зависший
  терминал, а не красный тест.

  Последствие: инвариант «у каждого цикла числовой лимит» (README 3, требование
  4 SPEC) на деле не пришпилен, но в PLAN записан как проверенный мутацией —
  а именно на этот раздел опирается следующий ревьювер, решая, можно ли трогать
  `cmd_auto`.

  Предложение: (а) дать `FakeRun` жёсткий потолок — после
  `artel.AUTO_MAX_STEPS` вызовов бросать `AssertionError("цикл не остановился
  на лимите")`, тогда удаление блока даёт быстрый красный тест вместо
  зависания; (б) привести строки 153-154 PLAN в соответствие с фактом —
  значение константы SPEC оставляет свободным («например, 30»), поэтому
  пришпиливать 30 не нужно, но и заявлять несуществующую проверку нельзя.
