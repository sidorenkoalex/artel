# SPEC: Ветко-корректные чтения статусов SPEC и REVIEW на переходах FSM

## Контекст

Переходы `spec_writing → spec_gate` и `review → acceptance/in_dev` в
`orchestrator/fsm.py` читают статус артефакта (`SPEC.md`, `REVIEW.md`) с
диска рабочей копии пульта, а не из ветки задачи, — класс «артефакто-чтения
ветко-зависимы» (T030), который T031 закрыл не для всех мест. Пока рабочее
дерево стояло на ветке задачи, дыра не стреляла; после закрепления главной
копии на main (T045) оба места стали блокерами, требующими ручного
чекаута Оператора на каждый переход. Инциденты: T046 27.08 (analyst
закоммитил `status: ready` в ветку, `advance` его не увидел, 15 холостых
шагов, ~$13) и T045 27.08 (`REVIEW.md status=None — жду вердикта» при
закоммиченном вердикте в ветке).

## Требования

1. Переход `spec_writing → spec_gate`: чтение статуса `SPEC.md` использует
   ветко-корректное чтение через примитивы `gitcmd` — при рабочем дереве
   пульта на чужой ветке (`gitcmd.on_foreign_branch`) статус читается из
   ВЕТКИ задачи (`git show`), иначе — прежний путь чтения с диска.
2. Переход `review → acceptance/in_dev`: чтение вердикта `REVIEW.md`
   (`status`, `iteration`) использует тот же принцип ветко-корректного
   чтения — из ветки задачи при чужом чекауте, иначе с диска.
3. Остальные читатели артефактов на переходах FSM (чтения `config.TASKS`
   в `orchestrator/fsm.py` и `orchestrator/artifacts.py`) проверены на
   принадлежность тому же классу «артефакто-чтения ветко-зависимы» —
   включая явно упомянутые: `fresh_verdict_iteration` и чтение
   `QUESTIONS.md` в состоянии `spec_writing`.
4. Каждый найденный по требованию 3 экземпляр того же класса закрыт в
   рамках этой задачи тем же принципом ветко-корректного чтения, а не
   отдельным вопросом на будущее («чини класс, не экземпляр»).
5. Поведение при отсутствии git или при отсутствии ветки задачи
   (песочницы без git, ранние состояния) не меняется — тот же паттерн
   деградации, что и в существующих ветко-корректных местах (T031,
   инвариант 28).
6. Инвариант 28 в `docs/invariants.md` дополнен перечислением новых мест
   ветко-корректного чтения, добавленных этой задачей.

## Критерии приёмки

AC-1. При рабочем дереве пульта на main и `SPEC.md` со статусом `ready`,
закоммиченным только в ветке задачи (не на диске main), `advance`
переводит переход `spec_writing → spec_gate` без ручного чекаута.

AC-2. При том же раскладе (рабочее дерево на main) с вердиктом
`REVIEW.md` (`status` и `iteration`), закоммиченным только в ветке
задачи, `advance` переводит переход `review → acceptance/in_dev` по
вердикту, без ручного чекаута.

AC-3. Прежнее поведение без git или без ветки задачи сохраняется —
существующие песочницы зелёные без правок сценариев.

AC-4. PLAN перечисляет все проверенные места чтений статусов/
фронтматтеров артефактов на переходах FSM и найденные экземпляры класса
«артефакто-чтения ветко-зависимы».

AC-5. Полный набор тестов зелёный.

AC-6. Инвариант 28 в `docs/invariants.md` дополнен новыми местами —
правка подготовлена как диф для Оператора (`docs/invariants.md` —
защищённый путь, как в T046), не закоммичена напрямую агентом.

## Не входит

- Механика фиксации артефактов (`orchestrator/fixation.py`) — не
  трогается.
- Гейт чистоты рабочей копии — не трогается.
- Брифы роли (`orchestrator/brief.py`) — уже ветко-корректны, не
  трогаются.
- Прямая правка `docs/invariants.md` в ветку задачи агентом — только
  подготовленный диф для Оператора.
- Ослабление или удаление существующих тестов, гейтов, лимитов,
  guard-проверок и инвариантов (принцип целостности, ADR-0002).
