## Замечания

- major — `tasks/T047/PLAN.md`, блок «Дифф для Оператора» (диф
  `docs/invariants.md`, хедер `@@ -52,7 +52,7 @@`) — счётчик строк в
  заголовке хунка неверен: реально изменяемый диапазон — 6 строк (3
  строки контекста + 1 удаление/добавление + 2 строки контекста после,
  проверено по факту — `| 25 |` в `docs/invariants.md` лежит на строке 52,
  `| 30 |` на строке 57, итого 6 строк, не 7). Воспроизвёл: вырезал блок
  диффа как есть и прогнал `git apply --check` против текущего
  `docs/invariants.md` на main — падает с `error: corrupt patch at line
  12`; `git apply --check --recount` (пересчитывающий хедер сам)
  проходит, то есть содержимое хантка корректно, а битый именно счётчик
  в `@@ ... @@`. AC-6 требует «правка подготовлена как диф для
  Оператора» — диф, который стандартный `git apply` отклоняет, не
  выполняет эту роль буквально (Оператору придётся либо руками
  поправить хедер, либо вспомнить `--recount`, либо накладывать через
  более снисходительный `patch -p1` — ни один из путей не описан и не
  гарантирован). Предложение: поправить хедер на `@@ -52,6 +52,6 @@`
  (или прогнать сам `git diff`/`git apply --recount` при подготовке диффа
  и вставить то, что реально проверено раскаткой) и приложить
  результат `git apply --check` в PLAN как доказательство applicability,
  тем же духом, что и остальная задача (доказывать, не полагаться на
  глаз).

- minor — `orchestrator/fsm.py:348-360` — `q_rel = f"tasks/{task_id}/QUESTIONS.md"`
  строится один раз для `ls_tree_files`, а `_read_branch_text_or_refuse`
  строит тот же путь заново внутри себя (`rel_name="QUESTIONS.md"` →
  `f"tasks/{task_id}/{rel_name}"`). Не дефект поведения, просто двойное
  вычисление одной и той же строки в соседних строках кода — не
  блокирует, отмечаю на будущее чтение кода.

## Предложения системе

- Класс «диф для Оператора в PLAN.md как код-блок» (прецедент T046,
  повтор в T047) не проверяется автоматически на applicability —
  доверие остаётся на глазомере автора. Стоит проверять `git apply
  --check` на diff-блок PLAN.md как часть шага «полный прогон» в PLAN
  всякий раз, когда задача готовит такой диф (или добавить это в скил
  conventions-core как явный шаг для защищённых путей), иначе класс
  дефекта («хедер хунка не совпадает с реальным диапазоном») будет
  повторяться при каждой подготовке диффа для Оператора.
