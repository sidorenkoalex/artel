# ТЗ: Ветко-корректные чтения статусов SPEC и REVIEW на переходах FSM

Ветко-корректные чтения статусов SPEC и REVIEW (срочная строка P3 27.08; вставка решением Оператора перед «ТЗ в ветке»).

Проблема: два перехода FSM читают статус артефакта из РАБОЧЕЙ КОПИИ пульта, а не из ветки задачи — класс «артефакто-чтения ветко-зависимы» (T030), который T031 закрыл не везде. Пока рабочее дерево стояло на ветке задачи, дыры не стреляли; worktree-норма (T045) закрепила главную копию на main — и оба места стали блокерами, требующими ручного чекаута Оператора на каждый переход:
- spec_writing → spec_gate: проверка «SPEC.md status: ready» читает config.TASKS/<id>/SPEC.md с диска — в main лежит шаблон-заглушка (draft); инцидент T046 27.08 — analyst закоммитил ready в ветку, advance его не видел, 15 холостых шагов (~$13);
- review → acceptance: чтение вердикта REVIEW.md (status/iteration) — тот же путь с диска; инцидент T045 27.08 («REVIEW.md status=None — жду вердикта» при закоммиченном вердикте в ветке), обход чекаутом.

Что сделать: оба чтения перевести на ветко-корректные примитивы gitcmd (T031, инвариант 28): при рабочем дереве на чужой ветке (gitcmd.on_foreign_branch) статус/фронтматтер читается из ВЕТКИ задачи (git show), иначе — прежний путь через диск (песочницы без git и ранние состояния не меняются — тот же паттерн, что в существующих местах инварианта 28). Заодно ПРОВЕРИТЬ остальные читатели артефактов на этот класс (grep по чтениям config.TASKS в переходах fsm/artifacts: например fresh_verdict_iteration, чтение QUESTIONS.md в spec_writing) — найденные экземпляры того же класса закрыть в этой же задаче («чини класс, не экземпляр»), с перечислением в PLAN.

Границы: только чтения статусов/фронтматтеров на переходах FSM; механику фиксации, гейт чистоты, брифы (уже ветко-корректны) не трогать; никакие защиты не ослабляются — наоборот, закрывается обход «переход не видит артефакт».

Критерии приёмки (ориентир): (1) при рабочем дереве на main и SPEC status: ready, закоммиченном только в ветке задачи, advance переводит spec_writing → spec_gate без чекаута; (2) при том же раскладе с вердиктом REVIEW (status+iteration в ветке) advance переводит review → acceptance/in_dev по вердикту; (3) прежнее поведение без git/без ветки сохраняется (существующие песочницы зелёные без правок сценариев); (4) PLAN перечисляет все проверенные места чтений и найденные экземпляры класса; (5) полный набор тестов зелёный; (6) инвариант 28 в docs/invariants.md дополнен новыми местами (правка docs/invariants.md — защищённый путь: подготовленным диффом для Оператора, как в T046).
