# SPEC: auto: детекция буксования цикла и алерты Оператору

## Контекст
Инциденты 02–03.09 (линт-до-лока — 19 шагов без перехода при
несостоявшейся эскалации роли; наблюдаемость — «ждём ответ» в текстах
коммитов; A7 — повторные отказы гейта ёмкости) не были видны никому до
конца цикла `auto` — Оператор узнавал о буксовании только из
собственных запросов статуса. Сверка кода подтверждает: поле `action`
записи журнала `fsm` («переход отклонён: ...») для всех трёх примеров
из ТЗ (гейт ёмкости diff — `fsm_advance.py:435/448`, лок приёмочных
тестов — `fsm_advance.py:510/522`, трассируемость AC — `fsm_advance.
py:372`) уже сегодня несёт стабильное имя класса, а меняющаяся деталь
(байты, sha) — в отдельном поле `detail`; существующий стоп-кран T038
(`auto._advance_refusal`/`_cmd_auto`) сравнивает именно `action`.
Требование 1 ниже фиксирует это тестами как регресс-гарантию (T038 не
ослабляется и не переписывается). Настоящий незакрытый разрыв — серии
шагов БЕЗ журналированного отказа вообще (агент «ещё работает») и без
единого механизма «остановка вне гейта = сигнал Оператору».

Батч вопросов (`QUESTIONS.md`) и ответ Оператора (`ANSWER-1.md`)
разрешили зоны и объём: алерт закрывается на ЛЮБОМ успешном переходе
задачи, кем бы он ни был вызван (мандат на расширение зон за пределы
исходных `orchestrator/auto.py`/`alerts.py`/`config.py` — на общую
точку перехода состояния, `orchestrator/store.py::set_state` либо
обработчики `orchestrator/fsm.py`/`orchestrator/fsm_advance.py`, выбор
разработчика); правило алерта — общее для каждой остановки `auto` не
на ручном гейте, кроме паузы; текст остановки по порогу холостых шагов
опускает хвост «, последний отказ: <класс>», когда классу неоткуда
взяться.

## Требования

1. Стоп-кран T038 (`auto.py`) останавливает цикл на втором подряд
   отказе `advance` без смены состояния задачи, если оба отказа
   принадлежат одному классу (совпадает поле `action` записи журнала
   `fsm`, начинающееся с «переход отклонён»), НЕЗАВИСИМО от отличий в
   поле `detail` (байты диффа, sha и т.п.). Два подряд отказа разных
   классов цикл по-прежнему не останавливают. Поведение для отказов,
   не журналируемых вовсе (агент ещё работает), и немедленная
   остановка на отказе `guard`'ом структуры артефакта — не меняются
   (SPEC T034/T038 без ослаблений).

2. Порог холостых шагов: N агентных шагов `run`+`advance` подряд, ни
   один из которых не сменил состояние задачи (в рамках одного вызова
   `auto`; смена состояния сбрасывает счётчик на 0), останавливают
   цикл. N — новая именованная константа `config.py`, значение по
   умолчанию 5. В серию засчитывается каждый такой шаг независимо от
   того, журналировал ли на нём `advance` отказ и с каким классом —
   в отличие от требования 1, здесь класс отказов на соседних шагах
   не обязан совпадать. Сообщение остановки — «цикл не сходится: N
   шагов без перехода, последний отказ: <класс>», где `<класс>` —
   `action` записи `fsm`, журналированной на последнем из N шагов;
   если на последнем из N шагов `advance` не журналировал отказ
   (агент ещё работал), хвост «, последний отказ: <класс>» опускается
   целиком — сообщение «цикл не сходится: N шагов без перехода».

3. Каждая остановка `auto`, случившаяся НЕ на ручном гейте (`spec_
   gate`, `acceptance`, `merge_gate` — состояния, уже показывающие
   «ЖДЁТ ОПЕРАТОРА» в `artel.py status`) и НЕ по штатной паузе
   Оператора, поднимает алерт `kind=attention` с id задачи и причиной
   остановки в тексте. Сюда входят все нижеперечисленные, буквальный
   список ТЗ — примеры, не потолок: переход в `escalated` (любая
   причина, включая исчерпанный бюджет), стоп-кран (требование 1),
   порог холостых шагов (требование 2), исчерпанный лимит
   `AUTO_MAX_STEPS`, красный CI в `verifying`, отказ `run` стартовать
   НЕ по причине паузы (бюджет до старта шага, лимит параллельных
   задач), структурный отказ `guard`'ом артефакта-условия. Остановка,
   на которой цикл не выполнил ни одного шага `run`+`advance` за этот
   вызов, потому что роли не было с самого начала (задача уже в `done`
   /`killed`, либо `spec_writing` без заведённого `TZ.md`) — алерт не
   поднимает: те же основания, что и у ручного гейта («ничего не
   требуется» — `config.AUTO_STOP`), ничего не буксовало, `auto`
   нечего было пытаться. Повторный прогон `auto`, застающий ту же
   незакрытую причину, не заводит дубликат алерта — переиспользуется
   существующий дедуп `alerts.raise_alert`.

4. Открытый алерт `kind=attention` этой задачи закрывается
   автоматически на следующем успешном переходе состояния задачи
   (`store.set_state` завершился), кем бы он ни был вызван — `auto`,
   ручной `advance`, `approve` или `reject` (мандат `ANSWER-1.md` на
   расширение зон, вариант B).

5. Тесты: стоп-кран требования 1 срабатывает на двух отказах одного
   класса с разными деталями и не срабатывает на разных классах; порог
   холостых требования 2 останавливает после N шагов и сбрасывается
   переходом; алерт требования 3 поднимается на каждой перечисленной
   причине остановки и не поднимается на ручном гейте/паузе/нулевом
   числе шагов; алерт требования 4 закрывается любым успешным
   переходом; существующие тесты (включая `tests/test_auto_cycle.py::
   AutoNeverPassesAGateTest` и стоп-кран T038) остаются зелёными без
   ослабления.

## Критерии приёмки

AC-1. Два подряд шага `auto` без смены состояния задачи, на обоих из
которых `advance` журналировал отказ с ОДИНАКОВЫМ `action` («переход
отклонён: ...»), но РАЗНЫМ `detail` (например, разный размер diff в
байтах на гейте ёмкости), останавливают цикл на втором из них — тем же
образом, что и буквально идентичный отказ.

AC-2. Два подряд отказа `advance` с разным `action` («переход
отклонён: ...») не останавливают цикл по стоп-крану требования 1.

AC-3. `config.py` несёт новую именованную константу порога холостых
шагов со значением по умолчанию 5.

AC-4. N (значение константы AC-3) шагов `run`+`advance` подряд внутри
одного вызова `auto`, ни один из которых не сменил состояние задачи —
независимо от того, журналировал ли `advance` отказ на каждом из них
и какого класса, — останавливают цикл с сообщением «цикл не сходится:
N шагов без перехода, последний отказ: <класс>», где `<класс>` —
`action` записи, журналированной на последнем из N шагов.

AC-5. Когда на последнем из N шагов `advance` не журналировал отказ
(агент ещё работал), сообщение остановки требования 2 — «цикл не
сходится: N шагов без перехода», без хвоста «, последний отказ:
<класс>».

AC-6. Успешная смена состояния задачи сбрасывает счётчик холостых
шагов требования 2 на 0 (в т.ч. если смена случилась раньше, чем
накопилось N шагов).

AC-7. Остановка `auto` переходом задачи в `escalated` (любой причины,
включая исчерпанный бюджет) поднимает алерт `kind=attention` с id
задачи и причиной остановки в тексте.

AC-8. Остановка `auto` стоп-краном требования 1 поднимает алерт
`kind=attention` с id задачи и причиной.

AC-9. Остановка `auto` порогом холостых шагов требования 2 поднимает
алерт `kind=attention` с id задачи и причиной.

AC-10. Остановка `auto` исчерпанным лимитом `AUTO_MAX_STEPS` поднимает
алерт `kind=attention` с id задачи и причиной.

AC-11. Остановка `auto` красным CI в `verifying` поднимает алерт
`kind=attention` с id задачи и причиной.

AC-12. Остановка `auto` отказом `run` стартовать НЕ по причине паузы
(в т.ч. исчерпанный бюджет до старта шага, лимит параллельных задач)
поднимает алерт `kind=attention` с id задачи и причиной.

AC-13. Остановка `auto` структурным отказом `guard`'ом
артефакта-условия поднимает алерт `kind=attention` с id задачи и
причиной.

AC-14. Остановка `auto` на ручном гейте (`spec_gate`, `acceptance`,
`merge_gate`) НЕ поднимает алерт.

AC-15. Остановка `auto` штатной паузой Оператора НЕ поднимает алерт.

AC-16. Вызов `auto`, не выполнивший ни одного шага `run`+`advance`
за этот вызов, потому что роли не было с самого начала (задача уже
в `done`/`killed`, либо в `spec_writing` без заведённого `TZ.md`), НЕ
поднимает алерт.

AC-17. Повторный вызов `auto`, останавливающийся по той же
незакрытой причине (тот же `target`/`kind`/`source`/`message`), не
заводит дубликат алерта — открытый алерт остаётся один (существующий
дедуп `alerts.raise_alert`).

AC-18. Открытый алерт `kind=attention` задачи закрывается
автоматически на следующем успешном переходе состояния этой задачи,
инициированном `auto` (`run`+`advance` внутри цикла).

AC-19. Открытый алерт `kind=attention` задачи закрывается
автоматически на следующем успешном переходе состояния этой задачи,
инициированном ручной командой Оператора — `artel.py advance`,
`approve` или `reject` — вне цикла `auto`.

AC-20. Существующий набор тестов (включая
`tests/test_auto_cycle.py::AutoNeverPassesAGateTest` и тесты
стоп-крана T038) остаётся зелёным без ослабления, удаления или
смягчения проверок.

## Не входит
- Доставка уведомлений на рабочий стол/телефон — отдельное решение
  Оператора (граница ТЗ).
- Изменение лимита 30 шагов (`config.AUTO_MAX_STEPS`), его значения,
  комментария или механики ручных гейтов (docs/invariants.md 18) —
  не трогается этой задачей.
- Watchdog мёртвых процессов (tasks/T084).
- Изменение `alerts.raise_alert`, дедупликации, ручного `ack` или
  авто-ack паттерна T035/T054/T088 (существующие источники `doctor.py`)
  — принцип целостности; единственное изменение `alerts.py` в объёме
  этой задачи — добавление `"attention"` в кортеж `KINDS` и точки
  заведения/авто-закрытия алерта этого вида.
- Переписывание существующих текстов «переход отклонён: ...» в
  `fsm.py`/`fsm_advance.py` или архитектуры «`action` — класс, `detail`
  — переменная часть» — она уже верна, требование 1 её не меняет, а
  фиксирует тестами.
- Новые промежуточные состояния FSM — эта задача не добавляет ни
  одного, счётчики требований 1–2 живут внутри существующих переходов.
