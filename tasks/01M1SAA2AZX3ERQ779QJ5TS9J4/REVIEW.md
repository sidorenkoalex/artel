## Замечания

- major — `tests/test_brief.py:373,388,400,425,433` (класс
  `ReturnReasonComponentTest`, все 5 новых тестовых методов) — ни один
  метод не несёт докстринга вовсе (только докстринг класса), в
  частности отсутствует обязательная по конвенции репозитория заявка
  `Ловит мутацию: …` (skills/test-authoring.md, п. «Чувствительность»;
  review-checklist п.3 требует её для КАЖДОГО нового/изменённого
  теста). Конвенция не специфична для `acceptance_tests/` — она
  систематически соблюдается в остальных развиточных юнит-тестах
  репозитория (например `tests/test_acceptance.py:93`,
  `tests/test_branch_freshness_gate.py:298`, `tests/test_amend.py:48`
  и далее). Без заявленной мутации ревьювер не может сверить, что тест
  действительно ловит правдоподобную поломку (а не тавтологичен) —
  сейчас это приходится восстанавливать реверс-инжинирингом кода, что
  и проделано в этом ревью вручную, но со следующей итерацией
  добавьте `Ловит мутацию: …` в докстринг каждого из 5 методов
  (например для `test_developer_brief_unchanged_after_normal_advance_from_tests_writing`
  — «предшественник `tests_writing` по ошибке добавлен в
  `_RETURN_TRIGGER_STATES`» и т.п., под конкретный сценарий метода).

- minor — `orchestrator/brief.py:817-818`
  (`test_author_answer_component`) — `return_reason_part` и `part`
  склеены напрямую (`f"{return_reason_part}{part}"`), без разделителя:
  между закрывающим маркером границы раздела «Причина возврата» и
  следующим заголовком `### tasks/<id>/ANSWER-n.md` остаётся только
  один перевод строки, тогда как `developer_brief`/`analyst_map_component`
  идут через `context_package.discipline(...)`/список `parts`, где
  между компонентами получается пустая строка (компонент сам
  заканчивается на `\n`, соединение добавляет ещё один). Чисто
  косметическое расхождение (проверил рантаймом — секции остаются
  корректно читаемыми, граница не разорвана), не мешает ни одному AC;
  для единообразия стоило бы вставить `\n` между `return_reason_part` и
  `part`.

## Предложения системе

- Формулировка требования 1 SPEC перечисляет ровно 3 класса возврата
  (`review->in_dev`, `reject` из acceptance/verifying/merge_gate,
  возврат из `escalated`), но выбранный (и правильный, судя по
  «Подходу» PLAN) механизм детектирования «по предшествующему
  состоянию» сам по себе шире буквы требования — он поймает и
  `merge_gate -> in_dev` по автоматическому конфликту merge
  (`fsm_merge_gate.py:125`), не входящий в перечисление. Для будущих
  задач того же класса («раздел брифа по предшественнику состояния»)
  стоит явно указывать в SPEC, что механизм триггерится ЛЮБЫМ входом
  из состояния-предшественника, а не только перечисленными случаями —
  чтобы это расхождение не всплывало каждый раз как вопрос ревьювера.
