# SPEC: бриф роли после возврата цитирует причину возврата первым пунктом

## Контекст
Трижды за день 05.09 (стек ч.3 — красный CI на раннере; регрессия №13 —
красная планка родительской задачи; канарейка ч.2 — утечка изоляции
тестов) developer после `reject` с подробной причиной отвечал «менять
нечего»: причина возврата уже лежит в журнале (`detail` записи
`state -> in_dev`), но бриф её не несёт или несёт неявно. Двигали задачу
только `ANSWER-n` Оператора — лишние $2 и итерация на каждый случай
(`docs/backlog.md`, строка «Причина reject/отклонённой приёмки не
доходит до роли»).

`orchestrator/brief.py` уже журналирует и включает в бриф разработчика
`PLAN.md`/`REVIEW.md`/последний `ANSWER-n.md` (SPEC
01M1NKTF173WV5CPDZ1C3WW69K, SPEC T075); задача — добавить явный
опережающий раздел, который цитирует причину возврата ПЕРВЫМ пунктом,
вместо того чтобы роль искала её сама по остальным компонентам.

## Требования

1. Бриф роли (`developer_brief`, `analyst_map_component`,
   `test_author_answer_component` — три сборщика `orchestrator/brief.py`,
   формирующие вход агента), чей текущий визит состояния начался
   возвратом с основанием, открывается разделом «Причина возврата»:
   - `review -> in_dev` по вердикту `changes_requested`;
   - `reject` Оператора из `acceptance`, `verifying` или `merge_gate`
     (во всех трёх случаях ведёт в `in_dev`);
   - возврат из `escalated` по `approve` Оператора (в `in_dev`,
     `spec_writing` или `tests_writing`, смотря откуда эскалировали).
2. Раздел несёт дословный текст поля `detail` последней записи журнала
   `state -> <текущее состояние>` данной задачи, относящейся к этому
   визиту — кроме возврата из `escalated`: там `detail` записи
   `state -> <состояние>`, которую пишет `approve`, — фиксированная фраза
   без содержательной причины, поэтому раздел вместо неё несёт дословный
   `detail` записи `state -> escalated`, которой задача вошла в этот
   цикл эскалации, и ссылку на `tasks/<id>/ANSWER-n.md` с наибольшим `n`
   (файл, который бриф уже включает отдельным компонентом, — раздел
   только указывает на него).
3. Раздел стоит до компонентов SPEC.md/PLAN.md/REVIEW.md/карты в брифе.
4. Раздел заканчивается текстом: «шаг без правки, закрывающей причину,
   не засчитывается».
5. Для визита состояния, не начавшегося возвратом (первый заход или
   обычный advance из штатного предшествующего состояния), раздел
   отсутствует — бриф не меняется относительно текущего поведения.

## Критерии приёмки

AC-1. Бриф роли (`developer_brief`/`analyst_map_component`/
`test_author_answer_component`), чей текущий визит состояния начался
возвратом — `review -> in_dev` по `changes_requested`, `reject` из
`acceptance`/`verifying`/`merge_gate`, либо возврат из `escalated` по
`approve` — открывается разделом «Причина возврата».

AC-2. Раздел «Причина возврата» несёт дословный текст поля `detail`
последней записи журнала `state -> <текущее состояние>` данной задачи —
для `review -> in_dev` и для `reject` из `acceptance`/`verifying`/
`merge_gate`.

AC-3. Для возврата из `escalated` по `approve` раздел «Причина возврата»
несёт дословный `detail` записи журнала `state -> escalated`, которой
задача вошла в этот цикл эскалации, и явную ссылку на файл
`tasks/<id>/ANSWER-n.md` с наибольшим `n`.

AC-4. Раздел «Причина возврата» расположен до текста SPEC.md/PLAN.md/
REVIEW.md/карты кодовой базы в брифе.

AC-5. Раздел «Причина возврата» заканчивается текстом «шаг без правки,
закрывающей причину, не засчитывается».

AC-6. Для визита состояния, не начавшегося возвратом (первый визит
состояния или обычный advance из штатного предшествующего состояния),
раздел «Причина возврата» отсутствует, остальной текст брифа не
меняется относительно текущего поведения.

AC-7. Бриф developer после `review -> in_dev` содержит текст замечаний
ревью (компонент REVIEW.md остаётся частью брифа, как и до этой задачи).

AC-8. Бриф developer после `reject` из `verifying` с причиной, называющей
упавшие тесты, несёт имена этих тестов дословно в разделе «Причина
возврата» (раздел передаёт текст `detail` как есть, без произвольного
изменения).

AC-9. Существующие тесты `tests/test_brief.py` и других файлов,
зависящих от собранного текста брифа, остаются зелёными.

## Не входит

- Изменение формата журнала: состав колонок `steps`, сигнатуры
  `store.journal`/`store.set_state` не меняются.
- Новые состояния FSM.
- Правка диспетчеров FSM (`fsm`, `fsm_advance`, `fsm_merge_gate` —
  модули пакета `orchestrator`) — раздел строится ЧТЕНИЕМ уже
  существующих записей журнала и артефактов, без изменения того, что и
  как они пишут, и без изменения текста уже журналируемых
  `detail`-сообщений.
- Ревьюер (роль `reviewer`): её вход собирает ревью-пакет модуля
  `review` пакета `orchestrator`, не `brief` — вне зоны задачи, раздел
  «Причина возврата» этого пакета не касается.
- Запрос состояния CI заново (`orchestrator/ci.py`) ради списка красных
  джобов — раздел цитирует уже записанный в журнал текст, не обращается
  к GitHub повторно.
- Разбор `detail` на структурированные поля — раздел передаёт текст как
  есть, без интерпретации содержимого.
