# SPEC: занятость зоны — только по старту developer (регрессия 01M1REVJ8AJ)

## Контекст

После мержа 01M1REVJ8AJDKAMK5VTKES5J6D (коммит d617c148, в пине с
10:57Z) `zone_lock._occupies` считает задачу занимающей зоны, если
после границы текущего пребывания (`"state -> tests_writing"`) в
журнале есть любая запись `"agent run started"` — без сверки актора.
Прогон роли test_author в `tests_writing` тоже журналирует
`"agent run started"` (та же точка `runner.run_agent_once`, актор —
имя роли), поэтому КАЖДАЯ задача с зафиксированной приёмочной планкой
«занимает» свои зоны ещё до первого шага developer, а занимающая
задача по `blocking_conflict` никогда не блокируется. Итог: механика
зон (SPEC 01M1REVJ8AJDKAMK5VTKES5J6D, требование 1) фактически
выключена для всех задач, дошедших до `tests_writing`. Факт по журналу
05.09: у 01M1RFVWV6 и 01M1R5B33C (общие зоны `orchestrator/doctor.py`,
`orchestrator/fsm_postmerge.py`) developer не стартовал ни у одной,
`_occupies` — `True` у обеих, `blocking_conflict` — `None` у обеих.
Класс дефекта — частичная поломка запущенной версии (ADR-0013 п.2:
исправляется hotfix конвейером, не аварийный режим).

## Требования

1. `zone_lock._occupies` (через `_visit_has_action` либо отдельную
   проверку) считает признаком занятости запись `"agent run started"`
   только с актором `developer`, после границы пребывания
   (`_stay_since_id`). Записи того же действия с актором analyst,
   test_author или reviewer признаком занятости не являются.
   `RELEASE_ACTION` остаётся признаком занятости независимо от актора
   записи — фильтр по роли `developer` требования 1 применяется только
   к `"agent run started"`.
2. Семантика SPEC 01M1REVJ8AJDKAMK5VTKES5J6D не меняется: ждущая зону
   задача зон не держит (ни для себя, ни как кандидат для соседей),
   владелец остаётся владельцем до `done`/`killed`, возврат из ревью
   (`review -> in_dev`) не сдвигает границу пребывания и не требует
   повторного старта developer. Меняется только фильтр роли в проверке
   признака занятости.
3. Копилка/скил (необязательно, приложением к PLAN.md, защищённый
   путь `skills/` не трогать напрямую — только unified-диф для
   Оператора): класс дефекта «маркер журнала без сверки роли» — строка
   в `skills/test-authoring.md` про фикстуры журнала с чужими ролями в
   том же пребывании, если разработчик сочтёт нужным.

## Критерии приёмки

AC-1. Задача, в чьём журнале после границы текущего пребывания
(последняя запись `"state -> tests_writing"`) есть запись
`"agent run started"` с актором, отличным от `developer` (например
`test_author`), но нет ни одной записи `"agent run started"` с актором
`developer` и нет `RELEASE_ACTION`, — `zone_lock._occupies` для неё
возвращает `False`.

AC-2. Задача из AC-1, выступая кандидатом в цикле `blocking_conflict`
для соседней задачи с пересекающейся зоной в `in_dev`, не блокирует
первый шаг соседа: `blocking_conflict`/`refusal` соседа возвращают
`None` — в отличие от текущего дефектного поведения, где такой сосед
ложно считается занявшим зону.

AC-3. Задача, в чьём журнале после границы пребывания есть запись
`"agent run started"` с актором `developer`, по-прежнему считается
занимающей зону: `_occupies` возвращает `True`, и она по-прежнему
блокирует первый шаг соседа с пересекающейся зоной через
`blocking_conflict`/`refusal`.

AC-4. Задача, в чьём журнале после границы пребывания есть запись
`zone_lock.RELEASE_ACTION`, по-прежнему считается занимающей зону
независимо от актора этой записи.

AC-5. `refusal` для соседа, заблокированного реальным владельцем
(актор `developer` либо `RELEASE_ACTION`), по-прежнему называет путь,
id и состояние владельца — форма сообщения не меняется, меняется
только состав кандидатов, которых учитывает фильтр занятости.

AC-6. `tests/test_zone_lock.py` и `tests/test_zones_gate.py` в
текущем виде — без правки существующих ассертов — остаются зелёными
после фикса.

AC-7. Новый тест воспроизводит регрессию буквально (принцип «тест
обязан ловить заявленную мутацию»): задача проходит границу
пребывания (журналируется `"state -> tests_writing"`), в ТОМ ЖЕ
пребывании журналируется `"agent run started"` с актором `test_author`
(симулирует реальный прогон роли test_author на стадии
`tests_writing`), запись `"agent run started"` с актором `developer`
не журналируется вовсе; сосед с пересекающейся зоной в `in_dev` НЕ
блокируется этой задачей. Без фикса (проверка признака занятости без
сверки актора) `_occupies` вернула бы `True` и тест падал бы —
песочница фиксирует именно ту синтетику, что пропустила дефект в
планке 01M1REVJ8AJ.

## Не входит

- Очередь ожидания зоны и её порядок (`queue_order`, `queue_position`,
  `cmd_zone_reorder`) — не трогается.
- Зоны внешних target — отдельная задача, здесь не расширяется.
- Изменение границы текущего пребывания (`"state -> tests_writing"`,
  `_stay_since_id`) — граница остаётся прежней, меняется только
  проверка признака занятости внутри неё.
