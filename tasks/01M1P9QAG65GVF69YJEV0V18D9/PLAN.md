# PLAN: Механика зон, часть 2 — занятость зоны на старте кода

## Подход
Занятость — не новое состояние FSM (SPEC требование 1, инварианты 1/18/32),
а предусловие/отказ перед стартом первого шага роли developer, по образцу
`budget.budget_block`/`parallel_limit.refusal`. Вся механика собрана в
новом модуле `orchestrator/zone_lock.py`:

- `blocking_conflict(conn, task_id, t)` — читает `t["zones"]` (часть 1) и
  зоны всех задач в диапазоне состояний `BLOCKING_STATES = ("in_dev",
  "review", "verifying", "acceptance", "merge_gate")`; пересечение вне
  `config.COMMON_ZONES` (часть 1) — конфликт. Единая точка вычисления —
  используется и отказом (`runner`), и наблюдаемостью (`catalog`,
  `doctor`), без дублирования логики.
- «Первый шаг» (SPEC требование 1) — граница читается тем же приёмом,
  что `store.refusal_history`: id записи `"state -> in_dev"` журнала
  задачи как начало текущего визита состояния; если после этой границы
  уже есть запись `"agent run started"` (её пишет `runner.
  run_agent_once`) или запись явного снятия Оператором (`RELEASE_ACTION`)
  — конфликт для этого визита больше не действует.
- `refusal(conn, task_id, t)` — именованный текст отказа («зона <путь>
  занята задачей <id> (<состояние>)», требование 2, AC-2).
- `runner._cmd_run` вызывает `zone_lock.refusal` для роли `developer`
  (что эквивалентно состоянию `in_dev` — `config.STATE_ROLE`) до спавна
  агента, журналирует отказ действием `zone_lock.REFUSAL_ACTION` и
  завершает `sys.exit` — тем же путём, что бюджет/лимит параллельных
  задач.
- `auto._cmd_auto` отличает эту причину остановки цикла по записи
  `zone_lock.REFUSAL_ACTION` в журнале (`_run_zone_wait_refusal`, тот же
  приём, что `_run_paused_refusal`) и останавливается с
  `config.AUTO_STOP_ZONE_WAIT` БЕЗ алерта буксования (требование 3,
  AC-4).
- `catalog.cmd_status` и `doctor.check_zone_waits` показывают ожидание и
  держателя зоны, используя `zone_lock.blocking_conflict` (требование 4,
  AC-5) — не отдельная копия проверки.
- Снятие по мержу/kill (требование 5, AC-6) не требует отдельного кода:
  как только держатель покидает `BLOCKING_STATES` (переходит в `done`
  или удаляется/`killed` при `kill`), `blocking_conflict` перестаёт
  находить пересечение при следующем вызове `run`/`auto`.
- Явное снятие Оператором (требование 6, AC-7) — `zone_lock.
  cmd_zone_release`, новая CLI-команда `artel.py zone-release <id>`:
  журналирует `RELEASE_ACTION` («ждёт зоны — снято Оператором (осознанный
  риск)») — маркер того же семейства «визит больше не в режиме
  ожидания», что и «agent run started».
- Очередь (требования 7-9, AC-8/AC-9) — чистая функция `zone_lock.
  queue_order`: сортировка по возрастанию `tasks.updated_at` (естественная
  метка approve — задача в `in_dev` попадает туда сразу за approve SPEC,
  `updated_at` этого перехода и есть момент approve), либо по
  колонке `tasks.zone_queue_position` (новая, `INTEGER NULL`), если
  Оператор явно переставил порядок командой `artel.py zone-reorder <id1>
  <id2> ...` → `zone_lock.cmd_zone_reorder`.
- Зоны — механика только основного (dogfood) target'а: `blocking_conflict`
  игнорирует задачи не-`config.DEFAULT_TARGET` (SPEC, «Не входит»).

Часть работы (весь модуль `zone_lock.py` и точки интеграции в
`runner.py`/`auto.py`/`catalog.py`/`doctor.py`/`config.py`/`store.py`/
`artel.py`) уже реализована предыдущим шагом developer, прерванным
таймаутом (WIP-чекпоинт 688e3ff1). Этот шаг — проверка того, что
реализация покрывает все AC приёмочных тестов (18/18 зелёных), полный
прогон `tests/` на регрессию (AC-10) и юнит-тесты на сам `zone_lock.py`.

## Влияние на систему
Новый модуль `orchestrator/zone_lock.py` без внешних сайд-эффектов, кроме
чтения `store`/`config`; интеграция — в 6 существующих модулей
(`runner.py`, `auto.py`, `catalog.py`, `doctor.py`, `config.py`,
`store.py`) и CLI-диспетчер `artel.py`, каждая точка — добавка (новая
ветка проверки/новая команда), ни одна существующая ветка кода не
изменена и не удалена. Новая колонка БД `tasks.zone_queue_position`
(`INTEGER NULL`, добавлена идемпотентно через `store.add_column` —
инвариант неразрушающих миграций уже используемый для `zones`/
`materialized_artifact_sha`) — обратно совместима, `NULL` не меняет
поведение для задач, заведённых до этой миграции.

Новое состояние FSM не добавляется (инварианты 1, 18, 32 не затронуты) —
занятость зоны реализована как предусловие перед стартом шага, тем же
классом решения, что `budget.budget_block`/`parallel_limit.refusal`,
которые уже прошли этот же тест на целостность. `auto` не открывает
алерт буксования на этой причине остановки (требование 3) — согласовано
с наблюдаемостью через `status`/`doctor` (требование 4): пользователь
Оператора видит причину явно, а не как неотличимое от реального
буксования зависание.

Существующие тесты, гейты, лимиты и guard-проверки не ослаблены и не
отключены — только дополнены новой точечной проверкой `doctor.
check_zone_waits`, включённой в `doctor.all_checks`.

Откат: `git revert` коммитов этой задачи полностью убирает модуль
`zone_lock.py` и все точки интеграции; колонка `zone_queue_position`
остаётся в схеме БД неиспользуемой (безопасно — `store.add_column`
идемпотентен, конфликта миграций при повторном добавлении нет).

## Риски
- Определение «первого шага» через журнал (id записи `"state ->
  in_dev"` + позднейшая `"agent run started"`) завязано на то, что
  `store.set_state` пишет маркер перехода на КАЖДОМ переходе состояния —
  инвариант, уже используемый `store.refusal_history`/`brief.
  advance_refusal_history` (SPEC T078); если этот инвариант когда-либо
  нарушится, `zone_lock` деградирует к «блокирует один и тот же визит
  `in_dev` всегда», не силенцирует проверку молча.
- Прямая синтетика песочниц, заводящая задачи `UPDATE tasks` в обход
  `set_state` (без маркера `"state -> in_dev"`), не отличается от
  «первого шага» в терминах этой проверки, что задокументировано и
  единообразно для одного непрерывного тестового сценария (докстринг
  `zone_lock.py`, абзац 3).
