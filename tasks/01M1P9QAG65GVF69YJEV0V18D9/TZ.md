# ТЗ: механика зон, часть 2 — занятость зоны на старте кода

Родитель: 01M1NKVPD2A79PQ6K0JVV1B2Q1 «Механика зон» (SPEC на гейте
04.09: решение о делении на три части; эта — часть 2). Источник
требований — ТЗ родителя, требования 3 и 5. Зависит от части 1
(поле `zones:` в SPEC, хранение в БД, общий список зон в
`orchestrator/config.py`); старт кода — после её мержа, до мержа —
только SPEC.

Требуется:
1. Перед первым шагом роли developer (состояние `in_dev`) зоны задачи
   сверяются с зонами всех задач в кодовой фазе (`in_dev` …
   `merge_gate`). Пересечение вне общего списка — именованный отказ
   «зона <путь> занята задачей <id> (<состояние>)»; шаг developer не
   запускается. Реализация — отказ/предусловие по образцу
   `budget_block`/`parallel_limit.refusal`, не новое состояние FSM
   (инварианты 1, 18, 32).
2. `auto` останавливается с причиной «ждёт зоны» и не открывает алерт
   буксования; `status` и `doctor` показывают ожидание зоны.
3. После мержа (`merge_gate` → done) или `kill` занявшей задачи
   следующий `auto`/`run` заблокированной задачи проходит.
4. Оператор может снять ожидание явной командой; снятие пишется в
   журнал задачи как осознанный риск.
5. Очередь заблокированных задач на зону упорядочена по времени
   `approve` их SPEC; Оператор может переставить порядок командой.
6. Тесты: отказ старта developer при пересечении и проход после
   мержа/убийства занявшей; общие зоны не конфликтуют; «ждёт зоны»
   без алерта буксования; снятие ожидания журналируется; порядок
   очереди; существующий набор `tests/` зелёный без ослабления.

Зоны: orchestrator/auto.py, orchestrator/fsm_advance.py (старт
in_dev), orchestrator/doctor.py, orchestrator/catalog.py
(status), orchestrator/artel.py (команды снятия ожидания и
перестановки очереди), tests/.

Не входит: сверка диффа с зонами при переходе в review (часть 3);
автоматическое переупорядочивание очереди; зоны внешних target.
