# SPEC: Механика зон, часть 2: занятость зоны на старте кода

## Контекст
Родитель 01M1NKVPD2A79PQ6K0JVV1B2Q1 «Механика зон» на гейте SPEC
04.09.2026 разделён Оператором на 3 части (SPEC родителя сужен до
части 1, коммит 630f00d7); эта задача — часть 2 (требования 3 и 5
родительского ТЗ): проверка занятости зоны перед первым шагом
developer, наблюдаемость ожидания, снятие ожидания и порядок очереди.
Часть 1 вводит машиночитаемое поле `zones` во frontmatter SPEC, его
сохранение в БД при `approve` и общий список зон вне конфликта в
`orchestrator/config.py` — эта задача только читает эти данные; старт
кода — после мержа части 1, до мержа этой задачи есть только SPEC
(явное условие ТЗ).

## Требования
1. Перед первым шагом роли developer (состояние `in_dev`) зоны
   текущей задачи сверяются с зонами всех задач, находящихся в фазах
   `in_dev` … `merge_gate`; пересечение вне общего списка зон (часть 1)
   даёт именованный отказ «зона <путь> занята задачей <id>
   (<состояние>)», и сам шаг не запускается. Реализация — предусловие/
   отказ перед стартом шага, по образцу `orchestrator/budget.
   budget_block`/`orchestrator/parallel_limit.refusal`; новое
   состояние FSM не добавляется (инварианты 1, 18, 32 —
   docs/invariants.md).
2. Пересечение по путям из общего списка зон (часть 1) не считается
   конфликтом при этой проверке.
3. При отказе по пересечению `orchestrator/auto.py` останавливает
   цикл `auto` с причиной «ждёт зоны» и не открывает алерт буксования.
4. `orchestrator/catalog.py` (`status`) и `orchestrator/doctor.py`
   показывают для заблокированной задачи ожидание зоны и занявшую её
   задачу.
5. Когда занявшая зону задача переходит `merge_gate → done` (мерж)
   или её убивают (`kill`), следующий `run`/`auto` заблокированной
   задачи проходит без отказа по пересечению зон.
6. Оператор может снять ожидание зоны явной командой
   (`orchestrator/artel.py`); снятие пишется в журнал задачи
   (`store.journal`) как осознанный риск.
7. Очередь задач, заблокированных пересечением одной и той же зоны,
   упорядочена по времени `approve` их SPEC (раньше `approve` —
   раньше в очереди); Оператор может явной командой переставить
   порядок очереди.
8. Существующий набор `tests/` остаётся зелёным; ни один
   существующий тест, гейт, лимит или guard-проверка не ослаблены и
   не отключены этой задачей.

## Критерии приёмки
AC-1. Перед первым шагом роли developer (состояние `in_dev`) зоны
задачи сверяются с зонами всех задач, находящихся в фазах `in_dev`
… `merge_gate`.

AC-2. Пересечение зон вне общего списка (часть 1) даёт именованный
отказ вида «зона <путь> занята задачей <id> (<состояние>)»; сам
первый шаг developer не запускается.

AC-3. Пересечение по путям из общего списка зон (часть 1) не
считается конфликтом при этой проверке — запуск проходит.

AC-4. При пересечении `auto` останавливается с причиной «ждёт зоны»
и не открывает алерт буксования.

AC-5. `status` и `doctor` показывают для заблокированной задачи
ожидание зоны и занявшую её задачу.

AC-6. После слияния (`merge_gate → done`) или убийства (`kill`)
занявшей зону задачи следующий `run`/`auto` заблокированной задачи
проходит без отказа по пересечению зон.

AC-7. Оператор может снять ожидание зоны явной командой; снятие
пишется в журнал задачи как осознанный риск.

AC-8. Очередь заблокированных пересечением зоны задач упорядочена по
времени `approve` их SPEC (раньше `approve` — раньше в очереди).

AC-9. Оператор может переставить порядок очереди явной командой.

AC-10. Существующий набор тестов (`tests/`) остаётся зелёным; ни
один существующий тест, гейт, лимит или guard-проверка не ослаблены
и не отключены этой задачей.

## Оценка объёма и деление
Сработавшие сигналы:
- **число затрагиваемых модулей/файлов зоны ≥ 5** —
  `orchestrator/auto.py` (причина «ждёт зоны», без алерта
  буксования), предусловие перед первым шагом `in_dev` (сверка
  занятости), `orchestrator/doctor.py`, `orchestrator/catalog.py`
  (отображение ожидания в `status`), `orchestrator/artel.py`
  (команды снятия ожидания и перестановки очереди) — 5 модулей, плюс
  `tests/` (общая зона, в конфликт не идёт).
- **число критериев приёмки ≥ 10** — AC-1..AC-10.

Деление не предлагается — обоснование монолита. Эта задача уже сама —
часть Оператор-утверждённого деления родителя 01M1NKVPD2A79PQ6K0JVV1B2Q1
на 3 части (гейт SPEC, 04.09.2026, коммит 630f00d7): часть 1 —
машиночитаемое поле/общий список (зависимость), эта задача — часть 2
(занятость на старте кода), часть 3 — сверка диффа при переходе в
review (отдельная задача). Пять модулей выше реализуют одну механику
— гейт занятости зоны перед стартом кода — и её грани неразделимы без
промежуточного нерабочего состояния:
- отказ (AC-1, AC-2) без наблюдаемости (AC-4, AC-5) оставляет
  заблокированную задачу без диагностики: `auto` намеренно не поднимает
  алерт буксования (AC-4) именно потому, что `status`/`doctor` берут
  на себя объяснение причины — раздельная поставка одного без
  другого воспроизводит ложное впечатление зависшей задачи;
- отказ без операторской команды снятия (AC-7) оставляет Оператора
  без рычага на случай, когда автоматическое снятие после мержа/kill
  не наступает быстро (занявшая задача сама эскалирована и стоит) —
  заблокированная задача виснет без recourse — это и есть
  «промежуточное нерабочее состояние» в терминах skills/
  spec-authoring.md;
- очередь (AC-8, AC-9) без основной блокировки (AC-1, AC-2)
  бессмысленна сама по себе — упорядочивать нечего, если ничего не
  ждёт.

Прецедент того же класса механики («предусловие/отказ перед стартом
шага + наблюдаемость + ручной рычаг Оператора», собранные одной
задачей) — tasks/T060/SPEC.md (лимитер `MAX_PARALLEL_TASKS`,
инвариант 32 docs/invariants.md): тоже касается старта `run`/`auto`,
`tests/`, при сопоставимом бюджете ($25), собран без деления.
