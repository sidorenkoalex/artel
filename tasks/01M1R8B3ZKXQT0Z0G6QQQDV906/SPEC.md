# SPEC: auto пробует переход по готовым артефактам до шага роли; PLAN status escalate уводит в escalated

## Контекст
Регрессия нового контура №11 (наблюдения 05.09, два симптома). (1)
Цикл `auto` в любом агентном состоянии сначала запускает шаг роли и
только потом пробует `advance` — если артефакт уже готов (PLAN
`status: ready` после возврата из эскалации по бюджету, планка уже
сдана, вердикт ревью уже вынесен), роль тратит шаг ($1–6) на
подтверждение очевидного; так потеряны шаги 05.09 у зон части 3,
тестов без сети, стоимости по видам, канарейки. (2) PLAN.md со
`status: escalate` в артефактной ветке не переводит задачу из in_dev
в escalated: `auto` перезапускает developer, пока не сработает
детекция буксования (5 шагов, канарейка ч.1 — четыре холостых шага
дважды за день, ~$15).

Зона `orchestrator/auto.py`, `orchestrator/fsm_advance.py`
пересекается с задачей «Механика зон, часть 2: занятость зоны на
старте кода» (01M1P9QAG65GVF69YJEV0V18D9, SPEC ready, код идёт
05.09) — по условию ТЗ старт кода этой задачи начинается только
после мержа части 2; до её мержа с этой задачей продвигается только
SPEC и планка (test_author).

## Требования
1. Перед каждым агентным шагом роли `auto` вызывает `fsm.cmd_advance`
   для текущего состояния задачи, прежде чем запускать саму роль
   (`verifying` не затрагивается — там уже свой опрос
   `_advance_verifying_poll`, отдельный от этой механики).
2. Если этот предварительный `advance` выполняет переход состояния —
   шаг роли на этой итерации не запускается, цикл продолжает уже с
   нового состояния.
3. Шаг роли запускается только тогда, когда предварительный `advance`
   отказал по причине «артефакт роли не готов» — тот же класс отказа,
   что и сегодня: обработчик состояния печатает статус БЕЗ журнальной
   записи «переход отклонён…» (например «SPEC.md ещё не ready…»,
   «REVIEW.md status=… — жду вердикта», «PLAN.md не ready —
   разработчик ещё работает»).
4. Отказы предварительного `advance` любого другого класса — guard
   (`cmd_advance` вернул `True`), лок `acceptance_tests/`, свежесть
   ветки, гейт ёмкости diff, «дерево не на ветке задачи» и т. п.
   (обработчик журналирует запись «переход отклонён: …») — не
   запускают шаг роли; цикл реагирует на них так же, как сегодня
   реагирует на такой же отказ `advance`, полученный ПОСЛЕ шага роли:
   стоп-кран двух одинаковых отказов подряд (SPEC T038), детекция
   буксования N шагов подряд без перехода, немедленная остановка при
   отказе guard'ом.
5. Каждый пропуск шага роли по причине «переход уже возможен» пишется
   в журнал задачи одной строкой: «шаг <роль> не нужен: переход
   выполнен по готовым артефактам», где `<роль>` — роль состояния ДО
   перехода.
6. PLAN.md со `status: escalate` на `advance` из состояния `in_dev`
   переводит задачу в `escalated` с текстом раздела «Эскалация»
   PLAN.md в журнале — по тому же правилу, что уже действует для
   REVIEW.md со `status: escalate` (эскалация ревьювера, обработчик
   `review` в `orchestrator/fsm_advance.py`) — независимо от того,
   лежит ли PLAN.md в рабочем каталоге задачи или только в
   артефактной ветке (материализация по SPEC
   01M1NKTF173WV5CPDZ1C3WW69K); шаг developer при этом не
   запускается.
7. Пороги существующих механизмов `auto` — лимит шагов за вызов
   (`AUTO_MAX_STEPS`), детекция буксования (`AUTO_STALL_STEPS_LIMIT`)
   и стоп-кран двух одинаковых отказов подряд (SPEC T038) — не
   меняются; меняется только момент, когда `advance` вызывается
   относительно шага роли.

## Критерии приёмки
AC-1. На каждой итерации цикла `auto`, где у текущего состояния есть
агентная роль (кроме `verifying`), `auto` вызывает `fsm.cmd_advance`
для этого состояния до вызова `runner.cmd_run`.

AC-2. Если этот предварительный `advance` выполняет переход
(состояние после вызова отличается от состояния до него) — `runner.
cmd_run` на этой итерации не вызывается, и в журнал задачи пишется
строка «шаг <роль> не нужен: переход выполнен по готовым
артефактам», где `<роль>` — роль состояния до перехода.

AC-3. Если предварительный `advance` отказал по причине «артефакт
роли не готов» (класс отказов без журнальной записи «переход
отклонён…» — как сегодня у SPEC.md/REVIEW.md/PLAN.md «ещё не
ready»/«жду вердикта»/«разработчик ещё работает») — `auto` запускает
шаг роли как раньше.

AC-4. Если предварительный `advance` отказал guard'ом (`cmd_advance`
вернул `True`) либо журналируемым отказом другого класса («переход
отклонён: …» — лок приёмочных тестов, дерево не на ветке, гейт
ёмкости diff, свежесть ветки и т. п.) — шаг роли на этой итерации не
запускается; цикл реагирует так же, как сегодня реагирует на такой
же отказ `advance`, полученный после шага роли: два одинаковых
отказа подряд останавливают цикл стоп-краном (SPEC T038), N подряд
без перехода — детекцией буксования, отказ guard'ом — немедленной
остановкой.

AC-5. Задача в `in_dev` с PLAN.md `status: ready` (сценарий «планка
сдана до возврата из эскалации по бюджету») — предварительный
`advance` переводит её в `review`, не запуская шаг developer.

AC-6. PLAN.md со `status: escalate` на `advance` из состояния
`in_dev` переводит задачу в `escalated` с текстом раздела
«Эскалация» PLAN.md в журнале задачи, не запуская шаг developer —
независимо от того, лежит ли PLAN.md в рабочем каталоге задачи или
только в артефактной ветке.

AC-7. Отказ по локу `acceptance_tests/` на предварительном `advance`
в `in_dev` не запускает шаг developer; повтор того же отказа на
следующей итерации `auto` останавливает цикл тем же стоп-краном, что
и сегодня.

AC-8. Существующие тесты `auto` — детекция буксования (N шагов
подряд без перехода), стоп-кран двух одинаковых отказов подряд
(SPEC T038), лимит `AUTO_MAX_STEPS` за вызов — остаются зелёными без
ослабления проверяемого ими поведения.

## Не входит
- Изменение порогов `AUTO_MAX_STEPS`, `AUTO_STALL_STEPS_LIMIT` и
  самого механизма стоп-крана/детекции буксования — меняется только
  момент вызова `advance`, не эти пороги.
- Смена состояний FSM.
- Механика опроса `verifying` (`_advance_verifying_poll`) — остаётся
  как есть.
- Занятость зон между параллельными задачами (01M1P9QAG65GVF69YJEV0V18D9,
  «Механика зон, часть 2») — отдельная задача; код этой задачи ждёт
  её мержа (см. «Контекст»).
