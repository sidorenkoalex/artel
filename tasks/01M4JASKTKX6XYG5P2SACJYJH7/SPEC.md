# SPEC: Порядок старта в очереди зоны — очередь Оператора и merge_after решают, кто стартует

## Контекст
Сегодня первый шаг разработчика пускает только занятость зоны:
`orchestrator/zone_lock.py::blocking_conflict` (~398) и `claim` (~459)
смотрят на `_occupies` (~349) и не учитывают ни других ожидающих задач,
ни `queue_order` (~567), ни `merge_after`. Поэтому освободившуюся зону
берёт тот, чей опрос пришёл первым: 05.10 часть 3 этапа 3 (merge_after =
часть 2) заняла зону раньше части 2 — взаимная блокировка; 05.10 17:14Z
зону взяла задача на позиции 4, а позиции 1 и 2 остались ждать.
`zone-reorder` (`cmd_zone_reorder`, ~617) пишет `zone_queue_position` и
печатает «переставлена» (даже без аргументов), но старт не решает;
`queue_position` (~590) считает конкурентами только задачи с ТОЧНО тем
же путём (`conflict[0] == path`, ~609), так что вложенные зоны
(`orchestrator/` и `orchestrator/ci.py`) попадают в разные очереди.
Отдельно: деление задачи на гейте SPEC
(`orchestrator/fsm.py::_spawn_division_subtasks`, ~819) переводит
родителя в `killed`, а `merge_after` зависящих от него задач остаётся на
родителе — `merge_after.check` (~126) / `merge_gate_refuses` (~387)
отказывают им «зависимость убита».

## Требования

1. Зону, которую никто не держит (ни одна задача её не занимает в
   смысле `_occupies`), получает первая по очереди задача среди задач,
   ожидающих пересекающуюся зону; пересечение — с учётом вложенности
   путей (`_paths_overlap`, ~204), т.е. `orchestrator/` и
   `orchestrator/ci.py` — одна очередь. Остальные ожидающие получают
   именованный отказ, текст которого содержит «ждёт очереди зоны:
   впереди <id>», где `<id>` — задача, стоящая впереди.
2. Порядок очереди: явная позиция Оператора (`zone-reorder`,
   `zone_queue_position`) главнее всего; без неё — зависимость раньше
   зависящей задачи (топологический порядок по `merge_after`); затем
   нынешние ключи `queue_order` (момент approve SPEC, затем
   `updated_at`).
3. Задача, у которой незавершённая (не `done`) зависимость `merge_after`
   ждёт пересекающуюся зону, зону не получает: отказ, текст которого
   содержит «ждёт зону ради зависимости <id>», где `<id>` — эта
   зависимость.
4. Ожидающая задача, которая сама не может стартовать, очередь не
   держит: при выборе «первой по очереди» (требование 1) она
   пропускается. Не может стартовать — цикл `run`/`auto` по ней не идёт
   (нет живого lease), задача на паузе (`pause`), задача в эскалации,
   а также задача, сама получающая отказ требования 3 (иначе явная
   позиция Оператора, поставившая зависящую задачу впереди зависимости,
   замкнула бы взаимную блокировку, которую ТЗ требует исключить).
5. `zone_lock.queue_position`, вывод `status` (`catalog`) и проверка
   `doctor` (`orchestrator/doctor/`) показывают ту же очередь, что решает
   старт по требованиям 1–4: тот же состав конкурентов (с учётом
   вложенности путей) и тот же порядок.
6. `zone-reorder` без аргументов — отказ с подсказкой формы вызова
   (`zone-reorder <id1> <id2> ...`): ни одна `zone_queue_position` не
   меняется, «переставлена» не печатается.
7. Деление задачи на гейте SPEC (approve на `spec_gate` с секцией
   «## Деление») переписывает `merge_after` каждой задачи, зависящей от
   родителя: элемент-родитель заменяется последней подзадачей деления,
   прочие элементы остаются. Запись — через `merge_after.rewrite` (~286),
   с записью журнала зависящей задачи «было → стало».
8. Смена ожидания существующих тестовых методов `tests/` — только
   перечнем раздела SPEC «Меняемое поведение» (инвариант 38).

## Критерии приёмки

AC-1. Зона свободна, две задачи в `in_dev` с живым циклом ждут вложенные
зоны (`orchestrator/` и `orchestrator/ci.py`), SPEC задачи B утверждён
раньше SPEC задачи A: `claim` задачи A отказывает текстом с «ждёт
очереди зоны: впереди B», `claim` задачи B проходит.

AC-2. В условиях AC-1 `zone-reorder A B` меняет исход: `claim` задачи A
проходит, `claim` задачи B отказывает текстом с «ждёт очереди зоны:
впереди A». То же — при одинаковой (не вложенной) зоне.

AC-3. Цепочка из трёх задач на одной зоне (C зависит от B, B от A по
`merge_after`; порядок approve SPEC обратный — C, B, A; все в `in_dev` с
живым циклом, зона свободна): первой зону получает A, затем (после
освобождения зоны A) B, затем C; ни на одном шаге ни одна задача не
остаётся без возможности стартовать при свободной зоне.

AC-4. Задача C с незавершённой зависимостью `merge_after` = A, которая
ждёт пересекающуюся зону, получает отказ с «ждёт зону ради зависимости
A» — в том числе когда `zone-reorder` поставил C впереди A; в этом
случае зону получает A (C очередь не держит, требование 4).

AC-5. Первая по очереди ожидающая задача без живого цикла, на паузе или
в эскалации очередь не держит: `claim` следующей по очереди задачи с
живым циклом проходит (по одному случаю на каждое из трёх условий).

AC-6. Для набора ожидающих задач с вложенными зонами порядок, который
показывают `queue_position`, `status` и `doctor`, совпадает с порядком,
в котором `claim` пропускает задачи: задача на позиции 1 — та, чей
`claim` проходит; вложенные зоны считаются одной очередью (общее «всего»).

AC-7. `zone-reorder` без аргументов завершается отказом с подсказкой
`zone-reorder <id1> <id2> ...`, не печатает «переставлена» и не меняет
`zone_queue_position` ни одной задачи.

AC-8. Задача X с `merge_after` = P (и, возможно, другими элементами);
approve на `spec_gate` задачи P с делением на подзадачи S1, S2: после
approve `merge_after` задачи X содержит S2 вместо P (прочие элементы
сохранены), журнал X содержит запись «было → стало» с P и S2, гейт мержа
X больше не отказывает «зависимость убита» из-за P.

## Оценка объёма и деление

Сработавший сигнал: число файлов зоны ≥ 5 (`orchestrator/zone_lock.py`,
`orchestrator/fsm.py`, `orchestrator/merge_after.py`,
`orchestrator/catalog.py`, `orchestrator/doctor/`; `tests/` и
`docs/codebase-map.md` — общие зоны). Возможный второй сигнал — зона
задевает механизм замка зон, на который опираются записи
`docs/invariants.md`.

Решение: **нарезка на 2 подзадачи** (секция «## Деление» ниже). Задача
состоит из двух независимых механик с непересекающимися собственными
зонами:
- требование 7 (переписывание `merge_after` при делении) живёт целиком в
  `orchestrator/fsm.py` + `orchestrator/merge_after.py` и не зависит от
  очереди зоны;
- требования 1–6 (очередь решает старт, показ очереди, `zone-reorder`)
  живут в `orchestrator/zone_lock.py` + `orchestrator/catalog.py` +
  `orchestrator/doctor/` и не трогают деление.
Общие у частей только общие зоны (`tests/`, `docs/codebase-map.md`) —
замок зон их не делит, части не ждут друг друга. Каждая часть мержима
отдельно с зелёной планкой: часть 1 только снимает ложный отказ гейта
мержа после деления; часть 2 меняет правило старта, опираясь на
`merge_after` как он есть в БД. Первой идёт часть 1: она держит
`merge_after` верным после деления, на него опирается топологический
порядок части 2.

Стоимость: часть 1 — класс «до 5 критериев, до 3 файлов» (~$25),
часть 2 — «до 10 критериев, до 4 файлов» (~$40); сумма ~$65 выше рамки
ТЗ ($60). Монолит — ~$45 по классу «до 15 критериев, до 7 файлов»
(значение `budget_usd` этого SPEC), но атомарной механики, которую
нельзя разрезать, здесь нет; выбор между делением и монолитом по
цене — решение Оператора на гейте.

## Деление

### Деление переписывает merge_after зависящих задач

Зоны: orchestrator/fsm.py, orchestrator/merge_after.py, docs/codebase-map.md, tests/
Порядок: первая, без зависимостей
Рамка: $25

Деление задачи на гейте SPEC (approve на `spec_gate` с секцией
«## Деление», `orchestrator/fsm.py::_spawn_division_subtasks`, ~819)
переводит родителя в `killed`, а `merge_after` задач, зависящих от
родителя, остаётся на нём — `orchestrator/merge_after.py::check` (~126) и
`merge_gate_refuses` (~387) отказывают зависящей задаче «зависимость
убита» (случай 05.10: 01M45FJD46 → подзадачи).

Требуется:
1. Деление задачи на гейте SPEC переписывает `merge_after` каждой задачи,
   зависящей от родителя: элемент-родитель заменяется последней
   подзадачей деления, прочие элементы остаются. Запись — через
   `merge_after.rewrite` (~286), с записью журнала зависящей задачи
   «было → стало».
2. Смена ожидания существующих тестов — только разделом SPEC «Меняемое
   поведение» (инвариант 38).

Критерий приёмки (направление): деление на гейте SPEC переписывает
`merge_after` зависящей задачи на последнюю подзадачу, журнал называет
«было → стало», гейт мержа зависящей задачи больше не отказывает
«зависимость убита» из-за родителя.

Только чтение: orchestrator/zone_lock.py, orchestrator/catalog.py,

### Очередь зоны решает старт

Зоны: orchestrator/zone_lock.py, orchestrator/catalog.py, orchestrator/doctor/, docs/codebase-map.md, tests/
Порядок: после части 1
Рамка: $40

Сегодня первый шаг разработчика пускает только занятость зоны:
`orchestrator/zone_lock.py::blocking_conflict` (~398) и `claim` (~459)
решают по `_occupies` (~349); ожидающие задачи, `queue_order` (~567) и
`merge_after` не учитываются. `queue_position` (~590) считает
конкурентами только задачи с ТОЧНО тем же путём (`conflict[0] == path`,
~609) — вложенные зоны попадают в разные очереди. `cmd_zone_reorder`
(~617) печатает «переставлена», в том числе без аргументов, но старт не
решает. Случаи 05.10: взаимная блокировка части 3 и части 2 этапа 3;
после мержа 01M462QACE зону взяла задача на позиции 4.

Требуется:
1. Зону, которую никто не держит, получает первая по очереди задача среди
   ожидающих пересекающуюся зону (с учётом вложенности путей,
   `_paths_overlap`, ~204); остальные получают именованный отказ «ждёт
   очереди зоны: впереди <id>».
2. Порядок очереди: ручной `zone-reorder` главнее; без него — зависимость
   раньше зависящей задачи (топологический порядок по `merge_after`),
   затем нынешние ключи. Задача, у которой незавершённая зависимость
   `merge_after` ждёт пересекающуюся зону, зону не получает (отказ «ждёт
   зону ради зависимости <id>»).
3. Ожидающая задача, которая сама не может стартовать (цикл не идёт,
   пауза, эскалация, отказ «ждёт зону ради зависимости»), очередь не
   держит.
4. `queue_position`, `status` и `doctor` показывают ту же очередь, что
   решает старт; `zone-reorder` без аргументов — отказ с подсказкой.
5. Смена поведения существующих тестов — только разделом SPEC «Меняемое
   поведение» (инвариант 38).

Критерии приёмки (направление): перестановка `zone-reorder` меняет, кто
стартует первым, в том числе при вложенных зонах; цепочка из трёх задач
с `merge_after` на одной зоне проходит без взаимной блокировки —
зависимость стартует раньше зависящей; ожидающая задача на паузе или без
живого цикла очередь не держит; `status`/`doctor` показывают тот же
порядок, что решает старт.

Только чтение: orchestrator/fsm.py, orchestrator/merge_after.py,
orchestrator/runner.py, orchestrator/auto.py, orchestrator/lease.py,
