# SPEC: Б2.1б — гейт мержа `target-human` открывает MR, черновой MR и `max_in_flight` через `forge`

## Контекст
Часть 2 из 2 задачи 01M5XXA2HY73D3WTXDR19Z5SWW (GitLab Б2.1, ADR-0029
п. 1, 7, 12). Часть 1 (01M5XZ9Z68V75VXF5Z66C708T4) вводит состояние
`awaiting_human`, поля `policy` (`max_awaiting`, `awaiting_holds_zones`),
функцию чтения умолчаний полей доставки и ссылку на MR задачи в БД (пара
`iid`, `web_url`); эта часть на них опирается. Сегодня гейт мержа
(`fsm_merge_gate._cmd_approve_merge_gate`, `fsm_merge_gate.py:1442`) умеет
только сливать ветку сам и отправлять `base`; черновой MR заводится только
для GitHub через `gh pr create` (`github_adapter.py:174`);
`policy.mr_assignee`, `draft_mr`, `max_in_flight` вне `targets.py` не
читаются. `forge.open_mr`/`undraft_mr`/`assign_mr` (`forge.py:218`, `:223`,
`:227`) реализованы для GitLab. `target-human` до Б2.3 неподдержан
(`targets.py:29-30`): поддержка в тестах — подменой
`targets.SUPPORTED_MERGE_GATES`/`SUPPORTED_FORGES` внутри теста.

Подтяжка на гейте мержа (`_sync_main_or_wait`, `fsm_merge_gate.py:711-758`)
всегда сливает `base` в ветку (merge) и `policy.freshness` не читает; метод
`freshness` и сжатие исполняются только на переходе `in_dev -> verifying`
(Б1.2). Поэтому для `target-human` сдвиг `base` на гейте решается
возвратом задачи в `in_dev`, а не подтяжкой на гейте (решение Оператора на
гейте SPEC, 27.10.2026).

## Требования

1. **`approve` на `merge_gate` для записи с `target-human`** (ADR-0029
   п. 1). Исполняются без изменений: сверка sha, ссылка документов,
   `no_paths`, неослабление по тексту и по исходам, лок планки, зелёный CI
   головы ветки, публикация головы ветки
   (`_ensure_branch_head_published`, `fsm_merge_gate.py:1513`), отказ во
   время канарейки (`_refuse_during_canary`, `fsm_merge_gate.py:1541`) —
   до открытия MR, мьютекс merge-окна (`_cmd_approve_merge_gate_cycle`,
   `fsm_merge_gate.py:1581`, захват `:1650`).
   Подтверждённый sha обязан совпасть с головой, которая уходит в MR, и с
   головой ветки на сервере (`origin/<ветка>` после публикации), иначе
   отказ, MR не открыт.
   Не исполняются: отказ по красному CI base (`_refuse_if_main_red`,
   `fsm_merge_gate.py:1525`), подтяжка на гейте (`_sync_main_or_wait`,
   `fsm_merge_gate.py:711-758`), слияние в scratch, приложения PLAN,
   `checks_local` по дереву мержа, карта и `guard --all`, отправка base,
   коммит закрытия и уборка (`fsm_merge_gate.py:1545` — задача не `done`),
   ожидание CI base (`_await_main_ci`, `fsm_merge_gate.py:644`, вызов
   `:1548`), справочник ядра, удаление ветки и рабочей копии.
2. **Сдвиг `base` на `approve`** для записи с `target-human`: подтяжка на
   гейте не выполняется; задача возвращается в `in_dev` с причиной «base
   сдвинулся — подготовка ветки заново», MR не открыт. Следующий переход
   `in_dev -> verifying` выполняет сжатие и подтяжку методом `freshness`
   (Б1.2).
3. **Задача с приложениями PLAN** в проекте с `target-human` — отказ
   `approve` с причиной «приложения не применяются в проекте с
   target-human — правку вносят люди проекта».
4. **Открытие MR через `forge`** после шагов требования 1:
   - ссылки на MR в БД нет — открыть MR ветки задачи в `base`;
   - исполнитель: `policy.mr_assignee` из одних цифр (строка) или `int` —
     в `forge` уходит `assignee_id` `int`; иное значение — MR без
     исполнителя и запись журнала задачи «исполнитель не числовой id — не
     назначен»; без `policy.mr_assignee` — MR без исполнителя и запись
     журнала об этом;
   - ссылка на MR в БД есть — нового MR не открывать: снять черновик
     (`undraft_mr`), назначить исполнителя (`assign_mr`) и обновить
     описание MR списком изменённых веткой защищённых путей подтверждённой
     головы — у MR по `iid` ссылки;
   - `open_mr` ответил 409 при отсутствии ссылки в БД — эскалация задачи с
     причиной «MR ветки уже существует, ссылки в БД нет», второй MR не
     открывается. Признак 409 — разбор кода из `reason` результата `forge`
     в `orchestrator/fsm_merge_gate.py` по тексту адаптера
     (`gitlab_adapter.py:211`, «GitLab ответил кодом 409 на …»);
   - успех — ссылка на MR, пара (`iid`, `web_url`), записана в БД и журнал
     задачи, задача переведена в `awaiting_human`;
   - любой другой отказ `forge` (в том числе `undraft_mr`/`assign_mr`/
     обновления описания) — задача остаётся на `merge_gate` с именованной
     причиной.
   Списочного запроса MR не добавляется.
5. **Предел `max_awaiting`**: если задач этого проекта в `awaiting_human`
   уже `policy.max_awaiting`, `approve` на `merge_gate` отказывает с
   причиной, задача остаётся на гейте; `status` показывает «очередь:
   предел awaiting_human». Задачи других проектов в счёт не входят. Счёт
   ведётся внутри мьютекса merge-окна проекта — после его захвата
   (`fsm_merge_gate.py:1650`).
6. **Черновой MR через `forge`** (ADR-0029 п. 7): для записи с
   `target-human` и `draft_mr: true` — черновой MR при первой отправке
   ветки (вход в `verifying`) через `forge.open_mr(draft=True)`, а не через
   `gh`; успех — ссылка на MR (`iid`, `web_url`) записывается в БД сразу.
   Отказ `forge.open_mr(draft=True)` — переход в `verifying` не
   выполняется, задача остаётся в `in_dev` с именованной причиной в
   журнале и в `status`. Для `draft_mr: false` — MR один, открывается на
   гейте мержа. В описании MR — подсветка изменённых веткой защищённых
   путей (не всех защищённых путей проекта). Поведение GitHub-проектов с
   `operator` не меняется.
7. **`max_in_flight`** (ADR-0029 п. 12). «Запись „ветка отправлена“» в
   этом SPEC — запись журнала задачи любой из двух форм:
   `gitcmd.PUSH_SENT_ACTION` (`gitcmd.py:176`) или
   `gitcmd.PUSH_SENT_LEGACY_ACTION` (`gitcmd.py:177`; обе читаются на
   `gitcmd.py:224-225`). Первая отправка — у задачи нет ни одной из них.
   Предел проверяется в единой точке отправки `orchestrator/gitcmd.py`
   перед ПЕРВОЙ отправкой ветки задачи: если незакрытых задач этого
   проекта с записью «ветка отправлена» (в любом неокончательном
   состоянии, включая `in_dev` после возврата, `review`, `escalated`,
   `awaiting_human`) уже `policy.max_in_flight`, отправка отказывается до
   вызова git с именованной причиной в журнале и в `status`. Закрытые
   (`done`, `killed`) задачи в счёт не входят. Покрывает все пути первой
   отправки: вход в `verifying` (задача ждёт в `in_dev`), черновой MR
   GitHub на входе в `in_dev` (`github_adapter.ensure_draft_mr`), путь
   `amend-tests` (`amend.py:834`), путь сжатия (`tests_writing.py:67-68`,
   отправка `:152`). Задачи других проектов не считаются. Повторная
   отправка задачи с записью «ветка отправлена» пределом не отказывается.
8. **Инварианты** — приложением PLAN к `tests/test_invariants.py`
   (защищённый путь): тест «для проекта с `target-human` пульт не
   выполняет слияние, не отправляет `base` и ничего не отправляет в ветку
   задачи в `awaiting_human`» (по образцу `MergeOnlyFromMergeGateTest`,
   `tests/test_invariants.py:646`); тест «MR открывается или снимается с
   черновика только для подтверждённой головы с зелёным CI» (речь о
   нечерновом MR гейта мержа: черновик на входе в `verifying` открывается
   до CI по требованию 6).

## Критерии приёмки

AC-1. На подменённом `forge` `approve` на `merge_gate` записи с
`target-human`: `policy.mr_assignee` `"42"` (строка из цифр) и `42`
(целое) уходят в `forge.open_mr` исполнителем `int` 42; `"alice"` — MR
открыт без исполнителя, в журнале задачи запись «исполнитель не числовой
id — не назначен»; без `policy.mr_assignee` — MR открыт без исполнителя, в
журнале задачи запись об этом.

AC-2. `approve` на `merge_gate` записи с `target-human` на подменённом
`forge`: MR ветки задачи в `base` открыт, задача в `awaiting_human`,
ссылка на MR — пара (`iid`, `web_url`) — в БД и в журнале задачи. В том же
`approve` исполнены публикация головы ветки, проверка канарейки (до вызова
`open_mr`) и захват мьютекса merge-окна проекта; во время живой канарейки
`approve` отказывает и `open_mr` не зван.

AC-3. В том же `approve` шпионы не видят слияния в scratch, отправки
`base`, коммита закрытия и уборки, удаления ветки и рабочей копии,
вызова `_await_main_ci` (ожидания CI base); задача не `done`.

AC-4. При красном CI base `approve` записи с `target-human` по нему не
отказывает и открывает MR; при красном CI головы ветки — отказ, MR не
открыт, задача на `merge_gate`.

AC-5. sha `approve` не совпал с головой ветки, уходящей в MR, — отказ, MR
не открыт, задача на `merge_gate`. sha совпал с фиксацией, но голова ветки
на сервере (`origin/<ветка>` после публикации) другая — отказ, MR не
открыт, задача на `merge_gate`.

AC-6. На `approve` записи с `target-human` сдвинулся base: подтяжка на
гейте не выполнена (шпион не видит слияния `base` в ветку и отправки
ветки), задача в `in_dev`, в журнале причина «base сдвинулся — подготовка
ветки заново», MR не открыт.

AC-7. Задача с приложениями PLAN — отказ `approve` с причиной «приложения
не применяются в проекте с target-human — правку вносят люди проекта», MR
не открыт, задача на `merge_gate`.

AC-8. Отказ `forge` при открытии MR — задача остаётся на `merge_gate` с
именованной причиной, ссылки на MR в БД нет.

AC-9. Ссылка на MR в БД есть: `approve` не зовёт `open_mr`, зовёт
`undraft_mr` и `assign_mr` с `iid` из ссылки; задача в `awaiting_human`.

AC-10. Подменённый `forge.open_mr` вернул результат с `reason` в тексте
адаптера для кода 409 («GitLab ответил кодом 409 на …») при отсутствии
ссылки в БД — задача эскалирована с причиной «MR ветки уже существует,
ссылки в БД нет», второй вызов `open_mr` не сделан. С `reason` другого кода
(например 403) — задача на `merge_gate` с именованной причиной, не
эскалирована.

AC-11. Отказ `undraft_mr` или `assign_mr` — задача на `merge_gate` с
именованной причиной; повторный `approve` не зовёт `open_mr` (второй MR не
открыт).

AC-12. Предел `max_awaiting`: при `policy.max_awaiting` = N и N задачах
этого проекта в `awaiting_human` `approve` на `merge_gate` (N+1)-й задачи —
отказ с причиной, задача на `merge_gate`, MR не открыт; `status` этой
задачи показывает «очередь: предел awaiting_human». При N−1 задачах этого
проекта и любом числе задач другого проекта в `awaiting_human` `approve`
проходит.

AC-13. `draft_mr: true`: на входе в `verifying` открыт черновой MR через
`forge.open_mr(draft=True)` (шпион `gh` не видит создания PR), ссылка на
MR (`iid`, `web_url`) в БД сразу после успеха; на `approve` гейта мержа
черновик снят, второй MR не открыт.

AC-14. `draft_mr: false`: на входе в `verifying` MR не открывается; MR
открывается только на `approve` гейта мержа.

AC-15. Описание MR, открытого пультом, называет изменённые веткой
защищённые пути и не называет защищённые пути, веткой не изменённые
(мутация «в описании перечислены все защищённые пути проекта» краснит
критерий). На `approve` гейта мержа описание чернового MR обновлено
списком изменённых веткой защищённых путей подтверждённой головы.

AC-16. `max_in_flight`: при `policy.max_in_flight` = N и N незакрытых
задачах этого проекта с записью «ветка отправлена» в журнале — среди них
задача в `review`, задача в `in_dev` после возврата, задача в
`escalated` и задача в `awaiting_human` — задача на входе в `verifying`
ветку не отправляет (шпион отправок не видит её ветки), остаётся в
`in_dev`, именованная причина — в журнале и в `status`. При N−1 таких
задачах этого проекта и любом числе таких задач другого проекта ветка
отправляется. При N−1 таких незакрытых задачах этого проекта и любом
числе задач этого проекта в `done`/`killed` с записью «ветка отправлена»
ветка отправляется.

AC-17. `max_in_flight` на пути `amend-tests`: при N задачах этого проекта
с записью «ветка отправлена» и задаче без такой записи `amend-tests` по ней
не отправляет ветку (шпион argv `gitcmd.git`/`gitcmd.in_repo` не видит её
отправки), в журнале — именованная причина предела.

AC-18. `max_in_flight` на пути входа в `in_dev` (черновой MR GitHub,
`github_adapter.ensure_draft_mr`): при N задачах этого проекта с записью
«ветка отправлена» первая отправка ветки новой задачи отказана до вызова
git с именованной причиной в журнале; задача этого проекта, у которой
запись «ветка отправлена» уже есть, отправляет ветку повторно без отказа.

AC-19. PLAN несёт приложение к `tests/test_invariants.py`, которое
применяется к base (`git apply --check`) и добавляет два теста
требования 8.

AC-20. `max_awaiting` под мьютексом: при `policy.max_awaiting` = N и N−1
задачах этого проекта в `awaiting_human` два параллельных `approve` на
`merge_gate` двух задач этого проекта — проходит ровно один (одна задача в
`awaiting_human`, у неё открыт MR), второй отказан с причиной предела,
вторая задача на `merge_gate`, её MR не открыт.

AC-21. Отказ `forge.open_mr(draft=True)` на входе в `verifying`
(`target-human`, `draft_mr: true`): переход не выполнен, задача в `in_dev`,
именованная причина — в журнале и в `status`, ссылки на MR в БД нет.

AC-22. Старая форма записи: задача, у которой в журнале есть только
`gitcmd.PUSH_SENT_LEGACY_ACTION` (без `PUSH_SENT_ACTION`), при N задачах
этого проекта с записью «ветка отправлена» отправляет ветку без отказа
пределом `max_in_flight` (это не первая отправка).

## Оценка объёма и деление

Сработавшие сигналы: файлов зоны ≥ 5 (8 модулей `orchestrator/`);
критериев приёмки ≥ 10 (22); `budget_usd` ≥ $30 ($45 — рамка ТЗ); зона
задевает механизм записей `docs/invariants.md` (гейт мержа, переходы FSM,
точка отправки `gitcmd.py`, `tests/test_invariants.py`).

Материал для решения Оператора — **обоснование монолита**: задача уже
часть 2 деления, принятого Оператором на гейте SPEC родителя 27.10.2026
(рамка $45). Дальнейший разрез по зонам неудобен: `fsm_merge_gate.py`
(гейт → MR) и `fsm_advance.py`/`github_adapter.py` (черновой MR на входе в
`verifying`) делят одну функцию открытия MR через `forge` и описание с
защищёнными путями (AC-13–AC-15 проверяют обе точки вместе: черновик на
входе, снятие и обновление описания на гейте); `max_in_flight` в
`gitcmd.py` отделим механически, но тогда черновой MR на входе в
`verifying` (первая отправка) мержится без предела отправок, который
ADR-0029 п. 12 вводит вместе с ним. Возможный разрез, если Оператор его
предпочтёт: (а) `max_in_flight` в `gitcmd.py` (AC-16–AC-18, AC-22) первой
частью; (б) гейт мержа, `max_awaiting`, черновой MR и приложение к
инвариантам (AC-1–AC-15, AC-19–AC-21). Калибровка для >15 критериев —
~$85; потолок держит рамка ТЗ $45.
