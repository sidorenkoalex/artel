## Пути обхода гейтов
- **Е-1 (требование 6, AC-13; Б-2).** `target-human` с `forge: github` в SPEC не разобран. Б2.1а прямо ведёт этот вариант (её AC-18), а у `forge._GitHub` нет `open_mr`. Если тесты AC-13 делать на `forge: gitlab`, утверждение «через `forge`, а не через `gh`» выполнится буквально без правки `gh`-пути. `ensure_draft_mr` и `_ensure_draft_mr_after_publish` для github-проекта с `target-human` по-прежнему заведут PR через `gh` на входе в `in_dev` и после push (`fsm_advance.py:361`, `:648`; `github_adapter.py:252`). Затем `forge.open_mr(draft=True)` откажет «не реализовано для github», и задача навсегда останется в `in_dev` (требование 6). Нужно одно из двух:
  - явная граница: `target-human` только с `forge: gitlab` до Б2.3, с отказом для github;
  - критерий на `forge: github`, где `gh pr create` не зовётся.
- **Е-2 (требование 7).** Счёт `max_in_flight` не защищён замком. Два цикла `auto` двух задач проекта на входе в `verifying` одновременно видят N−1 и отправляют обе ветки — предел превышен. Для `max_awaiting` Оператор потребовал счёт под мьютексом (решение №1 п. 4, AC-20). Для `max_in_flight` ни ТЗ, ни решения этого не требуют, поэтому это замечание, а не отклонение. Решает Оператор.
- **Е-3 (требование 4, AC-10).** Разбор кода 409 подстрокой `"409"` по всему `reason` пройдёт AC-10, но сочтёт 409-м любой ответ, путь которого содержит `409` (id проекта, `iid`). Задача тогда эскалируется ложно. В SPEC стоит закрепить разбор по шаблону `gitlab_adapter.py:211` («кодом (\d+) на») или добавить в AC-10 случай «код не 409, в пути есть 409».
- **Е-4 (требование 4, AC-9).** Что передавать в `assign_mr` на пути «ссылка есть», когда `mr_assignee` не числовой или отсутствует, SPEC не говорит. Буквально «назначить исполнителя» с `None` снимет исполнителя, которого люди проекта назначили черновику (`gitlab_adapter.py:542` шлёт `assignee_id: null`). Запись журнала «не назначен» на этом пути тоже не оговорена. Решает Оператор: (а) `assign_mr` не звать без числового id; (б) звать всегда.
