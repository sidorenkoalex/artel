# ANSWER-1: ответ Оператора

## Ответы

1. Вариант A. Перехода `spec_gate -> spec_writing` нет, пример в ТЗ
   ошибочен — вычеркнуть. Новый переход не заводить, объём критичного
   фикса не расширять.
2. Вариант A. Правило применяется к любому возврату в `in_dev` с
   основанием переделки: `review -> in_dev` (замечания), `acceptance ->
   in_dev`, `merge_gate -> in_dev`, `verifying -> in_dev` (reject
   Оператора). Одна причина — общий обработчик `in_dev`, не знающий
   источника возврата, — закрывается одним правилом: до первого
   завершённого шага developer после такого возврата пред-advance `auto`
   не выполняется, а гейт `in_dev -> review` не пропускает неизменённый
   код. Возврат из `escalated` в `in_dev` (`escalated_from = in_dev`)
   считать по тому же правилу, если эскалация случилась после замечаний
   ревью или reject (то есть основание переделки ещё не отработано).
3. Вариант A. Пункт про `tests_writing` после отказа трассируемости
   убрать: поведение уже верное. В SPEC зафиксировать его регресс-тестом
   («после отказа трассируемости `auto` запускает test_author») без новой
   логики. Случай возврата `escalated -> tests_writing` после ответа
   Оператора отдельным AC не нужен: отказ гейта `tests_writing` по
   маркерам `escalate` — журналируемый отказ вне `in_dev`, роль получает
   шаг на каждой итерации по существующей логике `auto`.
