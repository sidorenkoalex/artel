# SPEC: регрессия №13 — после замечаний ревью `auto` запускает разработчика, а не переход

## Контекст
Два инцидента 05.09 сразу после мержа задачи 01M1R8B3ZKXQT0Z0G6QQQDV906
(«auto: переход по готовым артефактам до запуска роли»): предварительный
`advance` внутри `auto` видит на ветке готовый по форме артефакт роли
(PLAN.md `status: ready`, код в ветке) и пропускает задачу дальше по FSM,
не запустив саму роль — хотя причина, по которой задача вернулась в это
состояние (замечания ревью, reject Оператора, возврат из эскалации),
ещё не отработана. Итог первого инцидента: ревьювер трижды подряд
рецензирует байт-в-байт тот же код, лимит ревью исчерпан, задача в
`escalated`. Второй инцидент (после ANSWER-1 этой же задачи): цикл
`auto` из `spec_writing` пред-advance'ом прочитал прежний QUESTIONS.md
(`status: ready`) и снова увёл задачу в `escalated`, не дав аналитику
шага — тот же класс бага, другой источник возврата.

Общий принцип фикса (ANSWER-2, п.2): пред-advance по готовым артефактам
допустим только когда артефакт роли НОВЕЕ события, вернувшего задачу в
это состояние (замечания ревью, reject, ANSWER Оператора); иначе цикл
обязан сначала дать роли шаг.

## Требования

1. Предварительный `advance` в цикле `auto` не выполняется, если текущее
   пребывание задачи в `in_dev` началось переходом с основанием
   переделки — `review -> in_dev` (замечания ревью), `acceptance ->
   in_dev` (reject приёмки), `merge_gate -> in_dev` (reject), `verifying
   -> in_dev` (reject) — и с этого перехода не было ни одного
   завершённого шага роли developer (запись `agent run finished` роли
   developer после записи `state -> in_dev`). В этом случае `auto` сразу
   запускает шаг роли developer.
2. Возврат из `escalated` в состояние роли (`in_dev`, `spec_writing`,
   `tests_writing`), случившийся по основанию переделки, ещё не
   отработанному (замечания ревью/reject, предшествовавшие эскалации) —
   по тому же правилу: предварительный `advance` не выполняется до
   первого завершённого шага соответствующей роли после возврата.
   Артефакт, бывший основанием прежней эскалации (QUESTIONS.md, PLAN.md
   со `status: escalate`, маркеры `AC-n: escalate`), не считается
   «готовым» для перехода, пока роль его не переписала. Переход
   `spec_gate -> spec_writing` (reject SPEC) в коде не существует —
   в объём задачи не входит (ANSWER-1, п.1).
3. Гейт `in_dev -> review` (`fsm_advance`) не пропускает переход, если
   REVIEW.md текущей итерации имеет `status: changes_requested`, а
   кодовая ветка не получила ни одного коммита разработчика после
   коммита этого REVIEW.md (сверка по времени/sha, не по тексту) —
   рубеж действует независимо от `auto`: ручной `advance` Оператора
   тоже не должен возвращать неизменённый код на ревью.
4. Отказ обоих рубежей (требования 1-2 в `auto`, требование 3 в
   `fsm_advance`) именован и журналируется с указанием номера итерации:
   «замечания ревью не отработаны: нет шага developer после итерации N».
5. Поведение `tests_writing` после отказа трассируемости AC (состояние
   не меняется, test_author получает шаг на каждой итерации) уже
   корректно и этой задачей не меняется — фиксируется регресс-тестом
   (ANSWER-1, п.3).

## Критерии приёмки

AC-1. Предварительный `advance` в цикле `auto` не выполняется, если
текущее пребывание задачи в `in_dev` началось одним из переходов —
`review -> in_dev` (замечания ревью), `acceptance -> in_dev` (reject
приёмки), `merge_gate -> in_dev` (reject), `verifying -> in_dev`
(reject) — и с этого перехода не было ни одного завершённого шага роли
developer (запись `agent run finished` роли developer после записи
`state -> in_dev`); `auto` сразу запускает шаг developer.

AC-2. Возврат из `escalated` в состояние роли (`in_dev`, `spec_writing`,
`tests_writing`), случившийся по основанию переделки, ещё не
отработанному — предварительный `advance` не выполняется до первого
завершённого шага соответствующей роли после возврата; артефакт —
основание прежней эскалации (QUESTIONS.md, PLAN.md со `status:
escalate`, маркеры `AC-n: escalate`) — не считается «готовым» для
перехода, пока роль его не переписала.

AC-3. Гейт `in_dev -> review` не пропускает переход, если REVIEW.md
текущей итерации имеет `status: changes_requested`, а кодовая ветка не
получила ни одного коммита разработчика после коммита этого REVIEW.md
(сверка по времени/sha, не по текстовому сравнению) — рубеж действует
независимо от `auto`, включая ручной `advance` Оператора.

AC-4. Отказ обоих рубежей (AC-1/AC-2 в `auto`, AC-3 в `fsm_advance`)
именован и журналируется с указанием номера итерации: «замечания ревью
не отработаны: нет шага developer после итерации N».

AC-5. Тест: сценарий «замечания ревью → auto» запускает шаг developer,
а не выполняет advance по готовому PLAN.md.

AC-6. Тест: после завершённого шага developer после возврата в `in_dev`
следующий `advance` (в т.ч. предварительный внутри `auto`) проходит
штатно — рубеж AC-1/AC-3 не блокирует его.

AC-7. Тест: ручной `advance` Оператора на неизменённом коде после
REVIEW.md `status: changes_requested` — отказ с именованной причиной
(AC-4), а не переход в `review`.

AC-8. Тест: возврат из `escalated` в состояние роли по ANSWER Оператора
— `auto` запускает шаг соответствующей роли, а не повторяет переход
обратно в `escalated` по старому артефакту-основанию эскалации.

AC-9. Регресс-тест: после отказа трассируемости AC в `tests_writing`
(состояние не меняется) `auto` по-прежнему запускает шаг test_author на
каждой итерации — фиксация уже корректного поведения, без новой логики.

AC-10. Существующие тесты `tests/test_auto_cycle.py`,
`tests/test_advance_guard.py` и приёмочная планка задачи
01M1R8B3ZKXQT0Z0G6QQQDV906 остаются зелёными без ослабления проверок.

## Оценка объёма и деление
Сработавший сигнал: число критериев приёмки = 10 (порог ≥ 10).

Обоснование монолита: два рубежа (AC-1/AC-2 в `auto` и AC-3 в
`fsm_advance`) закрывают ОДИН класс регрессии — пред-advance/ручной
advance, принимающий неотработанное основание переделки за готовый
артефакт. Рубеж только в `auto` (без AC-3) оставляет открытым путь
регрессии через ручной `advance` Оператора; рубеж только в
`fsm_advance` (без AC-1/AC-2) не чинит расход бюджета на холостые
итерации `auto`, который и был источником обоих инцидентов 05.09. Любая
частичная нарезка мержится в промежуточном состоянии, где регрессия
всё ещё воспроизводима одним из двух путей — граница зон
(`orchestrator/auto.py` / `orchestrator/fsm_advance.py`) здесь не
совпадает с границей независимо мержимых частей. AC-2 (возврат из
`escalated`) — тот же общий принцип «артефакт роли новее события
возврата», применённый к другому источнику входа в состояние роли
(эскалация вместо reject/changes_requested); отдельная задача частично
повторила бы разбор того же кода `auto`/`fsm.py`, что и AC-1, без
экономии на самостоятельной мержимости.

## Не входит

- Переход `spec_gate -> spec_writing` (reject SPEC) — не существует в
  коде сегодня, этой задачей не заводится (ANSWER-1, п.1).
- Изменение логики отказа трассируемости AC в `tests_writing` —
  поведение уже корректно, фиксируется тестом (AC-9), не меняется
  кодом (ANSWER-1, п.3).
- Отдельный AC под возврат `escalated -> tests_writing` конкретно после
  ответа Оператора test_author — покрывается общим правилом AC-2, не
  требует отдельной ветки логики (ANSWER-1, п.3).
- Ослабление, удаление или смягчение существующих гейтов, тестов,
  лимитов и инвариантов — только через ADR Оператора (принцип
  целостности, ADR-0002).
