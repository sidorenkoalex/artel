# PLAN: регрессия №13 — после замечаний ревью `auto` запускает разработчика, а не переход

## Подход

Два независимых рубежа одного класса регрессии («артефакт роли новее
события возврата — иначе шаг роли», ANSWER-2 п.2):

1. **`orchestrator/auto.py` — журнальный рубеж (AC-1/AC-2/AC-4 часть
   auto/AC-5/AC-8/AC-9).** Перед предварительным `advance` цикл проверяет:
   если текущая роль (`runner.step_role`) активна в одном из состояний
   `_REWORK_GATE_STATES = ("in_dev", "spec_writing", "tests_writing")`,
   и с ПОСЛЕДНЕЙ записи журнала `state -> <это состояние>` ещё не было
   записи `agent run finished` этой же роли — предварительный `advance`
   НЕ вызывается вовсе, цикл сразу проваливается в блок «запускаем роль»
   (тот же код, что раньше исполнялся только после отказа/готовности
   артефакта). Проверка — чисто журнальная (`store.task_steps`), не
   смотрит НИ на текст detail, НИ на имя предыдущего состояния: это
   намеренно (докстринг AC-2 в приёмке — мутация «проверка по имени
   предыдущего состояния» обязана ловиться) и одним и тем же кодом
   закрывает и AC-1 (прямой `review -> in_dev`), и AC-2/AC-8 (возврат
   через `escalated`), не требуя знания источника возврата.

   `review` НЕ входит в `_REWORK_GATE_STATES`: свежесть его собственного
   вердикта уже держит отдельный, давно существующий механизм
   (`artifacts.fresh_verdict_iteration`/`reviewed_iter`) — это не предмет
   данной задачи, и включение `review` сюда было бы расширением объёма
   без AC под него.

   Именованная причина (AC-4) достаёт номер итерации из detail найденной
   записи регэкспом `итерация (\d+)` — тот же формат, каким `fsm_advance.
   review` уже пишет `f"замечания ревью, итерация {iters}"`; когда такого
   номера в detail нет (acceptance/merge_gate/verifying reject, эскалация
   по другому основанию), причина остаётся именованной, но без
   выдуманного номера.

2. **`orchestrator/fsm_advance.py::in_dev` — git-based рубеж (AC-3/AC-4
   часть fsm_advance/AC-6/AC-7).** Отдельная проверка `_review_rework_
   gate_refuses`, встроенная в САМ гейт `in_dev -> review` (рядом с
   `_capacity_gate_refuses`/`_zones_gate_refuses`): если REVIEW.md
   текущей итерации (артефактная ветка) несёт `status: changes_requested`,
   а последний НЕ-«подтяжка main» коммит кодовой ветки старше коммита
   REVIEW.md — переход отказывает независимо от того, кто его вызвал
   (`auto` или ручной Оператор). Сверка — по времени коммитов (`%cI`,
   `datetime.fromisoformat`), не по sha и не по тексту: REVIEW.md и код
   живут на двух ветках без общего родителя (SPEC требование 3). Коммиты
   «подтяжка main» (`f"{task_id}: подтяжка ..."`, `fsm._pull_main_or_
   escalate`/`_auto_resolve_map_conflict`) явно исключаются из
   «последнего коммита кода» — иначе рутинная подтяжка (единственное, что
   двигало кодовую ветку между итерациями в реальном инциденте, SPEC
   «Контекст») маскировала бы неотработанные замечания под настоящий шаг
   developer.

   Внешний target и недоступный/незаглушенный git (лёгкие песочницы —
   `fake_git`, `disk_backed_show`) дают гейту деградировать в «не
   отказывать» — тот же приём деградации, что уже несёт `fsm._pull_main_
   or_escalate` (`git не ответил -> "fresh"`): отсутствие сигнала не
   значит «код не менялся».

3. **Тесты.** `tests/test_auto_cycle.py::FakeRun` дополнена журналом
   `agent run finished` под ролью, прочитанной ДО эффекта сценария —
   без этого фейк не воспроизводит реальное поведение `runner.cmd_run`
   (SPEC 745: журналирует «agent run finished» на КАЖДЫЙ успешный
   прогон), и новый журнальный рубеж (пункт 1) видел бы «роль никогда не
   отрабатывала» бесконечно для существующих тестов, использующих
   голые `lambda`. Двойного журналирования с `agent_step` (используется
   НОВОЙ приёмочной планкой этой же задачи, который журналирует
   САМ) избегает проверка «уже есть запись с этим action среди строк,
   добавленных за время вызова сценария — не добавляй свою».
   Регресс-тест `AC-9` фиксирует уже корректное поведение `tests_writing`
   без изменения логики (ANSWER-1 п.3).

4. **Фикс по ANSWER-3 (пост-approve регрессия против AC-7 приёмки
   01M1R8B3ZKXQT0Z0G6QQQDV906).** Журнальный рубеж пункта 1, реализованный
   как «нет шага роли с последней `state -> {state}» без разбора detail»,
   перехватывал и ЛЕГИТИМНЫЙ первый вход в состояние (например,
   `tests_writing -> in_dev`, когда developer этой задачи ещё ни разу не
   запускался) — рубеж срабатывал, пропуская предварительный `advance`
   целиком и запуская роль НАПРЯМУЮ, хотя до этой правки advance получал
   шанс сработать и мог сам отказать другим (не rework) классом —
   например локом `acceptance_tests/` (требование 4, AC-7 задачи
   01M1R8B3ZKXQT0Z0G6QQQDV906). Оператор воспроизвёл красным прогоном
   исторической планки этой задачи на коде текущей ветки (ANSWER-3, п.1,
   `git archive refs/artifacts/01M1R8B3ZKXQT0Z0G6QQQDV906
   tasks/01M1R8B3ZKXQT0Z0G6QQQDV906/acceptance_tests`).

   Фикс — `orchestrator/auto.py::_is_legit_first_entry_detail` +
   константы `_LEGIT_FIRST_ENTRY_DETAILS`/`_LEGIT_FIRST_ENTRY_PREFIXES`:
   `_role_step_since_state_entry` деградирует в «роль уже отработала»
   (пред-advance не держится), когда `detail` найденной записи `state ->
   {state}` дословно совпадает с одним из ДВУХ известных легитимных
   переходов — `spec_gate -> tests_writing` («гейт SPEC пройден —
   приёмочные тесты до кода») и `tests_writing -> in_dev` («приёмочные
   тесты готовы — трассируемость AC пройдена») — либо начинается с одного
   из ДВУХ префиксов `spec_gate -> in_dev` при `skip_tests`/без
   AC-разметки («тесты пропущены (skip_tests):»/«SPEC schema_version »).
   Это ИСЧЕРПЫВАЮЩИЙ список: `grep -n 'set_state(conn, task_id, "in_dev"'
   orchestrator/*.py` (и то же для `"tests_writing"`/`"spec_writing"`)
   называет ВСЕ точки кода, переводящие задачу в одно из трёх состояний
   `_REWORK_GATE_STATES` — единственные две НЕ по основанию переделки:
   `orchestrator/fsm.py::_cmd_approve` (обе ветки `spec_gate ->
   in_dev`/`spec_gate -> tests_writing`) и `orchestrator/fsm_advance.py::
   tests_writing` (`tests_writing -> in_dev`, AC trace пройдена). Все
   прочие — прямой reject (`review`/`acceptance`/`merge_gate`/`verifying
   -> in_dev`, включая содержательный конфликт merge,
   `orchestrator/fsm_merge_gate.py:125`) или возврат из `escalated` —
   остаются гейтуемыми без изменений.
   Возврат из `escalated` (`orchestrator/fsm.py::_cmd_approve`, «эскалация
   разрешена, продолжаем») НАМЕРЕННО не входит в список — этот текст один
   и тот же для ЛЮБОГО основания эскалации, различить rework/не-rework по
   нему нельзя, и ANSWER-2 п.2/AC-2/AC-8 требуют держать рубеж именно
   здесь (цена лишнего шага роли на не-rework возврате — уже принятый
   компромисс, см. «Влияние на систему» ниже, без изменений).

## Влияние на систему

- Журнальный рубеж (шаги 1, 4) применяется к КАЖДОМУ входу в
  `in_dev`/`spec_writing`/`tests_writing`, КРОМЕ трёх легитимных первых
  входов, дословно перечисленных `_is_legit_first_entry_detail` (шаг 4).
  Первая версия шага 1 (до ANSWER-3) держала пред-advance и на этих трёх
  входах тоже — предполагалось, что артефакт роли физически не может
  существовать на первом входе, и рубеж поэтому «безвреден»; предположение
  оказалось неверным ровно там, где артефакт роли (например PLAN.md
  developer) появляется НЕ вместе с самим первым входом, а раньше — и
  рубеж перехватывал переход НАПРЯМУЮ в шаг роли, минуя предварительный
  `advance`, которому в реальности было чем отказать (лок
  `acceptance_tests/`, требование 4) — регрессия, которую поймала AC-7
  приёмки 01M1R8B3ZKXQT0Z0G6QQQDV906 (ANSWER-3). Единственный класс, где
  рубеж ДОБАВЛЯЕТ шаг роли сверх прежнего поведения без строгой
  необходимости, остаётся тем же, что и до ANSWER-3, — возврат из
  `escalated` по НЕ-rework основанию (например, снятие эскалации по
  бюджету) с уже готовым артефактом: тратится один дополнительный шаг
  роли, прежде чем гейт пропустит задачу дальше. Это сознательный
  компромисс в пользу безопасности (ANSWER-2 п.2: «пред-advance допустим
  только когда артефакт роли новее события возврата») — дешевле одного
  лишнего шага, чем повторение регрессии №12/№13; ANSWER-3 не пересматривает
  этот компромисс, только сужает саму гейтуемую область на три конкретных
  легитимных перехода.
- `review` НЕ включён в новый журнальный рубеж — его свежесть уже
  защищена `reviewed_iter`/`fresh_verdict_iteration`; включение расширило
  бы объём задачи без AC.
- Git-based рубеж (шаг 2) — ДОПОЛНИТЕЛЬНОЕ условие существующего перехода
  `in_dev -> review`, не новое состояние FSM и не смягчение существующих
  проверок (`_capacity_gate_refuses`/`_zones_gate_refuses`/лок
  `acceptance_tests/` продолжают действовать как раньше, рубеж добавлен
  ПОСЛЕ них). Деградация «git не ответил -> не отказывать» — тот же
  принцип, что уже используют соседние функции того же файла
  (`_pull_main_or_escalate`), не новый прецедент.
- Существующие тесты `tests/test_auto_cycle.py` (41 после шага 4,
  включая неослабляемый `AutoNeverPassesAGateTest`) и `tests/
  test_advance_guard.py` (7) — зелёные без изменения ассертов, кроме
  добавленного журналирования в `FakeRun` (инфраструктурная правка,
  делающая фейк реалистичнее, не тест-специфичная подгонка) и нового
  регресс-теста шага 4. Прогнаны также `test_advance_refusal_history`,
  `test_review_freshness`, `test_review_registry_gate`, `test_zones_gate`,
  `test_capacity_gate`, `test_branch_freshness_gate`, `test_answer_gate`,
  `test_answer`, `test_invariants`, `test_fsm_branch_correct_status_reads`,

  поведение. Откат ТОЛЬКО шага 4 (при сохранении шага 1) вернул бы
  регрессию AC-7 — не самостоятельная точка отката.

## Риски

- Regex-эвристика извлечения номера итерации (`итерация (\d+)`) в
  `auto.py` завязана на формат detail, который пишет `fsm_advance.
  review` (`"замечания ревью, итерация {iters}"`); при изменении этого
  формата в будущей задаче сообщение AC-4 останется именованным, но
  потеряет номер (деградация текста, не поведения — тест AC-4 живёт в
  `tests/` и заметит расхождение).
- Git-based рубеж читает `t["branch"]` (код-ветку) через `gitcmd.git` в
  `config.ROOT` — только self-target; для внешнего target рубеж явно
  выключен (тот же довод, что у соседних `_capacity_gate_refuses`/
  `_zones_gate_refuses`).
- Белый список `_LEGIT_FIRST_ENTRY_DETAILS`/`_LEGIT_FIRST_ENTRY_PREFIXES`
  (шаг 4) завязан на дословный текст `detail=` трёх конкретных
  обработчиков (`fsm.py::_cmd_approve`, `fsm_advance.py::tests_writing`);
  новый легитимный первый вход в `in_dev`/`spec_writing`/`tests_writing`,
  заведённый будущей задачей, БЕЗ добавления его текста в этот список
  снова наступит на тот же класс регрессии, что и AC-7. Смягчение:
  список — единственное место, которое нужно тронуть (одна константа),
  и докстринг `_role_step_since_state_entry`/`_is_legit_first_entry_detail`
  прямо называет источник и способ проверки полноты (`grep -n
  'set_state(conn, task_id, "in_dev"' orchestrator/*.py` и аналоги для
  двух других состояний).
