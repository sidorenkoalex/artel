# PLAN: регрессия №13 — после замечаний ревью `auto` запускает разработчика, а не переход

## Подход

Два независимых рубежа одного класса регрессии («артефакт роли новее
события возврата — иначе шаг роли», ANSWER-2 п.2):

1. **`orchestrator/auto.py` — журнальный рубеж (AC-1/AC-2/AC-4 часть
   auto/AC-5/AC-8/AC-9).** Перед предварительным `advance` цикл проверяет:
   если текущая роль (`runner.step_role`) активна в одном из состояний
   `_REWORK_GATE_STATES = ("in_dev", "spec_writing", "tests_writing")`,
   и с ПОСЛЕДНЕЙ записи журнала `state -> <это состояние>` ещё не было
   записи `agent run finished` этой же роли — предварительный `advance`
   НЕ вызывается вовсе, цикл сразу проваливается в блок «запускаем роль»
   (тот же код, что раньше исполнялся только после отказа/готовности
   артефакта). Проверка — чисто журнальная (`store.task_steps`), не
   смотрит НИ на текст detail, НИ на имя предыдущего состояния: это
   намеренно (докстринг AC-2 в приёмке — мутация «проверка по имени
   предыдущего состояния» обязана ловиться) и одним и тем же кодом
   закрывает и AC-1 (прямой `review -> in_dev`), и AC-2/AC-8 (возврат
   через `escalated`), не требуя знания источника возврата.

   `review` НЕ входит в `_REWORK_GATE_STATES`: свежесть его собственного
   вердикта уже держит отдельный, давно существующий механизм
   (`artifacts.fresh_verdict_iteration`/`reviewed_iter`) — это не предмет
   данной задачи, и включение `review` сюда было бы расширением объёма
   без AC под него.

   Именованная причина (AC-4) достаёт номер итерации из detail найденной
   записи регэкспом `итерация (\d+)` — тот же формат, каким `fsm_advance.
   review` уже пишет `f"замечания ревью, итерация {iters}"`; когда такого
   номера в detail нет (acceptance/merge_gate/verifying reject, эскалация
   по другому основанию), причина остаётся именованной, но без
   выдуманного номера.

2. **`orchestrator/fsm_advance.py::in_dev` — git-based рубеж (AC-3/AC-4
   часть fsm_advance/AC-6/AC-7).** Отдельная проверка `_review_rework_
   gate_refuses`, встроенная в САМ гейт `in_dev -> review` (рядом с
   `_capacity_gate_refuses`/`_zones_gate_refuses`): если REVIEW.md
   текущей итерации (артефактная ветка) несёт `status: changes_requested`,
   а последний НЕ-«подтяжка main» коммит кодовой ветки старше коммита
   REVIEW.md — переход отказывает независимо от того, кто его вызвал
   (`auto` или ручной Оператор). Сверка — по времени коммитов (`%cI`,
   `datetime.fromisoformat`), не по sha и не по тексту: REVIEW.md и код
   живут на двух ветках без общего родителя (SPEC требование 3). Коммиты
   «подтяжка main» (`f"{task_id}: подтяжка ..."`, `fsm._pull_main_or_
   escalate`/`_auto_resolve_map_conflict`) явно исключаются из
   «последнего коммита кода» — иначе рутинная подтяжка (единственное, что
   двигало кодовую ветку между итерациями в реальном инциденте, SPEC
   «Контекст») маскировала бы неотработанные замечания под настоящий шаг
   developer.

   Внешний target и недоступный/незаглушенный git (лёгкие песочницы —
   `fake_git`, `disk_backed_show`) дают гейту деградировать в «не
   отказывать» — тот же приём деградации, что уже несёт `fsm._pull_main_
   or_escalate` (`git не ответил -> "fresh"`): отсутствие сигнала не
   значит «код не менялся».

3. **Тесты.** `tests/test_auto_cycle.py::FakeRun` дополнена журналом
   `agent run finished` под ролью, прочитанной ДО эффекта сценария —
   без этого фейк не воспроизводит реальное поведение `runner.cmd_run`
   (SPEC 745: журналирует «agent run finished» на КАЖДЫЙ успешный
   прогон), и новый журнальный рубеж (пункт 1) видел бы «роль никогда не
   отрабатывала» бесконечно для существующих тестов, использующих
   голые `lambda`. Двойного журналирования с `agent_step` (используется
   НОВОЙ приёмочной планкой этой же задачи, который журналирует
   САМ) избегает проверка «уже есть запись с этим action среди строк,
   добавленных за время вызова сценария — не добавляй свою».
   Регресс-тест `AC-9` фиксирует уже корректное поведение `tests_writing`
   без изменения логики (ANSWER-1 п.3).

## Шаги

1. `orchestrator/auto.py`: журнальный рубеж пред-advance
   (`_REWORK_GATE_STATES`, `_role_step_since_state_entry`,
   `_rework_not_addressed_reason`, встраивание в `_cmd_auto`).
2. `orchestrator/fsm_advance.py`: git-based рубеж `in_dev -> review`
   (`_commit_iso_date`, `_latest_developer_commit_iso_date`,
   `_review_rework_gate_refuses`, вызов в `in_dev()`).
3. `tests/test_auto_cycle.py`: `FakeRun` журналирует `agent run
   finished`, не задваивая запись `agent_step`; регенерация
   `docs/codebase-map.md`.

## Влияние на систему

- Новый журнальный рубеж (шаг 1) применяется универсально к ЛЮБОМУ
  входу в `in_dev`/`spec_writing`/`tests_writing` через `store.set_state`
  — включая легитимные «первые» входы (например, `spec_gate -> in_dev`
  при `skip_tests`). В этих случаях PLAN.md/аналогичный артефакт роли
  физически ещё не существует на ветке (роль не запускалась ни разу), и
  до рубежа переход всё равно отказывал бы через существующий узел
  `_read_branch_text_or_refuse` («дерево не на ветке задачи») — рубеж не
  меняет наблюдаемое поведение для этого класса входов, только даёт роли
  шанс раньше одной итерации advance. Единственный класс, где рубеж
  ДОБАВЛЯЕТ шаг роли сверх прежнего поведения без строгой необходимости —
  возврат из `escalated` по НЕ-rework основанию (например, снятие
  эскалации по бюджету) с уже готовым артефактом: тратится один
  дополнительный шаг роли, прежде чем гейт пропустит задачу дальше. Это
  сознательный компромисс в пользу безопасности (ANSWER-2 п.2: «пред-
  advance допустим только когда артефакт роли новее события возврата») —
  дешевле одного лишнего шага, чем повторение регрессии №12/№13.
- `review` НЕ включён в новый журнальный рубеж — его свежесть уже
  защищена `reviewed_iter`/`fresh_verdict_iteration`; включение расширило
  бы объём задачи без AC.
- Git-based рубеж (шаг 2) — ДОПОЛНИТЕЛЬНОЕ условие существующего перехода
  `in_dev -> review`, не новое состояние FSM и не смягчение существующих
  проверок (`_capacity_gate_refuses`/`_zones_gate_refuses`/лок
  `acceptance_tests/` продолжают действовать как раньше, рубеж добавлен
  ПОСЛЕ них). Деградация «git не ответил -> не отказывать» — тот же
  принцип, что уже используют соседние функции того же файла
  (`_pull_main_or_escalate`), не новый прецедент.
- Существующие тесты `tests/test_auto_cycle.py` (40, включая
  неослабляемый `AutoNeverPassesAGateTest`) и `tests/
  test_advance_guard.py` (7) — зелёные без изменения ассертов, кроме
  добавленного журналирования в `FakeRun` (инфраструктурная правка,
  делающая фейк реалистичнее, не тест-специфичная подгонка). Прогнаны
  также `test_advance_refusal_history`, `test_review_freshness`,
  `test_review_registry_gate`, `test_zones_gate`, `test_capacity_gate`,
  `test_branch_freshness_gate`, `test_answer_gate`, `test_answer`,
  `test_invariants`, `test_fsm_branch_correct_status_reads`,
  `test_fsm_draft_mr_reentry`, `test_step_refixation`, `test_fsm_autogate`
  — все зелёные.
- Откат: оба рубежа — чистые дополнительные условия (гейт может
  отказать, где раньше пропускал бы) без побочных эффектов на данные;
  ревёрт коммитов этой задачи полностью восстанавливает прежнее
  поведение.

## Риски

- Regex-эвристика извлечения номера итерации (`итерация (\d+)`) в
  `auto.py` завязана на формат detail, который пишет `fsm_advance.
  review` (`"замечания ревью, итерация {iters}"`); при изменении этого
  формата в будущей задаче сообщение AC-4 останется именованным, но
  потеряет номер (деградация текста, не поведения — тест AC-4 живёт в
  `tests/` и заметит расхождение).
- Git-based рубеж читает `t["branch"]` (код-ветку) через `gitcmd.git` в
  `config.ROOT` — только self-target; для внешнего target рубеж явно
  выключен (тот же довод, что у соседних `_capacity_gate_refuses`/
  `_zones_gate_refuses`).
