# QUESTIONS: регрессия №13 — после замечаний ревью `auto` пропускает шаг developer

## Вопросы

Требование 1 ТЗ (правило для `review -> in_dev`) и требование 3 ТЗ
(второй рубеж на `in_dev -> review` по REVIEW.md changes_requested)
однозначны и подтверждены кодом — по ним вопросов нет. Весь батч — про
требование 2 (обобщение правила на другие возвраты), которое при сверке
с кодом (`orchestrator/fsm.py`, `orchestrator/fsm_advance.py`,
`orchestrator/auto.py`) разошлось с реальными переходами FSM.

1. **Требование 2 называет переход `spec_gate -> spec_writing` (reject
   SPEC) — такого перехода в коде нет вовсе.** `fsm.cmd_reject`
   (`orchestrator/fsm.py:852-891`) обрабатывает только состояния
   `acceptance`, `merge_gate`, `verifying` (все три ведут в `in_dev`);
   для любого другого состояния, включая `spec_gate`, он завершается
   `sys.exit` без смены состояния. Обратного перехода `spec_gate ->
   spec_writing` не существует ни в `cmd_reject`, ни в `cmd_approve`, ни
   где-либо ещё (проверено `grep` по всей кодовой базе и `docs/` —
   везде встречается только прямой `spec_writing -> spec_gate`). Что
   имелось в виду? — варианты:
   A) Пример ошибочен, вычеркнуть его из требования 2 — фикс
      ограничивается реально существующими переходами (см. вопрос 2);
      `spec_gate -> spec_writing` вне объёма этой задачи, потому что
      физически невозможен в текущей системе.
   B) Имелся в виду другой, уже существующий переход с похожим смыслом
      (уточни, какой).
   C) Требуется сначала завести сам переход `spec_gate ->
      spec_writing` (reject SPEC) как новую возможность, а затем уже
      защитить его этим же правилом — тогда это отдельная задача до
      или вместо текущей, не одной SPEC с критичным фиксом регрессии.
   — дефолт: A (вычеркнуть пример, не расширять объём критичного
   фикса добавлением нового перехода FSM, которого раньше не было).

2. **Требование 2 формулирует правило как «для любого возврата в
   состояние роли с непустым основанием переделки», но приводит только
   два реально существующих примера возврата в `in_dev` — `review ->
   in_dev` (требование 1) и `acceptance -> in_dev`.** В коде
   `fsm.cmd_reject` есть ещё два перехода, ведущие в тот же `in_dev` тем
   же путём («возврат Оператора с причиной») и проходящие через тот же
   общий обработчик `fsm_advance.in_dev` (значит подверженные той же
   уязвимости — PLAN.md status: ready не тронут, пред-advance `auto`
   пропускает шаг developer): `merge_gate -> in_dev` (reject, `fsm.py:
   855-864`) и `verifying -> in_dev` (reject, `fsm.py:865-877`). Входят
   ли эти два перехода в объём правила требования 1/2 (обязателен
   свежий шаг developer после возврата, иначе пред-advance `auto` не
   выполняется)? — варианты:
   A) Да — правило применяется к ЛЮБОМУ возврату в `in_dev` с указанием
      причины, независимо от того, откуда он произошёл (`review`,
      `acceptance`, `merge_gate`, `verifying`): общий обработчик
      `in_dev` не различает источник возврата, значит и защита не
      должна его различать — иначе `merge_gate`/`verifying` reject
      останутся с тем же классом регрессии, что и породил эту задачу.
   B) Нет — только два явно названных ТЗ примера (`review`,
      `acceptance`); `merge_gate`/`verifying` reject — вне объёма,
      чинить отдельной задачей при необходимости.
   — дефолт: A (симметрия механики: одна причина бага — общий
     обработчик `in_dev`, не знающий об источнике возврата — должна
     закрываться одним общим правилом на все источники, иначе фикс
     заведомо неполон и регрессия повторится на необойдённых путях).

3. **Требование 2 называет «`tests_writing` после отказа
   трассируемости» как случай, требующий того же правила — но по факту
   кода такого случая-бага сегодня нет.** Отказ трассируемости AC в
   `fsm_advance.tests_writing` (`errors` не пусто) НЕ меняет состояние
   — задача остаётся в `tests_writing`, `set_state` не вызывается.
   `orchestrator/auto.py:322-349` уже трактует ЛЮБОЙ журналируемый отказ
   вне `in_dev` (включая этот) как класс, где роль обязана получить шанс
   на КАЖДОЙ итерации — эта логика закреплена явным комментарием и двумя
   тестами (`test_review_iterations_are_passed_without_the_operator`,
   `test_fresh_task_first_developer_step_still_runs`) именно чтобы не
   получить обратную регрессию: роль вообще перестаёт запускаться после
   первого же журналируемого отказа. То есть skip-ahead-бага (обхода
   роли по старому артефакту) для `tests_writing` сегодня нет — test_author
   и так перезапускается каждую итерацию. Что нужно сделать с этим
   пунктом? — варианты:
   A) Убрать пункт из требования 2 — поведение уже корректно, менять
      нечего; в SPEC зафиксировать явным регресс-тестом инвариант «после
      отказа трассируемости `auto` всё равно запускает test_author», не
      новую логику.
   B) Имеется в виду другой сценарий — например, возврат из `escalated`
      в `tests_writing` (`fsm.py:800-833`, `back = escalated_from`) после
      ответа Оператора на эскалацию test_author, где пред-advance
      МОЖЕТ повторно прочитать те же незакрытые маркеры `AC-n: escalate`
      и уйти обратно в эскалацию, а не дать test_author шанс — уточни,
      если это и есть искомый случай, тогда нужен отдельный AC под него.
   — дефолт: A (убрать пункт, зафиксировать текущее корректное поведение
     тестом, не менять код без найденного реального дефекта).

## Контекст
Сверка ТЗ с кодом (`orchestrator/auto.py`, `orchestrator/fsm.py`,
`orchestrator/fsm_advance.py`) подтвердила требования 1, 3, 4, 5
буквально — под них SPEC пишется без вопросов после ответа на этот
батч. Требование 2 нуждается в уточнении объёма (см. вопросы выше) —
без него нельзя разметить AC для SPEC.md, не совершив домысливание
несуществующего перехода FSM или произвольного выбора между «только 2
явных примера» и «все 4 источника возврата в `in_dev`».
