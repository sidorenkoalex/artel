# SPEC: D0 — внешний доверенный проект без песочницы: профиль чужого стека и чистое окружение тестов

## Контекст
ADR-0023, «Поправка 16.10.2026 (вторая)»: песочница (D1а, SPEC
01M51YKZNES22DZQY13D3QKF89) отложена, внешний доверенный проект (sled)
исполняет тесты на хосте, как артель. Сегодня пульт чужой стек гонять не
умеет: `_pytest_command` (`orchestrator/acceptance.py:35-65`) всегда ставит
интерпретатор venv пульта и `-p timeout`, полный набор берёт `<корень>/tests`
и дописывает `-n … -p xdist`; у sled тесты в `backend/tests`, запуск
`uv run pytest`, плагинов `pytest-timeout`/`pytest-xdist` нет. `_pytest_env`
(`acceptance.py:69-89`) отдаёт тестам копию всего окружения пульта, включая
токены. Точечные прогоны через `subprocess.run(timeout=…)` на таймауте
снимают только прямого потомка — дочерний python `uv run` остался бы жить.
Автогейт приёмки и `approve` на acceptance зовут полный набор без команды
профиля (`acceptance.acceptance_suite`, `docs/backlog.md:185`).

## Требования

1. `test_profile` (`orchestrator/targets.py`, `PROFILE_FIELDS`) получает три
   необязательных подполя; профиль без них остаётся правильным и ведёт себя
   как сейчас:
   - `runner`: `pult-pytest` (по умолчанию, сегодняшнее поведение) |
     `pytest-own`; иное значение — отказ проверки;
   - `workdir`: каталог прогона относительно корня репозитория;
     `targets.check` отказывает абсолютному пути и пути с сегментом `..`;
   - `env`: блочное отображение строк (новый вид подполя `mapping`;
     `orchestrator/yamlmini.py` не меняется); `targets.check` отказывает
     имени из точного перечня секретов — `secret_env_names()` провайдеров,
     `GITHUB_TOKEN`, `GH_TOKEN`, — сверка по точному имени.
   Подполя доходят до потребителей полями `project_profile.Profile`
   (`orchestrator/project_profile.py`). Поле `sandbox` не вводится.
2. В момент прогона `realpath` каталога `workdir` обязан лежать внутри
   дерева прогона; иначе прогон не запускается, а место запуска возвращает
   именованный отказ (текст называет `workdir` и причину).
3. `runner: pytest-own`: argv — команда профиля как есть, без подстановки
   интерпретатора пульта, без `-p timeout`/`-o timeout=…` и без
   `-n …`/`-p xdist`; пульт по-прежнему дописывает свои аргументы гейтов
   (`--collect-only -q`, `--junitxml`, `-o junit_logging=system-out`,
   `-p no:cacheprovider`) и аргументы, которые сегодня дописывает конкретное
   место запуска. Рабочий каталог прогона — `workdir` (без него — корень
   дерева прогона).
4. При `pytest-own` все пути профиля (`long_lived_dir`, долгоживущие пути,
   `workdir`) отсчитываются от корня репозитория; пульт переводит их в пути,
   верные из `workdir`. Полный набор берёт каталог `long_lived_dir`, а не
   `<корень>/tests`.
5. Окружение тестов при `pytest-own` состоит только из: `PATH` пульта;
   временного `HOME` (новый каталог на каждый прогон, удаляется после
   прогона, в том числе по таймауту и исключению); `TMPDIR`; `LANG`/`LC_ALL`
   при наличии у пульта; служебных переменных, которые сегодня ставит место
   запуска (`PYTHONPYCACHEPREFIX`, `PYTHONUNBUFFERED`, переменные плагина и
   отчёта двустороннего прогона); `test_profile.env`. Остальное окружение
   пульта, в том числе токены и переменные провайдеров, не передаётся. При
   `pult-pytest` окружение прежнее.
6. Таймаут при `pytest-own`: каждое место запуска (`acceptance.run`,
   `collect`, `run_repeat`, `run_plank`, два пути `_run_full_suite_now`,
   `_run_full_suite_to_log`, `two_sided._run_side`) запускает прогон в
   собственном сеансе и по таймауту и на любом исключении снимает всю группу
   процессов — как сегодня полный набор (`acceptance.py:1324-1337`,
   `:1373-1391`). При `pult-pytest` поведение прежнее.
7. Один источник команды профиля: автогейт приёмки (`fsm_autogate.py`),
   `approve` на acceptance (`fsm.py`), гейт мержа (`fsm_merge_gate.py`),
   `suite-run`, `plank-run`, `amend-tests`, двусторонний прогон и прогоны
   `pull` получают одни и те же `command`, `runner`, `workdir`, `env`
   профиля проекта задачи — через тот же канал, которым сегодня передаётся
   `command` (например, `Profile` вместо списка). `preflight`
   (`orchestrator/preflight.py`) и `acceptance-dry-run`
   (`orchestrator/dry_run.py`) pytest не запускают — их модули вне зон
   и не правятся; если разработчик найдёт в них запуск прогона, это
   эскалация. Для прогонов без задачи и для артели — сегодняшнее поведение.
   В вызывающих модулях меняется только передача профиля вместо команды,
   без изменения логики гейтов.
8. Ключ повторного использования итога полного набора (gate- и base-итог,
   `acceptance.py:1609-1640`, `:1740-1758`, `:1790-1792`;
   `suite_run.py:511,533`) при `pytest-own` учитывает `runner`, `workdir`
   и `env`; при `pult-pytest` ключ не меняется ни на байт.
9. До правки мест запуска тестами зафиксированы argv, `cwd` и окружение
   каждого из восьми мест запуска требования 6 для артели; после правки они
   неизменны.
10. Тесты детерминированы, без сети и без `uv`: учебный проект во временном
    каталоге с `runner: pytest-own` и командой, которая запускает pytest
    интерпретатором тестов через обёртку-скрипт, порождающий дочерний
    процесс.

## Критерии приёмки

AC-1. У артели (профиль без `runner`/`workdir`/`env`) argv, `cwd` и
окружение каждого из восьми мест запуска (`acceptance.run`, `collect`,
`run_repeat`, `run_plank`, два пути `_run_full_suite_now`,
`_run_full_suite_to_log`, `two_sided._run_side`) совпадают со значениями,
зафиксированными до правки.

AC-2. Учебный проект с `pytest-own`: тест, читающий `os.environ`, не видит
ни одной переменной окружения пульта вне перечня требования 5 (в том числе
подставленной в окружение пульта переменной-маркера и токенов), а
переменные `test_profile.env` видит.

AC-3. Учебный проект с `pytest-own`: `HOME` в тесте — временный каталог,
отличный от `HOME` пульта, и после прогона его нет на диске.

AC-4. Учебный проект с `pytest-own`: argv прогона — команда профиля без
интерпретатора пульта, без `-p timeout`, без `-n` и без `-p xdist`, а
рабочий каталог — `workdir`.

AC-5. Учебный проект с `pytest-own` и `workdir`: полный набор собирается из
`long_lived_dir` (путь от корня репозитория, переведённый в путь из
`workdir`), а не из `<корень>/tests`.

AC-6. По таймауту точечного прогона учебного проекта (обёртка порождает
дочерний процесс) дочерний процесс обёртки после возврата из места запуска
не остаётся жить.

AC-7. Автогейт приёмки, `approve` на acceptance и гейт мержа запускают
набор учебного проекта той же командой (argv) и в том же каталоге, что
`suite-run` той же задачи.

AC-8. `targets.check` отказывает `test_profile.env` с именем секрета
(`GITHUB_TOKEN`, `GH_TOKEN`, имя из `secret_env_names()` провайдера) и
`workdir` с сегментом `..` или абсолютным путём; профиль без новых подполей
проходит проверку.

AC-9. `workdir`, чей `realpath` в момент прогона выходит за дерево прогона
(например, символическая ссылка наружу), даёт именованный отказ, и прогон
не запускается.

AC-10. Итог полного набора при `pytest-own`, полученный с другим `workdir`
или другим `env`, не засчитывается повторно; ключ итога при `pult-pytest`
совпадает с ключом до правки.

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны — 14 (порог ≥ 5); `budget_usd` — 50
(порог ≥ $30). По калибровке (`config.BUDGET_CALIBRATION_TABLE`) задача
«8 и более файлов» — ~$85 либо деление; рамка ТЗ — $50.

Предлагается **нарезка на 3 части** по границам зон (ниже, «## Деление»):

1. **Профиль: подполя и фиксация argv** — `targets.py`, `project_profile.py`,
   `tests/`. Механика, на которую опираются остальные: поля `Profile` и
   проверка `targets.check`, плюс тесты-фиксация argv/`cwd`/окружения
   восьми мест запуска артели (требование 9 требует их ДО правки мест
   запуска). Самостоятельно мержима: новые подполя необязательны, никто их
   ещё не читает, поведение артели не меняется, фиксирующие тесты зелёные
   на текущем коде.
2. **Раннер `pytest-own` в местах запуска** — `acceptance.py`,
   `advance_gates/two_sided.py`, `tests/`. Требования 2–6, 8, 10 на уровне
   мест запуска: они принимают профиль (или его поля) рядом с прежним
   `command`. Самостоятельно мержима: вызывающие модули ещё передают только
   `command`, у артели путь `pult-pytest` прежний — фиксация части 1
   держит его неизменность.
3. **Один источник профиля у вызывающих** — `advance_gates/acceptance.py`,
   `fsm_merge_gate.py`, `suite_run.py`, `plank_run.py`, `pull.py`,
   `amend.py`, `notes.py`, `fsm.py`, `fsm_autogate.py`, `tests/`.
   Требование 7 и AC-7: передача профиля вместо команды без изменения
   логики гейтов. Мержима последней: опирается на приём профиля частью 2.

Альтернатива — монолит: атомарности нет (каждая часть оставляет систему
рабочей), поэтому монолит здесь обосновывается только ценой согласования
трёх задач против одной; по калибровке ему нужен потолок ~$85 при рамке
$50. Решение и рамки частей — за Оператором на гейте SPEC.
