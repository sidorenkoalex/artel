# SPEC: A7 — артель как внешний target: пин версии, шаг обновления, внешний флоу

## Контекст

Артель сегодня — «особый случай догфуда»: её задачи ведут первичку
артефактов прямо в `tasks/` пульта, в одной ветке `task/*`, а мерж
задачи (`approve` на `merge_gate`) чекаутит и двигает вперёд ГЛАВНУЮ
копию пульта (`config.ROOT`) — ту самую, из которой Оператор запускает
все последующие команды. Предпосылки (M1 — артефактная ветка/снапшот,
B1b — Draft-MR-флоу) готовы; задача снимает с артели этот особый
статус: она подключается в `targets.yaml` и живёт тем же внешним
флоу, что любой целевой проект, а конвейер, меняющий собственный код,
перестаёт менять код, которым исполняется, посреди работы — новая
механика пина запущенной версии (Stage0/Stage1).

Ответ Оператора (`ANSWER-1.md`) выбрал буквальное прочтение: пин
реально удерживает `config.ROOT` от изменения при мерже (не просто
предупреждает о расхождении), способ — плотницкая запись merge-
коммита в объектную базу main артели, без чекаута рабочего дерева
`config.ROOT` (по образцу `artifact_branch.write_commit`); мандат
явно включает правку проверки `root_branch != config.MAIN_BRANCH`
(`orchestrator/fsm_merge_gate.py`) и смежных допущений «главная копия
на main» — отдельный ADR не требуется. Границы мандата: инвариант 12
(мержит только `approve` из `merge_gate`), инвариант 19 (merge только
при зелёном CI) и инвариант входа T056 («пульт исполняется только из
главной копии») не ослабляются — меняется способ записи мержа, не эти
проверки.

## Требования

1. `targets.yaml` объявляет `artel` обычной записью target (forge
   github, свой url, base, token_slot, no_paths, merge_gate: operator)
   — без пометки «особый случай» в логике разбора.
2. Места пульта, различающие поведение по `target ==
   config.DEFAULT_TARGET` («догфуд-ветки»), переводятся на ту же
   логику, что применяется к любому внешнему target: doctor
   (target-layout, target-wrapper, remote-empty, base-branch,
   recovery, orphan-scan), `catalog.py` (заведение задачи),
   `fixation.py`, `checkpoint.py`, `cleanup.py`, `runner.py`
   (`role_cwd`), `fsm.py`/`fsm_advance.py`/`fsm_merge_gate.py`
   (self-ветки чтения артефактов и снапшота при закрытии), `store.py`
   (дефолт target в схеме) — кроме случаев, для которых общая логика
   к самой артели структурно неприменима: там решение — явное (ниже,
   в критериях приёмки), не молчаливый skip.
3. Новые задачи артели (заведённые после мержа этой задачи) ведут
   первичку артефактов в `.artel/projects/artel/` вне git пульта той
   же механикой M1/Б₃, что и любой внешний target: артефактная ветка
   пульта при жизни задачи, снапшот в `refs/artifacts/<id>` артели
   при закрытии (`done`/`killed`). В кодовые ветки и main артели
   артефакты новых задач не попадают. Исторические задачи в `tasks/`
   пульта не переносятся и не трогаются этой задачей.
4. Stage0 — пин запущенной версии: версия оркестратора, которой
   исполняются команды из главной копии пульта (`config.ROOT`),
   зафиксирована явным пином на sha. Переход `merge_gate -> done`
   (включая его служебные под-шаги — регенерацию карты кодовой базы
   и генерацию RETRO) не меняет рабочее дерево и HEAD `config.ROOT`.
   Единственный способ продвинуть `config.ROOT` вперёд — отдельная,
   вне цикла FSM задачи, операторская команда обновления пина.
5. Stage1 — шаг обновления: doctor показывает расхождение пин ↔
   текущий main артели информационно (не блокирует и не проваливает
   прогон) и печатает точную операторскую команду обновления пина;
   сам doctor пин не обновляет.
6. Обновление пина журналируется: кто обновил, когда, старый и новый
   sha.
7. Изменения защищённых путей (`config.PROTECTED_PATHS`) в диффе
   задачи артели подсвечиваются в Draft-MR задачи (комментарий или
   пункт чек-листа адаптера) — в дополнение к существующему
   предупреждению CI-job protected-paths, не взамен него.
8. Задача артели проходит полный внешний флоу end-to-end (заведение
   -> артефактная ветка -> Draft-MR -> verifying -> merge_gate ->
   done) без единой записи артефактов новой задачи в кодовые ветки
   или main пульта; существующие тесты, включая инварианты 12, 19 и
   T056, остаются зелёными без ослабления их проверяемого
   утверждения.

## Критерии приёмки

AC-1. `targets.yaml` несёт запись `artel` (forge, url, base,
token_slot, no_paths, merge_gate) без ветвления «особый случай» в
коде, который её разбирает (`orchestrator/targets.py`).

AC-2. `doctor.check_target_layout`, `check_target_wrapper`,
`check_remote_empty`, `check_base_branch` для `target == "artel"`
проверяют `.artel/projects/artel/` и возвращают тот же класс
результата (ok/warn/fail по тому же основанию), что и для любого
другого объявленного в `targets.yaml` target — без ветки вида
`if target == config.DEFAULT_TARGET: return Check(..., "skip"/"ok",
"догфуд...")`.

AC-3. `doctor.recovery_check` для `target == "artel"` сверяет sha
`.artel/projects/artel/` (артефактный репозиторий новых задач артели)
той же логикой, что и для любого внешнего target. Сверка HEAD самой
главной копии пульта (`config.ROOT`) в объём `recovery_check` не
входит — это отдельная забота doctor-проверки пина (AC-13); явное
решение, а не молчаливый skip.

AC-4. `doctor.check_orphans` сканирует на сироты обе директории
артели: исторический `tasks/` пульта (без изменений) и новый
`.artel/projects/artel/tasks/` — задача или ветка без строки БД в
любой из них заводит существующий incident-алерт тем же порядком,
что и сегодня для внешних target.

AC-5. Заведение НОВОЙ задачи артели (`cmd_new` без `target` или с
`target=artel`) идёт тем же путём, что заведение задачи любого
объявленного target — прежний однобраншевый flow заведения
(`_new_dogfood`) для новых задач больше не вызывается.

AC-6. `fixation.py`, `checkpoint.py`, `cleanup.py`, `runner.py`
(`role_cwd`), `fsm.py`/`fsm_advance.py`/`fsm_merge_gate.py` для
НОВОЙ задачи артели читают и пишут артефакты через артефактную ветку
пульта и снапшот-механику M1 (та же, что для любого внешнего
target), не через прямую запись в её ветку задачи. Дефолт `target` в
схеме `store.py` не меняется — историческая обратная совместимость
(задачи без явного target в БД) сохраняется.

AC-7. Полный сценарий одной новой задачи артели (заведение ->
артефактная ветка пульта при жизни -> Draft-MR -> verifying ->
merge_gate -> done) проходит без единой записи `tasks/<её id>/` в
код-ветках или main пульта — артефакты живут только в артефактной
ветке пульта и, после закрытия, в `refs/artifacts/<id>` артели.

AC-8. Переход `merge_gate -> done` (`approve`) записывает
merge-коммит в `refs/heads/main` артели через объектную базу git
(плотницки), не через `git checkout main` рабочего дерева
`config.ROOT`: рабочее дерево и HEAD `config.ROOT` идентичны
непосредственно до и сразу после успешного `approve`.

AC-9. Регенерация карты кодовой базы и генерация RETRO, выполняемые
тем же переходом (`fsm_postmerge.py`), тоже не меняют рабочее дерево
и HEAD `config.ROOT` — их коммиты попадают в main той же
неchekaut-механикой, что и сам merge-коммит (AC-8).

AC-10. Проверка `root_branch != config.MAIN_BRANCH`, сегодня
отказывающая `approve`, если главная копия пульта не на `main`
(`orchestrator/fsm_merge_gate.py`), убрана или заменена проверкой, не
зависящей от текущего чекаута `config.ROOT` — `approve` больше не
требует, чтобы главная копия стояла на `main`.

AC-11. Инвариант входа «пульт исполняется только из главной копии, не
из git-worktree» (`orchestrator/artel.py::_refuse_if_worktree`, T056)
не изменён и не ослаблен — существующий тест на него остаётся зелёным
без правки его проверяемого утверждения.

AC-12. Обязательный тест «merge не меняет запущенную версию»: после
успешного `approve` на `merge_gate` рабочее дерево и HEAD
`config.ROOT` остаются на зафиксированном пином sha, даже когда main
артели ушёл вперёд этим самым merge — уже запущенный процесс и любой
НОВЫЙ вызов `artel.py` из `config.ROOT` до операторского обновления
пина исполняются тем же кодом, что и до merge.

AC-13. `doctor` печатает отдельную информационную проверку:
расхождение между пином `config.ROOT` и текущим HEAD main артели —
называет оба sha и точную команду обновления пина. Статус этой
проверки никогда не `fail` и не блокирует прогон `doctor`.

AC-14. Отдельная операторская команда обновляет пин (продвигает
рабочее дерево и HEAD `config.ROOT` до нового sha main) и пишет
журнальную запись с операторской идентичностью, старым и новым sha,
временем обновления; `doctor` эту команду сам не вызывает.

AC-15. Существующие тесты инвариантов 12 (мержит только `approve` из
`merge_gate`) и 19 (merge требует зелёного CI головного коммита ветки
задачи) остаются кодированы и зелены без ослабления проверяемого ими
утверждения.

AC-16. Draft-MR задачи артели, диф которой затрагивает хотя бы один
путь из `config.PROTECTED_PATHS`, несёт комментарий или пункт
чек-листа адаптера, называющий затронутые защищённые пути —
независимо от предупреждения, которое уже печатает CI-job
protected-paths.

AC-17. Полный набор `tests/` пульта зелёный после реализации,
включая новые/изменённые тесты, покрывающие AC-1..AC-16.

## Не входит

- Д1 (нейтральное имя системы) — следующим шагом, «тихое окно после
  A7».
- M2 (sync с origin).
- Уборка исторических задач в `tasks/` пульта — отдельной задачей
  после A7 (решение Оператора V7-Q2).
- Разделение PAT и branch protection (триггер №24, этап 2 панели).
- Публикация артефактов в ветку `artel` целевых проектов (отложено
  ADR-0003).
- Изменение состава `config.PROTECTED_PATHS`/`no_paths` артели — AC-16
  подсвечивает существующий список, не расширяет и не сужает его.
- Отдельный ADR по переносу механики `merge_gate` на плотницкую
  запись — не требуется (мандат Оператора, `ANSWER-1.md`, вопрос 1).
