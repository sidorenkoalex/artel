# ANSWER-1: ответ Оператора

## Ответы

Вопрос 1 — вариант B, с мандатом.

Пин реально удерживает главную копию (`config.ROOT`) от изменения
при мерже: механика approve merge_gate переносится на запись в
объектную базу git без чекаута рабочего дерева (по образцу
`artifact_branch.write_commit`); рабочее дерево двигает вперёд только
отдельная журналируемая операторская команда обновления пина.

Мандат этим ответом: правка проверки `root_branch !=
config.MAIN_BRANCH` в `orchestrator/fsm_merge_gate.py` и сверка
смежных допущений «главная копия на main» (`fsm_advance.py`,
`cleanup.py`, `artel.py`) ВХОДЯТ в объём A7 — отдельный ADR не
требуется. Границы мандата: защиты не ослабляются — инвариант 12
(мержит только approve из merge_gate) и инвариант 19 (merge только
при зелёном CI) сохраняются со своими тестами; инвариант входа
«пульт исполняется только из главной копии» (T056) сохраняется —
меняется не он, а способ записи мержа. Ветко-корректные чтения
артефактов (T031/T047) уже не зависят от чекаута — вариант B
продолжает это направление.

Вопрос 2 — дефолт принят: «Зоны» ТЗ — ориентировочный, не
исчерпывающий список. SPEC перечисляет требования по фактически
затронутым местам (включая `fixation.py`, `checkpoint.py`,
`cleanup.py`, `runner.py`, `fsm.py`/`fsm_advance.py`/
`fsm_merge_gate.py`, `store.py` — self-ветки), PLAN разработчика
называет точный список правок. Требование 2 не сужается.

Общее: конфликт зон с активными задачами волны 2г по ходу
реализации — эскалация, как и записано в ТЗ; старт реализации —
после разгрузки волны.
