# REVIEW: A7 — артель как внешний target: пин версии, шаг обновления, внешний флоу

## Фаза A — проверка плана

Таблица покрытия PLAN.md полна (все 8 требований SPEC отображены на шаги
1-4), подход не противоречит M1/ADR-0003 в целом. Шаги (особенно шаг 1 и
шаг 2) по объёму — фактически «сделать всё разом» (7+ модулей self-пути,
плюс ~30 файлов тестов), что обычным правилом review-checklist («шаги —
проверяемые единицы размера MR») не приветствуется — но это уже
рассмотрено и принято Оператором отдельно (эскалация «гейт ёмкости diff»
в этом же PLAN.md, решение — вариант A, коммит `e34d048`, поднятие
`REVIEW_SNAPSHOT_DIFF_MAX_BYTES`); повторно не блокирую этим же
основанием.

Существенная находка Фазы A — ниже, в замечании R1-F1: сам «Подход» PLAN
корректно формулирует архитектурное допущение («код артели физически
живёт в `config.ROOT`»), но код `orchestrator/runner.py::role_cwd`
реализует это допущение НЕВЕРНО (см. Фазу B) — расхождение между текстом
плана и кодом, а не дефект самого плана.

## Замечания

- **blocker** — `orchestrator/runner.py:379-401` (`role_cwd`) — генерализация
  `role_cwd` отправляет роль НОВОЙ задачи артели в `.artel/projects/artel/workspace`
  (каталог без какой-либо git-связи с `config.ROOT`), тогда как ВСЯ
  остальная механика мержа/гейтов для self-target по-прежнему жёстко
  требует, чтобы кодовая ветка задачи (`tasks.branch`) физически
  существовала как локальная ветка внутри репозитория `config.ROOT`
  (`gitcmd.git()` всегда работает с `cwd=config.ROOT`, `orchestrator/gitcmd.py:16`).
  Это не домысел ревьювера — само же PLAN.md прямо формулирует ожидаемую
  архитектуру в разделе «Подход»: «код задачи (там, где он физически
  будет — `config.ROOT` для артели, чужой клон для остальных) заводит
  роль-разработчик первым коммитом внутри своего шага» — и `orchestrator/snapshot.py::_target_workspace`
  (новый код этой же задачи) явно СПЕЦИАЛЬНО обрабатывает
  `config.DEFAULT_TARGET`, возвращая `config.ROOT` (не
  `config.PROJECTS/artel/workspace`) ровно по этой причине: «у артели
  структурно нет отдельного клона себя самой». `role_cwd` — тот же класс
  необходимости, но эту специфику не удержал.

  Последствие — полный отказ реального (не тестового) прогона задачи
  артели дальше первого агентного шага, во всех местах, которые требуют
  ветку в `config.ROOT`:
  1. `orchestrator/github_adapter.py:74` (`ensure_draft_mr`, `git push -u
     origin branch`) — «src refspec branch does not match any», ветки
     нет локально в `config.ROOT`.
  2. `orchestrator/github_adapter.py:134-149` (`ensure_head_in_origin`,
     предусловие КАЖДОГО approve `merge_gate` и входа в `verifying`) — та
     же причина.
  3. `orchestrator/github_adapter.py:42-47` (`_touched_protected_paths`,
     AC-16) — `gitcmd.git("diff", ...)` не находит ветку, деградирует к
     пустому списку («git не ответил — не отказ») — AC-16 для
     реальной задачи молча перестаёт работать, а не «не входит», как
     задумано.
  4. `orchestrator/fsm_merge_gate.py::_cmd_approve_merge_gate` (плотницкий
     merge, Stage0) — `gitcmd.in_repo(scratch, "merge", "--no-ff",
     branch, ...)`, где `scratch` — worktree ИМЕННО `config.ROOT`, не
     видит ветку, реально созданную в отдельном каталоге workspace.
  5. `orchestrator/fsm_advance.py:406-463` (`_capacity_gate_refuses`,
     нарочно НЕ генерализован PLAN'ом именно из-за допущения «код в
     config.ROOT») — воспроизведено буквально при прогоне полного
     набора `tests/` этой сессией: `[T001] переход отклонён: гейт
     ёмкости: git не ответил на diff снимка (main...task/t001-x) —
     сверка размера невозможна: fatal: bad revision 'main...task/t001-x'`
     — тот же класс отказа, который получит ЛЮБАЯ реальная новая задача
     артели на переходе `in_dev -> review`, если её код действительно
     остался в `role_cwd()`, а не был вручную заведён в `config.ROOT`.
  6. `orchestrator/fsm.py:127-213` (`_pull_main_or_escalate`, тоже НЕ
     генерализован по тому же допущению) — то же самое: `workspace.ensure`
     создаёт worktree ИЗ `config.ROOT`, не видит ветку из
     `.artel/projects/artel/workspace`.
  7. `orchestrator/checkpoint.py:12-152` (три WIP-чекпоинта, `commit_
     timeout_checkpoint`/`commit_abnormal_checkpoint`/`commit_pause_
     now_checkpoint`) — они по-прежнему коммитят `workspace.path(task_id)`
     (тот же старый worktree-адрес), который теперь никогда не заводится
     для новой задачи артели (`_new_dogfood`/старый `role_cwd` убраны) —
     на реальном таймауте/аварийном завершении/`pause --now` шага
     развработчика WIP, реально лежащий в `.artel/projects/artel/workspace`,
     НЕ будет зачекпоинчен вовсе: `git -C <несуществующий каталог> add -A`
     просто откажет, функция молча вернёт «нечего коммитить» — именно тот
     класс потери WIP, ради устранения которого заводились T041/T074.
  8. `orchestrator/runner.py:158-168` (в `_cmd_run`, `if target ==
     config.DEFAULT_TARGET: on_branch = workspace.on_task_branch(...)`) —
     осиротевшая проверка: ссылается на worktree, который после этой же
     генерализации `role_cwd` никогда не заводится для новой задачи
     артели — сегодня безвредна (тихо возвращает `None`, «сверять не с
     чем»), но явный сигнал, что генерализация `role_cwd` не была
     сверена с остальными self-специфичными местами того же файла.

  Ни один из новых приёмочных тестов (AC-5/AC-6/AC-7/AC-8/AC-9/AC-12/AC-15,
  `tasks/01M1H224X5A8W159MKF1Q24R5Y/acceptance_tests/`) этого не ловит,
  потому что все они заводят кодовую ветку ЗАДАЧИ вручную прямо в
  `self.root` (`git checkout -b`/`git commit`), полностью в обход
  `runner.cmd_run -> role_cwd` — то есть в обход именно того пути,
  который сломан. `test_ac6_artifacts_via_m1_mechanics.py::
  RoleCwdUsesProjectsWorkspaceForArtelTest` проверяет только то, ЧТО
  возвращает `role_cwd` (изолированно), не проверяя, что остальная
  система остаётся работоспособной с этим возвратом. `test_ac7_full_
  scenario_no_pult_writes.py` прямым текстом комментирует ровно эту
  замену («роль-разработчик пишет код ПУЛЬТА напрямую в config.ROOT») —
  то есть тест физически кодирует ПРАВИЛЬНОЕ намерение архитектуры и
  тут же его нарушает, потому что реальный `role_cwd` этому намерению
  не соответствует.

  Предложение: `role_cwd` обязан сохранить self-специфичную ветвь для
  `target == config.DEFAULT_TARGET` (по образцу уже существующего
  `snapshot.py::_target_workspace` в этом же диффе) — либо возвращать
  `config.ROOT` напрямую, либо (для изоляции параллельных `auto`,
  инцидент 26-27.08, ради которого T045 вообще завёл механику worktree)
  сохранить прежний путь через `workspace.ensure`/`workspace.path`.
  Если ни один из вариантов не укладывается в мандат SPEC требования 2
  (буквально требующего generic-путь для `runner.py role_cwd`) без
  противоречия с допущением «код в config.ROOT» — это повод для
  эскалации Оператору за разрешением конфликта требования 2 и
  архитектурной реальности self-target, а не для тихого выбора одной
  стороны.

- **major** — Соответствие требованию 8/AC-7 фактически не проверено
  сквозным путём (см. blocker выше) — сама секция «Проверено
  исполнением» PLAN.md перечисляет только зелёные прогоны тестов и не
  включает ни одной попытки прогнать реальный `artel.py run`/`auto` на
  новой задаче артели до `merge_gate`. Рекомендация на будущее (не
  блокирует само по себе, отдельно от blocker выше) — для задач такого
  масштаба (смена механики исполнения самого пульта) включать в
  «Проверено исполнением» хотя бы один прогон через реальный CLI-вход
  (`artel.py new` → `run`/`auto` с подложным `claude`), а не только
  юнит/приёмочные тесты, специально сконструированные в обход
  проверяемого пути.

## Предложения системе

- Класс «self-target на самом деле не имеет отдельного клона, но
  generic-путь молча предполагает, что имеет» — в этой же задаче он
  корректно учтён в `snapshot.py::_target_workspace`, но пропущен в
  `runner.py::role_cwd` (R1-F1) и в WIP-чекпоинтах `checkpoint.py`. Когда
  задача генерализует self-путь по многим модулям сразу (Б1 из PLAN),
  стоит явно сверять КАЖДОЕ обобщаемое место с одним и тем же
  архитектурным допущением (здесь — «код артели живёт в config.ROOT»),
  а не полагаться на то, что раз для одного модуля решение найдено
  верно, для соседнего оно применится по аналогии само.
