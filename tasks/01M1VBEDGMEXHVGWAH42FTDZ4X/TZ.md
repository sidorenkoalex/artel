# ТЗ: budget под живым шагом и возврат из эскалации без холостого шага роли

# ТЗ: `budget` под живым шагом и возврат из эскалации без холостого шага роли

Источник: аудит обходных сценариев Оператора 06.09. За день пять раз
ставился внешний «отложенный подъём бюджета» (цикл ожидания конца шага
роли, затем `budget N`), потому что `cmd_budget` отказывает, пока lease
держит живой шаг («задачу ведёт сессия …, heartbeat N сек назад»), а
предупреждение «больше 70 %» приходит уже во время шага. Итог без
обхода — гарантированная эскалация по бюджету сразу после шага. Второй
дефект того же пути: возврат из эскалации (по бюджету, вопросу,
конфликту подтяжки) идёт в `escalated_from` либо `in_dev`, и рубеж
«возврат не отработан: нет шага developer после возврата» требует новый
шаг роли, даже если шаг был сдан до эскалации — 06.09 четыре холостых
шага developer «менять нечего» по $1.3–1.8 (01M1TQ0ZCY трижды,
01M1TQ0X14), а после `escalated_from = review` с approved-вердиктом
итерации 3 — ещё и четвёртый прогон ревьювера ($0.77). Строки копилки
05.09 («возврат из escalated перезапускает разработчика», второй вид
06.09).

Требуется:
1. `budget <id> <usd>` принимается под живым шагом: новый потолок
   пишется сразу (`tasks.budget_usd`), запись журнала «бюджет изменён»
   с пометкой «во время шага <роль>»; проверка потолка после шага
   (`budget.budget_block`/эскалация) читает актуальное значение. Отказ
   остаётся только для чужого живого lease ДРУГОЙ сессии, если Оператор
   не тот же (`session_id` иной хост) — иначе без отказа.
2. Возврат из `escalated` (`approve`, `budget` с подъёмом) не требует
   нового шага роли, если в текущем пребывании после последнего
   `state -> in_dev`/`review` шаг роли уже сдан (`agent run finished`
   роли состояния): рубеж «возврат не отработан» сверяется с последним
   сданным шагом ПОСЛЕ последней записи возврата из `review`
   (`changes_requested`), а не после любого `state -> in_dev`.
   Возврат из эскалации, случившейся после сданного шага, продолжает
   переход по готовым артефактам (advance-first, 01M1R8B3ZK).
3. Эскалация по бюджету после approved-вердикта ревью: возврат в
   `review` не требует нового прогона ревьювера — «вердикт уже учтён»
   применяется только при новом коде после вердикта (сверка sha кода,
   уже есть в `_review_verdict_is_fresh`/аналоге), иначе переход в
   `verifying`.
4. Тесты: (а) `budget` под живым lease своей сессии меняет потолок и
   журналирует; чужая сессия — отказ как раньше; (б) возврат из
   `escalated` после сданного шага developer — переход без нового шага;
   после возврата из ревью без шага — отказ как раньше (мутация: рубеж
   снят вовсе — красный); (в) возврат в `review` при approved-вердикте
   по тому же sha — в `verifying` без ревьювера; при новом sha — новый
   прогон; (г) существующие `tests/test_budget*.py`,
   `tests/test_fsm_review_rework*.py`, `tests/test_auto*.py` зелёные без
   правки ассертов.

Зоны: orchestrator/budget.py, orchestrator/lease.py, orchestrator/fsm.py,
orchestrator/fsm_advance.py, orchestrator/auto.py, tests/.
Порядок: после мержа «CI до ревью» (01M1TQ0TRC: те же `fsm.py`,
`fsm_advance.py`, `auto.py`) — сверить по `status`. Сигналы деления
сработают: ожидается монолит (один рубеж возврата) либо нарезка
«п.1 / п.2+3».

Не входит: калибровка потолков (01M1TQ11K4, ADR-0014); стоп-лосс.

Рамка: $25.
