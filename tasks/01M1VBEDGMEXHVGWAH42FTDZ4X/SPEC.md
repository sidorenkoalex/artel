# SPEC: budget под живым шагом и возврат из эскалации без холостого шага роли

## Контекст
Аудит обходных сценариев Оператора 06.09 нашёл два независимых
источника трения на одном и том же пути «эскалация -> возврат»:

1. `cmd_budget` отказывает поднять потолок, пока lease задачи держит
   живой шаг чужой сессии, — даже когда это тот же Оператор, просто
   из другого терминала того же хоста. Итог без обхода — гарантированная
   эскалация по бюджету сразу после шага, потому что предупреждение «>70%»
   приходит уже во время шага, а поднять потолок раньше нельзя.
2. Возврат из `escalated` (`approve`, `budget` с подъёмом) сегодня
   безусловно требует нового шага роли после возврата, даже если этот шаг
   уже был сдан ДО эскалации (типичный случай — эскалация по бюджету
   ловит завершившийся шаг роли до того, как он успел продвинуть задачу).
   06.09 это стоило четырёх холостых шагов developer «менять нечего» по
   $1.3–1.8 и одного лишнего прогона ревьювера ($0.77) там, где REVIEW.md
   уже нёс свежий approved-вердикт.

## Требования

1. `budget <id> <usd>` принимается, пока lease задачи держит живой шаг:
   `tasks.budget_usd` меняется немедленно, событие журнала «бюджет
   изменён» несёт пометку «во время шага <роль>»; проверка потолка
   после шага (`budget.budget_block`/эскалация по бюджету) видит уже
   применённое значение. Отказ остаётся только когда живой lease
   принадлежит другому хосту (другой Оператор физически); тот же хост —
   без отказа, независимо от session_id/терминала.
2. Возврат из `escalated` (`approve`, `budget` с подъёмом потолка) не
   требует нового шага роли, если после последнего возврата из `review`
   с вердиктом `changes_requested` для текущего состояния роли уже сдан
   («agent run finished») шаг этой роли: рубеж «возврат не отработан»
   сверяется именно с этим моментом, а не с фактом самой записи возврата
   из эскалации (`state -> in_dev`/`review`, оставленной самим
   возвратом). Если шаг уже сдан, последующий переход (ручной `advance`
   или предварительный `advance` внутри `auto`) продвигает задачу по уже
   готовым артефактам без нового прогона роли (advance-first,
   01M1R8B3ZK). Если шаг ещё не сдан — отказ остаётся прежним.
3. Эскалация по бюджету, наступившая во время шага reviewer с уже
   вынесенным approved-вердиктом REVIEW.md (эскалация из состояния
   `review`): при возврате в `review` переход в `verifying` не требует
   нового прогона ревьювера, если код (sha) ветки задачи не менялся с
   момента вынесения вердикта. Если код сменился после вердикта — нужен
   новый прогон ревьювера, как и раньше.

## Критерии приёмки

AC-1. `budget <id> <usd>`, вызванный при живом (heartbeat не протухшем)
lease задачи, принимается и меняет `tasks.budget_usd` немедленно, если
lease принадлежит тому же hostname, что и вызывающий процесс —
независимо от того, чей это `session_id`.

AC-2. Журнальная запись «бюджет изменён», сделанная во время живого шага
роли (условие AC-1), несёт в `detail` пометку «во время шага <роль>» с
именем роли текущего состояния задачи.

AC-3. Проверка потолка после шага (`budget.budget_block`/эскалация по
бюджету, наступающая по завершении шага) видит значение
`tasks.budget_usd`, применённое во время самого шага (AC-1), а не
значение, действовавшее на момент старта шага.

AC-4. `budget <id> <usd>` по-прежнему отказывает тем же текстом, что и
раньше, если lease задачи принадлежит живой (heartbeat не протухшей)
сессии с ДРУГИМ hostname, чем вызывающий процесс.

AC-5. Гейт «возврат не отработан» (применяемый к состоянию, в которое
вернулась задача из `escalated` через `approve` либо через `budget` с
подъёмом потолка выше израсходованного) сверяет наличие сданного шага
роли («agent run finished») с моментом ПОСЛЕДНЕГО возврата из `review`
с вердиктом `changes_requested` для этого состояния, а не с моментом
самой записи возврата из эскалации.

AC-6. Если шаг роли уже сдан после момента AC-5 (независимо от того, до
эскалации это случилось или после), последующий переход — ручной
`advance` Оператора либо предварительный `advance` внутри `auto` —
продвигает задачу по уже готовым артефактам без нового прогона роли
(advance-first, тот же механизм, что и 01M1R8B3ZK).

AC-7. Если шаг роли после момента AC-5 ещё не сдан, переход (ручной или
внутри `auto`) после возврата из эскалации по-прежнему отказывает тем же
текстом «возврат не отработан», что и до этой задачи.

AC-8. Эскалация по бюджету, наступившая во время шага reviewer с уже
вынесенным approved-вердиктом REVIEW.md (эскалация из состояния
`review`): при возврате в `review` переход в `verifying` происходит без
нового прогона ревьювера, если код (sha) ветки задачи не менялся с
момента вынесения этого вердикта.

AC-9. Та же эскалация, если код (sha) ветки задачи сменился после
вынесения вердикта, требует нового прогона ревьювера при возврате в
`review` — перехода в `verifying` без нового вердикта не происходит.

AC-10. Тест: `budget` под живым lease СВОЕЙ сессии меняет потолок задачи
и журналирует (AC-1/AC-2).

AC-11. Тест: `budget` под живым lease чужой сессии с ДРУГИМ hostname
отказывает, как и до этой задачи (AC-4).

AC-12. Тест: возврат из `escalated` после уже сданного шага developer
переходит без нового шага роли (AC-5/AC-6).

AC-13. Мутационный тест: возврат из `escalated` после возврата из
`review` (`changes_requested`) БЕЗ сданного шага роли по-прежнему
отказывает переходу («возврат не отработан») — тест обязан краснеть,
если этот рубеж снят вовсе, а не только ослаблен (AC-7).

AC-14. Тест: возврат в `review` при approved-вердикте по тому же sha
кода переходит в `verifying` без нового прогона ревьювера (AC-8).

AC-15. Тест: возврат в `review` при сменившемся после вердикта sha кода
требует нового прогона ревьювера (AC-9).

AC-16. Существующие `tests/test_budget*.py`, `tests/test_fsm_review_rework*.py`
и `tests/test_auto*.py` остаются зелёными без правки утверждений.

## Оценка объёма и деление
Сработавшие сигналы: число затрагиваемых модулей/файлов зоны — 5
(`orchestrator/budget.py`, `orchestrator/lease.py`, `orchestrator/fsm.py`,
`orchestrator/fsm_advance.py`, `orchestrator/auto.py`) при пороге ≥ 5;
число критериев приёмки — 16 при пороге ≥ 10.

Прогноз диффа: 40 КиБ (ниже половины потолка гейта ёмкости — сигнал
«прогноз диффа» этим не добавляется).

Обоснование монолита: требования 1–3 закрывают ОДИН пограничный
механизм — жизненный цикл задачи вокруг `budget`/эскалации/возврата, а
не три независимых.

- Требование 1 (приём `budget` под живым шагом) и требования 2–3
  (возврат из `escalated` без холостого шага, budget-эскалация после
  approved-вердикта) правят ОДНУ И ТУ ЖЕ функцию
  `orchestrator/budget.py::_cmd_budget` — она сегодня несёт и приём
  нового потолка, и продолжение возврата из `escalated`
  (`t["state"] == "escalated" and ...: store.set_state(conn, task_id,
  back, ...)`). Часть, взявшая только приём потолка, не мержима
  самостоятельно без несогласованности со второй частью, которая
  правит продолжение ТОЙ ЖЕ функции, — граница зоны (`budget.py`
  целиком) не совпадает с границей независимо мержимых частей.
- Требования 2 и 3 закрывают один класс: рубеж «возврат не отработан»
  сегодня — общий узел (`orchestrator/auto.py::_role_step_since_state_entry`),
  разделяемый пред-advance гейтом цикла `auto` И ручным гейтом
  `orchestrator/fsm_advance.py::_review_rework_gate`. Тот же класс
  «граница зон auto.py/fsm_advance.py не совпадает с границей
  независимо мержимых частей» уже был признан монолитом в SPEC
  01M1RHFRQ2C0P4A57XJJ1WZV8N — тот же общий узел, тот же довод.
  Требование 3 — частный случай требования 2 (возврат из `escalated`
  именно в `review`, тем же рубежом «шаг после последнего возврата»):
  отдельная задача под требование 3 повторила бы разбор того же кода
  `auto.py`/`fsm_advance.py`, что и требование 2, без экономии на
  самостоятельной мержимости.
- Промежуточное состояние («budget принимается под живым шагом, но
  возврат из эскалации по-прежнему требует холостого шага роли»)
  оставляет систему менее последовательной, чем сегодня: аудит 06.09
  описывает оба источника трения как факты ОДНОЙ и той же сессии
  работы Оператора над одними и теми же задачами — частичный мерж не
  устраняет ни один из них полностью, пока не смержена вторая часть.

## Не входит

- Калибровка дефолтных потолков бюджета (01M1TQ11K4, ADR-0014).
- Стоп-лосс программы (`orchestrator/budget.py::check_program_spend`,
  `config.PROGRAM_STOP_LOSS_USD`) — не меняется этой задачей.
- Изменение поведения живого lease под другими мутирующими командами
  (`approve`, `reject`, `run`, `advance`, `auto`, `kill`) — исключение из
  отказа по чужому живому lease распространяется только на `budget`.
- Механическая проверка порядка запуска задач («после мержа <id>») —
  пульт сегодня не исполняет такую зависимость (docs/backlog.md, П2,
  06.09); заметка ТЗ про порядок после 01M1TQ0TRC — ручной сигнал
  Оператору/разработчику проверить по `status`, не предмет кода этой
  задачи.
- Новое промежуточное состояние FSM — ни одно из требований не вставляет
  состояние между существующими; `tests/test_invariants.py` (счётчики,
  `MergeOnlyFromMergeGateTest` и подобные) изменений поведения не ждёт
  так же, как перечисленные в AC-16 планки.
