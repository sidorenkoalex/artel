# PLAN: Штатная команда правки зафиксированной планки приёмки

## Подход

Новая операторская команда `amend-tests <id> --reason "<основание>"`,
код — новый модуль `orchestrator/amend.py`, регистрация в диспетчере
`orchestrator/artel.py::main`. Команда не входит ни в один агентский
путь (`runner`/`auto`) — вызывается Оператором вручную, после того как
он сам уже отредактировал `tasks/<id>/acceptance_tests/` прямо в
worktree задачи (`workspace.path(id)`).

Последовательность одной командой (атомарно с точки зрения состояния —
либо все шаги проходят и лок сдвигается, либо первый же отказ не
меняет ничего):

1. `--reason` непустой (`is None`/пустая строка/пробелы — все три
   отказывают одинаково, REVIEW-урок AC-5: не различать «флага нет» и
   «флаг пуст»).
2. `tasks.tests_locked_sha` задачи не пуст (лок уже стоял) — иначе
   отказ, сверять нечего (AC-4).
3. `git status --porcelain` worktree задачи: есть изменения строго под
   `tasks/<id>/acceptance_tests/` (иначе отказ AC-2) и нет изменений
   ВНЕ этого пути (иначе отказ AC-3, даже если часть правки валидна).
4. Прогон `acceptance.run(tdir)` (тот же примитив, что и review-гейт)
   поверх ТЕКУЩЕГО (незакоммиченного) состояния worktree. Не «OK» —
   сверяется с маркером красноты ТЕМ ЖЕ разбором, что выход из
   `tests_writing` (`guard.scan_redness_markers(tdir)`): если он не
   находит ни одного файла без маркера — красный прогон легитимен
   (правка вносит намеренно красный тест, код ещё не готов) и не
   блокирует; если находит — отказ (AC-10).
5. `git add -- tasks/<id>/acceptance_tests` + `git commit -m
   "<id>: правка планки приёмки — <reason>"` (AC-1, AC-6). Без явной
   `-c user.name=`/`user.email=` — тем же доводом, что `answer.py`:
   правка планки содержательное решение Оператора, не служебный
   артефакт оркестратора, коммит остаётся под identity вызывающей
   сессии.
6. `tests_locked_sha` = новый HEAD ветки задачи (AC-1).
7. Одна запись журнала, `actor=operator`, `action` содержит буквально
   «правка планки» (AC-7) — единственное место, где эта метка
   появляется, `detail` несёт старый sha, новый sha, `--reason` и
   итоговую строку прогона `Ran N ... OK`/`FAILED` (AC-1, AC-11).
   Пишется через существующий `store.journal` — попадает в
   `report._all_steps` без отдельного кода (AC-8).
8. Сразу после записи — порог: последние 5 задач пульта program-wide,
   у которых `tests_locked_sha` не пуст («дошли до фиксации лока»),
   отсортированные по порядку заведения; число событий «правка планки»
   с `task_id` из этого окна; `> 1` — `alerts.raise_alert(conn, None,
   "threshold", ..., "планка девальвируется: ...")` (AC-9). Задач в
   истории меньше 5 — окно = все они (ANSWER-1).

Никакого запуска агента (`runner.spawn_agent`) и никакой оценки
содержимого диффа — только зоны/основание/лок/прогон (AC-12).

**Решение по интерпретации «task_number» (ANSWER-1, вопрос 1).** В
схеме БД нет колонки `task_number` — `store.task_number()` разбирает
только легаси-формат `Tnnn` и возвращает 0 для текущих ULID-id
(`01M1...`). Сам ANSWER-1 расшифровывает термин в скобках: «порядок
заведения». Беру за порядок заведения `tasks.created_at` (тот же
столбец, каким уже пользуется `store.latest_fixed_sha` для похожей
задачи «последняя по времени»), не строковое сравнение `id` — смесь
легаси `Tnnn` и ULID в одной программе лексикографически не
сопоставима с реальной хронологией (`T001` строкой больше `01M1...`,
хотя создана раньше). Расхождение с буквальным «task_number» не влияет
ни на один критерий приёмки: единственный сценарий с несколькими
задачами в окне (AC-9) — это одна и та же задача дважды, докстринг
теста прямо говорит «без предположений о конкретном способе
упорядочивания». Если Оператор ожидал именно `store.task_number()`
(легаси-нумерацию) — расхождение стоит проговорить на приёмке, это не
блокер: ANSWER-1 явно определяет термин через смысл, не через имя
колонки.

**Зона `store.py`.** Никакая новая SQL-функция не добавляется — окно
и счётчик считаются в `orchestrator/amend.py` целиком на уже
существующем публичном API (`store.all_tasks`, `store.task_steps`,
`store.update_task`, `store.journal`), как и просит ТЗ («только
точечное обновление tests_locked_sha и журнал существующим API»).
Принцип «SQL живёт только в store.py» (ADR-0003 3ж) от этого не
нарушается — SQL не появляется нигде за пределами store.py, просто
новых SQL-функций там не заводится вовсе.

## Шаги

1. `orchestrator/amend.py` — модуль команды: `cmd_amend_tests`
   (обвязка `lease.run_locked`, тем же приёмом, что `answer.cmd_answer`)
   + `_cmd_amend_tests` (логика) + приватные хелперы
   (`_worktree_changed_paths`, `_run_summary`, `_locked_window_task_ids`,
   `_amend_events_in_window`). Один MR, покрывает AC-1..AC-12.
2. Регистрация в `orchestrator/artel.py`: импорт модуля, разбор
   `--reason` (`_reason_arg`, тем же стилем, что `_tz_arg`), новая
   запись `"amend-tests"` в таблице диспетчера `main()`, абзац в
   докстринге модуля (конвенция файла — каждая команда описана).
3. Юнит-тесты `tests/test_amend.py`: чистые хелперы в изоляции —
   разбор `git status --porcelain` (переименования, untracked,
   modified), извлечение итоговой строки прогона (`Ran N`/`OK`/
   `FAILED`), окно из 5 залоченных задач program-wide по НЕСКОЛЬКИМ
   задачам разных target (сценарий, которого приёмочные тесты
   сознательно не покрывают — там окно всегда из одной задачи) и счёт
   событий строго по task_id окна. Юнит-тесты `tests/test_amend_argv.py`
   (или секция в том же файле) — `artel._reason_arg` в изоляции, тем
   же приёмом, что `tests/test_new_argv_parsing.py`.
4. Регенерация `docs/codebase-map.md` (`python3 scripts/codebase_map.py`)
   тем же коммитом — правятся `.py` файлы пакета (`conventions-core`).

## Влияние на систему

Новая мутирующая команда трогает: `tasks.tests_locked_sha` (единственное
поле, которое до сих пор мог задним числом двигать только инвариант 27
на переходе `in_dev -> review`, никогда — операторская команда напрямую)
и таблицу `steps`/`alerts`. Инвариант 27 (`in_dev`: `gitcmd.diff_paths`
между `tests_locked_sha` и HEAD по `acceptance_tests/`) НЕ ослабляется —
после успешной правки `tests_locked_sha` указывает РОВНО на коммит,
который эту же правку внёс, так что diff между локом и HEAD по-прежнему
пуст: команда легальный вход в инвариант, не обход (SPEC «Не входит»).
Тест `LockTest` (существующий, `tests/test_acceptance_tests_flow.py`)
не трогается и не должен покраснеть — команда его не касается напрямую,
но AC-13/шаг 2 гоняет полный набор `tests/` на CI, чтобы поймать
регресс, если он всё же случится.

`alerts` (kind=threshold) получает новый источник события — тот же
класс, что уже пишет `budget.check_program_spend` (`target=None`,
program-wide), дедуп уже даёт `alerts.raise_alert` без нового кода.

Откат: `git revert` коммита правки (сам amend-коммит) НЕ откатывает
`tests_locked_sha` автоматически — Оператор обязан либо откатить лок
второй правкой той же командой (с новым `--reason`, что тоже
инкрементирует счётчик правок и может подтолкнуть порог), либо
исправить БД вручную (та самая ручная цепочка, которую эта задача
заменяет для штатного пути, но остаётся резервной для отката ошибки
самой команды) — это осознанное ограничение, не баг: симметричного
«разлочить» SPEC не просит.

Никакой существующий тест/гейт/лимит не ослабляется: новая команда не
меняет ни один переход FSM, ни guard.py, ни gates.yaml/roles.yaml.

## Риски

- Если у Оператора несколько параллельных worktree-правок одной задачи
  (маловероятно) — `lease.run_locked` сериализует, как и остальные
  мутирующие команды.
- Порог считается по `created_at`, не по буквальному `task_number` —
  см. интерпретационное решение выше; расхождение стоит явно
  проговорить на приёмке.

## Предложения системе

- `scripts/guard.py`/ТЗ-конвенции говорят о «task_number» как о
  устоявшемся понятии (roadmap §5, инвариант 23 «program-wide, как
  пороги программы»), но в схеме БД такой колонки нет и легаси/ULID id
  не сравнимы напрямую — стоит явно задокументировать канонический
  источник «порядка заведения задачи» (created_at vs id) один раз в
  `docs/`, а не решать в PLAN каждой задачи, которой это понадобится.
- Класс «локед-фикстура test_author написана раньше, чем в main влилась
  зависимая по зонам задача (A7), и после подтяжки main в ветку разошлась
  с реальным поведением» — см. `## Эскалация` ниже. Стоит явно
  проговорить в скиле test_author/conventions-core: задача с явной
  зависимостью «запускать после мержа X» обязана либо писать
  приёмочные тесты уже ПОСЛЕ фактического мержа X в main (не раньше),
  либо явно закладывать в SPEC/фикстуру шаг ресинхронизации с
  изменившимся окружением зависимости.
- `orchestrator/fsm_advance.py::in_dev` — у роли `developer` нет
  структурного пути в `escalated` (в отличие от `spec_writing`/
  `tests_writing`/`review`), и `scripts/guard.py::RULES["plan"]
  ["statuses"]` не допускает `status: escalate` для `type: plan` —
  тот же класс, что уже отмечен прецедентом `tasks/T079/PLAN.md`
  («Эскалация: role_cwd generic-путь противоречит собственной
  self-механике»). Подтверждаю класс повторно этой задачей.

**Применение обеих правок ANSWER-2 не даёт зелёный прогон планки
задачи** — вскрылся ТРЕТИЙ, ранее замаскированный дефект той же
локед-фикстуры (маскировался R1-F1: все 13 тестов, доходящих до

дальнейшей правки `_sandbox.py` за пределами ДВУХ правок, на которые

эскалация, не самовольное расширение мандата.
