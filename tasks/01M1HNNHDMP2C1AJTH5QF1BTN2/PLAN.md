# PLAN: Штатная команда правки зафиксированной планки приёмки

## Подход

Операторская команда `amend-tests <id> --reason "<основание>"`, код —
модуль `orchestrator/amend.py`, регистрация в диспетчере
`orchestrator/artel.py::main`. Команда не входит ни в один агентский
путь (`runner`/`auto`) — вызывается Оператором вручную, после того как
он сам уже отредактировал `tasks/<id>/acceptance_tests/` прямо в
worktree задачи (`workspace.path(id)`).

**Пересмотр после A7 (ANSWER-3, машинно-видимый канал ADR-0012).**
Задача написана ДО мержа A7 (`01M1H224X5A8W159MKF1Q24R5Y`), когда
`tasks/<id>/` ещё жило в кодовой ветке задачи однобраншево. После A7
планка `tasks/<id>/` живёт ТОЛЬКО в артефактной ветке пульта
(`artifact_branch.branch_name`, `orchestrator/artifact_source.py`) —
и «коммит правки в ветку задачи» (SPEC требование 1) с этого момента
означает коммит в АРТЕФАКТНУЮ ветку, не в кодовую. Реализация первой
итерации (коммиты `e322f20`/подтяжка `3d79a14`) этого не учитывала —
коммитила правку в worktree кодовой ветки и сдвигала `tests_locked_sha`
на её HEAD, тогда как гейт `in_dev -> review`
(`orchestrator/fsm_advance.py::in_dev`, `lock_ref = branch`) сверяет
лок ИМЕННО с артефактной веткой: любой успешный `amend-tests` немедленно
ломал бы собственный переход (найдено эскалацией этого же PLAN,
воспроизведено регресс-тестом `tests/test_amend.py::
AmendThenReviewGateTest`, ныне зелёным). Эта итерация PLAN закрывает
находку буквально по ANSWER-3:

1. Команда по-прежнему читает правку Оператора С ДИСКА worktree
   кодовой ветки (`workspace.ensure`, `tasks/<id>/acceptance_tests/`)
   — единственная поверхность, на которой Оператор реально работает
   руками; если каталога там ещё нет (первая правка задачи, либо
   worktree свежий), команда сама материализует его текущим
   содержимым артефактной ветки ПЕРЕД сверкой «есть ли правка»
   (`_materialize_tests_if_missing`) — отдельной подкоманды не заводится,
   выбор разработчика (SPEC «не входит»: имя/размещение — не предмет
   приёмки, тот же принцип применён и к этому техническому решению).
2. Коммит правки идёт ПЛОТНИЦКИ прямо на артефактную ветку
   (`artifact_branch.commit_files`, тот же приём, что `checkpoint.
   _commit_external_step_artifacts`/`catalog._new_external_artifact_
   branch`) — без чекаута worktree, без побочного коммита в кодовую
   ветку вовсе.
3. `tests_locked_sha` сдвигается на sha ЭТОГО коммита (== новый HEAD
   артефактной ветки) — ту же ветку, с которой сверяет лок гейт.
4. `.gitignore`-исключённые файлы (`__pycache__`, `*.pyc` —
   неизбежный побочный продукт обязательного прогона AC-10) в коммит
   не попадают: и сверка «есть ли правка» (AC-2), и само содержимое
   коммита читаются одним и тем же `git ls-files --others
   --exclude-standard` worktree (`_tests_snapshot`), не сырым обходом
   каталога.
5. Сверка «есть ли правка вообще» (AC-2) больше не может опираться на
   `git status` worktree по каталогу `acceptance_tests/`: с A7
   `tasks/<id>/` НЕ отслеживается кодовой веткой вовсе, и материализация
   п.1 сама по себе всегда оставляет там untracked-файлы — `git status`
   показал бы «есть изменения» даже без единой правки Оператора. Сверка
   теперь по СОДЕРЖИМОМУ: снимок диска (`_tests_snapshot`) против
   снимка текущего состояния артефактной ветки (`_artifact_tests_
   snapshot`) — совпали побайтно → нечего фиксировать (AC-2), после
   правки Оператора отличаются → есть что коммитить.
6. AC-3 («изменения за пределами acceptance_tests/») по-прежнему через
   `git status --porcelain` worktree (`_worktree_changed_paths`,
   не тронута по существу) — но с добавленным `--untracked-files=all`:
   без него git схлопывает ПОЛНОСТЬЮ untracked каталог `tasks/` в одну
   строку `?? tasks/` (сама планка A7 сделала `tasks/<id>/` таким
   каталогом), и ни один путь под ним не сопоставился бы с префиксом
   `acceptance_tests/` — валидная правка ошибочно читалась бы как «вся
   за пределами» (найдено при первом же прогоне AC-1 этой итерации,
   `outside` буквально содержал `tasks/`, не пофайловый путь).

Никакого запуска агента (`runner.spawn_agent`) и никакой оценки
содержимого диффа — только зоны/основание/лок/прогон (AC-12), это не
изменилось.

**Переписывание `_sandbox.py` (ANSWER-3, вопрос 1, вариант б).**
Лок снят Оператором на файл
`tasks/01M1HNNHDMP2C1AJTH5QF1BTN2/acceptance_tests/_sandbox.py`
целиком под это переписывание (ANSWER-3). `AmendSandbox` переписан по
образцу `tests/test_acceptance_tests_flow.py::LockTest`: `enter_in_dev()`
пишет SPEC.md/acceptance_tests ПРЯМО на артефактную ветку задачи
(`artifact_commit` — тонкая обёртка `artifact_branch.commit_files`), а
не в worktree кодовой ветки — старая версия коммитила их туда напрямую
(`commit_task_dir`, `git -C <worktree> add/commit`), путём, которым
РЕАЛЬНАЯ роль никогда не пользуется (`checkpoint.
_commit_external_step_artifacts` переносит написанное в артефактную
ветку и убирает из рабочего каталога), поэтому `fsm.cmd_advance` не
видел изменений: `spec_writing -> spec_gate` не проходил вовсе (третий,
ранее замаскированный дефект фикстуры, вскрытый эскалацией — до правки
R1-F1 все 13/14 тестов падали `FileNotFoundError` РАНЬШЕ, чем успевали
дойти до этой точки). `workspace.ensure`'нутый worktree остался
ИСКЛЮЧИТЕЛЬНО поверхностью, которой реально оперирует production-команда:
`write_acceptance_tests()` (правка Оператора) и `git_wt()` (сверка
сообщения коммита — переадресован на артефактную ветку в `config.ROOT`,
т.к. коммит теперь ложится туда, не в worktree; интерфейс вызова
`test_ac6_commit_message_includes_reason.py` не изменился — метод
переопределён внутри `_sandbox.py`, вызывающий тест не тронут).
`head()` теперь возвращает HEAD артефактной ветки (`gitcmd.
branch_head_sha(self.branch)`), не HEAD worktree'а — та же ветка, что
сверяет гейт и что сдвигает production-код (см. выше). Прочие файлы
`acceptance_tests/` (test_ac1..test_ac13) НЕ ТРОНУТЫ ни одной правкой —
все их вызовы фикстуры (`enter_in_dev`, `write_acceptance_tests`,
`run_amend`, `head`, `row`, `state`, `git_wt`, `self.tdir`, `self.conn`,
`self.TASK`) остались с теми же именами и той же семантикой снаружи,
интерфейс не потребовал ни одной правки вызывающей стороны.

**Решение по интерпретации «task_number» (ANSWER-1, вопрос 1) — без
изменений этой итерацией.** В схеме БД нет колонки `task_number` —
`store.task_number()` разбирает только легаси-формат `Tnnn` и
возвращает 0 для текущих ULID-id. Беру за порядок заведения
`tasks.created_at` (тот же столбец, каким уже пользуется `store.
latest_fixed_sha`), не строковое сравнение `id` — смесь легаси `Tnnn`
и ULID в одной программе лексикографически не сопоставима с реальной
хронологией. Расхождение с буквальным «task_number» не влияет ни на
один критерий приёмки (единственный сценарий с несколькими задачами в
окне, AC-9, — одна и та же задача дважды).

**Зона `store.py`.** Без изменений: SQL не появляется нигде за
пределами `store.py`, новых SQL-функций не заводится вовсе — окно и
счётчик правок считаются в `orchestrator/amend.py` целиком на уже
существующем публичном API (`store.all_tasks`, `store.task_steps`,
`store.update_task`, `store.journal`).

## Влияние на систему

Новая мутирующая команда трогает: `tasks.tests_locked_sha` (единственное
поле, которое до сих пор мог задним числом двигать только инвариант 27
на переходе `in_dev -> review`, никогда — операторская команда напрямую)
и таблицу `steps`/`alerts`, а с этой итерации — ещё и артефактную ветку
пульта (новый коммит, тот же класс операции, что уже делает `checkpoint.
_commit_external_step_artifacts`/`catalog._new_external_artifact_branch`).
Инвариант 27 (`in_dev`: `gitcmd.diff_paths` между `tests_locked_sha` и
HEAD артефактной ветки по `acceptance_tests/`) НЕ ослабляется — после
успешной правки `tests_locked_sha` указывает РОВНО на коммит, который
эту же правку внёс на ТОЙ ЖЕ ветке, с которой сверяет гейт: diff между
локом и HEAD по-прежнему пуст. До этой итерации команда сдвигала лок на
HEAD ДРУГОГО дерева (worktree кодовой ветки) — то был не «легальный вход
в инвариант», а его фактическая поломка сразу после первого же успешного
`amend-tests` (регресс-тест `tests/test_amend.py::AmendThenReviewGateTest`
теперь ловит именно этот класс дефекта). Тест `LockTest` (существующий,
`tests/test_acceptance_tests_flow.py`) не трогается и не должен
покраснеть.

`alerts` (kind=threshold) — без изменений, тот же класс, что уже пишет
`budget.check_program_spend` (`target=None`, program-wide).

Откат: `git revert` коммита правки на артефактной ветке НЕ откатывает
`tests_locked_sha` автоматически — Оператор обязан либо откатить лок
второй правкой той же командой (с новым `--reason`), либо исправить БД
вручную — осознанное ограничение, не баг: симметричного «разлочить»
SPEC не просит.

Никакой существующий тест/гейт/лимит не ослабляется: новая команда не
меняет ни один переход FSM, ни guard.py, ни gates.yaml/roles.yaml.

**Прогон планки задачи** (после переписывания `_sandbox.py` и правки
асимметрии):

## Риски

- Если у Оператора несколько параллельных worktree-правок одной задачи
  (маловероятно) — `lease.run_locked` сериализует, как и остальные
  мутирующие команды.
- Порог считается по `created_at`, не по буквальному `task_number` —
  см. интерпретационное решение выше; расхождение стоит явно
  проговорить на приёмке.
- Материализация (`_materialize_tests_if_missing`) срабатывает только
  когда каталога `acceptance_tests/` нет на диске worktree ВООБЩЕ —
  если Оператор вручную удалил там один файл из нескольких (частичная
  правка на неполном каталоге), материализация не восполнит недостающее
  (каталог уже существует) — Оператор либо материализует сам заново
  (`rm -rf` каталога перед правкой), либо это читается как намеренное
  удаление файла (SPEC не различает эти два случая, `write_commit`
  «дописывание, не перезапись» и так не умеет удалять пути из дерева —
  тот же существующий, документированный предел артефактной ветки,
  `artifact_branch.py`, AC-12).

## Предложения системе

- `scripts/guard.py`/ТЗ-конвенции говорят о «task_number» как о
  устоявшемся понятии, но в схеме БД такой колонки нет и легаси/ULID id
  не сравнимы напрямую — стоит явно задокументировать канонический
  источник «порядка заведения задачи» (created_at vs id) один раз в
  `docs/`, а не решать в PLAN каждой задачи, которой это понадобится.
- Класс «локед-фикстура test_author написана раньше, чем в main влилась
  зависимая по зонам задача (A7), и после подтяжки main в ветку разошлась
  с реальным поведением» — задача с явной зависимостью «запускать после
  мержа X» должна либо писать приёмочные тесты уже ПОСЛЕ фактического
  мержа X в main (не раньше), либо явно закладывать в SPEC/фикстуру шаг
  ресинхронизации с изменившимся окружением зависимости. Эта задача —
  второе подтверждение класса (после `tasks/T079/PLAN.md`, «Эскалация:
  role_cwd generic-путь противоречит собственной self-механике»).
- `git status --porcelain` без `--untracked-files=all` схлопывает
  ПОЛНОСТЬЮ untracked каталог в одну строку `?? <каталог>/` — любой
  код, парсящий этот вывод построчно и сравнивающий пути с префиксом
  (не только `amend.py::_worktree_changed_paths`), рискует тем же
  классом дефекта на ЛЮБОМ каталоге, который с A7 стал полностью
  untracked в кодовой ветке (не только `tasks/<id>/`). Стоит явно
  проговорить в `conventions-core`/`fixation`-скиле как урок A7: код,
  парсящий `git status --porcelain` построчно, обязан явно решить,
  нужен ли ему `--untracked-files=all`, а не полагаться на прежнее
  (пред-A7) предположение «все интересные пути и так уже отслежены».
- `orchestrator/fsm_advance.py::in_dev` — у роли `developer` нет
  структурного пути в `escalated` (в отличие от `spec_writing`/
  `tests_writing`/`review`), и `scripts/guard.py::RULES["plan"]
  ["statuses"]` не допускает `status: escalate` для `type: plan` —
  тот же класс, что уже отмечен прецедентом `tasks/T079/PLAN.md`.
  Третье подтверждение класса этой задачей (эскалация оформлена как
  `status: draft` + раздел «## Эскалация» в теле PLAN, тем же приёмом).
