# PLAN: A2 — инварианты мультитаргета и изоляции workspace (тестовый слой)

## Подход

Пять инвариантов SPEC кодируются новым модулем
`tests/test_multitarget_invariants.py` (песочница по идиоме
`tests/test_multitarget.py`: пути `config` подменяются на временный
каталог, `claude`/`gh` не запускаются; для инварианта 1 — настоящий git
во временном репозитории, как в `KillKeepsMainIntactTest`). Отдельный
файл, а не расширение `test_multitarget.py`: тот модуль закрывает
критерии T019 (кирпичи фундамента), этот — системные инварианты T020
(реестр `docs/invariants.md`), и смешивать две разные природы тестов
в одном файле хуже, чем развести их так же, как разведены
`test_invariants.py`/`test_review_freshness.py`/`test_step_cost.py`.
Каждый класс регистрируется строкой реестра (инварианты 20–24).

Требование 2 (workspace) обнажило реальный дефект фундамента: `cmd_run`
всегда стартует агента с `cwd=config.ROOT` независимо от target — ADR-0003
§4 требует `.artel/projects/<target>/workspace/` для внешнего. Правка
локальная (`runner.py`): `cwd` вычисляется по target задачи, для
`DEFAULT_TARGET` (догфуд) остаётся `ROOT` — поведение T001–T020 не
меняется, потому что путь создания задач для другого target сейчас
нигде не существует (`cmd_new` жёстко пишет `DEFAULT_TARGET`, и это вне
объёма A2 — SPEC «Не входит»). Ветка для внешнего target проверяется
новым тестом через прямую вставку строки в БД (`store.insert_task`),
как это уже делает `test_multitarget.TaskNumberingTest
.test_counters_are_per_target` для счётчика.

Требование 3 (кросс-таргет БД) наткнулось на границу, названную самим
T019 (`tasks/T019/PLAN.md`, «Риски», п.2): идентификатор задачи сейчас
глобальная строка (`tasks.id TEXT PRIMARY KEY`), счётчик — per-target;
буквально одинаковая строка `"T001"` для двух target агентов столкнётся
в PRIMARY KEY (проверено: `store.insert_task` второй раз с тем же `id`
падает `IntegrityError`). T019 прямо отложил префикс идентификатора до
задачи, которая заводит команду создания задач второго target, — это
не входит и в A2 («Не входит»: «Реальный второй target в targets.yaml»,
«Новые механизмы — задача тестового слоя, не фич»). Переход на составной
PRIMARY KEY `(id, target)` — единственная альтернатива без префикса —
потребовал бы протащить `target` вторым параметром в каждый вызов
`store.get_task/update_task/journal/set_state/task_steps/charge` по
всем модулям пакета (греп — 9 модулей, около 60 мест): это НОВЫЙ
механизм адресации задач, а не дефект, вскрытый тестом, и по объёму
он — отдельная задача, не пункт PLAN A2. Тест поэтому строит
сосуществование ЧИСЛОВОГО номера (оба target независимо считают
от 1), а не буквальной строки: вторая задача получает отличимый id
(`SLED-T001` — префиксная схема, которую и предполагал T019 «Риски»
п.2), и на этой паре проверяется вся суть требования 3 — числа
независимы, журнал/spend/state одной строки не задевают другую.
Буквальная коллизия строки без префикса остаётся открытым риском —
зафиксирован ниже в «Риски» этого PLAN, это НЕ регресс, вносимый A2:
до A2 сценарий было некому проверить, теперь он поименован тестом
и явной строкой риска, а не тихим умолчанием.

Требования 1, 4, 5 без открытых вопросов интерпретации: изоляция
git пульта — уже свойство `.gitignore` (`.artel/` целиком), тест
подтверждает его на разных FSM-переходах вместо разового взгляда
в файл; экономика (`store.total_spent`) уже суммирует БЕЗ фильтра
по target — тест закрывает конкретно двух-target сценарий, которого
раньше не было; счётчик уже не смотрит на строки `tasks` при обычной
выдаче номера (`next_task_number`) — тест закрывает путь reseed
(`seed_task_counters`) после «архивации без DELETE» строки с
МАКСИМАЛЬНЫМ номером target'а, где коллизия была бы наблюдаема.

## Шаги

1. `runner.py`: `cwd` рабочего каталога роли — по target задачи
   (`config.ROOT` для догфуда, `config.PROJECTS/<target>/workspace/`
   иначе, каталог создаётся при отсутствии). Единственная правка
   продакшен-кода в задаче.
2. `tests/test_multitarget_invariants.py`: пять классов инвариантов
   1–5, с негативными сценариями требований 2 и 3.
3. `docs/invariants.md`: пять новых строк реестра «Кодированные
   тестами» (20–24) со ссылкой на класс теста и ADR-0003; одна строка
   во второй таблице — про отсутствие `--target` у `status` (см.
   «Покрытие требований», п.3).

## Покрытие требований

| Требование | Шаг |
|---|---|
| 1 (изоляция артефактов пульта, .artel вне git на переходах FSM) | 2, 3 |
| 2 (изоляция workspace: cwd + негативный тест HOME/конфигов) | 1, 2, 3 |
| 3 (кросс-таргет изоляция БД: числа независимы, команды не пересекаются) | 2, 3 |
| 4 (экономика сквозная, учёт раздельный — порог по сумме двух target) | 2, 3 |
| 5 (счётчик не переиспользует номера при архивации без DELETE) | 2, 3 |

Требование 3 SPEC упоминает «status с фильтром» как пример команды,
не путающей target. Фильтра `--target` у `status`/`show` сейчас нет
(`catalog.cmd_status` без параметров печатает все задачи всех target) —
это не регресс A2 и не пробел инварианта («команды не читают чужие
строки» верно и без фильтра, потому что каждая команда адресуется
по `task_id`, а не по target), а отдельная фича вывода. Названо строкой
во второй таблице `docs/invariants.md` («не кодируется», честная
причина), а не тихо опущено.

## Влияние на систему

**Правка `runner.py` (cwd по target).** Затрагивает ровно ветку
`run_agent_once` → `subprocess.Popen`. Для `target == DEFAULT_TARGET`
(все задачи T001–T020, единственный живой путь `cmd_new`)
`role_cwd` возвращает `config.ROOT` — байт в байт то же значение,
что было раньше; ни один существующий тест, зовущий `cmd_run`, не
меняет поведение (все они создают задачи через `catalog.cmd_new`,
то есть догфуд). Путь для внешнего target нигде в продакшен-коде
сейчас не достижим (`cmd_new` не принимает target — SPEC «Не входит»),
поэтому у правки нет второго живого вызывающего, кроме нового теста,
который создаёт строку напрямую через `store.insert_task`. Как
и `role_env`, каталог создаётся здесь же (`mkdir(parents=True,
exist_ok=True)`) и ошибка создания — `skipped`, а не тихий откат на
`ROOT` (тот же принцип T019, инвариант «отсутствие каталога курируемого
слоя — шаг не начинается»).

**Инварианты, гейты, тесты и лимиты рядом.** Не ослабляются:
инварианты 1–19 (`docs/invariants.md`) — новый код не трогает условия
ни одного перехода FSM, только откуда стартует процесс агента.
`guard.py`, `gates.yaml`, `.github/`, `templates/`, `skills/`,
`roles.yaml` не менялись. `docs/invariants.md` — protected-path,
правка обоснована здесь и это единственный тронутый защищённый файл;
`tests/test_invariants.py` не менялся вовсе (новые инварианты — в
отдельном, незащищённом модуле, тем же способом, что инварианты
11/14/19 регистрируют тесты `test_agent_log`/`test_kill_cleanup`/
`test_ci_status` — прецедент уже есть в реестре).

**Гигиена песочницы (найдено и закрыто в процессе).** Первая версия
`TmpRootTest` в `tests/test_multitarget_invariants.py` не подменяла
`config.ROOT` (по образцу `test_multitarget.TmpRootTest`, которому ROOT
не был нужен). Негативный тест требования 2 писал маркер в
`config.ROOT / "CLAUDE.md"`, рассчитывая на песочницу, — с непатченным
`ROOT` это оказался настоящий `CLAUDE.md` пульта. Поймано немедленно
контролем `git status --porcelain` после прогона (тот же контроль,
что и в мутационных пробах ниже), файл восстановлен `git checkout --`
до коммита чего-либо. Фикс — `ROOT` тоже в списке подменяемых путей
`TmpRootTest`, с копией `templates/` и `skills/` в песочницу (без них
`cmd_new`/`cmd_run` падают ENOENT — они читают эти каталоги от
`config.ROOT` по ходу). После фикса весь набор (383 теста) и
`git status --porcelain` после каждого прогона — чисто.

**Мутационная проверка (критерий приёмки 2 SPEC).**

- Инвариант 1 (артефакты пульта): временно убрана строка `.artel/`
  из `.gitignore` песочницы теста → `test_external_artifacts_never
  _appear_in_git_status` падает (`git status --porcelain` перестаёт
  быть пустым) — проверено прогоном, возвращено обратно.
- Инвариант 2 (workspace cwd): временно `role_cwd` заменена на
  `return config.ROOT` безусловно → `test_external_target_cwd_is_its
  _workspace` и `test_pult_root_marker_is_unreachable_from_external
  _workspace_cwd` падают (cwd = ROOT, маркер `CLAUDE.md` пульта
  становится «видимым» в рабочем каталоге) — проверено, возвращено.
- Инвариант 3 (кросс-таргет): временно `next_task_number` лишена
  фильтра `WHERE target=?` (общий счётчик) →
  `test_task_numbers_are_independent_per_target` падает (второй target
  получает 2, а не 1) — проверено, возвращено.
- Инвариант 4 (экономика): временно `store.total_spent` заменена на
  сумму без SUM (заглушка `return 0.0`) →
  `test_program_threshold_sums_two_targets` падает (порог не
  пересекается) — проверено, возвращено.
- Инвариант 5 (счётчик/архивация): временно `seed_task_counters`
  учитывает только НЕ архивированные строки (`WHERE state != 'archived'`
  в скане MAX) → `test_counter_is_not_reset_by_reconnect_after
  _archival` падает (номер 3 переиспользуется на архивированной
  строке) — проверено, возвращено.

## Риски

1. **Буквальная коллизия `tasks.id` при одинаковой строке (например,
   `"T001"`) для двух target остаётся открытой** — не регресс A2,
   унаследована от A1 (`tasks/T019/PLAN.md`, «Риски», п.2). Тест
   требования 3 использует отличимые id по префиксной схеме, которую
   уже предполагал T019; сама схема (как ровно форматировать id
   второго target) не выбрана нигде в коде — это решение вместе
   с командой, которая заводит задачи второго target (кандидат
   в A2b/будущую задачу мультитаргетного `new`, а не в A2).
2. **`status`/`show` без `--target` печатают все задачи всех target
   одной лентой.** Не мешает ни одному инварианту (адресация по
   `task_id` не путается), но с реальным вторым target вывод `status`
   станет длинным; фильтр — фича CLI/панели, кандидат вне A2.
