# ТЗ: Сверка свежести ветки до гейта

## Контекст

Роадмап §4 п.2а, второй шаг контура параллельности (после CAS T050):
сверка свежести до гейта. Строка P3 «Сверка свежести до гейта
(кластер „параллельные сессии“)».

Проблема: при параллельной работе (N=2) main уходит вперёд, пока
задача едет по конвейеру. Сегодня ветка задачи выносится на гейт
(review-пакет, приёмка, merge_gate) в том виде, в каком её оставил
developer: Оператор аппрувит срез, который может быть уже несовместим
с main, а конфликт или регресс обнаружится только при merge — после
того как решение принято. Approve должен видеть только свежий срез;
hash-фиксация не должна инвалидироваться задним числом.

## Решение (принято Оператором 27.08, строка P3)

1. Сверка на входе в гейтовые состояния — двух точках:
   - переход `in_dev -> review` (advance, перед сборкой ревью-пакета);
   - переход `acceptance -> merge_gate` (approve приёмки).
   Если ветка задачи отстала от main (main содержит коммиты, которых
   нет в ветке), оркестратор ДО перехода:
   а) подтягивает ветку: merge main в ветку задачи merge-коммитом
      оркестраторского авторства (не rebase — существующие sha и
      фиксации остаются валидными);
   б) прогоняет приёмочные тесты задачи (`tasks/<id>/acceptance_tests/`,
      если заведены) в worktree ветки;
   в) только при успехе (а) и (б) выполняет переход — фиксация на
      переходе получает уже свежий head, и approve-по-sha дальше
      видит актуальный срез.
2. Отказы не выносятся на гейт:
   - конфликт при подтяжке от main → эскалация (escalated) с
     диагностикой, merge-попытка аккуратно откатывается
     (`git merge --abort`), ветка остаётся в состоянии до подтяжки;
   - приёмочные после подтяжки красные → эскалация с перечнем
     упавших тестов; Оператор решает (вернуть в in_dev / kill).
3. Ветка НЕ отстала от main — сверка проходит бесплатно, поведение
   переходов не меняется.
4. doctor: новая проверка — активная (нетерминальная) задача, чья
   ветка отстала от main больше чем на N коммитов, даёт предупреждение
   (N — константа конфигурации, дефолт разумный, порядка 10).
5. Деградация без реального git (песочницы тестов, fake_git):
   сверка молча пропускается — как принято у остальных git-зависимых
   проверок (образцы в gitcmd/fsm). Прецедент 16 ложных падений
   test_spec_budget (28.08) не должен повториться.

## Границы

- Только orchestrator/ (fsm, gitcmd, doctor и смежные), тесты, карта.
- Не ослаблять существующие тесты/гейты/инварианты (ADR-0002).
- Инвариант «писатель main — оркестратор» (ADR-0005 п.9): подтяжка
  меняет ТОЛЬКО ветку задачи, main не трогается ничем.

## Не входит

- Фиксация approve по patch-id вместо sha (устойчивость вердикта к
  чистому rebase) — проработка уходит в задачу merge queue, где она
  и нужна; строка в P3 остаётся.
- Merge queue и возврат из merge_gate — следующие шаги цепочки §4 п.2а.
- Автоматический re-review после подтяжки: ревью-вердикт остаётся
  в силе, свежесть подтверждается прогоном приёмочных (решение этой
  задачи; ужесточение — отдельным решением Оператора при надобности).

## Приёмка (минимум)

- Ветка отстала от main → на входе в review и в merge_gate происходит
  подтяжка merge-коммитом + прогон приёмочных; переход выполняется
  только после успеха обоих.
- Конфликт подтяжки → escalated, merge отменён, ветка чистая,
  main нетронут.
- Красные приёмочные после подтяжки → escalated с перечнем упавших.
- Ветка не отстала → поведение переходов байт-в-байт прежнее.
- doctor предупреждает об отставании ветки активной задачи > N.
- Песочницы без git: сверка пропускается, существующие тесты зелёные
  без ослаблений.
