# PLAN: Сверка свежести ветки до гейта

## Подход

SPEC требует, чтобы на входе в `in_dev -> review` (`advance`) и
`acceptance -> merge_gate` (`approve`) оркестратор при отставании ветки
задачи от main **сам выполнял `git merge`** main в ветку задачи
(требования 1, 3, AC-1) с откатом `git merge --abort` при конфликте
(требование 5, AC-2).

Это прямо сталкивается с неослабляемым инвариантом системы
(`tests/test_invariants.py::MergeOnlyFromMergeGateTest`,
docs/invariants.md инвариант 12): «git merge выполняет только `approve`
из `merge_gate` — другого пути в системе нет» (источник — docs/design.md
§2, §4, CLAUDE.md: «мерж делает оркестратор» относится к ОДНОМУ мержу —
ветки задачи в main на `merge_gate`). Тест `test_no_other_state_and_
no_other_command_merges` буквально прогоняет `advance`/`approve` по
всем состояниям FSM и требует отсутствия `git merge` везде, кроме
`merge_gate`+`approve` — то есть ровно в двух точках, которые требует
завести SPEC T051. Правка этого теста (изменение множества разрешённых
состояний, различение направления мержа) — по ADR-0002 п.2 и докстринг
`tests/test_invariants.py` («НЕОСЛАБЛЯЕМЫЕ ТЕСТЫ... ослабить, отключить,
удалить может только Оператор отдельным ADR») — вне полномочий роли
разработчика, при любой моей уверенности, что различение «main→branch»
и «branch→main» было бы обоснованным сужением. ADR-0002, решение,
п.4: «Неуверенность в безопасности изменения = эскалация, не попытка» —
здесь не неуверенность, а установленный факт конфликта, тем более
эскалация, не самостоятельное решение.

Прогнал полный `tests/` (753 теста) без единой правки `fsm.py` —
зелёный, включая все 30 инвариантов; это подтверждает, что конфликт
наступает именно и только при попытке вызвать `git merge` из
`advance`/`approve` вне `merge_gate`, а не раньше.

**Что делаю в этой итерации.** Требования 1, 3–7, 10 и критерии
AC-1–AC-4 (сам механизм подтяжки на переходах) — **не реализую**,
эскалирую целиком (см. «Эскалация»): реализация требует либо права
менять неослабляемый тест, либо переопределения SPEC — оба вне зоны
роли. Не пишу и код механизма «про запас» (модуль синхронизации,
неподключённый к `fsm.py`): его форма впрямую зависит от того, какой
вариант реконсиляции выберет Оператор (обычный `git merge` vs плумбинг
без литерального `merge`), писать его сейчас — гадать на конструкции,
которую придётся переписывать (`skills/coding-standards.md`: не
проектировать под невыясненные требования).

Требования 2, 8, 9 (AC-5, AC-6) — независимы от точки конфликта
(чтение, не запись) и реализую полностью:

- `gitcmd.commits_behind(branch, base=None)` — `git rev-list --count
  branch..base` (`base` по умолчанию `config.MAIN_BRANCH`), число
  коммитов base, которых нет в branch (требование 2). Деградация в
  песочницах без реального git — по тому же приёму, что у
  `head_sha`/`is_clean`: непустой, но нечисловой вывод или ненулевой
  код возврата → `None`, не «ноль коммитов» (требование 9, AC-6) —
  `tests.sandbox.fake_git` и заглушка `SpyRun` в
  `tests/test_invariants.py` обе отвечают на нераспознанную команду
  кодом 0 и пустым stdout, что уже естественно разбирается в `None`
  без специального кейса.
- `config.STALE_BRANCH_WARN_COMMITS = 10` — порог N (SPEC: «дефолт
  порядка 10»), константа, не магическое число в `doctor.py`.
- `doctor.check_branch_freshness(conn)` — для каждой активной
  (нетерминальной, `state not in ("done", "killed")`, по образцу
  строки `orchestrator/doctor.py:467` этого же файла) задачи с веткой
  сверяет `commits_behind`; отставание больше порога — `Check(...,
  "warn", ...)` на каждую отставшую задачу (требование 8, AC-5).
  Не incident: в отличие от `check_orphans`/`check_leases` (реальные
  дефекты с жизненным циклом ack), отставание ветки — ожидаемое,
  самоустраняющееся состояние параллельной работы (roadmap §4 п.2а),
  тем же приёмом информационного warn, что `check_cli_version`/
  `check_target_layout`. Это решение — вопрос 3 «Эскалации» ниже (не
  блокирующий, дефолт — как реализовано).
  Подключена в `all_checks()` рядом с `check_orphans`/`check_leases`
  (тоже обход `store.all_tasks`).

**Локед-приёмочный `test_ac5_doctor_warns_lagging_branch.py` красный не
по вине кода — баг мока.** `DoctorWarnsLaggingActiveBranchTest.
all_checks()` (`_sandbox.py`-независимый хелпер прямо в файле) глушит
`doctor.subprocess.run` безусловным `return_value=CompletedProcess([],
1, "", "")`. `doctor.subprocess is gitcmd.subprocess` — один и тот же
объект модуля (проверено: `python3 -c "from orchestrator import doctor,
gitcmd; print(doctor.subprocess is gitcmd.subprocess)"` → `True`), так
что подмена глушит вообще ЛЮБОЙ `subprocess.run`, включая git-вызовы
`gitcmd.git()` — не только `claude --version`/live-smoke, которые тест,
похоже, и пытался нейтрализовать. Из-за этого `commits_behind` в этом
тесте детерминированно получает «git не ответил» и молча пропускает
ЛЮБУЮ задачу, независимо от реализации — не только мою. Это ровно та же
ловушка, которую тот же test_author уже поймал и задокументировал в
`tests/test_doctor.py:122-133` (`claude_only_run`/`claude_only_popen`:
«подмена атрибута `subprocess.run` глобальна на модуль» — комментарий
там же), только в этом конкретном файле она не применена. Прогнал
`check_branch_freshness` напрямую (без глушилки этого теста) на том же
сценарии (25 «пустых» коммитов лага) — код верно находит и warn'ит
(см. «Контекст»): дефект — в тесте, не в реализации. Правка локед-теста
вне зоны роли (`skills/coding-standards.md`; тот же прецедент, что
`tasks/T043/PLAN.md`, «Эскалация», вопрос 1) — вопрос 2 «Эскалации».

## Влияние на систему

Diff шага 1 — только чтение (`git rev-list --count`, без сайд-эффектов)
и новая независимая ветка `doctor`. `fsm.py` не тронут вовсе: полный
прогон `tests/` (753 теста, python3 -m unittest discover -s tests) —
зелёный без единой правки, включая весь `test_invariants.py` (30
инвариантов, в т.ч. `MergeOnlyFromMergeGateTest`) — прямое
подтверждение, что существующее поведение переходов не изменилось
ни на бит (закрывает требование 7 в его защитной части: «раз fsm.py не
трогали — старое поведение просто осталось прежним», при том что само
требование 7 как часть механизма подтяжки числится не закрытым выше).
Ни один тест, гейт, лимит или guard не ослаблен и не изменён —
добавлены только новый читающий примитив, новая константа и новая
independent-проверка `doctor`. Откат — `git revert` коммита шага 1,
без остаточных эффектов (ничего не пишет на диск/в git, кроме своего
собственного кода).

Главный риск системы — сама SPEC-требуемая подтяжка (требования 1, 3-7,
10) — не реализована и явно вынесена в эскалацию, а не спрятана
заглушкой: `advance`/`approve` продолжают отрабатывать переходы без
сверки свежести (буквально то же поведение, что до этой задачи) — с
задачей ничего не сломано, но и заявленная в SPEC защита («approve
должен видеть только свежий срез») в этой итерации не работает.

## Риски

- `STALE_BRANCH_WARN_COMMITS = 10` — начальное значение по SPEC
  («порядка 10»), не калибровано на реальном темпе ухода main вперёд;
  Оператор может счесть нужным поднять/опустить после недели
  наблюдений — константа в одном месте (`config.py`), правка тривиальна.
- `check_branch_freshness` не incident (см. «Подход») — если Оператор
  сочтёт, что дрейф ветки должен трекаться как ack-целевая проблема
  (как `check_orphans`/`check_leases`), это отдельная небольшая правка;
  явно вынесено вопросом 2 «Эскалации», не молчаливое решение.
- Каждый прогон `doctor` — по одному `git rev-list --count` на каждую
  активную задачу; при большом числе одновременных задач это N
  дополнительных subprocess-вызовов на прогон (та же цена, что у
  `check_orphans`/`check_leases`, которые уже обходят все задачи).

## Эскалация

### Вопросы

1. **[Блокирует всё требование целиком.]** Как реализовать подтяжку
   main в ветку задачи (требования 1, 3–7, 10; AC-1–AC-4), если её
   единственный SPEC'ированный механизм (`git merge` на `advance` из
   `in_dev` и `approve` из `acceptance`) буквально запрещён
   неослабляемым `tests/test_invariants.py::MergeOnlyFromMergeGateTest`
   (docs/invariants.md, инвариант 12), а изменение этого теста —
   по ADR-0002 право только Оператора?
   - **(а)** ADR, сужающий инвариант 12 до направления «ветка задачи →
     main» (собственно предмет design.md §2/§4 — «мерж прошедшего гейты
     MR», не любой `git merge` вообще), с правкой
     `test_invariants.py`/`docs/invariants.md` под Оператором (или
     новой задачей конвейера по ADR). Дальше — обычная реализация SPEC
     буквально: `git merge --no-ff` в worktree ветки задачи
     (`workspace.path`/`workspace.ensure`), `git merge --abort` при
     конфликте, `orchestrator/acceptance.py::run` на подтянутом
     дереве.
   - **(б)** Подтяжка через git-плумбинг (`merge-tree`/`commit-tree`/
     `update-ref`) вместо порцелейн-подкоманды `merge` — формально не
     задевает букву инварианта (нет подстроки `merge` в argv[1]), даёт
     тот же результат (двухродительский коммит), но: требует ещё и
     переопределения требования 5 (там явно назван `git merge --abort`
     как способ отката — плумбинг ничего не трогает в рабочем дереве,
     откатывать нечего) и по сути обходит намерение теста буквой, а не
     решает конфликт по существу — **не рекомендую**.
   - **(в)** Отказ от автоматической подтяжки в этих двух точках;
     оркестратор только детектирует и блокирует переход текстом
     («подтяни main вручную»), фактическую подтяжку делает Оператор/
     роль вне FSM. Меняет SPEC по существу (требование 3 — «оркестратор
     подтягивает», не «просит») — тоже решение Оператора, не роли.
   - **(default, если Оператор промолчит)** ничего не подключать: T051
     остаётся в текущем виде (только `doctor`-часть, требования 2/8/9),
     сама подтяжка — открытый долг до явного выбора (а)/(б)/(в).

2. **[Не блокирует само требование 8 — блокирует только зелёность
   одного локед-теста.]** `tasks/T051/acceptance_tests/
   test_ac5_doctor_warns_lagging_branch.py::
   DoctorWarnsLaggingActiveBranchTest.
   test_ac5_active_task_far_behind_main_gets_a_warning` красный из-за
   бага в собственном моке теста (см. «Подход»: `doctor.subprocess.run`
   глушится безусловно, что глушит и git-вызовы `gitcmd.git()` — тот же
   объект модуля). Прямой вызов `doctor.check_branch_freshness` без этой
   глушилки корректно находит отставание и warn'ит (см. «Контекст»).
   Правка локед-теста — не моя зона.
   - **(default)** test_author чинит мок тем же приёмом, что уже
     задокументирован и применён в этом же репозитории
     (`tests/test_doctor.py::claude_only_run`/`claude_only_popen`,
     строки 122–133): side_effect, отвечающий фейком только на
     `args[0] == "claude"`, остальное — в настоящий `subprocess.run`.
     Код `check_branch_freshness` менять не нужно — воспроизведено
     прогоном напрямую (см. «Контекст»).
   - Оператор ADR-ом решает иначе (например, признаёт тест
     неисправимым и снимает требование к этой конкретной проверке) —
     не рекомендую, дефект тривиально чинится по образцу, уже
     существующему в репозитории.

3. **[Не блокирует, можно решить на ревью.]** `check_branch_freshness`
   реализован как информационный `warn` (не заводит `alerts`/incident,
   не требует `alert-ack`) — по аналогии с `check_cli_version`, не с
   `check_orphans`/`check_leases`. Подходит это, или отставание ветки
   нужно трекать как ack-целевой incident?
   - **(а, как реализовано, default)** только `Check(..., "warn", ...)`
     в выводе `doctor`, без записи в `alerts`.
   - **(б)** дополнительно `alerts.raise_alert(..., "incident",
     "doctor.branch_freshness", ...)` с авто-ack при исчезновении
     условия (по образцу `check_orphans`/`_auto_ack_gone`).
