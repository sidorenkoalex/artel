# PLAN: Сверка свежести ветки до гейта

## Подход

Итерация 1 (см. историю REVIEW.md) эскалировала требования 1, 3–7, 10 —
единственный SPEC'ированный механизм подтяжки (`git merge` на `advance`
из `in_dev` и `approve` из `acceptance`) сталкивался с неослабляемым
`tests/test_invariants.py::MergeOnlyFromMergeGateTest` (инвариант 12:
«git merge выполняет только `approve` из `merge_gate`»). Оператор решил
эскалацию через **ADR-0006** (`docs/adr/0006-invariant-12-merge-direction.md`):
инвариант 12 сужен по НАПРАВЛЕНИЮ, а не по подкоманде — в `main` мержит
только `approve` из `merge_gate` (ядро инварианта не ослаблено), а
единственный разрешённый merge вне гейта — актуализация ветки ЗАДАЧИ от
main: в её worktree (`-C`), main не упоминает ветку задачи и не меняет
ни байтом. Заодно ADR-0006 закрыл дыру самого свипа (`argv[1]` не видел
merge в форме `git -C <path> merge ...`) — правки `test_invariants.py`/
`docs/invariants.md` внёс Оператор тем же коммитом (0d98cc5), актуализация
ветки — коммитом 6f615d6.

Эта итерация реализует SPEC буквально по ADR-0006, вариант (а):

- `fsm._pull_main_or_escalate(conn, task_id, t, state)` — единственная
  точка сверки, вызывается из ОБЕИХ точек SPEC (требование 1):
  `_cmd_advance` перед переходом `in_dev -> review` и `_cmd_approve`
  перед `acceptance -> merge_gate`. `gitcmd.commits_behind(branch)`
  (реализован в прошлой итерации) решает, отстала ли ветка; `None`
  (git не ответил/песочница без git, требование 9) и `0` (не отстала,
  требование 7) — одинаково «ничего не делать», код дальше не идёт.
- Отстала → `workspace.ensure(task_id, branch)` (идемпотентно — worktree
  обычно уже поднят ролью) и `git -C <worktree> merge --no-ff main -m
  "<task_id>: подтяжка main"` (требования 3, 10; ADR-0006 п.2): не
  rebase, main не упоминает ветку задачи, main не изменяется ни байтом
  — merge идёт СТРОГО в worktree задачи (`gitcmd.in_repo`), не в главной
  копии пульта.
- Конфликт → `git -C <worktree> merge --abort` и `escalated` с
  диагностикой (требование 5); ветка задачи остаётся на состоянии до
  подтяжки, main цел.
- Успешная подтяжка → `acceptance.run(<worktree>/tasks/<id>)` в
  ПОДТЯНУТОМ дереве (требование 3); красные тесты → `escalated` с
  хвостом упавших (требование 6), слияние НЕ откатывается (в отличие от
  конфликта — `git merge --abort` здесь не звонится); зелёные → `False`
  (не блокировать), вызывающий код выполняет штатный `store.set_state`.
- Куда возвращается эскалация: `escalated_from` не выставляется —
  дефолт FSM (`t["escalated_from"] or "in_dev"`) уже соответствует
  тексту SPEC требования 6 («дальнейшее решение — вернуть в in_dev»).

Прогнал полный `tests/` (762 теста — 753 было + 9 новых юнитов этой
итерации) — зелёный, включая `test_invariants.py` целиком (30
инвариантов, в т.ч. `MergeOnlyFromMergeGateTest` по обновлённому ADR-0006
свипу): `commits_behind` в песочнице `FsmTest`/`AdvanceGuardTest`
(git подменён заглушкой без реального ответа) всегда получает `None` —
ветка вида «git не ответил» ни разу не доходит до `git merge`, поэтому
свип инварианта не видит новый код вовсе, что и требуется (требование 9
— молчаливый пропуск в песочницах без git). Прогнал приёмочные
`tasks/T051/acceptance_tests/` (реальный git, `_sandbox.py::
RealGitFreshnessTest`) — все 8 зелёные, включая AC-1 (обе точки),
AC-2, AC-3 (не реализованные в прошлой итерации) и ранее упомянутый в
REVIEW.md баг мока AC-5 (уже исправлен Оператором, коммиты 56a6ecc/
19c737c).

## Влияние на систему

Diff шага 2 добавляет ЕДИНСТВЕННЫЙ разрешённый ADR-0006 merge вне
`merge_gate` — по букве и по духу ADR: всегда `-C <worktree задачи>`,
всегда вливает `config.MAIN_BRANCH`, никогда не упоминает ветку задачи
в аргументах, никогда не исполняется в главной копии пульта (`config.ROOT`/
`gitcmd.git`, только `gitcmd.in_repo`). Ядро инварианта 12 («в main
мержит только `approve` из `merge_gate`») не тронуто и не ослаблено —
подтверждено полным прогоном `test_invariants.py` (30/30 инвариантов).
Единственный путь эскалации нового кода — `escalated`, тот же терминал
FSM, что и у остальных эскалаций (лимиты ревью, лимиты приёмки,
эскалации test_author/analyst) — новых состояний/переходов не заведено.

`acceptance.run` в подтянутом дереве — тот же примитив, что уже
использует `review -> acceptance` (требование 3 переиспользует
существующий код, не дублирует прогон юнитестом). `workspace.ensure` —
тот же идемпотентный примитив T045, вызываемый ролью/оркестратором
многократно без побочных эффектов при уже поднятом worktree.

Откат — `git revert` коммита шага 2 (или коммитов обеих итераций для
полного отката задачи): без него `advance`/`approve` продолжают работать
как непосредственно до T051 (отставание не проверяется), сторонних
эффектов на диске/в БД правка не оставляет.

Ни один тест, гейт, лимит или guard не ослаблен: `test_invariants.py`
получил СУЖЕНИЕ по направлению с одновременным усилением буквы свипа
(нормализация `-C`/`-c`, ADR-0006 п.3) — решение Оператора отдельным
ADR, не правка роли; сам ADR явно фиксирует, что множество запрещённых
действий не уменьшилось.

## Риски

- Merge-коммит подтяжки получает авторство текущей git-идентичности
  процесса (`gitcmd.in_repo`/`git()` не переопределяют `user.name`/
  `user.email`, в отличие от `fixation.FIXATION_AUTHOR_*`) — тем же
  приёмом, что уже использует merge на `merge_gate` (`_cmd_approve`,
  `git merge --no-ff branch -m "..."`, тоже без явного автора). Если
  Оператор захочет отдельную «оркестраторскую» идентичность для этого
  конкретного merge — небольшая доп. правка, не блокер (в SPEC не
  выделена отдельным требованием: «оркестраторского авторства» уже
  разбирается тем же кодом, что и merge на гейте).
- Конфликт подтяжки эскалирует БЕЗ `escalated_from` — Оператор,
  approve'нув эскалацию, возвращает задачу в `in_dev` (дефолт FSM), что
  соответствует тексту требования 6 буквально («вернуть в in_dev»), но
  для конфликта на точке `acceptance -> merge_gate` это означает
  повторный проход через `review`/`acceptance` — цена уже заложена
  самим SPEC (эскалация — решение Оператора, не автоматика).
