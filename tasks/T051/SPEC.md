# SPEC: Сверка свежести ветки до гейта

## Контекст

Роадмап §4 п.2а, второй шаг контура параллельности (после CAS T050):
при параллельной работе (N=2) main уходит вперёд, пока задача едет по
конвейеру. Сегодня ветка задачи выносится на гейт (review-пакет,
приёмка, merge_gate) в том виде, в каком её оставил developer:
Оператор аппрувит срез, который может быть уже несовместим с main,
а конфликт или регресс обнаружится только при merge — после того как
решение уже принято. Approve должен видеть только свежий срез;
hash-фиксация не должна инвалидироваться задним числом.

## Требования

1. Сверка свежести выполняется в двух точках: на входе в переход
   `in_dev -> review` (advance, перед сборкой ревью-пакета) и на входе
   в переход `acceptance -> merge_gate` (approve приёмки).
2. Ветка задачи считается отставшей, если main содержит коммиты,
   которых нет в ветке задачи.
3. Если ветка отстала, до перехода оркестратор: (а) подтягивает main
   в ветку задачи merge-коммитом оркестраторского авторства (не
   rebase — существующие sha и фиксации остаются валидными);
   (б) прогоняет приёмочные тесты задачи (`tasks/<id>/acceptance_tests/`,
   если заведены) в worktree ветки задачи.
4. Переход выполняется только после успеха обоих шагов (а) и (б);
   фиксация на переходе получает уже свежий head ветки.
5. При конфликте подтяжки от main задача переходит в `escalated`
   с диагностикой конфликта; merge-попытка откатывается командой
   `git merge --abort`; ветка задачи остаётся в состоянии до подтяжки;
   main не изменяется.
6. Если после успешной подтяжки приёмочные тесты падают, задача
   переходит в `escalated` с перечнем упавших тестов; слияние с main
   при этом сохраняется (откат не выполняется) — дальнейшее решение
   (вернуть в `in_dev` / kill) принимает Оператор.
7. Если ветка задачи не отстала от main, сверка не меняет поведение
   перехода: он выполняется в точности как до этой задачи.
8. `doctor` получает новую проверку: активная (нетерминальная) задача,
   чья ветка отстала от main больше чем на N коммитов, порождает
   предупреждение; N — константа конфигурации, дефолт порядка 10.
9. В песочницах тестов без реального git (`fake_git` и аналогичные
   заглушки) сверка свежести молча пропускается — по образцу
   существующих git-зависимых проверок в `gitcmd`/`fsm`.
10. Подтяжка меняет только ветку задачи; main не изменяется никаким
    шагом сверки (ADR-0005 п.9, «писатель main — оркестратор»).
11. Изменения вносятся только в `orchestrator/` (`fsm.py`, `gitcmd.py`,
    `doctor.py` и смежные модули), тесты и карту кодовой базы
    (`docs/codebase-map.md`).

## Критерии приёмки

AC-1. Ветка задачи отстала от main → на входе в переход
`in_dev -> review` и на входе в переход `acceptance -> merge_gate`
оркестратор до перехода подтягивает main в ветку задачи merge-коммитом
оркестраторского авторства (не rebase) и прогоняет приёмочные тесты
задачи (`tasks/<id>/acceptance_tests/`, если заведены) в worktree
ветки; переход выполняется только после успеха обоих шагов.

AC-2. Конфликт при подтяжке main → задача переходит в `escalated`
с диагностикой конфликта, merge-попытка отменяется командой
`git merge --abort`, ветка задачи остаётся в состоянии до подтяжки,
main не изменяется.

AC-3. Приёмочные тесты после успешной подтяжки красные → задача
переходит в `escalated` с перечнем упавших тестов; слияние с main
при этом остаётся (откат не выполняется).

AC-4. Ветка задачи не отстала от main → переход выполняется в точности
как до этой задачи (поведение переходов байт-в-байт прежнее).

AC-5. `doctor` выдаёт предупреждение для каждой активной
(нетерминальной) задачи, чья ветка отстала от main больше чем на
N коммитов (N — константа конфигурации, дефолт порядка 10).

AC-6. В песочницах тестов без реального git (`fake_git` и аналогичные
заглушки) сверка свежести молча пропускается; существующие тесты
остаются зелёными без ослабления существующих тестов, гейтов,
лимитов, guard-проверок и инвариантов (ADR-0002).

## Не входит

- Фиксация approve по patch-id вместо sha (устойчивость вердикта
  к чистому rebase) — уходит в задачу merge queue, где она и нужна;
  строка в P3 остаётся.
- Merge queue и возврат из merge_gate — следующие шаги цепочки
  §4 п.2а.
- Автоматический re-review после подтяжки — ревью-вердикт остаётся
  в силе, свежесть подтверждается прогоном приёмочных (решение этой
  задачи); ужесточение — отдельным решением Оператора при надобности.
- Изменение схемы БД, `roles.yaml`, `targets.yaml`, `.github/`,
  `templates/`, `skills/`.
- Файлы вне `orchestrator/` (`fsm.py`, `gitcmd.py`, `doctor.py`
  и смежные модули), тестов и карты кодовой базы.
