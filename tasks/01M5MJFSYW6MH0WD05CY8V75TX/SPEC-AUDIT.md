# SPEC-AUDIT: suite-run записывает время каждого теста полного прогона по отметкам времени строк хода

## ТЗ и SPEC
- ТЗ треб. 1 → SPEC треб. 1–2; ТЗ 2 → SPEC 3; ТЗ 3 → SPEC 4; ТЗ 4 → SPEC 5; ТЗ 5 → SPEC 6; ТЗ 6 (а)–(д) → AC-1, AC-2, AC-3, AC-5, AC-6; ТЗ 7 и «Ограничение зон по смыслу» → «Не входит». Требования ТЗ не потеряны. ANSWER-n у задачи нет, решений Оператора на гейте SPEC в брифе нет.
- Уточнения против буквы ТЗ, все в пользу смысла ТЗ:
  - время строки — момент появления её ПЕРВЫХ байтов, а не её `\n` (SPEC треб. 1). ТЗ 1 говорит «время её появления», поэтому противоречия нет. Нужно это потому, что xdist дописывает `\n` только со следующим событием (наблюдение аудита 1);
  - при дочитывании после остановки хвост без `\n` разбирается как полная строка (SPEC треб. 3). ТЗ 2 «поток один раз дочитывает остаток» этого не запрещает, а без этого ТЗ 6(в) невыполним;
  - `workers?`/`items?` — для формы `1 worker [1 item]`;
  - нет файла времени → нет блока (SPEC треб. 5);
  - в файле допустимы повторные строки одного id, читатель их суммирует (SPEC треб. 4).

  Новых обязанностей сверх ТЗ эти уточнения не вводят.
- ТЗ 6(г) («с подменой — блок есть; лог, `failed.json`, `parse`, итог базы те же») в SPEC целиком лёг в AC-5, ТЗ 6(д) — в AC-6 (зелёный на текущем коде, как в ТЗ). Отклонения 3 аудита 1 больше нет.
- AC-4 и AC-7 — критерии к ТЗ 3 и ТЗ 2. В состав `tests/` ТЗ их не включает, и SPEC прямо пишет в «Не входит», что после мержа у них остаётся только планка. Вопрос закрыт открыто, решение за Оператором на гейте (см. «Матрица»).

## Пути обхода гейтов
- Писать весь файл времени после остановки потока, а не по мере появления строк: все AC проходят, но при гибели самого фонового процесса `suite-run` (снят Оператором, упал пульт) файл пуст — ровно тот случай, ради которого ТЗ 3 требует `flush` по ходу (отклонение 1).
- Вызывать `join` потока до отметки конца прогона: AC-7 проходит (≤ 2 с), но длительность прогона в журнале и сигнале близости к пределу растёт на время ожидания (отклонение 2).
- Других путей не найдено. Время «от начала прогона» вместо «от своего `gwN`» ловит AC-1; отметку по `\n` ловит AC-2 (быстрый < 1,5 с); потерю хвоста — AC-3.

## Вердикт
concerns — все 7 отклонений аудита итерации 1 SPEC закрыл, факты о коде верны. Осталось три мелких отклонения, решить их Оператор может на гейте:

1. **`flush` по мере появления не держится тестом** (SPEC «Требования» п. 4; AC-3). Реализация, которая пишет весь файл после остановки потока, проходит AC-2 и AC-3. Чтобы поймать это, AC-3 (или отдельная проверка) должен читать файл времени, пока прогон ещё идёт: например, быстрый тест есть в файле до истечения предела. Либо принять, что свойство держит только ревью.
2. **Ожидание потока и длительность прогона** (SPEC п. 3; `acceptance.py:2610, 2620, 2885–2887`). SPEC не говорит, входит ли ожидание потока (до 2 с) в измеряемую длительность прогона, а она питает `_signal_near_limit` и метрики. Предлагается одна фраза: остановка потока идёт после отметки конца прогона (`_last_run_completed_at`) и в длительность не входит.
3. **Порог AC-2 на границе квантования** (AC-2: «не меньше 1,5 с» при опросе «не реже раза в 0,5 с»). При опросе ровно раз в 0,5 с нижняя оценка времени спящего теста — 1,5 с, запаса нет. Можно спать 3 с при пороге 1,5 с или указать опрос в тесте чаще; мелочь против хрупкости.

Для сведения Оператора, не отклонение: AC-4 и AC-7 после мержа долгоживущей защиты не имеют. SPEC говорит это открыто («Не входит»), состав тестов совпадает с ТЗ 6.
