# SPEC: suite-run записывает время каждого теста полного прогона по отметкам времени строк хода

## Контекст
С 21.10 в журнале 16 полных прогонов выше 80 % предела (1500 с, `targets.yaml:53`
`full_suite_timeout_sec`), 7 из них оборваны по пределу. Какие тесты и файлы
съедают время, не видно: сводку `--durations` pytest печатает только в конце,
оборванный прогон до неё не доходит. При этом `suite-run` уже идёт с `-vv`
(`orchestrator/suite_run.py:73`), и рабочие процессы xdist печатают строку на
каждый завершённый тест (`[gwN] [ NN%] PASSED <id узла>`), которую разбирает
`suite_run._progress` (`_PROGRESS`, `_REPORT_SECTION`). Задача — снимать время
появления этих строк в лог-файле прогона `_run_full_suite_to_log`
(`orchestrator/acceptance.py:2854`), писать время каждого теста в файл рядом с
логом и печатать в отчёте `suite-run` блок «самые медленные», не меняя ни argv,
ни окружение, ни лог, ни итог полного прогона: их точно сверяют существующие
тесты (`tests/test_suite_run.py:353–358`,
`tests/test_01m56kcvctw5bv9twth54tw9q9_pult_pytest_unchanged.py:230–231, 295–311`,
`tests/test_01m52eedeyv14658x8vfnhcw8k_launch_places.py:152–175`).

## Требования

1. Пока идёт прогон `_run_full_suite_to_log` при `profile is None` (раннер
   `pult-pytest`), пульт в отдельном потоке читает прирост файла лога не реже
   раза в 0,5 с и для каждой новой полной строки хода вида
   `[gwN] … <ИСХОД> <id узла>` (исходы — те, что распознаёт
   `suite_run._PROGRESS`) записывает время её появления. Читаются только строки
   до первой секции отчёта (`suite_run._REPORT_SECTION`), как в `_progress`;
   неполная последняя строка (без перевода строки) ждёт следующего чтения.
2. Время теста — разница между появлением его строки и предыдущей строки хода
   того же рабочего процесса `gwN`; у первой строки процесса — от появления
   строки вида `^\d+ workers \[\d+ items\]`, а если её нет — от начала прогона.
   Повтор id узла в том же процессе (например, `PASSED`, затем `ERROR` на
   завершении фикстуры) прибавляет время к записи этого id, исход — худший
   (как в `_progress`). Разбор отметок — чистая функция нового модуля
   `orchestrator/suite_durations.py`, принимающая список пар
   (время появления, строка).
3. Поток — фоновый (daemon), не использует `acceptance.subprocess`, не меняет
   ни файл лога, ни процесс pytest. После `proc.wait` (и после снятия группы
   процессов по пределу) поток останавливается, пульт ждёт его не дольше 2 с,
   поток один раз дочитывает остаток лога. Сбой потока прогон, итог и лог не
   меняет.
4. Отметки пишутся в файл рядом с логом: `<имя лога без .log>.durations.tsv`
   (для прогона базы — от имени лога базы с `-base`), строка на тест: id узла,
   рабочий процесс, исход, секунды. Строка дописывается и сбрасывается
   (`flush`, без `fsync`) по мере появления — файл заполнен и при обрыве
   прогона по пределу. Имя файла не подпадает под шаблоны номеров логов
   (`suite_run._new_log`, `agent_log`).
5. После прогона ветки (зелёного, красного и оборванного по пределу; в режиме
   `--failed` — по повтору) `suite-run` дописывает в поле `report` в
   `suite_run._run` после `render` (тем же приёмом, что `suite_load_line`) блок
   «самые медленные»: 30 тестов и 15 файлов (сумма времени их тестов) с
   секундами; строки блока начинаются с двух пробелов и числа секунд. Блок не
   попадает ни в лог pytest, ни в `output` прогона; новых ключей `result.json`
   нет; по прогону базы блок не печатается.
6. argv и окружение полного прогона, ключ кэша итога, сигнатура
   `run_full_suite` и вызовы из гейтов и `notes` не меняются. Прогоны без лога
   (`log=None`) и прогоны раннера `pytest-own` не меняются (файла времени у
   них нет).
7. Тесты — новый файл в `tests/`, у каждого теста в докстринге строка
   «Ловит мутацию:»; состав — по критериям AC-1, AC-2, AC-3, AC-5, AC-6, AC-7.
   На текущем коде тесты AC-1, AC-2, AC-3, AC-5 и AC-6 красные, тест AC-7
   зелёный.

## Критерии приёмки

AC-1. Чистая функция разбора отметок по списку (время появления, строка) с
двумя рабочими процессами считает время каждого теста как разницу с
предыдущей строкой хода своего процесса; первую строку процесса — от строки
`N workers [M items]` (без неё — от начала прогона); повтор id узла в том же
процессе суммирует время и даёт худший исход; строки не хода и строки после
первой секции отчёта пропускает; неполная последняя строка (без перевода
строки) не засчитывается до следующего чтения.

AC-2. Прогон `_run_full_suite_to_log` маленького проекта песочницы с `-vv`
(два теста, один спит 2 с, `config.FULL_SUITE_WORKERS` = 2, `profile is None`)
оставляет рядом с логом файл `<имя лога без .log>.durations.tsv`, в котором
есть строки обоих id узла с рабочим процессом, исходом и секундами; у спящего
теста не меньше 1,5 с.

AC-3. Оборванный пределом прогон `_run_full_suite_to_log` (предел 5 с через
параметр `limit`, спящий тест 30 с, быстрый тест завершается до обрыва)
оставляет файл времени со строкой быстрого теста.

AC-4. Имя файла времени (`….durations.tsv`, и для лога базы с `-base`) не
подпадает под шаблоны номеров логов `suite_run._new_log` и `agent_log`:
появление файла времени не сдвигает номер следующего лога.

AC-5. `suite_run._run` с подменой `run_full_suite`, отдающей готовый вывод
зелёного, красного и оборванного по пределу прогона вместе с файлом времени,
дописывает в `report` после `render` блок «самые медленные»: до 30 тестов и до
15 файлов (сумма времени тестов файла) с секундами, каждая строка блока
начинается с двух пробелов и числа секунд; в режиме `--failed` блок строится
по повтору; по прогону базы блок не печатается.

AC-6. В том же прогоне `suite_run._run` (AC-5) лог побайтно равен логу,
полученному без файла времени; блока нет ни в логе, ни в `output` прогона;
`failed.json`, результат `parse(...)` и сохранённый итог базы те же, что без
файла времени; ключи `result.json` прежние.

AC-7. Шпион на запуск процесса полного прогона: argv и окружение
`run_full_suite` (с логом и без, `pult-pytest`) совпадают с теми, что были до
изменения; прогон с `log=None` и прогон раннера `pytest-own` файла времени не
создают.

AC-8. Сбой потока чтения (исключение при чтении лога или записи файла
времени) не меняет ни исход и `output` `_run_full_suite_to_log`, ни файл лога;
после завершения процесса pytest (в том числе снятого по пределу) поток
останавливается, и `_run_full_suite_to_log` ждёт его не дольше 2 с.

  без лога и без `-vv`, запись требует правки сверок окружения или argv —
  решение Оператора.
- `--durations` в CI (защищённый `.github/`).
- Ускорение самих тестов — отдельная задача по данным этой.
- Подъём предела 1500 с (только ADR Оператора).
- Правки вне ограничения зон по смыслу: в `orchestrator/acceptance.py` — только
  `_run_full_suite_to_log` (запуск и остановка потока чтения) и новые функции;
  в `orchestrator/suite_run.py` — только дописывание блока в `report` в `_run`;
  разбор вывода и итога (`parse`, `_progress`, `render`) не меняется.
- Правка `targets.yaml`, `pyproject.toml`, `.github/workflows/ci.yml`,
  `orchestrator/config.py`, `orchestrator/agent_log.py`,
  `orchestrator/fsm_merge_gate.py`, `orchestrator/notes.py` — только чтение.
- Правка существующих тестов (требование 7 ТЗ): подмены `run_full_suite` с
  узкой сигнатурой (`tests/test_approve_acceptance_full_suite.py:74`,
  `tests/test_fsm_merge_gate_remote_branch_cleanup.py:191`,
  `tests/test_doc_commit_suite_gate.py:98`) обязаны работать как есть;
  неизменность существующих тестов и полный зелёный набор `tests/` держит
  пульт.
