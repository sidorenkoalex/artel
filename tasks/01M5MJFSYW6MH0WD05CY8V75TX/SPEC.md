# SPEC: suite-run записывает время каждого теста полного прогона по отметкам времени строк хода

## Контекст
С 21.10 в журнале 16 полных прогонов выше 80 % предела (1500 с, `targets.yaml:53`
`full_suite_timeout_sec`), 7 из них оборваны по пределу. Какие тесты и файлы
съедают время, не видно: сводку `--durations` pytest печатает только в конце,
оборванный прогон до неё не доходит. При этом `suite-run` уже идёт с `-vv`
(`orchestrator/suite_run.py:73`), и рабочие процессы xdist печатают строку на
каждый завершённый тест (`[gwN] [ NN%] PASSED <id узла>`), которую разбирает
`suite_run._progress` (`_PROGRESS`, `_REPORT_SECTION`). Задача — снимать время
появления этих строк в лог-файле прогона `_run_full_suite_to_log`
(`orchestrator/acceptance.py:2854`), писать время каждого теста в файл рядом с
логом и печатать в отчёте `suite-run` блок «самые медленные», не меняя ни argv,
ни окружение, ни лог, ни итог полного прогона: их точно сверяют существующие
тесты (`tests/test_suite_run.py:353–358`,
`tests/test_01m56kcvctw5bv9twth54tw9q9_pult_pytest_unchanged.py:230–231, 295–311`,
`tests/test_01m52eedeyv14658x8vfnhcw8k_launch_places.py:152–175`).

Особенность вывода xdist (проверено живым прогоном pytest 9.1.1 + xdist 3.8.0
на аудите SPEC): контроллер пишет каждое событие как `"\n" + текст`, поэтому
строка хода получает перевод строки только со СЛЕДУЮЩИМ событием набора, а
последняя строка оборванного прогона так и остаётся без `\n`. Требования 1–2
ниже определяют момент отметки и судьбу такого хвоста так, чтобы время
доставалось тому тесту, чья строка появилась.

## Требования

1. Пока идёт прогон `_run_full_suite_to_log` при `profile is None` (раннер
   `pult-pytest`), пульт в отдельном потоке читает прирост файла лога не реже
   раза в 0,5 с и для каждой строки хода вида `[gwN] … <ИСХОД> <id узла>`
   (исходы — те, что распознаёт `suite_run._PROGRESS`) записывает время её
   появления. Время появления строки — момент того чтения, в котором в файле
   впервые оказались её первые байты (а не её завершающий `\n`). Строка
   разбирается, когда стала полной (пришёл её `\n`); неполная последняя строка
   ждёт следующего чтения, сохраняя время появления своих первых байтов.
   Читаются только строки до первой секции отчёта (`suite_run._REPORT_SECTION`),
   как в `_progress`.
2. Время теста — разница между временем появления его строки и предыдущей
   строки хода того же рабочего процесса `gwN`; у первой строки процесса — от
   появления строки вида `^\d+ workers? \[\d+ items?\]` (xdist пишет и
   `2 workers [2 items]`, и `1 worker [1 item]`), а если её нет — от начала
   прогона (момент перед запуском процесса pytest). Повтор id узла в том же
   процессе (например, `PASSED`, затем `ERROR` на завершении фикстуры)
   прибавляет время к записи этого id, исход — худший (как в `_progress`).
   Разбор отметок — чистая функция `durations(marks, start)` нового модуля
   `orchestrator/suite_durations.py`: `marks` — список пар (время появления в
   секундах, текст строки без перевода строки) в порядке появления, только
   полные строки; `start` — начало прогона в тех же секундах. Функция
   возвращает список записей (id узла, рабочий процесс, исход, секунды) — по
   одной на пару (id узла, процесс), в порядке первого появления.
3. Поток — фоновый (daemon), не использует `acceptance.subprocess`, открывает
   лог только на чтение и не меняет ни файл лога, ни процесс pytest. После
   `proc.wait` (и после снятия группы процессов по пределу) поток
   останавливается, пульт ждёт его не дольше 2 с, поток один раз дочитывает
   остаток лога. При этом дочитывании хвост без перевода строки разбирается как
   полная строка (процесс pytest уже завершён, дописать её некому): строка хода
   быстрого теста оборванного прогона попадает в файл времени. Сбой потока
   прогон, итог и лог не меняет.
4. Отметки пишутся в файл рядом с логом: `<имя лога без .log>.durations.tsv`
   (для прогона базы — от имени лога базы с `-base`), строка на тест: id узла,
   рабочий процесс, исход, секунды, через табуляцию. Строка дописывается и
   сбрасывается (`flush`, без `fsync`) по мере появления — файл заполнен и при
   обрыве прогона по пределу. Если id узла повторился в том же процессе после
   того, как его строка уже записана, в файле допустима повторная строка этого
   id и процесса; читатель файла (блок требования 5) суммирует строки одного id
   и процесса, исход берёт худший. Имя файла не подпадает под шаблоны номеров
   логов (`suite_run._new_log`, `agent_log`).
5. После прогона ветки (зелёного, красного и оборванного по пределу; в режиме
   `--failed` — по повтору) `suite-run` дописывает в поле `report` в
   `suite_run._run` после `render` (тем же приёмом, что `suite_load_line`) блок
   «самые медленные»: 30 самых медленных тестов и 15 самых медленных файлов
   (файл — часть id узла до `::`, его время — сумма времени его тестов) с
   секундами, в каждом списке по убыванию секунд; тестов или файлов меньше
   среза — печатаются все. Строки блока начинаются с двух пробелов и числа
   секунд. Блок не попадает ни в лог pytest, ни в `output` прогона; новых
   ключей `result.json` нет; по прогону базы блок не печатается. Файла времени
   нет (раннер `pytest-own`, профиль с отчётом —
   `orchestrator/acceptance.py:2569–2571`, сбой потока) или в нём нет строк —
   блок не печатается, `report` такой же, как до изменения.
6. argv и окружение полного прогона, ключ кэша итога, сигнатура
   `run_full_suite` и вызовы из гейтов и `notes` не меняются. Прогоны без лога
   (`log=None`) и прогоны раннера `pytest-own` не меняются (файла времени у
   них нет).
7. Тесты — новый файл в `tests/`, у каждого теста в докстринге строка
   «Ловит мутацию:»; состав — по критериям AC-1, AC-2, AC-3, AC-5, AC-6 (пункты
   (а)–(д) ТЗ). На текущем коде тесты AC-1, AC-2, AC-3 и AC-5 красные, тест
   AC-6 зелёный. Критерии AC-4 и AC-7 держит только планка задачи (см.
   «Не входит»).

## Критерии приёмки

AC-1. Чистая функция `orchestrator/suite_durations.durations(marks, start)` по
списку пар (время появления, строка) с двумя рабочими процессами считает время
каждого теста как разницу с временем предыдущей строки хода своего процесса (не
чужого); первую строку процесса — от времени строки `N workers [M items]`
(и `1 worker [1 item]`), а без такой строки — от `start`; повтор id узла в том
же процессе даёт одну запись с суммой времени и худшим исходом; строки не хода
и строки после первой секции отчёта (`suite_run._REPORT_SECTION`) пропускает.

AC-2. Прогон `_run_full_suite_to_log` маленького проекта песочницы с `-vv`
(два теста: быстрый и спящий 2 с, `config.FULL_SUITE_WORKERS` = 2,
`profile is None`) оставляет рядом с логом файл
`<имя лога без .log>.durations.tsv`, в котором есть строки обоих id узла с
рабочим процессом, исходом и секундами; у спящего теста не меньше 1,5 с, у
быстрого — меньше 1,5 с (время его строки берётся по появлению её байтов, а не
по приходу её `\n` вместе со строкой спящего теста). Лог прогона не содержит ни
одной строки файла времени.

AC-3. Оборванный пределом прогон `_run_full_suite_to_log` (предел 5 с через
параметр `limit`, спящий тест 30 с, быстрый тест завершается до обрыва)
оставляет файл времени со строкой быстрого теста, хотя его строка хода в логе
не завершена переводом строки.

AC-4. Имя файла времени (`….durations.tsv`, и для лога базы с `-base`) не
подпадает под шаблоны номеров логов `suite_run._new_log` и `agent_log`:
появление файла времени не сдвигает номер следующего лога.

AC-5. `suite_run._run` с подменой `run_full_suite`, отдающей готовый вывод
зелёного, красного и оборванного по пределу прогона и кладущей рядом с логом
файл времени больше среза (больше 30 тестов в больше чем 15 файлах, с повтором
одного id в том же процессе), дописывает в `report` после `render` блок «самые
медленные»: ровно 30 тестов и ровно 15 файлов, каждый список по убыванию
секунд, время файла — сумма времени его тестов, повтор id суммирован; каждая
строка блока начинается с двух пробелов и числа секунд. В режиме `--failed`
блок строится по файлу времени повтора; по прогону базы блок не печатается;
без файла времени (и с пустым файлом) блока нет. В тех же прогонах лог
побайтно равен логу, полученному без файла времени; блока нет ни в логе, ни в
`output`; `failed.json`, результат `parse(...)` и сохранённый итог базы те же,
что без файла времени; ключи `result.json` прежние.

AC-6. Шпион на запуск процесса полного прогона: argv и окружение
`run_full_suite` (с логом и без, `pult-pytest`) совпадают с теми, что были до
изменения; прогон с `log=None` и прогон раннера `pytest-own` файла времени не
создают.

AC-7. Сбой потока (файл времени не открывается на запись — на его месте
каталог) не меняет ни исход и `output` `_run_full_suite_to_log`, ни файл лога;
после возврата `_run_full_suite_to_log` (в том числе после снятия группы по
пределу) поток чтения не жив.

## Не входит
- Время тестов на гейтах (автогейт приёмки, гейт мержа, `notes`): прогон там
  без лога и без `-vv`, запись требует правки сверок окружения или argv —
  решение Оператора.
- `--durations` в CI (защищённый `.github/`).
- Ускорение самих тестов — отдельная задача по данным этой.
- Подъём предела 1500 с (только ADR Оператора).
- Файл времени у профиля с отчётом (`_run_full_suite_reported`,
  `orchestrator/acceptance.py:2569–2571`) — ТЗ ограничивает запись
  `profile is None`.
- Долгоживущие тесты в `tests/` на AC-4 (имя файла времени) и AC-7 (сбой потока,
  остановка потока): ТЗ перечисляет состав нового файла `tests/` пунктами
  (а)–(д); эти два свойства держит только планка задачи, после мержа
  долгоживущей защиты у них нет.
- Правки вне ограничения зон по смыслу: в `orchestrator/acceptance.py` — только
  `_run_full_suite_to_log` (запуск и остановка потока чтения) и новые функции;
  в `orchestrator/suite_run.py` — только дописывание блока в `report` в `_run`;
  разбор вывода и итога (`parse`, `_progress`, `render`) не меняется.
- Правка `targets.yaml`, `pyproject.toml`, `.github/workflows/ci.yml`,
  `orchestrator/config.py`, `orchestrator/agent_log.py`,
  `orchestrator/fsm_merge_gate.py`, `orchestrator/notes.py` — только чтение.
- Правка существующих тестов (требование 7 ТЗ): подмены `run_full_suite` с
  узкой сигнатурой (`tests/test_approve_acceptance_full_suite.py:74`,
  `tests/test_fsm_merge_gate_remote_branch_cleanup.py:191`,
  `tests/test_doc_commit_suite_gate.py:98`) обязаны работать как есть;
  неизменность существующих тестов и полный зелёный набор `tests/` держит
  пульт.
