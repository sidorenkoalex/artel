# ТЗ: suite-run записывает время каждого теста полного прогона по отметкам времени строк хода

# suite-run записывает время каждого теста полного прогона по отметкам времени строк хода

## Факты

Строка копилки «в логах полного прогона нет --durations» и строки бэклога «Ускорение полного набора тестов артели», «Время файла outcome_prior (G3б-2)» (состояние от 23.10). Сверено с `origin/main` 55d469fd (код `orchestrator/` и `tests/` совпадает с пином 870aa7e9).

- С 21.10 в журнале 16 полных прогонов выше 80 % предела, 7 из них оборваны по пределу; три — 23.10, после мержа 9e29a444 (1451, 1500, 1345 с). Предел 1500 с задаёт профиль проекта (`targets.yaml:53`, `full_suite_timeout_sec`; умолчание `config.FULL_SUITE_TIMEOUT_SEC` = 900). Какие тесты и файлы съедают время, по журналу и логам не видно: сводку `--durations` pytest печатает только в конце, а оборванный прогон до неё не доходит.
- argv полного прогона (`run_full_suite` в `orchestrator/acceptance.py`: `_pytest_command(...)` + `-n <FULL_SUITE_WORKERS> -p xdist` + `extra`) сверяют целиком десять мест в девяти тестовых файлах (`tests/test_suite_run.py:353–358`, `tests/test_01m56kcvctw5bv9twth54tw9q9_pult_pytest_unchanged.py:230–231` и другие); окружение прогона сверяют точно `tests/test_01m52eedeyv14658x8vfnhcw8k_launch_places.py:152–175` (три теста `test_ac7_full_suite_*`) и долгоживущий `tests/test_01m56kcvctw5bv9twth54tw9q9_pult_pytest_unchanged.py:295–311`. Поэтому ни argv, ни окружение полного прогона менять нельзя без правки существующих тестов.
- `suite-run` передаёт `extra = ("-vv",)` (`orchestrator/suite_run.py:73`): рабочие процессы xdist печатают по строке на завершённый тест с меткой процесса и исходом (`[gwN] [ NN%] PASSED <id узла>`); их уже разбирает `suite_run._progress` (`_PROGRESS`, `_REPORT_SECTION`).
- Прогон с логом идёт через `_run_full_suite_to_log` (`orchestrator/acceptance.py:2854`): вывод процесса пишется прямо в файл лога (`stdout=fh`, `PYTHONUNBUFFERED=1`), пульт ждёт `proc.wait(timeout=…)`, по пределу снимает группу процессов и читает лог целиком. Гейты (автогейт приёмки, гейт мержа, `notes`) зовут `run_full_suite` без лога и без `-vv` — в задачу не входят.
- Подмены `run_full_suite` в тестах написаны с узкой сигнатурой (`lambda root:` — `tests/test_approve_acceptance_full_suite.py:74`, `tests/test_fsm_merge_gate_remote_branch_cleanup.py:191`, `tests/test_doc_commit_suite_gate.py:98` (`def run(root):`)).

## Требования

1. Пока идёт прогон `_run_full_suite_to_log` при `profile is None` (раннер `pult-pytest`; у `pytest-own` файла времени нет), пульт в отдельном потоке читает прирост файла лога (не реже раза в 0,5 с) и для каждой новой полной строки хода вида `[gwN] … <ИСХОД> <id узла>` (исходы — те, что распознаёт `suite_run._PROGRESS`) записывает время её появления. Читаются только строки до первой секции отчёта (`suite_run._REPORT_SECTION`), как в `_progress`; неполная последняя строка (без перевода строки) ждёт следующего чтения. Время теста — разница между появлением его строки и предыдущей строки хода того же рабочего процесса `gwN`; у первой строки процесса — от появления строки вида `^\d+ workers \[\d+ items\]`, а если её нет — от начала прогона. Повтор id узла в том же процессе (например, `PASSED`, затем `ERROR` на завершении фикстуры) прибавляет время к записи этого id, исход — худший (как в `_progress`).
2. Поток — фоновый (daemon), не использует `acceptance.subprocess`, не меняет ни файл лога, ни процесс pytest; после `proc.wait` (и после снятия группы процессов по пределу) он останавливается, пульт ждёт его не дольше 2 с, поток один раз дочитывает остаток лога. Сбой потока прогон, итог и лог не меняет.
3. Отметки пишутся в файл рядом с логом: `<имя лога без .log>.durations.tsv` (и для прогона базы `-base`), строка на тест — id узла, рабочий процесс, исход, секунды; строка дописывается и сбрасывается (`flush`, без `fsync`) по мере появления, поэтому файл заполнен и при обрыве прогона по пределу. Имя не подпадает под шаблоны номеров логов (`suite_run._new_log`, `agent_log`).
4. После прогона ветки (зелёного, красного и оборванного по пределу; в режиме `--failed` — по повтору) `suite-run` дописывает в поле `report` в `_run` после `render` (тем же приёмом, что `suite_load_line`) блок «самые медленные»: 30 тестов и 15 файлов (сумма времени их тестов) с секундами; строки блока начинаются с двух пробелов и числа секунд. Блок не попадает ни в лог pytest, ни в `output` прогона; новых ключей `result.json` нет; по прогону базы блок не печатается.
5. argv и окружение полного прогона, ключ кэша итога, сигнатура `run_full_suite` и вызовы из гейтов и `notes` не меняются. Прогоны без лога (`log=None`) и прогоны раннера `pytest-own` не меняются.
6. Тесты (новый файл в `tests/`; у каждого в докстринге строка «Ловит мутацию:»): (а) разбор отметок — чистая функция: по списку (время появления, строка) с двумя рабочими процессами считает время каждого теста как разницу внутри своего процесса, первую строку процесса — от строки `N workers [M items]`, повтор id суммирует, строки не хода и строки после секции отчёта пропускает; (б) прогон `_run_full_suite_to_log` маленького проекта песочницы с `-vv` (два теста, один спит 2 с, `config.FULL_SUITE_WORKERS` = 2): файл времени содержит оба id узла, у спящего не меньше 1,5 с; (в) оборванный пределом прогон (предел 5 с через параметр `limit`, спящий тест 30 с, быстрый тест завершается до обрыва): файл времени содержит строку быстрого теста; (г) `suite_run._run` с подменой `run_full_suite`, отдающей готовый вывод зелёного и красного прогона и файл времени: блок «самые медленные» есть в `report`; лог побайтно равен логу без файла времени; `failed.json`, `parse(...)` и сохранённый итог базы те же; (д) шпион на запуск процесса: argv и окружение совпадают с теми, что были до изменения. На текущем коде (а)–(г) красные, (д) зелёный.
7. Существующие тесты не правятся и остаются зелёными.

Зоны: orchestrator/acceptance.py, orchestrator/suite_run.py, новый модуль разбора отметок в orchestrator/, docs/codebase-map.md, tests/

Ограничение зон по смыслу: в `orchestrator/acceptance.py` — только `_run_full_suite_to_log` (запуск и остановка потока чтения) и новые функции; в `orchestrator/suite_run.py` — только дописывание блока в `report` в `_run`; разбор вывода и итога не меняется.

Только чтение: targets.yaml (защищённый путь, профиль artel), pyproject.toml (защищённый), .github/workflows/ci.yml (защищённый), orchestrator/config.py, orchestrator/agent_log.py, orchestrator/fsm_merge_gate.py, orchestrator/notes.py.

Не входит: время тестов на гейтах (прогон без лога и без `-vv`; запись там требует правки сверок окружения или argv — решение Оператора); `--durations` в CI (защищённый `.github/`); ускорение самих тестов — отдельная задача по данным этой; подъём предела 1500 с (только ADR Оператора).
