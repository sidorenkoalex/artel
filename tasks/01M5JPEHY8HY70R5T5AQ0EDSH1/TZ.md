# Зависимость merge_after с общей зоной держит старт последователя в любом незавершённом состоянии

## Факты

Строка копилки `docs/backlog.md` «Взаимная блокировка зоны и порядка мержа» (13.10, приоритет 1). Дефект воспроизводится по коду на origin/main 524ea93b (сверено).

**Граница задачи одной фразой:** меняется только правило «своя незавершённая зависимость ждёт ту же зону» в решении о старте первого шага разработчика и показ взаимной блокировки в `doctor`; кто держит зону, очередь зоны без зависимостей, отказы гейтов и порядок мержа — прежние.

- Решение о старте — `orchestrator/zone_lock.py:565` (`_start_conflict`): держатель пересекающейся зоны (`_occupier`, :487), затем своя ждущая зависимость (`_waiting_dependency`, :537), затем очередь (`queue_order`).
- `_waiting_dependency` ищет зависимость только среди состава очереди (`_queue_members`, :504) — задач в `in_dev`, которые зону ещё не занимают. Зависимость в `escalated` до первого шага разработчика, а также в `spec_writing`, `spec_audit`, `spec_gate`, `tests_writing` в состав не входит и старт последователя не держит. Учитывается только прямая зависимость, транзитивная (`_ancestors`, :785) — нет.
- Итог (13.10, две пары одновременно): последователь получил зону, пока его зависимость стояла в `escalated`, дошёл до `merge_gate` и держит зону до мержа, а мерж ему запрещён до мержа зависимости (`merge_after.merge_gate_refuses`); зависимость, вернувшись в `in_dev`, ждёт ту же зону. 01M4RZB928 держал orchestrator/report.py, ждал мержа 01M4RZAYH3; 01M4RZBPG6 держал orchestrator/brief.py и orchestrator/role_prompt.py, ждал мержа 01M4RZBDFS. Выход был только ручной — `answer` со строкой «Зависимости мержа: нет».
- Тот же приём `_waiting_dependency` решает, держит ли ожидающая задача очередь (`_holds_queue`, :547); показ ожидания — `queue_wait` (:834), его читают `status` (`orchestrator/catalog.py:885`) и `doctor` (`orchestrator/doctor/hung_test_watchdog.py:271`, `check_zone_waits`).
- Штатные выходы Оператора уже есть и не меняются: `answer <id> <файл>` со строкой «Зависимости мержа: …» в `in_dev` и `merge_gate` (`orchestrator/answer.py:399–402`), `zone-release <id>` (`orchestrator/zone_lock.py:696`).

## Требуется

1. **Зависимость держит старт в любом незавершённом состоянии.** Первый шаг разработчика задачи не стартует, пока у неё есть зависимость `merge_after` — прямая или транзитивная — в любом состоянии, кроме `done` и `killed`, чьи зоны пересекаются с её зонами (тем же правилом пересечения, что у очереди: `_shared_zone`, с учётом вложенности). Вид конфликта — прежний «зависимость»: отказ и показ — «зона <путь> свободна, ждёт зону ради зависимости <id> (<состояние зависимости>)», состояние названо. Если зону уже занимает другая задача — главнее прежний конфликт «занята» (требование 5 SPEC 01M4JC5B3T не меняется). Зависимость, которой нет в БД, `done` или `killed`, старт не держит.
2. **Очередь и показ — то же решение.** `_holds_queue`, `queue_wait`, `status` и `doctor` используют то же правило требования 1: задача, ждущая зону ради зависимости, очередь не держит; `status` и `doctor` называют зависимость и её состояние. Порядок очереди без зависимостей, `zone-reorder` и правило «эскалированная задача, не являющаяся зависимостью, очередь не держит» — прежние.
3. **`doctor` называет уже возникшую взаимную блокировку.** Если задача в `in_dev` ждёт зону, занятую задачей, которая от неё зависит по `merge_after` (прямо или транзитивно), проверка `zone-waits` пишет для неё «взаимная блокировка с <id держателя> по merge_after» и выходы: `answer <id держателя> <файл>` со строкой «Зависимости мержа: …» либо `zone-release <id>`. Уровень — прежний `warn`, не incident.
4. **Неослабление.** Держатель зоны по-прежнему главнее; занятость, захват `claim` и его атомарность, `zone-release`, отказы `merge_gate` по `merge_after` и мандаты `answer` — прежние побайтно. Существующие тесты без правок и зелёные.
5. **Тесты** (детерминированы, без сети; песочница — приём `ZoneQueueSandbox` из tests/test_01m4jc5b3tyfcvy51rkz1am1vf_zone_queue_start.py, новые файлы в tests/):
   - зависимость A с пересекающейся зоной в каждом из состояний `escalated` (до первого шага разработчика), `spec_writing`, `spec_audit`, `spec_gate`, `tests_writing` — `claim` последователя C отказывает «ждёт зону ради зависимости A», текст называет состояние A; A переводится в `done`, затем отдельно в `killed` — `claim` C проходит;
   - транзитивная цепочка C → B → A, зона общая только у C и A, A в `escalated` — `claim` C отказывает с именем A;
   - зависимость без общей зоны в любом состоянии старт не держит; задача без `merge_after` в `escalated` очередь не держит (прежний сценарий AC-5 SPEC 01M4JC5B3T);
   - `status` и `doctor` для C называют A и его состояние, C помечен «не держит очередь», когда в очереди есть другие;
   - взаимная блокировка: C занимает зону (старт разработчика записан) и стоит в `merge_gate`, A — зависимость C — в `in_dev` ждёт ту же зону; `doctor` для A пишет «взаимная блокировка с C по merge_after» и оба выхода;
   - мутации, которые тесты ловят: зависимость ищется только в составе очереди (прежнее правило); не учитывается транзитивная зависимость; `killed`-зависимость держит старт; конфликт «зависимость» становится главнее конфликта «занята».
