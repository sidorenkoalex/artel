## Пути обхода гейтов
1. **Планка без живого цикла C** (AC-6). Тест-автор может сделать C без lease,
   и тогда пометка «не держит очередь» появится и при прежнем `_holds_queue`
   (zone_lock.py:558). Требование 2 в части `_holds_queue` останется непроверенным,
   а реализация, правящая только `_start_conflict`, пройдёт приёмку. При этом D
   позади живой C будет стоять «впереди C», хотя C стартовать не может: задача
   так лечит один тупик и создаёт другой.
2. **Обнаружение взаимной блокировки разбором текста.** Doctor может искать id
   держателя в `wait.reason` («занята <id> (…)», zone_lock.py:604) вместо
   `blocking_conflict`. AC-7 этого не различает. Это хрупко, но гейт не нарушает —
   стиль, на ревью.
3. **Первый держатель вместо всех.** `_occupier` возвращает первого найденного
   держателя (zone_lock.py:487–501). Если зону A одновременно занимают посторонняя X
   и зависящая от A задача C (пересечение по разным путям), то doctor, опирающийся
   на `blocking_conflict`, назовёт X и пропустит взаимную блокировку с C. AC-7
   строит сценарий с одним держателем — такая реализация проходит.
4. **Подсказка `auto` возвращает тупик** (вне зон, auto.py:200–202 — только
   чтение). На потолке ожидания `auto` советует `zone-release <id>`. Для C, ждущей
   зависимость, этот совет делает C держателем (`RELEASE_ACTION` поднимает
   `_occupies`, zone_lock.py:428–429) — и это ровно та взаимная блокировка, которую
   задача устраняет. Требование 3 её хотя бы покажет; правка подсказки — «Не
   входит». Это сведения Оператору, не отклонение SPEC.

## Вердикт
**concerns** — SPEC можно вести на гейт, но Оператору нужно решить пункты 1–2
(сам их снять я не могу).

1. **AC-6/AC-9 не ловят мутацию «`_holds_queue` по прежнему правилу»**
   (SPEC.md:85–87, :97–99; код zone_lock.py:547–562, :558). Требование 2
   (SPEC.md:41–45) называет `_holds_queue` прямо, но ни один критерий не требует
   живого цикла C и старта следующей в очереди задачи. Предложение: дополнить
   AC-6 так — «C с живым lease ждёт зависимость A (`escalated`), D позади C в той
   же зоне: `claim` D проходит» — и внести эту мутацию в AC-9.
2. **Выход «`answer <id держателя> <файл>`» не всегда исполним** (SPEC.md:46–51,
   AC-7 SPEC.md:88–92). `answer` принимает строку «Зависимости мержа» только в
   `escalated`/`in_dev`/`review`/`merge_gate` (answer.py:400–427), а для держателя в
   `verifying`/`acceptance` отказывает (answer.py:438–440). Требование 3 велит
   doctor печатать этот выход всегда. AC-7 проверяет только `merge_gate`. Решение
   Оператора: печатать `answer` только в состояниях, где он работает (и что
   печатать иначе), либо принять как есть. Это из ТЗ; правка самого `answer` —
   «Не входит».
3. **Несколько держателей** (zone_lock.py:487–501; SPEC.md:46–51). Взаимная
   блокировка, при которой зону A держат и посторонняя задача, и зависящая от A,
   критериями не покрыта, и реализация через первого держателя её пропустит.
   Лёгкое: можно принять как есть.
4. **Транзитивный обход через убитую промежуточную задачу** (SPEC.md:34–37;
   zone_lock.py:785–797). Для цепочки C → B(`killed`) → A правило «прямая или
   транзитивная, кроме `done`/`killed`» не говорит, держит ли A старт C через
   убитую B. `_ancestors` обходит любые состояния. Мерж C при убитой B всё равно
   бессрочно заблокирован (merge_after.py:420–429) до `answer`. Лёгкое: по
   умолчанию обход как у `_ancestors`.
5. **«И зелёные» из ТЗ п. 4** перенесено на гейт пульта (SPEC.md:54, :94, :118).
   Свойство держит гейт полного прогона. Сведения Оператору, не блокер.
