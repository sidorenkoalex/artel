# SPEC: Зависимость merge_after с общей зоной держит старт последователя в любом незавершённом состоянии

## Контекст
Решение о старте первого шага разработчика — `orchestrator/zone_lock.py::_start_conflict`:
держатель пересекающейся зоны (`_occupier`), затем своя ждущая зависимость
(`_waiting_dependency`), затем очередь (`queue_order`). `_waiting_dependency` ищет
зависимость только в составе очереди (`_queue_members` — задачи в `in_dev`, зону ещё не
занимающие), и только прямую. Зависимость в `escalated` до первого шага разработчика,
в `spec_writing`, `spec_audit`, `spec_gate`, `tests_writing` старт последователя не держит.
13.10 две пары (01M4RZB928 ← 01M4RZAYH3 по `orchestrator/report.py`; 01M4RZBPG6 ←
01M4RZBDFS по `orchestrator/brief.py`, `orchestrator/role_prompt.py`) попали во взаимную
блокировку: последователь держит зону до мержа, мерж ему запрещён до мержа зависимости
(`merge_after.merge_gate_refuses`), зависимость ждёт ту же зону. Выход был только ручной —
`answer` со строкой «Зависимости мержа: нет».

Граница задачи: меняется только правило «своя незавершённая зависимость ждёт ту же зону» в
решении о старте первого шага разработчика и показ взаимной блокировки в `doctor`; кто держит
зону, очередь зоны без зависимостей, отказы гейтов и порядок мержа — прежние.

## Требования

1. **Зависимость держит старт в любом незавершённом состоянии.** Первый шаг разработчика
   задачи не стартует, пока у неё есть зависимость `merge_after` — прямая или транзитивная —
   в любом состоянии, кроме `done` и `killed`, чьи зоны пересекаются с её зонами (тем же
   правилом пересечения, что у очереди: `_shared_zone`, с учётом вложенности). Вид
   конфликта — прежний «зависимость»: отказ и показ — «зона <путь> свободна, ждёт зону ради
   зависимости <id> (<состояние зависимости>)», состояние названо. Если зону уже занимает
   другая задача — главнее прежний конфликт «занята» (требование 5 SPEC
   01M4JC5B3TYFCVY51RKZ1AM1VF не меняется). Зависимость, которой нет в БД, `done` или
   `killed`, старт не держит.
2. **Очередь и показ — то же решение.** `_holds_queue`, `queue_wait`, `status` и `doctor`
   используют то же правило требования 1: задача, ждущая зону ради зависимости, очередь не
   держит; `status` и `doctor` называют зависимость и её состояние. Порядок очереди без
   зависимостей, `zone-reorder` и правило «эскалированная задача, не являющаяся
   зависимостью, очередь не держит» — прежние.
3. **`doctor` называет уже возникшую взаимную блокировку.** Если задача в `in_dev` ждёт
   зону, занятую задачей, которая от неё зависит по `merge_after` (прямо или транзитивно),
   проверка `zone-waits` (`orchestrator/doctor/hung_test_watchdog.py::check_zone_waits`)
   пишет для неё «взаимная блокировка с <id держателя> по merge_after» и выходы. Выход
   `answer <id держателя> <файл>` со строкой «Зависимости мержа: …» печатается в этом виде,
   только когда держатель в `escalated`, `in_dev`, `review` или `merge_gate`; в остальных
   состояниях держателя — в виде «после перехода держателя в merge_gate: answer <id
   держателя> <файл> со строкой „Зависимости мержа: …“». Второй выход — `zone-release <id>`
   — печатается в обоих случаях. Уровень — прежний `warn`, не incident.
4. **Неослабление.** Держатель зоны по-прежнему главнее; занятость, захват `claim` и его
   атомарность, `zone-release`, отказы `merge_gate` по `merge_after` и мандаты `answer` —
   прежние побайтно. Существующие тесты без правок.
5. **Тесты** — детерминированы, без сети; песочница — приём `ZoneQueueSandbox` из
   `tests/test_01m4jc5b3tyfcvy51rkz1am1vf_zone_queue_start.py`, новые файлы в `tests/`;
   покрывают сценарии критериев AC-1…AC-8 и ловят мутации AC-9.

Ограничение зон по смыслу (из ТЗ): в `orchestrator/zone_lock.py` — только
`_waiting_dependency` и её вызовы в `_start_conflict`, `_holds_queue`, `queue_wait`, текст
`_reason` для вида «зависимость»; в `orchestrator/doctor/hung_test_watchdog.py` — только
`check_zone_waits`.

## Критерии приёмки

AC-1. Зависимость A задачи C (`merge_after` C = A) с пересекающейся зоной в каждом из
состояний `escalated` (до первого шага разработчика A), `spec_writing`, `spec_audit`,
`spec_gate`, `tests_writing`: `claim` C (в `in_dev`, зона свободна) отказывает текстом,
содержащим «ждёт зону ради зависимости A» и название состояния A.

AC-2. После перевода A из AC-1 в `done` `claim` C проходит; отдельно — после перевода A в
`killed` `claim` C проходит. Зависимость, которой нет в БД, старт C не держит.

AC-3. Транзитивная цепочка C → B → A по `merge_after`, зона общая только у C и A, A в
`escalated`: `claim` C отказывает, отказ называет A.

AC-4. Зависимость без общей зоны с C в любом незавершённом состоянии старт C не держит;
задача без `merge_after` в `escalated` очередь не держит (прежний сценарий AC-5 SPEC
01M4JC5B3TYFCVY51RKZ1AM1VF).

AC-5. Если пересекающуюся зону C уже занимает другая задача, а зависимость A с общей зоной
не завершена, отказ `claim` C — прежний конфликт «занята» с именем держателя, не конфликт
«зависимость».

AC-6. `status` и `doctor` (`zone-waits`) для C из AC-1 называют A и состояние A; при
наличии в очереди зоны других ожидающих задач C помечена «не держит очередь». Отдельно:
C в `in_dev` с живым циклом (живой lease) ждёт зависимость A в `escalated` (A с
пересекающейся зоной, зону никто не занимает), задача D в `in_dev` стоит в очереди той же
зоны позади C: `claim` D проходит, а C в показе `status` и `doctor` (`zone-waits`) несёт
пометку «не держит очередь».

AC-7. Взаимная блокировка: C занимает зону (старт разработчика записан) и стоит в
`merge_gate`, A — зависимость C — в `in_dev` ждёт ту же зону: `doctor` в проверке
`zone-waits` для A пишет «взаимная блокировка с C по merge_after» и оба выхода —
`answer C <файл>` со строкой «Зависимости мержа: …» (без оговорки «после перехода
держателя в merge_gate») и `zone-release A`; уровень проверки `warn`. То же при
транзитивной зависимости держателя от A. Отдельно — тот же сценарий с держателем C в
`verifying`: выход `answer` напечатан в виде «после перехода держателя в merge_gate: answer
C <файл> …», `zone-release A` напечатан; уровень `warn`.

AC-8. Существующие тесты `tests/test_zone_lock.py` и
`tests/test_01m4jc5b3tyfcvy51rkz1am1vf_zone_queue_start.py` не правятся.

AC-9. Тесты задачи краснеют на каждой из мутаций: зависимость ищется только в составе
очереди (прежнее правило) в `_start_conflict`; `_holds_queue` по прежнему правилу
(зависимость ищется только в составе очереди); не учитывается транзитивная зависимость; `killed`-зависимость
держит старт; конфликт «зависимость» становится главнее конфликта «занята».
