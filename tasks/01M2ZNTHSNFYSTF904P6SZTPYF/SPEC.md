# SPEC: Интерфейс исполнителя роли, часть 1: команда, окружение, дом, предполётные проверки

## Контекст

Знание о Claude Code как исполнителе роли сегодня размазано по пульту
литералами: argv шага собирает `orchestrator/runner.py::role_cmd()`,
окружение — `role_env()`, манифест инструмента и вердикт модели —
`orchestrator/stack.py`, предполётные проверки — `orchestrator/doctor/`,
развёртывание дома роли — `orchestrator/catalog.py`. `roles.yaml` знает
про `executor` и `model`, но провайдера не называет. Пока это один
исполнитель, дублирование терпимо; запуск ролей на другом CLI начинается
с того, чтобы собрать всё это в один интерфейс провайдера. Задача — 1 из
плана провайдеров ролей, принятого Оператором 20.09: чистый рефакторинг
без изменения поведения, любое отличие argv/env от сегодняшних —
дефект.

## Требования

1. Пакет `orchestrator/providers/` несёт базовый интерфейс провайдера
   исполнителя роли (`orchestrator/providers/base.py`) с методами:
   `command(model)` — argv шага; `environment(role, task_id)` —
   переменные окружения, специфичные для провайдера (HOME/конфиг/
   секрет), поверх общего белого списка runner; `home_reference()` —
   путь к референсу дома роли и имя развёрнутого каталога;
   `preflight(role)` — список проверок до старта (CLI найден, версия,
   секрет, дом роли) в форме `doctor.Check`/`stack.StackCheck`, как
   сегодня; `cli_tool()` — имя инструмента манифеста и минимальная
   версия; `model_verdict(model)` — вердикт совместимости модели с
   установленным CLI.
2. `orchestrator/providers/claude.py` реализует этот интерфейс ровно
   сегодняшними значениями и вызовами: те же функции
   runner/stack/предполётных проверок переезжают в него либо зовутся из
   него.
3. `orchestrator/roles.py` получает `provider(role)`: значение поля
   `provider:` роли, а при отсутствии поля — `claude`. Сам `roles.yaml`
   в этой задаче не меняется.
4. Реестр провайдеров — словарь в `orchestrator/providers/__init__.py`.
   Неизвестное имя провайдера даёт именованный отказ `run`/`auto` до
   старта агента («провайдер <имя> роли <роль> не зарегистрирован») и
   красную строку `doctor`.
5. Runner зовёт провайдера, а не литералы: `role_cmd()` и `role_env()`
   сохраняют сигнатуры и результат байт-в-байт, но внутри берут
   провайдерские части из реестра по `roles.provider(role)`.
   `role_cmd()` остаётся без параметров — провайдер роли берётся из
   активного шага через существующий контекст вызывающего кода, не
   через глобальную переменную окружения. `_refuse_before_start` и
   `_resolved_role_model` получают вердикт модели через провайдера.
6. Стек и предполётные проверки идут через провайдера: инструмент
   провайдера объявляется провайдером в `stack.REQUIRED_TOOLS` (для
   `claude` — тот же обязательный инструмент, что сегодня); проверки
   «CLI найден», «версия CLI», «секрет», «дом роли» выполняются через
   `preflight()` провайдера каждой agent-роли — сегодня провайдер один,
   результат тот же набор проверок без дублей; офлайн-смок изоляции и
   живой смок в `orchestrator/doctor/` берут argv и окружение через
   провайдера. Вывод `doctor` дополняется строкой «провайдеры ролей:
   <роль → провайдер>».
7. Дом роли: развёртывание референса при `init`
   (`orchestrator/catalog.py`) идёт по `home_reference()` провайдера —
   для `claude` тот же каталог референса и то же имя развёрнутого
   каталога, что сегодня; сверка развёрнутого слоя с референсом в
   `orchestrator/doctor/preflight.py` — тоже через провайдера.
8. `docs/stack.md` получает раздел «Провайдер исполнителя роли»: что
   входит в интерфейс, что остаётся общим у runner. Карта кодовой базы
   обновляется генератором как обычно.
9. Поведение для `claude` не меняется ни в одной точке: argv шага,
   окружение роли и развёрнутый дом роли совпадают с сегодняшними.

## Критерии приёмки

AC-1. `orchestrator/providers/base.py` объявляет базовый интерфейс
провайдера с методами `command(model)`, `environment(role, task_id)`,
`home_reference()`, `preflight(role)`, `cli_tool()`,
`model_verdict(model)`.

AC-2. `orchestrator/providers/__init__.py` несёт словарь-реестр
провайдеров, в котором зарегистрировано имя `claude`; запрос по этому
имени отдаёт реализацию из `orchestrator/providers/claude.py`.

AC-3. `roles.provider(role)` возвращает значение поля `provider:` роли,
а для роли без этого поля — `claude`.

AC-4. Роль с незарегистрированным именем провайдера: `run`/`auto`
отказывают до старта агента строкой «провайдер <имя> роли <роль> не
зарегистрирован» (агент не запускается), `doctor` даёт по этому поводу
красную строку.

AC-5. `role_cmd()` остаётся без параметров и возвращает argv,
совпадающий элемент в элемент с зафиксированным до задачи ожидаемым
списком (абсолютный путь инструмента, `-p`, `--permission-mode
acceptEdits`, `--output-format stream-json --verbose`, `--allowedTools`,
`--setting-sources`, `--strict-mcp-config`).

AC-6. `role_env(role, task_id)` сохраняет сигнатуру и даёт тот же набор
ключей и значений, что до задачи; PATH и путь интерпретатора
сравниваются по составу, остальные ключи — по значению.

AC-7. `_refuse_before_start` и `_resolved_role_model` берут вердикт
совместимости модели через `model_verdict(model)` провайдера; отказы до
старта агента по модели, CLI и секрету остаются прежними.

AC-8. `stack.REQUIRED_TOOLS` получает инструмент провайдера от самого
провайдера (`cli_tool()`): для `claude` — то же имя инструмента и тот же
минимум версии, что сегодня, и он по-прежнему обязательный.

AC-9. Проверки «CLI найден», «версия CLI», «секрет», «дом роли»
выполняются через `preflight()` провайдера каждой agent-роли и дают тот
же набор проверок, что сегодня, без дублей.

AC-10. Офлайн-смок изоляции и живой смок в `orchestrator/doctor/` берут
argv и окружение через провайдера; офлайн-часть обоих зелёная.

AC-11. Вывод `doctor` содержит строку «провайдеры ролей: <роль →
провайдер>».

AC-12. Развёртывание дома роли в `orchestrator/catalog.py` идёт по
`home_reference()` провайдера и даёт для `claude` тот же каталог
референса и то же имя развёрнутого каталога, что до задачи; сверка
развёрнутого слоя с референсом идёт через провайдера.

AC-13. `docs/stack.md` несёт раздел «Провайдер исполнителя роли» с
описанием состава интерфейса и того, что остаётся общим у runner.

AC-14. `tests/test_runner_role_model.py`,
`tests/test_runner_model_preflight.py`, `tests/test_stack.py`,
`tests/test_doctor.py`, `tests/test_doctor_canary_pool.py` остаются
зелёными.

## Оценка объёма и деление

Прогноз диффа: 35 КиБ.

Сработавшие сигналы: число затрагиваемых модулей/файлов зоны (8 записей
`zones:`); число критериев приёмки (14).

**Обоснование монолита.** Разрезать нечего: единственная ценность задачи
— в том, что после неё существует РОВНО ОДИН источник истины о том, что
нужно исполнителю роли. Любой разрез оставляет систему на время
merge-окна с двумя такими источниками: провайдер знает флаги и
окружение, а `orchestrator/stack.py`/`orchestrator/doctor/`
по-прежнему несут те же значения литералами — это ровно тот дефект,
который задача устраняет, и синхронизировать их руками пришлось бы
именно в промежуточном состоянии. Планка задачи («argv и env
байт-в-байт те же») проверяема только в один ход: часть, где провайдер
уже введён, но runner ещё не зовёт его, не даёт этой проверке предмета,
а часть, где зовёт только runner, не покрывает `doctor`/`stack`/
`catalog`, которые сегодня собирают те же значения сами. Сам объём
умеренный и в основном переносной (поведение не меняется, прогноз диффа
35 КиБ), задача уже является частью 1 из пяти в плане, поделённом
Оператором 20.09.

Расхождение с калибровкой отмечаю явно: при 8 записях зон и 14
критериях приёмки калибровочный ориентир — ~$70, рамка Оператора в
ТЗ — $45, её и ставлю. Если гейт SPEC посчитает рамку заниженной,
поднять её вправе только Оператор командой `budget`.
