# PLAN: Guard планки: артефакты задачи читаются только из артефактной ветки, отказ на выходе tests_writing

## Подход

Три зоны SPEC — три правки, одна механика. Итерация 2 (после ANSWER-1
Оператора на эскалацию ревьювера, вариант B): правило требования 1
уточнено — ошибка только по пути, якоренному на рабочую копию.

1. **`scripts/guard.py` — статическая проверка по AST, не по тексту
   строки.** Функция `artifact_disk_read_errors_from_files(files)`
   над уже прочитанными `(label, текст)` парами (тот же приём, что
   `redness_marker_errors_from_files`/`indented_ac_marker_errors_from_files`)
   и обёртка `scan_artifact_disk_reads(tdir)` над ВСЕМИ
   `acceptance_tests/**/*.py` (не только `test_*.py` — AC-5). Нарушение —
   строковый литерал с именем из `ARTIFACT_FILE_NAMES` (`PLAN.md`,
   `SPEC.md`, `REVIEW.md`, `TZ.md`, `QUESTIONS.md`, `TEST_REPORT.md`,
   `ANSWER-`) внутри выражения доступа к файловой системе — операнд `/`
   или поддерево вызова `open`/`Path`/`pathlib.Path`/`os.path.join`/
   `os.path.exists`/`.read_text(`/`.joinpath(` (включая цепочку получателя —
   `TASK_DIR.joinpath("PLAN.md").read_text()`), — **и только если путь
   этого выражения якорится на рабочую копию (ANSWER-1, вариант B)**:
   предикат `_is_anchored(node, names)` — `__file__`, атрибут с суффиксом
   `config.ROOT`/`config.TASKS`, корневой литерал `tasks/…` (голое `tasks`
   — только первым аргументом вызова/корнем цепочки, не правым операндом
   `/` посреди `Path(tmp) / "tasks" / TASK / "SPEC.md"`), далее
   транзитивно по получателю атрибута/подписки/метода, по первому
   аргументу вызова, по левому операнду `/` и `+`, по началу f-строки;
   `_anchored_names(tree)` — имена, присвоенные от якорных выражений, с
   замыканием по цепочке присваиваний (`TASK_DIR = Path(__file__)…`,
   `PLAN_DIR = TASK_DIR.parent`), без различения областей видимости
   (в планке имя каталога задачи одно, цена различения — пропуск
   инцидентного чтения). Пути от временных каталогов (`tempfile`,
   `self.tdir` вложенной песочницы) не якорны — записи и чтения фикстур
   песочницы под правило не подпадают. AST выбран, потому что AC-4
   планки нарочно ставит имя артефакта в концевой комментарий строки с
   настоящим `open("fixture.txt")` — текстовая эвристика тут даёт ложную
   ошибку. `gitcmd.show`/`artifact_branch`/`subprocess.run` в набор
   выражений доступа не входят, поэтому требование 2 выполняется без
   отдельного белого списка. Текст ошибки — `<label>:<строка литерала>:
   чтение артефакта задачи <имя> с диска — читай из артефактной ветки:
   gitcmd.show(artifact_branch.branch_name(TASK_ID), "tasks/<id>/<имя>")`
   (требование 3); имя файла из литерала подставляется в рецепт только
   когда basename начинается с имени артефакта (`ANSWER-1.md`), иначе —
   само имя (R1-F2: часть f-строки `f"{TASK}-PLAN.md"` — литерал
   `-PLAN.md`, рецепт называет `PLAN.md`, не `-PLAN.md`). Файл с
   `SyntaxError` ошибок здесь не даёт — синтаксис ловит сухой сбор того же
   гейта точнее. Метка — путь относительно `tdir`
   (`acceptance_tests/test_x.py`): каталог на гейте — временная
   материализация, абсолютный путь в истории отказов брифа бесполезен.

2. **`orchestrator/advance_gates/tests_writing.py` — гейт.** Новый
   предикат `_tests_writing_artifact_source_gate(acc_tdir, task_id)`
   возвращает `GateRefusal("переход отклонён: планка читает артефакты с
   диска", "; ".join(errors), hint)` — тот же каркас `_run_gates`, что у
   сухого сбора, поэтому запись уходит `store.journal(..., "fsm", ...)` с
   префиксом «переход отклонён: », и история отказов брифа test_author
   (`brief.advance_refusal_history`) и стоп-кран T038 видят её тем же
   классом (AC-7); в `brief._ROLE_NOT_FINISHED_REFUSAL_ACTIONS` действие не
   вносится. **Ключевое решение:** предикат зовётся из
   `_tests_writing_dry_collect_gate` ДО `acceptance.collect`, а не
   отдельным элементом списка `_run_gates` в `fsm_advance.tests_writing`
   (`orchestrator/fsm_advance.py:337`) — этот файл не входит в зоны SPEC
   (`scripts/guard.py, orchestrator/advance_gates/tests_writing.py,
   tests/`), и гейт зон на `in_dev -> review` отказал бы правке. SPEC
   формулирует место как «рядом с сухим сбором» — вложение в тот же гейт
   этому соответствует; статическая проверка дешевле субпроцесса pytest и
   даёт точнее диагноз, поэтому идёт первой. Каталог — тот же `acc_tdir`,
   что у сухого сбора (`_tests_writing_acceptance_dir`): материализованная
   из ветки планка для внешнего target/worktree, `tdir` — для остального.

3. **`tests/` — два новых файла**, `check()`/`main()` guard не трогаются
   (требование 4/AC-8).

Бюджет: SPEC оценил $40, PLAN укладывается (три файла кода + два файла
тестов, ~330 строк диффа) — `budget_usd` не поднимается.

- **Ложные срабатывания — измерены прогоном `guard.scan_artifact_disk_reads`
  над всеми `tasks/*/acceptance_tests/` рабочей копии (R1-F3).** До

    фикстуру фиктивной задачи через `config.TASKS` (или имя, присвоенное
    от него: `task_dir`, `tdir`, `_dest_dir`) — `(config.TASKS / TASK /
    "SPEC.md").write_text(…)` в `_sandbox.py` 01M1GCN1, 01M1GV6H ×4,
    01M1SAA2 ×4, 01M1NKTF ×7, 01M1RQ12, 01M1SCQ6, 01M1TKP0 ×2, 01M28NWP,
    01M290PY, 01M2A22C, 01M2ARQM, T063, T071, T101. На исполнении
    `config.TASKS` там подменён временным каталогом, но статически путь
    якорится на `config.TASKS`, который ANSWER-1 прямо называет якорем, —
    по правилу B эти строки ошибочны. **Ожидание ANSWER-1 «после B ложных
    срабатываний в песочницах планок быть не должно» выполняется для
    песочниц с путями от `tempfile`/`self.tdir` (все 12 планок сентября с
    приёмом `LightTransitionSandbox`, включая планку задачи) и НЕ
    выполняется для песочниц, пишущих `config.TASKS` в тексте — их 14 в
    истории, последняя 01M2ARQM.** Это следствие текста ANSWER-1, не
    выбор разработчика; сузить якорь `config.TASKS` (например, не считать
    его якорем в файле, который патчит `config`) без нового решения
    Оператора нельзя. Живого эффекта нет: исторические планки гейт не
    пересекают; для новых планок в диф к `skills/test-authoring.md` внесена
    фраза «путь через `config.TASKS`/`config.ROOT` — якорный, даже если
    песочница подменяет их временным каталогом: бери `self.tdir`».
  - Прочий остаточный класс: литерал имени артефакта внутри якорного
    выражения к постороннему файлу с похожим именем (`TASK_DIR /
    "MY_PLAN.md"`) — подстрочное совпадение, роль получит отказ с
    файлом/строкой и переименует фикстуру.
- **Пропуски правила (ложноотрицательные)** — путь через переменную,
  присвоенную атрибутом (`self.task_dir = Path(__file__)…` и далее
  `self.task_dir / "PLAN.md"`): атрибуты не трассируются, чтобы не
  ловить `self.tdir` песочницы; такой инцидент гейт не остановит, его
  поймает красная планка на первом прогоне пультом, как до задачи.
- **Откат** — revert одного merge-коммита: новые функции guard никем, кроме
  гейта, не вызываются; строки `_tests_writing_dry_collect_gate`
  возвращаются к прежним.
- `orchestrator/pull.py`, `orchestrator/acceptance.py`, `orchestrator/amend.py`,
  `orchestrator/fsm_advance.py` не меняются (SPEC «Не входит», зоны).

## Риски

- Планка, у которой `acceptance_tests/` в момент гейта материализован из
  ветки (внешний target, self на своей ветке): проверка читает тот же
  каталог `acc_tdir`, что и сухой сбор, — если материализация вернула
  каталог без файлов (git не ответил), проверка молчит так же, как молчит
  сухой сбор на пустой планке; отдельного поведения не вводится.
- `amend-tests` новую проверку не зовёт (SPEC «Не входит», отдельное ТЗ по
  `orchestrator/amend.py:311–320`).
- Якорь `config.TASKS` ловит песочницы, пишущие его в тексте (14
  исторических планок, см. «Влияние»): первая новая планка с
  `(config.TASKS / TASK / "SPEC.md").write_text(…)` получит отказ с
  рецептом про артефактную ветку, который для записи фикстуры не по делу;
  подсказка гейта отсылает к скилу, где после применения дифа стоит
  фраза «бери `self.tdir`». Если Оператор сочтёт это лишним — сужение
  якоря отдельным решением, не этим MR.
- Имена якорятся по всему файлу без областей видимости: локальное имя
  `tdir`, в одной функции присвоенное от `config.TASKS`, а в другой — от
  `tempfile`, будет якорным в обеих. В 190 планках такого совпадения имён
  не встретилось.
