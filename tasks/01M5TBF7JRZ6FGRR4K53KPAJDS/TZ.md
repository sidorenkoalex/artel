# Эпики, шаг Э2б: надзирающий процесс эпика auto --epic

## Факты

ADR-0028 (принят 25.10.2026), уровень 2, п. 10; шаг Э2б после Э2а (конверт и `start_after` в `runner.py`).

1. `auto <id>` ведёт одну задачу отвязанным процессом (`orchestrator/artel.py` `_launch_detached`; `orchestrator/auto.py`), останавливается на гейтах Оператора; второй процесс на ту же задачу не запускается (живой lease).
2. Наблюдение `observe` (команды в `orchestrator/artel.py`, данные — `orchestrator/store.py`, `orchestrator/schema.py`) доставляет события задач в сессию Оператора.
3. Лимит параллельности — глобальный `MAX_PARALLEL_TASKS` (`orchestrator/config.py:409`).

## Требуется

1. `auto --epic <id>` — отвязанный долгоживущий процесс эпика с собственной блокировкой: второй `auto --epic` того же эпика — отказ с указанием живого процесса.
2. Для каждой задачи эпика, готовой к шагу (нет незавершённых `start_after`, конверт не исчерпан, не на гейте Оператора, нет живого lease другого процесса), запускает отвязанный `auto <id>` — не больше `epic parallel <id> N` одновременно (по умолчанию 1), не сверх `MAX_PARALLEL_TASKS`; очереди зон и merge-окна — как сейчас.
3. Гейты Оператора не проходит: дочерний `auto` останавливается как обычно; надзирающий процесс ждёт и после `approve` и мержа запускает задачи, у которых открылся `start_after`.
4. Дочерние задачи регистрируются в наблюдении эпика (`observe`), события приходят в сессию Оператора.
5. `epic stop <id>` останавливает надзирающий процесс и дочерние `auto` эпика штатным `stop` (не убийством процесса). Надзирающий процесс завершается сам, когда в эпике нет задач, которые можно вести (все окончательны или ждут Оператора/зависимостей без шансов продвинуться без него), с записью журнала.

Критерии приёмки:
- эпик из трёх задач, вторая `start_after` первой, `epic parallel 1`: запущена только первая; после её `done` — вторая; третья (без зависимостей) — после освобождения места;
- второй `auto --epic` — отказ с pid живого процесса;
- задача с живым lease чужого `auto` пропускается;
- задача на гейте SPEC — надзирающий процесс не запускает её снова и не вызывает `approve`;
- `epic stop` — надзирающий и дочерние процессы остановлены штатно (журнал `stop`, без `kill` процесса);
- исчерпанный конверт — новые задачи не запускаются, начатые продолжают.
