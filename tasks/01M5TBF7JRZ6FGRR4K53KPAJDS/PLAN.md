# PLAN: Эпики Э2б — надзирающий процесс эпика `auto --epic`

## Подход

Сверка с Э2а (требование 14) сделана первым шагом, расхождений нет:
маркер первого шага роли — `merge_after.role_step_started` («agent run
started»), ожидание `start_after` — `merge_after.start_after_pending`
(мёртвые — `killed`/пропавшие), конверт — `budget.epic_spent >= envelope_usd`
(`runner._first_step_refusal`).

Надзор — `auto.cmd_auto_epic`: отвязанный процесс `artel.py auto --epic <id>
--observation <ID> --attach`, цикл «разбор линии → запуски → сон
`EPIC_POLL_SEC`». Ключевые решения:

- **Блокировка** — своя таблица `epic_supervisors` (не `leases`). Запуск
  (`artel._launch_epic_supervisor`) делает дешёвую предпроверку: живая —
  отказ с pid, мёртвая — снятие с записью журнала; саму строку берёт
  надзирающий процесс своим `os.getpid()` в одной транзакции
  `BEGIN IMMEDIATE` (`auto._take_supervisor_lock`) — гонка двух запусков
  решается там, проигравший выходит с записью журнала. Живость — общая
  функция `lease.process_alive(pid, host, started_at)`: pid жив на этом
  хосте и `doctor.process_start_time(pid) <= started_at`; ею же сверяются
  дочерние `auto`.
- **Дочерние `auto`** — строки `epic_children` (pid, хост, время запуска,
  `step_id` = максимум журнала перед запуском). Исход запуска читается по
  записям задачи после `step_id` (`auto._child_holds`): отказ глобального
  лимита — не остановка; `auto остановлен` в гейте/эскалации/окончательном
  состоянии — не остановка «не на гейте»; иначе (`auto остановлен` в
  рабочем состоянии, `цикл оборван`, выход без записи — помечается записью
  задачи один раз) задача ждёт нового действия Оператора после этой
  записи. Перечень действий — записи автора `operator`: `state -> …`
  (approve/reject/budget), «ANSWER создан…» (answer/zones-extend),
  «бюджет изменён», «правка планки», «повтор CI ветки», `pause…`,
  `resume` (пишется только при снятии паузы), `epic retry`. Записи цикла
  `auto` и запуска дочернего в перечень не входят.
- **Готовность и место** — `auto._epic_view`: статус каждой
  неокончательной задачи (под дочерним, на гейте/в эскалации, ждёт
  Оператора, под чужим живым lease, ждёт `start_after`, заблокирована,
  готова), свободные места `min(parallel − живые дочерние,
  MAX_PARALLEL_TASKS − живые дочерние − прочие живые lease)`; живые lease —
  `parallel_limit.busy_other_tasks`, lease собственных живых дочерних в
  «прочие» не идут. Надзор живёт, пока есть задача не в статусе
  «заблокирована» (ожидание `start_after` на заблокированную — тоже
  заблокирована).
- **Запуск дочернего** — инъекция `launch_child` из `artel.py`
  (`_launch_epic_child`): `_launch_observation` (её отказ завершает надзор с
  записью и алертом) + `_spawn_detached`, вынесенный из `_launch_detached`
  без изменения поведения. Проверка `lease.is_live` (только heartbeat) в
  дочернем пути не делается: надзор уже сверил живость lease по pid, иначе
  lease мёртвого pid держал бы задачу (AC-18б). Перед запуском задача снова
  включается в набор наблюдения (`_cmd_stop` её оттуда выключает). Popen
  дочерних хранится и опрашивается `poll()` — вышедший не висит зомби с
  «живым» pid.
- **Наблюдение** — правило (а)/(б)/(в) в `artel._epic_observation`; при
  запуске все неокончательные задачи эпика добавляются в набор; сессия
  надзора — сессия наблюдения, отвязанному процессу передаётся
  `ARTEL_SESSION_ID`.
- **`epic stop`** — SIGTERM живому надзору (обработчик прерывает сон
  опроса, флаг проверяется перед каждым запуском), ожидание снятия его
  блокировки до `EPIC_STOP_WAIT_SEC`, затем SIGTERM живым дочерним из
  `epic_children`; мёртвая блокировка снимается без сигнала. `auto <id>`
  Оператора в `epic_children` нет — не трогается.
- **`watch`** — записи автора `store.EPIC_SUPERVISOR_ACTOR` с id эпика и
  алерты с `target` = id эпика доставляются, если в наборе есть задача
  этого эпика; записи надзора — без фильтра классов событий.

## Риски

- `process_start_time` через `ps` при сбое даёт `None` — дочерний считается
  не живым: место освобождается, а задача помечается «вышел без записи» и
  ждёт `epic retry`. Ложное удержание возможно только при сбое `ps`.
- Точность `ps -o lstart` — секунда; `started_at` пишется после `Popen`,
  тоже с отбрасыванием до секунды, поэтому старт ≤ записи для своего
  процесса.

## Предложения системе

- Журнальные действия команд Оператора (approve/answer/budget/…) не
  собраны в одном перечне — надзор эпика собирает их по модулям
  (`auto._operator_actions`); общий словарь «действие Оператора» в
  `store`/`refusal_classes` снял бы дубли при следующем потребителе.
- Отказ `run` по глобальному лимиту — литерал в `runner.py:229` без
  константы; надзору пришлось повторить строку (`auto._GLOBAL_LIMIT_REFUSAL_ACTION`).
