## Пути обхода гейтов

1. **Ручной `stop <id>` Оператора теряет силу.** Треб. 4 (SPEC.md:61–66)
   не блокирует перезапуск после остановки «по `stop`». Оператор, сделавший
   `artel.py stop <задача>` дочерней задаче эпика, увидит её перезапуск на
   следующем опросе надзора; `_cmd_stop` выключает задачу в наблюдении
   (`artel.py:1429`, `store.py:97–100`), а надзор по треб. 7 вернёт её
   (`store.add_observation_tasks`, `store.py:82–87`, `ON CONFLICT ... SET
   enabled=1`). Формулировка дословно следует решению гейта 26.10 (1), но
   следствие для одиночного `stop` в нём не разобрано, AC на него нет —
   отклонение 2.
2. **«Действие Оператора» неотличимо от записей самого пульта.** Цикл `auto`
   пишет свои записи актором `"operator"` (`auto.py:582` `auto_stop`,
   `:1008` старт цикла, `:183/:190/:228` ожидание зоны, `:649` обрыв,
   `:854` переход), так же пишет `_launch_detached` (`artel.py:1027`) и
   `lease.warn_foreign_live` (`lease.py:329`); `session_id` у надзора и
   сессии Оператора общий (`session.py`, файл `.artel/session-id`).
   Исполнитель, буквально читающий «запись журнала задачи командой
   Оператора» как «актор `operator` позже записи остановки», пройдёт
   AC-12/AC-13 и всё же получит перезапуск без решения Оператора, как
   только пульт допишет по задаче любую такую запись — отклонение 1.
3. Запуск `auto.cmd_auto` в процессе надзора вместо `_launch_detached`
   обошёл бы предпроверку lease и гейт свежести наблюдения — закрыто
   треб. 5 («отвязанный `auto <id>`») и треб. 7/AC-15.

## Вердикт

concerns — отклонения решаемы Оператором на гейте:

1. **Не определено «новое действие Оператора»** (SPEC.md:61–66, AC-12
   SPEC.md:163, AC-13 SPEC.md:167). Записи цикла `auto` и запуска идут
   актором `"operator"` (`auto.py:582`, `:1008`, `:183`, `:228`, `:649`,
   `:854`; `artel.py:1027`; `lease.py:329`), `session_id` общий
   (`session.py`). Нужен признак: например, «записи, кроме записей цикла
   `auto` (`zone_lock.AUTO_START_ACTION`/`AUTO_STOPPED_ACTION`/
   `CYCLE_ABORTED_ACTION`, `zone_lock.py:157–159`, и т. п.) и
   запуска надзором», либо перечень команд; и в AC-12 — запись пульта после
   остановки, которая перезапуск НЕ открывает.
2. **Перезапуск после ручного `stop <id>`** (SPEC.md:62; `artel.py:1429`,
   `store.py:82–87`): одиночный `stop` дочерней задачи эпика при живом
   надзоре не действует — задача перезапускается. Подтвердить, что так
   задумано (тогда записать в SPEC и AC), или засчитать ручной `stop`
   Оператора как «остановку не на гейте».
3. **Правило выбора наблюдения пересказано неверно** (SPEC.md:84–85
   против `store.py:225–236`, `artel.py:930–942`): у `auto <id>` наблюдение
   без флага выбирается только с задачей в наборе; у эпика задачи нет.
   SPEC фактически вводит другое правило («самое свежее активное
   наблюдение сессии и проекта»). Подтвердить его явно (или, например,
   «наблюдение, где есть хоть одна задача эпика, иначе самое свежее»).
4. **Живость блокировки только по pid** (SPEC.md:40–46, 97–98): без
   heartbeat и времени старта процесса блокировка после перезагрузки или
   SIGKILL при переиспользованном pid считается живой, а `epic stop` пошлёт
   SIGTERM постороннему процессу. Колонки заданы решением гейта 26.10 (2);
   сверка `started_at` с временем старта процесса
   (`doctor/stale_cycles.py:42` `process_start_time`) закрыла бы риск без новых
   колонок — на усмотрение Оператора.

Замечания без вердиктного веса:
- Записи надзора (`task_id` = id эпика) не приходят в сессию Оператора:
  `watch` читает только задачи набора (`store.py:118–124`); о
  самозавершении (треб. 9) и отказе наблюдения (треб. 7) Оператор узнает
  только из `log <эпик>`. ТЗ этого не требует.
- Треб. 8 «в журнале — записи ... каждого остановленного дочернего `auto`»
  (SPEC.md:99–100): `_cmd_stop` сам записи не пишет (`artel.py:1413–1432`),
  запись даёт дочерний `auto` после доигровки шага — критерий AC-16
  выполним этим путём.
- Рабочий каталог ветки задачи до Э1 и до Э2а — разработчику подтянуть
  main (треб. 10 это уже требует).
