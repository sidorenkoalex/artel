## Пути обхода гейтов

1. **Самостоятельное завершение без доставки в сессию.** Задача эпика
   попадает в набор наблюдения только «перед запуском своего `auto`»
   (треб. 9), правило (в) выбирает наблюдение без задач эпика. Надзор,
   завершившийся сам до первого запуска (все задачи окончательны,
   `start_after` на `killed`, исчерпанный конверт — AC-27..AC-29), или
   надзор, все задачи которого стоят на гейтах с самого старта, пишет
   журнал и алерт с id эпика, но по треб. 10 `watch` их не доставит: в
   наборе нет задачи эпика. AC-30 этого не ловит — его условие уже
   кладёт задачу эпика в набор. Требование выполняется буквально, смысл
   решения №2 («чтобы событие пришло в сессию») — нет. Нужен выбор
   Оператора: добавлять задачи эпика в набор при старте надзора, или
   доставлять события эпика наблюдению, выбранному надзором (по
   `epic_supervisors`).
2. **Подсчёт «живого дочернего `auto`» по lease — гонка с остановкой
   «не на гейте».** Треб. 7 считает живость по образцу
   `busy_other_tasks` (по lease). Между `_launch_detached` и взятием
   lease дочерним процессом (`auto.py:640-641`) только что запущенный
   ребёнок места не занимает — следующий проход надзора может запустить
   ещё одного. Сверх `MAX_PARALLEL_TASKS` дочерний `auto` получит отказ
   `runner.py:219-222` и остановится «run отказался стартовать»
   (`auto.py:966-968`) — по треб. 6 это остановка не на гейте, задача
   встанет до нового действия Оператора. Аналогично ребёнок, проигравший
   lease ручному `auto <id>`, выходит через `run_locked(...,
   on_refusal="print")` без записи остановки — «аварийный выход» по
   треб. 6. SPEC не говорит, чем считается живость дочернего (pid
   запуска или lease) и считается ли отказ лимита пульта остановкой не на
   гейте.
3. **`epic stop` и повторный `auto --epic`.** Дочерние, остановленные
   `epic stop`, пишут ту же запись `stop`, что и ручной `stop <id>`
   (`auto.py:119-123`); треб. 6 называет остановкой не на гейте «ручной
   `stop <id>` Оператора по дочерней задаче», про остановку `epic stop`
   молчит. Два прочтения: (а) все дети, шедшие под надзором, ждут
   `epic retry` по каждой; (б) остановка `epic stop` перезапуск не
   блокирует. Выбор за Оператором.
4. **Выключение задач в наблюдении `stop`** («Факты», п.1): треб. 10
   выполнимо буквально с фильтром по `enabled=1` — и записи `epic stop`
   до сессии не дойдут.
5. **Отказные записи команд** («Факты», п.2): разработчик, сверяющий по
   «команде», а не по успешному действию, откроет перезапуск отказом
   `amend-tests`/`ci-rerun`; повторная остановка тем же путём — лишний
   прогон шагов роли без решения Оператора.
6. **Нерабочий `ps` → два надзора.** `process_start_time` → `None`
   (`stale_cycles.py:47-55`) делает живую блокировку мёртвой (треб. 2) —
   второй `auto --epic` её снимет при живом первом, вопреки треб. 1.
   Буквальное следствие решения №2 п.4; отмечаю риск, не отклонение.

## Вердикт

concerns. SPEC полно отражает ТЗ, ANSWER-1 и три решения гейта; прежние
находки (alert-ack, `resume` без паузы, доставка `watch`, сессия
наблюдения, аварийный выход) закрыты требованиями 4, 5, 9, 10, 6. Факты о
коде подтверждаются. Отклонения, решаемые Оператором на гейте:

1. Треб. 9 + 10 / AC-30: задачи эпика попадают в набор наблюдения только
   при запуске дочернего — события надзора до первого запуска (в том
   числе самостоятельное завершение AC-27..AC-29) в сессию не дойдут
   (`orchestrator/watch.py:300-315`, `orchestrator/store.py:118-124`);
   AC-30 этого не ловит.
2. Треб. 7 / 6: не определено, по чему считается живой дочерний `auto`;
   при подсчёте по lease гонка запуска приводит к отказу лимита пульта
   (`orchestrator/runner.py:219-222`, `orchestrator/auto.py:966-968`),
   который по треб. 6 — остановка не на гейте, задача ждёт Оператора.
3. Треб. 6 + 11: остановка дочернего `epic stop` не классифицирована
   (`orchestrator/auto.py:119-123` — запись неотличима от ручного `stop`).
4. Треб. 10 + 11: `stop` выключает задачу во всех наблюдениях
   (`orchestrator/artel.py:1429`, `orchestrator/store.py:97-100`) — не
   сказано, считается ли выключенная задача «в наборе» для доставки
   событий надзора.
5. Треб. 4: отказные записи команд Оператора (`orchestrator/amend.py:161`,
   `orchestrator/ci_rerun.py:68`) — новое действие или нет.
6. Треб. 9: отказы `_launch_observation` кроме «устарело» (неактивное
   наблюдение, нет связи — `orchestrator/artel.py:955-969`, через
   `sys.exit`) поведением надзора не описаны.
7. Риски (не отклонения): новая миграция с собственной записью журнала
   уронит `tests/test_01m5tbbdfs6dwqy6ms263t1kpy_migration.py:122`;
   неопределённое время старта допускает два надзора
   (`orchestrator/doctor/stale_cycles.py:47-55`).
