# SPEC: Эпики Э2б — надзирающий процесс эпика `auto --epic`

## Контекст
ADR-0028 (принят 25.10.2026), уровень 2, п. 10; шаг Э2б после Э2а
(01M5TBCY7WTN121S136XP2C6SR — конверт эпика и `start_after`, проверка
перед первым шагом роли в `runner.py`). Сейчас `auto <id>` ведёт одну
задачу отвязанным процессом (`orchestrator/artel.py` `_launch_detached`,
`orchestrator/auto.py`), останавливается на гейтах Оператора; второй
процесс на ту же задачу не стартует (живой lease). Линию задач эпика
никто не ведёт: Оператор запускает `auto` каждой задаче руками и следит
за `start_after` сам. Задача вводит надзирающий процесс эпика
`auto --epic <id>`, лимит `epic parallel` и остановку `epic stop`.

Модуль команд эпика после мержа Э1 — `orchestrator/epics.py` (`cmd_epic`,
подкоманды `new/show/edit/close/add/remove`; `parallel` и `stop` в нём
нет). Таблица `epics` (`orchestrator/schema.py`, `EPICS_DDL`) колонки
лимита параллельности не несёт.

Решения Оператора по батчу вопросов — `ANSWER-1.md` (26.10.2026): п. 1 —
вариант A (гейт не повод для выхода), п. 2 — вариант A (место лимита —
живой дочерний `auto`), п. 3 — вариант A (наблюдение, выбранное при
запуске, без изменения схемы `observations`).

## Требования

1. **`auto --epic <id>`** запускает отвязанный долгоживущий надзирающий
   процесс эпика с собственной блокировкой эпика. Второй `auto --epic`
   того же эпика при живом надзирающем процессе — отказ с указанием pid
   живого процесса; второй процесс не запускается.
2. **`epic parallel <id> N`** задаёт лимит одновременно живых дочерних
   `auto` эпика; по умолчанию (не задан) — 1. Неразборное значение, `0` и
   отрицательное — отказ с причиной, лимит не меняется.
3. **Готовность задачи к запуску.** Надзирающий процесс считает задачу
   эпика готовой к запуску дочернего `auto`, когда одновременно:
   - задача не окончательна (не `done`, не `killed`);
   - задача не на гейте Оператора (`spec_gate`, `acceptance`,
     `merge_gate`) и не в `escalated`;
   - у задачи нет живого lease другого процесса (в том числе `auto <id>`,
     запущенного Оператором);
   - у задачи без первого шага роли (определение Э2а: в журнале нет
     записи «agent run started») все задачи её `start_after` в `done`;
   - у задачи без первого шага роли конверт эпика не исчерпан; задача с
     уже начатым шагом роли запускается и при исчерпанном конверте.
4. **Запуск.** Для готовой задачи (требование 3) надзирающий процесс
   запускает отвязанный `auto <id>`. Место лимита занимает живой дочерний
   `auto` эпика (решение Оператора, п. 2): одновременно живых дочерних
   `auto` не больше лимита `epic parallel` (требование 2) и не сверх
   `MAX_PARALLEL_TASKS` (`orchestrator/config.py:409`). Дочерний `auto`,
   остановившийся на гейте, место освобождает; задача после `approve`
   снова становится готовой и встаёт в очередь на место наравне с
   остальными. Очереди зон и merge-окна — как сейчас.
5. **Гейты.** Надзирающий процесс не вызывает `approve`/`reject` и не
   проходит гейты Оператора: дочерний `auto` останавливается на гейте как
   обычно, задачу на гейте надзирающий процесс снова не запускает. Пока
   задачи эпика на гейтах, процесс ждёт без шагов ролей и после `approve`
   и мержа запускает задачи, ставшие готовыми (в том числе те, у которых
   открылся `start_after`).
6. **Наблюдение.** Наблюдение эпика — наблюдение, выбранное при запуске
   `auto --epic` тем же правилом, что у `auto <id>` (`--observation <ID>`
   либо самое свежее активное наблюдение той же сессии и проекта). Каждая
   дочерняя задача перед запуском своего `auto` добавляется в набор задач
   этого наблюдения; события дочерних задач приходят в сессию Оператора.
   Схема `observations` не меняется.
7. **`epic stop <id>`** останавливает надзирающий процесс эпика и все
   живые дочерние `auto` эпика штатным `stop` (SIGTERM держателю lease,
   доигровка текущего шага), не убийством процесса. В журнале — записи
   остановки надзирающего процесса и каждого дочернего `auto`.
8. **Самостоятельное завершение.** Надзирающий процесс живёт, пока в
   эпике есть неокончательная задача на гейте Оператора, в `escalated`,
   под живым дочерним `auto`, готовая к запуску или ждущая `start_after`
   такой задачи. Он завершается сам с записью журнала, когда все задачи
   эпика окончательны либо оставшиеся заблокированы безвыходно без
   решения Оператора вне гейта: `start_after` на задачу в `killed`;
   исчерпанный конверт у задач без первого шага роли при отсутствии
   задач с начатым шагом.

## Критерии приёмки

AC-1. Эпик из трёх задач, вторая — `start_after` первой, третья без
зависимостей, `epic parallel 1`: после `auto --epic` запущен дочерний
`auto` только у первой задачи.

AC-2. В условиях AC-1, когда место освободилось: третья задача (без
зависимостей) запускается после освобождения места дочерним `auto`
первой; вторая задача запускается только после `done` первой и не
раньше.

AC-3. `epic parallel <id> 2`: одновременно живых дочерних `auto` эпика
из трёх готовых задач — не больше двух; эпик без заданного лимита — не
больше одного.

AC-4. `epic parallel <id> 0`, `epic parallel <id> -1` и неразборное
значение — отказ с причиной, лимит эпика не меняется.

AC-5. Готовых задач эпика больше, чем свободных мест под
`MAX_PARALLEL_TASKS`: надзирающий процесс не запускает дочерних `auto`
сверх `MAX_PARALLEL_TASKS` при лимите `epic parallel` выше него.

AC-6. Второй `auto --epic` того же эпика при живом надзирающем процессе
— отказ, в тексте отказа pid живого процесса; второй надзирающий процесс
не запущен.

AC-7. Задача эпика с живым lease чужого `auto <id>` пропускается:
надзирающий процесс не запускает ей дочерний `auto`.

AC-8. Задача эпика на гейте SPEC (`spec_gate`): надзирающий процесс не
запускает её снова и не вызывает `approve`; процесс не завершается, пока
задача на гейте.

AC-9. Задача эпика, дочерний `auto` которой остановился на гейте, после
`approve` Оператора снова запускается надзирающим процессом.

AC-10. Дочерняя задача перед запуском своего `auto` входит в набор задач
наблюдения, выбранного при запуске `auto --epic`.

AC-11. `epic stop <id>`: надзирающий процесс и дочерние `auto` эпика
остановлены штатно — в журнале записи остановки по `stop`, процессы
остановлены SIGTERM без `kill` процесса.

AC-12. Исчерпанный конверт эпика: задачам без первого шага роли новые
дочерние `auto` не запускаются; задача с начатым шагом роли запускается
и продолжает.

AC-13. Все задачи эпика окончательны (`done`/`killed`): надзирающий
процесс завершается сам с записью журнала.

AC-14. Единственная неокончательная задача эпика ждёт `start_after` на
задачу в `killed`: надзирающий процесс завершается сам с записью
журнала.

## Оценка объёма и деление

Сработавшие сигналы: зон 7 (≥ 5: `auto.py`, `epics.py`, `artel.py`,
`lease.py`, `store.py`, `schema.py`, `tests/`); критериев приёмки 14
(≥ 10); `budget_usd` $45 (≥ $30).

Материал для решения Оператора — обоснование монолита. Части механики
связаны атомарно: команда `epic parallel` и колонка лимита без
надзирающего процесса ничего не ограничивают (лимит никто не читает);
`epic stop` без надзирающего процесса и его блокировки не имеет адреса
остановки; надзирающий процесс без блокировки эпика нарушает требование 1
(два процесса ведут одну линию и удваивают запуски), без лимита — ведёт
все задачи разом. Разрез по зонам (`schema.py`/`store.py` отдельно от
`auto.py`/`epics.py`/`artel.py`) оставляет мержимой только мёртвую
колонку. Деление по командам (`auto --epic` без `parallel`/`stop`) даёт
промежуточное состояние, где запущенный надзирающий процесс нельзя
остановить штатно, кроме как `stop` каждой дочерней задачи руками.
