# SPEC: Эпики Э2б — надзирающий процесс эпика `auto --epic`

## Контекст
ADR-0028 (принят 25.10.2026), уровень 2, п. 10; шаг Э2б после Э2а
(01M5TBCY7WTN121S136XP2C6SR — конверт эпика и `start_after`, проверка
перед первым шагом роли в `runner.py`). Сейчас `auto <id>` ведёт одну
задачу отвязанным процессом (`orchestrator/artel.py` `_launch_detached`,
`orchestrator/auto.py`) и останавливается на гейтах Оператора; второй
процесс на ту же задачу не стартует (живой lease). Линию задач эпика
никто не ведёт: Оператор запускает `auto` каждой задаче руками и сам
следит за `start_after`. Задача вводит надзирающий процесс эпика
`auto --epic <id>`, лимит `epic parallel`, остановку `epic stop` и явное
разрешение перезапуска `epic retry`.

Модуль команд эпика после мержа Э1 — `orchestrator/epics.py` (`cmd_epic`,
подкоманды `new/show/edit/close/add/remove`; `parallel`, `stop` и `retry`
в нём нет). Таблица `epics` (`orchestrator/schema.py`, `EPICS_DDL`)
колонки лимита параллельности не несёт. `watch`
(`orchestrator/watch.py`) доставляет записи журнала по задачам набора
наблюдения и алерты по `target` из набора задач/проектов — записи и
алерты с id эпика в сессию сейчас не приходят.

Решения Оператора: батч вопросов — `ANSWER-1.md` (26.10.2026; пп. 1–3 —
вариант A); возвраты с гейта SPEC 26.10.2026 — после первого чтения
(решения 1–7), после аудита 2 (решения 1–4 и замечания) и после аудита 3
(решения 1–5: перечень действий без `alert-ack`, команда `epic retry`,
доставка через `watch`, сессия надзора, аварийный выход дочернего
`auto`) — вошли в требования 2–15 ниже.

## Требования

1. **`auto --epic <id>`** запускает отвязанный долгоживущий надзирающий
   процесс эпика с собственной блокировкой эпика. Второй `auto --epic`
   того же эпика при живом надзирающем процессе — отказ с указанием pid
   живого процесса; второй процесс не запускается.
2. **Блокировка надзора** — своя таблица `epic_supervisors` (`epic_id`,
   `pid`, `host`, `started_at`, `session_id`) в `orchestrator/schema.py` /
   `orchestrator/store.py`, не таблица `leases`. `session_id` — сессия,
   запустившая `auto --epic` (сессия надзора). Блокировка **живая**,
   когда pid жив на этом хосте И время старта процесса с этим pid
   (`orchestrator/doctor/stale_cycles.py` `process_start_time`) не позже
   `started_at` записи блокировки; иначе (pid не жив, время старта
   позже `started_at` или не определено) блокировка **мёртвая**. Мёртвая
   блокировка снимается при следующем `auto --epic` этого эпика с записью
   журнала, после чего новый надзирающий процесс запускается. Записи
   журнала надзирающего процесса — `store.journal` с `target` = проект
   эпика и `task_id` = id эпика.
3. **`epic parallel <id> N`** задаёт лимит одновременно живых дочерних
   `auto` эпика; по умолчанию (не задан) — 1. Неразборное значение, `0` и
   отрицательное — отказ с причиной, лимит не меняется.
4. **Новое действие Оператора** по задаче — запись журнала этой задачи,
   сделанная после записи её остановки, одной из команд Оператора:
   `answer`, `approve`, `reject`, `budget`, `amend-tests`,
   `zones-extend`, `ci-rerun`, `pause`, `resume`, `epic retry`
   (требование 5). `resume` считается новым действием, только когда
   снимает паузу задачи; `resume` задачи не на паузе новым действием не
   является. Записи цикла `auto` (`zone_lock.AUTO_START_ACTION`,
   `zone_lock.AUTO_STOPPED_ACTION`, `zone_lock.CYCLE_ABORTED_ACTION`) и
   записи запуска дочернего `auto` надзирающим процессом новым действием
   Оператора не являются и перезапуск не открывают.
5. **`epic retry <эпик> <задача>`** — явное действие Оператора
   «перезапустить задачу после остановки не на гейте»: пишет запись
   журнала задачи (`task_id` = id задачи, автор — Оператор), которая
   входит в перечень требования 4. Задача, не входящая в эпик, или
   несуществующие эпик/задача — отказ с причиной, записи журнала нет.
6. **Готовность задачи к запуску.** Надзирающий процесс считает задачу
   эпика готовой к запуску дочернего `auto`, когда одновременно:
   - задача не окончательна (не `done`, не `killed`);
   - задача не на гейте Оператора (`spec_gate`, `acceptance`,
     `merge_gate`) и не в `escalated`;
   - у задачи нет живого lease другого процесса (в том числе `auto <id>`,
     запущенного Оператором);
   - у задачи без первого шага роли (определение Э2а: в журнале нет
     записи «agent run started») все задачи её `start_after` в `done`;
   - у задачи без первого шага роли конверт эпика не исчерпан; задача с
     уже начатым шагом роли запускается и при исчерпанном конверте;
   - последний дочерний `auto` задачи, запущенный надзирающим процессом,
     не остановился не на гейте — либо после записи журнала о такой
     остановке по задаче есть новое действие Оператора (требование 4).
     Остановка не на гейте — пауза, стоп-кран, потолок бюджета, лимит
     шагов, отказ `advance`, ручной `stop <id>` Оператора по дочерней
     задаче, а также аварийный выход дочернего `auto`: запись
     `zone_lock.CYCLE_ABORTED_ACTION` либо выход дочернего процесса без
     записи о его остановке. До нового действия Оператора задача не
     перезапускается.
7. **Запуск.** Для готовой задачи (требование 6) надзирающий процесс
   запускает отвязанный `auto <id>`. Место лимита занимает живой дочерний
   `auto` эпика (ANSWER-1, п. 2): одновременно живых дочерних `auto` не
   больше лимита `epic parallel` (требование 3), и число живых дочерних
   `auto` вместе с прочими живыми lease пульта не превышает
   `config.MAX_PARALLEL_TASKS` — живость lease считается так же, как
   `orchestrator/parallel_limit.py` `busy_other_tasks`. Дочерний `auto`,
   остановившийся на гейте, место освобождает; задача после `approve`
   снова становится готовой и встаёт в очередь на место наравне с
   остальными. Очереди зон и merge-окна — как сейчас.
8. **Гейты.** Надзирающий процесс не вызывает `approve`/`reject` и не
   проходит гейты Оператора: дочерний `auto` останавливается на гейте как
   обычно, задачу на гейте надзирающий процесс снова не запускает. Пока
   задачи эпика на гейтах, процесс ждёт без шагов ролей и после `approve`
   и мержа запускает задачи, ставшие готовыми (в том числе те, у которых
   открылся `start_after`).
9. **Наблюдение эпика.** Наблюдение эпика принадлежит сессии надзора
   (требование 2). Правило выбора при запуске `auto --epic` — своё,
   правило эпика: (а) наблюдение, названное `--observation <ID>`; иначе
   (б) активное наблюдение сессии надзора, в наборе задач которого есть
   хоть одна задача эпика; иначе (в) самое свежее активное наблюдение
   сессии надзора в этом проекте. Наблюдение, названное
   `--observation`, но принадлежащее другой сессии, — отказ запуска. Нет
   ни одного подходящего наблюдения или выбранное принадлежит другой
   сессии — отказ запуска `auto --epic` с причиной: надзирающий процесс
   не запускается и блокировка не создаётся. Каждая дочерняя задача перед
   запуском своего `auto` добавляется в набор задач выбранного
   наблюдения; события дочерних задач приходят в сессию Оператора. Схема
   `observations` не меняется. Если наблюдение устарело и
   `_launch_observation` отказывает, надзирающий процесс не запускает
   дочерний `auto` и завершается с записью журнала (не ждёт молча).
10. **Доставка событий надзора.** `watch` доставляет в сессию алерты и
    записи журнала надзирающего процесса эпика (`task_id` = id эпика),
    если в наборе задач наблюдения есть хоть одна задача этого эпика.
11. **`epic stop <id>`** останавливает сначала надзирающий процесс эпика
    (после его остановки новых дочерних запусков нет), затем живые
    дочерние `auto`, запущенные надзирающим процессом, — штатным `stop`
    (SIGTERM держателю lease, доигровка текущего шага), не убийством
    процесса. `auto <id>` задачи эпика, запущенный Оператором (не
    надзирающим процессом), не останавливается. При мёртвой блокировке
    (требование 2) `epic stop` не шлёт сигнал процессу с её pid,
    останавливает живые дочерние `auto` и снимает блокировку. В журнале —
    записи остановки надзирающего процесса (или снятия мёртвой
    блокировки) и каждого остановленного дочернего `auto`.
12. **Самостоятельное завершение.** Надзирающий процесс живёт, пока в
    эпике есть неокончательная задача на гейте Оператора, в `escalated`,
    ждущая нового действия Оператора после остановки не на гейте
    (требование 6, последнее условие), под живым дочерним `auto`, готовая
    к запуску или ждущая `start_after` такой задачи. Он завершается сам с
    записью журнала, когда все задачи эпика окончательны либо оставшиеся
    заблокированы безвыходно без решения Оператора вне гейта:
    `start_after` на задачу в `killed`; исчерпанный конверт у задач без
    первого шага роли при отсутствии задач с начатым шагом.
13. **Алерт Оператору.** Самостоятельное завершение надзирающего процесса
    (требование 12) и его завершение по отказу наблюдения (требование 9)
    дополнительно к записи журнала открывают алерт Оператору по эпику
    (`orchestrator/alerts.py`, `kind=attention`); в сессию он приходит
    через `watch` (требование 10).
14. **Порядок разработки.** Разработка начинается после мержа Э2а
    (01M5TBCY7WTN121S136XP2C6SR). Разработчик первым шагом сверяет код
    Э2а с этим SPEC: маркер первого шага роли, проверку `start_after`,
    конверт эпика. Расхождение — эскалация, не подгонка.
15. **Существующие тесты.** Правка существующих тестов `tests/` этой
    задачей не заказана; понадобилась — эскалация с матрицей
    неослабления.

## Критерии приёмки

AC-1. Эпик из трёх задач, вторая — `start_after` первой, третья без
зависимостей, `epic parallel 1`: после `auto --epic` запущен дочерний
`auto` только у первой задачи.

AC-2. В условиях AC-1, когда место освободилось: третья задача (без
зависимостей) запускается после освобождения места дочерним `auto`
первой; вторая задача запускается только после `done` первой и не
раньше.

AC-3. `epic parallel <id> 2`: одновременно живых дочерних `auto` эпика
из трёх готовых задач — не больше двух; эпик без заданного лимита — не
больше одного.

AC-4. `epic parallel <id> 0`, `epic parallel <id> -1` и неразборное
значение — отказ с причиной, лимит эпика не меняется.

AC-5. Живой lease задачи вне эпика занимает место под
`MAX_PARALLEL_TASKS`: при лимите `epic parallel` выше свободных мест
надзирающий процесс запускает дочерних `auto` не больше, чем
`MAX_PARALLEL_TASKS` минус число прочих живых lease пульта.

AC-6. Второй `auto --epic` того же эпика при живом надзирающем процессе
— отказ, в тексте отказа pid живого процесса; второй надзирающий процесс
не запущен.

AC-7. Блокировка эпика в `epic_supervisors` с pid, не живым на этом
хосте: следующий `auto --epic` снимает её с записью журнала и запускает
надзирающий процесс.

AC-8. Блокировка эпика в `epic_supervisors` с pid живого процесса, время
старта которого (`process_start_time`) позже `started_at` записи:
блокировка считается мёртвой — следующий `auto --epic` снимает её с
записью журнала и запускает надзирающий процесс; `epic stop <id>` при
такой блокировке не шлёт сигнал этому процессу (процесс продолжает
работу) и снимает блокировку.

AC-9. Записи журнала надзирающего процесса несут `task_id` = id эпика и
`target` = проект эпика; блокировка надзора не создаёт строки в таблице
`leases`; строка `epic_supervisors` несёт `session_id` сессии,
запустившей `auto --epic`.

AC-10. Задача эпика с живым lease чужого `auto <id>` пропускается:
надзирающий процесс не запускает ей дочерний `auto`.

AC-11. Задача эпика на гейте SPEC (`spec_gate`): надзирающий процесс не
запускает её снова и не вызывает `approve`; процесс не завершается, пока
задача на гейте.

AC-12. Задача эпика, дочерний `auto` которой остановился на гейте, после
`approve` Оператора снова запускается надзирающим процессом.

AC-13. Дочерний `auto` задачи остановился не на гейте (пауза; лимит
шагов): надзирающий процесс не перезапускает задачу и не завершается
сам, пока по задаче нет нового действия Оператора; запись пульта по
задаче, сделанная после остановки и не являющаяся новым действием
Оператора (запись цикла `auto` — `AUTO_START_ACTION`,
`AUTO_STOPPED_ACTION` или `CYCLE_ABORTED_ACTION`), перезапуск не
открывает — задача по-прежнему не запущена.

AC-14. В условиях AC-13 (остановка паузой) после записи журнала задачи
командой `resume`, снявшей паузу и сделанной позже записи остановки,
задача снова запускается надзирающим процессом.

AC-15. Дочерний `auto` задачи остановился по лимиту шагов (задача не на
паузе): `resume` по этой задаче перезапуск не открывает — задача
по-прежнему не запущена.

AC-16. Дочерний `auto` задачи остановился не на гейте: `epic retry
<эпик> <задача>` пишет запись журнала задачи, после неё задача снова
запускается надзирающим процессом. `epic retry` с задачей, не входящей
в эпик, — отказ с причиной, записи журнала по задаче нет.

AC-17. Ручной `stop <id>` Оператора по дочерней задаче эпика: надзирающий
процесс не перезапускает задачу до нового действия Оператора по ней; после
такого действия задача снова запускается.

AC-18. Аварийный выход дочернего `auto`: (а) в журнале задачи запись
`CYCLE_ABORTED_ACTION`; (б) дочерний процесс завершился без записи о
своей остановке. В обоих случаях надзирающий процесс не перезапускает
задачу до нового действия Оператора по ней; после такого действия
задача снова запускается.

AC-19. `auto --epic <id> --observation <ID>` выбирает названное
наблюдение сессии надзора; без `--observation` — активное наблюдение
сессии надзора, в наборе которого есть задача эпика, даже если в той же
сессии и проекте есть более свежее активное наблюдение без задач эпика;
без обоих — самое свежее активное наблюдение сессии надзора в этом
проекте. Дочерняя задача перед запуском своего `auto` входит в набор
задач выбранного наблюдения.

AC-20. `auto --epic <id> --observation <ID>` с наблюдением другой
сессии: отказ запуска с причиной, надзирающий процесс не запущен, строки
в `epic_supervisors` нет; наблюдение другой сессии с задачей эпика без
`--observation` не выбирается.

AC-21. Ни одного наблюдения по правилу требования 9 нет: `auto --epic`
отказывает с причиной, надзирающий процесс не запущен, строки в
`epic_supervisors` нет.

AC-22. Наблюдение эпика устарело, `_launch_observation` отказывает:
надзирающий процесс не запускает дочерний `auto`, завершается с записью
журнала и открывает алерт `kind=attention`.

AC-23. `epic stop <id>` при живом надзирающем процессе: сначала
остановлен надзирающий процесс, после его остановки новых дочерних
запусков нет; затем дочерние `auto`, запущенные им, остановлены штатно
SIGTERM без `kill` процесса. Запись остановки по `stop` каждого дочернего
`auto` делает сам дочерний `auto` после доигровки шага — критерий ждёт её
появления в журнале с таймаутом.

AC-24. `epic stop <id>`: `auto <id>` задачи эпика, запущенный Оператором,
а не надзирающим процессом, продолжает работу — не остановлен, записи
его остановки в журнале нет.

AC-25. `epic stop <id>` при мёртвом надзирающем процессе (блокировка
есть, pid не жив на этом хосте): живые дочерние `auto` остановлены
штатно, блокировка эпика снята, в журнале — записи об этом.

AC-26. Исчерпанный конверт эпика: задачам без первого шага роли новые
дочерние `auto` не запускаются; задача с начатым шагом роли запускается
и продолжает.

AC-27. Все задачи эпика окончательны (`done`/`killed`): надзирающий
процесс завершается сам с записью журнала.

AC-28. Единственная неокончательная задача эпика ждёт `start_after` на
задачу в `killed`: надзирающий процесс завершается сам с записью
журнала.

AC-29. Конверт эпика исчерпан, неокончательные задачи — только без
первого шага роли, задач с начатым шагом нет: надзирающий процесс
завершается сам с записью журнала.

AC-30. В каждом случае самостоятельного завершения AC-27, AC-28, AC-29
`watch` наблюдения, в наборе задач которого есть задача эпика, выводит
в сессию алерт `kind=attention` по эпику и запись журнала завершения
надзирающего процесса (`task_id` = id эпика).

AC-31. Задача эпика в `escalated`: надзирающий процесс не запускает ей
дочерний `auto` и не завершается сам, пока задача в `escalated`.

## Оценка объёма и деление

Сработавшие сигналы: зон 8 (≥ 5: `auto.py`, `epics.py`, `artel.py`,
`lease.py`, `store.py`, `schema.py`, `watch.py`, `tests/`); критериев
приёмки 31 (≥ 10); `budget_usd` $65 (≥ $30).

Материал для решения Оператора — обоснование монолита. Части механики
связаны атомарно: команда `epic parallel` и колонка лимита без
надзирающего процесса ничего не ограничивают (лимит никто не читает);
`epic stop` без надзирающего процесса и его блокировки
(`epic_supervisors`) не имеет адреса остановки; `epic retry` без
надзирающего процесса ничего не перезапускает; доставка `watch` записей
и алертов с id эпика без надзирающего процесса доставлять нечего, а
надзирающий процесс без неё завершается молча для сессии; надзирающий
процесс без блокировки эпика нарушает требование 1 (два процесса ведут
одну линию и удваивают запуски), без лимита — ведёт все задачи разом.
Разрез по зонам (`schema.py`/`store.py` отдельно от
`auto.py`/`epics.py`/`artel.py`/`watch.py`) оставляет мержимыми только
мёртвые таблицу и колонку. Деление по командам (`auto --epic` без
`parallel`/`stop`/`retry`) даёт промежуточное состояние, где запущенный
надзирающий процесс нельзя остановить штатно, кроме как `stop` каждой
дочерней задачи руками, а задачу после аварийного выхода — вернуть в
линию.

Бюджет: класс «больше 15 критериев / 8 и более файлов» (~$85) ограничен
вниз рамкой ТЗ $65.
