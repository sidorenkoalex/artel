## Замечания

- blocker — `orchestrator/fsm.py:752-768` (`_handle_merge_conflict`) — при отказе `git merge --abort` (диск, права, гонка за `.git`) код всё равно переводит задачу в `in_dev`/`escalated`, просто дописывая `abort_note` в `detail`; `main` при этом остаётся с незавершённым merge (`MERGE_HEAD` не удалён, файл с конфликт-маркерами не разрешён). Проверено вручную: смок-тест на песочнице `_sandbox.MergeGateRealGitTest` с замоканным `gitcmd.git("merge","--abort")` → `returncode=1` даёт `state()=="in_dev"`, `MERGE_HEAD` существует, `git status --porcelain` → `UU shared.txt`. Это прямое нарушение AC-3/AC-4 («main остаётся в чистом состоянии») и требования 5 SPEC. Хуже того, последствие не локально: следующий `approve` ЛЮБОЙ другой задачи начинает с `git checkout main` + `git pull --ff-only` в том же ROOT (orchestrator/fsm.py:878-883) — `pull` на дереве с незавершённым merge откажет, и все дальнейшие merge из `merge_gate` будут падать инфраструктурным отказом, пока Оператор не поймёт причину и не почистит `main` руками. Ни один AC-тест такой сценарий не покрывает (AC-3/AC-4 проверяют только успешный `--abort`).
  Предложение: если `abort.returncode != 0` (или `abort is None`), не выполнять переход состояния вовсе — обработать как инфраструктурный отказ (по аналогии с веткой «files пуст» чуть выше, requirement 2, третий пункт: «git не ответил» это тоже инфраструктурный отказ), т.е. `sys.exit` с диагностикой, задача остаётся в `merge_gate`, `main` временно грязный, но явно и видимо (а не молча «залатанный» detail-строкой при формально успешном переходе). Плюс тест на этот путь.

## Вердикт

changes_requested — один блокер (`orchestrator/fsm.py:752-768`, `_handle_merge_conflict`): при отказе `git merge --abort` задача всё равно переходит в `in_dev`/`escalated`, хотя `main` не приведён в чистое состояние (нарушение AC-3/AC-4 и требования 5 SPEC), с риском для последующих merge-попыток других задач. Остальное по SPEC и приёмке — в порядке; полный набор тестов (762) и все AC1-AC8 зелёные, диф не выходит за заявленные файлы.

## Предложения системе

- `orchestrator/fsm.py` (класс «отказ вспомогательной git-команды не останавливает переход состояния»): здесь конкретно `git merge --abort` в `_handle_merge_conflict` — при добавлении подобных «выполни git-команду для чистоты после провала» шагов стоит явно решать, что происходит, если сама команда очистки тоже откажет, а не только записывать это в `detail`.
