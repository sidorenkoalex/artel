# SPEC: Возврат из merge_gate в разработку

## Контекст

Роадмап §4 п.2а, третий шаг контура параллельности (после CAS T050
и сверки свежести T051): возврат из `merge_gate`. Сегодня из
`merge_gate` только два пути — approve (merge) и kill. Красный CI
требует ручного вмешательства Оператора (прецедент T022), а провал
merge оставляет задачу в гейте молча
(`test_merge_failure_leaves_the_task_in_the_gate`) — дальше тоже
руки. Для контура N=2 штатный путь назад к разработчику отсутствует:
пока задача ждёт approve и CI, main может уйти вперёд.

## Требования

1. `reject` расширяется на состояние `merge_gate`: команда
   `artel.py reject <id> "<причина>"` из `merge_gate` выполняет один
   переход `merge_gate -> in_dev` и записывает причину (свободный
   текст Оператора) в журнал задачи. Из состояний, отличных от
   `merge_gate`, `reject` ведёт себя так же, как до этой задачи.
2. Провал merge при `approve` из `merge_gate` перестаёт быть
   молчаливым тупиком и разбирается на три исхода:
   - содержательный конфликт (git не разрешил merge автоматически) —
     оркестратор выполняет `git merge --abort`, возвращает `main`
     в чистое состояние и переводит задачу `merge_gate -> in_dev`
     с диагностикой конфликта (перечень конфликтующих файлов)
     в журнале;
   - если конфликтующие файлы затрагивают защищённые пути
     (`gates.yaml`, `roles.yaml`, `.github/`, `templates/`,
     `skills/` — зона Оператора по conventions-core) — задача вместо
     возврата в `in_dev` переходит в `escalated`, `main` при этом
     тоже приводится в чистое состояние (`git merge --abort`);
   - инфраструктурные отказы (git не ответил, красный или неполный
     CI) — поведение прежнее: `approve` отказывает, задача остаётся
     в `merge_gate`, автоматического возврата не происходит.
3. Красный CI сам по себе задачу из `merge_gate` не выталкивает —
   `approve` отказывает как сейчас (инвариант 19 не меняется);
   выбор (подождать/перезапустить CI или сделать `reject` с причиной)
   остаётся за Оператором.
4. Счётчики итераций задачи (`review_iters`, `accept_rejects` и
   любые новые, если заведены) не сбрасываются переходом
   `merge_gate -> in_dev` ни через `reject`, ни через автоматический
   возврат по конфликту (инвариант 4); действующий лимит итераций
   ревью (`LIMIT_REVIEW_ITERS`) ограничивает и цикл, начинающийся
   с возврата из `merge_gate`, — отдельного лимита на сам возврат
   из `merge_gate` эта задача не вводит.
5. Возврат из `merge_gate` (через `reject` или через конфликт при
   `approve`) ничего не мержит и не меняет `main`, кроме отмены уже
   начатой merge-попытки (`git merge --abort` в сценариях требования
   2); инварианты 12, 14, 15, 19 остаются истинными без изменений.
6. Новых состояний FSM не вводится: возврат использует существующие
   состояния (`in_dev`, `escalated`).
7. Изменения вносятся только в `orchestrator/` (`fsm.py` и смежные
   модули), тесты и карту кодовой базы (`docs/codebase-map.md`).

## Критерии приёмки

AC-1. `artel.py reject <id> "<причина>"` из состояния `merge_gate`
выполняет переход `merge_gate -> in_dev` и записывает переданную
причину в журнал задачи.

AC-2. `reject` из любого состояния, отличного от `merge_gate` (в
частности, из `acceptance`), ведёт себя так же, как до этой задачи —
без изменений в поведении, доступных состояниях и лимитах.

AC-3. При `approve` из `merge_gate`, если `git merge` завершается
содержательным конфликтом (не разрешён автоматически), оркестратор
выполняет `git merge --abort`, `main` остаётся в чистом состоянии
(без незавершённого merge), задача переходит `merge_gate -> in_dev`,
а перечень конфликтующих файлов записывается в журнал.

AC-4. Если конфликтующие файлы из AC-3 пересекаются с защищёнными
путями (`gates.yaml`, `roles.yaml`, `.github/`, `templates/`,
`skills/`), задача вместо перехода в `in_dev` переходит в
`escalated`; `main` приводится в чистое состояние тем же
`git merge --abort`.

AC-5. При красном или неполном CI-статусе ветки `approve` из
`merge_gate` отказывает, а задача остаётся в `merge_gate` — поведение
идентично (байт-в-байт) поведению до этой задачи; автоматического
перехода в `in_dev` или `escalated` по красному CI не происходит.

AC-6. Ни в одном из сценариев провала merge (содержательный конфликт,
конфликт в защищённых путях, инфраструктурный отказ, красный CI)
задача не переходит в состояние `done`.

AC-7. Счётчики итераций задачи (`review_iters`, `accept_rejects` и
любые новые, если введены этой задачей) не сбрасываются переходом
`merge_gate -> in_dev`, выполненным ни через `reject`, ни через
автоматический возврат по конфликту.

AC-8. Все существующие тесты пакета остаются зелёными; единственное
допустимое изменение существующего теста —
`test_merge_failure_leaves_the_task_in_the_gate`
(`tests/test_invariants.py`), и оно ограничено заменой сценария
«провал merge молча оставляет задачу в гейте» на явный возврат
(`in_dev`) или эскалацию (`escalated`) с записью в журнал; запрет
переводить задачу в `done` при провале merge (AC-6) этим изменением
не снимается.

## Не входит

- Merge queue (мержи по одному, обновление от main + приёмочные
  в той же операции) и сам контур N=2 — следующие шаги цепочки
  §4 п.2а.
- `verifying`/`await-ci` как отдельное состояние FSM (B1b) — остаётся
  строкой роадмапа.
- Автоматический возврат из `merge_gate` по красному CI — запрещён
  требованием 3.
- Новые состояния FSM.
- Изменение схемы БД — допускается, только если для возврата
  действительно нужен отдельный счётчик по образцу `accept_rejects`;
  это не требование задачи, а допустимая опция при реализации.
- Файлы вне `orchestrator/` (`fsm.py` и смежные модули), тестов
  и `docs/codebase-map.md`.
