# PLAN: Возврат из merge_gate в разработку

## Подход

Два независимых изменения в `orchestrator/fsm.py`, оба — расширение уже
существующих точек входа (`cmd_reject`, `cmd_approve`), новых состояний
и новых CLI-команд не вводится.

1. `_cmd_reject`: сейчас жёстко проверяет `state != "acceptance"` и
   отказывает `sys.exit` на любом другом состоянии. Расширяю проверку
   до `state not in ("acceptance", "merge_gate")`. Ветка `merge_gate`
   делает `store.set_state(..., "in_dev", "operator", ...)` с причиной
   в detail — без touching `accept_rejects`/`review_iters` (SPEC
   требование 4/AC-7: `reject` из `merge_gate` не считает попытку
   приёмки, это другой счётчик другого гейта). Ветка `acceptance`
   остаётся byte-for-byte как была.

2. `_cmd_approve`, ветка `merge_gate`: сейчас три git-команды
   (`checkout`, `pull --ff-only`, `merge --no-ff`) гоняются одним
   циклом с одинаковой обработкой отказа (`sys.exit`). Разношу:
   `checkout`/`pull` остаются в цикле с прежним поведением (отказ —
   инфраструктурный, задача остаётся в `merge_gate`, поведение AC-5
   не трогается). `merge --no-ff` выношу отдельно: при отказе зову
   новую функцию `_handle_merge_conflict(conn, task_id, state, branch,
   merge_res)`, которая:
   - журналит сырой `merge_res.stderr` (как раньше — не в состав
     diagnostics, а тем же способом что и старый код, для отладки);
   - спрашивает `git diff --name-only --diff-filter=U` (в ROOT, где
     уже стоит `checkout main` перед этим) — список файлов с
     неразрешённым конфликтом;
   - список пуст или git не ответил (rc не 0/None) → инфраструктурный
     отказ, поведение прежнее байт-в-байт: `sys.exit`, `merge_gate` не
     меняется (AC-5, AC-6 сценарий 3);
   - список не пуст → содержательный конфликт: `git merge --abort`
     (в ROOT), затем сверка списка файлов с `config.PROTECTED_PATHS`
     (новая константа — те же пять путей, что называет CLAUDE.md/
     conventions-core: `gates.yaml`, `roles.yaml`, `.github/`,
     `templates/`, `skills/`); пересечение — `escalated` (AC-4),
     иначе — `in_dev` (AC-3); оба перехода несут перечень
     конфликтующих файлов в `detail` (журналируется `set_state`
     автоматически) и не трогают `review_iters`/`accept_rejects`
     (AC-7 — ни один из них здесь не читается и не пишется).

`config.PROTECTED_PATHS` — новая константа (`orchestrator/config.py`),
единственный источник списка защищённых путей для сверки; дублирует
уже существующий список из CLAUDE.md/conventions-core текстом, но
как код нигде раньше не было — заводится этой задачей.

Приёмочные тесты (`tasks/T052/acceptance_tests/`, залочены test_author)
уже фиксируют именно эту разбивку: `_sandbox.MergeGateRealGitTest`
гоняет реальный git, ожидает `git diff --name-only --diff-filter=U`
косвенно (через наблюдаемое поведение — чистый main, конфликтующие
файлы в журнале), явную git-команду не диктует — свобода реализации
внутри `_handle_merge_conflict` есть, но наблюдаемый контракт (abort,
чистота main, файлы в журнале, in_dev/escalated) жёсткий.

## Шаги

1. `orchestrator/config.py`: константа `PROTECTED_PATHS`.
2. `orchestrator/fsm.py`: `_cmd_reject` — расширение на `merge_gate`.
3. `orchestrator/fsm.py`: `_cmd_approve`/`merge_gate` — вынос `git merge`
   из общего цикла, новая `_handle_merge_conflict`.
4. `tests/test_invariants.py`: единственная разрешённая правка
   существующего теста — `test_merge_failure_leaves_the_task_in_the_gate`
   переписывается под новый сценарий (содержательный конфликт → in_dev,
   а не молчаливый останов в `merge_gate`); плюс юнит-тесты нового
   поведения (reject из merge_gate вне acceptance-сценария AC-2 уже
   покрыт приёмкой — здесь только то, что приёмка не покрывает: сборка
   `PROTECTED_PATHS`-сверки как отдельной единицы, если потребуется).
5. `docs/codebase-map.md`: регенерация (`python3 scripts/codebase_map.py`)
   — `_cmd_reject`/`_cmd_approve` не публичные функции, `fsm.py` уже
   в карте, но конвенция требует прогонять генератор при правке `.py`
   в `orchestrator/` тем же коммитом (скил conventions-core).

## Влияние на систему

Изменение сфокусировано на двух функциях `fsm.py`, оба пути — строго
внутри разрешённых требованиями исходов (`in_dev`/`escalated`/отказ
без перехода). Инварианты:

- Инвариант 12 (ред. ADR-0006, «в main мержит только approve из
  merge_gate») — не нарушается: `git merge --abort` не пишет в main,
  откатывает попытку до её начала; никакого нового пути влить что-либо
  в main не появляется. `test_invariants.MergeOnlyFromMergeGateTest`
  не тронут, прогоняется как есть.
- Инвариант 19 (зелёный CI обязателен для merge) — ветка CI-отказа в
  `_cmd_approve` не переставляется и не трогается; AC-5 тест это же
  и проверяет отдельно от конфликтной ветки.
- Инвариант 4 (счётчики итераций не сбрасываются никаким переходом) —
  оба новых перехода (`reject`-из-merge_gate и авто-возврат по
  конфликту) не пишут `review_iters`/`accept_rejects` вовсе, то есть
  не могут их сбросить структурно, не только по факту прогона теста.
- Инвариант 6/7 (ручной гейт не проходится молча, approve/reject —
  единственный вход) — оба новых перехода инициированы либо явным
  вызовом Оператора (`reject`), либо самим `approve` (не `advance`,
  не поллингом) — новой лазейки для автопрохода гейта нет.
- `LIMIT_REVIEW_ITERS` (требование 4 SPEC) — задача, вернувшаяся в
  `in_dev` по конфликту или по `reject`, проходит обычный цикл
  `in_dev -> review`; если ревью снова отправит на доработку, это
  обычная итерация `review_iters`, тот же лимит, который уже
  действует — отдельного лимита на сам возврат из `merge_gate` не
  завожу (SPEC требование 4, последняя фраза; «Не входит» ТЗ).
- Откат: правка изолирована в `fsm.py` (плюс константа в `config.py` и
  тест в `test_invariants.py`) — `git revert` коммита задачи полностью
  восстанавливает прежнее поведение (провал merge → тупик в
  `merge_gate`, `reject` только из `acceptance`).

## Риски

- Список `PROTECTED_PATHS` дублирует текст CLAUDE.md/conventions-core
  вручную (нет единого источника) — разойдутся, если Оператор поменяет
  список защищённых путей в CLAUDE.md и забудет про код. Не решаю в
  этой задаче (вне объёма SPEC), но стоит иметь в виду при следующей
  правке защищённых путей.
- Определение «содержательный конфликт» через
  `git diff --name-only --diff-filter=U` — если в будущем `git merge`
  начнёт падать до создания индекса конфликта по причине, не связанной
  ни с конфликтом, ни с сетью/правами (экзотика), список файлов будет
  пуст и код классифицирует это как инфраструктурный отказ (безопасный
  дефолт — задача остаётся в `merge_gate`, не эскалирует и не тупит
  молча за пределами того, что уже было).
