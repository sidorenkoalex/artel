# ТЗ: Возврат из merge_gate в разработку

## Контекст

Роадмап §4 п.2а, третий шаг контура параллельности (после CAS T050 и
сверки свежести T051): возврат из merge_gate. Строка P3 «Возврат из
merge_gate (красный CI, конфликт мержа)».

Сегодня из merge_gate два пути: approve (merge) и kill. Красный CI =
ручное вмешательство Оператора (прецедент T022 — hotfix в ветку
руками); провал merge оставляет задачу в гейте молча
(`test_merge_failure_leaves_the_task_in_the_gate`), дальше тоже руки.
Для контура N=2 это дыра: «мир ушёл вперёд, пока задача стояла на
гейте» — штатная ситуация, а штатного пути назад к разработчику нет.
T051 сузила окно (свежий срез приезжает на гейт), но не закрыла его:
пока задача ждёт approve и CI, сосед может смержиться.

## Решение (принято Оператором 27.08, строка P3)

1. `reject` расширяется на merge_gate: `artel.py reject <id> "<причина>"`
   из merge_gate выполняет один переход `merge_gate -> in_dev` с
   записью причины в журнал. Класс причины — свободный текст Оператора
   (типовые: красный CI, конфликт мержа, вскрывшийся дефект).
   Вернувшаяся задача идёт обычным циклом: developer правит, ревью
   правки — инкрементальным диффом (механика T029 уже есть), приёмка,
   снова merge_gate. Новых состояний FSM не появляется (роадмап п.9:
   «маршрут правки один»).
2. Провал merge при approve из merge_gate перестаёт быть молчаливым
   тупиком:
   - содержательный конфликт (git не разрешил сам) → оркестратор
     выполняет `git merge --abort`, возвращает main в чистое состояние
     и переводит задачу `merge_gate -> in_dev` с диагностикой конфликта
     в журнале (конфликтующие файлы);
   - НО если конфликт затрагивает защищённые пути (`gates.yaml`,
     `roles.yaml`, `.github/`, `templates/`, `skills/` — зона Оператора
     по conventions-core) → `escalated`, не возврат: developer такие
     файлы чинить не вправе;
   - инфраструктурные отказы (git не ответил, красный/неполный CI) —
     поведение прежнее: отказ команды, задача остаётся в merge_gate,
     возврат — решением Оператора через reject (красный CI бывает
     флаком, автоматический возврат по нему запрещён).
3. Красный CI сам по себе задачу из гейта НЕ выталкивает — approve
   отказывает как сейчас (инвариант 19 нетронут), а Оператор выбирает:
   подождать/перезапустить CI или reject с причиной.
4. Счётчики итераций при возврате не сбрасываются (инвариант 4);
   лимит итераций ревью действует как обычно — возврат из merge_gate
   не даёт бесконечного цикла.
5. Возврат ничего не мержит и main не трогает (кроме `merge --abort`
   уже начатой merge-попытки в п.2); инварианты 12 (ред. ADR-0006),
   14, 15, 19 остаются истинными.

## Границы

- Только orchestrator/ (fsm и смежные), тесты, карта.
- Не ослаблять существующие тесты/гейты/инварианты (ADR-0002);
  `test_merge_failure_leaves_the_task_in_the_gate` при этом меняет
  ожидаемое поведение по СУТИ этой задачи — это не ослабление, а
  замена «молчаливого тупика» на «явный возврат с журналом»:
  корректировка теста разрешена этим ТЗ в этих рамках (задача от
  Оператора; сам запрет мержить при провале остаётся — задача не
  становится done).
- Деградация без реального git — по образцам T051.

## Не входит

- Merge queue (мержи по одному, обновление от main + приёмочные в той
  же операции) и N=2 — следующие шаги цепочки.
- verifying/await-ci как отдельное состояние (B1b) — связка остаётся
  строкой роадмапа.
- Автовозврат по красному CI (запрещён решением п.3).
- Изменение схемы БД допускается только если нужен счётчик возвратов —
  по образцу `accept_rejects`; новые состояния FSM — нет.

## Приёмка (минимум)

- reject из merge_gate переводит задачу в in_dev с причиной в журнале;
  из других состояний reject ведёт себя как раньше.
- Содержательный конфликт merge при approve: merge --abort, main чист,
  задача в in_dev, конфликтующие файлы в журнале.
- Конфликт в защищённых путях: escalated, main чист.
- Красный CI: approve отказывает, задача остаётся в merge_gate
  (поведение байт-в-байт прежнее).
- Провал merge не делает задачу done ни в каком сценарии.
- Счётчики итераций не сбрасываются возвратом.
- Существующие тесты зелёные; корректировка
  `test_merge_failure_leaves_the_task_in_the_gate` — только в рамках,
  явно разрешённых этим ТЗ.
