# PLAN: Один разбор строки зон с учётом переноса строки внутри пути

## Подход

Склейка разорванного вёрсткой пути переезжает в САМ разбор строки зон —
в `scripts/guard.py`, откуда её получают все потребители без собственной
копии (требование 1). Разбор при этом расслаивается на две функции, потому
что у строки зон два читателя с разными нуждами:

- `guard.zone_line_items(raw) -> list[str]` — только элементы перечня
  (деление по запятым, снятие завершающей точки предложения ТЗ, отсев
  пустых), в порядке записи. Это то, что нужно счёту зон для калибровки.
- `guard.zone_items(raw) -> set[str]` — те же элементы ПЛЮС кандидаты
  `PATH_MENTION` из той же строки (пояснение в скобках рядом с путём), как
  было до задачи. Это то, что нужно классификации путей.

Обе поверх одного приведения строки `guard._zone_line_text`: список YAML
склеивается запятой, перенос внутри пути снимается регулярным выражением
`guard._WRAPPED_PATH_BREAK` — буквально тем же правилом
`(?<=[/_-])\n[ \t]*`, что уже живёт в `orchestrator/catalog.py:279`
(`_TZ_WRAPPED_PATH_BREAK`). Правило копируется, а не переносится: SPEC
требование 3 запрещает править `catalog.py` (файл — зона задачи
01M3H1Z489CKJ8FHSRS4TYTPX2 в полёте), удаление его копии — отдельная
задача из «Не входит». Комментарий в `guard.py` называет эту двойственность
адресом, чтобы следующая задача нашла оба места.

`orchestrator/budget.py::count_zone_paths` становится
`len(guard.zone_line_items(text))` — свой разбор по запятым уходит
(требование 2). Именно `zone_line_items`, а не `zone_items`: через
`zone_items` в счёт попали бы кандидаты упоминаний путей, и строка
«scripts/guard.py (см. docs/stack.md), tests/» дала бы 4 зоны вместо 2 —
калибровка бюджета поехала бы. Импорт `from scripts import guard` в
`budget.py` цикла не создаёт: `guard` уже сейчас в графе импорта
`budget` через `orchestrator/retro.py:34`, а сам `guard` тянет только
`config`, `spend`, `yamlmini`, `zone_lock` — ни один из них `budget` не
импортирует.

`catalog.py` не меняется, и его предварительная склейка остаётся
безвредной: `sub("")` по уже склеенной строке ничего не находит
(идемпотентность — свойство самого выражения, требование 3, AC-3).

Потолок SPEC ($25) не переоцениваю — расхождения с числом файлов и шагов
плана нет.

## Влияние на систему

Затрагивается всё, что читает строку зон, — а это гейты и предупреждения
пульта, не только калибровка:

- `catalog._tz_path_check` (`orchestrator/catalog.py:188`) — отказ `new` по
  неклассифицированному и по защищённому пути ТЗ. После задачи он получает
  склейку, которой у него не было: разорванный путь перестаёт быть
  обрывком-каталогом. Это и есть предмет задачи (три отказа гейта 26.09
  чинились правкой ТЗ руками), гейт при этом не ослабляется — обрывок
  `orchestrator/` накрывал почти любой путь и ЗАНИЖАЛ число отказов, а
  целый путь покрывает ровно себя.
- `catalog._tz_zone_items` → `tasks.zones` и прогноз очереди зон
  (`zone_lock.forecast_overlaps`) — результат не меняется: склейка там уже
  была, вторая идемпотентна.
- `guard.spec_unclassified_paths` → гейт `spec_gate`
  (`fsm._approve_spec_gate`) и `budget.count_zone_paths` →
  `fsm.py:355`/`catalog.py:223` — значение `zones:` во frontmatter SPEC
  физически одна строка, переноса внутри пути в ней не бывает; поведение
  прежнее.

Ни один гейт, лимит, инвариант и тест не ослабляется: правило склейки
УЖИВАЕТ существующие проверки (`guard.PATH_MENTION`, `zone_lock._covered_by`,
`config.PROTECTED_PATHS`) без изменений, а `count_zone_paths` сохраняет
отсев пустых элементов и снятие завершающей точки — оба свойства зафиксированы
тестами шага 3 (`tests/test_zone_line_parse.py::CountZonePathsTest::
test_degenerate_inputs_keep_their_previous_counts`,
`::ZoneItemsWrapTest::test_line_without_a_wrap_keeps_the_previous_items`) и
планкой AC-2.

Откат — revert одного merge-коммита ветки: обе правки аддитивны,
внешних состояний (БД, файлов, веток) не создают.

## Риски

- Правило `(?<=[/_-])\n[ \t]*` — компромисс, уже принятый в
  `catalog.py:262–278`: разрыв в иной точке (`orchestrator/con⏎fig.py`) не
  склеивается (промах, не ложное срабатывание), а перенос после слова
  прозы не склеивается намеренно. Задача правило не расширяет.
- Узкий класс, которого у `catalog._tz_path_check` не было: `_tz_sections`
  склеивает ТЕЛА нескольких разделов «Зоны:» через `\n` (joiner по
  умолчанию), и если тело кончается ровно на `/`, `_` или `-`, новая
  склейка сольёт его с головой следующего тела в один непуть. ТЗ с двумя
  разделами «Зоны:», первый из которых кончается на разделитель, —
  вырожденный случай; отказ гейта от такого слияния не становится ложным
  (непуть-элемент ничего не покрывает, путь при этом не теряется:
  кандидаты `PATH_MENTION` берутся из той же склеенной строки). Чинить
  внутри задачи нельзя — это правка `catalog.py`, запрещённая
  требованием 3; отмечено ниже в «Предложения системе».

## Предложения системе

- Правило `_TZ_WRAPPED_PATH_BREAK` после этой задачи живёт в двух местах
  (`orchestrator/catalog.py:279` и `scripts/guard.py`) — не по выбору, а
  потому что зона `catalog.py` занята другой задачей в полёте. Класс:
  «зонный замок заставляет оставить дубликат правила в коде». Уборка уже
  описана в «Не входит» SPEC — стоит, чтобы такие отложенные уборки
  попадали в бэклог автоматически, а не держались на памяти следующего ТЗ.
- `skills/test-authoring.md` требует «Ловит мутацию: …» от КАЖДОГО нового
  теста, включая регрессию свойства, которое без подмены наблюдать нельзя
  (счёт зон здесь: старый и новый разбор не различает ни один вход —
  проверено перебором и ревью, и мной). Автор в такой ситуации пишет
  правдоподобную, но несбывающуюся мутацию; итерация 1 ревью ушла ровно на
  это. Класс: «обязательная заявка выталкивает автора в вымысел». Планка
  того же ТЗ пишет честнее — «Зелёный с рождения: … что держит»; стоит
  разрешить эту форму и в скиле, чтобы ревью сверяло её, а не фальшивую
  мутацию.
- Там же: `catalog._tz_sections` с `joiner="\n"` (`orchestrator/catalog.py:183`)
  склеивает тела разделов переносом, который теперь значим для разбора; у
  `_tz_zone_items` для этого уже есть `joiner=","`. Класс: «параметр,
  отличающий двух вызывающих, стал нести семантику разбора». Закрыть — той
  же задачей, что снимет дубликат склейки.
