## Проверяемость критериев

Красная фаза: все критерии идут через подделку `ci.gh`, поэтому до кода
настоящий `gh` не вызывается. Старый `_call` отвечает «не реализовано» без
`gh`: AC-1–AC-12 краснеют на утверждениях «шпион видел вызов» (решение
№1.8). AC-14 падает на `AttributeError` (`forge.github_call` нет), AC-15 —
на `TypeError` (лишний аргумент `target`), AC-17 — на ключах `GH_CALLS`.

неограниченного порождения процессов и меняющих команд против настоящего
репозитория нет: AC-10 работает git-командами в песочнице с локальным
голым `origin`. Одна оговорка: approve-сценарии (AC-3, AC-5, AC-6, AC-8,
AC-11, AC-12) читают CI через `ci.check_runs` → `ci.check_runs_page` →
`ci.gh("api", …)` (`orchestrator/ci.py:257-283`), то есть через ту же
подделку. Это безопасно, но см. отклонение 2.

## Пути обхода гейтов

- Белый список `github_call` можно «выполнить буквально», но пропустить
  `api` с записью: AC-14 его не проверяет, а шпион AC-13 на `ci.gh` видит
  `api`-вызовы `ci.check_runs_page` (`orchestrator/ci.py:267`). Тест,
  который отсеивает `api` по argv как «чтение CI», не заметит `api -X POST`
  из `_GitHub` (отклонение 2).
- Значение исполнителя фильтрует только `mr_assignee`. `github_call`
  пропускает любую строку после `--assignee=`/`--add-assignee=`, в том
  числе `@copilot`, `@me`, `a,b` (требование 7 описывает `<имя>` без
  правила). Если `mr_assignee` обойти (новый вызов `forge.assign_mr` с
  сырым значением), закрытый список не удержит (отклонение 3).
- Сверку адреса PR можно сделать только по владельцу — AC-1 это пропустит
  (отклонение 1). Вред — ссылка на PR чужого репозитория с тем же
  владельцем, то есть пульт потом будет читать и снимать черновик не того
  PR.

Не отклонение, к сведению Оператора: переименованный репозиторий
(GitHub отдаёт канонический адрес PR) даст несовпадение имени → PR без
ссылки → следующий `approve` уйдёт в эскалацию «уже существует». Это
отказ в безопасную сторону. И ещё: «уже существует» на входе в
`verifying` (`ensure_forge_draft_mr`) оставляет вход в `verifying`
отклонённым при каждом `advance` — ТЗ эскалации для пути черновика не
требует.

## Вердикт

`concerns` — SPEC можно вести дальше; три пробела проверяемости решаются
Оператором на гейте (уточнением критериев):

1. **AC-1 не различает владельца и имя** (`SPEC.md`, требование 1 и
   AC-1; разбор — `orchestrator/ci.py:103-116`). Случай чужого
   репозитория меняет только владельца
   (`https://<хост>/<другой владелец>/<имя>/pull/<номер>`), и реализация,
   сверяющая один владелец, проходит критерий. Предложение: добавить
   случай с тем же владельцем и другим именем (`…/<владелец>/<другое
   имя>/pull/<номер>` → без `iid`, ссылки нет), а лучше и хвост, не
   являющийся числом (`/pull/7/files`, `/pull/7x` → без `iid`).
2. **`api` с методом записи не закреплён критерием** (`SPEC.md`,
   требование 7 — «`api` с методом записи `_GitHub` не вызывает никогда»;
   ТЗ, требование 5). AC-14 не подаёт `github_call` вызов `api …`, а
   AC-13 не задаёт, как шпион `ci.gh` отделяет вызовы `_GitHub` от
   `ci.gh("api", …)` чтения CI (`orchestrator/ci.py:257-283`).
   Предложение: в AC-14 добавить `api -X POST repos/o/r/pulls/7/merge` и
   `api repos/o/r/pulls` → отказ с префиксом, `ci.gh` не вызван; в AC-13
   — шпион на четырёх функциях вызываемых напрямую (без approve) либо
   `ci.check_runs` подменён отдельно.
3. **Значение исполнителя в закрытом списке не задано** (`SPEC.md`,
   требование 7: `--assignee=<имя>`, `--add-assignee=<имя>`; правило имён —
