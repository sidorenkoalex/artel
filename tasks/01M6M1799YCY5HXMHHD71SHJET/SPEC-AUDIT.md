## Пути обхода гейтов

е-1. Разбор адреса из любого вывода `pr create`. Буква SPEC треб. 1 («номер PR
берётся из адреса PR в выводе `pr create`») не запрещает искать адрес в
stderr или при ненулевом коде. Реальный отказ `gh` «already exists» несёт
адрес существующего PR (б-1) — реализация получит `iid`, `open_forge_mr`
сохранит ссылку на PR, созданный не пультом (кем угодно в проекте), и гейт
вместо эскалации «MR ветки уже существует, ссылки в БД нет» снимет с него
черновик и назначит исполнителя. AC-5 этот путь пропускает, если фейк, как
написано в AC-5, лишь «содержит» текст без адреса. Нужно: адрес разбирается
только из stdout при коде выхода 0; признак «уже существует» — при ненулевом
коде, раньше любого разбора адреса; в AC-5 stderr фейка несёт адрес
существующего PR, и утверждается «ссылки в БД нет».

е-2. «Признак реализации, а не литерал» (треб. 8) не проверяется ничем.
Опыт: `support_comparisons` сторожа
(`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:467`) на тексте
`if forge.hosting(target) == "github"` в `github_adapter.py` находок не даёт
(`field_like` смотрит только имя атрибута `hosting`), тогда как
`targets.target(t).get("forge") == "github"` находит. Разработчик может выбрать
вид исполнителя сравнением `forge.hosting(...)` с литералом — AC-15 зелёный,
сторож зелёный, требование 8 нарушено. Нужен критерий (например, подменённая
реализация в `forge.IMPLEMENTATIONS` под иным ключом с признаком GitHub даёт
имя-исполнителя) или явное признание Оператором, что требование держит
только ревью.

е-3 (следствие в-1). Без названной точки входа закрытого списка
разработчик может держать проверку в помощнике, через который ходит только
часть вызовов; AC-13 (шпион) это ловит лишь для argv, которые функции
действительно строят, — что и требуется; угрозы вне в-1 не вижу.
