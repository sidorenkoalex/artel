# Ручной мерж для GitHub, часть 1: функции MR хостинга GitHub через `gh` (`open_mr`, `undraft_mr`, `assign_mr`, `mr_status`)

Решение Оператора 01.11: «forge `_GitHub`: `open_mr`/`undraft_mr`/`assign_mr`/`mr_status` через `gh`; открыть `github` + `target-human`; те же проверки записи и `doctor`». Работа поделена на две задачи: эта — функции MR хостинга GitHub без открытия пары; часть 2 (`TZ-github-target-human-part2.md`) — открытие пары, проверки записи и строки `doctor`. Номера строк — по origin/main 92bdb87b7; аналитик сверяет их по коду на момент SPEC.

## Факты

1. ## Требуется

1. **`_GitHub.open_mr(target, branch, base, title, body, draft, assignee)`** — одним вызовом `gh pr create --head <branch> --base <base> --title <title> --body <body>`, с `--draft` при `draft`, с `--assignee=<имя>` одним аргументом при заданном исполнителе; `gh` — через `ci.gh` с `repo` = адрес проекта (факт 5). Успех — `forge.MergeRequest` с номером PR в `iid`, адресом в `url` и полями из `mr_status` этого номера. Адрес PR в выводе не разобран — результат с причиной. Частичный успех: номер PR разобран из вывода `pr create`, а последующее чтение не удалось — результат несёт `iid` и `url` вместе с причиной, и ссылка на MR сохраняется в БД при любом исходе чтения в общей точке обоих путей открытия — `github_adapter.open_forge_mr` (через неё идут и черновик при входе в `verifying`, `ensure_forge_draft_mr`, и `_deliver_mr` гейта мержа; сейчас она выходит до `store.set_mr_link` при любой причине, `orchestrator/github_adapter.py:421-423`); запись журнала «MR открыт» при частичном успехе не пишется — SPEC называет это явно (иначе следующий `approve` получит «уже существует» и уйдёт в эскалацию при PR, созданном самим пультом). Отказ «PR этой ветки уже существует» `_deliver_mr` обязан узнавать так же, как 409 GitLab (эскалация, факт 8) — в обоих видах: проверка самого `gh` («a pull request for branch … into branch … already exists») и отказ сервера 422 («A pull request already exists»); SPEC закрепляет оба текста; форму признака (текст причины по образцу `orchestrator/fsm_merge_gate.py:1589` или отдельное поле результата) выбирает аналитик; тексты и поведение GitLab не меняются.
2. **`_GitHub.undraft_mr(target, mr)`** — читает PR (`mr_status`); черновик — `gh pr ready <номер>`, затем результат по новому чтению; не черновик — результат чтения без вызова изменения (как GitLab, факт 4).
3. **`_GitHub.assign_mr(target, mr, assignee)`** — `gh pr edit <номер> --add-assignee=<имя>` (одним аргументом), затем результат по новому чтению.
4. **`_GitHub.mr_status(target, mr)`** — `gh pr view <номер> --json number,url,title,state,isDraft,assignees,baseRefName,headRefName,headRefOid,mergeCommit`. Сопоставление полей:
   - `iid` ← `number`; `url` ← `url`; `title` ← `title`; `draft` ← `isDraft is True`;
   - `state` ← `OPEN` → `opened`, `MERGED` → `merged`, `CLOSED` → `closed`; иное значение — как есть (гейт его не узнает и откажет, факт 8);
   - `assignee` ← `login` первого из `assignees`, пусто — `None`;
   - `target_branch` ← `baseRefName`; `source_branch` ← `headRefName`; `sha` ← `headRefOid`;
   - `merge_commit_sha` ← `mergeCommit.oid`, `null` — `None`; `squash_commit_sha` — всегда `None` (GitHub отдаёт коммит вливания одним полем при всех трёх методах вливания).
   PR не найден — причина с подстрокой `(404)` (`mr-sync` даст «MR не найден», факт 9) — ТОЛЬКО когда ответ говорит об отсутствии PR; отсутствие репозитория («Could not resolve to a Repository …»), нехватка прав, отказ авторизации (код выхода 4) и сбой сети — причина без `(404)` («не прочитан»), иначе `mr-sync` скажет «MR не найден» при отозванном токене; вывод не JSON или без `number` — причина. Распознавание «не найден» по ответу `gh` аналитик закрепляет по `gh help` и записывает в SPEC; на пробе Оператор сверяет с живым ответом.
5. **Закрытый список вызовов `gh`** у `_GitHub` — `pr create`, `pr view`, `pr ready`, `pr edit <номер> --add-assignee=<имя>` (и прежнее чтение check runs); список проверяет и подкоманду, и флаги: `pr edit <номер> --base x` — вне списка. Вызов вне списка отказывает до запуска `gh` с именованной причиной (по образцу `orchestrator/gitlab_adapter.py:157`). `pr merge`, `pr close`, `pr comment`, `api` с методом записи адаптер не вызывает никогда (ADR-0029 п. 8, «Решения Оператора 26.10» п. 5).
6. **Исполнитель по имени для GitHub.** Вид исполнителя задаёт реализация в реестре `forge` (признак реализации, не сравнение значения `forge` с литералом — факт 12): GitLab — целое, как сейчас; GitHub — имя пользователя по правилу имён GitHub (латинские буквы, цифры и одиночные `-` не в начале и не в конце, до 39 знаков) или целое, переданное строкой. Отказ (не назначен, запись журнала): `@me`, `@copilot` и любое значение с `@`, список через запятую, значение с ведущим `-`, пробелы. Флаг передаётся одним аргументом `--assignee=<имя>` / `--add-assignee=<имя>`. Запись журнала о неназначенном для GitHub — своим текстом без «не числовой id»; прежний текст — для GitLab и для вызова без проекта. `--add-assignee` добавляет, а не заменяет исполнителя (у GitLab — замена): если поле сменили между черновиком и гейтом, у PR будут оба, `assignee` результата — первый; это отмечается в SPEC, поведение не выравнивается. `mr_assignee` получает проект; вызов без проекта (`mr_assignee(policy)`) ведёт себя как сейчас. Вызовы `orchestrator/github_adapter.py:416` и `orchestrator/fsm_merge_gate.py:1894` передают проект. Неназначенный исполнитель — запись журнала: для GitLab и вызова без проекта — прежним текстом, для GitHub — своим.
7. **Не меняется**: `token_user`, `token_expiry`, `protections`, `project_info`, `branch_pipeline`, `job_result`, `job_test_report` для GitHub по-прежнему «не реализовано» (факт 11 — сверка автора и строки `doctor` остаются прежними); путь `gh` гейта `operator` (`ensure_draft_mr`, `github_adapter.undraft_mr`) — без изменений; `SUPPORTED_PAIRS` — без изменений (часть 2).

Критерии приёмки (пара включается в тесте подменой `targets.SUPPORTED_PAIRS`; `gh` — подделка `ci.gh`, записывающая argv и отдающая заготовленный ответ):
- `open_mr`: черновик и не черновик, с исполнителем и без — argv подделки ровно по требованию 1 (флаги `--draft`, `--assignee` есть только когда нужны, `--repo` — адрес проекта); `iid`, `url` и поля чтения заполнены;
- `open_mr`, ответ «PR уже существует» → `approve` на `merge_gate` даёт эскалацию «MR ветки уже существует, ссылки в БД нет»; иной отказ `gh` → задача на гейте, причина в журнале, ссылки на MR в БД нет;
- `undraft_mr`: черновик → `pr ready` вызван один раз; не черновик → `pr ready` не вызван; отказ `gh` → причина, `_ready_existing_mr` оставляет задачу на гейте;
- `assign_mr`: argv с `--add-assignee=<login>` одним аргументом; отказ → задача на гейте с причиной;
- `mr_status`: `OPEN`/`MERGED`/`CLOSED` → `opened`/`merged`/`closed`; иное значение → `approve` отказывает «статус MR неизвестен»; PR не найден → `mr-sync` — «MR не найден», `--confirm` отказывает; `mergeCommit: null` → `merge_commit_sha` `None`; `squash_commit_sha` всегда `None`; нет `baseRefName` → `mr-sync` — «неизвестно»;
- `mr-sync` в песочнице с локальным `origin` (голый репозиторий), PR влит каждым из трёх методов — коммитом слияния, сжатием, перебазированием (в песочнице воспроизводится git-командами, `mergeCommit` подделки — получившийся коммит) → «влит этим MR» по признаку (а), `--confirm` → `done`, `closed_as=merged_upstream`; PR закрыт, правка внесена в base иначе → «в базе, влит иначе»;
- шпион на вызовах `_GitHub` видит только вызовы из закрытого списка требования 5 (чтения CI гейта — `ci.check_runs` и прочие вызовы вне `_GitHub` — список не ограничивает, SPEC перечисляет их поимённо); вызов вне списка, в том числе `pr edit <n> --base x`, отказан до запуска; `pr merge`, `pr close`, `pr comment` не появились ни разу;
- частичный успех `open_mr`: `pr create` вернул адрес, чтение отказало — ссылка на MR в БД сохранена, задача на гейте с причиной; повторный `approve` не уходит в эскалацию «уже существует»; то же при открытии черновика на входе в `verifying` (`ensure_forge_draft_mr`): ссылка сохранена, следующий вход не получает «уже существует»;
- «уже существует» в обоих текстах (проверка `gh`, отказ 422) → эскалация; «нет репозитория», код выхода 4, сбой сети → `mr-sync` «не прочитан», не «MR не найден»;
- исполнитель: GitHub и `alice` → `--assignee=alice`/`--add-assignee=alice`; GitHub и `42` → `42` строкой; GitHub и `@copilot`, `@me`, `a,b`, `-x`, `a b` → не назначен, `gh` без флага исполнителя, запись журнала GitHub-текстом; GitLab и `alice` → не назначен с прежней записью; булево — не назначен; `mr_assignee(policy)` без проекта — прежние ответы;
- `token_user` и прочие функции требования 7 для GitHub — по-прежнему «не реализовано для github», `gh` не вызван; запись «сверка автора — после адаптера» прежняя;
- сторож литералов и прежние тесты GitLab, гейта `operator`, `mr-sync` — зелёные без правки.

Безопасность тестов: ни одного обращения к настоящему GitHub и к настоящему `gh` — подделка на уровне `ci.gh` (или исполняемый файл `gh` во временном `PATH`, если аналитик выберет его); связка ключей не читается (`gitcmd.hosting_token` не вызывается или подменён); проекты — вымышленные во временной песочнице `config`, `origin` — локальный голый репозиторий; никогда — настоящий клон и настоящий локальный слой.
