2. **Распознавание «PR не найден» в `mr_status` (требование 4 ТЗ): закрепить текст GraphQL-ответа, а не «по `gh help`».** `gh` в окружении роли не запускается (даже `gh help exit-codes` требует подтверждения, которого в шаге нет), поэтому справка на этой машине НЕ прочитана; дальнейшее — по известной аналитику справке `gh`, не по опыту: `gh help exit-codes` называет только коды выхода `0` (успех), `1` (сбой), `2` (отмена), `4` (нужна авторизация) и текстов ответа сервера не содержит. Признак «не найден» тогда берётся из ответа GitHub GraphQL, который `gh pr view <номер>` печатает в stderr с кодом 1: `Could not resolve to a PullRequest with the number of <номер>`. Отсутствие репозитория — `Could not resolve to a Repository with the name …` (ТЗ, требование 4).
   - A) SPEC закрепляет «не найден» = код выхода 1 и в stderr подстрока `Could not resolve to a PullRequest` → причина с `(404)`; всё прочее (в том числе `Could not resolve to a Repository`, код 4, сбой сети, не JSON) → причина без `(404)` («не прочитан»). Текст сверяет Оператор на пробе после части 2 (ТЗ, «Не входит»).
     - ломается: ничего из нынешнего; если живой `gh` пишет иначе, отсутствующий PR даст `mr-sync` «неизвестно» вместо «MR не найден» (безопасная сторона: задача не закрывается по ложному «не найден»).
     - ослабляется: ничего; «MR не найден» держит `orchestrator/mr_sync.py:319-320`, ложное «не найден» при отозванном токене исключено.
     - цена: ничего сверх SPEC.
     - чьё решение: роль (аналитик) по ТЗ; Оператор подтверждает на пробе.
   - B) Оператор называет иной текст признака по живому ответу `gh` до SPEC.
     - ломается: ничего.
     - ослабляется: ничего.
     - цена: проба `gh pr view` на настоящем репозитории до SPEC — вне этой задачи (ТЗ, «Не входит»).
     - чьё решение: Оператор.
   - дефолт: A.

## Решения аналитика для SPEC (к сведению, не вопросы)

- Признак «PR этой ветки уже существует» (требование 1 ТЗ): отдельное
  булево поле результата `forge.MergeRequest` (по умолчанию `False`),
  которое ставит только `_GitHub.open_mr` на любом из двух текстов —
  проверка `gh` `a pull request for branch "…" into branch "…" already exists`
  и отказ сервера `A pull request already exists`; `_deliver_mr` эскалирует
  «MR ветки уже существует, ссылки в БД нет» по полю или по прежнему
  коду 409 GitLab (`orchestrator/fsm_merge_gate.py:1589-1590`, без
  изменения). Причина: признак не зависит от текста причины, и тексты
  GitLab не трогаются.
- `mr_assignee` с проектом, хостинг которого не определён (запись без
  `forge` или значение вне реестра), ведёт себя как вызов без проекта —
  иначе краснеет `tests/test_mr_delivery_units.py::ExistingLinkTest::test_without_numeric_assignee_assign_mr_is_not_called`
  (подмена `targets.target` там отдаёт запись без `forge`), а ТЗ требует
  прежние тесты зелёными без правки.
- Бюджет — $40 (рамка ТЗ; калибровка «до 15 критериев, до 7 файлов» —
  ~45, ставка только вниз); сигналы объёма (зон ≥ 5, критериев ≥ 10)
  — обоснованием монолита: ТЗ уже часть 1 деления на две.
