# PLAN: регрессия №16 — планка на переходе `in_dev -> verifying` гоняется и при свежей ветке

## Подход

`_acceptance_run_refuses` (`orchestrator/fsm_advance.py`) для собственного
target брала `acc_tdir = <worktree>/tasks/<id>` напрямую, без
материализации из артефактной ветки — на пути `Fresh` (подтяжка ничего
не делает) этот каталог на диске worktree пуст (автокоммит шага унёс
`tasks/<id>/` в артефактную ветку), и `acceptance.run` молча отвечал
зелёным «acceptance_tests/ нет — не заведены».

Правка — добавить для собственного target тот же приём, что уже стоит на
ветке внешнего target (`if target != config.DEFAULT_TARGET`):
`acceptance.materialize_from_branch(task_id, branch, run_cwd)` ДО
`acceptance.run`, независимо от исхода подтяжки. Материализация — идемпотентная
перезапись `tasks/<id>/acceptance_tests/` из артефактной ветки в
`run_cwd` (тот же `acceptance.materialize_from_branch`, что уже
используется `pull.py::_materialize_and_run_plank` и внешней веткой
`_acceptance_run_refuses`), поэтому её безопасно звонить и на пути
`Pulled`, где подтяжка уже прогнала планку сама (требование 3 SPEC — не
ослаблять до отсутствия повторного прогона).

Дальше нужно отличить «планки легитимно нет» (SPEC без AC-разметки либо
`skip_tests`) от «планка не найдена в источнике» при активном локе —
как это уже сделано в `pull.py::_materialize_and_run_plank`. Добавлен
локальный хелпер `_missing_plank_refuses()` внутри
`_acceptance_run_refuses`: если после материализации `acc_tdir /
"acceptance_tests"` не каталог — читает SPEC.md АРТЕФАКТНОЙ ветки
(`fsm._read_branch_text_or_refuse`, тот же узел чтения, что и у
`pull.py`) и решает по `guard.requires_ac_markup(meta)` — то же условие
легитимности, что и в `pull.py`, без дублирования правила другим кодом.
Легитимная пустота (нет AC-разметки, либо есть `skip_tests` — это
покрыто самим `requires_ac_markup`) не блокирует переход; иначе — именно
отказ «планка не найдена в источнике», не зелёное «не заведены».

Решение архитектурно не значимое — переиспользование существующего
приёма (`materialize_from_branch` + `requires_ac_markup`) на втором из
двух путей, где приём уже стоял на одном; отдельного ADR не требует.

## Шаги

1. `orchestrator/fsm_advance.py::_acceptance_run_refuses` — материализация
   планки для собственного target ДО `acceptance.run` (ветка
   `elif workspace.on_task_branch(...)`), плюс `_missing_plank_refuses()`
   на обеих ветках (внешний и собственный target) для отличения
   легитимного отсутствия планки от отказа «не найдена в источнике».
2. Юнит-тесты регрессии в `tests/test_branch_freshness_gate.py` (или
   соседний модуль того же назначения) на: `Fresh` + материализация +
   реальный прогон; отсутствие планки в источнике при локе → именованный
   отказ; `skip_tests` → переход проходит. Приёмочная планка задачи
   (`tasks/01M283NJV2PNDSS7J2HKS19YHJ/acceptance_tests/
   test_fresh_plank_materializes.py`) уже покрывает все пять критериев
   приёмки дословно — она залочена (T023), доработку не требует.

## Влияние на систему

Изменение — внутри одного гейта (`_acceptance_run_refuses`), порядок
состояний ADR-0015 не трогается. `acceptance.materialize_from_branch`
уже используется на трёх узлах (`pull.py`, внешний target той же
функции) — четвёртый вызов того же чистого приёма не меняет его
контракт и не расширяет поверхность. Путь `Pulled`/`Conflict` внутри
`pull.py` не правится (вне зоны, см. SPEC «Не входит») — только
используется как есть; собственный повторный прогон на этом пути
сохранён (AC-4), значит планка гоняется два раза на `Pulled` — то же
поведение, что было до правки, не ослабление.

Единственный новый инвариант — отказ «планка не найдена в источнике»
при локе/AC-разметке без легитимного пропуска: раньше такой случай
проходил переход зелёным молча, теперь блокирует его именованным
отказом. Это ужесточение (планка теперь гоняется там, где раньше не
гонялась) — не ослабление; принцип целостности не нарушен. Откат —
`git revert` коммита правки, гейт возвращается к прежнему (ошибочному)
поведению.

Побочных эффектов на другие переходы/гейты нет: `_acceptance_run_refuses`
вызывается только из `in_dev -> verifying` (и симметрично из `review ->
verifying` через тот же хелпер — уже проверено существующими тестами
`tests/test_branch_freshness_gate.py`, они остались зелёными без правки
ассертов).

## Риски

- Материализация на каждый `advance` (а не только при `Pulled`) — лишняя

  паттерн уже стоит на внешнем target с момента SPEC
