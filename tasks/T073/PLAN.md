# PLAN: Retention-политика и команда prune

## Подход

Два независимых механизма, оба уже опираются на существующее право
оркестратора убирать хвосты задачи (T008/T045):

1. **Уборка ветки/worktree при `done`** — расширение того же окна
   `merge_gate -> done` (`orchestrator/fsm.py` `_cmd_approve_merge_gate`),
   которое уже убирает worktree после успешного merge (T045). Ветка к
   этому моменту ТОЛЬКО ЧТО влита `--no-ff` — `cleanup.drop_task_branch`
   (право `kill`) для нашего случая не годится: она НАМЕРЕННО оставляет
   смерженную ветку (класс "убитая задача, чья ветка успела уехать в
   main отдельно" — история). Здесь наоборот: смержённость — не повод
   оставить, а условие удалить. Новая функция `cleanup.
   drop_merged_task_branch` использует безопасный `git branch -d`
   (не `-D`) — git сам откажет, если ветка внезапно не влита, и это
   единственная защита, которая тут нужна. Порядок — worktree первым
   (уже так в коде): `-d` не удалит ветку, пока её держит worktree.

2. **Команда `prune`** — новый модуль `orchestrator/prune.py`,
   `cmd_prune(execute: bool = False)` (стиль `doctor.cmd_doctor
   (restore=False)`/`canary.cmd_canary(..., rewrite_baseline=False)`).
   План (dry-run) и исполнение делят один и тот же расчёт кандидатов —
   различается только то, вызывается ли действие (`Path.unlink`/
   `store.archive_alert`) или нет; отчёт печатается в обоих режимах на
   одних и тех же данных, чтобы план и факт называли один материал
   (AC-7).

   - **Логи**: кандидат на удаление — файл `.artel/logs/*.log`,
     ОДНОВРЕМЕННО (а) старше `config.LOG_RETENTION_DAYS` (90) по mtime
     И (б) чей task_id (префикс имени файла до первого `-`,
     `<task_id>-<role>-<N>.log`, `orchestrator/agent_log.py`) не входит
     в "последние N" — топ `config.LOG_RETENTION_KEEP_TASKS` (20) id
     задач `store.all_tasks()`, отсортированных по `store.task_number()`
     по убыванию. Не найденный в БД task_id (лог осиротевшей/несуществующей
     задачи) в "последние N" тоже не входит — он либо удалится по
     возрасту, либо переживёт следующий прогон, если моложе порога;
     отдельного случая для него не заводится (SPEC не выделяет такой
     класс).
   - **Alerts**: кандидат на архивацию — любая строка `alerts` (любой
     `kind`, вне зависимости от `ack`) с `ts` старше
     `config.ALERT_ARCHIVE_DAYS` (90). Перенос — не дублирование:
     `store.archive_alert` вставляет строку в новую таблицу
     `alerts_archive` (та же схема + `archived_ts`) с тем же `id`,
     затем удаляет исходную строку той же транзакцией.

   SQL — только в `store.py` (ADR-0003 3ж, докстринг store.py:
   «единственный модуль, который пишет SQL»): `prune.py` зовёт новые
   функции `store.alerts_older_than`/`store.archive_alert` по имени,
   как и остальной пакет зовёт `alerts.py`/`budget.py`.

3. **CLI**: `prune` — новая строка таблицы команд `artel.py`, флаг
   `--execute` (по образцу `--restore`/`--rewrite-baseline` у соседних
   команд).

4. **`docs/retention.md`** — одностраничник по видам данных из
   требования 1 SPEC, со ссылкой на именованные константы конфига для
   N=20 и явными "90"/"squash"/"архив"/"вечн"/"premod" по каждому
   пункту (AC-8, AC-9).

5. **Текст уточнения инварианта 16** — готовится здесь, не в
   `docs/adr/` (AC-10, вне объёма этой задачи создавать/править ADR):

   > Инвариант 16 («История наблюдаемости переживает задачу:
   > `.artel/logs/` уборка не трогает») кодирует конкретный тест —
   > `test_kill_cleanup.KillCleanupTest.test_run_logs_survive_the_kill`
   > — и его область: УБОРКА ОДНОЙ ЗАДАЧИ на переходе её жизненного
   > цикла (`kill`, и с этой задачи — `done`) не имеет права
   > дотягиваться до `.artel/logs/`. Это защита от одного конкретного
   > риска — реакция на смерть/закрытие ОДНОЙ задачи стирает историю
   > наблюдаемости ВСЕХ задач заодно, тихо и без отдельного решения
   > Оператора.
   >
   > Команда `prune` — не уборка задачи и не срабатывает на переходе её
   > FSM: это отдельная, явно вызываемая Оператором операция над всем
   > `.artel/logs/`/`alerts` сразу, с собственной, задокументированной
   > политикой (`docs/retention.md`), по умолчанию dry-run, и с
   > отчётом о том, что́ именно тронуто. Она не привязана к жизненному
   > циклу ни одной конкретной задачи — работает и когда ни одна задача
   > не переходит между состояниями. Инвариант 16 запрещает КОСВЕННОЕ,
   > привязанное к судьбе одной задачи стирание логов; `prune` —
   > ПРЯМОЕ, поимённое, отчётное действие над логами КАК ТАКОВЫМИ,
   > симметричное остальным операторским командам (`kill`, `budget`,
   > `alert-ack`), которые тоже прямо и явно меняют состояние системы.
   > Коротко: «история переживает задачу» — да, но не переживает эпоху
   > без предела: у логов есть собственная, отдельно объявленная
   > политика хранения, и её исполняет только явная операторская
   > команда, а не побочный эффект закрытия чьей-то задачи.
   >
   > Предлагаемая правка текста инварианта 16 (docs/invariants.md,
   > строка 16), ЕСЛИ Оператор решит принять ADR: «История
   > наблюдаемости переживает ЗАДАЧУ: уборка `kill`/`done` не трогает
   > `.artel/logs/` — их удаляет только политика хранения (`prune`,
   > docs/retention.md), не побочный эффект перехода FSM отдельной
   > задачи.» Принятие — вне объёма этой задачи (SPEC «Не входит»).

## Шаги

1. `config.py`: константы `LOG_RETENTION_KEEP_TASKS = 20`,
   `LOG_RETENTION_DAYS = 90`, `ALERT_ARCHIVE_DAYS = 90`.
2. `store.py`: таблица `alerts_archive` (SCHEMA + `migrate()`,
   тем же приёмом, что и остальные догоняемые таблицы);
   `alerts_older_than(conn, cutoff_ts)`, `archive_alert(conn, alert_id)`.
3. `cleanup.py`: `drop_merged_task_branch(branch) -> str`.
4. `fsm.py`: `_cmd_approve_merge_gate` — после уборки worktree
   (`workspace.remove`) зовёт `cleanup.drop_merged_task_branch(branch)`
   и журналирует результат отдельной записью (AC-3: запись содержит
   имя ветки И глагол уборки, не совпадает с существующей записью
   `state -> done`).
5. `orchestrator/prune.py`: `cmd_prune(execute: bool = False)` —
   расчёт кандидатов (логи, alerts), dry-run/исполнение, отчёт
   (AC-4..AC-7).
6. `artel.py`: импорт `prune`, строка `"prune"` в таблице команд
   (флаг `--execute`), обновление докстринга (список команд, модулей).
7. `docs/retention.md` — новый файл (AC-8, AC-9).
8. Юнит-тесты (`tests/test_prune.py`, дополнение `tests/
   test_kill_cleanup.py`-соседа для новой функции `cleanup.
   drop_merged_task_branch` — отдельный файл `tests/
   test_done_branch_cleanup.py`, тот же стиль `TmpRepoTest`).
9. Регенерация `docs/codebase-map.md` (`python3 scripts/
   codebase_map.py`) — правятся `.py` в `orchestrator/`.

## Влияние на систему

- `store.py` получает новую таблицу (`alerts_archive`) и две функции
  чтения/переноса; существующие таблицы/функции не меняются, `alerts`
  теряет строки, но не бесследно (переезд, не удаление) — тот же
  принцип, что и у `docs/adr/0005` (архивация, не потеря). Ни один
  существующий тест не утверждает, что строки `alerts` вечны без
  архивации — `docs/invariants.md` о таблице `alerts` не говорит вовсе.
- `fsm.py` получает новый вызов на уже существующем, хорошо
  протестированном пути (`merge_gate -> done`); порядок (worktree
  первым) сохраняет инвариант "не удалить ветку, пока её держит
  worktree" (тот же, что уже проверен для `kill`, T045 AC-5).
  Провал `git branch -d` (git отказал — ветка внезапно не влита)
  не отменяет переход в `done`: `done` уже наступил (`set_state`
  выше), это симметрично тому, как `workspace.remove` уже сегодня не
  умеет отменить `done` при своём провале — уборка идёт ПОСЛЕ перехода
  и не может его откатить (тот же принцип, что `cleanup.
  cleanup_killed_task`, комментарий в cleanup.py: "любой невыясненный
  факт — это «оставлено», а не исключение").
- Инвариант 16 (`docs/invariants.md`, `test_kill_cleanup.
  test_run_logs_survive_the_kill`) НЕ ослабляется и не правится этой
  задачей: `prune` — отдельная, явно вызываемая команда, не часть
  уборки `kill`/`done` (см. текст уточнения выше). Тест инварианта
  проверяет `cleanup.cmd_kill` — тот логи по-прежнему не трогает
  (в `cleanup.py` логика для этого не добавлялась).
  `docs/invariants.md` и `tests/test_invariants.py` не редактируются
  (AC-11) — это подтверждает дифф-тест приёмки, залоченный test_author.
- `docs/adr/` не создаётся и не правится (AC-10) — то же самое
  подтверждает дифф-тест приёмки.
- `MAX_PARALLEL_TASKS`/lease/merge_lock не затрагиваются: `prune` не
  берёт lease конкретной задачи (не мутирует ни одну строку `tasks`)
  и не участвует в мьютексе merge-окна — она читает/чистит только
  `.artel/logs/` и `alerts`, тем же классом операций, что и `doctor`
  (не мутирующая по смыслу lease-контура команда).
- Откат: `LOG_RETENTION_KEEP_TASKS`/`ALERT_ARCHIVE_DAYS` — обычные
  константы конфига, правка требует Оператора (ADR-0002, класс
  «лимит»), но сам факт их появления не меняет поведения ничего, кроме
  новой команды `prune`. Уборка ветки на `done` — правится/откатывается
  как обычный код (не инвариант, не гейт, не лимит).

## Риски

- `git branch -d` в редком случае (главная копия ещё не видит merge-
  коммит по какой-то причине гонки) откажет — это оставляет ветку,
  не ломает переход; сообщение в журнале называет причину.
- Название архивной таблицы (`alerts_archive`) зафиксировано
  приёмочным тестом AC-6 (`tasks/T073/acceptance_tests/
  test_ac6_prune_execute_archives_old_alerts.py`) — контракт, не
  предмет выбора этой реализации.
