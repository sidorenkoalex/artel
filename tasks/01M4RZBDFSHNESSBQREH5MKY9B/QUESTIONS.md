# QUESTIONS: Бриф: шаблон артефакта роли целиком

## Вопросы

Контекст батча. Требование 7 ТЗ велит аналитику найти полным прогоном
набора все существующие тестовые методы, чьё ожидание изменится, и
внести их в раздел SPEC «Меняемое поведение». Я собрал черновой
прототип требований 1–5 в отдельном одноразовом worktree: таблица
«роль → шаблоны» в `brief.py`, чтение
`gitcmd.show(config.MAIN_BRANCH, "templates/<имя>", repo=config.ROOT)`
в конце `analyst_map_component`/`developer_brief`/`spec_auditor_brief`,
пометка и запись «бриф: шаблон не прочитан» при неудаче, правка миссий
`role_prompt.py`. На прототипе я прогнал 84 модуля `tests/`, которые
касаются брифа, миссий и `cmd_run` (1 615 тестов). Новыми покраснели три
метода, и все три — по самому заданному поведению, не из-за огрехов
прототипа:

- `tests/test_brief.py::DeveloperBriefTest::test_assembles_three_components_and_journals_their_hashes`:
  `3` → `4` (`tests/test_brief.py:224`). Скалярный литерал, совпадает с
  требованием 7 ТЗ.
- `tests/test_brief.py::AnalystMapComponentTest::test_adds_only_the_map_and_journals_one_hash`:
  `1` → `3` (`tests/test_brief.py:263`). Скалярный литерал, совпадает с
  требованием 7 ТЗ.
- `tests/test_review_package.py::CmdRunReviewPackageTest::test_developer_step_has_no_package`
  (`tests/test_review_package.py:1242`). Это `assertEqual` точного
  упорядоченного списка git-вызовов шага developer. Требование 3 ТЗ
  добавляет в шаг вызов `["-C", root, "show", "main:templates/PLAN.md"]`
  между `ls-tree … tasks/<id>` (`:1262–1264`) и
  `["config", "--get", "user.name"]` (`:1265`). Правка ожидания — это
  вставка элемента в литерал-список, а не смена скалярного литерала.

Третий метод разделом «Меняемое поведение» не оформить. Раздел принимает
только скалярные литералы, контейнер `approve` гейта SPEC отвергает
(`scripts/guard.py::behavior_change_refusals`, пункт «в»). Гейт
неослабления видит вставку элемента как смену маскированной формы
утверждения: `scripts/guard.py:1674–1685` даёт
`ASSERTION_CHANGE_OTHER`, а не «смену ожидания». Поэтому без мандата
Оператора рубеж `in_dev -> verifying` остановит задачу на этом методе,
хотя по существу утверждение становится строже (список длиннее, прежние
элементы на месте).

1. **Как пропустить обязательную правку ожидания `tests/test_review_package.py::CmdRunReviewPackageTest::test_developer_step_has_no_package` (вставка вызова `show main:templates/PLAN.md` в точный список git-вызовов)?**
   - A) Мандат строкой ANSWER: `Ослабление тестов разрешено: tests/test_review_package.py::CmdRunReviewPackageTest::test_developer_step_has_no_package`, а в SPEC — отдельное требование: в ожидаемый список вставлен ровно один элемент `["-C", root, "show", "main:templates/PLAN.md"]` между `ls-tree … tasks/<id>` и `config --get user.name`, прочие элементы и их порядок не меняются.
     - ломается: ничего; ожидаемый список становится длиннее на один вызов, а точное равенство всего списка сохраняется.
     - ослабляется: формально — контроль гейта неослабления над этим одним методом на время задачи (`orchestrator/advance_gates/test_integrity.py`, сверка с мандатом). Фактически утверждение строже прежнего; что вставлен ровно один элемент, проверяет ревьювер по требованию SPEC.
     - цена: ~0 — одна строка ANSWER, задача идёт своим маршрутом.
     - чьё решение: Оператор.
   - B) Шаблон PLAN developer не получает: таблица «роль → шаблоны» без developer, остальные роли — по ТЗ.
     - ломается: главная цель ТЗ — `templates/PLAN.md` по-прежнему читают отдельным вызовом 70% первых шагов developer (замер 12.10 в ТЗ); `test_review_package.py` не меняется.
     - ослабляется: ничего.
     - цена: задача теряет основной эффект; требования 1, 6 и 7 ТЗ (developer → PLAN, мутация «developer не получил шаблон PLAN», `3` → `4`) пришлось бы переписать.
     - чьё решение: Оператор.
   - C) Оператор сам правит ожидание теста отдельным MR в main до задачи, а аналитик пишет SPEC без этого метода.
     - ломается: до мержа этой задачи тест в main ждёт вызов, которого код ещё не делает, — main красный; либо правка едет одновременно с кодом, и тогда это вариант A.
     - ослабляется: зелёный main (CI `main`).
     - цена: отдельный MR Оператора и окно красного main.
     - чьё решение: Оператор.
   - дефолт: A — единственный вариант, который сохраняет цель ТЗ и не красит main; по существу утверждение строже прежнего.
