# ТЗ: диагностика таймаута и фактический контекст следующего шага роли

Источник: решение Оператора в чате 07.10.2026 — подготовить задачи по итогам аудита расхода.

## Проблема и факты
С 28.09 записано 14 частичных расходов на $243.47 (расчёт пульта, не подтверждённые списания). Задача 01M42PENCS26D0656X8FR7DFA7: пять таймаутов разработчика, оценка $107.50; первый запуск содержит 458 вызовов инструментов. После таймаута продолжалась работа с тестами. Нельзя объявить все эти случаи зависанием или полной потерей работы.
Чекпоинт уже существует: runner._finish_timeout вызывает checkpoint.commit_timeout_checkpoint до записи agent run TIMEOUT. Задачи о группах процессов, сохранении WIP и стороже уже завершены. Повторять эту механику не нужно. Отдельный черновик tz-k3-git-hang.md касается зависшего git после списания и не входит сюда.

## Требуется
1. При таймауте сохранять компактную машинную диагностику запуска: роль/попытка/модель, длительность, последняя зарегистрированная активность и её время при наличии, ограниченный хвост вызовов инструментов, текущие фактически известные результаты проверок, частичный расход с источником, исход чекпоинта и его SHA/ссылка при наличии. Объём ограничен; полного лога в брифе нет.
2. Диагностика различает факты и гипотезы. Последний вызов теста не доказывает зависший тест. Если завершение инструмента неизвестно, писать «завершение не зарегистрировано». Нельзя утверждать, что проверки прошли по одному тексту команды, либо что работа не прогрессировала только из-за отсутствия stdout.
3. При следующем разрешённом запуске той же роли передавать эту диагностику первым релевантным контекстом продолжения с указанием запуска и чекпоинта. Проверить актуальность SHA; более поздние изменения и ответы Оператора явно имеют приоритет. Роль должна проверить сохранённый результат и определить оставшуюся работу; пульт не генерирует за неё PLAN.
4. После нормального завершения старый таймаут не подаётся как причина нового шага. Диагностика другой роли/задачи не попадает в бриф. Для истории без данных — явное отсутствие сведений.
5. Повторные таймауты одного шага видны в компактной сводке для Оператора с числом запусков и накопленными токенами по видам, длительностью и отдельно условным/CLI расходом. Для Codex доллары — условная оценка; не основание для вывода об экономии денег или лимита подписки. Сводка не разрешает перезапуск и не меняет состояние задачи.

## Направление приёмки
Фикстуры: таймаут после полезной работы, незавершённый инструмент, готовый чекпоинт, ошибка чекпоинта, новые изменения после него, несколько таймаутов, другая роль, нормальное завершение после таймаута, старый запуск без данных. Проверить точность фактов, ограничение контекста и отсутствие повторного списания. Следующий бриф сохраняет SPEC, актуальные ANSWER и причины возврата, ограничения защищённых путей и проверки.

## Зоны и границы
Зоны: orchestrator/runner.py, orchestrator/agent_log.py, orchestrator/brief.py, orchestrator/checkpoint.py (только получение фактов результата), orchestrator/store.py (при необходимости), tests/. SPEC уточняет минимальные зоны и формат хранения.
Только чтение: таймауты и лимиты конфигурации, FSM/гейты, провайдеры, защищённые пути, настройки ролей.
Не входит: автоматический перезапуск, повышение таймаута/бюджета, новый стоп-кран, изменение правил checkpoint, удаление тестов, изменение полномочий, диагностика git после конца модели, ограничения вспомогательных агентов.

## Рамка и порядок
Не зависит от внедрения usage-аудита: использует уже доступные факты и честно называет ограничения. Бюджет и набор моделей требуют решения Оператора после калибровки. Черновик до cmd_new; задача не создана и не запущена.
