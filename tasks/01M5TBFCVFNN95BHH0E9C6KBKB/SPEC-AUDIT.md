## Пути обхода гейтов
- **AC-22 с журналом без `target`.** Исполнитель пишет журнал записи под `E…`
  без `target` (например, общим `store.journal` без проекта). AC-22 проходит, а
  в выборках по проекту отказ записи не виден. Это пункт 1 вердикта.
- Прежние пути (смена механики `_unsent`, слабые данные restore, молчаливая
  неудача записи) закрыты формулировками решения №2.

## Вердикт
**concerns.** Решения Оператора №1 и №2 внесены полностью, факты о коде
подтвердились, все шесть пунктов прошлого аудита сняты. Осталось одно мелкое
отклонение, Оператор может решить его на гейте без возврата:

1. **Требование 11 (SPEC.md:33) и AC-22 (SPEC.md:64), неудача записи ссылки.**
   Не названы `target` журнальной строки и код выхода команды. У отказа
   отправки `target` = проект эпика задан (требование 12, AC-21), а у неудачи
   записи — нет. Тест Э1 AC-30 держит `target` записей эпика только в своих
   сценариях. Слово «предупреждение» не говорит, что код выхода 0, хотя
   требование называет изменение БД успешным. Мутации «журнал без `target`» и
   «ненулевой код выхода» AC-22 не ловит. Дефолт: дописать в AC-22 «строкой с
   `task_id` — id эпика `E…` и `target` — проект эпика; команда завершается
   кодом 0».

К сведению, не отклонение: шаг кода может начаться до мержа Э2а (сейчас
`verifying`), а колонка `tasks.start_after` есть только в его ветке.
