# SPEC: Планка внешнего проекта внутри workdir: конфиг, импорты и фикстуры проекта

## Контекст
Планка задачи выкладывается в `<рабочая копия>/tasks/<id>/acceptance_tests/`
(`orchestrator/acceptance.py::materialize_from_branch`, `::materialize_files`,
`::plank_in_code_copy`), то есть вне `workdir` проекта (у sled `workdir: backend`).
Прогоны `pytest-own` (`acceptance.run`, `::collect`, `::run_plank`) идут из
`workdir`, но pytest определяет корень и конфиг по путям аргументов и находит
конфиг артели, а не `backend/pyproject.toml` (`pythonpath`, `addopts`, маркеры).
Фикстуры `backend/tests/conftest.py` планке не видны. Поэтому приёмочный тест
не может импортировать код проекта и пользоваться его фикстурами: на первой
задаче sled (01M55SKHZ293CCAK0N7T4H7ZMR) автор тестов обходил это через `ast`
и запуск pytest подпроцессом. Нужно, чтобы планка внешнего проекта была
обычным тестом проекта. Долгоживущие файлы (`long_lived_dir: backend/tests`)
лежат внутри `workdir`, у них этой проблемы нет.

### Выбранный способ и обоснование (ТЗ, п.2)
На время каждого прогона планки файлы планки выкладываются во временный
подкаталог `long_lived_dir` рабочей копии кода задачи (путь `long_lived_dir`
отсчитывается от корня рабочей копии, например `backend/tests/<каталог выкладки>/`).
Прогон идёт по этим путям, после прогона выкладка убирается.

Почему не `--rootdir`/`-c <конфиг проекта>`/`--confcutdir`: эти флаги меняют
корень и ini-конфиг, а фикстуры `conftest.py` pytest применяет только к
тестам внутри каталога этого `conftest.py`. Файл планки вне `backend/tests/` не
видит фикстур `backend/tests/conftest.py` при любом `rootdir`. Требование ТЗ
о фикстурах (п.1) при таком подходе не выполнено бы. Выкладка внутрь
`long_lived_dir` даёт ровно положение долгоживущего теста: тот же корень,
конфиг, `pythonpath`, `conftest.py` и тот же импорт кода проекта.

Все прогоны планки проходят через три функции `orchestrator/acceptance.py`:
`run` (вход в `verifying`, автогейт приёмки, подтяжка main), `collect`
(сухой сбор на выходе из `tests_writing` и в `amend-tests`) и `run_plank`
(`plank-run`). Вызывающие из `advance_gates/`, `pull.py`, `fsm_advance.py`
и `amend.py` получают поведение без собственной правки.

## Требования
1. У проекта с профилем тестов `pytest-own` и непустым `workdir` каждый
   прогон планки задачи исполняет её файлы из временной выкладки внутри
   `long_lived_dir` рабочей копии кода задачи. Это касается всех прогонов:
   сухого сбора (`acceptance.collect`), прогона (`acceptance.run`: вход в
   `verifying`, автогейт приёмки, подтяжка main), `plank-run`
   (`acceptance.run_plank`), сбора и прогона `amend-tests`. В выкладке pytest
   видит корень и конфиг проекта (`<workdir>/pyproject.toml` или иной конфиг
   проекта) и фикстуры `conftest.py` на пути `long_lived_dir`. Импорт кода
   проекта работает так же, как у долгоживущих тестов `long_lived_dir`.
2. Выкладка содержит ровно те файлы, которые даёт штатная выкладка планки
   (`materialize_from_branch` / `materialize_files`, вместе с помощником
   `_pult.py`), с тем же содержимым. Источник планки (ссылка документов задачи,
   ревизия, sha перечня) и гейты, которые от него зависят (фиксация, лок
   `acceptance_tests/`, перечень долгоживущих файлов), не меняются.
3. Каждый прогон из требования 1 по возврату убирает выкладку вместе с
   кешем байткода из рабочей копии. Это касается любого исхода: зелёного,
   красного, превышения `config.ACCEPTANCE_TIMEOUT_SEC`, отказа запуска и
   исключения внутри прогона. Вывод `git status --porcelain` рабочей копии
   после прогона совпадает с выводом до прогона.
4. Файлы выкладки не попадают в коммит и в дифф задачи. Это касается и
   остатка выкладки, который пережил принудительное прерывание процесса
   прогона, когда `finally` не исполнился. Такой остаток git рабочей копии
   не видит как неотслеживаемые файлы, поэтому `git add -A` чекпоинта
   (`orchestrator/checkpoint.py`) его не подбирает. Остаток убирает
   `acceptance.drop_from_code_copy`, который пульт зовёт на старте каждого
   шага (`orchestrator/runner.py`).
5. Выкладка не меняет исходов гейта зон и проверки «долгоживущие тесты не
   тронуты». Набор изменённых путей ветки и рабочей копии, который видят эти
   проверки, после прогона тот же, что без выкладки.
6. Узлы планки в выводе прогона, сводке гейта и журнале узнаются как планка
   задачи: путь каждого узла содержит id задачи и имя файла планки.
   Строка-заголовок прогона «планка: <каталог>, cwd: …» по-прежнему
   называет каталог планки `tasks/<id>/acceptance_tests`.
7. У артели (нет `workdir`, раннер `pult-pytest`) прогоны планки — `run`,
   `collect`, `run_plank` и их вызовы из `plank-run` и `amend-tests` — дают
   прежние исходы и прежние тексты: строку-заголовок, текст «планка не
   содержит ни одного теста», тексты таймаута и пути узлов. Это поведение
   закрепляют тесты, написанные и зелёные на коде до правки.
8. Тесты задачи детерминированы и не ходят в сеть. Они идут на учебном
   внешнем проекте с `workdir: backend`, своим `backend/pyproject.toml` (с
   `pythonpath`) и `backend/tests/conftest.py` с фикстурой. Приёмочный тест
   задачи этого проекта импортирует модуль проекта и использует фикстуру
   из его `conftest.py`.

## Критерии приёмки
AC-1. На учебном внешнем проекте (`workdir: backend`, `backend/pyproject.toml`
с `pythonpath`, `backend/tests/conftest.py` с фикстурой) приёмочный тест
задачи импортирует модуль проекта и использует фикстуру из `conftest.py`
проекта. Сухой сбор `acceptance.collect` на нём возвращает «собралось», а
прогон `acceptance.run` возвращает «зелёно».

AC-2. На том же учебном проекте `plank-run` (`acceptance.run_plank` с профилем
проекта) по тому же приёмочному тесту завершается с кодом выхода pytest `0`.

AC-3. На том же учебном проекте сухой сбор и прогон `amend-tests` по тому же
приёмочному тесту проходят без отказа сбора и без красного прогона.

AC-4. После прогона планки на учебном внешнем проекте в рабочей копии нет
файлов и каталогов выкладки, а `git status --porcelain` совпадает с выводом
до прогона. Это проверяется для каждого исхода: зелёного, красного и прогона,
прерванного превышением `config.ACCEPTANCE_TIMEOUT_SEC`.

AC-5. Остаток выкладки внутри `long_lived_dir`, который пережил обрыв прогона
без уборки, не виден `git status --porcelain` рабочей копии и не попадает в
коммит после `git add -A`. Вызов `acceptance.drop_from_code_copy` для задачи
убирает его с диска.

AC-6. Дифф ветки задачи после прогона планки на учебном внешнем проекте не
содержит файлов планки и путей выкладки.

AC-7. В выводе прогона планки на учебном внешнем проекте путь узла теста
планки содержит id задачи и имя файла планки. Строка-заголовок
«планка: …» называет каталог `tasks/<id>/acceptance_tests`.

AC-8. У артели (`pult-pytest`, без `workdir`) `acceptance.run`,
`acceptance.collect` и `acceptance.run_plank` на зелёной, красной, пустой
планке и при таймауте дают те же исходы и тексты (строка-заголовок, текст
«планка не содержит ни одного теста», текст таймаута, пути узлов
`tasks/<id>/acceptance_tests/…`), что и до правки. Тесты этого критерия
зелёные на коде main до правки.

## Оценка объёма и деление
Сработал сигнал `budget_usd` ≥ $30. Бюджет $35 — рамка Оператора из ТЗ, ниже
калибровочного класса «до 10 критериев, до 4 файлов» (~$40). Зон 4, критериев 8.

Обоснование монолита: здесь меняется одна механика — место исполнения файлов
планки внутри трёх функций прогона `orchestrator/acceptance.py` вместе с
уборкой и невидимостью для git. Части по границам зон самостоятельной ценности
не дают. `plank_run.py` и `amend.py` только зовут эти функции. Тесты `tests/`
без механики красные, а механика без тестов не проверяет требования ТЗ.
Отдельно можно было бы вынести только фиксацию поведения артели
(требование 7), но ТЗ требует её «до правки» в той же задаче, и отдельная
подзадача из одних тестов удвоила бы шаги analyst/review без выигрыша.
