# SPEC: Планка внешнего проекта внутри workdir: конфиг, импорты и фикстуры проекта

## Контекст
Планка задачи выкладывается в `<рабочая копия>/tasks/<id>/acceptance_tests/`
(`orchestrator/acceptance.py::materialize_from_branch`, `::materialize_files`,
`::plank_in_code_copy`), то есть вне `workdir` проекта (у sled `workdir: backend`).
Прогоны `pytest-own` (`acceptance.run`, `::collect`, `::run_plank`) идут из
`workdir`, но pytest определяет корень и конфиг по путям аргументов и находит
конфиг артели, а не `backend/pyproject.toml` (`pythonpath`, `addopts`, маркеры).
Фикстуры `backend/tests/conftest.py` планке не видны. Поэтому приёмочный тест
не может импортировать код проекта и пользоваться его фикстурами: на первой
задаче sled (01M55SKHZ293CCAK0N7T4H7ZMR) автор тестов обходил это через `ast`
и запуск pytest подпроцессом. Нужно, чтобы планка внешнего проекта была
обычным тестом проекта. Долгоживущие файлы (`long_lived_dir: backend/tests`)
лежат внутри `workdir`, у них этой проблемы нет.

### Выбранный способ и обоснование (ТЗ, п.2; способ принят Оператором на гейте SPEC 18.10)
На время каждого прогона планки её файлы выкладываются во временный каталог
внутри `long_lived_dir` рабочей копии кода задачи:

`<рабочая копия>/<long_lived_dir>/.artel-plank/<id>/acceptance_tests/`

Путь отсчитывается от корня рабочей копии кода, как и сам `long_lived_dir`
профиля (`targets.yaml:85`; ANSWER-1, вопрос 2). У sled это
`backend/tests/.artel-plank/<id>/acceptance_tests/`. `<id>` — id задачи в том
виде, в каком он стоит в `tasks/<id>/`. Сегмент `acceptance_tests` и id задачи
остаются в argv pytest. По этой подстроке существующие тесты узнают вызов
планки (`tests/test_01m52eehsrd93wmphwb5vjyrkd_profile_callers.py:269`, `:716`).
Прогон идёт по путям выкладки, после прогона выкладка убирается.

Почему не `--rootdir`/`-c <конфиг проекта>`/`--confcutdir`: эти флаги меняют
корень и ini-конфиг, а фикстуры `conftest.py` pytest применяет только к
тестам внутри каталога этого `conftest.py`. Файл планки вне `backend/tests/` не
видит фикстур `backend/tests/conftest.py` при любом `rootdir`, и требование ТЗ
о фикстурах (п.1) не выполнялось бы. Выкладка внутрь `long_lived_dir` даёт
ровно положение долгоживущего теста: тот же корень, конфиг, `pythonpath`,
`conftest.py` (в том числе вложенных подкаталогов) и тот же импорт кода
проекта.

Невидимость выкладки для git нужна потому, что чекпоинт коммитит рабочую
копию через `git add -A` (`orchestrator/checkpoint.py:1796`) и подбирает любой
неотслеживаемый файл, а гейт зон и фильтр чекпоинта сочли бы файл выкладки
посторонним изменением ветки. Признак долгоживущего файла
(`guard.is_long_lived_test_path`, `scripts/guard.py:3238-3250`) здесь ни при
чём: файл в подкаталоге выкладки под него не подпадает.

## Требования
1. Требования 1–9 действуют для проекта с профилем тестов `pytest-own`,
   непустым `workdir` и `long_lived_dir`, лежащим внутри `workdir`. Каждый
   прогон планки задачи такого проекта исполняет её файлы из выкладки
   `<рабочая копия>/<long_lived_dir>/.artel-plank/<id>/acceptance_tests/`.
   Это касается всех прогонов: сухого сбора (`acceptance.collect`), прогона
   (`acceptance.run`: вход в `verifying`, автогейт приёмки, подтяжка main),
   `plank-run` (`acceptance.run_plank`), а также сбора и прогона
   `amend-tests` в обеих его ветвях — с перечнем долгоживущих
   (`orchestrator/amend.py:535-565`) и без него (`orchestrator/amend.py:723-728`).
   В выкладке pytest видит корень и конфиг проекта (`<workdir>/pyproject.toml`
   или иной конфиг проекта) и фикстуры `conftest.py` на пути `long_lived_dir`.
   Импорт кода проекта работает так же, как у долгоживущих тестов.
2. Содержимое выкладки:
   - у сбора, прогона и `plank-run` — ровно те файлы, которые даёт штатная
     выкладка планки (`materialize_from_branch` / `materialize_files`, вместе
     с помощником `_pult.py`), с тем же содержимым;
   - у `amend-tests` — файлы `tasks/<id>/acceptance_tests/` рабочей копии на
     диске на момент вызова (правка Оператора) вместе с помощником, который
     выкладывает `plank_helper_laid_out` (`orchestrator/amend.py:684`, `:725`),
     с тем же содержимым.

   Источник планки (ссылка документов задачи, ревизия, sha перечня) и гейты,
   которые от него зависят (фиксация, лок `acceptance_tests/`, перечень
   долгоживущих файлов), не меняются.
3. `plank-run` отображает аргумент на путь выкладки. `plank-run <id>` гонит
   одной целью каталог выкладки. `plank-run <id> <файл>` гонит
   `<каталог выкладки>/<файл>`. `plank-run <id> <файл>::<узел>` гонит
   `<каталог выкладки>/<файл>::<узел>`. Чем `run_plank` узнаёт путь выкладки
   (параметр с id задачи или готовый путь от `plank_run.py`), решает
   разработчик.
4. `plank-run <id> <путь долгоживущего файла>[::<узел>]` внешнего проекта
   выкладку не создаёт. Ни одна цель pytest такого вызова не лежит ни под
   `<рабочая копия>/tasks/<id>/acceptance_tests`, ни под
   `<рабочая копия>/<long_lived_dir>/.artel-plank/<id>/`. Это
   требование-замена проверки
   `tests/test_01m56g23zqdhv2bkevwwc22r96_plank_run_long_lived.py:345-348`
   (решение Оператора 1 на гейте SPEC).
5. Выкладка существует только на время прогона планки. Каждый прогон из
   требования 1 по возврату убирает её вместе с кешем байткода из рабочей
   копии при любом исходе: зелёном, красном, превышении
   `config.ACCEPTANCE_TIMEOUT_SEC`, отказе запуска и исключении внутри
   прогона. Уборка стоит в `finally`. Вывод `git status --porcelain
   --untracked-files=all` рабочей копии после прогона совпадает с выводом до
   прогона.
6. Каталог выкладки исключён из git записью в общем файле исключений клона,
   а не файлом `.gitignore` в дереве. Рабочая копия задачи — `git worktree`
   клона, поэтому файл берётся по `git rev-parse --git-path info/exclude`
   рабочей копии (это `<клон>/.git/info/exclude`, общий для всех worktree
   проекта). Запись — один общий шаблон каталога выкладки (например
   `**/.artel-plank/`), без записей на id задачи. Запись дописывается
   идемпотентно: если она уже есть, второй раз не пишется, и файл от
   повторных прогонов не растёт. Запись делается ДО записи файлов выкладки
   на диск.
   Поэтому во время прогона планки выкладку не видят ни `_pult.changed_paths()`
   (`ls-files --others --exclude-standard`, `orchestrator/plank_helper.py:118-125`),
   ни гейт зон (`git status --untracked-files=all`,
   `orchestrator/advance_gates/zones.py:150-158`). Остаток выкладки,
   переживший принудительное прерывание процесса (когда `finally` не
   исполнился), git тоже не видит как неотслеживаемые файлы, и `git add -A`
   чекпоинта (`orchestrator/checkpoint.py:1796`) его не подбирает. Файлы
   выкладки не попадают ни в коммит, ни в дифф задачи. Остаток с диска
   убирает `acceptance.drop_from_code_copy`, который пульт зовёт на старте
   каждого шага (`orchestrator/runner.py:1218`).
7. Полный прогон набора внешнего проекта с целью `long_lived_dir`
   (`orchestrator/acceptance.py:1454`; ключ итога — `:1951`) не собирает
   файлы выкладки, в том числе её остатка, независимо от настройки
   `norecursedirs` проекта. Итог полного прогона, сохранённый под sha
   `clean_tree_sha` (`orchestrator/acceptance.py:1798-1810`), не содержит
   узлов планки. Аргумент pytest, которым полный прогон исключает выкладку
   (например `--ignore=<long_lived_dir>/.artel-plank`), не содержит подстроки

   полного прогона (`tests/test_01m52eehsrd93wmphwb5vjyrkd_profile_callers.py:269`),
   и такая подстрока покраснила бы его вне мандата.
8. Выкладка и её остаток не меняют исходов проверок ветки:
   - гейт зон и проверка «долгоживущие тесты не тронуты» во время прогона

## Критерии приёмки
AC-1. На учебном внешнем проекте (`workdir: backend`, `backend/pyproject.toml`
с `pythonpath`, `backend/tests/conftest.py` с фикстурой) приёмочный тест
задачи импортирует модуль проекта и использует фикстуру из `conftest.py`
проекта. Сухой сбор `acceptance.collect` на нём возвращает «собралось», а
прогон `acceptance.run` возвращает «зелёно».

AC-2. На том же учебном проекте `plank-run <id>`, `plank-run <id> <файл>` и
`plank-run <id> <файл>::<узел>` по тому же приёмочному тесту завершаются с
кодом выхода pytest `0`. Каждый вызов запускает pytest ровно раз, и его
единственная цель (разрешённая от рабочего каталога вызова) — соответственно
`<рабочая копия>/<long_lived_dir>/.artel-plank/<id>/acceptance_tests`, тот же
путь с `/<файл>` и тот же путь с `/<файл>::<узел>`.

AC-3. На учебном внешнем проекте `plank-run <id> <путь долгоживущего
файла>` и `plank-run <id> <путь долгоживущего файла>::<узел>` не создают

## Оценка объёма и деление
Сработали сигналы: `budget_usd` ≥ $30 и число критериев приёмки ≥ 10
(критериев 13, зон 4). Бюджет $35 — рамка Оператора из ТЗ («Рамка: $35»),
потолок задан Оператором; калибровочный класс «до 15 критериев, до 7 файлов»
дал бы ~$45. Если двух итераций ревью не хватит, поднять потолок — решение
Оператора командой `budget`.

Обоснование монолита (материал для решения Оператора): меняется одна
механика — место исполнения файлов планки внутри трёх функций прогона
`orchestrator/acceptance.py` вместе с уборкой, невидимостью для git и
изоляцией полного набора. Без невидимости и изоляции перенос выкладки внутрь
`long_lived_dir` сразу ломает полный прогон и чекпоинт, то есть промежуточное
состояние неработоспособно. `plank_run.py` и `amend.py` только зовут эти
функции и передают путь. Правка теста по мандату (требование 12) краснеет
без механики, а механика без неё краснит этот тест. Отдельно можно было бы
вынести только фиксацию поведения артели (требование 11), но ТЗ требует её
«до правки» в той же задаче, и подзадача из одних тестов удвоила бы шаги
analyst/review без выигрыша.
