# SPEC: advance по зафиксированному состоянию (симметрия с approve)

## Контекст
Инцидент T032: ревьюер обновил REVIEW.md (approved), но не закоммитил.
`advance` пропустил переход `review -> acceptance` по грязному
артефакту, а последующий `approve` на гейте `acceptance` отказал по
проверке чистоты (T021) — задача застряла между двумя проверками,
которые расходятся в требовании к состоянию рабочей копии; чинил
инцидент Оператор коммитом чужого вердикта вручную. `approve` уже
сверяет зафиксированное состояние артефактов (`fixation`/`confirm_fixation`,
T021); `advance` такой сверки не делает вовсе — асимметрия.

## Требования

1. `advance` выполняет переход только по зафиксированному (чистому)
   состоянию артефактов задачи — та же сверка чистоты, что использует
   `approve` (T021). Артефакт-условие перехода изменён, но не
   закоммичен — переход отказывает с именованной причиной вида
   «REVIEW.md не закоммичен — роль обязана коммитить артефакты (скил
   conventions-core); закоммить и повтори advance». Это отказ, не
   эскалация: подсказка, что незакоммиченный артефакт штатно
   докоммичивается, а не блокер, требующий решения Оператора.
2. Причина отказа пишется в журнал задачи и видна в `artel.py log <id>`.
3. Поведение `advance` для чистого состояния артефактов (как было до
   этой задачи) не меняется ни для одного из переходов. Существующие
   тесты `advance` не ослабляются. Новое поведение покрыто тестами:
   переход по грязному артефакту для каждого из трёх типов условия —
   SPEC ready, PLAN ready, REVIEW вердикт.
4. Место, где отказ по грязной копии невозможен без поломки
   легитимного флоу (переход, где грязь артефакта в процессе — штатное
   состояние) — не реализуется в обход: называется в PLAN разделе
   «Риски» с обоснованием, а не тихо пропускается и не тихо
   реализуется через силу.
5. Строка беклога «Подметалка minor» (P3) в `docs/roadmap.md`
   лишается предложения про асимметрию advance/approve (пункт «Из
   T032: ... асимметрию закрыть требованием чистоты и в advance») —
   этой задачей закрывается тот же пункт, который она удаляет, по
   образцу того, как T032 удалила свою строку беклога.

## Критерии приёмки

AC-1. Переход `spec_writing -> spec_gate` (условие: `SPEC.md`
status: ready) отказывает и не меняет состояние задачи, если рабочая
копия артефактов задачи не чиста на момент `advance`.

AC-2. Переход `in_dev -> review` (условие: `PLAN.md` status: ready
или approved) отказывает и не меняет состояние задачи по тому же
условию грязной копии.

AC-3. Переход из состояния `review` (условие: вердикт `REVIEW.md`) —
в `acceptance`, `in_dev` или `escalated`, смотря по вердикту — отказывает
и не меняет состояние задачи по тому же условию грязной копии.

AC-4. Причина отказа в каждом из AC-1..AC-3 называет конкретный
артефакт перехода (`SPEC.md` / `PLAN.md` / `REVIEW.md` соответственно)
и формулировку вида «<файл> не закоммичен — роль обязана коммитить
артефакты (скил conventions-core); закоммить и повтори advance».

AC-5. Отказ по AC-1..AC-3 — не эскалация: `state` задачи остаётся тем
же, что и до вызова `advance`; после коммита артефакта повторный
`advance` продвигает задачу штатно (как и до этой задачи для чистой
копии).

AC-6. Причина отказа по AC-1..AC-3 записана в журнал задачи и видна в
выводе `artel.py log <id>`.

AC-7. Существующее поведение `advance` для чистого состояния артефактов
не изменилось ни для одного из трёх переходов (AC-1..AC-3) — ни для
одной из веток внутри перехода `review` (approved/changes_requested/escalate).

AC-8. Тесты покрывают отказ по грязной копии для каждого из трёх типов
условия отдельно (SPEC ready, PLAN ready, REVIEW вердикт) и не
ослабляют существующие тесты `advance`.

AC-9. В `docs/roadmap.md` из строки беклога «Подметалка minor» (P3)
удалено предложение об асимметрии advance/approve («Из T032: ...
асимметрию закрыть требованием чистоты и в advance»); остальной текст
той же строки (прочие пункты «Из T0xx: ...») не изменён.

## Не входит

- Переход `tests_writing -> in_dev`: его условие — трассируемость AC
  по acceptance_tests/ (T023), не статус `ready` артефакта; ТЗ называет
  ровно три типа условия (SPEC ready, PLAN ready, REVIEW вердикт) — этот
  переход вне их числа и не трогается.
- Отказ `guard_refuses` (структура артефакта) — уже существующая
  проверка, не предмет задачи; сверка чистоты копии — проверка
  дополнительная и отдельная от неё.
- Поведение `approve`/`confirm_fixation` (T021) — не меняется, служит
  образцом сверки чистоты для `advance`, но сама не предмет задачи.
- Место (если найдётся), где грязь артефакта в процессе перехода
  легитимна: по требованию 4 — не реализуется отказом и не
  игнорируется молча, а называется в PLAN «Риски» с обоснованием.
- Прочие пункты строки беклога «Подметалка minor», кроме удаляемого
  по AC-9, — не трогаются.
