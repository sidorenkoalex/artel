# PLAN: advance по зафиксированному состоянию (симметрия с approve)

## Подход

`orchestrator/fsm.py` `cmd_advance` получает сверку чистоты рабочей
копии на тех же трёх переходах, что названы в SPEC (`spec_writing ->
spec_gate`, `in_dev -> review`, `review -> *`) — той же функцией,
которой уже пользуется `approve`: `fixation.read(task_id, target)`
(`orchestrator/fixation.py`). `read()`, не `fix()` — advance не имеет
права коммитить чужой WIP как побочный эффект проверки (тот же принцип,
что и у `confirm_fixation`, REVIEW.md T021 замечание 1 итерации 2).

Общий приём — новый частный хелпер `_dirty_refuses(conn, task_id,
target, artifact_name)` рядом с существующим `guard_refuses`: та же
форма (журналирует и печатает причину, возвращает `bool` — «переход
отменён»), тот же порядок вызова в каждом из трёх мест — сразу после
того, как статус артефакта признан условием перехода («ready» /
вердикт из `REVIEW_VERDICTS`), и **до** `guard_refuses` и до любых
побочных эффектов перехода (`budget.apply_spec_budget`,
`store.update_task(reviewed_iter=...)`, лок `acceptance_tests/`) —
отказ по грязной копии не должен ничего успеть посчитать или сдвинуть
раньше себя.

`fixation.read()` уже умеет вырожденный случай «сверять не с чем»
(`current` пустой — git не ответил или коммитов ещё нет): хелпер в этом
случае пропускает переход дальше, тем же способом, что и
`confirm_fixation` — поведение старых (не-git) песочниц `advance` не
меняется (see «Влияние на систему»).

Сообщение отказа — литерал по AC-4, не собирается из частей:
`f"{artifact_name} не закоммичен — роль обязана коммитить артефакты "
f"(скил conventions-core); закоммить и повтори advance"`; печатается
и журналируется одной и той же строкой, чтобы `artel.py log` (AC-6)
видел то же, что и Оператор в выводе `advance`.

Область применения хелпера — **только догфуд**
(`target == config.DEFAULT_TARGET`), не любой `target`: обоснование
и разбор альтернатив — «Риски» ниже (требование 4 SPEC).

`docs/roadmap.md`: из строки «Подметалка minor» убирается ровно
предложение «Из T032: ... асимметрию закрыть требованием чистоты и
в advance» (AC-9) — остальной текст строки не трогается.

## Влияние на систему

Меняется только `cmd_advance` (три места) — ни `confirm_fixation`,
ни `fixation.py`, ни поведение `approve` не трогаются (SPEC, «Не
входит»). Существующие тесты `advance`
(`tests/test_advance_guard.py`, `tests/test_git_fixation.py`) гоняют
`cmd_advance` в песочнице с заглушкой `gitcmd.git = lambda *a: None`
(`test_advance_guard.py`) — в ней `fixation.read()` всегда отдаёт
пустой `current` (git не отвечает), новый хелпер немедленно
пропускает переход дальше, поведение этих тестов не меняется без
правки самих тестов (AC-7/AC-8 требуют именно этого). Новый порядок
вызова (`_dirty_refuses` до `guard_refuses`) не меняет поведение guard
— он вызывается тем же образом, если чистота подтверждена.

Гейты/лимиты/тесты не ослабляются: новая проверка — дополнительное
условие перехода, не замена существующих (guard, лок
`acceptance_tests/`, лимит итераций ревью). Откат — правка тем же
диффом в обратную сторону (удалить хелпер и три вызова); данные (БД,
журнал) не мигрируют этой задачей.

## Риски

**Требование 4 SPEC — место, где грязь артефакта в процессе легитимна:
внешний target.** Для `target != config.DEFAULT_TARGET` артефактный
git-репозиторий `.artel/projects/<target>/` коммитит **сам
оркестратор целиком** на каждом переходе (`fixation._fix_external`,
вызывается из `store.set_state` → `fix()` — уже ПОСЛЕ решения
перейти). Роль внешнего target не коммитит артефакты сама (в отличие
от догфуда, где это прямая обязанность роли по скилу
conventions-core, на неё и ссылается сообщение отказа AC-4) — значит
непосредственно перед `advance` артефактный репозиторий закономерно
не закоммичен: это не забытый коммит роли, а нормальное
предшествующее состояние перед автоматической фиксацией того же
перехода. Наивная сверка чистоты для внешнего target отказывала бы
там **всегда**, блокируя `advance` навсегда для любой задачи не-
догфуд target — поломка легитимного флоу, которую требование 4
явно запрещает вносить втихую.

Отдельно: до A7 (ADR-0003 3д, «особый случай») сам гейтинг `advance`
(чтение статуса `PLAN.md`/`SPEC.md`/`REVIEW.md`) читает артефакты из
`tasks/<id>/` **пульта** (`config.TASKS`), не из артефактного репо
target'а — а `fixation.read()` для внешнего target сверяет именно
репо target'а (`.artel/projects/<target>/`). Это два разных дерева;
сверка чистоты одного как условие перехода, гейтящегося по другому,
не имела бы даже согласованного смысла до унификации хранения
артефактов (A7).

**Решение**: `_dirty_refuses` действует только при `target ==
config.DEFAULT_TARGET` — эксплицитная проверка в коде, а не молчаливое
совпадение по факту пустого `current` (для внешнего target `current`
почти всегда непустой — есть sha прошлой фиксации, значит без явной
проверки `target` хелпер отказывал бы). Покрыто отдельным юнит-тестом
(шаг 3) — не входит в залоченные `acceptance_tests/T033`, которые
проверяют только догфуд-сценарий.
