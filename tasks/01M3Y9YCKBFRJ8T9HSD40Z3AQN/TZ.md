# ТЗ: Набор моделей отдельной задачи — `new --set` с допуском по ADR-0019 п.5

Источник: решение Оператора 02.10.2026 (сессия при Операторе): боевой
набор пульта остаётся прежним (`claude-opus-5-5` во всех ролях), а
отдельную задачу Оператор может явно пустить на другом наборе, например
с ролями на Codex, если у набора есть допуск. ADR-0019 п.5 («вести
настоящие задачи можно только на наборе, имеющем допуск»; числа допуска
от 30.09; «первые три настоящие задачи набора идут под гейтами SPEC и
мержа с полной проверкой Оператора»; правила приостановки). Строка
копилки 02.10 о снятии раздела `role_models:` (связка codex).

Факты (пин 99b954f5):
- Модель роли разрешается одной функцией `orchestrator/models.py::
  resolve_role(role, catalog, local)`: запись `role_models:` локального
  слоя `.artel/models.yaml`, иначе ярус роли из `tiers:`. Контекста
  задачи у разрешения нет: набор един для всего пульта и для всех
  задач сразу.
- Вызовы без задачи: `runner.py:425` и `runner.py:1035` (запуск шага
  роли), `spend.py:442` (стоимость шага по тарифу модели),
  `stack.py:194`, `stack.py:532` (проверки окружения и `doctor`).
- Именованные наборы ролей есть только у канарейки: раздел
  `canary_sets:` локального слоя (вне git), `models.load_canary_sets`,
  флаг `canary --set`; у `new`/`run`/`auto` выбора набора нет.
- Вход Codex роли: `CODEX_HOME` — курируемый `.codex/` роли
  (`stack.py:315`); ограничение «профиль занят» относится только к
  отдельному профилю канарейки (`canary.py`).
- Прогоны канарейки по парам Codex лежат в `canary_runs` БД пульта
  (поля `set_name`, `title`, `verdict`, `review_iterations`,
  `escalations`, `models_summary`).

Требуется:
1. Запись допуска и наборов в репозитории — новый отслеживаемый git
   файл `model_sets.yaml` в корне (решение Оператора 02.10: не
   `canary_sets:` локального слоя и не `models.yaml`, который защищён).
   Файл несёт именованные наборы задач и допущенные пары; формат
   выбирает SPEC. Файл добавляется в `config.PROTECTED_PATHS` (роли его
   не правят) и в `notes.DOC_COMMIT_CONFIG_PATHS` (Оператор правит его
   `doc-commit` и командой требования 2). Допущенные пары «роль — модель
   каталога»: запись пары несёт роль, модель, дату, основание (ссылки
   на прогоны канарейки или документ замера), состояние (`допущена` /
   `приостановлена`) и счётчик настоящих задач. Набор допущен, если
   допущена каждая его пара, отличная от боевой.
2. Команда Оператора выдачи и снятия допуска пары (имя выбирает SPEC,
   например `admit <роль> <модель> --basis <текст>` и `admit --revoke`).
   Команда печатает сводку прогонов канарейки этой пары из
   `canary_runs` против чисел ADR-0019 п.5 (не меньше трёх чистых
   прогонов не меньше чем на двух шаблонах, из них хотя бы один
   среднего класса; для analyst — прогон на шаблоне с неясностью ТЗ с
   правильным исходом). Недобор — отказ с перечнем недостающего;
   выдать допуск вопреки недобору нельзя. Запись в `model_sets.yaml` —
   изолированным коммитом тем же механизмом, что `doc-commit` (окно
   тишины, удержание).
3. Набор задачи. `new <title> <тз> --set <набор>` заводит задачу с
   набором: набор — отображение «роль -> модель каталога» для части
   ролей; роль без записи в наборе идёт на боевой модели. Наборы
   описываются в `model_sets.yaml` (требование 1); в строку задачи в БД
   пишется имя набора и его состав на момент `new`, чтобы правка файла
   не меняла модели задачи в работе молча.
   Недопущенная или приостановленная пара — отказ `new` до заведения
   задачи с именем пары и причиной. Набор записывается в строку задачи в
   БД (миграция схемы — тем же приёмом, что прежние миграции
   `store.py`) и действует до закрытия задачи.
4. Разрешение модели роли учитывает задачу: шаг роли задачи с набором
   идёт на модели набора; провайдер, CLI, вход и тариф — от модели
   набора тем же порядком fail-closed, что у `role_models:` (каталог,
   `experimental`). Стоимость шага (`spend.py`) считается по тарифу
   модели, на которой шаг фактически шёл. Задачи без набора ведутся
   ровно как сейчас; поведение боевого набора не меняется.
5. Видимость: `status` показывает набор задачи рядом с бюджетом; запись
   журнала старта шага называет роль, модель и источник (набор задачи,
   `role_models:` или ярус); подсказки `approve` на гейтах SPEC, приёмки
   и мержа задачи с набором называют набор.
6. Пробный период набора (ADR-0019 п.5): пока у пары засчитано меньше
   трёх настоящих задач, задача с этой парой не проходит приёмку
   автогейтом — приёмка становится ручным гейтом Оператора с перечнем
   причин («пробная задача набора <имя>, N из 3»). Засчитывается задача,
   дошедшая до `done`.
7. Приостановка (ADR-0019 п.5): два возврата ревью подряд по вине роли
   допущенной пары (в одной задаче или в двух задачах подряд) или отказ
   автогейта по вине этой роли переводят пару в `приостановлена` и
   шлют алерт Оператору. Новые задачи с этой парой — отказ `new`
   (требование 3). Задача, у которой пара приостановлена посреди
   работы, ведётся дальше на боевой модели этой роли с записью в
   журнал; молчаливого продолжения на приостановленной паре нет. Как
   различать «вину роли» и «вину пульта» при отказе автогейта — SPEC,
   с опорой на существующую классификацию (`failure_classification.py`).
8. Смена набора у задачи в работе — только отдельной командой
   Оператора (например `set-models <id> <набор>|--default`) с записью
   в журнал; разрешена в состояниях, где роль не исполняется.
9. Тесты в `tests/`:
   - задача с набором: шаг роли из набора идёт на модели набора, роль
     без записи — на боевой; соседняя задача без набора — на боевой
     («Ловит мутацию: разрешение модели без учёта задачи»);
   - стоимость шага задачи с набором — по тарифу модели набора;
   - `new --set` с недопущенной и с приостановленной парой — отказ без
     заведения задачи (нет строки в БД и ветки);
   - пробная задача не проходит приёмку автогейтом, четвёртая — проходит;
   - два возврата ревью подряд приостанавливают пару, задача продолжает
     на боевой модели;
   - команда допуска при недоборе прогонов — отказ с перечнем.
   Существующие тесты разрешения моделей, канарейки и автогейта не
   удаляются и не ослабляются.
10. Документация: раздел в `docs/stack.md` (наборы задачи, допуск,
    пробный период, приостановка) и пункт в `docs/operator-session.md`
    о запуске задачи на наборе.
11. Проверка на деле — после мержа, вне задачи (сессия ассистента):
    допуск пары `developer -> gpt-6-sol` по истории канарейки, затем
    простая задача из бэклога с `--set` и проход её до мержа.
