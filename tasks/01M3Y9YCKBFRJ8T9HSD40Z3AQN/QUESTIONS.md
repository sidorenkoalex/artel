# QUESTIONS: Набор моделей отдельной задачи — `new --set` с допуском по ADR-0019 п.5

## Вопросы

Контекст сверки (пин рабочей копии задачи): таблица `canary_runs`
(`orchestrator/store.py:1077-1083`) несёт `title`, `review_iterations`,
`escalations`, `expected_escalation`, `actual_escalation`,
`marker_mismatch`, `verdict`, `set_name`, `models_summary`,
`acceptance_route`, `autogate_refusal`. Класса шаблона (быстрый/средний/
трудный) и числа повторов developer в ней нет, и в коде пульта класса
шаблона нет вовсе (`grep` по `orchestrator/canary.py`, `config.py`);
пул шаблонов — `~/.artel-canary`, который ролям читать нельзя.
Требование 2 ТЗ при этом запрещает выдавать допуск вопреки недобору,
то есть проверка обязана решаться по данным. Вопросы 1–2 — об этом.

1. **Откуда команда допуска узнаёт класс шаблона («хотя бы один среднего
   класса») и какой шаблон — «с неясностью ТЗ» для analyst?** — варианты:
   A) раздел шаблонов в `model_sets.yaml`: имя шаблона -> класс
   (`быстрый`/`средний`/`трудный`) и признак «неясность ТЗ»; заполняет
   Оператор тем же `doc-commit`; шаблон без записи в разделе не
   засчитывается в «средний» и в «неясность ТЗ», команда называет его в
   перечне недостающего; B) класс указывается флагом команды допуска
   (например `--medium <шаблон>`) под ответственность Оператора, без
   записи в файле; C) «неясность ТЗ» определяется по самой строке
   прогона (`expected_escalation` задан, `actual_escalation=1`,
   `marker_mismatch=0`), класс — по варианту A — дефолт: **A для класса +
   C для «неясности ТЗ»**: класс проверяем по данным в git, а правильный
   исход эскалации прогон уже записывает сам.

2. **Что считается «чистым прогоном» по строке `canary_runs`, если
   повторов developer таблица не хранит, а `orchestrator/canary.py`
   менять нельзя (только чтение)?** — варианты: A) чистый = `verdict`
   `green` + `review_iterations = 0` + нет эскалаций, кроме ожидаемой
   (`escalations = 0` либо `expected_escalation` задан, `actual_escalation
   = 1`, `marker_mismatch = 0`) + `autogate_refusal` пуст или отнесён к
   пульту/пулу (правило вины — то же, что SPEC зададит по требованию 7);
   условие «без повтора developer» не проверяется и сводка команды прямо
   пишет «повторы developer: нет данных»; B) то же, плюс расширить зоны на
   `orchestrator/canary.py` и завести колонку повторов developer (новые
   прогоны — с данными, старые — не засчитываются); C) то же, что A, но
   прогон без данных о повторах не засчитывается вовсе (тогда допуск по
   нынешней истории невозможен, и проверка на деле, требование 11 ТЗ,
   не пройдёт) — дефолт: **A** — единственный вариант, при котором
   допуск по существующей истории (требование 11) остаётся достижим без
   правки защищённого от задачи `canary.py`.

3. **Рамка $50 против объёма: делить задачу или вести монолитом?**
   Сигналы «большого объёма» срабатывают заведомо: зон-файлов 16
   (порог 5), критериев приёмки по девяти пунктам тестов ТЗ и восьми
   требованиям — больше 10 (порог 10); калибровка
   (`config.BUDGET_CALIBRATION_TABLE`) для «больше 15 критериев или 8+
   файлов зоны» даёт ~$85, вдвое выше рамки. — варианты: A) нарезка на
   три подзадачи: (1) `model_sets.yaml` + команда допуска (`config.py`,
   `notes.py`, `models.py`, `artel.py`, `docs/stack.md`); (2) набор
   задачи: `new --set`, миграция строки задачи, разрешение модели и
   стоимость с учётом задачи, видимость, `set-models` (`catalog.py`,
   `store.py`, `schema.py`, `models.py`, `runner.py`, `spend.py`,
   `stack.py`, `artel.py`, `fsm.py`, `docs/operator-session.md`) — после
   части 1; (3) пробный период и приостановка (`fsm_autogate.py`,
   `store.py`, `fsm.py`, `models.py`) — после части 2; рамка каждой
   ~$40–45, сумма ~$130; B) монолит с потолком $85 (выше рамки ТЗ);
   C) монолит в рамке $50 с риском исчерпания потолка посреди задачи —
   дефолт: **A** — ни один вариант не укладывается в $50, а нарезка
   даёт три самостоятельно мержимых шага вместо одного рискованного.

4. **Где живут счётчик настоящих задач пары и её состояние
   «приостановлена», и кто их пишет?** Требование 1 кладёт оба поля в
   запись пары `model_sets.yaml`; требования 6–7 меняют их автоматически
   (задача дошла до `done`; два возврата ревью подряд). Переход в `done`
   делает `orchestrator/fsm_merge_gate.py:848` (в «Только чтение»)
   внутри окна merge, возврат ревью — `orchestrator/fsm_advance.py:201`
   (вне зон); общая точка в зонах — `store.set_state`. — варианты:
   A) оба поля в файле; пульт пишет их сам изолированным коммитом тем же
   механизмом, что `doc-commit`, — после закрытия окна merge (отложенно,
   как неотправленные заметки) и при приостановке; зоны не расширяются,
   точка перехвата — на усмотрение разработчика в пределах зон;
   B) в файле только решение Оператора (роль, модель, дата, основание,
   состояние, выставленное командой); счётчик считается из БД (задачи в
   `done`, чей записанный состав набора содержит пару), автоматическая
   приостановка пишется в БД и перекрывает файл до разбора Оператором;
   C) вариант A, но зоны расширяются на `orchestrator/fsm_advance.py` —
   дефолт: **A** — буквально то, что требует ТЗ («запись пары несёт …
   состояние … и счётчик», «переводят пару в `приостановлена`»), без
   расширения зон.

5. **ADR-0019 п.5 строже ТЗ — по какому правилу работать?** ADR:
   набор допущен, если допущена каждая пара **и** набор целиком прошёл
   зелёный прогон трудного класса и одну пробную задачу; «первые три
   настоящие задачи **набора**». ТЗ: «набор допущен, если допущена
   каждая его пара, отличная от боевой»; пробный период — «пока у
   **пары** засчитано меньше трёх». — варианты: A) буквально ТЗ (только
   пары, счёт по паре); B) ТЗ + условие «прогон трудного класса набором
   целиком» на `new --set` (требует класса шаблонов, см. вопрос 1) —
   дефолт: **A** — ТЗ — более позднее и прямое решение Оператора, а
   `docs/adr/` задаче менять нельзя.

6. **Снятие допуска (`--revoke`) у пары, на которой идёт задача в
   работе, — как приостановка или иначе?** ТЗ описывает поведение
   задачи в работе только для приостановки (требование 7). — варианты:
   A) так же: роль этой задачи дальше идёт на боевой модели с записью в
   журнал; B) задача останавливается до решения Оператора (`set-models`);
   C) задача доводится на снятой паре — дефолт: **A** — то же правило
   «молчаливого продолжения на недопущенной паре нет».

7. **«Состояния, где роль не исполняется» для `set-models`
   (требование 8)** — варианты: A) любое состояние, кроме `done`/
   `killed`, при отсутствии живого lease шага (роль сейчас не
   запущена); B) только гейты и `escalated` (`spec_gate`, `acceptance`,
   `merge_gate`, `escalated`, а также приостановленная задача);
   C) только состояния вне `config.STATE_ROLE` и вне `spec_writing` —
   дефолт: **B** — перечень проверяем без гонки с запуском шага, и смена
   набора попадает на точку решения Оператора.
