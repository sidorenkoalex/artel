# SPEC: Набор моделей отдельной задачи — `new --set` с допуском по ADR-0019 п.5

## Контекст
Модель роли разрешается одной функцией `orchestrator/models.py::resolve_role`
без контекста задачи: набор моделей един для всего пульта и всех задач
(`runner.py:425`, `runner.py:1035`, `spend.py:442`, `stack.py:194`,
`stack.py:532`). Именованные наборы есть только у канарейки
(`canary_sets:` локального слоя, `canary --set`). Решение Оператора
02.10.2026: боевой набор остаётся прежним (`claude-opus-5-5` во всех
ролях), а отдельную задачу Оператор может явно пустить на другом наборе
(например, с ролями на Codex), если у набора есть допуск по ADR-0019 п.5.
Ответ Оператора ANSWER-1 уточнил ТЗ: условия допуска и пробный период —
строго по ADR-0019 п.5 (ТЗ в этой части слабее ADR и уступает ему),
в `model_sets.yaml` — только решения Оператора, автоматическое состояние
(счётчик пробных задач, автоматическая приостановка) — в БД, задача
делится на три подзадачи.

## Требования
1. **Файл наборов и допусков.** Новый отслеживаемый git файл
   `model_sets.yaml` в корне репозитория (формат выбирает SPEC подзадачи 1)
   несёт: именованные наборы задач (набор — отображение «роль -> модель
   каталога» для части ролей); допущенные пары «роль — модель каталога»
   с полями роль, модель, дата, основание (ссылки на прогоны канарейки
   или документ замера), состояние, выставленное командой допуска
   (`допущена` / `приостановлена`); раздел шаблонов канарейки: имя
   шаблона -> класс (`быстрый` / `средний` / `трудный`) (ANSWER-1 п.1).
   Файл несёт ТОЛЬКО решения Оператора: пульт его сам не коммитит
   (ANSWER-1 п.4). Файл входит в `config.PROTECTED_PATHS` и в
   `notes.DOC_COMMIT_CONFIG_PATHS`.
2. **Допуск набора** (ANSWER-1 п.5, ADR-0019 п.5): набор допущен, если
   допущена каждая его пара, отличная от боевой, И набор целиком прошёл
   зелёный прогон канарейки на шаблоне трудного класса (класс — по
   разделу шаблонов `model_sets.yaml`).
3. **Команда допуска пары** (имя выбирает SPEC подзадачи 1, например
   `admit <роль> <модель> --basis <текст>` и `admit --revoke`): печатает
   сводку прогонов канарейки этой пары из `canary_runs` против чисел
   ADR-0019 п.5 — не меньше трёх чистых прогонов не меньше чем на двух
   шаблонах, из них хотя бы один среднего класса; для analyst — ещё
   прогон на шаблоне с неясностью ТЗ с правильным исходом. Недобор —
   отказ с перечнем недостающего; выдать допуск вопреки недобору нельзя.
   Запись в `model_sets.yaml` — изолированным коммитом тем же механизмом,
   что `doc-commit` (окно тишины, удержание).
   - Шаблон без записи класса в разделе шаблонов не засчитывается ни в
     «средний», ни в «трудный» и называется в перечне недостающего
     (ANSWER-1 п.1).
   - «Неясность ТЗ с правильным исходом» для analyst — строка прогона с
     заданным `expected_escalation`, `actual_escalation = 1`,
     `marker_mismatch = 0` (ANSWER-1 п.1).
   - Чистый прогон — строка `canary_runs` с `verdict = green`,
     `review_iterations = 0`, без эскалаций, кроме ожидаемой
     (`escalations = 0` либо `expected_escalation` задан,
     `actual_escalation = 1`, `marker_mismatch = 0`), `autogate_refusal`
     пуст или отнесён к пульту/пулу по правилу вины (требование 9).
     Условие «без повтора developer» не проверяется; сводка команды прямо
     пишет «повторы developer: нет данных» (ANSWER-1 п.2).
4. **Набор задачи.** `new <title> <тз> --set <набор>` заводит задачу с
   набором из `model_sets.yaml`; роль без записи в наборе идёт на боевой
   модели. В строку задачи в БД пишется имя набора и его состав на момент
   `new` (миграция схемы — тем же приёмом, что прежние миграции
   `store.py`); набор действует до закрытия задачи, правка файла модели
   задачи в работе молча не меняет. Недопущенный набор (недопущенная или
   приостановленная пара либо нет зелёного прогона трудного класса
   набором целиком) — отказ `new` до заведения задачи с именем пары или
   набора и причиной.
5. **Разрешение модели с учётом задачи.** Шаг роли задачи с набором идёт
   на модели набора; провайдер, CLI, вход и тариф — от модели набора тем
   же порядком fail-closed, что у `role_models:` (каталог,
   `experimental`). Стоимость шага (`spend.py`) — по тарифу модели, на
   которой шаг фактически шёл. Задачи без набора ведутся ровно как
   сейчас; поведение боевого набора не меняется.
6. **Видимость.** `status` показывает набор задачи рядом с бюджетом;
   запись журнала старта шага называет роль, модель и источник (набор
   задачи, `role_models:` или ярус); подсказки `approve` на гейтах SPEC,
   приёмки и мержа задачи с набором называют набор.
7. **Смена набора у задачи в работе** — только командой Оператора
   (например `set-models <id> <набор>|--default`) с записью в журнал;
   разрешена только в состояниях `spec_gate`, `acceptance`, `merge_gate`,
   `escalated` и у приостановленной (`pause`) задачи; в остальных
   состояниях — отказ с перечнем допустимых (ANSWER-1 п.7).
8. **Пробный период набора** (ADR-0019 п.5, ANSWER-1 п.5): первые три
   настоящие задачи НАБОРА не проходят приёмку автогейтом — приёмка
   становится ручным гейтом Оператора с причиной «пробная задача набора
   <имя>, N из 3». Счётчик считается из БД: задачи в `done`, чей
   записанный состав набора совпадает с набором (ANSWER-1 п.4).
9. **Правило вины отказа автогейта** (требование 7 ТЗ, опора —
   существующие исходы `fsm_autogate._autogate_conditions` и классы
   `failure_classification.py`): отказ относится к роли, если его
   причина — критерии `manual`/`skip` в планке (test_author), красный
   полный набор `tests/` или непройденный критерий `ci` (developer);
   к пульту/пулу — ошибка источника планки или пустой каталог
   приёмочных тестов, незаведённый worktree, таймаут прогона или
   отсутствие `tests/` в worktree, исчерпанный бюджет, а также отказ
   попытки роли, классифицированный `failure_classification.py`
   (системные классы, обрыв потока, session limit, «модель не
   поддерживается CLI»). Причина вне обоих перечней — «не установлена»:
   прогон канарейки с ней не чистый (ADR-0019 п.5: «если причина
   установлена»), к роли для приостановки она не относится.
10. **Приостановка** (ADR-0019 п.5, ANSWER-1 п.4–5): два возврата ревью
    подряд по вине роли пары набора (в одной задаче или в двух задачах
    подряд) или отказ автогейта по вине роли пары (требование 9) в
    настоящей задаче переводят пару в «приостановлена» и шлют алерт
    Оператору. Автоматическая приостановка пишется в БД, перекрывает
    состояние пары в `model_sets.yaml` до разбора Оператором и снимается
    командой Оператора с записью в журнал. Новые задачи с этой парой —
    отказ `new` (требование 4).
11. **Задача в работе на недопущенной паре.** Задача, у пары которой
    допуск снят командой допуска (ANSWER-1 п.6) или пара приостановлена
    посреди работы, ведётся дальше на боевой модели этой роли с записью в
    журнал; молчаливого продолжения на снятой или приостановленной паре
    нет.
12. **Документация:** раздел в `docs/stack.md` (наборы задачи, допуск,
    пробный период, приостановка) и пункт в `docs/operator-session.md` о
    запуске задачи на наборе.

## Критерии приёмки
AC-1. Задача с набором: шаг роли из набора идёт на модели набора, роль
без записи в наборе — на боевой модели; соседняя задача без набора — на
боевой модели («Ловит мутацию: разрешение модели без учёта задачи»).

AC-2. Стоимость шага задачи с набором считается по тарифу модели набора.

AC-3. `new --set` с недопущенной парой и с приостановленной парой —
отказ без заведения задачи: нет строки задачи в БД и нет ветки задачи.

AC-4. `new --set` с набором, все пары которого допущены, но без зелёного
прогона трудного класса набором целиком, — отказ без заведения задачи с
причиной.

AC-5. Пробная задача набора (засчитано меньше трёх задач набора в
`done`) не проходит приёмку автогейтом — причина «пробная задача набора
<имя>, N из 3»; четвёртая задача набора проходит приёмку автогейтом.

AC-6. Два возврата ревью подряд по вине роли пары приостанавливают пару
(запись в БД, алерт Оператору); задача продолжает на боевой модели этой
роли с записью в журнал.

AC-7. Отказ автогейта по вине роли пары приостанавливает пару; отказ
автогейта по причине, отнесённой к пульту/пулу, пару не приостанавливает.

AC-8. Команда допуска при недоборе прогонов — отказ с перечнем
недостающего, `model_sets.yaml` не меняется; сводка содержит строку
«повторы developer: нет данных».

AC-9. Команда допуска не засчитывает шаблон без записи класса в разделе
шаблонов `model_sets.yaml` в «средний» и называет его в перечне
недостающего.

AC-10. Команда допуска для analyst без прогона с заданным
`expected_escalation`, `actual_escalation = 1`, `marker_mismatch = 0` —
отказ с этим пунктом в перечне недостающего.

AC-11. Прогон с `autogate_refusal`, отнесённым к пульту/пулу, засчитывается
чистым; прогон с отказом по вине роли или с неустановленной причиной —
не засчитывается.

AC-12. `set-models` в состоянии вне `spec_gate`, `acceptance`,
`merge_gate`, `escalated` у неприостановленной задачи — отказ с перечнем
допустимых состояний; в допустимом состоянии — смена набора с записью в
журнал.

AC-13. Правка состава набора в `model_sets.yaml` после `new` не меняет
модель роли задачи в работе: шаг идёт по составу, записанному в строку
задачи.

AC-14. `status` показывает набор задачи рядом с бюджетом; запись журнала
старта шага называет роль, модель и источник (набор задачи,
`role_models:` или ярус).

## Оценка объёма и деление
Сработавшие сигналы: число затрагиваемых модулей/файлов (в зонах 12
модулей `orchestrator/*.py`, порог 5), число критериев приёмки (14, порог
10). Калибровка (`config.BUDGET_CALIBRATION_TABLE`) для «больше 15
критериев или 8+ файлов зоны» даёт ~$85 — выше рамки ТЗ $50.

Прогноз диффа: 90 КиБ

Решение — **нарезка на три подзадачи** (ANSWER-1 п.3), в порядке
зависимостей:

1. **Файл наборов и команда допуска** — механика, на которую опираются
   остальные части: формат `model_sets.yaml`, проверка допуска пары и
   набора (включая условие трудного класса набором целиком), команда
   допуска. Условие трудного класса отнесено к части 1, потому что оно —
   часть определения «набор допущен», которое и проверяется данными
   `canary_runs` и разделом шаблонов этой же части; часть 2 пользуется
   готовым ответом «допущен ли набор», а часть 3 его не меняет.
   Самостоятельно мержима: добавляет файл и команду Оператора, ни одна
   задача на наборе ещё не может быть заведена — поведение пульта для
   задач не меняется.
2. **Набор задачи** — `new --set`, миграция строки задачи, разрешение
   модели и стоимость с учётом задачи, видимость, `set-models`, переход
   на боевую модель при снятом допуске. Требование ANSWER-1 п.3 «часть 2
   до мержа части 3 не позволяет вести задачу с набором без пробного
   периода» решено так: часть 2 делает приёмку ручным гейтом Оператора
   для ЛЮБОЙ задачи с набором (причина называет набор). Самостоятельно
   мержима: задачи без набора не меняются, задачи с набором идут под
   ручной приёмкой — строже, чем требует ADR, не слабее.
3. **Пробный период и приостановка** — заменяет безусловную ручную
   приёмку части 2 счётчиком «N из 3» из БД, вводит автоматическую
   приостановку пары в БД по правилу вины, команду её снятия и переход
   задачи в работе на боевую модель. Самостоятельно мержима: опирается
   только на смерженные части 1–2.

2. Шаг роли задачи с набором идёт на модели набора; провайдер, CLI, вход

4. Видимость: `status` показывает набор задачи рядом с бюджетом; запись

   `role_models:` или ярус); подсказки `approve` на гейтах SPEC, приёмки

5. Смена набора у задачи в работе — только командой Оператора (например

   отказ с перечнем допустимых. Новый набор проходит ту же проверку
   допуска, что и `new --set`.
6. Пока не смержена часть 3 (пробный период), задача с набором не
   проходит приёмку автогейтом: приёмка любой задачи с набором — ручной
   гейт Оператора, причина называет набор (решение ANSWER-1 п.3 родителя:
   ни одна задача с набором не идёт без ручной приёмки).
7. Документация: в `docs/stack.md` — набор задачи и разрешение модели

8. Тесты в `tests/`: задача с набором — шаг роли из набора на модели
   набора, роль без записи — на боевой, соседняя задача без набора — на
   боевой («Ловит мутацию: разрешение модели без учёта задачи»);
   стоимость шага задачи с набором — по тарифу модели набора; `new --set`
   с недопущенной и с приостановленной парой — отказ без заведения задачи
   (нет строки в БД и ветки); правка состава набора в файле после `new`
   не меняет модель задачи в работе; снятый допуск — шаг на боевой модели
   с записью в журнал; `set-models` вне допустимых состояний — отказ с
   перечнем; задача с набором не проходит приёмку автогейтом.
   Существующие тесты разрешения моделей, канарейки и автогейта не
   удаляются и не ослабляются.

Не входит: счётчик пробных задач и автоматическая приостановка (часть 3);
