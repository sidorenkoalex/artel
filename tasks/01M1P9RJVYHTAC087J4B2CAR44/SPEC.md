# SPEC: Инкрементальный дифф ревью после A7: база из кодовой ветки (регрессия №10)

## Контекст
С переводом пульта на единый (post-A7) механизм фиксации для ЛЮБОГО
target запись журнала «sha зафиксирован» (`store.record_fixation` ->
`fixation.fix`) несёт голову артефактного/фиксационного репозитория
`.artel/projects/<target>` (например `00e32aaf…`, коммит «fixation:
<target>»), а не голову кодовой ветки задачи. `orchestrator/review.py::
previous_verdict_sha` (T029) берёт эту запись базой инкрементального
diff для `review_package`; `git diff <base>...<ветка>` в репозитории
пульта этот объект не находит («Invalid symmetric difference
expression»), пакет ревьювера уходит с пометкой «diff не собран», «строк
diff 0» — воспроизведено у всех задач волны с итерации 2 (журналы
01M1NBWPKN…, 01M1NWCM3T…, 01M1NBWTSX…). Ревьювер вынужден восстанавливать
diff вручную через git — лишние токены и риск ревью не того diff.

## Требования
1. База инкрементального diff (`review.review_package`, итерация > 1) —
   sha кодовой ветки задачи на момент вынесения предыдущего вердикта, а
   не фиксационный sha артефактного/фиксационного репозитория target'а
   (`.artel/projects/<target>`). Источник этого sha — запись журнала
   фиксации «sha зафиксирован» (`store.record_fixation`): для НЕ-
   default target она уже несёт поле с sha кодовой ветки, для target по
   умолчанию (`config.DEFAULT_TARGET`) — нет; это поле заводится/
   выравнивается одинаково для ЛЮБОГО target. История кодовой ветки
   (git log/reflog) отдельным обходом не поднимается — источник sha
   остаётся существующий журнал фиксации.
2. Базу определить нельзя (первая итерация — в журнале ещё нет двух
   записей «sha зафиксирован»; либо sha кодовой ветки в записи не
   распознан) — diff остаётся полным, к `config.MAIN_BRANCH`, как
   сейчас; пометка пакета называет причину отсутствия базы.
3. Пометка пакета «diff не собран» на итерации > 1 поднимает Оператору
   алерт `kind=warning`, а не остаётся тихой строкой журнала; алерт
   авто-подтверждается, когда причина исчезает (диф следующего сбора
   пакета той же задачи собран успешно).
4. Существующие тесты, завязанные на `review.review_package`/
   `review.previous_verdict_sha` (T029, `tests/test_review_package.py`,
   `tests/test_review_freshness.py`), остаются зелёными без ослабления.

## Критерии приёмки
AC-1. `review.previous_verdict_sha` возвращает sha кодовой ветки задачи
(не фиксационный sha артефактного репозитория target'а) для итерации
> 1, когда в журнале есть ≥2 записи «sha зафиксирован» с распознанным
sha кодовой ветки.

AC-2. У задачи target по умолчанию (`config.DEFAULT_TARGET`) на
итерации 2 diff, собранный `review.review_package` от этой базы,
непустой (между итерациями были правки кода) — пакет не несёт пометку
«diff не собран».

AC-3. У задачи НЕ-default target на итерации 2 diff, собранный
`review.review_package` от этой же базы, непустой — пакет не несёт
пометку «diff не собран».

AC-4. Фиксационный sha артефактного/фиксационного репозитория target'а
(значение поля `sha=` записи «sha зафиксирован») ни при каких условиях
не используется как база инкрементального diff.

AC-5. Базу определить нельзя (итерация 1, либо sha кодовой ветки в
записи журнала не распознан) — `review.review_package` строит diff к
`config.MAIN_BRANCH` целиком, а текст пакета называет причину
отсутствия базы.

AC-6. Пометка «diff не собран» на итерации > 1 поднимает Оператору
алерт `kind=warning`; алерт авто-подтверждается, когда diff следующего
сбора пакета той же задачи собран успешно.

AC-7. Существующие тесты `tests/test_review_package.py`,
`tests/test_review_freshness.py` и другие тесты, завязанные на
`review_package`/`previous_verdict_sha`, остаются зелёными без
ослабления или удаления.

## Не входит
- Смена формата ревью-пакета: порядок частей, состав компонентов
  (`review.review_package`).
- Лимиты ёмкости пакета (`context_package.discipline`, деление на
  части).
