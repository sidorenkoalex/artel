# ТЗ: детерминированный тест AC-6 части 2 и ловля тестов, падающих от случайного зерна

Порядок: после 01M484RNV3QBDY3B0M16J916ZP

Источник: 06.10, прогон базы suite-run части 3 этапа 3 (01M484RNV3, зерно
344013504). Тест
`tests/test_01m45fk56dwmnbrka1vwm12h19_draft_mr.py::DraftMrHighlightTest::test_ac6_highlight_lists_no_paths_and_omits_artel_only_paths`
падает ложно примерно в 5,6% прогонов (1 из 18), при исправном коде.
Решение Оператора 06.10: завести задачу.

Факты (пин 4d6f5b77, сверка кода 06.10):
- Тест выбирает путь пульта случайно: `artel_only_path` (~103) —
  `self.rng.choice(config.PROTECTED_PATHS)`, 18 путей; зерно —
  `random.randrange(1 << 30)` (~59), печатается строкой «зерно: …».
- Проверка `assertNotIn(artel_path, text)` (~157) ищет путь подстрокой во
  всём тексте комментариев, а текст комментария всегда содержит
  «no_paths проекта <имя> в targets.yaml» (`orchestrator/github_adapter.py`
  ~100). При выборе `targets.yaml` тест красный, хотя путь пульта в
  перечне комментария не назван.
- Случайное зерно задают 88 файлов `tests/`: тот же класс ложных падений
  (случайный выбор из короткого конечного перечня) может сидеть и в
  других тестах.
- Рубеж `in_dev -> verifying` гоняет планку и долгоживущие файлы задачи
  одним прогоном: `orchestrator/advance_gates/acceptance.py::
  _acceptance_run_body` (~218, вызов `acceptance.run(..., extra=long_lived)`
  ~326); `orchestrator/acceptance.py::run` (~207).
- На выходе из `tests_writing` тесты по построению красные (кода ещё нет),
  поэтому многократный прогон там бессмыслен.

Требуется:
1. Тест AC-6 части 2 детерминирован и не слабее прежнего: путь пульта
   перебирается по всему `config.PROTECTED_PATHS` (`subTest` на каждый),
   а не выбирается случайно; отсутствие пути пульта проверяется по
   перечню путей, которые назвал комментарий, а не подстрокой всего
   текста. Мутации из его строки «Ловит мутацию» по-прежнему ловятся.
   Это смена утверждений существующего долгоживущего теста: разработчик
   эскалирует точный список (файл, класс, метод, было → стало), мандат
   выдаёт Оператор.
2. Рубеж `in_dev -> verifying`: долгоживущие файлы задачи, которые несут
   случайное зерно, после зелёного прогона гоняются ещё N раз (константа
   config, решение SPEC). Разный исход между прогонами — отказ перехода
   с именем теста и зёрнами красных прогонов («тест зависит от
   случайного зерна»). Признак «несёт случайное зерно» — решение SPEC
   (например, импорт `random` в файле). Время рубежа — оценка в SPEC.
3. Разовый замер: все долгоживущие файлы `tests/test_01m*_*.py` в `main`
   прогнать K раз (решение SPEC); найденные зависимые от зерна тесты —
   перечнем в PLAN (файл, метод, зерно красного прогона). Чинится только
   тест требования 1; остальные — строками для Оператора.
4. Тесты в `tests/` с заявками «Ловит мутацию»: рубеж отказывает на
   долгоживущем файле, красном при одном из зёрен, и пропускает
   детерминированный; файл без случайного зерна повторно не гоняется.
   Существующие тесты не ослабляются.
