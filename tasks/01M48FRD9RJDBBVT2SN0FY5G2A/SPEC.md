# SPEC: детерминированный тест AC-6 части 2 и ловля тестов, зависимых от случайного зерна

## Контекст
Долгоживущий тест
`tests/test_01m45fk56dwmnbrka1vwm12h19_draft_mr.py::DraftMrHighlightTest::test_ac6_highlight_lists_no_paths_and_omits_artel_only_paths`
падает ложно примерно в 5,6% прогонов при исправном коде (прогон базы
suite-run 06.10, зерно 344013504). Причина: путь пульта выбирается
случайно (`artel_only_path`, `self.rng.choice(config.PROTECTED_PATHS)`,
18 записей; зерно — `random.randrange(1 << 30)`), а `assertNotIn(artel_path,
text)` ищет его подстрокой во всём тексте комментариев, который всегда
содержит «no_paths проекта <имя> в targets.yaml»
(`orchestrator/github_adapter.py::_protected_paths_source`). При выборе
`targets.yaml` тест красный, хотя путь в перечне комментария не назван.
Тот же класс ложных падений (случайный выбор из короткого конечного
перечня) может сидеть и в других долгоживущих тестах: все долгоживущие
файлы `tests/test_01m*_*.py` в `main` импортируют `random` и печатают
строку «зерно: …». Рубеж `in_dev -> verifying` сейчас гоняет планку и
долгоживущие файлы задачи один раз
(`orchestrator/advance_gates/acceptance.py::_acceptance_run_body`, вызов
`acceptance.run(..., extra=long_lived)`), поэтому такой тест проходит рубеж
незамеченным в ~94% случаев.

## Требования

1. Тест AC-6 части 2
   (`tests/test_01m45fk56dwmnbrka1vwm12h19_draft_mr.py::DraftMrHighlightTest::test_ac6_highlight_lists_no_paths_and_omits_artel_only_paths`)
   детерминирован и не слабее прежнего:
   - путь пульта не выбирается случайно — метод перебирает ВСЕ записи
     `config.PROTECTED_PATHS`, по `subTest` на каждую запись, в каждом из
     сценариев метода, где путь пульта прежде выбирался случайно (дифф с
     путями `no_paths` проекта и дифф только с путём пульта);
   - отсутствие пути пульта проверяется по перечню путей, которые назвал
     комментарий черновика, а не подстрокой всего текста комментариев;
   - мутации из строки «Ловит мутацию» метода по-прежнему ловятся:
     (а) подсветка сверяет дифф с `config.PROTECTED_PATHS` для любого
     проекта; (б) перечень берётся из записи артели, а не проекта задачи.
   Это смена утверждений существующего долгоживущего теста: по ТЗ
   разработчик эскалирует точный список (файл, класс, метод, было →
   стало), мандат на смену выдаёт Оператор; без мандата метод не меняется.
2. Рубеж `in_dev -> verifying`: после ЗЕЛЁНОГО прогона планки и
   долгоживущих файлов задачи долгоживущие файлы задачи, несущие случайное
   зерно, прогоняются ещё N раз.
   - N — именованная константа `orchestrator/config.py`, значение 10;
     число повторов читается из неё в момент рубежа.
   - Признак «файл несёт случайное зерно»: файл импортирует модуль
     `random` (`import random` или `from random import …` в любом месте
     файла). Файл без такого импорта повторно не гоняется.
   - Красный хотя бы один из N повторов (разный исход между прогонами) —
     отказ перехода. Текст отказа (журнал задачи и вывод `advance`) несёт
     слова «тест зависит от случайного зерна», имя каждого красневшего
     теста (узел pytest: файл, класс, метод) и зёрна всех красных повторов
     этого теста. Зерно красного повтора — значение, напечатанное тестом
     строкой «зерно: N» (так его печатают все долгоживущие файлы `main`);
     красный повтор без такой строки называется в отказе с пометкой, что
     зерно не напечатано.
   - Каждый повтор ограничен `config.ACCEPTANCE_TIMEOUT_SEC`; истёкший
     предел — красный повтор (отказ, не пропуск).
   - Красный первый прогон — прежний отказ «приёмочные тесты красные»,
     повторы не выполняются.
   - Оценка времени рубежа: один прогон долгоживущих файлов задачи — от
     ~5 до ~30 с (замер 06.10: два файла 01M45FK56D вместе — 30 с), повторы
     добавляют рубежу N × это время, т.е. ~1–5 мин при N = 10. Вероятность
     поймать тест, ложно красный в 1 из 18 прогонов, за один проход рубежа
     — ~44% (1 − (17/18)^10).
3. Разовый замер: все долгоживущие файлы `tests/test_01m*_*.py` в `main`
   (sha `main`, от которого отведена ветка задачи) прогнаны K = 10 раз.
   Итог — раздел PLAN.md: sha `main`, K, число файлов, суммарное время и
   перечень найденных зависимых от зерна тестов строками (файл, метод,
   зерно красного прогона) либо явная запись, что таких не найдено.
   Чинится только тест требования 1; остальные найденные — строками для
   Оператора в том же разделе PLAN.md, без правки в этой задаче.
4. Поведение требования 2 держат тесты в `tests/` с заявками «Ловит
   мутацию»: рубеж отказывает на долгоживущем файле, красном при одном из
   зёрен, пропускает детерминированный, файл без случайного зерна
   повторно не гоняет. Этим требованием служат долгоживущие приёмочные
   тесты автора тестов к AC-4..AC-7 (`tests/test_<id>_*.py`); повтор того
   же свойства отдельным тестом разработчика в `tests/` не требуется.
   Существующие тесты не ослабляются.

## Критерии приёмки

AC-1. Метод `DraftMrHighlightTest::test_ac6_highlight_lists_no_paths_and_omits_artel_only_paths` не выбирает путь пульта случайно: в каждом сценарии, где прежде звался `artel_only_path`, он проходит по `subTest` на каждую из записей `config.PROTECTED_PATHS` (на `main` — 18), и число подтестов метода равно числу записей перечня, умноженному на число таких сценариев.

AC-2. На исправном коде `orchestrator/github_adapter.py` метод AC-1 зелёный при любом зерне генератора `random`, включая подтест записи `targets.yaml`: отсутствие пути пульта сверяется с перечнем путей, названных комментарием черновика, а не подстрокой текста «no_paths проекта <имя> в targets.yaml».

AC-3. Метод AC-1 красный при каждой из двух мутаций своей строки «Ловит мутацию»: (а) подсветка черновика MR сверяет дифф с `config.PROTECTED_PATHS` для любого проекта; (б) перечень защищённых путей берётся из записи артели, а не проекта задачи.

AC-4. На переходе `in_dev -> verifying` долгоживущий файл задачи, импортирующий `random`, чей тест зелёный в первом прогоне и красный хотя бы в одном из повторов, отклоняет переход; отказ в журнале задачи и в выводе `advance` несёт слова «тест зависит от случайного зерна», имя красневшего теста (файл, класс, метод) и зерно («зерно: N», напечатанное тестом) каждого красного повтора.

AC-5. Долгоживущий файл задачи, импортирующий `random` и зелёный во всех прогонах, переход `in_dev -> verifying` этой проверкой не отклоняет; файл исполнен ровно 1 + N раз, где N — значение константы `orchestrator/config.py`, прочитанное в момент рубежа (подмена значения меняет число повторов).

AC-6. Долгоживущий файл задачи без импорта `random` на переходе `in_dev -> verifying` исполняется ровно один раз — повторов нет.

AC-7. Красный первый прогон планки и долгоживущих файлов отклоняет переход прежним отказом «приёмочные тесты красные»; повторы при этом не выполняются.

AC-8. PLAN.md задачи несёт раздел разового замера: sha `main`, K = 10, число прогнанных долгоживущих файлов `tests/test_01m*_*.py`, суммарное время и перечень найденных зависимых от зерна тестов строками «файл, метод, зерно красного прогона» либо явную запись, что таких не найдено.

## Не входит

  конечный перечень перебирать целиком, случайными — только данные
  большого пространства») — защищённый путь, вносит Оператор после мержа.
- Починка прочих зависимых от зерна тестов, найденных замером
  (требование 3), — отдельными задачами.
- Многократный прогон всего `tests/` на гейтах пульта.
- Повторные прогоны на выходе из `tests_writing` (тесты там красные по
  построению) и повторы файлов планки `acceptance_tests/` — повторяются
  только долгоживущие файлы задачи на `in_dev -> verifying`.
- Правка `orchestrator/github_adapter.py` и путей «Только чтение» ТЗ
  (`conftest.py`, `tests/test_invariants.py`, `docs/invariants.md`,
  `docs/adr/`, `docs/roadmap.md`, `docs/backlog.md`,
  `docs/operator-session.md`, `templates/`, `skills/`, `CLAUDE.md`,
