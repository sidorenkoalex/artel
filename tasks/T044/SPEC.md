# SPEC: Lease задачи: advisory-замок параллельных сессий

## Контекст
На пульте реально работают две и более сессии одновременно, и ничто не
мешает двум сессиям мутировать одну задачу: инцидент 26.08.2026 —
перезапись `tasks/T036/TZ.md` сессией с устаревшим срезом дерева. Нужен
именованный отказ вместо тихой гонки. Решение Оператора 27.08.2026
(кластер «параллельные сессии») — advisory-замок задачи в `state.db`,
который мутирующие команды CLI берут перед работой.

## Требования
1. Новая таблица `leases` в `state.db`: `task_id`, `session_id`, `pid`,
   `hostname`, `heartbeat_ts`.
2. Мутирующие команды CLI — `run`, `auto`, `advance`, `approve`, `reject`,
   `kill`, `budget` — перед выполнением своей работы над задачей берут
   lease этой задачи.
3. Lease задачи свободен ИЛИ его `session_id` совпадает с `session_id`
   текущего вызова → захват/продление: `heartbeat_ts` обновляется на
   текущий момент, `pid`/`hostname`/`session_id` актуализируются.
4. Lease занят другим `session_id`, и его `heartbeat_ts` не старше порога
   свежести (требование 6) → команда отказывает именованным отказом,
   называющим держателя (`session_id`), `hostname` и возраст heartbeat в
   секундах; задача и её состояние (`tasks.state`, `budget_usd` и прочие
   поля) остаются как до вызова.
5. Lease занят другим `session_id`, и его `heartbeat_ts` старше порога
   свежести → lease перехватывается вызывающей сессией
   (`session_id`/`pid`/`hostname`/`heartbeat_ts` перезаписываются на
   вызывающую сторону), факт перехвата отражается отдельной записью в
   журнале задачи.
6. Порог свежести heartbeat, отделяющий «живой» lease от «протухшего» в
   требованиях 4–5, — новая константа `orchestrator/config.py`, по
   аналогии с существующими порогами (`BACKUP_MAX_AGE_DAYS`,
   `DOCTOR_MIN_FREE_MB`).
7. `auto` продлевает heartbeat своего lease на каждом шаге цикла, а не
   только один раз при старте.
8. Успешное завершение мутирующей команды освобождает lease, взятый ею
   для этой задачи.
9. `session_id` вызова остаётся тем же на протяжении последовательных
   вызовов CLI одной логической сессии — иначе «свой lease» (требование
   3) никогда не совпадёт при раздельных вызовах, и замок будет блокировать
   штатную работу сессии саму на себя. Конкретный источник/способ
   получения `session_id` конкретным вызовом CLI в рамках этого
   требования не фиксируется.
10. Читающие команды `show`, `status`, `log` lease не берут, не проверяют
    и не изменяют.
11. `doctor` заводит алерт `kind=incident` на каждый lease, чей `pid`
    мёртв на текущем host — по аналогии с существующей проверкой сирот
    (`check_orphans`, `orchestrator/doctor.py`).
12. Lease — advisory-механизм CLI, не второй конечный автомат: истина
    состояния задачи остаётся в `tasks.state` (FSM, `orchestrator/fsm.py`);
    lease не участвует в переходах FSM и не подменяет guard-проверки.
13. Существующие гейты, лимиты, guard-проверки и инварианты не
    ослабляются и не изменяются этой задачей — таблица `leases` и её
    проверки добавляются поверх существующей механики.

## Критерии приёмки
AC-1. Вызов любой из команд `run`/`auto`/`advance`/`approve`/`reject`/
`kill`/`budget` по задаче, чей lease удерживается другой активной (её
`heartbeat_ts` не старше порога свежести) сессией, завершается именованным
отказом («задачу ведёт сессия `<session_id>` с host `<hostname>`, heartbeat
`<N>` сек назад» или эквивалентным по содержанию сообщением), и состояние
задачи (`tasks.state`, `budget_usd` и прочие поля) не меняется.

AC-2. Повторный вызов мутирующей команды из той же сессии (совпадающий
`session_id`) по задаче с её же lease выполняется без отказа по лизингу, а
`heartbeat_ts` lease продлевается на текущий момент.

AC-3. Lease, чей `heartbeat_ts` старше порога свежести (константа в
`orchestrator/config.py`), перехватывается вызывающей сессией:
`session_id`/`pid`/`hostname`/`heartbeat_ts` lease переписываются на неё, а
факт перехвата отражается отдельной записью в журнале задачи.

AC-4. После успешного завершения мутирующей команды lease задачи, взятый
этой командой, освобождён — следующий вызов мутирующей команды от другой
сессии по этой задаче не встречает живой lease.

AC-5. Команды `show`, `status` и `log` выполняются по задаче с чужим живым
lease без отказа и без изменения таблицы `leases`.

AC-6. `doctor` обнаруживает lease с мёртвым `pid` на локальном host и
заводит по нему алерт `kind=incident`.

AC-7. Полный существующий набор тестов остаётся зелёным после изменения.

## Не входит
- Изменение семантики переходов FSM (`tasks.state`) — lease не становится
  вторым источником истины состояния и не влияет на guard/advance/
  approve/reject-логику переходов, только на право сессии вызвать
  мутирующую команду.
- Принудительный обход живого чужого lease Оператором (force-override) —
  в ТЗ не упомянут; единственный путь перехвата — протухание по порогу
  heartbeat (требование 5).
- Lease для CLI-команд, не перечисленных в требовании 2 (`init`, `new`,
  `target_init`, `doctor`, `version` и т. п.) — эта задача не расширяет
  список мутирующих команд сверх `run`/`auto`/`advance`/`approve`/
  `reject`/`kill`/`budget`.
- Ослабление, отключение или изменение существующих гейтов, лимитов,
  guard-проверок и инвариантов (принцип целостности, ADR-0002) — таблица
  `leases` и её проверки добавляются поверх существующей механики, не
  вместо неё.
- Отдельная CLI-команда для ручного просмотра или снятия lease Оператором
  (например `artel.py lease <id>`) — в ТЗ не запрошена.
