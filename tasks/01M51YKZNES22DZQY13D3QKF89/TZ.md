# ТЗ: D1а: код проекта в одноразовом контейнере Docker (круг 2)

# D1а: код проекта в одноразовом контейнере Docker (круг 2)

## Факты

Основание — ADR-0023, «Поправка 16.10.2026: механизм — контейнер Docker» (пункты 1–3, 5, 7). Пункты 6 (круг 1) и 4 (стенд compose) в эту задачу не входят: это задачи D2 и D1б.

Сейчас пульт исполняет код проекта на хосте с полным окружением Оператора:
- `_pytest_env` (`orchestrator/acceptance.py:69-89`) копирует `os.environ` целиком;
- места запуска: `acceptance.py:448` (`run`), `:556` (`collect`), `:665` (`run_repeat`), `:932` (`run_plank`), `:1324` и `:1345` (`_run_full_suite_now`, с наблюдением и без), `:1373` (`_run_full_suite_to_log`); `pull.py`, `notes.py`, `amend.py` и гейты вызывают эти функции, сами процессов не запускают;
- `_pytest_command` (`acceptance.py:35-65`) всегда ставит интерпретатор venv пульта и `-p timeout`; полный набор жёстко берёт `<корень>/tests` (`:1172`) и дописывает `-n … -p xdist` (`:1176`). У sled нет `pytest-timeout` и `pytest-xdist`, тесты — в `backend/tests`;
- профиль `test_profile` (`orchestrator/targets.py:41-53`): `install` описан, но не исполняется; поля `sandbox` в проверке нет, у артели в `targets.yaml` уже стоит `sandbox: off`;
- автогейт приёмки и `approve` на acceptance зовут полный набор без команды профиля проекта (`docs/backlog.md:185`, строка 07.10) — у внешнего проекта набор пошёл бы интерпретатором пульта.

Docker Desktop 28.4 на машине Оператора работает. Записи sled в `targets.yaml` пока нет; её вносит Оператор в D2.

Требуется:

1. Поле записи проекта `sandbox`: значения `required | off`; отсутствие означает `required` для любого проекта, без исключения по имени; иное значение — отказ `targets.check` с названием записи и поля (ADR-0023 п.9). У артели (`sandbox: off`) ни один путь запуска не меняется: до правки зафиксировать тестами argv, `cwd` и окружение каждого из семи мест запуска для артели и держать их неизменными.

2. Подполя `test_profile` (все необязательные, профиль артели без них остаётся правильным):
   - `runner`: `pult-pytest` (по умолчанию, сегодняшнее поведение) | `pytest-own` (команда профиля как есть: без интерпретатора пульта, `-p timeout` и `-n/-p xdist`; пульт по-прежнему дописывает свои аргументы гейтов — `--collect-only -q`, `--junitxml`, `-o junit_logging=system-out`, `-p no:cacheprovider`);
   - `workdir`: каталог прогона относительно корня репозитория, после `realpath` обязан остаться внутри рабочей копии;
   - `env`: блочное отображение строк (новый вид `mapping`; `yamlmini` не меняется); имена из точного перечня секретов (`secret_env_names` провайдеров, `GITHUB_TOKEN`, `GH_TOKEN`) — отказ проверки, сверка по точному имени, не по подстроке;
   - `image`: имя образа Docker с тегом; обязательно при `sandbox: required`.
   Полный набор при `pytest-own` берёт каталог из `workdir` и `long_lived_dir`, а не `<корень>/tests`.

3. Модуль `orchestrator/sandbox.py` — одна функция исполнения кода проекта. Проверка `sandbox: required` — первое условие внутри каждой из семи функций запуска; при `off` — прежний код без изменений. Контейнер запускается так:
   - `docker run --rm --name artel-<проект>-<задача или run>-<случайный суффикс>`;
   - `--network none`;
   - `--user <uid>:<gid>` Оператора, `--cap-drop ALL`, `--security-opt no-new-privileges`;
   - лимиты памяти и процессора — константы `config.py`;
   - рабочая копия монтируется по тому же абсолютному пути на запись; `.git` клона проекта — по тому же пути только на чтение; каталог отчётов прогона (`--junitxml`, журнал) — по тому же пути на запись; других монтирований нет;
   - окружение — только `test_profile.env`, `HOME=/tmp`, `PYTHONPYCACHEPREFIX` во временный каталог контейнера и переменные кэша (п.5); переменные окружения пульта не передаются;
   - рабочий каталог — `workdir`.
   Сокет Docker, `~/.ssh`, связка ключей, токены, БД и журналы пульта в контейнер не попадают.

4. Таймаут и сбои. По таймауту и на любом исключении контейнер останавливается командой `docker kill <имя>`, затем пульт убеждается, что контейнера нет. Ошибка самого Docker (демон недоступен, нет образа, коды выхода `docker run` 125–127) — именованный инфраструктурный отказ, а не «красные тесты»; прогон на хосте вместо контейнера запрещён (fail-closed, ADR-0002). Разбор вывода, наблюдение, замок полных прогонов машины и предел по профилю работают как сейчас.

5. Установка зависимостей. Перед прогоном при `sandbox: required` и непустом `install`: если хеш файлов блокировки в `workdir` изменился с прошлой успешной установки (хеш хранится в области проекта `.artel/projects/<имя>/`), пульт исполняет `install` отдельным одноразовым контейнером с тем же образом и монтированиями, но с сетью по умолчанию. Кэш пакетов — именованный том `artel-<проект>-cache`, смонтированный в установку и в прогоны; путь задаётся переменными `XDG_CACHE_HOME` и `UV_CACHE_DIR`. Сбой установки — именованный отказ прогона.

6. Один источник команды профиля: автогейт приёмки (`fsm_autogate.py`) и `approve` на acceptance (`fsm.py`) берут команду, `runner` и `workdir` профиля проекта задачи — тем же путём, что `suite-run`, `plank-run`, `preflight`, `acceptance-dry-run` (строка бэклога 07.10, `docs/backlog.md:185`).

7. `doctor` для проектов с `sandbox: required`: демон Docker отвечает; образ `image` есть локально; живая проба — одноразовый контейнер проекта не открывает внешний адрес и не видит переменных пульта. Для `sandbox: off` проверки не выполняются и запуск не блокируют. Сборка образа пультом не входит: Оператор собирает его вручную, `doctor` при отсутствии печатает команду сборки.

8. Тесты в `tests/` детерминированы и не требуют Docker: вместо `docker` — подставной исполняемый файл, записывающий argv и код выхода. Проверяется: argv и монтирования по п.3 (в том числе отсутствие лишних монтирований и переменных), выбор контейнера только при `required`, неизменность путей артели (п.1), `docker kill` по таймауту и исключению, именованный отказ при ошибке Docker и запрет запуска на хосте, повтор установки только при смене хеша, проверка полей профиля. Живой запуск с настоящим Docker — проба `doctor` и ручной критерий Оператора в PLAN, не тест набора.

Критерии приёмки:
- полный набор `tests/` зелёный; у артели argv, `cwd` и окружение всех семи мест запуска не изменились;
- учебный проект во временном каталоге с `sandbox: required` и `runner: pytest-own`: тест, читающий `os.environ`, не видит ни одной переменной пульта, кроме перечисленных в п.3; тест с выходом на внешний адрес падает; тест, пишущий вне рабочей копии на хосте, не оставляет следов;
- по таймауту контейнер снят и `docker ps -a` его не показывает;
- при остановленном Docker Desktop прогон проекта с `required` — именованный отказ, не прогон на хосте.

Зоны: `orchestrator/sandbox.py` (новый), `orchestrator/acceptance.py`, `orchestrator/targets.py`, `orchestrator/config.py` (константы лимитов), `orchestrator/fsm_autogate.py` и `orchestrator/fsm.py` (только п.6), `orchestrator/doctor/` (новая проверка), `tests/`. Только чтение: `docs/backlog.md`, `targets.yaml` (не меняются). Правка вне зон — эскалация до SPEC.

Не входит: запись sled и меры круга 1 (D2); стенд docker compose с базами и очередями (D1б); шаг роли в контейнере; белый список хостов для установки (`install_hosts` из ADR-0023 п.10 отменён поправкой 16.10); сборка образов пультом; Linux и Codex; песочница для артели.

Рамка: $60. При оценке аналитика выше рамки — деление на D1а-1 (пп. 1–4, 8 для `run`, `collect`, `run_repeat`, `run_plank`) и D1а-2 (полный набор, пп. 5–7).
