# GitLab, шаг Б2.3: хук `pre-push` в клоне проекта, сверки `doctor` для проекта с `target-human`, открытие `gitlab` и `target-human`

## Факты

ADR-0029 (принят 26.10.2026), п. 8 (адаптер, срок токена), п. 13 (единая точка отправки, хук — второй рубеж), п. 14 (порядок при инциденте). Влиты А0–В2 линии GitLab. Аналитик сверяет строки по коду после мержа Б2.2 и В2.

1. Поддержка закрыта списками `targets.SUPPORTED_FORGES = ("github",)` и `SUPPORTED_MERGE_GATES = ("operator",)` (`orchestrator/targets.py:29-30`); отказ — `targets.unsupported_reason` (`:270`), текст для хостинга — «адаптера нет (ADR-0029)» (`:286`) и `forge._hosting` (`orchestrator/forge.py:177`), хотя адаптер GitLab уже есть. Сторож — `tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py`.
2. Единая точка отправки и белый список ссылок — `orchestrator/gitcmd.py` (Б1.1); переменные окружения git, которые пульт задаёт и снимает, — `gitcmd.py:150-190`, `:640`. Хуки главной копии — `scripts/git-hooks/`, их сверка — `orchestrator/doctor/git_hooks.py`.
3. Решение сессии при Операторе 26.10 по замечанию R3-F1 (Б1.1): псевдоним в аргументах команды (`-c alias.*`, `!`-форма, `--config-env`), прячущий назначение отправки в значении, перебором форм в `gitcmd` не закрывается; закрывается постоянным `core.hooksPath` клона на каталог хуков пульта и хуком `pre-push` с теми же правилами.
4. Строки проекта в `doctor` — `orchestrator/doctor/project_checks.py` (`check_base_protection` `:176`, `check_no_paths` `:359`, `component_checks` `:400`); `forge-probe <проект> [--job <имя>]` — `artel.py:2380`, читает последний конвейер базы.
5. Защиты веток через API хостинга при роли токена Developer читаются не полностью: часть полей отдаёт только роль Maintainer.

## Требуется

1. **Хук `pre-push` в клоне проекта с `target-human`**: при подготовке клона (и `doctor --fix`) пульт прописывает в конфигурацию клона `core.hooksPath` на каталог хуков пульта вне зон записи ролей; хук проверяет те же правила, что `gitcmd` (только ветка задачи по шаблону и `refs/artifacts/*`; отправка в `base`, удаление веток, теги, `refs/heads/*` вне шаблона — отказ), при любой отправке из клона, как бы её ни запустили (в том числе псевдонимом и коротким именем удалённого репозитория). Каждый вызов отправки пульта по-прежнему задаёт `-c core.hooksPath=<каталог пульта>`.
2. **Сверки `gitcmd` перед отправкой** для проекта с `target-human`: `remote.origin.url` клона совпадает с адресом записи; в действующей конфигурации нет `url.*.insteadOf`/`pushInsteadOf`, `core.sshCommand`, иного `core.hooksPath`; в окружении вызова сняты `GIT_DIR`, `GIT_WORK_TREE`, `GIT_SSH_COMMAND`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`. Нарушение — отказ отправки с именем находки до вызова git.
3. **Строки `doctor` проекта с `target-human`** (только чтение):
   - контрольная сумма хука `pre-push` и значение `core.hooksPath` клона — `fail` при расхождении, `--fix` восстанавливает;
   - защиты веток: если API отдаёт неполные сведения при роли токена ниже Maintainer — `skip` «нужна роль Maintainer», а не `fail`;
   - шаблон ветки задачи против правил `workflow` конфигурации CI проекта: ветка по шаблону не попадает под конвейер — `warn` с именем правила;
   - файл конфигурации CI в `no_paths` у записи с компонентом `full_suite: ci|both` — иначе `fail`;
   - в задании `ci_job` нет перезапуска упавших тестов (`pytest-rerunfailures`/`--reruns`, `retry` задания) — иначе `warn` (инвариант 41: отчёт хостинга повторов не видит);
   - подмодули проекта на том же хостинге: адрес подмодуля доступен по тому же слоту токена — `ok`/`fail` с причиной; клон подмодулей — тем же слотом.
4. **`forge-probe <проект> --ref <ветка> | --sha <sha>`** — сведения конвейера названной ветки или коммита вместо последнего конвейера базы; прочий вывод прежний.
5. **Тексты отказа**: для хостинга с адаптером — без «адаптера нет»; причина называет действительное: неподдержанный гейт мержа или хостинг вне списка.
6. **Открытие**: `SUPPORTED_FORGES = ("github", "gitlab")`, `SUPPORTED_MERGE_GATES = ("operator", "target-human")`; сочетание `github` + `target-human` остаётся неподдержанным (отказ загрузки с причиной) до отдельного решения. Сторож А0 обновляется по мандату (п. «Существующие тесты»).
7. **Отказ при сбое вместо пропуска** (находки проверяющих приёмки Б2.1а и Б2.1б, 01.11): до открытия п. 6 каждый путь, где сбой чтения пропускает проверку, отказывает с причиной:
   - `fsm_merge_gate.py` (~`:1509`): `people_entry` вернул `None` из-за сбоя чтения записи у задачи проекта с `target-human` — отказ гейта мержа, не путь слияния в base;
   - `fsm_merge_gate.py` (~`:1740`): сбой чтения записи — отказ, а не пропуск предела `max_awaiting`;
   - `gitcmd.in_repo` и проверка `max_in_flight` (`gitcmd.py` ~`:774`, `:960`): `sqlite3.Error` — отказ отправки с причиной, а не `refusal = None`;
   - `github_adapter.py` (~`:173`): отказ пределом различается по коду результата, а не по строке stderr.
   - `fsm_merge_gate._mr_incident_stops` (~`:1684-1693`): статус MR вне `opened`/`merged`/`closed` (например `locked`, пустой) — отказ гейта с причиной, а не проход;
   - тест на правило ANSWER-1 п. 3 Б2.2 (`mr_sync.py` ~`:356`): открытый MR, чей `sha` уже предок `origin/<base>`, — признак (а) не засчитывается, `--confirm` отказывает (находка проверяющего приёмки Б2.2: мутация `state == "merged"` → `True` не ловится).
   - проверка записи «`full_suite: ci|both` только для хостинга с чтением отчёта задания» (В1.1) не зависит от того, загружен ли модуль `ci`: реестр хостингов не подставляется при импорте `ci` (`orchestrator/ci.py:28`, `orchestrator/targets.py:1098`), загрузка записи в `doctor` без `ci` отказывает так же (находка проверяющего приёмки В1.1);
   Критерии: на каждый путь — тест с подменённым сбоем (исключение чтения/БД) → отказ, шпион не видит слияния, отправки, открытия MR.
8. **Порядок действий при инциденте** (ADR-0029 п. 14): `docs/incident-external-project.md` — отзыв токена, срез журнала задачи, ссылка на MR, остановка задач проекта; без данных конкретных проектов.

Критерии приёмки (песочницы — вымышленные проекты с локальным `origin`):
- хук: отправка из клона в `base`, тега, удаление ветки, ветки вне шаблона — отказ хука, в том числе через `git -c alias.p=push`, `!`-псевдоним и короткое имя удалённого; ветка задачи и `refs/artifacts/*` — проходят;
- `gitcmd`: подменённый `remote.origin.url`, `insteadOf`, `pushInsteadOf`, `core.sshCommand`, чужой `core.hooksPath`, `GIT_SSH_COMMAND`/`GIT_DIR` в окружении — отказ до вызова git (шпион не видит `push`);
- `doctor`: изменённый хук — `fail`, `--fix` восстанавливает и строка `ok`; защиты при неполном ответе — `skip` «нужна роль Maintainer»; ветка вне `workflow` — `warn`; файл CI не в `no_paths` при `full_suite: ci` — `fail`; `--reruns` в задании — `warn`; подмодуль недоступен — `fail` с причиной;
- `forge-probe --ref`, `--sha` на подменённом `forge` — конвейер названной ветки или коммита;
- загрузка `gitlab` + `target-human` — без отказа; `github` + `target-human` — отказ с причиной; текст отказа без «адаптера нет»;
- артель и проекты `github` + `operator`: поведение и существующие тесты прежние.
