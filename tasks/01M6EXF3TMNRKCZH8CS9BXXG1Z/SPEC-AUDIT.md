# SPEC-AUDIT: GitLab Б2.3 — хук pre-push в клоне, сверки отправки, строки doctor, отказ при сбое, открытие gitlab и target-human

## ТЗ и SPEC

Решения ANSWER-1 пп. 1–5 в SPEC перенесены: пары поддержки (SPEC.md:47), мандат на сторож А0 с условиями (а)–(г) (SPEC.md:52-56), деление на 4 части и порядок (SPEC.md:72-76), добавка п. 5 к части 3 (SPEC.md:31-34). Отклонения:

- **А1. Потеряно место ТЗ п. 7, третий пункт.** ТЗ называет `gitcmd.py` «~`:774`, `:960`». В SPEC вместо этого «~`:774`, ~`:1244-1245`» (SPEC.md:40, SPEC.md:97). По коду это три разных места, и каждое пропускает проверку при сбое: `in_flight_refusal` `gitcmd.py:774-775` (`(TargetsError, sqlite3.Error)` → `None`), `_push_plan` `gitcmd.py:956-961` (`sqlite3.Error` → `waiting = None`, это и есть «проверка `max_in_flight`» из ТЗ) и `in_repo` `gitcmd.py:1242-1245` (`refusal = None`). Место `:960` из SPEC выпало. Текст части 1 станет ТЗ подзадачи, поэтому разработчик его не увидит, и отправка при сбое БД пройдёт мимо предела `max_in_flight`.
- **А2. Требование SPEC расходится с собственным AC.** Требование 4 перечисляет для `gitlab` три строки (SPEC.md:31-34). AC-6 требует: «ни одна строка не вызывает `gh`» (SPEC.md:60). Но `project-token` (`check_project_token`, `orchestrator/doctor/project_checks.py:225-246`) вызывает `gh auth token` через `_operator_gh_token` (`:211-222`), а строка выполняется для любой записи (`:52-53`). Значит, AC-6 требует правки строки, которой нет в требовании 4. Что делать для `gitlab` со сверкой «токен проекта ≠ токен Оператора», SPEC не говорит.
- **А3. Подмодули без зоны.** ТЗ: «клон подмодулей — тем же слотом», а в зонах ТЗ стоит «`orchestrator/workspace.py` (подготовка клона: `core.hooksPath`, подмодули)». SPEC отнёс клонирование подмодулей к части 3 (SPEC.md:143), но зон `workspace.py`/`gitcmd.py` у части 3 нет (SPEC.md:130). У части 2 есть зона `workspace.py`, но нет требования. В `workspace.py` о подмодулях сейчас нет ничего (grep `submodule` пуст), так что это новое поведение, у которого нет исполнителя.

## Факты против кода

Подтвердилось: `targets.py:29-30` (списки), `:283` `unsupported_reason`, `:299` текст «адаптера нет (ADR-0029)», `:128` `hosting_registry = None`, `:1098` чтение реестра; `ci.py:28` подстановка `targets.hosting_registry = lambda: forge.IMPLEMENTATIONS`; `forge.py:176-185` `_hosting`, текст `:184`. Также `fsm_merge_gate.py:1516` (`people_entry`), `github_adapter.py:347-355` (`TargetsError` → `None`), `fsm_merge_gate.py:1789-1808` (`TargetsError` → `False` на `:1796-1797`), `fsm_merge_gate.py:1661-1702` (статус вне трёх значений даёт `detail == ""` → `return False`, `:1695-1698`), `github_adapter.py:173` (различение по `IN_FLIGHT_LIMIT_REASON in stderr`), `mr_sync.py:356`. Строки сторожа А0 (`:41`, `:44-48`, `:165-166`, `:406`) на месте.

Не подтвердилось или неполно:
- **Б1.** «Каждый вызов отправки пульта **по-прежнему** задаёт `-c core.hooksPath=<каталог пульта>`» (SPEC.md:21, :118). В `orchestrator/gitcmd.py` нет ни одного `core.hooksPath` (grep по `orchestrator/` находит только `mutation_run.py:110` с `/dev/null` для коммита). Это новое поведение, а не прежнее. Ошибку унаследовали из ТЗ. Исполнитель, поверивший «по-прежнему», может её не реализовать, и AC-1/AC-2 этого не поймают.
- **Б2.** SPEC не учитывает, что `core.hooksPath` у клонов уже есть: `workspace.hooks_path()`/`set_clone_hooks` (`orchestrator/workspace.py:48-75`) ставят его всем клонам на `<ROOT>/scripts/git-hooks`. `doctor` уже сверяет его строкой `clone-hooks` со статусом `warn` (`orchestrator/doctor/git_hooks.py:148-172`) и чинит `_fix_project_clones` (`:175-192`). Требование 3 вводит `fail` для того же значения. Как старая строка `warn` соотносится с новой строкой `fail` (две строки на одно расхождение или замена), не сказано.
- **Б3.** «Новый файл хука проекта в `scripts/git-hooks/`» (SPEC.md:118). git вызывает только файл с именем `pre-push` из каталога `core.hooksPath`, а он уже занят хуком защиты main (`scripts/git-hooks/pre-push`). Отдельный файл не сработает, пока его не вызывает общий `pre-push`. Каталог общий для клонов всех проектов, включая артель, поэтому правила ветки задачи для `target-human` должны жить в общем хуке и выбираться по проекту клона. SPEC этого не говорит. Не сказано и откуда хук берёт шаблон ветки и `base` проекта.
- **Б4.** `people_entry` при сбое чтения возвращает `None` (`github_adapter.py:353-354`) и тем самым теряет признак `target-human`. SPEC требует отказа «у задачи проекта с `target-human`» (SPEC.md:38), но не говорит, по какому признаку узнать гейт проекта, если сама запись не прочиталась. Например: отказ для любого внешнего проекта при сбое чтения, или признак, сохранённый в строке задачи.

## Зоны

- **г2.** Сторож ac9 (`tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:474-508`) запрещает в `orchestrator/` вне `targets.py` сравнения значения `forge`/`merge_gate` с литералами `github`/`gitlab`/`operator`/`target-human`. Исключения перечислены поимённо (`:416-421`). Требование 4 («выбор проверки по `forge` записи») и требования 1–2 («для проекта с `target-human`») естественно пишутся именно таким сравнением в `doctor/project_checks.py` и `gitcmd.py`. Тогда ac9 краснеет, и исполнитель части 2/3 захочет добавить исключение в `EXEMPT`. Мандата на это нет: мандат на файл дан только части 4. SPEC не задаёт путь: признак через помощник `targets.py` (как `targets.merged_by_project_people`) или через реестр `forge`.
- **г3.** Часть 1 (отказ при `sqlite3.Error` в `in_repo`, `gitcmd.py:1242-1245`) не сужена до проектов под белым списком или с `target-human`. `in_repo` проверяет все отправки, в том числе артели. - **г4.** Части 3 разрешено идти «параллельно частям 1–2» (SPEC.md:75, :131), но AC-3 (контрольная сумма хука `pre-push` проекта, `--fix`) проверяет хук, который заводит часть 2. Порядок «без зависимостей» оставляет AC-3 без предмета или вынуждает часть 3 сверять несуществующий хук.

## Пути обхода гейтов

- **е1.** Нынешний `pre-push` пропускает всё при `ARTEL_PULT_GIT=1` в окружении (`scripts/git-hooks/pre-push:14-16`). Если хук проекта унаследует этот обход (по образцу), роль снимет второй рубеж одной переменной, в том числе внутри `!`-псевдонима. SPEC не запрещает маркер для хука проекта, а AC-1 обход не проверяет.
- **е2.** «Как бы её ни запустили» (SPEC.md:21) хуком недостижимо: `git push --no-verify` и `git -c core.hooksPath=/dev/null push` из оболочки роли хук не запускают, а эти вызовы идут мимо `gitcmd`. SPEC не называет модель угроз (что на деле держит отправку роли: отсутствие токена в окружении роли, отказ CLI) и не включает эти формы в AC-1. Критерий выполним буквально, но смысл «любой отправки» не держится.
- **е3.** Сторож ac9 смотрит только на выражения с `forge`/`merge_gate` в имени (`tests/test_01m5w27…:425-442`). Сравнение `forge.hosting(name) == "gitlab"` (атрибут `hosting`) сторожем не ловится. Исполнитель части 3, выбирая проверку по хостингу, обойдёт смысл ac9 («проверка поддержки — только в `targets.py`»), не тронув теста.
- **е4.** Требование 8, пункт про `people_entry`: если исполнитель различит сбой только у записей, которые прочитались (Б4), отказ при сбое формально «реализован», но сбой чтения по-прежнему ведёт в путь слияния в `base`. Сбой чтения — ровно тот случай, когда признака нет.
