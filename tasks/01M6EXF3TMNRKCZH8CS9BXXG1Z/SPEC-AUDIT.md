## Пути обхода гейтов

- **е4 (основное).** Требование 1 (SPEC.md:28, :30, :33) и AC-1 (SPEC.md:88-89) при общем каталоге хуков (Б4) противоречат друг другу. Если каталог один, хук может отличить клон `target-human` от клона `operator` и от главной копии только по наличию файла политики. Тогда два пути буквального исполнения:
  - (а) нет файла — поведение «как прежде». AC-1 п. 5 нарушен. Удаление файла политики из `.git` клона снимает правила `target-human`, и возвращается обход по `ARTEL_PULT_GIT=1`. Это тот же «пропуск при сбое чтения», который требование 8 закрывает в Python;
  - (б) нет файла — отказ. Ломаются клоны `operator` и главная копия (AC-1 п. 6, AC-13).

  Нужно решение: клоны `target-human` получают свой каталог хуков пульта (например `<config.ROOT>/scripts/git-hooks/<подкаталог>`), и признаком служит `core.hooksPath`, а не файл. Тогда «иной `core.hooksPath`» (требование 2, SPEC.md:39), эталон `doctor` и `--fix` (SPEC.md:43) сверяются с этим каталогом, а `clone-hooks` у прочих — с прежним. Либо нужен другой признак, который не снимается удалением файла роли. Сейчас SPEC говорит только «как `workspace.hooks_path`».
- **е5 (мелкое).** Удаление `refs/artifacts/<id>` единая точка отправки разрешает (`gitcmd.py:687-691`). В правилах хука (SPEC.md:29) есть только «`refs/artifacts/*` проходят» и «удаление веток — отказ», а об удалении `refs/artifacts/*` ничего не сказано. Вызова пульта, удаляющего такую ссылку в origin внешнего проекта, я в коде не нашёл: `artifact_cleanup.py:103` удаляет ветки артели. Так что поломки сейчас нет, но расхождение правил хука и `gitcmd` стоит назвать явно.
- **е6 (мелкое).** Файл политики лежит в `.git` клона. Это каталог git рабочих копий ролей, и роль может писать в него через git и оболочку. Модель угроз (SPEC.md:34-36) называет только постоянный `core.hooksPath`. Правку файла политики ролью она прямо не называет, хотя её тоже ловит только `doctor` (сумма по эталону записи, требование 3), а сверки отправки пульта (требование 2) файл не читают. Для отправок пульта это безвредно: их держит белый список `gitcmd`. Строка в модели угроз сняла бы вопрос.
