# PLAN: К1: секция «Предложения системе» — копилка наблюдений ролей

## Подход
`templates/` и `skills/` — защищённые пути (правит только Оператор
отдельным MR, SPEC требование 4). Поэтому реализация этой задачи в
ветке `task/t046-...` состоит из одного артефакта — этого PLAN.md — с
тремя приложенными унифицированными диффами (templates/PLAN.md,
templates/REVIEW.md, skills/conventions-core.md, см. «Дифф для
Оператора» ниже) и не трогает сами защищённые файлы напрямую.

Скил для абзаца о секции — `conventions-core.md` (не
`coding-standards`/`review-checklist`): копилку пишут обе роли,
которые сдают PLAN.md/REVIEW.md (developer и reviewer), а
`conventions-core` — единственный скил, общий для всех ролей и уже
описывающий структуру артефактов («## Артефакты»). Разнести абзац по
`coding-standards` и `review-checklist` означало бы задублировать
один и тот же текст в двух местах ради одной и той же механики.

Проверено, что `scripts/guard.py` не требует правок (требование 2):
`check_content` берёт список обязательных секций из `RULES[type]
["sections"]` и проверяет только их наличие в `headers`; секций сверх
этого списка не запрещает — заполненная, пустая и отсутствующая
`## Предложения системе` уже сегодня проходят без нарушений. Это
подтверждено прогоном `tasks/T046/acceptance_tests/
test_predlozheniya_sisteme.py::GuardAcceptsOptionalSectionTest` (6/6
green) до какой-либо правки кода — правка guard.py в объёме, который
требует SPEC («только если нужна»), равна нулю.

## Влияние на систему
Дифф ветки задачи ограничен `tasks/T046/PLAN.md` — ни один файл в
`orchestrator/`, `scripts/`, `tests/` не меняется, `templates/` и
`skills/` не коммитятся напрямую (проверено юнит-тестом AC-5,
`ProtectedPathsTest.test_ac5_branch_diff_does_not_touch_protected_paths`,
который читает реальный `git diff main...HEAD`). `scripts/guard.py` не
правится: его текущая логика (проверка только обязательных секций из
`RULES`) уже допускает необязательную секцию в любом из трёх
состояний — ослаблять или расширять guard не требуется, инвариант
«структура артефакта валидируется» не затронут. Полный набор
`tests/` (существовавший до этой задачи) прогнан без изменений и
зелёный — задача не меняет код, которому эти тесты принадлежат.
Существующие артефакты уже закрытых задач (`tasks/T0??/PLAN.md`,
`REVIEW.md` прошлых задач) не редактируются — требование 5 соблюдено
тем, что дифф ветки их не касается. Откат: если Оператор решит не
применять приложенный дифф — ветка `task/t046-...` не содержит
изменений в защищённых путях, откатывать нечего; если дифф уже
применён Оператором отдельным MR — откат равен git revert того MR,
эта ветка не участвует.

## Риски
Секция становится реально доступной ролям только после того, как
Оператор применит приложенный дифф своим MR — до этого момента К1
существует только как текст в этом PLAN.md. Это не «фича за флагом»
(нет условного кода, который можно забыть включить), а прямое
следствие требования 4 (защищённые пути); риск — организационный
(Оператор забудет применить MR), не технический.

## Порядок коммита Оператором
1. Оператор применяет все три диффа выше к `main` (или к своей
   ветке правки защищённых путей) одним MR — `templates/PLAN.md`,
   `templates/REVIEW.md` и `skills/conventions-core.md` меняются
   вместе, порядок применения между ними не важен (файлы
   независимы, конфликтов между диффами нет).
2. Оператор коммитит результат с сообщением в духе `T046: секция
   «Предложения системе» в шаблонах и conventions-core` и мержит
   MR в `main` в обход обычного FSM конвейера задач — так же, как
   был оформлен прецедент правки скилов 26.08.
3. После этого MR живые `templates/PLAN.md`, `templates/REVIEW.md`
   и `skills/conventions-core.md` несут секцию/абзац, и
   `tasks/T046/acceptance_tests/test_predlozheniya_sisteme.py`
   (AC-1, AC-3, `ProtectedPathsTest`) может быть перепроверен
   Оператором вручную на приёмке этого MR — до него автоматическая
   проверка их содержимого недостижима (см. докстринг файла).
4. Ветка `task/t046-k1-sektsiya-predlozheniya-sist` в этот MR
   Оператора не участвует и не мержится сама по себе с содержимым
   защищённых путей — только `tasks/T046/PLAN.md` идёт обычным
   путём задачи (review → merge_gate).
