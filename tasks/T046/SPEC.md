# SPEC: К1: секция «Предложения системе» — копилка наблюдений ролей

## Контекст
Агенты по ходу задач замечают вещи про саму систему (не про свою
задачу) — противоречие скила практике, повторившийся антипаттерн,
натирающая механика. Этим наблюдениям сейчас некуда деться: они умирают
вместе с контекстом агента. Свежие примеры из истории задач: класс
«вызов внешней команды без обработки сбоя» отмечен ревьювером в T042 и
повторно в T043 (два ревью заплачено за один и тот же урок);
ревьюверы T041 и T044 независимо списали шум тестов на
«предсуществующий сбой», которого не было; в T045 новая команда
workspace осталась без lease-защиты, которую задача строила для всех
остальных команд. Следующая ступень контура обучения (К2, куратор)
просыпается по триггеру «жалоба повторилась в копилке» — без копилки
триггер слеп. Это К1: копилка наблюдений в PLAN.md и REVIEW.md
(решение Оператора 27.08 по аудиту состояния).

## Требования

1. В `templates/PLAN.md` и `templates/REVIEW.md` добавить
   необязательную секцию `## Предложения системе` с краткой
   инструкцией-комментарием в теле шаблона: 0–5 пунктов, каждый — одна-
   две строки наблюдения о системе (скил противоречит практике,
   антипаттерн повторился, механика натирает), с адресом (файл/скил/
   класс проблемы), без свободных эссе.
2. Пустая секция и полное отсутствие секции в артефакте — оба валидны:
   `scripts/guard.py` не делает секцию обязательной ни для PLAN.md, ни
   для REVIEW.md. Правка guard.py вносится только в объёме, необходимом
   для того, чтобы новая секция не ломала валидацию существующих и
   новых артефактов — не для того, чтобы сделать её обязательной.
3. Скил(ы) ролей (`conventions-core` и/или `coding-standards`/
   `review-checklist` — по факту того, где уместнее) дополняются одним
   абзацем: что и когда писать в секцию «Предложения системе», с
   примером наблюдения.
4. `templates/` и `skills/` — защищённые пути (правит их только
   Оператор отдельным MR, см. прецедент правок скилов 26.08). Исполнитель
   задачи готовит текст правок этих двух путей как дифф, приложенный к
   PLAN.md (не коммитит их напрямую в ветку задачи под своей ролью);
   порядок финального коммита Оператором по этому диффу описывается в
   PLAN.md.
5. Существующие артефакты уже закрытых задач задним числом не
   правятся.

## Критерии приёмки

AC-1. Шаблоны `templates/PLAN.md` и `templates/REVIEW.md` содержат
секцию `## Предложения системе` с краткой инструкцией-комментарием.

AC-2. `scripts/guard.py` принимает артефакт (PLAN.md и REVIEW.md) и с
заполненной, и с пустой, и с отсутствующей секцией «Предложения
системе» — во всех трёх случаях валидация проходит без нарушений по
этой секции.

AC-3. Хотя бы один скил роли (`conventions-core` или
`coding-standards`/`review-checklist`) содержит абзац о том, что и
когда писать в секцию «Предложения системе», с примером.

AC-4. Существующий набор тестов (`tests/`) зелёный.

AC-5. Дифф задачи вне `templates/` и `skills/` не содержит правок этих
защищённых путей; правки `templates/` и `skills/` оформлены отдельно —
как подготовленный для Оператора дифф, а не как прямой коммит
исполнителя в ветку задачи; порядок финального коммита Оператором по
этому диффу описан в PLAN.md.

## Не входит

- Автоматика разбора копилки (агрегация, дедупликация, триггер
  повторной жалобы) — это следующая ступень контура (К2, куратор),
  срабатывающая по триггеру №6 из аудита 27.08.
- Правка `scripts/guard.py` сверх объёма, нужного для валидности новой
  необязательной секции — секция не становится обязательной.
- Задним числом правка артефактов уже закрытых задач под новый формат
  шаблона.
