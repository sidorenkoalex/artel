# PLAN: Merge queue: мержи строго по одному

## Подход

Второй, отдельный замок поверх уже существующего lease задачи (T044):
lease защищает задачу от параллельной мутации СВОЕЙ строки, но не main
от двух РАЗНЫХ задач, одновременно исполняющих merge-окно. Решение —
новый модуль `orchestrator/merge_lock.py` с одной строкой-мьютексом на
весь пульт (таблица `merge_locks`, пять колонок по образцу `leases`:
`task_id, session_id, pid, hostname, heartbeat_ts`, без PRIMARY KEY —
единственность строки не PK-инвариант БД, а инвариант приложения:
`store.set_merge_lock` всегда пишет через снос предыдущей строки), взятие
атомарно тем же приёмом, что `lease.acquire` (`BEGIN IMMEDIATE` до чтения
строки).

Отличие от lease по существу, не только именами: lease держит СЕССИЯ
через СЕРИЮ вызовов `auto` (её `release()` снимает только то, что взяла
С НУЛЯ сама — иначе `auto` отпускал бы lease между своими внутренними
`run`/`advance`). Мьютекс merge живёт РОВНО одну операцию — тело одного
вызова `approve` из `merge_gate` — поэтому `release()` снимает его
безусловно по завершении окна, без понятия «взят с нуля»: не отдельные
`insert_lease`/`update_lease`, а один `store.set_merge_lock` (DELETE +
INSERT), и не `(refusal, fresh)`, а просто `refusal: str | None`.

Второе отличие от lease по требованию 4 SPEC: `lease.acquire` перешагивает
только протухший heartbeat (пид держателя лизинг не проверяет — держатель
там обычно жив весь МЕЖДУ-командный интервал `auto`, и pid-детекцию несёт
только `doctor`). У мьютекса merge оба признака мёртвого держателя —
протухший heartbeat ИЛИ неживой pid на этом host — перешагиваются самим
`acquire()`, не только детектируются `doctor` постфактум: без этого
краш-без-освобождения сессии посреди merge-окна (единственный реальный
сценарий появления «мёртвого» держателя мьютекса, живущего одну операцию)
блокировал бы merge до истечения `LEASE_STALE_AFTER_SEC` (2 часа) вместо
немедленного перешагивания живым `doctor`-детектируемым признаком.
Обнаружено прогоном приёмочного `test_ac6_dead_pid_holder_does_not_block_
next_approve` (залочен test_author) до реализации этой ветки — падал на
`assertEqual('merge_gate', 'done')`.

Третье изменение — в `orchestrator/fsm.py`: `_pull_main_or_escalate`
(T051) возвращала `bool` (`True` — эскалация, `False` — «фреш» и
«подтянуто» неразличимо, оба вели переход дальше). Обеим существующим
точкам входа (`in_dev -> review`, `acceptance -> merge_gate`) это
различие не требовалось. Третьей, новой точке (`merge_gate -> done`,
требование 5) — требуется: «фреш» продолжает merge как раньше (AC-4),
«подтянуто» обязано ОСТАНОВИТЬ merge в этом же вызове и оставить задачу
на гейте (AC-3), «эскалация» — как и раньше. Меняю возврат на строковый
`"fresh" | "pulled" | "escalated"`, правлю обе существующие точки
(`== "escalated"` вместо `if ...:`) и добавляю третью.

Тело окна `merge_gate -> done` (сверка главной копии, сверка свежести,
CI, checkout/pull/merge, карта/RETRO, push, `done`) выношу в отдельную
`_cmd_approve_merge_gate(conn, task_id, state, t)` — сама ветка
`elif state == "merge_gate":` в `_cmd_approve` становится только
взятием/освобождением мьютекса вокруг вызова этой функции, try/finally
(требование 3). `_cmd_approve` получает третий параметр `sid` (session_id,
уже разрешённый `lease.resolve_session_id` в `cmd_approve`) — тот же
session_id, что взял lease задачи, берёт и мьютекс merge: один и тот же
вызывающий, одна identity.

Схема таблицы, session_id-контракт `merge_lock.acquire`/`release`,
формат отказа (session_id + задача держателя) и точка вызова
`_pull_main_or_escalate` внутри `_cmd_approve_merge_gate` — не решения
этого PLAN, а уже зафиксированные допущения залоченных приёмочных
(`tasks/T053/acceptance_tests/_mutex_sandbox.py`, «Допущения интерфейса»):
реализация обязана совпасть с ними буквально (имя таблицы `merge_locks`,
её пять колонок, порог `config.LEASE_STALE_AFTER_SEC`).

## Шаги

1. `orchestrator/store.py`: таблица `merge_locks` в `SCHEMA` и `migrate()`
   (по образцу `leases`); функции `merge_lock_row`, `set_merge_lock`,
   `release_merge_lock`.
2. `orchestrator/merge_lock.py` (новый модуль): `acquire(conn, task_id,
   session_id) -> str | None`, `release(conn, session_id) -> None`;
   атомарность `BEGIN IMMEDIATE`; перешагивание мёртвого держателя по
   обоим признакам (heartbeat, pid — требование 4).
3. `orchestrator/fsm.py`:
   - `_pull_main_or_escalate` — возврат `"fresh"/"pulled"/"escalated"`;
   - оба существующих вызова (`in_dev`, `acceptance`) — сверка на
     `== "escalated"`;
   - `_cmd_approve`/`cmd_approve` — прокидка `sid`;
   - тело `merge_gate` выносится в `_cmd_approve_merge_gate`, которая
     дополнительно (ДО сверки CI) вызывает `_pull_main_or_escalate`:
     `"pulled"` печатает новый head и возвращает без merge, `"fresh"`
     продолжает как раньше;
   - ветка `elif state == "merge_gate":` — взятие мьютекса
     (`sys.exit(refusal)` при отказе) + try/finally.
4. `orchestrator/doctor.py`: `check_merge_lock(conn) -> list[Check]` по
   образцу `check_leases`; подключение в `all_checks`.
5. `tests/test_merge_lock.py` (новый): юниты `acquire`/`release` в
   изоляции — свежее взятие, ре-вход своей сессии, отказ чужим свежим
   держателем (с именем и задачей), перехват протухшего heartbeat
   (с журналом), перехват мёртвого pid НА ЭТОМ host при свежем heartbeat
   (требование 4, ключевое отличие от lease), НЕ-перехват мёртвого pid
   на ЧУЖОМ host, release только своей сессией, атомарность под гонкой
   (по образцу `tests/test_lease.py::ConcurrentAcquireTest`).
6. `docs/codebase-map.md`: регенерация (`python3 scripts/codebase_map.py`).

## Влияние на систему

- Инвариант 12 (ред. ADR-0006, «в main мержит только `approve` из
  `merge_gate`») — не нарушается: мьютекс не открывает новый путь влить
  что-либо в main, только сериализует существующий (`test_invariants.
  MergeOnlyFromMergeGateTest` прогнан как есть, зелёный).
- Инвариант 14 (kill switch срабатывает всегда) — требование 9
  реализовано ОТСУТСТВИЕМ кода: `cmd_reject`/`cmd_kill` не импортируют
  и не зовут `merge_lock` вовсе, им физически неоткуда ждать чужого
  мьютекса. AC-5 проверяет это сквозным путём.
- Инвариант 19 (зелёный CI обязателен для merge) — не ослабляется:
  `"pulled"` явно НЕ доходит до сверки CI/checkout/merge в этом же
  вызове (требование 5) — новый head обязан заново пройти CI, тот же
  принцип, на котором уже стоял T051 для входа в гейт, теперь и внутри
  самого окна.
- `LIMIT_REVIEW_ITERS`/`LIMIT_ACCEPT_REJECTS` (T052) — не трогаются:
  подтяжка внутри окна не создаёт нового цикла ревью/приёмки, задача
  просто остаётся на `merge_gate` тем же гейтом.
- Обратная совместимость AC-4/AC-8 (T045 AC-8, T052 AC-2/AC-7): весь
  существующий набор (763 теста) прогнан после правки — зелёный без
  единой правки существующего теста, кроме двух мест `_pull_main_or_
  escalate`, где `if ...:` заменено на `== "escalated"` (то же
  булево условие, другая форма записи — `tests/test_branch_freshness_
  gate.py` не тронут и прогоняется как есть).
- Откат: `merge_lock.py` — новый файл (удаляется целиком), правки
  `store.py`/`fsm.py`/`doctor.py` — точечные добавления без замены
  существующих веток (кроме возврата `_pull_main_or_escalate` — правится
  обратно тем же diff `git revert`).

## Риски

- Таблица `merge_locks` не несёт PK/UNIQUE — единственность строки
  держится ТОЛЬКО дисциплиной `store.set_merge_lock` (DELETE+INSERT
  одной транзакцией). Прямая запись в обход этой функции (ручной SQL,
  будущая миграция) может завести вторую строку молча — `merge_lock_row`
  тогда вернёт первую попавшуюся без предупреждения. Схема зафиксирована
  залоченными приёмочными (`_mutex_sandbox.py`) буквально в этом виде —
  добавить PK вне этой задачи, отдельным решением, если понадобится
  укрепить инвариант на уровне БД.
- `_holder_is_dead` на чужом host решает только по heartbeat (pid чужой
  машины не проверить) — держатель на чужом host с ещё не протухшим
  heartbeat (< 2 часов) блокирует merge до истечения порога, даже если
  его процесс уже мёртв. Тот же компромисс, что уже принят `lease`/
  `doctor.check_leases` (SPEC T044) — не новый риск этой задачи.
