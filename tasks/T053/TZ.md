# ТЗ: Merge queue: мержи строго по одному

## Контекст

Роадмап §4 п.2а, четвёртый (последний перед N=2) шаг контура
параллельности: merge queue. Формулировка роадмапа (§2 B4 и §4 п.2а):
«merge_gate исполняется строго по одному, обновление ветки от main +
прогон приёмочных — в той же операции, что и merge».

Что уже есть: CAS-переходы (T050) — двойной переход невозможен на
уровне БД; сверка свежести (T051) — на гейт приезжает срез,
совместимый с main НА МОМЕНТ входа в merge_gate; возврат из
merge_gate (T052) — конфликт мержа и reject штатно возвращают в
разработку. Остались две дыры для N=2:
1) два процесса могут исполнять merge-окно ОДНОВРЕМЕННО для разных
   задач — гонка за main (обе прошли CAS своих задач, обе зовут
   checkout/pull/merge в главной копии);
2) пока задача стояла на гейте (ждала CI и Оператора), сосед мог
   смержиться — merge пройдёт по срезу, который уже не проверен
   против нового main.

## Решение (принято Оператором 27.08, §4 п.2а)

1. Глобальный мьютекс merge-окна. Ветка `merge_gate` команды approve
   (вся операция: сверка CI → checkout main → pull → merge → done)
   исполняется под глобальной блокировкой «merge» в БД — по образцу
   lease T044 (строка-замок с session_id/pid/heartbeat; взятие
   атомарно средствами SQLite). Держатель один на весь пульт, не на
   задачу. Вторая сессия, пришедшая с approve merge_gate, получает
   немедленный вежливый отказ с именем держателя и задачей («merge
   занят: T0xx, сессия ...») — без ожидания в цикле. Освобождение —
   гарантированное, при любом исходе операции (успех, отказ CI,
   конфликт, sys.exit) — по образцу try/finally в cmd_approve/lease.
   Мёртвый держатель (pid не жив) — та же деградация, что у lease:
   doctor видит, взятие перешагивает замок мёртвого процесса.
2. Сверка свежести ВНУТРИ окна. Под мьютексом, до сверки CI: если
   ветка задачи отстала от main — оркестратор подтягивает её
   механикой T051 (merge main в ветку в worktree + прогон приёмочных)
   и НЕ мержит в этом же вызове: head ветки изменился, зафиксированный
   sha честно инвалидирован, инвариант 19 (merge только по зелёному
   CI головного коммита) не ослабляется. Команда завершается
   сообщением: ветка подтянута, новый head <sha>, нужен зелёный CI
   нового head и повторный approve. Задача остаётся в merge_gate.
   Исходы конфликта подтяжки и красных приёмочных — ровно те же, что
   заданы T051/T052 (возврат in_dev / escalated, main чист).
3. Ветка не отстала — merge исполняется как сейчас, целиком под
   мьютексом; поведение вне конкуренции байт-в-байт прежнее.
4. reject и kill из merge_gate мьютекс merge не берут — они не мержат
   и не должны ждать чужой merge (kill обязан срабатывать всегда,
   инвариант 14).
5. Инварианты 12 (ред. ADR-0006), 14, 15, 19 остаются истинными.
   Прогон приёмочных при подтяжке — в worktree ветки, main не
   трогается ничем, кроме самого merge под мьютексом.

## Границы

- Только orchestrator/ (fsm, lease/store и смежные), тесты, карта.
- Схема БД: допускается строка/таблица замка по образцу leases —
  это и есть ожидаемая реализация; иных изменений схемы нет.
- Не ослаблять существующие тесты/гейты/инварианты (ADR-0002).

## Не входит

- N=2 (параллельные задачи в двух сессиях) — следующий шаг: он
  включается ПОСЛЕ этой задачи и отдельного решения Оператора.
- verifying/await-ci (B1b) — очередь не ждёт CI сама, она честно
  отказывает до зелёного CI нового head.
- patch-id-фиксация approve (устойчивость вердикта к rebase) — если
  developer упрётся в то, что без неё подтяжка на гейте генерирует
  лишний круг re-approve, зафиксировать фактуру в PLAN/эскалации;
  реализация — отдельным решением Оператора.
- Автопуш подтянутой ветки в origin (пуш — операторское действие).

## Приёмка (минимум)

- Два конкурентных approve из merge_gate (разные задачи): ровно один
  исполняет merge-окно; второй — немедленный отказ с держателем;
  после освобождения повтор проходит.
- Мьютекс освобождается при любом исходе окна: успех, красный CI,
  конфликт подтяжки, красные приёмочные (проверить хотя бы успех и
  один отказный путь).
- Задача отстала от main на гейте → подтяжка + приёмочные под
  мьютексом, merge НЕ выполняется, задача остаётся в merge_gate,
  сообщение содержит новый head; после зелёного CI нового head
  повторный approve мержит.
- Задача не отстала → merge байт-в-байт как до этой задачи.
- kill и reject из merge_gate работают при занятом мьютексе.
- Замок мёртвого держателя не блокирует merge навечно.
- Существующие тесты зелёные без ослаблений.
