# SPEC: Merge queue: мержи строго по одному

## Контекст

Роадмап §4 п.2а, четвёртый (последний перед N=2) шаг контура
параллельности: merge queue. Уже есть CAS-переходы (T050), сверка
свежести ветки на входе гейта (T051) и штатный возврат из merge_gate
при конфликте/reject (T052). Остаются две дыры для N=2: (1) два
процесса могут одновременно исполнять merge-окно для разных задач —
гонка за main; (2) пока задача стояла на гейте, main мог уйти вперёд,
и merge пройдёт по срезу, уже не проверенному против нового main.
Решение принято Оператором 27.08 (роадмап §4 п.2а).

## Требования

1. Merge-цикл команды `approve` из состояния `merge_gate` — переход
   `merge_gate -> done`
   (вся операция: сверка CI → checkout main → pull → merge → done)
   исполняется под глобальным мьютексом «merge» в БД, реализованным
   строкой/таблицей замка по образцу lease (T044): session_id/pid/
   hostname/heartbeat, взятие атомарно средствами SQLite (по образцу
   `BEGIN IMMEDIATE` в `lease.acquire`).
2. Держатель мьютекса один на весь пульт (не на задачу и не на
   target). Вторая сессия, вызвавшая `approve` из `merge_gate`, пока
   мьютекс занят другой сессией, получает немедленный именованный
   отказ (без ожидания/цикла) с указанием держателя (session_id)
   и задачи, которую он держит.
3. Мьютекс освобождается гарантированно при любом исходе операции
   окна — успех merge, отказ по красному CI, конфликт подтяжки,
   красные приёмочные тесты, `sys.exit` — по образцу try/finally
   в `cmd_approve`/`lease`.
4. Мёртвый держатель (протухший heartbeat / неживой pid — по
   аналогии с lease) не блокирует merge навечно: взятие мьютекса
   перешагивает замок мёртвого держателя; `doctor` детектирует
   мёртвого держателя тем же приёмом, что действующий `check_leases`
   (SPEC T044, требование 11).
5. Под мьютексом, до сверки CI: если ветка задачи отстала от main,
   оркестратор выполняет подтяжку механикой T051 (merge main в ветку
   задачи в её worktree + прогон приёмочных тестов задачи) и НЕ
   выполняет merge в main в этом же вызове — head ветки изменился,
   зафиксированный sha инвалидирован, инвариант 19 не ослабляется.
6. После успешной подтяжки под мьютексом задача остаётся
   в `merge_gate`; команда `approve` завершается сообщением с новым
   head ветки и требованием зелёного CI этого нового head перед
   повторным `approve`.
7. Исходы конфликта подтяжки и красных приёмочных тестов внутри окна
   `merge_gate` — те же переходы, что заданы T051/T052 (возврат
   `in_dev`/`escalated`); main не изменяется.
8. Если ветка задачи не отстала от main на момент взятия мьютекса,
   merge выполняется как до этой задачи — поведение вне конкуренции
   байт-в-байт прежнее.
9. `reject` и `kill` из `merge_gate` НЕ берут мьютекс merge — они не
   мержат и не должны ждать освобождения чужого merge-окна (инвариант
   14: kill switch срабатывает всегда).
10. Инварианты 12 (ред. ADR-0006), 14, 15, 19 остаются истинными.
    Прогон приёмочных при подтяжке выполняется в worktree ветки
    задачи; main не изменяется ничем, кроме самого merge под
    мьютексом.
11. Изменения — только в `orchestrator/` (`fsm.py`, `lease.py`,
    `store.py` и смежные модули), тестах и карте кодовой базы. Схема
    БД: допускается новая строка/таблица замка по образцу `leases` —
    иных изменений схемы нет.

## Критерии приёмки

AC-1. Два конкурентных `approve` из `merge_gate` для разных задач:
ровно один исполняет merge-окно; второй получает немедленный отказ
с именем держателя (session_id) и задачей, которую он держит; после
освобождения мьютекса повторный `approve` второй задачи проходит.

AC-2. Мьютекс освобождается при любом исходе окна — проверены как
минимум успешный merge и один отказный путь (красный CI, конфликт
подтяжки или красные приёмочные) — после которого мьютекс свободен
для следующего взятия.

AC-3. Задача отстала от main на входе в merge-окно → под мьютексом
выполняется подтяжка (merge main в ветку задачи + прогон приёмочных)
и merge в main НЕ выполняется; задача остаётся в `merge_gate`;
сообщение команды содержит новый head ветки; после зелёного CI нового
head повторный `approve` выполняет merge.

AC-4. Задача не отстала от main → переход `acceptance -> merge_gate`
и сам merge выполняются в точности как до этой задачи (байт-в-байт
прежнее поведение).

AC-5. `kill` и `reject` из `merge_gate` выполняются успешно, пока
мьютекс merge занят другой сессией (не ждут его освобождения).

AC-6. Мьютекс с мёртвым держателем (протухший heartbeat/неживой pid)
не блокирует merge навечно: следующее взятие перешагивает замок
мёртвого держателя.

AC-7. Существующие тесты (включая `test_invariants.py` и тесты T050/
T051/T052) остаются зелёными без ослабления существующих тестов,
гейтов, лимитов, guard-проверок и инвариантов (ADR-0002).

## Не входит

- N=2 (параллельные задачи в двух сессиях) — следующий шаг контура
  параллельности; включается ПОСЛЕ этой задачи отдельным решением
  Оператора.
- verifying/await-ci (B1b) — очередь не ждёт CI сама, она честно
  отказывает до зелёного CI нового head.
- patch-id-фиксация approve (устойчивость вердикта к rebase) — если
  developer упрётся в то, что без неё подтяжка на гейте генерирует
  лишний круг re-approve, зафиксировать фактуру в PLAN/эскалации;
  реализация — отдельным решением Оператора.
- Автопуш подтянутой ветки в origin (пуш — операторское действие).
- Изменение схемы БД сверх строки/таблицы замка по образцу `leases`;
  изменение `roles.yaml`, `targets.yaml`, `.github/`, `templates/`,
  `skills/`.
