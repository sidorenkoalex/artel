# SPEC: Свежий вердикт ревью после возврата

## Контекст
Найдено при тестовом прогоне T001: после отказа приёмки (`reject`)
задача возвращается в in_dev, но REVIEW.md сохраняет status: approved
с прошлой итерации. Последующие `advance` провозят задачу
in_dev → review → acceptance мгновенно, без нового прогона ревьювера —
исправленный после отказа код уезжает к мержу неревьюженным. Это дыра
в инварианте «каждый MR проходит ревью».

## Требования
1. Один вердикт ревьювера учитывается конечным автоматом ровно один раз:
   после возврата задачи в in_dev (по changes_requested или по отказу
   приёмки) переход review → acceptance невозможен по прежнему REVIEW.md —
   только по новому вердикту (следующий номер итерации).
2. При отказе перехода из-за устаревшего вердикта оркестратор печатает
   понятное сообщение (что ждёт нового прогона ревьювера) и пишет причину
   в журнал шагов.
3. Существующий счётчик итераций ревью и его лимит не меняются.
4. Логика покрыта юнит-тестами в tests/: сценарий «reject приёмки →
   старый approved не провозит» и позитивный «новый вердикт провозит».

## Критерии приёмки
1. Сценарий: review(approved) → acceptance → reject → in_dev →
   advance → review → advance НЕ переводит в acceptance, в выводе —
   сообщение о необходимости свежего вердикта.
2. После записи в REVIEW.md нового вердикта (iteration увеличен,
   status: approved) advance переводит в acceptance как обычно.
3. `python3 -m unittest discover -s tests` зелёный, включая тесты
   из требования 4.
4. guard и CI зелёные.

## Не входит
- Очистка каталога задачи при kill (отдельная задача).
- Запись stdout агента в файл по ходу шага (отдельная задача).
- Изменение лимитов и схемы состояний FSM.
