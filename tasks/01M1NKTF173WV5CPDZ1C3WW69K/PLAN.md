# PLAN: Артефакты роли — из артефактной ветки на старте шага (регрессия A7 №9)

## Подход

Три независимых, но родственных дефекта одного класса («артефактная
ветка — не единственный источник истины по `tasks/<id>/` в течение
шага») лечатся тремя точечными правками плюс одной guard-проверкой:

1. **Материализация на старте шага (требования 1, 2, AC-1/AC-2/AC-3/
   AC-8).** `orchestrator/artifact_branch.py` получает новую функцию
   `materialize_task_dir(task_id, dest_root)` — тем же git-приёмом, что
   `acceptance.materialize_from_branch` (`ls_tree_files`/`show`), но
   пишет НА МЕСТЕ и убирает файлы, отсутствующие в ветке (не только
   дописывает). Голова ветки читается ОДИН раз в начале и используется
   как ревизия для обоих git-чтений — атомарный снимок. `runner.
   role_cwd` зовёт её сразу после вычисления `path` (для self И для
   внешнего target — общий финальный блок, не дублирование по ветвям)
   и сохраняет sha использованной головы в новую колонку БД `tasks.
   materialized_artifact_sha` (не в файл диска — тот `commit_step_
   artifacts` стирает `shutil.rmtree`'ом в конце шага, колонка
   переживает). `task_id is None` (офлайн-смоук изоляции, `doctor.
   isolation_smoke` зовёт `role_cwd(None, None, ...)`) — материализация
   пропускается тихо, той же деградацией, что и отсутствие ветки.
   `brief.developer_brief` дополнена компонентами PLAN.md/REVIEW.md
   (`_plan_review_components`, тем же приёмом `_manifest_component`,
   что уже несёт SPEC.md) — общий источник `_branch_or_disk_text`, уже
   существующий для ANSWER/QUESTIONS.

2. **Конфликт-гвард автокоммита (требование 4, AC-6/AC-7).**
   `checkpoint._commit_external_step_artifacts` читает `tasks.
   materialized_artifact_sha` как baseline. Для каждого файла, который
   есть и на диске, и в текущей ветке: если диск совпадает с
   содержимым файла на baseline (роль его не трогала), а текущая ветка
   разошлась с baseline (правка Оператора между стартом и концом шага)
   — файл исключается из переноса, заводится `alerts.raise_alert(...,
   "incident", ...)` с текстом «конфликт артефактов: правка в ветке
   новее рабочего каталога — <путь>». Файл, реально изменённый ролью
   (диск ≠ baseline), конфликта не ловит — коммитится как обычно;
   конфликт по одному файлу не трогает остальные (общий `files`,
   поэлементное исключение, не ранний `return`).

3. **Лок удаления `acceptance_tests/` до фиксации (требование 7,
   AC-13/AC-14/AC-15).** Тот же цикл `_commit_external_step_artifacts`,
   который уже удаляет `type: questions` по сигналу «последний коммит
   пути — автокоммит этой же роли»: второе условие удаляемости —
   `role == "test_author"`, `t["state"] == "tests_writing"`,
   `not t["tests_locked_sha"]`, путь под `acceptance_tests/`. Не
   расширяет `_DELETABLE_ARTIFACT_TYPES` (тот остаётся только
   `{"questions"}` — `type` там читается из frontmatter, у .py-тестов
   его нет вовсе), а добавляет параллельную ветку `deletable` рядом.
   После лока (`tests_locked_sha` не пуст) ветка не срабатывает —
   прежнее поведение остаётся неизменным (AC-14). Цикл уже проходит по
   ВСЕМ кандидатам `set(existing) - set(files)` без `break` — несколько
   удалений одним шагом уже работают (AC-15) без дополнительной правки
   структуры цикла.

4. **Эскалация только статусом escalate (требование 6, AC-11/AC-12).**
   `scripts/guard.py`: `RULES["plan"]["statuses"]` получает `"escalate"`
   (наравне с уже валидным для `review`). Новая функция
   `escalation_status_errors(path, text, meta)` — для `type` в
   {plan, review, spec}, `status != escalate`, раздел `## Эскалация` на
   месте — читает подсекции «Вопросы»/«Блокирует» тем же приёмом, что
   `section_body` уже использует для остальных секций (headers
   регэкспом, `##` уровень), и признаёт нарушение, если хоть одна из
   двух непуста. Подключена в `check_content` безусловно (не только
   для новых типов) — существующие PLAN/REVIEW/SPEC без раздела
   «Эскалация» не задеты (AC-11, негативный тест).

5. **Тексты миссии и скилов без «прочитай ...SPEC.md» и без инструкции
   роли коммитить `tasks/<id>/` (требования 2, 3, AC-4, AC-5).**
   `orchestrator/role_prompt.py` — прямая правка (не защищённый путь):
   test_author больше не получает «Прочитай {task_ref}/SPEC.md», вместо
   этого — «на диске актуальная версия (материализована...)»; developer
   уже был зелёным по AC-4 (не трогает). Все четыре мисси (analyst/
   test_author/developer/reviewer) перестают инструктировать «закоммить
   ... в ветку» для `tasks/<id>/` — только код (developer) коммитится
   по-прежнему, артефакт переносит автокоммит оркестратора. Правка
   `skills/conventions-core.md`/`spec-authoring.md`/`test-authoring.md`
   (защищённый путь) — диф-приложение ниже, применяет Оператор;
   `review-checklist.md` не несёт инструкции коммита артефакта — правка
   не нужна (проверено `grep`, см. «Влияние на систему»).

## Шаги

1. `orchestrator/store.py`: колонка `tasks.materialized_artifact_sha`
   (миграция `add_column`).
2. `orchestrator/artifact_branch.py`: `materialize_task_dir`.
3. `orchestrator/runner.py`: `role_cwd` зовёт материализацию, пишет
   колонку; тихая деградация без ветки/при `task_id is None`.
4. `orchestrator/checkpoint.py`: конфликт-гвард (AC-6/AC-7) + лок
   удаления `acceptance_tests/` до фиксации (AC-13/AC-14/AC-15) в
   `_commit_external_step_artifacts`.
5. `scripts/guard.py`: `"escalate"` в `RULES["plan"]`,
   `escalation_status_errors` + подключение в `check_content`.
6. `orchestrator/brief.py`: `_plan_review_components`, подключение в
   `developer_brief`.
7. `orchestrator/role_prompt.py`: тексты миссий (AC-4 test_author; без
   инструкции коммита `tasks/<id>/` во всех четырёх).
8. Юнит-тесты новых чистых кусков (`tests/test_artifact_materialization.py`)
   + прогон приёмочных тестов задачи и полного набора `tests/`.
9. Диф-приложение по `skills/` (см. ниже) — Оператору для отдельного MR.

## Влияние на систему

- `runner.role_cwd` — одна из самых широко используемых функций пульта
  (вызывается из каждого агентного шага и из `doctor.isolation_smoke`).
  Новый блок материализации гейтится `if task_id is not None:` —
  единственный вызыватель с `task_id=None` (`doctor.isolation_smoke`,
  синтетический target) не задет. Для остальных вызывателей
  материализация — не-op при отсутствии артефактной ветки (`gitcmd.
  branch_head_sha` возвращает "" для несуществующей ветки/при отказе
  git) — тихая деградация тем же приёмом, что и весь остальной модуль;
  проверено прогоном полного набора `tests/` (см. «Проверено
  исполнением» будет в REVIEW).
- `checkpoint._commit_external_step_artifacts` — конфликт-гвард
  активируется ТОЛЬКО когда `tasks.materialized_artifact_sha` не пуст
  (то есть только для задач, у которых `role_cwd` реально
  материализовал диск на этом шаге) — старые/легаси-сценарии, где
  `role_cwd` не звался (часть существующих тестов пишет прямо в
  `workspace_task_dir()` в обход `role_cwd`), остаются с baseline
  `NULL` и ведут себя байт-в-байт как до этой задачи. Лок удаления
  `acceptance_tests/` до фиксации — новая ветка `deletable`, СТРОГО
  сузенная тремя условиями (роль, состояние, пустой лок) — не меняет
  `_DELETABLE_ARTIFACT_TYPES` и не трогает поведение после лока (AC-14
  подтверждает регрессионным тестом).
- `scripts/guard.py` — `RULES["plan"]["statuses"]` расширен добавлением
  значения, не заменой множества: существующие PLAN.md со статусами
  draft/ready/approved проходят как раньше. Новое правило
  `escalation_status_errors` активируется только при наличии раздела
  `## Эскалация` с непустыми «Вопросы»/«Блокирует» — обычный PLAN/
  REVIEW/SPEC без этого раздела не задет (AC-11, негативный тест
  `test_ac11_plan_without_an_escalation_section_is_not_flagged`).
- `brief.developer_brief` — новые компоненты PLAN.md/REVIEW.md
  добавляются в конец списка `parts` (после карты/конвенций, до
  ANSWER) — увеличивает размер брифа developer на два компонента,
  каждый уже проходит существующую дисциплину `_manifest_component`
  (потолок файла/части, AC не меняется). Компонента нет (PLAN.md ещё
  не написан на первом шаге, REVIEW.md — до первого ревью) — пустая
  строка, бриф не растёт (тот же приём, что ANSWER/QUESTIONS).
- `role_prompt.py` — правка только текста промпта (f-строки), логика
  сборки (`mission_brief_package`) не меняется; `grep -rn "Закоммит"
  skills/*.md` подтвердил, что только `spec-authoring.md`/
  `test-authoring.md` несут инструкцию коммита — `review-checklist.md`
  её не несёт, правка туда не нужна.
- Откат: все правки — независимые точечные добавления (новая колонка
  БД с `NULL` по умолчанию, новая функция, новая ветка условия) без
  удаления существующего кода — `git revert` коммита(ов) этой задачи
  возвращает прежнее поведение полностью, миграция колонки безопасна
  (лишняя `NULL`-колонка в схеме не мешает старому коду).
- Никакой существующий тест, гейт, лимит или guard не ослаблен и не
  удалён — только новые проверки/расширения enum'а. Полный набор
  `tests/` прогнан зелёным (см. REVIEW «Проверено исполнением»).

## Предложения системе

- Класс «конфликт-гвард нужен там, где источник истины материализуется
  на диск на старте шага, а меняться может извне за время шага» —
  сегодня решён локально в `checkpoint.py` через новую колонку БД
  `materialized_artifact_sha`. Если появится второй подобный сценарий
  (не `tasks/<id>/`, а другой материализуемый ресурс) — стоит вынести
  «сравнить диск/baseline/текущее» в отдельную маленькую функцию
  `fixation.py`/`artifact_branch.py`, а не копировать цикл ещё раз.

## Диф-приложение: `skills/conventions-core.md`, `skills/spec-authoring.md`, `skills/test-authoring.md`

Защищённый путь (`skills/`) — применяет Оператор отдельным MR
(`skills/conventions-core.md`, «Никогда: ... правка ... `skills/`»).
Убирает из трёх скилов инструкцию «Артефакты коммитятся в ту же ветку
задачи вместе с кодом» / «Закоммить файл/каталог в ветку задачи»
(требование 3 SPEC — роли больше не коммитят `tasks/<id>/` в кодовую
ветку, единственный путь артефактов в git — автокоммит оркестратора в
артефактную ветку) и добавляет в `conventions-core.md` короткую
заметку про материализацию `tasks/<id>/` на старте шага (требование 1).
`review-checklist.md` инструкции коммита артефакта не несёт — в дифе не
участвует (проверено `grep -n "рочитай\|Закоммит\|акоммит" skills/*.md`
перед подготовкой дифа).

`git apply --check` на чистом дереве (skills/ не тронут этой веткой
напрямую — подтверждено `git status --short skills/`, пусто) —
