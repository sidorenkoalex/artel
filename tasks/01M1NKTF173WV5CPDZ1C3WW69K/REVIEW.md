## Замечания

- **blocker** — `orchestrator/runner.py:448-452` (`role_cwd`) вместе с `orchestrator/checkpoint.py:31-138` (`commit_timeout_checkpoint`, `commit_abnormal_checkpoint`, `commit_pause_now_checkpoint`) — материализация `tasks/<id>/` для self-target пишет файлы ПРЯМО в git-worktree КОДОВОЙ ветки задачи (`workspace.path(task_id)` — тот же путь, что и `runner.role_cwd` возвращает для self, `path = wt_path`). Эти три WIP-чекпоинтные функции (существовали до этой задачи, не тронуты диффом) на таймауте/аварийном завершении шага/`pause --now` безусловно делают `git add -A` + `commit` по всему этому worktree (`_commit_worktree_change`, `checkpoint.py:405-417`) — `.gitignore` пульта каталог `tasks/<id>/` не исключает (проверено `cat .gitignore` — записи `tasks` нет). В результате только что материализованные, ещё НИЧЕМ не изменённые ролью файлы `tasks/<id>/` (например, SPEC.md) попадают commit'ом в КОДОВУЮ ветку `task/*` — ровно то, что требование 3 и AC-9 явно запрещают («единственный путь артефактов в git остаётся автокоммитом оркестратора в артефактную ветку»). Сценарий поломки: шаг developer стартует (role_cwd материализует SPEC.md/PLAN.md на диск worktree'а), агент виснет и ловит таймаут (частый случай — session limit, зависший инструмент) — `commit_timeout_checkpoint` коммитит `tasks/<id>/SPEC.md` в `task/*` до того, как роль вообще успела что-то написать. Живьём воспроизведено юнит-тестом (сценарий: `artifact_branch.commit_files` сеет SPEC.md в артефактную ветку → `runner.role_cwd` материализует его в worktree self-target'а → `checkpoint.commit_timeout_checkpoint` → `git ls-tree -r HEAD` worktree'а после чекпоинта содержит `tasks/<TASK>/SPEC.md`). PLAN «Влияние на систему» разбирает только `_commit_external_step_artifacts` — про эти три функции не сказано ни слова, взаимодействие явно не рассмотрено. Предложение: либо материализация для self-target не должна писать `tasks/<id>/` внутрь git-worktree кодовой ветки (материализовать в отдельный каталог вне дерева, которое коммитят WIP-чекпоинты), либо `_commit_worktree_change`/сами WIP-чекпоинты обязаны исключать `tasks/<task_id>/` из `git add -A` (например, добавить его в `.gitignore` worktree'а или явно `reset` путь после `add -A`) — класс один и тот же для всех трёх функций, чинить нужно все три, не одну.

- **blocker** — `orchestrator/store.py:211` (`migrate`) — новая колонка `materialized_artifact_sha` добавлена ТОЛЬКО через `add_column` в `migrate()`, но, в отличие от КАЖДОЙ предыдущей колонки того же списка (`reviewed_iter`, `verifying_attempts`, `draft_mr_created` и т.д. — все они уже есть в самом `CREATE TABLE tasks` базовой `SCHEMA`, `store.py:32-37`), в `CREATE TABLE tasks` она не добавлена. Из-за этого на свежей БД (как в тестовой песочнице) `add_column` каждый раз реально идёт по ветке `ALTER TABLE` (`table_columns` не находит колонку), а сама проверка «есть/нет» (`store.py:145-150`) не атомарна с самим `ALTER TABLE` — классический TOCTOU без блокировки. При параллельных вызовах `store.db()` (что штатно происходит, например, в `catalog.cmd_new` под конкурентным `take()`, tests/test_multitarget.py) несколько потоков одновременно видят «колонки нет» и одновременно шлют `ALTER TABLE ... ADD COLUMN materialized_artifact_sha` — все, кроме первого, падают необработанным `sqlite3.OperationalError: duplicate column name`, прямо в потоке, без отлова. Последствие — существующий немодифицированный тест `tests/test_multitarget.py::TaskNumberingTest::test_two_callers_at_once_do_not_get_the_same_number` падает: `AssertionError: 0 != 4` (все 4 конкурентных `take()` тихо потеряли исключение потока и не записали номер). Воспроизведено трижды подряд отдельным прогоном именно этого теста (`python3 -m unittest tests.test_multitarget.TaskNumberingTest.test_two_callers_at_once_do_not_get_the_same_number`), не разовая случайность. Это прямое нарушение AC-10/требования 5 («ни один существующий тест... не ослаблен»; тест не «ослаблен» текстом, но сломан фактически) и явное расхождение с заявленным в PLAN «Влияние на систему» — «полный набор `tests/` прогнан зелёным». Предложение: добавить `materialized_artifact_sha TEXT` прямо в `CREATE TABLE tasks` (`store.py:32-37`), как сделано для всех прежних колонок миграции — тогда `add_column` на свежей БД становится no-op и race не воспроизводится; либо (менее предпочтительно, раз конвенция файла — переносить старые колонки в SCHEMA) обернуть `add_column` в `try/except sqlite3.OperationalError` по тексту «duplicate column name» — но это лечит симптом только для этой колонки, не класс.

## Предложения системе

- Класс «WIP-чекпоинт таймаута/аварийного завершения (`commit_timeout_checkpoint` и парой) — это безусловный `git add -A` по worktree'у self-target, написанный до A7/до материализации артефактов» — теперь конфликтует с ЛЮБЫМ будущим кодом, который тоже пишет на диск того же worktree'а вне контроля роли (не только `tasks/<id>/`). Стоит явно задокументировать в `checkpoint.py`, что этот worktree — не «только то, что написала роль», и любая новая механика, кладущая файлы туда, обязана либо исключать себя из `add -A`, либо не жить в этом дереве.
- Класс «новая колонка `tasks.*` добавлена только в `migrate()`, без переноса в `CREATE TABLE tasks`» — конвенция файла явно другая (каждая прежняя колонка миграции присутствует в обеих местах), но нигде не записана как правило; отступление от неё тихо возвращает старый race `add_column`. Стоит явно зафиксировать в докстринге `store.migrate`/`add_column`, что новая колонка обязана попадать в `CREATE TABLE` тоже, а не только в цепочку `add_column`.
