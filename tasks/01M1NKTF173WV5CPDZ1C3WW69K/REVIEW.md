## Замечания

- **blocker** — `orchestrator/checkpoint.py:255` (`commit_abnormal_checkpoint`) и `orchestrator/checkpoint.py:288` (`commit_pause_now_checkpoint`) — обе функции вызывают `_commit_worktree_change(wt, message)` БЕЗ `exclude` и без разбора роли (мандат-ветвление, которое `commit_timeout_checkpoint` получил из main, здесь отсутствует вовсе). `runner.role_cwd` материализует `tasks/<id>/` из артефактной ветки в ТОТ ЖЕ git-worktree кодовой ветки для КАЖДОЙ роли (self-target, `target == config.DEFAULT_TARGET` — общий блок без разбора роли, `orchestrator/runner.py:439-452`), поэтому на аварийном завершении шага (`rc != 0`, обрыв stdout-пайпа) или на `pause --now` — для ЛЮБОЙ роли, включая `analyst`/`test_author`/`reviewer`, у которых нет мандата кода вовсе — свежематериализованные, ещё ничем не изменённые ролью файлы `tasks/<id>/` (SPEC.md и т.д.) коммитятся в КОДОВУЮ ветку `task/*`. Это ровно требование 3/AC-9 («единственный путь артефактов в git остаётся автокоммитом оркестратора в артефактную ветку») — только автоматикой оркестратора, не рукой роли, тот же класс, что итерация 1 блокировала под R1-F1 для всех трёх WIP-чекпоинтов («класс один и тот же для всех трёх функций, чинить нужно все три, не одну»). Подтверждено исполнением (не мнением): юнит-тест-репродукция (`role_cwd` материализует SPEC.md в worktree self-target → `commit_abnormal_checkpoint(conn, TASK, "reviewer", "rc=1")` → `git ls-tree -r HEAD` worktree'а после чекпоинта содержит `tasks/<TASK>/SPEC.md`) воспроизводит дефект стабильно для `commit_abnormal_checkpoint` и отдельно для `commit_pause_now_checkpoint` с ролью `reviewer` (см. «Проверено исполнением»). PLAN относит это к «расширение мандата на эти два пути — вне зоны этой задачи» (раздел «Подтяжка origin/main», «Разрешение») — но это не сужение зоны Оператором через эскалацию, а собственное решение разработчика; ANSWER-1 говорит только о том, ЧЬЮ реализацию конфликта взять за базу (main вместо дубля с `task_id`), а не о том, что дефект для двух из трёх чекпоинтов остаётся незакрытым. Ни приёмочный AC-9 (тестирует только `commit_step_artifacts`, happy path), ни новый `RoleCwdMaterializationSurvivesTimeoutCheckpointTest` (тестирует только `commit_timeout_checkpoint`) этот класс не ловят — пробел в покрытии, не только в коде. Предложение: та же правка, что уже применена к `commit_timeout_checkpoint` (мандат-ветвление `developer`/`_discard_out_of_mandate_changes`, либо `exclude=f"tasks/{task_id}"` для случаев, где WIP вне `tasks/<id>/` всё равно должен закоммититься) — для `commit_abnormal_checkpoint` и `commit_pause_now_checkpoint` тоже; если Оператор решит, что расширение мандата на эти два пути действительно вне зоны этой задачи — это требует явной эскалации с ANSWER Оператора, а не одностороннего решения разработчика в PLAN.
