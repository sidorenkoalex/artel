ANSWER-n.md у задачи нет, раздела «Решения Оператора на гейте SPEC» в брифе нет.

Не подтвердилось или неточно:
1. SPEC.md:151-152, «Не входит»: «отсутствие сравнения `forge` с литералами …
   держит долгоживущий сторож А0». Сторож исключает поимённо именно
   `("doctor/misc_checks.py", "check_base_branch")`
   (tests/test_01m5w27cy7k7nr9347nkd8f0nx_unsupported_project.py:416-421)
   и ловит только `ast.Compare` (:461-466). Ветку
   `if entry.get("forge") == "gitlab":` внутри `check_base_branch` сторож не
   увидит, как и `match`/`case "gitlab"` где угодно. Для новой функции строки
   срока токена (её нет в исключениях) утверждение верно.
2. SPEC.md:129, матрица, «без токена … по-прежнему `skip`»; ТЗ: «токена нет,
   поэтому `skip`». `forge.*` читает запись по имени через `targets.target`
   (forge.py:173, gitlab_adapter.py:221, :275), а не по переданному `entry`.
   `BaseBranchCheckTest` не подменяет `config.TARGETS` (tests/test_doctor.py:639-649).
   Поэтому `"sled"` либо не объявлен (`TargetsError` → причина «запись проекта
   не прочитана»), либо читается из настоящего targets.yaml пульта. Даже для
   записи из теста (`url: file:///…`) отказ пришёл бы раньше токена:
   «не https» (gitlab_adapter.py:131-133). Итог `skip` сохраняется в каждой
   ветке, но названная причина неверна. Ещё один момент для разработчика:
   сверяемая база берётся из переданного `entry`, а запись для хостинга — из
   `targets.target(name)`.
3. В SPEC не названо существующее обстоятельство, от которого зависит
   требование 5. Тесты части 1 `test_ac14_ci_views_follow_table`,
   `test_ac14_head_sha_local`, `test_ac15_unsupported_ci_functions_refuse`,
   `test_ac16_red_without_failed_job_names_none`
   (tests/test_01m5wcxbm7wcmrwcbwnchmar3t_gitlab_forge.py:1229, :1266, :1293,
   :1347) запрашивают фикстуру `lab` раньше `gl_clone`. `lab` подменяет
   `transport` (:227), а `gl_clone` → `real_git` → `RealGitSandbox.setUp`
   → `isolate_keychain_and_role` (tests/sandbox.py:1942). Песочница ставится
   ПОСЛЕ подмены теста. Тогда прямой `mock.patch.object(gitlab_adapter,
   "transport", …)` в помощнике перекроет транспорт теста, и эти долгоживущие
   тесты покраснеют.

## Проверяемость критериев

| Критерий | Проверяем | Ловимая мутация |
|---|---|---|
| AC-1 | да | токен (или заголовок `PRIVATE-TOKEN`) печатается в строке `doctor`/`forge-probe` |
| AC-2 | да | gitlab по-прежнему `skip`; `ok`/`warn` перепутаны; без токена зовётся транспорт. Не ловит: литерал `forge == "gitlab"` в `check_base_branch` (см. «Пути обхода») |
| AC-3 | частично | ловит: нет `warn` у близкого срока; `warn` у далёкого; `killed` идёт в счёт; без токена не `skip`. **Не ловит:** (а) границу — `<` вместо `<=` на `TOKEN_EXPIRY_WARN_DAYS` и `>` вместо `>=` на `TOKEN_NO_EXPIRY_TASKS_WARN` (AC не требует значений ровно на пороге, SPEC.md:83, :87); (б) счёт задач ВСЕХ проектов БД вместо задач этого проекта (AC не требует задач другого проекта); (в) статус строки при ошибке запроса с токеном (HTTP/сеть → `warn`/`fail` вместо `skip`) |
| AC-4 | да | нет пункта вывода; вызов записи (`open_mr`/`assign_mr` — разрешённые адаптеру POST/PUT) — ловит «все вызовы — GET»; отказ команды для неподдержанной записи |
| AC-5 | частично | песочница не подменяет транспорт (соединение на `https://localhost` → `socket.create_connection` вызван); подмена бросает не тот отказ (нет причины / `skip`). **Не ловит:** песочница перекрывает подмену, поставленную тестом ДО неё (порядок фикстур тестов части 1, «Факты» п. 3). Проверка приоритета в AC-5 (SPEC.md:107-108) порядок не задаёт, и естественный тест ставит свою подмену после песочницы. Полный прогон эту поломку поймает тестами части 1, но критерий её не держит |

## Пути обхода гейтов
1. **Литерал в исключённой функции.** Разработчик может написать
   `if entry.get("forge") == "gitlab":` в `check_base_branch`. Требование
   «без сравнения с литералами» (SPEC.md:48) формально стоит в требовании 2,
   а сторож AC-9 эту функцию исключает (тест А0:418). SPEC.md:151 отказывается
   от своего критерия, ссылаясь на сторож, так что нарушение проходит все
   проверки. То же для `match`/`case` в любой новой функции (сторож смотрит
   только `ast.Compare`).
2. **Граница порогов.** `days < TOKEN_EXPIRY_WARN_DAYS` и
   `count > TOKEN_NO_EXPIRY_TASKS_WARN` проходят AC-3, хотя требование 2 —
   «14 дней или меньше» и «не меньше порога».
3. **Счёт задач.** `len(store.all_tasks(conn))` без фильтра проекта проходит
   AC-3: в тесте один проект.
4. **Ошибка запроса у строки токена.** Любой статус при HTTP/сетевой ошибке
   (в том числе `warn` или `fail` под песочницей) не противоречит ни одному AC.
   Пример с `fail`: `doctor` красный в каждом тесте с gitlab-записью и токеном
   песочницы — это проявится, но не там, где положено.
