# SPEC: approve --note на гейте SPEC — указание Оператора для test_author и ревьювера

## Контекст
На `spec_gate` у Оператора два действия: `approve` (`fsm._approve_spec_gate`, `orchestrator/fsm.py:1337`) и `reject` (возврат аналитику, в том числе `reject --decision`); `answer` на `spec_gate` принимает только файл с мандатом (`orchestrator/answer.py:239`, `:268`), в `tests_writing` недоступен (`answer.INSTRUCTION_STATES`, `orchestrator/answer.py:216`). Уточнение к тестам, не вписанное в SPEC и не поданное мандатом, до test_author не доходит, а после его шага долгоживущие тесты закреплены (правка — только `amend-tests`). Сейчас единственный путь — возврат SPEC (круг «аналитик → аудитор» около $3 и 10–20 минут). Задача даёт Оператору канал: `approve <id> --note <файл>` пишет указание записью журнала, и оно попадает в бриф test_author и пакет ревьювера текущего прохождения гейта.

## Требования

1. Флаг `approve <id> --note <файл>` допустим только в состоянии `spec_gate`; вне его — отказ с причиной, содержащей «допустим только в состоянии spec_gate», до lease и повторно под lease (как `--as-epic`: `_as_epic_goal`, `fsm.py:1006-1027`; повтор — `fsm.py:1799-1801`). Файл обязателен, читается (образец `_read_decision_file`, `fsm.py:1934-1940`: отказ при `OSError`/`UnicodeDecodeError`) и непуст — пустым считается файл, текст которого после `strip()` пуст (образец `raw.strip()`, `orchestrator/answer.py:291`), то есть и файл только из пробелов и переводов строк; `--note` без значения или со значением, начинающимся с `--`, — отказ до lease. `--note` и его значение входят в `_approve_reason_indices` (`artel.py:2223`) и не попадают в `_approve_sha_arg` (`artel.py:2257`). Новый параметр `cmd_approve`/`_cmd_approve` — только именованный, по умолчанию `None`; без флага диспетчер (`artel.py:2696`) вызывает их без нового аргумента (приём `_approve_as_epic_kwargs`, `artel.py:2277`).
2. Отказ без записей журнала и без перехода, если хоть одна строка текста файла даёт `mandate.line_elements(строка, маркер) is not None` для любого из четырёх маркеров `mandate.MANDATE_MARKERS` (`orchestrator/advance_gates/mandate.py:55`, `:118`; цикл по маркерам, местный импорт `mandate`; `answer._has_mandate_lines` не импортируется — круг импортов `answer` → `fsm`). Подсказка в тексте отказа — по виду маркера найденной строки: для маркеров тестов (`mandate.TEST_WEAKENING_MANDATE_MARKER`, `mandate.TEST_ID_MANDATE_MARKER`) причина называет `answer <id> <файл>`; для маркеров зон (`mandate._ZONES_MANDATE_MARKER`) и зависимостей мержа (`mandate.MERGE_AFTER_MANDATE_MARKER`) причина называет, что они задаются полями SPEC и подаются возвратом `reject` (`answer` на `spec_gate` такие строки отклоняет — `orchestrator/answer.py:234-256` — и принимает только мандат тестов — `:261-268`). Отказ и тогда, когда текст начинается заголовком файла решения (`spec_gate_decision.starts_with_header`) — это файл для `reject --decision`.
3. Отказ без записей и без перехода, если `approve` поведёт задачу не в `tests_writing`: SPEC несёт деление, `skip_tests` либо SPEC без разметки AC — по тем же условиям, что `fsm.py:1486`, `:1491-1492`. Проверка — до lease чтением SPEC как в `_as_epic_goal` (без `_read_branch_text_or_refuse`, который сам пишет журнал), и повторно под lease. Мягкие отказы `approve` (`fsm.py:1350`, `:1371`, `:1389-1439`) — как сейчас: их собственная запись «approve отклонён» остаётся, указание не пишется.
4. Указание записывается отдельной записью журнала исполнителем `operator`, деталь — полный текст файла; запись делается внутри обработчика сразу после успешного `store.set_state(… "tests_writing" …)` (`fsm.py:1507`), под тем же lease. Если `set_state` бросил `CasConflict` или `DocsRefIncident` — записи нет. Действие записи — константа `fsm.SPEC_GATE_NOTE_ACTION = "указание Оператора на гейте SPEC"`: не совпадает ни с одним существующим действием и не начинается с `state -> ` (иначе её подхватят `_previous_state_name`, `brief.py:1522`, и выборки гейтов, `mandate.py:718`, `test_integrity.py:1095`). Предел размера сравнивается с размером файла в байтах (`len(Path(f).read_bytes())`, не длиной прочитанного текста: `read_text` меняет CRLF на LF): файл ровно `config.CONTEXT_FILE_MAX_BYTES` байт (`config.py:560`) принимается, на байт больше — отказ до lease.

Пакет ревьювера `review.review_package` (`review.py:770`) получает тот же текст отдельной частью сразу после цикла ANSWER-n (`review.py:969-975`), до долгоживущих файлов; только при наличии указания; набор ключей словаря пакета прежний; запись «бриф: компонент» от `reviewer` как у ANSWER (`review.py:852-861`). 8. Без `--note` поведение `approve` на `spec_gate`, бриф test_author и пакет ревьювера — прежние.

Приложения Оператора к PLAN (защищённые пути, коммит Оператора воротами мержа): `skills/test-authoring.md` и `skills/review-checklist.md` — по короткому абзацу о том, как учитывать раздел «Указание Оператора на гейте SPEC» (по образцу абзаца о ANSWER, `skills/review-checklist.md:82-85`; в `skills/review-checklist.md` абзац — элементом списка с отступом в три пробела рядом с абзацем об ANSWER). ## Критерии приёмки

AC-1. `approve <id> --note f` для задачи в `spec_gate` с SPEC с AC-разметкой без деления и без `skip_tests` переводит задачу в `tests_writing` и оставляет в журнале запись исполнителя `operator` с действием `fsm.SPEC_GATE_NOTE_ACTION`, деталь которой — полный текст файла `f`; значение `fsm.SPEC_GATE_NOTE_ACTION` — `"указание Оператора на гейте SPEC"`, оно не совпадает ни с одним прежним действием и не начинается с `state -> `.
AC-2. После AC-1 `brief.spec_gate_note(conn, task_id)` возвращает текст файла, а бриф test_author содержит раздел «Указание Оператора на гейте SPEC» с этим текстом и строкой `brief.SPEC_GATE_NOTE_PREAMBLE` (текст — по требованию 6) перед граничными маркерами, расположенный после причины возврата и ANSWER и до конвенций; в журнале — запись «бриф: компонент» для этого раздела.
AC-3. После AC-1 пакет ревьювера содержит часть с тем же текстом и строкой `review.SPEC_GATE_NOTE_PREAMBLE` (текст — по требованию 7) перед граничными маркерами, стоящую сразу после частей ANSWER-n и до долгоживущих файлов; набор ключей словаря пакета тот же, что без указания; в журнале — запись «бриф: компонент» от `reviewer`.
AC-4. `approve <id> --note f` для задачи не в `spec_gate` — отказ с причиной, содержащей «допустим только в состоянии spec_gate»; состояние, журнал и ссылка документов прежние.
AC-5. `--note` без значения, со значением, начинающимся с `--`, с несуществующим файлом, с нечитаемым файлом (ошибка чтения или декодирования), с пустым файлом и с файлом только из пробелов и переводов строк (пуст после `strip()`) — отказ с причиной; состояние, журнал и ссылка документов прежние.
AC-6. Файл, в котором хоть одна строка — строка одного из четырёх маркеров `mandate.MANDATE_MARKERS`, — отказ; проверяются четыре случая, по одному на маркер: для `mandate.TEST_WEAKENING_MANDATE_MARKER` и `mandate.TEST_ID_MANDATE_MARKER` причина называет `answer <id> <файл>`; для `mandate._ZONES_MANDATE_MARKER` и `mandate.MERGE_AFTER_MANDATE_MARKER` причина называет, что они задаются полями SPEC и подаются возвратом `reject`. Файл, начинающийся заголовком файла решения (`spec_gate_decision.starts_with_header`), — отказ. Во всех случаях состояние, журнал и ссылка документов прежние.
AC-7. Файл размером ровно `config.CONTEXT_FILE_MAX_BYTES` байт (`len(Path(f).read_bytes())`) принимается: переход в `tests_writing` и запись указания, как в AC-1; файл размером `config.CONTEXT_FILE_MAX_BYTES + 1` байт — отказ с причиной; состояние, журнал и ссылка документов прежние.
AC-8. `--note f` при SPEC с делением, с `skip_tests` и при SPEC без AC-разметки — отказ с причиной; состояние, журнал и ссылка документов прежние; в тестах этих случаев `fsm._maybe_ensure_draft_mr` подменён пустышкой (без push и `gh pr create`). При мягком отказе `approve` с `--note` в журнале есть только та же запись «approve отклонён», что и без `--note`, записи указания нет.
AC-9. Если `store.set_state` в `tests_writing` бросает `CasConflict` или `DocsRefIncident`, записи указания в журнале нет.
AC-10. Значение `--note` и сам флаг не попадают в `_approve_sha_arg`: `approve <id> --note f` и `approve <id> --note f <sha>` берут sha так же, как `approve <id>` и `approve <id> <sha>`.
AC-11. Повторное прохождение `spec_gate` той же задачей (после записи `state -> spec_gate` новее записи указания): `approve` без `--note` — `brief.spec_gate_note` возвращает `None`, раздела в брифе test_author и части в пакете ревьювера нет; `approve` с `--note` — в них новый текст. Возврат через эскалацию из `tests_writing` без нового `state -> spec_gate` указание сохраняет.
AC-12. `brief.spec_gate_note` берёт текст только из записи действия `fsm.SPEC_GATE_NOTE_ACTION` исполнителем `operator`: запись того же действия другим исполнителем и запись другого действия с тем же текстом ни `brief.spec_gate_note`, ни раздела брифа, ни части пакета не дают.
AC-13. Наличие указания не меняет последний `ANSWER-n` в брифе test_author, число ANSWER (`fsm._answer_file_count`) и номер последнего ANSWER (`fsm._latest_answer_number`), исход проверок мандатов, результат `brief._spec_gate_reasons` и прежних решений `reject --decision`.
AC-14. Справка `approve` в `orchestrator/artel.py` называет `--note`, строка продолжения — с отступом больше двух пробелов.
AC-15. Повтор проверок под lease: если после проверок до lease состояние задачи сменилось на отличное от `spec_gate` либо SPEC получил деление или `skip_tests` (тест подменяет `lease.run_locked` и меняет состояние задачи или SPEC до вызова обработчика), `approve --note` отказывает с причиной; перехода нет, записи указания нет. Случай смены состояния проверяется так: до вызова обработчика задача переводится в `escalated` с файлом `ANSWER-1.md` — состояние, где `approve` без флага выполняет переход (снятие эскалации, `_approve_escalated` в таблице обработчиков `fsm.py:1835-1848`); ожидается отказ `approve --note` с причиной, содержащей «допустим только в состоянии spec_gate», состояние остаётся `escalated`, записи указания нет (удаление повтора проверки под lease тест ловит: без него прошёл бы обычный переход из `escalated`). В тесте случая `skip_tests` `fsm._maybe_ensure_draft_mr` подменён пустышкой (без push и `gh pr create`).

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (fsm.py, artel.py, brief.py, review.py, role_prompt.py, два документа, tests/); число критериев приёмки ≥ 10 (15); `budget_usd` ≥ $30 (рамка Оператора в ТЗ — $45).

Материал для решения Оператора — обоснование монолита: механика одна — запись журнала от `approve --note` (fsm.py/artel.py) и её единственный читатель (функция `brief.py`, раздел брифа test_author, часть пакета ревьювера). Часть «только флаг» оставила бы в main записи указания, которые никто не читает: Оператор подавал бы указание, а test_author его не видел — канал выглядел бы рабочим, не работая. Часть «только читатель» без писателя — мёртвый код без проверяемого поведения. Документация и справка описывают тот же флаг. Разрез по ролям (бриф test_author отдельно от пакета ревьювера) возможен, но обе части опираются на одну функцию и одну константу действия, а вторая часть стоит дешевле отдельного круга задачи.
