## Пути обхода гейтов
- Правило требования 2 можно поставить только в `submodule update`
  (`_clone_submodules`), а в `fetch`/`pull`/`ls-remote` выставить лишь
  `useHttpPath` с прежним помощником: AC-2 проверяет наличие флага, AC-3 —
  помощник «в окружении вызова» без названной подкоманды, и тест на
  окружении `submodule update` пройдёт. Тогда on-demand-рекурсия `fetch`
  (опыт выше) отдаёт токен проекта по адресу подмодуля — нарушение «никогда
  токен проекта» п. 2. Отклонение 1.
- Текст общего помощника можно переписать под пути для всех записей:
  поведение записи без поля то же, `tests/test_hosting_token_units.py:27-28`
  значение `GIT_CONFIG_VALUE_2` не сверяет, а AC-2 «побайтно прежние» без
  закреплённого эталона сравнит с той же новой константой. Отклонение 2.

## Вердикт
concerns — SPEC вести можно, правки уточняющие; решение за Оператором на
гейте.

1. **Окружение AC-3 не привязано к подкомандам** (SPEC AC-2, AC-3;
   требование 3). Нужно: проверка помощника `git credential fill` (адрес
   подмодуля — его пароль, не пароль проекта) в окружении каждого из
   `fetch`, `pull`, `ls-remote`, `submodule update` (как минимум `fetch` и
   `submodule update`), а не одного «вызова». Опыт: `fetch` клона ходит в
   подмодуль (`path=g/sub.git`).
2. **AC-2 «побайтно прежние» без эталона** (SPEC AC-2;
   `orchestrator/gitcmd.py:51-56`; `tests/test_hosting_token_units.py:27-28`
   значение помощника не закрепляет). Нужно назвать эталон: литералы
   `GIT_CONFIG_*`, включая текст помощника, как на main (или их sha),
   иначе мутация общего помощника не ловится.
3. **Вторая форма AC-5 невыполнима** (SPEC AC-5; решение Оператора 4):
   сервер AC-4 — `http://`, а `check_submodules` относит такой адрес к виду
   «иной» и даёт `warn` без `ls-remote`
   (`orchestrator/doctor/project_checks.py:1336-1338`, `:1382-1386`); `ok`
   этой формой не получить. Остаётся только первая форма (перехват
   `subprocess.run` + `credential fill`); вторую стоит снять.
4. **Требование 5 не называет исход для `http://` на хосте записи** у
   подмодуля из поля: по `_remote_kind` это «иной» → сегодня ветка «не на
   хосте» (`project_checks.py:1382`), по требованию 5 — `fail` «другой
   хост», хотя хост тот же, а помощник (`url_host`, `gitcmd.py:61-73`)
   токен подмодуля такому адресу выдаст. Нужно одно правило.
5. **Требование 4: какой пустой слот отказывает** (SPEC требования 2, 4):
   не сказано, отказывает ли `_clone_submodules`, если путь поля не в
   `.gitmodules` (по п. 1 это только `warn`) или адрес на чужом хосте (по
   п. 2 слот «не читается»). Предлагаемое: отказ — только для пути из поля,
   который есть в `.gitmodules` и на хосте записи.
6. Замечания без отклонения (решить по желанию):
   - `push` есть в `HOSTING_SUBCOMMANDS` (`gitcmd.py:42`), но не в перечне
     требования 3/AC-2; исход тот же (токен проекта), стоит назвать явно;
   - предел 60 с AC-4 для вызова внутри `gitcmd.git` (`gitcmd.py:1295`,
     `subprocess.run` без `timeout`) ставится только обёрткой
     `subprocess.run` в тесте — форму можно назвать;
   - безопасность тестов не требует отрезать системный/глобальный конфиг
     git Оператора (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL`): на macOS
     системный `credential.helper=osxkeychain` получил бы пароли песочницы
     в любом git-вызове теста по http мимо `hosting_env`;
   - предпроверка пустого слота в `_clone_submodules` читает связку ключей
     до git; в процессе роли до неё не дойти (клон отказан раньше,
     `workspace.py:190-196`), но порядок «отказ роли — до чтения» для неё
     требованием 6 не назван.
