# SPEC: Отдельный токен для подмодулей внешнего проекта

## Контекст
Хостинговый git-вызов внешнего проекта авторизуется токеном слота
`token_slot` записи: `gitcmd.hosting_token` (`orchestrator/gitcmd.py:168-189`)
читает слот, `gitcmd.hosting_env` (:192-210) ставит помощник
`HOSTING_CREDENTIAL_HELPER` (:51-56), который отдаёт пароль на любой
запрос `get` с хостом записи (`ARTEL_HOSTING_HOST`) без учёта пути; хост
берётся из `url` записи в `gitcmd.git` (:1286-1293). Подмодули клона
извлекаются в одном месте — `workspace._clone_submodules`
(`orchestrator/workspace.py:141-153`) — тем же токеном проекта. Подмодуль в
другом репозитории того же хоста, к которому у токена проекта нет доступа,
не извлекается: клон не заводится («HTTP Basic: Access denied»), `doctor
--fix` строку `project-clones` не чинит, строка `doctor`
`project-submodules-<проект>` (`orchestrator/doctor/project_checks.py:1361-1400`)
даёт `fail` и заводится только при `merged_by_project_people` (:70-75).
`fetch` в клоне с извлечённым подмодулем идёт и в подмодуль (опыт
проверяющего 05.11, git 2.50.1; `fetch` в клоне — `orchestrator/snapshot.py:330`,
`orchestrator/doctor/project_checks.py:95`). Опыт 05.11 вне пульта: клон
токеном проекта и извлечение подмодуля отдельным токеном (только чтение)
проходят, если помощник выбирает токен по адресу с путём
(`credential.useHttpPath=true`); запрос к адресу без `.git` после
перенаправления хостинга приходит помощнику как `path=<группа>/<проект>.git`.
Поля записи для токенов подмодулей сейчас нет (`orchestrator/targets.py:41`,
`LOCAL_FIELDS["machine"]` :366, `_flatten` :796-810); проверка записи
(:837-916) неизвестные плоские поля не отвергает.

## Требования

1. **Поле записи** `machine.submodule_tokens` — отображение «путь
   подмодуля верхнего уровня в `.gitmodules` → имя слота связки ключей»,
   необязательное; нет поля — поведение прежнее. Поле объявлено в
   `LOCAL_FIELDS["machine"]` и переносится в плоскую запись (`_flatten`).
   Проверка при загрузке `targets` — отказ загрузки с именем поля, если:
   значение поля — не отображение; путь или слот — не непустая строка;
   поле задано в записи слоя репозитория (оно допустимо только в записи
   локального слоя, `machine`). Путь, которого нет в `.gitmodules` клона,
   — не отказ загрузки, а строка `doctor` `warn` (требование 5).
2. **Выбор токена по адресу** — только для записи с `submodule_tokens`:
   - адрес подмодуля из поля берётся из `.gitmodules` клона проекта
     `workspace.repo(<проект>)` (не рабочей копии задачи); относительный
     адрес (`./…`, `../…`) — разрешённый от `url` записи так же, как
     `doctor` `_resolve_submodule`;
   - токен слота подмодуля выдаётся только запросу с хостом записи
     (`ARTEL_HOSTING_HOST`) и путём, равным по `url_key` адресу этого
     подмодуля; такой запрос никогда не получает токен проекта;
   - запрос к прочим адресам хоста записи получает токен проекта, как
     сейчас;
   - запрос к другому хосту не получает ничего;
   - если адрес подмодуля, путь которого назван в `submodule_tokens`,
     указывает на другой хост, его токен не выдаётся никому и слот не
     читается; правило «другой хост — ничего» сильнее правила «адрес
     подмодуля — токен его слота»;
   - пустой слот подмодуля: по адресу этого подмодуля помощник не отдаёт
     ничего (и никогда — токен проекта); сам вызов при этом не
     отказывается (исключение — требование 4);
   - сравнение адресов — по `url_key` (без `.git` и завершающей косой
     черты), точное, не по префиксу;
   - значения токенов не попадают ни в argv git и помощника, ни в журнал
     пульта, ни в вывод команд (как у `HOSTING_CREDENTIAL_HELPER` сейчас).
3. **Где действует выбор**: слоты подмодулей читает и правило требования 2
   с `credential.useHttpPath=true` ставит хостинговый git-вызов записи с
   полем в `gitcmd.git` — подкоманды `fetch`, `pull`, `ls-remote`, `clone`,
   `submodule update`. `hosting_token` слоты подмодулей не читает; его
   вызыватели (`orchestrator/ci.py:84`, `orchestrator/gitlab_adapter.py:234`,
   `orchestrator/doctor/misc_checks.py:85`) работают побайтно как прежде.
   Путь запроса помощнику сравнивается без учёта суффикса `.git`. Запись
   без поля — окружение и argv вызова прежние, `useHttpPath` не ставится.
4. **Извлечение подмодулей** — `_clone_submodules` (единственное место)
   идёт с правилом требования 2; при пустом слоте подмодуля из поля —
   именованный отказ до запуска git, текст называет путь подмодуля и имя
   слота. Новых мест вызова `submodule update` не добавляется.
5. **`doctor`**: строка `project-submodules-<проект>` заводится для записи
   с `submodule_tokens` при любом `merge_gate`; для записи без поля условие
   прежнее (только `merged_by_project_people`). Подмодуль из
   `submodule_tokens` проверяется токеном его слота; слот пуст — `fail` с
   именем слота; путь поля, которого нет в `.gitmodules` клона, — `warn`;
   адрес подмодуля из поля на другом хосте — `fail` с путём подмодуля и
   хостом. Прочие подмодули записи проверяются, как сегодня, токеном
   проекта (на другом хосте — прежний `warn`).
6. **Процесс роли**: для записи с `submodule_tokens` действует прежний
   отказ `hosting_token` — именованный отказ до любого чтения связки
   ключей (ни слот проекта, ни слоты подмодулей не читаются; токены читает
   только сессия Оператора).
7. **Документация**: комментарий поля `submodule_tokens` в
   `orchestrator/targets.py`; `docs/codebase-map.md` меняется только
   повторной генерацией `scripts/codebase_map.py`.

## Критерии приёмки

Безопасность тестов (для всех критериев): связка ключей — подмена
`keychain.token`; хостинг — локальный HTTP-сервер на `127.0.0.1` во
временной песочнице, без внешней сети; проекты, записи и `.gitmodules` —
вымышленные, во временной песочнице; никогда — настоящий клон и настоящий
локальный слой; в текстах тестов — ни имён, ни адресов реальных проектов.

AC-1. Запись локального слоя с `machine.submodule_tokens` (путь → слот,
непустые строки) загружается `targets`, поле есть в плоской записи.
Загрузка отказывается, и текст отказа называет поле `submodule_tokens`,
для: пустого пути или пустого слота; значения поля, которое не
отображение; поля в записи слоя репозитория.

AC-2. Для записи без `submodule_tokens` окружение и argv хостингового
вызова побайтно совпадают с прежними: сравнение переменных `GIT_CONFIG_*`
и argv с записью без поля, `credential.useHttpPath` не выставлен. Для
записи с полем `credential.useHttpPath=true` есть в окружении каждого
хостингового git-вызова (`fetch`, `pull`, `ls-remote`, `clone`,
`submodule update`). Вызыватели `hosting_token` для записи с полем не
вызывают `keychain.token` для слотов подмодулей.

AC-3. Помощник учётных данных через `git credential fill` в окружении
вызова записи с `submodule_tokens` (образец —
`tests/test_01m545edths47hsb59akc1ez9c_project_token.py`):
адрес подмодуля из записи — пароль слота подмодуля, не пароль проекта;
адрес проекта, в том числе `path=<группа>/<проект>.git` у записи с `url`
без `.git`, — пароль проекта; третий адрес того же хоста — пароль проекта;
адрес с тем же префиксом, что у подмодуля (`<группа>/<подмодуль>-other.git`),
— не пароль подмодуля; другой хост — пусто. Дополнительно:
относительный адрес подмодуля (`../<подмодуль>.git`) разрешается от `url`
записи и получает пароль слота подмодуля; при расхождении `.gitmodules`
(в клоне — адрес подмодуля, в рабочей копии задачи — другой) выбор идёт по
клону; `.gitmodules` клона с адресом подмодуля из поля на другом хосте
(тот же путь) — запрос к этому хосту получает пусто, пароль подмодуля не
выдан никому, `keychain.token` для его слота не вызывается.

AC-4. Клон вымышленного проекта с подмодулем во временной песочнице:
локальный сервер на `127.0.0.1` — `http.server` со статической отдачей
файлов (репозитории `--bare` после `update-server-info`) и проверкой
пароля по префиксу пути, без `git http-backend`; два репозитория с разными
паролями; `url` записи и адреса `.gitmodules` — с суффиксом `.git`; в
окружении git-вызовов теста `GIT_TERMINAL_PROMPT=0`; у каждого git-вызова
теста предел времени не больше 60 с; сервер останавливается в `finally`.
Запись с `token_slot` и `submodule_tokens` — клон и `submodule update
--init --recursive` (через `_clone_submodules`) проходят; запись с одним
`token_slot` без `submodule_tokens` — отказ, как сейчас.

AC-5. `doctor` `project-submodules-<проект>`: выданный на `ls-remote`
пароль проверяется перехватом `subprocess.run` в `gitcmd` (окружение
вызова `ls-remote`) и `git credential fill` по адресу подмодуля в этом
окружении либо прогоном `doctor` против локального сервера AC-4 с разными
паролями; проба подмодуля токеном проекта — красный тест. Запись с
`merge_gate: target-human` и `https://`-адресом: подмодуль из поля с
токеном своего слота — `ok`; пустой слот подмодуля — `fail`, текст
называет имя слота; путь поля, которого нет в `.gitmodules` клона, —
`warn`; адрес подмодуля из поля на другом хосте — `fail`, текст называет
путь подмодуля и хост; прочий подмодуль на другом хосте — `warn`. Запись
`merge_gate: operator` с `submodule_tokens` — строка есть; запись
`merge_gate: operator` без поля — строки нет, как сейчас.

AC-6. В процессе роли хостинговый вызов для записи с `submodule_tokens` —
прежний именованный отказ `hosting_token`, `keychain.token` не вызывается
ни для слота проекта, ни для слотов подмодулей.

AC-7. Значения паролей песочницы (проекта и подмодуля) не встречаются ни
в журнале пульта, ни в выводе команд, ни в argv дочерних процессов
(перехват argv).

AC-8. Пустой слот подмодуля из поля (подмена `keychain.token` отдаёт
пусто для его слота): `_clone_submodules` — именованный отказ, текст
называет путь подмодуля и имя слота, git не вызван (перехват
`subprocess.run`); `fetch` той же записи не отказан; `git credential fill`
по адресу этого подмодуля в окружении вызова — пусто (не пароль проекта).

AC-9. Прежние тесты зелёные без правки: `tests/test_hosting_token_units.py`,
`tests/test_01m545edths47hsb59akc1ez9c_project_token.py`,
`tests/test_doctor_gitlab_ci_file.py`,
`tests/test_01m6ezxvfgh5z2876xwmqg35fp_gitlab_doctor_lines.py` (решение
Оператора на гейте SPEC, решение 6; файлы — только чтение).

## Оценка объёма и деление

Сработавшие сигналы: число файлов зоны ≥ 5 (`orchestrator/gitcmd.py`,
`orchestrator/targets.py`, `orchestrator/workspace.py`,
`orchestrator/doctor/project_checks.py`, плюс общие `docs/codebase-map.md`
и `tests/`); `budget_usd` ≥ $30 (рамка ТЗ $35). Критериев приёмки 9 —
ниже порога; слов-маркеров нет.

Прогноз диффа: 50 КиБ.

**Обоснование монолита** (материал для решения Оператора). Механика одна:
поле записи (`targets.py`) → выбор токена по адресу в помощнике и
окружении хостингового вызова (`gitcmd.py`) → его потребитель
`_clone_submodules` (`workspace.py`) → проверка тем же правилом в `doctor`
(`project_checks.py`). Поле без помощника — мёртвая настройка, которую
`doctor` (требование 5) не может проверить токеном подмодуля; помощник без
поля не имеет входа. Единственный отделимый кусок — строка `doctor`
(требование 5, AC-5), но она опирается на то же окружение `gitcmd.git`
(решение 4: пароль виден только в окружении вызова) и без него не
проверяема; отдельная подзадача удвоила бы фиксированную цену шагов
(analyst, аудит, test_author, ревью) при рамке ТЗ $35 и оставила бы
промежуточное состояние «поле есть, `doctor` его не видит».

  подмодуль из поля токена не получает, `doctor` — `fail`, требования 2, 5).

  уровня.

- Срок токена подмодуля (строка `doctor` `token-expiry`).

- Новые места вызова `submodule update` (в том числе извлечение подмодулей
  в рабочих копиях задач).
- Зелёность всего набора `tests/` — её держит пульт (полный зелёный набор
  и рубеж неослабления). Покраснел существующий тест — эскалация с именем
  теста, без его правки.
