# SPEC: защищённые пути — единый список, гейт зон отказывает всегда, CI падает

## Контекст
Защищённые пути системы сегодня живут двумя несогласованными списками:
`config.PROTECTED_PATHS` (используется только в `fsm_merge_gate` — по
конфликту merge) и отдельное регулярное выражение задания CI
`protected-paths` (`.github/workflows/ci.yml`), которое лишь предупреждает
(`::warning`), не проваливает шаг. Ни один из списков не блокирует
обычную правку защищённого пути ролью, если конфликта merge не возникло
и путь не назван в зонах задачи. Факт 11.09: developer задачи 01M1SHJX22
правил строку `docs/invariants.md` по требованию SPEC, и правку остановил
только гейт зон — случайно, потому что файл не был назван в зонах. Будь
он в зонах, правка инварианта ролью прошла бы все гейты и мерж. Источник:
копилка 11.09 (приоритет 2), решение Оператора 11.09 «инварианты правит
только Оператор».

Зоны `orchestrator/fsm_advance.py` и `orchestrator/fsm_merge_gate.py` на
момент постановки задачи заняты другой задачей в очереди (approve без sha
01M1SHJX22, деление B2) — задача стартует после их освобождения; это
эксплуатационный факт очереди зон, не требование SPEC.

## Требования
1. Единый источник списка защищённых путей — `config.PROTECTED_PATHS`,
   дополненный пятью путями: `docs/invariants.md`,
   `tests/test_invariants.py`, `docs/adr/`, `CLAUDE.md`, `targets.yaml`.
   Семантика префикса — та же, что несёт сегодняшний
   `fsm_merge_gate._touches_protected_path` (`path == p or
   path.startswith(p)`).
2. Гейт зон перехода `in_dev -> verifying` (`fsm_advance._zones_gate`)
   отказывает переход, если дифф ветки задачи против базы сравнения
   трогает путь из `config.PROTECTED_PATHS`, — независимо от того,
   заявлен ли этот путь в `zones`/`zones_extension`, и независимо от
   раздела «## Расширение зон» PLAN.md и мандата Оператора «Расширение
   зон разрешено» в ANSWER-n.md: мандат на расширение зон защищённые
   пути не покрывает.
3. Гейт мержа (`fsm_merge_gate`) отказывает в мерже ветки задачи, чей
   дифф против базы сравнения трогает путь из `config.PROTECTED_PATHS`,
   — переход в `escalated` с тем же именованным текстом отказа, не
   только при содержательном конфликте `git merge --no-ff` (сегодня
   эскалация по защищённому пути срабатывает исключительно внутри
   разбора конфликта, `_handle_merge_conflict`).
4. Оба отказа (требования 2 и 3) несут один и тот же именованный текст:
   «защищённый путь <путь> — правит только Оператор коммитом в main;
   предложи правку приложением к PLAN (unified-дифф)».
5. Задание CI `protected-paths` (`.github/workflows/ci.yml`) читает
   список защищённых путей из `config.PROTECTED_PATHS` python-
   однострочником, не дублирующим список отдельным регулярным
   выражением, и на событии `pull_request` ПАДАЕТ (ненулевой код
   выхода), если дифф трогает защищённый путь, — не выводит
   `::warning`. `.github/` сам входит в защищённые пути — правка
   `ci.yml` оформляется приложением unified-диффа к PLAN.md
   (проверенным `git apply --check` на чистом дереве перед сдачей),
   применяет Оператор.

## Критерии приёмки
AC-1. `config.PROTECTED_PATHS` содержит все пять добавленных путей:
`docs/invariants.md`, `tests/test_invariants.py`, `docs/adr/`,
`CLAUDE.md`, `targets.yaml` — вдобавок к пяти существующим
(`gates.yaml`, `roles.yaml`, `.github/`, `templates/`, `skills/`);
формула проверки принадлежности (`==` или `startswith`) не изменена.

AC-2. Гейт зон перехода `in_dev -> verifying` отказывает, если дифф
ветки задачи против базы сравнения (`gitcmd.diff_base`) трогает путь из
`config.PROTECTED_PATHS`, даже когда этот путь заявлен в `zones` или
`zones_extension` задачи.

AC-3. Гейт зон из AC-2 отказывает и тогда, когда PLAN.md несёт раздел
«## Расширение зон» со строкой `Пути:`, покрывающей защищённый путь, а
ANSWER-n.md ветки задачи несёт строку `Расширение зон разрешено:` на тот
же путь (обычное исключение AC-3 скила `zones`-гейта) — мандат
Оператора на расширение зон защищённые пути не покрывает, исключение к
ним не применяется.

AC-4. Отказы AC-2 и AC-3 несут именованный текст «защищённый путь
<путь> — правит только Оператор коммитом в main; предложи правку
приложением к PLAN (unified-дифф)» с конкретным задетым путём (или
перечнем путей, если их несколько) вместо `<путь>`.

AC-5. Гейт мержа (`fsm_merge_gate`) отклоняет `approve` из `merge_gate`
переходом в `escalated` с текстом из AC-4, если дифф ветки задачи
против базы сравнения трогает путь из `config.PROTECTED_PATHS`, — в
том числе когда `git merge --no-ff` этой ветки не даёт ни одного
конфликтующего файла (сегодняшняя проверка внутри
`_handle_merge_conflict` такой дифф пропускает, раз конфликта нет).

AC-6. Задание CI `protected-paths` вычисляет множество защищённых
путей из `config.PROTECTED_PATHS` python-однострочником (без отдельного
хардкод-регулярного выражения, дублирующего список) и на событии
`pull_request` завершается ненулевым кодом выхода (не `::warning`),
если `git diff --name-only база...HEAD` задевает защищённый путь.
Правка `.github/workflows/ci.yml` приложена к PLAN.md unified-диффом,
прошедшим `git apply --check` на чистом дереве.

AC-7. Тесты покрывают: (а) гейт зон отказывает по защищённому пути даже
при наличии раздела «Расширение зон» и подкрепляющего мандата на тот же
путь — мутация «мандат покрывает защищённые пути» красная; (б) гейт
мержа отклоняет переходом в `escalated` дифф с защищённым путём БЕЗ
конфликта `git merge --no-ff`; (в) `config.PROTECTED_PATHS` содержит
все пять путей из AC-1; (г) существующие тесты защищённых путей (гейт
зон, разбор конфликта merge по защищённому пути) остаются зелёными без
ослабления имеющихся утверждений.

## Оценка объёма и деление
Сработавший сигнал: зона задевает механизм, на который опирается
запись в `docs/invariants.md` — строки 34 и 79. Строка 34 описывает
сегодняшнее (более широкое) исключение «Расширение зон» гейта зон,
которое требования 2-3 (AC-2/AC-3) сужают для защищённых путей. Строка
79 описывает сегодняшнее поведение CI-задания `protected-paths` как
«в Фазе 0 деградирует до предупреждения» — требование 5 (AC-6) отменяет
эту деградацию (падение вместо warning).

Решение: монолит, без деления. Четыре части требования (единый список
— AC-1, гейт зон — AC-2/AC-3/AC-4, гейт мержа — AC-5, CI-задание — AC-6)
меняют один и тот же факт с четырёх разных точек контроля: список
защищённых путей существует, но ни одна проверка не блокирует правку
им роли (факт 11.09 из ТЗ). Промежуточный мерж любой части в
отдельности (например, расширенный список без обоих гейтов) оставляет
систему в том самом дефектном состоянии, ради устранения которого
заведена задача — правка защищённого пути ролью снова прошла бы гейты.
Зона мала (3 файла зоны, 7 критериев приёмки) — других сигналов
«подозрения на большой объём» (≥5 файлов зоны, ≥10 критериев,
`budget_usd` ≥ $30) нет; деление добавило бы координационные издержки
без реальной точки независимого мержа.

Правку самого текста строк 34/79 `docs/invariants.md` эта задача не
делает (ТЗ, «не входит»: «правка самих инвариантов и ADR») — после
мержа их формулировки текстово разойдутся с новым поведением
(исключение AC-3 гейта зон сузилось; CI-задание больше не деградирует
до warning). Актуализация текста инвариантов — на усмотрение Оператора
отдельным действием, не в рамках этого шага.

## Не входит
- Разделение токенов (PAT) для CI по автору PR — задание `protected-paths`
  падает безусловно на `pull_request`, без различения аккаунта-автора;
  инфраструктура раздельных токенов не заводится (комментарий
  `ci.yml` про «Фазу 0, один токен» теряет актуальность по смыслу, но
  сам механизм PAT эта задача не трогает).
- Правка содержимого `docs/invariants.md` (включая строки 34 и 79,
  устаревающие текстово после этой задачи) и содержимого `docs/adr/` —
  инварианты и ADR правит только Оператор.
- `docs/operator-session.md`.
- Новое состояние FSM не вводится: оба гейта (зон и мержа) остаются
  дополнительными предусловиями существующих переходов (`in_dev ->
  verifying`, `merge_gate -> done`/`escalated`), не новым шагом маршрута
  — `tests/test_invariants.py` (порядок состояний, инвариант 36) этой
  задачей не затронут по числу шагов между состояниями.
