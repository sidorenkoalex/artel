# SPEC: Эпики Э4 — проекция доски наружу: board, report из модели, внешние ссылки

## Контекст
ADR-0028 (принят 25.10.2026), п. 12–16, шаг Э4; идёт после Э1
(01M5TBBDFS6DWQY6MS263T1KPY), который ввёл модель доски
`orchestrator/board.py` (`build_model(conn, project)` — модель одного
проекта). Сейчас `report` — статическая HTML-доска, одна на все проекты
(`orchestrator/report.py` на main после Э1: колонки `STATE_ORDER` `:48`,
плитка `_tile_html` `:565`, `_board_html` `:596`, `cmd_report` `:1428` на
`store.all_tasks` `:1440`, множество проектов `_render` `:1378`; проект виден
меткой на плитке), построенная не из модели `board.py`, — два вида доски
могут разойтись. Внешних ссылок задач (ключ задачи во внешнем трекере) в БД
нет. Задача выводит модель доски наружу командой `board`, переводит `report`
на модель и добавляет хранение внешних ссылок задач и эпиков.

## Требования
1. **Вывод модели.** Команда `artel.py board --project <имя> [--json | --md | --html]` печатает модель доски `board.py` проекта:
   - `--json` — словарь с полем `schema_version` (контракт для будущего интерфейса доски), полями `columns`, `epics`, `cards`; у карточек — `waiting_on` и `refs`;
   - `--md` — таблица; `board` без флага вида печатает то же, что `--md`;
   - `--html` — страница.
   Все три вида строятся из одной модели. Команда не обращается к сети и не пишет в БД. Неизвестный проект (не заявлен в `targets.yaml`, и в БД нет ни задачи, ни эпика этого проекта) — отказ с причиной (назван проект).
2. **report из модели.** `report` строит модель `board.py` на каждый проект задач БД — все проекты, у которых есть задачи, включая не заявленные в `targets.yaml` (как сейчас `report.py:1440`, `:1378`), — и сводит карточки всех проектов в те же колонки, что сейчас, с нынешним порядком колонок и карточек. Всё, что показывает плитка доски, `report` берёт из модели.
   - «report без эпиков» (ни у одной задачи нет эпика): HTML-доска побайтно совпадает с выводом текущего `report`.
   - С эпиками: внутри колонки сначала идут группы эпиков в порядке id эпика — у группы заголовок «<id эпика> <название>», под ним карточки этого эпика, — затем карточки без эпика прежним порядком.
3. **report из модели — число запросов.** `cmd_report` открывает соединение `store.db()` один раз за прогон и передаёт его `build_model`. Построение моделей для `report` делает постоянное число запросов к таблице `steps`, не зависящее от числа задач: журнал для `waiting_on` читается пакетно, не запросом на каждую карточку (нынешний путь `board.waiting_on` → `zone_lock.queue_wait` читает `steps` на каждую задачу `in_dev` с зонами).
4. **Карточка модели — поля плитки.** Карточка модели `board.py` (`cards[]`) расширяется полями, которые нужны плитке `report` (`report.py:565-593`): `review_iters`, `escalated_from`, проект задачи (`project`), — в дополнение к уже имеющимся `task`, `title`, `state`, `budget_usd`, `spent_usd`.
5. **Внешние ссылки — хранение.** В БД — таблица `external_refs` с полями: вид (`task` | `epic`), идентификатор задачи или эпика, система, ключ, URL (необязательно), кто записал и когда. На существующей БД без этой таблицы она создаётся при открытии `store.db()`.
6. **Внешние ссылки — система.** Система — свободная непустая строка (например, `kaiten`, `gitlab-issue`). Если в записи проекта задано новое необязательное поле `policy.ref_systems` (список систем), система ссылки задачи или эпика этого проекта допустима только из этого списка; иначе запись ссылки отказывает с причиной.
7. **Внешние ссылки — запись.**
   - `new … --ref <система>:<ключ>` записывает ссылку задачи до создания её ветки; `--ref` можно указать несколько раз — записываются все ссылки;
   - `artel.py link <task|epic> <id> <система> <ключ> [--url …]` добавляет ссылку задаче или эпику; повторный `link` той же системы и того же ключа тому же объекту дубля не создаёт;
   - `artel.py link --remove …` снимает ссылку; `--remove` несуществующей ссылки отказывает с причиной;
   - `link` на несуществующий id задачи или эпика отказывает с причиной и ничего не записывает.
8. **Внешние ссылки — в модели.** Ссылки входят в модель доски: `cards[].refs` у задач, `epics[].refs` у эпиков. Элемент `refs` несёт систему, ключ, URL (или пусто), кто и когда записал; ссылки идут в порядке времени записи. Пульт внешний трекер не вызывает и не читает.
9. **`policy.ref_required`.** Новое необязательное поле записи проекта `policy.ref_required` (по умолчанию не задано) называет систему внешних ссылок. Если поле задано, `new` в этот проект без `--ref` этой системы отказывает с причиной (названа требуемая система). К учебной задаче канарейки (`cmd_new(canary=True)`, `canary_drive.py:54`) `ref_required` не применяется.
10. **Отказ `new` до побочных эффектов.** Отказ `new` по `ref_required` (требование 9) или по `ref_systems` (требование 6) происходит до создания ссылки документов задачи (`catalog.py:738`): после отказа нет ни строки задачи, ни ссылки `refs/artifacts/<id>`.
11. **Части деления наследуют ссылки.** Подзадачи, которые пульт заводит при делении (`catalog.spawn_subtask`, зов `fsm.py:1070`), получают копию `external_refs` родителя при заведении — `ref_required` делением не обходится.

## Критерии приёмки
AC-1. `board --project <проект> --json` песочного проекта с эпиком печатает словарь с полями `schema_version`, `columns`, `epics`, `cards`; каждая карточка несёт поля `waiting_on` и `refs`.

AC-2. Два вызова `board --json` одного проекта без изменений БД между ними дают одинаковый вывод, кроме поля `generated_at`; в фикстуре у карточки не меньше двух ссылок.

AC-3. Построение модели командой `board` не меняет БД: число изменений соединения БД (`total_changes`), замеренное до и после вызова команды на уже открытом соединении, — 0.

AC-4. `board --md` и `board --html` строятся из той же модели, что `--json`: подмена модели меняет вывод обоих видов; `board` без флага вида печатает то же, что `board --md`; `board --project` неизвестного проекта (нет в `targets.yaml`, нет задач и эпиков в БД) отказывает с причиной, в которой назван проект.

AC-5. «report без эпиков» на богатой фикстуре — не меньше двух заявленных проектов (артель и внешний), задача проекта, не заявленного в `targets.yaml`, эскалированная задача, задача в неизвестном FSM состоянии — и на пустой доске выдаёт HTML-доску, побайтно равную эталону. Эталон — литерал, снятый кодом main до правки; его вносит сессия при Операторе командой `amend-tests` (разработчик эталон не пишет). До внесения эталона тест проверяет форму доски на той же фикстуре: колонки в порядке FSM, неизвестное состояние — в конце, метка проекта у плитки внешнего проекта, плитка задачи незаявленного проекта на доске с его меткой, маркер эскалации, «Задач нет» на пустой доске.

AC-6. `report` с двумя эпиками в одной колонке: внутри колонки сначала группы эпиков в порядке id эпика, у каждой заголовок «<id эпика> <название>» и карточки этого эпика, затем карточки без эпика в прежнем порядке.

AC-7. Подмена `board.build_model` меняет доску `report`: подменённые значения карточки (название, состояние, `review_iters`, `escalated_from`, проект) видны на доске, настоящих нет.

AC-8. Карточка модели `board.py` несёт поля `review_iters`, `escalated_from` и `project` со значениями задачи из БД.

AC-9. `new … --ref kaiten:123` записывает ссылку (система `kaiten`, ключ `123`) в `external_refs`, и она видна в `cards[].refs` модели доски этой задачи с полями система, ключ, URL, кто и когда записал (кто и когда — непустые); `new` с двумя `--ref` записывает обе ссылки.

AC-10. `link task <id> <система> <ключ> --url <url>` добавляет ссылку задаче (видна в `cards[].refs` с этим URL), `link epic <id> <система> <ключ>` — эпику (видна в `epics[].refs`); две ссылки одного объекта идут в `refs` в порядке записи; повторный `link` той же системы и ключа тому же объекту не добавляет вторую строку в `external_refs`; `link --remove` с теми же реквизитами снимает ссылку (в модели её нет); `link --remove` несуществующей ссылки отказывает с причиной; `link` на несуществующий id задачи или эпика отказывает, в `external_refs` записи нет.

AC-11. Для проекта с заданным `policy.ref_required: <система>` `new` без `--ref` этой системы отказывает с причиной (названа система): задача не заводится, ссылки `refs/artifacts/<id>` нет; с `--ref <система>:<ключ>` — заводится. Учебная задача канарейки (`cmd_new(canary=True)`) в проект с `ref_required` заводится без `--ref`.

AC-12. Для проекта с заданным `policy.ref_systems` `new --ref` и `link` с системой вне списка отказывают, ссылка не записывается; после отказа `new` нет ни строки задачи, ни ссылки `refs/artifacts/<id>`; с системой из списка — записывается. Без `policy.ref_systems` принимается любая непустая система.

AC-13. Подзадача, заведённая пультом при делении родителя со ссылками, несёт копию ссылок родителя (`cards[].refs` подзадачи — те же система и ключ).

AC-14. `cmd_report` на наборе из 2 задач и на наборе из 7 задач (в обоих наборах есть задачи `in_dev` с зонами) делает одинаковое число запросов к `steps`, и в каждом прогоне `store.db()` вызывается один раз.

AC-15. На БД, созданной без таблицы `external_refs` (схема до этой задачи), открытие `store.db()` создаёт таблицу; `board --json` на такой БД печатает модель с пустыми `refs`, `link` записывает ссылку.
