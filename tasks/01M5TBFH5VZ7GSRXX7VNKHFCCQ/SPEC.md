# SPEC: Эпики Э4 — проекция доски наружу: board, report из модели, внешние ссылки

## Контекст
ADR-0028 (принят 25.10.2026), п. 12–16, шаг Э4; идёт после Э1
(01M5TBBDFS6DWQY6MS263T1KPY), который вводит модель доски
`orchestrator/board.py`. Сейчас `report` — статическая HTML-доска
(`orchestrator/report.py`: колонки `STATE_ORDER` `:46`, `_board_html` `:598`,
группировка по проекту), построенная не из модели `board.py`, — два вида
доски могут разойтись. Внешних ссылок задач (ключ задачи во внешнем трекере)
в БД нет. Задача выводит модель доски наружу командой `board`, переводит
`report` на модель и добавляет хранение внешних ссылок задач и эпиков.

## Требования
1. **Вывод модели.** Команда `artel.py board --project <имя> [--json | --md | --html]` печатает модель доски `board.py` проекта:
   - `--json` — словарь с полем `schema_version` (контракт для будущего интерфейса доски), полями `columns`, `epics`, `cards`; у карточек — `waiting_on` и `refs`;
   - `--md` — таблица;
   - `--html` — страница.
   Все три вида строятся из одной модели. Команда не обращается к сети и не пишет в БД.
2. **report из модели.** `report` строится из модели `board.py`. Для проекта без эпиков вид и содержимое HTML-доски не меняются относительно текущего вывода; для проекта с эпиками добавляется группировка карточек по эпикам.
3. **Внешние ссылки — хранение.** В БД — таблица `external_refs` с полями: вид (`task` | `epic`), идентификатор задачи или эпика, система (свободная строка, например `kaiten`, `gitlab-issue`), ключ, URL (необязательно), кто записал и когда.
4. **Внешние ссылки — запись.**
   - `new … --ref <система>:<ключ>` записывает ссылку задачи до создания её ветки;
   - `artel.py link <task|epic> <id> <система> <ключ> [--url …]` добавляет ссылку задаче или эпику;
   - `artel.py link --remove …` снимает ссылку.
5. **Внешние ссылки — в модели.** Ссылки входят в модель доски: `cards[].refs` у задач, `epics[].refs` у эпиков. Пульт внешний трекер не вызывает и не читает.
6. **`policy.ref_required`.** Новое необязательное поле записи проекта `policy.ref_required` (по умолчанию не задано) называет систему внешних ссылок. Если поле задано, `new` в этот проект без `--ref` этой системы отказывает с причиной (названа требуемая система).

## Критерии приёмки
AC-1. `board --project <проект> --json` песочного проекта с эпиком печатает словарь с полями `schema_version`, `columns`, `epics`, `cards`; каждая карточка несёт поля `waiting_on` и `refs`.

AC-2. Два вызова `board --json` одного проекта без изменений БД между ними дают одинаковый вывод, кроме поля `generated_at`.

AC-3. Построение модели командой `board` не меняет БД: число изменений соединения БД (`total_changes`) за вызов — 0.

AC-4. `board --md` и `board --html` строятся из той же модели, что `--json`: подмена модели меняет вывод обоих видов.

AC-5. `report` проекта без эпиков выдаёт HTML-доску, совпадающую с выводом текущего `report` (до правки) на той же фикстуре.

AC-6. `report` проекта с эпиком группирует карточки по эпикам.

AC-7. `new … --ref kaiten:123` записывает ссылку (система `kaiten`, ключ `123`) в `external_refs`, и она видна в `cards[].refs` модели доски этой задачи.

AC-8. `link task <id> <система> <ключ>` добавляет ссылку задаче (видна в `cards[].refs`), `link epic <id> <система> <ключ>` — эпику (видна в `epics[].refs`); `link --remove` с теми же реквизитами снимает ссылку (в модели её нет).

AC-9. Для проекта с заданным `policy.ref_required: <система>` `new` без `--ref` этой системы отказывает с причиной, задача не заводится; с `--ref <система>:<ключ>` — заводится.
