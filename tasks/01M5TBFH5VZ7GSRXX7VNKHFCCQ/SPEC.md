# SPEC: Эпики Э4 — проекция доски наружу: board, report из модели, внешние ссылки

## Контекст
ADR-0028 (принят 25.10.2026), п. 12–16, шаг Э4; идёт после Э1
(01M5TBBDFS6DWQY6MS263T1KPY), который ввёл модель доски
`orchestrator/board.py` (`build_model(conn, project)` — модель одного
проекта). Сейчас `report` — статическая HTML-доска, одна на все проекты
(`orchestrator/report.py` на main после Э1: колонки `STATE_ORDER` `:48`,
плитка `_tile_html` `:565`, `_board_html` `:596`, `cmd_report` `:1428` на
`store.all_tasks`; проект виден меткой на плитке), построенная не из модели
`board.py`, — два вида доски могут разойтись. Внешних ссылок задач (ключ
задачи во внешнем трекере) в БД нет. Задача выводит модель доски наружу
командой `board`, переводит `report` на модель и добавляет хранение внешних
ссылок задач и эпиков.

## Требования
1. **Вывод модели.** Команда `artel.py board --project <имя> [--json | --md | --html]` печатает модель доски `board.py` проекта:
   - `--json` — словарь с полем `schema_version` (контракт для будущего интерфейса доски), полями `columns`, `epics`, `cards`; у карточек — `waiting_on` и `refs`;
   - `--md` — таблица;
   - `--html` — страница.
   Все три вида строятся из одной модели. Команда не обращается к сети и не пишет в БД.
2. **report из модели.** `report` строит модель `board.py` на каждый проект и сводит карточки всех проектов в те же колонки, что сейчас, с нынешним порядком колонок и карточек. Всё, что показывает плитка доски, `report` берёт из модели.
   - «report без эпиков» (ни у одной задачи нет эпика): HTML-доска побайтно совпадает с выводом текущего `report`.
   - С эпиками: внутри колонки сначала идут группы эпиков — у группы заголовок «<id эпика> <название>», под ним карточки этого эпика, — затем карточки без эпика прежним порядком.
3. **Карточка модели — поля плитки.** Карточка модели `board.py` (`cards[]`) расширяется полями, которые нужны плитке `report` (`report.py:565-593`): `review_iters`, `escalated_from`, проект задачи (`project`), — в дополнение к уже имеющимся `task`, `title`, `state`, `budget_usd`, `spent_usd`.
4. **Внешние ссылки — хранение.** В БД — таблица `external_refs` с полями: вид (`task` | `epic`), идентификатор задачи или эпика, система, ключ, URL (необязательно), кто записал и когда.
5. **Внешние ссылки — система.** Система — свободная непустая строка (например, `kaiten`, `gitlab-issue`). Если в записи проекта задано новое необязательное поле `policy.ref_systems` (список систем), система ссылки задачи или эпика этого проекта допустима только из этого списка; иначе запись ссылки отказывает с причиной.
6. **Внешние ссылки — запись.**
   - `new … --ref <система>:<ключ>` записывает ссылку задачи до создания её ветки;
   - `artel.py link <task|epic> <id> <система> <ключ> [--url …]` добавляет ссылку задаче или эпику;
   - `artel.py link --remove …` снимает ссылку;
   - `link` на несуществующий id задачи или эпика отказывает с причиной и ничего не записывает.
7. **Внешние ссылки — в модели.** Ссылки входят в модель доски: `cards[].refs` у задач, `epics[].refs` у эпиков. Элемент `refs` несёт систему, ключ, URL (или пусто), кто и когда записал; ссылки идут в порядке времени записи. Пульт внешний трекер не вызывает и не читает.
8. **`policy.ref_required`.** Новое необязательное поле записи проекта `policy.ref_required` (по умолчанию не задано) называет систему внешних ссылок. Если поле задано, `new` в этот проект без `--ref` этой системы отказывает с причиной (названа требуемая система).
9. **Части деления наследуют ссылки.** Подзадачи, которые пульт заводит при делении (`catalog.spawn_subtask`, зов `fsm.py:1070`), получают копию `external_refs` родителя при заведении — `ref_required` делением не обходится.

## Критерии приёмки
AC-1. `board --project <проект> --json` песочного проекта с эпиком печатает словарь с полями `schema_version`, `columns`, `epics`, `cards`; каждая карточка несёт поля `waiting_on` и `refs`.

AC-2. Два вызова `board --json` одного проекта без изменений БД между ними дают одинаковый вывод, кроме поля `generated_at`; в фикстуре у карточки не меньше двух ссылок.

AC-3. Построение модели командой `board` не меняет БД: число изменений соединения БД (`total_changes`), замеренное до и после вызова команды на уже открытом соединении, — 0.

AC-4. `board --md` и `board --html` строятся из той же модели, что `--json`: подмена модели меняет вывод обоих видов.

AC-5. «report без эпиков» на богатой фикстуре — не меньше двух проектов (артель и внешний), эскалированная задача, задача в неизвестном FSM состоянии — и на пустой доске выдаёт HTML-доску, побайтно равную эталону. Эталон — литерал, снятый кодом main до правки; его вносит сессия при Операторе командой `amend-tests` (разработчик эталон не пишет). До внесения эталона тест проверяет форму доски на той же фикстуре: колонки в порядке FSM, неизвестное состояние — в конце, метка проекта у плитки внешнего проекта, маркер эскалации, «Задач нет» на пустой доске.

AC-6. `report` с эпиком: внутри колонки сначала группа эпика с заголовком «<id эпика> <название>» и карточками этого эпика, затем карточки без эпика в прежнем порядке.

AC-7. Подмена `board.build_model` меняет доску `report`: подменённые значения карточки (название, состояние, `review_iters`, `escalated_from`, проект) видны на доске, настоящих нет.

AC-8. Карточка модели `board.py` несёт поля `review_iters`, `escalated_from` и `project` со значениями задачи из БД.

AC-9. `new … --ref kaiten:123` записывает ссылку (система `kaiten`, ключ `123`) в `external_refs`, и она видна в `cards[].refs` модели доски этой задачи с полями система, ключ, URL, кто и когда записал (кто и когда — непустые).

AC-10. `link task <id> <система> <ключ> --url <url>` добавляет ссылку задаче (видна в `cards[].refs` с этим URL), `link epic <id> <система> <ключ>` — эпику (видна в `epics[].refs`); две ссылки одного объекта идут в `refs` в порядке записи; `link --remove` с теми же реквизитами снимает ссылку (в модели её нет); `link` на несуществующий id задачи или эпика отказывает, в `external_refs` записи нет.

AC-11. Для проекта с заданным `policy.ref_required: <система>` `new` без `--ref` этой системы отказывает с причиной, задача не заводится; с `--ref <система>:<ключ>` — заводится.

AC-12. Для проекта с заданным `policy.ref_systems` `new --ref` и `link` с системой вне списка отказывают, ссылка не записывается; с системой из списка — записывается. Без `policy.ref_systems` принимается любая непустая система.

AC-13. Подзадача, заведённая пультом при делении родителя со ссылками, несёт копию ссылок родителя (`cards[].refs` подзадачи — те же система и ключ).

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (7 модулей `orchestrator/` + `tests/`); число критериев приёмки ≥ 10 (13); `budget_usd` ≥ $30 (рамка ТЗ — $60).

Материал для решения Оператора — обоснование монолита:
- Задача уже сама — нарезка ADR-0028 (шаг Э4 из Э0–Э4); рамка ТЗ $60 совпадает с оценкой шага в ADR ($45–60).
- Естественный разрез — «внешние ссылки» (`schema.py`, `store.py`, `catalog.py`, `targets.py`, `artel.py`: `new --ref`, `link`, `ref_required`, `ref_systems`, наследование частями) и «вывод модели» (`board.py`, `report.py`, `artel.py`: `board`, `report` из модели, поля плитки). Обе части трогают `orchestrator/artel.py` (регистрация команд `link` и `board`) — разрез идёт поперёк зоны, и вторая часть зависит от первой (`cards[].refs`/`epics[].refs` в модели, AC-1, AC-9, AC-10).
- Если Оператор предпочтёт деление: часть 1 — внешние ссылки, `ref_required`, `ref_systems`, наследование частями (без отображения в модели); часть 2 — `board`, `report` из модели, поля плитки и `refs` в модели, порядок «после части 1»; общий файл `orchestrator/artel.py` в зонах обеих частей.

## Не входит
- Интерфейс доски (веб, бот), адаптеры к трекерам, вызов и чтение внешнего трекера.
- Имя ветки по ключу трекера (ADR-0029) — здесь только хранение ключа.
- `status` и `epic show` из модели — шаг Э1; модель `board.py` как таковая — Э1, здесь — её вывод, поля плитки и `refs` в ней и `report` из неё.
- Новые команды (`board`, `link`) в обходе команд `tests/test_invariants.py` — операторский коммит после мержа (ADR-0028 п. 17, таблица «Порядок исполнения»).
- Смена ожидаемых значений существующих тестов `report`: вид отчёта без эпиков не меняется, раздел «Меняемое поведение» не нужен. Правка вызовов в тестах из раздела «Матрица неослабления» — только по мандату Оператора; иная правка существующих тестов — эскалация.
- Эталон-литерал AC-5 — вносит сессия при Операторе (`amend-tests`), не разработчик.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность защищённых путей и непревышение бюджета — их держит пульт.
