## Требования
1. **Вывод модели.** Команда `artel.py board --project <имя> [--json | --md | --html]` печатает модель доски `board.py` проекта:
   - `--json` — словарь с полем `schema_version` (контракт для будущего интерфейса доски), полями `columns`, `epics`, `cards`; у карточек — `waiting_on` и `refs`;
   - `--md` — таблица; `board` без флага вида печатает то же, что `--md`;
   - `--html` — страница.
   Все три вида строятся из одной модели. Команда не обращается к сети и не пишет в БД. Неизвестный проект (не заявлен в `targets.yaml`, и в БД нет ни задачи, ни эпика этого проекта) — отказ с причиной (назван проект).
2. **report из модели.** `report` строит модель `board.py` на каждый проект задач БД — все проекты, у которых есть задачи, включая не заявленные в `targets.yaml` (как сейчас `report.py:1440`, `:1378`), — и сводит карточки всех проектов в те же колонки, что сейчас, с нынешним порядком колонок и карточек. Всё, что показывает плитка доски, `report` берёт из модели.
   - «report без эпиков» (ни у одной задачи нет эпика): HTML-доска побайтно совпадает с выводом текущего `report`.
   - С эпиками: внутри колонки сначала идут группы эпиков в порядке id эпика — у группы заголовок «<id эпика> <название>», под ним карточки этого эпика по возрастанию id задачи, — затем карточки без эпика прежним порядком.
3. **report из модели — без `waiting_on`, число запросов.** `build_model` получает флаг расчёта `waiting_on` (например, `with_waiting`, по умолчанию включён). `report` строит модели с выключенным флагом: `waiting_on` не считается, `zone_lock.queue_wait` не вызывается (плитка `report` `waiting_on` не показывает). `status`, `epic show` и `board` считают `waiting_on` как сейчас — через `zone_lock.queue_wait` (`board.py:34`). `orchestrator/zone_lock.py` не меняется, логика очереди зон в `board.py` не копируется. `cmd_report` открывает соединение `store.db()` один раз за прогон и передаёт его `build_model`; построение моделей для `report` делает число запросов к таблице `steps`, не зависящее от числа задач (при том же множестве проектов).
4. **Карточка модели — поля плитки.** Карточка модели `board.py` (`cards[]`) расширяется полями, которые нужны плитке `report` (`report.py:565-593`): `review_iters`, `escalated_from`, проект задачи (`project`), — в дополнение к уже имеющимся `task`, `title`, `state`, `budget_usd`, `spent_usd`.
5. **Внешние ссылки — хранение.** В БД — таблица `external_refs` с полями: вид (`task` | `epic`), идентификатор задачи или эпика, система, ключ, URL (необязательно), кто записал и когда. На существующей БД без этой таблицы она создаётся при открытии `store.db()`. «Кто записал» — актор команды, записавшей ссылку: `operator` для `new --ref` и `link`; при копии ссылок частям деления (требование 11) — исходные автор и время ссылки родителя.
6. **Внешние ссылки — система и ключ.** Система — свободная непустая строка (например, `kaiten`, `gitlab-issue`); ключ — непустая строка. Ссылка с пустой системой или пустым ключом (`new --ref kaiten:`, `new --ref :123`, `link task <id> kaiten ''`, `link task <id> '' 123`) отказывает с причиной, ссылка не пишется. Если в записи проекта задано новое необязательное поле `policy.ref_systems` (список систем), система ссылки задачи или эпика этого проекта допустима только из этого списка; иначе запись ссылки отказывает с причиной.
7. **Внешние ссылки — запись.**
   - `new … --ref <система>:<ключ>` записывает ссылку задачи до создания её ветки; `--ref` можно указать несколько раз — записываются все ссылки; значение `--ref` делится по первому «:» — система до него, ключ после, ключ с «:» внутри (`--ref gitlab-issue:grp/proj:42`) сохраняется целиком; значение без «:» отказывает с причиной, задача не заводится;
   - `artel.py link <task|epic> <id> <система> <ключ> [--url …]` добавляет ссылку задаче или эпику; повторный `link` той же системы и того же ключа тому же объекту дубля не создаёт;
   - `artel.py link --remove …` снимает ссылку; `--remove` несуществующей ссылки отказывает с причиной; `--remove` последней ссылки задачи в системе, которую требует `policy.ref_required` её проекта (требование 9), отказывает с причиной (названа система), ссылка остаётся;
   - `link` на несуществующий id задачи или эпика отказывает с причиной и ничего не записывает.
8. **Внешние ссылки — в модели.** Ссылки входят в модель доски: `cards[].refs` у задач, `epics[].refs` у эпиков. Элемент `refs` несёт систему, ключ, URL (или пусто), кто и когда записал; ссылки идут в порядке времени записи. Пульт внешний трекер не вызывает и не читает.
9. **`policy.ref_required`.** Новое необязательное поле записи проекта `policy.ref_required` (по умолчанию не задано) называет систему внешних ссылок. Если поле задано, `new` в этот проект без `--ref` этой системы отказывает с причиной (названа требуемая система). К учебной задаче канарейки (`cmd_new(canary=True)`, `canary_drive.py:54`) `ref_required` не применяется.
10. **Отказ `new` до побочных эффектов.** Отказ `new` по `ref_required` (требование 9) или по `ref_systems` (требование 6) происходит до создания ссылки документов задачи (`catalog.py:738`): после отказа нет ни строки задачи, ни ссылки `refs/artifacts/<id>`.
11. **Части деления наследуют ссылки.** Подзадачи, которые пульт заводит при делении (`catalog.spawn_subtask`, зов `fsm.py:1070`), получают копию `external_refs` родителя при заведении — `ref_required` делением не обходится; у копии автор и время — те же, что у ссылки родителя (требование 5).

## Критерии приёмки
AC-1. `board --project <проект> --json` песочного проекта с эпиком печатает словарь с полями `schema_version`, `columns`, `epics`, `cards`; каждая карточка несёт поля `waiting_on` и `refs`.

AC-2. Два вызова `board --json` одного проекта без изменений БД между ними дают одинаковый вывод, кроме поля `generated_at`; в фикстуре у карточки не меньше двух ссылок.

AC-3. Команда `board` не меняет БД: `store.db()` подменён измеряемым соединением (тем, через которое команда работает), и число его изменений (`total_changes`) до и после вызова команды — 0; запись через собственное соединение команды этим замером ловится. `board` (все три вида) и `report` работают без сети: при подменённых `socket` (создание соединения) и сетевых вызовах git (`fetch`/`push`/`ls-remote`) ни одного обращения за прогон команды нет.

AC-4. `board --md` и `board --html` строятся из той же модели, что `--json`: подмена модели меняет вывод обоих видов; `board` без флага вида печатает то же, что `board --md`; `board --project` неизвестного проекта (нет в `targets.yaml`, нет задач и эпиков в БД) отказывает с причиной, в которой назван проект.

AC-5. «report без эпиков» на богатой фикстуре — не меньше двух заявленных проектов (артель и внешний), id карточек двух проектов чередуются (в одной колонке по возрастанию id идут задача проекта А, задача проекта Б, снова задача проекта А), задача проекта, не заявленного в `targets.yaml`, эскалированная задача, задача в неизвестном FSM состоянии — и на пустой доске выдаёт HTML-доску, побайтно равную эталону. Эталон — литерал, снятый кодом main до правки; его вносит сессия при Операторе командой `amend-tests` (разработчик эталон не пишет). До внесения эталона тест проверяет форму доски на той же фикстуре: колонки в порядке FSM, неизвестное состояние — в конце, метка проекта у плитки внешнего проекта, плитка задачи незаявленного проекта на доске с его меткой, маркер эскалации, «Задач нет» на пустой доске.

AC-6. `report` с двумя эпиками в одной колонке: внутри колонки сначала группы эпиков в порядке id эпика, у каждой заголовок «<id эпика> <название>» и карточки этого эпика по возрастанию id задачи, затем карточки без эпика в прежнем порядке. В фикстуре у одного эпика в колонке не меньше двух карточек, заведённых в БД в порядке, обратном id; вывод в обратном порядке id внутри группы проваливает критерий.

AC-7. Подмена `board.build_model` меняет доску `report`: подменённые значения карточки (название, состояние, `review_iters`, `escalated_from`, проект) видны на доске, настоящих нет.

AC-8. Карточка модели `board.py` несёт поля `review_iters`, `escalated_from` и `project` со значениями задачи из БД.

AC-9. `new … --ref kaiten:123` записывает ссылку (система `kaiten`, ключ `123`) в `external_refs`, и она видна в `cards[].refs` модели доски этой задачи с полями система, ключ, URL, кто и когда записал (кто — `operator`, когда — непустое); `new` с двумя `--ref` записывает обе ссылки. `new --ref gitlab-issue:grp/proj:42` записывает систему `gitlab-issue` и ключ `grp/proj:42` целиком; `new --ref kaiten123` (без «:») отказывает с причиной — нет ни строки задачи, ни ссылки в `external_refs`. Ссылка записывается до создания ветки задачи: в момент вызова `catalog._ensure_task_worktree` (создание ветки и рабочей копии, `catalog.py:694`) строка `external_refs` этой задачи уже есть в БД.

AC-10. `link task <id> <система> <ключ> --url <url>` добавляет ссылку задаче (видна в `cards[].refs` с этим URL, кто записал — `operator`), `link epic <id> <система> <ключ>` — эпику (видна в `epics[].refs`); две ссылки одного объекта идут в `refs` в порядке записи; повторный `link` той же системы и ключа тому же объекту не добавляет вторую строку в `external_refs`; `link --remove` с теми же реквизитами снимает ссылку (в модели её нет); `link --remove` несуществующей ссылки отказывает с причиной; `link` на несуществующий id задачи или эпика отказывает, в `external_refs` записи нет.

AC-11. Для проекта с заданным `policy.ref_required: <система>` `new` без `--ref` этой системы отказывает с причиной (названа система): задача не заводится, ссылки `refs/artifacts/<id>` нет; с `--ref <система>:<ключ>` — заводится. Учебная задача канарейки (`cmd_new(canary=True)`) в проект с `ref_required` заводится без `--ref`. `link --remove` единственной ссылки требуемой системы у задачи этого проекта отказывает с причиной (названа система), ссылка остаётся в `external_refs` и в `cards[].refs`; при второй ссылке той же системы `--remove` одной из них снимает её.

AC-12. Для проекта с заданным `policy.ref_systems` `new --ref` и `link` с системой вне списка отказывают, ссылка не записывается; после отказа `new` нет ни строки задачи, ни ссылки `refs/artifacts/<id>`; с системой из списка — записывается. Без `policy.ref_systems` принимается любая непустая система; пустая система (`new --ref :<ключ>`, `link task <id> '' <ключ>`) и пустой ключ (`new --ref kaiten:`, `link task <id> kaiten ''`) отказывают с причиной, ссылка не записывается (после отказа `new` нет и строки задачи).

AC-13. Подзадача, заведённая пультом при делении родителя со ссылками, несёт копию ссылок родителя (`cards[].refs` подзадачи — те же система, ключ, URL, а кто и когда записал — те же, что у ссылки родителя).

AC-14. `cmd_report` на наборе из 2 задач и на наборе из 7 задач — одно и то же множество проектов в обоих наборах, в обоих есть задачи `in_dev` с зонами — делает одинаковое число запросов к `steps`, по одному запросу `store.last_step_times` на проект; в каждом прогоне `store.db()` вызывается один раз, `zone_lock.queue_wait` не вызывается. `board --json` того же проекта при задаче `in_dev`, ожидающей зону, несёт у её карточки `waiting_on` из `zone_lock.queue_wait` (`dependency`).

AC-15. На БД, созданной без таблицы `external_refs` (схема до этой задачи), открытие `store.db()` создаёт таблицу; `board --json` на такой БД печатает модель с пустыми `refs`, `link` записывает ссылку.

## Оценка объёма и деление
Сработавшие сигналы: число файлов зоны ≥ 5 (7 модулей `orchestrator/` + `tests/`); число критериев приёмки ≥ 10 (15); `budget_usd` ≥ $30 (рамка ТЗ — $60).

Материал для решения Оператора — обоснование монолита:
- Задача уже сама — нарезка ADR-0028 (шаг Э4 из Э0–Э4); рамка ТЗ $60 совпадает с оценкой шага в ADR ($45–60).
- Естественный разрез — «внешние ссылки» (`schema.py`, `store.py`, `catalog.py`, `targets.py`, `artel.py`: таблица и её догон на старой БД, `new --ref`, `link`, `ref_required`, `ref_systems`, наследование частями) и «вывод модели» (`board.py`, `report.py`, `artel.py`: `board`, `report` из модели без `waiting_on`, поля плитки). Обе части трогают `orchestrator/artel.py` (регистрация команд `link` и `board`) — разрез идёт поперёк зоны, и вторая часть зависит от первой (`cards[].refs`/`epics[].refs` в модели, AC-1, AC-9, AC-10).
- Если Оператор предпочтёт деление: часть 1 — внешние ссылки, догон таблицы, `ref_required`, `ref_systems`, канарейка, наследование частями (без отображения в модели); часть 2 — `board`, `report` из модели, число запросов к `steps`, поля плитки и `refs` в модели, порядок «после части 1»; общий файл `orchestrator/artel.py` в зонах обеих частей.

## Не входит
- Интерфейс доски (веб, бот), адаптеры к трекерам, вызов и чтение внешнего трекера.
- Имя ветки по ключу трекера (ADR-0029) — здесь только хранение ключа.
- `status` и `epic show` из модели — шаг Э1; модель `board.py` как таковая — Э1, здесь — её вывод, поля плитки, флаг расчёта `waiting_on` и `refs` в ней и `report` из неё.
- Правка `orchestrator/zone_lock.py` и пакетное чтение журнала для `waiting_on` (копия логики очереди зон в `board.py`): `report` строит модель без `waiting_on` (требование 3). Тесты Э1 `tests/test_01m5tbbdfs6dwqy6ms263t1kpy_board_model.py:202`, `:222` не затрагиваются.
- Правка `orchestrator/canary_drive.py`: канарейка исключается из `ref_required` на стороне `new`.
- Новые команды (`board`, `link`) в обходе команд `tests/test_invariants.py` — операторский коммит после мержа (ADR-0028 п. 17, таблица «Порядок исполнения»).
- Смена ожидаемых значений существующих тестов `report`: вид отчёта без эпиков не меняется, раздел «Меняемое поведение» не нужен. Правка вызовов в шести методах `tests/test_report.py` из «Матрицы неослабления» — по мандату `ANSWER-1.md`; `tests/test_report.py:1018`, `tests/test_01m4rzayh3swjw4wfbw4qw15fp_command_report.py:524`, `:550` и прочие существующие тесты не меняются; иная правка существующих тестов — эскалация.
- Эталон-литерал AC-5 — вносит сессия при Операторе (`amend-tests`), не разработчик.
- Полный зелёный набор `tests/`, зелёный CI ветки, неизменность защищённых путей и непревышение бюджета — их держит пульт.
