# SPEC-AUDIT: GitLab В1.1 — источник полного набора `full_suite: local | ci | both` на приёмке

## ТЗ и SPEC
Сверено с ТЗ, с SPEC родителя (`refs/artifacts/01M5XX9PW3K206Q3EKQCT649QF`,
подраздел «GitLab В1.1» и требования 1–4, 7, AC-1…AC-13) и с ANSWER-1/2/3
родителя. Требования 1–5 SPEC и AC-1…AC-13 совпадают с родителем почти
дословно. Решения перенесены: ANSWER-1 (номер задания вместо номера
конвейера, наибольший `id`) — SPEC.md:106-110; ANSWER-2 в.2 (три
условия, «неизвестно» вместо локального прогона, `--fresh-suite`
перечитывает CI) — SPEC.md:78-87; ANSWER-2 в.7 (`report` обязателен) —
SPEC.md:67-68; ANSWER-2 в.1 (локальный набор гейта мержа) — «Не входит»;
ANSWER-3 в.3 (тесты задачи на `in_dev → verifying`) — SPEC.md:111-114;
П1 гейта SPEC родителя (не-`success` статус — «неизвестно» независимо
от отчёта) — SPEC.md:100-105. Требований сверх ТЗ нет.

Расхождения:
- А1 (мелкое). Из фактов ТЗ выпал один: «`targets.py` не импортирует
  `forge`, а `forge` импортирует `targets` на верхнем уровне» (TZ.md:38-39;
  `forge.py:16`). В SPEC этого нет, а от него зависит, как сделать
  проверку реестра в требовании 1 (SPEC.md:64-66): нужен отложенный импорт
  или передача реестра. Следующие роли брифуются по SPEC и этого факта не
  увидят.
- А2 (мелкое). В строке матрицы родителя «Неизвестно не принимается
  `--accept-red`» есть оговорка «обрезанный отчёт не проходит через
  `--accept-red`», а в матрице SPEC (SPEC.md:209) её нет. Обрезанный
  отчёт — это по сути `TestReport(None, …)` (`gitlab_adapter.py:305-307`,
  `:476-494`), а он покрыт случаем «отчёт `None`» в AC-8. Это потеря
  формулировки, а не свойства.

|---|---|---|

| AC-2 | да | `ci_job` разрешён при `local` или при отсутствии `full_suite` |
| AC-3 | да | сравнение хостинга с литералом `"gitlab"` вместо проверки реестра (реестр подменён); проверка пропущена при `both` |

| AC-6 | да | берётся наименьший `id` попытки; в записи не тот sha или не то число тестов; зелёный не признан |

| AC-8 | да | любой из перечисленных случаев даёт зелёный или красный (тогда его принял бы `--accept-red`); не-`success` статус при отчёте с `failed` даёт красный |

| AC-11 | да | в `both` учтён только один источник; «неизвестно» CI при красном локальном даёт красный |

| AC-13 | да | `fsm_autogate.py:426` не расширен: зелёная приёмка `ci` подписана как локальный прогон |

Отклонения:
- В1. AC-1 (SPEC.md:134-135) проверяет только `ci` без `ci_job`.
  Требование 1 (SPEC.md:62-63) делает `ci_job` обязательным и при
  `both`. Нужен случай `both`, как в AC-3 и AC-4.
- В2. Ни один AC не проверяет отказ на значении `full_suite` вне
  `local | ci | both` (требование 1, SPEC.md:61). Отказ, называющий поле,
  требование заявляет («Каждый отказ загрузки называет имя поля»,
  SPEC.md:69), но тестом он не закреплён.
- В3. AC-9 (SPEC.md:175-180) не требует базы проекта, отличной от `main`.
  Мутация из Б1 остаётся незамеченной.
- В4. Требование 2 перечисляет четыре невыполненных условия, а AC-9
  проверяет два. Взаимодействие `fresh=True` с тремя условиями (AC-10)
  не проверяется.

## Зоны
Зоны SPEC (`targets.py`, `project_profile.py`, `acceptance.py`,
`fsm_autogate.py`, `ci.py`, `tests/`) покрывают всё, что заставляют
менять требования 1–4:
- проверка полей и реестра — `targets.py`;
- поля профиля — `project_profile.py`, вместе с `with_tools`;
- источник итога — `acceptance.py`;
- распознавание записи — `fsm_autogate.py:426`.

Карта `docs/codebase-map.md` входит в `config.COMMON_ZONES`
(`config.py:864`). Защищённых путей задача не трогает (`skills/`,
`templates/`, `gates.yaml`, `roles.yaml`, `.github/` не задеты). Песочница
не расширяется. Пути «только чтение» из ТЗ перенесены в «Не входит».
Лишних зон нет; `ci.py` взята на случай общего помощника и вреда не
несёт. Отклонений нет.

## Матрица неослабления

строк не хватает для свойств, которые задача трогает:

|---|---|---|---|---|
| Источник итога в `ci`/`both`, ранний выход из `_acceptance_suite_run` | `checks_local` исполняются после итога любого источника — `acceptance.py:3388-3411` (SPEC 01M590GJAF0EDV4NBC4C99MFVH, требование 13) | должно остаться: требование 2 правит `_acceptance_suite_run`, а не `acceptance_suite` | не покрыто: ни один AC не проверяет, что упавший `checks_local` красит зелёный итог CI в `ci` | отклонение Д1 |
| Распознавание итога CI автогейтом | `fsm_autogate.py:426` (подстрока «принят итог CI»), запись артели — прежние тесты автогейта | да: требование 5 + AC-13 | AC-13; для артели прежние тесты | строки в SPEC нет — отклонение Д2 (мелкое) |

- Д1. Свойство «`checks_local` после любого источника»
  (`acceptance.py:3376-3411`) задача трогает: в `ci`/`both` появляется
  новый источник. В матрице этого свойства нет, и ни один AC его не
  проверяет.
- Д2. Строки для `fsm_autogate.py:426` в матрице нет, хотя автогейт
  меняется.

Раздела «Меняемое поведение» в SPEC нет; правка существующих тестов не
заявлена (SPEC.md «Не входит»). Это согласуется с ТЗ («ожидается — нет»).

## Пути обхода гейтов
- Е1. Ранний возврат итога CI в обход `checks_local` (Д1). Исполнитель
  может вынести ветку `ci` в `acceptance_suite` до `run_checks_local`
  или вернуть итог CI из `_acceptance_suite_run` так, что упавший
  `checks_local` не покрасит зелёный итог. AC-6…AC-13 этого не увидят.
- Е2. Буквальный перенос условия свежести артели — `origin/main`
  (Б1). Проекты с другой базой получат проверку свежести не той ветки:
  голова, несвежая относительно базы, пройдёт, если содержит
  `origin/main`; свежая получит «неизвестно», если `origin/main` в неё
  не входит.
- Е3 (на заметку Оператору; не требование ТЗ). `ci_job` — любое имя
  задания. Задание, гоняющее подмножество тестов, даёт зелёный итог
  полного набора: пульт не сверяет его состав с локальным набором. Гейт
  по исходам с находкой о пропавших тестах на мерже — это часть 2
  (В1.2, матрица родителя, строка «Набор задания CI задаёт конфигурация
  CI ветки»). Между вливанием частей 1 и 2 этой защиты нет. Риск сейчас
  ограничен: `ci`/`both` допустимы только у хостинга с
  `job_test_report`, то есть у `gitlab`, а GitLab не входит в
  `SUPPORTED_FORGES` (`targets.py:29`) до Б2.3.
- Е4 (уже существует, не меняется задачей). `approve` при worktree, не
  стоящем на ветке задачи, пропускает полный набор и проходит
  (`fsm.py:1544-1551`). В режиме `ci` worktree итогу не нужен, но путь
  пропуска остаётся тем же. `fsm.py` по ТЗ только для чтения, поэтому это
  не отклонение SPEC, а сведение для Оператора.
