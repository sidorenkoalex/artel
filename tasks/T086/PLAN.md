# PLAN: verifying — auto-опрос CI и потолок по времени

## Подход

`auto` становится владельцем опроса CI в `verifying`, а потолок ожидания
меняет единицу измерения с попыток на время. Оба требования решаются
внутри существующих точек входа (`orchestrator/auto.py`,
`orchestrator/fsm.py`) — новой роли/состояния FSM не заводится,
трактовка исходов `ci.verifying_status` (SPEC T079/ADR-0009) не
меняется.

1. **Опрос владеет `auto`, не отдельный поток**. Главный цикл
   `_cmd_auto` (`orchestrator/auto.py`) сегодня — `while role is not
   None`, где `role = runner.step_role(t)`; `verifying` не входит в
   `STATE_ROLE`, поэтому роль `None` уже на входе, и цикл выходит,
   даже не заглянув в CI. Меняю условие на `while role is not None or
   state == "verifying"` и добавляю в тело ветку `if state ==
   "verifying":`, которая делает ОДИН advance-опрос (`fsm.cmd_advance`,
   ту же функцию, что вызывает ручной Оператор) и решает: перейти к
   следующей итерации без паузы (CI зелёный — `cmd_advance` уже увёл
   задачу в `acceptance`, дальше решает обычный конец цикла), сразу
   остановиться с подсказкой `reject` (завершённый красный CI), или
   поспать `config.VERIFYING_POLL_INTERVAL_SEC` и повторить (CI не
   отвечает или ещё идёт). Эта ветка живёт ДО блока, считающего
   `steps`/`AUTO_MAX_STEPS`, — пауза внешнего ожидания не шаг конвейера
   (требование 1, AC-2).

   Условие цикла через `or state == "verifying"` (не отдельный
   вызов-обёртка вокруг всего `_cmd_auto`) осознанно: `verifying`
   достижим и КАК СТАРТОВОЕ состояние вызова, и КАК РЕЗУЛЬТАТ обычного
   шага изнутри цикла (review → verifying при approved-вердикте,
   ADR-0009) — второе не покрыть однократной проверкой на входе в
   функцию, а именно это ловит существующий дев-тест
   `test_cycle_runs_the_task_from_dev_to_verifying`.

2. **Различение «красный, стоп» от «не отвечает/идёт, жду ещё» без
   повторного чтения CI**. `fsm.cmd_advance` для `verifying` уже
   журналирует прочитанный `note` действием «статус CI ветки
   (verifying)» — новая `ci.verifying_is_red(note)` (тот же приём, что
   уже несёт `ci.status_kind` для `branch_status`: сверка по
   подстроке, которую сама `verifying_status` кладёт в `note` для
   красного исхода — `"не зелёный:"`, уникальной среди всех четырёх
   исходов) читает эту строку из журнала вместо второго вызова
   `ci.verifying_status`. Один `gh`-опрос на итерацию, не два.

3. **Потолок — время, не попытки**. `orchestrator/fsm.py`, ветка
   `elif state == "verifying"`: заменяю `attempts >=
   config.LIMIT_VERIFYING_ATTEMPTS` на `elapsed >=
   config.VERIFYING_CEILING_SEC`, где `elapsed` — секунды с
   `t["updated_at"]` (момент последнего `set_state -> verifying`,
   пишется с точностью до микросекунд уже сегодня, `store.set_state`)
   до `datetime.now(timezone.utc)`. `tasks.verifying_attempts`
   остаётся в схеме и продолжает инкрементироваться — только
   информационно, без участия в условии эскалации (требование 3).
   `config.LIMIT_VERIFYING_ATTEMPTS` удаляется как константа: она
   ничего больше не решает, оставлять её было бы мёртвым кодом.

4. **`config.AUTO_STOP["verifying"]` становится недостижим и
   удаляется**. С новой веткой `_cmd_auto` состояние `verifying`
   больше не долетает до общего конца функции
   (`auto_stop_advice`/`AUTO_STOP.get(state, ...)`) ни в одном
   исходе — красный останавливает цикл сам, зелёный уводит дальше,
   потолок эскалирует. Оставлять запись в словаре — не тестируемый
   контракт, а труп. Подсказку для красного CI несёт новая пара
   `config.AUTO_STOP_VERIFYING_RED` (тот же приём, что
   `AUTO_STOP_BUDGET`/`AUTO_STOP_PAUSE` — стоп-условия вне словаря
   состояний, потому что зависят не только от имени состояния).

## Шаги

1. `orchestrator/config.py`: `LIMIT_VERIFYING_ATTEMPTS` →
   `VERIFYING_POLL_INTERVAL_SEC` (90) + `VERIFYING_CEILING_SEC`
   (90×60); убрать `"verifying"` из `AUTO_STOP`, добавить
   `AUTO_STOP_VERIFYING_RED`.
2. `orchestrator/ci.py`: `verifying_is_red(note)` — тот же приём, что
   `status_kind`.
3. `orchestrator/fsm.py`: ветка `verifying` — потолок по времени
   (`_verifying_elapsed_seconds`, новый маленький хелпер модуля) вместо
   попыток; `verifying_attempts` остаётся информационным.
4. `orchestrator/auto.py`: новая ветка цикла `_cmd_auto` для `state ==
   "verifying"` (advance-опрос, пауза, красный стоп) +
   `_verifying_poll_note` (тот же приём отсечки журнала, что
   `_advance_refusal` в этом же файле).
5. Юнит-тесты: `tests/test_auto_cycle.py` (дефолтная CI-фикстура
   песочницы — красный CI, правки трёх сломанных сборкой ассертов,
   новый тест на зелёный CI мид-цикла), `tests/test_ci_status.py`
   (`verifying_is_red`), новый `tests/test_verifying_ceiling.py`
   (потолок по времени и информационность счётчика попыток в
   `fsm.py`, независимо от `auto`).
6. Прогон `tasks/T086/acceptance_tests/` + `python3 -m unittest
   discover -s tests` + `scripts/guard.py`.

## Влияние на систему

- **`config.LIMIT_VERIFYING_ATTEMPTS` удаляется.** Единственные
  читатели — сама ветка `fsm.py`, которую эта задача и меняет; поиском
  по репозиторию (codebase-map, grep) подтверждено отсутствие других
  ссылок. Не ослабление лимита (ADR-0002) — замена одной единицы
  измерения потолка на другую по прямому мандату SPEC (требование 3).
- **`config.AUTO_STOP["verifying"]` удаляется**, `test_stop_table_
  covers_every_state_outside_state_role` (tests/test_auto_cycle.py)
  правится на явное исключение `verifying` из проверяемого множества —
  единственный тест, зависевший от полноты этого словаря по всем
  состояниям вне `STATE_ROLE`; он же документирует происходящее
  исключение комментарием.
- **Дефолтная CI-фикстура `tests/test_auto_cycle.py` меняется на
  красный CI** (сейчас ни один тест этого файла CI не мокает —
  `verifying` был безусловной остановкой). Без неё уже существующие
  тесты, гоняющие `self.auto()` по всем состояниям FSM (`FSM_STATES`,
  включая `verifying`), реально уснули бы на `time.sleep(90)` вечно
  (CI-статус без мока — `VERIFYING_NONE`, а он не стоп-условие).
  Красный — не GREEN, потому что: (а) он не меняет наблюдаемое
  поведение большинства уже написанных тестов (задача остаётся в
  `verifying`, агент не звался — то же самое, что и раньше по
  случайной, а не намеренной причине); (б) он единственный исход,
  воспроизводящий старое «стоп сразу, без цикла» — переключение на
  зелёный потребовало бы протащить через ВЕСЬ файл новую точку
  остановки (`acceptance`) и правку счётчиков шагов там, где сейчас их
  не ждут.
- **Приёмочные тесты T086 (`tasks/T086/acceptance_tests/`) залочены**
  (наследие T023) — код подгоняется под них, а не наоборот; в PLAN
  учтены буквально (см. `_sandbox.py` этого набора: `VerifyingTest`
  патчит `runner.cmd_run` на бросок при любом вызове — подтверждает,
  что опрос `verifying` не имеет права стартовать агента, ветка 1
  подхода это не нарушает).
- **Инвариант 18** (`auto` не проходит ручные гейты) не затронут:
  переход `verifying -> acceptance` уже автоматический при зелёном CI
  (ADR-0009), auto лишь опрашивает то же самое чаще; approve/reject
  на `acceptance`/`merge_gate` по-прежнему только у Оператора.
- **Откат**: оба изменения (владелец опроса, единица потолка) —
  чистая замена условий внутри `auto.py`/`fsm.py`, без миграции схемы
  (`tasks.verifying_attempts`/`updated_at` уже существуют) — откатывается
  возвратом старых констант и веток без следов в БД.

## Риски

- Двойной GH-запрос за опрос отсутствует (см. подход, п.2) —
  осознанно проверено при разработке; если бы пришлось матчить текст
  по-другому, риск был бы «опрос дороже, чем кажется» под нагрузкой
  сессии Оператора с несколькими параллельными задачами в `verifying`.
- Формулировка `"не зелёный:"` в `ci.verifying_is_red` — зависимость
  от точного текста, который генерирует сама `ci.verifying_status`
  (не внешний источник) — риск разъезда только при будущей правке
  этого текста в одном файле без парного обновления другого; помечено
  докстрингом на обеих сторонах.
