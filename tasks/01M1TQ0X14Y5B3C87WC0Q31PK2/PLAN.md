# PLAN: отказ push артефактной ветки в журнал и на повтор; doctor сверяет локальный ref с origin и CI артефактной ветки

## Подход

Классификация причины отказа push и её журналирование переезжают ВНУТРЬ
`artifact_branch.push(task_id)` (было — голый `git push`, `bool` без
единой записи журнала); вызывающий код продолжает звать `push` явно, как
и раньше — `push` не встраивается в `commit_files` автоматически.
Первая версия этого плана пробовала обратное (звать `push` изнутри
`commit_files` безусловно, чтобы получить push+журнал «бесплатно» для
всех трёх мест требования 1 разом) — эта версия сломала `test_ac6_
doctor_artifact_branch_sync.py`: планка НАМЕРЕННО строит расхождение
локального ref и origin голым `artifact_branch.commit_files` без
последующего push (`DoctorArtifactBranchSyncTest`/сосед в `_sandbox.py`
— «спека v2, не запушена»), и автоматический push внутри `commit_files`
доставил бы этот коммит в origin тем же вызовом, который обязан был
оставить его локальным. Раз локованная планка полагается на «`commit_
files` не пушит сама» — это и есть настоящий контракт функции, план
правится под него, а не наоборот.

Значит push остаётся явным вызовом на стороне каждого места требования 1:
- автокоммит шага (`checkpoint._commit_external_step_artifacts`,
  покрывает и таймаут, и аварийное завершение, и `pause --now` — все
  три чекпоинта зовут этот общий хелпер) — вызов `artifact_branch.push`
  там уже есть, меняется только то, что теперь он классифицирует и
  журналирует исход, а не отбрасывает `bool`;
- `catalog._new_external_artifact_branch` (`cmd_new`) — вызов тоже уже
  есть, та же правка внутри `push`;
- `answer._cmd_answer` (ANSWER Оператора) — вызова НЕ было вовсе
  (`answer.py` до этой задачи push не звал). Добавляется одна строка
  `artifact_branch.push(task_id)` после `commit_files`.

`orchestrator/answer.py` не входит в `zones` SPEC (зона называет только
`artifact_branch.py`, `checkpoint.py`, `doctor.py`, `catalog.py`,
`tests/`), хотя требование 1 SPEC явно называет ANSWER Оператора местом
вызова push, и локованный `tasks/.../acceptance_tests/
test_ac1_ac2_push_failure_no_origin.py::AnswerPushFailureTest` это
проверяет буквально — приоритет у планки (она и есть договор
приёмки), не у списка `zones`. Правка — одна строка, добавляющая уже
существующий в кодовой базе вызов (`artifact_branch.push`, тот же, что
`checkpoint.py`/`catalog.py` уже делают) в третье такое же место — не
новая механика, не архитектурное решение, весь риск площади правки —
одна строка кода + докстринг. Раздел «Расширение зон» ниже запрашивает
у Оператора мандат на неё явно (гейт `in_dev -> review`,
`fsm_advance._zones_gate_refuses`, откажет переход без него — это
штатный самообслуживаемый путь системы для ровно такой ситуации, не
эскалация: гейт печатает подсказку «оформи раздел «## Расширение
зон»... и повтори advance», а не уводит задачу в `escalated`).

`push(task_id) -> bool` сохраняет контракт возврата (bool, best-effort,
исключений наружу не бросает — AC-2), но теперь: (а) при отсутствии
origin (`gitcmd.has_no_remote`) классифицирует немедленно как «нет
origin» без попытки реального push; (б) иначе зовёт `git push` и при
отказе классифицирует stderr на «сеть»/«non-fast-forward» по подстрокам
(`rejected`/`fetch first` — реальный текст git при разошедшихся ветках,
проверено вживую бэйр-репозиторием; иначе — «сеть», единственный
оставшийся вариант требования 1); (в) журналирует исход через свежее
`store.db()`-соединение (та же цена, что уже платят `answer.py`/
`amend.py`/`catalog.py` в похожих местах без готового `conn` под рукой;
циклического импорта нет — `store.py` тянет `artifact_branch` только
отложенным импортом внутри функции). Успех тоже журналируется отдельной
строкой (AC-3: повторная попытка на следующем автокоммите обязана
оставить СВОЮ запись про исход, не молчать так же, как молчал бы
сегодняшний код).

Повтор (требование 2/AC-3) получается без отдельного флага-состояния:
`push` вызывается на каждом коммите КАЖДЫМ вызывающим местом заново,
включая случаи, когда предыдущий push проваливался, — персистентный
флаг «не пробовать больше» не заводится (тест `test_ac3_push_retry_
after_prior_failure.py` явно ловит такую «оптимизацию» как мутацию).

`doctor` получает две новые независимые проверки (требования 3-4):
`check_artifact_branch_sync` сравнивает `gitcmd.branch_head_sha` и
`gitcmd.remote_branch_sha` (последний уже читает origin ЖИВЫМ
`ls-remote`, не локальный tracking-ref — ровно то, что нужно против
инцидента «внешний коммит Оператора в origin, локальный не в курсе»)
для нетерминальных задач target artel; направление расхождения —
`git merge-base --is-ancestor` по обоим sha (через `gitcmd.git` —
обёртки в `gitcmd.py` не заводится, `gitcmd.py` не в зоне этой задачи),
предварённое точечным `git fetch -q origin <branch>` — без него
объект origin-коммита, полученного только через `ls-remote`, может
отсутствовать в локальной объектной базе, и `merge-base` отказывает
кодом 128 на обеих сверках сразу (поймано юнит-тестом на реальном
бэйр-репозитории при первой попытке — без fetch линейное расхождение
ошибочно читалось как «разошлись»). `check_artifact_branch_ci` — тот
же приём, что `ci.verifying_status` для `verifying`: `gh run list
--branch <branch>`, но собственным вызовом `ci.gh(...)` с расширенным
набором полей `--json` (добавлены `name`,`workflowName` — имя упавшей
джобы для AC-7), не правкой `ci.run_list` — `orchestrator/ci.py` не в
зоне этой задачи, а `ci.gh` уже публичная точка входа, которую
подменяют и приёмочные тесты этой задачи, и `ci.run_list` сама. Обе
проверки — новые записи в `all_checks`, ничего не блокируют (требование
4/AC-7 — «не входит» блокирующий гейт: ни `fsm.py`, ни `fsm_advance.py`,
ни `fsm_merge_gate.py` их не импортируют).

## Шаги

1. `orchestrator/artifact_branch.py`: классификация причины отказа push
   (`нет origin`/`сеть`/`non-fast-forward`), журналирование успеха и
   отказа (с обоими sha и подсказкой «свести merge-коммитом» для
   non-fast-forward) внутри `push`. `--force`/`-f`/`--force-with-lease`
   нигде не появляются — единственная команда push остаётся тем же
   безусловным `git push -q origin <branch>:<branch>` (AC-4).
2. `orchestrator/checkpoint.py`, `orchestrator/catalog.py`: докстринги,
   отражающие новое поведение `push` (классификация/журнал) — код
   вызова не меняется, он уже звал `push` на своём месте.
3. `orchestrator/answer.py` (расширение зон, см. ниже): добавить
   `artifact_branch.push(task_id)` после `commit_files` в `_cmd_answer`
   (AC-1, место вызова ANSWER Оператора).
4. `orchestrator/doctor.py`: `check_artifact_branch_sync` (AC-6),
   `check_artifact_branch_ci` (AC-7), обе добавлены в `all_checks`;
   `ci` — новый импорт модуля.
5. Юнит-тесты: `tests/test_artifact_branch_push.py` (классификация,
   журналирование успеха/отказа, отсутствие `--force` мутационно, на
   настоящем git — бэйр-репозиторий + внешний коммит в обход пульта),
   `tests/test_doctor_artifact_branch_sync.py` (пять исходов — ok, три
   направления warn, skip), `tests/test_doctor_artifact_branch_ci.py`
   (ok/warn/skip/исключение терминальных и чужого target). Существующие
   `tests/test_checkpoint*.py`, `tests/test_doctor.py`,
   `tests/test_answer*.py`, `tests/test_amend.py`, `tests/test_doctor_
   fix_ignored_artifacts.py`, `tests/test_multitarget.py`,
   `tests/test_catalog_new_race.py` прогнаны по модулям без правки
   ассертов (AC-8) — все зелёные.

## Влияние на систему

`push(task_id)` — единственная точка вызова `git push` в кодовой базе
для артефактной ветки; правка классификации/журнала внутри неё не
меняет то, ЧТО она отправляет (`git push -q origin <branch>:<branch>`,
без `--force`) — только то, что теперь пишет в журнал задачи. Три
существующих места вызова (`checkpoint.py`, `catalog.py`, теперь и
`answer.py`) не меняют own логику вокруг push — оборачивают тот же
вызов, что и раньше. Инвариант «push артефактной ветки не форсируется»
(AC-4) не ослабляется — единственная команда push как была без
`--force`/`-f`/`--force-with-lease`, так и остаётся; повтор (AC-3) не
добавляет силового пути, юнит- и приёмочный тесты ловят это мутационно
(spy на `gitcmd.git`).

`doctor` — только информационные `warn`/`skip`, ни одна из двух новых
проверок не заводит запись в `alerts` и не читается ни одним гейтом FSM
— требование «не входит» (блокирующий гейт CI артефактной ветки)
выполнено по построению, не отдельной проверкой.

Откат — правка локальна к четырём файлам (три зоны + `answer.py` по
мандату расширения), `git revert` коммита достаточно; данных/схемы БД
не заводится (журнал — уже существующая таблица `steps`).

## Риски

- Классификация «сеть» — категория по остаточному принципу (не «нет
  origin», не «non-fast-forward»): реальный сетевой сбой (DNS, таймаут)
  вживую в песочнице не воспроизвести без сети — покрыт только
  юнит-тестом на `_classify_push_failure` с фикстурным текстом stderr,
  не сквозным сценарием.
- `git merge-base --is-ancestor` для направления расхождения — прямой
  вызов `gitcmd.git` из `doctor.py` (обёртки в `gitcmd.py` нет, файл не
  в зоне этой задачи); отказ git (сбой процесса, неудавшийся fetch)
  деградирует в «разошлись» — не отдельный `skip`, риск минорный (та же
  информационная проверка, не гейт).
- Расширение зон на `orchestrator/answer.py` требует мандата Оператора
  (`## Расширение зон` выше + `ANSWER-n.md` с «Расширение зон
  разрешено: orchestrator/answer.py») ДО перехода `in_dev -> review` —
  без него `fsm_advance._zones_gate_refuses` откажет `advance` с
  подсказкой в журнале; это ожидаемый штатный отказ гейта, не авария.

## Предложения системе

- SPEC этой задачи (`zones:`) не включил `orchestrator/answer.py`, хотя
  требование 1 и приёмочный тест `test_ac1_ac2_push_failure_no_origin.py`
  явно называют ANSWER Оператора местом вызова push, а `answer.py` до
  этой задачи push не звал вовсе (значит правка неизбежна). Стоит явно
  сверять `zones` SPEC со списком мест, названных требованиями и
  приёмочными тестами, до передачи задачи в `in_dev` (класс — analyst,
  скил `spec-authoring`/`review-acceptance`): в этот раз обошлось
  однострочной правкой и штатным расширением зон, но при более широком
  требовании к «стороннему» файлу цена ошибки analyst выросла бы до
  полноценной эскалации.
