# ТЗ: Уборка родителя при делении на гейте SPEC и удаление влитой ветки при kill

# ТЗ: Уборка родителя при делении на гейте SPEC и удаление влитой ветки при kill

Источник: строка копилки П2 от 21.09 «Кодовые ветки задач done/killed
осиротевают навсегда» (docs/backlog.md). Задача параллельна линии
провайдеров и с ней не пересекается.

Факты (пин fd83eb5d):
- Деление: `fsm._spawn_division_subtasks` заводит подзадачи
  (`catalog.spawn_subtask`) и переводит родителя в `killed` с пометкой
  «поделена на: …». Никакой уборки не вызывает.
- Kill: `cleanup.cleanup_killed_task` удаляет worktree задачи
  (`workspace.remove`), каталог задачи (`drop_task_dir`) и кодовую ветку
  (`drop_task_branch`), итог пишет в журнал записью «уборка».
- `cleanup.drop_task_branch` оставляет ветку, уже содержащуюся в main
  («оставлена: смержена в main»); неслитую удаляет `-D`. Ветка
  родителя, поделённого на гейте SPEC, пустая (работа шла в артефактной
  ветке), поэтому формально «смержена» и не удалилась бы даже через kill.
- `doctor` (`orphans-branches`) требует, чтобы у задач `done`/`killed`
  кодовой ветки не было, и краснеет постоянно. Сейчас так висят два
  поделённых родителя: 01M31Y3RXXKS1BGC6JH3527FN0 и
  01M32K876ZCDZW8M5CZ1S5WY9J — у каждого worktree в каталоге worktree
  пульта и кодовая ветка без собственных коммитов относительно main.
  Команды уборки нет: `doctor --fix` чинит только артефактные ветки.

Требуется:
1. Деление на гейте SPEC после перевода родителя в `killed` убирает
   worktree и кодовую ветку родителя тем же механизмом, что kill
   (`cleanup.cleanup_killed_task` либо общий узел), с записью «уборка» в
   журнал родителя. Уборка не может отменить деление: сбой уборки —
   запись в журнал с причиной, подзадачи и состояние родителя остаются.
2. Артефактная ветка родителя и её содержимое (SPEC с разделом
   «## Деление», из которого нарезаны части) при делении НЕ удаляются и не
   меняются.
3. `drop_task_branch` удаляет и ветку, целиком содержащуюся в main
   (безопасным `git branch -d`: все её коммиты уже в main, ничего не
   теряется); неслитая ветка — как сегодня. Запись в журнале различает
   «удалена влитая ветка» и «удалена неслитая ветка». Прежнее обоснование
   «история убитой задачи» пересмотреть в SPEC с проверкой, что история
   действительно сохраняется в main.
4. Однократная уборка двух висящих родителей (факты выше) — штатной
   командой после мержа, без ручного git: аналитик предлагает путь
   (например, повторный вызов уборки для `killed`-задачи с веткой) и
   описывает его в SPEC; если для этого нужна новая команда пульта —
   вопрос к Оператору.
5. Тесты (tests/): деление на гейте SPEC — worktree и ветки родителя нет,
   артефактная ветка родителя на месте, подзадачи заведены; kill задачи с
   пустой веткой, с влитой веткой и с неслитой веткой — ветки нет во всех
   трёх случаях; сбой уборки при делении не отменяет деление; существующие
   тесты kill, деления и `doctor` зелёные, ни один не ослаблен.

Зоны: orchestrator/cleanup.py, orchestrator/fsm.py, tests/.

Только чтение (не менять): orchestrator/catalog.py,
orchestrator/workspace.py, orchestrator/gitcmd.py,
orchestrator/doctor/ (правило `orphans-branches` верное, меняется
поведение уборки, а не проверка), orchestrator/artifact_branch.py,
tests/test_invariants.py (защищённый путь), docs/backlog.md,
docs/retention.md.

Не входит: уборка кодовых веток на origin (там их больше двухсот,
отдельный вопрос политики хранения); уборка артефактных веток и снимков;
ветки задач старого формата `task/t001-…`, не связанные со строками БД;
`doctor --fix` для кодовых веток.
