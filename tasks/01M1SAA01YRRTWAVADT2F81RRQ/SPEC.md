# SPEC: посторонние файлы в каталоге планки не попадают в артефактную ветку

## Контекст

Дважды за один день (05.09) автокоммит шага роли утащил в артефактную
ветку сгенерированную карту кодовой базы внутри
`tasks/<id>/acceptance_tests/docs/codebase-map.md` — источник:
`scripts/codebase_map.py`, запущенный с рабочим каталогом внутри
каталога планки, пишет `docs/codebase-map.md` относительно `cwd`, а не
относительно корня репозитория. После мержа `guard --all` красил main
около сорока минут (guard пытался прочитать чужеродный `.md`-файл как
артефакт с frontmatter), Оператор убирал файл руками.

Три точечных изменения устраняют этот класс целиком: автокоммит
переносит из `acceptance_tests/` только заведомо разрешённые файлы
планки, guard называет посторонний файл именованной причиной вместо
попытки разбора, генератор карты пишет только в корень репозитория
независимо от `cwd` запуска.

## Требования

1. Автокоммит артефактов шага (`orchestrator/checkpoint.py`) переносит
   в артефактную ветку из `tasks/<id>/acceptance_tests/` только
   разрешённые файлы: `test_*.py`, `_sandbox.py`, `markers.py`,
   `__init__.py` и `*.md`/`*.txt` первого уровня; вложенные каталоги
   (кроме `__pycache__`, который игнорируется) и прочие файлы не
   коммитятся, а журналируются одной записью «в каталоге планки
   посторонние файлы: <список>».
2. `scripts/guard.py` (режим `--all` и режим артефактной ветки) считает
   посторонний файл внутри `acceptance_tests/` нарушением структуры с
   именованной причиной («посторонний файл в каталоге планки»), а не
   пытается разобрать его как артефакт с frontmatter.
3. `scripts/codebase_map.py` пишет карту только в
   `<корень репозитория>/docs/codebase-map.md`, определяя корень по
   `git rev-parse --show-toplevel` от cwd, а не относительно cwd;
   запуск из подкаталога даёт тот же результат.

## Критерии приёмки

AC-1. Автокоммит артефактов шага переносит в артефактную ветку из
`tasks/<id>/acceptance_tests/` только файлы: `test_*.py`, `_sandbox.py`,
`markers.py`, `__init__.py` и `*.md`/`*.txt`, лежащие непосредственно в
`acceptance_tests/` (первый уровень); всё прочее в каталоге, включая
любые файлы во вложенных подкаталогах (кроме уже игнорируемого
`__pycache__`), не переносится в артефактную ветку.

AC-2. Каждый посторонний файл (или несколько), отфильтрованный по
правилу AC-1 на одном шаге, порождает ровно одну запись в журнале с
формулировкой «в каталоге планки посторонние файлы: <список>» — не по
отдельной записи на файл.

AC-3. `scripts/guard.py` в режиме `--all` и в режиме
`--artifact-branch`, встретив внутри `acceptance_tests/` посторонний
файл (критерий допустимости — тот же, что в AC-1), выдаёт нарушение
структуры с именованной причиной «посторонний файл в каталоге планки»
и не пытается прочитать его как артефакт с frontmatter.

AC-4. `scripts/codebase_map.py` определяет корень дерева командой
`git rev-parse --show-toplevel` от текущего рабочего каталога (не
`Path.cwd()` напрямую) и пишет карту только в
`<корень>/docs/codebase-map.md`; запуск из любого подкаталога
репозитория (в т.ч. изнутри `tasks/<id>/acceptance_tests/`) даёт тот
же результат — файл появляется в корне, не рядом с cwd запуска.

AC-5. Юнит-тест воспроизводит автокоммит шага, у которого в
`acceptance_tests/` на диске присутствует посторонний файл (по
критерию AC-1): файл не попадает в артефактную ветку, в журнале —
запись по формату AC-2.

AC-6. Юнит-тест проверяет, что `guard.py` (оба режима из AC-3) на
наборе файлов/артефактной ветке с посторонним файлом внутри
`acceptance_tests/` выдаёт именно именованную ошибку «посторонний файл
в каталоге планки», а не ошибку разбора frontmatter или иную.

AC-7. Юнит-тест проверяет, что генератор карты, запущенный с рабочим
каталогом внутри подкаталога репозитория, пишет
`docs/codebase-map.md` в корень репозитория (определённый
`git rev-parse --show-toplevel`), а не в подкаталог запуска.

AC-8. Существующие тесты `orchestrator/checkpoint.py`, `scripts/guard.py`
и `scripts/codebase_map.py` остаются зелёными без ослабления
существующих проверок или лимитов.

## Оценка объёма и деление

Сработавший сигнал: «затронут инвариантный механизм» — зона
`scripts/guard.py` буквально встречается в `docs/invariants.md`
(строка про правила guard, действующие на живые задачи, ANSWER-3
01M1KS8K9RXWHX2PW3ZKB0P903). Остальные сигналы не сработали: зон
задачи 4 (< 5), критериев приёмки 8 (< 10), `budget_usd` $15 (< $30),
формулировок неопределённости в тексте нет, прогноз диффа не завышен.

**Обоснование монолита.** Требования 1–3 — три точечных изменения в
трёх разных файлах, устраняющие ОДИН инцидент («карта из чужого cwd
попадает в артефактную ветку и красит `guard --all`»), и ни одно не
самодостаточно без остальных: правка `scripts/codebase_map.py` (AC-4)
без фильтра `checkpoint.py` (AC-1) не защищает от уже сгенерированных
посторонних файлов иного происхождения; фильтр без именованной ошибки
`guard.py` (AC-3) оставляет тот же красный main для любого другого
источника постороннего файла, не только карты. Объём задачи (budget
$15, три точечных файла зоны + `tests/`) меньше накладных расходов
деления на 2+ подзадачи (минимум два дополнительных цикла SPEC/PLAN/
REVIEW). Решение утверждает Оператор на гейте SPEC.

## Не входит

- Правки уже существующих исторических артефактных веток, в которые
  посторонний файл попал до этой задачи.
