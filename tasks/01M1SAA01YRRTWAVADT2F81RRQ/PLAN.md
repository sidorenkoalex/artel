# PLAN: посторонние файлы в каталоге планки не попадают в артефактную ветку

## Подход

Три точечных изменения, ровно как названы в SPEC требованиями 1–3 —
один общий критерий допустимости файла первого уровня
`acceptance_tests/` (`test_*.py`, `_sandbox.py`, `markers.py`,
`__init__.py`, `*.md`/`*.txt`), применённый в двух независимых местах
(`checkpoint.py` при переносе в артефактную ветку, `guard.py` при
структурной проверке), плюс независимая правка корня в
`codebase_map.py`. Общий модуль под критерий не заводится: зона задачи
не включает нового файла, а сама проверка — 5–7 строк регулярки,
дублировать её дешевле, чем городить кросс-импорт `guard.py` →
`orchestrator.checkpoint` (guard — сознательно лёгкий модуль без
тяжёлых зависимостей `store`/`gitcmd`, докстринг модуля).

1. `orchestrator/checkpoint.py::_commit_external_step_artifacts` — после
   применения существующего фильтра `.gitignore` (`ignored`) выделяет
   из `files` посторонние файлы `acceptance_tests/` (критерий AC-1),
   исключает их из переноса и, если список непуст, пишет ОДНУ запись
   журнала «в каталоге планки посторонние файлы: <список>» (AC-2).
2. `scripts/guard.py::main` — в режиме `--all` (оба варианта, с
   `--artifact-branch` и без) отдельно сканирует
   `tasks/*/acceptance_tests/` на посторонние файлы тем же критерием,
   исключает их из обычного обхода `*.md` (чтобы не пытаться разобрать
   как артефакт) и добавляет по каждому именованную ошибку «посторонний
   файл в каталоге планки» (AC-3, AC-6).
3. `scripts/codebase_map.py::main` — корень дерева резолвится
   `git rev-parse --show-toplevel` от `Path.cwd()` вместо самого
   `Path.cwd()` (AC-4, AC-7); докстринг модуля поправлен под новое
   поведение.

## Шаги

1. Один MR — все три правки маленькие, точечные и по разным файлам без
   пересечений; общего рефакторинга нет, каждую можно ревьюить
   независимо по своему требованию SPEC.

## Покрытие требований

| Требование | Шаг |
|---|---|
| 1 (checkpoint) | 1 |
| 2 (guard) | 1 |
| 3 (codebase_map) | 1 |

## Влияние на систему

- `checkpoint._commit_external_step_artifacts` — новый фильтр сужает
  набор переносимых файлов ТОЛЬКО внутри `acceptance_tests/`; файлы вне
  этого подкаталога (`PLAN.md`, `SPEC.md`, `REVIEW.md` и т.п.) не
  затронуты. Существующий тест `tests/test_checkpoint_external_step_
  artifacts.py::test_second_step_accumulates_onto_the_first_not_
  replaces_it` и подобные — легитимные файлы планки (`test_*.py` и
  соседи) продолжают переноситься без изменений.
- `guard.py --all` — новый источник ошибок аддитивен: раньше
  посторонний .md-файл красил guard ошибкой разбора frontmatter, теперь
  красит именованной причиной; файл постороннего расширения раньше
  проходил молча, теперь тоже красит. И то и другое — ужесточение в
  сторону инцидента, не ослабление проверки ни для одного существующего
  валидного артефакта: SPEC/PLAN/REVIEW/TZ/QUESTIONS/ANSWER вне
  `acceptance_tests/` фильтром не затронуты, а разрешённый набор внутри
  `acceptance_tests/` (`test_*.py` и соседи первого уровня) по-прежнему
  проходит без ошибок.
- `codebase_map.py` — смена корня меняет ТОЛЬКО путь записи выходного
  файла, не содержимое карты (`build_modules(root)` как раньше строит
  карту от корня). Существующие вызыватели (`orchestrator/brief.py`,
  `orchestrator/fsm.py`, `orchestrator/fsm_postmerge.py`) зовут скрипт с
  `cwd=config.ROOT` или `cwd=<worktree задачи>` — оба уже являются
  вершиной своего git-дерева, `git rev-parse --show-toplevel` вернёт тот
  же путь, что раньше давал `Path.cwd()`: поведение существующих
  вызовов не меняется, меняется только некорректный случай (cwd внутри
  подкаталога).
- Тесты и гейты не ослабляются — только чинятся под новое поведение
  (AC-8), проверено `test_existing_zone_tests_not_weakened.py` из
  залоченной планки.
- Откат — три независимых `git revert` по каждому файлу зоны, никакой
  из трёх правок не зависит от остальных для отката.

## Риски

- Guard теперь сканирует `tasks/*/acceptance_tests/` отдельным проходом
  по диску при каждом `--all` — на реальном размере репозитория (сотни
  задач, у большинства уже нет `acceptance_tests/` после мержа/уборки)
  цена дополнительного обхода пренебрежимо мала.

## Предложения системе

- `scripts/guard.py` несёт уже вторую независимую реализацию «правило не
  распространяется на задачу, закрытую до его появления»
  (`_closed_before_split_assessment` из T023-эпохи и теперь
  `scan_extraneous_acceptance_files` этой задачи) — каждая заново
  проверяет `docs/retro/<id>.md` по своему пути к id. Кандидат на общий
  хелпер `_task_closed(task_id)`, если появится третий guard-класс с тем
  же исключением.
- Прогон `python3 scripts/guard.py --all` на реальном дереве пульта
  ДО фикса этого пункта красил 9 давно закрытых задач (легитимные
  `_util.py`/`_race.py`/… в их `acceptance_tests/`) — новое правило
  guard стоит всегда обкатывать реальным `--all`, не только фикстурами
  приёмочной планки, иначе регрессия на main всплывает только на первом
  же PR после мержа.
