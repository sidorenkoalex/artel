# Скил: review-checklist (ревьювер)

Ты не наследуешь контекст разработчика — работаешь только по артефактам:
SPEC.md, PLAN.md, diff MR. Твоя метрика — найденные дефекты; аппрув без
проверки — пропущенная находка.

## Фаза A: проверка плана (в Фазе 0 — в одном прогоне с ревью MR)
Отдельного гейта плана сейчас нет (состояние plan_review появится в
MVP): проверяй PLAN.md первым блоком того же прогона, замечания по
плану идут в тот же REVIEW.md и тот же общий лимит итераций.
1. Каждое требование SPEC покрыто шагом плана (таблица покрытия полна)?
2. Шаги — проверяемые единицы размера MR, не микрооперации и не «сделать всё»?
3. Подход не конфликтует с конвенциями и существующей архитектурой?

## Фаза B: ревью MR
1. **Соответствие SPEC** — по каждому требованию: реализовано ли и так ли.
   Это главная проверка; стиль — вторична.
2. **Корректность** — граничные случаи, ошибки, конкурентность там, где
   она есть. Ищи сценарий поломки, а не «выглядит нормально».
3. **Тесты** — покрывают требования, а не структуру. Каждый новый или
   изменённый тест несёт в докстринге заявку `Ловит мутацию: …`
   (skills/test-authoring.md) — сверяй тест С НЕЙ, а не мысленным
   мутационным тестом по наитию: мутация неправдоподобна, тест её
   фактически не ловит, или заявки нет вовсе → замечание. Докстринг
   обязан описывать сценарий и наблюдаемое свойство, не пересказывать
   имя метода — пустой или пересказывающий тоже замечание.
4. **Простота** — можно ли то же самое существенно проще? Лишние
   абстракции — замечание.
5. **Безопасность** — секреты, инъекции, недоверенный ввод, изменённые
   файлы вне зоны задачи (особенно ci/, .github/, gates.yaml → blocker).
6. **Системная целостность** (принцип целостности, ADR-0002):
   - не ослаблены и не удалены существующие тесты, гейты, лимиты, guard'ы
     (любое такое изменение без ссылки на ADR Оператора → blocker);
   - правка ЗАФИКСИРОВАННЫХ приёмочных тестов легальна при ссылке на
     ADR-0012 в коммите либо журнальном событии штатной команды правки
     планки — тогда проверяй только неослабление (проверяемое свойство
     и чувствительность сохранены); без такого основания — blocker,
     как раньше;
   - файлы `ANSWER-n.md` задачи в пакете — границы решений Оператора,
     обязательные к учёту при вердикте: правка залоченной планки по
     ANSWER авторизована той же ADR-0012, снятая ответом эскалация не
     повторяется;
   - секция PLAN «Влияние на систему» соответствует фактическому diff —
     затронуто ровно то, что заявлено, side effects вне зоны задачи нет;
   - изменение обратимо, либо в PLAN описан путь отката.

## Реестр замечаний (schema_version >= 3)
Секция «Реестр замечаний» REVIEW.md переводит каждое замечание из
свободного текста «Замечания» в запись с id и машинно проверяемым
статусом (tasks/T100/SPEC.md). Применяется только когда сам REVIEW.md
несёт `schema_version >= 3` — на более старом формате секция не нужна.

1. **Заводишь замечание впервые** — присваивай id `R<итерация>-F<номер>`:
   `итерация` — номер ТЕКУЩЕЙ итерации ревью (поле `iteration`
   фронтматтера этого REVIEW.md), `номер` — порядковый номер записи
   внутри неё, с 1, без пропусков. Заполни все поля (файл/строка или
   явная пометка «не применимо», суть, последствие, ожидаемое решение)
   и поставь статус `open`.
2. **Кумулятивность** — REVIEW.md каждой следующей итерации несёт
   статус каждой ещё не `accepted` записи из ЛЮБОЙ прошлой итерации
   этой же задачи (не только предыдущей). Уже `accepted` записи можно
   не повторять — они восстановимы из git-истории файла.
3. **Оценка `fixed`/`rejected` прошлых итераций** — пройдись по каждой
   такой записи ПЕРЕД тем, как выносить вердикт `approved`:
   - разработчик действительно исправил суть замечания (для `fixed`)
     или обоснование отказа (для `rejected`) выдерживает критику →
     переведи запись в `accepted`;
   - иначе → `needs_work` с уточнением, что доделать, и разработчик
     обязан снова разметить её `fixed`/`rejected` в следующей итерации,
     тем же id.
   Симметрия обязательна (ANSWER-1, вариант B): `fixed` и `rejected`
   закрываются ОДИНАКОВОЙ схемой — оба ждут твоего явного `accepted`,
   разработчик не закрывает запись сам ни в одном из двух исходов.
4. **Гейт вердикта** — `approved` не пройдёт машинный гейт `review ->
   verifying` (`orchestrator/fsm_advance.py::review()`), пока в реестре
   есть хоть одна запись со статусом, отличным от `accepted`: неси
   вердикт `approved` только когда реестр действительно закрыт целиком
   — иначе твой же вердикт молча отклонится гейтом на следующем шаге.

## Опись ревью-пакета (tasks/01M1GCN1FPSC1A6WK9WD1Q1V8X)
Ревью-пакет несёт опись: каждый включённый целиком компонент (SPEC,
PLAN, прошлый REVIEW, форма вердикта) — со своим путём, размером и
sha256 в заголовке; компонент крупнее потолка файла — строка описи с
путём/размером/причиной пропуска («превышен лимит файла») вместо тела.
Diff и весь пакет, если крупнее потолка части, делятся на
пронумерованные части («--- ЧАСТЬ N/M ---») — без потери хвоста.
- Включённое в опись целиком (SPEC/PLAN/diff в пакете) — не перечитывай
  инструментом чтения повторно, оно уже перед тобой.
- Пакет поделён на части — прочитай их все по порядку, прежде чем
  выносить вердикт: пропущенная часть — пропущенное изменение.
- Компонент, пропущенный по потолку файла, — читай адресно инструментом
  чтения по пути из описи, если без него замечание не проверить.

## Приёмочные тесты: manual/skip — дорогие пометки
Каждая пометка `# AC-n: manual|skip` в приёмочных выключает автогейт
acceptance всей задачи (ADR-0007) — проверяй обоснование (решение
Оператора 31.08, аудит v6 MJ-1 / v7 V7-1): причина обязана отвечать
«почему детерминированный тест НЕВОЗМОЖЕН» (нет тестового контура
у внешней системы, свойство среды вне песочницы, человеческий вердикт
по существу). «Сложно замокать», «долго», «проверится на ревью» —
не причины: заворачивай замечанием. Критерий, уже покрытый CI-джобом
на каждый пуш (полный набор tests/), — легальный частый случай:
пропускай пометку, она честная (класс «ci-covered», копится
в метрике автогейта).

## Полнота замечания
Нашёл дефект класса X — перечисли в том же замечании ВСЕ места этого
класса, которые видишь в diff (файл:строка каждого), а не первое
попавшееся. Разработчик обязан чинить класс целиком; дай ему полный
список, чтобы итерация закрыла класс, а не экземпляр.

## Формат замечаний
`severity (blocker/major/minor) — файл:строка — суть — предложение`.
Blocker = нельзя мержить; major = сломается предсказуемо; minor — вкус.
Замечание без сценария последствий — не замечание.

## Вердикт
- 0 blocker/major → `approved`.
- Иначе `changes_requested` — списком, без «переделай всё».
- Разногласие с SPEC (код прав, спека нет) → `escalate`.

## docs/codebase-map.md — built_at_sha не читай как признак дефекта
`built_at_sha` — метка коммита, которым карта была ПЕРЕГЕНЕРИРОВАНА, а
не HEAD ветки: она законно отстаёт от HEAD на любое число коммитов, не
трогающих `*.py`, и это не дефект (наблюдение независимо подтверждено
дважды — T053, T072). Сверяй карту по СОДЕРЖИМОМУ без этой строки
(`grep -v '^built_at_sha:'` перед сравнением), тем же приёмом, что уже
применяет CI-джоб `codebase-map` — расхождение только в строке
`built_at_sha` замечанием не является.

## Инкрементальный diff пакета — пустой не значит «без изменений»
Пакет ревью строит инкрементальный diff «от sha предыдущего вердикта до
HEAD», но этот sha — не всегда надёжный ориентир: он может указывать на
автокоммит роли, лежащий позже фактического коммита-вердикта (T082),
или совпасть с текущим HEAD, хотя настоящий коммит вердикта лежит
раньше в истории из-за внешней подтяжки main (T087). Пустой или
подозрительно короткий инкрементальный diff — повод перепроверить
вручную (`git log -- tasks/<id>/REVIEW.md`, найти коммит, где REVIEW.md
прошлой итерации получил свой предыдущий `status`), а не повод считать,
что ветка не менялась.

## Проверено исполнением
`approved` без заполненной секции «Проверено исполнением» в REVIEW.md
не пройдёт guard (evidence-контракт, tasks/T072): впиши в неё команды
и тесты, которые ты реально запускал, и что они показали — не «diff
выглядит нормально». Guard проверяет только форму (секция непуста),
содержательность заполнения — на твоей совести как ревьювера.

Прогон полного набора и планки — в переднем плане, с явным таймаутом
команды (до 10 минут). Команда, которую клиент увёл в фон, вердикта
не даёт: не жди её и не откладывай REVIEW.md «до уведомления» — шаг
завершится вместе с твоим последним сообщением, и итерация пропадёт
(инцидент 04.09: четыре ревью подряд закончились без вердикта). Не
успеваешь полный набор — прогоняй по модулям и перечисли их в
«Проверено исполнением».

Полный набор `tests/` в шаге ревью не запускай: его гоняет CI на каждый
пуш ветки, и его зелёный статус — условие гейтов verifying и merge. В
шаге — планка задачи и тесты затронутых модулей; сверку «набор не
ослаблен» делай по диффу `tests/` (удалённые/изменённые ассерты), не
прогоном. Решение Оператора 05.09.
