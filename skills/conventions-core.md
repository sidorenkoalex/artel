# Скил: conventions-core (базовый слой — все роли)

## Артефакты
- Все артефакты задачи живут в `tasks/<id>/`: SPEC.md, PLAN.md, REVIEW.md,
  QUESTIONS.md (батч analyst). Создаются из `templates/`, frontmatter
  обязателен. (TEST_REPORT.md — резерв под роль verifier, до C4 не
  создаётся.)
- Артефакт = единственный канал передачи между ролями. Всё, что не в
  артефакте, — не существует для следующей роли.
- Обновляя артефакт, меняй `status` во frontmatter — по нему оркестратор
  двигает FSM. Валидные статусы перечислены в шаблоне.
- Секция `## Предложения системе` в PLAN.md/REVIEW.md — необязательная
  копилка наблюдений о САМОЙ системе (не о своей задаче): скил разошёлся
  с практикой, антипаттерн повторился, механика натирает. Заметил такое
  по ходу задачи — впиши одну-две строки с адресом (файл/скил/класс
  проблемы), без эссе; иначе наблюдение умирает вместе с твоим контекстом.
  Пример: класс «вызов внешней команды без обработки сбоя» ревью отметило
  в T042 и повторно в T043 — за один и тот же урок заплатили дважды,
  потому что после первого раза его некуда было записать. Пустая секция
  и её отсутствие — оба валидны: копилка — приглашение, не повинность.
- Каталог `tasks/<id>/` рабочего каталога роли материализуется заново на
  старте КАЖДОГО шага из ГОЛОВЫ артефактной ветки (SPEC
  01M1NKTF173WV5CPDZ1C3WW69K) — на диске всегда актуальная версия
  (в том числе правка Оператора на гейте между твоими шагами), отдельно
  перечитывать её с диска после чужой правки не нужно.

## Git
- Ветка задачи: `task/<id>-<slug>` от свежего main.
- Коммиты: `<id>: <что сделано>` — по-русски, по делу, без «фиксы».
- Артефакты `tasks/<id>/` в кодовую ветку НЕ коммитишь (SPEC
  01M1NKTF173WV5CPDZ1C3WW69K): единственный путь артефактов в git —
  автокоммит оркестратора в артефактную ветку по итогам шага. Коммитишь
  только код — там, где твоя роль его меняет.
- Правишь `*.py` в orchestrator/, scripts/ или tests/ — регенерируй
  карту тем же коммитом: `python3 scripts/codebase_map.py` (иначе
  CI-джоб свежести красит твою ветку; карту на merge в main чинит
  оркестратор — T042; T028/T029 — два улова).
- То же самое правило действует, если `orchestrator/`, `scripts/` или
  `tests/` меняются не через Edit, а ПОДТЯЖКОЙ main в ветку задачи
  (`git merge main`/эквивалент свежести): подтяжка тоже меняет `*.py`,
  просто не через инструмент разработчика — регенерируй карту отдельным
  шагом сразу после разрешения конфликтов подтяжки. Формулировка выше
  исторически читалась только про правку через Edit и не покрывала этот
  случай явно; класс подтверждён дважды (T079 — обошлось ручным шагом
  внутри одной задачи; T087 — механика подтяжки main снова не
  регенерировала карту, пробел в формулировке подтверждён явно).
- Готовишь unified-диф по защищённому пути (`skills/`/`templates/`/
  `gates.yaml`/`roles.yaml`/`.github/`) как приложение к PLAN.md для
  Оператора — перед тем как его сдать, прогони `git apply --check
  <файл-с-диффом>` на чистом дереве и подтверди в PLAN.md, что патч
  применяется. Хедер хунка, не совпадающий с реальным диапазоном файла,
  не ловится глазомером автора и повторился дважды подряд (T046
  подготовил диф без такой проверки; T047 итерация 1 повторила тот же
  дефект, итерация 2 закрыла его именно прогоном `git apply --check`
  перед сдачей).
- Никогда: push в main, merge, изменение чужих веток, правка
  `gates.yaml` / `roles.yaml` / `.github/` / `templates/` / `skills/`
  (эти пути меняет только Оператор отдельным MR).
- Никогда: ослабление или удаление существующих тестов, гейтов, лимитов,
  guard-проверок и инвариантов — только Оператор через ADR в docs/adr/
  (принцип целостности, ADR-0002). Если твоя задача требует такого
  изменения — эскалируй с обоснованием, решение примет Оператор.

## Стиль коммуникации
- Пиши в артефактах конкретно: файл:строка, команда, наблюдение.
- Не пересказывай шаблон — заполняй его.
