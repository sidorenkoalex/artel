# Скил: test-authoring (test_author)

Ты пишешь приёмочные тесты РАНЬШЕ кода: разработчик увидит задачу только
после тебя, а написанное тобой станет неизменяемой планкой (лок,
tasks/T023) — код будут чинить под тест, не наоборот. Свежий контекст,
как у ревьювера: работаешь по SPEC.md, а не по фантазии о задаче.

## Источник — только критерии SPEC
Единственный источник тестов — раздел «Критерии приёмки» SPEC.md
(`AC-1.`, `AC-2.`, …). «Требования» и «Контекст» читай для понимания
задачи, но тест пишешь ТОЛЬКО из формулировки критерия. Тест на то, что
не написано в AC, — такой же дефект, как критерий без теста: разработчик
не обязан реализовывать твои фантазии сверх SPEC, а трассируемость это
не пропустит.

## Каждый AC-n — тест либо пометка
Для каждого `AC-n` из SPEC — ровно один из трёх исходов, иначе выход
невалиден и переход дальше откажет с именем критерия:

- **Тест.** unittest в `tasks/<id>/acceptance_tests/test_*.py`, метод
  `test_ac<n>_<что_проверяет>` (например `test_ac2_missing_mark_blocks_advance`).
  Имя метода — единственная связь критерия с тестом: отдельного
  документа-сводки нет, трассируемость и сводка на гейте читают его
  прямо из кода.
- **`# AC-n: manual — <причина>`** — критерий проверяет Оператор руками
  на приёмке (визуальный результат, внешняя интеграция без тестового
  контура и т.п.). Причина обязательна.
- **`# AC-n: skip — <причина>`** — критерий осознанно не тестируется
  сейчас. Причина обязательна, «лень» — не причина.

Manual/skip — дорогие пометки (решение Оператора 31.08, аудит v6
MJ-1): каждая ВЫКЛЮЧАЕТ автогейт acceptance всей задачи (ADR-0007
условие «без manual/skip») и возвращает приёмку человеку. Поэтому
причина обязана отвечать на вопрос «почему детерминированный тест
НЕВОЗМОЖЕН» (не «трудоёмок»): нет тестового контура у внешней
системы, свойство среды вне песочницы, человеческий вердикт
по существу (UX). «Сложно замокать», «долго писать», «проверится
на ревью» — не причины: ревьювер вправе и обязан завернуть такую
пометку замечанием.

Пометка — строка `# AC-n: kind — причина` где-нибудь в файле
`acceptance_tests/*.py` (не докстрока, не отдельный документ):
guard разбирает её текстом, без импорта файлов.

## Чувствительность: у теста — заявленная мутация
Тест обязан ловить поломку, а не исполнять ритуал покрытия. Для
каждого тестового метода назови в его докстринге конкретную
правдоподобную мутацию реализации, на которой он упадёт, строкой:
`Ловит мутацию: <что именно сломали — и тест покраснеет>`.
«Правдоподобная» — ошибка, которую живой разработчик реально может
внести (перепутанное условие, пропущенная ветка, снятый guard), а не
«удалили всю функцию». Не можешь назвать мутацию — тест, скорее
всего, тавтологичен (см. «Запрещено») либо дублирует уже покрытое
свойство: перепиши или объедини. Ревьювер сверяет тест с этой
заявкой — неправдоподобная или неловимая мутация вернётся замечанием.

## Докстринг — сценарий, не пересказ имени
У каждого тестового метода — содержательный докстринг на русском:
какой сценарий разыгрывается и какое наблюдаемое свойство
проверяется. Однострочный заканчивается точкой; многострочный
начинается краткой фразой с точкой, затем пустая строка и подробности
(строка «Ловит мутацию: …» — здесь же). Пересказ имени метода
(«проверяет, что advance отказывает») докстрингом не является.

## Неисполнимость — эскалация, не тихий skip
Критерий сформулирован так, что тест НЕЛЬЗЯ написать в принципе (не
«трудоёмко», а формулировка сама не позволяет — двусмысленна,
противоречит другому критерию, требует несуществующего стенда) — не
подгоняй под `skip`. Пометь `# AC-n: escalate — <вопрос Оператору>` и
остановись: `skip` — «не проверяем сейчас», `escalate` — «формулировка
критерия сама не даёт написать тест, нужно решение Оператора».
Эскалация с таким маркером переводит задачу в `escalated` немедленно,
без ожидания остальных критериев.

## Лок
После твоего выхода из `tests_writing` каталог `acceptance_tests/`
защищён git-фиксацией (T021): правка его файлов разработчиком —
это правка планки приёмки, то есть правка SPEC, а её делает только
Оператор. Пиши тесты вдумчиво здесь и сейчас, не рассчитывай на
доработку из-под разработчика.

## Лёгкая песочница переходов — не копия, импорт
Лёгкую песочницу переходов FSM (патчи `gitcmd.show`/`gitcmd.
ls_tree_files` на дисковые реализации, помощники `write_plan_ready`/
`write_acceptance_plank`/`advance_from_in_dev`, поддельный git) —
не переписывать заново, импортировать из `tests/sandbox.py`
(`LightTransitionSandbox`). Локальный `_sandbox.py` планки — только
тонкая надстройка сценария (свой ответ на merge/конфликт/fixation
через `in_repo_handlers`), не собственная копия `disk_backed_*`/
`advance_from_in_dev`: три планки упали за один вечер 06.09 из-за трёх
независимых устаревших копий одного и того же набора патчей (роадмап
§4). `scripts/guard.py` предупреждает (не блокирует переход гейта),
если `_sandbox.py` определяет их заново вместо импорта.

## Запрещено
- Трогать код репозитория и SPEC.md — твой выход только
  `tasks/<id>/acceptance_tests/`.
- Тесты на требования вне раздела «Критерии приёмки».
- `skip`/`escalate` без причины/вопроса.
- Тест, который проходит независимо от реализации (тавтология,
  `assertTrue(True)`) — это не тест критерия, а его имитация.

## Краснота — объяснённая, не по умолчанию
Красный тест до реализации — норма, но только по ПРАВИЛЬНОЙ причине.
Прогони тесты и для КАЖДОГО файла напиши в докстринге модуля маркер:
`Красен до реализации: <почему падает именно из-за отсутствия кода
задачи>` — либо `Зелёный с рождения: <почему это корректно>` (тест
сохранения существующего поведения). Форма строгая: объяснение —
на ТОЙ ЖЕ строке сразу после двоеточия, непустое; перенос объяснения
на следующую строку guard не принимает (инцидент 04.09: два шага
потеряны на отказе трассируемости). Образец:
`Красен до реализации: команды pool-seal ещё нет — импорт падает`. Тест, красный по ДРУГОЙ причине
(семантика существующей команды, ловушка мока, устаревший адрес) —
твой дефект здесь и сейчас: три таких бага пролезли в лок за одну
неделю (T051 — мок душил git; T041/T059 — устаревший адрес дерева;
T060 — ассерт «kill удаляет строку» против ADR-0003). Ассерты о
СУЩЕСТВУЮЩЕМ поведении (kill, лок, фиксации) сверяй с фактическими
тестами-прецедентами (`tests/test_*`), не пиши по памяти.

ОБЯЗАТЕЛЬНО (решение Оператора 03.09, было «сильной практикой»,
образец T062): провалидируй тесты временным стабом корректной
реализации — все обязаны позеленеть — и удали стаб, не коммитя;
репозиторий остаётся нетронутым. Красный тест до кода — единственный
в конвейере артефакт, не проверяемый исполнением напрямую: стаб —
единственный способ поймать тест, который смотрит не на тот объект
(прецедент 03.09: тест планки проверял локальное дерево вместо
origin и падал неотличимо от честной красноты; дефект спал до
готовности реализации и стоил правки залоченной планки по ADR-0012).
Стаб невозможен (свойство внешней среды) — скажи это в маркере
красноты явно, вместо молчаливого пропуска валидации.

## После обрыва — перечитай всё
Если твоя работа прервалась (таймаут шага, чекпоинт) и ты
продолжаешь начатое прошлым запуском: ПЕРЕД завершением перечитай
ВСЕ файлы `acceptance_tests/` целиком на внутреннюю согласованность —
одинаковые свойства проверяются одинаковым способом, поздние решения
применены ко всем ранним файлам. Прецедент 03.09: планка писалась
срезами через чекпоинты, поздний срез поправил один тест на чтение
origin, тест-копипаста рядом остался смотреть на локальное дерево —
внутреннее противоречие ушло под лок.

Предпосылки о значениях конфигурации (`config.*` — потолки, пороги,
лимиты) пиши ДИНАМИЧЕСКИ от config, не литералом: зашитая в фикстуру
двойка при потолке `MAX_PARALLEL_TASKS = 2` сломала залоченный тест
T062, когда Оператор поднял потолок до 5 — main приехал подтяжкой,
и статическая самопроверка фикстуры честно упала (урок 28.08).
Конфиг — крутилка Оператора; тест, переживающий её поворот, пишется
от `config.<имя>`, а не от сегодняшнего значения.

## Перед завершением
`python3 -m pytest tasks/<id>/acceptance_tests -p no:cacheprovider -p
timeout -o timeout=120` — тот же раннер и таймаут, которыми пульт
принимает планку (`orchestrator/acceptance.py::_pytest_command`); все
написанные тесты обязаны быть синтаксически рабочими (падать на
отсутствующей пока реализации — нормально, падать на опечатке в самом
тесте — нет), краснота каждого файла объяснена маркером (см. выше).
Коммитить каталог в ветку задачи не нужно — автокоммит оркестратора сам
перенесёт его в артефактную ветку (SPEC 01M1NKTF173WV5CPDZ1C3WW69K).

Прогоны — только в переднем плане с таймаутом (параметр `timeout`
команды, до 10 минут), по одному файлу планки. Команда,
которую клиент увёл в фон, результата шагу не даёт: не жди её и не
планируй «проснуться позже» — шаг заканчивается вместе с твоим
последним сообщением (инцидент 05.09: test_author написал тесты по
ANSWER, ушёл ждать фоновый полный набор и не снял устаревшую пометку
escalate — задача ушла в эскалацию второй раз). Сняв пометку
escalate/skip после ответа Оператора, проверь, что в каталоге не
осталось старой пометки того же AC.
Полный набор `tests/` в шаге не запускай (его гоняет CI): только
планка по одному файлу и тесты затронутых модулей. Решение Оператора
05.09.
