## 0. Краткий вывод

1. **Подключить sled завтра нельзя — и не по одной причине, а по
   структурной.** Весь git- и forge-слой оркестратора привязан к одному
   репозиторию — пульту: `gitcmd.git` исполняется с `cwd=config.ROOT`
   (`orchestrator/gitcmd.py:16`), `ci.gh` — тоже (`orchestrator/ci.py:36`),
   а `gh api repos/{owner}/{repo}/…` подставляет владельца и имя
   репозитория из этого же cwd (`ci.py:56–60`). Все операции внешнего
   флоу — push ветки задачи, Draft-MR, опрос CI, сверка свежести, diff
   ревью-пакета, merge в scratch-worktree, RETRO после мержа — при
   target=sled либо отработают против репозитория артели, либо честно
   откажут на первой же git-команде («голова не в origin»). Опасного
   пути (смержить sled в артель) нет — есть тупик на входе в `in_dev`.
2. **Что A7 действительно дала для внешнего target:** единая
   артефактная механика для любого target (артефактная ветка пульта,
   автокоммит артефактов шага из рабочего каталога target,
   материализация приёмочных тестов из ветки, снапшот в
   `refs/artifacts/<id>` origin целевого с дожимом doctor'ом), единая
   doctor-логика по всем записям targets.yaml вместо skip'ов догфуда,
   и подтверждённое на артели право записи `refs/artifacts` (на origin
   пульта уже пять таких ссылок). Это закрывает «артефактную» половину
   чек-листа B2; «кодовая» половина (клон целевого, ветка задачи в нём,
   MR/CI/merge в чужом репозитории) не реализована вовсе — роль
   внешнего target стартует в пустом каталоге `.artel/projects/<t>/
   workspace/` (`orchestrator/runner.py:431–433`), который никто не
   клонирует, с миссией «ветка уже выписана в этом рабочем каталоге»
   (`orchestrator/role_prompt.py:19–21, 41–43, 62–64`), которая для
   него ложна.
3. **Три поля targets.yaml — мёртвая декларация.** `token_slot`,
   `no_paths`, `project_skills` проверяются на форму (`orchestrator/
   targets.py:23–31, 78–87`) и больше нигде не читаются: токен роли
   берётся по слотам roles.yaml (`runner.py:346–357`), защищённые пути —
   из константы пульта `config.PROTECTED_PATHS` (`config.py:293–294`,
   потребители `github_adapter.py:46–47`, `fsm_merge_gate.py:27–28`),
   скилы — из roles.yaml. У CLI-команды `new` нет флага `--target`
   (`orchestrator/artel.py:299–304`): задачу для sled сегодня нельзя
   даже завести штатно.
4. **По чек-листу B2 (7 пунктов + обязательное право записи
   `refs/artifacts`, роадмап §3:214):** кодом обеспечены полностью —
   0 пунктов; частично (механика есть, но привязана к пульту) — 4
   (CI на PR, свежесть, merge_gate=operator, право записи refs/artifacts);
   вне кода по замыслу — 2 (бэклог, размер задачи); не начато — 2
   (тулчейн в образе B3, обвязка/маркер в части инвентаризации живого
   клона). Детали — §1.
5. **Рекомендация:** не стартовать B2 с sled, пока не смержены (а) три
   задачи «контекст target» (§5, ТЗ-1…ТЗ-3: репозиторный контекст
   git/gh, клон и ветка задачи внешнего target, `new --target`), (б) фикс
   регрессии №5 в target-параметризованном виде — иначе класс «код
   читает локальную копию там, где источник истины — origin» повторится
   на sled ровно в тех же местах, и (в) внешняя канарейка — прогон
   полного внешнего флоу на одноразовом GitHub-репозитории до первой
   задачи на sled (это и есть B3 «первая конвейерная задача», только
   с честным вторым origin). B-спайк руками (§3) — параллельно,
   он не ждёт кода.

## 2. Разрывы: что мешает подключить sled завтра

### 2.1 Конфигурация

**Запись в targets.yaml.** Формат обязателен полностью — семь полей
(`targets.py:23–31`), пропуск любого — `TargetsError` на КАЖДОМ чтении
файла, то есть сломанная запись sled сломает и артель
(`targets.py:57–58`, сознательное свойство файла). Запись для sled
тривиальна (`forge: github`, `url`, `base`, `token_slot: sled-token`,
`no_paths: […]`, `project_skills: []`, `merge_gate: operator`), но
targets.yaml — защищённый путь (`.github/workflows/ci.yml:84`) — правит
только Оператор, коммитом в main мимо конвейера. Это штатно (CLAUDE.md
пульта).

**token_slot / keychain.** Поле объявлено и валидируется, но не
читается: единственный потребитель `keychain.token(slot)` — цепочка
слотов РОЛИ из roles.yaml (`roles.token_slots`, `runner.role_token`,
`runner.py:346–357`; `doctor.check_token`, `doctor.py:116–133`), и это
подписочный токен Claude (`CLAUDE_CODE_OAUTH_TOKEN`, `runner.py:390–394`),
не токен форджа. Аутентификация git/gh для push, Draft-MR, опроса CI —
ambient-окружение Оператора (`gh auth`, credential helper macOS), потому
что все вызовы идут из `config.ROOT` под HOME Оператора для процесса
оркестратора (HOME подменяется только процессу роли, `runner.py:380`).
Следствие: «токен целевого» как сущность в коде отсутствует; для sled
всё будет от учётки Оператора. Именно здесь живёт риск §4.1.

**no_paths.** Только форма (`targets.py:28`, комментарий в
`targets.yaml:26–28` честно называет это «декларацией»). Действующий
enforcement — два, и оба про пульт: CI-job `protected-paths`
(`ci.yml:70–91`, предупреждение, не отказ; регулярное выражение путей
пульта захардкожено в `ci.yml:84`) и `config.PROTECTED_PATHS`
(`config.py:293–294`; конфликт мержа в этих путях эскалирует,
`fsm_merge_gate.py:27–28, 67–111`; комментарий на MR,
`github_adapter.py:34–47, 96–110`). ADR-0003 п.8 «no_paths целевого
проверяются до merge» и роадмап P3 «автогейт плана: пути × no_paths =
стоп» — не реализованы. Для sled `no_paths` — пустая декларация без
единого исполнителя.

**project_skills.** Не читается нигде (grep по `orchestrator/` даёт
только `targets.py`). Скилы роли — только из roles.yaml
(`roles.skills`), текст — с головы `main` пульта (`brief.skills_text`,
задача 01M1K7KP0D). Курируемый список проектных скилов sled
(ADR-0003 3з) сегодня нечем подключить.

**CLI.** `new` без `--target` (`artel.py:299–304`; `catalog.cmd_new`
готов принять target). `target-init <имя>` заводит четыре подкаталога
и локальный артефактный git-репозиторий без remote (`projects.py:60–93`),
но НЕ клонирует целевой в `workspace/`.

### 2.2 Механика (Draft-MR, verifying/CI, артефактная ветка, снапшот)

Корневая причина одна: **репозиторный контекст не параметризован по
target**. `gitcmd.git(*args)` → `cwd=config.ROOT` (`gitcmd.py:9–19`);
`ci.gh(*args)` → `cwd=config.ROOT` (`ci.py:23–43`). Есть и второй
примитив `gitcmd.in_repo(repo, *args)` (`gitcmd.py:104`) — им уже
пользуются fixation, snapshot, scratch-merge, — но forge-слой и FSM его
не применяют к клону целевого. Следствия по шагам флоу sled-задачи:

1. **Клон и ветка задачи.** `cmd_new` пишет имя ветки `task/<id>-<slug>`
   только в БД (`catalog.py:140, 149`; докстринг 108–112: «её создание
   и код — дело роли-разработчика в клоне целевого»). `role_cwd` для
   внешнего target делает `mkdir` и возвращает пустой каталог
   (`runner.py:431–433`); `workspace.ensure` (git worktree в РЕПОЗИТОРИИ
   ПУЛЬТА, `workspace.py:42–65`) зовётся только для `DEFAULT_TARGET`
   (`runner.py:425–428`). Миссии всех ролей утверждают «ветка уже
   выписана в этом рабочем каталоге (собственный worktree)»
   (`role_prompt.py:19–21, 41–43, 62–64`) — для sled это неправда, и
   роль с `--allowedTools Bash(git:*)` будет либо клонировать сама
   (куда? с какими кредами? под HOME роли credential helper Оператора
   недоступен), либо топтаться. Тест `ExternalWorkspaceIsolationTest.
   test_external_target_cwd_is_its_workspace` (`tests/
   test_multitarget_invariants.py:321–331`) проверяет только cwd, не
   наличие клона — планка это не ловит.
2. **Draft-MR.** `ensure_draft_mr` (`github_adapter.py:50–110`):
   `git push -u origin <branch>` из ROOT (74) — ветки sled в ROOT нет →
   отказ → `_incident` (журнал + алерт), переход в `in_dev` при этом
   совершается (Draft-MR — побочный эффект, `github_adapter.py:13–16`).
   Если бы ветка в ROOT была — `gh pr create` без `--repo` (82–85)
   завёл бы PR в репозитории АРТЕЛИ. Нужен `cwd=<клон целевого>` либо
   `gh --repo <url>`; `undraft_mr` (152–169) — то же.
3. **verifying / CI чужого репозитория.** `ci.head_sha(branch)`
   (`ci.py:46–53`) читает `refs/heads/<branch>` в ROOT; `check_runs`
   — репозиторий из cwd. Оба должны брать клон целевого и `--repo`.
   `gh run list` в `run_list` (`ci.py:128`) — тоже без `--repo`.
   Эмпирика T040 (события CI GitHub доезжают до 40 мин) применима
   и к sled — потолок 90 мин уместен.
4. **Артефактная ветка пульта для внешнего target — работает.**
   `artifact_branch.commit_files` пишет плотницки в ROOT от головы
   `main` пульта (`artifact_branch.py:117–137`), push best-effort
   (140–147); автокоммит артефактов шага берёт `tasks/<id>/` из
   `.artel/projects/<t>/workspace/tasks/<id>` и переносит в ветку
   (`checkpoint._commit_external_step_artifacts`, `checkpoint.py:
   277–280`); чтения FSM — через `artifact_source.resolve`
   (всегда артефактная ветка, `artifact_source.py:24–26`);
   приёмочные тесты материализуются из ветки (`acceptance.
   materialize_from_branch`, `acceptance.py:43–70`; вызовы в
   `fsm_advance.py:217–219, 309–316`). Побочность: артефактная ветка
   sled-задачи несёт полное дерево пульта + `tasks/<id>/` — это ветка
   пульта, по правилу «жизнь — где механика» так и задумано.
   Оговорка: `acceptance.run` исполняет `unittest discover` с
   `cwd=config.ROOT` (`acceptance.py:33`) — приёмочные тесты
   sled-задачи, которые должны импортировать код sled, запустятся из
   корня пульта без клона в `sys.path`. Для sled нужен `cwd=<клон>`
   (и — по ADR-0003 п.13 — контейнер).
5. **Снапшот в `refs/artifacts` чужого репозитория.** Механика верна
   (`snapshot.py:97–116`, `gitcmd.in_repo(workspace, "push", "origin",
   "<sha>:refs/artifacts/<id>")`), но требует, чтобы workspace был
   клоном с origin и правом push. Права: sled — репозиторий того же
   аккаунта, право есть по построению; проверки при подключении нет.
   Для чужого проекта (feedback, C2) `refs/artifacts/*` — не ветка,
   branch protection на них не распространяется; push такого ref
   требует права записи в репозиторий — это и есть «обязательное
   условие подключения» роадмапа.
6. **Легаси-фиксация внешнего target.** `fixation._fix_external`
   коммитит `.artel/projects/<t>/` (`fixation.py:59–98`; `workspace/`
   и `logs/` в его `.gitignore`, `projects.py:20`) — после M1/A7 там
   почти нечего фиксировать (артефакты ушли в ветку пульта); sha
   стабилен, `check_integrity` (`fixation.py:163–186`) для внешнего
   target вырождается в «всегда чисто». Журнал несёт два
   дополнительных sha — голову клона целевого и артефактной ветки
   (`store.record_fixation`, `store.py:653–667`). Не блокер, но
   инцидент целостности для sled сегодня ловить нечем: ни грязный
   клон, ни чужой коммит в его ветку не замечаются.
7. **RETRO и карта после мержа.** `_regenerate_and_commit_map` и
   `_generate_and_commit_retro` работают в scratch ПУЛЬТА
   (`fsm_merge_gate.py:337–340`) для любого target — для sled это
   коммит RETRO целевого в `docs/retro/` main артели. Правило
   «в пульте — только кухня пульта» (роадмап §3:209–212) требует для
   внешнего target ограничиться снапшотом (там RETRO уже есть,
   `snapshot.py:40, 93–95`).
8. **Автогейт приёмки.** Для внешнего target `acc_tdir`
   материализуется из ветки (`fsm_advance.py:309–316`), так что
   регрессия №6 (диск вместо ветки, задача 01M1NBWWPJMH) на sled в
   этой точке не воспроизведётся; но `_autogate_conditions`
   (`fsm_autogate.py:14–31`) смотрит `acc_tdir/acceptance_tests` —
   проверить на планке №6, что оба пути (self и внешний) покрыты
   одним тестом.

### 2.4 Doctor-проверки для внешнего target

Сегодня по каждой записи targets.yaml (`doctor.all_checks`,
`doctor.py:1039–1047`): `check_target_layout` — есть ли
`.artel/projects/<t>/.git` (артефактный репозиторий, `172–189`, warn);
`check_target_wrapper` — маркеры обвязки в workspace (`198–216`, warn);
`check_remote_empty` — у артефактного репозитория нет remote
(`942–955`, fail); `check_base_branch` — `gh repo view <url>` и
совпадение `base` (`958–988`, warn/skip); `recovery_check` — sha/
грязность/fsck артефактного репозитория (`421–476`). Плюс общие:
`check_pending_snapshots` (дожим снапшотов, `923–939`), `check_orphans`
(сканирует `.artel/projects/<t>/tasks`, `559–562`), `check_root_pin`
(пульт).

Чего нет для внешнего target (всё — про клон и фордж целевого, а не
про артефактный репозиторий):

1. **workspace — клон `url` с origin** и голова origin/base свежая
   (сейчас пустой каталог проходит все проверки).
2. **Право записи `refs/artifacts`** — `git push --dry-run origin
   HEAD:refs/artifacts/_probe` из workspace (чтение прав без записи).
3. **CI на pull_request у целевого** — наличие workflow в базовой ветке
   с триггером `pull_request` (`gh api repos/<o>/<r>/actions/workflows`
   или чтение `.github/workflows/*` в клоне) — иначе `verifying` будет
   висеть до потолка на каждой задаче.
4. **Защита базовой ветки** (ADR-0003 «Проверенные допущения» п.2,
   перенесено с GitLab на GitHub): `gh api repos/<o>/<r>/branches/<base>/
   protection` — информационно; для private Free-репозитория ответ
   «недоступно» ожидаем и сам по себе является фактом для §4.1.
5. **Напоминание триггера №24** («doctor warning при первом внешнем
   target с remote», `docs/triggers.md:47`) — не реализовано: в
   `orchestrator/` нет ни одного упоминания самоаппрува/№24.
   Сигнал вычислим: `gh api user` (логин учётки gh) совпадает с
   владельцем `url` целевого ИЛИ токен форджа один на все роли

6. **Токен форджа по `token_slot` целевого** присутствует в keychain
   (сейчас `check_token` — только слоты ролей для токена Claude).
7. **`no_paths` существуют в дереве целевого** (опечатка в списке —
   молчаливо пустая защита) и маркеры обвязки инвентаризованы уже В
   КЛОНЕ, не в пустом каталоге.

## 3. B-спайк руками и что можно свести в задачи конвейера

**Только руками (Оператор, вне конвейера)** — потому что это чужой
репозиторий, секреты и хост:

1. Запись `sled` в targets.yaml (защищённый путь) — после ТЗ-1/ТЗ-2,
   иначе запись мёртвая; до того — на ветке проверочного прогона.
2. Токен форджа для sled: решение — тот же аккаунт (риск §4.1 принят
   явно) или fine-grained PAT с `contents: write`, `pull_requests:
   write` на один репозиторий; в keychain-слот `sled-token`
   (`security add-generic-password`, вне git). Токен Claude — уже есть.
3. Сверка самого sled: есть ли CI на `pull_request` (если нет — добавить
   минимальный workflow руками в sled, иначе `verifying` бессмыслен);
   базовая ветка; защита ветки (Free/private — недоступна; решение:
   оставить как есть с принятым риском либо сделать sled публичным —
   решение Оператора); право push `refs/artifacts` (`--dry-run`).
4. Клон sled в `.artel/projects/sled/workspace` (до ТЗ-2 — руками,
   после — командой).
5. Собственно B-спайк изоляции (§2.3, таблица): образ с тулчейном sled
   и пином CLI, прокинутые токены, белый список сети, прогон одного
   шага роли в контейнере на клоне sled, повтор смоука MCP-вектора,
   проверка монтирования. Итог — страница фактуры в `docs/audits/`
   (по образцу `a-spike-2026-08-23.md`) и, при расхождениях, правки
   ADR-0003 п.14.
6. Ручной пробег чек-листа B2 по §1 перед стартом первой задачи.

**Сводится в задачи конвейера** (ТЗ-1…ТЗ-7, §5): репозиторный контекст;

## 4. Риски

### 4.1 Самоаппрув на общем токене (триггер №24)

Факты. Все операции форджа идут от ambient-учётки Оператора
(`gitcmd.git`/`ci.gh` с cwd ROOT под HOME Оператора; токен целевого в
коде не существует, §2.1). Draft-MR заводится, снимается с Draft и
мержится одной учёткой; вердикт ревьювера и approve Оператора живут
в артефактах и журнале БД пульта, на фордже их никто не требует.
Для пульта это принято ADR-0001; для sled (репозиторий того же
аккаунта) ситуация не меняется — «самоаппрув технически возможен на
чужих репо» (`docs/triggers.md:47`, остаточный риск фаз B–C принят
Оператором). Что усугубляет на B2: GitHub Free не даёт branch
protection на private-репозитории (`docs/design.md:485–487`), а
свойство «не может смержить» — у защиты ветки, не у токена (ADR-0003
«Проверенные допущения» п.2): раздельный PAT сам по себе самоаппрув не
запрещает, он лишь делает его видимым (другой автор коммита/MR).
Напоминание doctor'а по №24 — не реализовано (§2.4 п.5).

Рекомендация: (а) реализовать warn в ТЗ-5 — дёшево и закрывает букву
триггера; (б) на sled завести отдельный fine-grained PAT для ролей
(даже без защиты ветки — авторство MR и merge-коммита станет
различимым, что нужно для посева мутаций/метрик слепоты ревьюера
из вставки после B3); (в) решение о защите ветки (публичный sled или
Pro) — Оператору, в повестку go/no-go.

### 4.2 Остаточный риск фаз B–C

1. **`target-human` не реализован** (ни `awaiting_human`, ни
   undraft-как-гейт, ни merge-событие). Для sled (merge_gate=operator)
   не нужен; для C2 (feedback) — обязателен; sled его не отрепетирует.
2. **Единая точка отказа targets.yaml**: ошибка в записи sled ломает
   чтение файла для артели (`targets.py:57–58`) — при правке руками
   сначала `doctor` (`targets-yaml` fail), потом что-либо ещё.
3. **Артефактный репозиторий `.artel/projects/<t>/` после M1/A7 —
   рудимент**: фиксирует почти пустое дерево, `check_integrity` для
   внешнего target вырожден (§2.2 п.6). Не риск данных (артефакты — в
   ветке пульта и снапшоте), но ложное чувство контроля; кандидат на
   уборку после B2 отдельной мелочью (роадмап уже держит «контур
   счётчика — legacy»).
4. **Стоимость**: A7 стоила $134.86 при рамке $40 (RETRO); задачи
   класса «переделка механики» — делить на этапе ТЗ (решение 03.09).
   ТЗ-1 — именно такой класс, поэтому разбит на ТЗ-1/ТЗ-2/ТЗ-4 с
   реестром точек чтения первым пунктом SPEC.
5. **Гейт ёмкости diff выключен для внешнего target**
   (`fsm_advance.py:439–440`) — пока Р7 не закрыт, ревью sled-задачи
   структурно слепо (нет diff), а не просто «без потолка».

### 4.3 Классы регрессий нового флоу A7 применительно к внешнему target

**Класс А — «планка не покрыла полный флоу с эскалацией»** (ADR-0013,
регрессии №1–3, №7). Для внешнего target планка сегодня ещё уже:
единственные тесты с target ≠ self (`tests/test_multitarget_invariants.py`,
`test_multitarget.py`, `test_git_fixation.py`, `test_capacity_gate.py` и
др.) гоняют шаги с подменённым `subprocess`/`gitcmd.git` — ни один не
проводит sled-задачу через `new → in_dev → Draft-MR → verifying →
merge_gate → done → снапшот` на настоящем втором репозитории. Канарейка
v2 (ТЗ п.5) добавляет маршрут analyst/ANSWER/удаление артефакта — но
на self и с обходом verifying (п.4), внешний контур она не трогает.
Следствие: каждая из точек §2.2 будет «открыта» на живом sled, как
A7 открылась на живых задачах 03.09. Лечение — ТЗ-7 «внешняя
канарейка»: одноразовый репозиторий (GitHub, тот же аккаунт, либо
локальный bare-origin в песочнице для CI пульта) как второй target;
прогон с настоящим `git push`, с `gh` — на GitHub-варианте, обход
verifying — на локальном. Планка ТЗ-1 и ТЗ-2 обязана включать
хотя бы один тест на настоящем втором репозитории (не `fake_git`):
именно `fake_git` скрыл бы, что `git worktree add` шёл в пульт.

**Класс Б — «код читает локальную копию там, где источником истины
стал origin/артефактная ветка»** (регрессии №5, №6, №8; наблюдение
03.09 про автогейт). Для внешнего target «локальная копия» — это ещё
и «репозиторий пульта вместо клона целевого»; реестр точек (все
подтверждены кодом):

| Точка | Файл:строка | Что читает | Что должна читать для sled |
|---|---|---|---|
| Сверка свежести / подтяжка | `fsm.py:172–176, 184` | локальный `main` ROOT; worktree ПУЛЬТА | `origin/<base>` клона sled; worktree клона |
| Doctor «отставание ветки» | `doctor.py:635` | `commits_behind` в ROOT | клон sled |

| Draft-MR / undraft / комментарий | `github_adapter.py:82, 102, 162` | `gh` из ROOT | `gh --repo <url>` |
| Защищённые пути в MR | `github_adapter.py:42–47` | diff в ROOT, `config.PROTECTED_PATHS` | diff в клоне, `targets.yaml.no_paths` |

только для пульта — её ТЗ нужно дополнить до «база свежести —
origin/<base> репозитория ЦЕЛЕВОГО задачи», иначе на B2 повтор.

**Класс В — «утечка тестов в настоящий репозиторий»** (задача
01M1KVGD18P9H5WR7VM8TGPV1T): при появлении второго настоящего

### ТЗ-1: Репозиторный контекст target для git/gh-слоя

Источник: это исследование (§2.2, §4.3 класс Б); ADR-0003 п.4 и п.6
(workspace — эфемерный клон целевого; merge в целевой — только
оркестратор через адаптер); роадмап §3 B1b (Draft-MR-флоу, первый
прогон — на артели; второй — на sled) и §4 п.2г (реестр регрессий,
класс «локальная копия вместо источника истины»).

Суть: все операции над кодом задачи (push, MR, CI, свежесть, diff,
merge, RETRO) исполняются в репозитории ЦЕЛЕВОГО задачи, а не в
репозитории пульта. Сегодня `gitcmd.git` и `ci.gh` привязаны к
`config.ROOT`; для self это верно, для любого другого target — нет.

Требуется:
1. Понятие «репозиторный контекст target» в одном модуле: путь клона
   (`config.ROOT` для self; `.artel/projects/<t>/workspace` иначе),
   адрес форджа (`targets.yaml.url`), базовая ветка. Все точки
   таблицы §4.3 (класс Б) переводятся на него; SPEC НАЧИНАЕТСЯ с
   реестра этих точек (по образцу M1), каждая — с указанием, что
   читалось и что читается теперь.
2. `ci.gh` принимает контекст: `--repo <url>` для `pr create/ready/
   comment`, `api repos/<owner>/<repo>/…`, `run list`; `ci.head_sha`
   и `check_runs` — по клону целевого.
3. Сверка свежести и подтяжка (`_pull_main_or_escalate`) — против
   `origin/<base>` репозитория целевого (объединить с задачей
   01M1NBWPKNBXP9ZXXQDJM7AXPJ: её ТЗ дополняется параметризацией по
   target; одна из двух задач поглощает другую — решение Оператора).
4. Merge для внешнего target с `merge_gate: operator`: scratch-worktree
   и push `refs/heads/<base>` — в клоне целевого; для внешнего target
   после мержа НЕ регенерируется карта и НЕ коммитится RETRO в main
   (правило «в пульте — только кухня пульта»; RETRO — в снапшоте).
5. Гейт ёмкости diff и diff ревью-пакета — из клона целевого; для
   внешнего target гейт больше не пропускается.
6. Тесты: end-to-end на ДВУХ настоящих git-репозиториях в песочнице
   (пульт + целевой с локальным bare-origin): задача внешнего target
   проходит `new → in_dev → review (diff непустой) → merge_gate → done`
   с merge в origin целевого и без единого коммита в main пульта;
   существующие тесты зелёные; инвариант «тесты не пишут в настоящий
   репозиторий» (01M1KVGD18P9H5WR7VM8TGPV1T) — предусловие.

Зоны: orchestrator/gitcmd.py, ci.py, github_adapter.py, fsm.py,
fsm_advance.py, fsm_merge_gate.py, fsm_postmerge.py, review.py,
acceptance.py, doctor.py (branch-freshness), tests/sandbox.py, tests/.
Конфликт зон с №5/№6/№8 — эскалация; порядок — §6.

Не входит: клон и ветка задачи (ТЗ-2); `target-human`/`awaiting_human`
(C1); карта кодовой базы целевого (ТЗ-4); контейнер (ТЗ-6).

Рамка: $40 (класс «переделка механики»; делить дальше — если реестр
точек в SPEC превысит 15 строк, вынести merge/postmerge в отдельный
этап).

### ТЗ-2: Клон целевого, ветка задачи и рабочий каталог роли внешнего target

Источник: §2.2 п.1; ADR-0003 §4, 3д («workspace — эфемерный клон
целевого»; параллельные задачи одного проекта — per-task git worktree);
докстринг `snapshot.py:19–21` («origin — только если роль сама
клонирует»); миссии ролей `role_prompt.py`.

Суть: рабочий каталог роли внешнего target сегодня — пустой `mkdir`.
Нужно: `target-init` клонирует целевой, `role_cwd` даёт worktree клона
на ветке задачи, миссия роли говорит правду.

Требуется:
1. `target-init <t>` клонирует `targets.yaml.url` в
   `.artel/projects/<t>/workspace` (идемпотентно: есть клон с тем же
   origin — `fetch`); отказ именованный (нет доступа, url не тот).
2. `role_cwd` внешнего target — git worktree клона на ветке задачи
   (`.artel/projects/<t>/worktrees/<id>` или общий `config.WORKTREES` с
   пометкой target — решение исполнителя), ветка создаётся от
   `origin/<base>` при первом шаге; `run` отказывает, если worktree
   стоит не на ветке задачи (симметрия `runner.py:174–184`).
3. Автокоммит артефактов шага и WIP-чекпоинт таймаута читают
   `tasks/<id>/` из этого worktree (связка с 01M1NBWTSXEJB24PXR417YF1VA:
   зона роли для внешнего target — весь клон, кроме `tasks/<id>/`).
4. Миссии ролей формулируются по факту: для внешнего target —
   «клон целевого <url>, ветка задачи выписана в этом каталоге»;
   упоминание «worktree пульта» — только для self.
5. `new --target <t>` в CLI (`artel.py`), отказ на необъявленный target
   с перечнем объявленных (Р3 сливается сюда).
6. `kill`/`done` убирают worktree клона; `doctor` ловит сирот в клонах
   целевых (расширение `_orphan_worktrees`).
7. Тесты: два настоящих репозитория в песочнице; роль стартует в
   worktree клона на ветке задачи; `tasks/<id>/` не попадает в кодовую
   ветку целевого; `new --target`; существующие тесты зелёные.

Зоны: orchestrator/projects.py, workspace.py, runner.py,
role_prompt.py, checkpoint.py, cleanup.py, doctor.py, artel.py,
tests/. Предусловие: ТЗ-1 (контекст) — либо одна волна с ним.

Не входит: креды форджа роли (ТЗ-4); контейнер (ТЗ-6).

Рамка: $25.

### ТЗ-4: Исполнители полей targets.yaml — no_paths, token_slot, project_skills, карта целевого

Источник: §2.1; ADR-0003 п.2, п.8 («no_paths целевого проверяются до
merge»), п.12 (карта целевого при подключении), п.14 (project_skills —
курируемый список; CLAUDE.md целевого — в бриф как недоверенное),
3з; роадмап P3 «автогейт плана: пути × no_paths = стоп».

Суть: три поля объявлены и валидируются, но ничем не исполняются;
карта кодовой базы в брифе — всегда карта пульта.

Требуется:
1. `no_paths`: diff ветки задачи против базы (в контексте target,
   ТЗ-1) × `no_paths` → отказ перехода `in_dev → review` с перечнем
   путей (не эскалация — роль чинит); в merge_gate — эскалация при
   конфликте в этих путях (симметрия `config.PROTECTED_PATHS`);
   комментарий на MR — по `no_paths` целевого, а не по константе
   пульта. Для self `no_paths` артели из targets.yaml и
   `config.PROTECTED_PATHS` — один источник (решение исполнителя:
   константа читает targets.yaml или наоборот; дублирования не
   остаётся).
2. `token_slot`: токен форджа целевого из keychain-слота — роли
   (переменная окружения для credential helper / `GH_TOKEN`) и
   оркестратору для `gh --repo`; отсутствие — pre-flight fail с именем
   слота; `doctor.check_token` расширяется на слот целевого.
3. `project_skills`: список файлов `skills/` пульта (курируемых), которые
   добавляются в промпт роли для задач этого target; путь вне `skills/`
   — отказ загрузки конфигурации.
4. Карта кодовой базы целевого: генерация при `target-init` и на
   мерже (в контексте target), хранение в `.artel/projects/<t>/
   knowledge/maps/` (ADR-0003 3д); бриф developer/analyst для внешнего
   target получает карту ЦЕЛЕВОГО; `CLAUDE.md`/`AGENTS.md` целевого —
   в бриф как «недоверенные конвенции проекта» границами задачи
   01M1GV6H5D.
5. Тесты: отказ по `no_paths`; токен из слота целевого доходит до
   роли и не утекает в журнал; карта целевого в брифе; существующие
   тесты зелёные.

Зоны: orchestrator/targets.py, config.py, fsm_advance.py,
fsm_merge_gate.py, github_adapter.py, runner.py, doctor.py, brief.py,
roles.py, scripts/codebase_map.py (параметр корня), tests/.

Не входит: разделение PAT по ролям пульта (триггер №24); автогейт
плана целиком (P3).

Рамка: $25–40 (делить: 1–2 и 3–4 — два этапа).

### ТЗ-5: Doctor — проверки подключённого внешнего target

Источник: §2.4; ADR-0003 п.7 (проверка при подключении), «Проверенные
допущения» п.2 (сверка защиты базовой ветки при подключении и
периодически), п.14 (инвентаризация обвязки при подключении);
роадмап §3:213–215 (право записи `refs/artifacts` — обязательное
условие подключения); docs/triggers.md №24 (напоминание doctor).

Суть: doctor сегодня проверяет артефактный репозиторий target и имя
базовой ветки; клон и фордж целевого — слепая зона.

Требуется (по каждой объявленной записи targets.yaml, кроме self там,
где неприменимо — явное решение, не skip):
1. workspace — клон `url` с origin, голова `origin/<base>` не старше
   порога (fetch без изменения чекаута).
2. Право push в `refs/artifacts/*` — `git push --dry-run` пробного ref;
   отказ — fail (условие подключения).
3. CI на `pull_request` у целевого — есть workflow с этим триггером;
   нет — warn с текстом «verifying будет ждать до потолка».
4. Защита базовой ветки — информационно; недоступна (Free/private) —
   так и сказать.
5. Напоминание №24: учётка `gh` = владелец `url` или токен ролей
   общий (`token_fallback`) → warn «самоаппрув технически возможен;
   решение — docs/triggers.md №24»; не блокирует.
6. Токен форджа в слоте `token_slot` присутствует (после ТЗ-4).
7. `no_paths` существуют в дереве клона; маркеры обвязки
   инвентаризуются в клоне.
8. Тесты: каждая проверка — ok/warn/fail на песочнице с двумя
   репозиториями; self проходит без ложных warn.

Зоны: orchestrator/doctor.py, projects.py, tests/test_doctor.py.
Предусловие: ТЗ-2 (клон).

Не входит: авторешения; изменение прав на фордже.

Рамка: $25.

### ТЗ-6: Контейнерный запуск шага роли (B3 — песочница в строю)

Источник: ADR-0003 п.13 (контейнер обязателен до фазы C), п.14
(«песочница — единственная линия против вектора тулчейна»); роадмап §3
B3 и B-спайк; §2.3 этого отчёта; docs/design.md §8 «Песочницы».
Предусловие: фактура B-спайка руками (docs/audits/b-spike-<дата>.md).

Суть: шаг роли внешнего target исполняется в контейнере с клоном
целевого, токенами через окружение, пином CLI и белым списком сети;

Требуется:
1. Образ: пин `@anthropic-ai/claude-code@<config.CLI_VERSION_PIN>`

2. Запуск: `runner.spawn_agent` для внешнего target — `docker run` с

3. Сеть: белый список (api.anthropic.com, фордж целевого) — способ по

4. Тот же `role_cmd` (флаги изоляции) внутри контейнера; смоук

5. `acceptance.run` для внешнего target — в контейнере, `cwd=<клон>`.
6. Self остаётся на хосте (решение ADR-0003: контейнер — для чужого

7. Тесты: структурные (argv docker, монтирования, env без утечки

Зоны: sandbox/Dockerfile, orchestrator/runner.py, doctor.py,

### ТЗ-7: Внешняя канарейка — сквозной прогон внешнего флоу на одноразовом репозитории

Источник: §4.3 класс А; ADR-0013 ч.1 (канарейка — условие обновления
пина; «пути, которые планка не покрыла»); ТЗ канарейки v2 п.2, п.4
(эфемерный клон, обход verifying); роадмап B3 «первая конвейерная
задача».

Суть: канарейка v2 проверяет self-флоу; внешний флоу (второй origin,
Draft-MR, verifying, merge в чужой main, снапшот в чужой
`refs/artifacts`) без прогона до B2 будет «открыт» на sled так же,
как A7 открылась 03.09.

Требуется:
1. Второй target канарейки: локальный bare-репозиторий как origin
   (без форджа — обход Draft-MR/verifying, как в v2) — для CI пульта;
   и режим с настоящим одноразовым GitHub-репозиторием того же
   аккаунта (Draft-MR, verifying, merge, `refs/artifacts`) — по
   команде Оператора, не в CI.
2. Шаблон ТЗ канареечной задачи внешнего target — в пуле v2
   (руками, вне git), с маркером ожидаемого исхода.
3. Сверка после прогона: ноль коммитов в main пульта; артефактная
   ветка убрана после подтверждённого снапшота; `refs/artifacts/<id>`
   в origin целевого; MR закрыт как merged.
4. Условие входа в B2: зелёный прогон в GitHub-режиме — фиксируется в
   журнале (тот же механизм, что «зелёная канарейка → пин»).

Зоны: orchestrator/canary.py, tests/, .artel/tz (шаблон — руками).
Предусловия: ТЗ-1, ТЗ-2, канарейка v2 (01M1NEEWH5K1XPFRDGRMPYSBXJ).

Не входит: авторешения по красной канарейке; посев мутаций.

Рамка: $25.
