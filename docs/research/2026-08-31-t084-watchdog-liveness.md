# Исследование: watchdog живости конвейера

Задача: T084. Дата: 31.08.2026. Тип: предложение (не реализация,
SPEC требование 5) — код watchdog-механизма в объёме этой задачи не
писался.

## Контекст в двух предложениях

Роадмап P3 просил карту существующих механизмов, детектирующих (a)
задачу, числящуюся в агентном состоянии без живого процесса, и
(b) шаг/цикл, работающий дольше разумного порога без прогресса, и
предложение, чего не хватает поверх. Актуальность: решение Оператора
31.08 подняло `MAX_PARALLEL_TASKS` 5→10 (`orchestrator/config.py:140`) —
при десятке одновременных задач молчаливая смерть одной сессии
вероятнее и заметнее глазами Оператора уже не становится.

## 1. Карта существующих механизмов

Для каждого — что он детектит и НЕ детектит применительно ровно к
сценариям (a) и (b) из ТЗ.

### 1.1 Таймаут шага в runner (T022/T041)

Код: `orchestrator/runner.py:802` (`proc.wait(timeout=config.AGENT_TIMEOUT_SEC)`,
1800с, `orchestrator/config.py:45`), обработка истечения —
`runner.py:803-838`; чекпоинт WIP при таймауте —
`commit_timeout_checkpoint` (`runner.py:441`, T041).

- (a) **НЕ детектит.** Таймаут — это `proc.wait` того же самого
  оркестраторского процесса, который запустил агента. Если этот процесс
  (тот, что выполняет `run`/`auto`) сам умирает — падает, `kill -9`,
  падение хоста — никто не досчитывает 1800 секунд и не переходит в
  ветку обработки таймаута. Задача остаётся в агентном состоянии, WIP
  не чекпоинтится, журнал молчит: последняя запись — «agent run
  started» (`runner.py:761`) без терминальной пары.
- (b) **Частично детектит, но только внутри одного шага.** Если сам
  агентный процесс жив, но не выводит ничего дольше 1800с — таймаут
  сработает. Но порог — «дольше 30 минут» без всякого понятия
  прогресса внутри этого окна (агент может 29 минут переписывать один
  файл туда-обратно — не поймано); и порог действует только на ОДИН
  вызов `run`, не на серию шагов auto-цикла — многошаговое топтание,
  где каждый отдельный шаг укладывается в 1800с, таймаутом не ловится
  вовсе.

### 1.2 Health-check C0 (планируемый, фаза C)

Материал: `docs/roadmap.md:98-101`. Не реализован — фаза C не
начата (`docs/roadmap.md:244`, критерий выхода B ещё не закрыт).

- (a) **НЕ детектит** — ни сейчас (кода нет), ни по замыслу: C0 —
  health-check ПОЛЛЕРА MR GitLab («интервал 10 мин, health-check 5
  неудач подряд = алерт», `docs/roadmap.md:101`), другой компонент
  другой фазы. Он не про агентный шаг/auto-цикл конвейера вообще.
- (b) **НЕ детектит** — та же причина: относится к периодическому
  опросу GitLab, не к работе агента внутри задачи.

Механизм упомянут в SPEC как «рядом» ровно потому, что по названию
похож («health-check»), но по факту не пересекается со сценариями
ТЗ ни в реализации, ни в замысле.

### 1.3 Alerts A3 и авто-закрытие T035

Код: `orchestrator/alerts.py` (`raise_alert`, `open_alerts`, `ack`,
`auto_ack`); авто-закрытие — `orchestrator/doctor.py`, функция
`_auto_ack_gone` (вызывается из `check_orphans`, `check_backup_age`,
`check_leases:679`, `check_merge_lock`), SPEC T035.

- (a) **НЕ детектит сам по себе.** `alerts` — шина/носитель сигналов
  (таблица `alerts` в `state.db`, `store.py:47-50`), не источник
  наблюдения. Она заводит incident, только когда ЧТО-ТО ДРУГОЕ уже его
  нашло (см. 1.5 ниже — реально это `check_leases`) и закрывает его,
  когда та же проверка перестала находить условие. Собственной
  детекции мёртвого процесса у `alerts.py` нет.
- (b) **НЕ детектит.** Ни один из источников алертов A3
  (`check_orphans`, `check_backup_age`, `check_merge_lock`,
  `check_leases`) не измеряет прогресс шага/цикла — все они про
  «сирота», «бэкап устарел», «мьютекс с мёртвым держателем», «lease с
  мёртвым pid». Топтание живого процесса вне их предмета.
- Дополнительное ограничение, общее для всей ветки doctor/alerts:
  ничего из них не запускается по расписанию (грепом по коду и
  документации подтверждено — ни cron, ни systemd/launchd записи нет).
  `doctor` — команда CLI, вызываемая Оператором вручную. Сигнал
  существует только в момент, когда кто-то решил его спросить.

### 1.4 Отказ №12 реестра v5 — возраст состояния

Материал: `docs/audits/roadmap-audit-2026-08-24-v5-chief-engineer.md:100`
(строка таблицы реестра отказов: «Задачи-зомби | метрика возраста в
состоянии; еженедельный список старше X | inbox-напоминание»).

- (a) и (b) **НЕ детектит — не реализован.** Проверено: ни в
  `orchestrator/*.py`, ни в тестах нет кода, читающего возраст
  `tasks.state`/`tasks.updated_at` для алертинга (единственные
  упоминания «возраст состояния» — в самих SPEC/реестре, как задел на
  будущее: `tasks/T022/SPEC.md:116` явно пишет «не в этой задаче»).
  Это запись реестра отказов — признанный класс проблемы, не
  построенный детектор.
- Важная деталь для раздела 3: примитив для него уже есть в схеме —
  `tasks.updated_at` пишется атомарно при каждом успешном переходе
  состояния (`store.py:473-508`, `set_state`, T050), с точностью до
  микросекунд именно для того, чтобы не путать порядок событий под
  нагрузкой. Строить возраст состояния не с нуля, а поверх готовой
  колонки.

### 1.5 Lease/liveness (T044, T057, T062) + `doctor.check_leases`

Код: `orchestrator/lease.py` (таблица `leases`, `acquire`/`release`),
`orchestrator/liveness.py` (`_age_seconds`, `_pid_alive` — общие для
lease/merge_lock/doctor), `orchestrator/doctor.py:652-681`
(`check_leases`).

- (a) **Детектит — частично и только по требованию.**
  `check_leases` (`doctor.py:664-665`) находит lease с мёртвым `pid`
  **на том же хосте**, где выполняется `doctor`, и заводит
  `incident`-алерт `doctor.leases` немедленно (проверка — прямая
  адресуемость pid `os.kill(pid, 0)`, не завязана на порог давности
  `LEASE_STALE_AFTER_SEC=7200` — это отличает её от «lease протух», что
  проверяет `lease.acquire` при захвате). Условия, при которых это НЕ
  срабатывает: (1) `doctor` никто не вызвал — нет расписания (см. 1.3);
  (2) держатель lease — на другом хосте: `check_leases` explicitly
  «чужой host не проверяется» (докстринг `doctor.py:654-655`) —
  мульти-хост эксплуатация не покрыта в принципе, не только по частоте
  вызова.
- (b) **НЕ детектит.** Lease живёт, пока жив процесс, который его
  держит — топчущийся, но живой процесс лизу не тревожит: `heartbeat_ts`
  обновляется на `acquire()` в начале каждого мутирующего вызова
  (`lease.py:64-88`), а не непрерывно во время самого шага — но живости
  ради `check_leases` это и не нужно, ей важен только факт «pid
  адресуем», а не факт прогресса.

### 1.6 Стоп-кран T038 (auto: топтание без отказа)

Код: `orchestrator/auto.py` (`cmd_auto`, `auto_stop`), SPEC T038
(два подряд шага без смены состояния, `advance` оба раза отказал
записью в журнал «переход отклонён: …» с ДОСЛОВНО одинаковым текстом).

- (a) **НЕ детектит** — не про мёртвый процесс вообще, а про то, что
  `advance` (внутри ЖИВОГО процесса `auto`) дважды подряд отверг
  переход по одной и той же именованной причине.
- (b) **Детектит узкий подкласс, не общий случай.** Ловит ровно
  «топчется из-за одной и той же преграды advance» (SPEC-не-ready,
  грязная копия и т.п.). НЕ ловит: (i) шаги, где `advance` каждый раз
  отказывает с РАЗНЫМ текстом (SPEC T038 требование 5 — сознательно не
  триггерит, чтобы не путать разные причины); (ii) шаги, где `advance`
  вообще не отказывает записью в журнал — агент раз за разом переводит
  задачу в состояние `ready`-подобное, но артефакт по сути не движется
  содержательно (например, правит нерелевантные файлы) — тогда
  единственная верхняя граница — грубый `AUTO_MAX_STEPS=30`
  (`config.py:124`), который остановит цикл, но только после того, как
  сгорят все 30 шагов, а не раньше.

## 2. Дыры

Явные сценарии, которые НИ ОДИН механизм из раздела 1 не покрывает
целиком:

**Дыра 1 — молчаливая смерть держащего процесса без ручного `doctor`.**
`check_leases` (1.5) технически СПОСОБНА обнаружить мёртвый pid на
своём хосте немедленно, но это происходит только если кто-то вызвал
`doctor`. Между вызовами задача может висеть в агентном состоянии с
мёртвым lease сколь угодно долго незамеченной — прямое попадание в
сценарий (a) ТЗ, детектор для которого уже написан, но не подключён к
расписанию. Это САМАЯ дешёвая дыра к закрытию (см. Кандидат C ниже).

**Дыра 2 — смерть процесса на чужом хосте.** `check_leases` явно не
проверяет `pid` не на своём `hostname` (1.5). При эксплуатации с
нескольких машин (сейчас, судя по коду и материалам, не подтверждённый
сценарий — single-host) осталась бы совсем непокрытой. Отмечена для
полноты, приоритет низкий — нет фактуры мульти-хост запуска.

**Дыра 3 — auto-цикл топчется без идентичного текста отказа `advance`
и без исчерпания `AUTO_MAX_STEPS`.** T038 (1.6) ловит только
ДОСЛОВНО одинаковый повторный отказ. Цикл, где каждый шаг отказывает
по-разному или где `advance` вообще не пишет отказ (шаг формально
двигается, но не содержательно), топчется вплоть до 30 шагов —
верхняя граница есть, но она про деньги (потолок расхода), не про
раннее обнаружение «топтания без прогресса» именно как сценария (b).

**Дыра 4 — топтание внутри ОДНОГО шага, в пределах 1800-секундного
окна.** Ни таймаут (1.1), ни lease (1.5), ни alerts (1.3) не различают
«агент работает 25 минут и близок к результату» от «агент 25 минут
крутится без пользы» — оба укладываются в `AGENT_TIMEOUT_SEC` и не
дают никакого промежуточного сигнала.

**Дыра 5 — возраст состояния как класс задачи (отказ №12) не
реализован вообще.** Признанный класс (реестр v5 №100), явный задел в
SPEC T022, но код не написан (1.4). Без него не покрыт более общий
случай, шире буквальных (a)/(b) ТЗ: задача попросту забыта Оператором
в состоянии, ожидающем человека (например, `review_gate` неделю) — не
про мёртвый агентный процесс, но про ту же «живость конвейера».

Дыры 1 и 5 — самые дешёвые к закрытию, потому что под них уже есть
готовые примитивы (`check_leases`, `tasks.updated_at`) — не хватает
только регулярности вызова и, для 5, самой check-функции. Дыры 3 и 4 —
дороже: требуют нового понятия «прогресс» внутри уже идущего шага/
цикла, которого система сегодня не измеряет вовсе.

## 3. Оценка кандидатов

### Кандидат A — heartbeat шага в журнал

**Механизм.** Во время долгого агентного шага (между стартом
subprocess и его завершением, `runner.py:781-798`) периодически
писать heartbeat — либо новую запись в `steps`/журнал, либо (дешевле)
чаще обновлять уже существующий `leases.heartbeat_ts` из фонового
потока, а не только при `acquire()`. Естественное место — рядом с
`agent_log.OutputPump` (`orchestrator/agent_log.py`), который уже
крутится отдельным потоком и перекачивает вывод агента, пока `runner`
блокируется на `proc.wait`.

**Какие дыры закрывает.** Сам по себе — ни одной: heartbeat это
ИСТОЧНИК сигнала, не детектор. Он даёт МАТЕРИАЛ, на котором можно
построить обнаружение Дыры 4 (сравнить heartbeat с ростом лога/числом
новых строк вывода — «пишет» vs «пишет одно и то же» — прогресс), но
для этого нужен ЕЩЁ читатель (тот же `doctor` или новый watchdog),
которого этот кандидат сам не даёт.

**Что рядом переиспользовать.** `leases.heartbeat_ts` — уже
существующая колонка ровно такого назначения; `OutputPump` — уже
существующий фоновый поток, к которому можно привязать периодичность
без нового механизма многопоточности.

**Риски.** Частые записи в `state.db` из фонового потока во время
шага — конкурентный доступ при 10 параллельных задачах (WAL уже
включён, `store.enable_wal`, но контеншн стоит измерить, не
предполагать); усложняет и без того тонкую логику `lease.py`
(докстринг модуля явно описывает инвариант «кто взял с нуля, тот и
отпускает» — частые записи из другого потока рискуют его размыть, если
не изолировать чётко). Реальной фактуры (инцидента), где именно
топтание ВНУТРИ одного 30-минутного шага стоило денег или времени
Оператора, в материалах задачи нет — известные инциденты (T035, T046)
про смерть/топтание МЕЖДУ шагами, не внутри одного.

**Стоимость.** Средняя: новый поток/периодика + тесты конкурентности
— $15–25, ближе к верхней границе класса «типовая задача» из-за риска
гонок.

### Кандидат B — возраст состояния в doctor (отказ №12)

**Механизм.** Новая check-функция в `orchestrator/doctor.py` по
образцу `check_leases`/`check_backup_age`: для каждой задачи —
`now() - tasks.updated_at` (колонка уже пишется атомарно на каждом
переходе, `store.py:473-508`) против порога, свой для класса
состояния (агентные состояния типа `in_dev`/`reviewing` — короткий
порог; состояния, ожидающие Оператора, типа `review_gate`/`escalated`
— длинный порог, иначе ложные тревоги на легитимно долгих гейтах).
Превышение — `incident`-алерт по образцу существующих `raise_alert`
вызовов, с авто-ack по возвращении в норму (T035, тот же приём).

**Какие дыры закрывает.** Дыру 5 целиком. Дыру 1 и 3 — частично и
косвенно: возраст состояния коррелирует с «висит», но без сверки с
lease (1.5) не отличает «зависла» от «честно долго работает» —
ложноположительный на легитимно долгом шаге без комбинации с
`check_leases`. Дыру 4 не закрывает вовсе (шаг внутри 1800с не успеет
состариться настолько, чтобы сработать разумный порог).

**Что рядом переиспользовать.** Паттерн `Check`/`raise_alert`/
`_auto_ack_gone` в `doctor.py` — весь строительный материал уже есть,
это буквально «ещё одна check-функция» того же вида, что четыре
существующих.

**Риски.** Порог по классам состояний — ещё один конфиг, который
предстоит держать согласованным с `AGENT_TIMEOUT_SEC`/`AUTO_MAX_STEPS`
(не путать смыслы — это разные шкалы времени: секунды шага против
дней ожидания Оператора). Без комбинации с lease даёт шум на честно
долгих гейтах.

**Стоимость.** Небольшая: $15–25, ближе к нижней границе — паттерн
skeleton уже есть, работа в основном в подборе порогов и тестах.

### Кандидат C — сторожевой прогон watchdog по расписанию

**Механизм.** Периодический (внешний планировщик — cron/launchd, или
встроенный таймер внутри уже работающей `auto`-сессии) автоматический
вызов `doctor` (или узкого подмножества его проверок:
`check_leases` + будущий Кандидат B), без участия Оператора,
автоматически заводящий/закрывающий алерты по существующему пути
`raise_alert`/`_auto_ack_gone`.

**Какие дыры закрывает.** Дыру 1 **целиком** — детектор (`check_leases`)
уже написан и работает, не хватает буквально только регулярности
вызова. Делает Кандидат B полезным (без расписания возраст состояния
тоже никто вовремя не увидит — та же болезнь, что у alerts A3 сегодня,
раздел 1.3). Дыру 2 не закрывает (мульти-хост — ограничение самого
`check_leases`, не расписания). Дыры 3 и 4 не закрывает — doctor
работает МЕЖДУ шагами, не имеет доступа внутрь блокирующего
`proc.wait` идущего шага.

**Что рядом переиспользовать.** Весь код детекции (`check_leases`,
будущий возраст состояния) уже существует или относится к Кандидату
B — Кандидат C добавляет только обвязку вызова, не новую логику
обнаружения.

**Риски.** Инфраструктурный, не кодовый: у пульта сегодня нет
постоянного демона (Фаза 0 сознательно «CLI по требованию, не демон»
— решение Оператора 24.08, реестр v5 §1, «этап 1 — статика, демон в
Г0» согласно аудиту v4). Нужно решить, ЧЕМ физически планировать вызов
— внешний cron/launchd на машине, откуда управляют пультом, требует
доступа к этой машине и её собственного мониторинга (кто следит за
самим cron?); либо периодика внутри уже запущенной `auto`-сессии —
проще технически, но работает, только пока хоть одна `auto`-сессия
жива (сама подвержена сценарию (a), который должна ловить) и создаёт
вопрос «кто дежурный», аналогичный уже решённому для `merge_lock`
(единственный держатель мьютекса). Это решение должно быть предметом
собственной SPEC, не додумывается этим исследованием.

**Стоимость.** Средняя: сам вызов `doctor` дёшев, но проектирование
«кто и как планирует» — $15–25.

## 4. Рекомендация

**Строить, по приоритету:**

1. **Кандидат C** (сторожевой прогон по расписанию) — первым и
   отдельным MR. Обоснование: закрывает самую большую и самую дешёвую
   дыру (Дыра 1) практически без нового кода детекции — только
   регулярность вызова уже существующей проверки; является
   предпосылкой, без которой Кандидат B (и вообще вся ветка
   doctor/alerts, раздел 1.3) остаётся сигналом, который никто не
   видит вовремя.
2. **Кандидат B** (возраст состояния, отказ №12) — вторым MR, сразу
   вслед за C (без C он тоже бесполезен по той же причине). Закрывает
   Дыру 5 и снижает Дыру 3 при комбинации с проверкой lease (та же
   check-функция или соседняя — решается на этапе SPEC).

**Где жить:** `orchestrator/doctor.py` — сама логика детекции (для B);
обвязка расписания (для C) — вне кода пульта как таковая, решение
между внешним cron/launchd и встроенной периодикой внутри `auto` —
отдельный вопрос следующей SPEC, не этого исследования. Роль —
`analyst` пишет SPEC (по образцу T022/T035/T038), `developer`
реализует; фаза — P3 (там же, где сейчас стоит строка-исследование
T084), предусловий из фаз B/C не требует — оба кандидата работают на
существующем однохостовом Фазе-0 коде.

**Оценка (в стиле роадмапа):**
- «Watchdog: сторожевой прогон `doctor` по расписанию» — $15–25
- «Doctor: возраст состояния (отказ №12 реестра v5)» — $15–25

**НЕ строить сейчас — и почему:**

- **Кандидат A (heartbeat шага в журнал).** Решает только Дыру 4
  (топтание внутри одного 30-минутного шага), для которой в
  материалах задачи нет подтверждающей фактуры — известные инциденты
  про смерть/топтание МЕЖДУ шагами (T035, T046), не внутри одного.
  Добавляет конкурентный доступ к `state.db` из фонового потока при
  10 параллельных задачах — риск, соразмерность которого не с чем
  сверить без инцидента. `AGENT_TIMEOUT_SEC=1800с` уже служит верхней
  границей ущерба такого сценария. Отложить в P3 до появления
  фактуры — тем же приёмом, каким система уже откладывает пункты без
  инцидента (например, строка WIP-лимита, `docs/roadmap.md:184`: «не
  спешить»).
- **Демон-супервизор, автоматически перезапускающий упавший `auto`.**
  Не входил в список кандидатов SPEC, оценён дополнительно и отклонён:
  противоречит сознательному выбору Фазы 0 «CLI по требованию, не
  демон» (решение Оператора 24.08, аудит v4); маскирует причину смерти
  автоперезапуском вместо того, чтобы её алертить Оператору — рискует
  завести собственный класс топтания, аналогичный тому, что уже тушат
  T035/T038, но на уровень выше (процесс, а не advance).
- **Мульти-хостовая видимость lease (закрытие Дыры 2).** Нет фактуры
  эксплуатации с нескольких машин — `check_leases` сознательно
  пропускает чужой host, и это принятое ограничение, не забытый
  случай. YAGNI до появления сценария.

**Итог:** дешёвая связка Кандидат C → Кандидат B закрывает две из пяти
дыр (1 и 5) целиком и одну (3) частично, суммарно $30–50, почти без
нового кода детекции — переиспользует то, что уже написано в T022/T035.
Кандидат A и мульти-хост — в беклог без фактуры.
