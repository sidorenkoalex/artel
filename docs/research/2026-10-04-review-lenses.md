# Исследование: линзы ревью — домены, слои, свойства и виды проверок

Дата: 04.10.2026. Тип: исследование ассистентской сессии при Операторе,
не решение — решений Оператора по нему нет, код не менялся.

Вопрос Оператора: применима ли схема «архетип + домен» из
`docs/research/2026-09-22-chatgpt-agent-integration.md` к этапу ревью,
если проверка безопасности — не домен. Безопасность — только пример: та
же постановка касается БД, инфраструктуры, логического модуля. Нужно
разобрать, как вообще делятся проверки, и оценить это с точки зрения
удобства для агента-ревьювера, без привязки к человеческим процессам
(ролям в команде, кодовладельцам, ритуалам согласования).

Итог одной строкой: делить ревью нужно не на «домены» и не на роли, а на
**линзы** — единицы проверки с детерминированным триггером, пакетом
знаний и назначенным методом. Домен, слой, свойство и вид изменения —
четыре разных источника триггеров для одной и той же формы линзы. Самое
дешёвое и полезное для агента — не добавлять проверки, а убрать из его
контекста неактуальные и передать детерминированное коду.

---

## 1. Четыре оси деления проверок

Исходная модель (домен = путь владения) покрывает только одну из осей.
Проверки делятся минимум по четырём независимым основаниям:

| Ось | Что задаёт | Примеры в Артели | Примеры в целевом проекте | Чем срабатывает |
|---|---|---|---|---|
| **Место: логический модуль (домен)** | инварианты предметной логики | FSM задачи (`fsm*.py`, `advance_gates/`), учёт расхода (`spend.py`, `budget.py`), канарейка (`canary*.py`) | pricing, forecasting, биллинг | пути diff ∩ пути модуля |
| **Место: технический слой** | правила технологии | БД (`store.py`, `schema.py`), git-обвязка (`gitcmd.py`, `artifact_branch.py`), CI (`.github/`, `scripts/ci_*`), провайдеры LLM (`providers/`), UI (`report.py`) | миграции БД, Terraform/k8s, публичный API, фронтенд | пути diff ∩ пути слоя, расширения файлов |
| **Свойство (сквозная ось)** | атрибут качества, который обязан держаться в любом коде | безопасность (недоверенный текст агентов, argv в git, секреты провайдеров), конкурентность (lease, параллельные сессии), стоимость (токены входа), целостность (неослабление гейтов) | безопасность, производительность, надёжность, наблюдаемость | признаки в добавленных строках diff (`subprocess`, `shell=True`, `open(` на пути из артефакта, `sqlite3.connect`, `threading`) |
| **Вид изменения** | особый режим проверки самого изменения | рефакторинг (правила T015), правка теста/планки, правка скила или шаблона, миграция схемы | миграция данных, смена контракта API, новая зависимость, удаление функциональности | флаг во frontmatter SPEC (проверяемый `guard`) + детерминированные признаки diff |

Одно и то же предметное «БД» проецируется на все четыре оси:
`store.py` — слой; «целостность данных при параллельной записи» —
свойство; «миграция схемы» — вид изменения; «учёт расхода хранится
так-то» — инвариант модуля. Поэтому спор «БД — это домен или нет» не
имеет ответа: это вопрос о триггере, а не о сущности. Единица, с которой
работает агент, одна — линза; оси нужны только чтобы понять, ОТКУДА
берётся её триггер.

Пятая ось ортогональна первым четырём — **метод проверки**:

| Метод | Что умеет | Цена | Ошибки |
|---|---|---|---|
| Детерминированный (линтер, гейт, правило импорта, SAST-шаблон, линтер миграций) | факт формы: путь вне зон, запрещённый импорт, `CREATE INDEX` без `CONCURRENTLY` | ≈0 на прогон, разовая цена правила | ложные срабатывания по шаблону, не видит смысла |
| Исполнением (тесты, временная мутация, прогон планки, смоук) | факт поведения | секунды–минуты | только то, на что есть вход |
| Суждением модели | смысл: соответствие SPEC, сценарий эксплуатации, нарушение инварианта домена, лишняя сложность | доллары на прогон | пропуски при длинном контексте, ритуальные «проверено» |

Главное правило распределения: **суждение модели — только там, где нет
детерминированного или исполняемого метода**. Каждая проверка, которую
можно закодировать, переезжает в гейт по лестнице отчуждения
(`docs/operator-session.md`), а линза ревьювера сужается до остатка.

## 2. Что сейчас: факты по пульту

### 2.1. Устройство

- Ревьювер получает один скил `skills/review-checklist.md` (233 строки)
  целиком на каждой задаче, плюс ревью-пакет (`orchestrator/review.py`):
  SPEC, PLAN, прошлый REVIEW, diff. Механизма условной подгрузки знаний
  нет: состав скилов роли статичен (`roles.yaml`).
- Внутри чек-листа уже есть одна линза по виду изменения — «Задача
  класса рефакторинг (правила T015)», включается текстом SPEC, но
  решает это сам агент, читая условие, а не код.
- Пункт 5 «Безопасность» — одна строка. Его часть «файлы вне зоны
  задачи, `ci/`, `.github/`, `gates.yaml` → blocker» уже закрыта кодом:
  гейт зон (`orchestrator/advance_gates/zones.py`) и джоб
  `protected-paths` (`scripts/ci_protected_paths.py`). Ревьювер дублирует
  детерминированную проверку суждением.
- `skills/ui-standards.md` (слой UI) существует с T096, но не подключён
  ни одной роли: в `roles.yaml` его нет, в коде сборки промпта ссылок
  нет. Это линза без триггера — знание, которое агент не получает
  (см. §7, наблюдения).

### 2.2. Чем ревью фактически находит дефекты

Замер по реестрам замечаний (`tasks/*/REVIEW*.md`, schema ≥ 3): 251
запись в 111 файлах REVIEW. Классификация грубая — по ключевым словам,
первое совпадение, поэтому категория «тесты» завышена за счёт строк,
упоминающих тест в последствии; порядок величин она передаёт.

| Категория | Записей |
|---|---|
| тесты: заявка «Ловит мутацию», докстринг | 123 |
| тесты: сторож, планка, утверждения | 58 |
| соответствие SPEC / AC | 23 |
| тексты, журнал, документы | 16 |
| git, ветки, CI | 9 |
| данные, БД, схема | 3 |
| конкурентность, lease | 1 |
| безопасность | 0 |
| прочее | 18 |

По путям: `tests/` — 72 записи, `tasks/` — 22, `scripts/` — 13,
`orchestrator/doctor/` — 12, `docs/` — 12; дальше модули по 2–8.

Безопасность в 37 из 306 файлов REVIEW упоминается, но почти всегда как
аттестация отсутствия («секретов нет, недоверенного ввода нет»).
Единственная содержательная находка — R1-F1 задачи о границах
недоверенных данных в брифах (подделка заголовка части в недоверенном
компоненте), и задача сама была про безопасность.

Выводы из замера:

1. Сегодняшний ревьювер — по сути линза «качество тестов» плюс
   соответствие SPEC. Это совпадает с внешними данными: ревью находит
   преимущественно дефекты сопровождаемости, функциональные — меньшинство
   (Mäntylä, Lassenius 2009: 77% против 23%).
2. Пункт чек-листа, который действует на каждой задаче, но не
   срабатывает, вырождается в ритуальную аттестацию. Для агента это
   прямой расход внимания: строка «секретов нет» — вывод без проверки,
   та самая форма «всё зелёное», против которой написан контракт сессии.
3. Пульт — внутренний инструмент с узкой поверхностью атаки; на целевом
   проекте с HTTP-API, БД и инфраструктурой распределение будет другим.
   Линзы нужны прежде всего для целевых проектов и для редких, но дорогих
   видов изменений пульта (схема БД, гейты, git-обвязка, брифы).

## 3. Внешние практики

1. **Узкий отдельный проход с жёсткой постановкой** — Anthropic
   `claude-code-security-review` (открытый код, промпт
   `claudecode/prompts.py`, фильтр `claudecode/findings_filter.py`):
   - только изменения PR, «существующие проблемы не комментировать»;
   - явный список того, что НЕ репортить (DoS, rate limiting, утечки
     ресурсов, память вне C/C++, open redirect…), продублированный
     регулярными «жёсткими исключениями» в коде после прохода модели;
   - обязательное поле `exploit_scenario` и порог уверенности 0.8;
     затем второй проход модели — фильтр ложных срабатываний;
   - методика из трёх фаз: изучить принятые в репозитории паттерны →
     сравнить изменение с ними → проследить поток данных до опасной
     операции;
   - структурированный вывод (JSON: файл, строка, категория, сценарий,
     рекомендация);
   - расширение под проект — файлами добавочных категорий и добавочных
     правил фильтра, а не правкой базового промпта.
2. **Инструкции по путям** — CodeRabbit `path_instructions`: инструкции
   ревью привязаны к glob-маскам путей (аутентификация, Terraform, тесты).
   Это ровно линзы «место» с путевым триггером.
3. **Детерминированный кандидат + суждение модели** — связки SAST
   (Semgrep, CodeQL) с LLM-триажем: сканер находит кандидатов, модель
   отсеивает ложные. Публикуемые результаты — кратное снижение ложных
   срабатываний (SAST-Genius: 225 → 20 на их наборе); обратная связь
   статических анализаторов улучшает точность модели.
4. **Линтеры слоя** — для БД: Squawk, strong_migrations (опасные
   миграции: блокировки таблиц, индекс без `CONCURRENTLY`, `NOT NULL`
   с дефолтом); для архитектуры модулей: ArchUnit, Import Linter
   (контракты слоёв и границ импорта как тесты, «фитнес-функции»).
   Это детерминированные половины линз «слой» и «домен».
5. **Специализация повышает охват** — работы по многоагентной проверке
   кода (CodeX-Verify, 2025) показывают, что специализированные
   проверяющие с низкой корреляцией находок дополняют друг друга, прирост
   от каждого следующего убывает. Оговорка: источник читался по
   аннотации, состав агентов и набор данных не сверялись.
6. **Деградация следования инструкциям** — с ростом числа одновременных
   инструкций и длины контекста доля выполненных проверок падает: в
   работе о стойкости скилов (arXiv 2603.12123) набор из 24 проверок
   артефакта выполнялся в 8 прогонах из 10 в чистом контексте ~11 тыс.
   символов и в 3 из 10 в релевантном контексте ~300 тыс. символов;
   плюс известный эффект «потери в середине». Оговорка: цифры взяты из
   аннотации, полный текст недоступен из сессии.
7. **Что ищет ревью вообще** — Google eng-practices: дизайн,
   функциональность, сложность (включая переусложнение), тесты, имена,
   комментарии, стиль, документация. Это ядро, общее для любой задачи;
   всё сверх него — условное.

Общий знаменатель: (а) базовое ядро + условные добавки по путям или
признакам; (б) детерминированное — коду, модели — суждение над
кандидатами; (в) узкая постановка с явным «не репортить» и обязательным
обоснованием находки; (г) расширение под проект — аддитивными файлами.

## 4. Анализ со стороны агента

Что мешает агенту-ревьюверу сейчас:

- **Длина и безусловность чек-листа.** 233 строки на каждую задачу,
  вместе с SPEC, PLAN и diff. По п. 3.6 каждая неактуальная проверка не
  нейтральна — она снижает вероятность выполнения актуальных.
- **Условия, которые агент вычисляет сам.** «Если ТЗ называет задачу
  рефакторингом…», «если REVIEW несёт schema_version ≥ 3…» — агент
  тратит рассуждение на маршрутизацию, которую код делает без ошибок, и
  может ошибиться в ней молча.
- **Проверки без входа.** «Безопасность» без модели угроз проекта и без
  указания, где в diff опасные операции, — агент вынужден либо искать по
  всему diff, либо отписаться аттестацией.
- **Дубль детерминированного.** «Файлы вне зоны → blocker» уже проверяет
  гейт; агент повторяет работу и может разойтись с гейтом.

Что агенту удобно (по убыванию пользы):

1. **Только применимые линзы в контексте**, выбранные кодом, с
   объяснением, ПОЧЕМУ линза включена: «сработали пути
   `orchestrator/store.py`; признак `ALTER TABLE` в строке 1283».
2. **Якоря**: конкретные строки diff, на которых сработал признак, —
   готовые кандидаты вместо поиска иголки во всём diff (тот же приём,
   что SAST → LLM-триаж).
3. **Модель угроз / инварианты линзы** в 5–15 строках: что именно
   ломается в этом слое у этого проекта. Без неё узкая линза
   превращается в общий список OWASP.
4. **Явный список «не репортить»**: отсекает класс шумовых находок до
   того, как агент на них потратится.
5. **Обязательное обоснование находки в форме сценария поломки**
   (вход → путь → наблюдаемый вред). Это сильнее числового порога
   уверенности: самооценка уверенности моделью плохо откалибрована, а
   сценарий проверяем — ревьювер следующей итерации или разработчик
   может его воспроизвести.
6. **Отсутствие требования аттестации.** Линза не включена — агент о
   ней не пишет. Нет строки «секретов нет» — нет ритуала.
7. **Свежий контекст для тяжёлых линз.** Когда линза требует трассировки
   потока данных или чтения кода вне diff, отдельный проход с коротким
   пакетом выполняется надёжнее, чем раздел в конце длинного общего
   прогона.

Граница «раздел общего прогона против отдельного прохода»:

| Признак | Раздел в общем прогоне | Отдельный проход |
|---|---|---|
| Объём текста линзы | ≤ ~40 строк | больше |
| Нужно читать код вне diff | нет | да (трассировка, сравнение с паттернами репозитория) |
| Корреляция с находками ядра | высокая (тесты, SPEC) | низкая (безопасность, миграции) |
| Цена пропуска | обычная | необратимая (схема БД, секреты, гейты) |
| Частота срабатывания | частая | редкая — отдельный проход дёшев в среднем |

## 5. Предлагаемая форма: линза ревью

### 5.1. Пакет линзы

Один файл на линзу, одинаковая форма для всех четырёх осей. Набросок:

```yaml
# skills/review-lenses/db-schema.md (frontmatter)
lens: db-schema
axis: layer                 # module | layer | property | change
triggers:
  paths: [orchestrator/store.py, orchestrator/schema.py]
  added_lines: ['ALTER TABLE', 'CREATE TABLE', 'add_column\(']
  spec_flag: schema_change  # поле frontmatter SPEC, проверяет guard
participation: inline       # inline | separate | gate
deterministic: []           # имена гейтов/линтеров, которые линза дополняет
```

Тело — четыре обязательных раздела, каждый короткий:

- **Инварианты / модель угроз** — что ломается в этом слое у этого
  проекта (для `db-schema` пульта: миграция идемпотентна на свежей и
  старой БД, без гонки «есть колонка / ALTER», откат описан).
- **Что проверить** — 3–7 пунктов, каждый проверяем по якорю.
- **Не репортить** — классы находок, которые здесь шум.
- **Форма находки** — сценарий поломки обязателен; запись реестра несёт
  поле `lens`.

### 5.2. Механика

1. Пульт при сборке ревью-пакета (`review.review_package`) вычисляет
   активные линзы детерминированно: пути diff, регулярные признаки по
   ДОБАВЛЕННЫМ строкам, флаги SPEC. Семантических триггеров
   («изменение бизнес-правила») нет — их выбор моделью уже отвергнут
   ревью от 26.09 и противоречит детерминированному конвейеру.
2. В пакет добавляется раздел «Активные линзы»: имя, причина включения,
   якоря (файл:строка), текст линзы. Неактивные не попадают в контекст.
3. `participation`:
   - `inline` — раздел пакета общего прогона ревьювера (по умолчанию);
   - `separate` — отдельный прогон той же роли `reviewer` с коротким
     пакетом (линза + diff по путям линзы + якоря), вердикт пишется в
     тот же REVIEW.md отдельным блоком реестра; лимит итераций общий;
   - `gate` — блокирующая находка линзы не может быть снята вердиктом
     общего прогона.
4. Реестр замечаний получает поле `lens` (у находок ядра — `core`). Это
   даёт замер полезности каждой линзы: находок на прогон, доля принятых.
   Линза, которая 20 прогонов подряд ничего не находит, — кандидат на
   сужение триггера; линза с повторяющейся формой находки — кандидат на
   детерминированное правило (лестница отчуждения).
5. Проектный слой целевого проекта (`projects/<target>/knowledge/`,
   после ТЗ-4) добавляет свои линзы аддитивно, той же формой: модули
   предметной области, свои слои (Terraform, публичный API), свои
   свойства. Пульт не переписывает и не порождает линзы сам.

### 5.3. Связь с доменными архитекторами

Доменный архитектор из исследования 22.09 — та же линза оси «модуль»,
у которой `participation` распространяется на фазу проектирования
(`arch_design` до `tests_writing`), а не только на ревью. Пакет домена
(инварианты, граница, ловушки, точки входа, проверка — §3 итога 27.09)
и пакет линзы совпадают по составу; один файл может служить обоим
шагам. Отдельной сущности «архитектор» для ревью не требуется.

### 5.4. Ядро чек-листа

После выноса линз в `review-checklist.md` остаётся то, что применимо к
любой задаче: Фаза A (план), соответствие SPEC, корректность,
простота, тесты (это фактически самая результативная линза и она
безусловна — каждая задача меняет `tests/`), системная целостность в
части суждения. Выносятся: безопасность (→ `property/security`),
рефакторинг (→ `change/refactor`, триггер — флаг SPEC вместо чтения
агентом текста ТЗ), реестр замечаний по версии схемы (→ код сборки
пакета решает, давать ли раздел). Детерминированная половина п. 5 и
п. 6 (пути вне зон, защищённые пути) из текста убирается — её держат
гейты; ревьювер получает их результат в пакете как факт.

### 5.5. Стартовый набор линз для пульта

Только там, где есть путь или признак и реальная цена пропуска:

| Линза | Ось | Триггер | Участие |
|---|---|---|---|
| `change/refactor` | вид изменения | флаг SPEC | inline |
| `layer/db-schema` | слой | `store.py`, `schema.py`; `ALTER/CREATE TABLE` в добавленных строках | inline |
| `layer/git` | слой | `gitcmd.py`, `artifact_branch.py`, `workspace.py`; новые вызовы `git` | inline |
| `property/untrusted-text` | свойство | `brief.py`, `role_prompt.py`, `review.py`, `context_package.py`; вставка текста артефактов/логов в промпт | separate |
| `module/fsm-gates` | модуль | `fsm*.py`, `advance_gates/`, `gates.yaml` | gate |
| `layer/ui` | слой | `report.py`, `*.html` | inline (это `ui-standards.md`, наконец подключённый) |

Свойство «безопасность» целиком для пульта не выделяется: поверхность
атаки пульта — это ровно «недоверенный текст в промптах» и «argv в
git/subprocess», и они покрыты двумя узкими линзами выше. Для целевых
проектов с сетевой поверхностью — полная линза безопасности по образцу
§3.1.

## 6. Стоимость и порядок

- Линза `inline` добавляет к входу ревьювера 1–3 тыс. токенов только на
  задачах, где сработала; вынос безусловных разделов из ядра уменьшает
  вход на всех остальных. Нетто на типичной задаче пульта — снижение
  входа.
- Линза `separate` — отдельный прогон с пакетом в разы меньше общего;
  включается редко по построению триггера.
- Порядок, при котором каждый шаг даёт замер для следующего:
  1. поле `lens` в реестре замечаний и в `guard` — замер с первого дня
     (пока все находки `core`);
  2. механизм активных линз в `review.review_package` + перенос
     `change/refactor` и `layer/ui` (два прецедента, оба уже написаны
     текстом);
  3. стартовые `inline`-линзы слоёв пульта;
  4. `separate` и `gate` — по замеру: когда у линзы находки есть, но
     пропуски видны в ретро (находка позже ревью — CI, мерж, канарейка);
  5. проектные линзы целевого — после ТЗ-4.

## 7. Чего не делать

- Отдельные роли под каждую ось (security-reviewer, db-reviewer…)
  заранее: роль — это стоимость прогона и FSM-состояние; линза —
  раздел пакета. Отдельный проход — режим линзы, а не новая роль.
- Выбор линз моделью по смыслу задачи: недетерминировано, не
  проверяется гейтом, ошибается молча.
- Числовой порог уверенности как единственный фильтр — сценарий
  поломки проверяем, самооценка уверенности нет.
- Требование аттестации по каждой оси («безопасность: ок») — порождает
  ритуальные строки, не находки.
- Автоматическое порождение или переписывание линз пультом по истории:
  пульт предлагает (раздел report/doctor по замеру поля `lens`), правит
  Оператор.

## 8. Наблюдения (аномалии), найденные по ходу

1. `skills/ui-standards.md` не подключён ни одной роли: нет в
   `roles.yaml`, нет ссылок в коде сборки промпта. Разработчик UI-задачи
   его не получает — скил мёртв с T096. Строку в копилку
   `docs/backlog.md` нужно внести командой `note` из главной копии
   (сессия работает в облаке на ветке, прямой коммит в main закрыт
   хуками).
2. Пункт 5 `review-checklist.md` дублирует суждением гейт зон и джоб
   `protected-paths`; расхождение ревьювера с гейтом не отслеживается.
3. Пункт «Безопасность» на задачах пульта за весь корпус дал одну
   содержательную находку и десятки строк-аттестаций — пример проверки,
   которая расходует внимание агента без отдачи.
