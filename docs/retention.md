# Retention-политика

Что и как долго живёт в системе, по видам данных (refs/artifacts/T073:tasks/T073/SPEC.md,
требование 1; roadmap P3 «Retention-политика», $25). Реализует политику
команда `prune` (`orchestrator/prune.py`) для видов, где хранение не
привязано к переходу FSM одной задачи, и сам оркестратор — для видов,
где привязано (ветка/worktree на `done`).

## `.artel/logs/` — логи прогонов агентов

Лимит двойной, `prune` исполняет ОБА разом (AND, не OR): файл лога
удаляется, только если он ОДНОВРЕМЕННО

- старше **90 дней** (`config.LOG_RETENTION_DAYS`) по mtime, **И**
- его задача — вне **N=20 последних ЗАКРЫТЫХ задач** по ДАТЕ ЗАКРЫТИЯ
  из журнала (`config.LOG_RETENTION_KEEP_TASKS`, значение — решение
  Оператора 29.08, refs/artifacts/T073:tasks/T073/TZ.md, «Ответы Оператора»; правка —
  только Оператор, ADR-0002, класс «лимит»; отбор по дате закрытия, не
  по числовому номеру задачи — SPEC T094, требование 5: ULID-id
  сравнимого по величине номера не несёт, а `Tnnn`-задачи участвуют в
  этом же датовом отборе, не в отдельном отборе «последние N по
  номеру»). Ещё не закрытая задача в датовый отбор не попадает вовсе —
  её логи retention не трогает независимо от возраста.

Свежий лог не удаляется никогда, даже у древней задачи; лог задачи из
последних 20 закрытых не удаляется никогда, даже если ему сто лет.
Исполняет — `prune --execute` (без флага — dry-run, план без удаления).

То же двойное правило (SPEC 01M5KBQGMZ051ENRVS8F42MA4V) действует для:

- **промптов шагов** `<id>-<роль>-<n>.prompt.txt` верхнего уровня
  `.artel/logs/` — давность по mtime файла, задача — часть имени до
  первого `-`. Прочие файлы верхнего уровня (`*-state.db*` и т. п.) не
  убираются;
- **каталогов хозяйства `suite-run`** `.artel/logs/suite-run/<id>/` —
  каталог удаляется целиком; давность — по самому свежему файлу внутри
  (рекурсивно), у пустого каталога — по mtime самого каталога. Не
  убираются никогда: `lock.json` (замок прогонов), `pending-journal/`
  (отложенные записи журнала), подкаталог с именем не формы id задачи,
  подкаталог — символическая ссылка, каталог задачи, держащей замок
  (`suite_lock.holder()`), и каталог, в чьём `run.json` — pid живого
  процесса.

## Каталоги упразднённых механизмов

Рабочие каталоги механизмов, которых в коде пульта больше нет
(`prune.ABOLISHED_DIRS`; сейчас — `.artel/notes-work`, рабочий
репозиторий упразднённой команды `note`), удаляются целиком командой
`prune --execute` без условия давности (SPEC 01M5KBQGMZ051ENRVS8F42MA4V).
Удаление необратимо, поэтому каталог удаляется, только если он — корень
собственного репозитория git без несохранённой работы: нет
незакоммиченных правок, неотслеживаемых и игнорируемых файлов, коммитов
вне `refs/remotes/origin/*`, записей stash, HEAD — на ветке. Проверка
только локальная, без обращения к сети. Иначе каталог остаётся, а отчёт
печатает строку «оставлено: <причина>». Символическая ссылка на этом
месте не трогается — ни она, ни её цель.

## Сессии ролей (`.artel/home/.claude/projects`)

Протоколы сессий агентов ролей пишет CLI роли в курируемый HOME
(`.artel/home/.claude/projects`), по каталогу на рабочую копию задачи.
Объём на 06.10.2026 — 2,1 ГБ (2653 записи в 311 каталогах с конца
августа), рост — ~100–150 МБ в день работы конвейера (`docs/backlog.md`,
строка «Уборка протоколов сессий агентов ролей»). Политики хранения для них пока
нет: `prune` их не трогает, уборка — отдельная строка бэклога «Уборка
протоколов сессий агентов ролей».

## Ветки `task/*` пульта

Ветка задачи удаляется оркестратором при переходе в `done` — сразу
после уборки worktree (`git branch -d`, безопасное удаление: git
откажет сам, если ветка внезапно не влита). Тем же правом, каким
оркестратор уже убирает ветку/worktree при `kill` (T008/T045). Merge в
main остаётся **без squash** (`git merge --no-ff`) — история мержа
задачи в main полная и не теряется удалением самой ветки-указателя.

После мержа ветка задачи удаляется и в `origin` проекта (у артели и у
внешнего проекта; SPEC 01M5FGJW4RBN9C9P48Q8MDHJX1) при условии, что её
голова в `origin` входит в смерженный main; удаление условно по
прочитанной голове (`--force-with-lease`). Сбой удаления (отказ или
молчание хостинга, голова вне смерженного main) оставляет ветку и
пишется в журнал записью «уборка» с причиной; мерж он не отменяет, а
после исхода печатается подсказка ручной команды. Удаление head-ветки
на GitHub закрывает открытый PR; после мержа push в базу обычно уже
помечает PR смерженным, конечный статус PR сверяется на первом мерже
после внедрения.

Удаление ветки в `origin` идёт пушем из клона проекта и снимает ссылку
отслеживания только в клоне. Ссылки отслеживания `origin` главной копии
(корня пульта), ветки которых в `origin` больше нет, снимает
`pin-update` — `git remote prune origin` последним действием после
успешного сдвига пина (SPEC 01M5M675F6K2TE7TTJN3AET4PP): git главной
копии меняет только `pin-update` (инвариант 40), не мерж и не `prune`.
Отказ `pin-update` уборку не вызывает; сбой уборки — строка
предупреждения, сдвиг пина и код выхода он не меняет.

## `.artel/canary/` — диагностика незелёного прогона канарейки

Файл диагностики (SPEC 01M1TKP269W9JN3NBJCR5Q6C3B, требование 4) убирается,
только если он старше **90 дней** (`config.LOG_RETENTION_DAYS`) по mtime
— тот же порог давности, что и у `.artel/logs/` выше, но БЕЗ второго
условия («последние N закрытых задач»): `task_id` в пути диагностики
(`.artel/canary/<run_stamp>/<task_id>/`) — id уже уничтоженного
эфемерного клона канарейки, не задачи пульта, и в датовый отбор
`.artel/logs/` не участвует. Исполняет — `prune --execute` (без флага —
dry-run, план без удаления), тем же вызовом, что и остальную политику
этой страницы.

## Alerts

Alerts (любой `kind`, вне зависимости от `ack`) старше **90 дней**
(`config.ALERT_ARCHIVE_DAYS`) не удаляются — `prune --execute`
переносит их в архивную таблицу `alerts_archive` (та же схема, с
`archived_ts` момента переноса). Запись покидает `alerts` и появляется
в архиве с тем же `id` — перенос, не дублирование и не потеря.

## Worktree задачи (`.artel/worktrees/<id>`)

Убирается оркестратором при переходе задачи в `done` (уже было,
T045) и в `killed` (уже было, T008) — тем же правом уборки хвостов
задачи — немедленно, не по расписанию.

`.artel/worktrees/` — прежнее место рабочих копий задач (`config.
WORKTREES`); сейчас рабочие копии живут в `.artel/projects/<проект>/
worktrees/`. Бесхозные каталоги прежнего места убирает `prune --execute`
(без флага — план) (SPEC 01M5M675F6K2TE7TTJN3AET4PP). Бесхозный — каталог
(не символическая ссылка), чьё имя не id незакрытой задачи (имя задачи
`done`/`killed` защиты не даёт) и чей путь не зарегистрирован ни в `git
worktree list` главной копии, ни в `git worktree list` клона артели.
Удаляется каталог целиком, без перехода по ссылкам и без проверки
несохранённой работы; бесхозный каталог с `.git` (файл или каталог) не
удаляется — строка «оставлен — есть .git». Не получен хотя бы один из
двух перечней — вид пропускается целиком, строкой «пропущено».

## Report-страница (П2′, когда появится)

Перегенерируется на месте при каждом обновлении — истории отчётов
(прежних версий страницы) система не хранит.

## Журнал БД и артефакты гейтов

Вечны. Retention их не касается никогда — ни `prune`, ни любая другая
уборка. Журнал шагов (`steps`) — источник истины прошлого поведения
системы (docs/design.md §7); артефакты гейтов смерженных задач
(SPEC/PLAN/REVIEW) — история проекта (ADR-0005 п.1, уровень `full`).
Они хранятся в ссылках документов `refs/artifacts/<id>` на origin, не в
main (ADR-0018, ADR-0021 этап 4); ретроспективы задач, смерженных до
этапа 4, — ещё и в `docs/retro/` main. Ни ссылки, ни `docs/retro/`
retention не удаляет.

## Инвариант 16 и `prune`

`prune` — не часть уборки задачи (`kill`/`done`) и не срабатывает на
переходе FSM ни одной задачи: явная, отдельно вызываемая Оператором
команда над `.artel/logs/`/`alerts` в целом, по собственной политике
выше, с отчётом о сделанном. Инвариант 16 («История наблюдаемости
переживает задачу: `.artel/logs/` уборка не трогает») запрещает
КОСВЕННОЕ стирание логов как побочный эффект закрытия/убийства одной
конкретной задачи — этому `prune` не противоречит: у логов есть
собственная, отдельно объявленная политика хранения (эта страница), и
её исполняет только явная операторская команда. Полный текст уточнения
инварианта 16 (для ADR, который вправе принять только Оператор) —
`refs/artifacts/T073:tasks/T073/PLAN.md`, раздел «Подход», п.5.
