# Порядок действий при инциденте внешнего проекта

Основание — ADR-0029 п. 14. Инцидент внешнего проекта — всё, после чего
пульту нельзя продолжать работу с проектом как обычно: утечка или
подозрение на утечку токена проекта, MR с чужим или неожиданным
содержимым, отправка не в ту ветку, действие роли за пределами задачи.

Документ описывает порядок, а не конкретный проект: имена проектов,
адреса репозиториев, слоты токенов и сами токены сюда не пишутся. Ниже
`<проект>` — имя записи проекта в `targets.yaml` (локальный слой
`.artel/targets.yaml`), `<id>` — идентификатор задачи.

Действия выполняются по порядку: сначала прекращается возможность
навредить (1–2), затем сохраняются следы (3–4). Следы не теряются от
остановки — журнал и MR остаются на месте, — а действия с живым токеном
продолжаются, пока его не отозвали.

## 1. Остановка задач проекта

Цель — ни один цикл пульта не делает новых шагов, отправок и мержей по
проекту.

1. Перечень задач проекта — `artel.py status` (колонка проекта) или доска
   `artel.py board`.
2. Каждую живую задачу проекта — `artel.py pause --now <id>`: идущий шаг
   обрывается с чекпоинтом рабочей копии, новые шаги не стартуют. Для
   задачи без идущего шага достаточно `artel.py pause <id>`.
3. Циклы `auto`/`run`, запущенные вне пульта (фоновые сессии), — снять
   процесс; `artel.py doctor` покажет оставшиеся циклы и lease.
4. Задачу, которую продолжать нельзя вовсе, — `artel.py kill <id>` только
   после срезов (разделы 3–4): уборка kill удаляет ветку задачи.

Новые задачи проекта до разбора не заводятся.


## 2. Отзыв токена

Цель — токен проекта, которым пульт ходит в хостинг, больше ничего не
может.

1. Отозвать (revoke) токен в настройках хостинга проекта — у владельца
   токена; удалить его мало, если он мог быть скопирован.
2. Удалить значение из keychain пульта по слоту записи проекта
   (`token_slot` в записи `<проект>`), чтобы пульт не пробовал старый
   токен.
3. Проверить, что пульт токена больше не видит: `artel.py doctor`
   показывает проверку токена проекта не зелёной.
4. Если токен мог попасть в журнал, лог шага или артефакт — отметить это
   в разборе (шаг 3) с адресом файла, не копируя сам токен.

Новый токен выпускается только после разбора, с минимальными правами,
которые требует ADR-0029.

## 3. Срез журнала задачи

Цель — зафиксировать, что пульт и роли делали по задаче, до того как
уборка или ротация логов что-то сотрёт.

1. Журнал шагов каждой задачи проекта — `artel.py log <id>`; вывод
   сохранить в файл разбора инцидента.
2. Карточка задачи — `artel.py show <id>`: состояние, ветка, траты.
3. Логи прогонов шагов роли — каталог логов проекта
   (`.artel/projects/<проект>/logs/`); последний лог шага называет
   `artel.py show <id>`.
4. Документы задачи — `artel.py docs <id>`: SPEC, PLAN, REVIEW и записки
   шагов из ссылки документов `refs/artifacts/<id>`.

Срез — копия, а не перенос: исходные журнал, логи и документы не правятся
и не удаляются до конца разбора.

## 4. Ссылка на MR

Цель — разбор опирается на то, что действительно ушло в хостинг проекта.

1. Ссылка на MR задачи — в журнале задачи (запись открытия MR) и в
   карточке `artel.py show <id>`; её записывают в разбор вместе со срезом
   журнала.
2. MR не сливать. Если MR открыт и его содержимое под вопросом — перевести
   в черновик или закрыть руками в хостинге, не удаляя: история коммитов
   и обсуждений MR — часть следов.
3. Сверить головной коммит MR с головой ветки задачи в рабочей копии
   пульта: расхождение — признак отправки мимо пульта.
4. Людей проекта, ведущих гейт мержа (`merge_gate: target-human`),
   предупредить по их каналу, что MR задачи не принимается до конца
   разбора.

## После разбора

Решение о продолжении работы с проектом принимает Оператор: снятие паузы
задач (`artel.py resume <id>`), новый токен, при необходимости — строка в
`docs/backlog.md` о механике, которая инцидент допустила.
