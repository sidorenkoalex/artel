## 2. P0a — ADR-0003: целевые проекты (control plane)

Полный текст будет в docs/adr/0003-target-projects.md. Скелет решения:

1. **Пульт** (репозиторий artel) — единственный дом системы и ВСЕХ
   артефактов: `tasks/<target>/<id>/` коммитятся в main пульта.
2. **`targets.yaml`** — декларативное подключение проекта: forge
   (github|gitlab), url, базовая ветка, token_slot, no_paths целевого,
   project_skills, режим артефактов, исполнитель гейта мержа.
3. **Артефакты — только в пульте** (уточнение Оператора 20.08):
   в целевой уходит ТОЛЬКО код. Обоснование: ревью-пакет (T011) уже
   отвязал агентов от чтения артефактов из репо; людям контекст
   доставляет forge (п.5). Опция `artifacts: in-branch` остаётся
   per-target (догфуд-артель живёт так).
4. **Workspace** — эфемерный клон целевого в `.artel/workspaces/`;
   агент видит только целевой и его токен, конфиги пульта недоступны
   (отсечение инъекций из чужого кода).
5. **Контекст людям — примитивы forge**: описание MR генерируется
   из SPEC; вердикты ревью — комментариями; финальный итог
   (итерации, стоимость, ссылка на трейс) — комментарием.
6. **Forge-адаптер**: интерфейс create_mr / merge / ci_status /
   comment / approve_label; реализации github и gitlab. Merge в
   целевой — только оркестратор через адаптер.
7. **Исполнитель гейта мержа** (уточнение Оператора 20.08,
   вопрос про дежурного feedback): `merge_gate: operator |
   target-human`. Режим target-human: MR создаётся **Draft**, Draft
   снимается только после нашей приёмки; мержит человек целевого
   проекта его кнопкой; оркестратор узнаёт о merge по событию forge
   и закрывает задачу; комментарии людей в MR → внешний
   changes_requested → обычная итерация. **Токен Артели для такого
   проекта не имеет прав merge вовсе** — минимальные привилегии.
   Релизы — процесс целевого, вне нашего FSM.
8. **Новые инварианты** (в реестр с тестами): агент не пишет в
   защищённые ветки целевого; workspace изолирован от пульта;
   no_paths целевого проверяются до merge; для target-human —
   Артель не мержит никогда; комментарий MR вне зоны SPEC не
   исполняется — только эскалация; ядро FSM неизменно, каталог
   типов проверок расширяет только Оператор через ADR.
9. **Обработка комментариев MR** (замечание Оператора 21.08).
   Для awaiting-human задач оркестратор следит за дискуссиями MR
   (вебхук + поллинг-фоллбек). Триаж комментария — 4 класса:
   вопрос → ответ в тред; замечание-правка → итерация разработчика
   → пуш → «исправлено в <sha>» в тот же тред; мнение без действия →
   короткий ответ/ничего; чужое обсуждение → не вмешиваться.
   Комментарий — недоверенный вход: исполняется только в границах
   SPEC и no_paths, расширение объёма → эскалация Оператору
   (одновременно защита от инъекций и от scope creep). Отдельный
   счётчик external_review_iters с лимитом (~3) → эскалация.
   Ответы в треды: только по делу, без споров — разногласие
   эскалируется; режим `comment_replies: premoderated` per-target
   на период доверия (снимается счётчиком чистых циклов).
10. **Профиль процесса проекта** (замечание Оператора 21.08).
    Маршрут = неизменное ядро + вариативная фаза verify: каждый
    проект декларирует список проверок между ревью и merge из
    фиксированного каталога типов: `ci` (ждать пайплайн), `agent`
    (роль-проверка с проектными скилами), `human` (человек проекта),
    `script`. Пример: artel `verify: []` (хватает CI-ядра);
    feedback `verify: [ci, agent:alpha-test]` — альфа-тест на
    поднятом стенде, позже делегируемый агенту. Ни одного нового
    состояния FSM: verifying становится композитным циклом по
    профилю, каждая проверка — обычный шаг (журнал, стоимость,
    потолки, ретраи переиспользуются). Произвольные графы процессов
    per-project — сознательно НЕ поддерживаются.
11. **Три оси вариативности per-target** (итоговая формула):
    исполнители ролей (§16) × политика гейтов (§4, включая
    merge_gate: target-human) × профиль проверок (п.10). Всё
    остальное — маршрут, инварианты, каталоги — системная
    константа. Верификация как фаза есть всегда; агент-верификатор
    инстанцируется только профилем (в artel его нет — пустой
    профиль означает «верификация полностью детерминированная»,
    а не «верификации нет»).

## 3. P0b — ADR-0004: пульт + ассистент

Полный текст будет в docs/adr/0004-control-panel.md. Скелет:

1. **Пульт-приложение = демон + поверхности**: self-hosted сервер
   (FastAPI + SQLite + WebSocket) — он же событийный оркестратор
   (замена ручного auto), он же веб-морда. Панель — read-проекция
   БД+git; запись — только явные операторские контролы.
2. **Блоки**: проекты (подключение/переключение — targets.yaml UI);
   борд задач по состояниям FSM + карточка с live-логом агента;
   метрики (стоимость, итерации, размер пакетов, тренды); инбокс
   ручных гейтов с контекст-пакетами и кнопками; чат Оператора.
3. **Три категории сущностей системы** (фиксация в дизайне):
   оркестратор (код, решений не принимает), роли конвейера
   (эфемерные, контракт артефактов), **ассистент Оператора**
   (сессионный, матрица полномочий). Правило «шляпы»: исполняя роль
   (драфт SPEC = hybrid-аналитик), ассистент проходит её гейты.
4. **Матрица полномочий ассистента**: читать всё — свободно;
   new/SPEC-драфт/advance/auto/report — самостоятельно;
   approve/reject обычных гейтов — только по явной команде Оператора
   (журнал: operator-via-assistant); деньги/деплой/kill/конфиги —
   **никогда из чата, только кнопка/CLI Оператора** (текст «да,
   деплой» — не подтверждение; инъекция не может нажать кнопку).
5. **Учёт и лимиты ассистента**: actor=assistant в общем журнале,
   дневной/недельный бюджет (алерт 70%, стоп 100%, поднимает человек),
   rate-limit команд, счётчик ошибок ассистента (assistant-error),
   метрики: доля принятых как предложено решений, overhead ratio
   ($ ассистента / $ конвейера), стоимость «что происходит?».
6. **Дизайн — триада вместо роли** (решение Оператора 20.08):
   design-system как разовая задача-артефакт + скил ui-standards
   разработчику + визуальная приёмка скриншотами (расширение
   верификатора). Роль «дизайнер» не заводится (критерий §2).
7. **Этапы**: (1) read-only пульт [+ интерактивный макет артефактом
   ДО кода]; (2) auth + гейты-кнопки; (3) чат ассистента (Agent SDK);
   (4) событийный оркестратор поглощает auto (вебхуки forge).
   Телеграм понижен до нотификатора со ссылками (или отменяется).
