## 2. P0a — ADR-0003: целевые проекты (control plane)

Полный текст будет в docs/adr/0003-target-projects.md (при
переносе — сквозные якоря вместо двойной нумерации разделов).
Скелет решения:

1. **Пульт** (репозиторий artel) — единственный дом системы
   (оркестратор, конфиги, БД, журнал) и артефактов догфуда;
   хранение артефактов внешних проектов — по п.3 (замещает раннюю
   формулировку «дом всех артефактов»).
2. **`targets.yaml`** — декларативное подключение проекта: forge
   (github|gitlab), url, базовая ветка, token_slot, no_paths целевого,
   project_skills, исполнитель гейта мержа (поле «режим
   артефактов» убрано 22.08-2: режим один, публикация отложена).
3. **Хранение артефактов внешних целевых: target-branch —
   единственный режим текущего горизонта** (решение Оператора 21.08,
   итог обсуждения вариантов). **Orphan-ветка `artel`** (имя
   конфигурируемо) в репозитории целевого: только артефакты
   (`tasks/<id>/` + производные знания, п.3а), без кода и без общей
   истории с main — синхронизация из main не нужна по построению,
   CI целевого её не видит, рабочие ветки задач всегда от main
   (прецедент паттерна — gh-pages). Что это даёт: main чист;
   ничего не создаём на forge; те же права/токены, что на целевой;
   никакой второй точки отказа; люди видят полные артефакты в своём
   же репо; периметр по построению; protected branch силами GitLab
   целевого (пуш — только учётке Артели) — для GitLab-целевых
   enforcement честный; общий случай (GitHub Free без protection,
   чужие админы) — best effort, несущая гарантия всегда
   hash-фиксация (п.15). Рыночная сверка: платформы (Devin/Copilot/
   GitLab Duo) держат контекст в своём облаке, spec-driven лагерь
   (Kiro/Spec Kit/BMAD) — файлы в репо; target-branch — синтез под
   корпоративный периметр без вендорского облака.
   Носитель — git осознанно (гибрид: SQLite — состояние и запросы,
   git — документы, история, диффы, периметр; решающие критерии —
   человек в контуре и доступность корп-хостинга).
   Отложенные концепты: пространства с hub-storage — п.18
   (по триггеру); отдельный режим in-branch не заводим; догфуд-артель
   живёт текущей механикой (артефакты в ветках задач пульта) до A7,
   затем — обычный внешний target (решение 23.08).
   **Публикация следа — отложена целиком** (решение 22.08-2,
   замещает флаг publish_history). Ближний горизонт: артефакты
   внешних целевых — только локально в пульте (3д); в целевом от
   Артели только ветки task/ и MR; контекст людям — описание MR +
   комментарии. Триггер возврата — первый запрос людей целевого
   на полные артефакты; включение задним числом — идемпотентная
   дозаливка всей истории (первичка в пульте). Механика
   target-branch выше и 3в — спецификация на момент активации;
   все допущения о ветке (protected, имя, CI) — только при
   активации, из предусловий старта C уходят. Роль ветки при
   активации — «журнал проекта для людей», НЕ бэкап: сохранность
   первички — бэкап .artel/ (тест-эпоха, 3к) и серверные механизмы
   (нормальная работа). **Место спецификации** (решение 23.08,
   аудит v3 В1): при переписывании роадмапа начисто (§6 шаг 3)
   механика публикации — orphan-ветка, реплика, дозаливка, сверка
   head, права записи, bootstrap (пп.3/3а/3б/3в/3е, части
   п.15/п.17) — выносится в docs/deferred/publication.md;
   в нормативном тексте остаются триггер возврата и три строки
   сути: читатель перестаёт оплачивать чтение отменённого мира
   и путать активное с отложенным.
3а. **Производные знания проекта — рядом с его артефактами**
   (в `.artel/projects/<target>/knowledge/` пульта, 3д; в ветку
   `artel` целевого — при активации публикации): codebase-map,
   проектные скилы (если не в самом целевом), per-project копилка К1. Содержимое кода
   проекта не покидает периметр «репозиторий целевого + его каталог
   в пульте» (решение 22.08-2) — в память ассистента выдержки кода
   целевых не попадают: память хранит решения и указатели, знание
   кода живёт в knowledge/ проекта. Общепространственное — дома
   не имеет до пространств (п.18).
3б. **Свежесть производных знаний** — «кэш с меткой источника,
   сверка при потреблении, никогда молчаливое доверие» (целевой
   живёт без нас — люди мержат свои MR):
   - карта: `built_at_sha` в frontmatter; ленивая сверка при сборке
     брифа; регенерация до старта шага, если дифф main пересёк зону
     задачи; гибрид — скелет скриптом (дёшево, всегда), семантические
     аннотации агентом инкрементально по диффу; провал регенерации =
     алерт, не молчаливый старт со стухшей картой;
   - память ассистента: утверждения с датой и источником; сверка
     критичных фактов с живым источником при использовании; ревизия
     ассистентом под журналом изменений; внешние не пишут никогда —
     мир попадает в память только через события системы;
   - ветки задач: актуализация из main целевого перед merge_gate/
     снятием Draft + перепрогон CI; конфликт = итерация с лимитом.
3в. **Модель «реплика»: первичные артефакты — локально, ветка —
   публикация** (упрощение 21.08 вместо ранних саг). Артефакты
   рождаются и живут в локальном .artel/ пульта (как вся Фаза 0):
   транзакция шага локальна, сеть и доступность scm не участвуют.
   Публикация в ветку artel целевого (при активации — п.3) —
   фоновая; дефолт частоты — каждый ручной гейт (настройка;
   при активации — к моменту, когда человек открывает MR, SPEC
   и вердикты уже в ветке; до активации контекст людям — описание
   MR из SPEC и вердикты комментариями, п.5 — уточнение 23.08). От «механик несмежного
   хранения» остаются три строки: `code_sha` во frontmatter (+guard);
   идемпотентная дозаливка реплики (она же лечит любые проблемы
   ветки); «в ветку artel коммитит только оркестратор» — точка
   guard, гигиены п.16 и hash-фиксации п.15. Записанные компромиссы:
   лаг видимости до ближайшего гейта; черновики между гейтами —
   только локально. Hash-фиксация и approve-по-хэшу — несущие
   (админы целевого всесильны, история вечна). Токен без прав merge (нужен
   п.7) — проверка в A-спайке; допущения самой ветки (имя свободно;
   protected branch — у админа целевого; CI не триггерится на неё) —
   проверка при активации публикации, не в спайке. Триггеры публикации — ручные гейты ПЛЮС
   терминальные переходы (done/killed/escalated), атомарно одним
   коммитом (артефакты + журнальный срез): концовки задач в следе
   не теряются. При публикации сверяется ожидаемый head ветки
   с журналом — расхождение = событие «внешняя правка ветки», алерт
   (переписывание не лечится молча).
3г. **Двухуровневый срез — отложен целиком** (решение 22.08-2,
   схлопывает решение 22.08). Уровень 1 (процессный след) — отложен
   вместе с публикацией (п.3). Уровень 2 (ledger-экспорт экономики
   в git пульта) — отложен по триггеру «понадобился внешний экспорт
   экономики»: все три его роли сняты текущими решениями — вторая
   копия не нужна (потеря БД до сервера — принятый риск 3к, на
   сервере — серверные бэкапы СУБД), панельные тренды строятся
   одним запросом из единой БД (3ж), миграция БД — дамп-скрипт,
   не jsonl-импорт (3ж). При активации уровня 2 — только
   структурированные поля, никаких свободных текстов (код не
   утекает по построению состава); экономика в уровень 1 —
   настройка состава, дефолт нет (витрина сырости, экспозиция
   денег, необратимость git-истории).
3д. **Структура .artel/ — project-first** (единица управления —
   проект: подключение/отключение/восстановление = операции над
   одним каталогом; зеркальность публикации «каталог минус
   workspace → ветка»):
   ```
   .artel/                     ← .gitignore пульта целиком
   ├─ state.db                 ЕДИНАЯ БД всех проектов (см. 3ж)
   ├─ logs/                    логи самого пульта
   └─ projects/<target>/
      ├─ workspace/            эфемерный клон целевого (кэш)
      ├─ tasks/<id>/           первичные артефакты  → публикация
      ├─ knowledge/            maps/, skills/       → публикация
      └─ logs/                 стримы агентов проекта
   ```
   **`projects/<target>/` — локальный git-репозиторий без remote**
   (решение 23.08, аудит v3 Б1; workspace/ и logs/ — в .gitignore
   этого репо): целостность, история и диффы артефактов — штатным
   git вместо самописных механизмов. Коммитит только оркестратор
   на переходах FSM (= фиксация п.15), sha коммита — в журнал БД.
   Remote отсутствует физически — периметр п.3 сохранён
   по построению; doctor проверяет «git remote -v пуст»
   (+ git fsck при recovery). Бэкап каталога прежний, но теперь
   несёт историю. Агенты git-слоя не видят — пишут файлы как раньше.
   Параллельные задачи одного проекта (полная версия): workspace —
   per-task (git worktree); внешние публикации (при активации
   отложенных концептов) сериализуются: per-target очередь + одна
   глобальная очередь на запись в git пульта.
   На GitHub (remote пульта) уходят только система и догфуд-таски
   артели; .artel/ не коммитится конструктивно. Догфуд — особый
   случай (периметр артели = пульт): артефакты в ветках задач
   пульта, как всю Фазу 0, — **до A7** (решение 23.08): после A7
   артель — обычный внешний target с projects/artel/ и MR-флоу,
   особый случай снимается.
3е. **Дисциплина производных знаний**: skills/ и maps/ проекта правят
   только выделенные процессы (регенерация карты, задачи о скилах,
   Оператор) — точка сдачи не принимает их от посторонних задач
   (защита от тихого дрейфа знаний). Хэши компонентов брифа (версии
   карты и скилов, вошедшие в шаг) — в журнал: replay «по какой
   версии знал агент» восстановим. Bootstrap первой карты — в механике подключения проекта
   (ветка artel — при активации публикации, п.3).
3ж. **Единая БД на все проекты** (решение 22.08; серверная рамка
   3к сняла аргументы сплита: сирот при disconnect нет — это
   транзакция архивации (архив строк, никогда DELETE — решение
   22.08-2); бэкап — сервером целиком; периметр —
   серверный; параллелизм — Postgres по триггеру). Колонка target;
   сквозная экономика — единый кошелёк Оператора, суммарные лимиты
   и панельные тренды одним запросом; счётчики доверия — ключ
   (gate, target): доверие с догфуда не наследуется на целевые.
   Disconnect сохраняет счётчик нумерации задач target (архив
   строк; нумерация — персистентный счётчик per-target, НЕ
   COUNT(*) — иначе архивация строк переиспользует номера:
   коллизии id в журнале и в любой будущей дозаливке следа/экспорте;
   в объём A1) — реконнект не создаёт коллизий номеров.
   **Disconnect — процесс, не только данные** (решение 22.08-2):
   прогоняет kill-протокол п.7 по всем незавершённым задачам
   target (close_mr с комментарием, финальные ответы в тредах) —
   внешних висяков не остаётся. При недоступном токене (доступ
   отозван — главный принудительный сценарий) внешняя часть
   протокола — ручная деградация (решение 23.08): Оператор просит
   админа целевого закрыть MR-ы или закрывает своей УЗ, факт
   и способ фиксируются в журнале; внутренняя часть (kill,
   архивация) выполняется всегда. Reconnect: синхронизация,
   не bootstrap с нуля; следы внешней активности за период
   отключения — события «внешняя правка» с разбором,
   не инцидент компрометации. Рассмотренные и отменённые варианты:
   сплит system.db+per-project и поле db: — сняты рамкой 22.08.
   **Движко-независимость**: SQL только в store.py — это цель,
   не факт (сырой SQL сейчас в 5 модулях; консолидация — в объёме
   A1, 22.08-2); переносимая
   схема без SQLite-экзотики; серверная эпоха = переход на СУБД
   типа Postgres (уточнение 22.08-2), миграция — дамп-скрипт
   SQLite → Postgres при переезде, стандартная операция.
   Без ORM и repository-слоёв.
3з. **Роли: формула универсальности.** Агент = системный слой
   (промпт роли, методология-чеклисты, права — константа, protected
   paths пульта) + проектный слой (знание: карта, проектные скилы,
   конвенции целевого как данные — аддитивно, из projects/knowledge)
   + задачный слой (SPEC, пакет). **Проект не может ослабить роль**:
   кастомизация только аддитивная, а безопасность — курированием
   списка скилов и их ревью тем же конвейером (аддитивный текст
   может ослаблять семантически — защита процессная, не
   структурная); легальные оси вариативности —
   исполнители (design §16), verify-профиль (проектные агенты-проверки
   в системных слотах типов), параметры targets.yaml. Улучшение
   системного скила апгрейдит роль во всех проектах сразу.
3и. **Кросс-таргетные задачи** (пара panel+API будет порождать):
   в модели задача = один target; фича на два репо = две связанные
   задачи (поле related в SPEC), порядок «API раньше панели»,
   связывание и синхронизация гейтов — Оператором. Минимальная
   механика (решение 22.08-2): guard при старте шага — если
   related-задача не в done, алерт и подтверждение Оператора,
   не молчаливый старт (иначе итерации сгорают об красный CI
   до лимита). Иное — не поддерживается осознанно.
3к. **Инфраструктурные эпохи** (решение 22.08). Тест — ноутбук
   Оператора: поллер — прерываемый локальный процесс без SLA
   (работает в сессиях Оператора; догон без потерь — C0, 23.08);
   сохранность первички и hash-журнала — обязательный локальный
   бэкап .artel/
   (механизм — настройка Оператора: Time Machine/rsync) +
   recovery-сверка консистентности в doctor (A3, решение 22.08-2);
   давность последнего бэкапа проверяет doctor (>7 дней → алерт),
   restore-тест не требуется — принятый риск; восстановление из
   бэкапа — restore-режим doctor (A3, решения 23.08);
   прочие потери не рассматриваются. Нормальная работа — **self-hosted:
   выделенный корп-сервер** — тот же пульт, функционально ничем
   не отличающийся от ноутбука, плюс постоянный онлайн (демон/поллер
   always-on) и серверные механизмы устойчивости (комплексные бэкапы
   БД и артефактов, периметр). Переход между эпохами — не гейт
   и не триггер: по потребности в мощностях и постоянной работе,
   после обкатки основного флоу (уточнение 22.08-2); гейтится
   не сам переход, а запуск постоянного фонового режима — он
   требует серверной эпохи и сервисных УЗ (Р7). Инференс — как
   на ноутбуке; при ограничениях сети — подключение локальной/
   корпоративной LLM (Р6), гейтвей заранее не строим. Отмечено
   и отложено (не приоритет): секрет-слой при переносе (keychain
    ноутбука → серверное хранилище), перенос БД (дамп в СУБД
   сервера, 3ж).
4. **Workspace** — эфемерный клон целевого
   в `.artel/projects/<target>/workspace/` (3д);
   агент видит только целевой и его токен, конфиги пульта недоступны
   (отсечение инъекций из чужого кода).
5. **Контекст людям — примитивы forge**: описание MR генерируется
   из SPEC; вердикты ревью — комментариями; финальный итог
   (итерации, стоимость, ссылка на трейс) — комментарием.
6. **Forge-адаптер**: интерфейс create_mr / undraft / merge /
   close_mr / ci_status / comment / reply / list_discussions /
   mr_events / approve_label (полный список — по потребителям
   пп.7 и 9, ревью 21.08); реализации github и gitlab. Merge в
   целевой — только оркестратор через адаптер.
7. **Исполнитель гейта мержа** (уточнение Оператора 20.08,
   вопрос про дежурного feedback): `merge_gate: operator |
   target-human`. Режим target-human: MR создаётся **Draft**, Draft
   снимается только после нашей приёмки; мержит человек целевого
   проекта его кнопкой; оркестратор узнаёт о merge по событию forge
   и закрывает задачу; комментарии людей в MR → внешний
   changes_requested → обычная итерация. **Карта состояний внешнего
   хвоста** (решение 23.08, аудит v3 Флоу-1; кодоспособная,
   реализация — C1): Draft-MR создаётся при первом пуше ветки
   задачи (описание из SPEC, адаптер B1b) и висит Draft всю
   разработку — люди видят прогресс. `merge_gate` для target-human
   исполняется как **undraft**: approve Оператора по sha = команда
   снятия Draft, наш последний гейт — дальше решение чужое. После
   undraft задача переходит в новое состояние FSM **`awaiting_human`**
   (каноническое имя; «awaiting-human» в тексте — оно же) и стоит
   в нём до merge-события поллера → done. Лимит одновременных задач
   3 и наблюдение дискуссий (п.9) — свойства этого состояния,
   а не оверлей поверх FSM. Внешний changes_requested возвращает
   в in_dev обычным циклом — маршрут один, см. п.9. **Токен Артели для такого
   проекта не имеет прав merge вовсе** — минимальные привилегии
   (настройка access level — у админа целевого: допущение, проверить
   при подключении). Релизы — процесс целевого, вне нашего FSM.
   **Merge раньше нашей приёмки** (человек сам снял Draft — прав
   помешать у нас нет и не должно быть): инцидент → эскалация
   Оператору + уведомление в MR-тред, задача НЕ закрывается как
   done молча; протокол — письменно
   (описание MR + вики целевого), не устно: должен переживать
   ротацию дежурных (уточнение 22.08-2). Kill задачи
   при открытом внешнем MR: close_mr с комментарием; ветка task/ —
   по политике целевого (delete_source_branch). Лимит одновременных
   задач в awaiting-human — 3 (пропускная способность Оператора,
   решение 22.08-2): сверх лимита внешняя фаза не стартует, задачи
   ждут в очереди — задача остаётся в своём последнем внутреннем
   состоянии (MR не создаётся), в CLI/панели — пометка «queued:
   awaiting-human limit», порядок FIFO (уточнение 23.08).
8. **Новые инварианты**: наблюдаемое и тестируемое — в реестр
   («роли не выполняют push вне ветки своей задачи» — кодируемо);
   свойства чужих систем (защита веток целевого — у его админа) —
   во вторую таблицу реестра, без тестов-декораций (ревью 21.08);
   workspace изолирован от пульта;
   no_paths целевого проверяются до merge; для target-human —
   Артель не мержит никогда; комментарий MR вне зоны SPEC не
   исполняется — только эскалация; ядро FSM неизменно, каталог
   типов проверок расширяет только Оператор через ADR;
   merge_gate не переводится в conditional/auto, пока PAT ролей
   не разделены (обязательство ADR-0001; решение 22.08-2).
9. **Обработка комментариев MR** (замечание Оператора 21.08).
   Для awaiting-human задач оркестратор следит за дискуссиями MR
   (поллинг; вебхук — опция, см. ниже). Триаж комментария — 4 класса:
   вопрос → ответ в тред; замечание-правка → итерация разработчика
   → пуш → «исправлено в <sha>» в тот же тред; мнение без действия →
   короткий ответ/ничего; чужое обсуждение → не вмешиваться.
   Комментарий — недоверенный вход: исполняется только в границах
   SPEC и no_paths, расширение объёма → эскалация Оператору
   (одновременно защита от инъекций и от scope creep).
   Чужой коммит прямо в ветку task/ открытого MR — тот же
   недоверенный вход (решение 22.08-2): детект при старте итерации,
   триаж как у комментария; молча затирать или ребейзить чужую
   работу нельзя. Отдельный
   счётчик external_review_iters с лимитом (~3) → эскалация.
   **Маршрут правки один** (решение 23.08, аудит v3 Флоу-2):
   «итерация разработчика» из триажа = обычный цикл in_dev →
   review → verifying — внутреннее ревью обязательно, залоченные
   acceptance-тесты (A4) остаются зелёными. П.9 задаёт только канал
   коммуникации (триаж, премодерацию ответов и пуша), а не
   альтернативный маршрут кода в обход ревью. Снятие премодерации
   счётчиком чистых циклов ослабляет модерацию слов — но никогда
   не отменяет внутреннее ревью кода.
   Ответы в треды: только по делу, без споров — разногласие
   эскалируется. Режим `premoderated` per-target на период доверия
   покрывает ОБА канала (решение 22.08-2): ответы в треды И
   итерации-правки по внешним замечаниям — перед пушем правки
   по чужому комментарию Оператору уходит карточка (замечание +
   дифф), пуш по подтверждению; премодерация текста без кода —
   инверсия риска, запрещена. Снимается счётчиком чистых циклов.
   Носитель премодерации (решение 23.08) — очередь в БД: CLI
   `premod list/approve/reject` показывает неразобранные при каждом
   запуске; панельный инбокс читает ту же очередь (реализация — C3).
   Данные людей целевого (имена, тексты комментариев) в артефактах,
   журнале и очереди премодерации на ноутбуке Оператора — принятый
   риск (решение 23.08: рабочие данные на корп-устройстве).
   Канал: **поллинг — основной** (вебхуки корп-GitLab на хост
   Оператора не обещаем — входящей связности нет), вебхук — опция.
   Любой стоп задачи дольше 2 дней (бюджет, эскалация) при открытом
   внешнем MR → служебный комментарий в тред: «задача приостановлена,
   вернёмся» (решение 22.08-2) — бот не замолкает молча посреди
   диалога с людьми.
   Пост-merge (решение 23.08, замещает окно наблюдения 7 дней
   22.08-2): по merge задача закрывается, треды смерженных MR
   система не читает и служебных комментариев не пишет; дефекты
   и вопросы после merge — обычным порядком целевого (новая задача
   через Оператора); reopen MR системой не детектится — узнаём от
   людей (принятое следствие). Финальный итог-комментарий (п.5)
   остаётся частью закрытия.
10. **Профиль процесса проекта** (замечание Оператора 21.08).
    Маршрут = неизменное ядро + вариативная фаза verify: каждый
    проект декларирует список проверок между ревью и merge из
    фиксированного каталога типов: `ci` (ждать пайплайн), `agent`
    (роль-проверка с проектными скилами), `human` (человек проекта),
    `script`. Пример: artel `verify: []` (хватает CI-ядра);
    feedback — целевое состояние `verify: [ci, agent:alpha-test]`
    (альфа-тест на поднятом стенде, позже делегируемый агенту);
    **профиль поэтапный** (решение 22.08-2): C2 подключает feedback
    с `verify: [ci]`, расширение до agent:alpha-test — отдельным
    изменением при C4, декларировать неисполнимое нельзя. Ни одного нового
    состояния FSM: verifying становится композитным циклом по
    профилю, каждая проверка — обычный шаг (журнал, стоимость,
    потолки, ретраи переиспользуются). Произвольные графы процессов
    per-project — сознательно НЕ поддерживаются.
11. **Три оси вариативности per-target** (итоговая формула):
    исполнители ролей (design §16) × политика гейтов (design §4,
    включая
    merge_gate: target-human) × профиль проверок (п.10). Всё
    остальное — маршрут, инварианты, каталоги — системная
    константа. Верификация как фаза есть всегда; агент-верификатор
    ПОСЛЕ кода инстанцируется только профилем (в artel его нет —
    пустой профиль означает «верификация полностью
    детерминированная», а не «верификации нет»). Роль test_author
    ДО кода (A4, решение 23.08) — автор приёмочных тестов, системная
    константа маршрута для всех targets (скип — только явным полем
    SPEC); имя verifier закреплено за агентами verify-профиля
    (после кода), их носитель — состояние verifying (B1b).
12. **Подключение проекта включает карту** (финальное ревью):
    codebase-map целевого генерируется при подключении и обновляется
    по мержам — вход разработчика в чужой код без блужданий; для
    монолита feedback это кратная разница стоимости задачи (факты
    Фазы 0: учтённые $2.4–34.8 — учёт стоимости с T007, T001–T006
    вне учёта; итерации ревью умножают).
13. **Workspace внешних targets — в песочнице** (финальное ревью):
    контейнерный запуск ролей обязателен до фазы C — чужой код
    с недоверенным содержимым не исполняется на хосте Оператора.
    sandbox/Dockerfile существует с Фазы 0 — ввести в строй.
14. **Агентская обвязка целевого не наследуется** (замечание
    Оператора 21.08). Целевые проекты имеют свои CLAUDE.md/AGENTS.md,
    .claude/settings.json (hooks = произвольные команды!), .mcp.json,
    скилы, плагины — CLI подхватывает их автоматически, что даёт:
    перехват инструкций роли чужим файлом; **конфиг-инъекцию**
    (право коммита в целевой = исполнение кода в нашем агенте
    с нашими токенами — хуже prompt injection); недетерминированность
    окружения. Принцип: **окружение роли определяет только пульт**.
    Механика: запуск ролей с отключёнными проектными источниками
    настроек (--setting-sources без project, --strict-mcp-config —
    существование флагов проверяет спайк, фиксирует B1a; постоянство
    поведения при обновлениях CLI — пин версии + smoke-тест изоляции
    в doctor, A3, решение 23.08); CLAUDE.md
    целевого — в бриф как данные с пометкой «недоверенные конвенции
    проекта»; project_skills — только курируемый список из
    targets.yaml; инвентаризация .claude/.mcp.json при подключении
    (doctor) + подсветка изменений этих путей в MR. **Важно
    (ревью 21.08): флаги закрывают только конфиг-вектор агента;
    от исполнения чужого кода тулчейном (npm postinstall, make,
    тесты — неотъемлемая работа разработчика) песочница —
    ЕДИНСТВЕННАЯ линия, не вторая.** Это разные векторы.
15. **Целостность артефактов** (обсуждение 21.08): артефакты —
    управляющий вход системы (SPEC ведёт разработчика, REVIEW двигает
    FSM), их модификация = управление конвейером в обход гейтов.
    Принцип: **«читаемы всеми — писаемы только системой»**. Механика:
    запись в ветку артефактов — только учётка Артели, людям read
    (protected branches); **hash-фиксация** — журнал БД пульта (вне периметра
    внешних хранилищ) хранит фиксацию артефактов на каждом переходе
    FSM; реализация (решение 23.08, аудит v3 Б1, замещает пофайловые
    хэши): оркестратор коммитит артефактный git-репо целевого (3д)
    на каждом переходе, в журнал пишется commit sha — правило «все
    артефакты-входы» (SPEC, PLAN, REVIEW, acceptance) выполняется
    по построению: коммит фиксирует каталог целиком, будущие типы
    артефактов — автоматически; сверка на каждом следующем гейте
    и при старте шага = сравнение sha + чистота рабочей копии.
    **Approve привязан к sha**
    (ревью 21.08, закрытие TOCTOU): команда/кнопка подтверждает
    конкретный sha (`approve <id> <sha>`), расхождение = отказ —
    «показали одно, заапрувили другое» невозможно. Механики ветки
    артефактов (права записи, protected branch) — только при
    активированной публикации следа (п.3, отложена); hash-фиксация
    в журнале БД пульта и approve-по-хэшу — безусловны всегда,
    независимо от публикации (уточнение 22.08-2). **Честно про
    enforcement** (ревью 21.08):
    «писаемы только системой» — best effort по возможностям forge
    (GitHub Free private без branch protection — ADR-0001; ветки
    целевых — под чужими админами); НЕСУЩАЯ гарантия — hash-фиксация
    + журнал вне периметра ветки артефактов, не права записи. Подписанные
    коммиты — по триггеру «появился верификатор подписи» (без него —
    ритуал). Новый инвариант: «FSM принимает решения только по
    артефактам, чьи хэши зафиксированы его журналом».
16. **Гигиена артефактов**: в артефактах — ни секретов, ни длинных
    цитат чувствительного кода (история git неистребима — чистить
    поздно, надо не допускать). Правило в базовые скилы +
    guard-проверка паттернов токенов.
17. **Внешние правки артефактов — отложены целиком** (решение
    22.08-2; ранее флаг `allow_artifact_edits`, до того —
    пространственный). Без публикации следа (п.3) людям физически
    нечего править; при активации публикации концепт потребует

    (пуш в ветку — только учётке Артели, обратной синхронизации
    ветка→первичка нет): канал правок — MR в ветку artel, приём =
    re-гейт (SPEC → повторный spec_gate и т.д.) + занос в первичку
    оркестратором; правка никогда не принимается молча; счётчик
    external_edit_regates с лимитом 2 → эскалация. **Безусловные
    правила вне концепта (действуют всегда, для локальных
    артефактов):** вход шага сверяется с хэшем, зафиксированным
    журналом/approve, при СТАРТЕ шага, не только на гейтах —
    расхождение = стоп до разбора (решение 22.08-2, закрытие
    зазора approve→старт); чужой рукой поставленный вердикт ревью
    не учитывается никогда (авторство вердикта — только у ревьювера
    системы); правка budget_usd задним числом не действует
    (инвариант 10); расхождение хэша = инцидент целостности
    (стоп задачи, эскалация).
18. **Статусы реализации концептов** (решения Оператора 21.08).
    **Пространства — отложены целиком** (вместе с hub-storage,

    хранилище (кросс-проектная память ассистента, сквозная копилка)

    на scm подтверждена (решение 21.08) — пригодится при триггере.

    публикации + первый реальный запрос людей на правки». **Артефакты фазы B
