### П3 — симуляция (обязательный минимум + свои)

1. **Одновременный `cmd_new` двух операторов.** Клейм-реф серийную
   гонку решает (push создания в один реф — второй получает отказ),
   но что делает проигравший `cmd_new` — не сказано нигде: к моменту
   push уже созданы ветка, worktree, строка БД, закоммичено ТЗ.
   Перенумерация с откатом или мусор? → входит в BL-1 (SPEC M1).
   Замечание: клейм веткой (multi-operator.md:14) коллизию номера
   НЕ детектит вовсе — имя ветки содержит slug, `task/t085-a` и
   `task/t085-b` не конфликтуют → MN-1.
2. **Push-клейм при упавшей сети.** Push в `cmd_new` обязателен
   (правило 0) → при обрыве сети заведение задач блокируется целиком;
   фактура уже есть (31.08, 40 минут Connection refused). Поведение
   при отказе push не специфицировано → MJ-9.
3. **`refs/artifacts/*` удалён до/после GC.** До GC — восстановим
   из любого клона, у которого реф был сфетчен (но дефолтный fetch
   refspec `refs/heads/*` refs/artifacts НЕ тянет — клоны без
   явной настройки копий не имеют); после GC на форже — артефакты
   и RETRO задачи потеряны навсегда, в отличие от истории main.
   «Защита — политика» честно названа, но окно необратимости
   и отсутствие fetch-refspec в M1 не названы → входит в BL-1.
4. **RETRO не доехал, каталог задачи удалён.** Локальный реф жив
   (RETRO коммитится локально до push) — потеря только при смерти
   диска (принято ADR-0005 п.3). Но у соседей задачи НЕТ до
   успешного push: расход программы у них занижен → MJ-6.
5. **verifying при «check-runs пусты».** auto вышел (verifying —
   AUTO_STOP), Оператор зовёт advance руками; задержка событий CI
   ~40 мин (прецедент T040) при потолке 20 попыток: цикл-обёртка
   с минутным интервалом сожжёт потолок ДО прихода событий → ложная
   эскалация; та же болезнь, что «3 ретрая за секунды» 31.08 → MJ-4.
6. **10 параллельных задач → гейтовая очередь.** Арифметика — П7:
   ~6–8 подходов Оператора на задачу, при 10 задачах/день — 60–80
   касаний; факт журнала за 31.08 — 108 записей actor=operator
   (из них ~35–40 содержательных решений + 29 запусков auto) → MJ-10.
7. **Второй оператор получил отравленный артефакт первого.**
   При перехвате задачи (правило 2) агенты оператора B работают
   по брифам из артефактов оператора A; guard проверяет структуру,
   подпись коммитов — «по триггеру появления верификатора» (№14,
   бездействует). Инъекция в SPEC/PLAN доезжает в промпт чужой роли.
   Механизма приёмки чужого артефакта при передаче нет → Q-4.
8. **Kill чужой задачи при живом lease.** Lease — строка ЛОКАЛЬНОЙ
   БД владельца; у оператора B нет ни lease, ни самой строки задачи
   (`tasks` локальна) — kill сказать «нет такой задачи». Видимости
   чужих in-flight задач нет вообще: правило 4 упоминает «паспорта»
   в git, носителя паспорта не определяет ни M1, ни M2 → MJ-8.
9. **Два approve merge_gate в двух клонах одновременно.** merge_locks
   — локальная таблица: оба мьютекса пройдены, гонку решает отказ
   push у проигравшего ПОСЛЕ локального merge в его main-копию →
   локальный main разошёлся с origin, `pull --ff-only` (M2) откажет,
   чинить руками. Роадмап M2 про мерж-гонку молчит → MJ-5.

### П9 — premortem (методы v1-6/v2-G: смерть от лекарства 27–31.08)

1. **Смерть по деньгам от эфемерности.** Лекарство: best-effort sync +
   личные подписки. Через месяц двухоператорной эпохи: у каждого
   пульта своя SUM(spent_usd), чужое доезжает только с RETRO при
   done; программные пороги молчат при фактических ~130% стоп-лосса;
   go/no-go считается по числам, которые оба оператора знают
   заниженными; решение «go» на ложной экономике; пробой обнаружен
   при сверке подписок за квартал — точка невозврата пройдена
   в момент, когда пороги перестали быть глобальными de facto
   (первый день двухоператорности). Что должно было предотвратить:
   инвариант 23 («пороги — сумма по ВСЕМ задачам») — но его слово
   «всех target» молча не значит «всех операторов». Лечение — MJ-6.
2. **Смерть по вниманию от MAX_PARALLEL=10.** Лекарство: параллелизм
   ради пропускной способности при негруженных (по замыслу ADR-0007)
   гейтах. Реальность: автогейт мёртв (MJ-1), с $1400 отключён
   навсегда (MJ-2), verifying добавил ручную петлю (MJ-3), 100+
   операторских действий в день. Alarm fatigue, описанная в design §4
   как антипаттерн, наступает у самого Оператора: approve по инерции
   → пропущенный дефект на внешнем целевом (B2/C2) → доверие
   к конвейеру у первого же стороннего наблюдателя погибает. Точка
   невозврата — первый чужой репозиторий с проштампованным мержем.
   Что должно было предотвратить: operator-gates.md («гейт —
   проверка») — норматив без пропускной способности не работает.
   Лечение — MJ-1/MJ-2/MJ-10 разом (вернуть гейтам автоматику ИЛИ
   вернуть WIP к числу, которое человек проверяет честно).
3. **Смерть памяти от refs-топологии.** Лекарство: чистый main.
   M1 реализован буквально: артефакты и RETRO новых задач — только
   в refs; guard CI их не видит (ci.yml гоняет tasks/*/*.md по
   чекауту), канарейка не покрывает acceptance (MJ-11), coldstart
   пересевает по замороженному corpus'у. Через N месяцев случайное
   удаление пачки refs (миграция репо, «уборка» форджи, скрипт
   с ошибкой) + GC — и у системы нет ни артефактов, ни RETRO, ни
   расхода за всю refs-эпоху; К2/К3 остаются без корпуса. Точка
   невозврата — GC форджи. Что должно было предотвратить: ADR-0005
   («что обязано пережить потерю») — но его как раз перевернули без
   ADR. Лечение — BL-1 (реестр скрытой цены + ADR с ответом «что
   переживает потерю refs»).

## Приложение А — блайнд-эскиз фазы 0 (написан до чтения §3/Д1/multi-operator.md) и вердикты дельт

### Эскиз (дословно, фиксация до чтения)

**(а) N операторов без сервера.** Единственная разделяемая среда —
git remote; координация — атомарность push (CAS). Каждый оператор —
полный локальный узел (своя БД-кэш, истина — git). Клейм задачи —
push клейм-рефа; проигравший перечитывает и отступает. Номера: либо
бесколлизионные id (ULID/префикс оператора), либо CAS-реф-счётчик;
вариант с бесколлизионными id дешевле и не требует онлайна. Lease без
сервера — heartbeat-реф с таймстампом, протухание по возрасту (порог
много больше сессии); kill чужого — только при протухшем lease и по
команде своего Оператора. Гейты и бюджеты — собственность оператора
задачи; программные пороги — сумма журналов, доехавших до origin,
best-effort с честной пометкой «нижняя оценка». Merge в main
сериализует git: проигравший гонку подтягивает main и перепроходит CI
(инвариант 19 после актуализации). Чужие артефакты — данные: guard +
приёмочные у читателя, вход агента из чужого артефакта проходит те же
проверки, что из своего.

**(б) Артефакты и паспорта.** Артефакты — файлы `tasks/<id>/` в ветке
задачи; в main через merge_gate, там — история/эталон. Ничего
долговременного в `.artel/` (локальна, невоспроизводима у соседа).
Паспорт (статус FSM, счётчики, sha) — в локальной SQLite, но для
многооператорности обязан иметь git-проекцию: снапшот в ветку задачи
на каждом переходе FSM, локальная БД — восстановимый индекс. Иначе
второй оператор не отличит «в полёте» от «брошено». Удаление: ветку
удаляет оркестратор владельца после done/kill+RETRO; чужие ветки —
только подметалка по протухшему lease с журналом; `tasks/<id>/`
в main — retention-задача с гейтом Оператора; локальные логи —
владелец, аудитно-важное дублируется в git до смерти лога. Смерть
артефакта привязана к «прочитан и подтверждён» (merge/RETRO в main),
не к календарю.

**(в) Дебрендизация.** Одна конфиг-константа имени (дефолт нейтральный
— `orchestrator`/`.orch/`); ключ догфуд-target'а — зарезервированное
слово (`self`); CLI — `python3 -m orchestrator`, `artel.py` — тонкий
алиас на фазу миграции; каталог состояния — из конфига, старый путь
читается fallback'ом с предупреждением. Enforcement — CI-греп
на бренд вне белого списка (исторические доки, tasks/, ADR). Порядок:
конфиг-константа и alias → массовое переименование → каталог
состояния последним (миграция данных); однофазная жёсткая замена
сломала бы параллельные сессии.
