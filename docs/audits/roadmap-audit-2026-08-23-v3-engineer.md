## 1. Мой проект (блайнд-дизайн, сжато до несущих решений)

### Флоу и роли

FSM (владелец всех переходов — детерминированный оркестратор):
`INTAKE → SPEC_DRAFT → [гейт по классу риска] → TESTS_LOCKED →
IMPLEMENT → VERIFY(машинные гейты) → REVIEW → (FIX⇄VERIFY⇄REVIEW,
лимит 2) → ACCEPT[гейт по классу риска] → MERGE(оркестратор) →
DELIVERED → RETRO → CLOSED`. Оверлеи: `BLOCKED_ON_OPERATOR` (из
любого состояния, ноль токенов), `FAILED_BUDGET`, `CANCELLED`.

Роли (один агент = одна сессия = один переход):
- **Аналитик**: свободный текст → SPEC по схеме + машинные критерии
  приёмки + батч вопросов Оператору.
- **Тест-инженер** (отдельная сессия): критерии приёмки → исполняемые
  приёмочные тесты, коммитятся ДО разработчика и **лочатся** — CI
  запрещает ветке задачи менять файлы приёмочных тестов. Защита
  техническая, не конвенцией.
- **Разработчик**: SPEC + залоченные тесты + карта репо → код до
  зелёных машинных гейтов.
- **Ревьювер**: diff + SPEC, ничего из рассуждений разработчика;
  вердикт с **evidence-контрактом** — каждое замечание и каждый «ок»
  со ссылкой на строку/тест/выполненную команду, вердикт без
  доказательств отклоняется guard'ом.
- **Оркестратор**: не LLM; FSM, сборка контекстов по allowlist,
  merge, бюджеты, ретраи.

Классы риска дозируют гейты: docs-only → авто-мерж по зелёным гейтам;
low → агент-ревью, авто; normal → +приёмка Оператора; high → Оператор
на SPEC и на merge.

### Артефакты, состояние, восстановление

- Артефакты: frontmatter по схеме + фиксированные секции, машинная
  валидация дважды (перед передачей и в CI). Контекст агента собирает
  оркестратор из манифеста; в контекст НЕ входят чужие рассуждения,
  логи прошлых итераций, закрытые замечания. Даунстрим получает
  выжимки: ревьювер — diff+критерии; разработчик на фиксе — только
  открытые замечания.
- Кешируемая **карта репозитория** с меткой источника, обновляется
  при мерже — главная экономия на исследовании.
- Истина — durable store (SQLite) + **git: все первичные артефакты
  версионируются git'ом**, целостность и история — свойства носителя,
  не отдельная подсистема. Запуск агента = транзакция: нет валидного
  артефакта — состояние не сдвинулось, перезапуск идемпотентен
  (детерминированные имена веток/MR, check-before-create).
  Recovery = пересчёт из store+git+forge API.

### Качество при стохастичных исполнителях

Слоями от дешёвого к дорогому: (1) исполняемые гейты; (2) залоченные
приёмочные тесты, написанные до кода — разработчик не может подогнать
критерии под реализацию; (3) независимое ревью чистым контекстом —
защита от общей галлюцинации; (4) evidence-контракт вердикта;
(5) лимит итераций 2, затем эскалация с дайджестом разногласия;
(6) **канарейки** — 2–3 эталонные задачи с известным ответом,
прогоняются после изменения промптов/скилов/модели/CLI — регрессионный
тест самого конвейера. Различение «агент плохой vs инструкция плохая»:
перепрогон стадии с теми же входами; устойчивый одинаковый провал =
инструкция, разброс = стохастика.

### Оператор, экономика, гигиена, эволюция

- Вопрос Оператору: контекст ≤5 строк, 2–4 варианта с рекомендованным
  дефолтом и последствиями; **вопросы батчируются** — максимум одно
  прерывание на стадию. Ожидание = ноль токенов, оркестратор занят
  другими задачами.
- Лимиты худшего случая трижды: бюджет $, лимит итераций, таймаут
  стадии. Параллелизм между задачами — да (изоляция ветками, очередь
  мержей per-repo); внутри задачи — последовательно.
- **У каждого артефакта — владелец и TTL.** На CLOSE: tasks/<id>
  компактируется в RETRO-дайджест (история остаётся в git), ветки
  удаляются, логи итераций не переживают задачу. Память/уроки —
  курируемый файл фиксированного размера с merge-on-write, не
  append-only. Ничто не накапливается неограниченно.
- RETRO — обязательная стадия: классификация исхода (успех / провал
  агента / провал инструкции / провал SPEC) + патч к скилам/шаблонам
  в виде диффа; применяет только Оператор; каждая правка правил
  проверяется канарейками.

## 5. Оптимизация потока (цены — грубо, на 100 задач; базис: факт state.db $14.9/задачу средняя, диапазон $2.4–34.8)

1. **Поздние итерации ревью получают полный пакет, а не дельту.**
   Ревью-пакет (до 400 КБ ≈ 100K токенов) собирается заново на каждый
   прогон: SPEC+PLAN+прошлый REVIEW+полный diff — при том, что
   итерация 2–3 отличается от итерации 1 десятками строк. Роадмап сам
   это знает (P3 «Инкрементальный diff ревью», $25, факт T011
   «поздние прогоны съели экономию») — но держит в «мелочи вставками,
   когда конвейер свободен», а фазы B/C добавят external_review_iters
   с тем же полным пакетом на каждый чужой комментарий.
   *Цена промедления: ~15–25% стоимости ревью-прогонов ≈ $150–300
   на 100 задач; растёт с фазой C.* Рекомендация: P3-diff — в фазу A,
   до внешнего контура.
2. **Разработчик на итерации фикса перечитывает всё.** Каждая
   итерация — новая сессия: SPEC, PLAN, весь REVIEW (не только
   открытые замечания), повторное самостоятельное чтение репо без
   карты (карты пульта нет — факт §4 P3; «бриф разработчика» —
   предусловие C2, т.е. десятки догфуд- и panel-задач фаз A–B пройдут
   без него). Роадмап п.12 сам называет цену отсутствия карты
   «кратной». *~$200–500 на 100 задач + это главный вклад в метрику
   «трение», которой к go/no-go предстоит быть хорошей.* Рекомендация:
   бриф и генератор карты пульта — в фазу A вместе с A1–A3, тем более
   что механика ревью-пакета (T011) уже есть и переиспользуется.
3. **Календарная утилизация: конвейер стоит большую часть wall-clock.**
   Типовая задача: 2–3 ручных гейта (spec_gate, acceptance,
   merge_gate/premod) × лаг part-time Оператора (часы–дни) при
   машинном времени ~1 час. Задачи де-факто последовательны (рамка
   Фазы 0 «одна активная»; роадмап параллелит только «П1 параллельно»
   и фазу C с гейтами панели — без механики). При этом всё для
   межтаргетного параллелизма 2–3 задач уже спроектировано: worktree
   per-task (3д), лимит awaiting-human 3 (п.7), изоляция веток.
   *Цена: пропускная способность ~×2–3 лежит на земле; в календаре
   это месяцы пути до go/no-go.* Рекомендация: явно разрешить N=2
   параллельные задачи разных target'ов с фазы B; гонки за git пульта
   и SQLite назвать и принять (короткие транзакции + одна глобальная
   очередь записи — уже описана в 3д).
4. Не находки (проверено, натяжки нет): скилы ролей компактны
   (78 строк суммарно на разработчика — повторная передача дешева);
   SPEC мал; двойная валидация guard (локально+CI) — копейки;
   кэш промптов внутри шага используется, межшаговый честно списан
   (design §10).

## 6. Чистка (проход уборщика) + политика retention

Находки (в роадмапе нет ни одной процедуры удаления/архивации —
grep «удал/архив/ротац/retention» даёт только архив строк БД при
disconnect и уборку kill):

1. **`.artel/logs/` бессмертны и не наблюдаемы.** Каждый прогон пишет
   stream-json (сотни КБ–МБ); инвариант 16 защищает их от kill, но
   политики ротации нет вовсе. К фазе C — гигабайты, которые попадают
   в «обязательный бэкап .artel/» (3к) и раздувают его. Нюанс: даже
   законная ротация формально упрётся в инвариант 16 («история
   переживает задачу») — политику надо завести ADR'ом один раз, а не
   решать по месту.
2. **Смерженные ветки task/ в пульте не удаляются никогда**
   (cleanup работает только при kill и смерженную ветку явно
   «оставляет»; design §6 обещает «ветка смержена и удалена» — код
   Фазы 0 этого не делает). ~30 задач до go/no-go = ~30 мёртвых веток
   в каждом `git branch`.
3. **Копилка К1 не опустошается.** К2 («по триггеру») дистиллирует
   копилку в правки скилов, но перенос выученного не удаляет источник —
   вторая дистилляция переработает то же самое; копилка растёт
   до бесконечности и целиком входит в контекст каждого прогона К2.
4. **Таблицы premod и alerts не имеют финала строк.** У alerts есть
   acked, у premod — approve/reject, но разобранные строки живут вечно;
   «CLI печатает неквитированные при каждом запуске» — при накоплении
   мусора этот вывод сам станет шумом (alarm fatigue, о которой
   design §4 предупреждает применительно к гейтам).
5. **Память ассистента**: ревизия есть (п.8), потолка размера нет —
   единственный накопитель, напрямую попадающий в контекст каждой
   сессии ассистента.
6. **Судьба аудит-слоёв: роадмап оброс правками до нечитаемости.**
   Преамбула — 48 строк из шести слоёв решений (21.08, 22.08, 22.08-2,
   23.08…), решения вшиты в пункты скобками «(решение NN.08, замещает…)»;
   рядом 4 промпта и 3 отчёта аудитов, которые каждый следующий
   аудитор обязан читать целиком (этот — прочитал: ~1500 строк).
   Предложение: **после утверждения Р1/Р2/Р4 роадмап переписывается
   начисто** — решения инкорпорируются в текст ADR-0003/0004 без
   археологических пометок; хронология слоёв остаётся в git-истории;
   аудит-файлы и промпты переезжают в `docs/audits/` с индексом
   «находка → статус (внесено/отклонено/отложено)» — дедупликация
   будущих аудитов по индексу, а не полным чтением.

Предлагаемая политика retention (одна страница, кандидат в ADR):

| Артефакт | Создаёт | Финал | Кто чистит |
|---|---|---|---|
| tasks/<id>/ (догфуд, done) | роли | остаются в git как история (решение design §6), но в рабочих контекстах не участвуют | — |
| tasks/<id>/ (killed, не в main) | роли | удаляются (реализовано) | cleanup |
| .artel/logs/* | agent_log | 90 дней или N последних задач → удалить (ADR: уточнение инварианта 16 «переживает задачу, не эпоху») | doctor, при старте |
| ветки task/* смерженные | разработчик | удалять при переходе в done | fsm/cmd_approve |
| worktree per-task | оркестратор | prune при done/killed | cleanup |
| журнал БД | store | не чистится (лёгкий); архив строк при disconnect (уже решено) | — |
| premod/alerts разобранные | оркестратор | старше 90 дней → архивная таблица | doctor |
| копилка К1 | роли | дистиллированное К2 удаляется из копилки в том же MR | К2 |
| память ассистента | ассистент | жёсткий потолок размера; ревизия = компакция до потолка | ревизия п.8 |
| roadmap-audit-*.md | аудиторы | docs/audits/ + индекс статусов | Оператор, разово |
| преамбула роадмапа | правки | переписать начисто после утверждения ADR | Оператор, разово |

## 7. Логика флоу (проверка замкнутости графа состояний)

Состояния Фазы 0 замкнуты (7 состояний + escalated/killed, все
переходы имеют владельца — сверено с fsm.py). Дыры появляются там,
где роадмап добавляет внешний контур текстом, не трогая FSM:

1. **Внешняя фаза target-human не имеет выписанной карты состояний.**
   Текст п.7/п.9 описывает протокол (Draft → приёмка → undraft →
   человек мержит → merge-событие → закрытие), но: из какого состояния
   FSM создаётся MR; чем является «наша приёмка» для target-human
   (acceptance? тогда merge_gate для таких задач не существует —
   а он в FSM есть и в gates.yaml тоже); где стоит задача между
   undraft и merge-событием (awaiting-human — оверлей design §6,
   в реализованной FSM его нет); куда возвращает external
   changes_requested — не определено нигде. Исполнитель C1/C2 будет
   изобретать состояния сам — свобода агента в несущей механике.
   (Смежные MN-2/MJ-2 v2 касались очереди лимита и снятого пост-merge
   окна — сама карта состояний внешнего флоу не выписывалась никем.)
2. **Два механизма спорят за переход «внешнее замечание → правка».**
   п.7: комментарии людей → «внешний changes_requested → **обычная
   итерация**» (т.е. через внутреннее ревью). п.9: «замечание-правка →
   итерация разработчика → **пуш** → 'исправлено в <sha>'» — ревьювера
   в цепочке нет. Пока действует премодерация, Оператор видит дифф
   перед пушем; премодерация снимается счётчиком чистых циклов — после
   этого по чтению п.9 правка уходит в боевой корп-MR вообще без
   единой содержательной проверки, кроме CI. Инвариант «код проходит
   ревью до людей» молча теряется на самом чувствительном канале.
   Нужна одна фраза-владелец: внешняя итерация = обычный цикл
   in_dev → review с external-счётчиком.
3. **`escalated_from` асимметричен.** Провал агента возвращает в свой
   шаг, но эскалация вердиктом ревьювера (`status: escalate` — «код
   прав, спека нет») возвращается approve'ом всегда в in_dev: вопрос
   был про SPEC, а перезапускается разработчик, для которого ответа
   в артефактах нет (см. А5). Цикл формально замкнут, содержательно —
   через ручную правку файлов Оператором, не описанную нигде.
4. **verify-профиль без носителя-состояния.** П.10: «verifying
   становится композитным циклом» — но состояния verifying в
   реализованной FSM нет (review → acceptance напрямую), B1b вводит
   «ожидание CI» без называния, где задача стоит; await-ci лежит в P3
   без привязки к фазе B. Рассинхрон gates.yaml↔FSM уже известен
   (v1 P4-5) — новое здесь: каталог типов проверок собирается вешать
   на состояние, которого не существует, и никакая задача фаз A–B
   его не создаёт.

## 8. Стек (по слоям; вердикт — как в классе Б)

Сравнение: (а) блайнд-дизайн фазы 1, (б) фактический стек репозитория
и решения роадмапа, включая отложенные (Postgres «по триггеру»,
ledger — отложен, Agent SDK — этап 3, FastAPI — ADR-0004).
Инфраструктура — вне рамок.

| Слой | Мой выбор (фаза 1) | Факт репо / роадмап | Вердикт | Цена смены: сейчас vs через две фазы |
|---|---|---|---|---|
| **Язык оркестратора** | не специфицировал (любой скриптовый с дешёвым subprocess/SQLite) | Python stdlib, ноль внешних зависимостей (design §11); ADR-0004 официально ломает zero-deps (FastAPI+WebSocket) на этапе 1 панели | **Подходит.** Один побочный дефект zero-deps уже материализовался: roles.yaml не читается кодом — ROLE_SKILLS продублирован в config.py руками («Фаза 0: без yaml-парсера»), т.е. декларативный конфиг и исполняемая правда живут в двух местах и разойдутся первой же правкой скилов ролей | сейчас: ~0 (yaml-парсер всё равно приходит с FastAPI-стеком); через две фазы: часы разбора «почему роль не получила скил» |

Для десятков задач с демоном C0 + панельным API + CLI (три писателя) SQLite в WAL ещё держит; триггер назван | сейчас: не менять; через две фазы: дамп-скрипт — заложен, цена признана стандартной |

A2b/3б/3и добавляют машинные поля (code_sha, built_at_sha, related, iteration, budget) — каждое новое поле в самодельном парсере — кандидат в тихий баг (значение с `#` или `:` молча усечётся, guard не заметит). Валидация значений (не только наличия) отсутствует | сейчас: ~час (настоящий YAML-парсер — одна зависимость или vendored, guard строже на типы); через две фазы: поля размножены по шаблонам всех целевых, миграция + охота на молчаливые усечения в живых артефактах |

Одно упущение стека: guard гоняется в CI и руками ролей, но НЕ оркестратором перед передачей — невалидный артефакт обнаруживается на чужом шаге, а не на своём; вызов guard в cmd_advance — строк десять | сейчас: ~0; через две фазы: policy-движок унаследует привычку «валидность проверяет потребитель» |
| **Интеграция с forge** | адаптер с идемпотентными операциями, check-before-create | Фаза 0: интеграции нет вовсе — merge локальным git в cmd_approve, **статус CI перед merge кодом не проверяется** (красный CI видит Оператор глазами — design §6; branch protection отсутствует — ADR-0001); роадмап: forge-адаптер B1b/C1, поллер C0, await-ci — P3 «вставкой» | **Недостаточен уже для текущей эпохи, план есть — приоритет занижен.** «Нельзя смержить с красным CI» — инвариант из README — сегодня держится только вниманием человека: guard-условие «CI зелёный» не кодировано нигде в merge-пути. Один GET к Actions API в cmd_approve (merge_gate) снимает человеческий фактор до всякого адаптера; await-ci из P3 — та же логика, но лежит «вставкой, когда свободен» | сейчас: ~20 строк + тест-инвариант; через две фазы: адаптер B1b всё равно это реализует, но окно «merge мимо красного CI по невнимательности» открыто все фазы A–B |

**Что упрётся первым при росте единицы → десятки задач, и заложен ли
пересмотр:**

1. **Модель исполнения оркестратора: однопроцессный CLI в сессии
   Оператора.** Каждый шаг живёт, пока открыт терминал; `auto` держит
   одну задачу; событий нет — всё дергается человеком. Это упрётся
   раньше SQLite и раньше токен-экономики: десятки задач физически
   не прокачиваются через один терминал part-time Оператора.
   Пересмотр в роадмапе ЕСТЬ (событийный оркестратор — этап 4
   ADR-0004, поллер C0, демон 3к), но его триггер — прогресс панели
   и фазы C, а не нагрузка: если поток задач вырастет раньше, чем
   панель дойдёт до этапа 4, момент пересмотра не сработает —
   привязать демонизацию к числу задач в неделю, а не к номеру этапа.
2. **SQLite при трёх писателях** (демон + API + CLI) — второй;
   пересмотр заложен образцово (3ж, триггер + дамп-скрипт).
3. **argv-транспорт промпта и полные пакеты в каждый прогон** —
   растут линейно с итерациями и размером брифов (см. слой запуска
   и раздел 5.1).
4. **Рукописный frontmatter-парсер** при размножении машинных полей
   (слой формата) — момент пересмотра в роадмапе не заложен нигде;
   единственный слой с непокрытым ростом, дешёвый в фиксе сейчас.

Гейты part-time Оператора упрутся раньше любого слоя стека, но это
процесс, не стек (разобрано в 5.3) — стеком не лечится.

## 9. Предложения главного инженера

1. **Приёмочные тесты до кода, залоченные от ветки задачи** (см. А1).
   Суть: критерии приёмки SPEC материализуются в исполняемый тест
   отдельной сессией до разработчика; CI (или guard в merge-пути
   оркестратора — protected-paths уже так работает) отклоняет ветку,
   меняющую файлы `tasks/<id>/acceptance/`. Заменяет/усиливает:
   единственный содержательный гейт «ревьювер+глаза Оператора»
   становится исполняемым; закрывает сговор dev↔reviewer. Цена:
   +1 агентский шаг на задачу (~$1–3), инвариант-тест. Риск: тесты
   по плохим критериям лочат ошибку — лечится тем, что лок снимает
   только Оператор (та же механика, что budget).
2. **Канарейка конвейера** (см. А2). Суть: 1–2 эталонные задачи
   с известным эталонным диффом; replay после правки скилов/шаблонов/
   пина CLI/смены модели; сравнение — дифф против эталона + зелёные
   гейты. Механика replay почти готова: брифы хэшируются в журнале
   (3е). Усиливает: К2 (правки скилов получают регрессионный тест),
   MJ-8-фикс (детект деградации, а не только изоляции). Цена: ~$2–5
   на прогон, по триггеру правок, не кроном. Риск: эталон стухает
   с эволюцией репо — держать канарейки на замороженном срезе.
3. **Первичка целевых — локальный git без remote** (см. Б1).
   Заменяет: пофайловый hash-контур A2b/A3-restore на commit-sha +
   `git fsck`; бэкап .artel/ становится бэкапом git-репозиториев
   (bundle — атомарен и проверяем). Цена: ~0 (git init в механике
   подключения проекта), doctor-проверка «remote пуст». Риск:
   минимальный; главный контраргумент («периметр по построению»)
   решается отсутствием origin.
4. **Батч вопросов с рекомендованным дефолтом** (см. Б3). Одна правка
   escalation-rules + формат карточки: все известные вопросы разом,
   каждый с вариантами и дефолтом «если молчишь про этот пункт —
   предлагаю X, но не делаю». Сокращает календарь эскалаций в N раз
   при лаге Оператора. Цена: строки в скиле. Риск: соблазн Оператора
   штамповать дефолты — но это его информированный выбор, дефолт
   виден.
5. **Дайджест-закрытие задачи.** На done оркестратор генерирует
   `RETRO.md` ≤30 строк (что сделано, итерации, стоимость,
   чему научились — поля из журнала, не LLM) — и именно он, а не
   полные артефакты, становится входом для «поиска прецедентов»
   (memory-access) и дистилляции К2. Полные артефакты остаются
   историей git, но перестают быть кандидатами в чужие контексты.
   Цена: ~30 строк кода. Риск: нет.

## 10. Совпало / независимо подтверждено / ложные тревоги

**Совпало (класс Г, подтверждение архитектуры):** детерминированный
FSM-оркестратор без LLM; артефакты-файлы как единственный интерфейс
ролей; структурный guard; числовые лимиты всех циклов + эскалация
Оператору после лимита; глобальные счётчики на задачу; жёсткий
денежный потолок с алертом 70% и подъёмом только Оператором; свежий
контекст ревьювера; молчание ≠ согласие, ноль токенов в ожидании;
идемпотентный шаг, чекпоинт = артефакт в git; журнал шагов всегда;
kill switch с уборкой; карта кодовой базы как кэш со сверкой свежести
(3б ≈ мой «кэш с меткой источника»); сборка контекста оркестратором
(ревью-пакет/бриф ≈ мой манифест); окружение роли определяет только
пульт (п.14 ≈ мой allowlist); песочница для чужого кода; контур
обучения с правками только через Оператора; счётчики доверия;
недоверенность внешнего входа (комментарии, чужие коммиты);
идемпотентность внешних операций; очередь мержей при параллелизме.

**Независимо подтверждено** (блайнд-дизайн переоткрыл известное —
сигнал системности, не новые находки):
- recovery-сверка состояния при старте (v1 B4 → внесено в A3);
- алерты как механизм с носителем, не слово (v2 MJ-3 → таблица alerts);
- программные пороги стоп-лосса (v2 MJ-9 → пороги 70/90%);
- пин версии рантайма агента (v2 MJ-8 → пин CLI + smoke);
- инкрементальное ревью и бриф разработчика (роадмап знает сам — P3);
- health-check поллера (v2 → C0).

**Ложные тревоги** (кандидаты, убитые самоопровержением):
1. «Merge неидемпотентен при падении между merge и push» — убита
   чтением fsm.py: состояние не переходит в done до успеха всех
   команд, повторный approve на смерженной ветке безвреден
   («Already up to date»).
2. «Гонка SQLite: поллер C0 + auto-сессия Оператора» — убита: записи
   короткие, один хост, WAL; рамка «параллелизм — Postgres по
   триггеру» (3ж) это явно покрывает.
3. «Guard без формальной JSON Schema — слабая валидация» — убита:
   regex-guard уже проверяет всё, что двигает FSM (тип, статус,
   секции); схема добавила бы строгость, не защиту.
4. «Нет таймаута задачи целиком» — убита: awaiting-состояния с нулевой
   стоимостью делают таймаут задачи малоинформативным; потолок денег +
   таймаут шага ограничивают худший случай, «застряла > X часов» —
   алерт наблюдаемости (design §7), а не переход.
5. «Аналитика надо вернуть немедленно» — убита в Б5: для тестовой
   эпохи SPEC руками Оператора дешевле; признано преимуществом
   роадмапа.

### Итоговая калибровка

Крупных архитектурных расхождений с роадмапом мой проект не дал —
несущая рама (FSM, артефакты, лимиты, гейты) совпала, что
подтверждает её. Дельты сосредоточены в трёх местах, где роадмап
решает по-человечески то, что агентно дешевле: контроль качества
доказательствами и исполнением вместо чтения (А1, Б6, канарейки);
git как готовая подсистема целостности вместо самописной (Б1);
календарь Оператора как главный дефицит (Б3, поток-3). Плюс два
системных пропуска: гигиена накопления (А4, раздел 6) и невыписанный
внешний FSM (раздел 7), оба дешевле чинить до фазы B, чем после.
