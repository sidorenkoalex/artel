# ТЗ: повторное использование итога полного прогона tests/ на гейтах пульта для того же дерева

Порядок: после группы 3 и после 01M46D5T8SZ9D6S34TZFX8S46V (один полный
прогон на машину).

Источник: 05.10, разбор скорости конвейера. Полный набор (~4400 тестов,
~10 мин на гейтах пульта под нагрузкой) гоняется на задачу около пяти раз,
часть прогонов — на том же содержимом дерева:
- автогейт приёмки красный → `approve` в acceptance (в том числе
  `--accept-red`) гоняет набор заново на том же коммите (часть 1 этапа 3
  01M45FJVGQ, 05.10);
- задача с приложениями PLAN: после 01M46C776S автогейт гоняет набор на
  дереве «ветка + приложения», гейт мержа — на «слияние с main +
  приложения»; если main не сдвинулся, содержимое совпадает.
Решение Оператора 05.10: сделать после группы 3, приоритет 2.

Факты (пин f7a46d84, сверка кода 05.10):
- Единственный вход полного прогона гейтов — `orchestrator/acceptance.py::
  full_suite` (~875) поверх `run_full_suite` (~668); исходы различает
  `_full_suite_outcome` (~622).
- Итог уже сохраняется: `_remember_gate_failures` (~855) пишет
  `save_failures(sha, …)` (~826) в `config.LOGS/fullsuite-results/<sha>.json`
  — ключ по sha коммита, только чистое дерево (`clean_tree_sha` ~842);
  читает только suite-run (`saved_failures` ~814) для прогона базы.
- Вызовы гейтов: автогейт `orchestrator/fsm_autogate.py` (~297), approve
  `orchestrator/fsm.py::_acceptance_full_suite_ok` (~1106), гейт мержа
  `orchestrator/fsm_merge_gate.py::_full_suite_or_refuse` (~879, на
  scratch-дереве с наложенными приложениями, без коммита).

Требуется:
1. Ключ итога — содержимое дерева (хеш дерева git, для scratch-дерева гейта
   мержа — с наложенными приложениями, через временный индекс) плюс
   отпечаток окружения прогона: версия Python, отпечаток установленных
   пакетов окружения пульта, команда прогона; запись хранит исход, итоговую
   строку pytest, упавшие и путь к логу.
2. Гейт (автогейт приёмки, approve в acceptance, гейт мержа) при найденном
   итоге с тем же ключом не моложе предела (константа config, решение SPEC)
   берёт его вместо прогона; журнал и detail говорят «итог прогона <время>,
   дерево <хеш>, лог <путь> — использован повторно». Исход гейта тот же,
   что при прогоне (зелёный / красный с теми же упавшими; `--accept-red`
   работает по повторному итогу).
3. Повторно используются только завершённые прогоны с итоговой строкой
   pytest на чистом дереве; таймаут, «прогон не начат», нет tests/ — не
   используются. Любое сомнение в ключе (git не ответил, окружение не
   определилось) — обычный прогон (fail-closed).
4. Оператор может принудить новый прогон (флаг approve, решение SPEC).
5. Прогоны `suite-run` роли в повторное использование гейтами не входят,
   пока suite-run идёт в окружении роли (строка бэклога «suite-run роли —
   в окружении пульта»).
6. Тесты в `tests/` с заявками «Ловит мутацию»: approve после автогейта на
   том же дереве не запускает прогон; изменение одного файла, другое
   окружение или истёкший срок — прогон идёт; гейт мержа узнаёт дерево
   автогейта при неизменном main; таймаут повторно не используется; флаг
   принудительного прогона. Существующие тесты не ослабляются.
