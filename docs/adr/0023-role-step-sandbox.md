## Решение

### 1. Граница — два круга, один механизм пульта

Песочницу ставит и проверяет пульт, а не клиент модели (решение
Оператора 30.09, `docs/backlog.md:417`). Кругов два:

- **Круг 1 — шаг роли целиком**: процесс клиента модели и всё, что он
  запускает. Цель — что бы ни сделал агент (в том числе по внедрённой в
  данные проекта инструкции), он не выходит за файловые корни задачи, не
  видит секреты Оператора и не ходит в сеть, кроме сервера модели.
- **Круг 2 — исполнение кода проекта**: установка зависимостей и все
  прогоны тестов. Строже круга 1: нет токена модели, нет сети у тестов,
  окружение собирается из профиля, а не копией окружения Оператора.

Обе границы задаёт один модуль пульта (`orchestrator/sandbox.py` —
рабочее имя): по параметрам (корни записи, запрещённое чтение, режим сети)
он строит профиль песочницы и оборачивает команду. Провайдеры и места
прогона тестов его только вызывают.

Действует для проектов с `sandbox: required` (пункт 9). Артель
(`sandbox: off`) до решения вопроса 2 остаётся на прежних путях запуска
шага и прогона тестов без изменений, включая обработку сигналов и
поведение при остановке пульта.

### 2. Круг 2 исполняет процесс пульта, а не потомок роли

Прогоны, которые роль запускает своими командами, сегодня — потомки шага
роли (см. «Контекст»). Внутри песочницы круга 1 они унаследовали бы её
профиль: дать кругу 2 то, чего нет у круга 1 (сеть к реестрам для
установки), нельзя, а наложить второй, более строгий профиль
`sandbox-exec` изнутри уже запертого процесса, по известным данным,
нельзя тоже — **[предположение]**, проба п.1.

Выбранная схема: **команда роли только кладёт запрос, прогон исполняет
исполнитель запросов — отдельный процесс пульта вне песочницы роли.**
Это вводит новый доверенный вход «данные роли → действия пульта»;
ниже — его граница.

**2.1. Канал и идентичность.** На каждый шаг пульт заводит свой каталог
запросов `.artel/logs/requests/<id задачи>/<номер шага>/` с подкаталогами
`in/` (роли на запись) и `out/` (роли только на чтение) и открывает его в
профиле круга 1 только этого шага. Идентичность задачи и шага исполнитель
берёт из того, в каком каталоге лежит запрос, а не из тела запроса. Схема
отложенного журнала (идентичность из тела, общий каталог машины) здесь
не используется (см. «Контекст»). Каталог шага закрывается и удаляется
на конце шага; беглый процесс прошлого шага запросы следующему подать не
может.

**2.2. Поля запроса.**

| Поле | Доверенное ли | Что сверяется |
|---|---|---|
| задача, шаг | да — из пути каталога запросов | каталог создан пультом для текущего шага; иначе запрос не читается |
| `command` | нет | закрытое перечисление: `plank-run`, `suite-run-start`, `suite-run-status`, `preflight`, `acceptance-dry-run`, `run-selected` |
| `targets` (только `run-selected`) | нет | строгая схема: список не длиннее потолка; каждый элемент — путь файла или идентификатор теста `путь::имя`, не начинается с `-`; `realpath` каждого пути (со всеми компонентами) лежит внутри рабочей копии; в argv идут после разделителя `--` |
| `run_id` (только `suite-run-status`) | нет | идентификатор, выданный исполнителем этому же шагу |
| любое другое поле | — | отказ запроса |

Параметров pytest, путей отчёта, окружения, рабочего каталога и команды
установки запрос не несёт: argv, окружение и рабочий каталог исполнитель
собирает из профиля. `workdir` профиля тоже проверяется по `realpath`:
символьная ссылка наружу из рабочей копии — отказ. Установка (`install`)
по запросу не запускается: исполнитель сам сравнивает хеш файла
блокировки с хешем последней установки и ставит зависимости только при
расхождении.

**2.3. Чтение запроса.** Файл открывается без следования символьным
ссылкам, только обычный файл, с потолком размера; формат — JSON со строгой
схемой, неизвестные поля — отказ. Содержимое запроса не вставляется ни в
тексты отказов, ни в результаты: иначе через подставленную ссылку роль
получила бы канал чтения файлов с правами пульта.

**2.4. Отчёт и вывод.** Отчёт JUnit XML пишется в каталог пульта вне
рабочей копии (входит в корни записи круга 2) и читается без следования
ссылкам. Вывод прогона идёт в файл с потолком размера, а не в память
пульта (сегодня `capture_output`, см. «Контекст»): прогон, печатающий
гигабайты, не должен уметь остановить пульт. В `out/` роль получает код
выхода, усечённый вывод и разобранный отчёт с потолком размера — без
путей и сообщений пульта вне рабочей копии и без эха запроса. Итог,
полученный так, остаётся итогом для роли и гейтом не принимается (как
сейчас, `docs/backlog.md:303`).

**2.5. Жизненный цикл.**
- Исполнитель — отдельный процесс пульта (не поток), запускается на шаг
  и держит lease шага вместе с ним. При смерти родителя-пульта или потере
  lease он снимает группы своих прогонов и завершается сам; новый шаг или
  гейт по этой задаче не стартует, пока не подтверждено, что прогоны
  прежнего исполнителя сняты.
- На конце шага по любой причине (успех, ошибка, таймаут 2700 с, `kill`,
  `pause --now`) прогоны по запросам снимаются, необработанные запросы
  удаляются, каталог запросов закрывается — до того, как гейты берут
  рабочую копию.
- В полёте не больше одного запроса на шаг; потолок числа запросов за
  шаг. Занятый замок полных прогонов машины (`suite_lock`) — немедленный
  отказ, как у `suite-run` сегодня, а не ожидание до таймаута шага.
- Полный набор асинхронный, как сегодня: `suite-run-start` возвращает
  `run_id` сразу, `suite-run-status` — состояние и итог. Остальные команды
  синхронные: заглушка команды роли ждёт файл результата в пределах
  таймаута вызова инструмента.

**2.6. Кэш зависимостей.** `UV_CACHE_DIR` и кэш npm — на задачу, в её
области, а не общий на проект: иначе кэш, отравленный прогоном одной
задачи (роль меняет `uv.lock` в своей ветке, `--frozen` сверяет хеши
именно из него), использовали бы прогоны других задач и гейты. Цена —
повторные загрузки; если окажется дорого, общий кэш — только решением
Оператора (вопрос 11).

Отклонённая альтернатива: «круг 2 для вызовов из роли = круг 1 с
урезанным окружением» — тесты шли бы в одной песочнице с токеном модели,
а установка без сети к реестрам не работала бы. Остаётся запасным путём
только как записанное принятое отличие (вопрос 4).

### 3. Файловая система

Круг 1:
- запись — рабочая копия задачи (кроме файла `.git` в её корне — запись
  в него запрещена по точному пути), каталог документов задачи, каталог
  запросов шага, временный каталог шага (свой `TMPDIR`) и рабочие
  подкаталоги клиента модели в доме роли (журналы сессий и т.п.; точный
  перечень — проба);
- в доме роли только для чтения: `settings.json`, `CLAUDE.md` — шаг не
  может переписать свои же запреты для следующих шагов;
- в каталоге `.git` общего клона — только то, что нужно коммиту:
  `objects/`, ссылка ветки задачи (`refs/heads/task/<id>-…`) и её
  журнал в `logs/`; в `worktrees/<id>/` — только перечисленные файлы
  коммита (`HEAD`, `index`, `index.lock`, `ORIG_HEAD`, `COMMIT_EDITMSG`,
  `logs/`; точный перечень — проба п.8). Запись в `config`, `hooks/`,
  `info/`, ссылки других веток, `refs/artifacts/`, а в
  `worktrees/<id>/` — в `commondir`, `gitdir`, `config.worktree`
  запрещена. Причина: подменив `commondir`, строку `gitdir:` файла `.git`
  рабочей копии или конфигурацию, роль перенаправила бы git пульта на
  свою конфигурацию (`core.fsmonitor`, фильтры, `diff.external`,
  `core.pager`, `credential.helper`, псевдонимы), и пульт исполнил бы её
  код вне песочницы;
- git-вызовы пульта в области проекта с `sandbox: required` идут с явными
  `GIT_DIR` и `GIT_COMMON_DIR` (и рабочим каталогом), а перед ними пульт
  сверяет: файл `.git` рабочей копии и `commondir` указывают на ожидаемые
  пути, а `worktrees/<id>/HEAD` — символьная ссылка на ветку этой задачи.
  Роль вправе писать `HEAD` (он нужен коммиту), а пульт коммитит и пушит
  ветку, на которую указывает `HEAD`; полагаться только на хуки защиты
  `main` нельзя. Ожидаемые пути и имя ветки берутся из БД пульта
  (записываются при создании рабочей копии и ветки задачи), а не из файлов
  рабочей копии. Расхождение — отказ и инцидент. Хуки — по-прежнему пина
  (`core.hooksPath` клона, `workspace.py:14`, `:68-75`). Это делается
  отдельной функцией области внешнего проекта, а не правкой общего
  `gitcmd.in_repo`: тот передаёт `-C <репо>` позиционным аргументом, чтобы
  не ломать заглушки тестов (`gitcmd.py:232-243`);
- общий клон остаётся общим: ссылки других задач защищены запретом
  записи выше; объекты `objects/` общие — мусорные объекты одной задачи
  видны другим, вредного действия, кроме роста объёма, нет — принимается;
- внутри `.artel/` главной копии запись запрещена целиком, кроме
  перечисленных подкаталогов (порядок правил профиля — проба п.9);
- главная копия пульта (пин) — только чтение; БД и `.artel/logs` — только
  чтение (чтение БД в режиме WAL без права записи — проба п.10);
- чтение по умолчанию запрещено во всём домашнем каталоге Оператора,
  кроме явно разрешённого: дом роли, главная копия пульта, область своего
  проекта, каталоги инструментов. Закрыты `~/.ssh`, `~/.config/gh`,
  `~/.claude` и `~/.codex` Оператора, `~/Library/Keychains`,
  `~/.artel-canary`, области других проектов. Область своего проекта
  открыта на чтение целиком — документы и рабочие копии других задач того
  же проекта, клон со всеми ссылками; это принятое отличие (вопрос 13);
- обращение к службе связки ключей запрещено на уровне песочницы (а не
  только запуск `security` и `git-credential-osxkeychain` по пути).
  Клиенту Claude связка ключей не нужна — токен приходит переменной
  окружения (`providers/claude.py:199-203`). Не ломает ли запрет проверку
  сертификатов TLS — проба п.5.

Круг 2 (исполнитель пульта и гейты): запись — рабочая копия (или
временная копия для прогона базы) с теми же исключениями, что в круге 1:
файл `.git` в корне рабочей копии и весь каталог `.git` клона, включая
`worktrees/<id>/`, кругу 2 на запись закрыты целиком (прогону тестов git
не нужен, а исполняет он тот же недоверенный код — тесты, `conftest.py`,
плагины); свой временный каталог; каталог отчёта и вывода прогона вне
рабочей копии (пункт 2.4); кэш зависимостей задачи (пункт 2.6). Чтение —
как в круге 1 минус дом роли. Сверка `.git`, `commondir` и `HEAD` перед
git-операциями пульта действует и после прогонов круга 2.

### 4. Сеть

Песочница ОС на macOS не умеет фильтровать по имени хоста
(**[предположение]**, проба), поэтому вся исходящая сеть из песочницы
запрещена, кроме локального порта прокси пульта; прокси пропускает только
хосты из белого списка и пишет отказы в журнал задачи.

| Кто | Разрешено |
|---|---|
| Круг 1, роль на Claude | хосты API модели Anthropic; служебный трафик клиента выключен переменной окружения |
| Круг 1, роль на Codex | не входит в B3 (пункт 5, вопрос 5) |
| Круг 1, GitHub | закрыт: пушит пульт (см. «Контекст») |
| Круг 2, установка зависимостей | только реестры пакетов профиля (для sled: `pypi.org`, `files.pythonhosted.org`); загрузка интерпретатора менеджером пакетов запрещена — Python 3.12 должен быть на машине заранее (проба п.6) |
| Круг 2, тесты | без внешней сети; локальный интерфейс разрешён, но песочница различает порты, а не процессы — это доступ к любому локальному порту машины (локальные базы, демоны разработки Оператора); сокеты Unix запрещены целиком; перечень открытых локальных портов — проба п.13; тестам sled без PostgreSQL локальная сеть не нужна |

### 5. Секреты

- Круг 2 не получает ни одного секрета: окружение = переменные профиля +
  минимальный набор (`PATH` инструментов проекта, `HOME` — отдельный
  каталог проекта, `TMPDIR`, `LANG`/`LC_*`, `PYTHONPYCACHEPREFIX` на свежий
  временный каталог — тот же рубеж против устаревшего байткода, что у
  артели, `acceptance.py:68-89`). Копия окружения Оператора
  (`dict(os.environ)`) не используется. Обращение к службе связки ключей
  запрещено.
- Круг 1 на Claude несёт только токен подписки Claude, как сейчас. Код,
  запущенный агентом, может его прочитать и вынести на разрешённые
  серверы — в том числе на сервер модели под чужим ключом (например, в
  хранилище файлов чужой учётной записи). Это остаточный канал, а не
  закрытый рубеж; принимается. В штатной работе агент код проекта не
  запускает: тесты идут через запросы к исполнителю пульта (пункты 2, 8).
- Круг 1 на Claude: токена GitHub нет ни в окружении, ни через связку
  ключей. Риск №24 (общий токен пульта) не переоткрывается — он про
  токен, которым пушит пульт.
- **Codex на проектах с `sandbox: required` в B3 не исполняется.** Вход
  Codex хранится в системной связке ключей (`keyring`,
  `providers/codex.py:202-209`); клиенту нужен доступ к её службе, и код,
  запущенный агентом, мог бы обратиться к ней напрямую и, возможно,
  получить другие записи Оператора (учётные данные GitHub от
  `osxkeychain`) — **[предположение]**, проба п.3. Отказ проверяется не
  только на шаге роли, но и раньше: при заведении задачи с набором
  моделей (`new --set`) и при выборе провайдера роли для такого проекта —
  чтобы задача не дошла до середины конвейера (наборы `codex-dev`,
  `codex-all` в `model_sets.yaml:12`, `:17`). Снятие отказа — вопрос 5.
- Окружение шага роли: белый список манифеста (`stack.py:311-337`)
  расширяется только названными именами, которые ставит сам пульт
  (`HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`, переменная выключения
  служебного трафика клиента); `TMPDIR` уже в списке. Вычитание секретов
  чужих провайдеров (`runner.py:1032-1048`) не меняется. Правка манифеста
  идёт вместе со стражем таблицы паритета (`tests/test_stack_parity_table.py`).

### 6. Процесс и лимиты

- Таймауты — прежние: шаг 2700 с, прогоны — по профилю и константам
  пульта. По истечении снимается вся группа процессов: в круге 1 — как
  сейчас (`runner.py:74-92`); в круге 2 — единая функция исполнения кода
  проекта запускает прогон в собственном сеансе и снимает группу
  (`os.killpg`) по таймауту и на любом исключении, сохраняя обработку,
  которая уже есть у полного набора (`acceptance.py:1334-1337`,
  `:1388-1391`). Функция действует только для `sandbox: required`;
  артель остаётся на прежних путях (пункт 1). Сохраняет ли `sandbox-exec`
  pid и группу — проба п.7.
- Ограничений памяти, процессора и числа процессов этот механизм не даёт;
  ограничения ресурсов процесса ОС в решение не входят (число процессов
  на macOS считается по пользователю, размер — по одному файлу) — только
  проба п.12 и вопрос 8. Держит лимит времени.
- Беглые процессы роли: процесс, ушедший из группы шага (`setsid`),
  переживает шаг и может писать в рабочую копию, пока гейт её читает.
  Песочница этого не лечит (профиль наследуется, но процесс жив). В B3-2
  — проверка после шага: процессов с профилем круга 1 этой задачи не
  осталось, иначе снятие и отказ гейта с инцидентом; если надёжно
  отличить такие процессы не удастся — остаточный риск (вопрос 12).

### 7. Механизм — песочница ОС macOS (`sandbox-exec`) за интерфейсом пульта

Выбран вариант 1 (раздел «Рассмотренные варианты»). Интерфейс модуля
песочницы не зависит от механизма: контейнер или удалённый исполнитель
позже заменяют реализацию, а не места вызова.

### 8. Код проекта агент запускает только через команды пульта

Для проекта с `sandbox: required` роль на Claude получает белый список
инструментов без общего `python3`: `git`, сценарии пульта из пина по
полному пути и команды пульта, которые кладут запрос исполнителю
(`plank-run`, `suite-run`, `preflight`, `acceptance-dry-run` и новая
команда прогона указанных файлов или тестов проекта — без неё у
разработчика нет способа запустить отдельный тест). Белый список
инструментов — не граница (`docs/stack.md:541`): например,
`git -c core.fsmonitor=…` или `git -c alias.…` исполняют произвольную
команду. Граница — круг 1. Список нужен, чтобы роль **в штатной работе**
не исполняла код проекта рядом с токеном модели; обход списка агентом
остаётся внутри круга 1.

### 9. Отказ при недоступности и поле `sandbox`

- Проект с `sandbox: required` без работающей песочницы не исполняется:
  нет `sandbox-exec`, не поднялся прокси или исполнитель запросов, красная
  проба `doctor` — шаг и прогон отказывают с названной причиной (ADR-0002,
  fail-closed).
- Поле записи проекта `sandbox` — необязательное, вне `FIELDS` (все поля
  `FIELDS` обязательны, `targets.py:99-101`); отсутствие означает
  `required` для любого проекта, без исключения по имени (развилки по
  имени проекта ADR-0021 п.8 велит удалять). Значение вне
  `required | off` — отказ проверки с названием записи и поля.
- Запись артели получает `sandbox: off` явной правкой Оператора
  (`targets.yaml` — защищённый путь). Лишнее поле сегодня проверкой не
  отвергается (см. «Контекст»), поэтому строку можно внести заранее, до
  B3, — безопаснее, чем перед самым мержем. Для `sandbox: off` проба
  песочницы не выполняется и запуск пульта не блокирует.

| Подполе | Смысл | По умолчанию |
|---|---|---|
| `runner` | `pult-pytest` — сегодняшнее поведение (интерпретатор venv пульта, таймаут отдельного теста, параллель); `pytest-own` — pytest проекта его собственной командой: без интерпретатора, таймаута и параллели пульта; гейты по-прежнему дописывают свои аргументы pytest (`--collect-only -q`, `--junitxml`, `-o junit_logging=system-out`), а также `-p no:cacheprovider`; `PYTHONPYCACHEPREFIX` ставится в окружение | `pult-pytest` |
| `workdir` | рабочий каталог прогона относительно корня репозитория | корень |
| `env` | переменные окружения прогона, блочное отображение (только тестовые значения) | пусто |
| `install` | команда установки зависимостей (подполе уже есть); теперь исполняется в круге 2 перед прогоном, если изменился файл блокировки | пусто |
| `install_hosts` | хосты, разрешённые установке | пусто — установка без сети |
| `full_suite_timeout_sec` | предел полного прогона (подполе уже есть) | константа пульта |

Подполе `report_arg` из первой редакции снято: аргумент отчёта у pytest
один (`--junitxml`), его собирает пульт для обоих видов `runner`.

Схема (`orchestrator/targets.py`):
- `runner`, `workdir`, `env`, `install_hosts` — в `PROFILE_FIELDS` и
  `PROFILE_OPTIONAL` (`targets.py:39-51`); иначе проверка отвергнет их как
  неизвестные (`:127-128`). Профиль артели без новых подполей остаётся
  правильным;
- `env` — новый вид значения `mapping` в проверке профиля: вложенное
  блочное отображение строк. `yamlmini` его уже разбирает
  (`yamlmini.py:9-15`) и не меняется — потоковые отображения `{…}` не
  вводятся (`yamlmini` читают также frontmatter и `scripts/guard.py`);
- проверка запрещает в `env` имена из точного перечня: секреты всех
  провайдеров (`secret_env_names`), `GITHUB_TOKEN`, `GH_TOKEN`. Не по
  подстроке: иначе тестовое `JWT__SECRET` было бы отвергнуто.

Полный набор при `runner: pytest-own`: `run_full_suite` меняется —
каталог набора берётся из `workdir` и `long_lived_dir`, а не жёстко
`<корень>/tests`; `-n … -p xdist` (`acceptance.py:1172-1177`) не
дописывается. `suite-run`, `plank-run`, `preflight`,
`acceptance-dry-run` и приёмка берут команду профиля и `workdir`. Один
источник команды профиля для приёмки (`acceptance_suite`,
`fsm_autogate.py:326-328`, `fsm.py:1207-1209`) и гейта мержа — строка
бэклога 07.10 (`docs/backlog.md:110`) — входит в B3 как предусловие
критерия 12.

## Что входит в B3

Две задачи, вторую допустимо делить ещё на две (вопрос 6).

**Шаг 0 обеих задач — закрепление поведения артели тестами до правки:**
(а) у артели `acceptance.run` и `run_plank` идут через `subprocess.run`
без собственного сеанса; (б) предел полного прогона приёмки артели
прежний — меняется только источник команды профиля, а не предел (у
артели `full_suite_timeout_sec: 1500`, `targets.yaml:44`); (в) в
окружении шага роли артели имена прокси не выставляются.

**B3-1. Круг 2 и профиль** (пульт и гейты, без шага роли):
1. Модуль песочницы: профиль из параметров, обёртка команды, локальный
   прокси с белым списком и записью отказов в журнал.

   сеанс, снятие группы по таймауту и исключению, чистое окружение с
   `PYTHONPYCACHEPREFIX`, вывод в файл с потолком, отчёт в каталог пульта

   кругом 2 в `.git` рабочей копии и клона. Проверка `sandbox: required` —
   первое условие внутри каждой общей функции (`acceptance.run`,
   `collect`, `run_repeat`, `run_plank`, три пути полного набора); иначе —
   прежний код без изменений. Вызывающие (`pull.py`, `notes.py`,
   `amend.py`, гейты) правок не требуют.
3. Профиль: подполя `runner`, `workdir`, `env`, `install_hosts`; вид

## Критерии приёмки B3

1. Команда шага Claude для проекта с `sandbox: required` собирается только
   с обёрткой песочницы (офлайн-проверка `doctor`). Шаг на Codex, `new
   --set` с набором, назначающим роли Codex, и выбор Codex провайдером роли
   для такого проекта отказывают с названной причиной.
2. Из шага и из прогона круга 2 запись вне разрешённых корней отказана
   ОС: главная копия пульта, `~/`, `.artel/state.db`, `settings.json` дома
   роли, `config` и `hooks/` клона, ссылка ветки другой задачи, файл `.git`
   рабочей копии, `worktrees/<id>/commondir`, `gitdir`, `config.worktree`
   (круг 2 — весь `.git` клона, включая `worktrees/<id>/HEAD`). `git
   commit` в рабочей копии задачи из шага проходит.
3. После шага или прогона круга 2, в которых проба пыталась подменить
   `commondir`, строку `gitdir:` файла `.git`, `HEAD` рабочей копии
   (`ref: refs/heads/main`) или конфигурацию клона, git-операция пульта
   не исполняет ничего, кроме хуков пина, и не коммитит и не пушит другую
   ветку: подмена либо не записалась, либо обнаружена сверкой с
   ожидаемыми значениями из БД и дала отказ с инцидентом.
4. Чтение `~/.ssh`, `~/.config/gh`, `~/.claude` Оператора,
   `~/.artel-canary`, `~/Library/Keychains`, области другого проекта из
   шага и из прогона круга 2 отказано.
5. Из шага Claude и из прогона круга 2 `git credential fill` для
   `github.com`, `security find-generic-password` и прямое обращение к
   службе связки ключей не возвращают секрет.
6. Запрос к неразрешённому хосту из шага и из прогона круга 2 отказан,
   отказ записан в журнал задачи; запрос клиента модели к своему серверу
   проходит; установка достигает только `install_hosts`; подключение
   прогона к сокету Unix отказано.
7. Прогон круга 2 — потомок исполнителя или процесса пульта, а не шага
   роли (сверка родителя). Его окружение не содержит ни одного имени из
   секретов всех провайдеров, `GITHUB_TOKEN`, `GH_TOKEN` и ни одной
   переменной Оператора вне набора пункта 5; в нём есть
   `PYTHONPYCACHEPREFIX` на свежий каталог, команда несёт
   `-p no:cacheprovider`.
8. Исполнитель запросов: идентичность — только из каталога шага (запрос с
   чужим `task_id` в теле, положенный в свой каталог, исполняется от
   своей задачи или отказан как неизвестное поле); запрос в каталоге
   прошлого шага не читается; команда вне перечня, неизвестное поле,
   параметр, начинающийся с `-`, путь, `realpath` которого вне рабочей
   копии, — отказ; файл запроса — символьная ссылка, не обычный файл или
   больше потолка — отказ без эха содержимого; `install` по запросу не
   запускается; результат прогона по запросу гейтом не принимается.
9. Подмены символьными ссылками: на месте отчёта, на месте `workdir`, на
   месте тестового файла, на месте файла запроса — ни одна не даёт роли
   содержимое файла вне рабочей копии в `out/`.
10. Вывод прогона больше потолка обрезается в файле; память процесса
    пульта не растёт с размером вывода.
11. Жизненный цикл: после смерти процесса пульта (сигнал `KILL`) и после
    потери lease прогонов-сирот исполнителя нет; после конца шага по
    любой причине прогонов по запросам нет и каталог запросов шага
    закрыт до того, как гейт берёт рабочую копию; второй запрос в полёте
    и запрос сверх потолка за шаг — отказ; занятый замок полных прогонов
    машины — немедленный отказ.
12. Страж: вызовы `subprocess` в `acceptance.py` и модулях пульта,
    исполняющие код проекта, — только из перечня допустимых мест (единая
    функция круга 2 и прежние пути артели); новый вызов вне перечня
    красит набор.
13. Песочница, прокси или исполнитель недоступны, проба красная — шаг и
    прогон проекта с `sandbox: required` отказывают с названной причиной.
    Запись без поля `sandbox` ведёт себя как `required`; значение вне
    `required | off` — отказ проверки с названием записи и поля.
14. По таймауту и на исключении снимается вся группа процессов — шага и
    каждого прогона круга 2.
15. `runner: pytest-own` на sled: установка проходит; backend-тесты
    проходят без сети; приёмка и гейт мержа идут командой профиля из
    одного источника и читают отчёт JUnit XML; полный набор берёт каталог
    из профиля и идёт без параллели.
16. Гейты неослабления тестов, «Ловит мутацию», долгоживущие файлы и
    выкладка планки при `workdir: backend` и `long_lived_dir:
    backend/tests` дают тот же результат, что для `tests/` артели.
17. Поведение артели не меняется, и это закреплено тестами шага 0 до
    правки: `acceptance.run`/`run_plank` артели — `subprocess.run` без
    собственного сеанса; предел полного прогона приёмки артели прежний;
    имена прокси в окружении шага артели не выставляются; запись артели с
    `sandbox: off`; существующие тесты и канарейка зелёные.
18. Живая проверка на клоне sled при Операторе: шаг developer на учебной
    задаче, коммит, прогон выбранного теста по запросу, полный прогон
    через «запустить → состояние»; в журнале нет неожиданных отказов
    песочницы.

Оператора. Для sled локальная сеть тестам не нужна — **[предположение]**
по ADR п.4, подтверждает критерий 15.

Критерий приёмки 6 дополняется: «подключение прогона тестов круга 2 к
локальному порту, включая порт прокси, отказано».

### В. Python для круга 2 — каталог интерпретаторов uv, только чтение

Проба п.6: Python 3.12 на машине есть только в каталоге интерпретаторов
uv дома Оператора (`~/.local/share/uv/python`); Python Homebrew uv
отвергает (особенность машины, не песочницы). Решение: этот каталог —
каталог инструментов пункта 3 для круга 2, только чтение, вместе с
метаданными каталогов-предков; окружение установки и тестов получает
`UV_PYTHON_INSTALL_DIR` на него и `UV_PYTHON_DOWNLOADS=never`. Загрузку
интерпретатора закрывают два рубежа (проба п.6, 5а и 5б). Кругу 1 этот
каталог не открывается: клиенту модели он не нужен.

### Г. `.git` клона: `objects/info/alternates` закрыт, `AUTO_MERGE` — нет

Проба п.8: перечень записи пункта 3 (точный — протокол, «Перечень
записи в `.git`») достаточен для коммита. Решение: запись
`objects/info/alternates` закрыта точечным запретом по точному пути
поверх разрешения `objects/` — иначе роль расширяет поиск объектов git
пульта на чужой каталог. Остальной `objects/info/` не закрывается
(туда пишут `commit-graph` и `packs`). Порядок правил «позднее
сильнее» проверен пробой п.9 на `.artel`; на `.git` — **[предположение]**,
проверяет критерий 20. Запись `worktrees/<id>/AUTO_MERGE` и `.lock` не
открывается: ошибка git в выводе коммита принимается (коммит проходит,
`rc=0`). Проверен только коммит; слияние, перебазирование и
`cherry-pick` из круга 1 пробой не проверялись.

Новый критерий приёмки 20 (B3-2): из шага круга 1 запись
`objects/info/alternates` клона отказана, коммит проходит.

### Д. Читающие команды роли из круга 1 — отказ

Проба п.10: под запретом записи в каталог БД читающие команды работают,
только пока существуют файлы `-wal` и `-shm`; без них — «unable to open
database file». Решение: для проекта с `sandbox: required` все команды,
которые `_role_allowed_command` (`orchestrator/artel.py`) разрешает роли
и которые открывают БД пульта, из круга 1 отказывают с названной
причиной; команды-запросы пункта 2.2 (`plank-run`, `suite-run`,
`preflight`, `acceptance-dry-run`, прогон выбранных тестов) идут через
исполнитель, как прежде. Перечень `command` пункта 2.2 этой поправкой
не расширяется. Если SPEC B3-2 найдёт, что роли нужна какая-то читающая
команда, — эскалация Оператору (расширение доверенного входа — отдельное
решение с проверками критерия 8). Чтение БД и `.artel/logs` кругом 1 по

## Поправка 16.10.2026: механизм — контейнер Docker

Решение Оператора 16.10.2026 («этап 0 — ок»; план перехода на Docker,
ассистентская сессия 16.10.2026). Приоритет — запуск конвейера на внешнем
проекте, а не предельная изоляция.

Основание:
- проба 13.10 (`docs/research/2026-10-sandbox-probe.md`) показала, что
  собственный профиль `sandbox-exec` приходится закрывать по одной щели:
  выход через службу запуска программ (п.1б), доступ тестов к любым
  локальным портам, включая прокси (п.13), неналожение собственной
  песочницы Codex (п.3); механизм не документирован и помечен Apple
  устаревшим;
- подготовка 14–15.10 по задаче 01M4XVM49PP5WHSXT5S8JW85WN (ADR-0025,
  `docs/research/live-suite-stand.md`) ушла в доказательство вложенных
  песочниц клиентов на macOS и Linux; для подключения sled это не
  требуется;
- доводы против контейнера в «Рассмотренных вариантах» снимаются:
  рабочая копия монтируется по тому же абсолютному пути; вход Codex через
  связку ключей не нужен — Codex на внешних проектах и так не работает
  (пункт 5); медленные смонтированные каталоги для тестов sled терпимы;
  Docker Desktop 28.4 на машине Оператора работает.

Что поправка меняет в тексте выше (остальное — без изменений, если не
противоречит этому разделу):

1. Пункт 7: механизм — контейнер Docker (вариант 2), а не `sandbox-exec`.
   Интерфейс модуля песочницы прежний: меняется реализация, а не места
   вызова. Зависимость пульта от запущенного Docker Desktop принимается;
   для проекта с `sandbox: required` недоступность Docker — отказ по
   пункту 9.
2. Граница изоляции — контейнер. Песочницы клиентов модели внутри
   контейнера не требуются и не доказываются.
3. Круг 2 (код проекта, который запускает пульт): каждый запуск —
   одноразовый контейнер. Сеть отключена; рабочая копия смонтирована по
   тому же абсолютному пути на запись; `.git` клона — только на чтение;
   окружение — только переменные профиля; лимиты памяти и процессора;
   по таймауту контейнер останавливается по имени. Установка зависимостей
   — отдельный одноразовый контейнер с сетью, только при изменении файла
   блокировки; кэш пакетов — в томе проекта.
4. Инфраструктура проекта (базы данных, очереди) — стенд docker compose на
   задачу. Описание стенда хранит пульт в области проекта
   (`.artel/projects/<имя>/`), а не проект; сеть без выхода наружу; порты
   на хост не публикуются; данные во временной памяти; стенд сносится при
   мерже, ликвидации и таймауте задачи. Интеграционные тесты с PostgreSQL
   входят в объём: исключение «тесты с PostgreSQL» из раздела «Что входит
   в B3» снимается.
5. В контейнеры не передаются токен хостинга, сокет Docker, `~/.ssh`,
   связка ключей и переменные окружения Оператора. git, push, БД пульта и
   гейты работают только на хосте.
6. Круг 1 (шаг роли) на первом этапе остаётся на хосте с двумя мерами для
   проектов с `sandbox: required`: из белого списка инструментов роли
   убирается `Bash(python3:*)` — код проекта запускается только командами
   пульта; в окружение роли добавляется `GIT_CONFIG_NOSYSTEM=1`.
   Остаточный риск принят Оператором до задачи «шаг роли в контейнере».
7. Отменяются: профили `sandbox-exec`, прокси с белым списком хостов,
   исполнитель запросов роли (пункт 2 в части канала роли; B3-2 пп. 6–7)
   и критерии приёмки, относящиеся только к `sandbox-exec`; критерии
   задач уточняются в их ТЗ. Отказ Codex на внешних проектах (пункт 5)
   сохраняется.
8. Модель угроз для sled: доверенный код Оператора; защищаемся от ошибки
   или инъекции агента, а не от целенаправленного выхода из контейнера.
9. Риск общего токена ролей (`docs/triggers.md` №24) принят до первой
   задачи на sled при условии `merge_gate: operator` в записи sled.

Задачи вместо B3-1 и B3-2 (рамки — в `docs/roadmap.md`, фаза B):
- D1а — круг 2 в одном контейнере: модуль песочницы, обёртка всех мест

- D1б — стенд docker compose на задачу (пункт 4);

Последствия:

## Поправка 16.10.2026 (вторая): до D1а — внешний доверенный проект без песочницы

Решение Оператора 16.10.2026 («можно пока вообще без докера» — «ок»).

инъекции агента) это допускает. SPEC D1а сохраняется на гейте SPEC без
одобрения и без ликвидации — к нему возвращаемся при первом недоверенном

Что поправка меняет до мержа задач D1а (остальное — без изменений):

1. Внешний доверенный проект подключается с `sandbox: off`: код и тесты

5. Остаточный риск, принятый Оператором: агент роли и тесты sled имеют
