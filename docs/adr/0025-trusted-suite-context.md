# ADR-0025: Подготовка доверенного канала process/lease для suite-run

Статус: принято исследование и пересмотр, выпуск не согласован. Дата: 14.10.2026. Решение Оператора: «готовь расширение доверенного канала и пересмотр ADR/SPEC», без ослабления проверок и лимитов. Дополняет ADR-0024: разрешена подготовка узкого нового канала; прежний запрет нового full developer и все защитные свойства разрешённых маршрутов сохраняются. Исполнение исследовательского этапа относится к задаче 01M4XVM49PP5WHSXT5S8JW85WN, без повышения действующего потолка $45.

## Решение и границы этапа

Разрешена подготовка broker в процессе пульта вне песочницы роли, аутентификация kernel peer PID и связь цепочки родителей со стартовой ролью/идентичностью живого lease. Адрес сокета, ENV, HOME и доступный роли файл не считаются удостоверением. Общая песочница, запрет ps внутри роли, гейты, таймауты, существующие проверки и рамка расходов не изменяются. Не обещать глобальную OS-изоляцию или защиту от произвольной same-UID атаки вне действующего периметра.

До продуктовой реализации необходимы реальные capability-проверки Codex/Claude и macOS/Linux в существующих правах, обновлённый SPEC, аудит и новый гейт SPEC. Недоступность канала не легализуется skip/xfail, fallback на ENV/PGID или расширением sandbox.

Политика UNKNOWN/IPC outage при наличии активных lease пока НЕ принята: рекомендован именованный инфраструктурный отказ нового full без побочных эффектов, при сохранении чтения status/wait и разрешённого failed. Это новая граница доступности операторского full при сбое канала; требуется явное решение Оператора до фиксации SPEC/выпуска. Принятое исследование само по себе этого решения не заменяет.

## Проверка на машине Оператора

Синтетический ограниченный опыт /tmp/artel-task-drafts/suite-broker-macos-probe.py завершился exit0: LOCAL_PEERPID совпал с PID клиента, клиент работал в другой сессии, libproc дал PPID/start-time и цепочку до broker через промежуточный процесс. Источники констант/структуры — установленный SDK macOS sys/un.h, sys/proc_info.h, libproc.h. Это опыт вне песочницы роли, а не доказательство доступности socket реальному Codex/Claude или Linux. Временные socket/процессы убраны.

## Доказанные факты

- runner.py:74–92 запускает агента собственной сессией; :1570–1583 сохраняет его pgid. _spawn_and_wait ожидает агента в процессе пульта (:1510–1630): здесь можно разместить broker-поток вне песочницы агента без отдельного демона и новой службы.
- role_env (:964–1047) передаёт окружение обоим провайдерам; это канал доставки адреса, не удостоверение PID/роли.
- providers/codex.py:410–439 уже открывает suite_lock.directory() через --add-dir. Это подтверждает доступ к файловому каталогу, НЕ разрешение AF_UNIX connect. Для сокета никакого нового add-dir/права сети не предлагается.
- liveness.py:94–112 при отказе ps подтверждает лишь существование группы. Цепочку родителей не предоставляет.
- PLAN живого шага фиксирует новую сессию инструментальной оболочки и её промежуточный PPID; это данные разработчика, независимо здесь не воспроизведённые.
- Linux AF_UNIX SO_PEERCRED предоставляет PID/UID/GID подключившегося процесса; Apple XNU un.h объявляет LOCAL_PEERPID/LOCAL_PEERCRED, proc_info.h содержит PPID и время старта. Наличие API подтверждено первичными источниками; доступность в конкретных средах не проверена.

Источники: [Linux unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), [Apple un.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/un.h), [Apple proc_info.h](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/proc_info.h).

## Один предлагаемый маршрут

1. Перед spawn runner запускает в своём процессе короткоживущий AF_UNIX SOCK_STREAM broker-поток. Он обслуживает только запрос «какому активному шагу принадлежит вызывающий suite-run»; никаких выполнения команд, запуска тестов или выдачи мандатов. После spawn связывает активную регистрацию с точной ролью аргумента runner, task_id, идентичностью lease и PID+временем старта агента. До регистрации агентного PID ответы только NOT_READY, никогда разрешение.
2. Endpoint помещается в уже разрешённый suite-run каталог; короткое имя вычисляется из канонического пульта и pid владельца lease (учесть предел sun_path). Discovery — чтение существующей БД mode=ro и перечисление живых локальных lease; ARTEL_TASK/HOME/переменные адреса могут ускорять поиск, но не определяют решение и не исключают остальных lease. Для гарантии при снятии маркеров нельзя делать ENV обязательным каналом discovery.
3. Публичный cmd_suite_run открывает соединение непосредственно из своего Python-процесса. Не посылает self-claimed PID/role как доказательство. Сервер получает PID/UID peer из ядра: Linux SO_PEERCRED, macOS LOCAL_PEERPID и LOCAL_PEERCRED. Клиент проверяет kernel peer PID сервера против pid владельца lease: broker-поток имеет тот же PID, что пульт; подмена сокета другим процессом не аутентифицируется. UID совпадает с владельцем пульта. ENV-адрес и содержимое доступного роли каталога не доверены.
4. Broker вне песочницы читает цепочку PPID от kernel peer PID до зарегистрированного агентного PID: Linux /proc/<pid>/stat, macOS proc_pidinfo(PROC_PIDTBSDINFO) через libproc. Не вызывает ps из роли и не меняет её права. Сверяет PID+start-time каждого узла дважды, предел глубины, отсутствие циклов и непрерывность цепочки; сравнивает агентный start-time с сохранённым при spawn. Живой PID без start-time недостаточен. При исчезновении/смене узла результат UNKNOWN, а не «оператор».
5. Перед ответом broker на новом readonly-соединении проверяет прежнюю lease-идентичность, локальный hostname, holder PID, heartbeat и что шаг регистрации ещё активен. Роль берётся из регистрации старта, не только текущего FSM. Ответ на открытом аутентифицированном соединении относится только к данному вызову; одноразовый nonce коррелирует запрос/ответ, не является credential. Не писать переносимый разрешающий token на диск и не использовать кэш разрешения в следующем вызове.
6. Если доказан developer и требуется новый full — cmd отказывает до store.db, deliver_journal, mkdir/log/lock/Popen. --failed/status/--wait проходят прежние условия. Прочая доказанная роль проходит прежний путь. Доказанная непричастность к каждому актуальному агенту сохраняет операторский маршрут. Обычный статус сначала читается без записи и запуска. Проверка не переносится в acceptance.full_suite: операторские гейты остаются вне запрета.
7. Broker закрывается в finally всех исходов шага, деактивирует регистрацию до unlink. Stop не трогает lease/фон/замки и таймауты существующих узлов. Клиент имеет короткий отдельный IPC deadline и ограниченный размер ответа. Broker не использует соединение SQLite runner из другого потока.

## Обязательный стоп перед реализацией

Дизайн зависит от двух НЕПРОВЕРЕННЫХ предпосылок: (а) настоящий Codex workspace-write может соединиться с AF_UNIX в уже открытом suite-run каталоге и получить peer PID; (б) пульт вне песочницы может читать PPID+start-time всех нужных процессов на macOS/Linux. Никакой запасной переход на маркеры, прямой PPID или ps-bypass не разрешён. Минимальная capability-проверка после разрешения: broker в пульте, реальная вложенная команда инструмента создаёт соединение, peer PID совпадает с её собственным PID, цепочка достигает агентного anchor при новой сессии. Проба только удостоверения, без full suite и без запуска тестов. Проверить обе платформы и оба провайдера; синтетический setsid-shell дополняет, но не заменяет реальный provider-route.

UNKNOWN/отказ IPC при наличии активных lease нельзя молча считать доказанной непричастностью: это оставит обход. Но блокировать все операторские новые full из-за UNKNOWN нельзя считать сохранением прежнего маршрута. Поэтому политика такого сбоя — отдельное явное решение в ADR/SPEC до выпуска. Рекомендация: named infrastructure refusal без побочных эффектов и эскалация обслуживающего шага; кратковременная недоступность при сбое канала должна быть принята как новая граница, а не скрыта словом «без ослабления». Если Оператор не разрешает такую границу, этот дизайн не готов к реализации. --wait/status доступны без запуска; условия --failed сохраняются. Недоступность IPC на штатном Codex-маршруте блокирует весь вариант C; права песочницы не расширяются.

## Угрозы и границы

- PID reuse: kernel peer credential не содержит сам по себе start-time. Сверка start-time anchor и каждого узла, повторная проверка до ответа, живое соединение и отсутствие кэша снижают гонку. Это не атомарный снимок всей process-tree; абсолютной гарантии при враждебной гонке fork/exit не обещать. UNKNOWN при нестабильности.
- Lease expiry/release/смена шага: совпадение task_id недостаточно; registration и lease generation/все существующие поля идентичности должны совпасть до ответа. После прекращения шага удостоверение не действует. Новое поле БД не заказывается заранее.
- Оператор: запрос той же задачи in_dev не доказывает родство. Проверяется настоящий peer ancestry, а не состояние запрошенной задачи. Новая сессия оператора сама по себе также ничего не доказывает.
- Разрешённый фон: проверка только публичного нового запуска. --failed разрешён ещё до фонового spawn; внутренний _CHILD/full-suite не повторяет broker-policy. Новая сессия фона не используется как единственное доказательство разрешения.
- Подмена endpoint/relay: клиент проверяет peer PID сервера, сервер — настоящий peer PID клиента. У role-owned relay ancestry developer и результат запрета. Same-UID произвольный несандбоксированный атакующий, inject в пульт, передача FD и намеренный reparent после смерти оболочки — не общий security-perimeter этой задачи; существующий контракт не покрывает уничтожение всей связи. Нельзя выдавать дизайн за глобальную защиту от такого противника.
- Чужой host/namespace: локальные PID применимы только к тому же host/PID namespace. При несовпадении UNKNOWN и эскалация, без сравнения одинаковых чисел PID между средами.

## Минимальный scope: до пяти файлов

1. Новый orchestrator/suite_context.py: broker/client, ограниченный протокол, платформенные peer/process adapters, без общего сервера команд.
2. orchestrator/runner.py: lifecycle потока, регистрация шага/PID/lease, finally teardown; без изменения запуска, timeout/kill и провайдерской песочницы.
3. orchestrator/suite_run.py: readonly discovery и ранняя проверка только нового full; сохранение failed/status/wait.
4. orchestrator/role_prompt.py: согласование миссии developer.
5. Один новый адресный tests/test_suite_context.py: реальные IPC/process фикстуры и регрессии границы; долгоживущие носители сохраняются.

providers/codex.py и claude.py остаются чтением: их существующие command/environment не умеют peer удостоверение, но для AF_UNIX клиента не нужны API доставки нового tool-handler. Если capability-проверка требует их правки или нового allowlist/песочницы — новая эскалация, не скрытое расширение этих пяти файлов. Если всё-таки необходимо мигрировать старые пять сценариев/добавить тестовый файл сверх пяти, оценка и зоны пересматриваются; старый адресный мандат не расширяется на helper.

## AC пересмотренного SPEC

AC-C1. Разрешённая capability-проверка реальных инструментов Codex/Claude на macOS/Linux подтверждает AF_UNIX connect/peer credentials и доступ broker к PPID+start-time без изменения sandbox. Отказ любого обязательного канала — эскалация, а не пропуск теста/приём.
AC-C2. Непосредственный и вложенный shell с setsid/новой сессией классифицируются по kernel PID+ancestry к живому агенту; удаление ARTEL_ROLE/ARTEL_TASK не меняет доказанный developer. Self-claimed PID/role не принимаются.
AC-C3. Публичный новый full developer получает прежний именованный контрактный отказ без store.db/create/deliver/log/lock/Popen; IPC-read и readonly существующей БД допускаются.
AC-C4. Реальный оператор и подтверждённая иная роль сохраняют full для той же in_dev-задачи. Поддельный сокет и поддельный PID в payload не дают разрешения. Нет классификации по имени CLI/HOME/FSM целевой задачи.
AC-C5. Подтверждённый developer сохраняет failed, статус и wait по прежним условиям; разрешённый отделённый фон ветки/базы завершается без ложного запрета.
AC-C6. Все обязательные гейты, timeout/замок обоих направлений, критерии reuse и метрики из действующего SPEC сохраняют прежние assertions и исходы. Не запускать полный набор из роли для этой проверки.
AC-C7. Завершённая/просроченная/сменившаяся lease, PID reuse, исчезновение предка, несогласованные два снимка и несовпадение namespace не создают подтверждения developer либо ложного разрешения по нестабильному чтению. Registration teardown выполняется при success/error/timeout.
AC-C8. UNKNOWN/IPC outage имеет принятый Оператором исход, проверяемый отдельными отказными сценариями; не выдаётся за доказанное «не роль», не запускает фон/пишущую БД. Отдельно проверены сохранение чтения status/wait и отсутствие зависания клиента/server.

## Рекомендация Оператору

Принять данный C как рамку исследования/пересмотра, не как доказанную переносимость. Сначала capability-проверка и решение о named refusal при UNKNOWN; затем SPEC/планка/реализация в существующем бюджете. До этого эскалация сохраняется. 20 минут — размер подготовки этого дизайна, не обещание выполнить IPC, два platform adapters и live validation за 20 минут или уложиться без переоценки в прежний бюджет.

## Дополнение 14.10.2026: фактическая capability-проба и кандидат IPC-исключения

Прямой шаг developer на codex-all выполнил клиент из действующей песочницы Codex: AF_UNIX connect получил PermissionError errno1 Operation not permitted. До kernelpeerPID/ancestry проба не дошла. PLAN/NOTE task01M4XVM49PP5WHSXT5S8JW85WN подтверждают отсутствие изменений кода/планки/прав. Следовательно, первый дизайн без изменения прав недоступен в текущем provider-route; его нельзя считать реализуемым по одному writable-directory.

Отдельная ограниченная проба Оператора вне pipeline использовала codex-cli0.157.1 sandbox с временным профилем и точечным Unix-допуском. Native --allow-unix-socket разрешил один заданный socket; соседний socket и прямой TCP к контрольному слушателю получили EPERM; kernelpeerPID сохранился. Постоянные роли и конфигурация не менялись.

Конфигурационные пробы с permissions.<name>.network.unix_sockets при network.enabled=false не дали подключения ни с выключенным, ни с включённым feature network_proxy. Во втором варианте proxy не создаётся; соседний socket и прямой TCP также получили EPERM. Это проверено отдельным клиентом без предположения о наличии HTTP_PROXY. Рабочий временный профиль использовал network_proxy enabled, network.mode=limited, пустой набор разрешённых domains и единственный Unix-path allow: один socket доступен, другойsocket/прямойTCP denied, запрос через proxy к example.invalid получил HTTP403. Это ограниченная проверка debug sandbox, НЕ реальный providerexec после изменения профиля. Способ передачи эквивалентного ограниченного профиля в provider требует отдельной проверки; общую сеть открывать нельзя. wildcarddeny '*' текущий CLI отверг: пустая domainallowlist сохранена явно, несовместимый fallback запрещён.

Кандидат отдельного решения Оператора: разрешить ровно один socket текущего broker с обязательной kernel-аутентификацией и запретом любых остальных Unix/TCP/UDP/внешних domains; сохранить ps/system-process ограничения роли. При UNKNOWN/IPCfailure/несовместимой версии/недоступном фильтрующем proxy — именованный инфраструктурный отказ нового full без побочных эффектов, в том числе для оператора; status/wait/failed и внутренние гейты/CI прежние. Представление policy может измениться, но эффективные запреты должны остаться равными или сильнее; смену CLI/config assertions нельзя легализовать blanket-мандатом. Допуск ещё НЕ принят и в постоянные роли не применён.
