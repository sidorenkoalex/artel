# ADR-0029: Проект на GitLab с гейтом мержа людьми проекта — реализация ADR-0003 п. 7 и п. 10

Статус: принят 26.10.2026, не исполнен; задачи — интерфейс адаптера и GitLab, гейт `target-human` с `awaiting_human` и `mr-sync`, полный набор из CI и профиль `verify`. Редакция 3 (26.10.2026: независимая вычитка по коду и ответы Оператора). Основание — решения Оператора 25.10.2026 («после MR пока что всё делает человек»; свежесть ветки, автор и сжатие коммитов — переменными записи; автор — учётная запись токена, Оператор — соавтор; «ничего про конкретный проект не должно быть в репозитории артели, только интеграция для такого типа репозиториев и GitLab в частности») и 26.10.2026 («не закрывать, а оставить в статусе MR; общий конвейер, гейты которого в разных проектах работают по-разному; при ручном мерже — отдельной командой пробегаться по статусам MR и доводить до merged при подтверждении»; «ветка может быть влита отдельной веткой с другими MR, а текущая закрыта — нужно проверять фактическое нахождение в main»; стенд ветки — опциональная проверка приёмки проекта, альфа-тест — её агентская форма; имена `mr-sync`, `verify-ok`, `verify-fail` и предел 3 — приняты). Реализует то, что ADR-0003 решил, но код не исполняет: п. 7 (`merge_gate: target-human`, состояние `awaiting_human`) и п. 10 (профиль проверок `verify`). Дополняет ADR-0015, ADR-0021, ADR-0026, ADR-0028. Поведение существующих проектов не меняется: всё новое — полями записи с прежними значениями по умолчанию. Значения полей подключаемого проекта — только в его записи локального слоя.

## Контекст

- **Сейчас гейт мержа один — `operator`.** На `approve` в `merge_gate` пульт вливает ветку задачи в `base` и отправляет основную ветку (`fsm_merge_gate._push_merged_main`), удаляет ветку на сервере, задача — `done`. Поле `merge_gate: operator | target-human` проходит проверку записи (`targets.py`), но `target-human` не исполняется: запись с ним сейчас загружается, и пульт смержил бы сам. Состояния `awaiting_human` (ADR-0003 п. 7) в коде нет; поле `verify` (ADR-0003 п. 10) не заведено.
- **Хостинг — только GitHub** (`gh`, `orchestrator/ci.py`, `orchestrator/github_adapter.py`); `targets.FORGES` допускает `gitlab`, реализации нет: черновой MR для не-GitHub молча пропускается, ожидание CI через `gh` для GitLab не работает. `kill` удаляет ветку на сервере у любого хостинга (`cleanup._delete_origin_branch`); от GitHub зависит только закрытие PR.
- **Тип проекта, который нужно поддержать.**
  - Основная ветка — поток команды: MR вливает человек (дежурный), своим методом слияния (например, перебазированием или сжатием) и только при прошедшем конвейере.
  - Конвейер создаётся только для веток по правилу `workflow` (например, ровно `feature/<ключ трекера>`); на push ветки идут сборка и тесты; изолированный стенд ветки поднимается ручным заданием конвейера — по желанию человека.
  - Промежуточные и боевые окружения запускаются релизными ветками и тегами; их защищают настройки проекта.
  - Инсталляция GitLab может требовать совпадения email автора коммита с учётной записью, которая пушит.
  - Доступ пульта — токен служебной учётной записи проекта с ролью Developer.
- **Полный набор тестов такого проекта локально дорог** (базы, очереди, образы), а тот же набор команда гоняет в CI.
- **Внешние ссылки задач уже есть** (ADR-0028): `new --ref <система>:<ключ>`, поля `policy.ref_systems`, `policy.ref_required`; при делении ссылки копируются частям.

## Решение

### Гейт мержа и состояние «ждёт людей проекта»

1. **Гейт мержа `target-human` (ADR-0003 п. 7).** Пульт не мержит никогда (ADR-0003 п. 8).
   - **Подготовка ветки — не на гейте мержа.** Сжатие (`policy.squash_before_mr`) и свежесть (`policy.freshness`) выполняются на каждом переходе `in_dev → verifying` (ADR-0015 п. 2): сначала сжатие, затем подтяжка выбранным методом; конфликт — возврат в `in_dev` тем же путём, что конфликт подтяжки сейчас. Дальше голова проходит CI, ревью, приёмку как обычно.
   - **На `approve` в `merge_gate`** исполняются без изменений: сверка ссылки документов, гейт защищённых путей (`no_paths`), гейты неослабления по тексту и по исходам, лок планки, зелёный CI головы, подтяжка при сдвиге `base` (тем же методом; после неё — новый CI и гейт по исходам, возврат на гейт). Подтверждённый Оператором sha обязан совпасть с головой, которая уходит в MR, иначе — отказ с причиной. Не исполняются: слияние, приложения PLAN, карта и `guard --all` по дереву мержа, отправка `base`, ожидание CI `base`, справочник ядра, удаление ветки. Задача с приложениями PLAN отказывает: «приложения не применяются в проекте с target-human — правку вносят люди проекта».
   - **Затем** пульт открывает MR из ветки задачи в `base` (или снимает черновик с уже открытого, п. 6), назначает исполнителя `policy.mr_assignee` и переводит задачу в `awaiting_human` со ссылкой на MR.
2. **Состояние `awaiting_human` — новое состояние FSM по ADR-0003 п. 7.**
   - Входит в `fsm.STATES`; не окончательное; гейта Оператора нет — ждём людей проекта; `waiting_on` в модели доски — `human` (новое значение).
   - Предел одновременных задач проекта в этом состоянии — `policy.max_awaiting` (по умолчанию 3): сверх предела `approve` на `merge_gate` отказывает с причиной, задача остаётся на гейте; в `status` — пометка «очередь: предел awaiting_human». В `MAX_PARALLEL_TASKS` состояние не считается.
   - **Ветка принадлежит людям проекта.** Пульт в неё не отправляет, MR не меняет, ветку не удаляет — ни на `mr-sync --confirm`, ни на `kill`. `kill` задачи проекта с `target-human`, ветка которой уже отправлена, при любом хостинге не удаляет ветку на сервере и не закрывает MR (меняется `cleanup`), убирает только свою рабочую копию и пишет ссылку на MR в журнал.
   - **Зоны в `awaiting_human` — поле `policy.awaiting_holds_zones`** (по умолчанию `true`): задача держит свои зоны до `done`/`kill` — следующая задача не меняет те же файлы, пока MR не влит. При `false` зоны освобождаются при переходе в `awaiting_human`: следующая задача может менять те же файлы от `base` без правки предыдущей; возможный конфликт двух MR разрешают люди проекта при вливании (или подтяжка следующей задачи, если первая уже влита). Значение показывают `status` и `doctor`.
   - **Места пульта, которые учитывают состояние** (задача (б)): блокировка зон (`zone_lock.BLOCKING_STATES` — по полю `awaiting_holds_zones`); остановка `auto` без алерта (`config.AUTO_STOP`, `auto._NO_ALERT_FINAL_STATES`); надзор эпика (`auto.EPIC_GATE_STATES`, `_NOT_HOLDING_STOP_STATES`); модель доски (`board.waiting_on`); `report`, `watch`; `approve`, `reject`, `answer` в этом состоянии отказывают с подсказкой `mr-sync`; `doctor` проверку свежести ветки к нему не применяет; эскалация из `awaiting_human` возвращает в него же; рабочая копия хранится до `done`/`kill`; зависимые по `merge_after` ждут `done`.
3. **Команда `mr-sync [<id>…]`** — запуск Оператором (опрос по расписанию — позже, пункт C0 дорожной карты). По каждой задаче проекта с `target-human`, у которой открыт MR (в любом незакрытом состоянии), после `fetch` и только чтением сводит:
   - **статус MR**: открыт / влит / закрыт без вливания / не найден / переведён на другую целевую ветку (MR сверяется с `target_branch == base`);
   - **фактическое нахождение правки задачи в `base`**, от подтверждённой Оператором головы (`approve` на `merge_gate`):
     - (а) коммит вливания MR — `merge_commit_sha`, `squash_commit_sha` или голова MR по методу вливания — предок головы `base`;
     - (б) коммиты задачи найдены в `base` по содержимому правки (`git cherry`, `--no-merges`) — ловит перенос коммитов в другую ветку;
     - (в) вся правка задачи уже есть в `base`: обратное наложение диффа задачи от точки ответвления (`git apply --check -R --binary --whitespace=nowarn`) проходит, а прямое — нет; доказательство печатается по файлам — ловит сжатие и вливание вместе с другими MR через отдельную ветку.
   - **Итоги:** «влит этим MR» (а); при (а) и провале (в) — пометка «после вливания файлы менялись»; «в базе, влит иначе» (MR закрыт или открыт, правка в `base` по (б) или (в)); «в базе частично»; «нет в базе»; «MR не найден»; «MR переведён на другую ветку».
   - **Закрытие:** `done` — только по подтверждению Оператора `mr-sync <id> --confirm` и только при итоге «влит этим MR» или «в базе, влит иначе»; итог «в базе, влит иначе» лишь по признаку (в) требует `--confirm --by-content`. `closed_as` — `merged_upstream` или `merged_upstream_other`; коммит закрытия получает sha из доказательства (вливание MR или найденный коммит); по признаку (в) — голова `base` на момент сверки с пометкой «по содержимому». Прочие итоги — показ Оператору, решение за ним (`kill`, новая задача, ожидание).
   - **Инциденты** (ADR-0003 п. 7, п. 9): MR влит или закрыт до перехода в `awaiting_human` — эскалация; голова ветки на сервере не совпадает с последней своей отправкой (чужой коммит) — эскалация, без перезаписи. Проверяются `mr-sync` и `approve` на `merge_gate`.

### Ветка, коммиты, MR

4. **Свежесть ветки — поле `policy.freshness`:** `merge` (по умолчанию, как сейчас) или `rebase` (перебазирование ветки задачи на `origin/<base>` только в рабочей копии задачи, `base` не меняется). Перезапись своей ветки — только `--force-with-lease=refs/heads/<ветка>:<sha последней своей отправки из журнала>` и только до `awaiting_human`. Вариант «без подтяжки» не вводится: подтяжка — рубеж перехода `in_dev → verifying` (инвариант 39).
5. **Коммиты — поля записи.**
   - `policy.squash_before_mr` (по умолчанию `false`): коммиты задачи сжимаются в один (п. 1).
   - `policy.commit_template` (по умолчанию `{id}: {text}`), например `{ref}: {text}`.
   - `machine.commit_author` — автор и отправитель; пульт сверяет его с владельцем токена (чтение пользователя токена через API) до первой отправки.
   - `policy.co_author` — строка `Co-authored-by: …` (необязательно).
   - Шаблон, автор и соавтор применяются пультом к коммитам ролей при автокоммите и сжатии, не настройкой, которую может сменить роль. Документы задачи (`refs/artifacts/<id>`) пишутся тем же автором; если хостинг отвергает `refs/artifacts/*`, — запасной вариант ADR-0021 п. 9.
6. **Ветка задачи по ключу трекера.**
   - `policy.branch_template` (по умолчанию `task/{id}-{slug}`), например `feature/{ref}`; `{ref}` — ключ ссылки системы `policy.ref_required` (ADR-0028).
   - `policy.ref_pattern` — регулярное выражение допустимого ключа; шаблон с `{ref}` без обязательной ссылки или ключ не по выражению — отказ `new`.
   - `new` и деление отказывают, если ветка по шаблону уже есть на сервере или у любой задачи проекта в любом состоянии (части деления с копией ссылки родителя и новая задача после `kill` с тем же ключом не попадают в чужую ветку). Поиск веток пульта (`coldstart` и др.) учитывает шаблон, а не префикс `task/`.
   - `doctor` сверяет шаблон с правилом `workflow` конвейера проекта, если запись называет файл конвейера.
7. **Черновой MR — поле `policy.draft_mr`** (по умолчанию `true`, как сейчас): MR-черновик с первой отправки ветки (вход в `verifying`), люди видят ход работы; гейт мержа снимает черновик. При `false` MR один — на гейте мержа; подсветка защищённых путей — в описании MR. Исполнитель — `policy.mr_assignee`.

### Хостинг и CI

8. **Адаптер по `forge`.** Интерфейс: статус конвейера головы ветки, задания конвейера и их отчёты, результат задания по имени, открыть MR, снять черновик MR, назначить исполнителя MR, статус MR. Реализации: GitHub (нынешняя, без изменения поведения) и GitLab.
   - Первой задачей: загрузка записи с `merge_gate: target-human` или с `forge` без адаптера отказывает с причиной — до исполнения остальных пунктов.
   - **Зелёный CI на GitLab:** берётся конвейер ровно этого sha; если их несколько (ветка и MR), зелёными должны быть все. Все завершённые задания без права падать — `success`; задания `created`/`skipped` допустимы, только если они стоят за ручным заданием и не названы обязательными (`policy.ci_required_jobs`); `failed` без права падать — красный; `running`/`pending` — идёт; конвейер не создан (ветка не под `workflow`) — именованный отказ. Неполный статус — не зелёный (инвариант 19). Упавшее задание с правом падать — замечание ревьюверу.
   - **Белый список вызовов API GitLab:** чтение конвейеров, заданий, отчётов заданий, MR, пользователя токена; создание MR, снятие черновика, назначение исполнителя. Слияния, закрытия MR, комментариев, запуска заданий, тегов, релизов, веток через API, настроек, переменных, участников в адаптере нет (пересмотр ADR-0003 п. 5–6 в этой части — до C3).
   - Срок токена: `doctor` предупреждает за N дней до истечения, если API отдаёт дату; токен без срока — предупреждение после порога числа задач проекта.
9. **Источник полного набора — поле компонента `full_suite`** (в описании компонента записи): `local` (по умолчанию, как сейчас), `ci`, `both`.
   - В режиме `ci` результат берётся из задания `ci_job: <имя>`: зелёный, только если задание есть в конвейере ровно этого sha, без права падать, в статусе `success` и с разобранным отчётом тестов; отсутствует, пропущено, ручное или отчёт не разобран — итог «неизвестно», не зелёный (инвариант 41 — и для итога из CI).
   - Гейт неослабления по исходам (ADR-0026 п. 6) в режиме `ci` читает два отчёта задания `ci_job` — для головы ветки и для конвейера `base` на точке ответвления — и сравнивает тесты по идентификаторам; нет отчёта базы — отказ, а не пропуск.
   - До реализации чтения отчётов допустим только `both`.
   - Локально в режиме `ci` — тесты задачи.
10. **Профиль проверок проекта — поле `verify` (ADR-0003 п. 10).** Список проверок этапа `verifying` из каталога типов; по умолчанию пусто. Тип `ci` — существующее ядро `verifying`, в профиле не объявляется.
    - `human:<имя>` — ручная проверка: пульт ждёт отметки Оператора `verify-ok <id> <имя> <sha> "<итог>"` (действительна только для этой головы: новая голова — проверка заново) или `verify-fail <id> <имя> "<причина>"` (возврат в `in_dev`, считается в цикле с пределом — инвариант 3, после предела эскалация). `waiting_on` при ожидании отметки — `operator`. Пример — `human:stand`: изолированный стенд ветки развёрнут человеком ручным заданием конвейера и проверен. Пульт стенд не разворачивает и заданий не запускает.
    - `agent:<имя>` (альфа-тест — агентская проверка стенда по навыкам проекта) и `script:<имя>` — в каталоге типов, реализация отдельным решением (пункт C4); объявить неисполнимое нельзя — загрузка записи отказывает.
    - `auto` не вызывает `verify-ok`, `verify-fail`, `mr-sync --confirm` (инвариант 18).
11. **Параметры отправки ветки — поле `policy.push_options`** (по умолчанию пусто): `git push -o …` к каждой отправке ветки задачи. `-o ci.skip` запрещён (загрузка записи отказывает). Значения показывает `doctor` и строка статуса CI ревью-пакета.
12. **Нагрузка на проект — `policy.max_in_flight`** (по умолчанию без предела): число незакрытых задач проекта с веткой на сервере (от `verifying` до `awaiting_human`). Ветка кода отправляется только на входе в `verifying`.

### Страховки

13. **Единая точка отправки.** Белый список ссылок проверяет код в одной точке отправки (`gitcmd`): для проекта с `target-human` — только ветка задачи по шаблону и `refs/artifacts/*`; отправка в `base`, удаление веток, теги и `refs/heads/*` вне шаблона отклоняются до вызова git. Хук `pre-push` — второй рубеж: пульт задаёт каталог хуков в самом вызове (`-c core.hooksPath=<каталог пульта вне зон записи ролей>`), `doctor` сверяет контрольную сумму хука. `no_paths` проекта включает файлы конвейера. Токен — роль не выше Developer; `doctor` информационно показывает защиту основной ветки, тегов и релизных веток.
14. **Порядок действий при инциденте** (из C2 дорожной карты): отзыв токена, срез журнала задачи, ссылка на MR — короткий документ проекта в `docs/` до первой задачи.

## Пересматривает

- **ADR-0003 п. 5–6:** комментариев, `merge` и `close_mr` в адаптере нет (до C3).
- **ADR-0003 п. 7:** `done` — по подтверждению Оператора через `mr-sync`, а не по событию хостинга; `kill` не закрывает MR и не удаляет ветку; предел `awaiting_human` — отказом `approve`, без очереди FIFO.
- **ADR-0028:** `closed_as` бывает и у `done` (`merged_upstream`, `merged_upstream_other`; сейчас только `divided` у `killed`); `waiting_on` получает значение `human`; «`done` = коммит закрытия с коммитом мержа» расширяется — коммит закрытия с sha из доказательства `mr-sync`.
- **Дорожная карта (C2):** C0 (опрос по расписанию) перестаёт быть условием C2 — его заменяет ручной `mr-sync`.

## Инварианты

Строки `docs/invariants.md` — операторскими коммитами после мержа соответствующих задач:
- новая: «для проекта с `target-human` пульт не выполняет слияние, не отправляет `base` и ничего не отправляет в ветку задачи в `awaiting_human`» — тест по образцу `MergeOnlyFromMergeGateTest`;
- новая: «MR открывается или снимается с черновика только для подтверждённой головы с зелёным CI» (аналог 19);

## Решения Оператора 26.10

1. Имена команд `mr-sync`, `verify-ok`, `verify-fail` — приняты.
2. Предел `awaiting_human` по умолчанию — 3 — принят.
3. `mr-sync` проверяет не только статус MR, но и фактическое нахождение изменений задачи в основной ветке: ветку могут влить отдельной веткой вместе с другими MR, а сам MR закрыть (п. 3).
