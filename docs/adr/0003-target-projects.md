# ADR-0003: Целевые проекты (control plane)

Дата: 2026-08-24. Статус: принят (Р1 утверждён Оператором 23.08;
состав — роадмап §2, решения слоями 20–23.08, источники слоёв —
docs/audits/ с индексом находок).

## Контекст

Фаза 0 (ADR-0001) замкнула цикл «запрос → смерженный MR» на самом
пульте: артель дорабатывала только себя. Фазы A–C выводят конвейер
на внешние проекты — второй GitHub-проект (`sidorenkoalex/sled`)
и корпоративный GitLab (scm.x5.ru, проект feedback). Для этого нужен
control plane: как проект подключается, где живут его артефакты
и знания, какие права у токенов, где проходит периметр недоверенного
кода и как выглядит взаимодействие с людьми целевого проекта.

Решения принимались слоями 20–23.08 (финальное ревью 21.08,
аудиты 22.08, 22.08-2, v2–v4 23.08); этот ADR фиксирует итоговый
состав. До коммита текста выполнен A-спайк допущений (23.08,
docs/audits/a-spike-2026-08-23.md) — фактура в разделе «Проверенные
допущения» ниже. Задачи фаз A–C, бюджеты и критерии выхода — предмет
роадмапа, не этого ADR.

Нумерация пунктов — сквозные якоря (п.1–18, 3а–3к): на них ссылаются
роадмап, design.md и артефакты задач.

## Решение

### 1. Пульт

Репозиторий artel — единственный дом системы (оркестратор, конфиги,
БД, журнал) и артефактов догфуда; хранение артефактов внешних
проектов — по п.3 (замещает раннюю формулировку «дом всех
артефактов»).

### 2. targets.yaml

Декларативное подключение проекта: forge (github|gitlab), url,
базовая ветка, token_slot, no_paths целевого, project_skills,
исполнитель гейта мержа. Поле «режим артефактов» убрано (решение
22.08-2): режим один, публикация отложена.

### 3. Хранение артефактов внешних целевых

**Target-branch — единственный режим текущего горизонта** (решение
Оператора 21.08, итог обсуждения вариантов): orphan-ветка `artel`
(имя конфигурируемо) в репозитории целевого — только артефакты
(`tasks/<id>/` + производные знания, п.3а), без кода и без общей
истории с main (прецедент паттерна — gh-pages); рабочие ветки задач
всегда от main. Что даёт: main чист; ничего не создаём на forge;
те же права/токены, что на целевой; никакой второй точки отказа;
люди видят полные артефакты в своём же репо; периметр по построению.
Enforcement защиты ветки: для GitLab-целевых честный (protected
branch у админа целевого), общий случай (GitHub Free, чужие
админы) — best effort; несущая гарантия всегда hash-фиксация (п.15).
По умолчанию GitLab запускает пайплайн на любую ветку — при
активации публикации потребуется `workflow: rules` у целевого
(испр. 23.08, аудит v4 п.9). Носитель — git осознанно (гибрид:
SQLite — состояние и запросы, git — документы, история, диффы,
периметр; решающие критерии — человек в контуре и доступность
корп-хостинга).

**Публикация следа — отложена целиком** (решение 22.08-2, замещает
флаг publish_history). Ближний горизонт: артефакты внешних целевых —
только локально в пульте (3д); в целевом от Артели только ветки
task/ и MR; контекст людям — описание MR + комментарии (п.5).
Триггер возврата — первый запрос людей целевого на полные артефакты;
включение задним числом — идемпотентная дозаливка всей истории
(первичка в пульте). Все допущения о ветке (protected, имя,
отключение CI) проверяются только при активации, из предусловий
старта фазы C уходят. Роль ветки при активации — «журнал проекта
для людей», НЕ бэкап: сохранность первички — бэкап .artel/
(тест-эпоха, 3к) и серверные механизмы (нормальная работа).
Место спецификации механики публикации (orphan-ветка, реплика,
дозаливка, сверка head, права записи, bootstrap — пп.3/3а/3б/3в/3е,
части п.15/п.17) при переписывании роадмапа —
docs/deferred/publication.md (решение 23.08, аудит v3 В1);
в нормативном тексте остаются триггер возврата и суть в три строки.

Отложенные концепты: пространства с hub-storage — п.18 (по
триггеру); отдельный режим in-branch не заводится; догфуд-артель
живёт текущей механикой до A7, затем — обычный внешний target
(решение 23.08).

### 3а. Производные знания проекта — рядом с его артефактами

В `.artel/projects/<target>/knowledge/` пульта (в ветку `artel`
целевого — при активации публикации): codebase-map, проектные скилы
(если не в самом целевом), per-project копилка К1. Содержимое кода
проекта не покидает периметр «репозиторий целевого + его каталог
в пульте» (решение 22.08-2): в память ассистента выдержки кода
целевых не попадают — память хранит решения и указатели, знание кода
живёт в knowledge/ проекта. Общепространственное — дома не имеет
до пространств (п.18).

### 3б. Свежесть производных знаний

Принцип: «кэш с меткой источника, сверка при потреблении, никогда
молчаливое доверие» — целевой живёт без нас, люди мержат свои MR:

- карта: `built_at_sha` в frontmatter; ленивая сверка при сборке
  брифа; регенерация до старта шага, если дифф main пересёк зону
  задачи; гибрид — скелет скриптом (дёшево, всегда), семантические
  аннотации агентом инкрементально по диффу; провал регенерации =
  алерт, не молчаливый старт со стухшей картой;
- память ассистента: утверждения с датой и источником; сверка
  критичных фактов с живым источником при использовании; ревизия
  ассистентом под журналом изменений; внешние не пишут никогда —
  мир попадает в память только через события системы;
- ветки задач: актуализация из main целевого перед merge_gate/
  снятием Draft + перепрогон CI; конфликт = итерация с лимитом.

### 3в. Модель «реплика»

Первичные артефакты — локально, ветка — публикация (упрощение 21.08
вместо ранних саг). Артефакты рождаются и живут в локальном .artel/
пульта: транзакция шага локальна, сеть и доступность scm
не участвуют. Публикация в ветку artel целевого (при активации —
п.3) — фоновая; дефолт частоты — каждый ручной гейт (настройка);
до активации контекст людям — описание MR из SPEC и вердикты
комментариями (п.5, уточнение 23.08). Механика: `code_sha`
во frontmatter (+guard); идемпотентная дозаливка реплики (она же
лечит любые проблемы ветки); «в ветку artel коммитит только
оркестратор» — точка guard, гигиены п.16 и hash-фиксации п.15.
Записанные компромиссы: лаг видимости до ближайшего гейта; черновики
между гейтами — только локально.

Hash-фиксация и approve-по-хэшу — несущие; реальный носитель угрозы
(уточнение 23.08, аудит v4 п.7) — не «админы целевого» (публикация
отложена, в целевом только код), а: (а) роли, пишущие в тот же ROOT
с acceptEdits — approve должен фиксировать именно тот sha, который
Оператор видел; (б) TOCTOU между approve и стартом шага — закрыт
сверкой при старте (A2b, п.17).

Триггеры публикации — ручные гейты ПЛЮС терминальные переходы
(done/killed/escalated), атомарно одним коммитом (артефакты +
журнальный срез): концовки задач в следе не теряются. При публикации
сверяется ожидаемый head ветки с журналом — расхождение = событие
«внешняя правка ветки», алерт (переписывание не лечится молча).

### 3г. Двухуровневый срез — отложен целиком

Решение 22.08-2 (схлопывает решение 22.08). Уровень 1 (процессный
след) — отложен вместе с публикацией (п.3). Уровень 2 (ledger-экспорт
экономики в git пульта) — отложен по триггеру «понадобился внешний
экспорт экономики»: все три его роли сняты текущими решениями
(вторая копия не нужна — потеря БД до сервера принятый риск 3к,
на сервере серверные бэкапы СУБД; панельные тренды — одним запросом
из единой БД 3ж; миграция БД — дамп-скрипт, не jsonl-импорт).
При активации уровня 2 — только структурированные поля, никаких
свободных текстов; экономика в уровень 1 — настройка состава,
дефолт нет.

### 3д. Структура .artel/ — project-first

Единица управления — проект: подключение/отключение/восстановление =
операции над одним каталогом; зеркальность публикации «каталог минус
workspace → ветка»:

```
.artel/                     ← .gitignore пульта целиком
├─ state.db                 ЕДИНАЯ БД всех проектов (3ж)
├─ logs/                    логи самого пульта
└─ projects/<target>/
   ├─ workspace/            эфемерный клон целевого (кэш)
   ├─ tasks/<id>/           первичные артефакты  → публикация
   ├─ knowledge/            maps/, skills/       → публикация
   └─ logs/                 стримы агентов проекта
```

**`projects/<target>/` — локальный git-репозиторий без remote**
(решение 23.08, аудит v3 Б1; workspace/ и logs/ — в .gitignore этого
репо): целостность, история и диффы артефактов — штатным git вместо
самописных механизмов. Коммитит только оркестратор на переходах FSM
(= фиксация п.15), sha коммита — в журнал БД. Remote отсутствует
физически — периметр п.3 сохранён по построению; doctor проверяет
«git remote -v пуст» (+ git fsck при recovery). Агенты git-слоя
не видят — пишут файлы как раньше. Параллельные задачи одного
проекта (полная версия): workspace — per-task (git worktree);
внешние публикации сериализуются: per-target очередь + одна
глобальная очередь на запись в git пульта.

На GitHub (remote пульта) уходят только система и догфуд-таски
Фазы 0 (T001–T016, как есть); .artel/ не коммитится конструктивно.
Догфуд — особый случай (артефакты в ветках задач пульта, как всю
Фазу 0) — **до A7** (решение 23.08): после A7 артель — обычный
внешний target, первичка её задач — `.artel/projects/artel/` вне
git, в репо артели артефакты новых задач не попадают («чистый B»,
решение Оператора 23.08 по аудиту v4 п.1: ни в ветку задачи,
ни в ветку `artel`; git-след артели — по тому же триггеру публикации,
что у всех). Проверено по коду: флоу зависит от каталога текущей
задачи, прошлые задачи нужны только как RETRO/эталон — обрыв
git-истории на T016 флоу не ломает.

### 3е. Дисциплина производных знаний

skills/ и maps/ проекта правят только выделенные процессы
(регенерация карты, задачи о скилах, Оператор) — точка сдачи
не принимает их от посторонних задач (защита от тихого дрейфа
знаний). Хэши компонентов брифа (версии карты и скилов, вошедшие
в шаг) — в журнал: replay «по какой версии знал агент» восстановим.
Bootstrap первой карты — в механике подключения проекта (ветка
artel — при активации публикации, п.3).

### 3ж. Единая БД на все проекты

Решение 22.08; несущее обоснование — стоимость (аудит v4 п.6):
state.db уже есть и работает, сплит system.db+per-project — новый
код ради невозникшей проблемы. Контраргументы сняты по существу:
сирот при disconnect нет — транзакция архивации (архив строк,
никогда DELETE, решение 22.08-2); бэкап — целиком; параллелизм —
Postgres по триггеру. Колонка target; сквозная экономика — единый
кошелёк Оператора, суммарные лимиты и панельные тренды одним
запросом; счётчики доверия — ключ (gate, target): доверие с догфуда
не наследуется на целевые. Нумерация задач target — персистентный
счётчик per-target, НЕ COUNT(*) (иначе архивация строк
переиспользует номера; в объём A1) — реконнект не создаёт коллизий.

**Disconnect — процесс, не только данные** (решение 22.08-2):
прогоняет kill-протокол п.7 по всем незавершённым задачам target
(close_mr с комментарием, финальные ответы в тредах) — внешних
висяков не остаётся. При недоступном токене (доступ отозван —
главный принудительный сценарий) внешняя часть протокола — ручная
деградация (решение 23.08): Оператор просит админа целевого закрыть
MR-ы или закрывает своей УЗ, факт и способ фиксируются в журнале;
внутренняя часть (kill, архивация) выполняется всегда. Reconnect:
синхронизация, не bootstrap с нуля; следы внешней активности
за период отключения — события «внешняя правка» с разбором,
не инцидент компрометации.

**Движко-независимость**: SQL только в store.py — цель, не факт
(консолидация — в объёме A1, 22.08-2); переносимая схема без
SQLite-экзотики; **Postgres — по триггеру, не по эпохе** (испр.
23.08, аудит v4 п.3): триггер — второй одновременный
процесс-писатель в БД; наблюдаемый сигнал — SQLITE_BUSY в журнале,
считает doctor, kind=trigger; миграция — дамп-скрипт. До триггера —
SQLite с WAL (A1). Без ORM и repository-слоёв. Рассмотренные
и отменённые варианты: сплит system.db+per-project и поле db: —
сняты рамкой 22.08.

### 3з. Роли: формула универсальности

Агент = системный слой (промпт роли, методология-чеклисты, права —
константа, protected paths пульта) + проектный слой (знание: карта,
проектные скилы, конвенции целевого как данные — аддитивно,
из projects/knowledge) + задачный слой (SPEC, пакет). **Проект
не может ослабить роль**: кастомизация только аддитивная,
а безопасность — курированием списка скилов и их ревью тем же
конвейером (аддитивный текст может ослаблять семантически — защита
процессная, не структурная); легальные оси вариативности —
исполнители (design §16), verify-профиль, параметры targets.yaml.
Улучшение системного скила апгрейдит роль во всех проектах сразу.

### 3и. Кросс-таргетные задачи

В модели задача = один target; фича на два репо = две связанные
задачи (поле related в SPEC), связывание и синхронизация гейтов —
Оператором. Мотивирующий пример (panel↔API в двух репо) умер
с монорепо (аудит v4 п.5) — related-guard переводится по триггеру
«первая реальная кросс-репо задача» (строка в docs/triggers.md);
поле related в SPEC остаётся (дёшево). Иное — не поддерживается
осознанно.

### 3к. Инфраструктурные эпохи

Решение 22.08. Тест — ноутбук Оператора: поллер — прерываемый
локальный процесс без SLA (работает в сессиях Оператора; догон без
потерь — C0, 23.08); сохранность первички и hash-журнала —
обязательный локальный бэкап .artel/ (механизм — настройка
Оператора: Time Machine/rsync) + recovery-сверка консистентности
в doctor (A3, решение 22.08-2); давность последнего бэкапа проверяет
doctor (>7 дней → алерт), restore-тест не требуется — принятый риск;
восстановление из бэкапа — restore-режим doctor (решения 23.08);
прочие потери не рассматриваются.

Нормальная работа — **self-hosted: выделенный корп-сервер** — тот же
пульт, функционально не отличающийся от ноутбука, плюс постоянный
онлайн (демон/поллер always-on) и серверные механизмы устойчивости
(комплексные бэкапы БД и артефактов, периметр). Переход между
эпохами — не гейт и не триггер: по потребности в мощностях
и постоянной работе, после обкатки основного флоу (уточнение
22.08-2); гейтится не сам переход, а запуск постоянного фонового
режима — он требует серверной эпохи и сервисных УЗ (Р7). Инференс —
как на ноутбуке; при ограничениях сети — подключение локальной/
корпоративной LLM (Р6), гейтвей заранее не строим. Отмечено
и отложено: секрет-слой при переносе (keychain → серверное
хранилище), перенос БД (дамп в СУБД сервера, 3ж).

### 4. Workspace

Эфемерный клон целевого в `.artel/projects/<target>/workspace/`
(3д); агент видит только целевой и его токен, конфиги пульта
недоступны (отсечение инъекций из чужого кода).

### 5. Контекст людям — примитивы forge

Описание MR генерируется из SPEC; вердикты ревью — комментариями;
финальный итог (итерации, стоимость, ссылка на трейс) —
комментарием.

### 6. Forge-адаптер

Интерфейс create_mr / undraft / merge / close_mr / ci_status /
comment / reply / list_discussions / mr_events / approve_label
(полный список — по потребителям пп.7 и 9, ревью 21.08); реализации
github и gitlab. Merge в целевой — только оркестратор через адаптер.

### 7. Исполнитель гейта мержа

`merge_gate: operator | target-human` (уточнение Оператора 20.08).
Режим target-human: MR создаётся **Draft**, Draft снимается только
после нашей приёмки; мержит человек целевого проекта его кнопкой;
оркестратор узнаёт о merge по событию forge и закрывает задачу;
комментарии людей в MR → внешний changes_requested → обычная
итерация.

**Карта состояний внешнего хвоста** (решение 23.08, аудит v3 Флоу-1;
реализация — C1): Draft-MR создаётся при первом пуше ветки задачи
(описание из SPEC, адаптер B1b) и висит Draft всю разработку — люди
видят прогресс. `merge_gate` для target-human исполняется как
**undraft**: approve Оператора по sha = команда снятия Draft, наш
последний гейт — дальше решение чужое. После undraft задача
переходит в состояние FSM **`awaiting_human`** и стоит в нём
до merge-события поллера → done. Лимит одновременных задач 3
и наблюдение дискуссий (п.9) — свойства этого состояния, а не
оверлей поверх FSM. Внешний changes_requested возвращает в in_dev
обычным циклом — маршрут один (п.9).

**Токен Артели для такого проекта не имеет прав merge вовсе** —
минимальные привилегии; по итогам A-спайка допущение
переформулировано: «не может смержить» — свойство защиты ветки
целевого, не токена (см. «Проверенные допущения», п.2), проверка
в doctor при подключении. Релизы — процесс целевого, вне нашего FSM.

**Merge раньше нашей приёмки** (человек сам снял Draft — прав
помешать у нас нет и не должно быть): инцидент → эскалация Оператору
+ уведомление в MR-тред, задача НЕ закрывается как done молча;
протокол — письменно (описание MR + вики целевого), не устно: должен
переживать ротацию дежурных (уточнение 22.08-2). Kill задачи при
открытом внешнем MR: close_mr с комментарием; ветка task/ —
по политике целевого. Лимит одновременных задач в awaiting_human —
3 (пропускная способность Оператора, решение 22.08-2): сверх лимита
внешняя фаза не стартует — задача остаётся в последнем внутреннем
состоянии (MR не создаётся), в CLI/панели пометка «queued:
awaiting-human limit», порядок FIFO (уточнение 23.08).

### 8. Новые инварианты

Наблюдаемое и тестируемое — в реестр («роли не выполняют push вне
ветки своей задачи» — кодируемо); свойства чужих систем (защита
веток целевого — у его админа) — во вторую таблицу реестра, без
тестов-декораций (ревью 21.08); workspace изолирован от пульта;
no_paths целевого проверяются до merge; для target-human — Артель
не мержит никогда; комментарий MR вне зоны SPEC не исполняется —
только эскалация; ядро FSM неизменно, каталог типов проверок
расширяет только Оператор через ADR; merge_gate не переводится
в conditional/auto, пока PAT ролей не разделены (обязательство
ADR-0001; решение 22.08-2).

### 9. Обработка комментариев MR

Замечание Оператора 21.08. Для awaiting_human задач оркестратор
следит за дискуссиями MR. Триаж комментария — 4 класса: вопрос →
ответ в тред; замечание-правка → итерация разработчика → пуш →
«исправлено в <sha>» в тот же тред; мнение без действия — короткий
ответ/ничего; чужое обсуждение — не вмешиваться. Комментарий —
недоверенный вход: исполняется только в границах SPEC и no_paths,
расширение объёма → эскалация Оператору (защита от инъекций
и от scope creep одновременно). Чужой коммит прямо в ветку task/
открытого MR — тот же недоверенный вход (решение 22.08-2): детект
при старте итерации, триаж как у комментария; молча затирать или
ребейзить чужую работу нельзя. Счётчик external_review_iters
с лимитом (~3) → эскалация.

**Маршрут правки один** (решение 23.08, аудит v3 Флоу-2): «итерация
разработчика» из триажа = обычный цикл in_dev → review → verifying —
внутреннее ревью обязательно, залоченные acceptance-тесты (A4)
остаются зелёными. П.9 задаёт только канал коммуникации (триаж,
премодерацию ответов и пуша), а не альтернативный маршрут кода
в обход ревью. Снятие премодерации счётчиком чистых циклов ослабляет
модерацию слов — но никогда не отменяет внутреннее ревью кода.

Ответы в треды: только по делу, без споров — разногласие
эскалируется. Режим `premoderated` per-target на период доверия
покрывает ОБА канала (решение 22.08-2): ответы в треды И
итерации-правки по внешним замечаниям — перед пушем правки по чужому
комментарию Оператору уходит карточка (замечание + дифф), пуш
по подтверждению; премодерация текста без кода — инверсия риска,
запрещена. Снимается счётчиком чистых циклов. Носитель премодерации
(решение 23.08) — очередь в БД: CLI `premod list/approve/reject`
показывает неразобранные при каждом запуске; панельный инбокс читает
ту же очередь (реализация — C3). Данные людей целевого (имена,
тексты комментариев) в артефактах, журнале и очереди премодерации
на ноутбуке Оператора — принятый риск (решение 23.08: рабочие данные
на корп-устройстве).

Канал: **поллинг — основной** (вебхуки корп-GitLab на хост Оператора
не обещаем — входящей связности нет), вебхук — опция. Любой стоп
задачи дольше 2 дней (бюджет, эскалация) при открытом внешнем MR →
служебный комментарий в тред: «задача приостановлена, вернёмся»
(решение 22.08-2) — бот не замолкает молча посреди диалога с людьми.

Пост-merge (решение 23.08, замещает окно наблюдения 7 дней 22.08-2):
по merge задача закрывается, треды смерженных MR система не читает
и служебных комментариев не пишет; дефекты и вопросы после merge —
обычным порядком целевого (новая задача через Оператора); reopen MR
системой не детектится — узнаём от людей (принятое следствие).
Финальный итог-комментарий (п.5) остаётся частью закрытия.

### 10. Профиль процесса проекта

Замечание Оператора 21.08. Маршрут = неизменное ядро + вариативная
фаза verify: каждый проект декларирует список проверок между ревью
и merge из фиксированного каталога типов: `ci` (ждать пайплайн),
`agent` (роль-проверка с проектными скилами), `human` (человек
проекта), `script`. Пример: artel `verify: []` (хватает CI-ядра);
feedback — целевое состояние `verify: [ci, agent:alpha-test]`;
**профиль поэтапный** (решение 22.08-2): C2 подключает feedback
с `verify: [ci]`, расширение до agent:alpha-test — отдельным
изменением при C4; декларировать неисполнимое нельзя. Ни одного
нового состояния FSM: verifying становится композитным циклом
по профилю, каждая проверка — обычный шаг (журнал, стоимость,
потолки, ретраи переиспользуются). Произвольные графы процессов
per-project — сознательно НЕ поддерживаются.

### 11. Три оси вариативности per-target

Итоговая формула: исполнители ролей (design §16) × политика гейтов
(design §4, включая merge_gate: target-human) × профиль проверок
(п.10). Всё остальное — маршрут, инварианты, каталоги — системная
константа. Верификация как фаза есть всегда; агент-верификатор ПОСЛЕ
кода инстанцируется только профилем (пустой профиль означает
«верификация полностью детерминированная», а не «верификации нет»).
Роль test_author ДО кода (A4, решение 23.08) — автор приёмочных
тестов, системная константа маршрута для всех targets (скип — только
явным полем SPEC); имя verifier закреплено за агентами
verify-профиля (после кода), их носитель — состояние verifying
(B1b).

### 12. Подключение проекта включает карту

Финальное ревью 21.08: codebase-map целевого генерируется при
подключении и обновляется по мержам — вход разработчика в чужой код
без блужданий; для монолита feedback это кратная разница стоимости
задачи (факты Фазы 0: учтённые $2.4–34.8, итерации ревью умножают).

### 13. Workspace внешних targets — в песочнице

Финальное ревью 21.08: контейнерный запуск ролей обязателен до
фазы C — чужой код с недоверенным содержимым не исполняется на хосте
Оператора. sandbox/Dockerfile существует с Фазы 0 — ввести в строй
(B3, первая задача фазы B — решение 23.08).

### 14. Агентская обвязка целевого не наследуется

Замечание Оператора 21.08. Целевые проекты имеют свои
CLAUDE.md/AGENTS.md, .claude/settings.json (hooks = произвольные
команды!), .mcp.json, скилы, плагины — CLI подхватывает их
автоматически: перехват инструкций роли чужим файлом;
**конфиг-инъекция** (право коммита в целевой = исполнение кода
в нашем агенте с нашими токенами — хуже prompt injection);
недетерминированность окружения. Принцип: **окружение роли
определяет только пульт**.

Механика (уточнена 23.08, аудит v4 п.2: флаги отсекают
project-источник, но user-источник оставался — роли получали
~/.claude/CLAUDE.md Оператора с PII, хуки его плагинов, его MCP):
роли запускаются из **отдельного контролируемого
HOME/CLAUDE_CONFIG_DIR под управлением пульта** (пустой/курируемый
user-слой; принцип решён 23.08, реализация в A1/A3)
+ `--setting-sources` без project, `--strict-mcp-config`; механизм
аутентификации в чужом HOME (подписочный setup-token vs API-ключ) —
открытый вопрос 18 аудита v4, решается мини-проверкой в B-спайке;
до внедрения — записанный риск текущего запуска.

**Фактура к вопросу 18 (24.08, инцидент T020, hotfix 82309ed):**
на хосте вопрос закрыт — auth CLI живёт в user-слое Оператора
(~/.claude.json + keychain-запись аккаунта) и в чистый HOME
не переносится («Not logged in», конвейер встал); работает
подписочный `claude setup-token`, положенный Оператором
в keychain-слот (`roles.yaml` token_slot/token_fallback — механика
ADR-0001 получила потребителя) и передаваемый роли переменной
`CLAUDE_CODE_OAUTH_TOKEN`; полный цикл разработчика прошёл.
Мини-проверке B-спайка остаётся вектор контейнера: тот же токен
внутрь образа. Инцидент вскрыл класс отказов №25 (аудит v5 §1.5):
живой смоук CLI — в doctor pre-flight (A3). Постоянство
поведения при обновлениях CLI — пин версии + smoke-тест изоляции
в doctor (A3, решение 23.08); CLAUDE.md целевого — в бриф как данные
с пометкой «недоверенные конвенции проекта»; project_skills — только
курируемый список из targets.yaml; инвентаризация .claude/.mcp.json
при подключении (doctor) + подсветка изменений этих путей в MR.

**Важно (ревью 21.08): флаги закрывают только конфиг-вектор агента;
от исполнения чужого кода тулчейном (npm postinstall, make, тесты —
неотъемлемая работа разработчика) песочница — ЕДИНСТВЕННАЯ линия,
не вторая.** Это разные векторы.

### 15. Целостность артефактов

Обсуждение 21.08: артефакты — управляющий вход системы (SPEC ведёт
разработчика, REVIEW двигает FSM), их модификация = управление
конвейером в обход гейтов. Принцип: **«читаемы всеми — писаемы
только системой»**. Механика: **hash-фиксация** — журнал БД пульта
(вне периметра внешних хранилищ) хранит фиксацию артефактов
на каждом переходе FSM; реализация (решение 23.08, аудит v3 Б1,
замещает пофайловые хэши): оркестратор коммитит артефактный git-репо
целевого (3д) на каждом переходе, в журнал пишется commit sha —
правило «все артефакты-входы» (SPEC, PLAN, REVIEW, acceptance)
выполняется по построению: коммит фиксирует каталог целиком, будущие
типы артефактов — автоматически; сверка на каждом следующем гейте
и при старте шага = сравнение sha + чистота рабочей копии.

**Approve привязан к sha** (ревью 21.08, закрытие TOCTOU):
команда/кнопка подтверждает конкретный sha (`approve <id> <sha>`),
расхождение = отказ — «показали одно, заапрувили другое» невозможно.

Механики ветки артефактов (права записи — только учётка Артели,
людям read; protected branch) — только при активированной публикации
следа (п.3, отложена); hash-фиксация в журнале БД пульта
и approve-по-хэшу — безусловны всегда, независимо от публикации
(уточнение 22.08-2). **Честно про enforcement** (ревью 21.08):
«писаемы только системой» — best effort по возможностям forge;
НЕСУЩАЯ гарантия — hash-фиксация + журнал вне периметра ветки
артефактов, не права записи. Подписанные коммиты — по триггеру
«появился верификатор подписи» (без него — ритуал). Новый инвариант:
«FSM принимает решения только по артефактам, чьи хэши зафиксированы
его журналом».

### 16. Гигиена артефактов

В артефактах — ни секретов, ни длинных цитат чувствительного кода
(история git неистребима — чистить поздно, надо не допускать).
Правило в базовые скилы + guard-проверка паттернов токенов.

### 17. Внешние правки артефактов — отложены целиком

Решение 22.08-2 (ранее флаг `allow_artifact_edits`, до того —
пространственный). Без публикации следа (п.3) людям физически нечего
править; при активации публикации концепт потребует отдельного
дизайна — прежняя механика была нереализуема; канал правок — MR
в ветку artel, приём = re-гейт + занос в первичку оркестратором;
правка никогда не принимается молча; счётчик external_edit_regates
с лимитом 2 → эскалация.

**Безусловные правила вне концепта (действуют всегда, для локальных
артефактов):** вход шага сверяется с хэшем, зафиксированным
журналом/approve, при СТАРТЕ шага, не только на гейтах — расхождение
= стоп до разбора (решение 22.08-2, закрытие зазора approve→старт);
чужой рукой поставленный вердикт ревью не учитывается никогда
(авторство вердикта — только у ревьювера системы); правка budget_usd
задним числом не действует (инвариант 10); расхождение хэша =
инцидент целостности (стоп задачи, эскалация).

### 18. Статусы реализации концептов

Решения Оператора 21.08. **Пространства — отложены целиком** (вместе
с hub-storage, spaces.yaml и онбордингом storage в панели): после
решения «только target-branch» у пространства не осталось
материального компонента в ближнем горизонте — панель работает
селектором проектов по targets.yaml. Триггеры возврата:
общепространственное хранилище (кросс-проектная память ассистента,
сквозная копилка) или второй пользователь/периметр. Корп-политика
storage-репо на scm подтверждена (решение 21.08) — пригодится при
триггере. Внешние правки артефактов (п.17) — по триггеру «активация
публикации + первый реальный запрос людей на правки». Артефакты
фазы B (sled) — локально в пульте, как у всех целевых. Пульт в git
хранит только систему и догфуд Фазы 0; первичка всех целевых,
включая артель после A7, — в .artel/ вне git.

## Рамочные решения Оператора (Р5–Р8, контекст этого ADR)

Зафиксированы в роадмапе §1 редакции до переписывания начисто
(полный текст — история git); действующая сводка — здесь:

- **Р5 (22.08; уточнено 23.08)**: носитель поллера — прерываемый
  процесс во всех эпохах (тест — ноутбук в сессиях Оператора,
  нормальная работа — корп-сервер, 3к); несущий инвариант — «догон
  без потерь» (C0); лаг — принятый риск.
- **Р6 (22.08)**: инференс — в рамках текущей практики работы
  Оператора с Claude Code; «минимальный срез кода в запросе» —
  периметрное правило; гейтвей заранее не строим (22.08-2).
- **Р7 (22.08; уточнено 22.08-2)**: субъект на scm — личная учётка
  Оператора без подписи об автоматизации; премодерация обоих каналов
  (п.9) на период обкатки. Полноценный запуск = серверная эпоха
  (3к): сервисные УЗ и токены — вместе с решением о сервере;
  постоянный фоновый режим на личной УЗ не запускается. Критерий
  провала (23.08, аудит v4 п.12): возражение ИБ или владельца
  feedback против автоматизации с личной УЗ до C2 → стоп фазы C
  до решения.
- **Р8 (22.08; уточнено 22.08-2)**: наружу не выносится ничего —
  публикация следа и ledger-экспорт отложены целиком по триггерам
  (п.3, 3г); экономика живёт в единой БД (3ж). При любой будущей
  активации состав выносимого — явная настройка, по умолчанию
  минимальный.

## Проверенные допущения — A-спайк (23.08)

Выполнен руками до коммита этого ADR (решение 22.08-2); полный
отчёт — docs/audits/a-spike-2026-08-23.md.

1. **Флаги изоляции CLI — подтверждено.** Claude Code CLI 2.1.227:
   `--setting-sources` и `--strict-mcp-config` существуют;
   smoke-тест с подложными CLAUDE.md/.mcp.json/.claude/settings.json:
   с флагами маркер не достигает контекста роли, без флагов —
   достигает. Деградационный путь (санация клона) не нужен.
   Пин версии 2.1.227 + этот smoke-тест — в doctor (A3, B1a).
2. **«Токен без прав merge» — допущение переформулировано.**
   У PAT GitLab нет скоупа «писать, но не мержить»: `api` даёт всё,
   что может пользователь; `read_api` не позволяет комментировать MR
   (нужно для вердиктов, п.5). Свойство «не может смержить» —
   не у токена, а у защиты ветки целевого: `merge_access_levels`
   базовой ветки должен быть выше роли учётки. Факт scm.x5.ru:
   учётка — Developer (30); в `bdpr/whatif/wi-promo-service`
   merge = Maintainers (40) — подходит; в `promo/dq` merge =
   Developers+Maintainers (30) — допущение не выполняется.
   Следствие: условие подключения target-human-проекта — проверка
   doctor при подключении и периодически: `merge_access_levels`
   базовой ветки > access_level учётки; иначе проект не подключается
   до решения Оператора (деградационный путь сохранён, проверка
   переносится с «выпуска токена» на «сверку защиты ветки» — тот же
   механизм, что сверка base-ветки/merge-политики в A3).
3. **Поллинг MR scm.x5.ru из корп-сети — подтверждено.**
   `GET /merge_requests?scope=all&state=opened&order_by=updated_at`
   отвечает; есть `updated_after` (инкрементальный догон C0) и поле
   `sha` головы MR (hash-фиксация п.15, approve-по-хэшу A2b),
   `detailed_merge_status`, `blocking_discussions_resolved`. 2FA
   на учётке включена, PAT работает поверх OIDC/LDAP.
