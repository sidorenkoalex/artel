# ADR-0020: Долгоживущие приёмочные тесты пишутся сразу в tests/

Статус: принят. Дата: 29.09.2026. Решение Оператора (утверждено «ок по
рекомендациям» 28.09.2026). Сужает ADR-0018, пункт 2; дополняет ADR-0012
(правка зафиксированных приёмочных тестов распространяется на файлы в
`tests/` ветки задачи); закрывает вопрос, отложенный в «Следствиях»
ADR-0018, и триггер №28 реестра `docs/triggers.md`.
Исполнено (29.09.2026) задачами 01M3MVXZXF25KYY2P213E0M39X,
01M3N0BWYQ9KHVN41Z4G72706R, 01M3N3Z1ZHTGMSQZ4SNRYNJ2SJ,
01M3NSZ4YWZW9SD5Y6H62ATGRV и 01M3NMHHAMTFN2BNKBN209E15M. Уточнение
пункта 2 от 29.09.2026 отложено (блок после пункта 2). Пересмотрено
ADR-0021 (29.09.2026): пункты 1 и 3 — с этапа 1, пункт 12 — с этапа 3,
пункт 2 — на этапе 4.

## Контекст

Приёмочные тесты задачи пишет роль test_author до кода, в каталоге
`tasks/<id>/acceptance_tests/` ветки документов `artifact/<id>`; на
выходе из состояния `tests_writing` они фиксируются (инвариант 27), и
разработчик подгоняет код под них. После мержа их не исполняет никто
(ADR-0018, пункт 2): CI гоняет только `tests/`, а сами тесты уходят в
архивную ссылку `refs/artifacts/<id>`.

Из этого следуют два подтверждённых дефекта.

1. Свойство, которое обязано держаться после мержа, после мержа никто не
   сторожит, если разработчик не написал ему отдельный тест в `tests/`.
   Ревью 28.09 сделало это замечание в трёх задачах подряд:
   01M3KE8ZJXFARS6KC441PCDCQV (механизм фикстуры каталога без теста в
   `tests/`), 01M3M55070T5NJFYM3QQJH4B9V (порядок проверки входа Codex),
   01M3MHBNMT1VDXSRQNV1GX30BV (синтетический ответ канарейки). Каждое
   замечание стоило задаче лишнего круга ревью. Временная мера —
   правило ревьювера «свойство, обязанное держаться после мержа, — в
   `tests/`» (`skills/review-checklist.md`) — ловит дефект, но не
   устраняет его причину.
2. Разработчик дублирует приёмочные тесты. Замер 27.09 по девяти
   смерженным задачам: из 164 тестов, добавленных разработчиком в
   `tests/`, 102 повторяют приёмочные тесты задачи; из 154 приёмочных
   тестов 72 повторены полностью, 34 частично. Частичный повтор слабее
   оригинала: проверка опускается на уровень внутренней функции, и
   сквозная проверка команды теряется. Разработчики прямо пишут в
   заголовках файлов, что повторяют приёмочные тесты, потому что те не
   исполняются после мержа.

Проба 27.09 (перенос приёмочных тестов трёх задач в `tests/` в отдельном
клоне) показала, почему нынешние файлы нельзя просто переложить: без
правок зелёные 39 тестов из 67; вспомогательные модули одного имени
(`_util.py`, `_sandbox.py`) у разных задач дают 126 ошибок сбора при
совместном прогоне; корень репозитория вычисляется глубиной каталога;
часть тестов проверяет факты именно этой задачи (разница с базой ветки,
«файл не тронут», чтение `tasks/<id>/`) — у задачи-рефакторинга 13 из 20.

Практика согласна с направлением. Разработка через приёмочные тесты
(ATDD) и спецификация на примерах (Specification by Example, Адзич)
считают приёмочные тесты-свойства постоянной частью набора — «живой
документацией», исполняемой на каждой сборке; в Cucumber сценарий в
работе после прохождения переходит в регрессионный набор. Конвейеры
агентов 2025–2026 (GitHub Spec Kit, Kiro) пишут тесты сразу в основной
тестовый каталог проекта, отдельного архива приёмочных тестов у них нет.
Проверки конкретного изменения («в диффе есть X», «файл не тронут»),
наоборот, держат вне постоянного набора (эталонные наборы задач агентов,
правила уровня запроса на слияние). Фиксация тестов до кода с доступом
исполнителя только на чтение и механической сверкой — модель эталонного
набора SWE-bench (эталонный тестовый патч накладывается поверх работы
агента) и вывод исследования ImpossibleBench: доступ к тестам только на
чтение исключает правку тестов агентом, не ухудшая честные результаты.
Известная дыра той же модели — подмена настроек сбора тестов
(`conftest.py`, `pyproject.toml`); её закрывает отдельная задача
01M3MVXZXF25KYY2P213E0M39X (защищённые пути для настроек сбора тестов),
которая идёт первой и является предпосылкой этого решения.

## Решение

1. **Две группы приёмочных тестов.** test_author пишет приёмочные тесты
   двух групп.
   - Долгоживущие — свойства кода, которые обязаны держаться после
     мержа. Пишутся сразу в `tests/` кодовой ветки задачи
     `task/<id>-…` по правилам `tests/`: обращение к коду только через
     публичный интерфейс (команды пульта, публичные функции модулей);
     строка «Ловит мутацию: …» в докстринге каждого тестового метода;
     общие помощники — из `tests/sandbox.py`, без собственных
     вспомогательных модулей задачи (`_util.py`, `_sandbox.py`).
   - Разовые — факты именно этой задачи: разница с базой ветки, «файл не
     тронут», чтение `tasks/<id>/`. Пишутся, как сейчас, в
     `tasks/<id>/acceptance_tests/` ветки документов `artifact/<id>` и
     после мержа уходят в архив `refs/artifacts/<id>`.
   Пересмотрено ADR-0021, пункт 3 (29.09.2026, с этапа 1): ветки
   документов `artifact/<id>` нет; разовые тесты живут в ссылке
   `refs/artifacts/<id>` от `new` до конца жизни задачи.
2. **Пометка группы.** Каждый файл приёмочных тестов несёт в докстринге
   модуля строку, называющую его группу. Отсутствие строки — ошибка
   guard, а не значение по умолчанию. На выходе из `tests_writing`
   пульт проверяет каждый долгоживущий файл: он не читает `tasks/`, не
   обращается к git, не ссылается на номер задачи; у каждого метода есть
   строка «Ловит мутацию: …»; файл собирается pytest (сухой сбор, без
   исполнения). Нарушение — отказ перехода с именем файла и метода, пока
   исправить его может сам test_author, а не Оператор через
   `amend-tests`.

   **Уточнение пункта 2 от 29.09.2026 — отложено, в коде не
   исполнено.** Предлагалось: (а) внутри временной копии репозитория,
   которую строит `tests/sandbox.py`, разрешить пути `tasks/`, ветки
   документов и вызовы git, а запрещать только привязанное к
   настоящему репозиторию — путь от корня репозитория или от
   `Path(__file__)`, ветку или историю задачи, разницу с базовой
   веткой; (б) на выходе из `tests_writing` и на гейте мержа прогонять
   долгоживущие файлы в изолированной выгрузке кодовой ветки — без
   `.git` и без `tasks/`, с временными рабочим каталогом и `HOME`;
   (в) запретить долгоживущему файлу пропуск проверок (`skipTest`,
   `skipIf`, `unittest.skip`, `pytest.skip`) по тексту и по отчёту
   прогона. Задача 01M3P0SQQM453G9DP3NVDVGC49 ликвидирована решением
   Оператора 29.09.2026. Причина: документы задачи выкладываются внутрь
   рабочей копии кода, и прогон в выгрузке — заплата от этого
   устройства; устройство меняет ADR-0021. До этапа 4 ADR-0021
   действует строгая проверка по тексту (задача
   01M3N0BWYQ9KHVN41Z4G72706R): литерал `tasks/`, импорт
   `gitcmd`/`artifact_branch` и вызов git в долгоживущем файле — отказ,
   в том числе внутри временной копии. Часть (б) отклонена ADR-0021
   («Отклонённые альтернативы»); части (а) и (в) пересматриваются на
   этапе 4 ADR-0021.
3. **Фиксация.** На выходе из `tests_writing` в ветке документов
   записывается перечень «путь → контрольная сумма» долгоживущих файлов;
   перечень фиксируется вместе с разовыми тестами. Гейт сверяет суммы
   файлов кодовой ветки с перечнем на каждом переходе после
   `tests_writing` и на гейте мержа после подтяжки `main`; расхождение —
   отказ перехода. Разработчик долгоживущие файлы своей задачи не
   правит. Правка — только командой `amend-tests` по решению Оператора
   и в границах ADR-0012; команда распространяется на файлы в `tests/`
   ветки задачи, счётчик правок («больше одной правки на пять задач»)
   общий.
   Пересмотрено ADR-0021, пункт 3 (29.09.2026, с этапа 1): перечень
   записывается в ссылку `refs/artifacts/<id>`, а не в ветку
   документов.
4. **Разработчик дописывает тесты только на непокрытое.** Свойство,
   которое уже держит долгоживущий приёмочный тест, разработчик в
   `tests/` не повторяет.
5. **Имена файлов.** Имя долгоживущего файла несёт префикс, однозначно
   выводимый из id задачи. Две параллельные задачи не могут создать файл
   с одним путём: `tests/` входит в общие зоны, и гейт зон такого
   столкновения не видит.
6. **После мержа** долгоживущие файлы — обычная часть `tests/`: их
   исполняет CI, их покраснение — дефект, правка идёт по общим правилам
   `tests/` и гейта неослабления тестов. Перечень сумм в архиве задачи
   становится исторической записью и больше ни с чем не сверяется;
   каноническим экземпляром остаётся файл в `tests/`.
7. **Узкое право test_author на кодовую ветку.** test_author вправе
   только ДОБАВЛЯТЬ новые файлы под `tests/` кодовой ветки своей задачи.
   Изменение, переименование или удаление существующих файлов и любые
   правки вне `tests/` откатываются пультом, как сейчас
   (`orchestrator/checkpoint.py`, правило введено после инцидента
   01M1KT0792125J9ZNJNZJ86E9Q). Гейт на выходе из `tests_writing`
   проверяет это вторым рубежом: дифф кодовой ветки против её базы
   содержит только добавленные файлы `tests/` с префиксом задачи.
8. **Вывод устаревших долгоживущих тестов.** Требования меняются, и тест
   вместе с ними.
   - Замена чужого долгоживущего теста — только через приёмочные тесты
     новой задачи: её test_author пишет новый долгоживущий тест и
     называет в докстринге модуля заменяемый тест; старый тест снимается
     в той же задаче по мандату Оператора на ослабление тестов (гейт
     неослабления не меняется).
   - Удаление без замены (дубль, устаревшее свойство) — решением
     Оператора по итогам ревизии кодовой базы.
9. **ADR-0018 сужается.** Пункт 2 («приёмочные тесты смерженной задачи
   не исполняются и не чинятся») действует только для разовой группы.
   Пункты 3 и 6 — без изменений. Строка «Следствий» ADR-0018 о переносе
   приёмочных тестов в `tests/` заменяется ссылкой на это решение.
10. **Временное правило ревьювера сохраняется.** Правило
    `skills/review-checklist.md` «свойство, обязанное держаться после
    мержа, — в `tests/`» остаётся, пока схема не проработает 2–3 задачи;
    снимается отдельной строкой бэклога по итогам этих задач, а не
    мержем задач внедрения.
11. **Канарейка** проходит схему так же, как боевые задачи. После
    внедрения базовые строки замера канарейки (ADR-0019) снимаются
    заново: число шагов и стоимость ролей test_author и developer
    сдвигаются.
12. **Область действия** — собственный репозиторий пульта (target
    `artel`, `config.DEFAULT_TARGET`). Для внешних проектов поведение не
    меняется; распространение на них — отдельным решением: у них свой
    стек и своя раскладка тестов, а гейты заявки мутации и неослабления
    тестов работают только для собственного репозитория.
    Пересмотрено ADR-0021, пункты 8 и 9 (29.09.2026, с этапа 3):
    проверки распространяются на любой проект с профилем тестов в
    `targets.yaml`; проект без профиля работает только с разовыми
    тестами.

## Отклонённая альтернатива: копирование пультом

Рассматривался вариант, в котором test_author пишет все приёмочные
тесты, как сейчас, в ветку документов, а пульт после фиксации копирует
долгоживущие файлы в `tests/` кодовой ветки и сверяет копию с
оригиналом (строка бэклога 27.09, черновик задания от 28.09). Отклонён,
потому что по коду он дороже и хрупче (ревью схемы 28.09):

- файл обязан собираться и проходить в двух местах: вычисление корня по
  глубине каталога и импорт помощников по голому имени ломаются при
  переносе (126 ошибок сбора в пробе 27.09);
- любое место копии оставляет дыру: на верхнем уровне `tests/`
  помощники задачи нарушают инвариант импортов
  (`tests/test_invariants.py`, `StdlibOnlyImportsInvariantTest`), а
  подкаталог не видят гейт заявки мутации и тот же инвариант; закрытие
  дыры требует правки защищённого `tests/test_invariants.py`;
- `amend-tests` становится записью в две ветки без атомарности:
  сбой между коммитами разводит оригинал и копию и даёт ложный отказ
  сверки;
- вопрос общих помощников не решается: копии помощников каждой задачи
  фиксируются в `main`, никем не расширяются и молча расходятся;
- после мержа остаются два экземпляра одного теста, и неясно, какой из
  них канонический.

Запись сразу в `tests/` убирает модуль копирования, требование «файл
работает в двух местах», двухветочный `amend-tests` и отдельную сверку
«копия равна оригиналу». Цена — узкое отступление от правила
«test_author не коммитит в кодовую ветку» (пункт 7), проверяемое гейтом.

- Правки скилов (`skills/test-authoring.md`, `skills/coding-standards.md`,
  `skills/review-checklist.md`) и `docs/invariants.md` (инвариант 27:
  лок распространяется на перечень долгоживущих файлов) — приложениями к
  PLAN задач внедрения. Строки бэклога 28.09 «Правило „свойство кода —
  двойник в tests/“ в правилах автора тестов и разработчика» и «сторож
  проверяется временной мутацией кода» вливаются в задачу 1; строка
  бэклога 27.09 «Перенос приёмочных тестов в tests/ в ветке задачи»
  закрывается этим решением.
- Правки ADR-0018 по пункту 9 и строки триггера №28 в `docs/triggers.md`
  (правило ревьювера снимается не мержем задачи, а отдельной строкой
  бэклога) вносит Оператор коммитом вместе с этим ADR. Исполнено
  29.09.2026 (коммиты 314449f1 и 04ca6c28).
- ADR-0019, пункт 1, строка «тесты»: пересмотр, предусмотренный его
  «Следствиями», по-прежнему открыт — долгоживущие файлы добавляют в
  `tests/` сквозные проверки команд пульта.
- Ветка задачи до работы разработчика красна: CI `task/**` падает на
  долгоживущих тестах, пока нет кода. Пульт читает CI только головы
  ветки на `verifying`, автогейте и мерже, поэтому конвейер не ломается;
  цена — красные промежуточные прогоны и минуты CI.
- Набор `tests/` растёт на 5–15 тестов на задачу; время полного прогона
  и потолок `config.FULL_SUITE_TIMEOUT_SEC` автогейта нужно держать в
  поле зрения. Перекрывающиеся тесты выводит ревизия кодовой базы
  (пункт 8).
- Приёмочные тесты уже смерженных задач не переносятся: их свойства,
  оставшиеся без теста в `tests/`, при необходимости покрываются
  отдельной задачей по тому же критерию групп.
- Два риска существовали и до этого решения, но без защиты; решение
  их не создаёт, а меняет вес, поэтому защита вводится вместе с ним
  (решение Оператора 29.09.2026).
  - **Подгонка кода под конкретные входы теста.** До решения против неё
    не было ни правила, ни проверки; невольной страховкой служили
    повторные тесты разработчика на других входах — пункт 4 их убирает,
    риск растёт. Защита в задаче 1: пункт проверки ревьювера «код решает
    задачу в общем виде, а не для входов теста»; правило test_author
    проверять свойство на нескольких входах, а где естественно — на
    входах, порождаемых при каждом запуске модулем `random` с печатью
    зерна для воспроизведения (сторонние библиотеки в тестах не
    допускаются). Скрытые приёмочные тесты, которых разработчик не видит
    (модель SWE-bench), отложены строкой бэклога 29.09 до 2–3 задач по
    этой схеме или первого зафиксированного случая подгонки.
  - **Привязка долгоживущего теста к внутреннему устройству кода.** До
    решения такой тест уходил в архив после мержа и не мешал; теперь он
    живёт в `tests/` и мешает каждой будущей переделке — риск растёт
    заметно. Защита в задаче 1: правило пункта 1 (только публичный
    интерфейс) проверяется на выходе из `tests_writing` разбором файла —
    отказ при импорте имени с подчёркиванием, подмене внутреннего имени
    (`patch` пути к имени с подчёркиванием) и обращении к закрытому
    атрибуту; ревьювер проверяет границу групп и то же правило;
    разработчик, которому тест навязывает устройство кода, эскалирует
    (строка в правилах эскалации), ответ Оператора — правка теста
    командой `amend-tests` по ADR-0012. Привязку к внутреннему формату
    результата публичной функции разбор не ловит — это остаётся за
    ревьювером.
