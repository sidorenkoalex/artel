# ADR-0004: Пульт и ассистент Оператора

Дата: 2026-08-24. Статус: принят (Р2 утверждён Оператором 23.08;
состав — роадмап §3, решения слоями 20–23.08; разрез Р4 утверждён
23.08 и переигран вечером 23.08 — панель в монорепо).

## Контекст

Оператор управляет конвейером через CLI и чтение БД/логов; с ростом
числа проектов и задач нужен пульт — панель наблюдения и гейтов —
и рамка для чат-ассистента. Ключевые риски, из которых выведены
решения: необратимые действия как приз prompt injection; сервер без
auth; ассистент как неучитываемый расход и вектор долговременного
влияния через память. Нумерация пунктов — сквозные якоря (п.1–9),
на них ссылаются роадмап и design.md.

## Решение

### 1. Разрез системы и панели

Решение по Р4 (утро 23.08, переиграно вечером 23.08); носитель
этапа 1 — решение по аудиту v4 п.19.

**Панель — в монорепо artel** (Р4, вечер 23.08). Первоначально
планировалась отдельным приватным репо-target («API рождается
принудительно честным»); после A7 (артель сама идёт внешним флоу)
аргумент границы доверия ушёл: репозиторная граница ≠
runtime-граница — панель опасна в рантайме (чужой ввод, чат, рендер
текстов целевых), от этого защищает отдельный **процесс** + доступ
только через HTTP API, что делается и в монорепо. Честность API
обеспечивает инвариант-тест границы импортов: пакет `panel/`
не импортирует state/БД/оркестратор, только HTTP-клиент. Что даёт
монорепо: одна фича = один MR (главная экономия wall-clock при лаге
гейтов «часы–дни»); дрейф API↔панель ловится одним CI-прогоном; нет
второго приватного репо и второго пина. Задачи панели идут через A7
тем же внешним флоу. Второй проект фазы B — `sidorenkoalex/sled`
(механика внешнего режима на коде, который НЕ пульт).

**Этап 1 — без демона** (решение 23.08, аудит v4 п.19):
`artel report` генерирует статический HTML из state.db (борд,
метрики, журнал, алерты; обновление при каждом запуске CLI или
watch-режимом) — для read-проекции постоянный процесс не нужен,
live-лог этапа 1 — терминал, где конвейер и так запущен.
**Демон + HTTP API (FastAPI + SQLite + WebSocket) появляются
на этапе 2 вместе с Г1a**: сервер рождается одновременно с первой
write-операцией и её auth, а не живёт этап без защиты. Эндпоинты =
те же команды поверх модулей T015; `panel/` — отдельный процесс
(с этапа 2): веб-морда, потребитель API (статика может отдаваться
сервером artel — деплой одним процессом). Граница — не репо,
а процесс + инвариант-тест импортов (для report-генератора этапа 1 —
тот же инвариант: только чтение state.db через store, никакой
записи). Панель — read-проекция; запись — только явные операторские
контролы; доступа к БД у веб-панели нет конструктивно.

### 2. Блоки панели

Проекты (подключение: запись targets.yaml; ветка artel — только при
активации публикации, ADR-0003 п.3; переключение — селектор;
пространства как надстройка — по триггеру ADR-0003 п.18); борд задач
по состояниям FSM + карточка с live-логом агента; метрики
(стоимость, итерации, размер пакетов, тренды); инбокс ручных гейтов
с контекст-пакетами и кнопками; чат Оператора.

### 3. Три категории сущностей системы

Фиксация в дизайне: оркестратор (код, решений не принимает), роли
конвейера (эфемерные, контракт артефактов), **ассистент Оператора**
(сессионный, матрица полномочий). Правило «шляпы»: исполняя роль
(драфт SPEC = hybrid-аналитик), ассистент проходит её гейты. Штатный
исполнитель spec_writing — роль analyst конвейера (A5, решение
23.08); «шляпа» — альтернативный исполнитель той же роли, теми же
гейтами.

### 4. Матрица полномочий ассистента

Читать всё — свободно; new/SPEC-драфт/advance/auto/report —
самостоятельно; approve/reject **обратимых** гейтов — только
по явной команде Оператора (журнал: operator-via-assistant);
**всё необратимое — merge_gate, деньги, деплой, kill, конфиги —
никогда из чата, только кнопка/CLI Оператора** (решение 21.08
по находке ревью: merge необратим и главный приз инъекции; текст
«да, мержи» — не подтверждение; инъекция не может нажать кнопку).
Чат готовит карточку решения и даёт ссылку на кнопку. Страница
кнопки рендерит системный контекст-пакет — артефакты из первички
.artel/ со сверкой их хэшей с журналом БД перед рендером,
расхождение = кнопка блокируется + алерт (уточнение 23.08: артефакты
живут в файлах, в БД — хэши и журнал); карточка ассистента —
навигация, не источник правды (решение 22.08-2: хэш закрывает
подмену артефакта, это — искажение представления).

### 5. Учёт и лимиты ассистента

actor=assistant в общем журнале, дневной/недельный бюджет (алерт
70%, стоп 100%, поднимает человек), rate-limit команд, счётчик
ошибок ассистента (assistant-error), метрики: доля принятых как
предложено решений, overhead ratio ($ ассистента / $ конвейера),
стоимость «что происходит?»; порог отключения по overhead ratio
задаётся при Ч3 по первым двум неделям данных (решение 22.08-2).

### 6. Дизайн — триада вместо роли

Решение Оператора 20.08: design-system как разовая задача-артефакт
+ скил ui-standards разработчику + визуальная приёмка скриншотами
(расширение верификатора). Роль «дизайнер» не заводится (критерий
design §2).

### 7. Этапы

(1) read-only панель [+ интерактивный макет артефактом ДО кода];
(2) auth + гейты-кнопки; (3) чат ассистента — **основной путь:
MCP-сервер артели + Claude Code как ассистент** (решение 23.08,
аудит v4 п.20), не своё приложение: к этапу 3 API уже есть (Г0) —
MCP-обвязка поверх него почти бесплатна; матрица полномочий живёт
на стороне сервера (MCP отдаёт и принимает только разрешённое:
read-инструменты; команды — через очередь premod), собственный shell
ассистента к артели не подключён; минусы приняты: чат в терминале,
не в панели; overhead ratio считается по журналу MCP-вызовов.
**Agent SDK-приложение — по триггеру «MCP-вариант упёрся»**
(несчитаемый overhead, невыразимая матрица, подтверждённая нужда
во встроенном чате панели; строка в docs/triggers.md);
(4) событийный оркестратор поглощает auto (события forge —
поллинг/вебхук по ADR-0003 п.9 и 3к).

**Триггер демонизации — один**, из A6(д): поток задач в неделю,
считает doctor (решение 23.08, аудит v4 п.10); «этап 4» — носитель
работ, не второй триггер.

Критерии выхода этапов (решение 23.08; ред. по аудиту v4 п.19):
этап 1 — Оператор читает состояние конвейера в report-странице
вместо чтения БД/логов (факт использования, не деплоя); этап 2 —
первый ручной гейт пройден кнопкой с approve-по-хэшу; этап 3 —
неделя работы ассистента без единой операции мимо матрицы
полномочий, overhead ratio посчитан. Телеграм понижен
до нотификатора со ссылками (или отменяется).

**Деплой пульта** (решение 22.08-2, система обновляет сама себя):
рестарт на новом коде — только без шагов в полёте (awaiting_human
не мешает — состояние в БД); механика — команда `drain`: текущие
шаги дорабатывают, новые не стартуют, рестарт, снятие drain.

Чат ассистента (этап 3) — только после go/no-go программы (решение
23.08, аудит v3 В2: до точки решения ассистент не добавляет ничего
в её критерии).

### 8. Рамка чат-ассистента «как в рабочей сессии»

Обсуждение 21.08. Непрерывные сессии с компакцией; **память
ассистента — в наблюдаемой области пульта** с журналом изменений,
правится Оператором (память = вектор долговременного влияния:
инъекция в неё отравляет все будущие сессии — потому прозрачна);
инструменты — ТОЛЬКО API артели + чтение пульта — без
`.artel/projects/*/workspace/` и knowledge/ целевых (периметр кода,
ADR-0003 3а; артефакты tasks/ доступны — нужны для работы), ревизия
памяти включает проверку «нет цитат кода целевых» (решение 22.08-2);
**жёсткий потолок размера памяти** (решение 23.08, аудит v3
Чистка-5: единственный накопитель, напрямую входящий в контекст
каждой сессии) — ревизия = компакция до потолка, не только проверка;
о прошлых задачах память хранит указатель на RETRO.md (P3),
не пересказ. **Никакого shell и файлов хоста** («ассистенту
не хватает shell» = дырка в API = задача конвейеру); правка
системы — только задачей через гейты, не коммитом; **провенанс**:
рекомендация на основе недоверенного источника (логи, MR-комменты,
код) приходит со ссылкой на источник; одна активная сессия на пульт
(вторая вкладка — read-only); панель полнофункциональна без
ассистента.

Формула: сегодняшний ассистент минус shell и операторские коммиты,
плюс наблюдаемая память, плюс кнопочные подтверждения критичного.

**Процедура расширения API** (ревью 21.08: давление «ассистенту
не хватает инструмента» будет постоянным): запрос нового инструмента
= задача конвейеру с гейтами, никогда — исключение в рантайме; иначе
рамку сломают первым же «почему упал шаг».

### 9. Интерфейсы агентов — контракт

Команды CLI/API, форматы артефактов, структура промптов и брифов
меняются аддитивно; ломающее изменение — только с миграцией скилов
в том же MR.

## Последствия

- Задачи этапов (П1, П2′, П4; Г0, Г1a, Г1b, Г2; Ч1′–Ч3), их бюджеты
  и порядок — в роадмапе; этот ADR — нормативный источник решений.
- design.md получает суперсид-пометку §14 (телеграм-инбокс понижен
  до нотификатора, п.7 этого ADR); прежняя роль телеграм-бота как
  главной поверхности MVP отменена.
- Инвариант с тестом (Г2): API отклоняет необратимые операции для
  actor=assistant независимо от содержимого запроса.
