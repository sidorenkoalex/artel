# ADR-0032: Цена и рост набора тестов — размеры, поверхность решения в критериях, общее состояние, чистка по мутациям

Статус: принят 08.11.2026, не исполнен. Решение Оператора 08.11.2026 («ок по рекомендациям» — к вопросам 1–5 черновика: ориентиры размеров, обоснование больших проверок, порядок этапов, зависимость покрытия, номер; см. «Решения Оператора»). Черновик прошёл независимую проверку (вторая редакция). Класс по ADR-0002 — изменение правил тестов и гейтов: решение только Оператора. Дополняет ADR-0020 (долгоживущие приёмочные тесты), ADR-0027 (тесты в стиле pytest), ADR-0031 (один полный прогон на дерево кода). Не меняет: «тест до кода», «только публичный интерфейс», гейт неослабления, лок планки и счётчик ADR-0012, линт детерминизма, пределы 1500 с, 40 мин CI и 120 с на тест, место и число полных прогонов по ADR-0031.

## Контекст

ADR-0031 решает, **где и сколько раз** гоняется полный набор. Этот ADR — о том, **сколько стоит сам набор и как быстро дорожает**: даже один прогон на дерево упрётся в предел, если каждая задача добавляет десятки сквозных тестов.

Данные: журналы прогонов `.artel/logs/`, замер длительностей 24.10 (`01M5N8A5JB`), 240 серий прогонов мутаций до 25.10, статический разбор `tests/` на `8f5ee80e`. Числа из журналов воспроизводятся по `.artel/logs/`, но не по репозиторию.

- **Рост.** 27.10 — 8169 тестов, 08.11 — 9840: около 140 тестов в день. Полный набор на гейте — с 786 до 1073–1104 с при пределе 1500 с (`targets.yaml:53`), 04.11 под нагрузкой — 1276 с. CI идёт 20–27 мин при `timeout-minutes: 40` (`.github/workflows/ci.yml:216`, `:269`; ADR-0031, «Контекст»). При нынешнем темпе запас локального предела — около 2–3 недель.
- **Время сосредоточено в тяжёлых тестах.** Тесты дольше 3 с — 1219 из 6850 (18 %), 84 % суммы. Медленные тесты на отказ, «ничего не изменилось» и текст сообщения — 562 теста, около 4990 с, 39 % суммы (по именам тестов — оценка).
- **Подготовка дешёвая, дорого действие.** Общие песочницы `tests/sandbox.py` готовятся за 20–40 мс на тест (замер 08.11). Время — в самой команде пульта: вызовы git, дочерние процессы, вложенный pytest, живые процессы (разбор 24.10: в 9 из 15 тестов 66–88 % времени — git).
- **Правило о чистых функциях есть, но держится не везде.** `skills/test-authoring.md:192-196` требует проверять чистую функцию, разбор, формат текста и таблицу решений модульным тестом без песочницы, а песочницу брать только для связки «команда — FSM — база — git». Тест пишется до кода и только через публичный интерфейс (`:3`, `:98`). Если SPEC не называет публичную функцию решения, у test_author нет имени, к которому обратиться, и правило проверяется через команду. Где SPEC имя назвал, правило соблюдается: в `tests/test_01m4nz5qrb7mneycwgxewvwfp0_mandate_matrix.py` свойства формы матрицы проверяются прямым вызовом `mandate.matrix_refusals` (докстринг файла, строка 15). Аналитик сейчас такое имя не обязан называть: «SPEC — не карта реализации» (`skills/spec-authoring.md:165`).
- **Связка «по каждому состоянию» дорога, но это законная цена.** В том же файле отказ мандату без раздела матрицы проверяется через `cmd_answer` на песочнице с настоящим git в каждом состоянии `MANDATE_STATES` — около 4 с на тест. Это свойство связки, оно должно остаться; дорого то, что состояние каждый раз засевается с нуля.
- **Нет общего состояния.** В 402 файлах задач (все — долгоживущие: разовые по ADR-0020 п. 1 в `tests/` не попадают) нет ни одной фикстуры уровня класса или модуля; `setUpClass` нет, `setUpModule` — в трёх файлах.
- **Перекрытие по мутациям.** В 240 сериях (2401 мутация) из 2996 тестов, убивших хотя бы одну мутацию, тот же набор мутаций убивают 1351. Это верхняя оценка: в сериях только заявленные мутации волн консолидации, и тест может уникально ловить незаявленные. 313 мутаций (13 %) не убил ни один тест, хотя заявка «Ловит мутацию» на них была.
- **Паузы.** Линт детерминизма (`orchestrator/test_lint.py`, guard на выходе из `tests_writing`, `scripts/guard.py:4508-4523`) уже отказывает новым файлам на `time.sleep` с ненулевой паузой и на ожидании «до срока». Вызов `time.sleep(` остаётся примерно в 45 старых файлах; часть — в тексте дочерних сценариев и образцах линта.
- **Распределение по рабочим.** Полный набор идёт `-n auto` без `--dist` (`orchestrator/config.py:265`, `orchestrator/acceptance.py:3123`, `ci.yml:245`): длинные файлы в конце держат хвост прогона.
- **Консолидация догоняет, но не останавливает.** Волны 1а–3м смержены; после 24.10 добавилось 136 новых тестовых файлов. Сведение файлов без изменения того, что делает каждый тест, даёт 2–4 % времени (разбор 24.10).

Внешние практики:

- Размеры тестов по ресурсам, а не по объёму кода: малый, средний, большой, у каждого свой предел времени. Тест, вышедший за предел, переводится в больший размер, а предел не поднимается. Желаемая форма — много малых, умеренно средних, мало больших («Software Engineering at Google», гл. 11 и 14).
- Решения — в чистых функциях с входом и выходом простыми значениями, их проверяют многие быстрые тесты; оболочку с вводом-выводом — немногие сквозные («Functional core, imperative shell», G. Bernhardt).
- Выбор тестов по изменению для быстрой обратной связи при сохранении полного прогона (Machalica и др., «Predictive Test Selection», 2018; `pytest-testmon`).
- Ценность теста — мутации, которые ловит только он; набор чистят по покрытию мутаций, а не по числу тестов.

## Решение

1. **Поверхность решения — в формулировке критерия.** Для критерия-правила (разбор входа, условие отказа, текст сообщения, выбор ветки поведения) аналитик называет в самом тексте AC публичную функцию решения: модуль, имя, вход и выход простыми значениями. test_author пишет тесты только по формулировке AC (`skills/test-authoring.md:9-14`), поэтому имя должно стоять там, а не в «Требованиях».
   - Это явное исключение из `skills/spec-authoring.md:165` («SPEC — не карта реализации»): SPEC называет имя и контракт функции решения, но не её устройство.
   - Правило проверяется малыми тестами на функции: полный перебор конечных вариантов и входы от `random` — там, где они дёшевы (`skills/test-authoring.md:192-200`).
   - Связка проверяется **тестом подключения** на каждую команду и класс исхода (успех, отказ): по **всем** состояниям задачи — литералами `parametrize`, как сейчас; случайны только значения внутри состояния. Утверждение — наблюдаемое: исход команды и текст отказа совпадают с выводом функции на том же входе; при отказе БД, git и ссылки документов не меняются. Подмена функции в тесте подключения не нужна и не применяется.
   - Модуль функции импортируется целиком, к функции тест обращается внутри тела (`mandate.matrix_refusals`), а не `from … import` на уровне модуля: так сухой сбор на выходе из `tests_writing` не падает на ещё не существующем имени, тест краснеет «на атрибуте» (образец — докстринг `test_01m4nz5qrb…_mandate_matrix.py`).
   - Разработчик реализует функцию под названным именем; её переименование — по общим правилам `tests/` и гейта неослабления.
   - `skills/spec-audit.md` проверяет, что у каждого критерия-правила поверхность названа или записано, почему её нет; `skills/review-checklist.md` — что правило не проверяется через команду, когда функция названа.
   - Где поверхность не выделяется (поведение — сама последовательность действий с git и БД), критерий остаётся средним или большим тестом, как сейчас.

2. **Три размера тестов — как сигнал, а не гарантия.**

   | Размер | Ресурсы | Ориентир времени на тест |
   |---|---|---|
   | малый | чистые функции, временный каталог, подмены | до 1 с |
   | средний | песочница с настоящим git и БД пульта, команда пульта в процессе теста | до 10 с |
   | большой | дочерние процессы `artel.py` и pytest, живые процессы, сигналы, канарейка | до 60 с (отказ — по-прежнему только `PER_TEST_TIMEOUT_SEC = 120`, `orchestrator/stack.py:95`) |

   - **Новые файлы** объявляют размер меткой `pytest.mark.size(...)` на уровне модуля; метка регистрируется в `pyproject.toml`. guard на выходе из `tests_writing` проверяет, что метка есть и что малый тест не берёт песочниц с настоящим git (`RealGitSandbox` и потомки, `tests/sandbox.py`) и не вызывает `subprocess`. Это статическая проверка: команда пульта внутри «малого» теста может сама вызвать git — тогда размер выдаёт замер, а не guard.
   - **Существующие файлы** меток не получают: залоченные файлы и перечни сумм не правятся. Их размер выводится из замера (отчёт junit CI, ADR-0031 этап 4б) и ресурсов, которые видит разбор файла; реестр размеров живёт вне `tests/` — в отчёте слежения (п. 6).
   - Время сверяется по отчёту CI, а не по прогону на машине пульта: под нагрузкой ролей время раздувается на 20–40 %, и сигналы стали бы ложными. Границы совпадают с естественными группами замера 24.10: до 1 с — 4831 тест, 1–10 с — 1672, дольше 10 с — 347.
   - Выход за ориентир — строка в отчёте слежения, не отказ.

3. **Размеры проверок — в SPEC, а не измерение после лока.** Аналитик для каждого критерия указывает ожидаемый размер проверки (малый / средний / большой); **каждая** большая — с обоснованием одной строкой, почему меньший размер свойство не держит. Порога «столько-то больших без обоснования» нет: любое число произвольно и становится квотой. `skills/spec-audit.md` проверяет обоснования; Оператор видит число больших проверок на гейте SPEC.
   - Фактическая сумма длительностей новых тестов задачи (сумма по отдельным тестам из отчёта, не время по часам) пишется в журнал на `in_dev → verifying` и в отчёт слежения — для калибровки, **без эскалации и без отказа**.
   - Облегчение тестов после лока — только через `amend-tests` по мандату Оператора со счётчиком ADR-0012; этот ADR новых путей правки планки не вводит.

4. **Общее состояние только для чтения.** Тесты, которые дорогое состояние не меняют, делят одну фикстуру уровня класса в своём файле — только в файлах стиля pytest (ADR-0027 п. 1; смешение стилей запрещено).
   - Фикстура общего состояния строится **только** помощником `tests/fixtures.py`. guard отказывает фикстурам уровня класса, модуля и сессии вне этого помощника.
   - Помощник до и после каждого теста снимает отпечаток: содержимое БД пульта, ссылки и деревья git песочницы, файлы её каталога, `os.environ`, текущий каталог, значения атрибутов `config` из `PATCHED_ATTRS` (`tests/sandbox.py`), список дочерних процессов теста. При расхождении падает изменивший тест с именем изменившегося, а все оставшиеся тесты, делящие эту фикстуру, завершаются ошибкой «общее состояние загрязнено» — на загрязнённом состоянии никто не продолжает.
   - **Живые процессы общими не делаются**: дочерний процесс, который тест может остановить или который останется сиротой при обрыве по пределу, — у каждого теста свой.
   - Правка помощника и общей фикстуры видна гейту неослабления: guard прослеживает помощник фикстуры как помощник первого уровня тех тестов, что её берут (расширение ADR-0027 п. 3 на эту цепочку; слепая зона цепочек второго уровня — `skills/review-checklist.md:103-106`).
   - Каждый критерий остаётся отдельным тестом со своей строкой «Ловит мутацию»; утверждений в фикстуре нет (ADR-0027 п. 3).
   - Перевод существующих файлов на общую фикстуру — только волной консолидации по модулю с переводом на pytest и мандатом (ADR-0027 п. 8).
   - Пилот выбирается по данным этапа 1 среди классов с засеянным дорогим состоянием без живых процессов (например, тесты отказов на засеянной задаче). Файл окна канарейки (`test_01m5c6qa6s3ry9ps4h9zj58wq0_canary_window.py`) в пилот не годится: тесты делят живого потомка, которому шлют сигналы.

5. **Выбор тестов на шаге роли.** ADR-0031 п. 4 отводит шагу роли «тесты задачи и затронутых модулей». Затронутые выбираются по карте покрытия «тест → строки кода пульта».
   - Карту строит отдельный прогон в тихом окне или ночью, вне задания CI с пределом 40 мин; `.github/` — защищённый путь Оператора.
   - Зависимость (`coverage` / `pytest-cov`) в окружение пульта сейчас не добавляется. Решение — при заведении этапа 7, по данным слежения (п. 6): если обратная связь шага роли не узкое место, этап 7 не заводится и зависимость не нужна.
   - Тесты, которые работают через дочерние процессы и в карту не попадают, выбираются по модулям пульта, которые они импортируют, а при сомнении — включаются.
   - Выбор передаётся pytest списком файлов: сторож роли в корневом `conftest.py` запуск без путей и с путём `tests` отклоняет.
   - Полный набор остаётся единственным источником итога гейтов (ADR-0031 пп. 1–2, п. 5): выбор ускоряет обратную связь роли и гейтов не касается.

6. **Слежение за ценой набора.** По отчёту junit каждого прогона CI `main` (ADR-0031 этап 4б) пульт пишет: число тестов, сумму, время по часам, 20 самых медленных, долю каждого размера (п. 2), прирост от последней смерженной задачи. `doctor` предупреждает при 75 % предела (локального 1500 с и CI 40 мин), алерт — при 85 %. Предупреждение ставит в очередь волну облегчения (пп. 8–9), а не подъём предела.

7. **Распределение по рабочим.** Полный набор локально и в CI — с `--dist worksteal` (pytest-xdist 3.8.0). Переход — после трёх парных замеров «как сейчас / worksteal» на одном дереве: сверяются время по часам **и исходы по каждому тесту**; принимается, если время не хуже и исходы совпадают. Расхождение исходов — скрытая зависимость между тестами, она чинится до перехода как дефект теста.

8. **Чистка по покрытию мутаций — регулярно.** Раз в фазу вместе с ревизией кода — волна по **модулю кода пульта** (не по файлу тестов):
   - множество мутаций — заявленные во всех строках «Ловит мутацию» тестов, покрывающих модуль, **плюс** порождённые стандартными операторами мутаций по строкам модуля;
   - учитываются убивающие тесты из **всех** файлов `tests/`; тесты со случайным зерном гоняются на закреплённых зёрнах (несколько зёрен на тест);
   - кандидат на удаление — тест, каждую мутацию которого убивает другой оставшийся тест, и который не единственный тест своего критерия; кандидаты снимаются **по одному с пересчётом** — два взаимно перекрывающих теста не уходят оба;
   - удаление — решением Оператора по ADR-0020 п. 8 (второй пункт) с независимой проверкой, повторяющей прогон мутаций; матрица волны — строка на каждое свойство удаляемого теста, не на заявку;
   - мутации, которые не убил ни один тест, — отдельный список: ложная заявка чинится (тест или строка) до любого удаления в модуле;
   - тесты без строки «Ловит мутацию» не удаляются.

9. **Перевод существующих тяжёлых тестов.** Медленные тесты отказов, неизменности и текста, у которых правило проверяется через команду, переводятся на п. 1 и п. 4 в волнах консолидации по модулю: малые тесты на функцию решения (при необходимости функция делается публичной задачей-рефакторингом) плюс тест подключения по всем прежним состояниям. Доказательство — множество убиваемых мутаций не меньше прежнего (п. 8); мандат Оператора на каждый файл. Попутно снимаются оставшиеся `time.sleep` старых файлов.

## Последствия

- У критериев-правил основная масса проверок уходит в малые тесты; сквозными остаются тесты подключения — по одному на команду, класс исхода и состояние, а не на каждое правило.
- Засеянное дорогое состояние строится один раз на класс там, где тесты его не меняют.
- Рост времени набора виден заранее (п. 6), а не по ложному отказу автогейта.
- Аналитику добавляется работа: поверхность решения и размеры проверок в SPEC; разработчику — ограничение: решение правила живёт в названной функции.
- Тесты на функции решения сильнее привязаны к устройству кода: переименование функции — правка тестов по общим правилам. Цена ограничена тем, что поверхность — только для правил с входом и выходом простыми значениями.
- Выигрыш по времени не обещается: каждый этап меряется отдельно (п. 6 даёт данные).

## Отклонённые альтернативы

- **Поднять пределы 1500 с и 40 мин.** Откладывает упор на несколько недель и не меняет кривую роста.
- **Разрешить test_author внутренние имена.** Ломает защиту «тест не подогнан под реализацию» (`skills/test-authoring.md:98`); поверхность, названная в AC до кода, даёт ту же скорость без этого.
- **Отказаться от «тест до кода».** Снимает главную защиту от подгонки.
- **Одно случайное состояние в тесте подключения вместо перебора.** Делает обнаружение вероятностным (1/k за прогон) — ослабление (первая редакция черновика, отклонено проверкой).
- **Бюджет времени задачи с эскалацией после лока.** Облегчение планки после лока — только `amend-tests` со счётчиком ADR-0012, а замер под нагрузкой ролей даёт ложные эскалации; размеры проверок заявляются в SPEC до лока (п. 3).
- **Общий живой процесс на класс.** Сторож его состояния не видит, обрыв по пределу оставляет сироту.
- **Выбор тестов по изменению для гейтов.** Ослабляет гейт; полный набор один раз на дерево уже даёт ADR-0031.
- **Предсказательный выбор тестов по истории (как в Meta).** Требует истории падений большого объёма и модели; для нашего масштаба достаточно карты покрытия.
- **Сводить файлы без изменения тестов.** Разбор 24.10: 2–4 % времени.
