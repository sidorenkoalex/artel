# ADR-0005: Сохранность данных, эфемерность пульта и память проекта

Дата: 2026-08-27. Статус: предложен (черновик на подпись Оператора;
решения выработаны в сессии Оператора 26–27.08, фактура — инциденты
T035–T043 и обсуждение при постановке T043/RETRO).

## Контекст

Данные системы живут в трёх местах с разной судьбой: репозиторий
пульта (git, GitHub), каталоги задач `tasks/<id>/` (в git до merge,
у killed — умирают с веткой) и `.artel/` (БД-журнал, логи, home ролей,
после A7 планировались артефактные репо; в гитигноре, единственная
копия — диск пульта). Вопросы, вскрытые практикой: что обязано
пережить потерю пульта; где живёт память о прошлых задачах, когда
артефакты уезжают из main; чем платить за сохранность (бэкап, MinIO,
git-история); что происходит при «въезде» пульта в готовый проект.
Нумерация пунктов — сквозные якоря (п.1–8).

## Решение

### 1. Уровни сохранности — свойство target'а

Владелец target'а декларирует уровень в `targets.yaml`
(поле `preservation: full | partial`).

**full** — «артель — часть проекта»: артефакты задач мержатся
в целевой репозиторий вместе с кодом и живут в его git-истории вечно;
RETRO (`docs/retro/<id>.md`, T043) — в main; рабочее дерево от старых
каталогов задач можно чистить (`git rm`) — история хранит, RETRO
адресует (п.4). Потеря `.artel` теряет только текстуру журнала
и задачи в полёте. **Артель — full.**

**partial** — «в чужой main не следим»: в целевой репозиторий попадает
только смерженный код; артефакты и RETRO — в артефактном репо
`.artel/projects/<target>/` (git без remote, инвариант «remote пуст»
сохраняется — чужое не публикуем). Потеря пульта теряет артефакты
и память о прошлых задачах target'а — **принято владельцем заранее**,
организация бэкапов на стороне владельца в наши задачи не входит.

### 2. Следствие для A7: переезд артефактов артели отменён

«Особый случай догфуда» (ADR-0003 3д: артефакты артели в `tasks/`
пульта до A7) перестаёт быть временным — это штатная форма уровня
full. A7 худеет до: stage0/stage1, защищённые пути с подсветкой в MR,
тест «merge не меняет запущенную версию». Довод: история артефактов
артели в GitHub — бесплатная оффсайт-копия, которой переезд в
локальный `.artel` лишал бы.

### 3. Эфемерность `.artel`; отдельный бэкап не ведётся

Всё в `.artel/` обязано быть либо восстановимым (из репо пульта,
git-истории, RETRO), либо явно допустимым к потере. Решение
Оператора 27.08: **отдельный механизм бэкапа `.artel` не ведётся** —
сохранность определяется уровнем target'а (п.1). Остаточный риск
поименован и принят: текстура журнала БД (дословные записи шагов)
и состояние задач в полёте.

Следствие: doctor-проверка `check_backup_age` и маркер
`.artel/backup-marker` (A3, требование 9) теряют основание —
проверка **снимается** (или деградирует до информационной строки без
алерта). Это изменение защитного механизма легализуется настоящим
ADR (принцип целостности, ADR-0002); исполняется задачей холодного
старта (п.5) или ближайшей правкой doctor.

### 4. Вечный адрес артефактов и каскадный резолв

Ссылка на артефакты закрытой задачи — контент-адресная:
`<merge-sha>:tasks/<id>/` (формат RETRO, T043). Резолв — каскадом:
локальная история → `git fetch origin <sha>` → contents-API форджа
(raw.githubusercontent / GitLab files API). Развёртывания и песочницы
(B3) полную историю не тянут: shallow или partial clone
(`--filter=blob:none`), недостающее добирается каскадом; сетевой
доступ к форджу и так в белом списке песочницы ради MR.

### 5. Холодный старт и въезд в готовый проект

Потеря `.artel` или подключение нового пульта к существующему
target'у — штатный сценарий, не катастрофа. Требования (исполняются
задачей «холодный старт пульта», класс $15–25):

- **счётчик номеров**: БД — кэш; истина — максимум выданных номеров,
  наблюдаемый в мире (каталоги задач, ветки task/*, docs/retro/,
  история); посев от max+1 при init/восстановлении, doctor сверяет
  «счётчик ≥ наблюдаемого max»;
- **программный расход** (стоп-лосс §5): пересев суммой стоимостей
  из RETRO done/killed задач;
- **слой ролей `.artel/home`**: эталон хранится в репо пульта
  (курируемое содержимое — решение Оператора при исполнении);
- задачи в полёте: строки БД пересобираются руками по веткам task/*
  (обычно 0–2), журнал прошлого честно отсутствует.

### 6. Идентификаторы задач

`Tnnn` остаётся. Переход на ULID (time-ordered, короткий префикс
в отображении, резолв по префиксу) **одобрен по направлению,
исполняется по триггеру**: панель Г1 (кнопки гейтов обесценивают
произносимость) либо первый реальный конфликт нумерации
(конкурентный `new`, мультипульт) — что раньше. Мост (строка P3
«id-агностика + префикс-резолвер»): формат id знает единственная
функция-генератор; правило «id — непрозрачная строка» (никаких
парсингов `T%03d`, сортировок по числу, предположений о длине)
действует для нового кода немедленно. В кросс-target контекстах
до ULID номер пишется квалифицированно: `<target>/Tnnn`.
Смешанная нумерация после перехода (T001–Tnnn рядом с ULID) —
принята; резолвер префиксов обязан понимать обе схемы.

### 7. Чистка рабочего дерева (дополнение retention)

Для full-target'ов каталоги `tasks/<id>/` done-задач допустимо
убирать из рабочего дерева (git rm) по retention-правилу «держим N
последних» — содержимое остаётся в истории, RETRO даёт адрес (п.4).
Исполняется в составе retention-задачи (строка P3), не отдельно.

### 8. Мелочь: причина kill

`kill <id> "причина"` — аргумент причины с записью в журнал:
killed-RETRO сейчас показывает генеричное «kill switch» (T039).
Кандидат-строка P3, ~$0–15.

## Последствия

- targets.yaml получает поле `preservation` (артель — full);
  строка A7 роадмапа худеет (п.2); retention-строка дополняется
  чисткой дерева (п.7); строка «холодный старт» заводится задачей
  (п.5); check_backup_age снимается (п.3).
- Рассмотрено и отклонено: MinIO/объектное хранилище для артефактов
  (переизобретение git-свойств, несоразмерная инфраструктура;
  осмысленно только для логов при будущей потребности); немедленный
  переезд на ULID (плата удобством в CLI-эпоху при нулевой текущей
  выгоде — п.6 фиксирует триггерный путь); отдельный бэкап-репозиторий
  `.artel` (перекрыт уровнями сохранности — п.1, п.3).
