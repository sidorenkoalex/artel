# ADR-0021: Проект целиком в своей области, пульт неизменен в работе

Статус: принят. Дата: 29.09.2026. Решение Оператора (утверждено «Все
так, принять» 29.09.2026, редакция 2 после ревью). Продолжает ADR-0003
(целевые проекты) и доводит замысел задачи A7
(01M1H224X5A8W159MKF1Q24R5Y); отменяет решение 03.09 (рабочая копия
задачи артели под главной копией пульта) и пересмотр ADR-0003 от
27.08 (артефакты артели в `tasks/` пульта); пересматривает ADR-0003 3д
(артефакты внешнего проекта — в его репозитории, а не только локально в
пульте) и п.15 (репозиторий фиксации в области проекта упраздняется);
исполняет ADR-0018, пункты 1 и 4; снимает с канарейки дефект, при котором
она исполняет переходы кодом пина (ADR-0019, пункт 2, — теперь
исполняется); после исполнения пересматривается ADR-0020, пункт 2.
С этапа 1 пересматривает ADR-0005, разделы 2 и 4 (артефактная ветка
пульта при жизни задачи и снимок в `refs/artifacts/<id>` при закрытии;
закрытие при неотправленной ссылке больше не проходит — гейт мержа и
закрытие требуют совпадения локальной ссылки с `origin`, пункт 3), и
ADR-0016 (CI на пуш в `artifact/**` отменяется, пункт 4).

## Контекст

- Задача A7 требовала вести артель как обычный внешний проект:
  артефакты вне git пульта, общие ветки логики вместо развилок «проект —
  сам пульт». Исполнена частично. Решение 03.09 оставило задачи артели в
  рабочих копиях `.artel/worktrees/<id>` под главной копией пульта: код
  артели физически лежит в `config.ROOT`, и на него завязаны черновик
  MR, гейт мержа, замер объёма диффа, промежуточные коммиты. Пересмотр
  ADR-0003 от 27.08 отменил переезд артефактов артели в `.artel`.
- Итог на 29.09: 45 сравнений с `config.DEFAULT_TARGET` в `orchestrator/`;
  все проверки целостности тестов (долгоживущие файлы, перечень сумм,
  неослабление тестов, «Ловит мутацию», защищённые пути, зоны, замер
  объёма) работают только для артели. Внешний поток ни разу не
  исполнялся: 297 задач в БД, у всех проект `artel`.
- Латентные дефекты внешнего потока, найденные чтением кода 29.09
  (строки копилки): задание test_author велит писать долгоживущие файлы
  в `tests/` любого проекта, а закрепляет их пульт только для артели;
  снимок `tasks/<id>/` накладывается на `main` безусловно
  (`fsm_merge_gate.py`, функция `_overlay_artifact_snapshot`) — у
  внешнего проекта документы пульта попали бы в его репозиторий;
  удаление ветки документов при закрытии только
  локальное — в `origin` артели 187 веток `artifact/**`.
- Главная копия пульта меняется в ходе работы над задачами: в её git
  живут ветки `artifact/<id>`, ссылки `refs/artifacts/<id>`, рабочие
  копии задач, в её `main` мерж кладёт снимок `tasks/<id>/` и RETRO.
  Отсюда класс инцидентов: паразитная БД в рабочей копии (T052/T055),
  переключение главной копии запуском роли (26–27.08), локальные
  коммиты, ломающие канарейку и базу веток (11.09); правило «HEAD главной
  копии = пин» держится дисциплиной, а не устройством.
- Документы задачи выкладываются внутрь рабочей копии кода. Отсюда
  сложность ADR-0020: тест может тайком читать `tasks/<id>/`, и против
  этого понадобились признаки по тексту и прогон в изолированной выгрузке
  (задача 01M3P0SQQM453G9DP3NVDVGC49 ликвидирована 29.09 до исполнения).
- Канарейка работает на эфемерном клоне пульта со своей БД, но исполняет
  переходы кодом пина, а не кодом проверяемого коммита (строка копилки
  28.09, П1): изменения пульта впервые исполняются уже после
  `pin-update`, вопреки ADR-0019 п.2.
- В области внешнего проекта уже есть git-репозиторий фиксации без
  удалённого (ADR-0003 п.15): на каждом переходе пульт делает в нём
  `git add -A` и коммит (`fixation.py:77-93`), `doctor.recovery_check`
  сверяет его голову.

## Решение

1. **Пульт — инструмент.** Главная копия пульта (`config.ROOT`) в ходе
   работы над задачами не меняется: ни веток, ни коммитов, ни ссылок, ни
   рабочих копий в её git. Её HEAD — пин; меняет его только
   `pin-update`. Состояние пульта — БД, журналы, локальный слой моделей —
   в `.artel/` вне git, как сейчас.
2. **Область проекта.** Всё, что относится к проекту, живёт в
   `.artel/projects/<имя>/`:
   - `repo/` — клон репозитория проекта, источник рабочих копий задач
     (заменяет нынешний общий `workspace/` внешнего проекта);
   - `worktrees/<id>/` — рабочая копия ветки кода задачи `task/<id>-…`,
     отдельная у каждой задачи — параллельные задачи одного проекта не
     мешают друг другу;
   - `tasks/<id>/` — рабочая копия документов задачи на диске (ТЗ, SPEC,
     PLAN, REVIEW, RETRO, `acceptance_tests/`) рядом с рабочей копией
     кода, не внутри неё.
   Репозиторий фиксации в области проекта (ADR-0003 п.15) упраздняется:
   документы фиксируются в ссылке проекта (пункт 3), коммит ссылки и есть
   зафиксированное состояние, которое сверяют переходы (инвариант 25).
3. **Документы — одна ссылка в репозитории проекта.** Отдельного
   репозитория документов нет. Документы задачи живут в репозитории
   САМОГО проекта (клон `repo/` и его `origin`) под одной ссылкой
   `refs/artifacts/<id>` вне веток — от `new` до конца жизни задачи и
   после неё. Веток `artifact/<id>` нет.
   - Дерево ссылки — только `tasks/<id>/…`; первый коммит без родителя,
     с историей `main` проекта ссылка не связана. Пути документов внутри
     ссылки прежние (`tasks/<id>/SPEC.md`): чтение
     `gitcmd.show(<ссылка>, "tasks/<id>/PLAN.md")` в коде и в закреплённых
     тестах, формат 185 исторических снимков, задания ролей и скилы не
     меняются. Функция `artifact_branch.branch_name` остаётся и
     возвращает полное имя ссылки.
   - Запись — прямыми командами git (`commit-tree`, `update-ref` со
     сверкой прежнего значения; при расхождении — перечитать и повторить).
     Ссылка отправляется в `origin` проекта после каждого коммита; отказ
     `push` пишется в журнал и повторяется на следующем переходе; гейт
     мержа и закрытие задачи требуют, чтобы локальная ссылка совпадала с
     `origin`.
   - Закрытие задачи (`done`/`killed`) — последний коммит (RETRO) в ту же
     ссылку. Признак «закрыта» — по БД, не по наличию ветки; снимка и
     удаления ветки нет. Неизменность закрытой ссылки хостинг не
     обеспечивает (правила защищают ветки и теги) — её сверяет `doctor`
     с последним коммитом, записанным в журнал при закрытии.
   - Обычный `git clone`/`fetch` команды проекта ссылку не скачивает, CI
     проекта на неё не запускается, в список веток она не попадает. Пульт
     печатает ссылку на документы по номеру коммита (`status`, журнал,
     описание MR): хостинг открывает файл по такой ссылке (проверено на
     GitHub 29.09.2026 — SPEC задачи 01M3NSZ4YWZW9SD5Y6H62ATGRV из её
     снимка).
   - Команды, пишущие в документы, — `amend-tests` (ADR-0012), `answer`,
     `zones-extend`, автокоммит шага роли — пишут в ссылку тем же узлом.
     Зафиксированный коммит планки (`tests_locked_sha`) указывает на
     коммит ссылки; цепочка коммитов после закрытия остаётся достижимой
     (сегодня снимок без родителя делает её недостижимой).
4. **Фиксация — каждая часть в своё место.** Документы — в ссылку
   `refs/artifacts/<id>`; код и долгоживущие тесты — в ветку кода
   `task/<id>-…`. Обе уходят в `origin` проекта. В `main` проекта
   документы пульта не попадают (ADR-0018 п.1): наложение снимка
   `tasks/<id>/` и коммит RETRO на `main` отменяются для всех проектов.
   Проверку документов (`scripts/guard.py`) делают гейты пульта на
   переходах (отказ перехода, строже нынешнего мягкого режима CI для
   черновиков); прогон CI на пуше документов отменяется — переходы его и
   сейчас не читают.
5. **Разовые тесты во время прогона.** Закреплённые разовые тесты находят
   код относительно своего файла (`Path(__file__).parents[3]`, не менее
   1222 файлов). Пульт выкладывает `tasks/<id>/acceptance_tests/` внутрь
   рабочей копии кода только на время прогона и убирает после; прочие
   документы в рабочей копии кода не лежат никогда.
6. **Артель — проект как все.** Её клон — `.artel/projects/artel/repo`,
   задачи артели идут по общему потоку. Изменения пульта попадают в
   работу порядком «мерж в `origin/main` артели → канарейка на этом
   коммите, исполняющая код проверяемого коммита → `pin-update`»
   (ADR-0013, ADR-0019). Команды Оператора, пишущие в `main` артели
   (`doc-commit`, `note`, `canary pool-seal`), коммитят и отправляют в
   `origin` через клон артели в её области; главную копию пульта не
   меняет ничто, кроме `pin-update`. Документ, ушедший в `origin/main`
   дальше пина, попадает в главную копию со следующим `pin-update`.
7. **Роли.** Рабочий каталог роли — рабочая копия кода задачи; каталог
   документов задачи открыт роли на запись дополнительно (claude —
   `--add-dir`, codex — доступный для записи каталог песочницы; способ
   передачи каталога codex и поддержку флага закреплённой версией CLI
   проверяет SPEC этапа 1). Защита документов и закреплённых тестов от
   роли — гейты пульта (сверка с зафиксированным коммитом ссылки, перечень
   сумм, отметка автокоммита), а не права доступа: у claude разрешённый
   `python3` пишет куда угодно, изоляции файловой системы у ролей нет;
   настоящая изоляция — строка бэклога. Сценарии пульта (`scripts/guard.py`
   и прочие) роль запускает из пина по полному пути; скилы и шаблоны — из
   пина, как сейчас.
8. **Проверки смотрят на репозиторий проекта.** Зоны, замер объёма
   диффа, защищённые пути, неослабление тестов, «Ловит мутацию»,
   долгоживущие файлы и перечень сумм, приложения к PLAN, карта кодовой
   базы сверяются с репозиторием проекта (`repo_context`), а не с корнем
   пульта. Защищённые пути проекта — `no_paths` из `targets.yaml` (для
   артели — нынешний `PROTECTED_PATHS`). Проверки, зависящие от языка,
   включаются профилем тестов проекта (пункт 9); развилки
   `target == DEFAULT_TARGET` удаляются.
9. **Профиль тестов проекта** в `targets.yaml`: команда запуска тестов,
   где лежат долгоживущие тесты и как их называть, формат отчёта
   (JUnit XML), установка зависимостей. Для артели — нынешние pytest и
   `tests/test_<id>_<имя>.py`. Проект без профиля работает только с
   разовыми тестами, как до ADR-0020. Тесты проекта исполняются в его
   песочнице (ADR-0003: песочница — единственная линия от чужого кода).
10. **Канарейка** — клон пульта на проверяемом коммите, исполняющий
    СВОЙ код (не код пина), плюс область проекта `artel` в своём
    временном каталоге.
11. **Журналы и база** (`.artel/logs/`, `.artel/state.db`) остаются
    общими для пульта — это состояние пульта вне git, правило пункта 1
    они не нарушают. Разделение по проектам — триггер №29
    (`docs/triggers.md`).
12. **Инварианты.** Переход меняет инварианты, перечисленные ниже.
    Правка текста `docs/invariants.md` и теста `tests/test_invariants.py`
    — приложением к PLAN задачи соответствующего этапа (защищённые пути,
    применяет пульт на мерже того же этапа): код и инвариант меняются
    одним мержем.

    | № | Сейчас | После | Этап | Характер |
    |---|---|---|---|---|
    | 20 | артефакты и журналы внешнего проекта не появляются в рабочем дереве пульта | то же для любого проекта, включая артель | 2 | усиление |
    | 21 | каталог роли внешнего проекта — только `workspace/` | каталог роли любого проекта — рабочая копия задачи `worktrees/<id>/`, плюс каталог документов задачи на запись | 1–2 | расширение на один каталог (защита — гейты, пункт 7) |

    Второй инвариант под номером 36 (порядок состояний FSM) получает
    новый номер в приложении этапа 1.
13. **Переход — этапами.** Каждый этап — задача конвейера; вливается на
    рубеже волны при пустом конвейере (переноса живых задач нет); после
    мержа — канарейка на новом коммите `origin/main`, затем `pin-update`;
    откат — `pin --to` на предыдущий пин (ADR-0013): при пустом конвейере
    откату не мешают живые задачи в новом устройстве.
    - **этап 0:** канарейка исполняет код проверяемого коммита (клон
      пульта запускает свой `orchestrator/`), порядок «мерж → канарейка →
      `pin-update`» проверяется на деле; без этого остальные этапы
      попадают в работу непроверенными;
    - **этап 1:** одна ссылка документов вместо ветки `artifact/<id>` и
      снимка (пункт 3); документы вне рабочей копии кода, разовые тесты
      внутри неё только на время прогона (пункт 5); доступ ролей на
      запись к каталогу документов (пункт 7); упразднение репозитория
      фиксации области проекта; команда пульта чтения документа задачи с
      подтягиванием ссылки из `origin` (например `artel.py docs <id>
      [файл]`) и пакетное подтягивание всех `refs/artifacts/*` для
      ретроспектив и ревизий; отмена CI на пуше документов; правки
      инвариантов 21 (часть), 25, 28, 34, 36, 38; разовая уборка 187
      веток `artifact/**` в `origin` артели. До этапа 2 ссылки документов
      артели живут в git главной копии пульта (репозиторий проекта артели
      и есть она) — правило пункта 1 для артели выполняется с этапа 2;
    - **этап 2:** клон и рабочие копии задач в области проекта для любого
      проекта; артель переходит на них, `config.ROOT` перестаёт меняться.
      SPEC этапа находит всё, что предполагает «код = `config.ROOT`»: в
      том числе условия `ctx.path == config.ROOT` на гейте мержа
      (приложения к защищённым путям, карта кодовой базы — иначе они
      молча отключатся), `gitcmd.git` с рабочим каталогом `config.ROOT`
      по умолчанию, 162 упоминания `config.ROOT` в 52 модулях, хуки защиты
      `main` (`core.hooksPath` и `doctor/git_hooks.py` — только в главной
      копии; в клоне хуки не должны браться из проверяемого кода);
      правки инвариантов 20, 21;
    - **этап 3:** проверки из пункта 8 переводятся на `repo_context`,
      развилки `DEFAULT_TARGET` удаляются; профиль тестов проекта;
    - **этап 4:** отмена наложения снимка и коммита RETRO на `main`;
      уборка `tasks/` из `main` артели по условиям ADR-0018 (сверка
      снимков с `origin`, вторая копия каталогов без снимка и ветки,
      правка ссылок на `tasks/<id>/` в скилах и `docs/invariants.md`);
      пересмотр ADR-0020 п.2.
    Исторические задачи не переносятся: их снимки `refs/artifacts/<id>`
    остаются в репозитории артели и читаются как сейчас.

## Решения Оператора по вопросам черновика (29.09.2026)

1. Канарейку чинить первой — этап 0.
2. Репозиторий фиксации области проекта упразднить.
3. Разовые тесты — в рабочей копии кода только на время прогона.
4. В ссылке документов — только `tasks/<id>/…`, без родителя в `main`.
5. Закрытие — последний коммит RETRO в ту же ссылку, признак «закрыта»
   по БД, неизменность сверяет `doctor`.
6. Этапы вливаются на рубеже волны при пустом конвейере.
7. Защита документов от ролей — гейты; изоляция файловой системы ролей —
   строка бэклога.
8. Правки инвариантов — по таблице пункта 12, приложением к PLAN этапа.
9. Отдельного репозитория документов нет — ссылка в репозитории самого
   проекта; вариант «одна ветка `artifact/<id>` на всю жизнь» отклонён:
   клоны команды проекта скачивали бы все ветки документов, CI проекта
   запускался бы на каждый шаг роли, правила и уборка веток проекта могли
   бы их удалить. Для внешнего проекта при подключении `doctor`
   проверяет, что хостинг принимает пуш в `refs/artifacts/*` (GitHub —
   да; GitLab — проверить на первом проекте). Команда проекта видит
   документы задач — это свойство решения; чувствительное в документы не
   пишется.
10. Команды Оператора пишут в `main` артели через её клон.
11. Журналы и база — общие для пульта; разделение — триггер №29.

## Отклонённые альтернативы

- **Оставить артель особым случаем и доделать внешний поток отдельно.**
  Два потока, из которых один не исполняется, — сегодняшнее положение;
  дефекты внешнего потока видны только при чтении кода.
- **Отдельный репозиторий документов у каждого проекта** (`docs.git`).
  Лишняя сущность со своей сохранностью.
- **Документы только локально в пульте** (ADR-0003 3д в прежней
  редакции). Пульт меняется в ходе работы, сохранность — только
  резервными копиями.
- **Одна ветка `artifact/<id>` на всю жизнь задачи.** См. решение 9.
- **Документы в корне ссылки без `tasks/<id>/`.** Два формата ссылок
  (185 исторических снимков с префиксом), перевод путей при выкладке
  закреплённых тестов, правка чтения в коде и в закреплённых тестах —
  ради одной аккуратности.
- **Прогон в изолированной выгрузке как постоянная защита от чтения
  `tasks/`.** Лечит следствие устройства (документы внутри рабочей копии
  кода), а не причину; привязан к языку проекта.

## Следствия

- Один поток для всех проектов; внешний поток исполняется ежедневно на
  задачах артели.
- Правило «HEAD главной копии = пин» обеспечено устройством (с этапа 2);
  класс инцидентов вокруг главной копии закрыт; изменения пульта
  впервые исполняются в канарейке, а не после сдвига пина (с этапа 0).
- История документов задачи сохраняется целиком: ссылка ведётся с
  первого шага, `git log refs/artifacts/<id>` показывает каждый коммит
  роли, `git diff` — разницу между итерациями. Сегодняшний снимок
  закрытия — один коммит без истории, промежуточные версии теряются
  вместе с удалённой веткой.
- ADR-0020 упрощается: в рабочей копии кода документов нет, кроме
  `acceptance_tests/` на время прогона; тест, читающий SPEC или PLAN
  задачи с диска, падает в обычном прогоне. Признаки по тексту
  пересматриваются на этапе 4 с этой поправкой; прогон в выгрузке
  отклонён («Отклонённые альтернативы»).
- Объём: пять задач (этапы 0–4), каждая $40–70; этап 2 — крупнейший.
  Пульт перестраивает сам себя: каждый этап проверяется канарейкой до
  сдвига пина.
- Место на диске: клон каждого проекта в его области плюс рабочие копии
  задач; для артели — второй клон рядом с главной копией.
- Поверхность записи ролей растёт на один каталог документов задачи;
  защита — гейты, не права доступа (пункт 7).
