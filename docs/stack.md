# Стек пульта

Пульт объявляет свой стек в коде, а не удерживает его запретами:
источник истины — модуль `orchestrator/stack.py`. Этот документ
объясняет состав стека словами; конкретные числа версий (минимальная
версия Python, минимальные версии `git`/`gh`/`claude`) не дублируются
здесь — они живут ровно в одном месте, `orchestrator/stack.py`, чтобы
не разойтись с кодом молча.

## Что входит

- Минимальная версия Python — константа `REQUIRED_PYTHON` в
  `orchestrator/stack.py`.
- Внешние инструменты, от которых зависит пульт: `git`, `gh`, `claude`
  — каждый с минимальной версией и способом её проверки (`git
  --version`, `gh --version`, `claude --version`), объявленными в том
  же модуле (`REQUIRED_TOOLS`).
- Совместимость моделей ролей с CLI: минимальная версия `claude` — поле
  `min_cli_version` записи модели в каталоге `models.yaml` (раздел
  «Модели: каталог, ярусы, тариф» ниже). Один вердикт
  (`stack.model_cli_verdict`) служит предполётной сверке шага роли,
  строкам `check_stack()` по ролям и классу провала «модель не
  поддерживается CLI» без повторов (инцидент 19.09, SPEC
  01M2XJKV84SQ9VEVR0VNVKDNGJ); сам минимум приходит ему параметром из
  каталога. Модель, которой в каталоге нет, — отказ шага, а не
  предупреждение (до 20.09 таблица `MODEL_MIN_CLI_VERSION` жила в
  `orchestrator/stack.py`, и такая модель запускалась «как есть»).
- Правило «сторонних пакетов нет»: код `orchestrator/`, `scripts/`,
  `tests/` импортирует только стандартную библиотеку Python и модули
  самого репозитория. Допустимые исключения из этого правила — явный
  список `THIRD_PARTY_EXCEPTIONS` в `orchestrator/stack.py`, каждая
  запись которого обязана нести причину; список пуст на сегодня.

## Провайдер исполнителя роли

Роль конвейера исполняется агентным CLI. Всё, что пульту нужно знать о
конкретном CLI, объявлено в одном месте — пакете
`orchestrator/providers/`: базовый интерфейс в
`orchestrator/providers/base.py`, реализация для Claude Code в
`orchestrator/providers/claude.py`, словарь-реестр «имя → реализация»
в `orchestrator/providers/__init__.py`. Провайдер роли берётся из поля
`provider:` в `roles.yaml` (`orchestrator/roles.py::provider`); роль без
этого поля идёт на `claude`. Имя, которого нет в реестре, — именованный
отказ `run`/`auto` до старта агента и красная строка `doctor`, а не
тихий откат на провайдера по умолчанию.

В интерфейс входит:

- `command(model)` — argv шага роли целиком, включая флаг модели;
- `environment(role, task_id)` — переменные окружения, специфичные для
  исполнителя: дом роли, каталог его конфига, секрет подписки;
- `home_reference()` — каталог референса курируемого дома роли в
  репозитории и имя, под которым он разворачивается в `.artel/home`
  (`init`, `orchestrator/catalog.py`);
- `preflight(role)` — предполётные проверки до старта шага: CLI найден,
  версия CLI, секрет роли, дом роли;
- `cli_tool()` — имя инструмента для манифеста стека и его минимальная
  версия (запись `REQUIRED_TOOLS` собирается отсюда, не литералом);
- `model_verdict(model)` — вердикт совместимости модели с установленным
  CLI.

Общим у runner остаётся то, что не зависит от исполнителя: белый список
переменных окружения (`ROLE_ENV_ALLOWLIST` в этом же манифесте), PATH
роли и резолв объявленных инструментов, интерпретатор роли из
`.artel/venv`, метки `ARTEL_ROLE`/`ARTEL_TASK`, git-идентичность
коммитера, рабочий каталог шага, промпт роли, попытки и учёт стоимости.
Тела предполётных проверок тоже общие (`orchestrator/doctor/`) —
провайдер объявляет их состав и порядок, а не переписывает заново.

## Модели: каталог, ярусы, тариф

Модель, на которой идёт шаг роли, — не строка у роли, а результат
разрешения цепочки **роль → ярус → модель → провайдер** (SPEC
01M3009Y9AGGY6ZCFA7H1HJ1TD, план `docs/research/providers-codex-plan.md`
§3). Данные о моделях живут в трёх слоях, и у каждого своя причина
существовать отдельно:

1. **Каталог `models.yaml` в корне репозитория** — что пульт вообще
   умеет запускать: разделы по провайдерам (имя инструмента CLI,
   минимальная версия CLI провайдера, признак `cost_from_cli`), внутри —
   записи моделей (идентификатор, минимальная версия CLI, прейскурант
   `list_price_usd_per_mtok` по четырём видам токенов за миллион, дата
   прейскуранта, статус `supported`/`experimental`). В git, общее знание
   всех клонов; правит его Оператор командой `doc-commit`
   (`notes.DOC_COMMIT_CONFIG_PATHS`). В `config.PROTECTED_PATHS` путь
   войдёт частью 2 линии (01M300A14K): CI-джоб `protected-paths` читает
   список из ветки PR, поэтому объявить файл защищённым тем же мержем,
   который его создаёт, нельзя — см. комментарий у самого списка.
2. **Локальный слой `.artel/models.yaml`** — выбор конкретного пульта:
   `tiers:` (ярус → идентификатор модели из каталога), необязательный
   `overrides:` (собственный тариф по тем же четырём видам токенов с
   `calibrated_at` и `source`; форм записи цен принимается три — см.
   ниже) и необязательное `allow_experimental:`
   (явное разрешение модели со статусом `experimental`). **Вне git**:
   смена модели у одного пульта не должна менять её у всех клонов.
   Шаблон кладут `init` и `doctor --fix`, если файла нет; существующий
   файл ни одна из команд не перезаписывает. Образец —
   `docs/reference/models-local.example.yaml`.
3. **`roles.yaml`** — ярус роли, поле `model_tier` из закрытого перечня
   `strong | standard | cheap` у каждой agent-роли.

Разрешение цепочки — `orchestrator/models.py::resolve_role(role)`: ярус
роли, модель яруса, провайдер модели, минимум версии CLI и действующий
тариф (переопределение локального слоя, иначе прейскурант каталога) с
указанием источника. Каждое звено **fail-closed**: роль без яруса или с
ярусом вне перечня, ярус без модели в локальном слое, модель вне
каталога, `experimental` без явного разрешения — именованный отказ
`run`/`auto` ДО старта агента и красная строка `doctor`. Молчаливого
дефолта CLI больше нет: шаг agent-роли не запускается без явной модели.

Что делает Оператор:

- **сменить модель роли** — поправить `model_tier` роли приложением к
  PLAN (`roles.yaml` — защищённый путь) либо, чаще, поменять модель
  яруса в своём `.artel/models.yaml`: это правка одного пульта, ничего
  коммитить не нужно;
- **добавить модель или поправить цены/минимум версии CLI** —
  `artel.py doc-commit models.yaml --from <файл> --message "<основание>"`
  (префикс коммита `config:`) либо приложением к PLAN; дата
  прейскуранта (`price_date`) проставляется той же правкой;
- **завести собственный тариф** (прокси, скидка, свой счёт) — раздел
  `overrides:` локального слоя, с `calibrated_at` и `source`. Четыре
  цены пишутся любой из трёх форм: прямо записью модели, под ключом
  каталога `list_price_usd_per_mtok` или под `tariff_usd_per_mtok` —
  разбор принимает все три, файл пишется руками и имя ключа тут не
  повод для отказа;
- **посмотреть, что где действует** — `artel.py models`: таблица
  «провайдер, модель, статус, минимум CLI, прейскурант, действующий
  тариф и его источник, роли по ярусам», только чтение;
- **проверить слои** — `artel.py doctor`: строки `models-catalog`,
  `models-local` и цепочка «роль → ярус → модель → провайдер» в строке
  `role-providers`.

История тарифов (таблица в `state.db`) и потребитель действующего тарифа
— следующая задача линии; сегодня тариф только отдаётся разрешением
цепочки, а курс токенов пульта по-прежнему задан по роли
(`config.TOKEN_RATES`).

## Почему только стандартная библиотека

У пульта нет менеджера зависимостей и окружения для их установки —
интерпретатор, в котором стартует роль, разный в каждом месте
(локально, в CI, из PATH Оператора). Сторонний пакет, доступный в одной
среде и отсутствующий в другой, ломает конвейер молча и
непредсказуемо — код, который сегодня работает у одного участника
и падает у другого `ModuleNotFoundError`, обнаруживается не сразу и не
там, где внесена причина. Отказ от сторонних зависимостей убирает этот
класс дефектов целиком: если код запускается тем интерпретатором,
версия которого проходит `REQUIRED_PYTHON`, он гарантированно
запустится у кого угодно ещё, без установки чего-либо дополнительно.

Правило проверяется кодом, не удерживается на честном слове: тест
инварианта в `tests/test_invariants.py` разбирает `orchestrator/`,
`scripts/`, `tests/` через `ast` и падает на любом импорте модуля вне
стандартной библиотеки (`sys.stdlib_module_names`), вне пакетов
репозитория и вне `orchestrator.stack.THIRD_PARTY_EXCEPTIONS`.

## Как проверить

- `python3 orchestrator/artel.py version` — печатает фактическую версию
  Python исполнителя и результат `orchestrator.stack.check_stack()`
  (по строке на Python/`git`/`gh`/`claude`: `ok`, `WARN` при версии
  ниже минимальной или `FAIL`, если инструмента нет в PATH; плюс по
  строке на каждую agent-роль — модель берётся разрешением цепочки,
  `ok`/`FAIL` по минимуму версии CLI из каталога, `FAIL` для
  неразрешимой цепочки).
- `python3 orchestrator/artel.py doctor` — та же проверка стека в
  общем списке проверок `doctor` (`orchestrator/doctor.py::all_checks`
  подключает `orchestrator.stack.check_stack()` одной строкой).
- `python3 -m unittest tests.test_stack` — постоянная регрессия
  манифеста и `check_stack()`.

`check_stack()` не обращается к сети — сравнение идёт локальным
вызовом `<инструмент> --version` (docs/invariants.md, инвариант 35).
