# Стек пульта

Пульт объявляет свой стек в коде, а не удерживает его запретами:
источник истины — модуль `orchestrator/stack.py`. Этот документ
объясняет состав стека словами; конкретные числа версий (минимальная
версия Python, минимальные версии `git`/`gh`/`claude`) не дублируются
здесь — они живут ровно в одном месте, `orchestrator/stack.py`, чтобы
не разойтись с кодом молча.

## Что входит

- Минимальная версия Python — константа `REQUIRED_PYTHON` в
  `orchestrator/stack.py`.
- Внешние инструменты, от которых зависит пульт: `git`, `gh`, `claude`
  — каждый с минимальной версией и способом её проверки (`git
  --version`, `gh --version`, `claude --version`), объявленными в том
  же модуле (`REQUIRED_TOOLS`).
- Совместимость моделей ролей с CLI: минимальная версия `claude` — поле
  `min_cli_version` записи модели в каталоге `models.yaml` (раздел
  «Модели: каталог, ярусы, тариф» ниже). Один вердикт
  (`stack.model_cli_verdict`) служит предполётной сверке шага роли,
  строкам `check_stack()` по ролям и классу провала «модель не
  поддерживается CLI» без повторов (инцидент 19.09, SPEC
  01M2XJKV84SQ9VEVR0VNVKDNGJ); сам минимум приходит ему параметром из
  каталога. Модель, которой в каталоге нет, — отказ шага, а не
  предупреждение (до 20.09 таблица `MODEL_MIN_CLI_VERSION` жила в
  `orchestrator/stack.py`, и такая модель запускалась «как есть»).
- Правило «сторонних пакетов нет»: код `orchestrator/`, `scripts/`,
  `tests/` импортирует только стандартную библиотеку Python и модули
  самого репозитория. Допустимые исключения из этого правила — явный
  список `THIRD_PARTY_EXCEPTIONS` в `orchestrator/stack.py`, каждая
  запись которого обязана нести причину; список пуст на сегодня.

## Провайдер исполнителя роли

Роль конвейера исполняется агентным CLI. Всё, что пульту нужно знать о
конкретном CLI, объявлено в одном месте — пакете
`orchestrator/providers/`: базовый интерфейс в
`orchestrator/providers/base.py`, реализация для Claude Code в
`orchestrator/providers/claude.py`, словарь-реестр «имя → реализация»
в `orchestrator/providers/__init__.py`. Провайдер роли берётся из поля
`provider:` в `roles.yaml` (`orchestrator/roles.py::provider`); роль без
этого поля идёт на `claude`. Имя, которого нет в реестре, — именованный
отказ `run`/`auto` до старта агента и красная строка `doctor`, а не
тихий откат на провайдера по умолчанию.

В интерфейс входит:

- `command(model)` — argv шага роли целиком, включая флаг модели;
- `environment(role, task_id)` — переменные окружения, специфичные для
  исполнителя: дом роли, каталог его конфига, секрет подписки;
- `home_reference()` — каталог референса курируемого дома роли в
  репозитории и имя, под которым он разворачивается в `.artel/home`
  (`init`, `orchestrator/catalog.py`);
- `preflight(role)` — предполётные проверки до старта шага: CLI найден,
  версия CLI, секрет роли, дом роли;
- `cli_tool()` — имя инструмента для манифеста стека и его минимальная
  версия (запись `REQUIRED_TOOLS` собирается отсюда, не литералом);
- `model_verdict(model)` — вердикт совместимости модели с установленным
  CLI;
- `parse_output_line(raw_line)`, `failure_signatures()`,
  `required_cli_version(text)` — см. «Вывод и стоимость у провайдера»
  ниже.

Общим у runner остаётся то, что не зависит от исполнителя: белый список
переменных окружения (`ROLE_ENV_ALLOWLIST` в этом же манифесте), PATH
роли и резолв объявленных инструментов, интерпретатор роли из
`.artel/venv`, метки `ARTEL_ROLE`/`ARTEL_TASK`, git-идентичность
коммитера, рабочий каталог шага, промпт роли, попытки и учёт стоимости.
Тела предполётных проверок тоже общие (`orchestrator/doctor/`) —
провайдер объявляет их состав и порядок, а не переписывает заново.

### Вывод и стоимость у провайдера

Провайдер знает не только, что нужно исполнителю, но и что исполнитель
ОТДАЁТ. Строку вывода разбирает он — `parse_output_line(raw_line)` —
и отдаёт событие ОБЩЕГО вида (`orchestrator/providers/base.py`,
`StreamEvent`), в котором пульт читает пять вещей и больше ничего о
формате не знает:

- `log_text` — готовая строка лога шага (пустая — Оператору показывать
  нечего). Формат строки провайдерский: и отметка вызова инструмента, и
  сквозной проброс строки, которая в событие не разобралась (stderr,
  трейсбек CLI);
- `text` — что исполнитель сказал словами;
- `tool_calls` / `tool_results` — вызовы инструментов
  (`id`, имя, ключевой аргумент) и их результаты (`id` вызова, текст,
  признак ошибки). Двумя полями, а не одним: метрике трения шага нужны
  вызов и его результат вместе;
- `tokens_by_type` — учёт токенов ЭТОГО события разбивкой по четырём
  ОБЩИМ видам цены (`input`, `output`, `cache_write`, `cache_read` —
  `models.PRICE_KINDS`), не счётчиками конкретного CLI. `None` — учёта
  в событии не было (это не то же самое, что нулевой учёт);
- `run_result` — итог запуска: та же разбивка, цена в долларах ОТ CLI
  либо её отсутствие, признак ошибки и текст.

Разбор обязателен: провайдер без него — `NotImplementedError`, а не шаг
без лога, без трения и без стоимости. Через это событие идут все шесть
точек пульта, знавших формат Claude литералами до 21.09: лог шага
(`agent_log.render_agent_line`, `OutputPump`), метрика трения,
`spend.parse_cost_event`, `spend.stream_usage_by_type`,
`spend.partial_tokens_from_log`.

**Стоимость при `cost_from_cli: false`.** Раздел провайдера в
`models.yaml` объявляет признак `cost_from_cli` — сообщает ли его CLI
цену запуска. Учёт шага (`spend.charge_step`) ветвится так:

- цена в итоге запуска есть И `cost_from_cli: true` — прежний путь
  факта CLI: в `spent_usd` идёт цена CLI, строка журнала «agent cost
  KNOWN» несёт `источник=факт CLI`, `actual_usd=` и коэффициент сверки
  тарифа с фактом;
- цены в итоге запуска нет ЛИБО провайдер модели шага помечен
  `cost_from_cli: false` — стоимость считается по ДЕЙСТВУЮЩЕМУ тарифу
  модели шага (`spend.tariff_cost_usd`, каждый вид токенов своей ценой)
  и списывается в `spent_usd` как известная: «agent cost KNOWN» с
  `источник=расчёт по тарифу` и датой тарифа. Коэффициента сверки в ней
  нет и алерт расхождения курса не заводится — сверять расчёт не с чем,
  а `actual_usd=` в такой строке завёл бы расчёт в калибровку тарифа
  под видом факта;
- итога запуска нет вовсе (таймаут шага, обрыв пайпа) — прежние ветки
  «agent cost UNKNOWN»/«PARTIAL»/«ESTIMATED»/«LOST»;
- тариф модели шага не разрешился на пути расчёта — «agent cost
  UNCHARGED» и алерт: ноль в `spent_usd` выглядел бы как учтённый шаг.

Строки «agent cost KNOWN» и «agent cost PARTIAL» называют провайдера
шага полем `provider=` рядом с `model=` — разрез расхода по
провайдерам читается из журнала, а не угадывается по модели.

**Где токены видно.** Единицей бюджета и гейтов остаётся доллар, но
токены показываются рядом с ним в трёх местах, и разбирает записи
журнала для всех трёх один читатель — `orchestrator/retro.py`
(`token_breakdown_by_actor`/`task_token_breakdown`/
`token_totals_by_actor`):

- `status` (`orchestrator/catalog.py`) — суммарное число токенов задачи
  в той же строке, что и «$spent/budget»;
- RETRO (`orchestrator/retro.py`, блок стоимости) — по каждой роли
  доллары, сумма токенов, разбивка по четырём видам цены, провайдер и
  модель её шагов;
- `report` (`orchestrator/report.py`, панель «Токены и стоимость») —
  разбивка по видам рядом с долларами в разрезе задач и в разрезе
  ролей.

Задача, роль или строка, по которой записей токенов нет вовсе,
показывается прочерком, а не нулём: `input=0 … cache_read=0` читалось бы
как «шаг прошёл бесплатно», хотя пульт просто не записал разбивку.
Носителей у СУММЫ два, и читатель берёт их с деградацией: есть разбивка
по видам — сумма считается по ней, нет разбивки, но «agent run
finished» несёт `токенов N` — показывается это число (журнал до
появления разбивки по видам). Прочерк поэтому означает именно «записей
токенов нет», а не «записаны не тем видом записи»; сумма и разбивка
показываются независимо друг от друга — число рядом с прочерком
разбивки законно.

Отсюда же случай, когда разбивка покрывает ЧАСТЬ шагов строки (часть
шагов записана обоими носителями, часть — одним): сумма тогда больше
суммы показанной рядом разбивки, и строка называет разбивочное число
явно — «токенов N (с разбивкой M: input=…, …)». Скобки при числе иначе
читались бы как его разложение и врали бы: в разрезе ролей отчёта,
который суммирует весь журнал пульта, исторические записи без разбивки
не исчезнут никогда. Форма у всех трёх мест показа одна —
`retro.tokens_detail_text`.

Провайдер RETRO попадает и в локальный кэш ретро-корпуса
(`orchestrator/retro_corpus.py`) — необязательным полем, чтобы RETRO,
закрытые до его появления, из корпуса не исчезли.

**Классы провалов** (`orchestrator/failure_classification.py`) остаются
общими: набор классов, связка транзиентных системных с минутным
бэкоффом, алерты «обрыв потока» и «session limit», обрыв повторов у
детерминированного отказа. Провайдеру принадлежат только ТЕКСТЫ —
`failure_signatures()` отдаёт кортеж `(класс, сигнатуры)` В ПОРЯДКЕ
ПРОВЕРКИ (специфичные списки обязаны перехватывать текст раньше общего
якоря своего CLI) и `required_cli_version(text)` извлекает требуемую
версию CLI из текста отказа.

## Провайдер codex

Второй исполнитель роли — OpenAI Codex CLI (`codex exec`), реализация
`orchestrator/providers/codex.py`. Ни одна роль на него не переведена:
провайдер заведён, но ярусов на его модели нет, и ни один шаг пульта в
него не заходит, пока Оператор этого не сделает сам.

**Инструмент необязательный.** Запись в реестре провайдеров сама по себе
не делает CLI обязательным: `REQUIRED_TOOLS` несёт только `git`, `gh` и
CLI провайдера по умолчанию, а `codex` дописывается в сегодняшний
манифест (`stack.required_tools()`) ровно тогда, когда ярус хотя бы одной
agent-роли разрешается в модель раздела `codex` каталога. Пульт без
Codex проходит `doctor` и `check_stack()` как до его появления. Как
только ярус на его модель указал, отсутствие бинарника — красная строка
`doctor` и отказ `run`/`auto` ДО старта агента, с именем ненайденного
инструмента.

**Установка CLI.** Codex CLI ставит Оператор на свою машину сам — пульт
его не устанавливает и не обновляет. Минимальная версия — `0.155.1`
(`orchestrator/providers/codex.py::CLI_MINIMUM` и `min_cli_version`
раздела `codex` каталога `models.yaml`; числа не дублируются прозой —
они живут в этих двух местах). Установленную версию пульт спрашивает у
`codex --version`, а не у `claude --version`: версия чужого CLI дала бы
зелёный предполёт и провал попытки за деньги.

**Вход по подписке ChatGPT.** Ключа API у ролей на Codex нет: решением
Оператора 22.09.2026 (`docs/research/providers-codex-plan.md`, раздел 6
п.1) роли авторизуются подписочным входом. Причина не только
экономическая — зелёная строка `doctor` по наличию ключа в слоте
авторизацию не доказывала вовсе: `codex exec` читает ключ из
`CODEX_API_KEY`, а слот отдавался шагу под именем `OPENAI_API_KEY`
(живая проверка 22.09, `docs/research/codex-live-check-2026-09-22.md`).

Вход задаётся двумя парами — в курируемом `config.toml` дома роли и теми
же `-c`-флагами команды шага: `cli_auth_credentials_store = keyring`
(токены лежат в системной связке ключей) и `forced_login_method = chatgpt`
(способ входа принудительный, иначе CLI молча ушёл бы на ключ API).

**Что хранится и как обновляется.** Токены входа хранит и продлевает сам
Codex CLI в связке ключей; пульт их не читает, не пишет и не видит, а в
`.artel/home/.codex/` их нет — дом роли эфемерен. Продление CLI делает
сам, пока вход жив. **Повторный вход** нужен в двух случаях: срок входа
истёк (CLI перестал продлевать — тогда краснеет строка
`codex-chatgpt-auth`) и дом роли пересоздан (`init` после потери
`.artel/home`: указатель связки ключей живёт в
`.artel/home/Library/Preferences`, вместе с домом он исчезает).

**Два однократных шага Оператора.** Первый — указатель связки ключей для
дома роли. Без него OAuth-вход в изолированном `HOME` не сохраняется
вовсе (`persist_failed`, живая проверка 22.09); пульт этого шага не делает
(автоматическая установка указателя при развёртывании дома — отдельная
задача):

    HOME=.artel/home security default-keychain -d user -s <путь связки>

Второй — сам вход, с домом роли и теми же двумя парами, что несёт команда
шага:

    HOME=.artel/home CODEX_HOME=.artel/home/.codex codex \
      -c cli_auth_credentials_store=keyring \
      -c forced_login_method=chatgpt login

**Что исключено из окружения шага.** Ни `OPENAI_API_KEY`, ни
`CODEX_API_KEY`, ни `CODEX_ACCESS_TOKEN`: ни одного из этих имён нет в
белом списке манифеста (`stack.ROLE_ENV_ALLOWLIST`), а
`CodexProvider.environment` отдаёт шагу РОВНО `HOME` и `CODEX_HOME`
курируемого дома и keychain не спрашивает ни разу. Любое из трёх имён,
оказавшееся в собранном окружении шага, — красная строка
`codex-isolation-smoke` с именем переменной (без значения). Прежнюю запись
keychain с ключом OpenAI, если Оператор заводил её раньше, пульт не читает
и не удаляет: именованного адреса того слота в коде больше нет (её имя
осталось только в отчёте живых проверок,
`docs/research/codex-live-check-2026-09-22.md`).

**Чего проверка не доказывает.** `codex-chatgpt-auth` зовёт `codex login
status` с домом роли и теми же парами авторизации и зеленеет только при
коде выхода 0 И подтверждённом входе ChatGPT (кодом 0 CLI отвечает и на
«не вошёл», и на вход ключом API). Вывод CLI в строку `doctor` не попадает
— в нём адрес связки ключей и состояние авторизации. Остаток лимита
подписки эта строка не доказывает: живой запрос она не делает, и
исчерпанный лимит останется зелёным до первого настоящего шага (проверка
остатка — отдельная задача линии).

**Дом роли.** Референс — `docs/reference/role-home/codex/` (`config.toml`
и `AGENTS.md`); `init` разворачивает его в `.artel/home/.codex/`, и
именно туда смотрит `CODEX_HOME` процесса роли. Расхождение развёрнутого
слоя с референсом `doctor` называет жёлтой строкой `codex-role-home` —
отдельной от строки дома Claude, иначе расхождение одного из двух домов
схлопывалось бы с другим и оставалось незамеченным.

Развёртывание делает РОВНО холодный старт:
`catalog._deploy_role_home_reference` выходит первой же строкой, если
`.artel/home` уже существует, — то есть на живом пульте `.codex/` из
референса сам не появится. Хуже того, первое же обращение
`CodexProvider.environment` создаст `.artel/home/.codex/` ПУСТЫМ (CLI,
не нашедший `CODEX_HOME`, завёл бы каталог сам, и пульт о нём не знал
бы), и второй рубеж изоляции — курируемый `config.toml` — у шага будет
отсутствовать: держать изоляцию останутся только флаги самой команды
шага. Порядок доведения дома на работающем пульте — руками Оператора,
одной копией:

    cp -R docs/reference/role-home/codex/. .artel/home/.codex/

Проверка — та же жёлтая строка: пока `.artel/home/.codex/` пуст или
отличается от референса, `doctor` печатает `codex-role-home` с перечнем
расходящихся файлов; зелёной она станет, когда копия совпадёт. Пока
каталога нет вовсе, строка зелёная и говорит «курируемый слой ещё не
развёрнут» — это состояние пульта, который Codex не пользуется.

**Что выключено и почему.** Причина не теоретическая: живой запуск
0.155.1 с пользовательским конфигом Оператора в песочнице `read-only`
позвал MCP-сервер `cua_repl` («Computer Use») и попытался открыть
браузер на машине Оператора — не вышло только потому, что браузера не
было. Поэтому у шага роли выключено:

- песочница — `workspace-write` (запись только в рабочем каталоге шага);
- сеть песочницы — `sandbox_workspace_write.network_access = false`
  (всё сетевое идёт объявленными инструментами пульта, не самим CLI);
- политика подтверждений — `approval_policy = never` (роль исполняется
  headless, спрашивать некого);
- одиннадцать функций, включённых в 0.155.1 ПО УМОЛЧАНИЮ: `apps`,
  `browser_use`, `browser_use_external`, `browser_use_full_cdp_access`,
  `computer_use`, `in_app_browser`, `plugins`, `remote_plugin`,
  `plugin_sharing`, `skill_mcp_dependency_install`, `hooks`. `hooks`
  выключены наравне с остальными намеренно: хук, включённый ради
  запрета, сам становится исполняемым кодом в доме роли;
- MCP-серверов в курируемом доме нет ни одного.

Каждое из этих значений стоит ДВАЖДЫ — в `config.toml` курируемого дома
и флагом самой команды шага (`--disable <функция>`, `-c ключ=значение`,
`--sandbox workspace-write`). Это не избыточность: `.artel/home`
эфемерен (ADR-0005 п.3) и курируется руками, а команду шага собирает
код. Совпадение обеих половин и целость каждого пункта сверяет
офлайн-смок `doctor` (строка `codex-isolation-smoke`) — на реально
собранных команде и окружении, а не на своей копии списка флагов. Он же
жёлтой строкой называет секрет ДРУГОГО провайдера, оставшийся в
окружении шага из общего белого списка манифеста.

**Чужой секрет в шаге.** Белый список переменных окружения
(`stack.ROLE_ENV_ALLOWLIST`) общий на пульт, а не свой у каждого
провайдера: секрет, заданный Оператором для одного исполнителя,
копируется в окружение КАЖДОГО шага. Сегодня такой секрет в списке один —
токен подписки Claude, и он достаётся шагу на Codex; называет его
`codex-isolation-smoke` жёлтой строкой. Обратной стороны у этой пары
больше нет: ключ API OpenAI из белого списка ушёл вместе с каналом ключа,
и `foreign-provider-secrets` (жёлтая, с именами переменных и без единого
значения) на шаге роли на Claude его не называет — чинить там нечего.
Строка при этом остаётся: реестр провайдеров открыт, и следующий
исполнитель со своим секретом в списке попадёт в неё записью в реестр.
Предупреждение, а не отказ: сузить белый список по провайдеру можно только
правкой `orchestrator/runner.py`, и это отдельная задача линии.

Живой смок Codex обычный прогон `doctor` НЕ запускает
(`live_smoke_in_doctor = False`): вызов платный, а роли на Codex ещё
нет. Запустить его сегодня НЕЧЕМ: `live_smoke_command` зовётся ровно из
`doctor._live_smoke_run`, который при этом флаге выходит раньше сборки
argv, а отдельной команды пульта для явного запуска нет. Вход к нему
заводит задача линии, где живой запуск Codex нужен для канарейки и
калибровки расхода; разбор вывода, без которого итог живого вызова нечем
прочитать, у провайдера уже есть.

**Как перевести роль на Codex.** Нужны ОБЕ половины — модель и
исполнитель, и они живут в разных файлах:

1. модель — ярус локального слоя `.artel/models.yaml` (вне git, свой у
   каждого пульта): выбери модель раздела `codex` каталога и поставь её
   ярусу роли — `tiers: {strong: gpt-5.6-terra}`;
2. все модели раздела имеют `status: experimental`, поэтому разреши её
   явно: `allow_experimental: {gpt-5.6-terra: true}`;
3. исполнитель — поле `provider: codex` у этой роли в `roles.yaml`. Путь
   защищённый (`config.PROTECTED_PATHS`): меняет его только Оператор
   отдельным MR, роль конвейера своей веткой — нет;
4. вход по подписке — два однократных шага Оператора выше (указатель
   связки ключей для дома роли, затем `codex login` с домом роли); без
   первого вход не сохраняется;
5. `python3 orchestrator/artel.py doctor` — с этого момента `codex` стал
   обязательным инструментом манифеста, и строка про него обязана быть
   зелёной, как и `codex-chatgpt-auth`, `codex-role-home`,
   `codex-isolation-smoke`, `model-provider-cli`.

Пункт 3 не формальность и не «заодно». Исполнителя шага выбирает именно
поле `provider:` (`providers.for_role`, `runner`), а модель — цепочка
«роль → ярус → модель → провайдер»: ярус на `gpt-5.6-terra` при
`provider: claude` отправил бы шаг в `claude --model gpt-5.6-terra` —
оплаченная попытка, отказ от чужого CLI и расход, учтённый по тарифу
OpenAI. Поэтому расхождение двух половин пульт считает ошибкой
конфигурации: строка `model-provider-cli` краснеет в `doctor` и
БЛОКИРУЕТ шаг этой роли до старта агента, называя роль, её исполнителя и
провайдера модели. Обратный порядок правок (сначала `roles.yaml`, потом
ярус) даёт то же расхождение зеркально и останавливается той же строкой
— спокойнее менять обе половины одним заходом.

**Разбор вывода и источник стоимости.** Строки `codex exec --json`
переводит в событие общего вида `CodexProvider.parse_output_line`. Видов
события пять: `thread.started` и `turn.started` — служебные, пульту
сказать по ним нечего; `item.started` и `item.completed` — вызовы
инструментов и их результаты; `turn.completed` — итог запуска. Вызов и
его результат связаны ИДЕНТИФИКАТОРОМ элемента (`item.id`):
`item.started` даёт вызов (имя инструмента и ключевой аргумент —
команду, запрос, аргументы MCP), `item.completed` того же
идентификатора — результат (текст `aggregated_output` у команды, тело
ответа у MCP). Признак ошибки результата берётся из `status: failed`, а
НЕ из поля `error`: живой запуск 0.155.1 завершил вызов MCP состоянием
`failed` при `error: null`. `agent_message` отдаёт сказанный словами
текст; `reasoning` не отдаёт ничего — как и блок мышления у Claude.
Незнакомый вид события или элемента (`item.updated`, `item.type=error`
при переключении транспорта) — пустое событие: не ошибка, не исключение
и НЕ провал шага. Строка, не разобравшаяся как JSON-объект (stderr,
трейсбек CLI), уходит в лог шага целиком — молча не глотается ничего.

Итог запуска несёт разбивку токенов по четырём общим видам цены и
никакой стоимости: **цены от CLI нет** (`usd is None`, отличимо от
нулевой цены) — `codex exec --json` доллары не считает. Поэтому расход
шага считает пульт по ДЕЙСТВУЮЩЕМУ тарифу модели: раздел `codex`
каталога объявил `cost_from_cli: false`, и учёт идёт той же веткой
`spend.charge_step`, что описана выше в «Стоимость при
`cost_from_cli: false`» — запись «agent cost KNOWN» с
`источник=расчёт по тарифу`, без `actual_usd=` и без коэффициента сверки.
Арифметика разбивки не совпадает со счётчиками Claude и потому
перечислена явно: `input` = `input_tokens` МИНУС `cached_input_tokens`
(кэшированный вход входит в `input_tokens`), `cache_read` =
`cached_input_tokens`, `cache_write` = `cache_write_input_tokens`
(поля нет — ноль), `output` = `output_tokens` БЕЗ
`reasoning_output_tokens` (токены рассуждений — часть выхода). Неполный
`usage` — расход НЕИЗВЕСТЕН, а не нулевой: шаг уходит в «agent cost
UNCHARGED» с алертом, потому что ноль в `spent_usd` выглядел бы учтённым
шагом.

**Сигнатуры провалов — механизм без текстов.** Набор
`CodexProvider.failure_signatures()` свой и сегодня ПУСТ: тексты, которыми
Codex CLI сообщает о лимите подписки, неверном входе, недоступной модели
и обрыве, снимаются с живых случаев отдельной задачей линии — выдумывать
их пульт не вправе. Поведение по умолчанию от этого не страдает: провал,
чей текст не совпал ни с одной сигнатурой, остаётся неклассифицированным
и идёт в повтор с бэкоффом (как «системный кандидат» у Claude), а не в
детерминированный отказ шага. Набор Claude здесь не переиспользуется:
его слов Codex не произносит, а класс детерминированного отказа оборвал
бы повторы шага на чужом тексте. По той же причине пуст перечень
регулярок `required_cli_version` — своя формулировка Codex о минимальной
версии появится вместе с остальными текстами.

## Паритет безопасности роли: запрет у Claude → чем закрыт у Codex

Защита роли — не текст правил, а песочница провайдера плюс гейты пульта
(ADR-0017). Правила в брифе и в доме роли объясняют, а отказывают
механизмы: у Claude — флаги команды шага и `deny`-правила курируемого
`settings.json`, у Codex — песочница `workspace-write`, `--disable`
выключенных функций и `-c`-переопределения, продублированные в
`config.toml` дома роли. Механизмы разные, и совпадают они не везде:
таблица ниже несёт по строке на каждый запрет роли на Claude и честно
говорит, где паритета нет.

Строка «не закрыт» означает буквально «у исполнителя этого рубежа нет» —
не «нам всё равно»: у `codex exec` нет ни правил `deny` на чтение, ни
хуков на вызовы инструментов, а песочница `workspace-write` ограничивает
ЗАПИСЬ, но не чтение. Такие строки называют, чем состояние компенсируется
после шага.

| Запрет у роли на Claude | Чем закрыт у Claude | Чем закрыт у роли на Codex | Проверка doctor |
|---|---|---|---|
| Файлы вне рабочего каталога | `--permission-mode acceptEdits`: правка вне рабочего каталога ждёт подтверждения, которого в шаге дать некому | песочница `workspace-write` флагом команды шага: запись за границей рабочего каталога отказана самим CLI | `codex-isolation-smoke` |
| Сеть | белый список инструментов `--allowedTools Bash(git:*),Bash(python3:*)`: сетевое идёт только объявленными инструментами, не самим CLI | `sandbox_workspace_write.network_access = false` — и в `config.toml` дома роли, и флагом `-c` команды шага | `codex-isolation-smoke` |
| Связка ключей и секреты | `deny Bash(security find-generic-password:*)` и `deny Bash(openssl enc -d:*)` в `settings.json` дома роли | ключа API у шага нет ни под одним именем (`environment()` отдаёт РОВНО `HOME`/`CODEX_HOME` курируемого дома, keychain не спрашивается), а окружение шага сужается по провайдеру — чужой токен подписки в него не попадает | `codex-isolation-smoke`, `foreign-provider-secrets` |
| Инструменты и MCP | `--allowedTools` вместо полного Bash и `--strict-mcp-config`: ноль MCP-серверов независимо от `.mcp.json` рабочего каталога | MCP-серверов в курируемом `config.toml` дома роли нет ни одного; `plugins`, `remote_plugin`, `plugin_sharing`, `skill_mcp_dependency_install`, `apps` выключены флагами `--disable` команды шага | `codex-isolation-smoke` |
| Хуки | `--setting-sources` без `project`/`local`: клиентские хуки рабочего каталога не резолвятся | `--disable hooks` флагом команды шага и `hooks = false` в `config.toml` дома роли; своего хука-стража у роли нет намеренно — включённый ради запрета, он сам стал бы исполняемым кодом дома роли | `codex-isolation-smoke` |
| Чтение user-слоя Оператора | `HOME` и `CLAUDE_CONFIG_DIR` переписываются на курируемый дом роли ВСЕГДА, не `setdefault` | `HOME` и `CODEX_HOME` переписываются так же всегда; `--ignore-rules` флагом команды шага снимает правила чужих каталогов, курируемый `AGENTS.md` дома роли остаётся | `isolation-smoke`, `codex-isolation-smoke`, `codex-role-home` |
| Пул канарейки | `deny Read(~/.artel-canary/**)` в `settings.json` дома роли — отказ CLI до чтения | **не закрыт**: правил `deny` на чтение у `codex exec` нет, а песочница чтение за границей рабочего каталога разрешает. Компенсирует гейт пульта ПОСЛЕ шага: логи шагов ролей обоих провайдеров проверяются на имя каталога пула, совпадение — отказ и incident-алерт | `canary-pool-leak` |
| Посторонние файлы и защищённые пути | правило скила плюс гейты после шага: guard посторонних файлов, гейт зон, гейт защищённых путей | **не закрыт** у исполнителя: инструментов-фильтров по путям у `codex exec` нет, песочница разрешает запись всюду в рабочем каталоге. Компенсируют те же гейты после шага — они общие на оба провайдера и от исполнителя не зависят | — (гейты выхода из `in_dev` и мержа, не строка `doctor`) |

Две последние строки — оба «не закрыт» — объясняют, почему у Codex нет
аналога хука `bash_guard.py`: рубеж, который у Claude стоит ДО действия
роли, у Codex стоит ПОСЛЕ шага, и держат его гейты пульта, а не CLI. Это
принятый размен, а не недоделка: хук в доме роли — исполняемый код в
эфемерном каталоге, и доверия к нему ровно столько, сколько к самому дому.

Строки таблицы стережёт `tests/test_stack_parity_table.py`: пропавшая
строка запрета и строка без подтверждающей проверки (или без честной
пометки «не закрыт») красят набор.

## Модели: каталог, ярусы, тариф

Модель, на которой идёт шаг роли, — не строка у роли, а результат
разрешения цепочки **роль → ярус → модель → провайдер** (SPEC
01M3009Y9AGGY6ZCFA7H1HJ1TD, план `docs/research/providers-codex-plan.md`
§3). Данные о моделях живут в трёх слоях, и у каждого своя причина
существовать отдельно:

1. **Каталог `models.yaml` в корне репозитория** — что пульт вообще
   умеет запускать: разделы по провайдерам (имя инструмента CLI,
   минимальная версия CLI провайдера, признак `cost_from_cli`), внутри —
   записи моделей (идентификатор, минимальная версия CLI, прейскурант
   `list_price_usd_per_mtok` по четырём видам токенов за миллион, дата
   прейскуранта, статус `supported`/`experimental`). В git, общее знание
   всех клонов; правит его Оператор командой `doc-commit`
   (`notes.DOC_COMMIT_CONFIG_PATHS`). Путь — защищённый
   (`config.PROTECTED_PATHS`): состав каталога решает, на чём вообще
   идут роли, и роль конвейера не меняет его своей веткой.
2. **Локальный слой `.artel/models.yaml`** — выбор конкретного пульта:
   `tiers:` (ярус → идентификатор модели из каталога), необязательный
   `overrides:` (собственный тариф по тем же четырём видам токенов с
   `calibrated_at` и `source`; форм записи цен принимается три — см.
   ниже) и необязательное `allow_experimental:`
   (явное разрешение модели со статусом `experimental`). **Вне git**:
   смена модели у одного пульта не должна менять её у всех клонов.
   Шаблон кладут `init` и `doctor --fix`, если файла нет; существующий
   файл ни одна из команд не перезаписывает. Образец —
   `docs/reference/models-local.example.yaml`.
3. **`roles.yaml`** — ярус роли, поле `model_tier` из закрытого перечня
   `strong | standard | cheap` у каждой agent-роли.

Разрешение цепочки — `orchestrator/models.py::resolve_role(role)`: ярус
роли, модель яруса, провайдер модели, минимум версии CLI и действующий
тариф (переопределение локального слоя, иначе прейскурант каталога) с
указанием источника. Каждое звено **fail-closed**: роль без яруса или с
ярусом вне перечня, ярус без модели в локальном слое, модель вне
каталога, `experimental` без явного разрешения — именованный отказ
`run`/`auto` ДО старта агента и красная строка `doctor`. Молчаливого
дефолта CLI больше нет: шаг agent-роли не запускается без явной модели.

Что делает Оператор:

- **сменить модель роли** — поправить `model_tier` роли приложением к
  PLAN (`roles.yaml` — защищённый путь) либо, чаще, поменять модель
  яруса в своём `.artel/models.yaml`: это правка одного пульта, ничего
  коммитить не нужно;
- **добавить модель или поправить цены/минимум версии CLI** —
  `artel.py doc-commit models.yaml --from <файл> --message "<основание>"`
  (префикс коммита `config:`) либо приложением к PLAN; дата
  прейскуранта (`price_date`) проставляется той же правкой;
- **завести собственный тариф** (прокси, скидка, свой счёт) — раздел
  `overrides:` локального слоя, с `calibrated_at` и `source`. Четыре
  цены пишутся любой из трёх форм: прямо записью модели, под ключом
  каталога `list_price_usd_per_mtok` или под `tariff_usd_per_mtok` —
  разбор принимает все три, файл пишется руками и имя ключа тут не
  повод для отказа;
- **посмотреть, что где действует** — `artel.py models`: таблица
  «провайдер, модель, статус, минимум CLI, прейскурант, действующий
  тариф и его источник, роли по ярусам», только чтение;
- **проверить слои** — `artel.py doctor`: строки `models-catalog`,
  `models-local` и цепочка «роль → ярус → модель → провайдер» в строке
  `role-providers`.

### Тариф: по нему считаются деньги

Действующий тариф модели — не справочная величина, а единица учёта: по
нему `orchestrator/spend.py` считает стоимость шага, оставшегося без
финального события потока («agent cost PARTIAL»), и сверяет расчёт с
фактом CLI на каждом завершённом шаге («agent cost KNOWN»). До 21.09
цена задавалась по РОЛИ таблицей в `orchestrator/config.py`; цена того
устройства — инцидент 13.09–20.09: роли перевели на другую модель, а
курс остался прежним молча, и учёт разошёлся с фактом в 1.5–1.9 раза.
Теперь цена принадлежит модели, а сверка считается по паре **(роль,
модель)** — строки журнала другой модели и строки старше даты
действующего тарифа в коэффициент не входят. Панель `artel.py report`
показывает коэффициент расхождения **по модели**.

**Что делает Оператор при смене цен.** Прейскурант — `doc-commit
models.yaml` (с новой `price_date`); собственный тариф пульта —
`overrides:` локального слоя (с новой `calibrated_at` и `source`).
Обе даты — точка отсчёта сверки: шаги, записанные до неё, в коэффициент
нового тарифа не войдут, поэтому дату двигают вместе с ценой, а не
«когда-нибудь потом». Дальше ничего делать не нужно: следующий же
учтённый шаг сам разрешит новый тариф, запишет его в историю и начнёт
считать по нему.

**История тарифов — таблица `model_tariffs` в `state.db`**: модель,
четыре цены, `valid_from` (дата действующего тарифа) и источник. Пульт
дописывает строку сам, когда разрешённый тариф отличается от последней
записи этой модели; совпал — не пишет. Команды записи нет и не будет:
история отвечает на вопрос «по какой цене считался шаг такого-то числа»,
и правка её руками этот ответ обесценила бы. Строки журнала «agent cost
KNOWN/PARTIAL» несут ту же дату, так что шаг и его цена сходятся по ней.

**`doctor` сторожит тариф двумя строками**: `model-tariff-age` —
действующий тариф не старше `config.MODEL_TARIFF_MAX_AGE_DAYS` (90
дней); `model-tariff-vs-model-change` — у роли нет шагов на ДРУГОЙ
модели новее даты её сегодняшнего тарифа (ровно отпечаток инцидента
13.09–20.09). Обе — предупреждения: они не мешают шагу стартовать, но
называют модель и дату, с которыми надо что-то сделать.

## Почему только стандартная библиотека

У пульта нет менеджера зависимостей и окружения для их установки —
интерпретатор, в котором стартует роль, разный в каждом месте
(локально, в CI, из PATH Оператора). Сторонний пакет, доступный в одной
среде и отсутствующий в другой, ломает конвейер молча и
непредсказуемо — код, который сегодня работает у одного участника
и падает у другого `ModuleNotFoundError`, обнаруживается не сразу и не
там, где внесена причина. Отказ от сторонних зависимостей убирает этот
класс дефектов целиком: если код запускается тем интерпретатором,
версия которого проходит `REQUIRED_PYTHON`, он гарантированно
запустится у кого угодно ещё, без установки чего-либо дополнительно.

Правило проверяется кодом, не удерживается на честном слове: тест
инварианта в `tests/test_invariants.py` разбирает `orchestrator/`,
`scripts/`, `tests/` через `ast` и падает на любом импорте модуля вне
стандартной библиотеки (`sys.stdlib_module_names`), вне пакетов
репозитория и вне `orchestrator.stack.THIRD_PARTY_EXCEPTIONS`.

## Как проверить

- `python3 orchestrator/artel.py version` — печатает фактическую версию
  Python исполнителя и результат `orchestrator.stack.check_stack()`
  (по строке на Python/`git`/`gh`/`claude`: `ok`, `WARN` при версии
  ниже минимальной или `FAIL`, если инструмента нет в PATH; плюс по
  строке на каждую agent-роль — модель берётся разрешением цепочки,
  `ok`/`FAIL` по минимуму версии CLI из каталога, `FAIL` для
  неразрешимой цепочки).
- `python3 orchestrator/artel.py doctor` — та же проверка стека в
  общем списке проверок `doctor` (`orchestrator/doctor.py::all_checks`
  подключает `orchestrator.stack.check_stack()` одной строкой).
- `python3 -m unittest tests.test_stack` — постоянная регрессия
  манифеста и `check_stack()`.

`check_stack()` не обращается к сети — сравнение идёт локальным
вызовом `<инструмент> --version` (docs/invariants.md, инвариант 35).
